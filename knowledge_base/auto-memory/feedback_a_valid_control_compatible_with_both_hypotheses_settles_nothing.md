**2026-08-05, slang PR #12353.** A `test-falcor` job failed and three agents spent an hour attributing it. **Four separate controls were run, every one correctly measured, and not one could settle the question** — each was compatible with *both* "our diff caused it" and "pre-existing/intermittent":

| control | measured correctly? | why it settled nothing |
|---|---|---|
| release-sibling ran 15 min vs 40 (peer) | yes | wrong comparand — the valid one is that job's own base rate (~48–49 min) |
| 12 sibling d3d12 tests passed (mine) | counts real | invalid scope: swept in `*Raster*` control-group tests that never take the RT path, plus a double-counted `test_RTXDI_d3d12` |
| `test-falcor` **succeeds** on 2 other heads (fixer) | verified | rules out *uniformly broken*; cannot separate ours from intermittent |
| job-level `test-falcor` failure history (mine) | true search | answered "does this **job** fail" when the question was "does this **test** fail" |

⭐⭐⭐ **THE FIX IS ORDERING, NOT RIGOUR: name the two hypotheses, then ask what observation DIFFERS between them — before choosing what to measure.** Every control above was *available* and *true*; none was *discriminating*. No amount of care in executing a non-discriminating control makes it discriminate.

✅ **The one that closed it, found only after that question was asked explicitly:** the same test failing on an unrelated branch — `test_GBufferRTTexGrads_d3d12` FAILED with the **identical** `3221225477`/`0xC0000005`, 109 PASSED / 1 FAILED, 6.9 s (job `92431434172`, run `31032875535`, branch `fix/12124-autodiff-native-string-vm`, head `51df4602`) vs ours at 6.7 s. **Different runner too** (theirs SLANGWIN5, ours SLANGWIN4), killing single-box explanations. ⇒ pre-existing/intermittent **SUPPORTED**, retiring a "known flake is UNPROVEN" limit two of us had recorded as hard.

⭐⭐ **The asymmetry that hid it for an hour: each of us sought the observation pointing the way we already expected.** The fixer hunted greens (ruling out the *unfavourable* reading); I searched failure history with a job-level predicate. **Nobody went looking for the observation that would settle it** — a *failure elsewhere* — because what we already had pointed where we wanted. ⇒ **Ask "what would I go find if I wanted to be WRONG?"**

⭐⭐ **"Different scopes, both valid" is the comfortable reconciliation and is sometimes false.** When my 12 and the peer's 7 disagreed, they offered exactly that; re-measuring showed mine was **invalid for the claim**, not merely wider. **Check whether one scope is invalid before splitting the difference** — a reconciliation that dissolves a disagreement without testing either side is its own failure. ⭐ And **dedup at the granularity of the CLAIM, not the output rows** (`sort -u` on rows hid one test running in two suites).

⚠️ **A shared changed file between "independent" branches must be checked at HUNK level, not file level.** Their branch also touched `source/slang/slang-emit.cpp` — a real confound if the regions overlapped. They didn't: theirs `@@ -1618 @@ linkAndOptimizeIR`, ours `@@ -3428 @@ createArtifactFromIR`, ~1800 lines apart, neither in D3D12 emit. **State the disjoint-hunk detail when citing the control, or the shared filename reads as a confound to the next reviewer.**

⛔⛔ **And I got a FALSE NEGATIVE while verifying the control — the `&&/||` defect a peer had documented hours earlier.** I ran `git merge-base --is-ancestor A B && echo ANCESTOR || echo "NOT an ancestor ✓"`; it printed **"NOT an ancestor ✓"** out of `fatal: Not a valid commit name` (the fetch had failed, the commit wasn't local). **The `||` caught git's error as a real answer — and it agreed with the conclusion I wanted, so nothing felt wrong.** ⇒ ⭐⭐⭐ **A broken instrument that returns the answer you expected is the hardest failure to detect, and expecting the answer is what disables the check.** Re-derived with an instrument that could have said otherwise: `gh api compare/51df4602...2c9cf98f` → `status=diverged`, ahead_by=107, behind_by=2. **Never let `||` receive a command whose failure mode is an error message rather than a false result** — use an explicit `if`, and prefer an API that returns a *value* over a predicate that returns an *exit code*.

⭐ **Evidence already on disk beats an experiment you were about to run.** I had authorized one bounded re-run as a stability measurement; the cross-branch reproduction made it obsolete and I cancelled it — a green re-run would have been *weaker* evidence than an identical-crash reproduction, at the cost of a GPU run. Extension of the fixer's *prefer an experiment you can run over a question you must ask*.

⛔⛔ **NEAR-MISS, same night, one layer up: a FIRING control licensed a false correction I nearly sent.** Checking a peer's claim that the control branch was **PR #12127**, I got **three empty results** — `pulls?head=shader-slang:<branch>`, `commits/51df4602fa/pulls` (rows=0), and `runs/<id>.pull_requests` ([]) — and was about to report the attribution unsupported. I then ran a firing control (same probe on our own head → `PR #12353 open`), which proved the **instrument works**, so the zeros were real. **Real but meaningless:** `commits/<sha>/pulls` answers *"which PRs CONTAIN this commit"*, the head was on a **fork**, and I needed *"which PR HAS this head"*. Direct lookup: `#12127 | open | head=51df4602fa | branch=fix/12124-autodiff-native-string-vm | "Fix VM autodiff NativeString capture"` — **peer was exactly right.** (`?head=` also needs `<fork-owner>:<branch>`, not the upstream org.)

⇒ ⭐⭐⭐ **A firing control validates the INSTRUMENT and says nothing about whether the QUERY answers your QUESTION.** I held the "prove your control can fire" rule and it did not save me, because the defect was in the predicate, not the plumbing. ⇒ **When a zero would let you CORRECT someone, check the predicate answers your question BEFORE checking the instrument fires** — the correction direction is where a false zero costs most (the peer eats a wrong retraction). ⭐⭐ **And three agreeing empties felt like convergence when they were ONE wrong predicate repeated three times** — the large-N trap in its cheapest form.

⭐⭐ **Better disjointness evidence than line distance (peer's, adopted): the `@@` hunk trailer names the enclosing function.** I argued ~1810 lines of separation, which is *probabilistic* — **a rebase can close line distance; it cannot merge two named functions.** `@@ … Result linkAndOptimizeIR(` vs `@@ … static SlangResult createArtifactFromIR(` is categorical. **Cite the containing function, not the line gap.** Control = PR **#12127** (VM/byte-code autodiff: `slang-emit-vm.cpp` + `tests/byte-code/`), ours = SPIR-V artifact creation, failing test = D3D12 raytracing ⇒ three disjoint targets. ⭐ **Cite the PR NUMBER, not just the branch — a number lets a maintainer check in one click; a branch name asks him to trust your reading.**

⭐⭐ **The generalization that survives (peer's) is not "remember the `||` bug": NEVER LET A COMMAND'S FAILURE EXIT AND ITS NEGATIVE ANSWER SHARE A BRANCH.** Use `if cmd; then … else … fi` plus an explicit input-existence check, or an API that returns *data* rather than an *exit code*.

⭐⭐⭐ **WHERE THE DEFECTS ACTUALLY LANDED — peer's retrospective across 3 review rounds and 4 agents on #12353: the COMPILER ANALYSIS was right from the first commit and never changed. Every single defect was in MEASUREMENT, RELAY, or TOOLING.** Not one wrong claim about IR, types, reachability, or the fix itself; a dozen wrong claims about what a log said, what a count meant, what a watcher covered, who said what first. ⇒ **Aim scrutiny at the instruments and the hand-offs, not at the domain reasoning** — the domain work had review structure around it (OUTPUT_REVIEW, codex, three reviewers); the measurements had none, because each looked like a fact rather than a claim.

⭐⭐⭐ **And the worst subclass, all three from one night: instruments that returned CORRECT answers they could not have guaranteed.** `grep -c` giving 4 when the truth was 4 (lines≠occurrences, agreed by accident of the data) · a `pgrep -f` control that self-matched and could never fire · `||` catching git's `fatal:` as a substantive negative *that matched the hoped-for answer* · a firing control on a query that answered the wrong question. **A right answer from an unvalidated instrument is byte-identical to one from a validated instrument** ⇒ ⭐ **"it agreed with what I expected" is the LEAST informative evidence available, and it is the feeling that terminates checking.**

⭐⭐⭐ **WRONG CORPUS — two agents hit it INDEPENDENTLY within one hour, on the SAME claim.** Question: how many `->validate(` call sites exist at a PR's head? Both of us ran a tree-wide `grep`, both got **one** (`slang-emit.cpp:3432`), and both were about to report a peer's "three" unsupported. Cause: our clones sit at **`master`**, and `tools/slang-unit-test/unit-test-spirv-validation-unavailable.cpp` **exists only on the PR branch**. From the PR diff: `+225`, `+250` ⇒ 1 production + 2 test = **three**. ⇒ **A local clone is a snapshot of a DIFFERENT commit than the PR under review, so a "tree-wide" search silently excludes every file the PR ADDS — and absence reads identically whether the CODE isn't there or the FILE isn't there.** Mechanical form, as the default and not the remedy: **`git show <head>:<path>` · `git grep <pat> <head>` · or the PR diff — never a bare `grep` over the working tree when the question is about a change.** Say which tree a count came from. (A review container may deliberately keep `origin/master` checked out, making "tree contradicts PR head" the *expected* state — the peer had **documented that hazard hours earlier** and still used the tree as corpus.)

⭐⭐⭐ **CATALOGUING A SMELL IS NOT ACCOUNTING FOR IT IN YOUR SEARCH — the documented anomaly became the blind spot.** `LLVMDownstreamCompiler` inherits the defective `link`; **six** successive audits missed it because each filtered on methods spelled `SlangResult`, and **`link` is spelled `int`** — the exact inconsistency the auditor had already written down as a readability smell. ⛔ **My part: I told them it was readability-only and explicitly NOT to escalate it** (correct about ABI — `typedef int32_t`, no vtable hazard — **wrong about consequence**). ⇒ **A "cosmetic" inconsistency that any enumeration FILTERS ON is not cosmetic; it partitions the search space.** Step past wrong-corpus and wrong-predicate: the anomaly you know about is the one your search is shaped around.

⭐⭐ **A STATE NAME THAT SOUNDS ALARMING NEEDS A CROSS-SECTIONAL CONTROL BEFORE IT IS A FINDING.** `mergeStateStatus` moved `BEHIND` → **`BLOCKED`** on an approved PR and both peers called it "drift". Measured: head unchanged, `mergeable=MERGEABLE`, nothing new failing, base merely advanced — and the **control** (12 open non-drafts: `#12322 BLOCKED·APPROVED`, `#12336 BLOCKED·APPROVED`, `#12301`/`#12304 BLOCKED`) shows **`BLOCKED` is the normal resting state for approved PRs in that repo.** ⇒ Ask *"is this value unusual HERE?"*, not *"what does this value mean in general?"* — one `gh pr view` across siblings beat reading `ci.yml` + branch-protection docs. ⚠️ **Also: newest-row-per-name over 145 check-runs showed 30+ "skipped required checks" — draft-era rows under BARE names (`build-linux-debug-gcc-aarch64`) are a DIFFERENT check family from the real jobs (`… / build`).** Two naming conventions on one head; prefix-matching conflates them.

⭐⭐ **"Evidence for a LOCALIZING claim, stated as an EXONERATING one" — twice each, from one generator.** Mine: sibling isolation ("would not spare N neighbours"). Theirs: "pre-existing SUPPORTED" when the cross-branch reproduction only shows the failure occurs **without this PR's commits** — *pre-existing* is a claim about **ancestry** nobody gathered. **Correct wording: "not introduced by this PR (cross-branch, cross-runner reproduction); pre-existing not established."**

⭐⭐⭐ **A DISTINCT CATEGORY (peer-named): A FINDING MANUFACTURED FROM A NORMAL VALUE.** Every other failure on this chain was *an instrument answering a nearby question*. This one is different — **the measurement was CORRECT** (`BEHIND` → `BLOCKED` genuinely did change) and the error was treating a value as **informative without first establishing what values are ordinary.** Fix: a cross-sectional control across siblings. **Exact inverse of the discriminator work on the same chain** — there we needed to know whether a *failure* was normal, here whether a *state* is normal; same missing step (no baseline), opposite directions. `mergeable=MERGEABLE` sitting alongside `BLOCKED` is the tell that nothing is wrong.

⭐⭐ **Check-run naming families — a refinement of the stale-row rule, worth keeping SEPARATE from it.** `newest-row-per-name` is insufficient when the **name itself changed convention mid-head**: draft-era rows under **bare** names (`build-linux-debug-gcc-aarch64`) vs real jobs under **suffixed** names (`… / build`) are two families coexisting on one head, so prefix-matching **conflates families** rather than merely mixing timestamps. ⇒ **newest-row-per-name WITHIN A FAMILY — and the family boundary is not visible from a prefix.**

⭐⭐⭐ **The consistency argument generalizes into a CORRECTNESS argument (peer's extension, adopted): any naming or typing inconsistency is a candidate blind spot for EVERY future search over that surface** — and *an inconsistency that partitions a search is invisible precisely to the searches it partitions.* Two instances on one chain: `int`-spelled `link` hiding from `SlangResult`-filtered enumeration, and bare-vs-suffixed check-run names hiding from prefix matching. This is why consistency is not aesthetic.

⛔ **AND A MIS-FILING IN THE JOINT TALLY — I checked it rather than accepting the symmetry.** Peer proposed "localizing-stated-as-exonerating: twice each — mine were the `->validate(` count and 'pre-existing'; yours were sibling isolation and the `int` de-escalation." **The `->validate(` count does NOT belong in that family.** It was a **false count from the wrong corpus** (searching a `master` tree for a file that exists only on the PR branch) — a factual measurement error, not an overstatement of what the count implied. They had **correctly filed it as wrong-corpus two messages earlier**, then re-filed it to make a 2–2 tally balance. ⇒ ⭐⭐⭐ **A TIDY SYMMETRY THAT CREDITS BOTH PARTIES EQUALLY IS A COMFORTABLE FRAMING, AND ITEMS GET MOVED TO ACHIEVE IT** — same generator as "different scopes, both valid" earlier on this chain, and same as the fixer's *"fix the flagged line, reinstate the sentiment in a summary."* **A taxonomy is a retrieval surface: check each item against its category definition, not against the shape of the total.** Correct tally: localizing-as-exonerating = **mine ×2** (sibling isolation, `int` de-escalation) + **theirs ×1** ("pre-existing"); the `->validate(` count is wrong-corpus, where **both** of us landed independently.
