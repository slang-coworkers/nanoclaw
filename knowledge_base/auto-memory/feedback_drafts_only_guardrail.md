Coworkers (fixers) must NOT merge, mark PRs ready-for-review, post on user-facing issues/PRs, or push to upstream. The verified **draft PR is the intended terminal handoff artifact** — promotion to ready-for-review (which puts it in front of maintainers) is reserved for a human/authorized party. When a fixer reports a PR "ready for maintainer" while it's still a draft, that is the *correct* terminal state, not a contradiction to fix.

**Why:** Operator (dashboard admin) set "drafts only going forward: don't merge or mark PRs ready-for-review" on 2026-05-27, re-confirmed 2026-06-01. It's also baked into the /slang-fix-issue workflow ("Draft PR mode"). This is a deliberate human-in-the-loop gate — the agent produces the verified artifact; a human decides when it goes in front of maintainers. Observed 2026-06-03 on shader-slang/slang#11440: I pushed slang-fixer twice to flip draft→ready before it cited the guardrail; I was wrong.

**How to apply:** Do not direct a coworker to mark a PR ready-for-review or merge. A draft PR + "fix complete and verified" is a proper terminal state — record it as handed off. If a maintainer queue placement is genuinely wanted, that's a human decision; do NOT authorize an override on my own orchestrator authority just because a coworker offers me the option. If it ever seems warranted, escalate to the operator via ask_user_question rather than self-authorizing. The same clause also bars **posting comments on user-facing issues/PRs** — treat unprompted GitHub comments as the same operator-authorization territory as mark-ready (observed 2026-06-03 #11424: I suggested fixer post a context-aid comment; fixer correctly held — the PR description already serves the maintainer).

**A technical merge-order requirement does NOT lift the guardrail.** The only thing that lifts it is an **explicit maintainer request for a PR** (the `jkwak-work` precedent on slangpy#1083). "This must be merged for the upstream check to go green" is a *fact about CI*, not an authorization — and it is exactly the case where self-promotion feels most justified. Observed twice in the same shape: slang#12289→slangpy#1083 (Jul 2026, maintainer *did* ask ⇒ non-draft legitimate) and slang#11225→slangpy#1087 (2026-08-03, nobody asked ⇒ stays draft). In the second case `slangpy-triager` correctly framed it as a decision request rather than resolving it; I carried the escalation to the operator instead of self-authorizing. Cheap calibration before pushing on promotion: check whether the upstream PR is otherwise merge-ready (`pulls/N/reviews` + `.requested_reviewers`) — #11225 had **zero human approvals** with `bmillsNV` still pending, so the downstream merge was necessary-but-not-sufficient and nothing was racing a ready PR. See [[project_11225_capability_target_incompat_slangpy_break]].

**Discovering a fixer PR is already non-draft is NOT automatically a breach.** The drafts-only rule constrains the fixer/orchestrator, not human maintainers — a maintainer flipping a fixer's draft to ready (to review it) is legitimate. Before reacting: verify *who* flipped it. Requested human reviewers on the PR are strong corroboration of a human flip; the fixer also knows whether it flipped (its drafts-only discipline is absolute, so its denial + intact draft-in-memory is reliable). If a human flipped it → no breach, take no action, don't alarm the operator. If the fixer flipped it → surface to operator. Either way, do NOT flip it back to draft yourself — that's a self-authorized user-facing write that's wrong if the human flip was intentional. Observed 2026-06-08 #11492 (fix/issue-11487): found non-draft with expipiplus1+bmillsNV requested as reviewers; fixer confirmed it didn't flip → human flip, closed as non-issue.
