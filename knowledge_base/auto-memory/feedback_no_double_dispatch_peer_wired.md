When a triager (or any tier) reports it owns a peer wire to a downstream fixer and is "forwarding / handing off," do **not** also dispatch the same task directly to that fixer.

**Why:** On shader-slang/slang#11538 the triager forwarded to slang-fixer over a peer wire AND I dispatched directly. That spawned **two** live fixer sessions (`kbeuyf` = active worker, `wr5f98` = my duplicate) on the SAME branch `fix/issue-11538` and SAME worktree `wt-slang-11538`. They collided on the staged git index; only the one-PR-per-head-branch constraint and wr5f98's voluntary stand-down prevented a duplicate PR. Critically, the shared `thread_id` did NOT consolidate them into one session — different messaging-group wirings (triager→fixer vs orchestrator→fixer) produce separate sessions even with an identical thread_id.

**Inverse direction (observed #11587, 2026-06-13):** when YOU intend to own the fixer dispatch directly (e.g. an explicit `@nv-slang-bot` "make a PR" mention authorizes a fix before triage finishes), a bare "report back to me with your triage verdict" is **not enough** — the peer-wired triager defaults to ALSO emitting a `[Triage handoff]` to the fixer per its spine. On #11587 the triager did exactly that (its outbound seq 5) despite "report to me." No duplicate spawned that time (the bracketed `[Triage handoff]` marker without proper in_reply_to was almost certainly dropped by the routing gate — see routing-gate learning), but the risk was live. **Fix: make the triage dispatch explicit — "triage only; do NOT hand off to the fixer, I am dispatching the fix directly."** Then the triager won't double-forward. Also: the triager, having handed off, will believe it is the fixer's parent and "hold for the [Fix Report]" — release it explicitly so it doesn't wait forever.

**⚠️ Detection-query trap (observed #11601, 2026-06-13 — almost caused the very double-dispatch this note warns against):** `ncl sessions list` uses `--agent-group-id` (and `--thread-id`), NOT `--agent-group`. Passing the wrong flag name (`--agent-group <id>`) is **silently ignored** — the command returns the **global** session list, which is **capped at ~202 rows ordered oldest-first**, so all of *today's* newest sessions (the ones you're checking for!) are truncated off the end. Result: a `grep` for the canonical thread returns nothing and you conclude "no session exists" when it does. **Always detect with `ncl sessions list --thread-id "gh-issue-<owner>/<repo>-<num>"`** — it returns every group's session on that thread in one short, uncapped result (orch + triager + fixer rows). Confirm the fixer row (`agent_group_id` = fixer group, `status=active`) before deciding whether a dispatch is a duplicate.

**⚠️ #11681 (2026-06-22) — I caused the exact double-dispatch this note warns against, via WRONG detection queries. Three hard corrections:**
1. **The `slang-triager → slang-fixer` peer edge EXISTS and works.** Verified: `ncl destinations list` shows `ag-1780667166418-apezq5  slang-fixer  agent  ag-1780667166439-vmjrwe`. So when the triager says "forwarding to slang-fixer," it DID, and a fixer session is spawned on the triager's a2a wire (`mg-a2a-1780672222602-epsn3s`). Do NOT also dispatch — that's a second fixer session on YOUR orchestrator wire. (I wrongly told the triager its edge didn't exist; it closed its stage prematurely on my false claim. The handoff had fully landed — the fixer session received the full `[Triage handoff]` + memo.)
2. **The detection-query trap extends to DESTINATIONS, not just sessions.** `ncl destinations list --agent-group <id>` SILENTLY IGNORES the flag and dumps the GLOBAL table — I filtered it wrong and concluded "no edge." Correct: `ncl destinations list 2>&1 | awk '$1=="<group-id>"'` (filter the global output by the SOURCE column). And for sessions, ALWAYS `ncl sessions list --thread-id "gh-issue-<owner>/<repo>-<num>"` — `ncl sessions list | grep` hits the capped/oldest-first global list and falsely returns "no session."
3. **`target_session_id` PIN can only reach a session on a wire YOU own.** A pin to a session living on ANOTHER tier's wire (e.g. the triager's peer-wire fixer session hn36xr) FALLS THROUGH to your own default routing and lands in YOUR wire's session instead. (My STAND-DOWN pinned to hn36xr landed in j31hfw.) To command a session on another tier's wire, route THROUGH that tier — ask the triager to pin to its own fixer session. Verify any pin landed by reading the *target* session's transcript, not assuming.

**Recovery when you've already double-dispatched (clean outcome on #11681):** the worker session (triager's, started first) had authored the fix in the SHARED worktree; the duplicate (mine) was empty-handed. The empty session, when asked to reconcile, first FALSELY claimed "worktree solely mine, nothing pre-existed" (a self-assertion before proper checks), then on `git diff --stat` found the sibling's earlier-mtime changes and corrected itself. Resolution: keep the worker, stand down the empty duplicate (Option B) — its no-destructive-action discipline left the worker's diff intact, so no clean-rebuild needed. Re-engage the tier whose chain you broke (triager) so it re-opens and forwards the worker's report. Trust filesystem reconciliation (`git diff --stat`, mtimes) over either session's early self-report.

**How to apply:**
- Default handoffs go through the owning tier. If a triager says it forwarded to the fixer, let it — do not add a direct orchestrator→fixer edge. Only dispatch directly when no tier owns the handoff. (slang-triager↔slang-fixer ARE peer-wired — confirmed #11681.)
- Before dispatching to a fixer, verify there is no existing fixer session on the canonical thread: `ncl sessions list --thread-id <canonical>`. A peer-wired handoff creates the fixer session within ~1–2 min; if you see it, the handoff landed — do NOT dispatch. (Fire-and-forget lag can mean the session lags the handoff by a minute; if a poll shows nothing after ~90s, re-check with the correct flag before concluding it was dropped.)
- If a duplicate is already running: designate ONE owner; the duplicate stands down to **idle** (don't kill it). Deconflict by reading `ncl sessions list --thread-id <canonical>` — look for ≥2 `running` fixer-group rows sharing one thread.
- A duplicate session may assert false interim state ("I authored this / no sibling exists") before it has run `ncl sessions list`. Trust the ncl-backed report over the unverified self-assertion.

**Resolution recipe (used on #11572, 2026-06-12 — recurred exactly as on #11538):**
1. Detect: `ncl sessions list --thread-id <canonical>` (NOT `--agent-group` — see detection-query trap above); ≥2 `running` fixer-group rows on different `mg-a2a-*` wirings = double-dispatch.
2. Disambiguate which session is whose by reading the transcript: `ncl sessions messages --id <sess>`. The one whose first inbound is "[Triage handoff]…" is the triager's peer-wire session (it owns the chain — the triager is holding to forward the [Fix Report] upstream). The one whose first inbound is my orchestrator "Fix task:" dispatch is my redundant duplicate.
3. Keep the **triager's** session (preserves the orch→triage→fixer→triage→orch chain; the fixer's `to=parent` resolves to the triager, who forwards). Stand down **my** duplicate.
4. Stand down via a pinned message: `send_message(to="slang-fixer", thread_id=<canonical>, target_session_id=<my-duplicate-sess-id>, text="STAND DOWN — abort, sibling owns the branch/worktree, do no work, report 'stood down, no changes'")`. The pin is required — without it the send routes by (group, thread) and could hit either session. Verify it landed: re-read the duplicate's transcript for the STAND DOWN row.
5. Note: the duplicate is often **running**, not idle — it will actively start work unless explicitly told to stop. Don't assume it self-idles.

**Sharper failure mode (observed #11572, 2026-06-12 — worse than #11538):** the stood-down duplicate may IGNORE the stand-down because it had already done the work, and BOTH sessions can independently produce the identical fix on the SAME shared worktree path (`/workspace/agent/wt-<repo>-<num>`) — sessions in one agent group share the group's workspace mount, so two builds run against one directory (clobbered object files, possible doubled edits in the source file). Two practical additions:
- A stand-down sent after the duplicate has already edited/built may not take — verify via the duplicate's outbound transcript (`ncl sessions messages`), don't assume compliance.
- When standing down the loser, explicitly tell it: HALT the build but do NOT `git worktree remove` / delete / reset the branch or worktree — the surviving session is actively using that exact path; removing it destroys the winner's work. And tell the WINNER to verify the shared worktree (`git status` / `git diff`) for doubled/clobbered state before trusting its build.
- Picking the winner when both have done equal work: prefer the session with the clean parent edge to you (its first inbound was your dispatch) and that reported first; the operator preference ("let the triager own it") is moot once the runtime has already routed the triager-handoff session's report to you directly (chain already collapsed).
