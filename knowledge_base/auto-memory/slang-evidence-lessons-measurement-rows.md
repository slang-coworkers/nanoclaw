- ⛔⭐⭐⭐**TWO CHECKS OVER ONE CORRUPTED ARRAY ARE ONE CHECK — "redundant dimensions" is a claim about the DATA SOURCE, not the predicate** (08-04, MINE-MEASURED on live slang PRs; extends the WRONG-UNITS row above from *"a page default is an alarm"* to *"a page default can defeat every check derived from that page at once"*). The approver's `tier_eligible` gates PR size on **two** caps — files ≤ 150 **and** lines ≤ 8000 — and that looked like redundancy protecting the decision. It isn't, because on a truncating instrument both numbers come off the same capped array. #12345 (true: 177 files / 25,379 lines) read through three instruments: **PR API** 177 FAIL / 25,379 FAIL ⇒ abstain ✅ · **compare API** 177 FAIL / **6,335 pass** (returns all rows but zeroes 47 files' counts) ⇒ abstain, one dimension corrupt · **`gh pr view --json files`** **100 pass / 4,796 pass** ⇒ **no clause FAIL AT ALL — the bot decides a 177-file PR.** The file count *is* the cap (100 ≤ 150) and the line sum is derived from those same 100 rows. ⇒ ⭐⭐⭐**What protected the decision was an INSTRUMENT CHOICE (PR API scalar fields), not a clause property — one config change from evaporating, and the clause reports `pass`, never `unevaluable`, so nothing announces it.** ⭐⭐**Ask of any multi-check guard: do these predicates read from INDEPENDENT SOURCES? If they share one array, you have one check wearing two labels** — the guard-redundancy analogue of *a control is a claim needing its own verification*. ⭐⭐**The two APIs fail in DIFFERENT SHAPES — compare zeroes counts (rows intact), `pr view` drops rows — so a detector for one misses the other; enumerate per instrument.** ⛔⭐⭐**AND THE OBVIOUS DETECTOR OVER-REPORTS: `patch==null` is NOT the control, `changes==0` on a `modified` file is** — on #12344, `patch==null`=50 vs `changes==0`=47, converse=0; the 3 extras (`…/ast-reference/expressions/README.md` +156/−156, `…/core-module/README.md` +103/−103, `…/decorations/README.md` +90/−90) have the **patch elided but counts intact** ⇒ conflating "patch omitted" with "counts truncated" **fires on healthy input, which trains you to ignore the control** (same family as the healthy-noise row above). ✅**Fix: read caps from PR-API scalars, never sum a per-file array; tripwire on `changes==0`-while-`modified` or array-length==page-default, and FAIL TOWARD ABSTAIN.** ⚠️**No outcome has flipped yet** — #12345 abstained correctly (and merged at the decided commit `ac8179c8eb28`, 1 commit, 0 follow-ups) and #12344's true 6,851 is under its 8,000 cap — **but 6,851/8,000 = 86% of the cap is a BOUNDARY, not headroom** (cf. the near-miss row). ⭐⭐**Provenance: the approver self-corrected a polarity error here, a sibling found the compare truncation on #12344, and I measured that the redundancy was illusory — three tiers, none of which had the whole thing.**
