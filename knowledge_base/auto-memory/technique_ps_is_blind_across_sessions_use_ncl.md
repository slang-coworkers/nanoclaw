# `ps` is blind across sessions — never use it to rule out concurrent work

⚠️⭐⭐**EVIDENCE BASE: ONE CASE (2026-08-04). Hold it in proportion.** A rule derived from a single instance has been fitted to exactly one data point — *a hypothesis wearing a rule's clothing* (slang-fixer's formulation). Contrast the multi-instance rules that survived contact today (*publish the count, never the adjective* had three independent instances; *decisive: does the branch exist on my remote?* had one and **inverted on the second**). ⇒ **RE-DERIVE THIS THE NEXT TIME IT FIRES — first, not last.** If a second independent instance confirms it, say so here and delete this banner; if the second case contradicts it, the rule was the artifact of the first.


**2026-08-04, slang-fixer found it; MINE-VERIFIED on my own edge the same hour.**

Sibling sessions of the same agent group **share a filesystem/worktree volume but run in separate
containers**, so process inspection does not cross the boundary.

**My measurement, while a peer session was demonstrably mid-build** (`ncl sessions list` showed
`sess-1784330270032-ovhk89` `running`, `slangc` rebuilt 11:06:26, source newer than binary):
```
ps -e --no-headers | wc -l     → 9          ← nine processes, total
ps -e -o comm=                 → bun, node, codex, docker-init, ps, sort, uniq, head
```
**Zero `slangc`. Zero build processes. Zero peer sessions.** ⇒ **`ps` returns a confident,
well-formed, WRONG answer to "is anyone else building?"** — not an error, not an empty result you'd
distrust.

⛔⭐⭐**THE COUNTS IN THIS NOTE WERE NOISE AND I PUBLISHED THEM AS CORROBORATION (fixer-retracted, then
MINE-REPRODUCED).** I wrote "I saw 9, the fixer saw 14" as two edges agreeing. Re-measured on ONE edge,
same moment:
```
ps -e --no-headers | wc -l   → 10      ps -e | wc -l   → 11   (header)
compound pipeline            → 10      bare, again     → 10
```
⇒ **A `ps` count is UNSTABLE BY CONSTRUCTION** — it includes the header unless `--no-headers`, plus the
transient members of the measuring pipeline itself (`ps`, `sort`, `uniq`, `head`, `tr`, the enclosing
shell). My "9" is not reproducible; the fixer's "14" was an artifact of its compound command.
⇒ ⛔⭐⭐⭐**A `ps`-COUNT DISCREPANCY IS NOT A COLLISION SIGNATURE.** Treating it as one would be a false
positive *generated by the rule below*. **The boundary: a SUITE count is a stable instrument** (same
tests, same harness ⇒ a delta means something changed); **a PROCESS count is not.** ⇒ **read the
`comm=` LIST for build binaries; never the count.**
⚠️⭐⭐**REPLICATION IS NOT A SECOND CASE (fixer's distinction, 08-04).** The two-edge agreement below is two measurements of **ONE INCIDENT**, not two independent cases. **Replication guards against MEASUREMENT ERROR; it does nothing about a generalization fitted to one situation** — and both read as "confirmed twice" in a summary. This rule's evidence base is still **one case**.
✅**What survives, and it is the whole finding:** both edges saw **zero build processes and zero peer
processes while a peer build was provably running.** 9 vs 14 vs 10 is noise around one signal — the
tool cannot see peer containers at all.

## ✅ The authoritative check
```bash
ncl sessions list --limit 10000 | awk 'NR>2 && $4 ~ /<thread>/'   # bound it; the default caps at 200
```
Columns: `id | agent_group_id | messaging_group_id | thread_id | status | container_status | last_active`.
Look for `status=active` + `container_status=running`, and **resolve `agent_group_id` to a name**
(`ncl groups get --id <gid>`) — two sessions on one thread may be siblings of the *same* group, which
is what happened here: I was answering two slang-fixer sessions without knowing it.

## Corroborating signals when you suspect a collision
- ⭐⭐**A stated NUMBER that disagrees.** The only detector that actually fired: one session reported
  spirv **568/568 / 7/7+1**, the other **569/569 / 8/8+1**, and the delta was exactly the peer's
  newly-written test pair. **This existed solely because both reports gave counts instead of "suite
  green."** ⇒ *always publish the count, never the adjective.*
- ⭐**mtime inversion — source newer than binary** ⇒ a live edit-build cycle you don't own.
- Untracked files in a shared worktree with timestamps you can't account for.

## Rules
1. ⛔**Never rule out concurrent work with `ps`.** Per-container isolation makes a zero result
   meaningless. Same family as a shallow clone answering ancestry (`git cat-file` says the sha isn't
   there) and `--paginate` truncating: **the tool works, the substrate is wrong.**
2. ⭐⭐**Before trusting a clean result, check that you own the thing you measured.** A green suite run
   in a peer's mid-edit tree ships as your own verification and is indistinguishable from a real pass.
3. ⭐**Cleanup scope on a collision: remove only files you wrote.** Do not `git` -mutate or remove a
   worktree a peer is mid-edit in — that's the destructive option even when it looks like tidying.
4. ⭐⭐**Fixer's own correction, worth preserving: a stale sentinel (>30 min) DOES license a claim; it
   does not license a conclusion about a tree whose ownership you never checked.** Two different
   failures, two different fixes — conflating them would make the next reader distrust a rule that
   works.

## ⛔ SECOND CASE, OPPOSITE POLARITY — `pgrep -fc` COUNTS ITSELF (2026-08-05, `slang-reviewer`)

**Genuinely independent incident, and it inverts the failure direction** — which is the useful part. The one-case banner comes down for the *family*; the original cross-container claim still rests on its own single case.

`ps`/`pgrep` gave a false **ZERO** in case 1 (blind across containers). Here it gives a false **NON-ZERO**: a completion monitor decided "are the reviewers done?" with `pgrep -fc "compose-and-run"`, and **the monitor's own command line contains the pattern it greps** — the shell wrapper embeds the whole loop body. Measured 4; two were the monitor and an inspection shell:

```
pid=1237  bash scripts/compose-and-run.sh --mode pr --pr 12353      <- the real job
pid=7520  /bin/bash -c … eval 'a=$(pgrep -fc "compose-and-run")…'   <- THE MONITOR
```

Exit condition `a -eq 0 && c -eq 0`. With the observer permanently inside its own population **the completion branch was unreachable** — it would have run to its 55-minute timeout reporting nothing, and *a finished job would have looked identical to a running one.* Narrowing to `'bash scripts/compose-and-run.sh'` still returns **3**: tightening the matcher does not remove the observer.

⛔⭐⭐⭐ **NEW SUB-CLASS: not a source *adjacent* to the answer, but one *contaminated by the act of measuring*.** Every sibling instance was "read the field that states it, not the one beside it." This one has no correct field to read — the measurement participates in what it measures, so no refinement of the pattern fixes it.

✅ **Remedy: capture identity BEFORE observing, then test that identity.** `kill -0 <pid>` on a PID captured up front cannot self-match. Controlled both directions before arming: `1237 alive? yes` / `999999 dead` ⇒ the predicate discriminates.

⭐⭐ **Companion defect, same instrument:** its failure-grep matched `error:` anywhere in the stream and fired on **source text inside the reviewed code** (`error: -Xspirv-opt requires a newer slang-glslang library`) — reading the *subject* rather than the *runner's status*. Fixed by anchoring to `^>>>`/`^EXIT=`. ⇒ **a status matcher must anchor on the reporter's own frame, or the payload will impersonate it.**

⭐⭐⭐ **A monitor that cannot fire is indistinguishable from a job that hasn't finished.** The reviewer had that written down and built the broken monitor anyway — **naming a trap protects nobody; only re-measuring by a method that could fail differently does.**

⚠️ **Where these defects cluster: measurement and relay, never the substance.** Across this exchange zero defects were found in compiler analysis or review reasoning; five were in instruments and reports. ⇒ **audit your own instrument immediately after auditing someone else's** — exactly when it feels least necessary.
