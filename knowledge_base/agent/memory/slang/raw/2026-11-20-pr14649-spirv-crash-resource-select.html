Background

Slang compiles shaders through its own SSA-based intermediate representation. A function is a list of basic blocks; each block is a list of instructions ending in a branch. Two facts about this IR matter for this bug.

Fact 1 — the block list has a load-bearing order. The order of blocks in a function's list must be compatible with dominance: if block A dominates block B, then A appears before B in the list. The invariant is stated in the source itself (slang-ir.cpp, mergeCandidateParentsForHoistableInst: "We assume that the order of basic blocks in a function is compatible with the dominance relationship"). The function cloner relies on it: when it copies a function body it walks the blocks in list order, registering each cloned instruction as it goes, and an operand whose definition has not been seen yet is silently resolved to the original instruction instead of a clone.
Fact 2 — two late passes interact here. On Khronos targets, a runtime select between two textures (gMode != 0 ? gA : gB) cannot survive as a single instruction, so the specializeResourceSelections pass rewrites the operation that consumes the selected texture into an if/else that executes one copy per texture. Later — SPIR-V direct emission only — the eliminateUndefinedOpaqueHandles pass sees that an argument is an uninitialized Texture2D (Vulkan forbids OpUndef for opaque types) and fixes it by cloning the callee with that parameter specialized away. The clone is made by the cloner from Fact 1.

Intuition

The reporter's shader needs three ingredients, and removing any one of them makes the crash disappear:

void f(Texture2D unused)
{
    Texture2D t = gMode != 0 ? gA : gB;   // (b) runtime texture select
    gOut[0] = t.Load(0);
    uint w = gMode * 3;                   // (c) value defined after the select...
    if (gMode > 4)
        gOut[1] = w;                      //     ...and used in a later block
}

void main()
{
    Texture2D undef;
    f(undef);                             // (a) uninitialized texture argument
}

What each ingredient contributes:

IngredientRole in the failure
(a) uninitialized Texture2D argumenttriggers eliminateUndefinedOpaqueHandles, which clones f — the cloner is the consumer of the broken layout
(b) runtime texture selecttriggers specializeResourceSelections, which splits f's block — the producer of the broken layout
(c) w defined in the merge block, used laterthe value that gets wired across functions

Step by step:

  1. The resource-selection pass splits f's entry block at the texture-consuming operation. The instructions after the split point — including w = gMode * 3 — move into a newly created merge block. The inner if (gMode > 4) had already been lowered to its own blocks, sitting right after the entry block in the list.
  2. The pass appended the merge block at the end of the block list (func->addBlock(after)). So the list read: entry, inner-if blocks …, arms, merge — but dominance says the merge block (which defines w) comes before the inner-if blocks (which use w). List order no longer matched dominance order.
  3. The undefined-handle pass then cloned f. The cloner walked blocks in list order, so it cloned the inner-if block before the merge block. When it cloned the use of w, no clone of w existed yet, and findCloneForOperand fell back to the original w — an instruction inside the old f.
  4. specializeCall deallocated the now-unused original f. The clone was left holding a dangling operand, and SPIR-V emission dereferenced it: SIGSEGV.

The fix is one move: when the pass creates the dispatch arms and the merge block, insert them immediately after the block being split — the same adjacency the inliner already maintains when it splits a block around an inlined call (slang-ir-inline.cpp: afterBlock->insertAfter(callerBlock)). With the merge block back before the blocks that use its values, the cloner sees the definition before the use and never falls back.

Before the fix (block list order vs. dominance):

list:    entry → inner-true → inner-false → merge …  → arms → merge(dispatch)
                       ▲ use of w is cloned BEFORE w's block is reached
dominance:            entry → arms → merge(dispatch, defines w) → inner-true → …

After the fix, the list and dominance agree again:

list:    entry → arm0 → arm1 → merge(dispatch) → inner-true → inner-false → …
                       ▲ w's definition is cloned before any use

Code walkthrough

The PR is two commits, ordered so a reviewer can read the change as steps.

Commit 1 — the failing test

tests/spirv/resource-selection-uninitialized-param.slang reproduces the crash with all three ingredients, compiled to SPIR-V (plus an -O0 variant, matching the sibling resource-selection-*.slang tests). On the unpatched build the test fails deterministically — under -validate-ir the IR validator itself catches the broken layout (E40007: def must be ancestor of use), so the test does not depend on the segfault timing. Its CHECK lines pin the emitted shape loosely: an OpSelectionMerge (the sunk select) and an OpIMul (the w computation surviving the clone with a live operand).

Commit 2 — the fix

In emitConsumer (slang-ir-specialize-resource-selections.cpp), the pass used to create the merge block and arms with func->addBlock(...), which appends at the end of the block list. The fix keeps the creation logic but changes the attachment: a chain tail starts at the block the builder is currently inserting into — the split block at the top level, the arm at nested dispatch levels — and every new block is inserted after the previous one, ending with the merge block:

IRInst* listTail = builder.getBlock();
for (auto arm : arms)
{
    arm->insertAfter(listTail);
    listTail = arm;
}
after->insertAfter(listTail);

Details a reviewer may probe:

  • Why arms before merge? It matches the inliner's idiom and the natural reading order (true arm, false arm, then the join). The only hard ordering requirement is that the merge block — which ends up owning the moved continuation instructions — precedes the blocks that were already after the split point, and the chain guarantees that.
  • Nested dispatches (a consumer with several independently selected arguments) create their arms and merge inside an arm. Anchoring each level at builder.getBlock() places the nested chain right after its arm, which keeps every constraint intact: arms only use values from earlier blocks, and only the outermost merge receives continuation instructions.
  • The temporary continuation block in rewriteConsumer still uses func->addBlock. It is a scratch pen for the moved instructions; its contents are appended into the final merge block and it is deallocated before the pass returns, so no observer ever sees its position.
  • Why not also fix emitIfElseWithBlocks? That helper has the same append-at-end shape, but it is not on this crash path: its composite-select caller runs for HLSL, and on SPIR-V it runs after the undefined-handle pass, so it cannot feed this cloner. It stays as-is here and is noted in a follow-up.
Considered and dropped: the triage suggested pairing the fix with a cloner-side assertion that the findCloneForOperand fallback is only taken for module-scoped values. A full survey found many legitimate users of that fallback within the same function, and a narrowed cross-function version — implemented and tested — correctly caught this bug but also fired on all 39 tests/autodiff-dstdlib/* executions: autodiff cloning legitimately reuses instructions across functions that stay alive, which a clone-time check cannot distinguish from the deadly case (where the source function is later deallocated). Per the triage's pre-approved fallback, the assertion was dropped and cloner hardening is filed as a separate follow-up.

Quiz

Q1. Why does appending the merge block at the end of the function's block list break the cloner, given that block order "doesn't affect CFG topology"?

The CFG itself stays correct — branches name their targets explicitly. What breaks is the cloner's assumption (shared by hoisting) that list order respects dominance: it registers clones as it walks, so a use cloned before its definition's block is reached silently binds to the original instruction.

Q2. The fixed code inserts the new blocks with builder.getBlock() as the chain anchor. At a nested dispatch level, what does that return, and why is that the right anchor?

Nested dispatch blocks are created while the builder is inserting into an arm; only the outermost merge receives the continuation instructions, and it was anchored directly after the split block at the top level. Arms only consume values from earlier blocks, so their exact position among the new blocks is free as long as the outer merge precedes the blocks that follow the split point.

Q3. Why was the cloner-side assertion (fallback only for module-scoped operands) dropped instead of shipped?

The assertion did catch the bug in a revert drill. But all 39 tests/autodiff-dstdlib/* executions tripped it: autodiff primal/differential cloning reuses instructions across function boundaries where the source function stays alive. Clone-time checks cannot see the future deallocation that made the #14646 case deadly, so hardening needs its own investigation (filed as a follow-up).
