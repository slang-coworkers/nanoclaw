Background

When Slang compiles an entry point, every varying input/output — parameter or return value — is laid out before code emission. The layout records, for each leaf value, which semantic binds it: systemValueSemantic("SV_Depth", 0) or a plain location. Emitters trust the layout, not the source text. A leaf laid out as SV_Depth becomes gl_FragDepth / BuiltIn FragDepth; a leaf laid out as SV_Target1 becomes an ordinary color output at Location 1.

Semantics can be declared per field, or on an enclosing declaration. When both exist, the documented outer-most semantic wins policy applies the enclosing semantic to every leaf with a running index: void fs(out Out o : OUTPUT) with Out { float4 a : A; float4 b : B; } gives o.a → OUTPUT0, o.b → OUTPUT1. For user-defined semantics that composition is the point of the policy.

Deep background (skippable). The layout pass walks an entry-point signature recursively: processEntryPointVaryingParameterDecl takes a declaration (a parameter, the function itself for the result, or a struct field) plus a state carrying the nearest enclosing semantic. With no enclosing semantic, the decl's own semantic is adopted into the state and pushed down into fields and array elements; with one present, the decl's own semantic was silently skipped. The result of an entry point is laid out with decl = the function, so Output main() : SV_Target enters the walk as the outer-most semantic for every result-struct field. System-value semantics are classified purely by prefix — any SV_/NV_-prefixed name — except SV_Target<N> on fragment outputs, which is deliberately treated as an ordinary user output.

Intuition

Consider the issue's reproducer:

struct Output {
    float4 color : SV_Target;
    float   depth : SV_Depth;
};

[shader("fragment")]
Output main(Input input) : SV_Target { ... }

The : SV_Target on main becomes the outer-most semantic. Walking the result struct, the policy skips each field's own semantic and numbers leaves sequentially:

main() : SV_Target
outer semantic → color : SV_Target
rebound → SV_Target0 → Location 0 color
main() : SV_Target → depth : SV_Depth
rebound → SV_Target1 → Location 1 color
FragDepth never written

depth is silently rebound to SV_Target1: an ordinary color output. The shader compiles with exit 0, renders the image, and never writes depth — the exact silent miscompilation the issue reports. Deleting : SV_Target from the function restores SV_Depth, and FragDepth appears.

The fix keeps the outer-most-wins policy untouched for user-defined semantics, and adds one rule: when the skipped semantic is a system-value semantic and the outer semantic would bind the field to something different, that is never what the spelling means — reject it with E39034 naming both semantics. When the outer semantic would assign exactly the slot the field names itself (same base name, own index equal to the slot the running counter has reached), the spelling is redundant and stays legal with identical layout.

Code walkthrough

1. Diagnostic — slang-diagnostics.lua

New error outer-semantic-overrides-system-value-semantic (E39034): "the system-value semantic '~fieldSemantic' is ignored because the enclosing declaration applies its own '~outerSemantic' semantic", with the field's semantic as the primary span and the enclosing declaration's semantic as a secondary span, so the rendered error points at both spellings.

2. State — slang-parameter-binding.cpp, EntryPointParameterState

Two new fields, optSemanticLoc and optSemanticText, recorded wherever an enclosing semantic is adopted, so the secondary span has an exact source location and the message quotes the enclosing semantic as written.

3. Classification helper

The prefix rule moves into a named helper isSystemValueSemanticName (any SV_/NV_ prefix, case-insensitive), and the pre-existing inline check in processSimpleEntryPointParameter now calls it — one source of truth for "is this a system-value semantic".

4. The check — processEntryPointVaryingParameterDecl

The adoption branch is unchanged. A new else if fires when an outer semantic is already active and the decl's own semantic is a system value: it compares base names case-insensitively and the decl's own index against the running slot counter. Different name or different index → E39034. Identical slot → redundant, no diagnostic, byte-identical layout. Because the walk is shared, one site covers function results, out/inout parameters, and fields nested arbitrarily deep.

5. Tests

tests/diagnostics/outer-semantic-overrides-system-value-semantic.slang runs eight cases: the issue's shape errors on SPIR-V, HLSL and GLSL; nested-struct, out-parameter, and user-defined-outer variants error; two positive controls (a single SV_Target field under an outer SV_Target, and an indexed SV_Target1 field landing on the slot it names) compile clean and emit real SPIR-V. tests/spirv/depth-out-struct-fragdepth.slang guards the clean path: the struct result keeps BuiltIn FragDepth and no spurious Location-1 depth output appears.

Quiz — five questions

1. With no enclosing semantic anywhere, how are the semantics of two struct fields in an entry-point result used?

Correct. The adoption branch uses the decl's own semantic when no outer semantic is active; the new check only fires in the presence of an enclosing semantic.

2. Why does the depth output vanish rather than error in the original bug?

Correct. The outer-most-wins policy overwrites the field's own semantic during layout, and the emitters faithfully emit what the layout says; nothing downstream ever sees SV_Depth.
Not quite. The layout overwrote the field's semantic with SV_Target1, and emitters bind by layout — depth became an ordinary color output.

3. struct Out2 { float4 a : SV_Target; float4 b : SV_Target1; } with entry Out2 main() : SV_Target — what does the new check do?

Correct. a is compared when the running counter is at 0 (own index 0) and b when it has advanced to 1 (own index 1); both are redundant spellings of the same layout, so the same-slot exemption applies.
Not quite. Each field's own index matches the slot the running counter has reached when that field is visited, so the same-slot exemption keeps this legal with identical layout.

4. Which semantic names does the compiler classify as system values?

Correct. isSystemValueSemanticName keeps the pre-existing prefix rule as the whole classification (with SV_Target<N> on fragment outputs still special-cased downstream as an ordinary output).
Not quite. Classification is purely by prefix: any case-insensitive SV_/NV_-prefixed name is a system value.

5. After this change, what happens to a user-defined field semantic under an enclosing user-defined semantic, e.g. void fs(out Out o : OUTPUT) where Out { float4 a : A; float4 b : B; }?

Correct. That composition is the documented, intentional behavior of the outer-most-wins policy; the new check only fires when the skipped semantic is a system-value semantic.
Not quite. User-defined field semantics under an enclosing user-defined semantic keep the documented outer-most-wins composition, unchanged by this PR.
