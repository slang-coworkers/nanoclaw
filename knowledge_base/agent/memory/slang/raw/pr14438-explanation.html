1. Background

Deep background (skippable). A slangc run builds one end-to-end compile request. That request owns a front-end request, which preprocesses, parses and checks the source, and the back end, which generates code for the targets. Every diagnostic goes into a single diagnostic sink. The sink counts the diagnostics that have error severity, including warnings that -warnings-as-errors promotes.

slangc calls spCompile. If the result is a failure, source/slangc/main.cpp changes it to SLANG_E_INTERNAL_FAIL, and the tool exits with -1 (255 in a POSIX shell). The test runner slang-test runs slangc and can check that exit code: a filecheck= lane expects 0 unless it says exit-code=N. Since #14422, a diag= lane expects -1 by default, and an .expected file pins a result code = N line.

-E (also spelled -output-preprocessor) asks Slang to preprocess the input, write the token stream to stdout and stop. It never runs the parser or the semantic checker. The issue reporter found that this mode always reported success, even when preprocessing failed:

$ cat t.slang #define POUND_POUND ## Hello POUND_POUND There; $ slangc t.slang -E; echo $? error[E15405]: invalid '##' position Hello ## There ; 0 <- a build script sees success

The same input without -E exits -1. gcc -E, clang -E and cpp also write their output and exit 1 in this case.

2. Intuition

FrontEndCompileRequest::executeActionsInner does its work in three steps. First it preprocesses each file, which in -E mode also writes the tokens. Then it asks the sink whether any error was reported. Then it parses and checks the code. The -E early exit was placed between the first two steps, so a preprocess-only request returned before the error question was asked.

parseTranslationUnitpreprocess t.slang
sink: 1 error (E15405)
stdout: Hello ## There ;
→
before: -E? → return OKerror count never read
→
slangcexit 0
parseTranslationUnitpreprocess t.slang
sink: 1 error (E15405)
stdout: Hello ## There ;
→
after: errors? → FAILthen -E? → return OK
→
slangcexit -1, text already on stdout
Why the text survives. In -E mode, parseTranslationUnit writes the tokens to the stdout writer and then returns. The output is on stdout before any result is decided, so a failed result cannot remove it. This change affects only the exit code, as the issue asks.
Input under -EBeforeAfter
#error boom (E15900)0-1
## at the start of a macro body (E15405), duplicate macro parameter (E15408)0-1
#warning w with -warnings-as-errors all0-1

Requests without -E do not change. When the request is not preprocess-only, the -E branch is never taken. The old order and the new order both reach the error check, which then fails in the same way. Only the -E path behaves differently.

3. Code walkthrough

The fix (source/slang/slang-compile-request.cpp) moves the error-count check above the PreprocessorOutput return:

    for (TranslationUnitRequest* translationUnit : translationUnits)
    {
        parseTranslationUnit(translationUnit);
    }

    // Preprocessed text was already written by `parseTranslationUnit`, so errors do not discard it.
    if (getSink()->getErrorCount() != 0)
        return SLANG_FAIL;

    if (optionSet.getBoolOption(CompilerOptionName::PreprocessorOutput))
    {
        // If doing pre-processor output, then we are done
        return SLANG_OK;
    }

The caller needs no change. EndToEndCompileRequest::executeActionsInner already wraps this call in SLANG_RETURN_ON_FAIL, so the failure reaches spCompile, and slangc turns it into exit -1. The caller's own -E return runs only after the front end has succeeded.

The new test (tests/preprocessor/preproc-only-error-exit-code.slang) has four lanes. -D selects the error input and the parse-only input; both warning lanes use the default branch. The first three lanes check their diagnostic in stderr, the parse-only lane checks that stderr is empty, and all four check standard output = { followed by the preprocessed text, so a lane fails if the text stops being written to stdout:

//TEST:SIMPLE(filecheck=ERROR,exit-code=-1):-E -DTRIGGER_ERROR
//TEST:SIMPLE(filecheck=WARN):-E
//TEST:SIMPLE(filecheck=WARN_AS_ERROR,exit-code=-1):-E -warnings-as-errors all
//TEST:SIMPLE(filecheck=PARSE_ERROR):-E -DTRIGGER_PARSE_ERROR

On master, the two lanes that expect -1 fail with "expected exit code -1, but the exit code is 0". The other two lanes pass on master and with the fix. They pin what must not change: a warning alone exits 0, and code that only the parser rejects exits 0.

Existing tests. All 25 -E tests are in tests/preprocessor/ and tests/bugs/. Three of them report an error:

  • preproc-pound-pound-1.slang and preproc-detail-2.slang. #14422 had marked their diag= lines exit-code=0, to match the old behavior. This PR removes that option, so the lines use #14422's default of -1, which is what the issue asks for. Their filecheck= lines get exit-code=-1.
  • tests/bugs/preproc-lex-failure-2.slang.expected. Lexer error 10005 ("newline in literal") is counted in the sink, so result code = 0 becomes -1. The stderr and stdout blocks do not change.

The other -E tests that carry exit-code=0 (preproc-concat-3, preproc-detail-3, special-macro-redefine-*) report only warnings, so they still exit 0.

Verification. slang-test tests/preprocessor/ tests/bugs/ passes 1072/1072. On the L40S, the full suite passes 12041/12044. The 3 failures are fp8 cooperative-matrix CUDA lanes that fail with CUDA_ERROR_INVALID_PTX. They do not use -E, and this change does not touch requests without -E.

Open question for the maintainer. The chosen behavior is this: -E keeps its output and exits -1 on any error, as gcc -E and clang -E do. Please confirm that this is intended.
Out of scope. With -pass-through <compiler> -E, the front end is skipped completely (slang-end-to-end-request.cpp, the -E return after the pass-through check). That mode writes no text and exits 0 even for #error. This PR does not change it.

4. Quiz

1. After the fix, why does slangc -E still print Hello ## There ; when it exits -1?

  • The tokens are written to the stdout writer inside parseTranslationUnit, before the error check runs.
  • The end-to-end request writes the token stream again after the front end fails.
  • The error check skips requests that have PreprocessorOutput set.
  • slangc buffers stdout and flushes it only when a request fails.
The output is written when preprocessing finishes, in parseTranslationUnit. executeActionsInner decides the result after that. Nothing writes the text again or holds it back, so failing afterwards cannot remove it. The check applies to every request, and that is the whole point of the fix.

2. Which input still exits 0 under -E after this change?

  • #error boom
  • #warning w together with -warnings-as-errors all
  • #define P ## followed by a use of P
  • int x = ;
-E stops after preprocessing and never runs the parser, so the syntax error in int x = ; is never reported. The sink has no errors, and the request succeeds. The other three inputs put an error into the sink while preprocessing runs. That includes the promoted warning, because -warnings-as-errors reports it with error severity.

3. Why do the diag= lines of preproc-pound-pound-1 and preproc-detail-2 drop exit-code=0, instead of changing it to exit-code=-1?

  • slang-test does not check exit codes on diag= lines.
  • Since #14422, a diag= lane expects -1 by default, so the plain line already expects the compile to fail.
  • slang-test rejects exit-code=-1 as a reserved value.
  • The filecheck= lane on the next line makes the exit code of the diag= lane irrelevant.
#14422 changed _checkExpectedExitCode: diag= tests now expect -1 unless they say otherwise, and a diag= lane that succeeds (only warnings, or no diagnostics) writes exit-code=0. No test on master writes exit-code=-1 on a diag= line, so removing the override is the usual way to say "this compile fails". The value that is rejected is -2, the code for an internal compiler error. -1 is allowed.
