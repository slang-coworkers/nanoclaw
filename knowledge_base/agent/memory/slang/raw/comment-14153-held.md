- **Verdict:** Bug. The diagnostic regressed in #8117 (the fix for #8116, float add on device buffers). That change added `metal` to the texture `InterlockedAddF32` declaration in `hlsl.meta.slang` (a `case metal:` arm). It also removed the float check from the Metal `AtomicAdd`/`AtomicSub` emit cases. So the call passes the capability check, and no later step rejects a float texel. The generic `InterlockedAdd(t[coord], 1.0, original)` on a float texture, `RWBuffer<float>`, and `RWTexture2D<half>` take the same path. Planned fix: `t.InterlockedAddF32(...)` no longer declares Metal, so on Metal it fails the capability check (`E36107`). The generic `InterlockedAdd`/`InterlockedSub` on a float or half texture, on `RWBuffer<float>`, or on a half destination gets the Metal float-atomic diagnostic (`E55204`) that load/exchange/compare-exchange already use. Float add/sub on device buffers (`atomic_float`) and on groupshared memory do not change. One new diagnostic: float add/sub on `MetalObjectData` memory now gets `E55204`, because MSL defines atomics only on device and threadgroup memory. The Metal lane of `float-atomics.slang` will check for the diagnostic. We do not plan the `uint`-view emulation: `texture2d<float>` has no atomic members, so the shader would need a `texture2d<uint>` binding, and the host would have to bind an R32Uint view.
