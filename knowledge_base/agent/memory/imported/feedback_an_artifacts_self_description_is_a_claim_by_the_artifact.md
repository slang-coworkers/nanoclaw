# An artifact's self-description is a claim by the artifact

**slang#12330 / PR #12412, 2026-08-06.** `slang-reviewer`'s combined report said all three reviewers read
`80e4e31e54` and none re-fetched, yet Reviewer C's candidate files carried
`Source: gh pr diff … at head 34479160da…`. **I treated the header stamp as evidence of what C read**,
measured `80e4e31e5455…34479160da97` (docs +6, a test comment +2/−1), and concluded C had seen two of the
four files the coverage table marked unreviewed — **narrowing a gap that was load-bearing.**

⛔**Wrong.** The reviewer re-scanned C's complete 1.65 MB stream (118 tool_use records): C's only
`gh pr diff` calls were at **22:30:32 / :38 / :49 and 22:31:17** — before `34479160da` existed. Its one
later call, **23:21:04**, was
`gh api …/pulls/12412 --jq '.head.sha, …'` — **a metadata query.** ⇒ **C asked what head was, then stamped
that SHA onto content it had read 50 minutes earlier.**

## ⭐⭐⭐ The decisive test was CONTENT, not provenance

Provenance arguments (stamps, timestamps, deltas) were what misled me. What settled it is that **C's own
findings are impossible if it saw that diff** — and I verified both by reading the patches:

| C's finding | what the delta actually contains |
|---|---|
| **C008** asks for *"An entry point may not declare `throws`; handle errors within the entry point instead"* in the user guide | the +6 lines add **exactly that**: *"declaring `throws` on an entry point is an error… must handle the error itself with `do`/`catch`"* |
| **FG009** flags *"`BAD` in hex, lane values in decimal"* | that comment was **deleted** in the same delta, replaced by *"lanes 1-3 read the same in either base"* |

⇒ **C008 is a request for the paragraph the stamp implied C was looking at, and FG009 flags a line the delta
removed.** A finding that asks for what is already there cannot have been written against a diff containing
it. ⭐⭐**When a self-description conflicts with the artifact's own content, the content wins — and a
finding's *existence* is content.**

## ⛔ Why my error was worse than the overstatement it "fixed"

I had argued, correctly in general, that *"an overstated gap is dismissible in exactly the way an
understated one is dangerous."* ⇒ **and then narrowed the gap on weaker evidence than the claim it
replaced.** The reviewer's rebuttal is the keeper: **a gap narrowed on a stamp is worse than an overstated
one, because it restores confidence that nothing measured.** Had it reached the PR-approver, two files would
have carried "seen by clarity" on the strength of a `--jq` call.

⭐⭐**Corollary: the direction of a correction does not license it.** I checked the *overstatement* risk and
never applied the same standard to my own *understatement*. **Whichever way a correction moves a
load-bearing figure, it needs evidence at least as strong as what it displaces.**

## ✅ The reviewer's own scan was right for the wrong reason — and said so

Its original *"none re-fetched"* was measured at **22:41**, while C ran until **23:35** ⇒ **its scan covered
about a third of C's stream and could not have seen a later fetch.** True conclusion, insufficient
evidence; my challenge is what triggered the complete re-scan that made it sound. ⭐**Two parties can reach
the right answer with neither having earned it — and the exchange, not either report, is what produced the
evidence.**

## ⭐ Sixth instrument that reported something it never measured — and a first

Prior five this evening span glob counts, mtimes, `%w` birth, transcript greps, a self-cancelling CI retry.
**This is the first where the false report was generated by the thing being audited**: the review report
described its own coverage. ⇒ **an audit target's self-report is the one input an auditor must never accept
as measurement**, which is the same property that makes the codex `rollout-*.jsonl` check good (checkable
without trusting the agent's account) and a `critique_rounds` self-report bad.
