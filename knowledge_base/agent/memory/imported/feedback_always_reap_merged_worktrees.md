Standing operator authorization (dashboard-admin, 2026-06-29): **"You are always authorized to reap the merged-PR worktrees."** On any §8 / disk-pressure pass, MERGED-PR worktrees are reaped **immediately and autonomously** — no per-instance operator confirmation.

**Why:** merged-PR worktrees are unambiguously terminal (the work landed); asking the operator each time is pure friction on a recurring cleanup. The operator wants the supervisor to just clear them.

**How to apply:**
- The operator also asked, as part of this, to **categorize each worktree by PR state** on the disk-pressure tick (e.g. "supervisor tick 66"). Produce the categorization (MERGED / CLOSED / OPEN[-draft] / no-PR / custom-branch) every disk-pressure pass.
- **MERGED → reap now, autonomously** (no ask). **CLOSED → terminal, also reapable** (consistent with prior §8 practice). **OPEN[-draft] → PROTECT** (active work — never reap; especially the live merge-track ones). **no fix/issue PR → flag for fixer assessment** (may be parked-pre-PR with WIP, e.g. #11778 loop-phi; save-then-remove only if abandoned). **custom-branch (non-numeric) → manual.**
- Mechanics unchanged by this grant: the supervisor still **does NOT `git worktree remove`** from its own session (volume mounted read-only to Main; §8 MUST-NOT). "Reap" = **dispatch the save-then-remove GC a2a to the owning fixer** (slang-fixer / slangpy-fixer). The grant removes the operator-confirmation step, not the detect-and-dispatch model.
- Map slug→PR: `wt-slang-<n>`→shader-slang/slang `fix/issue-<n>`; `wt-rhi-<n>`→shader-slang/slang-rhi; `wt-slangpy-<n>` / slangpy-fixer/`wt-<n>`→shader-slang/slangpy. Verify MERGED state at classification time before reaping.

**Base clone is fetched PERIODICALLY, not continuously (observed 2026-06-29).** The slang-fixer base clone (`/workspace/agent/slang`, reachable from Main read-only at `/workspace/extra/ephemeral/prod-groups/slang-fixer/slang`) was on master `777a78adbf` (06-27 19:03Z) = its `origin/master`, **4 commits behind** real upstream master (`3a84a12b8e`, 06-29 05:20Z); last `FETCH_HEAD` 06-28 12:18Z (~17h stale). **This lag is the root of the recurring per-PR "sync against upstream and resolve conflicts" churn** maintainers keep requesting (#11541, #11581, …): worktrees branch off a stale base, drift behind, and need on-demand `merge origin/master`. A scheduled `git fetch`/rebase-onto-master on the base clone would reduce that churn. From Main you can read the base clone's git log via the ephemeral mount (read-only is fine for `git log`). NB the SAME `/dev/vdb` worktree volume is mounted at **different paths per container**: Main sees it read-only at `/workspace/extra/ephemeral/prod-groups/<group>/…`; the fixer sees it read-write at `/workspace/agent/…`. Same data, same `df` numbers.

**Variant-worktree branch-name caveat (observed 07-10, #9062 disk pass):** classifying reclaim candidates by the `fix/issue-<n>` head-branch convention is WRONG for variant worktrees. Dirs like `wt-slang-11917-asafe` / `wt-slang-11917-p3` carry differently-named branches (`fix/issue-11917-asafe`, `fix/issue-11917-**matrix**`), each with its OWN PR state — `-p3`→`fix/issue-11917-matrix` had OPEN PR #11987 (protected) even though a `fix/issue-11917` query returned the merged slice #11920. **Always read the ACTUAL branch per worktree from `git worktree list` (shows `[branch]`), then query that exact branch's PR state** — don't assume slug `-<n>-suffix` maps to `fix/issue-<n>`. Also: a "no-PR" worktree can still hold an **unpushed local commit** (git tree clean but `origin` lacks it) — full `git worktree remove` is only strictly safe after confirming no unpushed WIP; otherwise use the **build-output-clear** lever (delete regenerable `build/` only; source+commit+branch survive) which reclaims most of the space (~3.8G/worktree here) with zero WIP risk. Main relays candidates but the OWNING FIXER verifies branch+PR+unpushed state before touching anything.

**§8 save-then-remove gotcha (observed 06-29):** the `wip/reap/<branch>` *push* fails for any branch touching `.github/workflows/*.yml` (bot lacks `workflows` perm — see project_bot_workflows_permission; e.g. Falcor branches). **Removal is still safe regardless:** `git worktree remove` does NOT delete branch refs, so unpushed commits survive in the base clone (`/workspace/agent/<repo>`) and are fully recoverable by branch name. So a failed wip/reap push is NOT "work lost" — the worktree dir is reclaimed and the commit is preserved as a local ref. (A fixer loop bug once gated on `cmd | tail` exit instead of `git push` exit and removed worktrees despite the failed push — harmless because refs survive, but the lesson is: never gate on `cmd | tail`.) For abandoned commits on CLOSED issues, no need to push them off-box — the dangling refs are tiny and harmless.
