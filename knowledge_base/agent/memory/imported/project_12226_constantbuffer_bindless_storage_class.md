#12226 — `ConstantBuffer<T>` fetched bindlessly (`ResourceDescriptorHeap[]` / `DescriptorHandle`, `spvDescriptorHeapEXT`) emits `OpTypeBufferEXT StorageBuffer` + StorageBuffer buffer-pointer instead of Uniform. Driver reads a 16B storage-buffer descriptor from a heap slot the app filled with an 8B uniform-buffer descriptor → garbage read (real ABI break). Reporter aechelon-joshuamaros (external), Slang 2026.14, Vulkan/SPIR-V.

**Triaged 07-25 (top-of-tree 5281ccc66):** confirmed bug, **high/P1, SPIR-V target-emit**, REPRODUCED. **Element-shape-dependent** — scalar `ConstantBuffer<float>` correctly stays Uniform; only struct/array forms wrong.

**Regression from PR #11647.** The StorageBuffer flip is *deliberate*: `processConstantBufferDescriptorHeapLoad` (slang-ir-spirv-legalize.cpp:1300) was added by #11647 to fix #11483's nested-array-addressing garbage (a Uniform buffer pointer carries no pointer-type `ArrayStride`). **Naive revert regresses #11483.** Real defect = conflation of *descriptor kind* (ABI) with *pointer addressing class*.

**DESIGN-GATED — maintainer call (cc szihs / jkwak-work).** Triage memo `/workspace/agent/memory/triage-12226.md` (triager's fs) has 2 approaches (A vs B) on the device-ABI axis.

**Spec gate RESOLVED 07-25 (triager re-verified against published SPV_EXT_descriptor_heap rev1 asciidoc, §3.56.6/§3.56.8):** `OpTypeBufferEXT` storage class and `OpBufferPointerEXT` result class are **independent operands, no matching VUID** → DeepWiki's "must match" REFUTED; earlier "Approach B likely infeasible" was WRONG. Uniform descriptor kind is **ABI-forced**. Verdict comment 5075822113 **PATCHed in place** to correct this and reframe the maintainer question as A-vs-B on device-ABI. Open hypothesis (NOT fact): Uniform-descriptor slot → StorageBuffer data pointer legal on real drivers + bundled spirv-val?

**MAINTAINER RULING 07-25 (jkwak-work, comment 5097327434) [CONTESTED by reporter 07-27]:** behavior is **INTENTIONAL** — StorageBuffer is used so an array type inside the descriptor-heap struct can be addressed; Uniform storage class disallows taking a pointer to an array element in SPIR-V (the #11483 constraint). **✅ FIXER INVESTIGATION COMPLETE 07-28 16:38 @HEAD `dd6e011e56` (fixer msg 73540; report `/workspace/agent/reports/slang-12226.md` "2026-07-28 RE-OPEN"; delivered to triager on canonical thread `gh-issue-shader-slang/slang-12226` in_reply_to=8; NO code — contested design call).** All 3 triager questions answered w/ direct code evidence + local empirical confirmation:
- **Q1 — reporter's mechanism read CONFIRMED exactly.** Slang emits the heap-ARRAY index via `OpUntypedAccessChainKHR`+untyped-UniformConstant (emit-spirv.cpp:7606), then the buffer-DATA pointer via `OpBufferPointerEXT` whose Result Type = `inst->getDataType()` = a **TYPED IRPtrType** → typed `OpAccessChain` field access needing pointer-type ArrayStride (StorageBuffer-only, :2563). glslang keeps the data pointer **untyped-Uniform + `OpUntypedAccessChainKHR`** (stride from type decorations). **The whole emitter has only 3 `OpUntypedAccessChainKHR` sites — all heap/texel *indexing*, none does field/elem access on buffer data. That's the architectural gap.**
- **Reporter is mechanism-correct AND spec-correct.** Untyped-Uniform `OpBufferPointerEXT`+`OpUntypedAccessChainKHR` field access is legal (the two SPV_EXT_descriptor_heap storage-class operands are independent — the 07-25 spec finding). **jkwak's "Uniform can't take a pointer to an array element" is narrowly true ONLY for Slang's TYPED path; the untyped path sidesteps it, as glslang shows.**
- **Q2 — FEASIBLE for Slang but NOT localized.** IR pointer *types* are Slang's sole carrier of element-type + address-space through the whole legalize→emit pipeline (`emitFieldAddress`:8580 reads `getValueType()`; `emitGetElementPtr`:8650 + `processFieldAddress`:1475 propagate addr-space; `emitStructuredBufferGetElementPtr` assumes typed `OpAccessChain`). An untyped data pointer needs **~5-8 new untyped-aware consumers** (IR GEP/field-address insts have no type-operand slot → block-struct type threaded in parallel). **Emitter-architecture extension, not a config/class flip.** **Q3 — that's *why* typed:** it's the one canonical pointer representation the emitter is built around; #11647 picked StorageBuffer because within the typed representation it's the only class carrying the needed pointer-type ArrayStride.
- **3 BONUS empirical findings (worth surfacing regardless of A/B):** (a) Slang **already** emits typed-*Uniform* `OpBufferPointerEXT`+typed-Uniform `OpAccessChain` for scalar/vector/matrix CB heap elements and it validates → the StorageBuffer flip is scoped to **array-element structs only**. (b) The flip is **OVER-BROAD**: `processConstantBufferDescriptorHeapLoad`:1315 gates on `as<IRStructType>` = *every* struct, so even `ConstantBuffer<struct{float value;}>` (no array) needlessly fetches a storage-buffer descriptor; narrowing to structs-that-contain-arrays gives no-array CBs the correct Uniform descriptor kind cheaply. (c) jkwak's `-spirv-unified-descriptor-heap-stride` fixes the **stride/spacing NOT the descriptor kind** — `OpTypeBufferEXT StorageBuffer`+`%_ptr_StorageBuffer_...` persist with the flag; addresses the 8B-vs-16B size symptom but NOT the uniform-vs-storage descriptor interpretation that is the core defect. (States a fact about the flag — not relitigating the ruling.)

**BASIS SHIFT — jkwak's INTENTIONAL ruling is now technically CONTESTED with receipts.** The ruling rested on "Uniform can't address an array element"; the fixer + reporter (glslang) show that's avoidable via the untyped path (spec-legal, spirv-val-OK). So #12226 leans **REAL bug** (Slang should emit untyped-Uniform), NOT by-design — BUT the fix is real emitter work (~5-8 fns), not a one-liner, and **NO code lands on a contested design call.**
