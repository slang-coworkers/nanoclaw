## 🔴 Finding 2 — `0.146.1` is 14 h old and nothing gates it; `pnpm install -g` is ungated

Published `2026-08-05T16:00:31Z` = **14.0 h** before the PR opened, inside the repo's 3-day
(`4320` min) window. `CLAUDE.md:284-287` requires human sign-off to bypass; `docs/SECURITY.md:237`
gives the rationale. PR relies on `CLAUDE.md:330` (*"no minimumReleaseAge applies to this tree"*),
but that is about the **bun** tree — codex is installed by **pnpm** at `Dockerfile:173`, the tree
the gate governs. Two independent reasons it doesn't fire, both measured:

- **(a) `pnpm install -g` is not gated.** Same shell, same cwd, same `.npmrc`, same exact spec,
  pnpm 10.33.0: local `add @openai/codex@0.146.1` → `ERR_PNPM_NO_MATURE_MATCHING_VERSION`
  (*"released 14 hours ago"*) — **the control, proving the gate is live** — while
  `install -g @openai/codex@0.146.1` → `+ @openai/codex 0.146.1`.
- **(b) PRE-EXISTING, not this PR: the repo's gate spelling is inert under its own pinned pnpm.**
  `pnpm-workspace.yaml` nests the key under `pnpm:`; pnpm 10.33.0 (`packageManager: pnpm@10.33.0`)
  reports `config get minimumReleaseAge → undefined` for that shape and installs 0.146.1. Moved
  top-level it reports `4320` and holds at 0.146.0. Said so explicitly in the comment so it is not
  charged to this PR.

Fix offered: pin **0.146.0** (published 2026-07-29, 196 h old — past the gate, still 7 versions
ahead of 0.139.0). ⚠️**Exact pins do NOT bypass the gate** (exact 0.146.1 local add refused) — only

## Lessons spun out

- ⭐⭐⭐[[feedback_a_lockfile_hash_is_a_toolchain_fingerprint]] — an install-equivalent lockfile can
  still be a defect when the hash is load-bearing; bisect the *producer* by byte-exact
  reproduction across tool versions, and test the **fixed point** under the pinned tool.
- ⭐⭐⭐[[feedback_a_declared_supply_chain_gate_needs_a_refusal_control]] — reading a gate's config
  never establishes it fires; only a paired refuse/allow in one shell does. Two orthogonal
  bypasses here (global-install path, nested config key), neither visible in the config.

⚠️**My own near-miss, caught by an error message**: `grep -c … file || echo "base: 0"` on a
**missing** file printed `base: 0` — the exact shape of a false zero. Only the preceding
`mkdir: Read-only file system` error revealed the files were never staged. ⇒ never let a
count fall back to a literal `0`; prove the file exists (`wc -c`) first.
⚠️Second near-miss: `git grep -c` piped through `grep -v node_modules | head` printed **empty** for
4 symbols, which reads as "0 hits" — re-ran with an explicit `wc -l` and a must-hit positive
control before publishing.
