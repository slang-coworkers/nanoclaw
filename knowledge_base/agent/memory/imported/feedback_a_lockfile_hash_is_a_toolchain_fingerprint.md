# A lockfile hash is a toolchain fingerprint, not just a dependency set

Measured 2026-08-06 on [[project_nanoclaw_1097_codex_one_copy]] (slang-coworkers/nanoclaw#1097).

## The rule

When a repo **stamps a lockfile hash as infrastructure** — an image label, a drift guard, a
published "post-merge sha" — then two lockfiles that install the *identical* tree are still not
interchangeable. Check three things, in this order:

1. **Which tool version produced it.** Reproduce byte-exact across candidate versions.
2. **Is it a FIXED POINT under the tool the project pins?** Run the pinned tool's ordinary install
   and re-hash.
3. **What consumes the hash**, and what does that consumer do on mismatch.

## Why reading the diff finds nothing

The #1097 lock diff was 18 deleted lines removing an unused dep — obviously correct. The defect was
a **19th deleted line**, `"configVersion": 1`, which no reviewer reads as content. It meant the lock
was generated by a bun older than the one `Dockerfile:29` and `ci.yml:116` pin.

Attribution, same procedure per version (base lock + base `package.json`, delete the dep,
`bun install --lockfile-only`), real binaries downloaded per version:

| bun | sha256 | |
|---|---|---|
| 1.2.23 | `f7a924d5…` | **byte-exact to the PR's lock** |
| 1.3.0 | `f7a924d5…` | **byte-exact** |
| 1.3.8 | `37a46ee6…` | differs |
| **1.3.12** (pinned) | `37a46ee6…` | differs |

⭐⭐⭐**A byte-exact match across a version bisect is a much stronger claim than "this looks like an
old lock" — it names the producer.** Downloading three extra tool binaries cost ~90 s and converted
a suspicion into an attribution.

## The fixed-point test is the finding

| input lock | after the PINNED tool's ordinary install | |
|---|---|---|
| the PR's | rewritten to a **third** hash, `configVersion: 0` | REWRITTEN |
| base | unchanged | FIXED-POINT ← **control** |
| fresh regen under the pinned tool | unchanged | FIXED-POINT |

**One dependency set, three distinct hashes.** The base row is what makes it a defect rather than a
quirk of the tool: the *previous* lock was stable, so the PR introduced the instability.

Consequence chain, each leg at `file:line`: `build.sh:160` stamps the hash as an image label →
`CLAUDE.md:329` tells contributors to run plain `bun install` → doing that changes the hash with
**zero source change** → `pull.sh:252-256` / `build.sh:88-89` compare label vs on-disk hash →
*"Agent-runner lock drift — refusing to tag this image"* / exit 3.

## ⛔ `--frozen-lockfile` exit 0 proves nothing about this

All three locks passed `bun install --frozen-lockfile` with exit 0 and identical package counts, and
CI had **no `git diff --exit-code`** after its install step. So **green CI is fully consistent with a
lockfile no contributor can reproduce.** ⭐⭐ *A frozen install validates that the lock is
sufficient, never that it is canonical.* The two questions are orthogonal, and only the second one
is what the drift guard enforces.

## Generalization

Any artifact whose **hash** (not content) is compared somewhere: lockfiles, vendored bundles,
generated schemas, `requirements.txt`, image digests. The review question is not *"does this
install/build correctly?"* but ⭐⭐⭐**"if a contributor runs the documented command on this tree, does
the hash stay put?"** — and the answer is one command plus one control, not an argument.
