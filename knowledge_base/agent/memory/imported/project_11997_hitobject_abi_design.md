**#11997 "Design: single source-of-truth ABI for HitObject (native DXR SM 6.9 vs NVAPI) — explicit opt-in, no mixed codegen"** — filed 2026-07-08 by **@szihs (maintainer)**, no labels. This is the maintainer formalizing "the investigation and design agreed in team discussion." Explicitly **"Related: #11903 (original bug report), #11907 (draft fix, superseded by this design)."** — so #11997 SUPERSEDES the in-flight #11903/#11907 chain, see [[project_11903_hitobject_sm69_nvapi_pending]].

**The bug it tracks (same as #11903):** `-target hlsl -profile sm_6_9 -capability hlsl_nvapi` → type emits native `dx::HitObject` but constructors emit NVAPI intrinsics against it → mixed ABI, doesn't compile. Root cause: type emitter keys on `targetCaps.implies(_sm_6_9)` while each method's `__target_switch` resolves independently via `isBetterForTarget` (most-specialized wins); `case hlsl_nvapi` out-specializes bare `case hlsl` → NVAPI wins constructors, native wins type → disagree.

**Agreed requirements (design, from body):** (1) NVAPI HitObject must be EXPLICIT opt-in via new `nvapi_hit_objects` capability — never inferred/default (default-on retroactively a bug); (2) inference defaults to platform-standard SM 6.9, NVAPI only when `nvapi_hit_objects` explicitly requested; (3) post-resolution every switch routes NVAPI iff `nvapi_hit_objects` present, else SM 6.9 — no mixed output ever; (4) Slang HitObject API mirrors native-DXR surface, NVAPI-only shapes bottleneck through it or gate behind explicit cap; (5) **Deliverable: inventory ALL HitObject APIs + native-vs-NVAPI signatures** to find where one bottleneck works vs where divergence must be gated.

**Impl sketch (maintainer's):** add `def nvapi_hit_objects : hlsl_nvapi;`; nest `hlsl` ⊂ `nvapi_hit_objects` so NVAPI case wins iff explicitly present, native = base/default; re-gate NVAPI arms `case hlsl_nvapi:` → `case nvapi_hit_objects:`; type emitter keys `implies(nvapi_hit_objects)`; HitObject usage elevates to SM 6.9 unless explicit caps include `nvapi_hit_objects`; for signature-divergent `Invoke` (2-arg native vs 3-arg NVAPI) emit clean cross-ABI diagnostic. NOTE this GENERALIZES #11907's approach (which did single-source (B) + diagnostic but keyed off `hlsl_nvapi`, not a dedicated cap).

**Open questions (UNRESOLVED — design not converged):** (a) can Invoke's 2-arg/3-arg bottleneck through one Slang signature (thread TLAS on NVAPI path) or must stay gated? (b) naming `nvapi_hit_objects` vs `nvapi_ser`? (c) migration guidance for apps relying on implicit NVAPI HitObject.
