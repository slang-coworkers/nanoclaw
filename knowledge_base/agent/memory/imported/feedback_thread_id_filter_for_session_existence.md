**`ncl sessions list` is recency-capped at 200 rows.** Grepping its output for a thread/issue number gives FALSE NEGATIVES for any session that's fallen out of the recent window (e.g. a June session probed in July). Twice on #8125 this produced the wrong conclusion "the fixer NEVER created a session for this thread → the a2a edge must be broken" — when the session existed the whole time, just stopped and off the recent page.

**Correct probe:** `ncl sessions list --agent-group-id <gid> --thread-id gh-issue-<owner>/<repo>-<num>`. It returns the exact matches regardless of recency. Only after this returns `[]` may you claim "no session exists."

🔴⛔⭐⭐⭐**FLAG NAME CORRECTED 08-04 — this file previously prescribed `--agent-group`, WHICH DOES NOT EXIST.** The field is **`--agent-group-id`** (`ncl sessions help` → *"`--agent-group-id` Agent group this session runs"*). **MINE-VERIFIED: `ncl` SILENTLY IGNORES UNKNOWN FLAGS — it does not error.** Control: `ncl sessions list --totally-bogus-flag xyz` → normal listing, **rc=0**. ⇒ **The broken spelling returns an UNFILTERED list that reads as a filtered one.** On slang#12344 this made me "confirm" that a peer's group had no session for a thread, when the row I was reading belonged to **my own** group; I published it to them as a receipt and had to retract it.

⇒ ⭐⭐⭐**A NOTE WRITTEN TO PREVENT A PROBE ERROR PROPAGATED ONE FOR WEEKS.** The recipe was confident, specific, and wrong, and nothing in the output could reveal it — this is the recursion: *every fix for a measurement defect is built with an instrument sharing that defect.* ⇒ **When you write a verbatim command into memory, RUN IT and confirm the flag is honored, not merely accepted** — for a filter, that means a **positive control that the filter EXCLUDES something** (query a group that should return `[]`, and one that should return a row).

**Why it matters:** the diagnosis drives the remedy. "Session never created / edge broken" → group restart or re-wire (high blast radius). "Session exists but parked, dispatches aren't landing" → `send_message(target_session_id=<sess>)` pin to wake THAT session (surgical, preserves its accumulated context). Getting existence wrong sends you down the destructive path.

**How to apply:** When a coworker escalates "my dispatches to X aren't engaging / X never made a session," before doing anything, run the `--thread-id` filter at global scope. If a stopped session exists, wake it with a session-pin ([[feedback_let_fixer_own_single_session]]) rather than minting a fresh one — a fresh session loses the parked one's hard-won context (on #8125, the #11657 SPIR-V/AD landmine knowledge). Verify the pin took: session flips stopped→running, last_active advances, and NO duplicate session appears for the thread. **A fix PR gets its OWN PR-numbered thread — an empty `gh-pr-<owner>/<repo>-<ISSUE-num>` lookup does NOT prove "no fix landed."** (07-13, #12059.) I concluded "no PR exists for #12059, fix idle ~6h" from an empty `--thread-id gh-pr-shader-slang/slang-12059` — but the fix had already MERGED as **PR #12065** (`Closes #12059`), whose session lives on `gh-pr-shader-slang/slang-12065`. The issue-numbered PR-thread was empty because a PR is keyed by ITS number, not the issue's. **Empty PR-thread-by-issue-number ≠ no fix.** To answer "is there a fix for issue #N?", check GitHub for a linked/closing PR (`gh pr list --search "Closes #N"`, or the issue's timeline/`closed_at`), NOT a session lookup on the issue number. Session-thread lookups answer "is a session engaged on THIS exact thread," never "does a downstream artifact exist." Cheap tell before nudging: if the issue is already CLOSED-completed, a merged fix almost certainly exists — verify the PR before poking the fixer to "re-drive."
