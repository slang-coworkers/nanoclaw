**Finding:** The `VUID-StandaloneSpirv-None-10684` ("Invalid explicit layout decorations on Workgroup type") error seen under `slang-test -enable-debug-layers true` on groupshared tests is emitted by **Dawn's internal tint** (WGSL→SPIR-V on its forced Vulkan backend) — NOT Slang's SPIR-V emitter. Slang's own vk-path SPIR-V carries no ArrayStride on Workgroup arrays (stride gated to StorageBuffer/PhysicalStorageBuffer, slang-emit-spirv.cpp ~2445) and the embedded validator (v2026.2) accepts it. Three proofs: (1) `static-var-in-generic-type.slang` has no vk variant yet still trips vkCreateShaderModule → only the wgpu (Dawn-on-Vulkan) variant can reach Vulkan; (2) the 1.4.328 layer passes the vk variants, fails only the wgpu variant of the same shader; (3) producer fingerprint `%_arr_…_uint_N` (tint) vs Slang's `…_int_N`.

**Why tests pass:** VUID-10684 is a non-fatal validation-layer diagnostic — `vkCreateShaderModule` still returns VK_SUCCESS, the decoration is inert for real Workgroup memory, and COMPARE_COMPUTE grades the output buffer (stdout), not stderr.

**Why this matters / do-not-fix:** The tempting fix ("Slang should emit ArrayStride + WorkgroupMemoryExplicitLayoutKHR for groupshared arrays") is **REFUTED** — wrong layer; Slang's SPIR-V is already valid. Do NOT dispatch a fixer to add ArrayStride to Slang's Workgroup emission for this.

**Status:** parked, issue open, no fixer. Next move is a maintainer/spec call — file upstream with Dawn/tint, pin/track the 1.4.328 validator, or treat as benign. Re-engage only on a substantive human comment or explicit go.
