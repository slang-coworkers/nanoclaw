# Slang specialize.cpp: expanded-memo requires the re-drain loop; mutation-site requeues must enqueue-then-force

Context: shader-slang/slang#12604 / PR #12608 refactors `SpecializationContext`'s work list — splits the dual-role `workListSet` into `workListSet` (queued) + a per-drain `expanded` seeding memo, and converts the mutual `addToWorkList`/`addUsersToWorkList` recursion into an iterative `expandUseClosure`. Non-obvious findings, verified with 3 adversarial codex rounds + a 4087-test instrumented sweep + byte-identical emitted-CUDA checks:

1. **Do NOT remove the on-demand `specializeChildInsts` re-drain loop just because it "never fires."** Instrumenting it across 4087 tests showed no second-or-later drain ever found work — tempting to call it a dead safety net. But it is load-bearing for a subtle reason: converting the recursion to an iterative work-stack CHANGED the forward-use-closure ENQUEUE ORDER, and single-drain completeness is order-sensitive. The forced walk descends into a user iff it was newly queued (as the recursion did), so a no-op wrapper (`PtrType`/`TupleType`/… with no `maybeSpecializeInst` case) that is still queued when its grand-operand specializes shadows an already-popped `specialize` user. Concrete IR shape: `%S→%U, %S→%M, %M→%U, %U→%D`, `%U=TupleType(%S,%M)`, `%D=specialize(%G,%U)`, `%S` use-order `[%U,%M]` — iterative single-drain processes `%D` before `%M` and misses it; master's recursion enqueues `[%U,%D,%M]` and catches it. The re-drain loop makes output order-independent (= byte-identical to master). Removing it is a REGRESSION, not a simplification. Alternative if you must drop the loop: reproduce master's exact pre-order enqueue AND drop the memo (then single-drain is complete by construction — but you lose the dual-role split).

2. **Any site that requeues an EXISTING inst after a mutation must `enqueue(x); addUsersToWorkList(x)`, NOT `addToWorkList(x)`.** `addToWorkList` runs the `expanded`-memoized SEEDING walk, which pre-marks x's direct users `expanded` and then BLOCKS a subsequent force-walk (transitive re-notification lost). Two such sites in this pass: `maybeSpecializeFoldableInst` (peephole fold) and `maybeSpecializePackBranch` (which had `addToWorkList(replacement)` BEFORE `addUsersToWorkList(replacement)` — ordering defeats the force). All other ~14 `addToWorkList` sites enqueue freshly-created insts (not in `expanded` → safe); a `replaceWith` lambda force-walks the old users BEFORE `replaceUsesWith` (safe). Auditing this took TWO codex rounds — the coupling is easy to miss.

3. **Byte-identical verification trick without a full master build:** the pass compiles into `libslang-compiler.so`, not the thin `slangc` front-end. Build once, then swap ONLY `slang-ir-specialize.cpp` to the merge-base version, incremental-rebuild, save the `.so`. Run both by keeping the SAME build-tree `slangc` (so prelude path resolution matches — otherwise one INLINES the CUDA prelude and one `#include`s it, giving an 8000-line false diff) and selecting the payload via `LD_LIBRARY_PATH` (RUNPATH is searched after LD_LIBRARY_PATH; `ldd`-confirm). Compare EMITTED code (`-target cuda`), not `-dump-ir` (UID noise). Compare against the merge-base pass, not a full-tree master build — isolates the PR's effect.
