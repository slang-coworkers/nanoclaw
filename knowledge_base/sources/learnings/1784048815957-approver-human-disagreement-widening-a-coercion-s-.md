# [approver/human-disagreement] widening a coercion's viability interacts with overload resolution — probe for silent-ambiguity blast radius

Symptom: PR #11818 (fix #11730) un-nested a `return true` in `createInvokeExprForExplicitCtor` so an initializer-list argument reports itself as a viable coercion whenever its constructor type-checks (canCoerce probe now agrees with real coercion). My decision was ABSTAIN_POLICY (author_trust clause FAIL — bot-authored CONTRIBUTOR), so the challenger never ran. Between my decision commit and the merge, the maintainer (skiminki-nv) required ONE more commit before approving: an ambiguous-overload regression test (`init-list-as-arg-ambiguous.slang`).

The delta I could have seen coming: a function-call argument, unlike a var-decl initializer (`float3 c = {a,b}`) or a return value, goes through OVERLOAD RESOLUTION. Making more constructors viable during the canCoerce probe means a brace initializer like `{a, b}` (int2 + int) can now match MULTIPLE overloads — e.g. both `f(int3)` (flatten int2→2 components) and `f(ABC{int2;int})`. The correct behavior is a diagnosed AMBIGUOUS call, not a silent pick. The maintainer's concern was precisely that widening viability must not cause silent overload selection; the added test pins `//CHECK: ambiguous call`.

How to catch it (transferable): when a change WIDENS a type-coercion/conversion's viability answer (returns "coercible" in more cases, especially by un-gating a probe path so canCoerce agrees with real coercion), the blast radius is not just "more code compiles" — it is overload resolution. Ask: does this conversion now make previously-non-viable candidates viable, and if so can two candidates become equally applicable for the same argument? If yes, the fix must ensure the result is a *diagnosed ambiguity*, not a silent choice, and should carry an ambiguity regression test. This is the class of question the challenger (Step 3) should raise for any init-list/coercion-viability-widening change touching slang-check-conversion.cpp — flag "overload-ambiguity coverage" as a gap even when the direct positive/negative tests pass.

Note: this PR was ABSTAIN_POLICY (correct human-look hold; abstains excluded from agreement scoring) and merged with human APPROVED — so not a false-safe. But had the author been trusted and the challenger run, this is the gap I'd want it to surface. Fix: add "widening-coercion → overload-ambiguity" to the challenger's probe list for coercion changes.
