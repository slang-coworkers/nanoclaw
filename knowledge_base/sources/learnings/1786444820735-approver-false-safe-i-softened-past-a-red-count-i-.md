# [approver/false-safe] I softened past a red count I wrote myself — and my "over-conservative" calibration prior is what pushed me to do it

**Symptom** (slang-rhi#827, 2026-08-11): I wrote `bugs: 1` into my own synthesized review doc's embedded `_approver_result` block, then recorded `ABSTAIN_POLICY:OPEN_GAP`. Step 2 of the approver procedure is a **parse, not a judgment** — "any 🔴 Bug ⇒ BLOCK" — and `ABSTAIN_POLICY` is strictly *less* severe than `BLOCK`. So continuing past `bugs=1` to a softer state was exactly the upgrade the skill forbids the challenger to make ("investigation can only add caution, never upgrade a doc's 🔴 toward approval"). DECISION_REVIEW caught it (must-fix ×2, then approve); revised to `BLOCK:RED_BUG`.

**The structural tell:** two self-consistent positions existed and I took neither. Either `bugs=1` is the faithful count ⇒ BLOCK, or the source behind it is discounted ⇒ rewrite the block to `bugs=0` and grade gaps ⇒ OPEN_GAP. **A decision that contradicts a counter you yourself wrote is incoherent regardless of which branch is correct.** Cheap check, never run: re-read your own embedded result against your own verdict line before recording.

**Three defective premises produced the softening — all mine, none the bots':**

1. **Contamination rule applied to the wrong *class* of claim.** I discounted a reviewer's 🔴 because its capture postdated the PR merge. But a merge changes **time-varying** state (CI colour, whether a human objected); an **ABI break is a timeless property of the diff**. The reviewer read the diff at the pinned head — the merge did not alter what it read. Before discarding a late artifact, ask *could this specific claim have changed?* A rule learned from one class (here: a prior post-merge-contamination lesson) **silently widens to all classes unless its scope is written down**.
2. **Absence read off my own truncated grep.** I marked the binary-compat leg UNCONFIRMED because "no binary distribution appears to exist". My `install(` probe printed 2 lines and I concluded `install(TARGETS ...)` was absent — it was there, installing both library and headers, alongside a `*_BUILD_SHARED` option. The mixed-version configuration is *supported*, so the leg was confirmable all along. Two compounding errors: **"0 releases / 0 tags / no SOVERSION" bound the PREVALENCE of a deployment, not whether the contract is broken** (conflating "unlikely to be observed" with "not broken"); and **"uncertainty does not round up" was sound as a rule and vacuous as applied** — there was no uncertainty, only an unrun check. *Dressing an unrun check as principled caution is the failure mode to name.*
3. **A number lifted from a source I had myself declared unusable.** I wrote "CI 26/26 green" — copied from the post-merge capture whose time-varying claims I had discarded two paragraphs earlier. Independent check: 27 rollup entries, 25 SUCCESS + 2 SKIPPED. The count was wrong *and* the sourcing contradicted my own stated rule. **When you declare a source unusable, grep your own draft for numbers you took from it.**

**The calibration trap — the most transferable part.** My measured record on this repo is *over-conservative* (several prior abstains merged unchanged, same author). That prior pushed me to **soften** a red finding. It was right about my history and wrong about this decision. **A calibration prior is a reason to re-examine evidence, never a thumb on the scale for a specific verdict.** Note the direction: correcting for over-conservatism moved me to the *hardest* available state — against both the prior and the eventual human outcome. If a prior about your aggregate behavior is doing work inside a single verdict, it is being misused.

**Two smaller corrections of the same family:** I claimed an assertion "discriminates" between two policies after verifying only one branch — it is vacuous on 2 of 7 backends whose *concrete* implementations return the same error code as the virtual one, while the test is registered for all backends (**a discrimination claim is about both branches; enumerate both**). And I cleared a coverage flag by asserting a capability boundary ("those are the backends with feature X support") that I never checked — **a clearance is a claim; inventing a boundary to dispose of a finding is the same failure as the premise above**.
