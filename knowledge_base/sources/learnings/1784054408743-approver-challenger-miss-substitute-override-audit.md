# [approver/challenger-miss] Substitute-override audits must cover every _substituteImplOverride file, not just val.cpp/decl-ref.cpp

**Symptom:** On slang#12098 (memoize Val substitutions — a cache storing the `ioDiff` as a delta and replaying it via `*ioDiff += delta`), an approver source-audit subagent tasked to verify the "ioDiff is increment-only" contract concluded SAFE after reading only `slang-ast-val.cpp` + `slang-ast-decl-ref.cpp`. It reported "all override impls only use `++`/`+=`, never `=`." That was **incomplete**: `ModifiedType::_substituteImplOverride` lives in `slang-ast-type.cpp` (line ~2194) and does `*ioDiff = 1` — an assignment/clobber, the one override that violates the increment-only convention. The production claude-code-action review caught it (its gap #5); the scoped audit missed it.

**Root cause:** `_substituteImplOverride` methods are spread across at least three files — `slang-ast-val.cpp`, `slang-ast-decl-ref.cpp`, AND `slang-ast-type.cpp` (Type subclasses like ModifiedType live in type.cpp). An audit that names only the first two silently under-covers the override set. `gh api "search/code?q=repo:shader-slang/slang+<Class>+_substituteImplOverride"` or a tree-wide grep for `_substituteImplOverride` enumerates the true set.

**How to catch it:** When a PR changes a dispatch/visitor boundary (`substituteImpl`, `_substituteImplOverride`, or any `SLANG_AST_NODE_VIRTUAL_CALL`-fronted method) and its correctness rests on a *convention every override obeys* (e.g. "ioDiff is increment-only", "returns `this` when unchanged"), do NOT trust a partial file list. Enumerate ALL overrides tree-wide first, then spot-check the ones most likely to break the convention (Type nodes in type.cpp are frequent outliers). The primary bot review harvested at head is a strong cross-check precisely because it reads the whole tree — reconcile the local audit against it rather than treating the local audit as complete.

**Fix / outcome:** The ModifiedType `*ioDiff = 1` clobber turned out **boolean-safe** vs the cache's `*ioDiff += delta`: every downstream `diff`/`ioDiff` consumer in the substitution code tests zero-vs-nonzero only (`if(!diff)`, `if(diff)`, `if(diff!=0)`) — zero magnitude comparisons — so `= 1` and `+= (delta≥1)` both yield non-zero on the changed path. So the finding was a real latent-fragility gap (correctly 🟡, not 🔴) with no observable divergence, and the decision stayed WOULD_APPROVE. But had any consumer compared magnitude, the delta-replay cache would have diverged — which is exactly the class of bug a complete override audit exists to surface. Lesson: verify the *consumer contract* (boolean vs magnitude) whenever a change stores-and-replays a running counter like ioDiff.
