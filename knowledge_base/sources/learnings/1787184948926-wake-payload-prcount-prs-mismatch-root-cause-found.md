# Wake payload prCount/prs mismatch root cause found: unpaginated task-script fetch + hardcoded slice(0,20)

Resolves the open caveat in 2026-08-16 and 2026-08-20 learnings about `prCount` vs `prs.length` mismatch. The wake payload is NOT built by anything in `/workspace/agent/` — it's generated by a Node script embedded directly in the scheduled task definition. Find it via `ncl tasks list` → `ncl tasks get <series-id>` (for the babysitter: `task-1776715487702-ftr4s6`, recurrence `0 */2 * * *`). Read the `script` field.

Two independent, compounding bugs in that script:
1. `prCount = nonDraft.length` is computed from a **single unpaginated fetch** (`/pulls?state=open&per_page=50`, no page loop) — silently undercounts once total open PRs (draft+non-draft combined) exceed 50, since GitHub's default order is newest-first and older PRs fall off the fetched page.
2. `prs: nonDraft.map(...).slice(0, 20)` — the array is **hardcoded-truncated to 20** regardless of `prCount`, with no `hasMore`/`totalCount` flag exposed. So `prCount` and `prs.length` only agree when true non-draft count ≤ 20.

Live 2026-08-20 check: `gh pr list --repo shader-slang/slang --state open --draft=false --json number --jq 'length'` → 30, vs payload's `prCount: 24` and `prs.length: 20`. Same `evicted` list is built the same unpaginated way (`/actions/runs?event=merge_group&per_page=50`) — untested but same defect class, flagged as hypothesis only.

Takeaway: when a NanoClaw wake-payload/script bug needs root-causing, check `ncl tasks get <series>` BEFORE grepping the workspace or repo — the generator often lives entirely in the task's `script` field, invisible to filesystem search. `/app/src/scheduling/task-script.ts` is the host runtime that executes it (30s timeout, JSON-parses the last stdout line).

Never trust `prCount`/`prs` as ground truth for population size — always cross-check with a fresh `gh pr list --state open --draft=false` when correctness matters, per the existing "assert got>=total_count unconditionally" rule.
