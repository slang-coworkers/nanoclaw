# [approver/challenger-confirmed] New attribute-target widening: positive-control-per-mechanism + non-vacuous negative test

**Context:** slang#12689 "Allow user-defined attributes on enum members" (Fix #12551), WOULD_APPROVE, Devin-only tier. **Symptom / shape:** front-end WIDENING — allow a construct that was previously rejected. Distinct from the narrowing case (new rejection/diagnostic). Widening cannot create a dead-flag-always-skip and cannot break existing programs *by rejection*, so the standing gate/flag positive-control probe's severity is lower — BUT a **new attribute target is not pure widening of an existing flag**, it is a new capability, so it still earns a positive control.

**The checks that actually carried the decision (transferable):**
1. **Is the widening pure?** Find what the pre-change code did at the exact syntactic position. Here pre-PR `parseEnumCaseDecl` had NO `[` handling ⇒ `[` at a case always errored E20001, so the new `while(peek==LBracket) ParseSquareBracketAttributes(...)` loop only *rescues* previously-erroring input and touches nothing valid. Key subtlety the author got right and I verified: the loop is **bracket-only and never calls `ParseModifiers`**, because an enum case name can itself be a bareword modifier keyword (`point`, `linear`, `sample`) that `ParseModifiers` would eat — a regression the naive fix would introduce. Probe: "does the new collector consume more than the brackets?"
2. **Is the negative test vacuous?** A "wrong-target is rejected" test only carries bits if the target class is genuinely NOT a subclass of the attribute's declared target. Verified `EnumCaseDecl : public Decl` (NOT `VarDecl`), so a `Var`-only attr genuinely fails `effectiveAttrTarget->getClass().isSubClassOf(VarDecl)`. Always confirm the class hierarchy — a negative test where the two classes ARE related passes vacuously.
3. **Is the new target a live flag?** Trace set→match→consume: value read via `checkConstantEnumVal` at the `[__AttributeUsage]` site → matched exact-`==` in `getAttributeTargetSyntaxClasses` → `AttributeTargetModifier`. Demand a **positive control per claimed mechanism**: this PR touches parse, reflect, AND serialize round-trip, so it needs (and had) a test whose assertion fails if attributes don't survive EACH — `enum-case-attribute.slang` (codegen), `unit-test-enum-reflection.cpp` (getUserAttributeCount/arg values), `unit-precompiled-module-attribute.cpp` (findUserAttributeByName after module reload). Reflection/serialization are the mechanisms most likely to silently drop AST-modifier data (user attrs live in AST modifiers, not IR decorations).
4. **Inert-constant check:** a bumped bitmask (`All 0x0F→0x1F`) is only safe if nothing reads it. deepwiki confirmed `All` is a defined-but-unused sentinel here. Don't assume; confirm the constant has no reader.
5. **ABI:** `UserDefinedAttributeTargets` is in internal `source/slang/slang-syntax.h`, not `include/` — appending a value is fine. The mirrored `_AttributeTargets` core-module enum is additive.
