# Slang truncates matrices via an explicit-only generated ctor — verify at the generator, not the grep

Question (Slang Discord, 2026-08-07): is `(float3x3)someFloat3x4` legal, for pulling the rotation part out of DXR's `CommittedObjectToWorld3x4()`?

**Yes, and it yields the upper-left 3×3 — but it is EXPLICIT-only.**

- Generated, not written: `core.meta.slang:2857-2867` loops `rr` from `R..4`, `cc` from `C..4` and emits `__intrinsic_op(kIROp_MatrixReshape) __init(matrix<T,rr,cc,L> value)`. For `R=C=3` the `rr=3,cc=4` iteration is exactly the `float3x3 ← float3x4` ctor. Only larger-or-equal sources are generated.
- **Implicit assignment is rejected**: the builtin matrix→matrix coercion at `slang-check-conversion.cpp:2237-2244` requires equal row AND column counts (it exists only to change *layout*), and the generated truncating `__init` carries no `__implicit_conversion` marker. So `float3x3 m = my3x4;` errors while `(float3x3)my3x4` compiles. Keep the cast.
- **Upper-left, provably**: `slang-ir-peephole.cpp:1575-1618` truncates rows, then `slang-ir.cpp:4643-4652` reshapes each row by swizzling indices `[0..toCount)`. Runtime-pinned by `tests/bugs/matrix-reshape.slang`, which truncates a `float4x4` and asserts `m3[0][0]+m3[1][1]+m3[2][2] == 18` (=1+6+11) on DX/Vulkan/CPU/CUDA — arithmetic that only holds for the upper-left submatrix. Growing instead zero-pads.

**Method lessons, two of them:**

1. **`grep 'float3x3'` on `hlsl.meta.slang` returns ZERO** — the concrete spellings are typedefs emitted by a C++ meta-generator (`core.meta.slang:2601`), and the truncating ctor is generated by a loop. Both the type name and the declaration are invisible to a literal grep. Second time this week the same trap fired (cf. `$(ccName)`-generated RayQuery methods). **In `*.meta.slang`, grep the generator, not the spelling users type** — and treat a zero-hit grep on these files as "wrong query", not "absent".
2. **Docs gap worth knowing**: matrix truncation is a real, CI-tested feature that appears nowhere in `docs/user-guide/02-conventional-features.md` or `a1-01-matrix-layout.md`. So "not in the docs" was not evidence either.

**Also useful, verified:** `mul(vector, matrix)` (vector on the LEFT) exists at `hlsl.meta.slang:13611` and emits `OpMatrixTimesVector`. Since `vᵀM ≡ Mᵀv` and `inverse-transpose(ObjectToWorld) == transpose(WorldToObject)`, the correct normal transform is just `mul(nObj, (float3x3)CommittedWorldToObject3x4())` — no `transpose()`, no inversion, one instruction fewer than the transpose spelling. Tangents take the *ordinary* transform (`mul(o2w, tObj)`), not the inverse-transpose — they're surface directions, not perpendiculars. And the free-function `WorldToObject3x4()` is stage-gated `[require(..., raytracing_anyhit_closesthit_intersection)]` (`:20289`), so inline ray tracing in a compute shader must use the `RayQuery` member form.

Unpinned composition I flagged rather than asserted: no test does `(float3x3)CommittedObjectToWorld3x4()` in a single expression — the two halves are each tested, the join is not.
