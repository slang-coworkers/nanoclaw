# expand/each unroll count uses unflattened operand count of nested makeValuePack (slang#12796)

**Symptom:** `slangc` segfaults (Release, exit 139) / hits `SLANG_ASSERT(slang-ir-lower-tuple-types.cpp:134)` in `TupleLoweringContext::processGetTupleElement` — an out-of-range `getTupleElement(pack, i)` on a pack whose flattened arity is smaller than `i`. Only crashes on **whole-module** compile (no `-entry`); with `-entry` the offending generic is DCE-scoped away, so `slang-test` (always passes `-entry`) never catches this class. Repro: `slangc -target spirv-asm -experimental-feature -I tests/neural tests/neural/network-parameter-layout-converter-buffer.slang -o /tmp/o.spvasm`.

**Root cause (the non-obvious part):** `maybeSpecializeExpand()` (`source/slang/slang-ir-specialize.cpp:3180-3187`) derives the `expand` unroll count from `getCapture(0)->getOperandCount()`. When the capture is a **concatenation** `makeValuePack(scalar, nestedPack)` (typed e.g. `TypePack(Int, ValuePackType(Int))`), that raw operand count is **2** (scalar + one nested-pack operand), but the *flattened* arity is 1 when the nested pack is empty. The count (2) then disagrees with the flattened `getTupleElement` domain (1). `clonePatternValImpl` (`slang-ir-lower-expand-type.cpp:24-33`) reuses that single index across every `IREach` with no arity check. A `flattenPackOperand` helper already exists at `slang-ir-specialize.cpp:836` (used by `maybeSpecializeTypePackOrTupleType`) but the count sites don't call it. Same latent "first pack / unflattened count" pattern at AST analogs `slang-ast-type.cpp:1644` (`firstConcretePackSize`) and `slang-ast-val.cpp:3099` + `EachIntVal` silent fall-through.

**Triage lesson — don't rubber-stamp a reporter's §5:** the reporter framed it as "either the producer built a too-short pack, or the front-end should have diagnosed an arity mismatch." Both were **wrong as stated**: (a) the flattened `makeValuePack(2)` is *correct* for an empty tail pack — no producer built a bad pack; (b) the crashing `expand` indexes a **single** `each`-ed pack (others are broadcast scalars) → the program is well-formed, so a front-end arity diagnostic would false-reject valid code. Slang's real arity machinery (`E30438 GenericArityMismatch` @ `slang-check-overload.cpp:2939`; `computeTypePackUnificationMapping` uneven-division reject @ `slang-check-constraint.cpp:4236`) correctly does NOT fire here. The true owner is the count/flatten logic. Lesson: a "diagnosed, not fixed" report is a strong start, but confirm the *mechanism* by reading the IR (`-dump-ir-before specializeModule` shows the unflattened capture; `-dump-ir-before lowerTuples` shows the flattened `makeValuePack(2)` + OOR `getTupleElement`) before relaying the owner claim.
