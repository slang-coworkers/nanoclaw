# Slang autodiff wires Optional intrinsics but omits the parallel Conditional family (E99999)

**Finding (slang #11784, verified @HEAD 1a0c2a6d1).** `bwd_diff` of a `[Differentiable]` fn that calls `Conditional<T,b>.get()` aborts with `internal error[E99999]` pointing at `.get()` — even with a concrete literal flag (`true`), no generics.

**Root cause:** The autodiff transcriber knows the **Optional** intrinsic family but NOT its structural sibling **Conditional**. `Conditional<T,bool hasValue>` (core.meta.slang:1875-1909) exposes its `value` getter as `__intrinsic_op(kIROp_GetConditionalValue)`. `ForwardDiffTranscriber::translateInstImpl` (slang-ir-autodiff-fwd.cpp ~2600-2830) has cases for `GetOptionalValue`(:2663→translateGetOptionalValue:1848)/`MakeOptionalValue`(:2624)/`MakeOptionalNone`(:2688)/`OptionalHasValue`(:2796) but **none** for `kIROp_GetConditionalValue`/`MakeConditionalValue` (grep: zero matches in any slang-ir-autodiff*.cpp). So the inlined GetConditionalValue returns {null,null} and `translateInst` (fwd.cpp:3504-3505) raises `InternalCompilerError{.location=origInst->sourceLoc}`. Fix = mirror the Optional handling across fwd/transpose/primal-hoist (+ ConditionalType diff in differentiateType only if a *differentiated* Conditional flows through).

**Two reusable methodology lessons:**
1. **`bwd_diff` builds the FORWARD-diff fn first**, then transposes. So a backward-mode ICE can actually fire in the forward transcriber. Evidence: the `-dump-ir` showed `s_fwd_fn` only partially built (just GetDifferential/GetPrimal). A subagent guessed the throw was the transpose default (transpose.cpp:1588 SLANG_UNEXPECTED) — that site is real but UNREACHED for this repro; forward aborts first.
2. **Use the error's source-loc to discriminate throw sites.** `SLANG_UNEXPECTED(...)` attaches NO source loc; the forward transcriber's `InternalCompilerError{.location=origInst->sourceLoc}` does. The user-facing caret pointing at `.get()` proved it was the fwd `InternalCompilerError` default, not the locless transpose assert. Always verify a subagent's throw-site claim against (a) IR-dump partial state and (b) whether the user-facing loc matches `origInst->sourceLoc` — don't relay the guess.

**GH tooling:** `gh auth status` reporting "GH_TOKEN invalid" + `gh api user` 403 ("Resource not accessible by integration") are NORMAL false-negatives for a GitHub **App installation token** — repo-scoped writes (labels, comments, GraphQL Issue Type) still succeed. Don't conclude writes are broken from those two signals; the canary is an actual repo-scoped write.
