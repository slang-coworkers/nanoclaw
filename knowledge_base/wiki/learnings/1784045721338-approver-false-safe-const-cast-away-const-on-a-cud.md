# [approver/false-safe] const_cast-away-const on a CUDA grid-constant kernel param can miscompile at the hardware level — static review cannot clear it

**Symptom:** On shader-slang/slang#12080, I recorded WOULD_APPROVE across FOUR revisions (59d7eb0, 7b2dbbc12e, 849fc6f70969, 077d11a686a9) of a CUDA perf fix that marked entry-point by-value uniform aggregate kernel params `__grid_constant__ const` and forwarded their address into a `borrow in` helper via `const_cast<T*>(&param)`. The author then PIVOTED (head 25d931013795, commit msg changed to "forward entry-point uniform aggregate address"): removed the qualifier + const_cast entirely, going forward-only (`&param`, plain by-value param). The new tests carry `CHECK-NOT: __grid_constant__` / `CHECK-NOT: const_cast` regression guards and state the qualifier approach **"miscompiled on sm_100 / NVRTC and provided no measured speedup."** The head-current production review corroborated, calling it "the removed miscompiling qualifier."

**Root cause:** Every static signal cleared the `__grid_constant__` + const_cast approach every round: the production github-actions[bot] review reported "0 bugs / no correctness problems" (with dedicated IR-correctness + memory-safety + cross-backend passes that even checked "const_cast UB"), Devin reported "0 bugs / 0 flags," and my challenger reasoned the const_cast was sound because uniform entry-point params are read-only by language semantics (confirmed via deepwiki). All of that is *source-level / language-semantics* reasoning. The bug was a **hardware/driver-specific codegen miscompile** (sm_100 / a specific NVRTC): `__grid_constant__` tells the toolchain the param lives in immutable constant grid memory, and `const_cast`-ing away that const to forward a mutable-looking pointer is exactly the kind of construct a backend can miscompile — but only *that arch/driver* surfaces it, at runtime. Source-emit FileCheck tests and trace-level review are structurally blind to it.

**How to catch it:** When a change (a) casts away `const` / a type qualifier that the *target toolchain treats as a real semantic guarantee* (grid-constant, `__constant__`, restrict, etc.), or (b) relies on a backend/driver honoring an aliasing/memory-space contract, do NOT treat "0 bugs" from source-level reviewers + language-semantics reasoning as sufficient. Such constructs need **GPU-execution coverage on the target arch** (a COMPARE_COMPUTE / NVRTC-compiled-and-run test), not just source-emit FileCheck. If that execution coverage is absent, the correctness of the qualifier+cast is UNPROVEN by the available evidence → lean ABSTAIN (OPEN_GAP: "qualifier/cast correctness only verified at source level; no target-arch execution test"), not WOULD_APPROVE. A `const_cast` that exists *specifically to bridge a qualifier the emitter added* is a red flag: the simpler design (here, forward-only with no qualifier + callee-copies-before-write) is both sound and testable.

**Fix / calibration:** Recorded 4 false-safes on this PR (the __grid_constant__ revisions); the human/author outcome (pivot away from it as miscompiling) is the ground truth. Add to Step-0 recall for CUDA/emitter changes: "qualifier + const_cast to bridge it → demand target-arch execution coverage or ABSTAIN." Note the current forward-only revision (which I WOULD_APPROVE'd at 25d931013795) is the sound version and DOES add NVRTC COMPARE_COMPUTE tests — that's the coverage the earlier approach lacked. Caveat: the "miscompiled" claim originates in an untrusted PR artifact (author's test comments), but is corroborated by the production review's independent "removed miscompiling qualifier" phrasing.
