# [approver/false-safe] A test weakened to green a REPRODUCED failure on the code under review is a hard no-approve signal — read the test diff, not just the green

**Symptom:** slangpy#1075 finally added the reviewer-requested regression test (33-texture batched upload with `generate_mips`, validating texel data via `memcmp`). At head `b91339d` that test FAILED deterministically on the Metal backend (macos aarch64 clang, BOTH Release+Debug — 32 failed assertions, real values `-93 == 0`, `-157 == 0`) while Linux/Windows passed. The very next push (`d001b2b`, titled "Make batched upload regression portable") made CI green again — but it did so by DELETING the failing comparison: the test had compared every mip level of each array layer against layer 0; the "fix" removed the mip loop so it now compares only mip 0. Mip 0 is the directly-uploaded base data (which matched); the GENERATED mips (levels 1+) that actually differed are no longer asserted.

**Root cause / why it's dangerous:** A naive approver that only checks "is CI green at the head?" or "does the requested test now exist?" would see: gap fixed + test added + CI green → approve. That's a false-safe. The green was manufactured by narrowing the assertion to exclude the exact thing that failed, on the exact code path under review (batched texture-array upload + per-item mip generation — the path Devin flagged 🔴 and CodeRabbit flagged Major). All N array layers receive byte-identical input through the same `generate_mips`, so their generated mips SHOULD be identical; a within-run cross-layer divergence on one backend is a real defect signal, not a test-portability issue — "portable" was a euphemism for "stops asserting the broken part."

**How to catch it:** When a revision adds/edits a test on the reviewed path, ALWAYS diff the test itself (`gh api commits/<sha> --jq '.files[]|select(.filename|test("test"))|.patch'`), don't just note "test added" or "CI green." Ask: did the assertions get STRONGER (more coverage) or WEAKER (fewer levels/cases/fields checked)? Cross-reference against any recent red CI on the prior head — a test-only push that follows a real test failure is suspect until you confirm it FIXED the code, not muted the check. A `memcmp`/data-validation assertion narrowed to a subset (here: all-mips → mip-0-only) right after that assertion failed for real is the tell. Pull the failing job log at the prior head (`actions/jobs/<id>/logs`, grep `ERROR: (CHECK|REQUIRE)` + `values:`) to see exactly what was failing before deciding the follow-up "fixed" it.

**Fix / decision:** This is NOT an approve — two independent sufficient reasons: (1) a head-current reviewer 🔴 remained on the path (binding rule: investigation only adds caution, never upgrades a review 🔴); (2) the PR's own regression test demonstrated a real, deterministic, backend-specific defect and the response was to stop testing it. Recorded ABSTAIN_POLICY:OPEN_GAP with "human must look at the removed mip assertions + the Metal cross-layer generated-mip divergence." Stopped short of a verified hard-fail only because I couldn't prove from the lab whether the divergence is a `create_texture_array` bug vs a Metal/mip-gen backend quirk, and CodeRabbit hadn't re-reviewed the head — but a weakened-test-over-a-real-failure is, at minimum, a mandatory human-look and must never round up to approve. Also: CI matrix shape distinguishes flake from real — R6 was 1/12 cells (linux-gcc-release timing flake in a non-PR test); this was a consistent 2-cell same-platform pair (macos R+D) in the PR's OWN new test with real data mismatches = reproduced regression. See [[slangpy-1075]].
