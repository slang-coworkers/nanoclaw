# Adding a SPIR-V capability atom — ADDENDUM (two generated docs + test -capability)

# Addendum to "Adding a SPIR-V capability atom to Slang (capdef recipe)"

Two things from the #11541 review (shader-slang/slang) that the original recipe missed and that WILL fail CI / draw review nits if skipped:

## 1. A capdef atom change touches TWO checked-in generated docs, not one
- `docs/user-guide/a3-02-reference-capability-atoms.md` — regenerated by the build (`slang-capability-generator`), atoms listed **alphabetically**.
- `docs/command-line-slangc-reference.md` — **also enumerates capability atoms**, produced by `slangc -help-style markdown -h`, atoms listed in **declaration order**. Enforced by `.github/workflows/check-cmdline-ref.yml`, which does a **byte-exact** `diff` of `slangc -help-style markdown -h` against the checked-in file.

Regenerate BOTH and commit them:
```
slangc -help-style markdown -h > docs/command-line-slangc-reference.md   # after building with the new atom
```
The cmdline-ref file has **trailing spaces** (raw slangc output) — do NOT run prettier on it; that would strip them and break the byte-exact check. (`check-cmdline-ref.yml` and `check-formatting.yml` are both **draft-gated** — `draft != true` — so they only fire once the PR is marked ready, but a maintainer flipping it ready will hit them.)

## 2. The regression test needs `-capability <atom>` in the directive
```
//TEST:SIMPLE(filecheck=CHECK):-target spirv-asm -entry computeMain -stage compute -emit-spirv-directly -capability spvShader64BitIndexingEXT
```
Sibling `spirv_asm` SIMPLE tests pass it (e.g. `tests/spirv/deduplicate-annotation-spirv-asm.slang`). Without it, the `[require(<atom>)]` on a called function trips an implicit-capability-upgrade warning that fails under a `-restrictive-capability-check` config. Also: drop any `//TEST_INPUT:ubuffer(...)` line in a SIMPLE test (it's consumed only by execution directives like COMPARE_COMPUTE, ignored by SIMPLE), keep just the buffer declaration as the entry-point storage anchor.

## 3. Frame the test honestly
For an inert atom, the test is a *capability-declaration smoke test*: the `[require(<atom>)]` type-check is the real regression guard; the `// CHECK: OpCapability/OpExtension` lines only prove `spirv_asm` literal passthrough (hoisted verbatim), NOT atom-driven emission. Name the function for "requires the capability", not "uses <feature>". Put any future-consumer gating caveat as a plain `//` note (NOT in the `///` auto-doc line, which feeds the user-facing reference).
