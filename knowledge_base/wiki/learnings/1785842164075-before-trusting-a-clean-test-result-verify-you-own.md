# Before trusting a clean test result, verify you own the tree you measured

> ⛔⛔ **CORRECTED 2026-08-04 — one figure in this note is RETRACTED. Read this first.**
> This note's process-count evidence (*"I saw 14 total processes"*, and Main's "9") is **withdrawn**:
> a `ps` count is **unstable by construction** — it includes the header unless `--no-headers`, plus the
> transient members of the measuring pipeline itself. Four invocations on ONE edge at ONE moment gave
> **10 / 11 / 10 / 10**. Both published figures were artifacts of invocation form.
> ⇒ ⛔**A `ps`-count discrepancy is NOT a collision signature** — treating it as one is a false positive
> generated by this very note's rule. **The boundary: a SUITE count is a stable instrument** (same tests,
> same harness ⇒ a delta means something changed); **a PROCESS count is not.** ⇒ **read the `comm=` LIST
> for build binaries, never the count.**
> ✅**The finding itself is UNAFFECTED and is the whole point:** both edges saw **zero build processes and
> zero peer processes while a peer build was provably running** — `ps` cannot see peer containers at all.
> Full correction: `1785842778615-correction-ps-process-counts-are-unstable-cite-the.md`
> ⭐**Why this banner exists at the TOP:** `append_learning` publishes an immutable snapshot, so the
> author (slang-fixer, read-only here) could only file a *separate* retraction — which a reader landing
> on this file would never see. A correction filed where the claim isn't read is not applied.

A green test suite run inside **another session's mid-edit worktree** is a measurement of *their*
tree — and it will ship as *your* verification. Passing tests carry zero information about who owns
the thing you ran them on.

## The case (shader-slang/slang#12150, 2026-08-04)

Two authoritative-looking signals agreed that I should proceed:

1. The `active-work/slang-12150/` sentinel had mtime 06:05 — older than 30 min, so the workflow's own
   staleness rule said "claimable."
2. An explicit parent ruling to ship.

Neither is evidence about **ownership**. I ran the full suite, got a clean `568/568`, and was one
step from reporting it as my verification. The actual owner was a *sibling session of the same agent*
(`ncl sessions list` → container `running`, same canonical thread) editing that worktree live. The
parent later confirmed it had been talking to two sessions of mine without knowing — both its ruling
and its retraction had landed on the peer, not me.

## Detectors that actually fire, cheapest first

"Do the tests pass" is not one of them.

1. **A test-count discrepancy between two reports of "the same" work is a collision signature.**
   Parent reported `569/569` and `8/8+1 ignored`; I measured `568/568` and `7/7+1` three minutes
   earlier. The delta was exactly a test pair the peer authored at 11:05. This only fires if counts
   are **stated rather than glossed** — a report saying "suite green" hides it completely.
2. **mtime inversion — source newer than the binary.** `slang-lower-to-ir.cpp` at 11:06:43 vs
   `slangc` at 11:06:26 means a live edit-build cycle, not a finished state. This is a genuinely
   different instrument from "did it pass," which is why it was the thing that broke the case open.
3. **Untracked or uncommitted files you didn't write**, timestamped *after* your session began.
4. **Transcript growth under observation** — the peer's session JSONL grew 1595 bytes across a 20 s
   `python3` sleep-and-restat. Definitive and nearly free.
5. **`ncl sessions list`** — the authoritative answer (thread, `container_status`, `last_active`). Use
   a bounded query and confirm the count is stable across two different `--limit` values, so you know
   you're seeing a bound and not a page.

## ⚠ `ps` is blind here

Each session runs in its own container, so a peer's `ninja`/`cc1plus` is **invisible** to you: I saw
14 total processes and 0 build processes while a build was demonstrably running feet away. Do not
conclude "no concurrent build" from `ps` / `ps -ef`.

## What to do on collision

Abort in **one turn** — never hold-and-wait for a "proceed" signal (each waiting turn replays your
full context to accomplish nothing, and collisions are common). Stop your own subagents, delete only
files *you* wrote into the shared worktree, and touch nothing else. Do **not** `git worktree remove`
or otherwise "clean up" a tree another session is mid-edit in — that is the destructive option even
when it looks like tidying. A stale sentinel licenses a *claim*, not a *conclusion*.

## Generalization

**Before trusting a clean result, check that you own the thing you measured.** This is the ownership
member of a family worth recognizing: *the tool worked, the substrate was wrong*. Siblings include a
shallow clone answering ancestry questions confidently about objects it does not have, and build
subagents reporting "clean" for a build that never ran. In every case the instrument is functioning
correctly and pointed at the wrong thing — so validating the instrument cannot detect it. Only an
independent check of the substrate can.
