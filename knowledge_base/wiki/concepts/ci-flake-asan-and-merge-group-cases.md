# CI Flake — ASan, Merge-Group & Receipts-Level Root-Cause Cases

## TL;DR

- **`sanitizer-linux-clang` "ASan runtime does not come first in the initial library list" is a loader-ordering/environment flake, not a code bug.** Switching to static ASan linkage is **not** the fix. The tell is that a static "canary" preflight step is what gates the run, so **harden the canary, not the individual test steps.** Beware the GitHub Actions `success()` trap — a guard step that only runs on `success()` won't fire after the abort.
- **Merge-group-only surfacing (PR head green + merge-group `sanitizer` red) means the failure is not the evicted PR's** — in #12058 a deterministic overflow from a latent render-test caller bug, NOT the intermittent ASan-canary/LD_PRELOAD env flake. Do NOT requeue evicted PRs; pull the trace before the merge-group logs expire, and name a suspect commit as "bisect me", never as the cause: the first filing blamed slang-rhi and the #11960 bump, and both were wrong.
- **When an API takes a length-less data pointer (`const void*` with no size), an over-read is always a caller/producer bug** — do not propose clamping in the callee, and the library structurally cannot fix it.
- **An auto-filed sanitizer issue's "failing tests" list can be collateral from a different flake** — verify each listed test's `//TEST:` directive before assuming it's the trigger; separate conflated problems to different owners.
- **The sanitizer job's "PR-related" label means only that some stack frame is in a file the PR changed** — a PR that touches a file on a pre-existing bug's stack inherits it. Read the frame that produced the fault before blaming the PR.
- **A failed merge-group `check-ci` is not an eviction.** A stacked later entry's green run can merge the earlier entry (#13502 merged with no `RemovedFromMergeQueueEvent`); derive evictions from that timeline event only. It recurred on #13936 (2026-10-29), so a CI Health MQ counter of `failure: 1` can coexist with zero evictions.
- **A merged PR's `headRefOid` is not proof that commit is on master.** A push to a PR already in the merge queue dismissed the approval but did not dequeue it, and the queue merged the EARLIER head's content (#13936). When the head commit is newer than the `AddedToMergeQueue` event, or a `ReviewDismissed` follows the enqueue, compare the merged master commit's file content with the PR head before saying "fix landed".
- **`release-not-debug` + intermittent + rerun-clears + cross-API resource sharing is a missing-sync signature.** On a bit-exact comparison a tolerance widen masks rather than fixes; grep the working sibling path for the sync machinery it already has before widening anything.
- **`test_GBufferRTTexGrads_d3d12` on `test-falcor / Test (Falcor)` is catalogued flake anchor #12145** — a real `Mogwai.exe` `0xC0000005` on one D3D12 renderpass, PR-code-independent, maintainer-owned. `test-falcor` is NOT a required check; don't flake-note an approved PR, rerun-churn, or touch the branch.
- **Verify a self-filed bot CI issue's root cause at receipts level** — grep the cited magic constant before believing "hard-coded", read the failing step's actual API response, and treat a node-id 422 on a logins-only call as a pre-existing server-side entity, not your code.

The hard-to-classify sanitizer and merge-group reds, plus two catalogued anchors and the method that ties them together: **verify the root cause at receipts level before you name a layer or an owner.** An ASan abort that looks like a code bug is a loader-ordering flake gated by a canary; a merge-group overflow that looks like a library bug is a caller bug; a `release-not-debug` tolerance trip that looks numeric is a missing-sync bug; a self-filed bot issue that names a "hard-coded constant" never had that constant in the repo.
- **Several merge-queue "evictions" with the same red build-job set are usually ONE poisoned head plus queue-mates behind it.** Check each PR with GraphQL: a non-null `mergeQueueEntry` and no `RemovedFromMergeQueueEvent` means still queued. A stale-base PR calling a symbol master renamed is a semantic merge conflict: own-head CI green, merged tree does not compile.
- **A `ci_failed` webhook can describe a days-old yielded run** that a later maintainer approval un-gated. Check the run's `createdAt` and whether the required checks are green from another suite before acting; rerunning a stale yielded run costs a GPU runner and can flip `check-ci` red.

## ASan "runtime does not come first" flake + the canary-gating trap

The `sanitizer-linux-clang-x86_64` leg intermittently aborts with *"ASan runtime does not come first in the initial library list"* on the GCP linux-build pool. This is a loader-ordering/environment flake, **not** a code bug, and switching to static ASan linkage is **not** the fix. The tell is that a static "canary" preflight step is what actually gates the run, so hardening the canary (not the individual test steps) is the durable lever. Watch for the GitHub Actions `success()` trap when wiring the guard: a step that only runs on `success()` won't fire after the abort. Diagnosis + fix levers: [ASan 'runtime does not come first' CI flake — diagnosis, fix levers, and the GH Actions success() trap](../learnings/1782802321817-asan-runtime-does-not-come-first-ci-flake-diagnosi.md); the CANARY-is-the-gate correction: [CORRECTION to ASan-runtime-not-first learning — the CANARY is the gating step, harden it (not just test steps)](../learnings/1782802481315-correction-to-asan-runtime-not-first-learning-the-.md).

## Merge-Group-Only ASan Overflow: a Caller Bug, Not the Callee (#12058)

shader-slang/slang#12058: a deterministic ASan `heap-buffer-overflow` in `rhi::cpu::DeviceImpl::createBuffer` (`external/slang-rhi/src/cpu/cpu-buffer.cpp:36`, a `memcpy` READ of size 142 past a 140-byte region) aborted the merge-group `sanitizer` job while the PRs' own head checks stayed green, so the evicted PRs looked healthy. Head green plus merge-group red on `sanitizer` means the failure lives in something only the merge group runs, not in the evicted PR. It is not the #11833 ASan-canary/LD_PRELOAD flake, which is intermittent environment noise: this is a fixed overflow that bounces every batch, so requeuing evicted PRs is futile until it is fixed (it was classified a P1 merge-queue blocker). Merge-group logs expire quickly, so pull the exact ASan trace on the same sweep that spots the failure. The CI-babysitter's first framing, "likely fix in slang-rhi plus a submodule pin bump, suspect the #11960 ToT bump", was wrong on both counts, which is why a filing should state the signature as observed fact and name any suspect commit as "bisect me" rather than as the cause. The layer is the *caller* in the slang repo. In `tools/render-test/render-test-main.cpp:494-499`, `bufferSize = Math::Max(count*4, elementCount*stride)` can be non-4-aligned (here 142), and `bufferData.reserve(bufferSize / sizeof(uint32_t))` floor-truncates it into a `List<uint32_t>` of only 140 bytes. `shader-renderer-util.cpp:204` then sets `bufferDesc.size = 142` and passes that block as `initData`, and `createBuffer` copies the full `desc.size`. slang-rhi structurally cannot fix this, because `IDevice::createBuffer(const BufferDesc&, const void* initData, IBuffer**)` (`slang-rhi.h:3425`) takes `initData` as a length-less pointer whose contract is "covers `desc.size` bytes". That gives the reusable tell: when an API takes a length-less data pointer, an over-read is always a caller/producer bug, so don't propose clamping in the callee. The #11960 suspect was refuted without a rebuild by diffing just the implicated files (`src/cpu/cpu-buffer.cpp`, `src/resource-desc-utils.cpp`) across the two submodule pins (687dc186 → 29dc332e), which were byte-identical; `git cat-file -t` both endpoints first, because a shallow clone can make an empty diff meaningless. The fix ceils the word count at `render-test-main.cpp:497` (`(bufferSize + sizeof(uint32_t)-1)/sizeof(uint32_t)`). It is latent 2024-era code, so it is not a `regression` ([merge-group ASan overflow in cpu createBuffer is a render-test caller bug, not slang-rhi](../learnings/1783724432597-merge-group-asan-overflow-in-cpu-createbuffer-is-a.md)).

Also: an auto-filed sanitizer issue's "failing tests" list can be collateral — all 11 listed `(cpu)` tests were `EXECUTABLE` tests that never call `createBuffer` and failed on the *different* LD_PRELOAD canary flake; the actual overflow was triggered by an unlisted compute test, unpinnable from the shared multi-server log. Verify each listed test's `//TEST:` directive before assuming it's the culprit, and separate the two conflated problems to different owners ([a merge-group sanitizer issue's 'failing tests' list can be collateral, not the trigger](../learnings/1783724442644-a-merge-group-sanitizer-issue-s-failing-tests-list.md)).

**The sanitizer job's "PR-related" label is file attribution, not causation.** The `sanitizer-linux-clang-x86_64` classifier (`ci-slang-sanitizer.yml`) marks a UBSan/ASan log "PR-related", and fails the job, if ANY stack-frame path is in the PR's changed files. So a PR that edits a file on a pre-existing bug's stack inherits that bug as "PR-related" as soon as its new test reaches it. On #13494, which edited `slang-reflection-json.cpp`, the UBSan null `TypeReflection` really came from `processEntryPointVaryingParameter` (`slang-parameter-binding.cpp`): its MeshOutputType and HLSLPatchType branches assign `arrayTypeLayout->type = arrayType`, where `arrayType` is the null if-chain binding left over from the earlier `as<ArrayExpressionType>` branch. As a result, `out vertices`/`out indices` and `InputPatch` entry-point params have a null `TypeLayout::type` and reflect as kind None; the fix assigns `meshOutputType`/`patchType`. Before you call a sanitizer red the PR's fault, read the frame that produced the null or overflow, not just the label. A quick repro without a sanitizer build is gdb `break Slang::emitReflectionTypeInfoJSON if type == 0` on `slangc -reflection-json` ([the sanitizer "PR-related" label is file attribution](../learnings/1791509362714-slang-sanitizer-job-s-pr-related-label-is-file-att.md)). The converse also holds: a log whose frames touch no changed file is "pre-existing" and only warns on the PR, but the nightly has no diff and fails on it, so a PR's new test can turn the next nightly red; the per-log-file classification and local UBSan repro are on [[wiki/concepts/slang-build-release-divergences-and-sanitizers.md]].

## A Failed Merge-Group `check-ci` Is Not an Eviction, and a Merged Head Is Not Proof (#13502, #13936)

On shader-slang/slang on 2026-10-09, PR #13502's merge-group run 37923422416 failed `check-ci` at 13:30Z: three linux jobs hit the CMake zstd configure failure from a bad LLVM prebuilt tarball (see [Building & regression-testing Slang's LLVM path](slang-tooling-llvm-target-build.md)). Even so, #13502 merged at 14:38:31Z, and its timeline has no `RemovedFromMergeQueueEvent`. The run that merged it belonged to #13481. That stacked group run (37933324356) was built on #13502's group commit 19c885a5fd, started after the bad tarball was deleted, and passed `check-ci` at 14:38:02Z. Both PRs got a `MergedEvent` at 14:38:31Z. A green later entry whose group commit contains an earlier entry can therefore merge that earlier entry, even though the earlier entry's own run failed. This mechanism is inferred, because the required-check/ruleset config returns 403 to the bot token. The rule is the same one the superseding-batch case gives on [Control & Mechanism](verification-e-control-and-mechanism.md): never infer an eviction from a failed group run alone. Derive it from `RemovedFromMergeQueueEvent` and its reason (`failed_checks` / `checks_timed_out`) ([failed merge-group check-ci does not imply eviction](../learnings/1791564244082-failed-merge-group-check-ci-does-not-imply-evictio.md)).

The same shape recurred on 2026-10-29. #13936's own merge_group `CI` run (40789267968) failed at 00:54Z because a GitHub-hosted Windows runner was lost on `static-unit-test-windows-debug-cl-x86_64`, yet the PR was not evicted: the next group (#13764 stacked on top of it, run 40796308189) passed at 01:53Z, and both merged at 01:56:24Z with `RemovedFromMergeQueueEvent` reason `merged`. So "MQ run failed" does not imply "eviction". Read the GraphQL event's `reason` before reporting one, and expect the CI Health MQ counter's `failure: 1` to coexist with 0 evictions [Slang MQ can merge a PR whose own merge_group run failed](../learnings/1793262745459-slang-mq-can-merge-a-pr-whose-own-merge-group-run-.md).

**A merged PR can be missing its own last commit.** Clo3D pushed `8e6a3090d9` to #13936 at 00:04Z while the PR was already queued (enqueued 23:42Z on 10-28). The push dismissed the approval but did NOT remove the PR from the queue. The queue merged the earlier head's content (`0f2aeaf44d`) as master `110711ee26`, and GitHub still shows the PR as MERGED with head `8e6a3090d9`; a raw-file compare at the three refs proved the last commit's change is not on master. So `headRefOid` of a merged PR is not evidence that commit landed. For any merged PR whose head commit is newer than its `AddedToMergeQueue` event, or that has a `ReviewDismissed` event after enqueueing, compare the merged master commit's content with the PR head (raw file at both refs) before saying "merged with approval on head" or "fix landed". The sweep's helper `/workspace/agent/reports/tmp1029/gh/m3.py` lines commit dates up against approvals and queue events [GitHub merge queue can mark a PR merged without its last commit (slang #13936)](../learnings/1793263293775-github-merge-queue-can-mark-a-pr-merged-without-it.md).

## Release-Not-Debug + Rerun-Clears Is a Missing-Sync Signature, Not Numeric Tolerance

slang-rhi#787's `texture-shared-cuda.vulkan` intermittently trips a `CHECK_GE(... - 0.01f)` tolerance assert only on windows-release-gpu (passes debug + everywhere else), rerun-clears, PR-agnostic. The first read widened the tolerance; the maintainer's "release-but-not-debug is suspicious — check for missing synchronization" was right. The shader is a BIT-EXACT copy of exactly-representable values, so a synced run yields delta EXACTLY 0.0 — no legit rounding produces ~0.01, meaning tolerance MASKS rather than fixes; the CUDA↔Vulkan interop hand-off relies solely on a host-side wait with no external-semaphore wait or `VK_QUEUE_FAMILY_EXTERNAL` ownership transfer, while the sibling `cuda-surface.cpp` already has the correct machinery. "Release-but-not-debug + intermittent + rerun-clears + cross-API resource sharing" is a textbook missing-sync signature — investigate the sync path (and grep the working sibling path) before widening a tolerance on a bit-exact comparison ([slang-rhi #787 texture-shared-cuda.vulkan flake is a missing-sync bug, not numeric tolerance](../learnings/1784741714597-slang-rhi-787-texture-shared-cuda-vulkan-flake-is-.md)).

## `test_GBufferRTTexGrads_d3d12` is catalogued CI-flake anchor #12145

On a Slang PR, `test-falcor / Test (Falcor)` failing (~17min, so NOT a priority-yield) with `renderpasses/test_GBufferRTTexGrads_d3d12 : FAILED` / `Image tests FAILED` (often with `Error. Unknown VCS root ''`, and `check-ci` reflecting the Falcor red) is catalogued flake anchor **#12145** — a genuine `Mogwai.exe` `0xC0000005` access-violation on that one D3D12 renderpass, proven PR-code-independent across 16+ unrelated PRs and maintainer-owned by jkwak for fix-or-quarantine. Blast-radius check first (don't just assume flake): confirm `test-falcor` is SUCCESS on current master but red on your head AND your change can't affect Falcor codegen. `test-falcor` is NOT a required status check, so this red does not gate merge; don't post a flake-note on an approved PR (noise; #12145 carries the standing quarantine ask), don't rerun-churn or poll, and don't touch the branch if a maintainer approval sits on the current head. A single occurrence on an approved/mergeable PR does not need babysitter routing ([test_GBufferRTTexGrads_d3d12 is catalogued CI flake #12145 (not your regression)](../learnings/1785193029181-test-gbufferrttexgrads-d3d12-is-catalogued-ci-flak.md)).

## Verify a Self-Filed Bot CI Issue's Root Cause at Receipts Level (#12062)

A `nv-slang-bot` self-filed CI-health issue can be wrong about its own root cause. #12062 claimed a "hard-coded stale bot node id `BOT_kgDOCnlnWA`" in `pr-board-sync.yml` — but `grep`/`git log -S` found the id was NEVER in the repo, and the workflow's assignment code passes login strings, not node ids. The real cause was server-side: a phantom requested-reviewer already on PR #11964 made GitHub 422 on any reviewer-mutation REST call, and the failing step (`removeRequestedReviewers` @yml:1290) was the one mutation NOT wrapped in the fail-safe try/catch its siblings had. Reusable method: read the actual failing-step API to find `conclusion=failure`, note the response URL on the HttpError (it names the endpoint), grep the cited magic constant before believing "hard-coded", and treat a "global node id" 422 on a logins-only call as a pre-existing server-side entity, not your code ([verify a self-filed bot CI issue's root cause at receipts level — it can be wrong](../learnings/1783744499019-verify-a-self-filed-bot-ci-issue-s-root-cause-at-r.md)).

## gcc-ASan `spirv-opt` DEADLYSIGNAL Loop Is a Kernel-ASLR Flake — Run Under `setarch -R`

A gcc-built AddressSanitizer binary (e.g. SPIRV-Tools `build-asan/tools/spirv-opt`) that intermittently (~75% of runs, nondeterministic) prints **millions of bare `AddressSanitizer:DEADLYSIGNAL` lines with no stack** and never terminates is an **environment issue, NOT a bug in the program under test** — the *same* binary on the *same* input runs clean the other ~25% of the time. Root cause: high-entropy kernel ASLR (`vm.mmap_rnd_bits`, common on newer kernels/containers) is incompatible with ASan's shadow-memory mapping, so ASan's SEGV handler re-faults in a loop. It masquerades as "my fix is nondeterministically broken" (cost ~30 min of false investigation during the #13230 / SPIRV-Tools #6711 `MergeReturnPass` UAF fix). Fix: run the ASan binary under `setarch "$(uname -m)" -R <cmd>` (sets the `ADDR_NO_RANDOMIZE` personality; **no root needed**) → ASan then behaves deterministically (real `heap-use-after-free` when the bug fires, clean exit otherwise); `sysctl -w vm.mmap_rnd_bits=28` also works but needs root. Also set `ASAN_OPTIONS=detect_leaks=0:abort_on_error=1:disable_coredump=1` — gcc-ASan core dumps are multi-GB and make each abort take minutes; a single ASan `spirv-opt` run is actually <1s, so apparent "hangs" were really concurrent-load contention from multiple ASan processes/builds running at once ([gcc-ASan spirv-opt DEADLYSIGNAL loop is a kernel-ASLR flake — run under setarch -R](../learnings/1790190755068-gcc-asan-spirv-opt-deadlysignal-loop-is-a-kernel-a.md)).

## Several "evicted" PRs can be one poisoned head plus collateral (2026-10-12)

When several PRs show as evicted from the merge queue with the same failing-job set (all platform build jobs red) in consecutive merge-group runs, suspect one poisoned head. Speculative group runs stack on the tree of the PRs ahead, so queue-mates behind it fail without being removed. Check each PR with GraphQL: `pullRequest.mergeQueueEntry` non-null and no `RemovedFromMergeQueueEvent` means it is still queued and needs no requeue; only the earliest one actually ejected is the culprit. On shader-slang/slang the cause was a semantic merge conflict: master renamed `waitForNonDiagnosticResponse` to `waitForResponse` (#13475) while #13521's stale base added a call to the old name, so its own-head CI was green and `mergeable` stayed MERGEABLE, but the merged tree did not compile. Diagnose by diffing the PR base against master for renames of symbols the PR touches; the verdict is a legitimate failure for the author to rebase, not a requeue. `gh api --paginate` through the gateway also failed with a transient "GitHub is not connected" 401 while single calls worked, so page with `page=N` and retry [merge-queue evicted lists can be one poisoned head](../learnings/1791836334459-merge-queue-evicted-lists-can-be-one-poisoned-head.md). When the comment explaining this is built from a parent's bullets, re-derive its numbers: the first build job failed 3–4 minutes after each run started (one enqueue had sat about 2 hours in the queue first), and the PR-added call site comes from the `pulls/<n>/files` patch `+` lines, not from grepping the head file [verify a parent's timing and line-number claims](../learnings/1791857947061-verify-a-parent-s-timing-and-line-number-claims-ag.md).

## A maintainer approval can fire a late `ci_failed` from an old dispatched run

A bot `workflow_dispatch` CI run can yield to higher-priority CI while its `falcor-ci` environment gate still waits for approval. A later approval by an allowlisted maintainer auto-approves that environment, sometimes days later, and the Falcor job's failure on the old run arrives as a fresh `github.ci_failed` webhook. On 2026-10-12 a webhook named run 36801051802, created 10-01, which had failed at `wait-for-human-priority` ("Stop yielded bot CI"), at `check-ci`, and in the Falcor build at `upload-artifact` (FinalizeArtifact 404, infra; the build itself succeeded). Before acting on a `ci_failed` webhook, check the run's `createdAt`, whether the PR's required checks are green from another suite (GraphQL `isRequired(pullRequestNumber:)` on the head's check runs), and whether `ci-retry-yielded-bot` can still reach the run (it looks back 16 hours). If the required checks are green, the stale run is not actionable [a maintainer approval can trigger a late ci_failed webhook](../learnings/1791838490812-a-maintainer-approval-can-trigger-a-late-ci-failed.md).
