## Capability Declaration

**Adding a capability atom:** The single source of truth is `source/slang/slang-capabilities.capdef`. Two lines are needed per capability — an extension atom (`def SPV_EXT_foo : _spirv_1_0;`) and a capability atom (`def spvFooEXT : SPV_EXT_foo;`). Each requires `///` doc comment + `/// [EXT]` tag. The build runs `slang-capability-generator` to produce the C++ enum headers — never hand-edit those. Adding an atom also regenerates two checked-in docs: `docs/user-guide/a3-02-reference-capability-atoms.md` (alphabetical) and `docs/command-line-slangc-reference.md` (declaration order, byte-exact diff enforced by CI) ([Adding a SPIR-V capability atom to Slang (capdef recipe)](../learnings/1781120340432-adding-a-spir-v-capability-atom-to-slang-capdef-re.md), [Adding a SPIR-V capability atom — ADDENDUM (two generated docs + test -capability)](../learnings/1781122622446-adding-a-spir-v-capability-atom-addendum-two-gener.md)).

**Adding/reordering capdef atoms is `pr: non-breaking` — not an ABI break** (verified via #12244, MERGED): the public `SlangCapabilityID` is opaque, single-enumerator, and resolved by NAME at runtime via `ISession::findCapability(name)`; the generated `CapabilityName`/`CapabilityAtom` enums are internal-only, positional, and exposed by no public API, so inserting an atom mid-list shifts only internal ints. Carry the precision honestly: atoms ARE serialized by value into internal IR / `.slang-module` (`IRRequireCapabilityAtomDecoration` reads `intVal`), but that format is already not cross-version-stable (recompiled per compiler version), so every prior capdef add shifted these and none were breaking — claim "no public ABI break, consistent with module-versioning practice," not "never serialized by value" ([capability-atom rename PRs are ABI-safe (slang#12244)](../learnings/1785429130429-capability-atom-rename-prs-are-abi-safe-shadow-bia.md)).

**Specifying a capability through the compilation API:** the `CompilerOptionName::Capability` doc comment saying "intValue0 encodes a value from the CapabilityName enum" is a docs bug — `CapabilityName` is generated, internal, and not shipped in the SDK. The supported stable path is the STRING NAME: set `entry.value.kind = String` and `stringValue0 = "spvGroupNonUniformArithmetic"`, consumed at `TargetRequest::getTargetCaps()` via `findCapabilityName(...)`. Alternatively resolve the int at runtime with the public `IGlobalSession::findCapability(name)`. Do NOT recommend exposing `CapabilityName` publicly — raw ints are version-unstable by design (#12286) ([specify a capability via the compilation API by string name](../learnings/1785415625670-how-to-specify-a-capability-via-the-slang-compilat.md)).

**Where a resource-`[require]` capability diagnostic actually fires (cross-target, from the #12274 follow-up):** E36107 fires only on **entry-point-reachable** typed resources, NOT on unreferenced globals — a declared-but-unused `Buffer<uint>` global passes on an excluded target, while an entry point *taking* a `Buffer<uint>` param fails; and because the check runs over ALL `[shader]` entry points at module load, one illegal EP sinks its clean siblings' `load_program` (trust the CI failure log over DeepWiki's design-doc reading of what trips the diagnostic) ([E36107 is entry-point-scoped, not all-declarations](../learnings/1785453629709-slang-e36107-capability-check-entry-point-scoped-n.md)). The enforcement layer is counterintuitive: the method-level `[require]` on an intrinsic (e.g. `_Texture.Load`) is **inert** when that method's body is a case-less `__target_switch` — a switch with no case for the active target infers an empty body → empty inferred capability set → trivially passes. The effective gate is the **TYPE-level `[require]` on the resource's shape struct** (for `Buffer<T>` = `_Texture<T,__ShapeBuffer,...>`, the `[require]` on `struct __ShapeBuffer`), so the Approach-A diagnose fix drops the incapable target from the TYPE's require list (mirroring WGSL PR #6585), NOT the method's — with the caveat not to drop a target that has a real prelude type (`cpp`'s gap is a missing `case cpp:`, implement-territory, not incapability) ([case-less `__target_switch`: the enforcing require-clause is on the TYPE, not the method](../learnings/1785418069559-case-less-target-switch-the-enforcing-require-is-o.md)).

**Gating emit on a capability atom:** The correct pattern is `targetCaps.implies(CapabilityAtom::spvFooEXT)`. Do NOT gate on `isSPIRV(...)` (fires unconditionally for every SPIR-V target) and do NOT gate on extension-string atoms where a capability atom exists. The established precedent in `slang-emit-spirv.cpp:1692` gates on `CapabilityAtom::spvBindlessTextureNV`; ~8 sibling sites confirm this. An earlier triage learning incorrectly advised `isSPIRV()` — the correction is in [CORRECTION: SPIR-V capability emit-gating — use implies(CapabilityAtom::spv*), NOT isSPIRV()](../learnings/1781123971590-correction-spir-v-capability-emit-gating-use-impli.md). When adding a conditional capability for a stdlib `spirv_asm` intrinsic, see the option tree in [Conditionally requiring a SPIR-V capability for a stdlib spirv_asm intrinsic forces pass-level block manipulation — layer-choice tree](../learnings/1781974573249-conditionally-requiring-a-spir-v-capability-for-a-.md) (options: constexpr-only, post-hoc pass rewrite, new IR op, placeholder operand idiom).

**Triaging "add a capability" requests:** Check `external/spirv-headers/include/spirv/unified1/spirv.h` first — the `SpvCapability*` constant is usually already vendored. A bare capdef atom is inert until consumed by a `[require(...)]` intrinsic or C++ emit site ([Triaging an &quot;add a SPIR-V capability bit&quot; request — vendored-operand check + inert-atom scoping](../learnings/1781116222932-triaging-an-quot-add-a-spir-v-capability-bit-quot-.md)). New `Spv*` enum constants resolve from the SPIRV-Headers package, NOT from the stale `external/spirv/spirv.h` ([Slang SPIR-V emit: new Spv* enum constants resolve from the SPIRV-Headers package, not external/spirv/spirv.h](../learnings/1782322517394-slang-spir-v-emit-new-spv-enum-constants-resolve-f.md)).

**SPV_KHR_abort and multi-dependency chains:** `OpAbortKHR` is a block terminator (like OpKill) requiring both `SPV_KHR_abort` AND `SPV_KHR_constant_data` (for the `OpConstantDataKHR` message). New SPIR-V extension intrinsics must be modeled as terminators, not printf-parallel — after emitting the terminator, block emission must stop and unreachable code must be removed ([When planning a new SPIR-V opcode, check terminator-ness — not just value-producing-ness](../learnings/1781039584587-when-planning-a-new-spir-v-opcode-check-terminator.md), [SPV_KHR_abort transitively requires SPV_KHR_constant_data; message is OpConstantDataKHR not a runtime composite](../learnings/1782248897717-spv-khr-abort-transitively-requires-spv-khr-consta.md)).

**Conditionally requiring a capability for ray tracing:** To limit a shader to `SPV_KHR_ray_query` without pulling in `SPV_KHR_ray_tracing`, use `-capability spvRayQueryKHR` and verify no `TraceRay`/raygen path re-introduces the extension. The `RaytracingAccelerationStructure` type itself triggers a dual "any" requirement; post-PR #6615 dedup should collapse it to ray_query when only `RayQuery` usage exists ([Slang AS: forcing ray-query-only capability (avoid SPV_KHR_ray_tracing)](../learnings/1781905197543-slang-as-forcing-ray-query-only-capability-avoid-s.md)).

**`-capability` silently raises the SPIR-V version past an explicit `-profile` (#12097/#12099):** `slangc -profile spirv_1_4 -capability spvShaderInvocationReorderNV` silently emits a `; Version: 1.5` header (exit 0, no diagnostic). Root cause: `-capability` atoms are folded into target caps in `TargetRequest::getTargetCaps()` (`slang-target.cpp:214-232`) via `if (!targetCap.isIncompatibleWith(toAdd)) targetCap.join(toAdd)`, and `CapabilitySet::isIncompatibleWith` (`slang-capability.cpp:487-512`) treats two sets as compatible whenever they share ANY target abstract node — `spirv_1_4` and `spirv_1_5` are the SAME SPIR-V target, so the join proceeds and `determineSpirvVersion` takes the MAX (`requireSpirvVersion` = `Math::Max`). A version *raise* is thus always a *compatible* join, never flagged. The missing prerequisite for any conflict diagnostic: nothing records whether the profile's concrete version was USER-EXPLICIT vs defaulted (default is `spirv_1_5`), so a CLI-conflict check (fix layer A at the `getTargetCaps` join with a fire-once DiagnosticSink; cleaner layer B at parse-time in `slang-options.cpp`) must add that flag first. This is a distinct layer from the code-implied capability errors E41012/E41013 (`slang-check-shader.cpp`, gated by `-restrictive-capability-check`); a CLI conflict wants an unconditional error. Correct discriminator: key off "capability has NO valid realization at the explicit version (extension paths included)", NOT "default realization exceeds version" ([-capability silently raises SPIR-V version past explicit -profile (#12099)](../learnings/1784052596356-why-capability-silently-raises-spir-v-version-past.md)).

The specific over-require driving #12097 is that the SER extensions are pinned to `_spirv_1_5` in the capdef: `slang-capabilities.capdef:624` `def SPV_EXT_shader_invocation_reorder : _spirv_1_5 + SPV_KHR_ray_tracing;` (NV inherits at `:629`, motion aliases at `:862`/`:867`) — a deliberate simplification per the source comment, even though SER is usable at 1.4 given a physical-storage-buffer extension. **A capdef `_spirv_1_5`→`_spirv_1_4` floor edit ALONE does NOT make the 1.4 module valid:** the SER emit path (`emitOpTypeHitObject*`, `slang-emit-spirv.cpp:2745-2762`) declares only the reorder `OpExtension`/`OpCapability`; the only site that emits `OpExtension "SPV_KHR_physical_storage_buffer"` is `requirePhysicalStorageAddressing()` and it fires only under `PhysicalStorageBuffer64` addressing (buffer_reference usage), which a plain SER raygen shader never triggers. So the 1.4 path emits no PSB extension and spirv-val fails per SER's normative 1.4 dependency (1.4 + `SPV_KHR_ray_tracing` + one of {PSB extension, core 1.5}). The 1.4 path must declare the PSB *extension* without switching the memory model away from `Logical GLSL450`. Note `SPV_KHR_physical_storage_buffer` is a hardcoded emit string, not a capdef atom (only `SPV_EXT_physical_storage_buffer : _spirv_1_3` exists); capdef disjunction (`|`) could model the "1.4+PSB OR core-1.5" rule but still needs the emission change ([SPIR-V SER capability over-requires 1.5; capdef floor edit alone insufficient (#12097)](../learnings/1784052492569-spir-v-ser-capability-over-requires-1-5-capdef-flo.md)). #12097 and #12099 are a paired "allow the 1.4 downgrade" vs "reject the conflicting `-profile`/`-capability` combo" issue set from the same author (jkwak-work) for the identical repro — when triaging one of a paired allow/reject set, flag the tension to the maintainer rather than silently picking a side.

## Miscellaneous SPIR-V Pitfalls

- **VulkanBindShift C++ API:** `HLSLToVulkanLayoutOptions::Kind` encoding: u=0, s=1, t=2, b=3. Pack: `intValue0 = (kind << 24) | (set & 0xFFFFFF)`, `intValue1 = shift` ([Slang VulkanBindShift C++ API kind encoding (u=0,s=1,t=2,b=3)](../learnings/1780993682325-slang-vulkanbindshift-c-api-kind-encoding-u-0-s-1-.md)).
- **SlangPy kernel abstraction:** Fully collapses to zero overhead in Slang SPIR-V at `-O3` — 0 `OpFunctionCall`, byte-identical to a hand-rolled kernel. Runtime index arithmetic (1 sdiv + 1 srem + strided loads) is design-inherent, not a codegen defect ([SlangPy generated-kernel abstraction fully folds in slang SPIR-V (-O3), but is deferred to nvrtc for CUDA target](../learnings/1781017004302-slangpy-generated-kernel-abstraction-fully-folds-i.md), [Measure SlangPy generated-kernel codegen quality GPU-free via slangc SPIR-V opcode census](../learnings/1781050949927-measure-slangpy-generated-kernel-codegen-quality-g.md)).
- **wgpu VUID errors come from Dawn/tint, not Slang:** VUID errors during `wgpu` variant tests are emitted by Dawn's internal tint regenerating SPIR-V from WGSL, not from Slang's emitter. Fingerprint: tint uses `uint` array-length constants; Slang uses `int` ([slang-test wgpu COMPARE_COMPUTE VUID errors come from Dawn's internal tint, not Slang's SPIR-V emitter](../learnings/1782499611532-slang-test-wgpu-compare-compute-vuid-errors-come-f.md)).
- **Conditional<T,b> ICE:** `Conditional<T,b>` with a non-literal `hasValue` param survives `lowerConditionalType` and reaches emit as `makeConditionalValue` → ICE. Root cause is an upstream producer (autodiff, dynamic dispatch, or higher-order params) leaking an unresolved generic value param ([Conditional&lt;T,b&gt; ICE: non-literal flag survives lowerConditionalType to spirv-emit](../learnings/1782485307814-conditional-lt-t-b-gt-ice-non-literal-flag-survive.md)).
- **Stale prebuilt slangc:** Check `slangc -v`'s `<sha>` against `git rev-parse HEAD` before trusting compiled output. Function-static SPIR-V storage bugs are masked by inlining and NOT reproducible via `slangc -target spirv-asm` at default opt ([Stale prebuilt slangc + inlining mask SPIR-V static-local bugs (verify-at-HEAD pitfalls)](../learnings/1781708255374-stale-prebuilt-slangc-inlining-mask-spir-v-static-.md)).
- **`OpCompositeConstruct` of logical-pointer array (#9062):** SPIR-V logical addressing forbids logical (StorageBuffer/Uniform/Workgroup) pointers as operands to `OpCompositeConstruct`. The resource-legalization passes that eliminate arrays-of-resources only inspect the array's *direct* element type (they `unwrapArray()` through nested arrays and check whether the unwrapped type is *directly* a resource) — they do **not** recurse into struct fields, so a `struct { RWStructuredBuffer buf; }` used as `MyPtr[2]` is invisible while a bare `RWStructuredBuffer[2]` is caught. Autodiff reliably materializes this shape (`Array<T,N> : IDifferentiablePtrType` → whole array wrapped as one `DifferentialPtrPair` → lowered to a struct), which is why the maintainer couldn't repro without autodiff; pass ordering is fine (resource legalization runs after autodiff) — the escape is *structural blindness*, not a timing gap ([OpCompositeConstruct of logical-pointer array escapes resource legalization (struct-field blindness)](../learnings/1783524098198-slang-9062-spir-v-opcompositeconstruct-of-logical-.md)).
- **`spirv_asm` named registers leak into `OpName` (#12002):** the emitter emits an `OpName` for *every* named `%id` register in a `spirv_asm` block, unconditionally (not gated on debug-info level). Texture-sample intrinsics in `hlsl.meta.slang` name their raw-sample register `%sampled`, so every texture sample emits `OpName ... "sampled"` regardless of caller variable names. For any "debug name on the wrong inst" claim, the decisive discriminator is a **rename drill**: rename the user's variable and recompile — if the disputed `OpName` follows the rename it's real propagation, if it stays it's an emitter-baked intrinsic name and the match was coincidence ([spirv_asm named registers leak into OpName; texture-sample intrinsic uses %sampled](../learnings/1783525064110-slang-12002-spirv-asm-named-registers-leak-into-op.md)).
- **Sampler-vs-texture `[noinline]` param asymmetry (#12004):** `isIllegalSPIRVParameterType` always specializes textures but only specializes samplers when they are *arrays* (a legacy compile-time-blowup guard, #3546), so a scalar `SamplerState` param stays by-value `OpTypeSampler` while the texture is passed by index and reloaded in the callee. Emission is symmetric — the by-value-vs-by-index location is decided entirely by the specialize step, not emit, so don't chase it in the emitter; fixes here MUST `spirv-val`, not just FileCheck ([sampler-vs-texture noinline SPIR-V param asymmetry — isIllegalSPIRVParameterType isArray gate](../learnings/1783527024741-slang-12004-sampler-vs-texture-noinline-spir-v-par.md)).
- **`double→bool` cast emits a 1-word `OpConstant` (#12019):** `emitFloatToIntCast`'s float→bool path calls `builder.getIntValue(fromType, 0)` with the *double* type, minting a `kIROp_IntLit` stamped with a float type; at emit `emitIntConstant` switches on the type, double hits `default:` → one 32-bit word, but a float64 `OpConstant` needs two → "says it has 4 words, found 5". Only double is structurally invalid (for float/half the 1-word path accidentally matches the IEEE bit pattern). Fix at the producing cast (`getFloatValue(fromType, 0.0)`, mirroring the correct bool→float sibling), not by special-casing `emitIntConstant` — an int-lit-with-float-type should never exist ([double→bool SPIR-V: getIntValue(floatType,0) mints int-lit with float type → 1-word OpConstant](../learnings/1783587817471-slang-12019-double-bool-spir-v-getintvalue-floatty.md)).
- **`spirv-opt --strip-debug` deletes `DebugBuildIdentifier` (#8681):** you cannot just replace the hand-rolled `stripDbgSpirvFromArtifact` with spirv-opt's strip passes — that function is the `-separate-debug-info` splitter and hand-rolls the strip precisely to keep the DBI ext-inst (the hash linking the stripped main module to its `.dbg.spv`). Both `CreateStripDebugInfoPass` and `CreateStripNonSemanticInfoPass` unconditionally kill the DBI; the correct shape is a hybrid where spirv-opt owns the bulk strip but a thin Slang shim exempts/re-injects the DBI + its OpString + the NonSemantic import — the DBI exemption is irreducible ([spirv-opt strip-debug deletes DebugBuildIdentifier — separate-debug-info needs a DBI shim](../learnings/1783556986544-slang-8681-spirv-opt-strip-debug-deletes-debugbuil.md)).
- **64-bit buffer indexing bifurcates (#11967):** direct concrete-buffer subscript (`RWStructuredBuffer<int>[uint64_t idx]`) preserves `UInt64` to `OpAccessChain` and works, but the interface-constrained `IArray<T>`/`IRWArray<T>.__subscript(int index)` path (core.meta.slang, hard `int`) silently truncates a `uint64_t` index to 32-bit (front-end `warning E30081`). The fix is to widen the IArray/IRWArray subscript *requirement* to a generic `TIndex`, mirroring the buffer/Ptr subscripts — with the caveat that widening an interface requirement can force `Array`/`vector`/`matrix` conformances to re-satisfy. A >2^32-element execution test is impractical (>8 GB buffer), so the E2E guard is necessarily a codegen FileCheck for `OpTypeInt 64` on `OpAccessChain` ([64-bit indexing works on direct subscript but IArray/IRWArray truncates to 32-bit](../learnings/1783415716330-slang-64-bit-buffer-indexing-works-on-direct-subsc.md)).
- **vec3 `OpConstantComposite` over-count is a downstream spirv-opt fold, NOT Slang emit (#12104):** `output[0] = (value<eps) ? 0 : (value/value)` for a runtime `float3` emits `OpConstantComposite %v3float %float_1 ×4` (4 constituents on a vec3 → spirv-val rejects). The maintainer's (jkwak) leads pointed at Slang's own `processConstructor`/`emitCompositeConstruct`/`MakeVector` — those are WRONG. Layer-isolation drill (reusable for any "invalid SPIR-V only at optimization" bug): (1) `-dump-ir` shows `div(%value,%value)` surviving intact through every pass → Slang IR isn't folding it; (2) `-O0` emits correct `OpFDiv` while default/`-O1/2/3` emits the malformed constant — the only pipeline delta is `slang-emit.cpp` routing SPIR-V through `PassThroughMode::SpirvOpt` (vendored `external/spirv-tools` spirv-opt @ v2026.3); (3) `-fp-mode precise` → clean `OpFDiv ; NoContraction`, `-fp-mode fast` → malformed, confirming an IEEE-unsafe `x/x→1` fold (0/0=NaN); (4) width sweep shows a HARDCODED 4 constituents (float2→4, float3→4, float4→4), NOT a vec4→vec3 result-type shrink — the vec2-with-4 case is the smoking gun. Slang's own peephole folds `v-v` correctly to a 3-constituent zero-vector and leaves `v*v` as `OpFMul`; only `v/v` (no `x/x→1` rule in slang-ir-peephole/sccp) reaches the vulnerable downstream fold. Fix options: (A, true root) fix `external/spirv-tools/source/opt/folding_rules.cpp` to use the result type's component count (upstream + submodule bump); (B, in-tree actionable now) add a fast-math-gated `x/x→1` Slang peephole fold producing a correctly-sized ones vector so spirv-opt never sees the vulnerable `OpFDiv %a %a`. An emit-time constituent-count assert in `emitOpConstantComposite` (which has no `constituent-count==element-count` check today, `slang-emit-spirv-ops.h:1417-1425`) is a useful general net that converts silent-invalid-output into a loud failure, but does NOT catch this bug — the malformed constant is minted post-emit in spirv-opt ([#12104 vec3 OpConstantComposite 4-constituent bug is in downstream spirv-opt, not Slang (x/x fold)](../learnings/1784072018251-slang-12104-vec3-opconstantcomposite-4-constituent.md)). An earlier repro-blocked triage of the same issue (jkwak's `float3(float2(1,1),1)` minimal case validates fine; ~11 minimal shapes on near-HEAD all emit a correct 3-constituent composite) correctly ruled out the sub-vector UNDER-count path (`processConstructor`'s flatten at `slang-ir-spirv-legalize.cpp:1795-1810` already handles that) and flagged a post-legalize fold (`simplifyIRForSpirvLegalization`) as the suspect — since superseded by the spirv-opt root cause above, but the standing `emitOpConstantComposite` count-assert recommendation still holds ([vec3 OpConstantComposite over-count — repro-blocked, post-legalize fold suspect (#12104)](../learnings/1784069141044-slang-spir-v-vec3-opconstantcomposite-over-count-r.md)).

## Descriptor-Heap ConstantBuffer, Constant-Fold Width, and DebugEntryPoint Strings (2026-07-24/25 fold)

The `#12186` option-A rework (kind-dependent `uint2`/`uint64` `DescriptorHandle` width) closed out two of pdeayton's concerns with lessons that generalize past this PR. First, the "does the width conversion assert?" concern split into a **pre-existing gap** vs a PR-introduced edge: a module-scope `static const` handle initialized from a float/`bit_cast` source aborts at `emitGlobalInst` ("Unhandled global inst"), but the *same* `castFloatToInt` abort reproduces identically on master with no capability and no handle — so the A/B against a no-cap/no-handle control on master is what proves it's a general global-emit gap, not the PR's fault; the genuinely-new edge is the width-mismatch path hitting `tryGetConstantDescriptorHandleBits`'s missing cast case → `SLANG_RELEASE_ASSERT`. The principled layer is **SCCP** (`isEvaluableOpCode`, `slang-ir-sccp.cpp`), which runs at global scope before emit and already folds BitCast/CastFloatToInt but not MakeVector nor the DescriptorHandle casts — teaching it those retires both the bespoke walker and the assert ([slang#12186 option-a: layout change RESTORES cap-consistency; module-scope handle const from float/bitcast hits pre-existing global-emit gap](../learnings/1784912194039-slang-12186-option-a-layout-change-restores-cap-co.md)). A crucial repro caveat for any module-scope `static const` bug: the naive "declare + read into unused local" repro compiles clean because **DCE drops the unused global before emit** — the constant must be *observably consumed* (stored into a `RWStructuredBuffer` from the entry point) or a green compile falsely reads as "bug unreal"; also, a work item referencing symbols added by an *unmerged draft PR* (`tryGetConstantDescriptorHandleBits`) is not actionable on master — grep master for the symbol before treating it as ready-for-fix ([Module-scope static-const repros need the constant CONSUMED or DCE masks the bug](../learnings/1784915301574-module-scope-static-const-repros-need-the-constant.md)). Second, the Q2 "uint2 scalar layout — latent bug?" call was initially (wrongly) cleared as self-consistent by embedding the handle in a struct and matching std430 offsets — but in std430 `uint2` and `uint64` both align to 8, so the offsets *coincidentally* match and mask the bug. The maintainer's explicit two-arg query `alignof(T, Std430DataLayout)` fails on the PR (handle reports 4, `uint2` reports 8): the AlignOf/SizeOf **peephole** (`slang-ir-peephole.cpp`) resolves `layoutRules` correctly then calls `getNaturalSizeAndAlignment` hardcoded to natural rules, dropping the requested rule (invisible for uint64 where natural==std430, wrong for uint2). Durable rule: test the explicit `sizeof`/`alignof(T, LayoutRule)` query directly — struct offsets can coincidentally match and hide a query bug — and run a reviewer's exact minimal `static_assert` before an elaborate test of your own ([slang#12186 Q2 UPDATE: explicit alignof(T, Std430DataLayout) query CAN diverge from emitted struct layout — struct-embedding tests MASK it](../learnings/1784915310738-slang-12186-q2-update-explicit-alignof-t-std430dat.md)).

A distinct descriptor-heap ABI bug (`#12226`): a struct-typed `ConstantBuffer<T>` fetched via `ResourceDescriptorHeap[]` under `spvDescriptorHeapEXT` emits an `OpTypeBufferEXT` **StorageBuffer** (16B on the reporter's driver) instead of **Uniform** (8B) → 8 bytes of garbage. The naive "flip ConstantBuffer→Uniform in the heap path" fix is WRONG and regresses `#11483`: `processConstantBufferDescriptorHeapLoad` *deliberately* retypes struct/array heap ConstantBuffer loads to StorageBuffer (PR #11647, szihs) because a Uniform-class `OpBufferPointerEXT` carries no pointer-type `ArrayStride` (logical addressing), so nested-array offsets went undefined. The real defect is **conflating the descriptor *kind* fetched from the heap (an ABI fact — Uniform vs Storage, also sets the heap index stride via `OpConstantSizeOfEXT`) with the buffer-pointer *addressing class* (needs StorageBuffer for pointer ArrayStride)** ([Descriptor-heap ConstantBuffer StorageBuffer flip (#11647) is deliberate — descriptor kind vs pointer addressing class conflated](../learnings/1784939222858-descriptor-heap-constantbuffer-storagebuffer-flip-.md)). The remaining open question — must the two storage classes match? — was resolved by fetching the published `SPV_EXT_descriptor_heap` spec verbatim: `OpTypeBufferEXT` and `OpBufferPointerEXT`-result each carry a *separate* storage-class operand and **there is no normative rule requiring them to match** (the only place they coincide is a worked example, not a VUID; the `NonWritable` allowance explicitly contemplates a non-StorageBuffer result). DeepWiki claimed they must match — confidently wrong on this exact subsystem again — so "Approach B" (Uniform descriptor + StorageBuffer data pointer) is spec-legal; the residual question is a *device-ABI* one to confirm empirically with `SLANG_RUN_SPIRV_VALIDATION=1`, not a spec matching rule ([SPV_EXT_descriptor_heap: OpTypeBufferEXT and OpBufferPointerEXT storage classes are INDEPENDENT (no matching rule); DeepWiki wrong](../learnings/1784939925118-spv-ext-descriptor-heap-optypebufferext-and-opbuff.md)). Container tip recurring across these: `slangc -target spirv-asm` fails on the missing `slang-glslang` dylib — use `-O0 -target spirv -skip-spirv-validation` then disassemble with the in-tree `build/external/spirv-tools/.../spirv-dis`.

The RayQuery-return-by-value miscompile fix (`#12200`, closes `#12197`, SS/P1: opaque handle returned by value disconnects `OpRayQueryInitializeKHR` from `OpRayQueryProceedKHR` → `VK_ERROR_DEVICE_LOST`) landed as a scoped **NRVO** in `slang-lower-to-ir.cpp` — aliasing the named-return local to the return-destination out-param so the opaque handle builds in place, gated strictly to RayQuery/HitObject via `isNonCopyableOpaqueType` so it cannot regress the real by-value copy on DXIL. The 3-reviewer verdict was APPROVE_WITH_NITS / 0 bugs; the correctness crux (source-verified for a P1, not just relayed) is that NRVO elides only a provably-no-op whole-handle Load/Store layered on the pre-existing `maybeAddReturnDestinationParam` transform, with `findCommonReturnedLocalVar` bailing conservatively on any unrecognized statement ([PR #12200 RayQuery-return NRVO review — APPROVE_WITH_NITS, 0 bugs](../learnings/1784882737937-pr-12200-rayquery-return-nrvo-review-approve-with-.md)). Finally, the SPIR-V `DebugEntryPoint` command-line-string (`#12220`) has two independent accuracy bugs: `getDebugInfoCommandLineArgumentForEntryPoint` ends with a *literal* `sb << " -g2"` that never reads the requested level (so `-g3` still emits `-g2` despite an unused `getDebugInfoLevel()` accessor), and `writeCommandLineArgs` is a `switch(option.key)` with **no `default` case** that silently drops any un-cased option (`-lang`/`-profile`/`-gdwarf`/`-line-directive-mode` vanish while `-O0`/`-matrix-layout` survive). The command-line string is stored verbatim in the binary — grep it via `strings x.spv | grep -- '-target spirv'` without a disassembler; note `writeCommandLineArgs` also feeds the CPU/LLVM emit path but NOT the module-cache `buildHash`, so serializer edits don't change cache digests ([SPIR-V DebugEntryPoint command-line string: two roots (hardcoded -g2 + no-default serializer switch)](../learnings/1784915879616-spir-v-debugentrypoint-command-line-string-two-roo.md)).
