# SlangPy / SGL Runtime and GPU Device-Loss Triage

## TL;DR

- Adding a new `CallbackList` member to `sgl::Device` requires clearing it in `Device::close()` too — symmetric with the sibling lists — or a registered Python callback that captured the `Device` leaks / forms an uncollectable C++↔Python (nanobind) reference cycle across close.
- On NVIDIA Blackwell, a compute entry point whose ONLY `uniform` is a single scalar (routed to a 4-byte Vulkan push-constant range) can poison the device: the dispatch completes, then the NEXT unrelated submission hangs with `VK_ERROR_DEVICE_LOST` / NVRM Xid 109. Zero or 2+ scalar uniforms do not reproduce.
- Reliable workaround: wrap the scalar in a named `cbuffer CB { uint x; }` — routes through a descriptor-bound UBO instead of a push constant.
- `SLANG_RHI_ASSERT` is UNCONDITIONAL (no `NDEBUG` gate) and aborts via `std::abort()` even in release wheels — so a *deferred* device loss (not a SIGABRT) proves any size-mismatch assert on the path PASSED; a push-constant size mismatch is not the surfaced failure.
- N-vs-N+1 asymmetry localizes the layer: when only the N=1 case of an otherwise-uniform code path fails, the differentiator is size/shape UPSTREAM (driver or compiler codegen), not the consumer's per-item logic — slang-rhi treats any push-constant range identically once one exists.
- Deferred failure + cross-kernel/fresh-buffer poisoning = persistent GPU *context* corruption = a driver-bug signature, not a per-pipeline layout error.
- No-GPU driver-vs-compiler discriminator: diff the generated SPIR-V push-constant block (`SLANGPY_PRINT_GENERATED_SHADERS=1` → `-target spirv-asm`) for 1-scalar vs 2-scalar. Structural difference ⇒ escalate to the compiler; identical ⇒ the driver owns it (the device-loss half still needs Blackwell HW).

## SGL Device callback-list teardown must be symmetric

When you add a new `CallbackList` member to `sgl::Device` (e.g. the command-recording created / before-finish lifecycle hooks in slangpy#1155), you must also clear it in `Device::close()`, symmetric with the existing lists (`device_close`, `shader_hot_reload`, `command_recording_submitted`, `command_recording_discarded`). A Python callback registered on the new list can capture the `Device` — or objects that transitively reference it — so if `close()` doesn't drop the list that reference survives close and can leak or form an uncollectable reference cycle across the C++/Python (nanobind) boundary. codex CODE_REVIEW flagged exactly this as the sole must-fix in the #1155 implementation: the new lists were declared, registered, and notified correctly but omitted from the `close()` teardown. Grep `Device::close()` for the sibling `.clear()` calls and mirror them for any new list ([SGL: a new Device CallbackList must be cleared in Device::close() too](../learnings/1789375354695-sgl-adding-a-device-callbacklist-requires-clearing.md)).

## Single-scalar Vulkan push-constant device loss on Blackwell — and the reusable triage method

slangpy#1165 is the anchor case: a compute entry point whose ONLY `uniform` param is a single scalar (`uniform uint x`) on the raw `ComputeKernel.dispatch(vars=...)` path (NOT the functional API) corrupts the Vulkan device on NVIDIA Blackwell (RTX 5070 Ti, driver 615.71.09) — the offending dispatch completes and `device.wait()` returns, but the NEXT submission (any kernel, fresh buffers) hangs with `VK_ERROR_DEVICE_LOST` / NVRM Xid 109 CTX SWITCH TIMEOUT; zero or 2+ scalar uniforms do not reproduce. The reliable workaround is to wrap the scalar in a named `cbuffer CB { uint x; }` and pass `vars={..., "CB":{"x":...}}`, routing through a descriptor-bound UBO instead of a push constant. Root-cause verdict: NOT a slang-rhi layout bug — a lone scalar lowers to a valid, in-bounds 4-byte push-constant range `{offset=0,size=4,stageFlags=VK_SHADER_STAGE_ALL}` (`external/slang-rhi/src/vulkan/vk-shader-object-layout.cpp:298-314`, bound at `vk-shader-object.cpp:346-376`); the leading cause is an NVIDIA Blackwell driver fault on a minimal 4-byte push-constant range, possibly aggravated by the over-broad `VK_SHADER_STAGE_ALL` used for *all* ranges (standing `// TODO: be more clever` at layout.cpp:305), with Slang single-member push-constant codegen/reflection not fully excluded ([slangpy#1165: assert-config + bisection localize the root cause](../learnings/1789585644506-slangpy-1165-diagnosing-vulkan-push-constant-devic.md), [single scalar uniform → Vulkan device loss on Blackwell + triage method](../learnings/1789585750710-slangpy-single-scalar-uniform-vulkan-device-loss-o.md)). The investigation distilled four reusable triage moves. (1) `SLANG_RHI_ASSERT` is *unconditional and aborting* even in release wheels (`src/core/assert.h`; `handleAssert()`→`std::abort()`, no `NDEBUG` gate, and no `ScopedDisableAssert` scope on the bind/dispatch path), so seeing a *deferred device loss* rather than a SIGABRT proves the size-consistency assert PASSED and thereby eliminates the push-constant size-mismatch hypothesis — a powerful way to split "silent corruption" from "caught error". (2) An N-vs-N+1 bisection localizes the layer: slang-rhi treats any push-constant range identically once one exists (index/count/stageFlags are identical for 1 vs 2 scalars — only size differs, two scalars packing into one 8-byte range), so a "1 crashes, 2+ fine" asymmetry cannot originate in the middleware layout code and must be upstream (driver or compiler codegen). (3) Deferred failure plus cross-kernel/fresh-buffer poisoning is persistent GPU *context* corruption — a driver-bug signature, not a per-pipeline layout error (a bad layout fails at pipeline creation or on its own dispatch, not one submission later). (4) The no-GPU driver-vs-compiler discriminator is to capture the generated SPIR-V (`SLANGPY_PRINT_GENERATED_SHADERS=1` → `-target spirv-asm`) and diff the push-constant block / decorations for 1 vs 2 members — a structural difference ⇒ escalate to shader-slang/slang (compiler owns it); identical ⇒ the driver owns it (the device-loss half still needs Blackwell HW). Related but NOT a duplicate: slang#12349 / slang-rhi#810 (phantom push-constant-only descriptor set) shares the file family but needs a `ParameterBlock` and fails *immediately* (validation VUID-…-07988 + silent no-write), so #810 does not fix #1165; slang#10675 confirms Vulkan routes a scalar `uniform` to a push constant while Metal wraps it in a cbuffer.

## CoopVec + RT device-loss is a documented slang-rhi NV-driver interference class, not Slang codegen

When a `SPV_NV_cooperative_vector` (CoopVec) **compute** dispatch device-losts (`VK_ERROR_DEVICE_LOST`) **only after** a `VK_KHR_ray_tracing_pipeline` was created/used in the same `VkDevice` (slang#13191, RTX 4060 driver 591.86, via slangpy→slang-rhi), the Slang compiler is exonerated by source fact: Slang emits each SPIR-V module independently — CoopVec caps/extensions/Vulkan-memory-model/matmul operands derive purely from the module's own IR + target caps and are byte-identical regardless of any RT pipeline elsewhere in the device (`slang-emit-spirv.cpp:10103` matmul, per-module memory model `slang-ir-spirv-legalize.cpp:2564-2606`, capdef `slang-capabilities.capdef:679`), so if the identical dispatch works alone it is not codegen. slang-rhi already documents this interference class: `DeviceDesc::enableRayTracing` (default `true`, `include/slang-rhi.h ~3534`) warns "enabling these extensions has been observed to interfere with concurrent **cuDNN** usage on some driver/GPU pairs" (sibling `enableCUDALaunchFromGfx`/VK_NVX_binary_import carries the same warning; both gated behind opt-out flags by slang-rhi **PR #760**, RT gating at `vk-device.cpp:883`) — the comment names cuDNN NOT cooperative-vector, so CoopVec matmul being an NV tensor/cuDNN-adjacent path in the same class is an INFERENCE (verify, don't overstate). Nuance: with `enableRayTracing` defaulting on, RT extensions are enabled even when coopvec-alone works, so the trigger is RT-pipeline **creation/use**, not mere extension enablement. Discriminating tests need a coopvec-capable NV GPU (570+ driver) — `enableRayTracing=false` → coopvec stops crashing? confirms RT is the cause; RT-PSO created-but-never-dispatched isolates PSO-creation vs dispatch; dump+validate SPIR-V RT-present vs absent (expect identical/valid). This env (L40S, driver 565.57.01) cannot reproduce coopvec at all (lacks `VK_NV_cooperative_vector`, needs 570+), and coopvec still *compiles* (exit 0) so compile-only checks give false confidence; disposition: likely NV-driver bug, may belong on shader-slang/slang-rhi rather than the compiler repo ([CoopVec/RT VK_ERROR_DEVICE_LOST is a documented slang-rhi NV-driver interference class](../learnings/1789964362918-coopvec-rt-vk-error-device-lost-is-a-documented-sl.md)).
