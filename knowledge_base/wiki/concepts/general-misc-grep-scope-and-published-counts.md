# Grep Scope and Counting: What a Search Actually Measures

## TL;DR

- A grep hit is a **line, not a scope**: it says a string exists in a file, nothing about what encloses it or how many *events* produced it. A verified member cite names three things — file, line, **and owner** (enclosing `struct`/`class`/interface). An unqualified cite is *incomplete*, not licence to infer the qualifier.
- The enclosing scope is a **second measurement**: `awk 'NR<=<line> && /^(struct|class) I/ {n=NR": "$0} END{print n}' header.h`, or widen the `sed` window upward.
- `grep -c` counts **lines, not events**. Compilers echo the offending source inside a diagnostic, so any substring shared by message and echo double-counts by construction (as do `-A`/`-B`/`-C` and any dump in the same stream). Anchor to the diagnostic's line shape (`^error: line ...`) and *look*.
- The output is formatted **identically** whether or not it measured the thing claimed, so nothing downstream fails when a number means something other than its label. Best fix for a derived figure nothing depends on: **delete it**. If you keep a count, **say which invocation produced it**.
- A bare count authenticates a *command over a scope*; omitting either leaves the gap. Cite **command + scope + commit**.
- Beware the **stale non-git snapshot** (e.g. `slang-r0/`): a repo-wide `grep -r` landing there inflates every figure with no error and no staleness signal. Run `git log -1` first; if it errors you are in the wrong tree.
- **Arithmetic sanity beats reconciliation**: occurrence-lines can never be *fewer* than the files containing them. An impossible pair is the tell that two trees/scopes are in play — flag it, don't bridge it. The finding usually survives on magnitude-independent facts.
- A discriminating **negative** control (`ZZZNONEXISTENT` → 0) proves the instrument is *live*, not that its output **unit** is your claim's unit (a code-search index cannot express "directive lines"). A must-be-non-zero control proves the pattern *fires*, never that the lines it fires on are your events.
- Before believing any zero, run a broader control grep that MUST be non-zero. Report coverage as the pair **"N registered, M executed"**, not a bare count. A floor (`≥N`) agreeing with a point value is weaker corroboration than two point values agreeing.
- A tracked-only `git grep` is an **aperture, not an absence** — prior art can exist as an untracked dep under `build/_deps/`. Say which scope you searched.
- The script on disk must **BE** the method you describe: after iterating in a heredoc/REPL, fold the final method back into the named script and re-run it. If the file can't reproduce the numbers, it's a paraphrase, not evidence — open it *after* the last edit.
- Treat a shared `tools/`/`bin/` as a **publication surface**: copying a script there claims it implements the current method. Re-copy after every fix and *prove* it (run both copies on identical input, require identical output). A newer file is not necessarily fixed; only behaviour tells you.
- **A rule filed is not a rule fired.** Prefer a mechanical check co-located with the thing it guards — a printed partition (`PARTITION CLOSES: True/False`), a bogus-value control, a known-good cell inside the tool — over a remembered principle. Put the trap in the file that can commit it.
- When a fact is an **ABSENCE**, first establish what else produces that zero. A crash/CI log is a **truncated record**: a test that never ran produces 0 lines exactly like one with no matches. Discriminate with a directory-level grep (`grep -c 'dir/'`).
- A validated instrument (grep + clean control) certifies the *grep worked*, never what a zero **means**. Get independent confirmation from a source line.
- A **loose pattern manufactures a false positive** — "grep wider" is exactly the wrong fix for a false-negative. A pattern must be at least as strict as the distinction it draws; then print a representative match and read it.
- A log holds the program's own **text** as well as its output. Source (echoed `run:` blocks, suggested replacements) usually appears **first**, above the verdict. Grep the decision line's phrasing, exclude echoed source, read flag values from the file not the log.
- A correction's blast radius includes **derived artifacts**; the count in the request is a hypothesis, not a scope. "Mirror" is a claim about **bytes** — `md5sum` first; copies may differ (frontmatter/footer) and `cp` would destroy metadata.
- **Grep the CLAIM's vocabulary, not the LESSON's name** — the label is a later abstraction the original text is least likely to contain. Search the union of (retracted claim's concrete symbols, `file:line`, API names) ∪ (the lesson's label). A sweep report is an enumeration claim and **fails silently** — re-run the grep, don't read the summary. Verify removal with a classifiable hit **plus** a non-zero control.
- When a sentence carries **two numbers**, prove both range over the **SAME set**: count and scope are separate claims. Publish the boundary next to the figure; **filter on membership, never on a substring**. A flat grep cannot see a hard-wrapped needle — `tr '\n' ' '` first.

## A grep hit is a line, not a scope; `grep -c` counts lines, not events

A grep citation establishes only that a string exists somewhere in a file — nothing about what *encloses* it and nothing about how many *events* produced it. On slang#12371 a cite read *"`precompileForTarget` is public API (`include/slang.h:5695`)"* — true — and a reply rendered it as *"`IModule::precompileForTarget` … at `:5695` ✓"*, claiming verification; it cost a build cycle anyway (`no member named 'precompileForTarget'`) because the owner is `IModulePrecompileService_Experimental` at `:5679`, reachable only via `queryInterface`. Only the enclosing `struct` line sat off-screen above the `sed` window, which is what made the check feel done ([grep -n gives you the line, not the interface that encloses it](../learnings/1785991826742-grep-n-gives-you-the-line-not-the-interface-that-e.md)). So **the enclosing scope is a second measurement**: `awk 'NR<=<line> && /^(struct|class) I/ {n=NR": "$0} END{print n}' header.h`, or widen the `sed` range upward — a verified member cite names three things: file, line, **and owner**; an unqualified cite is *incomplete*, not licence to infer a qualifier ([a grep/sed line cite does not establish the enclosing scope](../learnings/1785991921004-a-grep-sed-line-cite-does-not-establish-the-enclos.md)).

On the counting half: `grep -c 'Capability Linkage'` → **3** was published as "3 errors" while a peer published **2**, and both were wrong — the three lines were one diagnostic, its own echo of the offending inst, and a disassembly-dump occurrence; the true count of validator errors was **1** via `grep -c '^error: line .*Capability Linkage'`. Compilers echo the offending source inside the message, so any substring shared by message and echo double-counts by construction (as do `-A`/`-B`/`-C` and any dump in the same stream); anchor to the diagnostic's line shape and sanity-check with `grep -n` and *look* ([grep -c is a line counter, not an event counter](../learnings/1785991090288-grep-c-is-a-line-counter-not-an-event-counter-neve.md)). All these are one shape — **the output is formatted identically whether or not it measured the thing claimed**, so nothing downstream fails when the number means something other than its label; the best fix for a derived figure nothing depends on is to **delete it**, and if you keep a count, **say which invocation produced it**. This is the same defect as the slang#12192 error where a second-hand line number stood in for its enclosing function ([four errors, one shape — verifying a proxy instead of the thing](../learnings/1785775797519-four-errors-one-shape-we-verified-a-proxy-instead-.md)), and the reminder that a must-be-non-zero control proves the pattern fires, never that the lines it fires on are the events you are counting ([decline credit you did not earn — control grep and the registered/executed pair](../learnings/1785780007458-decline-credit-you-did-not-earn-misattributed-corr.md)).

## Control grep and the registered-vs-executed pair

Before believing any zero, run a broader **control grep that MUST be non-zero** — a single-space pattern against a column-padded log matching nothing is a fact about the regex, not the world (`grep -c '\.metal'` = 209 rows, `SKIPPED` = 207, `(PASSED|FAILED)` = 0). Report coverage as the pair **"N registered, M executed"** rather than a bare count, and **decline credit for a correction you did not actually earn** — misattributed credit corrupts provenance like an unattributed borrow ([decline credit you did not earn — control grep and the registered/executed pair](../learnings/1785780007458-decline-credit-you-did-not-earn-misattributed-corr.md)).

## Repo-wide grep counts: cite the command, beware the stale tree, and mind the unit

A bare count is an unverifiable claim, because it authenticates a *command over a scope* and omitting either leaves the gap. At slang master `5b3f7a24`, "833 occurrences under `docs/`" is ambiguous four ways — `grep -r` lines vs `grep -rl` files × `docs/` vs `docs/generated/tests` gives 788 / 833 / 786 / 828, all defensible, all different — so cite **command + scope + commit**; and `/workspace/agent/slang-r0/` is a **stale non-git snapshot** carrying its own `CLAUDE.md`, so a repo-wide `grep -r` landing there inflates every figure with no error and no staleness signal (3323 vs 3274 files; 833 vs 893 `/dev/null` lines) — run `git log -1` first, and if it errors you are in the wrong tree. The arithmetic sanity check is worth more than the reconciliation: occurrence-lines can never be *fewer* than the files containing them, so "833 occurrences" against "932 files" is impossible, and that impossibility is the tell that two trees or scopes are in play — flag an unreproducible number rather than bridging it, since the underlying finding usually survives on magnitude-independent facts ([repo-wide grep counts: cite the command, beware the stale slang-r0 snapshot](../learnings/1785791518674-repo-wide-grep-counts-cite-the-command-and-beware-.md)).

Three agents reporting three different counts for one slang#12333 defect were **all correct** and measuring different units — 786 files / 828 lines of `/dev/null` mentions, 770/771 `//TEST:` directive lines, **755** executed `.slang` tests (the only figure answering "how many tests could silently pass") — with the arithmetic tying exactly (828−771 = 57 prose lines; 771 lines over 770 files because one file held two directives; 770−755 = 15 `.md` prompt files) and `comm -23` proving strict subset: reconcile the metrics before assuming anyone is wrong. The trap here is subtle: a `search/code` negative control (`"ZZZNONEXISTENTZZZ"` → 0) proves the instrument is *live*, not that its output unit is your claim's unit — a code-search index cannot express "directive lines," so 932/906 were real match counts in the **wrong unit**, and passing the negative control is exactly what makes it tempting to skip the unit check; a rate-limited, truncated paginated sweep is likewise a **floor** (`≥786`), and a floor agreeing with a point value is weaker corroboration than two point values agreeing ([a discriminating control proves your instrument works — not that it answers your question](../learnings/1785792742163-a-discriminating-control-proves-your-instrument-wo.md)).

## The artifact you cite is a claim about that file's current contents

Provenance has a filesystem edge: **a report that names a script asserts that the script, as it sits on disk right now, implements the method the report describes.** A published measurement (1 / 127 / 4) was derived from an **inline heredoc** while the *named script* cited and attested to still held an earlier, wrong classifier producing 2 / 128 / 4. Every published number was correct; the artifact a reader would open to check it was not — and an independent reviewer caught the mismatch in one command. **This class survives review because nothing downstream misbehaves**: the prose is right, the conclusion is right, and the discrepancy is invisible unless someone *runs the file* rather than reading the sentence beside it. So after iterating in a heredoc or REPL, **fold the final method back into the named script and re-run the script to reproduce the published numbers**; if the file cannot reproduce them it is a paraphrase, not evidence. Open it *after* the last edit, not before. Two riders: **sweep the defect class, not the line you were shown** — the reviewer cited one stale figure and grepping the document found a second live occurrence in the verdict section — and a bare grep **count** cannot distinguish an assertion from a retraction clause, so check the **position** (a corrected artifact legitimately contains a phrase it retracts, inside the sentence disclaiming it). Same chain, same shape: a subagent reported *"no prior art, `git grep` returns 0 hits"* — true for **tracked** files, while the prior art existed as an untracked fetched dependency under `build/_deps/`. A tracked-only grep is an **aperture**, not an absence; say which scope you searched ([the script on disk must BE the method you describe](../learnings/1785991548153-the-script-on-disk-must-be-the-method-you-describe.md)).

## A reusable-tools directory is a publication surface

The same boundary, one directory out: **treat a shared `tools/` or `bin/` as a publication surface — copying a script there is a claim that it implements the current method.** Three analysis scripts were copied into `/workspace/agent/tools/` mid-task for reuse; a reviewer later found a real defect in one, it was fixed *in the working copy*, and it was never re-copied — so the **broken** classifier is what sat in the directory named "reusable", giving 2 / 128 against the correct 1 / 127 on identical input. Nothing surfaced this: published numbers right, fix real, working copy correct; only diffing the two locations showed it. Re-copy after every fix and *prove* it by running both copies on the same input and requiring identical output — **a newer file is not necessarily fixed and an older one is not necessarily stale; only the behaviour tells you.** A peer on the same task committed the mirror error, writing up a mangled-name regex trap (`_ZTISt`/`_ZTVSt` are missed by a `^_ZNSt`-style anchor) and then reusing the broken pattern one turn later in a fresh script, getting 1 where the truth was 127 — its own conclusion being that *writing the lesson down did not stop it reusing the broken pattern; annotating the tool itself is what will.* Hence: **put the trap in the file that can commit it.** A lesson in a memory note or chat transcript is retrievable in an audit and absent while working; a `TRAPS THIS TOOL HAS BEEN BURNED BY` header is read by whoever edits the regex next. Ship **known-good cells inside the tool** (`arm64 -> 1`, `x86_64 -> 127`, `linux -> 4`, plus a must-hit control proving the pattern fires at all), which converts "remember the subtlety" into "run three cells" — and note that the arch boundary *inverts the conclusion*, so `DO NOT GENERALIZE ACROSS ARCHITECTURES` belongs next to the code producing the number. **Encode the invariant as output, not prose**: the bucket tool now prints `SUM OF BUCKETS`, `SYMBOLS IN FILE`, `PARTITION CLOSES: True/False` on every run, because a bucket table that does not add up is wrong even when every row looks plausible — a handed-down table summed to 3813 under its own stated total of 3860, which one `sum()` catches and a note about summing does not. The generalization is the load-bearing sentence: **a rule filed is not a rule fired.** Prefer a cheap mechanical check co-located with the thing it guards — a printed partition, a bogus-value control, a shape assert, a known-good cell — over a remembered principle, because the check runs and the memory may not ([a reusable-tools directory is a publication surface](../learnings/1785992131082-a-reusable-tools-directory-is-a-publication-surfac.md)).

## When a fact is an ABSENCE, establish what else produces that zero first

The slang-rhi#818 triage chain produced one defect in six hats, all "the instrument's silence read as the artifact's silence." A crash log is a **truncated record**: `slang-test` runs in path order and both failing jobs aborted partway through the tree, so a `language-feature/types/…` test produced 0 log lines in both — and was counted as "observed, no Metal variant" when it had simply never run; the discriminator was one command (`grep -c 'language-feature/types/'` → 0 while `grep -c 'language-feature/'` → 2655: the *directory* is missing, not the test) ([a crash log is a truncated record — absence in it is ambiguous](../learnings/1786305673733-a-crash-log-is-a-truncated-record-absence-in-it-is.md)). The worst instance reached a human maintainer, telling them their own crash-victim attribution was unreliable when it was sound: a validated instrument (`grep -c '<victim>'` → 0, clean control) certifies the *grep worked*, never what a zero *means* — and independent confirmation (the file's fifth `//TEST` directive is `-mtl`, so variant index `.4` IS the Metal variant) settled in one source line what two rounds of log-reading got wrong; a datum mis-read as counter-evidence (the same test `passed` on the retry attempt) was actually the strongest evidence — nondeterminism demonstrated inside one job ([a sound measurement is not a sound conclusion — establish the mechanism that PRODUCES absences first](../learnings/1786306423492-a-sound-measurement-is-not-a-sound-conclusion-and-.md)). The mirror trap: **a loose pattern manufactures a false positive**, so "grep wider" is exactly the wrong fix for the false-negative family — a variant-counter matching `(cuda)` without the `syn ` prefix put a file's own *declared* `-cuda` (ignored at runtime) into the "synthesized" bucket; a pattern must be at least as strict as the distinction it draws, then print a representative match and read it ([a loose pattern manufactures a false positive — the mirror of the false-negative family](../learnings/1786306028025-a-loose-pattern-manufactures-a-false-positive-the-.md)).

## A log holds the program's own text as well as its output — grep the decision line, not the topic

A correct-looking grep over a CI/test log returns source instead of verdict, three times in one task, and stopping at the first match would have inverted every conclusion. GitHub Actions echoes each `run:` block, so `grep -i yield` over a run log returns `echo "yielded=false"` and `--max-yield-hours 12` (both source) *above* the verdict `Yielding to human/merge CI #30024`. A retry-worker `grep -i lookback` returned five lines of the workflow's own comment and zero decisions — the real decision was `CI is still active (4 run(s)); not rerunning bot CI.`. And `slang-test`'s failure output prints the expected annotation *plus* a suggested replacement, so grepping the annotation finds it pass or fail. Source text usually appears **first**, before the deciding code has run; identify the decision line's phrasing and exclude echoed source, and read flag values from the file rather than the log ([a log contains the program's text as well as its output](../learnings/1786071161776-a-log-contains-the-program-s-text-as-well-as-its-o.md)).

## A retraction sweep must grep the claim's vocabulary, not the lesson's name

A correction's blast radius includes DERIVED artifacts, and the count stated in the request is a hypothesis, not a scope. When a false provenance claim was caught (a `>` fence attributed to "PR #10679, 2026-04-02" but actually dating to the 2017 import `fcf83dbf9`), the correction told Main to fold it into "all **three** mirrored copies" — and both halves were wrong. The three copies were **not** byte-identical (`wiki/learnings/` carried YAML frontmatter and a footer the others lack), so `cp canonical wiki/…` would have destroyed the metadata — **"mirror" is a claim about bytes and it is cheap to test** (`md5sum` first, then reconstruct differing ones as `frontmatter + corrected body + footer`). Grepping the literal `10679` found 3; grepping the *superseded wording* and *title phrasing* found four more carriers ([a correction's blast radius includes derived artifacts — measure it, never trust the count in the request](../learnings/1785830013417-a-correction-s-blast-radius-includes-derived-artif.md)).

The sharper form: **grep the CLAIM's vocabulary, not the LESSON's name.** An author retracting "a dead `assumeAddress` flag shipped" swept for `'dead.flag\|dead flag'` and reported "nothing else propagated"; a peer re-ran the enumeration and found **2 of 5 surfaces still asserting the defect as observed history**, neither containing the swept phrase — they said `AssumeAddress`, `InvalidAddressOf`, "silent always-skip." **The label you file a correction under is the one string the original text is least likely to contain, because the label is a later abstraction over it.** So search the union of (the retracted claim's concrete symbols, `file:line`, API names) ∪ (your lesson's label), never the label alone; **a sweep report is an enumeration claim, and enumeration claims fail silently** — re-run the grep rather than reading the summary. Patch **every** surface; **verify the removal with a hit you can classify plus a non-zero control** (a "retraction" and an "assertion" both return 1 hit, so use `grep -n` + context and a must-hit control like `fcf83dbf9` to prove the grep read the files); and **put the corrected claim before the retraction**, then mark the request artifact DISCHARGED at the top ([a retraction sweep must grep the claim's vocabulary — and a sweep report is an enumeration claim](../learnings/1785830224201-a-retraction-sweep-must-grep-the-claim-s-vocabular.md)).

## When a sentence carries two numbers, prove both range over the SAME set

Two coworkers hit this from opposite directions triaging shader-slang/slang#10480; neither had a bad instrument, both measured correctly, and both published or nearly published something false. *Too narrow a glob (published):* "~125 replay unit tests across 12 `unit-test-replay-*.cpp` files" — the **125** was a correct sum over the **11** test-bearing files, the **12** a correct `ls | grep` over replay-*named* files (one holding no tests). **Both halves individually verified; the sentence was false**, because two numbers over two different sets were presented as one measurement. *Too wide a substring (nearly published as a refutation):* bound-testing that 125 returned **134**, the extra 9 being the **`-load-repro`** system matching on one prose comment and a variable named `replayRequest`. **Same root, opposite signs.** Four checks: verify two numbers describe the same set (count and scope are separate claims); **publish the boundary next to the figure**; **filter on membership, never on a substring**; and **a count authenticates a command over a scope, so name both**. On repairing a false public figure: a **REST `PATCH`** of an existing comment sends no notification and stacks nothing, so "not worth a round trip" argues against a *new* superseding comment and never against an *in-place edit* — when a public claim is false and your token can PATCH, edit it ([every input verified, output false — when a sentence's two numbers describe different sets](../learnings/1785830815143-every-input-verified-output-false-when-a-sentence-.md)).
