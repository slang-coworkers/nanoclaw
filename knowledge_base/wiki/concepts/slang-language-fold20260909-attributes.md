# Slang Attributes: Parsing, Name Resolution, and Target Whitelist

How `[Attr(...)]` attributes flow through the Slang front-end: the parser (`parseAttributeName`, `ParseModifiers`), the checker's resolution (`lookUpAttributeDecl`), and the target whitelist (`_AttributeTargets` / `getAttributeTargetSyntaxClasses`) that decides which decl positions may carry a user attribute. Two independent gates — the parser and the whitelist — must both admit a new attribute position.

## TL;DR

- Attributes are parsed by `parseAttributeName` (name) + `ParseModifiers` (per-decl), resolved by `lookUpAttributeDecl` against a target whitelist (`_AttributeTargets` / `getAttributeTargetSyntaxClasses`); the parser and the whitelist are **separate** gates a new attribute position must clear.
- `[Attr]` on an enum member (#12551) is a **two-layer** gap: `parseEnumCaseDecl` never calls `ParseModifiers`, and `EnumCaseDecl` isn't in `_AttributeTargets` — but the reflection half already works (enum members reflect as `VariableReflection`, so per-member attribute reflection comes for free once the front-end admits it).
- A `::`-qualified attribute name is FOLDED to a flat underscore name in the parser by design (`[vk::binding]` → `vk_binding`), which is how builtin qualified attributes resolve. A fix for namespaced USER attributes must keep the flat lookup FIRST and add scoped resolution as a FALLBACK — never split the flat name on `_` (namespace/identifier names contain underscores). Today `[ns::Attr]` warns `E31000 unknown attribute 'ns_Attr'` and is silently dropped (#12668).
- A `string` argument of a user attribute reflects back only when it is a raw string LITERAL: `spReflectionUserAttribute_GetArgumentValueString` returns `nullptr` for anything else, so `static const string X = "..."; [Attr(X)]` type-checks but reads back null. A `#define X "..."` macro round-trips (the parser sees a literal). Source-read inference, not yet compiled.
- Float/half/double user-attribute arguments are not folded on master (#13952): reflection reads only a bare float literal (or an int literal implicitly cast); `1.0/2.0`, `static const float`, `float(2)` and a literal passed to a `double`/`half` parameter all reflect as invalid. Only `-1.5` works, because the parser folds unary minus on a literal. The front end has no float constant folder.
- A front-end fold for attribute arguments (open PR #13953) stores the result in a semantic field beside the argument (`Attribute::floatArgVals`, like `intArgVals`), never a synthetic literal in `args[i]`; reflection keeps a literal-shape fallback, because builtin attributes' arguments are never type-checked.
- Fold query-style through a scratch `DiagnosticSink`: `coerce()` already folds an integer operand converted to an integer or `half` type and reports its diagnostics, and the sink does not deduplicate, so a second fold on the real sink double-reports (test `half` as well as `float`).
- `tryConstantFoldExpr` folds integers in int64 without wrapping; normalize through `TypeCastIntVal::tryFoldImpl` before converting. Treat a `kIROp_Nop` intrinsic as identity only when operand type == result type.

## User Attributes on Enum Members: Two-Layer Front-End Gap (#12551)

Allowing `[Attr]` on enum members (#12551) is a TWO-LAYER front-end gap, both layers needing a fix. (1) PARSER — `parseEnumCaseDecl` (`slang-parser.cpp:6475`) reads only an identifier + optional `=tag` and never calls `ParseModifiers`, so `[...]` before a case is `E20001 unexpected token` at parse time — rejected before any semantic check, whereas every other member-decl path DOES call `ParseModifiers`. (2) TARGET WHITELIST — `_AttributeTargets` (`core.meta.slang:4733`, backed by the C++ `UserDefinedAttributeTargets`, `slang-syntax.h:587`) only lists Struct/Var/Function/Param, and `getAttributeTargetSyntaxClasses` (`slang-check-modifier.cpp:299`) has no `EnumCaseDecl` mapping, so `validateAttribute` would reject even if parsed. `EnumCaseDecl` DOES derive from `Decl`, so it can structurally hold modifiers — the slot is just never populated. KEY: the REFLECTION half already works — enum members are reflected as `VariableReflection` (`slang-reflection-api.cpp:603`), which already exposes `getUserAttributeCount`/`getUserAttributeByIndex`/`findAttributeByName` reading from AST modifiers, so once parser + whitelist admit the attribute, per-member reflection surfaces for free (NO new reflection API). Recommended fix: add modifier parsing to `parseEnumCaseDecl` plus a first-class enum-member `_AttributeTargets` member (a public-ish core-module enum, so the flag name/shape is a maintainer nod); additive/non-breaking since the syntax position was always an error before. Caveat: user attributes live in AST modifiers, not IR decorations, so precompiled/serialized `.slang-module` survival needs checking ([User attributes on enum members: two-layer front-end gap, reflection already works](../learnings/1786742270900-user-attributes-on-enum-members-two-layer-front-en.md)).

## `::`-Qualified Attribute Names Are Folded to Flat Underscore Names in the Parser (#12668)

When triaging attribute name-resolution bugs (e.g. #12668 — a user-defined attribute in a namespace not found via `[ns::Attr(...)]`), the root cause is in the PARSER, not the checker. `parseAttributeName` (`slang-parser.cpp:~941`) intentionally FOLDS a `::`-qualified attribute name into a single underscore-joined identifier: `[my_namespace::Example]` becomes the flat name `my_namespace_Example` before any semantic checking. `UncheckedAttribute`/`AttributeBase` (`slang-ast-modifier.h:~806/820`) then store only that flat `keywordName` (plus `originalIdentifierToken` = the LAST segment only), so the qualified path is unrecoverable, and `lookUpAttributeDecl` (`slang-check-modifier.cpp:~163`) does a flat lookup then appends `"Attribute"` via plain string concat (`~:224`) — so a namespaced user attribute is searched for as the nonexistent `my_namespace_ExampleAttribute`. WHY the fold is deliberate (a load-bearing constraint for any fix): Slang's builtin qualified attributes are REGISTERED under flat underscore names in `core.meta.slang` (`attribute_syntax [vk_binding(...)] : GLSLBindingAttribute;` `~:4381`, plus vk_location, vk_push_constant, vk_shader_record, gl_binding, …), so user source `[vk::binding(0,1)]` only works because the fold produces `vk_binding`, matching the registered `AttributeDecl` in the FIRST lookup branch (~30+ tests depend on this). A fix for user-defined qualified attributes must therefore keep the existing flat lookup FIRST and add scoped resolution only as a FALLBACK — never remove the fold. Splitting the flat name back on `_` is NOT viable (namespace/identifier names legitimately contain underscores — `my_namespace` itself does — so `_`-boundaries are ambiguous); the parser must PRESERVE the qualifier segments to fix it properly. Reproduces on CPU/front-end only: `slangc file.slang -target spirv -o out.spv` emits `warning E31000: unknown attribute 'ns_Attr'` and silently drops the attribute (exit 0, so it's a warning not an error) ([Slang attribute ::-qualified names are folded to underscore flat names in the parser (deliberate, for builtin vk::/gl_ attrs)](../learnings/1787273970210-slang-attribute-qualified-names-are-folded-to-unde.md)).

## String Arguments of User Attributes Reflect Only as Raw Literals

Consider a user who wants a named constant string in an attribute:

```slang
static const string kName = "foo";
[MyAttr(kName)] struct S {}
```

The checker accepts this, but reflection returns nothing for the argument. `spReflectionUserAttribute_GetArgumentValueString` (`slang-reflection-api.cpp` ~L401) returns a value only when the stored argument expression is a `StringLiteralExpr`, and `nullptr` otherwise. On the checking side (`slang-check-modifier.cpp` ~L997), a `string` parameter of a user-defined attribute is only `CheckTerm`'d and coerced, never folded to a constant, because `isValidCompileTimeConstantType` accepts only scalar integers and enums. So the argument stays a `VarExpr` referring to `kName`, and the reflection accessor sees a non-literal. A `#define kName "foo"` macro should round-trip, because preprocessing hands the parser a real literal. This is an inference from reading source (2026-09-29, from a Discord question about named constant strings in attributes) and has not been confirmed by compiling; verify with a reflection probe before telling a user it is the behaviour ([User-attribute string args: reflection only returns raw string literals](../learnings/1790669546280-slang-user-attribute-string-args-reflection-only-r.md)).

## Float Arguments of User Attributes: Not Folded on Master, and the Traps in Folding Them (#13952, PR #13953)

The same literal-only rule holds for `float`, `half` and `double` parameters. User-attribute arguments are folded only for int, bool and enum parameters (`isValidCompileTimeConstantType` → `checkConstantIntVal` → `Attribute::intArgVals`, `slang-check-modifier.cpp` ~L1009); a floating-point parameter keeps the checked `Expr`, and `spReflectionUserAttribute_GetArgumentValueFloat` (`slang-reflection-api.cpp` ~L375) reads only a bare `FloatingPointLiteralExpr` or an `ImplicitCastExpr(IntegerLiteralExpr)`. On master 52e29ab43, `slangc -reflection-json` reports "invalid value" for `1.0/2.0`, a `static const float` reference, `-(1.5)`, `float(2)`, an int constant passed to a float parameter, and even a plain literal passed to a `double` or `half` parameter. `-1.5` works only because the parser folds unary minus on a literal (`_foldFloatPrefixOp`). The front end has no float `Val` and no float constant folder (float folding exists only in IR SCCP, and user attributes are never lowered to IR), and `GetDefaultValueFloat` has the same limit, so a fix for #13952 needs a front-end float constant path rather than a reflection-side tweak [Slang user-attribute float args: no frontend float folding (#13952)](../learnings/1792995287897-slang-user-attribute-float-args-no-frontend-float-.md). That is still true on master as of 2026-10-27, with PR #13953 open.

PR #13953 folds the arguments in the checker and stores each result in a semantic field, `Attribute::floatArgVals`, beside `intArgVals`. Rewriting `args[i]` into a synthetic literal would be semantic-to-syntax reconstruction. Folding exposed these traps:

- **Reflection still needs the literal-shape fallback.** `findUserAttributeByName` iterates every `Attribute`, including builtins such as `[maxtessfactor(64.0)]`, whose arguments `checkAttribute` never type-checks, so a reader of checker-folded data alone silently regresses builtin attributes [Slang front-end float folding for user-attribute args: gotchas (#13952)](../learnings/1793000621319-slang-front-end-float-folding-for-user-attribute-a.md).
- **Integer folds do not wrap.** `tryConstantFoldExpr` computes integer arithmetic in int64 (`0u - 1u` folds to -1, `2147483647 + 1` to +2^31); normalize with `TypeCastIntVal::tryFoldImpl(astBuilder, type, val, nullptr)` before converting to another type [Slang front-end float folding for user-attribute args: gotchas (#13952)](../learnings/1793000621319-slang-front-end-float-folding-for-user-attribute-a.md).
- **Identity and cast shapes.** Unary `+` is not on the `BuiltinOperatorExpr` fast path (only `-`, `!` and `~` are); it is `__prefix __intrinsic_op(kIROp_Nop) T operator+(T)`. `__slang_noop_cast<T,U>` also uses op 0 and changes type, so a Nop intrinsic is identity only when operand type == result type. Implicit casts built by `CreateImplicitCastExpr` have a `SharedTypeExpr` callee with no `ImplicitConversionModifier` decl, so recognize them by the `TypeCastExpr` node kind; constructor-style `float(2)` resolves to a builtin `__init` that carries `ImplicitConversionModifier` [Slang front-end float folding for user-attribute args: gotchas (#13952)](../learnings/1793000621319-slang-front-end-float-folding-for-user-attribute-a.md).
- **A second fold on the real sink double-reports.** `coerce()` (`slang-check-conversion.cpp` ~2890–2990, via `getFoldedIntVal`) already constant-folds an integer operand to range-check it when the conversion cost is at least `kConversionCost_Default`: int→integer and int→`half` (`kConversionCost_IntegerToHalfConversion` = 500) qualify, int→`float`/`double` (400) do not. That fold reports the integer folder's diagnostics (E30002 divide by zero) on the real sink, and `DiagnosticSink` does not deduplicate, so in #13953 round 2 `[halfProbe(1 / 0)]` gave E30002 twice while a `float` parameter gave it once. The fix folds quietly: `DiagnosticSink scratch(getSourceManager(), nullptr, getSink()); SemanticsVisitor v(withSink(&scratch));` (the alternative is to skip operands that coercion has already folded). The scratch sink does not swallow declaration errors, because `ensureDecl` checks a referenced declaration in a fresh `SemanticsContext(getShared())` on the shared sink; only the folder's direct diagnostics and `ensureDecl`'s own CyclicReference go to scratch. Diagnostic-count tests should cover `half` as well as `float` [Front-end float folding of an int operand can double-report diagnostics for half targets (coerce already folds int→half)](../learnings/1793007390694-front-end-float-folding-of-an-int-operand-can-doub.md) [Slang checker: fold quietly with a scratch sink; coerce() already folds int→half](../learnings/1793009488997-slang-checker-fold-quietly-with-a-scratch-sink-coe.md).
- **Float literals are `float`.** Slang lexes an unsuffixed float literal as `float`, so `[doubleProbe(16777217.0)]` already arrives as 16777216; a double-precision rounding test needs intermediate results such as `16777216.0 + 1.0 - 16777216.0` [Adding a FIDDLE() field to an AST node needs a module-version bump (old .slang-module segfaults)](../learnings/1793002822043-adding-a-fiddle-field-to-an-ast-node-needs-a-modul.md).
- **Circular constants crash today.** Circular `static const float` definitions (`A = B; B = A;`) segfault slangc at 52e29ab43 even when nothing references them, so a new E39999 on that input replaces a crash rather than rejecting a valid program [Front-end float folding of an int operand can double-report diagnostics for half targets (coerce already folds int→half)](../learnings/1793007390694-front-end-float-folding-of-an-int-operand-can-doub.md).
- **The new AST field has costs outside the checker.** A `FIDDLE()` field of type `List<std::optional<T>>` needs a `dump(const std::optional<T>&)` overload in `slang-ast-dump.cpp` (clone and serialization already handle the type), and it shifts the serialized layout of every `Attribute` subclass, so it needs a `k_min`/`k_max` module-version bump; see [[wiki/concepts/slang-compiler-serialization-and-enums.md]] [Slang front-end float folding for user-attribute args: gotchas (#13952)](../learnings/1793000621319-slang-front-end-float-folding-for-user-attribute-a.md) [Adding a FIDDLE() field to an AST node needs a module-version bump (old .slang-module segfaults)](../learnings/1793002822043-adding-a-fiddle-field-to-an-ast-node-needs-a-modul.md) [Slang checker: fold quietly with a scratch sink; coerce() already folds int→half](../learnings/1793009488997-slang-checker-fold-quietly-with-a-scratch-sink-coe.md).
