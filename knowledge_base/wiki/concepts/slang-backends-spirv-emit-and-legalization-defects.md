# Slang SPIR-V emit and legalization defects: logical pointers, opaque copies, constants, and diagnostics

Recurring defect classes in SPIR-V legalization and emit, each with the layer the fix belongs in: logical pointers inside composites, copies of non-copyable opaque values, constant and scalar-type emit gaps, and where legalize-time diagnostics fire. The emitter overview is on [[wiki/concepts/slang-backends-spirv.md]].

## TL;DR

- SPIR-V symptoms usually trace upstream (an IR pass, a core-module producer, a downstream tool), not to emit. Verify the premise against real output: compile, disassemble, and cite primary spec text.
- A logical-address-space pointer may not be an operand of a composite instruction, and VariablePointers does not help; only physical pointers are legal in a struct. Validate with SPIRV-Tools v2026.4+, which the slang build dir can build as its own `spirv-val` target (no Vulkan SDK needed); the repro is invalid at `-O0` too. The fix belongs in type legalization; until then, pass the `Ptr` as a direct parameter instead of a struct field.
- A logical buffer-element pointer stored into a `Ptr<T>` struct field or array element is not reconciled by address-space specialization, and no valid SPIR-V exists for it (no logical→physical conversion). Diagnose it post-dataflow in the SPIR-V path, because `-g2` changes whether the struct survives.
- Resource legalization does not recurse into struct fields, so a struct holding a buffer, used as an array, escapes it (#9062); autodiff reliably builds that shape.
- A copy of a non-copyable opaque value (`__constref ParameterBlock`, a `RayQuery` return) is fixed in IR copy-elision or a scoped NRVO gated on `isNonCopyableOpaqueType`, not in AST lowering.
- `UIntPtr` is an emit-layer gap (add the type-decl case); `IntPtr` also needs signedness-classifier fixes.
- `OpConvertPtrToU` needs an unsigned result type, but `OpConvertUToPtr` accepts a signed operand. Emit pointer→signed-int as an unsigned convert plus `OpBitcast` in `emitCastPtrToInt` only.
- A constant whose IR type disagrees with its literal kind (`getIntValue(floatType, 0)`) emits a malformed `OpConstant`; fix the producing cast, not the constant emitter.
- The `IArray`/`IRWArray` subscript requirement takes `int`, so a `uint64_t` index truncates there while a direct buffer subscript keeps 64 bits.
- `legalizeSPIRV` worklist diagnostics fire before OpKill DCE, so they also fire on code after `discard`. A diagnostic that renders a resource type name must run before `lowerBufferElementTypeToStorageType`: capture the name early and defer the emit. Judge "peer" diagnostics by pass placement, not subject.
- When relaxing a rejection predicate, enumerate the discriminator's full range.
- `spirv_asm` `&x` on a non-addressable operand reports E29103, which is only a note, so lowering continues with a null operand and SPIR-V emit segfaults. Any failure path that emits only a note or warning lets codegen run on broken IR; promote it to an error and return a poison value. Put a lowering-time diagnostic test in an emitted entry point.
- The direct SPIR-V backend cannot decorate a global resource `OpVariable` (`$tex` names the inserted `OpLoad`; `[[vk::ext_decorate]]` is unknown). Before claiming "no workaround", try a GLSL intrinsic with `-emit-spirv-via-glsl` (QCOM image processing works that way).
- Prove a guard's else-branch reachability from its callers' asserts.
- A new SPIR-V opcode may be a block terminator (`OpAbortKHR`): model it as one, stop block emission, and remove the unreachable code.

## Logical pointers inside composites

A struct whose field is a `Ptr<T, Access, GroupShared/Function/Private>` emits a composite instruction that carries a logical pointer. slangc is silent (rc=0). A spirv-val from SPIRV-Tools v2026.4 reports "Instruction may not have a logical pointer operand" / "may not return a logical pointer"; the first note on this class used the Vulkan SDK 1.4.363.0 build of it and found that `SLANG_RUN_SPIRV_VALIDATION` did not flag the repro ([spirv-val v2026.4 flags logical-pointer composites](../learnings/1792158143962-get-a-spirv-val-new-enough-to-flag-logical-pointer.md)). The SDK is not needed: in the slang build dir, `ninja -f build-Release.ninja spirv-val libslang-glslang-0.0.0.so` (about 4 min on 64 cores, master 653bfdee) builds SPIRV-Tools v2026.4 at `build/external/spirv-tools/tools/Release/spirv-val`, and that binary flags the #13206 repro. Build the glslang `.so` with it, or `slangc -target spirv` at the default -O fails with "failed to load downstream compiler 'spirv-opt'" ([#13206: the in-tree spirv-val target catches it, and -O0 fails too](../learnings/1792650915179-13206-logical-ptr-in-struct-in-tree-spirv-val-targ.md)). The repro is invalid at every opt level, which corrects an earlier note that the composite appears only at `-O1` ([slang-test injects -O0](../learnings/1790037466327-slang-test-injects-o0-verifying-spir-v-logical-poi.md)): the default -O gives `OpCompositeConstruct %View` with a logical-pointer operand, and `-O0` fails with a different error, `Instruction may not return a logical pointer` on `OpCompositeExtract %_ptr_Workgroup_float`. Release slangc v2026.18 through v2026.19 and master 653bfdee all fail this way. A plain `Ptr` local, or `a.data[0]=1` with no subscript or method call, validates; the repro needs a struct value that is copied or captured through `this`. **Workarounds for users**, both verified with the in-tree spirv-val on master 653bfdee: pass the `Ptr<float, Access.ReadWrite, AddressSpace.GroupShared>` directly as a function parameter instead of wrapping it in a struct, or keep the struct and write `a.data[i] = v` instead of calling the `[nonmutating] set` subscript. No front-end diagnostic or doc covers the shape. Type legalization never splits the field out, because `isResourceType` (slang-legalize-types.cpp:164-200) does not treat a GroupShared `IRPtrType` as special, and a comment at slang-emit-spirv.cpp:12392 says nested struct pointers are not inspected [#13206 workarounds verified: direct Ptr param or a.data[i] both pass spirv-val](../learnings/1792658747822-13206-workarounds-verified-direct-ptr-param-or-a-d.md). VariablePointers is already declared and doesn't help; only `PhysicalStorageBuffer` pointers are legal in a composite. Path: a partial field write → SSA aggregate → `emitMakeStruct`. No SROA pass or diagnostic exists; `specialize-address-space` only re-types slots (#13039). Same class as #9062. Any fix must cover copies, returns, and phis of a struct that contains a logical pointer ([logical Ptr as struct field](../learnings/1790017243652-logical-address-space-ptr-as-a-struct-field-invali.md)). The maintainer set the fix direction as type legalization (draft PR #13305); the ad hoc pass in PR #13214 was closed.

**`OpCompositeConstruct` of logical-pointer array (#9062):** SPIR-V logical addressing forbids logical (StorageBuffer/Uniform/Workgroup) pointers as operands to `OpCompositeConstruct`. The resource-legalization passes that eliminate arrays-of-resources only inspect the array's *direct* element type (they `unwrapArray()` through nested arrays and check whether the unwrapped type is *directly* a resource) — they do **not** recurse into struct fields, so a `struct { RWStructuredBuffer buf; }` used as `MyPtr[2]` is invisible while a bare `RWStructuredBuffer[2]` is caught. Autodiff reliably materializes this shape (`Array<T,N> : IDifferentiablePtrType` → whole array wrapped as one `DifferentialPtrPair` → lowered to a struct), which is why the maintainer couldn't repro without autodiff; pass ordering is fine (resource legalization runs after autodiff) — the escape is *structural blindness*, not a timing gap ([OpCompositeConstruct of logical-pointer array escapes resource legalization (struct-field blindness)](../learnings/1783524098198-slang-9062-spir-v-opcompositeconstruct-of-logical-.md)).

**A logical buffer-element pointer stored into a `Ptr<T>` struct field or array element is unreconciled (#13418).** The #12592 slot reconciler (`reconcilePointerSlotWithStoredValue`, slang-ir-specialize-address-space.cpp) retypes only Var/DebugVar slots whose contained type is itself a pointer. A struct- or array-typed slot (`H h; h.p = &rwbuf[i]`, or `Ptr<float> a[2]; a[0] = &rwbuf[0]`) is skipped, and the dataflow also ignores stores (`case kIROp_Store: break;`). The result is `OpStore PSB* <- StorageBuffer*`, which fails validation at every opt level. It cannot be "made to compile" with the current types: SPIR-V has no logical→physical pointer conversion, and the surface `AddressSpace` enum has only Device, GroupShared and VaryingInput, so the field can only be physical. Draft PR #13305 splits out only logical-typed fields (`!isUserPointerType`), so it does not cover this case. Whether the struct survives depends on optimization: the no-call variant (`*h.p` inline) validates at the default level and at -O0, but fails at -g2 through the struct DebugVar. That rules out a front-end diagnostic; the check belongs post-dataflow in the SPIR-V path (the variant matrix is in issue comment 6495754058) [SPIR-V: logical buffer-element pointer stored into a Ptr<T> struct field/array element is unreconciled (slang#13418)](../learnings/1793274304877-spir-v-logical-buffer-element-pointer-stored-into-.md). To reproduce an address-space-clone bug, call a `[mutating]` method on a `groupshared` struct receiver, which does create a Workgroup clone. An `inout` argument that is a `groupshared float` element is copied into a Function temporary before address-space specialization, so it creates no Workgroup clone [slangc exits 0 on spirv-link failure; SPIRV validation env breaks precompiled-module probes](../learnings/1793272392830-slangc-exits-0-on-spirv-link-failure-spirv-validat.md).

**A null groupshared pointer under `-g`.** With `-g`, direct SPIR-V turns `Ptr<int, Access.ReadWrite, AddressSpace.GroupShared> p = nullptr` into `OpConvertUToPtr %_ptr_Workgroup_int`, which spirv-val rejects. The cause is `processPtrLit` in `slang-ir-spirv-legalize.cpp`, and the bug is pre-existing on master 1f0b33b86. slang-test COMPARE_COMPUTE direct-SPIR-V legs compile with debug info, so `-g`-only bugs show up there but not in a plain `slangc` probe. The GLSL side of the same null literal is on [[wiki/concepts/slang-backends-glsl.md]] [GLSL PtrLit can carry a non-UserPointer IRPtrType (null groupshared pointer)](../learnings/1793338055305-glsl-ptrlit-can-carry-a-non-userpointer-irptrtype-.md).

## Copies of non-copyable opaque values

`__constref ParameterBlock<T>` (or any opaque type) gets temp-copied in `addArg`, because `tryGetAddress` returns Simple, not Ptr, for a global. `processGlobalParam` only handles `IRGlobalParam`, so the copy survives to emit and ICEs. This is the same family as #7455/#8002. Fix it in IR copy-elision; PR #8008's AST-lowering approach was rejected 3× ([#8002 constref ParameterBlock ICE: fix in IR copy-elision](../learnings/1784754145569-slang-8002-constref-parameterblock-opaque-ice-copi.md)). Returning `RayQuery<...>` by value miscompiles because the callee value-copies the handle into the return-dest, and a bare `b = a` fails the same way. It is the general non-copyable value-copy defect. Disassembling the output refuted a confident source-only hypothesis ([RayQuery return-by-value = opaque value-copy](../learnings/1784785541306-rayquery-return-by-value-miscompile-opaque-value-c.md)).

**RayQuery return by value (#12200, closes #12197).** The P1 symptom is an opaque handle returned by value that disconnects `OpRayQueryInitializeKHR` from `OpRayQueryProceedKHR` and ends in `VK_ERROR_DEVICE_LOST`. The fix landed as a scoped **NRVO** in `slang-lower-to-ir.cpp` — aliasing the named-return local to the return-destination out-param so the opaque handle builds in place, gated strictly to RayQuery/HitObject via `isNonCopyableOpaqueType` so it cannot regress the real by-value copy on DXIL. The 3-reviewer verdict was APPROVE_WITH_NITS / 0 bugs; the correctness crux (source-verified for a P1, not just relayed) is that NRVO elides only a provably-no-op whole-handle Load/Store layered on the pre-existing `maybeAddReturnDestinationParam` transform, with `findCommonReturnedLocalVar` bailing conservatively on any unrecognized statement ([PR #12200 RayQuery-return NRVO review — APPROVE_WITH_NITS, 0 bugs](../learnings/1784882737937-pr-12200-rayquery-return-nrvo-review-approve-with-.md)).

## Scalar, constant and index emit gaps

"Unhandled global inst: UIntPtr" is a genuine emit-layer gap and an exception to the "unhandled inst ⇒ producer bug" heuristic. Pointer-sized integers get their width only at emit (`getPointerSize(targetReq)*8`), and no pass lowers them. The constant path already grouped `PtrType`+`UIntPtrType`, so only the type-decl switch in `emitGlobalInst` lacked `case kIROp_UIntPtrType:`. The existing body works as-is. `IntPtr` is not symmetric: `isSignedType` omits it, which trips `getUnsignedTypeFromSignedType`'s assert, and the value path emits a 32-bit constant under a 64-bit type. It needs `isSignedType(IntPtr)=true`, a `getUnsignedTypeFromSignedType` case, and a value-path arm ([UIntPtr/IntPtr: type-decl gap + signedness inconsistency](../learnings/1790007665223-spir-v-uintptr-intptr-scalar-emit-type-decl-gap-si.md)).

**Pointer→integer casts need an unsigned result type; integer→pointer casts do not (#14087).** `OpConvertPtrToU`, like `OpUConvert`, requires an unsigned result. In SPIRV-Tools `source/val/validate_conversion.cpp`, `ValidateConvertPtrToU` (:406) requires `IsUnsignedIntScalarType` on the result, while `ValidateConvertUToPtr` (:513) requires only `IsIntScalarType` on the operand, so a signed `int64_t` operand validates. `emitCastPtrToInt` used the inst's own signed type, so `(int64_t)ptr` emitted `OpConvertPtrToU %long`. The fix pattern emits to `getUnsignedTypeFromSignedType(type)` and then `emitOpBitcast`, as `emitIntCast` already does (slang-emit-spirv.cpp). A pointer→signed-int fix (slang#14090) needs that step only in `emitCastPtrToInt`, not in `emitCastIntToPtr` [NVIDIA Vulkan driver runs invalid OpConvertPtrToU %long — a vk COMPARE_COMPUTE leg only catches it under SLANG_RUN_SPIRV_VALIDATION=1](../learnings/1793337282511-nvidia-vulkan-driver-runs-invalid-opconvertptrtou-.md), [spirv-val: OpConvertUToPtr accepts signed int operands; only OpConvertPtrToU needs an unsigned type](../learnings/1793338994790-spirv-val-opconvertutoptr-accepts-signed-int-opera.md). When you review a fix that pairs `isSignedType` with `getUnsignedTypeFromSignedType`, do not ask for a switch to `getIntTypeInfo().isSigned`: that classifies IntPtr as signed and trips the helper's `SLANG_RELEASE_ASSERT(isSignedType(type))` (slang-ir-util.cpp:3418) [spirv-val: OpConvertUToPtr accepts signed int operands; only OpConvertPtrToU needs an unsigned type](../learnings/1793338994790-spirv-val-opconvertutoptr-accepts-signed-int-opera.md). How to test such a bug when the GPU runs the invalid module anyway is on [[wiki/concepts/slang-backends-spirv-validation-testing-and-environment.md]].

**`double→bool` cast emits a 1-word `OpConstant` (#12019):** `emitFloatToIntCast`'s float→bool path calls `builder.getIntValue(fromType, 0)` with the *double* type, minting a `kIROp_IntLit` stamped with a float type; at emit `emitIntConstant` switches on the type, double hits `default:` → one 32-bit word, but a float64 `OpConstant` needs two → "says it has 4 words, found 5". Only double is structurally invalid (for float/half the 1-word path accidentally matches the IEEE bit pattern). Fix at the producing cast (`getFloatValue(fromType, 0.0)`, mirroring the correct bool→float sibling), not by special-casing `emitIntConstant` — an int-lit-with-float-type should never exist ([double→bool SPIR-V: getIntValue(floatType,0) mints int-lit with float type → 1-word OpConstant](../learnings/1783587817471-slang-12019-double-bool-spir-v-getintvalue-floatty.md)).

**64-bit buffer indexing bifurcates (#11967):** direct concrete-buffer subscript (`RWStructuredBuffer<int>[uint64_t idx]`) preserves `UInt64` to `OpAccessChain` and works, but the interface-constrained `IArray<T>`/`IRWArray<T>.__subscript(int index)` path (core.meta.slang, hard `int`) silently truncates a `uint64_t` index to 32-bit (front-end `warning E30081`). The fix is to widen the IArray/IRWArray subscript *requirement* to a generic `TIndex`, mirroring the buffer/Ptr subscripts — with the caveat that widening an interface requirement can force `Array`/`vector`/`matrix` conformances to re-satisfy. A >2^32-element execution test is impractical (>8 GB buffer), so the E2E guard is necessarily a codegen FileCheck for `OpTypeInt 64` on `OpAccessChain` ([64-bit indexing works on direct subscript but IArray/IRWArray truncates to 32-bit](../learnings/1783415716330-slang-64-bit-buffer-indexing-works-on-direct-subsc.md)).

**Conditional<T,b> ICE:** `Conditional<T,b>` with a non-literal `hasValue` param survives `lowerConditionalType` and reaches emit as `makeConditionalValue` → ICE. Root cause is an upstream producer (autodiff, dynamic dispatch, or higher-order params) leaking an unresolved generic value param ([Conditional&lt;T,b&gt; ICE: non-literal flag survives lowerConditionalType to spirv-emit](../learnings/1782485307814-conditional-lt-t-b-gt-ice-non-literal-flag-survive.md)).

## Legalize-time diagnostics and rejection predicates

**Diagnostic placement in legalize: the worklist runs before OpKill DCE.** In `legalizeIRForSPIRV` (`slang-ir-spirv-legalize.cpp`), the `legalizeSPIRV()` worklist runs BEFORE `removeUnreachableCodeAfterDiscardForOpKill` and `eliminateDeadCode`. So every diagnostic emitted inside that worklist also fires for code after an unconditional `discard` in the OpKill configuration (SPIR-V < 1.6, no demote extension). The live instance on master b9199bdaa is E55210 `abort-format-must-be-string-literal` from `processAbort`: `discard; doAbort(x>2?"a":"b");` at `-profile spirv_1_5 -capability abort` still reports E55210. The tension is that a diagnostic which renders a resource type name only renders it because it runs before `lowerBufferElementTypeToStorageType`; moving it after DCE prints `of type ''`, and an `IRUnreachable` block skip doesn't help. The principled fix is reachability, or capturing the type-name string early and deferring only the emit to a post-DCE step that drops entries DCE removed ([diagnostic placement: type-name vs dead-code](../learnings/1784747930488-diagnostic-pass-placement-tradeoff-type-name-rende.md)). The #12191 story is a cautionary one: it targeted an E55215 bindless-`DescriptorHandle` diagnostic that existed only on PR #12186's branch, and #12186 (8d5db2471) then merged "option a" (the kind-dependent handle representation above, no diagnostic) instead, so that E55215 never reached master and code 55215 now means the CUDA multisampled-texture diagnostic (#12671). The July triage also wrongly called E55210 "not a peer" by comparing subjects; the right test is pass placement (is it emitted in the same pre-DCE worklist?). When a follow-up issue targets a diagnostic that exists only on an open PR branch, read `gh pr diff` for it and re-check the merged diff later, because the shape can change before merge and make the issue moot ([worklist diagnostics fire before OpKill DCE; E55215 bindless never landed](../learnings/1790670161351-spir-v-legalize-worklist-diagnostics-fire-before-o.md)).

**Relaxing a rejection predicate.** PR #12195 (`-fvk-use-direct-resource-params`) gated on "any texture NOT rejected by GLSL" instead of "read-only texture". That silently admitted FEEDBACK/UNKNOWN access and, through `unwrapArray`, texture arrays. Enumerate the discriminator's full range ([direct-resource-param gate leaks feedback/unknown/array](../learnings/1784772370437-spir-v-direct-resource-param-gate-relaxing-isilleg.md)).

**A lowering-time "diagnostic" that is only a note lets compilation continue into a crash (`spirv_asm` `&` operand, #13804, TOT 62fb75f99).** In `spirv_asm`, `&x` on an operand with no address, such as a global resource `RWStructuredBuffer buf`, reports E29103 "unable to take the address of this address-of asm operand". E29103 is declared as a `standalone_note` (`slang-diagnostics.lua:1222`), so it adds no error. Lowering returns a null operand (`slang-lower-to-ir.cpp:5668-5670`) and compilation goes on: `-target spirv` segfaults and hlsl gives E99999. `tests/language-feature/spirv-asm/bad-addr.slang` does not catch this, because its asm block sits in a non-entry function that is never emitted. A diagnostic test for a lowering-time diagnostic must put the code in an emitted entry point. The same triage hit an emit gap: the direct SPIR-V backend cannot `OpDecorate` a global resource `OpVariable`. `$tex` in `spirv_asm` names the `OpLoad` result, because legalize inserts a load before the asm block (`slang-ir-spirv-legalize.cpp:386-405`), and `[[vk::ext_decorate]]` is unknown (E31000, no effect). For SPV_QCOM_image_processing a validated workaround goes through glslang, which adds the `WeightTextureQCOM`/`BlockMatchTextureQCOM` decorations itself: `__glsl_extension(GL_QCOM_image_processing) __target_intrinsic(glsl, "textureWeightedQCOM") float4 f(Sampler2D<float4>, float2, Sampler2DArray<float4>);` compiled with `-target spirv -emit-spirv-via-glsl -capability glsl_spirv_1_6` (`-profile spirv_1_6` alone yields SPIR-V 1.0 on the via-GLSL path). The first triage draft said "no workaround exists"; a codex review found both this workaround and the crash. Before claiming "no workaround" for a missing SPIR-V feature, try `-emit-spirv-via-glsl` with a GLSL intrinsic ([spirv_asm & operand E29103 is only a note → segfault; QCOM via GLSL](../learnings/1792566757199-spirv-asm-operand-e29103-is-only-a-note-segfault-q.md)).

The general mechanism: if a failure path emits only a `standalone_note` (or a warning), `getErrorCount()` stays 0, the front-end gate after `generateIR()` lets compilation continue, and the backend crashes on whatever placeholder the failing code returned; here SPIR-V segfaults in `buildEntryPointReferenceGraph` (slang-ir-call-graph.cpp:88). The fix (PR #13809) promotes E29103 to `err(...)`, which alone stops the crash, and replaces the null operand with `getPoison(getPtrType(T))` for IR hygiene. A note→error promotion makes previously-compiling invalid code fail when it sits in unused functions or non-SPIR-V `__target_switch` cases, so the PR was labeled `pr: breaking change`. Test notes: one DIAGNOSTIC_TEST CHECK line consumes one diagnostic, so write `^^^ error E29103` on a single line; run crash repros with `slang-test -use-test-server`, because the in-process run dumps core; and `tests/functional/*` fails unless ALL targets are built, since `--target slangc slang-test` does not build the `functional` std module ([a standalone_note diagnostic on a failure path lets codegen run on broken IR](../learnings/1792573873487-slang-a-standalone-note-diagnostic-on-a-failure-pa.md)).

**Builtin-var Flat gate (#12064).** Prove else-branch reachability from the callers' asserts. `getBuiltinGlobalVar` asserts a pointer type, so the non-pointer branch is reachable only for `SPIRVAsmOperandBuiltinVar` (always BuiltinInput). An `IRGlobalParam` CAN be non-pointer; only `IRGlobalVar` is always a pointer ([Flat gate reachability](../learnings/1783767618309-approver-challenger-spir-v-builtin-var-flat-gate-p.md)).

## Planning a new SPIR-V opcode

**SPV_KHR_abort as a terminator:** `OpAbortKHR` is a block terminator (like OpKill), so new SPIR-V extension intrinsics must be modeled as terminators, not printf-parallel — after emitting the terminator, block emission must stop and unreachable code must be removed ([When planning a new SPIR-V opcode, check terminator-ness — not just value-producing-ness](../learnings/1781039584587-when-planning-a-new-spir-v-opcode-check-terminator.md)). `abort<each T>(format, args...)` takes runtime variadic args, so its message is a runtime `OpCompositeConstruct` (built by `processAbort` via `emitMakeStruct`), not `OpConstantDataKHR`, and there is no `SPV_KHR_constant_data` dependency; the shipped #11542 conformance bug was the `OpExtension "SPV_KHR_shader_abort"` token, where the registry name for `AbortKHR` is `SPV_KHR_abort` ([CORRECTION: abort message is a runtime composite, not OpConstantDataKHR](../learnings/1782251874470-correction-abort-message-is-a-runtime-composite-ru.md)).
