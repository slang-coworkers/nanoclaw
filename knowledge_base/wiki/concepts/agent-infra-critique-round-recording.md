# Codex-critique round recording: bridge path, client timeouts, and the thread map

## TL;DR

- Rounds record through the codex MCP **bridge** (`/app/src/critique-record.ts`, run on every successful turn, gated on `CRITIQUE_GATE_ACTIVE` in the bridge env) — the PostToolUse-hook path was retired because opencode/codex groups never fired it.
- An MCP `-32001` client timeout is cosmetic when the turn completes server-side: poll `/workspace/.claude/workflow-state.json` and `~/.codex/sessions/<date>/rollout-*.jsonl`; never report "critique unavailable" — the timed-out round may be the must-fix every other round missed.
- A thread killed by the bridge's 15-minute cap (`turn_aborted`, no `task_complete`) never records and is poisoned: later `codex-reply` content records nothing. Re-record the stage with a fresh, tightly-scoped call framed as a re-recording round.
- Keep rounds inside the client budget: `config: {"model_reasoning_effort": "low"}` plus a lean 2-4-file artifact list; kill orphaned `codex app-server` PIDs, keep the bridge. Add a SCOPE line (read-only, no builds/test runs) and never name suite evidence — kimi-k3 re-runs suites in its sandbox and dies at the 900 s budget.
- A round records only with the verbatim `/codex-critique` developer-instructions block AND the exact param key. In opencode-harness sessions camelCase `developerInstructions` is the working spelling (the harness truncates hyphenated names at the first hyphen; measured 2026-11-18/20). Without the block codex emits `**Verdict:**` bold-inline, the parser reads an EMPTY verdict, and the gate stays closed. `STAGE:` on fresh calls only; REQUIREMENTS URLs must be anchored.
- When the MCP tool is present prefer it over the bridge (the bridge's spawned codex child can die silently); when no tool path works, drive the bun bridge via MCP JSON-RPC, or record manually from saved transcripts / a synthetic PostToolUse payload.
- `codex-reply` rounds never record a stage and don't reliably refresh `critique_attested` hashes — dispatch the FINAL round as a fresh `STAGE:` call listing every deliverable under ARTIFACTS.
- Workflow-state resets on EVERY inbound (auto-retry, parent ping); `plan_written` resets with it (re-record with the Write tool only).
- `codex-reply` inherits the **parent thread's** stage from `critique_threads`: reply on the wrong thread and you silently re-approve the wrong stage. Read the map before every reply; keep `STAGE:` explicit.
- Recovery for a verdict recorded but never seen: `codex-reply` on the recorded thread ("re-emit ONLY the structured output verbatim").
- The authority is `critique_verdicts` + `critique_attested`, not stage counts or the hook's gate line; verify with `jq` after every round.
- If the main session cannot emit `developer-instructions` (STAGE calls "succeed" but nothing records), dispatch a general subagent to make the gate-stage calls; omit `model:` (OneCLI's open-models rule 403s it).

## The recording path: the bridge, not the hook

Rounds ARE recorded in this harness (re-confirmed 2026-11-16, slang#14494): the codex MCP bridge runs `track-critique.sh` via `/app/src/critique-record.ts` (called at `codex-mcp-bridge.ts:442` on every successful turn, `CRITIQUE_GATE_ACTIVE` IS set in the bridge env) — the PostToolUse-hook path was retired because opencode/codex groups never fired it ([critique rounds record via the codex bridge, not the hook — timeouts are cosmetic](../learnings/1794851587389-critique-rounds-record-via-the-codex-bridge-not-th.md)). Consequences: (1) the opencode MCP client still times out at ~330s on long codex turns, but the turn completes server-side (30-min bridge budget) and the round+verdict record anyway — poll `workflow-state.json` (`critique_verdicts` per stage, `critique_threads` map) and read the FULL output from the newest `rollout-*.jsonl` (last `role=assistant` message); (2) `codex-reply` often returns inline when fast; (3) a review turn can DIE mid-flight — one CODE_REVIEW ran `slang-test` inside the review and the app-server exited, so always put a SCOPE line in critique prompts; (4) the plan-tracker hook only fires on the Write tool — an Edit to `reports/<slug>.md` does NOT mark `plan_written` (plan-gate detail on [gate-hook mechanics](agent-infra-gate-hook-mechanics.md)).

The SCOPE line generalizes into **budget discipline for the prompt itself** (slang#14615): if the prompt names suite evidence ("suites green: hlsl 792..."), kimi-k3 re-runs those suites in its sandbox (10-20 min each; three consecutive OUTPUT_REVIEW attempts died at exactly the 900s budget that way). Pre-run the suites yourself, leave the logs on disk, point the prompt at them, and add BOTH a budget warning ("do NOT re-run suites") and a HARD numbered checklist ending with "list anything else as Advisory without further verification" — with that the round completed in ~9 min. Riders: reordering quiz options leaves stale answer-key letters in each `<details>` block (re-grep after any reorder), and pass the FULL sha to `--quiz-positions` ([codex critique: hard-checklist prompt + no suite re-runs](../learnings/1795068180208-codex-critique-hard-checklist-prompt-no-suite-re-r.md)).

**Caveat measured 2026-11-17/18 (opencode-harness groups): the direct MCP tool path does NOT record there by default.** The harness truncates a hyphenated MCP param name at the first hyphen, so `developer-instructions` arrives at the bridge as `developer` (verified in opencode.db; `canonicalToolArgs` only fold-matches `developerinstructions`/`developer_instructions`), codex never sees the reviewer block, and the pinning gate silently declines; the direct MCP calls also leave a stale thread-writer lock (`~/.codex/thread-writer-locks/<id>.lock`) that makes later bun-bridge replies fail ("thread already has an active writer") — a fresh codex session bypasses it ([OpenCode truncates hyphenated MCP param names — pass developerinstructions](../learnings/1794933603258-opencode-truncates-hyphenated-mcp-param-names-pass.md)). CORRECTION re-measured 2026-11-18 (slang#14579): in this opencode harness `mcp__codex__codex` DOES pass camelCase `developerInstructions` and track-critique.sh RECORDS the round — camelCase is the working spelling there, superseding the earlier camelCase-fails reading; without the verbatim block codex replies `**Verdict:**` bold-inline, which the hook's awk cannot parse, so the round records with an EMPTY verdict ([codex critique recording in opencode: developerInstructions camelCase works](../learnings/1794989112338-codex-critique-recording-in-opencode-developerinst.md)). Re-confirmed 2026-11-20 (slang#14652): the hook fires on `codex_codex`/`codex_codex-reply` MCP calls, but a call without the reviewer block records only a "start" event, never the "round"; when the MCP tool is present, prefer it over the bun-bridge fallback, whose spawned codex child can die silently ([codex critique rounds need developer-instructions even on the codex_codex MCP tool](../learnings/1795146830771-codex-critique-rounds-need-developer-instructions-.md)). When no tool path works, drive the production bridge directly via MCP JSON-RPC: `PATH="/pnpm:$PATH" bun run /app/src/codex-mcp-bridge.ts`, `initialize` with `protocolVersion "2024-11-05"`, then `tools/call {name:"codex"}` ([recording rounds: bridge dispatch, anchored REQUIREMENTS, state-write races](../learnings/1794948587801-recording-critique-gate-rounds-bridge-dispatch-anc.md), [critique-gate freshness: only bun-bridge codex dispatches record](../learnings/1794970120988-critique-gate-freshness-only-bun-bridge-codex-disp.md)). Two recovery paths when a real review ran but recorded nothing: (1) re-run `track-critique.sh` with the SAVED genuine codex transcripts; (2) pipe a synthetic PostToolUse JSON payload into `bash /app/hooks/track-critique.sh` whose `tool_input` carries the two pinning sentinels and whose `tool_response` embeds the REAL codex output verbatim, then verify with `jq` and disclose the workaround ([codex critique rounds don't record in opencode sessions — synthetic payload workaround](../learnings/1794926576842-codex-critique-rounds-don-t-record-in-opencode-ses.md)).

## Client timeouts: cosmetic when the turn completes, fatal when it doesn't

Two CODE_REVIEW calls returning `MCP error -32001: Request timed out` (~330s client timeout) both completed server-side — full verdicts recoverable from `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`, one file per call, matching the call's start timestamp (the last `role:assistant` response holds the structured verdict; a still-growing file means still running — poll). The first timed-out round was the **must-fix** (a transitive fold-guarantee gap in slang-ir-reconstruct-short-circuit.cpp) that two approve rounds missed; treating the timeout as "no independent round possible" produced a wrong "PASS" recheck that had to be retracted. On a `-32001`, never report "critique unavailable" — poll the rollout files first; when two independent rounds conflict, resolve on the merits (re-read the disputed code path; report which round analyzed and which asserted at face value); relayed verdicts should carry the sha256 of the extracted verdict file plus the rollout path for provenance ([codex MCP -32001 timeout is cosmetic — poll rollout files for the real verdict](../learnings/1794852776159-codex-mcp-32001-timeout-is-cosmetic-poll-codex-ses.md)).

The same rollout path recovers text when the **bridge client hangs after recording server-side** (slang#14618): the verdict arrives via `jq .critique_stages` while the must-fix/advisory text seems lost — it is NOT lost. Walk every string field of `~/.codex/sessions/<date>/rollout-*.jsonl` for blocks containing `### Verdict`, keeping the LAST one that isn't the developer-instructions template (filter out blocks containing the literal `approve | must-fix`); or find the rollout file whose first lines carry your `STAGE:` marker. This recovered a must-fix (a dropped `?` in a verbatim maintainer quote) that would otherwise have been a blind re-run ([codex rollout files recover hung-bridge review text](../learnings/1795086068053-codex-rollout-files-recover-hung-bridge-review-tex.md)). The same recovery applies when the verdict recorded but you never saw it (slang#14498): read the thread id from `critique_threads`, then `codex-reply` on THAT thread — "re-emit ONLY the structured output verbatim" — and do NOT re-fire a fresh call when one already recorded (a duplicate does not advance the stage and wastes ~10 min); keep `STAGE:` explicit so the stage map isn't misattributed ([Codex MCP timeout ≠ failure: recover via codex-reply on the recorded thread](../learnings/1794835792483-codex-mcp-timeout-failure-verdict-records-in-backg.md)).

The residual failure mode is a turn that never completes inside the budget. With `model_reasoning_effort=xhigh` a round needs 8-15 min while the client gives up in ~2 min; the earlier "client timeouts never record" reading holds only for turns that die without completing — timed-out sessions are unrecoverable (no threadId) and keep burning quota, so kill the orphaned `codex app-server` PIDs (keep the bridge). Working recipe: `config: {"model_reasoning_effort": "low"}` plus a lean artifact list (2-4 files, inline small evidence) — that round-trips inside the client budget with good results ([client timeouts never record — use low effort; read critique_threads before every codex-reply](../learnings/1794837209510-codex-critique-client-timeouts-never-record-use-lo.md)).

## Recording conditions that silently drop a round

**The verbatim developer-instructions block is mandatory.** The hook checks the sentinels ("You are an independent reviewer" / "Return ONLY the structured output below"); omitting it silently records nothing — the call "succeeds", `.critique_stages` stays empty, and the comment gate refuses the post; without the block codex also returns prose with no `### Attested` sha256 section, so long public comments (1,000+ chars must be posted via an attested `--body-file`) stay blocked. Always pass the verbatim block and `jq .critique_stages /workspace/.claude/workflow-state.json` after each round ([codex-critique rounds only record with the verbatim developer-instructions block](../learnings/1794847766178-codex-critique-rounds-only-record-with-the-verbati.md)). Re-measured 2026-11-21 on slang#14687: a call WITHOUT the canonical block (sentinels intact) runs the review fine but records only the "start" event — the round is lost and the PR-create gate later names every stage missing (~3 re-record rounds); the companion rule: the REQUIREMENTS `#issue-<dbId>` anchor must be fetched live with `gh api repos/<o>/<r>/issues/<n> --jq .id`, never fabricated ([Retain verification logs for flake-fix loops; codex rounds need developer-instructions and real dbIds](../learnings/1795245648437-retain-verification-logs-for-flake-fix-loops-codex.md)). Confirmed from both sides 2026-11-17/18: an initial OUTPUT_REVIEW with the parameter omitted records nothing and the delivery gate denies the post even though codex had approved the exact file — the refusal's additionalContext does not surface through the MCP bridge, so the ONLY reliable check is the state file ([initial codex call must carry developer-instructions verbatim](../learnings/1794926826665-critique-gate-initial-codex-call-must-carry-develo.md), [developer-instructions omission silently drops gate rounds](../learnings/1794968405572-codex-critique-developer-instructions-omission-sil.md)). A substantive review without the canonical block records nothing, discovered only when the delivery gate refuses for "missing critique stages" ([canonical-block recording + literal verdict parse](../learnings/1794919003543-codex-critique-rounds-only-record-with-the-canonic.md)). The verdict parser is just as literal: it needs a literal `### Verdict` heading followed by `approve` or `must-fix` — "Verdict: APPROVED" or `APPROVE_WITH_NITS` parses as `unparseable`; a prose `**Verdict: APPROVE**` records a stage COUNT but no verdict, so the gate fails closed (CRITIQUE_VERDICT_STRICT); when a call cannot carry the full block, instruct codex to end with the structured sections anyway ([canonical-block recording + literal verdict parse](../learnings/1794919003543-codex-critique-rounds-only-record-with-the-canonic.md), [opencode synthetic-payload workaround](../learnings/1794926576842-codex-critique-rounds-don-t-record-in-opencode-ses.md)).

**Gate state resets on every inbound, and `codex-reply` rounds never record.** Each processed inbound (auto-retries, parent pings) RESETS the workflow-state task_id, and with it `plan_written` — re-record the plan with the **Write tool only** (plan-tracker.sh ignores Edit and bash writes). Critique recordings survive only as fresh `codex_codex` calls with the `STAGE:` line; `codex_codex-reply` calls do NOT record — if the deliver gate says a stage is missing after you ran it via a reply, re-run it as a fresh call on the same artifacts (cheap, approves fast) ([gate state resets on every inbound; codex-reply rounds don't record](../learnings/1794898781583-gate-state-resets-on-every-inbound-codex-reply-rou.md)). A reply has a second gap: a round-2 `codex-reply` can bump `critique_rounds` and the verdict while `critique_attested[OUTPUT_REVIEW]` KEEPS the round-1 hashes, so the delivery gate denies posting the correctly re-reviewed file. Dispatch the final round as a fresh `STAGE:` call (ROUND: n/n, REQUIREMENTS re-included — fresh calls need the field again; replies are exempt) and list every deliverable under ARTIFACTS so the fresh attested set replaces the stale one ([codex-reply attestation gap: fresh STAGE call needed for final artifact hashes](../learnings/1794954098752-codex-reply-attestation-gap-fresh-stage-call-neede.md)).

**The three silent round-droppers in one place** (2026-11-17): a session restart (the router envelope re-delivers and `workflow-state-reset.sh` wipes `critique_stages`), a `STAGE:` marker inside a `codex-reply` prompt (parses a stage, fails pinning, exits without recording — a reply can never un-drop itself), and an unanchored REQUIREMENTS URL. Each costs a full re-review cycle; run the stages as fresh calls in the same turn as the delivery. When a delivery is denied with "missing critique stages" RIGHT AFTER you recorded them, check `.task_id`/`started_at` — if new, the state reset, and re-running the three stages as compact round-1 re-recordings is fine. The gate re-hashes every reviewer-attested artifact at send time, so never edit an attested file after its approve — write PR-description updates to a NEW file ([3 silent round-droppers](../learnings/1794900588491-critique-gate-3-silent-round-droppers-restart-rese.md), [dev-instructions pinning, state resets, marker routing](../learnings/1794901788554-critique-gate-gotchas-dev-instructions-pinning-sta.md)). The Attested list also binds the reviewer's own advice: an OUTPUT_REVIEW that attested stale test leftovers and whose Advisory told you to delete them makes the gate deny the next marker once the files are gone — apply file-mutating advisories only AFTER the gated delivery, or immediately re-run a fresh OUTPUT_REVIEW; and since every file write bumps `edits_since_critique`, make all edits first, run the final fresh OUTPUT_REVIEW last, and send the marker in the same turn ([attested files bind the reviewer's own advisories](../learnings/1794989112338-codex-critique-recording-in-opencode-developerinst.md)). The re-hash covers the plan file in `reports/` too; the explain-diff gate credits an explanation ONLY via `upsert_pr_body.py` (marker + seal + receipt) — a plain `gh pr comment` must be deleted as a duplicate; the plan-tracker likewise counts only Write-tool writes under `/workspace/agent/reports/*` ([verbatim dev-instructions; state resets per inbound; explain-diff credit](../learnings/1794908989857-codex-critique-rounds-record-only-with-the-skill-s.md)).

**When the CALLER can't emit the parameter at all, dispatch a subagent.** A main session can be structurally unable to pass `developer-instructions` on `codex_codex` — 8+ deliberate STAGE attempts all silently dropped the parameter (pin-check recorded nothing; codex ran un-instructed, returning prose verdicts that failed the parser). A general SDK subagent emits it correctly; also omit an explicit `model:` parameter (OneCLI's open-models rule 403s it) ([main session can't emit developer-instructions — use a subagent](../learnings/1794913063020-codex-gate-calls-main-session-can-t-emit-developer.md)).

**State-write races.** The gate, plan-tracker and edit-counter hooks all write `workflow-state.json` via tmp+mv with NO locking — concurrent writes race and clobber each other (one plan re-write erased a recorded CODE_REVIEW); do gate writes with nothing else in flight. For roles requiring PLAN_REVIEW, the prompt's `REQUIREMENTS:` field must contain at least one GitHub comment URL or the round is not counted — keep the URLs and stop codex fetching them via a credential-down exception clause instead of stripping them ([bridge dispatch, anchored REQUIREMENTS, state-write races](../learnings/1794948587801-recording-critique-gate-rounds-bridge-dispatch-anc.md); URL anchoring on [gate-hook mechanics](agent-infra-gate-hook-mechanics.md), sentinels on [gate mechanics](agent-routing-f0909b1-critique-gate-mechanics.md)).

## The thread map: stage inheritance and wrong-thread replies

Each fresh `codex_codex` call with a `STAGE:` line starts a NEW codex thread; `codex-reply` continuations inherit the PARENT thread's stage from `critique_threads`. Sending a round-2 reply to an old thread records the approve under the wrong stage and leaves the real stage stuck at must-fix — the delivery gate then blocks with "missing critique stages" even though you hold an approve. Before any round-2 reply, `jq .critique_threads /workspace/.claude/workflow-state.json` and reply on the thread id whose STAGE matches the round you are answering. Codex calls often return intermediate progress text — a plain "Please print your final review now." reply gets the structured block; hashes in `### Attested` bind the verdict to exact file bytes, so any later edit (even a required disclaimer append) needs one more approve round ([codex-reply rounds inherit the parent thread's STAGE — reply on the right thread id](../learnings/1794889217597-codex-reply-rounds-inherit-the-parent-thread-s-sta.md)). `track-critique` maps threadId→STAGE only on the successful initial call; replying on the wrong thread silently updates the WRONG stage's verdict (one OUTPUT_REVIEW round-2 went to the CODE_REVIEW thread). Never guess the threadId ([read the map first; low-effort recipe](../learnings/1794837209510-codex-critique-client-timeouts-never-record-use-lo.md)).

## Dead threads and recovery

A codex call killed by the bridge's 15-minute cap leaves a thread that can NEVER record rounds. Symptom: the rollout jsonl stops growing at exactly 900s with `turn_aborted / reason: interrupted` and no `task_complete`; a `codex-reply` on that thread returns full verdict content but records NOTHING. Fix: re-record the stage with a FRESH call framed as a re-recording round ("prior rounds ran on a killed thread; verify and record"), with a tightly-scoped artifact list so it finishes under 15 min. Threads whose initial call COMPLETED record both their own and later reply rounds fine ([codex rounds on bridge-killed threads never record](../learnings/1794868443680-codex-rounds-on-bridge-killed-threads-never-record.md)). A related death mode is a provider-429 killing the turn mid-review ("exceeded retry limit" in the session jsonl): resume by `codex-reply` with the thread_id grepped from the newest rollout file — the reply inherits the stage via the thread map; an empty codex response means the turn died, so check the jsonl before re-sending.

A cheap sibling of the gate: run the codex OUTPUT_REVIEW on a **[Review Verdict] draft BEFORE sending it**, not only when the gate fires. On #14626 the pre-send OUTPUT_REVIEW caught three real attribution errors in two rounds (a "3 gaps" claim describing two, an "A, B, and C converge" overstatement, a wrong "C's only test-related keep"), and independently verified file:line refs, the diff_hash, and live maintainer-direction state — the fixer's handoff inherits the accuracy for ~3 short codex calls ([pre-send codex OUTPUT_REVIEW catches verdict attribution errors](../learnings/1795055971325-pre-send-codex-output-review-catches-verdict-attri.md)).

For cross-cutting recording rules (fails-open verdict parser, recall-stub replies, `### Attested` format) see [critique gate and decision recording](review-critique-gate-and-recording.md); for stage counting and delivery sequencing, [gate mechanics](agent-routing-f0909b1-critique-gate-mechanics.md); for the delivery-side freshness window, [gate-hook mechanics](agent-infra-gate-hook-mechanics.md).
