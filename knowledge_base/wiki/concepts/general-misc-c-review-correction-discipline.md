## TL;DR

Fixing what a reviewer *quoted* is not fixing the defect; answering an ask in prose is not making the change; and a caveat that reaches your report but not the code is invisible where it matters. These are all "the artifact a future reader opens is not the one you edited."

- **The unit of repair is the claim's DEFECT CLASS across the whole artifact, not the quoted sentence** — a reviewer cites the instance they read, not an enumeration.
- **A reply is not a change; a directive is not a question** — diff the *asks* against the *diff*, not against your sent messages.
- **A concession that doesn't reach the code isn't one** — grep the source comments near cited lines for the *resolved* version when your report concedes an open question.
- **Name a predicate after what it tests, not what you intend** — and expect to reintroduce this one rung up.
- **"I tried X and it regressed" is scoped to the conditions X ran under** — state them, or the note defends a weaker design for you later.
- **A tool's output describes the tool; the stored state describes the world** — round-trip through the published artifact.
- **A fixed byte-range tail / fixed window silently suppresses the alarm it monitors** — and fails hardest exactly when the alarm should fire; make correctness independent of the window constant.
- **A proposed fix can void a sibling PR's published negative control** — re-run the sibling's controls against your predicate.

## Repair the defect class, not the sentence

A reviewer flagged an overstated heading ("SAME ROOT as #8183"); it was rewritten and the old string verified gone (grep = 0). Round two returned **four** must-fixes — all sentences the *new* heading now contradicted (the mechanism paragraph still said "SHARED root," the conclusion still said "same-root claim is CORRECT," etc.). The artifact was *less* coherent after the fix. **When a review flags a claim, the unit of repair is the claim's DEFECT CLASS across the whole artifact** — grep the *concept*, not the deleted sentence (`grep -niE "same root|shared root|same cause"`), and check every claim of the same *kind* (unmeasured behaviour asserted as fact: `kills|fixes|converts|stops`). Deleting the flagged string produces a true green check whose *scope* was one sentence. Corollary: fixing a conclusion does not fix the numbers or sub-claims derived from it — including a **counterparty's** artifact built on the retracted claim, who won't know unless told. See [Fixing a flagged heading but not the body it now contradicts — sweep the defect class, not the sentence](wiki/learnings/1786039407112-fixing-a-flagged-heading-but-not-the-body-it-now-c.md).

## A reply is not a change; a directive is not a question

A draft PR sat 3 weeks with an **unimplemented maintainer directive** while every summary signal read "engaged." Four well-argued prose replies had been sent — good replies, which is exactly why nobody noticed *no code ever moved* (the diff was byte-identical to what the maintainer first objected to). **A reply is not a change** — answering a review ask in prose consumes the same "I dealt with that" slot in memory; diff the *asks* against the *diff*, not your sent messages. **A directive is not a question** ("we should have X and nothing else, unless there are stronger reasons") ends a negotiation — another round of reasons restarts it. Three summary signals hid it: `updatedAt` is not a code-change signal (it was an `AssignedEvent` — check `commits`); a review *count* is not an ask count (ten `COMMENTED` reviews with empty bodies wrapped one unresolved thread — pull `reviewThreads{isResolved}`); and a stale working tree can encode a design never shipped. Also: a narrowly-scoped dispatch ("rebase for CI") bounds what you *change*, not what you *check*; prefer merge over rebase on a PR with inline comments (rebase orphans anchored `file:line` review threads). See [A reply is not a change: prose engagement can hide an unimplemented maintainer directive for weeks](wiki/learnings/1786021634866-a-reply-is-not-a-change-prose-engagement-can-hide-.md).

## A concession must reach the code a future reader opens

A review-request message conceded at length that a bounds guard's correctness was unresolved — while the comment *at that guard* read "it correctly gets no varying attribute," documenting the question as settled design. **A concession that doesn't reach the code isn't a concession**: the comment is written during implementation (when you believe the shape is understood) and never revisited because it isn't part of the diff you re-read; the report gets the later, more careful pass. Whenever a report says "unresolved," "open question," "not verified," "I only demonstrated X," grep the source near the cited lines for confident normative words in comments ("correctly," "intentionally," "by design," "always," "safe to") and check each against what you proved. Related: don't assume a helper is single-purpose because you reached it from one path (`grep` the callers before writing direction-specific prose); a cited test can fail to exercise the thing it's cited for; carrying test results forward across a no-op delta is legitimate, labelling them as run at the new head is not. See [When you concede an open question in a report, grep the SOURCE for comments asserting the resolved version](wiki/learnings/1786031904395-when-you-concede-an-open-question-in-a-report-grep.md).

## Name a predicate for what it tests; scope a negative result

**Name a predicate after what it tests, not what you intend.** A guard widened from `== "sv_target"` to `.startsWith("sv_")` was named `isSystemValueSemantic` — but the file's actual classification is `startsWith("sv_") || startsWith("nv_")`, so the name promised `NV_` coverage the body didn't provide (renamed `hasSVPrefixSemantic`, narrowing stated in the doc comment). The insidious part: this had *already* been fixed once in the same change (`isSVTargetSemantic` → renamed when the test widened) and reintroduced one level up — because **the second instance looks like a better name, not a worse one** (an abstraction-level name reads as an improvement). Tell: if the name states a *category* and the body tests a prefix/suffix/single-member, the name is broader than the code. What turns the rename into a decision is verifying the exclusion is *safe* (any `NV_` semantic falls through to a zero-mask default branch, so none can reach the code) — put that reason in the comment. Adjacent: amending a commit 404s every permalink you pinned to the old SHA; and a claim whose truth depends on which revision the reader has checked out is not worth making. See [Name a predicate after what it tests, not what you intend — and expect to reintroduce this one rung up](wiki/learnings/1786032280928-name-a-predicate-after-what-it-tests-not-what-you-.md).

**"I tried X and it regressed" is scoped to the conditions X ran under.** A note said "key-based lookup FAILS here — regressed a test; positional works because ORDER is preserved," written off real measured evidence — but it omitted that key lookup was tried against a *stale, pre-flatten layout*. The correct scope was "key lookup cannot *substitute for* rebuilding the layout"; the note as written argued for the weaker design, and the peer proposing "rebuild + key lookup + assert" was right. **A negative result is a measurement of X under conditions C, and C is exactly what gets compressed away in a summary** — later, C no longer holds (often because your own fix changed it), and the note asserts something you never tested, with the authority of "I measured this." Write the conditions into the claim, not the prose around it; check whether your own fix invalidated the condition; when a peer contradicts a measured note, audit the note's scope before the peer's claim. See ["I tried X and it regressed" is scoped to the conditions X ran under — state them, or it defends a weaker design for you later](wiki/learnings/1786032453631-i-tried-x-and-it-regressed-is-scoped-to-the-condit.md).

## A proposed fix can void a sibling PR's negative control

A correct suggested fix (make `shouldRunSPIRVValidation` also return false on `EmbedDownstreamIR`) silently destroyed the evidence an in-flight PR used to prove it had *not* broken validation — the PR's published control (assert a precompile is still rejected under `SLANG_RUN_SPIRV_VALIDATION=1`) becomes the *expected outcome* under the proposed predicate (exit 255 + 1 error → exit 0 + 0 errors). **When triaging issue X whose fix touches a predicate a sibling PR Y depends on, grep Y's body for its controls and re-run them against X's predicate** — a control is evidence only while it can still fail, and the collision is invisible unless you look, because both changes are individually correct. Publish two bounds with such a finding: that your stand-in flag matches the *observed outcome only*, and that the claim is "this specific command stops discriminating," not "the control is meaningless." (Cheap discriminator hit in the same chain: `pulls/N` 404s for a number that exists only as an issue.) See [A proposed fix can void a sibling PR's published negative control - check the PR's own alarm signature before endorsing the fix](wiki/learnings/1786000287614-a-proposed-fix-can-void-a-sibling-pr-s-published-n.md).

## The tool's output describes the tool; the window is not correctness

**A tool's output describes the tool; the stored state describes the world.** Four failures in one chain: `gh run cancel` → "cancel submitted" (the *request* was accepted; it stayed `queued`); `ncl tasks update --series-id` printing help (wrong flag, silent no-op); a *local* copy of a PR body (what you meant to publish, not what's live); `append_learning` exposing no edit path (*your interface* has none — the files are `rw` to another actor). Every one fails toward "verified." Corollaries with teeth: a dead fallback is worse than no fallback because you stop watching; **a parse failure is not a negative result** (a verifier printing `(unparsed)` reads like "old wording absent ⇒ succeeded" — every check needs its FAILURE distinguishable from its NEGATIVE RESULT); a count is a symptom, a class filter is a discriminator (30 skipped jobs could be a docs filter, matrix exclusion, or priority yield — filter by *name* and find all skipped). Round-trip through the published artifact: extract what you emitted from where the consumer reads it and re-run the consumer's operation. See [A tool's output describes the tool; the stored state describes the world](wiki/learnings/1786055230856-a-tool-s-output-describes-the-tool-the-stored-stat.md).

**A fixed byte-range tail / fixed window silently suppresses the alarm it monitors.** `curl -r -2048 ... | grep '^{' | tail -1` returns nothing when the newest JSONL record exceeds the range — and record width *grows with CI activity*, which is exactly what the alarm watches, so the monitor reads *nothing* precisely when it should fire (measured 16% oversized when `jobs_queued > 30` vs 0.5% quiet — 34× relative risk). Widening the window (`-r -8192`) is **the same bug with a later trigger date**; the actual fix adds a **boundary test the truncated case fails** (`jq -e .` — a head-truncated fragment fails, a complete record passes), making the size constant a *throughput knob, not a correctness one*. Make absence loud and distinguish failure modes (`fetch_failed` / `empty_response` / `no_complete_line_in_range` carrying the too-small range). Verify against the failure fixture, not `bash -n`; the row that matters is "oversized AND alarm-worthy" — proving the alarm now fires on the input that used to suppress it. After fixing, **every past "quiet" reading is no information, not a negative observation.** `cmd | grep | tail` cannot fail (`tail` exits 0 on empty input); use `pipefail` or validate the captured value. See [A fixed byte-range tail silently suppresses the alarm it monitors — and fails hardest exactly when the alarm should fire](wiki/learnings/1786033599984-a-fixed-byte-range-tail-silently-suppresses-the-al.md) and [Fixing a truncation bug by widening the window is the same bug deferred — make correctness independent of the constant](wiki/learnings/1786034387161-fixing-a-truncation-bug-by-widening-the-window-is-.md).
