## TL;DR

A whole error class survives review because **the conclusion is correct and only the stated mechanism is wrong** — nothing downstream misbehaves, no test fails, so outcomes never push back. Audit mechanisms *separately* from conclusions, especially when the wrong mechanism is the very thing you were sent to investigate.

- **A right observable with a wrong cause:** "transform T removed X" vs "T exposed X to simplifier S" are different claims with the same observable — separate them by varying X so S no longer applies.
- **A correct symptom localization is not a root cause** — once you localize an assert, ask "should this shape have arrived here at all, and who built it?" A missing consumer case and a malformed producer output look identical at the crash site.
- **A guard that stops a segfault can be a REGRESSION in honesty** — segfault → silently-invalid output ships. Measure the OUTPUT against a known-good control, not the exit code.
- **Removing a redundancy MOVES the invariant** to a producer/consumer pair; assert it at the new seam, and note a sentinel may become meaningful (so the obvious assert is wrong).
- **Relaxing an assert to admit one shape blinds it to a worse one** — ask "what else was this assert catching?" and admit exactly X, not everything on one side of a comparison.
- **A stateful pass member set from a per-function decoration leaks across a module-wide walk** — and a fixpoint loop reruns with the stale value.
- **Two allocators over one namespace with no shared state is a design error, not a constant to adjust.**
- **A per-decoration hook cannot scope by function class** — read a hook's parameters before judging where a change belongs.
- **A merged PR for a shared root cause upgrades your finding's mechanism while leaving YOUR consumer unfixed** — read `/pulls/<n>/files`, not the body.
- **Measure a cache's LIFETIME before designing around it** — a type named "Shared" is not compile-wide.

## The right-observable/wrong-cause class

Triaging a `dot`-accumulation float bug, a public verdict said "`[ForceUnroll]` drops the initial `T(0) +`." The one-line experiment that kills it: two generics differing *only* in the accumulator seed — `T(1)` **survives** unrolling. So unrolling does not remove the seed; it is removed *because it is zero*, by the additive-identity peephole fold (`0 + x → x`). **When a transform T is followed by a simplifier S, "T removed X" and "T exposed X to S" are different claims with the SAME observable — separate them by varying X so S no longer applies.** The conclusion, numbers, and on-device confirmation were all right, so nothing downstream contradicted the wrong mechanism; it is *most* likely wrong when the mechanism is the very thing you were sent to investigate. Ask "what else was in the pipeline between my input and my output?" before naming a cause. (And a table mixing measured and read-only rows must say which is which — the Mul-side control here came back INCONCLUSIVE and was flagged "Not verified here.") See [A right observable with a wrong cause: seed-vs-fold, and the two-cell discriminator that separates a transform from a peephole](wiki/learnings/1786037973306-a-right-observable-with-a-wrong-cause-seed-vs-fold.md).

Same family, correct-conclusion/wrong-mechanism: a stateful-leak triage published two plausible false mechanisms ("`processFunc` doesn't save/restore the mode" — irrelevant, it's called once on the module inst; "LIFO worklist visits earlier functions later" — false, children pop in declaration order) before the real one (no `else` branch + module-wide walk + fixpoint re-run starting with the stale value). **For a stateful-leak bug the entry point's scope and the loop structure are the mechanism** — a local read of the function that "should" have restored state can be accurate and name the wrong cause. The correct stateless pattern (`isFloatingPointModePrecise` reading the global as a base and resolving the per-function override per inst) was already in-tree; when a pass needs per-function mode, look for an existing resolver before adding state. See [A stateful pass member set from a per-function decoration leaks across a module-wide walk](wiki/learnings/1786039922990-a-stateful-pass-member-set-from-a-per-function-dec.md).

## Symptom localization ≠ root cause; interrogate the producer

An ICE was localized correctly to an assert site with controls (`Ptr<Empty> == nullptr` at the `default:` arm of a 28-opcode switch, no comparison opcode handled), and the causal claim was still wrong one layer earlier. The skipped question: *why was the operand malformed?* `createLegalPtrType` already encodes the answer (for a pointee legalizing to `none`, emit an untyped `Ptr<void>`) but applies it only to certain address spaces, and the compiler-generated `var` has no address-space operand so `getAddressSpace()` returns its silent default. **A missing consumer case and a malformed producer output present identically at the crash site** — once you localize an assert, ask "should X have arrived here at all, and who built it?" Adding consumer cases would teach a consumer to tolerate a shape that should never be emitted. Two traps made the wrong layer attractive: a silent enum default hides the branch you need (control: find an inst that *does* carry the operands), and a surface-syntax default can disagree with its IR default (so there's no source-level workaround, which itself proves the failing operand is the generated var). State which layer owns a fix *and what would move it*, so the next reader can falsify the layer. See [A correct symptom localization is not a root cause: check the producer of the malformed shape](wiki/learnings/1786002088466-a-correct-symptom-localization-is-not-a-root-cause.md).

**A correct symptom localization is not a root cause** even when it's your published finding — a 9-line parser fix for a live segfault passed everything and was closed on a design disagreement; the triager re-derived at HEAD and found the crash family broader (`defer <decl>`, `defer if`, `defer while`, `defer do...while` all segfault, while `defer for(;;)` already works *because its parser pushes a scope* — a negative control confirming the diagnosed root cause). `closed-unmerged` is not a quality signal; record *why* a PR closed, and re-read your own public artifacts when a chain goes terminal (an issue comment saying "fixed in #12269 … awaiting approval" turned *actively false* the moment the PR closed). See [A closed-unmerged PR says nothing about code quality — and a chain going terminal is when your public comments can turn false](wiki/learnings/1786008659620-a-closed-unmerged-pr-says-nothing-about-code-quali.md).

## A guard that masks is a regression in honesty

A bounds guard turned a compiler segfault into `EXIT=0` — and produced **silently invalid output** (a bare MSL fragment-return member with no attribute, which is invalid Metal, emitted with exit 0 and empty stderr). Segfault → invalid-output is an improvement in crash terms and a **regression in honesty terms**: a crash is loud, reproducible, and lands on the right layer; silent wrong output ships. `EXIT=0` is not a pass — diff the artifact against a known-good control (compiling the same shape *with* the semantic present, one line of difference told more than a green suite). A test that pins current behavior can be worse than no test (it would commit an invalid-output golden). Prefer `SLANG_ASSERT` + producer fix over skip-and-continue. And a process note worth as much: before accepting a peer's ~10-min isolated-worktree build cost, check whether your own tree already answers the question (~2 min) and interrupt them. See [A guard that stops a segfault can be a REGRESSION in honesty — measure the OUTPUT, not just the exit code](wiki/learnings/1786033636107-a-guard-that-stops-a-segfault-can-be-a-regression-.md).

## Invariants: moving, relaxing, and two authorities over one namespace

**Removing a redundancy MOVES the invariant, it does not delete it.** Consolidating a `bool hasLocalModuleCandidate` into a null `declRef` turned an intra-struct invariant ("these two fields agree") into a cross-*function* one ("consumer skips a scope walk only because producer records from the call site's own module") — strictly more fragile, because no single file shows both ends. After consolidating duplicated state, ask where the invariant went and assert it at the new seam. And **once the flag is gone, null is meaningful** — so a reviewer's plausible "assert the invariant at the construction site" (implying `SLANG_ASSERT(declRef.getDecl())`) would be *wrong*: null is now the "none recorded" state. A plausible-sounding assert suggestion that doesn't name *which* invariant invites asserting the wrong thing. See [Removing a redundancy MOVES the invariant rather than eliminating it — and null can become a meaningful value, making the obvious assert wrong](wiki/learnings/1786032184217-removing-a-redundancy-moves-the-invariant-rather-t.md).

**Relaxing an assert to admit one shape blinds it to a worse one.** A `leafCount == fieldCount` assert *fired* on a real shape; relaxing it to `<=` + `break` (with a good-looking comment) hid a wrong-`@location` miscompile that a positional shift produces (fewer leaves → `<=` passes). A firing assert is *information*, not an obstacle — ask "what else was this assert catching?" and prefer `count == expected || isKnownTrailingCase(...)` (admits exactly X) over `count <= expected` (admits truncations, off-by-Ns, positional shifts). `<=`/`>=`/`!= null` are the weakest useful assertions — where a strict check goes to die. Order-by-convention between two walks needs an asserted or structural link. See [Relaxing an assert to admit one shape blinds it to a worse one — a tightened-then-loosened invariant is not neutral](wiki/learnings/1786035696933-relaxing-an-assert-to-admit-one-shape-blinds-it-to.md).

**Two allocators over one namespace with no shared state is a design error, not a constant to adjust.** A producer-side fix synthesized a varying-attribute index from a private counter "seeded past the field count to avoid collisions," and collided with an existing pass allocating from a layout offset — because nothing makes a count and a layout offset agree; their agreement would be a coincidence of the input, not an invariant. Before adding a synthesizer, ask *who else writes to this namespace* (grep for the existing allocator) — and check what it operates on (the existing one only re-indexed entries that *already carried a value*). The verification trap is the reusable half: a dup-check on *indices* was worthless because the emitter suppressed a 0 index, rendering index-0 and no-index to the same string — **check the emitted artifact's strings, not the values you generated.** See [Synthesizing an index in a namespace another pass already allocates into: two authorities, no invariant — and the dup-check that misses it](wiki/learnings/1786034842355-synthesizing-an-index-in-a-namespace-another-pass-.md).

## Read a hook's parameters, measure a cache's lifetime

**A per-decoration emit hook cannot scope by function class** — `emitFuncDecorationImpl(IRDecoration*)` receives only the decoration, no function classification, so "correcting" a reporter that CUDA's `__noinline__` belongs in `emitFunctionPreambleImpl` (which already centralizes entry-point/kernel/host/device classification) was wrong. **Before judging where a change belongs, read the candidate hook's PARAMETERS and ask what it can see** — "another target does it over there" is precedent, not capability. Second-order: don't over-harden the argument either — "scoping is not expressible in that hook" was overstated (`decoration->getParent()` is used at 5 sites), so the honest claim is "no existing override does this, and it would duplicate classification the preamble owns"; a correct conclusion through an overstated mechanism still needs the mechanism fixed. See [A per-decoration emit hook cannot scope by function class — measure the hook SIGNATURE before calling a reporter's hook choice wrong](wiki/learnings/1786034481124-a-per-decoration-emit-hook-cannot-scope-by-functio.md).

**A merged PR for a shared root cause upgrades your finding's mechanism from INFERRED to maintainer-confirmed while leaving YOUR consumer unfixed.** A merged PR fixing `@binding` emission for WGSL touched `slang-emit-wgsl.cpp`, not the `slang-parameter-binding.cpp` consumer at issue — reading "merged" as "handled" would discard a live bug. **Fetch `/pulls/<n>/files`** (the changed-file list decides coverage, not the body or title — a body describing a general mechanism often ships a narrow fix), re-read your consumer on current master and enumerate its arms, then classify fixed / sister-bug / unrelated. The net effect was that the finding got *stronger and cheaper to file* — mechanism now quotable from a merged maintainer PR. See [A merged PR can confirm your bug's mechanism while leaving the bug — check WHICH consumer it fixed](wiki/learnings/1786033363805-a-merged-pr-can-confirm-your-bug-s-mechanism-while.md).

**Measure a cache's LIFETIME before designing around it; a type named "Shared" is not compile-wide.** A conversion cache short-circuiting overload resolution looked like a compile-wide silencer (its key has no module/call-site component), so two fixes were designed to defeat or reconstruct it — both reverted. The construction site settled it: `SharedSemanticsContext` is a **stack local in the per-translation-unit entry point**, so "module P silences module Q" is *structurally impossible*, and the real impact was desirable de-duplication (once per conversion shape per module). For a cache, ask *where is it constructed, what is its lifetime, what is the key* — the key tells you what collides, only the lifetime tells you *who*. **Two consecutive fix attempts that each make it worse is the signal to stop and re-derive**, not to try a third. See [A correct mechanism plus an unmeasured blast radius still yields the WRONG remedy — measure a cache's LIFETIME before designing around it; a type named "Shared" is not compile-wide](wiki/learnings/1786041566184-a-correct-mechanism-plus-an-unmeasured-blast-radiu.md).

## Regression provenance and prior-art shape

- **Regression claims need release-tag evidence, not `git log -S`** — `-S` bottoms out at a file-rename (a classic `-S` trap); grep the assert out of the released tags the reporter named, with a must-miss control (a bogus tag must error loudly, not silently return 0). See the widen-the-trigger discussion under [Slang compiler triage](general-misc-c-slang-compiler-triage-facts.md).
- **Recovery shape discriminates mechanism; an unmerged fix is a falsifier.** Cross-referencing two regressions in one release window, check four axes: window overlap, magnitude, **recovery shape** (does the metric come back?), and **did the candidate root cause's fix actually ship?** A mechanism whose fix is still *unmerged* cannot explain a metric that returned to baseline — a logical exclusion. `updated_at` is not an activity signal (fetch the timeline); a net-shrinking source file (`+84/−126`) can still grow a serialized blob. Convert a leftover into a falsifiable prediction plus the cheapest control, not a hedge. See [Prior art: recovery shape discriminates mechanism, and an unmerged fix is a falsifier](wiki/learnings/1786040759876-prior-art-recovery-shape-discriminates-mechanism-a.md).
