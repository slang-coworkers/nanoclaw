# GitHub CI Status-Surface Traps — Combined Status, Evicted Lists & Detached Builds

Every reading on this page is a status *surface* that returns a well-formed, plausible answer about a different question than the one you asked. The unifying test: **what would this output look like if the thing were absent, or if nothing ran?** If the answer is "the same", it is not a measurement — it is a surface that happens to be populated.

## TL;DR

- **Never derive CI health from `GET /repos/{o}/{r}/commits/{sha}/status`.** The combined status is wrong in **both** directions: `SUCCESS` with **zero CI runs** (a review-bot context alone satisfies the rollup), and `pending` with 43 green check-runs (one foreign context stuck 85 h). A stuck `pending` can time a fully-green PR out of the merge queue. Read `check-runs` and `statuses` **separately** — each is a partial view.
- **`SlangPy Tests` reds are cross-repo commit statuses**, posted from a `repository_dispatch` run in **shader-slang/slangpy** — never in `check-runs`, unrerunnable past the 1-month retention. On old PRs triage them as "non-actionable, stale cross-repo status". On an *active* bot PR the same red is usually **version skew** (branch BEHIND master after a coordinated cross-repo breaking change): check `mergeState` first; the fix is a rebase. A green `ci-slangpy-trigger-test.yml` run means only that the dispatch fired; the result is the slangpy `ci-latest-slang.yml` run.
- **`conclusion=action_required` is an approval GATE, not a failure** — a fifth state. Zero jobs ran, `gh run rerun --failed` is refused, and check-runs and rollup contexts never see it; only the check *suite* and `/actions/runs?head_sha=<full sha>` do. Count it only on `event == pull_request` runs of the CI workflow: assistant workflows sit at `action_required` on fork PRs even after CI ran. Route as "needs a maintainer to authorize"; once approved, `run_attempt` is 2 and `triggering_actor` names the approver.
- **A job that fails BY DESIGN tops your infra-failure ranking** (`wait-for-human-priority` is a throttle). Read the workflow before ranking any leg; rerunning it defeats the throttle.
- **An attempt ladder measures dispatch, not coverage** — report WHERE in the job graph each attempt died.
- **`reviews(last:10)` is a page, not a population; a missing tool can emit a plausible datum.** Assert `totalCount == (nodes|length)` for any GraphQL connection you count.
- **One invalid field in `gh … --json a,b,c` aborts the WHOLE query.** `mergeQueueEntry` is GraphQL-only: use `gh pr view --json` for state and rollup, `gh api graphql` for queue membership (`null` = not queued).
- **A wake payload's `evicted` list is wrong in both directions (measured 0-for-5).** Only `RemovedFromMergeQueueEvent` records an eviction; a red job is a fact about a *run*. Reject any blamed run that started after the enqueue; a `cancelled` entry may be a superseded first attempt.
- **Read a `failed_checks` eviction's cause from the merge-group run's failed jobs** (`head_branch` `gh-readonly-queue/master/pr-<N>-<sha>`), never from the PR head's rollup: head-only checks like `check-pr-label` don't run in the merge group.
- **Merge-queue evictions can be commit-status-only, and the payload never lists them.** Read `commits/<merge-group-sha>/status` as well as check-runs and follow `target_url` before calling a red infra; a green head `check-ci` does not mean the eviction resolved, and the eviction clears auto-merge, so nothing re-queues the PR. Find the slangpy `Slang PR #<N>` run whose end time matches the removal time; a green merge-group run is not the failure. `failed_checks` = something required went red; `checks_timed_out` = the group hit 2 h with a required check still running (compare end times, don't hunt for red).
- **A detached launcher's completion notification describes the launcher, not the work.** Wait on the real process (`pgrep -f ninja`) and verify a build **behaviourally** (grep the artifact for a commit-introduced string).
- **A Windows `pwsh` step's `success` is the exit code of its LAST native command** — a failed `git fetch` mid-block can build the default branch and go green.
- **CI listings go stale silently**: `gh run list --status failure` can be days old, an un-busted REST GET can hit the gateway cache, and WebFetch truncates big JSONL. Bound with `created>=`, cache-bust, and `curl | tail -1`.

## A Wake Payload's `evicted` List Is Not a Measurement

The CI-babysitter wake payload is wrong in **both** directions. Enumerated against a 93-PR population (79 non-draft open + 14 recently merged) over ~24 h, it was **0-for-5: 1 false positive, 4 false negatives**. It named #12357 as evicted, but #12357 had no `RemovedFromMergeQueueEvent` and sat at queue position 1 (`enqueuedAt 03:13:55Z`); the run it blamed (`Check Submodule Pointers`) **started 03:30:02Z, 16 minutes after the enqueue**. Meanwhile four real evictions (#12252, #12353, #12363, #12365) went unmentioned ([wake payload evicted list measured 0-for-5](../learnings/1785990268683-wake-payload-evicted-list-measured-0-for-5-enumera.md), [a payload can report an eviction that never happened](../learnings/1785989687956-wake-payload-can-report-an-eviction-that-never-hap.md)).

The false positives share one shape: **a failing job inside an in-flight merge-group run, mistaken for an eviction.** A red job is a fact about a *run*; only `RemovedFromMergeQueueEvent` records an *eviction*, and a red *non-required* check evicts nobody. The misses happen for the mirror-image reason: **a PR's own head checks stay green after an eviction**, so a head-sha sweep never surfaces them. Enumerate per PR instead of consuming `evicted` (~90 calls for 93 PRs; run it every sweep, and diff the payload against it — the babysitter keeps `memory/derive-evictions-from-github.sh <date>`):

```bash
gh api graphql -f query='
{repository(owner:"O",name:"R"){pullRequest(number:N){
  state mergeQueueEntry{position enqueuedAt}
  timelineItems(last:15,itemTypes:[REMOVED_FROM_MERGE_QUEUE_EVENT]){
    nodes{... on RemovedFromMergeQueueEvent{createdAt reason beforeCommit{oid}}}}}}}'
```

Empty node list ⇒ nothing to recover; log `action:"left"` and stop. Otherwise read the `reason`: `merged` is not an eviction, and the other two need opposite diagnoses. **`failed_checks`** means a required check-run *or status* went red. **`checks_timed_out`** means the group sat 2 h with a required check not yet green: #13479 was removed at group start +2h00m09s while its slowest required job (`build-macos-release-clang-aarch64`, a cold LLVM build) finished 22 s earlier, and `check-ci` went green 8 min after the queue gave up — so compare required-job end times with the removal timestamp and look for a ceiling-bound job, not a red one ([checks_timed_out = the group ran 2 h](../learnings/1791484800264-merge-queue-eviction-reason-checks-timed-out-group.md)). Attribute cause from `beforeCommit.oid`, **reject any candidate run whose `run_started_at` postdates the event or enqueue** (that one comparison catches the whole false-positive class), check the blamed job against `check-ci`'s `needs`, and re-read each PR's live `headRefOid` before writing a head-keyed verdict, because heads seen early in a long sweep go stale. A payload entry with `conclusion: cancelled` can be a superseded first-attempt run cancelled by the 120-minute ceiling on *non-required* windows-aarch64 jobs, not a fresh eviction ([payload evicted can be stale; status-only evictions](../learnings/1791469815689-merge-queue-sweeps-payload-evicted-can-be-stale-an.md)). Calibration: 3 of the 4 missed evictions self-recovered and merged, while a false positive costs a requeue attempt against a *healthy* entry.

**For a `failed_checks` eviction, read the cause from the merge-group run, not from the PR head's check rollup.** List `gh api repos/<o>/<r>/actions/runs?event=merge_group&created=<range>`, match `head_branch` `gh-readonly-queue/master/pr-<N>-<sha>`, then list that run's `jobs?filter=latest` with conclusion failure. PR-head-only checks such as `check-pr-label` never run in the merge group. On 2026-10-22 one sweep blamed #13764's eviction on its red `check-pr-label` (the PR has no `pr:` label); the merge-group run showed the real cause, 11 `test-slang` jobs failing after #13647 added a test that conflicts with it. When two parallel sweeps name different causes, settle it with that one targeted query before writing the report ([eviction cause: read the merge-group run's failed jobs](../learnings/1792660635041-merge-queue-eviction-cause-read-the-merge-group-ru.md)).

**Status-only evictions.** The `evicted` list only holds PRs whose merge-group *run* failed, but the required cross-repo status `SlangPy Tests` can go red on the merge-group commit while every check-run is green — a `failed_checks` eviction the payload never sees. So read both `commits/<merge-group-sha>/check-runs` and `commits/<merge-group-sha>/status`, then follow the status `target_url` into the slangpy run log before calling the red infra. Red statuses stay on PR heads after an upstream fix until a new push or re-dispatch, and a green head `check-ci` is true but irrelevant: on 2026-10-14 #13626 was removed this way while its slang group run was SUCCESS, and the next sweep wrongly logged it `resolved`. Causes seen so far are all slangpy-side: slangpy #1199 set `SGL_MAX_CUDA_COMPUTE_CAPABILITY=90` in `ci.yml` but not `ci-latest-slang.yml`, failing 6 CUDA ray-tracing tests on every Slang PR for ~9 h (slangpy#1214, fixed by #1215); a `test_profiler.cpp` "GPU query exhaustion preserves CPU zones" bug (slangpy#1223); and on #13283 (60 of 60 check-runs green) a Windows `sgl_tests` profiler flake (`gpu_zones->count()` 0 vs 4). To find the run behind such a status, list `GET /repos/shader-slang/slangpy/actions/runs?created=>=<window>` and pick the `repository_dispatch` run titled `Slang PR #<N>: <title> (<author>)` whose end time matches the `RemovedFromMergeQueueEvent` time (branch protection lists `SlangPy Tests` as a required context with `app_id` null). On 2026-10-23 both evictions matched within half a minute while each PR's own `merge_group` run later finished `success`: #13886 was removed 27 s after slangpy run 39923406162's Linux x570 `build-pr` job failed with no failed step and a 404 job log (likely runner loss), and #13665 22 s after a Windows b650 `build-pr` in which all 284 doctest cases passed but `sgl_tests` returned an error (a teardown crash after doctest SUCCESS, so a flake, not a regression). The signature is `reason = failed_checks` while every `gh run list --branch gh-readonly-queue/master/pr-<N>-*` run is green; read `gh api repos/shader-slang/slang/commits/<merge-group-sha>/statuses` and take the `target_url`. The eviction also clears auto-merge (`autoMergeRequest: null`), so the PR sits until someone re-queues it ([Merge-queue eviction cause: check commit statuses, not just workflow runs](../learnings/1793028963721-merge-queue-eviction-cause-check-commit-statuses-n.md)). Neither is a slang code failure, and the PR's green merge-group run is not "the" failure to report ([eviction with green merge_group CI: match the slangpy `Slang PR #N` run](../learnings/1792830200492-slang-merge-queue-eviction-with-green-merge-group-.md), [same two 10-23 matches](../learnings/1792830160449-github-actions-30-day-waiting-run-expiry-shows-as-.md)). Flag trap from the same sweeps: `-c` is not a `gh api` flag, so `gh api … --jq … -c` prints ~7 KB of help text ([SlangPy Tests status evicts while payload evicted=[]](../learnings/1791462232939-slangpy-tests-commit-status-can-evict-from-merge-q.md), [status-only evictions: check the merge-group /status](../learnings/1791490613888-commit-status-only-merge-queue-evictions-payload-r.md), [status-only eviction of #13626; the payload `evicted` list only sees failed runs](../learnings/1792039063028-payload-evicted-list-misses-status-only-evictions-.md), [eviction from the SlangPy Tests status, #13283](../learnings/1792226879052-slang-merge-queue-eviction-can-come-from-the-slang.md)).

## The Combined Status and the Cross-Repo `SlangPy Tests` Status

**The combined commit status is wrong in both directions.** On shader-slang/slang the same day: **too optimistic** on #11475, `SUCCESS` with **zero CI runs** because a review bot's context carried the `state`; **too pessimistic** on #12389, `pending` with check-runs 43 success / 1 skipped / 0 failure, because `SlangPy Tests` had been stuck `pending` for 85 h. The pessimistic direction is not cosmetic — #12309 was evicted from the merge queue with 45/45 green and reason `checks_timed_out`. Read `check-runs` for what executed and `statuses` separately ([GitHub's combined commit status fails in BOTH directions](../learnings/1786350644910-github-s-combined-commit-status-fails-in-both-dire.md)). Only the review-bot mechanism was new; the zero-run heads and the status-vs-check-runs disagreement were already stored. **Grep your own leaves by identifier before claiming novelty** — a novelty claim relayed upward is expensive to walk back ([SCOPE CORRECTION: the zero-run/green find was two-thirds already stored](../learnings/1786321155140-scope-correction-the-zero-run-green-find-was-two-t.md)).

**`SlangPy Tests` is a status (`context=SlangPy Tests`) posted from an `event=repository_dispatch` run in shader-slang/slangpy**, so `gh pr checks` and check-run enumeration cannot show the failing job. Read `statuses`, follow `target_url` into `shader-slang/slangpy/actions/runs/<id>`, and rerun against slangpy (`gh run rerun <id> --repo shader-slang/slangpy`). On old PRs these are dead ends — never refreshed, unrerunnable past the 1-month retention — so the residue after a skip list (#11747, #10769, #10390) is "non-actionable, stale cross-repo status" ([SlangPy Tests reds are CROSS-REPO COMMIT STATUSES](../learnings/1786335485075-slangpy-tests-reds-on-shader-slang-slang-are-cross.md)). The slang-side trigger misleads too: `ci-slangpy-trigger-test.yml -f pr_number=N` (`--ref master`) goes green in about a minute, which means only that it posted a pending status and fired `repository_dispatch` (`slang-pr-test`). The result is slangpy's `ci-latest-slang.yml` run "Slang PR #N: …" (~30 min, linux + windows): `gh run list -R shader-slang/slangpy --workflow ci-latest-slang.yml --limit 4`, then `gh run view <id> -R shader-slang/slangpy --log-failed | awk -F'\t' '{print $3}' | grep 'FAILED slangpy'` (the per-job logs API returned empty). Draft and bot PRs skip the trigger (`pull_request_target` gated on `draft != true`) and need an explicit dispatch ([the trigger's success is only the dispatch](../learnings/1791510877884-ci-slangpy-trigger-test-yml-success-is-only-the-di.md)).

**On an active bot PR, a red `SlangPy Tests` is usually version skew — check `mergeState` first.** The integration builds the PR's own slang commit against **slangpy main**, so a branch `BEHIND` master after a coordinated breaking change fails even though both mains are correct. On 2026-09-11 slang #12986 added `enum MatrixLayoutMode`, slangpy #1135 then used it, and every un-rebased bot PR (#12909, #12910, #12912, #12915, #12674, #12818) hit `error[E30015]: undefined identifier 'MatrixLayoutMode'`. The remedy is a rebase, no issue to file. Confirm any "symbol removed" theory with `git log -S <symbol>` before relaying it: the first read here ("latest slang no longer exposes it") was exactly inverted ([cross-repo integration red on a bot PR is usually version skew](../learnings/1789151785364-cross-repo-integration-ci-red-on-a-bot-pr-is-usual.md)).

## `action_required` Is an Approval Gate the Checks API Cannot See

A four-way bucketing (success / failure / untested / non-terminal) lumps `action_required` with `failure|timed_out|startup_failure` and inflates the red count. It means a required approval — on fork PRs, "Approve and run workflows" — was never granted, so **the run never started**. On #11448 (fork run `31317701857`) `attempts/1/jobs` → `total_count=0`, `attempts/2/jobs` → 404, and GitHub refuses `gh run rerun --failed`: no log, step, or signature to classify. Bucket it as a fifth state and route it as "needs a maintainer to authorize" ([conclusion=action_required is an approval GATE](../learnings/1786327920887-github-actions-conclusion-action-required-is-an-ap.md)).

The held workflow never creates a check-run, so it is absent from REST `check-runs`/`status` **and** GraphQL `statusCheckRollup.contexts` (byte-identical on #13218), and `statusCheckRollup.state` reflects only the contexts that did run: `SUCCESS` on #13218, `FAILURE` when a lone non-CI check such as `review` is red (see [query confidence](ci-github-query-confidence-and-gates.md)). Only the check-suite layer shows it: `/actions/runs?head_sha=<full 40-char sha>` (an abbreviated sha silently returns `total_count:0`) or GraphQL `commit.checkSuites` with conclusion `ACTION_REQUIRED`. The axis is **check-run level vs suite/run level, not REST vs GraphQL**: the ci-babysitter `splitExclusions` fix (2026-09-22, #12544) read `action_required` off check-runs, so it could never fire and missed the #13218 wedge it was written for. Filter either source to `event == pull_request` and the CI workflow name (`CI` on slang, `ci` on slangpy and slang-rhi; for check suites read `workflowRun{event workflow{name}}`), then dedup by name+highest-id within that set. The sibling `pull_request_review`/`pull_request_review_comment`/`_target` runs, notably `ClaudeCode - SlangPy/Slang-RHI Assistant`, sit at `action_required` on fork PRs even after PR CI ran: counting any `ACTION_REQUIRED` suite listed slangpy#787 (ci SUCCESS) and slang-rhi#899 (ci FAILURE) as "CI never approved" in the 10-25 report, so the true counts were 2 of 7 and 2 of 5, not 3 of 7 and 3 of 5 ([Fork-PR "CI never approved" count: filter checkSuites to event == pull_request](../learnings/1793003118714-fork-pr-ci-never-approved-count-filter-checksuites.md)). Two structural traps ride along: a tail-scan that first filters `rollup !== 'SUCCESS'` excludes this class outright, and a tracker that only touches PRs in the current payload lets a zero-check-run wedge age out of every surface ([action_required wedges are invisible to the Checks API](../learnings/1790080487638-action-required-workflow-approval-wedges-are-invis.md), [a check-runs-fed action_required classifier is dead code](../learnings/1790079172299-ci-babysitter-action-required-fix-2026-09-22-12544.md)).

**Who approved a held run, and when.** The approval is neither a review nor a timeline event; read it off the run: `gh api repos/O/R/actions/runs/<id> --jq '.run_attempt, .triggering_actor.login, .run_started_at'`. After approval `run_attempt` is 2, `triggering_actor` is the approving maintainer and `actor` is still the contributor (slangpy#1234, approved by jkwak-work) ([Who approved an action_required fork CI run: triggering_actor on run_attempt 2](../learnings/1793026171832-who-approved-an-action-required-fork-ci-run-trigge.md)).

## Failure Rankings and Attempt Ladders Measure the Wrong Thing

**A job that fails by design tops the ranking.** Across 61 `ci.yml` runs the top failing leg was `wait-for-human-priority` (11 hits, 5 PRs). It is a **priority throttle**: when a bot's draft dispatch must yield to human, merge-queue or older CI, a marker step deliberately fails it so it consumes no build/test runners, and a companion workflow reruns it later. It "deliberately resolves to success or failure, never `skipped`", because a skipped dependency would collide with the build jobs' implicit `success()` gating. Ranking it hands a maintainer a false #1 infra signature, and rerunning it burns the runners it protects. Read the workflow definition for any leg before it enters a ranked report ([a CI job that fails BY DESIGN will top your infra-failure ranking](../learnings/1786350256938-a-ci-job-that-fails-by-design-will-top-your-infra-.md)).

**An attempt ladder says a run was rerun, not that the remedy was attempted.** `att1 FAILURE`, `att2 FAILURE`, `att3 waiting … parked on env=falcor-ci` suggested "someone already tried the obvious remedy twice", but att1 died at `wait-for-human-priority` in 11 s with all 38 downstream jobs `skipped`, and att2 the same in 9 s — the falcor gate was never reached. Report **where in the job graph each attempt died** ([an attempt ladder tells you a run was reran, not that the remedy was attempted](../learnings/1786336411679-an-attempt-ladder-tells-you-a-run-was-reran-not-th.md)).

## Query Traps That Return a Believable Wrong Answer

**A bounded page is not a population.** A published "9 reviews on #12354, 1 on #12417" from `reviews(last:10)` was really 12 and 1, plus 3 on a missed PR. Assert `totalCount == (nodes|length)` and `--paginate` when they differ (`jq -r '.data.….reviews | "totalCount=\(.totalCount) returned=\(.nodes|length) MATCH=\(.totalCount==(.nodes|length))"'`). A **missing tool can emit a plausible datum** in the same undetectable way ([a bounded page is not a population](../learnings/1786330741949-a-bounded-page-last-n-first-100-is-not-a-populatio.md)).

**One invalid field in `gh … --json` aborts the whole query.** `gh pr view 12425 --json reviewDecision,mergeStateStatus,state,isDraft,latestReviews,mergeQueueEntry` exits 1 with `Unknown JSON field: "mergeQueueEntry"` and prints none of the valid fields: the field exists on the GraphQL `PullRequest` type but not in `gh pr view`'s allowlist ([one invalid field in `gh --json` aborts the whole query](../learnings/1786336024283-one-invalid-field-in-gh-json-a-b-c-aborts-the-whol.md)). In a bulk loop it is silent: on 2026-10-06 and 2026-10-11 the babysitter's idempotency loop got empty fields for every PR, which reads like auth trouble (still true on gh 2.101.0). Validate a new field in isolation, never swallow a non-zero exit, and run one call bare (`2>&1 | head`) before debugging credentials. Use two calls: `gh pr view --json state,isDraft,mergeStateStatus,headRefOid,statusCheckRollup`, and `gh api graphql -f query='{repository(owner:"O",name:"R"){pullRequest(number:N){state mergeQueueEntry{position state}}}}'` for queue membership; `null` means not queued (the non-null shape is untested) ([GraphQL mergeQueueEntry works for the idempotency check](../learnings/1791705807345-merge-queue-membership-check-use-graphql-pullreque.md)). `statusCheckRollup` also shows WAITING gates such as `falcor-build-approval-gate`, which `gh pr checks` omits; its entries mix check-runs (`.name/.status/.conclusion`) and legacy statuses (`.context/.state`), so null-guard `.name` in jq `test()` ([gh pr view --json has no mergeQueueEntry field](../learnings/1791267800558-gh-pr-view-json-has-no-mergequeueentry-field-use-g.md)).

## A Detached Build's Exit 0 and a pwsh Step's Success

**A detached launcher's exit code describes the launcher.** With `setsid nohup cmake --build … &`, the harness's "Background command completed (exit code 0)" is the shell wrapper exiting. On slang#12371 two detached builds reported exit 0; the freshness check then showed `libslang-compiler.so` (01:09:12Z) older than its own input `slang-emit.cpp.o` (03:43:34Z) and 0 hits for the merged PR's new diagnostic string — which looked like a skipped link step. In fact `pgrep -af ninja` showed both builds still live, racing in one ninja directory; ten minutes later the `.so` relinked and the probe returned 1. A stale-looking artifact mid-build is indistinguishable from a failed build. Before concluding, check `pgrep -f 'ninja -f build-*.ninja'` or wait on the real process (`until ! pgrep -f ninja; do sleep 20; done`), and never start a second `cmake --build` against a live ninja directory. The freshness check that works is **behavioural** — grep the built artifact for a string the commit introduced; timestamps cannot separate "not built yet" from "built without your change", and version strings are configure-time. After a dependency merges, rebuild staged inputs (`.slang-module` files) too, or the run is mixed-binary ([setsid + run_in_background makes exit code 0 report the wrapper](../learnings/1785988615115-setsid-run-in-background-makes-exit-code-0-report-.md)).

**A Windows `pwsh` step's success is its last native command's exit code.** GitHub Actions prepends `$ErrorActionPreference='stop'` and appends `exit $LASTEXITCODE`, but a native command's non-zero exit does not stop the block. In slangpy's `.github/actions/build-and-test-with-slang/action.yml:99-103` (`git clone; git fetch <ref>; git checkout FETCH_HEAD; git submodule update`), run 37684966838 hit a vanished merge-queue ref: the Linux leg (bash `-e`) failed correctly, while the Windows leg logged `fatal: couldn't find remote ref` and `error: pathspec 'FETCH_HEAD'`, built and tested the default branch, and went green. Check `$LASTEXITCODE` after each native call or set `$PSNativeCommandUseErrorActionPreference = $true` (pwsh 7.4+); find past cases by grepping `success` job logs for `error: pathspec 'FETCH_HEAD'` ([GitHub Actions pwsh run blocks hide failed git commands except the last one](../learnings/1791418811630-github-actions-pwsh-run-blocks-hide-failed-git-com.md)).

## Reading Fresh CI Data: Truncation, Stale Listings, and the Gateway Cache

- **WebFetch cannot read `health_snapshots.jsonl`** (`raw.githubusercontent.com/shader-slang/slang-ci-analytics/main/health_snapshots.jsonl`, an append-only file of ~8k polls). WebFetch truncates and returns a line near the cut as if it were the last — a `2026-03-03` snapshot was presented as latest when the truth was `2026-09-15` — and as the file grew it failed hard with `maxContentLength size of 10485760 exceeded`. Use `curl -s --max-time 30 <raw-url> | tail -1` and check that line's `timestamp` is same-day; public raw reads work in-container. The latest line's `merge_queue` (success/failure/in_progress) and `hosted_runner_usage` are a better live CI-failure proxy than the Actions failure API ([CI health snapshot: use curl|tail, not WebFetch](../learnings/1789546707009-ci-health-snapshot-use-curl-tail-not-webfetch-on-h.md)). Do not substitute `shader-slang.org/slang-ci-analytics/status.html`: it renders "All Systems Operational" with no numeric `jobs_queued`/`runs_queued` (those are JS-rendered), so record the gap under "Data Collection Notes" rather than invent numbers ([health_snapshots.jsonl also exceeds WebFetch's 10 MB cap](../learnings/1790065065697-ci-health-snapshots-jsonl-exceeds-webfetch-10mb-li.md)).
- **A `status=failure` listing can return only stale rows, with no error** — from the anonymous `actions/runs?status=failure` (newest 09-10 on a 09-15 call) and from authenticated `gh run list --branch master --status failure --limit 30` (nothing after 10-01 despite failing nightlies 10-05..10-07). The bounded `gh api "repos/O/R/actions/runs?branch=master&status=failure&created=%3E%3D2026-10-05&per_page=50"` returned `total_count=39`. The tell is a newest row days older than master's newest commit; bound with `created>=` and take the live picture from the snapshot's `merge_queue` counts. - **The egress gateway caches GitHub REST GETs keyed on the literal query string.** The un-busted URL kept returning Aug-27→31 failures on a 09-14 call, while appending `&_=$(date +%s%N)` to the same endpoint returned fresh data (GitHub ignores unknown params). This is the recurring "workflow-failures stale-date" heartbeat anomaly: the precheck script's curls don't cache-bust ([un-busted query gets a cached gateway response](../learnings/1789391780211-root-cause-of-the-recurring-slang-workflow-failure.md)).
