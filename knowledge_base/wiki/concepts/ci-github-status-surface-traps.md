# GitHub CI Status-Surface Traps — Combined Status, Evicted Lists & Detached Builds

Every reading on this page is a status *surface* that returns a well-formed, plausible answer about a different question than the one you asked. The unifying test: **what would this output look like if the thing were absent, or if nothing ran?** If the answer is "the same", it is not a measurement — it is a surface that happens to be populated.

## TL;DR

- **Never derive CI health from `GET /repos/{o}/{r}/commits/{sha}/status`.** The combined status is wrong in **both** directions: `SUCCESS` with **zero CI runs** (a review-bot context alone satisfies the rollup), and `pending` with 43 green check-runs (one foreign context stuck 85 h). A stuck `pending` can time a fully-green PR out of the merge queue (#12309 evicted 45/45 green, reason `checks_timed_out`). Read `check-runs` and `statuses` **separately** — each is a partial view.
- **`SlangPy Tests` reds are cross-repo commit statuses**, posted from a `repository_dispatch` run in **shader-slang/slangpy** — they never appear in `check-runs` and are unrerunnable past the 1-month retention. On old PRs the correct triage is "non-actionable, stale cross-repo status", not "failing test".
- **`conclusion=action_required` is an approval GATE, not a failure** — bucket it as a fifth state. Zero jobs ran, there is no log/step/signature to classify, and `gh run rerun --failed` is refused. Route as "needs a maintainer to authorize".
- **A job that fails BY DESIGN tops your infra-failure ranking.** `wait-for-human-priority` is a priority throttle that *deliberately* fails so it burns no runners. Read the workflow definition for any leg before ranking it; rerunning it defeats the throttle.
- **An attempt ladder measures dispatch, not coverage** — report WHERE in the job graph each attempt died. A ladder without per-attempt job states cannot answer "was the remedy attempted?".
- **`reviews(last:10)` is a page, not a population; a missing tool can emit a plausible datum.** Assert `totalCount == (nodes|length)` for any GraphQL connection you count.
- **One invalid field in `gh … --json a,b,c` aborts the WHOLE query** — the valid fields you needed never print. Validate a new field name in isolation.
- **A wake payload's `evicted` list is wrong in both directions — measured 0-for-5.** Only `RemovedFromMergeQueueEvent` with `reason=="failed_checks"` is an eviction; a red job is a fact about a *run*. Reject any blamed run whose start postdates the enqueue.
- **A completion notification from a detached launcher describes the launcher, not the work.** Wait on the real process (`pgrep -f ninja`), and verify a build **behaviourally** — grep the artifact for a string the commit introduced. A stale-looking artifact mid-build is indistinguishable from a failed build.

## A Wake Payload's `evicted` List Is Not a Measurement (2026-08-06 fold)

A degraded transport yields a well-formed, plausible, empty-or-short answer. The CI-babysitter wake payload is the productionized version of that failure, and it is wrong in **both** directions — enumerated against a 93-PR union population (79 non-draft open + 14 recently-merged) over the prior ~24h, the payload was **0-for-5: 1 false positive, 4 false negatives, 0 correct.** It named #12357 as evicted; truth was four evictions it never mentioned (#12252 06:51:45Z, #12353 00:41:16Z, #12363 14:01:51Z, #12365 15:25:54Z) plus one that never happened. **#12357 had an empty `RemovedFromMergeQueueEvent` list and was sitting in the queue at position 1** (`enqueuedAt 03:13:55Z`), while the run the payload blamed (`Check Submodule Pointers`, id 31068599983) **started 03:30:02Z — 16 minutes AFTER the enqueue** ([wake payload evicted list measured 0-for-5](../learnings/1785990268683-wake-payload-evicted-list-measured-0-for-5-enumera.md), [a payload can report an eviction that never happened](../learnings/1785989687956-wake-payload-can-report-an-eviction-that-never-hap.md)).

Both false positives in four hours (#12353, #12357) share one shape: **a failing job inside an in-flight merge-group run, mistaken for an eviction.** The category error is the whole lesson — **a red job is a fact about a *run*; only `RemovedFromMergeQueueEvent` is a record of an *eviction*.** A queue can run checks on a batch without evicting anything, and a red *non-required* check evicts nobody. The four real evictions were invisible for the mirror-image reason: **a PR's own head checks stay green after an eviction**, so nothing else in a head-sha-oriented sweep surfaces them. Enumerate per PR instead of consuming `evicted`:

```bash
gh api graphql -f query='
{repository(owner:"O",name:"R"){pullRequest(number:N){
  state mergeQueueEntry{position enqueuedAt}
  timelineItems(last:15,itemTypes:[REMOVED_FROM_MERGE_QUEUE_EVENT]){
    nodes{... on RemovedFromMergeQueueEvent{createdAt reason beforeCommit{oid}}}}}}}'
```

Require `reason == "failed_checks"` (`merged` and `checks_timed_out` are **not** evictions); empty node list ⇒ nothing to recover, log `action:"left"` and stop. Attribute cause from `beforeCommit.oid`, reading **both** check-runs and commit-status (the object-class rule), and **reject any candidate run whose `run_started_at` postdates the event or the enqueue** — that one timestamp comparison catches the whole false-positive class in a single step. Calibration worth carrying: **3 of the 4 real evictions self-recovered and merged with no action**, so the cost of the misses is lower than it looks, while the cost of the false positive is a requeue attempt against a *healthy* queue entry. ~90 API calls on a 93-PR population; run it every sweep.

## A Detached Build's "Exit Code 0" Describes the Launcher (2026-08-06 fold)

Same instrument-scope defect one layer down, on the local build. `setsid nohup cmake --build … &` plus the harness's *"Background command completed (exit code 0)"* notification describes **the shell wrapper exiting immediately**, not the compiler finishing. On slang#12371 two detached builds both reported exit 0, and a properly-conducted freshness check then produced a genuinely alarming picture: `slang-emit.cpp.o` at 03:43:34Z, `libslang-compiler.so` at **01:09:12Z — older than its own input**, and a behavioural probe for the merged PR's new diagnostic string in the built library at **0 hits**. That reads exactly like a silently-skipped link step. It wasn't: `pgrep -af ninja` showed **both builds still live** (and two `cmake --build` invocations racing in one ninja directory); ten minutes later the `.so` relinked at 03:54:41Z and the probe returned 1 ([setsid + run_in_background makes exit code 0 report the wrapper](../learnings/1785988615115-setsid-run-in-background-makes-exit-code-0-report-.md)).

⇒ ⭐⭐ **A stale-looking artifact mid-build is indistinguishable from a failed build — both readings were correct and the conclusion was wrong.** Check whether a builder is still alive before concluding anything: `pgrep -f 'ninja -f build-*.ninja'`, or arm a monitor that waits on the real process (`until ! pgrep -f ninja; do sleep 20; done`) rather than on an exit code — and never launch a second `cmake --build` against a live ninja directory. **The freshness check that actually works is behavioural**: grep the built binary or library for a string introduced by the commit you expect it to contain. Timestamps alone cannot separate "not built yet" from "built without your change", and `-v`/version strings are configure-time. Corollary for measurement hygiene: after a dependency merges, **rebuild the inputs too** — staged `.slang-module` files produced by the pre-merge binary would have made a "merged master" run a mixed-binary measurement.

## The combined commit status is wrong in BOTH directions, and four more status-surface traps (2026-08-11 fold)

**Never derive CI health from `GET /repos/{o}/{r}/commits/{sha}/status`.** The combined status fails in both directions, measured the same day on shader-slang/slang: **too optimistic** on #11475, where it read `SUCCESS` with **zero CI runs** at the sha because the `state` was carried by an unrelated third-party context (a review bot), so "green" meant *some bot reported success*, not *CI passed*; **too pessimistic** on #12389, where it read `pending` while check-runs were 43 success / 1 skipped / 0 failure, because one foreign context (`SlangPy Tests`, a cross-repo status) had been stuck `pending` for 85 h and pinned the whole rollup. The pessimistic direction is not cosmetic — a stuck `pending` can time a fully-green PR out of the merge queue, precedent #12309 evicted with 45/45 green and removal reason `checks_timed_out`. Read `check-runs` for what executed and read `statuses` separately, knowing each is a partial view ([GitHub's combined commit status fails in BOTH directions](../learnings/1786350644910-github-s-combined-commit-status-fails-in-both-dire.md)). The zero-run half of that is **narrower than it first sounded**: zero-run heads as a distinct state, and the commit-status surface disagreeing with `check-runs`, were both already stored (including #11475 itself, ruled "not 'no CI configured' and not 'green'"); only the *mechanism* — a review bot's context alone satisfying the rollup — was new. **Grep your own leaves by identifier before claiming novelty**, because a novelty claim relayed upward as "the cleanest instance either of us has found" is expensive to walk back ([SCOPE CORRECTION: the zero-run/green find was two-thirds already stored](../learnings/1786321155140-scope-correction-the-zero-run-green-find-was-two-t.md)).

**`SlangPy Tests` reds on shader-slang/slang are cross-repo commit statuses, not Actions check-runs.** They never appear in `commits/<sha>/check-runs`; they are statuses (`context=SlangPy Tests`) posted from an `event=repository_dispatch` run in **shader-slang/slangpy**. So `gh pr checks` and check-run enumeration cannot show you the failing job — read the `statuses` surface and follow `target_url` into `shader-slang/slangpy/actions/runs/<id>`, and any rerun would have to be issued against **slangpy** (`gh run rerun <id> --repo shader-slang/slangpy`). In practice they are dead ends: they are never refreshed and are unrerunnable past the 1-month log/run retention, so on old PRs (#11747, #10769, #10390 — the entire residue after a skip list applied) the correct triage is "non-actionable, stale cross-repo status", not "failing test" ([SlangPy Tests reds are CROSS-REPO COMMIT STATUSES, unrerunnable past 1 month](../learnings/1786335485075-slangpy-tests-reds-on-shader-slang-slang-are-cross.md)).

**`conclusion=action_required` is an approval GATE, not a failure — bucket it as a fifth state.** A sweep that buckets run conclusions four ways (success / failure / untested / non-terminal) will lump `action_required` with `failure|timed_out|startup_failure` and inflate the red count. It means a required approval was never granted so **the run never started** — on fork PRs, the "Approve and run workflows" gate for a first-time or outside contributor. Three independent surfaces confirm it on #11448 (fork `romeoahmed/slang`, run `31317701857`): `attempts/1/jobs` → `total_count=0` and `attempts/2/jobs` → 404, so nothing executed and there is no log, step, or signature to classify; GitHub itself refuses `gh run rerun --failed`; and the run carries no failed job to name. Bucket it separately and route it as "needs a maintainer to authorize", never as a flake or a regression ([conclusion=action_required is an approval GATE, not a failure](../learnings/1786327920887-github-actions-conclusion-action-required-is-an-ap.md)).

**A job that fails BY DESIGN will top your infra-failure ranking.** Across 61 recent `ci.yml` runs the top failing leg was `wait-for-human-priority` — 11 hits across 5 PRs, beating every GPU and test leg — and it is not a defect. Reading `.github/workflows/ci.yml` at source: the job is a **priority throttle**; when a bot's draft-testing dispatch must yield to human / merge-queue / older CI, a marker step *deliberately fails this job* so it consumes no expensive build/test runners, and a companion workflow reruns it once CI is quiet. The workflow comment is explicit that it "deliberately resolves to success or failure, never `skipped`", because a skipped dependency would collide with the implicit `success()` gating the build jobs. Ranking it blind hands a maintainer a false #1 infra signature, and **rerunning it defeats the throttle it implements**, burning the runners it exists to protect. ⇒ Read the workflow definition for any leg before it enters a ranked report ([a CI job that fails BY DESIGN will top your infra-failure ranking](../learnings/1786350256938-a-ci-job-that-fails-by-design-will-top-your-infra-.md)).

**An attempt ladder tells you a run was reran, NOT that the remedy was attempted.** A correct three-line ladder (`att1 FAILURE`, `att2 FAILURE`, `att3 waiting … parked on env=falcor-ci`) licensed the entirely reasonable and entirely wrong upstream conclusion *"someone already tried the obvious remedy twice."* The per-attempt job graph showed att1 died at `wait-for-human-priority` in **11 s** with all 38 downstream jobs `skipped`, att2 the same in **9 s** — so the falcor gate the reader cared about was never reached on either attempt. The attempt count measures *dispatch*, not *coverage*: report **where in the job graph each attempt died**, and treat a ladder without per-attempt job states as unable to answer "was the remedy attempted?" ([an attempt ladder tells you a run was reran, not that the remedy was attempted](../learnings/1786336411679-an-attempt-ladder-tells-you-a-run-was-reran-not-th.md)).

**Two counting traps that emit a believable wrong number rather than an error.** First, `reviews(last:10)` is a **page**, not a population: a published "9 reviews on #12354, 1 on #12417" was really **12** and **1**, plus **3** on a PR that had been missed — 16 across 3 PRs. For any GraphQL connection you are counting, assert `totalCount == (nodes|length)` and `--paginate` when they disagree (`jq -r '.data.….reviews | "totalCount=\(.totalCount) returned=\(.nodes|length) MATCH=\(.totalCount==(.nodes|length))"'`). Second, a **missing tool can emit a plausible datum** — the same shape as a bounded page, and equally undetectable from the number alone ([a bounded page is not a population — and a missing tool can emit a plausible datum](../learnings/1786330741949-a-bounded-page-last-n-first-100-is-not-a-populatio.md)).

**One invalid field in `gh … --json a,b,c` aborts the WHOLE query.** `gh pr view 12425 --json reviewDecision,mergeStateStatus,state,isDraft,latestReviews,mergeQueueEntry` prints `Unknown JSON field: "mergeQueueEntry"` plus the valid-field list and **none of the five valid fields** — including `reviewDecision`, the one actually needed. (`mergeQueueEntry` exists on the GraphQL `PullRequest` type but not in `gh pr view`'s own allowlist, so field validity is per-command, not per-GraphQL-schema.) Here the failure was loud, but the shape is what matters: one bad field name costs every other field in the same call, so in a script that only greps for its field of interest this reads as an empty/false answer. Validate a new field name in isolation before adding it to a multi-field query, and never let a `--json` call's non-zero exit be swallowed ([one invalid field in `gh --json` aborts the whole query](../learnings/1786336024283-one-invalid-field-in-gh-json-a-b-c-aborts-the-whol.md)).
