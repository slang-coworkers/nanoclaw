# GitHub CI Status-Surface Traps — Combined Status, Evicted Lists & Detached Builds

Every reading here is a status *surface* that returns a well-formed, plausible answer to a different question than the one asked. The unifying test: **what would this output look like if the thing were absent, or if nothing ran?** If the answer is "the same", it is not a measurement.

## TL;DR

- **Never derive CI health from the combined `commits/{sha}/status`.** It is wrong in **both** directions: `SUCCESS` with **zero CI runs** (a review-bot context alone satisfies it), and `pending` over 43 green check-runs (one foreign context stuck 85 h). Read `check-runs` and `statuses` **separately**.
- **`SlangPy Tests` reds are cross-repo commit statuses** from a `repository_dispatch` run in **shader-slang/slangpy**: never in `check-runs`, unrerunnable past 1-month retention. On an *active* bot PR the red is usually **version skew** (branch BEHIND master): check `mergeState`, rebase. A green `ci-slangpy-trigger-test.yml` means only the dispatch fired; after a slangpy fix, re-dispatch (a rerun replays the old tree). A merge-group `pending` > ~30 min with a failed `trigger-slangpy-tests` job has no run behind it: re-enqueue.
- **`conclusion=action_required` is an approval GATE, not a failure**: a fifth state. Zero jobs ran, rerun is refused, and check-runs and rollup never see it; only the check *suite* and `/actions/runs?head_sha=<full sha>` do. Count only `event == pull_request` CI runs. The approver is `triggering_actor` on `run_attempt` 2; approval does not survive an author push.
- **A job that fails BY DESIGN tops your infra-failure ranking** (`wait-for-human-priority` is a throttle). Read the workflow before ranking a leg; rerunning it defeats the throttle.
- **An attempt ladder measures dispatch, not coverage**: report WHERE in the job graph each attempt died.
- **`reviews(last:10)` is a page, not a population.** Assert `totalCount == (nodes|length)` for any GraphQL connection you count.
- **One invalid field in `gh … --json a,b,c` aborts the WHOLE query.** `mergeQueueEntry` is GraphQL-only (`null` = not queued); `gh issue view` has no `authorAssociation`.
- **A wake payload's `evicted` list is wrong in both directions (0-for-5).** Only `RemovedFromMergeQueueEvent` records an eviction; a red job is a fact about a *run*. Reject any blamed run started after the enqueue.
- **Read a `failed_checks` eviction's cause from the merge-group run** (`gh-readonly-queue/master/pr-<N>-<sha>`) failed jobs AND its commit `status`, never the PR head's rollup. Status-only evictions never reach the payload; a green head `check-ci` is not "resolved"; the eviction clears auto-merge. `checks_timed_out` = the group hit 2 h.
- **Green CI runs can hide a frozen merge queue**: also gate a health scan on weekday master head age (> ~6 h) and on every `gh-readonly-queue/master` ref's `status` + `check-runs`.
- **A detached launcher's completion notification describes the launcher.** Wait on the real process (`pgrep -f ninja`) and verify a build **behaviourally** (grep the artifact for a commit-introduced string).
- **A Windows `pwsh` step's `success` is the exit code of its LAST native command**: a failed `git fetch` mid-block can build the default branch and go green.
- **CI listings go stale silently**: `--status failure` lists can be days old, a 30-day-expired `waiting` run escapes `created>=`, an un-busted REST GET hits the gateway cache, WebFetch truncates big JSONL. Bound with `created>=`, cache-bust, `curl | tail -1`.

## A Wake Payload's `evicted` List Is Not a Measurement

Against 93 PRs over ~24 h the CI-babysitter wake payload was **0-for-5: 1 false positive, 4 false negatives**. It named #12357, which had no `RemovedFromMergeQueueEvent` and whose blamed run started 16 min after the enqueue, and missed four real evictions ([0-for-5](../learnings/1785990268683-wake-payload-evicted-list-measured-0-for-5-enumera.md), [phantom eviction](../learnings/1785989687956-wake-payload-can-report-an-eviction-that-never-hap.md)). A false positive is **a failing job inside an in-flight merge-group run**; a red non-required check evicts nobody. Nor is a failed required check in the PR's own group: #13848's group failed `check-ci`, yet the PR stayed queued and merged with the next PR's passing group, so count evictions only from `RemovedFromMergeQueueEvent` with `reason != merged`, never from `merge_group` run conclusions ([REST + timeline](../learnings/1793436218667-daily-github-sweep-closed-unmerged-prs-and-merge-q.md); cases on [ASan & merge-group cases](ci-flake-asan-and-merge-group-cases.md)). A miss is the mirror image: head checks stay green after an eviction, so a head-sha sweep never sees it. Enumerate per PR every sweep (~90 calls) and diff the payload (`memory/derive-evictions-from-github.sh <date>`), reading GraphQL `pullRequest{state mergeQueueEntry{position enqueuedAt} timelineItems(last:15,itemTypes:[REMOVED_FROM_MERGE_QUEUE_EVENT]){nodes{... on RemovedFromMergeQueueEvent{createdAt reason beforeCommit{oid}}}}}`.

Empty node list ⇒ log `action:"left"` and stop. **`failed_checks`**: a required check-run *or status* went red. **`checks_timed_out`**: the group sat 2 h with a required check not yet green (#13479 was removed at +2h00m09s, 22 s after its slowest required job, a cold-LLVM macOS build, finished), so look for a ceiling-bound job, not a red one ([checks_timed_out = the group ran 2 h](../learnings/1791484800264-merge-queue-eviction-reason-checks-timed-out-group.md)). Attribute cause from `beforeCommit.oid`, **reject any run whose `run_started_at` postdates the event or enqueue** (this catches the whole false-positive class), check the blamed job against `check-ci`'s `needs`, and re-read the live `headRefOid` before a head-keyed verdict. A `cancelled` entry can be a superseded attempt hit by the 120-min ceiling on non-required windows-aarch64 jobs ([payload evicted can be stale; status-only evictions](../learnings/1791469815689-merge-queue-sweeps-payload-evicted-can-be-stale-an.md)). Calibration: 3 of 4 misses self-recovered; a false positive costs a healthy entry's requeue.

**Read a `failed_checks` cause from the merge-group run, not the PR head's rollup:** list `actions/runs?event=merge_group&created=<range>`, match `head_branch` `gh-readonly-queue/master/pr-<N>-<sha>`, and list its `jobs?filter=latest` failures. Head-only checks such as `check-pr-label` never run there: a sweep blamed #13764 on its red `check-pr-label`, but the group run had 11 `test-slang` jobs failing on a test conflict with another PR. Settle disagreeing parallel sweeps with that query ([eviction cause: read the merge-group run's failed jobs](../learnings/1792660635041-merge-queue-eviction-cause-read-the-merge-group-ru.md)).

**Status-only evictions.** The required cross-repo status `SlangPy Tests` can go red on the merge-group commit while every check-run is green, a `failed_checks` eviction the payload (failed *runs* only) never sees. Read both `commits/<merge-group-sha>/check-runs` and `/statuses`, follow `target_url`, and read the slangpy log before calling it infra; the eviction clears auto-merge, so the PR sits until re-queued ([check commit statuses](../learnings/1793028963721-merge-queue-eviction-cause-check-commit-statuses-n.md)). Red statuses persist on PR heads until a re-push or re-dispatch, and a green head `check-ci` proves nothing (#13626 was wrongly logged `resolved`). Causes so far are all slangpy-side: a CUDA cap set in `ci.yml` but not `ci-latest-slang.yml` (slangpy#1214), a profiler GPU-query-exhaustion bug (slangpy#1223), and a Windows `sgl_tests` profiler flake on #13283 ([SlangPy Tests status evicts](../learnings/1791462232939-slangpy-tests-commit-status-can-evict-from-merge-q.md), [merge-group /status](../learnings/1791490613888-commit-status-only-merge-queue-evictions-payload-r.md), [status-only eviction of #13626](../learnings/1792039063028-payload-evicted-list-misses-status-only-evictions-.md), [eviction from the SlangPy Tests status, #13283](../learnings/1792226879052-slang-merge-queue-eviction-can-come-from-the-slang.md)). Flag trap: `-c` is not a `gh api` flag (`gh api … --jq … -c` prints ~7 KB of help).

**Find the slangpy run behind the status:** in `shader-slang/slangpy/actions/runs?created=>=<window>` take the `repository_dispatch` run `Slang PR #<N>: <title> (<author>)` whose end time matches the removal (`SlangPy Tests` is required, `app_id` null). On 10-23 two evictions matched within 30 s while the PRs' own `merge_group` runs went `success`: #13886 to a Linux `build-pr` runner loss (no failed step, 404 log), #13665 to a Windows `sgl_tests` teardown error after all doctest cases passed ([eviction with green merge_group CI: match the slangpy `Slang PR #N` run](../learnings/1792830200492-slang-merge-queue-eviction-with-green-merge-group-.md), [30-day waiting-run expiry](../learnings/1792830160449-github-actions-30-day-waiting-run-expiry-shows-as-.md)).

**A `pending` with no slangpy run behind it never resolves.** In merge-group CI the `trigger-slangpy-tests` job posts the `SlangPy Tests` pending status first and only then creates the dispatch token and fires the run. On 11-05 (#14110, commit 7cda6d34) "Post pending status" got HTTP 500 "Unexpected end of JSON input" from `POST /statuses` with githubstatus all green, yet the pending was recorded; the trigger steps were skipped, so no slangpy run existed and the queue entry timed out. `commits/<sha>/status` shows only `pending`; the tell is `trigger-slangpy-tests` with conclusion `failure` in `actions/runs/<run>/jobs`. Re-running the job hit the same 500 again; dequeue + re-enqueue for a fresh merge-group SHA is the remedy. A healthy pending turns green in ~30 min, so check every live `gh-readonly-queue` ref whose `SlangPy Tests` has been pending longer than that ([trigger-slangpy-tests dies on a GitHub 500](../learnings/1793909119749-merge-queue-slangpy-tests-can-stick-pending-when-t.md)).

**The largest case froze slang master** for ~16 h (slangpy#1250): nodejs.org listed `v27.0.0-alpha.0.0.0` first, the nodeenv < 1.11.1 that pyright-python uses on PATH-less self-hosted runners crashed (`int() … '0-alpha'`), and every `Slang PR #N` dispatch failed, evicting four PRs with green group `CI` (fix on [slangpy-ci-triage](slangpy-ci-triage.md)). Grep the job log for `0-alpha` / `nodeenv`; job-log URLs ignore suffix ranges (`bytes=-N` returns everything), so send `bytes=0-0`, read `Content-Range`, and request an explicit tail. REST to non-shader-slang repos 401s through OneCLI; GraphQL works ([pyright/nodeenv break evicts slang merge-queue PRs via SlangPy Tests](../learnings/1793349389191-slangpy-pyright-nodeenv-break-evicts-slang-merge-q.md)). Health scans read "master clean" throughout (a stuck queue produces no failed runs), so the scheduled task's prompt or script carries two probes: weekday master head age > ~6 h, and `status` + `check-runs` on every `git/matching-refs/heads/gh-readonly-queue/master` ref ([green CI runs can hide a stuck merge queue](../learnings/1793376411569-green-ci-runs-can-hide-a-stuck-merge-queue-check-c.md)).

## The Combined Status and the Cross-Repo `SlangPy Tests` Status

**The combined commit status is wrong in both directions.** On one day it was **too optimistic** on #11475 (`SUCCESS` with **zero CI runs**: a review bot's context set the `state`) and **too pessimistic** on #12389 (`pending` over 43 green check-runs: `SlangPy Tests` stuck 85 h), and #12309 was evicted with 45/45 green (`checks_timed_out`) ([combined status fails both ways](../learnings/1786350644910-github-s-combined-commit-status-fails-in-both-dire.md)). Only the review-bot mechanism was new: **grep your own leaves by identifier before claiming novelty**; a relayed novelty claim is expensive to walk back ([scope correction](../learnings/1786321155140-scope-correction-the-zero-run-green-find-was-two-t.md)).

**`SlangPy Tests` is a status posted from an `event=repository_dispatch` run in shader-slang/slangpy**, invisible to `gh pr checks` and check-run enumeration. Read `statuses`, follow `target_url`, and rerun there (`gh run rerun <id> --repo shader-slang/slangpy`); past 1-month retention they are dead ends ("non-actionable, stale cross-repo status") ([SlangPy Tests reds are CROSS-REPO COMMIT STATUSES](../learnings/1786335485075-slangpy-tests-reds-on-shader-slang-slang-are-cross.md)). A green `ci-slangpy-trigger-test.yml -f pr_number=N` (~1 min) only means it posted `pending` and fired `repository_dispatch`; the result is slangpy's `ci-latest-slang.yml` run "Slang PR #N: …" (~30 min; `--log-failed | grep 'FAILED slangpy'`). Draft and bot PRs skip the trigger (`pull_request_target` gated on `draft != true`) and need an explicit dispatch ([the trigger's success is only the dispatch](../learnings/1791510877884-ci-slangpy-trigger-test-yml-success-is-only-the-di.md)).

**After a slangpy-side fix, re-dispatch from slang instead of rerunning:** a `repository_dispatch` run's `GITHUB_SHA` is slangpy's head at dispatch time, so a rerun replays the pre-fix tree (inferred). `gh workflow run ci-slangpy-trigger-test.yml --repo shader-slang/slang -f pr_number=N` reads the PR's current head and starts a run ~30 s later; its frequent HTTP 500s create no run, so retry with backoff. Canary one PR and wait for BOTH Linux and Windows `build-pr`; `gh run view --log` is empty until the run ends (per-job logs still work, per [slangpy-ci-triage](slangpy-ci-triage.md)), and tight polls burn the shared token ([re-dispatch from slang](../learnings/1793370651623-re-triggering-slangpy-tests-after-an-upstream-slan.md)). **A red whose `target_url` names an OLDER run can be stale** (it can overwrite the newer run's `pending` until that run ends), so check the newest `repository_dispatch` run first. `SlangPy tests abandoned` = a `build-pr` matrix job that never appeared (infra drop). In failed logs grep `short test summary` / `FAILED `; `Hot reload failed` / `error[E…]` lines are deliberate ([stale red; abandoned](../learnings/1793376826751-red-slangpy-tests-whose-target-url-is-an-older-run.md)).

**On an active bot PR, a red `SlangPy Tests` is usually version skew; check `mergeState` first.** The integration builds the PR's slang commit against **slangpy main**, so a branch `BEHIND` master after a coordinated breaking change fails though both mains are correct (slang added `enum MatrixLayoutMode`, slangpy used it, and six un-rebased bot PRs hit `error[E30015]`). Rebase; there is no issue to file. Confirm a "symbol removed" theory with `git log -S <symbol>` before relaying it (the first read here was inverted) ([cross-repo integration red on a bot PR is usually version skew](../learnings/1789151785364-cross-repo-integration-ci-red-on-a-bot-pr-is-usual.md)).

## `action_required` Is an Approval Gate the Checks API Cannot See

Lumping `action_required` with `failure|timed_out|startup_failure` inflates the red count: an approval (fork PRs, "Approve and run workflows") was never granted, so **the run never started** (`attempts/1/jobs` → `total_count=0`; `gh run rerun --failed` is refused). Bucket it as a fifth state, "needs a maintainer to authorize" ([conclusion=action_required is an approval GATE](../learnings/1786327920887-github-actions-conclusion-action-required-is-an-ap.md)).

The held workflow creates no check-run, so it is absent from REST `check-runs`/`status` **and** GraphQL `statusCheckRollup.contexts`, whose `state` reflects only what ran (see [query confidence](ci-github-query-confidence-and-gates.md)). Only the suite layer shows it: `/actions/runs?head_sha=<full 40-char sha>` (an abbreviated sha silently returns `total_count:0`) or GraphQL `commit.checkSuites` with `ACTION_REQUIRED`. The axis is **check-run vs suite/run level, not REST vs GraphQL**: the babysitter's `splitExclusions` fix (#12544) read `action_required` off check-runs, so it never fired and missed the #13218 wedge it was written for. Filter to `event == pull_request` and the CI workflow (`CI` on slang, `ci` on slangpy and slang-rhi; for suites read `workflowRun{event workflow{name}}`) and dedup by name+highest-id: sibling review/`_target` runs sit at `action_required` on fork PRs even after CI ran, inflating a "CI never approved" count to 3 of 7 (true: 2) ([filter to event == pull_request](../learnings/1793003118714-fork-pr-ci-never-approved-count-filter-checksuites.md)). A tail-scan filtering `rollup !== 'SUCCESS'` first excludes this class outright, and a tracker touching only PRs in the current payload lets a zero-check-run wedge age out of every surface ([action_required wedges are invisible to the Checks API](../learnings/1790080487638-action-required-workflow-approval-wedges-are-invis.md), [a check-runs-fed action_required classifier is dead code](../learnings/1790079172299-ci-babysitter-action-required-fix-2026-09-22-12544.md)).

**Who approved a held run:** neither a review nor a timeline event; read `actions/runs/<id>` `.run_attempt, .triggering_actor.login, .run_started_at`. After approval `run_attempt` is 2, `triggering_actor` is the approving maintainer and `actor` is still the contributor ([triggering_actor](../learnings/1793026171832-who-approved-an-action-required-fork-ci-run-trigge.md)). A PR can also leave an ACTION_REQUIRED count without approval (slang #13473's held fork run vanished from an unchanged head, `actions/runs?head_sha=` returning 0 runs), so cross-check each PR that drops off before reporting it approved ([REST + timeline](../learnings/1793436218667-daily-github-sweep-closed-unmerged-prs-and-merge-q.md)).

**Fork CI approval does not survive a push**: every new push by the fork author creates a new `pull_request` `CI` run that is `action_required` again, so the count rises with no new PR. On 2026-11-01 the "fork PRs with CI never approved" count went 9 → 12 only because an author pushed fixes to three PRs approved on 10-30. Report such joiners as "re-needs approval after author push"; the lightweight checks' SUCCESS rollup meanwhile is not a test signal ([fork re-push resets CI approval](../learnings/1793522418229-github-sweep-clock-skew-vs-actions-stamps-and-fork.md)). slangpy behaves the same: on #1234 the author's pushes after approval put `ci` and `checks` back to `action_required`, visible only in `/actions/runs?head_sha=<full sha>`, while `/check-runs` and `/status` looked green. After any fork-PR push, read `/actions/runs` and name "maintainer must approve the fork runs" as the next action ([slangpy fork re-push](../learnings/1793632219099-fork-pr-ci-approval-does-not-carry-over-to-new-pus.md)).

## Failure Rankings and Attempt Ladders Measure the Wrong Thing

**A job that fails by design tops the ranking.** Across 61 `ci.yml` runs the top failing leg was `wait-for-human-priority`, a **priority throttle**: when a bot's draft dispatch must yield to human, merge-queue or older CI, a marker step fails it so it holds no runners, and a companion workflow reruns it later (never `skipped`, which would collide with the build jobs' implicit `success()` gating). Ranking it is a false #1 infra signature; rerunning it burns the runners it protects ([fails by design](../learnings/1786350256938-a-ci-job-that-fails-by-design-will-top-your-infra-.md)).

**An attempt ladder says a run was rerun, not that the remedy was attempted.** `att1 FAILURE, att2 FAILURE, att3 waiting … env=falcor-ci` looked like two tries at the remedy, but both died at `wait-for-human-priority` in ~10 s with all downstream jobs `skipped`. Report **where in the job graph each attempt died** ([attempt ladder](../learnings/1786336411679-an-attempt-ladder-tells-you-a-run-was-reran-not-th.md)).

## Query Traps That Return a Believable Wrong Answer

**A bounded page is not a population.** A published "9 reviews on #12354" from `reviews(last:10)` was really 12, and a third PR was missed. Assert `totalCount == (nodes|length)` and `--paginate` when they differ. A **missing tool can emit a plausible datum** in the same undetectable way ([a bounded page is not a population](../learnings/1786330741949-a-bounded-page-last-n-first-100-is-not-a-populatio.md)).

**One invalid field in `gh … --json` aborts the whole query.** `gh pr view N --json reviewDecision,…,mergeQueueEntry` exits 1 with `Unknown JSON field: "mergeQueueEntry"` and prints none of the valid fields (the field is GraphQL-only) ([one invalid field](../learnings/1786336024283-one-invalid-field-in-gh-json-a-b-c-aborts-the-whol.md)). In a bulk loop it is silent (the babysitter's idempotency loop twice got empty fields for every PR, like auth trouble), so validate a new field alone, never swallow a non-zero exit, and run one call bare (`2>&1 | head`) before debugging credentials. Use `gh pr view --json state,isDraft,mergeStateStatus,headRefOid,statusCheckRollup` plus GraphQL `pullRequest(number:N){state mergeQueueEntry{position state}}` for queue membership (`null` = not queued; non-null shape untested) ([GraphQL mergeQueueEntry](../learnings/1791705807345-merge-queue-membership-check-use-graphql-pullreque.md)). `statusCheckRollup` also shows WAITING gates (`falcor-build-approval-gate`) that `gh pr checks` omits, and mixes check-runs (`.name/.conclusion`) with legacy statuses (`.context/.state`), so null-guard `.name` in jq `test()` ([no mergeQueueEntry in gh pr view](../learnings/1791267800558-gh-pr-view-json-has-no-mergequeueentry-field-use-g.md)). `gh issue view N --json authorAssociation` fails the same way; read COLLABORATOR vs CONTRIBUTOR (for the triage skip rule) with `gh api repos/O/R/issues/N --jq .author_association`. `--json issueType,closedByPullRequestsReferences` works, a cheap drift check ([no authorAssociation](../learnings/1793639840678-gh-issue-view-json-has-no-authorassociation-use-gh.md)).

## A Detached Build's Exit 0 and a pwsh Step's Success

**A detached launcher's exit code describes the launcher.** With `setsid nohup cmake --build … &`, the harness's "Background command completed (exit code 0)" is the wrapper exiting. On slang#12371 two such builds reported exit 0 while `libslang-compiler.so` was older than its input `.o` and lacked the PR's new diagnostic; `pgrep -af ninja` showed both still racing in one ninja directory. Wait on the real process (`until ! pgrep -f ninja; do sleep 20; done`), never start a second `cmake --build` on a live ninja directory, and verify **behaviourally** by grepping the artifact for a string the commit introduced (timestamps and configure-time version strings cannot tell "not built yet" from "built without your change"). After a dependency merges, rebuild staged `.slang-module` inputs too, or the run is mixed-binary ([wrapper exit 0](../learnings/1785988615115-setsid-run-in-background-makes-exit-code-0-report-.md)).

**A Windows `pwsh` step's success is its last native command's exit code.** Actions wraps the block with `$ErrorActionPreference='stop'` and `exit $LASTEXITCODE`, but a native non-zero exit does not stop it. In slangpy's `build-and-test-with-slang/action.yml:99-103` (`git clone; git fetch <ref>; git checkout FETCH_HEAD; …`) a vanished merge-queue ref failed the Linux leg (bash `-e`), while the Windows leg logged `fatal: couldn't find remote ref`, built the default branch, and went green. Check `$LASTEXITCODE` after each native call or set `$PSNativeCommandUseErrorActionPreference = $true` (pwsh 7.4+); find past cases by grepping `success` job logs for `error: pathspec 'FETCH_HEAD'` ([pwsh hides failed git](../learnings/1791418811630-github-actions-pwsh-run-blocks-hide-failed-git-com.md)).

## Reading Fresh CI Data: Truncation, Stale Listings, and the Gateway Cache

- **WebFetch cannot read `health_snapshots.jsonl`** (slang-ci-analytics, ~8k appended polls): it truncated and presented a March line as latest, then failed at its 10 MB cap. Use `curl -s --max-time 30 <raw-url> | tail -1` and check the `timestamp` is same-day; its `merge_queue` and `hosted_runner_usage` are a better live CI-failure proxy than the Actions failure API ([curl|tail](../learnings/1789546707009-ci-health-snapshot-use-curl-tail-not-webfetch-on-h.md)). `status.html` is no substitute (JS-rendered "All Systems Operational", no numeric queue counts), so record the gap under "Data Collection Notes" rather than invent numbers ([10 MB cap](../learnings/1790065065697-ci-health-snapshots-jsonl-exceeds-webfetch-10mb-li.md)).
- **A `status=failure` listing can return only stale rows, with no error**: anonymous `actions/runs?status=failure` and `gh run list --branch master --status failure --limit 30` returned nothing after dates with known failing nightlies, while the same REST query with `created=%3E%3D<date>&per_page=50` returned 39. The tell is a newest row days older than master's head; bound with `created>=`. Same session: size an MDL perf flag from `confirmation.json` `plan.regressions` (1.12x), not the analyze log's first table (1.58x) ([stale --status failure](../learnings/1791360225685-gh-run-list-status-failure-can-silently-return-sta.md)). `created>=` has its own blind spot: a `waiting` run (e.g. bot-draft CI at an approval gate) hitting the 30-day limit ends `failure` with an old `created_at`, so diff yesterday's `status=waiting` list against today's and fetch each departure (8 of 14 were expiries) ([30-day waiting-run expiry](../learnings/1792830160449-github-actions-30-day-waiting-run-expiry-shows-as-.md)).
- **The egress gateway caches GitHub REST GETs keyed on the literal query string**: an un-busted URL kept returning two-week-old failures, while appending `&_=$(date +%s%N)` returned fresh data (GitHub ignores unknown params). That explains the recurring "workflow-failures stale-date" heartbeat anomaly ([gateway cache](../learnings/1789391780211-root-cause-of-the-recurring-slang-workflow-failure.md)).
