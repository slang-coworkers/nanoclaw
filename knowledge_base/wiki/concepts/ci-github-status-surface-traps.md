# GitHub CI Status-Surface Traps — Combined Status, Evicted Lists & Detached Builds

Every reading here is a status *surface* that returns a well-formed, plausible answer to a different question than the one asked. The unifying test: **what would this output look like if the thing were absent, or if nothing ran?** If the answer is "the same", it is not a measurement.

## TL;DR

- **Never derive CI health from the combined `commits/{sha}/status`**: it reads `SUCCESS` with **zero CI runs** (a review-bot context suffices) and `pending` over 43 green check-runs. Read `check-runs` and `statuses` **separately**.
- **`SlangPy Tests` is a cross-repo commit status** from a shader-slang/slangpy `repository_dispatch` run: never in `check-runs`, dead past 1-month retention. On an active bot PR a red is usually **version skew** (branch BEHIND master): rebase. A green trigger workflow means only the dispatch fired; after a slangpy fix re-dispatch (a rerun replays the old tree). A merge-group `pending` > ~30 min with a failed `trigger-slangpy-tests` job has no run behind it: re-enqueue. A PR head with NO `SlangPy Tests` status (only `license/cla`) after a `pull_request_target` `startup_failure` (the 11-09 brownout) stays BLOCKED forever: dispatch `ci-slangpy-trigger-test.yml -f pr_number=N`.
- **`conclusion=action_required` is an approval GATE** (a fifth state): zero jobs ran, rerun is refused, and only the check *suite* / `/actions/runs?head_sha=<full sha>` sees it. Count only `event == pull_request` CI runs. Approver = `triggering_actor` on `run_attempt` 2; approval does not survive an author push, and a held suite can vanish unapproved.
- **A job that fails BY DESIGN tops infra-failure rankings** (`wait-for-human-priority` is a throttle; rerunning it defeats it). **An attempt ladder measures dispatch, not coverage**: report where each attempt died.
- **A page is not a population**: assert `totalCount == (nodes|length)`. **One invalid `gh --json` field aborts the whole query** (`mergeQueueEntry` is GraphQL-only, `null` = not queued; `gh issue view` has no `authorAssociation`).
- **A wake payload's `evicted` list is wrong both ways (0-for-5).** Only `RemovedFromMergeQueueEvent` records an eviction; reject any blamed run started after the enqueue.
- **Read a `failed_checks` cause from the merge-group run's failed jobs AND commit `status`**, never the head rollup; status-only evictions never reach the payload, and the eviction clears auto-merge. `checks_timed_out` = the group hit 2 h.
- **Green CI runs can hide a frozen merge queue**: also probe weekday master head age (> ~6 h) and every `gh-readonly-queue/master` ref's `status` + `check-runs`.
- **A detached launcher's exit 0 describes the launcher**: wait on `pgrep -f ninja`; verify builds **behaviourally** (grep the artifact for a commit-introduced string). **A Windows `pwsh` step's `success` is its LAST native command's exit code.**
- **CI listings go stale silently** (`--status failure` lists, 30-day-expired `waiting` runs, gateway-cached REST GETs, WebFetch truncation): bound with `created>=`, cache-bust, `curl | tail -1`.

## A Wake Payload's `evicted` List Is Not a Measurement

Over 93 PRs in ~24 h the babysitter wake payload was **0-for-5**: it named #12357 (no `RemovedFromMergeQueueEvent`; blamed run started 16 min after enqueue) and missed four evictions ([0-for-5](../learnings/1785990268683-wake-payload-evicted-list-measured-0-for-5-enumera.md), [phantom](../learnings/1785989687956-wake-payload-can-report-an-eviction-that-never-hap.md)). Neither a red non-required check nor a failed required check in the PR's own group evicts (#13848's group failed `check-ci`, yet it merged with the next group): count only `RemovedFromMergeQueueEvent` with `reason != merged` ([timeline](../learnings/1793436218667-daily-github-sweep-closed-unmerged-prs-and-merge-q.md); cases on [ASan & merge-group cases](ci-flake-asan-and-merge-group-cases.md)). Head checks stay green after an eviction, so enumerate per PR every sweep (~90 calls) and diff the payload (`memory/derive-evictions-from-github.sh <date>`) via GraphQL `pullRequest{state mergeQueueEntry{position enqueuedAt} timelineItems(last:15,itemTypes:[REMOVED_FROM_MERGE_QUEUE_EVENT]){nodes{... on RemovedFromMergeQueueEvent{createdAt reason beforeCommit{oid}}}}}`.

Empty node list ⇒ log `action:"left"` and stop. `failed_checks` = a required check-run *or status* went red; `checks_timed_out` = the group sat 2 h with a required check not yet green, so look for a ceiling-bound job, not a red one (#13479 left 22 s after its cold-LLVM macOS build finished) ([timed out](../learnings/1791484800264-merge-queue-eviction-reason-checks-timed-out-group.md)). Attribute cause from `beforeCommit.oid`; **reject any run whose `run_started_at` postdates the event or enqueue** (the whole false-positive class); check the blamed job against `check-ci`'s `needs`; re-read the live `headRefOid` before a head-keyed verdict. A `cancelled` entry can be a superseded attempt hit by the 120-min ceiling on non-required windows-aarch64 jobs ([stale payload](../learnings/1791469815689-merge-queue-sweeps-payload-evicted-can-be-stale-an.md)).

**Read a `failed_checks` cause from the merge-group run, not the head rollup:** `actions/runs?event=merge_group&created=<range>`, match `head_branch` `gh-readonly-queue/master/pr-<N>-<sha>`, read its `jobs?filter=latest` failures. #13764 was blamed on a head-only red `check-pr-label`; its group run had 11 `test-slang` jobs failing on a conflict with another PR. This also settles disagreeing parallel sweeps ([group run](../learnings/1792660635041-merge-queue-eviction-cause-read-the-merge-group-ru.md)).

**Status-only evictions.** The required cross-repo status `SlangPy Tests` can go red on the merge-group commit with every check-run green, an eviction the payload (failed *runs* only) never sees. Read `commits/<merge-group-sha>/check-runs` and `/statuses`, follow `target_url`, read the slangpy log before calling it infra; the eviction clears auto-merge, so the PR sits until re-queued ([statuses](../learnings/1793028963721-merge-queue-eviction-cause-check-commit-statuses-n.md)). Red statuses persist on heads until a re-push or re-dispatch; a green head `check-ci` proves nothing (#13626 was wrongly logged `resolved`). Causes so far are slangpy-side: a CUDA cap in `ci.yml` but not `ci-latest-slang.yml` (slangpy#1214), a profiler GPU-query-exhaustion bug (slangpy#1223), a Windows `sgl_tests` profiler flake (#13283) ([slangpy#1214](../learnings/1791462232939-slangpy-tests-commit-status-can-evict-from-merge-q.md), [/status](../learnings/1791490613888-commit-status-only-merge-queue-evictions-payload-r.md), [#13626](../learnings/1792039063028-payload-evicted-list-misses-status-only-evictions-.md), [#13283](../learnings/1792226879052-slang-merge-queue-eviction-can-come-from-the-slang.md)). `-c` is not a `gh api` flag (it prints ~7 KB of help).

**Find the slangpy run behind the status:** in `shader-slang/slangpy/actions/runs?created=>=<window>`, the `repository_dispatch` run `Slang PR #<N>: <title> (<author>)` whose end time matches the removal (`app_id` null). On 10-23 two evictions with `success` group runs matched within 30 s: #13886 (Linux `build-pr` runner loss, 404 log), #13665 (Windows `sgl_tests` teardown error after all cases passed) ([match run](../learnings/1792830200492-slang-merge-queue-eviction-with-green-merge-group-.md), [expiry](../learnings/1792830160449-github-actions-30-day-waiting-run-expiry-shows-as-.md)).

**A `pending` with no slangpy run behind it never resolves.** `trigger-slangpy-tests` posts pending before creating the dispatch token and firing the run. On 11-05 (#14110, 7cda6d34) "Post pending status" got HTTP 500 "Unexpected end of JSON input" yet the pending was recorded; later steps skipped and the entry timed out. The tell is `trigger-slangpy-tests` = `failure` in `actions/runs/<run>/jobs`. A job rerun hit the same 500: dequeue + re-enqueue for a fresh SHA. Healthy pendings clear in ~30 min, so check every live `gh-readonly-queue` ref pending longer ([HTTP 500](../learnings/1793909119749-merge-queue-slangpy-tests-can-stick-pending-when-t.md)).

**The largest case froze slang master ~16 h** (slangpy#1250): nodejs.org listed `v27.0.0-alpha.0.0.0` first, nodeenv < 1.11.1 (pyright-python, PATH-less self-hosted runners) crashed on `int() … '0-alpha'`, and every `Slang PR #N` dispatch failed, evicting four PRs with green group `CI` (fix on [slangpy-ci-triage](slangpy-ci-triage.md)). Grep logs for `0-alpha` / `nodeenv`; job-log URLs ignore suffix ranges (`bytes=-N` returns all), so send `bytes=0-0`, read `Content-Range`, request an explicit tail. REST to non-shader-slang repos 401s through OneCLI; GraphQL works ([nodeenv](../learnings/1793349389191-slangpy-pyright-nodeenv-break-evicts-slang-merge-q.md)). A stuck queue produces no failed runs, so the scheduled health task also probes weekday master head age > ~6 h and `status` + `check-runs` on every `git/matching-refs/heads/gh-readonly-queue/master` ref ([stuck queue](../learnings/1793376411569-green-ci-runs-can-hide-a-stuck-merge-queue-check-c.md)).

## The Combined Status and the Cross-Repo `SlangPy Tests` Status

**The combined commit status is wrong both ways:** `SUCCESS` with **zero CI runs** on #11475 (a review bot's context set the `state`), `pending` over 43 green check-runs on #12389 (`SlangPy Tests` stuck 85 h), and #12309 evicted at 45/45 green (`checks_timed_out`) ([both ways](../learnings/1786350644910-github-s-combined-commit-status-fails-in-both-dire.md)). Only the review-bot mechanism was new: **grep your own leaves by identifier before claiming novelty** ([scope correction](../learnings/1786321155140-scope-correction-the-zero-run-green-find-was-two-t.md)).

**`SlangPy Tests` is posted from an `event=repository_dispatch` run in shader-slang/slangpy**, invisible to `gh pr checks` and check-runs: read `statuses`, follow `target_url`, rerun there (`gh run rerun <id> --repo shader-slang/slangpy`); past 1-month retention it is "non-actionable, stale cross-repo status" ([cross-repo](../learnings/1786335485075-slangpy-tests-reds-on-shader-slang-slang-are-cross.md)). A green `ci-slangpy-trigger-test.yml -f pr_number=N` (~1 min) only posted `pending` and fired the dispatch; the result is slangpy's `ci-latest-slang.yml` run "Slang PR #N: …" (~30 min; `--log-failed | grep 'FAILED slangpy'`). Draft and bot PRs skip the trigger (`pull_request_target` gated on `draft != true`) and need an explicit dispatch ([dispatch only](../learnings/1791510877884-ci-slangpy-trigger-test-yml-success-is-only-the-di.md)).

**After a slangpy-side fix, re-dispatch from slang; don't rerun:** a dispatch run's `GITHUB_SHA` is slangpy's head at dispatch time, so a rerun replays the pre-fix tree (inferred). `gh workflow run ci-slangpy-trigger-test.yml --repo shader-slang/slang -f pr_number=N` reads the PR's current head and starts a run ~30 s later; its frequent HTTP 500s create no run, so retry with backoff. Canary one PR, wait for BOTH Linux and Windows `build-pr`; `gh run view --log` is empty until the run ends (per-job logs work, per [slangpy-ci-triage](slangpy-ci-triage.md)); tight polls burn the shared token ([re-dispatch](../learnings/1793370651623-re-triggering-slangpy-tests-after-an-upstream-slan.md)). **A red whose `target_url` names an OLDER run can be stale** (it can overwrite a newer `pending`): check the newest dispatch run first. `SlangPy tests abandoned` = a `build-pr` matrix job never appeared (infra drop). Grep failed logs for `short test summary` / `FAILED `; `Hot reload failed` / `error[E…]` lines are deliberate ([stale red](../learnings/1793376826751-red-slangpy-tests-whose-target-url-is-an-older-run.md)).

**A MISSING `SlangPy Tests` status blocks a PR silently; look for the absent status, not a failed run.** GitHub's scheduled brownout of the default `pull_request_target` policy (11-09 16:21–18:00Z observed; next Mon 11-16 16:00–18:00 UTC; enforcement 2026-12-02) made every `pull_request_target` workflow in shader-slang/slang end `startup_failure` with zero jobs: `CI SlangPy Trigger Test`, `Claude PR Review`, `PR Maintenance`, `Slash Cleanup`. The trigger fires only on opened/synchronize/reopened/ready_for_review (and `merge_group`), so a head pushed inside the window never gets the status and nothing re-fires it. Symptom: auto-merge armed, `mergeStateStatus: BLOCKED`, every check-run green, `commits/<head>/status` listing only `license/cla`; the PR never enters the queue and master's head ages. Confirm with `gh run list --workflow "CI SlangPy Trigger Test"` (a `startup_failure` at the push time) and `actions/runs?status=startup_failure` for the other workflows. That "SlangPy Tests is required" is inferred from BLOCKED plus a green rollup, since branch protection is 403 to the bot. The brownout is distinct from the same day's 18:12–18:59Z Actions incident (zero-job `failure` runs; slangpy-side "SlangPy tests abandoned"). Tracked in shader-slang/slang#14427; the durable fix is an admin `pull_request_target` allow-list before the next brownout ([pull_request_target brownout strands SlangPy Tests](../learnings/1794254783516-pull-request-target-brownout-strands-slangpy-tests.md)). The repair is the same re-dispatch as above: `gh workflow run ci-slangpy-trigger-test.yml --repo shader-slang/slang -f pr_number=N` succeeded in under 30 s, posted `SlangPy Tests=pending` on the current head, and queued slangpy's `ci-latest-slang.yml` run about 30 s later. First check that the PR is open, non-draft and its head unchanged; skip DIRTY/BEHIND PRs, which are author-owned. A PR pushed inside the outage can have NO trigger run at all, not even a `startup_failure`, so search for the missing status and verify with `gh api repos/shader-slang/slang/commits/<sha>/status` ([re-dispatch from the Slang side](../learnings/1794255153466-missing-slangpy-tests-status-after-pull-request-ta.md)).

**On an active bot PR, a red `SlangPy Tests` is usually version skew; check `mergeState` first.** The PR's slang commit builds against **slangpy main**, so a branch `BEHIND` master after a coordinated breaking change fails with both mains correct (slang added `enum MatrixLayoutMode`, slangpy used it, six un-rebased bot PRs hit `error[E30015]`). Rebase; there is no issue to file. Confirm a "symbol removed" theory with `git log -S <symbol>` before relaying it ([version skew](../learnings/1789151785364-cross-repo-integration-ci-red-on-a-bot-pr-is-usual.md)).

## `action_required` Is an Approval Gate the Checks API Cannot See

An `action_required` run (fork PRs, "Approve and run workflows") **never started** (`attempts/1/jobs` → `total_count=0`; `gh run rerun --failed` is refused). Bucket it as a fifth state, "needs a maintainer to authorize", not with `failure|timed_out|startup_failure` ([gate](../learnings/1786327920887-github-actions-conclusion-action-required-is-an-ap.md)).

It creates no check-run, so it is absent from REST `check-runs`/`status` **and** GraphQL `statusCheckRollup.contexts` (see [query confidence](ci-github-query-confidence-and-gates.md)); only the suite layer shows it: `/actions/runs?head_sha=<full 40-char sha>` (an abbreviated sha silently returns `total_count:0`) or GraphQL `commit.checkSuites` with `ACTION_REQUIRED`. The axis is **check-run vs suite/run, not REST vs GraphQL**: the babysitter's `splitExclusions` fix (#12544) read it off check-runs, never fired, and missed the #13218 wedge it targeted. Filter to `event == pull_request` and the CI workflow (`CI` on slang, `ci` on slangpy and slang-rhi; for suites `workflowRun{event workflow{name}}`) and dedup by name+highest-id, since sibling review/`_target` runs sit at `action_required` on fork PRs even after CI ran (a "CI never approved" count read 3 of 7; true 2) ([event filter](../learnings/1793003118714-fork-pr-ci-never-approved-count-filter-checksuites.md)). A tail-scan filtering `rollup !== 'SUCCESS'` first excludes this class, and a tracker touching only current-payload PRs lets a zero-check-run wedge age out of every surface ([invisible](../learnings/1790080487638-action-required-workflow-approval-wedges-are-invis.md), [dead code](../learnings/1790079172299-ci-babysitter-action-required-fix-2026-09-22-12544.md)).

**Who approved a held run:** read `actions/runs/<id>` `.run_attempt, .triggering_actor.login, .run_started_at` (no review or timeline event): after approval `run_attempt` is 2, `triggering_actor` the maintainer, `actor` still the contributor ([approver](../learnings/1793026171832-who-approved-an-action-required-fork-ci-run-trigge.md)).

**The "CI never approved" count moves without approvals, both ways.** Each fork-author push makes a new `action_required` `CI` run: on 2026-11-01 the count went 9 → 12 only from pushes to three PRs approved 10-30. Report joiners as "re-needs approval after author push" (the lightweight checks' SUCCESS rollup is no test signal) ([re-push](../learnings/1793522418229-github-sweep-clock-skew-vs-actions-stamps-and-fork.md)). slangpy #1234 likewise put `ci` and `checks` back to `action_required`, visible only in `/actions/runs?head_sha=<full sha>` (`/check-runs`, `/status` green); after any fork-PR push read `/actions/runs` and name "maintainer must approve the fork runs" as the next action ([slangpy](../learnings/1793632219099-fork-pr-ci-approval-does-not-carry-over-to-new-pus.md)). Conversely a held suite can vanish from an unchanged head with no approval: slang #13473 (`actions/runs?head_sha=` → 0 runs) ([timeline](../learnings/1793436218667-daily-github-sweep-closed-unmerged-prs-and-merge-q.md)) and #13698 on 2026-11-06 ([vanished suite](../learnings/1793955615028-github-sweep-merge-queue-commit-dates-mq-bypass-va.md)). Cross-check each dropout; one with no CI suite left is still unapproved.

## Failure Rankings and Attempt Ladders Measure the Wrong Thing

**A job that fails by design tops the ranking.** Across 61 `ci.yml` runs the top failing leg was `wait-for-human-priority`, a **priority throttle**: a bot draft dispatch yielding to human, merge-queue or older CI is failed by a marker step so it holds no runners, and a companion workflow reruns it later (not `skipped`, which collides with the build jobs' implicit `success()` gating). Ranking it is a false #1 signature; rerunning it burns the runners it protects ([by design](../learnings/1786350256938-a-ci-job-that-fails-by-design-will-top-your-infra-.md)).

**An attempt ladder says a run was rerun, not that the remedy was attempted.** `att1 FAILURE, att2 FAILURE, att3 waiting … env=falcor-ci` looked like two remedy tries; both died at `wait-for-human-priority` in ~10 s with all downstream jobs `skipped`. Report **where in the job graph each attempt died** ([ladder](../learnings/1786336411679-an-attempt-ladder-tells-you-a-run-was-reran-not-th.md)).

## Query Traps That Return a Believable Wrong Answer

**A bounded page is not a population.** "9 reviews on #12354" from `reviews(last:10)` was really 12: assert `totalCount == (nodes|length)` and `--paginate` when they differ. A **missing tool can emit a plausible datum** just as undetectably ([page](../learnings/1786330741949-a-bounded-page-last-n-first-100-is-not-a-populatio.md)).

**One invalid field in `gh … --json` aborts the whole query:** `gh pr view N --json reviewDecision,…,mergeQueueEntry` exits 1 with `Unknown JSON field: "mergeQueueEntry"` and prints none of the valid fields ([invalid field](../learnings/1786336024283-one-invalid-field-in-gh-json-a-b-c-aborts-the-whol.md)). In a bulk loop it is silent (empty fields for every PR, like auth trouble): validate a new field alone, never swallow a non-zero exit, run one call bare (`2>&1 | head`) before debugging credentials. For queue membership use `gh pr view --json state,isDraft,mergeStateStatus,headRefOid,statusCheckRollup` plus GraphQL `pullRequest(number:N){state mergeQueueEntry{position state}}` (`null` = not queued; non-null shape untested) ([GraphQL](../learnings/1791705807345-merge-queue-membership-check-use-graphql-pullreque.md)). `statusCheckRollup` shows WAITING gates (`falcor-build-approval-gate`) that `gh pr checks` omits and mixes check-runs (`.name`) with statuses (`.context`): null-guard `.name` in jq `test()` ([rollup](../learnings/1791267800558-gh-pr-view-json-has-no-mergequeueentry-field-use-g.md)). `gh issue view N --json authorAssociation` fails the same way; read COLLABORATOR vs CONTRIBUTOR (triage skip rule) via `gh api repos/O/R/issues/N --jq .author_association`. `--json issueType,closedByPullRequestsReferences` works, a cheap drift check ([authorAssociation](../learnings/1793639840678-gh-issue-view-json-has-no-authorassociation-use-gh.md)).

## A Detached Build's Exit 0 and a pwsh Step's Success

**A detached launcher's exit code describes the launcher.** With `setsid nohup cmake --build … &`, "Background command completed (exit code 0)" is the wrapper exiting: on slang#12371 two builds reported exit 0 while `libslang-compiler.so` was older than its input `.o` and lacked the PR's new diagnostic, and `pgrep -af ninja` showed both racing in one ninja directory. Wait on the real process (`until ! pgrep -f ninja; do sleep 20; done`), never start a second `cmake --build` on a live ninja dir, and verify **behaviourally** by grepping the artifact for a commit-introduced string (timestamps and version strings cannot tell "not built" from "built without your change"). After a dependency merges, rebuild staged `.slang-module` inputs too, or the run is mixed-binary ([wrapper](../learnings/1785988615115-setsid-run-in-background-makes-exit-code-0-report-.md)).

**A Windows `pwsh` step's success is its last native command's exit code:** Actions wraps the block with `$ErrorActionPreference='stop'` and `exit $LASTEXITCODE`, but a native non-zero exit does not stop it. In slangpy's `build-and-test-with-slang/action.yml:99-103` (`git clone; git fetch <ref>; git checkout FETCH_HEAD; …`) a vanished merge-queue ref failed Linux (bash `-e`) while Windows logged `fatal: couldn't find remote ref`, built the default branch, and went green. Check `$LASTEXITCODE` after each native call or set `$PSNativeCommandUseErrorActionPreference = $true` (pwsh 7.4+); find past cases by grepping `success` job logs for `error: pathspec 'FETCH_HEAD'` ([pwsh](../learnings/1791418811630-github-actions-pwsh-run-blocks-hide-failed-git-com.md)).

## Reading Fresh CI Data: Truncation, Stale Listings, and the Gateway Cache

- **WebFetch cannot read `health_snapshots.jsonl`** (slang-ci-analytics): it truncated, showed a March line as latest, then hit its 10 MB cap. Use `curl -s --max-time 30 <raw-url> | tail -1` and check the `timestamp` is same-day; its `merge_queue` and `hosted_runner_usage` beat the Actions failure API as a live proxy ([curl|tail](../learnings/1789546707009-ci-health-snapshot-use-curl-tail-not-webfetch-on-h.md)). `status.html` is no substitute (JS-rendered "All Systems Operational", no numeric queue counts): record the gap under "Data Collection Notes" rather than invent numbers ([10 MB](../learnings/1790065065697-ci-health-snapshots-jsonl-exceeds-webfetch-10mb-li.md)).
- **A `status=failure` listing can silently return only stale rows**: anonymous `actions/runs?status=failure` and `gh run list --branch master --status failure --limit 30` returned nothing after dates with known failing nightlies, while REST with `created=%3E%3D<date>&per_page=50` returned 39. Tell: the newest row is days older than master's head; bound with `created>=`. Separately, size an MDL perf flag from `confirmation.json` `plan.regressions` (1.12x), not the analyze log's first table (1.58x) ([stale listing](../learnings/1791360225685-gh-run-list-status-failure-can-silently-return-sta.md)). `created>=` misses a `waiting` run (e.g. bot-draft CI at an approval gate) that hits the 30-day limit and ends `failure` with an old `created_at`: diff yesterday's `status=waiting` list against today's and fetch each departure (8 of 14 were expiries) ([expiry](../learnings/1792830160449-github-actions-30-day-waiting-run-expiry-shows-as-.md)).
- **The egress gateway caches GitHub REST GETs keyed on the literal query string**: an un-busted URL returned two-week-old failures; `&_=$(date +%s%N)` returns fresh data (GitHub ignores unknown params). That was the recurring "workflow-failures stale-date" heartbeat anomaly ([cache](../learnings/1789391780211-root-cause-of-the-recurring-slang-workflow-failure.md)).
