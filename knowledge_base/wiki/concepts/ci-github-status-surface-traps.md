# GitHub CI Status-Surface Traps — Combined Status, Evicted Lists & Detached Builds

Every reading on this page is a status *surface* that returns a well-formed, plausible answer to a different question than the one you asked. The unifying test: **what would this output look like if the thing were absent, or if nothing ran?** If the answer is "the same", it is not a measurement.

## TL;DR

- **Never derive CI health from `GET /repos/{o}/{r}/commits/{sha}/status`.** The combined status is wrong in **both** directions: `SUCCESS` with **zero CI runs** (a review-bot context alone satisfies it), and `pending` over 43 green check-runs (one foreign context stuck 85 h) — which can time a green PR out of the merge queue. Read `check-runs` and `statuses` **separately**.
- **`SlangPy Tests` reds are cross-repo commit statuses** from a `repository_dispatch` run in **shader-slang/slangpy** — never in `check-runs`, unrerunnable past 1-month retention. On an *active* bot PR the red is usually **version skew** (branch BEHIND master after a cross-repo breaking change): check `mergeState`, rebase. A green `ci-slangpy-trigger-test.yml` means only the dispatch fired. After a slangpy fix, re-dispatch (a rerun replays the old slangpy tree), and check the newest slangpy run before calling a red real.
- **`conclusion=action_required` is an approval GATE, not a failure** — a fifth state. Zero jobs ran, rerun is refused, and check-runs and rollup contexts never see it; only the check *suite* and `/actions/runs?head_sha=<full sha>` do. Count only `event == pull_request` runs of the CI workflow. Once approved, `run_attempt` is 2 and `triggering_actor` names the approver.
- **A job that fails BY DESIGN tops your infra-failure ranking** (`wait-for-human-priority` is a throttle). Read the workflow before ranking any leg; rerunning it defeats the throttle.
- **An attempt ladder measures dispatch, not coverage** — report WHERE in the job graph each attempt died.
- **`reviews(last:10)` is a page, not a population; a missing tool can emit a plausible datum.** Assert `totalCount == (nodes|length)` for any GraphQL connection you count.
- **One invalid field in `gh … --json a,b,c` aborts the WHOLE query.** `mergeQueueEntry` is GraphQL-only: `gh pr view --json` for state and rollup, `gh api graphql` for queue membership (`null` = not queued).
- **A wake payload's `evicted` list is wrong in both directions (measured 0-for-5).** Only `RemovedFromMergeQueueEvent` records an eviction; a red job is a fact about a *run*. Reject any blamed run started after the enqueue.
- **Read a `failed_checks` eviction's cause from the merge-group run's failed jobs** (`gh-readonly-queue/master/pr-<N>-<sha>`), never the PR head's rollup: head-only checks like `check-pr-label` don't run in the group.
- **Merge-queue evictions can be commit-status-only, and the payload never lists them.** Read the merge-group commit's `status` as well as check-runs and follow `target_url`; a green head `check-ci` does not mean resolved, and the eviction clears auto-merge. `failed_checks` = something required went red; `checks_timed_out` = the group hit 2 h with a required check still running.
- **Green CI runs can hide a frozen merge queue.** A stuck queue produces no failed runs, so also gate a health scan on weekday master head age (> ~6 h) and on `status` + `check-runs` of every `gh-readonly-queue/master` ref.
- **A detached launcher's completion notification describes the launcher, not the work.** Wait on the real process (`pgrep -f ninja`) and verify a build **behaviourally** (grep the artifact for a commit-introduced string).
- **A Windows `pwsh` step's `success` is the exit code of its LAST native command** — a failed `git fetch` mid-block can build the default branch and go green.
- **CI listings go stale silently**: `gh run list --status failure` can be days old, a 30-day-expired `waiting` run escapes a `created>=` query, an un-busted REST GET hits the gateway cache, and WebFetch truncates big JSONL. Bound with `created>=`, cache-bust, `curl | tail -1`.

## A Wake Payload's `evicted` List Is Not a Measurement

Against 93 PRs over ~24 h the CI-babysitter wake payload was **0-for-5: 1 false positive, 4 false negatives**. It named #12357, which had no `RemovedFromMergeQueueEvent` and whose blamed run started 16 min after the enqueue, and missed #12252, #12353, #12363, #12365 ([wake payload evicted list measured 0-for-5](../learnings/1785990268683-wake-payload-evicted-list-measured-0-for-5-enumera.md), [a payload can report an eviction that never happened](../learnings/1785989687956-wake-payload-can-report-an-eviction-that-never-hap.md)). A false positive is **a failing job inside an in-flight merge-group run** — a red job is a fact about a *run*, and a red non-required check evicts nobody. A miss is the mirror image: the PR's own head checks stay green after an eviction, so a head-sha sweep never sees it. Enumerate per PR every sweep (~90 calls) and diff the payload against it (`memory/derive-evictions-from-github.sh <date>`):

```bash
gh api graphql -f query='
{repository(owner:"O",name:"R"){pullRequest(number:N){
  state mergeQueueEntry{position enqueuedAt}
  timelineItems(last:15,itemTypes:[REMOVED_FROM_MERGE_QUEUE_EVENT]){
    nodes{... on RemovedFromMergeQueueEvent{createdAt reason beforeCommit{oid}}}}}}}'
```

Empty node list ⇒ log `action:"left"` and stop; `merged` is not an eviction. **`failed_checks`**: a required check-run *or status* went red. **`checks_timed_out`**: the group sat 2 h with a required check not yet green — #13479 was removed at +2h00m09s, 22 s after its slowest required job (`build-macos-release-clang-aarch64`, a cold LLVM build) finished, so look for a ceiling-bound job, not a red one ([checks_timed_out = the group ran 2 h](../learnings/1791484800264-merge-queue-eviction-reason-checks-timed-out-group.md)). Attribute cause from `beforeCommit.oid`, **reject any run whose `run_started_at` postdates the event or enqueue** (this catches the whole false-positive class), check the blamed job against `check-ci`'s `needs`, and re-read the live `headRefOid` before a head-keyed verdict. A `conclusion: cancelled` entry can be a superseded attempt cancelled by the 120-min ceiling on non-required windows-aarch64 jobs ([payload evicted can be stale; status-only evictions](../learnings/1791469815689-merge-queue-sweeps-payload-evicted-can-be-stale-an.md)). Calibration: 3 of the 4 misses self-recovered; a false positive costs a requeue of a healthy entry.

**Read a `failed_checks` cause from the merge-group run, not the PR head's rollup:** list `actions/runs?event=merge_group&created=<range>`, match `head_branch` `gh-readonly-queue/master/pr-<N>-<sha>`, and list its `jobs?filter=latest` failures. Head-only checks such as `check-pr-label` never run there: a sweep blamed #13764 on its red `check-pr-label`, but the group run had 11 `test-slang` jobs failing on a test conflict with #13647. Settle disagreeing parallel sweeps with that query before reporting ([eviction cause: read the merge-group run's failed jobs](../learnings/1792660635041-merge-queue-eviction-cause-read-the-merge-group-ru.md)).

**Status-only evictions.** The required cross-repo status `SlangPy Tests` can go red on the merge-group commit while every check-run is green — a `failed_checks` eviction the payload (failed *runs* only) never sees. Read both `commits/<merge-group-sha>/check-runs` and `/statuses`, follow `target_url`, and read the slangpy log before calling it infra; the eviction clears auto-merge (`autoMergeRequest: null`), so the PR sits until re-queued ([Merge-queue eviction cause: check commit statuses, not just workflow runs](../learnings/1793028963721-merge-queue-eviction-cause-check-commit-statuses-n.md)). Red statuses persist on PR heads until a re-push or re-dispatch, and a green head `check-ci` proves nothing (#13626 was wrongly logged `resolved`). Causes so far are all slangpy-side: slangpy #1199 set `SGL_MAX_CUDA_COMPUTE_CAPABILITY=90` in `ci.yml` but not `ci-latest-slang.yml` (6 CUDA ray-tracing failures on every Slang PR for ~9 h, slangpy#1214, fixed by #1215), a `test_profiler.cpp` GPU-query-exhaustion bug (slangpy#1223), and a Windows `sgl_tests` profiler flake on #13283 (`gpu_zones->count()` 0 vs 4) ([SlangPy Tests status evicts while payload evicted=[]](../learnings/1791462232939-slangpy-tests-commit-status-can-evict-from-merge-q.md), [status-only evictions: check the merge-group /status](../learnings/1791490613888-commit-status-only-merge-queue-evictions-payload-r.md), [status-only eviction of #13626](../learnings/1792039063028-payload-evicted-list-misses-status-only-evictions-.md), [eviction from the SlangPy Tests status, #13283](../learnings/1792226879052-slang-merge-queue-eviction-can-come-from-the-slang.md)). Flag trap: `-c` is not a `gh api` flag (`gh api … --jq … -c` prints ~7 KB of help).

**Find the slangpy run behind the status:** list `shader-slang/slangpy/actions/runs?created=>=<window>` and take the `repository_dispatch` run `Slang PR #<N>: <title> (<author>)` whose end time matches the removal (`SlangPy Tests` is required, `app_id` null). On 10-23 both evictions matched within 30 s while the PRs' own `merge_group` runs went `success`: #13886 to a Linux `build-pr` runner loss (no failed step, 404 log), #13665 to a Windows `sgl_tests` teardown error after all 284 doctest cases passed ([eviction with green merge_group CI: match the slangpy `Slang PR #N` run](../learnings/1792830200492-slang-merge-queue-eviction-with-green-merge-group-.md), [same two 10-23 matches; 30-day waiting-run expiry](../learnings/1792830160449-github-actions-30-day-waiting-run-expiry-shows-as-.md)).

**The largest case froze slang master** for ~16 h (10-29/30, slangpy#1250): nodejs.org listed `v27.0.0-alpha.0.0.0` first and the nodeenv < 1.11.1 that pyright-python uses on PATH-less self-hosted runners crashed (`int() … '0-alpha'`), so every `Slang PR #N` dispatch failed and #13918, #13855, #14052, #13848 were evicted with green group `CI` (fix on [slangpy-ci-triage](slangpy-ci-triage.md)). Grep a slangpy job log for `0-alpha` / `nodeenv`; job-log URLs ignore suffix ranges (`bytes=-N` returns everything), so send `bytes=0-0`, read `Content-Range`, and request an explicit tail. REST to non-shader-slang repos 401s through OneCLI; GraphQL works ([pyright/nodeenv break evicts slang merge-queue PRs via SlangPy Tests](../learnings/1793349389191-slangpy-pyright-nodeenv-break-evicts-slang-merge-q.md)). Health scans read "master clean" throughout — a stuck queue produces no failed runs — so the scheduled task's prompt or script (not a per-session note) carries two probes: weekday master head age > ~6 h, and `status` + `check-runs` on every `git/matching-refs/heads/gh-readonly-queue/master` ref ([green CI runs can hide a stuck merge queue](../learnings/1793376411569-green-ci-runs-can-hide-a-stuck-merge-queue-check-c.md)).

## The Combined Status and the Cross-Repo `SlangPy Tests` Status

**The combined commit status is wrong in both directions.** On one day it was **too optimistic** on #11475 (`SUCCESS` with **zero CI runs**: a review bot's context set the `state`) and **too pessimistic** on #12389 (`pending` over 43 green check-runs: `SlangPy Tests` stuck 85 h); #12309 was evicted with 45/45 green and `checks_timed_out`. Read `check-runs` and `statuses` separately ([GitHub's combined commit status fails in BOTH directions](../learnings/1786350644910-github-s-combined-commit-status-fails-in-both-dire.md)). Only the review-bot mechanism was new — **grep your own leaves by identifier before claiming novelty**; a novelty claim relayed upward is expensive to walk back ([SCOPE CORRECTION: the zero-run/green find was two-thirds already stored](../learnings/1786321155140-scope-correction-the-zero-run-green-find-was-two-t.md)).

**`SlangPy Tests` is a status posted from an `event=repository_dispatch` run in shader-slang/slangpy**, invisible to `gh pr checks` and check-run enumeration. Read `statuses`, follow `target_url`, and rerun there (`gh run rerun <id> --repo shader-slang/slangpy`); on old PRs past 1-month retention they are dead ends — "non-actionable, stale cross-repo status" ([SlangPy Tests reds are CROSS-REPO COMMIT STATUSES](../learnings/1786335485075-slangpy-tests-reds-on-shader-slang-slang-are-cross.md)). A green `ci-slangpy-trigger-test.yml -f pr_number=N` (~1 min) only means it posted `pending` and fired `repository_dispatch`; the result is slangpy's `ci-latest-slang.yml` run "Slang PR #N: …" (~30 min, linux + windows): `gh run list -R shader-slang/slangpy --workflow ci-latest-slang.yml --limit 4`, then `gh run view <id> -R shader-slang/slangpy --log-failed | grep 'FAILED slangpy'`. Draft and bot PRs skip the trigger (`pull_request_target` gated on `draft != true`) and need an explicit dispatch ([the trigger's success is only the dispatch](../learnings/1791510877884-ci-slangpy-trigger-test-yml-success-is-only-the-di.md)).

**After a slangpy-side fix, re-dispatch from slang instead of rerunning:** a `repository_dispatch` run's `GITHUB_SHA` is slangpy's head at dispatch time, so `gh run rerun` replays the pre-fix tree (inferred, untested). `gh workflow run ci-slangpy-trigger-test.yml --repo shader-slang/slang -f pr_number=N` reads the PR's current head and starts a new run ~30 s later; its frequent HTTP 500s create no run, so retry with backoff. Canary one PR and wait for BOTH Linux and Windows `build-pr` (some Linux runners passed with slangpy#1250 present); `gh run view --log` is empty until the run ends (the per-job logs API still works, per [slangpy-ci-triage](slangpy-ci-triage.md)), and tight polls burn the shared token ([re-dispatch SlangPy Tests from the Slang side](../learnings/1793370651623-re-triggering-slangpy-tests-after-an-upstream-slan.md)). **A red whose `target_url` names an OLDER run can be stale** — it can overwrite the newer run's `pending` until that run ends (#13855 red, then SUCCESS) — so check the newest `repository_dispatch` run first. `SlangPy tests abandoned` = a `build-pr` matrix job that never appeared (infra drop, not a test failure). In failed logs grep `short test summary` / `FAILED `; `Hot reload failed` / `error[E…]` lines are tests that break shaders on purpose ([stale red SlangPy Tests; `abandoned` = dropped matrix job](../learnings/1793376826751-red-slangpy-tests-whose-target-url-is-an-older-run.md)).

**On an active bot PR, a red `SlangPy Tests` is usually version skew — check `mergeState` first.** The integration builds the PR's slang commit against **slangpy main**, so a branch `BEHIND` master after a coordinated breaking change fails though both mains are correct: slang #12986 added `enum MatrixLayoutMode`, slangpy #1135 used it, and six un-rebased bot PRs hit `error[E30015]: undefined identifier 'MatrixLayoutMode'`. Rebase; there is no issue to file. Confirm a "symbol removed" theory with `git log -S <symbol>` before relaying it — the first read here was exactly inverted ([cross-repo integration red on a bot PR is usually version skew](../learnings/1789151785364-cross-repo-integration-ci-red-on-a-bot-pr-is-usual.md)).

## `action_required` Is an Approval Gate the Checks API Cannot See

Lumping `action_required` with `failure|timed_out|startup_failure` inflates the red count: an approval (fork PRs, "Approve and run workflows") was never granted, so **the run never started** — on #11448 `attempts/1/jobs` → `total_count=0`, and `gh run rerun --failed` is refused. Bucket it as a fifth state, "needs a maintainer to authorize" ([conclusion=action_required is an approval GATE](../learnings/1786327920887-github-actions-conclusion-action-required-is-an-ap.md)).

The held workflow creates no check-run, so it is absent from REST `check-runs`/`status` **and** GraphQL `statusCheckRollup.contexts`, whose `state` reflects only what ran (`SUCCESS` on #13218; `FAILURE` if a lone non-CI `review` check is red — see [query confidence](ci-github-query-confidence-and-gates.md)). Only the suite layer shows it: `/actions/runs?head_sha=<full 40-char sha>` (an abbreviated sha silently returns `total_count:0`) or GraphQL `commit.checkSuites` with conclusion `ACTION_REQUIRED`. The axis is **check-run vs suite/run level, not REST vs GraphQL**: the babysitter's `splitExclusions` fix (#12544) read `action_required` off check-runs, so it could never fire and missed the #13218 wedge it was written for. Filter to `event == pull_request` and the CI workflow (`CI` on slang, `ci` on slangpy and slang-rhi; for suites read `workflowRun{event workflow{name}}`) and dedup by name+highest-id: sibling review/`_target` runs such as `ClaudeCode - SlangPy/Slang-RHI Assistant` sit at `action_required` on fork PRs even after CI ran, which inflated a 10-25 "CI never approved" count to 3 of 7 and 3 of 5 (true: 2 and 2) ([Fork-PR "CI never approved" count: filter checkSuites to event == pull_request](../learnings/1793003118714-fork-pr-ci-never-approved-count-filter-checksuites.md)). A tail-scan that first filters `rollup !== 'SUCCESS'` excludes this class outright, and a tracker that only touches PRs in the current payload lets a zero-check-run wedge age out of every surface ([action_required wedges are invisible to the Checks API](../learnings/1790080487638-action-required-workflow-approval-wedges-are-invis.md), [a check-runs-fed action_required classifier is dead code](../learnings/1790079172299-ci-babysitter-action-required-fix-2026-09-22-12544.md)).

**Who approved a held run:** it is neither a review nor a timeline event — `gh api repos/O/R/actions/runs/<id> --jq '.run_attempt, .triggering_actor.login, .run_started_at'`. After approval `run_attempt` is 2, `triggering_actor` is the approving maintainer and `actor` is still the contributor (slangpy#1234) ([Who approved an action_required fork CI run: triggering_actor on run_attempt 2](../learnings/1793026171832-who-approved-an-action-required-fork-ci-run-trigge.md)).

## Failure Rankings and Attempt Ladders Measure the Wrong Thing

**A job that fails by design tops the ranking.** Across 61 `ci.yml` runs the top failing leg was `wait-for-human-priority` (11 hits, 5 PRs) — a **priority throttle**: when a bot's draft dispatch must yield to human, merge-queue or older CI, a marker step fails it so it holds no build/test runners, and a companion workflow reruns it later. It is never `skipped`, because a skipped dependency would collide with the build jobs' implicit `success()` gating. Ranking it is a false #1 infra signature; rerunning it burns the runners it protects. Read a leg's workflow before ranking it ([a CI job that fails BY DESIGN will top your infra-failure ranking](../learnings/1786350256938-a-ci-job-that-fails-by-design-will-top-your-infra-.md)).

**An attempt ladder says a run was rerun, not that the remedy was attempted.** `att1 FAILURE, att2 FAILURE, att3 waiting … env=falcor-ci` looked like two tries at the obvious remedy, but both died at `wait-for-human-priority` in ~10 s with all 38 downstream jobs `skipped` — the falcor gate was never reached. Report **where in the job graph each attempt died** ([an attempt ladder tells you a run was reran, not that the remedy was attempted](../learnings/1786336411679-an-attempt-ladder-tells-you-a-run-was-reran-not-th.md)).

## Query Traps That Return a Believable Wrong Answer

**A bounded page is not a population.** A published "9 reviews on #12354" from `reviews(last:10)` was really 12, and a third PR was missed. Assert `totalCount == (nodes|length)` and `--paginate` when they differ. A **missing tool can emit a plausible datum** in the same undetectable way ([a bounded page is not a population](../learnings/1786330741949-a-bounded-page-last-n-first-100-is-not-a-populatio.md)).

**One invalid field in `gh … --json` aborts the whole query.** `gh pr view N --json reviewDecision,…,mergeQueueEntry` exits 1 with `Unknown JSON field: "mergeQueueEntry"` and prints none of the valid fields: the field exists in GraphQL but not in `gh pr view`'s allowlist ([one invalid field in `gh --json` aborts the whole query](../learnings/1786336024283-one-invalid-field-in-gh-json-a-b-c-aborts-the-whol.md)). In a bulk loop it is silent: twice the babysitter's idempotency loop got empty fields for every PR, which reads like auth trouble. Validate a new field in isolation, never swallow a non-zero exit, and run one call bare (`2>&1 | head`) before debugging credentials. Use `gh pr view --json state,isDraft,mergeStateStatus,headRefOid,statusCheckRollup` plus `gh api graphql -f query='{repository(owner:"O",name:"R"){pullRequest(number:N){state mergeQueueEntry{position state}}}}'` for queue membership (`null` = not queued; the non-null shape is untested) ([GraphQL mergeQueueEntry works for the idempotency check](../learnings/1791705807345-merge-queue-membership-check-use-graphql-pullreque.md)). `statusCheckRollup` also shows WAITING gates such as `falcor-build-approval-gate` that `gh pr checks` omits; it mixes check-runs (`.name/.conclusion`) and legacy statuses (`.context/.state`), so null-guard `.name` in jq `test()` ([gh pr view --json has no mergeQueueEntry field](../learnings/1791267800558-gh-pr-view-json-has-no-mergequeueentry-field-use-g.md)).

## A Detached Build's Exit 0 and a pwsh Step's Success

**A detached launcher's exit code describes the launcher.** With `setsid nohup cmake --build … &`, the harness's "Background command completed (exit code 0)" is the wrapper exiting. On slang#12371 two such builds reported exit 0 while `libslang-compiler.so` was older than its own input `slang-emit.cpp.o` and lacked the merged PR's new diagnostic; `pgrep -af ninja` showed both still racing in one ninja directory, and the `.so` relinked ten minutes later. Wait on the real process (`until ! pgrep -f ninja; do sleep 20; done`), never start a second `cmake --build` against a live ninja directory, and verify **behaviourally** — grep the artifact for a string the commit introduced; timestamps cannot tell "not built yet" from "built without your change", and version strings are configure-time. After a dependency merges, rebuild staged `.slang-module` inputs too, or the run is mixed-binary ([setsid + run_in_background makes exit code 0 report the wrapper](../learnings/1785988615115-setsid-run-in-background-makes-exit-code-0-report-.md)).

**A Windows `pwsh` step's success is its last native command's exit code.** Actions wraps the block with `$ErrorActionPreference='stop'` and `exit $LASTEXITCODE`, but a native non-zero exit does not stop it. In slangpy's `build-and-test-with-slang/action.yml:99-103` (`git clone; git fetch <ref>; git checkout FETCH_HEAD; git submodule update`) a vanished merge-queue ref failed the Linux leg (bash `-e`) correctly, while the Windows leg logged `fatal: couldn't find remote ref`, built and tested the default branch, and went green. Check `$LASTEXITCODE` after each native call or set `$PSNativeCommandUseErrorActionPreference = $true` (pwsh 7.4+); find past cases by grepping `success` job logs for `error: pathspec 'FETCH_HEAD'` ([GitHub Actions pwsh run blocks hide failed git commands except the last one](../learnings/1791418811630-github-actions-pwsh-run-blocks-hide-failed-git-com.md)).

## Reading Fresh CI Data: Truncation, Stale Listings, and the Gateway Cache

- **WebFetch cannot read `health_snapshots.jsonl`** (`raw.githubusercontent.com/shader-slang/slang-ci-analytics/main/health_snapshots.jsonl`, ~8k appended polls): it truncated and presented a March line as latest when the truth was September, then failed hard at its 10 MB cap. Use `curl -s --max-time 30 <raw-url> | tail -1` and check the line's `timestamp` is same-day; its `merge_queue` and `hosted_runner_usage` are a better live CI-failure proxy than the Actions failure API ([CI health snapshot: use curl|tail, not WebFetch](../learnings/1789546707009-ci-health-snapshot-use-curl-tail-not-webfetch-on-h.md)). `status.html` is no substitute — JS-rendered "All Systems Operational" with no numeric queue counts — so record the gap under "Data Collection Notes" rather than invent numbers ([health_snapshots.jsonl also exceeds WebFetch's 10 MB cap](../learnings/1790065065697-ci-health-snapshots-jsonl-exceeds-webfetch-10mb-li.md)).
- **A `status=failure` listing can return only stale rows, with no error** — both anonymous `actions/runs?status=failure` and authenticated `gh run list --branch master --status failure --limit 30` returned nothing after dates with known failing nightlies, while `gh api "repos/O/R/actions/runs?branch=master&status=failure&created=%3E%3D<date>&per_page=50"` returned 39. The tell is a newest row days older than master's head; bound with `created>=` and take the live picture from the snapshot's `merge_queue`. Same session: size an MDL perf flag from `perf-confirmation-<run>-1` → `confirmation.json` `plan.regressions` (1.12x), not the analyze log's first table (1.58x) ([gh run list --status failure can silently return stale results](../learnings/1791360225685-gh-run-list-status-failure-can-silently-return-sta.md)). `created>=` has its own blind spot: a `waiting` run (e.g. bot-draft CI at an approval gate) that hits the 30-day limit ends `failure` with an old `created_at`, so diff yesterday's `status=waiting` list against today's and fetch each departure (10-24: 8 of 14 departures were expiries) ([30-day waiting-run expiry shows as failure on old created_at](../learnings/1792830160449-github-actions-30-day-waiting-run-expiry-shows-as-.md)).
- **The egress gateway caches GitHub REST GETs keyed on the literal query string**: an un-busted URL kept returning two-week-old failures, while appending `&_=$(date +%s%N)` returned fresh data (GitHub ignores unknown params). This is the recurring "workflow-failures stale-date" heartbeat anomaly — the precheck script's curls don't cache-bust ([un-busted query gets a cached gateway response](../learnings/1789391780211-root-cause-of-the-recurring-slang-workflow-failure.md)).
