# GitHub CI Status-Surface Traps — Combined Status, Evicted Lists & Detached Builds

Each reading here is a status *surface* giving a plausible answer to a different question than the one asked. The unifying test: **what would this output look like if the thing were absent, or if nothing ran?** If the answer is "the same", it is not a measurement.

## TL;DR

- **Never derive CI health from the combined `commits/{sha}/status`**: it reads `SUCCESS` with **zero CI runs** (a review-bot context) and `pending` over 43 green check-runs. Read `check-runs` and `statuses` **separately**.
- **`SlangPy Tests` is a cross-repo commit status** from a slangpy `repository_dispatch` run: never in `check-runs`. A red on a bot PR is usually **version skew** (BEHIND master): rebase. A green trigger means only the dispatch fired; after a slangpy fix re-dispatch (a rerun replays the old tree).
- **A MISSING `SlangPy Tests` status** (only `license/cla`) after a `pull_request_target` `startup_failure` blocks a PR forever: dispatch `ci-slangpy-trigger-test.yml -f pr_number=N`. A merge-group `pending` > ~30 min with a failed `trigger-slangpy-tests` job has no run behind it: re-enqueue. A head run titled `[with SlangPy #N]` built the paired slangpy PR; the queue builds slangpy main, so that PR merges first.
- **Zero-job `startup_failure` runs, all `pull_request_target`, in one time block = GitHub's policy brownout** (enforced **2026-12-02**), not YAML or runners; `status=failure` lists omit them.
- **`action_required` is an approval GATE** (fifth state): zero jobs, rerun refused, visible only at the suite layer (`/actions/runs?head_sha=<full sha>`). Count only `event == pull_request` CI runs. Approval does not survive an author push; a held suite can vanish unapproved.
- **A job that fails BY DESIGN tops failure rankings** (`wait-for-human-priority` is a throttle). **An attempt ladder measures dispatch, not coverage**: report where each attempt died.
- **A page is not a population**: assert `totalCount == (nodes|length)`. **One invalid `gh --json` field aborts the query** (`mergeQueueEntry` is GraphQL-only, `null` = not queued; `gh issue view` has no `authorAssociation`).
- **A wake payload's `evicted` list is wrong both ways (0-for-5)**: only `RemovedFromMergeQueueEvent` records an eviction; reject any blamed run started after the enqueue.
- **Read a `failed_checks` cause from the merge-group run's failed jobs AND commit `status`**, never the head rollup; status-only evictions never reach the payload and clear auto-merge. `checks_timed_out` = the group hit 2 h.
- **Green CI runs can hide a frozen queue**: probe master head age (> ~6 h on weekdays) and each `gh-readonly-queue/master` ref.
- **A detached launcher's exit 0 describes the launcher**: wait on `pgrep -f ninja`; verify builds **behaviourally** (grep the artifact for a commit-introduced string). **A Windows `pwsh` step's `success` is its LAST native command's exit code.**
- **CI listings go stale silently** (`--status failure`, 30-day-expired `waiting` runs, gateway-cached REST GETs, WebFetch truncation): bound with `created>=`, cache-bust, `curl | tail -1`.

## A Wake Payload's `evicted` List Is Not a Measurement

Over 93 PRs in ~24 h the wake payload was **0-for-5**: it named #12357 (no `RemovedFromMergeQueueEvent`; blamed run started 16 min after enqueue) and missed four evictions ([0-for-5](../learnings/1785990268683-wake-payload-evicted-list-measured-0-for-5-enumera.md), [phantom](../learnings/1785989687956-wake-payload-can-report-an-eviction-that-never-hap.md)). A red check in the PR's own group does not by itself evict (#13848's group failed `check-ci` yet merged with the next group): count only `RemovedFromMergeQueueEvent` with `reason != merged` ([timeline](../learnings/1793436218667-daily-github-sweep-closed-unmerged-prs-and-merge-q.md); cases on [ASan & merge-group cases](ci-flake-asan-and-merge-group-cases.md)). Head checks stay green after an eviction, so every sweep enumerates per PR via GraphQL `pullRequest{state mergeQueueEntry{position enqueuedAt} timelineItems(last:15,itemTypes:[REMOVED_FROM_MERGE_QUEUE_EVENT]){nodes{... on RemovedFromMergeQueueEvent{createdAt reason beforeCommit{oid}}}}}` and diffs the payload.

Empty node list ⇒ log `action:"left"` and stop. `failed_checks` = a required check-run *or status* went red; `checks_timed_out` = the group sat 2 h with a required check not yet green, so look for a ceiling-bound job, not a red one (#13479 left 22 s after its cold-LLVM macOS build finished) ([timed out](../learnings/1791484800264-merge-queue-eviction-reason-checks-timed-out-group.md)). Attribute cause from `beforeCommit.oid`; **reject any run whose `run_started_at` postdates the event or enqueue** (the whole false-positive class); check the blamed job against `check-ci`'s `needs`; re-read the live `headRefOid` first. A `cancelled` entry can be a superseded attempt hit by the 120-min ceiling on non-required windows-aarch64 jobs ([stale payload](../learnings/1791469815689-merge-queue-sweeps-payload-evicted-can-be-stale-an.md)).

**Read a `failed_checks` cause from the merge-group run, not the head rollup:** `actions/runs?event=merge_group&created=<range>`, match `head_branch` `gh-readonly-queue/master/pr-<N>-<sha>`, read its `jobs?filter=latest` failures. #13764 was blamed on a head-only red `check-pr-label`; its group run had 11 `test-slang` jobs failing on a conflict with another PR ([group run](../learnings/1792660635041-merge-queue-eviction-cause-read-the-merge-group-ru.md)).

**Status-only evictions.** The required `SlangPy Tests` status can go red on the merge-group commit with every check-run green, invisible to the payload (failed *runs* only). Read `commits/<merge-group-sha>/check-runs` and `/statuses`, follow `target_url`, read the slangpy log before calling it infra; the eviction clears auto-merge, so the PR sits until re-queued ([statuses](../learnings/1793028963721-merge-queue-eviction-cause-check-commit-statuses-n.md)). The merge-group sha is the event's `beforeCommit` or the `gh-readonly-queue/master/pr-N-*` head ([read its `/status`](../learnings/1794301164235-slang-mq-failed-checks-can-come-from-the-slangpy-t.md)). **A head run titled `[with SlangPy #N]` built the paired slangpy PR**; the merge-group dispatch builds slangpy main, so slang #13885 was evicted on two slangpy failures (`test_specialize_interface_function`). Merge the slangpy PR first ([paired slangpy PR](../learnings/1794300436417-slang-mq-eviction-via-slangpy-tests-when-a-pr-is-p.md)). Red statuses persist on heads until re-push or re-dispatch; a green head `check-ci` proves nothing (#13626 was wrongly logged `resolved`). Causes so far are slangpy-side: a CUDA cap only in `ci.yml` (slangpy#1214), a profiler GPU-query exhaustion (slangpy#1223), a Windows `sgl_tests` profiler flake (#13283) ([slangpy#1214](../learnings/1791462232939-slangpy-tests-commit-status-can-evict-from-merge-q.md), [/status](../learnings/1791490613888-commit-status-only-merge-queue-evictions-payload-r.md), [#13626](../learnings/1792039063028-payload-evicted-list-misses-status-only-evictions-.md), [#13283](../learnings/1792226879052-slang-merge-queue-eviction-can-come-from-the-slang.md)). `-c` is not a `gh api` flag.

**Find the slangpy run behind the status:** in `shader-slang/slangpy/actions/runs?created=>=<window>`, the `repository_dispatch` run `Slang PR #<N>: <title> (<author>)` whose end time matches the removal. Two 10-23 evictions with `success` group runs matched within 30 s: #13886 (Linux runner loss), #13665 (Windows `sgl_tests` teardown error) ([match run](../learnings/1792830200492-slang-merge-queue-eviction-with-green-merge-group-.md), [expiry](../learnings/1792830160449-github-actions-30-day-waiting-run-expiry-shows-as-.md)).

**A `pending` with no slangpy run behind it never resolves.** `trigger-slangpy-tests` posts pending before firing the dispatch. On 11-05 (#14110) "Post pending status" got HTTP 500 yet the pending was recorded; later steps skipped and the entry timed out. Tell: `trigger-slangpy-tests` = `failure` in `actions/runs/<run>/jobs`. A job rerun hit the same 500; dequeue + re-enqueue for a fresh SHA. Healthy pendings clear in ~30 min ([HTTP 500](../learnings/1793909119749-merge-queue-slangpy-tests-can-stick-pending-when-t.md)).

**The largest case froze slang master ~16 h** (slangpy#1250): nodejs.org listed `v27.0.0-alpha.0.0.0` first, nodeenv < 1.11.1 (pyright-python) crashed on `int() … '0-alpha'`, and every `Slang PR #N` dispatch failed, evicting four PRs with green group `CI` (fix on [slangpy-ci-triage](slangpy-ci-triage.md)). Grep logs for `0-alpha` / `nodeenv`. Job-log URLs ignore suffix ranges: send `bytes=0-0`, read `Content-Range`, request an explicit tail. REST to non-shader-slang repos 401s through OneCLI; GraphQL works ([nodeenv](../learnings/1793349389191-slangpy-pyright-nodeenv-break-evicts-slang-merge-q.md)). A stuck queue produces no failed runs, so the health task also probes weekday master head age > ~6 h and `status` + `check-runs` on each `git/matching-refs/heads/gh-readonly-queue/master` ref ([stuck queue](../learnings/1793376411569-green-ci-runs-can-hide-a-stuck-merge-queue-check-c.md)).

## The Combined Status and the Cross-Repo `SlangPy Tests` Status

**The combined commit status is wrong both ways:** `SUCCESS` with **zero CI runs** on #11475 (a review bot's context), `pending` over 43 green check-runs on #12389 ([both ways](../learnings/1786350644910-github-s-combined-commit-status-fails-in-both-dire.md)). Only the review-bot mechanism was new: **grep your own leaves by identifier before claiming novelty** ([scope correction](../learnings/1786321155140-scope-correction-the-zero-run-green-find-was-two-t.md)).

**`SlangPy Tests` is posted from an `event=repository_dispatch` run in shader-slang/slangpy**, invisible to `gh pr checks` and check-runs: read `statuses`, follow `target_url`, rerun there (`gh run rerun <id> --repo shader-slang/slangpy`); past 1-month retention it is non-actionable ([cross-repo](../learnings/1786335485075-slangpy-tests-reds-on-shader-slang-slang-are-cross.md)). A green `ci-slangpy-trigger-test.yml -f pr_number=N` (~1 min) only posted `pending` and fired the dispatch; the result is slangpy's `ci-latest-slang.yml` run "Slang PR #N: …" (~30 min; `--log-failed | grep 'FAILED slangpy'`). Draft and bot PRs skip the trigger (gated on `draft != true`) and need an explicit dispatch ([dispatch only](../learnings/1791510877884-ci-slangpy-trigger-test-yml-success-is-only-the-di.md)).

**After a slangpy-side fix, re-dispatch from slang; don't rerun:** a dispatch run's `GITHUB_SHA` is slangpy's head at dispatch time, so a rerun replays the pre-fix tree (inferred). `gh workflow run ci-slangpy-trigger-test.yml --repo shader-slang/slang -f pr_number=N` reads the PR's current head; its frequent HTTP 500s create no run, so retry with backoff. Canary one PR and wait for Linux and Windows `build-pr`; `gh run view --log` is empty until the run ends (per-job logs work); tight polls burn the shared token ([re-dispatch](../learnings/1793370651623-re-triggering-slangpy-tests-after-an-upstream-slan.md)). **A red whose `target_url` names an OLDER run can be stale** (it can overwrite a newer `pending`): check the newest dispatch run. `SlangPy tests abandoned` = a `build-pr` matrix job never appeared (infra drop). Grep failed logs for `short test summary` / `FAILED `; `Hot reload failed` / `error[E…]` lines are deliberate ([stale red](../learnings/1793376826751-red-slangpy-tests-whose-target-url-is-an-older-run.md)).

**A MISSING `SlangPy Tests` status blocks a PR silently; look for the absent status, not a failed run.** From **2026-12-02** GitHub blocks `pull_request_target` by default in public repos without their own event policy. Its brownout on 11-09 16:21–~18:00Z (next 11-16 16:00–18:00Z; not on githubstatus.com) ended every `pull_request_target` run (slang and slangpy) `startup_failure` with zero jobs; group `actions/runs?status=startup_failure` by event to spot it (the same day's 18:12–18:59Z Actions incident gave zero-job `failure` runs instead). The trigger fires only on opened/synchronize/reopened/ready_for_review (and `merge_group`), so a head pushed in the window never gets the status: auto-merge armed, `mergeStateStatus: BLOCKED`, all check-runs green, `commits/<head>/status` only `license/cla`. The PR never enqueues, review and shepherd assignment skip it, master's head ages. Per #14427 (11-10) no repo or inherited exception exists; the plan is a scoped admin exception before 12-02, then migration (`pull_request` + `workflow_run` relay; slash-cleanup → scheduled sweep); daily reports treat 12-02 as a hard deadline ([brownout strands SlangPy Tests](../learnings/1794254783516-pull-request-target-brownout-strands-slangpy-tests.md), [spot it by event](../learnings/1794300033367-github-pull-request-target-brownout-mass-startup-f.md), [enforcement 2026-12-02](../learnings/1794301550338-github-blocks-pull-request-target-by-default-from-.md)). Repair: the re-dispatch above once the PR is open, non-draft, head unchanged and not DIRTY/BEHIND; verify `pending` on `commits/<sha>/status` within 30 s ([re-dispatch from the Slang side](../learnings/1794255153466-missing-slangpy-tests-status-after-pull-request-ta.md)). Left alone, #14418 merged bypassing the queue (a `MergedEvent` with no `AddedToMergeQueueEvent` or `merge_group` run) ([MQ bypass](../learnings/1794301164235-slang-mq-failed-checks-can-come-from-the-slangpy-t.md)).

**On an active bot PR, a red `SlangPy Tests` is usually version skew; check `mergeState` first.** The PR's slang commit builds against **slangpy main**, so a branch `BEHIND` master after a coordinated breaking change fails with both mains correct (six un-rebased bot PRs hit `error[E30015]` on slang's new `enum MatrixLayoutMode`). Rebase; there is no issue to file. Confirm a "symbol removed" theory with `git log -S <symbol>` before relaying it ([version skew](../learnings/1789151785364-cross-repo-integration-ci-red-on-a-bot-pr-is-usual.md)).

## `action_required` Is an Approval Gate the Checks API Cannot See

An `action_required` run (fork PRs, "Approve and run workflows") **never started** (`attempts/1/jobs` → `total_count=0`; `gh run rerun --failed` is refused). Bucket it as a fifth state, "needs a maintainer to authorize", not with `failure|timed_out|startup_failure` ([gate](../learnings/1786327920887-github-actions-conclusion-action-required-is-an-ap.md)).

It creates no check-run, so REST `check-runs`/`status` **and** GraphQL `statusCheckRollup.contexts` miss it (see [query confidence](ci-github-query-confidence-and-gates.md)); only the suite layer shows it: `/actions/runs?head_sha=<full 40-char sha>` (an abbreviated sha silently returns `total_count:0`) or GraphQL `commit.checkSuites` with `ACTION_REQUIRED`. The axis is **check-run vs suite, not REST vs GraphQL**: the babysitter's `splitExclusions` fix (#12544) read check-runs, never fired, and missed the #13218 wedge. Filter to `event == pull_request` and the CI workflow (`CI` on slang, `ci` on slangpy/slang-rhi; suites: `workflowRun{event workflow{name}}`), dedup by name+highest-id: sibling review/`_target` runs stay `action_required` after CI ran (a count read 3 of 7; true 2) ([event filter](../learnings/1793003118714-fork-pr-ci-never-approved-count-filter-checksuites.md)). Pre-filtering `rollup !== 'SUCCESS'` excludes this class, and a tracker touching only current-payload PRs lets such a wedge age out of every surface ([invisible](../learnings/1790080487638-action-required-workflow-approval-wedges-are-invis.md), [dead code](../learnings/1790079172299-ci-babysitter-action-required-fix-2026-09-22-12544.md)).

**Who approved a held run:** `actions/runs/<id>` (no review or timeline event records it): after approval `run_attempt` is 2, `triggering_actor` the maintainer, `actor` still the contributor ([approver](../learnings/1793026171832-who-approved-an-action-required-fork-ci-run-trigge.md)).

**The "CI never approved" count moves without approvals, both ways.** Each fork-author push makes a new `action_required` `CI` run (11-01: 9 → 12 only from pushes); report joiners as "re-needs approval after author push" ([re-push](../learnings/1793522418229-github-sweep-clock-skew-vs-actions-stamps-and-fork.md)). slangpy #1234 likewise, visible only in `/actions/runs?head_sha=<full sha>`; after any fork-PR push the next action is "maintainer must approve the fork runs" ([slangpy](../learnings/1793632219099-fork-pr-ci-approval-does-not-carry-over-to-new-pus.md)). Conversely a held suite can vanish from an unchanged head unapproved: slang #13473 (`actions/runs?head_sha=` → 0 runs) ([timeline](../learnings/1793436218667-daily-github-sweep-closed-unmerged-prs-and-merge-q.md)) and #13698 on 2026-11-06 ([vanished suite](../learnings/1793955615028-github-sweep-merge-queue-commit-dates-mq-bypass-va.md)); a dropout with no CI suite left is still unapproved.

## Failure Rankings and Attempt Ladders Measure the Wrong Thing

**A job that fails by design tops the ranking.** Across 61 `ci.yml` runs the top failing leg was `wait-for-human-priority`, a **priority throttle**: a bot draft dispatch yielding to human, merge-queue or older CI is failed by a marker step so it holds no runners, and a companion workflow reruns it later (`skipped` would collide with the build jobs' implicit `success()` gating). Ranking it is a false #1; rerunning it burns the runners it protects ([by design](../learnings/1786350256938-a-ci-job-that-fails-by-design-will-top-your-infra-.md)).

**An attempt ladder says a run was rerun, not that the remedy was attempted.** `att1 FAILURE, att2 FAILURE` looked like two remedy tries; both died at `wait-for-human-priority` in ~10 s. Report **where in the job graph each attempt died** ([ladder](../learnings/1786336411679-an-attempt-ladder-tells-you-a-run-was-reran-not-th.md)).

## Query Traps That Return a Believable Wrong Answer

**A bounded page is not a population.** "9 reviews on #12354" from `reviews(last:10)` was really 12: assert `totalCount == (nodes|length)` and `--paginate` when they differ ([page](../learnings/1786330741949-a-bounded-page-last-n-first-100-is-not-a-populatio.md)).

**One invalid field in `gh … --json` aborts the whole query:** `gh pr view N --json reviewDecision,…,mergeQueueEntry` exits 1 with `Unknown JSON field`, printing none of the valid fields ([invalid field](../learnings/1786336024283-one-invalid-field-in-gh-json-a-b-c-aborts-the-whol.md)); in a bulk loop it is silent (empty fields, like auth trouble), so validate a new field alone first. For queue membership use `gh pr view --json state,isDraft,mergeStateStatus,headRefOid,statusCheckRollup` plus GraphQL `pullRequest(number:N){state mergeQueueEntry{position state}}` (`null` = not queued) ([GraphQL](../learnings/1791705807345-merge-queue-membership-check-use-graphql-pullreque.md)). `statusCheckRollup` shows WAITING gates (`falcor-build-approval-gate`) that `gh pr checks` omits and mixes check-runs (`.name`) with statuses (`.context`): null-guard `.name` in jq ([rollup](../learnings/1791267800558-gh-pr-view-json-has-no-mergequeueentry-field-use-g.md)). `gh issue view --json authorAssociation` fails the same way; use `gh api repos/O/R/issues/N --jq .author_association` (COLLABORATOR vs CONTRIBUTOR, the triage skip rule) ([authorAssociation](../learnings/1793639840678-gh-issue-view-json-has-no-authorassociation-use-gh.md)).

## A Detached Build's Exit 0 and a pwsh Step's Success

**A detached launcher's exit code describes the launcher.** With `setsid nohup cmake --build … &`, "exit code 0" is the wrapper: on slang#12371 two builds reported 0 while `libslang-compiler.so` was older than its input `.o` and lacked the PR's new diagnostic; `pgrep -af ninja` showed both racing in one ninja dir. Wait on the real process (`until ! pgrep -f ninja; do sleep 20; done`), never start a second `cmake --build` on a live ninja dir, and verify **behaviourally** (grep the artifact for a commit-introduced string). After a dependency merges, rebuild staged `.slang-module` inputs too ([wrapper](../learnings/1785988615115-setsid-run-in-background-makes-exit-code-0-report-.md)).

**A Windows `pwsh` step's success is its last native command's exit code:** Actions wraps the block with `$ErrorActionPreference='stop'` and `exit $LASTEXITCODE`, but a native non-zero exit doesn't stop it. In slangpy's `build-and-test-with-slang/action.yml:99-103` (`git clone; git fetch <ref>; git checkout FETCH_HEAD; …`) a vanished merge-queue ref failed Linux (bash `-e`) while Windows built the default branch and went green. Check `$LASTEXITCODE` after each native call or set `$PSNativeCommandUseErrorActionPreference = $true` (pwsh 7.4+); find past cases by grepping `success` job logs for `error: pathspec 'FETCH_HEAD'` ([pwsh](../learnings/1791418811630-github-actions-pwsh-run-blocks-hide-failed-git-com.md)).

## Reading Fresh CI Data: Truncation, Stale Listings, and the Gateway Cache

- **WebFetch cannot read `health_snapshots.jsonl`** (slang-ci-analytics): it truncated, showed a March line as latest, then hit its 10 MB cap. Use `curl -s --max-time 30 <raw-url> | tail -1` and check the `timestamp` is same-day; its `merge_queue` and `hosted_runner_usage` are a better live proxy than the Actions failure API ([curl|tail](../learnings/1789546707009-ci-health-snapshot-use-curl-tail-not-webfetch-on-h.md)). `status.html` is JS-rendered with no numbers: record the gap, never invent numbers ([10 MB](../learnings/1790065065697-ci-health-snapshots-jsonl-exceeds-webfetch-10mb-li.md)).
- **A `status=failure` listing can silently return only stale rows**: `actions/runs?status=failure` and `gh run list --status failure` returned nothing after known failing nightlies, while `created=%3E%3D<date>` returned 39. Tell: the newest row is days older than master's head; bound with `created>=`. Size an MDL perf flag from `confirmation.json` `plan.regressions` (1.12x), not the analyze log's first table (1.58x) ([stale listing](../learnings/1791360225685-gh-run-list-status-failure-can-silently-return-sta.md)). `created>=` misses a `waiting` run (e.g. bot-draft CI at an approval gate) that hits the 30-day limit and ends `failure` with an old `created_at`: diff yesterday's `status=waiting` list against today's (8 of 14 departures were expiries) ([expiry](../learnings/1792830160449-github-actions-30-day-waiting-run-expiry-shows-as-.md)).
- **The egress gateway caches GitHub REST GETs keyed on the literal query string**: an un-busted URL returned two-week-old failures; `&_=$(date +%s%N)` returns fresh data (GitHub ignores unknown params). That was the recurring "workflow-failures stale-date" heartbeat anomaly ([cache](../learnings/1789391780211-root-cause-of-the-recurring-slang-workflow-failure.md)).
