# Harvest Tiers, the Late-Post Race & Verdict Reporting

Reading the *review signal* correctly: what a harvest exit code means, why the production bot review almost always posts *after* your first harvest window closes (so you must re-harvest right before recording), and how to report a verdict against the PR's live human-review state. This is the review-signal companion to [head-pinning & debounce](review-pr-head-pinning-and-debounce.md) (which covers the head moving); the decision framework is on [approver decision & shadow-mode](review-pr-approver-decision-and-shadow-mode.md), and keeping the runs alive is on [reviewer-run survival](review-pr-reviewer-run-survival.md).

## TL;DR
- **The dominant timing hazard is the late-post race:** the production `github-actions[bot]` claude-pr-review lands 25–45 min after the push, and the "review" workflow JOB stays `in_progress` long after its inner sub-check completes. **Always re-harvest immediately before `record_decision`**, not just during the first window.
- **A sub-check reaching `skipped`/`completed` is a red herring, not evidence the primary review was skipped.** Key off the actual `github-actions[bot]` review appearing at the pinned SHA via `gh pr view --json reviews`.
- **harvest exit 20 = "no bot review AND no bot still working"** — it does NOT license asserting a *cause* ("production skips X"). On a fresh external-fork/first-time-contributor human PR it is usually the `Claude PR Review` check still IN_PROGRESS (a timing race); on slang-rhi (no `claude-pr-review.yml`) it is the legitimate Devin-only tier by design.
- **harvest exit 10 (stale-only) can hide an in-flight bot re-review** — check the commit-status/`review` check before falling to Devin-only.
- **`harvest.json` reports only the CHOSEN bot review** — verify per-commit via a GraphQL `commit{oid}` query when multiple reviews coexist across commits.
- **A stale bot review whose `<reviewed>...<head>` delta touches 0 `source/` files is source-current signal, not noise** — a 🟡/🔴 on byte-identical source is a maintainer-proxy "do not auto-approve" prior.
- **Re-check reviews at record time to finalize `mode` (live vs live_late)** — a human APPROVE (or a WOULD_APPROVE-invalidating `CHANGES_REQUESTED`) can race in during harvest/Devin; join a late verdict onto the same ledger row via `record_human_verdict`.
- **Before reporting a verdict, surface the PR's human-review state and author activity.** An existing maintainer APPROVE makes nits advisory; a self-resolving author has nothing to route; a standing `CHANGES_REQUESTED` caps at ABSTAIN — but read the review *body* + inline count, because CHANGES_REQUESTED is a status enum, not an edit list.
- **Verdict-detection guards must page or query by author** — the reviews list defaults to page 1 (30 items) and a bot review can be on page 2.
- **A maintainer self-merge with zero formal reviews is `NO_HUMAN_REVIEW`, not `APPROVED`** — recording APPROVED fabricates an agreement signal.

## Harvest tiers and exit-code semantics

`harvest-reviews.py` exit 20 ("no harvestable bot review → Devin-only") is ambiguous: on a `fix/issue-N`/bot/Claude-branch PR it means production genuinely skips, but on an external-fork/first-time-contributor/member human PR it usually means the `Claude PR Review` check is merely still IN_PROGRESS. Check `gh pr view <pr> --json statusCheckRollup` for a `review` check and cross-check the author before treating exit 20 as a skip; if the check is still running, Monitor it to COMPLETED and re-harvest (flips to exit 0) rather than falling to Devin-only prematurely and throwing away the authoritative primary review ([harvest exit 20 on a fresh external-fork PR is a timing race with the Claude PR Review check, not a production-skip](../learnings/1783767626000-approver-infra-abstain-harvest-exit-20-on-a-fresh-.md)). Exit 20 also does NOT license asserting a *cause* — it means "no review + no pending bot," not "production skips X"; encoding an unevidenced causal claim is an OUTPUT_REVIEW must-fix ([don't assert a CAUSE for harvest exit 20](../learnings/1783961748935-approver-critique-mustfix-don-t-assert-a-cause-for.md)). On **slang-rhi (and any repo lacking `claude-pr-review.yml`), harvest exit 20 is the expected Devin-only tier by design, not a missed harvest** — slang-rhi has only `claude.yml` (mention responder) and CodeRabbit auto-pauses to a walkthrough *issue comment*, so verify via the repo's `.github/workflows` + CodeRabbit's commit *status* (not its comments) before treating exit 20 as a skip ([slang-rhi Devin-only tier is legitimate, not a missed harvest](../learnings/1784011099646-approver-clause-gap-slang-rhi-devin-only-tier-is-l.md)).

harvest exit 10 (stale-only) can hide an in-flight bot re-review — check the commit-status API before falling to Devin ([harvest exit 10 (stale-only) can hide an in-flight bot re-review on a synchronize](../learnings/1783949042869-approver-clause-gap-harvest-exit-10-stale-only-can.md)). And `harvest.json` reports only the CHOSEN bot review — when multiple CodeRabbit reviews coexist across commits (a large full review at an older SHA + a small incremental re-review at the head), provenance caveats must reflect the FULL live picture via a GraphQL per-review `commit{oid}` query, not the single harvest verdict ([harvest.json reports only the chosen bot review; verify per-commit via GraphQL](../learnings/1784034639546-approver-critique-mustfix-harvest-json-reports-onl.md)).

Two fresh-PR confirmations of the exit-20 timing hazard, both where exit 20 misfired on a just-opened human-authored non-fixer PR that production review was EXPECTED to run on. On slang#13003 `collect-reviews.sh` returned exit 20 at ~08:36 (`{found:false}`) and a fallback-tier doc was synthesized from CodeRabbit's summary + Devin → WOULD_APPROVE, but the production `github-actions[bot]` review posted ~3 min later carrying "🟡 Has issues — 1 gap" (only DECISION_REVIEW caught the now-existing primary, forcing a re-harvest → PRIMARY tier → ABSTAIN). The exit-20-vs-22 discriminator failed because the claude check-run hadn't materialized yet — on a fresh non-fixer PR "no review yet" is very often "review imminent." So before RECORDING any fallback-tier decision that arose from exit 20 on an expected-review PR, do a final re-harvest at record time; if it flips to 0, re-synthesize primary tier and re-decide (do NOT do this for genuine-skip classes — fixer `fix/issue-N`, bot-authored, Claude branches — where Devin-only is correct) ([harvest exit 20 can be a timing race on a freshly-opened PR, not a genuine skip](../learnings/1789116600310-approver-critique-mustfix-harvest-exit-20-can-be-a.md)). On slang#13004 the same exit 20 fired while the production "Claude PR Review" workflow was ACTIVELY running — a tooling bug: the job surfaces as a check-run whose NAME is literally `review` (app=`github-actions`, status=`in_progress`), and `harvest-reviews.py`'s `pending_bot` detection didn't match that name, so it classified "no bot working" (exit 20) instead of "bot still running" (exit 22). Cross-check live state before falling to Devin-only — `gh api repos/<repo>/commits/<sha>/check-runs --jq '.check_runs[] | select(.status=="in_progress") | .name'` and look for an in-progress `review` check-run (confirm via the run's `.name`=="Claude PR Review"); if present, treat as exit 22, poll to completed (~30s intervals, ~6 min cap), then re-harvest. `pending_bot` should treat an in-progress `github-actions`-app check-run named `review` as a pending primary → exit 22 ([collect-reviews.sh pending_bot misses a check-run literally named "review" — near-miss Devin-only fallback](../learnings/1789122292981-approver-infra-abstain-collect-reviews-sh-pending-.md)).

## The late-post race: re-harvest right before recording

The dominant harvest hazard is the **late-post race**: on slang the production `github-actions[bot]` claude-pr-review does not post promptly, and its "Claude Code Assistant" check-run reaching `skipped`/`completed` is a red herring, not evidence the primary review was skipped — the real formal review lands 25–45 min after the push, and the "review" workflow JOB stays `in_progress` long after its inner sub-check completes (a large post-review dismiss+submit lag). Key off the actual `github-actions[bot]` review appearing at the pinned SHA via `gh pr view --json reviews`, and **always re-harvest immediately before `record_decision`**, not just during the exit-22 window ([Claude Code Assistant skipped while the real claude-pr-review posts 25-45min later](../learnings/1784075137829-approver-infra-abstain-slang-claude-code-assistant.md), [claude-pr-review sub-check completion ≠ review body posted](../learnings/1784078543250-approver-clause-gap-claude-pr-review-sub-check-com.md), [re-harvest before recording — primary can post mid-session after a Devin-only draft](../learnings/1784032917245-approver-challenger-miss-re-harvest-before-recordi.md), [re-harvest AGAIN right before record_decision — slow prod reviews post seconds after your window](../learnings/1783962571176-approver-critique-mustfix-re-harvest-again-right-b.md)). Treat a "hung" in-progress review as merely slow, and re-harvest at the settled head rather than freezing the first-second result ([a "hung" production review may just be slow — re-harvest before falling to Devin-only](../learnings/1783958635135-approver-critique-mustfix-a-hung-production-review.md), [harvest timing-race on fresh reviewable PRs — re-harvest at the settled head, never freeze the first-second result](../learnings/1783957917061-approver-clause-gap-harvest-timing-race-on-fresh-r.md), [wait out the IN_PROGRESS production review before Devin-only; and debounce a head that moves mid-decision](../learnings/1783935971762-approver-infra-abstain-confirmed-wait-out-the-in-p.md)). On a `synchronize` re-push whose head is a master-merge, **harvest exit 10 (stale-only) + a live `in_progress` "review" check-run is a timing race, not a Devin-only trigger — wait for the primary** ([stale-harvest + in_progress production review = wait, don't fall to Devin-only](../learnings/1784042795116-approver-infra-abstain-stale-harvest-in-progress-p.md), [on synchronize the production 'review' check can still be in_progress at synthesis — poll it to settle AND re-harvest before recording](../learnings/1784049951158-approver-infra-abstain-on-synchronize-the-producti.md)).

A late human APPROVE can likewise race in during harvest/Devin: the `mode` ledger tag is derived at staging, so **re-check reviews at record time** — a maintainer APPROVE on the pinned SHA in the harvest+Devin window means the correct tag is `live_late`, and any late verdict (especially a `CHANGES_REQUESTED` that would invalidate a WOULD_APPROVE) must be joined onto the same ledger row via `record_human_verdict` ([mode=live can be stale on fast PRs — a human review may land between staging and decision](../learnings/1784026123581-approver-clause-gap-mode-live-can-be-stale-on-fast.md), [re-check PR reviews before finalizing mode — a human APPROVE can race in during harvest/Devin](../learnings/1783963597891-approver-clause-gap-re-check-pr-reviews-before-fin.md), [re-fetch PR reviews at record time, not just at staging (confirmed live on #11987 R2)](../learnings/1784050296652-approver-clause-gap-re-fetch-pr-reviews-at-record-.md), [pr-approver must re-fetch reviews at record time not just staging](../learnings/1784050376318-pr-approver-must-re-fetch-reviews-at-record-time-n.md)).

## Stale reviews as corroboration

Two refinements on stale-review handling. A stale-but-recent production bot review that lands on a PRIOR head is weak as a verdict source but strong corroboration — harvest still surfaces it; use it as an independent agreement signal ([on a live multi-revision PR, a production bot review that lands on a PRIOR head is stale-as-verdict-source but strong corroboration](../learnings/1783959025798-approver-challenger-miss-on-a-live-multi-revision-.md)). And a stale bot review whose `<reviewed>...<head>` delta touches 0 `source/` files is source-current signal, not noise — count source-touching files in the compare API; a 🟡/🔴 verdict on byte-identical source is a maintainer-proxy "do not auto-approve" prior that keeps the decision from rounding up ([a stale bot review whose head-delta touches 0 source files is source-current](../learnings/1784035570681-approver-clause-gap-a-stale-bot-review-whose-head-.md)).

## Verdict reporting: human-review state, self-resolution, CHANGES_REQUESTED

A review's findings are not the whole disposition. Before reporting a verdict, also surface the PR's human-review state and author activity: an existing maintainer APPROVE means merge is imminent and nits are advisory; on an actively-iterated PR the author is often self-resolving threads (`[Agent] Applied in <sha>`), so there is nothing to route — and on a human contributor's own approved branch, do NOT let the fixer push (send an explicit STAND DOWN if you already forwarded) ([check existing human reviews + author self-resolution before reporting a verdict](../learnings/1783669294473-slang-pr-review-check-existing-human-reviews-autho.md)). Never read a coarse status enum as an edit list: `reviewDecision=CHANGES_REQUESTED` can be an investigation HOLD, a merge-queue block, or a prose concern — read the review *body* and the *inline comment count*; if both are empty of concrete asks, the posture is *hold*, not *revise*, and one CR coexists with prior APPROVEs rather than negating them ([CHANGES_REQUESTED is not an edit list — read the review body + inline count](../learnings/1783731922642-changes-requested-edit-list-read-the-review-body-i.md)). A clean code review does not license WOULD_APPROVE while a human reviewer is mid-cycle: an unresolved + non-outdated maintainer review thread on the pinned commit, or `reviewDecision=REVIEW_REQUIRED` with the sole reviewer engaged, is a CHALLENGER_CONCERN abstain even when the fixer's latest push closes every raised ask — approving there preempts an active human review, the highest-severity false-safe ([fixer PR that closes the maintainer's asks still ABSTAINs while the human is mid-cycle](../learnings/1783806650503-approver-challenger-fixer-pr-that-closes-the-maint.md)).

Likewise, a guard that checks "did the bot post its review yet?" via the reviews list reads only page 1 (30 items) by default — on a PR with many human inline-comment reviews the bot's newer review is pushed to page 2 and the guard falsely reports zero, re-waking the reviewer forever; page or query-filter by author, or verify a claimed review id by fetching it directly ([verdict-detection guards must page or query by author](../learnings/1783665568170-verdict-detection-guards-must-page-or-query-by-aut.md)). And when a `pr_merged` webhook stamps `record_human_verdict`, read the actual review state: a maintainer self-merge with zero formal reviews (`reviewDecision: REVIEW_REQUIRED`, empty `reviews`) is `NO_HUMAN_REVIEW`, not `APPROVED` — recording APPROVED on a self-merge fabricates an agreement signal and biases accuracy upward ([stamp maintainer self-merge as NO_HUMAN_REVIEW, not APPROVED](../learnings/1783726677874-stamp-maintainer-self-merge-as-no-human-review-not.md)).

**Scope a bot follow-up-review verdict to the diff you actually reviewed — never say "merge-ready" or "complete", and attribute a test PASS to whoever ran it.** Three overclaims to avoid in a follow-up review verdict, all caught by the codex OUTPUT_REVIEW gate on slang#13020: (1) **"merge-ready" from a scoped follow-up review** — a review that only looks at a specific fix/diff cannot certify the whole PR is mergeable; say *"resolves the blocker I raised; no remaining correctness issue found in this follow-up diff; CI green + maintainer review remain authoritative"* (a "human should verify / CI must pass" caveat sitting next to a "merge-ready" claim does NOT neutralize it — drop the claim). (2) **"the key/fix is complete"** — "complete" asserts you checked every input/path; if you verified one path, say *"sufficient for the reviewed <X> change"* and state what you checked was NOT relevant. (3) **asserting tests PASS when you didn't run them** — as a read-only reviewer you verify test LOGIC (does it exercise the bug path: same fixture, in-place mutation, fails-before/passes-after), not runtime status; attribute the PASS explicitly (*"you report PASS; I verified the test logic exercises the stale path; runtime status per your report"*). Run OUTPUT_REVIEW on the actual drafted verdict PROSE, not just the code — it is what catches wording overclaims after CODE_REVIEW has already approved the code ([scope a bot follow-up-review verdict to the reviewed diff — never claim "merge-ready"/"complete", attribute test-pass to whoever ran it](../learnings/1789173449943-scope-a-bot-follow-up-review-verdict-to-the-review.md)).
