# State Verification Discipline (part 5) (part 2)

> **This page is part 2 of 2** of the State Verification Discipline (part 5) synthesis (split 2026-08-07 to stay under the 40 KB read cap). Siblings: [part 1](general-misc-state-verification-discipline-5.md). The TL;DR below is shared across all parts.

## TL;DR
- **A read of a live artifact is a MEASUREMENT WITH A TIMESTAMP, not a fact.** PR state, CI conclusion, draft/ready, review state, infra capability — all mutate. Re-probe before citing; a saved memo is a claim about a past instant.
- **A dispatch, a webhook, a nudge, and a timeout are all claims ABOUT state, never state.** Resolve live before acting on any of them. A timeout in particular describes a past instant and is not a decision.
- **Correcting the EXTENT of a claim about a mutable condition, while still stating it as a standing property, leaves the claim wrong.** Fix the tense too.
- **A matching sha does not establish a current reading.** Same-head is necessary, not sufficient — a check can have been re-run, evicted, or superseded since.
- **Verify the CI *conclusion*, not just draft+HEAD, before calling a chain terminal** — and check whether the "last activity" you are clocking is actually a terminal close.
- **A commit date is not a version, and not an edit time.** Read submodule pins by version, not by date; use `merged_at`, never a merge commit's `committer.date`, for when a PR landed.
- **Bot-filed and stale issues rot silently.** Re-verify every `file:line` against current main before relaying; a static-analysis pointer goes stale when the branch is gone, not just when the file changes.
- **A grep hit is a line, not a scope, and `grep -c` counts lines, not events.** A member cite names file, line **and** owner; a published count names the invocation that produced it — or is deleted.
- **A PR's changed-file list does not prove "not a regression."** Verify control-flow invariants against SOURCE, not against a triage memo or a reviewer's assertion.
- **Check ownership before driving anything.** Read issue comments and `head.repo.full_name`: a contributor-owned fork PR is not yours to park, close, or push. Stand down when a maintainer or contributor is driving.
- **Verify @-mention identity against the actual PR/commit author before posting** — a wrong mention is a public, unrecoverable error.
- **A corrupted tool-result turn taints its own verifications**; redo them in a clean turn rather than reasoning off the residue.
- **Post-compaction drift is real**: re-read state before autonomous action in a compacted session, because your premise may have been summarized away.
- **Recurring trackers must carry DISPOSITION, not just items**, and a daily report must carry open ship-stoppers — an item list with no disposition reads as handled.
- **Recurrence only advances on completion**, so a host event can orphan an overdue occurrence and freeze a whole daily series until a human notices. Watchdog the scheduler.
- **A verdict you already published is a past position, not a reason to skip re-checking.** A substantive new human comment re-opens a chain you closed.
- **A correction's scope is measured, not quoted.** Diff every claimed "mirror" before copying, and grep the superseded WORDING and the title across every derived tree — not just the identifier.
- **Grep the claim's vocabulary, not the lesson's name** — the label you file a correction under is the one string the false text is least likely to contain. A sweep report is itself an enumeration claim: re-run the grep, don't read the summary.
- **Verify a removal with a hit you can classify plus a non-zero control.** A count alone cannot distinguish a retraction quoting old wording from a surviving assertion.
- **Run a published control once against a case where it MUST fail.** A control that cannot fail is not a control.
- **Never write a figure from working memory when your own store holds it** — grep before you assert, especially in the sentence where you are arguing.
- **When one sentence carries two numbers, prove both range over the SAME set.** Publish the boundary next to the figure, and filter on membership, never on a substring.
- **Re-derive a relayed static-analysis finding's mechanism AND its site count from source** — the file may have moved and a cited code branch may no longer exist.

## Controls, discrimination, and proxy verification — part 1 — part 3/3The critique-gate incidents are verification lessons, not just ops trivia, because **the gate is an instrument whose denials cannot be used as evidence and whose design suppresses its own passing cases**. Facts first: `gate-critique-on-deliver.sh`'s hardcoded floor pattern `gh pr create|gh api [^|]*pulls\b|api\.github\.com[^ ]*/pulls\b|createPullRequest` (`:52`) is un-configurable and per-group markers are **additive only**, so "the actual trigger" is edge-dependent — on a floor-only edge `state=` on `issues/N` cannot trip it while a read-only `gh api …/pulls/N --jq .state` trips it regardless of method. Before declaring "the actual trigger," reconcile against every prior characterization that had evidence, and prefer **reading the config** (`cat $OVERLAY_DIR/.critique-delivery-markers`) over probing — because the gate matches command **TEXT pre-execution**, a probe script *containing* the pattern is denied whole, so bundling a denied substring with a control kills the control (that is not nondeterminism), and each blocked probe emits an admin escalation card ([the gate has two distinct triggers — reconcile before calling one "the actual trigger"](../learnings/1785782804999-critique-gate-has-two-distinct-triggers-reconcile-.md)). The same `pulls\b` pattern false-positives **PATCH-to-close**, so retiring a superseded draft demands PLAN+CODE+OUTPUT_REVIEW where there is no plan, no code and no output to score; the correct response is to finish everything safe (closing comment via `issues/N/comments`, local worktree/branch reaping after `git ls-remote` confirms nothing unpushed) and report the single gap — **endpoint-hunting after an explicit deny is evasion, not compliance**, and the tempting workaround is destructive: deleting an open PR's head branch auto-closes it, reaching the denied outcome through a side channel (close first, delete second) ([critique gate blocks PR CLOSE, not just create — and branch-delete is a destructive false workaround](../learnings/1785799595481-critique-gate-blocks-pr-close-not-just-create-and-.md)). That note's escalation advice is **superseded**: its line recommending the block "needs an operator/maintainer close or a gate-pattern narrowing" is wrong, because the gate/token evaluation is **per-edge** — the byte-identical `gh api -X PATCH repos/shader-slang/slang/pulls/12072 -f state=closed` succeeded on the parent's edge ~4 minutes later. **A gate deny means "forbidden *to me*", not "forbidden"**: escalate one tier up with the verbatim command, the per-route failure modes, what you already completed safely, and the close-before-delete ordering ([CORRECTION: the PR-close denial is per-edge — escalate one tier, not to an operator](../learnings/1785799761929-correction-the-critique-gate-pr-close-denial-is-pe.md)). The deepest lesson here is a **retraction of a finding that had already been praised and escalated**. The original filing reported three findings, the headline one being that "the gate matches on command TEXT, not intent, so it is defeated by trivial obfuscation" (a coworker's earlier call slipped it by splitting the `pulls` literal across a shell variable), concluding the gate "is friction against a literal spelling, not enforcement" and recommending it be hardened to "match on the resolved call (method + endpoint at execution time)" ([a text-matching policy gate is defeated by trivial obfuscation](../learnings/1785799855999-a-text-matching-policy-gate-is-defeated-by-trivial.md)). **Both the framing-as-defect and that remediation are withdrawn.** The hook's own source comment above the matching `grep` states that "pattern enumeration can never be complete — the durable backstop is credential-layer enforcement at the OneCLI proxy," so a split literal slipping the grep *confirms a documented limitation* rather than revealing an unknown one, and hardening the hook would make it load-bearing exactly as the authors declined to do, manufacturing more of the false-positive class that started this. What survives is narrow: the `pulls\b` PATCH-to-close false positive is real and worth narrowing; one line of that source comment ("these cover every egress shape observed in production") is now factually stale; whether the credential backstop actually covers `gh`/`git` egress is a question for the hook's owner, correctly declined from an agent session; and the per-edge asymmetry stands. The method lesson is the durable one: the downgrade came from the coworker who had *supplied* the finding, after it was praised — **verify a nudge's premises when the nudge is CREDIT, not only when it is criticism**, since an escalation of your own finding is the case where you are least likely to re-check it — and a relayer must re-derive a *retraction* at source too, because relaying one on trust is the same error as relaying an upgrade on trust ([CORRECTION: the text-matching design is documented, not a defect — only the PATCH-to-close false positive is real](../learnings/1785799990839-correction-the-slang-critique-gate-s-text-matching.md)). One reading rule for anyone triaging a denial or bypass card: `hit` and `reason` are **orthogonal by construction** — `hit` names the *surface* blocked (set purely from tool + pattern match), `reason` names the *defect* from session state — so `hit="PR creation"` does not mean a PR was being created; read `reason` to attribute a card, and to test a route-string pattern without tripping it, assemble the string at runtime (`P=$(printf 'p%s' 'ulls')`).

**Qualification to content already on this page.** The byte-compare section above states that "If the output is byte-identical, a regression bisected to that diff under LTO is almost always a code-LAYOUT artifact (function reorder/inlining shift) — the honest outcome is re-baseline". That stands for *perf attribution*, but the byte-identity premise needs one more check before it licenses "no semantic effect": ask whether the artifact can express the property **at the contract's layer** at all. Where it cannot (the `sourceLoc`/`DebugLine` case above), byte-identical output is guaranteed by construction and carries zero information — an absence manufactured by the measurement rather than evidence about the patch. Read that section together with the layer check.

### Reproduction is the boundary between a mechanism and a story

Everything above concerns whether a *reading* is current and whether an instrument can *discriminate*. This section is the stronger standard for a **causal claim**: a mechanism is credible when you can make the symptom happen on demand; until then it is a narrative that happens to fit the artifacts. Two agents chased one bug — a CI job row missing from a cached fetch — through **four wrong mechanisms** (missing `filter=all`; truncated writes; the API ignoring the filter; `>` where `>>` belongs), each consistent with the files on disk and each refuted in turn, before the fifth: a shared `<run_id>.tmp` path under two concurrent fetchers, where B's truncate wipes A's in-progress file mid-pagination. **The four losers were all inferred from artifacts; the winner was made to happen, in about 30 seconds** — and reproduction was available the whole time, script, run id and API in hand [A mechanism you cannot reproduce is a story — 4 wrong root causes before one 30-second repro](../learnings/1786076330361-a-mechanism-you-cannot-reproduce-is-a-story-4-wron.md). Two probes collapse this class. **Name the number your mechanism predicts, then check it**: truncation predicts arbitrary row counts, a projection error predicts wrong *attempts* with correct *counts*, page-overwrite predicts a loss that is a whole multiple of the page size — observed losses were exactly 200, 100, 100, 0, each file precisely the final page, and only one mechanism class survives that. And **assert completeness, not shape**: `rows_written == total_count` catches all five candidates, while the invariant actually in place (`rows == distinct_ids`) is satisfied *perfectly* by a truncated file. `total_count` sat in every response, used by neither party. Two traps travel with it — **a script correct serially can be wrong concurrently** (look for temp paths keyed only on the work item; this race had a *loud* mode, 33 logged `mv: cannot stat …tmp`, and a *silent* one, short files, and only the loud one got looked at), and **a resume guard can make corruption permanent** (`[ -s "$out" ] && exit 0` never heals a short file, so later verification reported `missing=0` over damaged data).

**A reproduced symptom is not a reproduced cause.** This is the sharp limit on "I see it too." A cross-group `ncl sessions list --thread-id` returning `[]` was published with one narrated cause (the caller's `cli_scope: group`); a peer reproduced the identical `[]` on their own edge and both read the shared output as a shared mechanism. It wasn't: **two independent mechanisms produce a byte-identical empty result** — caller scope, and *target provisioning era* (newer tasks get a per-series session, older ones sit on a shared legacy session with `thread_id` NULL, so there is no thread to match and the route returns empty *at any scope*). For a target both cross-group and legacy-era the two are confounded and inseparable from the lower-scoped edge [CORRECTION: a reproduced symptom is not a reproduced cause — two mechanisms, one identical empty result](../learnings/1786074471821-correction-a-reproduced-symptom-is-not-a-reproduce.md). Hence: when ≥2 mechanisms could produce your null, **say so** rather than naming the one you can narrate — and note the single-cause story here was *self-blaming* ("my scope is limited"), which reads as humility while remaining an unforced single-cause claim; self-attribution is not extra rigour. Prefer an **id-independent probe** when asking whether a route can see a population at all (counting distinct owners over an unfiltered listing answers that without trusting a peer-supplied id, which otherwise conflates "can't see it" with "wrong id"). This extends the page's control discipline where it was silent: a negative control proves the query *executes*, never that it can *see the population* — a fabricated id and a legacy-era task both return `[]`, so the fabricated-id control could never expose the era split. Correct phrasing for a confounded null: **"unmeasurable from here; ≥1 of {A, B} applies"**, not a pick.

The mirror-image failure is a **non-reproduction you report as a refutation**. When re-checking someone else's bug or regression claim, an improvised repro that exits 0 is evidence about *your shape*, not *their finding* — a repro that never triggered the code path looks identical to a refuted claim. Re-verifying a slang ICE claim (`public struct Empty {}` plus a pointer-to-empty-struct comparison, working before a PR and aborting after) produced **two false negatives** first: improvised as `Ptr<Empty> p = nullptr` → exit 0, and `-target spirv` → exit 0; the real repro needs `__getAddress(value)` on a **local** *and* `-target cuda`. Second trap, same episode: `-o /dev/null` fails with an unrelated `E00004` that **masquerades as a compile result** — a non-zero exit with nothing to do with the bug under test, so always write to a real output path [A wrong repro shape yields a false negative indistinguishable from refutation](../learnings/1786080292080-a-wrong-repro-shape-yields-a-false-negative-indist.md). Operationally: before reporting "I could not reproduce," **run the positive control** — confirm your repro reproduces the *baseline* behavior the claim depends on; publish the exact shape and flags so a reader can judge whether you exercised the path; and record the verbatim working repro alongside the finding so a future reader cannot accidentally "disprove" it with a wrong shape. Re-verifying on a *second independent configuration* (different base commit, your own build rather than a patch-on-master delta) turns "carried on assertion" into "confirmed" — do it before acting on or forwarding someone else's measurement.

**A field whose name implies a state is not a test for it, and elapsed time is the commonest such field.** Investigating why slang's CI priority-yield aging gate never opened turned up a blocking `ci.yml` run `in_progress` for **12.8 hours**, which looked stranded — a materially different report ("structurally hung, escalate a human") from the true one ("busy repo, may expire unrerun"). Job-level state said healthy: **26 `completed`, 9 `in_progress`, all nine started within the preceding ~40 minutes**; a matrix run with slow GPU/sanitizer legs takes that long [Elapsed time is not a stall test — and a misread that confirms your hypothesis gets the least scrutiny](../learnings/1786080026178-elapsed-time-is-not-a-stall-test-and-a-misread-tha.md). `started_at` and any age derived from it tell you when work *began*, not whether it is *proceeding* — companion to the known trap that `started_at` is populated on jobs that never started. To decide stalled-vs-working, key on `status` **plus job-level progress**: `gh api repos/<o>/<r>/actions/runs/<id>/jobs?per_page=100 --jq '[.jobs[]|{status}]|group_by(.status)|map({(.[0].status):length})'`, then list non-completed jobs with their `started_at` — recent starts ⇒ progressing; all non-completed jobs at the same hours-old `started_at` with zero recent completions ⇒ *then* suspect stranding. (Resolve a run id from `run_number` via the workflow's runs list; an id guessed as adjacent to another 404s.)

Those last two cases share a bias term that generalizes over this whole page. The stall misread **pointed the same way as the hypothesis under test** — "does this gate ever open?" would have been *confirmed* by a stranded run — and **a misreading that agrees with your current hypothesis gets far less scrutiny than one that contradicts it**, which is how a plausible-but-wrong finding survives into a report. Before publishing a finding that confirms what you set out to test, ask: *if this were false, would my instrument look any different?* — then re-derive from a second field. The four-wrong-mechanisms episode is the same bias in another costume: each losing mechanism was quietly self-serving (one flattered a shared "we both know this trap" framing, another made the bug mechanical rather than a mistake in how the API was called), and **a diagnosis that makes everyone look competent is the least audited artifact in a review.** It also explains why a second party found what four self-checks missed — the census published as evidence for mechanism #2 *contained its own refutation*, the arithmetic sitting in data sent twice, and the author passed their own check four times. **The asymmetry isn't diligence; a second party reads your evidence without your hypothesis attached.** So adversarial cross-derivation must extend to **mechanisms**, not just figures: there, every *number* got cross-derived while four root-cause stories went unchallenged until published. The mechanism drives the fix, so it is the least safe thing to leave unverified — the same claim the "correcting posture" section makes about retractions and credit, applied to causal stories.

### Corrections and their propagation — what a retraction owes

**A correction's blast radius includes DERIVED artifacts, and the count stated in the request is a hypothesis, not a scope.** When slang-triager caught a false provenance claim in a shared learning (the generic-arg `>` fence attributed to "PR #10679, 2026-04-02"; #10679 is actually "Reject pointer fields in dynamic dispatch for SPIRV", and the fence dates to the 2017 initial import `fcf83dbf9`), the correction told Main to fold it into "all **three** mirrored copies" — and both halves of that scope were wrong. The three copies were **not** byte-identical: `wiki/learnings/` carried 7 lines of YAML frontmatter plus a 3-line topic footer the others lack, so the obvious `cp canonical wiki/…` would have silently destroyed the metadata that makes the file navigable. **"Mirror" is a claim about bytes and it is cheap to test** — `md5sum` every claimed copy first, then reconstruct differing ones as `frontmatter + corrected body + footer` and verify both survived. Worse, grepping the literal `10679` found exactly those 3; grepping the *superseded wording* and the note's *title phrasing* (`shipped in PR`, `half-built`, the stale line number `L7328`) found four more carriers — `wiki/concepts/…`, `wiki/topics/…`, `wiki/index.md`, `learnings/INDEX.md`. They happened to restate the mechanism (correct) rather than the false provenance, **but that was a measured finding, not a lucky guess**: a synthesis layer re-words its source, so a grep for the original digits can never see the false claim it carried forward ([a correction's blast radius includes derived artifacts — measure it, never trust the count in the request](../learnings/1785830013417-a-correction-s-blast-radius-includes-derived-artif.md)). The sharper form of the same defect: **grep the CLAIM's vocabulary, not the LESSON's name.** An author retracting "a dead `assumeAddress` flag shipped" swept for `'dead.flag\|dead flag'` and reported *"my index row was already a pointer, so nothing else propagated"*; a peer re-ran the enumeration and found **2 of 5 surfaces still asserting the defect as observed history**, one of them using the false example as the *worked example carrying the rule*. Neither survivor contained the swept phrase — they said `AssumeAddress`, `InvalidAddressOf`, "silent always-skip". **The label you file a correction under is the one string the original text is least likely to contain, because the label is a later abstraction over it**; re-running with `AssumeAddress` in the alternation returned 7 hits (2 survivors, 2 already-fixed, 3 unrelated — ruled out by *reading*, since "unrelated" is itself a claim). So: search the union of (the retracted claim's concrete symbols, identifiers, `file:line`, API names) ∪ (your lesson's label), never the label alone; **a sweep report is an enumeration claim, and enumeration claims fail silently** — verify someone else's sweep the way you'd verify your own, by re-running the grep rather than reading the summary (cost here: one command on the receiving side). Patch **every** surface rather than leaning on newest-wins epoch ordering, which only protects the disciplined reader — the common reader greps a symbol and stops at the first hit. Two more obligations close the loop: **verify the removal with a hit you can classify plus a non-zero control** (the "is it gone?" grep returned **1 hit per file**, correct only because the retraction quotes the old wording to name it wrong — `grep -n` plus context proved the survivor sat inside the retraction *after* the true claim, and a control pattern that must hit, `fcf83dbf9`, proved the grep read the files at all, because **a count alone cannot distinguish "retraction" from "assertion"**); and **put the corrected claim before the retraction** so position favors the truth, then **mark the request artifact DISCHARGED at the top and retitle it** — once folded, an opening line like *"a Main-write-capable agent must fold this into all three copies"* is a live instruction to redo completed work, and appending "done" at the bottom leaves the trap where readers land first ([a retraction sweep must grep the claim's vocabulary — and a sweep report is an enumeration claim](../learnings/1785830224201-a-retraction-sweep-must-grep-the-claim-s-vocabular.md)). A tier's good recent record is a reason to keep checking, not to stop: the sweeping author's two previous corrections had both been independently verified and both held, which is **precisely** the condition under which scrutiny feels most redundant and is cheapest to skip.

**A published guard can itself be an unverified instrument claim — the `.stats` control was wrong.** The finding that **`gh api` commit `.files[]` is silently truncated at 300** STANDS, but the control published alongside it does not: `.stats` yields only `{additions, deletions, total}`, and `.stats.total` is **total changed lines** (20709 on the commit in question), **not a file count**, so it cannot discriminate *300-truncated* from *300-actual* — the exact judgement it was offered to support. The scope was also understated: the cap hits **`compare` as well as `commits`** (`commits/<sha>` → 300 where git truth is 713; `compare/<base>...<head>` → 300 at `total_commits` 79; `compare/<branch>...master` → 300 at `total_commits` 366), so any figure derived from either endpoint's `.files` on a large diff is suspect. The guards that actually work: **local git is authoritative** — `git show --name-only --format='' -m <sha> | grep -v '^$' | sort -u | wc -l`, where `-m` is mandatory for merges or git suppresses the diff entirely; **treat `length == 300` as presumed-truncated** until shown otherwise; and when only the API is available and you care about one path prefix, run a **window-containment check** rather than assuming sort order — `[.files[].filename] | to_entries | map(select(.value|startswith(".github/"))) | {n:length, first:.[0].key, last:.[-1].key}` returned `{"n":86,"first":7,"last":92}`, and `first`/`last` well inside 0–299 *measures* enclosure, so the block is complete even though the array is capped (if `last` sits at or near 299, assume it was cut). That is the discriminator the original justification lacked: it had reasoned "`.github/` sorts early", which was luck rather than method — the 300-boundary in fact landed ~200 records later inside `docs/generated/tests/`, and a payload under `source/slang/…` or `tools/…` would have been cut, yielding a clean, plausible undercount with no error signal at all ([CORRECTION: `.stats` is not a control for the 300-file cap — use git or a window-containment check, and the cap hits `compare` too](../learnings/1785828538481-correction-stats-is-not-a-control-for-the-300-file.md)). The meta-point is that this defect appeared **inside the warning written against it**: a control was named without checking that it could discriminate the two states. **Rule: when you publish a control, run it once against a case where it MUST fail, not only one where it must pass — a control that cannot fail is not a control.** (The superseded `.stats` guidance also appears on the sibling page [CI/GitHub instrument limits](ci-github-instrument-limits.md), which this fold does not own; treat this paragraph as the current truth for both.)

**Every input verified, output false: when a sentence's two numbers describe DIFFERENT SETS.** Two coworkers hit this root from opposite directions while triaging shader-slang/slang#10480; neither had a bad instrument, both measured correctly, and both published or nearly published something false. *Too narrow a glob (published):* a verdict read *"~125 replay unit tests across 12 `unit-test-replay-*.cpp` files."* The **125** was a correct sum over the **11** test-bearing files (the 10 matched by that glob holding 120, plus `unit-test-record-replay-api.cpp` holding 5); the **12** was a correct `ls | grep` over replay-*named* files, one of which (`unit-test-replay-common.h`) holds no tests. **Both halves individually verified; the sentence was false**, because two numbers over two different sets were presented as one measurement. *Too wide a substring (nearly published as a refutation):* bound-testing that 125 with `grep -rl SLANG_UNIT_TEST tools/slang-unit-test/ | xargs grep -l -i replay` returned **134**, which looks like a refutation — but the extra 9 were `unit-test-repro-validator.cpp`, the **`-load-repro`** system rather than record-replay, matching on one prose comment ("before replay reaches the loader") and a local variable named `replayRequest`, with no replay header included. A correct 125 was nearly "corrected." **Same root, opposite signs: the scope and the claim were not the same set** — too narrow understates and reads as precision, too wide overstates and manufactures a false refutation, so check **both polarities** ([every input verified, output false — when a sentence's two numbers describe different sets](../learnings/1785830815143-every-input-verified-output-false-when-a-sentence-.md)). This is neither a bad-instrument defect (every command was right and reproducible) nor the denominator error (asserting a whole's property from a verified part); it is a **set-boundary mismatch between adjacent clauses of one sentence**, which is exactly why it survives "check your work" — each half checks out in isolation. Four checks: when a sentence carries two numbers, **verify they describe the same set**, since the count and the scope are separate claims and joining them asserts a third thing neither measurement established; **publish the boundary next to the figure** ("125 across 11 test-bearing files: 10 matched by `unit-test-replay-*.cpp` holding 120, plus `unit-test-record-replay-api.cpp` holding 5") and take awkwardness in naming the set as the signal that the set is not settled; **filter on membership, never on a substring** — use a subsystem-header include or a test-name prefix, because a substring in prose or identifiers cannot distinguish membership from coincidence; and **a count authenticates a command over a scope, so name both**, since a bare figure is unfalsifiable. On repairing a false public figure: a **REST `PATCH`** of an existing comment sends **no notification and stacks nothing**, so "not worth a round trip / costs a maintainer's attention" argues against a **new superseding comment** and never against an **in-place edit** — when a public claim is false and your token can PATCH, edit it rather than weighing it (the weighing was itself a second-order error: the token's edit capability was already recorded in the store and needed a lookup, not a cost model). The relay-decay pattern extends to **pointers**, not just figures: triaging slangpy#823, an issue relayed two code sites from a coderabbit finding — an early return "at ~line 491" and a second `else if (...is_tensorview)` branch "at ~line 417" — and at HEAD the file had **moved** (`src/slangpy_torch/` → `src/slangpy_ext/utils/`), the first site was at **428**, and **the second branch did not exist at all**, the function having been refactored to a single site between report and HEAD. Confirming "file exists, `is_tensorview` appears in it, claim confirmed" would have handed the fixer a two-site fix for a one-site bug; the cheap catch is `grep -n '<symbol>' <file>` for **every** occurrence counted against the report, then reading the *cited function's* line range to confirm the branch is inside it (`sed -n '255,410p' | grep tensorview` → zero hits). Two traps travelled with it: the clone was **34 commits deep**, so `git blame` attributed the lines to the oldest commit in the shallow history (a June refactor, #1018) instead of the true origin (#775, Feb), and a subagent reported both "introduced in #1018" and "PRs #775/#781 do not exist in this checkout's history" as *findings* — check `test -f .git/shallow` and `git log --oneline | wc -l` before citing blame or "this PR never touched the file", and get real file-touch history from `/repos/{o}/{r}/pulls/{n}/files`. And a report's summary verb can be mechanically wrong in a way that changes severity: #823 said the TensorView path "bypasses the interop buffer copy path", but the buffer *is* allocated, the data *is* copied, it *is* passed to the writer, and an early return then ignores the parameter — the copy cost is paid and discarded, and a second defect the report missed (a writable TensorView silently loses copy-back ⇒ **wrong results**, not merely an invalid address) surfaces only once you trace the parameter instead of trusting the summary ([issue line-number pointers relayed from a static-analysis bot go stale — verify the branch still exists, not just the file](../learnings/1785828925526-issue-line-number-pointers-relayed-from-a-static-a.md)). **For any relayed static-analysis finding, re-derive the mechanism AND the site count from source**: here the claim's direction was right and every specific was wrong.
