# slang-test False Greens and Verification Discipline

Running the slang-test harness is one thing; **trusting its result** is another. This page covers the ways a green run can be meaningless — chiefly the test-server false-green cluster (the `-v` verbosity/reporter drift and replay-folder collisions it borders are on [slang-test Harness Internals and In-Process Unit Tests](slang-test-harness-internals-and-unit-tests.md)) — and the verification discipline (stale binaries, positive/negative controls, discriminating tests, load-bearing counts) that keeps a PASS from carrying zero information.

## TL;DR

- **Run `slang-test` from the repository root.** Parallel form: `./build/Release/bin/slang-test -use-test-server -server-count 8`. Single test: `slang-test tests/path/to/test.slang`. Unit tests: `slang-test slang-unit-test-tool/`.
- **Never use `$?` as the pass/fail signal — `slang-test`'s exit code was 0 on a FAILED test.** Parse the `FAILED test:` / `% of tests passed` lines.
- **A unit test that crashes the test server was reported PASSED pre-PR #11753** (RPC death leaves `ExecuteResult resultCode=0` → Pass), so a test that "starts failing after #11753" is **crashing the server**; that PR only changed reporting.
- **The unit-test retry path in test-server mode also reports failures as passes (#11911)** — a green merge-queue or per-PR gate does **not** certify C++ unit-test health. Verify behaviorally.
- **Device caching in `slang-test` silently defeats per-invocation debug-callback bridges** — a cached device reuses the prior callback wiring, so per-invocation regressions go undetected as false greens.
- **`slang-test` can crash at startup in-container while direct `slangc` runs fine** — don't read a harness crash as a compiler failure; beware a codex "revert-without-rebuild" false positive.
- **For a GPU-free test that must exercise real RHI device code (not a mock), create a real CPU-backend device inside a `gfx-unit-test` `SLANG_UNIT_TEST`.**
- **Harness internals — `-v` verbosity plumbing, replay-folder collisions under parallel test-servers, and how to unit-test harness and compiler internals (own-TU dual-compile, Windows per-DLL CRT environments)** — live on [slang-test Harness Internals and In-Process Unit Tests](slang-test-harness-internals-and-unit-tests.md).
- **Prove the relink before reporting numbers: require `test_binary_mtime > build_start`.** A build exiting 0 can rebuild nothing, and a stale binary *passes* the very test you are validating.
- **Re-run suite pass-counts yourself for a PR body**; don't transcribe a subagent's number.
- **Re-run any subagent's cited reproducer yourself, and anchor IR greps to the TYPE** (`kIROp_PseudoPtr`, `= *pseudo_ptr(`) so they can't match a mangled symbol name.
- **Negative-control every branch-coverage claim**: neuter the target branch, rebuild, re-run. If the test still passes, it does not isolate that branch — drop it.
- **Probe each branch of a new pass at each parent kind** (function, global init, module-scope `static const`) via a whole-value use; a lowering moved later needs a `-target glsl` value run.
- **One positive control per HAZARD, not per fix.** When a fix converts leak into double-release, sabotage the specific new guard (`if (owned)` → `if (true)`) and extend the test so it has something to trip on.
- **Count assertion-bearing tests (a `//TEST:` directive plus CHECKs), not test files, and name which test carries the proof.** Support fixtures are inputs, not coverage.
- **Ask: in my test's configuration, does the fallback path produce the same answer as the fix?** If yes, that test cannot distinguish fixed from broken — construct the case where fallback and correct answer differ.
- **Bound a small change to a shared resolver empirically: byte-compare head vs master `slangc` over every SPIR-V test, and log every input where old and new logic disagree.** Normalize worktree paths first (`-g2` embeds them). Disagreements that are not overridden downstream are where undisclosed fixes and missing tests hide.
- **A worktree-cleanliness-guard trip is not always author hygiene** — it can be a deterministic test that crashed mid-run. Grep the SAME run's log for `FAILED test:` / crash first.
- **`DIAGNOSTIC_TEST(diag=CHECK)` does catch a crash→diagnostic regression via empty stderr** — but only when diagnostic and crash are mutually exclusive. If the crash is downstream of the diagnostic, add a `SIMPLE` test asserting `result code = N`.
- **A fatal diagnostic suppresses codegen, so positive-compilation cases must live in a separate file.**
- **`//CHECK:` in a DIAGNOSTIC_TEST is exactly 8 chars — carets start at column 9**; a leading space fails "Column position(s) don't match". Match by error CODE, and quote the `.mailmap`-mapped name when git-blame identity matters.
- **Backend-codegen compile time IS separately measurable in-tree today** (`-report-perf-benchmark` + `tools/compile-perf`); scrutinize a subagent's *bottom line* more than its file:line findings. Suspect RPC timeout / workload sizing before escalating a flaky test to a concurrency-contract design.
- **A SIMPLE lane never runs spirv-val, and a `//CHECK:` line followed by a separate `// ^^^` line is not parsed as a check.** Pin emitted ops instead of "no VUID", use the `/*CHECK: … */` block form for carets, and make every diagnostic test fail on master first.

## False Greens: Test-Server Crashes Reported as Pass

A unit test that crashes the test server is reported **PASSED** pre-PR #11753 ([slang-test false-green: a unit test that crashes the test-server is reported PASSED (#11751)](../learnings/1782398466162-slang-test-false-green-a-unit-test-that-crashes-th.md)). Root cause: an RPC/connection death leaves `ExecuteResult` at its default `resultCode=0` which maps to Pass. PR #11753 fixes slang-test to record RPC failures as Fail — so a test that "starts failing after #11753" is actually crashing the server; the PR only changed reporting ([slang-test RPC-failure reporting (#11753): 'fails after the fix' ⇒ test-server crash](../learnings/1782397269166-slang-test-rpc-failure-reporting-11753-fails-after.md)).

## test-server retry false-green (#11911) — verify behaviorally; merge-green ≠ unit-test health

The unit-test retry path silently reports failed tests as passing in test-server mode (#11911), extending the false-green cluster (#11751/#11753) ([1783009679066-slang-test-test-server-retry-false-gre](../learnings/1783009679066-slang-test-test-server-retry-false-green-11911-gh-.md)). Fix these behaviorally, not by reading code — the Defect-A registry-drain repro is platform-dependent ([1783013967417-slang-test-harness-false-green-fixes-v](../learnings/1783013967417-slang-test-harness-false-green-fixes-verify-behavi.md)). Behavioral verification is required for the harness's *reporting flow* only; struct-driven harness internals can carry a `slang-unit-test` ([Harness Internals](slang-test-harness-internals-and-unit-tests.md)). Fleet consequence: **a green merge-queue / per-PR CI gate does NOT guarantee C++ unit-test health** until the #11911 fixes land (fix PR #11913 open as of 07-05) ([1783239972308-slang-merge-queue-green-c-unit-test-he](../learnings/1783239972308-slang-merge-queue-green-c-unit-test-health-test-se.md)).

Several verification traps recur. (1) `slang-test` can crash at startup in-container while direct `slangc` runs fine — don't read the harness crash as a compiler failure, and beware a codex "revert-without-rebuild" false positive where the old binary is still on disk ([Slang verify gotchas: slang-test crashes at startup in-container; codex revert-without-rebuild false positive](../learnings/1782819445679-slang-verify-gotchas-slang-test-crashes-at-startup.md)). ## Reproducer & Regression-Test Verification Discipline

Three verification traps recur when a regression test or a subagent's repro is taken on faith. **(1) Negative control before trusting branch coverage.** A passing test meant to cover a *specific* branch is not proof it exercises that branch — it may pass via a different always-present trigger. Temporarily neuter the target branch (e.g. `continue` instead of `return true`), rebuild, re-run; if it STILL passes, it doesn't isolate the branch. On PR #12281 a generic-empty-type test passed even with the `IRGeneric` branch of `hasEmptyTypeLegalizationWork` neutered (any named empty struct is hoisted to module global scope and fires the struct-root scan regardless), so the misleading "generic coverage" test was dropped ([verify a test isolates its target branch with a negative control](../learnings/1785548777549-verify-a-test-isolates-its-target-branch-with-a-ne.md)). **(2) Re-run a subagent's cited reproducer yourself, and grep IR by TYPE not substring.** A subagent reported a confident PseudoPtr reproducer it never ran — the source fails front-end E41019, and its "PseudoPtr count" came from `grep -i pseudo` matching the mangled *function name* `test_pseudo_ptr`, not `IRPseudoPtrType`. Run the repro before trusting it, and anchor IR-type greps (`= *pseudo_ptr\(`, `kIROp_PseudoPtr`) so they can't match symbol names ([verify a subagent's reproducer by running it; grep the IR TYPE not a symbol substring](../learnings/1785548791828-verify-a-subagent-s-reproducer-by-running-it-grep-.md)). **(3) A worktree-cleanliness-guard failure can mask a real test failure.** A `slang-test left generated or modified files in the worktree` CI trip is not always benign author-cleanup — it can be the downstream symptom of a deterministic test that crashed mid-run. On PR #12182 a leftover `moduleG6276.slang` was first classified as hygiene, but a fresh run exposed `optixMultipleDefinition.internal` failing deterministically on linux-debug/release + windows. Grep the SAME run's test-slang log for `FAILED test:` / `COMPILE ERROR` / crash before stopping at "hygiene" ([worktree-cleanliness-guard can mask a real test failure](../learnings/1785535887677-worktree-cleanliness-guard-can-mask-a-real-test-fa.md)). **(4) Probe every branch of a pass at every parent kind, through whole-value uses.** On #13378 R2 `lowerArrayBuiltinCasts` unrolled ≤16-element casts and looped otherwise; the loop branch asserted an enclosing block (assuming module-scope casts have literal length), but the condition was `!literal || count > 16`, so `static const row_major float4x4 src[17]; static const float4x4 dst[17] = src;` with `dst` passed to a function hit the release assert (E99997) on every target. Element reads (`dst[i]`) missed it because a `getElement(cast)` peephole folds the cast away. Test each branch at each parent kind; when a PR moves a lowering later (past `deferBufferLoad`), build its value test with `-target glsl`, where revived whole-buffer loads emit `copyLogical` and hit E99999 (#13379) ([late-lowered IR pass: test literal-length arrays above the unroll limit at module scope](../learnings/1790933910032-late-lowered-ir-pass-test-literal-length-arrays-un.md)).

## Bounding a shared-resolver change: byte-compare head vs master over every SPIR-V test

A small edit to a resolver that many paths share (on PR #13610, `getGlobalParamAddressSpace` in `slang-ir-spirv-legalize.cpp`) cannot be bounded by reading the diff, but it can be bounded by measurement. Build Release at head and reuse an existing Release build at the same base as master. Parse every `//TEST:SIMPLE...:` line that targets SPIR-V, run both `slangc` binaries with identical arguments (cwd = the head worktree, `-o` into a scratch dir rather than the worktree), and compare stdout plus stderr; also compile every Vulkan compute test with `-target spirv-asm -stage compute`, once plain and once with `-fvk-t-shift 100 0 -fvk-s-shift 200 0 -fvk-u-shift 300 0`. **Normalize worktree paths before comparing**: `-g2` debug info embeds the `-I <bin dir>` `OpString` and source hashes, and 100+ apparent diffs vanished once the worktree names were replaced. Separately, instrument the changed function to log, under a `getenv` gate, every input where the old and new logic disagree, and run the full suite with the variable set. On #13610 the pair found an **undisclosed second fix**: a ParameterBlock in space ≥ 1 under `-fvk-u-shift`/`-fvk-t-shift` threw E99997 on master, because the old loop was order-dependent (`[UA, RegisterSpace]` threw, `[RegisterSpace, UA]` did not); no issue tracked it and the PR had no test for it. They also showed that the other ~226 changed reconciliations were overridden downstream, so output was byte-identical. Cross-check newly accepted output against the direct-SPIR-V `Binding`/`DescriptorSet` decorations from `-emit-spirv-via-glsl` on master, which never ICEd. Logistics: a new `git worktree add` tree has no submodules, so copy `external/` from an existing worktree at the same base with `tar` (rsync isn't installed) ([byte-compare head vs master slangc over all SPIR-V tests](../learnings/1791924730900-review-technique-byte-compare-head-vs-master-slang.md)).

## DIAGNOSTIC_TEST Caret Alignment + git-blame .mailmap Identity

Two authoring gotchas for the slang-test **DIAGNOSTIC_TEST** matcher (distinct from LLVM FileCheck — it parses machine-readable diag output and runs even when FileCheck isn't installed). A `//CHECK:` prefix is exactly 8 chars, so carets must start at the char immediately after it — `//CHECK:^^^ E41000` puts the first caret at column 9, while `//CHECK: ^^^` (leading space) shifts every caret and fails with "Column position(s) don't match"; slang-test prints a "Suggested annotations you can copy" block on mismatch, so use it as ground truth and match by error CODE (`E41000`), not free text. A parallel provenance trap when answering "who wrote this?": `git blame`/`%aN` render the CURRENT name via `.mailmap` (shader-slang maps historical `Tim Foley` → `Theresa Foley`), so quote the name blame ACTUALLY shows (`%aN`, mailmap-applied), not raw `%an`; find a comment's origin PR with `git log -1 <sha>` or the `git log -S '<text>' --reverse` pickaxe ([DIAGNOSTIC_TEST caret alignment + git-blame .mailmap identity (slang#12236/#12245)](../learnings/1785230187967-diagnostic-test-caret-alignment-git-blame-mailmap-.md)).

**Two caret forms check nothing or cannot reach.** A `//CHECK:` on one line with `//   ^^^^ message` on the next is not parsed as a check at all: on PR #13659 a `DIAGNOSTIC_TEST(diag=CHECK,non-exhaustive)` written that way passed on master, where the diagnostic does not exist, and on a mutated head with the cause removed. The single-line `//CHECK: ^^^ msg` cannot point at columns below 10, because the prefix occupies them, and fails with "Column position(s) don't match". The block form works, with carets aligned to the source columns of the previous non-annotation line:
```
uint loadWithTargetOnly()
/*CHECK:
     ^^^^^^^^^^^^^^^^^^ 'loadWithTargetOnly' uses undeclared capability 'spirv_1_0'
*/
```
Every new diagnostic test needs a revert or mutation drill: it must FAIL on master or with the cause removed ([separate //CHECK: + // ^^^ lines check nothing](../learnings/1792102157772-diagnostic-test-caret-annotations-a-separate-check.md)).

## `diag=CHECK` is not LLVM FileCheck: `CHECK-NOT`/`CHECK-DAG` are silently ignored, and it's exhaustive by default

The `//DIAGNOSTIC_TEST:SIMPLE(diag=CHECK)` matcher (`checkAnnotations` in `tools/slang-test/diagnostic-annotation-util.cpp`, driven by `_diagnosticAnnotationTest` in `slang-test-main.cpp`) is a **custom annotation matcher over machine-readable diagnostics, not LLVM FileCheck**. slang-test adds `-enable-machine-readable-diagnostics`, so each diagnostic arrives as a tab-separated row (code, severity, location, message) with no source echo, and the parser recognizes only the exact prefix `//CHECK:`. `//CHECK-NOT:` and `//CHECK-DAG:` fail that prefix and are **silently dropped**; they work only under `filecheck=CHECK`. Combined with `non-exhaustive`, a test whose only annotations are `CHECK-DAG`/`CHECK-NOT` has zero recognized annotations and **passes vacuously**, so prove a diagnostic test is live by breaking one annotation and watching it FAIL. The negative guarantees come from **exhaustive matching, the default** (`exhaustive = !isNonExhaustiveDiagTest()`): every emitted row must be matched and vice-versa, so an unexpected `E99997` ICE or a duplicate diagnostic leaves an unmatched row and fails "Exhaustive check failed". To prove a case does not warn, leave it unannotated. Annotations match by **substring** against message, severity, error code or "severity code", each consuming one unmatched row. **One diagnostic is often two rows**: a primary row and a span row, deduplicated only when the span text equals the primary's. So `//CHECK: E29000` alone is insufficient; annotate both facets (`//CHECK: E29000` + `//CHECK: snippet`). No-location diagnostics (Line 0/Col 0) still work exhaustively if every error and span row is annotated by text in emission order. Add `non-exhaustive` only for a genuine secondary diagnostic you are deliberately not annotating; the harness rejects an unnecessary one ([diag=CHECK: CHECK-DAG is ignored and non-exhaustive can pass vacuously](../learnings/1789680163713-slang-test-diag-check-check-dag-is-ignored-and-non.md); [diag=CHECK is exhaustive and ignores CHECK-NOT](../learnings/1789718875570-slang-diag-check-diagnostic-test-is-exhaustive-and.md)). A design corollary from the first atom: when two passes independently diagnose the same IR shape, hand off at a single point (establish the winning diagnostic exactly where you suppress the other), because the passes can differ in reachability and "the second pass will re-derive it" can silently drop the diagnostic.

## Stale Test Binaries and Per-Hazard Positive Controls

**A stale test binary can pass the very test you are validating — prove the relink before reporting numbers.** The cheap check is an mtime comparison: capture a timestamp before the build and require `test_binary_mtime > build_start`; refuse to report numbers if it doesn't hold, and prefer that positive relink signal over inferring from a build command's exit 0 (a build can exit 0 having rebuilt nothing relevant). Observed on slangpy#1073: a `sgl_tests` binary in the worktree was **10 days old** and still passed the cross-thread profiler test used to validate a concurrency fix; the build subagent caught the stale mtime and refused to report. This is nastier than an ordinary stale-artifact bug because the stale binary *passes* (no error) and the result is *plausible* (same test name, same numbers), and for a nondeterministic timing fix it means you have *zero* signal while believing you have positive signal. The general test: *if my change hadn't been compiled in at all, would this still have gone green?* If yes, the PASS carries no information — and the same discipline applies to any cached/derived artifact you then measure (binaries, generated docs, emitted shader assembly, lockfiles) ([a stale test binary can pass the very test you're validating](../learnings/1785772374507-a-stale-test-binary-can-pass-the-very-test-you-re-.md)).

**One positive control per HAZARD, not per fix — when your fix introduces a new failure mode, prove the test catches THAT one too.** On slangpy#1073 the fixer fixed a reference **leak** in `Profiler::end_zone` — and the fix was itself buggy: releasing on *every* zone-stack mismatch let the same reference be released **twice**, and since `release_zone_from_global_frame` asserts `count > 0`, release builds underflow a packed counter and corrupt shared state. A leak had been converted into potential memory corruption. The remedy needed **two** controls: remove the release stanza (proves the test still catches the original leak) *and* weaken the new ownership guard to `true` (proves it catches the new double-release) — and the test had to be **extended** to re-present the rejected token, because control 2 has nothing to trip on otherwise. How to apply: enumerate hazards not fixes (leak, double-release, underflow, deadlock, stall) and give each its own control; **sabotage the specific guard** (`if (owned)` → `if (true)`), not the whole feature; if a control has nothing to trip on, the test is too narrow. Watch for *"my fix converted failure mode A into failure mode B"* — common in reference counting, ring buffers, and completion gates, and invisible to a control that only tests A ([one positive control per hazard](../learnings/1785773520364-one-positive-control-per-hazard-when-a-fix-introdu.md)).

## Crash→Diagnostic Regression Tests + Load-Bearing Pass-Counts

`//DIAGNOSTIC_TEST:SIMPLE(diag=CHECK):` robustly catches a crash-regression even though its path (`_diagnosticAnnotationTest`) parses only stderr diagnostics and ignores the process result code: the buggy compiler segfaults with **empty stderr / zero diagnostics**, so the exhaustive annotation check fails when the expected (e.g. `E30015`) has no match. This holds only when the diagnostic and the crash are mutually exclusive — true for a front-end error (`executeActionsInner` returns before `generateIR()` on non-zero error count); if the crash is *downstream* of the diagnostic, add a `SIMPLE` `.expected` test asserting `result code = N`. Also: a fatal diagnostic suppresses codegen, so positive-compilation cases must live in a separate file ([DIAGNOSTIC diag=CHECK catches a crash-regression via empty stderr](../learnings/1785349746955-diagnostic-diag-check-catches-a-crash-regression-v.md)). And treat pass/fail counts in a PR body as load-bearing: re-run the suite yourself rather than transcribing a build subagent's number (a subagent reported `defer/` as 39/39; a fresh run was 38/38 — 13 dx11 variants ignored) ([verify slang-test suite pass-counts from a fresh run, not a build subagent's number](../learnings/1785349753826-verify-slang-test-suite-pass-counts-from-a-fresh-r.md)).

## Counting Assertion-Bearing Tests + Backend-Codegen Timing Is Measurable

**Count assertion-bearing tests, not test files — and name which one carries the proof.** A coverage claim inflates without anyone lying when the count is taken over the wrong scope: "6 tests committed" was really **3 assertion-bearing tests plus 3 support inputs** (an `__include`d file, an `#include`d helper, a second top-level file). Support fixtures are **inputs, not coverage**. Worse than the count: two of the three real tests could pass while the feature was broken. The feature scoped a SPIR-V `DebugFunction` to its owning `DebugCompilationUnit`; when the lookup misses, emission falls back to a module-global scope pinned to the entry-point CU (PR #10907 for #10906) — so in a single-CU translation unit the broken fallback *coincides with the expected answer* and the test goes green either way. Only the **two-CU** test discriminates — a discriminator, not a fixture, so say so in the PR body *and* in a test comment so a future editor doesn't prune it. Generalized authoring question whenever a feature has a fallback path: *in my test's configuration, does the fallback produce the same answer as the fix?* If yes, construct the case where fallback and correct answer *differ*, and confirm each test fails *for the reason you intend* ([count assertion-bearing tests, not test files — and name your discriminating test](../learnings/1785824059809-count-assertion-bearing-tests-not-test-files-and-n.md)).

**Backend codegen compile time IS separately measurable in-tree today — and a subagent's inverted bottom line is the generalizable tell.** "Is this user's slow compile front-end or backend?" is answerable with no compiler change: `slangc -report-perf-benchmark` prints per-phase timers as `[*] <phase> <count> <ms>`, and `tools/compile-perf/breakdown.py:56` already lists **`emitEntryPointsSourceFromIR`** (the `SLANG_PROFILE` at `source/slang/slang-emit.cpp:2747`) as a named bucket under `generateOutput`. An `Explore` subagent reported the exact opposite bottom line — "backend codegen time is NOT separately attributable… recommend updating `breakdown.py`'s TREE" — at a line it itself cited. Why it inverted: it read that `SLANG_PROFILE` is a **flat** RAII timer with no parent/child link and concluded the *tooling* cannot attribute — but nesting is **reconstructed downstream** by `breakdown.py`. **The tell: a claim about a CAPABILITY derived from reading a MECHANISM one layer below it.** The cheap check is not "re-read the argument" but *run the tool / open the file the capability lives in* — a subagent's **bottom line** deserves more scrutiny than its file:line findings. Real caveat: the profiler is flat, so a parent's time exceeds the sum of named children and `breakdown.py` surfaces the gap as `<parent> (self)` — a named leaf is trustworthy, but an *unnamed* hotspot needs the self-time residual ([backend-codegen compile time IS separately measurable (`-report-perf-benchmark` + `tools/compile-perf`); a subagent reported the opposite](../learnings/1785838127386-backend-codegen-compile-time-is-separately-measura.md)).

The through-line across the whole family — skipped test, stale binary, vacuous assertion, inert `CHECK-NOT` — is one bug in different disguises: **present but not exercising.** The general check: name the defect, then name the assertion that fails when *only* that defect is reintroduced, and negative-control both directions (flip each positive to a nonexistent name, expect RED; restore and confirm green).

A SPIR-V FileCheck test is a common vehicle for this vacuity. A `//TEST:SIMPLE(filecheck=CHECK): -target spirv` test that only asserts a positive shape line plus `//CHECK-NOT: error:` can be fully vacuous — passing whether or not the fix is present (found on #12592) — for two compounding reasons: (1) the rejected SPIR-V is disassembled into the output even on validation failure (`slang-emit.cpp` calls `disassemble(...)` regardless, and `SIMPLE` FileCheck does not gate on the compiler result code), so a positive `OpTypePointer StorageBuffer` line still matches in the *failed* output; and (2) `CHECK-NOT: error:` cannot catch a SPIRV validation failure, because diagnostics render as `<severity> <id>:` and a validation failure prints `internal error 99999:` — no `error:` substring, so `-NOT` never fires. An extra value-vs-slot trap: a positive `OpTypePointer StorageBuffer` matches in BOTH buggy and fixed modules when only the pointer *slot's pointee* is wrong. Fix pattern: assert the *buggy artifact is ABSENT* (`//CHECK-NOT: PhysicalStorageBuffer`), or that the slot `OpVariable`/`OpStore` operand types agree — and, subsuming this, run every new SPIRV test against the pre-fix binary and confirm it FAILS, or it proves nothing ([SPIR-V test vacuity: a validation-failure disassembly + `internal error` defeats `CHECK-NOT: error:`](../learnings/1789244351461-slang-spir-v-test-vacuity-a-validation-failure-dis.md)).

## SPIR-V Test Verification Locally: Render-API Tagging, Injected `-O0`, and What `spirv-val` Validates

Three compounding traps when verifying a SPIR-V emit fix on a local (often GPU-/Vulkan-less) machine. **(1) Render-API tagging skips compile-only tests.** `slang-test <file>` may report a `-target spirv[-asm]` test as **IGNORED (0/0)** on a box with no usable Vulkan loader — slang-test tags spirv/spirv-asm tests with a Vulkan render-API requirement and skips them when no Vulkan device can be created (slang-test-main.cpp ~5980-6009), even for known-good committed tests (e.g. `coverage-counter-width-*-spirv.slang`, `atomic-64bit.slang`). SPIR-V emit is compile-time, so verify with `slangc` directly plus `SLANG_RUN_SPIRV_VALIDATION=1` (off by default; CI exports it). **(2) `slang-test` injects `-O0` when a directive gives no opt level** (confirmed via `slang-test -v`), so a `CHECK-NOT: OpCompositeConstruct` never exercises the downstream SPIRV-Tools optimizer — the illegal composite appears only at `-O1`/default, making the `-O0`-only check a false green. Pass an explicit `-O1` on the SIMPLE directive (and `-Xslang -O1` on COMPARE_COMPUTE). **(3) Check the validator's real version, don't recall it.** The in-tree validator is **v2026.4.rc2** (not the recalled v2024.2) and `SLANG_RUN_SPIRV_VALIDATION=1` **does reject** logical-pointer Function vars, so a validation-backed test (or validation paired with a spirv-asm `CHECK-NOT` on `OpCompositeConstruct`/`OpCompositeExtract` of a `%_ptr_Workgroup_*` type) beats text matching alone ([in-tree spirv-val v2026.4.rc2 does catch logical-pointer Function vars](../learnings/1790785645539-slang-in-tree-spirv-val-v2026-4-rc2-does-catch-log.md)). Also: `SLANG_RUN_SPIRV_VALIDATION` validates Slang's **pre-optimizer** module, not the final spirv-opt output, and spirv-asm shows a constant's *value* but not its binary *word count*, so a FileCheck on `OpConstant %long 0` cannot catch a mis-sized (32-bit-under-64-bit) pointer-sized constant — only validation can ([SPIR-V compile-only tests are render-API tagged; verify with direct slangc](../learnings/1790009629117-spir-v-compile-only-tests-are-render-api-tagged-ve.md), [slang-test injects -O0; verifying SPIR-V logical-pointer fixes needs explicit -O1 + a current spirv-val](../learnings/1790037466327-slang-test-injects-o0-verifying-spir-v-logical-poi.md)).

---

**A SIMPLE lane does not run SPIR-V validation, so `X-NOT: VUID` proves nothing.** A control fragment shader calling `GroupMemoryBarrierWithGroupSync()` (invalid SPIR-V, VUID-04682 under `SLANG_RUN_SPIRV_VALIDATION=1` with slangc) PASSED a `//TEST:SIMPLE(filecheck=X): -target spirv -stage fragment` lane with `X-NOT: VUID`. `-target spirv` output reaches FileCheck as disassembly, with a "standard error = {" block that a naive `-NOT: error` also matches. Pin the construct itself with `-target spirv-asm` (`CHECK: OpEntryPoint Fragment`, `CHECK-NOT: OpControlBarrier`), run validation separately with slangc plus `SLANG_RUN_SPIRV_VALIDATION=1` for the PR evidence, and check any "no error" detector against a known-bad control first (slang#13631 / PR #13659) [SIMPLE lanes do not run SPIR-V validation](../learnings/1792090114561-slang-test-simple-lanes-do-not-run-spir-v-validati.md).
