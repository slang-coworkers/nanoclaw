# PR-Approver: Design-Fragility False-Safe & Relevance-Class Challenger Misses

Two challenger failure families that a green harness and a correct-provenance spot-check both miss. **Design-fragility:** a representation is unsound even though no test triggers it — interning-safety is not design-soundness. **Relevance class:** a premise is *true* and *irrelevant* — it cites the right file and line but cannot bear on the path in question, so it passes every check we run. Both are worse than an ordinary wrong argument, because the ordinary wrong argument gets caught.

## TL;DR

- Interning-safety ≠ design-soundness. When a review doc's gaps include a design/representation concern — a transient mutable pointer bolted onto an interned/canonical value type, a stack-pointer lifetime/escape, a second parallel representation, a transient invalid-SSA/dominance shape — the challenger must NOT clear it merely because "no test triggers it." A green harness cannot prove a representation is principled; escalate to CHALLENGER_CONCERN → ABSTAIN.
- Treat a maintainer's "how is this supposed to work?" COMMENTED review as a soft-negative even absent CHANGES_REQUESTED.
- "The bad shape is deleted before it matters / thrown away / never actually used" is NOT a proof of safety — it assumes no intervening pass observes it AND that the author intended it, both unproven. A dominance violation in SSA IR is a representation bug regardless of whether one downstream path tolerates it; fix the producer. Raise plausibility on cross-block operand-placement 🔴s in autodiff transpose.
- The RELEVANCE class: a premise can be TRUE and IRRELEVANT. Interrogate every cited claim with TWO questions, not one: (1) is it true? (provenance: right file/line/commit, claim matches source) and (2) does it bear on the path in question? (relevance: name the specific configuration/branch/state the conclusion is about, then check the cited mechanism actually operates in that state).
- Read the enclosing guard of every cited line: `sed -n '<line-20>,<line>p' file | grep -nE "if \(|else|#if"`. If the guard is `X` and the claim is about `!X`, the citation is inadmissible regardless of correctness. When retracting, retract the MECHANISM separately from the INFERENCE and state the guard, not just the line range.
- "An earlier diagnostic already rejects this" needs the mandatory-path proof, not the diagnostic's existence. For a diff adding a bounded recursive predicate: which direction does the fallthrough fail (a cap returning the PERMISSIVE value fails OPEN into the very bug the PR fixes), and is the upstream rejection a universal gate or a per-walker counter (`grep -rn <CAP>` and check the mandatory path; per-walker `recursionDepth` params are the tell). "Finite/valid" does not imply "shallower than a fixed bound."
- "That shape is degenerate / nobody writes that" is a testable claim about behavior — compile it. For a "no-op" control-flow claim enumerate three independent parts: is the condition still evaluated (1), does any body still run (2), is the value used (3) — side effects live in (1)+(2); a claim that only (3) is dead doesn't make them dead. Probe the constrained-generic case explicitly when a change narrows what's accepted. A code owner's APPROVE settles the INTENDED fork, not an undiscussed narrowing the PR body never mentions.
- Citation-uniformity is a mechanical self-check: in an artifact where claims cite `file:line`, the UNCITED load-bearing sentence is the defect. Run one awk pass flagging paragraphs with no `file.ext:NN`, no backtick command, no 6-digit id, no `N/M` ratio; peripheral rigor manufactures confidence in the unmeasured centre. A replacement rationale is a NEW claim needing its own instrument. `runs-on` scope-of-fault ≠ scope-of-routing.
- Review-input integrity: before attributing a missing extraction to a parser, prove the input contained the thing to extract (`grep -ociE` → 0 ⇒ capture problem, not parse problem), then run the fix as a counterfactual and confirm it changes the outcome. Collapsing two independent defects into one causal story is the error.
- Treat "Devin exit 0 + zero flags" as suspicious, never clean — a genuinely clean run renders a `No flags`/`0 Flags` token, so an absent flags summary means the scrape was early. No `\d+ Flags?`, no `No flags`, no `Analysis complete` ⇒ INCONCLUSIVE (ABSTAIN_INFRA). Auth-gated per-flag detail bodies are real signals — probe each, never record them as cleared.
- "Pending at poll end" is "not proven yet," never "absent." Exit 20/22 are timestamped observations, not durable absences; `status green ≠ harvestable review`. Re-probe X immediately before committing any artifact whose content depends on "X was not available," and phrase every negative finding with its observation time.
- Report the LAST occurrence plus the size of the clean run after it, never the first — a range without a denominator hides live-vs-historical. A silence in COMMENTARY is not a silence in the PHENOMENON (logs measure who complained, not what occurred).

## Design-fragility false-safe: interning-safety ≠ design-soundness

**The false-safe: PR #12098 (Memoize Val substitutions) WOULD_APPROVE but the author closed it unmerged for a redesigned successor #12106.** The challenger cleared "gap #4 — transient `substitutionCache`-pointer threaded on `SubstitutionSet`" as "undemonstrated future-proofing," but csyonghe's live COMMENTED review probed that exact wiring ("field appears never initialized to non-null — how is this supposed to work?") and the successor removed it entirely (environment-local cache). The lesson: when a review doc's gaps include a **design/representation** concern (a transient mutable pointer bolted onto an interned/canonical value type, a stack-pointer lifetime/escape, a second parallel representation), the challenger must NOT clear it merely because "no test triggers it" — a green harness cannot prove a representation is principled; escalate to CHALLENGER_CONCERN → ABSTAIN, and treat a maintainer's "how is this supposed to work?" COMMENTED review as a soft-negative even absent CHANGES_REQUESTED. Interning-safety ≠ design-soundness ([approver false-safe PR12098 — challenger cleared the exact cache-wiring axis the maintainer probed; design-fragility gaps aren't advisory](../learnings/1785272574884-approver-false-safe-pr12098-would-approve-but-auth.md)).

The same representation-concern discipline vindicated an ABSTAIN on slang#12095 (autodiff promotion placement). CodeRabbit raised a secondary 🔴 the primary review missed: `promoteOperandsToTargetType`/`transposeArithmetic` reconstructed a forward-block `newInst` referencing a primal `newOperand` placed at `oldLoc` in the REVERSE block — a transient invalid-SSA / dominance shape. Holding at ABSTAIN_POLICY:CHALLENGER_CONCERN @`485ba73b` (not rounding up on the FP narrative) meant the head never got a false-safe; the author then landed exactly one commit ("Preserve SSA when promoting autodiff operands") DELETING the reconstructed-inst path, with a comment stating the very invariant the old code violated, and kaizhangNV APPROVED only the revised head `ede2eab8` (nobody approved the decision head) — so on the `pr_merged` join, diff decision-head-vs-merged-head FIRST: the head moved by one SSA-fix commit, `record_human_verdict(485ba73b)=CHANGES_REQUESTED`, ABSTAIN VINDICATED (do-not-round-up class), not over-caution ([[approver/human-agreement] PR-12095 ABSTAIN-CHALLENGER_CONCERN-VINDICATED: unproven-🔴-fixed-before-merge, decision-head-not-the-merged-head](../learnings/1785436774423-approver-human-agreement-pr-12095-abstain-challeng.md)). The challenger-side lesson is sharper: the *lean* toward false-positive ("the reconstructed container is a throwaway never actually transposed; the block is `removeAndDeallocate()`'d later") was WRONG even though the policy of holding-at-ABSTAIN saved the decision. "The bad shape is deleted before it matters" is NOT a proof of safety — it assumes no intervening pass observes it AND that the author intended it, both unproven; a dominance violation in SSA IR is a representation bug regardless of whether one downstream path tolerates it (fix the producer). Raise plausibility weight on cross-block operand-placement 🔴s in autodiff transpose specifically — differential-vs-primal insts belong in different blocks, so any reconstruction referencing both is a dominance smell; the correct read is "likely real," strengthening toward the same ABSTAIN with a truer rationale ([[approver/challenger-miss] transient-invalid-SSA in IR reconstruction is NOT auto-benign: "throwaway container never transposed" lean was WRONG on slang#12095](../learnings/1785436795717-approver-challenger-miss-transient-invalid-ssa-in-.md)).

## Challenger misses of the RELEVANCE class: a true premise that cannot bear on the path

The 2026-08-03 slang-rhi cluster surfaced a failure family the existing checks are structurally blind to. Every prior challenger discipline interrogates whether a claim is **true** — right file, right line, right commit, claim matches source. These misses were all **true and irrelevant**, and that is worse: a wrong argument gets caught by provenance checking, while a mis-scoped one *passes every check we run*.

**The archetype: read the enclosing guard of every cited line.** On slang-rhi#800 the residency 🔴 was cleared three revisions running on the ground that "EVERY buffer is globally registered via `registerResource` at creation (`metal-buffer.cpp:86`), so it is resident regardless." The finding was about devices **without** a residency set; `registerResource` does all its work inside `if (m_hasResidencySet)` (`metal-device.cpp:611`). So the argument used residency-set-path registration to argue the *fallback* was safe — not a weak argument about the fallback, one that **cannot bear on the fallback at all**. Circular, not merely mis-scoped, and it survived three revisions while being cited as an independent second ground each time, because an argument decorated with real `file:line` reads as mechanism-grounded and a reviewer spot-checking citations confirms them and moves on. The control is two questions, not one — (1) *is it true?* (provenance) and (2) *does it bear on the path in question?* (relevance: name the specific configuration/branch/state the conclusion is about, then check the cited mechanism actually operates in that state). Question 2 is cheap and mechanical for guarded code: `sed -n '<line-20>,<line>p' file.cpp | grep -nE "if \(|else|#if"`; if the guard is `X` and the claim is about `!X`, the citation is inadmissible regardless of correctness. A second-order trap on the way out: a correction that writes "`metal-device.cpp:611-618` adds it to the set" is *true* and **omits the gate**, letting the next reader reconstruct unconditional registration from the correction itself — retract the **mechanism** separately from the **inference**, and state the guard, not just the line range ([[approver/challenger-miss] an argument that cites real file:line but cannot bear on the path — the argument-side twin of the non-discriminating signal](../learnings/1785775240063-approver-challenger-miss-an-argument-that-cites-re.md)).

**"An earlier diagnostic already rejects this" needs the mandatory-path proof, not the diagnostic's existence.** On slang#11118 (`Atomic<T>` as `[__NonCopyableType]` + transitive `typeContainsNonCopyableImpl`) the production bot flagged the new depth cap returning the permissive `false`; the challenger cleared it as pure future-proofing on the theory that the front end rejects anything that deep — an independent critique proved that wrong and the gap became the *principal* ABSTAIN ground. E39997 (`kMaxTypeNestingDepth=128`) is raised by **specific walkers each carrying its own `recursionDepth`** (`slang-check-shader.cpp:604/1307/1509/1645`, `slang-type-layout.cpp:5320`, `slang-check-expr.cpp:2020/2725`, `slang-check-decl.cpp:3173`) — there is no single gate every declaration passes, and E39999 covers inheritance *cycles* only, not a valid deeply-nested acyclic generic struct. Two ordered questions for any diff adding a **bounded** recursive predicate: **which direction does the fallthrough fail** (write out what the cap's return value *means* to every caller — if the permissive value routes to pre-fix behavior, the guard reintroduces the bug at the boundary instead of erroring), and **is the upstream rejection a universal gate or a per-walker counter** (`grep -rn <CAP_CONSTANT> source/` and check whether any site lies on the *mandatory* path to the new code; per-walker `recursionDepth` parameters are the tell). A comment justifying `X` in `if (depth >= CAP) return X;` by asserting which programs are "valid" — here "valid programs have finite-depth struct layouts" — is itself a defect: finite and valid does not imply shallower than a fixed 128 ([[approver/challenger-miss] a depth cap returning the PERMISSIVE value fails OPEN into the very bug the PR fixes; E39997 is not a universal front-end gate](../learnings/1785745165071-approver-challenger-miss-a-depth-recursion-cap-tha.md)).

**"That shape is degenerate / nobody writes that" is a testable claim about behavior, not a licence to clear — compile it.** On slang#12246 (a `pr: breaking change` rejecting non-integer `switch` conditions) I derived WOULD_APPROVE and was overturned at DECISION_REVIEW → ABSTAIN_POLICY:OPEN_GAP, because I cleared a Devin over-rejection flag on the *inferred* premise that a `switch` with no case labels "selects `default` unconditionally ⇒ semantically a no-op ⇒ nobody depends on it." Two probes the critique provoked falsified it: a selector with a side effect + a working default body emits observable HLSL buffer writes at baseline and hits E30607 at head, and `T : IInteger` `default:`-only compiles clean at baseline and is rejected at head — a type parameter *constrained to be an integer* refused for not being one. A no-case-label `switch` is not a no-op: the selector expression is still evaluated (arbitrary side effects), the default body still executes (real control flow), and only the selector's *value* is unused. For any "no-op" control-flow claim, enumerate the three independent parts — is the condition still evaluated (1), does any body still run (2), is the value used (3) — because side effects live in (1)+(2) and a claim that only (3) is dead does not make them dead ([a "no case labels ⇒ semantic no-op" premise was FALSE and overturned my WOULD_APPROVE](../learnings/1785837956189-approver-challenger-miss-no-case-labels-semantic-n.md)). Two aggravating traps to carry: my negative-evidence sweep searched `default:`-only across 196 switches and reported "zero instances" as if exhaustive — it missed empty-body, side-effecting-selector, and constrained-generic variants, so a scope-limited grep reported as a count reads as coverage of the class it doesn't cover; and when a change narrows what's accepted, probe the **constrained-generic** case explicitly, because a predicate keyed on the type's *representation* (`BasicExpressionType`/`EnumDecl`) rather than its *constraints* rejects parameters whose constraints already guarantee the property — the most defensible-looking member of the newly-broken set. A code owner's APPROVE at the pinned head settles the *intended* fork (reject-vs-coerce), not an *undiscussed* narrowing the PR body never mentions; treating a sign-off on the intended change as a sign-off on an unintended side effect is exactly rounding up.

**Citation-uniformity is a mechanical self-check: in an artifact where claims cite `file:line`, the UNCITED sentence is the defect.** The #12246 miss above and a co-occurring orchestrator miss shared one signature — an uncited load-bearing sentence sitting among file:line-cited reads (mine: "no case labels ⇒ no-op"; the orchestrator's: "PASSING spirv-val [0/866] with zero diagnostic text", inferred from a summary line while the log actually held 1732 `- PASS` paired 1:1 with 1732 `- FAIL`). Both authors had been rigorous in the *alarming* direction — re-deriving a bot-authored flake table, constructing off-diagonal CI controls — which is the trap: **peripheral rigor manufactures confidence in the unmeasured centre, and the uncited sentence is the centre.** Run one awk pass over your own draft flagging paragraphs with no `file.ext:NN`, no backtick command, no 6-digit id, and no `N/M` ratio; headings show up correctly-uncited, and what you hunt is a *substantive claim* in that list. It is a grep, not a vigilance rule, and it fired on its own author (an uncited "the predicate is exactly integer-or-enum" — instrumented, the predicate accepts integer-**or-bool**-or-enum at `slang-check-decl.cpp:12038`, cosmetically harmless but imprecise and uncited, which is the point). Two companions: **a replacement rationale is a NEW claim needing its own instrument** — when "runner-scoped to SLANGWIN5" was refuted it was replaced with "the defect reproduces across branches so a rerun re-tests nothing", *also* false and uncited, reading as corrected only because it was newer (being a fix for a known error is not evidence for the fix); and a `runs-on` label set means **scope-of-fault and scope-of-routing are independent** — never infer a dispatch property (which host runs it, whether a rerun helps) from a defect property (where the fault reproduces) ([the uncited sentence is the defect — a mechanical citation-uniformity self-check](../learnings/1785839025292-approver-critique-mustfix-citation-uniformity-in-a.md)).

## Review-input integrity: prove the input before attributing the defect

**A plausible defect found while hunting is the easiest thing to over-credit — run the fix as a counterfactual.** The empty `## Flags` section in a Devin artifact was attributed to `devin-fetch.sh:157` splitting on a real-newline pattern against JSON-quoted `innerText`, and called "confirmed empirically" on the strength of `wc -l` = 1. Decoding first and re-running the *exact* split still yields one part, and `flags?` occurs **zero** times in the scraped page decoded or not — a decode cannot conjure a marker never captured. Actual cause: the done-poll was satisfied *solely* by the `Checks\s*\d+/\d+` CI counter, so the script scraped a page whose Flags panel had not rendered; the flags-toggle click found no matching button and silently no-oped under `|| true`. The missing decode is a **real but latent second bug**, and collapsing two independent defects into one causal story is the error. Before attributing a missing extraction to a *parser*, prove the input contained the thing to extract (`grep -ociE 'flags?' devin-page.txt` → 0 ⇒ capture problem, NOT parse problem), then run the fix as a counterfactual and confirm it changes the outcome ([[approver/challenger-miss] I mis-attributed the empty-Flags defect to the missing json.loads — the real cause is scraping before the panel renders](../learnings/1785787630832-approver-challenger-miss-i-mis-attributed-the-empt.md)).

The underlying tool defect stands on its own and is a **review-input integrity** issue, not a nit: `devin-fetch.sh` exited 0 with an empty flags section on slangpy#1090 while Devin had produced **2 Investigate flags** — one of two review sources silently zeroed. Treat "Devin exit 0 + zero flags" as **suspicious, never clean**: a genuinely clean run still renders a `No flags`/`0 Flags` token, so an *absent* flags summary means the scrape was early. Cheap assertion — no `\d+ Flags?`, no `No flags`, no `Analysis complete` ⇒ INCONCLUSIVE (ABSTAIN_INFRA), and auth-gated per-flag detail bodies ("115 lines left") are real signals whose rationale is unavailable: probe each yourself, never record them as cleared ([[approver/challenger] devin-fetch.sh false-clean: a `Checks N/M` readiness branch plus JSON-quoted innerText](../learnings/1785786175123-approver-challenger-devin-fetch-sh-false-clean-che.md)).

## Negative findings are timestamped observations, not absences

**"Pending at poll end" is "not proven yet", never "absent."** Two approver rows recorded `0/0/0` with docs affirmatively stating no CodeRabbit signal existed — and in both the review had landed *before the doc was written* (slangpy#1085: last poll 15:03:39 exit 22 pending, review 15:04:52, doc 15:06:22, with 4 🟠 Major findings sitting on `pulls/N/comments`; slangpy#1063: harvest exit **20** = "genuine skip, none pending", review 9 minutes later). Exit 22 correctly said "pending, review imminent" and the *last* iteration's result was then treated as durable through the following 2m43s; exit 20 is worse because there is no imminence signal at all — `PENDING_STATUS_RE` matches a *pending commit status*, so a bot that hasn't posted its status yet, or posts green without a review object, fires exit 20 and looks authoritative. The two failure modes multiply: because both docs concluded "no review at all", nothing prompted the manual `pulls/N/comments` read that saved every other affected row. Rules: **re-probe X immediately before committing any artifact whose content depends on "X was not available"**; `status green ≠ harvestable review` and no-status-yet ≠ no-review-coming; and phrase every negative finding with its observation time — "CodeRabbit status was pending as of 15:03:39" is auditable, "there is no CodeRabbit signal" is a different, stronger, and here false claim ([[approver/challenger-miss] a poll that ends "pending" means "not proven yet", not "does not exist"](../learnings/1785779216968-approver-challenger-miss-a-poll-that-ends-pending-.md)). The same discipline applies to the reporting side: report the **LAST** occurrence plus the size of the clean run after it, never the first — "first seen 06-24" and "last seen 07-19, then 557 clean files" support opposite decisions from the same data — and remember that a silence in **commentary** is not a silence in the **phenomenon** (log mentions measure who complained, not what occurred) ([[approver/calibration] report the LAST occurrence plus the clean run after it; a silence in commentary is not a silence in the phenomenon](../learnings/1785822559259-approver-calibration-report-the-last-occurrence-pl.md)).
