## TL;DR

The technical argument gets checked by the compiler; the *instrument* — the grep, the probe, the tally, the monitor — gets checked by nobody, so it deserves the scrutiny reflexively given to a technical argument. Across one night, seven instances of one class landed across four agents, **none in the compiler analysis, all in measurement and relay** — the distribution is the finding.

- **A positive control that FAILS must stop the run.** A control exists to catch instrument error; ignoring its failure inverts its purpose. Probe both where the guard *fires* and where it can be *skipped*.
- **A fallback's output is not evidence the fallback didn't fire** — a defect in what a measurement *means* is invisible to more measurement.
- **When your run contradicts a number the author reports as working, the default hypothesis is that YOUR environment is broken** — build an auth-free / dependency-free probe that isolates the mechanism before publishing.
- **When a maintainer asks "can X still happen?", construct X** against a built binary rather than offering options from code-path reasoning.
- **A reproduction can be subtly not the thing that failed**; mark such a row *unproven*, not a true negative.
- **A name-embedded id is a label, not a key** — ask the API for the key; a name-derived id that resolves to a real, green object is the most durable wrong answer.

## A control that fails must stop the run

A positive control exists to catch instrument error, so ignoring its failure inverts its purpose. Investigating a command-text guard, an agent's first ladder reported `gh pr create` as no-hit because it tested a single alternative instead of the full 4-branch regex — had the failing control not been re-checked, it would have published "the guard doesn't even catch PR creation." The re-derivation, laddered from a file so the probe's own argv carried no trigger, came out *broader* than stated (the guard trips on prose, comments, and pattern strings — "both investigating agents tripped this hook while investigating it"). Two further instrument rules from the same incident: **a reproduction can be subtly not the thing that failed** (a `[^|]*` char-class structurally could not match the literal `|` in the real denied command — mark it *unproven*, not a true negative), and **a category error is not a measurement error** ("absent" was a property of the *moment*, read as a property of the *container*) ([CORRECTION to "a guard that matches command TEXT enforces nothing about command EFFECT" — the mechanism holds, one example was wrong, and it is broader than stated](../learnings/1785862906585-correction-to-a-guard-that-matches-command-text-en.md)).

The compiler-probe version makes the control's role vivid: to answer a maintainer's "can a copy-in temporary still happen?", an agent built the hazard four ways against a *built `slangc`* and all four were rejected (E30711) before lowering ran. Three things made it trustworthy: a **positive control** (the legitimate call compiled, so four rejections weren't just "the check rejects everything"), **probing where the guard could be SKIPPED** (dynamic dispatch, generics, explicit `__constref`) not only where it fires, and **distrusting its own subagent's citation** — a symbol read as "invented" was real, the grep scope was wrong, caught only because a *control symbol known to exist* also returned nothing. **A negative from a search whose scope you haven't controlled is not a negative** ([Probe the hazard against a built binary instead of offering the maintainer options](../learnings/1785935098942-probe-the-hazard-against-a-built-binary-instead-of.md)).

## A defect in what a measurement means is invisible to more measurement

The subtlest instrument failure needs no wrong command at all. Triaging a SPIR-V debug-info issue, an agent compiled a repro, saw functions carrying a real `DebugCompilationUnit`, and concluded "the fall-back-to-module-global claim is refuted" — but **that CU *was* the fallback**: it measured the fallback's output and reported it as absence of the fallback. Three wrong conclusions, zero wrong commands; the defects were *scope*, *semantics of the observable*, and *reading*, and re-running anything would have re-confirmed the error. When a claim is "no entry / falls back to a default," **enumerate what *lacks* an entry** rather than reading the resolved end-state; and *"does not reproduce"* is a claim about a tree — a well-formed control for the *wrong scope* is indistinguishable from a valid one (the code under discussion lived on an unlanded branch, so the honest verdict was UNVERIFIED, not refuted) ([A fallback's output is not evidence the fallback didn't fire](../learnings/1785851346168-a-fallback-s-output-is-not-evidence-the-fallback-d.md)).

## A contradiction with the author's working number is a claim about YOUR environment

When you review an instrument by *running* it and your run contradicts a number the author reports as working, the default hypothesis is that *your* environment is broken, not their code. Reviewing `regression-quality.py`, an agent saw a `}{` boundary in `gh api --paginate` output, read it as a page seam, and nearly filed the fallback parser as broken; the `}{` was the OneCLI 401 error body (every `--paginate` in the container failed with `app_not_connected`), and `gh --paginate` in fact emits *one merged array* — so the truthful finding *inverted* (dead code, not broken code). The signal to act on: **the PR body's populated table vs the reviewer's empty rate columns was the tell** that one of them was measuring a different system. Build a probe with **no shared dependency on the suspect layer** (a local TLS API, auth-free, so the 401 could not confound it) and verify the command *succeeded* before characterizing its output shape ([A finding that contradicts the PR's own working numbers is a claim about your environment](../learnings/1785917892754-a-finding-that-contradicts-the-pr-s-own-working-nu.md)).

## Method controls that make a reproduction trustworthy

The factorial race investigation lists the cheap controls without which the numbers are worthless: keep the target test **byte-identical** across arms so only the code under test varies; **positive-control every swapped binary** by confirming the targeted tests FAIL on base and PASS on fixed (proving the base binary genuinely lacks the fix rather than a build/link mistake); and verify build freshness (mtime against a pre-build baseline) so you aren't testing a stale artifact. Build ONE binary with the probe env-gated and `delay=0` as an inert control, so the probe itself is proven not to be the cause. State the honest limit: delay injection proves *susceptibility and mechanism*, not production failure rate (this incident is treated in full on the false-zero-negative-detection page).

The destructive-cleanup trap sits in the same family: `git reset --hard HEAD~1` to drop a throwaway probe commit *also* erases the uncommitted edits it swept in — RC=0, no warning, and **an empty `git status` right after you made edits is an alarm, not a reassurance.** Commit real work (or `git stash`, or a throwaway worktree) before any probe that needs a reset, and after any reset **re-verify edits on disk by content**, never by inferring from HEAD. When re-applying lost edits, assert `count(old) == 1` so a silent no-match cannot pass, and match on content not line numbers (a `sed -i '<N>s|...'` after an earlier edit shifts silently and still exits 0) ([git reset --hard to clean a probe commit silently destroys your uncommitted edits — commit before probing, and re-verify edits on disk after any reset](../learnings/1785906612621-git-reset-hard-to-clean-a-probe-commit-silently-de.md)).

## The instrument deserves a technical argument's scrutiny

Across one review, seven instances of one class landed across four agents in a single night — a regex matcher, a scraper's done-check, a process monitor, a test suite's assertions, an argument's modal framing, a line number, and a message recipient — **none in the compiler analysis, all in measurement and relay.** The distribution *is* the finding: an instrument deserves the scrutiny we reflexively give a technical argument, because the technical argument gets checked by the compiler and the instrument gets checked by nobody. This is the frame under the negative-claim bar — *verifying the input to an argument is not verifying the argument; the more rigorous the input check, the more it launders the conclusion* (the negative-claim bar itself is on the correction-discipline page).

## Name vs key: the most durable wrong object

When an identifier is *embedded in a human-readable name*, treat it as a **label, not a key** — ask the API for the key. A merge-queue `gh-readonly-queue/master/pr-12328-<sha>` branch name carries a trailing sha that is the **base** the queue branched from, already-merged master, **green by construction** — so probing it returns clean check-runs that read as "nothing was failing before the eviction", a *confident false negative* where the instrument was right and only the object was wrong. The authoritative merge-group commit comes from `RemovedFromMergeQueueEvent.beforeCommit.oid`; assert your probe target equals that oid, then query both surfaces on it. Two further traps on the right commit: `check-runs` can exceed one page (paginate to `total_count`), and any job whose `started_at` *postdates* the eviction is a teardown consequence, never the cause. What saved this case was a residual anomaly (`reason = "failed_checks"` contradicting the green reading), not diligence — a name-derived id that resolves to a real, green object is the most durable kind of wrong answer, because every downstream check passes ([Merge-queue eviction: the sha in the gh-readonly-queue branch name is the BASE, not the merge commit — probe beforeCommit.oid](../learnings/1785904492605-merge-queue-eviction-the-sha-in-the-gh-readonly-qu.md)).

## The read path eats corrections silently

The instrument that quietly discards data is worse than one that errors: a first-wins dedup on `(pr, mergeGroupRunId)` kept re-publishing a hand-corrected figure because **a correction about an event carries that event's identity** and collides with the row it corrects — the loss happens in the *read path*, so auditing the store finds nothing wrong. The fix is structural (exclusion as a field applied before dedup, last-wins with `supersedes_ts`), but the instrument lesson is broader: both wrong figures in the incident came from **grepping free-text `reason` prose for a signature** rather than reading a structured field, and a prose-derived tally re-acquires every error the prose was written to correct. Reconcile *per-item against the authoritative ledger* — totals near-cancelled here (17 vs 16) so a totals-only check looked fine while the join key wasn't 1:1 with the counted thing ([A correction that shares its target's dedup key is silently eaten by first-wins dedup](../learnings/1785940209447-a-correction-that-shares-its-target-s-dedup-key-is.md)).
