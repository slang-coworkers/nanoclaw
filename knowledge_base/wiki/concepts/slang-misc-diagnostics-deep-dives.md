# Slang Diagnostics: Deep-Dive Incidents & Case Studies

Split from [Slang Diagnostics System: Catalog, Definitions, and Rendering](slang-misc-diagnostics-catalog-and-system.md) (over the 40 KB cap). The system-mechanics half (Lua definitions, the generated catalog + `regenerate.py`, rendering/FileCheck gotchas, warn→error escalation, API option plumbing, false-positive adjudication) stays there. This half collects the worked *incidents* — each a concrete case where a diagnostic's behavior, provenance, or severity had to be reasoned out end-to-end.

## TL;DR

- **A "new" diagnostic can report a discard that was always happening.** E36121 (#11225) didn't add a restriction — `getTargetCaps()` had silently dropped incompatible requested capabilities forever; a second walk now *reports* it. Before calling a diagnostic a new restriction, check whether the underlying discard predated it. Caveat: an inertness claim is a claim about *all* readers of an option — enumerate them (5 files read the raw `Capability` array directly, bypassing `getTargetCaps()`).
- **Prove a one-site guard fix *complete* by enumerating the diagnostic's distinct variable values** (`grep -ohE "<msg>" *.log | sort | uniq -c`). One distinct pair → sufficient; ≥2 → the one-liner is only the first fix. Pull *raw* logs, not the triage digest (digests drop the cardinality that determines scope). And **prove the negative arm reproduces first** — a version-pinned build cannot reproduce an *unreleased* upstream diagnostic, so a clean without-guard arm proves nothing.
- **A warning is not the end of a compile — run the reported snippet to codegen** before grading a permissiveness complaint docs-only. `| head` masks exit status (redirect + check `$?`); test a *release* binary too (`SLANG_ASSERT`→`SLANG_ASSUME` turns a clean debug error into a release crash); probe the matrix including the cell that removes your prime suspect; pin the breaking pass from the `-dump-ir` schedule, not `slang-emit.cpp` line order.
- **A severity DOWNGRADE resting on API semantics needs the receiver verified, not just the call site.** `queue->Signal` is GPU-timeline; `fence->Signal` is CPU — grep all call sites of the verb and confirm the receiver. Downgrades deserve *more* scrutiny than upgrades (an under-stated severity is agreed with and closes the thread). Resolve every `file:line` against the pinned commit — inline anchors drift to the diff hunk.
- **Touching a shared type/name formatter** (`getTypeNameHint`, anything reached by `printDiagnosticArg`) silently regresses unrelated exhaustive `diag=` goldens — and **draft-PR CI hides it** (build/test jobs skip on drafts). Grep callers, run the broad diagnostic dirs locally, and confirm via merge-base your change is the reaching edit before touching a pre-existing golden.
- **A diagnostic with no Decl needs a direct `diagnose()`** — `[deprecated]`/`[RemovedSince]` work by `findModifier<>` on a Decl, so a synthetic special case like `(Struct)0` can't reuse the attribute path.
- **A loc-less diagnostic whose front-end clearly stamped the loc** points at a later pass that RE-SYNTHESIZES the access (std140 block-struct wrapping) without `IRBuilderSourceLocRAII`. Fix producer-side. The IR truth can be masked on master by statement-granularity `OpLine` — re-run a subagent's `reproduced` claim against the user-visible observable before posting the label.
- **Missing-return severity is target-gated, not language-gated** (E41009 hard error on Khronos/WGPU vs E41010 warning on HLSL/Metal/CUDA/CPP). Verify a "depends on #N" claim by checking whether the symbols it adds exist on master, not just the PR state.

## E36121: A New Diagnostic Can Report a Discard That Was Always Happening

`TargetRequest::getTargetCaps()` (`source/slang/slang-target.cpp`) has walked the requested-capability array since long before #11225, ending each iteration with `if (!targetCap.isIncompatibleWith(toAdd)) targetCap.join(toAdd);` — the incompatible case simply falls through: **no join, no diagnostic, no trace**, so an incompatible requested capability never entered `cookedCapabilities`. What #11225 adds (`checkCapabilities()`, called from `checkEntryPoints`) is a *second* walk over the same `targetOptionSet.getArray(CompilerOptionName::Capability)` that now **reports** what the first walk was already discarding. **E36121 is not a new restriction — it is a newly-visible pre-existing discard.** The compatibility question is answerable statically for the cooked path: `hlsl_nvapi` is `def hlsl_nvapi : hlsl;` (strictly the hlsl target family), `isIncompatibleWith` is true when **zero** target sets intersect, and non-d3d12 device types cook to non-hlsl atoms (vulkan→`spirv`, metal→`metal`, wgpu→`wgsl`, cuda→`cuda`, cpu→`cpp`/`llvm`), so on every non-d3d12 target the capability was already being dropped at cook time. Corollary worth keeping: E36121 is keyed on the **target** with no device term (`checkCapabilities` reads only the option set and cooked caps), so a `dxil + hlsl_nvapi` pairing is verifiable with `slangc` alone — "can't test that arm" is too coarse; only device creation, runtime NVAPI linkage and Windows subcase execution need real CI ([getTargetCaps already silently drops incompatible requested capabilities — E36121 diagnoses a discard that was always happening](wiki/learnings/1785751218246-slang-gettargetcaps-already-silently-drops-incompa.md)).

⚠️ **Scoped correction — "both arms inert ⇒ pure diagnostic suppression" does NOT follow.** That earlier conclusion verified only the **cooked** capability set. Five files read `getArray(CompilerOptionName::Capability)` **directly**, bypassing `getTargetCaps()`, and one of them (`slang-type-layout.cpp:3549`, `maybePromoteDescriptorHandleCapability`) computes `specificCapabilityRequested` from the raw array — so removing an entry can flip `descriptor_handle` auto-promotion on metal/cuda/wgpu/cpu, a real present-tense behavior change. Because the promotion mutates the capability set, its observable effect is **accept/reject and diagnostics, not sizing** — so measure diagnostics on a no-profile target, not layout. Two other consequences for diagnostics work here: the E36121 emitter's input is the **requested** array (the `-capability`/API request path), so an in-source `[__requiresNVAPI]`/`[require]` never enters it and is **not a second fix site**; and an inertness claim is a claim about *all* readers of an option, so enumerate them up front rather than analysing the obvious one and generalizing. Full reader map and the layout-vs-capability split live on [[wiki/concepts/slang-misc-compiler-internals.md]] ([CORRECTION — both-arms-inert was scoped to the cooked capability set only](wiki/learnings/1785751609559-correction-both-arms-inert-was-scoped-to-the-cooke.md)).

## Prove a One-Site Guard Fix Complete by Enumerating the Diagnostic's Distinct Values

When a diagnostic fires N times and you propose a **one-site** guard, "consistency with the other guarded sites" argues the fix is *idiomatic*, never that it is *sufficient* — and only sufficiency justifies rejecting a broader audit. The closing step is a uniqueness check on the diagnostic's **variable parts**:

```bash
grep -ohE "requested capability '[^']+' is incompatible with compilation target '[^']+'" *.log | sort | uniq -c
#   56 requested capability 'hlsl_nvapi' is incompatible with compilation target 'spirv'
```

One distinct pair → the single site is sufficient. Two or more → the one-line fix is merely the first of several and the scope is wrong. On slangpy#1087/#1088 this returned exactly one pair (`hlsl_nvapi` → `spirv`), 28× per platform; had a second capability appeared, a triage memo that recommended one site and ruled the audit out of scope would have been wrong in a way its own cited evidence could not catch — so run the enumeration **before** recommending the single-site fix. Enumerate the *other* variable too (only `spirv` appeared as a target, which bounds what can be claimed as verified vs. covered-by-construction — metal/CUDA/CPU had no job in the matrix), pull the **raw** logs rather than the issue/triage digest (`gh api repos/<o>/<r>/actions/jobs/<id>/logs`; digests summarize the failure *shape* and routinely drop the *cardinality* that determines scope), and cross-check counts per job rather than only in aggregate ("28 failures" across two logs vs. 28 *per* log are different facts, and reviewers read ambiguous phrasing the weaker way). Adjacent tell: **0 failed assertions alongside N failed test cases** is doctest's signature for a thrown exception during setup (module-load failure), i.e. one root cause, before you read a single test ([enumerate a diagnostic's distinct values to prove a one-site fix is complete](wiki/learnings/1785748284485-enumerate-a-diagnostic-s-distinct-values-to-prove-.md)).

**And prove the negative arm reproduces first.** For a "add a guard so a new diagnostic stops firing" fix, the with-guard arm is the worthless half: when the downstream project pins a released tarball (`SGL_SLANG_VERSION`, `external/CMakeLists.txt:85`) and the diagnostic comes from an *unreleased* upstream change, a build against the pin **cannot** reproduce it, so a green local test proves no-regression and nothing about the bug. Close the loop with an A/B against a local build of the upstream PR (`SGL_LOCAL_SLANG=ON` + `SGL_LOCAL_SLANG_DIR` + `SGL_LOCAL_SLANG_BUILD_DIR`, the mechanism CI uses): **without** the guard must show the error verbatim, captured in the PR body as reproduction proof; **with** it must be clean. If the without-guard arm comes back clean, the honest conclusion is "locally unproven; rests on CI plus code inspection" — a *negative result*, not a pass. Also confirm the harness creates real devices, or a GPU-skipped run makes the A/B vacuous regardless of outcome; and a guard arm you cannot exercise locally (e.g. `SGL_HAS_D3D12: OFF` in-container) must be **declared** as a caveat in the PR, not implied. Sequencing for a downstream fix pinned to upstream releases is **merge → tag → bump** (check `merged`/`merged_at` via REST and list actual release tags — an unmerged PR is in no tag *because* it is unmerged), and opening a draft is not gated by what gates promoting it ([verifying a guard fix: enumerate the diagnostic's distinct pairs, and prove the negative arm reproduces first](wiki/learnings/1785746886431-verifying-a-guard-fix-enumerate-the-diagnostic-s-d.md)).

## A Warning Is Not the End of a Compile — Run the Reported Snippet to Codegen (#8785)

For any "the compiler accepts/permits X" report, run X **to codegen on the real targets** before ruling the compiler innocent. On slang#8785 the reporter quoted `warning 38040: parameter 'payload' is treated as 'uniform'` for the documented amplification-shader form `out payload TaskData payload`; a first triage verified the front-end mechanism (amplification is absent from the varying-input stage switch in `slang-check-shader.cpp:2118-2155` → force-uniform + warn), confirmed the docs advise unsupported syntax, and concluded **"the documentation is wrong, not the compiler"** — classing it docs/medium/P2. Compiling the snippet at HEAD `546ad18f7` inverted that: `-target spirv` → **ICE** `assert failure: slang-ir-glsl-legalize.cpp(5235): call->getArgCount() == 4`; `-target metal` → **ICE** `slang-ir-legalize-varying-params.cpp(4566)`; `hlsl` exits 0 but emits writes into a read-only `cbuffer` that the bundled `dxc 1.9` then rejects; `glsl` exits 0 and emits writes into a `push_constant` block — same defect, silently. On the **released** `slangc 2026.13.1`: **SIGSEGV, exit 139, core dumped.** So the real grade was bug/high/P1 `reproduced` — the compiler crashes on the very input the docs recommend. **A warning means the front end had an opinion, not that compilation completed**; reporters quote the first thing they see. This is the companion to the defect-inversion rule ("does this permissiveness defect also REJECT valid code?"): also ask **"does it CRASH on the invalid code it accepts?"** ([a front-end warning is not the end of a compile run](wiki/learnings/1785803987320-a-front-end-warning-is-not-the-end-of-a-compile-ru.md), [compile the reported snippet all the way to codegen — a quoted warning may be hiding an ICE](wiki/learnings/1785803858075-compile-the-reported-snippet-all-the-way-to-codege.md)).

Four method traps from that chain, all reusable. **(1) `| head` masks exit status** — `slangc … 2>&1 | head -12` reported `EXIT=0` on a run that had segfaulted, because the pipeline's status is `head`'s; redirect to a file and check `$?` (`slangc … > log 2>&1; echo "EXIT=$?"`). **(2) Test a release binary too:** `SLANG_ASSERT` becomes `SLANG_ASSUME` in release (`slang-common.h:364` vs `:371`), so the violated invariant is UB rather than a message — "it's only a debug assert" is backwards; debug gives a clean error, release gives a crash. **(3) Probe the matrix and include the cell that removes your prime suspect.** The conspicuous suspect was the `payload` modifier, but `out payload T`, `in payload T`, `inout payload T`, bare `payload T` **and `out T` with no modifier** all ICE, while `in T` warns/compiles but emits the payload as a silently-wrong PushConstant, and `uniform T` / a plain local / a `groupshared` global are clean — as is an `out payload` param whose `DispatchMesh` is handed a *groupshared* var, or one with no `DispatchMesh` call at all. So the true trigger is **"the value passed to `DispatchMesh` is an entry-point parameter"**, not the modifier; a fix teaching the checker about `payload` alone would leave `out T p` crashing. **(4) Pin the breaking pass from the dump, not from `slang-emit.cpp` line order.** Project the one signature you care about against the pass name and collapse consecutive duplicates so the transition is a single line:

```bash
awk '/^### AFTER/{pass=$3} /func %DispatchMesh/{print pass"\t"$0}' ir.dump \
  | sed 's/RefParam([^)]*)/REFPARAM/' | awk '{if($0!=prev)print; prev=$0}'
```

4-param through `specializeResourceUsage`, 3-param immediately after **`specializeFuncsForBufferLoadArgs`** — and run the same sweep on the WORKING input as a control (the `groupshared` form never drops arity), which rules out "this pass always does that." An Explore subagent confidently attributed the drop to `legalizeEntryPointsForGLSL` with a tidy story attached; the dump shows the drop already complete before that pass runs, because `SLANG_PASS(...)` at a lower line number is not proof of what ran when (passes sit behind target conditionals) — **adjudicate subagent attributions against the dump, not against plausibility.**

Two prose-discipline corollaries recorded on the same chain. **Scope your greps in prose:** a public claim that `grep` for `taskPayloadSharedEXT` "across this tree returns nothing" was really `--include=*.md --include=*.slang --include=*.rst`; the tree has **19** hits including `slang-emit-glsl.cpp` and `slang-ir-glsl-legalize.cpp` — the very emitter and legalize pass that *implement* the rate, i.e. proof the `groupshared` idiom is supported. The load-bearing claims (markdown = 0, `coming-from-glsl*` filename = 0) were genuinely zero, so the verdict survived, but the phrasing inverted its own best evidence. Say **"zero in markdown," never "zero tree-wide"** — and when a search returns empty, ask whether a *non*-empty result would have helped your argument before citing the emptiness. The doc bug in fact lived in a different repo (`shader-slang/shader-slang.github.io`, `docs/coming-from-glsl.md:942-954` + `:959`, found via `gh api "search/code?q=taskPayloadSharedEXT+org:shader-slang"`), so when a reporter cites a `docs.shader-slang.org` URL absent from the compiler tree, search the org before concluding the text doesn't exist, and say plainly the fix isn't a PR in this repo. **Re-read an artifact live immediately before editing it:** a `PATCH` in flight would have overwritten a superseding correction and re-asserted the wrong conclusion publicly — it failed on its own first read, luck rather than process. Bonus: the reporter's subtler claim held too — both in-tree amplification tests dispatch exactly **one** task thread (`task-simple.slang:37`, `task-groupshared.slang:34`), and at `[numthreads(32,1,1)]` with a local payload the emitted SPIR-V is a single unsynchronized `OpStore` from all 32 threads with **no `OpControlBarrier`**; when a reporter flags a test as "works only because there is exactly one thread," check the thread count — they may have found a coverage hole.

## A Severity DOWNGRADE Resting on API Semantics Needs the Receiver Verified, Not Just the Call Site

When a severity **downgrade** rests on an API's timing/ordering semantics, verify the semantics of the **exact method invoked — receiver *and* signature** — not merely that the call site exists at the cited line. On slang-rhi#797 a CodeRabbit 🟠 Major flagged a non-aborting `CHECK` followed by an unconditional call reaching `WaitForSingleObject(…, INFINITE)`; two tiers converged on nit-class (correct) but recorded the *reason* as "the `INFINITE` wait is on a **CPU-signalled** fence." At the pinned SHA `b34042ac`, `d3d12-command.cpp:2162` is `m_d3dQueue->Signal(m_trackingFence.get(), …)` — `ID3D12CommandQueue::Signal`, a **GPU-timeline** signal; the CPU shape is the other method on the other receiver (`m_trackingFence->Signal(value)`, `ID3D12Fence::Signal`) and appears nowhere in the file (all four `Signal(` sites, `:2044 :2129 :2132 :2162`, are queue-side). The conclusion survived for a *different* reason — the Signal is enqueued fresh at wait time and only needs already-submitted work to drain — which is precisely the danger: **right conclusion, wrong mechanism is the hardest class to catch, because the verdict it supports is correct so nothing ever prompts a re-check**, and here the false premise was written into the decision artifact *as the strengthening* while the true one went unrecorded. Downgrades deserve this scrutiny more than upgrades: an over-stated severity gets argued down by the next reader, an under-stated one is agreed with and closes the thread. Clean verification shape: grep **all** call sites of the verb in the file and confirm they share the receiver you assumed (4/4 queue-side ⇒ no CPU-signal path existed to have meant), then walk the path end to end. This is not an argument for blanket distrust — two adjacent claims in the same downgrade held under the same check (a pre-existing non-aborting-`CHECK`-then-`getResult` idiom with 4 call sites in `tests/test-cmd-query.cpp`; and `ci.yml` having **zero** `timeout-minutes`, so a real hang is bounded only by GitHub's default job limit) — only for checking the load-bearing one. Companion trap: **resolve every `file:line` against the pinned commit before it enters a recorded artifact.** The finding's line was cited as `:412` by both tiers via different routes (range-relative numbering from a `sed -n '395,425p'` window; CodeRabbit's inline anchor propagated verbatim), while the `CHECK` is at `:409` and `:412` is the `getResult` it warns about — a real line in the relevant block, just not the one the finding is about, so it survives review. Cite the line the finding's **claim** is about (inline anchors drift to the diff hunk, not the semantic subject) and cross-check `original_line`/`start_line` against the prose. Note the approver already held a learning covering exactly this and had applied it to bot-reported *counts* but not to *line refs* — **having the rule isn't executing it** ([a severity downgrade resting on API timeline semantics — verify the receiver, not just that the call site exists](wiki/learnings/1785780844550-a-severity-downgrade-resting-on-api-timeline-seman.md)).

## Touching a Shared Type/Name Formatter Silently Regresses Unrelated `diag=` Goldens

Changing a **shared type/name formatter** — `getTypeNameHint` in `source/slang/slang-ir-util.cpp`, or anything reached by `printDiagnosticArg` (`slang-ir.cpp:36`, the generic `IRInst`/`IRType` diagnostic-argument renderer) — can silently alter the *message text of completely unrelated diagnostics*. On PR #12005 / issue #7878, adding a `case kIROp_OptionalType` to `getTypeNameHint` so a new diagnostic (E41037) could render `Optional<T>` also changed how a pre-existing `__ref`/`__constref` dynamic-dispatch diagnostic rendered an `IROptionalType` param — from the empty string `''` to `'Optional<IFoo>'` — failing the exhaustive `//DIAGNOSTIC_TEST:SIMPLE(diag=CHECK):` golden `tests/language-feature/dynamic-dispatch/diagnose-ref-interface-in-compound.slang` (+ its `.1` hlsl variant) on both the position-match and exhaustive-check. Why it bites: (1) **draft-PR CI hides it** — build/test jobs are SKIPPED on drafts (only `check-ci`+`wait-for-human-priority` show a cosmetic failure), so the regression surfaces only when the PR flips non-draft and the real `pull_request` build runs, often after a maintainer already approved; (2) `.slang` goldens are runtime-interpreted, so a stale golden isn't caught by a C++ rebuild — you must actually run the affected test; (3) diagnostic goldens are scattered (`tests/diagnostics/`, `tests/language-feature/dynamic-dispatch/`, `tests/glsl-intrinsic/`, `tests/autodiff/`, `tests/compute/`, …), so a two-directory local sweep does NOT bound the blast radius. **What to do:** when you touch a shared render/format helper, `grep -rn getTypeNameHint source/slang/` for callers AND run the broad diagnostic dirs locally before trusting draft CI, and SAY SO in the report — don't claim a two-dir sweep covers every golden. The exhaustive-check failure output prints the exact replacement annotation ("Suggested annotations you can copy") — copy it verbatim; caret columns are almost always unchanged (only message text moved), so the fix is a pure message refresh, not a re-alignment. This is a genuine golden *refresh* (the message became more informative), not silencing — but confirm via merge-base that YOUR change is the reaching edit before touching a pre-existing test ([Shared diagnostic formatter changes silently regress unrelated exhaustive diag= goldens (masked on draft CI)](wiki/learnings/1783657592434-shared-diagnostic-formatter-changes-silently-regre.md)).

## (Struct)0 Zero-Cast Has No Decl -- Deprecation Needs a Direct diagnose() (#12045)

The legacy HLSL `(Struct)0` cast (treated as `Struct s = {}`, default-init not zero-init) is a hardcoded compiler special case in `SemanticsExprVisitor::visitTypeCastExpr` (`slang-check-expr.cpp:7389`), gated on target StructDecl + exactly one `IntegerLiteralExpr` arg == 0, firing only for C-style cast syntax (not `T(0)`). Key nuance for deprecating it: Slang's `[deprecated]`/`[RemovedSince]` machinery works by `findModifier<>` on a **`Decl`** -- but the zero-cast has NO declaration to attach an attribute to, so a deprecation CANNOT reuse the attribute path. It must be a direct version-gated `diagnose()` inserted at the special-case site (:7404), reusing the `moduleDecl->languageVersion` comparison idiom + a new diagnostic; the removal version is an ABI-relevant `SlangLanguageVersion` enum append ([slang (Struct)0 zero-cast is a synthetic special case, no Decl for [deprecated] attribute](wiki/learnings/1783690411342-slang-struct-0-zero-cast-is-a-synthetic-special-ca.md)).

## Source-Loc Dropped by std140 Re-Synthesis (Real at IR Level, Masked by Statement-Granularity OpLine) (2026-07-23 fold)

Issue #12192: under `spvBindlessTextureNV`, the E55215 diagnostic on a `ConstantBuffer<T>.Handle` prints with NO source location while the identical diagnostic on `StructuredBuffer`/`ByteAddressBuffer` reports a real `line:col`. The front-end DOES stamp the loc, but it is dropped later: the CB element is wrapped into a std140 block-struct and its field access is **re-synthesized** in `slang-ir-lower-buffer-element-type.cpp` via `setInsertBefore(user)` + `emitFieldAddress`/`emitLoad` with no `IRBuilderSourceLocRAII` — a StructuredBuffer scalar load is not re-synthesized this way and keeps its loc. When a diagnostic prints loc-less but the front-end clearly stamped it, suspect a later pass that RE-SYNTHESIZES the access (block-struct wrapping, std140 packing); fix producer-side when you own the synthesizing pass ([diagnostic no-loc on ConstantBuffer descriptor-handle: loc dropped by std140 re-synthesis, not the frontend](wiki/learnings/1784762842417-diagnostic-no-loc-on-constantbuffer-descriptor-han.md)).

The observable, though, is subtler than the IR truth: the loc drop is REAL at the IR-instruction level but **masked on master** because Slang emits `OpLine`/`DebugLine` at *statement* granularity — every statement carries some loc-bearing inst, so the statement's `OpLine` covers the loc-less CB access and `-g2`/`-g1` debug info looks correct. A build+run subagent mis-read "the CB access has no OpLine of its own" as "master-reproducible"; re-running the repro showed the statement-level OpLine lands on the right line. Always re-run a subagent's `reproduced` claim and read the actual output before posting a public `reproduced` label — the clean user-visible symptom here is the E55215 diagnostic (a direct `inst->sourceLoc` consumer), not the debug-info golden ([CB source-loc drop is IR-level real but MASKED on master by statement-granularity OpLine — verify observables yourself](wiki/learnings/1784778798903-cb-source-loc-drop-is-ir-level-real-but-masked-on-.md)).

Missing-return severity is **target-gated, not language-gated** (a portability trap): `doesTargetAllowMissingReturns` returns false for Khronos/WGPU targets → hard `E41009 MissingReturnError`, true for HLSL/DXIL/Metal/CUDA/CPP → warning `E41010` only. The check runs twice by design — lowering-time (`CodeGenTarget::None`, warning) and link/emit-time (real target, error on strict targets) — both gated by `shouldRunNonEssentialValidation()`. Issue #12264 (skiminki-nv) proposes making it an unconditional `E41009` on all targets for language version 202c by gating on `module->languageVersion` (in scope at the lowering-time call). It is PARKED: #12179 (which adds `SLANG_LANGUAGE_VERSION_202C`) is an unmerged prerequisite — verify a "depends on #N" claim by checking whether the symbols it adds exist on master, not just the PR state ([missing-return severity is target-gated; 202c proposal moves it to language-version gating](wiki/learnings/1785336991633-missing-return-severity-is-target-gated-202c-propo.md)).
