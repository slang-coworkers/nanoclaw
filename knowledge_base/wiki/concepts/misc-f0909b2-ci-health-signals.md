## TL;DR

- **An idle metric is not a fault until a weekday control says so.** A "frozen 56.8h" CI reading was a Saturday+Sunday gap; get the per-day merged-PR rate across surrounding days before escalating any "frozen / stalled / zero for N hours" metric. A skeptical check is *directional* — run it on the alarming reading, not just the optimistic one.
- **Before naming X as the cause of a blockage, verify X is on the blocked path** — for GitHub Actions that's two fields, `event` and `head_branch` (a dev-branch `workflow_dispatch` cannot gate a merge queue). And "green" ≠ "passing": a job can go green by *subtracting* a test — diff the workflow before crediting a recovery.
- **A zero-capacity alarm needs the CONJUNCTION with demand, not the zero.** `total==0` is designed autoscaler behavior (1119 harmless frames); the pathological predicate is `total==0 AND queued>0`, ranked on duration × demand. Separate present-and-zero from absent (an absent group key is *no information*, not zero).
- **Flake-vs-real is settled by breadth and reproducibility, not a partial read.** Enumerate *every* failing leg before classifying — a deterministic failure across ≥3 independent backend families is self-attributing (a one-runner flake can't reproduce identically on unrelated hardware).
- **Requeue is the rarest, most-thrashing action — gate it on three independent surfaces** (intermittent signature + head-moved-and-now-green + `mergeQueueEntry` state), each alone misleading.
- **The instrument returns a believable answer precisely where it is blind:** GraphQL `author.login` omits `[bot]` for `github-actions`/`coderabbitai`; `actions/runs?head_sha=` returns `total_count=0` for an abbreviated sha; `--is-ancestor` proves a commit merged, never that its content survived. Cross-check with a disagreeing instrument.
- **Length is a cost you impose, not thoroughness you display** — and long prose is where unchecked figures survive.

## An idle metric is not a fault; verify the cause is on the blocked path

The keystone escalation lesson: a maintainer-facing #1 action item was wrong two days running because an idle clock was read as an incident [[an idle metric is not a fault until a weekday control says so]](../learnings/1786437042173-an-idle-metric-is-not-a-fault-until-a-weekday-cont.md). shader-slang's CI was reported "frozen 56.8h" (master sha unchanged, `merge_group` runs = 0) and blamed on a wedged `falcor-ci` gate — but the gap was Saturday+Sunday (Fri 11, Sat 1, Sun 0, Mon 5 merged PRs, trivially checkable per day), and the blamed gate was an `event=workflow_dispatch` run on a *dev branch* (`head_branch=fix/issue-11981`) that cannot gate a merge queue (proof: still `waiting` at 67h while 5 PRs merged past it). Two transferable rules: get the per-day rate across surrounding days before escalating any "frozen/stalled/zero-for-N-hours" metric (a zero on Sat+Sun is a calendar, not a fault) — and note that a skeptical check is *directional*: the author had a "don't report a green snapshot as health" guard and only ever pointed it at optimistic readings, never at the alarming one. Before naming X the cause of a blockage, verify X is on the blocked path (`event` + `head_branch`), and sweep the whole report for other claims a discriminator invalidates — "a check earned in one place is a check everywhere." Escalation cost is asymmetric: fabricating a freeze spends a maintainer's attention on a no-op *and* trains them to discount the next alarm, so when the remedy is "go click this" the bar for the causal link goes up. (Related trap in the same pass: a macOS job went green only because a merged PR subtracted the Metal API — diff the workflow before crediting a recovery; "green" and "passing" are not the same claim.)

## A capacity alarm is a conjunction, ranked on duration × demand

Investigating a self-hosted runner pool reading `busy:0, total:0`, "the pool has zero runners" is not a finding — 1119 of 5686 frames show `total==0` going back 5+ months, because the autoscaler *drops the pool to zero when nothing is queued* [[a zero-capacity alarm needs the CONJUNCTION with demand, not the zero]](../learnings/1786438759188-a-zero-capacity-alarm-needs-the-conjunction-with-d.md). A bare `total==0` is `starved-vs-no-demand` and carries no information; the pathological predicate is `total==0 AND queued>0` (209 frames), which itself needs *duration* (scale-up lag is usually a single frame), so the real event ranks on **duration × demand** — the 26h episode at peak queue 4 was harmless, the 15.2h at peak queue 44 was the actual outage. "Ask what a victim looks like: zero capacity only harms you if something is waiting." Two adjacent traps both failing toward "quiet": an *absent* group key is not `total: 0` (`runner_groups` enumerates only groups with current demand, so absent ⇒ no information — separate present-and-zero / present-and-sentinel / absent before any absence-based claim, or you overstate onset), and a depth threshold detects a capacity failure late and incidentally (`total==0 AND queued>0` sustained ≥2 frames fires ~14h earlier than a `jobs_queued>30` alarm). Instrument aside that reads as "no outage": `bc` is not installed in the agent container, and `printf "%.1fh" "$(… | bc)"` renders empty as `0.0h` — use `awk` for arithmetic.

## Flake-vs-real: breadth and reproducibility, read in full

Three atoms build the flake-vs-real discriminant. The foundation: enumerate *every* failing leg before classifying a multi-platform `test-slang` red — breadth across independent backends *is* the discriminating evidence, because a deterministic `CHECK-NOT`/FileCheck miss reproducing identically across ≥3 backend families rules out "flake" (a one-runner flake can't reproduce on unrelated hardware) [[read the full failing-leg set before classifying a test-slang red]](../learnings/1786507887853-read-the-full-failing-leg-set-before-classifying-a.md). The direction that misleads is the inverse — read only one leg and you might reach for "flake," and it's exactly the breadth you skipped that would have ruled it out (on PR #12489 a 3-leg citation undercounted a spread that was also Windows debug+release ×VK/DX/CUDA — the verdict was right but "luck-preserving, not method"). A genuine one-runner flake alongside a deterministic multi-platform failure is *moot* — the PR is red on the deterministic signature regardless. The external-pipeline refinement: a Falcor failure has evidence-strength tiers — in-job retry reproduces (strongest), consistent multi-backend spread (strong), and full-length + branch-isolated single external-pipeline failure (**weakest**, "needs author eyes," not "confirmed regression") [[Falcor full-length+branch-isolated failure is "needs author eyes", not "confirmed regression"]](../learnings/1786501058011-falcor-full-length-branch-isolated-failure-is-need.md). A disambiguating ~47min rerun buys an *asymmetric* probe (a repeat fail strengthens "real"; a single clear doesn't prove "transient" because a flaky real bug also clears), so it's not worth the infra cost when the author owns it regardless — and a duration-keyed retry wrapper would auto-absorb early-death transients while preserving full-length failures as author signal.

The rarest action gets the strictest gate: requeuing a merge-queue-evicted PR needs **three independent surfaces that must ALL hold** [[evicted-PR requeue decision needs three independent surfaces, each alone misleading]](../learnings/1786494014693-evicted-pr-requeue-decision-needs-three-independen.md) — (1) a clearly-intermittent failure signature (not a bare external `failed`, not a consistent multi-platform failure); (2) the head has moved since eviction AND CI now passes on the new head (a moved head could still be broken; confirm the previously-failing job passes on it); (3) `mergeQueueEntry` (GraphQL only) confirms current queue state (`null` = nothing to requeue). On PR #12459 all three said "do not requeue — the author re-enqueues"; a requeue would have acted on a superseded head. No single surface is load-bearing, so no single misread flips the decision.

## Instruments that return a believable answer precisely where they're blind

Three "false-negative instrument" atoms, all the same class — the instrument's answer is believable exactly in the state where it's wrong. GraphQL `author.login` **omits the `[bot]` suffix** for `github-actions` and `coderabbitai` (while `nv-slang-bot[bot]` carries it), so a "did a human comment last?" predicate built on a bot-login allowlist silently classifies those two as humans — 152 comment rows mislabeled across 31 chains, producing believable false "we haven't answered" nudges [[GraphQL author.login omits [bot] suffix — breaks "human spoke last" detection]](../learnings/1786453325216-graphql-author-login-omits-bot-suffix-for-github-a.md). Prefer `author.__typename == "Bot"`, or a suffix-agnostic set including `github-actions`/`coderabbitai`/`dependabot`; and enumerate the actual comments (author + timestamp) before composing a nudge. Similarly, `GET actions/runs?head_sha=` requires the full 40-char sha and **silently returns `total_count=0` for a 12-char abbreviation** — which is exactly the evidence for "CI never ran" / "no review bot working," pushing the decision toward a named, plausible, conservative-looking wrong answer; `commits/<40>/check-runs` returning 23 on the same ref is the cheap detector [[actions/runs?head_sha= silently returns total_count=0 for an ABBREVIATED sha — and my write-up taught the broken form]](../learnings/1786453444486-approver-infra-abstain-actions-runs-head-sha-silen.md). That atom carries a second, sharper lesson: the author *ran the correct 40-char form* but *wrote up the abbreviated one* pairing a broken command with a correct result — **a write-up that abbreviates a command has changed the command**; paste commands verbatim or re-run the abbreviated form (and reconstruct how a credited catch was actually found before accepting it — "I found X" and "X exists" are different claims). Third, `git merge-base --is-ancestor` (and "my SHA is in the merge") proves a commit *merged*, never that its content *survived* — on slang#12189 a later same-branch commit reverted the content per review, so the feature never landed while the issue sat OPEN with a false "Documented" bot comment for ~19 days; verify content at the merge base (`git show origin/master:path | grep -c '<marker>'`), and re-check that `Closes #N` is still in the merged body [[a merged commit's content can be reverted by a later same-branch commit — --is-ancestor won't catch it]](../learnings/1786464133493-a-merged-commit-s-content-can-be-reverted-by-a-lat.md).

## Length is a cost, not thoroughness — and where wrong figures hide

Maintainer `swoods-nv` on slang#12337: "The bot is extremely verbose here. Can anyone tell me why I was assigned?" — measured, the bot out-wrote the humans ~20:1 (~14.7KB of prose vs 665+73 chars) [[maintainer feedback: our GitHub comments are too verbose]](../learnings/1786460449898-maintainer-feedback-our-github-comments-are-too-ve.md). Length is a cost imposed on every maintainer who lands on the issue, not thoroughness displayed; a 5-bullet shape and "verify every claim" license *correct* prose (usually shorter), with the verification work on disk and only the receipts a reviewer needs in the comment. Lead with the answer in one or two sentences; cut the enumeration of searches run and the meta-commentary about method. The trap when responding to this feedback is replying at length — acknowledge in one sentence and fix the behavior. And the connection is not incidental: **long prose is where unchecked figures survive** — the same issue's 4,395-char comment carried two wrong pass-counts (counted commented-out `RegisterPass` lines; `grep -cE '^\s+optimizer\.RegisterPass'` vs the `//`-anchored form is the discriminator), sitting past the point any reader would still be auditing. Brevity is a *correctness* mechanism: fewer claims means every claim gets checked. (Also: answer "why was I assigned" from the timeline actor, not the bot's own artifact — a maintainer asking that may be about to conclude the bot did it.)
