# Ownership and Mention Identity

## TL;DR

- Before naming a person as the author/owner of a PR, commit, or change in a public GitHub comment, verify the identity against the live source (`gh api .../pulls/<n> --jq .user.login`, commit `.author.login`), never from memory or inference. A wrong `@`-mention is a maintainer-visible credibility error.
- The PR-number/commit citation can be correct while the *person* is wrong — verify the author independently of the number.
- Labels/assignees (`Office-<name>`) are a cross-check on who a maintainer *thinks* owns a change, not proof of authorship — confirm against the actual author.
- Confirm PR authorship via `pulls/<n>/commits`, NEVER `commits?sha=<branch>`. Branch-scoped endpoints return the branch's full ancestry, so a maintainer master-merge drags in the bot's commits from *other* PRs and produces a false "the bot worked this PR" positive.
- Never repeat a maintainer authorization as a verbatim quote unless their words are in a real inbound. Verify provenance (does the quoted comment id actually exist / resolve?) before propagating it into public artifacts.
- Attribute a go-ahead that came from a relayer's judgment as "per the handoff / held pending maintainer review" — never "the maintainer asked for X."
- "Verify it's clean" means re-read the CURRENT bytes on GitHub (`gh api .../comments/<id> --jq .body`, `gh pr view --json body`), not your memory of what you wrote.
- Fix errors on the right surface: your own comment → `PATCH`/edit-in-place; a PR body you don't own → route to the fixer. Correct the flagger factually and fix any internal notes carrying the same error.
- Stand down when a maintainer or external contributor is already driving a fix — a competing bot PR is likely to be closed even when correct. Bias to advisory triage.
- Stand-down detection signals: `assignees` set to a maintainer, an active external contributor or "I'll take this" comment, or a linked PR already open.
- Check for a community/duplicate PR at every gate, not only at triage: before routing and on each fixer status message (triager), before dispatch (orchestrator), at setup, when the build is kicked off, and again before `gh pr create` (fixer), and at review start (reviewer). External reporters often open a non-draft `Fixes #N` PR seconds to hours after filing, including after our triage comment. Query the issue timeline for `cross-referenced` PRs, not just `in:body` search, and re-check sibling issues in a batch.
- A core-team, self-assigned, or known self-fixing reporter is a strong signal they will fix it themselves (a fork-PR cross-reference minutes after filing is the tell). If their PR appears, stand the fixer down, edit our own issue comment in place, and post measured input (master-compiles/PR-errors shapes with parity twins, a local GPU run of their head) on the ISSUE, never on the human's PR. Re-derive PR linkage from `gh pr list --author` + `Fixes #N`, never from a memo's PR number; `action_required` CI on an outside PR means a maintainer must approve the run.
- If a community PR exists, validate it locally against the triage acceptance criteria and report the gaps up; never open a competing bot PR. A reviewer who finds one surfaces it as the top concern — choosing between two PRs is the shepherd's decision.
- Before calling a design change "unapproved", list the PR's commit authors and assignees: the maintainer may have pushed it herself, and then the bot chain stands down unless asked.
- On an issue handoff, check issue comments and author intent BEFORE coding. If an external contributor was invited/is writing the fix, stop at a read-only plan; re-engage only if they abandon it AND a maintainer explicitly asks the bot to take over.
- If drafting anyway, keep the draft thin and parked, and close it the moment the issue closes — never let a parked draft rot against a closed issue.
- A supervisor "dropped-promise, re-wake and open the PR" nudge can resolve to STAND-DOWN, not re-wake: re-verify the issue's *current* assignee first. A self-assignment by a collaborator between triage and the nudge flips the correct action.
- A parked issue changes owner or direction silently. On every re-check read the issue timeline (`assigned`, `labeled`, `milestoned`, Issue Type, `cross-referenced`, `closed`) and open every new issue or PR that links to it, not just the comments. An assignee, self-assigned or assigned by a maintainer, owns the issue: hand off to the fixer only if they ask for or agree to a bot PR, otherwise close the chain upstream. If a linked issue moved the direction, do not hand off. Post no new comment; edit the bot's own last comment in place so it names the owner or new plan and no longer invites a PR on the old one. A human-set Issue Type is a lean toward an option, not a pick. Diff live state (head SHA, labels, draft, comments since) against the re-check prompt before following its branches; the prompt can be days out of date.
- Answer a maintainer's perf CHANGES_REQUESTED on a reporter PR with a measurement: the PR's own benchmark, main vs PR, on our GPU (twice per device, compare medians). Post the table on the issue and name the blocking reviewer; a CHANGES_REQUESTED on an old head still blocks after new pushes.
- "Unassigned" is a live fact, not a triage-time one: check `gh issue view N --json assignees` at every GO and every re-chase (a bot can auto-assign a maintainer seconds after a bot PR opens). If an assignee exists, ask them the go/no-go or CI question in a triager delta comment on the issue; keep the operator for what the maintainer cannot do.
- Answer a parent's "open the PR" premise with the better-grounded outcome, not blind obedience — preserve the diff as a ready-to-apply advisory and sharpen the public triage comment to maintainer-facing.
- An isolated `gh api .../comments` re-query is authoritative; a batched `gh issue view --json comments,labels,...` can return stale `comments:[]`/`labels:[]` — don't conclude "my triage artifact vanished" from the batched read.

## Verifying author and mention identity before posting

Before naming a person as the author or owner of a PR, commit, or change in a GitHub comment, verify it against the actual source — not memory or inference. An `@`-mention of the wrong author is a public, maintainer-visible error that costs credibility (incident #11877: the verdict said "@skiminki-nv (author of #11493)" but csyonghe authored it, and jkwak-work publicly called it out). The PR-number and commit citations can be right while the *person* is wrong, so verify the person independently: `gh api repos/<o>/<r>/pulls/<n> --jq '{author: .user.login}'` and/or the commit's `.author.login`. Existing labels and assignees (`Office-<name>`) are a cross-check on who a maintainer *thinks* owns a change, but confirm against the actual author. ⚠️ If caught with a wrong mention, correct it in-place on the bot's own comment, reply factually to the flagger, and fix any internal notes that carried the same error ([verify @-mention identity against PR/commit author before posting](../learnings/1783355490728-verify-mention-identity-against-pr-commit-author-b.md)).

A relayed authorization can carry a *fabricated* maintainer attribution straight into public GitHub artifacts, so audit the bytes and attribute policy to the actual authorizer. On slang#12176 the orchestrator relayed a draft-PR authorization framed as a verbatim maintainer quote ("jkwak-work commented: 'create the README as a draft PR'") with a comment id that 404'd — the quote was manufactured, and the false attribution propagated into a public issue comment *and* the PR body ("per the maintainer's go"). ⛔ The trap: because the "maintainer's go" was believed when the downstream artifacts were written, the first "verify nothing fabricated reached GitHub" report wrongly said "clean" — only re-reading the live bytes (`gh api …/comments/<id> --jq .body`, `gh pr view --json body`) exposed it. The rules that follow: verify authorization provenance (does the quoted comment actually exist?) before repeating it publicly; attribute a go-ahead that came from the relayer's judgment as "per the handoff / held pending maintainer review," never "the maintainer asked for X" unless their words are in a real inbound; ✅ "verify it's clean" means read the CURRENT bytes, not your memory of what you wrote; and fix on the right surface — your own comment gets a `PATCH`, the PR body routes to the fixer ([a relayed authorization can carry a fabricated maintainer attribution into public GitHub artifacts — audit the bytes](../learnings/1784656869644-a-relayed-authorization-can-carry-a-fabricated-mai.md)).

## Confirming PR authorship from the right endpoint

Confirm PR authorship via `pulls/<n>/commits`, never `commits?sha=<branch>`. The branch-scoped endpoints return the branch's full *ancestry* — once a maintainer merges master into a long-lived PR branch, that ancestry includes the bot's commits from *other* merged PRs, producing a false positive: "the bot pushed N commits to this PR" when it never touched the branch. On slang#10788, `commits?sha=copilot/fix-empty-structs-handling` showed "9 nv-slang-bot commits" (relayed to the operator as "bot engaged"), but `pulls/10788/commits` showed 5 commits, 0 from the bot — the 9 were master's unrelated bot commits dragged in by a maintainer master-merge. ⚠️ Because authorship drives stand-down-vs-re-drive decisions, getting it wrong inverts the correct action (re-driving a "stalled" chain maintainers actually own = clobber risk). Always confirm the *author* of the specific commits via the PR-scoped endpoint before asserting "the bot worked / didn't work this PR" ([verify PR authorship via pulls/<n>/commits, never commits?sha=branch](../learnings/1783639312952-verify-pr-authorship-via-pulls-n-commits-never-com.md)).

## Standing down when someone else owns the fix

When an issue already has a maintainer or external contributor active on it, a competing bot PR is likely to be closed even when correct — this is a consolidated rule drawn across seven postmortems. Bias toward advisory triage; if drafting, keep it thin and parked, and close it the moment the issue closes. Detection signals: `assignees` set to a maintainer, an active external contributor or "I'll take this" comment, or a linked PR already open. ⛔ Do not let a parked draft rot against a closed issue ([CONSOLIDATED — stand down when a maintainer/contributor is already driving the fix](../learnings/1782648000000-CONSOLIDATED-stand-down-when-maintainer-or-contributor-drives-fix.md)).

The specific case of an invited external contributor: on an issue handoff, check issue comments and author intent *before* coding. If an external contributor said they are writing a PR, or a maintainer publicly invited them to build the fix, do not auto-implement a competing draft PR. Stand down at a read-only plan. Re-engage only if the contributor abandons the PR AND a maintainer explicitly asks the bot to take over ([don't auto-implement issues owned by an invited external contributor](../learnings/1780473504394-don-t-auto-implement-issues-owned-by-an-invited-ex.md)).

A supervisor or parent nudge — "the fixer dropped a promise, no PR exists, re-wake it and open the draft" — can resolve to STAND-DOWN, not re-wake, so re-verify the issue's *current* assignee first. Concrete case: slang#11970 (Metal bindless MSL). The nudge was factually right (no PR, no `fix/issue-11970` branch, the fixer's cited commit `52fee2521b` never pushed to origin, bug still live at HEAD) — but between triage (07-07) and the nudge (07-14) the issue was self-assigned (07-08) by `jhelferty-nv`, a core collaborator who authored the very framework the recommended fix extends (#11331). That triggers the CONSOLIDATED stand-down rule: an assigned maintainer means a competing bot PR gets closed even when correct; the durable value is the analysis plus tests offered as an advisory. ✅ Right move: tell the fixer NOT to open a PR (preserve its diff as a ready-to-apply advisory), sharpen the public triage comment to a maintainer-facing advisory (Next-action = maintainer-owned; strip stale "handed to fixer / fix incoming" framing), and report the corrected picture up — the parent's "open the PR" premise is answered with a better-grounded outcome, not obeyed blindly. ⚠️ Also: an isolated `gh api .../comments` re-query is authoritative, whereas a batched multi-field `gh issue view --json comments,labels,...` can return stale `comments:[]`/`labels:[]` — don't conclude "my triage artifact vanished" from the batched read ([a supervisor dropped-promise nudge can resolve to STAND-DOWN, not re-wake — re-verify assignee first](../learnings/1784033086075-a-supervisor-dropped-promise-nudge-can-resolve-to-.md)).

The same live check governs an Orchestrator GO whose justification is "the issue is unassigned, so a bot draft PR pre-empts no owner", and the assignee changes who should be asked, not only whether to proceed. On shader-slang/slang#13554 (2026-10-10), github-actions[bot] auto-assigned jkwak-work 18 s after bot PR #13563 opened (04:32:50Z). For four days the Orchestrator kept telling the operator the issue was "unassigned" and twice asked them to decide on GPU CI. When jkwak-work then commented on the issue, a single question in a triager delta comment ("un-draft for GPU CI?") got the PR approved, un-drafted, GPU-verified and merged in about 25 h; the operator question had never been needed. Run the assignee check at decision time and before each status report; if an assignee exists, route the go/no-go or CI question to them on GitHub, and keep the operator only for things the maintainer cannot do, such as a ci-approver gate nobody is releasing ([verify assignee live before an orchestrator GO that rests on "unassigned"](../learnings/1792030832310-verify-assignee-live-before-an-orchestrator-go-tha.md)).

An issue parked for maintainer direction changes owner or direction the same way, usually without a comment, so every re-check reads the issue timeline as well as the comments. `gh issue view --comments` misses most of what moves a parked chain: a maintainer self-assigns, assigns someone else, labels, milestones or sets the native Issue Type (the GraphQL `IssueTypeAddedEvent`); the reporter opens a `Fixes #N` PR; or the owner opens a new issue that links back and closes siblings. Read `gh api repos/<o>/<r>/issues/<n>/timeline` for `assigned`, `labeled`, `milestoned`, `cross-referenced` and `closed` events, and open every new issue or PR that links to the parked one. Four outcomes recur. (1) A reporter PR makes a handoff a duplicate. On shader-slang/slang#13641 there was no new comment, but the external reporter had opened non-draft PR #13707 (`Fixes #13641`) and a maintainer had self-assigned and milestoned the issue; under the triage step-9 rule nothing is posted, because a ready-for-review `Fixes #N` PR already shows the trail ([Parked-issue re-checks: read the timeline, not just the comments](../learnings/1792681388552-parked-issue-re-checks-read-the-timeline-not-just-.md)). (2) An assignment is human ownership, whether the maintainer self-assigns or assigns another human. The parent's rule since 2026-10-22 (#13638) is that "direction arrived → hand off to slang-fixer" no longer applies by default: hand off only if the owner asks for or agrees to a bot PR, and otherwise close the chain to the parent, because a bot PR would duplicate or collide with the owner's own work ([Parked issue self-assigned by a maintainer: fixer handoff becomes conditional](../learnings/1792674358775-parked-issue-self-assigned-by-a-maintainer-fixer-h.md)). On #13878 nobody answered the bot's (a)/(b) question, but jkwak-work assigned kaizhangNV, labeled the issue and set a milestone; a comments-only check would have reported the chain "still parked/silent" ([Parked-issue re-check: a maintainer assigning a human counts as human ownership](../learnings/1793030545714-parked-issue-re-check-a-maintainer-assigning-a-hum.md)). (3) A linked issue can move the direction. On #13750 (2026-10-26) the assignee opened overhaul issue #13956, which picked option C instead of the tentatively chosen C++ rule A, and the same day closed a sibling issue and its bot PR as will-not-fix. A comments-only check would have reported "nothing changed", and a later handoff would have carried an out-of-date brief; when the direction has moved, do not hand off ([Parked-issue re-checks: read the timeline cross-references, not just the comments](../learnings/1793041485668-parked-issue-re-checks-read-the-timeline-cross-ref.md)). (4) A human-set Issue Type (Type=Documentation on a design-question issue) is a lean toward an option, not an explicit pick (#13637, #13638) ([Parked-issue re-check: read the timeline, not just comments](../learnings/1792681430638-parked-issue-re-check-read-the-timeline-not-just-c.md)). In every outcome the bot posts no new comment. If its own last comment still promises a fixer or invites a PR on the old plan, edit it in place (an edit sends no notification) so it names the assignee or the new direction and offers the bot fix on request (#13878, #13750). The newest bot comment may be the fixer's, not the triager's, since both post as nv-slang-bot; when it already carries the live state, do not PATCH it and do not post a duplicate 5-bullet. The re-check prompt is itself stale input: a one-shot prompt states the chain as of when it was written, so diff the live head SHA, labels, draft state and comments since its date before taking any of its branches. On #13876 the maintainer had reversed the decision four days after the prompt, and the fixer had reworked the PR through the webhook without a `[Fix Report]`; the right move was one `[Report]` delta correcting the parent's `[Triage Resolution]`, with the new decision recorded verbatim in the chain-state page ([one-shot re-check prompts can be overtaken by events](../learnings/1793102591047-one-shot-re-check-prompts-can-be-overtaken-by-even.md); the general staleness rule is in [Scope, staleness, and missing side-effects](verification-e-scope-staleness-and-side-effects.md)). The close-out goes to the parent as `[Resolution]` when the re-check answers a live parent inbound; a one-shot `--process-after` re-check has no inbound, so it reports with the ungated `[Report]` instead ([Message Routing & Gating](agent-routing-message-routing-and-gating.md)). A reporter's side-finding issue filed together with their own PR (#13847/#13848) is not ours to triage either; a sibling session may be holding it on purpose.

## Checking for a community or duplicate PR before building, reviewing, or opening

Four chains on 2026-10-15 lost work because nobody looked for a human PR at the moment it mattered. On slang#13635 the reporter opened #13645 23 minutes *before* the triage handoff, the triager's comment still promised "a fixer opens a draft PR", and the fixer did a ~6-minute build plus a repro before noticing. On slang#13639 the reporter opened non-draft #13646 about 25 minutes *after* the triage comment, when the fixer already had a worktree and a plan; only codex PLAN_REVIEW spotted the link. On slang#13636 the reporter's non-draft #13644 (same deletion, CLA signed) preceded bot PR #13650 by 12 minutes, the fixer never searched, and the peer reviewer found it by accident from a CI run on an unfamiliar branch and made it the top concern ([search for a community PR on the issue before opening a bot fix PR](../learnings/1792079739619-search-for-a-community-pr-on-the-issue-before-open.md)). In the albertrodriguezclo batch (#13631–#13662) the same reporter sometimes opened `Fixes #N` 16 seconds after the issue (#13662 → #13663) and sometimes hours later, after our triage comment (#13642 → #13651) ([re-check for a community PR right before building](../learnings/1792074164816-re-check-for-a-community-pr-right-before-building-.md), [check the issue timeline for cross-referenced PRs before building](../learnings/1792076007832-check-issue-timeline-for-cross-referenced-prs-befo.md), [batch reporter files issue + PR together; search alternate wording](../learnings/1792084496275-batch-external-reporter-files-issue-pr-together-al.md)). The reviewer-side account of #13650 is folded on the review-process pages.

The check therefore runs at every gate, because a PR can appear between any two of them:

- **Triager, before routing and again on each fixer status message:** the timeline query below, then re-check the timelines of *sibling* issues in a batch, since a PR can land after you already parked a sibling. Keyword dedup against older issues also needs two or three phrasings: the issue's own wording ("loadModuleFromIRBlob") missed an older duplicate phrased differently ("IR binary modules", #8744).
- **Fixer, at setup, before the first source edit, as soon as the build is kicked off, and again before `gh pr create`:** `gh api repos/<o>/<r>/issues/<n>/timeline --jq '.[]|select(.event=="cross-referenced")|.source.issue.number'` plus `gh pr list -R <o>/<r> --search "<n> in:body" --state open`. A search alone is not the link graph; the timeline sees PRs that link from a comment or commit.
- **Reviewer, at review start:** `gh pr list -R <repo> --state all --search "<n> OR <key symbol>"`, and `closingIssuesReferences` on the open PRs.

When a community PR exists, validate it rather than compete with it: apply it on a throwaway branch (`gh pr diff N > x.diff && git apply x.diff`, delete the branch afterwards), run the triage acceptance matrix, and report the gaps up to the parent. If both PRs already exist, post a coordination note on both. Use `gh pr view N --json …` and `gh pr diff N` for these reads, since even a read-only `gh api repos/.../pulls/N` trips the critique gate's PR-creation arm.

The reporter's own profile tells you how often to look. Consider slang#13793 (2026-10-20): kaizhangNV, a core-team MEMBER, filed it and self-assigned it, and the issue timeline showed a cross-reference to their fork PR (kaizhangNV/slang#24) one minute after filing. It was triaged and handed to slang-fixer within 31 minutes anyway; about 4.5–5 hours later the reporter opened #13798 (`Fixes #13793`, ready for review), and the fixer's competing design was thrown away. The bot's early comment also broke the R6 issue-wait rule (wait 4 days on a new human issue), whose gate nanoclaw#1993 was still a draft, so until it merges this timeline check is the only guard. When the reporter is core team, self-assigned, or known to self-fix, run `gh api repos/<o>/<r>/issues/<N>/timeline --jq '.[]|select(.event=="cross-referenced")'` before dispatch, at handoff, on every fixer status message, and before the fixer opens a PR. A fixer working such an issue re-checks as soon as its build is kicked off, not only before push: on slang#13766 albertrodriguezclo opened #13775 sixteen minutes after triage while the worktree build ran, and a check planned for "before push" came too late to save the build and test cost. (A recall subagent that sees your own fresh `active-work/<target>` sentinel and running build reports it as a "peer collision"; compare the sentinel's `started-at` with your own claim before acting.) The recovery that worked on #13793: the triager stood the fixer down, opened no competing PR, edited its own issue comment in place to hand review to the human PR, and posted the fixer's measured regression shapes (inputs that compile on master but error on the PR, each paired with a parity twin) on the issue, with nothing on the human's PR. On slangpy#1231 the same rule turned a scheduled "no reporter PR after 72 h → hand to fixer" plan into a review: the reporter had opened #1234 ten minutes after our invite, but our index line recorded #1233 (another issue's PR), so re-derive linkage from `gh pr list --author <reporter>` plus a `Fixes #N` grep of the body, never from a memo. The outside-contributor PR's `ci`/`checks` runs sat at `action_required`, meaning a maintainer must approve the workflow run; that is the real blocker, so the Next-action names the shepherd and requested reviewers. Building the PR head locally (`--target slangpy_ext`, then the new test, the repro and a vulkan/cuda/cpu device sweep) turned "a PR exists" into evidence, posted as non-blocking notes on the issue rather than the contributor's PR ([triage: re-check the timeline before and during a fixer handoff](../learnings/1792555065568-triage-re-check-the-issue-timeline-for-a-reporter-.md), [check the timeline for a reporter or assignee PR before dispatching](../learnings/1792555081581-check-the-issue-timeline-for-a-reporter-or-assigne.md), [recheck for a reporter's PR right after the build starts](../learnings/1792503223381-recheck-for-a-reporter-s-own-pr-right-after-the-bu.md), [verify a reporter's PR on GPU before a scheduled fixer handoff](../learnings/1792422129310-before-a-scheduled-fixer-handoff-on-a-reporter-pat.md)).

The same evidence-on-the-issue approach later unblocked that PR. ccummingsNV left CHANGES_REQUESTED on slangpy#1234 because it "doubles name lookups per dispatch"; the reporter reworked it and posted Windows numbers. What moved the chain was our own GPU measurement with the PR's own benchmark: put the PR's new benchmark file in the main worktree as an untracked file, build `slangpy_ext` and run it twice per device, merge the PR locally, rebuild and rerun, then restore with `checkout --detach <base>` and rebuild. The built-in benchmark table prints ms to three decimals, too coarse for µs dispatches, so a small pytest plugin kept outside the worktree logged the per-iteration means; single outlier iterations moved a 10-sample mean by about 25%, so compare medians as well. Post the main→PR table on the issue, not on the contributor's PR, and name the blocking reviewer for a re-review: a CHANGES_REQUESTED review on an old head still blocks, because GitHub does not clear it when new commits are pushed ([answer a maintainer's perf CHANGES_REQUESTED on a reporter PR by running the PR's own benchmark against main](../learnings/1792681690533-answer-a-maintainer-s-perf-changes-requested-on-a-.md)).

The same "who is actually driving this" check applies before calling a direction change unapproved. On #13406 a reviewer flagged commit `4752340d4c` ("Defer the __ref_writeonly read check") as walking back jhelferty-nv's "every read is an error" request with no approving comment, but jhelferty-nv had self-assigned the PR and authored that commit and the 13 others after 10-13. List authors with `gh api repos/<o>/<r>/pulls/<n>/commits --jq '.[] | "\(.sha[0:10]) \(.author.login)"'` and check assignees first; once a maintainer takes over the branch, the fixer and reviewer stand down unless she asks ([check commit authors before flagging "no maintainer approval"](../learnings/1792056812976-before-flagging-no-maintainer-approval-for-a-desig.md)).
