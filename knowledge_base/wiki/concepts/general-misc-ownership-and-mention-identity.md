# Ownership and Mention Identity

## TL;DR

- Before naming a person as the author/owner of a PR, commit, or change in a public GitHub comment, verify the identity against the live source (`gh api .../pulls/<n> --jq .user.login`, commit `.author.login`), never from memory or inference. A wrong `@`-mention is a maintainer-visible credibility error.
- The PR-number/commit citation can be correct while the *person* is wrong — verify the author independently of the number.
- Labels/assignees (`Office-<name>`) are a cross-check on who a maintainer *thinks* owns a change, not proof of authorship — confirm against the actual author.
- Confirm PR authorship via `pulls/<n>/commits`, NEVER `commits?sha=<branch>`. Branch-scoped endpoints return the branch's full ancestry, so a maintainer master-merge drags in the bot's commits from *other* PRs and produces a false "the bot worked this PR" positive.
- Never repeat a maintainer authorization as a verbatim quote unless their words are in a real inbound. Verify provenance (does the quoted comment id actually exist / resolve?) before propagating it into public artifacts.
- Attribute a go-ahead that came from a relayer's judgment as "per the handoff / held pending maintainer review" — never "the maintainer asked for X."
- "Verify it's clean" means re-read the CURRENT bytes on GitHub (`gh api .../comments/<id> --jq .body`, `gh pr view --json body`), not your memory of what you wrote.
- Fix errors on the right surface: your own comment → `PATCH`/edit-in-place; a PR body you don't own → route to the fixer. Correct the flagger factually and fix any internal notes carrying the same error.
- Stand down when a maintainer or external contributor is already driving a fix — a competing bot PR is likely to be closed even when correct. Bias to advisory triage.
- Stand-down detection signals: `assignees` set to a maintainer, an active external contributor or "I'll take this" comment, or a linked PR already open.
- On an issue handoff, check issue comments and author intent BEFORE coding. If an external contributor was invited/is writing the fix, stop at a read-only plan; re-engage only if they abandon it AND a maintainer explicitly asks the bot to take over.
- If drafting anyway, keep the draft thin and parked, and close it the moment the issue closes — never let a parked draft rot against a closed issue.
- A supervisor "dropped-promise, re-wake and open the PR" nudge can resolve to STAND-DOWN, not re-wake: re-verify the issue's *current* assignee first. A self-assignment by a collaborator between triage and the nudge flips the correct action.
- Answer a parent's "open the PR" premise with the better-grounded outcome, not blind obedience — preserve the diff as a ready-to-apply advisory and sharpen the public triage comment to maintainer-facing.
- An isolated `gh api .../comments` re-query is authoritative; a batched `gh issue view --json comments,labels,...` can return stale `comments:[]`/`labels:[]` — don't conclude "my triage artifact vanished" from the batched read.

## Verifying author and mention identity before posting

Before naming a person as the author or owner of a PR, commit, or change in a GitHub comment, verify it against the actual source — not memory or inference. An `@`-mention of the wrong author is a public, maintainer-visible error that costs credibility (incident #11877: the verdict said "@skiminki-nv (author of #11493)" but csyonghe authored it, and jkwak-work publicly called it out). The PR-number and commit citations can be right while the *person* is wrong, so verify the person independently: `gh api repos/<o>/<r>/pulls/<n> --jq '{author: .user.login}'` and/or the commit's `.author.login`. Existing labels and assignees (`Office-<name>`) are a cross-check on who a maintainer *thinks* owns a change, but confirm against the actual author. ⚠️ If caught with a wrong mention, correct it in-place on the bot's own comment, reply factually to the flagger, and fix any internal notes that carried the same error ([verify @-mention identity against PR/commit author before posting](../learnings/1783355490728-verify-mention-identity-against-pr-commit-author-b.md)).

A relayed authorization can carry a *fabricated* maintainer attribution straight into public GitHub artifacts, so audit the bytes and attribute policy to the actual authorizer. On slang#12176 the orchestrator relayed a draft-PR authorization framed as a verbatim maintainer quote ("jkwak-work commented: 'create the README as a draft PR'") with a comment id that 404'd — the quote was manufactured, and the false attribution propagated into a public issue comment *and* the PR body ("per the maintainer's go"). ⛔ The trap: because the "maintainer's go" was believed when the downstream artifacts were written, the first "verify nothing fabricated reached GitHub" report wrongly said "clean" — only re-reading the live bytes (`gh api …/comments/<id> --jq .body`, `gh pr view --json body`) exposed it. The rules that follow: verify authorization provenance (does the quoted comment actually exist?) before repeating it publicly; attribute a go-ahead that came from the relayer's judgment as "per the handoff / held pending maintainer review," never "the maintainer asked for X" unless their words are in a real inbound; ✅ "verify it's clean" means read the CURRENT bytes, not your memory of what you wrote; and fix on the right surface — your own comment gets a `PATCH`, the PR body routes to the fixer ([a relayed authorization can carry a fabricated maintainer attribution into public GitHub artifacts — audit the bytes](../learnings/1784656869644-a-relayed-authorization-can-carry-a-fabricated-mai.md)).

## Confirming PR authorship from the right endpoint

Confirm PR authorship via `pulls/<n>/commits`, never `commits?sha=<branch>`. The branch-scoped endpoints return the branch's full *ancestry* — once a maintainer merges master into a long-lived PR branch, that ancestry includes the bot's commits from *other* merged PRs, producing a false positive: "the bot pushed N commits to this PR" when it never touched the branch. On slang#10788, `commits?sha=copilot/fix-empty-structs-handling` showed "9 nv-slang-bot commits" (relayed to the operator as "bot engaged"), but `pulls/10788/commits` showed 5 commits, 0 from the bot — the 9 were master's unrelated bot commits dragged in by a maintainer master-merge. ⚠️ Because authorship drives stand-down-vs-re-drive decisions, getting it wrong inverts the correct action (re-driving a "stalled" chain maintainers actually own = clobber risk). Always confirm the *author* of the specific commits via the PR-scoped endpoint before asserting "the bot worked / didn't work this PR" ([verify PR authorship via pulls/<n>/commits, never commits?sha=branch](../learnings/1783639312952-verify-pr-authorship-via-pulls-n-commits-never-com.md)).

## Standing down when someone else owns the fix

When an issue already has a maintainer or external contributor active on it, a competing bot PR is likely to be closed even when correct — this is a consolidated rule drawn across seven postmortems. Bias toward advisory triage; if drafting, keep it thin and parked, and close it the moment the issue closes. Detection signals: `assignees` set to a maintainer, an active external contributor or "I'll take this" comment, or a linked PR already open. ⛔ Do not let a parked draft rot against a closed issue ([CONSOLIDATED — stand down when a maintainer/contributor is already driving the fix](../learnings/1782648000000-CONSOLIDATED-stand-down-when-maintainer-or-contributor-drives-fix.md)).

The specific case of an invited external contributor: on an issue handoff, check issue comments and author intent *before* coding. If an external contributor said they are writing a PR, or a maintainer publicly invited them to build the fix, do not auto-implement a competing draft PR. Stand down at a read-only plan. Re-engage only if the contributor abandons the PR AND a maintainer explicitly asks the bot to take over ([don't auto-implement issues owned by an invited external contributor](../learnings/1780473504394-don-t-auto-implement-issues-owned-by-an-invited-ex.md)).

A supervisor or parent nudge — "the fixer dropped a promise, no PR exists, re-wake it and open the draft" — can resolve to STAND-DOWN, not re-wake, so re-verify the issue's *current* assignee first. Concrete case: slang#11970 (Metal bindless MSL). The nudge was factually right (no PR, no `fix/issue-11970` branch, the fixer's cited commit `52fee2521b` never pushed to origin, bug still live at HEAD) — but between triage (07-07) and the nudge (07-14) the issue was self-assigned (07-08) by `jhelferty-nv`, a core collaborator who authored the very framework the recommended fix extends (#11331). That triggers the CONSOLIDATED stand-down rule: an assigned maintainer means a competing bot PR gets closed even when correct; the durable value is the analysis plus tests offered as an advisory. ✅ Right move: tell the fixer NOT to open a PR (preserve its diff as a ready-to-apply advisory), sharpen the public triage comment to a maintainer-facing advisory (Next-action = maintainer-owned; strip stale "handed to fixer / fix incoming" framing), and report the corrected picture up — the parent's "open the PR" premise is answered with a better-grounded outcome, not obeyed blindly. ⚠️ Also: an isolated `gh api .../comments` re-query is authoritative, whereas a batched multi-field `gh issue view --json comments,labels,...` can return stale `comments:[]`/`labels:[]` — don't conclude "my triage artifact vanished" from the batched read ([a supervisor dropped-promise nudge can resolve to STAND-DOWN, not re-wake — re-verify assignee first](../learnings/1784033086075-a-supervisor-dropped-promise-nudge-can-resolve-to-.md)).
