# Ownership and Mention Identity

## TL;DR

- Verify any person you name as author/owner in a public comment against the live source (`gh api .../pulls/<n> --jq .user.login`, commit `.author.login`), never from memory. The PR number can be right while the person is wrong. `Office-<name>` labels and assignees are a cross-check, not proof.
- Confirm PR authorship via `pulls/<n>/commits`, never `commits?sha=<branch>`: branch ancestry drags in the bot's commits from other PRs after a maintainer master-merge, a false "the bot worked this PR".
- Quote a maintainer authorization only when the words are in a real inbound and the cited comment id resolves. A relayer's judgment is "per the handoff / held pending maintainer review", never "the maintainer asked for X".
- "Verify it's clean" means re-reading the current bytes on GitHub. Fix your own comment by edit-in-place; route a PR body you don't own to its owner; correct the flagger factually and fix internal notes carrying the same error.
- Stand down when a maintainer or external contributor drives the fix (maintainer assignee, "I'll take this", invited contributor, linked PR open): a competing bot PR is likely closed even when correct. Bias to advisory triage; any draft stays thin and parked and closes when the issue closes. Re-engage only if the contributor abandons it AND a maintainer asks the bot.
- "Unassigned" is a live fact: re-check `gh issue view N --json assignees` at every GO, nudge, and status report (a bot can auto-assign a maintainer seconds after a bot PR opens). An assignee changes whom to ask: ask them on GitHub, keep the operator for what they cannot do.
- A "dropped promise, re-wake and open the PR" nudge can resolve to STAND-DOWN. Answer the parent's premise with the better-grounded outcome; keep the diff as a ready-to-apply advisory and make the public triage comment maintainer-facing.
- Parked issues change silently. On every re-check read the issue timeline (`assigned`, `labeled`, `milestoned`, Issue Type, `cross-referenced`, `closed`) and open every linking issue or PR; `issue.updatedAt` later than the last comment is the trigger. An assignee owns the issue (hand off only on their ask); a moved direction means no handoff; Issue Type and label-only signals (`SPF:*`, `slang 202c`) are hints, not decisions. Check `state`/`closedAt` and the reporter's own PR list too: a merged `Fixes #N` PR means a parent `[Report]` only, with no fixer and no issue post.
- Before saying a human PR "covers" the triage findings, build its head in a private worktree and run the full repro matrix; if your own fix is already built, report only-yours / only-theirs / conflicting cases and let the parent decide.
- On those re-checks post nothing new; edit the bot's own last comment in place so it names the owner or new plan. Diff live state against a one-shot re-check prompt before following its branches.
- Look for a community/duplicate PR at every gate: orchestrator before dispatch; triager before routing and on each fixer status; fixer at setup, when the build starts, and before `gh pr create`; reviewer at start. Use the timeline `cross-referenced` query, not only `in:body` search; re-check siblings in a batch; dedup with 2–3 phrasings.
- Core-team, self-assigned, or self-fixing reporters usually fix it themselves. When their PR exists: stand the fixer down, validate it locally against the acceptance criteria, report the results to the parent, which relays them to maintainers (2026-11-05 ruling; earlier chains posted evidence on the issue), never post findings on their PR, never open a competing PR. A defect that also reproduces on master is filed as its own deduped bug (Type=Bug, `reproduced`), naming the PR in plain text only.
- A maintainer self-assign or milestone, even with no comment, holds the issue: before any deferred post or push re-read assignee + milestone + timeline; post nothing, push nothing, cancel the one-shot, park prepared commits on a local-only branch. Re-derive PR linkage from `gh pr list --author` + `Fixes #N`, not a memo. `action_required` CI on an outside PR means a maintainer must approve the run.
- Answer a perf CHANGES_REQUESTED with the PR's own benchmark, main vs PR on our GPU, medians over two runs; post on the issue and name the blocking reviewer. An old-head CHANGES_REQUESTED still blocks.
- Before calling a design change "unapproved", list commit authors and assignees: the maintainer may have written it.
- An isolated `gh api .../comments` read is authoritative; a batched `gh issue view --json comments,labels,...` can return stale empties.

## Verifying author and mention identity before posting

Before naming a person as the author or owner of a PR, commit, or change in a GitHub comment, verify it against the live source: `gh api repos/<o>/<r>/pulls/<n> --jq '{author: .user.login}'` and/or the commit's `.author.login`. The PR number can be right while the person is wrong: #11877's verdict credited "@skiminki-nv (author of #11493)", csyonghe wrote it, and jkwak-work called it out publicly. Labels and assignees (`Office-<name>`) show who a maintainer *thinks* owns a change, not who authored it. ⚠️ If caught, correct the bot's own comment in place, reply factually to the flagger, and fix internal notes that carried the same error ([verify @-mention identity against PR/commit author before posting](../learnings/1783355490728-verify-mention-identity-against-pr-commit-author-b.md)).

Authorization provenance needs the same check. On slang#12176 a draft-PR go was relayed as a verbatim quote ("jkwak-work commented: 'create the README as a draft PR'") whose comment id 404'd, and the false attribution reached a public issue comment and the PR body ("per the maintainer's go"). ⛔ The first "nothing fabricated reached GitHub" audit said "clean" from memory; only re-reading the live bytes (`gh api …/comments/<id> --jq .body`, `gh pr view --json body`) exposed it. So confirm a quoted comment exists before repeating it, attribute a relayer's go-ahead as "per the handoff / held pending maintainer review", ✅ verify against the CURRENT bytes, and fix on the right surface: `PATCH` your own comment, route the PR body to the fixer ([a relayed authorization can carry a fabricated maintainer attribution into public GitHub artifacts — audit the bytes](../learnings/1784656869644-a-relayed-authorization-can-carry-a-fabricated-mai.md)).

## Confirming PR authorship from the right endpoint

Use `pulls/<n>/commits`, never `commits?sha=<branch>`: a branch-scoped listing returns full ancestry, which after a maintainer merges master into a long-lived PR branch includes the bot's commits from *other* merged PRs. On slang#10788 `commits?sha=copilot/fix-empty-structs-handling` showed 9 nv-slang-bot commits (relayed to the operator as "bot engaged"); `pulls/10788/commits` showed 5, none from the bot. ⚠️ Authorship decides stand-down vs re-drive, so a false positive inverts the action and risks clobbering a chain maintainers own ([verify PR authorship via pulls/<n>/commits, never commits?sha=branch](../learnings/1783639312952-verify-pr-authorship-via-pulls-n-commits-never-com.md)).

The same listing (`gh api repos/<o>/<r>/pulls/<n>/commits --jq '.[] | "\(.sha[0:10]) \(.author.login)"'`) plus the assignees comes before calling a direction change unapproved. On #13406 a reviewer flagged commit `4752340d4c` ("Defer the __ref_writeonly read check") as walking back jhelferty-nv's "every read is an error" request with no approving comment, but they had self-assigned the PR and authored that commit and the 13 others after 10-13. Once a maintainer takes over the branch, the fixer and reviewer stand down unless they ask ([check commit authors before flagging "no maintainer approval"](../learnings/1792056812976-before-flagging-no-maintainer-approval-for-a-desig.md)).

## Standing down when someone else owns the fix

When a maintainer or external contributor already drives an issue, a competing bot PR is likely closed even when correct (seven postmortems). Signals: a maintainer assignee, an "I'll take this" comment, a linked open PR, or a maintainer inviting a contributor to build the fix. On a handoff, read comments and author intent *before* coding; if owned, stop at a read-only plan and offer advisory triage. Re-engage only if the contributor abandons the PR AND a maintainer explicitly asks the bot. A draft made anyway stays thin and parked; ⛔ close it the moment the issue closes ([CONSOLIDATED — stand down when a maintainer/contributor is already driving the fix](../learnings/1782648000000-CONSOLIDATED-stand-down-when-maintainer-or-contributor-drives-fix.md), [don't auto-implement issues owned by an invited external contributor](../learnings/1780473504394-don-t-auto-implement-issues-owned-by-an-invited-ex.md)).

The assignee is a live fact; re-check it at every GO, nudge, and status report. On slang#11970 a supervisor's "dropped promise, re-wake the fixer and open the draft" nudge was factually right (no PR or branch, bug live at HEAD), but between triage and nudge core collaborator `jhelferty-nv`, author of the framework the fix extends, had self-assigned it. ✅ STAND-DOWN was right: the fixer opens no PR and keeps its diff as a ready-to-apply advisory, the public triage comment becomes a maintainer-facing advisory (strip "handed to fixer / fix incoming"), and the corrected picture goes up, answering the parent's premise rather than obeying it. ⚠️ An isolated `gh api .../comments` re-query is authoritative; a batched `gh issue view --json comments,labels,...` can return stale empties, so don't conclude "my triage artifact vanished" from it ([a supervisor dropped-promise nudge can resolve to STAND-DOWN, not re-wake — re-verify assignee first](../learnings/1784033086075-a-supervisor-dropped-promise-nudge-can-resolve-to-.md)). The assignee also changes whom to ask: on slang#13554 a bot auto-assigned jkwak-work 18 s after bot PR #13563 opened, yet for four days the Orchestrator called the issue "unassigned" and twice asked the operator about GPU CI; one triager comment to jkwak-work got the PR approved, GPU-verified and merged in ~25 h. Route go/no-go and CI questions to the assignee on GitHub; keep the operator for what the maintainer cannot do, such as a ci-approver gate nobody is releasing ([verify assignee live before an orchestrator GO that rests on "unassigned"](../learnings/1792030832310-verify-assignee-live-before-an-orchestrator-go-tha.md)).

A parked issue changes owner or direction the same way, usually without a comment. On every re-check read `gh api repos/<o>/<r>/issues/<n>/timeline` for `assigned`, `labeled`, `milestoned`, `cross-referenced` and `closed` events and the native Issue Type (GraphQL `IssueTypeAddedEvent`), and open every issue or PR that links back; `issue.updatedAt` later than the last comment means the timeline moved. The recurring outcomes:

- **A reporter PR makes a handoff a duplicate.** On #13641, with no new comment, the reporter had opened non-draft #13707 (`Fixes #13641`) and a maintainer had self-assigned and milestoned the issue; under triage step 9 nothing is posted, since the ready PR already shows the trail. The PR may already have merged and closed the issue, which `--comments` does not show: #14066's self-assigned MEMBER reporter merged #14068 within ~20 h, and #14069's invited reporter opened #14072 18 minutes later and merged it. So check `state`/`closedAt` and the timeline (`cross-referenced`, `closed`) first, then `gh pr view <pr> --json state,mergedAt,closingIssuesReferences`, before any post or label; a merged `Fixes`/`Closes #N` PR gets a parent `[Report]` only, with no fixer and no issue post ([Parked-on-reporter re-checks: read the issue timeline, not just comments](../learnings/1793663874761-parked-on-reporter-re-checks-read-the-issue-timeli.md), [R6-hold re-checks: check the timeline for a merged reporter PR before posting](../learnings/1793661430992-r6-hold-re-checks-check-the-timeline-for-a-merged-.md)). The timeline shows only this issue's cross-references, so also run `gh pr list -R <o>/<r> --author <reporter> --state all`: batch reporters fix sibling issues we parked (the #14029 re-check found #14149 fixing sibling #14135). `gh issue view --json authorAssociation` does not exist (the field is per-comment); it exits 1 and breaks a `| jq` pipe ([Parked-issue re-check: scan the reporter's own PR list](../learnings/1793637251147-parked-issue-re-check-scan-the-reporter-s-own-pr-l.md)).
- **An assignment is human ownership**, whether the maintainer self-assigns or assigns another human. The parent's rule since 2026-10-22 (#13638): hand off to slang-fixer only if the owner asks for or agrees to a bot PR, otherwise close the chain to the parent ([Parked issue self-assigned by a maintainer: fixer handoff becomes conditional](../learnings/1792674358775-parked-issue-self-assigned-by-a-maintainer-fixer-h.md)). On #13878 nobody answered the bot's (a)/(b) question, but jkwak-work assigned kaizhangNV, labeled the issue and set a milestone; a comments-only check would have reported "still parked" ([Parked-issue re-check: a maintainer assigning a human counts as human ownership](../learnings/1793030545714-parked-issue-re-check-a-maintainer-assigning-a-hum.md)). #13900 was the same, and the reporter also closed the dependent slang-rhi PR as blocked on the issue. The ownership also freezes our own deferred work. On slang#14179 (2026-11-05) a triage comment was scheduled and a fix was held locally to fold into bot PR #13572, both timed to an "R6 hold" (that 4-day wait is retired; R6 is label-only, see [triage decisions](agent-fixer-triage-decisions.md)); meanwhile jkwak-work self-assigned and milestoned the issue without a comment. The parent ruled the issue held: post nothing (no comment, labels or Type), push no commit and add no `Fixes #N` to the PR, cancel the one-shot, keep the draft and memo, and resume only on an @nv-slang-bot mention, the assignee's ask or an operator ask. So any deferred post or push re-reads `gh api repos/<o>/<r>/issues/<n> --jq '{a:[.assignees[].login],m:.milestone.title}'` and the `/timeline` actor first, and a prepared commit is parked on a local-only branch (`git branch local/issue-<n>-<slug> <sha>`, then `git reset --keep <pushed-head>` on the PR branch) so a routine push of the PR cannot carry it ([before a held/scheduled issue post, re-check assignee + milestone](../learnings/1793879399551-before-a-held-scheduled-issue-post-re-check-assign.md), [a maintainer-assigned issue is held: don't fold its fix into a bot PR](../learnings/1793879440953-a-maintainer-assigned-issue-is-held-don-t-fold-its.md)).
- **A linked issue can move the direction.** On #13750 the assignee opened overhaul issue #13956, which picked option C over the tentative C++ rule A, and closed a sibling issue and its bot PR as will-not-fix. When the direction has moved, do not hand off an out-of-date brief ([Parked-issue re-checks: read the timeline cross-references, not just the comments](../learnings/1793041485668-parked-issue-re-checks-read-the-timeline-cross-ref.md)).
- **Issue Type and labels are hints, not picks.** A human-set Type (Documentation on a design-question issue, #13637/#13638) leans toward an option. On #13870 the maintainer, without a comment, reassigned to the decision owner, added `SPF:*` labels (Slang Proposed Feature lifecycle: Proposal / Experimental / Stable / Proposing to Stabilize / Proposing to Deprecate / Deprecated / Rejected / Withdrawn) and `slang 202c` (the breaking-change gate `isSlang202cOrLater` in `slang-check-decl.cpp`: a version-gated language change), and set a milestone. Record these as a routing hint and keep the chain parked until a comment states the decision ([Maintainer direction can arrive as labels/assignee with no comment — check the issue timeline on re-checks](../learnings/1793286193023-maintainer-direction-can-arrive-as-labels-assignee.md)).

In every outcome the bot posts no new comment. If its own last comment still promises a fixer or invites a PR on the old plan, edit it in place (no notification) to name the assignee or new direction and offer the bot fix on request (#13878, #13750). The newest nv-slang-bot comment may be the fixer's; when it already carries the live state, neither PATCH it nor post a duplicate 5-bullet. A one-shot re-check prompt is itself stale input: diff the live head SHA, labels, draft state and comments since its date before taking any branch. On #13876 the maintainer reversed the decision four days after the prompt and the fixer reworked the PR via webhook without a `[Fix Report]`; the right move was one `[Report]` delta correcting the parent's `[Triage Resolution]`, the new decision recorded verbatim in the chain-state page ([one-shot re-check prompts can be overtaken by events](../learnings/1793102591047-one-shot-re-check-prompts-can-be-overtaken-by-even.md); the general staleness rule is in [Scope, staleness, and missing side-effects](verification-e-scope-staleness-and-side-effects.md)). The close-out is `[Resolution]` when the re-check answers a live parent inbound; a one-shot `--process-after` re-check has no inbound and reports with the ungated `[Report]` ([Message Routing & Gating](agent-routing-message-routing-and-gating.md)). A reporter's side-finding issue filed together with their own PR (#13847/#13848) is not ours to triage either; a sibling session may be holding it on purpose.

## Checking for a community or duplicate PR before building, reviewing, or opening

A human PR can appear before or after any gate, and each miss cost real work: slang#13635's #13645 opened 23 min *before* the triage handoff and the fixer built for ~6 min before noticing; slang#13639's #13646 opened ~25 min *after* triage, caught only by codex PLAN_REVIEW; slang#13636's #13644 preceded bot PR #13650 by 12 min, the fixer never searched, and the peer reviewer found it by accident ([search for a community PR on the issue before opening a bot fix PR](../learnings/1792079739619-search-for-a-community-pr-on-the-issue-before-open.md)). A batch reporter opened `Fixes #N` 16 s after the issue (#13662 → #13663) or hours after our triage (#13642 → #13651) ([re-check for a community PR right before building](../learnings/1792074164816-re-check-for-a-community-pr-right-before-building-.md), [check the issue timeline for cross-referenced PRs before building](../learnings/1792076007832-check-issue-timeline-for-cross-referenced-prs-befo.md), [batch reporter files issue + PR together; search alternate wording](../learnings/1792084496275-batch-external-reporter-files-issue-pr-together-al.md)); slang#13766's #13775 landed mid-build, too late for a "before push" check ([recheck for a reporter's PR right after the build starts](../learnings/1792503223381-recheck-for-a-reporter-s-own-pr-right-after-the-bu.md)); slang#14019's #14022 opened 98 s before the triage comment and the "no duplicate" search missed it (also #13909/#13927) ([Check the issue timeline for a contributor PR before building a triaged fix](../learnings/1793284881331-check-the-issue-timeline-for-a-contributor-pr-befo.md)). The reviewer-side account of #13650 is on the review-process pages.

The check therefore runs at every gate:

- **Orchestrator before dispatch; triager before routing and on each fixer status message:** the timeline query below, then the timelines of *sibling* issues in a batch, since a PR can land after you parked a sibling. Keyword dedup against older issues needs two or three phrasings: "loadModuleFromIRBlob" missed an older duplicate phrased "IR binary modules" (#8744).
- **Fixer at setup, before the first source edit, as soon as the build starts, and before `gh pr create`:** `gh api repos/<o>/<r>/issues/<n>/timeline --jq '.[]|select(.event=="cross-referenced")|.source.issue.number'` plus `gh pr list -R <o>/<r> --search "<n> in:body" --state open`. A search is not the link graph; the timeline sees PRs that link from a comment or commit.
- **Reviewer at review start:** `gh pr list -R <repo> --state all --search "<n> OR <key symbol>"`, and `closingIssuesReferences` on the open PRs.

(A recall subagent may report your own fresh `active-work/<target>` sentinel as a "peer collision"; compare its `started-at` with your claim.)

The reporter's profile tells you how often to look. On slang#13793 a core-team MEMBER filed and self-assigned the issue, the timeline cross-referenced their fork PR a minute later, it was handed to slang-fixer anyway, and ~5 h later their #13798 (`Fixes #13793`) made the fixer's design waste. The merged R6 is label-only with no waiting period ([triage decisions](agent-fixer-triage-decisions.md)), so for a core-team, self-assigned, or self-fixing reporter the `cross-referenced` query is the only guard: run it before dispatch, at handoff, on every fixer status, and before the fixer opens a PR. The recovery that worked: stand the fixer down, open no competing PR, edit our issue comment in place to hand review to the human PR, and post the fixer's measured regression shapes (master-compiles/PR-errors inputs, each with a parity twin) on the issue, nothing on the human's PR ([triage: re-check the timeline before and during a fixer handoff](../learnings/1792555065568-triage-re-check-the-issue-timeline-for-a-reporter-.md), [check the timeline for a reporter or assignee PR before dispatching](../learnings/1792555081581-check-the-issue-timeline-for-a-reporter-or-assigne.md)).

On slang#14153 the reporter's #14170 opened 45 min after filing, while the bot built a stacked fix under a hold; the parent deferred to the human PR and the branch was dropped. Run the search plus timeline at Setup and before every review round. If your branch already exists, build both heads, run the same probe matrix, report the cases only yours covers, only theirs covers, and the conflicting hunks, and let the parent decide; call out a semantic test conflict explicitly (a capability-level E36107 made the human PR's emit-level E55204 test line unreachable) ([check for a reporter-opened PR before building a bot fix](../learnings/1793622493442-before-building-a-bot-fix-check-for-a-reporter-ope.md)). Before an issue comment says a human PR "covers" the triage findings, build its head privately and run the full repro matrix (#14133: #14150 tested only the simple case; we ran 4 repros × 7 targets × {default, `-O0`} plus NVRTC). Reusing a worktree: `git checkout --detach refs/triage/prN-head`; per submodule `git -c protocol.file.allow=always -c submodule.<name>.url=/workspace/agent/slang/.git/modules/<name> submodule update --init -- <path>` (the shared clone's submodule repos are shallow, so `--reference` fails); `cmake --preset default`, build `slangc` + `slang-glslang` (~3 min, 56 jobs). A stale `-version` string is not a stale binary; confirm by a behavior change. `/tmp` is wiped on restart, so keep repros in a memory bundle (`repro-<N>.md`) ([verify a human fix PR on a private worktree before claiming coverage](../learnings/1793667471112-verify-a-human-fix-pr-on-a-private-worktree-before.md)).

When a community PR exists, validate it rather than compete: apply it on a throwaway branch (`gh pr diff N > x.diff && git apply x.diff`, delete the branch afterwards), run the triage acceptance matrix, and report gaps up; if both PRs exist, post a coordination note on both. Since a 2026-11-05 parent ruling (precedents #13419/#13420/#13640/#13733) the validation results go to the parent only, which relays them to the maintainers; no review findings are posted on the human PR. A defect found on that PR that also reproduces on master (surplus attribute arguments assert in Debug because `checkAttribute` never rejects `argCount > paramCount`) is deduped and filed as its own bug with Type=Bug and the `reproduced` label, which needs no operator go-ahead; the new issue mentions the PR in plain text only and never asks the contributor to fix the pre-existing bug in their PR. No re-check is scheduled, because the PR's webhooks and merge are the resumable artifact (#14135 → PR #14149 → spin-off #14349) ([human PR validation: report findings up, file master-reproducible defects separately](../learnings/1793890745354-human-pr-validation-report-findings-up-file-master.md)). Use `gh pr view N --json …` and `gh pr diff N`, since even a read-only `gh api repos/.../pulls/N` trips the critique gate's PR-creation arm. On slangpy#1231 a scheduled "no reporter PR after 72 h → hand to fixer" became a review: the reporter had opened #1234 ten minutes after our invite, but our index recorded #1233, so re-derive linkage from `gh pr list --author <reporter>` plus a `Fixes #N` grep of the body, never a memo. Its CI sat at `action_required` (a maintainer must approve the run), the real blocker, so the Next-action names the shepherd and requested reviewers. Building the head (`--target slangpy_ext`, new test, repro, vulkan/cuda/cpu sweep) turned "a PR exists" into evidence, posted as non-blocking notes on the issue, not the contributor's PR ([verify a reporter's PR on GPU before a scheduled fixer handoff](../learnings/1792422129310-before-a-scheduled-fixer-handoff-on-a-reporter-pat.md)).

The same approach later unblocked it: ccummingsNV's CHANGES_REQUESTED ("doubles name lookups per dispatch") moved on our GPU run of the PR's own benchmark, untracked in the main worktree, twice per device on main and then on the locally merged PR (restore with `checkout --detach <base>`). The built-in table's 3-decimal ms is too coarse for µs dispatches, so a pytest plugin outside the worktree logged per-iteration means; outliers moved a 10-sample mean ~25%, so compare medians. Post the main→PR table on the issue and name the blocking reviewer for a re-review: GitHub does not clear a CHANGES_REQUESTED review on an old head when new commits land ([answer a maintainer's perf CHANGES_REQUESTED on a reporter PR by running the PR's own benchmark against main](../learnings/1792681690533-answer-a-maintainer-s-perf-changes-requested-on-a-.md)).
