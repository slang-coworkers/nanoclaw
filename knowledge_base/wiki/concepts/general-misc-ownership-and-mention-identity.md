# Ownership and Mention Identity

## TL;DR

- Verify any person you name as author/owner in a public comment against the live source (`gh api .../pulls/<n> --jq .user.login`, commit `.author.login`), never from memory. The PR number can be right while the person is wrong. `Office-<name>` labels and assignees are a cross-check, not proof.
- Confirm PR authorship via `pulls/<n>/commits`, never `commits?sha=<branch>`: branch ancestry drags in the bot's commits from other PRs after a maintainer master-merge, a false "the bot worked this PR".
- Quote a maintainer authorization only when the words are in a real inbound and the cited comment id resolves. A relayer's judgment is "per the handoff / held pending maintainer review", never "the maintainer asked for X".
- "Verify it's clean" means re-reading the current bytes on GitHub. Fix your own comment by edit-in-place; route a PR body you don't own to its owner; correct the flagger factually and fix internal notes carrying the same error.
- Stand down when a maintainer or external contributor drives the fix (maintainer assignee, "I'll take this", invited contributor, linked PR open): a competing bot PR is likely closed even when correct. Bias to advisory triage; any draft stays thin and parked and closes when the issue closes. Re-engage only if the contributor abandons it AND a maintainer asks the bot.
- "Unassigned" is a live fact: re-check `gh issue view N --json assignees` at every GO, nudge, and status report (a bot can auto-assign a maintainer seconds after a bot PR opens). An assignee changes whom to ask: ask them on GitHub, keep the operator for what they cannot do.
- A "dropped promise, re-wake and open the PR" nudge can resolve to STAND-DOWN. Answer the parent's premise with the better-grounded outcome; keep the diff as a ready-to-apply advisory and make the public triage comment maintainer-facing.
- Parked issues change silently. On every re-check read the issue timeline (`assigned`, `labeled`, `milestoned`, Issue Type, `cross-referenced`, `closed`) and open every linking issue or PR; `issue.updatedAt` later than the last comment is the trigger. An assignee owns the issue (hand off only on their ask); a moved direction means no handoff; Issue Type and label-only signals (`SPF:*`, `slang 202c`) are hints, not decisions.
- On those re-checks post nothing new; edit the bot's own last comment in place so it names the owner or new plan. Diff live state against a one-shot re-check prompt before following its branches.
- Look for a community/duplicate PR at every gate: orchestrator before dispatch; triager before routing and on each fixer status; fixer at setup, when the build starts, and before `gh pr create`; reviewer at start. Use the timeline `cross-referenced` query, not only `in:body` search; re-check siblings in a batch; dedup with 2–3 phrasings.
- Core-team, self-assigned, or self-fixing reporters usually fix it themselves. When their PR exists: stand the fixer down, validate it locally against the acceptance criteria, post measured evidence on the ISSUE (never their PR), never open a competing PR. Re-derive PR linkage from `gh pr list --author` + `Fixes #N`, not a memo. `action_required` CI on an outside PR means a maintainer must approve the run.
- Answer a perf CHANGES_REQUESTED with the PR's own benchmark, main vs PR on our GPU, medians over two runs; post on the issue and name the blocking reviewer. An old-head CHANGES_REQUESTED still blocks.
- Before calling a design change "unapproved", list commit authors and assignees: the maintainer may have written it.
- An isolated `gh api .../comments` read is authoritative; a batched `gh issue view --json comments,labels,...` can return stale empties.

## Verifying author and mention identity before posting

Before naming a person as the author or owner of a PR, commit, or change in a GitHub comment, verify it against the live source: `gh api repos/<o>/<r>/pulls/<n> --jq '{author: .user.login}'` and/or the commit's `.author.login`. The PR-number citation can be right while the person is wrong (#11877: the verdict credited "@skiminki-nv (author of #11493)", csyonghe wrote it, and jkwak-work called it out publicly). Labels and assignees (`Office-<name>`) show who a maintainer *thinks* owns a change, not who authored it. ⚠️ If caught, correct the bot's own comment in place, reply factually to the flagger, and fix internal notes that carried the same error ([verify @-mention identity against PR/commit author before posting](../learnings/1783355490728-verify-mention-identity-against-pr-commit-author-b.md)).

Authorization provenance needs the same check, because a relayed authorization can carry a fabricated maintainer attribution into public artifacts. On slang#12176 a draft-PR go was relayed as a verbatim quote ("jkwak-work commented: 'create the README as a draft PR'") whose comment id 404'd; the false attribution reached a public issue comment and the PR body ("per the maintainer's go"). ⛔ The first "nothing fabricated reached GitHub" report said "clean" because it relied on memory of what had been written; only re-reading the live bytes (`gh api …/comments/<id> --jq .body`, `gh pr view --json body`) exposed it. So: confirm the quoted comment exists before repeating it; attribute a go-ahead that came from the relayer's judgment as "per the handoff / held pending maintainer review"; ✅ verify by reading the CURRENT bytes; and fix on the right surface — `PATCH` your own comment, route the PR body to the fixer ([a relayed authorization can carry a fabricated maintainer attribution into public GitHub artifacts — audit the bytes](../learnings/1784656869644-a-relayed-authorization-can-carry-a-fabricated-mai.md)).

## Confirming PR authorship from the right endpoint

Confirm PR authorship via `pulls/<n>/commits`, never `commits?sha=<branch>`. Branch-scoped endpoints return the branch's full ancestry, which after a maintainer merges master into a long-lived PR branch includes the bot's commits from *other* merged PRs. On slang#10788, `commits?sha=copilot/fix-empty-structs-handling` showed 9 nv-slang-bot commits (relayed to the operator as "bot engaged"), but `pulls/10788/commits` showed 5 commits, none from the bot. ⚠️ Authorship drives stand-down vs re-drive, so a false positive inverts the action — re-driving a "stalled" chain that maintainers own is a clobber risk ([verify PR authorship via pulls/<n>/commits, never commits?sha=branch](../learnings/1783639312952-verify-pr-authorship-via-pulls-n-commits-never-com.md)).

The same listing, `gh api repos/<o>/<r>/pulls/<n>/commits --jq '.[] | "\(.sha[0:10]) \(.author.login)"'`, plus the assignees, comes before calling a direction change unapproved. On #13406 a reviewer flagged commit `4752340d4c` ("Defer the __ref_writeonly read check") as walking back jhelferty-nv's "every read is an error" request with no approving comment, but jhelferty-nv had self-assigned the PR and authored that commit and the 13 others after 10-13. Once a maintainer takes over the branch, the fixer and reviewer stand down unless she asks ([check commit authors before flagging "no maintainer approval"](../learnings/1792056812976-before-flagging-no-maintainer-approval-for-a-desig.md)).

## Standing down when someone else owns the fix

When a maintainer or external contributor is already driving an issue, a competing bot PR is likely to be closed even when correct (consolidated across seven postmortems). Detection signals: `assignees` set to a maintainer, an active contributor or "I'll take this" comment, a linked PR already open, or a maintainer publicly inviting a contributor to build the fix. On a handoff, read the issue comments and author intent *before* coding; if the issue is owned this way, stop at a read-only plan and offer advisory triage. Re-engage only if the contributor abandons the PR AND a maintainer explicitly asks the bot to take over. If drafting anyway, keep the draft thin and parked; ⛔ close it the moment the issue closes rather than let it rot ([CONSOLIDATED — stand down when a maintainer/contributor is already driving the fix](../learnings/1782648000000-CONSOLIDATED-stand-down-when-maintainer-or-contributor-drives-fix.md), [don't auto-implement issues owned by an invited external contributor](../learnings/1780473504394-don-t-auto-implement-issues-owned-by-an-invited-ex.md)).

The assignee is a live fact, so re-check it at every GO, nudge, and status report. On slang#11970 (Metal bindless MSL) a supervisor's "the fixer dropped a promise, re-wake it and open the draft" nudge was factually right (no PR, no `fix/issue-11970` branch, the cited commit `52fee2521b` never pushed, bug still live at HEAD), but between triage (07-07) and the nudge (07-14) core collaborator `jhelferty-nv`, who authored the framework the fix extends (#11331), had self-assigned it. ✅ The right move was STAND-DOWN: tell the fixer not to open a PR and keep its diff as a ready-to-apply advisory, rewrite the public triage comment as a maintainer-facing advisory (Next-action maintainer-owned; strip "handed to fixer / fix incoming"), and report the corrected picture up — answering the parent's premise rather than obeying it. ⚠️ An isolated `gh api .../comments` re-query is authoritative; a batched `gh issue view --json comments,labels,...` can return stale `comments:[]`/`labels:[]`, so don't conclude "my triage artifact vanished" from it ([a supervisor dropped-promise nudge can resolve to STAND-DOWN, not re-wake — re-verify assignee first](../learnings/1784033086075-a-supervisor-dropped-promise-nudge-can-resolve-to-.md)). The assignee also changes whom to ask. On slang#13554 github-actions[bot] auto-assigned jkwak-work 18 s after bot PR #13563 opened, yet for four days the Orchestrator told the operator the issue was "unassigned" and twice asked them about GPU CI; one triager delta comment to jkwak-work ("un-draft for GPU CI?") got the PR approved, un-drafted, GPU-verified and merged in about 25 h. Route go/no-go and CI questions to the assignee on GitHub, and keep the operator for what the maintainer cannot do, such as a ci-approver gate nobody is releasing ([verify assignee live before an orchestrator GO that rests on "unassigned"](../learnings/1792030832310-verify-assignee-live-before-an-orchestrator-go-tha.md)).

An issue parked for maintainer direction changes owner or direction the same way, usually without a comment, so `gh issue view --comments` is not enough. On every re-check read `gh api repos/<o>/<r>/issues/<n>/timeline` for `assigned`, `labeled`, `milestoned`, `cross-referenced` and `closed` events and the native Issue Type (GraphQL `IssueTypeAddedEvent`), and open every new issue or PR that links back. A quick trigger: `issue.updatedAt` later than the last comment means the timeline moved. The recurring outcomes:

- **A reporter PR makes a handoff a duplicate.** On #13641 there was no new comment, but the external reporter had opened non-draft #13707 (`Fixes #13641`) and a maintainer had self-assigned and milestoned the issue; under triage step 9 nothing is posted, because the ready-for-review PR already shows the trail.
- **An assignment is human ownership**, whether the maintainer self-assigns or assigns another human. The parent's rule since 2026-10-22 (#13638): hand off to slang-fixer only if the owner asks for or agrees to a bot PR, otherwise close the chain to the parent ([Parked issue self-assigned by a maintainer: fixer handoff becomes conditional](../learnings/1792674358775-parked-issue-self-assigned-by-a-maintainer-fixer-h.md)). On #13878 nobody answered the bot's (a)/(b) question, but jkwak-work assigned kaizhangNV, labeled the issue and set a milestone; a comments-only check would have reported "still parked" ([Parked-issue re-check: a maintainer assigning a human counts as human ownership](../learnings/1793030545714-parked-issue-re-check-a-maintainer-assigning-a-hum.md)). #13900 was the same, with the reporter also closing the dependent slang-rhi PR as blocked on the issue.
- **A linked issue can move the direction.** On #13750 the assignee opened overhaul issue #13956, which picked option C instead of the tentative C++ rule A, and closed a sibling issue and its bot PR as will-not-fix. A handoff would have carried an out-of-date brief; when the direction has moved, do not hand off ([Parked-issue re-checks: read the timeline cross-references, not just the comments](../learnings/1793041485668-parked-issue-re-checks-read-the-timeline-cross-ref.md)).
- **Issue Type and labels are hints, not picks.** A human-set Type (Documentation on a design-question issue, #13637/#13638) leans toward an option. On #13870 the maintainer wrote no comment but reassigned to the decision owner, added `SPF:*` labels (the Slang Proposed Feature lifecycle: Proposal / Experimental / Stable / Proposing to Stabilize / Proposing to Deprecate / Deprecated / Rejected / Withdrawn), added `slang 202c` (it maps to the breaking-change gate `isSlang202cOrLater` in `source/slang/slang-check-decl.cpp`, suggesting a version-gated language change) and set a milestone. Record these as a routing hint and keep the chain parked until a comment states the decision ([Maintainer direction can arrive as labels/assignee with no comment — check the issue timeline on re-checks](../learnings/1793286193023-maintainer-direction-can-arrive-as-labels-assignee.md)).

In every outcome the bot posts no new comment. If its own last comment still promises a fixer or invites a PR on the old plan, edit it in place (an edit sends no notification) so it names the assignee or new direction and offers the bot fix on request (#13878, #13750). The newest nv-slang-bot comment may be the fixer's, not the triager's; when it already carries the live state, neither PATCH it nor post a duplicate 5-bullet. A one-shot re-check prompt is itself stale input, so diff the live head SHA, labels, draft state and comments since its date before taking any of its branches. On #13876 the maintainer reversed the decision four days after the prompt and the fixer reworked the PR through the webhook without a `[Fix Report]`; the right move was one `[Report]` delta correcting the parent's `[Triage Resolution]`, with the new decision recorded verbatim in the chain-state page ([one-shot re-check prompts can be overtaken by events](../learnings/1793102591047-one-shot-re-check-prompts-can-be-overtaken-by-even.md); the general staleness rule is in [Scope, staleness, and missing side-effects](verification-e-scope-staleness-and-side-effects.md)). The close-out is `[Resolution]` when the re-check answers a live parent inbound; a one-shot `--process-after` re-check has no inbound and reports with the ungated `[Report]` ([Message Routing & Gating](agent-routing-message-routing-and-gating.md)). A reporter's side-finding issue filed together with their own PR (#13847/#13848) is not ours to triage either; a sibling session may be holding it on purpose.

## Checking for a community or duplicate PR before building, reviewing, or opening

A human PR can appear before or after any gate, and each miss cost real work. On slang#13635 the reporter's #13645 opened 23 minutes *before* the triage handoff, the triage comment still promised "a fixer opens a draft PR", and the fixer spent ~6 minutes building and reproducing before noticing. On slang#13639 non-draft #13646 opened ~25 minutes *after* the triage comment, when the fixer already had a worktree and plan; only codex PLAN_REVIEW spotted it. On slang#13636 the reporter's non-draft #13644 (same deletion, CLA signed) preceded bot PR #13650 by 12 minutes; the fixer never searched, and the peer reviewer found it by accident from a CI run and made it the top concern ([search for a community PR on the issue before opening a bot fix PR](../learnings/1792079739619-search-for-a-community-pr-on-the-issue-before-open.md)). In the albertrodriguezclo batch (#13631–#13662) the reporter opened `Fixes #N` 16 seconds after the issue (#13662 → #13663) or hours after our triage comment (#13642 → #13651) ([re-check for a community PR right before building](../learnings/1792074164816-re-check-for-a-community-pr-right-before-building-.md), [check the issue timeline for cross-referenced PRs before building](../learnings/1792076007832-check-issue-timeline-for-cross-referenced-prs-befo.md), [batch reporter files issue + PR together; search alternate wording](../learnings/1792084496275-batch-external-reporter-files-issue-pr-together-al.md)); on slang#13766 their #13775 landed 16 minutes after triage while the worktree build ran, too late for a "before push" check ([recheck for a reporter's PR right after the build starts](../learnings/1792503223381-recheck-for-a-reporter-s-own-pr-right-after-the-bu.md)); on slang#14019 the reporter's #14022 opened at 14:37:45Z, 98 s before the triage comment, and the triager's "no duplicate" search missed it (#13909/#13927 was the same race) ([Check the issue timeline for a contributor PR before building a triaged fix](../learnings/1793284881331-check-the-issue-timeline-for-a-contributor-pr-befo.md)). The reviewer-side account of #13650 is folded on the review-process pages.

The check therefore runs at every gate:

- **Orchestrator before dispatch; triager before routing and again on each fixer status message:** the timeline query below, then the timelines of *sibling* issues in a batch, since a PR can land after you parked a sibling. Keyword dedup against older issues needs two or three phrasings: "loadModuleFromIRBlob" missed an older duplicate phrased "IR binary modules" (#8744).
- **Fixer at setup, before the first source edit, as soon as the build is kicked off, and before `gh pr create`:** `gh api repos/<o>/<r>/issues/<n>/timeline --jq '.[]|select(.event=="cross-referenced")|.source.issue.number'` plus `gh pr list -R <o>/<r> --search "<n> in:body" --state open`. A search is not the link graph; the timeline sees PRs that link from a comment or commit.
- **Reviewer at review start:** `gh pr list -R <repo> --state all --search "<n> OR <key symbol>"`, and `closingIssuesReferences` on the open PRs.

(A recall subagent that sees your own fresh `active-work/<target>` sentinel and running build reports it as a "peer collision"; compare the sentinel's `started-at` with your own claim before acting.)

The reporter's profile tells you how often to look. On slang#13793 (2026-10-20) kaizhangNV, a core-team MEMBER, filed and self-assigned the issue, and the timeline showed a cross-reference to their fork PR (kaizhangNV/slang#24) one minute after filing. It was handed to slang-fixer within 31 minutes anyway; about 4.5–5 hours later the reporter opened #13798 (`Fixes #13793`, ready for review) and the fixer's competing design was thrown away. The early bot comment also broke the R6 issue-wait rule (wait 4 days on a new human issue), whose gate nanoclaw#1993 was still a draft, so until it merges the timeline check is the only guard. For a core-team, self-assigned, or known self-fixing reporter, run the `cross-referenced` query before dispatch, at handoff, on every fixer status message, and before the fixer opens a PR. The recovery that worked: the triager stood the fixer down, opened no competing PR, edited its own issue comment in place to hand review to the human PR, and posted the fixer's measured regression shapes (inputs that compile on master but error on the PR, each paired with a parity twin) on the issue, with nothing on the human's PR ([triage: re-check the timeline before and during a fixer handoff](../learnings/1792555065568-triage-re-check-the-issue-timeline-for-a-reporter-.md), [check the timeline for a reporter or assignee PR before dispatching](../learnings/1792555081581-check-the-issue-timeline-for-a-reporter-or-assigne.md)).

When a community PR exists, validate it rather than compete with it: apply it on a throwaway branch (`gh pr diff N > x.diff && git apply x.diff`, delete the branch afterwards), run the triage acceptance matrix, and report the gaps up; if both PRs already exist, post a coordination note on both. Use `gh pr view N --json …` and `gh pr diff N` for these reads, since even a read-only `gh api repos/.../pulls/N` trips the critique gate's PR-creation arm. On slangpy#1231 this turned a scheduled "no reporter PR after 72 h → hand to fixer" plan into a review: the reporter had opened #1234 ten minutes after our invite, but our index line recorded #1233 (another issue's PR), so re-derive linkage from `gh pr list --author <reporter>` plus a `Fixes #N` grep of the body, never from a memo. The PR's `ci`/`checks` runs sat at `action_required` — a maintainer must approve the workflow run — which was the real blocker, so the Next-action names the shepherd and requested reviewers. Building the PR head locally (`--target slangpy_ext`, then the new test, the repro and a vulkan/cuda/cpu device sweep) turned "a PR exists" into evidence, posted as non-blocking notes on the issue rather than the contributor's PR ([verify a reporter's PR on GPU before a scheduled fixer handoff](../learnings/1792422129310-before-a-scheduled-fixer-handoff-on-a-reporter-pat.md)).

The same evidence-on-the-issue approach later unblocked that PR. ccummingsNV left CHANGES_REQUESTED on slangpy#1234 because it "doubles name lookups per dispatch"; what moved the chain was our GPU measurement with the PR's own benchmark. Put the PR's benchmark file in the main worktree as an untracked file, build `slangpy_ext` and run it twice per device; merge the PR locally, rebuild and rerun; restore with `checkout --detach <base>` and rebuild. The built-in benchmark table prints ms to three decimals, too coarse for µs dispatches, so a small pytest plugin kept outside the worktree logged per-iteration means; single outlier iterations moved a 10-sample mean by about 25%, so compare medians too. Post the main→PR table on the issue and name the blocking reviewer for a re-review: GitHub does not clear a CHANGES_REQUESTED review on an old head when new commits are pushed ([answer a maintainer's perf CHANGES_REQUESTED on a reporter PR by running the PR's own benchmark against main](../learnings/1792681690533-answer-a-maintainer-s-perf-changes-requested-on-a-.md)).
