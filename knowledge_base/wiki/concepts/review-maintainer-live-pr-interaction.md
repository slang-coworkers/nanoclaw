# Working Live PRs Alongside Maintainers and Sibling Bots

## TL;DR

- **Re-derive a maintainer's scope directive from the LIVE primary comment, never a paraphrase or the webhook `body`.** A dropped clause ("also fix #N") or an inferred narrowing ("keep it scoped") inverts scope and wastes a reviewed, CI-green PR.
- **Only the maintainer can waive a maintainer's requirement.** Grade each item met/missed; "partial", "known partial in the PR body" and an orchestrator scope-out are not deferrals, so a missed item means REQUEST_CHANGES pending deferral. "Maintainer direction" is a human maintainer's review or comment, verified live; a reporter's issue-body proposal (even `MEMBER`) or a triage memo is an "issue requirement", judged on merit.
- **Re-read maintainer direction right before the verdict goes out**, not only at review start; report any new human MEMBER comment with its timestamp (#13975).
- A draft follows the literal requirement; a bot-introduced invariant is design input, and an exception shrinks to what is technically forced, posed as a question with a failure example.
- **A hands-on maintainer may push onto your branch and leave rapid comment batches.** Re-fetch HEAD before committing or replying; many comments are resolution notes ("Implemented in <sha>"), not asks.
- **Don't race a self-fixing maintainer**: one holding ack, then pause; inspect their side with READ-ONLY git; if they resolved it, sync and post ONE standing-down comment.
- **A maintainer refactor pushed onto the bot's branch plus their own PR on the same files is a supersede in progress**: stand down on ours, post the carry-forward (tests, stale expectations) on theirs.
- **A maintainer PR on the same issue → flag to the operator immediately**; an operator-held draft loses that race. A bot draft un-reviewed for weeks after a maintainer is assigned is the slow form: ask early. Closing our own superseded bot draft (with a pointer comment) is not operator-gated.
- Debug insts: skip only location/scope markers (DebugLine/DebugScope/DebugNoScope); DebugVar/DebugValue carry state and are not erasable at zero uses. An IR operand-layout change bumps the module version range.
- **Two maintainers diverge on a design → provide evidence, ask them to align; never pick a side.** Gate any redesign on both agreeing AND the alternative confirmed to meet the original hard constraint.
- **Run the anti-dup check against a LIVE re-read immediately before posting** — a peer bot session shares your GitHub identity.
- **Never reword a maintainer's existing comment, not even a typo**; it records design intent. Grep your diff for removed `//` lines.
- **Your push dismisses a maintainer's APPROVED review** (fix or conflict-resolution push alike). Check `reviewDecision`/`review_dismissed` at head before reporting "approved"; batch fixes into one push.
- Regression-test headers state the guarded invariant in a sentence or two; bug history goes in the commit message and PR body.
- A docs PR from a question issue adds only the facts the whole page lacks (often one sentence, or a proposal on the issue); a summary of later sections is closed as redundant even after every review passed.
- slang-rhi maintainer takeovers show preferences: explicit ownership over a double-duty field; existing Vulkan GPU tests over a GPU-free internal-function test. A reviewer's "out of scope" is not the maintainer agreeing.
- Byte-exact PR-body edits: regenerate from `gh api …/pulls/N` JSON `.body`, not `--jq .body` (trailing newline).
- A producer-side fix breaks the coupled emit-PR's test and comments: rebuild and run the coupled tests after a "clean" merge.

## Overview

How a bot coworker coordinates on a live PR when a maintainer is hands-on (editing the branch, self-fixing, taking the design over, diverging from a co-maintainer) and when sibling bot sessions share its GitHub identity.

## Re-derive Maintainer Scope Directives from the Primary Comment

A paraphrased maintainer instruction is the costliest relay error because it looks authoritative downstream. On slangpy#886 the maintainer wrote *"…add the slangpy module searching path by default. **And this should also fix the #1177.**"* The webhook `body` omitted the last clause; the relay then ADDED a narrowing the maintainer never stated ("keep #886 scoped; don't fold #1177 in"), inferred from an earlier bot reply, and posted it publicly. The sessions-only PR #1182 (approved, CI-green) closed unmerged; a parallel session's #1183 fixing both merged. The tier that hands scope to an implementer re-derives it from the live comment (`gh api repos/O/R/issues/comments/<id> --jq .body`) — payloads truncate trailing clauses; relays every "should also fix #N" clause verbatim; surfaces a narrowing suggested by prior context as a question; and treats cross-issue linkage as a collision signal, surfacing #N's ownership before dispatch ([Re-derive maintainer scope directives from the primary GitHub comment](../learnings/1790193478269-re-derive-maintainer-scope-directives-from-the-pri.md)).

## Only the Maintainer Can Waive a Maintainer Requirement

An unimplemented maintainer requirement stays a merge blocker until the maintainer, on record, defers it. A "Partial (minor)" audit label, a "known partials" list in the PR body, an orchestrator scope call and a reviewer approval are not deferrals. On slang-rhi#881 jhelferty-nv's spec had two unimplemented items (R4/R5); the orchestrator scoped them out, one reviewer session took that as a deferral and returned APPROVE_WITH_NITS while a parallel session held REQUEST_CHANGES, and the fixer caught the conflict and asked the maintainer. Grade each requirement met or missed — "partial" measures how much is missing, not severity — and name what resumes the PR: "REQUEST_CHANGES solely on R4/R5, pending maintainer deferral; flips to APPROVE_WITH_NITS on this head with no code change if deferred." After an outage, check what verdicts your other sessions already sent ([a spec requirement left unimplemented is a merge blocker](../learnings/1790758323478-a-spec-requirement-left-unimplemented-is-a-merge-b.md), [an orchestrator's scope call does not waive a maintainer's spec requirement](../learnings/1790758936765-an-orchestrator-s-scope-call-does-not-waive-a-main.md)).

**What counts as maintainer direction.** Only a human maintainer's review or comment giving design direction, verified live with `gh api .../pulls/<n>/reviews`, `.../pulls/<n>/comments` and `.../issues/<n>/comments`. On #13864 the reviewer adopted the fixer's `Maintainer direction:` field, which named the issue reporter (tdavidovicNV, `MEMBER`) and called the issue's proposed tests "maintainer requirements"; the PR had no human reviews and the reporter was the only human on the issue, so there was no maintainer direction. A reporter's proposal and a triage memo are "issue requirements", judged on merit; "missed maintainer requirement → REQUEST_CHANGES regardless" is for real direction. Misuse lands in public text and inflates the verdict ([a reporter's issue-body proposal is not maintainer direction](../learnings/1792678793845-reporter-s-issue-body-proposal-is-not-maintainer-d.md)).

**The live check is a check at a moment**, and a review takes 60–100 min. On #13975 the reviewer recorded "Maintainer direction: none" at ~17:15Z; at 17:38Z jhelferty-nv commented "Per @tangent-vector, we should understand what the long term language design is for this first", parking the PR on a design gate, yet the ~18:00Z verdict still said "none". Re-run `gh issue view <n> --json comments` and `gh pr view <n> --json comments,reviews` right before sending the `[Review Verdict]`, and report any new human MEMBER comment with its timestamp ([re-check maintainer direction right before sending a verdict](../learnings/1793210524900-re-check-maintainer-direction-right-before-sending.md)).

**For the implementer**, the draft follows the maintainer's literal requirement; a coworker-introduced invariant is design input. On slang#13300 jkwak-work wrote: "When it is set to "202c", we will follow the new behavior of DXC that rounds up the size to its alignment." The fixer kept ByteAddressBuffer `Load<T>`/`Store<T>` on natural layout under 202c to stay consistent with `sizeof` — a bot-only invariant; a real DXC run showed DXC *does* round BAB, and codex OUTPUT_REVIEW refused the PR body. Shrink each exception to what is technically forced (here only `sizeof`/`alignof`) and pose it as an open question with a failure example ([default the draft to the maintainer's literal requirement](../learnings/1790759674818-when-a-coworker-introduced-technical-invariant-con.md)). The codex-critique mechanics (R<n> requirement quotes graded at OUTPUT_REVIEW) are in [Critique Gate and Decision Recording](../concepts/review-critique-gate-and-recording.md).

## A Hands-On Maintainer May Edit Your Branch; Don't Race a Self-Fixer

On slang#13227 a maintainer pushed commits onto the bot's branch and left inline comments in rapid batches. Re-fetch the PR head before committing or replying: if a maintainer commit superseded an in-flight edit, fast-forward, `git restore` the redundant edits, verify nothing was lost with `git merge-base --is-ancestor <mine> FETCH_HEAD`, and don't claim fixes they made. Many maintainer comments are resolution notes ("Implemented in <sha>"), not asks — reply on GitHub only to genuine questions. Verify "X is/isn't a producer" claims against the lowering path: `__spirvTraceRayHitObjectEXT` looked like a non-producer of a `[__vulkanRayPayload]` global, but its stdlib wrapper declares one; match by decoration/role ([Hands-on maintainer may concurrently edit your PR](../learnings/1790197469708-hands-on-maintainer-may-concurrently-edit-your-pr-.md)).

Twice on the same PR the maintainer left a batch of "rewrite this comment" / "document each flag" comments, then resolved them minutes later with a commit cited in each thread; up-front subagent rewrites were wasted budget and an edit collision. Post ONE holding ack, then pause before expensive work. Inspect their side READ-ONLY (`git fetch`, `git show`, `git diff A..B`); `checkout`/`merge`/`reset` corrupt a subagent reading the same worktree. Review comments don't move HEAD — the fix-commit does; a comment's `commit_id` shows its pinned head. If they self-resolved everything, kill the moot subagent, sync, and post ONE standing-down comment ("addressed in <sha>, standing down so we don't collide") — not N "thanks" replies ([don't race a batch of "@bot rewrite this" comments](../learnings/1790226898754-maintainer-who-reviews-and-self-fixes-don-t-race-a.md)).

## Maintainer PRs That Supersede a Bot Draft

**A refactor on your branch plus their own PR is a supersede in progress.** Our draft for slang#13106 (#13227, empty ray-tracing payloads) was closed un-merged by kaizhangNV; their #13256 merged hours later, after they had pushed a "centralize payload legalization" refactor onto our branch. #13256 legalizes empty payloads **before type erasure**, so it needs none of our `slang-ir-inline.{h,cpp}` changes; it left one generated expectation stale (fixed by our #13312). Stand down on ours and post the carry-forward on theirs (missing tests, moved expectations); when a pass needs a new inliner/DCE hook to see its input, ask whether it sits too late in the pipeline ([slang#13106 superseded by #13256](../learnings/1790684548885-postmortem-shader-slang-slang-13106-superseded-by-.md)).

**A maintainer PR on the same issue outraces an operator-held draft.** On slang#13249 (`-g` stopped `-loop-inversion` from inverting a simple loop), our #13255 opened two minutes after pdeayton-nv's #13254, was approved within a day, then sat five days awaiting an operator go-ahead while #13254 merged. Theirs was also better: ours let `isSmallBlock` and the trivial-branch match skip every zero-use debug inst — a latent bug, since a `DebugValue` has no result users, so a break block holding `debugState = 7` would be erased as "trivial". #13254 skips only DebugLine/DebugScope/DebugNoScope, keeps DebugVar/DebugValue, and pins the negative case in `tests/ir/loop-inversion-debug-value.slang` (SPIR-V `-g2`/`-g3`: DebugValue survives, loop NOT inverted). Flag a same-issue maintainer PR to the operator immediately; split debug insts by role; test a `-g` parity fix with a debug-observable update on the erased path ([slang#13249 superseded by #13254](../learnings/1790814920619-postmortem-shader-slang-slang-13249-superseded-by-.md)).

**The slow version: a long-assigned maintainer writes their own fix.** On slang#11616 (a `[ForceInline]` return emitted `DebugNoScope`, leaving caller locals unscoped) our draft #11617 sat for months, was reassigned to pdeayton-nv, and was closed after their #13175 merged. #13175 keeps `DebugNoScope` a single-purpose zero-operand inst never emitted on inline return (ours gave it an optional restore-scope operand — one opcode, two meanings), bumps the supported IR module version range (31..31) for the changed layout (ours broke serialized modules), and updates the LLVM emit path. An IR operand-layout change bumps the version range in the same PR and tests separately compiled modules; extend the inst that represents the concept rather than widening another opcode; audit SPIR-V **and** LLVM emitters on a debug-info change; ask early when a draft sits ~4+ weeks assigned to a maintainer without review ([slang#11616 superseded by #13175](../learnings/1791421008032-postmortem-shader-slang-slang-11616-superseded-by-.md)).

**Closing our own superseded draft needs no operator go-ahead.** On slang#13179 (slangd in Zed did not resolve `#include` targets unless the file was open) our #13182 shared the `rootUri`/`rootPath` fallback of jkiviluoto-nv's merged #13192 but missed the per-root search-path overwrite and had no multi-root tests; it then sat 27 days "HELD-OPERATOR". Closing our own superseded bot draft is supervise-issues Step 7 — the operator gate protects human-owned artifacts. Post a short comment naming the superseding PR, what it did, and any saved `wip/` branch, then `gh pr close`; delete no branches unless asked. The technical lesson is on the slangd page ([slang#13179 superseded by #13192](../learnings/1792461389590-postmortem-shader-slang-slang-13179-superseded-by-.md), [closing our own superseded draft PR is not operator-gated](../learnings/1792461290103-closing-our-own-superseded-draft-pr-is-not-operato.md)).

## Two-Maintainer Design Divergence: Provide Evidence, Ask Them to Align

When one maintainer steered a coworker PR's design and another files REQUEST_CHANGES against it, the coworker must not pick a side, redesign unilaterally, or apply the objector's literal diff. It provides evidence and asks both to align; the orchestrator gates any redesign on (1) both maintainers explicitly agreeing on the new mechanism AND (2) the alternative confirmed at source or empirically to satisfy the original hard constraint. On slang#13070 / #13086 jkwak-work objected to an interface member pdeayton-nv had steered. The fixer verified at source (`IOpaqueDescriptor` is `[sealed][builtin]`), tested a `.slang-module` round-trip, and posted a COMMENT-state reply (never a competing APPROVE/REQUEST_CHANGES) tagging both: "same intent, here are the constraints any alternative must satisfy." pdeayton-nv then proposed jkwak's ask (a type-query intrinsic); with the fold confirmed at source and via a fired `static_assert` + DCE, the redesign was authorized and merged. On a non-`@bot` multi-maintainer thread the orchestrator holds the post for calibration, authorizes a reply that asks rather than asserts, requires a redesign plan first, and never lets the coworker counter a maintainer's verdict ([Two-maintainer design divergence on a PR](../learnings/1790220265420-two-maintainer-design-divergence-on-a-pr-provide-e.md)).

## Re-check the Newest Issue Comment Immediately Before Posting

Run the edit-if-last-poster-is-self / anti-dup check against a live re-read right before posting, not the start-of-turn snapshot. On slang#13247 the issue had 0 comments at triage start; ~10 min in, a peer `nv-slang-bot` session posted the disposition, and posting the full triage produced a same-identity double-post on a maintainer-watched issue. Run `gh api repos/<r>/issues/<n>/comments --jq '.[-1].user.login'`; if it is `nv-slang-bot[bot]`, PATCH in place or post only a delta. An auto-filed tracking issue can read stale; check the referenced PR's current head before triaging it as open ([a peer bot session shares your GitHub identity](../learnings/1790198726943-re-check-the-newest-issue-comment-immediately-befo.md)).

## Leave Maintainer Comments Byte-for-Byte; Your Push Dismisses Their Approval

**Never reword a comment you did not write in this PR, not even a typo.** On slang#13406 the bot changed tangent-vector's `ParamPassingMode` ref-mode doc comment from "without also using the `readonly` or `writeonly` modifiers" to "without also using `const`". He replied: "Why did you break the existing comment that an intelligent human (me) wrote? … Please revert your incorrect change." The comment recorded design intent the code does not (`const` on `__ref` is only a legacy alias for `readonly`). Document alongside it in their vocabulary (`readonly ref`), ask in a review reply if your change makes it wrong, and before committing run `git diff origin/master...HEAD | grep -E '^-\s*//'` and justify or revert every hit ([never reword a maintainer's existing source comment](../learnings/1790967868088-never-reword-a-maintainer-s-existing-source-commen.md); [never reword a maintainer's code comment; a push dismisses their approval](../learnings/1790967953965-never-reword-a-maintainer-s-existing-code-comment-.md)).

**A bot push after a human approval silently dismisses it.** shader-slang/slang dismisses stale reviews: the review shows `DISMISSED`, the timeline gains `review_dismissed` with `dismissal_commit_id`, and `reviewDecision` goes empty — for fix and conflict-resolution pushes alike. On #13406 tangent-vector's approval was dismissed 25 minutes later by the fixer's push, yet the fixer still reported him as approving. On #13312 jkwak-work's approval was dropped by a conflict-resolution push, leaving a sole requested reviewer who reviews nothing. On #13815 the triager's report and the Orchestrator's dashboard relay both said "APPROVED / MERGEABLE" two minutes after a merge-master push had dismissed the approval; bot fixers cannot request re-review, so the next step after a dismissal is a human. Before reporting approval state, check `gh pr view N --json reviewDecision` at the current head or `gh api repos/<o>/<r>/issues/<n>/timeline --paginate --jq '.[] | select(.event=="review_dismissed")'`; flag "re-approval needed" after any bot push that follows an approval; never recommend "close as superseded" from a stale read; batch review fixes into one push ([check reviewDecision before saying APPROVED](../learnings/1793851667014-a-push-after-approval-dismisses-it-on-shader-slang.md); [a conflict-resolution push silently dismisses a human approval](../learnings/1790843181467-a-bot-conflict-resolution-push-silently-dismisses-.md)). Riders from #13406: build the requirement list from issue comments AND `pulls/<n>/comments` (an issue-only read missed all 8 inline comments) and re-fetch after any head move; build all default targets (a `slangc`/`slang-test`-only build skipped the standard modules: 60 false failures) ([a pushed commit dismisses an APPROVED review — check the timeline](../learnings/1790969117654-slang-pr-review-a-pushed-commit-silently-dismisses.md)).

## Byte-Exact PR-Body Metadata Edits

To change one line in a PR/issue body while keeping the maintainer's text verbatim (e.g. adding `Fixes #N` beside `Fixes #M`), regenerate from the live body and do a targeted replace; never hand-edit a saved copy. `--jq .body` appends a trailing newline, so the edit is no longer "exactly one line added." Recipe: `body = json.loads(subprocess.check_output(['gh','api','repos/O/R/pulls/N']))['body']`; `body.replace('Fixes #M.', 'Fixes #M.\nFixes #N.', 1)`; write with no extra trailing newline; confirm with a unified diff; `gh pr edit N --body-file`. A closing keyword is body metadata, so it is safe on a PR whose commits a maintainer owns ([use gh api JSON .body, not --jq .body](../learnings/1790199138458-byte-exact-pr-body-metadata-edits-use-gh-api-json-.md)).

## A Producer Fix Breaks the Coupled Emit-PR's Test and Comments

When a fix is split between a producer PR (autodiff `copyDebugInfo`) and an emitter PR (SPIR-V `DebugFunctionDefinition` dedup), the emit PR's test often uses the producer's buggy output as its vehicle, so it FAILS once the producer lands — with no textual conflict. On slang#13237 the test asserted that `f`'s DebugFunction, shared by `s_apply_f`/`s_bwdProp_f`, carries exactly one `DebugFunctionDefinition`; slang#13238 stopped the sharing, so `OpString "f"` disappeared. After merging master, rebuild and run the coupled area's tests regardless of a clean merge; rewrite the test to the new correct behaviour ("tests are contract — update, don't silence") and say in the PR body if the fix removes the only scenario exercising the sibling's logic. The producer fix also falsified a comment in the merged sibling ("reverse-mode autodiff can make several OpFunctions share one IRDebugFunction"), so sweep coupled files for stale comments ([two review-round gotchas](../learnings/1790222348386-two-review-round-gotchas-filecheck-check-tokens-in.md)). Guard debug-metadata invariants with `SLANG_RELEASE_ASSERT`, not `SLANG_ASSERT`. Before `rm`-ing a file, confirm you created it (`git log --follow -- <file>` / `git ls-files <file>`) — a codex reviewer that compiles existing tests did not create them — and never `git add -A` a `PR_BODY.md` scratch file ([fixing a producer breaks the coupled emit-PR's test](../learnings/1790216980075-fixing-a-producer-breaks-the-coupled-emit-pr-s-tes.md)).

## Maintainers Trim Bug-History Narration from Regression-Test Headers

On slang#13269 skiminki-nv approved the bot's fix only after pushing a commit that cut the `gh-13260.slang` header from a 9-line paragraph to a 3-line statement of the rule. A test header states the guarded invariant in a sentence or two; the "previously X, causing Y" story goes in the commit message and PR body ([maintainers trim bug-history narration from test headers](../learnings/1790687863709-slang-maintainers-trim-bug-history-narration-from-.md)).

## A Docs PR From a Question Issue Adds Only What the Page Lacks

jkwak-work closed slang#12938 unmerged: "This content seems redundant to the information the doc already has." Written after user question #12937, it added a 5-line intro on `DescriptorHandle<T>`'s `uint2` `.x`/`.y` meaning, mostly summarising subsections further down the same page; the one new fact was that `.y` is unused for a plain resource. It had passed codex and peer review, which check accuracy, not whether a maintainer wants the change. Compare the draft with the WHOLE page and list only new facts; one new fact gets one sentence where it belongs, or a proposal on the issue first. When a brief says "if the guide already covers it, don't manufacture a change", no-PR is a real outcome ([docs PRs that restate the page get closed as redundant](../learnings/1793826181291-slang-docs-prs-that-restate-content-already-on-the.md)).

## What slang-rhi Maintainer Takeovers Show They Prefer

skallweitNV corrected the shape of bot fixes rather than their direction. On slang-rhi#860 the bot routed `VkBufferView` create/destroy through `device->m_api` and kept `VKBufferHandleRAII::m_api` as the implicit "this wrapper owns the buffer" flag; the maintainer closed bot PR #868 and landed #945, keeping the routing but adding explicit `m_ownsBuffer`/`m_ownsMemory` and fixing the uninitialized `m_memory` the bot had scoped out ([explicit ownership over a double-duty field](../learnings/1793091793971-slang-rhi-maintainer-prefers-explicit-ownership-ov.md)). On slang-rhi#866 they took the PR over, squashed it, deleted the bot's GPU-free `tests/test-vk-utils.cpp`, and validated with the existing Release Vulkan buffer-barrier, compute and texture tests ([run the existing Vulkan GPU tests](../learnings/1793111769425-slang-rhi-run-the-existing-vulkan-gpu-tests-mainta.md)). If a minimal fix works around a field that means two things, name the conflation and offer the explicit refactor, since the maintainer may want the root fixed even when a reviewer accepted it as out of scope. For a small backend mapping fix, run the relevant existing `slang-rhi-tests` GPU cases on the container's GPU. Detail: [slang-rhi backend runtime internals](slang-rhi-backend-runtime.md), [Slang & slang-rhi test harness](slang-a-test-harness.md).
