# Working Live PRs Alongside Maintainers and Sibling Bots

## TL;DR

- Re-derive a maintainer's scope directive from the LIVE primary comment — a dropped "also fix #N" clause or an inferred narrowing inverts scope and wastes a green PR.
- Only the maintainer can waive a maintainer's requirement: grade met/missed; "partial", PR-body "known partials", orchestrator scope-outs are not deferrals. Direction = a human maintainer's review/comment verified live; a reporter's proposal (even MEMBER) is an "issue requirement".
- Re-read maintainer direction right before the verdict goes out; report new human MEMBER comments with timestamps (#13975).
- A draft follows the literal requirement; a bot-introduced invariant is design input; an exception shrinks to what is technically forced, posed as a question.
- A hands-on maintainer may push onto your branch; comment batches are often resolution notes — re-fetch HEAD before committing or replying; don't race a self-fixer (one holding ack, read-only inspection, ONE stand-down).
- A maintainer refactor on your branch + their own PR = supersede: stand down on ours, carry forward on theirs. A maintainer PR on the same issue → flag to the operator at once (an operator-held draft loses); weeks-unreviewed after assignment: ask early. Closing our own superseded draft (pointer comment) is not operator-gated.
- Debug insts: skip only DebugLine/DebugScope/DebugNoScope (DebugVar/DebugValue carry state); an IR operand-layout change bumps the module version range.
- Two maintainers diverge on a design → provide evidence, ask them to align, never pick a side; keep the work local until both agree.
- Run the anti-dup check against a LIVE re-read immediately before posting — a peer bot session shares your GitHub identity.
- Never reword a maintainer's existing comment, not even a typo; grep the diff for removed `//` lines.
- Your push dismisses a maintainer's APPROVED review (fix and conflict-resolution pushes alike) — check `reviewDecision`/`review_dismissed` at head before reporting "approved"; batch fixes into one push.
- Regression-test headers state the invariant in a sentence or two; bug history goes in the commit message and PR body.
- A docs PR adds only facts the page lacks; a summary of later sections is closed as redundant even after reviews pass.
- A bare "driver bug" comment is a blame hypothesis, not a ruling — check the label-tell (#14415 vs #14493), assignee/close actions, and mechanism evidence; keep the chain alive but watch-only where the fix helps either way.
- slang-rhi takeovers prefer explicit ownership over double-duty fields and existing Vulkan GPU tests over new GPU-free tests.
- Byte-exact PR-body edits use `gh api` JSON `.body`, not `--jq .body`; a producer-side fix breaks the coupled emit-PR's test — rebuild and run coupled tests after a "clean" merge.

## Overview

How a bot coworker coordinates on a live PR when a maintainer is hands-on (editing the branch, self-fixing, taking the design over, diverging from a co-maintainer) and when sibling bot sessions share its GitHub identity.

## Re-derive Scope Directives from the Primary Comment

A paraphrased maintainer instruction is the costliest relay error because it looks authoritative downstream. On slangpy#886 the webhook `body` dropped the maintainer's trailing clause *"**And this should also fix the #1177.**"*; the relay then ADDED a narrowing never stated ("keep #886 scoped"), inferred from an earlier bot reply, and posted it publicly — the sessions-only PR #1182 (approved, CI-green) closed unmerged while a parallel #1183 fixing both merged. The tier that hands scope to an implementer re-derives it from the live comment (`gh api repos/O/R/issues/comments/<id> --jq .body`): payloads truncate trailing clauses; relay every "should also fix #N" verbatim; surface a context-suggested narrowing as a question; treat cross-issue linkage as a collision signal, surfacing #N's ownership before dispatch ([Re-derive maintainer scope directives from the primary GitHub comment](../learnings/1790193478269-re-derive-maintainer-scope-directives-from-the-pri.md)).

## Only the Maintainer Can Waive a Maintainer Requirement

An unimplemented maintainer requirement stays a merge blocker until the maintainer, on record, defers it. A "Partial (minor)" label, a PR-body "known partials" list, an orchestrator scope call and a reviewer approval are not deferrals. On slang-rhi#881 jhelferty-nv's spec had two unimplemented items (R4/R5); the orchestrator scoped them out, one session returned APPROVE_WITH_NITS while a parallel held REQUEST_CHANGES — the fixer caught the conflict and asked the maintainer. Grade each requirement met or missed — "partial" measures how much is missing, not severity — and name what resumes the PR ("REQUEST_CHANGES solely on R4/R5, pending maintainer deferral"). After an outage, check what verdicts sibling sessions already sent ([a spec requirement left unimplemented is a merge blocker](../learnings/1790758323478-a-spec-requirement-left-unimplemented-is-a-merge-b.md), [an orchestrator's scope call does not waive a maintainer's spec requirement](../learnings/1790758936765-an-orchestrator-s-scope-call-does-not-waive-a-main.md)).

**What counts as maintainer direction.** Only a human maintainer's review or comment giving design direction, verified live with `gh api .../pulls/<n>/reviews`, `.../pulls/<n>/comments` and `.../issues/<n>/comments`. On #13864 the reviewer adopted a `Maintainer direction:` field naming the issue reporter (tdavidovicNV, `MEMBER`); the PR had no human reviews, so there was no maintainer direction. A reporter's proposal and a triage memo are "issue requirements", judged on merit; "missed maintainer requirement → REQUEST_CHANGES regardless" is for real direction — misuse lands in public text and inflates the verdict ([a reporter's issue-body proposal is not maintainer direction](../learnings/1792678793845-reporter-s-issue-body-proposal-is-not-maintainer-d.md)). Expect the codex advisory to disagree every time: codex treats a MEMBER-authored issue body as binding, this policy an "issue requirement" — check `author_association`, follow the policy, and when both readings agree the tracked items are verified-met, say so and move on (#14520 r3) ([critique gate keyword-matches [Fix Report] in verdicts; MEMBER issue-body policy tension](../learnings/1794935349519-critique-gate-keyword-matches-fix-report-in-verdic.md)).

**The live check is a check at a moment**, and a review takes 60–100 min. On #13975 the reviewer recorded "Maintainer direction: none" at ~17:15Z; at 17:38Z jhelferty-nv commented "we should understand what the long term language design is for this first", parking the PR on a design gate, yet the ~18:00Z verdict still said "none". Re-run `gh issue view <n> --json comments` and `gh pr view <n> --json comments,reviews` right before sending the `[Review Verdict]`; report any new human MEMBER comment with its timestamp ([re-check maintainer direction right before sending a verdict](../learnings/1793210524900-re-check-maintainer-direction-right-before-sending.md)).

**For the implementer**, the draft follows the maintainer's literal requirement; a coworker-introduced invariant is design input. On slang#13300 jkwak-work's requirement (round up to alignment under `202c`) was met with a bot-only invariant keeping ByteAddressBuffer `Load<T>`/`Store<T>` on natural layout for `sizeof` consistency; a real DXC run showed DXC *does* round BAB, and codex OUTPUT_REVIEW refused the PR body. Shrink each exception to what is technically forced (here only `sizeof`/`alignof`), posed as an open question with a failure example ([default the draft to the maintainer's literal requirement](../learnings/1790759674818-when-a-coworker-introduced-technical-invariant-con.md)). The codex-critique mechanics (R<n> requirement quotes graded at OUTPUT_REVIEW) are in [Critique Gate and Decision Recording](../concepts/review-critique-gate-and-recording.md).

## A Bare "Driver Bug" Comment Is Not a Ruling — the Label Is the Tell

On slang#14493 jkwak-work commented "we think that it is a driver side bug" on an issue where our chain had a bisected, OpPhi-verified compiler-side fix in review; the chain did not stand down. The tell: in #14415 his real driver-bug rulings always added the `Vendor Driver Bug` label within minutes; here there was no label, assignee change, or close request — a blame disagreement, most likely conflation with #14415. Events confirmed the read: kaizhangNV invested a redesign on our PR branch, jkwak-work APPROVED the compiler fix, and it merged (PR #14502). Rules: a bare "driver bug / known problem" comment is blame data, not a classification — check the maintainer's classification tells, assignee/close-request changes, and whether it conflicts with verified mechanism evidence (an OpPhi/liveness delta in spirv-dis text is driver-independent). Where the compiler-side fix helps under either blame reading, keep the chain alive but watch-only; run the assessment through the issue-side owner (triager) with the comment verbatim; don't block on operator input for non-blocking calls ([maintainer driver-bug comments: check the label-tell](../learnings/1794989231182-maintainer-driver-bug-comments-check-the-label-tel.md), [jkwak-work: the Vendor Driver Bug label is the tell](../learnings/1794989264757-jkwak-work-driver-bug-comments-the-vendor-driver-b.md)).

## A Hands-On Maintainer May Edit Your Branch; Don't Race a Self-Fixer

On slang#13227 a maintainer pushed commits onto the bot's branch and left inline comments in rapid batches. Re-fetch the PR head before committing or replying: if a maintainer commit superseded an in-flight edit, fast-forward, `git restore` the redundant edits, verify with `git merge-base --is-ancestor <mine> FETCH_HEAD`, and don't claim fixes they made. Many maintainer comments are resolution notes ("Implemented in <sha>"), not asks — reply on GitHub only to genuine questions. Verify "X is/isn't a producer" claims against the lowering path: `__spirvTraceRayHitObjectEXT` looked like a non-producer of a `[__vulkanRayPayload]` global, but its stdlib wrapper declares one; match by decoration/role ([Hands-on maintainer may concurrently edit your PR](../learnings/1790197469708-hands-on-maintainer-may-concurrently-edit-your-pr-.md)).

Twice on the same PR the maintainer left a batch of "rewrite this comment" / "document each flag" comments, then resolved them minutes later with a commit cited in each thread; up-front subagent rewrites were wasted budget and an edit collision. Post ONE holding ack, then pause before expensive work. Inspect their side READ-ONLY (`git fetch`, `git show`, `git diff A..B`); `checkout`/`merge`/`reset` corrupt a subagent reading the same worktree. Review comments don't move HEAD — the fix-commit does (`commit_id` pins the head). If they self-resolved everything, kill the moot subagent, sync, and post ONE standing-down comment ("addressed in <sha>, standing down") — not N "thanks" replies ([don't race a batch of "@bot rewrite this" comments](../learnings/1790226898754-maintainer-who-reviews-and-self-fixes-don-t-race-a.md)).

## Maintainer PRs That Supersede a Bot Draft

**A refactor on your branch plus their own PR is a supersede in progress.** Our draft for slang#13106 (#13227, empty ray-tracing payloads) was closed un-merged by kaizhangNV; their #13256 merged hours later, after they had pushed a "centralize payload legalization" refactor onto our branch. #13256 legalizes empty payloads **before type erasure**, so it needs none of our `slang-ir-inline.{h,cpp}` changes; it left one generated expectation stale (fixed by our #13312). Stand down on ours and post the carry-forward on theirs (missing tests, moved expectations); when a pass needs a new inliner/DCE hook to see its input, ask whether it sits too late in the pipeline ([slang#13106 superseded by #13256](../learnings/1790684548885-postmortem-shader-slang-slang-13106-superseded-by-.md)).

**A maintainer PR on the same issue outraces an operator-held draft.** On slang#13249 (`-g` stopped `-loop-inversion` from inverting a simple loop) our #13255 opened two minutes after pdeayton-nv's #13254, was approved within a day, then sat five days awaiting an operator go-ahead while #13254 merged. Theirs was also better: ours let `isSmallBlock` and the trivial-branch match skip every zero-use debug inst — a latent bug (a `DebugValue` has no result users, so a break block holding `debugState = 7` would be erased as "trivial"). #13254 skips only DebugLine/DebugScope/DebugNoScope, keeps DebugVar/DebugValue, and pins the negative case in `tests/ir/loop-inversion-debug-value.slang` (SPIR-V `-g2`/`-g3`: DebugValue survives, loop NOT inverted). Flag a same-issue maintainer PR to the operator immediately; split debug insts by role; test a `-g` parity fix with a debug-observable update on the erased path ([slang#13249 superseded by #13254](../learnings/1790814920619-postmortem-shader-slang-slang-13249-superseded-by-.md)).

**A concurrent maintainer PR with the same approach loses us the race — land the pinning test or stand off.** On slang#14557 (NVRTC did not enable OptiX for a compute shader using `optix_coopvec`) our draft #14563 set a `RequiresOptix` flag at two sites plus a bespoke `isOptixCoopVecEnabled` predicate (170 lines/8 files, no regression test); jkwak-work's #14560 opened 43 min earlier and merged within hours; ours closed as the duplicate. Their fix is the transferable shape: ONE condition at the single point where downstream compile options are assembled (`pipelineType == RayTracing || getTargetCaps().implies(CapabilityAtom::optix_coopvec)` → `Flag::RequiresOptix`), keyed on the canonical capability-atom implication, plus a modified `tests/cuda/optix-coopvec.slang` pinning the path end-to-end. For "downstream compile needs header-set X when target has capability Y" bugs the fix belongs at the options-assembly point, not replicated per stage; always ship the target-specific regression test in the same PR — a draft without a pinning test loses to a smaller tested patch. When a human maintainer opens a same-approach PR on an issue we hold a draft on, land ours fast with the missing test or propose ours as review input ([slang#14557 superseded by #14560](../learnings/1794982445190-postmortem-shader-slang-slang-14557-superseded-by-.md)).

**The slow version: a long-assigned maintainer writes their own fix.** On slang#11616 (a `[ForceInline]` return emitted `DebugNoScope`, leaving caller locals unscoped) our draft #11617 sat for months, was reassigned to pdeayton-nv, and was closed after their #13175 merged. #13175 keeps `DebugNoScope` a single-purpose zero-operand inst never emitted on inline return (ours gave it an optional restore-scope operand — one opcode, two meanings), bumps the supported IR module version range (31..31) for the changed layout (ours broke serialized modules), and updates the LLVM emit path. An IR operand-layout change bumps the version range in the same PR and tests separately compiled modules; extend the inst that represents the concept rather than widening another opcode; audit SPIR-V **and** LLVM emitters on a debug-info change; ask early when a draft sits ~4+ weeks assigned to a maintainer without review ([slang#11616 superseded by #13175](../learnings/1791421008032-postmortem-shader-slang-slang-11616-superseded-by-.md)).

**Closing our own superseded draft needs no operator go-ahead.** On slang#13179 (slangd in Zed did not resolve `#include` targets unless the file was open) our #13182 shared the `rootUri`/`rootPath` fallback of jkiviluoto-nv's merged #13192 but missed the per-root search-path overwrite and had no multi-root tests; it sat 27 days "HELD-OPERATOR". Closing our own superseded bot draft is supervise-issues Step 7 — the operator gate protects human-owned artifacts. Post a short comment naming the superseding PR, what it did, and any saved `wip/` branch, then `gh pr close`; delete no branches unless asked (technical lesson on the slangd page) ([slang#13179 superseded by #13192](../learnings/1792461389590-postmortem-shader-slang-slang-13179-superseded-by-.md), [closing our own superseded draft PR is not operator-gated](../learnings/1792461290103-closing-our-own-superseded-draft-pr-is-not-operato.md)).

## Two-Maintainer Design Divergence: Evidence, Ask Them to Align

When one maintainer steers a coworker PR's design and another files REQUEST_CHANGES against it, the coworker must not pick a side, redesign unilaterally, or apply the objector's literal diff: it provides evidence and asks both to align; the orchestrator gates any redesign on (1) both maintainers explicitly agreeing AND (2) the alternative confirmed at source or empirically to satisfy the original hard constraint. On slang#13070/#13086 jkwak-work objected to an interface member pdeayton-nv had steered. The fixer verified at source (`IOpaqueDescriptor` is `[sealed][builtin]`), tested a `.slang-module` round-trip, and posted a COMMENT-state reply (never a competing APPROVE/REQUEST_CHANGES) tagging both: "same intent, here are the constraints any alternative must satisfy." pdeayton-nv then proposed jkwak's ask; with the fold confirmed at source and via a fired `static_assert` + DCE, the redesign was authorized and merged. On a non-`@bot` multi-maintainer thread the orchestrator holds the post for calibration, authorizes a reply that asks rather than asserts, and never lets the coworker counter a maintainer's verdict ([Two-maintainer design divergence on a PR](../learnings/1790220265420-two-maintainer-design-divergence-on-a-pr-provide-e.md)).

The divergence is cheaper to catch before any code exists: when a change redefines language semantics, read the review threads of the linked and sibling PRs too, especially `author_association` MEMBER comments. On #14366 pdeayton-nv (MEMBER) asked on the issue for an explicit `[[vk::location]]` on a struct field to be an absolute Location in every stage; the fixer had implemented and verified that locally when tangent-vector (MEMBER) wrote on sibling PR #14335 that field Locations should *not* be absolute — master's struct-relative behaviour is the intended one. The chain was parked before anything was pushed. If two maintainers' positions differ, or one has not weighed in on a rule the other set, ask both to agree first and keep the work local (branch + patch file) until they do; a draft PR settles nothing — it would be reviewed against the opposite rule the same day [Before building a language-rule change from an issue spec, check sibling PR threads for MEMBER comments that contradict it](../learnings/1793999570748-before-building-a-language-rule-change-from-an-iss.md).

## Re-check the Newest Issue Comment Immediately Before Posting

Run the edit-if-last-poster-is-self / anti-dup check against a live re-read right before posting, not the start-of-turn snapshot. On slang#13247 a peer `nv-slang-bot` session posted the disposition ~10 min into triage on a 0-comment issue — posting the full triage produced a same-identity double-post on a maintainer-watched issue. Run `gh api repos/<r>/issues/<n>/comments --jq '.[-1].user.login'`; if it is `nv-slang-bot[bot]`, PATCH in place or post only a delta. An auto-filed tracking issue can read stale; check the referenced PR's current head before triaging it as open ([a peer bot session shares your GitHub identity](../learnings/1790198726943-re-check-the-newest-issue-comment-immediately-befo.md)).

## Leave Maintainer Comments Byte-for-Byte; Your Push Dismisses Their Approval

**Never reword a comment you did not write in this PR, not even a typo.** On slang#13406 the bot changed tangent-vector's `ParamPassingMode` ref-mode doc comment from "without also using the `readonly` or `writeonly` modifiers" to "without also using `const`". He replied: "Why did you break the existing comment that an intelligent human (me) wrote? … Please revert your incorrect change." The comment recorded design intent the code does not (`const` on `__ref` is only a legacy alias for `readonly`). Document alongside it in their vocabulary (`readonly ref`), ask in a review reply if your change makes it wrong, and before committing run `git diff origin/master...HEAD | grep -E '^-\s*//'` and justify or revert every hit ([never reword a maintainer's existing source comment](../learnings/1790967868088-never-reword-a-maintainer-s-existing-source-commen.md); [never reword a maintainer's code comment; a push dismisses their approval](../learnings/1790967953965-never-reword-a-maintainer-s-existing-code-comment-.md)).

**A bot push after a human approval silently dismisses it.** shader-slang/slang dismisses stale reviews: `DISMISSED`, timeline `review_dismissed` with `dismissal_commit_id`, `reviewDecision` empty — fix and conflict-resolution pushes alike (#13406: fixer's push dismissed tangent-vector's approval 25 min later, still reported as approving; #13312: conflict-resolution push; #13815: two reports said "APPROVED / MERGEABLE" 2 min after a merge-master push). Bot fixers cannot request re-review — after a dismissal the next step is a human. Before reporting approval state, check `gh pr view N --json reviewDecision` at the head or the `review_dismissed` timeline; flag "re-approval needed" after any post-approval bot push; batch fixes into one push ([check reviewDecision before saying APPROVED](../learnings/1793851667014-a-push-after-approval-dismisses-it-on-shader-slang.md); [a conflict-resolution push silently dismisses a human approval](../learnings/1790843181467-a-bot-conflict-resolution-push-silently-dismisses-.md)). Riders from #13406: build the requirement list from issue comments AND `pulls/<n>/comments` (an issue-only read missed all 8 inline comments); build all default targets (`slangc`/`slang-test`-only skipped the standard modules: 60 false failures); re-fetch after any head move ([a pushed commit dismisses an APPROVED review — check the timeline](../learnings/1790969117654-slang-pr-review-a-pushed-commit-silently-dismisses.md)). Even a maintainer-REQUESTED push costs the approval (#14540: jkwak-work's requested conflict-resolution push auto-dismissed his approval) — say so in the confirmation comment. A master merge can MOVE source files (slang-check-decl.cpp → `source/slang/semantic-checking/`), so file:line citations go 404 — re-verify at the merged head; BEHIND does NOT block merging — only DIRTY/CONFLICTING does ([pushing to an approved PR dismisses the approval; master merges can move source files](../learnings/1795140674253-pushing-to-an-approved-pr-dismisses-the-approval-m.md)).

## Byte-Exact PR-Body Metadata Edits

To change one line in a PR/issue body while keeping the maintainer's text verbatim (e.g. adding `Fixes #N` beside `Fixes #M`), regenerate from the live body and do a targeted replace; never hand-edit a saved copy — `--jq .body` appends a trailing newline, so the edit is no longer "exactly one line added." Recipe: `body = json.loads(subprocess.check_output(['gh','api','repos/O/R/pulls/N']))['body']`; `body.replace('Fixes #M.', 'Fixes #M.\nFixes #N.', 1)`; write with no extra trailing newline; confirm with a unified diff; `gh pr edit N --body-file`. A closing keyword is body metadata — safe on a PR whose commits a maintainer owns ([use gh api JSON .body, not --jq .body](../learnings/1790199138458-byte-exact-pr-body-metadata-edits-use-gh-api-json-.md)).

## A Producer Fix Breaks the Coupled Emit-PR's Test and Comments

When a fix is split between a producer PR (autodiff `copyDebugInfo`) and an emitter PR (SPIR-V `DebugFunctionDefinition` dedup), the emit PR's test often uses the producer's buggy output as its vehicle, so it FAILS once the producer lands — with no textual conflict (slang#13237/#13238: the emit test asserted `f`'s shared DebugFunction carries one `DebugFunctionDefinition`; the producer stopped the sharing and `OpString "f"` disappeared). After merging master, rebuild and run the coupled area's tests regardless of a clean merge; rewrite the test to the new correct behaviour ("tests are contract — update, don't silence") and say in the PR body if the fix removes the only scenario exercising the sibling's logic; the producer fix also falsified a comment in the merged sibling — sweep coupled files for stale comments ([two review-round gotchas](../learnings/1790222348386-two-review-round-gotchas-filecheck-check-tokens-in.md)). Guard debug-metadata invariants with `SLANG_RELEASE_ASSERT`, not `SLANG_ASSERT`. Before `rm`-ing a file, confirm you created it (`git log --follow -- <file>`) — a codex reviewer that compiles existing tests did not create them; never `git add -A` a `PR_BODY.md` scratch file ([fixing a producer breaks the coupled emit-PR's test](../learnings/1790216980075-fixing-a-producer-breaks-the-coupled-emit-pr-s-tes.md)).

## Maintainers Trim Bug History from Test Headers

On slang#13269 skiminki-nv approved the bot's fix only after pushing a commit that cut the `gh-13260.slang` header from a 9-line paragraph to a 3-line rule statement. A test header states the guarded invariant in a sentence or two; the "previously X, causing Y" story goes in the commit message and PR body ([maintainers trim bug-history narration from test headers](../learnings/1790687863709-slang-maintainers-trim-bug-history-narration-from-.md)).

## A Docs PR Adds Only What the Page Lacks

jkwak-work closed slang#12938 unmerged: "This content seems redundant to the information the doc already has." Written after user question #12937, it added a 5-line intro on `DescriptorHandle<T>`'s `uint2` `.x`/`.y` meaning, mostly summarising subsections further down the same page; the one new fact was that `.y` is unused for a plain resource. It had passed codex and peer review — which check accuracy, not whether a maintainer wants the change. Compare the draft with the WHOLE page and list only new facts: one new fact gets one sentence where it belongs, or a proposal on the issue first. When a brief says "if the guide already covers it, don't manufacture a change", no-PR is a real outcome ([docs PRs that restate the page get closed as redundant](../learnings/1793826181291-slang-docs-prs-that-restate-content-already-on-the.md)).

## What slang-rhi Maintainer Takeovers Show They Prefer

skallweitNV corrected the shape of bot fixes rather than their direction. On slang-rhi#860 the bot routed `VkBufferView` create/destroy through `device->m_api` and kept `VKBufferHandleRAII::m_api` as the implicit owns-the-buffer flag; the maintainer closed bot PR #868 and landed #945, keeping the routing but adding explicit `m_ownsBuffer`/`m_ownsMemory` and fixing the uninitialized `m_memory` ([explicit ownership over a double-duty field](../learnings/1793091793971-slang-rhi-maintainer-prefers-explicit-ownership-ov.md)). On slang-rhi#866 they took the PR over, squashed it, deleted the bot's GPU-free `tests/test-vk-utils.cpp`, and validated with the existing Release Vulkan buffer-barrier/compute/texture tests ([run the existing Vulkan GPU tests](../learnings/1793111769425-slang-rhi-run-the-existing-vulkan-gpu-tests-mainta.md)). If a minimal fix works around a field that means two things, name the conflation and offer the explicit refactor — the maintainer may want the root fixed even when a reviewer accepted it as out of scope. For a small backend mapping fix, run the relevant existing `slang-rhi-tests` GPU cases on the container's GPU.
