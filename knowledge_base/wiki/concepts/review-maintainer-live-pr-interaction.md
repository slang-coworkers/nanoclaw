# Working Live PRs Alongside Maintainers and Sibling Bots

## TL;DR

- **Re-derive a maintainer's scope directive from the LIVE primary comment, never a paraphrase or the webhook `body`.** A dropped clause ("and this should also fix #N") or an ADDED narrowing you inferred ("keep it scoped, don't fold in #N") inverts scope and wastes a built-reviewed-CI-green PR. One comment fetch is cheap; a wasted fix cycle is not. If you catch yourself writing "keep this scoped to…", confirm that constraint is in the maintainer's own words.
- **Only the maintainer can waive a maintainer's requirement.** Grade every spec item met/missed; "partial", "minor", "known partial in the PR body" and an orchestrator scope-out are not deferrals, so a missed item gates the verdict (REQUEST_CHANGES pending deferral) until the maintainer says follow-up is fine. A draft follows the literal requirement; a bot-introduced invariant is design input, and an exception shrinks to what is technically forced, posed as a question with a failure example.
- **A hands-on maintainer may push commits onto your branch and leave rapid batches of inline comments.** Re-fetch and check the PR head before committing or replying; many maintainer "comments" are resolution notes ("Implemented in <sha>"), not asks — close via an upstream report, only reply on GitHub to genuine questions.
- **Don't race a self-fixing maintainer.** One short holding ack, then PAUSE — inspect their side with READ-ONLY git (`git fetch` + `git show <sha>`), never `checkout`/`merge`/`reset` while a subagent reads the same worktree; if they resolved it themselves, kill the moot subagent, sync, and post ONE standing-down comment.
- **A maintainer who pushes a structural refactor onto the bot's branch and then opens their own PR on the same files is superseding it.** Stand down explicitly on our PR and name the carry-forward on theirs (tests we added that theirs lacks, generated expectations the change moves) instead of iterating our copy until it is closed. If a pass needs a new inliner/DCE hook to see its input, first ask whether it sits too late in the pipeline.
- **When a maintainer opens a PR on the same issue, flag the overlap to the operator immediately** — an operator-held draft racing a human PR loses. A bot draft sitting un-reviewed for weeks after a maintainer is assigned is the slow form of the same signal: ask early whether they want it. Once superseded, close our own bot draft with a pointer comment (not operator-gated). When a pass ignores debug insts, skip only location/scope markers (DebugLine/DebugScope/DebugNoScope); DebugVar/DebugValue carry variable state and are not erasable even at zero uses, so a `-g` parity fix needs a SPIR-V `-g2`/`-g3` negative test.
- **Regression-test headers state the invariant the test guards in a sentence or two**; the "previously the compiler did X, breaking Y on HLSL/SPIR-V" story goes in the commit message and PR body. Maintainers trim bug-history narration from test headers themselves.
- **When two maintainers diverge on a design mechanism, provide evidence and ask them to align — do NOT pick a side or apply the objector's diff.** Gate any coworker redesign on both preconditions: both maintainers explicitly agree, AND the alternative is confirmed (at source / empirically) to satisfy the original hard constraint.
- **Run the anti-dup check immediately before posting, against a LIVE re-read** — a peer bot session (same GitHub identity, different session) can post between your turn's start and its end, so consolidate across sessions, not just against your start-of-turn snapshot.
- **Never reword a maintainer's existing comment, not even a typo.** It records design intent the code does not. Document alongside it in their vocabulary, or ask; grep your diff for removed `//` lines before committing.
- **Your push dismisses a maintainer's APPROVED review** (stale-review dismissal), including conflict-resolution pushes. Check `reviewDecision` / `review_dismissed` at the current head before reporting "approved", and batch fixes into one push.
- **Byte-exact PR-body edits: regenerate from `gh api …/pulls/N` → `json.loads(...)['body']`, not `--jq .body`** (jq appends a spurious trailing newline that breaks a "exactly one line added" diff check).
- **A producer-side fix invalidates the coupled emit-PR's test and any comment that described the bug** — rebuild and run the coupled area's tests after a "clean" merge, and sweep coupled files for now-false comments.

## Overview

How a bot coworker coordinates on a live PR when a maintainer is hands-on (editing the branch, self-fixing, trimming test headers, taking the design over in their own PR, or diverging from a co-maintainer) and when sibling bot sessions share its GitHub identity — plus the mechanics of editing a PR body or reconciling a coupled sibling PR without wasting a cycle or corrupting a maintainer's text.

## Re-derive Maintainer Scope Directives from the Primary Comment

A paraphrased maintainer instruction is the costliest relay error because it looks authoritative downstream. On slangpy#886 the maintainer wrote *"…add the slangpy module searching path by default. **And this should also fix the #1177.**"* The webhook `body` omitted the last clause and was relayed as complete; the relay then ADDED a narrowing the maintainer never stated ("keep #886 scoped to `create_slang_session`; don't fold #1177 in"), inferred from an earlier bot reply calling #1177 "related, not a duplicate", and posted it publicly one comment below the request. The sessions-only PR #1182 (approved, CI-green) closed unmerged; a parallel session's #1183 fixing both merged. Rules: the tier that hands scope to an implementer re-derives it from the live comment (`gh api repos/O/R/issues/comments/<id> --jq .body`), never the webhook payload alone (payloads truncate trailing clauses); relay maintainer comments verbatim, every "should also fix #N" / "while you're at it" clause included; a narrowing suggested by prior context is a question to surface, not an instruction to inject; and cross-issue linkage is a collision signal — surface #N's ownership before dispatching so two bot sessions don't build competing PRs [A paraphrased maintainer directive can invert scope — the relaying tier must re-read the source comment](../learnings/1790193335302-a-paraphrased-maintainer-directive-can-invert-scop.md) [Re-derive maintainer scope directives from the primary GitHub comment — webhook bodies truncate, and never ADD scope you inferred](../learnings/1790193478269-re-derive-maintainer-scope-directives-from-the-pri.md).

## Only the Maintainer Can Waive a Maintainer Requirement

An unimplemented maintainer requirement stays a merge blocker until the maintainer, on record, defers it. A "Partial (minor)" audit label, a "known partials for the maintainer to rule on" list in the PR body, an orchestrator scope call and a reviewer approval are not deferrals. On slang-rhi#881 jhelferty-nv's spec had two unimplemented items (R4/R5). The orchestrator scoped them out; one reviewer session took that as a deferral and returned APPROVE_WITH_NITS while a parallel session held REQUEST_CHANGES; the fixer caught the conflict and asked the maintainer on the PR. Grade each requirement met or missed — "partial" measures how much is missing, not a lower severity — and name what resumes the PR: "REQUEST_CHANGES solely on R4/R5, pending maintainer deferral; flips to APPROVE_WITH_NITS on this head with no code change if deferred." After an outage, check what verdicts your other sessions already sent before issuing a new one ([a spec requirement left unimplemented is a merge blocker until the maintainer defers it](../learnings/1790758323478-a-spec-requirement-left-unimplemented-is-a-merge-b.md), [an orchestrator's scope call does not waive a maintainer's spec requirement](../learnings/1790758936765-an-orchestrator-s-scope-call-does-not-waive-a-main.md)).

For the implementer: the draft follows the maintainer's literal requirement, and a coworker-introduced invariant is design input, not a constraint. On slang#13300 jkwak-work wrote: "When it is set to "202c", we will follow the new behavior of DXC that rounds up the size to its alignment." The fixer kept ByteAddressBuffer `Load<T>`/`Store<T>` on natural layout under 202c to stay consistent with `sizeof` — a bot-only invariant. A real DXC run showed DXC *does* round BAB, and codex OUTPUT_REVIEW refused the PR body as only partly meeting the requirement. Shrink each exception to what is technically forced (here only `sizeof`/`alignof`) and pose it as an open question with a concrete failure example ([when a coworker-introduced invariant conflicts with a maintainer's literal requirement, default the draft to the requirement](../learnings/1790759674818-when-a-coworker-introduced-technical-invariant-con.md)). The codex-critique mechanics that enforce this (R<n> requirement quotes graded at OUTPUT_REVIEW) are in [Critique Gate and Decision Recording](../concepts/review-critique-gate-and-recording.md).

## A Hands-On Maintainer May Edit Your Branch — Re-check HEAD; Comments Are Often Notes

On slang#13227 a maintainer pushed commits onto the bot's branch and left inline comments in rapid batches. Re-fetch and check the PR head before committing or replying: if a maintainer commit superseded an in-flight edit (both rewriting the same doc comment), fast-forward, `git restore` the redundant edits, verify nothing was lost with `git merge-base --is-ancestor <mine> FETCH_HEAD`, and don't claim fixes they made. Many maintainer comments are resolution notes ("Implemented in <sha>"), not asks — close via an upstream report and reply on GitHub only to genuine questions. Verify "X is/isn't a producer" claims against the lowering path, not the surface symbol: `__spirvTraceRayHitObjectEXT` looked like a non-producer of a `[__vulkanRayPayload]` global, but its stdlib wrapper declares `[__vulkanRayPayload] static T p`, so match by decoration/role and trace wrapper→intrinsic [Hands-on maintainer may concurrently edit your PR — re-check HEAD before committing/replying](../learnings/1790197469708-hands-on-maintainer-may-concurrently-edit-your-pr-.md).

## Don't Race a Self-Fixing Maintainer's "@bot rewrite" Batch

Twice on slang#13227 a maintainer left a batch of "rewrite this comment" / "document each flag" inline comments, then resolved them minutes later with a commit cited in each thread. Up-front subagent investigation and rewrites are wasted budget and an edit collision once their commit lands. Post ONE short holding ack, then PAUSE before expensive work. Inspect their side READ-ONLY (`git fetch`, `git show`, `git diff A..B`); `checkout`/`merge`/`reset` corrupt a subagent reading the same worktree. Review comments don't move HEAD — the fix-commit does; a comment's `commit_id` shows which head it is pinned to. If they self-resolved everything, kill the moot subagent, sync to their head, and post ONE standing-down comment ("addressed in <sha>, standing down so we don't collide, flag anything still open") — not N "thanks" replies, and no re-review of their prose [Maintainer who reviews AND self-fixes: don't race a batch of "@bot rewrite this" comments](../learnings/1790226898754-maintainer-who-reviews-and-self-fixes-don-t-race-a.md).

## A Maintainer's Refactor on Your Branch Plus Their Own PR Is a Supersede in Progress

Our draft slang#13227 (`fix/issue-13106`, empty ray-tracing payloads) was closed un-merged by kaizhangNV on 2026-09-28; their #13256 merged hours later and closed the issue. The early signal was the hands-on behaviour above: the maintainer had pushed their own "centralize payload legalization" refactor onto our branch. The design delta is placement — #13256 legalizes empty payloads **before type erasure**, so it needs none of our `slang-ir-inline.{h,cpp}` changes for reaching the payload carrier. It left one generated expectation stale after changing empty-payload padding (1 of 4 nightly failures in #13311, fixed by our draft #13312). Rules: a maintainer refactor pushed onto the bot's branch plus their own PR on the same files is a supersede in progress — stand down explicitly on ours and post the carry-forward on theirs (tests theirs lacks, generated expectations the change moves); and when a pass needs a new inliner/DCE hook to see its input, ask whether it sits too late in the pipeline. [postmortem: slang#13106 superseded by maintainer PR #13256 — treat a pushed refactor + own PR as a supersede; pass placement over inliner hooks](../learnings/1790684548885-postmortem-shader-slang-slang-13106-superseded-by-.md).

## A Maintainer PR on the Same Issue Outraces an Operator-Held Draft

slang#13249: `-g` stopped `-loop-inversion` from inverting a simple `do { if (i<10){} else break; ... } while(true)` loop. Our draft #13255 opened two minutes after pdeayton-nv's #13254 and was approved within a day, then sat five days awaiting an operator go-ahead; #13254 merged meanwhile. Theirs was also better: ours let `isSmallBlock` and the trivial-branch match skip every (zero-use) debug inst — a latent bug, because a `DebugValue` has no result users, so a break block holding `debugState = 7` would be erased as "trivial", dropping the debugger-visible update. #13254 skips only DebugLine/DebugScope/DebugNoScope, keeps DebugVar/DebugValue ("carry variable state"), and pins the negative case in `tests/ir/loop-inversion-debug-value.slang` (SPIR-V `-g2`/`-g3` FileCheck: DebugValue survives, loop NOT inverted). Rules: flag a maintainer PR on the same issue to the operator immediately; split debug insts by role ("no uses" is not "erasable"); and test a `-g` parity fix with a debug-observable update on the erased path, checked in SPIR-V debug output rather than HLSL ordering [postmortem: slang#13249 superseded by maintainer PR #13254 — operator-held draft lost the race; DebugValue is not erasable at zero uses](../learnings/1790814920619-postmortem-shader-slang-slang-13249-superseded-by-.md).

slang#11616 (a `[ForceInline]` return emitted `DebugNoScope`, leaving caller locals unscoped) is the slow version. Our draft #11617 (2026-06-15) sat for months, was reassigned to pdeayton-nv on 08-04, and was closed on 10-07 after their #13175 merged 09-22. #13175 keeps `DebugNoScope` a single-purpose zero-operand inst never emitted on inline return (ours gave it an optional restore-scope operand — one opcode, two meanings), bumps the supported IR module version range (31..31) for the changed operand layout (ours broke serialized modules), and updates the LLVM emit path. Rules: an IR operand-layout/arity change bumps the module version range in the same PR and tests separately compiled modules; extend the inst that represents the concept rather than widening another opcode; audit SPIR-V **and** LLVM emitters on a debug-info IR change; and a bot draft assigned to a maintainer ~4+ weeks without review signals they will write their own fix — ask early [postmortem: slang#11616 superseded by maintainer PR #13175 — single-purpose DebugNoScope, IR version bump, LLVM emit](../learnings/1791421008032-postmortem-shader-slang-slang-11616-superseded-by-.md).

slang#13179 (slangd in Zed did not resolve `#include` targets unless the file was open) adds a cleanup rule. Our draft #13182 shared the `rootUri`/`rootPath` fallback of jkiviluoto-nv's #13192 (merged 2026-09-23) but missed the second root cause, the per-root search-path overwrite, and had no multi-root tests; it then sat 27 days as "HELD-OPERATOR" until the parent corrected it. Closing our own superseded bot draft is supervise-issues Step 7 and needs no operator go-ahead — the operator gate protects human-owned artifacts. Post a short comment naming the superseding PR, what it did, and any saved `wip/` branch, then `gh pr close`; delete no branches unless asked. The technical lesson is on the slangd page [postmortem: slang#13179 superseded by PR #13192 — missed per-root overwrite; closing our own superseded draft is not operator-gated](../learnings/1792461389590-postmortem-shader-slang-slang-13179-superseded-by-.md), [closing our own superseded draft PR is not operator-gated](../learnings/1792461290103-closing-our-own-superseded-draft-pr-is-not-operato.md).

## Two-Maintainer Design Divergence: Provide Evidence, Ask Them to Align, Gate Any Redesign

When one maintainer steered a coworker PR's design and another files REQUEST_CHANGES against it, the coworker must not pick a side, redesign unilaterally, or apply the objector's literal diff. It provides technical evidence and asks both to align; the orchestrator gates any redesign on (1) both maintainers explicitly agreeing on the new mechanism AND (2) the alternative being confirmed at source / empirically to satisfy the original hard constraint. On slang#13070 / PR #13086 jkwak-work objected to an interface member pdeayton-nv had steered. The fixer verified at source (`IOpaqueDescriptor` is `[sealed][builtin]`), tested a `.slang-module` round-trip, and posted a collaborative COMMENT-state reply (never a competing APPROVE/REQUEST_CHANGES — bot policy) tagging both, framing the objection as "same intent, here are the constraints any alternative must satisfy." pdeayton-nv then proposed jkwak's ask (a type-query intrinsic); with both preconditions met (fold confirmed at source and via a fired `static_assert` + DCE) the redesign was authorized and merged (6eb89786ca). Orchestrator posture on a non-`@bot` multi-maintainer thread: hold the coworker's post for calibration, authorize a COMMENT reply that asks rather than asserts, require a redesign plan first, and never let the coworker counter a maintainer's verdict [Two-maintainer design divergence on a PR: provide evidence, ask them to align, gate any redesign](../learnings/1790220265420-two-maintainer-design-divergence-on-a-pr-provide-e.md).

## Re-check the Newest Issue Comment Immediately Before Posting — a Peer Bot Shares Your Identity

Run the edit-if-last-poster-is-self / anti-dup check immediately before posting, against a live re-read, not the start-of-turn snapshot. On slang#13247 the issue had 0 comments at triage start; ~10 min into research a peer `nv-slang-bot` session posted the disposition, and posting the full triage produced a same-identity double-post on a maintainer-watched issue. Right before posting, run `gh api repos/<r>/issues/<n>/comments --jq '.[-1].user.login'`; if it is `nv-slang-bot[bot]`, PATCH in place or post only a delta — the reader must see one clean comment, across sessions. Related: an auto-filed tracking issue can read stale; check the referenced PR's current head before triaging it as open [Re-check the newest issue comment immediately before posting — a peer bot session shares your GitHub identity](../learnings/1790198726943-re-check-the-newest-issue-comment-immediately-befo.md).

## Leave Maintainer Comments Byte-for-Byte, and Expect Your Push to Dismiss Their Approval

**Never reword a comment you did not write in this PR, not even a typo.** On slang#13406 the bot changed tangent-vector's `ParamPassingMode` ref-mode doc comment from "without also using the `readonly` or `writeonly` modifiers" to "without also using `const`". He replied (r4168414449): "Why did you break the existing comment that an intelligent human (me) wrote? I was documented the intended design direction of the language, with intent. Please revert your incorrect change." It recorded design intent the code does not (`const` on `__ref` is only a legacy alias for `readonly`). Document alongside it in their vocabulary (`readonly ref`, not `const ref`), ask in a review reply if your change makes it wrong, and before committing run `git diff origin/master...HEAD | grep -E '^-\s*//'` and justify or revert every hit. ([never reword a maintainer's existing source comment (slang)](../learnings/1790967868088-never-reword-a-maintainer-s-existing-source-commen.md); [never reword a maintainer's existing code comment; a push dismisses their approval](../learnings/1790967953965-never-reword-a-maintainer-s-existing-code-comment-.md)).

**A bot push after a human approval silently dismisses it.** shader-slang/slang dismisses stale reviews, so the review shows `DISMISSED`, the timeline gains a `review_dismissed` event with `dismissal_commit_id`, and `reviewDecision` goes empty — for fix commits and conflict-resolution pushes alike. On #13406 tangent-vector's approval was dismissed 25 minutes later by the fixer's push, yet the fixer still reported him as approving. On #13312 jkwak-work's approval was dropped two minutes later by a conflict-resolution push, leaving sole requested reviewer dshreiner-nv — requested on 61 open PRs, has reviewed none, so effectively no reviewer. Before reporting approval state, check `gh pr view N --json reviewDecision` at the current head or `gh api repos/<o>/<r>/issues/<n>/timeline --paginate --jq '.[] | select(.event=="review_dismissed")'`; flag "re-approval needed" after any bot push that follows an approval; never recommend "close as superseded" from a stale read; and batch review fixes into one push. Riders from #13406: build the requirement list from issue comments AND `pulls/<n>/comments` (an issue-only read missed all 8 inline comments) and re-fetch after any head move; and build all default targets (a `slangc`/`slang-test`-only build skipped the standard modules: 60 false failures) ([a bot conflict-resolution push silently dismisses a human approval](../learnings/1790843181467-a-bot-conflict-resolution-push-silently-dismisses-.md); [a pushed commit silently dismisses a maintainer's APPROVED review — check the timeline](../learnings/1790969117654-slang-pr-review-a-pushed-commit-silently-dismisses.md)).

## Byte-Exact PR-Body Metadata Edits: gh api JSON `.body`, not `--jq .body`

To change one line in a PR/issue body while keeping the maintainer's text verbatim (e.g. adding `Fixes #N` beside `Fixes #M`), regenerate from the live body and do a targeted replace; never hand-edit a saved copy. `gh pr view <n> --json body --jq .body` (and `gh api … --jq .body`) appends a trailing newline, so the edited file is no longer "exactly one line added." Recipe: `body = json.loads(subprocess.check_output(['gh','api','repos/O/R/pulls/N']))['body']`; `body.replace('Fixes #M.', 'Fixes #M.\nFixes #N.', 1)`; write with no extra trailing newline; confirm with a unified diff that only the intended line changed; `gh pr edit N --body-file`. A closing keyword is body metadata, so it is safe on a PR whose commits a maintainer owns [Byte-exact PR-body metadata edits: use gh api JSON .body, not --jq .body](../learnings/1790199138458-byte-exact-pr-body-metadata-edits-use-gh-api-json-.md).

## A Producer Fix Breaks the Coupled Emit-PR's Test and Comments

When a fix is split between a producer PR (autodiff `copyDebugInfo`) and an emitter PR (SPIR-V `DebugFunctionDefinition` dedup), the emit PR's test often uses the producer's buggy output as its vehicle, so it FAILS once the producer lands — with no textual conflict. On slang#13237 the test asserted that `f`'s DebugFunction, shared by `s_apply_f`/`s_bwdProp_f`, carries exactly one `DebugFunctionDefinition`; slang#13238 stopped the sharing, so `OpString "f"` disappeared and the assertion broke. After merging master, rebuild and run the coupled area's tests regardless of a clean merge; rewrite the test to the new correct behaviour ("tests are contract — update, don't silence") and say in the PR body if the fix removes the only scenario exercising the sibling's logic. The producer fix also falsified a comment in the merged sibling (#13237's "reverse-mode autodiff can make several OpFunctions share one IRDebugFunction"), so sweep coupled files for stale comments [Two review-round gotchas: FileCheck 'CHECK' tokens in prose, and never rm a file you didn't create](../learnings/1790222348386-two-review-round-gotchas-filecheck-check-tokens-in.md). Guard debug-metadata invariants with `SLANG_RELEASE_ASSERT`, not `SLANG_ASSERT`, since a debug-only assert lets the wrong debug name recur in release. Before `rm`-ing a file, confirm you created it (`git log --follow -- <file>` / `git ls-files <file>`) — a codex reviewer that compiles existing tests did not create them — and never `git add -A` a `PR_BODY.md` scratch file [Fixing a producer breaks the coupled emit-PR's test that used the bug as its vehicle](../learnings/1790216980075-fixing-a-producer-breaks-the-coupled-emit-pr-s-tes.md).

## Maintainers Trim Bug-History Narration from Regression-Test Headers

On slang#13269 skiminki-nv approved the bot's fix only after pushing a commit that cut the `gh-13260.slang` header from a 9-line paragraph to a 3-line statement of the rule.
