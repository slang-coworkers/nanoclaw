# Working Live PRs Alongside Maintainers and Sibling Bots

How a bot coworker coordinates on a live PR when a human maintainer is hands-on (editing the branch, reviewing and self-fixing, or diverging from a co-maintainer) and when sibling bot sessions share the same GitHub identity — plus the mechanical care needed to edit a PR body or reconcile a coupled sibling PR without wasting a cycle or corrupting a maintainer's text.

## TL;DR

- **Re-derive a maintainer's scope directive from the LIVE primary comment, never a paraphrase or the webhook `body`.** A dropped clause ("and this should also fix #N") or an ADDED narrowing you inferred ("keep it scoped, don't fold in #N") inverts scope and wastes a built-reviewed-CI-green PR. One comment fetch is cheap; a wasted fix cycle is not. If you catch yourself writing "keep this scoped to…", confirm that constraint is in the maintainer's own words.
- **A hands-on maintainer may push commits onto your branch and leave rapid batches of inline comments.** Re-fetch and check the PR head before committing or replying; many maintainer "comments" are resolution notes ("Implemented in <sha>"), not asks — close via an upstream report, only reply on GitHub to genuine questions.
- **Don't race a self-fixing maintainer.** One short holding ack, then PAUSE — inspect their side with READ-ONLY git (`git fetch` + `git show <sha>`), never `checkout`/`merge`/`reset` while a subagent reads the same worktree; if they resolved it themselves, kill the moot subagent, sync, and post ONE standing-down comment.
- **When two maintainers diverge on a design mechanism, provide evidence and ask them to align — do NOT pick a side or apply the objector's diff.** Gate any coworker redesign on both preconditions: both maintainers explicitly agree, AND the alternative is confirmed (at source / empirically) to satisfy the original hard constraint.
- **Run the anti-dup check immediately before posting, against a LIVE re-read** — a peer bot session (same GitHub identity, different session) can post between your turn's start and its end, so consolidate across sessions, not just against your start-of-turn snapshot.
- **Byte-exact PR-body edits: regenerate from `gh api …/pulls/N` → `json.loads(...)['body']`, not `--jq .body`** (jq appends a spurious trailing newline that breaks a "exactly one line added" diff check).
- **A producer-side fix invalidates the coupled emit-PR's test and any comment that described the bug** — rebuild and run the coupled area's tests after a "clean" merge, and sweep coupled files for now-false comments.

## Re-derive Maintainer Scope Directives from the Primary Comment

A relayed or paraphrased maintainer instruction is the most expensive kind of relay error, because it looks authoritative downstream. On slangpy#886 the maintainer's issue comment read verbatim *"…add the slangpy module searching path by default. **And this should also fix the #1177.**"* Two failures compounded: (1) the webhook `body` OMITTED the final "also fix #1177" clause, and it was relayed as complete; (2) a scope NARROWING was then ADDED that the maintainer never stated ("keep #886 scoped to `create_slang_session`; don't fold #1177 in") — inferred from prior context (an earlier bot reply had called #1177 "related, not a duplicate"). The maintainer's comment explicitly requested the unified fix, so the sessions-only PR #1182 (built, peer-reviewed APPROVE_WITH_NITS, CI-green) could not satisfy it and was closed unmerged; a parallel bot session's #1183 (`Fixes #886` + `Fixes #1177`, "Supersedes #1182") merged. The inverted scope was even posted publicly one comment below the maintainer's request. Rules: **the tier that hands scope to an implementer owns re-deriving it from the live GitHub comment** (`gh api repos/O/R/issues/comments/<id> --jq .body`), never from the webhook payload alone (payloads truncate/omit trailing clauses); **relay maintainer comments verbatim, every "should also fix #N" / "while you're at it" clause included** (paraphrase drops scope, and a relay-added narrowing is itself a load-bearing claim); **never ADD a constraint the maintainer did not state** — if prior context suggests a narrowing, that is a question to surface, not an instruction to inject; and **cross-issue linkage is a collision signal** — surface #N's ownership before dispatching so two bot sessions don't build competing PRs [A paraphrased maintainer directive can invert scope — the relaying tier must re-read the source comment](../learnings/1790193335302-a-paraphrased-maintainer-directive-can-invert-scop.md) [Re-derive maintainer scope directives from the primary GitHub comment — webhook bodies truncate, and never ADD scope you inferred](../learnings/1790193478269-re-derive-maintainer-scope-directives-from-the-pri.md).

## A Hands-On Maintainer May Edit Your Branch — Re-check HEAD; Comments Are Often Notes

On slang#13227 a maintainer pushed their own commits directly onto the bot's `fix/issue-13106` branch (a large refactor, then comment-polish commits) and left many inline comments in rapid batches. Before committing edits or posting a reply, **re-fetch and check the PR head** — in-flight edits get superseded by a maintainer commit that lands mid-work (e.g. both rewriting the same doc comment); fast-forward to the head, `git restore` your now-redundant edits, and don't claim "I fixed X" when the maintainer already fixed it (`git merge-base --is-ancestor <mine> FETCH_HEAD` verifies nothing was lost). **Maintainer review comments are often resolution/acknowledgment notes** ("Implemented in <sha>", "Added in <sha>"), not asks — close via an upstream report to your parent per chain rules, and reply on GitHub only to genuine questions/change-requests. And **verify "X is/isn't a producer" code claims against the actual lowering path, not the surface symbol**: a claim that `__spirvTraceRayHitObjectEXT` "isn't a producer" of a `[__vulkanRayPayload]` global was wrong because its stdlib *wrapper* declares `[__vulkanRayPayload] static T p`, so the calling path IS a producer — match by decoration/role and trace wrapper→intrinsic [Hands-on maintainer may concurrently edit your PR — re-check HEAD before committing/replying](../learnings/1790197469708-hands-on-maintainer-may-concurrently-edit-your-pr-.md).

## Don't Race a Self-Fixing Maintainer's "@bot rewrite" Batch

Some maintainers leave a large batch of inline "rewrite this comment" / "document each flag" review comments AND then resolve them THEMSELVES by pushing a commit minutes later, replying to each thread citing that commit (observed twice on slang#13227). Spinning up an investigation subagent and authoring rewrites up front is pure wasted budget and an edit collision the moment their commit lands. Tactics: honor reply-promptly with ONE short holding ack, then PAUSE before expensive edit work; **inspect their side READ-ONLY** (`git fetch` + `git show <sha> --stat` + `git diff A..B` operate on committed objects, NOT the working tree — never `checkout`/`merge`/`reset` while a subagent reads the same worktree, it corrupts the subagent's reads mid-analysis); re-check the PR head (review comments don't move HEAD, the maintainer's fix-commit does — the comment `commit_id` tells you which head they're pinned to); and if the maintainer self-resolved everything, KILL the moot subagent, sync to their head, and post ONE standing-down comment ("you've addressed these in <sha>, standing down so we don't collide, flag anything still open") — not N redundant "thanks" replies, and don't re-review the maintainer's own doc prose. A batch of "@bot rewrite this" from a maintainer actively pushing to the branch is "make the PR clear," which they may complete themselves — not automatically a work order to duplicate [Maintainer who reviews AND self-fixes: don't race a batch of "@bot rewrite this" comments](../learnings/1790226898754-maintainer-who-reviews-and-self-fixes-don-t-race-a.md).

## Two-Maintainer Design Divergence: Provide Evidence, Ask Them to Align, Gate Any Redesign

When two maintainers diverge on a *design mechanism* for a coworker's PR (one steered the current design, another files REQUEST_CHANGES against it), the coworker must **not** pick a side, redesign unilaterally, or apply the objector's literal diff — redesigning to satisfy one risks diverging from the other and makes the coworker appear to take sides. It provides the technical evidence and asks *both* to align on the mechanism first; the orchestrator gates any coworker-initiated redesign on **two preconditions: (1) both maintainers explicitly agree on the new mechanism, AND (2) a viable alternative is confirmed — at source / empirically, not assumed — to satisfy the original hard constraint.** On slang#13070 / PR #13086 (merged 6eb89786ca): jkwak-work filed REQUEST_CHANGES on an interface member that pdeayton-nv had steered; the fixer verified at source (`IOpaqueDescriptor` is `[sealed][builtin]` ⇒ no external conformer can break it), built a `.slang-module` round-trip to test serialization, and posted a **collaborative COMMENT-state reply** (never a competing APPROVE/REQUEST_CHANGES review — bot policy) tagging both maintainers, framing the objection's fix as "same intent, here are the constraints any alternative must satisfy," and asked them to settle it. pdeayton-nv then proposed exactly jkwak's ask (a type-query intrinsic); both preconditions met (aligned + fold confirmed at source AND empirically via a fired `static_assert` + DCE), the redesign was authorized, both approved, merged. Orchestrator posture: on a non-`@bot`-mention multi-maintainer thread, hold the coworker's GitHub post for calibration, then authorize a COMMENT-state reply that ASKS rather than asserts; require a redesign plan before implementing; never let the coworker counter a maintainer's review verdict with its own [Two-maintainer design divergence on a PR: provide evidence, ask them to align, gate any redesign](../learnings/1790220265420-two-maintainer-design-divergence-on-a-pr-provide-e.md).

## Re-check the Newest Issue Comment Immediately Before Posting — a Peer Bot Shares Your Identity

The edit-if-last-poster-is-self / anti-dup check must run **immediately before posting, against a LIVE re-read** — not against the "N comments" snapshot taken at the start of the turn. On a long research turn (multiple subagents, minutes elapsed), another `nv-slang-bot` **session** (same GitHub identity, different session) can post on the same issue in between: on slang#13247 the issue had 0 comments at triage start, and ~10 min later a peer bot session posted the disposition while research was still running, so posting the full triage as a fresh comment produced a same-identity double-post on a maintainer-watched issue. Remediation was to delete the just-posted comment (safe — created it, seconds old) and repoint the idfile to the surviving peer comment. So: `gh api repos/<r>/issues/<n>/comments --jq '.[-1].user.login'` right before posting — if it's `nv-slang-bot[bot]`, PATCH-in-place or post only a delta (the anti-dup rule is about the READER seeing one clean comment, so consolidate even across sessions). Related: a tracking issue can be auto-filed from an earlier PR snapshot and read STALE — verify the tracked fix hasn't already landed in the referenced PR's current head diff before triaging it as open [Re-check the newest issue comment immediately before posting — a peer bot session shares your GitHub identity](../learnings/1790198726943-re-check-the-newest-issue-comment-immediately-befo.md).

## Byte-Exact PR-Body Metadata Edits: gh api JSON `.body`, not `--jq .body`

To add/change one line in a PR/issue body while preserving the maintainer's text verbatim (e.g. appending `Fixes #N` beside an existing `Fixes #M`), regenerate the body from the LIVE source of truth and do a targeted string replace — do NOT hand-edit a previously-saved copy. The pitfall that fails a byte-exact diff check: `gh pr view <n> --json body --jq .body` (and `gh api … --jq .body`) appends a spurious trailing newline to jq's string output, so a saved-then-edited file gains an extra trailing blank line and the change is no longer "exactly one line added." Clean recipe: `body = json.loads(subprocess.check_output(['gh','api','repos/O/R/pulls/N']))['body']` gives the exact string with no jq artifact; `body.replace('Fixes #M.', 'Fixes #M.\nFixes #N.', 1)`, write with no extra trailing newline, verify with a unified diff that ONLY the intended line changed, then `gh pr edit N --body-file`. Adding a `Fixes #N` closing keyword is body-metadata (does not touch commits), so it is safe on a PR whose commits a maintainer owns [Byte-exact PR-body metadata edits: use gh api JSON .body, not --jq .body](../learnings/1790199138458-byte-exact-pr-body-metadata-edits-use-gh-api-json-.md).

## A Producer Fix Breaks the Coupled Emit-PR's Test and Comments

When two PRs split a fix across a producer (e.g. autodiff `copyDebugInfo`) and its consumer/emitter (e.g. SPIR-V `DebugFunctionDefinition` dedup), the emit-side PR's regression test often uses the producer's *buggy* output as its test vehicle — so once the producer PR lands, that test's premise is invalidated and it FAILS, with zero textual merge conflict. On slang#13237 the emit test asserted `f`'s DebugFunction record — shared by autodiff's `s_apply_f`/`s_bwdProp_f` bodies — carries exactly one `DebugFunctionDefinition`; slang#13238's producer fix stops the sharing, so `OpString "f"` is no longer emitted for a derivative body and the assertion breaks. Lessons: after merging master into a fix branch, don't trust "clean merge, no conflicts" — rebuild and run the *coupled area's* tests specifically (a semantic interaction won't show as a git conflict); reconcile by renaming+rewriting the test to the new correct behavior ("tests are contract — update, don't silence") and state plainly in the PR body if the fix removes the only scenario exercising the sibling's logic (don't overclaim preserved coverage — codex OUTPUT_REVIEW will flag it); a producer fix likewise makes a *comment* in the coupled already-merged PR factually false (#13237's "reverse-mode autodiff can make several OpFunctions share one IRDebugFunction" became untrue), so sweep coupled files for now-stale comments, not just code [Two review-round gotchas: FileCheck 'CHECK' tokens in prose, and never rm a file you didn't create](../learnings/1790222348386-two-review-round-gotchas-filecheck-check-tokens-in.md). Debug metadata is compiler *output*: guard an invariant whose violation would silently re-emit the wrong debug name with `SLANG_RELEASE_ASSERT`, not `SLANG_ASSERT` (a debug-only assert lets the fixed bug silently recur in release). Cleanup hygiene from the same rounds: before `rm`-ing a file, run `git log --follow -- <file>` / `git ls-files <file>` to confirm you created it (a codex reviewer with full filesystem access READS/compiles *existing* repo tests to verify a finding — that does not mean it created them), and never `git add -A` a `PR_BODY.md` scratch file into the worktree (add tracked files explicitly) [Fixing a producer breaks the coupled emit-PR's test that used the bug as its vehicle](../learnings/1790216980075-fixing-a-producer-breaks-the-coupled-emit-pr-s-tes.md).
