# PR-Approver: Absence Arguments, Evidence Discipline & Durable-Record Mechanics

## TL;DR

- **An absence-of-log-line argument carries zero information until you prove the line would have been emitted AND printed at that run's severity and verbosity.** Grep the *branch*, not the message text; sibling branches in one `if/else` routinely differ in severity; then confirm that severity reaches *this* log at *this* run's verbosity and outcome. The one-command control: count all lines of that severity — zero of any kind means the channel was closed, so you measured the harness, not the code.
- **Never establish an absence, a count, or a completeness claim with a summarizing fetch tool.** Summarizers answer "what does this argue?"; code answers "how many / does X exist / is this all of them?". Enumerate JSON with stdlib `urllib` at `per_page=100`, loop until a short page, count in code. A summarizer's silence is not a signal — it cannot report its own truncation.
- **Before asserting a negative, grep the material you have ALREADY fetched for ordinals and back-references** ("third round", "as I said above", "reverted my earlier fix"); such a phrase contradicting your conclusion means the conclusion is wrong. Never assert a negative from a lossy view; verification is symmetric — reproduce a peer's specific evidence deterministically before contradicting it.
- **"The API returned an error" is not "the information is unavailable."** A tool error gating a load-bearing premise gets ONE adversarial retry before it becomes a caveat — follow redirects, unauth vs auth, REST vs GraphQL vs timeline vs compare — then name both methods in the artifact. GitHub Actions job logs are PUBLIC (302 → signed blob; `curl -sSL` follows with no credentials).
- **A job-log 410 is retention expiry (~5-day window on slang), not breakage.** Discriminate with a fresh-job positive control FIRST; transfer the answer via byte-identical blob reads (never expire); settle the "did it pass *because* of the fix?" residual from the pre-PR base source. Write "could not verify at SHA by method M", never "logs unavailable".
- **Narrowing a claim is not testing its premise.** Ask what observation would settle it and whether it is cheaply available before recording either version; retract at paragraph granularity, naming the file and quoting the retracted sentences.
- **Species 1 — the record of diligence outlives the diligence.** Labels, resolving links, headings, stated tallies, green CI, exit-0 harvests all stay green without the underlying work. Ask: *would this check still be green if the work did not exist?* If yes, re-derive the datapoint (open the file at the SHA, run the command, count from artifacts). Order operations so the record cannot precede the reality. Read a smooth agreement as an untested hypothesis.
- **Species 2 — the apparatus is subject to the effect under test.** Ask: *would this probe report the same result whether or not the thing I am testing is true?* Identical outcomes ⇒ no probe. One probe per invocation. GitHub credential injection is PER-PATH: read `x-ratelimit` PRESENCE (not value) on the exact path you will call. A false capability-NEGATIVE published into shared prose is the most dangerous class — prefer "I could not verify X by method M" over "X is unavailable."
- **Cross-tier counts:** "I ran the identical command" ≠ "we ran the identical query" — CLI semantics vary per caller-scope, so each side must state its scope. A membership check (`get <id>`) cannot detect truncation; completeness needs a BOUND test (explicit `--limit` far above expected, stable when raised) — an unbounded count is a floor, not a total. A denial inherits the scope of the surface you checked; attribute by group + session id + thread. A new instrument whose first act confirms your prior belief deserves more suspicion, not less. A correction is itself a relay — accept a refutation without inheriting its substitute figure.

## Absence arguments: zero information until you prove the channel was open

A refutation built on "the log doesn't say so" / "the endpoint returned nothing" is the approver's most common self-inflicted false-clean, and it is *structurally* unsound rather than merely sloppy.

**An absence-of-log-line argument carries zero information until you prove the line would have been emitted AND printed at that run's verbosity.** On slang-rhi#800 a bot 🔴 (indirect dispatch can crash on Metal devices without a residency set) was partly refuted by grepping both CI logs for four strings (`MTLResidencySet creation failed`, `using per-encoder useResource fallback`, `GPUFamilyApple6 not supported`, `SLANG_RHI_METAL_NO_RESIDENCY_SET`) and finding 0. The counts were correct; the inference was not. The three ways into the fallback **do not share a severity** (`metal-device.cpp:109-145`: env-var and Apple6 paths are `Info`, `newResidencySet`-null is `Warning`), and the harness routes them differently (`testing.cpp:209-219`: `Info` → doctest `INFO()`, flushed only when a test FAILS or under `options().verbose`; `Warning` → `MESSAGE()`, unconditional). The run was non-verbose and all-green, so **zero `[Info]` lines of any kind existed**: 2 of 3 paths were undetectable by construction. The success path `m_hasResidencySet = true` emits **nothing**, so the positive claim had no direct evidence either. Inversion trap: `INFO()` diagnostics appear only when the run fails, so on a green run, where the absence argument looks strongest, it carries nothing. Before writing "X never happened because the log doesn't say so", ask in order: does the code emit anything on that path (grep the *branch*, not the message text)? at what severity (sibling branches in one `if/else` routinely differ)? does that severity reach *this* log at *this* run's verbosity and outcome? The one-command control: **count all lines of that severity**; zero of any kind means the channel is closed and you measured the harness, not the code. Decision impact was nil (ABSTAIN_POLICY / CHALLENGER_CONCERN held through six critique rounds) **and that is the point**: the primary basis moved from a procedural "standing CHANGES_REQUESTED" (cleared by a human 51 seconds later) to the substantive residency gap. *A withhold justified by the wrong reason is a latent false-safe*: when the wrong reason evaporates, the real risk remains ([[approver/critique-mustfix] an absence-of-log-line argument carries zero information until you prove the line would be emitted AND printed](../learnings/1785772353384-approver-critique-mustfix-an-absence-of-log-line-a.md)).

⚠️ **That correction was itself only half-right: NARROWING a claim is not TESTING its premise.** The residency corollary of the #800 calibration atom is **withdrawn**: "the third refutation finally had execution behind it", "CI ran the residency-**set** path", "the `!m_hasResidencySet` fallback is unexercised for all Metal ops — pre-existing harness scope, not PR-introduced", and "the technical withhold reason was retired on evidence" are retracted (the last *inverted*: the residency gap was the PRIMARY basis, review state secondary). The polarity then flipped: `m_hasResidencySet = true` is set **only** inside `else if (supportsFamily(MTL::GPUFamilyApple6))`, the hosted `Apple Paravirtual device` on `macos-26-arm64` **lacks Apple6**, and a sibling job on that image logs the terminal-`else` fallback message, so **CI runs the FALLBACK by default**: the *residency-SET* path is the uncovered one, and the missing artifact is an **Apple6 run**, never a `SLANG_RHI_METAL_NO_RESIDENCY_SET` run. "Unexercised" had been rewritten as "unverified": weaker, same direction, **same untested premise** (*which path does CI take?*), so the retraction inherited the error and laundered it as diligence. Ask what observation would settle a claim and whether it is cheaply available before recording either version; here it was one unauthenticated `curl` of a public job log. Retract at **paragraph granularity**, naming the file and quoting the retracted sentences: that atom's five-log-check coverage checklist and Metal residency taxonomy remain correct and were expensive to derive ([[approver/critique-mustfix] CORRECTION to the slang-rhi#800 calibration atom — narrowing a claim is not testing its premise](../learnings/1785774267946-approver-critique-mustfix-correction-to-my-own-sla.md)).

**Never establish absence, a count, or a completeness claim with a summarizing fetch tool.** Telling the orchestrator that four review comments *"did not exist"*, an error injected into a state record that was already correct, came from `WebFetch`, which answers a prompt against a page with a small summarizing model: prose-shaped, not an enumerator, silently degrading on long JSON. Three calls to one URL reported page-3 counts of 18 / 16 / 16 against a truth of **50**, and one comment's body length as 1088 / 856 against 1198; asked *"is there any element with created_at starting 2026-08-03T08:03? YES or NO"* it answered **NO** and listed the timestamps it did see as if exhaustive. **A summarizer cannot report its own truncation, so its confident `NO` is worth nothing.** Summarizer for *"what does this argue?"*; code for *"how many / does X exist / is this all of them?"*: fetch the JSON with stdlib `urllib` at `per_page=100` and loop until a short page. Red flags: two calls disagreeing on a total or body length, a count near a round number, a "there is no X" backed only by prose. **Never assert a negative from a lossy view** (say "I did not find it in N pages I enumerated deterministically", or nothing), and **before contradicting a peer who supplied specific evidence (exact counts, verbatim quotes), reproduce their query deterministically**: specificity is cheap to verify and expensive to fabricate, so the burden sits on the contradiction. The disproof was in hand all along: a body already fetched verbatim opened *"This is the third round raising the guard"*, i.e. two prior rounds, the batch being called nonexistent ([[approver/critique-mustfix] never establish absence or counts with a summarizing fetch tool — it fabricated a confident NO and three counts for one URL](../learnings/1785761721232-approver-critique-mustfix-never-establish-absence-.md)). The check order: **grep material you have ALREADY fetched for ordinals and back-references implying the positive** ("third round", "as I said above", "reverted my earlier fix"); when one contradicts the conclusion you are forming, *the conclusion is what's wrong*; then re-run deterministically; only then state absence, scoped to what you enumerated. Verification runs **both ways**: the peer's own enumeration was short too (two comments in an `11:02` batch that deterministically contains four), so what protects the record is the method, not the speaker ([[approver/clause-gap] CORRECTION — grep your own already-fetched material before reporting a negative; verification is symmetric](../learnings/1785761810820-approver-clause-gap-correction-to-empty-body-comme.md)).

**A tool error gating a load-bearing premise gets ONE adversarial retry before it becomes a caveat.** On slang-rhi#807 the macOS runner's OS version decided whether a deleted test assertion (`CHECK_FALSE(device->hasCapability(metallib_4_0))`) was load-bearing or cosmetic. `actions/jobs/<job_id>/logs` returned 403 "must have admin rights", the premise was recorded as **unresolvable**, and "runner macOS version unknown" shipped as a caveat driving a conservative lean that only happened to be correct. The endpoint is **public**: it 302-redirects to a signed Azure blob, and `curl -sSL` returns the full log **with no credentials** on a public repo (256,628 bytes; its startup group shows `Operating System / macOS / 26.5.2`, `Runner Image: macos-26-arm64` ⇒ major 26 ⇒ the assertion **was** load-bearing). The 403 did not reproduce (302 with `Location:`, authenticated `gh api` 200), so a shim produced it; don't key this rule on seeing a 403. **"The API returned an error" is not "the information is unavailable."** Before writing "could not determine" about anything a verdict leans on, try one genuinely different path (follow redirects; unauthenticated vs authenticated, which fail differently; REST vs GraphQL vs `issues/<n>/timeline` vs `compare/<a>...<b>`; another endpoint carrying the same fact), then name **both** methods in the artifact ([[approver/infra-abstain] GitHub Actions job logs are PUBLIC — follow the 302, and never let one tool error close a load-bearing premise](../learnings/1785766450209-approver-infra-abstain-github-actions-job-logs-are.md)).

**A job-log 410 is retention expiry, not breakage: positive-control it FIRST, transfer via byte-identical blob, and settle the load-bearing question from SOURCE.** Proving `tests/metal/ray-query-intrinsics.slang` actually EXECUTED (not merely "the job was green") on slang#12142's head `2a61c227a2ca`, every log endpoint returned HTTP 410 Gone (per-job, per-run, per-attempt, `gh run view --log`) and all 16 run artifacts were `expired: true`. One call settles it: the *identical command* on a job that finished minutes ago (`gh api actions/jobs/$NJOB/logs | wc -c` → 60116 bytes). If the fresh job returns bytes, method and token are HEALTHY and the *data* is gone. Slang's measured window is ≈5 days (07-31/08-01/08-03/08-04 ✅, 07-29/07-23 ❌ 410), far below GitHub's 90-day artifact default, and the 410 is **per-run, not per-attempt**, so no sibling attempt recovers it. Write "could not verify at the pinned SHA by method M", M named, never "logs unavailable" (a false capability-negative with no failure signature), and never infer execution from a green conclusion. Two transfer paths: (1) **byte-identical blob**: tree/blob reads never expire, so if the test file's blob SHA matches at the pinned SHA and a recent commit, quote verbatim result lines from a *recent* run (MTL passed on all four legs, metallib `passed` on macOS only / `ignored` on Linux, mtl GPU `ignored` everywhere), always citing the tally control `100% (7121/7121), 3516 ignored` so the grep isn't a zero-hit against a dead instrument, and stating the limit (byte-identity pins the *test input*, not the *compiler*); (2) the question no log can answer, "did it pass *because* of the fix?", is settled from the **pre-PR base**: base `4f4ec505761e` bakes `get_` into `kCandidateCommittedMetal[]` while the test asserts `is_candidate_triangle_front_facing`, so the checks fail without the PR, better evidence than a log line and non-expiring ([job-log 410 is retention expiry — positive-control it, then transfer via byte-identical blob + settle load-bearing from source](../learnings/1785841389780-approver-infra-abstain-github-job-logs-410-after-5.md)). Same family: `gh api .../contents/<path>?ref=<sha>` returns `encoding=none`/`content_len=0` for files over ~1 MB (`hlsl.meta.slang` is 1.2 MB), so `--jq .content | base64 -d | grep -c X` prints a confident `0` indistinguishable from "not present"; use `-H "Accept: application/vnd.github.raw"` and check `wc -c` against `.size`. A zero-hit grep needs a must-be-non-zero control before it means anything.

## Two species of broken check (evidence discipline & the durable record)

**Species 1 — the record of diligence outlives the diligence.** Distilled from ~14 defects across two review tiers in one chain: every *cheap* verification reads a **record** of work rather than re-deriving it, and records are satisfiable without the work, so they come back green either way. Instances, all by people who already held the rule in writing: a "VERIFIED" label written before the check ran; a maxim that outlived its proof (compacting an index deleted the evidence paragraph and kept the one-liner, recursively including the paragraph saying *"do NOT compress it away, or what remains is a plausible maxim with nothing under it"*); a resolving markdown link (link integrity is not content presence); a stated tally ("nine defects" went unchallenged because nobody argues with a count; audited from artifacts it was ~14, drifting the *comfortable* way on both sides independently); a grep for **remembered wording** (searching your store for what you *think* you wrote reads your intent, not the artifact); a green CI conclusion (registered ≠ executed; green can mean the code compiled out); and an exit-0 harvest (succeeded ≠ read everything). **The discriminating question: if the underlying work did not exist, would this check still be green?** If yes, it is a record check, and only re-deriving is not fooled: open the file at the pinned SHA, grep for the load-bearing **datapoint** rather than the rule's title, run the command rather than reading it, count from artifacts rather than memory. Record checks *feel* like diligence, so they replace the expensive check under time pressure, when stakes are highest. Two near-free defenses: when restoring or moving content, **verify the EVIDENCE, not the heading**; and **order operations so the record cannot precede the reality** (write the child file, grep to confirm, *then* shorten the parent; run the check, *then* write the label; count from artifacts, *then* state the number). Every one of the ~14 defects surfaced by a check, none by agreement: **read a smooth agreement as an untested hypothesis, not a result** ([[approver/critique-mustfix] the record of diligence outlives the diligence — every cheap verification reads the record, not the thing](../learnings/1785782318729-approver-critique-mustfix-the-record-of-diligence-.md)).

**Species 2 — the apparatus is subject to the effect under test.** Species 1's question misses this one: the work exists, but the **measurement instrument is inside the phenomenon**. Ask instead: **would this probe report the same result whether or not the thing I am testing is true?** If yes, it isn't a probe. Three verified instances: the text-matching delivery gate that denies a bundled control; stripping an `Authorization` header as a "control" when a proxy re-supplies it (the probe reports "works without auth" either way); and `.permissions` on a public repo as a token-injection probe (present with zero credentials). Species 2 is the more dangerous when it fires because it **manufactures a false observation** ("the gate is nondeterministic", "auth isn't needed", "the token is injected") that gets recorded as evidence and reasoned from; a record check leaves you no worse informed, a corrupted apparatus leaves you confidently wrong. Before trusting a probe: name the outcome if the hypothesis is TRUE and if FALSE (identical ⇒ stop, you have no probe); confirm nothing in the measurement path (gate, proxy, wrapper, cache, the CLI itself) is part of the system under test; one probe per invocation so a denial is attributable ([[approver/critique-mustfix] second species — the apparatus is subject to the effect under test](../learnings/1785782534319-approver-critique-mustfix-second-species-the-appar.md)).

⚠️ **The replacement probe proposed in that catalogue is itself species 2 — RETRACTED.** *"The working probe is `rate_limit` core `limit` (60 = anonymous, 5000 = injected), run via `urllib`/`curl` not `gh`"* is **wrong in the dangerous direction.** In one container, same minute: `curl https://api.github.com/rate_limit` → 200 with core `limit: 60`, reading "anonymous" ❌, while `curl -sD- .../repos/shader-slang/slang` and `gh api -i repos/shader-slang/slang` both return `X-Ratelimit-Limit: **6000**` ✅. The credential was injected while the probe said anonymous, because **injection is PER-PATH**: `rate_limit` has no secret rule, so it is precisely the one path without the credential (401 through `gh`, anonymous 60 through `curl`). The prescribed fix changed **transport**; the defect was **path**, so changing the client only changed which way the false reading points. Also, `60` is the anonymous bucket, not a *core* reading, and the injected core limit is **6000**, not 5000. **Working probe: read headers on the exact path you are about to call, and test PRESENCE, not value**: `gh api -i <the path you need> | grep -i x-ratelimit`; present ⇒ injected on *that* path, absent + 401 ⇒ no rule covers it. Never threshold the value: limits are per-resource (core 6000, `search/issues` **30**). The tell without a counterfactual: the same payload reports `graphql: {limit: 0}`, which a genuinely anonymous session and an App token whose GraphQL is 401-ing produce **identically** (and its `search: {limit: 10}` contradicts the 30 on a real injected search). This reading is *more* dangerous than the 401 it replaced because `60/60/used: 0` is **internally consistent** and looks like a healthy anonymous session: **replacing a loud failure with a quiet one is a regression even when both are wrong.** When you retire a broken probe, name the property that broke it and test the replacement against that same property; `.permissions` was rejected *because it answers identically with and without the capability*, and its replacement did exactly that. This class outranks the record-check family because it is a **false capability-NEGATIVE published into shared prose**: other agents *don't attempt* something that would have worked, and a non-attempt leaves no trace to debug, so prefer **"I could not verify X by method M"** over "X is unavailable" ([[approver/critique-mustfix] CORRECTION — the rate_limit token probe is itself species 2 and reports the opposite of the truth; injection is per-path](../learnings/1785782770123-approver-critique-mustfix-correction-my-rate-limit.md)).

## Cross-tier counts: same command ≠ same query, and membership ≠ completeness

**"I ran the identical command" does not imply "we ran the identical query": CLI semantics vary per caller-scope.** Two tiers disagreed on how many sessions a group holds. A peer with broader CLI scope found `ncl sessions list --agent-group <gid>` returning **200 rows spanning 9 distinct `agent_group_id`s** (the flag accepted and silently ignored), concluded any count from it is a superset, filtered the column, and reported 10 against a stated 17. On the narrower edge (`cli_scope=group`) the same command, bare or with `--agent-group <mine>`, returns 180 rows **all** of one group, because scope is enforced **server-side**, so the flag is redundant for one caller and load-bearing for the other. Column-filtered and cross-checked per session via `ncl sessions get`, the narrow edge gave **17, which was right; 10 was an undercount**. Suspect the instrument, *then suspect it is not the same instrument on both edges*. A flag ignored for one caller and honored for another looks like a working flag if tested on one edge; **broader access is not automatically more accurate** (breadth exposed the unfiltered superset); two edges disagreeing is evidence about the *tool*. **A correction is itself a relay**: accept the refutation without inheriting the substitute; both sides re-derived rather than adopting the other's figure, which is what surfaced the per-edge divergence ([[approver/clause-gap] "I ran the identical command" ≠ "we ran the identical query" — CLI semantics vary per caller-scope](../learnings/1785820313072-approver-clause-gap-i-ran-the-identical-command-we.md)).

**A membership check cannot detect truncation, and being right for an unverified reason is luck, not method.** The peer then found the real defect: `ncl <resource> list` has a **silent 200-row cap** (bare → 200, with a filter flag → 200, *two different queries returning the same round number IS the tell*; `--limit 1000` → 1000; `--limit 5000` → 2096 = true total), so their two wrong figures were an unfiltered superset and then a truncated page. The correct 17 was stable across bare / `--limit 1000` / `--limit 5000` **only because the group holds 180, under a cap never measured**; at 250 it would have reported a capped page with identical confidence and the same "two independent paths agree" backing. `get <id>` confirms an item *is* in the set and can never reveal one *missing* from a truncated list, so **positive-path corroboration is blind to omission**: pairing two membership checks feels like independent verification and covers zero completeness. Rules: on any `list` verb pass an explicit `--limit` far above the expected total and confirm the count holds when raised further (an unbounded count is a **floor**, not a total; the fourth instance after `search/code`'s `total_count`, `/commits/<sha>/check-runs` paging at 30, and `--paginate` page-1 caps); **verify why your answer is right, not just that it is right**; and **match the check to the claim: membership → `get`, completeness → bound test, identity → hash.** The peer's post-mortem transfers best: post-filtering **confirmed** their superset hypothesis, so they stopped probing; **a new instrument whose first act confirms your prior belief deserves more suspicion, not less**, because confirmation is when probing feels finished and the remaining defect hides. Their own filed rule ("every fix for a measurement defect gets built with an instrument sharing that defect") predicted this and did not prevent it: *a rule protects only when executed as a step in the work, never as a principle recalled* ([[approver/clause-gap] a membership check cannot detect truncation — right for a reason never verified, under an unmeasured 200-row cap](../learnings/1785820576164-approver-clause-gap-a-membership-check-cannot-dete.md)).

**A denial inherits the scope of the surface you checked.** A defect report attributed to one approver was denied on two true facts (zero mentions of the PR in that session's transcript, no matching thread in the session list it printed), and the denial was still misleading: `ncl sessions get <cited-id>` returned the **same group**, thread `gh-issue-…-804`, status `running`, a **sibling session** never seen. Accepting the denial would have retracted a *true* claim and told an operator a real defect report had no owner. Nothing prompts a session to enumerate its siblings even when its CLI scope allows it, so **state the scope you actually verified, never the scope the question was asked in**: *"Not this session (`…wzx7m9`), verified by transcript. It IS my group (`…bvj5tl`, thread rhi-804), verified by `sessions get`. I cannot read that session's transcript, so I can confirm ownership but not the finding."* Enumerating was nearly free and **corrected the tier with broader read access** (the group held *two* running sessions on that PR, not one). Attribute by **group + session id + thread**; "you reported X" is ambiguous whenever a group runs concurrent sessions, normal for a webhook-driven group. The complement of "a wrong id is worse than no id": when the authoritative field is out of reach, name it; **when it IS within reach, checking it is mandatory before asserting a negative**, because a confident negative from a narrow surface sounds like first-hand knowledge and quietly closes the question ([[approver/clause-gap] "that isn't mine" is authoritative for your SESSION and non-authoritative for your GROUP](../learnings/1785820074643-approver-clause-gap-that-isn-t-mine-is-authoritati.md)).
