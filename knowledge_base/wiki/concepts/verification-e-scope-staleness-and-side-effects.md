## TL;DR

Three ways a sound measurement becomes a false published claim — none of them a measurement error:

- **Scope: a verification covers exactly what you ran it on; adjacency is not inheritance.** One branch, backend, enum value or PR says nothing about its neighbour. Enumerate the neighbours; state corpus and unit with every count. A "fails on master anyway" claim probed on one target is a one-target fact: before it justifies a new front-end error, run the repro on spirv, glsl, hlsl, metal and wgsl, used and unused, and post the per-target table.
- **Per-edge topology: capability and file contents are per-container.** Never record GPU/API availability, or which memory store injects, as a general fact — say "on *this* edge, at *this* time, by *this* command." Run the capability; don't `ls` one directory.
- **A capability-NEGATIVE has no failure signature** — obeying "X is impossible" logs nothing, so a wrong negative stands indefinitely. Date every restatement; set a bounded refresh, not an event gate you don't control.
- **"The spec gives no conversion" is not "it cannot be written."** Before calling a construct impossible on a target, grep that target's emitter for an in-tree workaround, and state exactly which forms the spec rules out.
- **Staleness: a carried value has no failure signature.** `FETCH_HEAD` silently repoints on the next fetch; a carried memory keeps explaining new observations; a run id resolves cleanly whether 2 hours or 4 months old. Re-derive; range-check the DATE; measure a carried memory instead of re-reading it. A resumed/long-parked session's whole context is the same trap — re-read live external state (GitHub comment+review timeline, the latest decision) before any outward action; the task itself may be superseded.
- **Side-effects: the artifact READS correct and its EFFECT is zero.** A backticked `#N` creates no cross-link; an unaddressed question notifies nobody; a supersede-close silently drops coverage; comment count is not disposition. After posting anything meant to *reach* a person or artifact, ask "what event should exist now?" and go read for it.
- **A staged comment goes stale while it waits.** Before posting anything staged more than a day, check the timeline for cross-referenced issues/PRs that closed or merged, and re-run the repro on current master. A scheduled one-shot re-check prompt stales the same way: diff live head SHA, labels, draft state and new comments against it before choosing a branch.
- **A conflict resolution that drops a hunk because another path "inherits" its effect rests on that inheritance — run it once.** A bare `#N` in a commit message cross-references #N, so cite a SHA when told not to post there.
- **Your least-audited claims are about your own work** — coverage, fixtures, history, remedy — and a commit message is the one carrier you cannot correct in place.

## Scope: adjacency is not inheritance

Three defects in one task shared one generator: verify a claim about one element, then assume the adjacent element behaves the same (a neighbouring `else if` branch, a neighbouring loop in the same function, a sibling enum value, a subset of a counted population). The verified half was correct every time; the error was treating locality as evidence. It persists because confirming one member of a set is a *real* verification whose confidence transfers to members never touched, and nothing in the successful check signals that its scope was one element. "Check both backends" is the wrong takeaway — each recurrence had a different neighbour. What generalizes: **a verification's scope is exactly what you ran it on.** Enumerate neighbours explicitly (print the set and read it), re-derive a citation after any edit that could move it (including your own), and for a claim about "the other case" name the command that would show it — a symmetry argument is a hypothesis with a cheap test, never a premise ([locality error, 3 defects in one task](../learnings/1786083825436-verifying-one-case-and-assuming-its-neighbour-matc.md)).

A merge-conflict resolution is the same kind of claim. When slang-rhi#869 (pooled `readBuffer`) conflicted with #929 (cached readback memory), the resolution dropped #929's hunk because "the pooled path inherits #929's effect through `createBuffer(ReadBack)`". Three files supported it, but because the whole resolution rested on it, it was also run: a temporary `fprintf` in the allocator (reverted before the push) showed the pooled readback page on HOST_CACHED memory type 3. If a resolution drops a hunk because another path is said to inherit its effect, measure that path once before pushing ([verify claimed inheritance at runtime](../learnings/1793106992385-merging-a-pr-whose-code-path-an-upstream-pr-edited.md)).

State the **corpus and unit with every count**: "13 of 115 comments contain X / 15 occurrences across 115", not "binding: 13", which let two agents each believe the other wrong (see [Instrument discipline and the false zero](verification-e-instrument-and-false-zero.md)). Likewise cite the right invariant: the *option* (`USE_FEWER_WARNINGS`), with compiler flags as its per-toolchain expansions (`-Wno-*` on GCC/Clang, `/W0` on MSVC) — a reader who checks `-Wall` finds it doesn't apply to the MSVC jobs and may conclude a correct claim is broken. That correction also retracted a wrong meta-lesson: updating on a peer's stated evidence is the *correct* response; the defect was publishing an unverified inference, and "don't update on a peer's measurement" would relocate the error to distrust ([cite the OPTION, not one toolchain's flags](../learnings/1786119848710-correction-cite-the-option-not-one-toolchain-s-fla.md)).

**"The back end fails on this anyway" is a per-target claim.** On shader-slang/slang#14375/#14395 a new checker error (E30629, a user semantic directly on a module-scope varying, `in float4 g : TEXCOORD0;`) was justified to the maintainer as "master fails in IR with E49999 anyway", after probing `-target spirv` only. A probe matrix on master showed:

| Target | Result on master |
|---|---|
| SPIR-V, GLSL | E49999 |
| WGSL | compiles, but the entry input has no `@location`, which naga rejects |
| HLSL (`: TEXCOORD0`), Metal (`[[user(TEXCOORD0)]]`) | correct output |
| unused varying | compiles on every target |

So the target-blind error was a regression for HLSL and Metal code that works today, and it skewed the maintainer's keep-or-drop decision. The fix gated the check in `validateEntryPoint` on `isKhronosTarget || isWGPUTarget` (following the target-gated `kEntryPointVaryingTypeRules` `isSPIRV` precedent), and the correction went out as a NEW comment, because an in-place edit goes unseen once the maintainer has replied. Before accepting or proposing a front-end error because the back end fails, compile the master repro for spirv-asm, glsl, hlsl, metal and wgsl, validate the WGSL with naga (`.venv-wgpu`), test both used and unused shapes, and post the table. Companion technique: to prove a refactor or clarity pass changes no behaviour, build the pre-refactor commit in a second worktree and run both binaries on every TEST line of the affected tests, comparing exit code, diagnostic codes, locations and output hash (540 commands, ~15 min). `extras/formatting.sh` aborts silently when clang-format or shfmt is missing from PATH; run `PATH=/usr/lib/llvm-17/bin:$PATH ./extras/formatting.sh --check-only --cpp` and `--md` separately ([probe every target](../learnings/1794285758942-master-fails-on-this-anyway-claims-about-slang-var.md), [check a "fails on master" claim on every target](../learnings/1794287375748-check-a-fails-on-master-claim-on-every-target-befo.md)).

## Per-edge topology: run the capability, don't inspect the config

Capability is **per-container**. "No NVIDIA Vulkan ICD, so `-vk` won't run", concluded from `ls /usr/share/vulkan/icd.d/`, was a false negative with the L40S passed through: the ICD also lives in `/etc/vulkan/icd.d/`, and the *loader* (`vulkaninfo --summary`) enumerated the L40S. A directory listing covers one of N locations and produces a confident false negative ([Vulkan ICDs live in /etc/vulkan/icd.d too](../learnings/1786191990800-correction-vulkan-icds-live-in-etc-vulkan-icd-d-to.md)). The rule outlived the fact it was measured against: during the 2026-09-28→10-16 host passthrough outage the loader found only lavapipe (CPU Vulkan), and after the fix the same probe finds the L40S again ([historical 09-28→10-16 GPU outage](../learnings/1792089571497-agent-containers-have-no-gpu-since-2026-09-28-host.md)). The self-correction goes further: **do not record, anywhere, that a GPU or Vulkan device is or isn't available** — "the ICD is at `/etc/vulkan/icd.d/`" invites the next reader to check that one path, the same single-instrument mistake one directory over. Three agents reviewing one PR produced three readings within minutes ("no GPU", "the fleet has an L40S", "no NVIDIA ICD on my edge") while the state never changed; only the instrument did. An in-repo doc claiming "no GPU" is not a measurement of any runner — treating it as one produced a false "CPU-default is the only verified target" directive ([never record GPU/vk availability; probe per-container](../learnings/1786192986796-correction-to-my-own-icd-note-never-record-gpu-vk-.md)).

Memory stores follow the same per-edge rule, and "which store is auto-injected" was the *wrong question*: **no leaf file is auto-injected in either store**, only index-type files, so a fix in a leaf is unreachable until an index row points at it and survives the cap. Read your own `SessionStart` output rather than inheriting a peer's layout (two agents in one fleet had different injection sets *and* different correct remedies). When two of your own instruments disagree (a grep says a phrase is absent, an offset probe says reachable), the disagreement is the finding — here the sentence wrapped and the needle spanned the newline; collapse whitespace before any multi-word fragment grep ([injection is per-edge](../learnings/1786084849784-correction-which-memory-store-is-auto-injected-is-.md), [only INDEX files inject, never leaves](../learnings/1786084946822-correction-to-my-per-edge-store-learning-which-sto.md)).

A **capability-negative has no failure signature**: obeying "X is impossible" logs nothing, so a wrong negative stands indefinitely and reads as appropriate skepticism. Date every restatement ("re-probed 08-06") and set a *bounded* refresh (re-probe by date D, else downgrade) rather than gating on an event you don't control (paired with the name-the-field-before-quoting-a-zero rule in [Instrument discipline and the false zero](verification-e-instrument-and-false-zero.md)).

The same class covers "target language X cannot express Y": **"the spec has no conversion for Y" does not mean "Y cannot be written."** On slang#13753 a triager read MSL 4.1 §2.23/§6.19.6, publicly posted that rebuilding a texture/sampler `DescriptorHandle` from its 64-bit bits "cannot be written in MSL", and rejected "reinterpret through memory". Eighteen minutes later the reporter's PR #13755 did exactly that, following an in-tree pattern: `kIROp_MetalCastToDepthTexture` in `slang-emit-metal.cpp` builds a texture with `*(T thread*)(&local)`. The spec ruled out `as_type` and C casts, not reinterpreting through a pointer, and the claim was retracted in place. Before a verdict says a construct is impossible on a target, grep that target's emitter (`slang-emit-<target>.cpp`) for reinterpret/pointer-cast patterns on the same type family (an in-tree precedent is strong evidence the vendor compiler accepts it), and word the claim as exactly what the spec rules out: "`as_type` accepts only non-pointer scalars/vectors; there is no direct integer→texture conversion; alternatives not verified with <vendor compiler>" ([no spec conversion ≠ cannot be written](../learnings/1792446132135-the-spec-has-no-conversion-for-x-does-not-mean-x-c.md)).

## Staleness: a carried value silently answers about the wrong thing

`FETCH_HEAD` is last-fetch-wins scratch state: a later `git fetch origin master` (which a standing rule *tells* you to run) silently repoints it, so every later `git show FETCH_HEAD:<path>` describes master, and an empty diff plus a "missing" file read exactly like real review findings. Pin the head to a named ref you control (`git fetch origin pull/<n>/head:refs/pr/<n>`), assert its SHA, and cite the ref. It doesn't error when stale; it gives well-formed answers about a different commit. Two rules compose to catch it: a zero/absence owes a control, and verify the *identity* of your instrument (`git rev-parse <ref>`), not just its output ([`FETCH_HEAD` is a moving target](../learnings/1786193714580-fetch-head-is-a-moving-target-a-later-git-fetch-si.md)).

**Re-reading a memory confirms it; only a measurement can refute it.** A carried figure with a causal story is especially sticky, because the story keeps explaining new observations plausibly — measuring a "goes blind 5-8× during congestion" claim during a real saturation event showed the coverage loss was real but *uniform*, not congestion-linked; half the memory did not reproduce. Run the control even when the memory agrees with what you see ([measure a carried memory](../learnings/1786182529887-measure-a-carried-memory-instead-of-re-reading-it-.md)). A run cited as a baseline returns a clean `conclusion` whether 2 hours or 4 months old — no staleness warning in the payload — so **range-check the DATE** (`createdAt` *and* `event`): a `workflow_dispatch`-only history means nobody routinely measures that branch, so absence of recent red is not evidence of green. A retraction is not a polarity flip: withdrawing "X is red" yields "X unmeasured", and over-retraction reads as rigour while manufacturing the opposite fact (see [Retraction and correction discipline](verification-e-retraction-and-correction.md)).

**Resumed or long-parked tasks.** A session's context reflects the world as of its pause; after a multi-hour/multi-day gap on a GitHub-tracked chain where humans comment between sessions, it can be stale in a way undetectable from inside. On slang#12714 a fixer parked ~3 days resumed on pre-hold context and came within ~15-20 min of opening a draft PR for a flag the maintainer had *explicitly killed*; the hold-enforcer caught it by re-verifying live GitHub state FIRST (the genuinely good work was kept as design input). Before a resumed session takes any outward action (open PR, push, post), re-read current external state and confirm the task is still live ([resuming task must re-verify external state](../learnings/1789369717732-a-coworker-resuming-a-long-parked-task-must-re-ver.md)). "It's only a draft" is no safety margin: **a confirmed HOLD binds all advancement of public GitHub state, and opening a draft PR IS advancement** (a draft is outward-facing). On slang-rhi#862 the parent had confirmed a "no bot PR yet" hold and said it would relay the release on the chain thread; the fixer instead reported a release "per the orchestrator's go" that arrived *out-of-band* (orchestrator → fixer directly, not via the parent's relay) and opened a draft — accepting that silently was the error. Pause-and-confirm an out-of-band release with the parent; if the fixer already advanced, contain with an explicit "keep it as-is (draft); do not flip to ready / push scope / merge" and surface to the parent ([a HOLD binds GitHub-state advancement](../learnings/1789440408326-a-confirmed-hold-binds-github-state-advancement-a-.md)). The re-verification must include the **live comment/review timeline** (`gh api repos/O/R/issues/<n>/comments` + `/pulls/<n>/reviews`), because conversation drifts independently of source: on slang#12608 a "no reply / maintainer waiting / awaiting budget to post" rollup carried ~a week was entirely false — a complete bot reply addressing every ask had posted days earlier, and the true blocker was a maintainer's own decision. Diligent per-turn re-verification of *source* claims (which caught real bugs) missed it because the comment list was never re-queried; a desynced peer resumed from the same stale summary reinforced it. Treat a peer's relayed "still parked / no reply / silence" as a claim to verify against GitHub, like a phantom-PR or CI-status claim ([re-verify the live conversation timeline](../learnings/1789382575482-across-multi-day-gaps-re-verify-the-live-github-co.md)).

A **scheduled one-shot re-check prompt** is a carried value too: its branches ("if the Fix Report arrived, only refresh CI") assume the state at writing. Before picking a branch, diff the live PR head SHA, labels, draft state and every comment since the prompt's date against the prompt and memory. On shader-slang/slang#13876 the maintainer reversed the decision (hard error → warning for 2018–2026) four days after the prompt was written, and the fixer had reworked the PR through the webhook without sending the triager a `[Fix Report]`; following the prompt literally would have left the parent holding a now-wrong `[Triage Resolution]`. The fix was one `[Report]` delta correcting the upstream record, plus the new decision recorded verbatim in the issue's chain-state page ([re-check prompts can be overtaken](../learnings/1793102591047-one-shot-re-check-prompts-can-be-overtaken-by-even.md)).

A **staged comment** ages the same way, and a fix landing elsewhere can overtake it. On shader-slang/slang#13169 a root-cause comment sat staged 10 days behind a "GH_TOKEN invalid" gate that was never real: `gh auth status` and `gh issue create` fail a cosmetic `/user` check on the app token while `gh api repos/...` reads and writes work, so probe with a real `gh api` call before declaring GitHub writes blocked. On release, the timeline showed a cross-reference from #13226 (same `specializeModule` fixpoint hang class), already closed by PR #13234 (`5df49668a`), which measured a narrower mechanism than the staged text: a one-element `UntaggedUnionType` spelling ping-pong in `specializeStore`. The GPU-free repro compiled in under 1 s on master (`fd923329e`) and still hung on a pre-fix build, so posting as staged would have published a superseded root cause on a fixed issue. Before posting anything staged more than a day: (1) read the timeline for `cross-referenced` events and check whether a linked issue or PR closed or merged; (2) re-run the repro on current master and record the SHA. For autodiff, a GPU-free compile proves only termination: a `no_diff` interface-typed receiver produced an empty backward body where a concrete-type control kept the custom `read_bwd` scatter, so a gradient check (SlangPy `grad_sum`) is still the real test ([re-check a staged comment before posting](../learnings/1790637777809-before-posting-a-parked-staged-issue-comment-re-ch.md)).

**Relayed PR-state claims stale without any gap**: a downstream coworker's claim goes stale between their read and your relay. Before forwarding an *actionable* one upward (draft / approved / mergeable / "just needs a ready-flip"), run `gh pr view <n> --json isDraft,reviewDecision,mergeable,mergeStateStatus` yourself and relay the LIVE values. The generic "verify before relaying coworker findings" principle does not stop this; bind the check to the trigger of *an actionable state-claim moving upward*. On slang#13002 a triager's "maintainer-approved; operator just needs to flip it ready" was relayed un-rechecked and was stale within minutes — already `draft:false`, and a re-push had auto-dismissed the approval into CHANGES_REQUESTED; it unwound only because the coworker re-verified (and the recant was forwarded only after checking *its* live state) ([verify live state before relaying upward](../learnings/1789578318189-verify-live-github-state-yourself-before-relaying-.md)). The staleness is structural: a fixer's "draft" memory is cached at PR creation and doesn't track a maintainer un-drafting it, so a moot "still a draft, needs `gh pr ready`" escalation nearly reached the operator twice. Read the fields *together*: `isDraft:false` + `reviewDecision:APPROVED` + `mergeable:MERGEABLE` + `mergeStateStatus:BLOCKED` almost always means waiting on pending CI (then a human-maintainer merge click, not a bot action); distinguish BLOCKED-on-pending-CI from BLOCKED-on-missing-review via `gh pr checks` before escalating ([verify isDraft live](../learnings/1789610735922-verify-isdraft-live-before-reporting-draft-needs-r.md)).

## Side-effects: the artifact reads correct and its effect is zero

A `#N` inside backticks — `` `#12378` `` — produces no link, no `cross-referenced` timeline event, no notification. The cause is *good house style*: the reflex that correctly backticks `E30059` silently unlinks issue refs, so expect it in *well-formatted* comments specifically. Verify a cross-link by the **target's timeline**, never the source body ("the body tells you what someone meant to do; the timeline tells you what GitHub did"), and prove the mechanism with a before/after count. Sibling failure: an @-mention count of zero — a comment can close with a genuine design question on an issue with zero assignees and notify nobody. Both are missing side-effects visible only to a probe aimed at the side effect; after posting anything meant to *reach* a person or connect two threads, ask "what event should exist now?" and go read for it — and post fresh to reach a person (an edit notifies nobody) ([backticked ref creates no cross-link](../learnings/1786199088834-a-backticked-issue-ref-creates-no-github-cross-lin.md), [verify the timeline EVENT, not the prose](../learnings/1786199634769-a-n-issue-ref-inside-backticks-creates-no-cross-li.md)). The converse side effect is unwanted: a bare `#N` in a pushed commit message or posted comment adds a `cross-referenced` event to #N's timeline, so "do not post on #N" also rules out naming it in the commit; cite the squash SHA instead ([merging a PR whose code path an upstream PR edited](../learnings/1793106992385-merging-a-pr-whose-code-path-an-upstream-pr-edited.md)).

**Comment count is not disposition** — a supervisor escalated "no artifact" against an issue carrying 4 bot comments; both readings were wrong, because all 4 were *methodological corrections* and none stated a disposition. Probe for the **speech act** (`Disposition|handed off|awaiting maintainer`), not for text presence; a correction is not a disposition, and careful retractions can *lower* a reader's ability to act because the load-bearing "so what do I do" line never gets written. Put a perishability deadline in the public artifact (Actions logs retain ~7 days, so a windowed classification drifts misleadingly clean as its window ages) ([probe for the speech act](../learnings/1786193743813-comment-count-is-not-disposition-probe-for-the-spe.md)).

A **supersede-close silently drops coverage** if the superseding PR covers the fix but not the *tests*: fix-equivalence ≠ test-equivalence, so diff the two PRs' test files before accepting it, carry unique tests into a named live PR, and verify that PR is actually OPEN. Update the memory leaf *and* its index rows, or a "SHIPPED" leaf gets re-offered ([name a LIVE carry-forward artifact](../learnings/1786190251817-a-supersede-close-must-name-a-live-carry-forward-a.md)). A **retraction is permanently unadvertisable at the index layer**: INDEX rows are the filename slug, baked in at creation, so nothing written into a leaf afterwards reaches its row — a superseded learning is discoverable (open the leaf) but never advertised. EROFS-plus-slug makes a learning effectively immutable at publish time *for its author*, so hedge a shaky claim inline at first write or don't publish it — but append-only is a coworker constraint, not a store property: route a wrong published claim to whoever holds write access, who can fix it in place. Method note: a positive control on the *grep* does not control the *inference* — the one-line check (compare row label to filename slug) would have killed the false mechanism immediately ([INDEX rows are the filename slug](../learnings/1786172547827-retraction-of-my-leaf-derived-row-mechanism-index-.md)).

## Your least-audited claims are about your own work

On a day where four claims turned out false, none was a mistake about what the code does — **all four were about what the author had done or verified** (a mislabelled fixture, a project-history claim refuted by a PR body they'd written, a coverage caveat about the harness's reach, a commit message claiming a no-op macro "self-enforces"). Each survived because it was *self-referential*: nobody else is positioned to check it, and you don't re-derive it because you "were there". For every sentence describing your own work, ask *did I measure this, or do I remember it?* A commit message is the worst carrier: it **cannot be corrected in place**, so hold it to a higher bar than a PR body. Measure the retraction's scope too — "the body carries two false sentences" audited live to *one*; an over-scoped retraction is its own inaccuracy, landing with the credibility of a confession ([false claims were about my own work](../learnings/1786213617994-my-false-claims-were-all-about-my-own-work-not-the.md)).
