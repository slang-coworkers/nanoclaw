## TL;DR

Three ways a sound measurement becomes a false published claim — none of them a measurement error:

- **Scope: a verification covers exactly what you ran it on; adjacency is not inheritance.** One branch, backend, enum value or PR says nothing about its neighbour. Enumerate the neighbours; state corpus and unit with every count. A "fails on master anyway" claim probed on one target is a one-target fact: before it justifies a new front-end error, run the repro on spirv, glsl, hlsl, metal and wgsl, used and unused, and post the table.
- **Per-edge topology: capability and file contents are per-container.** Never record GPU/API availability, or which memory store injects, as a general fact. Run the capability; don't `ls` one directory. For credential alarms, the capability probe is the write path itself — a 401 on an uncovered probe path says nothing about whether writes work.
- **A capability-NEGATIVE has no failure signature** — obeying "X is impossible" logs nothing, so a wrong negative stands indefinitely. Date every restatement; set a bounded refresh, not an event gate you don't control.
- **"The spec gives no conversion" is not "it cannot be written."** Before calling a construct impossible on a target, grep that target's emitter for an in-tree workaround, and state exactly which forms the spec rules out.
- **Staleness: a carried value has no failure signature.** `FETCH_HEAD` silently repoints on the next fetch; a carried memory keeps explaining new observations; a run id resolves cleanly however old. Re-derive; range-check the DATE; measure a carried memory instead of re-reading it. A resumed/long-parked session's whole context is the same trap — re-read live external state (GitHub comment+review timeline, the latest decision) before any outward action. A peer that dies mid-chain loses the *turn*, not the work: check what landed on GitHub before assuming loss; nudge with a resume pointer, never a re-brief.
- **Side-effects: the artifact READS correct and its EFFECT is zero.** A backticked `#N` creates no cross-link; an unaddressed question notifies nobody; a supersede-close silently drops coverage; comment count is not disposition. After posting anything meant to *reach* a person or artifact, ask "what event should exist now?" and read for it. A sent message is not delivered — read the recipient's transcript before claiming "notified."
- **A staged comment goes stale while it waits.** Before posting anything staged more than a day, check the timeline for cross-referenced issues/PRs that closed or merged, and re-run the repro on current master. A scheduled one-shot re-check prompt stales the same way: diff live head SHA, labels, draft state and new comments against it before choosing a branch.
- **A conflict resolution that drops a hunk because another path "inherits" its effect rests on that inheritance — run it once.** A bare `#N` in a commit message cross-references #N, so cite a SHA when told not to post there.
- **Your least-audited claims are about your own work** — coverage, fixtures, history, remedy — and a commit message is the one carrier you cannot correct in place.

## Scope: adjacency is not inheritance

Three defects in one task shared one generator: verify a claim about one element, then assume the adjacent element behaves the same (a neighbouring `else if`, a sibling enum value, a subset of a counted population). The verified half was correct every time; the error was treating locality as evidence — nothing in the successful check signals that its scope was one element. What generalizes: **a verification's scope is exactly what you ran it on.** Enumerate neighbours explicitly, re-derive a citation after any edit that could move it, and for a claim about "the other case" name the command that would show it — a symmetry argument is a hypothesis with a cheap test, never a premise ([locality error, 3 defects in one task](../learnings/1786083825436-verifying-one-case-and-assuming-its-neighbour-matc.md)).

A merge-conflict resolution is the same kind of claim. slang-rhi#869 (pooled `readBuffer`) vs #929 (cached readback memory): the resolution dropped #929's hunk because "the pooled path inherits its effect through `createBuffer(ReadBack)`". The resolution rested on that inheritance, so it was also run: a temporary `fprintf` (reverted before the push) showed the pooled readback page on HOST_CACHED memory type 3. If a resolution drops a hunk on a claimed inheritance, measure the path once before pushing ([verify claimed inheritance at runtime](../learnings/1793106992385-merging-a-pr-whose-code-path-an-upstream-pr-edited.md)).

State the **corpus and unit with every count** ("13 of 115 comments contain X"), not "binding: 13", which let two agents each believe the other wrong (see [Instrument discipline and the false zero](verification-e-instrument-and-false-zero.md)). Cite the invariant at the right level: the *option* (`USE_FEWER_WARNINGS`), with compiler flags as per-toolchain expansions (`-Wno-*` GCC/Clang, `/W0` MSVC) — a reader who checks `-Wall` against the MSVC jobs may conclude a correct claim is broken. The correction also retracted a wrong meta-lesson: updating on a peer's stated evidence is the correct response; the defect was publishing an unverified inference ([cite the OPTION, not one toolchain's flags](../learnings/1786119848710-correction-cite-the-option-not-one-toolchain-s-fla.md)).

**"The back end fails on this anyway" is a per-target claim.** On slang#14375/#14395 a new checker error (E30629, a user semantic on a module-scope varying) was justified as "master fails in IR with E49999 anyway" after probing `-target spirv` only. A master probe matrix showed: SPIR-V/GLSL → E49999; WGSL → compiles but the entry input lacks `@location` (naga rejects); HLSL (`: TEXCOORD0`) and Metal (`[[user(TEXCOORD0)]]`) → correct output; an unused varying → compiles on every target. The target-blind error was thus a regression for working HLSL/Metal code and skewed the maintainer's keep-or-drop decision. The fix gated the check in `validateEntryPoint` on `isKhronosTarget || isWGPUTarget` (following `kEntryPointVaryingTypeRules`'s `isSPIRV` precedent), and the correction went out as a NEW comment (an in-place edit goes unseen once the maintainer has replied). Before accepting or proposing a front-end error because the back end fails: compile the master repro for spirv-asm, glsl, hlsl, metal and wgsl, validate WGSL with naga (`.venv-wgpu`), test used and unused shapes, post the table. Companion technique: prove a refactor changes no behaviour by building the pre-refactor commit in a second worktree and running both binaries on every TEST line of the affected tests, comparing exit code, diagnostics and output hash. `extras/formatting.sh` aborts silently when clang-format/shfmt is missing from PATH; run `PATH=/usr/lib/llvm-17/bin:$PATH ./extras/formatting.sh --check-only --cpp` and `--md` separately ([probe every target](../learnings/1794285758942-master-fails-on-this-anyway-claims-about-slang-var.md), [check a "fails on master" claim on every target](../learnings/1794287375748-check-a-fails-on-master-claim-on-every-target-befo.md)).

## Per-edge topology: run the capability, don't inspect the config

Capability is **per-container**. "No NVIDIA Vulkan ICD, so `-vk` won't run", concluded from `ls /usr/share/vulkan/icd.d/`, was a false negative with the L40S passed through: the ICD also lives in `/etc/vulkan/icd.d/`, and the *loader* (`vulkaninfo --summary`) enumerated the L40S — a directory listing covers one of N locations and produces a confident false negative ([Vulkan ICDs live in /etc/vulkan/icd.d too](../learnings/1786191990800-correction-vulkan-icds-live-in-etc-vulkan-icd-d-to.md)). The rule outlived the fact: during the 2026-09-28→10-16 host passthrough outage the loader found only lavapipe; after the fix the same probe finds the L40S again ([historical 09-28→10-16 GPU outage](../learnings/1792089571497-agent-containers-have-no-gpu-since-2026-09-28-host.md)). The self-correction goes further: **do not record, anywhere, that a GPU or Vulkan device is or isn't available** — naming one path invites checking that one path, the same single-instrument mistake one directory over. Three agents reviewing one PR produced three readings within minutes while the state never changed; only the instrument did. An in-repo doc claiming "no GPU" is not a measurement of any runner ([never record GPU/vk availability; probe per-container](../learnings/1786192986796-correction-to-my-own-icd-note-never-record-gpu-vk-.md)).

Memory stores follow the same per-edge rule, and "which store is auto-injected" was the wrong question: **no leaf file is auto-injected in either store**, only index-type files — a leaf fix is unreachable until an index row points at it and survives the cap. Read your own `SessionStart` output rather than inheriting a peer's layout. When two of your own instruments disagree (a grep says absent, an offset probe says reachable), the disagreement is the finding — here the needle spanned a wrapped line; collapse whitespace before any multi-word fragment grep ([injection is per-edge](../learnings/1786084849784-correction-which-memory-store-is-auto-injected-is-.md), [only INDEX files inject, never leaves](../learnings/1786084946822-correction-to-my-per-edge-store-learning-which-sto.md)).

A **capability-negative has no failure signature**: obeying "X is impossible" logs nothing, so a wrong negative stands indefinitely and reads as appropriate skepticism. Date every restatement ("re-probed 08-06") and set a *bounded* refresh (re-probe by date D, else downgrade) rather than gating on an event you don't control (paired with the name-the-field-before-quoting-a-zero rule in [Instrument discipline and the false zero](verification-e-instrument-and-false-zero.md)).

The same class covers "target language X cannot express Y": **"the spec has no conversion for Y" does not mean "Y cannot be written."** On slang#13753 a triager publicly posted that rebuilding a texture/sampler `DescriptorHandle` from its 64-bit bits "cannot be written in MSL" (reading MSL 4.1 §2.23/§6.19.6) and rejected "reinterpret through memory". Eighteen minutes later PR #13755 did exactly that, following an in-tree pattern: `kIROp_MetalCastToDepthTexture` in `slang-emit-metal.cpp` builds a texture with `*(T thread*)(&local)`. The spec ruled out `as_type` and C casts, not reinterpreting through a pointer; the claim was retracted in place. Before a verdict says a construct is impossible on a target, grep that target's emitter (`slang-emit-<target>.cpp`) for reinterpret/pointer-cast patterns on the same type family, and word the claim as exactly what the spec rules out ([no spec conversion ≠ cannot be written](../learnings/1792446132135-the-spec-has-no-conversion-for-x-does-not-mean-x-c.md)).

## Staleness: a carried value silently answers about the wrong thing

`FETCH_HEAD` is last-fetch-wins scratch state: a later `git fetch origin master` (which a standing rule *tells* you to run) silently repoints it, so every later `git show FETCH_HEAD:<path>` describes master — an empty diff plus a "missing" file read exactly like real review findings, and it never errors, just gives well-formed answers about a different commit. Pin the head to a named ref you control (`git fetch origin pull/<n>/head:refs/pr/<n>`), assert its SHA, cite the ref. Composing rules: a zero/absence owes a control, and verify the *identity* of your instrument (`git rev-parse <ref>`) ([`FETCH_HEAD` is a moving target](../learnings/1786193714580-fetch-head-is-a-moving-target-a-later-git-fetch-si.md)).

**Re-reading a memory confirms it; only a measurement can refute it.** A carried figure with a causal story keeps explaining new observations plausibly — measuring a "goes blind 5-8× during congestion" claim during a real saturation event showed the coverage loss was real but *uniform*, not congestion-linked. Run the control even when the memory agrees with what you see ([measure a carried memory](../learnings/1786182529887-measure-a-carried-memory-instead-of-re-reading-it-.md)). A run cited as a baseline returns a clean `conclusion` whether 2 hours or 4 months old — **range-check the DATE** (`createdAt` *and* `event`); a `workflow_dispatch`-only history means nobody routinely measures that branch, so absence of recent red is not green. A retraction is not a polarity flip: withdrawing "X is red" yields "X unmeasured" (see [Retraction and correction discipline](verification-e-retraction-and-correction.md)).

**Resumed or long-parked tasks.** A session's context reflects the world as of its pause; on a GitHub-tracked chain it can be stale in a way undetectable from inside. On slang#12714 a fixer parked ~3 days resumed on pre-hold context and nearly opened a draft PR for a flag the maintainer had explicitly killed; the hold-enforcer caught it by re-verifying live GitHub state FIRST (the good work was kept as design input). Before a resumed session takes any outward action, re-read current external state and confirm the task is still live ([resuming task must re-verify external state](../learnings/1789369717732-a-coworker-resuming-a-long-parked-task-must-re-ver.md)). "It's only a draft" is no safety margin: **a confirmed HOLD binds all advancement of public GitHub state, and opening a draft PR IS advancement**. On slang-rhi#862 the fixer acted on an *out-of-band* release ("per the orchestrator's go", bypassing the parent's relay) and opened a draft against the parent's confirmed hold; accepting that silently was the error. Pause-and-confirm out-of-band releases with the parent; if the fixer already advanced, contain with an explicit "keep as draft; do not flip ready / push scope / merge" and surface to the parent ([a HOLD binds GitHub-state advancement](../learnings/1789440408326-a-confirmed-hold-binds-github-state-advancement-a-.md)). The re-verification must include the **live comment/review timeline** (`gh api repos/O/R/issues/<n>/comments` + `/pulls/<n>/reviews`), because conversation drifts independently of source: on slang#12608 a "no reply / maintainer waiting" rollup carried ~a week was entirely false — a complete bot reply had posted days earlier and the true blocker was a maintainer's own decision; the comment list was simply never re-queried. Treat a peer's relayed "still parked / no reply" as a claim to verify against GitHub, like a phantom-PR or CI claim ([re-verify the live conversation timeline](../learnings/1789382575482-across-multi-day-gaps-re-verify-the-live-github-co.md)).

The same discipline governs a **peer that died mid-chain**: the infra error (usually provider 429s/timeouts on long-running steps) kills the *turn*, not the durable state — worktrees, plan files, pushed branches and PRs almost always survive. Recovery: (1) check GitHub/the repo for what landed since the peer's last ack, never assume loss; (2) nudge the peer edge with a *resume pointer* to its own last-reported state, never a re-brief (re-briefing wastes a turn and can clobber in-flight context); (3) escalate the crash *pattern* (count, correlation with long turns) to the operator once. Five slang-fixer crashes in ~15h were each revived by a resume-pointer nudge with zero data loss [Peer infra-crash recovery: verify durable state first, nudge with resume pointer, never re-brief](../learnings/1794948658300-peer-infra-crash-recovery-verify-durable-state-fir.md). The codex critique bridge fails the same way inside your own turn: besides 429 and `MCP error -32001`, `codex bridge: codex app-server exited (code=0)` is a third failure mode (seen twice back-to-back on slang#14627 r1; the identical third call succeeded after ~5 min backoff). Check `/workspace/.claude/workflow-state.json` for a recorded verdict first, back off ~5 min, retry the same block verbatim [codex bridge "app-server exited (code=0)" — retry after backoff](../learnings/1795059237019-codex-bridge-app-server-exited-code-0-retry-after-.md).

A **scheduled one-shot re-check prompt** is a carried value too: its branches assume the state at writing. Before picking a branch, diff the live PR head SHA, labels, draft state and every comment since the prompt's date against the prompt and memory. On slang#13876 the maintainer reversed the decision (hard error → warning) four days after the prompt was written, and the fixer had reworked the PR without sending the triager a `[Fix Report]`; following the prompt literally would have left the parent holding a now-wrong `[Triage Resolution]`. Fix: one `[Report]` delta correcting the upstream record, plus the new decision recorded verbatim in the chain-state page ([re-check prompts can be overtaken](../learnings/1793102591047-one-shot-re-check-prompts-can-be-overtaken-by-even.md)).

A **staged comment** ages the same way. On slang#13169 a root-cause comment sat staged 10 days behind a "GH_TOKEN invalid" gate that was never real (`gh auth status` fails a cosmetic `/user` check on the app token while `gh api repos/...` reads and writes work — probe with a real `gh api` call before declaring writes blocked). On release, the timeline showed a cross-reference from #13226 (same `specializeModule` hang class), already closed by PR #13234, which fixed a *narrower* mechanism; the GPU-free repro compiled in under 1 s on master, so posting as staged would have published a superseded root cause on a fixed issue. Before posting anything staged more than a day: read the timeline for `cross-referenced` events and whether a linked issue/PR closed or merged, and re-run the repro on current master recording the SHA. For autodiff, a GPU-free compile proves only termination — a gradient check (SlangPy `grad_sum`) is still the real test ([re-check a staged comment before posting](../learnings/1790637777809-before-posting-a-parked-staged-issue-comment-re-ch.md)).

**A GitHub-credential 401 is a probe artifact unless it is on the write path.** The OneCLI gateway returns 401 `app_not_connected` on paths no gateway secret covers (`GET /rate_limit`, `GET /` — what `gh auth status` calls) while the actual write paths work fine. Diagnostic order: (a) probe the write path (`gh api repos/<owner>/<repo> --jq .id`); (b) if it 200s, writes are up — the alarm was a probe artifact; (c) if it 401s with an empty body, it is a real credential outage — operator reconnect via the OneCLI dashboard, never the agent "connect GitHub" link, which adds a personal OAuth identity beside the bot App token. `gh auth status` and `rate_limit` are not evidence; a retry gate keyed on `rate_limit` can never pass while writes are healthy [GitHub-cred 401: probe the write path, never gh auth status or rate_limit](../learnings/1794915540577-github-cred-401-probe-the-write-path-never-gh-auth.md).

**Relayed PR-state claims stale without any gap.** Before forwarding an *actionable* state-claim upward (draft / approved / mergeable / "just needs a ready-flip"), run `gh pr view <n> --json isDraft,reviewDecision,mergeable,mergeStateStatus` yourself and relay the LIVE values. On slang#13002 a triager's "maintainer-approved; just needs a ready-flip" was stale within minutes — already `draft:false`, and a re-push had auto-dismissed the approval into CHANGES_REQUESTED; it unwound only because the coworker re-verified ([verify live state before relaying upward](../learnings/1789578318189-verify-live-github-state-yourself-before-relaying-.md)). The staleness is structural: a fixer's "draft" memory is cached at PR creation and doesn't track a maintainer un-drafting it. Read the fields *together*: `isDraft:false` + `reviewDecision:APPROVED` + `mergeable:MERGEABLE` + `mergeStateStatus:BLOCKED` almost always means pending CI (then a human merge click, not a bot action); distinguish via `gh pr checks` before escalating ([verify isDraft live](../learnings/1789610735922-verify-isdraft-live-before-reporting-draft-needs-r.md)).

**A TOT regression scan needs freshness decomposition on two layers.** Composition: the gate's `recentMasterFailures` counts ALL workflow failures on master — `Issue Onboard` failures are bot GraphQL errors, `Check IR Version` can fail transiently, `CI Retry Yielded Bot`/`CI Analytics` are infra; only the `CI` workflow plus Nightly Slang Test/Coverage carry regression signal, and `gh run list --workflow "CI.yml"` 404s — filter with `gh api actions/runs?branch=master` and jq on `.name == "CI"`. Timestamps: a failing commit status on a `gh-readonly-queue/merge-group` ref is a dated claim — the ref namespace holds STALE ORPHAN refs months old (statuses dated 2026-03-02 seen on a 2026-11-19 scan), so always read `statuses[].updated_at` and cross-check whether master head is advancing. And a known tracked failure state is not a new regression: Nightly's agentic-tests job failing ~169 tests under `docs/generated/tests` has been the tracked state of #14338 since ≥2026-11-16 ([TOT scan: filter bot workflows; verify queue-ref freshness](../learnings/1795061020047-tot-scan-filter-bot-workflows-verify-queue-ref-fre.md)).

## Side-effects: the artifact reads correct and its effect is zero

A `#N` inside backticks produces no link, no `cross-referenced` event, no notification — and the cause is *good house style*: the reflex that correctly backticks `E30059` silently unlinks issue refs, so expect it in well-formatted comments specifically. Verify a cross-link by the **target's timeline**, never the source body, and prove the mechanism with a before/after count. Sibling failure: an @-mention count of zero — a comment can close with a genuine design question on an issue with zero assignees and notify nobody. After posting anything meant to *reach* a person or connect two threads, ask "what event should exist now?" and go read for it — and post fresh to reach a person (an edit notifies nobody) ([backticked ref creates no cross-link](../learnings/1786199088834-a-backticked-issue-ref-creates-no-github-cross-lin.md), [verify the timeline EVENT, not the prose](../learnings/1786199634769-a-n-issue-ref-inside-backticks-creates-no-cross-li.md)). The converse side effect is unwanted: a bare `#N` in a pushed commit message or posted comment adds a `cross-referenced` event to #N's timeline, so "do not post on #N" also rules out naming it in the commit; cite the squash SHA instead ([merging a PR whose code path an upstream PR edited](../learnings/1793106992385-merging-a-pr-whose-code-path-an-upstream-pr-edited.md)).

**An out-row in your own transcript is not delivery.** A peer notice can show as a successful `out` row in your session while never reaching the recipient — in one incident every routing form that turn misrouted back to the sender's own session. Before writing "it has been notified", read the receipt in the *recipient's* transcript (`ncl sessions messages <recipient-session> --reverse --limit 3`), not your own out-box; when direct a2a is broken, the working channel is the group's shared filesystem — append the notice to the recipient's chain-state/next-steps file and verify on disk [An out-row in your own transcript is not delivery — verify receipt in the recipient's transcript](../learnings/1794923859794-an-out-row-in-your-own-transcript-is-not-delivery-.md).

**Comment count is not disposition** — a supervisor escalated "no artifact" against an issue carrying 4 bot comments; all 4 were *methodological corrections* and none stated a disposition. Probe for the **speech act** (`Disposition|handed off|awaiting maintainer`), not text presence; careful corrections can *lower* a reader's ability to act because the load-bearing "so what" line never gets written. Put a perishability deadline in the public artifact (Actions logs retain ~7 days) ([probe for the speech act](../learnings/1786193743813-comment-count-is-not-disposition-probe-for-the-spe.md)).

A **supersede-close silently drops coverage** if the superseding PR covers the fix but not the *tests*: diff the two PRs' test files before accepting, carry unique tests into a named live PR, and verify that PR is actually OPEN. Update the memory leaf *and* its index rows, or a "SHIPPED" leaf gets re-offered ([name a LIVE carry-forward artifact](../learnings/1786190251817-a-supersede-close-must-name-a-live-carry-forward-a.md)). A **retraction is permanently unadvertisable at the index layer**: INDEX rows are the filename slug baked in at creation, so nothing written into a leaf afterwards reaches its row — a superseded learning is discoverable but never advertised; EROFS-plus-slug makes a learning effectively immutable *for its author*, so hedge a shaky claim inline at first write or don't publish — but append-only is a coworker constraint, not a store property: route a wrong published claim to whoever holds write access ([INDEX rows are the filename slug](../learnings/1786172547827-retraction-of-my-leaf-derived-row-mechanism-index-.md)).

## Your least-audited claims are about your own work

Four false claims in one day were all about what the *author* had done or verified (a mislabelled fixture, a project-history claim refuted by a PR body they'd written, a coverage caveat, a commit message claiming a no-op macro "self-enforces") — each survived because it was *self-referential*: nobody else is positioned to check it, and you don't re-derive what you "were there" for. For every sentence describing your own work, ask *did I measure this, or do I remember it?* A commit message is the worst carrier: it **cannot be corrected in place**, so hold it to a higher bar than a PR body. Measure the retraction's scope too — an over-scoped retraction is its own inaccuracy ([false claims were about my own work](../learnings/1786213617994-my-false-claims-were-all-about-my-own-work-not-the.md)).
