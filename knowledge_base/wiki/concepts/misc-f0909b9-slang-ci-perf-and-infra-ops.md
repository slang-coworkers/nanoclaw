# Slang CI health, heartbeat monitoring, and perf/benchview infrastructure

Operational facts for the Slang CI-health / maintainer / heartbeat roles: reading failures at the source, test-falcor rerun traps, heartbeat data quality, weekly load, and the compile-perf/BenchView landscape.

## TL;DR

- **Read the failing log line before asserting causation** — a verified correlated fact (a TTL exists) is not a cause. Read the step's *output*, not its echoed `##[group]Run …` source ("LLVM prebuilt not found in GCS" matches the script's `echo` on a cache hit).
- **test-falcor has two distinct failure modes:** a 403 after a status came back is a *bridge auth* rejection; "artifact unavailable (expired)" is manufactured by a `--failed` rerun of a >1-day-old run whose 1-day build artifact is gone. Check both; grep `rerun-log.jsonl` for the run_id before any rerun.
- **A post-rebase deterministic test-slang failure on every platform (incl. CPU/aarch64), unrelated to the diff, is a master semantic-merge break** — file against master; don't push a "fix" onto the innocent PR.
- **`shader-slang/slang`'s default branch is `master`** — a `main` query silently 404s; prefer `gh pr view --json mergeStateStatus` (`BEHIND` = needs rebase). `shader-slang/slang-rhi` uses `main`: read `default_branch` before a comment names a base branch.
- **Heartbeat precheck's slang `workflow_failures` field is repeat-prone stale** — spot-check it against a live API call every wake. Re-derive a carried "since <anchor>, now ~Nh" duration from the anchor, never last figure + delta.
- **The Saturday CMake Options burst (479 hosted jobs, Sat 08:00Z, ~4 h) is expected load**, not Critical, and blinds `health_snapshots` for ~2.5 h; a bot dispatch can cause one any day. Attribute a queue spike to its dominant workflow first.
- **merge_group runs skip the functional `test-falcor`** — check the job, not the run, for "MQ Falcor passed"; judge a Falcor nightly red from PR CI runs on the same master content.
- **Slang's scheduled workflows have no fork guard** (16 of 17), so a fork with Actions enabled fails `ci-health.yml` every 15 min. Tell a complaining contributor to disable Actions on the fork; PR CI runs upstream.
- **Perf/benchview:** compile-time alerting is the mature fork template; runtime perf is greenfield. BenchView is a downstream consumer by URL, and MDL results push to a PRIVATE repo. Source-verify inherited perf "facts" against the current tree.
- **Per-pass compile-time A/B:** phase-scoped callgrind plus ABBA wall-clock where valgrind exists. On the shared box (no valgrind/perf/sudo), bisect with shuffled interleaved timer rounds over per-commit Release builds plus tools-only-commit A/A controls, then attribute with a revert experiment.
- **When an MDL perf red moves the SAME IR-pass timers on several backends, read `claude-perf-bisect.yml`'s `bisect.json` before calling it noise**: a rebuild-confirmed shift well above the A/A spread is real even at `interval`.
- **Nightly MDL perf: split disclosed benchmark resizes from real regressions; a green night after a red one is usually a sub-threshold confirmation** (1.08× < 1.10×), not baseline absorption. Read `Confirmation:`; size a real step by per-timer geomeans over size-matched workloads (`perf-confirmation-*` artifacts expire in a week).
- **A `workflow_dispatch` run's `head_sha` is not the commit it built**: a manual MDL perf dispatch with a `ref` input records master tip but builds the checkout `ref:` (read it in the log) — an old-ref link error is a backfill, not a master regression.

## Causation must be read at the failure site

A `test-falcor` cluster was diagnosed 403, then escalated as "it's the ~24h artifact TTL" once the TTL was verified to *exist*. The failing log said `run-external-ci: trigger failed: HTTP Error 403: Forbidden`, a ~15s auth rejection *before any artifact is fetched*: the TTL was real and causally irrelevant. Read the failing line (`gh run view <run-id> --log-failed --job <job-id>`) before relaying a root cause, and treat a coworker's root-cause label as a hypothesis, doubly after a flip-flop ([causation at the failure site](../learnings/1788459591745-verify-causation-at-the-failure-site-a-verified-co.md)).

Read the *output*, not the step's source: GitHub prints each step's script in its `##[group]Run …` block, so grepping "not found in GCS" matches setup-llvm-from-gcs's `echo "⚠️  LLVM prebuilt not found in GCS"` on a cache HIT too (likewise "Downloaded LLVM prebuilt"). To confirm a real miss, drop lines containing `echo `, look for `🔨 Building LLVM from source`, and read `Checking for LLVM prebuilt: <url>` for the probed key; fetch with `--allow-escape-sequences` and strip ANSI (`sed 's/\x1b\[[0-9;]*m//g'`). It nearly mis-verified a LNK2019 failure on #13526 as a cache miss ([LLVM grep matches echo](../learnings/1791620024633-grepping-job-logs-for-llvm-prebuilt-not-found-in-g.md)).

## test-falcor: two distinct failure modes, and the stale-rerun trap

`gh run rerun <id> --failed` reruns only the failed job, not the build jobs that made its artifact, and the Windows-falcor build artifact has `retention-days: 1`, so a `--failed` rerun of a run older than ~1 day fails at artifact resolution whatever the original error. A sweep reran 7 such PRs; all re-failed in seconds with "artifact unavailable (expired)." Check `created_at` (>24h ⇒ no `--failed` rerun) and grep `rerun-log.jsonl` for the run_id before any rerun ([stale-run reruns fail](../learnings/1788546124300-test-falcor-reruns-fail-deterministically-once-the.md)).

The 403 and the expiry are two code paths: a fresh run got a status back from external CI, then a 403 (genuine bridge auth rejection), while a stale rerun died at artifact resolution *before* triggering, saying nothing about the 403; before a unifying "structurally cannot" claim, read a second class member — here the original failure's raw log ([403 vs expiry distinct](../learnings/1788546545702-correction-test-falcor-403-and-artifact-expiry-are.md)). With the bridge confirmed healthy, 6 `--failed` reruns of day-old runs still failed "artifact unavailable": the preconditions are independent, and a test-job rerun cannot regenerate a stale artifact ([check artifact age too](../learnings/1788589902152-falcor-bridge-403-confirmation-must-also-check-bui.md)). A `--job` rerun of `test-falcor` fails the same way in ~19 s at `Run external CI`, with no GitLab pipeline. A fresh push, a full rerun, or a rerun of the producing `build-windows-release-cl-x86_64-gpu-falcor / build` job regenerates it and cascades into `test-falcor`; check `artifacts?name=slang-tests-windows-x86_64-cl-release-falcor` (`total_count` 0 = gone) first. A rerun that reaches the bridge submits a new Falcor pipeline (#13886) ([--job rerun 19s](../learnings/1793081639779-test-falcor-job-rerun-fails-in-19s-once-the-run-s-.md)).

## Flake vs. real: master merge breaks and the master branch name

When `test-slang` fails **deterministically on every platform (incl. CPU-only/aarch64) right after a rebase** on tests unrelated to the diff, suspect a master semantic merge conflict. Case: #12830 added warning E40021 while #12828 (touching the affected tests) merged ~2 min earlier without it; neither CI saw the other, so every rebasing PR inherited the red. Find it on a CPU/aarch64 job, attribute with `git log origin/master -S "<text>"` and `git log -- <testfile>`, prove master is broken independent of the PR, fix master, and tell the author to rebase. Contrast: a `test-falcor` 403/download/VCS-root failure in ~18s, before any shader compiled, is infra ([master merge break](../learnings/1788457867847-post-rebase-cross-platform-test-slang-failure-on-a.md)).

A `--branch main` / `sha=main` query silently 404s and reads as "no base-branch CI run found," making a BEHIND PR look like a live regression; `gh pr view --json mergeStateStatus` (`BEHIND` plus a failing test a recent master commit touched) separates "needs rebase" from "regression on master" ([master, not main](../learnings/1788675668651-shader-slang-slang-default-branch-is-master-not-ma.md)). `shader-slang/slang-rhi` uses `main`, though parents say "master" out of habit (slang-rhi#956), so check `gh api repos/<owner>/<repo> --jq .default_branch` before a GitHub comment names a base branch ([slang-rhi is main](../learnings/1793869591386-slang-rhi-default-branch-is-main-not-master.md)).

A recurring nightly red is not always new: `agentic-tests` failed two nights with the same 6 tests, explained by open PR #12881 (adds them to expected-failures); check `expected-failures.txt` / #12881 before re-flagging, and diff `FAILED test:` lines across nights' job logs (`.../jobs/{job_id}/logs`) for a stable fingerprint ([agentic-tests cluster](../learnings/1788428378771-slang-nightly-slang-test-agentic-tests-2-night-fai.md)).

## Heartbeat monitoring reliability

The precheck's `workflow_failures.slang` field returns stale data (days-old runs, wrong `total_count`) while `slangpy`/`slang-rhi` in the same payload are live, so it is not a proxy or rate-limit outage. After a **3rd occurrence** it is a standing characteristic: spot-check slang's field against a live API call every wake. A single anomalous read that self-corrects on immediate retry is different: retry once ([stale for slang only](../learnings/1788404324277-heartbeat-precheck-workflow-failures-fetch-returne.md), [confirmed recurring](../learnings/1788410539745-heartbeat-precheck-s-slang-workflow-failures-stale.md)). When a report carries "since <anchor>, now ~Nh" across wakes, recompute N from the anchor: a base error survives indefinitely because every delta looks consistent; one figure read "~59h" when anchor-to-now was ~31h ([verify the base](../learnings/1788393885068-heartbeat-verify-the-base-not-just-the-deltas-on-d.md)).

### Scheduled workflows run on forks

At master 9a4817c881 (2026-10-27), 16 of 17 scheduled workflows lack an `if: github.repository == 'shader-slang/slang'` guard; only `sccache-populate.yml` has one. `ci-health.yml` runs `*/15 * * * *` and needs the project's GCP Workload Identity, so a fork with Actions enabled fails every 15 minutes. Until 9a4817c881 `CONTRIBUTING.md` told contributors to enable them. Answer a complaint with Settings > Actions > General > Disable actions on the fork; those reds are not upstream CI health ([no fork guards](../learnings/1793089763873-slang-scheduled-ci-workflows-lack-fork-guards-ci-h.md)).

### The Saturday CMake Options burst is expected load, and it blinds CI Health

Before flagging a `jobs_queued`/`hosted_runner_usage` Critical, attribute the backlog to its dominant workflow and read its triggers. "CMake Options" runs `schedule: cron "0 8 * * 6"` (Saturday 08:00 UTC) + `workflow_dispatch` only; its OS-matrix fan-out taking up to half the org's hosted budget is accepted (why its `merge_group` trigger was removed). On a Saturday with it dominating, report informational/🟢 ([Saturday is expected](../learnings/1789812585102-slang-ci-saturday-cmake-options-queue-saturation-i.md)). The dispatch need not be human or Saturday: on 2026-10-22 two nv-slang-bot dispatches on #13850's branch pushed `jobs_queued` to 458 and `runs_queued` to 43, so read `queue_by_group` / `hosted_runner_usage.queued.by_workflow` before calling a spike a capacity outage ([bot dispatches](../learnings/1792660471559-ci-sweep-full-ubuntu-latest-log-header-scan-exhaus.md)).

The burst (~479 hosted jobs) blinds the health feed: CI Health's `update-health` job is itself `ubuntu-latest` and cannot start, so `health_snapshots.jsonl` has a 106–152 min gap every Saturday from ~07:50Z, and the first snapshot after it is a lower bound on the peak, not a runner outage ([burst blinds CI Health](../learnings/1792312349410-slang-ci-saturday-cmake-options-burst-blinds-ci-he.md)). On 2026-10-24 the run took 4 h 08 min, holding all 60 hosted slots until ~11:15Z: a ~2.5 h snapshot gap, cancelled queued CI Health and `Populate sccache` runs, a "critical" first snapshot, and other `CI` runs' hosted `filter` jobs waiting ~70 min. Read its verdict after ~12:30Z or Sunday. Riders: a rate-limit sleep floor must skip the `search` resource (30/min), and a "rerun" regex matches "not rerunning bot CI." ([~4 h run](../learnings/1792916619171-weekly-cmake-options-run-lasts-4-h-and-blinds-the-.md)).

In `ci.yml` merge_group runs `test-falcor` is **skipped** (`falcor-build-approval-gate` skips for merge_group and `test-falcor` has no `always()`; only `test-falcor-perf` runs), so "MQ Falcor passed" needs the job's conclusion ([burst atom](../learnings/1792312349410-slang-ci-saturday-cmake-options-burst-blinds-ci-he.md)), and a Falcor nightly red cannot be judged from the merge queue at all: read `test-falcor / Test (Falcor)` on PR CI runs built on the same master content (the GitLab pipeline log is unreachable) ([MQ skips test-falcor](../learnings/1793952713959-mdl-perf-nightly-read-the-auto-bisect-artifact-bef.md)). The Actions API listing window moves (a date filter returning 940 runs one day returned 0 the next), so streak counts from `workflows/<id>/runs` can shrink; carry streaks from earlier sweeps. Through the OneCLI proxy `/rate_limit` reports unauthenticated limits (60/h) while real calls get 6000/h; read `X-Ratelimit-*` on a real call ([burst atom](../learnings/1792312349410-slang-ci-saturday-cmake-options-burst-blinds-ci-he.md)).

## Maintainer readying a bot draft PR

A maintainer may flip a bot draft to ready-for-review; check the timeline actor and do NOT revert it — "drafts only / never `gh pr ready`" constrains *our* actions. With "dismiss stale reviews on push" on (slang has it), a force-push of review fixes dismisses the approval (`reviewDecision: REVIEW_REQUIRED`), which is expected; say so when the delta is doc/comment/test-only. Once ready, `ci.yml` auto-runs on synchronize, so do NOT `gh workflow run ci.yml` again ([readying a bot draft](../learnings/1788380981281-maintainer-readying-a-bot-draft-pr-force-push-dism.md)).

## Perf and benchview infrastructure

Perf-CI landscape (epic #12941): **compile-TIME alerting is mature and the fork template**: `nightly-mdl-perf-test.yml` has a separate `analyze` job running `tools/compile-perf/trend.py` (`--rel 1.10` = 10% gate) that posts to Slack, with results in external repo `shader-slang/slang-compile-perf` (gh-pages dashboard). **RUNTIME alerting is greenfield**: the runtime path is pass/fail only, metrics reach benchview (NVIDIA-internal) via a GitLab Falcor2 bridge, and placement needs a maintainer LOCUS decision. `analyze` runs on a GitHub-hosted runner because the NVIDIA perf-pool proxy DENIES CONNECT to hooks.slack.com ([fork template](../learnings/1788881870741-slang-perf-alerting-compile-perf-is-the-fork-templ.md)). Grounding facts, correcting circulated mislabels:

- **MDL benchmark results push to a PRIVATE repo.** `perf-push-benchmark-results.yml` runs `tools/benchmark/compile.py --samples 16 --target dxil`, a COMPILE-TIME MDL sweep (not runtime), and pushes `benchmarks.json` to private `shader-slang/slang-material-modules-benchmark` via a PAT. Exposing them on a public benchview is an ops/security/hosting decision ([PRIVATE repo](../learnings/1788881853471-slang-benchview-results-land-in-a-private-repo-the.md), [facts corrected](../learnings/1788884756637-slang-perf-alerting-facts-corrected-perf-push-benc.md)).
- **BenchView is a downstream consumer by URL.** In the 2026-09 audits "benchview" appeared only in `tools/compile-perf/bench.py` comments (raw samples kept for a downstream BenchView format), with no ingestion code, endpoint or creds. Verify an audit branch exists before auditing (`dev/ccummings/benchview` does not; one 404 is not conclusive — use four probes) ([consumer by URL](../learnings/1788882146534-slang-benchview-is-a-downstream-consumer-by-url-no.md)).
- **compile-perf emit workloads share one shader by design**: every codegen workload uses `gen=workloads.gen_codegen`, differing only in `-target`, to isolate the emit path. The suite lacks backend-DISTINCTIVE source shapes, not coverage, so better targeting means generators stressing each backend's legalization. `check-python-core.yml` hard-codes the module import list, so renaming a `tools/compile-perf/*.py` module without updating it turns CI red ([emit_* share gen_codegen](../learnings/1788881942527-compile-perf-emit-workloads-all-share-one-shader-g.md)).
- A straight fork of the compile-perf Slack template does NOT meet a rich-alert spec (no magnitude or commit/PR link), and `trend.py`'s adaptive trailing median does NOT detect gradual drift ([facts corrected](../learnings/1788884756637-slang-perf-alerting-facts-corrected-perf-push-benc.md)).

Perf-epic sub-tasks are maintainer-curated, no-repro ops/infra work: don't auto-dispatch a fixer; triage, 5-bullet, report up (closures and reply content: [[wiki/concepts/agent-fixer-codex-skills-f0909b0-triage-routing-and-classification.md]]).

**Answering "does this pass change regress compile time?" deterministically.** A shared 64-core box is too noisy (load moved medians ±10%), so scope callgrind to the phase: `valgrind --tool=callgrind --toggle-collect='Slang::linkIR*' slangc ...` gives run-identical instruction counts, and `callgrind_annotate --inclusive=yes` shows which function absorbed the delta. Build Release base and fix from one tree differing in one file (copy `bin/` and `lib/` out; rpath is `$ORIGIN/../lib`), pair with an ABBA wall-clock run, and check the `.spv` is byte-identical. SPIR-V workloads need `--target slang-glslang` built in Release with `libslang-glslang-*.so` copied next to `libslang-compiler` (else "failed to load downstream compiler 'spirv-opt'"). Don't claim "X% of total compile" from phase-share × phase-delta: measure whole-process Ir and report a paired IQR entirely above zero ([phase-scoped callgrind](../learnings/1791325135172-deterministic-compile-perf-a-b-for-a-slang-pass-ca.md)).

## Triaging the Nightly MDL Perf Test gate

**First check which commit a red dispatch actually built.** `nightly-mdl-perf-test.yml` takes `ref` and `suite-ref` inputs, so a manual `workflow_dispatch` (a perf bisect or backfill) can build an old commit with the current suite while the run records `head_sha` = master tip, and CI gates count its red as a master failure. Run 42828865221 (2026-11-10) showed `head_sha` `4f66408b`, but its `actions/checkout` block had `ref: ed15ffc9…` (2026-06-25) and `SUITE_REF: 500e75be…`; its Windows LNK2005/LNK1169 (`mimalloc.lib` vs `SPIRV-Tools-opt.lib(mimalloc.cpp.obj)`) came from a ref older than the mimalloc link fixes, while the scheduled run on master built fine. Before blaming the commits near `head_sha`, read `event`/`actor` and `gh run view <id> --log-failed | grep -a 'ref:'` ([dispatch head_sha is not the built ref](../learnings/1794326924367-workflow-dispatch-run-head-sha-is-not-the-ref-it-b.md), [manual perf dispatch shows master head_sha](../learnings/1794341123370-manual-perf-dispatch-shows-master-head-sha-but-bui.md)).

When `trend.py` lights many workloads/metrics at once, split it. (1) **Check for a disclosed methodology change first**: merged PRs touching `tools/compile-perf/lib/manifest.py` `default_size`/`sweep_sizes` often predict the ratio in their body (#13035). (2) **Read which timer flagged**: a localized pass regression moves a sub-pass timer (`specializeModule`, `simplifyIR`, `linkAndOptimizeIR`) while `compileInner` stays under threshold; `compileInner` moving for every workload suggests runner contention. (3) **Narrow suspects to PRs touching `core.meta.slang` / `hlsl.meta.slang`**: the prelude is checked and specialized on every compile, so new generics there inflate `specializeModule`/`simplifyIR` across unrelated workloads under titles with no perf hint. (4) Self-merge (author == merged_by, no APPROVED review) marks thin review, a signal not proof. Example (2026-09-19): four workloads' 2.4–10× jumps were #13035's resize; a separate ~1.7–2.4× `specializeModule`/`simplifyIR` jump traced to self-merged #13138/#13135 (prelude generics) ([resize vs regression](../learnings/1789805493629-separating-disclosed-benchmark-resize-noise-from-g.md)).

**A green night after a red one is usually a threshold miss, not baseline absorption.** `analyze` compares each night to a trailing-7 median. After a 10-07 step, 10-09 went green and one reading blamed absorption ([trailing median hides steps](../learnings/1791619655084-nightly-mdl-perf-test-detect-real-steps-hidden-by-.md)), but the median was still 45.9 ms (only 2 of 7 trailing nights post-step) and confirmation measured 1.08×, under the 1.10× ERROR threshold, so it only warned. Grep the analyze log for `Confirmation:` and `baseline: trailing 7 point(s)` first ([threshold miss](../learnings/1791622838976-nightly-compile-perf-a-green-night-after-a-red-one.md)). The median moves only once 4 of 7 nights are post-step, after which a real step goes quiet, so localize early against a fixed green night. For front-end moves after 2026-10-07, check #13445 (e2e217dd2) first: it turned `SemanticsVisitor::getTypeTags` from a cached `aggTypeDecl->typeTags` read into a per-call walk with no `-Gec` gate (#13565).

**Size a step with per-timer geomeans, not the `analyze` flags.** `analyze` lists only counters over ratio ≥1.1 / abs ≥2 ms against the trailing median, and chronic noise makes lone flags unreliable. `gh run download <run-id> --repo shader-slang/slang -p 'perf-confirmation-*'` gives `results.json` (per workload: `size`, `timers.<name>.median`); older nights live in shader-slang/slang-compile-perf `daily/<date>-<sha>/results.json`. Keep workloads whose `size` matches between nights (≥1 ms baseline), then take the per-timer geomean ratio against the fixed green night. A real front-end regression moves one phase broadly while backend timers stay ~1.00; runner noise moves every phase together and rotates nightly. Measured: SemanticChecking up in 48/54 workloads (~1.075×) after 10-07 ([per-timer geomean](../learnings/1791619655084-nightly-mdl-perf-test-detect-real-steps-hidden-by-.md)); 10-16 SemanticChecking 1.052 vs 10-12, 39/54 above the prior four nights' max. The per-push store (slang-material-modules-benchmark) is DXIL-only and bimodal across runners, so it cannot localize a front-end shift. Artifacts expire after ~a week (10-07/10-08 returned 404 on 10-16), so record geomeans durably ([size a step](../learnings/1792138989940-mdl-perf-nightly-size-a-front-end-step-with-per-ti.md)).

**Read the auto-bisect artifact before calling a red noise.** Most reds are single-counter jitter, but when the same IR-pass timers (`simplifyNonSSAIR`, `linkAndOptimizeIR`) rise 8-22% together on several backends, open the `claude-perf-bisect.yml` run that fires after the nightly. `gh run download <bisect-run> -n perf-bisect-<run>-1` gives `bisect.json`: `status` (`culprit` or `interval`), `probes`, and base-vs-head rebuild timings with the A/A spread. A rebuild-confirmed shift (+8-13% against a 0.68% A/A) is real even when the bisect stops at `interval`; the nightly log's "Real or noise" line says the same. On 2026-11-06 it stopped at interval b3d4e7ad..6d43c8d8, 11 commits, no culprit ([read bisect.json](../learnings/1793952713959-mdl-perf-nightly-read-the-auto-bisect-artifact-bef.md)). The verdict lives only in artifacts (`perf-bisect-<run>-1`, `perf-classification-<run>-1`), not job logs. Without `gh run download`, take artifact IDs from the tail of the `classify` job and `GET https://api.github.com/repos/shader-slang/slang/actions/artifacts/<id>/zip` with no Authorization header — the OneCLI proxy authenticates it, far cheaper than full logs ([artifacts via proxy](../learnings/1793954343982-ci-sweep-read-actions-artifacts-via-proxy-find-los.md)).

**Finishing the bisect locally without perf or valgrind.** The shared coworker box has no perf counters (`perf_event_paranoid=4`, no PMU), no valgrind and no sudo. What works: one build-capable worktree (submodules need `git -c protocol.file.allow=always submodule update --init --recursive`, else "transport 'file' not allowed"); an incremental Release `slangc` build per first-parent commit (~2-5 min), copying `bin/slangc` and `lib/*.so*` to `builds/<sha>`; inputs from `tools/compile-perf/lib/workloads.py` (e.g. `gen_matrix_chain(512)`) with flags from `manifest.py`; then 15-20 rounds, after one warm-up, each running every build × workload once in shuffled order pinned with `taskset`, comparing medians. Tools-only commits (render-test, slang-test, scripts) produce a byte-identical `libslang-compiler.so`, so they are free A/A controls; copied binary dirs give a second A/A (pairs within ~1.2%, spread ≤2.5%). A revert experiment (reverse-apply one PR hunk on head, rebuild, measure) attributes the cost: on 2026-11-06 it pinned the interval above to #13792's 24-line `canInstHaveSideEffectAtAddress` hunk, filed as #14381. Local ratios exceeded the Windows runner's (+16-22% vs +10-13%) with the same shape ([local bisect + A/A](../learnings/1793956764481-local-compile-perf-bisect-without-perf-valgrind-in.md)).
