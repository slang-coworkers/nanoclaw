## TL;DR

CUDA/OptiX backend facts, mostly around ray tracing, the NVRTC-compiled prelude, and GPU-free verification:

- **OptiX payload register count is carried by a separate `payloadSize` operand, NOT the `_optix_trace_typed_32` name** — that one 32-slot transport is emitted for every payload size. When triaging "traced as N registers," grep the `payloadSize` immediate, not the intrinsic symbol. The prelude's `optix*WithRegs` helpers have fixed-width `N<=16`/`N<=32` catch-alls that over-read/over-write for N in [9,15] AND [17,31].
- **An `inout` ray payload is legalized TWICE** (VaryingInput + VaryingOutput), and a direction-agnostic `case RayPayload:` branch double-reads the registers. The dead reads survive DCE because `kIROp_GetOptiXPayloadRegister` is conservatively side-effecting — fix at the producer, don't mark it pure.
- **OptiX hit-attribute lowering is field-wise (one 32-bit register per scalar leaf), not byte-packed.** A `ReportHit` write path must gather leaves into ONE `optixReportIntersection` call (OptiX has no per-attribute setter), and must emit `__float_as_uint` explicitly (CUDA `kIROp_BitCast` is a numeric cast, not bit-preserving).
- **HLSL ray flags are passed verbatim into `optixTrace` with no validation.** Only `RAY_FLAG_SKIP_TRIANGLES`(0x100) and `SKIP_PROCEDURAL_PRIMITIVES`(0x200) lack an OptiX equivalent (0x400 DOES map); key an "unsupported" diagnostic off the named `OptixRayFlags` set (supported = 0x4FF), not a `>=0x100` threshold.
- **The whole `slang-cuda-prelude.h` is fed to NVRTC verbatim**, so any OptiX helper using an SDK-N symbol without `#if (OPTIX_VERSION >= NNNNN)` breaks ALL RT shaders on older SDKs. Resolve thresholds from `external/optix-dev` git tags (7.x decls live in `optix_7_device.h`), verify GPU-free with nvcc.
- **CUDA `noinline` policy must be target-gated** — `IRNoInlineDecoration` is already consumed by SPIR-V/LLVM/HLSL emitters, so an ungated heuristic pass would regress them.
- **`inout` subobject copy-in/out is design-gated on CUDA** by the `undoParameterCopy` abort-safety constraint (OptiX abort intrinsics can skip writeback); WGSL already does the copy unconditionally.
- **A `case cuda: __intrinsic_asm "name"` forwards ALL of the enclosing function's args positionally** (unlike the spirv/glsl cases, which pass explicit helper operands), so mirroring a `__target_switch` case across overloads of different arity emits a wrong-arity CUDA call NVRTC rejects — add a matching-arity prelude wrapper. Gate CUDA-codegen correctness on `-target ptx -Xnvrtc` (a bare `-target cuda` EXIT 0 can be a silent drop, and missing-return E41009 is target-gated OFF for CUDA/DXIL).

## OptiX payloads: register count is `payloadSize`, and `inout` is legalized twice

`_optix_trace_typed_32` is OptiX's ONE register-trace transport — 32 inline-asm register slots are ALWAYS emitted regardless of payload size; the real payload word count is conveyed SOLELY by a separate `payloadSize = (int)sizeof...(Payload)` operand. So the intrinsic name appears in the PTX for N=8, N=16, N=40 too; when triaging a "traced as 32 registers" report, grep the `payloadSize` immediate loaded before the trace call, not the symbol — the bug is Slang passing the wrong number of `pr.regs[i]` ARGUMENTS. The prelude's `optixTraceWithRegs`/`optixTraverseWithRegs`/`optixInvokeWithRegs` each have `if constexpr (N==0..8)` branches then TWO fixed-width catch-alls (`N<=16` passes regs[0..15], `N<=32` passes regs[0..31]), so `PayloadRegisters<T,N>` is over-read/over-written for N in [9,15] AND [17,31] — when a report cites one window, check the sibling catch-all branch. OOB is read AND write (OptiX's variadic trace assigns returned values back), but NVRTC scalarizes the struct so the PTX has undefined extra register operands, not materialized stack OOB — distinguish source-level UB from PTX manifestation; scope the verdict to the codegen defect and disclaim the runtime hang as "consistent with, not proven" (repro is GPU-free via `-target cuda`/`-target ptx`) ([Slang CUDA/OptiX payload register count is carried by payloadSize](../learnings/1786644040522-slang-cuda-optix-payload-register-count-is-carried.md)).

An `inout` ray payload is legalized TWICE and double-reads its registers: `processMutableParam` calls `createLegalVaryingVal` once as `VaryingInput` and once as `VaryingOutput`, and the CUDA `case LayoutResourceKind::RayPayload:` keys off `getLayoutResourceKind` (always `RayPayload`) while IGNORING `info.kind` (the requested direction), so the register readback (`emitOptiXPayloadRead`) fires on BOTH passes → double reads. Writeback stays correct because a `getCount()==0` guard dedups writeback REGISTRATION only — that guard is the smoking gun (an author who dedups a secondary effect but not the primary one knew the branch runs twice). The dead reads survive DCE because `kIROp_GetOptiXPayloadRegister` has no `hoistable`/pure flag and isn't side-effect-free, so `mightHaveSideEffects()` is conservatively true — so the fix must be "don't emit the second read" (producer), NOT "mark pure so DCE cleans it" (a mutable payload register can be legitimately re-read). Reproducible without a GPU via text CUDA emit + `-dump-ir` ([OptiX inout ray-payload legalized twice: direction-agnostic RayPayload branch double-reads](../learnings/1786656384074-optix-inout-ray-payload-legalized-twice-direction-.md)).

## Hit attributes and ray flags

OptiX hit-attribute lowering is field-wise — one 32-bit OptiX attribute register per scalar leaf — NOT a byte-packed/padding-preserving blob: `emitOptiXAttributeFetch` recurses fields/elements/lanes and consumes exactly one register per scalar `IRBasicType` leaf (CUDA emit wraps float leaves in `__int_as_float`). The 8-register/32-byte cap + its diagnostic live in the legalize pass. So anyone extending `ReportHit` to CUDA must flatten the WRITE side field-wise to match the reader — a whole-struct `bit_cast<uint[N]>` would DESYNC on padding, sub-dword fields, and float bit layout → silent wrong runtime values; the read path is the canonical contract ([OptiX hit-attribute lowering is field-wise, not byte-packed](../learnings/1787174981538-optix-hit-attribute-lowering-is-field-wise-not-byt.md)). The `ReportHit` write path (slang#12637) adds several sharp facts: OptiX has NO per-attribute-register setter (contrast ray *payloads*, which have `optixSetPayload_N`) — hit attributes are written ONLY via one `optixReportIntersection(hitT, hitKind, a0..a7)` call, so the write path must gather all leaves into ONE call, not per-register stores; **CUDA lowers `kIROp_BitCast` as a plain numeric C cast, NOT bit-preserving**, so moving a float into a 32-bit attribute register requires an explicit `__float_as_uint(x)` (an IR BitCast would emit `(unsigned int)(0.5f)` → 0; verify via PTX: `0.5f` → `1056964608` = `0x3F000000`); a new target-specific IR marker op carrying an aggregate operand must be flattened AFTER post-inline DCE but BEFORE empty-type/resource legalization; and FileCheck slang-tests are silently IGNORED when slang-llvm is absent (a vacuous `0/0` pass) — verify CUDA/OptiX emit by direct `slangc -target cuda` + per-leaf grep ([OptiX ReportHit write path: no attribute setter, non-bit-preserving CUDA BitCast, pass ordering](../learnings/1787792439688-optix-reporthit-write-path-no-attribute-setter-non.md)).

HLSL `TraceRay`'s ray-flags argument is emitted verbatim into `optixTrace(...)` with NO bit validation — the CUDA arm of `TraceRay`'s `__target_switch` is literally `case cuda: __intrinsic_asm "optixTrace";`, and the generic intrinsic-asm path writes the operand as-is, so flags with no OptiX equivalent silently miscompile (exit 0, then a runtime GPU fault reading like a null-ptr deref). The correct fix is a compile-time diagnostic, not a bit translation, because the flags ARE meaningful — OptiX just can't express them per-ray (it controls triangle/AABB skipping at the pipeline level). Any `case cuda: __intrinsic_asm "..."` bare pass-through in a `.meta.slang` `__target_switch` does zero operand validation, so enum/flag args whose value space differs between HLSL/DXR and OptiX are candidates for this same silent-miscompile ([CUDA/OptiX TraceRay ray-flags are a bare intrinsic-asm pass-through](../learnings/1787172018498-cuda-optix-traceray-ray-flags-are-a-bare-intrinsic.md)). The exact mask, resolved from `external/optix-dev/include/optix_types.h`: `OptixRayFlags` defines bits 0–7 plus `FORCE_OPACITY_MICROMAP_2_STATE=1<<10` (=0x400) — no bit 8 or 9. HLSL RAY_FLAG maps identically for bits 0–7 (including `CULL_OPAQUE(0x40)↔CULL_DISABLED_ANYHIT` — value AND semantics match, NOT a hazard) and `RAY_FLAG_FORCE_OMM_2_STATE(0x400)↔FORCE_OPACITY_MICROMAP_2_STATE` (coincident, DOES translate). **The ONLY unsupported HLSL bits are `SKIP_TRIANGLES=0x100` and `SKIP_PROCEDURAL_PRIMITIVES=0x200`.** Correct mask: supported = 0x4FF, unsupported = `flags & ~0x4FF` — key it off the named OptiX set, not a `>=0x100` threshold (which would wrongly flag 0x400) ([HLSL RAY_FLAG vs OptiX OptixRayFlags — only 0x100/0x200 lack an equivalent](../learnings/1787173053502-hlsl-ray-flag-vs-optix-optixrayflags-only-0x100-0x.md)).

A second, orthogonal trap in `case cuda: __intrinsic_asm` beyond that missing operand validation: the CUDA arm forwards **ALL** of the enclosing function's arguments **positionally**, whereas the spirv/glsl arms call helpers with EXPLICIT operands (e.g. `__spirvExecuteShaderEXT(HitOrMiss, p)` / `__glslInvoke(HitOrMiss, __rayPayloadLocation(p))`) that pass a fixed operand list regardless of the enclosing signature. So when mirroring a `__target_switch` case across overloads of different arity in `hlsl.meta.slang` (slang#12553), copying the 3-arg overload's `case cuda: __intrinsic_asm "optixInvoke";` verbatim into a 2-arg overload emits `optixInvoke(hit, payload)` instead of `optixInvoke(accelStruct, hit, payload)` — an arity the CUDA prelude never provided, so NVRTC errors `no instance of overloaded function "optixInvoke" matches the argument list`. The fix adds a matching-arity wrapper to `prelude/slang-cuda-prelude.h` that forwards to the existing one (a null `(OptixTraversableHandle)0` handle — the 3-arg wrapper ignores both handles and packs only the payload, so it is exact, not a stub). Two verification lessons: `-target cuda` returning EXIT 0 was a SILENT no-op (the invoke was dropped, not compiled) — the real CUDA-codegen gate is `-target ptx -Xnvrtc -I external/optix-dev/include/`, which actually compiles the emitted C++ through NVRTC (present in the fleet env); and missing-return E41009 is target-gated (`doesTargetAllowMissingReturns`, `slang-ir-missing-return.cpp:18-26`, false ONLY for Khronos/WGPU), so the same core-module gap gives E41009 on SPIR-V/GLSL, a silent drop on CUDA, and nothing on DXIL (matches `case hlsl:`) — do not frame it as "warning on DXIL" ([case cuda __intrinsic_asm forwards args positionally — dropping an arg breaks NVRTC arity](../learnings/1786786566207-case-cuda-intrinsic-asm-forwards-args-positionally.md)).

## The NVRTC-compiled prelude and version gating

The entire `prelude/slang-cuda-prelude.h` is prepended verbatim to the NVRTC translation unit, so every helper must compile against the user's OptiX SDK version regardless of whether it's called. OptiX intrinsics are version-tiered (`optixTraverse` is 8.0+, `optixMakeHitObject` full form is 9.0 with an 8.1 `#elif`, ordinary `optixTrace` is 7.x), so a helper added without its `#if (OPTIX_VERSION >= NNNNN)` guard breaks ALL RT shaders on lower SDKs — when a `-target ptx` compile fails with `no instance of overloaded function "optixXxx"` even for a trivial shader, suspect an ungated prelude helper, not the user's code. The fix adds the missing guard; do NOT declare a global minimum version and drop lower-SDK support without a maintainer's policy call. This recurs because filecheck tests only compile against the bundled OptiX 9.0 headers (the #10503 coverage gap) ([OptiX version-gating bugs in slang-cuda-prelude.h recur — the whole prelude is NVRTC-compiled](../learnings/1787175488691-optix-version-gating-bugs-in-slang-cuda-prelude-h-.md)). Do NOT guess the threshold: `external/optix-dev` has every version as a git tag — `git show v8.0.0:include/optix_device.h | grep -c 'void optixTraverse('`. Trap: in OptiX 7.x the real device decls live in `optix_7_device.h` (the plain `optix_device.h` is a 47-line wrapper), so grepping only `optix_device.h` for a 7.x tag gives a false "absent." Use a single `#if` when the signature is unchanged across tiers; tier only when it changes. Verify GPU-free by extracting old headers and running a prelude probe with nvcc; a testless PR is often correct here (the in-tree headers are 9.0, so no CI test can fail-before/pass-after — document the out-of-band verification) ([resolve OptiX prelude version-gate thresholds from optix-dev git tags, verify GPU-free with nvcc](../learnings/1787227776278-resolve-optix-prelude-version-gate-thresholds-from.md)).

## noinline policy and inout subobject lowering

Making CUDA emit `__noinline__` is a mechanism/policy split: PR #12419 made CUDA the 4th backend to *emit* the decoration from an existing `IRNoInlineDecoration`, but generated code has zero hand-written `[noinline]`, so it recovers 0% on its own; #12620 is the follow-up policy (a heuristic deciding which device funcs to mark). A heuristic noinline pass MUST be CUDA-target-gated: `IRNoInlineDecoration` has zero consumers in `slang-ir-inline.cpp` (it is purely a downstream hint), but SPIR-V (`DontInline`), LLVM (`noinline`), and HLSL (`[noinline]`) emitters already emit from it — an ungated pass would make those backends start emitting noinline and regress them. Recommended shape: an opt-in `-cuda-noinline-threshold=<n>` flag (default OFF → byte-identical output) driving a CUDA-gated IR pass that runs AFTER `performForceInlining`, BEFORE emit ([CUDA noinline: a heuristic pass must be target-gated](../learnings/1787146175748-cuda-noinline-a-heuristic-pass-must-be-target-gate.md)).

For CUDA/OptiX wrong-code around `inout` params: Slang's front end represents `inout` with copy-in/copy-out wrappers, but `addArg` only materializes a temp for a NON-addressable l-value — for an addressable subobject like `path.sg` it passes the field-address DIRECTLY (`&path.sg`) with no copy. For CUDA/CPP an `inout T` param emits as a POINTER `T*` (not a C++ reference), and `undoParameterCopy` (scheduled for CUDA/Metal/CPP) actively REMOVES copy-in/out temps to pass direct pointers — *specifically because* OptiX abort intrinsics (`IgnoreHit`/`TerminateRay`) can abort BEFORE a copy-back would run, silently dropping the payload mutation. WGSL does the OPPOSITE: `legalizeCall` materializes a `function`-space temp with copy-in/copy-out unconditionally (WGSL forbids a pointer to a struct field). So the "temporary workaround" reporters ask for (copy-in/out the subobject) is ALREADY implemented for WGSL and is the natural analogue for CUDA — but landing it on CUDA is design-gated: it must not reintroduce the abort-before-writeback hazard (restrict to provably-abort-free callees, or write back on all exit paths). Also: a green SPIR-V/HLSL run never clears a CUDA param-passing change — the CUDA emitter inherits `CPPSourceEmitter` and its `-target cuda` emit is GPU-free FileCheck-verifiable ([CUDA vs WGSL inout-subobject lowering divergence (and the undoParameterCopy abort-safety constraint)](../learnings/1788636814094-cuda-vs-wgsl-inout-subobject-lowering-divergence-a.md)).
