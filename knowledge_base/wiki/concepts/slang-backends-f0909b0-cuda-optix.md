## TL;DR

CUDA/OptiX backend facts, mostly around ray tracing, the NVRTC-compiled prelude, and GPU-free verification:

- **OptiX payload register count is carried by a separate `payloadSize` operand, NOT the `_optix_trace_typed_32` name** — that one 32-slot transport is emitted for every payload size. When triaging "traced as N registers," grep the `payloadSize` immediate, not the intrinsic symbol. The prelude's `optix*WithRegs` helpers have fixed-width `N<=16`/`N<=32` catch-alls that over-read/over-write for N in [9,15] AND [17,31].
- **An `inout` ray payload is legalized TWICE** (VaryingInput + VaryingOutput), and a direction-agnostic `case RayPayload:` branch double-reads the registers. The dead reads survive DCE because `kIROp_GetOptiXPayloadRegister` is conservatively side-effecting — fix at the producer, don't mark it pure.
- **OptiX hit-attribute lowering is field-wise (one 32-bit register per scalar leaf), not byte-packed.** A `ReportHit` write path must gather leaves into ONE `optixReportIntersection` call (OptiX has no per-attribute setter), and must emit `__float_as_uint` explicitly (CUDA `kIROp_BitCast` is a numeric cast, not bit-preserving).
- **HLSL ray flags are passed verbatim into `optixTrace` with no validation.** Only `RAY_FLAG_SKIP_TRIANGLES`(0x100) and `SKIP_PROCEDURAL_PRIMITIVES`(0x200) lack an OptiX equivalent (0x400 DOES map); key an "unsupported" diagnostic off the named `OptixRayFlags` set (supported = 0x4FF), not a `>=0x100` threshold.
- **`OptixRayFlags` bits 0–7 are identical in every OptiX release 7.0–9.1, but the 0x400 OMM flag first appears in 7.6.0**, so emitting ray flags by name needs `#if OPTIX_VERSION >= 70600` around it. A long-lived draft adding a `slang-diagnostics.lua` entry must re-check its code against master before rebasing.
- **Lower shader-record (SBT) globals to an opaque intrinsic only after `specializeResourceUsage` and the global-init move.** Earlier, a `ConstantBuffer<T>` helper param stays unspecialized and its reads get `__ldg` (the #10188 stale-SBT read), `expand` bodies crash, and per-entry-point reference graphs miss generic calls and the static initializers CUDA injects into EVERY entry point.
- **On CUDA, GeometryIndex means the OptiX SBT GAS index** (HitObject since SER; pipeline `GeometryIndex()` since PR #13437, via `optixGetSbtGASIndex()`, OptiX >= 7.1). It equals the DXR geometry ordinal only under slang-rhi's one-record-per-input layout.
- **The whole `slang-cuda-prelude.h` is fed to NVRTC verbatim**, so any OptiX helper using an SDK-N symbol without `#if (OPTIX_VERSION >= NNNNN)` breaks ALL RT shaders on older SDKs. Resolve thresholds from `external/optix-dev` git tags (7.x decls live in `optix_7_device.h`), verify GPU-free with nvcc.
- **Slang never forwards `-O<n>` to NVRTC** (the driver's switch has been commented out since 2019), and NVRTC optimizes by default with no `-O` flag, so `-target ptx -O0` and `-O3` give byte-identical PTX. Never blame "-O3 not forwarded" for a missing CUDA optimization.
- **A 1D CUtexObject from slang-rhi is array-backed, so an integer 1D texel Load must use `tex.level.2d … [x,0]`.** Integer `tex.level.1d` compiles to the linear-memory `TLD … 1D` (same as `tex1Dfetch`) and reads zeros. Decide PTX texture forms GPU-free from SASS (`cuobjdump -sass | grep -E 'TLD|TEX'`).
- **CUDA `noinline` policy must be target-gated** — `IRNoInlineDecoration` is already consumed by SPIR-V/LLVM/HLSL emitters, so an ungated heuristic pass would regress them.
- **`inout` subobject copy-in/out is design-gated on CUDA** by the `undoParameterCopy` abort-safety constraint (OptiX abort intrinsics can skip writeback); WGSL already does the copy unconditionally.
- **A `case cuda: __intrinsic_asm "name"` forwards ALL of the enclosing function's args positionally** (unlike the spirv/glsl cases, which pass explicit helper operands), so mirroring a `__target_switch` case across overloads of different arity emits a wrong-arity CUDA call NVRTC rejects — add a matching-arity prelude wrapper. Gate CUDA-codegen correctness on `-target ptx -Xnvrtc` (a bare `-target cuda` EXIT 0 can be a silent drop, and missing-return E41009 is target-gated OFF for CUDA/DXIL).

## OptiX payloads: register count is `payloadSize`, and `inout` is legalized twice

`_optix_trace_typed_32` is OptiX's ONE register-trace transport — 32 inline-asm register slots are ALWAYS emitted regardless of payload size; the real payload word count is conveyed SOLELY by a separate `payloadSize = (int)sizeof...(Payload)` operand. So the intrinsic name appears in the PTX for N=8, N=16, N=40 too; when triaging a "traced as 32 registers" report, grep the `payloadSize` immediate loaded before the trace call, not the symbol — the bug is Slang passing the wrong number of `pr.regs[i]` ARGUMENTS. The prelude's `optixTraceWithRegs`/`optixTraverseWithRegs`/`optixInvokeWithRegs` each have `if constexpr (N==0..8)` branches then TWO fixed-width catch-alls (`N<=16` passes regs[0..15], `N<=32` passes regs[0..31]), so `PayloadRegisters<T,N>` is over-read/over-written for N in [9,15] AND [17,31] — when a report cites one window, check the sibling catch-all branch. OOB is read AND write (OptiX's variadic trace assigns returned values back), but NVRTC scalarizes the struct so the PTX has undefined extra register operands, not materialized stack OOB — distinguish source-level UB from PTX manifestation; scope the verdict to the codegen defect and disclaim the runtime hang as "consistent with, not proven" (repro is GPU-free via `-target cuda`/`-target ptx`) ([Slang CUDA/OptiX payload register count is carried by payloadSize](../learnings/1786644040522-slang-cuda-optix-payload-register-count-is-carried.md)).

An `inout` ray payload is legalized TWICE and double-reads its registers: `processMutableParam` calls `createLegalVaryingVal` once as `VaryingInput` and once as `VaryingOutput`, and the CUDA `case LayoutResourceKind::RayPayload:` keys off `getLayoutResourceKind` (always `RayPayload`) while IGNORING `info.kind` (the requested direction), so the register readback (`emitOptiXPayloadRead`) fires on BOTH passes → double reads. Writeback stays correct because a `getCount()==0` guard dedups writeback REGISTRATION only — that guard is the smoking gun (an author who dedups a secondary effect but not the primary one knew the branch runs twice). The dead reads survive DCE because `kIROp_GetOptiXPayloadRegister` has no `hoistable`/pure flag and isn't side-effect-free, so `mightHaveSideEffects()` is conservatively true — so the fix must be "don't emit the second read" (producer), NOT "mark pure so DCE cleans it" (a mutable payload register can be legitimately re-read). Reproducible without a GPU via text CUDA emit + `-dump-ir` ([OptiX inout ray-payload legalized twice: direction-agnostic RayPayload branch double-reads](../learnings/1786656384074-optix-inout-ray-payload-legalized-twice-direction-.md)).

## Hit attributes and ray flags

OptiX hit-attribute lowering is field-wise — one 32-bit OptiX attribute register per scalar leaf — NOT a byte-packed/padding-preserving blob: `emitOptiXAttributeFetch` recurses fields/elements/lanes and consumes exactly one register per scalar `IRBasicType` leaf (CUDA emit wraps float leaves in `__int_as_float`). The 8-register/32-byte cap + its diagnostic live in the legalize pass. So anyone extending `ReportHit` to CUDA must flatten the WRITE side field-wise to match the reader — a whole-struct `bit_cast<uint[N]>` would DESYNC on padding, sub-dword fields, and float bit layout → silent wrong runtime values; the read path is the canonical contract ([OptiX hit-attribute lowering is field-wise, not byte-packed](../learnings/1787174981538-optix-hit-attribute-lowering-is-field-wise-not-byt.md)). The `ReportHit` write path (slang#12637) adds several sharp facts: OptiX has NO per-attribute-register setter (contrast ray *payloads*, which have `optixSetPayload_N`) — hit attributes are written ONLY via one `optixReportIntersection(hitT, hitKind, a0..a7)` call, so the write path must gather all leaves into ONE call, not per-register stores; **CUDA lowers `kIROp_BitCast` as a plain numeric C cast, NOT bit-preserving**, so moving a float into a 32-bit attribute register requires an explicit `__float_as_uint(x)` (an IR BitCast would emit `(unsigned int)(0.5f)` → 0; verify via PTX: `0.5f` → `1056964608` = `0x3F000000`); a new target-specific IR marker op carrying an aggregate operand must be flattened AFTER post-inline DCE but BEFORE empty-type/resource legalization; and FileCheck slang-tests are silently IGNORED when slang-llvm is absent (a vacuous `0/0` pass) — verify CUDA/OptiX emit by direct `slangc -target cuda` + per-leaf grep ([OptiX ReportHit write path: no attribute setter, non-bit-preserving CUDA BitCast, pass ordering](../learnings/1787792439688-optix-reporthit-write-path-no-attribute-setter-non.md)).

HLSL `TraceRay`'s ray-flags argument is emitted verbatim into `optixTrace(...)` with NO bit validation — the CUDA arm of `TraceRay`'s `__target_switch` is literally `case cuda: __intrinsic_asm "optixTrace";`, and the generic intrinsic-asm path writes the operand as-is, so flags with no OptiX equivalent silently miscompile (exit 0, then a runtime GPU fault reading like a null-ptr deref). The correct fix is a compile-time diagnostic, not a bit translation, because the flags ARE meaningful — OptiX just can't express them per-ray (it controls triangle/AABB skipping at the pipeline level). Any `case cuda: __intrinsic_asm "..."` bare pass-through in a `.meta.slang` `__target_switch` does zero operand validation, so enum/flag args whose value space differs between HLSL/DXR and OptiX are candidates for this same silent-miscompile ([CUDA/OptiX TraceRay ray-flags are a bare intrinsic-asm pass-through](../learnings/1787172018498-cuda-optix-traceray-ray-flags-are-a-bare-intrinsic.md)). The exact mask, resolved from `external/optix-dev/include/optix_types.h`: `OptixRayFlags` defines bits 0–7 plus `FORCE_OPACITY_MICROMAP_2_STATE=1<<10` (=0x400) — no bit 8 or 9. HLSL RAY_FLAG maps identically for bits 0–7 (including `CULL_OPAQUE(0x40)↔CULL_DISABLED_ANYHIT` — value AND semantics match, NOT a hazard) and `RAY_FLAG_FORCE_OMM_2_STATE(0x400)↔FORCE_OPACITY_MICROMAP_2_STATE` (coincident, DOES translate). **The ONLY unsupported HLSL bits are `SKIP_TRIANGLES=0x100` and `SKIP_PROCEDURAL_PRIMITIVES=0x200`.** Correct mask: supported = 0x4FF, unsupported = `flags & ~0x4FF` — key it off the named OptiX set, not a `>=0x100` threshold (which would wrongly flag 0x400) ([HLSL RAY_FLAG vs OptiX OptixRayFlags — only 0x100/0x200 lack an equivalent](../learnings/1787173053502-hlsl-ray-flag-vs-optix-optixrayflags-only-0x100-0x.md)).

https://github.com/NVIDIA/optix-dev.git && git sparse-checkout set include`. A process note from

A second, orthogonal trap in `case cuda: __intrinsic_asm` beyond that missing operand validation: the CUDA arm forwards **ALL** of the enclosing function's arguments **positionally**, whereas the spirv/glsl arms call helpers with EXPLICIT operands (e.g. `__spirvExecuteShaderEXT(HitOrMiss, p)` / `__glslInvoke(HitOrMiss, __rayPayloadLocation(p))`) that pass a fixed operand list regardless of the enclosing signature. So when mirroring a `__target_switch` case across overloads of different arity in `hlsl.meta.slang` (slang#12553), copying the 3-arg overload's `case cuda: __intrinsic_asm "optixInvoke";` verbatim into a 2-arg overload emits `optixInvoke(hit, payload)` instead of `optixInvoke(accelStruct, hit, payload)` — an arity the CUDA prelude never provided, so NVRTC errors `no instance of overloaded function "optixInvoke" matches the argument list`. The fix adds a matching-arity wrapper to `prelude/slang-cuda-prelude.h` that forwards to the existing one (a null `(OptixTraversableHandle)0` handle — the 3-arg wrapper ignores both handles and packs only the payload, so it is exact, not a stub). Two verification lessons: `-target cuda` returning EXIT 0 was a SILENT no-op (the invoke was dropped, not compiled) — the real CUDA-codegen gate is `-target ptx -Xnvrtc -I external/optix-dev/include/`, which actually compiles the emitted C++ through NVRTC (present in the fleet env); and missing-return E41009 is target-gated (`doesTargetAllowMissingReturns`, `slang-ir-missing-return.cpp:18-26`, false ONLY for Khronos/WGPU), so the same core-module gap gives E41009 on SPIR-V/GLSL, a silent drop on CUDA, and nothing on DXIL (matches `case hlsl:`) — do not frame it as "warning on DXIL" ([case cuda __intrinsic_asm forwards args positionally — dropping an arg breaks NVRTC arity](../learnings/1786786566207-case-cuda-intrinsic-asm-forwards-args-positionally.md)).

On `-target cuda`, GeometryIndex is the OptiX SBT GAS index: `HitObject.GetGeometryIndex()` lowers to `optixHitObjectGetSbtGASIndex()`, `HitObject.MakeHit`'s `GeometryIndex` argument is passed as `sbtGASIdx`, and since PR #13437 (merged 2026-10-06) the pipeline `GeometryIndex()` gets a `case cuda:` calling `optixGetSbtGASIndex()` (it was E36107 before). OptiX (through 9.0) has no build-input-ordinal query; the SBT GAS index is the sum of `numSbtRecords` over earlier inputs plus the per-primitive `sbtIndexOffset`, and offsets must lie in [0, numSbtRecords-1] (`optix_types.h:717`), so one record per input (slang-rhi's layout) forces offset 0 and the index equals the DXR ordinal. DeepWiki conflated the pipeline function with the HitObject method ([CUDA SER path already treats GeometryIndex as the OptiX SBT GAS index](../learnings/1790318608424-slang-cuda-ser-path-already-treats-geometryindex-a.md)). `optixGetSbtGASIndex()` first appears in OptiX 7.1.0, so `GeometryIndex()` on CUDA needs OptiX >= 7.1; against 7.0 headers NVRTC reports it undefined ([optixGetSbtGASIndex needs OptiX >= 7.1](../learnings/1791203817991-optixgetsbtgasindex-needs-optix-7-1-reviewer-a-bac.md)). Separately, the OptiX 9 prelude `optixMakeHitObject` overloads build the hit from `optixHitObjectGetTraverseData` and ignore `MakeHit`/`MakeMotionHit`'s explicit hit args, a known gap documented in docs/cuda-target.md ([property-getter `[require]` is not enforced](../learnings/1791199099928-slang-property-getter-require-is-not-enforced-a-mi.md)).

## The NVRTC-compiled prelude and version gating

The entire `prelude/slang-cuda-prelude.h` is prepended verbatim to the NVRTC translation unit, so every helper must compile against the user's OptiX SDK version regardless of whether it's called. OptiX intrinsics are version-tiered (`optixTraverse` is 8.0+, `optixMakeHitObject` full form is 9.0 with an 8.1 `#elif`, ordinary `optixTrace` is 7.x), so a helper added without its `#if (OPTIX_VERSION >= NNNNN)` guard breaks ALL RT shaders on lower SDKs — when a `-target ptx` compile fails with `no instance of overloaded function "optixXxx"` even for a trivial shader, suspect an ungated prelude helper, not the user's code. The fix adds the missing guard; do NOT declare a global minimum version and drop lower-SDK support without a maintainer's policy call. This recurs because filecheck tests only compile against the bundled OptiX 9.0 headers (the #10503 coverage gap) ([OptiX version-gating bugs in slang-cuda-prelude.h recur — the whole prelude is NVRTC-compiled](../learnings/1787175488691-optix-version-gating-bugs-in-slang-cuda-prelude-h-.md)). Do NOT guess the threshold: `external/optix-dev` has every version as a git tag — `git show v8.0.0:include/optix_device.h | grep -c 'void optixTraverse('`. Trap: in OptiX 7.x the real device decls live in `optix_7_device.h` (the plain `optix_device.h` is a 47-line wrapper), so grepping only `optix_device.h` for a 7.x tag gives a false "absent." Stock 7.0.0 headers do not compile under NVRTC 12.x at all (`optix_7_types.h` has an unguarded `#include <stddef.h>`, which 7.1.0 guards with `#if !defined(__CUDACC_RTC__)`), so put a stub `stddef.h` on `-Xnvrtc -I` to probe 7.0 symbols ([same](../learnings/1791203817991-optixgetsbtgasindex-needs-optix-7-1-reviewer-a-bac.md)). Use a single `#if` when the signature is unchanged across tiers; tier only when it changes. Verify GPU-free by extracting old headers and running a prelude probe with nvcc; a testless PR is often correct here (the in-tree headers are 9.0, so no CI test can fail-before/pass-after — document the out-of-band verification) ([resolve OptiX prelude version-gate thresholds from optix-dev git tags, verify GPU-free with nvcc](../learnings/1787227776278-resolve-optix-prelude-version-gate-thresholds-from.md)).

## noinline policy and inout subobject lowering

Making CUDA emit `__noinline__` is a mechanism/policy split: PR #12419 made CUDA the 4th backend to *emit* the decoration from an existing `IRNoInlineDecoration`, but generated code has zero hand-written `[noinline]`, so it recovers 0% on its own; #12620 is the follow-up policy (a heuristic deciding which device funcs to mark). A heuristic noinline pass MUST be CUDA-target-gated: `IRNoInlineDecoration` has zero consumers in `slang-ir-inline.cpp` (it is purely a downstream hint), but SPIR-V (`DontInline`), LLVM (`noinline`), and HLSL (`[noinline]`) emitters already emit from it — an ungated pass would make those backends start emitting noinline and regress them. Recommended shape: an opt-in `-cuda-noinline-threshold=<n>` flag (default OFF → byte-identical output) driving a CUDA-gated IR pass that runs AFTER `performForceInlining`, BEFORE emit ([CUDA noinline: a heuristic pass must be target-gated](../learnings/1787146175748-cuda-noinline-a-heuristic-pass-must-be-target-gate.md)).

**What NVRTC/NVVM do with the optimization level and at a `__noinline__` boundary** (verified 2026-10-02, master 8fbd9d033, CUDA 12.6). `slang-code-gen.cpp:796-812` maps `-O<n>` into `DownstreamCompileOptions::optimizationLevel`, but the NVRTC driver never reads it: the switch at `slang-nvrtc-compiler.cpp:1234-1238` has been commented out since #1151 (2019). NVRTC has no `-O` option (`-Xnvrtc -O3` → "unrecognized option") and optimizes by default; `-g` adds `--device-debug` plus `--dopt=on` (CUDA ≥ 11.7). So `-target ptx -O0` and `-O3` give byte-identical PTX, and `-O0` is not honored downstream. Measured with hand-edited CUDA and `ptxas -v`, NVVM promotes a pointer-to-struct parameter to scalars across `__noinline__` (dropping the caller's copy) only if aliasing is ruled out — the param is `__restrict__`, or the callee reads it before writing through another pointer — and even then promotion stopped above 3 fields read (4 or 9 fields kept the full copy; an observed threshold, with the responsible NVVM pass unconfirmed; LLVM ArgumentPromotion defaults to 3 in LLVM 14, 2 in LLVM 15). For the signature-rewrite direction (#13108 / #13177): passing a field pointer (`&s.a`) still makes the caller's struct escape, so its frame stays; copy-in plus write-back after the call removes the frame but is unsafe on CUDA/OptiX under IgnoreHit/thread termination (the `undoParameterCopy` rationale, `slang-ir-undo-param-copy.cpp:9`, below). Tooling: PTX from `slangc -target ptx` ends with a NUL byte, so grep it with `-a` or strip it with `tr -d '\000'` ([Slang never forwards -O<n> to NVRTC; NVVM argpromotion across __noinline__ is narrow](../learnings/1790961575284-slang-never-forwards-o-n-to-nvrtc-nvrtc-optimizes-.md)).

For CUDA/OptiX wrong-code around `inout` params: Slang's front end represents `inout` with copy-in/copy-out wrappers, but `addArg` only materializes a temp for a NON-addressable l-value — for an addressable subobject like `path.sg` it passes the field-address DIRECTLY (`&path.sg`) with no copy. For CUDA/CPP an `inout T` param emits as a POINTER `T*` (not a C++ reference), and `undoParameterCopy` (scheduled for CUDA/Metal/CPP) actively REMOVES copy-in/out temps to pass direct pointers — *specifically because* OptiX abort intrinsics (`IgnoreHit`/`TerminateRay`) can abort BEFORE a copy-back would run, silently dropping the payload mutation. WGSL does the OPPOSITE: `legalizeCall` materializes a `function`-space temp with copy-in/copy-out unconditionally (WGSL forbids a pointer to a struct field). So the "temporary workaround" reporters ask for (copy-in/out the subobject) is ALREADY implemented for WGSL and is the natural analogue for CUDA — but landing it on CUDA is design-gated: it must not reintroduce the abort-before-writeback hazard (restrict to provably-abort-free callees, or write back on all exit paths). Also: a green SPIR-V/HLSL run never clears a CUDA param-passing change — the CUDA emitter inherits `CPPSourceEmitter` and its `-target cuda` emit is GPU-free FileCheck-verifiable ([CUDA vs WGSL inout-subobject lowering divergence (and the undoParameterCopy abort-safety constraint)](../learnings/1788636814094-cuda-vs-wgsl-inout-subobject-lowering-divergence-a.md)).

When a built-in (e.g. a ray-tracing intrinsic) is rejected for a target with `E36107: unavailable features in entry point`, suspect the FIRST argument of its `[require(<target-atom-set>, <capability>)]` — the abstract target set (`glsl_spirv`, `cuda_glsl_spirv`, …) — not the capability compound named second. In `hlsl.meta.slang`, `TraceMotionRay`/`RayCurrentTime` are `[require(glsl_spirv, raytracing_motionblur_…)]`; the reporter assumed the capability was the gate, but `raytracing_motionblur` already includes a `cuda` conjunct — the real block is the narrow `glsl_spirv` first arg (a sibling, `HitObject.TraceMotionRay`, uses `cuda_glsl_spirv` and works on CUDA). E36107 prints two `note:` lines — the use site AND the `[require]` declaration — so jump to the declaration and compare its first arg to a working sibling's. The fix lands lock-step: widen the `[require]` first arg, add the matching `case <target>: __intrinsic_asm` arm, and — for a value-bearing call whose new overload has different arity — add the matching-arity prelude overload (the CUDA case forwards all args positionally, per the arity note below), and reproduce GPU-free with `slangc repro.slang -target <t> -entry … -stage …` ([E36107 on a CUDA RT intrinsic: check the `[require]` FIRST-arg target set, not the capability compound](../learnings/1789186196430-e36107-for-an-rt-intrinsic-on-cuda-check-the-requi.md)).

NVRTC `-pch` for the CUDA prelude shipped in PR #12880, gated on NVRTC ≥12.8 AND the leading-`#include` prelude form (it helps only the `#include` prelude, not prepended text; a one-shot `-pch` is a net regression, so the code amortization-gates it; the 256 MB default heap is managed reactively). `nvrtcGetPCHCreateStatus` loads as an OPTIONAL/null-tolerant symbol (init() still works on <12.8) and a Slang-owned `slang-nvrtc-pch-status: created|not-created|create-failed` diagnostics token lets a unit test read the PCH outcome. Two review gotchas from the cycle: reading `IArtifactDiagnostics::getRaw()` with no diagnostics appended returned a `nullptr`-backed terminated slice whose `SLANG_ASSERT(in[0]==0)` then deref'd null — make the empty terminated slice `""`-backed (a real NUL) and exercise the "no output" branch of any diagnostics-reading test; and `getDownstreamCompilerVersion` was removed from master (use the compiler `Desc` version via `getDesc()`/`SemanticVersion`), so a branch cut from stale master compiled locally yet would not merge — confirm the branch is rebased onto current `origin/master` before trusting "builds locally", and note a DRAFT PR skips Slang CI (`draft != true`), so the ≥12.8 behavioral asserts don't run until it is marked ready ([empty-diagnostics null-deref + removed getDownstreamCompilerVersion](../learnings/1789272763883-nvrtc-pch-review-slang-12880-empty-diagnostics-nul.md), [NVRTC -pch for the CUDA prelude SHIPPED (#12880)](../learnings/1789272870056-nvrtc-pch-for-cuda-prelude-shipped-pr-12880-findin.md)).

A super-linear **downstreamCompile timer** on a matrix-heavy CUDA kernel is nvrtc-intrinsic, not a Slang emit-size artifact. Slang emits **O(N)** CUDA C++ for an N-matrix-multiply chain — CUDA does not legalize/scalarize matrix types (`targetLegalizesMatrixTypes()` is false for CUDA), matrices stay as the prelude `Matrix<T,ROWS,COLS>` struct, and `mul(matrix,matrix)` is `[__readNone]` (not force-inline) so it emits once as a specialized helper with N call sites. The downstreamCompile timer (PR #13050) wraps exactly the downstream `compiler->compile(...)` call (`slang-code-gen.cpp:1028`), which for `-target ptx`/`cuda` is the NVRTC wrapper — so it isolates nvrtc's own source→PTX cost and *excludes* Slang's IR passes (including the already-tracked O(n²) redundancy-removal cost of #13010/#13059). Therefore super-linearity in that bucket on an O(N)-source kernel is genuinely nvrtc-intrinsic → upstream NVIDIA, no Slang code lever (likely register-pressure/dependency-chain pathology in nvrtc's allocator). Don't assume Slang handed nvrtc a super-linearly-larger input; and note the reporter's `backend_matrix`/`gen_matrix_chain` workloads are local/uncommitted (grep of `tools/compile-perf/` is empty — only `codegen_ptx`/`gen_codegen` scalar math is committed), so their exact numbers aren't reproducible from the repo ([a downstreamCompile-timer super-linearity on a matrix kernel is nvrtc-intrinsic, not a Slang emit-size artifact](../learnings/1789389982745-a-downstreamcompile-timer-super-linearity-on-a-mat.md)).

## 1D texture integer Load: array-backed textures need the 2D form (#12630)

Choose the PTX texture form from SASS, which needs no GPU: `nvcc -arch=sm_XX -cubin x.cu && cuobjdump -sass x.cubin | grep -E 'TLD|TEX'`, then read the dimension token at the end of each texture instruction. For slang#12630 (nvcc 12.6, identical on sm_52/61/70/75/80/86/89/90): integer `tex.level.1d.v4.f32.s32` → `TLD … 1D`, the same opcode and dimension as `tex1Dfetch` (the linear-memory fetch); CUDA's own `tex1DLod<float4>` on a 1D texture object → `TEX … 2D`; `tex.level.2d…s32 [t,{x,0}]` → `TLD … 2D`; `tex.level.a1d…s32` → `TLD … ARRAY_1D`. Every 1D CUtexObject slang-rhi creates is array-backed, so the matching integer fetch is the 2D one at row 0. That is consistent with the L40S result where `tex.level.1d…s32` returned all zeros. Status: PR #13377, not yet runtime-verified; its T4 CUDA test checks values. Container and test gotchas from the same task: a GPU-less container with a stale CMake cache fails to link on `'/usr/lib/x86_64-linux-gnu/libcuda.so' missing` (reconfigure with `-DCUDA_cuda_driver_LIBRARY=/usr/local/cuda/lib64/stubs/libcuda.so`); the render-test CPU backend has no `Texture1D` subscript operator, and its integer texel unpackers cover only RGBA32Uint/R32Uint/R16Uint (no RGBA8Uint/Sint or RGBA32Sint; the run produces empty output with no clear error), so a `-cpu` reference line has to use RGBA32Uint and Sint coverage has to be CUDA-only; a bot `workflow_dispatch` of ci.yml can wait on two gates (`wait-for-human-priority` yielding, and the `falcor-ci` environment approval only ci-approvers grant), and `ci-retry-yielded-bot` retries only completed runs, so a run parked on falcor-ci never yields a CUDA result on its own ([CUDA 1D texture Load: integer tex.level.1d = linear-memory TLD.1D](../learnings/1790894433645-cuda-1d-texture-load-integer-tex-level-1d-linear-m.md)).

## Shader-record (SBT) globals: lower after specialization and the global-init move

Consider PR #12646 (slang#12628), which maps a global `shaderRecordEXT` `ConstantBuffer` to the
OptiX SBT on CUDA by rewriting the `IRGlobalParam` into an opaque intrinsic, `GetOptiXSbtDataPtr`.
Placed early in `linkAndOptimizeIR`, next to `collectOptiXEntryPointUniformParams`
(`slang-emit.cpp` ~:1391), the rewrite broke three things, all reproduced on a Release build.
First, `specializeResourceUsage` (~:2097) specializes a callee's ConstantBuffer/resource
parameter only when the call-site argument is a `kIROp_GlobalParam`
(`slang-ir-specialize-resources.cpp` ~:740; any other opcode gives `ThisFuncFailed`). A helper
`float4 readIt(ConstantBuffer<T> cb)` therefore stayed unspecialized and the raw SBT pointer
flowed into the parameter; the `isPointerToImmutableLocation` walker cannot see the
`GetOptiXSbtDataPtr` root through a function parameter, so the callee emitted
`__ldg(&cb->field)`, which is the #10188 stale-SBT-read bug. Second, a use inside an `expand` body
crashed slangc, because `IRExpand` owns a block but is not an `IRGlobalValueWithCode`, and
`specializeModule` (~:1552) had not run yet. Third, a reference-graph diagnostic missed
interface/generic calls, since before specialization the call graph does not follow witness
tables. Moving the rewrite to just after `specializeResourceUsage` fixed all three. The review
probe is `readIt(gSbt)` with a ConstantBuffer-typed parameter, then a grep of the callee for
`__ldg`
[rewriting a global param into an opaque intrinsic before specializeResourceUsage](../learnings/1790827641249-cuda-optix-rewriting-a-global-param-into-an-opaque.md),
[lower shader-record globals after specialization](../learnings/1790831529525-cuda-optix-lower-shader-record-globals-after-speci.md).

The pass order has a second constraint. `moveGlobalVarInitializationToEntryPoints`
(`slang-ir-explicit-global-init.cpp` ~:107-114, 187-240) injects EVERY global initializer into
EVERY entry point, even entry points that never reference the global, and CUDA/CPU run it late
(~:2483). Any per-entry-point diagnostic built from `buildEntryPointReferenceGraph` before that
pass is therefore unsound for uses inside a `static` initializer. With an RT entry point and a
compute entry point in one compile plus `static uint x = gSbt.id;`, the compute kernel ends up
calling `optixGetSbtDataPointer()` with no error; on SPIR-V spirv-val catches the analog
(VUID-07119), but on CUDA nothing does. Run such lowering after the global-init move (~:2490)
[every static initializer reaches every entry point](../learnings/1790827641249-cuda-optix-rewriting-a-global-param-into-an-opaque.md).
Provenance can still be lost after the move: a ConstantBuffer handle stored in a struct field,
returned, or chosen by `select` loses its root, and `isPointerToImmutableLocation` then calls it
immutable by type. `lowerImmutableBufferLoadForCUDA` therefore needs a module-level guard; PR
#12646 keyed it on the deduplicated IR types of `GetOptiXSbtDataPtr`
[module-level `__ldg` guard](../learnings/1790831529525-cuda-optix-lower-shader-record-globals-after-speci.md).
