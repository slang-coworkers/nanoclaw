## TL;DR

CUDA/OptiX backend facts, mostly around ray tracing, the NVRTC-compiled prelude, and GPU-free verification:

- **OptiX payload register count is the separate `payloadSize` operand, NOT the `_optix_trace_typed_32` name**, which is emitted for every payload size; grep the `payloadSize` immediate. The prelude's `optix*WithRegs` fixed-width `N<=16`/`N<=32` catch-alls over-read/over-write for N in [9,15] AND [17,31].
- **An `inout` ray payload is legalized TWICE** (VaryingInput + VaryingOutput) and a direction-agnostic `case RayPayload:` double-reads the registers; the reads survive DCE because `kIROp_GetOptiXPayloadRegister` is side-effecting. Fix the producer; don't mark it pure.
- **Hit attributes are field-wise (one 32-bit register per scalar leaf), not byte-packed.** `ReportHit` must gather leaves into ONE `optixReportIntersection` call and emit `__float_as_uint` explicitly (CUDA `kIROp_BitCast` is a numeric cast).
- **HLSL ray flags pass verbatim into `optixTrace`.** Only `SKIP_TRIANGLES`(0x100) and `SKIP_PROCEDURAL_PRIMITIVES`(0x200) lack an OptiX equivalent (0x400 maps); key a diagnostic off the named `OptixRayFlags` set (supported = 0x4FF), not `>=0x100`.
- **`OptixRayFlags` bits 0–7 are identical in OptiX 7.0–9.1; the 0x400 OMM flag first appears in 7.6.0**, so named emission needs `#if OPTIX_VERSION >= 70600`. A long-lived draft adding a `slang-diagnostics.lua` entry must re-check its code against master before rebasing.
- **Lower shader-record (SBT) globals to an opaque intrinsic only after `specializeResourceUsage` and the global-init move.** Earlier, a `ConstantBuffer<T>` helper param stays unspecialized and gets `__ldg` (#10188), `expand` bodies crash, and reference graphs miss generic calls and the static initializers CUDA injects into EVERY entry point.
- **On CUDA, GeometryIndex is the OptiX SBT GAS index** (HitObject since SER; pipeline `GeometryIndex()` since PR #13437 via `optixGetSbtGASIndex()`, OptiX >= 7.1). It equals the DXR ordinal only under slang-rhi's one-record-per-input layout.
- **All of `slang-cuda-prelude.h` goes to NVRTC verbatim**, so an OptiX helper using an SDK-N symbol without `#if (OPTIX_VERSION >= NNNNN)` breaks ALL RT shaders on older SDKs. Resolve thresholds from `external/optix-dev` tags (7.x decls in `optix_7_device.h`), verify with nvcc. The OptiX block is compiled only for RT-stage entry points, so a type compute can name (e.g. `RayDesc`) must live outside it.
- **NVRTC `-pch` (12.8+) is requested only when the emitted source starts with `#include`**, so any CUDA front matter ahead of the prelude include silently disables it.
- **Slang never forwards `-O<n>` to NVRTC** (switch commented out since 2019) and NVRTC optimizes by default, so `-target ptx -O0` and `-O3` PTX are byte-identical.
- **A slang-rhi 1D CUtexObject is array-backed, so an integer 1D texel Load must use `tex.level.2d … [x,0]`**; integer `tex.level.1d` is the linear-memory `TLD … 1D` and reads zeros. Decide PTX texture forms from SASS (`cuobjdump -sass`). Linear-memory texture objects have no built-in Slang target (#14064); an `__intrinsic_asm "tex1Dfetch<float>(...)"` over a `uniform uint64_t` handle works.
- **CUDA `noinline` policy must be target-gated**: SPIR-V/LLVM/HLSL emitters already consume `IRNoInlineDecoration`.
- **`inout` subobject copy-in/out is design-gated on CUDA** by `undoParameterCopy` abort safety (OptiX aborts can skip writeback); WGSL already copies unconditionally.
- **`case cuda: __intrinsic_asm "name"` forwards ALL the function's args positionally** (spirv/glsl pass explicit operands), so mirroring a case across overloads of different arity needs a matching-arity prelude wrapper. Gate CUDA codegen on `-target ptx -Xnvrtc`: a bare `-target cuda` EXIT 0 can be a silent drop, and E41009 is OFF for CUDA/DXIL.

## OptiX payloads: register count is `payloadSize`, and `inout` is legalized twice

`_optix_trace_typed_32` is OptiX's one register-trace transport: it always emits 32 inline-asm register slots, and the real payload word count travels only in the separate `payloadSize = (int)sizeof...(Payload)` operand. To triage "traced as N registers", grep the `payloadSize` immediate loaded before the call, not the symbol; the bug is Slang passing the wrong number of `pr.regs[i]` arguments. The prelude's `optixTraceWithRegs`/`optixTraverseWithRegs`/`optixInvokeWithRegs` have `if constexpr (N==0..8)` branches and then two fixed-width catch-alls (`N<=16` passes regs[0..15], `N<=32` passes regs[0..31]), so `PayloadRegisters<T,N>` is over-read and over-written (OptiX assigns returned values back) for N in [9,15] and [17,31]; when a report cites one window, check the sibling. NVRTC scalarizes the struct, so the PTX shows undefined extra register operands, not stack OOB; scope the verdict to the codegen defect (a runtime hang is "consistent with, not proven"). Repro GPU-free via `-target ptx` ([Slang CUDA/OptiX payload register count is carried by payloadSize](../learnings/1786644040522-slang-cuda-optix-payload-register-count-is-carried.md)).

An `inout` payload is legalized twice: `processMutableParam` calls `createLegalVaryingVal` once as `VaryingInput` and once as `VaryingOutput`, and the CUDA `case LayoutResourceKind::RayPayload:` keys off `getLayoutResourceKind` (always `RayPayload`) while ignoring `info.kind`, so `emitOptiXPayloadRead` fires on both passes. Writeback stays correct only because a `getCount()==0` guard dedups its registration. The dead reads survive DCE because `kIROp_GetOptiXPayloadRegister` is not pure or hoistable (`mightHaveSideEffects()` is true). The fix is to not emit the second read (producer), not to mark the op pure, since a mutable payload register can legitimately be re-read. Reproduce GPU-free with text CUDA emit plus `-dump-ir` ([OptiX inout ray-payload legalized twice: direction-agnostic RayPayload branch double-reads](../learnings/1786656384074-optix-inout-ray-payload-legalized-twice-direction-.md)).

## Hit attributes, ray flags, and RT intrinsics

Hit-attribute lowering is field-wise, not byte-packed: `emitOptiXAttributeFetch` recurses fields, elements and lanes, takes one 32-bit register per scalar `IRBasicType` leaf, and wraps float leaves in `__int_as_float`; the 8-register cap and its diagnostic live in the legalize pass. That reader is the canonical contract, so a `ReportHit` writer must flatten field-wise too; a whole-struct `bit_cast<uint[N]>` desyncs on padding, sub-dword fields and float bits ([OptiX hit-attribute lowering is field-wise, not byte-packed](../learnings/1787174981538-optix-hit-attribute-lowering-is-field-wise-not-byt.md)). The write path (slang#12637) adds four rules. OptiX has no per-attribute setter, so all leaves go into ONE `optixReportIntersection(hitT, hitKind, a0..a7)` call. CUDA lowers `kIROp_BitCast` as a numeric C cast, so a float needs an explicit `__float_as_uint(x)` (PTX must show `0.5f` as `1056964608`, not 0). A target-specific marker op with an aggregate operand is flattened after post-inline DCE and before empty-type/resource legalization. FileCheck slang-tests are a vacuous `0/0` pass without slang-llvm, so check CUDA/OptiX emit with direct `slangc -target cuda` and a per-leaf grep ([OptiX ReportHit write path: no attribute setter, non-bit-preserving CUDA BitCast, pass ordering](../learnings/1787792439688-optix-reporthit-write-path-no-attribute-setter-non.md)). Releases without PR #12783 (e.g. v2026.14.1) reject portable `ReportHit(t, kind, attrs)` on `-target cuda`/`ptx` with E36107. The workaround passes scalar fields to `ReportHitOptix` with `asuint` on floats: `ReportHitOptix(1.0f, 1u, a.id, asuint(a.weight))` becomes `optixReportIntersection(1.0f, 1U, id, F32_asuint(weight))`, which matches the reader (`optixGetAttribute_0()`, `__int_as_float(optixGetAttribute_1())`), so values round-trip ([pre-fix ReportHit workaround: ReportHitOptix with asuint per field](../learnings/1792400325654-pre-fix-reporthit-workaround-for-cuda-optix-report.md)).

The CUDA arm of `TraceRay` is `case cuda: __intrinsic_asm "optixTrace";`, and the generic intrinsic-asm path writes the ray-flags operand verbatim, so flags with no OptiX equivalent silently miscompile (exit 0, then a runtime GPU fault that looks like a null-pointer deref). The fix is a compile-time diagnostic, not a bit translation (OptiX skips triangles/AABBs per pipeline, not per ray). Any bare `case cuda: __intrinsic_asm` pass-through whose enum/flag value space differs between DXR and OptiX belongs to the same silent-miscompile class ([CUDA/OptiX TraceRay ray-flags are a bare intrinsic-asm pass-through](../learnings/1787172018498-cuda-optix-traceray-ray-flags-are-a-bare-intrinsic.md)). From `external/optix-dev/include/optix_types.h`, `OptixRayFlags` has bits 0–7 plus `FORCE_OPACITY_MICROMAP_2_STATE=1<<10` (0x400), and nothing at bit 8 or 9. HLSL bits 0–7 map identically (`CULL_OPAQUE(0x40)↔CULL_DISABLED_ANYHIT` matches in value and semantics) and `RAY_FLAG_FORCE_OMM_2_STATE(0x400)` coincides with the OMM flag. **Only `SKIP_TRIANGLES=0x100` and `SKIP_PROCEDURAL_PRIMITIVES=0x200` are unsupported**: supported = 0x4FF, unsupported = `flags & ~0x4FF`; a `>=0x100` threshold would wrongly flag 0x400 ([HLSL RAY_FLAG vs OptiX OptixRayFlags — only 0x100/0x200 lack an equivalent](../learnings/1787173053502-hlsl-ray-flag-vs-optix-optixrayflags-only-0x100-0x.md)).

All 12 NVIDIA/optix-dev tags (v7.0.0–v9.1.0) define bits 0–7 with identical names and values, none defines bit 8 or 9, and the OMM flag first appears in v7.6.0 (`OPTIX_VERSION` 70600; the header was `optix_7_types.h` before 7.7). Emitting ray flags by name, maintainer jkwak-work's direction on slang#12629 following his HLSL barrier-flag pattern from #11437, therefore needs `#if OPTIX_VERSION >= 70600` around the OMM flag. Check a tag with a sparse `git clone --depth 1 --branch vX` of NVIDIA/optix-dev (`include` only). Process note: while slang#12644 sat as a draft for six weeks, master gave its diagnostic code (55215) to another error; re-check a long-lived draft's `slang-diagnostics.lua` code against master before rebasing ([OptiX ray-flag names are stable 7.0–9.1; the OMM flag needs OPTIX_VERSION >= 70600](../learnings/1790820168701-optix-ray-flag-names-are-stable-7-0-9-1-omm-flag-n.md)).

A second `case cuda: __intrinsic_asm` trap is arity: the CUDA arm forwards ALL the enclosing function's arguments positionally, while spirv/glsl arms call helpers with explicit operands (`__spirvExecuteShaderEXT(HitOrMiss, p)`, `__glslInvoke(HitOrMiss, __rayPayloadLocation(p))`). Copying the 3-arg overload's `"optixInvoke"` case into a 2-arg overload (slang#12553) emits `optixInvoke(hit, payload)`, an arity the prelude lacks, and NVRTC fails with `no instance of overloaded function "optixInvoke" matches the argument list`. The fix is a matching-arity prelude wrapper that forwards a null `(OptixTraversableHandle)0`, which is exact because the 3-arg wrapper ignores the handles. Verification: `-target cuda` exit 0 was a silent drop, so gate CUDA codegen on `-target ptx -Xnvrtc -I external/optix-dev/include/`; missing-return E41009 is target-gated (`doesTargetAllowMissingReturns`, `slang-ir-missing-return.cpp:18-26`, false only for Khronos/WGPU), so the same core-module gap is E41009 on SPIR-V/GLSL, a silent drop on CUDA and nothing on DXIL ([case cuda __intrinsic_asm forwards args positionally — dropping an arg breaks NVRTC arity](../learnings/1786786566207-case-cuda-intrinsic-asm-forwards-args-positionally.md)).

When a built-in is rejected with `E36107: unavailable features in entry point`, check the FIRST argument of its `[require(<target-atom-set>, <capability>)]`, not the capability. `TraceMotionRay`/`RayCurrentTime` in `hlsl.meta.slang` are `[require(glsl_spirv, raytracing_motionblur_…)]`; `raytracing_motionblur` already has a `cuda` conjunct, so the narrow `glsl_spirv` is the block (sibling `HitObject.TraceMotionRay` uses `cuda_glsl_spirv` and works on CUDA). E36107 prints two `note:` lines, the use site and the `[require]` declaration, so compare the declaration's first arg against a working sibling. The fix lands lock-step: widen the first arg, add the `case <target>: __intrinsic_asm` arm, and add a matching-arity prelude overload when arity differs; reproduce GPU-free with `slangc repro.slang -target <t> -entry … -stage …` ([E36107 on a CUDA RT intrinsic: check the `[require]` FIRST-arg target set, not the capability compound](../learnings/1789186196430-e36107-for-an-rt-intrinsic-on-cuda-check-the-requi.md)).

On `-target cuda`, GeometryIndex is the OptiX SBT GAS index: `HitObject.GetGeometryIndex()` lowers to `optixHitObjectGetSbtGASIndex()`, `HitObject.MakeHit`'s `GeometryIndex` argument is passed as `sbtGASIdx`, and since PR #13437 (merged 2026-10-06) pipeline `GeometryIndex()` has a `case cuda:` calling `optixGetSbtGASIndex()` (it was E36107 before). OptiX (through 9.0) has no build-input-ordinal query; the SBT GAS index is the sum of `numSbtRecords` over earlier inputs plus the per-primitive `sbtIndexOffset`, which must lie in [0, numSbtRecords-1] (`optix_types.h:717`), so slang-rhi's one-record-per-input layout forces offset 0 and the index equals the DXR ordinal. (DeepWiki conflates the pipeline function with the HitObject method) ([CUDA SER path already treats GeometryIndex as the OptiX SBT GAS index](../learnings/1790318608424-slang-cuda-ser-path-already-treats-geometryindex-a.md)). `optixGetSbtGASIndex()` first appears in OptiX 7.1.0, so CUDA `GeometryIndex()` needs OptiX >= 7.1; against 7.0 headers NVRTC reports it undefined ([optixGetSbtGASIndex needs OptiX >= 7.1](../learnings/1791203817991-optixgetsbtgasindex-needs-optix-7-1-reviewer-a-bac.md)). Separately, the OptiX 9 prelude `optixMakeHitObject` overloads build the hit from `optixHitObjectGetTraverseData` and ignore `MakeHit`/`MakeMotionHit`'s explicit hit args, a known gap documented in docs/cuda-target.md ([property-getter `[require]` is not enforced](../learnings/1791199099928-slang-property-getter-require-is-not-enforced-a-mi.md)).

## The NVRTC-compiled prelude and version gating

All of `prelude/slang-cuda-prelude.h` is prepended to the NVRTC translation unit, so every helper must compile against the user's OptiX SDK whether or not it is called. OptiX intrinsics are version-tiered (`optixTrace` 7.x, `optixTraverse` 8.0+, full `optixMakeHitObject` 9.0 with an 8.1 `#elif`), so a helper missing its `#if (OPTIX_VERSION >= NNNNN)` guard breaks ALL RT shaders on older SDKs. When even a trivial shader fails `-target ptx` with `no instance of overloaded function "optixXxx"`, suspect an ungated prelude helper, not the user's code. Dropping lower-SDK support instead is a maintainer policy call. The bug recurs because filecheck tests compile only against the bundled OptiX 9.0 headers (the #10503 gap) ([OptiX version-gating bugs in slang-cuda-prelude.h recur — the whole prelude is NVRTC-compiled](../learnings/1787175488691-optix-version-gating-bugs-in-slang-cuda-prelude-h-.md)). Read thresholds from `external/optix-dev` git tags rather than guessing (`git show v8.0.0:include/optix_device.h | grep -c 'void optixTraverse('`). In 7.x the device declarations live in `optix_7_device.h` (plain `optix_device.h` is a 47-line wrapper, so grepping it gives a false "absent"), and stock 7.0.0 headers do not compile under NVRTC 12.x (unguarded `#include <stddef.h>`), so put a stub `stddef.h` on `-Xnvrtc -I` to probe 7.0 ([same](../learnings/1791203817991-optixgetsbtgasindex-needs-optix-7-1-reviewer-a-bac.md)). Use one `#if` unless the signature changes across tiers, and verify GPU-free with an nvcc prelude probe against old headers; a testless PR documenting that out-of-band check is often correct, since with in-tree 9.0 headers no CI test can fail before and pass after ([resolve OptiX prelude version-gate thresholds from optix-dev git tags, verify GPU-free with nvcc](../learnings/1787227776278-resolve-optix-prelude-version-gate-thresholds-from.md)).

The OptiX block is compiled only for ray-tracing entry points: `slang-code-gen.cpp` (~:960-970) sets `PipelineType::RayTracing` for raygen, intersection, anyhit, closesthit, miss and callable, and `slang-nvrtc-compiler.cpp` (~:1341) calls `_maybeAddOptixSupport`, the only place adding `-DSLANG_CUDA_ENABLE_OPTIX`, only for that pipeline type. A compute shader never sees the `#ifdef SLANG_CUDA_ENABLE_OPTIX` block, so a plain data type it can name, such as `RayDesc` (#12638), must be defined outside it (v2026.14.1). The GPU-free method for testing such a prelude patch is on [[wiki/concepts/slang-backends-cuda-ptx-surface-asm-verification.md]] ([SLANG_CUDA_ENABLE_OPTIX is set by entry-point stage, not by feature use](../learnings/1792400439374-cuda-slang-cuda-enable-optix-is-set-by-entry-point.md)).

NVRTC `-pch` for the CUDA prelude shipped in PR #12880. It is gated on NVRTC ≥12.8 and on the leading-`#include` prelude form (it does not help prepended text), and on amortization, since a one-shot `-pch` is a net regression; the 256 MB default heap is managed reactively. `nvrtcGetPCHCreateStatus` loads as an optional symbol so init() works below 12.8, and a `slang-nvrtc-pch-status: created|not-created|create-failed` diagnostics token lets a unit test read the outcome. Review gotchas: `IArtifactDiagnostics::getRaw()` with no diagnostics returned a `nullptr`-backed terminated slice that `SLANG_ASSERT(in[0]==0)` dereferenced, so back an empty terminated slice with `""` and test the no-output branch; `getDownstreamCompilerVersion` was removed from master (use `getDesc()`/`SemanticVersion`), so a stale-master branch built locally but would not merge. Rebase onto current `origin/master` before trusting "builds locally"; a DRAFT PR skips Slang CI, so the ≥12.8 asserts run only once it is ready ([empty-diagnostics null-deref + removed getDownstreamCompilerVersion](../learnings/1789272763883-nvrtc-pch-review-slang-12880-empty-diagnostics-nul.md), [NVRTC -pch for the CUDA prelude SHIPPED (#12880)](../learnings/1789272870056-nvrtc-pch-for-cuda-prelude-shipped-pr-12880-findin.md)). The leading-`#include` gate is Slang's own and is stricter than NVRTC: `pchRequested` (`source/compiler-core/slang-nvrtc-compiler.cpp`, ~line 1430) asks for `-pch` only when the whole emitted source `trimStart().startsWith("#include")`, so anything `CUDASourceEmitter::emitFrontMatterImpl` writes ahead of the prelude include, such as `#define SLANG_CUDA_ENABLE_FAST_MATH 1` under `-fp-mode fast` (PR #12872) or the `#ifndef`-guarded `SLANG_CUDA_ENABLE_{HALF,BF16,FP8}` from the #14037 fix, silently drops `-pch` for that module. NVRTC's real stop point is the first non-directive token, so leading directives would still be precompiled; a follow-up can let the check skip leading top-level directives. Look at this check before adding CUDA front matter; a container with NVRTC 12.6 cannot show the effect. Why the front matter exists is on [[wiki/concepts/slang-backends-cuda-nvrtc-vs-offline-nvcc.md]] [CUDA front-matter defines turn off NVRTC -pch on -target ptx](../learnings/1793299799398-cuda-front-matter-defines-turn-off-nvrtc-pch-on-ta.md).

A super-linear **downstreamCompile timer** on a matrix-heavy CUDA kernel is NVRTC's own cost, not Slang emit size. Slang emits O(N) CUDA C++ for an N-multiply chain: CUDA does not legalize matrix types (`targetLegalizesMatrixTypes()` is false), matrices stay prelude `Matrix<T,ROWS,COLS>` structs, and `mul(matrix,matrix)` is `[__readNone]`, so it is emitted once with N call sites. The timer (PR #13050) wraps only `compiler->compile(...)` (`slang-code-gen.cpp:1028`) and excludes Slang IR passes (including the O(n²) redundancy-removal cost of #13010/#13059), so super-linearity there goes upstream to NVIDIA. The reporter's `backend_matrix`/`gen_matrix_chain` workloads are not in `tools/compile-perf/`, so the numbers are not reproducible ([a downstreamCompile-timer super-linearity on a matrix kernel is nvrtc-intrinsic, not a Slang emit-size artifact](../learnings/1789389982745-a-downstreamcompile-timer-super-linearity-on-a-mat.md)).

## Optimization level, noinline policy, and inout subobject lowering

Making CUDA emit `__noinline__` splits into mechanism and policy. PR #12419 made CUDA the 4th backend to emit it from an existing `IRNoInlineDecoration`, but generated code has no hand-written `[noinline]`, so it recovers nothing alone; #12620 is the policy, a heuristic choosing which device functions to mark. `IRNoInlineDecoration` has no consumers in `slang-ir-inline.cpp` (it is purely a downstream hint), but the SPIR-V (`DontInline`), LLVM (`noinline`) and HLSL (`[noinline]`) emitters already emit from it, so an ungated heuristic pass would regress them. Recommended shape: an opt-in `-cuda-noinline-threshold=<n>` (default OFF) driving a CUDA-gated pass after `performForceInlining`, before emit ([CUDA noinline: a heuristic pass must be target-gated](../learnings/1787146175748-cuda-noinline-a-heuristic-pass-must-be-target-gate.md)).

`slang-code-gen.cpp:796-812` maps `-O<n>` into `DownstreamCompileOptions::optimizationLevel`, but the NVRTC driver never reads it: its switch at `slang-nvrtc-compiler.cpp:1234-1238` has been commented out since #1151 (2019). NVRTC has no `-O` option (`-Xnvrtc -O3` is "unrecognized option") and optimizes by default; So `-target ptx -O0` and `-O3` give byte-identical PTX (verified on CUDA 12.6). Measured with `ptxas -v`, NVVM promotes a pointer-to-struct parameter to scalars across `__noinline__` (dropping the caller's copy) only when aliasing is ruled out (`__restrict__`, or the callee reads before writing through another pointer) and at most 3 fields are read (an observed threshold; LLVM ArgumentPromotion defaults to 3 in LLVM 14, 2 in 15). For the signature-rewrite direction (#13108 / #13177), passing a field pointer (`&s.a`) still makes the caller's struct escape, and copy-in plus write-back removes the frame but is unsafe on CUDA/OptiX under IgnoreHit/thread termination (the `undoParameterCopy` rationale, `slang-ir-undo-param-copy.cpp:9`, below). PTX from `slangc -target ptx` ends with a NUL byte, so grep it with `-a` or strip it with `tr -d '\000'` ([Slang never forwards -O<n> to NVRTC; NVVM argpromotion across __noinline__ is narrow](../learnings/1790961575284-slang-never-forwards-o-n-to-nvrtc-nvrtc-optimizes-.md)).

The front end represents `inout` with copy-in/copy-out wrappers, but `addArg` materializes a temp only for a NON-addressable l-value; an addressable subobject like `path.sg` is passed as the field address `&path.sg` with no copy. On CUDA/CPP an `inout T` param emits as a pointer `T*`, and `undoParameterCopy` (scheduled for CUDA/Metal/CPP) actively removes copy-in/out temps, specifically because OptiX abort intrinsics (`IgnoreHit`/`TerminateRay`) can abort before a copy-back runs and silently drop the payload mutation. WGSL does the opposite: `legalizeCall` always materializes a `function`-space temp with copy-in/copy-out (WGSL forbids a pointer to a struct field). So the copy-in/out workaround reporters ask for already exists for WGSL, but on CUDA it is design-gated: it must not reintroduce the abort-before-writeback hazard (restrict to provably abort-free callees, or write back on all exit paths). A green SPIR-V/HLSL run never clears a CUDA param-passing change; the CUDA emitter inherits `CPPSourceEmitter`, and its `-target cuda` emit is GPU-free FileCheck-verifiable ([CUDA vs WGSL inout-subobject lowering divergence (and the undoParameterCopy abort-safety constraint)](../learnings/1788636814094-cuda-vs-wgsl-inout-subobject-lowering-divergence-a.md)).

## 1D texture integer Load: array-backed textures need the 2D form (#12630)

Choose the PTX texture form from SASS, which needs no GPU: `nvcc -arch=sm_XX -cubin x.cu && cuobjdump -sass x.cubin | grep -E 'TLD|TEX'`, then read the dimension token at the end of each texture instruction. For slang#12630 (nvcc 12.6, identical on sm_52 through sm_90): integer `tex.level.1d.v4.f32.s32` gives `TLD … 1D`, the same as `tex1Dfetch` (linear-memory fetch); CUDA's own `tex1DLod<float4>` on a 1D texture object gives `TEX … 2D`; `tex.level.2d…s32 [t,{x,0}]` gives `TLD … 2D`; `tex.level.a1d…s32` gives `TLD … ARRAY_1D`. Every 1D CUtexObject slang-rhi creates is array-backed, so the matching integer fetch is the 2D one at row 0, consistent with the L40S result where `tex.level.1d…s32` returned all zeros. Fix: PR #13377 (its T4 CUDA test checks values). Gotchas: a GPU-less container with a stale CMake cache fails to link on a missing `libcuda.so` (reconfigure with `-DCUDA_cuda_driver_LIBRARY=/usr/local/cuda/lib64/stubs/libcuda.so`). The render-test CPU backend has no `Texture1D` subscript and unpacks only RGBA32Uint/R32Uint/R16Uint integer texels (others silently give empty output), so a `-cpu` reference uses RGBA32Uint and Sint coverage is CUDA-only. A bot `workflow_dispatch` of ci.yml can park on `wait-for-human-priority` or the `falcor-ci` environment approval (ci-approvers only), and `ci-retry-yielded-bot` retries only completed runs, so a falcor-ci-parked run never yields a CUDA result alone ([CUDA 1D texture Load: integer tex.level.1d = linear-memory TLD.1D](../learnings/1790894433645-cuda-1d-texture-load-integer-tex-level-1d-linear-m.md)).

The linear-memory side has no built-in Slang target (#14064). On CUDA/PTX, Slang rejects read-only `Buffer<T>` (E36107, note `__ShapeBuffer`; `[require(cpp_glsl_hlsl_metal_spirv)]` at `hlsl.meta.slang:590` since #12289), and `Texture1D` is the CUDA-array path, so nothing lowers to a raw-CUDA `tex1Dfetch` over a `cudaResourceTypeLinear` texture object. A user-level workaround works: declare `float fetchLinear(uint64_t tex, int i) { __target_switch { case cuda: __intrinsic_asm "tex1Dfetch<float>((cudaTextureObject_t)$0, $1)"; } }` and pass the `CUtexObject` as a `uniform uint64_t`. It emits PTX `tex.1d.v4.f32.s32 [t, {i}]`, and on 2026-10-29 it returned 1000/1000 correct values on the L40S (CUDA 12.6, driver-API host, `CU_RESOURCE_TYPE_LINEAR` float with 1 channel). Compute entry-point uniforms on CUDA become plain kernel parameters (`k(ulonglong, float*, uint)`), so a small `cuModuleLoadData` + `cuLaunchKernel` host is enough to run a Slang-emitted PTX kernel on the GPU. slang-rhi does not help: it creates texture objects only over CUDA arrays and mipmapped arrays, and its TypedBuffer binding writes a device pointer [CUDA linear-memory texture objects from Slang today: __intrinsic_asm tex1Dfetch over a uint64_t handle](../learnings/1793312171013-cuda-linear-memory-texture-objects-from-slang-toda.md).

## Shader-record (SBT) globals: lower after specialization and the global-init move

PR #12646 (slang#12628) maps a global `shaderRecordEXT` `ConstantBuffer` to the OptiX SBT on CUDA by rewriting the `IRGlobalParam` into an opaque intrinsic, `GetOptiXSbtDataPtr`. Placed early in `linkAndOptimizeIR`, next to `collectOptiXEntryPointUniformParams` (`slang-emit.cpp` ~:1391), the rewrite broke three things. First, `specializeResourceUsage` (~:2097) specializes a callee's ConstantBuffer/resource parameter only when the call-site argument is a `kIROp_GlobalParam` (`slang-ir-specialize-resources.cpp` ~:740; any other opcode gives `ThisFuncFailed`), so a helper `float4 readIt(ConstantBuffer<T> cb)` stayed unspecialized; `isPointerToImmutableLocation` cannot see the `GetOptiXSbtDataPtr` root through a parameter, and the callee emitted `__ldg(&cb->field)`, the #10188 stale-SBT-read bug. Second, a use inside an `expand` body crashed slangc (`IRExpand` owns a block but is not an `IRGlobalValueWithCode`, and `specializeModule` ~:1552 had not run). Third, a reference-graph diagnostic missed interface/generic calls, which before specialization do not follow witness tables. Moving the rewrite to just after `specializeResourceUsage` fixed all three; the review probe is `readIt(gSbt)` with a ConstantBuffer-typed parameter, then a grep of the callee for `__ldg` [rewriting a global param into an opaque intrinsic before specializeResourceUsage](../learnings/1790827641249-cuda-optix-rewriting-a-global-param-into-an-opaque.md), [lower shader-record globals after specialization](../learnings/1790831529525-cuda-optix-lower-shader-record-globals-after-speci.md).

A second ordering constraint: `moveGlobalVarInitializationToEntryPoints` (`slang-ir-explicit-global-init.cpp` ~:107-114, 187-240) injects EVERY global initializer into EVERY entry point, even ones that never reference the global, and CUDA/CPU run it late (~:2483). A per-entry-point diagnostic built from `buildEntryPointReferenceGraph` before that pass is unsound for uses inside a `static` initializer: with an RT and a compute entry point in one compile plus `static uint x = gSbt.id;`, the compute kernel calls `optixGetSbtDataPointer()` with no error (on SPIR-V spirv-val catches the analog, VUID-07119; on CUDA nothing does). Run such lowering after the global-init move (~:2490) [every static initializer reaches every entry point](../learnings/1790827641249-cuda-optix-rewriting-a-global-param-into-an-opaque.md). Provenance can still be lost after the move: a ConstantBuffer handle stored in a struct field, returned, or chosen by `select` loses its root, and `isPointerToImmutableLocation` then calls it immutable by type, so `lowerImmutableBufferLoadForCUDA` needs a module-level guard; PR #12646 keyed it on the deduplicated IR types of `GetOptiXSbtDataPtr` [module-level `__ldg` guard](../learnings/1790831529525-cuda-optix-lower-shader-record-globals-after-speci.md).
