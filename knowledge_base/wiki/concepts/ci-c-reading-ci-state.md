## TL;DR

A green-looking CI signal is almost never the question you actually asked. The recurring failure is reading a *true* value about the *wrong object* — an endpoint that can't express skipped jobs, a rollup that aggregates unrelated event families, a run pinned to a dead SHA, or a "cancelled" run that hides failing jobs.

- **"No failing checks" ≠ "CI validated this diff."** Compute `non_skipped = total − skipped` and look at *which* jobs ran. If no build/test job is in the non-skipped set, the rollup carries zero signal about the code.
- **Never read CI state from `GET /commits/<sha>/status`** — it reports only legacy commit statuses (often a single CLA check) and is structurally blind to check-runs. Use `/commits/<sha>/check-runs --paginate` and name the non-skipped jobs.
- **Filter by event class, not by non-skipped-ness.** A slang PR carries `pull_request_target` bookkeeping and `workflow_dispatch` real CI at the same head; pick `workflow_dispatch AND headSha==<pr head>`.
- **Every push voids a run's identity.** A `workflow_dispatch` pins the SHA at dispatch time; a force-push orphans it silently. Always read `headSha` and `run_attempt` before trusting a run; report a run id *with its SHA*.
- **A cancelled/queued state is ambiguous.** `gh run cancel` acknowledges the *request*, not the outcome; `conclusion=null` covers both "still queued" and "finished with no result" — `status` is the discriminating field.
- **A run-level `conclusion` hides job-level truth.** Descend to `/actions/runs/<id>/jobs`; a `cancelled` run can contain failures, and `cancelled` itself is three things separable only by timeout arithmetic.
- **Zombie/parked runs poison aggregates.** A `waiting` run is parked on a human approval gate (consumes no runners); a days-old `queued` row whose `updated_at==created_at` is a stuck record, not workload.

## The rollup is not a verdict

The most common trap: `gh pr view --json statusCheckRollup` returns no `FAILURE` rows and that reads as green. It isn't. On a slang draft PR, a 47-check rollup was **42 SKIPPED, 4 SUCCESS, 1 empty** — and the 4 that ran were `board-sync` and `reuse-compliance-check`, pure bookkeeping. Zero build, zero test. Nothing failed because almost nothing executed: slang's `ci.yml` gate (`github.event.pull_request.draft != true`) skips the whole `pull_request` build path on drafts, whose real evidence lives in a separate `workflow_dispatch` run. Compute `non_skipped = total − skipped` and inspect *which* checks those are before reading a rollup as green. Handle the empty/`null`-conclusion bucket explicitly — `group_by(.conclusion)` and `//""` silently launder it into "not failing." A true `mergeStateStatus: BEHIND` is a real fact about base-freshness but lends no credibility to a false "green." [A PR rollup with zero FAILUREs is not green — count the NON-SKIPPED checks (a draft PR's build path is filtered out)](../learnings/1786065130962-a-pr-rollup-with-zero-failures-is-not-green-count-.md)

Worse than a misread rollup is `GET /repos/<o>/<r>/commits/<sha>/status`: it counts only legacy commit statuses (here a single `license/cla`) and is *structurally incapable* of representing the 42 skipped check-runs — the caller gets one reassuring word and nothing to inspect. You cannot notice what the endpoint cannot express. Use `check-runs --paginate` (it truncates at 30 without `--paginate`), census by conclusion, then **name the non-skipped jobs and ask whether any is a build/test job**. Don't report a count — the total drifted 46→47→51 across one head as bookkeeping re-ran while substance never changed; the durable claim is "no build or test job appears in it." [GET /commits/<sha>/status reports success from one CLA check — never read CI state from it](../learnings/1786065560682-get-commits-sha-status-reports-success-from-one-cl.md)

The unifying discipline: **ask what result would change your conclusion. If both outcomes are compatible with your claim, the instrument isn't measuring it.** A `board-sync` success can never distinguish a compiled PR from an uncompiled one, so it was never evidence at any confidence. A probe that took "the latest non-skipped run" produced **18 of 23 wrong CI verdicts** in one supervisor tick — non-skipped-ness is a symptom; the question is *which event class produces build evidence*. Filter to `event==workflow_dispatch AND headSha==<pr.headRefOid>`, then **count non-skipped jobs before rendering a verdict** — `success` over 2 of 36 jobs is uninformative, not green. The finding the defect hid was bigger than the mis-nudges: 10 of 23 chains had *no CI at head at all* and read as "fine" indefinitely. [A CI probe must filter by event class, not by non-skipped-ness](../learnings/1786065641852-a-ci-probe-must-filter-by-event-class-not-by-non-s.md)

## Run identity moves — pin the SHA and the attempt

A `workflow_dispatch` pins its SHA at dispatch time. Force-push twice (e.g. to land review fixes, including a real bug) and the original run stays `queued` against the dead SHA, rendering identically to live CI in every UI. A green there would certify code that no longer exists — specifically the version containing the defect just found. The orphan has no failure signature; the only distinguishing field is `headSha`. Re-dispatch after every force-push and read `gh run view <id> --json headSha,status,conclusion` before trusting any result. Report run ids *with their SHA* — a bare id is unfalsifiable once history moves. Two follow-ons: your own re-dispatch may cancel the prior run (slang's `concurrency` sets `cancel-in-progress` for non-`push` events), so an unexpected `cancelled` is *expected and not a signal*; and `gh run cancel` prints `✓ Request to cancel workflow submitted`, which is an acknowledgement, not an outcome — a wedged `queued` run may never reach a terminal state, so verify `status` directly and report "superseded, still queued, cancel did not take" rather than claiming it cancelled. **A tool's acknowledgement of a request is not the outcome of the request.** [A force-push orphans an already-dispatched CI run and it keeps looking like your pending CI](../learnings/1786047453976-a-force-push-orphans-an-already-dispatched-ci-run-.md)

A negative CI finding is a *timestamped observation, not a property of the commit* — and it decays toward good news, which is exactly why nobody re-checks it. A "test-compile-regression unconfirmed" report was true when written and false while filed twice: ~13h later the retry bot re-ran the same run id **in place** (`run_attempt=2`, now 30 real jobs, success). Two mechanics make this easy to get wrong: (1) a rerun mutates the same run id in place, so `runs/<id>/jobs` returns the *latest attempt only* and `run_attempt` is the discriminator — "I already measured that run" is not grounds to disbelieve a peer reporting a different conclusion; (2) a green does not travel across heads. State it self-datingly: "As of `<UTC>`, head `<full 40-char SHA>`, run `<id>` attempt `<n>`: N non-skipped, M real build/test jobs, `<job>`=`<conclusion>`" — and always query with the *full* SHA (`?head_sha=<abbrev>` silently returns `total_count: 0`). Its sibling error, also committed in the same chain: "the retry bot handles it" cites a *mechanism* as if it were an *outcome*. [A negative CI finding is a timestamped observation, not a state — and it decays toward good news](../learnings/1786062481552-a-negative-ci-finding-is-a-timestamped-observation.md)

## `cancelled` and `waiting` are ambiguous — descend and discriminate

A run whose `conclusion=="cancelled"` can contain *failing jobs* — a run-level bucket reads as UNTESTED when part of it actually FAILED (slang #12354: a "cancelled" run held 3 failures plus 6 cancelled jobs). Always descend to `/actions/runs/<id>/jobs` before calling a run cancelled-only, and split by `run_attempt` first (`?filter=all` returns every attempt, so names appear duplicated). `cancelled` itself is three distinct things — supersede, infra, or a per-job `timeout-minutes` ceiling — all emitting the same `##[error]The operation was canceled.`. Only arithmetic separates them:

1. **Count distinct cancel `completed_at` stamps.** Supersede kills everything at once → *one* stamp; independent per-job timeouts → *N distinct* stamps spread over hours.
2. **Compare each cancelled job's elapsed against the ceiling in its *reusable* workflow file** (not the caller) — round-number matches (30/50/80/15 min) are the tell that the timeout fired.
3. **Cross-section the timeout class by `head_branch`** across ~60 recent runs: fires only on this PR's branch ⇒ the PR's own cost regression (author-owned, rerun cannot succeed); fires on unrelated branches too ⇒ systemic capacity ceiling. Bucketing on `conclusion` alone files a timeout as "flake" and triggers a futile rerun. Note `check-ci` is an aggregator red only because siblings are — never its own bucket. [Discriminate a per-job timeout-minutes cancel: PR-specific cost regression vs systemic capacity ceiling](../learnings/1786198665211-discriminate-a-per-job-timeout-minutes-cancel-pr-s.md) [Run-level CI bucketing hides job-level failures; discriminate `cancelled` by timeout arithmetic](../learnings/1786206264424-run-level-ci-bucketing-hides-job-level-failures-di.md)

GitHub's `waiting` status means *parked on a deployment-environment approval gate* — a human — and consumes **zero** runners. A capacity throttle that counts `waiting` as active livelocks the queue: slang's `ci_priority_common.py` put `waiting`/`requested`/`pending` in `ACTIVE_STATUSES`, so one run parked 27h on `environment=falcor-ci` review made every later bot dispatch yield (7❌/1✅/1-null of 9). The cheap tell the members weren't deliberate: the constant was *broader than its own docstring* ("queued or in progress"). When a status set models resource contention, audit every member against "does this state hold the resource?" The diagnostic trap: a healthy yield deliberately reports `conclusion=failure` on its aggregator job (to consume no expensive runners), so load-shedding is indistinguishable from a broken build at `/actions/runs?status=failure`. Discriminate by `event` (`workflow_dispatch` + `triggering_actor==nv-slang-bot[bot]`), presence of the `wait-for-human-priority` job, or the yield naming its blocker in the log — and use `/actions/runs/<id>/pending_deployments` to distinguish "parked on a human" from "queued for a runner" in one call. The behaviour is bounded (`--max-yield-hours 12`), so the correct report is "bot CI is ~12h late," not "dead." [A "waiting" run consumes no runners — but a capacity throttle that counts it livelocks the queue](../learnings/1786205852182-a-waiting-run-consumes-no-runners-but-a-capacity-t.md)

Zombie `queued` runs poison queue metrics directly. `?status=queued&per_page=100` returned 6 runs, two of them 71–73 days old with `updated_at` never advancing past May — 33% of the "queue" was a permanent constant, dragging max-age to 105983 min and firing a "depth ≥ 3" alarm forever. Before alarming on any count or percentile from a queue endpoint, check that the population *varies*: a row whose `updated_at==created_at` and is days old is a stuck record, not workload. Sort by `created_at` ascending, drop rows older than a sanity bound, and *log how many you dropped*. Corollary for the same repo: `event=dynamic` "pages build and deployment" runs carry a lagged `head_sha`, so join pages runs to commits by `created_at` adjacency, never by SHA. [Zombie queued CI runs poison queue metrics — 33% of a queue was two 71-day-old constants](../learnings/1786134666479-zombie-queued-ci-runs-poison-queue-metrics-33-of-a.md)
