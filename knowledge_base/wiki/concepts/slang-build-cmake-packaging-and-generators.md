# Slang Build — CMake Packaging, Generators, System Deps, and WASM

## TL;DR

- `generator()` tools are `EXCLUDE_FROM_ALL` — the default/Debug preset does not build them; verify a generator-backed step with a *plain* default build (NOT `--target <tool>`), which is the only build that reveals the gap.
- `SLANG_USE_SYSTEM_*` has no bundled fallback — read the `add_subdirectory` bundled-build gate, not the `find_package` line: `ON ⇒ bundled skipped unconditionally`, and `CONFIG QUIET` governs messaging, not fallback.
- With a system package a dependency is an IMPORTED target: test inheritance through `INTERFACE_LINK_LIBRARIES` (a static lib's PRIVATE dep appears as `$<LINK_ONLY:dep>`), never `LINK_LIBRARIES`, and never set PRIVATE properties on it.
- Docs-of-record PRs (licenses / dependency maps / pin policy) need per-cell source verification — read each LICENSE/header banner and each `LINK_WITH_*`/`#include` consumer, never analogy; a `.gitmodules` `branch =` may be a tag.
- Docs routing: `docs/design/*.md` is hand-maintained; `docs/generated/design/**` is auto-generated (`generated: true`) and hand-edits are overwritten — route new design docs to `docs/design/`.
- Release packaging: WASM bypasses CPack; the File-check step is not a validation gate — adding files to release archives requires touching both edit sites.
- The macOS release signing failure at v2026.12.0.1 was a greedy version-parse bug on 4-component tags, not an expired cert; `"0 valid identities found"` is a red herring.
- MSVC `/DEBUG` for Release PDBs silently disables `/OPT:REF` and `/OPT:ICF` (#12054) — larger binaries, no functional change; re-adding `/OPT` needs incremental OFF (LNK4075 otherwise).
- Editing `source/slang-llvm/` — the default build fetches a PREBUILT `libslang-llvm.so`, so your edit is NOT compiled locally.
- Editing only an included prelude header (`prelude/slang-cpp-types.h`) does not regenerate the embedded C++ prelude, and slang-test, slangc and render-test hide it by loading the source-tree prelude. `touch prelude/slang-cpp-prelude.h` before building, and check the library with `strings`.
- GCC <14.3 FIDDLE errors where line N expands `FIDDLE_<N-1>` are GCC libcpp PR108900 (off-by-one `__LINE__` once a TU passes 0x50000000 locations), not stale PCH or a generator bug; any header growth can trip a different TU. Fix: `-flarge-source-files` for GNU. Reproducing needs the exact Ubuntu CI headers.
- `slang-wasm` ships build artifacts (`slang-wasm.js` + `.wasm` + `interface.d.ts`) but has no npm publish — web-packaging asks are maintainer-infra, HOLD not fixer.
- Companion page [[wiki/concepts/slang-build-pch-provenance-and-capgen.md]] covers the stale-GCC-PCH FIDDLE-state trap, `SKIP_PRECOMPILE_HEADERS`, binary provenance, and the capability-generator invariants. Prior companion [[wiki/concepts/slang-misc-build-infrastructure-and-tooling.md]] covers CMake options, compiler flags, downstream-compiler discovery, and language-server config.

This page collects the CMake-packaging and generator-tooling build notes: release packaging (WASM/CPack + macOS signing), generator tools excluded from the default preset, the `SLANG_USE_SYSTEM_*` bundled-build gate, docs-of-record verification and docs routing, the MSVC `/DEBUG` `/OPT` regression, the `source/slang-llvm/` prebuilt-artifact trap, and `slang-wasm` npm packaging as maintainer-infra.

## MSVC /DEBUG for Release PDBs Silently Disables /OPT:REF and /OPT:ICF (#12054)

Slang's default MSVC Release build loses dead-code elimination and identical-COMDAT folding (larger binaries, no functional change) because `SLANG_ENABLE_RELEASE_DEBUG_INFO` defaults ON, injecting `/DEBUG` into MSVC Release links -- and MSVC's linker flips `/OPT` defaults (`REF->NOREF`, `ICF->NOICF`) whenever `/DEBUG` is present, which Slang never re-asserts. The non-obvious wrinkle: `/DEBUG` implies `/INCREMENTAL`, under which `/OPT:REF|ICF` are silently ignored (LNK4075), so re-adding them only works with incremental OFF -- Release already carries `/INCREMENTAL:NO` (clean) but a fix that also touches RelWithDebInfo must guard against LNK4075. Verify MSVC-linker behavior against Microsoft's `/DEBUG` doc + a code trace, not DeepWiki ([slang#12054: MSVC /DEBUG for Release PDBs silently disables /OPT:REF and /OPT:ICF](../learnings/1783729799704-slang-12054-msvc-debug-for-release-pdbs-silently-d.md)).

## Release Packaging: WASM Bypasses CPack (2026-07-14 fold)

Slang release packaging has two distinct edit sites, and the File-check step is not a validation gate. Platform ZIP/TGZ archives are built by CPack (files enter via `install(... COMPONENT metadata)` in `CMakeLists.txt`), but **WASM packages bypass CPack** entirely — so adding files to release archives (e.g. issue #12083's `LICENSES/` dir) requires touching both sites, and the release File-check step will not catch a WASM omission ([Slang release: WASM packages bypass CPack; File-check is not a validation gate](../learnings/1783957891963-slang-release-wasm-packages-bypass-cpack-file-chec.md)).

### macOS release signing failure was a greedy version-parse bug, not an expired cert (#12143)

The macOS release build's "Sign and notarize binaries" failure starting at tag v2026.12.0.1 was framed by jkwak as an expired signing cert, but triage proved a **workflow version-parsing bug**. `release.yml:217` re-derives the version from the resolved dylib filename with a greedy regex `sed -E 's/.*\.0\.([0-9]+(\.[0-9]+)*)\.dylib$/\1/'`. The real file is `libslang-compiler.0.${SLANG_VERSION_NUMERIC}.dylib`, and `SLANG_VERSION_NUMERIC` accepts N dotted components; for a 4-component tag the file is `libslang-compiler.0.2026.12.0.1.dylib`, where greedy `.*\.0\.` matches through the interior `.0.` and extracts `version=1`, so the rebuilt binaries array points at a nonexistent `libslang-compiler.0.1.dylib` and the sign loop's else `exit 1`s **before** codesign runs. Latent since PR #8926; failures began exactly at the first 4-component tag. The `"0 valid identities found"` line is a **red herring** — it comes from `security find-identity -v` at :177, which runs before cert import (:189) and gives zero signal on cert validity because the job dies earlier. Immediate fix: anchor the parse on the fixed prefix, `sed -E 's/^libslang-compiler\.0\.(.*)\.dylib$/\1/'`. Two lessons this reinforces: (1) it's another workflow-file bug the bot can't PR (no `workflows` permission, same as #11985/#12062), so it routes to a human/maintainer, not slang-fixer — the same routing consequence already noted for the RelWithDebInfo/common-setup change above; (2) method — when a CI failure is framed as cause X, read the actual failing step's script and reproduce with a 30-second `sed` (the error string `0.1.dylib` itself encoded the real bug), rather than accepting the initial framing ([slang release.yml macOS signing: greedy version-parse breaks on 4-component tags](../learnings/1784270564328-slang-release-yml-macos-signing-greedy-version-par.md)).

## CPack all-in-one archives emit duplicate parent-dir markers → break strict archive verifiers

With `CPACK_ARCHIVE_COMPONENT_INSTALL ON` + `CPACK_COMPONENTS_ALL_IN_ONE_PACKAGE ON`, CPack's archive generator stages each install component into its own tree and calls `addOneComponentToArchive` once per component **without deduplicating shared parent-directory entries** — so whenever ≥2 install components share a top-level prefix, that prefix's directory marker (e.g. `share/`) appears **once per component** in the single combined `.zip`/`.tar.gz`. On slang#13184 the nightly Release CI failed with `error: duplicate archive path: share` at the "Verify bundled user skills" step (a regression from #12963, which added a `user-skills` component under `share/slang/agent-skills` alongside the pre-existing docs component under `share/doc/slang`). Confirmation is cheap: reproduce with a ~15-line CMake project (two `install(... COMPONENT …)` rules under the same prefix + those two CPACK vars), `cpack -G TGZ`, then `tar -tzf pkg.tar.gz | sed 's#/$##' | sort | uniq -d` — the ONLY arrangement that removes the dup is putting both installs in ONE component (distinct-named components and `CPACK_COMPONENTS_GROUPING ALL_COMPONENTS_IN_ONE` still duplicate). Fix pattern: a duplicate *directory* marker is benign (idempotent on extract), so a strict archive checker should classify by entry type — tolerate directory+directory repeats but still reject duplicate *file* entries and directory/file collisions (track `dict[path -> is_directory]`, not a `set`). Build-scope facts: `extras/verify-user-skills-package.py` is pure Python and fully unit-testable in ~0.3s (`python3 -m unittest extras.tests.test_verify_user_skills_package`) — don't spin a 20-min Slang build for a packaging/verifier-only change — and `./extras/formatting.sh` does NOT format Python (no Python formatter in the repo toolchain) ([CPack all-in-one archives emit duplicate parent-dir markers → breaks strict archive verifiers](../learnings/1789894488167-cpack-all-in-one-archives-emit-duplicate-parent-di.md)).

## generator() Tools Are EXCLUDE_FROM_ALL — Not Built by the Default/Debug Preset (2026-07-21 fold)

A tool registered via the `generator(...)` macro in `tools/CMakeLists.txt` is `EXCLUDE_FROM_ALL` and its only reverse-dependency is the `all-generators` custom target — which has no `ALL` keyword, so nothing in a normal build depends on it. `cmake --workflow --preset debug` (configure `default` + build the default `ALL`) does NOT build generator tools; the `generators` preset that builds `all-generators` runs only in the WASM/emscripten CI branch. Consequence: if a CI step (or the standard debug/release build) needs a generator tool's binary, it will be absent — `find build/generators -name <tool>` returns empty. Danger: a build subagent that runs `--target <tool>` explicitly produces it and masks the gap; only a plain default build reveals it. Verify a generator-backed CI step by doing a *plain* `cmake --build --preset debug --target slang-test` (NOT `--target <tool>`) and checking the binary appears. Fix (in-tree convention): make a real ALL-graph target depend on it. `REQUIRED_BY <t>` uses `add_dependencies(<t> …)` which requires `<t>` to already exist — the existing `REQUIRED_BY slang-test` precedents work because they're defined *after* the `slang-test` target (~:284), so a `generator()` call near the top of the file can't use it (configure error "Cannot add target-level dependencies to non-existent target slang-test"). Instead add `add_dependencies(slang-test <tool>)` *after* the slang-test definition (~:311), guarded `if(TARGET <tool> AND NOT SLANG_GENERATORS_PATH)` (generators are imported when cross-compiling). Found via slang#12157 — a CI enforce step called a generator tool a reviewer proved was never built in the debug path ([Slang generator() tools are EXCLUDE_FROM_ALL — not built by the default/debug preset](../learnings/1784567879388-slang-generator-tools-are-exclude-from-all-not-bui.md)).

## SLANG_USE_SYSTEM_* Has No Bundled Fallback, and Docs-of-Record Need Per-Cell Verification (2026-07-23 fold)

Determine a "use system package" option's fallback behavior by reading the **`add_subdirectory` bundled-build gate**, not the `find_package` line: in Slang's `external/CMakeLists.txt` every `SLANG_USE_SYSTEM_<X>` follows `if(NOT SLANG_USE_SYSTEM_<X>) add_subdirectory(<x>) endif()`, so ON ⇒ bundled skipped **unconditionally** with NO fallback — `CONFIG QUIET` only suppresses the not-found *message*, it does not re-enable the submodule (a claim two independent sources got wrong, caught by codex reading the gate) ([SLANG_USE_SYSTEM_* has no bundled fallback — QUIET ≠ fallback; verify at the add_subdirectory gate](../learnings/1784761099055-slang-use-system-has-no-bundled-fallback-quiet-fal.md)). Relatedly, docs-of-record PRs (licenses, dependency→output maps, submodule pin policy) draw many small factual rounds — verify **every cell** from the authoritative source, never analogy: read each dep's LICENSE/COPYING or source-header banner (dxc = NCSA in `dxcapi.h`; lua's MIT is at the END of `lua.h`), derive output mapping from actual `LINK_WITH_*`/`#include` consumers (metal-cpp/Vulkan-Headers feed tools/slang-rhi, not the compiler backend), and treat `.gitmodules` `branch =` as possibly a TAG (fast_float `v8.2.7`) not always a branch ([docs-of-record PRs (licenses/deps/pin-policy) need per-cell source verification](../learnings/1784765808308-docs-of-record-prs-licenses-deps-pin-policy-need-p.md)).

A `SLANG_USE_SYSTEM_*` path also changes what the CMake code may assume about a target, because a dependency can now be an IMPORTED target from `find_package` (measured on PR #13867, `SLANG_USE_SYSTEM_SPIRV_TOOLS`, 2026-10-28). An IMPORTED target has no `LINK_LIBRARIES`. A STATIC library's PRIVATE dependency is recorded in `INTERFACE_LINK_LIBRARIES` as `$<LINK_ONLY:dep>`, both on the in-tree target and in its installed export, so "does consumer X inherit dep D from static lib L" is `D IN_LIST` or `"$<LINK_ONLY:D>" IN_LIST` L's `INTERFACE_LINK_LIBRARIES`; that one check covers bundled and system packages. For a SHARED L the PRIVATE dep is correctly absent from the interface, because D lives inside L's DLL. `target_compile_definitions(<imported target> PRIVATE ...)` is a hard configure error ("may only set INTERFACE properties on IMPORTED targets"), so guard it with `get_target_property(_imp tgt IMPORTED)` wherever a target may come from either Slang or a system package (the `external/CMakeLists.txt` MI_DEBUG block hit this). Vendored SPIRV-Tools installed static with `SPIRV_TOOLS_USE_MIMALLOC(_IN_STATIC_BUILD)` exports `mimalloc-static` in BOTH the SPIRV-Tools and SPIRV-Tools-opt export sets and installs no mimalloc headers, so `find_package(SPIRV-Tools-opt)` fails with "Some (but not all) targets in this export set were already defined"; to test a system-SPIRV-Tools-with-mimalloc path, install mimalloc standalone and patch `SPIRV-ToolsConfig.cmake` with `find_dependency(mimalloc)`. A probe gotcha: if you temporarily edit `CMakeLists.txt` for a configure probe and then revert it, a later `ninja` in that build dir re-runs CMake (the mtime changed) and silently regenerates without the probe, so keep the probe in place through the build and revert afterwards ([detect a transitive link via INTERFACE_LINK_LIBRARIES](../learnings/1793228740752-cmake-detect-a-dependency-s-transitive-link-via-in.md)).

Docs *routing* is likewise decided by the target folder: `docs/design/*.md` is HAND-maintained developer design notes (add a line to its `README.md` index; write against function/pass names, not line numbers) and is where a NEW canonical design doc belongs, whereas `docs/generated/design/**` is AUTO-GENERATED (front-matter `generated: true`) and hand-edits there are overwritten — so route "please document X" tasks to `docs/design/`, never to the generated tree (`docs/user-guide/a4-02-reference-capability-atoms.md` from `slang-capabilities.capdef` is similarly generated) ([docs/design is hand-maintained; docs/generated/design is regenerated — route new design docs to docs/design](../learnings/1784830597951-slang-docs-routing-docs-design-is-hand-maintained-.md)).

## slang-wasm ships build artifacts but has no npm publish — web-packaging asks are maintainer-infra, not compiler work (2026-08-03 fold)

A recurring class of web/bundler triage (e.g. #12317 "bundler plugins for the web") hinges on a build-infrastructure fact rather than a compiler capability: **`slang-wasm` already emits everything an npm package needs, but nothing publishes it.** `source/slang-wasm/CMakeLists.txt` links with `--emit-tsd interface.d.ts` + `-sEXPORT_ES6=1 -sMODULARIZE=1`, producing `slang-wasm.js` + `slang-wasm.wasm` + `interface.d.ts`; these are assembled *only* in `.github/workflows/release.yml` (tag-triggered, Linux-only) by manual `cp`/`zip` (~lines 283-292, an `exit 0` bypasses CPack) into `slang-<version>-wasm.zip`. There is **no `package.json` in the source tree** and **no `npm publish`/`NODE_AUTH_TOKEN`/`registry-url` anywhere in `.github/workflows/`** (grep = 0). So "publish `@shader-slang/slang-wasm` to npm" is a *packaging + maintainer-infra* task (npm scope + `NPM_TOKEN` secret + publish cadence) — classify as a design/policy gate and HOLD, don't forward to the fixer as a compiler change. Two adjacent facts sharpen the triage: reflection→TypeScript-type codegen is *already* feasible on the bound surface (`ProgramLayout.toJsonObject()` + `getGlobalParamsTypeLayout`/`VariableLayoutReflection`/`TypeReflection`, backed by `source/slang/slang-reflection-json.cpp`) so an unplugin needs no new C++ — but `createSession` takes only an int target and exposes no compiler-*option* surface, so anything needing compile flags first needs the binding widened; and WGSL/WebGPU is officially experimental/WIP (`README.md:118`,`:126`, `docs/user-guide/09-targets.md:419`) — a status one Explore subagent got backwards, so verify it by direct README read and carry the WIP hedge into the public verdict ([slang-wasm ships types but is not npm-published; publishing is CI-packaging not compiler work](../learnings/1785699886372-slang-wasm-ships-types-but-is-not-npm-published-pu.md)). This is the same "read the build graph / workflow, don't infer capability from the binding" discipline as the [SLANG_USE_SYSTEM_* add_subdirectory-gate](../learnings/1784761099055-slang-use-system-has-no-bundled-fallback-quiet-fal.md) fold above and the [binary-provenance](../learnings/1785167795738-tests-spirv-opname-prefix-failures-from-stale-slan.md) fold on the companion page [[wiki/concepts/slang-build-pch-provenance-and-capgen.md]].

Two release-packaging `install()` traps recur, both invisible behind a green Linux CI. `cmake/FetchDXC.cmake` stages `dxcompiler`/`dxil` into the build tree via bare custom targets (`copy-dxcompiler`/`copy-dxil`) that carry **zero `install(...)` calls** and are never handed to `install()`, so CPack never packages DXC — the fix routes through `install_fetched_shared_library` (the same helper `slang-llvm` uses), needs no C++/ABI change (DXC loads by bare library name and installed binaries carry `INSTALL_RPATH "$ORIGIN/../lib;$ORIGIN"`, so a co-located DXC is auto-found), and the source-built (macOS) DXC's UOI-NCSA license text already ships in `LICENSES/`. Note that the `-dxc-path` (`-<compiler>-path` → `setDownstreamCompilerPath`) CLI override DOES exist — DeepWiki wrongly denied it, so trust the source for flag-existence questions ([DXC install gap; -dxc-path exists; UOI-NCSA text already shipped](../learnings/1789128761047-slang-dxc-install-gap-dxc-path-exists-deepwiki-wro.md)). Separately, a top-level `install()` guard **cannot reference `SLANG_BUILD_MIMALLOC`**: it is `set()` inside the `external/` subdirectory scope without `PARENT_SCOPE`, so it is undefined (silently false) at top level. Inline the equivalent boolean (`SLANG_ENABLE_MIMALLOC OR (SLANG_ENABLE_SLANG_GLSLANG AND NOT SLANG_USE_SYSTEM_SPIRV_TOOLS AND SLANG_ENABLE_SPIRV_TOOLS_MIMALLOC)` `AND NOT SLANG_OVERRIDE_MIMALLOC_PATH`) with a comment noting the variable is deliberately out of scope — because mimalloc defaults off on Linux CI, a broken predicate ships silently green ([SLANG_BUILD_MIMALLOC is unreachable at top-level scope — the PARENT_SCOPE trap](../learnings/1789247912043-slang-cmake-slang-build-mimalloc-is-unreachable-at.md)).

## Embedded C++ prelude: slang-embed's DEPENDS lists only the top-level header

`prelude/CMakeLists.txt` runs slang-embed only for `*-prelude.h` files. slang-embed inlines `slang-cpp-types.h` into the generated `slang-cpp-prelude.h.cpp`, but the custom command DEPENDS only on the top-level `slang-cpp-prelude.h`. So an incremental build after editing only `slang-cpp-types.h` (or another included header) leaves the prelude embedded in libslang-compiler stale. Check with `strings build/Debug/lib/libslang-compiler.so | grep -c <NewType>`, and fix it locally with `touch prelude/slang-cpp-prelude.h` before building. Local tests do not notice: `TestToolUtil::setSessionDefaultPreludeFromRootPath` replaces the embedded prelude in slang-test, slangc and render-test with a `#include` of the source-tree `prelude/slang-cpp-prelude.h`. So local tests go green while API users (the SlangPy CPU device, slang-rhi) get the stale prelude. Found on slang#13705 / PR #13716. The same work found a vacuous negative: in a `//TEST:SIMPLE(filecheck=X)` lane, `X-NOT: error` can never fail usefully, because slang-test output always contains the header `standard error = {`; check `X: result code = 0` instead ([editing only prelude/slang-cpp-types.h does not regenerate the embedded prelude](../learnings/1792170798320-editing-only-prelude-slang-cpp-types-h-does-not-re.md)).

## GCC <14.3 off-by-one `__LINE__` breaks FIDDLE in huge TUs — `-flarge-source-files` (PR108900)

A Linux GCC 13 build (e.g. SlangPy CI on Ubuntu 24.04, GCC 13.3) can fail in one Slang TU with FIDDLE errors where `FIDDLE` at source line N expands `FIDDLE_<N-1>`, another header's body, because `__LINE__` is one short. This is neither stale PCH state (the #12227 class on [[wiki/concepts/slang-build-pch-provenance-and-capgen.md]]) nor a FIDDLE generator bug. It is GCC libcpp bug PR108900, fixed in GCC 14.3 (via the PR120061 rework) and 15, unfixed in 13.x. Once a TU passes 0x50000000 source locations (`LINE_MAP_MAX_LOCATION_WITH_PACKED_RANGES`), an `#include` that lands on the freshly created, empty ordinary line map makes the includer resume one line short. About 12 `slang-common-objects` TUs exceed that threshold, so any header growth can move the crossing onto an `#include` and trip the bug in a different TU from the one you edited.

Reproducing needs the exact CI headers; host gcc-12, or conda gcc-13 with its own sysroot, does not reproduce because the line counts differ. The working recipe is micromamba `gxx_linux-64=13.3` (pass `--ssl-verify $SSL_CERT_FILE` behind the OneCLI proxy) plus Ubuntu noble debs extracted with `dpkg-deb -x` (libstdc++-13-dev, libc6-dev, linux-libc-dev, libgcc-13-dev, libcrypt-dev), compiling with `-nostdinc -nostdinc++ -isystem <root>/usr/include/c++/13 ...` and Ubuntu's default `-D_FORTIFY_SOURCE=3 -fstack-protector-strong -fcf-protection -fstack-clash-protection`, against a PCH built the same way. `-fdump-internal-locations` shows the culprit as an EMPTY `LC_RENAME` map right before an `LC_ENTER`. The fix is `-flarge-source-files` for GNU compilers, which sets `default_range_bits=0` and uses about 32x fewer locations, so the peak drops to ~6% of the threshold. Compile-time cost is within noise and RSS grows 3–4%. It landed on PR shader-slang/slang#13406 in `cmake/CompilerFlags.cmake` `set_default_compile_options`; master is exposed too ([GCC <14.3 off-by-one __LINE__ breaks FIDDLE in huge TUs; -flarge-source-files](../learnings/1791635533469-gcc-14-3-off-by-one-line-breaks-slang-fiddle-in-hu.md)).
