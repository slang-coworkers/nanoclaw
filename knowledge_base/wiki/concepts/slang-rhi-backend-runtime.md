# slang-rhi backend runtime internals

`slang-rhi` is the graphics-abstraction runtime library (Vulkan / D3D12 / CUDA / Metal / WGPU backends) vendored as a submodule and exercised by slang-test's `render-test`. This page collects source-verified facts about its **runtime** internals — buffer/queue lifetime, the CUDA constant-buffer pool, the CUDA heap's pinned-page leak, CUDA entry-point name lookup, staging-heap pooling, and Vulkan device creation on the fleet's software Vulkan — as distinct from the compiler's target emit (the `slang-backends-*` pages) and from slang-rhi test/build authoring ([Slang & slang-rhi test harness](slang-a-test-harness.md)). Facts below were source-verified at HEAD `e17f6d7` unless noted.

## TL;DR

- **A null-deref pinned at ONE site usually has a symmetric twin — grep every deref of the pointer before endorsing a one-site fix.** An imported Vulkan buffer with a null `m_buffer.m_api` crashes in *both* `~BufferImpl` (view teardown, `:169`) and `getView()` (view creation, `:333`); a destructor-only fix is incomplete, and a texel-SRV/UAV import hits the create side first.
- **A pointer that doubles as an ownership flag cannot be "fixed" by populating it.** `VKBufferHandleRAII::m_api` is null on imports *and* gates whether the destructor frees the `VkBuffer` — so source the dispatch table from the always-valid `getDevice<DeviceImpl>()->m_api`; setting the ownership field double-frees the caller's buffer. The maintainer's landed fix (#945) went further and replaced the flag with explicit `m_ownsBuffer`/`m_ownsMemory`, so name the conflation and offer that refactor instead of only routing around it.
- **The Vulkan `VkQueue` is shared de-facto and guarded nowhere.** It is never imported (only instance/device/physicalDevice are) and is always re-fetched via `vkGetDeviceQueue(...,0,...)`, so two `DeviceImpl` wrapping one native `VkDevice` get the *same* handle. The existing mutexes guard only the command-buffer pool — a per-wrapper mutex cannot serialize a shared native queue; you need an app-supplied shared object or a library-owned per-native-queue registry.
- **A `string_view` key into a bump-allocator's pages stays valid across `vector<Page>` growth** — the backing bytes are heap-allocated *outside* the vector, so reallocation moves the Page structs, not the bytes. Interning packed param packets by byte-content is lifetime-safe iff the map is cleared *before* the pool frees its pages and is read only during build.
- **Before slang-rhi#923 (2026-10-22), a destroyed CUDA device leaks its 256 MiB pinned heap pages while another device holds the primary context** (slangpy pytest's cached devices do). Measure with VmRSS plus `device.report_heaps()`, not smaps. A CI OOM at `cuda-heap.cpp:395` means a pre-#923 slang-rhi.
- **StagingHeap ReadBack pages are `HOST_VISIBLE | HOST_COHERENT`, NOT `HOST_CACHED`, on main before PR #929** — don't claim "faster CPU reads" for readback staging (that is the separate `IHeap`/`HeapImpl` path). On the L40S that uncached type reads at about 0.15 GB/s against about 4.7 GB/s for the HOST_CACHED type that #929 selects. The pooled `readBuffer` of #869 inherits #929's choice through `createBuffer(ReadBack)` (verified at runtime: memory type 3, flags `0xe`). `StagingHeap::map` returns an *offset-advanced* pointer; `memcpy` directly, no manual offset math.
- **To prove pooling in a GPU test, use a fresh device (`DontCacheDevice`).** Cached devices retain one standard page, so `getNumPages()>=1` after a read does not distinguish pooled from transient. A fresh heap starts at 0 pages; `0→1` after the first read is the definitive discriminator.
- **Tie a pooled staging allocation's lifetime to GPU completion, not RAII scope-exit.** `commandList->retainResource(handle)` holds it in the command buffer's tracked set until *retirement* (`CommandBuffer::reset`), so a post-submit `waitOnHost` failure keeps a possibly-in-flight page owned instead of returning it to the pool. Use `RefPtr<StagingHeap::Handle>` (`allocHandle`), never bare alloc/free — that leaks on any post-alloc `SLANG_RETURN_ON_FAIL` and trips the `m_totalUsed==0` teardown assert.
- **D3D11/D3D12 `clearTextureUint`/`Sint` silently do nothing on a RenderTarget-only texture** (only the UAV path exists; the float clear has an RT branch). Vulkan, Metal and WGPU are fine, so a new integer-RT clear test fails on D3D only.
- **A CUDA `cuModuleGetFunction … NOT_FOUND` at pipeline creation: grep the log for E40100 first.** Slang renames an entry point named `main` to `main_0`, and the RHI appears to look up the original name. slang-rhi squash-merges, so re-pin a submodule that points at a PR head once the PR merges.
- **Run `-vk` on the L40S first; lavapipe is only the fallback.** Coworker containers have an NVIDIA L40S with the NVIDIA Vulkan ICD ([containers have an NVIDIA L40S](../learnings/1792133264162-coworker-containers-have-an-nvidia-l40s-gpu-cuda-vulkan.md)), so measure with `nvidia-smi -L` each session and report a failure as infra. Only when lavapipe (Mesa 22.3.6) is the sole ICD, as during the 2026-09-28→10-16 passthrough outage, does Vulkan device creation fail because slang-rhi pushes `VK_KHR_shader_non_semantic_info` unconditionally; a local-only guard on that push plus `VK_ICD_FILENAMES=…lvp_icd…` then gives real readbacks through `render-test` (revert it, never commit it).
- **Slang puts every Vulkan push-constant block at Offset 0, but slang-rhi gives the ranges consecutive offsets,** so a global `[[vk::push_constant]]` plus entry-point uniforms reads the wrong bytes, and two blocks used by one entry point are invalid SPIR-V that slangc accepts with exit 0. Use a plain global `uniform` (UBO) instead, and check DeepWiki layout claims against slangc output.
- **On D3D12, a shader with both global `uniform` data and `ConstantBuffer` params gets CBVs one register high in slang-rhi's root signature** (`b0,b2,b3` vs HLSL `b0,b1,b2`), so dx12 pipeline creation fails while vk/cuda pass. Split such render-test tests.
- **Overflow-safe range check:** never form `offset + size` (both are `size_t`, it wraps). Validate `offset > desc.size` first, then `size > desc.size - offset`.

## Vulkan buffer and queue lifetime

When a bug report pins a null-pointer deref at one site, grep for **every** deref of that pointer before endorsing a targeted fix — the symmetric create/read site often shares the fault. In slang-rhi#860, an external reporter correctly found that `DeviceImpl::createBufferFromNativeHandle` (`src/vulkan/vk-buffer.cpp:475`) imports a borrowed `VkBuffer` but never calls `VKBufferHandleRAII::init()`, leaving `m_buffer.m_api` null, so `~BufferImpl()` destroys cached `VkBufferView`s through that null `m_api` (`:169`) and crashes — and proposed a destructor-only fix. The missed fact: `BufferImpl::getView()` **creates** the view via the *same* `m_buffer.m_api->vkCreateBufferView(...)` (`:333`), so an imported buffer bound as a texel SRV/UAV crashes at `:333` **before** it can ever reach the destructor — the reporter's own repro precondition ("acquire a view") is unmeetable without also fixing the create side. The correct fix routes *both* `getView:333` and `~BufferImpl:169` through `getDevice<DeviceImpl>()->m_api` (the device dispatch table is always valid; mirror the descriptor-handle loop at `:157-163`). Crucially, `VKBufferHandleRAII::m_api` doubles as an **ownership flag** — its destructor (`vk-buffer.h:30-34`) frees the buffer + memory iff `m_api != null` — so you cannot "fix" the null deref by simply setting `m_api` on an import; that would free the caller's buffer (double-free). When a pointer conflates dispatch-table with ownership, source the dispatch table elsewhere, never populate the ownership-flagging field. (Vulkan-specific: D3D12/Metal/WGPU/CUDA `BufferImpl` have no per-buffer view cache freed through a borrowed api pointer.) [imported-buffer null m_api: create site shares the deref](../learnings/1789372389751-slang-rhi-imported-buffer-null-m-api-the-create-si.md) The bot's PR (#868) did exactly that: device-API routing on both sites, `m_api` kept as the implicit ownership flag, and the uninitialized `m_memory` scoped out as pre-existing. Maintainer skallweitNV closed it and landed #945, which keeps the device-API routing but replaces the double-duty field with explicit `m_ownsBuffer`/`m_ownsMemory` bools: handles default to null, copy is disabled, and ownership is set after each successful allocation. An imported buffer owns neither, so its `m_api` can be valid, and the uninitialized `m_memory` is fixed in the same change. So when a minimal fix works around a field that means two things (API access and ownership), name the conflation and offer the explicit-ownership refactor as an alternative in the explanation comment; a reviewer accepting the root issue as "pre-existing / out of scope" is not the maintainer agreeing ([slang-rhi maintainer prefers explicit ownership over a field doing double duty (#860 → #945)](../learnings/1793091793971-slang-rhi-maintainer-prefers-explicit-ownership-ov.md)).

The Vulkan `VkQueue` is shared de-facto and guarded nowhere (triage of slang-rhi#863). It is **never imported** — `DeviceNativeHandles` has only 3 slots (instance/physicalDevice/device, `include/slang-rhi.h:3431-3433`), and even for an imported native `VkDevice` the queue is always fetched via `vkGetDeviceQueue(m_device, m_queueFamilyIndex, 0, &queue)` (`src/vulkan/vk-device.cpp:1857-1858`). Consequence: two independent `DeviceImpl` wrapping the same native `VkDevice` receive the **same** `VkQueue` handle, with no explicit import. And the queue is completely unguarded even within a single Device — two internal submitters share it (`CommandQueueImpl::submit`, `vk-command.cpp:2131`; `VulkanDeviceQueue::flushStepA`, `vk-device-queue.cpp:124`), plus `SurfaceImpl::present`/`destroySwapchain` and both `vkQueueWaitIdle` sites; the existing mutexes (`CommandQueueImpl::m_mutex`, `m_deferredDeleteQueueMutex`) guard only the command-buffer pool. d3d12/cuda mirror the same "pool mutex only, submit unlocked" pattern, and there is **no cross-`DeviceImpl` sync and no native-queue registry** anywhere. So a per-wrapper mutex genuinely cannot serialize a shared native queue — the fix requires either an app-supplied shared object (the only thing that can also cover the app's own out-of-RHI raw calls) or a library-owned per-native-queue registry funneled through a single choke-point wrapper. [Vulkan shares one VkQueue de-facto and guards it nowhere](../learnings/1789373034879-slang-rhi-vulkan-shares-one-vkqueue-de-facto-and-g.md)

## Guarding a public getter that the RHI also calls internally

Before adding an error/guard at a maintainer-named "choke point" method, grep its INTERNAL callers first — a guard that fires on legitimate internal use is a regression, not a safeguard. For slang-rhi#787 (forbid `getDeviceAddress`/bindless handles on `Shared` resources on Vulkan, so the queue-family reacquire stays complete), `IBuffer::getDeviceAddress()` is a public API AND is called ~20× internally during command recording (acceleration-structure/micromap build inputs + scratch, cluster ops, cooperative-vector src/dst); a naive guard returning 0 for a `Shared` buffer used on those *legitimately tracked* internal paths corrupts a valid operation (codex flagged it HIGH), and because `BufferOffsetPair::getDeviceAddress()` computes `base + offset`, a 0 sentinel + nonzero offset fabricates a bogus valid-looking address — preserve `base ? base + offset : 0`. Fix pattern: split a **public guarded** entry from an **internal unguarded** accessor (`getDeviceAddressUnchecked()` + a `getBufferDeviceAddress(BufferOffsetPair)` helper) and reroute the internal recording sites to the unchecked one; the guard then applies only to the app-facing call (which forms an *untracked* GPU reference), while internal operands are retained in the command buffer's `m_trackedObjects` and reacquired normally. The discriminator for which sites reroute: "app-provided operand (could be `Shared`)" vs "RHI-owned internal buffer (never `Shared` — SBT, AS/micromap backing)" ([Guarding a public getter that RHI calls internally breaks internal uses — split public-guarded from internal-unchecked](../learnings/1790032907874-guarding-a-public-getter-that-rhi-calls-internally.md)).

## CUDA constant-buffer pool: interning by byte-content is lifetime-safe

Interning packed global-param packets by byte-content — a `std::unordered_map<std::string_view, CUdeviceptr>` whose `string_view` keys point into `objectData.host` (slang-rhi#861) — reads as a dangling-key hazard but is not one, and the reasons generalize. `objectData.host` comes from `ConstantBufferPool::Pool::allocate` (`src/cuda/cuda-constant-buffer-pool.cpp:96`), a **bump allocator** whose pages are `HeapAlloc`s returning an inline `address` (`include/slang-rhi.h:3135/3138`) that points to memory heap-allocated **outside** the `std::vector<Page>` — so `vector<Page>` reallocation on `push_back` moves the Page structs but NOT the backing bytes, keeping the `string_view` keys valid across pool growth (append-only during a build; no written region is rewritten/freed mid-build). Ownership is co-terminous: `BindingCache` and `ConstantBufferPool` are both members of `CommandBufferImpl` (`cuda-command.h:116-117`), and `CommandBufferImpl::reset()` clears the map (`:1465`) **before** freeing pool pages (`:1466`); the map is read only via `try_emplace` during building, never after free. The paired execution-side copy-skip (`m_globalParamsState` in `cmdDispatchCompute`) is correct because `CommandExecutor` is strictly per-command-buffer, `computePipeline->m_globalParams` is a stable distinct per-pipeline device symbol whose sole writer is the dispatch copy, the stream is single-threaded FIFO, and `cmdExecuteCallback` clears the cache — but the two halves are coupled: source-pointer identity is a valid byte-equality proxy **only** because interning canonicalizes device addresses, so splitting them keeps correctness but loses the win. (This was a read-only triage: slang-rhi has no `reproduced`/`CUDA`/`perf` labels — `enhancement` is the right label for such an optimization.) [CUDA string_view-keyed intern map into ConstantBufferPool is lifetime-safe](../learnings/1789372807192-slang-rhi-cuda-string-view-keyed-intern-map-into-c.md)

## CUDA heap: a destroyed device leaks 256 MiB pinned pages before slang-rhi#923

Up to slang-rhi 57018e3 (slang-rhi#923, merged 2026-10-22), `HeapImpl::~HeapImpl` (`src/cuda/cuda-heap.cpp:306-310` at d825f483) frees only the page cache, and `Heap::~Heap` (`src/heap.cpp:18-24`) then deletes the resident pages without `cuMemFree`/`cuMemFreeHost`. CUDA devices use the primary context, so the leaked memory comes back only when the last device releases that context. The heap uses a 256 MiB page for any request up to 64 MiB (`heap.cpp:45-48`). In slangpy pytest the session-cached test devices hold the context for the whole run, so every uncached device that did an upload or readback strands one 256 MiB pinned page. Repro on the L40S with the slangpy 0.43.1 wheel: keep one CUDA device open, then in a loop create a second device, upload one texture and close it. VmRSS grows 256 MiB per cycle; it grows 0 with no upload, or with no other device kept open (script `/workspace/agent/repro-13890/variants2.py`; context shader-slang/slang#13891) ([CUDA heap leaks a 256 MiB pinned page per destroyed device while the primary context is alive](../learnings/1792770237658-slang-rhi-cuda-heap-leaks-256-mib-pinned-page-per-.md)).

Diagnosis notes from the same work. `/proc/self/smaps` does not attribute this RSS to any one mapping, so use VmRSS together with `device.report_heaps()`. `Heap::allocate`'s OOM retry (`heap.cpp:77-82`) never runs on CUDA, because `SLANG_CUDA_RETURN_ON_FAIL_REPORT` returns `SLANG_FAIL` for every `CUresult` (`cuda-utils.h:83`); that is the -2147467259 seen in logs. A CI OOM at `cuda-heap.cpp:395` means the slang-rhi in use predates #923; after the fix the call is at `:406`. Give repro variant modes names that are not substrings of each other: "noupload" contains "upload" and broke the first control run.

## Staging-heap pooling for readback

Routing Vulkan `readBuffer` through the pooled `m_readbackHeap` `StagingHeap` (slang-rhi#862) rests on several non-obvious facts. StagingHeap ReadBack pages are **not** `HOST_CACHED`: `StagingHeap::allocPage` creates them via `device->createBuffer` with `memoryType=ReadBack`, which requests only `HOST_VISIBLE | HOST_COHERENT` (`src/vulkan/vk-buffer.cpp:414-416`); the `HOST_CACHED` flags at `vk-heap.cpp:38-40` are the *separate* `IHeap`/`HeapImpl` path, which StagingHeap does not use — so don't claim "faster CPU reads" for readback staging (a triage memo did and was wrong; codex OUTPUT_REVIEW caught it). `StagingHeap::map(alloc, &ptr)` returns an offset-advanced pointer (`page->getMapped() + offset`, `staging-heap.cpp:181`), so after `map` you `memcpy` directly — `getOffset()` is only the *destination* offset for `copyBuffer`. `StagingHeap::free()` retains one empty *standard* page (16 MiB) for reuse and frees oversized pages immediately, so after a readback `getUsed()==0` but `getNumPages()>=1`. Because of that retained page, **to prove pooling in a GPU test you must use a fresh device** — `GPU_TEST_CASE(name, Vulkan | DontCacheDevice)`; `StagingHeap::initialize()` pre-allocates nothing, so a fresh heap starts at `getNumPages()==0`, and `0→1` after the first read is a definitive discriminator (the transient impl never touches the heap). Use overflow-safe range validation (validate `offset > desc.size`, then `size > desc.size - offset`; never form the wrapping `offset + size`). [Vulkan readBuffer pooling: HOST_CACHED myth, fresh-device pooling proof](../learnings/1789440138998-slang-rhi-vulkan-readbuffer-pooling-host-cached-my.md) The cost of that choice is measurable on the fleet's L40S (Linux driver, 2026-10-20). For a TRANSFER_DST buffer, Vulkan memory type 1 is DEVICE_LOCAL, type 2 is HOST_VISIBLE|HOST_COHERENT (uncached, about 0.15 GB/s CPU read), and type 3 adds HOST_CACHED (about 4.7 GB/s map+memcpy at 256 MiB). slang-rhi main picks type 2 for ReadBack buffers, the `readBuffer` staging buffer and readback StagingHeap pages; PR #929 (7577eea, slang-rhi#928) picks type 3 for all three. So "ReadBack staging is not HOST_CACHED" is a fact about main before #929, not a design invariant ([slang-rhi-tests -tc needs a device suffix wildcard; L40S Vulkan memory types](../learnings/1792502963862-slang-rhi-tests-tc-needs-a-device-suffix-wildcard.md)). When #869 (pooled `readBuffer`) conflicted with #929, because #929 edited the transient staging buffer that #869 deletes, the resolution kept #869's body and dropped #929's hunk on the claim that the pooled path still inherits #929's effect. The code supports that claim (`device.cpp:436` sets the ReadBack heap, `staging-heap.cpp:234-238` calls `createBuffer`, and `vk-buffer.cpp` prefers HOST_CACHED), and a temporary `fprintf` in `allocateVkMemory` (reverted before the push) confirmed it on the L40S: the readback-heap page got memory type 3, flags `0xe` (HOST_CACHED), and the upload page got type 2. A conflict resolution that drops a hunk because "the other path inherits it" rests on that inheritance, so check it at runtime, not only by reading ([merging a PR whose code path an upstream PR edited: verify the claimed inheritance at runtime](../learnings/1793106992385-merging-a-pr-whose-code-path-an-upstream-pr-edited.md)).

The **correct** way to free a pooled staging allocation is completion-coupled, not RAII scope-exit — a bare `RefPtr` free at function-scope exit can return a page that is still in flight if a later `waitOnHost` fails. Tie the allocation to command completion via the command buffer's tracked-object set, mirroring `CommandEncoder::uploadBufferData`/`uploadTextureData` (`src/command-buffer.cpp:616,688`): after `copyBuffer`, call `checked_cast<CommandEncoder*>(commandEncoder.get())->m_commandList->retainResource(staging)`, then `submit`/`waitOnHost`/`map`. `retainResource(RefObject*)` (`src/command-list.h:473`) inserts a `RefPtr` into the command buffer's `m_trackedObjects` (`std::set<RefPtr<RefObject>>`, `command-buffer.h:422`), which is cleared in `CommandBuffer::reset()` — i.e. at **retirement** — so on a successful `waitOnHost` retirement frees the page (`getUsed()==0`), while on a post-submit `waitOnHost` failure the un-retired command buffer keeps the handle owned and the possibly-in-flight shared page is NOT returned to the pool. (Note `CommandList::reset()` does NOT clear `m_trackedObjects`; retirement does.) Use `RefPtr<StagingHeap::Handle>` via `allocHandle`, never bare alloc/free — freeing only on the success path leaks on any post-alloc `SLANG_RETURN_ON_FAIL` and trips `StagingHeap::release()`'s `m_totalUsed==0` assert at teardown (`Device::readTexture` itself still has this latent non-RAII leak). One known residual to flag as a follow-up, not a blocker: `~DeviceImpl` (`vk-device.cpp:147`) calls `m_queue->waitOnHost()` ignoring its result, then releases both staging heaps (which assert `m_totalUsed==0`), so a failed teardown wait leaves a retained handle unfreed — a pre-existing hazard shared by every retained-staging path, fixable only by a cross-backend teardown reorder. (And don't over-claim `checked_cast` as "type-safe": it validates only in debug and is a plain `static_cast` in release.) [tie pooled-staging lifetime to GPU completion via retainResource](../learnings/1789448569968-slang-rhi-fix-pattern-tie-pooled-staging-lifetime-.md)

**For a Slang examples/sample-app fix of a Vulkan dynamic-rendering format-mismatch VUID, do NOT credit "the VUID is left to CI to catch" — CI cannot observe it.** Two independent reasons (PR #13127, colorTarget.format vs attachment format): slang-rhi surface/swapchain/format tests skip on headless CI at the `hasMonitor()` guard (green CI only compiles the surface path, never runs it), and the examples' offline/test CI path runs with the Vulkan validation layer DISABLED (`enableValidation = !isTestMode()`) — plus examples are skipped on Vulkan platforms. Such a fix is verified BY CONSTRUCTION + compile/link, not by any CI gate; state that honestly in the verdict rather than repeating the PR body's "left to CI." Reviewer A reached the same conclusion independently by reading `enableValidation = !isTestMode()`. For format bugs, follow the value to the actual VkImageCreateInfo/VkSwapchainCreateInfoKHR/ColorTargetDesc.format field — don't trust the getter name alone. ([Vulkan VUID in Slang examples: 'left to CI' is not a real gate — validation is OFF in offline CI](../learnings/1789564810840-vulkan-vuid-in-slang-examples-left-to-ci-is-not-a-.md))

## D3D11/D3D12 integer texture clears are no-ops on RenderTarget-only textures

In slang-rhi main f0c50c7 (and PR #899 head f76fb50), D3D11 and D3D12 `cmdClearTextureUint` (`d3d11-command.cpp:340`, `d3d12-command.cpp:505`) handle only `TextureUsage::UnorderedAccess`, and `clearTextureSint` routes through the same `commands::ClearTextureUint`. On a texture with RenderTarget usage and no UAV, integer clears therefore do nothing and report nothing, while `cmdClearTextureFloat` has a RenderTarget branch and works. Vulkan (`vkCmdClearColorImage`), Metal (clear engine) and WGPU handle the case. A new test that clears integer render targets fails on D3D only at the cleared subresource. The fix direction is an RT branch that converts int to float for `ClearRenderTargetView`, which is exact only up to 2^24; Dawn uses a draw (`apply_clear_big_integer_color_value_with_draw`) for larger values ([D3D11/D3D12 clearTextureUint/Sint are no-ops on RenderTarget-only textures](../learnings/1792518561170-slang-rhi-d3d11-d3d12-cleartextureuint-sint-are-no.md)). Two side facts from the same atom live elsewhere: on slang-rhi CI a green `build (windows, aarch64, msvc, Debug)` says nothing about tests, because the matrix `unit-test` flag skips its `Unit Tests` step ([[wiki/concepts/slang-a-test-harness.md]]); and backtick-wrapped `### Attested` hashes break the critique gate ([[wiki/concepts/agent-routing-f0909b1-critique-gate-mechanics.md]]).

## CUDA pipeline creation: an entry point named `main` is renamed `main_0` (E40100)

Consider a slangpy compute kernel declared `[shader("compute")] void main()` and dispatched on CUDA. In slangpy#1189 CI (2026-09-29) this failed at pipeline creation with `cuModuleGetFunction … CUDA_ERROR_NOT_FOUND named symbol not found` (slang-rhi `src/cuda/cuda-pipeline.cpp:89`). Slang had logged `warning[E40100]: entry point 'main' has been renamed to 'main_0'`, and the nine warnings matched the nine failures one for one. The working hypothesis, not yet verified with coverage off, is that the RHI looks up the entry point by its original name while the CUDA module exports the renamed symbol. When triaging a CUDA "named symbol not found", grep the log for E40100 first. Existing slangpy tests that use `void main` only load modules and never create a CUDA pipeline, so they do not catch this. A related submodule fact from the same work: slang-rhi squash-merges (single-parent commits on main), so a slangpy submodule pinned to an open slang-rhi PR head must be re-pinned to the squash commit once that PR merges ([CUDA: entry point `main` renamed to `main_0` (E40100) → cuModuleGetFunction NOT_FOUND](../learnings/1790685200036-cuda-entry-point-named-main-is-renamed-to-main-0-e.md)).

## Vulkan device creation on lavapipe: `VK_KHR_shader_non_semantic_info` is not optional

The agent containers normally run `-vk` on the passed-through NVIDIA L40S, and this section applies only when lavapipe is the sole Vulkan ICD. That was the state during the 2026-09-28→10-16 host passthrough outage ([passthrough restored 2026-10-16](../learnings/1792142517350-correction-gpu-passthrough-restored-2026-10-16-con.md)); never record it as "no GPU". With lavapipe only, `slang-test ... -vk` reports `Check vk,vulkan: Not Supported` even though mesa lavapipe is installed (`/usr/share/vulkan/icd.d/lvp_icd.x86_64.json`). The cause is in device creation, not in slang-test: `external/slang-rhi/src/vulkan/vk-device.cpp` (~:595) pushes `VK_KHR_shader_non_semantic_info` unconditionally, lavapipe from Mesa 22.3.6 does not expose that extension, and `vkCreateDevice` fails (visible with `VK_LOADER_DEBUG=error,warn`). This pins down the "required extension" that the older fleet observations on [[wiki/concepts/misc-f0909b7-ci-build-git-coworker-ops.md]] and [[wiki/concepts/slangpy-build-and-infra-operations.md]] reported only as a failed device create.

When a question needs observed Vulkan values rather than SPIR-V text, a local-only workaround works. Guard that push with `extensionNames.count(...)`, rebuild only the `render-test` target, and run with `VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.x86_64.json`:

```bash
slang-test -bindir build/Release/bin render-test <file> -vk -compute -output-using-type -shaderobj -o out.txt
```

That produces real Vulkan readbacks, and also works with `-emit-spirv-via-glsl`. Revert the guard and rebuild afterwards, and never commit it. Two neighbouring traps from the same investigation (slang#13446): `slangc -target host-callable -o x` fails with E00098 "cannot access as a blob", so use `-reflection-json` without `-o`; and for LLVM, render-test uses `host-callable` (plus `emit-cpu-via-llvm`), whose reflection differs from `shader-sharedlib` [observed Vulkan runs on lavapipe need slang-rhi non_semantic_info made optional](../learnings/1792028852820-observed-vulkan-runs-on-lavapipe-in-agent-containe.md).

## Vulkan push-constant ranges: slang-rhi's offsets disagree with Slang's layout (slangpy#1232)

Consider a SlangPy kernel with a global `[[vk::push_constant]]` block and also an entry-point `uniform float k`, dispatched on Vulkan (verified on the L40S with Slang 2026.19 and slang-rhi e0eeb428). Slang lays out every push-constant block at SPIR-V Offset 0, the global block and the entry-point uniforms alike, and reports each with `pushConstantBuffer` index 0 in its own scope (the program-wide counter that numbers them 0 and 1 is described on [[wiki/concepts/slang-test-gpu-lanes-on-shared-l40s.md]]). slang-rhi's `addAllPushConstantRangesRec` (`vk-shader-object-layout.cpp:907-916`) instead gives the ranges consecutive offsets, so the entry-point uniform data is pushed after the global block while the shader reads it at 0. That happens even when the shader never reads the global block: in a raw kernel, `k` read back the bits written to `push`. If the entry point reads both blocks, Slang emits two PushConstant interfaces, which violates `VUID-StandaloneSpirv-OpEntryPoint-06674`, and slangc still exits 0 unless `SLANG_RUN_SPIRV_VALIDATION=1` is set. DeepWiki claimed that Slang merges the blocks; slangc output shows it does not, so check any DeepWiki layout claim against slangc output.

`ParameterBlock<T>` plus a global push constant breaks in a second way: the set that holds only the push constant becomes an empty descriptor set at index 0 (slang#12349), which the open draft slang-rhi#810 fixes (verified). A plain global `uniform T x;`, which becomes a descriptor-bound UBO, works on both SlangPy paths and is the workaround. To read the real `maxPushConstantsSize` without `vulkaninfo`, call `vkGetPhysicalDeviceProperties` through ctypes: the limits struct starts at byte 296, and `maxPushConstantsSize` is at byte 328 (256 on the L40S) [global push_constant + entry-point uniforms: Slang and slang-rhi disagree on offsets](../learnings/1792164718700-vulkan-global-vk-push-constant-entry-point-uniform.md).

## D3D12 root signature: global uniforms plus `ConstantBuffer` params put CBVs one register high (slang#13824)

Consider a render-test compute shader with both a global `uniform` value and a `ConstantBuffer<T>` parameter, run on the dx12 lane. The HLSL uses `b0` for the implicit global constant buffer and `b1`, `b2` for the `ConstantBuffer` params, but slang-rhi builds a root signature with `b0,b2,b3`. `RootSignatureDescBuilder::addAsConstantBuffer` (`external/slang-rhi/src/d3d12/d3d12-shader-object-layout.cpp:644-667`, slang-rhi b856e635) adds the ordinary-data CBV and then increments the CBV offset (`offsetForRangeType++`) before it recurses, but for the global scope the sub-object offsets that reflection reports already count the implicit `b0`. `CreateComputePipelineState` then fails with "Shader CBV descriptor range (BaseShaderRegister=1, …) is not fully bound in root signature"; vk and cuda pass. For render-test tests, the workaround is not to mix global uniforms with `ConstantBuffer` params in one dx12 test, and to split the test instead (PR #13829). The Linux container has no dx12, but a small C++ probe that replays the builder's register math over real Slang reflection (`IComponentType::getLayout`, `getSubObjectRangeOffset`, `getContainerVarLayout`/`getElementVarLayout`, `getDescriptorSetDescriptorRangeIndexOffset`) predicts the mismatch. For a `globalExistentialType __Dynamic`, specialize with `findTypeByName("__Dynamic")` first. Probe: `/workspace/agent/scratch-13824-fix/rsprobe/probe.cpp` in the slang-fixer container [slang-rhi D3D12 root signature: global uniforms + ConstantBuffer params → CBVs one register high](../learnings/1792692825590-slang-rhi-d3d12-root-signature-global-uniforms-con.md). The Vulkan counterpart, where slang-rhi's push-constant offsets disagree with Slang's layout, is in the previous section.
