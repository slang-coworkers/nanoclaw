# slang-rhi backend runtime internals

`slang-rhi` is the graphics-abstraction runtime library (Vulkan / D3D12 / CUDA / Metal / WGPU backends) vendored as a submodule and exercised by slang-test's `render-test`. This page collects source-verified facts about its **runtime** internals — buffer/queue lifetime, the CUDA constant-buffer pool, and staging-heap pooling — as distinct from the compiler's target emit (the `slang-backends-*` pages) and from slang-rhi test/build authoring ([Slang & slang-rhi test harness](slang-a-test-harness.md)). Facts below were source-verified at HEAD `e17f6d7` unless noted.

## TL;DR

- **A null-deref pinned at ONE site usually has a symmetric twin — grep every deref of the pointer before endorsing a one-site fix.** An imported Vulkan buffer with a null `m_buffer.m_api` crashes in *both* `~BufferImpl` (view teardown, `:169`) and `getView()` (view creation, `:333`); a destructor-only fix is incomplete, and a texel-SRV/UAV import hits the create side first.
- **A pointer that doubles as an ownership flag cannot be "fixed" by populating it.** `VKBufferHandleRAII::m_api` is null on imports *and* gates whether the destructor frees the `VkBuffer` — so source the dispatch table from the always-valid `getDevice<DeviceImpl>()->m_api`; setting the ownership field double-frees the caller's buffer.
- **The Vulkan `VkQueue` is shared de-facto and guarded nowhere.** It is never imported (only instance/device/physicalDevice are) and is always re-fetched via `vkGetDeviceQueue(...,0,...)`, so two `DeviceImpl` wrapping one native `VkDevice` get the *same* handle. The existing mutexes guard only the command-buffer pool — a per-wrapper mutex cannot serialize a shared native queue; you need an app-supplied shared object or a library-owned per-native-queue registry.
- **A `string_view` key into a bump-allocator's pages stays valid across `vector<Page>` growth** — the backing bytes are heap-allocated *outside* the vector, so reallocation moves the Page structs, not the bytes. Interning packed param packets by byte-content is lifetime-safe iff the map is cleared *before* the pool frees its pages and is read only during build.
- **StagingHeap ReadBack pages are `HOST_VISIBLE | HOST_COHERENT`, NOT `HOST_CACHED`** — don't claim "faster CPU reads" for readback staging (that is the separate `IHeap`/`HeapImpl` path). `StagingHeap::map` returns an *offset-advanced* pointer; `memcpy` directly, no manual offset math.
- **To prove pooling in a GPU test, use a fresh device (`DontCacheDevice`).** Cached devices retain one standard page, so `getNumPages()>=1` after a read does not distinguish pooled from transient. A fresh heap starts at 0 pages; `0→1` after the first read is the definitive discriminator.
- **Tie a pooled staging allocation's lifetime to GPU completion, not RAII scope-exit.** `commandList->retainResource(handle)` holds it in the command buffer's tracked set until *retirement* (`CommandBuffer::reset`), so a post-submit `waitOnHost` failure keeps a possibly-in-flight page owned instead of returning it to the pool. Use `RefPtr<StagingHeap::Handle>` (`allocHandle`), never bare alloc/free — that leaks on any post-alloc `SLANG_RETURN_ON_FAIL` and trips the `m_totalUsed==0` teardown assert.
- **Overflow-safe range check:** never form `offset + size` (both are `size_t`, it wraps). Validate `offset > desc.size` first, then `size > desc.size - offset`.

## Vulkan buffer and queue lifetime

When a bug report pins a null-pointer deref at one site, grep for **every** deref of that pointer before endorsing a targeted fix — the symmetric create/read site often shares the fault. In slang-rhi#860, an external reporter correctly found that `DeviceImpl::createBufferFromNativeHandle` (`src/vulkan/vk-buffer.cpp:475`) imports a borrowed `VkBuffer` but never calls `VKBufferHandleRAII::init()`, leaving `m_buffer.m_api` null, so `~BufferImpl()` destroys cached `VkBufferView`s through that null `m_api` (`:169`) and crashes — and proposed a destructor-only fix. The missed fact: `BufferImpl::getView()` **creates** the view via the *same* `m_buffer.m_api->vkCreateBufferView(...)` (`:333`), so an imported buffer bound as a texel SRV/UAV crashes at `:333` **before** it can ever reach the destructor — the reporter's own repro precondition ("acquire a view") is unmeetable without also fixing the create side. The correct fix routes *both* `getView:333` and `~BufferImpl:169` through `getDevice<DeviceImpl>()->m_api` (the device dispatch table is always valid; mirror the descriptor-handle loop at `:157-163`). Crucially, `VKBufferHandleRAII::m_api` doubles as an **ownership flag** — its destructor (`vk-buffer.h:30-34`) frees the buffer + memory iff `m_api != null` — so you cannot "fix" the null deref by simply setting `m_api` on an import; that would free the caller's buffer (double-free). When a pointer conflates dispatch-table with ownership, source the dispatch table elsewhere, never populate the ownership-flagging field. (Vulkan-specific: D3D12/Metal/WGPU/CUDA `BufferImpl` have no per-buffer view cache freed through a borrowed api pointer.) [imported-buffer null m_api: create site shares the deref](../learnings/1789372389751-slang-rhi-imported-buffer-null-m-api-the-create-si.md)

The Vulkan `VkQueue` is shared de-facto and guarded nowhere (triage of slang-rhi#863). It is **never imported** — `DeviceNativeHandles` has only 3 slots (instance/physicalDevice/device, `include/slang-rhi.h:3431-3433`), and even for an imported native `VkDevice` the queue is always fetched via `vkGetDeviceQueue(m_device, m_queueFamilyIndex, 0, &queue)` (`src/vulkan/vk-device.cpp:1857-1858`). Consequence: two independent `DeviceImpl` wrapping the same native `VkDevice` receive the **same** `VkQueue` handle, with no explicit import. And the queue is completely unguarded even within a single Device — two internal submitters share it (`CommandQueueImpl::submit`, `vk-command.cpp:2131`; `VulkanDeviceQueue::flushStepA`, `vk-device-queue.cpp:124`), plus `SurfaceImpl::present`/`destroySwapchain` and both `vkQueueWaitIdle` sites; the existing mutexes (`CommandQueueImpl::m_mutex`, `m_deferredDeleteQueueMutex`) guard only the command-buffer pool. d3d12/cuda mirror the same "pool mutex only, submit unlocked" pattern, and there is **no cross-`DeviceImpl` sync and no native-queue registry** anywhere. So a per-wrapper mutex genuinely cannot serialize a shared native queue — the fix requires either an app-supplied shared object (the only thing that can also cover the app's own out-of-RHI raw calls) or a library-owned per-native-queue registry funneled through a single choke-point wrapper. [Vulkan shares one VkQueue de-facto and guards it nowhere](../learnings/1789373034879-slang-rhi-vulkan-shares-one-vkqueue-de-facto-and-g.md)

## CUDA constant-buffer pool: interning by byte-content is lifetime-safe

Interning packed global-param packets by byte-content — a `std::unordered_map<std::string_view, CUdeviceptr>` whose `string_view` keys point into `objectData.host` (slang-rhi#861) — reads as a dangling-key hazard but is not one, and the reasons generalize. `objectData.host` comes from `ConstantBufferPool::Pool::allocate` (`src/cuda/cuda-constant-buffer-pool.cpp:96`), a **bump allocator** whose pages are `HeapAlloc`s returning an inline `address` (`include/slang-rhi.h:3135/3138`) that points to memory heap-allocated **outside** the `std::vector<Page>` — so `vector<Page>` reallocation on `push_back` moves the Page structs but NOT the backing bytes, keeping the `string_view` keys valid across pool growth (append-only during a build; no written region is rewritten/freed mid-build). Ownership is co-terminous: `BindingCache` and `ConstantBufferPool` are both members of `CommandBufferImpl` (`cuda-command.h:116-117`), and `CommandBufferImpl::reset()` clears the map (`:1465`) **before** freeing pool pages (`:1466`); the map is read only via `try_emplace` during building, never after free. The paired execution-side copy-skip (`m_globalParamsState` in `cmdDispatchCompute`) is correct because `CommandExecutor` is strictly per-command-buffer, `computePipeline->m_globalParams` is a stable distinct per-pipeline device symbol whose sole writer is the dispatch copy, the stream is single-threaded FIFO, and `cmdExecuteCallback` clears the cache — but the two halves are coupled: source-pointer identity is a valid byte-equality proxy **only** because interning canonicalizes device addresses, so splitting them keeps correctness but loses the win. (This was a read-only triage: slang-rhi has no `reproduced`/`CUDA`/`perf` labels — `enhancement` is the right label for such an optimization.) [CUDA string_view-keyed intern map into ConstantBufferPool is lifetime-safe](../learnings/1789372807192-slang-rhi-cuda-string-view-keyed-intern-map-into-c.md)

## Staging-heap pooling for readback

Routing Vulkan `readBuffer` through the pooled `m_readbackHeap` `StagingHeap` (slang-rhi#862) rests on several non-obvious facts. StagingHeap ReadBack pages are **not** `HOST_CACHED`: `StagingHeap::allocPage` creates them via `device->createBuffer` with `memoryType=ReadBack`, which requests only `HOST_VISIBLE | HOST_COHERENT` (`src/vulkan/vk-buffer.cpp:414-416`); the `HOST_CACHED` flags at `vk-heap.cpp:38-40` are the *separate* `IHeap`/`HeapImpl` path, which StagingHeap does not use — so don't claim "faster CPU reads" for readback staging (a triage memo did and was wrong; codex OUTPUT_REVIEW caught it). `StagingHeap::map(alloc, &ptr)` returns an offset-advanced pointer (`page->getMapped() + offset`, `staging-heap.cpp:181`), so after `map` you `memcpy` directly — `getOffset()` is only the *destination* offset for `copyBuffer`. `StagingHeap::free()` retains one empty *standard* page (16 MiB) for reuse and frees oversized pages immediately, so after a readback `getUsed()==0` but `getNumPages()>=1`. Because of that retained page, **to prove pooling in a GPU test you must use a fresh device** — `GPU_TEST_CASE(name, Vulkan | DontCacheDevice)`; `StagingHeap::initialize()` pre-allocates nothing, so a fresh heap starts at `getNumPages()==0`, and `0→1` after the first read is a definitive discriminator (the transient impl never touches the heap). Use overflow-safe range validation (validate `offset > desc.size`, then `size > desc.size - offset`; never form the wrapping `offset + size`). [Vulkan readBuffer pooling: HOST_CACHED myth, fresh-device pooling proof](../learnings/1789440138998-slang-rhi-vulkan-readbuffer-pooling-host-cached-my.md)

The **correct** way to free a pooled staging allocation is completion-coupled, not RAII scope-exit — a bare `RefPtr` free at function-scope exit can return a page that is still in flight if a later `waitOnHost` fails. Tie the allocation to command completion via the command buffer's tracked-object set, mirroring `CommandEncoder::uploadBufferData`/`uploadTextureData` (`src/command-buffer.cpp:616,688`): after `copyBuffer`, call `checked_cast<CommandEncoder*>(commandEncoder.get())->m_commandList->retainResource(staging)`, then `submit`/`waitOnHost`/`map`. `retainResource(RefObject*)` (`src/command-list.h:473`) inserts a `RefPtr` into the command buffer's `m_trackedObjects` (`std::set<RefPtr<RefObject>>`, `command-buffer.h:422`), which is cleared in `CommandBuffer::reset()` — i.e. at **retirement** — so on a successful `waitOnHost` retirement frees the page (`getUsed()==0`), while on a post-submit `waitOnHost` failure the un-retired command buffer keeps the handle owned and the possibly-in-flight shared page is NOT returned to the pool. (Note `CommandList::reset()` does NOT clear `m_trackedObjects`; retirement does.) Use `RefPtr<StagingHeap::Handle>` via `allocHandle`, never bare alloc/free — freeing only on the success path leaks on any post-alloc `SLANG_RETURN_ON_FAIL` and trips `StagingHeap::release()`'s `m_totalUsed==0` assert at teardown (`Device::readTexture` itself still has this latent non-RAII leak). One known residual to flag as a follow-up, not a blocker: `~DeviceImpl` (`vk-device.cpp:147`) calls `m_queue->waitOnHost()` ignoring its result, then releases both staging heaps (which assert `m_totalUsed==0`), so a failed teardown wait leaves a retained handle unfreed — a pre-existing hazard shared by every retained-staging path, fixable only by a cross-backend teardown reorder. (And don't over-claim `checked_cast` as "type-safe": it validates only in debug and is a plain `static_cast` in release.)
