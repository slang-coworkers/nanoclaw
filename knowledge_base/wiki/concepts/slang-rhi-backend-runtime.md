# slang-rhi backend runtime internals

`slang-rhi` is the graphics-abstraction runtime library (Vulkan / D3D12 / CUDA / Metal / WGPU backends), vendored as a submodule and exercised by slang-test's `render-test`. This page collects source-verified facts about its **runtime** internals — buffer/queue lifetime, the CUDA constant-buffer pool and heap, CUDA entry-point lookup, staging-heap pooling, push-constant and root-signature layout, and Vulkan device creation on software Vulkan — as distinct from the compiler's target emit (the `slang-backends-*` pages) and from slang-rhi test/build authoring ([Slang & slang-rhi test harness](slang-a-test-harness.md)). Facts were source-verified at HEAD `e17f6d7` unless noted.

## TL;DR

- **A null deref pinned at one site usually has a symmetric twin; grep every deref of the pointer before endorsing a one-site fix.** An imported Vulkan buffer's null `m_buffer.m_api` crashes both `~BufferImpl` (view teardown, `:169`) and `getView()` (view creation, `:333`), and a texel-SRV/UAV import hits the create side first.
- **A pointer that doubles as an ownership flag cannot be fixed by populating it.** Setting `VKBufferHandleRAII::m_api` on an import double-frees the caller's buffer; take the dispatch table from `getDevice<DeviceImpl>()->m_api`. The maintainer's landed fix (#945) replaced the flag with explicit `m_ownsBuffer`/`m_ownsMemory`, so name the conflation and offer that refactor.
- **The Vulkan `VkQueue` is shared de-facto and guarded nowhere.** It is never imported and always re-fetched at index 0, so two `DeviceImpl` over one `VkDevice` get the same handle, and the existing mutexes guard only the command-buffer pool. A per-wrapper mutex cannot serialize it; that needs an app-supplied shared object or a library-owned per-native-queue registry.
- **Before guarding a public getter, grep its internal callers.** `getDeviceAddress()` is also called ~20× during command recording, so split a public guarded entry from an internal unchecked accessor, and keep `base ? base + offset : 0`.
- **`string_view` keys into a bump allocator's pages survive `vector<Page>` growth** (the bytes live outside the vector). A byte-content intern map is lifetime-safe iff it is cleared before the pool frees its pages and read only during build.
- **Before slang-rhi#923 (2026-10-22), a destroyed CUDA device leaks its 256 MiB pinned heap page while another device holds the primary context** (slangpy pytest's cached devices do). Measure with VmRSS plus `device.report_heaps()`, not smaps; a CI OOM at `cuda-heap.cpp:395` means a pre-#923 slang-rhi.
- **On main before PR #929, StagingHeap ReadBack pages are `HOST_VISIBLE | HOST_COHERENT`, not `HOST_CACHED`** (about 0.15 vs 4.7 GB/s CPU read on the L40S), so don't claim "faster CPU reads" for readback staging. #869's pooled `readBuffer` inherits #929's cached type (verified at runtime). `StagingHeap::map` returns an offset-advanced pointer.
- **Prove pooling on a fresh device (`DontCacheDevice`):** cached devices keep one standard page, while a fresh heap goes `0→1` pages on the first read.
- **Tie a pooled staging allocation's lifetime to GPU completion, not scope exit:** `retainResource` holds it until command-buffer retirement, as a `RefPtr<StagingHeap::Handle>` from `allocHandle`, never bare alloc/free.
- **Overflow-safe range check:** never form `offset + size` (`size_t` wraps); check `offset > desc.size`, then `size > desc.size - offset`.
- **A Vulkan VUID fix in Slang examples is not CI-gated** (surface tests skip headless, examples run with validation off); it is verified by construction, so say so.
- **D3D11/D3D12 `clearTextureUint`/`Sint` silently do nothing on a RenderTarget-only texture**; Vulkan, Metal and WGPU are fine, so a new integer-RT clear test fails on D3D only.
- **A CUDA `cuModuleGetFunction … NOT_FOUND` at pipeline creation: grep the log for E40100 first** (`main` renamed to `main_0`). slang-rhi squash-merges, so re-pin a submodule that points at a PR head once the PR merges.
- **Run `-vk` on the L40S first; lavapipe is only the fallback.** Measure with `nvidia-smi -L` each session and report a failure as infra. Only with lavapipe as the sole ICD does device creation fail, because slang-rhi pushes `VK_KHR_shader_non_semantic_info` unconditionally; a local-only guard plus `VK_ICD_FILENAMES=…lvp_icd…` then gives real readbacks (never commit it).
- **Slang puts every Vulkan push-constant block at Offset 0, but slang-rhi gives the ranges consecutive offsets,** so a global `[[vk::push_constant]]` plus entry-point uniforms reads the wrong bytes. Use a plain global `uniform` (UBO), and check DeepWiki layout claims against slangc output.
- **On D3D12, global `uniform` data plus `ConstantBuffer` params get CBVs one register high in slang-rhi's root signature** (`b0,b2,b3` vs HLSL `b0,b1,b2`), so dx12 pipeline creation fails while vk/cuda pass; split such render-test tests.

## Vulkan buffer and queue lifetime

**A null deref pinned at one site has a create-site twin (slang-rhi#860).** An external reporter correctly found that `DeviceImpl::createBufferFromNativeHandle` (`src/vulkan/vk-buffer.cpp:475`) imports a borrowed `VkBuffer` without calling `VKBufferHandleRAII::init()`, leaving `m_buffer.m_api` null, so `~BufferImpl()` crashes destroying cached `VkBufferView`s through it (`:169`), and proposed a destructor-only fix. But `BufferImpl::getView()` *creates* the view through the same `m_buffer.m_api->vkCreateBufferView(...)` (`:333`), so an imported buffer bound as a texel SRV/UAV crashes there before it can reach the destructor; the report's own precondition ("acquire a view") is unmeetable without fixing the create side. The fix routes both sites through `getDevice<DeviceImpl>()->m_api`, which is always valid (mirror the descriptor-handle loop at `:157-163`). Setting `m_api` on an import is not a fix, because it doubles as an ownership flag: the destructor (`vk-buffer.h:30-34`) frees buffer and memory iff `m_api != null`, so populating it double-frees the caller's buffer. The fault is Vulkan-specific; no other backend's `BufferImpl` frees a per-buffer view cache through a borrowed api pointer ([create site shares the deref](../learnings/1789372389751-slang-rhi-imported-buffer-null-m-api-the-create-si.md)). The bot's PR #868 did exactly that, kept `m_api` as the implicit ownership flag, and scoped out the uninitialized `m_memory`. Maintainer skallweitNV closed it and landed #945: the same device-API routing, but explicit `m_ownsBuffer`/`m_ownsMemory` bools (handles default to null, copy is disabled, ownership is set after each successful allocation), so an imported buffer owns neither, its `m_api` can be valid, and `m_memory` is fixed in the same change. When a minimal fix routes around a field that means two things, name the conflation and offer the explicit-ownership refactor in the explanation comment; a reviewer accepting the root issue as "pre-existing / out of scope" is not the maintainer agreeing ([explicit ownership over double duty](../learnings/1793091793971-slang-rhi-maintainer-prefers-explicit-ownership-ov.md)).

**The Vulkan `VkQueue` is shared de-facto and guarded nowhere (slang-rhi#863).** `DeviceNativeHandles` has only instance/physicalDevice/device slots (`include/slang-rhi.h:3431-3433`), and even for an imported `VkDevice` the queue comes from `vkGetDeviceQueue(m_device, m_queueFamilyIndex, 0, &queue)` (`src/vulkan/vk-device.cpp:1857-1858`), so two `DeviceImpl` wrapping one native `VkDevice` get the same `VkQueue`. Even within one device nothing locks it: `CommandQueueImpl::submit` (`vk-command.cpp:2131`), `VulkanDeviceQueue::flushStepA` (`vk-device-queue.cpp:124`), `SurfaceImpl::present`/`destroySwapchain` and both `vkQueueWaitIdle` sites use it, while `CommandQueueImpl::m_mutex` and `m_deferredDeleteQueueMutex` guard only the command-buffer pool. d3d12 and cuda follow the same "pool mutex only, submit unlocked" pattern, and there is no cross-`DeviceImpl` sync or native-queue registry anywhere. A per-wrapper mutex therefore cannot serialize a shared native queue; that needs an app-supplied shared object (the only thing that also covers the app's own out-of-RHI raw calls) or a library-owned per-native-queue registry behind one choke-point wrapper ([one VkQueue, guarded nowhere](../learnings/1789373034879-slang-rhi-vulkan-shares-one-vkqueue-de-facto-and-g.md)).

## Guarding a public getter that the RHI also calls internally

Before adding a guard at a maintainer-named choke point, grep its internal callers; a guard that fires on legitimate internal use is a regression, not a safeguard. For slang-rhi#787 (forbid `getDeviceAddress`/bindless handles on `Shared` resources on Vulkan, so the queue-family reacquire stays complete), `IBuffer::getDeviceAddress()` is public but is also called ~20× during command recording (acceleration-structure/micromap build inputs and scratch, cluster ops, cooperative-vector src/dst). A guard returning 0 for a `Shared` buffer corrupts those tracked internal operations (codex flagged it HIGH), and because `BufferOffsetPair::getDeviceAddress()` computes `base + offset`, a 0 sentinel plus a nonzero offset fabricates a valid-looking address; preserve `base ? base + offset : 0`. Split a public guarded entry from an internal unchecked accessor (`getDeviceAddressUnchecked()` plus a `getBufferDeviceAddress(BufferOffsetPair)` helper) and reroute the internal recording sites to it, so the guard applies only to the app-facing call that forms an untracked GPU reference, while internal operands are retained in `m_trackedObjects` and reacquired normally. Reroute a site when its operand is app-provided (could be `Shared`), not when it is an RHI-owned internal buffer (SBT, AS/micromap backing) ([split public-guarded from internal-unchecked](../learnings/1790032907874-guarding-a-public-getter-that-rhi-calls-internally.md)).

## CUDA constant-buffer pool: interning by byte-content is lifetime-safe

Interning packed global-param packets by byte content — a `std::unordered_map<std::string_view, CUdeviceptr>` whose keys point into `objectData.host` (slang-rhi#861) — reads as a dangling-key hazard but is not one. `objectData.host` comes from `ConstantBufferPool::Pool::allocate` (`src/cuda/cuda-constant-buffer-pool.cpp:96`), a bump allocator whose pages are `HeapAlloc`s with an inline `address` (`include/slang-rhi.h:3135/3138`) pointing to memory allocated outside the `std::vector<Page>`; reallocation on `push_back` moves the Page structs, not the bytes, and the pool is append-only during a build. Ownership is co-terminous: `BindingCache` and `ConstantBufferPool` are both members of `CommandBufferImpl` (`cuda-command.h:116-117`), whose `reset()` clears the map (`:1465`) before freeing pool pages (`:1466`), and the map is read only via `try_emplace` during building. The paired execution-side copy-skip (`m_globalParamsState` in `cmdDispatchCompute`) is correct because `CommandExecutor` is per-command-buffer, `computePipeline->m_globalParams` is a stable per-pipeline device symbol written only by the dispatch copy, the stream is single-threaded FIFO, and `cmdExecuteCallback` clears the cache. The halves are coupled: source-pointer identity proxies byte equality only because interning canonicalizes device addresses, so splitting them keeps correctness but loses the win. slang-rhi has no `reproduced`/`CUDA`/`perf` labels; `enhancement` fits such an optimization ([intern map is lifetime-safe](../learnings/1789372807192-slang-rhi-cuda-string-view-keyed-intern-map-into-c.md)).

## CUDA heap: a destroyed device leaks 256 MiB pinned pages before slang-rhi#923

Up to slang-rhi 57018e3 (slang-rhi#923, merged 2026-10-22), `HeapImpl::~HeapImpl` (`src/cuda/cuda-heap.cpp:306-310` at d825f483) frees only the page cache, and `Heap::~Heap` (`src/heap.cpp:18-24`) then deletes the resident pages without `cuMemFree`/`cuMemFreeHost`. CUDA devices share the primary context, so the memory returns only when the last device releases it, and the heap uses a 256 MiB page for any request up to 64 MiB (`heap.cpp:45-48`). In slangpy pytest the session-cached devices hold the context for the whole run, so every uncached device that did an upload or readback strands one 256 MiB pinned page. Repro on the L40S with the slangpy 0.43.1 wheel: keep one CUDA device open, then loop creating a second device, uploading one texture and closing it; VmRSS grows 256 MiB per cycle, and 0 with no upload or no other open device (`/workspace/agent/repro-13890/variants2.py`; shader-slang/slang#13891) ([CUDA heap leaks a pinned page per device](../learnings/1792770237658-slang-rhi-cuda-heap-leaks-256-mib-pinned-page-per-.md)).

Diagnosis notes: `/proc/self/smaps` attributes this RSS to no single mapping, so use VmRSS with `device.report_heaps()`. `Heap::allocate`'s OOM retry (`heap.cpp:77-82`) never runs on CUDA, because `SLANG_CUDA_RETURN_ON_FAIL_REPORT` returns `SLANG_FAIL` for every `CUresult` (`cuda-utils.h:83`), the -2147467259 seen in logs. A CI OOM at `cuda-heap.cpp:395` means a pre-#923 slang-rhi; after the fix the call is at `:406`. Give repro variant modes names that are not substrings of each other: "noupload" contains "upload" and broke the first control run.

## Staging-heap pooling for readback

Routing Vulkan `readBuffer` through the pooled `m_readbackHeap` `StagingHeap` (slang-rhi#862) rests on several non-obvious facts. **ReadBack pages are not `HOST_CACHED` on main before #929**: `StagingHeap::allocPage` calls `device->createBuffer` with `memoryType=ReadBack`, which requests only `HOST_VISIBLE | HOST_COHERENT` (`src/vulkan/vk-buffer.cpp:414-416`); the `HOST_CACHED` flags at `vk-heap.cpp:38-40` belong to the separate `IHeap`/`HeapImpl` path. A triage memo claimed "faster CPU reads" for readback staging and was wrong (codex OUTPUT_REVIEW caught it). `StagingHeap::map(alloc, &ptr)` returns `page->getMapped() + offset` (`staging-heap.cpp:181`), so `memcpy` directly; `getOffset()` is only the destination offset for `copyBuffer`. `StagingHeap::free()` keeps one empty standard page (16 MiB) and frees oversized pages at once, so after a readback `getUsed()==0` but `getNumPages()>=1`. A GPU test that proves pooling must therefore use a fresh device (`GPU_TEST_CASE(name, Vulkan | DontCacheDevice)`): `StagingHeap::initialize()` pre-allocates nothing, so `getNumPages()` going `0→1` after the first read is definitive (the transient path never touches the heap). Validate ranges overflow-safely: check `offset > desc.size`, then `size > desc.size - offset`, never the wrapping `offset + size` ([HOST_CACHED myth, fresh-device proof](../learnings/1789440138998-slang-rhi-vulkan-readbuffer-pooling-host-cached-my.md)).

**The cost of uncached readback on the L40S** (Linux driver, 2026-10-20): for a TRANSFER_DST buffer, Vulkan memory type 1 is DEVICE_LOCAL, type 2 is HOST_VISIBLE|HOST_COHERENT (uncached, about 0.15 GB/s CPU read), and type 3 adds HOST_CACHED (about 4.7 GB/s map+memcpy at 256 MiB). Main picks type 2 for ReadBack buffers, the `readBuffer` staging buffer and readback StagingHeap pages; PR #929 (7577eea, slang-rhi#928) picks type 3 for all three. So "ReadBack staging is not HOST_CACHED" describes main before #929, not a design invariant ([L40S Vulkan memory types](../learnings/1792502963862-slang-rhi-tests-tc-needs-a-device-suffix-wildcard.md)). When #869 (pooled `readBuffer`) conflicted with #929, which edited the transient staging buffer that #869 deletes, the resolution kept #869's body and dropped #929's hunk on the claim that the pooled path inherits #929's effect. The code supports it (`device.cpp:436` sets the ReadBack heap, `staging-heap.cpp:234-238` calls `createBuffer`, `vk-buffer.cpp` prefers HOST_CACHED), and a temporary `fprintf` in `allocateVkMemory` (reverted before the push) confirmed on the L40S that the readback page got type 3, flags `0xe`, and the upload page type 2. A resolution that drops a hunk because "the other path inherits it" rests on that inheritance, so check it at runtime, not only by reading ([verify claimed inheritance at runtime](../learnings/1793106992385-merging-a-pr-whose-code-path-an-upstream-pr-edited.md)).

**Free a pooled staging allocation on GPU completion, not at RAII scope exit.** A `RefPtr` freed at function exit can return a still-in-flight page when a later `waitOnHost` fails. Mirror `CommandEncoder::uploadBufferData`/`uploadTextureData` (`src/command-buffer.cpp:616,688`): after `copyBuffer`, call `checked_cast<CommandEncoder*>(commandEncoder.get())->m_commandList->retainResource(staging)`, then `submit`/`waitOnHost`/`map`. `retainResource(RefObject*)` (`src/command-list.h:473`) inserts a `RefPtr` into `m_trackedObjects` (`std::set<RefPtr<RefObject>>`, `command-buffer.h:422`), which `CommandBuffer::reset()` clears at retirement (`CommandList::reset()` does not), so a successful wait frees the page (`getUsed()==0`) while a failed one leaves it owned by the un-retired command buffer instead of back in the pool. Hold it as `RefPtr<StagingHeap::Handle>` from `allocHandle`, never bare alloc/free: freeing only on success leaks on any post-alloc `SLANG_RETURN_ON_FAIL` and trips `StagingHeap::release()`'s `m_totalUsed==0` teardown assert (`Device::readTexture` still has this latent leak). Flag one residual as a follow-up, not a blocker: `~DeviceImpl` (`vk-device.cpp:147`) ignores the result of `m_queue->waitOnHost()` before releasing both staging heaps, so a failed teardown wait leaves a retained handle unfreed; every retained-staging path shares it, and only a cross-backend teardown reorder fixes it. `checked_cast` validates only in debug (a plain `static_cast` in release), so do not call it type-safe ([retainResource ties lifetime to completion](../learnings/1789448569968-slang-rhi-fix-pattern-tie-pooled-staging-lifetime-.md)).

## Vulkan VUIDs in Slang examples are not CI-gated

A Slang examples fix for a Vulkan dynamic-rendering format-mismatch VUID (PR #13127, `colorTarget.format` vs attachment format) is not checked by any CI gate, so do not credit "the VUID is left to CI to catch". slang-rhi surface/swapchain/format tests skip on headless CI at the `hasMonitor()` guard (green CI only compiles the surface path), the examples' offline/test path runs with the Vulkan validation layer disabled (`enableValidation = !isTestMode()`), and examples are skipped on Vulkan platforms. Such a fix is verified by construction plus compile/link; say so in the verdict rather than repeating the PR body. For format bugs, follow the value to the actual `VkImageCreateInfo`/`VkSwapchainCreateInfoKHR`/`ColorTargetDesc.format` field rather than trusting a getter name ([validation is OFF in offline CI](../learnings/1789564810840-vulkan-vuid-in-slang-examples-left-to-ci-is-not-a-.md)).

## D3D11/D3D12 integer texture clears are no-ops on RenderTarget-only textures

In slang-rhi main f0c50c7 (and PR #899 head f76fb50), D3D11 and D3D12 `cmdClearTextureUint` (`d3d11-command.cpp:340`, `d3d12-command.cpp:505`) handle only `TextureUsage::UnorderedAccess`, and `clearTextureSint` routes through the same `commands::ClearTextureUint`. On a texture with RenderTarget usage and no UAV, integer clears do nothing and report nothing, while `cmdClearTextureFloat` has a RenderTarget branch. Vulkan (`vkCmdClearColorImage`), Metal (clear engine) and WGPU handle the case, so a new integer render-target clear test fails on D3D only, at the cleared subresource. The fix direction is an RT branch converting int to float for `ClearRenderTargetView`, exact only up to 2^24; Dawn uses a draw (`apply_clear_big_integer_color_value_with_draw`) for larger values ([D3D integer RT clears are no-ops](../learnings/1792518561170-slang-rhi-d3d11-d3d12-cleartextureuint-sint-are-no.md)). Two side facts from that atom live elsewhere: on slang-rhi CI a green `build (windows, aarch64, msvc, Debug)` says nothing about tests, because the matrix `unit-test` flag skips its `Unit Tests` step ([[wiki/concepts/slang-a-test-harness.md]]); and backtick-wrapped `### Attested` hashes break the critique gate ([[wiki/concepts/agent-routing-f0909b1-critique-gate-mechanics.md]]).

## CUDA pipeline creation: an entry point named `main` is renamed `main_0` (E40100)

Consider a slangpy compute kernel declared `[shader("compute")] void main()` and dispatched on CUDA. In slangpy#1189 CI (2026-09-29) it failed at pipeline creation with `cuModuleGetFunction … CUDA_ERROR_NOT_FOUND named symbol not found` (slang-rhi `src/cuda/cuda-pipeline.cpp:89`), and Slang's `warning[E40100]: entry point 'main' has been renamed to 'main_0'` matched the nine failures one for one. The working hypothesis, not yet verified with coverage off, is that the RHI looks up the original name while the CUDA module exports the renamed symbol, so grep a CUDA "named symbol not found" log for E40100 first. Existing slangpy tests with `void main` only load modules and never create a CUDA pipeline, so they miss this. Also: slang-rhi squash-merges (single-parent commits on main), so a slangpy submodule pinned to an open slang-rhi PR head must be re-pinned to the squash commit once it merges ([`main` → `main_0` breaks CUDA lookup](../learnings/1790685200036-cuda-entry-point-named-main-is-renamed-to-main-0-e.md)).

## Vulkan device creation on lavapipe: `VK_KHR_shader_non_semantic_info` is not optional

Coworker containers run `-vk` on the passed-through NVIDIA L40S with the NVIDIA Vulkan ICD; measure with `nvidia-smi -L` each session and report a failure to the operator as infra ([containers have an NVIDIA L40S](../learnings/1792133264162-coworker-containers-have-an-nvidia-l40s-gpu-cuda-vulkan.md)). This section applies only when lavapipe is the sole Vulkan ICD, as during the 2026-09-28→10-16 host passthrough outage ([passthrough restored 2026-10-16](../learnings/1792142517350-correction-gpu-passthrough-restored-2026-10-16-con.md)); never record that state as "no GPU". With lavapipe only, `slang-test ... -vk` reports `Check vk,vulkan: Not Supported` even though mesa lavapipe is installed (`/usr/share/vulkan/icd.d/lvp_icd.x86_64.json`). The cause is device creation, not slang-test: `external/slang-rhi/src/vulkan/vk-device.cpp` (~:595) pushes `VK_KHR_shader_non_semantic_info` unconditionally, lavapipe from Mesa 22.3.6 does not expose it, and `vkCreateDevice` fails (visible with `VK_LOADER_DEBUG=error,warn`). This names the "required extension" that older fleet observations on [[wiki/concepts/misc-f0909b7-ci-build-git-coworker-ops.md]] and [[wiki/concepts/slangpy-build-and-infra-operations.md]] reported only as a failed device create.

When a question needs observed Vulkan values rather than SPIR-V text, a local-only workaround works: guard that push with `extensionNames.count(...)`, rebuild only `render-test`, and run with `VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.x86_64.json`:

```bash
slang-test -bindir build/Release/bin render-test <file> -vk -compute -output-using-type -shaderobj -o out.txt
```

That produces real Vulkan readbacks, also with `-emit-spirv-via-glsl`. Revert the guard and rebuild afterwards; never commit it. Two neighbouring traps (slang#13446): `slangc -target host-callable -o x` fails with E00098 "cannot access as a blob", so use `-reflection-json` without `-o`; and for LLVM, render-test uses `host-callable` (plus `emit-cpu-via-llvm`), whose reflection differs from `shader-sharedlib` ([lavapipe needs non_semantic_info optional](../learnings/1792028852820-observed-vulkan-runs-on-lavapipe-in-agent-containe.md)).

## Vulkan push-constant ranges: slang-rhi's offsets disagree with Slang's layout (slangpy#1232)

Consider a SlangPy kernel with a global `[[vk::push_constant]]` block and an entry-point `uniform float k`, dispatched on Vulkan (verified on the L40S with Slang 2026.19 and slang-rhi e0eeb428). Slang lays out every push-constant block at SPIR-V Offset 0, global and entry-point alike, and reports each with `pushConstantBuffer` index 0 in its own scope (the program-wide counter that numbers them 0 and 1 is on [[wiki/concepts/slang-test-gpu-lanes-on-shared-l40s.md]]). slang-rhi's `addAllPushConstantRangesRec` (`vk-shader-object-layout.cpp:907-916`) instead gives the ranges consecutive offsets, so the entry-point data is pushed after the global block while the shader reads it at 0, even when the shader never reads the global block: in a raw kernel, `k` read back the bits written to `push`. If the entry point reads both blocks, Slang emits two PushConstant interfaces, violating `VUID-StandaloneSpirv-OpEntryPoint-06674`, and slangc still exits 0 unless `SLANG_RUN_SPIRV_VALIDATION=1` is set. DeepWiki claimed Slang merges the blocks; slangc output shows it does not.

`ParameterBlock<T>` plus a global push constant breaks a second way: the set holding only the push constant becomes an empty descriptor set at index 0 (slang#12349), which the open draft slang-rhi#810 fixes (verified). A plain global `uniform T x;`, which becomes a descriptor-bound UBO, works on both SlangPy paths and is the workaround. To read the real `maxPushConstantsSize` without `vulkaninfo`, call `vkGetPhysicalDeviceProperties` through ctypes: the limits struct starts at byte 296 and `maxPushConstantsSize` is at byte 328 (256 on the L40S) ([push-constant offsets disagree](../learnings/1792164718700-vulkan-global-vk-push-constant-entry-point-uniform.md)).

## D3D12 root signature: global uniforms plus `ConstantBuffer` params put CBVs one register high (slang#13824)

Consider a render-test compute shader with both a global `uniform` value and a `ConstantBuffer<T>` parameter, run on the dx12 lane. The HLSL uses `b0` for the implicit global constant buffer and `b1`, `b2` for the `ConstantBuffer` params, but slang-rhi builds a root signature with `b0,b2,b3`. `RootSignatureDescBuilder::addAsConstantBuffer` (`external/slang-rhi/src/d3d12/d3d12-shader-object-layout.cpp:644-667`, slang-rhi b856e635) adds the ordinary-data CBV and increments the CBV offset (`offsetForRangeType++`) before recursing, but for the global scope the sub-object offsets that reflection reports already count the implicit `b0`. `CreateComputePipelineState` then fails with "Shader CBV descriptor range (BaseShaderRegister=1, …) is not fully bound in root signature"; vk and cuda pass. The render-test workaround is not to mix global uniforms with `ConstantBuffer` params in one dx12 test, and to split it (PR #13829). The Linux container has no dx12, but a small C++ probe replaying the builder's register math over real Slang reflection (`IComponentType::getLayout`, `getSubObjectRangeOffset`, `getContainerVarLayout`/`getElementVarLayout`, `getDescriptorSetDescriptorRangeIndexOffset`) predicts the mismatch; for a `globalExistentialType __Dynamic`, specialize with `findTypeByName("__Dynamic")` first.
