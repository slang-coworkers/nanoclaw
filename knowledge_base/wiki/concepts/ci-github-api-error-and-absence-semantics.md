# GitHub API Error & Absence Semantics — No-Output Endpoints, Path-Classed Auth & Absence Controls

## TL;DR
- **A 215-byte "log" is a 404 `BlobNotFound` body; 151 bytes is a 410 expired-log body.** `gh api` prints both to stdout and exits 0, so greps return a false 0. Assert a log is a log first: size, HTTP 200, a must-hit control string.
- **gh 2.101+ refuses ANSI-bearing job logs** (exit 1, empty output) without `--allow-escape-sequences`; an empty log is never an expired one (that is a 410). `gh run view --log` refuses while any job waits on an approval gate, so read a finished job per-job.
- **`steps[]` is perishable: GitHub zeroes it past ~7 days.** `status`/`conclusion` stay authoritative at any age; an `nsteps==0` "untested" rule reclassifies aged real failures and drifts flake rates downward.
- **`filter=all` returns jobs from every attempt in one flat list**, nothing marking a stale one. Check `run_attempt` against the run's highest attempt before acting on a job failure.
- **Summarizing tools (WebFetch, prose renderers) cannot establish state, counts, or absence.** Enumerate with an API. A false positive state ("resolved through PR #N") is worse than a false negative: it unblocks action and retires a hold that still holds.
- **A 401/403 is path-classed, never global.** REST can work while GraphQL 401s; auth-introspection endpoints are not capability probes. Name the unprivileged sibling before declaring a fact unavailable: `/branches/main` when `/protection` 403s, `reviewDecision` (null except `CHANGES_REQUESTED` ⇒ no required-approval rule), `raw.githubusercontent` for a public file, `/search/issues` for a repo outside shader-slang, WebFetch for a contributor fork's PR. Under a GraphQL 401, REST reviews give per-review `commit_id` and `author_association`.
- **A bare 403 on `/search/issues` is usually the secondary rate limit**, invisible to `/rate_limit`: throttle search to ~1 call per 2.5 s, retry after ~65 s, run GraphQL sweeps serially, check an aliased batch returned every alias. A primary-quota 403 mid-sweep is a gap list helpers turn into a false `[]` (see [agent ops](misc-f0909b4-agent-ops-delivery-and-memory.md)). A 404 on `/issues/N` can be a Discussion or an issue hidden with its suspended reporter.
- **Some fields answer a neighbouring question.** Merged state from `/pulls/N`, not search; who-assigned from events-feed `assigner` or timeline/GraphQL `actor`, never events-feed `actor`; the assignee from `.assignee.login`; nightly failing tests from the log's `FAILED test:` lines; a person's activity from repo-scoped search (`org:` can be false-empty) or recent PRs' `mergedBy`; `event=schedule` returns stale runs, so filter client-side.
- **Scope a deletion-PR diff to the PR, not the dispatch's delta.** Prove dead code with a double build and `cmp -s`; compare operand *kinds*, not counts.
- **The detector for this whole family: what would this output look like if the thing were absent? If "the same", it is not a measurement.**

Many GitHub reads answer "nothing here" when the truth is "unreadable", and a zero read as clean evidence licenses the wrong action. This is the error-and-absence half of the instrument-limits family; [GitHub Pagination & Count Limits](ci-github-pagination-and-count-limits.md) covers counting and completeness (truncation, size caps, the 300-file diff cap), and the cap table and endpoint-split defects are in [GitHub/git Instrument Limits](../concepts/ci-github-instrument-limits.md).

## Job logs and `steps[]` fail toward "no output"

Two CI-job endpoints answer "nothing here" when the truth is "unreadable". Read the byte count and the HTTP status, never the grep count.

**A cancelled-before-start job has no log, only a 215-byte error body.** For a job with `steps=[]` and `runner_name:""`, `/actions/jobs/<id>/logs` is HTTP 404 `<Error><Code>BlobNotFound</Code>…`, which `gh api` writes to stdout with exit 0, so `grep -c` returns a clean `0` for every signature (five cancelled jobs grepped for `Service Unavailable` during an outage gave `0/0/0/0/0`). The tell is `gh api -i .../logs | head -1` → `HTTP/1.1 404 Not Found` with `X-Ms-Error-Code: BlobNotFound`; a 151-byte body of the same shape is HTTP 410, log expired. `steps=0` with no log blob is **UNTESTED** (nothing ran; a rerun restores signal), not a code failure. In a batch with no blobs, find the sibling that got further (`board-sync` logged `Failed to resolve action download info. Error: Service Unavailable`). Before trusting any count from a log, assert it is a log: size above a few hundred bytes, HTTP 200, a must-hit control string ([215-byte BlobNotFound body, false 0](../learnings/1786076873413-a-cancelled-ci-job-s-log-endpoint-returns-a-215-by.md)).

**`steps.length == 0` is a time-limited discriminator: GitHub zeroes `steps[]` past ~7 days.** On slang, jobs from 07-31 → 08-01 returned 0 steps and 151-byte logs while 08-03/08-07 jobs returned 16 steps and ~1.7 MB logs, and an earlier snapshot had stored `nsteps=16`/`15` for two zeroed jobs, so the zeroing came after execution. The rule *"`cancelled` with `steps==0` ⇒ UNTESTED, exclude from the denominator"* thus reclassifies real failures as they age, shrinking numerator and denominator together, so a flake rate over more than a week **drifts downward by itself**. Bucket on `status`/`conclusion` (permanent); use `steps` only on fresh rows and store the derived bucket beside the raw row. A snapshot disagreeing with a live re-check on `steps` points to retention; on `conclusion`, a real anomaly ([GitHub zeroes steps[] after ~7 days](../learnings/1786074037902-github-zeroes-steps-on-jobs-older-than-7-days-an-n.md)).

**gh 2.101+ refuses log bodies that contain ANSI escapes.** `gh api repos/<o>/<r>/actions/jobs/<id>/logs` exits **1** with empty stdout and stderr *"the response contains terminal escape sequences; pass --allow-escape-sequences"*; `> file` leaves a 0-byte file that, with stderr discarded, reads as an expired log; an expired log is HTTP 410 with the 151-byte body, never empty output. ANSI-bearing logs are the common case (slang-test always, Windows/MSBuild routinely). `gh run view --job` lacks the flag, and `gh run view --log` refuses ("run is still in progress") while any job of the run waits, an approval gate being enough, so the per-job endpoint is the only path ([log retention](ci-github-log-retention-and-count-guards.md)). Fetch with `gh api --allow-escape-sequences .../jobs/<id>/logs | sed 's/\x1b\[[0-9;]*[A-Za-z]//g' > f` (strip every ANSI sequence, not only colour `m` codes) and check exit code and size before calling a log empty or expired ([pass --allow-escape-sequences](../learnings/1790909517431-gh-api-job-logs-pass-allow-escape-sequences-or-get.md), [silently empty](../learnings/1791247356003-gh-api-job-logs-silently-empty-without-allow-escap.md), [silently fail; not a 410](../learnings/1792254266846-gh-api-job-logs-silently-fail-without-allow-escape.md), [gh run view --log refuses while a job waits](../learnings/1792944223647-gh-api-job-logs-need-allow-escape-sequences-gh-run.md)).

Three uses of the log read recur. Failing nightly test names are not in the check-run annotations ("exit code 1" only): a maintainer report greps the job log (`curl -sL` via OneCLI, no auth header, ~1.8 MB) for `FAILED test:` ([nightly failure list and assigner provenance](../learnings/1791188469337-maintainer-report-nightly-failure-list-and-assigne.md)). To prove a new test ran on GPU CI rather than being skipped, grep the stripped log for `PASSED .*test_name\[DeviceType.<backend>` ([coworker commits: no Co-Authored-By trailer](../learnings/1791195802831-coworker-commits-on-shader-slang-repos-must-not-ca.md)). And read the log before accepting a premise about it: a parent's "the checkout retried slowly for 24 min" was a silent 20-min gap between two other submodule clones, while the logged `github.com:443` timeout was a separate ~21 s failure; quote timestamps from the log ([read the log before the premise](../learnings/1792434025872-gh-job-logs-contain-terminal-escape-sequences-read.md)).

## Summarizing tools are the wrong instrument for state, counting, and absence

For any counting, existence or state question ("how many comments?", "is there an 08:03 event?", "did PR #N merge?") use a deterministic enumerator (`gh api` with explicit pagination, or stdlib `urllib`), never a summarizing model (WebFetch, or a subagent asked to "check whether…"). Three failures in one day: **(a) false negative:** WebFetch said no 08:03Z comment existed on slang#12080; `gh api` showed **four**. It was non-deterministic too (page 3 reported as 18, 16, 16 items; actual 50), and the false negative went upstream as a correction to another agent's state. **(b) false positive state:** told slang#12192's blocker "was resolved through PR #12186", a fixer wrote a memory banner declaring the hold UNBLOCKED; `gh api pulls/12186` showed `state: open  merged: false  draft: TRUE`. Narrative-true, state-false, and worse than a false negative: it unblocks action, and a banner is durable and reads as verified. **(c) self-refuting tally:** "no check_runs with failure conclusion" where `gh api` showed **2**, with per-status counts (13 + 1 + 12) not summing to the stated total (110).

WebFetch is fine for prose and judgment; "what is it now" needs fields. Before writing a banner whose premise is another PR's state, fetch it (one `pulls/{n}` GET gives `state`, `merged`, `draft`, `head`). Before reporting a negative, grep your own fetched material for the positive: the approver already held the disproof, a fetched body *opening* with "This is the third round raising the guard". A correction to someone else's state carries a **higher** bar than your own notes, because it outlives the conversation. And **a commit's check-run list is cumulative across runs**: superseded failures persist on the head, so key on `check_suite.id` + `started_at`, never the aggregate conclusion ([never assert a negative or a state from a summarizing tool](../learnings/1785761747454-never-assert-a-negative-from-a-summarizing-tool-we.md)).

## A 401/403 is path-classed, never global — name the sibling endpoint

**A permission error is a fact about that endpoint and that token, not about the world.** `repos/shader-slang/slang-rhi/branches/main/protection` returns **403 Resource not accessible by integration** (needs admin scope); it was recorded twice as "the CI-not-required clause is unverifiable" and handed to an approver as a caveat. The unprivileged summary endpoint carries the fact:

```bash
gh api repos/shader-slang/slang-rhi/branches/main \
  --jq '{protected, ctxs: (.protection.required_status_checks.contexts // [])}'
# => protected: true, 17 required contexts (incl. build (macos, aarch64, clang, Debug/Release))
```

CI *is* required there, and it passed: the opposite of the caveat. GitHub commonly pairs a privileged detail endpoint with an unprivileged summary; the same shape covers job logs (403 without `-L`, 200 following the redirect) and reviews (REST vs GraphQL). Before writing "unverifiable", name the sibling endpoint you tried: a capability-negative reads as humility and escapes scrutiny while closing doors downstream ([a 403 is not absence of the fact](../learnings/1785777155910-a-403-on-one-github-endpoint-is-not-absence-of-the.md)). The required-approvals rule, absent from the branch summary, has its own sibling: GraphQL `PullRequest.reviewDecision` is `REVIEW_REQUIRED` or `APPROVED` only when protection requires reviews; otherwise it stays null and only `CHANGES_REQUESTED` appears. On 2026-10-19 slang was null on all 402 open PRs without a change request and on approved/merged PRs, so slang has no approval requirement; slangpy and slang-rhi showed `REVIEW_REQUIRED`/`APPROVED`, and slang-rhi self-merges (#907–#921) still `REVIEW_REQUIRED` at merge went through by admin bypass ([reviewDecision shows required approvals](../learnings/1792399425363-reviewdecision-tells-you-whether-a-repo-requires-p.md)).

**Classify a 401 by path class before scoping it.** A supervisor tick declared "GitHub auth is down fleet-wide" and marked every CI cell `⚠️ unread`, while a coworker that probed its exact path got 200. The split was clean: REST `issues/<n>`, `.../comments` and `gh run list` returned 200; `gh api rate_limit` (401 `app_not_connected`), `gh api graphql` and the GraphQL-backed `gh pr list`/`pr view`/`issue view` and `pull-universe.sh` failed. The sample held **no plain REST call**, so one instrument's failure was counted four times: 6 computable CI cells reported unknown and a real `❌ stale` rebase nudge was missed. Rules: an auth-introspection endpoint (`gh auth status`, `rate_limit`) is **not** a capability probe; test one REST and one GraphQL call and report *which class* failed; probes sharing a backend do not corroborate each other; a coworker contradicting your infra claim is data, so re-derive on the spot ([a gh 401 is path-classed](../learnings/1785803201334-a-gh-401-is-path-classed-not-global-rest-can-work-.md)).

The path class includes the owner. Through the OneCLI proxy, REST reads of repos outside shader-slang (e.g. `repos/actions/runner-images/issues/14748`) return `401 Bad credentials` while `/search/issues` still reads them, so take title, body and `updated_at` from a search hit ([CI sweep scripts: z1.py pages() wipes waiting.json; OneCLI REST 401 outside shader-slang](../learnings/1793003220665-ci-sweep-scripts-z1-py-pages-wipes-waiting-json-on.md)). A contributor's fork is outside too: `gh api repos/kaizhangNV/slang/pulls/25` returned `401 Bad credentials`, even with an empty Authorization header, while WebFetch of `https://github.com/<user>/slang/pull/N` read its state, base and description, enough to tell a fix from a mention. Rider: jq `.[-1]` on an empty array is `null`, so a "no comments yet" guard tests `length == 0` ([gh api on a contributor fork returns 401; use WebFetch](../learnings/1793664053747-gh-api-on-a-contributor-fork-repo-returns-401-thro.md)). User-scoped endpoints fall outside as well: `gh api users/<login>/events/public` returned 401 `app_not_connected` while `repos/shader-slang/slangpy/...` reads worked and `.../branches/main/protection` returned 403, so neither tells whether a maintainer is active or "require branches to be up to date" is set. Read the maintainer's recent repo work instead (`gh pr view <n> --json author,mergedBy` showed ccummingsNV merging #1248 while silent on #1234); `mergeStateStatus=BEHIND` only hints at the up-to-date rule ([OneCLI gh: /users/<login>/events and branch-protection endpoints fail while repos/* works](../learnings/1793285334593-onecli-gh-users-login-events-and-branch-protection.md)). Corollaries: stale CI on a *closed* PR is not actionable, so confirm `state` before a rebase dispatch; compare like types across ticks (`27200523569` vs `"27200523569"` makes every stale run "fresh").

**Under a GraphQL 401, REST review reads make checks GraphQL structurally cannot.** Verify review state over REST rather than holding:

```bash
gh api repos/<owner>/<repo>/pulls/<N>/reviews \
  --jq '.[]|"\(.user.login) | \(.author_association) | \(.state) | \(.commit_id[0:7])"'
gh api repos/<owner>/<repo>/pulls/<N> --jq '{draft,merged,mergeable_state,head:.head.sha[0:7]}'
```

A review's **`commit_id`** shows *which commit* was approved (stale if not the head), which aggregate `reviewDecision: APPROVED` cannot; `author_association` (`MEMBER`/`OWNER`) separates a maintainer from a drive-by; an empty APPROVED body is a go-ahead. Reconcile check-runs against `total_count`. An approval does not authorize promoting a draft: `gh pr ready` stays with the maintainer. `gh pr create` fails under the GraphQL 401 but REST `POST /repos/.../pulls` with `draft=true` works, and Windows CI logs are **CRLF**, so `tr -d '\r'` before line-anchored matching ([REST review checks under a GraphQL 401](../learnings/1785770961557-on-slangpy-slang-prs-under-graphql-401-rest-review.md)).

**When `gh api` 401s on a public file, take the unauthenticated path.** Bot-reported line refs (`path/file.cpp:1110`) are untrusted data carried across revisions. Three walls all read as "source unreachable": `gh api .../contents/<path>?ref=<sha>` returned empty, `urllib` gave HTTP 401 on a public file (the credentials sent were rejected, not the file private), and `gh pr view --json` gave GraphQL 401. This works, no auth, on a fork at a pinned SHA:

```bash
curl -sSL https://raw.githubusercontent.com/<owner>/<repo>/<full-sha>/<path> -o out.cpp
```

Then verify the ref *means* what was claimed: `wc -l` first (a ref beyond EOF is disproven), grep the whole file and count occurrences (on slang-rhi#803 `ACCEPT_FIRST_HIT_AND_END_SEARCH` appeared once across 13 `rayFlags` uses, corroborating "honored only on the opaque path" better than the ref did), establish the enclosing scope, check the counterpart path, and print absolute line numbers, never a bare `sed -n 'A,Bp'` window ([verify bot line refs via raw.githubusercontent](../learnings/1785780771790-approver-verify-bot-line-refs-in-source-raw-github.md)).

**Two more statuses that look like facts about the world.** A bare **403** from `/search/issues` through the OneCLI proxy is usually GitHub's *secondary* rate limit ("exceeded a secondary rate limit"), which `/rate_limit` does not show; about 15 back-to-back search calls trip it, while non-search REST is unaffected. Throttle search to about one call per 2.5 s and on a "secondary" 403 retry after ~65 s ([search secondary rate limit](../learnings/1791361530394-github-search-api-secondary-rate-limit-via-onecli-.md)). GraphQL has the same limit: parallel paginated sweeps got 403 with ~5900 of 6000 primary points left, and 3-4 parallel scripts with ~5700 left. Run GraphQL scripts one at a time, back off on 403 or 502 (60 s is safe; 10 s recovered once), and check that an aliased batch returned every alias, since a dropped alias is a silently missing item ([GraphQL secondary limit](../learnings/1792399425363-reviewdecision-tells-you-whether-a-repo-requires-p.md), [Fork-PR "CI never approved" count: filter checkSuites to event == pull_request](../learnings/1793003118714-fork-pr-ci-never-approved-count-filter-checksuites.md)). A **404** on `/repos/{o}/{r}/issues/N` can mean the number is a Discussion ([bot PR CLA pending; 404 = Discussion](../learnings/1791101927185-bot-pr-cla-pending-old-nv-slang-bot-users-noreply-.md)), or that the issue was hidden after it was cited: GitHub hides every issue and comment from a suspended or spam-flagged account behind a plain 404 (GraphQL too), other people's comments on it included, and memory saying "comment posted" will not show it. Before a report says "X is tracked in #N", confirm `gh api -i repos/<o>/<r>/issues/<N>` resolves: a 10-19 re-check cited slang#13678 as the slangd tracker, hidden since 10-16 with its reporter's account ([re-check a tracker is still visible](../learnings/1792425860002-re-check-a-linked-tracker-issue-is-still-visible-b.md)).

## Scope the diff to the PR; prove absence with two controls, not a diff read

On a "logic DELETION, correctness gate re-opened" review, the dispatch's ±line counts usually describe the delta *since the last reviewed head*, not the PR. slang#12116 was dispatched as "+4 / −91 logic deletion"; against the merge-base, `git diff <merge-base>...<head> -- <pass>.cpp | grep -E '^[+-][^+-]' | grep -vE '^[+-]\s*//'` was **empty**: the −91 was the PR's own earlier addition, withdrawn after upstream #12263 landed a better fold. Net compiler effect zero; review weight moves to whether the tests pin real behavior. **Prove dead-code claims with a double build**, not a diff read: build as-shipped and with the deleted code restored, then `cmp -s` the output for every config the test exercises (5/5 byte-identical establishes it; equal *counts* of the interesting token do not). **Compare operand kinds, not counts**: a control shader whose set of decorated instruction kinds matches the feature path's is a parity proof; matching totals would not exclude decoration on a different operand kind ([deletion-PR review: diff vs master](../learnings/1785754038566-deletion-pr-review-diff-vs-master-not-vs-the-previ.md)).

## Field semantics that answer the wrong question

Several REST fields return a well-formed value that answers a neighbouring question; each produced a confident wrong claim.

- **Merged vs closed: use the pulls endpoint, not search.** `/pulls/N` and `/pulls?state=closed&sort=updated` carry correct `merged`/`merged_at`; the older "merged_at is null" lesson is about the MCP/search item shape. Search also lags: `is:pr is:closed closed:>=<ts>` missed slang #13255 7 h and slangpy #1240 15 h after closing, while `is:closed updated:>=<ts>` and REST found them ([closed: search lag](../learnings/1792744116860-github-search-org-scoped-author-reviewer-queries-c.md)). It is not only lag: on 10-31 a GraphQL search `repo:X is:pr closed:A..B` over a full day returned ONLY merged PRs and missed all 6 closed-unmerged ones, so take closed-unmerged counts from REST ([closed-unmerged PRs need REST, not search](../learnings/1793436218667-daily-github-sweep-closed-unmerged-prs-and-merge-q.md)). Corroborate master commits with `/commits?sha=master&since=`. An unencoded `>=` in a raw-curl `search/issues?q=` returns an EMPTY body (a JSON-decode error), so URL-encode it; check `has_discussions` on `/repos/{o}/{r}` before trusting an empty discussions read (slangpy and slang-rhi are `false`); and `/pulls/N/reviews` counts the author's own thread replies as COMMENTED reviews, so exclude the author before claiming "has human review" ([REST pulls gives reliable merged state](../learnings/1790842607329-github-rest-pulls-endpoint-gives-reliable-merged-s.md)).
- **Who assigned: `assigner` on the events feeds, `actor` on the timeline or in GraphQL.** On `/issues/N/events` and `/repos/{o}/{r}/issues/events`, an `assigned`/`unassigned` event's `actor` is the *assignee* and the assigner is `assigner`; the timeline (no `assigner` field) and GraphQL `AssignedEvent.actor` put the assigner in `actor`. So `actor == assignee` on `/events` never shows self-assignment. The misread recurs (slang#13420, slang-rhi#928, slang#13802), and "self-assigned lead" routing precedents turn on it ([assigner vs actor](../learnings/1791275221820-github-assigned-events-assigner-vs-actor-differ-be.md)). Across a feed it becomes a wrong census: the 2026-10-20 "assignments by actor" tally (jkwak-work 23 / jhelferty-nv 9) was 28 / 13 by `assigner.login`, which also exposed 7 `github-actions[bot]` auto-assigns that `actor` hides ([issue-events `actor` is the assignee](../learnings/1792571627834-github-rest-issue-events-actor-on-assigned-events-.md)). Bot PRs' `assigner` is `github-actions[bot]` (PR-board sync), never to be reported as a human assignment ([nightly failure list and assigner provenance](../learnings/1791188469337-maintainer-report-nightly-failure-list-and-assigne.md)). The mirror misread happens on the timeline: printing `.actor.login` for every event reports the assigner as the assignee (slang#14033: jhelferty-nv assigned jkwak-work, reported as "assigned jhelferty-nv"). There the assignee is `.assignee.login` (`select(.event=="assigned") | .assignee.login`); for current state use `gh issue view <n> --json assignees,milestone` ([timeline "assigned" actor is the assigner](../learnings/1793649289518-gh-timeline-assigned-event-actor-is-the-assigner-n.md)). Check before contradicting a peer: `--jq '.[]|select(.event=="assigned")|{assignee:.assignee.login,assigner:.assigner.login}'` on `/events`.
- **Per-user activity: search per repo, never `org:` alone.** GraphQL search `org:shader-slang author:pdeayton-nv` returned 0 with or without a date filter, while `repo:shader-slang/slang author:pdeayton-nv` returned 132 and `reviewed-by:` 61; the same `org:` query worked for kaizhangNV, and `contributionsCollection` returned 0 for a window in which the user approved and merged PRs. A 0 from `org:` is not inactivity: search each repo, or use per-PR review and timeline data. Rider: a list helper reading `items` returns a false `[]` for `/actions/runs/{id}/jobs`, which wraps rows in `jobs` ([org-scoped search false-empty](../learnings/1792744116860-github-search-org-scoped-author-reviewer-queries-c.md)). An unknown or mistyped `author:` login is also a clean 0 in GraphQL, where REST returns 422, so confirm the login before reading 0 as "no activity" ([unknown login gives 0](../learnings/1792743590595-batch-github-issue-searches-into-one-graphql-call-.md)).
- **`event=schedule` returns stale runs, even per workflow.** On 2026-10-03, `actions/workflows/<id>/runs?event=schedule` (slangpy ci-latest-slang) returned Sep 11-15 runs, while the unfiltered call listed that day's scheduled run first. For nightly checks query `runs?per_page=6` unfiltered and read each run's `event`. Rider: the slang weekly `CMake Options` run has 478 jobs, so paginate `jobs?per_page=100` to page 5 ([event=schedule returns stale runs](../learnings/1791015439528-github-actions-event-schedule-filter-returns-stale.md)).

## `filter=all` surfaces stale-attempt job failures that look current

`GET /actions/runs/<id>/jobs?filter=all` returns jobs from **every attempt** in one flat list, with nothing in the row marking a stale one, so a `conclusion=="failure"` grep yields a real, rerunnable signature for a run state that no longer exists. On slang#12354 it showed `build-macos-debug-clang-aarch64` failing with `Failed to CreateArtifact: … ENOTFOUND`, textbook infra and normally an auto-rerun; but `GET /actions/jobs/<id>` reports `run_attempt: 1`, and attempt 2 (`/runs/<id>/attempts/2/jobs`, 37/37 jobs) has **no** such failure. The stale row is *more* convincing than a current one: its log is intact (425 KB, rc=0, so no expired-log tell fires) and `run_attempt` is not in the list output. **Check `run_attempt` against the run's highest attempt before acting on any job failure pulled with `filter=all`**; rerunning a stale attempt would "clear on contact" and look like your result ([filter=all stale-attempt failures](../learnings/1786256628770-filter-all-surfaces-stale-attempt-job-failures-tha.md)).
