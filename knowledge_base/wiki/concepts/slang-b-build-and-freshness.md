## TL;DR

- **`slangc -v` is NOT a freshness instrument** — `SLANG_VERSION_FULL` is a CACHE variable baked at *configure* time (`cmake/GitVersion.cmake`), so a fresh build can report a commit tens behind HEAD; and after `git pull`, source mtimes are rewritten for files whose content never changed. Establish freshness by object mtimes vs the HEAD commit date scoped to your files, or (better) a behavioural discriminator with a guilty control.
- **A `slangc` under a PR worktree's `build/` may be a fetched RELEASE TARBALL, not a build of that PR.** A binary's location inside a source tree says nothing about which revision produced it. Prefer the exact path your build wrote (`build/<Config>/bin/slangc`), never a `find`/glob hit.
- **The core-module generated header is SHARED across configs**, not per-config — two concurrent builds off the same edited `*.meta.slang` contaminate each other. Serialize them. After editing a meta file, `cmake -E touch` it or the cached bootstrap silently embeds the OLD source.
- **Concurrent ninja on one build dir is a recurring race** presenting as ranlib "No such file" *or* false `undefined reference` errors naming your own symbols. Read `.ninja_log` for a later successful link; `REBUILD_EXIT=1` does not mean the tree is fine.
- **A delegated build (`Agent` subagent) dies silently when reaped** — ninja takes SIGINT, writes no exit code, and a failure-signature monitor stays silent. Background the build in your own session with a marker file; a monitor must watch three outcomes: done, broken, and *process-gone-with-no-exit-file*.
- Native backtrace without gdb: `backtrace_symbols_fd` + the shipped `.dwarf` sidecar; match the sidecar to the *loaded* library version.

## `slangc -v` and mtime are both false freshness instruments

`SLANG_VERSION_FULL` is a **CACHE** variable in `cmake/GitVersion.cmake:113`, so `git describe` runs on *first configure only* and never refreshes on reconfigure or rebuild. A freshly-built binary printed `2026.13.1-61-ga916653b70` when its source was actually `v2026.14.1-42-g9eb90c50a0`. (In another build, `slangc -v` prints a bare integer that decodes to the *build timestamp*, not a git hash — either way it cannot pin a binary to a commit.) **Never use `slangc -v` to confirm which commit you are testing.** Use instead:

- **Binary and shared-library mtimes** — check `build/Debug/lib/libslang-compiler.so.*` (the 61 MB library holds the compiler code), not just the ~339 KB `slangc`.
- A **behavioural discriminator** — pick a commit in your range that changed observable behaviour and run its repro, with a guilty control. E.g. `-std 202c` (added by #12179) accepted by the current build, rejected `E15207` by an older one, while guilty control `-std 9999` errored on both. This is strictly better than any version string.

Also: after `git pull`, source **mtimes** are rewritten, so "source newer than binary" is true for files whose content never changed. The valid instrument is `git log <base>..HEAD -- <paths>` (empty ⇒ no drift *for claims about those files*; pair with a tree-wide `git log --since` as a non-zero control, or an empty result is indistinguishable from a broken invocation). And a **freshness control is scoped to the tree that ran it** — a peer's "0 commits touched these files between build time and HEAD" was true for their snapshot and did not transfer to a clone where the binary was 10 days and 8 commits old. Re-derive freshness in your own tree. [slangc -v lies about freshness (CACHE var), and IRPtrType's address space defaults to Generic when the operand is absent](wiki/learnings/1786001761726-slangc-v-lies-about-freshness-cache-var-and-irptrt.md) [Exit 255 is slangc's generic failure code — it cannot discriminate an ICE from a clean diagnostic](wiki/learnings/1786200321229-exit-255-is-slangc-s-generic-failure-code-it-canno.md)

### A worktree's `build/` legitimately contains fetched binaries

A reviewer ran `.../wt-12155/build/slang-2026.14.1-linux-x86_64/bin/slangc`, saw the bug still crash "despite the guard," and concluded the binary didn't represent the PR head. It didn't — but because it was a **prebuilt release tarball the build system fetches as a dependency** (`slangc -v` → `2026.14.1`, mtime pre-dating the PR). Its crash carried zero information. The real artifact would be at `build/Release/bin/slangc`. **A binary's location inside a source tree says nothing about which revision produced it** — prefer the exact path your build wrote, never a glob hit (a worktree's `build/` contains third-party and fetched-dependency binaries with the same basename). Confirm with `stat -c '%y'` against your build start, plus a behavioural discriminator. A probe where the *control also fails* (`-o /dev/null` → `E00070`; a guessed flag name errors before the parser) measured nothing. [A slangc under a PR worktree's build/ dir may be a fetched RELEASE TARBALL, not a build of that PR](wiki/learnings/1786039375947-a-slangc-under-a-pr-worktree-s-build-dir-may-be-a-.md)

## Core-module edits: shared header, stale-binary silence, mandatory touch

Within one multi-config build tree there is exactly ONE `build/source/slang-core-module/core-module-meta/hlsl.meta.slang.h` — **shared across Debug/Release**, not per-config. So two concurrent builds off the same edited source contaminate each other's embedded core module (a Release restore and a Debug guilty-control build minutes apart nearly poisoned each other). **Serialize any two builds that touch a `*.meta.slang`.**

The load-bearing hazard: **mtime lies about a stale binary.** `slangc`'s mtime tells you when the binary was linked, nothing about which core-module source is embedded in it — a one-minute-old `slangc` was still emitting the *patched* core module from a previous session. Check it **behaviourally** by compiling something whose output differs between states (`grep -c 'for(;;)' probe.cu` → 1 pristine / 0 patched; emitted `#line` directives shift on a one-line upstream insertion and are a second independent tell). To scope a *partially* stale binary, `git log --oneline --since='<build time>' -- <meta files>` (empty ⇒ still valid for claims about those files; pair with a tree-wide control).

Rebuild recipe (the `cmake -E touch` is **not** optional — without it the cached bootstrap silently embeds the OLD source):

```bash
cmake -E touch source/slang/hlsl.meta.slang
cmake --build --preset <preset> --target generate_core_module_headers
cmake --build --preset <preset> --target slangc
```

A link failure right after this (`undefined reference to ...`) can be a stale-link race, not a real break: check whether the defining object is newer than the link step and re-run once. [Slang core-module generated header is shared across configs — a stale slangc lies silently, and mtime will not tell you](wiki/learnings/1786040498662-slang-core-module-generated-header-is-shared-acros.md)

## Concurrent ninja on one build dir: a recurring, shape-shifting race

The symptom changes; the class doesn't. Instances observed: `FAILED: libSPIRV-Tools-opt.a` + `ranlib: 'No such file'` (2026-07); `FAILED: libslang-compiler.so` + **7 `undefined reference`** serialization symbols (2026-08); a third occurrence *during recovery* on `libslang-without-embedded-core-module.so`. A shared-build-dir race can present as a **link error naming your own symbols** — the most misleading face, reading as "your patch broke the build." All seven undefined references were false: the object existed, was fresh, defined the symbol (`nm -C --defined-only`), and was on the failing link line; `.ninja_log` showed the library linking successfully seconds *after* the reported failure.

Recognizer, cheapest first:
1. **Read `build/.ninja_log`** for a successful link of the same target at/after your failure timestamp — the discriminator.
2. Confirm the artifact (grep the `.so` for a string unique to your change, with a known-present string as control), not the exit code.
3. `pgrep -af ninja` before concluding anything.

`REBUILD_EXIT=1` reads as "rebuild failed, tree is fine" and that inference is **unsafe** — on the third occurrence the rebuild died before relinking, leaving the binary holding the probe's string while the exit code said "failed." A serial rebuild is an *attempt*, not an exit; confirm the result at the artifact. Reverting source is not reverting the build; `git checkout -- .` on a shared clone is the unrecoverable move (restore named files from snapshots); `git show HEAD:<path>` is the only source of source facts on a patched tree. And a causal claim ("another ninja was running in the same `build/`") needs its referent pinned even about your own edge: `/workspace/**` is per-container, so `findmnt -no SOURCE,TARGET --target <path>` — device *and* subpath — before any claim about a file or build. [Concurrent ninja on one build dir: SECOND instance, different symptom (7 false undefined-reference errors) — recognize the class, and pin the referent of your own causal claim](wiki/learnings/1786036606295-concurrent-ninja-on-one-build-dir-second-instance-.md)

## Delegated builds die silently — background in your own session, watch three outcomes

Do **not** hand a 15-25 min Slang build to an `Agent` subagent and expect it to survive. When the subagent is reaped, its child `ninja` receives **SIGINT** and the log ends `ninja: build stopped: interrupted by user`. This contradicts `/slang-implement` Step 5 and `/slang-fix-issue` Step 6 ("always delegate it to an `Agent` subagent… blocks until done") — honour the *intent* (keep build output out of context) by backgrounding in your own session (`Bash run_in_background`, or `nohup`), writing the exit code to a dedicated marker file.

It is silent because the interruption is not a build failure: the exit-code marker is never written (a waiter hangs forever), the log's last lines are ordinary `[221/1453]` progress, and a monitor grepping only failure signatures stays silent — indistinguishable from "still compiling." **A build monitor must watch THREE outcomes:** exit-file appears (done), failure signature (broken), and **process gone while no exit file exists** (killed). Diagnose before re-running (`pgrep -a -f "ninja|cmake"`, `free -g` + `dmesg | tail`, `df -h`, `uptime` — these hosts hit load 120-190, so a loaded build takes ~115 min not 25). Recovery is cheap (ninja resumes at the last object). Observed 4+ times.

Two discriminators for the silent case: (1) "no new objects" is ambiguous between *linking* and *dead* — check for a linker process (`ld`/`lld`/`collect2`); add `.ninja_log` mtime staleness as a monitored condition (it fires where `FAILED:`/`error:` greps structurally can't). (2) **Scope by CWD, never by argv** — a worktree path is absent from *ninja's* bare argv (its identity is CWD-only), so `pgrep -f 'ninja.*wt-<name>'` returns a false zero for healthy builds; use `for p in $(pgrep -x ninja); do readlink /proc/$p/cwd; done | grep -c "wt-<name>"`. Also: `pgrep -xc <name> || echo 0` **fabricates a second datum** (pgrep prints `0` *and* exits non-zero, so the fallback appends another `0` → `"0\n0"` → integer-expression error) — the instrument's own defect imitates the finding. And **recall timing**: a *subject-matter* recall doesn't surface an operation lesson — grep the store for the OPERATION you're about to perform, not just the topic. [A delegated Slang build dies silently when its subagent is reaped — ninja takes SIGINT and writes no exit code](wiki/learnings/1786069823574-a-delegated-slang-build-dies-silently-when-its-sub.md)

## Native backtrace without gdb; symbolize with the `.dwarf` sidecar

For a deterministic rc=139 segfault inside `libslang-compiler` reached from Python (gdb not installable in time), install a C-level SIGSEGV handler that calls `backtrace_symbols_fd(2)` before dying — via `ctypes` from Python, or `LD_PRELOAD` of a tiny `__attribute__((constructor))` shared object for a standalone binary. The backtrace prints bare `lib(+0xOFFSET)`; **check for a `.dwarf` sidecar next to the library before rebuilding** — slang ships them (`build/Release/lib/libslang-compiler.so.0.2026.14.1.dwarf`, 346 MB). `addr2line -f -C -e <sidecar>.dwarf 0xOFFSET` turns anonymous frames into a named chain in minutes; a full Debug rebuild (15-30 min) is unnecessary. **Match the sidecar to the *loaded* library version** (slangpy vendors 2026.12, not a sibling slang checkout's 2026.14.1; the wrong sidecar yields plausible garbage). Escalate a runtime crash into a `slangc`-only command-line repro (worth far more upstream). And **symbolize every "successful" reproduction and confirm the frame matches the bug** — same exit code + same trigger shape ≠ same bug (a minimized single-file version crashed in a *different* frame, `GlslangDownstreamCompiler::_invoke`). `rc=124` is `timeout`'s code, not a crash — don't convert a timeout into a version verdict. `gh auth status` reports the App token "invalid" while `gh issue view`/`create` work — test an actual read before believing the error. [Native backtrace without gdb: libc backtrace_symbols_fd + .dwarf sidecar (settled slangpy#820 attribution -> slang#12392)](wiki/learnings/1786023645422-native-backtrace-without-gdb-libc-backtrace-symbol.md)

## Measuring without a full build: perf bisect and reflection

**Release-axis perf regression with zero Slang builds.** `tools/compile-perf/native/api-driver.cpp` compiles once and `dlopen`s whatever libslang it's pointed at, so one host driver measures every release (`fetch_releases.py --repo <checkout>`, then `bench.py --api --only api_many_kernels`). And `.rodata` section size (`readelf -S -W` on each release binary) is a proxy bisect for core-module blob growth — no benchmark, no GPU (parse the hex size column, not the address; look at `libslang-compiler.so`, which a 145 MB `libslang-llvm.so` otherwise masks). On a contended host (load 100 on 8 cores) interleave tags round-robin, take min-of-mins, verify under median, and use a **guilty control inside the same binaries** (other phases staying ~1× while the target hits 10× is what separates "release is slower" from "machine was busy"). A cheap predictive test on a cached binary killed a plausible-but-wrong attribution in one command (~83% of a recovery predated the commit a subagent had confidently credited). [Measure a Slang release-axis perf regression with zero builds: dlopen'd api-driver + ELF .rodata as a proxy bisect](wiki/learnings/1786041227237-measure-a-slang-release-axis-perf-regression-with-.md)

**Reflection values by linking `libslang.so`.** "No in-tree CLI surfaces this" is not "cannot be measured" — a ~40-line host program linking `-lslang` reads reflection values with no GPU. The step that matters: `findEntryPointByName` + `createCompositeComponentType` + `link()` **before** `getLayout()` — without composing and linking the entry point the witness table isn't in the program and an existential-size question measures the wrong thing. **The control is the point**: a plain concrete-struct parameter returning its true size (64) proves the instrument reads real sizes, not a constant. This upgraded a three-week-old "code fact, not runtime-run" into a measurement. [Measure Slang reflection values by linking libslang.so — no GPU, no in-tree CLI needed](wiki/learnings/1786082640745-measure-slang-reflection-values-by-linking-libslan.md)
