## TL;DR

- **A bare unparenthesized function name as a statement (`GroupMemoryBarrierWithGroupSync;`) is silently accepted and dropped** — exit 0, no diagnostic, even under `-warnings-as-errors all`. A one-character typo removes a barrier ⇒ latent data race. Only *overloaded* names error (E39999 ambiguous). Root: the `// TODO` stub in `CheckExpr` (`slang-check-expr.cpp:3849`). Filed **#12428**.
- **`import a.b` reaches subdirectories via a PARSER dot→slash rewrite**, but `-I` search itself is non-recursive and quoted imports get no sugar. One `-I` root can serve a whole hierarchy *only* with dotted names.
- **Parallel compilation needs one `IGlobalSession` PER THREAD** — a mutex around `createSession` provably cannot help, because every `Linkage` copies the global session's by-value `NamePool`.
- **`slang` is a dispatcher** that routes `slang foo` to a sibling `slang-foo` binary — sibling-dir only, no PATH search, no abbreviation.
- **Scalar `SV_DispatchThreadID` is component `.x`, not a flattened index** — silently collides across a column. Use `SV_GroupIndex` for a flat id.
- **`WorkgroupSize()` folds to a compile-time constant pre-emit** (returns signed `int3`, not `uint3`); spec-constant `[numthreads]` works on SPIR-V/GLSL only, hard-errors elsewhere.
- Matrix truncation `(float3x3)m3x4` is explicit-cast-only (generated ctor, no implicit marker) and yields the upper-left submatrix.
- In `*.meta.slang`, a zero-hit grep on a user-facing spelling means "wrong query" (types/methods are meta-generated), not "absent."

## The bare-function-name silent drop (#12428) — a whole class of "silently accepted, nothing emitted"

`GroupMemoryBarrierWithGroupSync;` — no parens, as an expression-statement — compiles clean (exit 0, zero diagnostics) and emits **nothing**: HLSL 0 barriers vs 1 with parens, SPIR-V `OpControlBarrier` 0 vs 1, and 0 vs ~380 barrier mentions in `-dump-ir`. Still silent under `-warnings-as-errors all` and `-validate-ir`. For a barrier this is a silent data race from one missing character. Measured on release `slangc 2026.14.1`; filed **shader-slang/slang#12428**.

The behaviour is broad and precisely characterized:

- **All six targets**, not just HLSL/SPIR-V — bare→called goes 0→1 for `controlBarrier`/`threadgroup_barrier`/`workgroupBarrier`/`__syncthreads` too.
- **Not builtin-specific** — a plain user-defined `void sideEffect()` referenced bare is equally silent.
- **`[NoDiscard]` is blind to it** (strongest dedup evidence): `f();` → `error[E30059] result discarded`, exit 255; `f;` → silent, exit 0. The mechanism whose whole job is catching an ignored result does not fire on the bare form.
- **Asymmetry is the discriminating control**: a bare *overloaded* name (`max;`) → `error[E39999] ambiguous reference`, because `maybeResolveOverloadedExpr` reaches `diagnoseAmbiguousReference` only for `OverloadedExpr`, and a single-overload ref sails through untouched. Testing with a random overloaded intrinsic gives a false all-clear.

Mechanism, verified in source at master `716ec597`:
- `slang-check-expr.cpp:3843-3849` — `CheckExpr` runs `maybeResolveOverloadedExpr`, then the value-check is a literal `// TODO: Implement this step.` stub. **That TODO is the missing check.**
- `slang-check-decl.cpp:1773-1787` — a `CallableDecl` declRef legitimately yields a `FuncType` (needed for `IFunc`/lambdas/`__fwd_diff(f)`), so nothing downstream objects. Any fix must keep those legal; a maintainer choosing warning-vs-error at the TODO is the trigger.
- No unused/no-effect diagnostic exists at all — the whole generated catalog (695 codes) has only `30058 dangling-equality-expr` in that family.

The most instructive method note: **"0 mentions in a `-dump-ir` body dump" does NOT mean lowering never ran.** `visitExpressionStmt` (`slang-lower-to-ir.cpp:8783`) calls `lowerLValueExpr`, and `ensureDecl` does `subIRBuilder.setInsertInto(subIRBuilder.getModule())` (`:14866`) — the `IRFunc` is materialized at **module scope**, nothing lands in the entry-point body, and the uncalled global is DCE'd. Absence from a body dump cannot discriminate "never lowered" from "lowered into a different parent then DCE'd." The decisive positive instrument was `[deprecated(...)]`: writing the function bare then fires `warning[E31200]` at exactly `bar;` col 5, proving lookup fully resolved the declRef and *still* nothing complained it was unapplied. And the biggest lever: **release binaries are one curl away — stop inferring what you can measure.** "No compiler on PATH" is a claim about PATH, not availability; source-reading structurally cannot settle an *absence* claim (no-diagnostic-exists and I-failed-to-find-it look identical). Always pair a run with controls (a typo at the same line:col must diagnose; the parenthesized variant must emit). ## Module resolution: `import a.b` is parser sugar; `-I` is non-recursive

- `-I` search is **non-recursive**: a dep at `packages/mylib/src/mylib.slang` with `import mylib; -I packages` FAILS (`E00001 cannot open file 'mylib.slang'`); it works only with `-I packages/mylib/src`.
- **BUT dotted import names reach subdirectories**: `import mylib.core;` with the file at `<root>/mylib/core.slang` and a single `-I <root>` succeeds. One `-I` root serves a whole hierarchy *provided modules use dotted names*.
- The mechanism is in the **parser**, not the filename helper: `parseFileReferenceDeclBase` (`slang-parser.cpp:1341-1352`) appends `/` for each `Dot` token ("we allow a dotted format for the name, as sugar"), so the module name already contains slashes before file lookup. `getFileNameFromModuleName` (`slang-session.cpp:1468`) does only underscore→dash and `.slang` append — grepping *there* for dot translation reads as "feature doesn't exist." A guilty control settles it: delete the target and the diagnostic becomes `cannot open file 'mylib/core.slang'` — with a slash, proving the translation happened.

Sharp edges: quoted imports get NO sugar (`import "mylib.core";` → literal `mylib.core.slang`); a module's `module` decl need not match its import path (nothing enforces agreement); `module mylib.core;` is invalid syntax (one identifier or one string literal). Outside the language server, `.slang-module` (IR) is tried *before* source (`slang-session.cpp:1583`), so a stale binary module can shadow fresher source — freshness validation rejects stale IR only when the source is reachable. [Slang `import a.b` reaches subdirectories via a PARSER dot→slash rewrite; `-I` itself is non-recursive and quoted imports get no sugar](../learnings/1786040130872-slang-import-a-b-reaches-subdirectories-via-a-pars.md)

## Parallel compilation: one `IGlobalSession` per thread, full stop

A user hit `STATUS_ACCESS_VIOLATION` in parallel shader compilation "even with a mutex on the global session." The tempting wrong answer is "also lock the objects created from it" — that pushes toward ever-finer locking and cannot fix this. Correct answer: **a distinct `IGlobalSession` per thread.** `docs/user-guide/08-compiling.md:720` and `slang.h:4071` state the global session is not thread-safe; `:1011` rules out the middle ground (N sessions, one shared global session): front-end operations "require external synchronization when multiple threads share a global session, a session, **or objects created from them**."

A lock around `createSession` provably cannot help because the shared state is touched *after* it returns: `slang-session.cpp:71` does `namePool = session->getNamePool();` — every `Linkage` (=`ISession`) copies a handle to the global session's **by-value** `NamePool`, so concurrent `loadModule`/type-checking on separate sessions interns names into one unsynchronized pool. Maintainer-confirmed on #8581. Only *backend emission* is parallel-safe, and only after full specialize+link. Bonus: there is **no module-unload API by design** (`ISession` exposes load+enumerate only; #4645 CLOSED not_planned — recreate the session, which is cheap because the core module amortizes on the global session). Method note: when a user says "I added the obvious lock and it still crashes," ask *which window the lock covers vs where the shared state is actually touched*, not "what else should I lock" — verify the ownership/copy site (here one line). [Slang: parallel compilation needs one IGlobalSession PER THREAD — a mutex around createSession cannot work](../learnings/1786088362639-slang-parallel-compilation-needs-one-iglobalsessio.md)

## The `slang` dispatcher

`source/slang-dispatcher/` builds an executable named `slang` with a builtin subcommand table (compile→slangc, interpret→slangi, help, version) and falls through any unknown subcommand to a sibling binary `slang-<subcommand>` (`main.cpp:484`). So a tool named `slang-foo` becomes `slang foo` with zero dispatcher changes (PR #10621, first release v2026.5.1). Three measured gotchas: **PATH is NOT searched** (only the running `slang`'s own directory — contradicting #10621's own prose about "the system path"); no abbreviation aliasing (`slang pkg` looks for `slang-pkg`, not `slang-package`); and `looksLikeFilePath()` is just "contains a dot," so a dotted subcommand is treated as a file. The `slang` binary is not in `build/{Debug,Release}/bin` — it's in the packaged tree `build/slang-<ver>-linux-x86_64/bin/slang`. Reporting "no dispatcher binary in this build" was a false capability-negative that forced inference when it could have been executed; look in the packaged tree before concluding a tool isn't built. Only one `//TEST:DISPATCHER` case exists tree-wide; the delegation path is untested. [Slang already has a `slang` dispatcher that routes unknown subcommands to sibling `slang-<name>` binaries — sibling-dir ONLY, no PATH](../learnings/1786040102016-slang-already-has-a-slang-dispatcher-that-routes-u.md)

## System-value semantics and workgroup intrinsics

**Scalar `SV_DispatchThreadID` narrows by SWIZZLE, not linearization.** Slang relaxes HLSL's `uint3` requirement (allows `uint`/`uint2`/`int`/`int2`), and `tryConvertValue` (`slang-ir-legalize-varying-params.cpp:293`) emits a swizzle with `index=0` ⇒ component `.x`. So `void main(uint tid : SV_DispatchThreadID)` under `[numthreads(8,8,1)]` silently **collides** — every thread in a column sees the same `tid`. It compiles clean; the scalar form is correct only for a 1D dispatch. For a flat index use `SV_GroupIndex` (scalar `uint`, group-local) or flatten yourself. The derivation identities are load-bearing when a target lacks the builtins: `dispatchThreadID = groupID*extents + groupThreadID`, `groupIndex = (z*Ny+y)*Nx+x` (x fastest); `emitCalcGroupExtents` bails on a non-literal extent. Metal/WGSL diagnose `SystemValueTypeIncompatible` rather than converting, so `uint2` is safest on SPIR-V/GLSL/CUDA. [Slang scalar SV_DispatchThreadID is component .x, not a flattened index](../learnings/1786115913613-slang-scalar-sv-dispatchthreadid-is-component-x-no.md)

**`WorkgroupSize()` is a compile-time constant, not a runtime read**, and returns signed **`int3`** (`hlsl.meta.slang:7837` — DeepWiki's `uint3` is wrong; corroborated by `tests/spirv/spec-constant-numthreads.slang`). `materializeGetWorkGroupSize` (`slang-ir-translate-global-varying-var.cpp:438`) splices the `IRNumThreadsDecoration` operands into each use site (so it's *not* restricted to literal extents, unlike `emitCalcGroupExtents`). It runs inside `linkAndOptimizeIR` outside any `switch(target)`, so the op is erased before emit everywhere — a positive-control grep of `GetWorkGroupSize` across all seven emitters returns **0 in every one**, and *absence in the emitters was the evidence it's portable, not that it's unsupported* (the opposite of the usual missing-arm reading; WGSL is untested, say "untested" not "unsupported"). Spec constants in `[numthreads]`: SPIR-V/GLSL work; HLSL/Metal/WGSL/CPU hard-error *at the attribute* ("Specialization constants are not supported in the 'numthreads' attribute", `slang-emit-c-like.cpp:294`). Don't confuse `WorkgroupSize()` with `uint3 WorkgroupCount()` (how many groups dispatched; GLSL/SPIR-V-only, no HLSL/CUDA/Metal/WGSL arm). [Slang WorkgroupSize() folds to a constant pre-emit; WorkgroupCount() is GLSL/SPIR-V only](../learnings/1786117126710-slang-workgroupsize-folds-to-a-constant-pre-emit-w.md)

## Matrix truncation is explicit-cast-only and yields the upper-left submatrix

`(float3x3)someFloat3x4` is legal and yields the upper-left 3×3 — but **explicit-only**. The truncating ctor is *generated*, not written: `core.meta.slang:2857-2867` loops `rr` from R..4, `cc` from C..4 emitting `__intrinsic_op(kIROp_MatrixReshape) __init(matrix<T,rr,cc,L>)`; only larger-or-equal sources are generated. Implicit assignment is rejected (the builtin matrix→matrix coercion at `slang-check-conversion.cpp:2237` requires equal rows AND columns, and the generated ctor has no `__implicit_conversion` marker) — so `float3x3 m = my3x4;` errors while `(float3x3)my3x4` compiles. Upper-left is provable: `slang-ir-peephole.cpp:1575` truncates rows, `slang-ir.cpp:4643` reshapes each row by swizzling `[0..toCount)`; `tests/bugs/matrix-reshape.slang` asserts the diagonal sum only the upper-left submatrix produces. Growing zero-pads.

Method lesson worth reusing: `grep 'float3x3'` on `hlsl.meta.slang` returns **ZERO** — concrete spellings are typedefs from a C++ meta-generator (`core.meta.slang:2601`) and the truncating ctor is loop-generated. Both the type name and the declaration are invisible to a literal grep. **In `*.meta.slang`, grep the generator, not the spelling users type — and treat a zero-hit grep there as "wrong query," not "absent."** (Same trap fired on `$(ccName)`-generated RayQuery methods and on `operator ++` written with a space.) [Slang truncates matrices via an explicit-only generated ctor — verify at the generator, not the grep](../learnings/1786134501113-slang-truncates-matrices-via-an-explicit-only-gene.md)

## Generics: independent axes and full-contract checks

On BFloat16 for cooperative vectors (#12411), a maintainer chained three blockers; measurement showed two sit on **independent axes**. `CoopVecComponentType` (an `enum` passed as `constexpr`) is the *memory interpretation*; `CoopVec<T,N>`'s `T` is the *register element type* (`T : __BuiltinArithmeticType`). Nothing constrains them to agree — the decisive cell is a type that fails one axis and works the other (`CoopVec<FloatE4M3,4>` fails E38029, yet `coopVecMatMul<float,4,4>(..., ::FloatE4M3, ...)` compiles). But the check that kept it honest was reading the signature of *every* API the issue named: `coopVecLoad` takes no interpretation parameter, so for that API the constraint *is* the only gate. Rules: when a report chains blockers, test whether each gates the others (one command); before declaring a blocker off the critical path, enumerate every API named ("not on the path" is a claim about a set); an in-tree precedent is evidence about the interface, not proof a swap works — check the *whole* contract (`CoopVec` inherits `IComparable` whose `equals`/`lessThan` do per-element scalar ops that BFloat16 lacks → E39999). A hand-written core-module struct outside `FOREACH_BASE_TYPE` cannot inherit conformance via the generated loop, so "just add the conformance" is never a one-liner for those types. [A generic constraint and a runtime enum parameter can be two independent axes — measure both before calling one a blocker](../learnings/1786049811729-a-generic-constraint-and-a-runtime-enum-parameter-.md)

## Constant folding: an all-literal probe never touches the backend

Slang folds all-literal arithmetic before it reaches the backend, so a "real hardware" measurement on constant inputs may measure only the constant folder. Probing `dot(float2(-0.0,-0.0), float2(1,1))` on `-target spirv` with literal operands emitted `OpDot` count **0** — the GPU never saw an `OpDot`. Control: grep the emitted target code for the op you believe you're testing and require count ≥ 1. Fix: read operands from a buffer (`RWStructuredBuffer` + `//TEST_INPUT:ubuffer(data=[0x80000000 ...])`, hex for exact bit patterns like `-0.0`). Second trap: `slang-test` front-inserts `-O0` into any directive lacking `-OX`, while standalone `slangc` uses the default level — so `OpDot` survives at `-O0` and folds at `-O1`; always record the opt level with the number. Related: unrolling an accumulator loop drops the `T(0) +` seed, an observable signed-zero change (`0.0 + (-0.0) == +0.0`), so "just unroll it" needs an identity-element-absorption check. [Slang folds all-literal arithmetic before it reaches the backend — a "real hardware" measurement on constant inputs may never touch the driver](../learnings/1786037229044-slang-folds-all-literal-arithmetic-before-it-reach.md) [Slang: [ForceUnroll] on a core-module __target_switch default arm — measure the arm set per overload, the FP and integer twins differ](../learnings/1786035420979-slang-forceunroll-on-a-core-module-target-switch-d.md)

The `[ForceUnroll]`/`__target_switch` atom also teaches: **measure the target-arm set per overload, not per function name.** `hlsl.meta.slang`'s two `dot` fallbacks differ — FP has `glsl`/`metal` arms, integer does *not*, so the same `default:` loop falls through on glsl/metal for integers but not floats. A blast-radius measurement done on a float shader concluded "C-like targets only" and was wrong for the integer twin; measure the matrix per overload. `[ForceUnroll]` failure is a hard error (E40020 `CannotUnrollLoop`), but for `vector<T,N>` the trip count is bounded 1..4 by language rule (`N>=5` rejected E38206), so the risk is structurally bounded there.

## The "core module counts as imported" trap

"No `import` line ⇒ cross-module logic cannot fire" is **FALSE** in Slang. A file with zero imports that locally redefines a core name (`int max(int,int)`) trips `warning[E38208]: ... overriding a candidate declared in this module ... chose ... from imported module 'core'`. The core module reports as an imported module (`getModuleDecl()`), it just has no `import` statement because it's implicit. Any reasoning "cross-module behaviour requires a visible import" is unsound — the implicit modules are `core`, plus `glsl` under `-allow-glsl`. A structural exclusion is stronger than a statistical one *only when the enumeration is complete*; when it isn't, it's worse, because it licenses skipping the checks that would have caught it. Grep for the *behaviour*, not the syntax that usually accompanies it. ["No import ⇒ cross-module logic cannot fire" is FALSE in Slang — the core module reports as `imported module 'core'`, so stdlib shadowing needs zero import lines](../learnings/1786044404247-no-import-cross-module-logic-cannot-fire-is-false-.md)

## `__target_switch`: whole-function case selection, missing-return gating, and capability hoisting

Beyond "measure the target-arm set per overload," two failure modes of `specializeTargetSwitch` (`slang-ir-specialize-target-switch.cpp`) recur when authoring core-module methods. It selects EXACTLY ONE case for the whole function by capability specificity ("larger implied atom set wins", `slang-capability.cpp:1417-1420`), reading GLOBAL target caps — it is the producer-side selection layer, upstream of the `targetCaps.implies(...)` gates in `slang-ir-spirv-legalize.cpp`/`slang-emit-spirv.cpp` (editing those does not move selection and regresses, slang#11631; fix in the meta-source producer).

First, a method whose `__target_switch` LACKS a case for the compile target does NOT fall back: `specializeTargetSwitch` injects `emitMissingReturn()`, a sentinel terminator, and the consequence is TARGET-GATED by `doesTargetAllowMissingReturns` (`slang-ir-missing-return.cpp:18-26`) — `false` for `isKhronosTarget || isWGPUTarget` → hard `E41009 "non-void function must return"` (SPIR-V/GLSL/WGPU); `true` elsewhere → at most an `E41010` warning, and on CUDA the call is SILENTLY DROPPED (worse than an error). The E41009 text is fixed regardless of the callee's real return type — it fires even on a `void` method (the pass keys on the sentinel, not on non-void-ness). This bit HitObject/SER methods (#12553 2-arg `HitObject::Invoke`, #10307 `HitObject.FromRayQuery`) that had only `case hlsl:`. Fix: mirror a sibling overload's `spirv`/`glsl`/`cuda` cases onto the broken method and widen its `[require(...)]`; a key enabler was that the SPIR-V/GLSL SER ops (`OpHitObjectExecuteShaderEXT/NV`) never take an AccelerationStructure (it is baked into the `HitObject`; the explicit TLAS is a pure NVAPI/DXIL artifact), so a no-TLAS form maps to identical ops — but `case cuda: __intrinsic_asm "optixInvoke"` forwards args positionally, so dropping the TLAS changes the emitted arity and needs matching 2-arg prelude wrappers in `slang-cuda-prelude.h`. (Tooling: `hlsl.meta.slang` is >1 MB, so `gh api .../contents/...` returns empty `content:""` — verify merged content via local `git show <ref>:... | grep`, not the contents API.) [HitObject/SER core-module method missing a `__target_switch` case → E41009](../learnings/1789454795235-hitobject-ser-core-module-method-missing-a-spirv-g.md)

Second, when two capabilities are enabled together the more-specialized arm captures the WHOLE function and a less-specialized arm's per-kind carve-out is never reached (#13070: `spvBindlessTextureNV` = 1 atom vs `spvDescriptorHeapEXT` = 2 atoms → texture/sampler handles wrongly routed to the EXT heap instead of native `OpConvertUTo{Image,Sampler}NV`). The fix pattern — preferred over a compound `case A + B:` whose specificity ranking is unverified — is to HOIST a second `__target_switch` AHEAD of the main one that mentions ONLY the less-specialized capability, with a `default: break` so it falls through for every other target; because the hoisted switch never names the specialized cap, that cap cannot out-rank it and the subset is decided first. LOAD-BEARING: a case body ending in `break;` compiles to a branch to the after-switch continuation, but a bare hoisted switch with NO `default` would TRAP (missing-return) on every target where the named cap is absent — so the hoisted switch MUST have `default: break`. [__target_switch: hoist a less-specialized capability's per-kind case ahead of the main switch](../learnings/1789460740871-slang-target-switch-hoist-a-less-specialized-capab.md)

## meta.slang `static_assert` is the only compile-time diagnostic — error-only, per-instantiation

`static_assert(constexpr bool, NativeString msg)` (`core.meta.slang:483`) is the ONLY compile-time diagnostic primitive in the meta language — there is no `static_warn`/`static_warning`/`__diagnostic`. So a REJECT keyed on a generic parameter's value lives cleanly in `*.meta.slang`, but a WARNING keyed on one CANNOT — it forces a checker-side path (a `slang-diagnostics.lua` entry + a hook at the conversion site). In a generic member body `static_assert` fires PER-INSTANTIATION (only when the offending specialization is actually used), giving a targeted error at the user's call site while leaving other specializations untouched — pervasive precedent in `_Texture` method bodies keyed on generic `let` ints/`Shape` (`hlsl.meta.slang:1791/1894/1937`, the `isShadow`/`isArray`/`isMS`/`access` family at `:1135-1161`). When the discriminating flag rides on a generic type `T` bound by an interface rather than an in-scope `let`, read the interface's `static const` (e.g. `_Texture`'s `static const DescriptorKind kind`, readable through `DescriptorHandle<T>` as `T.kind`; the core module already branches `switch(T.kind)` at `hlsl.meta.slang:28023`). Prefer `static_assert` over *omitting* a member — omission gives a generic "cannot convert X to Y", `static_assert` lets you author the exact guidance (context: #13085, ResourceDescriptorHeap single-index → combined texture/sampler silently defaulting sampler slot 0, whose two zero-fill `__init`s are at `:27622` and `:27905`). [meta.slang can reject (not warn) a member per-instantiation via `static_assert` on a generic `let`/`T.kind`](../learnings/1789457618247-meta-slang-can-reject-not-warn-a-member-per-instan.md)

## No Decl→SourceLanguage path post-parse — dialect scoping needs a module-AST hook

Scoping a behavior to the HLSL or GLSL dialect at check/lowering time is not a one-line branch: the semantic checker never branches on the translation-unit source language. Investigating #13073 at master `c0e27bc0e7`, an exhaustive sweep of `slang-check*.{cpp,h}` finds the raw `SourceLanguage` enum consulted exactly once — in the *parser* (`slang-parser.cpp:10022`), to decide whether to stamp a `GLSLModuleModifier` onto the `ModuleDecl`. After parse only that boolean marker survives; `TranslationUnitRequest::sourceLanguage` is a front-end-request field never copied onto the `ModuleDecl`, so there is no reliable Decl→SourceLanguage path. Everywhere the checker needs "is this GLSL-flavored" it reads the `GLSLModuleModifier` marker + the `AllowGLSL` option (via `isGLSLOperatorScope`), never the source language. So any "scope this to the dialect" feature must first add a module-AST hook — a bare `HLSLModuleModifier` mirroring the GLSL one, or (the cleaner maintainer-preferred design) a single `ModuleSourceLanguageModifier` carrying a `SourceLanguage` payload, both reachable at check and lowering via `getModuleDecl(decl)`. Baking the dialect onto the *defining* module's AST rather than reading a global option at each use site is what keeps semantics stable across module boundaries — a use-site option read gives different answers for the defining module vs a downstream importer (witness/ABI divergence) ([Slang checker has no Decl→SourceLanguage path — HLSL-dialect scoping needs net-new module-AST plumbing](../learnings/1789502791946-slang-checker-has-no-decl-sourcelanguage-path-hlsl.md)).
