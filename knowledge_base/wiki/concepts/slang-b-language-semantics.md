## TL;DR

- **A bare unparenthesized function name as a statement (`GroupMemoryBarrierWithGroupSync;`) is silently accepted and dropped** — exit 0, no diagnostic, even under `-warnings-as-errors all`. A one-character typo removes a barrier ⇒ latent data race. Only *overloaded* names error (E39999 ambiguous). Root: the `// TODO` stub in `CheckExpr` (`slang-check-expr.cpp:3849`). Filed **#12428**.
- **`import a.b` reaches subdirectories via a PARSER dot→slash rewrite**, but `-I` search itself is non-recursive and quoted imports get no sugar. One `-I` root can serve a whole hierarchy *only* with dotted names.
- **Parallel compilation needs one `IGlobalSession` PER THREAD** — a mutex around `createSession` provably cannot help, because every `Linkage` copies the global session's by-value `NamePool`.
- **`slang` is a dispatcher** that routes `slang foo` to a sibling `slang-foo` binary — sibling-dir only, no PATH search, no abbreviation.
- **Scalar `SV_DispatchThreadID` is component `.x`, not a flattened index** — silently collides across a column. Use `SV_GroupIndex` for a flat id.
- **`WorkgroupSize()` folds to a compile-time constant pre-emit** (returns signed `int3`, not `uint3`); spec-constant `[numthreads]` works on SPIR-V/GLSL only, hard-errors elsewhere.
- Matrix truncation `(float3x3)m3x4` is explicit-cast-only (generated ctor, no implicit marker) and yields the upper-left submatrix.
- In `*.meta.slang`, a zero-hit grep on a user-facing spelling means "wrong query" (types/methods are meta-generated), not "absent."

## The bare-function-name silent drop (#12428) — a whole class of "silently accepted, nothing emitted"

`GroupMemoryBarrierWithGroupSync;` — no parens, as an expression-statement — compiles clean (exit 0, zero diagnostics) and emits **nothing**: HLSL 0 barriers vs 1 with parens, SPIR-V `OpControlBarrier` 0 vs 1, and 0 vs ~380 barrier mentions in `-dump-ir`. Still silent under `-warnings-as-errors all` and `-validate-ir`. For a barrier this is a silent data race from one missing character. Measured on release `slangc 2026.14.1`; filed **shader-slang/slang#12428**.

The behaviour is broad and precisely characterized:

- **All six targets**, not just HLSL/SPIR-V — bare→called goes 0→1 for `controlBarrier`/`threadgroup_barrier`/`workgroupBarrier`/`__syncthreads` too.
- **Not builtin-specific** — a plain user-defined `void sideEffect()` referenced bare is equally silent.
- **`[NoDiscard]` is blind to it** (strongest dedup evidence): `f();` → `error[E30059] result discarded`, exit 255; `f;` → silent, exit 0. The mechanism whose whole job is catching an ignored result does not fire on the bare form.
- **Asymmetry is the discriminating control**: a bare *overloaded* name (`max;`) → `error[E39999] ambiguous reference`, because `maybeResolveOverloadedExpr` reaches `diagnoseAmbiguousReference` only for `OverloadedExpr`, and a single-overload ref sails through untouched. Testing with a random overloaded intrinsic gives a false all-clear.

Mechanism, verified in source at master `716ec597`:
- `slang-check-expr.cpp:3843-3849` — `CheckExpr` runs `maybeResolveOverloadedExpr`, then the value-check is a literal `// TODO: Implement this step.` stub. **That TODO is the missing check.**
- `slang-check-decl.cpp:1773-1787` — a `CallableDecl` declRef legitimately yields a `FuncType` (needed for `IFunc`/lambdas/`__fwd_diff(f)`), so nothing downstream objects. Any fix must keep those legal; a maintainer choosing warning-vs-error at the TODO is the trigger.
- No unused/no-effect diagnostic exists at all — the whole generated catalog (695 codes) has only `30058 dangling-equality-expr` in that family.

The most instructive method note: **"0 mentions in a `-dump-ir` body dump" does NOT mean lowering never ran.** `visitExpressionStmt` (`slang-lower-to-ir.cpp:8783`) calls `lowerLValueExpr`, and `ensureDecl` does `subIRBuilder.setInsertInto(subIRBuilder.getModule())` (`:14866`) — the `IRFunc` is materialized at **module scope**, nothing lands in the entry-point body, and the uncalled global is DCE'd. Absence from a body dump cannot discriminate "never lowered" from "lowered into a different parent then DCE'd." The decisive positive instrument was `[deprecated(...)]`: writing the function bare then fires `warning[E31200]` at exactly `bar;` col 5, proving lookup fully resolved the declRef and *still* nothing complained it was unapplied. And the biggest lever: **release binaries are one curl away — stop inferring what you can measure.** "No compiler on PATH" is a claim about PATH, not availability; source-reading structurally cannot settle an *absence* claim (no-diagnostic-exists and I-failed-to-find-it look identical). Always pair a run with controls (a typo at the same line:col must diagnose; the parenthesized variant must emit). ## Module resolution: `import a.b` is parser sugar; `-I` is non-recursive

- `-I` search is **non-recursive**: a dep at `packages/mylib/src/mylib.slang` with `import mylib; -I packages` FAILS (`E00001 cannot open file 'mylib.slang'`); it works only with `-I packages/mylib/src`.
- **BUT dotted import names reach subdirectories**: `import mylib.core;` with the file at `<root>/mylib/core.slang` and a single `-I <root>` succeeds. One `-I` root serves a whole hierarchy *provided modules use dotted names*.
- The mechanism is in the **parser**, not the filename helper: `parseFileReferenceDeclBase` (`slang-parser.cpp:1341-1352`) appends `/` for each `Dot` token ("we allow a dotted format for the name, as sugar"), so the module name already contains slashes before file lookup. `getFileNameFromModuleName` (`slang-session.cpp:1468`) does only underscore→dash and `.slang` append — grepping *there* for dot translation reads as "feature doesn't exist." A guilty control settles it: delete the target and the diagnostic becomes `cannot open file 'mylib/core.slang'` — with a slash, proving the translation happened.

Sharp edges: quoted imports get NO sugar (`import "mylib.core";` → literal `mylib.core.slang`); a module's `module` decl need not match its import path (nothing enforces agreement); `module mylib.core;` is invalid syntax (one identifier or one string literal). Outside the language server, `.slang-module` (IR) is tried *before* source (`slang-session.cpp:1583`), so a stale binary module can shadow fresher source — freshness validation rejects stale IR only when the source is reachable. [Slang `import a.b` reaches subdirectories via a PARSER dot→slash rewrite; `-I` itself is non-recursive and quoted imports get no sugar](wiki/learnings/1786040130872-slang-import-a-b-reaches-subdirectories-via-a-pars.md)

## Parallel compilation: one `IGlobalSession` per thread, full stop

A user hit `STATUS_ACCESS_VIOLATION` in parallel shader compilation "even with a mutex on the global session." The tempting wrong answer is "also lock the objects created from it" — that pushes toward ever-finer locking and cannot fix this. Correct answer: **a distinct `IGlobalSession` per thread.** `docs/user-guide/08-compiling.md:720` and `slang.h:4071` state the global session is not thread-safe; `:1011` rules out the middle ground (N sessions, one shared global session): front-end operations "require external synchronization when multiple threads share a global session, a session, **or objects created from them**."

A lock around `createSession` provably cannot help because the shared state is touched *after* it returns: `slang-session.cpp:71` does `namePool = session->getNamePool();` — every `Linkage` (=`ISession`) copies a handle to the global session's **by-value** `NamePool`, so concurrent `loadModule`/type-checking on separate sessions interns names into one unsynchronized pool. Maintainer-confirmed on #8581. Only *backend emission* is parallel-safe, and only after full specialize+link. Bonus: there is **no module-unload API by design** (`ISession` exposes load+enumerate only; #4645 CLOSED not_planned — recreate the session, which is cheap because the core module amortizes on the global session). Method note: when a user says "I added the obvious lock and it still crashes," ask *which window the lock covers vs where the shared state is actually touched*, not "what else should I lock" — verify the ownership/copy site (here one line). [Slang: parallel compilation needs one IGlobalSession PER THREAD — a mutex around createSession cannot work](wiki/learnings/1786088362639-slang-parallel-compilation-needs-one-iglobalsessio.md)

## The `slang` dispatcher

`source/slang-dispatcher/` builds an executable named `slang` with a builtin subcommand table (compile→slangc, interpret→slangi, help, version) and falls through any unknown subcommand to a sibling binary `slang-<subcommand>` (`main.cpp:484`). So a tool named `slang-foo` becomes `slang foo` with zero dispatcher changes (PR #10621, first release v2026.5.1). Three measured gotchas: **PATH is NOT searched** (only the running `slang`'s own directory — contradicting #10621's own prose about "the system path"); no abbreviation aliasing (`slang pkg` looks for `slang-pkg`, not `slang-package`); and `looksLikeFilePath()` is just "contains a dot," so a dotted subcommand is treated as a file. The `slang` binary is not in `build/{Debug,Release}/bin` — it's in the packaged tree `build/slang-<ver>-linux-x86_64/bin/slang`. Reporting "no dispatcher binary in this build" was a false capability-negative that forced inference when it could have been executed; look in the packaged tree before concluding a tool isn't built. Only one `//TEST:DISPATCHER` case exists tree-wide; the delegation path is untested. [Slang already has a `slang` dispatcher that routes unknown subcommands to sibling `slang-<name>` binaries — sibling-dir ONLY, no PATH](wiki/learnings/1786040102016-slang-already-has-a-slang-dispatcher-that-routes-u.md)

## System-value semantics and workgroup intrinsics

**Scalar `SV_DispatchThreadID` narrows by SWIZZLE, not linearization.** Slang relaxes HLSL's `uint3` requirement (allows `uint`/`uint2`/`int`/`int2`), and `tryConvertValue` (`slang-ir-legalize-varying-params.cpp:293`) emits a swizzle with `index=0` ⇒ component `.x`. So `void main(uint tid : SV_DispatchThreadID)` under `[numthreads(8,8,1)]` silently **collides** — every thread in a column sees the same `tid`. It compiles clean; the scalar form is correct only for a 1D dispatch. For a flat index use `SV_GroupIndex` (scalar `uint`, group-local) or flatten yourself. The derivation identities are load-bearing when a target lacks the builtins: `dispatchThreadID = groupID*extents + groupThreadID`, `groupIndex = (z*Ny+y)*Nx+x` (x fastest); `emitCalcGroupExtents` bails on a non-literal extent. Metal/WGSL diagnose `SystemValueTypeIncompatible` rather than converting, so `uint2` is safest on SPIR-V/GLSL/CUDA. [Slang scalar SV_DispatchThreadID is component .x, not a flattened index](wiki/learnings/1786115913613-slang-scalar-sv-dispatchthreadid-is-component-x-no.md)

**`WorkgroupSize()` is a compile-time constant, not a runtime read**, and returns signed **`int3`** (`hlsl.meta.slang:7837` — DeepWiki's `uint3` is wrong; corroborated by `tests/spirv/spec-constant-numthreads.slang`). `materializeGetWorkGroupSize` (`slang-ir-translate-global-varying-var.cpp:438`) splices the `IRNumThreadsDecoration` operands into each use site (so it's *not* restricted to literal extents, unlike `emitCalcGroupExtents`). It runs inside `linkAndOptimizeIR` outside any `switch(target)`, so the op is erased before emit everywhere — a positive-control grep of `GetWorkGroupSize` across all seven emitters returns **0 in every one**, and *absence in the emitters was the evidence it's portable, not that it's unsupported* (the opposite of the usual missing-arm reading; WGSL is untested, say "untested" not "unsupported"). Spec constants in `[numthreads]`: SPIR-V/GLSL work; HLSL/Metal/WGSL/CPU hard-error *at the attribute* ("Specialization constants are not supported in the 'numthreads' attribute", `slang-emit-c-like.cpp:294`). Don't confuse `WorkgroupSize()` with `uint3 WorkgroupCount()` (how many groups dispatched; GLSL/SPIR-V-only, no HLSL/CUDA/Metal/WGSL arm). [Slang WorkgroupSize() folds to a constant pre-emit; WorkgroupCount() is GLSL/SPIR-V only](wiki/learnings/1786117126710-slang-workgroupsize-folds-to-a-constant-pre-emit-w.md)

## Matrix truncation is explicit-cast-only and yields the upper-left submatrix

`(float3x3)someFloat3x4` is legal and yields the upper-left 3×3 — but **explicit-only**. The truncating ctor is *generated*, not written: `core.meta.slang:2857-2867` loops `rr` from R..4, `cc` from C..4 emitting `__intrinsic_op(kIROp_MatrixReshape) __init(matrix<T,rr,cc,L>)`; only larger-or-equal sources are generated. Implicit assignment is rejected (the builtin matrix→matrix coercion at `slang-check-conversion.cpp:2237` requires equal rows AND columns, and the generated ctor has no `__implicit_conversion` marker) — so `float3x3 m = my3x4;` errors while `(float3x3)my3x4` compiles. Upper-left is provable: `slang-ir-peephole.cpp:1575` truncates rows, `slang-ir.cpp:4643` reshapes each row by swizzling `[0..toCount)`; `tests/bugs/matrix-reshape.slang` asserts the diagonal sum only the upper-left submatrix produces. Growing zero-pads.

Method lesson worth reusing: `grep 'float3x3'` on `hlsl.meta.slang` returns **ZERO** — concrete spellings are typedefs from a C++ meta-generator (`core.meta.slang:2601`) and the truncating ctor is loop-generated. Both the type name and the declaration are invisible to a literal grep. **In `*.meta.slang`, grep the generator, not the spelling users type — and treat a zero-hit grep there as "wrong query," not "absent."** (Same trap fired on `$(ccName)`-generated RayQuery methods and on `operator ++` written with a space.) [Slang truncates matrices via an explicit-only generated ctor — verify at the generator, not the grep](wiki/learnings/1786134501113-slang-truncates-matrices-via-an-explicit-only-gene.md)

## Generics: independent axes and full-contract checks

On BFloat16 for cooperative vectors (#12411), a maintainer chained three blockers; measurement showed two sit on **independent axes**. `CoopVecComponentType` (an `enum` passed as `constexpr`) is the *memory interpretation*; `CoopVec<T,N>`'s `T` is the *register element type* (`T : __BuiltinArithmeticType`). Nothing constrains them to agree — the decisive cell is a type that fails one axis and works the other (`CoopVec<FloatE4M3,4>` fails E38029, yet `coopVecMatMul<float,4,4>(..., ::FloatE4M3, ...)` compiles). But the check that kept it honest was reading the signature of *every* API the issue named: `coopVecLoad` takes no interpretation parameter, so for that API the constraint *is* the only gate. Rules: when a report chains blockers, test whether each gates the others (one command); before declaring a blocker off the critical path, enumerate every API named ("not on the path" is a claim about a set); an in-tree precedent is evidence about the interface, not proof a swap works — check the *whole* contract (`CoopVec` inherits `IComparable` whose `equals`/`lessThan` do per-element scalar ops that BFloat16 lacks → E39999). A hand-written core-module struct outside `FOREACH_BASE_TYPE` cannot inherit conformance via the generated loop, so "just add the conformance" is never a one-liner for those types. [A generic constraint and a runtime enum parameter can be two independent axes — measure both before calling one a blocker](wiki/learnings/1786049811729-a-generic-constraint-and-a-runtime-enum-parameter-.md)

## Constant folding: an all-literal probe never touches the backend

Slang folds all-literal arithmetic before it reaches the backend, so a "real hardware" measurement on constant inputs may measure only the constant folder. Probing `dot(float2(-0.0,-0.0), float2(1,1))` on `-target spirv` with literal operands emitted `OpDot` count **0** — the GPU never saw an `OpDot`. Control: grep the emitted target code for the op you believe you're testing and require count ≥ 1. Fix: read operands from a buffer (`RWStructuredBuffer` + `//TEST_INPUT:ubuffer(data=[0x80000000 ...])`, hex for exact bit patterns like `-0.0`). Second trap: `slang-test` front-inserts `-O0` into any directive lacking `-OX`, while standalone `slangc` uses the default level — so `OpDot` survives at `-O0` and folds at `-O1`; always record the opt level with the number. Related: unrolling an accumulator loop drops the `T(0) +` seed, an observable signed-zero change (`0.0 + (-0.0) == +0.0`), so "just unroll it" needs an identity-element-absorption check. [Slang folds all-literal arithmetic before it reaches the backend — a "real hardware" measurement on constant inputs may never touch the driver](wiki/learnings/1786037229044-slang-folds-all-literal-arithmetic-before-it-reach.md) [Slang: [ForceUnroll] on a core-module __target_switch default arm — measure the arm set per overload, the FP and integer twins differ](wiki/learnings/1786035420979-slang-forceunroll-on-a-core-module-target-switch-d.md)

The `[ForceUnroll]`/`__target_switch` atom also teaches: **measure the target-arm set per overload, not per function name.** `hlsl.meta.slang`'s two `dot` fallbacks differ — FP has `glsl`/`metal` arms, integer does *not*, so the same `default:` loop falls through on glsl/metal for integers but not floats. A blast-radius measurement done on a float shader concluded "C-like targets only" and was wrong for the integer twin; measure the matrix per overload. `[ForceUnroll]` failure is a hard error (E40020 `CannotUnrollLoop`), but for `vector<T,N>` the trip count is bounded 1..4 by language rule (`N>=5` rejected E38206), so the risk is structurally bounded there.

## The "core module counts as imported" trap

"No `import` line ⇒ cross-module logic cannot fire" is **FALSE** in Slang. A file with zero imports that locally redefines a core name (`int max(int,int)`) trips `warning[E38208]: ... overriding a candidate declared in this module ... chose ... from imported module 'core'`. The core module reports as an imported module (`getModuleDecl()`), it just has no `import` statement because it's implicit. Any reasoning "cross-module behaviour requires a visible import" is unsound — the implicit modules are `core`, plus `glsl` under `-allow-glsl`. A structural exclusion is stronger than a statistical one *only when the enumeration is complete*; when it isn't, it's worse, because it licenses skipping the checks that would have caught it. Grep for the *behaviour*, not the syntax that usually accompanies it. ["No import ⇒ cross-module logic cannot fire" is FALSE in Slang — the core module reports as `imported module 'core'`, so stdlib shadowing needs zero import lines](wiki/learnings/1786044404247-no-import-cross-module-logic-cannot-fire-is-false-.md)
