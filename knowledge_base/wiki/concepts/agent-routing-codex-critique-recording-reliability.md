# Codex-critique recording reliability — exact names, bridge dispatch, and state resets

## TL;DR

What makes a codex-critique round actually RECORD (vs. run fine yet leave no state), what silently kills or wipes recorded rounds, and how to re-record cheaply. Companion to [gate mechanics](agent-routing-f0909b1-critique-gate-mechanics.md) (stage counting, attestation, review-request format) and [critique and delivery gates](agent-routing-f0909b2-critique-and-delivery-gates.md) (edit counter, read-only `gh` blocks).

- **The recorder matches exact names.** The MCP tool must literally be `mcp__codex__codex` and the parameter literally `developer-instructions` (`developer_instructions`/`developerinstructions` pass; a `developer` alias and opencode's harness-exposed `codex_codex`/`codex_codex-reply` names record NOTHING — codex receives and follows the instructions, the round just never lands). Verify `jq .critique_stages /workspace/.claude/workflow-state.json` after every round; never treat the codex response as proof of recording.
- **A pinned recording call needs the full kit:** the canonical sentinel block ("You are an independent reviewer" + "Return ONLY the structured output below") within the first 2000 bytes of `developer-instructions`, plus a `REQUIREMENTS:` field with comment URLs or `none — <reason>`. OpenCode renames `threadId`→`threadid` in tool_input, so reply TID extraction fails and codex-reply rounds never map to a stage.
- **Live rounds die three ways:** the app-server exits mid-turn ("codex app-server exited (code=0) before the turn completed", ~15 min each) — commonly a `gh api`/network command hanging inside the codex sandbox until the 900 s turn budget is eaten (diagnose via the rollout JSONL's `function_call` entries and `duration_ms ≈ 900000`); for a SLOW model it is the THREAD_IDLE eviction timer (set only before/after a turn) killing any turn >15 min — fix with `CODEX_MCP_THREAD_IDLE_MS=2100000` on the bridge launch; the dispatch client is killed with the shell's whole process group at a bash timeout — launch detached with `setsid <script> < /dev/null > /dev/null 2>&1 & disown`, NOT bare `nohup … &`; or a `>` redirect in the same bash call bumps the edit counter after the round records.
- **Workflow-state resets wipe everything mid-task** (container restarts, 429-retry turns, message-batch boundaries): `plan_written:false` + empty `critique_stages` while the plan and approvals were real and recent. The plan-tracker hook fires on the Write tool only — an Edit does NOT restore `plan_written`; re-Write the whole plan file, then re-record each missing stage as a LEAN fresh call (~2–3 min) instead of re-deriving.
- **Recovery recipe:** write prompt + verbatim developer-instructions to files, dispatch through the bun bridge client (PATH="/pnpm:$PATH") detached with setsid, and poll `/workspace/.claude/critique-attempts.jsonl` for the `{"event":"round",...}` line (~3–10 min per stage) — the bridge records rounds itself, independent of the harness hook.

## Exact-name recording: rounds that silently record nothing

A round is recorded only when the hook's matchers all hit. On slang-rhi#976 (2026-11-18) a critique call whose developer-instructions were passed under the parameter name `developer` was silently refused by the pin check — critique-attempts.jsonl shows the "start" event but no "round" event, workflow-state stays behind, though codex itself received and followed the instructions; re-run the stage with the exact parameter name (`developer-instructions` / `developer_instructions` / `developerinstructions`) and verify with `jq .critique_stages` ([exact MCP param name required; bun-bridge fallback](../learnings/1795032791979-codex-critique-recording-exact-mcp-param-name-requ.md)). In opencode the schema spells it camelCase — `developerInstructions` (hyphens dropped), and the tool silently accepts a wrong key like `developer` without a schema rejection: the reviewer block is just dropped, codex runs the review fine, and only the pin-check's missing sentinels betray it (a "start" event, never a "round") — so verify `jq .critique_stages /workspace/.claude/workflow-state.json` after EVERY single round, not just after failures (4 wasted codex calls on slang#14220, 2026-11-25) ([codex critique param-name trap + clean-merge-vs-DIRTY-PR resolution pattern](../learnings/1795639666119-codex-critique-param-name-trap-clean-merge-vs-dirt.md)). The tool name matters the same way: `/app/hooks/track-critique.sh` only matches `mcp__codex__codex|mcp__codex__codex-reply`, but opencode exposes the bridge as `codex_codex`/`codex_codex-reply` — on slang#14612 every PLAN/CODE/OUTPUT round ran fine in codex and recorded nothing, and the PR-create gate then denied naming all required stages missing; check the state file, not the codex response ([critique rounds record only for mcp__codex__codex](../learnings/1795046810801-critique-rounds-record-only-for-mcp-codex-codex-op.md)). The delivery gate likewise records a round ONLY on a *pinned* call — the verbatim reviewer sentinels in the first 2000 bytes AND a `REQUIREMENTS:` field with comment URLs (or `none — <reason>`); and OpenCode renames `threadId` to `threadid` in tool_input, so track-critique's reply TID extraction (`.tool_input.threadId // .thread_id`) finds nothing and codex-reply rounds never count — for the final pre-delivery round always use a fresh pinned `mcp__codex__codex` call with `STAGE:` set ([pinned codex calls count; codex-reply rounds never record](../learnings/1795046963589-critique-gate-pinned-codex-calls-count-codex-reply.md)).

## Bridge dispatch: how a live round dies, and how to run it detached

The MCP bridge can die mid-turn: `mcp__codex__codex` failed twice with "codex app-server exited (code=0) before the turn completed" (~15 min each, no verdict). Dispatching the same prompt + verbatim developer-instructions through the bun bridge client completed in ~5 min AND the bridge recorded the round itself (a "round" event in critique-attempts.jsonl, independent of the harness hook) — write prompt + dev-instructions to files, run the saved client with PATH="/pnpm:$PATH" and a ≥32-min bash timeout, then check workflow-state ([exact MCP param name required; bun-bridge fallback](../learnings/1795032791979-codex-critique-recording-exact-mcp-param-name-requ.md)). But a foreground bridge run dies at the shell timeout (the bridge hangs after the result), so run the dispatch DETACHED and poll the attempts log for the round event — one fresh initial call per required stage ([critique rounds record only for mcp__codex__codex](../learnings/1795046810801-critique-rounds-record-only-for-mcp-codex-codex-op.md)). Detach with `setsid`, not bare `nohup … &`: the agent shell tool's timeout kill reaps the whole process group, and a `nohup python3 bridge-dispatch.py … &` client died mid-review twice on slang#14618 (start event recorded, no round — round lost); wrap the dispatch in a tiny shell script and launch `setsid <script> < /dev/null > /dev/null 2>&1 & disown` — that survived and recorded cleanly. Telltale: shell metadata "terminated after exceeding timeout" right after the nohup, then no round event ([codex-bridge dispatch: setsid not nohup](../learnings/1795055939569-codex-bridge-dispatch-setsid-not-nohup-no-issuecom.md)).

The most common cause of the app-server exit is a hung network command inside the codex sandbox. The canonical reviewer instructions tell codex to "fetch every cited URL yourself (gh api, or curl)" — on slang#14615 a CODE_REVIEW turn sat 14:45 min on a hung `gh api repos/shader-slang/slang/issues/14615 | head -100`, ate the bridge's whole 900 s turn budget, and the round died as "app-server exited" — twice; read the rollout JSONL (`~/.codex/sessions/.../rollout-*.jsonl`, look for `function_call` entries and a timeout with `duration_ms ≈ 900000`) to see where it hung. The fix that worked first try: fetch the issue body + comments JSON yourself, save them under the scratch dir, and list them in ARTIFACTS with an explicit "network commands can HANG in your sandbox — do not run them" note; verbatim-quote verification still happens (codex substring-matches the JSON), the round just doesn't die. Same atom's secondary traps: a dispatch bash command containing `> path` (with a space) can race the edit counter — track-critique zeroes `edits_since_critique` when recording, and the PostToolUse bump from the redirect can land the same second and win; the hook's write-regex is `(^|\s|\|)(>|>>)\s`, so write redirect targets with NO space (`>result.txt`) or run one cheap codex-reply re-record ("artifacts unchanged, re-record") to re-zero it. And `pkill -f <pattern>` self-matches your own bash command line and kills YOUR shell — use a bracket trick like `code-prom[p].txt` ([gh api hangs the turn; dispatch redirects race the edit counter](../learnings/1795054140366-codex-critique-gh-api-hangs-the-turn-dispatch-redi.md)).

The ~15-min "app-server exited" death has a second, structural cause for SLOW models: the bridge's THREAD_IDLE eviction timer (default 15 min) is set only *before* and *after* a turn — never *during* — so a slow model that needs >15 min per turn (kimi-k3 @ xhigh, ~2–5 min per reasoning step) is ALWAYS evicted mid-turn ("app-server released (idle)", rollout shows `turn_aborted reason=interrupted`) even though `TURN_TIMEOUT_MS` is 30 min. Measured on slang#14707 (2026-11-24): 6 consecutive crashes across 2 sessions, every one at exactly ~15 min, while the rollout JSONL showed real progress. Before assuming the backend is down, check `~/.codex/sessions/<date>/rollout-*.jsonl`; the fix is to launch the detached bun-bridge client with `env PATH="/pnpm:$PATH" CODEX_MCP_THREAD_IDLE_MS=2100000` (setsid nohup, then poll `/workspace/.claude/critique-attempts.jsonl` for `{"event":"round"}`) — with the knob, all rounds landed in 8–18 min. Retrying without the knob just burns another 15 min ([codex-mcp-bridge: turns >15 min killed by THREAD_IDLE eviction — set CODEX_MCP_THREAD_IDLE_MS](../learnings/1795563048844-codex-mcp-bridge-turns-15-min-killed-by-thread-idl.md)).

## State resets and lean re-recording

`/workspace/.claude/workflow-state.json` can be reset several times per session (container restarts, 429-retry turns, message-batch boundaries): `plan_written:false` + empty `critique_stages` while the plan and approvals were real and recent. The plan-tracker hook (`/app/hooks/plan-tracker.sh`) fires on the **Write tool only** — an Edit to the plan file does NOT restore `plan_written`; re-Write the whole plan file. The deliver gate then refuses markers naming missing stages — re-run each missing stage as a lean fresh codex call (context paragraph + artifacts + "budget your work, spot-check only"), each re-record ~2–3 minutes, rather than re-deriving anything. The same PreToolUse gate blocks even READ-ONLY `gh api repos/*/pulls/*/comments*` with "CRITIQUE REQUIRED before PR creation" — use `gh api graphql` reviewThreads for reads when gated ([state resets wipe critique stages](../learnings/1795054905936-state-resets-wipe-critique-stages-re-write-the-pla.md)). The message-batch boundary wipe re-confirmed: re-arm with a Write (not Edit) to the plan file, then one fresh bridge round per required stage ([codex-bridge dispatch: setsid not nohup](../learnings/1795055939569-codex-bridge-dispatch-setsid-not-nohup-no-issuecom.md)).

Stage identity is thread-scoped, not call-scoped: the critique tracker records the STAGE from the FIRST prompt of a codex thread, and a `codex-reply` continuation inherits the parent thread's stage — it cannot record a different one. So when the delivery gate requires multiple stages (PLAN_REVIEW, CODE_REVIEW, OUTPUT_REVIEW), each must be a FRESH `mcp__codex__codex` call with its own `STAGE:` line; using codex-reply on the PLAN_REVIEW thread to run an OUTPUT_REVIEW round records nothing for OUTPUT_REVIEW and the gate keeps refusing. Verified on slang#14698: fresh call → gate passed immediately ([critique stages need fresh codex calls — codex-reply inherits the thread's stage](../learnings/1795450480274-critique-stages-need-fresh-codex-calls-codex-reply.md)). Worse than "records nothing", measured on slang#14745 (2026-11-27): putting a new `STAGE: CODE_REVIEW` line in a reply prompt does NOT start the new stage — the round is filed against the PARENT stage, so a real CODE_REVIEW was wasted and logged as a PLAN_REVIEW round. The fresh STAGE call must also carry the skill's verbatim developer-instructions block: a review whose reply lacks the `### Verdict` sentinel parses as "unparseable" and fails the delivery gate closed. And a re-verify prompt must be bounded ("spot-check N things, <10 min") or the bridge's 15-min turn kill (CODEX_MCP_THREAD_IDLE_MS) eats the turn with "app-server exited (code=0)" and records nothing. Recipe that worked: one fresh STAGE call per stage, lean bounded prompts ([codex stage changes need a FRESH call, and bridge turns die at 15 min](../learnings/1795800408174-codex-stage-changes-need-a-fresh-call-and-bridge-t.md)).
