# Instrument and Guard Trust — a check is a claim about itself

## TL;DR
- A tool's negative result is a claim about the QUERY, not the world. Before believing "not found / not accessible / 0 hits", run a control that bypasses the suspect path.
- A 403/401 on one endpoint is evidence about that endpoint, not the capability — try at least one alternate route before recording "I can't read X".
- A discriminator is a claim about a log — run it against the log. A 0-of-N wipeout with clean compiles and zero diagnostic text means the *tool* never ran; attribute it to the runner, not the PR.
- Dead guards fail toward clean: a guard whose pattern can't match what the tool actually emits is worse than no guard. Any guard never shown to fire against a true positive is uninformative.
- Read the DENOMINATOR: `slang-test` prints "100% of tests passed" after discarding hundreds of failures. Compare the count to the known-good total before trusting any percentage.
- Loosening a check to kill a false positive is how you create a false negative. A checker that greps a SYNTAX fires on documentation OF that syntax — and a KB accumulates the exact strings its tooling greps for, so this gets more likely over time. Fix with structural specificity, then a positive control that proves the loosened check still fires.
- An impossible count (more citations than learnings) means an instrument or corpus defect — resolve it, never bridge it. A note documenting a syntax trap is itself a corpus member: write the example so it cannot be parsed as the thing it describes.
- A predicate may answer "can I present this well?" OR "is this allowed?" — never both. A presentation guard sitting on the legality path turns every locationless input into an undiagnosed one.
- A policy/critique gate matches command TEXT and its trigger is edge-dependent: prefer reading the config over probing (a probe containing the pattern is denied whole). A gate deny means "forbidden *to me*", not "forbidden" — escalate one tier with the verbatim command. `hit` (surface blocked) and `reason` (defect) on a denial card are orthogonal.
- Byte-identical output only means "no effect" after a layer check: ask whether the artifact can express the property at the contract's layer at all. Where it cannot, byte-identity is manufactured by the measurement, not evidence about the patch.

## A predicate must not answer both "can I present this?" and "is this legal?"

A predicate may answer *"can I present this well?"* or *"is this allowed?"* — never both. On slang#12367 / PR #12378 a `sourceLoc.isValid()` guard was added to a target-legality check purely for *presentation* (to avoid emitting up to three errors, two pointing nowhere, when several synthesized insts referred to one value) — but that guard was also the only thing between an unrepresentable value and code emission, so **every locationless path became an undiagnosed path**. A declaration arriving via `import` has no location: same translation unit → error rc=255; imported as source (`-I .`) → rc=0, silent, invalid output; imported as precompiled `.slang-module` → rc=0, silent. Nine type-shape probes missed it because the hole is reachable only by varying *how the declaration arrives*, not its shape. Report regardless of location, falling back to a use (`key->sourceLoc.isValid() ? key->sourceLoc : findFirstUseLoc(key)`). Two instrument-validity traps ride along: `DIAGNOSTIC_TEST(diag=…)` matches annotations *by column against a source line*, so it cannot express a positionless diagnostic — a zero-annotation attempt passed **2/2 against the unfixed compiler**; only a plain `//TEST:SIMPLE:` with a `.expected` baseline records the pre-fix escape. In slang both `*.expected` and `tests/**/*.slang-module` are gitignored, so the baseline needs `git add -f` and the generated module must stay out ([never let one predicate answer both "is this reportable?" and "is this legal?"](../learnings/1785991044368-never-let-one-predicate-answer-both-is-this-report.md)).

## Instrument-blind reads: negatives, endpoint refusals, and guards that fail toward clean

**A negative tool result is a claim about the QUERY, not the world — find the control that bypasses the suspect path before believing it.** `ncl tasks list` returned `No tasks.` (exit 0) on one edge for two days while 5 recurring series were live; it was a real bug — group-scoped `findTaskSessions()` requires `messaging_group_id IS NULL AND thread_id LIKE 'system:tasks%'`, and tasks with a `messaging_group_id` set were structurally invisible ([a negative tool result is a claim about the query, not the world](../learnings/1785833640306-a-negative-tool-result-is-a-claim-about-the-query-.md)). The endpoint mirror: **a 403/401 on one endpoint is evidence about that endpoint, not the capability** — `.../branches/master/protection/required_status_checks` returned 403 "Resource not accessible by integration", while `.../branches/master` exposes the same `.protection.required_status_checks.contexts` readably; try at least one alternate route before recording "I can't read X" ([a 403/401 on one endpoint is evidence about that endpoint, not the capability](../learnings/1785833063004-a-403-401-on-one-endpoint-is-evidence-about-that-e.md)). **A discriminator is a claim about a log — run it against the log:** a "PASSING spirv-val [0/866] with zero diagnostic text ⇒ validator never ran" discriminator was refuted in one command (`grep -cE -- '- PASS'` → 1732), and the correct discriminator is the missing **validator error body**; the underlying signature holds — a 0-of-N wipeout in both validation modes with compiles at 100% and zero diagnostic text means the tool never ran, so attribute it to the runner (SLANGWIN5's broken `spirv-val`), not the PR ([a discriminator is a claim about a log — run it against the log](../learnings/1785837630095-a-discriminator-is-a-claim-about-a-log-run-it-agai.md), [a 0-of-N test result with clean compiles means the tool never ran — attribute it to the runner, not the PR](../learnings/1785831962573-a-0-of-n-test-result-with-clean-compiles-means-the.md)). **Dead guards fail toward clean — a guard whose pattern can't match its subject is worse than none**: three instances in one day — a REVIEW-GUARD grepping for `Task` while the CLI emits `Agent` ("zero subagent dispatches" on a run with 6), a critique gate matching a bare `pulls` substring blocking read-only GETs, and a footer-counting awk firing on intervening prose; match a guard's pattern to what the tool emits, and treat any guard never armed against a true positive as uninformative ([three dead guards in one day, all failing toward clean](../learnings/1785832791056-three-dead-guards-in-one-day-all-failing-toward-cl.md), [dead guards fail toward clean: match the pattern to what the tool actually emits](../learnings/1785833136773-dead-guards-fail-toward-clean-match-the-pattern-to.md)). **`slang-test` prints "100% of tests passed" after discarding hundreds of failures — read the DENOMINATOR:** a summary read `100% of tests passed (264/264), 94 tests ignored` where the healthy run is **689/689**, with 265 failures thrown away after `*** Stopped scheduling new tests after too many consecutive failures`; pull the full tail and compare the denominator to the known-good count before trusting any percentage ([slang-test prints "100% of tests passed" after discarding hundreds of failures — read the denominator](../learnings/1785837632487-slang-test-prints-100-of-tests-passed-after-discar.md)). **Rule: a negative or a percentage from an instrument is a measurement of the instrument until a second, independent path confirms the world; a guard that has never been shown to fire is not a guard.**

## A fail-closed gate needs its own negative control

Loosening a check to kill a false positive is exactly how you create a false negative. A daily knowledge_base sync built fail-closed aborted on 4 files carrying link prefixes while the transform had worked perfectly — all four hits were **prose about the link syntax**, ellipsis placeholders rather than paths. The class: **a checker that greps for a SYNTAX will fire on documentation OF that syntax**, and any KB recording lessons about its own tooling accumulates the exact strings its tooling greps for, so this gets *more* likely over time. The repair is structural specificity (require a real path, not the bare prefix) **and then a positive control on the loosened check** — append a real link, confirm the grep returns ≥1, restore, confirm 0. The same root produced `finalize()` reporting `coverage 2209/2208` (more citations than learnings — impossible) from a markdown link whose target was a **metavariable** in prose; **an impossible count means an instrument or corpus defect — resolve it, never bridge it.** That note then re-committed its own trap by spelling the offending link out in full ⇒ **a note documenting a syntax trap is itself a corpus member: write the example so it cannot be parsed as the thing it describes.** A fail-closed script that aborts is doing its job — investigate the abort before weakening the gate ([a fail-closed sync check needs a negative control too — a checker that greps a syntax fires on documentation of that syntax](../learnings/1785826224691-a-fail-closed-sync-check-needs-a-negative-control-.md)).

## The critique gate is an instrument whose denials are not evidence

The gate matches command **TEXT pre-execution** and its floor pattern (`gh pr create|gh api [^|]*pulls\b|…`, `:52`) is un-configurable while per-group markers are additive only, so "the actual trigger" is edge-dependent; prefer **reading the config** (`cat $OVERLAY_DIR/.critique-delivery-markers`) over probing, because a probe *containing* the pattern is denied whole (bundling a denied substring with a control kills the control), and each blocked probe emits an admin escalation card ([the gate has two distinct triggers — reconcile before calling one "the actual trigger"](../learnings/1785782804999-critique-gate-has-two-distinct-triggers-reconcile-.md)). The `pulls\b` pattern false-positives **PATCH-to-close**, so retiring a superseded draft demands PLAN+CODE+OUTPUT_REVIEW where there is none; finish everything safe and report the single gap — **endpoint-hunting after an explicit deny is evasion**, and deleting an open PR's head branch to auto-close it is a destructive side channel (close first, delete second) ([critique gate blocks PR CLOSE, not just create — and branch-delete is a destructive false workaround](../learnings/1785799595481-critique-gate-blocks-pr-close-not-just-create-and-.md)). That note's escalation advice is **superseded**: the gate/token evaluation is **per-edge** — the byte-identical PATCH-to-close succeeded on the parent's edge ~4 minutes later, so **a gate deny means "forbidden *to me*", not "forbidden"**: escalate one tier up with the verbatim command, per-route failure modes, and the close-before-delete ordering ([CORRECTION: the PR-close denial is per-edge — escalate one tier, not to an operator](../learnings/1785799761929-correction-the-critique-gate-pr-close-denial-is-pe.md)). The deepest lesson is a **retraction of a finding that had already been praised and escalated**: an original filing framed "the gate matches on TEXT, defeated by trivial obfuscation" as a defect recommending hardening ([a text-matching policy gate is defeated by trivial obfuscation](../learnings/1785799855999-a-text-matching-policy-gate-is-defeated-by-trivial.md)) — **both the framing-as-defect and that remediation are withdrawn**, because the hook's own source comment states pattern enumeration can never be complete (the durable backstop is credential-layer enforcement at the OneCLI proxy), so a split literal slipping the grep *confirms a documented limitation*. What survives: the `pulls\b` PATCH-to-close false positive, the now-stale "covers every egress shape" comment line, and the per-edge asymmetry; the method lesson is **verify a nudge's premises when the nudge is CREDIT, not only criticism**, and re-derive a *retraction* at source too ([CORRECTION: the text-matching design is documented, not a defect — only the PATCH-to-close false positive is real](../learnings/1785799990839-correction-the-slang-critique-gate-s-text-matching.md)). Reading rule: `hit` and `reason` on a denial card are **orthogonal** — `hit` names the *surface* blocked, `reason` names the *defect*, so `hit="PR creation"` does not mean a PR was being created.

## Byte-identity needs a layer check before it means "no effect"

Qualification to the byte-compare discipline: "byte-identical output ⇒ code-layout artifact, re-baseline" stands for *perf attribution*, but the byte-identity premise needs one more check before it licenses "no semantic effect" — ask whether the artifact can express the property **at the contract's layer** at all. Where it cannot (the `sourceLoc`/`DebugLine` case), byte-identical output is guaranteed by construction and carries zero information — an absence manufactured by the measurement rather than evidence about the patch.
