# Slang Compiler Frontend and Semantic Checking

This page covers front-end mechanics that run before IR: the capability contract (`-capability` vs `[require]`), the lexer's escape-decode layering, semantic-checker synthesis of hidden storage members, AST expression classification order, and modifier-list ordering. The recurring discipline: fix the producer, not the consumer; test the most-derived type first; and verify ordering/precedence empirically because static reads of the AST types mislead.

## TL;DR
- `-capability` affects only stage-2 target-compatibility checking, NOT stage-1 function self-consistency; public functions must declare `[require(...)]` explicitly and the flag cannot widen that declaration.
- Dropping a `[require]` capability is a **SILENT runtime-divergence** (SS-class) that only hits codegen-DECISION caps (path selection, SPIR-V versioning); usage-driven caps are unaffected.
- "Cooked capability set identical ⇒ inert" does NOT hold: five files read the raw `getArray(CompilerOptionName::Capability)` outside `getTargetCaps()`, and `maybePromoteDescriptorHandleCapability` can flip `descriptor_handle` auto-promotion on no-`Profile` targets (metal/cuda/wgpu/cpu). The promotion changes accept/reject, diagnostics, and CUDA RT emission (not sizing), and it sticks to the session's `TargetRequest`. Measure what the mechanism actually mutates.
- `MemoryScope` enum + IR attribute + coherent-buffer emit wiring already exist, but atomics hard-code `SpvScopeDevice`; exposing atomic scope is pure plumbing.
- Escape **validation** must ride the **decode layer** that interprets escapes, not the token scan pass — so consumers that opt out of interpretation (`#include` file-name paths, where `\` is a path separator) also opt out of validation.
- A hidden storage member synthesized **after** ctor-signature collection needs its own `initExpr`, or it stays uninitialized in the synthesized ctor.
- `VarExpr`/`MemberExpr`/`StaticMemberExpr` all derive from `DeclRefExpr`: any `as<>`-cascade must test the **most-derived** type first, or `as<DeclRefExpr>` swallows member accesses.
- Slang builds the modifier list in **reverse declaration order**, so `findModifier<T>()` returns the **last-written** attribute; verify "which duplicate wins" empirically.
- Modern-syntax `var`/`let`/param leading modifiers stay on the decl and never reach the type (`parseModernVarDeclBaseCommon` uses plain `ParseTypeExp`), so `row_major var v: float2x3[2]` silently keeps the default layout and `row_major var x: int` gets no E39026 (pre-existing since ≤2025.1). Fix at the parser: thread the modifiers into the type parse.
- A `true` from `doFunctionSignaturesMatch` both rejects a second body (E30201) AND silently merges a body-less prototype with its definition; calls bind to the prototype's types, the body lowers with its own. Any widening of the predicate must be tested on the prototype + mismatched-definition shape (pointers ICE on SPIR-V/Metal).
- Decl placement is validated twice: the parser's exact-type `isDeclAllowed` (E30102, a parse error that stops compilation) and the looser subclass-based checker table `validateDeclNesting` (E31400). Moving a case between them changes coverage, not just the message.
- After merging master into a PR that splits an enum, grep for new `==`/`!=` comparisons on it: those compile cleanly but can change overload identity (E39999), unlike `case` labels.
- The ICE "unknown type modifier in semantic checking" (E99999) is `checkTypeModifier`'s catch-all: the parser puts every leading modifier in a type position on the type, so any decl modifier there (`override`, `static`, `public`, `inline`, `inout`, `precise`) hits it. The fix shape is E31201 `ModifierNotAllowed`; dedup new reports against #13336/#10239/#10306.

## Capability System: `-capability` vs `[require]`

The `-capability` command-line flag only affects target-compatibility checking (stage 2), not function self-consistency checking (stage 1). Public functions must declare `[require(...)]` explicitly; the flag cannot widen that declaration ([Slang `-capability` does not silence 'use of undeclared capability' — it's a per-function contract](../learnings/1779907427493-slang-capability-does-not-silence-use-of-undeclare.md)).

The `[require]` attribute dropping capabilities is a silent runtime-divergence (SS-class severity): the missed-emit causes runtime-divergent behavior for capabilities that gate codegen decisions like path selection and SPIR-V versioning, while usage-driven caps are unaffected ([slang#11631 severity: [require]-drop is a SILENT runtime-divergence (SS-class), and only hits codegen-DECISION caps](../learnings/1781686744418-slang-11631-severity-require-drop-is-a-silent-runt.md)).

**The requested-capability array has readers OUTSIDE `getTargetCaps()`, so "the cooked set is identical ⇒ inert" does not hold.** `TargetRequest::getTargetCaps()` has always silently dropped a requested capability that `isIncompatibleWith` the target (the E36121 consequence is on the diagnostics catalog page), but **five** files read `targetOptionSet.getArray(CompilerOptionName::Capability)` *directly*: `slang-target.cpp` (the cooking walk itself), `slang-check-shader.cpp:2485` (#11225's `checkCapabilities`, the E36121 emitter — its input is the *requested* array, i.e. the `-capability`/API request path, so an in-source `[require]` never enters it and is not a second fix site), `slang-options.cpp:4515,4582`, plus the two that bite. `maybePromoteDescriptorHandleCapability()` (`slang-type-layout.cpp:3549`) scans the raw array for `specificCapabilityRequested`, and at `:3559` `if (!specificProfileRequested && !specificCapabilityRequested)` calls `addUnexpandedCapabilites(CapabilityName::descriptor_handle)` + `setTargetCaps()` — so **removing** an array entry can flip that boolean and switch auto-promotion ON. That is exactly what a downstream guard on an unconditional `hlsl_nvapi` request did (exposure: metal/cuda/wgpu/cpu — the device types given no `Profile`; where a profile IS set, `!specificProfileRequested` short-circuits the predicate entirely, and reachability is further bounded by the helper firing only from the two `DescriptorHandleType` arms of type layout). Two scope limits recorded in the same correction, both of which would otherwise produce a false null: the promotion mutates only the **capability set**, so its observable effects are accept/reject, diagnostics and capability-gated emission (the CUDA RT break below), and **not sizing** — `DescriptorHandle<T>`'s layout is chosen at `slang-type-layout.cpp:5669` by `implies(spvBindlessTextureNV)` → `uint64`, else `areResourceTypesBindlessOnTarget` → layout of `T`, else `uint2`, none of which reads `descriptor_handle`; and `slang-ir-layout.cpp:449` *does* size off a raw-array scan but keys on a **different atom** (`spvBindlessTextureNV`), so it is not this mechanism (two mechanisms sharing one call site are not one mechanism). Practical rule: an A/B comparing **layout or size** across the guard's arms shows no difference either way, so derive the measurement from what the mechanism actually mutates (accept/reject on a no-profile target) and prove the arms differ observably *at all* before trusting a null ([CORRECTION — both-arms-inert was scoped to the cooked capability set only; the raw Capability array is read outside getTargetCaps()](../learnings/1785751609559-correction-both-arms-inert-was-scoped-to-the-cooke.md)).

**Confirmed consequence: the promotion breaks CUDA ray-tracing emission, and it is session-sticky.** The effect of `maybePromoteDescriptorHandleCapability` is not limited to accept/reject and diagnostics. On Slang 2026.18 and 18.3 (`slang-type-layout.cpp:3557`), when a `DescriptorHandle` type is laid out on a target with no profile AND no raw Capability entry, the helper adds `descriptor_handle = glsl_spirv | _sm_6_6 | cpp | cuda | metal | wgsl` unexpanded onto the target caps. After that, a CUDA/OptiX closest-hit shader emits the bare HLSL name `BuiltInTriangleIntersectionAttributes` with no `struct BuiltInTriangleIntersectionAttributes_0` declared, and nvrtc reports the identifier undefined. An explicit `-capability descriptor_handle` does NOT break, so the fault is in how the promotion merges the alias. Repro: `slangc rt_dh.slang -target cuda -entry closest_hit -stage closesthit -g` with no `-profile` and no `-capability`; adding any single `-capability` (cuda, hlsl_nvapi, descriptor_handle) fixes it. The promotion mutates the session's `TargetRequest`, so an earlier, unrelated module that uses `DescriptorHandle` breaks later RT programs in the same session (verified with an API harness). This is the exposure predicted above, now observed: slangpy's cuda/metal/wgpu/cpu sessions have no profile, so the old unconditional session-level `hlsl_nvapi` entry was silently suppressing the promotion, and removing it (slangpy#1088) surfaced the break in `test_cluster_acceleration_structure_trace[cuda]`. Removing a "stray" capability entry can change behaviour on profile-less targets with no diagnostic; A/B-test on cuda with a `DescriptorHandle` in the session ([descriptor_handle auto-promotion breaks CUDA RT emission on profile-less sessions, session-sticky](../learnings/1790706580325-slang-descriptor-handle-auto-promotion-breaks-cuda.md)).

## MemoryScope Machinery Exists but Is Unwired

Slang already has a `MemoryScope` enum, an IR attribute, and coherent-buffer emit wiring, but all atomic operations hard-code `SpvScopeDevice`. Exposing atomic scope would be pure plumbing (add an `IRMemoryScopeAttr` decoration to atomic insts) reusing the existing representation ([Slang MemoryScope machinery exists but is unwired to atomics (issue #6970)](../learnings/1782215139629-slang-memoryscope-machinery-exists-but-is-unwired-.md)).

## Lexer: Escape Validation Belongs in the Decode Layer, Not the Scan Pass

Escape-sequence *interpretation* in the Slang lexer is deferred and context-dependent: `getStringLiteralTokenValue` decodes escapes for real string values, but `getFileNameTokenValue` returns the **raw** quoted content and deliberately never processes escapes (`\` is a valid Windows path separator). Regression #11829 landed because PR #11714 added escape *validation* (`\u`/`\U` digit-count → E10007/E10008) into the token **scanning** pass, making it universal before a token's downstream role is known — so it fired on `#include "dir\utility\f.slangh"` paths. The principle: escape *validation* must ride the decode layer that interprets escapes, so consumers that opt out of interpretation (file-name paths) also opt out of validation ([Lexer escape-validation must be deferred to the decode layer, not the scan pass (#include paths opt out)](../learnings/1782799753646-lexer-escape-validation-must-be-deferred-to-the-de.md)).

## Synthesized Member Storage Added After Ctor-Signature Collection Needs Its Own `initExpr`

When the front-end synthesizes a hidden storage member **after** the constructor signature is collected — e.g. the bitfield backing word `$bit_field_backing_N` created in `SemanticsDeclAttributesVisitor` — that member needs its own `initExpr`, otherwise it is left uninitialized in the synthesized ctor ([Synthesized struct storage added after ctor-signature collection needs its own initExpr](../learnings/1782847970010-synthesized-struct-storage-added-after-ctor-signat.md)). Related: the `IDefaultInitializable` synthesis loop is off for bitfield structs, and a raw literal beats `DefaultConstruct` for backend-robust zero-init ([Slang synthesized-member init: IDefaultInitializable loop is off for bitfield structs; raw literal beats DefaultConstruct for backend-robust zero](../learnings/1782847433081-slang-synthesized-member-init-idefaultinitializabl.md)).

## AST Expr Classification: Order `as<derived>` Before `as<base>`

In `source/slang/slang-ast-expr.h`, `VarExpr`, `MemberExpr`, and `StaticMemberExpr` all derive from `DeclRefExpr` (and `DerefMemberExpr` from `MemberExpr`); `IndexExpr` derives directly from `Expr`. Because `as<Base>` matches a derived instance, any `as<>`-cascade that classifies expressions **must test the most-derived type first** — putting `as<DeclRefExpr>` before `as<MemberExpr>` makes the MemberExpr branch dead code and swallows every member access, seeing only the field's own `declRef` and losing the base object. This was the exact ordering bug behind the E30051 false-positive alias in `_exprsDefinitelyAlias` (`slang-check-expr.cpp`, introduced by PR #11151): `a.x` and `b.x` were judged to alias because both name field `x` ([Slang AST: MemberExpr/VarExpr/StaticMemberExpr derive from DeclRefExpr — order as&lt;derived&gt; before as&lt;base&gt;](../learnings/1782898009300-slang-ast-memberexpr-varexpr-staticmemberexpr-deri.md)). Triage technique: when static reading of the AST-node types contradicts observed behavior, run cheap empirical discriminators (same field / different base vs. different field / same base) before trusting your read — and note `-dump-ast` is unmaintained.

## Modifier List Is Reverse-Declaration Order; `findModifier` Returns the Last-Written Attribute; Type-Position Modifiers ICE

`findModifier<T>()` (`slang-ast-base.h:737`) returns the *first* element of the decl's modifier linked list, but Slang builds that list in **reverse declaration order** — so first-in-list is the **last-written** source attribute. Empirically, three stacked `[numthreads(...)]` attributes emit the LAST one's `LocalSize`, so any "which duplicate/conflicting modifier wins" reasoning must be verified empirically, not assumed from source order ([Slang stores modifiers in reverse-declaration order; findModifier returns the last-written attribute](../learnings/1782905768996-slang-stores-modifiers-in-reverse-declaration-orde.md)). Related (issue #11881): duplicate `[numthreads]` is genuinely undiagnosed because `NumThreadsAttribute` is absent from `getModifierConflictGroupKind()` (falls to `default: NodeBase`), so the duplicate-modifier loop never fires; adding a `case ASTNodeType::NumThreadsAttribute` reuses the existing error E31202 — but watch the layout-synthesized `NumThreadsAttribute` added after the conflict loop.

The same list is fragile inside `SemanticsVisitor::checkModifiers` (`slang-check-modifier.cpp`), whose loop unlinks each modifier (`modifier->next = nullptr`) before calling `checkModifier`. Memory qualifiers (`readonly`, `writeonly`, `coherent`, …) fold into ONE `MemoryQualifierSetModifier` that `checkModifier` finds via `syntaxNode->findModifier<MemoryQualifierSetModifier>()`, so swapping one modifier for another inside the loop (e.g. `ReadOnlyModifier` → `GLSLReadOnlyModifier`) hides the set built for the earlier qualifier; a second set is created and the core module fails with E31202 "duplicate modifier" on `readonly writeonly` in glsl.meta.slang. Do such a substitution by splicing into `syntaxNode->modifiers` before the loop ([checkModifiers: substitute a modifier IN the list, not in the loop](../learnings/1791337734435-slang-checkmodifiers-substitute-a-modifier-in-the-.md)).

The parser also decides where modifiers land, and one consequence is an ICE family. Whenever a type is parsed with `ParseType()` → `_parseTypeSpec(parser)` (`slang-parser.cpp:3694`), ALL leading modifiers go onto the type as a `ModifiedTypeExpr`, deliberately ("we rely on downstream semantic checking", comment at `:3437-3442`). `SemanticsExprVisitor::checkTypeModifier` (`slang-check-expr.cpp:9560`) accepts only unorm/snorm/no_diff/const/volatile (matrix layout is handled by the caller), and its catch-all `else` (`:9594-9601`) reports `Diagnostics::Unexpected` (E99999, "unknown type modifier in semantic checking"). So `property override float3 X`, `let x : static float`, `typealias T = public float;`, `S<override float>`, `func f() -> inline float` and `(override float)i` all hit the same ICE. The natural replacement is `Diagnostics::ModifierNotAllowed{.modifier = modifier}` (E31201), which is what `override property` already reports. Open issues on this one branch: #13336 (property), #10239 (`func f(x: inout int)`, documented-valid syntax that needs a parser fix instead), and #10306 (`typedef precise int`, `-lang hlsl`); check a new "unknown type modifier" report against those three before retriaging it [unknown type modifier ICE = checkTypeModifier catch-all](../learnings/1790727973088-slang-ice-unknown-type-modifier-in-semantic-checki.md).

Modern-syntax declarations are the mirror-image gap: their leading modifiers never reach the type at all. `parseModernVarDeclBaseCommon` (`slang-parser.cpp`) parses `: Type` with plain `ParseTypeExp`, while leading modifiers arrive either through `ParseDeclWithModifiers` (`parser->pendingModifiers`, attached later by `CompleteDecl`) or through `parseModernParamDecl`'s `decl->modifiers`, so they stay on the decl and never become a `ModifiedTypeExpr`. The only applier left is `maybeApplyLayoutModifier` (`slang-check-decl.cpp`), which handles a bare matrix only. So `row_major var v: float2x3[2]` (and the cbuffer, global, 2-D and `func f(uniform row_major v: float2x3[2])` forms) silently keeps the default layout, and `row_major var x: int` gets no E39026. It is not a #12992 regression: the same counts reproduce on 3e98d9563, v2026.19 and v2025.1. The prototyped producer fix (+12/−6, #13390) gives `parseModernVarDeclBaseCommon` an optional `Modifiers*` (`pendingModifiers` for var/let, `&decl->modifiers` for `ModernParamDecl`) and parses the type with #13384's `_parseTraditionalParamTypeExpr`, which grafts `MatrixLayoutModifier` onto the atomic type before the postfix `[N]`. Regression time-travel tip from the same work: `git checkout <sha>` in an existing built worktree plus an incremental `cmake --build build --config Release --target slangc` (~10 min for ~30 files of drift) is far cheaper than a fresh worktree, and snapshot binaries with `cp -a build/Release/{bin,lib}` because slangc loads `libslang-compiler.so` from `../lib` [leading modifiers on modern var/let/param never reach the type expression](../learnings/1790931602247-leading-modifiers-on-modern-syntax-var-let-param-n.md).

Fixing the producer applies to the parser too, and it decides which test suite must run. Changing the parser or AST (especially building new `Expr`/AST nodes) requires running `tests/language-server/` locally, not just `tests/diagnostics` + `tests/compute`: the language-server robustness tests feed malformed/partial source (e.g. `robustness-4.slang` is literally `[]`) and require the server to survive without crashing — a change clean on well-formed input can still crash on malformed input (#12674 was green locally on diagnostics+compute but failed 13 language-server tests in CI). The producer fix: `Parser::ReadToken(TokenType::Identifier)` on a mismatch returns the *mismatched* token WITHOUT advancing, so building a node from it (`varExpr->name = tok.getName()`) yields a null-named node that later crashes `CheckTerm`/lookup — guard construction on `tok.type == TokenType::Identifier` and leave the node null so downstream takes its null-safe path (similarly guard `parser->currentModule` before `->ownedScope` on the reflection/string-parse path, which `parseTermFromSourceFile` never sets). And know the harness: `slang-test -use-test-server` reuses server processes across tests, so ONE crashing test fails every other test on that server — a broad, non-deterministic, cross-platform failure set usually traces to a single crash; isolate by running suspects one at a time and find the one that fails *deterministically in isolation* ([parser/AST changes must run tests/language-server — malformed-input crashes + shared-server collateral](../learnings/1789271917061-parser-ast-changes-must-run-tests-language-server-.md)).

## Parser: Decl-vs-Statement Cannot Be Disambiguated Lexically

A lexical rule for "is this a statement vs a declaration" is **unsound** in Slang (from the #13208 design investigation, `slang-parser.cpp` @ HEAD 0d06f4bd0). Neither "identifier immediately followed by `(`" nor "leading statement keyword" is safe evidence — all of these are valid *declarations* at file/struct scope: `float(x);` (a variable decl via a parenthesized declarator, `_parseSimpleTypeSpec`→`parseDirectAbstractDeclarator`), `__init(...)`/`__subscript(...)` (declaration syntax beginning `ident(`), `syntax ctor = __init;` then `ctor(...)` (a user syntax alias, consulted before the declarator fallback), and `struct if {}; if(x);` (keywords are contextual/shadowable). So disambiguation must be a genuine **declaration parse attempt**, not a token pattern — which also refines the narrower "any call-shaped `ident(...)` at global scope is never a declaration" heuristic used to detect a top-level `static_assert(`. Critically, "build the decl but don't add it" is NOT non-committing: declaration parsing mutates shared state well before `CompleteDecl`/`AddMember` (namespaces add members, buffer parsing adds a scope member, modifier parsing can bump the module language version), so a speculative decl probe must be a truly side-effect-free recognizer or a parse whose entire pre-completion mutation set is transactionally rolled back — the existing cursor-snapshot sites (`getCursor`/`setCursor`) only ever parse **expressions**, not declarations. Architecture map: a two-stage parse — `ParsingStage::Decl` parses file scope + aggregate bodies eagerly, while function bodies are captured as `UnparsedStmt` and re-parsed on demand in `ParsingStage::Body` (so semantic-state disambiguation exists only in the Body stage); `ParseStatement`'s cursor-snapshot guess-then-commit is a SEPARATE loop from the shared decl-only loop (`parseDecls`→`ParseDecl`→`ParseDeclWithModifiers`), and `ParseStatement` has no decl-only-vs-decl-or-statement flag — that is the seam any "declaration-or-statement(context)" refactor introduces. The accept-then-diagnose precedent (`CompleteDecl`→`DeclNotAllowed`; the richer `DeclNotAllowedInContext` via `validateDeclNesting`) is Decl-only, and there is no Stmt-carrying-Decl node (`UnparsedStmt` is Stmt-only) ([parser: decl-vs-statement can't be disambiguated lexically; needs a side-effect-free declaration probe](../learnings/1790107330312-slang-parser-decl-vs-statement-can-t-be-disambigua.md)).

## Two Decl-Nesting Validators: Parser E30102 Masks the Looser Checker E31400 Table

Declaration placement is checked twice. The parser's `isDeclAllowed` (slang-parser.cpp ~5550) switches on the exact `ASTNodeType`, allows unknown kinds by default, and reports E30102 (`DeclNotAllowed`). The checker's `validateDeclNesting` (slang-check-decl.cpp ~317, from #10456) classifies by subclass, reports E31400 (`DeclNotAllowedInContext`), and skips decls the parser already marked `nestingAlreadyDiagnosed`. The checker table is the looser one: with the parser check disabled, `__generic<T> int x;`, `using N;` inside a struct, `module`/`implementing` inside a namespace, and an interface `typealias` all pass with no diagnostic, and `__constraint` inside a struct becomes a fatal E40002. Because E30102 is a parse error, it also stops compilation before semantic checking (compile-request.cpp ~833), so a change that moves a case from parser to checker changes both the diagnostic and how far compilation gets. Probe pitfall from the #13499 triage: an env-gated prototype that tests `getenv("X")` treats `X=` (set but empty) as ON, so run the baseline column with `env -u X` [two decl-nesting validators; parser E30102 masks the looser E31400 table](../learnings/1791410610457-slang-has-two-decl-nesting-validators-parser-e3010.md). Why the nesting table could ship as a hard error with no version gate is on [[wiki/concepts/misc-f0909b3-slang-frontend-binding-fixes.md]].

## Eager Local-Generic Conformance Checking Tightens Non-Conformance Diagnostics (#13092)

Fixing a "read-before-checked" crash by driving a function-local generic type to `ReadyForConformances` eagerly (slang#13092: `visitBlockStmt` now drives local `GenericDecl`s whose inner is an `AggTypeDeclBase` through `ensureAllDeclsRec`) has a **wider behavioral footprint than "stop the crash"** — it also makes the compiler **eagerly reject non-conforming local generics**. Verified on both builds with a declared-but-**unused** `struct Bad<V> : IOp { V val; }` (missing `apply`): unfixed compiles clean (exit 0, the local generic's conformance was never checked); fixed emits `error[E38100]: missing interface member` at the declaration. This is principled and consistent — a MODULE-SCOPE non-conforming generic already errors E38100 even when unused, so local generics were the inconsistent gap (the same bug as the crash); the tightening aligns local scope with module scope rather than adding an arbitrary rule. **But** it can break downstream integration builds (e.g. Falcor CI) that harbor a *latent* non-conforming local generic previously accepted only because of the bug — the correct resolution then is to fix the downstream shader, not weaken the compiler fix. Fix-class takeaways: (1) when a fix moves a type into eager conformance checking, always test the **declared-but-unused non-conforming** case on both builds to reveal the diagnostic-tightening footprint; (2) call the footprint out to the maintainer; (3) external integration checks (Falcor) fail opaquely in GitHub `run-external-ci` logs (only "pipeline finished with status 'failed'"), so you cannot self-diagnose — escalate to the maintainer who holds the external-pipeline log ([Filling witness tables for local generic conformances also tightens non-conformance diagnostics (E38100) — downstream break risk](../learnings/1790181214204-filling-witness-tables-for-local-generic-conforman.md)).

## Redeclaration Matching: Loosening `doFunctionSignaturesMatch` Also Merges Prototypes with Mismatched Definitions (#13384)

`doFunctionSignaturesMatch` has one caller, `checkFuncRedeclaration`, and a `true` result does two things. If both declarations have bodies, it reports E30201; if only one does, it silently chains the body-less prototype and the definition into one redeclaration family, and the only follow-up check is on the return type. Calls then resolve against the primary (prototype's) parameter types, because `addOverloadCandidate` skips non-primary declarations, while the body is lowered with the definition's own types. #13384 made the predicate compare parameter types "up to matrix layout" so that two bodies differing only in layout report E30201, which also made `float pick(row_major float2x3 m);` + a `column_major` definition merge. Outcome by shape: arrays and bare matrices (by value or `inout`) are benign (the call converts, CPU values are correct, DXC accepts the same pair); pointers (`float pick(row_major float2x3* p);`) are not, since nothing converts the memory behind the pointer, so the IR call and callee types disagree: E99997 ICE (`slang-ir.cpp:5822 resultType`) on SPIR-V and Metal, downstream type errors on CUDA→PTX and CPU. The #13384 fix adds an explicit E30200 check after the two-bodies check [loosening doFunctionSignaturesMatch also merges a prototype with a mismatched definition](../learnings/1790926235230-loosening-dofunctionsignaturesmatch-also-merges-a-.md) [an "equal up to X" signature relation also merges forward declarations](../learnings/1790931809642-an-equal-up-to-x-signature-relation-also-merges-fo.md).

How to apply: when reviewing any change that widens signature matching, compile a body-less prototype followed by a mismatched definition for every type wrapper the predicate looks through, on a non-HLSL target with `[noinline]`. A reviewer flagged this shape from a source trace as an "unconfirmed gap"; compiling it is what made it a bug. A companion trap in the same PR: when adding a token to a type's mangled name, place it where nesting stays unambiguous — a layout suffix emitted after a matrix's element type made `matrix<matrix<..,RowMajor>,..>` and `matrix<matrix<..>,..,RowMajor>` mangle identically (layout handling in the conversion-cost cache and mangler is on [[wiki/concepts/slang-language-coercion-and-overload.md]]). Tooling note from that review run: the local correctness reviewer again lost all its subagents to the 600 s background-wait ceiling (a 146 B final review), because `compose-and-run.sh` still does not default `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`; always pass it [same](../learnings/1790926235230-loosening-dofunctionsignaturesmatch-also-merges-a-.md).

**A merge can silently change overload identity for a split enum.** When a PR splits an enumerator (`ParamPassingMode::Ref` → `RefReadWrite`/`RefReadOnly`/`RefWriteOnly`) while master replaces a modifier-presence check with an exact mode comparison (#13232: `doFunctionSignaturesMatch` → `_doParamPassingModesMatchForOverload`), the merge compiles cleanly but changes behaviour: a `readonly __ref` declaration and a `__ref` definition became two overloads sharing one mangled name, giving E39999 "ambiguous call". New `case X:` labels on the old enumerator break the build; new `==`/`!=` comparisons do not. So after resolving conflicts, grep master's diff for new comparisons on the split enum, decide each one's category explicitly, and pin it with a test plus a revert drill. To run `slang-static-unit-test` locally, configure a separate `build-static/` with `-DSLANG_LIB_TYPE=STATIC` (and `-DSLANG_SLANG_LLVM_FLAVOR=DISABLE`); the target exists only in a static build [merging master after a refactor can change overload identity of split enum modes](../learnings/1791413169329-merging-master-after-a-refactor-can-silently-chang.md).
