# Slang Compiler Frontend and Semantic Checking

This page covers front-end mechanics that run before IR: the capability contract (`-capability` vs `[require]`), the lexer's escape-decode layering, semantic-checker synthesis of hidden storage members, AST expression classification order, and modifier-list ordering. The recurring discipline: fix the producer, not the consumer; test the most-derived type first; and verify ordering/precedence empirically because static reads of the AST types mislead.

## TL;DR
- `-capability` affects only stage-2 target-compatibility checking, NOT stage-1 function self-consistency; public functions must declare `[require(...)]` explicitly and the flag cannot widen that declaration.
- Dropping a `[require]` capability is a **SILENT runtime-divergence** (SS-class) that only hits codegen-DECISION caps (path selection, SPIR-V versioning); usage-driven caps are unaffected.
- "Cooked capability set identical ⇒ inert" does NOT hold: five files read the raw `getArray(CompilerOptionName::Capability)` outside `getTargetCaps()`, and `maybePromoteDescriptorHandleCapability` can flip `descriptor_handle` auto-promotion on no-`Profile` targets (metal/cuda/wgpu/cpu). The promotion changes accept/reject, diagnostics, and CUDA RT emission (not sizing), and it sticks to the session's `TargetRequest`. Measure what the mechanism actually mutates.
- `MemoryScope` enum + IR attribute + coherent-buffer emit wiring already exist, but atomics hard-code `SpvScopeDevice`; exposing atomic scope is pure plumbing.
- Escape **validation** must ride the **decode layer** that interprets escapes, not the token scan pass — so consumers that opt out of interpretation (`#include` file-name paths, where `\` is a path separator) also opt out of validation.
- A hidden storage member synthesized **after** ctor-signature collection needs its own `initExpr`, or it stays uninitialized in the synthesized ctor.
- `VarExpr`/`MemberExpr`/`StaticMemberExpr` all derive from `DeclRefExpr`: any `as<>`-cascade must test the **most-derived** type first, or `as<DeclRefExpr>` swallows member accesses.
- Slang builds the modifier list in **reverse declaration order**, so `findModifier<T>()` returns the **last-written** attribute; verify "which duplicate wins" empirically.
- Modern-syntax `var`/`let`/param leading modifiers stay on the decl and never reach the type (`parseModernVarDeclBaseCommon` uses plain `ParseTypeExp`), so `row_major var v: float2x3[2]` silently keeps the default layout and `row_major var x: int` gets no E39026 (pre-existing since ≤2025.1). Fix at the parser: thread the modifiers into the type parse.
- A `true` from `doFunctionSignaturesMatch` both rejects a second body (E30201) AND silently merges a body-less prototype with its definition; calls bind to the prototype's types, the body lowers with its own. Any widening of the predicate must be tested on the prototype + mismatched-definition shape (pointers ICE on SPIR-V/Metal).
- Decl placement is validated twice: the parser's exact-type `isDeclAllowed` (E30102, a parse error that stops compilation) and the looser subclass-based checker table `validateDeclNesting` (E31400). Moving a case between them changes coverage, not just the message.
- After merging master into a PR that splits an enum, grep for new `==`/`!=` comparisons on it: those compile cleanly but can change overload identity (E39999), unlike `case` labels.
- The ICE "unknown type modifier in semantic checking" (E99999) is `checkTypeModifier`'s catch-all: the parser puts every leading modifier in a type position on the type, so any decl modifier there (`override`, `static`, `public`, `inline`, `inout`, `precise`) hits it. The fix shape is E31201 `ModifierNotAllowed`; dedup new reports against #13336/#10239/#10306.

## Capability System: `-capability` vs `[require]`

The `-capability` flag only affects target-compatibility checking (stage 2), not function self-consistency checking (stage 1); public functions must declare `[require(...)]` explicitly ([Slang `-capability` does not silence 'use of undeclared capability' — it's a per-function contract](../learnings/1779907427493-slang-capability-does-not-silence-use-of-undeclare.md)). A `[require]` that drops capabilities is a silent runtime divergence (SS-class): the missed emit diverges at runtime for caps that gate codegen decisions (path selection, SPIR-V versioning), while usage-driven caps are unaffected ([slang#11631 severity: [require]-drop is a SILENT runtime-divergence (SS-class), and only hits codegen-DECISION caps](../learnings/1781686744418-slang-11631-severity-require-drop-is-a-silent-runt.md)).

**The requested-capability array has readers OUTSIDE `getTargetCaps()`, so "the cooked set is identical ⇒ inert" does not hold.** `TargetRequest::getTargetCaps()` silently drops a requested capability that `isIncompatibleWith` the target (E36121 is on the diagnostics catalog page), but five files read `targetOptionSet.getArray(CompilerOptionName::Capability)` directly: `slang-target.cpp` (the cooking walk), `slang-check-shader.cpp:2485` (#11225's `checkCapabilities`, the E36121 emitter — its input is the *requested* array, so an in-source `[require]` never enters it), `slang-options.cpp:4515,4582`, and the one that bites. `maybePromoteDescriptorHandleCapability()` (`slang-type-layout.cpp:3549`) scans the raw array, and at `:3559` `if (!specificProfileRequested && !specificCapabilityRequested)` adds `descriptor_handle` and calls `setTargetCaps()` — so **removing** an array entry can switch auto-promotion ON. Exposure: metal/cuda/wgpu/cpu (device types given no `Profile`; a set profile short-circuits the predicate), and only from the two `DescriptorHandleType` arms of type layout. The promotion mutates only the **capability set**, so its effects are accept/reject, diagnostics and capability-gated emission, **not sizing**: `DescriptorHandle<T>` layout (`slang-type-layout.cpp:5669`) picks `uint64` on `spvBindlessTextureNV`, else the layout of `T` if bindless, else `uint2`, never reading `descriptor_handle`; and `slang-ir-layout.cpp:449` sizes off a raw-array scan of a *different* atom (`spvBindlessTextureNV`), so it is a separate mechanism. Rule: a layout/size A/B shows no difference either way; measure what the mechanism mutates (accept/reject on a no-profile target) and prove the arms differ observably at all before trusting a null ([CORRECTION — both-arms-inert was scoped to the cooked capability set only; the raw Capability array is read outside getTargetCaps()](../learnings/1785751609559-correction-both-arms-inert-was-scoped-to-the-cooke.md)).

**Confirmed: the promotion breaks CUDA ray-tracing emission, and it is session-sticky.** On Slang 2026.18/18.3 (`slang-type-layout.cpp:3557`), laying out a `DescriptorHandle` on a target with no profile and no raw Capability entry adds `descriptor_handle = glsl_spirv | _sm_6_6 | cpp | cuda | metal | wgsl` unexpanded; a CUDA/OptiX closest-hit shader then emits the bare HLSL name `BuiltInTriangleIntersectionAttributes` with no `struct BuiltInTriangleIntersectionAttributes_0` declared, and nvrtc reports it undefined. An explicit `-capability descriptor_handle` does NOT break, so the fault is in how the promotion merges the alias. Repro: `slangc rt_dh.slang -target cuda -entry closest_hit -stage closesthit -g` with no `-profile`/`-capability`; any single `-capability` fixes it. Because the session's `TargetRequest` is mutated, an earlier unrelated module using `DescriptorHandle` breaks later RT programs in the same session (API harness). slangpy's cuda/metal/wgpu/cpu sessions have no profile, so its old unconditional `hlsl_nvapi` entry was suppressing the promotion; removing it (slangpy#1088) surfaced the break in `test_cluster_acceleration_structure_trace[cuda]`. Removing a "stray" capability entry can change behaviour on profile-less targets with no diagnostic — A/B on cuda with a `DescriptorHandle` in the session ([descriptor_handle auto-promotion breaks CUDA RT emission on profile-less sessions, session-sticky](../learnings/1790706580325-slang-descriptor-handle-auto-promotion-breaks-cuda.md)).

## MemoryScope Machinery Exists but Is Unwired

Slang already has a `MemoryScope` enum, an IR attribute, and coherent-buffer emit wiring, but all atomics hard-code `SpvScopeDevice`; exposing atomic scope is pure plumbing (an `IRMemoryScopeAttr` decoration on atomic insts) ([Slang MemoryScope machinery exists but is unwired to atomics (issue #6970)](../learnings/1782215139629-slang-memoryscope-machinery-exists-but-is-unwired-.md)).

## Lexer: Escape Validation Belongs in the Decode Layer, Not the Scan Pass

Escape *interpretation* is deferred and context-dependent: `getStringLiteralTokenValue` decodes escapes, but `getFileNameTokenValue` returns the raw quoted content and never processes escapes (`\` is a Windows path separator). Regression #11829 came from PR #11714 adding `\u`/`\U` digit-count validation (E10007/E10008) to the token **scanning** pass, before a token's role is known, so it fired on `#include "dir\utility\f.slangh"`. Validation must ride the decode layer, so consumers that opt out of interpretation also opt out of validation ([Lexer escape-validation must be deferred to the decode layer, not the scan pass (#include paths opt out)](../learnings/1782799753646-lexer-escape-validation-must-be-deferred-to-the-de.md)).

## Synthesized Member Storage Added After Ctor-Signature Collection Needs Its Own `initExpr`

A hidden storage member synthesized **after** the ctor signature is collected — e.g. the bitfield backing word `$bit_field_backing_N` from `SemanticsDeclAttributesVisitor` — needs its own `initExpr`, or it stays uninitialized in the synthesized ctor ([Synthesized struct storage added after ctor-signature collection needs its own initExpr](../learnings/1782847970010-synthesized-struct-storage-added-after-ctor-signat.md)). The `IDefaultInitializable` synthesis loop is off for bitfield structs, and a raw literal beats `DefaultConstruct` for backend-robust zero-init ([Slang synthesized-member init: IDefaultInitializable loop is off for bitfield structs; raw literal beats DefaultConstruct for backend-robust zero](../learnings/1782847433081-slang-synthesized-member-init-idefaultinitializabl.md)).

## AST Expr Classification: Order `as<derived>` Before `as<base>`

In `slang-ast-expr.h`, `VarExpr`, `MemberExpr` and `StaticMemberExpr` derive from `DeclRefExpr` (`DerefMemberExpr` from `MemberExpr`); `IndexExpr` derives from `Expr`. Any `as<>`-cascade must test the most-derived type first: `as<DeclRefExpr>` before `as<MemberExpr>` makes the member branch dead and sees only the field's `declRef`, losing the base object. That was the E30051 false-positive alias in `_exprsDefinitelyAlias` (`slang-check-expr.cpp`, PR #11151): `a.x` and `b.x` "aliased" because both name field `x`. When a static read of AST types contradicts behaviour, run cheap discriminators (same field/different base vs. different field/same base) — `-dump-ast` is unmaintained ([Slang AST: MemberExpr/VarExpr/StaticMemberExpr derive from DeclRefExpr — order as&lt;derived&gt; before as&lt;base&gt;](../learnings/1782898009300-slang-ast-memberexpr-varexpr-staticmemberexpr-deri.md)).

## Modifier List Is Reverse-Declaration Order; `findModifier` Returns the Last-Written Attribute; Type-Position Modifiers ICE

`findModifier<T>()` (`slang-ast-base.h:737`) returns the first element of the modifier linked list, but the list is built in **reverse declaration order**, so it returns the **last-written** attribute: three stacked `[numthreads(...)]` emit the last one's `LocalSize`. Verify "which duplicate wins" empirically. Duplicate `[numthreads]` is undiagnosed (#11881) because `NumThreadsAttribute` is absent from `getModifierConflictGroupKind()` (falls to `default: NodeBase`); a `case ASTNodeType::NumThreadsAttribute` reuses E31202 — but watch the layout-synthesized `NumThreadsAttribute` added after the conflict loop ([Slang stores modifiers in reverse-declaration order; findModifier returns the last-written attribute](../learnings/1782905768996-slang-stores-modifiers-in-reverse-declaration-orde.md)).

The list is fragile inside `SemanticsVisitor::checkModifiers` (`slang-check-modifier.cpp`), whose loop unlinks each modifier (`modifier->next = nullptr`) before `checkModifier`. Memory qualifiers (`readonly`, `writeonly`, `coherent`, …) fold into ONE `MemoryQualifierSetModifier` found via `syntaxNode->findModifier<MemoryQualifierSetModifier>()`, so swapping a modifier inside the loop (e.g. `ReadOnlyModifier` → `GLSLReadOnlyModifier`) hides the earlier set; a second set is created and the core module fails E31202 on `readonly writeonly` in glsl.meta.slang. Splice substitutions into `syntaxNode->modifiers` before the loop ([checkModifiers: substitute a modifier IN the list, not in the loop](../learnings/1791337734435-slang-checkmodifiers-substitute-a-modifier-in-the-.md)).

**Type-position modifiers ICE.** When a type is parsed via `ParseType()` → `_parseTypeSpec` (`slang-parser.cpp:3694`), ALL leading modifiers go onto the type as a `ModifiedTypeExpr`, deliberately ("we rely on downstream semantic checking", `:3437-3442`). `SemanticsExprVisitor::checkTypeModifier` (`slang-check-expr.cpp:9560`) accepts only unorm/snorm/no_diff/const/volatile (matrix layout is the caller's), and its catch-all (`:9594-9601`) reports E99999 "unknown type modifier in semantic checking". So `property override float3 X`, `let x : static float`, `typealias T = public float;`, `S<override float>`, `func f() -> inline float` and `(override float)i` all ICE. The replacement is `Diagnostics::ModifierNotAllowed{.modifier = modifier}` (E31201), as `override property` already reports. Open issues on this branch: #13336 (property), #10239 (`func f(x: inout int)`, valid syntax needing a parser fix) and #10306 (`typedef precise int`, `-lang hlsl`) — check new reports against them [unknown type modifier ICE = checkTypeModifier catch-all](../learnings/1790727973088-slang-ice-unknown-type-modifier-in-semantic-checki.md).

**Modern-syntax decls are the mirror-image gap: leading modifiers never reach the type.** `parseModernVarDeclBaseCommon` parses `: Type` with plain `ParseTypeExp`, while leading modifiers arrive via `ParseDeclWithModifiers` (`pendingModifiers`, attached by `CompleteDecl`) or `parseModernParamDecl`'s `decl->modifiers`, so they never become a `ModifiedTypeExpr`. The only applier left, `maybeApplyLayoutModifier` (`slang-check-decl.cpp`), handles a bare matrix only. So `row_major var v: float2x3[2]` (and cbuffer, global, 2-D and `func f(uniform row_major v: float2x3[2])` forms) keeps the default layout, and `row_major var x: int` gets no E39026. Not a #12992 regression: identical on 3e98d9563, v2026.19 and v2025.1. The prototyped producer fix (+12/−6, #13390) gives `parseModernVarDeclBaseCommon` an optional `Modifiers*` (`pendingModifiers` for var/let, `&decl->modifiers` for `ModernParamDecl`) and parses the type with #13384's `_parseTraditionalParamTypeExpr`, which grafts `MatrixLayoutModifier` onto the atomic type before the postfix `[N]`. Time-travel tip: `git checkout <sha>` in an existing built worktree plus incremental `cmake --build build --config Release --target slangc` (~10 min for ~30 files) beats a fresh worktree; snapshot with `cp -a build/Release/{bin,lib}` since slangc loads `libslang-compiler.so` from `../lib` [leading modifiers on modern var/let/param never reach the type expression](../learnings/1790931602247-leading-modifiers-on-modern-syntax-var-let-param-n.md).

**Parser/AST changes must run `tests/language-server/`**, not just `tests/diagnostics` + `tests/compute`: the robustness tests feed malformed source (`robustness-4.slang` is literally `[]`) and require no crash — #12674 was green locally but failed 13 language-server tests in CI. Producer fix there: `Parser::ReadToken(TokenType::Identifier)` on a mismatch returns the mismatched token WITHOUT advancing, so `varExpr->name = tok.getName()` builds a null-named node that crashes `CheckTerm`/lookup — guard on `tok.type == TokenType::Identifier` and leave the node null (likewise guard `parser->currentModule` before `->ownedScope` on the reflection/string-parse path, which `parseTermFromSourceFile` never sets). Harness: `slang-test -use-test-server` reuses server processes, so ONE crash fails every other test on that server; a broad non-deterministic cross-platform failure set usually traces to one crash — find the test that fails deterministically in isolation ([parser/AST changes must run tests/language-server — malformed-input crashes + shared-server collateral](../learnings/1789271917061-parser-ast-changes-must-run-tests-language-server-.md)).

## Parser: Decl-vs-Statement Cannot Be Disambiguated Lexically

From the #13208 design investigation (`slang-parser.cpp` @ 0d06f4bd0): neither "identifier followed by `(`" nor "leading statement keyword" is safe evidence, since all of these are valid *declarations* at file/struct scope: `float(x);` (parenthesized declarator, `_parseSimpleTypeSpec`→`parseDirectAbstractDeclarator`), `__init(...)`/`__subscript(...)`, `syntax ctor = __init;` then `ctor(...)` (a user syntax alias consulted before the declarator fallback), and `struct if {}; if(x);` (keywords are shadowable). Disambiguation must be a genuine declaration parse attempt — which also refines the "call-shaped `ident(...)` at global scope is never a declaration" heuristic for a top-level `static_assert(`. "Build the decl but don't add it" is NOT non-committing: declaration parsing mutates shared state before `CompleteDecl`/`AddMember` (namespaces add members, buffer parsing adds a scope member, modifier parsing can bump the module language version), so a speculative probe must be side-effect-free or fully rolled back; the existing `getCursor`/`setCursor` snapshot sites only parse expressions. Architecture: `ParsingStage::Decl` parses file scope + aggregate bodies eagerly, while function bodies are captured as `UnparsedStmt` and re-parsed in `ParsingStage::Body` (the only stage with semantic disambiguation). `ParseStatement`'s guess-then-commit loop is separate from the decl-only loop (`parseDecls`→`ParseDecl`→`ParseDeclWithModifiers`) and has no decl-only flag — the seam a "declaration-or-statement(context)" refactor introduces. Accept-then-diagnose (`CompleteDecl`→`DeclNotAllowed`; `DeclNotAllowedInContext` via `validateDeclNesting`) is Decl-only, and no Stmt-carrying-Decl node exists ([parser: decl-vs-statement can't be disambiguated lexically; needs a side-effect-free declaration probe](../learnings/1790107330312-slang-parser-decl-vs-statement-can-t-be-disambigua.md)).

## Two Decl-Nesting Validators: Parser E30102 Masks the Looser Checker E31400 Table

The parser's `isDeclAllowed` (slang-parser.cpp ~5550) switches on the exact `ASTNodeType`, allows unknown kinds by default, and reports E30102 (`DeclNotAllowed`). The checker's `validateDeclNesting` (slang-check-decl.cpp ~317, #10456) classifies by subclass, reports E31400 (`DeclNotAllowedInContext`), and skips decls marked `nestingAlreadyDiagnosed`. The checker table is looser: with the parser check disabled, `__generic<T> int x;`, `using N;` in a struct, `module`/`implementing` in a namespace, and an interface `typealias` pass silently, and `__constraint` in a struct becomes fatal E40002. E30102 is a parse error that stops compilation before checking (compile-request.cpp ~833), so moving a case changes both the diagnostic and how far compilation gets. Probe pitfall (#13499): an env-gated prototype testing `getenv("X")` treats `X=` as ON — run the baseline with `env -u X` [two decl-nesting validators; parser E30102 masks the looser E31400 table](../learnings/1791410610457-slang-has-two-decl-nesting-validators-parser-e3010.md). Why the nesting table could ship as a hard error with no version gate is on [[wiki/concepts/misc-f0909b3-slang-frontend-binding-fixes.md]].

## Eager Local-Generic Conformance Checking Tightens Non-Conformance Diagnostics (#13092)

slang#13092 fixed a read-before-checked crash by having `visitBlockStmt` drive local `GenericDecl`s whose inner is an `AggTypeDeclBase` through `ensureAllDeclsRec` to `ReadyForConformances`. That also eagerly rejects non-conforming local generics: a declared-but-**unused** `struct Bad<V> : IOp { V val; }` (missing `apply`) compiles clean before and errors E38100 after. This is principled — module-scope non-conforming generics already error even when unused, so local scope was the inconsistent gap. But it can break downstream integration builds (Falcor CI) with latent non-conforming local generics; fix the downstream shader, not the compiler. Takeaways: when a fix moves a type into eager conformance checking, test the declared-but-unused non-conforming case on both builds and call out the footprint; external integration failures show only "pipeline finished with status 'failed'" in `run-external-ci` logs, so escalate to the maintainer holding the pipeline log ([Filling witness tables for local generic conformances also tightens non-conformance diagnostics (E38100) — downstream break risk](../learnings/1790181214204-filling-witness-tables-for-local-generic-conforman.md)).

## Redeclaration Matching: Loosening `doFunctionSignaturesMatch` Also Merges Prototypes with Mismatched Definitions (#13384)

`doFunctionSignaturesMatch` has one caller, `checkFuncRedeclaration`, and `true` does two things: two bodies → E30201; one body → the body-less prototype and the definition are silently chained into one redeclaration family, with only the return type re-checked. Calls resolve against the prototype's parameter types (`addOverloadCandidate` skips non-primary declarations) while the body lowers with its own. #13384 made the predicate compare parameter types "up to matrix layout" (so layout-only body pairs report E30201), which also merged `float pick(row_major float2x3 m);` with a `column_major` definition. Arrays and bare matrices (by value or `inout`) are benign (the call converts; DXC accepts the pair); pointers (`float pick(row_major float2x3* p);`) are not — nothing converts the memory, so IR call and callee types disagree: E99997 (`slang-ir.cpp:5822 resultType`) on SPIR-V/Metal, type errors on CUDA→PTX and CPU. The fix adds an explicit E30200 check after the two-bodies check. When reviewing any widening of signature matching, compile a body-less prototype + mismatched definition for every wrapper the predicate looks through, on a non-HLSL target with `[noinline]`; a source-trace "unconfirmed gap" became a bug only once compiled. Also: place a new mangled-name token where nesting stays unambiguous — a layout suffix after a matrix's element type made `matrix<matrix<..,RowMajor>,..>` and `matrix<matrix<..>,..,RowMajor>` mangle identically (conversion-cost cache/mangler layout handling: [[wiki/concepts/slang-language-coercion-and-overload.md]]). Tooling: the local correctness reviewer again lost all subagents to the 600 s background-wait ceiling (146 B review) because `compose-and-run.sh` does not default `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`; always pass it [loosening doFunctionSignaturesMatch also merges a prototype with a mismatched definition](../learnings/1790926235230-loosening-dofunctionsignaturesmatch-also-merges-a-.md) [an "equal up to X" signature relation also merges forward declarations](../learnings/1790931809642-an-equal-up-to-x-signature-relation-also-merges-fo.md).

**A merge can silently change overload identity for a split enum.** A PR split `ParamPassingMode::Ref` → `RefReadWrite`/`RefReadOnly`/`RefWriteOnly` while master replaced a modifier-presence check with an exact mode comparison (#13232: `_doParamPassingModesMatchForOverload`); the merge compiled but a `readonly __ref` declaration and a `__ref` definition became two overloads sharing one mangled name (E39999 "ambiguous call"). New `case X:` labels on the old enumerator break the build; new `==`/`!=` do not — after resolving conflicts, grep master's diff for comparisons on the split enum, categorize each, and pin with a test plus revert drill. `slang-static-unit-test` exists only in a static build: configure `build-static/` with `-DSLANG_LIB_TYPE=STATIC -DSLANG_SLANG_LLVM_FLAVOR=DISABLE` [merging master after a refactor can change overload identity of split enum modes](../learnings/1791413169329-merging-master-after-a-refactor-can-silently-chang.md).

## Reviewing the `GLSLModuleModifier`→`ModuleSourceLanguageModifier` refactor (#13112)

The known pitfall — "GLSL permitted" (`-allow-glsl`) ≠ "source language is GLSL", and `TranslationUnitRequest` is nullptr on reflection/language-server paths so the old fallback was load-bearing — is resolved by design: `isModuleGLSLFlavored() = AllowGLSL-option || getModuleSourceLanguage()==GLSL` keeps the AllowGLSL term, and the modifier is attached to every module AST at parse time (reachable via `getModuleDecl(decl)` without a TU), defaulting to `Slang`. Verify both explicitly when reviewing this refactor class. When correctness (Reviewer A) and clarity (Reviewer C) independently flag the same thing (here the `sourceLanguage` field), treat it as high-signal convergence ([GLSLModuleModifier→SourceLanguage refactor: how PR 13112 addressed the known pitfall + a cross-reviewer convergence signal](../learnings/1789515728058-glslmodulemodifier-sourcelanguage-refactor-how-pr-.md)).
