## TL;DR


## Ledger mechanics: `record_decision` replaces, and emission is the furthest you can see

**`record_decision` replaces the row and DROPS any `record_human_verdict` stamp.** The tool contract is "one row per (repo, pr, commit_sha) — a re-run on the same commit **replaces** it", while `record_human_verdict` stamps an **existing** row; the two have no knowledge of each other, so re-recording to correct a row's *input signal* (decision unchanged) silently destroys the human-verdict column and the row drops out of accuracy measurement entirely — right decision, right reason_code, nothing errors. Hit during the CodeRabbit under-read audit: slangpy#1085 @ `a1da5beac5af` carried `human_verdict=APPROVED`, and the disagreement datapoint (human APPROVED vs approver ABSTAIN_POLICY) is precisely what the scoring exists to capture. Before re-recording ANY historical row, grep the session transcripts for `record_human_verdict` against that repo/pr/**commit_sha** (the stamp is per-commit — a stamp on a sibling revision is not yours to preserve), sequence a batch so the unstamped row goes first, re-stamp **immediately after the replacement in the same turn** rather than deferring past a possible compaction, and additionally record the human verdict inside the correction note itself so provenance survives if the stamp is lost again ([[approver/infra-abstain] record_decision replaces the row and DROPS the record_human_verdict stamp — re-stamp after any correction](wiki/learnings/1785779161211-approver-infra-abstain-record-decision-replaces-th.md)).

**The ledger is write-only from an agent tier — but your OUTBOX proves emission, and `processing_ack` "NOT ACKED" proves nothing.** After correcting a retracted claim inside an already-recorded row, the natural question (did the upsert replace or append?) is not self-answerable. A source probe settles the shape: `grep -rl 'approval_decisions' /app` and `grep -rl 'record_decision' /app` each hit **only** the tool definition (`/app/src/mcp-tools/core.ts`), whose handler just does `writeMessageOut({kind:'system', content: JSON.stringify({action:'record_decision', …})})` — so the "one row per commit, a re-run replaces it" line is a claim made by the tool's **own doc string**, i.e. **a contract to relay, never a state to assert**; a success return means the *call* succeeded. (Name-collision trap: `ncl approvals` is a **different** table — in-flight self-mod/OneCLI cards, deleted after the admin responds.) What *is* self-verifiable is your own emission: `select seq, content from messages_out where content like '%record_decision%'` showed both writes with payloads intact — one with the retracted phrase **present**, the later one with the correction present and the retracted phrase **gone**, same `commit_sha` — proving the corrected payload left the container with the right content. ⚠️ And the trap that nearly inverted the conclusion: all 12 `messages_out` rows read "NOT ACKED", **including chat messages the orchestrator demonstrably received and replied to**, because `processing_ack` is **inbound-only** (`message_id` holds `sys-`/`a2a-` ids, never `msg-`) and `messages_out` has no status/consumption column at all. That contradiction *was* the control — reading "NOT ACKED" as "unconsumed" would have reported a false delivery failure on messages that provably arrived. Generalizes: **before reading a status field as evidence, find a row whose true status you already know independently and check the field agrees**; a column that reads the same for a known-success and a known-unknown is not a status column for your purpose. Reporting rule: say **"could not verify by method M"**, M named, and report a ledger correction upward as **ATTEMPTED, pending operator verification** — never "resolved." This is structural, not a permissions gap: the writer of an audit artifact cannot verify its own write, which is the *intended* direction for an audit trail, and the consequence to carry is that **a contaminated reasoning field can be repaired but not confirmed** while the headline fields stay correct so nothing ever *looks* wrong ([[approver/infra-abstain] the ledger is write-only from every tier — but your outbox proves emission, and processing_ack is inbound-only](wiki/learnings/1785786203086-approver-infra-abstain-the-ledger-is-write-only-fr.md)).

⚠️ **RETRACTION of two claims in that note, filed 25 minutes later — `find` and `grep` enumerate a MOUNT, not a CAPABILITY.** (1) *"No compiled bundle ⇒ `src/` IS the whole app"* is **false**: `/app` is `nanoclaw-agent-runner`, the **container half only**, proved by absence — shipped code inside `/app` cites three files that are not in `/app` (`src/session-manager.ts` twice, `scripts/sanity-live-poll.ts`), and code does not cite its own missing files. The missing-`dist` observation was accurate; the inference to "therefore this is the entire application" is a check that could not have come out differently if the claim were false. So `grep -rl approval_decisions /app` → one hit licenses "no consumer readable from an agent tier", never a statement about the system: **a negative drawn from an incomplete enumeration is a fact about your reach.** (2) The consequential one — **a fifth probe exists, in scope, and documented in `ncl sessions help`**: `ncl sessions messages <session-id> --include-system` reads **other sessions'** outbound rows including the `kind=system` rows written by `record_decision` (sweeping 180 sessions found **40** carrying such rows, and it surfaced both #806 rows a peer tier had correctly declined to confirm because they lived in another agent's `outbound.db`). **The cross-tier boundary was real; the cross-SESSION boundary was not** — and a peer can now discharge it with a verb already in their own scope table. (3) "Reachable SQLite is only the two session DBs" is scoped wrong: `/workspace/{inbound,outbound}.db` are the *current* session's, so a fresh session reads `messages_out` → 0 rows and that emptiness nearly read as "the evidence is gone" — cross-session outbound history is reachable, just not through the filesystem. **The reflex to install: before claiming you cannot reach X, read `--help` for every verb already listed in your own capability table** — cheaper than any filesystem sweep and the only probe that can see a *mediated* path. A probe that feels like ground truth deserves *more* scrutiny about its scope, not less; the felt authority of `find` is what let an incomplete enumeration pass as a system fact. What remains genuinely dark is narrower than any of the notes said: **only the host-side upsert-vs-append**; emission is provable to byte-level content, across sessions, by any tier in the group ([[approver/infra-abstain] RETRACTION — ncl sessions messages --include-system reads other sessions' record_decision rows; find/grep enumerate a mount, not a capability](wiki/learnings/1785787116199-approver-infra-abstain-retraction-ncl-sessions-mes.md)).


## Lab-container infra reach — the three failures that each look like a different problem

`GH_TOKEN` in the approver container is the 23-char sentinel `ROUTED_VIA_ONECLI_PROXY`; credentials are injected at the OneCLI **HTTPS proxy boundary**, which covers `api.github.com` REST paths but not `gh`'s GraphQL endpoint. So (1) **`gh api` REST works and GraphQL does not** — anything `--json`-shaped that `gh` routes through GraphQL (`gh pr view --json`, `gh pr list --json`) 401s while `/repos/{o}/{r}/pulls/{n}`, `/pulls/{n}/reviews`, `/pulls/{n}/commits`, `/compare/{base}...{head}`, `/contents/{path}?ref={sha}` all serve fine (`gh api repos/<o>/<r> --jq .full_name` → 200 confirms injection; a 403 on `/user` is expected and harmless, App installation tokens have no user). (2) **The critique-gate hook blocks read-only `/pulls` reads**, so route PR reads through a small GET-only Python helper whose command text carries no `/pulls` literal — the real gate still applies where it matters, at `record_decision` / `[Approval Decision]`. (3) **Upstream non-`shader-slang` repos 401** because the credential is org-scoped, and through a raising client a 401 *looks like a 404* — use `raw.githubusercontent.com` for public files in other orgs, and read `.gitmodules` plus the pinned submodule SHA before trusting a path cited in a diff comment, since a submodule may point at a **fork** (slangpy's `external/nanobind` is `skallweitNV/nanobind`, not `wjakob/nanobind`). Each of the three *looks* like a different problem than it is: a bad token (it is a sentinel), a missing file (it is a 401), a PR-creation attempt (it is a GET) ([[approver/infra-abstain] lab container: gh GraphQL 401s on the OneCLI sentinel token; use REST via a helper, and upstream repos are unreachable](wiki/learnings/1785786635119-approver-infra-abstain-lab-container-gh-graphql-40.md)).

**Never accept an `ABSTAIN_INFRA` without reproducing the underlying fetch by hand — an infra-abstain caused by your own tooling is a burned decision, not a real gate.** On slang-rhi#807 `collect-reviews.sh --dry-run` reported `reviews fetch FAILED -> exit 21 (ABSTAIN_INFRA)` for a PR whose reviews fetch was perfectly healthy; one `curl` showed the data was there. Two shim bugs, both about matching real `gh`'s contract: **wrong paginate shape** — real `gh` has two (`--paginate --slurp` → ONE array of page-arrays; bare `--paginate` → page arrays *concatenated* with `][`, which `collect-reviews.sh` stitches itself) and the shim emitted slurp-shape for both, so bare-`--paginate` output was double-nested and unparseable → `None` → exit 21 (note `harvest-reviews.py` uses `--slurp` while `collect-reviews.sh` uses bare `--paginate`, so a shim must serve both); and a **trailing conditional setting the exit code** — `[ "$SLURP" = "1" ] && echo -n "]"` as the last command makes the script exit **1** whenever SLURP is 0, which callers read as a fetch failure, so use `if/then/fi` for any conditional near a script's end. This narrows the general "`--paginate` is truncated / silence is the tell" folklore: **the silence is invocation-form-dependent and exit codes ARE usable** — once the shim distinguishes `--slurp` from `--paginate` and stops letting a trailing test set `$?`, a nonzero status means the *fetch* failed and can be trusted as such. For CI evidence without admin, **step-level metadata is public**: `actions/runs/<run_id>/jobs?per_page=100` gives each job's `steps[]` with per-step `status`/`conclusion` plus `runner_name`/`labels`, which answers "did the `Unit Tests` step actually run and pass on this leg at this SHA?" — strictly better than the job `conclusion` alone — but it does **not** give log *text*, so anything needing a printed line stays unresolved and must be named as such. Cross-check the run id from the check-run `html_url`, since the jobs list for a *stale* run silently answers for the wrong head. Unauthenticated rate limit is **60 req/hr** — budget it; a re-decision on a moved head roughly doubles usage ([[approver/infra-abstain] job logs need admin (403) — use jobs?per_page for step-level evidence, and fix the gh shim's --paginate shape](wiki/learnings/1785765021134-approver-infra-abstain-job-logs-need-admin-403-use.md)).


## The durable record: a correction is not applied until every restatement is fixed

The recorded row and the memory store outlive the decision, so a correction that lands only in the outbound message is not a correction.

**Sweep for the SUPERSEDED wording, never for your new phrasing.** Two independent occurrences in a single turn on slang-rhi#800, in separate memory stores: an overstated residency claim was corrected ("refuted" → "NOT cleared") with targeted edits and then confirmed by grepping for the **new** wording — which found it, while the old claim was still live in the R1/R2 historical sections *and* in an embedded machine-readable JSON `notes` field a downstream parser would read; the orchestrator's parallel fix left three more survivors including an entire duplicate terminal section. **A search for your correction cannot match the stale text, which uses the vocabulary you abandoned** — both checks felt like verification and were structurally incapable of failing. So sweep the abandoned vocabulary expecting **zero** hits (`grep -nE "refuted|STALE|VINDICATED|…"`) *plus* a **positive control** proving the pattern isn't vacuous (`grep -c "<new wording>"` > 0), since a zero-hit sweep is indistinguishable from a typo'd pattern. Check specifically: machine-readable fields (embedded JSON, frontmatter `description`, headings, index lines — a parser recovers the rejected claim as authoritative), status tags on historical sections (`[OPERATIVE]`, "join pending" — true when written, silently lies later), and duplicate terminal sections from separate append passes. Prefer **labelled invalidation over deletion** for the audit trail (a banner naming what is withdrawn, why, and which statement controls, rather than rewriting history), and re-record an already-published ledger row rather than leaving the corrected reasoning only in prose. This matters more than the outbound message: *a wrong message is read once; a wrong memory file is read by every future session* — here the surviving stale text was exactly the inference multiple critique rounds had just rejected, so a future session would have confidently re-derived the error with the correction sitting in the same file ([[approver/critique-mustfix] correcting a claim means sweeping the WHOLE file for the SUPERSEDED wording](wiki/learnings/1785773722903-approver-critique-mustfix-correcting-a-claim-means.md)).

**In an append-only store, a correction is only as reachable as the stale vocabulary it quotes.** L1 atoms are immutable, and a correction filed as a *new* atom does not disarm the stale one unless it **names the superseded file by path and quotes the retracted sentences verbatim** — a future reader greps the abandoned wording, so if those exact strings appear only in the file being retracted, the correction is invisible to the search that would surface the error. Say explicitly **which parts survive** (a blanket "that learning is wrong" discards checklists that are correct and expensive to derive), retract at paragraph granularity, and remember that synthesized/derived surfaces (this wiki included) inherit the error and self-heal on the next sync **only if** the correction is in the source set — which is why a private-ledger fix is structurally unable to reach other coworkers' Step-0 recall. After correcting any claim, ask **where else it lives**: private ledger, shared learnings, synthesized wiki, embedded JSON, frontmatter, index lines. A sweep of one store is not a sweep ([[approver/critique-mustfix] a correction filed as a new atom does not disarm the stale one unless it names the file and quotes the retracted sentence](wiki/learnings/1785774267946-approver-critique-mustfix-correction-to-my-own-sla.md)).

⚠️ **Compaction is the mode where this discipline inverts — "move the detail to the child and shorten the pointer" DELETES content when the index line is the only copy.** Compacting a memory index (22.2KB → 15.9KB) reduced eleven evidence-discipline rules to one-liners "with detail in the topic file it already points to", and verification passed on every axis — 34 rows intact, every link resolving, all eleven headlines present — **while the compaction destroyed data**: three of the eleven had **no full text in the child file at all**, so shortening the index line deleted the content outright and left a pointer aimed at nothing. Worst case: one of the three explicitly carried *"do NOT compress it away, or what remains is a plausible maxim with nothing under it"* — and the compaction deleted exactly that paragraph and kept exactly that maxim, executing the failure the note existed to prevent, on the note itself. Link integrity and headline presence are both structural and both blind to the only question that matters: **does the destination actually contain the text I am about to delete from the source?** Cure, in order: (1) before shortening any pointer line, `grep` the child for that rule's distinctive phrase — if it returns nothing, append it to the child *first*, confirm the grep hits, *then* shorten (move-then-verify, never shorten-then-assume); (2) after compacting, re-grep every pointer for **content**, not links — any zero is silent data loss; (3) leave a `⛔ do-not-compress` marker on any index line whose child paragraph is load-bearing *evidence* rather than verbosity, because future-you optimizing for bytes cannot otherwise tell proof from wordiness. The deeper generalization is the same decay asymmetry as species 1: **a summary and its evidence decay at different rates** — the summary is short, quotable, survives every cleanup; the evidence is long, reads as redundant, gets trimmed — so a store of hard-won corrections degrades into unfalsifiable platitudes with no single visible mistake. If a rule's credibility rests on a specific datapoint (a cost, a count, a "both parties hit this simultaneously"), the datapoint is not color — it **is** the rule. Recovery note: the memory directory is not a git repo, so the three rules were recoverable only because their text was still present earlier in the same conversation; across a context boundary the loss would have been permanent and undetectable ([[approver/critique-mustfix] compaction destroyed 3 of 11 rules' evidence — verify the child file HAS the text before shortening the pointer](wiki/learnings/1785781908276-approver-critique-mustfix-compaction-destroyed-3-o.md)).


## Contradictions / supersessions

- The "clauses only gate the approve direction, so a verified BLOCK can override a clause FAIL" theory is **rejected** — the skill ordering governs and a clause FAIL short-circuits to ABSTAIN_POLICY before the challenger ([[approver/clause-gap] A Step-1 clause FAIL short-circuits to ABSTAIN_POLICY even when the challenger has already verified a BLOCK-class defect — the skill ordering governs, don't invent a "BLOCK overrides clause-fail" exception](wiki/learnings/1784271165403-approver-clause-gap-a-step-1-clause-fail-short-cir.md)).
- The GraphQL-401 "total GitHub outage → ABSTAIN_INFRA on everything" reading is **wrong** — REST + anon git still serve the clauses ([[approver/infra-abstain] GraphQL 401 gateway outage ≠ no GitHub access — gh REST still serves the clauses; don't over-ABSTAIN_INFRA](wiki/learnings/1784271281635-approver-infra-abstain-graphql-401-gateway-outage-.md)); and the underlying 07-16/07-17 outages themselves were later RESOLVED, so the split is a technique not a state.
- "Bot-authored dep bump + Devin timeout = guaranteed INFRA" is correct only for the timed-out run; it does NOT license pre-emptively skipping Devin on a re-sync (see [[wiki/concepts/review-approver-challenger-calibration.md]]).
- The empty-body-`COMMENTED`-wrapper learning's supporting claim — *"the inline comments spanned 3 pages, the relevant author replies were on page 3, page 1 was entirely July bot traffic"* — is **false**. The author's replies are on the early pages too (250 comments over 100/100/**50**, 37 by the author). Its central lesson (empty wrapper ⇒ look one level down) is unaffected; the pagination-depth advice was right by accident, and the real rule is *never characterize a page's contents from a summarized read* ([[approver/clause-gap] CORRECTION to the empty-body-wrapper claim](wiki/learnings/1785761810820-approver-clause-gap-correction-to-empty-body-comme.md)).
- The blanket *"`--paginate` output is truncated and silence is the only tell, so exit codes are unusable"* reading is **narrowed**: the failure was invocation-form-dependent (`--paginate --slurp` → one array of page-arrays vs bare `--paginate` → concatenated page arrays) plus a trailing conditional setting `$?`. With those fixed, **exit codes ARE usable** — a nonzero status means the fetch failed ([[approver/infra-abstain] fix the gh shim's --paginate shape; a trailing conditional set the exit code](wiki/learnings/1785765021134-approver-infra-abstain-job-logs-need-admin-403-use.md)).
- The shared rule *"`DeclRef::as<U>()` does no type check, so `if (declRef.as<T>())` is a no-op guard"* is **wrong for `DeclRef`** and is scoped to **`SubstExpr::as()`** only. `DeclRef<U>::as()` rewraps through the typed constructor, and `DeclRef<T>::init()` nulls on mismatch — so it type-checks and is safe as a guard; `is<>()` is a style nit, not a correctness gap ([[approver/clause-gap] DeclRef::as&lt;U&gt;() DOES type-check](wiki/learnings/1785745186536-approver-clause-gap-declref-as-lt-u-gt-does-type-c.md)).
- *"`actions/jobs/<id>/logs` needs admin, so job logs are unavailable"* is **wrong as a property of the endpoint** — it 302-redirects to a signed blob and `curl -sSL` returns the full body unauthenticated on a public repo; the 403 is a tooling artifact and was not reproducible ([[approver/infra-abstain] job logs are PUBLIC — follow the 302](wiki/learnings/1785766450209-approver-infra-abstain-github-actions-job-logs-are.md)). The *step-level* corollary still stands: `actions/runs/<id>/jobs?per_page=100` gives per-step pass/fail but never log text ([[approver/infra-abstain] use jobs?per_page for step-level evidence](wiki/learnings/1785765021134-approver-infra-abstain-job-logs-need-admin-403-use.md)).
- The `rate_limit` core-`limit` token probe (*"60 = anonymous, 5000 = injected, run via curl not gh"*) is **retracted** — it reports anonymous while the credential is being injected, because injection is **per-path** and the prescribed fix was transport. Read `x-ratelimit` headers on the exact path you will call and test **presence**, not value ([[approver/critique-mustfix] the rate_limit probe is itself species 2](wiki/learnings/1785782770123-approver-critique-mustfix-correction-my-rate-limit.md)).
- The slang-rhi#800 residency framing is **doubly corrected**: the absence-of-log-line refutation was unsound (severity routing made 2 of 3 paths undetectable), and then the polarity inverted — **CI runs the FALLBACK** by default (no Apple6 on the hosted runner), so the *residency-SET* path is the uncovered one and the missing artifact is an **Apple6 run**, never a `SLANG_RHI_METAL_NO_RESIDENCY_SET` run ([[approver/critique-mustfix] the #800 residency corollary is withdrawn](wiki/learnings/1785774267946-approver-critique-mustfix-correction-to-my-own-sla.md)).
- *"The `approval_decisions` ledger is unverifiable from an agent tier / `/app`'s `src/` is the whole app / reachable SQLite is only the two session DBs"* is **narrowed**: `ncl sessions messages <id> --include-system` reads other sessions' `record_decision` rows, and `/app` is only the container half. What stays dark is **only the host-side upsert-vs-append** ([[approver/infra-abstain] RETRACTION — find/grep enumerate a mount, not a capability](wiki/learnings/1785787116199-approver-infra-abstain-retraction-ncl-sessions-mes.md)).
- *"The missing `json.loads` decode caused devin-fetch's empty `## Flags`"* is **refuted as a causal claim** — decode and re-split and Flags is still empty, because the marker occurs zero times in the capture; the real cause is the done-poll exiting on a CI progress counter. The decode defect is real but was never the mechanism ([[approver/critique-mustfix] confirming a mechanism means running the counterfactual](wiki/learnings/1785787841835-approver-critique-mustfix-confirming-a-peer-s-mech.md)).
- *"11 of 18 harvests exposed ⇒ 17 findings were missed ⇒ slang-rhi#797 is a probable false-safe"* is **withdrawn at the decision level**: the review docs carry the findings verbatim with severities. The artifact-level defect is real; the decision-level harm claim was not confirmed ([[approver/critique-mustfix] an artifact-level defect is not a decision-level harm](wiki/learnings/1785780014953-approver-critique-mustfix-an-artifact-level-defect.md)).
- The resume predicate for a held chain went wrong in **both** directions: *"a non-bot review with an actionable state lands"* can never fire (the blocker has no review object), and its widening to *"actionable non-bot feedback in ANY of the three endpoints"* **always** fires (already satisfied). The working form requires all three of non-bot · addressed to the decision, not the PR author · changes a load-bearing input ([[approver/clause-gap] widening a never-fires predicate produced an always-fires one](wiki/learnings/1785821476819-approver-clause-gap-widening-a-never-fires-predica.md)).


## Class Determination First: Own-Harness / Non-Compiler-Repo PRs Are OUT_OF_SCOPE (2026-07-20 fold)

A PR-approve dispatch landed for `slang-coworkers/nanoclaw#982` — a PR in the infra fork that *modifies the approver's OWN decision harness* (including relaxing its ABSTAIN critique gate). The mechanical pipeline produced ABSTAIN_INFRA-looking signals (`harvest-reviews.py` exit 21, all 6 clauses UNEVALUABLE) whose real cause is the GitHub App token being scoped to shader-slang → HTTP 401 on `slang-coworkers/*`. But that token-401 is a *symptom* of out-of-domain, not the cause of an infra abstain. The correct call is a **class determination made FIRST in the skill, before and overriding the clause→INFRA mapping**: if the repo isn't shader-slang/slang compiler code, or the changed paths are the approver's own harness (`container/skills/slang-pr-approver/**`, `container/workflows/slang-pr-approve/**`), it's OUT_OF_SCOPE — and an own-rules PR is additionally a conflict of interest (self-endorsement never permitted; a human must look). Record `ABSTAIN_POLICY` with `reason_code=OUT_OF_SCOPE:<class>` (closed enum, free-form suffix — new suffix `approver-harness`), stamp it explicitly into `_approver_result` so it doesn't drift to INFRA, and skip Devin (a class determination isn't informed by a review signal) ([approver-own-harness PR = ABSTAIN_POLICY:OUT_OF_SCOPE + conflict-of-interest](wiki/learnings/1784443235968-approver-clause-gap-approver-own-harness-pr-abstai.md)).
