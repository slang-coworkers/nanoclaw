## TL;DR

- **One coworker name is N concurrent sessions.** A destination name, a GitHub bot login (`nv-slang-bot[bot]`), a container, and its `/workspace/agent/` clone are all shared by every session of a coworker. So a path, log line, commit, filed issue, `updated_at`, or artifact carries **zero** information about which session produced it. Attribution is a **missing-key problem, not a care problem** — fix it with a key (session id, thread), never with more attention.
- **Authorship is a claim about a SESSION.** Settle it from that session's own `direction=out` rows (`ncl sessions messages --id <sess> --limit 500 --full`), not from presence, a timestamp, adjacency, or a peer's summary. `ncl sessions messages` has **no sender column** — `direction=in` proves arrival, never who sent it.
- **Mount identity is per-container / per-group / per-session.** `/workspace/agent` is per-agent-group (shared by sibling sessions); `/workspace` is per-session; the same absolute `/workspace/**` path names a **different object** in each container. Prove identity with `findmnt -T`, never with a matching `HEAD`.
- **Shared clone hazards:** a sibling's `commit --amend`/force-push rewrites the head of a PR you opened; `git stash` is per-clone so a bare `pop` can take a sibling's work; a `--hard` reset destroys a sibling's uncommitted work. The isolation rule "don't touch a sibling's worktree" is about *places*; per-clone namespaces (stash, `refs/`, config) are reachable from inside an isolated worktree.
- **Routing needs an explicit `thread_id`.** `in_reply_to` selects the *edge* (which peer), not the *session* (which of that peer's N conversations); it silently derives the wrong thread when the referenced inbound is thread-less.
- **A handoff granting destructive authority needs the same audit as one assigning blame** — blame gets contested by the accused; authority is accepted by the flattered, and the loss lands on a third party not in the conversation.

## One name, N sessions — the deployment shape

Measured repeatedly: a parent's destinations block shows **one** entry named `slang-fixer` while `ncl sessions list` shows **eight** live sessions behind it, one per thread, sharing one bot identity, one container, one `/workspace/agent/`. A group of 9-19 concurrent sessions is normal. This is the **deployment shape, not a race careful work avoids** — careful work caught the resulting errors only by luck of cross-checking. [One destination name can be N concurrent sessions — a filesystem path carries zero attribution](../learnings/1786035415029-one-destination-name-can-be-n-concurrent-sessions-.md)

The direct consequence: a filesystem artifact carries no attribution. Across one day this produced 7 attribution errors, none self-caught — a parent credited a session in good faith with a 10-item batch, a formatting error, an ICE filing, and suite logs, all real, all from that bot, none from that session. [One destination name can be N concurrent sessions — a filesystem path carries zero attribution](../learnings/1786035415029-one-destination-name-can-be-n-concurrent-sessions-.md)

Under a shared identity, "you did X" is a claim about a session, and errors run in **both directions** — "not you" when it was, and "that was you" when it wasn't. Two opposite-direction errors rule out both carelessness and bias; they point at a missing key. Six attribution errors landed in a single supervisor tick, every one caught by the recipient, not the sender. **A recipient can prove "it wasn't this session" but can never see your routing** — the routing half is invisible from their side and yours alone to fix. [Attribution and routing behind one coworker name is a missing-key problem, not a care problem](../learnings/1786109852075-attribution-and-routing-behind-one-coworker-name-i.md)

`updated_at` says WHEN, never WHO — it is monotonic across all writers sharing the identity. Attribute to the tier ("the triage tier added…"), not the session ("you added…"), unless attribution is load-bearing (credit, blame, "did my dispatch cause this?"). Suspect a sibling most when a spin-off issue is involved: an issue filed while triaging another gives two sessions a legitimate claim on its body. [Shared bot identity: an artifact's updated_at cannot tell you which session wrote it](../learnings/1786040214790-shared-bot-identity-an-artifact-s-updated-at-canno.md)

### Resolve group→name before calling two sessions a collision

A duplicate-work detector of the form "two running sessions on one thread = collision" **false-positives on every reviewed PR**, because a fixer session and a reviewer session legitimately share the issue/PR thread. The valid rule is "two running sessions **of the same coworker**", and the `agent_group_id` → coworker-name resolution is the step that gets skipped. Cross-coworker sessions on one thread are the design; only same-coworker duplicates are a collision. [Resolve agent_group_id to a coworker name BEFORE calling two sessions on one thread a collision](../learnings/1786096459202-resolve-agent-group-id-to-a-coworker-name-before-c.md) [Resolve agent_group_id to a coworker name before reading a session list as a collision](../learnings/1786096520048-resolve-agent-group-id-to-a-coworker-name-before-r.md)

The same missing resolution step makes ONE author look like TWO (splitting your own commit and your own memory leaf across imagined sessions) and TWO authors look like ONE (crediting a sibling's findings to whichever session replied). The resolution belongs **before** the attribution, not after a peer objects.

## The settling instrument: direction=out rows

`ncl sessions messages <id>` emits `seq | direction | kind | timestamp | text` — **no `sender`/`author`/`from` column exists**. So a `direction=in` row proves a message arrived in that inbox and nothing about who sent it; one inbox interleaves parent, peers, and system notifications (`Learning saved:` rows arrive as `in` too). "X said Y" is not readable from your own transcript. [`ncl sessions messages` has NO sender column — `direction=in` proves arrival, never authorship](../learnings/1786083556955-ncl-sessions-messages-has-no-sender-column-directi.md)

The check, one command: before claiming "X said Y", find that same text as an `out` row on **X's** side — pairing `out`@t on the sender with `in`@t on the receiver establishes authorship. If scope blocks reading X's session (`session not found` is a scope limit indistinguishable from genuine absence), **ask the party with global scope (the parent)**; do not infer. A memorable failure: a peer attributed the *parent's* byte-identical outbound to the correspondent it was waiting on — "expectation supplied the sender." He then attached a *correct, previously-filed* rule ("an ack is not a state change") to the fabricated ack, making a false story read as rigour. **A valid rule does not validate the instance you attach it to; check the instance exists first.** [`ncl sessions messages` has NO sender column — `direction=in` proves arrival, never authorship](../learnings/1786083556955-ncl-sessions-messages-has-no-sender-column-directi.md)

"Check my own rows" is insufficient when "my own" is plural: name **which** session on both ends, split `in` vs `out`, count only in the `out` rows. Both a triager and an orchestrator erred here — one attributing a fixer's exchange to a triager, the other running an authorship census on the wrong one of its own two sessions. [A handoff granting destructive authority needs the same audit as one assigning blame — and under a shared bot identity, authorship is a claim about a SESSION](../learnings/1786046309728-a-handoff-granting-destructive-authority-needs-the.md) [Under a shared bot identity, "you did X" is a claim about a SESSION — only that session's own out-rows settle it, and a worktree mtime never does](../learnings/1786046014429-under-a-shared-bot-identity-you-did-x-is-a-claim-a.md)

**Timestamps do not settle authorship.** `.git/worktrees/<n>` mtime is **activity, not creation** (it reads later than the moment you personally listed the worktree in the same session). What settles ownership: (a) the dirty *content* naming its author (a diagnostic name, a test path), (b) per-session `direction=out` rows, (c) the full path/worktree name keyed exactly. Never a timestamp, never a summary, never adjacency. [Under a shared bot identity, "you did X" is a claim about a SESSION — only that session's own out-rows settle it, and a worktree mtime never does](../learnings/1786046014429-under-a-shared-bot-identity-you-did-x-is-a-claim-a.md)

**A memory leaf's `originSessionId` frontmatter is the only attribution** — the path carries none, because `/workspace/agent/memory/` is shared across every session in the container. [Resolve agent_group_id to a coworker name before reading a session list as a collision](../learnings/1786096520048-resolve-agent-group-id-to-a-coworker-name-before-r.md)

## Mount identity: per-container, per-group, per-session

Three distinct facts, all easy to conflate because every path starts `/workspace`:

- **`/workspace/agent`** (clone included) is a **per-agent-group bind mount** — a subvolume named after the group (`/dev/vdb[/prod-groups/<group>]`). Shared by every session of that group, concurrently. [/workspace/agent (clone included) is a per-group bind mount — another tier's clean git status is no evidence about your tree](../learnings/1786033864470-workspace-agent-clone-included-is-a-per-group-bind.md) [workspace-agent is group-shared while workspace is session-private](../learnings/1786039078377-workspace-agent-is-group-shared-while-workspace-is.md)
- **`/workspace`** is **per-session** (`/dev/vda1[...sess-<id>]`), private to one session. [workspace-agent is group-shared while workspace is session-private](../learnings/1786039078377-workspace-agent-is-group-shared-while-workspace-is.md)
- The same absolute `/workspace/agent/slang` path names a **different object per group** — different block device and subpath, so they cannot alias, even when `HEAD` matches at the same SHA. [findmnt -T settles cross-container path identity; matching HEAD does not](../learnings/1786033956026-findmnt-t-settles-cross-container-path-identity-ma.md)

`findmnt -T <path>` is the one-command identity check — it settles what content comparison cannot. **Identity needs a field that cannot agree by coincidence** (mount source, device, inode); a matching commit, file length, or content hash can all coincide. A matching `HEAD` is *expected* between two clones of one repo, not evidence they are the same object; that one agreeing field lent false authority to a disagreeing `git status` and nearly inverted a true "the tree is dirty" report. [findmnt -T settles cross-container path identity; matching HEAD does not](../learnings/1786033956026-findmnt-t-settles-cross-container-path-identity-ma.md) [/workspace/agent (clone included) is a per-group bind mount — another tier's clean git status is no evidence about your tree](../learnings/1786033864470-workspace-agent-clone-included-is-a-per-group-bind.md)

**A clean `git status` on your mount is zero evidence about a peer's tree** and cannot refute a peer's dirt report — only a session inside that group has standing. And a dirty shared tree does not invalidate your measurements; it *obligates* you to prove the modified-file set is disjoint from every file your findings rest on (`git diff --name-only | grep -E 'file1|file2' || echo EMPTY`) with `HEAD` still matching the SHA you cite. [/workspace/agent (clone included) is a per-group bind mount — another tier's clean git status is no evidence about your tree](../learnings/1786033864470-workspace-agent-clone-included-is-a-per-group-bind.md) [findmnt -T settles cross-container path identity; matching HEAD does not](../learnings/1786033956026-findmnt-t-settles-cross-container-path-identity-ma.md)

A shared mount makes a concurrent-writer story *plausible*; it does not make it *demonstrated*. A link failure was misdiagnosed as a build race, then refuted by its own timeline (the blamed object's mtime postdated the failure and never defined the missing symbol). Plausibility is what makes the wrong diagnosis attractive — an mtime identifies neither a writer nor a cause. [workspace-agent is group-shared while workspace is session-private](../learnings/1786039078377-workspace-agent-is-group-shared-while-workspace-is.md)

### Finding unexpected dirt in a shared clone — no destructive op

The safe sequence contains no destructive operation anywhere: **read the diff → identify the author (sibling probes are often self-labelled, e.g. `-- TRIAGE PROBE (revert me)`) → decide, leaving it untouched if it isn't yours.** `git checkout -- .` or `git reset --hard` there destroys another session's live uncommitted work unrecoverably; a `--hard` reset is safe only on a tree you have just proven clean. [/workspace/agent (clone included) is a per-group bind mount — another tier's clean git status is no evidence about your tree](../learnings/1786033864470-workspace-agent-clone-included-is-a-per-group-bind.md) [findmnt -T settles cross-container path identity; matching HEAD does not](../learnings/1786033956026-findmnt-t-settles-cross-container-path-identity-ma.md)

## Shared clone: branch, stash, and worktree hazards

Worktrees are keyed by **issue** (`wt-slang-12385`), not by session. Two sessions on one issue share one worktree and one branch, so a peer's `commit --amend` + force-push silently rewrites the head of a PR *you* opened — including over a commit a human was assigned to review. Author metadata cannot tell you who did it (same bot); **`git reflog show <branch> --date=iso` can**, timestamping and labelling every move. Read the reflog before accepting or denying blame for a git action you don't remember. To undo a peer's force-push, lease against **their** sha, not yours; tag both SHAs first as free insurance. [Peer sessions share one worktree per issue — a sibling's force-push rewrites your PR head](../learnings/1786025100448-peer-sessions-share-one-worktree-per-issue-a-sibli.md)

Even two of *your own* sessions can mutate one branch within an hour — one force-pushed 13→14 and commented, another reverted 14→13 and commented 71 s later, neither aware of the other, producing two bot comments arguing with each other. Before reporting or editing PR state, **re-read it live** (`gh pr view --json headRefOid,title,isDraft,state`; `git ls-remote`); a comment you don't remember writing is the tell another session is active. Superseded comments: annotate with a `> [!NOTE] Superseded` banner, don't delete — turn a contradiction into a sequence and preserve the audit trail. [Two sessions on one branch: check live remote state before reporting, and never assume you made the last change](../learnings/1786026012219-two-sessions-on-one-branch-check-live-remote-state.md)

**`git stash` is per-clone, not per-worktree** — `refs/stash` is a single namespace shared by every worktree. A bare `git stash pop` can take a *sibling session's* stash entry. The compounding trap: `git stash push -- <file>` prints "No local changes to save" and exits 0 when the change is already **committed**, so a conditional push paired with a bare pop takes whatever a sibling pushed last. Their work survived one incident only because the modify/delete conflict made git *keep* the entry; a clean pop would have dropped it, destroying a sibling's uncommitted work. Use worktree-local `git checkout HEAD~1 -- <file>` / `git checkout HEAD -- <file>` for revert drills instead. **A rule scoped to a PLACE ("don't touch a sibling's worktree") does not cover access via a NAME** — ask what a resource is scoped to, not whether your command mentions their directory. [git stash is per-CLONE, not per-worktree — a bare `stash pop` in wt-<x>/ takes a SIBLING session's stash](../learnings/1786032031180-git-stash-is-per-clone-not-per-worktree-a-bare-sta.md) [git stash is per-clone, not per-worktree — a bare pop can take a sibling session's work](../learnings/1786032094049-git-stash-is-per-clone-not-per-worktree-a-bare-pop.md)

Mitigation for the whole family: **`git worktree` per build-touching chain** (or `isolation: "worktree"` on a build subagent) removes the class rather than absorbing it — a sibling's `wt-12362` sits at its own detached HEAD with its own `.so`, isolated from the primary clone's relinks. Cost measured at ~6.6 G per built worktree; worktree the chains that BUILD, not every chain. The hazard is **per-agent-group, not fleet-wide** — two coworkers can hold clones at the same `HEAD` that are different objects on different devices. [A received tree-state warning is evidence someone WAS writing, never that they ARE - and N sessions sharing one clone is the deployment shape, not a race careful work avoids](../learnings/1786002088482-a-received-tree-state-warning-is-evidence-someone-.md)

A received tree-state warning is evidence someone **was** writing, never that they **are**: the round trip (measure → compose → deliver → read) routinely exceeds an uncommitted edit's lifetime, and a hedge does not extend the shelf life. When you receive one, `git status` before believing it; when you send one, expect it to expire. [A received tree-state warning is evidence someone WAS writing, never that they ARE - and N sessions sharing one clone is the deployment shape, not a race careful work avoids](../learnings/1786002088482-a-received-tree-state-warning-is-evidence-someone-.md)

## Routing: thread_id, not in_reply_to

`in_reply_to` resolves the **edge** (which peer), not the **session** (which of that peer's N concurrent conversations). When the inbound it references is itself thread-less, the runtime falls back to the most recent thread known for that peer — the wrong session's — and the misroute succeeds silently. Set `thread_id` explicitly on every message to a multi-session group. Sender-side tells you are about to misroute: your outbound row shows `thread=None`, two outbound rows share one `in_reply_to`, or the inbound you're replying to has `thread_id = NULL`. The cheaper receiving-side detector: two messages in one batch assigning you *opposite* session ids is impossible for one session and is the strongest single tell; and if handed context that doesn't match your own artifacts, check your store before absorbing it (a file's *absence* is good evidence you didn't write it). [in_reply_to selects the edge, not the session — set thread_id explicitly](../learnings/1786069209416-in-reply-to-selects-the-edge-not-the-session-set-t.md)

### A successful restart is not a delivered wake message

`ncl groups restart --message` returning `{"restarted": 1}` is a report about a **container**, not a **session's inbox**. A group restart wakes the *group*, and the `on_wake` message is consumed by *a* fresh container's first poll — not necessarily the per-thread session holding the work you meant to resume. One chain was dead for **24 days** after a restart Main reported as a successful resume; the wake never reached that session. Verify with `ncl sessions messages <session-id> --limit 5` — confirm a **new inbound row** timestamped after the restart. The failure is silent and looks like patience: a stalled chain with no new rows is byte-identical to one whose owner is working. Use `target_session_id` on `send_message`/`send_file` to pin a wake; a group restart has no such targeting. Before diagnosing a peer as stuck, check whether anything was ever delivered to it — **attribute to the transport before the agent.** [A successful container restart is not a delivered wake message — verify the inbound row in the target session](../learnings/1786082935150-a-successful-container-restart-is-not-a-delivered-.md)

### ask_user_question has undeliverable branches

From an **a2a-born session**, `ask_user_question` emits a card that the host drops as `echo_drop:noop_pattern` (its body `[system: ask_question]` reads as a content-free echo) and delivers to the recipient **payload-less** — a notification with title/options/question stripped. Measured: 12 emitted, 12 dropped, timestamps matching to the second. These do NOT appear in `ncl approvals list`; they land in `ncl dropped-messages list`, which nobody checks. **A card row in your own `messages_out` is not evidence anyone saw it** — the row is written and counted, so the sender's self-check passes. For agent→agent or agent→parent decisions use `send_message` with the canonical `thread_id`; if you used `ask_user_question` and got no reply, check `dropped-messages` for your group before reporting "the operator did not answer." Cost on one chain: 20 hours of a fixer holding a correctly-analysed decision. [ask_user_question from an a2a-born session is echo-dropped as a noop — the card is emitted, counted, and arrives payload-less](../learnings/1786129496986-ask-user-question-from-an-a2a-born-session-is-echo.md)

## Destructive-authority handoffs and per-edge memory

**Audit a handoff granting destructive authority exactly as hard as an accusation.** Blame is contested by the accused (who has motive and rows to refute it); authority is accepted by the flattered, costs the recipient nothing visible, and the loss lands on a third party not in the conversation — so the permissive misattribution survives the exchange unexamined. Two live instances: a session told all 3 dirty files were "almost certainly yours" (the signal covered 2; the third was attributed on adjacency alone); "reaping remains yours" for two worktrees holding 5 live tracked modifications the recipient never created. **Adjacency in a conversation is not authorship.** [A handoff granting destructive authority needs the same audit as one assigning blame — and under a shared bot identity, authorship is a claim about a SESSION](../learnings/1786046309728-a-handoff-granting-destructive-authority-needs-the.md) [Under a shared bot identity, "you did X" is a claim about a SESSION — only that session's own out-rows settle it, and a worktree mtime never does](../learnings/1786046014429-under-a-shared-bot-identity-you-did-x-is-a-claim-a.md)

Key every path claim by its **full** name: `wt-12330` (triager) and `wt-slang-12330` (fixer) are two different worktrees for one issue, five characters apart, different owners — a `wt-*12330` substring silently merges them. [A handoff granting destructive authority needs the same audit as one assigning blame — and under a shared bot identity, authorship is a claim about a SESSION](../learnings/1786046309728-a-handoff-granting-destructive-authority-needs-the.md)

**Which memory store auto-injects is a per-edge fact, not a fleet fact.** Two coworkers found the same defect (a note written to a store the loader doesn't read) and drew *opposite correct* conclusions because their injection topologies differ — on one edge only `~/.claude/.../memory` loads, on another both stores inject. Measure it from your own `SessionStart` hook output; do not inherit a peer's topology, or you'll dismiss a store that does load or trust one that doesn't. A remedy ("fix it in every store") that was correct on one edge would have been wrong on another (writing a carve-out into a store with no rule to carve out). Corollary that generalizes regardless of topology: **verifying by presence in the file you just edited always passes** — that mechanical fact makes wrong-address the nastiest variant; require both stores non-zero (`grep -c "<string>" A/file B/file`), never `cp` to sync (merge per-file additively), and write both stores in the same action. [Which memory store is auto-injected is PER-EDGE — measure it from your own SessionStart output, never inherit a peer's topology](../learnings/1786084759196-which-memory-store-is-auto-injected-is-per-edge-me.md)
