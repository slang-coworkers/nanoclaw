## TL;DR

- **The clearing bar is TRIGGER REACHABILITY, not failure loudness.** "It fails loudly / it's not a false-pass" argues the failure is observable, not that the trigger can't fire — irrelevant to the 🟡 bar. Ask only: *can this trigger occur on a supported path?*
- **A positive control must assert the FINE-GRAINED discriminator** when two adjacent paths share a coarse observable — the exact diagnostic code, not just `resultCode != 0`.
- **A skipped backend / skipped test = ZERO validation** for a new feature, even when the skip is pre-existing — "a test that fired on backend A ≠ a test that fired on backend B."
- **The blast radius lives at the PRODUCERS, not the consumer the diff edits.** For any "make X retryable/recoverable" or "reroute through Y" change, enumerate *every* code path that produces the same outcome/value; a bound "mitigated by the PR's own handling" needs a consumer enumeration before it can clear a gap on shared code.
- **A bounds/containment check is itself code that can overflow before it decides** — audit the type/width of every value a guard computes (`count * size`) against the narrowest shipped platform, not the 64-bit dev host. The safety net is the HIGHEST-value place to look for a bug.
- **When a PR converts a false-merge/dedup collision by SELECTING a survivor rather than PREVENTING the merge**, clear it against a *transforming* variant where the merged entities differ observably — a pure-forwarder repro hides the misdispatch.
- **Read the actual diff hunk before trusting a reviewer's prose classification** — a CodeRabbit "Major" enum-ABI claim can be fabricated (append vs mid-insert); a refuted mechanically-checkable Major lowers the ceiling to ABSTAIN but does not clear the batch. Resolve a red sanitizer's *baseline* run (separate workflow) before ruling a leak pre-existing/introduced.
- **A negative "no behavior change" claim IS positively verifiable for a pure prose/string diff** — read every hunk; don't reflexively abstain on the "zero bits" heuristic. But on approver-source PRs, verify the DETECTORS survive, not just the labels.
- **An invariant-claiming comment is a load-bearing claim** — verify "every X does Y" mechanically across ALL sites, not just the touched one.

## The one clearing question: is the trigger reachable?

The most-repeated challenger lesson is that a 🟡 gap clears ONLY when its trigger is unreachable on a supported path or clearly inconsequential — and several atoms document conflating that with something else. The explicit correction: on slang#12347 a new test-runner's missing try/catch was cleared as "a crash is loud, not a false-green," but loudness is about the *failure* being observable, not the *trigger* being unreachable — and `SLANG_ASSERT` throws when the env var is unset, so internals tests reach it, making the trigger reachable → OPEN_GAP regardless of how loud the failure is [loud failure ≠ gap clear](../learnings/1786724279217-approver-challenger-miss-correction-loud-failure-n.md). Two more atoms are the same fallacy in other guises: "pre-existing skip ⇒ no regression" on slangpy#1109 conflated the *skip* (predates the PR) with the *absence of validation for newly-added behavior* (new) — a feature's own new code untested on a supported backend is a gap the PR introduces, and "passes on backends A/B/C" does not transfer to a dark backend D, *especially* when the change is a compiler-adjacent workaround where backend divergence is the expected failure mode [skipped backend = zero validation](../learnings/1786701590626-approver-challenger-miss-skipped-backend-test-zero.md). The distilled rule "a test that fired on backend A ≠ a test that fired on backend B" generalizes the core "a test in the diff ≠ a test that fired."

**Positive controls must discriminate.** On slang#12491 the fix's correctness hinged on hitting the *read-error* path (`E00106`) rather than the sibling *clean-EOF* path (a different diagnostic) — both exit non-zero, so a test asserting only `resultCode != 0` would pass on the WRONG path; the control MUST assert the fine-grained discriminator (the exact diagnostic), and a challenger should verify it gates on that, not the coarse signal [positive control must assert fine-grained discriminator](../learnings/1786583605296-approver-challenger-positive-control-must-assert-t.md).

## The blast radius lives at the producers, not the consumer

A family of atoms shows that clearing a gap "the PR's own handling mitigates it" or "rerouting is safe" requires enumerating everything that produces the affected value. On slang#12471 a bound — "a dropped packet is bounded by the PR's own loss-handling" — was a REACH over-claim: `HTTPPacketConnection` is core-library code with multiple consumers, and the retry mitigation lived in only *one* of them; a mitigation in one caller cannot bound the blast radius of a change to shared code (`gh api search/code` for the class → confirm EVERY consumer gets it) [REACH over-claim needs consumer enumeration](../learnings/1786616668096-approver-critique-mustfix-reach-over-claim-blast-r.md). On slang#12573 (making `ProtocolError` retryable) the same shape: `ProtocolError` is produced by TWO distinct situations (corrupted replies AND well-formed JSON-RPC error replies), and the PR retries+relabels both — the standing question for any "make outcome X retryable/recoverable" PR is *"what else already produces X?"*, answered at the producers, not the consumer the diff edits [retry that widens a bucket](../learnings/1786964870296-approver-challenger-miss-a-retry-that-widens-a-fai.md). The loc-resolver conversion PR (slang#12421) is the mirror at call sites: when a PR adds a wrapper/variant of a lookup (`findX` → `findXThrough…`), the risk is in the call sites it *didn't* convert — grep the whole tree for the OLD name and audit each remaining caller; a "tests are thin" 🟡 cluster is a *tell* that the loc-correctness surface is under-covered [loc-resolver: audit every call site](../learnings/1786735691218-approver-challenger-miss-loc-resolver-conversion-p.md). The completeness principle recurs in the type-layout clause-gap: a PR adding a `ModifiedType` case to `_createTypeLayout` left the parallel `getSimpleVaryingParameterTypeLayout` catch-all unhandled — Slang layout has TWO structurally-parallel non-shared functions, so grep for the SIBLING catch-alls and confirm the new type can't reach them; any "add a case to the big type switch" fix should be checked against every parallel switch over the same type universe [two parallel layout entry points](../learnings/1786662217774-approver-clause-gap-slang-type-layout-has-two-para.md).

## The guard itself is a suspect

Two atoms invert the intuition that a safety net is trustworthy. On slang#12446 R7, the containment guard the approver had *cited as the fix* contained the defect: `array.getCount() * Count(elementSize)` overflows the signed `int32_t` multiply on a 32-bit shipped target (WASM/32-bit ARM) *before* the containment check runs, admitting an out-of-blob span — a bounds/containment check is itself code that can overflow before it decides, so audit the type and width of every value it computes against the narrowest shipped platform, and treat the safety net as the HIGHEST-value place to look for a bug (a guard added for a prior finding carries an implicit "this is now handled" that suppresses scrutiny) [overflow inside the guard](../learnings/1786655480876-approver-challenger-miss-i-read-the-new-safety-gua.md). On slang#12569 a dedup-collision fix added a guard in `cloneInst` that *selects a survivor* rather than *preventing the false merge* (the GVN key excludes witness-table entries) — the PR's pure-forwarder test passes coincidentally, hiding a silent misdispatch; the transferable probe is to construct the minimal *transforming* variant where the two merged entities are observationally DIFFERENT and check which survivor wins — a green test on the equivalence case carries ZERO bits about the transforming case [dedup-hit guard is symptom-only](../learnings/1786975349449-approver-challenger-miss-a-dedup-hit-guard-that-on.md). A fix-UB PR is the related trap: its stated purpose creates a strong prior that the edited region is now UB-clean, but the author fixed the UB they were chasing, not every UB in the lines they touched — run the challenger on the edited statements themselves (enumerate the input domain of each float→int cast / narrowing / unaligned read), and chase a prior-commit bot finding on the same line even when a head-current re-review dropped it [fix-UB PR: check the edited statements](../learnings/1786634197324-approver-challenger-miss-fix-ub-pr-check-the-edite.md).

The safe-use counterpart: adding a `SLANG_RELEASE_ASSERT` on a diagnosed path is a red flag (it can *introduce* a release-abort — the exact failure class the fix claims to fix) until proven unreachable — the technique is to recursion-audit the producer/consumer type-shape sets and confirm every producer-non-null shape is in the consumer-non-null set, plus verify the error-count guard runs BEFORE the assert (catching the partial-success trap) [proving a new RELEASE_ASSERT safe](../learnings/1786812108237-approver-challenger-technique-proving-a-new-slang-.md).

## Verify the mechanically-checkable, from source

Several atoms are about resolving cheap, mechanically-verifiable claims against the actual artifact rather than trusting prose. A CodeRabbit "Major" ABI/enum finding on slang-rhi#841 was fabricated — it claimed a mid-enum insertion but the hunk appends at the END (append-only = ABI-safe); a mechanically-verifiable finding is the CHEAPEST to confirm and the one you MUST open before trusting the batch, but a refuted Major only *lowers the ceiling to ABSTAIN* (no verified 🔴) — it does not clear the remaining plausible-real gaps on a brand-new public API [CodeRabbit Major ABI/enum false positive](../learnings/1786803100315-approver-challenger-miss-coderabbit-major-abi-enum.md). An invariant-claiming comment in a diff is likewise load-bearing: on slang PR #12506 a comment asserted "every site that sets `failed` must diagnose an error" — verify it MECHANICALLY across all 8 `failed = true` sites (and the negative direction: the replaced diagnostic isn't orphaned), because the review doc / Devin confirm the touched site is correct but neither audits whether the stated invariant is tree-wide true [invariant-claiming comment: verify all sites](../learnings/1786801759746-approver-a-diff-s-invariant-claiming-comment-is-a-.md). On slangpy#1110 a red LeakSanitizer check was wrongly ruled "no baseline exists" — the sanitizer runs via a *separate* nightly `sanitizers.yml` workflow, not a per-commit PR check, so resolve the workflow's run history filtered by `head_branch=main` and compare base-run vs head-run annotations (base==head root-count ⇒ pre-existing; head>base ⇒ regression); "no baseline" must be proven, not assumed from a commit check-run absence, and don't assert "cannot regress" for a teardown/GC change that can alter destruction order [leak-fix: verify the sanitizer baseline](../learnings/1786969507326-approver-challenger-miss-leak-fix-pr-verify-the-sa.md).

Finally, a **calibration of the "zero bits" heuristic**: the standing probe "a negative safety claim needs a positive control" is true for *runtime/logic* diffs, but for a **pure prose/comment/diagnostic-string diff** the "no behavior change" claim is POSITIVELY verifiable by reading every hunk — don't reflexively route it to OPEN_GAP; the control exists (read the hunks). The real thing to probe on approver-source PRs is that the DETECTORS survive (harvest exit codes, `reviewers_complete`, clause UNEVALUABLE), not just the emitted verdict labels [negative no-behavior-change is verifiable for prose diffs](../learnings/1786970495420-approver-challenger-miss-negative-no-behavior-chan.md).

A **dead-code/born-dead removal proof** must respect the checkout's own limits. The approver's slang clone (`/workspace/agent/slang`) is a **shallow** clone, so `git log --all -S<sym>` cannot see history before the shallow boundary AND reports spurious *whole-file additions* at each boundary commit — meaning any "no call site ever existed across full history / born-dead across full history" claim is literally unprovable there (the traversal is truncated). Before writing any "never/always/across all history" claim about a symbol, run `git rev-parse --is-shallow-repository`; if true, rest the conclusion on **fixed reference points** instead — the introduction commit (`git log --oneline -S<id> -- <file> | tail -1`, proving it was added already-unused), the PR merge-base, `origin/master`, and the PR head — each verified with a ref-qualified `git grep` that returns only the definition and no invocation. That is strictly stronger than a history scan anyway: what makes a removal safe is that no caller exists *now* (merge-base/master/head), plus #1 ruling out "born with a caller." And a claim that contradicts a caveat you wrote elsewhere in the same audit trail (here: "born-dead across full history" vs your own note that the clone is shallow) is a self-inconsistency the OUTPUT_REVIEW gate reliably catches — scan your own artifacts for that before requesting critique; leave a reviewer's verbatim prose (e.g. Devin's "uncalled since") untouched under `## Devin`, and scope only your own approver-authored claims to the evidence [[on a shallow clone prove born-dead from fixed reference points, never "across full history"]](../learnings/1788979080856-approver-critique-mustfix-on-a-shallow-clone-prove.md) (slang#12866).

## When the coverage that exists watches the wrong path

Two shapes where a full-looking test suite / green signal carries almost no bits about the code the PR actually changed.

**An interface-adapter PR moves the implementation OUTSIDE the upstream conformance suite.** When a PR implements an upstream interface locally and installs it process-wide (slangpy#1098: `NanothreadTaskPool : rhi::ITaskPool`, installed for all of slang-rhi via `rhi::getRHI()->setTaskPool(...)`), the upstream project already owns a conformance suite for that interface — but it runs against upstream's *own* implementations, never against your adapter. slang-rhi's `tests/test-task-pool.cpp` (`testWorkStealingWaitTaskFromCallback`, `testWorkStealingNestedWait`, …) exercises `BlockingTaskPool`/`ThreadedTaskPool`; substituting a new implementation silently moves it out of that safety net, so the PR's local test file becomes the *only* check and its coverage gaps become the product's coverage gaps. The probe: read the interface's documented contract at the *pinned upstream commit* (a submodule bump can *change* the contract), enumerate which contract directions upstream's conformance tests cover, and apply the both-directions control per direction. Reachability here is a **contract** question, not a call-graph one — "today's only caller waits from the submitting thread" does not clear a direction the header blesses and upstream conformance-tests (here waiting from *inside* a callback, whose narrower "executes only ready tasks from `group`" scope is exactly what the doc cites as making callback-side waiting safe). A blessed-and-conformance-tested direction the adapter never exercises is a nameable `ABSTAIN_POLICY:OPEN_GAP`, not a nit; the cheap remedy is to run the upstream conformance suite against the new adapter [[approver/challenger-probe] Interface-adapter PRs: upstream conformance tests do NOT run against your adapter](../learnings/1786386180624-approver-challenger-probe-interface-adapter-prs-up.md).

**A coverage-counter coalescing change can over-report with green CI and byte-identical LCOV.** On slang#12683 ("Coalesce line coverage counters per straight-line region") the pass groups consecutive line markers in one basic block onto one counter, splitting only at instructions that "may abandon the invocation" (`discard`, `abort`, unresolvable call, or a `mayNotReturn` callee). That test under-approximates for ray-tracing hit terminators `IgnoreHit`/`AcceptHitAndEndSearch`: they end the invocation but lower to a `GenericAsm` modeled as ordinary `void` core-module functions, so `mayNotFallThrough` returns false at their call site and markers on both sides coalesce onto one counter → the after-marker over-reports (the ONE unsound direction; every other `mayNotReturn` imprecision over-approximates and only adds safe extra splits). CI-green + byte-identical LCOV on the bundled demos carries near-zero bits here: no test triggers the RT path, and even if hit the failure is a wrong *number*, never a compile/validation error a codegen diff would surface. The meaningful control is a closesthit/anyhit shader with an unconditional `IgnoreHit()`/`AcceptHitAndEndSearch()` and markers on both sides in the same block, asserting the after-marker is NOT coalesced. (Related same-PR win, correctly fixed: a memoized `mayNotReturn` cycle-break cached an optimistic `false` that could poison non-recursive callers — its "recursion rejected by checkForRecursiveFunctions" justification is false on CPU/CUDA, coverage's primary targets — so the author moved to a conservative over-approximating cycle-break.)
