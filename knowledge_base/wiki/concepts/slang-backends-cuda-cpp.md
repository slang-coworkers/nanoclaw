# Slang CUDA & CPU/C++ Backends: C-Family Emitter Codegen

The CUDA and CPU/C++ targets share one code path — `CPPSourceEmitter` (`source/slang/slang-emit-cpp.cpp`), which `CUDASourceEmitter` inherits (`slang-emit-cuda.h:44`). This shared "C-family emitter" is distinct from the SPIR-V and HLSL paths, and its lowering choices produce a target asymmetry that has surfaced as a real performance bug.

## TL;DR

- **CUDA and CPU/C++ are one emitter, so a C-family emit bug is never CUDA-only.** `CUDASourceEmitter` inherits `CPPSourceEmitter`; scope any finding to both targets before recording it.
- **A multi-component swizzle READ re-emits its base once per component.** The C-family emitter lowers it to a per-component brace initializer `float3{ base.x, base.y, base.z }`, calling `emitOperand(getBase())` inside the loop — so a folded base (texture fetch, helper call, `saturate(...)`) is textually duplicated N×.
- **The multi-use fold guard cannot see this.** `shouldFoldInstIntoUseSites` only refuses to fold on >1 *IR* uses, and a multi-element swizzle is a SINGLE IR use that expands to N *textual* references.
- **The trigger is a non-trivial folded base, not the vector type.** `.rgb` of a register-resident local emits one fetch and is fast; a minimal local-base repro is therefore not a repro at all.
- **`float3`'s 12-byte CUDA layout is a red herring for this perf bug** — the layout fact is true, the causal attribution to register pressure was retracted. Values are always correct; this is codegen quality, not a wrong-result bug.
- **Confirm emit-duplication GPU-free by counting occurrences, not lines.** `slangc repro.slang -target cuda -entry <e> -stage compute -o k.cu` (or `-target cpp`), then `grep -o tex2Dfetch | wc -l` — the whole brace initializer is on ONE line, so `grep -c` reports 1 even when the fetch appears 3×.
- **`SLANGPY_PRINT_GENERATED_SHADERS=1` dumps the SlangPy wrapper, not the emitted CUDA C++** — wrong tool for an emit question.
- **User workaround: remove the folded expression from under the swizzle.** Bind the fetch to a named local (`float4 s = tex[q];` then read `s.r/s.g/s.b`) and write via lane assignment instead of a constructor-swizzle (`float4(shade(uv).rgb, a)` calls `shade` 3×).
- **SlangPy does not vendor the Slang compiler** — its `.gitmodules` has only `external/slang-rhi`, Slang is a prebuilt FetchContent binary. Any "vector arithmetic is slow/wrong on CUDA" report whose math lives in the user's `.slang` body is an upstream `shader-slang/slang` codegen issue.
- **`-target cpp` struct layout is C/C++ natural alignment (`CPULayoutRulesImpl`), not std140/std430** — a struct shared with a GPU buffer must be paired with `-fvk-use-c-layout`.
- **`export` roots a host-callable function against DCE; `public` does not.** `export`→`HLSLExportModifier` adds `HLSLExportDecoration` **and** `KeepAliveDecoration`; `public` adds only `PublicDecoration`, so `public __extern_cpp` + `-whole-program` emits nothing. The gap is at `getHLSLExports()`, which checks `HLSLExportDecoration` and never `KeepAlive`.
- **Use `-dump-ir` to tell a link-drop from an emit-filter drop:** "appears once then vanishes" means dropped at linking; "persists to the final module" means filtered at emit.
- **An unused global of a resource type with no CPU prelude struct (RTAS, `RasterizerOrdered*`) breaks `host-callable`**, and `GlobalParams` fields are never DCE'd (stable host layout), so the fix is a correctly sized prelude type, never dropping the global.
- **`-target hpp` for a `__extern_cpp` compute entrypoint emits wrapper BODIES, not prototypes** — the three CPU wrappers call a `_example` workhorse emitted nowhere, so the header won't compile. Fix is to guard the wrapper loop in `CPPSourceEmitter::emitModuleImpl` on `shouldEmitOnlyHeader()` and emit prototypes only; no forward-decl is needed once the bodies are gone.
- **A green SPIR-V/HLSL run does not clear CUDA for a param-passing change.** `getSharedBaseAddr`'s `__cvta_generic_to_shared(($0).m_data)` assumes by-value; by-ref emits `((&data)).m_data` and nvrtc rejects it. The groupshared-by-ref inlining lives only in `GLSLResourceReturnFunctionInliningPass` (Khronos targets), so vk masks it — `test-linux-release-gcc-x86_64-sm80`'s `tests/neural/` + `tests/cooperative-matrix/` are the canary.
- **Before changing any param-passing convention, grep the neural/coopmat stdlib for `__intrinsic_asm` bodies that deref `$0` with `.member`.**
- **A case-less `__target_switch` in `*.meta.slang` silently emits an EMPTY helper body** — a no-op kernel (PTX `ret;`) at exit 0 with no diagnostic. Suspect it whenever a shader "compiles to an empty kernel"; grep the emitted `.cu` for the `#line` marker that pins the source line.
- **Case-PRESENT plus an un-instantiated prelude template fails LOUDLY** (NVRTC "referenced but not defined"). Silent-empty and loud-undefined are opposite signatures of similar-looking texel-type gaps — do not dedup them.
- **A "make-it-a-no-op" prelude typedef is safe only if the type's METHODS have no target case for that backend.** `SamplerComparisonState`'s dummy CUDA typedef is safe because `SampleCmp` and siblings are `__target_switch`ed with no `cuda` case, so calling one errors loudly.
- **Use `$TR` (call return type) when an intrinsic string needs the result type spelled** — `$T<n>` unwraps a texture operand to its ELEMENT type, so `tex2Dgather<$T0>` emitted a scalar into a `float4` and NVRTC rejected the constructor. The one-token `$T0`→`$TR` fix generalizes to any CUDA texture op returning a vector wider than the element type.
- **`precise` on a LOCAL is emitted by the shared `CLikeSourceEmitter::emitTempModifiers`, so it leaks to all four C-like targets** — valid on HLSL+GLSL, invalid on CUDA/C++/Metal/WGSL. Gate at emit on source-language support, not at the target-agnostic producer.
- **Check whether the "extra" inputs are also broken before narrowing a guard called too broad.** `tex*fetch_int<T>` has NO half instantiation at ANY width (prelude instantiates float/uint/int only), so excluding `half3` from `static_assert(!__isHalf<T>())` would reintroduce the bug — half/half2/half3/half4 all hit E41400.
- **One CUDA-illegal entry point sinks its clean siblings.** Slang capability-checks ALL `[shader]` entry points at module load, so a typed `Buffer<T>`/`RWBuffer<T>` EP fails `load_program` for entry points that never reference it. Wrap the offending EP in `#ifndef __TARGET_CUDA__` — the preprocessor runs before the capability check. Do NOT guard `StructuredBuffer`/`RWStructuredBuffer`/`ByteAddressBuffer`; they lower to real pointers and work on CUDA.
- **A `-target ptx` repro is a compile check, not a GPU run.** `//TEST:SIMPLE: -target ptx` needs only NVRTC + FileCheck, so don't punt it as hardware-gated. Coworker containers have an NVIDIA L40S (CUDA 12.6 `nvcc`/`ptxas` + NVIDIA Vulkan; the 2026-09-28→10-16 no-GPU period was a host passthrough outage), so CUDA execution repros run locally too. Confirm with `nvidia-smi -L` each session.
- **Editing `hlsl.meta.slang` requires the core-module-header regen** before the change is observable in a built `slangc`.
- **A global templated CUDA vector `operator` MUST be SFINAE-gated** to the registered vector types (via a traits table keyed on `SlangCudaVectorTraits<T>::kWidth > 0`) or it becomes a candidate for every type in the program; keep `__half2` packed intrinsics as NON-template overloads so exact-match resolution keeps the packed path. The CUDA vector types are distinct structs (not one class template), and `bool2/3/4`/`__half3/4` are prelude-defined, so verify a prelude refactor offline with `nvcc -std=c++17`.
- **CPU/CUDA operator typing belongs in the preludes, not in IR casts**: mixed-type vector shifts got prelude `<<`/`>>` overloads plus an own-type scalar splat (#13684), not a result-type cast of the amount.
- **`__exp2f` (base-2 exp) does NOT exist as a CUDA device intrinsic** — so under `-fp-mode fast`, F32 exp2 stays precise (`::exp2f`) while `__sinf/__cosf/__tanf/__sincosf/__logf/__log2f/__log10f/__expf/__powf`(+`__exp10f`) redirect. Always verify each `__*f` fast-math name against nvcc, never a from-memory triage list.
- **`__intrinsic_asm` has TWO `$`-marker families reading DIFFERENT operand sources:** plain `$N` reads the ENCLOSING call's args (guarded → E99997 on OOB), bracket `$[N]` reads the intrinsic carrier's OWN operands (UNGUARDED → raw SIGSEGV on OOB). A statement-form `__intrinsic_asm "text", args;` value-arg is read by `$[N]` but silently DROPPED by `$N` — read the marker-dispatch switch, not a candidate report's one-line summary.

## The float3/swizzle-base re-evaluation perf bug (slang#12073, from slangpy#1059)

**Symptom:** a hot loop reading a multi-component swizzle (`.rgb`/`.xyz`) runs ~3× slower on CUDA (2.87× on an L40S/NVRTC 13) than reading a whole `float4` or accumulating in named scalars; Vulkan (SPIR-V) and D3D12 (HLSL) show no penalty. Values are correct — this is codegen quality, not a wrong-result bug.

**Root cause — the base is re-emitted once per component.** `CPPSourceEmitter`'s `kIROp_Swizzle` handler (`slang-emit-cpp.cpp:1642-1719`, per-component loop at 1692-1716) lowers a multi-component swizzle READ to `float3{ base.x, base.y, base.z }` and calls `emitOperand(getBase())` inside the loop. When `shouldFoldInstIntoUseSites` (`slang-emit-c-like.cpp:1685-1687`) folds the base into its use sites — a texture fetch, buffer load, or helper call — the fetch is textually duplicated N×. The fold guard refuses only on >1 *IR* uses, and the swizzle is a SINGLE IR use that expands to N *textual* references. Repro fetch counts at HEAD `8f0c3515d`: `f4_all`=1, `f3_loop`=**3**, `f3_epi`=1. SPIR-V emits one `OpVectorShuffle` and HLSL a native `.xyz`, both evaluating the base once — the entire backend asymmetry ([C-family swizzle re-evaluates base per component](../learnings/1783910573494-slang-c-family-swizzle-re-evaluates-base-per-compo.md)).

**Trigger boundary:** only a non-trivial folded base (fetch / helper call / `saturate(...)`) is slow. `.rgb` of a register-resident local (the `f3_epi` control) emits one fetch and is fast, so a minimal local-base repro is not a repro — a production epilogue whose `.rgb` base was an expensive helper expression is ([slowdown is swizzle-base re-evaluation, not float3 layout](../learnings/1783910857099-float3-vec3-cuda-slowdown-is-swizzle-base-re-evalu.md)).

**Fix (shipped, draft PR #12078):** `CPPSourceEmitter::shouldFoldInstIntoUseSites` (override at `slang-emit-cpp.cpp:1931-1970`) already refuses to fold a vector/matrix value whose user is a reshape/cast (1943-1951), because "the implementation of cast will have multiple references to it." A multi-element swizzle base is the identical situation, so the fix returns `false` for an `IRSwizzle` user with `getElementCount() > 1` whose base is the fold candidate; the base materializes as a temp through existing machinery and CUDA `f3_loop` drops from 3 fetches to 1 ([fix seam](../learnings/1783910573494-slang-c-family-swizzle-re-evaluates-base-per-compo.md), [#12073 fix: swizzle-base fold guard implemented](../learnings/1783939557238-slang-12073-fix-swizzle-base-fold-guard-implemente.md)).

**User workaround:** remove the folded expression from directly under the swizzle — bind the fetch to a named local (`float4 s = tex[q];` then read `s.r/s.g/s.b`) and write via lane assignment (`v.a = a; dst[tid] = v;`) instead of a constructor-swizzle (`float4(shade(uv).rgb, a)` calls `shade` 3×) ([float3 .rgb slowdown is base re-evaluation, not layout](../learnings/1783911049805-slang-cuda-cpp-float3-rgb-swizzle-slowdown-is-base.md)).

**Superseded: the vec3-layout hypothesis.** The first triage ([float3 loop arithmetic ~3x slower than float4](../learnings/1783908909248-slang-cuda-float3-loop-arithmetic-3x-slower-than-f.md)) attributed the slowdown to `float3`'s 12-byte/4-byte-aligned CUDA layout (vs `float4`'s 16/16) defeating NVRTC register allocation, and called it CUDA-only. Both are false: GPU-free emitted-`.cu` inspection proved base re-evaluation, scoped to CUDA **and** CPU/C++ (shared emitter), and the `f3_epi` control falsifies the layout cause ([correction](../learnings/1783911049805-slang-cuda-cpp-float3-rgb-swizzle-slowdown-is-base.md)). The emission form that note observed (`float3{a,b,c}` vs `OpVectorShuffle`) was right; only the register-spill inference is retracted. Its ownership rule stands: SlangPy does not vendor Slang (prebuilt FetchContent binary) and is transparent to vector types, so a CUDA vector-math report whose math lives in the user's `.slang` body is an upstream `shader-slang/slang` codegen issue ([ownership](../learnings/1783908909248-slang-cuda-float3-loop-arithmetic-3x-slower-than-f.md)).

**Reusable rules.** Confirm GPU-free with `slangc repro.slang -target cuda -entry <e> -stage compute -o k.cu` (or `-target cpp` — same emitter), then count occurrences with `grep -o tex2Dfetch | wc -l`; the whole initializer is on one line, so `grep -c` reports 1. `SLANGPY_PRINT_GENERATED_SHADERS=1` dumps the SlangPy wrapper, not the emitted CUDA C++ ([confirmation recipe](../learnings/1783910573494-slang-c-family-swizzle-re-evaluates-base-per-compo.md)). A layout fact being true does not make it the cause: count operations in the actual emitted code before recording a mechanism ([triage meta-lesson](../learnings/1783910857099-float3-vec3-cuda-slowdown-is-swizzle-base-re-evalu.md)). This is unrelated to Metal PR #10031 packed-vec3, which is a buffer-layout stride concern.

## CPU/C++ Host Targets: Struct Layout, `-target hpp`/`cpp` Rooting, Header-Only Prototypes (#9401/#9403)

`slangc -target cpp` uses C/C++ natural-alignment layout (`CPULayoutRulesImpl`), not std140/std430, so a struct shared between Slang and C++ that also backs a GPU buffer must be paired with `-fvk-use-c-layout` ([C++ target struct layout != std140/std430](../learnings/1783986652112-slang-c-target-struct-layout-does-not-match-std140.md)).

**`export` roots against DCE; `public` does not.** `export`→`HLSLExportModifier` adds `HLSLExportDecoration` **and** `KeepAliveDecoration`; `public` adds only `PublicDecoration`, so `public __extern_cpp` + `-whole-program` emits nothing and only `export __extern_cpp` works ([export without entrypoint works via -whole-program](../learnings/1784381336769-slang-target-hpp-cpp-export-without-entrypoint-wor.md)). A maintainer's one-liner ("give `__extern_cpp` a `KeepAliveDecoration`") is necessary but insufficient: the asymmetry is a linking-root gap at `getHLSLExports()`, which checks `HLSLExportDecoration` and never `KeepAlive`, and the separate "requires an entrypoint" gate is decoration-independent (`-whole-program` is the existing answer). In `-dump-ir`, "appears once then vanishes" is a link drop; "persists to the final module" is an emit-filter drop ([public-vs-export is a LINKING-ROOT gap](../learnings/1784383334778-slang-host-target-public-vs-export-emission-asymme.md)).

**`-target hpp` on a `__extern_cpp` compute entrypoint** emits the three CPU wrappers (`example`/`_Group`/`_Thread`) as full definitions calling a `_example` workhorse emitted nowhere, so the header won't compile: the wrapper loop in `CPPSourceEmitter::emitModuleImpl` never consults `shouldEmitOnlyHeader()` ([hpp emits wrapper bodies not decls](../learnings/1784381106344-slang-9403-target-hpp-emits-wrapper-bodies-not-dec.md)). Guarding that loop to emit prototypes only is the whole fix — no forward-decl of `_example` is needed once the bodies are gone (validated with g++ against the `-target cpp` output) ([fix is prototypes only, no fwd-decl](../learnings/1784382795938-slang-target-hpp-compute-entrypoint-emits-wrapper-.md)). Both reproduce GPU-free with a Debug slangc.

**An unused global resource with no prelude type breaks `cpp`/`host-callable`/`shader-sharedlib` (#13705).** Every global shader parameter with a uniform size becomes a field of `GlobalParams` (slang-ir-collect-global-uniforms.cpp:188-276). That struct is a binary-interface type, so DCE never drops a field: the reflected host layout has to stay stable, and "drop the unused global" is never the fix. `_getResourceTypePrefix` in slang-emit-cpp.cpp prints HLSL names (`RaytracingAccelerationStructure`, `RasterizerOrderedStructuredBuffer`, `RasterizerOrderedByteAddressBuffer`) that `prelude/slang-cpp-types.h` never defines, so a declaration that is never used still fails in clang/gcc with "unknown type name". The fix is a prelude type of the size the layout reserves (the CPU layout gives RTAS one pointer, slang-type-layout.cpp:1604), as CUDA did for RTAS by always typedef'ing `OptixTraversableHandle` (#8411). `-emit-cpu-via-llvm` is unaffected, because slang-ir-lower-cpu-resource-types.cpp lowers these types to `void*`. CPU user-code atomics are a documented non-feature (docs/cpu-target.md: only the compiler-generated integer `AtomicAdd` for shader coverage). Widening the `Interlocked*` `[require]` alone would turn E36107 into E99999 for every op except add, because the C++ emitter lowers only `kIROp_AtomicAdd`; the CPU `RWByteAddressBuffer` also lacks `asStructuredBuffer` ([CPU C++ prelude: unused resource types with no prelude struct break host-callable](../learnings/1792162041270-cpu-c-prelude-unused-resource-types-with-no-prelud.md)).

## CUDA Arch Selection: `-capability cuda_sm_NN` Is Not a Selector, and an Explicit `-Xnvrtc -arch` Skips SM Checks (#13198, #13286)

Do NOT describe `-capability cuda_sm_NN` as a working CUDA/PTX target selector (HEAD 4233b2c, NVRTC 12.6). (1) **Bounded, ceiling 9.0**: `cuda_sm_*` atoms exist only for {1_0…9_0}, so `cuda_sm_7_5`/`8_6`/`10_0` give `error[E00014]: unknown profile`, and `getCUDASMVersionForAtom` caps at 9.0. (2) **A FLOOR via max(), not a pin**: NVRTC arch = `max(NVRTC-version floor, requested capability)`, so `-capability cuda_sm_1_0` emits `.target sm_50` on NVRTC 12.6. (3) **`linkWithOptions()` is inert for the arch** (same class as #13197). New atoms are deferred in #12839 for `.slang-module` serialized-ID compat ([`-capability cuda_sm_NN` is not a usable arch selector](../learnings/1790003555136-slang-cuda-capability-cuda-sm-nn-is-not-a-usable-a.md)).

PR #13286 (merged 2026-09-28) changed the explicit route. Before it (e.g. v2025.24) Slang always appended its own `-arch=compute_NN`, so a user `-Xnvrtc --gpu-architecture=` doubled the arch (NVRTC 12.6: "defined more than once"). Now an explicit `-Xnvrtc -arch=`/`--gpu-architecture=` skips Slang's derived-arch block (`slang-nvrtc-compiler.cpp:1324` gate, block `:1325-1377`), the adapter's ONLY read of `options.requiredCapabilityVersions`. Nothing then checks shader minimums (`__cuda_sm_version`, emitter minimums such as wave match 7.0 or coopmat 8.0, `_cuda_sm_*` atoms): `__cuda_sm_version(9.0)` with `-Xnvrtc --gpu-architecture=compute_75` returns rc 0 and `.target sm_75` with no diagnostic, even under `-restrictive-capability-check`. A too-low target fails only if NVRTC hits an undefined intrinsic (WaveMatch + compute_60 → `__match_all_sync is undefined`), so check which side of #13286 a binary is on. Whether an override should still diagnose a higher minimum is open on #13198 (2026-10-05); SlangPy #1199 depends on it ([explicit -Xnvrtc -arch bypasses collected CUDA SM requirements (post-#13286)](../learnings/1791190691660-slang-nvrtc-explicit-xnvrtc-arch-post-13286-bypass.md)).

To reproduce DownstreamArgs forwarding to NVRTC through the Slang API with a PTX target (#12861), do not use `--gpu-architecture=compute_NN` as the harmless first entry: Slang passes its own arch flag, so NVRTC fails with "defined more than once" whatever the entry order, and the test proves nothing. Use `-DFOO=1` as the neutral entry and `--this-option-must-fail` as the sentinel. On v2026.16.1 the order [neutral, sentinel] compiles, which is the bug; on v2026.19 (after PR #12900) it fails with "unrecognized option". `IModule::findEntryPointByName` returns null unless the function has `[shader("compute")]`, so check the result before calling through it ([NVRTC DownstreamArgs repro: don't use --gpu-architecture as the neutral arg](../learnings/1792155142006-nvrtc-downstreamargs-repro-don-t-use-gpu-architect.md)).

## groupshared-by-ref Regresses CUDA Emit While a vk-Only Inline Pass Masks It

When `groupshared` params become pass-by-reference (#10641 / PR #11709), the neural stdlib intrinsic `getSharedBaseAddr` — `__cvta_generic_to_shared(($0).m_data)`, which assumes `$0` arrives by value — emits `((&data)).m_data`, `.m_data` on a pointer, and nvrtc rejects it. SPIR-V stays green because the groupshared-by-ref inlining lives only in `GLSLResourceReturnFunctionInliningPass` (Khronos targets) and the emit-side unwrap was added only to `slang-emit-hlsl.cpp`, never `slang-emit-cuda.cpp`. A green SPIR-V/HLSL run does not clear CUDA; `test-linux-release-gcc-x86_64-sm80`'s `tests/neural/` + `tests/cooperative-matrix/` (nvrtc + Vulkan) are the canary ([groupshared param by-ref regresses CUDA emit](../learnings/1784741954379-groupshared-param-by-ref-regresses-cuda-emit-vk-on.md)).

## CUDA/PTX Texel-Type and Prelude Gaps (#12274–#12300)

**Silent-empty and loud-undefined are opposite signatures of look-alike gaps; do not dedup them.** `Buffer<T>.Load` for CUDA (#12274) hits a case-less `__target_switch` in `hlsl.meta.slang` → an empty helper body → a no-op kernel (PTX `ret;`) at exit 0 with no error; suspect it whenever a shader "compiles to an empty kernel", and grep the emitted `.cu` for the `#line` marker that pins the source line ([case-less __target_switch silently emits an empty body](../learnings/1785371749664-case-less-target-switch-in-meta-slang-silently-emi.md)). Half-typed `_Texture<T>.Load` (#12277) has a *present* cuda case that calls an un-instantiated prelude template (`tex2Dfetch_int<__half4>` declared, never defined) → a loud NVRTC "referenced but not defined" error ([half-texel gap: loud undefined-template vs #12274 silent-empty](../learnings/1785373293265-cuda-texture-load-half-texel-gap-loud-undefined-te.md)). Its fix, `static_assert(!__isHalf<T>())` in the cuda case, is not too broad: `tex*fetch_int<T>` has no half instantiation at ANY width (the prelude instantiates float/uint/int only), so a reviewer's "exclude half3" would reintroduce the bug (half/half2/half3/half4 all → E41400). Before narrowing a guard flagged as too broad, check whether the extra inputs are also broken ([half3 is NOT overreach](../learnings/1785465186257-cuda-half-texture-load-fix-half3-is-not-overreach-.md)).

**`SamplerComparisonState` (#12278/#12300).** The CUDA prelude defines a dummy `SamplerState` typedef but no comparison counterpart, so `SamplerComparisonState g_scmp;` breaks CUDA/PTX ([no prelude typedef](../learnings/1785373084246-cuda-samplercomparisonstate-has-no-prelude-typedef.md)). The symmetric one-liner `typedef SamplerComparisonStateUnused* SamplerComparisonState;` is safe because `SampleCmp` and its siblings in `hlsl.meta.slang` are `__target_switch`ed with no `cuda` case: calling one fails loudly, and a declared/bound-but-unused sampler only occupies uniform space as a harmless pointer. The general reviewer test for any "make-it-a-no-op" prelude fix is whether the type's *methods* have a target case for that backend ([no-op typedef is safe](../learnings/1785445968024-cuda-samplercomparisonstate-no-op-prelude-typedef-.md)).

**`Gather` result type (#12276): use `$TR`, not `$T0`.** `$Tn` unwraps a texture arg to its element type (`slang-intrinsic-expand.cpp`), so `tex2Dgather<$T0>` emitted a scalar `tex2Dgather<float>` into a `float4` and NVRTC found no suitable constructor. The one-token fix (both `Gather` overloads) generalizes to any CUDA texture op returning a vector wider than the element type. A `//TEST:SIMPLE: -target ptx` directive is an end-to-end NVRTC compile-check needing no GPU, so don't punt it as hardware-gated ([Gather $T0 vs $TR](../learnings/1785417049714-cuda-gather-t0-vs-tr-marker-local-gpu-nvrtc-filech.md)). For execution, coworker containers have an NVIDIA L40S ([current fact](../learnings/1792133264162-coworker-containers-have-an-nvidia-l40s-gpu-cuda-vulkan.md)); the 2026-09-28→10-16 no-GPU period was a host passthrough outage ([outage record](../learnings/1792089571497-agent-containers-have-no-gpu-since-2026-09-28-host.md)). Confirm with `nvidia-smi -L`.

**`precise` on a local (#12279)** is emitted verbatim by the shared `CLikeSourceEmitter::emitTempModifiers`, so it leaks to all four C-like targets, not the two the title named: valid on HLSL+GLSL, invalid on CUDA/C++/Metal/WGSL. Guard on source-language support at emit, not at the target-agnostic producer ([precise leaks to 4 C-like targets](../learnings/1785373326278-precise-local-qualifier-leaks-to-4-c-like-targets-.md)). The whole cluster reproduces GPU-free (Debug slangc + NVRTC/nvcc 12.6, emit-and-inspect).

## One CUDA-Illegal Entry Point Sinks Its Siblings: Guard It with `#ifndef __TARGET_CUDA__`

Slang capability-checks ALL `[shader]` entry points at module load, so one EP using a CUDA-illegal feature (typed `Buffer<T>`/`RWBuffer<T>` → E36107) fails `load_program` for siblings that never reference it. Wrap the offending EP in `#ifndef __TARGET_CUDA__ … #endif`: the preprocessor runs before the capability check, and `__TARGET_CUDA__` (family: `__TARGET_D3D12__`/`__TARGET_VULKAN__`/`__TARGET_METAL__`) is a session macro for the CUDA target. Do NOT guard `StructuredBuffer`/`RWStructuredBuffer`/`ByteAddressBuffer`; they lower to real pointers and work on CUDA. This shipped as slangpy PR #1083 to unblock slang#12289's required `SlangPy Tests` check, and because slangpy's `ci-latest-slang.yml` checks out slangpy's default branch, the guard had to MERGE to slangpy main before the slang PR could go green — a prerequisite, not a follow-up ([guard test-only CUDA EPs with `#ifndef __TARGET_CUDA__`](../learnings/1785453604826-guard-test-only-shader-eps-from-cuda-with-ifndef-t.md)).

## `__intrinsic_asm` Markers, Prelude Vector Operators, Fast-Math Transcendentals

**`$N` reads the CALL; `$[N]` reads the carrier's OWN operands.** In `slang-intrinsic-expand.cpp`, plain `$N` (digit case, `:366-374`) expands against `m_args`, the enclosing `m_callInst`'s operands; out-of-bounds trips the `:370` `SLANG_RELEASE_ASSERT` → E99997. Bracket `$[N]` (`case '['`, `:868-892`) expands against `m_intrinsicInst->getOperand(1+argIndex)`, the intrinsic carrier's own operands (the `IRGenericAsm` for a statement-form `__intrinsic_asm`), and that `getOperand` is UNGUARDED, so an out-of-bounds `$[N]` is a raw SIGSEGV. For `__intrinsic_asm "text", args;` the args are read by `$[N]` (`USE($[0]), v` → `USE(&v_0)`) and silently dropped by `$N` — which is why the core module's `__sizeOf<T>()` (`$[0], T`) works. A slang#12529 candidate report's "the GenericAsm value-operands have no reader in any emitter" was wrong; read the `_emitSpecial` marker-dispatch switch and enumerate every marker case rather than trusting a summary ([intrinsic_asm has TWO marker families](../learnings/1786631581576-intrinsic-asm-has-two-marker-families-with-differe.md)). Like `$TR` vs `$T0` above, the lesson is knowing exactly which operand a `$`-marker reads.

**Templated CUDA prelude vector operators must be SFINAE-gated and coexist with packed `__half2` overloads (PR #12410).** The CUDA vector types (`int2`, `char4`, `__half2`, plus prelude-defined `bool2/3/4`, `__half3/4`) are distinct structs, not one class template, so `template<class T,int N> VecN<T,N> operator+` is impossible; use a traits table (`template<class T> struct SlangCudaVectorTraits;` left undefined, one specialization per vector type carrying `kWidth`/`BoolVector`/`kIsIntegral`). A global templated `operator+(T,T)` MUST be constrained to registered types (`SlangCudaVectorTraits<T>::kWidth > 0` via a hand-rolled two-line `enable_if`; the NVRTC prelude has no `<type_traits>`), or it becomes a candidate for every type — `struct Foo{int x,y;}` and scalar `int+int` misbehave without the gate. `__half2` arithmetic stays NON-template overloads on `__hadd2`/`__hsub2`/`__hmul2`/`__h2div`/`__hneg2` (one `add.f16x2` instead of two `add.f16`): the exact-match non-template wins, keeping PTX byte-identical, while `__half2` compare/logical and all `__half3/4` operators fall through to the templates (the prelude `#define`s `__CUDA_NO_HALF2_OPERATORS__` before `<cuda_fp16.h>` so the toolchain's operators don't collide). `if constexpr` width dispatch is well-formed only inside a template, and `__device__` lambdas need `--extended-lambda`, which NVRTC doesn't pass — splice the operator token directly. Verify offline with `nvcc -std=c++17` (the flag Slang's NVRTC path passes, `source/compiler-core/slang-nvrtc-compiler.cpp`), and report the win structurally (684 operator definitions per TU → 21 templates + 13 packed overloads), not as wall-clock compile time (a 33-kernel PTX sweep was 32/33 identical opcode multisets; bool4 was one instruction shorter) ([templated vector operators must be SFINAE-gated](../learnings/1787075202710-cuda-prelude-templated-vector-operators-must-be-sf.md)).

**Operator typing belongs in the preludes; the IR stays type-faithful (#13553).** PR #13562 fixed `int3 >> uint3` on CPU/CUDA by casting both shift operands to the result type in `unifyBinaryExprOperands`. Maintainer jkwak-work asked whether the fix belonged in the CUDA prelude; given master-build evidence for both options, he closed it and opened #13684 instead. #13684 adds mixed-type `<<`/`>>` vector operators to both preludes (slang-cuda-prelude.h, slang-cpp-types-core.h) and keeps one IR change, `splatScalarOperandsOfVectorShift`, which splats a scalar shift operand to a vector of its OWN type, the same rule as Metal/WGSL `legalizeScalarOperandsToMatchComposite`. So for a CPU/CUDA operator-typing bug, make the prelude carry the operator's type semantics and do not cast the shift amount in IR. Asking with evidence settled the design in one round ([Mixed-type vector shifts: maintainer preferred prelude operators + own-type scalar splat](../learnings/1792165281967-mixed-type-vector-shifts-maintainer-preferred-prel.md)).

**Fast-math transcendentals (slang#12619): `__exp2f` does not exist.** Under `-fp-mode fast` exactly nine F32 wrappers redirect to a hardware-approximate intrinsic — `__sinf, __cosf, __tanf, __sincosf, __logf, __log2f, __log10f, __expf, __powf` — plus `__exp10f`. nvcc 12.6 rejects `__exp2f` ("identifier __exp2f is undefined in device code"), so F32 exp2 stays precise (`::exp2f`) alongside atan2, asin, acos, atan, and sqrt; a triage memo listing exp2 as redirectable was wrong. Verify every `__*f` name against nvcc: a minimal `__device__` harness mirroring the prelude wrappers, `nvcc -std=c++17 -c` twice (default and `-DSLANG_CUDA_ENABLE_FAST_MATH=1`), then `-ptx` both and `grep -cE '\.approx\.'` — the fast build must compile and show more approx ops (2 min, no 20-min build; nvcc is at `/usr/local/cuda-12.6/bin/nvcc`) ([__exp2f does NOT exist](../learnings/1787147170237-cuda-fast-math-redirectable-transcendentals-exp2f-.md)).
