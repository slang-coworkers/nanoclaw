# Slang CUDA & CPU/C++ Backends: C-Family Emitter Codegen

The CUDA and CPU/C++ targets share one code path — `CPPSourceEmitter` (`source/slang/slang-emit-cpp.cpp`), which `CUDASourceEmitter` inherits (`slang-emit-cuda.h:44`). This shared "C-family emitter" is distinct from the SPIR-V and HLSL paths, and its lowering choices produce a target asymmetry that has surfaced as a real performance bug.

## TL;DR

- **CUDA and CPU/C++ are one emitter, so a C-family emit bug is never CUDA-only.** `CUDASourceEmitter` inherits `CPPSourceEmitter`; scope any finding to both targets before recording it.
- **A multi-component swizzle READ re-emits its base once per component.** The C-family emitter lowers it to a per-component brace initializer `float3{ base.x, base.y, base.z }`, calling `emitOperand(getBase())` inside the loop — so a folded base (texture fetch, helper call, `saturate(...)`) is textually duplicated N×.
- **The multi-use fold guard cannot see this.** `shouldFoldInstIntoUseSites` only refuses to fold on >1 *IR* uses, and a multi-element swizzle is a SINGLE IR use that expands to N *textual* references.
- **The trigger is a non-trivial folded base, not the vector type.** `.rgb` of a register-resident local emits one fetch and is fast; a minimal local-base repro is therefore not a repro at all.
- **`float3`'s 12-byte CUDA layout is a red herring for this perf bug** — the layout fact is true, the causal attribution to register pressure was retracted. Values are always correct; this is codegen quality, not a wrong-result bug.
- **Confirm emit-duplication GPU-free by counting occurrences, not lines.** `slangc repro.slang -target cuda -entry <e> -stage compute -o k.cu` (or `-target cpp`), then `grep -o tex2Dfetch | wc -l` — the whole brace initializer is on ONE line, so `grep -c` reports 1 even when the fetch appears 3×.
- **`SLANGPY_PRINT_GENERATED_SHADERS=1` dumps the SlangPy wrapper, not the emitted CUDA C++** — wrong tool for an emit question.
- **User workaround: remove the folded expression from under the swizzle.** Bind the fetch to a named local (`float4 s = tex[q];` then read `s.r/s.g/s.b`) and write via lane assignment instead of a constructor-swizzle (`float4(shade(uv).rgb, a)` calls `shade` 3×).
- **SlangPy does not vendor the Slang compiler** — its `.gitmodules` has only `external/slang-rhi`, Slang is a prebuilt FetchContent binary. Any "vector arithmetic is slow/wrong on CUDA" report whose math lives in the user's `.slang` body is an upstream `shader-slang/slang` codegen issue.
- **`-target cpp` struct layout is C/C++ natural alignment (`CPULayoutRulesImpl`), not std140/std430** — a struct shared with a GPU buffer must be paired with `-fvk-use-c-layout`.
- **`export` roots a host-callable function against DCE; `public` does not.** `export`→`HLSLExportModifier` adds `HLSLExportDecoration` **and** `KeepAliveDecoration`; `public` adds only `PublicDecoration`, so `public __extern_cpp` + `-whole-program` emits nothing. The gap is at `getHLSLExports()`, which checks `HLSLExportDecoration` and never `KeepAlive`.
- **Use `-dump-ir` to tell a link-drop from an emit-filter drop:** "appears once then vanishes" means dropped at linking; "persists to the final module" means filtered at emit.
- **`-target hpp` for a `__extern_cpp` compute entrypoint emits wrapper BODIES, not prototypes** — the three CPU wrappers call a `_example` workhorse emitted nowhere, so the header won't compile. Fix is to guard the wrapper loop in `CPPSourceEmitter::emitModuleImpl` on `shouldEmitOnlyHeader()` and emit prototypes only; no forward-decl is needed once the bodies are gone.
- **A green SPIR-V/HLSL run does not clear CUDA for a param-passing change.** `getSharedBaseAddr`'s `__cvta_generic_to_shared(($0).m_data)` assumes by-value; by-ref emits `((&data)).m_data` and nvrtc rejects it. The groupshared-by-ref inlining lives only in `GLSLResourceReturnFunctionInliningPass` (Khronos targets), so vk masks it — `test-linux-release-gcc-x86_64-sm80`'s `tests/neural/` + `tests/cooperative-matrix/` are the canary.
- **Before changing any param-passing convention, grep the neural/coopmat stdlib for `__intrinsic_asm` bodies that deref `$0` with `.member`.**
- **A case-less `__target_switch` in `*.meta.slang` silently emits an EMPTY helper body** — a no-op kernel (PTX `ret;`) at exit 0 with no diagnostic. Suspect it whenever a shader "compiles to an empty kernel"; grep the emitted `.cu` for the `#line` marker that pins the source line.
- **Case-PRESENT plus an un-instantiated prelude template fails LOUDLY** (NVRTC "referenced but not defined"). Silent-empty and loud-undefined are opposite signatures of similar-looking texel-type gaps — do not dedup them.
- **A "make-it-a-no-op" prelude typedef is safe only if the type's METHODS have no target case for that backend.** `SamplerComparisonState`'s dummy CUDA typedef is safe because `SampleCmp` and siblings are `__target_switch`ed with no `cuda` case, so calling one errors loudly.
- **Use `$TR` (call return type) when an intrinsic string needs the result type spelled** — `$T<n>` unwraps a texture operand to its ELEMENT type, so `tex2Dgather<$T0>` emitted a scalar into a `float4` and NVRTC rejected the constructor. The one-token `$T0`→`$TR` fix generalizes to any CUDA texture op returning a vector wider than the element type.
- **`precise` on a LOCAL is emitted by the shared `CLikeSourceEmitter::emitTempModifiers`, so it leaks to all four C-like targets** — valid on HLSL+GLSL, invalid on CUDA/C++/Metal/WGSL. Gate at emit on source-language support, not at the target-agnostic producer.
- **Check whether the "extra" inputs are also broken before narrowing a guard called too broad.** `tex*fetch_int<T>` has NO half instantiation at ANY width (prelude instantiates float/uint/int only), so excluding `half3` from `static_assert(!__isHalf<T>())` would reintroduce the bug — half/half2/half3/half4 all hit E41400.
- **One CUDA-illegal entry point sinks its clean siblings.** Slang capability-checks ALL `[shader]` entry points at module load, so a typed `Buffer<T>`/`RWBuffer<T>` EP fails `load_program` for entry points that never reference it. Wrap the offending EP in `#ifndef __TARGET_CUDA__` — the preprocessor runs before the capability check. Do NOT guard `StructuredBuffer`/`RWStructuredBuffer`/`ByteAddressBuffer`; they lower to real pointers and work on CUDA.
- **Check `nvidia-smi` before punting a CUDA repro as hardware-gated** — the prod slang-fixer container has an NVIDIA L40S plus NVRTC and FileCheck, so a `//TEST:SIMPLE: -target ptx` directive is a real end-to-end compile-check locally.
- **Editing `hlsl.meta.slang` requires the core-module-header regen** before the change is observable in a built `slangc`.
- **A global templated CUDA vector `operator` MUST be SFINAE-gated** to the registered vector types (via a traits table keyed on `SlangCudaVectorTraits<T>::kWidth > 0`) or it becomes a candidate for every type in the program; keep `__half2` packed intrinsics as NON-template overloads so exact-match resolution keeps the packed path. The CUDA vector types are distinct structs (not one class template), and `bool2/3/4`/`__half3/4` are prelude-defined, so verify a prelude refactor offline with `nvcc -std=c++17`.
- **`__exp2f` (base-2 exp) does NOT exist as a CUDA device intrinsic** — so under `-fp-mode fast`, F32 exp2 stays precise (`::exp2f`) while `__sinf/__cosf/__tanf/__sincosf/__logf/__log2f/__log10f/__expf/__powf`(+`__exp10f`) redirect. Always verify each `__*f` fast-math name against nvcc, never a from-memory triage list.
- **`__intrinsic_asm` has TWO `$`-marker families reading DIFFERENT operand sources:** plain `$N` reads the ENCLOSING call's args (guarded → E99997 on OOB), bracket `$[N]` reads the intrinsic carrier's OWN operands (UNGUARDED → raw SIGSEGV on OOB). A statement-form `__intrinsic_asm "text", args;` value-arg is read by `$[N]` but silently DROPPED by `$N` — read the marker-dispatch switch, not a candidate report's one-line summary.

## The float3/swizzle-base re-evaluation perf bug (slang#12073, from slangpy#1059)

**Symptom:** a hot loop reading a multi-component swizzle (`.rgb`/`.xyz`) runs ~3× slower on the CUDA backend (measured 2.87× on an L40S/NVRTC 13) than reading a whole `float4` or accumulating in named scalars. Vulkan (SPIR-V) and D3D12 (HLSL) show no penalty.

**Root cause — the base is re-emitted once per swizzle component.** The C-family emitter lowers a multi-component swizzle READ to a per-component brace initializer `float3{ base.x, base.y, base.z }`. `CPPSourceEmitter`'s `kIROp_Swizzle` handler (`slang-emit-cpp.cpp:1642-1719`, the per-component loop at 1692-1716) calls `emitOperand(getBase())` *inside* the loop, so the base expression is re-emitted for every component. When the base is a value that `shouldFoldInstIntoUseSites` (`slang-emit-c-like.cpp:1685-1687`) folds into its use sites — a texture fetch, a buffer load, a helper call — the fetch is **textually duplicated N×** (N = swizzle width). Verified emitted-`.cu` fetch counts in the repro: `f4_all`=1 `tex2Dfetch`, `f3_loop`=**3**, `f3_epi`=1. SPIR-V emits a single `OpVectorShuffle` and HLSL a native `.xyz` — both evaluate the base once, which is the entire source of the backend asymmetry. The output values are correct; this is a codegen-quality/perf defect, not a wrong-result bug. See [Slang CUDA/CPP multi-component swizzle re-evaluates its base once per component (perf)](../learnings/1783909950787-slang-cuda-cpp-multi-component-swizzle-re-evaluate.md) and [slang C-family swizzle re-evaluates base per component (CUDA/CPP perf bug)](../learnings/1783910573494-slang-c-family-swizzle-re-evaluates-base-per-compo.md).

**Why the fold gate misses it:** `shouldFoldInstIntoUseSites` only refuses to fold on >1 *IR* uses. A multi-element swizzle is a SINGLE IR use that expands to N *textual* references — invisible to the multi-use guard ([slang C-family swizzle re-evaluates base per component (CUDA/CPP perf bug)](../learnings/1783910573494-slang-c-family-swizzle-re-evaluates-base-per-compo.md)).

**Trigger boundary:** the slowdown fires only when the swizzle base is a non-trivial folded expression (texture fetch / helper call / `saturate(...)`). It does NOT fire when the base is a cheap register-resident local — which is exactly why the minimal `f3_epi` control (`.rgb` of a local) is fast while a production epilogue whose `.rgb` base was an expensive helper expression is slow ([float3/vec3 CUDA slowdown is swizzle-base re-evaluation, not float3 layout](../learnings/1783910857099-float3-vec3-cuda-slowdown-is-swizzle-base-re-evalu.md)).

**Fix seam:** `CPPSourceEmitter::shouldFoldInstIntoUseSites` (override at `slang-emit-cpp.cpp:1931-1970`) ALREADY refuses to fold a vector/matrix value when its user is a reshape/cast (1943-1951), rationale "the implementation of cast will have multiple references to it." A multi-element swizzle base is the identical situation — extend that guard to `kIROp_Swizzle` with `getElementCount()>1` so the base materializes as a temp via existing machinery. Target-scoped, minimal, no adjacent regression ([slang C-family swizzle re-evaluates base per component (CUDA/CPP perf bug)](../learnings/1783910573494-slang-c-family-swizzle-re-evaluates-base-per-compo.md)). Alternative emit-side fix: bind the swizzle base to a temp once when `elementCount>1` and the base is non-trivial/folded ([Slang CUDA/CPP multi-component swizzle re-evaluates its base once per component (perf)](../learnings/1783909950787-slang-cuda-cpp-multi-component-swizzle-re-evaluate.md)).

**User workaround:** bind the fetch to a named local first, then read its components — `float4 s = tex[q]; use s.r/s.g/s.b` — and write via lane assignment (`v.a = a; dst[tid] = v;`) instead of constructor-swizzle (`float4(shade(uv).rgb, a)` calls `shade` 3×). Each removes a folded expression from directly under a multi-component swizzle so the base is evaluated once ([Slang CUDA/CPP float3 .rgb swizzle slowdown is base re-evaluation, not layout](../learnings/1783911049805-slang-cuda-cpp-float3-rgb-swizzle-slowdown-is-base.md)).

## Contradictions / supersessions

**The vec3-layout hypothesis was WRONG and is superseded.** The first triage note ([Slang CUDA float3 loop arithmetic ~3x slower than float4 (vec3 layout + swizzle-constructor emission)](../learnings/1783908909248-slang-cuda-float3-loop-arithmetic-3x-slower-than-f.md)) attributed the slowdown to `float3`'s 12-byte/4-byte-aligned CUDA layout (vs `float4`'s 16-byte/16-byte) defeating NVRTC register allocation, and framed it as CUDA-only. Both claims are false. Two later corrections ([CORRECTION: Slang float3 CUDA slowdown is swizzle-base re-evaluation, NOT vec3 layout/register pressure](../learnings/1783910402434-correction-slang-float3-cuda-slowdown-is-swizzle-b.md), [Slang CUDA/CPP float3 .rgb swizzle slowdown is base re-evaluation, not layout](../learnings/1783911049805-slang-cuda-cpp-float3-rgb-swizzle-slowdown-is-base.md)) proved via GPU-free emitted-`.cu` inspection at slang HEAD `8f0c3515d` that the real cause is swizzle-base re-evaluation, and that the scope is **CUDA + CPU/C++** (shared emitter), not CUDA-alone. The 12-byte float3 layout is a real fact but a red herring for this perf bug — falsified by the `f3_epi` control (native `float3` with a register-resident base emits 1 fetch, is fast). The emission *form* observed in the original note (`float3{a,b,c}` constructors vs `OpVectorShuffle`) was correct; only the *causal consequence* (register spilling) was mis-inferred. Treat 1783908909248's layout attribution as retracted; keep its ownership rule of thumb (below).

## Reusable rules

- **Ownership:** SlangPy does not vendor the Slang compiler (its `.gitmodules` has only `external/slang-rhi`; Slang is a prebuilt FetchContent binary) and is transparent to vector types. So any "float3/vector arithmetic is slow/wrong on CUDA" report where the math lives in the user's `.slang` body is an upstream `shader-slang/slang` codegen issue — SlangPy has no lever ([Slang CUDA float3 loop arithmetic ~3x slower than float4 (vec3 layout + swizzle-constructor emission)](../learnings/1783908909248-slang-cuda-float3-loop-arithmetic-3x-slower-than-f.md)).
- **Confirmation recipe (GPU-free):** `slangc repro.slang -target cuda -entry <e> -stage compute -o k.cu` (or `-target cpp` — same emitter) then count how many times an expensive base appears per `.rgb`/`.xyz`. The whole `float3{...}` initializer is on ONE line, so `grep -c` (counts lines) reports 1 even when the fetch appears 3× — use `grep -o tex2Dfetch | wc -l`. `SLANGPY_PRINT_GENERATED_SHADERS=1` dumps the Slang *wrapper*, not the emitted CUDA C++ — wrong tool ([slang C-family swizzle re-evaluates base per component (CUDA/CPP perf bug)](../learnings/1783910573494-slang-c-family-swizzle-re-evaluates-base-per-compo.md)).
- **Triage meta-lesson:** a layout/alignment fact being true does not make it the cause. When a codegen perf asymmetry has a tidy structural explanation, confirm it by counting operations in the actual emitted target code before recording the mechanism ([float3/vec3 CUDA slowdown is swizzle-base re-evaluation, not float3 layout](../learnings/1783910857099-float3-vec3-cuda-slowdown-is-swizzle-base-re-evalu.md)). NOT related to Metal PR #10031 packed-vec3 (that is buffer-layout stride, a different concern).

## #12073 Swizzle-Base Fix Shipped + C++ Struct-Layout Caveat (2026-07-14 fold)

The #12073 swizzle-base duplication fix shipped (draft PR #12078): a one-spot guard in `CPPSourceEmitter::shouldFoldInstIntoUseSites` returns `false` for a multi-component `IRSwizzle` whose base is the fold candidate, mirroring the existing reshape/cast "multiple references" precedent ([slang #12073 fix: swizzle-base fold guard implemented](../learnings/1783939557238-slang-12073-fix-swizzle-base-fold-guard-implemente.md)). ## #9401 / #9403 `-target hpp`/`cpp` Host Emission: Rooting, Whole-Program, and Header-Only Prototypes (2026-07-20 fold)

Two sibling `-target hpp`/`cpp` reports on the CPU/C++ emitter clarified how host-callable functions get rooted and emitted. First, **`export` roots against DCE but `public` does not**: `export`→`HLSLExportModifier` adds both `HLSLExportDecoration` **and** `KeepAliveDecoration`, while `public` adds only `PublicDecoration` — so `public __extern_cpp` + `-whole-program` still emits nothing; only `export __extern_cpp` works ([hpp/cpp export without entrypoint works via -whole-program; public never roots](../learnings/1784381336769-slang-target-hpp-cpp-export-without-entrypoint-wor.md)). A maintainer's proposed one-liner ("give `__extern_cpp` a `KeepAliveDecoration`") is necessary-but-insufficient: the public/export asymmetry is a **linking-root gap** at `getHLSLExports()` (which checks `HLSLExportDecoration`, never `KeepAlive`), and the separate "requires an entrypoint" gate is decoration-independent (`-whole-program` is the existing answer). `-dump-ir` "appears once then vanishes" vs "persists to final module" is the fast discriminator between a link-drop and an emit-filter-drop ([public-vs-export is a LINKING-ROOT gap, not KeepAlive/DCE](../learnings/1784383334778-slang-host-target-public-vs-export-emission-asymme.md)). Second, for a `__extern_cpp` **compute entrypoint**, `-target hpp` wrongly emits the three CPU wrappers (`example`/`_Group`/`_Thread`) as full definitions calling a `_example` workhorse that is emitted nowhere → the header won't compile. Root cause: the wrapper loop in `CPPSourceEmitter::emitModuleImpl` never consults `shouldEmitOnlyHeader()` ([hpp emits wrapper bodies not decls](../learnings/1784381106344-slang-9403-target-hpp-emits-wrapper-bodies-not-dec.md)). The principled fix is smaller than the obvious two-gap patch: guard the wrapper loop on `shouldEmitOnlyHeader()` to emit **prototypes only** — no forward-decl of `_example` needed, because once the bodies are gone nothing references it (validated with g++ against the `-target cpp` output) ([fix is prototypes only, no fwd-decl](../learnings/1784382795938-slang-target-hpp-compute-entrypoint-emits-wrapper-.md)). Both are GPU-free, host-reproducible with a Debug slangc.

## groupshared-by-ref Regresses CUDA Emit While a vk-Only Inline Pass Masks It (2026-07-23 fold)

When a change makes `groupshared` params pass **by reference** (#10641 / PR #11709), watch CUDA specifically. The neural stdlib intrinsic `getSharedBaseAddr` does `__cvta_generic_to_shared(($0).m_data)` assuming `$0` arrives by value; by-ref it becomes `&data`, so CUDA emits `((&data)).m_data` — `.m_data` on a pointer — and nvrtc rejects it. SPIR-V/`vk` stays green because the groupshared-by-ref inlining lives only in `GLSLResourceReturnFunctionInliningPass` (Khronos targets) and the emit-side unwrap was added only to `slang-emit-hlsl.cpp`, never `slang-emit-cuda.cpp`. A green SPIR-V/HLSL run does NOT clear CUDA — the `test-linux-release-gcc-x86_64-sm80` job's `tests/neural/`+`tests/cooperative-matrix/` on nvrtc+Vulkan are the canary; grep the neural/coopmat stdlib for `__intrinsic_asm` bodies that deref `$0` with `.member` before changing any param-passing convention ([groupshared param by-ref regresses CUDA emit (vk-only inline pass masks it)](../learnings/1784741954379-groupshared-param-by-ref-regresses-cuda-emit-vk-on.md)).

**A jkwak-filed CUDA/PTX texel-type cluster, plus a shared C-like emit leak.** Two texture/buffer gaps that look alike but have opposite failure signatures: `Buffer<T>.Load` for CUDA hits a **case-less `__target_switch`** in `hlsl.meta.slang` (no `cuda` case) → an **empty helper body** → silent no-op kernel (PTX `ret;`), exit 0 no error — suspect a case-less `__target_switch` whenever a shader "compiles to an empty/no-op kernel," and grep the emitted `.cu` for the `#line` marker that pins the source line ([case-less __target_switch in *.meta.slang silently emits an empty body](../learnings/1785371749664-case-less-target-switch-in-meta-slang-silently-emi.md)); whereas half-typed `_Texture<T>.Load` has a *present* cuda case that calls an **un-instantiated** prelude template (`tex2Dfetch_int<__half4>` declared, never defined) → a **loud** NVRTC "referenced but not defined" link error — so case-LESS switch ⇒ silent-empty, case-PRESENT + missing prelude instantiation ⇒ loud undefined symbol; do NOT dedup them ([CUDA texture Load half-texel gap: loud undefined-template vs #12274 silent-empty](../learnings/1785373293265-cuda-texture-load-half-texel-gap-loud-undefined-te.md)). A third prelude gap: `SamplerComparisonState g_scmp;` breaks CUDA/PTX because the prelude defines a dummy `SamplerState` typedef but **no comparison-state counterpart** — the symmetric one-liner (`typedef SamplerComparisonStateUnused* SamplerComparisonState;`) makes a declared/bound comparison sampler a harmless no-op (it does not implement `SampleCmp`) ([CUDA SamplerComparisonState has no prelude typedef](../learnings/1785373084246-cuda-samplercomparisonstate-has-no-prelude-typedef.md)). All three reproduce GPU-free (Debug slangc + NVRTC/nvcc 12.6, emit-and-inspect). Separately, the `precise` qualifier on a *local* is emitted verbatim by the SHARED base `CLikeSourceEmitter::emitTempModifiers`, so the HLSL-only spelling leaks to **all four** C-like targets the reporter's #12279 title named only two of — valid on HLSL+GLSL, invalid on CUDA/C++/Metal/WGSL; the correct guard predicate is source-language support, and gating belongs at emit, not the target-agnostic producer ([precise local qualifier leaks to 4 C-like targets, not just CUDA/C++](../learnings/1785373326278-precise-local-qualifier-leaks-to-4-c-like-targets-.md)).

**The cluster's texel-type and prelude fixes shipped, with review nuances that generalize.** For #12276's `Gather` result-type bug, the CUDA intrinsic string must reference the call's **return type** via the `$TR` marker, not the texture-element type via `$T0`: `$Tn` unwraps a texture arg to its element type (`slang-intrinsic-expand.cpp`), so `tex2Dgather<$T0>` emitted a scalar `tex2Dgather<float>` assigned into a `float4` → NVRTC "no suitable constructor" — the one-token `$T0`→`$TR` fix (both `Gather` overloads) generalizes to any CUDA texture op whose signature returns a vector wider than the element type. Notably the prod slang-fixer container HAS an NVIDIA L40S GPU + NVRTC + FileCheck, so a `//TEST:SIMPLE: -target ptx` directive is a real end-to-end NVRTC compile-check locally — check `nvidia-smi` before punting a CUDA repro as hardware-gated ([CUDA gather $T0 vs $TR + local GPU/NVRTC/FileCheck present](../learnings/1785417049714-cuda-gather-t0-vs-tr-marker-local-gpu-nvrtc-filech.md)). For #12278/#12300, the `SamplerComparisonState` no-op prelude typedef is *safe* because `SampleCmp` and its siblings in `hlsl.meta.slang` are capability-gated with a `__target_switch` that has **no `cuda` case** — so *calling* a comparison sampler on CUDA fails with a loud diagnostic, and the dummy typedef only lets a declared/bound-but-unused sampler occupy uniform space as a harmless pointer (the general reviewer test for any "make-it-a-no-op" prelude fix: check whether the type's *methods* have a target case for the backend) ([CUDA SamplerComparisonState no-op prelude typedef is safe](../learnings/1785445968024-cuda-samplercomparisonstate-no-op-prelude-typedef-.md)). For the #12277 half-texture `Load` fix (`static_assert(!__isHalf<T>())` in the cuda case), a reviewer's "guard too broad, exclude half3" was WRONG: `tex*fetch_int<T>` has **no** half instantiation for ANY width (prelude only instantiates float/uint/int), so `half3` hits the same NVRTC undefined-template error — narrowing to widths {1,2,4} would reintroduce the bug (verified: half/half2/half3/half4 all → E41400) — a durable lesson that "guard too broad" flags deserve a check whether the extra inputs are *also* broken before narrowing ([CUDA half-texture Load: half3 is NOT overreach](../learnings/1785465186257-cuda-half-texture-load-fix-half3-is-not-overreach-.md)).

**CUDA whole-module capability checks sink clean sibling entry points — guard the offending EP with `#ifndef __TARGET_CUDA__`.** When a `.slang` module bundles multiple `[shader]` entry points and one uses a CUDA-illegal feature (e.g. typed `Buffer<T>`/`RWBuffer<T>` → E36107), Slang capability-checks ALL entry points at module load, so that one bad EP fails `load_program` even for siblings that never reference it. The fix is to wrap the offending EP in `#ifndef __TARGET_CUDA__ … #endif` — the preprocessor runs BEFORE the capability check, and `__TARGET_CUDA__` (family: `__TARGET_D3D12__`/`__TARGET_VULKAN__`/`__TARGET_METAL__`/`__TARGET_CUDA__`) is injected as a session macro for the CUDA target, so the EP is stripped before E36107 sees it; do NOT guard `StructuredBuffer`/`RWStructuredBuffer`/`ByteAddressBuffer` (they lower to real pointers and work on CUDA). This shipped as slangpy PR #1083 to unblock slang#12289's required `SlangPy Tests` check — and because slangpy's `ci-latest-slang.yml` dispatch checks out slangpy at its default branch, such a guard must MERGE to slangpy main to green the slang PR, making it a prerequisite rather than a follow-up ([guard test-only CUDA EPs with `#ifndef __TARGET_CUDA__`](../learnings/1785453604826-guard-test-only-shader-eps-from-cuda-with-ifndef-t.md)).

## CUDA codegen fold (2026-09-09): intrinsic-asm markers, prelude vector operators, fast-math transcendentals

**`__intrinsic_asm` has TWO `$`-marker families with different operand sources — `$N` reads the CALL, `$[N]` reads the carrier's OWN operands.** Triaging shader-slang/slang#12529 (statement-form `__intrinsic_asm` value-arg mishandling), a candidate report's headline "the GenericAsm value-operands 1..N have no reader in any emitter" was WRONG — refuted by reading the marker handler in `slang-intrinsic-expand.cpp`. Plain `$N` (the digit-case, `:366-374`) expands against `m_args` = the ENCLOSING `m_callInst`'s operands; OOB trips the `:370` `SLANG_RELEASE_ASSERT` → E99997. Bracket `$[N]` (the `case '['`, `:868-892`) expands against `m_intrinsicInst->getOperand(1+argIndex)` = the intrinsic-carrier's OWN operands (for a statement-form `__intrinsic_asm` that carrier is the `IRGenericAsm`), and its `getOperand` is UNGUARDED, so OOB `$[N]` is a raw SIGSEGV, not the assert. Consequence for `__intrinsic_asm "text", args;`: the args ARE read by `$[N]` (`USE($[0]), v` → `USE(&v_0)`) but silently dropped by plain `$N` (which reads the enclosing call) — which is why the core modules' `__sizeOf<T>()` (`$[0], T`) works while a plain-`$N` statement value-arg is inert. So "no reader" is false; the correct statement is "plain `$N` reads the call, not the statement's own operands." Recurring lesson: read the actual marker-dispatch switch (`_emitSpecial`), not a report's confident summary — the two branches sit a few lines apart with visibly different operand sources, and an unguarded `getOperand` next to a guarded sibling is a second crash the report may miss (enumerate ALL marker cases) ([intrinsic_asm has TWO marker families with different operand sources ($N=call, $[N]=own)](../learnings/1786631581576-intrinsic-asm-has-two-marker-families-with-differe.md)). (This complements the `$TR` vs `$T0` texture-marker fix above — both are lessons about knowing exactly which operand a `$`-marker reads.)

**CUDA prelude vector operators: templated forms must be SFINAE-gated and coexist with packed `__half2` non-template overloads.** Converting the CUDA prelude's fixed-width vector operators from per-(type,width,op) macros to templates (maintainer request on PR #12410), verified offline with nvcc 12.6 `-std=c++17` (the exact flag Slang's NVRTC path passes — `source/compiler-core/slang-nvrtc-compiler.cpp`): the CUDA vector types (`int2`, `char4`, `__half2`, plus prelude-defined `bool2/3/4`, `__half3/4`) are distinct, unrelated structs, NOT one class template, so `template<class T,int N> VecN<T,N> operator+` is impossible — use a traits table (`template<class T> struct SlangCudaVectorTraits;` left undefined, one explicit specialization per vector type carrying `kWidth`/`BoolVector`/`kIsIntegral`). A global templated `operator+(T,T)` MUST be SFINAE-constrained to the registered types (gate on `SlangCudaVectorTraits<T>::kWidth > 0` via a hand-rolled two-line `enable_if` — the NVRTC prelude does not include `<type_traits>`), or it becomes a candidate for every type (verified: `struct Foo{int x,y;}` and scalar `int+int` misbehave without the gate). `__half2` arithmetic must stay NON-template overloads backed by `__hadd2`/`__hsub2`/`__hmul2`/`__h2div`/`__hneg2` (one `add.f16x2` vs two scalar `add.f16`): a non-template exact-match wins over the template, preserving the packed path (byte-identical PTX), while `__half2` compare/logical and all `__half3/4` operators correctly fall through to the templates (the prelude also `#define __CUDA_NO_HALF2_OPERATORS__` before `<cuda_fp16.h>` so the toolchain's own operators don't collide). `if constexpr` width dispatch is well-formed inside a template but NOT in a plain function (that is why the macro form couldn't use it), and `__device__` lambdas need `--extended-lambda` (NVRTC doesn't pass it) — splice the operator token directly. Report the parse-cost win structurally (684 concrete operator definitions per TU → 21 templates + 13 packed overloads), NOT as a wall-clock compile-time claim at small scale (a 33-kernel PTX sweep was 32/33 identical opcode multisets; the one difference, bool4, was one instruction shorter) ([CUDA prelude: templated vector operators must be SFINAE-gated + coexist with packed __half2 overloads](../learnings/1787075202710-cuda-prelude-templated-vector-operators-must-be-sf.md)).

**CUDA fast-math redirectable transcendentals — `__exp2f` does not exist.** Wiring `-fp-mode fast` to CUDA transcendental emission (slang#12619), the redirectable F32 wrappers with a hardware-approximate `__*f` intrinsic are exactly nine — `__sinf, __cosf, __tanf, __sincosf, __logf, __log2f, __log10f, __expf, __powf` — plus `__exp10f` (base-10). There is NO `__exp2f`: nvcc 12.6 errors "identifier __exp2f is undefined in device code", so F32 exp2 must stay precise (`::exp2f`) under fast math, alongside the other non-redirectable ones (atan2, asin, acos, atan, sqrt). A triage memo listing exp2 as redirectable was wrong — always verify each `__*f` name against nvcc, never trust a from-memory list. Fast verification (2 min, no 20-min build): write a minimal `__device__` harness mirroring the prelude wrappers, `nvcc -std=c++17 -c` it twice (default + `-DSLANG_CUDA_ENABLE_FAST_MATH=1`), and `-ptx` both then `grep -cE '\.approx\.'` (fast build should compile AND show more approx ops); nvcc 12.6 is at `/usr/local/cuda-12.6/bin/nvcc` in-container ([CUDA fast-math redirectable transcendentals — __exp2f does NOT exist (base-2 has no fast intrinsic)](../learnings/1787147170237-cuda-fast-math-redirectable-transcendentals-exp2f-.md)).
