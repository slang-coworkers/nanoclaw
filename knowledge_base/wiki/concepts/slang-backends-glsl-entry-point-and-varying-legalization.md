# Slang GLSL legalization: entry-point parameters, varyings, and precise outputs

`legalizeEntryPointsForGLSL` (`slang-ir-glsl-legalize.cpp`) turns entry-point parameters and results into global varyings for the GLSL target and for SPIR-V, which goes through the same pass. This page collects the bugs that arise in that rewrite: decorations attached to the entry point or to a varying, decorations such as `precise` that must survive onto the replacement global, global-scope GLSL-style inputs, and lifting `layout(...)` qualifiers onto an entry point. General GLSL emission and glslang integration are on [[wiki/concepts/slang-backends-glsl.md]].

## TL;DR

- **A new per-entry-point system-value decoration must gate on `kind == LayoutResourceKind::VaryingOutput`.** `legalizeEntryPointParameterForGLSL` calls `createGLSLGlobalVaryings` twice for `inout` params; unconditional assignment attaches the decoration twice and the emitter (no dedup, no break) emits it twice → invalid GLSL.
- **Also add any such new op to `isSimpleDecoration`** (`slang-ir.cpp`) so `addDecoration` can deduplicate, mirroring `kIROp_EarlyDepthStencilDecoration`.
- **`SV_Depth{Greater,Less}Equal` directional mode is DROPPED on the via-GLSL path** — the `layout(depth_greater)`/`depth_less` qualifiers are an unfinished TODO in glsl-legalize; only `DepthReplacing` survives. Direct SPIR-V is correct.
- **A global-scope array-of-struct GS input crashes glsl-legalize**, not SPIR-V: `in triangle CoarseVertex v[3];` asserts `realGlobalVar` (E99997) even at `-O0` and on `-target glsl`. Plain `in triangle CoarseVertex v;` and `in triangle float4 p[3];` both compile — array-of-struct is the precise trigger.
- **A multi-repro issue closed by a single-repro PR must have each repro re-checked at HEAD** — that is how this one stayed broken behind a `Fixes #N` close.
- **`precise` on an entry-point out param or struct field is dropped on SPIR-V, HLSL/DXIL and GLSL** (#13287; #12208 covered only locals): glsl-legalize copies only interpolation decorations to the varying, `computePreciseInsts` seeds only in-function insts, and the C-like emitter prints `precise` only on temps. Check DXIL with `-target dxil-asm | grep "fmul fast"`. The fix carries the decoration to the replacement global when any chain link is precise (or-semantics, including the `systemNameToGlobalMap` reuse branch), seeds decorated globals in `computePreciseInsts`, and follows `swizzledStore`; `precise` on an entry-point return value and `spirv_asm` intrinsics remain gaps.
- **Lifting a standalone `layout(...) in;` qualifier onto an entry point must gate on direction (`InModifier`) and resolve scope with `getParentDecl`,** not raw `parentDecl`, which is the `GenericDecl` for a generic entry point. A via-glsl `OpExecutionMode` CHECK must wildcard the entry-point operand, because glslang renames it to `main`.
- **`gl_*` builtin outputs never get `emitVarModifiers`**, so `precise` needs a global `precise gl_Position;` redeclaration before first use. `-pass-through glslang` aborts with E99997 today; test hand-edited GLSL by calling `glslang_compile_1_2` in `libslang-glslang` directly.

## System-Value Legalization (Per-Entry-Point Decorations)

When adding a new `GLSLSystemValueKind` whose handler decorates the ENTRY POINT (not the global param) — e.g. conservative-depth `FragDepthGreater`/`FragDepthLess` decorations — two rules apply:

1. Gate `systemValueKind` assignment on `kind == LayoutResourceKind::VaryingOutput`, mirroring `sv_position` at `slang-ir-glsl-legalize.cpp ~478-498`. `legalizeEntryPointParameterForGLSL` calls `createGLSLGlobalVaryings` twice for `inout` params; unconditional assignment attaches the decoration twice and the emitter (iterating all decorations without dedup/break) emits it twice → invalid GLSL.

2. Add the new op to `isSimpleDecoration` in `slang-ir.cpp ~86`, mirroring `kIROp_EarlyDepthStencilDecoration`, so `addDecoration` can deduplicate.

For depth specifically, the double-attach is unreachable in practice — `SV_Depth`/`SV_DepthGreaterEqual`/`SV_DepthLessEqual` are setter-only (no getter), so using one as input is rejected by the frontend with E30702 `SystemValueSemanticInvalidDirection` before legalization. Both rules are still valuable defense-in-depth for any NEW entry-point decoration whose semantic has a getter ([GLSL legalize: per-entry-point system-value decorations must gate on VaryingOutput (inout double-attach)](../learnings/1782173862922-glsl-legalize-per-entry-point-system-value-decorat.md), [GLSL legalize: per-entry-point system-value decorations must gate on VaryingOutput (inout double-attach)](../learnings/1782175454099-glsl-legalize-per-entry-point-system-value-decorat.md)).

**SV_Depth directional mode is dropped via GLSL (`-emit-spirv-via-glsl`):** There is an unfinished `// TODO` at `slang-ir-glsl-legalize.cpp:~577-592` where `layout(depth_greater)`/`layout(depth_less)` qualifiers should be emitted but are not. Only `DepthReplacing` survives the via-GLSL path ([Slang SV_Depth{Greater,Less}Equal: direct SPIR-V correct, GLSL/via-GLSL drops directional mode](../learnings/1782165817624-slang-sv-depth-greater-less-equal-direct-spir-v-co.md)).

## `precise` on entry-point outputs is lost at several layers (#13287, #13292)

Consider a vertex shader that declares `out precise float4 pos : SV_Position`. The `precise` fix #12208 (b1f63b2489, first shipped in v2026.18.3) covers only function-local values, so at HEAD 86f6dc1e2 this output gets no protection on SPIR-V, HLSL/DXIL or GLSL. Lowering does attach `IRPreciseDecoration` to params and struct keys (`addVarDecorations`, `slang-lower-to-ir.cpp:3192`; key `:13137`, param `:14404`), and three consumers then lose it. First, `legalizeEntryPointsForGLSL` → `createVarLayoutForLegalizedGlobalParam` (`slang-ir-glsl-legalize.cpp:1047-1063`) walks the param→field-key chain but copies only `IRInterpolationModeDecoration` onto the global varying. Second, `computePreciseInsts` (`slang-emit-spirv.cpp:10560`) seeds only insts inside function blocks (`:10576-10585`), so struct keys and global vars never become seeds. Third, the C-like emitter prints `precise` only through `emitTempModifiers` (`slang-emit-c-like.cpp:4734`); `emitSimpleFuncParamImpl` (`:3906`) and struct-field emit (`:4598`) never do. So `-target dxil` gets `fmul fast` for the output, while DXC compiling the same HLSL directly marks it precise. A `precise` out param on a non-inlined callee does work, because that param survives to emit. To check whether `precise` reached DXC, compile with `slangc -target dxil-asm` and grep for `fmul fast`/`fadd fast`; DXC runs locally in the container ([precise on entry-point out params/struct fields is dropped (#13287)](../learnings/1790611075004-precise-on-entry-point-out-params-struct-fields-is.md)).

On the GLSL path the emitter has a fourth gap for builtins. `GLSLSourceEmitter::tryEmitGlobalParamImpl` sends every `gl_*` global to `_maybeEmitGLSLBuiltin` and returns before `emitVarModifiers`, so a decoration such as `IRPreciseDecoration` on a builtin output is never printed unless a dedicated redeclaration case exists. The GLSL form that works is `precise gl_Position;` redeclared at global scope before `main`: glslang then puts `NoContraction` on the `fmul`/`fadd` feeding `gl_Position`, even when the value flows through a local struct member. glslang rejects the requalification after first use ("cannot change qualification after use", `ParseHelper` `addQualifierToExisting`), and it also honours `precise` on GLSL function out-params. DXC accepts both `out precise float4 x` and `precise out float4 x`, and either one removes the `fast` flags ([testing GLSL→SPIR-V qualifier fixes via libslang-glslang (#13292)](../learnings/1790614490406-testing-glsl-spir-v-qualifier-fixes-without-slangc.md)).

Checking hand-edited GLSL like this needs a way to run glslang, and `slangc -pass-through glslang x.glsl -target spirv` currently aborts with E99997 "no matching IR symbol" (seen 2026-09-28 on both the 2026.13.1 and 2026.18.3 builds). The workaround is a roughly 20-line C++ harness that includes `source/slang-glslang/slang-glslang.h` and calls `glslang_compile_1_2` from `build/Release/lib/libslang-glslang-*.so` with action=0, slangStage=1 (vertex) and optimizationLevel=0. It collects the output bytes and scans the words for `OpDecorate` (`0x00030047`) with decoration 42 to count `NoContraction` ([testing GLSL→SPIR-V qualifier fixes via libslang-glslang (#13292)](../learnings/1790614490406-testing-glsl-spir-v-qualifier-fixes-without-slangc.md)).

A fix prototype for #13287 (measured at base 68563d2f3, eval trial slang-13287#r1, fork PR slang-coworkers/slang-eval#8) shows what each layer needs, and finds one more gap. In the GLSL legalizer, `legalizeEntryPointsForGLSL` → `createSimpleGLSLGlobalVarying` replaces every output leaf with a fresh global, and `createVarLayoutForLegalizedGlobalParam` copies only the interpolation mode from the `OuterParamInfoLink` chain. The fix adds `IRPreciseDecoration` to the new global when any link in the chain is precise. That is or-semantics, unlike interpolation, where the innermost link wins. The same decoration must also be applied on the `systemNameToGlobalMap` reuse branch (for example `gl_ClipDistance`, shared by `SV_ClipDistance0` and `SV_ClipDistance1`), because that branch never reaches `createVarLayoutForLegalizedGlobalParam`. Because SPIR-V goes through the same legalizer, this one drop affected both SPIR-V and GLSL. In `computePreciseInsts`, seeding the decorated globals as well is enough, since the existing pointer→store edge then reaches the arithmetic. The extra gap is that `outPos.xyz = …` (and `precise float4 v; v.xyz = …`) lowers to `swizzledStore`, not `store`, and the cone walk ignored it, so the output got 0 `NoContraction`. The walk has to follow `getDest()`/`getSource()` of `IRSwizzledStore` and `IRMatrixSwizzleStore`.

Three cases are still not covered after that fix. `precise float4 main() : SV_Position` is accepted by the checker on a `CallableDecl`, but lowering never decorates the `IRFunc`, while DXC honours it. `spirv_asm` intrinsics (`mul`, `dot`, `lerp`) still dead-end the walk. And the GLSL text emitter still never redeclares `precise gl_Position;`, because the emitter skips `gl_*` globals. A quick DXC check needs no separate dxc binary: `slangc x.hlsl -pass-through dxc -target dxil-asm -profile vs_6_0 -entry main -stage vertex`, then grep for `fmul fast` against plain `fmul` [precise on entry-point outputs: carry IRPreciseDecoration to the replacement global; follow swizzledStore](../learnings/1792180124301-precise-on-entry-point-outputs-glsl-legalizer-must.md).

## Global-scope GS inputs (#12169) and lifting `layout(...)` qualifiers onto an entry point

slang#12169 — a global-scope GLSL-style geometry-shader input `in triangle CoarseVertex coarseVertices[3];` crashes `slangc … -target spirv` at `slang-ir-glsl-legalize.cpp:4401 SLANG_ASSERT(realGlobalVar)` (E99997). It reproduces even at `-O0` (before spirv-opt) and on `-target glsl` too — so it is INSIDE the IR legalize pass, not SPIR-V-specific or downstream. Empirically the trigger is precisely **array-of-struct at global scope**: plain `in triangle CoarseVertex v;` compiles, array-of-vector `in triangle float4 p[3];` compiles, but `in triangle CoarseVertex v[3];` crashes. Root-cause hypothesis (needs IR-dump confirmation): the `in` branch's `if (as<IRStructType>(globalVarType))` check (`:4358`) routes plain structs through `tryReplaceUsesOfStageInput`; `array<struct>` fails the struct check and falls to the else branch that matches the `GlobalVariableShadowingGlobalParameterDecoration` key against scalarized tuple element keys — no element matches → `realGlobalVar` stays null → assert. Crucially, this is a **prematurely-closed issue**: PR #11678 (`Fixes #9058`) fixed only the reordered-entry-point-param repro (`failure1.slang`) but closed all of #9058, leaving `failure2.slang` (this exact global-scope form) unfixed — the sibling triage lesson being that a multi-repro issue closed by a single-repro PR must have each repro re-checked at HEAD ([slang #12169 — #9058 closed prematurely; global-scope array-of-struct GS input still asserts realGlobalVar](../learnings/1784603960285-slang-12169-9058-closed-prematurely-global-scope-a.md)).

Lifting a standalone GLSL `layout(...) in;` qualifier onto an entry point (the `EmptyDecl`-marker → checker-lift pattern in `slang-check-shader.cpp`, used by `local_size_*`/`derivative_group_*`) has two correctness requirements. First, gate on **direction**, not just the marker: `layout(<q>) out;` and bare `layout(<q>);` also parse into an `EmptyDecl` carrying the marker, so for a direction-sensitive qualifier like `early_fragment_tests` (#12655 / PR #13033) additionally require an `InModifier` (`emptyDecl->findModifier<InModifier>()`) — "mirror the precedent" copies a latent leniency because the sibling `local_size_*` lifts do NOT gate on direction. Second, resolve the scope with `getParentDecl(entryPointFuncDecl)`, NOT raw `->parentDecl`: for a *specialized generic* entry point `->parentDecl` is the enclosing `GenericDecl`, whose `getMembersOfType<EmptyDecl>()` scan misses the module-scope sibling `layout(...) in;`, so the attribute is silently never synthesized — a latent pre-existing bug in the `local_size_*` lift too (a generic compute entry point then emits `LocalSize 1 1 1`). Recognizing the token for ALL forms in the parser while gating activation in the checker also turns a prior `E31217` hard error into a silent accepted-but-inert no-op — a PR-introduced behavior change worth flagging as a diagnose-vs-silently-accept design question ([GLSL layout lift must gate on direction, not just the marker](../learnings/1789222923705-glsl-layout-qualifier-lift-must-gate-on-direction-.md), [GLSL layout→entry-point lift must use getParentDecl; local_size lift has a latent generic bug](../learnings/1789227359016-glsl-layout-entry-point-lift-must-use-getparentdec.md)).

Testing both SPIR-V emit paths for such an entry-point attribute: the `-target spirv` default is the DIRECT backend, and only the via-glsl path renames the entry point. A `//TEST:SIMPLE: -target spirv` directive uses the direct SPIR-V backend (output shows `OpSource Slang`, entry point kept as e.g. `%csMain`), so pairing bare `-target spirv` with `-target spirv -emit-spirv-directly` exercises the direct backend TWICE — to also cover glslang, one directive must use `-emit-spirv-via-glsl` (output shows `OpSource GLSL`, entry point renamed to `%main`). Because via-glsl renames the entry point, an `OpExecutionMode` CHECK on that path must WILDCARD the entry-point operand (`// CHECKGLSL: OpExecutionMode {{.*}} EarlyFragmentTests`, precedent `tests/glsl/fragment-depth-greater-less.slang`) or use a `%{{.*}}` wildcard for the shared name — a literal `%main` assertion produces a false CI failure even when the compiler is correct, while the direct path legitimately keeps `%main`/`%csMain`. (Relatedly, a new nullary `GLSLLayout*Attribute` AST class inserted mid-header is NOT an ABI/enum break — `ASTNodeType` is FIDDLE-regenerated from declaration order each build, so the append-only rule for `include/` enums does not apply.) ([default SPIR-V backend is direct; -target spirv + -emit-spirv-directly test the same path](../learnings/1789231961570-slang-default-spir-v-backend-is-direct-target-spir.md), [via-glsl OpExecutionMode CHECK must wildcard the entry-point operand](../learnings/1789224142753-via-glsl-opexecutionmode-check-must-wildcard-the-e.md)).
