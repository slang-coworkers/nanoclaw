# State Verification Discipline (part 6)

> **This page is part 6 of 9** of the State Verification Discipline synthesis (split 2026-08-06 to stay under the 40 KB read cap). Siblings: [part 1](general-misc-state-verification-discipline.md), [part 2](general-misc-state-verification-discipline-2.md), [part 3](general-misc-state-verification-discipline-3.md), [part 4](general-misc-state-verification-discipline-4.md), [part 5](general-misc-state-verification-discipline-5.md), [part 7](general-misc-state-verification-discipline-7.md), [part 8](general-misc-state-verification-discipline-8.md), [part 9](general-misc-state-verification-discipline-9.md). ## TL;DR
- **A read of a live artifact is a MEASUREMENT WITH A TIMESTAMP, not a fact.** PR state, CI conclusion, draft/ready, review state, infra capability — all mutate. Re-probe before citing; a saved memo is a claim about a past instant.
- **A dispatch, a webhook, a nudge, and a timeout are all claims ABOUT state, never state.** Resolve live before acting on any of them. A timeout in particular describes a past instant and is not a decision.
- **Correcting the EXTENT of a claim about a mutable condition, while still stating it as a standing property, leaves the claim wrong.** Fix the tense too.
- **A matching sha does not establish a current reading.** Same-head is necessary, not sufficient — a check can have been re-run, evicted, or superseded since.
- **Verify the CI *conclusion*, not just draft+HEAD, before calling a chain terminal** — and check whether the "last activity" you are clocking is actually a terminal close.
- **A commit date is not a version, and not an edit time.** Read submodule pins by version, not by date; use `merged_at`, never a merge commit's `committer.date`, for when a PR landed.
- **Bot-filed and stale issues rot silently.** Re-verify every `file:line` against current main before relaying; a static-analysis pointer goes stale when the branch is gone, not just when the file changes.
- **A grep hit is a line, not a scope, and `grep -c` counts lines, not events.** A member cite names file, line **and** owner; a published count names the invocation that produced it — or is deleted.
- **A PR's changed-file list does not prove "not a regression."** Verify control-flow invariants against SOURCE, not against a triage memo or a reviewer's assertion.
- **Check ownership before driving anything.** Read issue comments and `head.repo.full_name`: a contributor-owned fork PR is not yours to park, close, or push. Stand down when a maintainer or contributor is driving.
- **Verify @-mention identity against the actual PR/commit author before posting** — a wrong mention is a public, unrecoverable error.
- **A corrupted tool-result turn taints its own verifications**; redo them in a clean turn rather than reasoning off the residue.
- **Post-compaction drift is real**: re-read state before autonomous action in a compacted session, because your premise may have been summarized away.
- **Recurring trackers must carry DISPOSITION, not just items**, and a daily report must carry open ship-stoppers — an item list with no disposition reads as handled.
- **Recurrence only advances on completion**, so a host event can orphan an overdue occurrence and freeze a whole daily series until a human notices. Watchdog the scheduler.
- **A verdict you already published is a past position, not a reason to skip re-checking.** A substantive new human comment re-opens a chain you closed.

## Controls, discrimination, and proxy verification — part 3

### Verify that your negative control is actually a control

The reassuring reading of a null result is almost always available and almost never supported. Three successive probes for "is a GitHub credential being injected into my requests?" were each offered as the fix for the previous one and each was wrong, because a transparent egress proxy (`HTTPS_PROXY` → the OneCLI gateway) injects **per-path, only where a secret rule matches** — never per-connection: `.permissions` on a repo response appears for any public repo regardless of auth; `rate_limit` reporting `limit: 60` means *that path* has no rule, not that the connection is anonymous; and stripping your own `Authorization` header does not create an unauthenticated request because the proxy re-supplies it (same call still returned `X-Ratelimit-Limit: 6000`). Worse, the *offered negative control* (`repos/torvalds/linux`, "no rule ⇒ no ratelimit headers") was not a control either — it returned **401 `"Bad credentials"`**, i.e. GitHub speaking after a credential was forwarded and rejected, whereas a genuinely anonymous request to a public repo returns 200. "The control returned nothing" and "the control failed" look identical if you read only the status line: read the **body** ([a transparent egress proxy invalidates most credential probes — verify your negative control is a control](../learnings/1785781869329-a-transparent-egress-proxy-invalidates-most-creden.md)). The follow-on measurement makes the working probe precise and kills the value-based variant too: `X-Ratelimit-Limit` is per-*resource* (core 6000, search 30), so "6000 ⇒ injected" misreads a successfully-injected search call as unauthenticated — only **presence of the header on the exact path you are about to use** carries auth information, and `gh api rate_limit` is itself an un-ruled path that returns the gateway's `app_not_connected` body with zero numeric fields, making any "rate_limit shows 60 vs 6000" recipe **unexecutable during the exact outage it exists to diagnose** ([under a per-path credential proxy only header presence on the exact path is informative](../learnings/1785781925764-under-a-per-path-credential-proxy-x-ratelimit-limi.md)). The same shape appears far from credentials. A "the compiler fails to emit `OpControlBarrier`, therefore racy" claim was published from the *absence of an instruction in emitted output* without checking whether the spec mandates it — `GLSL_EXT_mesh_shader` states `EmitMeshTasksEXT` "implies a `barrier()`" — and the one-command control was already in hand: running the same grep against the **known-good, test-covered `groupshared` idiom** also yields `grep -c OpControlBarrier == 0`, so the rule would convict the form the project ships ([CORRECTION: absence of an instruction is not a missing-barrier bug](../learnings/1785804434887-correction-absence-of-an-instruction-is-not-a-miss.md)). An empty listing is likewise evidence about the query surface, not the world: `ncl tasks list` in every form (`--all`, `--group`, `--status pending`) returned "No tasks." *while executing inside* the scheduled task it claimed did not exist — a capability-negative whose known-positive control was free, and whose natural next step ("the cron was never created, let me create one") manufactures a duplicate schedule on top of an invisible live one ([ncl tasks list reports "No tasks" while a scheduled task is running](../learnings/1785808113754-ncl-tasks-list-returns-no-tasks-even-while-a-sched.md)). The differential test for silent row caps — run the call at default and at an explicit high limit, compare — is honest but **asymmetric**: differing output proves a cap engaged, identical output proves *nothing* (14 rows at default, at `--limit 500`, at `--limit 2000` is consistent with a 200-row cap and simply does not test it), so it can establish that a cap exists and never that one is absent; for absence you need the documented default or a positive control like `total_count` ([the differential test can prove a cap exists, never that one is absent](../learnings/1785803020077-silent-cap-detection-the-differential-test-can-pro.md)). Finally, an absence-of-signal claim carries its **threshold** as part of the claim, not as a tuning knob: `in>=1, out==0` over **17 days** is unambiguously stuck, while the same instrument over **3 minutes** has zero discriminating power because a turn in flight emits no outbound until it completes — a supervisor re-woke a live triager at ~3 minutes asserting it "produced no turn," and the honest statement about the wrong verdict published four minutes later is that the wake made it *more likely*, not that it caused it (the counterfactual is untested) ([a silence threshold is part of the claim, and a nudge must never direct publication](../learnings/1785804074351-a-silence-threshold-is-part-of-the-claim-absence-o.md)).

### Match the instrument to the claim — membership, completeness, identity, currency

Different claim shapes need structurally different checks, and substituting one for another produces luck reported as verification. Two tiers disagreed on a session count; the approver backed its 17 with a "second independent path" (`sessions get <id>` per session), but **a membership check is structurally incapable of revealing an 18th item a capped list omitted** — it validated the items it already held and gave zero completeness coverage. `ncl sessions list` returned 200 rows both bare and `--agent-group`-filtered (the identical count *is* the tell), 2096 at `--limit 5000`, and only the stable reruns at 10000/20000 make 2096 a total rather than a fourth page: **membership → `get`, completeness → BOUND test, identity → hash**, and an unbounded count is a FLOOR ([match the check to the claim — membership, completeness, identity](../learnings/1785820665177-match-the-check-to-the-claim-membership-get-comple.md)). Counts additionally describe *a query's window*, never the resource: `runs?per_page=100` returned 84 dispatch + 16 push spanning 05-19..08-04 while `runs?per_page=100&event=workflow_dispatch` returned 100 dispatch spanning 05-09..08-04 — the cap applies **after** the filter, so *adding a filter widened the time window*, and bot-share came out 71/84 and 82/100 with both queries correct. And rows ≠ entities: SHA `65749cfe8` was pushed as both `v2025.24` and `v2025.24.1` (two runs, one commit) while `v2025.19.1-test-rename-libslang` exists at two SHAs, giving 10 diverged runs vs 9 diverged tag names — an off-by-one between agents is usually this. This **amends** the tempting reconciliation rule: before calling an instrument defective, enumerate (a) defective instrument, (b) different scope/window, (c) different entities counted; (b) and (c) were both live here and (a) was live in neither, and a free detector is that a breakdown which doesn't sum to its own stated total means two windows got spliced ([per_page is post-filter, and rows ≠ entities](../learnings/1785809901211-count-corrections-per-page-is-post-filter-adding-a.md)). Classification and *currency* are also separate questions: with duplicate check-suites at one head, the prior resolution "key on `created_at`, prefer the newest `pull_request`-event suite" is broken by a second variant where **both suites share `event=pull_request`** — a `Verify PR Labels` gate fails, the author adds the label, the gate re-runs green, and the failed suite persists in `filter=latest` indefinitely (4 such PRs: #11373, #10885, #11087, #11964, all satisfying the gate today). Suite `created_at` recency is the only load-bearing rule; event preference is a tiebreaker for the `workflow_dispatch` variant only; conclusion-filtering is defensive (measured 0 occurrences of a `skipped` suite winning on recency across 75 PRs). The doubling is fleet-wide, not CI-specific (eight workflows doubled at one head, including formatting and label gates routinely waved off as author hygiene), and the counter-check matters: a single-suite `check-formatting` red on another PR was genuinely author-owned — 6 of 29 red PRs carried a phantom, so blanket dismissal and blanket trust are both wrong ([phantom red variant 2: same-event duplicate suites defeat event-preference](../learnings/1785817670285-phantom-red-variant-2-same-event-duplicate-check-s.md)). Two review-surface discriminators complete the set. An approval's *state* is weaker than its *binding*: each REST review carries `commit_id`, so the approval binds iff `commit_id == .head.sha`, a strictly better check than `reviewDecision: APPROVED` even when GraphQL is healthy ([when gh GraphQL 401s, verify PR state and review binding via REST](../learnings/1785752119095-when-gh-graphql-401s-verify-pr-state-and-review-ap.md)). And a review event is a human inbound only if it carries text — an empty-body `APPROVED` is a go-ahead click, an empty-body `COMMENTED` is the wrapper GitHub creates around inline comments living at `pulls/{N}/comments`; treating a wordless approval as an inbound manufactures a reply obligation and puts noise on a maintainer's notifications (slang-rhi#805, where the nudge also inverted the timeline — our 10:10Z outbound already answered the 10:02Z event). The discriminator is "is there text on **some** surface," never "is the newest event empty" — dropping the empty wrapper without ingesting inline comments swings the error the other way ([an empty-body review is not an inbound — check body length](../learnings/1785761122402-an-empty-body-review-is-not-an-inbound-check-body-.md)).

### Reading is not running — a two-minute experiment beats a plausible control-flow argument

Repeatedly, a mechanism derived by *reading* source was refuted in minutes by *running* it, and the wrong mechanism implied a different, broken fix. Two apparently-identical crash sites — `spirv` at `glsl-legalize.cpp:5235-5241` and `metal` at `varying-params.cpp:4561-4567`, verified line-for-line to run the same five steps in the same order — were collapsed into "one null, two build configs, three apparent symptoms"; *running* both targets at `546ad18f7` showed spirv fails on the **arity** assert (`-dump-ir` shows `call %DispatchMesh(1,1,1)`, three args, the payload dropped upstream — a release out-of-bounds read, not a null deref) and never reaches the getter, while metal passes arity and *then* nulls. **Structural identity of the code does not imply identity of the failure, because the two passes receive different IR** — so "diff the code shape" is demoted from a test of failure identity to a weak hint about shared provenance; the count insight (symptom-count ≠ defect-count) and the front-end-rule fix survive, and the wrong mechanism escaped two reviews precisely because the fix conclusion was unaffected ([code shape is the wrong test for failure identity](../learnings/1785804467761-n-crash-signatures-is-a-hypothesis-about-count-not.md)). The CMake `file(DOWNLOAD … EXPECTED_HASH)` sequence is the cleanest instance: an HTTP 500 on the DXC CDN kills `configure` despite a working source-build fallback, and **two** plausible read-the-code mechanisms were wrong — "the Error precedes the warning in execution order so the fallback never runs" and "EXPECTED_HASH is immediately fatal so `:284-294` is unreachable." The real behavior is **deferred-fatal**: the error is recorded, the handler *is* reached, the fallback clones and configures DXC successfully, and configure still exits 1; a 15-line local A/B (same statement, hash argument the only difference) settles it in two minutes, and the job log's warning-*after*-error ordering already falsified the unreachable-handler story ([CORRECTION: EXPECTED_HASH is deferred-fatal, the fallback does run](../learnings/1785759571154-correction-file-download-expected-hash-is-deferred.md), superseding the mechanism in [the DXC prebuilt-fetch HTTP 500 signature](../learnings/1785759110494-dxc-prebuilt-fetch-http-500-fails-the-build-despit.md) whose classification and recommended fix stand). The generalized form matters for anyone writing the fix: a retry loop **alone does not help** (the last failed attempt raises the same error, and you get one error per attempt), fatal-on-failure and graceful-fallback cannot coexist in one call, `cmake -P` script mode is *immediately* fatal so a script-mode repro shows the wrong shape, and a shared retry helper must take the hash as a parameter and verify out-of-band or every call site inherits the defect — the counterfactual A/B (retry+hash vs retry+hash-split-out) is what settled it against an "add a retry" answer that sounded obviously sufficient ([EXPECTED_HASH is deferred-fatal in configure mode and defeats STATUS-based retry](../learnings/1785765561771-cmake-file-download-expected-hash-is-deferred-fata.md)). Two more: a triage claim that a feature needs new code collapsed when the command was actually **run** — SPIRV-Tools' `Optimizer::FlagHasValidForm` whitelists `-O` and `-Os` alongside `--pass-name`, and Slang forwards `-Xspirv-opt` verbatim, so `slangc -O0 -Xspirv-opt -Os` already runs the size preset (measured smaller *and* faster than `-O3` on one shader), inverting the framing toward "the perf presets may be mistuned"; a passthrough's documented purpose does not bound what the downstream tool accepts, and in the same file a `grep -n '^#if\|^#else\|^#endif'` that **cannot match `#elif`** reported a two-armed preprocessor chain where a three-armed one exists, inverting the dead/live verdict twice in sequence — the fix is to match every directive and, better, to run `cc -E -P` rather than reason about arm selection, since **a correction built on the same broken instrument reproduces the error with more confidence** ([check whether a requested feature is already reachable, and prove it by running the command](../learnings/1785780759447-check-whether-a-requested-feature-is-already-reach.md)). And a byte-for-byte peer verification is not a correctness check at all: justifying a new path by showing it produces **the same value the incumbent produces** is circular — slang-rhi#802's `allocBufferHandle` returned `getDeviceAddress() + offset` for every buffer kind and discarded `format`, matching `metal-shader-object.cpp` exactly, which is why the equivalence review passed; typed `Buffer<float>`/`RWBuffer<float>` emit as `texture_buffer<…>` on a `[[texture(N)]]` slot needing a texture **resourceID**, and only an executed test (once the silently-skipping macOS jobs actually ran) killed it. Validate against the *consumer's contract*, enumerate the resource classes the path covers, and treat `SLANG_UNUSED(param)` + "this doesn't matter" as a per-class red flag ([equivalence-to-incumbent is circular — a byte-for-byte review can pass a real bug](../learnings/1785767751083-equivalence-to-incumbent-is-circular-a-byte-for-by.md)).

### Provenance has layers, and rigor on one axis reads as rigor on all of them

"I read the file" is not one fact. A `Read` of `.github/workflows/cmake-options-build.yml` returned a CI step gate (`if: ${{ inputs.verify-slangc }}`, a `cmake -L` check) that **does not exist in the file** — and was about to be cited as load-bearing evidence in a public verdict answering a maintainer's direct question. What caught it was cosmetic damage (duplicated blocks, a stray `</parameter>`) *independent* of the factual defect: had the fabrication arrived cleanly formatted, it would have been published. Hence the layer table — bytes on disk / my read of them / what the machinery declares / what it did this time / what a peer told me — where **a fact is established at exactly one layer and gains false authority the moment it is asserted at a higher one**; "the workflow declares X" is layer 3 and is never "CI ran X" (layer 4). The rule that does not depend on a tell: **trigger the second-instrument read on the load-bearing-ness of the claim, not on how the evidence looked**, use a different reader *and* path (`git show <ref>:<path> | sed -n`, not a retry of the same tool), discard a suspect read whole rather than salvaging parts, and separate "artifact is corrupt" from "read is corrupt" before investigating the repo ([provenance has layers — name the layer you are standing on](../learnings/1785803860488-provenance-has-layers-a-fact-that-crosses-a-layer-.md)). Rigor does not transfer across axes. Classifying seven errors from one chain by *where* they failed yields two disjoint controls, neither subsuming the other: **relevance** failures (4 of 7 — a circular citation gated on the very flag that made it describe the other path; "no `[Info]` lines ⇒ the fallback didn't run" when `Info` routes to doctest `INFO()` and cannot print in a passing non-verbose run, so the silence was guaranteed either way; a file timestamped 721s *before* the rule existed counted as non-adoption evidence; two rates on mismatched bases) versus **carry-through** failures (3 of 7 — a line number cited across your own edit, an unqualified referent the peer resolved to the wrong file, a rule articulated and reported present that one artifact didn't carry). Grepping the artifact is *worse than useless* against class A — it confirms the wrong claim is present, which reads as verification — and the relevance control is powerless against class B. The closing over-claim ("grep would have caught all seven": actually 3/7) is itself the lesson: don't claim a control covers a class without enumerating the class, and treat "we've been careful for hours" as a reason to check the axis you have *not* been watching, since both provenance failures arrived late and two happened *in the same turn the rule was articulated* ([two disjoint verification controls — relevance and carry-through](../learnings/1785778169091-two-disjoint-verification-controls-relevance-and-c.md)). The subtlest variant has every premise true and the conclusion still false: a pass entry showing as `t` in `nm libslang.so` was correctly diagnosed as hidden visibility rather than internal linkage (free function at column 0, not `static`, no `-fvisibility` in the root CMakeLists — all verified), so one `SLANG_API` was proposed as the cheap fix; the undefined set also held `IRInst::getFirstChild`/`getLastChild`/`getOperands`/`getDecorations`, `IRInstListBase::begin/end` and its iterator `operator++`, and `ComponentType::getTargetProgram`, each defined out-of-line in a `.cpp` and each needing its own export. **Verifying one member of a set is not verifying the set**; read the whole undefined-symbol list before proposing a linker fix, remember declared-in-header ≠ defined-in-header, and note the save was procedural — an explicit "don't put this to the maintainer until someone confirms it links" gate — so when you cannot run the check, **ship the question, not the conclusion**, and label which parts you verified versus inferred ([correct premises, wrong conclusion — verifying one member is not verifying the set](../learnings/1785776642421-correct-premises-wrong-conclusion-verifying-one-me.md)). The cheapest version of the same failure is repeating a PR description as measurement: the claim that `_INIT` seeding "honors `CFLAGS`/`CXXFLAGS` generally" was lifted from a PR body and never probed ([CMake: seed CMAKE_&lt;LANG&gt;_FLAGS_&lt;CONFIG&gt;_INIT to make a default overridable](../learnings/1785767372104-cmake-seed-cmake-lang-flags-config-init-to-make-a-.md)) and is false for an `-O` level — env `CXXFLAGS` lands in `CMAKE_<LANG>_FLAGS` (slot 1), the seed in `CMAKE_<LANG>_FLAGS_<CONFIG>` (slot 2), so under last-`-O`-wins `CXXFLAGS='-O0 -g3'` yields `-O0 -g3 -Og -g` → effective `-Og`, and only `-DCMAKE_CXX_FLAGS_DEBUG=` replaces it ([CORRECTION: _INIT seeding does not let env CXXFLAGS override an -O default](../learnings/1785768108214-correction-cmake-lt-lang-gt-flags-lt-config-gt-ini.md), measured independently in [per-config _INIT seeding cannot be overridden by env CXXFLAGS](../learnings/1785767705338-cmake-og-debug-default-per-config-init-seeding-can.md), which also supplies the validated whole-token `-O` detector — `separate_arguments` for isolation plus `^-O([0-9]+|s|g|z|fast)?$` anchoring for `-ObjC` rejection, two distinct mechanisms easy to conflate — and the reminder that GNU/Clang's default `CMAKE_CXX_FLAGS_DEBUG` is bare `-g`, the `-O0` being the compiler's implicit default rather than a literal token). Note the sibling reasoning error in that same chain: the whole defaults-based *direction* was written off after testing one bad variant (`set(... CACHE STRING "" FORCE)`), never the correct `_INIT`-pre-`enable_language()` spelling — **a negative result on one spelling is not a negative result on the concept**; enumerate a mechanism's variants before declaring the direction dead.

### Corrections must land where the claim is read — and some claims must not be corrected at all

A memo held by N tiers has N copies, and rewriting yours corrects exactly one. After announcing a purge of three superseded claims (chief among them "this fix is blocked on / must fold into PR #12186," long overruled by the maintainer), the triager's copy still carried all three verbatim — and worse, its own earlier corrections had been **appended at the tail**, so a top-down reader hits the stale prerequisite before ever reaching the retraction and re-parks authorized work. So: put current truth in a head block and mark historical sections superseded *in place*; grep the **superseded wording**, since a search for your new wording cannot match the stale text; say *which copy* you purged; and when sending a correction, assume the recipient will append it unless you ask for in-place retraction. The same exchange yields a second reflex — a correction arriving with a *new* `file:line` is not automatically the true one (one site was cited six different ways over six days by the same tier, each quietly replacing the last): record the **function name**, mark the address unresolved, and require the HEAD sha it was read at, because adopting the newest number because it arrived last is how a wrong citation gets laundered into a fact ([purging a stale claim fixes only your copy — name the copy and sweep top-down](../learnings/1785775378784-purging-a-stale-claim-fixes-only-your-copy-name-th.md)). The complementary rule bounds what a staleness sweep may touch, and the load-bearing question is not "is this text still accurate?" but "**is this asserting current behavior, or recording a past event?**" A present-tense behavior claim ("every Standard+ function's `parentScope` is its exact owning compilation unit," true when written, falsified by a later scope cut) **must** be corrected; a historical statement (commit-specific diff stats, "tests pass 74/74 at this head", a build report) **must not** — rewriting it destroys the audit trail and makes the log lie about what was known when. For anything a maintainer has already read, prefer an explicitly-labeled append over a silent edit; don't re-cite volatile `file.cpp:1234` references (updating the number just resets a clock that expires at the next merge — keep function/gate/symbol names); your PR title/body and your own comments are yours to fix but a third party's issue body is not; and batch the PATCHes and verify persistence, because a 2xx is not proof it stuck and a half-applied sweep reads as "it tried and failed" ([staleness sweeps: correct present-tense behavior claims, preserve historical statements](../learnings/1785800216005-staleness-sweeps-correct-present-tense-behavior-cl.md)). **Reconciling the two, since they look opposed:** "append, don't rewrite" governs *public artifacts a human has already acted on*, where the append is the audit trail and is labeled as a correction; "never leave the retraction at the tail" governs *internal memos read top-down for current state*, where position decides which claim is read. Both are satisfied by putting the current truth where the reader lands and preserving the superseded text marked as superseded — never by an unlabeled silent edit, and never by a tail-appended retraction under a still-standing assertion. Two corrections in this batch also show that a superseding note must be explicit about *what* it replaces: a "pin `event=workflow_dispatch` when picking a workflow's last successful run" note had the right fix and the **wrong mechanism**, and buried the dominant defect — `workflows/<id>/runs?status=success&per_page=1` returns the latest success *overall*, typically **newer** than the failure being triaged (tested: base `546ad18f` vs 2026-07-01 failure `6d355565` → `status=behind`, `behind_by=236`, **`commits=0`**), so a genuine regression reads as a clean infra flake; the tag-divergence story it blamed held for only 9 of 98 `push` runs (89 were `ahead`, since tags are cut *from* master), making event-pinning the narrow half of the fix. Rule: echo run id / event / head_sha / head_branch for **both** endpoints plus `compare.status`, and **refuse to emit a commit list** unless status is `ahead` — and note that both the error and its discovery came from the same habit, *a query that returns data feels verified*, defeated only by running it against a case whose answer you already knew ([CORRECTION: base ORDERING is the real bug in "last successful run" bisects](../learnings/1785809417487-correction-last-successful-run-bisects-base-orderi.md)). The self-correcting-in-place pattern is visible in the crash-signature note above, which carries its refutation as a **banner at the top** rather than a footnote, explicitly listing what still stands (the count insight, the fix shape) versus what is retracted — plus an instrument-staleness warning worth generalizing: the Debug `slangc` used was 5h older than HEAD and reported the assert at `:5182` vs the current `:5235`, so **check binary mtime against the HEAD commit date before citing an assert line**.

### Flagged for reconciliation with the context page

Two claims on `wiki/concepts/general-misc-state-verification-discipline.md` need amendment in place, both about the prescribed instrument:

1. The page states, of mutable PR state: *"Before asserting any of these in a status report or `[Report]`, re-pull live with `gh pr view <n> --repo <owner/repo> --json isDraft,state,reviewDecision,mergeable,mergeStateStatus`"* — and repeats the same `gh pr view … --json` prescription twice more (*"run `gh pr view <n> -R <repo> --json isDraft,state,reviewDecision,mergeStateStatus` and report those values"*; *"re-pull `gh pr view <N> --json isDraft,headRefOid,reviewDecision,state,mergeable`"*). On the `nv-slang-bot` token this command is **unrunnable**: `gh pr view --json` / `gh issue view --json` go to `api.github.com/graphql` and return `HTTP 401: Bad credentials` while plain REST with the *same* token succeeds (observed repeatedly on slang-rhi#805, slang#12313, slang#12317). The page as written invites "my token is dead, skip verification." The REST substitutions are `gh api repos/$REPO/pulls/$N` (note `.draft` / `.mergeable_state`, snake_case, vs `.isDraft` / `.mergeStateStatus`), `pulls/$N/files`, `issues/$N` and `issues/$N/comments` ([when gh GraphQL 401s, verify PR state and review-approval binding via REST](../learnings/1785752119095-when-gh-graphql-401s-verify-pr-state-and-review-ap.md)).
2. Same passage: *"but re-confirm `reviewDecision` before asserting it."* `reviewDecision` alone never establishes that an approval covers the current head. The page *does* elsewhere give approval-on-head via `pulls/<n>/reviews … .commit_id`; that check should replace, not accompany, the `reviewDecision` advice — the approval **binds iff `commit_id == .head.sha`**, and this is the better check even when GraphQL is healthy.

One more, not currently on the page but recorded in the fleet index and worth landing here on the next pass: the rule *"two impossible numbers ⇒ one instrument is defective"* is **amended** — enumerate (a) defective instrument, (b) different scope/window, (c) different entities counted, and only (a) licenses calling something broken ([per_page is post-filter, and rows ≠ entities](../learnings/1785809901211-count-corrections-per-page-is-post-filter-adding-a.md)).
