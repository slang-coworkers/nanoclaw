## TL;DR

Transferable challenger probes for the slang PR-approver — the independent, from-source checks that catch defects Devin/CodeRabbit skim past. Most are "read the whole producer / every trigger / every branch," not "trust the PR body's justification."

- **Registration / gate / emit PRs: enumerate every producer branch.** When a PR adds a registration (`addFileDependency`, a decoration, an emit, a gate term) at ONE site inside a function with multiple branches producing the same output, grep the enclosing function for every `return` that yields the same product and check each. An unjustified "deliberately not touched" in an untrusted body is a claim to probe, not a boundary to respect.
- **Diagnostic-pass PRs: check the pass's own run-gate, not just the trigger-present test.** A diagnostic is only as reachable as the pass that emits it; if the pass is opt/flag-gated but the failure it guards is always-run, the bug survives on the ungated path while the default-path test stays green.
- **New declaration-warning: prove zero blast radius by enumeration keyed on the exact AST gate** — grep the core module and existing tests for the trigger keyed on the exact AST class (separate sibling shapes the gate is disjoint from), then confirm green CI at head. "Zero blast radius" is a provable enumeration, not a plausibility call.
- **Gate-REMOVAL / hoist PRs invert the dead-flag probe** — a symbol moved out of an `#ifdef` can't silently-skip; the real risks are redefinition in the guarded build, dependency scope at the new location, and dangling still-gated users.
- **CI-gate `if:`/`needs` analysis:** a job with `needs` but no status function gets implicit `success()`, so a skipped need makes it SKIP (not proceed). A `result=='skipped'` allowance must be *scoped to the event that skips it* or the security gate fails OPEN. Enumerate EVERY trigger in `on:` and answer the trust question per-trigger; a `workflow_dispatch` trigger checks out the dispatcher-selected ref.
- **A `workflow_dispatch`-only probe makes no green-by-construction CI claim** — the zero-bits rule doesn't transfer; the real questions are supply-chain surface.
- **Collective-op equivalence claims are RED FLAGS to probe stage-by-stage** — wave-aggregate count-equivalence is FALSE in fragment stages (helper lanes are counted but have no memory effect).
- **Head-motion discipline:** on an actively-iterating PR the head can move between staging and record; re-verify the LIVE head *at record time*, re-cite line numbers at the pinned head, and decide each revision only from its own fresh evidence. A maintainer re-request on an unchanged decided head owes an independently-defensible re-verification, not a no-op or blind-trust.
- **Investigate direction before BLOCK** — a huge changedFiles count can be benign stale-branch reformat drift; the size cap correctly ABSTAINs, but BLOCK requires a verified 🔴 bug, not a file count.

## Producer/gate/emit PRs: read the whole producer

The core probe for any "populate/register/gate/emit X" PR is enumerate-every-branch. A [gate/dep-registration PR must be probed for a SECOND load path with the same trigger](../learnings/1787262162130-approver-challenger-miss-a-gate-dep-registration-p.md): the fix added `addFileDependency` in the primary include loop but a second `.slang-module` load path (the standard-module fallback) returned a module without it — the exact bug, left uncovered. The MISS came from accepting the body's unjustified "deliberately not touched"; the first challenger question for these PRs is "how many producer branches are there, and does the PR cover all of them?"

For [diagnostic-pass PRs, check the pass's own run-gate](../learnings/1787335910005-approver-challenger-miss-diagnostic-pass-prs-check.md): E55215 is emitted only by `checkUnsupportedInst`, gated on `!shouldPerformMinimumOptimizations()`, while the CUDA emitter failure it guards is *not* opt-gated — so under `-minimum-slang-optimization` the ICE stays reachable and undiagnosed and the default-path test is green. This is the diagnostic analogue of the gate/flag positive-control probe: the run-gate is the flag.

For a [new declaration-warning, prove zero blast radius by enumeration](../learnings/1787347377434-approver-challenger-probe-new-declaration-warning-.md) keyed on the exact AST predicate (`as<CallableDecl>`, separating the `ParamDecl` siblings the gate is disjoint from) across the core module and pre-existing tests — a diagnostic-surfacing change's blast radius is every input that already triggers it, which can redden clean-output tests bots don't run. And [gate-REMOVAL / hoist PRs invert the dead-flag probe](../learnings/1787348836397-approver-challenger-probe-gate-removal-prs-invert-.md): a symbol hoisted out of `#ifdef GUARD` can't silently skip, so probe redefinition-in-the-guarded-build (`grep -n 'struct <Name>'` → expect exactly one), dependency scope at the new location, and dangling still-gated users; a compile-time-only hoist is the widening exception.

## CI-gate `if:`/`needs`/`success()` analysis

Three atoms document the GitHub-Actions job-gating semantics that trip up CI-gate PRs. [Skipping a gate job does NOT let a `needs`-dependent run](../learnings/1787749255968-approver-challenger-miss-skipping-a-gate-job-does-.md): a job with `needs` but an `if:` carrying no status function is rewritten to `success() && (<original>)`, and a *skipped* need is not a success — so the author's "GitHub treats a skipped need as satisfying the dependency" is FALSE; the downstream job skips too, and the `always()` aggregate `check-ci` then FAILS (fail-closed, self-defeating). The correct fix uses a status function *and* re-asserts the other deps' success explicitly.

Worse, [a skipped-gate allowance must be scoped to the event that skips it](../learnings/1787773301880-approver-challenger-miss-a-skipped-gate-allowance-.md), or the security gate fails OPEN: an unconditional `... || needs.<gate>.result == 'skipped'` accepts a skipped gate on *every* event, not just the intended `merge_group` — and because the gate's own `if:` has an implicit `success()` over its upstream `filter`, it skips on `pull_request` too, running the protected job without approval. Also verified: job outputs can persist even when the producing job later becomes non-successful, so "a failed upstream yields empty outputs" is a FALSE security argument — a boundary must fail closed by construction. A fix for one failure direction can open the other (R1 fail-closed → R2 fail-open), so trace the new `if:` in full for both directions.

The generalization is [check EVERY declared trigger, not just the one the PR justifies](../learnings/1787929050935-approver-challenger-miss-ci-workflow-that-omits-an.md): a nightly that justifies dropping the approval gate for `schedule` (safe: `github.sha` = default-branch tip) can silently declare `workflow_dispatch` (dispatcher chooses the ref → arbitrary-branch checkout onto the gated internal resource). Enumerate `on:`, answer trust per-trigger, and check WHERE the gate actually lives — an `environment:` gate on a job in `ci.yml` does not protect a *different* workflow calling the same reusable jobs directly. Conversely, a [`workflow_dispatch`-only capability probe](../learnings/1787211686414-approver-challenger-miss-no-op-capability-probe-wo.md) makes NO green-by-construction CI claim on the PR, so the zero-bits rule does not transfer — read `on:` first; if the only trigger is `workflow_dispatch`, the real questions are supply-chain surface (permission scope, does it checkout code, secrets).

## Collective-op equivalence and head-motion discipline

A [collective-op equivalence claim is a RED FLAG](../learnings/1788201896759-approver-challenger-miss-wave-aggregate-count-equi.md): wave-aggregate count-equivalence ("aggregated == per-lane by construction") is FALSE in fragment stages — helper invocations participate in wave ops (counted by `WaveActiveCountBits`, electable by `WaveIsFirstLane`) but their stores have no memory effect, so counts silently under/overcount. Don't clear such a claim on a program-point argument; enumerate the ways the active mask differs from the set of lanes with observable effect (helper lanes, divergent control flow, whether the elected write is effective), and require a per-STAGE trigger-present test. The same atom warns: a change whose whole justification is a performance number is a CLAIM to probe (the human's own measurement showed no speedup), not a premise.

Head-motion is a recurring auditability trap. On [rapid-fire synchronize pushes, re-verify the LIVE head at RECORD time](../learnings/1787558531650-approver-clause-gap-rapid-fire-synchronize-pushes-.md), not just at staging — a critique-gated decision can take minutes and go stale during its own critique (a BLOCK staged on one head had its bug fixed by the push that superseded it). Make `gh pr view --json headRefOid` == staged commit_sha a pre-record gate. [A bot-authored PR head can move mid-decision](../learnings/1787682906018-approver-clause-gap-bot-authored-pr-head-can-move-.md) — the automated author reacts to review signal fast, sometimes shipping the exact fix the critique surfaced; re-confirm the head at the start of recording and after the critique, and decide Rn only from Rn's fresh evidence. A [maintainer re-request on an already-decided unchanged head](../learnings/1787294720097-approver-dispatch-maintainer-re-request-on-an-alre.md) owes an independently-defensible verdict: neither silently no-op nor blindly re-emit the prior session's decision.md — re-verify the load-bearing claims from source at head, then `record_decision` idempotently (append-only, first-write-wins; re-recording the same verdict is a harmless no-op). Finally, [investigate direction before BLOCK](../learnings/1787157759114-approver-clause-gap-a-tiny-feature-pr-can-show-a-h.md): a tiny-feature PR can show a huge changedFiles count from benign stale-branch reformat drift — the `tier_eligible` size cap ABSTAINs correctly, but BLOCK requires a verified 🔴 bug; verify drift-vs-revert by comparing head content against each merge parent before treating the count as alarming.
