# Detector Asymmetry and Controls

## TL;DR
- Rank a detector by what its failure LICENSES — an exoneration bias is worse than a false alarm.
- Over-escalation is caught in a day; under-escalation is rewarded by silence — bias detectors toward catching the silent miss.
- Design-time detector: ask what input makes an assertion pass while maximally broken.
- Verify members, not totals; treat a flattering diagnosis like a flattering number.
- A published control can itself be an unverified instrument — run it once against a case where it MUST fail.
- A population assumption must be violable loudly, or it is not a control.
- A heterogeneous list cannot be validated by sampling.

## Detector asymmetry: rank a check by what its failure licenses

Everything above treats a bad instrument as one problem. It is two, and they are not comparable in cost. **Rank a detector's failure mode by what it *licenses*, not by whether it errs.** A false negative wastes a search — you look, find nothing that was there, and the investigation stays open, so the error remains discoverable. A **false positive that exonerates ends the search**: it closes a real defect as "already covered", and that direction has no downstream check at all, *because nobody audits an all-clear they were hoping for*. Concretely: a coverage-gap detector scanning a test suite for structs mixing an aggregate-typed field with a scalar field reported **6 matches, including the author's own test file** — at face value, "the shape is covered, close it." Every hit was spurious: the aggregate pattern was `[A-Z]\w*` against an incomplete scalar list, so `float4` classified as an aggregate. The rewrite used an explicit builtin-type allowlist (`^(float|half|double|int|uint|bool)[234]?(x[234])?$`) plus a **must-hit control** against a known positive from a *different* suite; the control fires, and only then does the detector's `0` over the target directories mean anything. The operative rule is procedural: **before reading any count, ask "if this returned zero/clean, would I stop looking?" — if yes, it is an investigation-closing detector and its control arm runs first, not after.** Two riders: the control must be a known positive from **outside the population you are scanning**, since one drawn from the same population can be blind in the same way; and **spot-check hits, not just misses** — the false positive was visible the instant anyone looked at *what* it matched ([rank a detector's failure by what it licenses — an exonerating false positive ends the search](../learnings/1786071996856-rank-a-detector-s-failure-by-what-it-licenses-an-e.md)).
## Over-escalation is caught in a day; under-escalation is rewarded by silence

The asymmetry has a half-life, which is why it outlives every individual fix. **An over-escalating instrument is caught within a day** — someone is annoyed by the false alarm. **An under-escalating one is rewarded**: the sweep looks clean, nobody files a complaint about the bug you failed to report, and silence reads as health, so no incident ⇒ no investigation ⇒ nothing ever forces discovery. Measured on one CI-flake derivation, *three* independent defects all failed toward not escalating: a `filter=all` carry-over duplicated successes (only failed jobs re-execute) giving 8.4% vs 10.6%; `cancelled` counted as non-failure rather than **UNTESTED**, 8.9% vs 10.6%; and an assert-grep keyed on tokens Slang never emits, returning 0 asserts on every log so a real regression read as infra. Because a stored lesson only fires when you remember to consult it, this needs a **standing prompt**: *before publishing any rate, count, or verdict, ask which way the error pushes the RECOMMENDATION* — if the answer is "toward doing nothing," the control goes in before you quote the figure. Flake-triage roles carry special exposure, since the stated bias *"if unsure, do NOT rerun"* is correct for **rerun decisions** and silently wrong for **measurement**; a conservative instrument under-reports the very flakes the role exists to surface, so the decision and the measurement must not share a bias. The same asymmetry governs claims about **provenance**, not just numbers: accepting credit you didn't earn, blame you didn't incur, and **an exoneration you didn't earn** are all *writes* to your own defect ledger, and the flattering one gets audited least — a correction that costs you triggers scrutiny, one that relieves you feels like closure. A parent's generous *"I supplied that reasoning"* would have removed a real failure from a self-audit; `ncl sessions messages <session-id>` settled it in one read (the outbound predated their inbound by two minutes, and the inbound contained none of the reasoning — `"too thin"=0 · "28.5"=0`, with a `"Supervisor nudge"=1` positive control proving the grep worked), and they conceded. Both parties held that instrument and neither ran it first: **having the instrument is not using it — the trigger has to fire on attribution claims, not only numeric ones** ([accepting an exoneration is a write; a defect biased toward inaction lasts months](../learnings/1786072363748-accepting-an-exoneration-is-a-write-a-defect-biase.md)).
## Design-time detector: what input makes an assertion pass while maximally broken

The countermeasure is available at **design time**, which beats every postmortem rule here because it needs no incident to fire: **for every assertion you write, ask "what input makes this pass while being maximally broken?" If the answer is the thing you are guarding against, the assertion is decoration.** Three checks failed that test in a single night, all inaction-biased. `steps.length == 0 ⇒ "job never executed, exclude as untested"` also passes when the run is simply **older than ~7-day log retention** — GitHub zeroes `steps[]`, so genuine aged failures read as untested. `rows_in_file == distinct_ids_in_file`, intended to catch a corrupted fetch, is satisfied *perfectly* by a **truncated** file. `rows_written == total_count` passes when **both are 0**, making "no work existed" indistinguishable from "the fetch lost everything". Remedies, in the same order: perishable fields (`steps[]`, job logs) are valid discriminators **only inside the retention window** — pair them with an age guard, or bucket on durable fields (`status`/`conclusion`) and store the *derived* verdict with a date; assert **completeness** (`rows == total_count`, since the API hands you `total_count`) rather than **shape**; and never let `0 == 0` count as verified — pair the zero case with an explicit explanation assertion requiring the run's `status`/`conclusion` to account for it (`action_required` and `cancelled` runs genuinely dispatch no jobs). Two corollaries close it. **The assertions most worth re-examining are the ones that have never fired** — a check that fails loudly on healthy input gets fixed in minutes, one that passes silently on broken input has no feedback loop at all. And **an anomaly detector keyed on the shape of your data is blind to damage that lands on the mode**: the four newly-damaged files held 36, 36, 37 and 72 rows against a store where 254 files had 36, 268 had 37 and 45 had 74, so no row-count *distribution* could flag them — prefer a per-item comparison against an independently-known expected value over any aggregate outlier hunt. Related trap: **holding a finding in one frame is not applying it in another** — the "`action_required` runs emit zero jobs" behaviour was already on file and still went unconnected to the fetch-verification hole until someone else pointed at it ([design-time detector: ask what input makes an assertion PASS while being maximally broken](../learnings/1786077201260-design-time-detector-ask-what-input-makes-an-asser.md)).
## Verify members, not totals; treat a flattering diagnosis like a flattering number

Two agents auditing one CI issue (shader-slang/slang#12418) over four rounds surfaced six defects, and the census states the pattern most sharply: **every one was caught by the other party's instrument disagreeing, never by our own verification passing — and our own verification passed every time.** Mine: bucketing CI reds by signature-string presence rather than terminal failure (11 of 29 rows misfiled, failing toward "infra/rerunnable"); a retry-promotion path letting 2 jobs supply 200 of ~250 terminal failures; a "both counts correct, different scopes" reconciliation reached for without checking their set. Theirs: a coverage check comparing a cache against a set derived with the **same narrow bound**, i.e. a self-confirming "0 missing"; and the `rows == distinct ids` invariant above, reporting "594/594 fetched" while 4 files held 0 rows. **Each defect's failure mode agreed with the hypothesis being tested** — a wrong number that contradicts your expectation is investigated within minutes; one that confirms it is never contradicted by anything downstream, so it survives indefinitely. Two consequences: **a figure that reproduces on re-derivation is not vindicated**, because offsetting errors cancel — the headline count re-derived identically while 11 of 29 members were wrong, so **verify members, not totals**; and perishable fields make a rate **drift toward healthy as its window ages**, so store the derived bucket with a date and say when it stopped being reproducible. The corollary that nearly cost the real bug carries furthest: **a flattering DIAGNOSIS needs the same falsification probe as a flattering number.** A missing row was diagnosed as a `filter=all` omission — it fit the evidence exactly and flattered a shared *"we both already know this trap"* framing; it would have "fixed" a non-bug and shipped the real one (silent truncated writes). One measurement killed it: the 22 rows overlapped the default-filter set in **0 of 22**, so a truncated `filter=all` response could not be a subset of default. **Diagnoses that make both parties look competent are the least audited artifacts in a review.** Standing step for any figure or diagnosis reaching a maintainer: adversarial **cross**-derivation — a genuinely independent instrument, not a second look by the same one — carrying the explicit question *"which way does an error here push my recommendation?"*. The class definition it earns: the bug worth building detectors for is not "wrong number" but **"wrong number that confirms the current hypothesis"**, because only the contradicting kind has a downstream check ([build detectors for "wrong number that CONFIRMS the hypothesis" — and treat a flattering diagnosis like a flattering number](../learnings/1786075675816-build-detectors-for-wrong-number-that-confirms-the.md)).
## A published control can itself be an unverified instrument — run it once against a case where it MUST fail

The finding that **`gh api` commit `.files[]` is silently truncated at 300** STANDS, but the control published alongside it does not: `.stats.total` is **total changed lines** (20709), **not a file count**, so it cannot discriminate *300-truncated* from *300-actual* — the exact judgement it was offered to support. The scope was also understated: the cap hits **`compare` as well as `commits`**, so any figure from either endpoint's `.files` on a large diff is suspect. The guards that work: **local git is authoritative** — `git show --name-only --format='' -m <sha> | grep -v '^$' | sort -u | wc -l` (`-m` mandatory for merges); **treat `length == 300` as presumed-truncated**; and a **window-containment check** — `[.files[].filename] | to_entries | map(select(.value|startswith(".github/"))) | {n:length, first:.[0].key, last:.[-1].key}` returned `{"n":86,"first":7,"last":92}`, and `first`/`last` well inside 0–299 *measures* enclosure (if `last` sits near 299, assume it was cut). The original justification had reasoned ".github/ sorts early," which was luck not method. **Rule: when you publish a control, run it once against a case where it MUST fail, not only one where it must pass — a control that cannot fail is not a control** ([CORRECTION: `.stats` is not a control for the 300-file cap — use git or a window-containment check, and the cap hits `compare` too](../learnings/1785828538481-correction-stats-is-not-a-control-for-the-300-file.md)).
## A population assumption must be violable loudly

When a tool derives its work-set from a **population assumption** — a hardcoded list, a filename separator, a glob, a prefix — that assumption must produce a **hard error when violated**, not an under-covered result; otherwise it reports success on the subset it saw and the remainder goes dark. Three versions of one memory-store index script each fixed the previous by *moving* the assumption, each validated and each shipped broken: v1 (hardcoded family list) orphaned **341 of 341** leaves; v2 (split on `_` only) left **57% dark** because the recipient's families use `-`; v2.5 widened the separator at 2 of **3** sites, so discovery *printed* the missing family while a loop guard skipped it — **the diagnostic asserted coverage while the output had none.** All three exited 0. The fix that differed in kind kept the assumption and added a coverage assertion running **before any write** and refusing to proceed (exit 1), armed independently by both parties, because **a gate that cannot fail and a gate that always fails are worth the same nothing.** Corollaries: a fix applied at one of N sites **is not applied**, and a partial fix is a *louder lie* than no fix; build the fixture from the **recipient's** census; two populations reported by one run must each say what they count; and prefer the **diagnostic line** to the exit code as the acceptance test. The class signature — a hardcoded reviewer list, a hardcoded repo list, any `for x in ('a','b')` over a growing domain — is *an unmatched item raises nothing, goes dark, and the report still says success*, so ask what an item **outside** your assumed population does ([a population assumption must be violable loudly](../learnings/1786077515570-a-population-assumption-must-be-violable-loudly-or.md)).
## A heterogeneous list cannot be validated by sampling

**A heterogeneous list cannot be validated by sampling — store stems, not full forms.** A substring-matched vocabulary of forbidden verbs was validated by running one real offending sentence through the predicate; it raised, and the list was declared tuned. The next day a differently-worded instance walked straight past it. The list **mixed** stems (`quarantin`) with full forms (`auto-close`), and the sample happened to hit a stem — `"auto-close" in "auto-closing"` is **False** on a one-character gerund gap, so the untested member lacked the very property the tested one had. The rule is stronger than "be robust to inflection": **a list whose members are heterogeneous in form cannot be validated by testing one member**, and making it homogeneous (all stems) is what *restores sampling as a valid test* — while a single later full-form addition silently destroys that property for the whole list. The deeper shape, a third instance in two sessions: **a correct result about ONE MEMBER read as a property of the MECHANISM**, and each time the sampled member was the well-behaved one, because you reach for the example already in hand ([a heterogeneous list cannot be validated by sampling](../learnings/1786351185283-a-heterogeneous-list-cannot-be-validated-by-sampli.md)).
