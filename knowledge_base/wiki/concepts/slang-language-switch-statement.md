# Slang switch: front-end validation, missing diagnostics & SPIR-V codegen

Slang's C-style `switch` has a cluster of independent defects surfaced by maintainer **skiminki-nv** in a systematic hardening sweep (issues #9999, #12236–#12240, 2026-07). They *look* like one bug family — they share the two-pass file cluster `slang-check-stmt.cpp` (semantic `SemanticsStmtVisitor::visitSwitchStmt` / `validateCaseStmts`), `slang-lower-to-ir.cpp` (`lowerSwitchCases`), and `slang-emit-spirv.cpp` (`kIROp_Switch` emit) — but they have **distinct root sites at different layers**, so one fix rarely covers two. The transferable discipline is: verify the actual root site with `-dump-ir` before deduping, and hold the fix (triage + verdict only) because skiminki-nv self-files these to *track* and self-defers until an explicit "make a PR."

## Missing-diagnostic facet: statements silently dropped (front-end/lowering asymmetry)

The oldest thread is a **silent-drop** gap: statements before the first `case`/`default` label — and, in the general #9999 case, an entire label-less switch body — are discarded with **no diagnostic**, while statements after a `break` correctly warn `E41000 unreachable-code`. The asymmetry's root is that `lowerSwitchCases()` (`slang-lower-to-ir.cpp` ~L9305) never *lowers* pre-first-label statements, so they never reach `startBlockIfNeeded()` (the only `Diagnostics::UnreachableCode` emit site); a `break` terminates the IR block so the *next* statement does hit that path. #12236 (leading statements) and #9999 (whole label-less body) are the **same root** — one fix at the L9305 branch covers both — and the recommended shape is to emit E41000 there rather than discard, co-located with the established "IR-lowering does source-level E41000 diagnosis" pattern [Slang switch: pre-first-case statements silently dropped (E41000 gap), same root as #9999](../learnings/1785173842957-slang-switch-pre-first-case-statements-silently-dr.md). The #9999 design fork (warning E41000 vs a hard E30606 error) was resolved 2026-07-27 in favor of a warning — see [[wiki/topics/slang-compiler.md]].

## Placement facet: nested case labels escape uniqueness checks and ICE

A **traversal-depth mismatch** between the two passes lets `case`/`default` labels nested inside an inner `{ }` block or `if` slip past validation: `validateCaseStmts` (`slang-check-stmt.cpp:360-399`) iterates **only the direct children** of the switch body's `SeqStmt`, so a deeper `case` is never added to the duplicate-detection `HashSet` (E30605 never fires), while `lowerSwitchCases` *recurses* through `BlockStmt`/`SeqStmt` and hoists it — yielding either a silent duplicate-case emit or, for a `case` inside an `if`, an `SLANG_UNEXPECTED("case or default not under switch")` E99997 ICE. The recommended fix makes `validateCaseStmts` recurse and reject any non-direct-child case with a new 306xx diagnostic [slang-switch-nested-case-labels-escape-uniqueness-and-ICE](../learnings/1785176032715-slang-switch-nested-case-labels-escape-uniqueness-.md). The load-bearing refinement the triage memo omitted: the recursion **must STOP at a nested `SwitchStmt` boundary** — a `case` inside an inner switch is legal and belongs to that inner switch, and mirroring `lowerSwitchCases`'s existing stop-condition avoids false-positives on every nested switch; `__target_switch`/`__stage_switch` use a *different* AST node (`TargetCaseStmt`) and must not be touched [slang switch #12239 — reject nested case labels in validateCaseStmts, but STOP recursion at inner SwitchStmt](../learnings/1785176804780-slang-switch-12239-reject-nested-case-labels-in-va.md).

## Condition-type facet: bool and float selectors reach invalid SPIR-V

Two sibling bugs are wrong-typed switch *conditions* that the front-end fails to normalize. **Bool** (`switch(b)` with `case true:`) aborts on `-target spirv` with the `slang-emit-spirv.cpp: intLit` assert, because `lowerSwitchCases`→`IRBuilder::getIntValue` mints an `IRBoolLit` (a distinct op from `IRIntLit`) for a bool `caseType` and no SPIR-V legalization normalizes it; the fix is to normalize in `processSwitch()` (insert a bool→int `IRIntCast`, rebuild the `IRSwitch` with true→1/false→0), never to relax the emit assert [slang bool switch condition asserts on SPIR-V (intLit) — missing bool→int legalization](../learnings/1785174386328-slang-bool-switch-condition-asserts-on-spir-v-intl.md). **Float** (`switch(f)`) is accepted and produces invalid codegen on *every* backend (SPIR-V just catches it via validation) because `SemanticsStmtVisitor::visitSwitchStmt` has a literal `// TODO(tfoley): need to coerce condition to an integral type` at `slang-check-stmt.cpp:406` — the condition is never validated to integer while each case label *is* coerced, yielding an inconsistent `switch(float, …, int-labels)` IR. This is a front-end representation bug (codegen legalization is the wrong layer), and enforcing "switch condition must be integral" at the shared `visitSwitchStmt:406` site is one policy point covering **both** float and bool [slang-float-switch-condition-accepted-invalid-codegen-frontend-gap](../learnings/1785175092329-slang-float-switch-condition-accepted-invalid-code.md). Both carry maintainer design forks (reject vs coerce), so they are triage-and-hold, not fix-authorized.

## Emit facet: OpSwitch case literals hard-coded to 32 bits

The purely emit-layer bug: a 64-bit integer selector (`uint64_t`/`int64_t`) emits a truncated `OpSwitch` — `slang-emit-spirv.cpp` writes each case literal as a single `SpvWord` (`emitOperand((SpvWord)intLit->getValue())`), but the SPIR-V spec requires a literal to occupy the same word count as the selector type (2 words for 64-bit). The IR is correct (`lowerSwitchCases` builds i64 case values); the fix belongs at emit, mirroring the width-aware `emitIntConstant`/`SpvLiteralInteger::from64` model already in the same file, and is verifiable at compile time with `SLANG_RUN_SPIRV_VALIDATION=1` (a 32-bit control compiles clean) [SPIR-V OpSwitch case literals are emitted at fixed 32-bit width (breaks 64-bit selectors)](../learnings/1785176355400-spir-v-opswitch-case-literals-are-emitted-at-fixed.md). This is a **distinct** root from the bool/float condition bugs — do not fold them together. The shipped #12240 fix pins two reusable specifics: query selector width once via `getIntTypeInfo(...)` and emit `SpvLiteralInteger::from64(...)` (2 words) when `width > 32` else `from32(...)` (the 32-bit path stays bit-identical to the old cast); and its `-target spirv-asm` FileCheck must match the SIGNED 64-bit decimal that spirv-dis prints for a case literal (e.g. `-4294967301`, not the unsigned two's-complement), with case values chosen above 2^32 so a correct two-word literal is distinguishable from a truncated one. The same close-out also surfaced a delivery-gate mechanic that binds every switch-fix PR: `gh pr create` is DENIED by the critique-gate hook until PLAN_REVIEW **and** CODE_REVIEW **and** OUTPUT_REVIEW are each recorded (OUTPUT=approve), each via a fresh `/codex-critique` call using the canonical developer-instructions VERBATIM (the hook diffs sentinel lines); and codex is strict on test-comment hygiene, flagging change-history narration ("Previously… truncated") and "Regression test for…" openers — keep enduring rationale in the comment and put the issue link as a trailing "See <url>" ([SPIR-V OpSwitch case literals must match selector word-count (#12240) + delivery-gate needs all 3 codex stages](../learnings/1785233535175-spir-v-opswitch-case-literals-must-match-selector-.md)).

## enum:bool switch facet — a front-end fold that unlocks four backends (#12260 / PR #12275)

A fifth condition-type facet closes the cluster: `switch` on `enum E : bool` failed `E39999 "could not extract value from integer constant"` at every case on ALL targets, because `TypeCastIntVal::tryFoldImpl`'s inner `convertValue` lambda (`slang-ast-val.cpp`) had cases for every integer base type but **no `BaseType::Bool` arm**, so the enum-case fold returned an unfolded `TypeCastIntVal` that the downstream `checkConstantIntVal` consumer rejected — a front-end *checker* failure, distinct from the SPIR-V-legalize `E99997` that #12237/#12254 hit for plain `switch(bool)` ([enum:bool switch fails E39999 — TypeCastIntVal lacks BaseType::Bool](../learnings/1785318110996-enum-bool-switch-fails-e39999-typecastintval-tryfo.md)). The correct fix arm is the C boolean cast `resultValue = (resultValue != 0)` matching every sibling case — **not** the `& 1` truncation first proposed: `& 1` is not load-bearing for the wraparound test (that is enforced upstream in `_incrementEnumerator`) and would actively regress direct `(bool)2`/`(bool)4` folds that share the same `convertValue` path ([CORRECTION: fix arm is (bool)!=0 NOT &1 — verify load-bearing claims before posting](../learnings/1785320231054-correction-enum-bool-switch-fix-arm-is-bool-0-not-.md)). The deeper reviewer lesson generalizes the whole facet: a **target-agnostic front-end fold newly lets a construct reach codegen on every backend**, and each backend's switch/selector legalization is the real gate — they are asymmetric ([target-agnostic front-end fold reaches ALL backends](../learnings/1785374956687-target-agnostic-front-end-fold-reaches-all-backend.md)). Concretely, `legalizeBoolSwitchForKhronos` (fully target-agnostic despite the name) was wired SPIR-V/GLSL-only, so the newly-reachable `switch(enum:bool)` ICEd on WGSL with `E99997 "unexpected: 8 bit integer value emitted"` at `WGSLSourceEmitter::emitSimpleValueImpl` (no `BaseType::Bool` arm → falls into the `Int8` `SLANG_UNEXPECTED`); the fix is to run the bool-switch legalize for the WGSL block too, not to add a Bool arm to the emitter ([WGSL crashes on bool-typed IRIntLit switch case — legalizeBoolSwitch must run for WGSL too](../learnings/1785375838727-wgsl-crashes-on-bool-typed-irintlit-switch-case-no.md)).
