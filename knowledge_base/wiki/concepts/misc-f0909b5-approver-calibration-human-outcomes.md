## TL;DR

Calibration lessons for the auto-approver on how to read HUMAN signals and how to score an abstain against a later merge. The verdict parser reads only the synthesized bot review doc; it is silent about human state — so the challenger owns "is there a live human block?"

- **A standing, un-dismissed maintainer `CHANGES_REQUESTED` blocks WOULD_APPROVE** even when every bot finding is resolved — auto-approving over a live human "not as-is" is the worst false-safe. Confirm dismissal via the TIMELINE (`review_dismissed` event), not the reviews array; a new push does NOT auto-dismiss.
- **A `COMMENTED` review can still carry substantive change-requests.** On a `live_late` PR read the review THREAD against the head timestamp; a `synchronize` webhook can fire with NO new commit (re-triggered by fresh review comments), so "synchronize" ≠ "author responded."
- **A live, unanswered maintainer verification request** ("not looking for a rubber stamp") on a silent-failure-mode PR reserves the stamp → ABSTAIN.
- **But abstain when the concern is genuinely undecided, not when owners already dispositioned it.** If the exact mechanism is named by a MEMBER who then approved, the scope concern was raised before approval, and a follow-up issue tracks the residual — "a human must look" is already satisfied and the abstain reads as over-caution.
- **Score honestly against the falsifiable reading** ("material enough not to merge as-is"). A clean merge at your exact decided head REFUTES a merge-blocker abstain — do NOT launder it as "correct because a human looked." Distinguish motivation-question blocks (clear via discussion, merge unchanged) from code-demand blocks (clear via commits). Separate the DECISION from the RATIONALE — a correct decision can carry a challenger-miss rationale, and they file under different categories.
- **A proven concern that never REACHED the PR before merge produced zero effect** — escalate proportionally to merge-imminence with a ready-to-paste counterexample; a correct abstain arriving after merge is indistinguishable from none.
- **Confirmed-safe shapes** (emit an existing IR decoration on one more backend, in a target-scoped override, tested both directions + downstream compiler, CI green on that leg) are low-risk approves. A staged strict policy silently over-abstains; a DO-NOT-MERGE repro PR is a CHALLENGER_CONCERN abstain.

## Live human blocks gate auto-approve

The single worst false-safe an approver can produce is auto-approving over a human who formally said "not as-is." On slang#12631 R2 the new commit fixed the exact bot gap and Devin was clean, but a maintainer's standing `CHANGES_REQUESTED` ("I'm curious what led to the need for this PR") was un-addressed — correct call ABSTAIN, and the mechanical rule is to fetch the review state and confirm dismissal via the TIMELINE `review_dismissed` event, since a push does not auto-dismiss ([A standing un-dismissed maintainer CHANGES_REQUESTED blocks WOULD_APPROVE](../learnings/1787250398767-approver-challenger-miss-a-standing-un-dismissed-m.md)). The explicit form generalizes to `COMMENTED` reviews: a maintainer can leave the state `COMMENTED` while posting "please remove X / add Y" comments at the current head with the author replying "will do" — that head is a known-superseded design, and the `synchronize` webhook that dispatched the decision may have fired with NO new commit, so check `commits|length` and timestamps ([live_late head carrying open+agreed maintainer change-requests is an ABSTAIN](../learnings/1787273882132-approver-challenger-live-late-head-carrying-open-a.md)). A live, unanswered maintainer verification request is equally decisive: on bot-authored #12642 (a silent-corruption fast-path predicate), a maintainer posted "not looking for a rubber stamp — a concrete counterexample would be most useful" and the shepherd hadn't reviewed — recording WOULD_APPROVE would assert a positive verdict over an in-progress human review ([Bot-authored optimization PRs can carry a live human verification request](../learnings/1787298638613-approver-challenger-miss-bot-authored-optimization.md)).

## When an abstain over a human concern is over-caution

The mirror-image error is abstaining when the owners have already dispositioned the concern. On slang#12304 the fix's architect (MEMBER) explicitly named the exact visibility concern, declared removing it the intended direction, and approved at the decided head; the scope concern was raised in-thread before approval and a follow-up issue (#12667) tracked the residual — so "a human must look" was already satisfied and the abstain added no signal ([concern already resolved on the PR thread ⇒ abstain reads as over-caution](../learnings/1787268099813-approver-human-disagreement-concern-already-resolv.md)). Reserve CHALLENGER_CONCERN abstains for concerns owners have NOT weighed (novel mechanism, claim-vs-code mismatch, unraised blast radius).

## Scoring an abstain against the merge outcome

Multiple joins sharpen the falsifiable reading. On #12631 the maintainer's motivation-question `CHANGES_REQUESTED` cleared with ZERO code change (approved the same head 25 min later, merged unchanged) — the transferable refinement is that a *motivation/necessity question* is a different class from a "this code is wrong" block and frequently clears via discussion, so frame the abstain as "deferring pending re-review" and expect approve-unchanged, not "the change is deficient" ([JOIN #12631: a "why is this needed?" block clears with zero code change](../learnings/1787253126764-approver-human-disagreement-join-12631-a-why-is-th.md)). A follow-up filing correction on that same PR is instructive: the R2 abstain (deferring to a live un-dismissed block) was CORRECT and NOT falsified by the same-head merge, so it must be re-categorized `[approver/calibration]` not `[approver/human-disagreement]` — because the CATEGORY drives Step-0 recall, a correct-decision signal filed under a disagreement tag pollutes the prior; score the DECISION and the RATIONALE separately (the challenger-miss — calling a question "unresolved" without reading `issues/N/comments` — stays the real error) ([#12631 R2 final classification — deferring to a live block was correct, the only error was a challenger-miss](../learnings/1787253771412-approver-calibration-12631-r2-final-classification.md)). A merge-consistency observation is bound to the merged head, not to the defect you decided on: citing #12106's clean merge as precedent failed because a LATER revision had DELETED the workload, so the merged tree was consistent for a different reason than "human tolerated the missing row" — before citing any prior PR's merge as waiver evidence, confirm the defect ACTUALLY EXISTED at the merged head ([a merge-consistency observation is bound to the merged head](../learnings/1787304440316-approver-challenger-miss-a-merge-consistency-obser.md)).

Two honest over-abstain scores: on #12679 (a documented generated-file hand-edit) the human merged as-is with an explicit APPROVE, so a documented pragmatic exception by a trusted MEMBER + clean bot review is MERGEABLE without forcing regenerate-from-source — reserve OPEN_GAP for an edit that's wrong or that regeneration would overwrite ([#12679 conservative/false ABSTAIN — human approved a documented hand-edit](../learnings/1787313720844-approver-human-disagreement-12679-conservative-fal.md)). And on #12569 the PR MERGED unchanged at the ABSTAIN head even though the concern (a silent transforming-forwarding miscompile) was empirically PROVEN true — two facts coexist: the abstain is refuted as a merge-blocker (over-abstain), but the bug shipped; the decisive nuance is that the counterexample NEVER REACHED the PR before merge, so a read-only approver holding a proven silent-miscompile must escalate proportionally to merge-imminence with a ready-to-paste counterexample rather than route a slow independent-repro handoff ([slang#12569 merged unchanged at my ABSTAIN head — a proven concern that never reached the PR](../learnings/1787558345957-approver-human-disagreement-slang-12569-merged-unc.md)).

## Confirmed shapes and policy/process traps

A confirmed HIT establishes a low-risk approve shape: a change that makes one more backend EMIT an already-existing IR decoration, in a target-specific emitter override whose base is an unoverridden no-op virtual, touching only emitter + test, shipping a directional test PLUS a downstream-compiler arm, with green CI on the affected target legs — for this shape the gate/flag probe does NOT apply (the emit is unconditional) and green CI is strong positive evidence ([Confirmed-safe shape: emit an existing IR decoration on one more C-like backend](../learnings/1787313711473-approver-human-agreement-confirmed-safe-shape-emit.md)). A sibling confirmed HIT is the **additive per-arm intrinsic-asm narrowing** shape (slang#12669, Fix #12634, 3-component CUDA/PTX texture samples — merged UNCHANGED at the decided head with 0 interval commits): the change adds `if (T is <type>) __intrinsic_asm "..."` arms and leaves the pre-existing default `__intrinsic_asm` line untouched, so output for every other input is byte-identical (verify the default line is literally unchanged in the diff); the match-table-with-default-fallthrough construct has in-file precedent (`textureStore` in the same file), a strong not-novel signal (grep the touched file for the idiom); the referenced prelude helper (`_slang_vector_reshape<Elem,3,Elem,4>`) exists at the pinned head with the spelled template-arg order; and the regression test is a GPU-free `SIMPLE(filecheck=)` with a positive (`CUDA: _slang_vector_reshape<...>`) AND negative (`CUDA-NOT: tex*<Elem3>`) trigger-present control plus scalar/2-/4-comp identity controls, so it fails if the fix doesn't fire. Same Devin-only tier (bot-authored `fix/issue-N` branch → no production `github-actions[bot]` review, harvest exit 20 correct) — a clean Devin plus these checks is sufficient for WOULD_APPROVE, and this is the calibration-affirming direction: don't tighten the bar for the class ([additive per-arm CUDA intrinsic narrowing is a safe WOULD_APPROVE shape](../learnings/1787707846329-approver-confirmed-hit-additive-per-arm-cuda-intri.md)). A descriptive help-string/generated-doc PR has exactly one failure mode — prose stating something FALSE about the code — so the decisive probe is a single source read confirming the prose matches the function at head; missing production review and bot authorship are expected, not abstain-worthy ([descriptive-help-string docs PR is safe when the documented behavior is verified at head](../learnings/1787371051821-approver-human-disagreement-confirmed-hit-descript.md)). Two process traps: a staged per-PR `policy/APPROVAL_POLICY.json` silently OVERRIDES the wide group mount (it's first in `eval-clauses.py` resolution after `--policy`), so a `head_provenance`/`tier_eligible` clause fail on a fork PR may be an artifact of the strict bundled `v0-shadow` default — always read `clauses.json.policy_version` before trusting a clause FAIL, since it fails safe and its symptom is indistinguishable from diligence ([staged per-PR policy overrides the wide mount → strict v0-shadow fires](../learnings/1787331171131-approver-clause-gap-staged-per-pr-policy-overrides.md)). And a "DO NOT MERGE" repro PR that disables the CI matrix is a CHALLENGER_CONCERN → ABSTAIN (merging it is a master CI-integrity regression the author forbids) — NOT WOULD_APPROVE, NOT BLOCK (the YAML is correct for its purpose), NOT an infra abstain (the pipeline ran); CodeRabbit auto-skips such titles (`collect-reviews.sh` exit 20 is EXPECTED, not an infra gap) ([DO-NOT-MERGE repro PR that disables CI is a CHALLENGER_CONCERN abstain](../learnings/1787310301140-approver-challenger-miss-do-not-merge-repro-pr-tha.md)).
