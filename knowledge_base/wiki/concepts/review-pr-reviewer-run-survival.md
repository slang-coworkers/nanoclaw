# Reviewer-Run Survival & Review-Tool Operational Infra

Keeping the reviewer and Devin runs alive long enough to produce a trustworthy artifact, invoking the tools so they don't false-skip, posting the result correctly, and clearing the critique gate. Every reviewer fails toward CLEAN — an absent reviewer and a clean reviewer are byte-identical downstream — so this page is about *proving a run happened* before you trust its silence. The decision framework is on [approver decision & shadow-mode](review-pr-approver-decision-and-shadow-mode.md); reading the harvested review signal is on [harvest tiers & verdict reporting](review-pr-harvest-tiers-and-verdict-reporting.md).

## TL;DR
- **Every reviewer fails toward CLEAN.** Verify each reviewer actually produced findings before treating "no findings" as a result; watch the artifact / exit marker, not the subagent return.
- **`run_in_background` reviewer runs are killed at session teardown**, arriving as `status: stopped` with a possibly-deleted run_dir — indistinguishable from "0 findings." Always verify the run survived AND cleared its permission guard before trusting output.
- **Reviewer A has a 600 s background-wait ceiling** in the inner `claude --print` CLI that kills the six subagents before `final-review.md` is written (`REVIEW-GUARD FAIL: final review is <500 bytes`). That's an infra timeout, not a 0-findings result — recover the analysis from `stream.jsonl`.
- **A first-attempt Devin timeout (exit 3) is "not done yet," not unavailability** — retry once (clear the chrome profile, delete stale `devin-error.txt`, widen `--max-minutes`) before recording NO_REVIEW_SIGNAL / ABSTAIN_INFRA. Only abstain when Devin is the SOLE signal.
- **Never wrap `devin-fetch.sh` in an outer `timeout` shorter than its own `--max-minutes`** — exit 124/137 manufactures a false NO_REVIEW_SIGNAL. Invoke it via `bash devin-fetch.sh` (it ships without its exec bit → exit 126 false-skip).
- **Cross-check Devin's raw `devin-page.txt` tally before synthesizing** — `devin-fetch.sh` can drop the "N Flag" block from `devin-flags.md`; a `devin-commit-status.txt` of "unknown" means "not fully settled," not ABSTAIN.
- **Never pre-fill `reviewers_complete:true` before Devin reaches a terminal state** — it's a harness-integrity assertion the critique gate checks against the artifact on disk.
- **The critique gate only records a round for the exact `/codex-critique` format; DECISION_REVIEW and OUTPUT_REVIEW must be separate calls;** read-only `gh api .../pulls` GETs false-positive the delivery gate — use `gh pr view --json` / `gh graphql` instead.
- **A fast maintainer self-merge is normal.** Do NOT escalate on the 1st silent reping (operator ruling).

## Reviewer-run survival: teardown and the 600 s ceiling

`compose-and-run.sh` / `run-clarity.sh` launched with `run_in_background` are killed at session teardown, arriving as `status: stopped` with a possibly-deleted run_dir — indistinguishable from a "0 findings" verdict; always verify the run survived AND cleared its permission guard before trusting output ([verify reviewer runs survived + cleared the guard before trusting output](../learnings/1783971373048-slang-pr-review-verify-reviewer-runs-survived-clea.md)). Reviewer A additionally has a **600 s background-wait ceiling** in the inner `claude --print` CLI that kills the six subagents before `final-review.md` is written (`REVIEW-GUARD FAIL: final review is <500 bytes`) — this is an infra timeout, not a 0-findings result; recover the analysis from `stream.jsonl` rather than reporting empty ([Reviewer A 600s bg-wait ceiling truncates final-review.md — recover from stream.jsonl](../learnings/1783983883017-slang-pr-review-reviewer-a-600s-bg-wait-ceiling-tr.md)).

Two concrete refinements sharpen this. On a large diff (slang#12782, 43 files / 5009-line) the near-empty `final-review.md` (332 bytes, exit 1, log line `Background tasks still running after 600s; terminating`) made `summarize.py` read 0 bugs / 0 gaps / 0 questions — an artifact of the empty file, NOT a clean review; the six specialist subagents DID run (~$20) and found real bugs (the true verdict was REQUEST_CHANGES), so never report 0/0/0 as "clean" in this state. Recover the findings from the run's `stream.jsonl`, whose `task_notification` records carry each subagent's full review verbatim in the `summary` field, and to avoid the timeout on big diffs set `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` (wait indefinitely) before the compose-and-run invocation, per the runner's own log hint ([empty final-review.md on a large diff is a 600s bg-wait timeout — recover subagents from stream.jsonl](../learnings/1789468288728-reviewer-a-empty-final-review-md-on-large-diffs-60.md)). A second, distinct failure mode: a subagent that dies mid-run ("Agent terminated early due to an API error", 0 tools/0 tokens) can make the orchestrator END WITHOUT the synthesis, leaving `final-review.md` a ~1KB TRUNCATED intermediate turn (e.g. "Waiting for the final reviewer (code-quality)") while the summarizer still reports `Run state: success` / 0/0/0 and an artifact-presence monitor reports DONE — both misleading. DETECTION: compare `final-review.md` size to a normal run (~8-12KB); a ~1KB file is truncated. RECOVERY (no re-run needed if ≥5/6 lenses completed): the completed subagents' full reviews live in `<run_dir>/stream.jsonl` as `{"subtype":"task_notification"}` records (`len(summary)>200`), while a dead subagent's record has `status:"stopped"` and a ~400-char envelope-only summary; the `subagents/` dir is usually empty (outputs cleared before preservation), so stream.jsonl is the source of truth. The recovered reports are unfiltered (no dedup/severity pass) — set `reviewers_complete=false`, disclose the truncation, and flag the missing lens ([final-review.md can be a truncated stub — verify size, recover lenses from stream.jsonl task_notifications](../learnings/1789483811315-reviewer-a-final-review-md-can-be-a-truncated-stub.md)).

The approver and the reviewer runs it consumes are session-teardown-fragile — a synchronize burst can cost whole review rounds (R3 of slang#12023 died with no doc), and a PR can merge undecided while the reviewer doc never returns; verify the run survived before trusting output ([reviewer runs are session-teardown-fragile — a synchronize burst can cost whole review rounds](../learnings/1783969636640-approver-reviewer-runs-are-session-teardown-fragil.md), [PR merged undecided while reviewer doc never returned (slang#12060)](../learnings/1783964822172-approver-infra-abstain-pr-merged-undecided-while-r.md)).

**Operator ruling (contradiction).** The slang#12060 learning above (PR merged undecided while the reviewer doc never returned) originally recommended escalating on the 1st silent reping. The operator **overruled** this (2026-07-13): it would fire on every fast maintainer self-merge, a normal healthy pattern — the reviewer-doc-never-returned failure is real, but the fix is NOT reping-escalation ([operator ruling: do NOT escalate on 1st silent reping (fast self-merge is acceptable)](../learnings/1783965620899-approver-clause-gap-operator-ruling-do-not-escalat.md)).

## Devin infra: retries, exec bits, drops, stalls, and cached snapshots

Devin failures on the sole-signal Devin-only tier are dominated by transient conditions a single retry recovers, so **retry once (clear the chrome profile, delete stale `devin-error.txt`, widen `--max-minutes`) before recording NO_REVIEW_SIGNAL / ABSTAIN_INFRA** — a first-attempt exit-3 timeout is usually "not done yet," not a real failure ([devin-fetch.sh timeout (exit 3) on fresh PRs — retry once](../learnings/1784019236976-approver-infra-abstain-devin-fetch-sh-timeout-exit.md), [Devin timeout on the sole-signal Devin-only tier: retry once](../learnings/1784074357103-approver-infra-abstain-devin-timeout-on-the-sole-s.md), [Devin-only tier: retry a timed-out Devin before ABSTAIN_INFRA](../learnings/1783993723797-approver-infra-abstain-devin-only-tier-retry-a-tim.md), [Devin timeout (exit 3) on a just-opened PR: re-poll once — the head-started session often completes clean](../learnings/1783961759956-approver-infra-abstain-devin-timeout-exit-3-on-a-j.md)). Checkpoint the pinned commit + clause/challenger state to `tmp/STATE.md` early, so a mid-run container restart can resume the session without re-deriving.

`devin-fetch.sh` ships without its exec bit in approver containers, so a by-path call dies exit 126 (a false Devin-skip) — always invoke via `bash devin-fetch.sh` ([devin-fetch.sh missing exec bit false-skips Devin](../learnings/1783997801258-approver-devin-fetch-sh-missing-exec-bit-false-ski.md), [devin-fetch.sh needs bash prefix + tolerate first-run timeout](../learnings/1783949034225-approver-infra-devin-fetch-sh-needs-bash-prefix-to.md)) — and never wrap it in an outer `timeout` shorter than its own `--max-minutes` deadline (exit 124/137 is not one of the script's own 0/2/3/4 codes and manufactures a false ABSTAIN_INFRA:NO_REVIEW_SIGNAL that burns the infra gate) ([outer timeout wrapper on devin-fetch.sh causes false NO_REVIEW_SIGNAL — let --max-minutes govern](../learnings/1783796304562-approver-infra-abstain-outer-timeout-wrapper-on-de.md), [devin-fetch.sh: never wrap in an outer timeout shorter than its --max-minutes](../learnings/1783934997171-approver-infra-abstain-devin-fetch-sh-never-wrap-i.md)). Ops: invoke approver scripts via `python3`/`bash` and use `gh graphql` (not `gh api pulls`, which the critique gate denies) for read-only fetches ([invoke approver scripts via python3/bash; use gh graphql (not gh api pulls) for read-only fetches](../learnings/1783960724921-approver-ops-invoke-approver-scripts-via-python3-b.md)).

A Devin **stall at the URL-rewrite handoff is non-blocking when the primary bot-review tier is already secured** — start Devin in the background early to overlap the harvest wait, cap its wait ~3 min after the primary lands, note `devin: skipped_stall`, and only escalate to ABSTAIN_INFRA when Devin is the SOLE signal ([Devin devin-fetch.sh stall at URL-rewrite is non-blocking when the primary tier is secured](../learnings/1784042688985-approver-infra-abstain-devin-devin-fetch-sh-stall-.md)). Two silent-data traps invalidate a Devin "clean" read: `devin-fetch.sh` can drop the "N Flag" block from `devin-flags.md` while the raw `devin-page.txt` shows `≥1 Flag` — always cross-check the raw page's tally (`grep -nE '[0-9]+ Bug|[0-9]+ Flag'`) before synthesizing, and treat "Loading diffs…"/commit-status `unknown` as "not fully settled" ([devin-fetch.sh drops the 'N Flag' block — cross-check raw devin-page.txt](../learnings/1784017360003-approver-infra-abstain-devin-fetch-sh-drops-the-n-.md)); and a `devin-commit-status.txt` reading `"unknown"` (not "up to date") on a `synchronize` signals a CACHED prior-revision analysis — do NOT abstain and do NOT trust it blindly; verify each flagged finding directly against the pinned head's `compare` delta, since a byte-for-byte-verified finding stands regardless of Devin's cache state ([Devin commit-status 'unknown' ≠ ABSTAIN — verify the flagged finding on the pinned head](../learnings/1784016854486-approver-infra-abstain-devin-commit-status-unknown.md)). For a companion clang-format PR whose base is the feature branch, a maintainer force-push of that base makes Devin's commit-scoped review miss the parent PR's full merge-delta — compare Devin's file count to the live `base...head` scope; a scope mismatch is ABSTAIN_INFRA (STALE_STAGE), and the substantive change lives in the parent PR ([companion clang-format PR — base force-pushed underneath ⇒ Devin misses merge-delta](../learnings/1784021932868-approver-infra-abstain-companion-clang-format-pr-b.md)).

## Runner operational notes: post-back, disclaimer, cited-file verification

`post-review.sh` POSTs the review body verbatim (event=COMMENT) and does NOT append the required bot-transparency disclaimer, and neither does the reviewer's `final-review.md`, so a freshly posted bot review is missing it ([post-review.sh posts body verbatim — no bot-transparency disclaimer](../learnings/1783665412901-post-review-sh-posts-body-verbatim-no-bot-transpar.md)). Editing the body afterward via REST `PUT /pulls/N/reviews/{id}` returns 404 under the App token; use the GraphQL `updatePullRequestReview` mutation (state stays COMMENTED), or better, append the disclaimer to `final-review.md` before posting ([REST review-body edit 404s under App token; use GraphQL updatePullRequestReview](../learnings/1783669185294-slang-pr-review-rest-review-body-edit-404s-under-a.md)). Copy `final-review.md`/`clarity-review.md`/`tool-uses.jsonl` into your own `/workspace/agent/review-<pr>/` dir immediately — the runner `transcripts/` dir is shared across concurrent sessions and gets clobbered fast; agent-browser (Reviewer B) reliably cannot launch Chrome here (dbus/DevToolsActivePort), a deterministic skip, not a retry-worthy transient. Reviewer A can also hallucinate/import test files not in the PR and build a whole gap around them: at merge time run `gh api .../pulls/<N>/files` and drop any file-specific finding A cites that isn't in the authoritative list, but preserve its true kernel (e.g. "ships with no regression test" on a 0-test PR) ([verify Reviewer A's cited files against the authoritative PR file list](../learnings/1783681518930-verify-reviewer-a-s-cited-files-against-the-author.md)).

A separate concurrency hazard on the SAME shared checkout: `compose-and-run.sh` (Reviewer A) defaults `REPO_ROOT=/workspace/agent/slang` and its end-of-run diff-integrity guard reads/writes `$REPO_ROOT/tmp/pr-diff.patch` + `tmp/context.json`. When a second review run launches against the same container's shared checkout mid-flight, the two race on those `tmp/` files — the later run's `gh pr diff > tmp/pr-diff.patch` clobbers the first's, so the first run's guard re-reads the wrong PR's files and trips `INTEGRITY-FAIL` (exit 1) listing a completely different PR, even though `final-review.md` is verifiably 100% about the correct PR. It is usually a **false positive** (the model got the right diff via its own live `gh pr diff <N>` early) but must NOT be hand-waved — a genuine wrong-diff review looks identical from the exit code alone. Discriminate: `grep -ic '<correct-topic>' final-review.md` vs `'<wrong-topic>'` (clean = all-correct, zero-wrong), `grep -il '<wrong-topic>' <run_dir>/subagents/*` (clean = no hits), and confirm a concurrent run dir (`ls -dt <skill>/transcripts/pr-*` still growing with no `final-review.md`) + the `tmp/pr-diff.patch` mtime falling inside your run window. **Fix = re-run in an isolated git worktree** (as Reviewer C already does): `git -C /workspace/agent/slang worktree add --detach /workspace/agent/wt-<pr>-reviewA origin/master` then `REPO_ROOT=/workspace/agent/wt-<pr>-reviewA bash <skill>/scripts/compose-and-run.sh --mode pr --pr <N> --repo <owner/repo>` — the worktree gives the run its own `tmp/` (a worktree of `origin/master` carries REVIEW.md + `.claude/agents/` so the run is unchanged); name it `wt-<pr>-<tag>` so supervise-issues GC reaps it. The durable fix (proposed) is for `compose-and-run.sh` to isolate per-run by default ([concurrent runs race on shared REPO_ROOT tmp/pr-diff.patch → false INTEGRITY-FAIL; isolate in a worktree](../learnings/1789053876664-slang-pr-review-runner-concurrent-runs-race-on-sha.md)). Confirm false-vs-real without stalling: the run's own `pr-diff.reference` (captured via `gh pr diff` at dispatch) is authoritative — its sha256 should equal `final-review.md`'s footer `diff sha256` and Reviewer C's run-dir-name hash; all three matching means every reviewer saw the correct diff, and the orchestrating CLI further self-heals by isolating the correct diff into `tmp/iso-<pr>-review/pr-diff.patch` and re-running the affected subagents, so the final review stays grounded even though the post-run net still re-inspects the clobbered *shared* `tmp/pr-diff.patch` (and `context.json`'s `pr`/`head_sha`/`diff_sha256` are likewise polluted — use the verified `pr-diff.reference` sha as `diff_hash`, keep `reviewers_complete:true`, and disclose the race) ([INTEGRITY-FAIL confirmation recipe + tmp/iso-<pr>/ self-heal](../learnings/1789506920553-slang-pr-review-runner-integrity-fail-can-be-a-fal.md)). A sibling guard, **REVIEW-GUARD FAIL** (`final review looks like an infrastructure error, not a review`), false-trips the same way when the review's own text contains infra-error *wording* — e.g. a coverage note "the cross-backend and clarity passes terminated on transient API errors", or findings that legitimately discuss `exit(-1)`/`SLANG_UNEXPECTED`/crash. The discriminator is identical: read `final-review.md` — a full Verdict + Findings + inline-comments review is a false trip (use it), a <500-byte stub with no verdict is a real failure (recover subagents from `stream.jsonl`) ([REVIEW-GUARD FAIL false-trips on infra-error wording inside a valid review](../learnings/1789512038521-slang-pr-review-runner-review-guard-fail-can-false.md)). When two A-sessions collide this way, confirm the review is valid via four checks — `final-review.md` footer `<sha>` == `gh pr view --json headRefOid`, that footer's `diff sha256` == `sha256sum <run_dir>/pr-diff.reference`, findings cite the requested PR's files, and `summarize.py` shows drift==0 — then set `reviewers_complete:true` but document the rc=1 override with this evidence; do **not** delete a concurrent run's `tmp/pr-diff.patch` to clear your own guard (it may be in active use), and pre-warming `git fetch origin master` before dispatch only shrinks the A/C git-lock race, not the scratch-file collision ([concurrent A-sessions collide on tmp/pr-diff.patch → false integrity guard; confirm via four checks, don't delete the other's file](../learnings/1789518412257-concurrent-slang-pr-review-runner-sessions-collide.md)).

**Finding your run dir and recovering mis-captured output.** Identify YOUR run dir from the background job's own `>>> output → <RUN_DIR>` line (grep the bg log for `output → \S+`), not `ls -dt` — a stale run with a leftover `final-review.md` misleads the latter; the clarity run-dir name embeds the reviewed head SHA (`pr-pr<N>-<headsha>-<bundlehash>-…`) so it self-disambiguates, whereas Reviewer A's `pr-<ts>` does not (sanity-check a token unique to the head under review inside `<dir>/pr-diff.reference`) ([identify a run dir from the bg log's "output →" line, not ls -dt](../learnings/1789507730747-slang-pr-review-runner-identify-a-run-dir-from-the.md)). Reviewer C can silently mis-capture its artifact: `clarity-review.md` comes out tiny (<2KB, no `### `/`## Kept`/`## Review Body` headers, rc=0) because the model wrote the real review to a `tmp/` path or a trailing meta-message got captured instead — recover the canonical body from the run's `stream.jsonl` (the largest assistant text turn containing `## Review Body`/`## Kept`, or the content of the `Write` tool_use targeting the candidates file) and note the provenance so the fixer knows it is genuine C output ([clarity-runner can lose its output to a tmp/ file — recover the Write tool_use from stream.jsonl](../learnings/1789573892015-clarity-runner-reviewer-c-can-lose-its-output-to-a.md), [clarity-review.md can capture a trailing meta-message — recover the real body from stream.jsonl](../learnings/1789517911038-slang-clarity-review-runner-can-capture-a-trailing.md)); the naive drift grep `grep -cE '(POST|PUT|PATCH|DELETE)'` over `tool-uses.jsonl` likewise false-positives on Agent-dispatch prompt text containing "PATCH" — scope it to command/name fields (`gh api|--method (POST|PUT|…)|post-github|pulls/[0-9]+/reviews`). **Reviewing slang-rhi PRs:** keep `REPO_ROOT=/workspace/agent/slang` (it owns REVIEW.md + the 6-subagent pipeline + clarity skills) and pass `--repo shader-slang/slang-rhi --pr <N>`; the slang checkout vendors slang-rhi at `external/slang-rhi/`, so the subagents get REAL source context (not diff-only) to independently confirm a fix — the pinned submodule may lag PR head, so verify exact hunks against `gh pr diff` ([reviews slang-rhi PRs with real source via vendored external/slang-rhi](../learnings/1789438594576-slang-pr-review-runner-reviews-slang-rhi-prs-with-.md)).

## Critique-gate hygiene

The gate only records a round when the codex call uses the exact `/codex-critique` format — freeform codex calls don't count toward delivery ([critique gate only records a round when the codex call uses the exact /codex-critique format](../learnings/1783939165247-approver-critique-mustfix-critique-gate-only-recor.md)) — and DECISION_REVIEW / OUTPUT_REVIEW must be *separate* calls (the tracker keys each round to the first stage token; use `reason_code=CLEAN` for WOULD_APPROVE) ([OUTPUT_REVIEW must be its own codex call; reason_code=CLEAN for WOULD_APPROVE](../learnings/1783978376082-approver-critique-mustfix-output-review-must-be-it.md)). Per-revision `[Approval Decision]` delivery to the dashboard is mandatory and distinct from the materiality-gated upstream `[Report]` ([per-revision [Approval Decision] delivery is mandatory (dashboard)](../learnings/1783958368120-approver-critique-mustfix-per-revision-approval-de.md)).

`/app/hooks/gate-critique-on-deliver.sh` matches `gh api [^|]*pulls\b`, intended for PR *creation* but firing on ANY `gh api` command containing `pulls` including read-only GETs of reviews/comments; the denial actually triggers only when this coincides with an unmet critique requirement (`edits_since_critique>0` or stale OUTPUT_REVIEW), and at 3 denials the gate escalates to admin + hard-blocks. Avoid: on a revision turn, answer "did the review materially change" from local artifacts (R2 vs R1 review-doc.md) rather than re-fetching; if you must read PR data, use `gh pr view <n> --json ...` (matches nothing) instead of `gh api .../pulls/...`; never write a file in the same command as a read (bumps `edits_since_critique`) ([critique gate false-positives on read-only gh api .../pulls GETs — don't burn denial strikes](../learnings/1783913716215-approver-critique-mustfix-critique-gate-false-posi.md)). Never optimistically pre-fill `reviewers_complete:true` before Devin reaches a terminal state — it is a harness-integrity assertion the critique gate checks against the artifact on disk, true only when `devin-flags.md` exists or a bot review was harvested ([never set reviewers_complete:true before Devin reaches a terminal state](../learnings/1784049951184-approver-critique-mustfix-never-set-reviewers-comp.md)).

**Invoke the `/slang-pr-review` and clarity-review runner scripts from the WRITABLE skill copy at `/home/node/.claude/skills/<runner>/scripts/`, NOT `/app/skills/...`.** `/app/skills` is a read-only filesystem; `compose-and-run.sh` and `run-clarity.sh` both `mkdir -p "$SKILL_DIR/transcripts/..."` where `$SKILL_DIR` resolves to the script's own directory, so launched from `/app/skills` they die instantly with `mkdir: cannot create directory … Read-only file system` and exit 1 within seconds — which looks deceptively like a fast "exit 0" background completion (always check the log tail). The `/home/node/.claude/skills/*` copies are separate writable directories (not symlinks to /app). Also: despite `gh auth status` reporting "The token in GH_TOKEN is invalid", `gh pr view/diff` on a PUBLIC repo still works read-only — enough for Reviewer A's `gh pr diff` and clarity's `gh pr view` (writes would fail, but chat-triggered reviews don't post). Resolve run_dir with `ls -dt <skill>/transcripts/*/ | head -1`. ([slang-pr-review runner scripts must run from /home/node/.claude/skills (not /app/skills — read-only)](../learnings/1789621947264-slang-pr-review-runner-scripts-must-run-from-home-.md))
