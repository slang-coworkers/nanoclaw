# Slang Test Harness — FileCheck Mechanics and Output-Path Traps

> **Part 3 of 3** of the Slang Test Harness synthesis (split 2026-08-08 to stay under the 40 KB read cap). Siblings: [part 1](slang-misc-test-harness.md) · [part 2](slang-misc-test-harness-2.md).

This part covers **FileCheck itself**: where slang-test gets it, how to prove it actually ran, the `CHECK-NOT` region and vacuity traps, the `-o`/`result code` and `-g2` `OpString` self-match traps, and the harness defaults (`-O0` front-insertion, pre-opt SPIR-V validation) that make a fold-dependent assertion unmatchable. Directive authoring is in [part 1](slang-misc-test-harness.md); running the harness is in [part 2](slang-misc-test-harness-2.md).

## TL;DR

- **`slang-test` never invokes a `FileCheck` binary from `PATH`.** It loads FileCheck in-process from the `slang-llvm` shared library (`test-context.cpp:95-113` → `loadSharedLibrary("slang-llvm")` → `createLLVMFileCheck_V1`, gated at `slang-test-main.cpp:5915` on `hasLlvm`). A `pip`/`apt` FileCheck on `PATH` cannot influence it either way.
- **The library lives at `build/Debug/lib/libslang-llvm.so`, not in `bin/`** — probe with `find build -iname '*slang-llvm*'`, never `ls build/Debug/bin/` or `which FileCheck`, and name the scope you actually searched.
- **When the library genuinely is missing, `filecheck=` tests report `Ignored` (0/0) or pass vacuously** — a whole suite goes green while asserting nothing, so counting `passed` proves nothing.
- **The only control that discriminates evaluated-and-passed from silently-skipped: inject a deliberately broken CHECK pattern, require RED, then restore.** Verify the control itself landed — controls that were themselves vacuous have been observed.
- **If you land on a build without the library, copy a prebuilt `libslang-llvm.so` into your worktree's `build/Debug/lib/`** — FileCheck V1 is target-independent, so version drift is fine.
- **A Python FileCheck emulator is a different implementation from LLVM's.** Validate it bidirectionally, derive options from each file's own `//TEST:` directive, and report results as "passes under an emulator; LLVM FileCheck in CI is authoritative" — never as "regression suite green."
- **Without FileCheck, verify CHECK lines with an ORDERED matcher** (each CHECK matches at or after the previous match's end). Global count-the-matches approximations cannot express ordered `CHECK` / windowed `CHECK-NOT` semantics and report spurious failures.
- **A `CHECK-NOT` only scans the region between its adjacent positive CHECKs.** The only reliable whole-output negative is a lone `-NOT` under its own `filecheck=` prefix with no positive directives to bound it; moving a bounded negative to the top does not fix it.
- **Even a correctly-scoped `CHECK-NOT` is vacuous if DCE removed its subject.** Grep the real output for the forbidden instruction with the decoration stripped — zero hits means the negative asserts nothing. Fence every negative with a positive.
- **Prove a negative is live by flipping it to a pattern you know is present, confirming RED, then restoring** — and `diff` that the edit actually landed.
- **Never write a dump-based FileCheck test to `-o /dev/null`.** It is Windows-invalid (`error[E00004]`, exit 255) yet `-dump-ir` already printed the matched text, so the test stays GREEN. Use `-o -` plus a status assertion.
- **`-o -` and dropping `-o` are not equivalent — with `-g`, dropping `-o` flips the driver into `-whole-program` mode**, silently changing what is compiled. Prefer `-o -`.
- **Write `result code = {{0}}`, not `result code = 0`.** Under `-g` the IR dump embeds the whole source, so the literal matches its own comment echoed back and passes even when the real exit was 255. `{{N}}` is evaluated as a regex; `{N}` is the inert spelling.
- **At `-g2` Slang embeds the entire source — comments included — as an `OpString`, so FileCheck matches your own `//CHECK` lines.** Drop `-g2` if unneeded (`OpName` is emitted regardless), or anchor with `{{^}}`.
- **Never count with a bare `grep -c '<Op>'`** — it counts your own comment lines echoed in the `OpString`. Use `grep -cE 'OpExtInst.*<Op>'`.
- **Reproduce the Windows `-o /dev/null` failure on Linux with `-dump-ir -o /nonexistent-dir/out.spv`** — same `E00004`, exit 255, IR still dumped, test still green. That is the negative control for any `result code` assertion.
- **Diff emit/lowering changes against FileCheck goldens whenever you have not PROVED FileCheck ran.** Uniform failure across all arches = deterministic real regression; one platform only = golden drift or flake. A decoration arm shared by multiple decl kinds is the classic over-broad trap.
- **A suite-wide opt-level override plumbs through `context->options` and both `addDefault*` helpers**; the `-O0` default lives in `slang-test-optimization-options.h` and is front-inserted deliberately. `-O0` is the sole spirv-opt early-out.
- **`SLANG_RUN_SPIRV_VALIDATION=1` validates PRE-optimization SPIR-V**, so an optimizer-introduced defect passes validation — pin it with a `-target spirv-asm` operand-count assertion anchored by `{{$}}`.
- **The SPIR-V `OpSource` SourceLanguage token is env-dependent** (`Slang` by default, `Unknown` where aarch64 CI exports `SLANG_USE_SPV_SOURCE_LANGUAGE_UNKNOWN=1`) — match `OpSource {{Slang|Unknown}} 1` and reproduce by setting the env var yourself.
- **A `-target spirv` SIMPLE test with no `[shader("compute")]`/`-entry`/`-stage` compiles a module with NO entry point** and silently exercises only the fallback path.
- **A fixture whose correctness depends on an exact byte offset needs `text eol=lf` in `.gitattributes`**, or Windows CI checks it out as CRLF and every `\n`→`\r\n` shifts the target byte. Prefer content-anchored matches.
- **Attempt a crafted minimal reproducer before concluding a sanitizer witness is un-addable** — a maintainer often lands the very test you called impossible.
- **Ask of every new test: what would have to break for this to stay green?** If the answer includes "the compile fails," the test needs a status assertion.

## Real FileCheck via libslang-llvm.so, Ordered-Match Fallback, and slang-test's -O0 / Pre-Opt Validation Defaults (2026-07-23 fold)

### Where FileCheck comes from, and how to tell whether it actually ran (2026-08-04 correction)

**Read this before assuming your `filecheck=` tests are skipping.** The mechanism, read from source: `slang-test` **never** invokes a `FileCheck` executable from `PATH`. It loads FileCheck in-process from the `slang-llvm` shared library — `TestContext::locateLLVMFileCheck()` at `tools/slang-test/test-context.cpp:95-113` calls `loader->loadSharedLibrary("slang-llvm", …)` then `findFuncByName("createLLVMFileCheck_V1")`, invoked from `slang-test-main.cpp:5917` and **gated at `:5915` on `if (hasLlvm)`** (`checkPassThroughSupport(SLANG_PASS_THROUGH_LLVM)`). Consequence: a `pip install filecheck` emulator on `~/.local/bin`, an `apt`-installed LLVM `FileCheck`, or anything else on `PATH` **cannot influence slang-test at all** — the library is the dependency ([slang-test `filecheck=` tests need the slang-llvm library, not a FileCheck binary on PATH](../learnings/1785824518254-slang-test-filecheck-tests-need-the-slang-llvm-lib.md)).

**⛔ The corrected empirical answer: LLVM FileCheck DOES run locally in the standard container build.** An earlier version of this note claimed the library was absent and therefore `filecheck=` tests skip locally. That is **false and retracted.** The claim came from `ls build/Debug/bin/ | grep slang-llvm` returning nothing — but the library lives in **`build/Debug/lib/libslang-llvm.so`** (152 MB), and `DefaultSharedLibraryLoader` searches library paths, so an empty `bin/` establishes nothing. One command settles it: `find build -iname '*slang-llvm*'`. Searching a single directory and reporting a tree-wide negative is the defect; **name the scope you actually searched.** Settled the right way — with a failable control rather than a "passed" line, since a skipped test and a passing test are the same colour in the summary:

```
# 1. baseline
./build/Debug/bin/slang-test tests/language-feature/function-calls/forceinline-basic-block.slang
  → "Supported backends: … llvm …" ; "passed test:" ; 100% (1/1)
# 2. CONTROL — inject a deliberately broken CHECK pattern into the same file
  → "FAILED test:" ; 0% of tests passed (0/1)
# 3. restore → passes again
```

The broken assertion fails, so the checker is genuinely evaluating ⇒ a green run over `filecheck=` files in this environment is real evidence, not a skip. ⚠️ `slang-test`'s **process exit code was 0 even on the FAILED test** — parse the `FAILED test:` / `% of tests passed` lines, never `$?`. Two standing rules this reinforces: a "passed" line alone never proves the checker ran (only a deliberately-broken control discriminates *evaluated-and-passed* from *silently-skipped*), and **false capability-negatives are the worst class to leave in shared prose** — others act on them by *not trying*, so the error never appears in anyone's transcript. Note also that the earlier note contradicted an already-correct 2026-07-02 learning saying local `filecheck=` tests do run; **contradicting an existing note is a signal to re-verify, not to overwrite.** The prior note's discovery path (a bundled DXC-tree FileCheck at `build/_deps/dxc_source-src/utils/FileCheck`) differs from the in-process `slang-llvm` path traced above, and both may resolve depending on build config — **don't infer availability from either path; run the control** ([CORRECTION — the "slang-llvm absent / filecheck= tests skip" claim was FALSE; LLVM FileCheck runs locally, proved with a failable control](../learnings/1785824734935-correction-slang-llvm-filecheck-my-library-absent-.md)).

If you ever do end up on a build where the library is genuinely missing (probe, don't assume), a `pip install filecheck` emulator is a reasonable **parallel** harness for local iteration, but it is a third-party Python re-implementation — a *different* implementation from LLVM's, which is what CI runs via `slang-llvm`. Validate it bidirectionally first (satisfiable input → exit 0; the actual defect reintroduced → exit 1, including the specific anchors your assertions rely on such as `{{$}}` rejecting an extra operand); derive compile options from each file's own `//TEST:` directive so the harness can't drift from the test; distrust global "count the matches" approximations, which cannot express FileCheck's *ordered* `CHECK` / windowed `CHECK-NOT` semantics and report spurious failures on a file that legitimately has the same pattern twice (tempting to then "fix" a correct assertion); and report results as "passes under a FileCheck-compatible emulator; **LLVM FileCheck in CI is authoritative**", never as "regression suite green."

Three further traps for anyone writing `//TEST:SIMPLE(filecheck=...)` tests. When the local build genuinely lacks the `slang-llvm` library, slang-test reports the test **"ignored"** (0/0) or PASSES VACUOUSLY — counting `passed` proves nothing; a Python FileCheck simulator that passed for #12170 later FAILED under real FileCheck (backreference/scan semantics differ). Make slang-test actually run it by copying a prebuilt `libslang-llvm.so` from the shared base clone into your worktree's `build/Debug/lib/` (FileCheck V1 is target-independent, so version drift is fine) ([run filecheck .slang tests through real slang-test (copy libslang-llvm.so), never a simulator](../learnings/1784743223082-run-filecheck-slang-tests-through-real-slang-test-.md)). If you genuinely cannot get FileCheck, verify the CHECK lines yourself with an **ordered matcher** (FileCheck semantics: each CHECK matches at/after the previous match's end; translate `{{...}}` to regex, `re.escape` the literal spans) — this caught a real coverage gap where a test exercised all texture shapes but only ASSERTED on the 1D arm, and it enforces the top-of-output-pragma-first ordering and positive+negative capability-boundary pins ([verify FileCheck CHECK directives by ordered-matching emitted output when FileCheck is absent locally](../learnings/1784751927211-verify-filecheck-check-directives-by-ordered-match.md)).

Two harness defaults bite SPIR-V-opt regression pins: slang-test **prepends `-O0`** to any directive without an explicit `-OX`, so a fold-dependent CHECK can never match unless you add `-O1` (a bare manual `slangc` uses the *compiler's* optimizing default and misleads you); and `SLANG_RUN_SPIRV_VALIDATION=1` validates the **pre-optimization** SPIR-V, so an optimizer-introduced defect passes validation — the real signal is a `-target spirv-asm` (post-opt) FileCheck operand-count assertion, pinned with a `{{$}}` end-of-line anchor to distinguish correct-3 from buggy-4 ([slang-test injects -O0 by default; SPIRV validation runs pre-opt](../learnings/1784762873836-slang-test-injects-o0-by-default-spirv-validation-.md)).

Four more authoring traps specific to SPIR-V debug/FileCheck tests, all seen on PR #12202/#12204/#12206. **(1) A `-target spirv` SIMPLE test with a bare `[numthreads(1,1,1)] void computeMain(...)` and NO `[shader("compute")]`/`-entry`/`-stage` compiles a module with NO entry point** — entry-point auto-deduction keys on the `[shader(...)]` attribute — so any feature keyed on entry-point context (e.g. the emitter's `m_defaultDebugSource` primary debug-source path) silently exercises only the module-scan fallback and a regression in the primary path goes green; add `[shader("compute")]` (template: `tests/spirv/debug-info-line-function.slang`), and add a `#include` multi-source test for any "pick the main/non-included source" branch ([SPIR-V debug tests need [shader("compute")]/-entry or they silently test the fallback path](../learnings/1784822694362-slang-spir-v-debug-tests-need-shader-compute-entry.md)). **(2) The `OpSource` SourceLanguage token is env-dependent** — default `Slang`, but the aarch64 `test-slang` CI jobs export `SLANG_USE_SPV_SOURCE_LANGUAGE_UNKNOWN=1` (a swiftshader workaround) so the token disassembles as `Unknown`; a hardcoded `OpSource Slang 1` CHECK passes on x86_64 and fails deterministically aarch64-only. Match it language-agnostic (`OpSource {{Slang|Unknown}} 1`), and reproduce without an aarch64 box by running the test both normally AND with that env var set ([OpSource language token is env-dependent Slang vs Unknown; FileCheck must use {{Slang|Unknown}} — aarch64 trap](../learnings/1784830837048-spir-v-opsource-language-token-is-env-dependent-sl.md)). **(3) At `-g2`, Slang embeds the entire .slang source — comments included — as an `OpString`**, and FileCheck runs over that disassembly, so a `-NOT` or mnemonic CHECK matches the text written in your own directive comments (false positives and vacuous passes); drop `-g2` if you don't need embedded source (`OpName` is emitted regardless of `-g2`), or anchor with line-start forms like `{{^}}OpName %` ([-g2 embeds source-as-OpString and FileCheck matches your own directive comments](../learnings/1784838497425-slang-test-spirv-filecheck-g2-embeds-source-as-ops.md)). **(4) A fixture whose correctness depends on an EXACT byte offset needs `text eol=lf` in `.gitattributes`** — otherwise Windows CI checks it out as CRLF and every `\n`→`\r\n` above the marker shifts the target byte, failing deterministically Windows-CL-only (repro without a box via `sed 's/$/\r/'`); prefer content-anchored matches, and note a test that only needs to EXCEED a threshold is CRLF-safe ([byte-exact .slang fixtures need `text eol=lf` in .gitattributes or fail on Windows CRLF](../learnings/1784845596400-byte-exact-slang-test-fixtures-need-text-eol-lf-in.md)).

## Crafted Minimal Repros and FileCheck CHECK-NOT Regions (2026-07-14 fold)

Before concluding a sanitizer witness (ASan/LSan/UB) is un-addable, attempt a **crafted minimal reproducer** that forces the exact failing condition — don't stop at "the natural repro needs a GPU / an >8GB buffer"; a maintainer often lands the very test you called impossible (slang#12058) ([attempt a crafted minimal repro before concluding a witness is un-addable](../learnings/1783977754690-attempt-a-crafted-minimal-repro-before-concluding-.md)). And a `CHECK-NOT`/`SPV-NOT`/`GLSL-NOT` only scans the region between its preceding and following positive `CHECK` — a forbidden token emitted *earlier* (a GLSL buffer-block or a SPIR-V type decl before `main`/`OpEntryPoint`) is silently missed, so whole-file negatives need a top anchor ([FileCheck CHECK-NOT region is bounded by adjacent positive matches](../learnings/1783994288793-filecheck-check-not-region-is-bounded-by-adjacent-.md)).

**The only reliable whole-output negative is a `-NOT` under its own `filecheck=` prefix with no positive directives to bound it.** Moving a bounded negative to the *top* of the prefix does not fix it either — it is then bounded by the next positive CHECK. On `desc-heap-nonuniform-spirv.slang` a trailing `SPVNONCONST-NOT` after two positive CHECKs was scanning only 6 remaining lines, and a `%uint` pattern could not possibly have fired against the one `OpCompositeExtract %float` left in that window. The fix costs one extra `//TEST:` line (same entry point, same flags) and makes the negative real:

```
//TEST:SIMPLE(filecheck=SPVNONCONST):        -target spirv-asm -entry mainNonConstSibling
//TEST:SIMPLE(filecheck=SPVNONCONSTSIBLING): -target spirv-asm -entry mainNonConstSibling
// SPVNONCONST: %[[IDX:[0-9]+]] = OpCompositeExtract %uint %{{.*}} 0 {{.*}}; NonUniform
// lone -NOT under its own prefix -> scans the entire disassembly
// SPVNONCONSTSIBLING-NOT: OpCompositeExtract %uint %{{.*}} 1 {{.*}}; NonUniform
```

Prove the negative is live by flipping it to a pattern you *know* is present and confirming RED (`sed -i` the directive, run `slang-test`, restore) — and verify the control itself: two of the controls tried on this file were themselves vacuous, so `diff` that the edit landed and confirm the flipped pattern really exists in the output ([CHECK-NOT is bounded by surrounding positive CHECKs — a lone-prefix negative is the only whole-output assertion](../learnings/1785748572125-filecheck-check-not-is-bounded-by-surrounding-posi.md), independently re-derived on #10918 where flipping `CHECK-NOT: OpExtInst {{.*}} Debug{{Global}}Variable` to `CHECK-NOT: OpEntryPoint` — definitely present — still passed 1/1 ([FileCheck tests that pass without testing anything](../learnings/1785779116844-filecheck-tests-that-pass-without-testing-anything.md))).

**Even a correctly-scoped `CHECK-NOT` is worthless if its subject is never emitted at all.** On #12116 the fixer correctly gave the negative its own prefix — then asserted `-NOT: OpCompositeExtract %uint %{{.*}} 1 {{.*}}; NonUniform` on a shader where the `.y` lane's only consumer was a `makeVector` that upstream peephole folds delete, so DCE removed the lane-1 extract entirely (`grep -cE 'OpCompositeExtract %uint %[0-9]+ 1' out.spvasm` → **0**). The check passed unconditionally, cost a full extra compile for zero guard value, and *still* passed when the decoration logic was inverted to over-decorate everything. Vacuity test: grep the real output for the forbidden instruction with the decoration part stripped off — zero hits ⇒ vacuous. Then make the subject live to separate "property sound" from "test proves nothing" (adding `uint2 raw = (uint2)th; … + float(raw.y);` produced an undecorated `OpCompositeExtract %uint %11 1`, confirming the property while indicting the test). Two review consequences: recommend a positive "so the test is not vacuous" fence next to any negative check (in-tree idiom: `tests/spirv/nonuniform-constant-index-no-leak.slang`), and when a clarity reviewer flags a directive/comment contradiction but says "no build in this checkout, cannot resolve" — that is precisely the finding a build resolves; build it ([a CHECK-NOT can be vacuous because DCE removed its subject](../learnings/1785754047907-a-filecheck-check-not-can-be-vacuous-because-dce-r.md)).

## FileCheck Golden Traps + Suite-Wide Opt-Level Plumbing (2026-07-20 fold)

Three harness gotchas. **(1) Diff emit/lowering changes against FileCheck goldens whenever you have not *proved* FileCheck ran** — a green "no compile error" run is NOT a pass: where the `slang-llvm` library is unavailable, `slang-test` silently SKIPS `SIMPLE(filecheck=…)` tests. (Corrected 2026-08-04: "FileCheck is usually missing in-container" is **false** for the standard build — `build/Debug/lib/libslang-llvm.so` is present and LLVM FileCheck really evaluates; see *Where FileCheck comes from* below. Establish which case you are in with a failable control, not by inspecting `bin/`.) Grep every golden touching the modifier/inst you changed and eyeball slangc output vs the ordered `//CHECK:` lines. "Uniform failure across all arches" = deterministic real regression; "one platform only" = golden-drift/flake. A decoration arm shared by multiple decl kinds (func vs struct vs field) is the classic over-broad trap (cost a maintainer-approved PR a 7-platform RED on a `.cuh` golden) ([diff emit/header changes against FileCheck goldens even when FileCheck is absent](../learnings/1784421575539-emit-header-changes-diff-against-filecheck-goldens.md)). **(2) LLVM FileCheck parses a stray `CHECK:` token inside prose/backticks as a live directive** — stock FileCheck scans every line for the active prefix followed by `:`, ignoring comments/backticks/markdown, so a literal `CHECK:` in an explanatory comment silently registers a real (and failing) directive that stops the intended assertion below it. Never put the active-prefix token in prose ([LLVM FileCheck parses a stray CHECK: token in prose as a live directive](../learnings/1784435207146-llvm-filecheck-parses-a-stray-check-token-inside-p.md)). **(3) Suite-wide opt-level override plumbs through `context->options` and the two `addDefault*` helpers** — the `-O0` default lives in `slang-test-optimization-options.h` (`kTestOptimizationOption`, front-inserted deliberately); add a `defaultOptimizationLevel` to `Options`, thread an override param into `addDefaultSlangOptimization`/`addDefaultRenderTestSlangOptimization`, and pass `context->options.defaultOptimizationLevel` at the call sites (`TestContext::options` is public). `-O0` is the sole spirv-opt early-out, so "force max SpvOpt suite-wide" = `-O3`/maximal ([slang-test suite-wide opt-level override: plumb via context->options](../learnings/1784440518963-slang-test-suite-wide-opt-level-override-plumb-via.md)).

## Output paths and status assertions: `-o /dev/null` passes on a failing compile; `-g` makes `result code = 0` self-match (2026-08-04 fold)

**Never write a dump-based FileCheck test to `-o /dev/null`.** This supersedes an earlier note calling it "the idiomatic pattern" for `-dump-ir` tests — it is an anti-pattern, fixed repo-wide in #12333 / PR #12334. `/dev/null` is not a valid output path on **Windows**, so slangc reports `error[E00004]: cannot write output file` and returns a non-zero code (−1/255), yet the test still **passes**: `-dump-ir` prints the IR the assertions match *before* codegen reaches the failing write, and FileCheck only checks text it was told to look for, so a nonzero result code is invisible unless asserted. Net effect is a test that appears to guard a behavior but would keep passing if the compiler stopped working on that path entirely — on one platform, silently, permanently. Caught by pdeayton-nv in review on #12281, not by CI ([dump-based FileCheck tests need `-o -` and an explicit `result code = 0`](../learnings/1785775051459-dump-based-filecheck-tests-need-o-and-an-explicit-.md)). Use **`-o -`** (stdout, valid on every host) and pin the exit status. Note `-o -` and *dropping* `-o` are **not** equivalent: both make the backend run when the test has an entry point and are byte-identical for plain tests, but **with `-g`, dropping `-o` flips the driver into `-whole-program` mode** (visible verbatim in the `-g`-embedded debug string), silently changing what is compiled — prefer `-o -`.

**And the status assertion itself has an inert spelling.** `slang-test` builds the FileCheck buffer as `result code = <N>` / `standard error = {…}` / `standard output = {…}` (`slang-test-main.cpp:1876`), so `// PREFIX: result code = 0` normally pins the exit status — but under `-g` the IR dump embeds the whole source file in `DebugSource("<path>", "<file text>")` insts, so the literal matches **its own comment echoed back inside the dump** and passes even when the real first line is `result code = 255`. Measured: `result code = 0` passed on both a healthy and a forced-failing compile; `result code = {{0}}` passed healthy and **failed** on the failing compile. Break the literal — `{{…}}` is a FileCheck regex, so it matches the digit without the pattern text containing the digit that would self-match. (A reviewer confidently claimed `{{0}}` means literal `{0}`; disproven by control — `{0}` passes on a healthy compile, i.e. it *is* the inert spelling, and `{{1}}` fails on an exit-0 compile, so `{{N}}` is evaluated as a regex.) This is the same family as the known `-g2` `OpString` self-match trap one layer earlier (IR dump, not emitted SPIR-V), where the whole source including `//CHECK` lines lands in an `OpString`: a `CHECK-NOT: DebugGlobalVariable` matches its own comment text, and a positive `CHECK-DAG: DebugGlobalVariable {{.*}} %payload` can pass on the echoed comment with no real instruction present — confirm the hazard is live with `slangc … | grep -o 'CHECK-DAG: <your text>'` returning your own line, and fix by breaking the literal and anchoring on the opcode (`OpExtInst {{.*}} Debug{{Global}}Variable`). **Corollary: never count with a bare `grep -c '<Op>'`** — it counts the test file's own comment lines echoed in the `OpString`, which inflated a figure published to a maintainer (claimed 3 debug records; the real answer was 1); use `grep -cE 'OpExtInst.*<Op>'` ([FileCheck tests that pass without testing anything: bounded CHECK-NOT and OpString self-match](../learnings/1785779116844-filecheck-tests-that-pass-without-testing-anything.md), [never use `-o /dev/null` in slang tests — and `-g` makes `result code` assertions self-match](../learnings/1785787436624-never-use-o-dev-null-in-slang-tests-and-g-makes-re.md)).

Reproduce the Windows failure on Linux with no Windows box: substitute an unwritable path (`-dump-ir -o /nonexistent-dir/out.spv`) — same `E00004`, exit 255, IR still fully dumped, test still green. That is the negative control for any `result code` assertion you add. **Known latent instance:** `tests/autodiff/func-extension/subscript-accessor.slang` still carries the `-o /dev/null` pattern (surfaced to pdeayton-nv, deliberately out of scope on #12281) — a cheap standalone fix for whoever next touches that area. The unifying question for any new test: *"what would have to break for this to stay green?"* — if the answer includes "the compile fails," the test needs a status assertion. And remember the ambient inert mode underneath all of this: with the `slang-llvm` library unavailable, `filecheck=` tests report `TestResult::Ignored`, not failed (`slang-test-main.cpp:815-822`, "Ignore if FileCheck is not available"), so a whole suite can look green while asserting nothing. `FileCheck` is not on `PATH` in the container and never needs to be — slang-test loads it in-process from `libslang-llvm.so`, which **is** present in the standard `build/Debug/lib/`, so it is normally live. Either way the verification is the same and takes one edit: break an assertion on purpose and confirm RED before trusting any green run.

## `100% of tests passed` on a TRUNCATED run — the `failed(pending retry)` grep, and never store the denominator

The `Ignored`/vacuous-green mode above is not the only way this harness turns a non-result into green. `slang-test` also reports a clean `100% of tests passed (264/264)` on a run **truncated by its consecutive-failure breaker**, because the disqualifying failures never *enter* the total rather than being subtracted from it. Verified in source at master `0864e60e6`: `slang-test-main.cpp:5121` early-returns while `stopSchedulingTests` is set, so remaining tests are never scheduled and never reach the reporter; a `PendingRetry` result prints `failed(pending retry) '<name>'` and returns **before** `m_totalTestCount++` (`test-reporter.cpp:368-372`, incremented `:378`) — *"don't count it in any statistics yet"* — and once the breaker fires, retries are skipped so those failures are counted **nowhere**; `runTotal = rawTotal - ignoredCount` (`:694`), percentage printed `:713`. Only `ignoredCount` is a real subtraction, so `264/264` is *arithmetically true* and merely answers a different question than the one you asked — a self-consistent number is far harder to distrust than a lopsided ratio, which is exactly what makes a percentage-grep feel safe. The stream split makes the naive grep fail *by construction*, not by luck: the percentage prints to **stdout** while the bail notice `fprintf(stderr, …)`s (`slang-test-main.cpp:6131-6137`), so `cmd 2>/dev/null | grep '% of tests passed'` discards the disqualifying fact. Watch **both** numbers in `100% of tests passed (264/264), 94 tests ignored` (the `Ignored` path and the breaker path are independent green-manufacturers), and never use `$?` — `slang-test` exits 0 even with failing tests ([`100% of tests passed` on a truncated run: measure the baseline in-session, not a stored constant; the exact accounting](../learnings/1785837790090-correction-slang-test-denominator-check-measure-th.md)).

The **validated** safe pattern — proven on real output in both directions, not reasoned — is `slang-test ... 2>&1 | grep -E '% of tests passed|Stopped scheduling|Skipping retries|failed\(pending retry\)|failing tests'`. `failed(pending retry)` is the **load-bearing** term and the one most likely missing from anyone else's pattern: it fired **265 times** on a real truncated run versus one line for the bail notice, and it prints to **stdout** (`test-reporter.cpp:371`), so it survives exactly the stderr-dropping pipeline that causes the problem. Validation caught its own trap — the first attempt returned **zero matches** because it was pointed at a build log with no test output; *a positive control that returns zero is telling you the control is wrong, not that the world is clean.* On a healthy run the same pattern surfaces only the `689/689` pass line, so it does not false-alarm — a pattern that fires on the bad case but also the good is useless, and both directions matter ([the `failed(pending retry)` grep for the slang-test fake-pass, proven both directions](../learnings/1785838168354-validated-grep-for-the-slang-test-fake-pass-failed.md)). Deeper discipline: **never store a per-directory total as a constant** — remembering `dynamic-dispatch=689`, `interfaces=71`, etc. is itself the defect this warns against, since a stored constant silently ages (hunting a phantom regression after the suite grows, passing a truncated run after it shrinks). Derive the expected value in the same session (baseline before, again after, compare), or run a two-sided drill (neuter → run → restore → run), which is *structurally immune* because it never needs the right absolute number, only that the two runs differ. **A derived-in-session expected value beats a stored one, because a stored one becomes another thing that can be wrong without announcing it.**
