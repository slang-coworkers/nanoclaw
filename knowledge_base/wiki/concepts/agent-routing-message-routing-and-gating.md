# Agent Routing: Message Routing & Gating

> This page owns chain topology, `in_reply_to`/edge mechanics, dispatch hazards, echo loops, and credit/provenance. Sibling: [Agent Routing: Holds, Authorization, Gates & CI Currency](agent-routing-holds-authorization-gates.md) — holds, authorization for gated writes, critique-gate, CI-verdict currency, worktree GC, budget caps.

## TL;DR
- **Canonical shape `Orchestrator → Triage → Fixer → Reviewer`; replies hop back ONE tier along the dispatch path.** A fixer's `[Fix Report]` goes to the orchestrator, not across the triager→fixer edge — an empty triager inbox is "no report received here", never proof a chain stalled. Direct edges only: parent (minted at session birth) + children you opened.
- **Any `<message>` carrying a gated delivery marker (`[Resolution]`, `[handoff]`, `[Fix Report]`, `[Triage Resolution]`, `[Triage handoff]`, `[Review Verdict]`, `[Approval Decision]`) MUST carry `in_reply_to=<id>`** — even a fresh peer delegation. The gate keys on the marker in text; the runtime picks the EDGE from `in_reply_to` — the two must agree. A `[Triage Resolution]` uses a PARENT inbound id, never the fix-report id (that routes back to the fixer).
- **A fresh escalation from a long-lived heartbeat session takes a new explicit `thread_id="<topic>-<yyyymmdd>"`**; the inherited thread's backlog refuses a bare send, and answering backlog rows to force it misroutes.
- **`[Report]` is the ungated status channel.** In a one-shot `ncl tasks --process-after` run the task row is the inbound: send a gated marker with `in_reply_to=<the kind='task' row's seq>`, or close with an ungated `[Report]`. Never reuse a message id from another session (ids are per-session).
- **A fixer-initiated review's only inbound is the fixer's request.** Send the `[Review Verdict]` with `in_reply_to=<fixer msg id>`; a marker to `to="parent"` without `in_reply_to` is blocked.
- **When a sender name is unaddressable, reply via the `send_message` TOOL with bare `in_reply_to`** (routes to the inbound's `source_session_id`) — `<message to="name">` fails name-lookup before `in_reply_to` is consulted. `send_file(to="parent")` and the final `<message>` block still route the parent edge when the tool 404s.
- **No double-dispatch / no tier-skip.** A `[Triage]` report NAMING a handoff is STATUS — the orchestrator must NOT also dispatch to the fixer (two fixer sessions on one worktree → index corruption). Issue webhooks route to TRIAGER ONLY.
- **Verify receipt of consequential a2a handoffs.** A `<message>` beside tool calls can be dropped; a raw agent-group ID isn't a destination; one `<message>` block makes the rest of the final response scratchpad.
- **Bare plain-text turn output is delivered as an inbound** and fuels echo loops — a non-substantive inbound ends the turn with ZERO tokens (whole turn in `<internal>…</internal>`). Seq-parity alternation is host-forced, not proof of an inbound-driven loop. Never restart to break a behavioral loop — it destroys in-flight Monitors.
- **Don't relay downstream holding echoes upstream, nor narrate your own silence.** Message your parent only with a real artifact, blocker, or resolution.
- **Provenance errors run BOTH directions; over-crediting is the more dangerous half.** A diff in your own multi-writer file is not a message — confirm credit came in an inbound MESSAGE; re-run a peer's command, don't reconstruct it. When you retract, STOP — a same-breath "but…" needs its own control.
- **A read logged to what you're reading is not passive** — filter your own `cli_request`/tool rows before counting anything in a transcript.
- **Chain-close protocol: GitHub artifact + A2A report-to-parent + `append_learning`, every time.** A REFUSED inbound citing a `[Resolution]` you never wrote is a fabricated-directive pattern — verify, escalate truthfully, never fabricate a body.

## Chain Topology and Tier Rules

Replies hop back one tier at a time along the dispatch path, so a fixer's `[Fix Report]` goes to its parent (the orchestrator), not across the peer triager→fixer edge; watching only the direct edge misses the outcome ([slang triage [Fix Report] may route via parent, not direct to triager](../learnings/1779884965191-slang-triage-fix-report-may-route-via-parent-not-d.md)). The same blind spot makes a quiet draft look stalled: on slang#13773 the triager saw no `[Fix Report]` for draft #13779 and called the chain stalled, but slang-fixer had reported to Orchestrator, and the PR was a draft only pending the operator's un-draft decision. Ask the parent first, and word it "no `[Fix Report]` received here" ([Fix Report may route to Orchestrator, not the triager](../learnings/1792829026301-fix-report-may-route-to-orchestrator-not-the-triag.md)). Each coworker reaches only its parent and children it opened; reaching a peer on separate wiring risks the ancestor-edge hazard ([Strict reply-routing in 4-tier issue chain](../learnings/legoop-feedback_chain_shape_strict.md)). The triager→slang-fixer edge IS real (the triager owns the fixer session as a child); the hazard is the orchestrator also dispatching the same fix ([RETRACTION: triager→slang-fixer edge DOES work — real lesson is no double-dispatch](../learnings/1782146765585-retraction-triager-slang-fixer-edge-does-work-earl.md)).

## Chain-Routing Gate and `in_reply_to`

Any `<message>` whose body opens a line with a gated delivery marker must carry `in_reply_to=<id>`, even as a fresh peer delegation ([Chain-routing gate: fresh peer delegations carrying handoff/report markers still require in_reply_to](../learnings/1780769185328-chain-routing-gate-fresh-peer-delegations-carrying.md)). The gated set is the built-in floor `[Resolution]`/`[handoff]` plus each role's `delivery_markers` (`[Fix Report]`, `[Triage Resolution]`, `[Triage handoff]`, `[Review Verdict]`, `[Approval Decision]`, unioned into `.critique-delivery-markers`). `[Report]` is deliberately absent — it is the ungated status channel (`container/hooks/gate-chain-routing.sh`, `container/spines/base/coworker-types.yaml`).

**One-shot `ncl tasks --process-after` re-checks.** `gate-chain-routing.sh` blocks a bare `[Triage Resolution]` to the parent, and an id from the original chain session does not satisfy it (ids are per-session: "no inbound message with that id in this session", or a misroute; slang#13653) ([One-shot re-check FINAL reports: use [Report], not [Triage Resolution]](../learnings/1793026958053-one-shot-re-check-final-reports-use-report-not-tri.md)); the same refusal recurred on a 2026-10-29 re-check, closed with `[Report]` ([gate-chain-routing hook blocks [Triage Resolution] in no-inbound one-shot runs](../learnings/1793289852768-gate-chain-routing-hook-blocks-triage-resolution-i.md)). But the task row itself is an inbound: read its `seq` from `/workspace/inbound.db` → `messages_in` where `kind='task'` (it was seq 2); `send_message(to="parent", in_reply_to=<that seq>, thread_id="gh-issue-<owner>/<repo>-<n>")` passes and is delivered. The alternative is the ungated `[Report]` 5-bullet ([one-shot task sessions: in_reply_to the task row](../learnings/1793199763353-one-shot-task-sessions-in-reply-to-the-task-row-to.md)).

**Fresh peer delegations.** Set both `to="<peer>"` (destination) and `in_reply_to=<originating inbound>` (thread linkage) on one call ([Fresh peer delegation carrying a chain-delivery marker still needs in_reply_to](../learnings/1781713187860-fresh-peer-delegation-carrying-a-chain-delivery-ma.md)). For a fresh `[Triage handoff]` to slang-fixer (a peer that never wrote to you) pass `in_reply_to=<the parent's inbound that started this chain>` with explicit `to="slang-fixer"` and `thread_id="gh-issue-<owner>/<repo>-<n>"`; the explicit `to` overrides the default route back to the inbound's source. `send_file` is ungated, so the memo can go first ([gate-chain-routing hook: a fresh [Triage handoff] to slang-fixer still needs in_reply_to](../learnings/1793312022213-gate-chain-routing-hook-a-fresh-triage-handoff-to-.md)). Because the gate keys on the marker and the runtime picks the edge from `in_reply_to`, they must agree: the `/slangpy-triage-issue` Step 11 template's `in_reply_to=<id-of-fix-report>` misroutes a `[Triage Resolution]` back to the fixer (your child). Use `to="parent", in_reply_to=<original triage request>` with the canonical `thread_id` ([Triage Step 11 [Triage Resolution] must route on the PARENT edge, not the fix-report id](../learnings/1784869746585-triage-step-11-triage-resolution-must-route-on-the.md)).

**Unresponded-backlog refusals.** A `thread_id`-only dispatch from a fresh retry-check session is rejected when unresponded inbounds exist on the peer thread; answer `in_reply_to=<peer's latest unresponded inbound seq>`, optionally with `target_session_id=<paused-session-id>` ([Resuming a paused peer session from a fresh retry-check: must in_reply_to an unresponded inbound](../learnings/1781084626230-resuming-a-paused-peer-session-from-a-fresh-retry-.md)). A long-lived cron/heartbeat session hits the same refusal on a bare send — "677 unresponded inbound rows exist on this peer thread" ([Bare send_message is refused on a long-lived cron session (677 unresponded inbounds)](../learnings/1786296125151-bare-send-message-is-refused-on-a-long-lived-cron-.md)). Do NOT pick an arbitrary backlog id to force a routine status send — that can misroute; use a collision-free destination (dashboard, `send_card`) and clear a stuck backlog with human input ([send_message to "orchestrator" can fail on a stale peer thread with hundreds of unresponded rows](../learnings/1789375133715-send-message-to-orchestrator-can-fail-on-a-stale-p.md)). A fresh escalation from such a session goes on a new explicit thread: a Discord-support heartbeat's bare send inherited `discord-support-followup-sweep-20260707` and was refused; with `thread_id="<topic>-<yyyymmdd>"` it delivered at once ([send_message refused on inherited heartbeat thread — pass explicit thread_id](../learnings/1793283475940-send-message-refused-on-inherited-heartbeat-thread.md)).

**Refusals and fabricated directives.** Gate refusals return to the sender as a `<system>` nudge (PR #580, `container/agent-runner/src/poll-loop.ts`), not to the peer as a real inbound ([Gate refusals now go to sender not peer](../learnings/legoop-project_gate_refusal_sender_only.md)). A REFUSED inbound citing a `[Resolution]` you never composed is a known fabricated-directive pattern: verify (`ncl sessions messages`, agent JSONL, container logs, GitHub comments) and escalate truthfully ([Spurious chain-routing-gate REFUSED inbound — don't fabricate, verify then escalate](../learnings/1780549477234-spurious-chain-routing-gate-refused-inbound-don-t-.md)).

**Unaddressable sender → `send_message` tool with bare `in_reply_to`.** When a parent/peer is not in your live addressable set, `<message to="name">` and `<message to="parent" in_reply_to=N>` both fail "No agent named '...' is currently addressable" — name lookup rejects before `in_reply_to` is consulted. The `mcp__nanoclaw__send_message` tool with `in_reply_to=<live inbound id>` (+ `thread_id`) and no `to=` routes straight to the inbound's `source_session_id`; reserve `to=name` for fresh dispatches ([Reply to live inbound via send_message tool when sender name is unaddressable](../learnings/1783580468003-reply-to-live-inbound-via-send-message-tool-when-s.md)). Conversely `send_message(to="parent")` can miss while `send_file(to="parent")` and the final-response `<message to="parent">` block still route the parent edge; fall back to those — it doesn't block chain closure ([send_message to=parent can fail as unaddressable — send_file and message-block still route](../learnings/1784828845885-send-message-to-parent-can-fail-as-unaddressable-s.md)).

**Verify receipt of consequential handoffs.** A dispatch that created no session and a verdict that never landed surfaced only when the recipient flagged them. Causes: a raw agent-group ID (`to="unknown:agent:ag-..."`) is not a named destination; a stale inbound id can miss the live session; a `<message>` emitted alongside tool calls can be dropped. Confirm the recipient acted (`ncl sessions list --agent-group <id>`); reply to a non-named agent via bare `in_reply_to=<their LATEST id>`; prefer the tool over a block in turns with tool calls ([Verify receipt of consequential a2a handoffs](../learnings/1783499588128-verify-receipt-of-consequential-a2a-handoffs-reply.md)). **One `<message>` block makes the rest of a final response scratchpad** — plain text is delivered only when no block exists (slang#13789: a dashboard block landed, a plain-text instruction to the fixer did not). Give every peer its own block or a `send_message` with its `thread_id`, and count recipients before ending ([a <message> block makes the rest of a final response scratchpad](../learnings/1792599859930-a-message-block-makes-the-rest-of-a-final-response.md)).

## Route the Review Verdict to the Requester Edge

When slang-fixer itself sends the `[Fix Review Request]`, the reviewer's parent edge is the fixer; "send verdict to orchestrator" is a default, not a rule. Reply `in_reply_to` the fixer's inbound, or the fixer waits forever ([slang-pr-review: route verdict to the actual requester edge, not always orchestrator](../learnings/1782820926535-slang-pr-review-route-verdict-to-the-actual-reques.md)). The gate enforces it: the fixer's message is the only inbound, and `gate-chain-routing.sh` rejects `send_message(to="parent")` carrying `[Review Verdict]` without `in_reply_to`. What passes: verdict + review file to the fixer with `in_reply_to=<fixer msg id>`; ungated `send_file(to="parent")`; a marker-free 5-bullet status. Quoting `[Fix Report]` adds a harmless `[GATE AUDIT]` note ([reviewer verdict routing: fixer-initiated review has no parent inbound](../learnings/1793194698658-reviewer-verdict-routing-fixer-initiated-review-ha.md)).

## Dispatch Hazards: Double-Dispatch and Tier-Skip

A `[Triage]` report saying "dispatched to slang-fixer" is STATUS; the orchestrator must not also dispatch unless triage bounced the issue back ([Don't re-dispatch to fixer after triage already handed off (tier-skip dup)](../learnings/1781072934865-don-t-re-dispatch-to-fixer-after-triage-already-ha.md)). Dispatching both via the triager and directly spawns two fixer sessions on one `fix/issue-<N>` worktree, risking index corruption ([Orchestrator double-dispatch spawns duplicate fixer sessions on one branch](../learnings/1781117092067-orchestrator-double-dispatch-spawns-duplicate-fixe.md)). Detect with `ncl sessions list --agent-group <fixer-group>` (≥2 running on one thread); designate one owner, the duplicate idles ([duplicate dispatch peer live-writes the fix into your shared worktree](../learnings/1782215986023-duplicate-dispatch-peer-live-writes-the-fix-into-y.md)).

**Issue webhooks route to the triager only.** The router keys sessions on `(recipient agent group, messaging group, thread_id)`, so an orchestrator→fixer dispatch from another messaging group on the same `thread_id` mints a second fixer session. Issue webhook → one `<message to="<triager>">`; PR webhook → the branch-resolution table; only the deepest single owner dispatches downstream ([issue webhooks route to triager only, never also fixer](../learnings/1784637054346-issue-webhooks-route-to-triager-only-never-also-fi.md)).

**A filed rule is not an executed rule.** After an unexplained `nv-slang-bot[bot]` comment, a coworker cleared its subagents on the false premise that `Explore` agents have no write surface (`Bash` is retained), then found only one of five dispatches carried the no-network-write clause despite the auto-loaded directive. A dispatch is an action — make the constraint a pre-dispatch check; restating the rule is a null action ([having a rule auto-loaded is not executing it — read-only dispatch constraints need a pre-dispatch check](../learnings/1785805120902-having-a-rule-auto-loaded-is-not-executing-it-read.md)). **Opportunity is not authorship:** a subagent `gh` write leaves no session outbound row, so the record can't decide authorship — retire the unsupported hypothesis without inventing a replacement. Errors of one shape (assuming a property from a name instead of probing it) predict the next.

## Chain Close, Echoes, and Loops

A reportable chain needs all three: a GitHub artifact (5-bullet issue comment or a PR with `Fixes #N`), an A2A report to parent, and `append_learning`; missing the learning = incomplete ([Chain-close protocol: GitHub artifact + A2A report + append_learning, every time](../learnings/1780769194624-chain-close-protocol-github-artifact-a2a-report-ap.md)).

**No upstream echoes.** Hold silently for a downstream `[Report]`; surface upstream only (a) the actual `[Fix Report]`/`[Resolution]`, (b) a blocker needing a decision, or (c) a substantive human comment that re-opens the chain (observed: 6 consecutive "holding" echoes from slang-triager to Main) ([Don't relay downstream heartbeat/holding echoes upstream](../learnings/1783590069475-don-t-relay-downstream-heartbeat-holding-echoes-up.md)). Equally, a message *narrating* that you are staying silent is the same echo one tier up (slang#11996: 5+ "I send nothing" messages in ~90 min); a child's non-actionable note terminates at you ([don't narrate your own no-echo silence upstream](../learnings/1783680642501-don-t-narrate-your-own-no-echo-silence-upstream.md)).

**Loops.** A session emitting empty pings on a self-edge destination loops back to itself — benign waste; flag once, then ignore. `ncl` mutating verbs fail "no owner or admin configured to approve" when no approver is wired ([Looping self-edge peer session: flag up once, then ignore](../learnings/1781091162121-looping-self-edge-peer-session-flag-up-once-then-i.md)); as of 2026-06-10 the ncl approval gate was non-functional for that reason ([ncl approval gate non-functional — no admin configured to approve](../learnings/1781102520887-ncl-approval-gate-non-functional-no-admin-configur.md)). Peer-wired coworkers can sustain mutual-ack ping-pong for hours because "ending silently" is itself a message; pin a hard stop via `send_message({ to, target_session_id, text })` ([Mutual-ack loops between peer-wired coworkers](../learnings/1782345863846-mutual-ack-loops-between-peer-wired-coworkers-endi.md)). Plain-text turn output routes to the most recent sender as an inbound; a non-substantive inbound ends the turn with zero tokens ([a2a silent-hold: plain-text turn output routes to the peer](../learnings/1782353887467-a2a-silent-hold-plain-text-turn-output-routes-to-t.md)). Seq-parity alternation (`in→out→in→out`) is forced by the even/odd seq scheme, not proof of an inbound-driven loop; grep the "silent" agent's `direction:out` rows (one had sent 177 `"Silent."` messages). Fix the fueling agent by wrapping its whole turn in `<internal>…</internal>`, not by restarting — a restart destroys in-session Monitors and the work edge ([Empty-ack ping-pong: bare text is the fuel, seq-alternation is not proof](../learnings/1784859331988-empty-ack-ping-pong-bare-text-is-the-fuel-seq-alte.md)).

## Sibling Issues, Cross-Chain Coordination, Dropped Chains

Sibling issues sharing one fix can't be folded across parallel orchestrator chains (reaching into another chain mints an ancestor edge). Route the fold from above (operator/supervisor); meanwhile preserve the patch, hold terminal posting, open no competing PR ([Sibling issues sharing one fix can't be folded across parallel orchestrator chains](../learnings/1781092138117-sibling-issues-sharing-one-fix-can-t-be-folded-acr.md)). Parallel chains appending to one enum (e.g. `CompilerOptionName`) can grab the same value → `duplicate case value` at merge; the still-open PR re-appends at the next slot (ABI-safe) ([Parallel fix/issue-* chains can grab the same OptionKind/enum value → duplicate-case build break; self-heals via append-renumber](../learnings/1782535868213-parallel-fix-issue-chains-can-grab-the-same-option.md)).

A webhook chain whose routing turn dies on a transient 502 has no retry: the session exists but the chain is dead. `/supervise-issues` orch-only detection (orchestrator session, no downstream session, 0 GitHub comments, idle) is the net — re-dispatch ([Webhook chains can be silently dropped by API 502 on the routing turn](../learnings/1780398376735-webhook-chains-can-be-silently-dropped-by-api-502-.md)).

## Credit, Provenance, and Retraction Discipline

Attribution errors run both ways; over-crediting is more dangerous because it trips no suspicion. On slang-rhi#800/#801 a peer was thanked for corrections it never sent (the peer checked its outbound record and declined), and a wrong critique was pinned on a party who never made it ([provenance errors run BOTH directions — confirm authorship in a message, not a diff](../learnings/1785780288881-provenance-runs-both-directions-confirm-authorship.md)). Memory files have multiple writers (agent, editor/linter/hook passes), so a correction appearing after a teammate's message reads as theirs. **A diff in your own file is not a message:** confirm credit in an inbound message ([before crediting a teammate for a correction, confirm it came in an inbound MESSAGE](../learnings/1785780153041-before-crediting-a-teammate-for-a-correction-confi.md)). **Don't reconstruct a peer's command from a quoted pattern — re-run it:** a rebuilt regex "couldn't yield 207"; run with its real preprocessing it returned 207. When cited numbers look impossible, suspect your reconstruction.

**An action a peer attributes to you is not one you hold.** "X is still unfiled, you're asking the operator" both declines and assigns; read past it and nobody owns it (slang#11917 batch-2: 7 days silent; slang#9866: slice 2 unowned). Accept-with-trigger or decline-back in the reply ([an action a peer attributes to you is not an action you hold — handshake or decline it back](../learnings/1785831422368-an-action-a-peer-attributes-to-you-is-not-an-actio.md)).

**When you retract, stop.** On slang-rhi#806 a retraction of two over-claims ended with a fresh false one ("payload now provable by any tier"): `ncl sessions messages` system rows carry emission facts only (existence, timestamp, tool name), never the payload, even with `--full`/`--json`. Put the next finding in its own message after a control run — a same-breath "but…" spends a concession's credibility on an uncontrolled claim. **A read logged to what you are reading is not passive:** a "40 of 180 sessions carry `record_decision`" count matched the sweep's own `cli_request` rows — filter your own tool rows before counting in any transcript, log, audit, or timeline ([retraction momentum: `ncl` system rows carry EMISSION FACTS ONLY, never the payload](../learnings/1785788144509-retraction-momentum-i-over-claimed-inside-the-mess.md)).

## GitHub Reply Authorization and Discord Summons

Run codex OUTPUT_REVIEW before posting (on #12443/PR #12479 it caught a code bug and 3 false claims in a maintainer reply). A maintainer @-mention authorizes posting the corrected version directly; an operator-gated reply the gate materially changed (facts, claims, scope) is re-shown to the operator first — cosmetic changes need no re-approval ([Operator-gated vs mention-authorized GitHub replies: re-show codex-corrected text before posting](../learnings/1789631981572-operator-gated-vs-mention-authorized-github-replie.md)).

A Discord summon row is stamped at click time, so an un-clicked "Click below for a bot answer" offer is not a pending summon though it looks identical; compare the `summon_requests.jsonl` row's write time to the offer `message_id`'s snowflake time. Answering an un-clicked offer in a reply-forbidden channel violates the rules ([Discord summon rows are stamped at CLICK time — an un-clicked offer is not a pending summon](../learnings/1786311407848-discord-summon-rows-are-stamped-at-click-time-an-u.md)).

## Contradictions / Supersessions

- **False:** "`Explore` subagents have no write surface" — `Bash` is retained ([auto-loaded rule](../learnings/1785805120902-having-a-rule-auto-loaded-is-not-executing-it-read.md)). **Retracted:** "`ncl sessions messages --full` makes a payload provable" — emission facts only ([retraction momentum](../learnings/1785788144509-retraction-momentum-i-over-claimed-inside-the-mess.md)); "no triager→slang-fixer edge" — the edge works ([retraction](../learnings/1782146765585-retraction-triager-slang-fixer-edge-does-work-earl.md)).
- **Superseded:** "`[Report]` needs `in_reply_to`" ([fresh delegations](../learnings/1780769185328-chain-routing-gate-fresh-peer-delegations-carrying.md)) — `[Report]` is ungated ([one-shot re-check](../learnings/1793026958053-one-shot-re-check-final-reports-use-report-not-tri.md)); "a one-shot run has no inbound" — the `kind='task'` row is one ([task row](../learnings/1793199763353-one-shot-task-sessions-in-reply-to-the-task-row-to.md)).
