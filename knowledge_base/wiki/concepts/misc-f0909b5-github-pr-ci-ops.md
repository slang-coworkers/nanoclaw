## TL;DR

Operational findings for agents driving GitHub PR/issue work, scheduled tasks, and CI diagnosis — most are silent-false-result traps.

- **GitHub query false-empties & staleness:** `nv-slang-bot` is a GitHub *App*, so `author:app/nv-slang-bot` (not `author:nv-slang-bot`) is required or search returns 0 silently. A deleted head branch 404s on the contents API — read add/keep/remove from `gh pr diff`, never infer from `contents?ref=<branch>`. Read a submodule pin from `git ls-tree origin/main`, not a possibly-stale local clone. `closingIssuesReferences` (auto-close armed) and a `Closes #N` body keyword are two independent facts. An issue may cite symbols that live only in an unmerged PR's branch. Discord forum channels legitimately return empty on channel-level reads (content is in threads).
- **Bot `workflows`-permission guard is PATH-based:** even a plain `.md` under `.github/workflows/` is rejected for the App; `git push --dry-run` is a FALSE GREEN. Route any change under `.github/workflows/**` to a human committer from the start. `release.yml` (build-slang-llvm mapping, LTO/develop-build default flips) is under that guard too.
- **Wake-payload / scheduled-task scripts:** the babysitter's `prCount`/`prs` mismatch is an unpaginated single-page fetch + a hardcoded `slice(0,20)` — the generator lives in the task's `script` field (`ncl tasks get <series>`), invisible to filesystem search. Never trust `prCount`; cross-check with a fresh `gh pr list`. Log conventions drift — re-read the durable log's field spec before writing.
- **CI diagnosis:** a PR closed seconds before an epic is a deferral (revive it), not a rejection. `gitlab-master.nvidia.com` is unreachable from the sandbox (OneCLI has no rule) — use cross-PR base-rate comparison instead. Slang release binaries diverge from a local `default`-preset build (LTO/develop-build defaults), and `slangc -v` is the surface to make a build self-reporting.

## GitHub query false-empties and staleness

Several atoms document queries that return a wrong answer with no error. `nv-slang-bot` is a GitHub App whose login is `nv-slang-bot[bot]`, so the search qualifier must be `author:app/nv-slang-bot` — the plain `author:nv-slang-bot` matches a nonexistent user account and returns `total_count: 0` silently; always run a positive control (a known bot PR number) before trusting a 0 ([GitHub search: bot-authored PRs need author:app/ prefix](../learnings/1787300278876-github-search-bot-authored-prs-need-author-app-pre.md)). A deleted head branch (frequent on close/merge) 404s on `contents/<path>?ref=<headBranch>` with "No commit found for the ref," which is trivially misread as "the file isn't there ⇒ the PR removed it" — a concrete miss inverted a conclusion (a PR that actually DELETED 13 files was read as "kept them"); source add/keep/remove from `gh pr diff`, and note this ties to "agreement is not corroboration" since the peer's confirming claim was the one least likely to be re-run ([A deleted branch 404s on the contents API — that is not "file kept"](../learnings/1787229512774-a-deleted-branch-404s-on-the-contents-api-that-is-.md)). A submodule pin must be read from `git ls-tree <ref> <path>` against an up-to-date ref (`origin/main` after fetch), not the local clone's HEAD or `git submodule status` — a clone 59 commits behind agreed with itself but cited the wrong SHA; run `git rev-list --count HEAD..origin/main` before quoting any pin/line-number, and prefer `gh pr/issue view` (live remote) for state ([Submodule pin: read it from git ls-tree of the up-to-date ref](../learnings/1787226506058-submodule-pin-read-it-from-git-ls-tree-of-the-up-t.md)). `closingIssuesReferences` (populated even by a manual UI link, with no body keyword) and a literal `Closes/Fixes/Resolves #N` body keyword answer two different questions — check both explicitly; when the body keyword is absent, do NOT suppress the issue post ([closingIssuesReferences ≠ a Closes-keyword in the PR body](../learnings/1787174946805-closingissuesreferences-a-closes-keyword-in-the-pr.md)). An issue split out from PR #NNNN may cite symbols/error codes that do NOT exist on master — they can live only in the still-open source PR's branch — so `gh pr view <sourcePR>` + `gh pr diff | grep <symbol>` before recommending a fix location ([Issue may describe code that lives only in an unmerged PR](../learnings/1787545144849-issue-may-describe-code-that-lives-only-in-an-unme.md)). And a Discord forum channel legitimately returns empty on `GET /channels/{id}/messages` because all content lives in threads — confirm the channel *type* before minting a "degraded read" caveat (this cost 3 daily reports of falsely-flagged support-read degradation); read forums via `/guilds/{guild}/threads/active` filtered by `parent_id` ([Discord forum channels return empty on channel-level reads (not an outage)](../learnings/1787472813956-discord-forum-channels-return-empty-on-channel-lev.md)).

## The bot workflows-permission guard is path-based

Confirmed live: `nv-slang-bot[bot]` (a GitHub App lacking the `workflows` permission) is blocked from pushing ANY file under `.github/workflows/` — including a plain `README.md`, not just `.yml`/`.yaml` — because the guard is PATH-based, and a prior triage prediction that "Markdown should push" was FALSE ([A plain .md inside .github/workflows/ IS blocked for the bot](../learnings/1787260827740-a-plain-md-inside-github-workflows-is-blocked-for-.md), [Bot workflows-permission guard is path-based](../learnings/1787261003461-bot-workflows-permission-guard-is-path-based-block.md)). A critical second trap: `git push --dry-run` is a FALSE GREEN (returns rc=0, "would set upstream") while only the real push triggers the server-side rejection — always do the real push and verify the branch landed (`git ls-remote`). Route anything touching `.github/workflows/**` to a human committer or a `workflows`-scoped PAT from the start; a whole-commit-in-the-guarded-dir has no split to do (a push is atomic). This governs `release.yml` too: `release.yml:161-162` maps `build-slang-llvm: true` → `USE_SYSTEM_LLVM` else `DISABLE` (set only for linux/x86_64, windows/x86_64, macos/aarch64), so any other platform's release zip never contains slang-llvm and a downstream `FETCH_BINARY_IF_POSSIBLE` config silently falls back to DISABLE — and fixing it requires a human because `release.yml` is under the guard ([release.yml build-slang-llvm maps to USE_SYSTEM_LLVM/DISABLE, not FETCH](../learnings/1787288555514-release-yml-build-slang-llvm-maps-to-use-system-ll.md)). Related divergence: Slang release binaries differ from a local `default`-preset build because `SLANG_ENABLE_RELEASE_LTO` (default OFF, ON in release.yml) and `SLANG_STANDARD_MODULE_DEVELOP_BUILD` (default ON, OFF in release.yml) — a default LTO flip regresses ALL of CI (which uses the plain preset), and `slangc -v` (`getBuildTagString`) is the cheap surface to make a build self-reporting; options that edit `.github/workflows/*` are not bot-actionable ([Slang release-vs-local divergence: default flip regresses ALL CI, and -v is the self-report surface](../learnings/1787217736575-slang-release-vs-local-divergence-default-flip-reg.md)).

## Wake-payload and scheduled-task scripts

The babysitter sweep's `prCount` (24) overstating the `prs` array length (20) was first flagged as a probe-worthy anomaly ([Wake payload prCount can overstate the prs array length](../learnings/1787184440941-wake-payload-prcount-can-overstate-the-prs-array-l.md)), then root-caused to two compounding bugs in a Node script embedded in the scheduled task definition: `prCount` from a single unpaginated `/pulls?per_page=50` fetch (undercounts once total open PRs exceed 50) and `prs` hardcoded-truncated to `slice(0,20)` — the generator lives entirely in the task's `script` field (`ncl tasks get <series>`), invisible to filesystem search, so check that BEFORE grepping the workspace/repo ([Wake payload prCount/prs mismatch root cause: unpaginated fetch + hardcoded slice(0,20)](../learnings/1787184948926-wake-payload-prcount-prs-mismatch-root-cause-found.md)). The pagination defect was confirmed on BOTH `prs` and `evicted` (single-page-50 = 18 vs fully-paginated = 110 non-draft / 298 total) and fixed with a shape-aware `fetchAllPages` helper (a bare array from `/pulls` vs `{total_count, workflow_runs}` from `/actions/runs`) plus an early-stop predicate and a `prsTruncated` visibility field ([Wake-payload pagination bug confirmed on BOTH prs and evicted — fix drafted+live-tested](../learnings/1787250588200-wake-payload-pagination-bug-confirmed-on-both-prs-.md)). A related log-convention drift: the durable `rerun-log.jsonl` `action` field must be `"decline"` (not `"rerun"`) for a considered-and-refused verdict — 10 bad lines were written from memory before the file was re-read; when a stored file names a specific field convention, open and re-check it before writing, not just from memory ([rerun-log.jsonl action field: use "decline" not "rerun"](../learnings/1787213227139-rerun-log-jsonl-action-field-use-decline-not-rerun.md)). And a scheduled task can silently no-op on a path mismatch: the daily PR-report task references `pr_report.py` at a `~/.claude/skills/` path that does not exist (exit 2, treated as transient and skipped), while the real script is at `/workspace/agent/slang-skills/skills/...` returning meaningful exit codes (10=due, 0=quiet, else=transient) — an exit 2 means check the script path first ([slang-pr-report script actual path differs from scheduled-task instructions](../learnings/1787548020529-slang-pr-report-script-actual-path-differs-from-sc.md)).

## CI diagnosis and triage sequencing

When triaging a maintainer-authored CI/infra epic, check for a CLOSED PR by the same author with a close timestamp within seconds of the issue — that is almost always a deliberate deferral to sequence the work (the closed PR is the ready-to-revive change), not a rejection; correct triage is "revive #1120 once runners land," and the issue's own "current state" prose can be stale (re-derive the pin from the submodule gitlink) ([A PR closed seconds before an epic is filed is a deferral, not a rejection](../learnings/1787226161533-a-pr-closed-seconds-before-an-epic-is-filed-is-a-d.md)). When a `test-falcor` job fails, `gitlab-master.nvidia.com` is unreachable from the sandbox (OneCLI gateway has no rule → HTTP 502 `resolution_failed`, WebFetch and curl fail identically) — you cannot inspect the GitLab-side breakdown, so the workaround is cross-PR base-rate comparison (sample job conclusions/durations across recent runs to tell outage from intermittent-but-real, full-run from early-abort) ([gitlab-master.nvidia.com is unreachable from this sandbox network](../learnings/1787295623501-gitlab-master-nvidia-com-is-unreachable-from-this-.md)).
