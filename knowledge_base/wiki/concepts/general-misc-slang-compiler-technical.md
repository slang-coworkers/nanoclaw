# Slang Compiler Technical Findings

Concrete findings about the Slang compiler codebase: checking external-tool claims at the pinned SHA, IR crash diagnosis, descriptor-heap specialization and surface syntax, cooperative-matrix coverage, rebase-experiment pitfalls, expected-failure semantics, platform-macro conversion, which slang-test harness pins which property, precompiled-module import resolution, and cross-session component-type and threading rules.

## TL;DR

- A DeepWiki answer about an external or vendored repo is a hypothesis; read the source at the pinned submodule SHA. DeepWiki misses string-literal bulk-declaration files and conflates cooperative-vector with cooperative-matrix.
- For an IR-pass crash, the frame nearest the assertion is a hypothesis, not the fix site. Dump IR against the repro first, and assume "missing null check" is multi-site until grepped.
- Text-only FileCheck does not prove SPIR-V validity. Run `SLANG_RUN_SPIRV_VALIDATION=1` for any change that shapes emitted SPIR-V.
- In a specialized clone, reuse an existing hoistable global rather than parameterizing it. A heap global demoted to a `uint` parameter yields invalid SPIR-V.
- Check whether a request is front-end surface syntax before scoping backend work; the descriptor-heap backend exists behind `DescriptorHandle<T>`. A context-typed builtin returns a concrete proxy, never a return-only generic.
- A locationless warning can fire on compiler-synthesized structures. Deduplicated type-getters cannot carry a per-instance `sourceLoc`; put location markers on the non-deduped type.
- Never gate a correctness check on `sourceLoc.isValid()`. Diagnostic-quality plumbing and correctness gating must not share a predicate.
- When testing a check, vary how the declaration arrives (same file, imported source, precompiled module), not only its shape. Serialization drops locations, and with them every location-gated check.
- On `-I`, a precompiled `.slang-module` beats `.slang` source of the same name; with no `-I`, resolution falls back to cwd. An import-path experiment needs a negative control that fails with "cannot open file". `.slang-module` is gitignored, so a stale one hides easily.
- Pick the harness by the property you need pinned: `diag=` pins message text only and passes if the compiler emits the diagnostic and then segfaults; `TEST:SIMPLE(filecheck=)` sees the `result code = X` line, so lead with `CHECK: result code = 0`; `//TEST:SIMPLE:` with a `.expected` file pins the code too.
- Before asserting that a symbol appears in emitted output, grep the target's prelude. On a target that emits its prelude verbatim, a bare prelude-defined name is a vacuous anchor.
- `*.expected` is gitignored: it needs `git add -f` and never shows in `git status`. A missing baseline makes the test fail 0/1, loudly. Generate baselines by promoting `.actual`, never hand-write them, and never commit `.actual`.
- A suite number from your working tree describes the tree, not the commit. Bind it with a detached worktree at the pushed SHA and an empty `git status --porcelain`.
- Reading the code that decides an outcome raises confidence in the mechanism, not in the outcome. For "does it pass / fire / what exit code", the run is the evidence.
- A control that cannot fail is not a control. Print byte sizes with grep counts (`NA` on zero-byte output), and capture `out=$(cmd 2>&1); rc=$?`, since `$?` after a pipeline reads the last command.
- Separate "this change caused it" from "this change doesn't cover it" with the feature's own off-switch before calling anything a regression.
- Before declaring "master is red" from a rebase experiment, find the merge_group run for the exact current-HEAD tree. A change to name hints or mangling is cross-cutting.
- An expected-failure-list entry only reclassifies a `Fail`. A listed test that passes stays Pass, so a mis-scoped entry is XPASS noise, never a red build.
- `//TEST:LANG_SERVER` cannot observe published diagnostics in test mode. Verify LSP-diagnostic fixes with an A/B probe against real `slangd`.
- Storing an address is not a read: the uninit checker excludes pointer-typed value operands, keyed on the operand's data type. Sweep all of `tests/` for a broad frontend change.
- Converting `#ifdef X` to `#if X` can narrow platform coverage. Enumerate the platforms each arm selects, and check `_FAMILY` aggregates on both sides.
- Document what a guard guarantees, not how bad input arrives. Arrival-path claims are often wrong even when the guard is right.
- Slang ships no PBR/tonemap/gamma helpers. "Too bright" in a Blender→glTF scene is units and color management; a black debug visualization means NaN (`normalize` of a zero vector), not a zero vector.
- A fresh `git worktree` has no submodules, and `git submodule update` there rewrites the shared `core.worktree`, breaking sibling checkouts. Verify pins, then copy trees with `tar --exclude=.git`.
- Component types from different `ISession`s cannot be mixed in one `CompositeComponentType`. Creation checks only null-ness, returns `SLANG_OK`, and crashes later in `getEntryPointCode()`. To reuse a module across sessions, serialize it and deserialize it in the current session.
- Unsupported-and-unchecked is the dangerous quadrant. Establish it by grepping for the identity/validation check, not for a diagnostic name.

## DeepWiki Is a Hypothesis — Verify at the Pinned SHA

DeepWiki's RAG index can miss files that declare semantics in string literals (glslang `Initialize.cpp` / `Builtins.cpp`), because those chunks sit far from the declaration sites a question asks about. It also indexes `main`/HEAD, which can differ from the submodule pin. Before calling a code claim a "contradiction" with DeepWiki, fetch the file at the exact pinned SHA (`curl https://raw.githubusercontent.com/.../<pinned-sha>/<file>`) and grep it. A DeepWiki "no, X doesn't do Y" is a hypothesis ([deepwiki-can-miss-files-in-large-or-vendored-codebases-cross-check-source](../learnings/1779621016571-deepwiki-can-miss-files-in-large-or-vendored-codeb.md)).

DeepWiki also conflates cooperative-**vector** with cooperative-**matrix**. Asked about SM 6.10 `linalg` `InterlockedAccumulate`, it answers "yes" and cites CoopVec helpers, but `Matrix::Accumulate` and `Matrix::InterlockedAccumulate` are absent from `struct CoopMat` in `hlsl.meta.slang` (checked at HEAD). The `InterlockedAccumulate` string in the CoopVec prelude is a name collision. Confirm CoopMat coverage by reading `hlsl.meta.slang` ([CoopMat vs CoopVec linalg InterlockedAccumulate — DeepWiki conflates them](../learnings/1781544794615-coopmat-vs-coopvec-linalg-interlockedaccumulate-de.md)).

## IR Crash Diagnosis: Dump IR, Don't Trust the Stack Trace Alone

The frame nearest an IR-pass assertion is a starting hypothesis. A triage memo either includes a `-dump-ir` step against the repro before it commits to a fix site, or tells the fixer to verify with `-dump-ir` and ranks the candidates as hypotheses. Witness-table lookup in dynamic-dispatch specialization has five or more unguarded `findWitnessTableEntry` callers, so a "missing null check" is plausibly multi-site ([Don't trust the stack-trace-implied fix site alone — dump-IR the repro](../learnings/1780683697167-don-t-trust-the-stack-trace-implied-fix-site-alone.md)).

## Descriptor Heaps: `[noinline]` Specialization and the `ResourceDescriptorHeap` Surface

For shader-slang/slang#11498, `kIROp_SPIRVLoadDescriptorFromHeap` goes through the existing specialization allowlist sites (`isParamSuitableForSpecialization`, `getCallInfoForArg`, `getSpecializedValueForArg`) the same way `IRCastDescriptorHandleToResource` does. In `getSpecializedValueForArg`, the cloned callee reuses the hoistable heap global directly and parameterizes only the `index`, keyed on the result type. Parameterizing the heap global as a `uint` `OpFunctionParameter` makes a uint scalar the base of `OpUntypedAccessChainKHR`, which is invalid SPIR-V. Text-only FileCheck and green local tests miss this; `SLANG_RUN_SPIRV_VALIDATION=1` catches it ([Approach-A fix for descriptor-heap [noinline] texture params: reuse the hoistable heap global, do NOT parameterize it as uint](../learnings/1780769595819-approach-a-fix-for-descriptor-heap-noinline-textur.md)).

The descriptor-heap backend already exists behind `DescriptorHandle<T>`. `ResourceDescriptorHeap` and `SamplerDescriptorHeap` appear only as HLSL emit output (`slang-emit-hlsl.cpp:1328-1345`), so accepting them as input (slang#11568) is front-end surface work, not new codegen. The first design, magic globals whose generic `operator[]` returns `DescriptorHandle<T>`, fails with E39999: Slang solves a generic subscript's type parameter from the index arguments only, so a return-position-only `T` cannot be inferred ([Approach A is a dead end](../learnings/1781222607198-correction-resourcedescriptorheap-approach-a-retur.md)). The maintainer team chose a concrete proxy: builtin `UntypedResourceHandle` / `UntypedSamplerHandle` types that `ResourceDescriptorHeap[i]` returns and that implicitly convert to a resource, a sampler, or their handle types. For any context-typed builtin, return a concrete proxy, never a return-only generic ([#11568 now implemented via UntypedResourceHandle](../learnings/1782422418340-update-slang-11568-maintainer-team-now-implementin.md)).

## E31106/E31107 Fire on Compiler-Synthesized Entry-Point Uniform Groups

E31106/E31107 (locationless warnings about mixed-resource constant-buffer groups) also fire on a plain single-file compute entry point that mixes resource params with a `uniform` ordinary param. The offending `ConstantBuffer<>` is synthesized by `CollectEntryPointUniformParams::ensureCollectedParamAndTypeHaveBeenCreated()`. The warning targets user-authored mixed `cbuffer` / `[vk::push_constants]` groups, so firing on the synthesized group is over-eager. The recommended fix marks the synthesized struct and skips the diagnostic. `getConstantBufferType` is a deduplicated type-getter and cannot carry a per-instance `sourceLoc`, so the marker lives on the non-deduped `paramStructType` ([E31106/E31107 also fire on the SYNTHESIZED entry-point uniform param group (not just imported modules)](../learnings/1782751325517-e31106-e31107-also-fire-on-the-synthesized-entry-p.md)).

## Controlled-Rebase Experiments Mislead When the Change Is Cross-Cutting

"Unrelated" failures in a rebase-onto-master experiment do not prove a master regression. A change that looks isolated can be cross-cutting: qualifying extension-method name hints changes `getNameForNameHint`, which feeds SPIR-V debug names, every C-like emitter's identifiers, and diagnostic call-site notes, so it breaks any test that hard-codes an extension-method symbol name. The cheap decisive check is the merge_group run on branch `gh-readonly-queue/master/pr-<lastPR>-<sha>`, where `<sha>` is the parent of current master HEAD; that run tested the exact current-HEAD tree. If it is green, master is not red and the regression is in the experiment's own delta. Do this check before posting "master is red" to GitHub ([Controlled-rebase experiments mislead when the 'isolated' change is cross-cutting (name hints/mangling)](../learnings/1781841056611-controlled-rebase-experiments-mislead-when-the-iso.md)).

## Expected-Failure List Only Reclassifies a Fail

An entry in an `-expected-failure-list` file (`tests/expected-failure-coverage.txt`, `expected-failure-no-gpu.txt`) reclassifies a result only when `result == Fail`. A listed test that passes stays Pass. A non-platform-scoped entry on a platform where the test passes yields XPASS noise, with no failure count and no exit-code change. Before recommending that an entry be platform-gated as a correctness fix, check whether the test fails on that platform; if it passes, the entry is at worst cosmetic ([expected-failure list only reclassifies a Fail — never reddens a passing listed test](../learnings/1781641446803-expected-failure-list-only-reclassifies-a-fail-nev.md)).

## LANG_SERVER Harness Cannot Observe Diagnostics in Test Mode

The `//TEST:LANG_SERVER` harness cannot see published diagnostics: the `publishDiagnostics` throttle/debounce is disabled in test mode, so a FileCheck on diagnostics sees nothing. No committable automated regression test exists for an LSP-diagnostic bug (false or missing diagnostics on didOpen) through this harness. Verify against real `slangd` with an A/B probe (control vs fix branch) that compares the published diagnostic sets ([CORRECTION: //TEST:LANG_SERVER harness can't observe diagnostics in test mode (re #11532)](../learnings/1781116005493-correction-test-lang-server-harness-can-t-observe-.md)).

## Uninit Checker: Storing an Address Is Not a Read

In `getInstructionUsageType`, the operand-role split that counts a store's value operand (operand 1) as a read excludes pointer-typed values: `inst == user->getOperand(1) && !as<IRPtrTypeBase>(inst->getDataType())`. Storing a `Ptr(...)` value does not read the pointed-to memory, so flagging it gives a spurious E41016. The predicate keys on `inst->getDataType()` (the tracked operand), not on the user, because Store is void-typed. A shared frontend pass has a broad blast radius: run the full `tests/` sweep before pushing, not just the new test's directory ([Uninit-checker: storing an ADDRESS isn't a read; and run the FULL suite for broad-blast-radius frontend changes](../learnings/1782448931140-uninit-checker-storing-an-address-isn-t-a-read-and.md)).

## Macro Conversion: Presence→Value Can Silently Narrow Platform Coverage

When value-style platform macros move from `#ifdef X` / `defined(X)` to `#if X`, the old always-true presence test may have hidden that the chosen macro does not cover the intended family. For each arm, list the platforms the new macro selects against what the old test admitted. If one side uses a `_FAMILY` aggregate, check whether the sibling should too: `SLANG_APPLE_FAMILY` rather than bare `SLANG_OSX`, which dropped iOS from the dlfcn arm ([Converting presence→value macro tests can silently narrow platform coverage (iOS dropped from dlfcn)](../learnings/1782324227290-converting-presence-value-macro-tests-can-silently.md)).

## Discord Support: Graphics Fundamentals, Not Slang Bugs (PBR Gamma, Normal-Map TBN)

Two Discord support cases (one asker writing a PBR renderer from LearnOpenGL) share one fact: **Slang has no built-in PBR, tonemap, gamma, or color-space helpers**; this is the user's own shader code.

**PBR too bright and gamma off in a Blender-exported glTF scene** is units and color management, not shading math. (1) glTF `KHR_lights_punctual` stores light `intensity` in candela (lm/sr). Blender's exporter converts watts as `energy/(4π)` and, in the default **Spec** lighting mode, also multiplies by 683 (`PBR_WATTS_TO_LUMENS`), so intensities reach hundreds of thousands, hence the user's `/1000` fudge. Fix: keep physical intensities plus one scene-wide exposure multiply, or re-export with Lighting Mode = **Compat**. (2) Gamma has two independent causes: sRGB encoding applied more than once (a manual `pow(c,1/2.2)` on top of sRGB textures and an `*_SRGB` target; encode exactly once), and Blender's default view transform being **AgX** (Filmic on older builds), not Reinhard `x/(x+1)`. Match Blender by setting View Transform to **Standard** or by implementing AgX in-shader ([Blender→glTF PBR too-bright + gamma mismatch: candela units, exposure, AgX view transform](../learnings/1784300430455-blender-gltf-pbr-too-bright-gamma-mismatch-candela.md)).

**Normal-map / TBN debugging** found two bugs. Bug 1 is `mul` argument order: `float3x3(T,B,N)` puts the vectors in rows, and `mul(matrix, vector)` treats the vector as a column, so `mul(TBN, float3(0,0,1))` returns `(T.z,B.z,N.z)`. The fix is `mul(float3(0,0,1), TBN)` ≡ `mul(transpose(TBN), v)` (see `docs/user-guide/a1-01-matrix-layout.md`; the row/column-major memory-layout mode is irrelevant to matrices built in-shader). A flat `(0,0,1)` test exercises only the N row, so "flat works" does not validate the tangent basis. Bug 2, the real one, is a missing tangent attribute: `float4(T*0.5+0.5,1)` rendered black, not gray, and black means NaN from `normalize((0,0,0))` (an unbound vertex attribute reads as zero). Fix it with CPU-side tangents (MikkTSpace, assimp `aiProcess_CalcTangentSpace`) or derive TBN in-shader from `ddx`/`ddy` (Slang supports `OpDPdx`/`OpDPdy` on SPIR-V and Metal). The reusable ladder for "normal map wrong" in any shader language: test flat `(0,0,1)` (mul order and N only); render the raw sampled normal as color (light blue means the texture data is fine, which isolates sRGB/BC5/format issues from the basis); render T, B, N each as color (black = NaN, guard with `if (dot(t,t) < 1e-6)`; flat gray = constant or degenerate) ([Slang normal-map/TBN debugging: mul arg-order + NaN-tangent chain](../learnings/1784305210428-slang-normal-map-tbn-debugging-mul-arg-order-nan-t.md)).

## Precompiled `.slang-module` Import: Resolution Order, and Serialization as a Diagnostic-Escape Hatch

On shader-slang/slang#12378 (new `E55216`, "function-typed value is not supported on this target"), one declaration gives three results by delivery path. Same file: `error[E55216]`, rc=255. Imported as `.slang` source on `-I`: the same error. Imported as a precompiled `.slang-module`: rc=0 and no diagnostic, with `Slang_FuncType<int32_t, int32_t> gModFn_0;` in the C++ output and `var<private> gModFn_0 : ;` (the #12367 empty-type failure) in WGSL. The hole is serialization losing `sourceLoc`, not "cross-module" in general. Both module-level arms in `slang-ir-check-unsupported-inst.cpp` (struct field on `field->getKey()->sourceLoc`, GlobalVar on `globalInst->sourceLoc`) skip a value whose location is invalid, and that check is the only thing between the shape and emit. Nine type shapes were all handled; only changing how the declaration arrived reached the hole. A `diag=` test cannot express a locationless diagnostic (annotations match columns on a source line), so only a `.expected` comparison pins it; the pre-fix baseline records `result code = 0` with empty stderr. A location fallback is not a fix: `findFirstUseLoc` recovers nothing for a deserialized declaration, because its uses are the module's own locationless insts (instrumented, both `sourceLoc.isValid()` and `firstUseLoc.isValid()` were 0) ([functype global from a precompiled .slang-module escapes the #12378 E55216 check](../learnings/1785989877894-slang-a-functype-global-imported-from-a-precompile.md)).

That experiment is readable only because the import path was proven. Measured with `slangc <consumer> -target cpp -I <moddir> -I <srcdir>`: a `.slang-module` beats `.slang` source for the same module name (rc=0, no diagnostic, same as module-only; source-only gives rc=255). With no `-I`, resolution falls back to cwd. This defect produced both failure directions on one PR: a stale `.slang-module` in the "source" pole made both poles look escaped, and a consumer beside the source made the "module" pole re-run the source pole. The setup that works: `.slang` and `.slang-module` in separate directories with absolute paths, per-pole consumer copies, and a first run with no `-I` that must print `error[E00001]: cannot open file 'mod_lib.slang'` before any pole result counts. `.slang-module` is gitignored (`.gitignore:51`), so a stale one is invisible. For any delivery-path variable (include paths, module caches, `PATH`, symlinked configs), state the resolution order you depend on and prove the negative case breaks; an unproven control fails in both directions, and one of the two tables was right only by luck of layout ([a .slang-module beats .slang source on -I](../learnings/1785991288743-slang-import-resolution-a-slang-module-beats-slang.md)).

## Ways a slang-test Result Lies: Ignored Baselines, Prelude-Matched Names, Unpinned Exit Codes

**`*.expected` is gitignored** (`.gitignore:39`, with `*.actual` and `*.expected.png`). All 180 tracked baselines were force-added, and `.gitignore:34-36` admits that enumerating the exceptions "is hard." `git add <dir>` and `git add -A` skip a new baseline and `git status` never lists it, while the sibling `.slang` stages and the local run passes from disk. Use `git add -f` and verify with `git ls-tree -r <sha> | grep my-test`. A missing baseline fails loudly: `runSimpleTest` synthesizes `"result code = 0\nstandard error = {\n}\nstandard output = {\n}\n"` (`tools/slang-test/slang-test-main.cpp:2187-2190`) and `TEST:SIMPLE:` compares it strictly (`:2132`), so a test whose point is a compiler error fails 0/1 on CI's first run. The scarier reading ("it passes only if the fix does nothing") came from reading those two sites without running them, and had the polarity wrong. Only a checkout of the pushed commit sees what a reviewer sees (`git worktree add --detach /tmp/verify <sha>`, empty `git status --porcelain`, then `slang-test -bindir …`); on #12378 the working tree reported `744/744` where the commit was `743/744`. Generate a `.expected` from a real run, never by hand (comparison is byte-exact, so a plausible `255` fails where the harness records `-1`), and confirm by moving it aside and diffing the fresh `.actual`. A pre-fix crash proves the test fails without the fix, not that the baseline's content is right ([gitignored .expected makes slang-test fail 0/1](../learnings/1785987659514-a-gitignored-expected-file-makes-slang-test-fail-0.md), [gitignored .expected can be missing from the commit while git status says clean](../learnings/1785987524819-a-gitignored-expected-can-be-missing-from-the-comm.md)).

Peer review on #12367 found two more assertions that cannot fail, after a green suite. **On a target that emits its prelude verbatim, a prelude-defined name is not an anchor.** `//CHECK: Slang_FuncType` on `-target host-cpp` matches the prelude: `host-cpp` is `ArtifactStyle::Host`, so `isHeterogeneousTarget` holds and `slang-emit.cpp:2942` emits `get_slang_cpp_host_prelude()`, which defines the name at `prelude/slang-cpp-host-prelude.h:63`. A shader without `[DllImport]` emits the name once; with it, three times. Anchor on a body-only declaration (`//CHECK: Slang_FuncType<{{.*}}> {{.*}}= nullptr`) and prove it both ways: against the no-`[DllImport]` control the new anchor fails 0/1 while the bare name passes 1/1. Grep `prelude/*.h` before asserting a symbol in emitted output. **`diag=` never asserts the exit code; `TEST:SIMPLE(filecheck=)` can.** `_diagnosticAnnotationTest` (`slang-test-main.cpp:840-844`) receives no result code and reads only the `standard error = {` block, so a `diag=` test passes if the compiler emits the diagnostic and then crashes. A 2026-07 probe (`//CHECK: result code = 255` → 0/1) concluded `filecheck=` cannot see the code either, but on master (2026-10-24, `52e29ab43b`) `runSimpleTest` hands `getOutput()` to `_validateOutput` → `_fileCheckTest`, and `getOutput()` opens with `result code = X`; so under `TEST:SIMPLE(filecheck=)` a first `CHECK: result code = 0` does pin a clean exit, as #13507 review advised ([filecheck=A,B is one prefix; add `CHECK: result code = 0` first](../learnings/1791427324960-slang-test-filecheck-a-b-is-one-prefix-the-second-.md)). The failed probe most likely asserted the wrong code; check the `.actual` for the real value before pinning a non-zero one. Plain `//TEST:SIMPLE:` with a `.expected` also pins it (precedent `tests/spirv/direct-spirv-emit.slang.expected`). This matters when a fix turns a segfault into a diagnostic: `diag=` proves the message, the result-code line proves the crash is gone. Promote the baseline from `slang-test`'s `.actual`, and never commit `.actual` (`.gitignore:38`). Pick the harness by the property you need pinned, not by what the directory usually uses ([prelude-matched names and exit codes no harness checks](../learnings/1785987113227-two-ways-a-slang-test-assertion-lies-prelude-match.md)).

## Cross-Session Component Types: Unsupported-AND-Unchecked Is the Dangerous Quadrant

A module loaded on one `ISession` cannot go into `createCompositeComponentType` on another (a user wanted this to fan specialization across threads), and nothing says so. `source/slang/slang-session.cpp:390-443` checks only null-ness (`Diagnostics::NullComponentType` at `:415`, `:430`). Grepping the file for `getLinkage() ==`/`!=`, `m_linkage ==`/`!=`, `!= this`, `getSession() !=` finds nothing, and no `SLANG_ASSERT` checks linkage identity, so the call returns `SLANG_OK` and the program crashes later in `getEntryPointCode()`. Maintainer `csyonghe` on #8437 (open): *"component types created from different sessions cannot be mixed together in a single CompositeComponentType… you must first serialize that module, and deserialize it from the current session."* Pass that remedy on.

| | checked | unchecked |
|---|---|---|
| **supported** | fine | fine |
| **unsupported** | clean error, found immediately | ⚠️ UB / crash far from the cause |

A user told only "unsupported" about the bottom-right cell blames their own code when the crash comes, so say "and nothing will diagnose it." Find the quadrant by grepping for the identity or validation check (`==`/`!=` on the owning object), not for a diagnostic name; an assert or an early `SLANG_E_INVALID_ARG` also counts as checked. To prove a lock is absent, enumerate every lock in the file, since a caller could hold one. Read the threading docs rather than infer the obvious rule: Slang requires one global session per thread (`docs/user-guide/08-compiling.md:720-721`, extended to "objects created from them" at `:1011`; `include/slang.h:4071-4074`). The experimental carve-out at `:1015-1028` (serial front end, then `getEntryPointCode` / `getTargetCode` / `getTargetMetadata` / `getResultAsFileSystem` concurrently after `link()`) can save a threading design by moving the thread boundary later ([unsupported-and-unchecked is the dangerous quadrant — grep for the identity check, not the diagnostic](../learnings/1786245351511-unsupported-and-unchecked-is-the-dangerous-quadran.md)).

## Document a Guard's Guarantee, Not Arrival Paths

When a guard rejects X regardless of how X arrived, document the guarantee ("drops X regardless of provenance"), not an enumeration of arrival paths. An arrival-path claim is a checkable statement about compiler behavior and can be wrong while the guard is right: in one three-round review, three successive explanations of why a foreign-FileDecl case was impossible were each wrong, and the guard conjunct was correct throughout ([Document a guard's guarantee, not the enumeration of how the bad input arrives](../learnings/1780493380222-document-a-guard-s-guarantee-not-the-enumeration-o.md)).
