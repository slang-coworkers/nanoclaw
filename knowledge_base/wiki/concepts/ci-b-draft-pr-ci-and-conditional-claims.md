# Draft-PR CI, Priority-Yield, and Conditional Claims

Why a slang bot draft PR shows no CI signal (draft gate, priority yield, the `waiting`-run deadlock), what an agent may and may not do about it, and the claim-hygiene rules that came out of getting it wrong.

## TL;DR

- **On a slang bot draft PR with no CI signal, nothing about your push cadence is the lever.** A draft gets no `pull_request` CI *by design* (jobs gate on `draft != true`); manual `workflow_dispatch` runs *yield* while higher-priority CI is active (`priority-gate-yielded`); and the retry that would rerun them is blocked whenever *any* repo CI run is active — including a run parked on a manual environment approval, because `waiting ∈ ACTIVE_STATUSES`. The earlier "pushing starves your own CI" mechanism was published, propagated to a public PR body, and is **RETRACTED** — the branch it blamed never executed.
- **Since ~2026-10-01 bot dispatch CI has run no build/test.** 80–135 `waiting` runs (bot dispatches plus approved PR and fork runs parked on `falcor-ci`) drain only by GitHub's 30-day timeout while more arrive every day, so a bot draft's "CI SUCCESS" is `filter` + `check-ci` only: count non-skipped jobs, not the conclusion. The fix is the open, unreviewed PR #12738 — point owners at it instead of proposing another.
- **It is a deadlock, not a slow queue.** The retry lists only `completed` runs, counts `waiting` as active, and the 12 h yield escalation runs only at run start, so nothing ever retries a stuck dispatch, not even after the 30-day expiry completes it (outside the lookback, and `failed_only_because_priority_gate` is false). #12738 fixes only the `waiting`-as-active half. Re-dispatching or merging master gives no signal. Only a `falcor-ci` approval plus `gh run rerun --failed`, or a maintainer's ready-flip, unblocks it. Cancelling a yielded run is not a lever: the cancelled gate job makes it permanently ineligible for the retry. Report it as infra and never ready-flip yourself. Only bot *dispatches* are throttled: a bot ready-for-review PR's `pull_request` run gets the full matrix.
- **After a push to a non-draft slang PR, never also `gh workflow run ci.yml`.** The push already starts `pull_request` CI. The bot dispatch yields, its `check-ci` completes `failure`, and branch protection counts every `check-ci` on the head, so the PR stays BLOCKED even after approval. Only entering the merge queue clears it. Push only and cite the `pull_request` run id.
- **Don't feed the jam or overclaim it.** On a 30-day falcor-gate expiry webhook, leave the draft and report once; merge master only on maintainer action or when master touches the PR's files. Never say a yielded `waiting` dispatch "will be rerun". Never dispatch `cmake-options.yml` (~478 jobs) for a draft: it blocks the merge queue.
- **"CI re-triggered" on a bot draft is not a verification signal** — the run waits on the priority yield and the `falcor-ci` approval until a human marks the PR ready; verify locally. A "passing run" on a draft may be the PR Maintenance workflow, not build/test: check `workflowName`. Asked to "rebase" a PR under review, or blocked on BEHIND, merge `origin/master` instead of force-pushing (maintainer request), confirm `behind_by: 0`, and say so.
- **When a scheduled job writes its decision to a log on every fire, READ THE LOG.** Source says what *could* happen; the log says what *did*. The retracted mechanism was about a code path that fired 0 of ~100 times; one `gh run view --log` would have discriminated in seconds. Citation-checking measures accuracy, not causality — two reviewers verified the line numbers and none could catch an unexecuted branch.
- **Name the enabling condition inside any absence/negative claim.** "No CI ran on this head" was true at every measurement and false 4 seconds after a maintainer flipped the PR out of draft. A conditional observation stated as a property of the artifact is unfalsifiable by the reader.
- **CI terminal is not chain terminal.** A maintainer approved and answered the review's central question 6 minutes before two agents declared the chain closed — because their watchers were armed on the workflow run, nothing on the PR's review state.
- **The `evicted` wake payload has TWO failure modes** — false positive (wasted investigation, loud) and false negative (a PR stranded green-headed, silent). Re-derive evictions independently every sweep; a precision-only score hides the lossy half.
- **A matching workload/test name is not a matching regression** — verify the time window and magnitude overlap before citing prior art.

## The draft-PR / priority-yield mechanism (corrected)

The accurate account after two retraction/correction passes: [RETRACTION — the published draft-PR CI mechanism is wrong](../learnings/1786001875366-retraction-the-draft-pr-ci-mechanism-i-published-i.md) [CORRECTION: pushing does NOT starve draft-PR CI; `waiting` counts as active](../learnings/1786002067914-correction-pushing-does-not-starve-draft-pr-ci-the.md)

1. **A draft PR has no `pull_request` CI by design.** `.github/workflows/ci.yml:15` gates the `filter` job on `github.event_name != 'pull_request' || github.event.pull_request.draft != true` (repeated at `:681`), and every build/test job `needs: filter`. Those skips are expected, not evidence; hence the manual-dispatch convention.
2. **Bot `workflow_dispatch` runs yield while higher-priority CI is active** (`ci.yml:99-101` sets `IS_THROTTLED_BOT` only when the event is `workflow_dispatch` AND `triggering_actor` is `nv-slang-bot[bot]`). The run shows three non-skipped jobs: `filter: success`, `wait-for-human-priority: failure`, `check-ci: failure`, reason `::error::priority-gate-yielded`. Benign.
3. **The retry is blocked whenever *any* repo CI run is active.** `main()` in `extras/ci/retry-yielded-bot-ci.py` calls `any_active_ci(...)` and returns at `:187-193` (`CI is still active (N run(s)); not rerunning bot CI.`) **before candidate selection.** `ACTIVE_STATUSES` includes **`waiting`** (`ci_priority_common.py:29`) and the query is repo-wide, so **one run parked on a manual environment approval suppresses bot retries repo-wide until a human clicks.** Measured: a `falcor-vet-approve-gate` run parked ~2.45h on a `falcor-ci` approval blocked 20 consecutive retry fires.

⇒ **Push cadence is not the lever; don't hold work back for it.** A *non-draft* bot PR takes the `IS_THROTTLED_BOT != true` path and does not yield (`wait-for-human-priority: success`, 36 non-skipped jobs; its `pull_request` run gets the full 44-job matrix), so the starvation hits bot drafts only ([only bot drafts are throttled](../learnings/1792486355939-ci-sweep-snapshot-misses-jobs-in-waiting-runs-only.md)). That flip is human/operator-gated; don't push to work around it. Don't hand "nudge CI" to the fixer as an action item; a local build of the head is load-bearing on an active draft (state its single-configuration scope honestly).

**On a non-draft PR the fast path is the `pull_request` run only; a bot dispatch still yields and its red check BLOCKS merge.** After a push, do not also run `gh workflow run ci.yml --ref <branch>`: the dispatch is `IS_THROTTLED_BOT`, so `wait-for-human-priority` fails, build/test skips and `check-ci` completes `failure`. Branch protection counts every `check-ci` check-run on the head sha and the green `pull_request` one does not override it, so the PR shows `mergeStateStatus: BLOCKED` even after approval (#13782, #13801, #13849 on 2026-10-22; #11387 on 10-23, dispatch 7 s before the `pull_request` run). `retry-yielded-bot-ci.py` never clears it while `waiting` runs exist, and a full-matrix rerun is wasteful; a maintainer entering the merge queue clears it because the merge-group run replaces the check. Push only and cite the `pull_request` run id; if you already dispatched, say the red `check-ci` from run `<id>` is a stale bot dispatch that the merge queue clears ([never dispatch ci.yml on a non-draft PR after a push](../learnings/1792758459493-never-workflow-dispatch-ci-yml-on-a-non-draft-slan.md)).

### Since ~2026-10-01 the jam is a permanent deadlock

**Backlog.** On 10-18, 85 slang CI runs sat at `falcor-build-approval-gate` (environment `falcor-ci`): 80 bot dispatches plus 5 human fork runs back to 09-16 (76 on 10-19), so every `ci-retry-yielded-bot` fire (hourly at :17, plus on CI `workflow_run`) logs `CI is still active (85 run(s)); not rerunning bot CI`. It drains only through GitHub's 30-day pending-deployment timeout ("The deployment was rejected or didn't satisfy other protection rules") while bot dispatches add ~6/day, so it never reaches 0 unless a CI owner approves or cancels. A cancel drains the count but leaves that PR with no result: a `cancelled` gate job makes `failed_only_because_priority_gate` false, so an agent never cancels its own yielded run to get a retry [don't cancel a yielded run at the falcor gate](../learnings/1793328120073-do-not-cancel-a-yielded-bot-ci-run-waiting-at-the-.md). Meanwhile a bot draft's "CI SUCCESS" covers only `filter` + `check-ci` and REUSE/board-sync (48 jobs skipped; docs-only drafts pass legitimately via the path filter), so count non-skipped jobs, not the conclusion, before calling it green or comparing it with a human PR ([no build/test since 10-01](../learnings/1792313744673-slang-bot-draft-ci-has-run-no-build-test-since-10-.md)). The gate came from #11620; the fix is shader-slang/slang#12738 by szihs ("don't treat "waiting" runs as active in the bot-CI priority gate", 1 file, +14/−1), open since 08-25 with 0 reviews, no requested reviewers, 300+ commits behind. Point CI owners at it rather than proposing a new fix ([fix PR #12738 exists](../learnings/1792399653342-slang-bot-draft-ci-starvation-fix-pr-12738-exists-.md)).

**Three independent causes (checked against the scripts 2026-10-20).** (1) The pending falcor gate keeps the run `status=waiting`, never `completed`, and `retry-yielded-bot-ci.py` lists only `status=completed` workflow_dispatch runs. (2) `fetch_active_runs` in `ci_priority_common.py` counts `waiting` as active, so stuck runs block each other. Human fork PRs feed the set: an approved fork `CI` run builds and tests (43/44 ✅ on 10-27) then parks `waiting` on `falcor-build-approval-gate` (required reviewers `ci-approvers`; read `/actions/runs/<id>/pending_deployments`) ([approved fork runs park on falcor-ci](../learnings/1793090644449-slang-ci-closed-fork-pr-turns-its-unapproved-runs-.md); its closed-fork 0-job failures are on [query confidence](ci-github-query-confidence-and-gates.md)). A maintainer bulk-approved 34 on 10-27, each holding the retry off for up to 30 days ([watch-list sweep](../learnings/1793177249369-watch-list-sweep-judge-a-ci-delivery-fix-by-the-ra.md), [bulk approval saturates CI](../learnings/1793176887944-bulk-approval-of-parked-fork-ci-runs-saturates-sla.md)). On 10-29, 135 `ci.yml` runs were `waiting` (three pages at `per_page=100`; one page misses a third): 78 yielded bot dispatches and 57 `pull_request` runs parked after their gate succeeded; every fire logged `CI is still active (137 run(s))`; check with `gh run view <retry run id> --log | grep "CI is still active"`. Cause (1) outlives the expiry: the completed run is outside the 16 h lookback and `failed_only_because_priority_gate` is false (run 36526246596, #13305; 40804024110, 40780863789, 40732468787 still `waiting`), and it is past GitHub's 30-day rerun limit, so new CI needs a fresh dispatch ([never auto-retried while gate pending](../learnings/1793251805673-yielded-bot-ci-runs-are-never-auto-retried-while-t.md)). #12738 removes only cause (2). A fix for (1) making the falcor gate depend on `wait-for-human-priority` must also make the `build-...-falcor` job's `always() && result in (success, skipped)` opt-in require `wait-for-human-priority` success, or a yielded run builds Falcor without approval ([retry disabled by waiting runs, 10-29](../learnings/1793252623672-yielded-bot-ci-retry-is-disabled-by-waiting-runs-a.md)). (3) The 12 h `--max-yield-hours` escalation in `wait-for-priority.py` runs only at run start/restart, so it never fires.

**What unblocks it.** Over 7 days the bot made 96 dispatches: 0 reruns, 0 reaching build/test (the few "success" runs ran 2 jobs). Re-dispatching or merging master yields the same way. It unblocks only when (a) a `ci-approvers` member approves `falcor-ci` and someone runs `gh run rerun <id> --failed` (approval alone does nothing; build/test already skipped), or (b) a maintainer marks the PR ready or starts CI (`pull_request` CI is not throttled). Never tell anyone "retry-yielded-bot-ci will rerun it" ([not rerun while 'waiting'](../learnings/1793105473572-a-priority-yielded-bot-ci-yml-dispatch-on-a-draft-.md)); never mark a PR ready yourself to get CI ([dispatches deadlock behind falcor-ci](../learnings/1792519787823-slang-ci-bot-workflow-dispatch-runs-deadlock-behin.md)). Each timeout fires a `github.ci_failed` webhook for a possibly long-superseded head ([webhook staleness](../concepts/agent-b-staleness-webhooks-supervisor.md)). On that 30-day expiry webhook on a bot draft (#12479, #12542, #12647, #13127, #13130, #13189, #13201, #13202), leave the PR and report once as infra: merging master moves the head away from what reviewers saw and a new dispatch adds another `waiting` run. Merge master only when a maintainer asks, re-reviews or marks ready, or when master changes the PR's files (#12479, where #13378 touched `slang-check-conversion.cpp`) ([30-day expiry: don't merge master](../learnings/1792609273772-falcor-gate-30-day-expiry-on-a-bot-draft-don-t-mer.md)).

**Say exactly what a yielded dispatch has done.** It shows `wait-for-human-priority=failure`, build jobs `skipped`, `falcor-build-approval-gate=waiting`, and the run stays `waiting`; "it will be rerun later" is an overclaim. Say: builds skipped, no upstream result yet, retry only if the run completes and CI is quiet. The dispatch filter diffs only `HEAD^1`, so keep a code/test commit at the head or the matrix skips as docs-only and reports success (PR #13826; codex OUTPUT_REVIEW caught it) ([yielded dispatch not auto-rerun](../learnings/1792623521995-slang-ci-a-yielded-bot-workflow-dispatch-is-not-au.md)). Don't reach for a bigger workflow: `gh workflow run cmake-options.yml` launches ~478 jobs, fills the org's 60 hosted runners and blocks merge-queue CI (#13839 waited 35+ min; slang-discord-support flagged CRITICAL); it dropped `merge_group` for this reason and runs weekly. Don't dispatch it for a draft even if a triage brief lists "cmake-options-matrix entries"; check whether the matrix exercises the change at all (#13827 built only pinned mimalloc v2.1.7, not the v2.5.2 path). A mistaken dispatch takes ~60 s after `gh run cancel <id>` to show cancelled ([don't dispatch cmake-options.yml for a draft](../learnings/1792633007029-don-t-dispatch-cmake-options-yml-cmake-options-mat.md)). Dispatch runs skip the `pull_request`-only via-glsl and examples steps, understating wall-clock; see [Windows GPU slang-test jobs](ci-windows-gpu-test-job-split-and-merge.md).

**"CI re-triggered" on a draft is not verification.** A `CI` run on a long-lived bot draft sits `waiting` behind the yield and the `falcor-ci` approval (`ci-approvers`) until a human marks the PR ready (#13130's month-old run hit the 30-day limit). Report "waiting on the approval gate" and verify locally (container GPU for vk/cuda). A "passing" draft run may be PR Maintenance, not build/test; check `gh run view <id> --json workflowName` (wrong on #13883, 2026-10-23) ([passing draft run is often PR Maintenance](../learnings/1792764974147-slang-pr-a-passing-run-from-a-draft-is-often-pr-ma.md)). Asked to "rebase" a pushed PR under review, merge `origin/master` instead: a rebase needs a destructive force-push with explicit session authorization, and jhelferty-nv asked the bot to merge from master (shader-slang/slang#12194, comment 5145911960). Confirm `behind_by: 0` via the compare API and tell the requester about the deviation ([merge master instead of force-push](../learnings/1792261602957-bot-pr-on-shader-slang-slang-ci-matrix-waits-for-r.md)). Likewise when auto-merge is blocked on BEHIND: the owner merges master, never rebase + force-push ([PR Maintenance atom](../learnings/1792764974147-slang-pr-a-passing-run-from-a-draft-is-often-pr-ma.md)).

### What was wrong, and the method lesson

The retracted claim: `has_newer_run_for_branch()` makes every push disqualify the prior yielded dispatch, so "responding promptly to review starves the CI you're waiting for." **The line numbers were accurate; the causal conclusion did not follow**: the check compares candidates *within a branch*, so a branch's newest dispatch always survives (all 27 branches with yielded dispatches kept exactly one). Across 100 consecutive fires the verdict was `CI is still active` 98×, `Rerunning` 2×, and the blamed branch **0×**.

- **When a script logs its decision on every fire, read the log, not just the source.** Ask: *does the branch I'm blaming ever execute?*
- **Citation-checking measures accuracy, not causality.** Two reviewers verified the line numbers; that cannot catch an unexecuted branch.
- **When you publish a mechanism, name the discriminator that would falsify it.**
- **Blast radius:** within 9 minutes the wrong mechanism reached a 56 KB review artifact, a shared learning, a triager who relayed it, and a public PR body where a fixer changed his behaviour. A mechanism from an authoritative tier carries weight peers cannot audit past the citations.

(Enumeration caveats: `gh run list --branch` cannot see amended-away SHAs, and `statusCheckRollup` can report 0 failing while `commits/<sha>/check-runs` reports 2.)

## Name the enabling condition — a conditional observation is not a property

For three review rounds on slang #12353, "zero build/test jobs have executed on this head" was item 1 of the operator summary: accurate at every measurement, and **false 4 seconds** after the maintainer flipped the PR out of draft (13 jobs green, 5 running). It was a *consequence of draft state*, not a property of the change, and since it never named that gate it could not expire. Posting "nothing tested, distrust the green checks" after the flip would tell a human to distrust a real full-matrix signal [conditional observation stated as a property](../learnings/1785966205857-a-conditional-observation-stated-as-a-property-no-.md).

The defect class is a conditional observation stated as a property of the artifact: not wrong, but unqualified and unfalsifiable by a reader. Rules:

1. **Name the enabling condition inside any absence/negative claim.** "No X **because** Y" self-expires when Y changes; if you can't name Y, you measured an absence without knowing its cause.
2. **Re-check absence claims after any upstream state change**: draft→ready, a label, a branch move, a token rotation, a config flip.
3. On a draft PR, "CI red" is usually the priority-yield gate and "CI absent" the draft gate. Neither is a code signal; say which.
4. **Positive counterpart:** state a resolving signal as positively as the absence ("first full matrix on a head carrying this change, N/N green").

Tool gotcha: `gh run` `conclusion` is empty/null both "in flight" and "finished with no result", so a tally on `conclusion` alone drops in-progress runs; `status` distinguishes them; use `.conclusion // "RUNNING"`.

## CI terminal is not chain terminal

A PR review chain reached terminal CI (34 of 37 jobs green) and two agents moved to close it. **The maintainer had approved six minutes earlier and answered the review's central question** (extend to sibling functions or keep narrow?) in the same comment: "approve and merge as is. Please make another PR for the follow up". Their watchers were armed on the workflow run, nothing on the PR's review state, so the resolving event went unobserved (one agent had compacted its context inside that window) [CI terminal is not chain terminal](../learnings/1785970543490-ci-terminal-is-not-chain-terminal-a-maintainer-app.md).

1. **Before declaring a chain closed, re-read live PR state**: `reviewDecision`, `reviews[]`, comments since your last check. CI terminal is one input, not the verdict.
2. **A peer announcing a context compaction is a trigger to re-verify and re-brief**: anything inside their window is gone from their context and still true.
3. **Set the resume trigger on what actually advances the chain** ("maintainer merges, or the follow-up PR needs writing"), never anything CI-shaped.
4. **A state a human deliberately set is only theirs to change.** `mergeStateStatus=BEHIND` on an approved head belongs to the maintainer; force-pushing a rebase can dismiss the approval. When auto-merge is blocked only by BEHIND, the owner merges master (no force-push).

Bonus trap: the maintainer's framing ("apply the fix to all other sibling functions whose return type is `SlangResult`") was base-class framing that can't reach an implementation inheriting the interface directly, the same subclasses-vs-implementors enumeration defect four agents had made. A maintainer's framing gets less scrutiny than a peer's, so it needs the same check.

## The `evicted` wake payload is lossy, not merely noisy

The stored position on the slang CI wake payload's `evicted` field ("0-for-7, treat as ABSENT, always wrong") was incomplete: one sweep it named #12309 with the correct `mergeGroupRunId` (a real eviction) *and* omitted #12363 (a real `failed_checks` eviction, still stranded 20h later with a green head): precision 1/1, recall 1/2 [`evicted` can be a FALSE-NEGATIVE](../learnings/1786011778780-wake-payload-evicted-can-be-a-false-negative-not-o.md).

A **false positive** wastes investigation (loud, self-correcting); a **false negative** leaves a PR stranded green-headed with nothing prompting a look (silent, indistinguishable from "no evictions"). A precision-only score reads as fully characterized while recall was never measured. **Re-derive evictions every sweep** whatever `evicted` says (including `[]`) by enumerating `RemovedFromMergeQueueEvent` over recent merge-group branches; treat the payload as a hint, never the population. Report precision and recall separately; "0-for-N" collapses them.

## A matching name is not a matching regression

A user reported an `api_many_kernels` perf regression from 2026.5 to 2026.7. Prior-art search found one open issue on that workload (#12139), even naming the same phase (`apiLoadModule`), and it was nearly cited as "tracked here". Wrong issue: #12139's window is the ToT boundary 2026-07-15→07-16, while v2026.5 published 2026-03-19 and v2026.7 2026-04-21, and it is +6% vs the user's +400% with a different dominant phase [matching name is not a matching regression](../learnings/1786036897742-a-matching-workload-test-name-is-not-a-matching-re.md).

Before citing prior art, verify its window *overlaps* the reporter's (fetch `/releases` publish dates and the suspect PR's `merged_at`) and check magnitude: a benchmark name is a measurement surface for many regressions. "No tracking issue exists" needs a why (here the workload was added months after v2026.7 shipped, and the dashboard's release axis is a retrospective replay of downloaded binaries, so an untracked regression there is expected). When a chart is your only source, say the numbers are chart-derived and cross-validate against any ratio the page publishes.
