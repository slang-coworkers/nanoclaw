# Agent Routing: Chain Parking and Bot Detection

Why a chain parked on an external party has no observer, the silence fallback it needs (an absolute date plus a named terminal act, written where the chain is read), and three GitHub-observability traps a supervisor/watcher hits: keying a watcher to a captured SHA, the draft-PR rollup-vs-check-runs split, and a closed-set allowlist for bot detection.

## TL;DR
- **A chain parked on an external party's reply has no observer on the branch where that party never replies.** No event means no webhook delivery, and a sweep correctly leaves a "looks parked" chain parked; a chain parked forever looks like one parked appropriately until a human asks.
- ⇒ **Set the silence fallback in the same act as the gate:** an absolute date ("if silent by 2026-08-21"), a named terminal act (close as answered, escalate, or proceed) so the next session executes instead of re-deliberating, written where the chain is read (issue comment or chain memo), not only in a scheduler.
- **Audit before arming.** The fallback is usually a written exit condition, not a new cron. "Will I hear if something happens?" is usually yes (verify the path fired before); "will I notice if nothing happens?" is almost always no.
- **For a quiet external requester the terminal act is close-as-answered, no nudge.** Closing is cheap and reversible (a substantive human comment re-opens the chain). An internal party or routed maintainer may be nudged, justified by deviation from the repo's norm, never by a day count.
- **Every internal park needs a timer.** A coworker's "will report when the PR opens" ack is not one (a stopped container never reports); arm an `ncl tasks create --process-after` re-chase that checks GitHub. When a blocker is disproved in one thread, wake every session parked on it with a pinned GO.
- **A maintainer-owned park needs no more timers.** Once a maintainer is assigned and the bot's comment lays out the options, webhooks deliver everything; after one silent re-check, report "still parked" and stop scheduling.
- **A one-shot timer session cannot see the owner's progress.** It reads live state first (branch PR + head SHA, fix memory, comments newer than the last bot comment) and reports only what is newer; a consumed answer is "not actionable: already handled in PR #N", never a re-dispatch.
- **A re-chase reads the recipient's sessions, not its own inbox**, newest-first on the canonical thread; the follow-up task names the recipient's session id.
- **There is no CI-green webhook** (`github.ci_failed` is failure-only); a step waiting on green CI needs a one-shot `--process-after` re-check of the run's conclusion.
- **A parked merge-conflict PR's re-check records the main sha it saw**, so the next measures drift with `compare/<last-seen-main>...main` filtered to the conflict files, no clone.
- **A parked issue's re-check reads `issues/<n>/timeline` and `issues/<n>/events`, not only comments** (self-assign, milestone, linked/merged PR; real `assigner`). An assignee owns the decision: no ping, no further re-check; a silent self-assign names an owner, not a direction. Also search the org for the issue URL, check `parent`/`sub_issues` and spec PRs for design issues, and re-test "not in a release yet" claims against the latest tag.
- **Key a PR watcher to the PR NUMBER, not a captured SHA**; a force-push blinds a SHA-keyed guard, which then reports on a dead commit forever.
- **On a draft PR, `statusCheckRollup` and `commits/<sha>/check-runs` differ:** a `workflow_dispatch` matrix appears only in `check-runs`, so cite the run id and `check-runs` as coverage evidence.
- **A closed-set allowlist is the wrong shape for bot detection.** Use `__typename == Bot` or per-comment `is_bot` (allowlist only as fallback, suffix-matching the un-normalized login); a derived authoritative boolean makes an upstream bug uncorrectable downstream.
- **An `issue_opened` webhook authored by our own bot is usually our own in-flight chain;** find and consolidate on it before dispatching a fresh triage.

## Parking a Chain on an External Party Needs a Silence Date and a Terminal Act

Webhook verification, the delivery-log audit and the 12-hour sweep all answer "will I hear if something happens?"; **none fires on nothing happening**. So when a chain's next step belongs to an external party who owes us nothing, the most likely branch (they never reply) has no observer. On slang#12313, after a maintainer offered the requester a concrete alternative, parking was correct and both instruments were real (all four prior comments had woken the chain, and the sweep enumerated it), yet the gap took a deliberate audit to notice. The fix was not another cron (13 guard series were already armed on a proven event path) but a **written exit condition**: an absolute date, a named terminal act, written in the comment or memo the next session opens. For a quiet external requester that act is **close as answered, with no nudge**: a reminder spends a maintainer-adjacent channel's credibility on someone who chose not to engage, and the inbound-not-a-close rule makes closing reversible. An internal party or routed maintainer may be nudged, justified by deviation from the repo's norm, never an absolute day count ([parking on an external party needs a silence date and a terminal act](../learnings/1786082293702-parking-on-an-external-party-needs-a-silence-date-.md)).

**A park on an operator or maintainer decision needs an active re-chase.** On slang#13073 PR(2) a chain parked on the operator's choice of critique-gate-clear mechanism sat ~5 days until the external maintainer publicly asked "What has happened to this PR?". "Escalated to the operator" is not done: Main owns the chase, so arm a gated `ncl tasks create` poll or a supervise-issues entry before ending the turn; a pushed branch keeps the work safe but never resumes the chain ([parking a chain on a human/operator decision needs a re-chase timer or it stalls silently](../learnings/1790028684307-parking-a-chain-on-a-human-operator-decision-needs.md)). Such a chain is maintainer-gated, not dropped: on slang#13301 draft #13742 arrived 41 min after saipraveenb25 chose an option ([bot-draft CI note: a chain awaiting a maintainer's choice is maintainer-gated](../learnings/1792313744673-slang-bot-draft-ci-has-run-no-build-test-since-10-.md)). The timer stops once a maintainer owns the park: with a maintainer assigned and the bot's triage comment laying out the options, webhooks deliver every event a re-check would look for, so after one silent re-check report "still parked" and schedule nothing further (slang#13900, 2026-11-05, as #13796/#13633) ([don't poll maintainer-owned parked issues](../learnings/1793891043249-don-t-poll-maintainer-owned-parked-issues.md)).

**Internal parks get a timer too.** On shader-slang/slang#12714 the chain stalled silently three times; most recently a fixer acked "will report the PR number the moment it opens" on 2026-09-14 and its container stopped ($5.78 of a $150 cap, so not budget), unnoticed for 14 days until the maintainer asked. A dead container never speaks, so a park on a coworker's artifact gets an `ncl tasks create --process-after <ISO>` re-chase that checks **GitHub** and re-arms while the artifact is missing. Detector: a work session with `container_status=stopped` and `last_active` equal to its creation minute. A recalled PR number is not evidence (a note named a nonexistent #12797); check it with `github_get_pull_request` ([a coworker's "will report" ack is not a timer](../learnings/1790627350003-a-coworker-s-will-report-when-the-pr-opens-ack-is-.md)). **A park on green CI needs a timer because there is no green webhook:** on slangpy#1225 (2026-10-16) CI went green in 15 min but `github.ci_failed` fires only on failure, so the "re-request review once green" step never ran and the PR idled 4 days. Create a one-shot re-check (`--process-after` ≈ CI duration + 15 min) running `gh run view <id> --json conclusion`, or have the parent watch ([no CI-green webhook: schedule a one-shot re-check](../learnings/1792483997051-ci-green-webhook-doesn-t-always-arrive-when-a-step.md)). **A park on a blocker must hear when it clears elsewhere:** on slangpy#1167 → slang#13169 a "bot GH token invalid" alarm was disproved in the `…slangpy-1167/slang-escalation` thread, but a separate session on `gh-issue-shader-slang/slang-13169` had told slang-triager to hold, and an approved maintainer-critical localization sat unposted 10 days. Enumerate every parked session (`ncl sessions list --limit 2000 | grep <issue-num>`, a `stopped` session whose last outbound says parked/held/waiting) and wake each with a pinned (`target_session_id`) GO ([an unblock proven in one thread must reach every session parked on it](../learnings/1790637455225-an-unblock-proven-in-one-thread-must-be-pushed-to-.md)). A park released after days re-verifies staged content before posting; see [scope, staleness and side-effects](verification-e-scope-staleness-and-side-effects.md).

**Task sessions are isolated, which bites both ways.** A coworker answering a task's dispatch replies on that task's edge, and once the task session closes the replies land nowhere read: on #13412 (2026-10-06) the triager's reports and three open asks to closed session `system:tasks:rechase-13409-sibling-7aad` sat unseen ~28 h. So a re-chase reads the coworker's sessions on the canonical thread newest-first (`ncl sessions list | grep <thread>`, then `ncl sessions messages <sid> --reverse --json --limit 10 --full`), and a task that dispatches work outliving it writes the follow-up task naming the recipient's session id ([re-chase task replies land in the closed task session](../learnings/1791316462228-reports-answering-a-re-chase-task-s-dispatch-go-to.md)). Conversely a one-shot timer cannot see what the owner did after it was set: on shader-slang/slang#10232 (2026-11-05) slang-fixer's timer t-11314a fired 21 h after the owner had already acted on jkwak-work's answer (draft PR #14332, three review rounds) and still asked Main to "re-dispatch the build". A re-check first reads the branch's PR (`gh pr list --head fix/issue-<N>`) and head SHA, the owner's `memory/fix-<N>.md`, and comments newer than the last bot comment, reports only what is newer, and ends with "not actionable: already handled in PR #N" when the answer was consumed ([one-shot re-check sessions cannot see the chain owner's progress](../learnings/1793903645395-one-shot-re-check-sessions-cannot-see-the-chain-ow.md)).

**A merge-conflict park measures rebase drift without a clone.** Each re-check records the main sha it saw; the next runs `gh api repos/O/R/compare/<main-sha-at-last-check>...main --jq '.commits[]..., .files[].filename'` filtered to the conflict set, and if the submodule pin moved, `gh api repos/O/<sub>/compare/<pr-pin>...<new-main-pin>` returning `ahead` with `behind_by=0` confirms a fast-forward (slangpy#1189, 2026-10-29) [Parked-PR re-check: measure rebase-cost drift with compare/<last-seen-main>...main, no clone](../learnings/1793282577009-parked-pr-re-check-measure-rebase-cost-drift-with-.md).

**A parked issue's re-check reads the timeline and events, not only comments.** Assignment, milestone and cross-referenced-PR events never appear in the comment list. On slang-rhi#943 (2026-11-01) nobody commented, but a maintainer self-assigned, set a milestone and the linked PR merged; a silent self-assign names a decision owner, not a direction, so the issue stays parked, and our in-place status edit names the owner without `@` ([Parked-issue re-check: check the timeline, not just the comments](../learnings/1793538181143-parked-issue-re-check-check-the-timeline-not-just-.md)). The same read caught an overhaul issue replacing a chosen direction (slang#13750 → #13956), a reporter PR whose merge closed the issue (#14069 → #14072), and draft PR #14358 implementing slang#14101 (2026-11-06), which closed the bot chain; a comments-only check reported "nothing changed" each time ([timeline cross-references](../learnings/1793041485668-parked-issue-re-checks-read-the-timeline-cross-ref.md), [parked-on-reporter re-checks](../learnings/1793663874761-parked-on-reporter-re-checks-read-the-issue-timeli.md), [Parked-issue re-checks: read the timeline, not just comments](../learnings/1793981006662-parked-issue-re-checks-read-the-timeline-not-just-.md)). Filter with `gh api repos/<o>/<r>/issues/<n>/timeline --jq '.[] | select(.event=="cross-referenced" or .event=="assigned")'` (`.source.issue.pull_request.html_url` names a linking PR); assignments are also on `issues/<n>/events` (`--jq '.[]|select(.event=="assigned")|{assignee:.assignee.login,assigner:.assigner.login,created_at}'`), which `gh issue view --comments` never shows. On slang#14091 a re-check reported "no maintainer reply" four days after one maintainer assigned another. An assignee owns the decision, so no ping and no further re-check, and the report names the assignee; read `assigner`, since `actor` can show the assignee ([Parked-issue re-checks must read issue events (assignees), not just comments](../learnings/1793959518362-parked-issue-re-checks-must-read-issue-events-assi.md); ownership rules on [ownership and mention identity](general-misc-ownership-and-mention-identity.md)). For a language-design issue, find where the decision will be made: `issues/N/parent` and `issues/N/sub_issues --jq '.[]|"\(.number) \(.state) \(.title)"'` surface trackers the comments never link (#13721 under #13719; tracker #13979 holds proposal, spec and impl sub-issues), and `gh search prs --repo shader-slang/spec "<topic>"` finds spec text that precedes any proposal (spec#66); spec pages describing current behavior are not a decision ([Find where a parked design issue's decision will be made with the GitHub sub-issue API](../learnings/1793991783678-find-where-a-parked-design-issue-s-decision-will-b.md)). The timeline shows only links made to your issue, so also run `gh search issues "<repo>/issues/<N>" --owner shader-slang`: on 2026-11-03 slang-rhi#915 had no new comments, but the search found slang#9643, where jkwak-work had chosen `[vk::offset]` on entry-point uniforms (draft PR #14108); read that chain's state before handing off ([search for the issue URL across the org](../learnings/1793718200378-parked-chain-re-checks-search-for-the-issue-url-ac.md)).

**A re-check also re-tests the chain's own time-bound claims.** No trigger fires when a release ships, so "not in a release yet (latest vX)" silently goes false; on slang#13972 v2026.21 shipped #13908 between re-checks. Run `gh api repos/<o>/<r>/compare/<sha>...<latest_tag> --jq '{ahead_by,behind_by}'` (`behind_by` 0 means released). If we are still the last poster, PATCH our comment with a short "_Edited <date>: …_" line; an edit sends no notification, so when urgency rises only a fresh comment pinging the assignee reaches them ([re-check release status, not just replies/fixes](../learnings/1793808304535-parked-chains-re-check-release-status-not-just-rep.md)).

## Watchers, Draft-PR Surfaces, and Bot Detection (2026-08-14 fold)

**Key a PR watcher to the PR NUMBER, not a captured SHA.** A verdict-guard cron armed on `c1bb185a0f` went blind when a rebase force-pushed that head away; the verdict landed on `47a59c359b` while the guard fired ~88 times over ~44 h on a dead commit. The discriminator is `git merge-base --is-ancestor <captured-sha> FETCH_HEAD` (not reachable) versus `gh pr view <n> --json headRefOid`; poll by number and re-resolve the head each fire ([key a PR watcher to the PR number, not a captured SHA](../learnings/1786280351305-key-a-pr-watcher-to-the-pr-number-not-a-captured-s.md)). **On a draft PR, `statusCheckRollup` and `commits/<sha>/check-runs` expose different sets.** On slang#12014 (draft, head `72a3b5025d`) a supervisor and a peer reported "no build coverage" for four ticks while 34 build/test jobs from a `workflow_dispatch` run passed: `check-runs` returned 87 entries including all 39 dispatch jobs, the rollup 49 excluding them, so the page read `45 SKIPPED / 3 SUCCESS`. Cite the run id and `check-runs`; the rollup and any dashboard on it will report "no coverage" ([on a draft PR, statusCheckRollup and commits/<sha>/check-runs expose different sets](../learnings/1786280978623-on-a-draft-pr-statuscheckrollup-and-commits-sha-ch.md)). **A closed-set allowlist is the wrong shape for bot detection.** A supervisor's `is_bot = author in ["nv-slang-bot[bot]","nv-slang-bot"]`, consumed as authoritative, typed `coderabbitai` and `github-actions` as humans and sent 2 of 15 false "human spoke last, unanswered" nudges on chains whose owners had refuted the premise four times. The predicate is `__typename == Bot` (GraphQL) or per-comment `is_bot`, with an allowlist only as fallback (some views strip `[bot]` from `login`, so suffix-match the un-normalized value). A derived `authoritative-when-present` boolean discards the evidence a later stage needs to disagree, which is why a consumer-side fix was inert and the bug fired twice more after being declared fixed ([a closed-set allowlist is the wrong shape for bot detection](../learnings/1786280996629-a-closed-set-allowlist-is-the-wrong-shape-for-bot-.md)).

## An `issue_opened` webhook authored by our own bot is often our own in-flight chain

A `github.issue_opened` webhook authored by `nv-slang-bot[bot]` (or another of our bot identities) is often the output of a running "file + fix" chain (CI-babysitter → Orchestrator → fixer), and the body's "a draft PR will be linked below" is that chain's promise. On slang#13184 the webhook reached a fresh Orchestrator session with no memory of the chain that had dispatched `slang-fixer` ~15 min earlier on topic thread `slang-ci-nightly-release-userskills-archive` (fix already committed, unpushed); routing it to triage started a second fixer and a triage comment racing one issue. Before routing such an event: (1) look for an in-flight chain with `ncl sessions list --limit 2000 | grep -iE "<issue-#>|<topic-keywords>"`, including non-canonical topic threads; (2) consolidate on it, since it is usually furthest along; (3) steer it via its exact `thread_id` + `target_session_id` pin (verify the a2a link owner via `ncl messaging-groups get`); (4) have that fixer open the PR and call `report_pr_created`, so the PR→session mapping routes every later webhook to one owner. Detector: two `running` sessions in one agent group for one task ([issue_opened webhook by nv-slang-bot[bot] is often our own in-flight chain — check before dispatching](../learnings/1789894290167-issue-opened-webhook-by-nv-slang-bot-bot-is-often-.md)).
