# Agent Routing: Chain Parking and Bot Detection

Why a chain parked on an external party has no observer, the silence fallback it needs (an absolute date plus a named terminal act, written where the chain is read), and three GitHub-observability traps a supervisor/watcher hits: keying a watcher to a captured SHA, the draft-PR rollup-vs-check-runs split, and a closed-set allowlist for bot detection.

## TL;DR
- **Parking a chain on an external party's reply has no observer on the branch where that party never replies.** A webhook is an event-delivery mechanism, so no event means no delivery; a sweep enumerating in-flight chains sees one that "looks parked" and correctly leaves it parked. Neither fires on nothing happening — a chain parked forever is indistinguishable from one parked appropriately until a human asks "whatever happened to that?"
- ⇒ **When you park work on an external party's reply, set the silence fallback in the same act as the gate.** Three parts, all required: **a date** that is concrete and absolute ("if silent by 2026-08-21"), not "eventually"; **a defined terminal act** — close as answered, escalate, or proceed — named specifically so the future session *executes* rather than re-deliberates; and it must be **written where the chain is read** (the issue comment or chain memo the next session opens), not only in a scheduler, because a cron fires blind.
- **Audit before arming — the fallback is usually not a new cron but a written exit condition.** Keep the two questions separate: *will I hear if something happens?* → usually yes, but verify the path fired before rather than assuming; *will I notice if nothing happens?* → almost always no, and that is the one that needs authoring.
- **For a quiet external requester the terminal act is close-as-answered, with no nudge** — someone who goes silent after a maintainer offered a concrete alternative is not owed a chase. Closing is cheap and reversible (a substantive human comment re-opens a closed chain), so "close with the reasoning on the record" beats "park indefinitely." A chain parked on an internal party or a routed maintainer can legitimately be nudged — but justify that by deviation from the repo's norm, never by an absolute day count.
- **Key a PR watcher to the PR NUMBER, not a captured SHA.** A verdict-guard armed on a captured head goes silently blind when a rebase force-pushes it away and reports plausibly on a dead commit forever. `git merge-base --is-ancestor <captured-sha> FETCH_HEAD` versus `gh pr view <n> --json headRefOid` (the live head) is the discriminator; poll by number and re-resolve the head each fire.
- **On a draft PR, `statusCheckRollup` and `commits/<sha>/check-runs` expose DIFFERENT sets.** A manual `workflow_dispatch` matrix is invisible on the PR page: `check-runs` includes the dispatch jobs, the rollup excludes them, so the page reads mostly SKIPPED while a full matrix is green. Cite the run id and `commits/<sha>/check-runs` as evidence — the rollup (and any dashboard on it) will correctly report "no coverage" while coverage demonstrably exists.
- **A closed-set allowlist is the wrong shape for bot detection.** The failure is the predicate's **shape**, not its contents — use `__typename == Bot` (GraphQL) or per-comment `is_bot`, with an allowlist only a fallback (note some views strip `[bot]` from `login`, so suffix-match the un-normalized value). And a derived boolean discards the evidence a later stage needs to disagree — an `authoritative-when-present` field turns an upstream bug uncorrectable, which is why a consumer-side fix is inert.

## Parking a Chain on an External Party Needs a Silence Date and a Terminal Act

Every instrument in this synthesis — webhook verification, the delivery-log audit, the 12-hour sweep — answers *"will I hear about it if something happens?"* **None of them fires on nothing happening.** A webhook is an event-delivery mechanism, so no event means no delivery; a sweep enumerating in-flight chains sees one that "looks parked" and correctly leaves it parked. So when a chain's next step belongs to an external party, the branch where that party **never replies has no observer at all** — and that is the most likely branch when you are waiting on someone outside the system who owes you nothing. The failure is silent and looks like success: a chain parked forever is indistinguishable from one parked appropriately, right up until a human asks "whatever happened to that?"

Observed on slang#12313: after a maintainer offered the requester a concrete technical alternative, parking was the correct disposition, and *both* watching instruments were real — the webhook path was **proven**, not assumed (all four prior comments on the issue had woken the chain), and the sweep did enumerate it. The gap took a deliberate audit to notice.

⇒ **When you park work on an external party's reply, set the silence fallback in the same act as the gate.** Three parts, all required: **a date** that is concrete and absolute ("if silent by 2026-08-21"), not "eventually" or a relative phrase that decays; **a defined terminal act** — close as answered, escalate, or proceed on the assumption — named specifically, so the future session *executes* rather than re-deliberates; and it must be **written where the chain is read** (the issue comment or chain memo the next session actually opens), not only in a scheduler, because a cron fires blind.

**Audit before arming — the fallback is usually not a new cron.** The reflex is to schedule a guard task; here that was decided against, because 13 guard series were already armed, the webhook path was proven, and the sweep already enumerated the chain, so another cron would have been duplicate noise on an event path that demonstrably works. **What was missing was not an instrument but a written exit condition.** Keep the two questions separate: *will I hear if something happens?* → usually yes, but verify the path fired before rather than assuming; *will I notice if nothing happens?* → almost always no, and that is the one that needs authoring.

**Choosing the terminal act.** For a quiet *external* requester the right fallback is **close as answered, with no nudge**: someone who goes silent after a maintainer offered a concrete alternative is not owed a chase, and a reminder spends a maintainer-adjacent channel's credibility on someone who chose not to engage. A chain parked on an *internal* party, or on a maintainer routed the issue, can legitimately be nudged — but justify that by **deviation from the repo's norm, never by an absolute day count**. Closing is cheap and reversible here, because a substantive human comment re-opens a closed chain (the inbound-not-a-close rule), which makes "close with the reasoning on the record" strictly better than "park indefinitely" ([parking on an external party needs a silence date and a terminal act](../learnings/1786082293702-parking-on-an-external-party-needs-a-silence-date-.md)).

## Watchers, Draft-PR Surfaces, and Bot Detection (2026-08-14 fold)

Three GitHub-observability traps a supervisor/watcher hits. **Key a PR watcher to the PR NUMBER, not a captured SHA.** A verdict-guard cron armed on `c1bb185a0f` went silently blind when a rebase force-pushed that head away; the real CI verdict landed on `47a59c359b`, and the guard fired ~88 times across ~44 h reporting plausibly on a dead commit forever. `git merge-base --is-ancestor <captured-sha> FETCH_HEAD` (NOT reachable) versus `gh pr view <n> --json headRefOid` (the live head) is the discriminator; poll by number and re-resolve the head each fire ([key a PR watcher to the PR number, not a captured SHA](../learnings/1786280351305-key-a-pr-watcher-to-the-pr-number-not-a-captured-s.md)). **On a draft PR, `statusCheckRollup` and `commits/<sha>/check-runs` expose DIFFERENT sets.** A supervisor and a peer independently reported "no build coverage" for four ticks on slang#12014 (draft, head `72a3b5025d`) — it had 34 passing build/test jobs the whole time, from a `workflow_dispatch` run: `commits/<sha>/check-runs` returned 87 entries *including* all 39 dispatch jobs, while `gh pr view --json statusCheckRollup` returned 49 entries *excluding* them, so the PR page reads `45 SKIPPED / 3 SUCCESS` while a full matrix is green. On a draft whose coverage came from a manual dispatch, cite the run id and `commits/<sha>/check-runs` as evidence — the rollup (and any dashboard built on it) will correctly report "no coverage" while coverage demonstrably exists ([on a draft PR, statusCheckRollup and commits/<sha>/check-runs expose different sets](../learnings/1786280978623-on-a-draft-pr-statuscheckrollup-and-commits-sha-ch.md)). **A closed-set allowlist is the wrong shape for bot detection.** A supervisor's `is_bot = author in ["nv-slang-bot[bot]","nv-slang-bot"]`, consumed as authoritative, mis-typed `coderabbitai` and `github-actions` as humans → 2 of 15 false "human spoke last, unanswered" nudges on chains whose owners had already refuted the premise four times. Two rules: the failure is the allowlist's **shape**, not its contents — the predicate is `__typename == Bot` (GraphQL) or the API's per-comment `is_bot`, with an allowlist only a fallback (note the API strips `[bot]` from `login` in some views, so suffix-match the un-normalized value); and **a derived boolean discards the evidence a later stage would need to disagree** — an `authoritative-when-present` field turns an upstream bug uncorrectable, which is why a consumer-side fix was inert and it fired twice more after being declared fixed ([a closed-set allowlist is the wrong shape for bot detection](../learnings/1786280996629-a-closed-set-allowlist-is-the-wrong-shape-for-bot-.md)).
