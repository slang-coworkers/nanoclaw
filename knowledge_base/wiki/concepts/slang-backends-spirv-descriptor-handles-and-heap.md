# Slang SPIR-V DescriptorHandle, bindless, and descriptor-heap emission

How `DescriptorHandle<T>` lowers on SPIR-V under the default heap path, `spvBindlessTextureNV` and `spvDescriptorHeapEXT`: descriptor-load coalescing, `NonUniformResourceIndex` propagation, capability-dependent handle width, and heap `ConstantBuffer`/acceleration-structure ABI. Heap specialization allowlists, stride and atomics are on [[wiki/concepts/slang-backends-spirv.md]].

## TL;DR

- The per-use descriptor `OpLoad` (#12051) is emit strategy, not a SPIR-V rule: `pinDescriptor()` (`OpCopyObject`) proves one load is valid. It is introduced by `legalizeIRForSPIRV` and the emit walk after the last `-dump-ir` snapshot.
- Coalescing a dominating read-only `UniformConstant` load is safe even for a divergent index: per-lane divergence is not per-iteration variance (PR #12111).
- `-dump-ir` is blind at both ends: it starts after early lowering and misses SPIR-V legalize/emit mutations. Disassemble for late questions and check the specific operand, not a whole-dump grep.
- Inlined and `[noinline]` shapes answer cross-call questions differently, so test the exact shape. Label SPIR-V operands from `OpTypeFunction`, never by source position.
- The NonUniform mark is lost through the DescriptorHandle Cast round-trip and through arithmetic into a callee (`findNonuniformIndexInst` owns call args). Keep one shared propagating-op predicate; walk with a worklist and a visited set.
- glslang propagates `nonuniformEXT` only from the final index position and never decorates `OpSampledImage`; verify via `OpDecorate` target ids, not grep counts.
- `DescriptorHandle<T>` is `uint2` on plain spirv/glsl and scalar `uint64` under `spvBindlessTextureNV`/cuda. Making width depend on a new discriminator means auditing every width consumer; a module-scope `OpBitcast` is invalid SPIR-V.
- An emitter's accept-set and any legalization guard mirroring it share ONE predicate. When the second consumer guard for one defect still misses a case, stop and fix the producer (#12186: kind-ungated read-back conversions in `hlsl.meta.slang`).
- SPV_NV_bindless_texture accepts `uint2` OR `uint64` under addressing mode 64 (public retraction on #12186); read the primary spec, and compile a reviewer's alternative before agreeing with it.
- A module-scope `static const` repro must observably consume the constant, or DCE hides the bug. Test explicit `sizeof`/`alignof(T, LayoutRule)` queries directly; struct offsets can coincide.
- `DescriptorHandle<RaytracingAccelerationStructure>` + `spvDescriptorHeapEXT` is supported from v2026.11. The EXT heap is driver-managed: write the descriptor, don't memcpy the address. Slot 0 works, slot ≥1 crashes ⇒ AS stride mismatch.
- In std140 `float4[2]` is byte-identical to a row-major `float2x4`, and matrix-layout mode never touches arrays; with a descriptor heap, suspect #11483 (fixed by #11647).
- The heap `ConstantBuffer` StorageBuffer flip (#11647) was deliberate: the descriptor KIND (Uniform vs Storage) and the buffer-pointer addressing class are separate, and per spec the `OpTypeBufferEXT` and `OpBufferPointerEXT` storage classes are independent. PR #12256 (#12226) keeps a Uniform descriptor and uses an untyped Uniform data pointer.
- `-capability spvDescriptorHeapEXT` changes only `DescriptorHandle<T>` lowering: a plain `ParameterBlock<T>` param keeps set/binding. Use `ConstantBuffer<T>.Handle` (needs `UntypedPointersKHR`), a `T*` BDA param, or `[vk::push_constant] ConstantBuffer<T>`.
- A static emit-crash hypothesis needs a debug-build confirmation; an orphan inst reaching emit points at a clone/specialize pass.
- VUID-...-flags-11312 on `__slang_resource_heap` (set 1, binding 1) = SPIR-V built without `spvDescriptorHeapEXT`; grep the asm for SPV_EXT_descriptor_heap. API: a Capability option entry, not a `+` profile.
- An atomic on `RWTexture2D<uint>.Handle` still emits format `Unknown` and fails spirv-val on v2026.20 and master. #11130 is closed, but its fix was reverted before the release, and no format attribute helps; point users at the OPEN tracker #10024. A closed issue is not a shipped fix: check the fixing PR for a revert and compare against the release tag.

## Descriptor-load coalescing (#12051, PR #12111)

**Reload is an emit artifact.** With `Texture2D tex = texH;` sampled 3×, HLSL loads once but SPIR-V emits 3 `OpLoad` from one `OpAccessChain`; `pinDescriptor()` (`OpCopyObject`) collapses them to 1, which proves a single load is valid. Tooling: with a bare Debug build, `-target spirv-asm` needs a RELEASE `libslang-glslang-*.so` on `LD_LIBRARY_PATH` ([descriptor reload is an emit-time artifact](../learnings/1783759451138-slang-12051-spir-v-descriptor-reload-is-an-emit-ti.md)). On the default path the generic IR holds one shared `getElement(__slang_resource_heap, index)`. The per-use `OpLoad` comes from `legalizeIRForSPIRV` + the emit walk after the last `-dump-ir` snapshot, not from `shouldDuplicateInstAtUseSite`. The lever is therefore emit/legalize: materialize one load when its def dominates the uses ([CORRECTION: emit-time OpLoad-per-use](../learnings/1784075115135-correction-slang-12051-spir-v-descriptor-reload-is.md)).

**Why the existing redundancy pass misses it.** `legalizeIRForSPIRV` runs `legalizeSPIRV` first (which inserts the loads) and then `simplifyIRForSpirvLegalization` → `removeRedundancyInFunc`. Ordering is not the reason; `isMovableInst`'s `kIROp_Load` case accepts only CB/ParameterBlock pointers. `CastDescriptorHandleToResource` (the lowering only for `spvBindlessTextureNV`) is not movable; `CastDynamicResource` is ([legalize pass ordering](../learnings/1784269362740-slang-12111-spir-v-legalize-pass-ordering-removere.md)).

**The NonUniform guard was unnecessary.** At `insertLoadAtLatestLocation` uniform and divergent IR are identical: the heap index has no `NonUniformResourceIndex` and no `IRSPIRVNonUniformResourceDecoration`, and the `isNonUniform` at `:690` belongs to the plain resource-array path. A plain `Texture2D t[16]` keeps its decorations; only the heap path loses them ([divergent NonUniform marker stripped before legalize](../learnings/1784081063099-slang-12051-descriptorhandle-divergent-nonuniform-.md)). Coalescing is correct: per-lane divergence is not per-iteration variance, `spvDescriptorHeapEXT` already emits 2 loads with 0 NonUniform and validates, and the missing hint is a documented gap (`desc-heap-nonuniform.slang:8-12`). So Option A drops the guard, and NonUniform preservation is a separate follow-up (#12110). Before calling a plan's guard mandatory, verify that the signal it reads exists at the fix site ([option-a: the invariance guard was over-specified](../learnings/1784081353064-slang-12051-option-a-the-invariance-guard-was-over.md)). The precise mechanism: the mark exists early (`%34 = nonUniformResourceIndex(%33)`). `makeVector` → `CastUInt2ToDescriptorHandle` → `CastDescriptorHandleToUInt2` → `swizzle` then re-extracts the index unmarked. A whole-dump `grep -c` is inflated by the capability-atom name ([CORRECTION: the Cast round-trip drops the mark](../learnings/1784083614756-slang-12051-correction-descriptorhandle-nonuniform.md)). `-dump-ir`'s first snapshot (`AFTER validateAndRemoveAssumeAddress`) is already past early lowering, so the dump is blind at both ends ([REFINEMENT: -dump-ir starts too late](../learnings/1784083913871-refinement-slang-12051-the-nonuniform-marker-exist.md)).

**Safe shape for SPIR-V-legalize CSE/coalesce PRs:** the shared load dominates by construction (`setInsertAfter(subAddr)`), the change is decoration-neutral, and scope follows the read-only `UniformConstant` invariant, not a builtin-name gate ([UniformConstant load-coalescing is a safe shape](../learnings/1784126649253-approver-confirmed-spir-v-uniformconstant-load-coa.md)).

**`[noinline]` and the #12027 workaround.** Inlined and `[noinline]` helpers answer differently. With `[noinline]`, a resource passed as a loaded descriptor value is loaded caller-side, and #12111 coalesces those loads N→1 across the call. #12027 passes an IMAGE across a call as a `%uint` bindless index and a SAMPLER as a real descriptor. A change is a regression only if the image parameter flips from `%uint` to `OpTypeImage` ([load-coalescing vs [noinline] + #12027 workaround](../learnings/1784128384354-slang-12051-12111-descriptorhandle-load-coalescing.md)). After two mislabeled public answers: resolve operand roles from the raw `OpTypeFunction` / `OpFunctionParameter` / type-def lines, never from source position ([image passes as uint INDEX, sampler as real descriptor](../learnings/1784128407283-slang-bindless-noinline-image-passes-as-uint-index.md)).

**Sampler-vs-texture `[noinline]` param asymmetry (#12004):** `isIllegalSPIRVParameterType` always specializes textures but only specializes samplers when they are *arrays* (a legacy compile-time-blowup guard, #3546), so a scalar `SamplerState` param stays by-value `OpTypeSampler` while the texture is passed by index and reloaded in the callee. Emission is symmetric — the by-value-vs-by-index location is decided entirely by the specialize step, not emit, so don't chase it in the emitter; fixes here MUST `spirv-val`, not just FileCheck ([sampler-vs-texture noinline SPIR-V param asymmetry — isIllegalSPIRVParameterType isArray gate](../learnings/1783527024741-slang-12004-sampler-vs-texture-noinline-spir-v-par.md)).

## NonUniformResourceIndex propagation

**DescriptorHandle round-trip (PR #12116, #12161).** The float pass (`slang-ir-float-non-uniform-resource-index.cpp`) adds SPIR-V-gated `kIROp_CastUInt2ToDescriptorHandle` and `kIROp_MakeVector` cases. They float the wrapper to the heap index, fixing VUID-RuntimeSpirv-None-10148 on the default heap path. The flagged `if (floatMode != SPIRV) break;` asymmetry follows the file-header contract (textual = hint; SPIR-V `OpDecorate NonUniform` is position-specific). Verdict: APPROVE_WITH_NITS ([#12116 guard asymmetry is a nit](../learnings/1784536684181-slang-12116-nonuniform-float-pass-guard-asymmetry-.md)). On HLSL/GLSL the mark lands nested in `uint2(...).x`. Whether DXC/glslang honour it can be read from the SPIR-V without a GPU, and was answered on #12161 (2026-10-07) through `-emit-spirv-via-glsl`: for the nested form `heap[uvec2(nonuniformEXT(i),0U).x]` (emitted before #12263), glslang decorates only the `OpCopyObject %uint` of the index and leaves the `OpAccessChain` and `OpLoad` undecorated, whereas the canonical `heap[nonuniformEXT(i)]` gets the index, access chain and load decorated; DXC sets `createHandleFromHeap`'s nonUniformIndex flag for both forms. Separately, glslang never decorates the `OpSampledImage` built by `sampler2D(tex[nonuniformEXT(i)], s[nonuniformEXT(j)])`, even for plain `Texture2D[]` arrays, on v2026.12 and master, while Slang's direct SPIR-V path does. Check this by listing the ids that `OpDecorate ... NonUniform` targets and reading their definitions; a raw `grep -c NonUniform` also counts `OpCapability ShaderNonUniform` and inline `; NonUniform` annotations, so it overstates coverage ([textual targets: nested in uint2(...).x by design](../learnings/1784539603707-nonuniform-on-descriptorhandle-round-trip-lands-ne.md), [glslang propagates nonuniformEXT only from the final index position](../learnings/1791406267340-glslang-propagates-nonuniformext-only-from-the-fin.md)).

**Through arithmetic (#13072).** The spelling `buffers[NUR(i)*i][0]` / `.Load(...)` lowers to a CALL. The float pass floats the mark through `mul`, but the mark dead-ends at the call argument. The real gate is `findNonuniformIndexInst` in `slang-ir-specialize-function-call.cpp`, which walked only `IntCast`. The float pass's arithmetic path runs only for same-function access (e.g. `arr[NUR(i)*i][0] = v`). Dump IR to find the real layer; use a worklist + visited set (naive recursion took >10 s on a 29-node `v=v+v` chain); re-insert the mark with `newParam->getFullType()`; keep one `isNonUniformIndexArithmeticOp` predicate ([NUR through arithmetic: fix is in the specializer](../learnings/1789465468604-nonuniformresourceindex-through-arithmetic-fix-is-.md)).

## spvBindlessTextureNV and DescriptorHandle width (#12185, #12186)

**Over-broad producer.** A non-image/sampler `DescriptorHandle<T>` under `-capability spvBindlessTextureNV` aborts with `Unsupported result type for CastDescriptorHandleToResource` (E99997). The `case spvBindlessTextureNV:` arm in `hlsl.meta.slang` forwards every kind to `__castDescriptorHandleToResource<T>`, while sibling arms switch on `T.kind`. The emit switch in `slang-emit-spirv.cpp` handles only texture/sampler. Fix it on the producer side and turn the emit `default` into a diagnostic ([spvBindlessTextureNV abort: producer over-broadcasts](../learnings/1784687930584-slang-12185-spvbindlesstexturenv-descriptorhandle-.md)). The follow-up guard mirrored the emit accept-set by hand and omitted `kIROp_SamplerComparisonStateType` (encodable via `OpConvertUToSamplerNV`), which turned an abort into a wrong diagnostic. Extract `isBindlessTextureNVEncodableResourceType(IRType*)`, which matches `kIROp_TextureType || as<IRSamplerStateTypeBase>` on unwrapped types, and use it at both sites ([accept-set + mirroring guard share ONE predicate](../learnings/1784697407327-emit-switch-accept-set-a-legalization-guard-that-m.md)).

**Representation is capability-dependent.** The handle is a scalar `%ulong` under `spvBindlessTextureNV`/cuda, so the AS cast must be `RaytracingAccelerationStructure((uint64_t)handle)`. A maintainer's proposed `__asuint64((uint2)handle)` failed spirv-val once swapped in and compiled, which is how to settle such a suggestion ([DescriptorHandle is uint64-native under spvBindlessTextureNV](../learnings/1784762549887-descriptorhandle-is-uint64-native-under-spvbindles.md)). Making width *kind-dependent* touched 8 consumer sites: type emit, default-construct legalization, both byte-address cast selectors, IR layout, the sizeof/alignof peephole, AST layout, and reflection. Grep every `implies(CapabilityAtom::X)`/`getUInt64Type`, and keep classification as one IR predicate plus a mirrored AST predicate. In a block, a `uint2`↔`uint64` cast needs a real `OpBitcast`, but a module-scope `OpBitcast` is invalid ("must appear in a block"), so materialize the constant from its bits. Compare in the native representation ([kind-dependent representation: audit ALL width consumers](../learnings/1784859574140-kind-dependent-spir-v-representation-change-audit-.md)).

**Four consumer guards ⇒ one producer hole.** Four emit-time guards each caught a different subset, and the fourth had to walk the operand graph to recover width. The root cause: the handle read-back conversions in `hlsl.meta.slang` (`extension uint2 { __init<T>(DescriptorHandle<T>) }` and the `uint64_t` sibling) are capability-gated but not kind-gated. That one hole showed up at module scope (`OpIAdd %ulong` on `%v2uint`), in a function-scope cast, and in descriptor-heap lowering (a scalar `OpCompositeExtract` that trips spirv-opt `const_folding_rules.cpp:129`). Escalate the public `.meta.slang` fix instead of writing a fifth guard. Both integer constructors are public, so user code can reach the shape: use a diagnostic, not an assert. The spec lesson from the same work: SPV_NV_bindless_texture accepts `uint2` OR `uint64` at `OpSamplerImageAddressingModeNV 64`. A caveated DeepWiki answer said otherwise and cost a public retraction. Read the primary spec, and do not treat spirv-val silence as evidence ([cite the spec; four guards ⇒ upstream hole](../learnings/1785776557998-cite-the-spec-not-a-summarizer-spv-nv-bindless-tex.md)).

The `#12186` option-A rework (kind-dependent `uint2`/`uint64` `DescriptorHandle` width) answered two of pdeayton's concerns with general lessons. First, "does the width conversion assert?" split into a **pre-existing gap** and a PR-introduced edge. A module-scope `static const` handle initialized from a float/`bit_cast` source aborts at `emitGlobalInst` ("Unhandled global inst"), but the same `castFloatToInt` abort reproduces on master with no capability and no handle; that A/B control proves a general global-emit gap. The new edge is the width-mismatch path reaching `tryGetConstantDescriptorHandleBits`'s missing cast case → `SLANG_RELEASE_ASSERT`. The principled layer is **SCCP** (`isEvaluableOpCode`, `slang-ir-sccp.cpp`), which runs at global scope before emit and folds BitCast/CastFloatToInt but not MakeVector or the DescriptorHandle casts; teaching it those retires both the bespoke walker and the assert ([slang#12186 option-a: layout change RESTORES cap-consistency; module-scope handle const from float/bitcast hits pre-existing global-emit gap](../learnings/1784912194039-slang-12186-option-a-layout-change-restores-cap-co.md)). A module-scope `static const` repro must *observably consume* the constant (store it to a `RWStructuredBuffer` from the entry point), because DCE drops an unused global before emit and a green compile then falsely reads as "bug unreal"; and a work item that names symbols from an *unmerged draft PR* (`tryGetConstantDescriptorHandleBits`) is not actionable on master until you grep master for them ([Module-scope static-const repros need the constant CONSUMED or DCE masks the bug](../learnings/1784915301574-module-scope-static-const-repros-need-the-constant.md)). Second, Q2 "uint2 scalar layout — latent bug?" was first wrongly cleared by embedding the handle in a struct and matching std430 offsets, but `uint2` and `uint64` both align to 8 in std430, so the offsets coincide. The maintainer's explicit `alignof(T, Std430DataLayout)` fails on the PR (handle 4, `uint2` 8): the AlignOf/SizeOf **peephole** (`slang-ir-peephole.cpp`) resolves `layoutRules` and then calls `getNaturalSizeAndAlignment`, which is hardcoded to natural rules (invisible for uint64, where natural == std430). Test the explicit `sizeof`/`alignof(T, LayoutRule)` query directly, and run a reviewer's exact minimal `static_assert` before writing an elaborate test ([slang#12186 Q2 UPDATE: explicit alignof(T, Std430DataLayout) query CAN diverge from emitted struct layout — struct-embedding tests MASK it](../learnings/1784915310738-slang-12186-q2-update-explicit-alignof-t-std430dat.md)).

## Descriptor heap: acceleration structures and ConstantBuffer storage class

**AS through `spvDescriptorHeapEXT`.** The path is supported and regression-tested from v2026.11 (`tests/spirv/descriptor-heap-acceleration-structure*.slang`). Keep two values apart: the handle `uint2` (`.x` = heap index) and the slot contents (an 8-byte device address, not the opaque handle). Diagnosis order:
1. grep `-target spirv-asm` output for `OpConvertUToAccelerationStructureKHR` (missing = old build);
2. run VK GPU-assisted validation;
3. if slot 0 works but slot ≥1 crashes, suspect an AS stride mismatch (`-spirv-resource-heap-stride`, #11231/#11494).

([diagnosing DescriptorHandle<RaytracingAccelerationStructure> crashes](../learnings/1785051051163-diagnosing-descriptorhandle-lt-raytracingaccelerat.md)). The EXT `ResourceHeapEXT` is driver-managed (slang-rhi uses `VK_DESCRIPTOR_TYPE_MUTABLE_EXT`). Fill the AS slot with `vkUpdateDescriptorSets` + `VkWriteDescriptorSetAccelerationStructureKHR`, not a raw memcpy. The raw uint64 model holds only for an app buffer (`RaytracingAccelerationStructure(myBuffer[i])`). Tell: the AS fails at index 0 with a correct `.x` while textures work ⇒ the host is memcpy'ing. Escape hatch: override `getDescriptorFromHandle` ([AS heap is driver-managed](../learnings/1785056296611-spvdescriptorheapext-as-heap-is-driver-managed-des.md)).

**"`float4[N]` reads garbage, `float2x4` works."** In std140, `float4[2]` (32 B) is byte-identical to a row-major `float2x4`; column-major is 64 B. Matrix-layout mode changes only matrices. Without heap involvement, suspect host packing and check `spirv-dis | grep -E "Offset|ArrayStride|MatrixStride"` ([std140: row-major float2x4 == float4[2]](../learnings/1785073305394-std140-row-major-float2x4-and-float4-2-are-byte-id.md)). With a descriptor heap it is #11483: a heap-fetched `ConstantBuffer<T>` becomes a `Uniform` `OpBufferPointerEXT`, and `getPointerArrayStrideValue` emits no stride for Uniform. #11647 fixed it by retyping to StorageBuffer, so tell users to update forward. The #12226 regression follows below. Workaround: fetch through `StructuredBuffer<T>` ([float4[N] garbage + descriptor heap = #11483](../learnings/1785073991889-discord-float4-n-in-struct-reads-garbage-matrix-wo.md)).

A distinct descriptor-heap ABI bug (`#12226`): a struct-typed `ConstantBuffer<T>` fetched via `ResourceDescriptorHeap[]` under `spvDescriptorHeapEXT` emits an `OpTypeBufferEXT` **StorageBuffer** (16B on the reporter's driver) instead of **Uniform** (8B) → 8 bytes of garbage. The naive "flip ConstantBuffer→Uniform in the heap path" fix is WRONG and regresses `#11483`: `processConstantBufferDescriptorHeapLoad` *deliberately* retypes struct/array heap ConstantBuffer loads to StorageBuffer (PR #11647, szihs) because a Uniform-class `OpBufferPointerEXT` carries no pointer-type `ArrayStride` (logical addressing), so nested-array offsets went undefined. The real defect is **conflating the descriptor *kind* fetched from the heap (an ABI fact — Uniform vs Storage, also sets the heap index stride via `OpConstantSizeOfEXT`) with the buffer-pointer *addressing class* (needs StorageBuffer for pointer ArrayStride)** ([Descriptor-heap ConstantBuffer StorageBuffer flip (#11647) is deliberate — descriptor kind vs pointer addressing class conflated](../learnings/1784939222858-descriptor-heap-constantbuffer-storagebuffer-flip-.md)). The remaining open question — must the two storage classes match? — was resolved by fetching the published `SPV_EXT_descriptor_heap` spec verbatim: `OpTypeBufferEXT` and `OpBufferPointerEXT`-result each carry a *separate* storage-class operand and **there is no normative rule requiring them to match** (the only place they coincide is a worked example, not a VUID; the `NonWritable` allowance explicitly contemplates a non-StorageBuffer result). DeepWiki claimed they must match — confidently wrong on this exact subsystem again — so "Approach B" (Uniform descriptor + StorageBuffer data pointer) is spec-legal; the residual question is a *device-ABI* one to confirm empirically with `SLANG_RUN_SPIRV_VALIDATION=1`, not a spec matching rule ([SPV_EXT_descriptor_heap: OpTypeBufferEXT and OpBufferPointerEXT storage classes are INDEPENDENT (no matching rule); DeepWiki wrong](../learnings/1784939925118-spv-ext-descriptor-heap-optypebufferext-and-opbuff.md)). Container tip recurring across these: `slangc -target spirv-asm` fails on the missing `slang-glslang` dylib — use `-O0 -target spirv -skip-spirv-validation` then disassemble with the in-tree `build/external/spirv-tools/.../spirv-dis`.

**Typed vs untyped data pointer (#12226).** Slang's `emitDescriptorHeapLoad` returns a TYPED `IRPtrType`, so access goes through `OpAccessChain`. A typed pointer to an array element needs a pointer `ArrayStride`, which only exists for StorageBuffer/PhysicalStorageBuffer. glslang instead uses an untyped Uniform pointer + `OpUntypedAccessChainKHR`. Two framing corrections:
- Slang already emits valid typed Uniform access for scalar/vector/matrix CB elements, so the problem is specific to array elements.
- `processConstantBufferDescriptorHeapLoad` flips EVERY struct to StorageBuffer, which is broader than needed.

The untyped path was estimated at ~5-8 new untyped-aware consumers, i.e. an emitter-architecture extension. `-spirv-unified-descriptor-heap-stride` fixes the stride, not the descriptor kind ([heap CB typed-vs-untyped OpBufferPointerEXT](../learnings/1785256702253-slang-descriptor-heap-constantbuffer-typed-vs-unty.md)). PR #12256 (merged 2026-07-29, closes #12226) took that path: the descriptor stays `OpTypeBufferEXT Uniform`, and the data pointer is a new `SPIRVUntypedPtrType` IR flavor emitted as `OpTypeUntypedPointerKHR Uniform` and reached with `OpUntypedAccessChainKHR`. The heap ConstantBuffer is a uniform-buffer descriptor on v2026.20.

**`-capability spvDescriptorHeapEXT` changes only `DescriptorHandle<T>` lowering.** Verified with release slangc v2026.20: a plain `uniform ParameterBlock<T>` entry-point param still gets `DescriptorSet 0`/`Binding 0` and no DescriptorHeapEXT capability, so Vulkan validation asks for `VkShaderDescriptorSetAndBindingMappingInfoEXT`. The native heap route is `uniform ConstantBuffer<T>.Handle h` (dereferenced as `*h`): a `uint2` handle in a PushConstant block, `OpTypeBufferEXT Uniform`, `OpBufferPointerEXT`, `OpUntypedAccessChainKHR`, and no set/binding. `ParameterBlock<T>.Handle` is rejected (E30027 member not found). That route needs `OpCapability UntypedPointersKHR` (SPV_KHR_untyped_pointers), so tell users so. Two routes without untyped pointers also compile on v2026.20: a `T*` buffer-device-address param needs only `PhysicalStorageBufferAddresses`, and `[vk::push_constant] ConstantBuffer<T>` needs only `OpCapability Shader`. The VK_EXT_descriptor_heap proposal lists VK_KHR_shader_untyped_pointers as a dependency (proposal only; the final spec was not checked). Spec access from the container: docs.vulkan.org and registry.khronos.org return 403 to WebFetch, while `raw.githubusercontent.com/KhronosGroup/Vulkan-Docs/main/proposals/VK_EXT_descriptor_heap.adoc` works ([spvDescriptorHeapEXT does not remove set/binding from ParameterBlock/ConstantBuffer params](../learnings/1792525428195-spvdescriptorheapext-does-not-remove-set-binding-f.md)).

**VUID-VkGraphicsPipelineCreateInfo-flags-11312 on `__slang_resource_heap` (Set 1, Binding 1) means the shader was compiled without `spvDescriptorHeapEXT`.** That variable is Slang's legacy bindless array. With the capability, a `DescriptorHandle<Sampler2D>` fragment shader (v2026.20) emits SPV_EXT_descriptor_heap and keeps only the `globalParams` set/binding. On the API, `findProfile("spirv_1_5+...+spvDescriptorHeapEXT")` returns 0 and drops the capability, as does a plain profile; a Capability `CompilerOptionEntry` on `TargetDesc` or `SessionDesc` applies it ([[wiki/concepts/slangc-target-coverage-and-capabilities.md]]). `-bindless-space-index N` changes only the set; the binding stays 1. Grep the asm for SPV_EXT_descriptor_heap first, then look for a second session, a hardware-dependent branch, or a leftover `+` profile string [VUID-11312 "no mapping for __slang_resource_heap" = SPIR-V compiled without spvDescriptorHeapEXT](../learnings/1793006419948-vuid-11312-no-mapping-for-slang-resource-heap-spir.md).

## Texture atomics through a handle: format Unknown (#10024; closed #11130)

Consider `RWTexture2D<uint>.Handle h;` used with `InterlockedOr(h[p], 1)` on SPIR-V. A plain `RWTexture2D<uint>` global gets format `R32ui`, but the handle's `OpTypeImage` still has format `Unknown` on v2026.20, so spirv-val fails it: VUID-04658 without `spvDescriptorHeapEXT`, VUID-11416 with it. `[format]` and `[vk::image_format]` do not help, whether they sit on the handle, on a local, or on `= ResourceDescriptorHeap[i]`. A buffer-handle atomic (`RWStructuredBuffer<uint>.Handle`) validates. The E41403 validator gap on the same shape (#11506) is a separate bug, on [[wiki/concepts/slang-backends-spirv.md]]. #11130 was closed on 2026-10-14 as fixed by #13537, but #13712 reverted #13537 on 2026-10-16, before v2026.20 was tagged on 10-17. The method generalizes: a closed issue is not a shipped fix, so check the fixing PR for a revert (look for commits that touch its test file) and compare the dates against the release tag ([#11130 closed but not fixed in any release](../learnings/1792612858405-slang-11130-handle-texture-atomics-format-unknown-.md)).

The bug is unchanged at master 653bfdeef4 (2026-10-22), so do not point users at closed #11130. The OPEN tracker is #10024 ("[[format]] not propagated through DescriptorHandle", csyonghe, milestone Q1 2027, "requires a big refactoring"). The likely root cause is that format inference runs only when the variable type unwraps to `TextureTypeBase`: in `maybeApplyLayoutModifier` (`slang-check-decl.cpp:2585-2600`), and in `slang-ir-resolve-texture-format.cpp:134-154`, which handles only global texture and texture-array insts. A handle is neither, so it never gets a format. The workaround that validates is `RWStructuredBuffer<uint>.Handle` [DescriptorHandle textures get no image format: open tracker is #10024](../learnings/1792658643801-slang-descriptorhandle-textures-get-no-image-forma.md).

## Emit crashes on the heap path

**SIGSEGV from an orphan `IRParam` (#11496).** A `DescriptorHandle<Texture2D>` passed into a `[noinline]` callee together with a buffer-pointer array argument, then sampled, crashed SPIR-V emit under `-capability spvDescriptorHeapEXT`. The static-read triage blamed an unguarded optional format operand (`getFormatInst()` without `hasFormat()`), but a debug build with that guard still crashed: the operand value was an orphan `IRParam` with no parent function and a null `getFullType()`, left behind by `specializeFuncsForBufferLoadArgs` and the post-clone `simplifyFunc`/`replaceImageElementType` path. The root cause is tracked in #11498; the partial fix #11499 turns the crash into E99997. Confirm a static root-cause hypothesis for an emit crash with a debug build, and tell "operand list too short" apart from "the value itself is orphaned": an orphan inst reaching emit points at a clone/specialize pass ([#11496: static getFormatInst() hypothesis was wrong; real cause is an orphan IRParam](../learnings/1780768927407-slang-11496-spir-v-sigsegv-static-getformatinst-tr.md)). The allowlist side of the same cluster is on [[wiki/concepts/slang-backends-spirv.md]].
