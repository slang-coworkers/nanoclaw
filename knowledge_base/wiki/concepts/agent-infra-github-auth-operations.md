# GitHub Auth and Operations in Agent Containers

> Related pages: [Agent GitHub Token Boundaries and Write-Blocks](agent-github-token-boundaries-and-write-blocks.md) (07-16/07-17 auth-outage diagnostics, empty-list-looks-like-success trap, Discussions and workflow-push write-blocks, review under an invalid token, human-cred merge ≠ bot-write recovery) · [Agent GitHub Fork-Takeover and Rebase Mechanics](agent-github-fork-takeover-and-rebase.md) (PR takeover from a contributor fork, App-token rebase, unauth REST fallback).

## TL;DR

- **`gh auth status` / `gh api user` / any identity probe is a FALSE-NEGATIVE.** They return 401 / "token invalid" / `app_not_connected` even when GitHub reads AND writes work. The `GH_TOKEN` is a OneCLI routing sentinel; the real GitHub App installation token is injected on the wire and has no `/user` identity. Never self-block on a probe.
- **Verify reads** with a real org-scoped call: `gh api repos/<o>/<r> --jq .full_name`. **Verify writes** by attempting the actual write and trusting its exit code / returned URL. Escalate "GitHub down" only on a real 4xx from the endpoint you need.
- **Works:** org-scoped REST `gh api repos/<o>/<r>/...` (GET + POST/PATCH comments, labels, bodies); `git push` of `fix/issue-*` branches; `gh pr create --draft`; raw-token `git push https://x-access-token:${GH_TOKEN}@github.com/...`.
- **Unreliable:** porcelain `gh issue view` (can return empty; use REST); deep pagination (keep `--limit 100`, page 2 goes unauthenticated → 401). `search` is on the proxy allow-list: `gh search issues` works, but inline `gh api search/issues?q=` breaks on unencoded `>`/`,`/`+`.
- **nv-slang-bot perms:** `actions/contents/issues/pull_requests:write, metadata/org_projects:read`. NOT `workflows` — any push touching `.github/workflows/*` is rejected atomically (whole push fails). Route workflow patches to the orchestrator's PAT, or cross-fork via `slang-coworkers`.
- **Bot login is `nv-slang-bot`** (no `[bot]` suffix) — edit-in-place guards comparing to `"nv-slang-bot[bot]"` never match → duplicate POSTs. A session can only edit/delete comments IT created; cross-session comment edit 403s. Exactly one tier owns the issue-level 5-bullet.
- **Merge-queue enqueue is structurally blocked** for the bot — always escalate evictions for human requeue.
- **`report_pr_created({repo,pr_number})` binds the CALLING session.** Open the PR from the fix-chain session; never re-fire it from a non-owning session to "re-confirm" — that steals the PR's webhooks.
- **Fork-PR CI approval gate is keyed on origin-of-head (fork vs same-repo), not author** — the bot's same-repo `fix/issue-N` branches skip it.
- **A `/slang-pr-review` preflight warning is not a block**: public-repo diff reads work even unauthenticated; only a failing real write is degradation.

## The core rule: identity probes are false negatives

`gh auth status`, `gh api user`, `gh api rate_limit` and `gh api repos/szihs/*` return 401 / "token in GH_TOKEN is invalid" / `app_not_connected` **even when GitHub reads AND writes work**. Never treat them as proof GitHub is unavailable, and never self-block on them ([CONSOLIDATED: GitHub auth & ops in agent containers](../learnings/1780558152381-CONSOLIDATED-github-auth-and-ops-in-agent-containers.md)).

The mechanism: GitHub traffic routes through the OneCLI HTTPS proxy (`HTTPS_PROXY`/`HTTP_PROXY` in the container env), which injects credentials by URL-path match. The git remote holds `x-access-token:placeholder@github.com`, and `GH_TOKEN` is a literal ~23-char sentinel `ROUTED_VIA_ONECLI_PR…`; the real `nv-slang-bot[bot]` App installation token is injected on the outbound call, so a local "invalid token" reading inspects the sentinel. `gh auth status` probes `GET /user`, which an App *installation* token cannot call; that says nothing about repo or org capability ([GH_TOKEN is a OneCLI routing sentinel](../learnings/1789099182120-gh-cli-works-for-repo-scoped-writes-despite-invali.md), [gh auth status uses GET /user](../learnings/1789106327782-gh-auth-status-false-negative-under-app-installati.md), [GH_TOKEN invalid but gh api succeeds via the proxy](../learnings/1783636613641-gh-auth-status-shows-gh-token-invalid-but-gh-api-s.md)). Unsetting `GH_TOKEN` to force a stored-cred fallback fails hard: there are no stored creds, and the env token is the only auth ([gh auth status false-negative with App installation token](../learnings/1782895550564-gh-auth-status-false-negative-with-app-installatio.md)).

**Verify reads** with the real call you need: `gh api repos/shader-slang/slang --jq .full_name`, `gh api repos/.../pulls/<N>`, or `gh pr view/diff <N> -R <o>/<r>` (exit 0). **Verify writes** by attempting the write: `gh api --method POST repos/<o>/<r>/pulls/<PR>/comments/<CID>/replies -f body=... --jq '.html_url'` returns the posted URL on HTTP 201. Escalate "write path down" only on a real 4xx from *that* endpoint ([gh auth status 401 is a FALSE NEGATIVE — verify via a real write](../learnings/1783388957871-gh-auth-status-401-is-a-false-negative-for-nv-slan.md)). When authorized to post, post autonomously: routing a fully drafted answer up to parent on a false 401 cost a round-trip and produced two byte-identical replies on a maintainer's thread when the parent both directed a retry and posted itself. A repo-local PreToolUse hook (`gate-critique-on-deliver.sh`) can also false-positive on any `gh api .../pulls/...` command by substring-matching "pulls" as PR creation; that is a gate misfire, not a GitHub failure.

**When OneCLI really is disconnected.** An `app_not_connected` ("GitHub is not connected in OneCLI") can be a real proxy disconnect while the token is fine. Bypass OneCLI and call `https://api.github.com` directly with `curl -H "Authorization: Bearer $GH_TOKEN"`: verify with `GET /repos/<o>/<r>` (200), then post with `jq -Rsn --arg b "$BODY" '{body:$b}' | curl -s -H "Authorization: Bearer $GH_TOKEN" -H "Accept: application/vnd.github+json" -X POST ".../issues/N/comments" --data @-` (201 = posted) ([gh via OneCLI can be down while direct curl works](../learnings/1783873229538-gh-via-onecli-can-be-down-while-direct-curl-to-git.md)). The `slang-maintainer` container had a genuine OneCLI integration gap (`app_not_connected`, only unauthenticated public reads); on #11410 its verbatim drafted verdict was routed through a GitHub-capable coworker (`slang-triager`, `slang-fixer`) instead of blocking on a reconnect ([slang-maintainer container cannot post to GitHub](../learnings/1780356530581-slang-maintainer-container-cannot-post-to-github.md)).

## What works and what does not

**Works:** org-scoped REST via `gh api repos/<o>/<r>/...` (GET issues/PRs/comments; POST/PATCH comments, labels, PR/issue body) and `gh api graphql`; `git push` of `fix/issue-*` branches; `gh pr create --draft`; raw-token `git push "https://x-access-token:${GH_TOKEN}@github.com/<o>/<r>.git" <branch>` and `curl -H "Authorization: Bearer ${GH_TOKEN}"`. CI-log reads work too (`gh run view <run-id> -R shader-slang/slang`, `gh run view --job <job-id> --log`); to find the last-good emsdk, grep the last green wasm-job log for `Resolving SDK version 'X.Y.Z' to 'sdk-releases-<hash>-64bit'` ([last-good emsdk from the green run log](../learnings/1780624123110-find-last-good-emsdk-version-for-an-emsdk-install-.md)).

**Unreliable:** porcelain `gh issue view <n>` returned EMPTY under the App token while `gh api repos/.../issues/N` worked, so prefer REST. The `mcp__slang-mcp__github_*` tools read (get_issue, search_issues) but expose no comment/label/type write; writes go through `gh api`. Search is credentialed (`search` is on the proxy's path allow-list); earlier "search returns empty" readings were query-construction failures. `gh api "search/issues?q=…+created:>2026-09-20"` died with "unexpected end of JSON input" on the unencoded operators, while `gh search issues --repo shader-slang/slang "Foo Bar" --created ">2026-09-20" --json number,state,title` worked for a dup-search. Use the porcelain or encode the query, and allow for search-index lag before reading a zero as "not filed" ([use gh search issues](../learnings/1790842344778-gh-api-search-issues-with-inline-query-string-can-.md)).

**Pagination 401:** keep `gh api` / `gh run list` / `gh pr list` to `--limit 100` (one page); page-2 fetches go unauthenticated through the proxy and 401. Narrow by filter rather than deep-paging.

**`@` in `--field`:** `gh api --field body="@username..."` fails because gh reads a leading `@` as a file path. Use `jq -Rs '{body: .}' < file.md | gh api ... --method POST --input -` or `--raw-field` / `-f` ([gh CLI --field expands @ as file path](../learnings/1778859843367-gh-cli-field-expands-as-file-path.md)).

**The fork-PR CI approval gate does not apply to the bot fixer.** GitHub gates Actions on *fork-based* PRs from outside contributors behind "Approve and run workflows", keyed on **origin-of-head, not PR author**. The slang-fixer opens same-repo `fix/issue-N → master` PRs, so its CI runs immediately (PR #12115). Only the community-contributor lane (fork head) needs a maintainer-approve-workflow node; never claim the bot fixer "hit fork-PR workflow-approval gating" ([fork-PR CI gate keyed on origin-of-head](../learnings/1785530290363-fork-pr-ci-approval-gate-is-keyed-on-origin-of-hea.md)).

## nv-slang-bot identity and permissions

`nv-slang-bot` carries `actions:write, contents:write, issues:write, pull_requests:write, metadata:read, organization_projects:read`, and NOT `workflows` ([CONSOLIDATED: GitHub auth & ops](../learnings/1780558152381-CONSOLIDATED-github-auth-and-ops-in-agent-containers.md)). Comment `.user.login` via gh is `nv-slang-bot` (no `[bot]` suffix), so an edit-if-self guard testing `[ "$LOGIN" = "nv-slang-bot[bot]" ]` never matches and POSTs duplicates instead of PATCHing; match by substring ([nv-slang-bot login has NO [bot] suffix](../learnings/1782857315349-edit-if-self-check-nv-slang-bot-login-has-no-bot-s.md)).

A session can edit or delete only comments it created: PATCHing another session's comment 403s despite `issues:write`, though both render as the same bot, so post a fresh delta ([403 on cross-session comment-edit](../learnings/1782388835952-nv-slang-bot-403-on-issue-assign-and-cross-session.md)). Two tiers posting on one issue leave comments neither can consolidate, so exactly ONE tier owns the issue-level 5-bullet. That atom's 403 on setting an assignee (#11751) no longer holds: on 2026-10-23 the bot assigned #13892 by pre-checking `GET /assignees/<login>` (204), creating the issue WITHOUT assignees, then `POST issues/<N>/assignees`, then verifying `.assignees`. GitHub silently drops rejected assignees, and a failed create-with-assignees invites a duplicate-issue retry ([nv-slang-bot CAN set issue assignees](../learnings/1792776424407-nv-slang-bot-can-set-issue-assignees-2026-10-23-cr.md)).

If `POST issues/:n/labels` 403s, fall back to `gh issue edit --add-label`, which succeeds where the raw REST path is inconsistently denied ([labels 403 → gh issue edit --add-label](../learnings/1782866408005-gh-labels-if-post-issues-n-labels-403s-fall-back-t.md)). In a partially degraded gateway session other REST/GraphQL paths can work while labels 403: set Issue Type via GraphQL and defer the label to a healthy session. If a REST mutation 403s with an admin-rights message, try the GraphQL equivalent (for the bot's own comment, resolve the node id and use `updateIssueComment`). With a truly invalid token every `gh` call can return empty rather than error; for read-only needs on public repos, `WebFetch("https://github.com/<owner>/<repo>/issues/<N>")` gets title, body, author, state and labels with no token, but cannot write and may miss long threads ([CONSOLIDATED: GitHub auth & ops](../learnings/1780558152381-CONSOLIDATED-github-auth-and-ops-in-agent-containers.md)).

## Workflow files: a structural block

The App lacks `workflows`, so any push that creates or edits a file under `.github/workflows/` is rejected atomically: the whole push fails, non-workflow files included. `git push --dry-run` does not catch it. A stale `origin/master` can produce the same error text; rebase onto the real tip (`git ls-remote origin refs/heads/master` → `git fetch origin master` → `git rebase`) ([CONSOLIDATED: workflows pushes & elevated permissions](../learnings/1780558703303-CONSOLIDATED-github-workflows-and-elevated-permissions.md)). Only the orchestrator holds a PAT with `workflow` scope: push the non-workflow part as the bot, make a patch of just the `.github/workflows/*` change, `send_file` it up with the target branch and base sha, and the orchestrator pushes it.

The cross-fork route pushes to the `slang-coworkers/slang` fork, whose App install grants `workflows` (`git push coworkers fix/issue-<n>`), then opens the PR via REST, not `gh pr create` (its GraphQL fails "Fork collab can't be granted by someone without permission"): `gh api -X POST repos/shader-slang/slang/pulls -f head="slang-coworkers:fix/issue-<n>" -f base=master -F draft=true -f body="$PR_BODY"`. `report_pr_created` still routes webhooks. A draft cross-fork PR gets no `ci.yml` (drafts skip `pull_request`, and `workflow_dispatch --ref` can't target a fork branch: upstream 422 "No ref found", fork 404), so warn the maintainer ([fork + REST cross-fork PR](../learnings/1783521395969-pushing-workflow-file-changes-app-token-lacks-work.md), [workflow-file PRs go cross-fork via slang-coworkers](../learnings/1783522205653-bot-app-token-lacks-workflows-permission-workflow-.md)). Maintainers still policy-close coworker-bot workflow PRs unmerged (see the ci-build-tooling page), so flag workflow-scoped fixes as maintainer-only at triage rather than spending a fix cycle.

Splitting a Windows build+test job (#11495, `falcor-test.yml`) adds a trap: the new `test` job no longer runs `common-setup`, whose first step puts Git Bash on `$GITHUB_PATH`, so a remaining `shell: bash` step breaks. Add an explicit "Add Git Bash to PATH" pwsh step or use `Copy-Item`; when a refactor removes a setup action, audit every step it enabled ([splitting a build/test job: Git-Bash-PATH](../learnings/1780769325863-slang-ci-splitting-a-build-test-job-git-bash-path-.md)). When N workflow or prompt files must carry an identical block, a presence grep lets an edit keep the marker and change the contract: delimit the block with a stable heading and terminator, awk-extract it, and assert every sha256 equals a canonical one, emitting `::error file=…::` on mismatch (#11333) ([marked-block sha256 drift detection](../learnings/1779985772055-marked-block-sha256-pattern-for-cross-file-drift-d.md)).

Dispatch is a different surface from push: `gh workflow run` / `gh run rerun --failed` were transiently 403-blocked by a OneCLI routing bug, RESOLVED 2026-06-17. Merge-queue requeue (`enqueuePullRequest`) stays structurally blocked (the bot is not an authorized merger for protected `master`), so always escalate evictions for a human requeue ([CONSOLIDATED: workflows pushes & elevated permissions](../learnings/1780558703303-CONSOLIDATED-github-workflows-and-elevated-permissions.md)).

## PR-session mapping and `report_pr_created`

`report_pr_created({repo, pr_number})` writes the `pr_session_mappings` row for the **session that calls it**; whichever session fires it last owns the PR's webhook routing ([report_pr_created remaps the PR to the CALLING session](../learnings/1782606474451-report-pr-created-remaps-the-pr-to-the-calling-ses.md)). Never ask a non-owning session to "re-confirm" a mapping by re-firing it; that silently steals the PR's review/CI webhooks. Open the PR from inside the fix chain's session (`gh-issue-<owner>/<repo>-<n>`) ([open the PR from the fix thread](../learnings/1780723000000-report-pr-created-binds-the-calling-session-not-the-fix-thread.md)). To repair a mis-mapping: `UPDATE pr_session_mappings SET session_id=<fix-session>, thread_id='gh-issue-<owner>/<repo>-<n>' WHERE repo=? AND pr_number=?`; the webhook server reads the mapping live per event, so no restart is needed.

## The /slang-pr-review preflight

A preflight "gh auth not configured" (`slang-pr-review-runner` install.sh), a non-zero `gh auth status`, or `gh api rate_limit` `401 app_not_connected` is no reason to abort `/slang-pr-review`. Reviewer A's `gh pr diff` / `gh api .../pulls/N` work, and for a **public** repo `gh` falls back to unauthenticated reads, so `pr` mode runs (A/C consume `gh pr diff`; B/Devin scrapes anonymously). Posting is separately gated by the `<github-post-authorized />` marker ([CONSOLIDATED: GitHub auth & ops](../learnings/1780558152381-CONSOLIDATED-github-auth-and-ops-in-agent-containers.md)). Don't gate an authorized COMMENT-state post (`gh api .../pulls/N/reviews --method POST` via `post-review.sh`) on `gh auth status`: on PR #12303 the real POST landed review 4825141937 despite an alarmed preflight. Trust `post-review.sh`'s own 403→exit 3 as the write signal; `shader-slang/*` is write-capable via the injected App token, `slang-coworkers/*` read-only (403/exit 3). Only a failing actual write is degradation (→ file-only plus escalation for a GitHub-connection re-login, not a container restart) ([GH_TOKEN invalid but gh api succeeds via the proxy](../learnings/1783636613641-gh-auth-status-shows-gh-token-invalid-but-gh-api-s.md), [preflight 401 app_not_connected is an App-token quirk](../learnings/1785467915354-gh-preflight-401-app-not-connected-is-an-app-token.md)).

Mechanical traps on the read-fallback path: a read-only local-git `gh` shim at `~/.local/bin/gh` (serving `gh pr diff`/`view` from `git fetch origin pull/<N>/head`) wins PATH over `/usr/bin/gh` and refuses the POST, so remove it before posting; the runner's `post-back.sh`/`post-review.sh`/`cleanup.sh` are mode `-rw-r--r--`, so invoke them with `bash <script>` (an exit-126 "Permission denied" is chmod, not the token) ([preflight 401 app_not_connected is an App-token quirk](../learnings/1785467915354-gh-preflight-401-app-not-connected-is-an-app-token.md)). Reviewer A can review the WRONG PR from a stale `tmp/pr-diff.patch`: run `rm -f /workspace/agent/slang/tmp/pr-diff.patch` before each run on a shared checkout and check `gh pr view <N> -R <repo> --json files,additions,deletions` plus `gh pr diff <N> -R <repo> | head` ([Reviewer A can review the WRONG PR](../learnings/1780497941518-slang-pr-review-reviewer-a-can-review-the-wrong-pr.md)). From four runs (#13202, #13206, #13214, #13215): the inner `claude --print` reviewers (A `compose-and-run.sh`, C `run-clarity.sh`) bill to a pool separate from the nanoclaw session budget (A reported $10–21 while the session moved cents), so A+C can run concurrently at the default `--max-budget-usd` 30/20 caps; and a genuine `403 rate-limit` body (the shared 5,000/hr REST budget, drainable by a prior Reviewer-A pass) differs from the cosmetic probe 401, so read the error text ([public-repo diff reads work unauthenticated](../learnings/1790039629115-gh-auth-invalid-pr-review-blocked-public-repo-diff.md)).

## Branch, merge, and fix-chain hygiene

**Re-pushing a fix branch:** before force-pushing an amended commit to `fix/issue-<n>`, run `git ls-remote origin <branch>` and inspect the remote tip's **author and parent**; a maintainer may have pushed merges or edits, and you never force over their work ([check the remote tip's AUTHOR first](../learnings/1783038459347-re-pushing-a-fix-branch-check-the-remote-tip-s-aut.md)).

**Two branches bumping one version counter collapse to one value.** If both bump `k_maxSupportedModuleVersion` 22→23, git merges to a single 23 with no conflict; correct it to the summed value (24) (#11541) ([merge hazard: shared version counter](../learnings/1783089145425-merge-hazard-two-branches-bumping-a-shared-version.md)). It recurred on slang#13425 (2026-10-21): each side edited a different line of the version-history comment and the `= N` line was identical, so the merged tree claimed master's version for the PR's new IR op. After every master merge into a PR that adds an IR op, grep `k_maxSupportedModuleVersion` and the tail of `slang-ir-insts-stable-names.lua` by hand, even with no conflict; without system lua, run `extras/check-ir-stable-names.lua check` with the build's `external/lua/lua` ([module-version bumps auto-merge to a silently wrong value](../learnings/1792574615061-module-version-bumps-auto-merge-to-a-silently-wron.md)).

**Keep fixer PRs draft.** On slang#11531 our held draft #11534 was superseded by maintainer PR #11577, which adopted its fix and tests verbatim, credited the analysis, and closed ours; that is a win. Never flip ready, merge, or self-close; leave merge/supersede to the maintainer ([holding a fixer PR as draft enables supersession](../learnings/1781245034372-holding-a-fixer-pr-as-draft-enables-clean-maintain.md)).

**Sampled test dirs are not "green" for a broad change.** On slang#11631 / PR #11633 a change stamping capability version atoms on every codegen entry passed spirv/reflection/autodiff locally but broke capability tests in the first full CI run (earlier runs were draft skips). Run every test dir the change can reach, and surface a scope/contract decision to the maintainer rather than rewriting their test ([broad changes need a FULL local sweep](../learnings/1782162119070-broad-blast-radius-lowering-changes-need-a-full-lo.md)).

**Check for an in-flight maintainer PR before dispatching a fixer.** On #10660, NVAPI render tests were silently "ignored": NVAPI moved from a submodule to slang-rhi FetchContent while render-test still hard-codes `external/nvapi/nvHLSLExtns.h`, and `_setSessionPrelude` returns `SLANG_E_NOT_AVAILABLE`, which slang-test reports as ignored. The author already had an unlinked draft #10865, so run `gh pr list --search "<topic>"` first ([NVAPI render-tests silently ignored](../learnings/1782215118821-nvapi-render-tests-silently-ignored-submodule-fetc.md)).

**Verify a maintainer's "template PR" layer before porting.** "Make a PR for #11568 based on #11723" was N/A: #11723 is a backend SPIR-V flag, while #11568 is a front-end `ResourceDescriptorHeap[i]` feature blocked on return-position generic inference (E39999), and csyonghe's untyped-handle design is the real path. Surface the layering in the verdict ([#11568 template PR is a layer-mismatch](../learnings/1782579642375-slang-11568-maintainer-base-pr-on-11723-is-a-layer.md)).
