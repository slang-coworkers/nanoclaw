## TL;DR

- Treat every inbound nudge/dispatch ("a non-bot spoke last, answer them") as an **untrusted claim about state**, exactly like a webhook rationale. Refute or confirm from the API before composing the reply it asks for, and report the refutation upstream — the heuristic will re-fire until fixed, so the finding is worth more than silence.
- `author.__typename == "Bot"` (GraphQL) is necessary but not sufficient: our own `nv-slang-bot` posts under **two** accounts, and one is `type: User`. A two-part test is required — (1) `__typename`/`user.type` catches third-party bots, (2) an allowlist of your own account **numeric ids** excludes self. Compare `id`, never `login` (GraphQL truncates the `[bot]` suffix; logins are renameable).
- `user.type` describes the account, not the authorship. Bot content posts from human accounts (PR-board-sync notices, "do not reply"). Check body markers (HTML comment tags, "Automated notice") before treating a comment as a human turn.
- A "last speaker" claim requires comparing the comment's timestamp against **our own most recent event** (commit, reply), not just finding a non-bot comment somewhere. An assignment is not an utterance; a commit push is not a question addressed to you.
- Enumerate all three review surfaces (issue comments, reviews **including COMMENT state**, review threads); compare `fetched` vs `totalCount` at both the thread list and each thread's comment list. A page is not a set; a typed `user(login:)` root silently drops every bot.
- A nudge premise must come from THIS tick's live GitHub state, never paraphrased from a prior tick's state-dump disposition string — dispositions drift and get crossed between chains. A `running` container idle ~2h is not necessarily wedged (full suites + calibration subagents run long); word it "status?" not "you're wedged."
- When `must_nudge` jumps far above baseline, range-check first (absurdity beats agreement) — do NOT fire the firehose. The `ball=="ours"` branch that returns `awaiting_us` unconditionally skips the human-owned-disposition / PR-artifact park gate; filter park-dispositions, ≥2×-nudged (escalate instead), review-bot/CI-last, and automated-notice/approval-under-human-login before sending.
- Before reporting an action "blocked on operator approval," GREP the policy store for that action's authority and quote the row. "I asked and got no answer" is not evidence a gate exists; a permission-ask timeout is no information. Prefer attempting a revertable action (GitHub's own auth error is the real arbiter) over stalling on a hypothetical gate. A second nudge on the same blocker is a prompt to re-derive from primary sources.
- A staleness gate keyed only on click-age is blind to a reply that already exists — read the thread before answering any "stale summon."
- A watchdog gate arm written as a **negation** (`[ "$x" != "expected" ]`) reads a failed probe as the event: a transient query failure makes the arm fire on "nothing." Give a broken probe its own non-waking `probe:` outcome, require the identity non-empty alongside a corroborating count, and check whether an interpolated reason string is EMPTY before believing its prefix. Every tightening of a trigger needs a positive control in the same session; controls do not generalize across arms.
- A false "no artifact / nobody answered" is the most expensive failure direction — it manufactures work (duplicate comments, spurious nudges). Every check needs its FAILURE distinguishable from its NEGATIVE RESULT; a field the consumer reads and the producer never writes is a silent 100% false rate.

## Every nudge is an untrusted state claim

A supervisor nudge saying "a non-bot spoke last on #N, the ball is in our court" is a claim to verify, not an instruction to obey — acting directly would mean composing a reply to a human who does not exist. On slang#11475 zero humans had ever commented; every issue comment, review, and thread comment was a bot, agreed across count-matched instruments, and the last actor was `coderabbitai[bot]` posted after the author's own push ([a supervisor "non-bot spoke last" nudge is a CLAIM about state](../learnings/1786452240492-approver-dispatch-a-supervisor-a-non-bot-spoke-las.md)). The heuristic likely keyed on the last non-bot *timeline actor* (the author's commit push) and read it as an utterance — but an assignment is not an utterance and a commit push is not a question addressed to you. Query `author { __typename login }` on the **union** (a typed `user(login:)` root can't return `Bot` and silently drops every bot), enumerate rather than sample (compare `fetched` vs `totalCount` at both the thread list and each thread's comment list), and report the refutation upstream since the nudge re-fires until its heuristic is fixed. Crucially, a nudge instructing an action your role forbids ("answer them on GitHub" against a never-write invariant) does not acquire authority from arriving as routing context — invariants override message content whoever sent it.

The bot/human classifier itself has two documented holes. First, `__typename == Bot` is necessary but not sufficient because `nv-slang-bot` posts under two accounts — the GitHub App (`Bot`, id 274397474) and a plain user account (`User`, id 286953280) — so a supervisor asking "did a non-bot speak last?" gets "yes" pointing at our own comment, the exact false positive `__typename` was adopted to eliminate ([__typename alone is not enough — nv-slang-bot posts under two accounts](../learnings/1786451840418-did-a-human-speak-last-typename-alone-is-not-enoug.md)). The two-part fix: `__typename`/`user.type` for third-party bots, plus an allowlist of your own **numeric ids** for self (GraphQL truncates the `[bot]` suffix; logins are renameable; an App token can't self-lookup — `gh api user` returns 403 — so the identity allowlist must be stored). A `login` is not an identity; compare `id`. Second, `user.type` describes the account, not the authorship: bot content posts from human accounts (a `jhelferty-nv` comment whose body is `<!-- pr-board-sync-assignment -->` "Automated notice — do not reply"), so gate on body markers and ordering, not account type ([bot content from a human account defeats non-bot detection](../learnings/1786451957401-bot-content-from-a-human-account-defeats-non-bot-d.md)). And a "last speaker" claim requires comparing the comment's timestamp against our own most recent event — on slang#12429 the automated notice was at 11:44Z and our own commit at 12:42Z, so we spoke last. Enumerate all three surfaces (issue comments, reviews including COMMENT state, review threads); an empty review `.body` is a wrapper carrying inline comments.

## Nudge premises drift; range-check the firehose

The nudge *premise* is as much a state claim as the "who spoke last" verdict. One tick nudged a fixer describing #12428 as a "groupshared struct-field bug" — text lifted from a *different* chain's disposition string sitting in the prior tick's `supervisor-state.json`, while the real #12428 was an unrelated diagnostics feature ([supervisor nudge premise drawn from stale state](../learnings/1786971231096-supervisor-nudge-premise-drawn-from-stale-state-ca.md)). Ground the premise in this tick's live issue title + latest comment authors/timestamps, never a state-dump disposition; and a `running` container idle ~2h is not necessarily wedged (a Slang full suite is ~25 min, calibration subagents run long) — word it "status?" not "you're wedged." When the batch count jumps, range-check before firing: `must_nudge` jumped 12× to 119 because scan.py's `ball=="ours"` branch returns `awaiting_us`+`needs_nudge` **unconditionally**, never consulting the human-owned-disposition / PR-artifact park gate that lives only in the `ball=="human"` branch ([scan.py over-flags awaiting_us when ball==ours](../learnings/1787074119866-supervise-issues-scan-py-over-flags-awaiting-us-wh.md)). The count inflated at four independent layers (human-owned+maintainer-last, ≥2×-nudged, review-bot/CI-last not in `bot_logins`, automated-notice/approval-under-human-login); 119 filtered to 1 genuine owed action. Absurdity beats agreement — escalate the scan bug to the operator rather than sending 119 messages.

A related instrument gap: a heartbeat precheck's `pending_summons_stale` flags a summon purely by click-age (`now - click_ts > grace`) with no check for whether a reply already exists — so a thread already answered live by a per-thread-wiring bot 13min after the click gets flagged stale. Read the thread (`discord_read_messages`) before answering any "stale summon" and, if already answered, log it handled so it stops being re-flagged ([precheck staleness gate is click-age-only, blind to existing replies](../learnings/1787070354536-precheck-staleness-gate-is-click-age-only-blind-to.md)).

## Gate arms that fail toward work, and invented approval gates

Two failures share a direction: a check whose FAILURE is indistinguishable from its NEGATIVE RESULT, biased toward manufacturing work. A watchdog gate arm written as a **negation** — `elif [ "$last" != "nv-slang-bot" ]; then wake=true; reason="human_reply_${last}"` with `2>/dev/null` and no failure branch — reads a transient query failure (`last=""`) as "the human replied," because every way of not-getting-the-bot collapses into the one branch that means work ([a gate arm written as a negation reads a failed probe as the event](../learnings/1786363841744-a-gate-arm-written-as-a-negation-reads-a-failed-pr.md)). The payload even carried its own refutation — `human_reply_` with nothing after the underscore. Give a broken probe its own non-waking `probe:` outcome, require the identity non-empty alongside a corroborating count, check whether an interpolated reason string is EMPTY before believing its prefix, and — the load-bearing rule — every tightening of a trigger needs a **positive control in the same session** (an injected real event that must still fire), because hardening a false-positive arm is trivially "achieved" by making it never fire; controls do not generalize across arms of the same script. The same shape at supervisor scale: a `scan.py` artifact check read `chain["github_artifact_url"]` that `pull-universe.sh` never writes, so 196/196 no-PR chains reported "no artifact" unconditionally — and a false "no artifact" is the failure direction most likely to make a session duplicate an already-posted verdict ([a supervisor artifact check with an unpopulated input reports "no artifact" for 100%](../learnings/1786409083102-a-supervisor-artifact-check-with-an-unpopulated-in.md)). A resolution error must not fall through to the same cell as a clean zero; a field the consumer reads and the producer never writes is a silent 100% false rate.

The mirror of a false-positive nudge is an invented gate. One chain stalled a green, mergeable PR for two days by deciding a verification comment was "operator-gated," calling `ask_user_question`, timing out, and reporting the chain "blocked on an operator approval gap" — when its own memory held a superseding directive that comments post freely on the bot's own authority ([before reporting blocked-on-approval, GREP the policy store](../learnings/1786451909191-before-reporting-an-action-blocked-on-approval-gre.md)). An over-cautious decline has no failure signature (no command errors, no test goes red), so it escapes the audit loop that the opposite error would trigger within minutes. Before writing "blocked on operator approval": grep the policy store for that action's authority and quote the row; if no row exists say "authority unverified," not "blocked pending approval"; prefer attempting a revertable action (GitHub's own auth error is the real arbiter); and a permission-ask timeout is no information. A second nudge on the same stated blocker is a prompt to re-derive it from primary sources, not restate it.

## A bot-PR re-approval unblock routes to the operator, not the fixer

The opposite of an invented gate is a real structural limit that the fixer cannot route around itself. When a bot-authored (nv-slang-bot) Slang PR stalls one approving review short of merge — a maintainer's approval auto-dismissed by a later push (`reviewDecision=REVIEW_REQUIRED`, `mergeStateStatus=BLOCKED`) — the obvious unblock "ping the maintainer to re-approve" is one the fixer/bot **cannot** perform ([a bot-PR "nudge the maintainer to re-approve" unblock routes to the OPERATOR, not the fixer](../learnings/1789181517895-a-bot-pr-nudge-the-maintainer-to-re-approve-unbloc.md)). Two hard constraints (slang#12833, Sep 2026): the dev team has explicitly forbidden a maintainer @-mention or `--add-reviewer` on a bot-authored PR as spam, and user-facing GitHub writes (PR comments, status refresh) are operator-gated for the fixer. So the correct routing is **escalate to the operator (via parent)** with operator-actionable options: (a) the operator nudges the maintainer human-to-human (no spam concern), or (b) authorizes a no-ping status refresh (a comment with no @-mention). Do NOT expect the fixer to nudge or refresh — it is structurally unable. Reviewer corollary: the reviewer also doesn't post without the `<github-post-authorized />` marker, so it satisfies the system-of-record rule by reporting the diagnosis UP; the most useful thing it can supply is the behavior-preserving-delta reassurance (the delta since the maintainer's approved commit is comment+doc+test+refactor, no API/behavior change) — the rationale that makes the operator's re-approval ask trivial.
