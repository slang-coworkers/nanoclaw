# Slang WGSL emit: matrix-operator validity and storage orientation, template-list ambiguity, buffer-element gaps, enable/requires directives, push constants, and GPU-free naga/Tint validation

Slang's WGSL emitter (`slang-emit-wgsl.cpp`) can produce text that compiles with rc 0 but is rejected by wgpu/naga. The recurring families are expressions that are legal in the Metal/HLSL shapes the emitter mirrors but not in WGSL (matrix negation, non-float matrices), comma-separated lists that WGSL's template-list grammar mis-parses, buffer-element lowering that leaves non-host-shareable or untyped values behind, and built-ins whose `enable` directive is never requested. All of them can be checked without a GPU, with naga-wasm or with the real Tint front end through Dawn's null backend. The broader WGSL backend lives on [[wiki/concepts/slang-backends-wgsl-metal.md]]; WGSL via Tint is on [[wiki/concepts/slang-backends-f0909b0-glsl-wgsl-bindless.md]]. WGSL f16, `half`→`u16` producers and const-expression NaN/Inf are on [WGSL f16, sub-word storage and const-expressions](slang-backends-wgsl-f16-and-const-expressions.md); `DescriptorHandle` spelling and WGSL resource tables are on [DescriptorHandle emit and bindless targets](slang-backends-descriptor-handle-emit-and-bindless-targets.md).

## TL;DR

- **GPU-free WGSL check: `npm install naga-wasm@30.2.0`, then `validate(parseWgsl(src))`.** It throws on parse or validation errors, needs no Rust toolchain, and works on node 22 despite a node >=24.12 warning.
- **naga-wasm 30.2 and Tint have different blind spots, so use Tint for any verdict on f16, subgroups, uniformity, const-expressions or new directives.** naga-wasm rejects spec-valid `bitcast<vec2<f16>>(u32)`, every `enable subgroups;` and `requires immediate_address_space;`, and runs no uniformity analysis.
- **Real Tint without a GPU: `npm install webgpu@0.6.2`, `create(['backend=null'])`, then `createShaderModule({code}).getCompilationInfo()`.** Request `shader-f16` (and `subgroups`) in `requestDevice`, or every `enable f16;` is a harness false negative. Set `XDG_RUNTIME_DIR=/tmp` and end with `process.exit(0)`.
- **`subgroups_f16` no longer exists** (removed from Dawn/Tint in Apr 2025). f16 subgroup ops need only `enable f16; enable subgroups;`, yet Slang still emits `enable subgroups_f16;` whenever `half` and any subgroup op meet (#13636).
- **Tint's own lowering (`src/tint/lang/wgsl/reader/lower/lower.cc`) is the cross-target reference for a WGSL built-in's meaning**: `workgroupUniformLoad(p)` is barrier; load; barrier, which Slang's non-WGSL arms drop (#13631). DeepWiki describes current code, not design intent.
- **WGSL push constants are `var<immediate>`** (module scope, no `@group/@binding`, no arrays, at most one per entry point). Slang emits `var<uniform>` with no binding (#13639), and every buffer matrix becomes a `_MatrixStorage_*` array, which `var<immediate>` forbids.
- **A native WGSL `matRxC` in a buffer equals Slang `row_major` storage byte for byte**; Slang `column_major` (the slangc CLI default) is its transpose and needs `matCxR` plus `transpose()`.
- **Directive order is checked by Tint**: a `__requirePrelude("diagnostic(...)")` can land after a helper `fn` in the shared insertion-ordered prelude set, giving "directives must come before all global declarations".
- **WGSL template-list ambiguity (§3.9):** in `f(a < b, a > b)` the `a <` opens a candidate template list, commas do not clear it, and the later `>` (including `>=`) closes it, so the list mis-parses. `<=` and `<<` never open one. Slang emits call and constructor args at `EmitOp::General`, where `maybeEmitParens` does not parenthesize relational operators (#13566).
- **To exercise WGSL `select(...)` argument lists, use vector `&&`/`||`** (`(u <= v) && (u >= v)` on `float2`). A `{a, b}` struct initializer lowers to a synthesized-ctor call, not `kIROp_MakeStruct`, so it only re-tests the call-argument path.
- **For a "wrap this op in parens" emit fix, reuse the shared printer**: `emit("("); defaultEmitInstExpr(inst, getInfo(EmitOp::General)); emit(")");` (Metal's MakeArray uses the same pattern).
- **WGSL has no unary `-` on matrices and no single-scalar matrix constructor.** `matCxR<T>(0) - m` is invalid (`vecN<T>(0)` is a valid splat). Emit `T(-1) * m` (keeps IEEE -0) or `matCxR<T>() - m`. Scalar `uint` `- x` is also naga-rejected (#13571).
- **int64/uint64 matrices survive `legalizeMatrixTypes` on WGSL** (only 32-bit `IRIntType`/`IRUIntType`/`IRBoolType` are lowered) and emit `mat2x2<i64>`, which naga rejects. A WGSL emitter `SLANG_ASSERT(isFloatingType(matrixElt))` is reachable from user code, and in Release it is `[[assume]]` UB.
- **Probe more than one source spelling before calling a shape unreachable** — `int64_t2x2(...)` gave E38203 where `matrix<int64_t,2,2>(...)` compiled.
- **`bool` inside `var<uniform>`/`var<storage>` is emitted with rc 0 but is not host-shareable (#13590).** Three gaps in `slang-ir-lower-buffer-element-type.cpp` must be fixed together: the bool→int leaf mapping exists only in the Khronos policy (all WGSL targets, Tint ones included, use `WGSLBufferElementTypeLoweringPolicy`); the std140 array-element widening replaces the leaf's cast with `VectorReshape` instead of composing the two; and `needsElementLowering` skips top-level `vector<bool,N>`.
- **A bare WGSL expression statement (`x.data_0[i32(N)].x;`) usually means an IR inst with a null type, not an emitter bug.** The `kIROp_VectorReshape`→scalar peephole built its swizzle with a null `resultType`; the fix is `emitSwizzle(inst->getDataType(), …)` (#13607).
- **When a PR turns an ICE into rc 0, validate the new output with naga or spirv-val**, on shapes beyond the PR's own type.
- **wgpu-py is the pip-only naga validator** (`pip install wgpu`, user or venv), and its `create_compute_pipeline(layout="auto")` also catches `var<uniform>` alignment errors. naga enforces §11.4 pointer-argument address spaces and rejects `ptr<workgroup>` params. A slang-tint stub library only captures WGSL; it validates nothing.
- **On WGSL, `-force-glsl-scalar-layout`/`-fvk-use-c-layout` change the entry-point uniform buffer's IR layout while reflection stays std140 (#13704)**, so the host offsets and the shader disagree.
- **An undefined resource value (`LoadFromUninitializedMemory`/`Poison` of a `Texture2D`) gives rc 0 and invalid output on GLSL and WGSL.** `checkUnsupportedInst` rejects only an opaque `DefaultConstruct`, so validate with `-emit-spirv-via-glsl` (glslang) and Tint.
- **`@builtin(primitive_index)` needs `enable primitive_index;` (naga ≥29, Tint/Chrome 142), and the WGSL varying legalizer cannot request enables.** The producer-side hook is a required-extension field on `SystemValueInfo` plus `addRequireWGSLExtensionDecoration`. A raw `SV_WaveLaneIndex` parameter likewise omits `enable subgroups;`.
- **The #13572 fix lowers every non-float matrix on WGPU** (`return !isFloatingType(elementType)`), and the existing 32-bit vector-width validation then reports E38203. A regression test built from int64 *scalars* is vacuous, because AST lowering already makes an int64 vector and E38203 fires on the old build too. Build the matrix from a float-matrix cast, and write location-less annotations (the lowered vector has no source location).

## Validating WGSL in-container: naga-wasm vs. real Tint

You can check whether Slang's WGSL output parses and validates in wgpu/Naga without a GPU or a Rust toolchain. `npm install naga-wasm@30.2.0` installs the naga translator compiled to WASM (it warns about node >=24.12 but works on node 22):

```js
import { parseWgsl, validate } from "naga-wasm";
const m = parseWgsl(src); validate(m);  // throws on parse/validation error
```

It is the cheapest oracle for the emitter bugs below: each naga error message quoted on this page came from it ([GPU-free WGSL parse/validate check: naga-wasm](../learnings/1791663423398-gpu-free-wgsl-parse-validate-check-naga-wasm-via-n.md)). A second naga route needs only pip and also runs pipeline-level checks. `pip install --user --break-system-packages wgpu` (0.32 when measured; or into a venv, `python3 -m venv /tmp/wgpuenv && /tmp/wgpuenv/bin/pip install wgpu`) bundles wgpu-native and naga (29.x); then call `wgpu.gpu.request_adapter_sync()` → `request_device_sync()` → `create_shader_module(code=src)` inside a `try` (it raises the naga error with a source span) → `create_compute_pipeline(layout="auto", compute={"module": m, "entry_point": "main"})`. On the L40S fleet it picks the Vulkan adapter (the `XDG_RUNTIME_DIR` warnings are harmless), and pipeline creation is where naga rejects a bad `var<uniform>` layout with "Alignment requirements for address space Uniform". naga enforces WGSL §11.4: a pointer argument must match the parameter's address space ("Argument 0 value doesn't match the type"), and `ptr<workgroup,T>` function parameters are rejected. That confirmed the explicit-`__constref` WGSL bugs of #13703/#13709, two of them on master too: a `static` global argument emits `&(var<private>)` into a `ptr<function>` parameter (the #12173 family on [[wiki/concepts/slang-backends-wgsl-metal.md]]), and a `groupshared` argument makes a `ptr<workgroup>` parameter. It has naga's blind spots, listed below, so a report says which validator ran. A slang-tint stub library (`scratch-13391/libslang-tint.so`, see the bindless/Tint page) only captures the WGSL that Slang hands to Tint and validates nothing (`-target wgsl-spirv-asm` fails with it), so pass the captured text to one of these validators ([validate WGSL locally with naga via wgpu-py](../learnings/1792441518888-validate-slang-wgsl-output-locally-with-naga-via-w.md)). The case that prompted the recipe (#13704) is a WGSL IR-vs-reflection split: `slang-ir-entry-point-uniforms.cpp:559` sets the synthesized entry-point constant buffer's layout op from `-force-glsl-scalar-layout`/`-fvk-use-c-layout` with no target check. WGSL lowering honours that op (Natural/C rule), while `WGSLLayoutRulesFamilyImpl` reflection ignores every layout option and stays std140; HLSL, Metal, C++ and CUDA ignore the op (`getTypeLayoutRuleNameForBuffer:2416`), and `-fvk-use-dx-layout` breaks WGSL uniforms through `:2460` ([wgpu-py (naga) is a pip-installable real WGSL validator](../learnings/1792162080215-wgpu-py-naga-is-a-pip-installable-real-wgsl-valida.md)).

naga is not the reference compiler, though, and it is wrong in both directions on recent WGSL. naga-wasm 30.2.0 (and naga generally, so wgpu-py too) rejects the spec-listed f16 bitcasts `bitcast<vec2<f16>>(u32)` ("expected vec2<f16>, got f32") and `bitcast<u32>(vec2<f16>)` (§17.2.1) ([naga-wasm rejects spec-valid f16 bitcasts](../learnings/1792085330619-naga-wasm-rejects-spec-valid-wgsl-f16-bitcasts-val.md)). It rejects every `enable subgroups;` as "not yet supported" ([naga-wasm cannot validate `enable subgroups;`](../learnings/1792070896998-wgsl-subgroups-f16-is-dead-naga-wasm-30-cannot-val.md)), and `requires immediate_address_space;` as an unknown language extension even though it accepts `var<immediate>` itself ([naga 30.2 `var<immediate>` support gap](../learnings/1792071495705-wgsl-var-immediate-push-constants-spec-rules-naga-.md)). It does not run the uniformity analysis, and it misses Tint-only errors such as a NaN/Inf const-expression or a user-function call at module scope. Version-match the validator before trusting a pass or a fail on new WGSL features, and use Tint for any verdict involving f16, subgroups, uniformity, const-expressions or new directives.

**The real Tint front end runs in the container through Dawn's null backend.** `npm install webgpu@0.6.2` (dawn-gpu/node-webgpu, about 137 MB, ships linux-x64), then in an ESM script:

```js
import { create, globals } from "webgpu"; Object.assign(globalThis, globals);
const gpu = create(["backend=null"]);
const dev = await (await gpu.requestAdapter()).requestDevice({ requiredFeatures: ["shader-f16", "subgroups"] });
const m = dev.createShaderModule({ code });
console.log((await m.getCompilationInfo()).messages); process.exit(0);
```

Messages carry line and column and match the `tint` CLI text. The null adapter reports `subgroups` and `shader-f16`, the wgslLanguageFeatures (including `immediate_address_space`) and limits (`maxImmediateSize=64`), so it matches what WGSL issue reporters see in Chrome. Use `backend=null`: the default Vulkan backend needs `XDG_RUNTIME_DIR` (set it to `/tmp` anyway to silence warnings) and then rejects lavapipe/llvmpipe for missing `shaderUniform*ArrayDynamicIndexing`. Without `process.exit(0)` the process may hang ([dawn.node null backend catches uniformity errors](../learnings/1792071853801-gpu-free-tint-wgsl-validation-uniformity-errors-in.md), [real-Tint validation via node webgpu](../learnings/1792074422249-gpu-free-real-tint-wgsl-validation-via-node-webgpu.md), [null adapter reports language features and limits](../learnings/1792086855977-gpu-free-tint-wgsl-validation-dawn-node-webgpu-nul.md)). The device must request `shader-f16`: the triager's `/workspace/agent/tools/tint-validate/tint-validate.mjs` calls `requestDevice()` with no features, so every `enable f16;` fails with "extension 'f16' is not allowed in the current environment", a harness false negative. A `var x : u16` line is a good negative control ("u16 is unsupported in WGSL") ([tint-validate.mjs rejects all f16 unless shader-f16 is requested](../learnings/1792085503561-tint-validate-mjs-rejects-all-f16-wgsl-unless-the-.md)). The same Null backend is reachable from C by linking the prebuilt Dawn that slang-rhi fetches (`<rhi-build>/_deps/dawn-src/{include,lib64/libdawn.so}`), with `timedWaitAnyEnable=1`, `WGPUBackendType_Null` and `WGPUFeatureName_ShaderF16` (harness: slang-fixer `reports/tint-wgsl-validator.c`). In a Slang build the wgpu backend exists only with `-DSLANG_EXCLUDE_DAWN=OFF` (the Linux default), and `-wgpu` COMPARE_COMPUTE rows still report "Not Supported" on llvmpipe for the same Vulkan-feature reason [naga-wasm rejects spec-valid f16 bitcasts](../learnings/1792085330619-naga-wasm-rejects-spec-valid-wgsl-f16-bitcasts-val.md). In-tree `wgsl-spirv-asm` (Tint) rows are ignored on Linux, because slang-tint is fetched only for Windows x64, so this harness is the local Tint oracle ([PackedFloat types never reach the WGSL FloatLit switch](../learnings/1792099072974-slang-packedfloat-types-bf16-fp8-never-reach-the-w.md)).

Tint facts measured this way: a function `@diagnostic` attribute does not cover its callees; a conflicting severity for the same rule is an error; an unknown rule only warns; `derivative_uniformity` and `subgroup_uniformity` are independent rules (subgroup ops get "'subgroupAdd' must only be called from subgroup uniform control flow"); and directives must precede every global declaration. Slang can violate the last one, because WGSL helper preludes share an insertion-ordered set, so a `__requirePrelude("diagnostic(...)")` can land after `fn _slang_getNan()` [dawn.node null backend catches uniformity errors](../learnings/1792071853801-gpu-free-tint-wgsl-validation-uniformity-errors-in.md).

**Spec and Tint sources without a browser.** Tint's extension list is the `enum extension` block of `curl https://raw.githubusercontent.com/google/dawn/main/src/tint/lang/wgsl/wgsl.def`. Other Dawn files come from `curl -sL "https://dawn.googlesource.com/dawn/+/refs/heads/main/<path>?format=TEXT" | base64 -d`, and commit messages from googlesource `+/<sha>?format=JSON` with the 4-byte `)]}'` prefix stripped; `gh api repos/google/dawn` returns 401 through the gateway. Fetch the WGSL spec with `curl -sL https://gpuweb.github.io/gpuweb/wgsl/` and strip tags in Python; WebFetch to w3.org returned 429 ([subgroups_f16 is dead](../learnings/1792070896998-wgsl-subgroups-f16-is-dead-naga-wasm-30-cannot-val.md), [Tint's lowering is the cross-target reference](../learnings/1792071135841-wgsl-built-in-semantics-use-tint-s-lowering-as-the.md)).

## Template-list ambiguity in comma-separated argument lists (#13566)

Consider `vec2<bool>(a_0 < b_0, a_0 > b_0)`. naga reports "expected `)`, found b_0". WGSL §3.9 disambiguates template lists syntactically: `ident <` opens a candidate list, commas do not clear it, and a later `>` (including `>=`) closes it, while `<=` and `<<` never open one. Slang emits call and constructor arguments at `EmitOp::General`, and `maybeEmitParens` does not parenthesize relational operators at that precedence, so the bare comparison reaches the output. User-side workarounds mostly fail: source parens `(a < b)` are dropped and locals get folded back into the call; only rewriting so that no `<` is followed by `>` in the same list (`b < a`) works [same](../learnings/1791663423398-gpu-free-wgsl-parse-validate-check-naga-wasm-via-n.md).

Testing the fix (PR #13569) needs inputs that actually reach each comma-separated emit path. `Flags f = { a < b, a > b };` does not reach the WGSL `kIROp_MakeStruct` case: it lowers to a call of the synthesized constructor `Flags_x24init_0(...)` and only re-tests the call-argument path (see [[wiki/concepts/slang-language-core-struct-construction-lowering.md]]). To exercise the `select(...)` argument lists, use vector `&&`/`||`, such as `(u <= v) && (u >= v)` on `float2`, which the WGSL emitter lowers to `select(vec2<bool>(false), rhs, lhs)`. For the emit side, `m_writer->emit("("); defaultEmitInstExpr(inst, getInfo(EmitOp::General)); m_writer->emit(")");` reuses the shared printer instead of copying it, the same wrap-the-default pattern Metal uses for MakeArray [a `{a, b}` initializer list on WGSL lowers to a synthesized ctor call](../learnings/1791675327416-slang-a-b-initializer-list-on-wgsl-lowers-to-a-syn.md).

## Matrix negation: `T(0) - m` is not WGSL (#13571)

WGSL has no single-scalar matrix constructor and no unary `-` on matrices. `WGSLSourceEmitter::tryEmitInstExprImpl`'s `kIROp_Neg` case (slang-emit-wgsl.cpp ~:1756) lowered both vectors and matrices to `(T(0) - x)`. `vecN<T>(0)` is a valid splat, but `matCxR<T>(0)` is not; naga reports "cannot cast a {AbstractInt} to a mat2x2<f32>". The form was added in #7936 by mirroring Metal, where `matrix<…>(0)` IS valid MSL; #12909 fixed only the operand parens, and its test pins the invalid form. Legal replacements are `(f32(-1) * m)`, which keeps IEEE -0 like `-x`, or the zero-value constructor `mat2x2<f32>() - m`. Releases up to 2025.12 emitted `- mat2x2(...)`, also invalid, so this was never valid and is not a regression.

Int, uint and bool matrices are unaffected, because `legalizeMatrixTypes` turns them into arrays of row vectors. Matrix-plus-scalar is fine as well: `legalizeBinaryOp` splats the scalar into `MakeMatrixFromScalar`, which the base emitter expands element by element. A sibling defect is scalar `uint` negation, which emits `- x` and is also naga-rejected ("Operation Negate can't work") [WGSL matrix negation `T(0) - m` is invalid; use `T(-1) * m`](../learnings/1791749878369-wgsl-emitter-matrix-negation-t-0-m-is-invalid-use-.md).

## 64-bit integer matrices reach the emitter as `IRMatrixType`

"`legalizeMatrixTypes` lowers integer matrices" is only true for 32-bit elements. `shouldLowerMatrixType` (slang-ir-legalize-matrix-types.cpp:76-78) lowers only `IRBoolType`, `IRIntType` and `IRUIntType` for WGSL, so `matrix<int64_t,2,2>` and `matrix<uint64_t,2,2>` compile with rc 0 to `-target wgsl` and emit `mat2x2<i64>(...)`, which naga rejects with "matrix scalar type must be floating-point", even for a plain `m + m`. Other element types fail earlier: int16/uint16 give E56103, and int8 and double give ICEs.

For review this means any WGSL emitter code that does `SLANG_ASSERT(isFloatingType(matrixElt))` on the grounds that integer matrices are lowered is reachable from user code, and in Release `SLANG_ASSERT` is `SLANG_ASSUME` (`[[assume]]`), so the violation is UB rather than a clean failure (found on #13572). When probing such a claim, try more than one source spelling: `int64_t2x2(buf[0],...)` with a `RWStructuredBuffer<int64_t>` gave E38203 in one probe, while `matrix<int64_t,2,2>(b[0],b[1],b[2],b[3])` with an `o[0] = float2x2(-m)[0][0]` consumer compiled cleanly [int64/uint64 matrices survive legalizeMatrixTypes on WGSL](../learnings/1791763584478-wgsl-int64-uint64-matrices-survive-legalizematrixt.md).

**The fix and its test (#13572).** On WGPU targets `shouldLowerMatrixType` now lowers every non-float matrix (`return !isFloatingType(elementType)`), so the WGPU vector-width validation in `slang-ir-validate.cpp` (allowedWidths = 32) reports E38203 instead of the emitter ICEing on `-m` or printing `mat3x3<i64>`. The first regression test built the matrix from int64 scalars, `matrix<int64_t,2,2>(b[0],b[1],b[2],b[3])`; AST lowering already creates an int64 *vector* there, so E38203 fired on the unfixed build too and the test proved nothing. Converting a float matrix (`matrix<int64_t,2,2>(floatMat)`) means no 64-bit vector exists until matrix lowering, and the old build fails the row. The diagnostic then has no source location, so the DIAGNOSTIC_TEST annotations must be location-less, without carets. This is the same spelling sensitivity as the probe above, and the general rule is to run every new diagnostic or negative row against the unfixed build before trusting it [a diagnostic test for WGSL matrix lowering can be vacuous](../learnings/1791809366702-slang-wgsl-a-diagnostic-test-for-matrix-lowering-c.md).

## Buffer-element lowering: `bool` is not host-shareable (#13590)

Consider `struct P { bool b; bool a[2]; }; ConstantBuffer<P> gC;`, or a `StructuredBuffer<bool2>`, compiled with `-target wgsl`. WGSL forbids `bool` inside `var<uniform>`/`var<storage>` because it is not host-shareable, yet Slang emits it and exits 0, so the error surfaces only downstream: naga reports "The type is not host-shareable", and Tint/Chrome reject it as well. The bug dates back to at least v2025.1. It comes from three coupled gaps in `slang-ir-lower-buffer-element-type.cpp`, and fixing any one alone does not help:

1. The only bool→int leaf mapping is in `KhronosTargetBufferElementTypeLoweringPolicy::lowerLeafLogicalType`, behind `shouldEmitSPIRVDirectly`. Every WGSL target, including the Tint WGSL→SPIR-V ones (`isWGPUTarget`), uses `WGSLBufferElementTypeLoweringPolicy`, so a WGSL case added to the Khronos switch has no effect.
2. The WGSL std140 array-element widening in `getLoweredTypeInfoImpl` overwrites the leaf's `convertLoweredToOriginal` with `VectorReshape`. With a leaf-only fix, `bool[N]` and bool matrices (already arrays of bool vectors after `legalizeMatrixTypes`) then use a `u32` as an `if` condition, so the reshape and the cast have to be composed.
3. `needsElementLowering` accepts scalar `bool` but not a top-level `vector<bool,N>`, so `StructuredBuffer<bool2>` is skipped. On SPIR-V the same shape fails spirv-val (`OpTypeBool` in StorageBuffer).

An 88-line prototype covering all three made 14 of 16 shapes pass naga with reflection unchanged. The other two are `ByteAddressBuffer` (#10207, a separate path) and push constants, which get no `@binding` on WGSL at all [WGSL bool in uniform/storage buffers: 3 coupled gaps](../learnings/1791890303067-wgsl-bool-in-uniform-storage-buffers-3-coupled-gap.md).

## A null-typed `VectorReshape` swizzle prints as a dangling statement (#13607)

The same std140 widening leads to the next silent failure. Consider:

```slang
struct S { float a[3]; };
ConstantBuffer<S> gC;
RWStructuredBuffer<S> gOut;
gOut[0].a = gC.a;   // invalid WGSL on master
// gOut[0] = gC;    // invalid WGSL once #13607 fixes the CopyLogical ICE
```

Unpacking a std140-widened scalar-array element uses the opcode conversion `ConversionMethod = kIROp_VectorReshape`. In `slang-ir-peephole.cpp` (~:1556), the `kIROp_VectorReshape` case folds a vector→scalar reshape into a swizzle by calling `builder.emitSwizzle(resultType, …)`, where `resultType = as<IRVectorType>(inst->getDataType())` is null whenever the result is a scalar. The untyped swizzle is printed as a bare expression statement such as `gC_0.a_0.data_0[i32(N)].x;`, and a later use refers to an undeclared `_S1`. slangc exits 0 and naga fails with "expected assignment or increment/decrement, found ';'". The fix is `emitSwizzle(inst->getDataType(), …)`; `builder.emitVectorReshape(type, v)` is already typed and safe. The regression test is `tests/wgsl/uniform-array-copy-to-storage.slang` in PR #13607 [VectorReshape→scalar peephole emits a typeless swizzle](../learnings/1791921698811-vectorreshape-scalar-peephole-emits-a-typeless-swi.md), [VectorReshape-to-scalar swizzle was built with a null result type](../learnings/1791924339218-slang-peephole-vectorreshape-to-scalar-swizzle-was.md).

Two review lessons follow. A bare expression statement in WGSL output usually points to an IR inst with a null type, so check the IR before blaming the emitter. And #13607 turned a master ICE (the cross-layout `CopyLogical` on [[wiki/concepts/slang-backends-f0909b0-spirv-legalization-crashes.md]]) into rc 0. When a PR does that, validate the new output with naga or spirv-val and probe shapes beyond the PR's own type: probing only `bool` missed the float arrays that now reached the broken peephole.

## Undefined resource values: rc 0 with invalid GLSL and WGSL (#13700)

A slangc exit of 0 for `-target glsl` or `-target wgsl` does not mean the output is valid. Consider a `LoadFromUninitializedMemory` or `Poison` whose type is a resource, such as an undefined `Texture2D` local that is read on some path. On master, and with PR #13700 applied, the two targets fail in different ways. GLSL prints an undeclared identifier, because `shouldFoldInstIntoUseSites` folds resource-typed values on GLSL before it reaches the check that never folds undefined values. WGSL declares a function-scope `var t : texture_2d<f32>`, which Tint rejects with "must have constructible type". `checkUnsupportedInst` (slang-ir-check-unsupported-inst.cpp:391) rejects an opaque `DefaultConstruct` on Khronos and WGSL targets, but not the undefined ops, so neither shape gets a diagnostic.

Validate downstream: `slangc -target spirv -emit-spirv-via-glsl` runs glslang over the GLSL, and the Dawn-node Tint harness above checks the WGSL. Use `int` cbuffer conditions in such repros, not `bool`, or the bool-in-uniform bug (#13590, above) fails first and masks the result. A related front-end hang has no texture in it: a phi of `{undef, self}`, or a swap cycle in a loop, hangs slangc on master, for example `int t; for(..){ if(c==i){int r; t=r;} o[i]=t; }` on SPIR-V and HLSL. The `arg == inst` skip in #13700 fixes it ([Slang GLSL/WGSL 'compiles' checks hide invalid output for undefined resources](../learnings/1792155974717-slang-glsl-wgsl-compiles-checks-hide-invalid-outpu.md)).

## Required `enable`/`requires` directives: missing, stale, and misplaced (#13617, #13636)

WGSL `@builtin(primitive_index)` is a fragment-only `u32` input. Since wgpu/naga 29.0.0 (and Tint/Chrome 142), a module that uses it must declare `enable primitive_index;`, and the host must request the "primitive-index" device feature. Measured on naga 30.0.1: no enable gives a parse error, an `i32` type gives a validation error, and a vertex-stage use is invalid. On master 8230cdaeb, Slang marks `SV_PrimitiveID` unsupported on WGSL (E55202) in `LegalizeWGSLEntryPointContext::getSystemValueInfo` (slang-ir-legalize-varying-params.cpp ~:5260), and `SystemValueInfo` has no field for a required extension.

The clean producer-side hook is to add that field and have `legalizeSystemValue` attach `addRequireWGSLExtensionDecoration(entryPointFunc, ext)`. The emitter already consumes the decoration: `emitGlobalInstImpl` → `handleRequiredCapabilitiesImpl` (slang-emit-wgsl.cpp ~:1905) feeds the extension tracker, and `emitFrontMatterImpl` writes `enable X;`. Front matter is emitted after the body, so a request made while emitting the body still lands. A prototype validated under naga. A related gap: a raw `uint l : SV_WaveLaneIndex` entry parameter emits `@builtin(subgroup_invocation_id)` without `enable subgroups;`, because only the Wave* intrinsics call `__requireTargetExtension("subgroups")`. The spec requires the enable for subgroup built-in values, even though naga 30.0.1 accepts its absence [WGSL primitive_index needs `enable primitive_index;`](../learnings/1791954062918-wgsl-primitive-index-needs-enable-primitive-index-.md).

The opposite failure is an enable that no longer exists. Dawn/Tint removed the `subgroups_f16` enable-extension and the SubgroupsF16 GPU feature in April 2025 (dawn e2c7a2a0b8, a reland of 7bb9a04ba9); it is not in WGSL spec §4.1.1 or Tint's `wgsl.def`, and f16 subgroup ops need only `enable f16;` plus `enable subgroups;` (dawn 9a0904693b). Slang's `handleRequiredCapabilitiesImpl` (slang-emit-wgsl.cpp ~:1917, from #6213) still hard-codes `subgroups_f16`, so any `half` use together with any subgroup op, even one on `uint`, produces a module Tint rejects (#13636) [WGSL `subgroups_f16` is dead](../learnings/1792070896998-wgsl-subgroups-f16-is-dead-naga-wasm-30-cannot-val.md). WGSL also has `requires X;`, a documentary language-extension directive that must precede all declarations; `ShaderExtensionTracker::appendExtensionRequireLinesForWGSL` emits only `enable X;` today [WGSL `var<immediate>` spec rules](../learnings/1792071495705-wgsl-var-immediate-push-constants-spec-rules-naga-.md).

## WGSL built-in semantics: Tint's lowering is the cross-target reference (#13631)

When a Slang intrinsic mirrors a WGSL built-in, check what that built-in means on the other backends. Tint's own SPIR-V/HLSL/MSL translation, `src/tint/lang/wgsl/reader/lower/lower.cc`, is the ground truth: it lowers `workgroupUniformLoad(p)` to `workgroupBarrier(); load (or atomicLoad); workgroupBarrier()`. Slang's `workgroupUniformLoad` in `hlsl.meta.slang` has `default: return v;`, so it drops both barriers on SPIR-V, HLSL, GLSL, Metal and CUDA (slang#13631). DeepWiki echoed the buggy code as if it were the design ("does not implicitly include a barrier"), so treat a DeepWiki answer as a description of current code, not design intent [Tint's lowering is the cross-target reference](../learnings/1792071135841-wgsl-built-in-semantics-use-tint-s-lowering-as-the.md).

## Push constants: WGSL `var<immediate>` (#13639)

Slang emits WGSL push constants (`[[vk::push_constant]]`, `layout(push_constant)`) as `var<uniform>` with no `@group`/`@binding`, which is invalid. `emitParameterGroupImpl` in slang-emit-wgsl.cpp has no `PushConstantBuffer` case and hard-codes `var<uniform>`. The WGSL `immediate_address_space` language extension defines the target form, `var<immediate>`: module scope, no `@group`/`@binding`, storage-layout (std430-compatible) constraints, a host-shareable and constructible store type with no arrays and no structs containing arrays, and at most one immediate variable statically accessed per entry point. The WebGPU API sets it with `setImmediates` [WGSL `var<immediate>` spec rules](../learnings/1792071495705-wgsl-var-immediate-push-constants-spec-rules-naga-.md).

The no-arrays rule collides with Slang's buffer matrix lowering. `shouldLowerMatrixType` (slang-ir-lower-buffer-element-type.cpp:2613) keeps a matrix native only under the Natural layout rule, which WGSL never uses, so every WGSL buffer matrix is wrapped in a `_MatrixStorage_*` struct holding an array; int and bool matrices become `vector<T,C>[R]` even earlier, in `legalizeMatrixTypes`. Both forms are arrays, so neither is legal inside `var<immediate>`. Push constants also reach buffer lowering as `AddressSpace::Uniform` (:2572); the PushConstant address space is unused there [WGSL matrix storage orientation](../learnings/1792086860208-wgsl-matrix-storage-native-matrxc-slang-row-major-.md).

## Matrix storage orientation: native `matRxC` is Slang row-major (#13666)

Slang emits an HLSL-semantics `floatRxC` as WGSL `matRxC` (slang-emit-wgsl.cpp:595-602, the "terminology reversal"), so each WGSL column holds one Slang row. A native WGSL matrix in a std430, storage or immediate buffer therefore matches Slang `row_major` storage byte for byte: a row-major `float4x3` is 64 bytes, the same as `mat4x3<f32>`. Slang `column_major` storage is the transpose and needs WGSL `matCxR` plus `transpose()`, with different sizes (column-major `float3x4` is 64 bytes against 48 for row-major). Column-major is the slangc CLI default (slang-end-to-end-request.cpp:1324), while the API default is row-major, so a fix that keeps matrices native for WGSL has to handle both orientations [WGSL matrix storage orientation](../learnings/1792086860208-wgsl-matrix-storage-native-matrxc-slang-row-major-.md).
