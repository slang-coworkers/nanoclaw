## TL;DR


## Absence arguments: zero information until you prove the channel was open

A refutation built on "the log doesn't say so" / "the endpoint returned nothing" is the approver's most common self-inflicted false-clean, and it is *structurally* unsound rather than merely sloppy.

**An absence-of-log-line argument carries zero information until you prove the line would have been emitted AND printed at that run's verbosity.** On slang-rhi#800 a bot 🔴 (indirect dispatch can crash on Metal devices without a residency set) was partly refuted by grepping both CI logs for four strings — `MTLResidencySet creation failed`, `using per-encoder useResource fallback`, `GPUFamilyApple6 not supported`, `SLANG_RHI_METAL_NO_RESIDENCY_SET` — and finding 0 occurrences. The counts were correct; the inference was not. The three ways into the fallback **do not share a severity** (`metal-device.cpp:109-145`: env-var and Apple6 paths are `Info`, `newResidencySet`-null is `Warning`), and the harness routes them differently (`testing.cpp:209-219`: `Info` → doctest `INFO()`, *captured context flushed only when a test FAILS* or under `options().verbose`; `Warning` → `MESSAGE()`, unconditional). The run was non-verbose and all-green ⇒ **zero `[Info]` lines of any kind existed**, so 2 of 3 paths were undetectable by construction and the check could only ever have caught the third. Worse, the success path `m_hasResidencySet = true` emits **nothing**, so the positive claim had no direct evidence either. Note the inversion trap: an `INFO()`-based absence argument is strongest exactly where it is weakest — the diagnostic becomes visible precisely when the run fails and you no longer need it. Three questions in order before writing "X never happened because the log doesn't say so": does the code emit anything on that path (grep the *branch*, not the message text)?; at what severity (sibling branches in one `if/else` routinely differ)?; and does that severity reach *this* log at *this* run's verbosity and outcome? The one-command sanity check: **count all lines of that severity** — zero of any kind means the channel is closed, so you have measured the harness, not the code. Decision impact here was nil (ABSTAIN_POLICY / CHALLENGER_CONCERN held through six critique rounds) **and that is the point**: what changed is that the primary basis moved from a procedural "standing CHANGES_REQUESTED" (cleared by a human 51 seconds later) to the substantive unresolved residency gap — *a withhold justified by the wrong reason is a latent false-safe*, because when the wrong reason evaporates the real risk remains ([[approver/critique-mustfix] an absence-of-log-line argument carries zero information until you prove the line would be emitted AND printed](../learnings/1785772353384-approver-critique-mustfix-an-absence-of-log-line-a.md)).

⚠️ **And that correction was itself only half-right — NARROWING a claim is not TESTING its premise.** The residency corollary of the #800 calibration atom is **withdrawn**: "the third refutation finally had execution behind it", "CI ran the residency-**set** path", "the `!m_hasResidencySet` fallback is unexercised for all Metal ops — pre-existing harness scope, not PR-introduced", and "the technical withhold reason was retired on evidence" are all retracted (the last one *inverted* — the residency gap was the PRIMARY basis, review state secondary). Then the polarity flipped again: `m_hasResidencySet = true` is set **only** inside `else if (supportsFamily(MTL::GPUFamilyApple6))`, the hosted `Apple Paravirtual device` on `macos-26-arm64` **lacks Apple6**, and a sibling job on that same image logs the terminal-`else` fallback message ⇒ **CI runs the FALLBACK by default**, so the *residency-SET* path is the uncovered one and the missing artifact is an **Apple6 run**, never a `SLANG_RHI_METAL_NO_RESIDENCY_SET` run. The durable lesson: "the fallback is unexercised" was retracted and rewritten as "the fallback is unverified" — weaker, same direction, **same untested premise** (*which path does CI take?*) — so the retraction *inherited the error and laundered it as diligence*. Ask what observation would settle it and whether that observation is cheaply available before recording either version; here it was one unauthenticated `curl` of a public job log. Retract at **paragraph granularity** (that atom's five-log-check coverage checklist and its Metal residency taxonomy remain correct and were expensive to derive), and note the propagation requirement below ([[approver/critique-mustfix] CORRECTION to the slang-rhi#800 calibration atom — narrowing a claim is not testing its premise](../learnings/1785774267946-approver-critique-mustfix-correction-to-my-own-sla.md)).

**Never establish absence, a count, or a completeness claim with a summarizing fetch tool.** Reporting to the orchestrator that four review comments *"did not exist"* — introducing an error into a state record that was already correct — came from using `WebFetch`, which answers a prompt against a page **using a small fast summarizing model**: prose-shaped, not an enumerator, and it degrades silently on long JSON. The same URL, three consecutive calls, reported page-3 item counts of 18 / 16 / 16 against a truth of **50**, and one comment's body length as 1088 / 856 against 1198; asked point-blank *"is there any element with created_at starting 2026-08-03T08:03? YES or NO"* it answered **NO** and listed the timestamps it *did* see as if exhaustive, with nothing signalling truncation. **A summarizer's silence is not a signal — it cannot report its own truncation, so a confident `NO` from one is worth nothing.** Tool-selection rule: summarizer for *"what does this argue?"*, code for *"how many / does X exist / is this all of them?"* — fetch the JSON with stdlib `urllib` at `per_page=100` and loop until a short page. Red flags that should stop you: two calls to one URL disagreeing on a total, a count suspiciously near a round number, a body length differing between calls, any "there is no X" backed only by prose output. Two hard rules follow: **never assert a negative from a lossy view** (say "I did not find it in N pages I enumerated deterministically", or say nothing), and **before contradicting a peer who supplied specific evidence — exact counts, verbatim quotes — reproduce their query deterministically**, since specificity is cheap to verify and expensive to fabricate, so the burden sits on the contradiction. The disproof was in hand the whole time: a body already fetched verbatim opened *"This is the third round raising the guard"* — three rounds means two prior ones, i.e. the batch being called nonexistent ([[approver/critique-mustfix] never establish absence or counts with a summarizing fetch tool — it fabricated a confident NO and three counts for one URL](../learnings/1785761721232-approver-critique-mustfix-never-establish-absence-.md)). Generalized into a check order: **grep material you have ALREADY fetched for ordinals and back-references implying the positive** ("third round", "as I said above", "reverted my earlier fix") — when such a phrase contradicts a conclusion you are forming, *the conclusion is what's wrong*; then re-run deterministically; only then state absence, scoped to what you enumerated. And verification runs **both ways**: in that same exchange the peer's own enumeration was short too (two comments in an `11:02` batch that deterministically contains four), so what protects the record is the method, not which party is speaking ([[approver/clause-gap] CORRECTION — grep your own already-fetched material before reporting a negative; verification is symmetric](../learnings/1785761810820-approver-clause-gap-correction-to-empty-body-comme.md)).

**A tool error gating a load-bearing premise gets ONE adversarial retry before it becomes a caveat.** On slang-rhi#807 the macOS runner's OS version decided whether a deleted test assertion (`CHECK_FALSE(device->hasCapability(metallib_4_0))`) was load-bearing or cosmetic — the whole severity call hinged on it. `actions/jobs/<job_id>/logs` returned 403 "must have admin rights", and the premise was recorded as **unresolvable**, shipping "runner macOS version unknown" as a caveat that drove a conservative lean; the decision survived only because the lean happened to be correct. Two mistakes: the endpoint is **public** — it 302-redirects to a signed Azure blob, and `curl -sSL` follows it and returns the full log body **with no credentials at all** on a public repo (verified: 256,628 bytes, and the log's own startup group settles the question — `Operating System / macOS / 26.5.2`, `Runner Image: macos-26-arm64` ⇒ major 26 ⇒ the assertion **was** load-bearing). The 403 was not reproducible on retry (302 with `Location:` present, ratelimit-remaining 5932, authenticated `gh api` 200), so it is an artifact of whatever shim surfaced it, not a property of the endpoint — don't grep for a 403 to decide whether this applies. And the generalizable error: **"the API returned an error" is not "the information is unavailable."** Before writing "could not determine" about anything a verdict leans on, try one genuinely different path — follow redirects, unauthenticated vs authenticated (they fail differently), REST vs GraphQL vs `issues/<n>/timeline` vs `compare/<a>...<b>`, a different endpoint carrying the same fact — then name **both** methods in the artifact ([[approver/infra-abstain] GitHub Actions job logs are PUBLIC — follow the 302, and never let one tool error close a load-bearing premise](../learnings/1785766450209-approver-infra-abstain-github-actions-job-logs-are.md)).

**A job-log 410 is retention expiry, not breakage — prove it with a fresh-job positive control FIRST, then transfer via byte-identical blob and settle the load-bearing question from SOURCE.** Trying to prove `tests/metal/ray-query-intrinsics.slang` actually EXECUTED (not merely "the job was green") on slang#12142's head `2a61c227a2ca`, every log endpoint returned HTTP 410 Gone — per-job, per-run, per-attempt, `gh run view --log`, and all 16 run artifacts `expired: true`. A 410 is easy to misread as "my token/transport is broken" or "unavailable, caveat and move on." The discriminator that settles it in one call is a positive control run *first, always*: fetch the log of a job that finished minutes ago with the *identical command* (`gh api actions/jobs/$NJOB/logs | wc -c` → 60116 bytes) — if the fresh job returns bytes and the old one 410s, the method + token are HEALTHY and the *data* is gone. Measured on slang the retention window is ≈5 days (07-31/08-01/08-03/08-04 ✅, 07-29/07-23 ❌ 410), far shorter than GitHub's 90-day artifact default, and the 410 is **per-run, not per-attempt** so you cannot recover an expired attempt's sibling. Then write "could not verify at the pinned SHA by method M", M named — never "logs unavailable" (a false capability-negative with no observable failure signature) and never infer execution from a green conclusion. Two transfer paths recover the answer without the pinned-SHA log: (1) **byte-identical blob** — tree/blob reads never expire, so if the test file's blob SHA matches at the pinned SHA and a recent commit, quote the verbatim result lines from a *recent* run (here MTL passed on all four legs, metallib `passed` on macOS only / `ignored` on Linux, mtl GPU `ignored` everywhere — always cite the tally control `100% (7121/7121), 3516 ignored` so the grep isn't a zero-hit against a dead instrument), stating the limit honestly (byte-identity pins the *test input*, not the *compiler*); and (2) the residual question a log can NEVER answer — "did it pass *because* of the fix, or would it pass anyway?" — is settled from the **pre-PR base**: base `4f4ec505761e` bakes `get_` into `kCandidateCommittedMetal[]` while the test asserts `is_candidate_triangle_front_facing`, so the checks fail without the PR — strictly better evidence than a log line, and it never expires ([job-log 410 is retention expiry — positive-control it, then transfer via byte-identical blob + settle load-bearing from source](../learnings/1785841389780-approver-infra-abstain-github-job-logs-410-after-5.md)). Bonus trap in the same family: `gh api .../contents/<path>?ref=<sha>` returns `encoding=none`/`content_len=0` for files over ~1 MB (`hlsl.meta.slang` is 1.2 MB), so `--jq .content | base64 -d | grep -c X` prints a confident `0` indistinguishable from "not present" — fix with `-H "Accept: application/vnd.github.raw"` and verify `wc -c` against `.size`; a zero-hit grep needs a must-be-non-zero control before it means anything.

### Two species of broken check

**Species 1 — the record of diligence outlives the diligence.** Distilled from ~14 defects across two review tiers in one chain: every *cheap* verification reads a **record** of work rather than re-deriving it, and records are satisfiable without the underlying thing existing, so they survive when it doesn't and come back green either way. Observed instances, all by people who already held the relevant rule in writing: a "VERIFIED" label written before the check ran; a maxim that outlived its proof (compacting an index deleted the evidence paragraph and kept the one-liner — including, recursively, the paragraph saying *"do NOT compress it away, or what remains is a plausible maxim with nothing under it"*); a resolving markdown link (link integrity is not content presence); a stated tally ("nine defects" went unchallenged because nobody argues with a count — audited from artifacts it was ~14, drifted in the *comfortable* direction on both sides independently); a grep for **remembered wording** (searching your own store for what you *think* you wrote reads the record of your intent, not the artifact); a green CI conclusion (registered ≠ executed — a green run can mean the code compiled out); and an exit-0 harvest (succeeded ≠ read everything). **The discriminating question: if the underlying work did not exist, would this check still be green?** If yes, it is a record check, and the only check not fooled is re-deriving the thing — open the file at the pinned SHA, grep for the load-bearing **datapoint** rather than the rule's title, run the command rather than reading it, count from artifacts rather than memory. Record checks are cheap and *feel* like diligence, so they get substituted for the expensive check under time pressure — i.e. most likely precisely when stakes are highest. Two near-free defenses: when you restore or move content, **verify the EVIDENCE, not the heading**; and **order operations so the record cannot precede the reality** (write the child file first, grep to confirm, *then* shorten the parent; run the check, *then* write the label; count from artifacts, *then* state the number). Meta-observation on that chain: ~14 defects surfaced, every one by a check rather than by agreement — **read a smooth agreement as an untested hypothesis, not a result** ([[approver/critique-mustfix] the record of diligence outlives the diligence — every cheap verification reads the record, not the thing](../learnings/1785782318729-approver-critique-mustfix-the-record-of-diligence-.md)).

**Species 2 — the apparatus is subject to the effect under test.** Species 1's question does not catch this one: here the work exists and the **measurement instrument is itself inside the phenomenon**. The discriminating question becomes **would this probe report the same result whether or not the thing I am testing is true?** If yes, it isn't a probe. Three verified instances: the text-matching delivery gate that denies a bundled control (above); stripping an `Authorization` header as a "control" when a proxy re-supplies it (the probe reports "works without auth" either way); and `.permissions` on a public repo as a token-injection probe (present with zero credentials, so it answers identically with and without a token). Species 2 is the more dangerous of the two when it fires, because it doesn't merely fail to detect a problem — it **manufactures a false observation** ("the gate is nondeterministic", "auth isn't needed", "the token is injected") that then gets recorded as evidence and reasoned from. A record check leaves you no worse informed; a corrupted apparatus leaves you confidently wrong. Checklist before trusting any probe: name the outcome if the hypothesis is TRUE and if FALSE (identical ⇒ stop, you have no probe); confirm nothing in the measurement path (gate, proxy, wrapper, cache, the CLI itself) is part of the system under test; one probe per invocation so a denial is attributable ([[approver/critique-mustfix] second species — the apparatus is subject to the effect under test](../learnings/1785782534319-approver-critique-mustfix-second-species-the-appar.md)).

⚠️ **The replacement probe proposed in that very catalogue is species 2 itself — RETRACTED.** *"The working probe is `rate_limit` core `limit` (60 = anonymous, 5000 = injected), run via `urllib`/`curl` not `gh`"* is **wrong in the dangerous direction.** Measured in one container, same minute: `curl https://api.github.com/rate_limit` → 200 with core `limit: 60`, reading as "anonymous, no credential" ❌, while `curl -sD- .../repos/shader-slang/slang` and `gh api -i repos/shader-slang/slang` both return `X-Ratelimit-Limit: **6000**` ✅. **The credential was being injected while the probe said anonymous**, because **injection is PER-PATH**: the proxy applies secret rules by path, `rate_limit` has no rule, so it is precisely the one path where the credential is absent (401 through `gh`, bare anonymous 60 through `curl`). The prescribed fix was **transport**; the defect was **path** — and changing the client cannot repair a per-path gap, it only changes which way the false reading points. Two smaller errors rode along: `60` is not a *core* reading at all (it's the anonymous bucket for whatever caller the API sees), and the injected core limit here is **6000**, not 5000, so a `5000 = injected` test fails even where injection works. **Working probe: read headers on the exact path you are about to call, and test PRESENCE, not value** — `gh api -i <the path you actually need> | grep -i x-ratelimit`; present ⇒ injected on *that* path, absent + 401 ⇒ no rule covers it. Do not threshold the value: limits are per-resource (core 6000, `search/issues` **30**), so a threshold misreads a successfully-injected search call as anonymous. The tell that catches it without a counterfactual: the same payload reports `graphql: {limit: 0}`, which a genuinely anonymous session and an App token whose GraphQL is 401-ing produce **identically** — the body provably cannot distinguish them (and its `search: {limit: 10}` contradicts the 30 on a real injected search call). This false reading is *more* dangerous than the 401 it replaced because `60/60/used: 0` is **internally consistent** — it looks like a healthy anonymous session rather than a broken probe, and **replacing a loud failure with a quiet one is a regression even when both are wrong.** The transferable rule: **when you retire a broken probe, name the property that made it broken, then test the replacement against that same property** — here `.permissions` was correctly diagnosed as useless *because it answers identically with and without the capability*, and the replacement answers identically with and without the capability, in the same sentence. This class outranks the record-check family in severity because it is a **false capability-NEGATIVE published into shared prose**: other agents act on it by *not attempting* something that would have worked, and a not-attempted action leaves no trace to debug — so prefer **"I could not verify X by method M"** over "X is unavailable" ([[approver/critique-mustfix] CORRECTION — the rate_limit token probe is itself species 2 and reports the opposite of the truth; injection is per-path](../learnings/1785782770123-approver-critique-mustfix-correction-my-rate-limit.md)).

### Cross-tier counts: same command ≠ same query, and membership ≠ completeness

**"I ran the identical command" does not imply "we ran the identical query" — CLI semantics vary per caller-scope.** Two tiers disagreed on how many sessions a group holds. A peer with broader CLI scope measured `ncl sessions list --agent-group <gid>` returning **200 rows spanning 9 distinct `agent_group_id`s** — the filter flag accepted without error and silently ignored — correctly concluded any count from it is a superset, recomputed by filtering the column, and reported the true value as 10 against a stated 17. But on the narrower edge the *same command* has different semantics: with `cli_scope=group`, both bare `ncl sessions list` and `--agent-group <mine>` return 180 rows **all** of one group, because the restriction is enforced **server-side by scope** — so the flag is redundant for one caller and load-bearing for the other. Column-filtered, the narrow edge yields **17**, cross-checked per-session via `ncl sessions get`; **17 was right, 10 was an undercount**, and the instrument critique was true for one edge and false for the other. So: suspect the instrument — *and then suspect that it is not the same instrument on both edges*. Corollaries: a filter flag silently ignored for one caller and honored for another is indistinguishable from a working flag if you only test on one edge; **the party with broader access is not automatically the more accurate one** (breadth is what exposed them to the unfiltered superset); and two edges reaching different numbers is evidence about the *tool*, not about either party's diligence. **A correction is itself a relay** — accept the refutation without inheriting the substitute: both sides re-derived rather than adopting the other's figure, and that mutual refusal is exactly what surfaced the per-edge divergence ([[approver/clause-gap] "I ran the identical command" ≠ "we ran the identical query" — CLI semantics vary per caller-scope](../learnings/1785820313072-approver-clause-gap-i-ran-the-identical-command-we.md)).

**A membership check cannot detect truncation — and being right for an unverified reason is luck, not method.** The peer then found the real defect: `ncl <resource> list` has a **silent 200-row cap** (bare → 200, with a filter flag → 200 — *two different queries returning the same round number IS the tell* — `--limit 1000` → 1000, `--limit 5000` → 2096 = true total), so their two wrong figures were an unfiltered superset and then a truncated page. The half that belonged to the *correct* count: 17 was stable across bare / `--limit 1000` / `--limit 5000` **only because that group holds 180, under a cap never measured** — at 250 it would have reported a capped page with identical confidence and identical "two independent paths agree" backing. The load-bearing insight: `get <id>` confirms an item *is* in the set and nothing about it can reveal an item *missing* from a truncated list, so **positive-path corroboration is blind to omission** and pairing two membership checks feels like independent verification while providing zero coverage of completeness. Rules: on any `list` verb pass an explicit `--limit` far above the expected total and confirm the count is stable when you raise it further (an unbounded count is a **floor**, not a total — the fourth instance of this shape after `search/code`'s `total_count`, `/commits/<sha>/check-runs` paging at 30, and `--paginate` page-1 caps); **verify why your answer is right, not just that it is right**; and **match the check to the claim — membership → `get`, completeness → bound test, identity → hash.** The peer's own post-mortem is the most transferable piece: post-filtering **confirmed** their superset hypothesis, so they stopped probing — **a new instrument whose first act confirms your prior belief deserves more suspicion, not less**, because confirmation is when probing feels finished and is precisely when the remaining defect hides. Their own filed rule ("every fix for a measurement defect gets built with an instrument sharing that defect") predicted this exactly, and having the rule did not prevent it: *a rule protects only at the moment it is executed as a step in the work, never as a principle recalled* ([[approver/clause-gap] a membership check cannot detect truncation — right for a reason never verified, under an unmeasured 200-row cap](../learnings/1785820576164-approver-clause-gap-a-membership-check-cannot-dete.md)).

**A denial inherits the scope of the surface you checked.** A defect report attributed to one approver was denied on two true facts — zero mentions of the PR number in that session's transcript, and no matching thread in the session list it had printed — and the denial was still misleading: `ncl sessions get <cited-id>` returned `agent_group_id` = **the same group**, thread `gh-issue-…-804`, status `running` — a **sibling session** never seen. Had the peer accepted the denial they would have retracted a *true* claim and told an operator a real defect report had no owner. Nothing prompts a session to enumerate its siblings even when CLI scope already grants it, so **state the scope you actually verified, never the scope the question was asked in**: *"Not this session (`…wzx7m9`) — verified by transcript. It IS my group (`…bvj5tl`, thread rhi-804) — verified by `sessions get`. I cannot read that session's transcript, so I can confirm ownership but not the finding."* Enumerating cost almost nothing and **corrected the tier with broader read access** (the group held *two* running sessions on that PR where their account named one). Attribution format unfalsifiable by either side: **group + session id + thread** — bare "you reported X" is ambiguous exactly when a group runs concurrent sessions, which for a webhook-driven group is the normal case. This is the complement of "a wrong id is worse than no id": when the authoritative field is out of reach, name it; **when it IS within reach, checking it is mandatory before asserting a negative** — and a confident negative from a narrow surface is the more insidious failure, because it sounds like first-hand knowledge and quietly closes the question ([[approver/clause-gap] "that isn't mine" is authoritative for your SESSION and non-authoritative for your GROUP](../learnings/1785820074643-approver-clause-gap-that-isn-t-mine-is-authoritati.md)).
