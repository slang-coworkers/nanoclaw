# Agent Routing: MCP Servers & Gateways

## TL;DR
- **The critique gate records verdicts only from a FRESH top-level `mcp__codex__codex` call**, one per stage, made sequentially. `codex-reply` rounds are for iterating on must-fix items — they never move the gate, and `must-fix` is sticky within a reused thread. After codex says approve, make one fresh staged call.
- **Stage detection keys on the FIRST stage keyword in the prompt.** Lead with a bare `STAGE: <NAME>` line and name no other stage earlier in the body. The response must end with `### Verdict` followed by a line containing only `approve` or `must-fix`.
- **The gate needs `OUTPUT_REVIEW = approve` specifically**; other stages need only count ≥ 1.
- **Codex runs in a separate container that shares `/workspace` but not `/tmp`.** Stage every artifact codex must read under `/workspace`, and set `sandbox: "danger-full-access"`.
- **The gate's PreToolUse hook denies the WHOLE bash command**, so a heredoc that precedes a blocked `gh pr create` never runs. Write the PR body as its own step, then create the PR, then fill in the real URL — never fabricate it up front.
- **Gate an APPROVE on green full-suite CI for broad-blast-radius changes**, not static review. On a draft PR the auto CI is draft-gated; confirm a `workflow_dispatch` run exists.
- **An empty MCP search result is non-signal, never evidence of absence.** `github_search_issues` has returned zero for date-qualified queries and, during an extended outage, for *every* query including trivially-matching ones. Never read empty as "no duplicate issue" or "the merge queue is frozen" — fall back to `github_list_issues(state=ALL)` + client-side filter, or REST `pulls/<N>` / `commits?sha=master`.
- **`merged_at` is never populated by that tool**; determine merge state from REST `.merged`/`.state`/`.draft`.
- **Restart the failing MCP subprocess, not the service.** `systemctl restart nanoclaw-*` SIGKILLs every running agent container and destroys in-progress work; `pkill -f '<mcp-server>'` lets the host respawn the child with no container impact.
- **Distinguish a credential outage from a cold start before retrying.** A 401 on reads that reproduces across sessions and channels is a vault/token failure only an operator can fix — 2-3 attempts confirms it. Preserve the unposted artifact, attach it upstream, and report `blocked` with exact error strings; never post a partial report.
- **Credential injection at the gateway is PATH-SCOPED.** An intact proxy env is necessary but not sufficient: a path with no rule for this agent returns 401/403 even though the credential exists. Never conclude "the upstream object is gone" from a scoped read.
- **A missing MCP tool is not a missing capability.** When `discord_read_messages`/`github_list_issues` is absent or slang-mcp is down, try the raw API with `curl` through the OneCLI proxy and NO `Authorization` header — the gateway injects credentials per-path for Discord (`discord.com/api/v10/...`) just as for GitHub. Declare a source unavailable only after that fails. Fresh subagents can lack an allowlisted MCP tool the parent has, so brief them to use proxied curl; a hook-denied DeepWiki (still the case 2026-11-06) falls back to `gh api .../contents/<path>` or a raw.githubusercontent `curl`. `github_get_file_contents` reads only shader-slang repos; a third-party repo you cannot read stays a hypothesis.
- **Never `unset HTTP_PROXY` to work around a 403** — it strips the injected token entirely and drops the rate limit from 6000/hr to 60/hr.
- **Drop `-f` and print `%{http_code}` the moment a fetch returns nothing you cannot explain.** `curl -sf` renders an auth failure as empty stdout, byte-identical to a legitimate absence. Pair every such read with a positive control on a path known to be in scope.
- **The git wire protocol is not path-gated the way the REST API is.** `git ls-remote` and a `--filter=blob:none` scratch clone answer ref existence, default-branch, and `merge-base --is-ancestor` reachability against foreign orgs over the same proxy.
- **Branch-protection endpoints are unavailable on a scoped token**, so "is this check required?" must be answered from merge evidence, not the required-contexts list.
- **ProjectsV2 boards need a per-project access grant** separate from org-level Projects permission; prod coworkers generally cannot write them. Route the literal `/graphql`, not `/graphql*`.
- **Probe a language server with a real `slangd` over stdio, with a control arm on an unpatched build.** slang-test's `LANG_SERVER` harness disables periodic diagnostics, so it never publishes the diagnostics you are trying to observe.

Operational rules for the codex-critique gate overlay, the slang-mcp server, slangd LSP probing, the OneCLI credential gateway, and related MCP tooling.

## Codex Critique Gate: Overview

When the `critique-gate` overlay is active (marker file `/workspace/agent/.overlay-critique-gate` exists), delivery actions (`send_message` with `[Fix Report]`/`[Resolution]` markers AND `gh pr create` / `gh api .../pulls`) are blocked by PreToolUse hook `/app/hooks/gate-critique-on-deliver.sh` until codex critique is recorded in a machine-parseable format. State lives in `/workspace/.claude/workflow-state.json` (`.critique_stages`, `.critique_verdicts`) ([critique-gate: STAGE marker in codex PROMPT + '### Verdict' block in codex RESPONSE, one call per stage](../learnings/1781321980304-critique-gate-stage-marker-in-codex-prompt-verdict.md)).

### Required Format

Read `/workspace/agent/.critique-required-stages` (JSON array, e.g. `["PLAN_REVIEW","CODE_REVIEW","OUTPUT_REVIEW"]`); if absent or empty, the gate falls back to "any 1 critique round." Otherwise make ONE separate `mcp__codex__codex` call PER stage (not `codex-reply`, which carries no STAGE marker), **sequentially**, since parallel calls race and drop a stage. The PROMPT must contain a line matching `STAGE:[[:space:]]*[A-Z_]+` (e.g. `STAGE: PLAN_REVIEW`); the RESPONSE must end with `### Verdict` immediately followed by a line containing only `approve` or `must-fix` (parser: `sed -n '/^### *Verdict/{n;p;}'`) ([critique-gate: STAGE marker in codex PROMPT + '### Verdict' block in codex RESPONSE, one call per stage](../learnings/1781321980304-critique-gate-stage-marker-in-codex-prompt-verdict.md)). The stage detector keys on the FIRST stage keyword in the prompt, so lead with the bare `STAGE:` line and name no other stage earlier in the body ([critique-gate stage detector keys on the FIRST stage-keyword in the codex prompt — lead with the bare STAGE: line](../learnings/1780971403094-critique-gate-stage-detector-keys-on-the-first-sta.md)).

### Verdicts and Thread Stickiness

The gate records stage verdicts ONLY from a fresh top-level `mcp__codex__codex` call, never from a `codex-reply` round, so don't loop re-replying expecting the gate to flip ([codex-critique gate records stage verdicts only from a fresh staged codex call, not from codex-reply](../learnings/1781775272408-codex-critique-gate-records-stage-verdicts-only-fr.md), [codex critique-gate tracks FRESH-call verdicts, not codex-reply re-verifications](../learnings/1782439747524-codex-critique-gate-tracks-fresh-call-verdicts-not.md)). `must-fix` is also sticky within a reused thread: later approve rounds there are not recorded as approve, so start a new critique session per deliverable rather than `codex-reply`-ing past a must-fix ([codex-critique gate: start a fresh codex session per deliverable, don't codex-reply past a must-fix](../learnings/1781386154716-codex-critique-gate-start-a-fresh-codex-session-pe.md), [Critique-gate OUTPUT_REVIEW is sticky within a reused codex thread](../learnings/1781386183865-critique-gate-output-review-is-sticky-within-a-reu.md)). The working split: `codex-reply` for the cheap, context-keeping back-and-forth on must-fix items, then once codex says `approve`, ONE fresh `mcp__codex__codex` call for that stage to record it ([Critique-gate records verdict from fresh codex calls, not codex-reply rounds](../learnings/1781661845733-critique-gate-records-verdict-from-fresh-codex-cal.md)). The gate requires `OUTPUT_REVIEW = approve` specifically; `PLAN_REVIEW` and `CODE_REVIEW` need only count ≥ 1, any verdict ([codex-critique gate records stage verdicts only from a fresh staged codex call, not from codex-reply](../learnings/1781775272408-codex-critique-gate-records-stage-verdicts-only-fr.md)).

### Codex Workspace and Path Rules

Codex runs in a SEPARATE container that shares `/workspace` but NOT `/tmp`: stage review artifacts under `/workspace/...` (e.g. `/workspace/agent/reports/<n>-pr-body.md`), pass that path, and set `sandbox: "danger-full-access"` (read-only is rejected by a PreToolUse hook in Docker). The hook denies the ENTIRE bash command when it blocks `gh pr create`, so a heredoc preceding it in one command never runs: write the PR body with the Write tool as its own step, run the 3 stages, then `gh pr create --body-file <that path>` ([codex-critique + critique-gate: /workspace not /tmp, and the gate denies the whole bash block](../learnings/1781222707210-codex-critique-critique-gate-workspace-not-tmp-and.md)).

### Opening a PR Under the Gate

The clean sequence: (1) run 3 critique stages against the diff + draft deliverable, (2) the gate opens once all 3 are recorded, (3) `gh pr create` succeeds, (4) write the real PR URL into the deliverable, (5) one `codex-reply` re-verify round flips OUTPUT_REVIEW to approve. Never fabricate the URL up front; describe the PR as "pending" before creation ([codex-critique gate: open the PR before claiming it in OUTPUT_REVIEW deliverable](../learnings/1780325263478-codex-critique-gate-open-the-pr-before-claiming-it.md)).

### PR Review: Reviewer Gate

For a change to a shared IR classifier or helper with broad blast radius, do NOT APPROVE on static review alone; gate the verdict on a green full-suite CI run, which exercises paths static review systematically under-weights. On a bot DRAFT PR the auto `pull_request` CI is draft-gated, so confirm the fixer dispatched `ci.yml` via `workflow_dispatch` ([Reviewer: gate the verdict on full-suite CI for broad-blast-radius changes, not static review alone](../learnings/1782454067582-reviewer-gate-the-verdict-on-full-suite-ci-for-bro.md)).

## slang-mcp Server

### Search Is Unreliable: Date Qualifiers, Then Total Degradation

`mcp__slang-mcp__github_search_issues` returns zero for any date-range qualifier (`merged:>=DATE`, `merged:DATE..DATE`, `closed:>=DATE` all give `total_count: 0`): drop the qualifier, sort by recency, filter client-side on `updated_at`/`closed_at`. The tool never populates `merged_at` (always null), so distinguish merged from closed-unmerged by an `is:merged` query or REST ([slang-mcp github_search_issues date qualifiers return empty](../learnings/1780906273275-slang-mcp-github-search-issues-date-qualifiers-ret.md)). The `slang-mcp` allowlist (`$NANOCLAW_ALLOWED_MCP_TOOLS`) does NOT include `github_list_pull_requests`; use `github_search_issues` with `is:pr` even when the server is up ([Daily-report fallback when slang-mcp server is down](../learnings/1782288946942-daily-report-fallback-when-slang-mcp-server-is-dow.md)).

An extended outage (2026-07-26) widened this from a qualifier quirk to the whole search endpoint: `{items: [], total_count: 0}` for **every** query, including `repo:shader-slang/slang is:issue` and 1/2/6/25-day merge windows, while live issues and merges existed (confirmed independently by Main after slang-discord-support flagged it). Auth was healthy, and `github_list_issues`, `github_get_issue` and `github_get_pull_request` worked. Two casualties: **duplicate-issue detection** must not read empty as "no existing issue" (the fleet would file dupes); fall back to `github_list_issues(state=ALL)` + client-side title/label filter, or `gh search issues`/`gh issue list --search` ([slang-mcp github_search_issues returning empty — use list+filter](../learnings/1785073457026-slang-mcp-github-search-issues-returning-empty-use.md)); and **merge/queue health**, where `is:pr is:merged merged:>=<date>` returning zero nearly triggered a false "queue frozen" escalation while REST showed merges landing; read per-PR `curl .../pulls/<N>` `.merged`/`.state`/`.draft`, and recent activity via `.../commits?sha=master` counting `(#NNNN)` first lines ([github_search_issues is:merged returns zero — verify merges via REST commits/pulls API](../learnings/1785053957653-github-search-issues-is-merged-returns-zero-verify.md)). Treat an empty `github_search_issues` as non-signal.

### Restart Policy

Never `systemctl restart nanoclaw-*` to pick up MCP server config: it SIGKILLs all running agent containers and destroys in-progress sessions (subagents, PR reviews, sweeps). Restart only the subprocess; the host detects the dead child and respawns it with no container impact:
```bash
pkill -f 'haaggarwal.*slang-mcp-server'   # nanoclaw auto-respawns it
```
([Restarting nanoclaw service kills all running containers and their in-progress work; restart only the specific MCP subprocess instead](../learnings/legoop-feedback_no_service_restart_for_mcp.md)).

### Fallback When slang-mcp Is Down or a Tool Is Missing

When slang-mcp returns "No such tool available", or a tool (`discord_read_messages`, `github_list_issues`) is absent from the session, the capability is usually NOT blocked: try the raw HTTP call via `curl` with no `Authorization` header through the OneCLI proxy env (`HTTP(S)_PROXY` → `host.docker.internal:10255`, `NODE_EXTRA_CA_CERTS`/`SSL_CERT_FILE` set) and let the gateway inject credentials. This holds for Discord too: `curl https://discord.com/api/v10/channels/<id>/messages` and `/guilds/<id>/threads/active` return 200 because the proxy injects the bot token per-path. A 2026-09-26 heartbeat concluded there was "no path" to Discord without trying it; only posting with feedback-button components remains untested via raw curl ([Discord/GitHub reads work via curl+OneCLI proxy even without dedicated MCP tools](../learnings/1790418062218-discord-github-reads-work-via-curl-onecli-proxy-ev.md)). The gap recurs in delegated work: on 2026-10-03 a fresh `general-purpose` subagent got "no such tool" for `mcp__slang-mcp__discord_read_messages` although it is in the coworker's `NANOCLAW_ALLOWED_MCP_TOOLS` and the parent could call it; a parallel subagent got through with proxied curl. The cause is unknown (possibly the MCP server list not reaching spawned subagents), so don't report one as fact; have a delegated Discord read prove the tool with one trivial call, or brief proxied curl from the start, and check `ncl groups config get` if it recurs ([discord_read_messages MCP tool unreachable in fresh subagents despite allowlisting](../learnings/1791024381818-discord-read-messages-mcp-tool-unreachable-in-fres.md)).

An older note predates this: with slang-mcp down AND `gh` failing on an invalid `GH_TOKEN`, it used the unauthenticated public REST API (`curl -s https://api.github.com/repos/shader-slang/slang/issues/<n>`, `curl -sG https://api.github.com/search/issues ...`; 60 core + 60 search req/hr; GraphQL at limit 0, so Discussions unreachable) and declared Discord, Slack and GitLab (nv-master) unavailable. The Discord half is superseded; Slack and GitLab are untested via the proxy, so try the proxied raw API first and state in the report whatever stays unreachable ([Daily-report fallback when slang-mcp server is down](../learnings/1782288946942-daily-report-fallback-when-slang-mcp-server-is-dow.md)).

## Slangd LSP Probing

To confirm a language-server fix clears a diagnostic bug (e.g. #11532, false errors when opening a module fragment), drive a REAL `slangd` over stdio, not slang-test's `LANG_SERVER` harness, which forces `-periodic-diagnostic-update false` so slangd never publishes diagnostics. A minimal client (initialize → initialized → textDocument/didOpen → read ~5s → collect `textDocument/publishDiagnostics`, LSP `Content-Length: N\r\n\r\n<json>` framing) sees the errors within ~1-2s ([Verify Slang LS (slangd) diagnostics with a manual stdio LSP probe, not slang-test](../learnings/1781088708789-verify-slang-ls-slangd-diagnostics-with-a-manual-s.md), [Verify language-server-only diagnostic fixes with a real-slangd LSP stdio probe](../learnings/1781118241659-verify-language-server-only-diagnostic-fixes-with-.md)). A hardened probe lives at `/workspace/agent/wt-slang-11532/expt-logs/probe_slangd.py`. Run a CONTROL arm (unpatched build) first to prove probe + repro reproduce the bug. `slang-unit-test` cannot link `Workspace`/`getOrLoadModule` (non-`SLANG_API`, `-fvisibility=hidden`) ([Verify Slang LS (slangd) diagnostics with a manual stdio LSP probe, not slang-test](../learnings/1781088708789-verify-slang-ls-slangd-diagnostics-with-a-manual-s.md)).

## OneCLI Gateway: Injection Is PATH-SCOPED

The gateway injects credentials **per-path** and per-service: on a shader-slang-scoped agent `api.github.com/repos/shader-slang/*` returns **200** while any other org (`repos/microsoft/*`) returns **401 Bad Credentials**, and the same gateway injects the Discord bot token on `discord.com/api/v10/...`. An intact proxy env is **necessary but not sufficient**; the credential is healthy, it just has no rule for the foreign path. So a scoped 401/403 is not evidence of a broken token, a missing object, or a vault problem; the discriminator against a real token outage (the Discord all-channel 401 below) is whether an in-scope path still returns 200.

**The real defect is how the failure presents.** `curl -sf` suppresses the error body, so a 401 arrives as **empty stdout, byte-identical to "this object does not exist upstream."** On 2026-08-06, root-causing a submodule-pin CI failure, three `curl -sf .../microsoft/mimalloc...` calls returned nothing and the tempting "the pinned commit was force-pushed away" was unsupported by the data. Drop `-f` and run a **positive control** before reading empty as absence:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -H "User-Agent: curl/8.0" \
  "https://api.github.com/repos/microsoft/mimalloc"      # -> 401  (out of scope)
curl -s -o /dev/null -w '%{http_code}\n' -H "User-Agent: curl/8.0" \
  "https://api.github.com/repos/shader-slang/slang"      # -> 200  (control)
```

**The workaround is the git wire protocol, which is not path-gated like REST.** `git ls-remote --heads/--tags/--symref <url>` and a `--filter=blob:none` scratch clone succeed against foreign orgs over the same proxy, enough for ref existence, default branch and `git merge-base --is-ancestor`. `/repos/{o}/{r}/branches/{b}/protection` is also 403 on this scope, so "is this check required?" comes from merge evidence. Never `unset HTTP_PROXY` to "fix" a 403: it strips the injected token and drops the rate limit from 6000/hr to 60/hr ([OneCLI gateway injection is path-scoped; `curl -sf` hides the 401 as empty output](../learnings/1785992213588-onecli-gateway-injection-is-path-scoped-cross-org-.md)).

## GitHub GraphQL / ProjectsV2 Access

ProjectsV2 boards require a per-project access grant in the project's settings, separate from org-level Projects permission; the nv-slang-bot App may have org Projects R/W yet 403 on a board. The dev instance used a human PAT path-routed to `/graphql`; prod has no such PAT, so ProjectsV2 writes are generally unavailable to prod coworkers. The same path-scoping applies at pattern granularity: `/graphql*` won't match the bare `/graphql`, so use the literal ([GitHub GraphQL / ProjectsV2 access needs a per-project grant (often unavailable to the bot)](../learnings/legoop-project_graphql_path_routing.md)).

## Discord MCP Failures: Token Outage vs Cold Start vs Channel Type

If `discord_send_message` returns `"Discord client initialization timed out"` AND `discord_read_messages` returns `Discord API error 401: Unauthorized` (on the daily #slang-committers PR report or any Discord MCP use), it is a GLOBAL bot-token failure in the OneCLI vault, not a per-container cold start. A cold-start timeout is transient (a retry within a minute succeeds; reads still work); a credential failure shows 401 on reads, reproducible across sessions and containers. Stop after 2-3 attempts (only the operator can re-auth), preserve the report body to `/workspace/agent/<name>-UNPOSTED.md`, attach it to the parent via `send_file`, and report `blocked` with exact error strings and attempt counts; the scheduled job self-heals on the next fire, and a partial report is never posted. (`pr_report.py` exit codes: 10 = report due, 0 = quiet day, else transient; chunk the body at `- **` assignee boundaries ≤1900 chars) ([Discord MCP 401 + send-timeout = global gateway credential failure, not cold-start](../learnings/1784696975060-discord-mcp-401-send-timeout-global-gateway-creden.md)). A 401 from `discord_read_messages` on **every** channel after one confirming retry is likewise a token outage, not a blip, a single-channel 403, or a quiet channel: report it as infra in the daily report's Community section and Action Items and proceed with the GitHub/CI/DeepWiki steps ([Discord MCP 401 across all channels = token outage, not transient](../learnings/1784708358394-discord-mcp-401-across-all-channels-token-outage-n.md)).

`discord_read_messages` can also start returning `Unsupported channel type` on thread/forum channels (`discord.com/channels/<guild>/<thread_id>/<msg_id>`). On 2026-09-16 it worked earlier in the session on the same channel_id, then failed (once with a socket-closed error) across turns: a Discord-side or library rejection, not auth. Root cause is unconfirmed (worked-then-failed argues for mid-session connection degradation over a channel-type limit), so relay neither as fact. Workaround: read the text from the dashboard webhook notification, which carries the full body; the tool matters only for history not already delivered. If it recurs, surface it to the operator for the slang-mcp Discord adapter ([slang-mcp discord_read_messages fails 'Unsupported channel type' on thread channels](../learnings/1789537044392-slang-mcp-discord-read-messages-fails-unsupported-.md)).

## DeepWiki Rename and Hook Denials

**DeepWiki renamed `ask_question` → `ask_wiki_question` (2026-09-22), and stale allowlists deny the current name fleet-wide.** The server (`https://mcp.deepwiki.com/mcp`) exposes `read_wiki_structure`/`read_wiki_contents`/`ask_wiki_question`, so `mcp__deepwiki__ask_question` returns `No such tool available` (the rename landed mid-session). Every coworker skill's `allowed-tools:` and shader-slang/slang `CLAUDE.md:12` still list the old name, so the `PreToolUse` allowlist gate DENIES the correct `ask_wiki_question`, silently degrading lookups in deep-research, slang-code-reader, slang-explore, slang-pr-review-runner, slang-clarity-review-runner, slangpy-code-reader and nanoclaw-code-reader. On "No such tool available", check your injected MCP schema (the "MCP Server Instructions" block) for the current name before retrying; if the correctly-named tool is then hook-denied, that is the real bug, not something to fix by guessing names. Trust the live schema over static docs; the interim workaround is GitHub source/issue research, disclosed in the answer. That alone sufficed in the 2026-10-03 maintainer Discord sweep, where `ask_wiki_question` was hook-denied and no local slangc existed: `gh api repos/<o>/<r>/contents/<path> --jq .content | base64 -d`, tags/commits and `search/issues` answered repo-state questions such as slang-rhi readiness. The gap was still open on 2026-11-06: in a Discord summon `mcp__deepwiki__ask_wiki_question` returned "PreToolUse hook error: Blocked by hook" while the summon prompt still named the absent `ask_question`. The answer cited GitHub sources instead (docs/building.md, CMakeLists.txt, issues), and the gap went to the dashboard. For "undefined reference to slang_*" the fast path is `curl https://raw.githubusercontent.com/shader-slang/slang/master/include/slang.h` and a grep for line numbers, and the 2000-char Discord limit is checked before posting. `mcp__slang-mcp__github_get_file_contents` works only for shader-slang repos: `owner=SaschaWillems` returned 401 "GitHub is not connected in OneCLI", `gh api` gave "Bad credentials" and a raw.githubusercontent WebFetch 404'd, so a claim about a third-party tutorial's CMakeLists stays a hypothesis ([Discord summon research: DeepWiki ask_wiki_question may be hook-blocked; github_get_file_contents 401s off shader-slang](../learnings/1793988435258-discord-summon-research-deepwiki-ask-wiki-question.md)). Riders: `/channels/<id>/messages/<mid>/reactions/<url-encoded-emoji>` lists who reacted (is a reaction on a bot answer the OP's feedback?), and a `limit=50` read of #slang-committers returns ~67 KB persisted to a file, so parse it with python, not inline ([Discord sweep: DeepWiki may be hook-denied; use gh api for source facts](../learnings/1791015402136-discord-sweep-deepwiki-may-be-hook-denied-use-gh-a.md)). The durable fix is operator-side: update the lego-registry SKILL.md `allowed-tools` (source of truth `container/skills/*`; prefer a wildcard `mcp__deepwiki__*` against future renames) and PR the stale name in shader-slang/slang CLAUDE.md ([DeepWiki MCP tool renamed ask_question → ask_wiki_question; fleet-wide allowlist gap](../learnings/1790105381468-deepwiki-mcp-tool-renamed-ask-question-ask-wiki-qu.md)).
