# Slang PR Process, Maintainer Workflow, and Issue Lifecycle

## TL;DR

- The on-call maintainer rotates ~biweekly: look it up live; reconcile by searching the channel for the *topic*, not a reply to the bot.
- Internal "APPROVE-clean" verdicts are invisible on GitHub; reconcile every handoff against live PR state.
- `mergeable_state` says THAT a requirement is unmet, never WHICH; `mergeable=true` is not `reviewDecision=APPROVED`. An approval counts only if it was given at the head: `commit_id == head` alone can be a carried-forward approval (GitHub moves a kept review's commit to the new head), so also compare `submittedAt` with the head commit's date. `COMMENTED` is not a verdict.
- Don't push after an APPROVE unless required: any new head commit (even a comment reword the maintainer asked for) dismisses it, so after it say "dismissed, awaiting re-approval" in every status. `behind` is not a rebase cue and does not block the merge queue.
- Events under jhelferty-nv's login (assignments, milestones, review requests, board moves) are mostly the triage automation; count only their written comments as their activity.
- Verify a merge by CONTENT, not ancestry (squash rewrites SHAs); auto-close lags; a blocked verification call means UNKNOWN.
- Required check names = kebab-case job key. A `failed_checks` eviction CLEARS auto-merge → manual requeue.
- Verify against checkout HEAD, not a stale `build/Release/bin/slangc`; author-date in a [good,bad] window is not release membership; re-check `gh pr list` after a long build (the reporter may have self-fixed).
- Bot writes: `push:false` in `.permissions` is normal (only a real `git push` is authoritative); one `gh api … comments POST` yields `.id` and `.html_url`; re-push after the LAST amend BEFORE `gh pr create`.
- Bot PRs: no `--assignee`/`--reviewer`, even when asked; @-mention in the description.
- Codegen asymmetry: lift the BAD leg to the good one (#12004). Doc-vs-behavior: measure the behavior fix's cost first (#11682).
- Comments describe code as-is (no history, no PR pointers); touch existing comments only when their code changed; rationale goes in the PR explanation comment; a long comment for an exceptional case means remove the case. Doc comment = one-sentence brief, blank `///`, contract; params named by role.
- **A clean textual merge proves nothing semantic**: run both sibling PRs' new tests on a scratch merge; after merging master into an API-changing PR, grep master's added files for removed forms and prove causation against a master control.
- **Reassignment after the bot's draft PR exists → freeze, don't stand down** (#13463/#13475).

Companion: [[wiki/concepts/slang-pr-maintainer-scope-and-evidence.md]] (draft-PR footprint, maintainer-decision reversals).

## Reading Live PR State

Before calling a handoff merge-ready, reconcile draft status, CI, review decision and unresolved threads on the live PR; an internal verdict is not visible there ([handoff: verify live PR state](../learnings/1779622726384-slang-maintainer-handoff-verify-on-pr-state-agains.md)).

**`mergeable_state` is one opaque enum.** On #12148 CI was green and a maintainer `APPROVED` at HEAD, yet the PR sat at `mergeable: true` + `mergeable_state: "blocked"`: two names in `requested_reviewers` had not reviewed. Report the observation, candidate blockers and blind spots, not a cause ("awaiting a merge click" vs "awaiting a second reviewer" need different follow-ups). Read `--jq '{mergeable, mergeable_state, requested_reviewers:[.requested_reviewers[].login]}'`, then `pulls/<n>/reviews --jq '.[] | "\(.user.login) | \(.state) | \(.commit_id)"'`: a requested name without an APPROVED/CHANGES_REQUESTED review is outstanding (`COMMENTED` does not discharge it). Check-runs are cumulative across runs; filter for conclusions other than success/skipped/neutral instead of trusting the badge. Name your token: with an App/bot token, `GET /repos/*/branches/<b>/protection` returns 403 and GraphQL `reviewDecision` 401, while REST `requested_reviewers` is readable. Read the field that would change if your hypothesis were false ([mergeable_state: THAT, not WHICH](../learnings/1785791831427-mergeable-state-tells-you-that-a-requirement-is-un.md)).

`mergeable=true` (no conflicts) is not `reviewDecision=APPROVED` either: on #12935 (offered as the fix for #13259), "MERGEABLE since 09-16" hid an unresolved CHANGES_REQUESTED (does `return none()` merely relocate the ICE?) that #13259's requested test targeted. Read `gh pr view --json reviewDecision,reviews` before calling a PR idle; "repro compiles + validates" is not the reviewer's bar, and a PR with an open soundness concern does not claim `Closes #X` ([verify review state before "idle-mergeable"](../learnings/1790310304171-verify-a-pr-s-actual-review-state-before-framing-i.md)).

**Approvals and pushes.** A new head commit dismisses an approval (`APPROVED` → `REVIEW_REQUIRED`); "Update branch" and body edits do not, and when an approval survives a base-branch merge GitHub rewrites its `commit_id` to the new head (#13849: a 10-22 approval reported against a 10-28 bot master-merge commit) ([review commit field can move forward](../learnings/1793176871441-github-review-commit-field-can-move-forward-to-a-l.md)). On #12034 a comment-only reword (`a0635cc612`, 16:50) dismissed jkwak-work's 16:46 approval of `bdf2c2a2d0`; #12009 repeated it, and both were relayed as "approved, awaiting merge" while `REVIEW_REQUIRED`. Push after approval only for a requested code change or a real CI fix; for a requested cosmetic change, say it dismisses the approval and let the maintainer decide. A requested change still costs the approval: on #13880 a one-line reword the maintainer asked for dismissed their approval, so after any requested push every status says the approval was dismissed and the PR waits for re-approval, and a CI failure afterwards is a question to the maintainer before another push ([any push to an approved PR dismisses the approval](../learnings/1793204795938-shader-slang-slang-any-push-to-an-approved-pr-dism.md)). `mergeable_state=behind` on an approved, conflict-free PR is benign; the maintainer resolves it at merge, and #13880 entered the merge queue 25 commits behind ([Closes #N / draft footprint](../learnings/1785751816891-closes-n-does-not-excuse-an-issue-footprint-while-.md)). "Approved at HEAD" means `decision=="APPROVED"` plus an approval whose `commit == head` and whose `submittedAt` is later than the head commit's committer date (`/pulls/N/commits`); with only the first two, call it "approval carried forward (not dismissed)". Supervisors check it before recording a fixer's "approved" as terminal:

```
gh pr view <n> -R <owner>/<repo> --json reviewDecision,headRefOid,reviews --jq '{decision:.reviewDecision, head:.headRefOid, approvals:[.reviews[]|select(.state=="APPROVED")|{who:.author.login, commit:.commit_id}]}'
```

Re-requesting review is a `requested_reviewers` write forbidden by the dev-team operator directive; surface that conflict to the parent (scoped override, or a no-@ "ready for re-approval" comment) ([never push after approval; re-verify at HEAD](../learnings/1784048061144-never-push-after-a-maintainer-approval-unless-requ.md), [comment-only commit dismisses approval](../learnings/1784048274524-never-push-after-a-maintainer-approves-even-a-comm.md)).

## Verifying a Merge

`git merge-base --is-ancestor <branch-sha> origin/main` fails for a squash-merged change: on slang-rhi#805 → PR #806, branch commit `f3b9f02` was squashed into `57b5dec`, and `--is-ancestor` said NO while `README.md` at `origin/main` carried the fix. Verify by content (`git show origin/main:path/to/file` after a fetch); `git rev-list --parents -n 1 <sha>` gives merge shape (1 parent = squash/fast-forward, 2 = merge), `git show --stat <sha>` the scope. `--is-ancestor` stays correct for "was X in the build that reproduced this?". Issue closure lags the merge (`Closes #805` fired a second later), so a read at `merged_at + 0s` can see `state: open`; re-read. A blocked verification call (here, a critique gate) means UNKNOWN, not UNCHANGED; a git-only fallback cannot answer issue/review state. Publish at the granularity verified, attribute causes only to whoever could observe them, and demand more evidence for exculpatory explanations ([squash breaks ancestry checks](../learnings/1785780766923-squash-merge-breaks-ancestry-checks-verify-a-merge.md)).

## CI: Status Checks, Merge Queue, Falcor Workflows

Required status-check names in `shader-slang/slang` equal the job key (kebab-case, no separate `name:`), so renaming a job key requires updating branch protection; workflow-file changes need a patch handoff because the bot lacks `workflows` permission ([status check name = job key](../learnings/1781311479883-slang-required-status-check-name-job-key-kebab-cas.md)).

Investigate evictions via `merge_group` runs (they age out quickly); a batch failure evicts the whole batch, and most evictions are Falcor timeout flakes ([merge-queue evictions](../learnings/1782392258907-investigating-merge-queue-evictions-in-shader-slan.md)). The shader-coverage `vkdemo::Context` missing-default-constructor break is all-platform, not MSVC-only, and evicts unrelated PRs ([vkdemo break is all-platform](../learnings/1781301993943-shader-coverage-vkdemo-context-break-is-all-platfo.md)). A `failed_checks` eviction clears auto-merge, so post-eviction `autoMergeRequest = null` does not mean it was never on, and the PR will not requeue itself; the bot cannot enqueue (#11675 "not authorized to push to queue branch"), so a green+approved bot PR evicted by a flake needs a manual requeue (#12122/#12151/#12152; #12289 after the #12145 GBufferRTTexGrads_d3d12 flake). Read the timeline (`AutoMergeEnabledEvent` → `RemovedFromMergeQueueEvent`), not the bare null; HOLD while a hand-queuer is engaged, but never call it self-recovering ([eviction clears auto-merge](../learnings/1785485875128-merge-queue-failed-checks-eviction-clears-auto-mer.md)).

The Falcor 3-file YML refactor (dispatcher + build + test reusable workflows) hinges on per-test-type artifact paths, `merge_group` triggers and job-key naming for required checks ([Falcor YML refactor gotchas](../learnings/1781366281118-slang-11600-falcor-3-file-yml-refactor-implementat.md)). `FALCOR_LOCAL_SLANG` is a relative, per-config build dir (not absolute), and building Falcor from source needs Slang built with GFX enabled (PR #11602) ([FALCOR_LOCAL_SLANG details](../learnings/1781368939396-correction-falcor-local-slang-usage-details-verifi.md)).

## Bot GitHub Writes

`nv-slang-bot` can push and open PRs on `shader-slang/slang-rhi` and the other shader-slang repos; `push:false` in a `gh api` `.permissions` probe is the normal App-token shape, and only a real `git push` is authoritative ([slang-rhi is bot-writable](../learnings/1781057580026-CONSOLIDATED-slang-rhi-is-bot-writable.md)).

**Post a comment once.** Re-running the POST with a different `--jq` duplicates it (#12110: comments 4976372131 + 4976372230). Use `RESP=$(jq -Rsn --arg b "$BODY" '{body:$b}' | gh api "repos/$REPO/issues/$N/comments" --method POST --input -)` and read `.id` and `.html_url` from `$RESP` (the triage workflow's snippet keeps only `.id`); afterwards count comments and delete any duplicate you authored this turn ([POST a comment once](../learnings/1784083867185-never-run-the-gh-post-comment-command-twice-to-cap.md)).

**Re-push before `gh pr create`.** The PR, reviewers and CI see the remote branch, not local HEAD: on slang#11983 (PR #12148) four local amends were never pushed, so the PR opened on the stale first commit and a `github.ci_failed` webhook (`head_sha=1787e466d8`) failed on already-fixed bugs. After the last amend, `git push --force origin fix/issue-<n>` (only when `git log origin/master..origin/fix/issue-<n>` shows solely bot-authored commits) and check `git rev-parse HEAD` equals `origin/fix/issue-<n>`. A `ci_failed` `head_sha` differing from local HEAD means a stale remote; compare `gh pr view <n> --json headRefOid`. Draft PRs don't auto-run CI on push; re-dispatch with `gh workflow run ci.yml --ref fix/issue-<n>` ([re-push before gh pr create](../learnings/1784316959883-re-push-after-every-amend-before-gh-pr-create-else.md)).

**No assignee or reviewer on bot PRs.** When jkwak asked the bot on slang#11967 to "make a PR and assign it to me," the ruling was a draft with no `--assignee`/`--reviewer`: the standing operator/dev-team [MUST NOT] on bot assignee/reviewer mutations (naming a maintainer reads as spam; CODEOWNERS auto-routes shader-slang/dev on ready-flip) outranks a maintainer's mechanical request, and peer triagers/fixers neither override it nor escalate to lift it; an @-mention in the description meets the intent. The gate applies at PR-open, separately from the operator-gated `gh pr ready`/`gh pr merge` (comments and labels are free); the fixer correctly bounced the question to the triager edge ([no-assignee gate beats "assign to me"](../learnings/1784277158125-maintainer-assign-the-pr-to-me-loses-to-standing-o.md)). `Closes/Fixes #N` stays off a draft PR and does not excuse omitting the issue footprint; a discharged blocker line is wrong and gets PATCHed in place; a create-only token asks the owning tier (slang-rhi#805 → #806).

## A Clean Textual Merge Is Not a Semantic Merge

**Sibling PRs in one diagnostic family.** #13514 (#13489 Case 2, nested `try`) claimed its conflict with the open #13503 "would be textual only". The local merge was clean, but after a Release rebuild the new `tests/language-feature/error-handling/try-nested-throwing-call.slang` failed ("Exhaustive check failed: Found 6 diagnostic(s) without annotations"): #13503 widened E30091 ("callee in 'try' does not throw") from `FuncDecl` callees to any non-throwing `FuncType` callee (subscript `operator[]`, conversion `float.init`), and since `//DIAGNOSTIC_TEST:SIMPLE` is exhaustive by default, #13514's rows for `try s[f()]` and `try (float)f()` had silently asserted E30091's absence. Merge such PRs in a scratch worktree, run both PRs' new tests, then restore with `git checkout --detach <pr-head>` and rebuild. Reviewer C (clarity) raised it as Medium; the empirical check made it a must-fix (["textual only" sibling conflict: verify by merging and running the new exhaustive tests](../learnings/1791463760924-conflict-with-sibling-pr-is-textual-only-verify-by.md)).

**Merging master into a long-lived API-changing PR.** Taking over stale #11344 (`_Texture<T:ITexelData>`; texture aliases lost their trailing `let format:int`; `Buffer` arity 2→1), `git merge origin/master` showed only textual conflicts, but code master ADDED after the PR's base using the old API merged cleanly and then failed: three core-module intrinsics (`T:ITexelElement` over `_Texture<T,…>`) and five tests (`RWTexture2D<uint,0,37>`, `Buffer<>` arity, a generic `let value = tex.Load()`, an inferred-format capability check, a reflection `.expected`). Grep `git diff --diff-filter=AM <base> origin/master -- source tests tools` for the removed forms; run the full suite; run each failure on a master control built at the exact merge SHA in a separate worktree (gfx-smoke failed on both: environmental); and never cite a test as "passing on the merge" from a run after editing its `.expected` — re-run against the committed file ([merging master into a long-lived API-changing PR: textual conflicts are half the breakage](../learnings/1791498585662-merging-master-into-a-long-lived-api-changing-pr-t.md)).

## Regression Verification Discipline

`build/Release/bin/slangc` is not checkout HEAD: confirm the binary version string and checkout ancestry before claiming a repro (slang#11483's crash was a stale pre-#11211 build) ([stale build, not master](../learnings/1780648913125-correction-slang-11483-crash-was-a-stale-pre-11211.md)). An author-date inside a [good, bad] window does not put a commit in a release; check `git merge-base --is-ancestor` (seen on a precompiled `.slang-module` import emitting location-less diagnostics) ([verify commit-vs-tag ancestry](../learnings/1780401515127-slang-precompiled-slang-module-import-triggers-loc.md)). The #11483 reporter already had the #11211 fix, so the wrong-data symptom is a distinct defect; GPU-free spirv-val cannot refute a runtime/driver symptom, so it stays open for hardware retest ([#11483 wrong-data is distinct](../learnings/1780820664909-slang-11483-reporter-s-release-already-had-11211-w.md)). For coverage-manifest bugs, read the association-copy sites and consumer validity guards before accepting a "not propagated" root cause; on #11629 HEAD contradicted it ([#11629 root cause contradicted at HEAD](../learnings/1781626696031-slang-11629-reporter-s-root-cause-contradicted-by-.md)). A P0 merge-queue stopper can be self-fixed mid-build (#11814: the reporter merged an identical #11817 ~14h into our debug build); re-check `gh pr list` and the linked-PR timeline before opening a PR ([P0 stoppers self-fixed mid-build](../learnings/1782867800939-p0-merge-queue-stoppers-can-be-self-fixed-mid-buil.md)).

## Fix-Direction Discipline

For a codegen asymmetry, converge on the good leg even when lowering it is the smaller diff: on slang#12004 (sampler-vs-texture `[noinline]` SPIR-V param asymmetry), PR #12027's Approach A (specialize scalar `SamplerState` params like textures, passing both by bindless index) was closed unmerged: *"we don't want to make changes to the SamplerState side. Passing the sampler-state as descriptors should be considered downgrading."* The by-value `OpTypeSampler` is the desired form; the texture's by-index reload is the #3252 old-driver workaround. Triage had picked A as fastest over Approach B (revert the texture workaround so both pass by value), missing that A is a downgrade. B is not authorized ("no plan to remove the workaround" unless proven driver-safe) and relaxing #3252 is maintainer-owned, so it is not reopened unilaterally. Triage defaults toward the better-codegen leg and flags the risk of touching the older invariant ([#12004 Approach A rejected](../learnings/1783635981424-slang-12004-outcome-approach-a-rejected-as-downgra.md)).

A doc-vs-behavior mismatch can be fixed on either side; measure the behavior fix's cost (test churn, output changes, optimization-shape effects) before recommending it. On #11682 (`slangc -g0` help text vs. still-emitted `OpSource`/`OpName`), a `None→Minimal` default flip defeated front-end optimizations suite-wide and gating names on `None` broke ~273 tests, steering the maintainer to a one-line docs-only fix (merged PR #12201); surfacing that blast radius was the triager's key contribution ([doc-vs-behavior: measure the cost](../learnings/1784844793184-a-doc-vs-behavior-bug-can-fix-either-side-measure-.md)).

## Code Comments Describe the Code As-Is

**No history, no pointers.** shader-slang maintainers (pdeayton-nv, PR #12148 review) ban change-history narration ("unchanged from before this change", "previously we…", "now we…") and PR/issue pointers ("see the issue linked in the PR", "deferred to a follow-up", "pending #12150"); both rot at merge. Comments state the resulting behavior ("null here → emitter uses the module-global scope"); tracking references go in the PR body or commit message. Before pushing a review fix, grep added comments for `before this change|unchanged from|previously|see .* issue|pending #|deferred to` ([comments describe code as-is](../learnings/1784573605212-code-comments-must-describe-the-code-as-is-never-c.md)).

**Minimal churn: existing comments stay verbatim.** Touch an existing comment only when its code changed; design rationale goes in the PR explanation comment, not the source. On bot PR #13283, jkwak-work (the shepherd) left nine inline comments, each asking to remove or revert a bot-added or rewritten comment: a pre-existing comment the bot had "improved" read worse and was restored; doc comments on enum values and caches were "too obvious"; internal details (an internal enum such as `FoldPolicy`, cache rationale, override contracts) stay out of declaration docs — one plain sentence per function says what it returns and, for two similarly named functions, how they differ. When a maintainer asks why a golden test "stores X in a temporary", check the emitted code and IR before answering; the bot's own test comment had the wrong cause ([Slang maintainers want minimal comment churn](../learnings/1791941642114-slang-maintainers-want-minimal-comment-churn-keep-.md)).

**A long comment for an exceptional case means restructure.** On slang#12701 (2026-10-06) jhelferty-nv requested changes on comment style alone: a 13-line doc block for an exceptional case is a smell (thread short comments through the function instead); reuse existing human comments, matching their style and ~70-column wrap; and "why is this being removed?" about one line cut from a pre-existing TODO. The fix restored every pre-existing comment verbatim and removed the case: the optional, default-valued `defaultArgSource` parameter (with an "absent" branch and an unequal-arity fallback) became an explicit, always-set argument (the callee for ordinary calls, the overload-selected declaration on a witness redirect), the fallback a `SLANG_RELEASE_ASSERT`, and a two-line `///` plus a short call-site comment sufficed. Default-valued parameters draw objections on their own too (jkwak) ([leave existing comments verbatim; a long comment for an exceptional case means restructure](../learnings/1791320932441-slang-reviewers-leave-existing-comments-verbatim-a.md)).

**Doc-comment shape.** Any comment directly on a function (`///` or `//`) is a doc comment: one sentence on what it does (or returns), a blank `///`, then the behavioural contract if needed; a comment describing one detail ("defaults come from X") fails (tangent-vector, 2026-10-09, #12701). Name parameters by role: `funcDeclRefForDefaultArgs` ("the decl-ref used to determine default args"), not `defaultArgsDeclRef` ("a decl-ref to the default args") ([doc comments: one-sentence brief, blank line, contract; name params by role](../learnings/1791566071976-slang-doc-comments-one-sentence-what-it-does-brief.md)).

## Triage Boundaries and Park Lifecycles

A rename/branding request has no engineering surface: a governance call, classified as feature request and parked at triage with no fixer and no self-close ([rename is governance](../learnings/1783935538903-triage-of-rename-branding-requests-governance-not-.md)). Docs for a compiler-limitation bug belong in the compiler repo (SlangPy docs PR #1060 was closed and redirected to the Slang docs) ([docs go in the compiler repo](../learnings/1783943839130-docs-for-a-compiler-limitation-bug-belong-in-the-c.md)). On slang#12058 the maintainer landed the ASan fix in their own PR while our fixer was auth-down, validating the triage; a stalled fixer's late draft is reaped ([#12058 validated by maintainer fix](../learnings/1783977766628-triage-validated-by-maintainer-s-own-merged-fix-a-.md)). A park is not a dead end: slang#12054's self-fix park flipped to a maintainer-authorized bot draft that merged ([#12054 park → bot draft shipped](../learnings/1783981181191-slang-12054-shipped-park-for-self-fix-that-flipped.md)).

**Reassignment after the bot's draft PR exists is a freeze, not a stand-down.** The stand-down precedent (#13420/#13436) is for reassignment *before* a PR exists. On slang#13463 (PR #13475), jkwak-work reassigned the issue to jkiviluoto-nv 14 hours after the bot draft opened, without declining the PR; the assignee adopted, un-drafted, merged master into, approved, verified in real Zed and merged it five days later (fac7213eba), with no bot pushes after the reassignment. So when the reassignment does not decline the PR, keep the draft, freeze proactive bot work (no un-draft, rebase, push, re-run or @-mention), relay every human comment verbatim on the canonical thread, and act only on an explicit human ask, fetching before any push (the assignee may force-push). Check a fixer's counter-proposal to the GO against the code: auditing every setting's null path at the base commit found a third outlier neither proposal named (`clangFormatFallbackStyle` null → "" → clang-format silently falls back to LLVM style) ([maintainer reassign after a bot PR exists: freeze, don't stand down](../learnings/1791822138397-maintainer-reassign-after-a-bot-pr-exists-freeze-d.md)).
