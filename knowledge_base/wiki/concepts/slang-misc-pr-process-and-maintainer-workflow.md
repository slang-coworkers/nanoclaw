# Slang PR Process, Maintainer Workflow, and Issue Lifecycle

## TL;DR

- The on-call Slang maintainer rotates ~biweekly — never hardcode; look it up live, and reconcile by searching the channel for the *topic*, not for a reply to the bot.
- Reconcile a maintainer handoff against LIVE PR state before calling it merge-ready — an internal "APPROVE-clean" verdict is invisible on GitHub.
- `mergeable_state` tells you THAT a requirement is unmet, never WHICH one — read `requested_reviewers` + `/reviews` (approval counts only if `commit_id == head`; `COMMENTED` is not a verdict). `behind` is not a rebase cue — a push auto-dismisses the approval.
- Verify a merge by CONTENT, not ancestry — a squash rewrites SHAs, so `--is-ancestor` gives a false "not merged." A blocked verification call means UNKNOWN, not UNCHANGED.
- `push:false` in a bot token's `.permissions` is the normal App-token shape, not a denial — the only authoritative test is an actual `git push`.
- Required status-check names = the kebab-case job key; a `failed_checks` merge-queue eviction CLEARS auto-merge, so `autoMergeRequest=null` means manual-requeue, not self-recovering.
- Verify a bug against checkout HEAD, not a stale `build/Release/bin/slangc`; an author-date inside a [good,bad] window doesn't prove it's in a release — check ancestry.
- Never push after a maintainer APPROVES unless required — any new head commit (even a comment reword) auto-dismisses the approval; re-verify `reviewDecision` at HEAD before reporting "approved."
- Capture BOTH `.id` and `.html_url` from ONE `gh api … comments POST` (a second POST duplicates); re-push after the LAST amend BEFORE `gh pr create` — PR/CI run the *remote*, not local HEAD.
- For a codegen asymmetry, lift the BAD leg to the good — don't downgrade the good leg for a smaller diff (#12004).

This page covers PR/issue-state verification, maintainer rotation, merge-queue mechanics, bot write access, regression discipline, and issue-lifecycle patterns. Companion: [[wiki/concepts/slang-misc-pr-process-and-maintainer-workflow-2.md]] (draft-PR footprint, maintainer-decision reversals).

## Maintainer Identity and Rotation

The on-call Slang duty maintainer rotates on a roughly two-week cadence and can be reassigned ad hoc. Any routing, @-mention, or escalation must use a **live lookup** via the Slang Maintainer agent — never hardcode a name ([Current Slang maintainer is dynamic — ask the Slang Maintainer agent, never hardcode](../learnings/1782144700294-current-slang-maintainer-is-dynamic-ask-the-slang-.md)). The developer tagged as `tfoley` in Slang TODO comments is Theresa Foley (often goes by "Tess"), not "Tim Foley", as confirmed in the repo's `.mailmap` ([Slang compiler: tfoley real name](../learnings/1777487718343-slang-compiler-tess-foley-name.md)).

**Reconcile the rotation from INDIRECT evidence — the bi-weekly ask is never answered directly.** The recurring "who is the next Slang Maintainer?" prompt in `#slang-committers` (`1352357976878481468`) has gone unanswered *as a reply* every cycle since 2026-06-22, so a reconciliation that looks for a response to the bot's question yields "unanswered" forever and the rotation record rots. Humans reveal the current maintainer in passing instead: on 2026-07-27 shannonwoods_90576 wrote "`<@1306357396771311747>` for visibility as current maintainer" in an unrelated thread about support-channel answer quality — that is the answer for the 2026-07-21 → 2026-08-03 term, just not where you would look for it. Second gotcha: the PR-escalation report changed rendering mid-July, so older posts show `<@jkwaknv>` while posts from 2026-07-23 onward show the raw ID — resolve ID → handle via `/workspace/agent/memory/github-to-discord.json` (keys are GitHub usernames, values are Discord **IDs**, so it is a reverse lookup), and cross-check by matching the same person's PR set under the handle in an old report and under the ID in a new one. Generalizes to any "did a human answer our bot?" reconciliation: **search the channel for the topic, not for a reply to your message** ([reconciling the Slang maintainer rotation from indirect Discord evidence](../learnings/1785758534668-reconciling-the-slang-maintainer-rotation-from-ind.md)).

## Maintainer Handoff: Reconcile Live PR State

An internal "APPROVE-clean" verdict from a reviewer is **not** visible on GitHub. Before treating a maintainer handoff as merge-ready, always reconcile against the live PR state: draft status, CI, review decision, and unresolved threads ([slang maintainer handoff — verify on-PR state against internal verdicts](../learnings/1779622726384-slang-maintainer-handoff-verify-on-pr-state-agains.md)).

**`mergeable_state` tells you THAT a requirement is unmet, never WHICH one.** A PR showing `mergeable: true` + `mergeable_state: "blocked"` with every head check-run success/skipped invites the report "branch protection, just awaiting the human merge click" — that is an *inference*, not an observation, because `mergeable_state` is a single opaque enum. On #12148 CI was fully green and a live maintainer `APPROVED` whose `commit_id` equalled HEAD, and it was still `blocked`: the actual gate was an unmet **review requirement** — two reviewers sat in `requested_reviewers` with no submitted review. "Awaiting a merge click" and "awaiting a second reviewer" demand completely different follow-ups, so the wrong one sends someone to press a button that isn't there, or parks a PR everyone believes is one click from landing. What to read instead: `--jq '{mergeable, mergeable_state, requested_reviewers:[.requested_reviewers[].login]}'`, then `pulls/<n>/reviews --jq '.[] | "\(.user.login) | \(.state) | \(.commit_id)"'` — a name in `requested_reviewers` with no APPROVED/CHANGES_REQUESTED object is an outstanding request. Non-negotiables: an approval counts only if its `commit_id` equals current head; **`COMMENTED` is not a verdict** and does not discharge a request; check-runs are cumulative across runs, so filter for any conclusion that isn't success/skipped/neutral rather than trusting an aggregate badge. **Tokens see different things — say which you used:** with a GitHub App/bot token `GET /repos/*/branches/<b>/protection` is **403** and GraphQL `reviewDecision` is **401**, so the authoritative "which rule is unmet" is simply unreadable, while `requested_reviewers` *is* readable via REST. Correct report shape: state the observation, name the candidate blockers, flag the blind spot — don't collapse it into a confident cause. Ask which field would **change** if your hypothesis were false, then read that field ([mergeable_state tells you THAT a requirement is unmet, never WHICH one](../learnings/1785791831427-mergeable-state-tells-you-that-a-requirement-is-un.md)). Relatedly, `mergeable_state=behind` on an approved PR is **not** a reason to rebase: a conflict-free trail behind base is benign, and any push auto-dismisses a fresh approval — trading a binding approval for a cosmetic fast-forward. Let the maintainer resolve `behind` at merge ([Closes #N does not excuse an issue footprint while the PR is a draft](../learnings/1785751816891-closes-n-does-not-excuse-an-issue-footprint-while-.md)).

**Verify a merge by CONTENT, not by ancestry — squash rewrites your SHAs.** `git merge-base --is-ancestor <your-branch-sha> origin/main` returns non-zero **even when the change is fully merged**, because a squash merge collapses your commits into a brand-new SHA with no ancestry link (observed on slang-rhi#805 → PR #806: branch commit `f3b9f02` squashed into `57b5dec`; `--is-ancestor` said NO while `README.md` at `origin/main` plainly carried the fix). Reporting "not merged" off a failed ancestry check is a false negative that looks authoritative. Instead: read the merged file content at the base branch (`git fetch origin main; git show origin/main:path/to/file`), check merge shape on the landing commit (`git rev-list --parents -n 1 <sha>` — 1 parent = squash or fast-forward, 2 = true merge), and confirm scope with `git show --stat --format="author=%an committer=%cn%nsubject=%s" <sha>` (which also catches something extra sneaking into the merged result). **Scope guard:** `--is-ancestor` is not broken in general — it remains the right tool for *"was commit X in the build that reproduced this bug?"*, where both sides are real commits on one graph; it is wrong only for *"did MY branch land?"* under squash. Two facts about the auto-close on the same chain, one of which is a **retraction**: the claim that `Closes #805` failed to fire was **false** (`merged_at: …18:10:04Z`, `closed_at: …18:10:05Z`, `state: closed`, `state_reason: completed` — the keyword fired one second after the merge); what *is* independently true is that issue closure is **eventually consistent** with the merge — the close is a follow-up action, not part of the merge transaction — so a read at `merged_at + 0s` can legitimately observe `state: open`, and you should **re-read after a beat before reporting "the keyword didn't fire."** But that race was *not* the cause here either (second retraction, opposite direction): the reporting agent's issue-state call was **denied by its critique gate and never ran**, its fallback was git-only — which cannot see GitHub issue state at all — and it asserted "still OPEN" by carrying a value from an ~8-hour-old upstream message, ~2 minutes after `closed_at`. ⭐ **The lead lesson: a blocked verification call means UNKNOWN, not UNCHANGED**, and the fallback was **capability-mismatched** — git answers "did this content land?" only, never issue state, review state or labels, so no amount of care within that fallback could have helped. The asymmetry that makes it worth catching: taking the false negative at face value would have meant performing a human-gated close on an already-closed issue, and a stale read implying *more* action is more dangerous than one implying less. Publishing rules that follow, since this file went wrong twice in opposite directions: **file at the granularity of what was actually VERIFIED** (a solid mechanism and a guessed consequence published as one artifact inherit equal apparent confidence), **attribute causes only to whoever could observe them** (a cause inside another agent's container is not yours to assert), and note that a **charitable/exculpatory explanation needs *more* evidence than an accusatory one** because it draws less scrutiny — the "one-second race" story fit two timestamps, was promoted from "fits my data" to "almost certainly what happened," and made the error look unavoidable ([squash merge breaks ancestry checks — verify a merge by content, not by is-ancestor](../learnings/1785780766923-squash-merge-breaks-ancestry-checks-verify-a-merge.md)).

## Merge Queue Evictions

How to investigate PR evictions: use `merge_group` event workflow run queries. Key facts: merge_group runs age out quickly, a batch failure evicts all PRs in the batch, and most evictions in practice are caused by Falcor timeout flakes rather than code regressions ([Investigating merge-queue evictions in shader-slang (merge_group runs)](../learnings/1782392258907-investigating-merge-queue-evictions-in-shader-slan.md)). A missing-default-constructor build break is all-platform (not MSVC-only) and causes merge queue evictions for unrelated PRs ([shader-coverage vkdemo::Context break is all-platform and blocks the merge queue (not MSVC-only)](../learnings/1781301993943-shader-coverage-vkdemo-context-break-is-all-platfo.md)).

A `failed_checks` eviction **clears the auto-merge** that was enabled on the evicted PR, so a post-eviction `autoMergeRequest = null` does **not** mean the author never turned auto-merge on — the eviction consumed it, and the PR will not auto-requeue or auto-merge on its own. This flips the babysitter disposition: a green+approved bot PR evicted by a flake is the **manual-requeue pattern** (#12122/#12151/#12152), not a "within the auto-requeue window, self-heals" case, because the bot itself cannot enqueue (#11675 "not authorized to push to queue branch"). Read the timeline (`AutoMergeEnabledEvent` then `RemovedFromMergeQueueEvent`) rather than inferring from the bare null — if auto-merge was on and a failed_checks eviction fired, the parent/maintainer must re-add and re-enable it by hand; HOLD (no immediate nudge) while a hand-queuer is engaged, but do not call it self-recovering (confirmed on #12289, evicted by the #12145 GBufferRTTexGrads_d3d12 flake) ([merge-queue failed_checks eviction CLEARS auto-merge — post-eviction autoMergeRequest=null is not 'never had it'](../learnings/1785485875128-merge-queue-failed-checks-eviction-clears-auto-mer.md)).

## Bot Write Access: push:false Is Not a Denial

`nv-slang-bot` can push branches and open PRs on `shader-slang/slang-rhi`. `gh api` returning `push:false` in `.permissions` is the normal shape of a GitHub App installation token and does **not** indicate write access is denied — the only authoritative test is an actual `git push` ([CONSOLIDATED: shader-slang/slang-rhi (and all shader-slang repos) are bot-writable — push:false probes are false-positives](../learnings/1781057580026-CONSOLIDATED-slang-rhi-is-bot-writable.md)).

## Regression Verification Discipline

Verifying against `build/Release/bin/slangc` is **not** the same as verifying against checkout HEAD. Both the binary version string and the checkout ancestry must be confirmed before claiming a bug reproduces on current code ([CORRECTION: slang#11483 crash was a stale pre-#11211 build, not master](../learnings/1780648913125-correction-slang-11483-crash-was-a-stale-pre-11211.md)). A commit's author-date being inside a [good, bad] window does not mean it's in a specific release — always verify with `git merge-base --is-ancestor` ([Slang: precompiled .slang-module import triggers location-less diagnostics; verify commit-vs-tag ancestry before attributing a regression](../learnings/1780401515127-slang-precompiled-slang-module-import-triggers-loc.md)).

The reporter of slang#11483 was already on a release containing the #11211 crash fix. The crash and wrong-data symptom are **distinct defects**; a GPU-free spirv-val pass cannot refute a runtime-only/driver symptom — the issue must remain open pending hardware retest ([slang#11483: reporter's release already had #11211 — wrong-data is a distinct OPEN defect, not the fixed crash](../learnings/1780820664909-slang-11483-reporter-s-release-already-had-11211-w.md)).

For coverage-manifest bugs, always read both the association-copy sites and consumer validity guards before accepting a reported root cause — the "not propagated" root cause may already be fixed at HEAD ([slang #11629 — reporter's root cause contradicted by HEAD; verify propagation before fixing coverage-manifest gaps](../learnings/1781626696031-slang-11629-reporter-s-root-cause-contradicted-by-.md)).

## Re-check gh pr list after a long build — the reporter may have self-fixed

On a P0 flaky-test/merge-queue-stopper (#11814), a correct fix was diagnosed and built, but the issue **reporter merged their own identical fix (#11817) ~14h into the debug build**. The lesson: a P0 merge-queue stopper can be self-fixed mid-build, so re-check `gh pr list` (and the issue's linked-PR timeline) **after** the build completes, before opening a duplicate PR ([P0 merge-queue stoppers can be self-fixed mid-build — re-check gh pr list AFTER the build](../learnings/1782867800939-p0-merge-queue-stoppers-can-be-self-fixed-mid-buil.md)).

## For a Codegen-Consistency Asymmetry, Converge on the GOOD Leg — Not the Low-Risk One

When triaging an asymmetry with a "good" leg and a "bad" leg, the fix should lift the *bad* leg to the good — not lower the good leg to the bad, even when lowering is the smaller/lower-risk diff. On slang#12004 (the sampler-vs-texture `[noinline]` SPIR-V param asymmetry), PR #12027's Approach A — specialize scalar `SamplerState` params like textures so both pass by bindless index — was **CLOSED UNMERGED and explicitly rejected** by the maintainer: *"we don't want to make changes to the SamplerState side. Passing the sampler-state as descriptors should be considered downgrading."* The key insight, which was NOT obvious from the code and which the triage guessed wrong: the sampler passed by-value as a loaded `OpTypeSampler` is the DESIRED form, and the texture passed by-index-and-reloaded is the WORKAROUND (from #3252, for old driver bugs). So the principled direction is Approach B (revert the texture index workaround → both by value), not A. The triage memo *did* enumerate B and flag it as the reporter's preference + a maintainer call, but RECOMMENDED A as "fastest correct fix that doesn't regress adjacent surfaces" — a framing that under-weighted that A is itself a quality regression (downgrade) even if behavior-symmetric. Lesson: lead by asking which leg is the better codegen and default the recommendation toward converging on THAT, flagging the risk of touching the older invariant, rather than defaulting to the low-risk-but-downgrading direction. B is NOT authorized here ("no plan to remove the workaround"; removal scheduled only if proven driver-safe) — do NOT re-open with B unilaterally; relaxing the #3252 texture-always-specialize invariant is maintainer-owned and explicitly deferred. Chain outcome was still clean: the PR surfaced the exact A-vs-B tradeoff on the real invariant so maintainers could decide with full framing ([slang#12004 OUTCOME — Approach A rejected as "downgrading"; sampler-as-descriptor is the desired form, not the bug](../learnings/1783635981424-slang-12004-outcome-approach-a-rejected-as-downgra.md)).

A related fix-direction discipline applies to a doc-vs-behavior mismatch ("docs say X, code does Y"): both sides are valid fix targets, so do NOT assume the code change is the "real" fix — *measure the behavior fix's cost* (test churn, output changes, opt-shape effects) before recommending it. On #11682 (`slangc -g0` help text vs. still-emitted `OpSource`/`OpName`) the behavior attempts each carried large blast radius (a `None→Minimal` default flip defeated front-end optimizations suite-wide; gating names on `None` broke ~273 tests), which is exactly what steered the maintainer to a ~free one-line docs-only fix (merged PR #12201) — surfacing the behavior fix's true blast radius is the triager's highest-value contribution ([a doc-vs-behavior bug can fix either side — measure the behavior-fix cost before assuming code is the "real" fix (#11682 chose docs-only)](../learnings/1784844793184-a-doc-vs-behavior-bug-can-fix-either-side-measure-.md)).

## Triage/Process Boundaries and Park-Lifecycles (2026-07-14 fold)

A rename/branding request has no engineering surface — classify feature-request, park at triage, and do NOT dispatch a fixer or self-close (a rename is a project-governance call) ([triage of rename/branding requests: governance, not engineering](../learnings/1783935538903-triage-of-rename-branding-requests-governance-not-.md)). Docs for a *compiler-limitation* bug belong in the compiler repo, not the transparent wrapper: a SlangPy docs note (PR #1060) was closed by the maintainer, who directed it to the Slang docs instead ([docs for a compiler-limitation bug belong in the compiler repo](../learnings/1783943839130-docs-for-a-compiler-limitation-bug-belong-in-the-c.md)). Two lifecycle validations: slang#12058's ASan fix was landed by the maintainer's own PR while our fixer was auth-down — cleanly validating the triage and showing a stalled fixer's late draft gets reaped by the maintainer ([triage validated by maintainer's own merged fix](../learnings/1783977766628-triage-validated-by-maintainer-s-own-merged-fix-a-.md)); and slang#12054 shows a **park is not a dead end** — a contributor-self-fix park flipped to a maintainer-authorized bot draft that merged, a clean full lifecycle ([slang#12054 SHIPPED: park-for-self-fix flipped to bot draft](../learnings/1783981181191-slang-12054-shipped-park-for-self-fix-that-flipped.md)).

## Never Push After a Maintainer Approves (Even a Comment-Only Commit Auto-Dismisses It); Re-verify reviewDecision at HEAD (2026-07-15 fold)

Two-part rule, both observed failing on shader-slang/slang the same day (2026-07-14, #12034 and #12009). **(1)** Do NOT push any commit to a PR after a maintainer has APPROVED it unless the push is strictly required (a requested code change or a real CI fix). GitHub **auto-dismisses the approval** on ANY new commit to the head — turning `reviewDecision: APPROVED` back into `REVIEW_REQUIRED` and forcing re-review. This includes a comment-only / cosmetic reword: on #12034 jkwak-work APPROVED at 16:46 on head `bdf2c2a2d0`, then a comment-only "restructure the comment, no change to emitted SPIR-V" commit `a0635cc612` pushed at 16:50 auto-dismissed the approval at 16:50:23 for zero functional gain (same pattern hit #12009). A comment reword is never worth losing an approval — if the PR is approved and you have a cosmetic tweak, HOLD it. Subtlety: even when the maintainer *requested* the comment change, applying it still dismisses their approval — so flag the trade-off ("applying this will dismiss your approval — want me to, or leave it?") and let them decide rather than silently pushing. **(2)** Before reporting a PR as "APPROVED / awaiting merge," re-verify `reviewDecision` at HEAD — do NOT infer it from "I saw an approve webhook earlier." An approval is only live if it sits on the *current* head commit: the approving review's `commit_id` must equal `headRefOid`. Both #12034 and #12009 were relayed as APPROVED/awaiting-merge while at HEAD both were `REVIEW_REQUIRED` with the review DISMISSED by a later push. Verify-at-HEAD one-liner: `gh pr view <n> -R <owner>/<repo> --json reviewDecision,headRefOid,reviews --jq '{decision:.reviewDecision, head:.headRefOid, approvals:[.reviews[]|select(.state=="APPROVED")|{who:.author.login, commit:.commit_id}]}'` — "approved at HEAD" requires `decision=="APPROVED"` AND an approval whose `commit == head`. Supervisor/orchestrator corollary: when a fixer relays "PR approved, awaiting merge," verify `reviewDecision==APPROVED` at HEAD before recording it terminal-positive — the claim is frequently one push stale. Related conflict: the natural remedy (re-request review) is a `requested_reviewers` write forbidden for any maintainer/reporter by the dev-team operator directive, so you can't just re-request to re-land the approval — surface the conflict to parent (scoped override, or a no-@ "ready for re-approval" nudge comment). Note "Update branch"/body edits do NOT dismiss an existing approval — only a new head commit does ([never push after a maintainer approval unless required — post-approval commit auto-dismisses; re-verify reviewDecision at HEAD](../learnings/1784048061144-never-push-after-a-maintainer-approval-unless-requ.md), [never push after a maintainer approves — even a comment-only commit auto-dismisses the approval](../learnings/1784048274524-never-push-after-a-maintainer-approves-even-a-comm.md)).

## Never Run the gh POST-Comment Command Twice to Capture Both id and url (2026-07-15 fold)

When posting a triage/verdict comment via `gh api .../comments --method POST`, capture BOTH `.id` and `.html_url` from ONE call — never POST once with `--jq '.html_url'` and again with `--jq '.id'`: the second POST creates a **duplicate GitHub comment** (observed on #12110, 2026-07-15: comments 4976372131 + 4976372230, ~1s apart). Capture the full response once: `RESP=$(jq -Rsn --arg b "$BODY" '{body:$b}' | gh api "repos/$REPO/issues/$N/comments" --method POST --input -)`, then `echo "$RESP" | jq -r '.id'` and `.html_url` from the same `$RESP`. The triage workflow's own snippet only captures `.id` (writes to IDFILE) — if you also want the URL, derive it from that single stored response. After any comment POST, immediately `gh api .../comments` to count; if a duplicate appeared, delete the extra (safe when you authored both this turn) ([never run the gh POST-comment command twice to capture both id and url](../learnings/1784083867185-never-run-the-gh-post-comment-command-twice-to-cap.md)).

## Re-push After Every Amend BEFORE gh pr create — the PR and CI Run the Remote, Not Local HEAD

`gh pr create` opens a PR against whatever the **remote** branch points at, not your local HEAD — so if you `git commit --amend` or rebase a `fix/` branch after an initial `git push` and don't re-push before opening, the PR diff, the reviewer's view, and CI all run the stale earlier commit. On slang#11983 (PR #12148) the first commit was pushed, then amended four times locally (null-deref, multi-CU misscope, source-manager-anchoring fixes from codex review) with no re-push before `gh pr create`; the PR opened against the stale buggy first commit and a `github.ci_failed` webhook fired with `head_sha=1787e466d8`, correctly failing on bugs already fixed locally. Rules: after the LAST amend/rebase and before `gh pr create`, run `git push --force origin fix/issue-<n>` (safe only when `git log origin/master..origin/fix/issue-<n>` shows solely your own bot-authored commits — never force over a maintainer's commit), and sanity-check `git rev-parse HEAD == git rev-parse origin/fix/issue-<n>`. Corollary for CI-failure triage: a `ci_failed` webhook whose `head_sha` is NOT your current local HEAD is a **stale-remote signal**, not necessarily a real code failure — check `gh pr view <n> --json headRefOid` against local HEAD first. Re-dispatch CI after the force-push (`gh workflow run ci.yml --ref fix/issue-<n>`), since a push doesn't auto-run CI on draft PRs ([re-push after every amend before gh pr create — else the PR/CI runs the stale first commit](../learnings/1784316959883-re-push-after-every-amend-before-gh-pr-create-else.md)).

## Maintainer "assign the PR to me" LOSES to the Standing Operator No-Assignee Gate

When a maintainer explicitly asks the bot to "make a PR and assign it to me" (jkwak on slang#11967) and a chain-authority conflict is flagged, the ruling is: **open the draft PR with NO `--assignee` and NO `--reviewer`.** There is a standing operator/dev-team [MUST NOT] on bot-PR assignee/reviewer mutations (even naming a maintainer reads as spam; CODEOWNERS auto-routes shader-slang/dev on ready-flip) — an operator-level gate that a triager or fixer, being a *peer* rather than the operator, cannot authorize an override of, and should NOT escalate to the operator to lift (not the bot's call to force). The operator gate wins over the maintainer's mechanical request. Satisfy the maintainer's *intent* without the forbidden mutation by @-mentioning them in the PR **description prose** ("@X — opened per your request on #N; ready for your review/ready-flip"), which notifies them without an assignee/reviewer API write; keep `Closes/Fixes #N` off while the PR is a draft. This is stricter than — and separate from — the operator-gated `gh pr ready`/`gh pr merge` writes (comments/labels are free): the assignee/reviewer no-op applies even at PR-open time. The fixer correctly HELD the question and bounced it to the triager edge (owner of the fixer edge) to rule, rather than deciding it ([maintainer "assign the PR to me" loses to standing operator no-assignee gate; satisfy intent via @-mention in the description](../learnings/1784277158125-maintainer-assign-the-pr-to-me-loses-to-standing-o.md)).

## Code Comments Describe the Code As-Is — Never Change-History or PR/Issue Pointers (2026-07-21 fold)

A source comment describes what the code does and why it is as it is, for a reader seeing it fresh with no PR/diff context. Two phrasings are explicitly banned by shader-slang maintainers (pdeayton-nv, PR #12148 review): (1) **change-history narration** — "unchanged from before this change", "previously we…", "now we…"; the reader has no "before", so the comment must stand on its own describing the current code; (2) **PR/issue pointers** — "see the issue linked in the PR", "deferred to a follow-up", "pending #12150"; a tracking issue belongs in the PR description or commit message, not the source. Both rot immediately: once the PR merges there is no "before" and the linked-issue context is gone, leaving a comment that only made sense during review. This is the same discipline as the repo CLAUDE.md's "Commit message ≠ code comment" / "design rationale goes in the PR body, not source", now confirmed by a second maintainer. How to apply: when a review narrows/changes scope, rewrite affected comments to describe the *resulting* behavior directly (state a case's actual response — "null here → emitter uses the module-global scope" — rather than "deferred to #N"); before pushing a review-fix, grep the diff's added comments for `before this change|unchanged from|previously|see .* issue|pending #|deferred to`, and keep the follow-up reference in the PR body only ([Code comments must describe the code as-is — never change-history ("unchanged from before") or PR-pointers ("see linked issue")](../learnings/1784573605212-code-comments-must-describe-the-code-as-is-never-c.md)).
