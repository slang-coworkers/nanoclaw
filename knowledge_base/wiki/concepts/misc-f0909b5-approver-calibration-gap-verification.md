## TL;DR

How the auto-approver decides whether a flagged gap CLEARS or forces ABSTAIN(OPEN_GAP), grounded in verifying against source rather than plausibility. The through-line: every judgment call bends one-directionally toward approval, so name the escape hatch and check it literally.

- **The Step-3 severity bar has THREE disjunctive ABSTAIN prongs** (plausible trigger / real blast radius / undermines purpose) — treating small blast-radius as a *mitigator* of a fired trigger is the classic slide. Name WHICH escape hatch you invoke ("unreachable" / "covered elsewhere" / "pure future-proofing") and verify it; grep your own draft for "but"/"however" after conceding a trigger.
- **A no-trigger clearance resting on an unstated API guarantee is OPEN_GAP** unless the guarantee is in the vendor docs/header ("the count is always positive", "empty is not a real state"). An external-API version-floor claim needs ground-truth header verification, not internal consistency. A "GPU-less CI, no trigger" rationale is self-contradictory when the same PR runs GPU lanes.
- **A red head on a shipped config is not approvable** — separate the FACT (head is red) from the HYPOTHESIS (transient vs a persistent new dependency the change introduced); disclose the split, don't round up.
- **Reachability can be settled earlier in the pipeline:** a sibling type-kind that "falls through to a buggy branch" may be REJECTED or SPECIALIZED-AWAY at check/specialize before the consumer runs — characterization tests pin where a kind is legal.
- **Documented ≠ fixed:** an in-code TODO with a placeholder link (`NNNN`) and no pin test leaves the behavior byte-identical → still OPEN. But "will regeneration reproduce X?" is checkable against the prompt + source-doc — spend the cheap grep before handing a human an "unknowable."
- **Test coverage:** a revision can satisfy a reviewer's literal ask while regressing what matters — diff test directives against the prior revision for CI *reachability*; a cited negative control must exercise the exact CHANGED branch predicate, not just the same file area; on a big revision, diff against BASE for stray committed artifacts and treat any author "why it's untested" note as a claim to falsify.
- **Output-neutral IR refactors must be PROVEN per removed encoding/state** — direct-enqueue preservation is necessary but not sufficient; a memoized one-shot walk can drop transitive re-notification on a single-drain caller; require a discriminating output-control test.

## The one-directional slide and named escape hatches

The recurring failure is bending a judgment call toward approval. On docs-only #12631 the challenger conceded the `python`→`python3` trigger was plausible then cleared it because the blast radius was small — but the three ABSTAIN prongs are DISJUNCTIVE, so blast-radius only ADDS caution, never removes a fired trigger; the fix is to name which escape hatch you're invoking and verify it literally, and grep your draft for "but"/"however" after conceding a trigger ([Blast-radius is a separate prong, not a mitigator of the plausible-trigger prong](../learnings/1787173201975-approver-challenger-miss-blast-radius-is-a-separat.md)). Two "unreachable" clearances rested on unverified premises: on #12649 the residual gap (an empty-set folded into a not-available code) was cleared on "empty is not a real NVRTC state," but NVRTC's docs give no such guarantee and a documented defect can return 0 — an API's *typical* behavior is not a *guaranteed* invariant, so name the SOURCE of the guarantee and read it ([NVRTC empty-set clearance rested on an unverified "not a real state" premise](../learnings/1787254161831-approver-challenger-miss-nvrtc-empty-set-clearance.md)); and on the same PR a coverage gap was cleared as "inherent to GPU-less CI" while the same investigation cited passing GPU lanes — a self-contradiction, and the real (surviving) gap is that the integration test is no-op-equivalent, which is OPEN_GAP not a clear ([A "gap clears because GPU-less CI" rationale is self-contradictory when the same PR runs GPU lanes](../learnings/1787309040135-approver-challenger-miss-a-gap-clears-because-gpu-.md)). An external-API version-floor claim ("API X introduced in V") is a claim about a third party's headers, so verifying it against the PR's own gating is circular — check it against the real upstream headers at V and V-1; a docs-only factual error that undermines the PR's stated purpose is a CRITIQUE_MUSTFIX ABSTAIN even when the code is correct ([API-introduction-version claims need ground-truth header verification](../learnings/1787286715383-approver-challenger-miss-api-introduction-version-.md)). And a red build whose proximate cause looks transient (curl/SSL) still abstains: separate the FACT (head red on a shipped config) from the HYPOTHESIS (flake vs a persistent new dependency the change introduced), do the cheap discriminating read, and disclose the split rather than rounding "might be a flake" up to approve ([A red build with a transient-looking cause still abstains — disclose, don't round](../learnings/1787216719469-approver-challenger-a-red-build-with-a-transient-l.md)).

## Reachability and "documented ≠ fixed"

A structurally-real fall-through can be dynamically unreachable because an upstream stage rejects the only way to produce it: on #12435 the `GlobalGenericParamDecl` half of a buggy `getDefaultVal` branch is rejected at the CHECK stage with E38207 before IR lowering, and `docs/generated/tests/**` characterization tests pinned exactly where the type-kind is legal — so when challenging "sibling kind X falls through," check whether X is rejected or specialized-away at an earlier stage ([global type_param is unreachable — rejected at CHECK stage before IR lowering](../learnings/1787173740909-approver-clause-gap-global-type-param-is-unreachab.md)). Conversely, documentation is not a fix: an author who responds to a challenger gap with an accurate in-code TODO that has a placeholder link (`NNNN`) and no pin test leaves the runtime byte-identical → grade the behavior at head, not the prose about it ([A documented gap with a placeholder link and no pin test is still OPEN](../learnings/1787210660984-approver-challenger-calibration-a-documented-gap-w.md)). For generated artifacts specifically, edit-correctness and hand-edit-acceptability are TWO separate questions: verify correctness from source as usual, but a hand-edit that skips the documented regenerate-from-source path is an OPEN_GAP unless the deviation is genuinely inconsequential AND durable — "the lint doesn't enforce it" answers neither ([edit-correctness and hand-edit-acceptability are two separate questions](../learnings/1787298906713-approver-critique-mustfix-for-a-generated-auto-pro.md)). Yet the durability half is often checkable, not unknowable: "will a regeneration reproduce X?" reduces to "do the per-bundle `_prompt.md` or cited `source_doc` direct X?" — a grep, and inputs silent on it means regeneration won't reproduce it ([Will regeneration reproduce X? is checkable — don't abstain on it as unknowable](../learnings/1787309983848-approver-clause-gap-will-regeneration-reproduce-x-.md)). And an accurate critique finding can be accurate-but-intentional: a "second path has the same shape" flag is not automatically a defect — read the resolver to see whether that path can even carry the user-facing input before widening a fix ([Critique finding can be accurate-but-intentional; verify the resolver before acting](../learnings/1787306565821-critique-finding-can-be-accurate-but-intentional-v.md)).

## Test-coverage discipline

"Author addressed the reviewer's comment" ≠ "coverage improved." A `synchronize` that converts a compile-only `//TEST:SIMPLE:-target spirv` (runs in GPU-free CI) into a Vulkan execution test (skipped on GPU-less lanes) REGRESSES CI reachability for a compile-time bug — diff the changed test directives against the prior revision and ask whether CI reachability regressed ([A synchronize that "fixes" a test gap can REGRESS CI coverage](../learnings/1787295337772-approver-challenger-calibration-a-synchronize-that.md)). A cited negative-test control must exercise the exact CHANGED branch predicate: on #12690 an existing "does not conform" test used an EQUALITY constraint that the new prefilter explicitly EXCLUDES (`if (!isEqualityConstraint)`), so it reads like coverage but runs the skipped branch — match a control by the predicate the diff narrows, not by topic/file-area ([A cited negative-test control must exercise the CHANGED code path](../learnings/1787369819615-approver-critique-mustfix-a-cited-negative-test-co.md)). On a big multi-commit "address feedback" revision, diff against BASE not just the feature hunks — R4 of #12490 added five stray committed compiler-output artifacts (.spv/.dbg.spv/.hlsl) at repo root that a logic reviewer (Devin) can't see, a concrete must-not-merge OPEN_GAP; and an author's "why it's untested" note ("no diagnostic populates top-level secondary_spans") is a CLAIM to falsify against source (E30515 declares two top-level spans), same as a bot's "addressed" claim ([Diff a big revision against BASE for stray artifacts; an author's "why untested" note is a claim](../learnings/1787557514309-approver-challenger-diff-a-big-address-feedback-re.md)).

## Proving output-neutral IR refactors

A refactor that splits an overloaded set/flag or replaces mutual recursion with a memoized iterative walk is claimed "byte-identical output," but that must be PROVEN per removed encoding, not asserted (precedents #12343/#12405 silently regressed while looking inert). The probes: confirm each direct enqueue fires regardless of the memo, confirm the mutation-notification channel bypasses the memo (force-seed), confirm the memo resets at every drain entry, and note that a persistent pointer-set is safe against deletion because Slang IR uses a bump-allocator that never recycles addresses within a drain ([Proving a split-the-walk / add-a-memo IR refactor is output-neutral](../learnings/1787315793233-approver-challenger-miss-proving-a-split-the-walk-.md)). But the direct-enqueue proof is INCOMPLETE: when the old code was mutually recursive, re-enqueuing A transitively re-walked A's entire forward closure reaching a *transitive* user C through an inert pass-through B — a persistent memo suppresses that once B is memoized, and force-seeding A does not reach C. The load-bearing question is "does any caller depend on the removed transitive re-notification, and does it re-drain to a fixpoint?" A full-module driver re-drains and MASKS the miss; a single-drain on-demand caller does NOT, and a full-module-only test reads as coverage while testing the masked path (the vacuous-guard trap) → ABSTAIN ([Split-the-walk memo can drop transitive re-notification on a single-drain caller](../learnings/1787316644498-approver-critique-mustfix-split-the-walk-memo-can-.md)). The complement is a confirmed-safe criterion: a DCE "clear-a-mark by generation counter" epoch scheme is sound ONLY if it keeps the once-per-call zero-baseline AND starts the epoch ≥1 incrementing only inside its own loop — the rejected "start high and skip the zeroing" alternative is UNSOUND because an unbounded serialize index can equal a high starting epoch → false-alive; here byte-identical CI + a positive-control test carries real bits because the failure mode changes codegen ([DCE epoch-stamp fix is safe iff the up-front zero-baseline is kept](../learnings/1787321284226-approver-confirmed-dce-epoch-stamp-fix-slang-12607.md)). And the "enumerate every producer branch" probe generalizes and was validated by a human: for any "register/emit/gate X at the producer" PR, if the fix patches one of several branches that yield the same product, the principled fix is to move UP to the layer where the product is aggregated branch-agnostically — but a relocation to a filtering layer introduces its own over-inclusion risk, so audit the full membership of the list being filtered ([Confirmed: the "enumerate every producer branch" probe was right — #12666 reworked to a layer above all branches](../learnings/1787350698021-approver-challenger-miss-confirmed-the-enumerate-e.md)).
