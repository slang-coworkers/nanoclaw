## TL;DR

- **An ABSTAIN is a fact about (diff × POLICY VERSION), never about the diff alone.** Re-read the policy file on every re-gate; do not replay a clause result. The same byte-identical diff produced opposite clause outcomes across a policy widening — even "same answer as last time" (still ABSTAIN_POLICY) hid a completely changed reason (`CLAUSE_FAIL` → `OPEN_GAP`).
- **A widened clause is not a discharged concern — it relocates the work from Step 1 to Step 3.** `protected_paths: pass` after the globs were cut to one is not the end of analysis; the supply-chain reasoning is now the challenger's job, and a genuine secret-reach gap surfaced *only* because Step 3 did that work.
- `eval-clauses.py` resolves its policy through a 4-step chain whose **last step is a silent fallback to the STRICT bundled default**. Measured ~4% of runs (12/279) fell back — several landing `CLAUSE_FAIL` the live policy would have passed. It **fails safe** (over-abstains, never over-approves), which is exactly why it survives unnoticed: its symptom is indistinguishable from diligence. `clauses.json` records `policy_version`, making mount-presence auditable per-decision after the fact.
- A **fail-safe defect is harder to find than a fail-open one** — state the direction in any escalation or someone "fixes" it into failing open. The real defect is the *silence* and the *ephemeral storage* of the authoritative policy, not the safe values.
- **`//` in jq (and `?:`, `get(k,default)`, `getattr`, `||`) is a falsy-coalesce, not a presence test** — it collapses `false`, `null`, and missing into one output. For a boolean config key that erases the exact distinction (`false` = intentional strictness vs missing = bug) whose two states demand opposite fixes. An absence claim about a config key demands `has()` before it is spoken.
- **Deterministic clauses are mechanical predicates, not quality judgments.** `tier_eligible` sums additions+deletions with no test-vs-production distinction, so adding a requested test can push a PR *over* the cap; that is expected — abstain means "a human must look", not "the PR got worse."
- When a PR adds a term to an **exit-code / pass-fail predicate**, trace what FEEDS the variables the new term reads — not just the new code (expected failures increment the consecutive-failure abort counter because `runTest()` returns raw `Fail` before reclassification).

## An ABSTAIN is a fact about (diff × policy version)

The keystone: a decision's identity includes the policy that produced it. On slang#12084, two prior ABSTAIN rows on the same file were `CLAUSE_FAIL:no_protected_paths`; re-gating the *same byte-identical diff* produced 6/6 pass — because the **policy file** had changed on 2026-08-04 to `v0-shadow-wide`, cutting `protected_paths` from 8 globs to one and widening caps 400→8000 / 30→150 [[a widened policy clause moves the work from Step 1 to Step 3]](../learnings/1786458728156-approver-clause-gap-a-widened-policy-clause-moves-.md). "We already abstained on this PR, it's a stale replay" re-emits a decision the policy of record no longer supports. Read `policy_version` out of `clauses.json` on every decision and treat it as part of the decision's identity; a row without its policy version is not comparable to a later row. And know *which* policy file governs — `eval-clauses.py` resolution order is `--policy` → `<ws>/policy/APPROVAL_POLICY.json` → group-mounted → bundled default, where the **bundled default is the conservative one** and the mounted one is wide; they give opposite answers on `.github/**`.

The deeper point: the widening's stated rationale is sound (in shadow mode the approver never auto-approves, so a Step-1 terminal FAIL "protects nothing and only destroys measurement signal" — 91% of resolved abstains were later approved), but it means **a widened clause relocates the concern, it doesn't discharge it.** The same policy file says verbatim "MUST BE RE-TIGHTENED BEFORE ANY ENFORCEMENT: `.github/workflows/**` is a supply-chain surface." Treating `no_protected_paths: pass` as the end of analysis is how widening-for-measurement turns into measurement of nothing — the approver ran the supply-chain probes by hand (new action dependency? trigger widening? new secret reach?) and the *vindication* was a genuine secret-reach gap that surfaced only because Step 3 did the work the widened clause no longer does. Note also: a `pass` on a clause whose predicate was *deleted* is not the same fact as a `pass` on a clause that was *evaluated* (read the evidence string); under `require_ci_green: false`, `ci_green_on_sha` prints `pass` with evidence "policy does not require CI green" — vacuous, not evidence CI is green.

By the later `v0-shadow-wide-r2` policy the widening reaches its terminus: `protected_paths=[".github/workflows/**"]` is the ONLY abstain trigger (author association, fork-head provenance, and size caps are all wide-open), so EVERY GitHub-Actions-workflow-file PR deterministically ABSTAINs at Step 1 on `CLAUSE_FAIL:no_protected_paths`, and the well-formed ones (trusted author, green CI, no blocking review) are merged by a human shortly after — the policy working exactly as the operator designed it ("abstains only on GitHub workflow files"), NOT a false-abstain to drive toward approval; these rows are excluded from agreement scoring, so don't treat the subsequent merge as a miss (#12975 merged unchanged at the exact ABSTAIN'd head). The human gate is correct precisely because workflow-YAML risk is SEMANTIC and invisible to the eligibility clauses or a byte-diff: secret / `GITHUB_TOKEN` exposure, `pull_request_target` + checkout-of-untrusted-head, `permissions:` escalation, `${{ github.event.* }}` injection into `run:`, and cross-repo `repository_dispatch` payloads. Recognize the shape early (a single/mostly `.github/workflows/**` edit), report it as the intended human-gate, and don't burn a Devin/challenger pass trying to upgrade it — the clause fail short-circuits; if the class is ever made approvable, those five probes are the review lens, not codegen correctness [[GitHub-workflow-file PRs under wide-r2 abstain-then-merge by design — the real risk is workflow semantics a human owns]](../learnings/1788979996344-approver-calibration-github-workflow-file-prs-unde.md).

## The silent strict fallback fails safe — which is why it hid

Two atoms document the same defect from complementary angles: `eval-clauses.py`'s policy resolution ends in a **silent** fallback to the conservative bundled default when the group mount is absent [[the approval policy silently falls back to the STRICT bundled default when its mount is absent — 12/279 runs]](../learnings/1786459972267-approver-clause-gap-the-approval-policy-silently-f.md) [[a fail-safe defect hides behind output that looks like diligence]](../learnings/1786460270909-a-fail-safe-defect-hides-behind-output-that-looks-.md). Two (later three) clauses flip together — `protected_paths` (8 globs → 1), `allow_fork_head` (which fails *every fork-authored PR*, the majority of external contributions), and the caps (a 20× tightening). It is not hypothetical: because each workspace records `policy_version` in `clauses.json`, the history is auditable — 216 `v0-shadow-relaxed`, 51 `v0-shadow-wide`, **12 `v0-shadow`** across 279 workspaces, one PR flipping policy within its own 6-revision chain. The generative insight: **a config whose absence silently changes a verdict is the false-green shape one layer up from the decision** — every clause-level anti-false-green discipline assumes the *policy* is a fixed input, and it isn't. The failure direction is toward ABSTAIN (fails safe), which is precisely why it persists: "an abstain looks like caution," its symptom is indistinguishable from diligence, and nobody goes looking when a system's failure mode produces the output you'd praise. State the direction in any escalation or someone reverses the polarity into failing open; the real fixes are making the fallback *loud* (print the resolved policy path, warn at `eval-clauses.py:283`) and putting the authoritative policy on durable storage (it was observed on ephemeral `/dev/vdb`, so the authoritative copy was the least durable one). Two method notes ride along: dates establish which policy *was current*, only `policy_version` establishes which was *used*; and audit on a **copy** — overwriting `clauses.json` in place destroys the hash the critique gate attested and invalidates the very decision under audit.

## The jq presence trap — a defaulting operator erases the distinction you query

A self-correction sharpens the fallback finding into a reusable instrument rule. The original leaf said `allow_fork_head` was "entirely ABSENT from the bundled default"; ground truth is it's present and explicitly `false` [[correction to the policy-fallback leaf: allow_fork_head is present and explicitly false, NOT absent — jq's // is a falsy-coalesce]](../learnings/1786460459367-approver-clause-gap-correction-to-the-policy-fallb.md). The distinction is load-bearing, not pedantic: "absent" implies *add the key* (which quietly loosens a deliberately strict default — exactly the fail-open the same leaf warned against), while "explicitly false" means the strictness is intentional and the only real defects are the silent fallback and the ephemeral storage. The instrument that erased the distinction was `jq -r '.allow_fork_head // "ABSENT"'` — and **`//` is an alternative/falsy-coalesce operator, not a presence test**: it fires on `false`, on `null`, and on a missing key, collapsing the three states you most need to tell apart for a boolean config key. The genus: any defaulting operator (`//`, `?:`, `get(k, default)`, `getattr(o, k, default)`, `||`) is an instrument that erases the very distinction you're querying — ask *am I testing for PRESENCE or reading a VALUE?* Presence needs `has("k")`; an unambiguous value needs `.k | tojson` (so `false`/`null`/`true` are distinct); ground truth is `grep -n '"k"' file`. The tell the author had and ignored: an **absence claim** is the shape their own standing rules already flag as needing enumeration rather than recall.

## Exit-code and size clauses are mechanical — trace what feeds the new term

Two clause-mechanics atoms. First, `tier_eligible` sums `additions+deletions` across all changed files with **no test-vs-production distinction** — so on slangpy#1101 a test-only +17-line commit that added the coverage CodeRabbit had requested pushed the PR *further over* the 400-line cap, abstaining again [[tier_eligible counts test churn — addressing a "add a test" nit can push a PR OVER the size cap]](../learnings/1786480040703-approver-clause-gap-tier-eligible-counts-test-chur.md). This is correct, expected behavior — a bigger diff is a bigger diff, abstain means "a human must look" (a routing decision, not a penalty), and "the change was an improvement" is not grounds to relax a mechanical predicate. Practical notes: name *why* the size grew so the human isn't misled into thinking the PR got worse; a PR a few lines over with an otherwise-clean signal is a prime quick-approve candidate; excluding test churn is a policy-file change, not an approver judgment. Second, when a PR adds a term to an exit-code or pass/fail predicate, reason about what *feeds* the variables the new term reads, not just the new code: slang#12471's new `!aborted` exit term reads a variable set by the pre-existing `reportTestFailure`, which is driven by a **raw, pre-reclassification** `TestResult::Fail` — so 32 consecutive *expected* failures now red a run with zero unexpected failures, because `runTest()` returns raw `Fail` and the reclassification to `ExpectedFail` happens downstream in the reporter [[expected failures increment the consecutive-failure abort counter — a new !aborted exit term can red a run with zero real failures]](../learnings/1786464323274-approver-clause-gap-expected-failures-increment-th.md). A "the tested path covers it" clearance is wrong when the term is load-bearing on a different, untested path — uncertainty drives ABSTAIN, and the critique gate (DECISION_REVIEW) earned its keep by catching a hand-wave clear.

## A refactor that deletes its own property's only test is green by construction

The class-defining clause-gap: slangpy#1099 made nanothread a private SGL dependency (one shared task pool), passed 12/12 real CI build jobs — and *also deleted the only test that observed the property the PR exists to establish* (`worker_id != 0`), replacing it with a strictly weaker assertion [[a refactor that deletes its own property's only test is green by construction]](../learnings/1786437465551-approver-clause-gap-a-refactor-that-deletes-its-ow.md). For a linkage/signature refactor, green CI is a strong positive control for compile+link but **cannot witness a runtime topology property** (which pool, which thread); when the same diff removes the test that did witness it, CI is green by construction for that property. The mechanical check on every refactor: name the property the PR claims, grep the pre-image and post-image for tests asserting it, and if the count went to zero that's an OPEN_GAP regardless of how green CI is or whether the new code is correct today — the dangerous pattern is a *deleted* test whose mechanism was the API being removed, so it looks like necessary cleanup rather than coverage loss. Corollary on positive controls: record *what* a control covers, not just that one exists ("12/12 green" is a positive control for compile/link and a vacuous one for pool sharing) — write the scope next to the claim.
