## TL;DR

A tight family of front-end bugs around interface requirements that carry defaults, default-method bodies, and synthesized witnesses:

- **Interface-requirement default argument lost at lowering (#12640/#12700).** A 0-arg call on a concrete struct is accepted because overload resolution wins on the interface **requirement** DeclRef (which carries the default), but lowering resolves through the witness to the satisfying **impl** (no default) and reads a null `initExpr` → `SLANG_ASSERT(argExpr)` (Debug ICE, Release silent SIGSEGV). The checker and lowering see **different decls** for the same call. Any fix must close the Release segfault, not just the Debug assert.
- **Two fixes, two layers.** The minimal lowering fix enumerates args from the checker-accepted requirement declRef (pre-`.resolve()`); the principled producer-side fix materializes the default with full This/witness substitution in `CompleteOverloadCandidate` (subsumes the This-dependent-default #12700 case).
- **Do NOT assert equal param counts** between requirement and satisfying method — the core module contains satisfying shapes where counts differ (static-satisfied-by-nonstatic, accessors, synthesized witnesses); the assert crashes the core-module bootstrap. "Alignment guaranteed by conformance" has TWO satisfaction paths (direct signature match + synthesized witness) and must hold on both.
- **A defaulted interface method whose body calls sibling `this` methods** or constructs `This(literal)` crashes at builtin scalars (`_replaceInstUsesWith(null)`); give scalars an explicit forwarding witness. This is the same producer root cause as the inherited-default-method witness bug.
- **`missing-override` E30853 fires for TRANSITIVELY-inherited defaulted requirements** — an `extension`/`struct` satisfying a defaulted requirement from *any* ancestor needs `override`. A core-module `.meta.slang` build-break that "passes tests" is a **stale core-module cache** tell.
- **Synthesized `IDefaultInitializable.$init()` witness visibility** falls to module-default Internal (interface requirements carry visibility implicitly, not as an explicit modifier) → cross-module `-zero-initialize` E30600. Cap the witness by the **conforming TYPE** (= the ctor's return type), NOT `parentDecl` (a `public extension` over an `internal` type over-exposes → E30604).
- **Lambda `this`-capture is silently dropped in interface default methods** — `visitThisExpr`'s `InterfaceDefaultImplDecl` branch omits the `maybeRegisterLambdaCapture` guard the `AggTypeDeclBase` branch has. Validate the fix through IR generic specialization, not just the checker.

## The interface-requirement default-argument crash (#12640 / #12700)

The canonical shape: `interface IFoo { void func(float A = 1.0); } struct Foo : IFoo { void func(float A){...} } Foo f; f.func();` — the checker accepts 0 args, lowering crashes on a null `initExpr` [member call default-arg vs lowering witness-resolve mismatch](../learnings/1787182352078-slang-member-call-on-concrete-struct-interface-req.md). The full chain: member lookup returns both `Foo::func` (Self facet) and `IFoo::func` (interface facet, via a SuperType breadcrumb); there IS a concrete-preference tie-break (`CompareOverloadCandidates` `isInterfaceRequirement`) but it is gated on both candidates being `Applicable`; arity is checked per-candidate *first* (`CountParameters` reads `param->initExpr`), so with 0 args `Foo::func` (1 required, no default) fails arity while `IFoo::func` (default present) passes and wins by status, never reaching the tie-break. The checked InvokeExpr callee is built from `IFoo::func` as a `LookupDeclRef`; at lowering `resolve()` walks the witness table to `Foo::func` and `addDirectCallArgs` reads `getInitExpr(Foo::func param)` = null → assert.

The second atom states the fix precisely: the callee and the default-source are two different declRefs — `addDirectCallArgs` uses its declRef *only* to enumerate params, so enumerate from `resolvedInfo.funcDeclRef` (the checker-accepted requirement, pre-`.resolve()`) instead of the resolved impl; because the requirement is reached via a `LookupDeclRef` carrying the subtype witness, `getInitExpr` substitutes `This`-dependent defaults for free [interface default-arg lost through witness resolution](../learnings/1787185562412-interface-default-arg-lost-through-witness-resolut.md). Also promote the assert to `SLANG_RELEASE_ASSERT` to kill the Release silent path. Test gotchas: `static const` interface requirements must be `int`/`bool` (`static const float` errors E30306), so use `static const int` for a This-dependent-default test.

The third atom generalizes and warns against treating #12700 as a distinct crash: same root cause, both crash identically at `:5180` on a no-fix tree [interface-requirement default-arg crash producer/consumer](../learnings/1787411384320-interface-requirement-default-argument-crash-produ.md). The distinction is forward-looking: a narrow #12640-only lowering fallback fixes the literal case but leaves #12700 broken (a This-dependent default `kDefault` needs This/witness substitution to resolve `kDefault → Foo::kDefault`). The recommended **producer-side** fix substitutes the requirement param's `initExpr` through the concrete call's This-type/witness SubstitutionSet in `CompleteOverloadCandidate` and appends it — subsuming both. Conformance never copies a requirement's default onto the satisfying method's param.

## Do not assert equal param counts; "guaranteed by conformance" has two paths

A peer reviewer's suggestion to `SLANG_ASSERT(reqParams.getCount() == resolvedParams.getCount())` when sourcing defaults from the unresolved requirement vs the resolved concrete method **crashes the core-module bootstrap** — proof the core module contains satisfying shapes where counts differ (static-requirement-satisfied-by-nonstatic wrappers treating the first param as implicit `this`, subscript/accessor forms, synthesized witnesses) [requirement vs satisfying param counts not equal](../learnings/1787558664699-interface-requirement-vs-satisfying-method-param-c.md). Keep positional correspondence as a comment and rely on the existing `argIndex < ...getCount()` bound. The lesson: a "reasonable invariant" from a reviewer must be validated by a full build (core module included) before being asserted — the core module is the strictest stress test.

The companion review atom explains *why* positional alignment holds and how to verify such claims: interface conformance has TWO satisfaction paths — direct signature match (`doesSignatureMatchRequirement`, equal param count + positional types) and synthesized witness (`trySynthesizeMethodRequirementWitness` copies params 1:1 from the *requirement*) — and a "positional alignment guaranteed by conformance" claim must hold on both [alignment guaranteed by one path when two exist](../learnings/1787413809758-alignment-guaranteed-by-one-path-when-two-conforma.md). A correctness reviewer citing only path 1 while a clarity reviewer flags the missing path 2 is the pattern; neither is a proven bug, but the legitimate nit is to make the invariant precise and `SLANG_ASSERT` the count *when the default source is set*, so a future conformance-model change fails at the owning layer, not two frames deeper as a null-deref.

## Default-method bodies crash at scalars; the transitive override rule

A DEFAULTED interface method whose body constructs `This(1.0)` and operates on it (e.g. `IFloatingPoint.rcp() { return This(1.0).div(this); }`) crashes `slang-ir.cpp:9064` (null `other` in `_replaceInstUsesWith`) when specialized at a builtin **scalar** [defaulted interface method with This(literal) crashes at scalar](../learnings/1788386927002-slang-defaulted-interface-method-with-this-literal.md). Bisected: the identical expression inline in a generic function compiles fine — only the default-method path crashes; vector/matrix conformers are unaffected because `This(1.0)` splats into a real construction, whereas for a scalar it degenerates to an identity that default-method specialization mishandles. Workaround: give builtin scalars an explicit forwarding witness (`override This rcp() { return rcp(this); }`). This is the same producer/default-method-witness family as the inherited-default-method crash (cross-reference the interfaces/witness page); the underlying scalar specialization bug remains for user-defined scalar-like conformers.

`missing-override` E30853 fires when an `extension`/`struct` redefines a defaulted interface requirement without `override`, even when the default body lives on a *transitive* ancestor interface [missing-override E30853 fires transitively](../learnings/1788385185036-missing-override-e30853-fires-for-transitively-inh.md). In #12890 this was `matrix<T,R,C,L> : IReal` overriding `IFloatingPoint.rcp()`'s default without `override` — a HARD compile error in `hlsl.meta.slang` that breaks the shared core module for *every* backend. Cheap decisive verification: write a synthetic structural mirror of the conformance shape and compile it against prebuilt master `slangc` (~1 min, no core-module regen). A build-breaking `.meta.slang` change that reportedly "passes tests 261/261" is a red flag for a **stale core-module cache** — the documented CLAUDE.md footgun (`cmake -E touch` + `generate_core_module_headers` before rebuilding `slangc`). Rule of thumb: if a reviewer's build-breaker contradicts a green test run on a `.meta.slang` change, suspect the cache.

## Witness-swap discrimination tests

When an interface conformance forwards each requirement to a free math function, the realistic bug class is a **copy-paste witness swap** (`exp` wired to `log`) or a no-op/identity witness — and a regression test only guards against it if a swap/no-op changes the observed output [witness-swap discrimination tests](../learnings/1788388670959-witness-swap-discrimination-tests-avoid-self-cance.md). Several natural inputs fail to discriminate: `exp(log(x)) == x` is invariant under swapping the two *and* under making both identity; sum-invariant `saturate` inputs cancel; odd/zero-crossing functions at 0 (`sin(0)+tan(0)=0`) hold for any `f(0)=0`. Test each in isolation with distinct expected values (`applyExp(0)→1`, `applyLog(1)→0`). Separately, a `matrix` `rcp()` override that replaces the broad default with row-by-row reciprocal produces the same numeric result on `-cpu`, so its only real guard is a compile-only cross-target test (`-target metal`/`-target wgsl`) asserting the *specific bad lowering is absent* (`METAL-NOT:` on the matrix-division form), not merely that `computeMain` appears. Reflection framing note: renaming a public interface with a back-compat `typealias` is source/ABI-safe, but reflection resolves the alias and reports the **canonical** name, so `getTypeFullName()`-string consumers matching the old name silently stop — frame it as a maintainer label decision, not a code defect.

## Synthesized IDefaultInitializable witness visibility

Under `-zero-initialize`, a module embedding a field of a `public` struct (from another module, conforming to an interface) fails with spurious `E30600 declaration not accessible` [synthesized $init witness gets Internal visibility](../learnings/1788747672994-slang-synthesized-idefaultinitializable-init-witne.md). Mechanism: `-zero-initialize` force-adds `IDefaultInitializable` inside the per-base inheritance loop (a struct with no base clause never enters it — which is why removing the interface conformance makes the bug vanish); if the struct has an explicit value ctor, `_synthesizeCtorSignature` early-returns so the only zero-arg ctor is the `IDefaultInitializable.$init()` requirement-witness; that witness's visibility is set by `addModifiersToSynthesizedDecl` only when the requirement carries an explicit `VisibilityModifier`, but interface requirements carry visibility *implicitly*, so the witness falls back to module-default = Internal → cross-module E30600. Minimal fix: inside `trySynthesizeConstructorRequirementWitness`'s `isDefaultInitializableType` block, set visibility to `Min(getDeclVisibility(parentDecl), getDeclVisibility(requirement))`. Two gotchas the reviewer caught: the generic witness-synthesis path sets `parentDecl` to a placeholder GenericDecl whose null-inner `getDeclVisibility` returns Public (over-promotes), and promoting a witness whose signature references a lower-visibility type triggers E30604 — constructors are safe only because `$init()` is parameterless and returns the conforming type. Also: a bare `module X;` resolves to language version 2025, so `getDeclVisibility` uses `defaultVisibility` (Internal), not the legacy→Public path.

The review of that very fix (#12921) corrects the cap: capping at `getDeclVisibility(context->parentDecl)` is WRONG because `parentDecl` may be an `ExtensionDecl` whose own visibility is not capped to the extended type's — a `public extension Foo : IDefaultInitializable {}` over an `internal struct Foo` makes `parentDecl` public, so `Min` collapses to the extension's visibility and the parameterless `$init()` (return type = extended type) becomes public while its return type stays internal → NEW spurious E30604 [cap by conformingType, not parentDecl](../learnings/1788756424590-synthesized-idefaultinitializable-witness-visibili.md). Correct fix: cap by the conforming TYPE (`getTypeVisibility(context->conformingType)`), which equals the ctor's return type for both direct and extension conformance and can never over-expose. Meta-lessons: three reviewers converged (correctness + clarity independently found it; Devin "clean" merely echoed the PR description = non-informative); and the PR body/handoff claimed a restriction and a test file that were absent from the pushed head — always diff the actual head against the described change.

## Lambda `this`-capture in interface default methods

Capturing `this` in a lambda inside an interface **default method** fails semantic check with cryptic `E30019`/`E30011` ("expected typeof(..._slang_Lambda_...), got 'This'") — the same lambda in a normal struct method works, and local-only capture in a default method works [lambda this-capture broken in default methods](../learnings/1788769686058-lambda-this-capture-broken-in-interface-default-me.md). Root cause: `SemanticsExprVisitor::visitThisExpr` walks the scope chain; the `AggTypeDeclBase` branch does `if (m_parentLambdaExpr) return maybeRegisterLambdaCapture(expr)`, but the `InterfaceDefaultImplDecl` branch just sets the type and returns — no capture registration. The second atom pins that this is the *sole* registration site for `this` (member-call bases bypass `CheckExpr`), so its absence is the whole bug, and adds the **load-bearing validation gate**: the synthesized `LambdaDecl` closure struct is NOT generic over `This`, whereas an `InterfaceDefaultImplDecl` body lowers into a generic function parameterized on `This`, so whether a `This`-typed capture field survives IR generic lowering is not answerable by static reading — you must build with the fix and run the repro (`-target cpp`, expect `42`) [lambda this-capture visitThisExpr branch asymmetry](../learnings/1788770320317-lambda-this-capture-broken-in-interface-default-me.md). General lesson: an AST-level capture fix for an entity whose type is a generic parameter of an enclosing desugared-to-generic decl must be validated through IR generic specialization.
