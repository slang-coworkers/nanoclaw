## TL;DR

Cross-agent coordination lessons: how to treat a peer's correction, an a2a bounce, a subagent's report, an outward-facing action, a recurring trigger, and a held GitHub chain. The unifying rule is that a message (from a peer, a hook, or a subagent) is a claim about state, not the state — verify against ground truth (live main, the real binary, the GitHub issue) before acting.

- **A peer's "correction" can be a stale checkout, not your error** — if the peer's line numbers are *smaller* than yours, their tree is *shorter* → they're behind. Resolve against LIVE main (`git rev-parse HEAD` vs `origin/main` vs `gh api`) before conceding; don't let an honest firsthand read of an old tree overturn your read of a current one.
- **Verify a capability in the peer's ACTUAL environment before asserting it** — skills and their embedded tools drift across agent groups; "feature X already exists in your tree, your tool is just stale" based on YOUR version is a version-skew trap. Cite a concrete version marker; a peer-delivered skill file is not a sanctioned self-mod channel.
- **An a2a `bounced-unknown` can be a broken ROUTE, not a dead recipient** — stop at two re-drives, escalate so a parent can dispatch the same handoff from a *different edge* on the canonical thread, and don't downgrade the review leg on your own authority.
- **A build subagent that returns a narrated plan is not a completed build** — gate on the artifact (`ls ./build/.../slang-test`), not the subagent's prose "result." A subagent can stop without doing the work; prefer a detached build + a Monitor on the log.
- **Dispatch long background jobs directly, never `nohup ... &` inside `run_in_background`** — the trailing `&` detaches the real process and the wrapper exits 0 instantly, firing a false completion notification. `run_in_background` is not bound by the 2-min foreground timeout.
- **Outward-action guardrails must ride the INITIAL dispatch** — a typed coworker's first turn often already posts to GitHub / @-mentions a human; a follow-up guardrail only binds future turns, and editing a comment does not un-send a notification. Predict the outward step from the issue shape and gate it up front.
- **A one-shot time-gated nudge needs a durable "already-fired" latch** — the action's own side effect (your comment) rarely satisfies the gate's cancel conditions, so it re-fires every sweep. Live re-verification is necessary but not sufficient; pair the trigger with a durable spent-state flag it checks.
- **Verify GitHub state before posting a triage resolution** — a maintainer may have closed the issue while your chain waited; GitHub is the system of record, edges are not.
- **When report-ups bounce on a held chain, post the disposition ON GitHub** — the supervisor's signal is observable GitHub state, not your bounced upstream messages; a silent hold looks identical to a dropped chain from the outside.

## Peers, routes, and capability claims

Three atoms treat a peer's message as a claim to verify. [A peer's correction can be a stale checkout](../learnings/1787227106706-a-peer-s-correction-can-be-a-stale-checkout-not-yo.md): when a peer claims a function/flag doesn't exist or gives smaller line numbers, resolve against LIVE main first — a peer weeks behind origin/main gives an honest firsthand read of an old tree that contradicts your current one. The discriminator that settles it: smaller line numbers ⇒ shorter tree ⇒ they're behind; confirm with `git rev-parse` across HEAD/origin/main/`gh api` and date the disputed token with `git log -S`. [Verify a capability in the peer's ACTUAL environment](../learnings/1788238641032-verify-a-capability-in-a-peer-s-actual-environment.md) extends "verify before relaying as fact" to capabilities: telling a peer "feature X already exists in your tree" based on your own installed skill version is a version-skew trap (a 522-line tool with the feature vs their 403-line one without); cite a concrete version marker (file mtime, line count, a signature grep) and route cross-group skew to the operator, since a peer-delivered skill file is not a sanctioned self-mod channel. And [an a2a `bounced-unknown` can be a broken route, not a dead recipient](../learnings/1787266017501-a2a-bounced-unknown-can-be-a-broken-route-not-a-de.md): a redrive notice names the message+target but not whether the recipient or the edge failed; stop at two re-drives, escalate so a parent can route around the broken edge from a different one on the canonical thread, and don't substitute the codex critique for the peer-review leg on your own authority.

## Subagent and background-job control

Two atoms guard against a subagent's report being mistaken for completion. [A build subagent that returns a narrated plan is not a completed build](../learnings/1787331423750-a-build-subagent-that-returns-a-narrated-plan-is-n.md): a stop-notification whose text describes what it *will* do (a test plan) rather than what it *did* (exit codes, PASS/FAIL, binary path) means the task was NOT run — verify `ls ./build/Debug/bin/slang-test` before believing it (the artifact is proof, not the prose), and prefer a detached build + a Monitor gated on both `BINARY_OK` and every failure signature. (The same atom notes a fresh `git worktree add` does not populate submodules — run `git submodule update --init --recursive` first.) Relatedly, [dispatch long background jobs directly, never via `nohup ... &`](../learnings/1788280727625-dispatch-long-background-jobs-directly-never-via-n.md): the trailing `&` detaches the real process and the backgrounded shell returns exit 0 instantly, so the harness fires a completion notification for the instant-exiting wrapper (observed: "completed" in a second while the real review ran ~24 min). Invoke the script directly under `run_in_background` (not bound by the 2-min foreground timeout); if already detached, capture the run_dir and arm a Monitor with an `until` loop keyed on the terminal marker plus crash markers.

## Guardrails, one-shot triggers, and GitHub as system of record

[Outward-action guardrails must ride the initial dispatch](../learnings/1788165792149-outward-action-guardrails-must-ride-the-initial-di.md): a typed coworker's first turn often already performs the irreversible outward action (posting to GitHub, @-mentioning a maintainer, opening a PR from someone's branch), and a follow-up guardrail only constrains future turns — editing/deleting the comment does not un-send the notification. Predict the hard-to-reverse step from the issue shape (existing-fix-on-a-personal-branch, "coordinate with maintainer") and put the gate in the initial dispatch. Similarly, [a one-shot time-gated nudge needs a durable "already-fired" latch](../learnings/1788102208361-a-one-shot-time-gated-nudge-needs-a-durable-alread.md): the action's own side effect (your follow-up comment) is a different kind of object than what the gate reads, so it satisfies no cancel condition and re-fires every sweep — "re-verify live before posting" confirms the data state but can't see its own past firing; add a durable spent-state flag as an extra conjunct (an idempotency/"sent" bit).

GitHub is the ground truth two atoms defer to. [Verify GitHub state before posting a triage resolution](../learnings/1788159643469-verify-github-state-before-posting-a-triage-resolu.md): when a fixer's report and a parent's directive contradict, `gh api` the issue state + cited PR yourself — one call revealed an issue auto-closed 4 days earlier by a merged maintainer PR, so acting on the parent's stale premise would have posted a wrong resolution and triggered a wrong maintainer ping. A long-running fixer chain drifts while upstream maintainers resolve independently; re-check at every state change. And [when report-ups bounce on a held chain, post the disposition ON GitHub](../learnings/1788226544723-held-github-chains-when-report-ups-bounce-post-the.md): the supervisor keys on observable GitHub state, not your bounced upstream messages, so re-sending upstream doesn't clear the stuck-flag — make the hold observable with a fresh incremental issue comment (delta only, don't re-ping maintainers a human already pinged), since a silent hold looks identical to a dropped chain from the outside.
