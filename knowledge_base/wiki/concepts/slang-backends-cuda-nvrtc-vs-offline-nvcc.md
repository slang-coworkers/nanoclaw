# Slang CUDA output: NVRTC vs an offline nvcc build

The CUDA source Slang emits has two consumers. Slang's own NVRTC call compiles it for `-target ptx`, for the runtime and for every slang-test CUDA lane (the prelude sees `SLANG_CUDA_RTC=1`). A user who asks for `-target cuda` compiles it later with their own nvcc. Several inputs reach only the NVRTC path: forwarded `-D` defines, the feature-enable macros, `--fmad=false`, and the `SLANG_CUDA_RTC` prelude branches. So a CUDA change can pass every slang-test lane and still break offline nvcc, or the reverse. This page records which inputs differ and how to check each path. The prelude's OptiX version gating and NVRTC `-pch` are on [[wiki/concepts/slang-backends-f0909b0-cuda-optix.md]], and the GPU-free ways to test a patched prelude are on [[wiki/concepts/slang-backends-cuda-ptx-surface-asm-verification.md]].

## TL;DR

- **Check both paths.** `-target ptx` runs NVRTC; `-target cuda` followed by your own `nvcc` is the offline path. Neither one proves the other.
- **Every Slang macro define is forwarded to every downstream compiler that takes defines**, not only in pass-through mode: `slangc -D` and `SessionDesc::preprocessorMacros` reach NVRTC, gcc/clang, MSVC, FXC, Metal and slang-llvm (which drops the value). DXC, glslang, Tint and direct SPIR-V get none. Removing this is a breaking change (#14015), because prelude macros rely on it.
- **Sentinel for "which compiler sees my defines":** `-Doutput_0=)(`. The name exists only in emitted code, so Slang's own preprocessor never expands it; ptx and shader-sharedlib fail, dxil and spirv pass.
- **NVRTC's implicit builtin header reads command-line defines:** `-D_WIN32=1` breaks it (`CUDART_CB` becomes `__stdcall`), while the same `#define` placed in the `.cu` before the prelude compiles fine.
- **`SLANG_CUDA_ENABLE_HALF/BF16/FP8` reach NVRTC only as `-D` flags**, so `-target cuda` + plain nvcc fails on half code (#14037). `emitFrontMatterImpl` runs after `emitModule`, so it can read the finished extension tracker and write `#ifndef`-guarded defines ahead of the prelude include.
- **Anything written ahead of the prelude `#include` turns off NVRTC `-pch`**, because Slang requests `-pch` only when the source starts with `#include`. NVRTC itself would still precompile through leading directives; Slang's check is the strict part.
- **`SLANG_CUDA_RTC` prelude branches compile only under NVRTC; non-RTC branches compile only under offline nvcc.** slang-test exercises the non-RTC branch only through the `ci-slang-test.yml` nvcc fixture, which enables HALF, BF16 and FP8 together. Check single-type configurations by hand.
- **The prelude's RTC `intptr_t`/`uintptr_t` typedefs clash with CCCL** (`cooperative_groups.h` and any `cuda/std` header), so such a kernel fails on `-target ptx` but passes with nvcc: an nvcc-only check is a false PASS.
- **Guard sm_70-only prelude overloads with `!defined(__CUDA_ARCH__) || __CUDA_ARCH__ >= 700`**; the `defined(__CUDA_ARCH__) && ...` form hides them from nvcc's host pass.
- **nvcc ignores every `FP_CONTRACT` pragma.** Only `__fadd_rn`/`__fmul_rn` (and the f64, f16 and half2 `_rn` families) keep a multiply and an add unfused in source. `-fp-mode precise` already passes `--fmad=false` to NVRTC, so only offline-nvcc users of `-target cuda` see contraction.
- **On CUDA, Slang `fma()` and `mad()` both lower to `F32_fma` → `::fmaf`**, which stays fused even under `--fmad=false`.

## Macro defines are forwarded to downstream compilers

Since #2263 (2022), `source/slang/slang-code-gen.cpp:551-565` copies every Slang `MacroDefine` (from `slangc -D` or `SessionDesc::preprocessorMacros`) into `DownstreamCompileOptions::defines` on every downstream compile, not only in pass-through mode, so Slang-emitted code is preprocessed a second time with the user's macros. The consumers are NVRTC, gcc/clang, MSVC, FXC, Metal and slang-llvm (which drops the value). DXC is called with `nullptr, 0` defines, and glslang, Tint and direct SPIR-V take none. To see which compiler gets them, pass `-Doutput_0=)(`: `output_0` exists only in emitted code, so Slang's own preprocessor never touches it, and the build breaks exactly where the define is forwarded (ptx and shader-sharedlib fail, dxil and spirv pass) [Slang -D macros reach NVRTC/C++ host/FXC/Metal but not DXC/glslang — sentinel test](../learnings/1793278502436-slang-d-macros-reach-nvrtc-c-host-fxc-metal-but-no.md).

On NVRTC, forwarded defines also reach the implicit `__nv_nvrtc_builtin_header.h`, which reads command-line defines only. `-D_WIN32=1` makes `CUDART_CB` expand to `__stdcall` and breaks that header, while the same `#define` written into the generated `.cu` before the prelude compiles fine. The forwarding is documented and relied on for prelude macros (`docs/cpu-target.md:627`, `slang-cuda-prelude.h:21-24`, `tests/compute/bound-check-zero-index.slang`), so removing it is a breaking change (#14015) [Slang -D macros reach NVRTC/C++ host/FXC/Metal but not DXC/glslang — sentinel test](../learnings/1793278502436-slang-d-macros-reach-nvrtc-c-host-fxc-metal-but-no.md).

## Feature-enable macros and CUDA front matter

The prelude's half, bfloat16 and fp8 support sits behind `SLANG_CUDA_ENABLE_HALF`, `SLANG_CUDA_ENABLE_BF16` and `SLANG_CUDA_ENABLE_FP8`. Slang decides them from the module's type use, but today it passes them only to NVRTC, as `-D` flags (`slang-code-gen.cpp:586-597` → `slang-nvrtc-compiler.cpp`). `-target cuda` output compiled with plain nvcc therefore fails on half code (#14037), although `docs/cuda-target.md:263` already promises that Slang defines HALF. The emitted source can carry the defines itself. In `emitEntryPointsSourceFromIR` (`slang-emit.cpp` ~:3121 vs :3155), `emitModule` runs before `emitFrontMatter` and the prelude, and the body string is appended afterwards, so `CUDASourceEmitter::emitFrontMatterImpl` can read the completed `m_extensionTracker` and write `#define SLANG_CUDA_ENABLE_HALF 1` and its siblings ahead of the prelude include. A `#define X 1` plus `-DX` is an identical redefinition, and nvcc does not warn about it [CUDA source front matter can read the extension tracker; ncl tasks create may time out yet succeed](../learnings/1793295336959-cuda-source-front-matter-can-read-the-extension-tr.md).

Front matter has a cost on NVRTC 12.8+: Slang requests `-pch` only when the emitted source `trimStart().startsWith("#include")`, so any define written ahead of the prelude include, including `SLANG_CUDA_ENABLE_FAST_MATH` under `-fp-mode fast` (PR #12872) and the #14037 enable macros, silently drops `-pch` for that module, although NVRTC itself would precompile through leading directives. The gate and the proposed follow-up are on [[wiki/concepts/slang-backends-f0909b0-cuda-optix.md]] [CUDA front-matter defines turn off NVRTC -pch on -target ptx](../learnings/1793299799398-cuda-front-matter-defines-turn-off-nvrtc-pch-on-ta.md).

## Prelude branches that only one path compiles

slang-test reaches CUDA only through NVRTC (`SLANG_CUDA_RTC=1`), so prelude code on the non-RTC branch is compiled in CI only by the `ci-slang-test.yml` nvcc fixture (`tests/cuda/cuda-prelude-vec1-make.cu`). That fixture defines HALF, BF16 and FP8 together, so check single-type configurations by hand with `nvcc -cubin -arch=sm_89 -I prelude` [CUDA front-matter defines turn off NVRTC -pch on -target ptx](../learnings/1793299799398-cuda-front-matter-defines-turn-off-nvrtc-pch-on-ta.md). The same split decides how an architecture guard must be written. nvcc compiles a `.cu` twice, once for the host with `__CUDA_ARCH__` undefined, so an sm_70-only overload such as 16-bit `atomicCAS` must be guarded with `!defined(__CUDA_ARCH__) || __CUDA_ARCH__ >= 700` (the form of CUDA's own `sm_70_rt.h`); with `defined(__CUDA_ARCH__) && ...` the host pass cannot see the overload and offline nvcc fails with "no instance of overloaded function" [CUDA float atomic CAS loop: write the operand's own bits, not fminf's result; guard 16-bit atomicCAS with !defined(__CUDA_ARCH__) || >= 700](../learnings/1793302322805-cuda-float-atomic-cas-loop-write-the-operand-s-own.md). The float-atomic context is on [[wiki/concepts/slang-backends-float-atomic-min-max.md]].

The RTC branch fails in the opposite direction. At master 9b3ac252d with NVRTC 12.6.85, `prelude/slang-cuda-prelude.h:291` and `:297` declare `typedef ptrdiff_t intptr_t;` and `typedef size_t uintptr_t;` under `SLANG_CUDA_RTC`, and CCCL's `cuda/std/__cuda/cstdint_prelude.h:48-49` (CCCL 2.5, 2.7 and 2.8) declares them as `int64_t`/`uint64_t`. Any Slang CUDA kernel that pulls in a CCCL header, for example through `__requirePrelude("#include <cooperative_groups.h>")`, fails `-target ptx` with "invalid redeclaration of type name intptr_t", while `-target cuda` followed by nvcc succeeds, so an nvcc-only check gives a false PASS. An A/B through NVRTC directly (ctypes on `libnvrtc`) proved the cause: with the two typedefs aligned to `int64_t`/`uint64_t` the build has 0 errors, and a control without `cooperative_groups.h` compiles either way. This blocks grid-wide sync via `this_grid().sync()` (#14029) and any future CUDA intrinsic that includes a CCCL header. To A/B a prelude edit on NVRTC, rewrite the generated `.cu`'s absolute-path `#include` to a relative name and pass `-I<dir>` [Slang CUDA prelude intptr_t typedefs break any CCCL header (e.g. cooperative_groups.h) on NVRTC 12.6](../learnings/1793291460496-slang-cuda-prelude-intptr-t-typedefs-break-any-ccc.md).

## FP contraction: NVRTC gets `--fmad=false`, offline nvcc does not

Verified with CUDA 12.6 nvcc `-arch=sm_89 -ptx` while triaging #14036: `#pragma STDC FP_CONTRACT OFF`, `#pragma fp_contract(off)` and `#pragma clang fp contract(off)` are all silently ignored, and `a*b+c` still becomes `fma.rn.f32`. `__fadd_rn(__fmul_rn(a,b),c)` stays `mul.rn` + `add.rn` even under the default `--fmad=true`, and `fmaf()` stays `fma.rn` even under `--fmad=false`. So a Slang CUDA source fix for `-fp-mode precise` or the `precise` qualifier has to emit the `_rn` intrinsics, not a pragma; they exist for f32 (`__fadd_rn`/`__fsub_rn`/`__fmul_rn`), f64 (`__dadd_rn`...), f16 (`__hadd_rn`...) and half2 (`__hadd2_rn`...). Slang's own `-target ptx -fp-mode precise` path already passes `--fmad=false` to NVRTC (PR #12801, `slang-nvrtc-compiler.cpp:1250`), so only offline-nvcc users of `-target cuda` output are exposed. On CUDA, Slang's `fma()` and `mad()` both lower to `F32_fma` → `::fmaf` [nvcc ignores FP_CONTRACT pragmas; __fadd_rn/__fmul_rn are the only source-level anti-FMA lever](../learnings/1793294457044-nvcc-ignores-fp-contract-pragmas-fadd-rn-fmul-rn-a.md). The SPIR-V side of `precise` is on [[wiki/concepts/slang-backends-spirv-precise-and-nocontraction.md]].
