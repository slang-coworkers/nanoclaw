# SlangPy Crashing Tests, Native-SIGSEGV Testing, and sgl_tests / CI Flake

How deliberately-crashing tests interact with Crashpad and wedge CI, the pattern for regression-testing a native SIGSEGV under pytest, GFX-pipeline test flake, the `sgl_tests` teardown exit-code flake (#1062) and its CI-hang corrections, and the profiler `drain()`/`flush()` ordering work (#1072 / PR #1073). Includes the incremental fold of 2026-07-17.

## TL;DR
- **A test that deliberately crashes (SIGSEGV/SIGABRT) HANGS the "Unit Tests (Python)" step for hours** because Crashpad intercepts it to capture a minidump, while passing locally where crashpad is off — "passes locally, hangs in CI" is the signature. Hard-guard on the CI env: `if spy.crashpad.is_supported(): pytest.skip(...)`.
- **The pattern to regression-test a native SIGSEGV under pytest**: run the crashing call in an ISOLATED SUBPROCESS (test file doubles as worker via `os._exit(_child_main(...))`), assert on the NEGATIVE returncode (`-signal.SIGSEGV == -11`), use TARGETED `@pytest.mark.xfail(raises=..., strict=True)` so a landed fix becomes an XPASS hard-failure, bracket the crash with FLUSHED phase prints, gate to POSIX.
- **A single-test Python failure on ONE backend (e.g. `test_tensor_interfaces[d3d12]`) where other backends of that test pass + it's green on the PR base + your change is backend-agnostic is flaky CI** — matrix-vector grad tests are maintainer-documented unreliable on GFX pipelines. Report, don't hunt.
- **The `sgl_tests` teardown exit-code flake (#1062) is a distinct class**: doctest prints `[doctest] Status: SUCCESS!` then the process exits nonzero during post-`main` teardown (GPU-resource destruction), which `tools/ci.py` turns into a `RuntimeError` reddening the cross-repo *SlangPy Tests* check on unrelated slang PRs.
- **Crashpad is NOT armed in the C++ `sgl_tests` binary — an empty `.crashpad/reports/` says nothing about fault location**; the `_Exit(result)` candidate fix suppresses the (CI-disabled, non-blocking) LeakSanitizer report, and the maintainer REJECTED exit-code masking — a teardown flake needs a root-cause fix.
- **A deliberately-crashing GPU test lands in an unkillable D-state process** — hard-guard on the CI env, don't probe crashpad; the separate slangpy#1051/#1053 6-hour hang was ultimately the known **CUDA-OOM cascade** from `pytest -n auto` opening 4 concurrent GPU contexts, NOT the crash-test.
- **PR #1063 also carried a `ProfilerImpl::drain()` snapshot-ordering race (#1072)** (thread-count-independent); the #1072 fix (PR #1073) reorders the two snapshots and rests on a happens-before argument — its regression guards are probabilistic, not deterministic.
- **The reorder does NOT make `flush()` deterministic — the barrier covers only 1 of the collector's 3 input channels** (per-thread rings; not `sealed_frame_events` / `pending_gpu_results`).
- **SlangPy macOS wheels link via nanobind's curated symbol allow-list, not libpython** — a LINK-time `Undefined symbols ... "_PySomething"` is almost always a CPython C-API symbol missing from that allow-list, NOT a missing libpython link.

## Crashing Regression Tests, Native-SIGSEGV Testing & CI Flake (2026-07-13 fold)

**A deliberately-crashing test hangs CI even when it passes locally.** If a SlangPy Python test intentionally triggers a native crash (SIGSEGV/SIGABRT) — e.g. a regression tripwire for a known-crashing GPU path — it will HANG the "Unit Tests (Python)" CI step for hours (2h+ linux/windows, 6h macOS), not crash cleanly. SlangPy's CI unit-test lanes build with the `crashpad` flag and `slangpy/testing/plugin.py` starts the Crashpad handler at `pytest_sessionstart` (gated on `spy.crashpad.is_supported()`); Crashpad intercepts the crash to capture a minidump and wedges the run. It does NOT reproduce on a local dev build where crashpad is disabled — so "passes locally, hangs in CI" is the signature. Diagnosis tell: Build + C++ tests pass, only "Unit Tests (Python)" is stuck `in_progress` with a multi-hour duration. Fix: guard the test with `if spy.crashpad.is_supported(): pytest.skip(...)` so it only runs on non-Crashpad builds; keep non-crashing controls always-on. Subprocess isolation stops a SIGSEGV from killing the pytest worker but does NOT stop a process-level crash handler from intercepting it ([a test that deliberately crashes (SIGSEGV) hangs SlangPy CI because Crashpad intercepts it](../learnings/1783909321657-a-test-that-deliberately-crashes-sigsegv-hangs-sla.md)).

**The pattern to regression-test a native SIGSEGV under pytest** (used for slangpy#1051 / slang#12070, `test_diff_loop_runtime_start.py`): run the crashing call in an ISOLATED SUBPROCESS (the test file doubles as the worker via `if __name__ == "__main__": os._exit(_child_main(...))`; `os._exit` avoids teardown perturbing the exit code); the parent asserts on returncode (a signal death is a NEGATIVE returncode, `-signal.SIGSEGV == -11`, not shell 139); use TARGETED `@pytest.mark.xfail(raises=_KnownCrash, strict=True)` so a clean exit (fix landed) becomes an XPASS hard-failure forcing marker removal; bracket the crash with FLUSHED `PHASE:begin`/`PHASE:end` prints so a crash in setup/teardown is surfaced not masked; compute the "fixed but wrong" oracle in numpy with a NON-SQUARE shape; gate to POSIX. A SIGSEGV discards block-buffered stdout — capture generated shaders with `python -u` or `SLANGPY_PRINT_GENERATED_SHADERS=1` ([regression-testing a native SIGSEGV under pytest (subprocess + strict xfail + phase bracket)](../learnings/1783875908806-regression-testing-a-native-sigsegv-under-pytest-s.md)).

**Matrix-vector grad tests flake on GFX pipelines.** `test_pytorch.py::test_tensor_interfaces[DeviceType.d3d12]` fails intermittently in Windows CI (`AssertionError: Tensor deviates by <large N>`) while 5120+ tests pass and the build succeeds — it is flaky, not a real regression. Confirm fast: the same test's `[cuda]`/`[vulkan]` variants PASS in the same run, and the sibling `test_tensor_arguments` (same helper, same grad assertion) is explicitly `pytest.skip("Test currently unreliable on GFX pipelines")` — maintainer-documented unreliability. `nv-slang-bot` CANNOT `gh run rerun --failed` (`Must have admin rights`), so a human must re-run or push a no-op. Triage rule: a single-test Python failure on ONE backend, where other backends of that test pass + it's green on the PR base + your change is backend-agnostic, is flaky CI — report, don't hunt ([slangpy CI: test_tensor_interfaces[d3d12] and matrix-vector grad tests are flaky on GFX pipelines](../learnings/1783887861915-slangpy-ci-test-tensor-interfaces-d3d12-and-matrix.md)).


## sgl_tests Teardown Exit-Code Flake and CI-Hang Corrections (2026-07-14 fold)

The `sgl_tests` teardown exit-code flake (#1062) is a distinct class: doctest prints a green `[doctest] Status: SUCCESS!` then the *process* exits nonzero during post-`main` teardown (`static_shutdown`/`close_all_devices` GPU-resource destruction), which `tools/ci.py`'s `run_command` turns into a `RuntimeError` reddening the cross-repo *SlangPy Tests* check on unrelated slang PRs ([sgl_tests exit-code flake root cause + tracking issue #1062](../learnings/1783930954720-sgl-tests-exit-code-flake-root-cause-tracking-issu.md)). The candidate fix is `std::fflush(nullptr); std::_Exit(result)` to bypass teardown ([#1062: no minidump, post-main teardown, fix with std::_Exit](../learnings/1783932346816-sgl-tests-exit-code-flake-1062-no-minidump-exists-.md)), but two evidence legs need correcting: crashpad is neither producing a minidump NOR armed in the C++ binary, so an empty `.crashpad/reports/` says nothing about fault location ([CORRECTION: crashpad is not armed; empty reports/ uninformative](../learnings/1783932949420-correction-to-1062-learning-crashpad-is-not-armed-.md)), and `_Exit` suppresses the (CI-disabled, non-blocking) LeakSanitizer end-of-run report ([_Exit fix #1064 suppresses LeakSanitizer report](../learnings/1783932699675-sgl-tests-exit-fix-1064-suppresses-leaksanitizer-e.md)). Maintainer @skallweitNV **rejected exit-code masking** — a teardown flake needs a root-cause fix, not `_Exit(result)` ([maintainer rejected exit-code masking](../learnings/1783937217747-sgl-tests-exit-code-flake-maintainer-rejected-exit.md)). Two related CI-hang corrections: a deliberately-crashing GPU test lands in an unkillable D-state process, so hard-guard on the CI env instead of probing crashpad ([CORRECTION: crashing GPU test wedges CI (unkillable)](../learnings/1783931282447-correction-a-deliberately-crashing-gpu-test-wedges.md)); and the separate slangpy#1051/#1053 6-hour hang was ultimately the known **CUDA-OOM cascade** from `pytest -n auto` opening 4 concurrent GPU contexts, NOT the crash-test ([CORRECTION #2: 6h hang was CUDA-OOM cascade](../learnings/1783974986070-correction-2-slangpy-1051-pr-1053-the-6h-ci-hang-w.md)). The same PR #1063 (self-merged, CodeRabbit Major findings unresolved) also carried a `ProfilerImpl::drain()` snapshot-ordering race (#1072): the async collector snapshotted the per-thread CPU event queues BEFORE `sealed_frame_events` under separate mutex scopes, so a producer could publish a zone and seal its frame in the unlocked window → the marker was consumed ahead of its zone and the frame finalized with zones missing — thread-count-INDEPENDENT (both the macOS cross-thread and Windows single-thread GPU tests fail on it) [SlangPy profiler PR #1063 also had a drain() snapshot-ordering race (#1072)](../learnings/1784869755509-slangpy-profiler-pr-1063-also-had-a-drain-snapshot.md). The #1072 fix (PR #1073, +14/−5) reorders the two snapshots — `sealed_frame_events` under `sealed_frame_mutex` FIRST, then acquire-load `write_index` — and its soundness rests on a C++ happens-before / release-sequence argument (the acq-rel RMW chain on `global_frame` synchronizes each zone-releaser with the sealer); the two cited regression guards PRE-EXIST on main and are probabilistic (they only catch #1072 if the collector drains in the exact race window), so a green run corroborates but does not prove — the memory-model argument is the real proof and the PR added NO deterministic test (verdict: APPROVE_WITH_NITS, nit = coverage) [SGL profiler drain() #1072 fix — snapshot reorder + why its guard tests are probabilistic](../learnings/1784870556172-sgl-profiler-drain-1072-fix-snapshot-reorder-why-i.md).

**And the reorder does NOT make `flush()` deterministic — a separate barrier gap covers only 1 of the collector's 3 input channels.** `Profiler::flush()` documents (`src/sgl/utils/profiler.h:476`) that it blocks "until the collector consumes events published before this call and publishes both snapshot products," but the implementation snapshots watermarks only from each thread's ring `write_index` (`profiler.cpp:~1710`) and `flush_targets_satisfied()` checks only `read_index >= flush_targets[i]` (`~1616-1629`). `drain()` has **three** independent inputs: the per-thread lock-free CPU/zone ring queues (*the only one in the barrier*), `sealed_frame_events` (frame markers, under `sealed_frame_mutex`), and `pending_gpu_results` (pushed at `~1046`/`~1289` under `gpu_result_mutex`). Channels 2 and 3 don't participate, so a frame marker or GPU result published before `flush()` returns can be missed — the collector snapshots a side queue, the event is published, and `flush()` still returns once the CPU watermark is met, leaving frame statistics incomplete until some later collector iteration. Consequence: `tests/sgl/device/test_profiler.cpp` *"device close settles pending frame statistics"* stays timing-dependent **even after** the #1072/#1073 fix — the reorder guarantees ordering only *within* one drain pass and cannot force another pass for a side-channel publication a pass already missed. Two constraints for anyone fixing it: the **GPU watermark must cover already-*published* results only** (waiting on *unresolved* queries exceeds the documented "published before this call" contract and can block indefinitely when a query never resolves; `tick()` is what moves resolved results into `pending_gpu_results` and is documented as not waiting — `profiler.h:471-474`), and an **"expected zone count" scheme must count `push()` successes, not zone attachments** (`ThreadData::push()` returns false and bumps `drop_count` when the ring is full, `~326-328`, but `end_zone` **discards that return value** at `~2186` and unconditionally calls `release_zone_from_global_frame` at `~2188`, so a dropped zone still decrements the frame's live-zone count and an attachment-based count would wait forever for an event never published). Diagnosed by skallweitNV, the profiler's author, on PR #1073 and verified first-hand against source ([profiler `flush()` barrier covers only 1 of 3 collector input channels](../learnings/1785769306938-slangpy-profiler-flush-barrier-covers-only-1-of-3-.md)).
