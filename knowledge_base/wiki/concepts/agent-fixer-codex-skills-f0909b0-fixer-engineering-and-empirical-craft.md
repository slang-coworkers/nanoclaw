## TL;DR

- **A clean Linux build does not clear a removed POSIX include.** `<unistd.h>` is often pulled in transitively via libstdc++ internals on Linux but not on macOS/libc++ — the removal is a latent portability break. Verify by reconstructing the compile from `compile_commands.json`, `-fsyntax-only` on PR-head source, and `-E -H` to find which header actually provides the symbol; relay as "toolchain-dependent," not "CI is red."
- **Append a new `CompilerOptionName` before `CountOf` using `(predecessor's explicit value)+1` read at HEAD** — never a triage memo's precomputed "next=N"; the enum grows frequently and a rebase can collide. Re-check the CountOf predecessor after any rebase.
- **Refute a triage root cause with a cheap experiment before shipping a mask.** For an arch-only miscompile, a frame-poison test only covers memory you can fill; whole-process `valgrind --track-origins=yes` flags a *dependency* on an uninitialized value even when local output is correct. The real fix was a producer-side one-line default member initializer. Don't ship a change you can't name a failing test for.
- **An invalid per-agent `GH_TOKEN` silently degrades a fixer to read-only** (no `gh`, no git push). The authenticated MCP GitHub tools use a separate connection and still work — triage via MCP, report the token as an explicit `Blocker`, don't retry pushes. It's typically per-agent (a OneCLI secret gap), not a fleet outage.
- **`actions/upload-artifact` excludes hidden files by default** — including everything inside a dot-prefixed directory. `path: .crashpad/` uploads an EMPTY artifact unless `include-hidden-files: true`; combined with `if-no-files-found: ignore` the failure is silent.
- **A moved skill-script path in a scheduled task fails as exit 2 (Python "can't open file").** Prefer runtime path DISCOVERY over the `/slang-<name>` slash fix IF the script keeps cwd-relative state; pin cwd (`cd /workspace/agent`) so it isn't silently reset. Give setup failures a dedicated exit code (e.g. 42) that ALERTS, not a silent transient-skip.
- **One PR can be the fix vehicle for multiple issues, so a mystery `nv-slang-bot[bot]` commit on your branch is likely a sibling chain, not a fleet incident.** Check `gh pr view --json closingIssuesReferences` before escalating; amend only your own files (explicit `git add <files>`, never `-A`); coordination is by convention, so escalate to serialize competing code edits.
- **NVRTC `-pch` (12.8+) helps ONLY the `#include`-form prelude, not raw prepended text** — the automatic PCH stop-point is the first non-directive token. Slang's CLI path uses the include form (`_addCUDAPrelude`) and wins ~104ms→22ms; a bare library embedding the default text does not. Default PCH heap is 256MB (manage reactively, never proactively — a proactive set FREES the heap); one-shot `-pch` is a +30–70ms regression, so gate it behind an amortization guard.
- **For a compile-time-performance feature, an empirical run on the real toolkit beats doc-derived reasoning** for "does it fire / does it help." NVRTC automatic PCH keys on the TU's leading-directive TEXT, not included-file content — a same-path header swap silently reuses a STALE PCH.
- **`okf_synth.py finalize` APPENDS a reading every call — run it exactly ONCE per pass** or a duplicate reading can trip a spurious ESCALATE; use `scan` for intermediate looks. A flat 690-file memory pile cannot converge under a 4-item/day fold (INDEX-STALE is permanent, top offenders carry LIVE state) — it needs a one-time bulk `issues/` migration, an owner call.
- **codex-critique optimizes for DRY/aesthetics; the human maintainer optimizes for reviewability and minimal blast radius — when they conflict, the human wins.** A scope-expanding refactor into a subsystem nobody asked you to change is a red flag even when tests pass and codex approves. Decline the must-fix with justification; re-read the original ask.
- **When a GitHub issue links a public reproduction repo, `git clone` it (`--recurse-submodules`, checking the pinned SHA) and read the ACTUAL code before building a minimal model.** A triage paraphrase routinely drops the load-bearing detail; a synthesized repro can reproduce a *similar* symptom while misattributing the cause.

## Toolchain and build-fix craft

Three atoms teach that the local build's success is not the whole answer. A removed `#include <unistd.h>` compiled clean on Linux because libstdc++ internals pull it in transitively, but would break macOS/libc++ where that path doesn't exist — a *latent portability break*, not "CI is currently red" ([removed POSIX include compiles clean on Linux](../learnings/1786516325450-a-removed-posix-include-can-compile-clean-on-linux.md)). The verification recipe (reconstruct the compile from `compile_commands.json`, `-fsyntax-only` PR-head source, `-E -H` to find the real provider header) reconciles a reviewer's 🔴 "build breaks" against a fixer's genuinely-green Linux run — both right at different layers; the fix is re-adding under `#if !SLANG_WINDOWS_FAMILY`. (Trap noted: don't read `$?` after an intervening `echo`. Also: the clarity-review runner can die on a transient `API Error: 400` at final payload assembly — re-dispatch, findings unaffected.)

Appending a public enum is a HEAD-relative operation: a new `CompilerOptionName` goes before `CountOf` using `(predecessor's explicit value)+1` read in the current checkout — a triage memo's "DumpModule=121 → new=122" was stale (the real predecessor at HEAD was `DebugInfoIncludeSource=157`, so 158), and a rebase can silently collide the integer you picked ([CompilerOptionName next-value at HEAD](../learnings/1787249396007-compileroptionname-next-value-read-to-countof-pred.md)). Re-check the CountOf predecessor after any rebase. (Bonus: a new opt-in bool needs no `getDefault`/`allowDuplicate` entry, and the contiguity `SLANG_ASSERT` only covers UserValue(0)..CountOfParsableOptions.)

The deepest debugging atom refutes a triage root cause empirically before shipping a mask. On an aarch64-only miscompile, the triage blamed uninitialized VM working-set frames and recommended zero-init; a cheap env-gated experiment (baseline / poison `0xCC` / zero-fill `0x00`) all produced correct output on x86_64, proving Approach A INERT — you shouldn't ship a change you can't name a failing test for ([arch-only miscompile — poison test then valgrind](../learnings/1788340267545-arch-only-miscompile-refute-the-triage-root-cause-.md)). The real lever was whole-process `valgrind --track-origins=yes`, which flags a *dependency* on an uninitialized value even when local output is correct (a frame-poison only covers memory you can fill, not the emit step or libc); origin was a ctor-less `PathInfo` struct whose `type` field had no default member initializer — a one-line producer-side fix. Caveats: the read is benign-in-effect on x86_64, so aarch64 CI is the real oracle; `-Wno-maybe-uninitialized` is why nothing warned; `valgrind` needed an `install_packages` (worktree/build persist across the restart).

## CI infra, credentials, and scheduled tasks

An invalid per-agent `GH_TOKEN` silently blocks ALL GitHub writes — no `gh`, no git push, so rebase/ready/merge/comment are impossible, which can be the root cause of a whole stale open-PR backlog ([invalid GH_TOKEN degrades a fixer to read-only](../learnings/1788265619832-invalid-per-agent-gh-token-silently-degrades-a-fix.md)). The recovery: the authenticated MCP GitHub tools (`mcp__slang-mcp__github_*`) use a separate connection and still work, so do full read-only triage via MCP, report the token as an explicit `Blocker` in the 5-bullet (framing writes as recommendations), and let the parent escalate the credential restore — don't burn cycles retrying pushes. It's typically per-agent (a OneCLI secret gap), not a fleet outage. (Related: the critique-gate hook regex-blocks even a harmless `curl .../pulls/N` GET, and `github_get_pull_request` doesn't expose CI check-run status — use MCP reads + supervisor states.)

`actions/upload-artifact` (v4–v7) excludes hidden files by default and defines "hidden" as anything beginning with `.` OR inside a dot-prefixed directory, so `path: .crashpad/` uploads an EMPTY artifact without `include-hidden-files: true`; with `if-no-files-found: ignore` the failure is completely silent ([upload-artifact drops dot-directory contents](../learnings/1787124782643-upload-artifact-silently-drops-dot-directory-conte.md)). (The same slangpy case had a second bug: Crashpad writes to `<db>/pending/` on POSIX, not `reports/`.) Whenever an artifact path is or contains a dot-directory, add `include-hidden-files: true`.

A moved skill-script path in a scheduled `ncl` task shows up as exit 2 (Python "can't open file") when an external skill is reinstalled at a different location — check the task run log, since the old path often worked for weeks first ([fixing a moved skill-script path](../learnings/1787548728235-fixing-a-moved-skill-script-path-in-a-scheduled-ta.md)). Two non-obvious fixes: prefer runtime path DISCOVERY over the tempting `/slang-<name>` slash-name fix IF the script keeps cwd-relative state (invoking from the skill dir silently reset weeks of stall clocks); pin cwd + resolve `$SCRIPT` from an ordered candidate list with a bounded `find` fallback. And give a broken path a dedicated setup-failure exit code (42=not-found) that ALERTS to the parent, so it doesn't masquerade as a transient skip that goes dark every fire. (`ncl tasks` is group-scoped from inside a container — the owning agent must run `ncl tasks update` in its own container.)

Branch coordination: one PR can be the fix vehicle for multiple triaged issues, so each of its `Fixes #A`/`Fixes #B` entries may have its own fixer chain legitimately pushing commits under the shared `nv-slang-bot[bot]` identity ([one PR, multiple triaged issues](../learnings/1787779963798-one-pr-can-be-the-fix-vehicle-for-multiple-triaged.md)). So a mystery bot-authored commit on your branch is NOT automatically a fleet-safety incident — check `gh pr view --json closingIssuesReferences` before escalating; after any rebase/force-push re-verify the FINAL committed content, amend only your own files (`git add <files>`, never `-A`), and escalate to the parent to serialize competing code edits (no cross-session lock exists).

## NVRTC PCH: empirical findings and a self-correction

Three atoms document one compile-time-performance investigation and reinforce that empirical runs on the real toolkit beat doc-derived reasoning. NVRTC `-pch` (12.8+) helps ONLY when the prelude reaches the TU via `#include`, because the automatic PCH "header stop point" is the first token that is NOT a preprocessing directive: an `#include "slang-cuda-prelude.h"` first line precompiles the whole ~8600-line prelude (104ms→22ms, 4.7×), while the raw *prepended* prelude text stops after ~140 lines and gets NO speedup ([NVRTC -pch helps only the #include-form prelude](../learnings/1787147387204-nvrtc-pch-12-8-helps-only-the-include-form-prelude.md)). Slang's CLI / `-target ptx` path uses the include form via `TestToolUtil::_addCUDAPrelude`, so it benefits; a bare library embedding the default text does not. The default PCH heap is 256MB (not 0), so heap management must be *reactive* — grow only on `HEAP_EXHAUSTED (=14)` — because a proactive `nvrtcSetPCHHeapSize` FREES an existing heap; and one-shot `-pch` is a +30–70ms regression (the first compile builds a PCH nobody reuses), so the driver fix needs an amortization guard (engage only after ≥1 prior compile). A [later correction](../learnings/1787307716454-correction-nvrtc-pch-helps-include-form-prelude-on.md) explicitly REFUTES an earlier learning's claim that `-pch` works on the prepended-text form: a static-code-read + vendor-docs reasoning got the API *lifetime* right (process-global heap) but the *engagement conditions* wrong (which prelude form, default heap size, one-shot cost) — the meta-lesson being to keep framing such items as to-verify empirically, not settled.

The invalidation semantics are the subtle third finding: automatic PCH keys on the compile options + the TU's leading run of preprocessing-directive TEXT, NOT on the content/mtime of `#include`d files ([NVRTC PCH keys on TU leading-directive text](../learnings/1787354583234-nvrtc-automatic-pch-keys-on-tu-leading-directive-t.md)). An inline `#define` change invalidates correctly (CREATE); a same-path included-file content change reuses a STALE PCH and emits wrong output. Slang's own `-target ptx` flow is safe (the `.h` is a fixed build artifact; runtime prelude changes go through `setLanguagePrelude`, changing the inline text), but the `-target cuda` app-driven path needs the caveat documented, and a regression test must change the *leading prelude text* (not the shader body, which sits after the stop-point) to exercise invalidation at all.

## OKF memory synthesis and codex judgment

Two OKF-synthesis atoms cover the memory-fold process. `okf_synth.py finalize` APPENDS a reading to `.okf-synth-state.json` on every invocation, so running it twice in one pass writes duplicate readings that can trip a SPURIOUS `ESCALATE` (the stall check is "backlog non-decreasing over the last 3 readings") — call `finalize` exactly ONCE per pass and use `scan` for intermediate looks ([okf-synth finalize once per pass](../learnings/1787285821812-okf-synth-finalize-run-it-exactly-once-per-pass-an.md)). That atom also gives the durable per-issue fold pattern (distil each `triage-<N>.md` in place to `type: triage` frontmatter + verdict/repro/root-cause/resume-state, replacing sprawling narrative with `[[links]]` to shared lessons). The convergence blocker is structural, not the fold logic: a flat ~690-file `triage-*.md` pile cannot converge under a 4-item/day fold because INDEX-STALE is permanent (you can't link 690 files from a 16k-budget always-loaded index) and the top OVERSIZE offenders carry LIVE chain state that shouldn't be autonomously folded ([OKF can't converge on a flat 690-file tree](../learnings/1788150355474-okf-synthesis-can-t-converge-on-a-flat-690-file-tr.md)). The recommendation is a one-time bulk migration into `memory/issues/` with a generated on-demand index (resolving INDEX-STALE + NO-FRONTMATTER at once) — an owner call, since 4/day would take ~150 days.

Finally, two atoms on codex-critique as a fixer tool. Codex optimizes for DRY / "single source of truth"; a human maintainer optimizes for reviewability and minimal blast radius — and when they conflict the human wins ([codex-critique pushes scope-expanding over-engineering](../learnings/1788380776351-codex-critique-can-push-scope-expanding-over-engin.md)). Across ~13 rounds codex pushed a parser-rewriting "unify the tables" refactor that the lead architect then rejected as "collateral damage to the parser" for what should be a trivial semantic check; "single source of truth" is also wrong when the two sources answer *different questions* (the parser's "what tokens may follow `operator`" vs the checker's "is this an actual operator"). A scope-expanding refactor into a subsystem nobody asked you to change is a red flag even when tests pass and codex approves — decline the must-fix with justification and re-read the original ask. But codex-critique also earns its keep: running the CODE_REVIEW stage even on a "no code change" investigation is what cloned the actual public repro and caught a modeling error ([clone the actual repro repo](../learnings/1787799707169-clone-the-actual-repro-repo-before-modeling-it-fro.md)) — the paraphrase-built minimal repro had the wrong index values, the wrong op (sampler `SampleLevel` vs fetch), and the wrong binding model. When an issue links a public reproduction repo, `git clone` it (`--recurse-submodules`, checking the pinned SHA via `git ls-tree`, not default HEAD) and read the ACTUAL shader+host code before modeling — a synthesized repro can reproduce a *similar* symptom while misattributing the cause.

## Contradictions / supersessions

[The NVRTC correction atom](../learnings/1787307716454-correction-nvrtc-pch-helps-include-form-prelude-on.md) explicitly SUPERSEDES an earlier learning's claim that `-pch` helps the raw prepended-text prelude — the include-form-only finding is authoritative; the process-global-heap point from the earlier learning stands. The two codex atoms are complementary, not contradictory: codex over-reaches on scope/aesthetics ([over-engineering](../learnings/1788380776351-codex-critique-can-push-scope-expanding-over-engin.md)) yet is high-value for catching factual/modeling errors ([clone-repro](../learnings/1787799707169-clone-the-actual-repro-repo-before-modeling-it-fro.md)) — the resolution is "authoritative on facts, not on scope," matching the approver-side codex guidance.
