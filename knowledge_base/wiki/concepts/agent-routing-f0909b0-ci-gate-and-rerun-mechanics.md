## TL;DR

- GitHub Actions `status` has two non-running states that look alike: `queued` (waiting for a runner — **drains with time**) and `waiting` (waiting for **environment approval from a human** — **does not drain**). Any gate that folds both into one "active" set can be jammed forever by a single `waiting` run. Split the active set by status before concluding "contention is clearing."
- Read `conclusion` before interpreting `runner_name`. Empty `runner_name` does NOT mean starvation — `conclusion: skipped` (a `needs:`/`if:` short-circuit) also yields null runner. Three states: `queued/failure`+empty → infra/starvation; `skipped`+empty → look upstream at the gating job; any+non-empty → it ran, read the log. A concurrent real outage is the most dangerous backdrop — co-occurrence is not causation; require the victim to show the mechanism's fingerprint (`queued` with no runner).
- A GHA rerun mutates the **same** run id (increments `run_attempt`); it does not create a new one. "Same run id since last tick" is satisfied equally by "nobody re-dispatched" and "re-dispatched and failed again" — key any "has this re-run?" check on `(databaseId, run_attempt)`. `runs/<id>/jobs` returns the LATEST attempt only; use `runs/<id>/attempts/<n>/jobs` for a specific attempt. `run_started_at` diverging from `created_at` is itself a rerun signal.
- A run's `conclusion` cannot tell you what a gate decided — a priority/retry helper reports `conclusion: success` even when it did nothing. Read the decision line or step conclusions, not the rollup.
- A stale bot priority-yield is NOT terminal: at any age past the gate ceiling (`--max-yield-hours`, age from the fixed `created_at`) one manual full rerun escalates and proceeds despite contention. Only the *automatic* retry helper expires (its `--lookback-hours` window). "No automatic rerun" ≠ "no rerun possible." Check `triggering_actor` before using any rerun as gate evidence (`github-actions[bot]` bypasses the throttle branch entirely).
- A `test-slang` job can be terminally failed while its parent run is non-terminal (`waiting`/`in_progress`) because `test-falcor` sits on a deployment-approval gate — then EVERY rerun form is refused ("already running"/"cannot be rerun") for sibling jobs in that SAME run. Scope: a `pull_request` run is per-PR (doesn't wedge other PRs); `merge_group` runs are rerunnable when `completed/failure`. Record `action:left` (non-terminal), don't keep retrying.
- Falcor gate latency + ~1-day build-artifact retention = unrecoverable: once the wait exceeds retention the job fails on a missing `slang-tests-*` artifact and rerunning just reproduces it. Only a fresh push, a retention bump, or faster approval fixes it. Classify `artifact-expiry-blocked (non-rerunnable)`, distinct from ordinary Falcor flakes.
- Rank CI-gate fixes by failure DIRECTION, not completeness: a fails-safe lever wastes work; a fails-open lever ships a missed defect. A de-gate is only safe as a **conservative classifier** ("run it unless PROVABLY irrelevant"), never "guess whether it's needed."
- Re-check `isDraft` at the moment of CI dispatch — a human ready-flip between pushes turns the drafts-only manual dispatch into a cosmetic-red false alarm on top of the real `pull_request` run.
- Re-read the authoritative hold surface at the moment of a gated action, not at planning time — an always-loaded "always do X when C" rule fires without a deliberation gap and silently beats a superseding hold that lives in a split-out on-demand file.
- Never judge GitHub API quota from `/rate_limit` behind the OneCLI gateway — the credential is injected per-path, so `/rate_limit` reports the anonymous 60 bucket. Read `X-Ratelimit-Limit` from a real `/repos/...` response. The instrument that reports on quota is subject to the quota's plumbing.

## Two states that look alike: waiting vs queued, skipped vs starved

The central trap is a status allowlist that folds "blocked on a human" in with "blocked on a resource." In the Actions API, `queued` drains with time but `waiting` (environment approval) does not — so `ci.yml`'s bot-priority retry helper, whose `ACTIVE_STATUSES` includes `waiting`, was jammed indefinitely: seven "active" runs, five draining `queued` but two `waiting` aged ~36h/~58h on an unactioned `falcor-ci` approval, making the "quiet" precondition structurally unreachable and reddening every yielded bot run in the fleet ([GitHub Actions `waiting` ≠ queued — a human approval gate that jams CI retry](../learnings/1786404029507-github-actions-waiting-queued-it-s-a-human-approva.md)). `gh run list` renders both as pending-ish; the distinction only shows in `status`. Whenever you see a set defined by a status allowlist, ask which members can clear on their own. The symmetric read-error is `runner_name`: empty is not evidence of starvation because `conclusion: skipped` (a `needs:`/`if:` short-circuit) also yields null runner — 37 jobs read "starved by the dead GPU pool" but were all `skipped` by one 13-second gate job, while a genuine concurrent pool outage co-occurred but was causally unrelated ([empty runner_name does not distinguish starved from skipped](../learnings/1786438262793-empty-runner-name-does-not-distinguish-starved-by-.md)). Read `conclusion` first; a concurrent outage is FACT while the causal link is HYPOTHESIS, and require the victim to show `queued`-with-no-runner rather than merely co-occur.

## Reruns mutate in place; read the decision, not the rollup

A supervisor probe misfired on every retried run by asserting "same run id as last tick ⇒ nobody re-dispatched" — mechanically impossible, because a GHA rerun increments `run_attempt` on the **same** `databaseId` rather than minting a new id ([a GHA rerun mutates the same run id — key on (databaseId, run_attempt)](../learnings/1786454704637-a-gha-rerun-mutates-the-same-run-id-comparing-run-.md)). "Run id unchanged" is satisfied equally by "nobody re-dispatched" and "re-dispatched and failed again." Companion traps: `runs/<id>/jobs` returns the latest attempt only (use `attempts/<n>/jobs` for a specific one — the failure set can change under a stable id), and `run_started_at` diverging from `created_at` is itself a rerun signal from a single snapshot. The meta-lesson: when you refuse the same request a third time, escalate the *mechanism* (name the unread field) rather than re-arguing the substance — a suppression flag the violating instrument never consults is not a gate. This also settles the priority-yield question: a stale bot yield is NOT terminal — the gate (`wait-for-priority.py --max-yield-hours 12`) computes age from the fixed `created_at`, so past the ceiling one manual full rerun *escalates* and proceeds despite contention (older = more certainly escalates); only the automatic retry helper's `--lookback-hours 16` window expires ([a stale yielded run is NOT terminal — the gate escalates on any rerun](../learnings/1786440049067-slang-ci-priority-yield-a-stale-yielded-run-is-not.md)). "No automatic rerun" ≠ "no rerun possible." Check `triggering_actor` before citing any rerun as gate evidence (`github-actions[bot]` fails `IS_THROTTLED_BOT` and bypasses the branch entirely), and a helper's own `conclusion: success` proves only that it ran — read the decision line or step conclusions.

## The Falcor environment gate: rerun-blocker and artifact-expiry

The `falcor-ci` deployment-approval gate produces two distinct non-rerunnable states. First, while `test-falcor` sits `waiting`, a `test-slang` (or any sibling) job can be terminally `completed/failure` while the parent run is non-terminal — and then every rerun form is refused ("run/job cannot be rerun; already running") for the whole run ([Falcor approval gate makes intermittent test-slang reds un-rerunnable](../learnings/1786465690642-falcor-approval-gate-makes-intermittent-test-slang.md), [test-falcor waiting blocks gh run rerun for sibling jobs in the SAME PR run](../learnings/1786986200860-test-falcor-waiting-on-environment-gate-blocks-gh-.md)). Scope matters: a `pull_request` run is per-PR and does NOT wedge other PRs (don't overstate blast radius without checking `event`); a `merge_group` batch that reached `completed/failure` IS rerunnable with `--failed`. Record `action:left` with reason "run non-terminal (falcor gate)"; don't force a whole-workflow rerun (violates the "only rerun --failed" safety rule), and distinguish an echoed script-source line (`echo "::error::…"`) from a real fired `##[error]`. Second, when the gate wait exceeds the ~1-day `slang-tests-*` artifact retention, the job eventually runs but fails immediately on a missing artifact — **not a flake, not rerunnable** (rerunning reproduces it); only a fresh push, a retention bump, or faster approval clears it ([Falcor gate latency compounds with 1-day artifact retention](../learnings/1787077102662-falcor-gate-latency-compounds-with-1-day-artifact-.md)). Classify `artifact-expiry-blocked (non-rerunnable)`, distinct from ordinary Falcor flakes, and don't nudge the author (their next push clears it). When advising a maintainer on cutting flaky-rerun volume, rank levers by failure DIRECTION not completeness: a retry-on-transient wrapper fails safe (wasted minutes), a gate-decouple is pure win, but a de-gate fails OPEN (a misclassified PR ships uncaught) — so a de-gate is acceptable only as a conservative classifier that runs Falcor unless the diff is PROVABLY shader-irrelevant ([CI-gate levers rank by failure DIRECTION, not completeness](../learnings/1786522092980-ci-gate-levers-rank-by-failure-direction-not-compl.md)).

## Timing and instrument hygiene at the moment of action

Two "re-check at action time" rules. Re-query `gh pr view --json isDraft` at the moment of a drafts-only manual `ci.yml` dispatch — a human ready-flip between pushes turns the manual run into a cosmetic-red false alarm (only `wait-for-human-priority`+`check-ci` fail, builds skipped) firing on top of the real `pull_request` run the ready-flip already triggered ([re-check isDraft at the moment of CI dispatch](../learnings/1786606902247-re-check-isdraft-at-the-moment-of-ci-dispatch-a-hu.md)). And re-read the authoritative hold surface at the gated action itself: an always-loaded "always dispatch CI on drafts" rule fires with no deliberation gap and silently beats a superseding "no `ci.yml` dispatch while any run is `waiting`" hold living in a split-out on-demand file — grep the hold surface for the action verb immediately before executing, not at planning time ([re-read the authoritative hold surface at a gated action](../learnings/1786467632283-re-read-the-authoritative-hold-surface-at-a-gated-.md)). Finally, quota: behind the OneCLI gateway the credential is injected per-path, so `/rate_limit` reports the anonymous 60 bucket while `/repos/...` reports 6000 — never judge quota from `/rate_limit`; read `X-Ratelimit-Limit` off a real request, and note the tell is internal contradiction (`used:0` after ten calls) not a second tool ([never judge GitHub API quota from /rate_limit](../learnings/1786381107939-never-judge-github-api-quota-from-rate-limit-the-g.md)). The instrument that reports on quota is itself subject to the quota's plumbing — prefer a response header on a real request over a dedicated status endpoint.
