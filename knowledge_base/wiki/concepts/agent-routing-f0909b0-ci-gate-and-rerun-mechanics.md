# CI gate & rerun mechanics — waiting vs queued, priority-yield, Falcor gates, run_attempt, and reading the right instrument

## TL;DR

- GitHub Actions `status` has two non-running states that look alike: `queued` (waiting for a runner — **drains with time**) and `waiting` (waiting for **environment approval from a human** — **does not drain**). Any gate that folds both into one "active" set can be jammed forever by a single `waiting` run. Split the active set by status before concluding "contention is clearing."
- Read `conclusion` before interpreting `runner_name`. Empty `runner_name` does NOT mean starvation — `conclusion: skipped` (a `needs:`/`if:` short-circuit) also yields null runner. Three states: `queued/failure`+empty → infra/starvation; `skipped`+empty → look upstream at the gating job; any+non-empty → it ran, read the log. A concurrent real outage is the most dangerous backdrop — co-occurrence is not causation; require the victim to show the mechanism's fingerprint (`queued` with no runner). Conversely a job cancelled while queued has a `started_at` but no runner: count real starts only where `runner_name` is non-empty.
- A GHA rerun mutates the **same** run id (increments `run_attempt`); it does not create a new one. "Same run id since last tick" is satisfied equally by "nobody re-dispatched" and "re-dispatched and failed again" — key any "has this re-run?" check on `(databaseId, run_attempt)`. `runs/<id>/jobs` returns the LATEST attempt only; use `runs/<id>/attempts/<n>/jobs` for a specific attempt. `run_started_at` diverging from `created_at` is itself a rerun signal.
- A run's `conclusion` cannot tell you what a gate decided — a priority/retry helper reports `conclusion: success` even when it did nothing. Read the decision line or step conclusions, not the rollup.
- A stale bot priority-yield is NOT terminal: at any age past the gate ceiling (`--max-yield-hours`, age from the fixed `created_at`) up to GitHub's 30-day rerun limit, one manual full rerun escalates and proceeds despite contention. A yielded run still `waiting` on the `falcor-ci` gate is never auto-retried and fails only at the 30-day approval timeout (gate job `steps=[]`, ~30 d duration): classify it yield + approval expiry, not a code failure, and don't rerun it; only a push or a maintainer's "Update branch" re-arms the gate, so report it up instead of pushing a refresh. Never cancel such a run either: a `cancelled` gate job makes `failed_only_because_priority_gate` false, so the retry helper rejects it for good; get the PR un-drafted, or re-dispatch once while human and MQ CI are quiet. Only the *automatic* retry helper expires (its `--lookback-hours` window). "No automatic rerun" ≠ "no rerun possible." Check `triggering_actor` before using any rerun as gate evidence (`github-actions[bot]` bypasses the throttle branch entirely).
- A `test-slang` job can be terminally failed while its parent run is non-terminal (`waiting`/`in_progress`) because `test-falcor` sits on a deployment-approval gate — then EVERY rerun form is refused ("already running"/"cannot be rerun") for sibling jobs in that SAME run. Scope: a `pull_request` run is per-PR (doesn't wedge other PRs); `merge_group` runs are rerunnable when `completed/failure`. Record `action:left` (non-terminal), don't keep retrying.
- Falcor gate latency + ~1-day build-artifact retention = unrecoverable: once the wait exceeds retention the job fails on a missing `slang-tests-*` artifact and rerunning just reproduces it. Only a fresh push, a retention bump, or faster approval fixes it. Classify `artifact-expiry-blocked (non-rerunnable)`, distinct from ordinary Falcor flakes.
- A Falcor approval gate that timed out to `conclusion: CANCELLED` is terminal, so it vanishes from the payload's `blockedChecks` while `mergeStateStatus` stays `BLOCKED`. Never call a PR clean from empty blocked-signal fields; run `gh pr checks` too. Classify `gate-wedged` (needs a human re-approve, not a rerun).
- Rank CI-gate fixes by failure DIRECTION, not completeness: a fails-safe lever wastes work; a fails-open lever ships a missed defect. A de-gate is only safe as a **conservative classifier** ("run it unless PROVABLY irrelevant"), never "guess whether it's needed."
- Re-check `isDraft` at the moment of CI dispatch — a human ready-flip between pushes turns the drafts-only manual dispatch into a cosmetic-red false alarm on top of the real `pull_request` run.
- Re-read the authoritative hold surface at the moment of a gated action, not at planning time — an always-loaded "always do X when C" rule fires without a deliberation gap and silently beats a superseding hold that lives in a split-out on-demand file.
- Never judge GitHub API quota from `/rate_limit` behind the OneCLI gateway — the credential is injected per-path, so `/rate_limit` reports the anonymous 60 bucket. Read `X-Ratelimit-Limit` from a real `/repos/...` response. The instrument that reports on quota is subject to the quota's plumbing.
- PR and merge-queue CI do not run `docs/generated/tests`. Two nightlies do: `Nightly Slang Test` / `agentic-tests` gates on them (against `_meta/expected-failures.txt`), and `Nightly Slang Coverage Test` runs them with failures tolerated. So a target-gated pass or an intentional emitter change can merge green and break the nightly; the fix is usually a CHECK refresh. Triage by failing target (`.slang.N` = Nth TEST line) and target guards in the green→red compare; a lost runner's logs 404 (BlobNotFound), so read `check-runs/<id>/annotations`. To find the breaking merge, bisect `slangc` from the `slang-tests-linux-x86_64-gcc-release` artifact of consecutive MQ runs instead of building.
- A nonzero `ci.yml` `status=waiting` count is the Falcor approval gate, not backpressure; it no longer reaches zero, so never gate a dispatch on it.

## Two states that look alike: waiting vs queued, skipped vs starved

The central trap is a status allowlist that folds "blocked on a human" in with "blocked on a resource." In the Actions API, `queued` drains with time but `waiting` (environment approval) does not — so `ci.yml`'s bot-priority retry helper, whose `ACTIVE_STATUSES` includes `waiting`, was jammed indefinitely: seven "active" runs, five draining `queued` but two `waiting` aged ~36h/~58h on an unactioned `falcor-ci` approval, making the "quiet" precondition structurally unreachable and reddening every yielded bot run in the fleet ([GitHub Actions `waiting` ≠ queued — a human approval gate that jams CI retry](../learnings/1786404029507-github-actions-waiting-queued-it-s-a-human-approva.md)). `gh run list` renders both as pending-ish; the distinction only shows in `status`. Whenever you see a set defined by a status allowlist, ask which members can clear on their own. The symmetric read-error is `runner_name`: empty is not evidence of starvation because `conclusion: skipped` (a `needs:`/`if:` short-circuit) also yields null runner — 37 jobs read "starved by the dead GPU pool" but were all `skipped` by one 13-second gate job, while a genuine concurrent pool outage co-occurred but was causally unrelated ([empty runner_name does not distinguish starved from skipped](../learnings/1786438262793-empty-runner-name-does-not-distinguish-starved-by-.md)). Read `conclusion` first; a concurrent outage is FACT while the causal link is HYPOTHESIS, and require the victim to show `queued`-with-no-runner rather than merely co-occur. The converse trap is `started_at`: a job cancelled while still queued carries a `started_at` but an empty `runner_name`, so counting job starts by `started_at` invents runs. Inside a 3 h window when the Windows GPU pool had 0 runners, 24 such phantom "T4 starts" appeared. To measure real runner starts (for example, to bound a pool outage), filter on a non-empty `runner_name`, and confirm the outage with `health_snapshots.jsonl` `runner_groups[...].total == 0` plus the last and first jobs that have a runner name ([measure real job starts by runner name](../learnings/1792572260133-bisect-a-slang-nightly-regression-with-mq-build-ar.md)).

The same distinction retires an older fleet rule, "don't `gh workflow run ci.yml` until `actions/workflows/ci.yml/runs?status=waiting` returns `total_count=0`". As of 2026-09-27 shader-slang/slang had 73 `ci.yml` runs in `status=waiting`, each parked on a `falcor-build-approval-gate` job (human branches included), so the count can no longer reach zero, while newer runs still finish (a 2026-09-26 run completed 41 jobs with 72 older runs parked). A nonzero waiting count is the approval gate, not queue contention: read the waiting job's name from `/actions/runs/<id>/jobs` (status `waiting`) before treating it as backpressure [ci.yml waiting-runs count can no longer reach zero (falcor-build-approval-gate)](../learnings/1790496460678-ci-yml-waiting-runs-count-can-no-longer-reach-zero.md).

## Reruns mutate in place; read the decision, not the rollup

A supervisor probe misfired on every retried run by asserting "same run id as last tick ⇒ nobody re-dispatched" — mechanically impossible, because a GHA rerun increments `run_attempt` on the **same** `databaseId` rather than minting a new id ([a GHA rerun mutates the same run id — key on (databaseId, run_attempt)](../learnings/1786454704637-a-gha-rerun-mutates-the-same-run-id-comparing-run-.md)). "Run id unchanged" is satisfied equally by "nobody re-dispatched" and "re-dispatched and failed again." Companion traps: `runs/<id>/jobs` returns the latest attempt only (use `attempts/<n>/jobs` for a specific one — the failure set can change under a stable id), and `run_started_at` diverging from `created_at` is itself a rerun signal from a single snapshot. The meta-lesson: when you refuse the same request a third time, escalate the *mechanism* (name the unread field) rather than re-arguing the substance — a suppression flag the violating instrument never consults is not a gate. This also settles the priority-yield question: a stale bot yield is NOT terminal — the gate (`wait-for-priority.py --max-yield-hours 12`) computes age from the fixed `created_at`, so past the ceiling one manual full rerun *escalates* and proceeds despite contention (older = more certainly escalates); only the automatic retry helper's `--lookback-hours 16` window expires ([a stale yielded run is NOT terminal — the gate escalates on any rerun](../learnings/1786440049067-slang-ci-priority-yield-a-stale-yielded-run-is-not.md)). "No automatic rerun" ≠ "no rerun possible." Check `triggering_actor` before citing any rerun as gate evidence (`github-actions[bot]` fails `IS_THROTTLED_BOT` and bypasses the branch entirely), and a helper's own `conclusion: success` proves only that it ran — read the decision line or step conclusions.

## The Falcor environment gate: rerun-blocker and artifact-expiry

The `falcor-ci` deployment-approval gate produces two distinct non-rerunnable states. First, while `test-falcor` sits `waiting`, a `test-slang` (or any sibling) job can be terminally `completed/failure` while the parent run is non-terminal — and then every rerun form is refused ("run/job cannot be rerun; already running") for the whole run ([Falcor approval gate makes intermittent test-slang reds un-rerunnable](../learnings/1786465690642-falcor-approval-gate-makes-intermittent-test-slang.md), [test-falcor waiting blocks gh run rerun for sibling jobs in the SAME PR run](../learnings/1786986200860-test-falcor-waiting-on-environment-gate-blocks-gh-.md)). Scope matters: a `pull_request` run is per-PR and does NOT wedge other PRs (don't overstate blast radius without checking `event`); a `merge_group` batch that reached `completed/failure` IS rerunnable with `--failed`. Record `action:left` with reason "run non-terminal (falcor gate)"; don't force a whole-workflow rerun (violates the "only rerun --failed" safety rule), and distinguish an echoed script-source line (`echo "::error::…"`) from a real fired `##[error]`. Second, when the gate wait exceeds the ~1-day `slang-tests-*` artifact retention, the job eventually runs but fails immediately on a missing artifact — **not a flake, not rerunnable** (rerunning reproduces it); only a fresh push, a retention bump, or faster approval clears it ([Falcor gate latency compounds with 1-day artifact retention](../learnings/1787077102662-falcor-gate-latency-compounds-with-1-day-artifact-.md)). Classify `artifact-expiry-blocked (non-rerunnable)`, distinct from ordinary Falcor flakes, and don't nudge the author (their next push clears it). When advising a maintainer on cutting flaky-rerun volume, rank levers by failure DIRECTION not completeness: a retry-on-transient wrapper fails safe (wasted minutes), a gate-decouple is pure win, but a de-gate fails OPEN (a misclassified PR ships uncaught) — so a de-gate is acceptable only as a conservative classifier that runs Falcor unless the diff is PROVABLY shader-irrelevant ([CI-gate levers rank by failure DIRECTION, not completeness](../learnings/1786522092980-ci-gate-levers-rank-by-failure-direction-not-compl.md)).

A third Falcor state is invisible to the wake payload. A `falcor-build-approval-gate` run that times out of WAITING becomes a **completed** run with `conclusion: CANCELLED`; that is terminal, so it drops out of `blockedChecks` (which only captures check-run `status` in `{waiting, requested, pending}`), yet the PR's `mergeStateStatus` stays `BLOCKED` and `gh pr checks` reports it as `fail`. On 2026-09-30 a sweep marked #12716 and #13270 `resolved` on "blockedChecks empty, same head sha, must be clean"; both were reclassified to `gate-wedged`. Never infer clean from `blockedChecks:[] && onlyBlocked:false` alone: always also run `gh pr checks` or read `mergeStateStatus`/`statusCheckRollup` conclusions for CANCELLED/FAILURE. A CANCELLED approval-gate run is not fixable by rerun; it needs a human to re-approve inside the workflow's approval window ([Falcor gate CANCELLED (not WAITING) is invisible to blockedChecks](../learnings/1790755755702-falcor-gate-cancelled-not-waiting-is-invisible-to-.md)).

A yielded bot `workflow_dispatch` run (`wait-for-human-priority` + `check-ci` failed) can also sit at `falcor-build-approval-gate` in status `waiting`, and then it is never retried at all. In `ci.yml` the gate `needs` only `filter` and uses `environment: falcor-ci`, so it waits for a human even after the priority job has yielded, and that keeps the run's status open. `extras/ci/retry-yielded-bot-ci.py` reruns only runs with `status=completed` created within `--lookback-hours 16` (and skips while CI is active), so the run sits open until GitHub's 30-day environment-approval timeout and then fails with `wait-for-human-priority` + `falcor-build-approval-gate` + `check-ci` and every build/test skipped. By then `gh run rerun` is refused ("created over a month ago", GitHub's 30-day rerun limit), and a fresh `gh workflow run ci.yml` starts a new 12 h aging clock (`wait-for-priority.py` ages from `created_at`), so it can yield and stick the same way. The tell is a `ci_failed` webhook about 30 days after a bot dispatch with only the gate jobs failed: the failed `falcor-build-approval-gate` job has `steps=[]` and `completedAt` ≈ `startedAt` + 30 d, `wait-for-human-priority` failed at its "Stop yielded bot CI" step (a priority yield), and the third failure is the aggregate `check-ci`. Classify it as yield plus approval expiry, not a code failure: don't hunt for a bug and don't rerun, because a re-dispatch just yields again and the bot cannot approve the `falcor-ci` environment ([falcor gate with no steps + 30-day duration = expired env approval](../learnings/1792735967556-falcor-build-approval-gate-with-no-steps-30-day-du.md)). Three 2026-10-29 recurrences confirm the signature and add detail. On slang#13333 (run 36647612850, dispatched 09-29 23:54Z) the gate concluded `failure` at exactly 10-29 23:54Z, its job log was already gone (`BlobNotFound`), and all 46 build/test jobs were skipped [slang CI: falcor-build-approval-gate "failure" 30 days later = expired environment approval, not a code failure](../learnings/1793318217230-slang-ci-falcor-build-approval-gate-failure-30-day.md). On #13331 (run 36639710975, dispatched 09-29, failed 10-29) the 16 h lookback (`--lookback-hours 16`, near line 133 of the retry script) is what keeps a run that completes 30 days after creation from ever being retried [Bot CI on a draft can hang 30 days on the falcor-ci approval gate, and the yield-retry bot then never reruns it](../learnings/1793313053464-bot-ci-on-a-draft-can-hang-30-days-on-the-falcor-c.md). The gate's annotation reads "The deployment was rejected or didn't satisfy other protection rules", and `gh run rerun --failed` is refused ("created over a month ago"), so only a new run re-arms the gate: a push, or a maintainer clicking "Update branch". Treat it as waiting on a human and report it up rather than pushing a refresh, because a refresh only restarts the same 30-day wait for a human [slang CI falcor-build-approval-gate "fails" after 30 days unapproved, and a run older than a month can't be re-run](../learnings/1793306572297-slang-ci-falcor-build-approval-gate-fails-after-30.md). Re-dispatch (`gh workflow run ci.yml --ref <branch>`) only when the PR actually needs fresh CI, ideally after merging current master into it. Do not promise an automatic retry for a run in this state, and do not cancel it to get one (next paragraph). Also, a push to a draft PR runs no builds (the `pull_request` runs are skipped), so after pushing you still have to dispatch CI explicitly (shader-slang/slang#13228) ([bot CI stuck 30 days on a pending falcor-ci approval](../learnings/1792723271790-bot-ci-on-shader-slang-slang-can-get-stuck-for-30-.md)). A non-draft bot PR's `pull_request` run does the same thing after it has built and tested: it parks on `falcor-build-approval-gate` (`waiting`) with no approver, and the retry helper keeps counting it as active. So every bot ready-flip adds one more permanent "active" run to the bot-CI starvation ([GraphQL timelineItems(since:) totalCount ignores since; bot PRs park at the Falcor gate](../learnings/1792486262354-graphql-timelineitems-since-totalcount-ignores-sin.md)).

**Never cancel a yielded run that is still `waiting` at the gate in the hope that `ci-retry-yielded-bot` picks it up.** The script cannot see the run while it waits, because `fetch_recent_completed_runs` asks only for `status=completed`. Cancelling does not make it visible in a useful way: `failed_only_because_priority_gate` returns False when any job other than the yielded marker or `check-ci` concluded `failure` or `cancelled`, and a cancel sets `falcor-build-approval-gate` to `cancelled`, so the script rejects the run for good and the PR is left with no build or test result. On PR #14079 (2026-10-30) slang-fixer cancelled yielded dispatch runs 40985513023 and 40991896824 expecting a retry, and neither was retried; this corrects an older fleet note that said cancelling makes the run retryable. To get real CI on a yielded draft, ask a human to mark it ready (`pull_request` CI then runs at full priority), or start one fresh dispatch at a time while no human or merge-queue CI is active, and keep a code commit at the head, because a dispatch diffs only `HEAD^1...HEAD` and a docs-only head commit skips every job while still reporting success [Do not cancel a yielded bot CI run waiting at the falcor approval gate](../learnings/1793328120073-do-not-cancel-a-yielded-bot-ci-run-waiting-at-the-.md) [Do not cancel a yielded bot CI run on shader-slang/slang — it disqualifies the auto-retry](../learnings/1793328089059-do-not-cancel-a-yielded-bot-ci-run-on-shader-slang.md).

## Coverage the PR gate never runs: nightly-only agentic docs tests

A green PR and merge-queue run is not a full-suite verdict: neither runs `docs/generated/tests`. Two nightlies do. `Nightly Slang Test` / `agentic-tests` gates on them, with known failures listed in `docs/generated/tests/_meta/expected-failures.txt`; `Nightly Slang Coverage Test` also runs them (`ci-slang-coverage-test.yml` calls `run-coverage.sh --with-agentic-tests`) but tolerates failures. So a change that breaks only those tests merges green and surfaces a day later, including an intentional emitter change such as #13569's WGSL comparison parens; the usual fix is to refresh the CHECK (precedents #13454, #13731). Locally, `regenerate.py lint` can show 2 YAML errors only because PyYAML is not installed (it falls back to a simpler parser) while the nightly reports 0, so diff the lint output before and after your edit instead of chasing them; and `gh run view <run> --log-failed --job <id>` fetches the job log when `gh api .../actions/jobs/<id>/logs` returns empty ([docs/generated/tests runs in two nightlies, not one](../learnings/1792225630977-docs-generated-tests-runs-in-two-nightlies-not-one.md)). On 2026-10-02 the nightly went red on `docs/generated/tests/design/ir-reference/differentiation/reverse-mode-emitted-name-prefixes.slang`, on the CUDA and Metal legs only, after #13358 added a CUDA/Metal-only `expandAutodiffParameterContexts` pass. To triage an agentic nightly red, list which targets fail (the `.slang.N` suffix maps to the Nth `//TEST` line) and grep `compare/<green>...<red>` for target guards in `slang-emit.cpp`. Two tooling notes from the same triage: `actions/runs?created=<ISO>..<ISO>` works through the OneCLI proxy with the colons encoded as `%3A`, and when a job's runner was lost `actions/jobs/<id>/logs` returns BlobNotFound, so read `check-runs/<id>/annotations` instead ([agentic docs tests only run nightly, so target-gated passes can merge red](../learnings/1790929124431-slang-ci-agentic-docs-tests-only-run-nightly-so-ta.md)).

To find which merge broke such a nightly test, bisect over merge-queue build artifacts instead of building. Every `merge_group` `CI` run uploads `slang-tests-linux-x86_64-gcc-release` (~365 MB); list it with `GET /repos/shader-slang/slang/actions/runs/<mq_run_id>/artifacts` and download `archive_download_url` through the OneCLI proxy with no auth header (~5 s). Unzip only `Release/bin/slangc*` and `Release/lib/*`, run `LD_LIBRARY_PATH=<dir>/Release/lib <dir>/Release/bin/slangc test.slang -target hlsl ...`, and compare the output across consecutive MQ heads. That found in minutes that #13724 broke the `docs/generated/tests` HLSL `#line` test. Only PR and MQ CI runs carry these artifacts; nightly, Release and schedule runs have none ([bisect a nightly regression with MQ build artifacts](../learnings/1792572260133-bisect-a-slang-nightly-regression-with-mq-build-ar.md)). For bisecting across published releases instead, see [release tarball repro and version bisect](slang-tooling-release-tarball-repro-and-version-bisect.md).

## Timing and instrument hygiene at the moment of action

Two "re-check at action time" rules. Re-query `gh pr view --json isDraft` at the moment of a drafts-only manual `ci.yml` dispatch — a human ready-flip between pushes turns the manual run into a cosmetic-red false alarm (only `wait-for-human-priority`+`check-ci` fail, builds skipped) firing on top of the real `pull_request` run the ready-flip already triggered ([re-check isDraft at the moment of CI dispatch](../learnings/1786606902247-re-check-isdraft-at-the-moment-of-ci-dispatch-a-hu.md)). And re-read the authoritative hold surface at the gated action itself: an always-loaded "always dispatch CI on drafts" rule fires with no deliberation gap and silently beats a superseding "no `ci.yml` dispatch while any run is `waiting`" hold living in a split-out on-demand file — grep the hold surface for the action verb immediately before executing, not at planning time ([re-read the authoritative hold surface at a gated action](../learnings/1786467632283-re-read-the-authoritative-hold-surface-at-a-gated-.md)). Finally, quota: behind the OneCLI gateway the credential is injected per-path, so `/rate_limit` reports the anonymous 60 bucket while `/repos/...` reports 6000 — never judge quota from `/rate_limit`; read `X-Ratelimit-Limit` off a real request, and note the tell is internal contradiction (`used:0` after ten calls) not a second tool ([never judge GitHub API quota from /rate_limit](../learnings/1786381107939-never-judge-github-api-quota-from-rate-limit-the-g.md)). The instrument that reports on quota is itself subject to the quota's plumbing — prefer a response header on a real request over a dedicated status endpoint.
