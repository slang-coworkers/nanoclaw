# CI gate & rerun mechanics — waiting vs queued, priority-yield, Falcor gates, run_attempt, and reading the right instrument

## TL;DR

- GitHub Actions `status` has two non-running states that look alike: `queued` (waiting for a runner — **drains with time**) and `waiting` (waiting for **environment approval from a human** — **does not drain**). Any gate that folds both into one "active" set can be jammed forever by a single `waiting` run. Split the active set by status before concluding "contention is clearing."
- Read `conclusion` before interpreting `runner_name`. Empty `runner_name` does NOT mean starvation — `conclusion: skipped` (a `needs:`/`if:` short-circuit) also yields null runner. Three states: `queued/failure`+empty → infra/starvation; `skipped`+empty → look upstream at the gating job; any+non-empty → it ran, read the log. A concurrent real outage is the most dangerous backdrop — co-occurrence is not causation; require the victim to show the mechanism's fingerprint (`queued` with no runner). Conversely a job cancelled while queued has a `started_at` but no runner: count real starts only where `runner_name` is non-empty.
- A GHA rerun mutates the **same** run id (increments `run_attempt`); it does not create a new one. "Same run id since last tick" is satisfied equally by "nobody re-dispatched" and "re-dispatched and failed again" — key any "has this re-run?" check on `(databaseId, run_attempt)`. `runs/<id>/jobs` returns the LATEST attempt only; use `runs/<id>/attempts/<n>/jobs` for a specific attempt. `run_started_at` diverging from `created_at` is itself a rerun signal.
- A run's `conclusion` cannot tell you what a gate decided — a priority/retry helper reports `conclusion: success` even when it did nothing. Read the decision line or step conclusions, not the rollup.
- A stale bot priority-yield is NOT terminal: at any age past the gate ceiling (`--max-yield-hours`, age from the fixed `created_at`) up to GitHub's 30-day rerun limit, one manual full rerun escalates and proceeds despite contention. A yielded run still `waiting` on the `falcor-ci` gate is never auto-retried and fails only at the 30-day approval timeout (gate job `steps=[]`, ~30 d duration): classify it yield + approval expiry, not a code failure, and don't rerun it; only a push or a maintainer's "Update branch" re-arms the gate, so report it up instead of pushing a refresh. Never cancel such a run either: a `cancelled` gate job makes `failed_only_because_priority_gate` false, so the retry helper rejects it for good; get the PR un-drafted, or re-dispatch once while human and MQ CI are quiet. Only the *automatic* retry helper expires (its `--lookback-hours` window). "No automatic rerun" ≠ "no rerun possible." Check `triggering_actor` before using any rerun as gate evidence (`github-actions[bot]` bypasses the throttle branch entirely).
- Reading a 30-day expiry `ci_failed`: count `falcor-build-approval-gate` as a third gate job (a check that accepts only `wait-for-human-priority` + `check-ci` misses it), and compare the webhook's `head_sha` with the PR's current `headRefOid` — if they differ, the run is superseded: no rerun, no edit, read `gh pr checks` on the current head. Before any re-dispatch, check `mergeable`; merge master (not rebase) if it conflicts.
- A `test-slang` job can be terminally failed while its parent run is non-terminal (`waiting`/`in_progress`) because `test-falcor` sits on a deployment-approval gate — then EVERY rerun form is refused ("already running"/"cannot be rerun") for sibling jobs in that SAME run. Scope: a `pull_request` run is per-PR (doesn't wedge other PRs); `merge_group` runs are rerunnable when `completed/failure`. Record `action:left` (non-terminal), don't keep retrying.
- Falcor gate latency + ~1-day build-artifact retention = unrecoverable: once the wait exceeds retention the job fails on a missing `slang-tests-*` artifact and rerunning just reproduces it. Only a fresh push, a retention bump, or faster approval fixes it. Classify `artifact-expiry-blocked (non-rerunnable)`, distinct from ordinary Falcor flakes.
- A Falcor approval gate that timed out to `conclusion: CANCELLED` is terminal, so it vanishes from the payload's `blockedChecks` while `mergeStateStatus` stays `BLOCKED`. Never call a PR clean from empty blocked-signal fields; run `gh pr checks` too. Classify `gate-wedged` (needs a human re-approve, not a rerun).
- Rank CI-gate fixes by failure DIRECTION, not completeness: a fails-safe lever wastes work; a fails-open lever ships a missed defect. A de-gate is only safe as a **conservative classifier** ("run it unless PROVABLY irrelevant"), never "guess whether it's needed."
- Re-check `isDraft` at the moment of CI dispatch — a human ready-flip between pushes turns the drafts-only manual dispatch into a cosmetic-red false alarm on top of the real `pull_request` run.
- Re-read the authoritative hold surface at the moment of a gated action, not at planning time — an always-loaded "always do X when C" rule fires without a deliberation gap and silently beats a superseding hold that lives in a split-out on-demand file.
- Never judge GitHub API quota from `/rate_limit` behind the OneCLI gateway — the credential is injected per-path, so `/rate_limit` reports the anonymous 60 bucket. Read `X-Ratelimit-Limit` from a real `/repos/...` response. The instrument that reports on quota is subject to the quota's plumbing.
- PR and merge-queue CI do not run `docs/generated/tests`. Two nightlies do: `Nightly Slang Test` / `agentic-tests` gates on them (against `_meta/expected-failures.txt`), and `Nightly Slang Coverage Test` runs them with failures tolerated. So a target-gated pass or an intentional emitter change can merge green and break the nightly; the fix is usually a CHECK refresh. Triage by failing target (`.slang.N` = Nth TEST line) and target guards in the green→red compare; a lost runner's logs 404 (BlobNotFound), so read `check-runs/<id>/annotations`. To find the breaking merge, bisect `slangc` from the `slang-tests-linux-x86_64-gcc-release` artifact of consecutive MQ runs instead of building.
- A nonzero `ci.yml` `status=waiting` count is the Falcor approval gate, not backpressure; it no longer reaches zero, so never gate a dispatch on it.

## Two states that look alike: waiting vs queued, skipped vs starved

The central trap is a status allowlist that folds "blocked on a human" in with "blocked on a resource." `queued` drains with time; `waiting` (environment approval) does not. `ci.yml`'s bot-priority retry helper, whose `ACTIVE_STATUSES` includes `waiting`, was jammed indefinitely: of seven "active" runs, two were `waiting` ~36h/~58h on an unactioned `falcor-ci` approval, so the "quiet" precondition was unreachable and every yielded bot run in the fleet went red ([GitHub Actions `waiting` ≠ queued — a human approval gate that jams CI retry](../learnings/1786404029507-github-actions-waiting-queued-it-s-a-human-approva.md)). `gh run list` renders both as pending; only `status` distinguishes them, so for any status-allowlist set, ask which members clear on their own. The symmetric read-error is `runner_name`: 37 jobs read "starved by the dead GPU pool" were all `skipped` by one 13-second gate job, while a real concurrent pool outage was causally unrelated ([empty runner_name does not distinguish starved from skipped](../learnings/1786438262793-empty-runner-name-does-not-distinguish-starved-by-.md)). Read `conclusion` first; the outage is FACT, the causal link HYPOTHESIS until the victim shows `queued`-with-no-runner. Conversely, a job cancelled while queued carries `started_at` but no runner: in a 3 h window with 0 Windows GPU runners, 24 phantom "T4 starts" appeared. To bound a pool outage, count starts with non-empty `runner_name` and confirm with `health_snapshots.jsonl` `runner_groups[...].total == 0` ([measure real job starts by runner name](../learnings/1792572260133-bisect-a-slang-nightly-regression-with-mq-build-ar.md)).

This retires the old rule "don't `gh workflow run ci.yml` until `ci.yml/runs?status=waiting` returns `total_count=0`": on 2026-09-27 shader-slang/slang had 73 `ci.yml` runs parked on `falcor-build-approval-gate` (human branches included), so the count cannot reach zero, yet newer runs still finish. Read the waiting job's name from `/actions/runs/<id>/jobs` before treating a waiting count as backpressure [ci.yml waiting-runs count can no longer reach zero (falcor-build-approval-gate)](../learnings/1790496460678-ci-yml-waiting-runs-count-can-no-longer-reach-zero.md).

## Reruns mutate in place; read the decision, not the rollup

A supervisor probe misfired on every retried run by asserting "same run id as last tick ⇒ nobody re-dispatched": a GHA rerun increments `run_attempt` on the **same** `databaseId` ([a GHA rerun mutates the same run id — key on (databaseId, run_attempt)](../learnings/1786454704637-a-gha-rerun-mutates-the-same-run-id-comparing-run-.md)). `runs/<id>/jobs` returns the latest attempt only (use `attempts/<n>/jobs`; the failure set can change under a stable id), and `run_started_at` ≠ `created_at` signals a rerun from one snapshot. Meta-lesson: when refusing the same request a third time, escalate the *mechanism* (name the unread field) instead of re-arguing; a suppression flag the instrument never consults is not a gate. A stale bot yield is NOT terminal: `wait-for-priority.py --max-yield-hours 12` ages from the fixed `created_at`, so past the ceiling one manual full rerun *escalates* and proceeds despite contention; only the automatic helper's `--lookback-hours 16` window expires ([a stale yielded run is NOT terminal — the gate escalates on any rerun](../learnings/1786440049067-slang-ci-priority-yield-a-stale-yielded-run-is-not.md)). Check `triggering_actor` before citing a rerun as gate evidence (`github-actions[bot]` fails `IS_THROTTLED_BOT` and bypasses the branch), and treat a helper's `conclusion: success` as proof only that it ran.

## The Falcor environment gate: rerun-blocker and artifact-expiry

The gate also keeps a run's top-level `status` at `queued` for days after 44 of 45 jobs have passed, so count jobs before calling such a run stuck, and never cancel or re-run it (see [reading CI state](ci-c-reading-ci-state.md)).

The `falcor-ci` gate produces two non-rerunnable states. First, while `test-falcor` is `waiting`, a sibling `test-slang` job can be `completed/failure` in a non-terminal run, and every rerun form is refused ("cannot be rerun; already running") ([Falcor approval gate makes intermittent test-slang reds un-rerunnable](../learnings/1786465690642-falcor-approval-gate-makes-intermittent-test-slang.md), [test-falcor waiting blocks gh run rerun for sibling jobs in the SAME PR run](../learnings/1786986200860-test-falcor-waiting-on-environment-gate-blocks-gh-.md)). A `pull_request` run is per-PR (check `event` before claiming blast radius); a `merge_group` run at `completed/failure` IS rerunnable with `--failed`. Record `action:left` ("run non-terminal (falcor gate)"), never force a whole-workflow rerun (violates "only rerun --failed"), and distinguish an echoed `echo "::error::…"` source line from a fired `##[error]`. Second, when the wait exceeds the ~1-day `slang-tests-*` artifact retention, the job fails on a missing artifact: **not a flake, not rerunnable**; only a fresh push, a retention bump or faster approval clears it ([Falcor gate latency compounds with 1-day artifact retention](../learnings/1787077102662-falcor-gate-latency-compounds-with-1-day-artifact-.md)). Classify `artifact-expiry-blocked (non-rerunnable)` and don't nudge the author (their next push clears it). When advising on flaky-rerun volume, rank levers by failure DIRECTION: a retry-on-transient wrapper fails safe, a gate-decouple is pure win, a de-gate fails OPEN, so it is acceptable only as a conservative classifier that runs Falcor unless the diff is PROVABLY shader-irrelevant ([CI-gate levers rank by failure DIRECTION, not completeness](../learnings/1786522092980-ci-gate-levers-rank-by-failure-direction-not-compl.md)).

A third state is invisible to the wake payload: a gate run that times out of WAITING completes with `conclusion: CANCELLED`, which is terminal, so it drops out of `blockedChecks` (only `{waiting, requested, pending}`) while `mergeStateStatus` stays `BLOCKED` and `gh pr checks` shows `fail`. A 2026-09-30 sweep wrongly marked #12716 and #13270 `resolved` on "blockedChecks empty, same head sha"; both were `gate-wedged`. Never infer clean from `blockedChecks:[] && onlyBlocked:false`; also run `gh pr checks` or read `statusCheckRollup` for CANCELLED/FAILURE. It needs a human re-approve, not a rerun ([Falcor gate CANCELLED (not WAITING) is invisible to blockedChecks](../learnings/1790755755702-falcor-gate-cancelled-not-waiting-is-invisible-to-.md)).

### Yielded bot runs and the 30-day approval expiry

A yielded bot `workflow_dispatch` run (`wait-for-human-priority` + `check-ci` failed) can sit at `falcor-build-approval-gate` in `waiting` and is then never retried. The gate `needs` only `filter` and uses `environment: falcor-ci`, so it waits for a human even after the yield and keeps the run open (one report saw `in_progress`; the API lists `waiting`), and `extras/ci/retry-yielded-bot-ci.py` reruns only `status=completed` runs created within `--lookback-hours 16` (near line 133). The run fails only at GitHub's 30-day approval timeout, when `gh run rerun` is refused ("created over a month ago") and a fresh dispatch restarts a 12 h aging clock that can yield and stick again ([falcor gate with no steps + 30-day duration = expired env approval](../learnings/1792735967556-falcor-build-approval-gate-with-no-steps-30-day-du.md), [never auto-retried](../learnings/1793362527224-a-yielded-bot-ci-run-held-open-by-a-falcor-ci-appr.md), [Bot CI on a draft can hang 30 days on the falcor-ci approval gate, and the yield-retry bot then never reruns it](../learnings/1793313053464-bot-ci-on-a-draft-can-hang-30-days-on-the-falcor-c.md)).

**Signature** (confirmed on #13333 run 36647612850, #13331 run 36639710975, #13356 run 36780286138, #13353 run 36776797458, 2026-10-29/30): a `ci_failed` webhook ~30 days after a bot dispatch; the gate job has `steps=[]` and `started_at`→`completed_at` exactly 30 d, its log often already `BlobNotFound`; `wait-for-human-priority` failed at "Stop yielded bot CI"; `check-ci` is the aggregate; all ~46 build/test jobs skipped; annotation "The deployment was rejected or didn't satisfy other protection rules" [slang CI: falcor-build-approval-gate "failure" 30 days later = expired environment approval, not a code failure](../learnings/1793318217230-slang-ci-falcor-build-approval-gate-failure-30-day.md). A yield check accepting only `wait-for-human-priority` + `check-ci` misses it, so count `falcor-build-approval-gate` as a third gate job ([a bot CI run on a draft PR can sit 30 days and then post ci_failed with no build/test run](../learnings/1793396267284-a-bot-ci-run-on-a-draft-pr-can-sit-30-days-and-the.md)). The webhook may name an OLD head: if its `head_sha` ≠ the PR's `headRefOid`, the run is superseded; don't rerun or edit, read `gh pr checks` on the current head ([stale github.ci_failed ~30 days after a bot workflow_dispatch](../learnings/1793394266543-stale-github-ci-failed-30-days-after-a-bot-workflo.md)).

**Handling.** Classify yield + approval expiry, not a code failure or flake: don't reproduce, don't `gh run rerun --failed`, and don't promise an automatic retry; the bot cannot approve `falcor-ci`. Only a new run re-arms the gate (a push, or a maintainer's "Update branch"), and a refresh just restarts the 30-day wait, so report it up as waiting on a human rather than pushing [slang CI falcor-build-approval-gate "fails" after 30 days unapproved, and a run older than a month can't be re-run](../learnings/1793306572297-slang-ci-falcor-build-approval-gate-fails-after-30.md). Re-dispatch (`gh workflow run ci.yml --ref <branch>`) only when fresh CI is actually needed, after `gh pr view --json mergeable`; a 30-day-old PR often conflicts, so `git merge origin/master` (no rebase) first ([never auto-retried](../learnings/1793362527224-a-yielded-bot-ci-run-held-open-by-a-falcor-ci-appr.md)). A push to a draft runs no builds (`pull_request` runs skip), so dispatch explicitly afterward (#13228) ([bot CI stuck 30 days on a pending falcor-ci approval](../learnings/1792723271790-bot-ci-on-shader-slang-slang-can-get-stuck-for-30-.md)). A non-draft bot PR's `pull_request` run also parks at the gate (`waiting`, no approver) after building and testing, and the helper counts it as active, so every bot ready-flip adds a permanent "active" run to bot-CI starvation ([GraphQL timelineItems(since:) totalCount ignores since; bot PRs park at the Falcor gate](../learnings/1792486262354-graphql-timelineitems-since-totalcount-ignores-sin.md)).

**Never cancel a yielded run still `waiting` at the gate to get it retried.** `fetch_recent_completed_runs` asks only for `status=completed`, and after a cancel `failed_only_because_priority_gate` returns False (the gate job is now `cancelled`), so the script rejects the run for good and the PR has no build/test result. On PR #14079 (2026-10-30) runs 40985513023 and 40991896824 were cancelled this way and never retried; this corrects an older note that cancelling makes a run retryable. For real CI on a yielded draft, ask a human to mark it ready (`pull_request` CI runs at full priority), or start one fresh dispatch at a time while no human or merge-queue CI is active, with a code commit at the head, because a dispatch diffs only `HEAD^1...HEAD` and a docs-only head skips every job while reporting success [Do not cancel a yielded bot CI run waiting at the falcor approval gate](../learnings/1793328120073-do-not-cancel-a-yielded-bot-ci-run-waiting-at-the-.md) [Do not cancel a yielded bot CI run on shader-slang/slang — it disqualifies the auto-retry](../learnings/1793328089059-do-not-cancel-a-yielded-bot-ci-run-on-shader-slang.md).

## Coverage the PR gate never runs: nightly-only agentic docs tests

Neither PR nor merge-queue CI runs `docs/generated/tests`. `Nightly Slang Test` / `agentic-tests` gates on them (known failures in `docs/generated/tests/_meta/expected-failures.txt`); `Nightly Slang Coverage Test` runs them via `run-coverage.sh --with-agentic-tests` but tolerates failures. So a change that breaks only those tests merges green and surfaces a day later, including an intentional emitter change such as #13569's WGSL comparison parens; the usual fix is a CHECK refresh (precedents #13454, #13731). Locally, `regenerate.py lint` shows 2 phantom YAML errors without PyYAML while the nightly reports 0, so diff lint output before/after your edit; `gh run view <run> --log-failed --job <id>` fetches a log when `actions/jobs/<id>/logs` returns empty ([docs/generated/tests runs in two nightlies, not one](../learnings/1792225630977-docs-generated-tests-runs-in-two-nightlies-not-one.md)). Example: on 2026-10-02 the nightly went red on `.../differentiation/reverse-mode-emitted-name-prefixes.slang`, CUDA and Metal legs only, after #13358 added a CUDA/Metal-only `expandAutodiffParameterContexts` pass. Triage by which targets fail (`.slang.N` = Nth `//TEST` line) and grep `compare/<green>...<red>` for target guards in `slang-emit.cpp`. `actions/runs?created=<ISO>..<ISO>` works through the OneCLI proxy with colons as `%3A`; a lost runner's logs return BlobNotFound, so read `check-runs/<id>/annotations` ([agentic docs tests only run nightly, so target-gated passes can merge red](../learnings/1790929124431-slang-ci-agentic-docs-tests-only-run-nightly-so-ta.md)).

To find the breaking merge, bisect merge-queue build artifacts instead of building. Every `merge_group` `CI` run uploads `slang-tests-linux-x86_64-gcc-release` (~365 MB): list it via `GET /repos/shader-slang/slang/actions/runs/<mq_run_id>/artifacts`, download `archive_download_url` through the proxy with no auth header (~5 s), unzip only `Release/bin/slangc*` and `Release/lib/*`, run with `LD_LIBRARY_PATH=<dir>/Release/lib`, and compare output across consecutive MQ heads. That found in minutes that #13724 broke the HLSL `#line` test. Only PR and MQ runs carry these artifacts ([bisect a nightly regression with MQ build artifacts](../learnings/1792572260133-bisect-a-slang-nightly-regression-with-mq-build-ar.md)). For bisecting published releases, see [release tarball repro and version bisect](slang-tooling-release-tarball-repro-and-version-bisect.md).

## Timing and instrument hygiene at the moment of action

Re-query `gh pr view --json isDraft` at the moment of a drafts-only manual `ci.yml` dispatch: a human ready-flip between pushes makes the manual run a cosmetic-red false alarm (only `wait-for-human-priority`+`check-ci` fail, builds skipped) on top of the real `pull_request` run ([re-check isDraft at the moment of CI dispatch](../learnings/1786606902247-re-check-isdraft-at-the-moment-of-ci-dispatch-a-hu.md)). Re-read the authoritative hold surface at the gated action itself: an always-loaded "always dispatch CI on drafts" rule fires with no deliberation gap and silently beats a superseding hold in a split-out on-demand file, so grep the hold surface for the action verb immediately before executing ([re-read the authoritative hold surface at a gated action](../learnings/1786467632283-re-read-the-authoritative-hold-surface-at-a-gated-.md)). Quota: behind the OneCLI gateway the credential is injected per-path, so `/rate_limit` reports the anonymous 60 bucket while `/repos/...` reports 6000; read `X-Ratelimit-Limit` off a real request. The tell is internal contradiction (`used:0` after ten calls); prefer a response header on a real request over a dedicated status endpoint ([never judge GitHub API quota from /rate_limit](../learnings/1786381107939-never-judge-github-api-quota-from-rate-limit-the-g.md)).
