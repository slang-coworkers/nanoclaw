# Slang Coercion & Overload Resolution

How Slang coerces values into generic containers (`Optional<T>` and friends) and how initializer-list coercion into a `vector<T,N>` routes through constructor overload resolution before the legacy component reader. (Witness tables and conformance live in [[wiki/concepts/slang-language-witness-and-conformance.md]]; visibility/layout/codegen surfaces live in [[wiki/concepts/slang-language-visibility-and-layout.md]]; generic specialization and inference live in [[wiki/concepts/slang-language-generics-and-type-system.md]].)

## TL;DR

- No covariant conversion of ANY generic type's arguments (`Optional<Derived>`↛`Optional<Base>`, arrays, tuples, user generics) — `_coerce` has no type-arg recursion. `Optional<opaque>` via a generic member escapes the E30902 front-end guard (T abstract at check time, concrete only at IR specialization).
- **`canCoerce`'s two conversion-cost caches must key on every cost-relevant input.** The linkage-global `BasicTypeKey` cache drops matrix layout (layout-only overloads always ambiguous); the per-module `TypePair` cache dropped l-value-ness (#13394: an earlier `inout` call poisons later by-value overload picks). Shapes the fast-path key can't encode (generic params) fall to the slow path, so check that key too.
- `vector<T,N>` is a struct with explicit composition ctors; init-list coercion tries ctor overload resolution FIRST, falls back to the tail-padding component reader only when no ctor matches the arg count — element count decides the path (`{1,2,3}`→`{1,2,3,0}` vs `{1,int2(2,3)}`→`{1,1,2,3}`).
- **Coherence is per-access, and heap resources cannot spell `globallycoherent`.** A `ResourceDescriptorHeap[i]`/`DescriptorHandle<T>` buffer rejects the modifier (E31201/E30076), and heap lowering never attaches `IRMemoryQualifierSetDecoration`. On SPIR-V use `loadCoherent`/`storeCoherent<4, MemoryScope::Device>(&buf[i])` with `-capability vk_mem_model` (without it: an E99997 assert; other targets: E36107).

## Optional<T> and Generic-Container Coercion

Two related gaps in how `Optional<T>` interacts with generics. **`Optional<T>` covariance is unsupported** — Slang does NOT implicitly convert `Optional<Derived>` to `Optional<Base>` even though the single-value `Derived → Base` existential boxing works, and this generalizes: there is no covariant conversion of *any* generic type's type arguments (not Optional, arrays, tuples, or user generics). The mechanism: `tryGetSubtypeWitness(Optional<Derived>, Optional<Base>)` returns null because the generic parameter `T` is invariant/opaque to the facet system, and the one generic-app path in `_coerce` is an equality-modulo-witness fallback that never *recurses coercion* into the args (the gap is an acknowledged TODO at `slang-check-inheritance.cpp`). Fix menu: a targeted bespoke `_coerce` branch for `Optional<A> → Optional<B>` gated on `tryGetSubtypeWitness(A,B)` (reuses existing MakeOptional/existential-boxing IR, no new op — mirrors how the codebase handles every other container coercion), vs a general per-parameter-variance model (language-design project). csyonghe wants it supported, jkwak treats it as nice-to-have sugar → maintainer-owned language decision, draft-only ([slang generic-container covariance unsupported — _coerce has no type-arg recursion (Optional Derived to Base, #7406)](../learnings/1783523269992-slang-generic-container-covariance-unsupported-coe.md)). **`Optional<opaque>` via a generic member escapes the E30902 guard** — returning `none` for `Optional<T>` from a generic struct's member accessor where T binds to a resource/opaque type (e.g. Texture2D) ICEs at SPIR-V emit (`E99997: Unhandled local inst: defaultConstruct`), while the same construct as a generic free function is caught cleanly with E30902. The diagnostic already exists but fires from three front-end sites all gated on `typeTransitivelyContainsOpaqueHandle`, which run at AST-check time when `Optional<T>` still has T *abstract* → the test is false; the concrete `Optional<Texture2D>` only materializes during IR generic specialization, after semantic checking, and nothing re-runs the usable-type check. Sibling #9932 (DescriptorHandle) is NOT a dup fix — DescriptorHandle has a representable zero so its fix made it COMPILE, whereas a bare resource has no default value and maintainers want a DIAGNOSTIC; fix homes are the dedicated `checkForOptionalNoneUsage` pass or `processMakeOptionalNone` (both have a sink) ([slang#7878 Optional-of-opaque via generic member escapes the E30902 front-end guard](../learnings/1783523243524-slang-7878-optional-of-opaque-via-generic-member-e.md)).

## Initializer-List → Vector Coercion Routes Through Ctor Overload Resolution First

`vector<T,N>` is a core-module `DeclRefType<StructDecl>` with EXPLICIT composition constructors (`core.meta.slang:2777-2805` — for `vector<T,4>`: `(T,T,T,T)`, `(vec2,T,T)`, `(T,vec2,T)`, `(T,T,vec2)`, `(vec2,vec2)`, `(vec3,T)`, `(T,vec3)` — crucially NO 3-parameter ctor). `_coerceInitializerList` (`slang-check-conversion.cpp:1378`) tries constructor overload resolution FIRST (`createInvokeExprForExplicitCtor`, :1403) and only falls back to the legacy component-wise reader `_readAggregateValueFromInitializerList` (:998-1053, fills left-to-right, tail-pads missing components with 0) when NO constructor matches the arg count. So the number of init-list *elements* decides which path fires, and that is the source of an observed inconsistency (#12093): `int4 v={1,2,3}` (3 args, no 3-arg ctor → legacy path → `{1,2,3,0}` tail-pad) vs `int4 v={1,int2(2,3)}` (2 args → only the `(vec2,vec2)` ctor applies → scalar `1` implicit-splats to `int2(1,1)` at cost `kConversionCost_ScalarToVector=2`, `slang-ast-support-types.h:172` → `{1,1,2,3}`). Verify GPU-free via `build/Debug/bin/slangi` (CPU interpreter — this is a front-end coercion bug). Disposition is design-gated (reporter skiminki-nv is a maintainer asking a semantics question; every fix changes compiling behavior): candidate fixes are (A) suppress scalar→vector splat when a vector composition ctor is selected from an init-list, (B) component-count flatten before ctor resolution, (C) disallow implicit under-fill. Same "vector is a struct, init-list routes through ctor overload resolution" area as #11730 ([init-list→vector (vec2,vec2) composition ctor splats scalars, diverges from tail-pad](../learnings/1784025263407-slang-init-list-vector-vec2-vec2-composition-ctor-.md)).

## Type-modifier add/drop policy already lives in `coerce`; coherence is access-based (proposal 031)

When a triage/design question asks "should modifier X be add/droppable during conversion, implicitly or explicitly?" (e.g. #13084 making `globallycoherent` a type modifier), the machinery already exists — don't propose it net-new. Type modifiers are `ModifiedType` (`slang-ast-type.h:1364`) wrapping a base type + `TypeModifierVal` subclasses (`UNormModifierVal`/`SNormModifierVal`/`NoDiffModifierVal`, `slang-ast-val.h:1185-1213`); the parser routes them onto the type via `_moveTypeModifiersToTypeExpr`, the modifier survives to IR as an `IRAttributedType` attr (`visitModifiedType`), and there is NO public-ABI surface (reflection peels it via `unwrapModifiedType`). Crucially, **`coerce` already owns the add/drop policy**: the `_coerce` modifier block (`slang-check-conversion.cpp:1940-2036`) calls `_canModifierBeAddedDuringCoercion` (:1572) / `_canModifierBeDroppedDuringCoercion` (:1596) per modifier then wraps via `createModifierCast` (unorm/snorm return true both ways = freely implicit); neither helper consults `CoercionSite` today but it's available, so "explicit-only drop" = return false for implicit and let the `CoercionSite::ExplicitCoercion` path permit it (a ~1-param thread). But **coherence is access-based, not type-based, in Slang today** for both pointers and resources: `globallycoherent`→`MemoryQualifierSetModifier`→`IRMemoryQualifierSetDecoration` on the resource var, and each load/store's coherent-ness is decided per-access at emit by `NeedToUseCoherentLoadOrStore` walking back to the var; for pointers the team *deliberately chose* per-operation coherence (`loadCoherent`/`storeCoherent` carrying `IRMemoryScopeAttr`) and explicitly BANNED `Ptr<coherent T>` (`external/spec/proposals/031-coherent-pointer-operations-and-access.md`, whose alternatives §2/§4/§5 are type-modifier variants, all rejected) — so proposing coherence-as-type-modifier for resources runs opposite to that decision. And coherence's target fulfillability is declaration-based on HLSL/GLSL/SPIR-V-GLSL450, per-access only on SPIR-V+Vulkan-memory-model, and **silently dropped entirely on Metal/WGSL/CUDA** (a pre-existing gap worth a diagnostic) — a type-modifier model changes front-end *policy* (can close the silent-drop leak uniformly at coerce) but adds no *expressiveness*, and an implicit "add coherence" conversion is only physically honorable on SPIR-V+VMM ([Slang type-modifier coercion is the reusable hook for add/drop policy; coherence is access-based (proposal 031)](../learnings/1789753912256-slang-type-modifier-coercion-is-the-reusable-hook-.md)).

The access-based model is also the only route for descriptor-heap resources today (master e6be8dcdd, #13440). `globallycoherent` cannot be spelled on a resource from `ResourceDescriptorHeap[i]` or `DescriptorHandle<T>`: a local gives E31201 from `isModifierAllowedOnDecl`, `DescriptorHandle<globallycoherent T>` gives E31201 from `checkTypeModifier` (#10852, parked pending the resource-type refactor), and a `static` global gives E30076. Neither heap lowering (`lowerDynamicResourceHeap` for the default `__slang_resource_heap`, `emitDescriptorHeapLoad` for spvDescriptorHeapEXT) attaches `IRMemoryQualifierSetDecoration`, so `NeedToUseCoherentLoadOrStore` never fires for heap buffers. What works on SPIR-V is proposal 031's per-access path: `loadCoherent<4, MemoryScope::Device>(&buf[i])` / `storeCoherent<4, MemoryScope::Device>(&buf[j], v)` (or `__getAddress(buf[i])`) with `-capability vk_mem_model`, which emits MakePointerVisible/Available|NonPrivatePointer and passes spirv-val on the default heap, on spvDescriptorHeapEXT and through a DescriptorHandle field. Without `vk_mem_model` it hits the E99997 assert at `slang-emit-spirv.cpp:8962` rather than a diagnostic, and other targets give E36107. DXC accepts the local `globallycoherent` heap form and annotates the DXIL handle, but drops the qualifier entirely in SPIR-V even with `-fspv-use-vulkan-memory-model` ([coherent access on a ResourceDescriptorHeap/DescriptorHandle buffer: loadCoherent/storeCoherent(&buf[i]) + vk_mem_model](../learnings/1791217879185-coherent-access-on-a-resourcedescriptorheap-descri.md)).

## Conversion-cost caches: both keys must carry every cost-relevant bit (matrix layout, #13394 l-value-ness)

`SemanticsVisitor::canCoerce` (slang-check-conversion.cpp ~3200) consults one of two caches and returns the cached cost *before* it reaches `toType->equals(fromType)`, so a key that omits any input `_coerce` prices on silently reuses the first cost computed for that key, exact matches included. The **linkage-global `conversionCostCache`** is keyed by `BasicTypeKey` (`makeBasicTypeKey`, slang-check-impl.h:171-185) and covers only constant-shape scalars, vectors and matrices; it has an `isLValue` bit but builds the rest from base type, rows and columns only, leaving out `MatrixExpressionType::getLayout()`. So whichever matrix→matrix cost was computed first for a shape (e.g. `kConversionCost_MatrixLayout = 5`) is reused for every layout pair, and `pick(m: row_major float2x3)` + `pick(m: column_major float2x3)` is E39999 "ambiguous" even for an exactly row_major argument; both candidates also print as `func pick(float2x3)` because `_toTextOverride` omits the layout. Prototype fix: return `BasicTypeKey::invalid()` for a matrix whose layout is not Unknown(0), which resolves these with no slang-test regressions in the subsets run ([global conversion-cost cache key ignores matrix layout](../learnings/1790917787458-slang-s-global-conversion-cost-cache-key-ignores-m.md)). Everything else (e.g. generic `vector<…,N>`) goes to the **per-module `m_typeConversionCostCache`**, which was keyed by `TypePair{to, from}` with NO l-value bit. `_coerce` adds `kConversionCost_LValueCast` (800) for an l-value source, and that flag comes from the *parameter* (`coerceArgToParam`), so an earlier `inout` call caches an inflated cost and a later by-value call to an overload set picks the wrong overload. It regressed in v2026.1.2 with 45774a4486 (#9780); the #13394 fix keys the cache with `ConversionCostKey{toType, fromType, fromIsLValue}` ([per-module key must include l-value-ness](../learnings/1790942037348-slang-conversion-cost-cache-per-module-key-must-in.md)). The two are distinct key omissions in the same lookup, not one bug. Lesson from #13394: when a reviewer proposes "encode X into the fast-path key", check the shapes that *can't* be encoded (generic params); they fall back to the slow path, and the bug is usually in the slow path's key. Layout is also dropped by mangling (slang-mangle.cpp:217-224, #13383: layout-only overloads silently link to one body) and by the type printer, while `Type::equals` does distinguish layouts, so a matrix-layout bug hunt should check all three; redeclaration matching for layout-only signatures is on [[wiki/concepts/slang-compiler-frontend-and-checking.md]]. Tooling trap from the same fix: `./extras/formatting.sh` silently skips C++ when clang-format is not on PATH (use `PATH=/usr/lib/llvm-17/bin:$PATH`).
