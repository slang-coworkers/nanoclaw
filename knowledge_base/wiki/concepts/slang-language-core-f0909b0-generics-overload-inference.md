## TL;DR

Slang's generic/overload machinery has several structural traps that recur across bugs:

- **Two constraint-discharge paths exist and disagree.** `TryCheckOverloadCandidateConstraints` uses a fixpoint worklist solver (`trySolveGenericArguments`) only for the *outermost* generic; nested generics fall back to a **linear, declaration-order** pass that cannot see witnesses established by a later constraint. This makes `where`-constraint order load-bearing on nested generics.
- **OverloadRank is DEAD for generic-vs-generic disambiguation.** `CompareOverloadCandidates` early-returns 0 when either candidate is `Generic`/`UnspecializedGeneric`, skipping both scope-rank and overload-rank. So `[OverloadRank(n)]` in `.meta.slang` never applies between two generic overloads.
- **Slang does not rank overloads by constraint specificity.** `compareOverloadCandidateSpecificity` only counts generic params. Two overloads differing *only* in a constraint bound (e.g. `__BuiltinArithmeticType` vs `ICoopElement`) are ambiguous whenever the discriminating type param is specified explicitly rather than inferred from an argument. Always test the **fully-explicit-generic-args** call, not just the inferred form — prefer a single widened bound.
- **Unsuffixed int literals commit to `int` at parse time** (no deferred/contextual literal type). In generic inference the literal-sourced `Element=int` is solved *before* the conformance witness runs, so a conformer's `uint` is never offered — this is an **ordering / eager-commit** defect, not a type-join tie-break defect (`TryJoinTypes(int,uint)` already returns `uint`).
- **`[ForwardDerivativeOf]` resolution routes through ordinary overload resolution** over imaginary args and inherits both blind spots above, so a shaped derivative + a catch-all primal → ambiguous → E31148.
- **Constraint-failed generic candidates are status-pruned** (status 0 = worst) before the multi-candidate note loop, so E39999 omits their useful reason (the reason *is* now captured per-candidate in `genericInferenceFailure`).
- **ABI-additive claims for implied-constraint synthesis need two conditions** (exclude optional constraints; skip already-satisfiable) and three cache invalidations.
- HLSL `template<...>` reuses ~90% of the generics machinery; net-new risk is the duck-typed-at-instantiation decl, the instance registry, and same-module rejection. A **base-class split** (`GenericDecl → ParameterizedDecl`) breaks invariants the derived class silently held (never-null `inner`).

## Two constraint-discharge paths and declaration-order sensitivity

When the *declaration order* of generic `where` constraints decides whether code compiles, the prime suspect is the split inside `TryCheckOverloadCandidateConstraints` (`slang-check-overload.cpp:1157`): a fixpoint worklist solver `trySolveGenericArguments` runs only when `genericIsOutermost`, correctly blocking each witness constraint until its dependencies are ready via `hasUnreadyDependenciesForWitnessConstraint`; **nested** generics fall through to a per-constraint **linear pass** (`:1260`) that visits `getMembers()` in strict declaration order and cannot see witnesses established later [where-constraint order](../learnings/1787226105001-generic-where-constraint-declaration-order-sensiti.md). PR #11210 consolidated solving into the worklist and #11368 made it order-agnostic, but only on the outermost path — the nested linear fallback remains order-sensitive. The "does not conform" message here is `TypeArgumentDoesNotConformToInterface` (now in `diagnostics/type-errors.lua`), emitted at `:1303` (linear reject) and `:1598` (solver).

## Overload ranking gaps: OverloadRank, specificity, constraint-only splits

Two independent facts make constraint-based disambiguation of generics unreliable. First, **`[OverloadRank]` is unreachable for generic candidates**: `CompareOverloadCandidates` early-returns 0 at lines 2420–2426 when either candidate flavor is `Generic`/`UnspecializedGeneric`, skipping `getScopeRank` and `getOverloadRank` [OverloadRank unreachable](../learnings/1787965552599-slang-generic-overload-overloadrank-is-unreachable.md). So the "glsl beats core" preference encoded in `[OverloadRank(15)]` vs negative core rank never applies between generic operator overloads — the *only* thing separating them is the generic-param-count block (`:2214-2219`), which is why removing that tie-breaker (proposed for `-std 202c`) makes the core/GLSL builtin operator calls ambiguous.

Second, **Slang does not rank by constraint specificity** — `slang-check-overload.cpp:2201` explicitly does not implement it. So two overloads differing only in a type param's bound are distinguished only through argument matching [constraint-only split needs inferable param](../learnings/1787359986220-slang-overload-split-by-constraint-only-disambigua.md). If the discriminating param is inferable from an argument, the split resolves; if it is explicit-only (`coopVecLoad<4,half>(byteAddressBuffer)`), it is E39999 ambiguous. The follow-up refinement is sharper still: even an *inferable* param becomes ambiguous once the caller spells **all** generic args explicitly (`coopVecLoad<4,float,DefaultDataLayout>(sbuf)`), because argument-matching no longer discriminates [fully-explicit split regresses](../learnings/1787395523470-coopvecload-two-overload-split-regresses-fully-exp.md). General rule: before splitting an API into constraint-only-differing overloads, test the fully-explicit call; prefer a single widened bound (or `[OverloadRank]` only if both must coexist — and note that rank is itself dead for generics).

## `[ForwardDerivativeOf]` inherits the overload blind spots

A `[ForwardDerivativeOf(f)]` whose derivative has a *shaped* generic signature (`vector<T,N>`) fails E31148 when the primal `f` also has an applicable *catch-all* generic overload [ForwardDerivativeOf shaped-vs-catchall](../learnings/1787954897660-slang-forwardderivativeof-shaped-vs-catchall-gener.md). This is two coupled gaps: (1) `checkDerivativeOfAttributeImpl` cannot bind a derivative whose signature is a constrained subset of a catch-all primal's (the "inverse generic argument solving" is unimplemented, `:19082`); (2) derivative resolution routes through ordinary overload resolution, where `compareOverloadCandidateSpecificity` ignores constraint tightness and `CompareOverloadCandidates` early-returns a tie for generic flavors — so the two `pow` overloads tie/attach to the catch-all, then gap (1) fails the rebind. **Decisive probe:** narrow the catch-all so it is not applicable to `vector<T,N>` (`<T:IFloat>` → `<T:__BuiltinFloatingPointType>`, since `float3` conforms to `IFloat` but not the builtin scalar interface) — the config then compiles clean, distinguishing gap (2) from a typo. Adding a public generic wrapper beside a scalar/vector/matrix builtin breaks the generated shaped derivative registrations in `diff.meta.slang` at core-module load.

## Literal inference is an ordering defect, not a tie-break defect

`acceptBox(box, 3)` failing `UIntBox does not conform to IBox<int>` (for a `struct UIntBox : IBox<uint>`) is the canonical case: unsuffixed decimal literals commit to `BaseType::Int` at parse time (`_determineIntegerLiteralType`; there is no leptonic/contextual literal type) [unsuffixed literal commits to int](../learnings/1787674982285-slang-generic-inference-unsuffixed-int-literal-com.md). The `GenericArgumentSolver` collects discovered ordinary constraints (`Element=int`) *before* the witness constraint, solves `Element=int` first, then substitutes it into the witness supertype (`IBox<int>`), so `_tryJoinTypeWithInterface(UIntBox, IBox<int>)` unifies `IBox<uint>` vs `IBox<int>` where neither operand is a generic param → nothing binds → `Element=uint` is never discovered. The companion atom nails the trap: this *looks* like a type-join tie-break (int vs uint) but is not — `TryJoinTypes(int,uint)` already returns `uint` (conversion costs 300>250); the two facts are simply never co-live because the literal solves first and blocks discovery [literal-vs-conformance is ordering](../learnings/1787675243000-slang-12753-literal-vs-conformance-generic-inferen.md). Fix direction: defer/deprioritize literal-sourced ordinary constraints below witness inference (keeping the arg `DefaultSubstitutionArg` until the witness runs), or implement a real deferred-representability literal type. Meta-lesson: before "fixing the join" in a generic-inference conflict, check whether both constraints are even co-live.

## Constraint-failed candidates are status-pruned out of diagnostics

When an overload set contains a generic candidate whose conformance constraint is unsatisfied, the "no overload applicable" E39999 omits it and its constraint, listing only concrete overloads — remove the concrete overloads and the useful E38029 appears [overload notes drop constraint-failed generics](../learnings/1788895654799-slang-overload-notes-drop-constraint-failed-generi.md). The failure reason *is* now captured per-candidate (`OverloadCandidate::genericInferenceFailure`, a tagged union), updating the older #12035/#7857 learning. The real gap is two-part: (1) the candidate is assigned `Status::GenericArgumentInferenceFailed` = enum 0 = worst, so `CompareOverloadCandidates` ranks it below concrete arg-mismatch candidates and `AddOverloadCandidateInner` drops it before it enters `bestCandidates`; (2) the multi-candidate note loop iterates only `bestCandidates` and never reads `genericInferenceFailure` (the single-candidate `CompleteOverloadCandidate` path does — which is why removing the concretes surfaces the diagnostic). Recommended low-risk fix: retain dropped candidates in a diagnostics-only side list and reuse `CompleteOverloadCandidate`'s switch; do **not** raise the candidate status (status is the first selection tiebreak everywhere).

## Implied-constraint synthesis: additive is necessary-but-not-sufficient

A follow-up correction to an "additive ⇒ non-breaking" ABI claim for implied-constraint synthesis: two conditions must **both** hold or a currently-compiling program's mangle changes [implied-constraint additive needs two conditions](../learnings/1787958848031-implied-constraint-abi-additive-claim-needs-two-co.md). (1) Exclude OPTIONAL constraints from inference — an optional bound already compiles today via `NoneWitness`, so inferring a required `T:IFoo` from it strengthens a valid signature. (2) Skip constraints already satisfiable by existing/transitive evidence, using `isSubtype(...NoCaching)` then `isTypeEqualityWitness` for equality (a bare identity test misses `T==V, V==U`). Three distinct caches must be invalidated when you `addDirectMemberDecl` a synthesized `GenericTypeConstraintDecl`: the subtype-witness negative cache (avoid poisoning via `NoCaching`), the default-substitution-args cache (`_cachedArgsForDefaultSubstitution.clear()`), and the inheritance-info cache (epoch-gated on *extension* registration, so a constraint-member-add does not bump the epoch → explicit `.remove()`). Discovery must be structural, not a `JustTrying` resolve (which returns false and only suppresses the diagnostic).

## HLSL templates: reuse the generics machinery; watch the base-class split

For the deliberately-limited HLSL `template<...>` compat feature (#12550, spec#61), the scariest requirements already exist and should be reused, not rebuilt: argument inference / fixpoint solver (`inferGenericArguments`, `trySolveGenericArguments`), SFINAE-like silent candidate rejection (`OverloadResolveContext::Mode::JustTrying` + discardable `DiagnosticSink`), committed-instance dedup (ASTBuilder hash-consing via `getGenericAppDeclRef`), and a parser that is ~70% there (`ParseGenericDeclImpl`; `template` is not reserved) [HLSL-templates reuse map](../learnings/1786742192588-slang-limited-hlsl-templates-12550-reuse-map-the-h.md). The genuinely net-new risk: a template-flavored decl distinct from `GenericDecl` (out of ordinary lookup, duck-typed at instantiation), a durable instance registry preserving the lexical parent chain (`ASTCloner::cloneSyntaxNode` does *not* preserve it), a specialization-time expansion budget, and the same-module rejection point.

STEP 1 of that feature reparents the AST node onto a new base and generalizes consumers from `as<GenericDecl>` to `as<ParameterizedDecl>` — the highest-yield bug is an **invariant the derived class silently maintained that the new sibling does not** [base-class split null-inner](../learnings/1786869369727-base-class-split-genericdecl-parameterizeddecl-sur.md). `GenericDecl::inner` is never null, but the new `TemplateDecl` sibling can have `inner==null` (EOF parse), and two generalized consumers then deref it → slangc/language-server crash. The principled producer-side fix restores the never-null invariant (synthesize `EmptyDecl`) rather than adding per-consumer null guards. Also durable: a `//CHECK-NOT: error` on a template positive-parse test is shallow because a `TemplateDecl`'s inner is deliberately kept out of the member list and never semantically checked in step 1.

## Two-phase constraint-parameter emission leaks placeholder types

Fixing an order-dependency in `emitGenericDecl` by splitting constraint-parameter emission into a predeclare pass (placeholder type + `setValue`) and a finalize pass (`setFullType`) leaks the placeholder into composite witnesses: a sibling constraint's supertype lowering a `TypePackSubtypeWitness` reads each element witness param's *current* `getFullType()` and bakes it into a permanent `IRTypePack`; a later `setFullType` does not update the already-constructed pack [two-phase param predeclare leaks placeholder](../learnings/1787268164470-two-phase-ir-param-predeclare-leaks-placeholder-ty.md). Scalar witnesses are safe (the caller supplies the witness-table type); composite/pack witnesses snapshot the element type. Fix: derive composite-witness element types from the semantic witness supertype, not the param's stored IR type. Also note `isGenericConstraintParameterDecl` is true for equality constraints too, so a `T == A & B` reaches the finalizer with a conjunction supertype when `-disable-non-essential-validations` is set — a `SLANG_RELEASE_ASSERT(!conjunction)` there is unsafe (equality conjunctions are not flattened at header checking).
