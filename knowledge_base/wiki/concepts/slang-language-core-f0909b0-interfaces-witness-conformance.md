## TL;DR

Conformance bugs in Slang cluster around a few mechanisms. Keep these front of mind:

- **Interface self-conformance (`isSubtype(IFoo, IFoo)`) is load-bearing**, not just a bug — most dynamic-dispatch/existential machinery relies on it (`Optional<IFoo>`, `IFoo[]`, autodiff materials). Tim Foley's `dyn IFoo` split removes it, and forming `dyn IFoo` everywhere breaks 68+ base files in predictable buckets. Isolate to explicit generic-arg sites + required conformance constraints.
- **Witness tables can legitimately have duplicate requirement keys** (autodiff DiffPair path relies on `findWitnessTableEntry` returning the first match). Do NOT assert uniqueness.
- **Associated-type resolution reads the conforming type's CANONICAL witness table.** Order-of-conformance-checking and canonical-witness *ownership* bugs (not the inheritance DAG) produce spurious `E38029`/`E38106`. `_getInheritanceInfo` caches a frame only when nothing was skipped, so an `isBeingChecked()` skip of an unrelated sibling leaves a partial, uncached frame that recomputes wrong.
- **Inherited DEFAULT methods that call sibling `this` methods** crash (`slang-ir.cpp` `_replaceInstUsesWith(null)`) via a **producer** bug: a stale `conformingWitness` context field bakes the wrong (derived) witness table into `specialize(defaultImpl, ...)`. One producer fix resolves both static (#12814) and dynamic (#11487) variants. Consumer-side null-guards / closure walks are the "do not mask" anti-pattern.
- **Un-named requirement keys collide on the empty mangled name** during witness-table clone deferral (equality-constraint keys are a second un-named class beyond `IRBuiltinRequirementKey`).
- **`tryLookUpRequirementWitness` only handles the `InheritanceDecl` declRef arm**, returning `none` for a `LookupDeclRef` base — but this has no natural `.slang` repro because normal compilation resolves through `tryResolve`/`getUnspecializedLookupRec` which handles all three shapes.
- A **redeclared (shadowed) inherited interface member** returns a ≥2-candidate overload; the member-access-base path filters out all interface-parented candidates and empties the set → ErrorType with no diagnostic → E99997 ICE.
- A lazily-synthesized conformance (e.g. enum `__EnumType`) plus a cache invalidated only by a *different* event (extension epochs) is an order-dependent false-negative trap.
- A **function-local** type conforming to an interface whose requirement is a *constrained* generic method crashes in `doesGenericSignatureMatchRequirement` (`getSub` returns null because the constraint decl never reached `SignatureChecked`) — another read-before-checked ordering bug, fixed with `ensureDecl(constraintDecl, SignatureChecked)`, not a consumer null-guard. Related discipline: `SLANG_ASSERT` is `SLANG_ASSUME`/UB in release, so use `SLANG_RELEASE_ASSERT` for a real guard on out-of-contract input.

## Self-conformance and the `dyn IFoo` split

`isSubtype(IFoo, IFoo)` succeeding is relied upon by most dynamic-dispatch/existential code — passing an interface type as a generic argument (`Optional<IFoo>`, structured buffers of interfaces, autodiff materials) works via self-conformance [interface self-conformance is load-bearing](../learnings/1786772419196-interface-self-conformance-is-load-bearing-for-sla.md). Tim Foley's proposed AST-level `ExistentialType` makes `ExistentialType(IFoo)` NOT conform to `IFoo`; measured on base b4853080d1, forming `dyn IFoo` at all explicit generic-argument sites and removing self-conformance broke 68 base files (dynamic-dispatch 51, autodiff 11, interfaces 5, generics 1). The low-churn slice that validates the ill-formed case without the blast radius: form the existential *only* at explicit generic-type-argument sites and *only* for required conformance-constrained params (skip equality and `where optional T:IFoo`). An `ExistentialType` node must canonicalize to a distinct node (never the wrapped interface), because `Val::equals` compares resolved-pointer identity — collapsing them re-enables self-conformance.

The companion atom maps the front-end machinery that must become `ExistentialType`-aware: the chokepoint is `CoerceToProperTypeImpl` (the single funnel for var/field/param/return/generic-arg/element positions — "an interface is not a proper type, an existential is"), but exempt the constraint supertype re-entry (use the already-resolved `constraintParam->sup.type`, else `ITexelElement`→`dyn ITexelElement` breaks the core-module build) [forming dyn IFoo needs auto-unboxing](../learnings/1786781226502-slang-forming-dyn-ifoo-everywhere-needs-auto-unbox.md). Breakage buckets are the deferred existential machinery: member access needs `maybeOpenExistential` to recognize `ExistentialType`; make-existential coercion (`X → dyn IFoo`) is unimplemented; conjunctions checked per-operand produce `(dyn IFoo)&(dyn IBar)`; autodiff type mangling and `tryGetDifferentialType` have no `ExistentialType` case. Note E38029 (front-end reflexive-conformance reject) is distinct from the IR-pass E33180 whose `isExistentialDerived` already classifies both bare and extracted existential types.

## Duplicate requirement keys are legitimate

While fixing a generic enum-extension conformance merging with int's conformance (#12540), an added guard in `findWitnessTableEntry` asserting at-most-one-entry-per-key was **wrong** — the autodiff differential-pair path legitimately produces duplicate keys and relies on first-match (the `matrix-row-major-dedup.slang` test fired the assert) [duplicate requirement keys are legitimate](../learnings/1786802981602-witness-tables-can-legitimately-have-duplicate-req.md). The #12540 fix is narrower: give each conformance witness table an identity operand (its mangled name) so semantically-distinct conformances don't dedup, without touching first-match. Method note: the revert-drill caught this — an advisory guard that fires on a suite you didn't touch means checking whether the invariant is real on pristine master first.

## Order-dependent associated-type resolution: the #12659 / #12874 family

Several bugs share a root: resolving an inherited requirement's associated-type return reads the conforming type's **canonical** witness table, and that table is null/partial if built in the wrong order. In #12659, an interface with sibling `associatedtype ... : IFirst<Context>` bounds fails the *second* use of `Context` as a generic arg: `tryAddConstraintBase` skips a constraint when `checkState.isBeingChecked()` (a cycle-breaker), so while the first sibling is mid-check the unrelated `Context : IContext` constraint is skipped, producing a partial facet list that `_getInheritanceInfo` refuses to cache (it caches only when nothing was skipped) → recomputed-wrong → E38029 [assoc-type as generic arg loses witness](../learnings/1787248050437-assoc-type-as-generic-arg-loses-conformance-witnes.md). Fix direction: scope the `isBeingChecked()` skip to the constraint's own subject. A closely related, *pre-existing* re-entrancy in `tryResolveConstraintTypes` resolves both endpoints of an equality eagerly and defers only a `MemberExpr`, not a `GenericAppExpr`, so a generic-app sup `Wrapper<Context>` re-enters `_calcInheritanceInfo(Context)` while in-progress → spurious E38029 [equality-constraint generic-app re-entrancy](../learnings/1788291891545-slang-inheritance-equality-constraint-generic-app-.md). Note an *interface*-typed equality sup is independently rejected E30404, so use a generic-app struct sup to demonstrate the re-entrancy.

#12822 shows the emission site can be a fall-through symptom: `R<Container> value;` with `where T.Element == ConcreteElement` is rejected E38029 at **module scope** but passes as a **local var** [assoc-type projection not reduced at module scope](../learnings/1787950486759-slang-12822-assoc-type-projection-not-reduced-at-m.md). The equality-blind linear pass IS the emission site, but gating it on `isEqualityConstraint` only fixes the *message*, not the rejection — the actual root cause is that the associated-type projection `Container.Element` is not reduced to `ConcreteElement` at module-scope validation (in a function body the worklist solver reduces it and never reaches the linear pass). The triage lesson: run the pass/fail isolation matrix even when a prior learning names an "obvious" emission-site defect.

The #12874 case first looked like a witness-table **storage↔resolution asymmetry**: a struct conforming to `IProvider & IShape & ISelfShape` (IShape redundant) fails to resolve an assoc-type requirement (`Item` left as `Value.Item` → E38106), with `_mergeFacetLists` preferring the lowest-directness facet and non-canonical paths storing only a bare `RequirementWitness(...)` of `Flavor::val` that `getUnspecializedLookupRec` rejects [redundant interface base breaks assoc-type witness (superseded)](../learnings/1788298656584-slang-conformance-redundant-interface-base-breaks-.md). But this was **superseded**: a full fixer investigation proved the real root cause is conformance-check **ORDER** — bases are checked in declaration order (`checkAggTypeConformance`/`checkExtensionConformance`), and if the decl owning the canonical path is checked *after* the requirement, its `witnessTable` is null → E38106; the storage/resolution asymmetry and the `val`-reference were red herrings [correction: #12874 is conformance-check ordering](../learnings/1788307346729-correction-to-12874-root-cause-it-is-conformance-c.md). The independent third atom on this bug adds the critical safety constraint: the "obvious" fix of reordering bases base-interfaces-first (topological DAG sort) is **UNSOUND** — it regresses a diamond `IDerived & ICanonical & INeedsShape` by demoting the canonical owner behind a consumer; the real dependency is **canonical-witness ownership** (directness + declaration-order tie-break), not the sibling inheritance DAG [conformance-order bugs assoc-type E38106](../learnings/1788307210066-slang-conformance-order-bugs-assoc-type-e38106-reo.md). Correct direction: phased/on-demand witness construction (`ensureDecl(sub, ReadyForConformances)` + re-resolve), with the caveat that a sibling conformance needs *targeted per-conformance* readiness (whole-type `ensureDecl(self)` mid-check → `CyclicReference`). Prove any ordering fix against a canonical-owner-demoting diamond counter-example.

## Function-local conformance crashes when the requirement is a constrained generic method

A function-local `struct Op : IOp` whose interface requirement is a **constrained** generic method (`int apply<T:__BuiltinArithmeticType>(T)`) SIGSEGVs slangc in the **front-end** — target-independent, with no diagnostic — while moving `Op` to module scope, dropping `: IOp`, or dropping the constraint each makes it compile; the target-independence is the tell that this is not an emit/IR bug, so don't chase the emitters [function-local conformance with a constrained generic method crashes (null getSub)](../learnings/1789014792514-function-local-interface-conformance-with-constrai.md). It is the same read-before-checked ordering hazard as the #12659/#12874 family, one level up: `doesGenericSignatureMatchRequirement` (`slang-check-decl.cpp` ~6152) calls `getSub(m_astBuilder, satisfyingConstraintDeclRef)`, but `getSub`/`getSup` on a `GenericTypeConstraintDecl` return non-null only after the decl reaches `DeclCheckState::SignatureChecked`. A module-scope type's members' generic constraints are advanced before `ReadyForConformances`; a **function-local** type nested in a function body gets no such guarantee, so `getSub` returns NULL. `Val::equals` (`slang-ast-base.h:436`, `this == val || (val && this->resolve() == val->resolve())`) guards only the ARGUMENT, not the RECEIVER, so a null `satisfyingSubType->resolve()` segfaults. The principled fix is producer/ordering — `ensureDecl(satisfyingConstraintDecl, DeclCheckState::SignatureChecked)` before reading getSub/getSup (the same function already does exactly this in its And-type-flattening path) — not a consumer null-guard, because module-scope compiles prove the conformance is a supported feature.

Two invariants generalize from that fix [SLANG_ASSERT is SLANG_ASSUME (UB) in release; ensureDecl-before-enumeration for constraint flattening](../learnings/1789019735283-slang-assert-is-slang-assume-ub-in-release-ensured.md). First, `SLANG_ASSERT` is **not** a fail-loud check in release: `source/core/slang-common.h` (~L371) defines it to `SLANG_ASSUME` (`[[assume]]`/`__builtin_assume`/`__assume`), so asserting a value that *can* be false is undefined behavior in release, not a checked abort — use `SLANG_RELEASE_ASSERT` (runs `handleAssert(..., fatal=true)` in both configs) for a genuine guard on out-of-contract input. Second, `DeclCheckState::SignatureChecked` both populates a constraint decl's sub/sup AND flattens conjunction bounds (`T : A & B`) into per-conjunct members, so any consumer reading `getSub`/`getSup`/`getFromType`/`getToType` must `ensureDecl(constraintDecl, SignatureChecked)` first — advancing the **constraint decls only**, never the enclosing type (that re-enters the in-progress conformance check → `CyclicReference`) — and must do it **before enumerating/counting** the generic's members, not just before the comparison: a late pass leaves the member snapshot stale and can silently accept an over-constrained local impl against a weaker requirement (a soundness bug, not just the crash). Diagnostic tests that also emit a `note:` need `//DIAGNOSTIC_TEST:SIMPLE(diag=CHECK,non-exhaustive):` (the default exhaustive mode fails on any unmatched note/caret line).

## The `tryLookUpRequirementWitness` LookupDeclRef gap has no natural repro

`tryLookUpRequirementWitness` returns `Flavor::none` when a `DeclaredSubtypeWitness`'s declRef base is a `LookupDeclRef` (an associated conformance reached *through* another witness), because the branch only handles `.as<InheritanceDecl>()` [tryLookUpRequirementWitness LookupDeclRef gap](../learnings/1787675479061-trylookuprequirementwitness-lookupdeclref-gap-has-.md). Twelve natural `.slang` shapes all compile fine on unfixed master, because a `LookupDeclRef` normally resolves through `_resolveImplOverride → tryResolve → getUnspecializedLookupRec`, which handles all three declRef shapes; the buggy direct call fires only from an internal resolver on a still-symbolic witness chain (only the #12691 structural-RT draft branch exercises it). For such "internal-resolver-only" gaps, don't hunt a `.slang` repro; the fix (delegate the LookupDeclRef arm to `getUnspecializedLookupRec`/`specializeLookedUpRec`) collapses the drift where `syntax.cpp` knew 1 of 3 declRef shapes and `decl-ref.cpp` knew all 3.

## Inherited-default-method crash: one producer root cause

A static generic `combine<Value>` calling a DEFAULT method (`combineInPlace`) declared on base `IBase`, where `Value : IDerived : IBase`, aborts `slang-ir.cpp(9011): other` (`_replaceInstUsesWith(null)`) [inherited default-method static specialization crash](../learnings/1787932414310-inherited-default-method-static-specialization-cra.md). Via `-dump-ir`: the nested `Value:IBase` witness entry is `specialize(defaultImplGeneric, Value, <Value:IDerived table>)` — the WRONG (outer, IDerived) table, whose inner `lookupWitness(IBase.combine)` misses → null → crash. The precise mechanism: `slang-check-decl.cpp:11298` sets `context.conformingWitness = subIsSuperWitness` once and never refreshes it; the nested recursion threads the correct `subIsReqWitness` only as a *parameter*, while `findDefaultInterfaceImpl` reads the STALE context field. The companion atom confirms this one producer fix resolves **both** the static (#12814) and dynamic (#11487) variants because it sits upstream of the static/dynamic split, and stresses that #11487's earlier consumer-side patch (`findWitnessTableEntryInInheritanceClosure`) NEVER merged and is the "do not mask" anti-pattern [inherited default-method: static and dynamic share one root cause](../learnings/1787937170959-inherited-default-method-witness-assert-static-128.md). Two flat-lookup consumers behave differently: `maybeSpecializeWitnessLookup` is null-guarded, but `specializeWitnessLookup` (`slang-ir-translate.cpp:348`) is unguarded and fires the assert — check which one is on the crash path. Reproduce/verify tip: CPU-independent, any `-target`; leave `SLANG_ASSERT` unset (`release-assert-only` skips the debug assert and produces silently wrong IR).

## Witness-table clone deferral collides on the empty mangled name

`slangc` aborting `slang-dictionary.h(325): The key already exists` while compiling generic code with associated-type **equality** constraints in a diamond is a back-end IR bug [witness-table clone deferral collides on empty name](../learnings/1787936873954-slang-witness-table-clone-deferral-collides-on-emp.md). Two disambiguation tricks made triage fast: the assert **line** tells you the container (`:325` = plain `Dictionary`, not the semantic checker's `OrderedDictionary` at `:576`), and `-dump-ir` printing the whole lowered module localizes the crash to `linkIR` (before any named pass). Root cause: `cloneWitnessTableImpl` defers entries keyed by `getMangledName(requirementKey)`, which returns an empty slice for un-named keys; equality-constraint requirement keys carry no linkage/mangled name, so two of them defer under `""` → second `add("")` asserts. The existing eager-clone guard already handles un-named `IRBuiltinRequirementKey` for this exact reason — equality-constraint keys are a second uncovered class. Fix layer: broaden the eager-clone guard (minimal, no serialized-IR change), or give equality-constraint keys a distinct mangled name (touches linkage names).

## Shadowed inherited members and lazily-synthesized conformances

When a derived interface re-declares (shadows) an inherited member name, member lookup on a constrained type param returns a ≥2-candidate overload (base + derived) — a correct shape that `CompareLookupResultItems` knows how to rank [shadowed inherited interface member ICE](../learnings/1786585128863-shadowed-inherited-interface-member-member-base-ov.md). The bug (#12513): the type-arg context resolves via normal ranking, but the member-access base (`.X` on it) runs `maybeInsertImplicitOpForMemberBase`, which applies only a filter removing every interface-parented candidate (meant to prefer a concrete def) — with all candidates being requirements, the filter empties the set → ErrorType with **no diagnostic** → E99997 ICE at lowering. The discriminator: a shadowed non-member ICEs silently while the same non-member *without* the shadow gives clean E30027, proving the base is poisoned before member resolution. Fix: when the filter empties the set, rank the original overload with `resolveOverloadedLookup(refineLookup(..., LookupMask::Default))` (three subtleties, each a real trap — use `resolveOverloadedLookup` not `maybeResolveOverloadedExpr`; wrap in `refineLookup`; use `LookupMask::Default` not `::type`).

An enum spuriously failing a `T : __EnumType` constraint (E38029) *only* while checking the multi-file `__include` module that declares it is a strong **stale-negative-cache** hypothesis [enum __EnumType conformance stale cache](../learnings/1788776018731-enum-enumtype-conformance-failing-in-multi-file-in.md): the enum's `__EnumType` conformance is synthesized late (at `ReadyForLookup`), inheritance-info caches negative witnesses, and the cache is validated only against per-decl *extension* epochs — adding the synthesized conformance bumps no epoch. If any decl checked before the enum's `ReadyForLookup` queries its inheritance (extensions are driven `ReadyForLookup`-first, so an extension touching the enum is the prime trigger), a negative result is cached and never refreshed. The general lesson: a lazily-synthesized conformance combined with a cache whose invalidation tracks a *different* event is an order-dependent false-negative trap; fix where the facet list is built (force `ensureDecl(subject, ReadyForLookup)`) or invalidate on the late `addMember` — guarding only `isSubtype` is insufficient because an earlier caller cached the poison.
