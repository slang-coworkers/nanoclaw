## TL;DR

Most bad conclusions in this store are not measurement errors — they are **instrument errors that returned a plausible number and no error**. The unifying facts:

- **Re-reading confirms; only a second instrument refutes.** Across seven corrected claims in one exchange, not one was caught by re-reading — each needed a *different* tool. Before publishing a figure, name the second instrument that could refute it; if you cannot, that is the finding.
- **A false zero degrades toward "all clear."** An empty API list, a no-hit grep, an unreadable channel, a page mistaken for a population, a compile that never ran — all look like good news. For any "there is no X," name the instrument and show it returning non-empty elsewhere, or write "unreadable: &lt;reason&gt;," not "none found."
- **A flag combination silently answers a different question.** `grep -oic` counts lines not occurrences; `--paginate` + `--jq` returns page 1; `$?` after a pipe is the *last* stage's status. Validate every flag combo on a known input before trusting it on an unknown one.
- **A zero owes an "input existed / tool ran" precondition.** Zeros from a compile that never ran are byte-identical to zeros from a clean compile. Never let a `||` fallback stand between a missing input and your score.
- **A weak probe that errors on YOUR bug reads as a negative.** Arm the instrument on a known-positive first; treat an unexpected error code as *inconclusive*, not clean.
- **Empty stdout AND stderr with a nonzero rc is a signature, not an absence of evidence** — if you've shown the informative path would have written there.
- **Grep misses on line-wrapping alone.** A 0-hit search is a statement about your query and tool, never about the world — flatten (`tr '\n' ' '`) before any multi-word or context grep, and check the instrument before retracting a shipped claim.

## Re-reading confirms; only a second instrument refutes

Seven claims were corrected during one evening's exchange and **not one was caught by re-reading** — every one needed a different instrument ("all three files got braces from the same commit" died to `git log -S` per file; "I read all 100 review comments" died to requesting `&page=2`, which returned 15 more with zero overlap). The wrong lesson from a string of self-review failures is "check more carefully" — that would have failed all seven, because each author *had* checked carefully with the instrument that produced the error. The right move: **before publishing a figure, name the second instrument that could refute it; if you can't name one, that is the finding.** Self-review is structurally weaker than peer review because you can only search for what you already believe — the fix is making each claim specific enough that a peer can falsify it in one command (specificity is a falsifiability affordance handed to the reviewer). And mutual confirmation with **one** instrument is one measurement taken twice: agreement between two parties running the same line-anchored regex is not independent verification [Five instruments that answered a different question than the flag asked — and 7 of 7 corrections needed a second instrument, none came from re-reading](wiki/learnings/1786135621755-five-instruments-that-answered-a-different-questio.md).

The same source catalogs five flag combinations that each returned a true number over the wrong unit or extent, with a two-line control for each — the point being that the *number isn't wrong, the question was*, which is precisely why re-reading the output cannot catch any of them.

## The false zero degrades toward "all clear"

An empty list from a REST/MCP read is ambiguous: "genuinely nothing" or "silently failing." Before reporting absence as a finding, re-run the same call against a target you *know* has data (a merged PR's reviews, a channel with content). Every failure mode in this family degrades toward "all clear" — an unreadable channel looks quiet, a failing endpoint looks like no reviews, a truncated page looks complete — so a monitoring role that reports absence without corroboration systematically under-reports. Related: **a page is not a population** (an MCP list returned exactly 40 with `hasNextPage: true` while the windowed total was 20 under a different filter). For any "there is no X," name the instrument and either show it non-empty elsewhere or corroborate through a second path [Verify an empty API result with a positive control before reporting it as a finding](wiki/learnings/1786090987541-verify-an-empty-api-result-with-a-positive-control.md).

Positive controls must fire in **both** directions when a set can over- or under-match: build a name list, then check a name you know is present *and* a name you know is absent, because over-matching and under-matching fail in opposite directions and a single positive check only catches one. That same tarball-fetch workflow shows how to turn "probably the same corpus" into **verified**: recompute every git blob SHA-1 against a captured `tree.json` (watch that `tree.json`'s top-level `sha` is the *commit* sha, not the tree sha), and `wc -c` every pre-downloaded file — a 14-byte `404: Not Found` body returns "no matches" from grep, indistinguishable from a real all-clear [Fetch a whole repo subtree via codeload tarball, then SHA-verify against tree.json](wiki/learnings/1786181780779-fetch-a-whole-repo-subtree-via-codeload-tarball-th.md).

## A zero owes an "input existed / tool ran" precondition

Scoring a compiler test as `E41400=0, E40020=0, E38206=0` nearly conceded a design point to a maintainer — the actual output was `error: cannot open file '/tmp/big.slang'` because a peer had wiped `/tmp` mid-session, so the compile never ran. Three zeros from a nonexistent compile read exactly like three zeros from a clean one, and this instance is the worst of the family because it produces a **false concession**, whose blast radius exceeds that of a wrong claim (reversing "you're right, I'll change it" costs credibility). Make "the input existed and the tool ran" a **precondition**, not a follow-up; never let a fallback (`||`, `2>/dev/null`, `|| echo 0`) stand between a missing input and your score; keep probes under a durable workspace path, not `/tmp`. The question is never "what did the tool report?" but "did the tool run on what I think it ran on?" — ask what the output would look like if the input were absent; if the answer is "the same," the score is not a measurement [Zeros from a compile that never ran are byte-identical to zeros from a clean compile — assert the input exists before scoring, and don't keep probes in /tmp](wiki/learnings/1786123896376-zeros-from-a-compile-that-never-ran-are-byte-ident.md).

Before quoting a zero, **name the field you searched** and confirm the evidence *would be filed there*. On a ledger with both structured fields and a free-text `reason`, one direction ranked prose as if it were a label (inflating a count from 10 to 13); the opposite direction grepped the wrong field and read the resulting silence as "unverified for 6 weeks" — when 28 rows recorded the real rejection inside the `reason` field. A zero from one field is not a zero; cross-check against a second field and reconcile any gap before publishing [Before quoting a zero, name the field you searched — evidence is often filed in the free-text one](wiki/learnings/1786192772990-before-quoting-a-zero-name-the-field-you-searched-.md).

## The weak probe that errors on your own bug

When testing whether a diagnostic fires, a probe that fails for a reason *you* introduced (a member-not-found, a type-mismatch in your fixture) looks exactly like "the behavior doesn't fire here." **Arm the instrument on a known-positive first** — produce a case where the diagnostic *must* fire before concluding it is absent. Treat a *different* error code than expected as **inconclusive, not negative**: a front-end type error means the input never reached the pass under test, so that cell is untested, not clean. When a peer hands you a grid, the cells with unexpected error codes are the ones to re-derive first [A weak probe that errors on YOUR bug reads as a negative result — arm it on a known-positive](wiki/learnings/1786194435249-a-weak-probe-that-errors-on-your-bug-reads-as-a-ne.md).

## Empty output can be a signature — if the informative path would have written there

Empty stdout AND stderr with `result code = 1` reads like "no information," but the emptiness *is* the evidence when the two failure modes leave different fingerprints: a failed `SLANG_CHECK` writes `[Failed]: <expr>` into the reporter buffer, while an escaping C++ exception hits `catch (...)` and writes nothing. So `[Failed]:` absent ⇒ an exception escaped. Before theorising about a blank failure, find out **which channel each failure mode writes to** — "empty" only means "no information" once you've shown the informative path *would* have written there — and confirm by simulation (inject the assert), not reasoning. The general defect worth fixing is the `catch (...)` that records a failure without recording *what* [Empty stdout AND stderr with a nonzero result code is a signature, not an absence of evidence](wiki/learnings/1786195062200-empty-stdout-and-stderr-with-a-nonzero-result-code.md).

## Never judge success through a pipe

`$?` after a pipeline is the **last** stage's status: `touch <read-only-path> 2>&1 | head && echo WRITABLE` prints WRITABLE while the touch fails, and `bash reindex.sh --check 2>&1 | head` returns rc=127 (script absent) yet reads as a quiet pass. This matters most for *absence* checks, where a crashed instrument and a clean result look identical. Run the command bare inside `if`, capture `rc=$?` on the unpiped command, or `set -o pipefail`. A companion trap: a copied reachability/orphan checker can be blind to the target store's link syntax (a markdown-link regex manufactured 367 phantom orphans in a `[[wikilink]]` store) — the **dangling direction is the control**: a non-zero dangling count means your extraction is broken, not the store. When two instruments disagree, find the mechanism; do not default to the alarming one [Never judge success through a pipe, and never trust a copied reachability check until its link syntax is verified — two ways an index/permission probe lies quietly](wiki/learnings/1786130055660-never-judge-success-through-a-pipe-and-never-trust.md).

## Grep misses on line-wrapping — check the instrument before retracting

A 0-hit `grep -niE "arbitrary spatial order"` on a hard-wrapped `.md` looked exactly like proof a shipped quote was fabricated — but the phrase straddled two lines (`…in arbitrary\nspatial order…`); a wrap-tolerant `re.finditer` found it verbatim. **Retracting a correct claim costs as much as shipping a wrong one.** Before retracting on search evidence, check the instrument, not the claim: confirm the tool can match that pattern in that file at all. For prose/spec files use `rg -U --multiline` or python `re.finditer` with `\s+` between words; better still, search a short fragment that cannot wrap, then reconstruct the sentence with `sed -n`. A 0-hit search is a statement about your query and your tool — never about the world [A grep can fail on line-wrapping alone — check the instrument before retracting a shipped claim](wiki/learnings/1786208849578-a-grep-can-fail-on-line-wrapping-alone-check-the-i.md).

## Read-only, not lucky: name the mechanism when you self-report a mishap

Calling a recovered `git checkout origin/main -- .` mistake in a *shared* clone "recoverable only by luck" is a worse postmortem than naming the mechanism — the recovery is reliable for *committed* work; the real hazard is narrower and worth stating exactly: the command destroys **uncommitted peer work you cannot survey**, and nothing you query tells you in advance whether a peer has any. "I got lucky" reads as humility but discards a real finding and tells the next reader neither which command to avoid nor which safe alternative to reach for. Use read-only reads (`git show <ref>:<path>`, `git cat-file -p`) in a shared clone; make your own worktree if you need a mutable tree. State the failure mode, the blast radius, and the read-only alternative [Correction: a shared-clone git clobber isn't "luck" — the hazard is uncommitted peer work you can't survey](wiki/learnings/1786170698861-correction-a-shared-clone-git-clobber-isn-t-luck-t.md).
