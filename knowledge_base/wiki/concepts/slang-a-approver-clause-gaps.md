## TL;DR

- **`ci_green_on_sha` reads the legacy combined-status API, which can be green on trivial posters alone** while build check-runs are red. The hazard is *exactly one trivial poster going green* (not zero — a zero-count combined status returns `pending`, which is fail-safe). `shader-slang/slang` is the fleet's worst case: 2 contexts speak for 278 check-runs and return a confident `success`.
- **The defect (D2) fires one policy flag away on slangpy#1090** — under `require_ci_green: true` the same clause emits `pass — combined status=success` over 4 red builds. As *executed* it took the `:184` policy-skip path and certified nothing; the two cases emit an identical bare `pass`, which is itself the defect.
- **Never quote a clause tally without the policy version.** "6/6 pass" was 4/6 under the bundled policy — `no_protected_paths` and `head_provenance` passes were bought entirely by the widened `v0-shadow-wide`. A clause whose evidence cites a policy grant is conditional on configuration, not a property of the PR.
- **CI-gate precision is bounded by the coarsest identity the CI provider exposes.** On an Actions-only repo all suites share `app.slug=github-actions`, so `CI_GATE_REQUIRED_SUITE` cannot discriminate; `REQUIRED_CHECK_RUN` needs a roll-up job that slangpy lacks.
- **Fail-safe abstains are a silent failure class** — an outcome join (abstain vs merged+APPROVED+clean-review) is the only instrument that finds a *correct-policy, over-strict clause* false-negative; its first run paid for itself.
- **Method that recurs:** where a code path is short and side-effect-free, execute the other branch instead of arguing about it; run the program's own predicate, not a stdlib lookalike; read the `evidence` field before theorizing about a `status` field; and a prediction confirmed by a *reinterpreted* observation is not confirmed.

## The `ci_green_on_sha` combined-status defect (D2)

The eligibility clause queries the legacy combined-status API, which can report `state: success` on the word of a review bot (`CodeRabbit`, `license/cla`) while every build leg on `check-runs` is red. **The hazard is not zero posters** — a zero-count combined status returns `state: pending`, which no clause reads as green, so a repo with no status posters is *fail-safe*. The real hazard is *exactly one trivial poster going green*, and the smaller the poster-to-check-run ratio the more dangerous. Measured: `shader-slang/slang` returns `success` from 2 contexts (`license/cla`, `SlangPy Tests`) speaking for **278** check-runs — the fleet's worst case; slangpy and slang-rhi have 0 posters and fail safe. The generalizable shape: the hazard on a threshold check is rarely at the empty end (usually guarded) — it is *just past empty*, where the guard is satisfied and the substance is missing. [[approver/clause-gap] CORRECTION: zero status-posters is the FAIL-SAFE case — the hazard is exactly one trivial poster, and shader-slang/slang is the worst case (2 contexts speak for 278 check-runs)](wiki/learnings/1785940416707-approver-clause-gap-correction-zero-status-posters.md)

On slangpy#1090 R2 (`bb870c1750cc`) the defect **fires one policy flag away**, proven by executing the bundled path: under `require_ci_green: true` the clause takes `:186-195`, reads `combined state=success | contexts=['CodeRabbit']`, and emits `pass` while `check-runs` reports 4 `failure` legs. The right framing is neither "it fired" nor "latent": the only thing between this decision and a green certification over red builds is an explicitly-temporary measurement flag scheduled to be re-tightened (and `:183` defaults `require_ci_green` to `True` on an absent key, so a lost policy mount opts into the buggy path today). The verdict was still a correct BLOCK only because a human-driven path read job logs directly and ignored the clause — **the verdict path and the eligibility path must not disagree silently**, which is the cheapest possible tripwire for this class. Fix: consult check-runs as well as combined status, treat absent build signal as `unevaluable`, distinguish `skipped` from `pass`, and sequence `require_ci_green: true` *after* the check-runs fix. [[approver/clause-gap] ci_green_on_sha passed on a CodeRabbit-only combined status while 4 builds failed — the D2 defect fired for real on slangpy#1090 R2](wiki/learnings/1785936275585-approver-clause-gap-ci-green-on-sha-passed-on-a-co.md) [[approver/clause-gap] D2 DOES fire on slangpy#1090 — one policy flag away, proven by executing the bundled path; and my earlier fnmatch check was the wrong instrument for eval-clauses.py globs](wiki/learnings/1785938138560-approver-clause-gap-d2-does-fire-on-slangpy-1090-o.md)

The arc through this finding is itself a lesson. An intermediate note claimed the clause "reported pass *on substance*" — **false; it took the `:184` policy-skip path** (`require_ci_green: false` in the loaded `v0-shadow-wide`) and never queried anything. The error: observing `status: pass` and separately observing red builds, then fusing them into a mechanism *without reading the `evidence` field* (`"policy does not require CI green"`) sitting in the same JSON object. The fusion felt safe because it looked like a filed prediction coming true, and was framed as correcting a peer for being "too generous" — **self-criticism and peer-criticism both felt like skepticism while functioning as confirmation bias.** Read the `evidence`/detail field before theorizing about a status field; a prediction confirmed by a *reinterpreted* observation is not confirmed — re-derive it, don't promote it. The residual real defect: the clause emits the *identical* `pass` on two unrelated grounds (`:184` policy-skip and `:190` combined-status-success), so a reader scanning only `status` cannot distinguish them. [[approver/clause-gap] CORRECTION: ci_green_on_sha on slangpy#1090 R2 took the policy-skip path, not the substantive one — I read a pass and inferred its cause without reading the evidence string](wiki/learnings/1785936858731-approver-clause-gap-correction-ci-green-on-sha-on-.md)

## Policy version is load-bearing; protected paths hinge on layout coincidence

**"6/6 clauses pass" is meaningless without the policy version.** On slangpy#1090 R2 two of the six passes were bought by the widened `v0-shadow-wide` (`allow_fork_head: true`, `require_ci_green: false`, `max_total_lines: 8000`, `protected_paths` cut to 1 glob): `head_provenance` "fork head allowed by policy" would fail under the bundle, and `no_protected_paths` "7 paths, none protected" would fail because the PR touches `external/slang-rhi` which the bundle's `external/**` catches. The widening is human-signed, temporary, and carries "MUST BE RE-TIGHTENED" — so these passes are *scheduled to reverse*, and any precision statistic gathered under `wide` describes a population the enforcing policy will not admit. Never quote a tally without the version; a clause whose evidence cites a policy grant ("allowed by policy") is conditional on configuration, not a property of the PR. And **diff size is not change size** — `external/slang-rhi` is a `+1/-1` gitlink carrying the entire Vulkan/Metal import implementation. [[approver/clause-gap] "6/6 clauses pass" is meaningless without naming the loaded policy — on slangpy#1090 R2 two of the six passes were bought by v0-shadow-wide's widening](wiki/learnings/1785937877397-approver-clause-gap-6-6-clauses-pass-is-meaningles.md)

The `external/**` glob is the **sole guard for the submodule gitlink** on slangpy — it *looks* redundant beside `.github/**` and `**/*.yml`, but a drop-one counterfactual (run through the skill's own `glob_to_re`, not `fnmatch`) shows the outer gitlink `external/slang-rhi` loses protection and the clause passes clean. The inner `.github/workflows/*.yml` files match *only* via `external/**` once tree-anchored (they live at `external/slang-rhi/.github/...`, and `.github/**` compiles to `^\.github/.*$`, anchored at the repo root). **A guard that works by coincidence is indistinguishable from a designed one in the config — and reads as redundant, which is what gets it deleted** at re-tightening. Before removing any glob, run the drop-one counterfactual and check the *outer* gitlink entries, not just inner files. The real fix is to treat any gitlink modification as protected, removing the layout dependence. [[approver/clause-gap] Do not tidy external/** — it is the SOLE glob protecting the gitlink on slangpy, and a guard that works by coincidence reads as redundant in the config](wiki/learnings/1785938893186-approver-clause-gap-do-not-tidy-external-it-is-the.md)

## Gate precision is bounded by CI-provider identity

Arming `CI_GATE_REQUIRED_SUITE=github-actions` would *not* have parked slangpy#1090: on an Actions-only repo **all seven suites share `app.slug=github-actions`** (`app.name` identical too), so the matcher (`appSlug === req_`) matches the trivial successes as readily as the failing build suite — byte-identical in effect to unset. `CI_GATE_REQUIRED_CHECK_RUN` is the branch that can discriminate, but only where a **roll-up** check-run exists: slang has `check-ci`; slangpy has *none* (its runs are 12 individual `build (...)` legs with no single name meaning "the build passed"), so slangpy needs a `needs: [build]` + `if: always()` aggregate job before the gate can be precise there — an infra gap, not a config choice. **Verify a config value has discriminating power on the actual data before recommending it** — a recommendation naming the wrong knob is not a small error: the operator sets it, sees no change (identical to unset), and concludes the gate doesn't work. [[approver/infra-abstain] CI_GATE_REQUIRED_SUITE cannot discriminate on Actions-only repos (all suites share app.slug=github-actions) — and slangpy has no roll-up check-run to name, so REQUIRED_CHECK_RUN needs a new gating job there](wiki/learnings/1785943914319-approver-infra-abstain-ci-gate-required-suite-cann.md)

## False-safe detection: the outcome join

Fail-safe abstains are a silent failure class — a decision the procedure got *right*, recorded as an abstain, where nothing alerts because caution looks like caution. An **outcome join** (join every recorded Step-1 abstain against the PR's real outcome, flag `merged + reviewDecision APPROVED + clean review`) is the only instrument that sees both causes of the same recorded outcome: wrong-policy-loaded (a version audit finds this) *and* correct-policy-over-strict-clause (only the join finds this). Its first run found slangpy#1002 — era-correct `v0-shadow-relaxed`, no staging bug, `no_protected_paths` fired legitimately on `.github/**` on a PR that merged APPROVED with a 0-bug review. Build a detector for a silent failure class even when you think you found the instances — the ones you found are the ones some other signal surfaced. Artifact constraint that shaped it: only 1 of 57 workspaces retained `record-payload.json`, but all 57 had `clauses.json` + `context.json`, so the join is built from durable artifacts, not the ledger. [[approver/false-safe] Built the ABSTAIN-vs-merged join and it immediately found a SECOND unambiguous false-negative — slangpy#1002, era-correct policy, no staging bug involved: no_protected_paths fired on a PR that merged APPROVED with a clean APPROVE/0-gap review](wiki/learnings/1785947355558-approver-false-safe-built-the-abstain-vs-merged-jo.md)

Working the soft rows, slangpy#1084's four Devin "Investigate" flags all resolve to nits — and the `permissions: {}` flag **inverts the intent**: read as a hazard, it is actually the callee's *documented required contract* (`pr-board-sync.yml`: "callers should set `permissions: {}`"), so the flag pushed toward *granting* permissions the design withholds. **For a PR that delegates (reusable workflow, shared action), severity cannot be judged from the caller alone** — read the callee's contract before promoting a delegation flag to a gap (cheap: two `gh api contents` calls). A check that only sees one side of a join manufactures a concern as readily as it misses one. [[approver/challenger-miss] Worked 3 of the 8 soft rows: slangpy#1084's four "Investigate" flags all resolve to nits against source — the reusable workflow's own header documents `permissions: {}` as the required caller contract, so the flag inverted the intent](wiki/learnings/1785948569292-approver-challenger-miss-worked-3-of-the-8-soft-ro.md)

## The reusable method threads

Two more recur across these decisions. **Execute the other branch, don't argue about it** — the terminating move on a three-round disagreement was ~10 lines fetching the commit's combined status and branching exactly as the clause does; a runnable counterfactual beats unbounded argument every time. And **run the program's own predicate, not a stdlib lookalike** — the skill uses a hand-written `glob_to_re` where `**`→`.*`, not Python's `fnmatch` (which treats `*` as crossing separators); the earlier fnmatch check agreed *by luck* on a bare `**` suffix, and a mid-pattern `*` would have parted the answers. A registry entry, likewise, declares an *intent* not a mapping that exists: "listed in `.external-skills.json` ⇒ ephemeral" was false for `slangpy-pr-approver` because the declared source repo doesn't carry the skill — so nothing overwrites it and a local edit is durable. Verify both ends of any declared mapping, and when a positive control fails for a *path* reason (skills live under `skills/`, not root), that is a signal to fix the probe, not evidence about the subject. [[approver/clause-gap] "Listed in .external-skills.json ⇒ ephemeral" is FALSE for slangpy-pr-approver — the declared source (shader-slang/slang-skills@main) has 30 skills under skills/ and no approver among them, so nothing overwrites it; my own positive control initially failed too (skills live in skills/, not root)](wiki/learnings/1785946546703-approver-clause-gap-listed-in-external-skills-json.md)

The repo's **own test comments are a 65ms authority on whether a construct is intended** — deciding #12246 (reject non-integer `switch`), the load-bearing question ("is a case-less `switch` real?") was already answered by `tests/bugs/empty-switch.slang` ("This is kind of silly - but it is a valid construct... we want to check condition expression is executed"), an executable assertion on four backends. A 40-minute build confirming a 65ms grep is not diligence; it is a search that was never run. For "is X valid/intended/relied upon?", grep the test corpus for intent prose first, look for an executable assertion second, check whether X already fails before the change third, and build the changed compiler only fourth. [[approver/challenger-miss] The repo's own TEST COMMENTS are a 65ms authority on whether a construct is intended — I spent a 40-min compiler build proving what tests/bugs/empty-switch.slang already stated](wiki/learnings/1785846271995-approver-challenger-miss-the-repo-s-own-test-comme.md)
