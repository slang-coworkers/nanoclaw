# gh CLI CI Status & Merge Signals — Instrument-Lie Folds

## TL;DR
- **`gh pr checks`/`gh pr view` are GraphQL-backed** — on a GraphQL-401-while-REST-healthy split they print to stderr and emit nothing on stdout, so a stdout-grepping sweep reads every PR false-green. Probe `gh api graphql -f query='{viewer{login}}'` before trusting uniform all-green; enumerate failures via REST check-runs + statuses.
- **`gh pr checks` can also omit failing check runs while GraphQL is healthy** (#13880: 5 pass / 52 skipping while check-runs had `check-ci` and `wait-for-human-priority` failed). Count conclusions from `commits/<head>/check-runs` before stating CI status; on a bot PR that red pair over a mostly-skipped run is a priority yield ("CI red, not yet run"), never "passing".
- **`is:merged` through the slang-mcp search tool returned 0 (July–August)** — there, infer merge from the closing issue's `state==closed` + matching `closed_at`. By 2026-11 GraphQL `is:merged merged:W0..W1` counts window merges correctly; never count them from commit dates.
- **A merged PR with no `AddedToMergeQueueEvent` bypassed the queue** (admins can, `enforcement_level: non_admins`); confirm with merge time vs its CI run's start.
- **`gh run rerun` rc=0 is not proof it fired, and an unchanged `run_attempt` is not proof it didn't** — proof is a second rerun's 403 "already running"; key reruns on `(workflow_id, event, name)`.
- **A `success` conclusion can mean "declined to act"** — priority-yield aging is contention-gated (12h yield-out / 16h lookback, then expires unrerun), not a timer; grep the decision line from the log output, not the echoed `run:` block.
- **Bucket a red by terminal outcome, never by a signature string** — `slang-test` retries, so signature-presence over-counts; a correct total can hide a wrong composition.
- **"CI failing" means a REQUIRED check concluded `failure`** — not a CANCELLED approval gate (`falcor-build-approval-gate` on external PRs) or a non-required job (`board-sync`, `review`); an absent required `check-ci` (fork runs awaiting approval) is "not run". Read required contexts from `branches/master` (`/protection` 403s), or audit every label with one aliased GraphQL `isRequired(pullRequestNumber:)` query (1 point for six PRs); `gh pr checks` folds CANCELLED into fail. Zero `isRequired:true` contexts = required CI never ran (blocker is approval). Filter the label on required checks; don't drop it.
- **A merge-queue eviction's reason (`failed_checks` / `checks_timed_out` / `merged`) is only in GraphQL `RemovedFromMergeQueueEvent.reason`**. `checks_timed_out` usually means a required SM80Plus job had not started ~2 h after enqueue; before calling a pool outage, check whether a later-created same-name job ran. A green merge-group run does not mean the PR merged.
- **Merge-queue enqueues/evictions (and board status changes) do not bump `updatedAt`**, so an `updated:>=W0` pre-filter misses them. Enumerate from repo-wide `issues/events` or `event=merge_group` runs, then read the per-PR timeline.
- **Stale master head + empty queue: diff the failing test names of two eviction runs.** An identical set is PR-side, not infra or a master regression.
- **A PR comment does not stop the merge queue** — reach whoever queued it by name, file at once, or have a human dequeue. A ready all-green PR on a merge-queue branch reads `mergeStateStatus: BLOCKED` until queued; not a failing gate.
- **`gh .user.login` omits the `[bot]` suffix** (`nv-slang-bot`, not `nv-slang-bot[bot]`); edit-if-last-poster-is-self guards must compare the bare login or they post a duplicate.

Incident folds where `gh`/git status- and merge-reading tools returned coherent-but-wrong answers, and the resulting corrections/supersessions.

For *how to drive* the tools see [gh CLI Usage & PR/Issue Mechanics](ci-gh-cli-usage.md); related: [gh CLI Output Channels & Filter Encodings](ci-gh-cli-output-channels-and-filters.md), [gh CLI Control Design & Over-Claim Origins](ci-gh-cli-control-design-and-overclaims.md).

## gh .user.login Omits the [bot] Suffix

The REST API returns a bot account's login bare (`nv-slang-bot`), not the UI's `nv-slang-bot[bot]`, so an "edit-if-last-poster-is-self" guard comparing against `nv-slang-bot[bot]` mis-fires and posts a DUPLICATE. Compare against the bare login ([gh .user.login omits the [bot] suffix — edit-if-self guards must compare bare login](../learnings/1783935090568-gh-user-login-omits-the-bot-suffix-edit-if-self-gu.md)).

## GraphQL-401-while-REST-healthy phantom-greens a CI sweep (`gh pr checks` is GraphQL-backed)

When the GitHub gateway is in a **partial** state — GraphQL returns `401 Bad credentials` while REST is fully healthy (`gh api repos/.../pulls/N`, `commits/<sha>/check-runs`, `commits/<sha>/statuses`, `actions/runs`, even `gh run rerun --failed` succeed) — the CI-sweep entry-point tools silently lie. `gh pr checks <N>` and `gh pr view <N>` are **GraphQL-backed**: on a 401 they print to **stderr** and return **nothing on stdout**, so a loop grepping stdout for `fail` (or using `2>/dev/null`) reports **every PR false-green**. Observed twice on the Slang CI babysitter: a clean 20/20 "no failures" that was pure phantom. Root cause: a recurrence of the App-token-refresh gateway split (`project_github_gateway_actions_graphql_401`).

Defense: never trust empty `gh pr checks`/`gh pr view` output as green — on suspiciously-uniform all-green, probe `gh api graphql -f query='{viewer{login}}'`; if it 401s while REST works, route the ENTIRE failure enumeration through REST and proceed (reads AND reruns work, so do NOT hold read-only):

```bash
sha=$(gh api repos/<o>/<r>/pulls/$PR --jq '.head.sha')
gh api "repos/<o>/<r>/commits/$sha/check-runs?per_page=100" --paginate \
 | jq -s '[.[]|.check_runs[]]|[.[]|select(.conclusion=="failure" or .conclusion=="cancelled" or .conclusion=="timed_out" or .conclusion=="startup_failure")]|group_by(.name)|map(.[0])'
gh api "repos/<o>/<r>/commits/$sha/statuses?per_page=100" \
 | jq '[.[]|select(.state=="failure" or .state=="error")]|group_by(.context)|map(.[0])'
```

Notes: (1) `--paginate` concatenates JSON objects, so slurp with `-s`; do **NOT** use the optional-`?` form (`.check_runs[]?`) an earlier revision recommended — **that `?` is a silencer**: it swallows a gateway error document (no `.check_runs` key) and returns a clean-looking page-1-only result. Gate on shape (`jq -e '.check_runs'` per page) and reconcile the count. (2) Some required gates (merge-queue aggregators, cross-repo checks like SlangPy Tests) are commit **statuses**, not check-runs — check both. (3) The wake payload's `evicted` list may be GraphQL-derived → cross-check evictions via REST `actions/runs?event=merge_group`. Distinct from a full actions:write outage (`gh run rerun` 403 "Must have admin rights"); a fresh GraphQL-401-while-REST-ok is worth an operator ping via parent ([gh pr checks phantom-greens the CI sweep when GraphQL is 401 but REST is healthy](../learnings/1785586525718-gh-pr-checks-phantom-greens-the-ci-sweep-when-grap.md)).

**`gh pr checks` can hide failing check runs even when GraphQL answers.** On slang #13880 `gh pr checks --json bucket` returned only 5 pass and 52 skipping, while `gh api repos/<o>/<r>/commits/<head>/check-runs --paginate` showed `check-ci` and `wait-for-human-priority` as **failure**, 92 skipped and `falcor-build-approval-gate` waiting; the PR badge was red and the "0 failures" sent upstream was wrong. Before stating CI status, count conclusions from the commit's check-runs (`--jq '.check_runs[] | .conclusion // .status' | sort | uniq -c`). On bot-authored slang PRs, a red `check-ci` + `wait-for-human-priority` over a mostly-skipped run is the priority yield — nothing has built or been tested; report "CI red: priority yield, not yet run", never passing ([`gh pr checks` can hide failing check runs](../learnings/1792703301263-gh-pr-checks-can-hide-failing-check-runs-read-ci-s.md)).

## is:merged Search Is Broken — Infer PR Merge From Simultaneous Issue-Close

`mcp__slang-mcp__github_search_issues` with `is:merged` returned 0 results over wide windows while PRs were demonstrably merging (confirmed 07-26 and 08-01). There, don't use `is:merged`: check whether the PR's **closing issue** is CLOSED via `github_get_issue` — a `Fixes #N`/`Closes #N` PR auto-closes its issue at the merge instant, so `issue.state == closed` + matching `closed_at` = merged (#12071 CLOSED 2026-07-30T18:34Z confirmed PR #12095 though `is:merged` returned nothing). Paging the REST `commits` API also works, but it truncates to ~15 entries — widen or paginate or you undercount (counted 5, actual 9) ([is:merged search broken — infer PR merge from simultaneous issue-close](../learnings/1785572253771-is-merged-search-broken-infer-pr-merge-from-simult.md)). By the 2026-11-05/06 sweeps GraphQL `is:merged merged:W0..W1` (merge-time search) counted window merges correctly and the commit-date routes were the broken ones: a merge-queue commit carries its enqueue time, so `history(since:)` and `commits?until=` misplace PRs queued before a boundary and merged after it (see [Counts, apertures & reconciliation](misc-f0909b1-counts-apertures-and-reconciliation.md)) ([Master history(since:) undercounts merges when the MQ commit predates the window](../learnings/1793955732333-master-history-since-undercounts-merges-when-the-m.md)).

## `gh run rerun` Returns 0 Before Anything Changes

`gh run rerun <id> -R <r> --failed` exits **0** once the API accepts the request, but `run_attempt` can still read the **old** value right after (observed: `att=1` read back, nearly logged "rerun failed to take", then `att=2, in_progress, steps=4` seconds later). Unambiguous confirmation: **issue the rerun again** — if the first took, GitHub replies 403 `{"message":"This workflow is already running"}`; if it accepts again, the first never fired. Otherwise re-query after a beat and check `run_attempt`, `status` and `steps` length together (a real re-execution has a fresh non-empty `steps`). Keying trap: one job *name* can exist on a single sha under two `event`s (`pull_request` and `push`), so rerunning "the REUSE run" greened one instance while the other stayed red [gh run rerun returns rc=0 before run_attempt increments — the proof it took is a second call returning 403 "already running"](../learnings/1786077463765-gh-run-rerun-returns-rc-0-before-run-attempt-incre.md).

## A `success` Conclusion Can Mean "Declined to Act" — Priority-Yield Aging

Aging (`ci-retry-yielded-bot`, believed "~8h") does **not** force a yielded bot CI run to a verdict on a timer. `wait-for-priority.py --max-yield-hours 12` escalates only when the gate **runs again** and finds itself aged out (age from *original* creation, across reruns). Reruns come only from `retry-yielded-bot-ci.py`, whose **first gate** is `any_active_ci(...)`: if any `ci.yml` run repo-wide is `queued|in_progress|waiting` it prints `CI is still active (N run(s)); not rerunning bot CI.` and exits 0 — then `--max-reruns 1` per fire. Real params: **12h yield-out / 16h lookback**; past the lookback a run **expires unrerun** (one busy day: 60/60 fires over 5.4h blocked at gate 1). **The aging run concludes `success` even when it did nothing**, so grep its decision line from the log's *output*, not its echoed `run:` block; a rerun mutates the same run id in place, so `run_attempt` shows whether aging touched it [slang priority-yield aging is CONTENTION-gated, not a timer — a yielded run can expire unrerun](../learnings/1786079520646-slang-priority-yield-aging-is-contention-gated-not.md).

## Bucket a Red by Terminal Outcome, Not by a Signature String

On slang #12418 "test-server JSON-RPC breakdown = 18" came from grepping failing job logs for `JSON RPC failure`; re-deriving by **terminal failure** (the `FAILED test:` line) returned **18 again** — but **11 of 29 rows were misfiled**: string-presence over-counted by ~11 while an independent window error under-counted by about as much. `slang-test` retries, so in all 11 misfiled jobs the string came from a retry-*passing* test while the terminal red was a deterministic regression reproducing across SHAs, runners and platforms — a rerun cannot succeed. Presence proves an event occurred, never that it caused the red. `Too many failed tests for retry(N) - setting all to failed` promotes every pending-retry test to terminal; `failed(pending retry)` / `[Failed]:` are first-attempt only. Rule: **a total that reproduces is not a composition that reproduces** — when a challenged figure comes back unchanged, name its members, since offsetting errors pass every sum check and misfiling toward *infra* prescribes a futile rerun [A correct total can hide a wrong composition — reclassify by TERMINAL outcome, never by signature-string presence](../learnings/1786074478624-a-correct-total-can-hide-a-wrong-composition-recla.md).

## "CI failing" Must Mean a Required Check Failed — `pr_report.py` False Positive

`summarize_ci()` in `slang-pr-report/scripts/pr_report.py` (`:896-914`) marks a PR `CI_FAILED` when *any* completed check concludes outside {success, neutral, skipped}, counting CANCELLED runs and non-required jobs. On 2026-10-05 it publicly labelled two PRs "CI failing, needs fixes" and the author corrected it in #slang-committers: on slang#13270 the only red was `falcor-build-approval-gate` (`environment: falcor-ci`; an external contributor can't approve it, so it times out CANCELLED), on slang#11964 only `board-sync`. Before a "CI failing" label: (1) Is the red job required? Master's required contexts are `check-formatting`, `check-ci`, `SlangPy Tests`, readable unprivileged via `gh api repos/shader-slang/slang/branches/master --jq .protection.required_status_checks.contexts` (`/protection` returns 403 for the app token). (2) Failure or cancellation? `gh pr checks` folds CANCELLED into "fail"; read GraphQL `statusCheckRollup` or REST check-run `conclusion`. Same rule as terminal-outcome bucketing: a cancelled approval gate is a policy exit, not a code failure ([pr_report.py "CI failing" false positive from non-required checks](../learnings/1791188233110-pr-report-py-ci-failing-false-positive-from-non-re.md)).

The cheapest audit of every label is one GraphQL query, one alias per PR, asking each head context whether it is required:

```graphql
repository(owner:"O",name:"R"){ pullRequest(number:N){ commits(last:1){ nodes{ commit{ statusCheckRollup{ contexts(first:100){ nodes{
  ... on CheckRun{ name conclusion isRequired(pullRequestNumber:N) }
  ... on StatusContext{ context state isRequired(pullRequestNumber:N) } }}}}}}}}
```

Six PRs across slang and slang-rhi cost 1 point with no REST branch-protection or check-runs call (matters when three sweeps share the REST quota). The bug persisted across reports: 10-26 had one false label of six (slang#11964: required checks green, reds only the non-required `board-sync` and `check-pr-label`; slang#13776, #13630, #12489, #12415, slang-rhi#899 each had a red required check) ([Verify PR-report "CI failing" labels with one GraphQL isRequired query](../learnings/1793002682253-verify-pr-report-ci-failing-labels-with-one-graphq.md)); 11-02 had 3 of 8 false — slang#13901 and #13959 red only on the non-required `review` with `check-ci` absent (fork runs awaiting approval: "not run", not "failing"), plus #11964 again. Through the OneCLI proxy GraphQL `rateLimit.remaining` jumped between consecutive calls (4170, 5590, 5407, 3482), so one reading is not a reliable budget [H] ([GraphQL CheckRun.isRequired(pullRequestNumber:) separates real from false CI failures](../learnings/1793607720073-graphql-checkrun-isrequired-pullrequestnumber-sepa.md)). 11-09 repeated the same three: #13901/#13959 are fork heads where NO required check ran, #11964 has all three required checks SUCCESS. A head with zero `isRequired:true` contexts means required CI never ran (usually a fork awaiting approval), so "needs fixes" is wrong and the blocker is review or CI approval. `isRequired` is per repo: slang-rhi marks each of its 16 build jobs (incl. Windows) required, so a red Debug build there is a true failure. Fix: filter the label on required checks, don't drop it ([11-09: same 3 false positives; zero required contexts = CI never ran](../learnings/1794213214751-pr-report-ci-failing-false-positives-check-isrequi.md)).

## Merge-queue eviction reason lives only in GraphQL

The REST issue-timeline `removed_from_merge_queue` event has no reason field. Query `pullRequest(number:N){ timelineItems(itemTypes:[REMOVED_FROM_MERGE_QUEUE_EVENT],first:5){ nodes{ ... on RemovedFromMergeQueueEvent{ createdAt reason } } } }` via `POST https://api.github.com/graphql` (works through the proxy without an auth header). Reasons seen: `failed_checks`, `checks_timed_out`, `merged`. Slang #13615 was evicted `checks_timed_out` though its group CI run finished SUCCESS one second later; cause: a 100-min SM80Plus queue wait (recurrence of closed #13614), confirmed from job `started_at - created_at` in `actions/runs/<id>/jobs` [merge-queue eviction reason via GraphQL](../learnings/1792139409374-merge-queue-eviction-reason-use-graphql-removedfro.md).

**`checks_timed_out` is a two-hour SM80 wait, and one lost job is not a pool outage.** #14111 was evicted twice with `checks_timed_out`, 121 and 123 min after each `AddedToMergeQueueEvent`; both times the group's `test-linux-release-gcc-x86_64-sm80 / test-slang` job (Linux, self-hosted, SM80Plus) had not started — one waited 159.9 min, the other never got a runner (`runner_name` null, `cancelled`). The merge-group run can still finish `success` later, so a green run is not a merge; compute waits from job `created_at` → `started_at` (tracking #14252) ([MQ evicts with checks_timed_out ~2 h after enqueue](../learnings/1793781538310-slang-merge-queue-evicts-with-checks-timed-out-abo.md)). Before calling a pool outage, list the same-named job on other runs: a PR run's sm80 job created one minute LATER ran in 10 min on `linux-sm80plus-f13cf173` while the queue entry's job sat `queued` with `runner_id 0` for 70+ min. That is one lost job; the fix is a human re-run before the 2 h timeout, since eviction also clears auto-merge. The bot token gets 403 on `actions/runners`, so pool health is inferable only from job timestamps ([compare against a later-created sm80 job](../learnings/1793822643773-merge-queue-sm80-job-stuck-compare-against-a-later.md)).

**A stale master head with an empty queue: compare failing test names across eviction runs.** When master's head is hours old and nothing is queued, read the merge-queue timeline of the last PR with auto-merge. On 2026-11-04 it was #14269 (adds an exit-code check to slang-test SIMPLE tests): it failed the same 7 tests in merge-group runs at 07:48Z and 14:14Z and in its own head CI; those tests came from #14051, merged just before. Grep `FAILED test:` in `gh run view <run> --job <id> --log-failed` for two runs and diff; an identical set means PR-side, not infra or a master regression. `gh api .../pulls/<n>/files --paginate` failed with a OneCLI 401 on page 2 there; page by hand with `?per_page=100&page=N` ([compare failing test names across eviction runs](../learnings/1793808444330-stale-master-head-with-empty-merge-queue-compare-f.md)).

**The queue does not read PR comments.** jkwak-work queued external PR #14150 at 00:45Z; at 01:10Z nv-slang-bot commented two cases that compile on master and fail with the PR (integer `/` or `%` in a `[ForceInline]` helper; a user constructor under `-g`). The queue merged it at 02:06Z, and next morning jvepsalainen-nv filed #14235 (CUDA broken in the falcor2-slang nightly) and the bot filed #14238. A regression found on a queued PR must reach the queuer by name, be filed immediately, or be acted on by a human who dequeues the PR. Conversely, GitHub reports a ready all-green PR on this merge-queue branch as `mergeStateStatus: BLOCKED` until someone queues it (#14045) — not a failing gate ([a bot comment on a queued PR does not stop the merge queue](../learnings/1793695966509-a-bot-comment-on-a-queued-pr-does-not-stop-the-mer.md)).

**Merge-queue events do not bump a PR's `updatedAt`, so a search-first scan misses them.** #14351 was enqueued 11-08 12:06Z and evicted (`failed_checks`) 13:34Z, yet `updatedAt` stayed 11-07T01:17Z; board status changes don't bump it either. Selecting `is:pr updated:>=W0` and then reading `timelineItems(itemTypes:[ADDED_TO_MERGE_QUEUE_EVENT, REMOVED_FROM_MERGE_QUEUE_EVENT])` silently drops activity on quiet PRs. Enumerate repo-wide instead: REST `/repos/{o}/{r}/issues/events` (`added_to_merge_queue` / `removed_from_merge_queue`, paginated back past W0), or `actions/runs?event=merge_group&created=W0..W1`, whose branches (`gh-readonly-queue/master/pr-<N>-…`) name the PR; use the per-PR timeline only for details such as the eviction reason. #14351's eviction cause (failed job logs) was HTTP 504 download failures (sccache setup, optix-dev zip) during GitHub's anonymous-traffic incident, not its code ([merge-queue events do not bump updatedAt](../learnings/1794215145532-github-merge-queue-events-do-not-bump-a-pr-s-updat.md), [Slang CI 11-09: MQ-only PRs missing from `updated:` search](../learnings/1794213563648-slang-ci-11-09-anonymous-download-504s-mq-only-prs.md)).

**Detect a merge-queue bypass from the timeline plus run timing.** A merged PR with no `AddedToMergeQueueEvent` was merged directly: #14363 merged 4 s after its CI run started, and the run finished green 2 h later. Branch protection's `enforcement_level: non_admins` lets admins do this, so a sweep must not assume every master commit passed a merge group ([GitHub sweep: merge-queue commit dates, MQ bypass, vanished AR suites, onboard auto-assign](../learnings/1793955615028-github-sweep-merge-queue-commit-dates-mq-bypass-va.md)).

## Contradictions / supersessions

- **"`is:merged` search is broken"** — scoped: the slang-mcp search tool in July–August; by 2026-11 GraphQL `is:merged merged:W0..W1` is correct and commit-date filters break.
- **`--paginate` "gives no non-zero exit code"** — superseded. `gh` exits 1; a pipe into `jq` (or `2>/dev/null`) launders it. A mechanism claim must name the *invocation form* measured.
- **`jq -s '[.[]|.check_runs[]?]'` as the recommended `--paginate` slurp** — superseded; the `?` silences gateway error documents. The GraphQL-401 snippet now drops it, so a non-check-runs page fails loudly; gate on `jq -e '.check_runs'` and reconcile the count.
- **`repos/.../branches/main/protection` 403 ⇒ "CI-not-required clause unverifiable"** — retracted; `branches/main` carries `.protection.required_status_checks.contexts` unprivileged.
- **"GitHub auth is down fleet-wide"** — retracted; a REST-vs-GraphQL path-class split, and four agreeing probes were all one instrument (introspection + GraphQL-backed).
- **"Aging forces a yielded bot CI run through in ~8h"** — retracted; contention-gated (12h yield-out / 16h lookback, then expires unrerun).
