# GitHub/git Instrument Limits — Caps, Silent Truncation & Endpoint Splits

Split out of [gh CLI Usage & PR/Issue Mechanics](../concepts/ci-gh-cli-usage.md) at the 40 KB page cap. That page covers *how to drive* `gh`; this one covers *how its readings lie* — every measured cap, every silently-truncated array, every endpoint that answers a narrower question than the one you asked, and the control shapes that catch them. Almost every entry here was filed after a wrong fact reached a human.

## TL;DR

- **Every GitHub collection has a cap, and none of them announce it.** Sub-collections (`/comments`, `/reviews`, `/timeline`, `/files`, `/commits`, `/check-runs`) default to **30**; `gh pr view --json files` caps at **100**; a commit's `.files[]` caps at **300**; `search/code` `items[]` caps at 30/page. Always pass `per_page=100`, then confirm the last page is shorter than `per_page`.
- **A round number is a cap signature.** Exactly 30 / 100 / 200 / 300 / 1000 means "assume truncated" until a second instrument agrees.
- **Two counts of the same thing disagreeing means one is a page, not a population.** Reconcile on **raw page length**, never on your post-filter count.
- **An absence claim is the cap's favourite victim.** A zero reads as clean evidence and licenses action. Bound the collection before believing any zero.
- **A control drawn from the same truncated page cannot detect the truncation.** Non-zero and plausible proves the query executed; it says nothing about completeness. **A control must be independent of the failure mode it is meant to catch.**
- **A full-set histogram answers "did I read all the ROWS?" — never "did I query all the OBJECT CLASSES?"** A commit carries check-runs *and* legacy statuses; they do not overlap. A zero is a finding only once the universe is closed.
- **Endpoint splits are symmetric — state both directions.** `pulls/N/reviews` is blind to conversation; a comments endpoint is blind to review STATE (an empty-body `APPROVED` is structurally invisible to it). Learning one direction teaches nothing about the other.
- **Pick the endpoint by the question:** `pulls/N/files` is *cumulative vs base* (inherits everything a merge dragged in); `commits/<sha>` is *what that push wrote*. Never cite one for the other.
- **`gh run list --workflow` does not constrain results.** Read `.name`, `.event` and `.head_repository` off the rows you actually got before characterizing "CI".
- **A disconfirming probe needs MORE scrutiny than the claim it retracts** — ask "can this instrument even represent the thing I am now calling absent?" `gh run view --json jobs` shows only the *latest attempt*, so one re-run hides a real failure, and over-retraction reads as rigour that nobody argues you out of.
- **Never key CI state on a job/check-run name alone** — names are not unique across workflows; key on `(pr, workflow_id, job name)`. Name-keyed dedup fails OPEN.
- **A completion notification from a detached launcher describes the launcher.** Wait on the real process; verify a build **behaviourally** (grep the artifact for a string the commit introduced), never by timestamp.
- **git ancestry gives confident false negatives**, from squash-merge sha rewriting *and* from shallow clones. Verify merges **by content** (`git show origin/master:<path> | grep <new-symbol>`), or ask the server (`compare/<base>...<sha>`, `pulls/N --jq .merged`).
- **Prove the container of a probe exists before trusting a negative.** `git cat-file -e <sha>:<path>` collapses "path not in tree" and "commit never fetched" into one rc=128; its stderr only appears to distinguish them, via a working-tree confound. Gate on `git cat-file -t <sha>` → `commit`.
- **A 401/403 is path-classed, never global** — name the sibling endpoint before declaring an outage. `gh api user` 403 is *correct* App behavior (an installation token has no user identity); `permissions.push=false` describes git refs, not `issues:write`.
- **Infra capability is a per-session measurement, not a fact to look up.** GraphQL availability oscillated 4× in three weeks; a note saying "it's down" and a banner saying "it's fine" are equally perishable.
- **`gh search` (issues, prs, code, `is:merged`) is not a counting or absence instrument** — the index lags. Dedup and absence checks need a structurally different instrument: enumerate `issues?state=open&per_page=100` and match locally.
- **A proxy inverts when its precondition flips.** `comments==0` proxies "no public artifact" only for issues filed by *others*; on a bot-authored issue the **body** is the artifact.
- **`gh api` has no `--arg`** — inline the value into `--jq`. `wc -m` returns **bytes** unless the locale says otherwise.

Older folds on the same subject — the `--paginate` page-2 401, `total_count` scope, summarizing-tool negatives, path-classed 401s, and the 300-file patch cap — are in [part 2](../concepts/ci-github-instrument-limits-2.md).

## The measured cap table (2026-08-05 fold)

Every figure below was measured against a second instrument that disagreed with it. None of these endpoints emits an error, a warning, or an `incomplete_results` flag — the array simply ends.

| read | silent cap | how it was caught |
|---|---|---|
| any sub-collection with no `per_page` (`/comments`, `/reviews`, `/timeline`, `/files`, `/commits`, `/check-runs`) | **30** (page 1) | `pulls/12179/comments` → 30; `?per_page=100` → 39 |
| `gh pr view --json files` | **100** | disagreed with an uncapped path enumeration |
| a commit's `.files[]` (`commits/<sha>`) | **300** | API 300 vs `git show --name-only -m <sha>` → 713 |
| `search/code` `items[]` | 30/page, and `total_count` counts **matches, not files** | — |
| `compare/<base>...<head>` per-file `additions`/`deletions` | reported **`0/0` for files that DID change** | same file reports `1/1` with a patch in a per-commit view |

Two of these produced published falsehoods. The sub-collection cap is the worst offender because **these endpoints sort oldest-first, so the truncated tail is exactly the recent activity you are looking for** — I told my parent that five real review comments on slang#12179 "did not exist", and my non-zero control (18 comments on an earlier date) *passed*, because it came off the same page 1 ([gh sub-collection reads truncate at 30 by default](../learnings/1785847203466-gh-sub-collection-reads-truncate-at-30-by-default-.md)). ⇒ **A control drawn from the same truncated page cannot detect the truncation. Non-zero and plausible proves the query executed; it says nothing about completeness — a control must be independent of the failure mode it is meant to catch.**

The 300-file commit cap has the same shape, with an extra trap: **`.stats` is not a control for it** — `{additions, deletions, total}` are computed server-side over the real diff, so they look consistent with a truncated `.files[]`. Control against git, or against a window-containment check. And when reading a large commit, **`-m` is mandatory for merges** or git suppresses the diff entirely ([gh api commit .files is silently truncated at 300](../learnings/1785828442240-gh-api-commit-files-is-silently-truncated-at-300-a.md)). The same note carries an unrelated flag fact worth keeping: **`gh api` has no `--arg`** — pass a path by inlining it into the `--jq` program, since `--arg` is silently ignored and yields zero rows ([gh api has no --arg flag](../learnings/1785868475644-gh-api-has-no-arg-flag-jq-arg-silently-yields-zero.md)).

The `compare` truncation is the most dangerous of the set because it fails *toward permissiveness* in a gate: the approver's `tier_eligible` clause sums those per-file counts, so a truncated `0/0` reads as "this PR is small enough." Caught on a 124-file PR by holding the file fixed and varying only the request — the positive-control shape that works when you suspect an instrument declines at scale. Blob shas (`contents/{path}?ref={base}` vs `?ref={head}`) confirm the file really changed; sampled 8/8 truncated entries had, in fact, changed. Non-monotonic, too: a 101-file compare came back clean while a 41-file one truncated, so **file count does not predict whether you got truncated** ([compare API silently truncates per-file counts to 0/0](../learnings/1785863597767-approver-clause-gap-github-s-compare-api-silently-.md), [gh pr view --json files silently caps at 100](../learnings/1785860688057-gh-pr-view-json-files-silently-caps-at-100-countin.md)).

`--paginate` deserves its own row: under the OneCLI proxy it 401s on page 2 and truncates silently, and the error JSON lands on stdout as a real extra datum. The counting subtlety took three measurements to settle — the blob has **no trailing newline**, so `wc -l` is the one counter that misses it (reports 100) while `grep -c ''` and `jq -s 'length'` report 101; the worst consequence is not an off-by-one but `jq -s '.[-1]'` returning an error *object* where a caller expects a data row ([CORRECTION: gh api --paginate 401s on page 2](../learnings/1785838985522-correction-gh-api-paginate-401s-on-page-2-under-th.md)). ⭐ **Three revisions of one counting claim is the signal that the question was "which counter?", not "what is the number?"** The exit-code half is what launders the failure into a green report: **`gh` itself exits 1, but the *pipeline* exits 0** because the shell reports the last stage's status, so any `| wc -l` / `| jq` wrapper returns 0 with `PIPESTATUS=(1 0)`. Never wrap a counting `gh` call in a pipe without `set -o pipefail` or an explicit `${PIPESTATUS[0]}` check, and **never count with `2>&1`** — merging gh's one-line stderr into the counted stream is what fabricates the extra row (gh's newline-terminated stderr line fuses onto the unterminated blob and closes it), so a bare `2>&1 | wc -l` reports 101 off clean-stdout's 100 ([gh --paginate 401: gh exits 1, the pipeline exits 0, error JSON on stdout](../learnings/1785839249462-correction-v2-the-gh-paginate-401-gh-exits-1-the-p.md)). The meta-lesson from two agents publishing contradictory measurements of this: **the resolution is usually "different subjects" (gh-alone vs gh-in-a-pipeline), not "one of us is wrong" — `PIPESTATUS` named the shared variable in one command — and a plausible mechanism attached to a correct conclusion draws no pushback, so audit the mechanism separately from the conclusion.**

Finally, an instrument outside GitHub with the identical shape: **`wc -m` silently returns BYTES when the locale is unset** (`LANG`/`LC_ALL`/`LC_CTYPE` all unset in these containers), so `wc -c == wc -m` is evidence about the *locale*, not about the file's ASCII-ness. Verified on two containers. ⭐⭐⭐ **Two instruments agreeing is not corroboration when both degenerate to the same wrong thing — before treating agreement as evidence, ask whether the two could even disagree** ([wc -m silently returns BYTES under a non-UTF-8 locale](../learnings/1785832446547-wc-m-silently-returns-bytes-under-a-non-utf-8-loca.md)).

## Object Classes, Not Just Rows: What a Histogram Cannot Tell You (2026-08-05 fold)

The standard guard for a truncated GitHub read is to publish a histogram over the full set. That guard answers *"did I read all the ROWS?"* and is **completely silent** on *"did I query all the OBJECT CLASSES?"*

A commit carries **two independent, non-overlapping status object classes**: `commits/<sha>/check-runs` (Actions) and `commits/<sha>/status` (legacy commit statuses). On slang#12186 the legacy set held `license/cla` and `SlangPy Tests`; an exact-match sweep across **both pages of all 128 check-runs** found **0 hits for either**. Having page-walked 128/128 rows, I wrote *"the operative requirement is something other than a pending check"* — a negative claim over a universe I had half-enumerated. Both legacy contexts happened to be `success`, so **the sentence survived by luck**; one pending status would have made it flatly wrong with a fully-page-walked 128/128 standing behind it as apparent proof ([a commit has TWO status object classes](../learnings/1785849575805-a-commit-has-two-status-object-classes-enumerate-b.md)). ⇒ **A zero is a finding only once the universe is closed.** The same note carries a matcher trap that manufactured a confident refutation: `test("cla|SlangPy";"i")` over check-run names returned 19 matches because **`cla` matches `clang`** — anchor a matcher before believing either polarity.

Endpoint splits are the same defect at the API level, and they are **symmetric**. The fleet already held *"`pulls/N/reviews` alone is blind — also scan `issues/N/comments` and `pulls/N/comments`."* I had internalized that as "reviews alone misses comments" and was then blindsided by the inverse: a GitHub **approval carries no comment body**, so an empty-body `APPROVED` is *structurally invisible* to any comments-oriented tool. I told the approver that #12324 had no APPROVED review; `jkiviluoto-nv` had approved 53 minutes earlier. Four independent instruments (`pulls/N/reviews`, the MCP reviews tool, GraphQL `reviewDecision`, GraphQL `latestReviews`) all agreed against me ([an empty-body APPROVED is invisible to a comments endpoint](../learnings/1785849572099-an-empty-body-approved-is-invisible-to-a-comments-.md)). ⇒ ⭐⭐⭐ **A directional statement of a symmetric rule teaches only the direction you were burned in — state both, or the untaught half returns as a fresh defect.** ⭐⭐ **A fresh measurement contradicting yours means audit your instrument before disputing the peer.**

Read STATE from `pulls/{n}/reviews` or GraphQL; read inline feedback from `pulls/{n}/comments`; read conversation from `issues/{n}/comments`. A bare "no approval seen" sourced from a comments listing is not a measurement.

Picking the wrong endpoint is the *cheap* version of the same error, and it produced a fabricated fact twice in one afternoon by two different agents. **`pulls/N/files` is cumulative vs the base** and inherits everything a merge commit dragged in; **`commits/<sha>` is what that push wrote.** I had recorded *"push `08181a69b4` carried 33 added `.github/workflows/*.yml` ⇒ the bot-can't-push-workflows issue is conclusively stale."* Measured: that commit has **1 parent, 2 files, +2/−3, zero workflow paths** — the workflow paths live in a two-parent merge, and there are 72 of them, not 33. So the retraction was two-part: **wrong commit *and* a fabricated count**, and it had me one dispatch away from contradicting a correct peer. The `workflows` App permission gates the *push*, at receive time — inherited ancestry in a cumulative view is not evidence of a push ([pulls-N-files is cumulative, commits-sha is what the push wrote](../learnings/1785847094771-pulls-n-files-is-cumulative-commits-sha-is-what-th.md)).

`gh run list --workflow <f>` has a filter that does not filter: it can return rows from *other* workflows. A supervisor read `conclusion` off such rows and reported "CI hasn't run in over two weeks" on slang#11135 — the rows were actually a `pull_request_review_comment`-triggered bot-assistant gate, not the build pipeline. Before asserting any CI state, read `.name` **and** `.event` **and** `.head_repository` off the rows you actually got; `action_required` on a fork PR is a maintainer approval gate, not a failure ([gh run list --workflow does NOT constrain results](../learnings/1785847099622-gh-run-list-workflow-does-not-constrain-results-ch.md)).

## Runs, Attempts and Job Names: Reads That Answer a Narrower Question (2026-08-06 fold)

**`gh run view <id> --json jobs` — and `GET /actions/runs/{id}/jobs` — return ONLY the latest attempt.** A job that failed on attempt 1 and was re-run green is **structurally invisible** to both. I had correctly reported a Falcor failure on my PR head, later "checked myself" with `gh run view 31047790392 --json jobs`, saw `Test (Falcor) = SUCCESS`, and **retracted a true report**. The tell that history exists is one field: `gh api …/actions/runs/<id> --jq .run_attempt` > 1 ⇒ a re-run happened; then read `…/actions/runs/<id>/attempts/1/jobs`. On that run (`run_attempt: 2`) attempt 1 held `Test (Falcor)` **FAILURE** (job `92454170957`, runner SLANGWIN4, `Mogwai.exe exited with return code 3221225477` = `0xC0000005`) and attempt 2 the same job green. Any returned job also carries `run_attempt` — if it reads `2` you are not looking at the original outcome ([gh run view --json jobs shows only the latest attempt](../learnings/1785992152145-gh-run-view-json-jobs-shows-only-the-latest-attemp.md)).

Two derived rules from that retraction, both larger than the endpoint. ⭐⭐⭐ **A disconfirming probe deserves MORE scrutiny than the claim it kills: an over-retraction costs as much as an over-claim and is far harder to catch, because withdrawing reads as rigour and no reviewer argues you into keeping a claim.** The question to ask of the probe is *can this instrument even represent the thing I am now saying is absent?* — mine could not, so the negative was guaranteed independent of the truth. And it arrived wearing the clothes of a mistake I had **already admitted** that session (confusing `Test (Falcor)` with `Test (Falcor Perf)`), which made "I misread the job" a ready-made explanation: ⭐⭐ **two different failure modes can produce the same surface symptom, and fixing one is not evidence about the other.** Bonus, in the same run: attempt 1 FAILED / attempt 2 PASSED on one sha is a **same-SHA pass/fail pair**, the categorical evidence a flake investigation wants — **when an API collapses history you lose the comparison, not just a data point.** Cheapest step of all, skipped for an hour: **one `gh issue list` on the failure signature** — proving-it's-not-mine and finding-who-owns-it are different questions and the second is cheaper (that failure was already tracked with 8 prior occurrences).

**Job and check-run names are not unique across workflows, so a name-keyed check-runs probe fails OPEN.** `shader-slang/slang` uses the job name `check-formatting` in *two* workflows — `check-formatting.yml` ("Check Formatting") and `check-toc.yml` ("Check Table of Contents") — so one sha returns two rows under that name from unrelated checks. On #11389 (`378491c6cdcc`) the formatting row is `failure` (run `26865648843`, 05:31:16Z) and the TOC row `success` (run `26865648858`, 05:37:22Z); a newest-wins dedup on `.name` with `sort_by(.started_at)|last` picks the TOC success and **silently clears a genuine formatting red** — it cleared #11389 and #9809 for me. Same family as the `workflow_dispatch` phantom-red (one sha, two suites) but inverted: that one *shows* stale reds, this one *hides* live ones. Both are cured by putting workflow identity in the key: **`(pr, workflow_id, job name)`**, recovering the workflow from `details_url` (`/actions/runs/<run_id>/job/<job_id>`) or by cross-checking `actions/runs?head_sha=<sha>` on `.path` ([check-formatting is a job name shared by two slang workflows](../learnings/1785990188609-check-formatting-is-a-job-name-shared-by-two-slang.md)).

**Scope that defect precisely — it is exploitable on 17/79 PRs, not "unsafe by default", and it does not flap between calls.** Measured across all 79 non-draft open slang PRs: **70/79** carry ≥1 duplicated check-run name on their head sha (up to 43 distinct duplicated names on one sha; `build` ×5 on #11389), but **duplicate names are not the dangerous shape** — most are benign retries of the same check converging on one verdict. The exploitable shape is narrower: **a `failure` coexisting with a non-failure under one name, from DIFFERENT run ids** — **17/79 = 22%**, not 89%. Nor does the probe vary: 6 consecutive calls on #9809 returned response order `failure,success` every time and `sort_by(.started_at)|last` returned `success` all 6. The real defect is that #9809's two rows share **identical `started_at` AND `completed_at`** (22:10:16Z / 22:10:59Z), so **no sort key can discriminate them** and the verdict is *unspecified* — a reason to distrust it, not evidence that it changes. ⭐⭐ **"Unspecified" and "observed to vary" are different claims and only one is falsifiable; a claim that makes a real defect sound worse is still a fabrication.** Say *order-dependent, therefore unreliable* ([correction: 17/79 exploitable, and it does not flap](../learnings/1785990889561-correction-the-check-runs-name-collision-is-exploi.md)). The detector, with the index trap that neuters it:

```bash
gh api "/repos/O/R/commits/$SHA/check-runs?per_page=100" --jq '
  [.check_runs[]|{name,c:.conclusion,r:(.details_url|split("/")[7])}]
  | group_by(.name) | map(select(length>1))
  | map(select(any(.c=="failure")) | select(any(.c!="failure")))
  | map(select(([.[]|.r]|unique|length)>1))'
```

`split("/")[7]` is the run id; **index 6 is the literal string `"runs"`**, which makes every row identical and returns a confident zero.

**When a check goes red and nothing in your repo changed, do not theorize — diff the last-GREEN job log against the first-RED one.** `Check Submodule Pointers` failed 6 consecutive merge-queue runs on slang while no commit had touched `external/mimalloc` since 07-15. The two logs, same pinned sha, name the cause outright: green 21:19:58Z `pinned 8c532c32 … against main (remote default branch)`, red 22:33:19Z `… against main3`. **Upstream microsoft/mimalloc flipped its default branch `main` → `main3`**, and the `.gitmodules` stanza has no `branch =` line, so the checker follows the *remote default* — a value living outside your repo (confirmed by `git ls-remote --symref <url> HEAD` → `refs/heads/main3`). Generalization: **any check whose input is "the upstream default branch", a floating tag, or `@latest` has a hidden external dependency**, and this class is **rerun-cannot-succeed** — 95 success / 5 failure over the last 100 runs is a clean state change, not a flake distribution. Three traps rode along: failures ~1h apart read as an hourly cron, but the workflow has **no `schedule:` block** (the cadence was merge-queue arrival rate — read the `on:` block before calling anything "the nightly"); **red ≠ blocking**, since #12352/#12353/#12322 all merged with it red because it is not a required check, so it is never grounds for a requeue nor an eviction cause; and on a high-volume repo `/actions/runs?per_page=100` can span **~12 minutes** (measured 04:30:03→04:42:38 of `total_count=40000`), so a name filter over that page returns zero and reads as "this workflow never runs" — resolve the id from `/actions/workflows` and query `/actions/workflows/<id>/runs`, always reporting the window your page actually spans ([diff the last-green log against the first-red log](../learnings/1785992236992-a-ci-failure-that-starts-with-no-local-commit-diff.md), [check-submodules went red after mimalloc flipped its default branch](../learnings/1785989696877-check-submodules-went-red-for-all-merge-group-runs.md)).

## Ancestry, Presence, and Shallow Clones: Negatives With No Failure Signature (2026-08-05 fold)

`git merge-base --is-ancestor <my-sha> origin/master` returning NO does **not** mean your work didn't land. Two independent mechanisms produce a confident FALSE indistinguishable from a true negative: **squash-merge rewrites the sha** (shader-slang repos are squash-only, so your head is never an ancestor — slang#12238 head `f3b5b51188` → NO, while the change was fully merged as `645ac5eef2`), and **a shallow clone cannot see the object** (a sha outside the fetched depth makes ancestry return FALSE, not error). Either alone makes you report "my fix isn't on master" about merged work — or redo it ([local git ancestry gives confident false negatives](../learnings/1785847142026-local-git-ancestry-gives-confident-false-negatives.md), [shallow clone mode 4: ancestry predicates false-negative at a graft root](../learnings/1785838259620-shallow-clone-mode-4-ancestry-predicates-false-neg.md)).

Verify by **content**, which is authoritative under both failure modes: `git show origin/master:<path> | grep -n <NewSymbol>` (pick a symbol that could not pre-date the change), `git ls-tree origin/master <new-test>`, or `git log origin/master --grep=<issue>`. For genuine ancestry on an unfetched sha, ask the server: `compare/<base>...<sha> --jq .status`, or `pulls/<n> --jq '{merged, merged_at, merge_commit_sha}'`.

File-existence probes fail the same way, and the obvious workaround fails too. `git cat-file -e <sha>:<path>` collapses **"path not in that tree"** and **"I don't have that tree at all"** into a single rc=128, and the idiomatic `2>/dev/null && echo PRESENT || echo absent` discards the only text that might distinguish them. Reading the stderr *looks* like the fix — but the two messages differ only because the probed file happened to exist in the **working tree**. With a path absent from disk as well, they become byte-identical apart from the ref name:

```
A′ path absent in tree, absent on disk   → fatal: path 'zzz.slang' does not exist in 'HEAD'
B′ commit unfetched,   absent on disk    → fatal: path 'zzz.slang' does not exist in '948da432…'
```

So `exists on disk, but not in <X>` is a statement about your **checkout**, not about whether `<X>` is a fetched object — and it misleads in exactly the case that matters, asking about a PR head you never fetched. **Establish the commit before asking anything about its tree:** `git cat-file -t <sha>` must print `commit` (it fails only on a genuinely missing object), or `git ls-tree --name-only <sha> -- <dir>/` must list something. For presence at a sha you may not have, the server is simplest: `contents/<path>?ref=<sha>` → 404 means genuinely absent ([git cat-file -e in a shallow clone reports FAKE ABSENCE](../learnings/1785847146872-git-cat-file-e-sha-path-in-a-shallow-clone-reports.md), [its stderr only appears to distinguish them](../learnings/1785847652028-approver-clause-gap-git-cat-file-e-sha-path-cannot.md), [verify commit-presence per-sha with the contents API](../learnings/1785841467377-verify-commit-presence-per-sha-with-the-contents-a.md)).

⇒ **A negative from a tool that lacks the data looks exactly like a negative from a tool that has it.** The positive control is cheap: run the same query against something that *must* return yes (`origin/master~1` for ancestry, `cat-file -t` for presence). If that fails too, your instrument is blind — not your commit missing. Worth noting how close the near-miss was: I nearly dismissed the `cat-file` finding because my own notes said tree/blob reads are immune to shallow-clone effects. That was true of the *ancestry-predicate* failure the rule was written about and **did not transfer**. ⭐⭐ **A rule's scope is the case it was measured on; test rather than reason when a new case merely resembles it.**

## Capability Negatives and Perishable Infra Facts (2026-08-05 fold)

**A 401/403 is path-classed, never global, and two specific signals do not measure what they appear to.** `permissions.push=false` describes push access to **git refs** — `issues:write` is a separate scope. `gh api user` 403 is *correct* behavior for a GitHub App installation token, which has no user identity at all. Both are returned by an edge that is **successfully writing**, so neither is a control: a passing edge and a failing edge return identical values ([permissions.push=false and gh api user 403 do NOT measure issues:write](../learnings/1785838110268-permissions-push-false-and-gh-api-user-403-do-not-.md)).

This class is uniquely self-concealing: **people act on a capability-negative by not trying**, so the error never surfaces in anyone's logs. ⇒ **Before recording "I can't do X", construct a case where the probe must return positive and confirm it does. If you can't construct that case, the probe isn't a control.**

Infra capability is also **perishable**. GraphQL availability on this fleet went outage (07-17) → fixed (07-17) → recurred (08-03) → fixed (08-04) — four transitions in under three weeks, superseding the "GraphQL is 401" premise in five separate notes whose REST workarounds nonetheless remain valid. ⭐ **Correcting the *extent* of a claim about a mutable condition while still stating it as a standing property leaves the claim wrong** — my framing went "401 on my edge" → corrected to "fleet-wide" → shown to be transient in both; the correction fixed the extent and kept the tense. ⇒ **Treat availability as a per-session measurement, not a fact to look up: re-probe with one call before citing it** ([gh GraphQL RECOVERED — the 401 is OSCILLATING](../learnings/1785847386829-infra-gh-graphql-recovered-2026-08-04-12-41z-the-4.md)).

⭐⭐⭐ **A capability probe is a measurement with a timestamp, not a property of the token — and this class is uniquely self-concealing because a false ceiling is discharged by *not trying*, so it never appears in anyone's transcript and decays into a permanent-looking fact that propagates by copy-paste.** Contrast a false *floor* (claiming a capability you lack), which fails loudly the first time someone relies on it. Measured 08-04: the bot's GraphQL had 401'd "Bad credentials" across several sessions, was written into shared doctrine as *"GraphQL is disabled for our token"* / *"`gh pr view --json` 401s on the bot token"* (stamped verbatim 6× in one concept file), then **recovered with no action by anyone** — no restart, no re-auth, no config change — and `updateIssue` mutations succeeded immediately ([GraphQL 401 recovered untouched; four issues sat blocked behind the false ceiling](../learnings/1785839495372-a-capability-probe-is-a-measurement-with-a-timesta.md), [a capability claim phrased as a property of the token never expires](../learnings/1785839697908-a-capability-claim-written-as-a-property-of-the-to.md)). The cost was invisible and asymmetric: four issues (#12313, #12317, #12316, #12320) sat with Issue Type blank *because of the belief*, three carrying a public sentence — *"I was unable to set the native Issue Type this session due to a token limitation"* — that had silently become false, each a standing ask of a maintainer for work the bot could already do. ⇒ **Phrase a capability finding with its timestamp and its probe** (✅ *"GraphQL 401'd at 09:4xZ; probe `gh api graphql -f query='{viewer{login}}'` before relying on it"* ❌ *"on the bot token X 401s"*); the test before writing one down is *would this sentence still be true tomorrow if the cause were transient?* **Re-probe at session start** (one call unblocked four chains here). **Never collapse independent capabilities** — GraphQL availability and write scope are unrelated: on the very edge that just ran four mutations, `gh api user` still 403s and `permissions.push` is still `false`. And **when a capability recovers, sweep the artifacts that deferred to it, not just the wording** — grep your own posted comments for the limitation sentence, because a discharged limitation leaves live instructions behind it where readers land; the prose fix is the cheap half, the queue of things not attempted is the expensive half. The retrieval failure that let it survive: both tiers filed the correcting fact under the *outage* (the incident) rather than under the *phrasing habit* (the mechanism), so a task about capability never retrieved it — **key a lesson to the question that will summon it, never to the incident that produced it.**

## Search Is Not a Counting or Absence Instrument (2026-08-05 fold)

`gh search issues` returns **false zeroes** — the index lags, so a fresh or low-traffic issue is absent from results while existing perfectly well. I used it to conclude "zero open issues track this" and was about to file on that basis. The reliable check is a **structurally different instrument**: enumerate `repos/{o}/{r}/issues?state=open&per_page=100` (paginated) and regex titles+bodies locally — 60 open issues, one pass, no index involved ([never dedup issues with gh search](../learnings/1785856116224-never-dedup-issues-with-gh-search-and-failed-on-a-.md), [title-only issue search is not a prior-art claim](../learnings/1785880085907-title-only-github-issue-search-is-not-prior-art-cl.md), [query the body dimension for prior art](../learnings/1785881386033-github-prior-art-search-query-the-body-dimension-a.md)).

Code search is worse than lagging — it is **stale in a way that reads as current**: it returned a file that had been *deleted* as a live hit. The correction here is the durable part. My first instinct was to blame the stale index for two false advisories; tracing provenance showed **neither came from search at all** (one originated in a diff-scoped Devin flag relayed verbatim; the other in Devin's flag text passed through unchecked), and `search/code` was touched exactly once, *after* the challenge, while discharging an advisory — where the stale hit was **caught and overridden** by a live per-workflow read. The instrument worked as caught-and-corrected; the actual cause was uncritically forwarding a diff-scoped reviewer's open question as a finding ([a stale code-search index returns a deleted file as current](../learnings/1785856771209-a-stale-code-search-index-returns-a-deleted-file-a.md), [gh search code silently excludes files](../learnings/1785867483864-mechanism-established-gh-search-code-silently-excl.md)). ⇒ ⭐⭐⭐ **When one claim in a batch is challenged, re-audit the whole batch — and check the provenance of each item before assigning a common cause.** A tidy shared mechanism for several errors is attractive and frequently wrong.

Same note, separate lesson worth carrying: **"a job failed on a run that used the box" is not "the job failed because of the box."** A cost figure of "3 merge-queue evictions caused by this bad runner" survived several review rounds, mine and my parent's; auditing per-job `runner_name` before posting collapsed one of the three — that PR's only failing job was a Falcor image test that **also fails on healthy hosts**. The honest figure was 2. Ask which *job* failed on which `runner_name`, and whether it fails elsewhere in the same window.

## A Proxy Inverts When Its Precondition Flips (2026-08-05 fold)

A supervisor nudge fired the "no resumable GitHub artifact" gap on slang#12337 and asked for a 5-bullet comment. **The premise was measurably false and posting would have degraded the artifact.** `comments=0` was TRUE; "no artifact / invisible to any human" was FALSE, because **our own bot authored the issue** — the artifact is the 8,783-byte **body**, and every fact the nudge listed as missing was already in it (verified by grep with a zero-control, not from memory). `comments=0` was the *intended* state: the analysis went in via three in-place body PATCHes precisely because a PATCH notifies nobody ([comments==0 only proxies "no artifact" for issues filed by SOMEONE ELSE](../learnings/1785846721964-comments-0-only-proxies-no-github-artifact-for-iss.md)).

⇒ **`comments==0` is a valid artifact-absence proxy only for issues filed by others.** When we authored the issue, the body is our footprint, so the proxy **inverts — it fires hardest exactly where the public footprint is most complete.** Same family as `permissions.push` for `issues:write` and `rate_limit` as an auth probe: the instrument answers a different question than the one being asked, and the answer is locally correct. ⇒ **Before acting on a detector, check whether its precondition holds for this case; a detector firing is a claim, not a fact.**
