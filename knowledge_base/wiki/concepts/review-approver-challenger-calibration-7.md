## Retraction hygiene: a correction filed as a new atom does not disarm the stale one

The 08-03 slang-rhi sweep is this page's own worst case, and it generalizes into the strongest rule on the page. Three independent surfaces (the approver's #800 and #801 rows, the orchestrator's project notes, this concept page) each carried the residency-polarity error; each got a **new** correction atom; and the stale wording kept being read, because a correction filed alongside the error does not remove it from where readers land. What actually disarms it: **name the file and quote the superseded sentence verbatim**, then sweep for the *superseded* phrasing — grepping your fix cannot match the stale text it replaced. The sweep order that catches everything: headings → title/frontmatter → tables → index rows → prose → **serialized payloads** (`*.json`), and specifically the `challenger` field of an already-recorded `approval_decisions` row: prose artifacts are working notes, **the ledger row is the audit artifact of record**, and `record_decision` is idempotent per `(repo, pr, commit_sha)` so re-recording corrects in place rather than appending — there is no excuse for leaving it stale. Watch for surfaces a linter or concurrent process copied your text into (a mid-session restructure duplicated one index bullet into an archive file, and the stale copy survived two rounds of correcting the "original"), and re-run the critique stage afterward since post-approve edits invalidate the attestation hashes ([[approver/challenger-miss] the retraction's blast radius includes the RECORDED LEDGER ROW](../learnings/1785785616042-approver-challenger-miss-n-sources-agree-is-a-clai.md)).

Two supporting facts about *why* the error persisted through two retractions. First, **the failure was recall, not evidence-gathering**: two agents made the same error on the same fact in the same week while each already held a note recording it correctly — the approver's own `pr-802` row carried, marked `FACT`, the verbatim `GPUFamilyApple6 not supported; using per-encoder useResource fallback` line and the conclusion that CI exercises the fallback. Neither grepped. So **before asserting any environment/coverage premise, grep your own store for the distinguishing token** (here `Apple6`) — a premise about a *stable property of the CI environment* is exactly the kind of fact you have probably already established and forgotten, and it is cheaper than any log fetch. **Cross-check sibling rows in the same subsystem before filing**: two adjacent rows asserted **opposite defaults for the same flag**, and a 30-second grep would have surfaced the contradiction long before the human join did. Second, **label the evidence class whenever a citation becomes load-bearing for more than one chain** — calling job `91655709489` "the one job where the device check failed" conflated job-level failure with device-check failure (the job's conclusion was `success`) and a same-run observation with a cross-job environment inference (the line came from a different commit's log). The inference remains valid — same job name/label/adapter, and `GPUFamilyApple6` is a driver property of the adapter, independent of whether any shader compiled — but it must be **labelled** as an environment inference, or the next reader upgrades it to a direct observation for free ([[approver/challenger-miss] narrowing a claim is not testing its premise — and the correct fact was already in my own store (recall failure, not evidence failure)](../learnings/1785778812255-approver-challenger-miss-narrowing-a-claim-is-not-.md)).

And the mirror-image calibration that the whole episode teaches: **a caveat can be wrong in the direction of EXCESS caution, and that is still an error.** Most atoms on this page warn against rounding *up*; this is the other failure. Two rows recorded a configuration as "merged unverified" when CI had been running that exact configuration by default the whole time. Withholding on a question the evidence already answered is not free — it burns maintainer trust and, worse, **points attention at the wrong risk.** So run the mirror check on every caveat, not just every approval: *"what would I have to observe for this caveat to be UNNECESSARY — and have I looked for it?"* The standing rule of one adversarial retry before writing "could not determine" extends to retrying against the possibility that **the answer is favorable to the PR**. A config you call "unverified" deserves one direct check of what CI actually does by default — "needs a special env var to exercise" is a claim about CI's default, and CI defaults are cheap to read and frequently counter-intuitive (here "modern Apple Silicon ⇒ modern path" is exactly backwards on a Paravirtual device). And **when a green run cannot show you a diagnostic, look for the failing SIBLING job** rather than concluding the fact is unobtainable: same image, same adapter, different outcome — `Debug callback output` measured 0 in four green logs and **3** in the one job where the Metal device check failed. One failing sibling settled a question twice declared unsettleable. Check the *assignment* site, not just the print site, to know which runs can carry the value at all ([[approver/calibration] a caveat can be wrong toward EXCESS caution — the sibling-job trick](../learnings/1785778241162-approver-calibration-a-caveat-can-be-wrong-in-the-.md), [[approver/challenger-miss] a diagnostic captured ONLY on the failure path cannot be read from a green log](../learnings/1785778085689-approver-challenger-miss-a-diagnostic-captured-onl.md)). The generalized precondition, worth memorizing: **before inferring a runtime configuration from a missing log line, prove the line would be (a) generated, (b) captured, and (c) printed at that verbosity.** On slang-rhi that decomposes into two independent suppressors, either alone sufficient — `checkDeviceTypeAvailable` assigns `result.debugCallbackOutput` only inside `RETURN_NOT_AVAILABLE` (`tests/testing.cpp:884`) while the reporter's `printf` is unconditional (an unconditional print does not imply an unconditional value), and `Info`-severity messages route to doctest `INFO()`, flushed only on failure or `-v`. One more scoping rule from the same correction: **before calling a code path zero-coverage, grep for PRE-EXISTING tests that reach it** — coverage is a property of the test suite, not of the diff (seven `bind-pointers-*.metal` cases already exercised the path, one of them existing *specifically* to force the non-base-address resolve).
