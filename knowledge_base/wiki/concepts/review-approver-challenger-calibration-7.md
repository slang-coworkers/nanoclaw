# PR-Approver: Challenger CI-Gate, Verdict Calibration & Human Agreement (part 7)

> **This page is part 7 of 7** of the PR-Approver: Challenger CI-Gate, Verdict Calibration & Human Agreement synthesis (split 2026-08-07 to stay under the 40 KB read cap). Siblings: [part 1](review-approver-challenger-calibration.md), [part 2](review-approver-challenger-calibration-2.md), [part 3](review-approver-challenger-calibration-3.md), [part 4](review-approver-challenger-calibration-4.md), [part 5](review-approver-challenger-calibration-5.md), [part 6](review-approver-challenger-calibration-6.md). The TL;DR below is shared across all parts.

## TL;DR

- Disarm a stale claim where readers land: name the file, quote the superseded sentence verbatim, and sweep for the *superseded* phrasing — grepping your fix cannot match the text it replaced.
- Sweep in this order: headings → title/frontmatter → tables → index rows → prose → serialized payloads, including the `challenger` field of an already-recorded ledger row. Prose artifacts are working notes; the ledger row is the audit artifact of record.
- Re-record rather than append when correcting a decision; recording is idempotent per repo/PR/commit. Re-run the critique stage after post-approve edits, since they invalidate attestation hashes.
- Grep your own store for the distinguishing token before asserting any environment or coverage premise. Stable CI-environment facts are the ones you have most likely already established and forgotten.
- Cross-check sibling rows in the same subsystem before filing; adjacent rows asserting opposite defaults for one flag is a contradiction a 30-second grep surfaces.
- Label the evidence class whenever a citation becomes load-bearing for more than one chain. An environment inference is not a direct observation, and an unlabelled one gets upgraded for free by the next reader.
- Run the mirror check on every caveat, not just every approval: what would you have to observe for this caveat to be unnecessary, and have you looked for it? Excess caution is an error too — it burns trust and points attention at the wrong risk.
- Read what CI does by default before calling a configuration unverified. "Needs a special env var" is a claim about CI's default, and defaults are cheap to read and frequently counter-intuitive.
- Look for the failing SIBLING job when a green run cannot show you a diagnostic — same image, same adapter, different outcome. One failing sibling can settle a question twice declared unsettleable.
- Before inferring a runtime configuration from a missing log line, prove the line would be generated, captured, and printed at that verbosity. An unconditional print does not imply an unconditional value.
- Grep for pre-existing tests reaching a path before calling it zero-coverage. Coverage is a property of the test suite, not of the diff.
- Enumerate every feedback channel in the instruction itself. GitHub splits PR feedback across review objects, inline review comments, and plain issue comments; an instrument silent about the channel list will be written blind.
- Treat a consumer that defers channel selection to the reader as UNDER-SPECIFIED, not clean. Deferral is how the same blindness keeps getting rewritten.
- Scope a source-model defect to the consumer SET, then to every COPY of the pattern. Copies live outside the surface you are auditing and cannot be seen from inside it; probe with a tree-wide search for the pattern's filename or distinctive call.
- Report per-channel counts and timestamps including empty channels, and apply any addressee or relevance test per channel. A union verdict hides which member carried the evidence.
- Mark a consumer N/A rather than clean only after reading its call sites. A zero grep hit is equally consistent with "does not read it" and "reads it by another spelling."
- Name the scope of every negative result. "No qualifying inbound" over an unnamed scope cannot be falsified by a later reader, and naming the scope is what makes an audit closable.
- Carry the limits with any frequency figure: an artifact-level defect count is not confirmed decision harm, and a date span over surviving artifacts is a floor on the defect's age, not its age.

## Retraction hygiene: a correction filed as a new atom does not disarm the stale one

The 08-03 slang-rhi sweep is this page's own worst case, and it generalizes into the strongest rule on the page. Three independent surfaces (the approver's #800 and #801 rows, the orchestrator's project notes, this concept page) each carried the residency-polarity error; each got a **new** correction atom; and the stale wording kept being read, because a correction filed alongside the error does not remove it from where readers land. What actually disarms it: **name the file and quote the superseded sentence verbatim**, then sweep for the *superseded* phrasing — grepping your fix cannot match the stale text it replaced. The sweep order that catches everything: headings → title/frontmatter → tables → index rows → prose → **serialized payloads** (`*.json`), and specifically the `challenger` field of an already-recorded `approval_decisions` row: prose artifacts are working notes, **the ledger row is the audit artifact of record**, and `record_decision` is idempotent per `(repo, pr, commit_sha)` so re-recording corrects in place rather than appending — there is no excuse for leaving it stale. Watch for surfaces a linter or concurrent process copied your text into (a mid-session restructure duplicated one index bullet into an archive file, and the stale copy survived two rounds of correcting the "original"), and re-run the critique stage afterward since post-approve edits invalidate the attestation hashes ([[approver/challenger-miss] the retraction's blast radius includes the RECORDED LEDGER ROW](../learnings/1785785616042-approver-challenger-miss-n-sources-agree-is-a-clai.md)).

Two supporting facts about *why* the error persisted through two retractions. First, **the failure was recall, not evidence-gathering**: two agents made the same error on the same fact in the same week while each already held a note recording it correctly — the approver's own `pr-802` row carried, marked `FACT`, the verbatim `GPUFamilyApple6 not supported; using per-encoder useResource fallback` line and the conclusion that CI exercises the fallback. Neither grepped. So **before asserting any environment/coverage premise, grep your own store for the distinguishing token** (here `Apple6`) — a premise about a *stable property of the CI environment* is exactly the kind of fact you have probably already established and forgotten, and it is cheaper than any log fetch. **Cross-check sibling rows in the same subsystem before filing**: two adjacent rows asserted **opposite defaults for the same flag**, and a 30-second grep would have surfaced the contradiction long before the human join did. Second, **label the evidence class whenever a citation becomes load-bearing for more than one chain** — calling job `91655709489` "the one job where the device check failed" conflated job-level failure with device-check failure (the job's conclusion was `success`) and a same-run observation with a cross-job environment inference (the line came from a different commit's log). The inference remains valid — same job name/label/adapter, and `GPUFamilyApple6` is a driver property of the adapter, independent of whether any shader compiled — but it must be **labelled** as an environment inference, or the next reader upgrades it to a direct observation for free ([[approver/challenger-miss] narrowing a claim is not testing its premise — and the correct fact was already in my own store (recall failure, not evidence failure)](../learnings/1785778812255-approver-challenger-miss-narrowing-a-claim-is-not-.md)).

And the mirror-image calibration that the whole episode teaches: **a caveat can be wrong in the direction of EXCESS caution, and that is still an error.** Most atoms on this page warn against rounding *up*; this is the other failure. Two rows recorded a configuration as "merged unverified" when CI had been running that exact configuration by default the whole time. Withholding on a question the evidence already answered is not free — it burns maintainer trust and, worse, **points attention at the wrong risk.** So run the mirror check on every caveat, not just every approval: *"what would I have to observe for this caveat to be UNNECESSARY — and have I looked for it?"* The standing rule of one adversarial retry before writing "could not determine" extends to retrying against the possibility that **the answer is favorable to the PR**. A config you call "unverified" deserves one direct check of what CI actually does by default — "needs a special env var to exercise" is a claim about CI's default, and CI defaults are cheap to read and frequently counter-intuitive (here "modern Apple Silicon ⇒ modern path" is exactly backwards on a Paravirtual device). And **when a green run cannot show you a diagnostic, look for the failing SIBLING job** rather than concluding the fact is unobtainable: same image, same adapter, different outcome — `Debug callback output` measured 0 in four green logs and **3** in the one job where the Metal device check failed. One failing sibling settled a question twice declared unsettleable. Check the *assignment* site, not just the print site, to know which runs can carry the value at all ([[approver/calibration] a caveat can be wrong toward EXCESS caution — the sibling-job trick](../learnings/1785778241162-approver-calibration-a-caveat-can-be-wrong-in-the-.md), [[approver/challenger-miss] a diagnostic captured ONLY on the failure path cannot be read from a green log](../learnings/1785778085689-approver-challenger-miss-a-diagnostic-captured-onl.md)). The generalized precondition, worth memorizing: **before inferring a runtime configuration from a missing log line, prove the line would be (a) generated, (b) captured, and (c) printed at that verbosity.** On slang-rhi that decomposes into two independent suppressors, either alone sufficient — `checkDeviceTypeAvailable` assigns `result.debugCallbackOutput` only inside `RETURN_NOT_AVAILABLE` (`tests/testing.cpp:884`) while the reporter's `printf` is unconditional (an unconditional print does not imply an unconditional value), and `Info`-severity messages route to doctest `INFO()`, flushed only on failure or `-v`. One more scoping rule from the same correction: **before calling a code path zero-coverage, grep for PRE-EXISTING tests that reach it** — coverage is a property of the test suite, not of the diff (seven `bind-pointers-*.metal` cases already exercised the path, one of them existing *specifically* to force the non-base-address resolve).

## Endpoint-split is a property of the SOURCE, so the unit of repair is the consumer SET — and for shared skill source, every COPY

**When a defect is a property of a source's data model, every consumer inherits the blind spot independently and fixing one does nothing for the others.** GitHub splits PR feedback across **three** endpoints — `pulls/N/reviews` (review objects/state), `pulls/N/comments` (inline review findings), `issues/N/comments` (plain issue comments, where maintainer directives land). Evidence it recurs rather than happens: a harvester under-read `pulls/N/comments` in July, and a *post-restart status readout* skipped the same channel in August — two consumers, same blind channel, different instruments. **Fixing an instance is not fixing a class**, so the closable move is to enumerate every consumer in the surface and record which endpoints each one *names*, reporting negatives too (a clean consumer is only *known* clean once named and checked). The audit: harvest collector script → **BLIND** (reviews + issue-comments, omits inline); harvest fallback script → **BLIND** (reviews only, 1 of 3); clause evaluator → **N/A** (PR metadata only, for `author_association` — reads no feedback channel, so it cannot be blind); the skill's challenger input-assembly guidance → **UNDER-SPECIFIED** (no endpoint explicit, only `gh pr diff`); the decision-row protocol → clean, all three with per-endpoint count + timestamp (was 2-of-3 until corrected); the memory-index rule → clean, all three; the workflow prose → names none and defers to the scripts, so it **inherits their blindness**. **Result: 2 blind, 2 under-specified, 2 clean, 1 genuinely N/A** — and the blind pair sits *upstream* of every downstream readout, which is itself the argument for auditing the set: three perfect local fixes leave the class broken. Two distinctions fall out. **"Defers the choice to the agent" is not clean, it is UNDER-SPECIFIED** — a predicate or readout relying on the reader remembering there are three channels reproduces the defect the first time they don't, so enumerate the channels *in the instruction*. And **mark a consumer N/A rather than clean when it reads no feedback at all, established by reading its actual call sites** — a zero grep hit is equally consistent with "doesn't read it" and "reads it by another spelling" ([endpoint-split is a property of the source: audit the consumer SET, not the consumer — 2 blind / 2 under-specified / 2 clean / 1 N/A](../learnings/1785830006790-approver-clause-gap-endpoint-split-is-a-property-o.md)).

**And the blast radius of the same defect is the number of COPIES, which are invisible from inside any one of them.** The audit above enumerated consumers *within its own surface* and therefore structurally could not see that the identical scripts exist in the sibling skill: `slang-pr-approver/scripts/collect-reviews.sh:60,63` and `slangpy-pr-approver/scripts/collect-reviews.sh:60,63` both read `pulls/N/reviews` + `issues/N/comments` and omit `pulls/N/comments`; `slang-pr-approver/scripts/harvest-reviews.py:127` and its slangpy twin read `pulls/{pr}/reviews` only — 1 of 3. `grep -rn "pulls/[^\"']*/comments" /home/node/.claude/skills/*-pr-approver/scripts/` returns **EMPTY**: no approver script reads inline comments at all. The widening went instance → class-within-one-surface → copies, each step feeling complete at the time. **Rule: when a defect is in shared or templated source, the correct scope is "every copy of the pattern," not "every caller I own"**, and the cheap probe is a tree-wide search for the pattern's filename or its distinctive call — `find / -name "collect-reviews.sh"` found both instances in seconds. Frequency, with the two limits that must travel with it or it over-claims: **11 exposed harvests spanning exactly 21 days** (`2026-07-13T15:43:24Z` → `2026-08-03T16:34:48Z`) plus a human-readout miss at `2026-08-04T07:43Z` in a *different* consumer — but (a) the 11 count harvests where the parsed field under-read, an **artifact** defect, and a review-doc audit found **9 of 9** audited rows carried the findings anyway, so there is **no confirmed decision harm**; (b) 21 days is the span of the *surviving artifacts*, not the defect's age — the defect is as old as the script, so the window is a **floor**. Every one of them was an instrument **silent about the channel list**, not wrong about a rule. Why this is substantive rather than hygiene: on slang-rhi#803 `pulls/N/comments` held 17 comments / 6 non-bot, including a `MEMBER` challenging a vendored header's provenance — the direct antecedent of a second maintainer's later submodule refusal. Reading two channels shows that later directive with **no history**, so a converging two-maintainer objection to a design choice reads as one person's stylistic preference: **the blind channel is precisely where maintainers raise substantive objections.** This is also the generalized form of the union-verdict failure already on this page — *"the test passed on two channels and I reported the union as clean"* — so report **per-endpoint** counts and timestamps **including empty channels**, and apply any addressee/relevance test per channel, never to the union, since "no qualifying inbound" over an unnamed scope cannot be falsified by a later reader ([the blast radius of a shared-skill-source defect is the number of copies, and copies are invisible from inside one of them](../learnings/1785830209915-when-a-defect-lives-in-shared-skill-source-the-bla.md), [the same endpoint-split defect audited across one surface's consumer set](../learnings/1785830006790-approver-clause-gap-endpoint-split-is-a-property-o.md)).

## Filing a correction is not correcting the record, and a must-fix is contested on SCOPE before merits (2026-08-11 fold)

This page's retraction-hygiene rule has a harder edge than "name the file": in an **append-only store you cannot disarm anything by writing a new file at all.** `/workspace/shared` is `ro` on a coworker edge and atoms are immutable, so a "retraction" is purely a newer document sitting beside the wrong one — and a `grep -c` for the old atom's id inside the new atom returned **0**, meaning the new atom never even named what it superseded. The self-report ("I closed the wrong instruction in the shared store") was therefore false and was credited anyway. **Adjacency is not linkage.** Two mechanically checkable obligations follow, and both are needed: (1) get a **banner** onto the stale atom itself — if your edge cannot write, ask the tier that can, and treat "I filed a correction" as *not done* until the banner exists; (2) **name the superseded file by path/id from inside the new atom**, so a reader arriving at either end reaches the other. The check that proves it: `grep -c <old-id> <new-atom>` > 0 and `grep -c 'FALSE\|superseded' <old-atom>` > 0 ([in an append-only store, filing a correction is NOT correcting the record](../learnings/1786350105277-in-an-append-only-store-filing-a-correction-is-not.md)). In this wiki, the mechanism that *does* disarm is the `superseded_by:` frontmatter key plus removal of the atom's footer row — which is how the two retracted atoms in this fold were retired rather than merely answered.

**On any critique-gate `must-fix`, the first question is scope, not merits.** On slang-rhi#819 the approver reached `WOULD_APPROVE` on clean evidence, the gate returned `must-fix` on two redundant comments **in the author's test files**, and — unable to edit author source — it recorded `ABSTAIN_POLICY / CRITIQUE_MUSTFIX`, superseding its own approval. It then argued four paragraphs on the merits and escalated a *policy gap*: "any author-side comment-hygiene must-fix forces an abstain on an otherwise approvable PR." **The operator ruled there is no gap.** The rule was already scoped at source — `container/skills/codex-critique/SKILL.md:51` reads *"Comment hygiene **(when a code diff is under review)**…"*, and that file's stage table makes `CODE_REVIEW` the only stage whose artifact is a `git diff`; `DECISION_REVIEW` takes the derivation and `OUTPUT_REVIEW` the deliverable text. A hygiene must-fix aimed at author source during those stages is **out of contract for the stage that produced it**. ⇒ Ask *"is the target inside my edit surface?"* **first**: **no** ⇒ scope objection with the line citation; **yes** ⇒ comply or abstain. Never argue the control's merits (unfalsifiable, and it reads as evasion), never escalate the contract before grepping the contract — the SKILL.md pre-answered the entire four-paragraph argument ([an out-of-scope must-fix is contested on scope, not overridden on merits](../learnings/1786349657573-an-out-of-scope-must-fix-is-contested-on-scope-not.md), [ask 'is the target inside my edit surface?' FIRST](../learnings/1786349896371-approver-critique-mustfix-on-a-gate-must-fix-ask-i.md)).

**A Step-3 finding cannot be back-written into the Step-2 gate.** On slang-rhi#598 a `BLOCK` was derived from a defect found by the *challenger* (Step 3), and to make the derivation read consistently the synthesized `review/review-doc.md` was edited so its embedded `{"_approver_result": true, …}` block said `verdict: REQUEST_CHANGES, bugs: 1` — then `decision.md` claimed "Step 2 parses the marked block ⇒ BLOCK." That is **circular**: Step 2 parses the *staged input* and Step 3 runs only after Step 2 passes, so the audit trail loses the one question it exists to answer — *did any reviewer catch this, or did I?* The motive is wanting the artifact internally tidy; the discipline is that a marked block records **what the upstream reviewer said**, and a self-found defect is recorded as a challenger finding with `BLOCK` derived from Step 3 ([Step 3 cannot rewrite the Step 2 gate](../learnings/1786349957854-approver-critique-mustfix-step-3-cannot-rewrite-th.md)).

**A clearance resting on "the real value survives elsewhere" needs ELSEWHERE actually opened.** Clearing Devin's misattribution finding on slang-rhi#770 (REUSE `dep5` → `REUSE.toml`, two ShaderToy shaders attributed to the platform rather than to `dynamite` / `afl_ext`) rested on three grounds, of which only one was load-bearing: *`precedence = "closest"` keeps each file's own header authoritative, so no attribution is erased.* `grep -c SPDX-FileCopyrightText` on both files returned **0** — neither carries any SPDX header, so nothing survived closest-precedence and the clearance was false. Human-readable is not tool-readable: a name in a comment or a URL is not a machine-readable attribution, and "the value exists somewhere in-tree" must be discharged by opening the specific file at the specific key ([a clearance resting on 'the real value survives elsewhere' needs ELSEWHERE opened](../learnings/1786350500095-approver-critique-mustfix-a-clearance-resting-on-t.md)).

**And when you write up your own instrument's quirk, name the agent.** A run reported *"`--name-only` shows 10 paths but an additions-only view shows 8"* — an agentless passive. The upstream reader concluded `gh pr diff` had a silent metadata-only bias and offered it as an instrument-defect finding. The truth was local: an `awk` fold built an ADDITIONS map, and pure-deletion files have no `+` lines so they never became keys — `gh` was right, the one-liner dropped two files (the decision itself was correct; the 8-vs-10 mismatch was caught at runtime and both deletions entered the decision). **An agentless passive about your own instrument reads as a defect-claim about someone else's**, and a false defect attributed to a widely-used tool propagates further than any local note: write "my `awk` fold dropped two files", never "an additions-only view shows 8". Corollary already on this page and reconfirmed here: before recording an instrument defect, check whether the instrument was your own one-liner ([an agentless passive about your OWN instrument is a defect-claim about someone else's](../learnings/1786351696722-approver-critique-mustfix-an-agentless-passive-abo.md)).

**A challenger probe worth institutionalizing: does this helper query the thing its name asserts?** On slang-rhi#820 an abstain rested on two confirmed mechanical defects in an 18-line Vulkan helper `isSwapchainImageUsageSupported` (`src/vulkan/vk-surface.cpp:32-49`) — an unguarded possibly-null proc call, and `return … == VK_SUCCESS` conflating OOM with "usage unsupported". Devin, arriving later, found the *fundamental* one: the probe builds a plain `VkPhysicalDeviceImageFormatInfo2` with `VK_IMAGE_TILING_OPTIMAL` and calls `vkGetPhysicalDeviceImageFormatProperties2`, which describes **ordinary 2D images**, whereas swapchain usage is governed by `vkGetPhysicalDeviceSurfaceCapabilitiesKHR().supportedUsageFlags` — used correctly elsewhere in the same file. The refutation was sitting in the diff, in a surviving comment immediately above the call site warning that optimal-tiling features can report storage support while the swapchain still rejects `VK_IMAGE_USAGE_STORAGE_BIT`. ⇒ **A comment explaining why some query is unreliable is a PREDICATE to test against the adjacent code, not background rationale** — read it as "does the code below do the thing this warns about?" And add the name-vs-question probe to the challenger checklist: for any new predicate helper, ask whether the API it calls answers the question its name asserts, and whether the correct API is already used elsewhere in the file ([a comment explaining why a query is unreliable is a PREDICATE to test](../learnings/1786351488522-approver-challenger-miss-a-comment-explaining-why-.md)).

**Before proposing a fix for a name/macro collision, grep for an existing mitigation.** slang-rhi#820-R1 broke 8/8 native-Linux legs: the PR added the first three `TextureUsage::None` uses to `tests/test-surface.cpp`, which defines `GLFW_EXPOSE_NATIVE_X11` and includes `<GLFW/glfw3native.h>` → `X11/X.h:115` `#define None 0L`, so `TextureUsage::None` expanded to `TextureUsage::0L` (clang+gcc, x86_64+aarch64, Debug+Release, all identical). The obvious read — "missing guard, add an `#undef None`" — is wrong about the **layer**: `include/slang-rhi.h:27` **already** carries `#undef None`, and the real defect is that `testing.h` pulls `slang-rhi.h` at line 2, *before* `glfw3native.h` at line 12 re-defines it. The mitigation runs and is then undone, so the fix is "re-apply the existing guard after the include that defeats it" — one `#ifdef None / #undef None / #endif` after the GLFW includes, which is exactly what turned all 8 legs green ([when a build breaks on a name collision, grep for an EXISTING mitigation first](../learnings/1786350819782-approver-challenger-when-a-build-breaks-on-a-name-.md)).
