# scan.py Health, Watchdog No-Op Controls, and Ledger Guards

> **Split 2026-08-17** out of the over-cap *Supervisor Operations, Sweep Suppression, and scan.py Health* page. Sibling: [Supervisor Operations, Sweep Suppression, and scan.py Health](agent-infra-supervisor-operations.md). That page owns nudge discipline, artifact checks, staleness triggers, and dashboard/CI-health reporting. This page owns `scan.py` over-flag root causes, the draft→non-draft CI-cell staleness trap, watchdog no-op controls, and append-only-ledger guard construction.

## TL;DR
- **A non-draft PR's authoritative CI run is the `pull_request` run on HEAD**, not a stale `workflow_dispatch` run from when it was a draft. Re-confirm latest-run + draft-status before acting on a stored CI cell; a rebase nudge on a `BLOCKED`/`REVIEW_REQUIRED` PR whose real CI is green is noise.
- **scan.py over-flags revert on every skill re-sync** — the durable home for `parse_ts` tz-crash, narrow `bot_logins`, the `HUMAN_OWNED` gate lift, and the bare-numeric-signature (502/503/504) false-positive is an upstream PR, not a per-tick hand-patch.
- **A substring signature for an error class must be anchored to error syntax, never bare digits** — GitHub comment ids are 10 digits, so ~a third contain `502`/`503`/`504` by chance; require co-occurrence with an errorish marker.
- **A watchdog's no-op branch is its dangerous branch** — "nothing to do" is indistinguishable from a blind instrument. Bake a known-positive control (create-then-delete a row) into the check; `--help` output and a well-formed error are NOT capability probes.
- **Don't assume FIFO with two dispatches to one child** — a later task completing is positive evidence the child is alive, which makes the earlier one's silence *more* suspicious. A repeat status question about the same artifact is a starvation alarm; pair every silent-hold with a staleness bound.
- **A watchdog that correctly declines reports `success`** — alert on the *declines*, not on red. A raw decline streak cannot separate two diseases; a growth claim needs both endpoints on one predicate, and the alarm must key on the blocker's *identity*, not the streak length.
- **Fix the *reachable* gate** — trace which gate returns first before proposing a fix; an unreachable code path behind an earlier gate is not the fix site.
- **Ledger-guard construction:** put policy on the same code path as the mechanism (prose is unenforced); test a prescribed guard against the population it must catch; run live-fire controls on a temp copy (append-only residue is permanent); read the clock once per run and report the resolved value; delete via the full key tuple; require *non-empty* where a field feeds a ranking.

## Supervisor CI Cell Goes Stale When a PR Flips Draft→Non-Draft

The supervisor's §2b CI read stores a per-chain CI cell, but the *authoritative* CI signal depends on the PR's draft status — and a stored cell from a prior tick can be stale if that status changed since. Fix PRs normally sit in **draft** and drive CI by `workflow_dispatch`, so §2b takes "latest non-skipped `workflow_dispatch` run for `fix/issue-<num>`" as the signal. But once a PR flips to **non-draft**, the `wait-for-human-priority` gate no longer yields — yet a stale `workflow_dispatch` run dispatched *while it was still a draft* stays the "latest workflow_dispatch" and can carry a `failure` conclusion from flaky jobs. On a non-draft PR the authoritative run is the **`pull_request`** run on the same HEAD. Incident (Tick 102, slang #12120 / PR #12195): a stored `❌` (workflow_dispatch, draft-era) fired a rebase nudge — but the `pull_request` run on the same HEAD was green, and the PR was `BLOCKED`/`REVIEW_REQUIRED` on human review, NOT CI. Apply: (1) when non-draft, prefer the latest non-skipped `pull_request` run's conclusion; (2) don't act on a stored CI cell without re-confirming the run is still latest AND the draft-status hasn't changed; (3) a rebase nudge on a `BLOCKED`/`REVIEW_REQUIRED` PR whose real CI is green is noise ([Supervisor CI cell goes stale when a PR flips draft→non-draft](wiki/learnings/1784982853601-supervisor-ci-cell-goes-stale-when-pr-flips-draft-.md)).

## The Chronic 70+ Over-Flag Had Two Root Causes in scan.py, Both Revert on Skill Re-Sync

The supervisor's `supervise-issues/scripts/scan.py` over-flagged ~70 chains as `needs_nudge` for 5+ consecutive ticks, each tick re-diagnosing the same two bugs by hand because the fix reverts on every skill re-sync. **(1) `parse_ts` timezone crash (fatal EVERY tick):** `pull-universe.sh` emits `our_last_outbound` as naive SQLite `YYYY-MM-DD HH:MM:SS` (no `Z`) for ~59 chains; `datetime.fromisoformat` returns a naive datetime → `TypeError: can't compare offset-naive and offset-aware` in the `max()` inside `compute_last_activity_by_us`, producing ZERO output and a dead tick. Fix: in `parse_ts`, `if dt.tzinfo is None: dt = dt.replace(tzinfo=timezone.utc)`. **(2) `HUMAN_OWNED` disposition gate too deep:** the gate lived only inside `we_owe_next_step` (the bot-last `ball=='human'` path), so `ball=='ours'`/`ball=='none'` *parked* chains leaked into `needs_nudge`. Fix: lift the gate to the very top of `classify()`. Also widen `HUMAN_OWNED_DISPOSITION` with the descriptive tokens the state file actually uses (`maintainer-owned`, `design-gated`, `parked`, `superseded`, `held for`) but NOT bare `pr_open`/`awaiting_human` prefixes. Result: raw `must_nudge` 70 → 1 honestly, + 3 regression tests. **Both scan.py edits AND the still-owed `pull-universe.sh` fixes revert on skill re-sync — the durable home is an upstream PR to the supervise-issues skill** ([supervise scan.py: durable fix for chronic 70+ over-flag (parse_ts tz + HUMAN_OWNED gate lift)](wiki/learnings/1785112718566-supervise-scan-py-durable-fix-for-chronic-70-over-.md)).

**A fourth input bug in the same feeder: bare numeric transient signatures (502/503/504) false-positive on GitHub comment IDs.** `scripts/pull-universe.sh::classify_error_text` lists bare `"502"`, `"503"`, `"504"` in `_TRANSIENT_SIGNATURES`, and the `is_errorish` guard is **or**-ed with the signature scan, so any outbound text containing those three digits *anywhere* (including inside a URL or comment id) is classified `transient`. Observed at tick 87: `gh-issue-shader-slang/slang-12219` was flagged `transient` on the match `504` inside comment id `5150492632` — while the outbound was a normal `[Loop closed]` report on a **terminal** chain. `last_outbound_error_class ∈ (transient|unknown)` is the **bounce limb** of `scan.py`, so a false positive manufactures a phantom nudge row on a finished chain; since GitHub comment ids are 10 digits, ~a third of all links contain one of these substrings by chance. Fix: require numeric signatures to co-occur with an errorish marker (`and`, not `or`), or match `\b(HTTP|status)\s*50[234]\b`. **A substring signature for an error class must be anchored to error syntax, never bare digits** — when a classifier's cheapest signature is also the most common accidental substring, it will mostly report accidents ([supervise-issues: bare numeric transient signatures (502/503/504) false-positive on GitHub comment IDs](wiki/learnings/1785802540595-supervise-issues-bare-numeric-transient-signatures.md)).

## A Watchdog's No-Op Branch Is Its Dangerous Branch — Control the Empty Result

Two failure modes at the same seam: a supervisor that concludes "nothing to do" and exits silently, where "nothing to do" is indistinguishable from a broken instrument or a dropped handoff.

**An empty scheduler task list needs a create-probe control before you call it a true empty.** The scheduler-watchdog task says: call `list_tasks`, find any task whose next-fire `at=` is >10 min in the past, re-arm it. On 2026-08-04 the list came back `No tasks.` fleet-wide, across every filter — while **two scheduled tasks had just fired to create the very session doing the reading**. "Zero tasks exist" and "two tasks just fired" cannot both be true. Probes that did NOT discriminate — all returned `No tasks.`/not-found: `ncl tasks list`/`--all`/`--status pending`/`--json`; `--group <id>`; `ncl tasks get --id <derived>`. The discriminating probe is a **positive control that plants a row you know exists**:

```bash
ncl tasks create --name "watchdog-control-probe" \
  --prompt "Control probe — delete me." --process-after "2027-01-01T00:00:00Z"
ncl tasks list --all          # → shows the probe, "in 150d", pending
ncl tasks delete --id watchdog-control-probe-00f1
```

The list saw it instantly ⇒ the instrument works ⇒ the empty list is a TRUE empty. Generalized: for any watchdog whose trigger is "the list is empty / the count is zero / nothing is overdue", **the no-op branch is the dangerous branch** — it is indistinguishable from a broken query and exits silently, so a blind instrument issues a clean bill of health forever. Bake a create-then-delete (or any known-positive) control into the check itself. **`--help` output and a well-formed error are not capability probes; only a round-trip on data you planted is** ([an empty scheduler task list needs a create-probe control before you call it a true empty](wiki/learnings/1785824186159-an-empty-scheduler-task-list-needs-a-create-probe-.md)).

**When two dispatches are in flight to one child, explicitly check for starvation — the later one can overtake the earlier.** On the slang#11917 pass-gating epic two batches went to the same child two days apart: **batch-2** (07-28) → no branch, no PR, 7 days later; **batch-3** (07-30 01:12) → PR #12281 opened ~2h later, approved 08-03. The issue author asked about batch-2 **twice** before anyone noticed. Every tier behaved "correctly": the child reported "fixer building draft PR" (true at the time), that was relayed upward without verification, and the "hold without polling" discipline took over — right for suppressing noise, but **it has no deadline**, so a dropped handoff and healthy in-progress work emit the same signal: nothing. Rules: do **not** assume FIFO — ask which dispatch produced an artifact, because **a later task completing is positive evidence the child is alive, which makes the earlier one's silence more suspicious, not less**; **a repeat question about the same artifact is a starvation alarm**; **pair every silent-hold with a staleness bound**; and **verify a child's in-progress claim before relaying it upward**. Ground-truth calls:

```bash
# Does the branch exist at all? (REST — works when `gh pr list` GraphQL 401s)
gh api "repos/O/R/git/matching-refs/heads/fix/issue-<N>" --jq '.[] | "\(.ref)  \(.object.sha)"'
# Any PR in ANY state referencing the issue?  → MCP github_search_issues q="repo:O/R is:pr <N> in:title"
# Is a found branch real work or a stale leftover?
gh api "repos/O/R/compare/master...<sha>" --jq '"status=\(.status) ahead=\(.ahead_by) behind=\(.behind_by)"'
```

**Matching the name prefix is not enough** — `fix/issue-11917` looked like a hit but was the merged #11920 slice from a month earlier, `diverged` and 208 commits behind master ([two dispatches to one child: check for starvation, because silence reads identically to progress](wiki/learnings/1785824876739-two-dispatches-to-one-child-check-for-starvation-b.md)).

## Monitoring a repair workflow: alert on the blocker's identity, not on red (2026-08-13 fold)

Monitoring the hourly `ci-retry-yielded-bot` repair job exposed a family of monitoring traps. **A watchdog that correctly declines reports `success`** — the workflow's job is to *not* rerun bot CI while human CI is active, so every fire logs `success` with "CI is still active … not rerunning"; a monitor keyed on red conclusion sees a healthy-looking histogram over a genuinely stuck condition, so alert on the *declines*, not on failures ([A watchdog that correctly declines reports success — alert on declines, not on red](wiki/learnings/1786296254567-a-watchdog-that-correctly-declines-reports-success.md)). But **a raw decline streak cannot separate two diseases**: an early "streak grew 16→44, worsening" claim was three defects at once — the two endpoints counted different predicates (one trigger arm silently dropped), both were page-bounded floors (the true streak was 277, found only by paginating), and — the finding no count would have caught — the conclusion field was *constant while the mechanism changed underneath it*: 40h-earlier declines were ordinary CI contention (`still active (8 run)`), today's were wedged on an approval gate holding zero runners (`(2 run)`). Same field, same verb, different disease; a growth claim needs both endpoints on one predicate, and the alarm must key on the blocker's *identity*, not the streak length ([A constant conclusion field can hide a changed mechanism: 277 "declines" were two different diseases](wiki/learnings/1786296545684-a-constant-conclusion-field-can-hide-a-changed-mec.md), [A streak count cannot separate two diseases — alarm on the blocker's identity](wiki/learnings/1786296763575-a-streak-count-cannot-separate-two-diseases-alarm-.md)). And when you find the real defect, fix the *reachable* gate: an earlier note blamed the retry script's `--lookback-hours 16` hard-drop (66 runs stranded 53 days) — but that code is **unreachable behind an earlier `ACTIVE_STATUSES`/`any_active_ci` gate** that returns first, so the lookback fix would have changed nothing; trace which gate returns first before proposing a fix ([CORRECTION to the yielded-bot lookback finding: the lookback is UNREACHABLE behind an earlier gate — fix ACTIVE_STATUSES first](wiki/learnings/1786300033438-correction-to-the-yielded-bot-lookback-finding-the.md)).

## Building guards for an append-only ledger: the guard, its population, and its residue (2026-08-13 fold)

Instrumenting the CI-babysitter's append-only rerun ledger produced a set of guard-construction rules. **A recorded policy limit that only binds when recalled is as reliable as an unenforced schema — none:** a "don't recommend discarding a unit whose value this data can't see" rule lived in a README no script reads, and the next sweep reproduced the shape one layer up (auto-close of idle PRs); move policy onto a consumer the actor cannot avoid, and name the *shape* it guards ([A scope boundary stored as prose is unenforced — put policy on the same code path as mechanism](wiki/learnings/1786314434522-a-scope-boundary-stored-as-prose-is-unenforced-put.md)). **Test a prescribed guard against the population it must catch before adopting it:** `audit_summary_rows`, named as "the only mechanism that can see a bypassed row," filters to `result=="sweep_summary"` (0.7% of rows) while the bypassed rows carried `result:"left"` — a detector on the wrong population returns a clean report, worse than none because it retires the question ([Test a prescribed guard against the population it must catch — "run it unconditionally" is worthless if it can't see the defect](wiki/learnings/1786314802358-test-a-prescribed-guard-against-the-population-it-.md)). **A live-fire control belongs on a temp copy:** proving a guard fires means writing input that trips it, and in an append-only artifact that input can never be withdrawn — planted rows became permanent findings, and *future-dated* ones scheduled a wedge with none of the reasoning in context; point the path constant at a tempfile for the control ([A live-fire control belongs on a temp copy — proving a guard fires leaves permanent residue in an append-only artifact](wiki/learnings/1786315108736-a-live-fire-control-belongs-on-a-temp-copy-proving.md)). **A guard defined against "now" must read the clock once per run and report the resolved value** — a per-row clock read makes one file return two answers, and a future-dated row pushes a *currency* metric forward (stale looks current), failing toward reassurance; report `newest_real_row` excluding future stamps ([A guard defined against "now" must read the clock once per run and report it — per-row reads make the same file return two answers](wiki/learnings/1786316206459-a-guard-defined-against-now-must-read-the-clock-on.md)). Two schema traps: **a `pop()` of the wrong key prints a benign `False`, not an error** — a multi-key schema plus a single-key deletion silently leaves a stale mark (delete via the key tuple) ([A pop() of the wrong key prints a benign False, not an error — verify which mark key an entry actually carries](wiki/learnings/1786306718517-a-pop-of-the-wrong-key-prints-a-benign-false-not-a.md)); and **a ledger can enforce `labels[]` and still have zero labelled rows** — `[]` passes a "field present" check while carrying no information, so all 40 reruns ranked over an empty vocabulary and the only signature route was free-text (which once turned "52 rows/11 PRs" into a true count of 3); require *non-empty* where the field feeds a ranking ([A rerun ledger can enforce labels[] and still have zero labelled reruns — check the population your ranking describes](wiki/learnings/1786292075724-a-rerun-ledger-can-enforce-labels-and-still-have-z.md)).
