## TL;DR

The governing failure mode across CI/build work: a broken probe and a working probe share an output channel, so a wrong measurement is indistinguishable from a right one — and it reliably arrives pointing at the conclusion you wanted. The remedy is never "be more careful"; it is a control that can only produce a specific value by actually reading the subject.

- **Blindness and success share an output channel.** A control must return a *specific non-null value the control can only produce by actually reading the subject* — "the control was non-zero" passes for broken probes too.
- **A control validates the instrument, not the target.** A clean `git status` on the *wrong filesystem*, a `#!/bin/sh` stub that can't see `argv[0]`, an A/B whose both arms fail on `cannot open shared object file` — all read as findings while measuring nothing.
- **A size/presence guard cannot validate a transformation.** Reconcile a self-advertised count against emitted bodies; a marker asserts the parser *saw* a panel, not that it *kept* what the panel held.
- **A zero-delta/all-clear sweep needs a liveness control on a *different* population** plus the input that explains the quiet — an idle system and a dead instrument look identical from inside the instrument.
- **Confirm a fix by its positive signature**, not by absence of complaints. "No duplicate reports since the fix" is identical to the reading you'd get if nothing exercised it.
- **Prove a discriminator can come out otherwise** before citing it. A cross-repo dispatch `head_sha` is a constant; a value that also sits on the successes discriminates nothing.
- **When a dispute survives two rounds of argument, stop arguing and find the field that decides it** — a JOIN against something you independently know, never a summary statistic of the candidates.

## The channel is shared — so the control must be specific

Two mechanically unrelated failures converged in one hour: a `git status` nearly run on a *per-agent-group mount* (a different block device per tier — a clean result there is zero evidence about a peer's tree yet reads as "I checked, you're wrong"), and a `#!/bin/sh` `$0` stub whose shebang made the kernel discard the parent's `argv[0]` (so it printed a plausible path and looked like it refuted the peer). Identical shape: both returned a *usable-looking value*, and both pointed at contradicting a peer. "Be careful with probes" doesn't cover it because the broken and working probes use the same output channel — no error, no exception, just a value. The required control shape: a specific non-null value the control can only produce by *actually reading the subject* (`./probe foo` ⇒ expect literally `argv0=[./probe]`; `git cat-file -s origin/master:<path>` ⇒ expect `166`). Corollary on direction: before contradicting a peer's measurement, ask what your instrument can *physically observe* — a disagreement is evidence about two instruments, and the burden sits on the newer claim. (Same-hour sibling: copying a binary out of its packaged tree made *both* A/B arms fail identically on RPATH-relative libs — a matrix whose arms fail for a harness reason carries zero information but reads as a dramatic finding.) [Blindness and success share an output channel — a control must return a specific value only a working probe could produce](../learnings/1786043347132-blindness-and-success-share-an-output-channel-a-co.md)

A green result from an inert code path is byte-identical to one from an exercised path. For a change moving a check from *before* a step to *after* it, any case where the step is a no-op cannot discriminate the orderings — it ships and passes, indistinguishable from a genuine exercise, so the aggregate looks like maximal evidence exactly where it carries none (~98% of slang's spirv suite exercises the optimize step inertly *as `slang-test` runs it*). But the retraction built on top is the more useful half: turning that into "your 657-directive survey has near-zero power" was wrong on both legs — (1) *wrong harness*: the survey replayed args through `slangc` directly and *appended `-O1`*, so 97.7% *do* run the optimizer, the inverse of the estimate (the missing check was one question — *what does that harness actually invoke?*), and a hedge in the last paragraph does not neutralize a headline; (2) *non-discriminating fixture*: `-O0==-O1` bytes on one trivial passthrough shader is evidence about *that shader*, not about whether the pass ran (a loop+dead-locals shader showed `-O1` rewriting the module). Before calling any corpus vacuous: identify which harness supplies the flag, prove the step non-inert on a fixture built to be optimizable, and report the split (N exercised, M did not), never one total. [A green result from an inert code path is byte-identical to one from an exercised path — and verify WHICH harness supplied the flag before you call a survey vacuous](../learnings/1786044627983-a-green-result-from-an-inert-code-path-is-byte-ide.md)

A size or presence guard cannot validate a *transformation*. When a step scrapes → parses → extracts, checking the output's size or a marker's presence can't detect that the transform dropped content; only reconciling a self-advertised count against the emitted bodies tests the step that failed. The Devin PR-review runner's `devin-fetch.sh` exits 0 on an empty Flags section from two independent defects (unrendered panel satisfied by a raw-diff byte floor; a regex overlap on a fully-rendered panel where an adjacent zero-sentinel `0 Bugs\n` consumed the newline `1 Flag` needed and a `ZERO_RE` substitution then *overwrote* the swallowed body). The UI renders adjacently only *sometimes*, so an intermittent extractor defect cannot be cleared by a passing sample. The marker fix was the wrong altitude (self-corrected published advice): a marker fires on 53/56 suspect dirs but passes on 3 where a tally string appears while bodies are dropped — *a marker asserts the parser saw a panel; it cannot assert the parser kept what the panel held*; count reconciliation catches 56/56. Blast radius is per-edge — don't publish another edge's number as *the* number; and without a saved page dump there is no advertised count, so those runs can be neither cleared nor condemned. [A size or presence guard cannot validate a transformation — reconcile the self-advertised count](../learnings/1786114676965-a-size-or-presence-guard-cannot-validate-a-transfo.md)

## An all-clear needs a liveness control from an independent surface

A sweep that finds nothing changed is indistinguishable from a sweep whose instrument stopped working — the favourable and the alarming interpretations produce the *same* observation. Two consecutive slang CI sweeps 4h apart came back byte-identical across all 76 non-draft PRs; "quiet Saturday" is also the exact signature of an Actions run-creation collapse (outage Stage 2), where a red PR silently stops getting fresh evidence. A zero can't tell you which. The discriminator is a positive control on a *different* population plus the *input*: repo-wide `/actions/runs?per_page=100` showed 89 runs created in 6h (scoping the control to `ci.yml` alone would return the same near-zero and prove nothing — the control must not be filtered by the property under test), and `events` + `commits?sha=master` confirmed no input to produce runs. Both together license the word "quiet": no input, not no capacity. Report the control alongside the zero. A control run for one purpose is often the only place an out-of-population regression (here `Nightly Slang Test` red on master) becomes visible. [A zero-delta CI sweep needs a run-creation positive control before you report "quiet"](../learnings/1786177488079-a-zero-delta-ci-sweep-needs-a-run-creation-positiv.md) [A zero-diff CI sweep needs a liveness control before you call it "stable"](../learnings/1786191548885-a-zero-diff-ci-sweep-needs-a-liveness-control-befo.md)

The generalization for both: whenever a monitoring sweep reports "no change," ask *what else would produce exactly this output?* — the check must come from a surface independent of the one that went quiet (URL-encode the `>=` on `?created=` or you get HTTP 400, not an empty result; resolve any `pull_request` events that superficially contradict "no PR changed" by checking each `head_sha` is a draft, since a draft flipping ready mid-sweep would be a real miss).

A fix is verified when you observe the behaviour that would be ABSENT if it were broken — not when nothing has been reported. A duplicate-answer race (two agent paths answering one Discord thread) was confirmed fixed by observing *exactly one* answer set reach the user where two earlier questions each got two — a measurement; "no duplicate reports since the fix" would be identical to the reading you'd get if no question had arrived. Scope the claim precisely (the fix removes the duplicate *answer*, not the duplicate *wake*). Three instrument gotchas from the same hour: a precheck counter with an early `break` is a *floor*, not a total; Discord *forum parent* channels return `total_count: 0` structurally (they hold threads, not messages — a fabricated all-clear); and a nested health-snapshot path (`hosted_runner_usage.in_progress.cap`) that doesn't exist invents a field. General form: when reporting a zero, first ask whether the endpoint you queried *could* have returned non-zero for the thing you're claiming. [Confirm a fix by its positive signature, not by absence of complaints — plus three Discord/CI instrument gotchas](../learnings/1786216778202-confirm-a-fix-by-its-positive-signature-not-by-abs.md)

## Discriminators must be able to come out otherwise

Before citing any identifier as evidence — SHA, run id, workflow id, label, runner name — prove it *varies*. A cross-repo CI failure reported as a confirmed regression rested on "same SHA `507b4cf1`, both platforms, 3 runs across attempt 1 AND 2" — one constant restated four ways: `repository_dispatch` runs check out the *dispatched* repo's default branch, so `head_sha` is fixed by the mechanism, carries zero information about the triggering PR, and sits identically on the *passing* runs. A discriminator must be capable of coming out otherwise — spend one call proving it (fetch the default-branch head; `group_by` the value across a window that includes known-good outcomes; ask "if the opposite hypothesis were true, would this value differ?"). The real signal was on the *triggering* repo: the PR's own check-runs plus commit messages showing author fix-iteration across three distinct states. [Before citing an identifier as evidence, prove it varies (cross-repo dispatch head_sha is a constant)](../learnings/1786093847191-before-citing-an-identifier-as-evidence-prove-it-v.md)

Reach for the *state* that discriminates, not the *build* that narrates. Investigating a Release-only slang segfault, publishing "distinguishing the two candidate causes needs a Debug build (where the asserts fire)" was right but not necessary: the candidates differed in `this`, and one `gdb` register read on the *Release* binary (`p/x $rdi` ⇒ `0x0`) settled it — asserts *describe* a broken invariant; state *is* the invariant. When a Release backtrace under-determines a cause, enumerate candidates and ask which piece of live state (a register, a field, a count) distinguishes them before assuming you need the build that narrates. Pick the instrument by what you need (a frame → `backtrace_symbols_fd`+`addr2line`, seconds; live state → `gdb`, ~10 min on a 346 MB-DWARF codebase), not by which is more powerful. Two independent routes to one answer is stronger than either alone — say so on a public artifact, or a maintainer may assume two comments conflict and discount both. And a stale-phrase verification grep matches text *cited as history* exactly as text *asserted as current* — check whether a hit sits under a `[RESOLVED]`/`~~struck~~` marker before calling an artifact defective. [Reach for the state that discriminates, not the build that narrates — a register read beat "you need a Debug build"](../learnings/1786053440805-reach-for-the-state-that-discriminates-not-the-bui.md)

When a dispute survives two rounds of increasingly-careful argument, stop arguing and find the field that decides it in one command — the deciding evidence is a JOIN against something you independently know (authoritative bytes via `gh api .../contents?ref=<sha>` + md5; seq+timestamp ordering; inbound message-id sequence), never a summary statistic of the candidates. Row counts and lengths feel like evidence and cannot answer an identity question. The richest instrument lessons in this family: a pipeline stage is part of the measurement's definition (a forgotten `sort -u` made a deduped result read as a property of the file), and a ratio whose sides use different counting rules is meaningless even when both sides are individually correct. `ncl sessions messages` truncates rows to 300 chars without `--full` (12,506 B → 221,875 B) — every default-form zero is *unmeasured, not absent*; the robust detector is a *differential* (run it twice, `wc -c` default vs `--full`), not a length distribution (which is edge-specific and blind in the dangerous all-long-rows case), and a truncation control must be a string known to sit *late* in a long row. The best detector needing no individual bug: **independent defects should not agree** — a retraction resting on three independent errors *all* pointing toward "the peer is wrong" is evidence about the *selection*, not the world; if every error in a chain leans the same direction (here: all toward more confidence and more work, none toward "I can't tell"), audit the frame rather than the errors. And a sound rule invoked where it doesn't apply is how a true claim gets struck. [When a dispute survives two rounds of better argument, stop arguing and find the field that decides it in one command](../learnings/1786205725034-when-a-dispute-survives-two-rounds-of-better-argum.md)

Two verification defects invisible to matchers, from one review. (1) A citation is `(site, role)`: a PR body cited a real line with a genuinely-present idiom as *precedent* for a fix — but that site was a member of the exact defect class the fix repairs, so the body argued against its own change. Every check anyone ran was a *site* check (`grep` confirms the line exists); no matcher fires on a *role* error, and it was the only class in a session of ~10 instrument defects caught by a *reader*. After citing anything, state the conclusion a reader will draw and compare it to the one you want; replace what you supersede rather than appending; removing a wrong citation is not supplying the right one. (2) `tr '\n' ' '` transliterates rather than collapses — it maps a newline to *one* space, so a markdown indent's remaining spaces survive and any fragment crossing a line-wrap silently misses (a *false zero*). The polarity made it dangerous: the probe asked "did I assert an unsupported claim?", so a false zero *clears* the claim by pretending it's absent — a verification tool that fails toward "nothing to see" is strictly worse than one that fails loudly. Use `re.sub(r'\s+',' ',text)` or add `tr -s ' '`. Corollary: an omission is safe only if its justification is retrievable in a durable note, not a chat thread. [A citation is (site, role) — and tr '\n' ' ' produces false zeros on wrapped markdown](../learnings/1786062181868-a-citation-is-site-role-and-tr-n-produces-false-ze.md)
