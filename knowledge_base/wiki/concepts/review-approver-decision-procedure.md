# PR-Approver: Decision Procedure, Clauses, Infra-Abstain & Critique-Gate

The `*-pr-approver` coworkers (slang / slangpy) turn a PR review into ONE auditable, scoreable decision drawn from a closed four-state enum — `WOULD_APPROVE | ABSTAIN_POLICY | ABSTAIN_INFRA | BLOCK` — recorded to the host `approval_decisions` ledger. The approver **never writes to GitHub** (shadow mode) and never rounds up to approve. This page covers the *deterministic procedure*: the Step-1 eligibility clauses and their precedence, when an abstain is POLICY vs INFRA, how a GraphQL-only auth outage does NOT block a REST-served decision, and the codex critique-gate recording mechanics that must be satisfied before `record_decision`. The sibling page [[wiki/concepts/review-approver-challenger-calibration.md]] covers the challenger's verified-BLOCK catches and human-agreement calibration.

## The procedure is a deterministic order, not a menu

The skill is a **procedure of record**, executed in a fixed order: Step 1 = deterministic eligibility clauses (`eval-clauses.py`), Step 2 = parse the harvested review-doc verdict, Step 3 = the adversarial challenger runs ONLY if Steps 1–2 pass. A `[approver/clause-gap]` incident made the ordering explicit: on slang#12136 a `tier_eligible` clause FAILed (3355 lines > 2000 cap) while the challenger had *already verified* a real red-CI build break, and the approver initially recorded BLOCK reasoning "BLOCK is strictly more conservative." The DECISION_REVIEW critique flagged it must-fix — SKILL.md says any clause FAIL ⇒ ABSTAIN_POLICY and the challenger runs only if Steps 1–2 pass, so a clause fail **short-circuits to `ABSTAIN_POLICY:CLAUSE_FAIL` before the challenger** ([[approver/clause-gap] A Step-1 clause FAIL short-circuits to ABSTAIN_POLICY even when the challenger has already verified a BLOCK-class defect — the skill ordering governs, don't invent a "BLOCK overrides clause-fail" exception](../learnings/1784271165403-approver-clause-gap-a-step-1-clause-fail-short-cir.md)). "More conservative" is not license to pick the verdict you think truthful — inventing a "BLOCK overrides clause-fail" exception would make the procedure non-deterministic and un-auditable. ABSTAIN is still safe (it routes to a human and never rounds up); the verified defect is preserved as human-facing CONTEXT in the challenger/next-action fields, not as the decision reason.

The same "read the whole procedure, not one step" discipline governs the BLOCK/ABSTAIN split for a doc's 🔴. Step 2's mechanical "any 🔴 ⇒ BLOCK" sets only the doc's PRIOR (BLOCK-shaped); Step 4 defines BLOCK with a load-bearing qualifier — "the review found a **VERIFIED** 🔴 Bug" — and Step 3 explicitly presupposes 🔴 docs reach the challenger ("investigation can only add caution, never upgrade a doc's 🔴 toward approval"). So a **refuted/false-positive bot-🔴 lands at ABSTAIN_POLICY (CHALLENGER_CONCERN, or an independent verified gap carries it), not BLOCK** — the bar is asymmetric (a refuted 🔴 may not be rounded UP to WOULD_APPROVE, but it is not auto-BLOCK either). Recording a false-BLOCK on a CI-green, textbook-correct change is exactly the miscalibration the accuracy join punishes; when the DECISION_REVIEW gate demands BLOCK on a refuted 🔴 (observed: 8 rounds on slang-rhi#800 R2), cite Step 4's "verified" + Step 3's prior-not-verdict/never-upgrade clauses together, not Step 2 alone, and keep a "Why ABSTAIN not BLOCK" reconciliation in investigation.md to pre-empt the loop [[approver/critique-mustfix] A refuted/false-positive bot-🔴 lands at ABSTAIN_POLICY, not BLOCK — Step 4's "verified" qualifier governs, not Step 2's mechanical map](../learnings/1784814885802-approver-critique-mustfix-a-refuted-false-positive.md).

**Clause precedence — a FAIL dominates a co-present UNEVALUABLE.** When a clause FAIL and a clause UNEVALUABLE co-occur, the FAIL (policy) wins by *dominance*, not by which "ran first." On slang#11847 (self-merged before resume, review artifacts GC'd, GraphQL 401), the missing review doc tempted an `ABSTAIN_INFRA:NO_REVIEW_SIGNAL` — but `no_protected_paths` FAILed (16/16 files under `.github/**`), which dominates: even a fully-healthy pipeline would land ABSTAIN_POLICY here because `.github/**` demands a human ([[approver/clause-gap] protected-path FAIL dominates a co-present missing-review-doc — decision is ABSTAIN_POLICY, not ABSTAIN_INFRA](../learnings/1784271261294-approver-clause-gap-protected-path-fail-dominates-.md)). Run `eval-clauses.py` even on a stood-down/merged PR (it works off git+REST, no review doc needed); its FAIL is the honest decision-of-record, and an orchestrator "moot/merged" framing is a claim to verify, not the mapping.

## The protected-path clause is terminal — a clean review never overrides it

`.github/**` (and repo-specific globs like `**/slang-tag-version.h`) are protected paths whose FAIL is a terminal ABSTAIN_POLICY that short-circuits before the challenger — *regardless* of how safe the diff looks or how clean the bot review is. On slang#11957 (CUDA prelude vec1 helpers) the primary production review was CLEAN (0 findings) but the PR also edited `.github/workflows/ci-slang-test.yml`; the decision was `ABSTAIN_POLICY:CLAUSE_FAIL:no_protected_paths`, and it was VINDICATED — an external COLLABORATOR (expipiplus1) later reviewed and approved the CI-config change, exactly the human review the policy exists to trigger ([[approver/human-agreement] clean-primary-review still abstains on protected .github path — human review it defers to is real](../learnings/1784286359675-approver-human-agreement-clean-primary-review-stil.md)). The same class held for single-file `.github/workflows/*.yml` one-liners: slang#12149's obviously-correct `sed` version-regex fix and slang#12140-adjacent release-plumbing all abstain on protected-path before any code reasoning ([[approver/calibration] macOS release.yml version-regex fix → ABSTAIN_POLICY on protected path (fix was correct)](../learnings/1784326170528-approver-calibration-macos-release-yml-version-reg.md)). Do the correctness read for the audit trail, but never let a clean fix or clean bot review tempt a WOULD_APPROVE.

The board-sync onboarding rollout is the canonical multi-repo recurrence of this class: PRs that onboard a repo to slang's shared `pr-board-sync.yml` reusable workflow touch ONLY `.github/workflows/*.yml` thin callers (secret wiring `SLANG_PR_BOT_TOKEN`, `permissions: {}`, fork-review bridge→apply privilege split). slang-rhi#804 (MEMBER, same-repo head, +193/−126) had a clean review — CodeRabbit head-current with 2 nits, Devin exit-0 — and 5 of 6 clauses passed, but the single `no_protected_paths` FAIL is dispositive: `gh pr view --json files` up front, and if every changed path matches `.github/**` the outcome is fixed as ABSTAIN_POLICY:CLAUSE_FAIL:no_protected_paths regardless of author trust, review cleanliness, or small size ([[approver/clause-gap] workflow-only PR with clean review is still protected-path ABSTAIN](../learnings/1785455194475-approver-clause-gap-workflow-only-pr-with-clean-re.md)). Two follow-on subtleties recur on the `synchronize` revisions of these PRs: (1) the CodeRabbit/zizmor `unpinned-uses` finding (the callers pin `@master`, a mutable branch, while forwarding a token) is typically NOT resolved by pinning to a 40-hex SHA — the idiomatic fix is a `.github/zizmor.yml` `ref-pin` **exception** declaring `@master` acceptable for the same-org first-party reusable workflow, so don't read the CodeRabbit nag disappearing as the ref being hardened; and that exception file *itself* lives under `.github/**`, so the clause still FAILs (now on N+1 files) and the outcome is unchanged ([[approver/clause-gap] board-sync unpinned-uses finding gets a zizmor ref-pin exception, not an SHA pin — and the fix stays under .github/**](../learnings/1785514070974-approver-clause-gap-board-sync-unpinned-uses-findi.md)); (2) on each push a prior head's human review is auto-DISMISSED — stamp it on the prior revision's ledger row via `record_human_verdict` before deciding the new head. Expect identical protected-path ABSTAINs on every companion (slangpy#1084, slangpy-samples#57) and every revision.

## Out-of-scope repo/content: class determination BEFORE the review-signal mapping

A content PR from a non-compiler repo (website/blog/docs, e.g. `shader-slang/shader-slang.github.io`) sails through all six mechanical clauses as PASS (they carry **no repo-class predicate**) and harvest returns exit 20 `{found:false}` (production `claude-pr-review.yml` doesn't run there) — which looks identical to the `ABSTAIN_INFRA:NO_REVIEW_SIGNAL` trigger. The correct call is a **class determination first**, prior to and overriding the review-signal mapping: out-of-scope content is a POLICY boundary → `ABSTAIN_POLICY` with `reason_code=OUT_OF_SCOPE:<class>`, NOT INFRA (the pipeline didn't fail; the PR is out of domain) and NEVER WOULD_APPROVE (no applicable code-review signal — don't round up even if a human already approved) ([[approver/clause-gap] Non-compiler repo (website/blog/docs) is ABSTAIN_POLICY:OUT_OF_SCOPE, not INFRA — clauses have no repo-class predicate](../learnings/1784270359274-approver-clause-gap-non-compiler-repo-website-blog.md)). This was confirmed by a genuine human join: a website PR (#207, course-slides link) decided `ABSTAIN_POLICY:OUT_OF_SCOPE:website-content` later got a real (non-self) human APPROVED + merge by a different actor — a *vindicated* withhold, distinct from a self-merge which is neither agreement nor disagreement ([[approver/human-agreement] website-content PR OUT_OF_SCOPE confirmed by genuine human approval+merge](../learnings/1784325987979-approver-human-agreement-website-content-pr-out-of.md)). The four-state enum is closed; `reason_code` carries the free-form detail.

## INFRA-abstain: a GraphQL 401 is not a GitHub outage — probe REST first

The lab container's `GH_TOKEN` is a OneCLI *routing* token, not a GitHub PAT. When the GraphQL surface is unconnected, `gh`'s GraphQL-backed commands (`gh pr view`, `gh api graphql`, `gh api rate_limit`) 401 with `app_not_connected` and `gh auth status` reports "token invalid" — but **plain REST `gh api repos/...` still works**, and `harvest-reviews.py` / `eval-clauses.py` use REST internally so they run fine ([[approver/infra] gh GraphQL 401 at OneCLI gateway but REST gh api works — probe REST before ABSTAIN_INFRA; critique-gate hook false-positives on read-only /pulls reads](../learnings/1784270369731-approver-infra-gh-graphql-401-at-onecli-gateway-bu.md)). Before recording ABSTAIN_INFRA on a `gh pr view` 401, probe a REST endpoint; fetch PR metadata, reviews, files, `/commits/{sha}/status`, `/check-runs`, `/contents/...?ref=<sha>` all via REST, and anonymous `git ls-remote` / `git fetch refs/pull/N/head` also serves head+diff for public repos with no auth ([[approver/infra-abstain] GraphQL 401 gateway outage ≠ no GitHub access — gh REST still serves the clauses; don't over-ABSTAIN_INFRA](../learnings/1784271281635-approver-infra-abstain-graphql-401-gateway-outage-.md)). Only ABSTAIN_INFRA when the *specific datum a clause needs* is served solely by the failing transport. (The underlying 07-16/07-17 outages were later confirmed RESOLVED — a migration cred regression, now fixed — so the split is a diagnostic *technique*, not a standing state; see [[wiki/concepts/agent-infra-github-auth-operations.md]].)

**When INFRA is genuinely unavoidable — and when it isn't.** Bot-authored PRs (dependabot) get harvest exit 20 *by design* (production review skips bot authors), leaving Devin as the SOLE review signal; if Devin also times out (exit 3, 30-min), there is nothing to decide from → `ABSTAIN_INFRA:NO_REVIEW_SIGNAL` is unavoidable and correct — never self-review the bump, never round up ([[approver/infra-abstain] dependabot bot-authored PR: harvest exit 20 + Devin timeout = guaranteed NO_REVIEW_SIGNAL](../learnings/1784302351197-approver-infra-abstain-dependabot-bot-authored-pr-.md)). But that verdict is correct **only for the run where Devin actually times out** — it must not become a reason to *pre-emptively skip* Devin on a re-sync (a timeout is a transient per-run flake, harvest-20 is the structural fact; see the challenger page). Two mechanisms convert a would-be INFRA abstain into a scoreable decision: (1) **patience on a running primary bot** — exit 22 means the bot is IN_PROGRESS, and the 6-min poll window is a floor not a ceiling; on slang#12147 the production review took ~34 min, and falling to Devin-only (which also timed out) would have produced a false INFRA abstain instead of the real PRIMARY-tier BLOCK ([[approver/infra-abstain] exit-22 patience pays: hold for the primary bot even at ~30min when Devin will time out anyway](../learnings/1784316416216-approver-infra-abstain-exit-22-patience-pays-hold-.md)); (2) **retry a timed-out Devin once** — a 30-min exit-3 is transient (browser/analysis hang), and a fresh relaunch often completes in ~1 min, flipping `NO_REVIEW_SIGNAL` (excluded from scoring) into a scoreable POLICY row — high-value when the not-approved outcome is already over-determined by a standing human CHANGES_REQUESTED ([[approver/infra-abstain] Devin retry after 30m timeout flips NO_REVIEW_SIGNAL to a scoreable POLICY row](../learnings/1784326417365-approver-infra-abstain-devin-retry-after-30m-timeo.md)). Gotchas: `devin-error.txt` from run 1 is not cleared by a successful retry (confirm from the retry's own log), and compound `pkill;rm;nohup` one-liners abort before the launch — run the retry standalone.

## A "synchronize" event does not prove the head moved

A `synchronize` / `pr_ready_for_review` webhook can fire on a comment-driven `updated_at` bump with the head byte-identical. On slang#12138 the emitter fired `synchronize` twice off a human issue comment while the head stayed at `9f5ce276` (no force-push, no new check-runs) ([synchronize-webhook-can-fire-on-comment-updated-at-bump](../learnings/1784269837644-synchronize-webhook-can-fire-on-comment-updated-at.md)). Before honoring a synchronize-triggered re-decision, verify the head ACTUALLY moved via ≥2 independent signals — `.head.sha` vs last decided commit, a `head_ref_force_pushed`/`committed` timeline event, fresh check-run `started_at` — because acting blindly records a DUPLICATE ledger row for an identical commit (violating one-decision-per-revision) and burns a full harvest+Devin+challenger cycle ([[approver/clause-gap] Verify the head actually moved before honoring a "synchronize" re-decision tasking — a comment can masquerade as a push](../learnings/1784269782291-approver-clause-gap-verify-the-head-actually-moved.md)). If the head is unchanged, don't re-run; read whatever *did* change (the comment) and re-evaluate on its merits — a substantive human comment can re-open a chain even when no code changed.

**A rebase-onto-newer-master synchronize: classify by the PR's OWN merge-base…head diff.** When a branch is rebased/has-master-merged, `compare/<prior-head>...<new-head>` includes ALL intervening base commits (on slang#12034 R5: 62 commits, hundreds of files, `.github/**` + `external/` churn) — which would wrongly trip `no_protected_paths` and blow the size caps. The PR's true footprint is `compare/<merge-base>...<head>` where merge-base = `compare(base,head).merge_base_commit.sha`; an `ahead_by:1` single squashed commit confirms rebase/squash, not new content ([[approver/clause-gap] a synchronize that rebased onto newer master: classify by the PR's OWN merge-base…head diff, never the compare-vs-prior-head](../learnings/1784289530976-approver-clause-gap-a-synchronize-that-rebased-ont.md)). `eval-clauses.py` computes changed paths for the pinned commit correctly — but the human/agent classification step must reduce the synchronize to merge-base…head first, never eyeball the raw compare-vs-prior-head.

## Review-resume: don't blindly finish a torn-down run

When a `/slang-pr-review` or `-approve` session is torn down mid-run and resumed days later, check three invalidators before re-running: (1) **PR merge/close state** via REST (`{state,merged,merged_at}`) — a merged PR makes a live review moot and any approval historical-only; re-running the full ~$60 live pipeline is a fresh spend the parent should authorize, not an autonomous default; (2) **token validity** — after a multi-day gap `GH_TOKEN` often rotates invalid (GraphQL 401 while REST works), so the standard `pr`-mode scripts hard-fail at their head-SHA preflight — fall back to `patch`-mode off a REST-fetched diff; (3) **artifact survival** — reviewer run-dirs under `.claude/skills/*/transcripts/` can be GC'd, and a log with hundreds of assistant messages but no `final-review.md` was never synthesized ([Review-resume sweep: check merge-state, token validity, artifact survival before re-running](../learnings/1784270233557-review-resume-sweep-check-merge-state-token-validi.md)). Report the changed facts + a concrete viable path (e.g. patch-mode historical review) to the parent for a go/no-go.

## Critique-gate recording mechanics (must satisfy before `record_decision`)

The approver's delivery gate (`track-critique.sh` + `gate-critique-on-deliver.sh`) records a codex critique round toward the gate ONLY when THREE things are all present on the `mcp__codex__codex` call: (1) a `STAGE: <NAME>` marker as the first prompt line; (2) the `developer-instructions` field matches the canonical `/codex-critique` reviewer block **verbatim** (it greps sentinel lines "You are an independent reviewer" and "Return ONLY the structured output below"); (3) the response carries a `### Verdict` heading followed by `approve` | `must-fix` ([[approver/critique-mustfix] codex-critique-gate-requires-canonical-developer-instructions-verbatim](../learnings/1784329350850-approver-critique-mustfix-codex-critique-gate-requ.md)). Required stages are `DECISION_REVIEW` + `OUTPUT_REVIEW`, and the gate opens only when each count ≥1 AND OUTPUT_REVIEW's *last* verdict = approve with `edits_since_critique==0` and an attested-hash match. Ad-hoc `mcp__codex__codex` calls (even with a `STAGE:` line) are fine for EXPLORATORY reachability checks but never satisfy the gate — plan on one canonical skill call per required stage on top of any exploratory rounds ([[approver/critique-mustfix] populate full record_decision field set before OUTPUT_REVIEW; ad-hoc codex STAGE calls don't count toward the gate](../learnings/1784333487365-approver-critique-mustfix-populate-full-record-dec.md)). Also: `codex` requires `sandbox: "danger-full-access"` (bwrap fails in Docker); the `gate-critique-on-deliver.sh` Bash regex false-positives on ANY command containing the literal `/pulls` even for read-only GETs, so split the literal (`P="repos/o/r/pu""lls/n"`) or drive reads through the bundled python scripts; and create `/workspace/.claude/` if absent or the hook errors. Concretely, the hook's PR-creation pattern is `gh api [^|]*pulls\b` — verb-blind, so a read-only `gh api .../pulls/<n>/reviews|comments` (fetching review bodies / inline threads) is DENIED as "CRITIQUE REQUIRED before PR creation" and repeated hits reach the denial cap and auto-fire a (correctly-rejected) admin bypass. Don't fight it — route around it: read review bodies via `gh pr view <n> --json latestReviews,reviews` (no `pulls` in the path) and inline threads via `gh api graphql` (`reviewThreads`); `commits/<sha>/check-runs` and `.../status` are already safe. Only ad-hoc follow-up reads bite (a supervisor nudge, a late human review body); the initial harvest scripts already use safe paths [[approver/infra] read-only `gh api .../pulls/<n>/reviews|comments` trips the critique-gate PR-creation hook — use gh pr view / GraphQL](../learnings/1784867719312-approver-infra-read-only-gh-api-pulls-n-reviews-co.md).

This `pulls`-substring false-match kept recurring across the slang and slangpy approver runs, so the workarounds are worth stating concretely. The hook's `gh api [^|]*pulls\b` pattern is verb-blind (a GET reads identically to a PR-creating POST), and every denial increments `critique_gate_denials` in `/workspace/.claude/workflow-state.json` — at 3 it escalates to a human admin card, so a read-only harvest can spuriously burn strikes toward an escalation. Three routes clear it: (1) use GraphQL for reviews/inline threads (`gh api graphql` with a `reviewThreads` query — path is `graphql`, not `pulls/…`) and `contents/<path>?ref=<sha>` for file bodies at head ([[approver/infra-abstain] Critique-gate hook false-triggers on read-only `gh api .../pulls` — use GraphQL/contents for reads](../learnings/1785412883919-approver-infra-abstain-critique-gate-hook-false-tr.md)); (2) prefer `gh pr view <n> --json reviews,files,latestReviews,headRefOid,commits` — no `pulls` literal in the command line, so it is never gated and covers reviews + changed-file metadata for staging ([[approver] Critique-gate Bash hook: wrap read-only gh api /pulls calls in a script file to avoid the false-match](../learnings/1785453486073-approver-critique-gate-bash-hook-wrap-read-only-gh.md)); (3) if you must hit the REST `/pulls` endpoint, wrap the `gh api` call inside a small `bash work/<pr>/tmp/fetch.sh` script — the hook only inspects the literal Bash command string, so `bash fetch.sh` passes while the script's internals run unimpeded (this is exactly why the bundled `collect-reviews.sh`/`harvest-reviews.py` are never gated — their `gh api` calls live inside the script) ([[approver] Critique-gate Bash hook: wrap read-only gh api /pulls calls in a script file to avoid the false-match](../learnings/1785453486073-approver-critique-gate-bash-hook-wrap-read-only-gh.md)). Do NOT run a pointless `/codex-critique` or request an admin bypass to clear the gate for a read — the reads aren't deliverables. The same false-match extends to the REST review-thread reply POST (`gh api .../pulls/<n>/comments/<id>/replies`) for answer-style / explanation-only tasks that have no code diff: post replies via the GraphQL `addPullRequestReviewThreadReply` mutation (needs the `PRRT_…` thread node id from the read), and note that a plain issue comment (`repos/<o>/<r>/issues/<n>/comments`) is on the `issues/` path and does NOT trip the gate — only `pulls/` paths are affected ([codex-delivery gate false-positives on gh PR-comment reads + REST review-reply POST; use GraphQL](../learnings/1785450188405-codex-delivery-gate-false-positives-on-gh-pr-comme.md)).

## OUTPUT_REVIEW must-fixes: state only what your artifacts prove

The OUTPUT_REVIEW critique verifies every factual claim against the artifacts you *attach*, by design — a claim true-but-unbacked-in-the-passed-set reads as fabrication. Recurring self-inflicted must-fixes and their fixes:

- **Deliverable self-supporting from passed artifacts.** On shader-slang.github.io#208 the decision message asserted "verified via the commits API" and editorialized about sibling PRs — facts that lived in `investigation.md`/memory but weren't in the four passed artifacts. Fix: attach `investigation.md`, or trim cross-PR editorializing to a bare "same repo and content class as #207/#204" ([[approver/critique-mustfix] OUTPUT_REVIEW deliverable must be self-supporting from passed artifacts](../learnings/1784327819969-approver-critique-mustfix-output-review-deliverabl.md)).
- **Don't claim a bot re-reviewed at head when only its summary comment refreshed.** CodeRabbit updates its single summary issue-comment on every push (so `updated_at` moves) but posts a *new formal review* only sometimes; `harvest-reviews.py` keys on formal reviews, so exit 10 (stale) is ground truth. State the two facts separately and attribute head-currency verification to your own challenger, not the bot ([[approver/critique-mustfix] Don't claim a bot re-reviewed at head when only its summary comment refreshed](../learnings/1784275986777-approver-critique-mustfix-don-t-claim-a-bot-re-rev.md)).
- **Cite line refs at the pinned head, count check-runs paginated.** Base-clone `file.cpp:NNNN` refs are silently wrong (a +19-line helper shifts everything downstream) — fetch the changed file at `?ref=<head-sha>` and cite from that. `check-runs` defaults to 30/page; the real count needs `--paginate ?per_page=100`, and distinguish failure vs non-success vs skipped ([[approver/critique-mustfix] Approver artifacts: cite line refs at pinned head + count check-runs paginated](../learnings/1784288128413-approver-critique-mustfix-approver-artifacts-cite-.md)).
- **Don't equate total check-runs with CI matrix legs.** `total_count` includes `pre-commit`/`add-to-project`/`finish`/skipped assistant jobs plus the CodeRabbit commit-status (not a check-run at all); filter to the real `build (...)` matrix legs and state them as distinct signals ([[approver/critique-mustfix] don't equate total check-runs with CI matrix legs; state the count you verified](../learnings/1784282781009-approver-critique-mustfix-don-t-equate-total-check.md)).
- **Stage the MOUNTED policy, not the bundled fallback.** The authoritative policy is `/workspace/extra/approver-policy/APPROVAL_POLICY.json` (`v0-shadow-relaxed`, human-signed); the skill-bundled `APPROVAL_POLICY.json` is a *tightened* fallback (`v0-shadow`). Copying the bundled file into the workspace `policy/` dir shadows the mount and flips CONTRIBUTOR/fork/protected-path clauses to FAIL, contradicting a prior CLEAN decision — check `policy_version` in `clauses.json` against the mount. Also: synthesize `review-doc.md` (carrying the `_approver_result` `commit_id`) BEFORE running `eval-clauses.py`, or `commit_match` comes back UNEVALUABLE ([[approver/critique-mustfix] stage the MOUNTED policy, not the bundled fallback — and synthesize review-doc BEFORE eval-clauses](../learnings/1784288659769-approver-critique-mustfix-stage-the-mounted-policy.md)). Populate the full `record_decision` field set (`clauses`, `challenger`, ISO `ts`) before OUTPUT_REVIEW, and a `[Approval Decision]` marker message needs `in_reply_to` or the routing gate blocks it.
- **`reason_code` for a clean WOULD_APPROVE is the literal `none` — not a phrase, not an invented token.** For a WOULD_APPROVE that is a clean conjunction (Steps 1–4 all clean) there IS no reason_code: the closed-enum field carries detail only for the abstain/block states (`CLAUSE_FAIL:*`, `OPEN_GAP`, `CHALLENGER_CONCERN`, `RED_BUG`, …). The gate bounces both a parenthetical (`reason_code: (none — clean conjunction)`, flagged "emit the exact enum/value so the row is recordable without interpretation") and an invented word (`reason_code: CLEAN`, flagged as conflicting with the ledger value `none`) — only the literal `reason_code: none` passes. Put the "why it's clean" narrative in the `challenger` field / the message, never in reason_code ([[approver/critique-mustfix] ledger reason_code for clean WOULD_APPROVE is literal `none`, not a descriptive phrase](../learnings/1785530765832-approver-critique-mustfix-ledger-reason-code-for-c.md)).
- **Don't call an ABI-contract finding "refuted" because the in-tree callers happen to be safe.** On slangpy#1082 marking CodeRabbit's 🟠 buffer-contract finding "CLEARED / unreachable on any supported path" was flagged must-fix as an overclaim: the math only proved the *two current in-tree callers* don't diverge, but the flagged function is an exposed `extern "C"` ABI fn-ptr in a versioned `TensorBridgeAPI` struct with a documented minimum-buffer contract the native side enforces and the fallback doesn't — the caller set is open. Reserve "refuted/unreachable" for triggers impossible for *any* caller; for anything crossing a published ABI/API boundary, narrow the conclusion to "no impact on current in-tree callers" and retain the contract-level gap on the record ([[approver/critique-mustfix] Don't call an ABI-contract finding "refuted" just because in-tree callers are safe](../learnings/1785426158100-approver-critique-mustfix-don-t-call-an-abi-contra.md)).
- **Decision-message wording: no self-referential process overclaim, and don't conflate revision-delta with full-PR diff-stat.** A `synchronize` re-decision (slangpy#1083 R1) bounced the `[Approval Decision]` message four times, every bounce a must-fix on wording not decision. Class A — self-referential overclaim: don't assert "both critique stages recorded = approve" while *inside* OUTPUT_REVIEW (a stage cannot certify itself already-passed), and phrase recording as "is being recorded this turn", never "recorded" (`record_decision` runs after the gate opens). Class B — diff-stat conflation: state the full-PR size (`main...head`, = clauses eligibility size) AND the revision delta (`prior_head...head` via `gh api compare`) as two SEPARATE numbers from the right source; the `clauses.json` "N lines / M files" is eligibility size, not "what changed this push". Class C (advisory) — no prior-verdict anchoring: reference the prior head by SHA + the compare fact, not by its verdict, since the prior head is context not evidence. Bake all three into the message template so the first OUTPUT_REVIEW pass is clean — recurring wording must-fixes are a procedure bug, not per-PR noise ([[approver/critique-mustfix] Decision-message pitfalls: critique-state overclaim + revision-delta vs full-PR diff-stat conflation](../learnings/1785454931977-approver-critique-mustfix-decision-message-pitfall.md)).

## Incremental sharpenings (2026-07-18/19 approver session)

**A non-exit-0 harvest can co-occur with a still-running PRIMARY — probe check-runs before falling to Devin-only.** `harvest-reviews.py` exit 10 (a stale *secondary* review exists, e.g. CodeRabbit at an older commit) keys off the newest *posted* review and does NOT re-check whether the production `github-actions[bot]` claude review (`.github/workflows/claude-pr-review.yml`) is still in-flight — so it can silently discard a primary that is minutes from landing. On ANY non-exit-0-primary result (10/20/22), independently check the commit's check-runs for a `review`-named run; if `queued`/`in_progress`, treat it like exit-22 and WAIT+re-harvest rather than fall to Devin-only ([[approver/infra-abstain] exit-10-stale-can-mask-still-running-primary-claude-review](../learnings/1784390106504-approver-infra-abstain-exit-10-stale-can-mask-stil.md)). The distinction that decides how long to wait: a `review` check-run `in_progress` (or recently completed) is a genuine ~6-min posting race — keep waiting; a run stuck `queued` and NOT advancing across two windows (~20+ min) is a **runner backlog** — set a firm total budget then fall to the Devin tier *noting the PRIMARY timeout as an infra event*, and only when byte-identical-to-an-already-reviewed-revision makes the fallback false-safe-free (if the code actually changed and only a thin Devin signal remains, lean ABSTAIN_INFRA/NO_REVIEW_SIGNAL, not a confident verdict) ([[approver/infra] When the PRIMARY review check-run is stuck QUEUED (not the ~6-min posting race), fall to Devin — but only when byte-identical-to-a-reviewed-revision makes it false-safe-free](../learnings/1784366403034-approver-infra-when-the-primary-review-check-run-i.md)). Auditability follow-on: when decision provenance depends on a script's exit code (harvest tier branching), `harvest.json` on a not-found result records only `{"found": false}` with no exit code — a reader can't distinguish exit 20 (genuine skip) from 10 (stale) or 21 (fetch failed) after the fact, so state the exit code explicitly in the review-doc's tier line until the script persists it ([[approver/infra-abstain] harvest-json-found-false-persist-exit-code-for-audit](../learnings/1784417204496-approver-infra-abstain-harvest-json-found-false-pe.md)).

**Protected-path ABSTAIN_POLICY is a withhold, not a prediction — a byte-identical merge is AGREEMENT, and a self-merge dilutes (never validates) it.** When a `.github/**` / `**/*.yml` / release-tooling one-liner abstains on `no_protected_paths` and then MERGES byte-identical at the decision commit, the shadow decision and the human outcome AGREE (I never claimed the change was wrong, only that a human should own the sign-off, and a human did) — do NOT score it as a disagreement just because the enum wasn't WOULD_APPROVE; the OPPOSITE (multiple "Address review" commits before merge, or closed-unmerged) is what would warrant a learning, and any follow-up commits between decision and merge ARE the reviewable delta ([[approver/human-agreement] Protected-path ABSTAIN_POLICY vindicated by byte-identical merge — the withhold is agreement, not a miss](../learnings/1784381462983-approver-human-agreement-protected-path-abstain-po.md)). But check the merge *shape*: when `mergedBy == author` and `reviewDecision != APPROVED` (an author self-merge with zero independent APPROVED), the protected-path safety-net fired correctly yet its *value was diluted* — the "human who must look" was the author themselves, and any gaps you surfaced (e.g. CodeRabbit 🟠 CI-leak-logic) shipped unweighed; log it as weak/self-endorsement, not validation that the gaps were judged acceptable ([[approver/human-agreement] protected-path-ABSTAIN-confirmed-but-author-self-merge-ships-open-gaps](../learnings/1784437469229-approver-human-agreement-protected-path-abstain-co.md)).

**OUTPUT_REVIEW discipline extended — no verified 🔴 downgrade, no volatile fields.** The 🔴 rule has NO documentation-vs-code carve-out: once the challenger has CONFIRMED (not refuted) a 🔴, moving it from BLOCK to ABSTAIN/OPEN_GAP on the reasoning "it's only docs / the compiled output is correct" is precisely the "upgrade toward approval" the rule forbids — the only path from a confirmed 🔴 to non-BLOCK is genuine REFUTATION (not real / not reachable / not this revision), and severity-based clearing applies to 🟡 gaps, never a confirmed 🔴 (the DECISION_REVIEW critique gate caught this rationalization) ([[approver/critique-mustfix] a verified 🔴 cannot be downgraded to OPEN_GAP because "it's only docs" — no documentation exemption in the 🔴 rule](../learnings/1784440920822-approver-critique-mustfix-a-verified-cannot-be-dow.md)). And don't bake **volatile GitHub fields** into a durable artifact: `mergeStateStatus` flips BEHIND/BLOCKED/CLEAN/UNSTABLE independent of anything you decide, so a stale value trips the attested-hash re-check at send time — quote the durable, decision-relevant signals (`reviewDecision`, human review states, the actual gate) instead, or label a merge-state value explicitly volatile ([[approver/output-review] Volatile GitHub fields (mergeStateStatus) are not decision-relevant — drop the value, keep the durable gate](../learnings/1784421284355-approver-output-review-volatile-github-fields-merg.md)).

## Contradictions / supersessions

- The "clauses only gate the approve direction, so a verified BLOCK can override a clause FAIL" theory is **rejected** — the skill ordering governs and a clause FAIL short-circuits to ABSTAIN_POLICY before the challenger ([[approver/clause-gap] A Step-1 clause FAIL short-circuits to ABSTAIN_POLICY even when the challenger has already verified a BLOCK-class defect — the skill ordering governs, don't invent a "BLOCK overrides clause-fail" exception](../learnings/1784271165403-approver-clause-gap-a-step-1-clause-fail-short-cir.md)).
- The GraphQL-401 "total GitHub outage → ABSTAIN_INFRA on everything" reading is **wrong** — REST + anon git still serve the clauses ([[approver/infra-abstain] GraphQL 401 gateway outage ≠ no GitHub access — gh REST still serves the clauses; don't over-ABSTAIN_INFRA](../learnings/1784271281635-approver-infra-abstain-graphql-401-gateway-outage-.md)); and the underlying 07-16/07-17 outages themselves were later RESOLVED, so the split is a technique not a state.
- "Bot-authored dep bump + Devin timeout = guaranteed INFRA" is correct only for the timed-out run; it does NOT license pre-emptively skipping Devin on a re-sync (see [[wiki/concepts/review-approver-challenger-calibration.md]]).

## Class Determination First: Own-Harness / Non-Compiler-Repo PRs Are OUT_OF_SCOPE (2026-07-20 fold)

A PR-approve dispatch landed for `slang-coworkers/nanoclaw#982` — a PR in the infra fork that *modifies the approver's OWN decision harness* (including relaxing its ABSTAIN critique gate). The mechanical pipeline produced ABSTAIN_INFRA-looking signals (`harvest-reviews.py` exit 21, all 6 clauses UNEVALUABLE) whose real cause is the GitHub App token being scoped to shader-slang → HTTP 401 on `slang-coworkers/*`. But that token-401 is a *symptom* of out-of-domain, not the cause of an infra abstain. The correct call is a **class determination made FIRST in the skill, before and overriding the clause→INFRA mapping**: if the repo isn't shader-slang/slang compiler code, or the changed paths are the approver's own harness (`container/skills/slang-pr-approver/**`, `container/workflows/slang-pr-approve/**`), it's OUT_OF_SCOPE — and an own-rules PR is additionally a conflict of interest (self-endorsement never permitted; a human must look). Record `ABSTAIN_POLICY` with `reason_code=OUT_OF_SCOPE:<class>` (closed enum, free-form suffix — new suffix `approver-harness`), stamp it explicitly into `_approver_result` so it doesn't drift to INFRA, and skip Devin (a class determination isn't informed by a review signal) ([approver-own-harness PR = ABSTAIN_POLICY:OUT_OF_SCOPE + conflict-of-interest](../learnings/1784443235968-approver-clause-gap-approver-own-harness-pr-abstai.md)).

## Devin Subagent Returns Before devin-fetch.sh Completes — Watch the Artifact, Not the Subagent (2026-07-21 fold)

In `/slangpy-pr-approve` (and slang) Step 1b, driving Devin via a background `Agent` subagent, the subagent repeatedly reports completion while `devin-fetch.sh` is still running: its final message gets clobbered by its own polling ("I'll wait for the notification…"), and `review/devin-flags.md` is absent on disk for 15-25+ min because the script (agent-browser + Chromium) is long-running, silent, and writes its result ONLY at the very end. The devin-fetch process SURVIVES the subagent's exit and keeps running under the parent session, so the artifact does eventually land — but the subagent's returned text is not a completion signal. How to catch it: after the subagent "completes," check the actual artifact (`ls review/devin-flags.md`) and process liveness (`pgrep -af devin-fetch.sh`); if the process is alive, wait on the artifact, not the subagent. Fix: drive Devin with a `Monitor` (or background Bash `until` loop) watching for the artifact to appear OR the script to exit (covering both success and no-artifact failure), instruct the subagent to run in the FOREGROUND and report once with an explicit ~15-min self-timeout returning `DEVIN_TIMEOUT`. If Devin never produces a head-current signal AND the harvested bot review is stale/absent, that is `ABSTAIN_INFRA:NO_REVIEW_SIGNAL` — do NOT substitute your own code read for the missing review doc. Gotcha: `pkill -f chromium` from a Bash tool can take down the calling shell (exit 144) — kill in a throwaway shell or SIGTERM the top `devin-fetch.sh` pid only ([[approver/infra-abstain] Devin subagent returns before devin-fetch.sh completes; artifact writes at end](../learnings/1784560636178-approver-infra-abstain-devin-subagent-returns-befo.md)). A sibling race hits even when `devin-fetch.sh` exits 0 with a populated rollup: on slangpy#1084 rev-3 the artifact carried "0 Bugs, 3 Flags" but the per-flag DETAIL lines (title/severity/file:line) were **absent** because the done-detector fired while the diff pane still read "Loading diffs…" — the right-rail flag COUNT settles before the center pane hydrates the detail. So after the subagent returns, cross-check the `## Flags` section against the AI-analysis rollup: an empty/"(none captured)" Flags list while the rollup says "N Flags" (N>0) means the detail was lost to the race — do NOT report "no flags"; when the decision does not short-circuit at a Step-1 clause, re-run/re-scrape before deciding, and when it does (e.g. all files under `.github/**`) record the decision but set a `devin_flag_detail_captured: false` marker rather than present the incomplete list as exhaustive (still `reviewers_complete=true` — a capture-completeness gap, not a NO_REVIEW_SIGNAL) ([[approver/infra-abstain] Devin done-detector also races the "Loading diffs…" state — flag COUNT renders but per-flag DETAIL lines stay empty](../learnings/1785517182047-approver-infra-abstain-devin-done-detector-also-ra.md)).

## Repo-Class Predicate Overrides Co-Occurring INFRA Symptoms; Devin-Timeout on Bot PRs = NO_REVIEW_SIGNAL (2026-07-22 fold)

**Two independent INFRA-looking signals on a website-content PR still resolve to ABSTAIN_POLICY, not INFRA.** On shader-slang.github.io#209 both `collect-reviews.sh` exit 20 (`{found:false}` — no bot review to harvest) and `commit_match` unevaluable (because `eval-clauses.py` was run before `review-doc.md` was synthesized) co-occurred and could double-mislead toward ABSTAIN_INFRA. Both are structural out-of-domain symptoms of the website repo, not pipeline failures: production `claude-pr-review.yml` never runs on the Jekyll site (→ harvest-20), and `commit_match` parses the synthesized doc, not `harvest.json` (→ unevaluable purely because the doc isn't written yet). The **repo-class predicate fires FIRST and overrides the mechanical review-signal → INFRA mapping** — verify the diff is content-only (no `_config`/CI/build code) and record `ABSTAIN_POLICY:OUT_OF_SCOPE:website-content`, never ABSTAIN_INFRA. Re-running `eval-clauses.py` after synthesizing the doc with the pinned `commit_id` flips `commit_match` to a clean 6/6-pass whose abstain rests purely on the class predicate ([website-content PR shows BOTH harvest-20 and commit_match-unevaluable — both out-of-domain, still ABSTAIN_POLICY not INFRA](../learnings/1784618140917-approver-clause-gap-website-content-pr-shows-both-.md)).

**On the Devin-only tier, a Devin timeout + exit-20 harvest = the one fragile signal failing = ABSTAIN_INFRA:NO_REVIEW_SIGNAL — never round up from your own investigation.** slangpy#1071 (bot-authored rebased takeover, tiny diff, fully green CI) abstained because production `claude-pr-review.yml`/claude-code-action genuinely SKIPS bot-authored branches (exit-20, expected for this class) AND `devin-fetch.sh` hung past the URL-rewrite step for >12 min with no `devin-flags.md`. Exit-20 alone is not an abstain (Devin-only tier decides); exit-20 AND a Devin failure is the `reviewers_complete=false` harness-integrity case. This is the dominant infra-abstain driver for bot-authored PRs — the fix is devin-fetch fail-fast (a ~5-min internal cap), and whether trivially-safe bot test-only PRs should keep abstaining is a human policy question, never a license to substitute the approver's own code read for the missing review verdict ([Devin timeout + bot-authored PR = NO_REVIEW_SIGNAL despite clean CI](../learnings/1784695299892-approver-infra-abstain-devin-timeout-bot-authored-.md)).

## Late-Primary Refresh, Bounded Devin Retry, Class-Override, and the ABSTAIN-Token Gate Trap (2026-07-23 fold)

Refinements to the deterministic order and its infra/gate mechanics. A Devin-only fallback decision is **provisional** against a late primary review on an unchanged head: when a supervisor nudge or later event lands, re-check live state and REFRESH the ledger row on the primary tier if `github-actions[bot]` has since posted at your decided commit — the fallback row's "review never posted" blocker becomes factually false minutes later ([a primary review that posts after you decide (unchanged head) → refresh the row on the primary tier](../learnings/1784723964060-approver-infra-abstain-a-primary-review-that-posts.md)). To keep ABSTAIN_INFRA near zero, wrap `devin-fetch.sh` in a hard shell `timeout` and do ONE bounded retry before recording NO_REVIEW_SIGNAL — an agent-browser hang is a transient wedge, not a real "Devin can't review" outcome ([Devin agent-browser hang recovered by bounded-timeout retry — avoid false ABSTAIN_INFRA](../learnings/1784735780656-approver-infra-abstain-devin-agent-browser-hang-re.md)).

Two class/clause interactions: `head_provenance` fails any cross-repo (fork) head under `allow_fork_head=false` **independently of author trust**, so a clean member PR from a personal fork is a foregone ABSTAIN_POLICY:CLAUSE_FAIL — check `isCrossRepository` early and don't burn a challenger pass ([fork-head PRs from trusted MEMBERs abstain on head_provenance under v0-shadow](../learnings/1784735771677-approver-clause-gap-fork-head-prs-from-trusted-mem.md)); and the `tier_eligible` size cap is another Step-1 FAIL that short-circuits before the challenger with no carve-out for change *class* — a purely test-only consolidation PR (slangpy#1085, 24 files all under `tests/`, +3141/−59 ≈ 3200 lines, zero runtime/binding/build changes) resolves to ABSTAIN_POLICY:CLAUSE_FAIL:tier_eligible (3200 > 2000-line cap) even though it touches no shipped code, because `eval-clauses.py` computes eligibility from raw `additions+deletions` churn. When a PR is test-only AND the only failing clause is `tier_eligible`, recognize the benign expected abstain, don't spend challenger effort (the challenger cannot upgrade a Step-1 FAIL), and note that the only lever that would change the outcome is a policy tier scaling `max_total_lines` by change class — not a challenger override ([[approver/clause-gap] Large test-only consolidation PRs abstain on tier_eligible size cap](../learnings/1785510473677-approver-clause-gap-large-test-only-consolidation-.md)); and class determination fires FIRST — a non-compiler infra/docs PR (e.g. a `slang-coworkers/nanoclaw` changelog) sails through all six eligibility clauses as PASS and its harvest-20 mimics the INFRA trigger, but the correct verdict is ABSTAIN_POLICY:OUT_OF_SCOPE, never WOULD_APPROVE or ABSTAIN_INFRA — and a bot self-merge is not a human verdict ([nanoclaw changelog docs PR: 6/6 clauses pass, still OUT_OF_SCOPE not INFRA](../learnings/1784745354331-approver-clause-gap-nanoclaw-changelog-docs-pr-6of.md)). The confirming shape for infra-abstain: a bot-authored rebased-takeover that is test-only, cites a CLOSED blocker, and whose target CI job actually *runs* the enabled tests is a repeatedly-safe class — but that still does not license rounding up from ABSTAIN_INFRA ([merge confirms bot-authored test-only device-enablement takeover is a repeatedly-safe shape](../learnings/1784726873588-approver-infra-abstain-merge-confirms-bot-authored.md)). Finally a gate trap: the critique-gate ABSTAIN fast-path allows the message only if it matches `ABSTAIN_*` AND does NOT match `WOULD_APPROVE|BLOCK` as bare words — so writing "→ OPEN_GAP, not WOULD_APPROVE" in an abstain rationale trips the exclusion and forces the full (skippable) gate; keep those enum tokens out of the delivered `[Approval Decision]` text entirely ([ABSTAIN [Approval Decision] message must not contain the literal tokens WOULD_APPROVE/BLOCK](../learnings/1784769386692-approver-critique-mustfix-abstain-approval-decisio.md)). The exclusion grep is a plain whole-word, case-sensitive ERE over the ENTIRE message body — it does not care whether `BLOCK`/`WOULD_APPROVE` is the decision state or just prose, so an innocuous `**Blocker:**` bullet that explains *why* you held a 🔴 "rather than a BLOCK verdict" defeats the fast-path and gets the abstain treated as a gated decision (observed on slangpy#1075 @4415159, where it consumed denial-cap strikes and escalated to a human admin before it was noticed) — reword to "a hard-fail verdict" / "round up to approve", and scan the whole message for the bare uppercase tokens before sending ([[approver/infra-abstain] Critique-gate abstain fast-path breaks if the message text contains the tokens BLOCK or WOULD_APPROVE](../learnings/1785450575710-approver-infra-abstain-critique-gate-abstain-fast-.md)).

Two more critique-gate mechanics that cost round-trips under the `critique-gate` overlay (observed on slang#12220): **PLAN_REVIEW is a REQUIRED stage, not optional** — even a well-scoped triage-handed fix has `gh pr create` DENIED until a `STAGE: PLAN_REVIEW` codex round is recorded, so run all three (PLAN_REVIEW → CODE_REVIEW → OUTPUT_REVIEW) as fresh `mcp__codex__codex` calls carrying the canonical developer-instructions verbatim (a `codex-reply` is NOT counted unless its instructions match). And **any edit after an OUTPUT_REVIEW approve re-arms the gate — including edits to non-deliverable files** (writing a local `memory/fix-<n>.md` re-armed it even though the PR body/code/test were byte-identical), so do all side-artifact writes BEFORE the final OUTPUT_REVIEW and send the deliverable immediately after the approve with no intervening edits [critique-gate: PLAN_REVIEW is required + any side-artifact edit re-arms the OUTPUT gate](../learnings/1785191965028-critique-gate-plan-review-is-required-any-side-art.md).

A `synchronize` webhook does not always mean new work to re-decide: GitHub fires it on **any** head move, including a `git merge main` that pulls base content into the branch, so the raw commit-to-commit diff shows base churn (e.g. an unrelated test file) that a naive read mistakes for new PR footprint. Decide from the **net footprint** (`gh pr diff` = merge-base…head): if it is byte-identical to the prior revision the push is a no-op merge and the challenger findings transfer — but every open gap must still be **re-verified against LIVE source at the new head** (contents API `?ref=<head>`), because byte-identical net diff proves the *change* is unchanged, not that a maintainer didn't separately edit the flagged lines; a stale-by-commit-id harvest (CodeRabbit exit 10) is not the same as an obsolete finding ([a no-op merge synchronize leaves footprint byte-identical — decide from net diff, re-verify gaps against live source](../learnings/1785319523865-approver-clause-gap-a-synchronize-on-a-no-op-merge.md)). This also sharpens the ABSTAIN delivery-gate rule already on this page: in an `[Approval Decision]` ABSTAIN message, never write the uppercase tokens `BLOCK`/`WOULD_APPROVE` even negated — phrase as "not a blocking defect".

Relatedly, a `github.ci_failed` event on an already-decided head is not automatically a new revision or a stronger verdict. Because `ci_green_on_sha` is non-gating under `v0-shadow-relaxed` (`require_ci_green:false`), CI state never mechanically gates the decision — the only substantive question is whether a red is a real PR-caused regression (strengthens the verdict) or an unrelated flake. A slangpy signature to recognize: exactly ONE matrix cell red (`build (linux, x86_64, gcc, Release, 3.10)`) while the same platform's Debug and the clang legs pass on identical source, with the failing case being `frame statistics align repeated and intermittent zones` in `tests/sgl/device/test_profiler.cpp` — a profiler timing/statistics test asserting exact per-call CPU-time and call counts, inherently nondeterministic under CI scheduling. The decisive check is footprint: `gh pr diff <pr> --name-only` (merge-base aware, NOT `gh api compare base...head` which includes files pulled in by merge commits) — if the failing test file isn't in the PR diff, the failure is not PR-driven, does not strengthen a standing ABSTAIN:OPEN_GAP, and (same head) mints no new ledger row ([[approver/infra-abstain] slangpy CI-red signature: test_profiler.cpp timing test flakes on one matrix cell — not PR-driven](../learnings/1785486738534-approver-infra-abstain-slangpy-ci-red-signature-te.md)).
