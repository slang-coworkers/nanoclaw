# PR-Approver: Decision Procedure, Clauses, Infra-Abstain & Critique-Gate

The `*-pr-approver` coworkers (slang / slangpy) turn a PR review into ONE auditable, scoreable decision drawn from a closed four-state enum — `WOULD_APPROVE | ABSTAIN_POLICY | ABSTAIN_INFRA | BLOCK` — recorded to the host `approval_decisions` ledger. The approver **never writes to GitHub** (shadow mode) and never rounds up to approve. This page covers the *deterministic procedure*: the Step-1 eligibility clauses and their precedence, when an abstain is POLICY vs INFRA, how a GraphQL-only auth outage does NOT block a REST-served decision, and the codex critique-gate recording mechanics that must be satisfied before `record_decision`. It also covers what the procedure *cannot* measure — clauses that read proxies, a review-signal harvest that queries one of three endpoints, a Devin tier that exits 0 on nothing — and the evidence discipline a recorded row demands, since almost every approver defect on record is a correct measurement over an unverified scope rather than a wrong verdict. The sibling page [review-approver-challenger-calibration](../concepts/review-approver-challenger-calibration.md) covers the challenger's verified-BLOCK catches and human-agreement calibration.

## The procedure is a deterministic order, not a menu

The skill is a **procedure of record**, executed in a fixed order: Step 1 = deterministic eligibility clauses (`eval-clauses.py`), Step 2 = parse the harvested review-doc verdict, Step 3 = the adversarial challenger runs ONLY if Steps 1–2 pass. A `[approver/clause-gap]` incident made the ordering explicit: on slang#12136 a `tier_eligible` clause FAILed (3355 lines > 2000 cap) while the challenger had *already verified* a real red-CI build break, and the approver initially recorded BLOCK reasoning "BLOCK is strictly more conservative." The DECISION_REVIEW critique flagged it must-fix — SKILL.md says any clause FAIL ⇒ ABSTAIN_POLICY and the challenger runs only if Steps 1–2 pass, so a clause fail **short-circuits to `ABSTAIN_POLICY:CLAUSE_FAIL` before the challenger** ([[approver/clause-gap] A Step-1 clause FAIL short-circuits to ABSTAIN_POLICY even when the challenger has already verified a BLOCK-class defect — the skill ordering governs, don't invent a "BLOCK overrides clause-fail" exception](../learnings/1784271165403-approver-clause-gap-a-step-1-clause-fail-short-cir.md)). "More conservative" is not license to pick the verdict you think truthful — inventing a "BLOCK overrides clause-fail" exception would make the procedure non-deterministic and un-auditable. ABSTAIN is still safe (it routes to a human and never rounds up); the verified defect is preserved as human-facing CONTEXT in the challenger/next-action fields, not as the decision reason.

The same "read the whole procedure, not one step" discipline governs the BLOCK/ABSTAIN split for a doc's 🔴. Step 2's mechanical "any 🔴 ⇒ BLOCK" sets only the doc's PRIOR (BLOCK-shaped); Step 4 defines BLOCK with a load-bearing qualifier — "the review found a **VERIFIED** 🔴 Bug" — and Step 3 explicitly presupposes 🔴 docs reach the challenger ("investigation can only add caution, never upgrade a doc's 🔴 toward approval"). So a **refuted/false-positive bot-🔴 lands at ABSTAIN_POLICY (CHALLENGER_CONCERN, or an independent verified gap carries it), not BLOCK** — the bar is asymmetric (a refuted 🔴 may not be rounded UP to WOULD_APPROVE, but it is not auto-BLOCK either). Recording a false-BLOCK on a CI-green, textbook-correct change is exactly the miscalibration the accuracy join punishes; when the DECISION_REVIEW gate demands BLOCK on a refuted 🔴 (observed: 8 rounds on slang-rhi#800 R2), cite Step 4's "verified" + Step 3's prior-not-verdict/never-upgrade clauses together, not Step 2 alone, and keep a "Why ABSTAIN not BLOCK" reconciliation in investigation.md to pre-empt the loop [[approver/critique-mustfix] A refuted/false-positive bot-🔴 lands at ABSTAIN_POLICY, not BLOCK — Step 4's "verified" qualifier governs, not Step 2's mechanical map](../learnings/1784814885802-approver-critique-mustfix-a-refuted-false-positive.md).

**Clause precedence — a FAIL dominates a co-present UNEVALUABLE.** When a clause FAIL and a clause UNEVALUABLE co-occur, the FAIL (policy) wins by *dominance*, not by which "ran first." On slang#11847 (self-merged before resume, review artifacts GC'd, GraphQL 401), the missing review doc tempted an `ABSTAIN_INFRA:NO_REVIEW_SIGNAL` — but `no_protected_paths` FAILed (16/16 files under `.github/**`), which dominates: even a fully-healthy pipeline would land ABSTAIN_POLICY here because `.github/**` demands a human ([[approver/clause-gap] protected-path FAIL dominates a co-present missing-review-doc — decision is ABSTAIN_POLICY, not ABSTAIN_INFRA](../learnings/1784271261294-approver-clause-gap-protected-path-fail-dominates-.md)). Run `eval-clauses.py` even on a stood-down/merged PR (it works off git+REST, no review doc needed); its FAIL is the honest decision-of-record, and an orchestrator "moot/merged" framing is a claim to verify, not the mapping.

## The protected-path clause is terminal — a clean review never overrides it

`.github/**` (and repo-specific globs like `**/slang-tag-version.h`) are protected paths whose FAIL is a terminal ABSTAIN_POLICY that short-circuits before the challenger — *regardless* of how safe the diff looks or how clean the bot review is. On slang#11957 (CUDA prelude vec1 helpers) the primary production review was CLEAN (0 findings) but the PR also edited `.github/workflows/ci-slang-test.yml`; the decision was `ABSTAIN_POLICY:CLAUSE_FAIL:no_protected_paths`, and it was VINDICATED — an external COLLABORATOR (expipiplus1) later reviewed and approved the CI-config change, exactly the human review the policy exists to trigger ([[approver/human-agreement] clean-primary-review still abstains on protected .github path — human review it defers to is real](../learnings/1784286359675-approver-human-agreement-clean-primary-review-stil.md)). The same class held for single-file `.github/workflows/*.yml` one-liners: slang#12149's obviously-correct `sed` version-regex fix and slang#12140-adjacent release-plumbing all abstain on protected-path before any code reasoning ([[approver/calibration] macOS release.yml version-regex fix → ABSTAIN_POLICY on protected path (fix was correct)](../learnings/1784326170528-approver-calibration-macos-release-yml-version-reg.md)). Do the correctness read for the audit trail, but never let a clean fix or clean bot review tempt a WOULD_APPROVE.

The board-sync onboarding rollout is the canonical multi-repo recurrence of this class: PRs that onboard a repo to slang's shared `pr-board-sync.yml` reusable workflow touch ONLY `.github/workflows/*.yml` thin callers (secret wiring `SLANG_PR_BOT_TOKEN`, `permissions: {}`, fork-review bridge→apply privilege split). slang-rhi#804 (MEMBER, same-repo head, +193/−126) had a clean review — CodeRabbit head-current with 2 nits, Devin exit-0 — and 5 of 6 clauses passed, but the single `no_protected_paths` FAIL is dispositive: `gh pr view --json files` up front, and if every changed path matches `.github/**` the outcome is fixed as ABSTAIN_POLICY:CLAUSE_FAIL:no_protected_paths regardless of author trust, review cleanliness, or small size ([[approver/clause-gap] workflow-only PR with clean review is still protected-path ABSTAIN](../learnings/1785455194475-approver-clause-gap-workflow-only-pr-with-clean-re.md)). Two follow-on subtleties recur on the `synchronize` revisions of these PRs: (1) the CodeRabbit/zizmor `unpinned-uses` finding (the callers pin `@master`, a mutable branch, while forwarding a token) is typically NOT resolved by pinning to a 40-hex SHA — the idiomatic fix is a `.github/zizmor.yml` `ref-pin` **exception** declaring `@master` acceptable for the same-org first-party reusable workflow, so don't read the CodeRabbit nag disappearing as the ref being hardened; and that exception file *itself* lives under `.github/**`, so the clause still FAILs (now on N+1 files) and the outcome is unchanged ([[approver/clause-gap] board-sync unpinned-uses finding gets a zizmor ref-pin exception, not an SHA pin — and the fix stays under .github/**](../learnings/1785514070974-approver-clause-gap-board-sync-unpinned-uses-findi.md)); (2) on each push a prior head's human review is auto-DISMISSED — stamp it on the prior revision's ledger row via `record_human_verdict` before deciding the new head. Expect identical protected-path ABSTAINs on every companion (slangpy#1084, slangpy-samples#57) and every revision.

## Out-of-scope repo/content: class determination BEFORE the review-signal mapping

A content PR from a non-compiler repo (website/blog/docs, e.g. `shader-slang/shader-slang.github.io`) sails through all six mechanical clauses as PASS (they carry **no repo-class predicate**) and harvest returns exit 20 `{found:false}` (production `claude-pr-review.yml` doesn't run there) — which looks identical to the `ABSTAIN_INFRA:NO_REVIEW_SIGNAL` trigger. The correct call is a **class determination first**, prior to and overriding the review-signal mapping: out-of-scope content is a POLICY boundary → `ABSTAIN_POLICY` with `reason_code=OUT_OF_SCOPE:<class>`, NOT INFRA (the pipeline didn't fail; the PR is out of domain) and NEVER WOULD_APPROVE (no applicable code-review signal — don't round up even if a human already approved) ([[approver/clause-gap] Non-compiler repo (website/blog/docs) is ABSTAIN_POLICY:OUT_OF_SCOPE, not INFRA — clauses have no repo-class predicate](../learnings/1784270359274-approver-clause-gap-non-compiler-repo-website-blog.md)). This was confirmed by a genuine human join: a website PR (#207, course-slides link) decided `ABSTAIN_POLICY:OUT_OF_SCOPE:website-content` later got a real (non-self) human APPROVED + merge by a different actor — a *vindicated* withhold, distinct from a self-merge which is neither agreement nor disagreement ([[approver/human-agreement] website-content PR OUT_OF_SCOPE confirmed by genuine human approval+merge](../learnings/1784325987979-approver-human-agreement-website-content-pr-out-of.md)). The four-state enum is closed; `reason_code` carries the free-form detail.

## INFRA-abstain: a GraphQL 401 is not a GitHub outage — probe REST first

The lab container's `GH_TOKEN` is a OneCLI *routing* token, not a GitHub PAT. When the GraphQL surface is unconnected, `gh`'s GraphQL-backed commands (`gh pr view`, `gh api graphql`, `gh api rate_limit`) 401 with `app_not_connected` and `gh auth status` reports "token invalid" — but **plain REST `gh api repos/...` still works**, and `harvest-reviews.py` / `eval-clauses.py` use REST internally so they run fine ([[approver/infra] gh GraphQL 401 at OneCLI gateway but REST gh api works — probe REST before ABSTAIN_INFRA; critique-gate hook false-positives on read-only /pulls reads](../learnings/1784270369731-approver-infra-gh-graphql-401-at-onecli-gateway-bu.md)). Before recording ABSTAIN_INFRA on a `gh pr view` 401, probe a REST endpoint; fetch PR metadata, reviews, files, `/commits/{sha}/status`, `/check-runs`, `/contents/...?ref=<sha>` all via REST, and anonymous `git ls-remote` / `git fetch refs/pull/N/head` also serves head+diff for public repos with no auth ([[approver/infra-abstain] GraphQL 401 gateway outage ≠ no GitHub access — gh REST still serves the clauses; don't over-ABSTAIN_INFRA](../learnings/1784271281635-approver-infra-abstain-graphql-401-gateway-outage-.md)). Only ABSTAIN_INFRA when the *specific datum a clause needs* is served solely by the failing transport. (The underlying 07-16/07-17 outages were later confirmed RESOLVED — a migration cred regression, now fixed — so the split is a diagnostic *technique*, not a standing state; see [agent-infra-github-auth-operations](../concepts/agent-infra-github-auth-operations.md).)

**When INFRA is genuinely unavoidable — and when it isn't.** Bot-authored PRs (dependabot) get harvest exit 20 *by design* (production review skips bot authors), leaving Devin as the SOLE review signal; if Devin also times out (exit 3, 30-min), there is nothing to decide from → `ABSTAIN_INFRA:NO_REVIEW_SIGNAL` is unavoidable and correct — never self-review the bump, never round up ([[approver/infra-abstain] dependabot bot-authored PR: harvest exit 20 + Devin timeout = guaranteed NO_REVIEW_SIGNAL](../learnings/1784302351197-approver-infra-abstain-dependabot-bot-authored-pr-.md)). But that verdict is correct **only for the run where Devin actually times out** — it must not become a reason to *pre-emptively skip* Devin on a re-sync (a timeout is a transient per-run flake, harvest-20 is the structural fact; see the challenger page). Two mechanisms convert a would-be INFRA abstain into a scoreable decision: (1) **patience on a running primary bot** — exit 22 means the bot is IN_PROGRESS, and the 6-min poll window is a floor not a ceiling; on slang#12147 the production review took ~34 min, and falling to Devin-only (which also timed out) would have produced a false INFRA abstain instead of the real PRIMARY-tier BLOCK ([[approver/infra-abstain] exit-22 patience pays: hold for the primary bot even at ~30min when Devin will time out anyway](../learnings/1784316416216-approver-infra-abstain-exit-22-patience-pays-hold-.md)); (2) **retry a timed-out Devin once** — a 30-min exit-3 is transient (browser/analysis hang), and a fresh relaunch often completes in ~1 min, flipping `NO_REVIEW_SIGNAL` (excluded from scoring) into a scoreable POLICY row — high-value when the not-approved outcome is already over-determined by a standing human CHANGES_REQUESTED ([[approver/infra-abstain] Devin retry after 30m timeout flips NO_REVIEW_SIGNAL to a scoreable POLICY row](../learnings/1784326417365-approver-infra-abstain-devin-retry-after-30m-timeo.md)). Gotchas: `devin-error.txt` from run 1 is not cleared by a successful retry (confirm from the retry's own log), and compound `pkill;rm;nohup` one-liners abort before the launch — run the retry standalone.

## A webhook is a notification, never evidence of state

The payload selects which PR to look at; it is not the evidence. This holds for every event class, and the failure is symmetric — a webhook can overstate a change (`synchronize` on an unmoved head) or overstate a terminal outcome (`pr_closed` on a PR that is live `open`).

**`pr_closed` with `merged:false` can be a seconds-long close/reopen bounce.** On slang#12080 a `pr_closed` inbound arrived against two recorded `WOULD_APPROVE / CLEAN` rows — textbook false-safe shape (closed-unmerged + standing approve ⇒ `human_verdict=CHANGES_REQUESTED`, the highest-severity calibration finding). The author had closed and reopened **4 seconds apart** (the classic CI re-trigger), and at the payload level a bounce is byte-indistinguishable from a terminal close: same event name, same `merged:false`, no `reopened_at`. Scoring off the payload would have fabricated a `CHANGES_REQUESTED` against clean rows and permanently poisoned calibration (atoms are append-only). So on **every** `pr_closed` / `pr_merged` / `pr_review` join: re-read live `state` + `closed_at` first (`state=open` / `closed_at=null` ⇒ **no join, stop**; `closed_at==null` on a `pr_closed` inbound is the cheap tell it was reopened), then read the `closed`/`reopened` pair on `issues/{n}/timeline` — which is often *not* page 1 (on #12080 it sat on page 2 of 3 behind 100 force-push/review events), so paginate to the end or the bounce is invisible. A close/reopen pair seconds apart **by the author** is a CI re-trigger; no human judged the code. Never round a `merged=false` webhook up to a false-safe — a fabricated false-safe is worse than a missed one, because it teaches the challenger to distrust a procedure that was correct ([[approver/clause-gap] a pr_closed webhook can be a seconds-long close/reopen bounce — verify live state, not the payload, before scoring any join](../learnings/1785741585307-approver-clause-gap-a-pr-closed-webhook-can-be-a-s.md)).

A `synchronize` / `pr_ready_for_review` webhook can fire on a comment-driven `updated_at` bump with the head byte-identical. On slang#12138 the emitter fired `synchronize` twice off a human issue comment while the head stayed at `9f5ce276` (no force-push, no new check-runs) ([synchronize-webhook-can-fire-on-comment-updated-at-bump](../learnings/1784269837644-synchronize-webhook-can-fire-on-comment-updated-at.md)). Before honoring a synchronize-triggered re-decision, verify the head ACTUALLY moved via ≥2 independent signals — `.head.sha` vs last decided commit, a `head_ref_force_pushed`/`committed` timeline event, fresh check-run `started_at` — because acting blindly records a DUPLICATE ledger row for an identical commit (violating one-decision-per-revision) and burns a full harvest+Devin+challenger cycle ([[approver/clause-gap] Verify the head actually moved before honoring a "synchronize" re-decision tasking — a comment can masquerade as a push](../learnings/1784269782291-approver-clause-gap-verify-the-head-actually-moved.md)). If the head is unchanged, don't re-run; read whatever *did* change (the comment) and re-evaluate on its merits — a substantive human comment can re-open a chain even when no code changed.

**A rebase-onto-newer-master synchronize: classify by the PR's OWN merge-base…head diff.** When a branch is rebased/has-master-merged, `compare/<prior-head>...<new-head>` includes ALL intervening base commits (on slang#12034 R5: 62 commits, hundreds of files, `.github/**` + `external/` churn) — which would wrongly trip `no_protected_paths` and blow the size caps. The PR's true footprint is `compare/<merge-base>...<head>` where merge-base = `compare(base,head).merge_base_commit.sha`; an `ahead_by:1` single squashed commit confirms rebase/squash, not new content ([[approver/clause-gap] a synchronize that rebased onto newer master: classify by the PR's OWN merge-base…head diff, never the compare-vs-prior-head](../learnings/1784289530976-approver-clause-gap-a-synchronize-that-rebased-ont.md)). `eval-clauses.py` computes changed paths for the pinned commit correctly — but the human/agent classification step must reduce the synchronize to merge-base…head first, never eyeball the raw compare-vs-prior-head. A stale local `main` fabricates the same illusion from the other direction: on slang-rhi#807 a `main...HEAD` diff showed **8 phantom `.github/**` files** — enough to trip the protected-path clause — purely because the local branch was 3 weeks behind, so always diff against the PR's *real* base SHA ([[approver/clause-gap] verify a workaround PR's premise against the PINNED dependency version, never master](../learnings/1785764986434-approver-clause-gap-verify-a-workaround-pr-s-premi.md)).

**A standing "let it ride if codegen-inert" decision expires when the author pivots design — check the subject-of-record still EXISTS, not just that it is unchanged.** slang#12080 carried a standing rule (re-run the gated procedure only when codegen changes; on an inert synchronize let the recorded row ride) that worked for ~6 heads of nit-polish. ~18 heads later the naive inert check said "everything changed" (rebase drift touched all 11 files) — alarming and uninformative — while the real finding was worse: **the approved construct no longer existed.** Both rows had approved one specific lowering (`builder.emitGetAddress(builder.getPtrType(arg->getDataType()), arg)`); the author had pivoted to a third design (retype the parameter via `getBorrowInParamType` + a new `AddressSpace::CudaKernelParam` enumerator, an explicit `IRLoad`, a new `lowerImmutableBufferLoadForCUDA` pass) — a lineage whose *first* design had been approved 4× and then reported to MISCOMPILE. A diff-shaped question assumes both sides still describe the same construct; a pivot breaks that premise, so make the inert check **existence-first**: grep the new head for the specific call/predicate the row approved (absent ⇒ the row is stale, retire it and re-gate), grep for new load-bearing vocabulary (a new `AddressSpace`, `SLANG_PASS`, IR op, `setFullType` call — new vocabulary means new design, not polish), neutralize rebase contamination by diffing file content at both SHAs via `raw.githubusercontent.com` rather than `gh compare`, and cap the standing rule by head count. Write the row's subject-of-record as a **greppable anchor** so the existence check is mechanical, re-derive `mode` (reviews accumulated during the ride ⇒ `live` became `live_late`), and rewrite the memory-index line too — a stale "standing / re-gate only on genuine emit change" index entry is itself load-bearing and invites the next session to ride a row whose subject is gone ([[approver/clause-gap] a standing "let it ride if codegen-inert" decision expires on a design pivot — assert the subject-of-record still exists](../learnings/1785741613665-approver-clause-gap-a-standing-let-it-ride-if-code.md)).

## Review-resume: don't blindly finish a torn-down run

When a `/slang-pr-review` or `-approve` session is torn down mid-run and resumed days later, check three invalidators before re-running: (1) **PR merge/close state** via REST (`{state,merged,merged_at}`) — a merged PR makes a live review moot and any approval historical-only; re-running the full ~$60 live pipeline is a fresh spend the parent should authorize, not an autonomous default; (2) **token validity** — after a multi-day gap `GH_TOKEN` often rotates invalid (GraphQL 401 while REST works), so the standard `pr`-mode scripts hard-fail at their head-SHA preflight — fall back to `patch`-mode off a REST-fetched diff; (3) **artifact survival** — reviewer run-dirs under `.claude/skills/*/transcripts/` can be GC'd, and a log with hundreds of assistant messages but no `final-review.md` was never synthesized ([Review-resume sweep: check merge-state, token validity, artifact survival before re-running](../learnings/1784270233557-review-resume-sweep-check-merge-state-token-validi.md)). Report the changed facts + a concrete viable path (e.g. patch-mode historical review) to the parent for a go/no-go.

## The review signal is endpoint-split — three surfaces, and the harvest reads one

The single largest measured defect class in the approver pipeline is not a wrong verdict; it is a **correct tally over the wrong surface**. GitHub scatters PR feedback across three disjoint endpoints and the harvest queries one:

1. **`pulls/N/reviews`** — review *wrappers*, and the only place a `state` (`APPROVED` / `CHANGES_REQUESTED` / `COMMENTED`) lives.
2. **`pulls/N/comments`** — inline findings. This is where the *substance* usually lives.
3. **`issues/N/comments`** — PR conversation text, where **maintainer directives** arrive with no review object and no state at all.

**Endpoint split #1 — an empty-body `COMMENTED` review is a wrapper, not silence.** GitHub models a review as a wrapper containing inline comments; submit an inline batch with no top-level prose and `/reviews` shows `body: ""` while `/comments` carries multi-paragraph text at the same timestamp. On slang#12080 two opposite wrong conclusions were each one step away — "empty body ⇒ nothing was said ⇒ retract the nudge" (the author had written four substantial replies) and "a maintainer spoke ⇒ re-decide" (the text was the author answering *bot* findings). The discriminator is **"is there text on any surface"**, then classify by **audience**: `in_reply_to_id` pointing at a bot comment is the cheap tell that a burst is informational. Two rules, one per direction: *empty body ≠ silence* (an empty `COMMENTED` wrapper is the expected shape for an inline-only batch — look one level down, never conclude "nothing happened"), and *text ≠ actionable* (author-answers-bot must not re-arm the procedure; reviewer-raises-objection must) ([[approver/clause-gap] an empty-body COMMENTED review is a wrapper, not silence — the substance lives on the inline-comments endpoint](../learnings/1785761437816-approver-clause-gap-an-empty-body-commented-review.md)). ⚠️ That learning's supporting claim *"the inline comments spanned 3 pages, the relevant replies were on page 3, page 1 was entirely July bot traffic"* is **FALSE and retracted** — the author's replies are spread across the early pages too (deterministic count: **250** inline comments over 3 pages of 100/100/**50**, 37 by the author). It was derived from a summarizing fetch, so its "paginate to page 3" advice was right by accident; the real defect was never pagination depth but using a lossy reader for an enumeration question. Correct guidance: author and reviewer comments can land on **any** page; never characterize a page's contents from a summarized read, enumerate with stdlib `urllib` and count in code until a short page ([[approver/clause-gap] CORRECTION — the empty-body-wrapper learning's page-1 claim is false; grep your own already-fetched material before reporting a negative](../learnings/1785761810820-approver-clause-gap-correction-to-empty-body-comme.md)).

**Endpoint split #2 — CodeRabbit findings live on `pulls/N/comments`, and the harvest tallies `reviews[].body`.** This is the dangerous one because it under-reads on a **successful exit-0 harvest**. A CodeRabbit review body is frequently status boilerplate only (`**Actionable comments posted: 11**` plus a collapsed run-config), containing **zero** severity markers, while the 11 findings — 2 of them 🟠 Major / Functional Correctness on slang-rhi#803 R1 — sit on the unqueried endpoint. Whether you see findings in the body is **CodeRabbit formatting luck, not harvester correctness**, so "body had no markers ⇒ no findings" is never a valid inference. Two companion traps from the same investigation: GitHub **rewrites** an inline comment's `commit_id` as the head advances (8 of 11 findings originally posted at R1 later reported R3), so bucket provenance by **`original_commit_id`**; and a **green CodeRabbit commit status does NOT imply a harvestable review object** at that commit. One hypothesis worth not re-chasing: this is *not* a bot-detection bug — the harvest scripts filter with an exact-match allowlist (`login in ("github-actions[bot]","coderabbitai[bot]")`) over REST, with no `endswith` and no GraphQL in that path (the suffix asymmetry is still a real trap for hand-written checks: REST `user.login` carries `[bot]` and `user.type=="Bot"`, GraphQL `author.login` is bare with `__typename=="Bot"`, and `gh pr view --json reviews` returns **`login` only** — no in-band way to detect a bot at all). The procedural failure that actually caused the row: exit-22 correctly reported `pending`, the review landed 3 minutes later, and the artifact was synthesized 7 minutes after that **without one final cheap re-probe** — *a timeout is a statement about a past instant, not about the present*, so re-probe at the LAST moment before committing the artifact ([[approver/infra-abstain] CodeRabbit findings live on pulls/N/comments, not reviews[].body — a successful exit-0 harvest can still score 0 findings](../learnings/1785778078080-approver-infra-abstain-coderabbit-findings-live-on.md)).

**Measured blast radius, and the right way to report it.** Audited across stored rows, the signature (`Actionable comments posted: N>0` with zero body markers) fires on **11 of 18** CodeRabbit harvests that found a review — 17 findings never in the machine-parsed input, every harvest exit 0, no error to notice. Partition the hits by whether the field was *load-bearing*: where a clause FAILED the decision short-circuited at Step 1 and the under-read is cosmetic for the verdict; where all clauses passed the review signal **was** the decision input (6 such rows, one of them a WOULD_APPROVE on slang-rhi#797 whose Devin had timed out — the row least able to absorb an under-read is exactly where one happened). The generalizable move: when you find a parsing bug, **sweep your own stored artifacts for the signature and partition by load-bearingness** ([[approver/infra-abstain] endpoint-split audit: 11 of 18 CodeRabbit harvests silently under-read — detection recipe + load-bearing partition](../learnings/1785779251344-approver-infra-abstain-endpoint-split-audit-11-of-.md)). At slangpy scale the rate is worse: of **12** CodeRabbit reviews claiming `N>0`, **11 carried zero body markers** (~92%), and yet only 2 of 40 recorded rows were wrong — because **the agent reading `pulls/N/comments` by hand during synthesis was the safety net, not the tooling**. Across the 7 rows whose revision had inline findings, 100% of those findings are cited by `file:line` in the review doc. The 2 rows that failed are exactly the two where the harvest concluded **no review existed at all** (exit 22-timeout, exit 20), so nothing prompted a manual read and the doc affirmatively asserted "no CodeRabbit signal" — *the under-read only becomes a wrong row when it coincides with a false absence*. A high manual-compensation rate is not reassurance; it is a latent defect waiting for the day the prompt to compensate is absent ([[approver/clause-gap] the CodeRabbit body-only tally under-reads ~92% of the time — manual reading, not tooling, was the safety net](../learnings/1785779185938-approver-clause-gap-the-coderabbit-body-only-tally.md)).

⚠️ **But an artifact-level defect is not a decision-level harm — confirm against the decision input of record before crying false-safe.** The same audit initially escalated slang-rhi#797 as a probable false-safe from `harvest.json` alone. Opening the actual decision input (`review/review-doc.md`) showed **both** CodeRabbit findings quoted verbatim with per-finding severity and an explicit call (*"🟠 Major … test-robustness nit, test-only … Not blocking"*), and an embedded result of `bugs:0, gaps:1, questions:1, verdict: APPROVE_WITH_NITS` — not 0/0/0; 9 of 9 auditable rows carry severity markers in the doc. Keep two questions strictly separate: **is the artifact wrong?** (yes — worth fixing) and **was the decision wrong?** (answerable *only* by opening `review-doc.md` and the recorded verdict fields). "The recorded signal field is untrustworthy on N rows" is true and useful; "N findings were missed" is a stronger claim needing per-row confirmation, and publishing it unverified is an over-claim in the *alarming* direction — the mirror of rounding up to approve, and just as much a calibration failure. Finding a bug creates momentum toward finding its victims; that momentum is precisely when to slow down ([[approver/critique-mustfix] an artifact-level defect is not a decision-level harm — open the decision input of record before crying false-safe](../learnings/1785780014953-approver-critique-mustfix-an-artifact-level-defect.md)).

**Endpoint split #3 — maintainer directives arrive on `issues/N/comments` with no review state, and they outrank everything with one.** On slang-rhi#803 a scan reported "7 reviews, all COMMENTED — no CHANGES_REQUESTED, no standing blocker" indefinitely, while skallweitNV (MEMBER) had posted *"we want to keep slang-rhi free from using git submodules. Can you fetch TinyBVH through FetchContent as we do for the other dependencies?"* — a concrete change request invalidating the PR's approach, carrying no review state because it is not a review object. `pulls/N/reviews` **structurally cannot see** it, so any "is there a standing blocker?" check built on review states has a permanent blind spot for the highest-authority feedback on the PR. Treat the standing-blocker question as a **union over all three endpoints, filtered by `author_association`** (`MEMBER`/`OWNER`/`COLLABORATOR` on a plain issue comment outranks a bot's `COMMENTED` review object — authority is `author_association`, never API shape), paginate all three, and record which endpoint each directive came from so a later scan doesn't "retire" it by re-checking only reviews. Two comments from one maintainer can differ in kind: a bandwidth note is a tripwire, "do X instead of Y" is a directive a later revision must satisfy ([[approver/clause-gap] maintainer directives live on issues/N/comments and carry no review state — union all three endpoints, authority from author_association](../learnings/1785780753487-approver-clause-gap-maintainer-directive-on-issues.md)).

**For a join, `issues/N/timeline` is the one endpoint that orders everything together.** Joining slang#11667 (`pr_merged`) against a row pinned at `ad924934`, `pulls/N/reviews` showed only bot reviews at the pinned commit plus one human `approved` at a later commit — which reads as "no human ever objected to my head, and the merge is APPROVED-equivalent." Both halves were wrong: the decisive signal was a plain issue comment rejecting the approach (a CHANGES_REQUESTED-equivalent invisible to `/reviews`), and the head had been force-pushed between that comment and the approval. `gh api repos/O/R/issues/N/timeline?per_page=100 --paginate` interleaves `committed`, `head_ref_force_pushed`, `reviewed`, `merged`, `closed` **in one timestamp ordering**, which is what proves whether an objection predated or postdated a head move — here establishing the maintainer objected AT the pinned head, making the row scorable as CHANGES_REQUESTED rather than a neutral "head moved, no signal." On a force-pushed fork branch `compare A...B` is misleading (`ahead_by=108` from a rebase); confirm content by **sha256 of the file blobs** via `contents/<path>?ref=<sha>`, never by ahead/behind. Never infer "a human considered X" from "a human approved" — compare timestamps ([[approver/clause-gap] score a join with issues/N/timeline — it interleaves force-pushes with reviews, and maintainer vetoes arrive as plain issue comments](../learnings/1785782777239-approver-clause-gap-score-a-join-with-issues-n-tim.md)).

### The general rule: a predicate written in one endpoint's vocabulary silently excludes the others

The harvester bug and the resume-trigger bug are the same defect: **the data model of the query quietly became the definition of the thing**, and both times the omission was invisible because the query succeeded. A hold/resume trigger recorded as *"a non-bot **review** with an actionable **state** lands"* is a `review`+`state` predicate — and the directive that was the entire reason for holding lives only on `issues/N/comments` with no review object and no state, so the check could never fire on its own stated blocker and would report "nothing actionable" indefinitely. When writing any gate, trigger, or blocker predicate, ask **which surfaces can carry this signal, and does my predicate's vocabulary reach all of them?** — and prefer semantic terms ("actionable feedback from a non-bot") over schema terms ("review with state X"), because schema terms inherit one endpoint's blind spots. The same section carries a companion trap: **a deletion is not a disposition.** An approvals queue reading `[]` with `get` returning "approval not found" for each prior id does not mean "all three were rejected" — rows delete on approve OR reject OR expiry and `get` returns the identical `not found` for all three, so absence identifies the *set*, not the member (same shape as `mergeable_state`, which names *that* something is unmet, never *which*). Before reading absence as evidence, enumerate every path that produces the same absence; if more than one does, mark the disposition **unknowable** rather than inferring it. And naming an unreachable authoritative field is a *complete* answer, not a hedge — "cannot read; field F is authoritative; the tier that can read it should map it" beats deriving an id by timestamp adjacency, because **a wrong identifier is worse than no identifier**: the next reader re-verifies *through* it and lands somewhere else ([[approver/clause-gap] a deletion is not a disposition, and a predicate in one endpoint's vocabulary silently excludes the others](../learnings/1785819644171-approver-clause-gap-a-deletion-is-not-a-dispositio.md)).

⚠️ **Widening that never-fires predicate produced an always-fires one — and the missing discriminator was the ADDRESSEE, not the endpoint.** The fix *"actionable non-bot feedback in ANY of the three endpoints"* is **already satisfied literally** by the directive being waited on, so the resume condition read as *already met*: it would wake a fresh decision immediately, forever, with nothing new to decide. The maintainer comment opens `@<contributor>` — it is a change request **to the PR author**, actionable for the PR and not an inbound to the approval decision. Endpoint told you where to look; state told you the API shape; neither told you **who is being asked to act**. Ordered test for "is this a decision-relevant inbound?": (1) non-bot author, via `author_association` — not a login-suffix heuristic, since `gh pr view --json reviews` strips `[bot]`; (2) addressed to the contributor, or to the reviewer/decision?; (3) does it change a load-bearing input (size total, a gate/ABI premise, CI state, a standing verdict)? All three, or it is not a resume trigger. **After any predicate fix, evaluate it against the KNOWN CURRENT STATE: if it fires now with nothing new, it is wrong** — one lookup, catches the whole class. The always-fires direction is the worse half: a never-fires predicate sits inert, an always-fires one burns a re-decision on every check and trains the reader to ignore the signal ([[approver/clause-gap] widening a never-fires predicate produced an always-fires one — the missing discriminator was the addressee](../learnings/1785821476819-approver-clause-gap-widening-a-never-fires-predica.md)).

## Clauses read proxies — `ci_green_on_sha`, `commit_match`, `tier_eligible`

Three of the six mechanical clauses evaluate a *proxy* for the thing they name, and in each case the failure direction is toward the answer that permits an approval.

**`ci_green_on_sha` reads the legacy combined status, which is blind to GitHub Actions.** `eval-clauses.py:187` derives CI state exclusively from `commits/{sha}/status`; `grep -cF check-runs eval-clauses.py` = **0** in both the slang and slangpy approvers. On slangpy#1090 that combined status returned `state:success` with `n:2` — and those two statuses were **`license/cla` and `CodeRabbit`**, no build at all — while `commits/{sha}/check-runs` carried every real `build (...)` matrix job ([[approver/clause-gap] ci_green_on_sha reads combined status only — blind to Actions check-runs, and defaults to require_ci_green=true](../learnings/1785787076247-approver-clause-gap-ci-green-on-sha-reads-combined.md)). At the moment of first evaluation the same commit had **6 of 12 builds `in_progress`**, including both macOS legs — the only Metal-capable platform and the one the PR targets — so a clause keyed on combined status would have reported green over a build that had not finished and could still fail ([[approver/clause-gap] ci_green_on_sha says success while every build is still in_progress](../learnings/1785786196856-approver-clause-gap-ci-green-on-sha-reads-combined.md)). The perverse part: `require_ci_green` **defaults to `true`** when the key is absent, and the mounted `v0-shadow-relaxed` policy sets it `false` — so the defect is inert in shadow mode and activates for anyone *tightening* the gate or running without a mounted policy. **The stricter setting is strictly less trustworthy than the lax one; do not read "we require CI green" as "we verified CI."** Correct behavior: AND both surfaces, `unevaluable` on any non-terminal run (⇒ `ABSTAIN_INFRA:CLAUSE_UNEVALUABLE:ci_green_on_sha`), `fail` on any adverse conclusion, and — critically — **absence of build signal on both surfaces must be `unevaluable`, not `pass`**, since the current code has no path distinguishing "no builds ran" from "all builds passed."

**`commit_match` reads `reviews[].commit_id`, which GitHub retroactively rewrites to the current head.** On slangpy#1068 the only human review was `ccummingsNV APPROVED submitted_at=2026-07-29T10:05:29Z`, while the decided head `266b2072e621` is a merge commit dated **2026-08-03T19:22:22Z** — five days later. `reviews[].commit_id` nonetheless reported `266b2072e621`, so `commit_match` passed *"review commit_id == pinned"* on a stale approval: a false-safe in the approve direction, reporting freshness it never verified. The obvious spot-check cannot save you — other PRs retained *historical* `commit_id`s, so inequality is not a reliable staleness signal either; the rewrite is silent and inconsistent. **Compare timestamps, not SHAs**: a review is stale iff its `submitted_at` precedes the author date of the commit it claims to review (independent control: slangpy#1084's `jkwak-work APPROVED` at `21:13:48Z` carries a commit dated `22:22:34Z`). Keep the two questions apart — "is the approval record stale?" is not "did the reviewed code change?" (on #1068 the net diff vs `main` was 1 file / +8 / −0, so the reviewed tree was byte-identical) — or the finding reads as more alarming than the evidence supports. A timestamp-inverted review should route to the Devin-only tier like harvest exit 10; and a human approval, fresh or stale, is a **JOIN signal**, never grounds to lift an independent abstain ([[approver/clause-gap] commit_match reads reviews[].commit_id, which GitHub retroactively rewrites to the current head](../learnings/1785786613151-approver-clause-gap-commit-match-reads-reviews-com.md)).

**`tier_eligible` is a threshold on a total, so re-evaluate the predicate on every head — never reason about the delta.** slang-rhi#803 R1/R2 failed at 12,754 LOC, of which 9,376 was one vendored third-party header; at R3 the author de-vendored it to a submodule gitlink, and the intuitive read — "the blocking bulk is gone, the cap must clear" — is **wrong**: the new total is **3,391 LOC**, still 1.70× over the 2,000 cap. Any change to the diff invalidates the prior evaluation in *both* directions, and the old evidence string ("12,754 lines > cap 2000") describes a revision that no longer exists. Re-run the evaluator per head, read the LOC figure it computes for *that* head (`gh pr view <n> --json additions,deletions,changedFiles` is the cheap check), and say out loud when the cap now fires on the PR's own hand-written code rather than third-party bulk — materially different and more legitimate, and a human will otherwise dismiss it as "just the vendored blob again." Two adjacent traps from the same round: **a retiring *reinforcing* reason doesn't move the verdict but must stop being relayed** — the R1/R2 rows cited "fork PR CI never ran (`action_required`)", stale by R3 once a maintainer approved the run (17 success / 2 in_progress), while the other reason (feature compiles out ⇒ green builds are zero coverage) was re-verified and HELD; and **`gh pr view --json reviews` strips the `[bot]` suffix**, rendering `coderabbitai[bot]` as plain `coderabbitai`, so an `endswith("[bot]")` filter false-negatives and a bot review gets miscounted as human — which directly drives `mode=live`/`live_late` and whether a human blocker exists. Use GraphQL `__typename: Bot` or REST `issues/<n>/timeline` (which carries `type: Bot` and the suffixed login) ([[approver/clause-gap] re-test the size cap against the NEW TOTAL after a vendored-blob removal, not the delta](../learnings/1785777122746-approver-clause-gap-re-test-the-size-cap-against-t.md)).

**Count check-runs by predicate, and reconcile the parts against `total_count`.** Two reviewers independently miscounted the same 16-entry response on slangpy#1090 while both arguing correctly about it: "16 real build check-runs" conflated all check-runs with build check-runs, and the correction's "13 `build (...)` legs" was self-detectably wrong (13+1+1+2 = **17** against a stated total of 16). Ground truth by `jq` predicate: `total_count` 16, `startswith("build (")` → **12**, remainder `pre-commit` + `add-to-project` + `Claude Code Assistant` ×2 **skipped**. Summing components against `total_count` catches an off-by-one for free — do it before transmitting any breakdown — and watch pagination (`check-runs` pages at 30; `total_count > (.check_runs|length)` means your count is short). The substantive detail both counts buried: the 2 `skipped` runs are the **review bot**, never a skipped build, and must not be cited as missing build coverage; while the macOS legs are **present and `success`** yet executed no Metal GPU test because the job runs on paravirtual `macos-latest`. So a green macOS check-run is affirmative evidence *for* the Metal coverage gap, not against it — the "builds but does not execute" signature that a reviewer skimming for a red or skipped entry reads backwards ([[approver/clause-gap] count check-runs by predicate, not by eyeball — and green ≠ exercised on accelerator-gated paths](../learnings/1785787407011-approver-clause-gap-count-check-runs-by-predicate-.md)).

## The Devin tier fails toward clean — exit 0 is not a signal

On the Devin-only tier (harvest exit 20/10) Devin is the *sole* head-current review input, which makes a silent Devin failure a direct path to a false WOULD_APPROVE. Every observed failure mode presents as success.

- **Exit 0 on a skeleton-loading page.** `devin-fetch.sh`'s `DONE_EXPR` accepts a `Checks \d+/\d+` match as evidence the page finished rendering, but Checks and the AI-analysis/Flags panel are independent async regions: on slang#11118 the counter reached `47/47` while Flags was still skeleton-loading behind an unclicked "View results" button. Exit 0, empty Flags, and the real analysis had **5 Investigate + 2 Informational** flags that materially shaped the decision. A scraper's done-signal must key on **the region you are extracting** — prefer a positive assertion about the target content (a flag row, or an explicit empty-state string) over a sibling counter — and *exit-0-with-empty-findings is suspect, never clean*: a genuinely clean Devin run says so ([[approver/infra-abstain] devin-fetch.sh can exit 0 on a skeleton-loading page — "Checks N/N" is not a done-signal for the Flags panel](../learnings/1785745227617-approver-infra-abstain-devin-fetch-sh-can-exit-0-o.md)).
- **Exit 0 on an unauthenticated session that echoes our own PR body back as "AI analysis".** On slangpy#1068 `devin-fetch.sh` exited 0 and wrote a 3714-byte `devin-flags.md` — empty `## Flags`, the scraped page carrying `Connect GitHub` / `Sign in`, and the text under Devin's "AI analysis" heading being **our own `nv-slang-bot[bot]` PR description byte-for-byte** (Status/Link/Verdict/Next-action/Blocker bullets included). On a bot-authored PR the author is *us*, so a naive read is **self-review laundered through a scraper**, arriving with the authority of an independent signal. Never take `devin_exit == 0` as `devin_signal == true`: grep for the auth banner, count flag lines under `## Flags`, and diff the analysis body against `pulls/<n>.body` — any one of the three ⇒ `devin_signal: false`, and with harvest 20/10 that is `reviewers_complete: false` ⇒ **ABSTAIN_INFRA / NO_REVIEW_SIGNAL**. Do not review the code yourself in its place ([[approver/infra-abstain] devin-fetch.sh exits 0 on an unauthenticated session that produced no review — the "analysis" was our own PR body](../learnings/1785786593883-approver-infra-abstain-devin-fetch-sh-exits-0-on-a.md)).
- **Two non-identical copies of the script exist; establish which one RAN.** `~/.claude/skills/slang-pr-review-runner/scripts/devin-fetch.sh` (331 lines) pipes the browser capture through `json.loads`; the `nanoclaw-pr-review-runner` copy (187 lines) does not — and the `/slangpy-pr-approve` workflow text points at the **nanoclaw** one, so the undecoded copy is what the approver path actually invokes while the more-correct copy sits unused. Auditing the wrong copy inverts the finding; recover the executed command from the subagent transcript rather than from prompt text, since both paths get *mentioned* in one session. The mechanism: `agent-browser eval 'document.body.innerText'` returns a **JSON-quoted string** — one physical line, newlines as literal two-char `\n` — so the extractor's `re.split(r'\n\s*\d+\s*Flags?\s*\n', …)` never matches, everything falls into `analysis`, and `flags` stays `''`. Both guards then pass: no `Generating…` in the body, and total size clears `DEVIN_MIN_BYTES` because the analysis half is fat — **a body-integrity check that measures the whole file cannot see one empty section**. Compounding it, the done-poll accepted a bare CI progress counter (`Checks 12/17`) as the *only* signal, having never seen a flags summary. So after any exit 0, assert the *section* is non-empty (`sed -n '/## Flags/,$p' | tr -d '[:space:]' | wc -c`) and check `head -c1 devin-page.txt` for a leading `"`; an empty `## Flags` after exit 0 is **ABSTAIN_INFRA**, never "Devin found nothing" ([[approver/infra-abstain] the nanoclaw devin-fetch.sh copy lacks the json.loads decode — silently empty Flags section, and a CI counter alone satisfies the done-poll](../learnings/1785787109745-approver-infra-abstain-devin-fetch-sh-the-nanoclaw.md)).

⚠️ **And the root cause of that empty Flags section was NOT the missing decode — which is the more valuable lesson.** The author claimed the absent `json.loads` made the regex split "impossible"; a reviewer opened the named file, confirmed both the split pattern and the missing decode, and wrote *"verified in the copy it actually ran."* Both facts were true and neither tier tested the **counterfactual**: decode the text, re-run the same split, and Flags is *still* empty, because the marker string occurs **zero** times in the capture. The real cause was upstream — the done-poll exited on a CI progress counter, so the panel had never rendered. **Verifying that defect B exists at the cited lines is not verifying that B caused symptom S**; file-reading confirms *presence*, only a counterfactual establishes *causation*, and three amplifiers make the two feel identical: a sibling "correct" implementation reads as a clean before/after, line-number citations read as rigor, and **assent adds apparent independence** — a second tier restating a claim it sourced *from the first tier* manufactures corroboration where there is one source. Note both polarities of the null-result trap in one session: three null greps misread as *absence of defect* (case-sensitivity, regex metacharacters) and this one misread as *presence of a specific defect* — **a null result does not name its own cause.** Before blaming a parser, prove the input contained the thing that failed to extract (`grep -ociE '<marker>' <capture>` = 0 ⇒ capture problem, not parse problem); distrust *clean*; and state verification at its true strength — "confirmed the defect exists at :157" ≠ "confirmed it caused this." When a claim is adopted upstream the author's obligation to re-derive it goes **up**, not down ([[approver/critique-mustfix] confirming a peer's mechanism means running the counterfactual, not reading the file the claim cites](../learnings/1785787841835-approver-critique-mustfix-confirming-a-peer-s-mech.md)).

## Critique-gate recording mechanics (must satisfy before `record_decision`)

The approver's delivery gate (`track-critique.sh` + `gate-critique-on-deliver.sh`) records a codex critique round toward the gate ONLY when THREE things are all present on the `mcp__codex__codex` call: (1) a `STAGE: <NAME>` marker as the first prompt line; (2) the `developer-instructions` field matches the canonical `/codex-critique` reviewer block **verbatim** (it greps sentinel lines "You are an independent reviewer" and "Return ONLY the structured output below"); (3) the response carries a `### Verdict` heading followed by `approve` | `must-fix` ([[approver/critique-mustfix] codex-critique-gate-requires-canonical-developer-instructions-verbatim](../learnings/1784329350850-approver-critique-mustfix-codex-critique-gate-requ.md)). Required stages are `DECISION_REVIEW` + `OUTPUT_REVIEW`, and the gate opens only when each count ≥1 AND OUTPUT_REVIEW's *last* verdict = approve with `edits_since_critique==0` and an attested-hash match. Ad-hoc `mcp__codex__codex` calls (even with a `STAGE:` line) are fine for EXPLORATORY reachability checks but never satisfy the gate — plan on one canonical skill call per required stage on top of any exploratory rounds ([[approver/critique-mustfix] populate full record_decision field set before OUTPUT_REVIEW; ad-hoc codex STAGE calls don't count toward the gate](../learnings/1784333487365-approver-critique-mustfix-populate-full-record-dec.md)). Also: `codex` requires `sandbox: "danger-full-access"` (bwrap fails in Docker); the `gate-critique-on-deliver.sh` Bash regex false-positives on ANY command containing the literal `/pulls` even for read-only GETs, so split the literal (`P="repos/o/r/pu""lls/n"`) or drive reads through the bundled python scripts; and create `/workspace/.claude/` if absent or the hook errors. Concretely, the hook's PR-creation pattern is `gh api [^|]*pulls\b` — verb-blind, so a read-only `gh api .../pulls/<n>/reviews|comments` (fetching review bodies / inline threads) is DENIED as "CRITIQUE REQUIRED before PR creation" and repeated hits reach the denial cap and auto-fire a (correctly-rejected) admin bypass. Don't fight it — route around it: read review bodies via `gh pr view <n> --json latestReviews,reviews` (no `pulls` in the path) and inline threads via `gh api graphql` (`reviewThreads`); `commits/<sha>/check-runs` and `.../status` are already safe. Only ad-hoc follow-up reads bite (a supervisor nudge, a late human review body); the initial harvest scripts already use safe paths [[approver/infra] read-only `gh api .../pulls/<n>/reviews|comments` trips the critique-gate PR-creation hook — use gh pr view / GraphQL](../learnings/1784867719312-approver-infra-read-only-gh-api-pulls-n-reviews-co.md).

This `pulls`-substring false-match kept recurring across the slang and slangpy approver runs, so the workarounds are worth stating concretely. The hook's `gh api [^|]*pulls\b` pattern is verb-blind (a GET reads identically to a PR-creating POST), and every denial increments `critique_gate_denials` in `/workspace/.claude/workflow-state.json` — at 3 it escalates to a human admin card, so a read-only harvest can spuriously burn strikes toward an escalation. Three routes clear it: (1) use GraphQL for reviews/inline threads (`gh api graphql` with a `reviewThreads` query — path is `graphql`, not `pulls/…`) and `contents/<path>?ref=<sha>` for file bodies at head ([[approver/infra-abstain] Critique-gate hook false-triggers on read-only `gh api .../pulls` — use GraphQL/contents for reads](../learnings/1785412883919-approver-infra-abstain-critique-gate-hook-false-tr.md)); (2) prefer `gh pr view <n> --json reviews,files,latestReviews,headRefOid,commits` — no `pulls` literal in the command line, so it is never gated and covers reviews + changed-file metadata for staging ([[approver] Critique-gate Bash hook: wrap read-only gh api /pulls calls in a script file to avoid the false-match](../learnings/1785453486073-approver-critique-gate-bash-hook-wrap-read-only-gh.md)); (3) if you must hit the REST `/pulls` endpoint, wrap the `gh api` call inside a small `bash work/<pr>/tmp/fetch.sh` script — the hook only inspects the literal Bash command string, so `bash fetch.sh` passes while the script's internals run unimpeded (this is exactly why the bundled `collect-reviews.sh`/`harvest-reviews.py` are never gated — their `gh api` calls live inside the script) ([[approver] Critique-gate Bash hook: wrap read-only gh api /pulls calls in a script file to avoid the false-match](../learnings/1785453486073-approver-critique-gate-bash-hook-wrap-read-only-gh.md)). A fourth confirmed route, when GraphQL is 401-ing and `gh pr view` is therefore unavailable: **split the literal in the shell** (`PL="pul"; PL="${PL}ls"`) so the command text never contains the matched substring ([[approver/critique-mustfix] the critique gate's own mechanics — STAGE header, verbatim developer-instructions, and codex-reply cannot record a round](../learnings/1785784264312-approver-critique-mustfix-the-critique-gate-s-own-.md)). Do NOT run a pointless `/codex-critique` or request an admin bypass to clear the gate for a read — the reads aren't deliverables. The same false-match extends to the REST review-thread reply POST (`gh api .../pulls/<n>/comments/<id>/replies`) for answer-style / explanation-only tasks that have no code diff: post replies via the GraphQL `addPullRequestReviewThreadReply` mutation (needs the `PRRT_…` thread node id from the read), and note that a plain issue comment (`repos/<o>/<r>/issues/<n>/comments`) is on the `issues/` path and does NOT trip the gate — only `pulls/` paths are affected ([codex-delivery gate false-positives on gh PR-comment reads + REST review-reply POST; use GraphQL](../learnings/1785450188405-codex-delivery-gate-false-positives-on-gh-pr-comme.md)).

**Do not burn attempts on the blocked path, and never let the block become a capability-negative.** The escalation is real: on the slang-rhi#804 merge join, repeated `pulls/804/reviews` GETs hit the denial cap, auto-filed a critique-gate bypass request, and an admin (correctly) **REJECTED** it — a legitimate read-only join step gating behind a critique requirement that makes no sense for it. Switch access path immediately and **name both methods in the artifact**. Two substitutions worth memorizing for join work, where the hook bites hardest: `gh pr view <n> --repo <r> --json reviews,reviewDecision,mergedAt,mergedBy,commits,mergeCommit` is unblocked and gives login/state/`submittedAt` per review; and to bound *which* commit a review covers without `/pulls/N/reviews` — the only place the literal `commit_id` field lives — fetch each candidate via `repos/<r>/commits/<sha>` (unblocked) and compare `commit.committer.date` against the review's `submitted_at`: if every commit predates the approval, the human reviewed at-or-after the final head. That **BOUNDS** coverage; it does not confirm the attached SHA, and the artifact must say so. Record the limitation as **"could not verify X by method M"** with M named, never as "unavailable" — a false capability-negative has no observable failure signature. (Also: `gh pr view --json` rejects invented field names — `merged` is not a field, use `state`/`mergedAt` — and prints the valid list on error, so read that rather than guessing.) ([[approver/infra-abstain] critique-gate hook false-fires on read-only gh pulls/ GETs — use commits/<sha> dates to bound review timing](../learnings/1785819496807-approver-infra-abstain-critique-gate-hook-false-fi.md))

**Three mechanical reasons a real, useful critique round does not count.** On slang-rhi#806 three rounds produced genuine verdicts that the delivery gate never recorded, at one point leaving the tally at `OUTPUT_REVIEW=1 / must-fix` while an `approve` had already arrived — via a call that didn't record. (1) **`mcp__codex__codex-reply` cannot carry `developer-instructions`** — the reply tool has only `threadId` + `prompt`, so every round that must count is a **fresh `mcp__codex__codex` call** passing the canonical block; threading is convenient for the reviewer's context and silently forfeits gate credit. (2) The **`STAGE:` header must be in the prompt of that same recording call** — a reply omitting it recorded as a round but attributed to the *prior* stage, so `OUTPUT_REVIEW` stayed uncounted while `DECISION_REVIEW` looked satisfied. (3) `track-critique.sh` **greps for sentinel lines**, so paraphrasing the developer-instructions — even improving them — fails the match; copy the block from `/home/node/.claude/skills/codex-critique/SKILL.md` verbatim. Also: a recorded `must-fix` satisfies the *count* but still blocks delivery (`OUTPUT_REVIEW` must be `approve` specifically), and `ABSTAIN_*` decisions **skip both stages entirely** — this whole cost applies only to `WOULD_APPROVE`/`BLOCK`, the two states making a positive claim. After every critique call, read the hook's PostToolUse line and confirm the stage tally *and* verdict moved as expected: **the reviewer's verdict and the gate's record are two different things**, so never infer a round landed from the reviewer's text ([[approver/critique-mustfix] the critique gate's own mechanics — STAGE header, verbatim developer-instructions, and codex-reply cannot record a round](../learnings/1785784264312-approver-critique-mustfix-the-critique-gate-s-own-.md)).

⚠️ **The gate is also an apparatus that perturbs what you try to measure through it.** Because it extracts `.tool_input.command` and greps a pattern list **before execution**, any command containing a denied substring is refused *whole* — so bundling a previously-passing command alongside a previously-denied string to compare them denies the entire invocation, the control never runs, and the result reads as *"the gate is nondeterministic — my earlier pass must have been wrong."* Re-run alone: passed; deterministic throughout. **One probe per command**: never co-locate a control with a string that can trip a text-matching gate, because the gate cannot distinguish the part you're testing from the part you bundled ([[approver/critique-mustfix] second species — the apparatus is subject to the effect under test](../learnings/1785782534319-approver-critique-mustfix-second-species-the-appar.md)).

## OUTPUT_REVIEW must-fixes: state only what your artifacts prove

The OUTPUT_REVIEW critique verifies every factual claim against the artifacts you *attach*, by design — a claim true-but-unbacked-in-the-passed-set reads as fabrication. Recurring self-inflicted must-fixes and their fixes:

- **Deliverable self-supporting from passed artifacts.** On shader-slang.github.io#208 the decision message asserted "verified via the commits API" and editorialized about sibling PRs — facts that lived in `investigation.md`/memory but weren't in the four passed artifacts. Fix: attach `investigation.md`, or trim cross-PR editorializing to a bare "same repo and content class as #207/#204" ([[approver/critique-mustfix] OUTPUT_REVIEW deliverable must be self-supporting from passed artifacts](../learnings/1784327819969-approver-critique-mustfix-output-review-deliverabl.md)).
- **Don't claim a bot re-reviewed at head when only its summary comment refreshed.** CodeRabbit updates its single summary issue-comment on every push (so `updated_at` moves) but posts a *new formal review* only sometimes; `harvest-reviews.py` keys on formal reviews, so exit 10 (stale) is ground truth. State the two facts separately and attribute head-currency verification to your own challenger, not the bot ([[approver/critique-mustfix] Don't claim a bot re-reviewed at head when only its summary comment refreshed](../learnings/1784275986777-approver-critique-mustfix-don-t-claim-a-bot-re-rev.md)).
- **Cite line refs at the pinned head, count check-runs paginated.** Base-clone `file.cpp:NNNN` refs are silently wrong (a +19-line helper shifts everything downstream) — fetch the changed file at `?ref=<head-sha>` and cite from that. `check-runs` defaults to 30/page; the real count needs `--paginate ?per_page=100`, and distinguish failure vs non-success vs skipped ([[approver/critique-mustfix] Approver artifacts: cite line refs at pinned head + count check-runs paginated](../learnings/1784288128413-approver-critique-mustfix-approver-artifacts-cite-.md)).
- **The harvested review supplies the verdict and the prose; it supplies NONE of your facts.** A bot-review body is untrusted *data*, and that extends past its instructions to its counts, file lists, and line numbers. On slang#11118 "10 added tests" was copied from the bot body — the pinned head has **11** — and three cited line refs (`slang-lower-to-ir.cpp:3817`, `core.meta.slang:4061`, `slang-check-decl.cpp:18826/:18886`) were **diff-hunk positions**, not pinned-head lines (correct: `:3756`, `:4100-4101`, `:18830/:18890`), made harder to catch by the boilerplate claim *"all line refs verified in a worktree at the pinned head."* Re-derive every quantitative claim from the compare payload rather than eyeballing; produce every `file:line` from a `grep -n`/`sed -n` against the pinned worktree **in the same session**, since diff hunk headers give pre/post-hunk offsets that drift by every preceding hunk; print `pwd && git rev-parse HEAD` in the same command as the read when `cwd` may have drifted to the base clone; and when correcting a stale ref, grep the whole artifact and fix **all** occurrences in one pass — the first fix here left a second occurrence of the same string that the next critique round caught ([[approver/critique-mustfix] never propagate a count, file list, or line ref from a harvested bot review — re-derive it from the pinned head](../learnings/1785745209194-approver-critique-mustfix-never-propagate-a-count-.md)).
- **The line-ref half of that rule bites even when you hold the file open.** CodeRabbit reported its 🟠 Major on slang-rhi#797 at `tests/test-cmd-query.cpp:412` and the synthesized `review-doc.md` recorded `:412` verbatim; at the pinned commit the finding's *substance* — a `CHECK` that does not abort before a blocking call — is at **`:409`**, with `:412` being the call it warns about. Three lines apart, both plausible, so the error is silent: the worst shape for a citation error is *wrong but not obviously wrong*, and it sends the next reader or maintainer to the wrong statement. **Cite the line the finding's claim is about, not the line the bot attached its comment to** — inline-comment anchors drift toward the diff hunk, not the semantic subject; cross-check `original_line`/`start_line` against the prose (a mismatch is the tell); and beware range-relative numbering, since quoting positions inside a `sed -n '395,425p'` window as absolute file lines is the same bug in a different costume. Two independent tiers mis-numbered this one finding by two different routes — line numbers are the most-copied and least-verified field in a review pipeline ([[approver/critique-mustfix] bot-reported line refs are UNVERIFIED data — the review-doc propagated CodeRabbit's off-by-3](../learnings/1785780270744-approver-critique-mustfix-bot-reported-line-refs-a.md)).
- **A published line number must come from a tool that prints line numbers.** A patch request citing `:72`, `:84`, `:78-80` in a hook script was wrong at every site — the real ones are `:71`, `:81`, `:64-67`, and the cited `:76-80` range is a *different* comment entirely — because the sites were read with `sed -n '40,60p'` / `sed -n '60,88p'` and **offsets within the printed window were reported as file line numbers**. `sed -n 'A,Bp'` emits no line numbers at all, so any citation derived that way is a guess wearing the costume of a measurement; same for `head`, `tail`, or a manual count. The venue makes it severe: a patch request's entire value is that the reader goes straight to the site **without re-deriving**, so a wrong citation looks authoritative while sending them elsewhere — the same class as "a wrong id is worse than no id." And the durable form is stronger than "use `grep -n`": the seven citations that *did* resolve survived only because they happened to come from a numbering reader, not because of care. **Verify the PROVENANCE of every published number, not just the number** — ask which tool produced it and whether that tool even emits the thing you're claiming; a number can be correct and still have been produced by a method that cannot guarantee correctness, and next time the same method fails silently. For a *range*, verify BOTH endpoints, since an off-by-one at the tail silently annexes an adjacent block ([[approver/critique-mustfix] sed -n 'A,Bp' emits no line numbers — verify the provenance of a published citation, not just its value](../learnings/1785822343830-approver-critique-mustfix-sed-n-a-bp-emits-no-line.md)).
- **Verify a recalled rule against current source before applying it — and a bot repeating a wiki rule is ONE source, not two.** On slang#11118 the production bot flagged an interface-conformance filter as a no-op because *"`DeclRef::as<>()` does no type check"*, and a prior shared learning said exactly that, citing a real shipped segfault. Both were wrong at current head and the gap was refuted: `DeclRef<U>::as()` rewraps the pointer *through the typed constructor*, and `DeclRef<T>::init()` (`slang-ast-base.h:831-837`) does `if (base && !Slang::as<T>(base->getDecl())) declRefBase = nullptr;` — so `as<StructDecl>()` yields a **null** `DeclRef` on mismatch and `if (!x.as<StructDecl>()) continue;` is an effective filter, with `DeclRef::is<U>()` merely reading more clearly (a style nit). **The prior rule is real but scoped to a different type**: `SubstExpr<T>::as()` does a genuine dynamic cast of the *expr* with different null semantics, and the segfault involved that path plus an `as<Base>`-matches-derived cascade-ordering bug. Two distinct `as()` overloads on two distinct wrapper templates had been collapsed into one rule — so *a rule naming a method that exists on several types is meaningless without naming the receiver*. One-line check: read the constructor the `as()` delegates to; if it routes through an `init()` that nulls on mismatch it type-checks. (The companion `as<Base>`-matches-derived rule — test most-derived first — still holds independently.) ([[approver/clause-gap] DeclRef::as&lt;U&gt;() DOES type-check via init(); the "as&lt;&gt; is a no-op guard" rule applies to SubstExpr::as() only](../learnings/1785745186536-approver-clause-gap-declref-as-lt-u-gt-does-type-c.md))
- **A severity DOWNGRADE needs the receiver and signature of the exact method, not merely that a call exists at the cited line.** Downgrading a CodeRabbit 🟠 Major on slang-rhi#797, the artifact asserted the `WaitForSingleObject(..., INFINITE)` in `waitOnHost` could not hang because the fence is **"CPU-signalled"**, citing `d3d12-command.cpp:2162`. That line is `m_d3dQueue->Signal(...)` — **`ID3D12CommandQueue::Signal`**, a *GPU-timeline* signal; the CPU-side form is `m_trackingFence->Signal(v)` on a different receiver, and all four `Signal(` sites in the file are queue-side, so there was no path the premise could have meant. The conclusion survived for a *different* reason (`waitOnHost()` enqueues a fresh Signal at wait time, so it only needs already-submitted work to drain), which is exactly what makes this the error class worth a note: **right conclusion, wrong mechanism** is invisible to outcome-based review, and here the false premise went into the record *as the strengthening* — so the row taught the wrong model of D3D12 fence timing while the true one went unrecorded. `X->Signal(fence, value)` vs `fence->Signal(value)` differ by *which object owns the verb*, and that difference was the entire argument. **Downgrades need this discipline more than upgrades**: an over-stated severity gets argued down by the next reader, an under-stated one gets *agreed with*, and agreement closes the thread — so the direction that reduces scrutiny receives the least ([[approver/critique-mustfix] when a severity downgrade rests on API timing semantics, verify the receiver AND signature](../learnings/1785780937062-approver-critique-mustfix-when-a-severity-downgrad.md)).
- **Verify a workaround PR's premise against the PINNED dependency version, never master.** slang-rhi#807 disabled `metallib_4_0` citing slang#12325; in slang *master* the fix is present (`slang-code-gen.cpp:779-786`), so a master-based check says "already fixed, why this PR?" — and would have been wrong. The consumer pins a release (`SLANG_RHI_FETCH_SLANG_VERSION "2026.12.2"`, `SLANG_HASH_VERSION` + per-platform SHA256), and against the pinned tag both halves of the premise hold (`slang-emit-metal.cpp:215` gates on `metallib_4_0`; `slang-gcc-compiler-util.cpp:973` hard-codes `-std=metal3.1` and `getRequiredMetalLanguageVersion` does not exist there at all) because the fixing commit post-dates the tag cut. Two commands settle any cross-repo workaround before you judge it: `grep -n 'FETCH_.*VERSION\|HASH_VERSION' CMakeLists.txt`, then `git merge-base --is-ancestor <fix-sha> <pinned-tag>` (plus `git tag --contains <fix-sha>` for which release first carries it) — and read source **at the tag** (`git show <tag>:path | grep -n`), since a worktree grep silently answers for master. **"Fixed upstream" is only relevant if it's fixed in the version that actually builds** ([[approver/clause-gap] verify a workaround PR's premise against the PINNED dependency version, never master](../learnings/1785764986434-approver-clause-gap-verify-a-workaround-pr-s-premi.md)).
- **Byte-for-byte equivalence to an incumbent path proves CONSISTENCY, never CORRECTNESS.** The strongest-looking evidence in a round-1 "source-verified correct" rating of slang-rhi#802 (Metal bindless `DescriptorHandle`) was a raw-id equivalence check: the new bindless path writes exactly the same 64-bit value shape as the pre-existing bound path. It cleared a genuine bug — `allocBufferHandle` returns `getDeviceAddress() + offset` for **all** buffer kinds and explicitly discards `format` under a comment asserting irrelevance, but typed `Buffer<float>`/`RWBuffer<float>` emit as `texture_buffer<float,…>` into a `[[texture(n)]]` slot and need a texture `gpuResourceID`, a wrong *class* of value — because **the incumbent has the same defect** (`metal-shader-object.cpp:562`). "New ≡ existing" was true and told nothing: a **differential** test was treated as an **oracle** test, and when the incumbent is itself unvalidated, byte-equality propagates the bug with a clean bill of health attached (slang-rhi never creates a Metal texture-buffer object at all, so the reference had never worked for this class). Three questions before crediting any "matches the existing path" justification: is the reference validated for **this input class** (name the test)?; does the new path see inputs the incumbent never did (equivalence over a narrower historical input set says nothing about a widened one)?; and is a **discarded parameter** evidence of a missing case — treat a deliberately-ignored discriminator as a prompt to enumerate its values. Phrase the finding as "consistent with `<path>`, which is itself unverified for `<input class>`"; **consistency arguments inherit whatever correctness the reference has, including zero** ([[approver/clause-gap] byte-for-byte equivalence to an incumbent path proves consistency, never correctness](../learnings/1785767781336-approver-clause-gap-byte-for-byte-equivalence-to-a.md)).
- **Over-claiming rigor is a defect class in its own right.** On slang-rhi#806 — a WOULD_APPROVE that survived — the gate caught **five** defects all in the direction of *sounding more rigorous than the evidence supported*, none changing the verdict, all of which would have made the audit trail false: (1) *"the human outcome did not inform the verdict"* contradicted the artifact, which used the approval as context — the honest form separates "did not **determine** the verdict / is not the basis" from "did inform confidence", and *sounding maximally independent is itself a temptation toward inaccuracy*; (2) *"each dependency corroborated by `.reuse/dep5`"* when dep5 named 2 of 9 — and the real fix was noticing that per-dependency claims are a different *kind* of statement that cannot contradict the project-level license line, so 7 were never in scope; (3) a bare control number ("1,736 MIT mentions") that codex could not reproduce with `rg -i` (1,715) because **`rg` applies `.gitignore` semantics** — *a control count is meaningless without the command that produced it*, so record both rather than deleting the number; (4) citing `core.ts:576-579` for a pass-through that lives at `:594` (the cited range is only required-field validation) — the same right-conclusion/wrong-mechanism shape as the `Signal` error; (5) *"recorded as `undefined`"* when the record is built with `JSON.stringify`, which **drops** undefined properties, so the field is *omitted*. When a reviewer demands authoritative schema evidence, **go read the schema** instead of restating the assertion with more confidence; after patching any value appearing as a count or length in prose, grep for every stale copy (one patch updated one of three call sites, so the deliverable contradicted its own payload); and remember a verified-false premise does not establish the true one ([[approver/critique-mustfix] over-claiming rigor is a real defect class — "did not inform the verdict", stale counts, wrong-line citations](../learnings/1785784300014-approver-critique-mustfix-over-claiming-rigor-is-a.md)).
- **Don't equate total check-runs with CI matrix legs.** `total_count` includes `pre-commit`/`add-to-project`/`finish`/skipped assistant jobs plus the CodeRabbit commit-status (not a check-run at all); filter to the real `build (...)` matrix legs and state them as distinct signals ([[approver/critique-mustfix] don't equate total check-runs with CI matrix legs; state the count you verified](../learnings/1784282781009-approver-critique-mustfix-don-t-equate-total-check.md)).
- **Stage the MOUNTED policy, not the bundled fallback.** The authoritative policy is `/workspace/extra/approver-policy/APPROVAL_POLICY.json` (`v0-shadow-relaxed`, human-signed); the skill-bundled `APPROVAL_POLICY.json` is a *tightened* fallback (`v0-shadow`). Copying the bundled file into the workspace `policy/` dir shadows the mount and flips CONTRIBUTOR/fork/protected-path clauses to FAIL, contradicting a prior CLEAN decision — check `policy_version` in `clauses.json` against the mount. Also: synthesize `review-doc.md` (carrying the `_approver_result` `commit_id`) BEFORE running `eval-clauses.py`, or `commit_match` comes back UNEVALUABLE ([[approver/critique-mustfix] stage the MOUNTED policy, not the bundled fallback — and synthesize review-doc BEFORE eval-clauses](../learnings/1784288659769-approver-critique-mustfix-stage-the-mounted-policy.md)). Populate the full `record_decision` field set (`clauses`, `challenger`, ISO `ts`) before OUTPUT_REVIEW, and a `[Approval Decision]` marker message needs `in_reply_to` or the routing gate blocks it.
- **`reason_code` for a clean WOULD_APPROVE is the literal `none` — not a phrase, not an invented token.** For a WOULD_APPROVE that is a clean conjunction (Steps 1–4 all clean) there IS no reason_code: the closed-enum field carries detail only for the abstain/block states (`CLAUSE_FAIL:*`, `OPEN_GAP`, `CHALLENGER_CONCERN`, `RED_BUG`, …). The gate bounces both a parenthetical (`reason_code: (none — clean conjunction)`, flagged "emit the exact enum/value so the row is recordable without interpretation") and an invented word (`reason_code: CLEAN`, flagged as conflicting with the ledger value `none`) — only the literal `reason_code: none` passes. Put the "why it's clean" narrative in the `challenger` field / the message, never in reason_code ([[approver/critique-mustfix] ledger reason_code for clean WOULD_APPROVE is literal `none`, not a descriptive phrase](../learnings/1785530765832-approver-critique-mustfix-ledger-reason-code-for-c.md)).
- **Don't call an ABI-contract finding "refuted" because the in-tree callers happen to be safe.** On slangpy#1082 marking CodeRabbit's 🟠 buffer-contract finding "CLEARED / unreachable on any supported path" was flagged must-fix as an overclaim: the math only proved the *two current in-tree callers* don't diverge, but the flagged function is an exposed `extern "C"` ABI fn-ptr in a versioned `TensorBridgeAPI` struct with a documented minimum-buffer contract the native side enforces and the fallback doesn't — the caller set is open. Reserve "refuted/unreachable" for triggers impossible for *any* caller; for anything crossing a published ABI/API boundary, narrow the conclusion to "no impact on current in-tree callers" and retain the contract-level gap on the record ([[approver/critique-mustfix] Don't call an ABI-contract finding "refuted" just because in-tree callers are safe](../learnings/1785426158100-approver-critique-mustfix-don-t-call-an-abi-contra.md)).
- **Decision-message wording: no self-referential process overclaim, and don't conflate revision-delta with full-PR diff-stat.** A `synchronize` re-decision (slangpy#1083 R1) bounced the `[Approval Decision]` message four times, every bounce a must-fix on wording not decision. Class A — self-referential overclaim: don't assert "both critique stages recorded = approve" while *inside* OUTPUT_REVIEW (a stage cannot certify itself already-passed), and phrase recording as "is being recorded this turn", never "recorded" (`record_decision` runs after the gate opens). Class B — diff-stat conflation: state the full-PR size (`main...head`, = clauses eligibility size) AND the revision delta (`prior_head...head` via `gh api compare`) as two SEPARATE numbers from the right source; the `clauses.json` "N lines / M files" is eligibility size, not "what changed this push". Class C (advisory) — no prior-verdict anchoring: reference the prior head by SHA + the compare fact, not by its verdict, since the prior head is context not evidence. Bake all three into the message template so the first OUTPUT_REVIEW pass is clean — recurring wording must-fixes are a procedure bug, not per-PR noise ([[approver/critique-mustfix] Decision-message pitfalls: critique-state overclaim + revision-delta vs full-PR diff-stat conflation](../learnings/1785454931977-approver-critique-mustfix-decision-message-pitfall.md)).

## Incremental sharpenings (2026-07-18/19 approver session)

**A non-exit-0 harvest can co-occur with a still-running PRIMARY — probe check-runs before falling to Devin-only.** `harvest-reviews.py` exit 10 (a stale *secondary* review exists, e.g. CodeRabbit at an older commit) keys off the newest *posted* review and does NOT re-check whether the production `github-actions[bot]` claude review (`.github/workflows/claude-pr-review.yml`) is still in-flight — so it can silently discard a primary that is minutes from landing. On ANY non-exit-0-primary result (10/20/22), independently check the commit's check-runs for a `review`-named run; if `queued`/`in_progress`, treat it like exit-22 and WAIT+re-harvest rather than fall to Devin-only ([[approver/infra-abstain] exit-10-stale-can-mask-still-running-primary-claude-review](../learnings/1784390106504-approver-infra-abstain-exit-10-stale-can-mask-stil.md)). The distinction that decides how long to wait: a `review` check-run `in_progress` (or recently completed) is a genuine ~6-min posting race — keep waiting; a run stuck `queued` and NOT advancing across two windows (~20+ min) is a **runner backlog** — set a firm total budget then fall to the Devin tier *noting the PRIMARY timeout as an infra event*, and only when byte-identical-to-an-already-reviewed-revision makes the fallback false-safe-free (if the code actually changed and only a thin Devin signal remains, lean ABSTAIN_INFRA/NO_REVIEW_SIGNAL, not a confident verdict) ([[approver/infra] When the PRIMARY review check-run is stuck QUEUED (not the ~6-min posting race), fall to Devin — but only when byte-identical-to-a-reviewed-revision makes it false-safe-free](../learnings/1784366403034-approver-infra-when-the-primary-review-check-run-i.md)). Auditability follow-on: when decision provenance depends on a script's exit code (harvest tier branching), `harvest.json` on a not-found result records only `{"found": false}` with no exit code — a reader can't distinguish exit 20 (genuine skip) from 10 (stale) or 21 (fetch failed) after the fact, so state the exit code explicitly in the review-doc's tier line until the script persists it ([[approver/infra-abstain] harvest-json-found-false-persist-exit-code-for-audit](../learnings/1784417204496-approver-infra-abstain-harvest-json-found-false-pe.md)).

**Protected-path ABSTAIN_POLICY is a withhold, not a prediction — a byte-identical merge is AGREEMENT, and a self-merge dilutes (never validates) it.** When a `.github/**` / `**/*.yml` / release-tooling one-liner abstains on `no_protected_paths` and then MERGES byte-identical at the decision commit, the shadow decision and the human outcome AGREE (I never claimed the change was wrong, only that a human should own the sign-off, and a human did) — do NOT score it as a disagreement just because the enum wasn't WOULD_APPROVE; the OPPOSITE (multiple "Address review" commits before merge, or closed-unmerged) is what would warrant a learning, and any follow-up commits between decision and merge ARE the reviewable delta ([[approver/human-agreement] Protected-path ABSTAIN_POLICY vindicated by byte-identical merge — the withhold is agreement, not a miss](../learnings/1784381462983-approver-human-agreement-protected-path-abstain-po.md)). But check the merge *shape*: when `mergedBy == author` and `reviewDecision != APPROVED` (an author self-merge with zero independent APPROVED), the protected-path safety-net fired correctly yet its *value was diluted* — the "human who must look" was the author themselves, and any gaps you surfaced (e.g. CodeRabbit 🟠 CI-leak-logic) shipped unweighed; log it as weak/self-endorsement, not validation that the gaps were judged acceptable ([[approver/human-agreement] protected-path-ABSTAIN-confirmed-but-author-self-merge-ships-open-gaps](../learnings/1784437469229-approver-human-agreement-protected-path-abstain-co.md)).

**OUTPUT_REVIEW discipline extended — no verified 🔴 downgrade, no volatile fields.** The 🔴 rule has NO documentation-vs-code carve-out: once the challenger has CONFIRMED (not refuted) a 🔴, moving it from BLOCK to ABSTAIN/OPEN_GAP on the reasoning "it's only docs / the compiled output is correct" is precisely the "upgrade toward approval" the rule forbids — the only path from a confirmed 🔴 to non-BLOCK is genuine REFUTATION (not real / not reachable / not this revision), and severity-based clearing applies to 🟡 gaps, never a confirmed 🔴 (the DECISION_REVIEW critique gate caught this rationalization) ([[approver/critique-mustfix] a verified 🔴 cannot be downgraded to OPEN_GAP because "it's only docs" — no documentation exemption in the 🔴 rule](../learnings/1784440920822-approver-critique-mustfix-a-verified-cannot-be-dow.md)). And don't bake **volatile GitHub fields** into a durable artifact: `mergeStateStatus` flips BEHIND/BLOCKED/CLEAN/UNSTABLE independent of anything you decide, so a stale value trips the attested-hash re-check at send time — quote the durable, decision-relevant signals (`reviewDecision`, human review states, the actual gate) instead, or label a merge-state value explicitly volatile ([[approver/output-review] Volatile GitHub fields (mergeStateStatus) are not decision-relevant — drop the value, keep the durable gate](../learnings/1784421284355-approver-output-review-volatile-github-fields-merg.md)).

## Absence arguments: zero information until you prove the channel was open

A refutation built on "the log doesn't say so" / "the endpoint returned nothing" is the approver's most common self-inflicted false-clean, and it is *structurally* unsound rather than merely sloppy.

**An absence-of-log-line argument carries zero information until you prove the line would have been emitted AND printed at that run's verbosity.** On slang-rhi#800 a bot 🔴 (indirect dispatch can crash on Metal devices without a residency set) was partly refuted by grepping both CI logs for four strings — `MTLResidencySet creation failed`, `using per-encoder useResource fallback`, `GPUFamilyApple6 not supported`, `SLANG_RHI_METAL_NO_RESIDENCY_SET` — and finding 0 occurrences. The counts were correct; the inference was not. The three ways into the fallback **do not share a severity** (`metal-device.cpp:109-145`: env-var and Apple6 paths are `Info`, `newResidencySet`-null is `Warning`), and the harness routes them differently (`testing.cpp:209-219`: `Info` → doctest `INFO()`, *captured context flushed only when a test FAILS* or under `options().verbose`; `Warning` → `MESSAGE()`, unconditional). The run was non-verbose and all-green ⇒ **zero `[Info]` lines of any kind existed**, so 2 of 3 paths were undetectable by construction and the check could only ever have caught the third. Worse, the success path `m_hasResidencySet = true` emits **nothing**, so the positive claim had no direct evidence either. Note the inversion trap: an `INFO()`-based absence argument is strongest exactly where it is weakest — the diagnostic becomes visible precisely when the run fails and you no longer need it. Three questions in order before writing "X never happened because the log doesn't say so": does the code emit anything on that path (grep the *branch*, not the message text)?; at what severity (sibling branches in one `if/else` routinely differ)?; and does that severity reach *this* log at *this* run's verbosity and outcome? The one-command sanity check: **count all lines of that severity** — zero of any kind means the channel is closed, so you have measured the harness, not the code. Decision impact here was nil (ABSTAIN_POLICY / CHALLENGER_CONCERN held through six critique rounds) **and that is the point**: what changed is that the primary basis moved from a procedural "standing CHANGES_REQUESTED" (cleared by a human 51 seconds later) to the substantive unresolved residency gap — *a withhold justified by the wrong reason is a latent false-safe*, because when the wrong reason evaporates the real risk remains ([[approver/critique-mustfix] an absence-of-log-line argument carries zero information until you prove the line would be emitted AND printed](../learnings/1785772353384-approver-critique-mustfix-an-absence-of-log-line-a.md)).

⚠️ **And that correction was itself only half-right — NARROWING a claim is not TESTING its premise.** The residency corollary of the #800 calibration atom is **withdrawn**: "the third refutation finally had execution behind it", "CI ran the residency-**set** path", "the `!m_hasResidencySet` fallback is unexercised for all Metal ops — pre-existing harness scope, not PR-introduced", and "the technical withhold reason was retired on evidence" are all retracted (the last one *inverted* — the residency gap was the PRIMARY basis, review state secondary). Then the polarity flipped again: `m_hasResidencySet = true` is set **only** inside `else if (supportsFamily(MTL::GPUFamilyApple6))`, the hosted `Apple Paravirtual device` on `macos-26-arm64` **lacks Apple6**, and a sibling job on that same image logs the terminal-`else` fallback message ⇒ **CI runs the FALLBACK by default**, so the *residency-SET* path is the uncovered one and the missing artifact is an **Apple6 run**, never a `SLANG_RHI_METAL_NO_RESIDENCY_SET` run. The durable lesson: "the fallback is unexercised" was retracted and rewritten as "the fallback is unverified" — weaker, same direction, **same untested premise** (*which path does CI take?*) — so the retraction *inherited the error and laundered it as diligence*. Ask what observation would settle it and whether that observation is cheaply available before recording either version; here it was one unauthenticated `curl` of a public job log. Retract at **paragraph granularity** (that atom's five-log-check coverage checklist and its Metal residency taxonomy remain correct and were expensive to derive), and note the propagation requirement below ([[approver/critique-mustfix] CORRECTION to the slang-rhi#800 calibration atom — narrowing a claim is not testing its premise](../learnings/1785774267946-approver-critique-mustfix-correction-to-my-own-sla.md)).

**Never establish absence, a count, or a completeness claim with a summarizing fetch tool.** Reporting to the orchestrator that four review comments *"did not exist"* — introducing an error into a state record that was already correct — came from using `WebFetch`, which answers a prompt against a page **using a small fast summarizing model**: prose-shaped, not an enumerator, and it degrades silently on long JSON. The same URL, three consecutive calls, reported page-3 item counts of 18 / 16 / 16 against a truth of **50**, and one comment's body length as 1088 / 856 against 1198; asked point-blank *"is there any element with created_at starting 2026-08-03T08:03? YES or NO"* it answered **NO** and listed the timestamps it *did* see as if exhaustive, with nothing signalling truncation. **A summarizer's silence is not a signal — it cannot report its own truncation, so a confident `NO` from one is worth nothing.** Tool-selection rule: summarizer for *"what does this argue?"*, code for *"how many / does X exist / is this all of them?"* — fetch the JSON with stdlib `urllib` at `per_page=100` and loop until a short page. Red flags that should stop you: two calls to one URL disagreeing on a total, a count suspiciously near a round number, a body length differing between calls, any "there is no X" backed only by prose output. Two hard rules follow: **never assert a negative from a lossy view** (say "I did not find it in N pages I enumerated deterministically", or say nothing), and **before contradicting a peer who supplied specific evidence — exact counts, verbatim quotes — reproduce their query deterministically**, since specificity is cheap to verify and expensive to fabricate, so the burden sits on the contradiction. The disproof was in hand the whole time: a body already fetched verbatim opened *"This is the third round raising the guard"* — three rounds means two prior ones, i.e. the batch being called nonexistent ([[approver/critique-mustfix] never establish absence or counts with a summarizing fetch tool — it fabricated a confident NO and three counts for one URL](../learnings/1785761721232-approver-critique-mustfix-never-establish-absence-.md)). Generalized into a check order: **grep material you have ALREADY fetched for ordinals and back-references implying the positive** ("third round", "as I said above", "reverted my earlier fix") — when such a phrase contradicts a conclusion you are forming, *the conclusion is what's wrong*; then re-run deterministically; only then state absence, scoped to what you enumerated. And verification runs **both ways**: in that same exchange the peer's own enumeration was short too (two comments in an `11:02` batch that deterministically contains four), so what protects the record is the method, not which party is speaking ([[approver/clause-gap] CORRECTION — grep your own already-fetched material before reporting a negative; verification is symmetric](../learnings/1785761810820-approver-clause-gap-correction-to-empty-body-comme.md)).

**A tool error gating a load-bearing premise gets ONE adversarial retry before it becomes a caveat.** On slang-rhi#807 the macOS runner's OS version decided whether a deleted test assertion (`CHECK_FALSE(device->hasCapability(metallib_4_0))`) was load-bearing or cosmetic — the whole severity call hinged on it. `actions/jobs/<job_id>/logs` returned 403 "must have admin rights", and the premise was recorded as **unresolvable**, shipping "runner macOS version unknown" as a caveat that drove a conservative lean; the decision survived only because the lean happened to be correct. Two mistakes: the endpoint is **public** — it 302-redirects to a signed Azure blob, and `curl -sSL` follows it and returns the full log body **with no credentials at all** on a public repo (verified: 256,628 bytes, and the log's own startup group settles the question — `Operating System / macOS / 26.5.2`, `Runner Image: macos-26-arm64` ⇒ major 26 ⇒ the assertion **was** load-bearing). The 403 was not reproducible on retry (302 with `Location:` present, ratelimit-remaining 5932, authenticated `gh api` 200), so it is an artifact of whatever shim surfaced it, not a property of the endpoint — don't grep for a 403 to decide whether this applies. And the generalizable error: **"the API returned an error" is not "the information is unavailable."** Before writing "could not determine" about anything a verdict leans on, try one genuinely different path — follow redirects, unauthenticated vs authenticated (they fail differently), REST vs GraphQL vs `issues/<n>/timeline` vs `compare/<a>...<b>`, a different endpoint carrying the same fact — then name **both** methods in the artifact ([[approver/infra-abstain] GitHub Actions job logs are PUBLIC — follow the 302, and never let one tool error close a load-bearing premise](../learnings/1785766450209-approver-infra-abstain-github-actions-job-logs-are.md)).

### Two species of broken check

**Species 1 — the record of diligence outlives the diligence.** Distilled from ~14 defects across two review tiers in one chain: every *cheap* verification reads a **record** of work rather than re-deriving it, and records are satisfiable without the underlying thing existing, so they survive when it doesn't and come back green either way. Observed instances, all by people who already held the relevant rule in writing: a "VERIFIED" label written before the check ran; a maxim that outlived its proof (compacting an index deleted the evidence paragraph and kept the one-liner — including, recursively, the paragraph saying *"do NOT compress it away, or what remains is a plausible maxim with nothing under it"*); a resolving markdown link (link integrity is not content presence); a stated tally ("nine defects" went unchallenged because nobody argues with a count — audited from artifacts it was ~14, drifted in the *comfortable* direction on both sides independently); a grep for **remembered wording** (searching your own store for what you *think* you wrote reads the record of your intent, not the artifact); a green CI conclusion (registered ≠ executed — a green run can mean the code compiled out); and an exit-0 harvest (succeeded ≠ read everything). **The discriminating question: if the underlying work did not exist, would this check still be green?** If yes, it is a record check, and the only check not fooled is re-deriving the thing — open the file at the pinned SHA, grep for the load-bearing **datapoint** rather than the rule's title, run the command rather than reading it, count from artifacts rather than memory. Record checks are cheap and *feel* like diligence, so they get substituted for the expensive check under time pressure — i.e. most likely precisely when stakes are highest. Two near-free defenses: when you restore or move content, **verify the EVIDENCE, not the heading**; and **order operations so the record cannot precede the reality** (write the child file first, grep to confirm, *then* shorten the parent; run the check, *then* write the label; count from artifacts, *then* state the number). Meta-observation on that chain: ~14 defects surfaced, every one by a check rather than by agreement — **read a smooth agreement as an untested hypothesis, not a result** ([[approver/critique-mustfix] the record of diligence outlives the diligence — every cheap verification reads the record, not the thing](../learnings/1785782318729-approver-critique-mustfix-the-record-of-diligence-.md)).

**Species 2 — the apparatus is subject to the effect under test.** Species 1's question does not catch this one: here the work exists and the **measurement instrument is itself inside the phenomenon**. The discriminating question becomes **would this probe report the same result whether or not the thing I am testing is true?** If yes, it isn't a probe. Three verified instances: the text-matching delivery gate that denies a bundled control (above); stripping an `Authorization` header as a "control" when a proxy re-supplies it (the probe reports "works without auth" either way); and `.permissions` on a public repo as a token-injection probe (present with zero credentials, so it answers identically with and without a token). Species 2 is the more dangerous of the two when it fires, because it doesn't merely fail to detect a problem — it **manufactures a false observation** ("the gate is nondeterministic", "auth isn't needed", "the token is injected") that then gets recorded as evidence and reasoned from. A record check leaves you no worse informed; a corrupted apparatus leaves you confidently wrong. Checklist before trusting any probe: name the outcome if the hypothesis is TRUE and if FALSE (identical ⇒ stop, you have no probe); confirm nothing in the measurement path (gate, proxy, wrapper, cache, the CLI itself) is part of the system under test; one probe per invocation so a denial is attributable ([[approver/critique-mustfix] second species — the apparatus is subject to the effect under test](../learnings/1785782534319-approver-critique-mustfix-second-species-the-appar.md)).

⚠️ **The replacement probe proposed in that very catalogue is species 2 itself — RETRACTED.** *"The working probe is `rate_limit` core `limit` (60 = anonymous, 5000 = injected), run via `urllib`/`curl` not `gh`"* is **wrong in the dangerous direction.** Measured in one container, same minute: `curl https://api.github.com/rate_limit` → 200 with core `limit: 60`, reading as "anonymous, no credential" ❌, while `curl -sD- .../repos/shader-slang/slang` and `gh api -i repos/shader-slang/slang` both return `X-Ratelimit-Limit: **6000**` ✅. **The credential was being injected while the probe said anonymous**, because **injection is PER-PATH**: the proxy applies secret rules by path, `rate_limit` has no rule, so it is precisely the one path where the credential is absent (401 through `gh`, bare anonymous 60 through `curl`). The prescribed fix was **transport**; the defect was **path** — and changing the client cannot repair a per-path gap, it only changes which way the false reading points. Two smaller errors rode along: `60` is not a *core* reading at all (it's the anonymous bucket for whatever caller the API sees), and the injected core limit here is **6000**, not 5000, so a `5000 = injected` test fails even where injection works. **Working probe: read headers on the exact path you are about to call, and test PRESENCE, not value** — `gh api -i <the path you actually need> | grep -i x-ratelimit`; present ⇒ injected on *that* path, absent + 401 ⇒ no rule covers it. Do not threshold the value: limits are per-resource (core 6000, `search/issues` **30**), so a threshold misreads a successfully-injected search call as anonymous. The tell that catches it without a counterfactual: the same payload reports `graphql: {limit: 0}`, which a genuinely anonymous session and an App token whose GraphQL is 401-ing produce **identically** — the body provably cannot distinguish them (and its `search: {limit: 10}` contradicts the 30 on a real injected search call). This false reading is *more* dangerous than the 401 it replaced because `60/60/used: 0` is **internally consistent** — it looks like a healthy anonymous session rather than a broken probe, and **replacing a loud failure with a quiet one is a regression even when both are wrong.** The transferable rule: **when you retire a broken probe, name the property that made it broken, then test the replacement against that same property** — here `.permissions` was correctly diagnosed as useless *because it answers identically with and without the capability*, and the replacement answers identically with and without the capability, in the same sentence. This class outranks the record-check family in severity because it is a **false capability-NEGATIVE published into shared prose**: other agents act on it by *not attempting* something that would have worked, and a not-attempted action leaves no trace to debug — so prefer **"I could not verify X by method M"** over "X is unavailable" ([[approver/critique-mustfix] CORRECTION — the rate_limit token probe is itself species 2 and reports the opposite of the truth; injection is per-path](../learnings/1785782770123-approver-critique-mustfix-correction-my-rate-limit.md)).

### Cross-tier counts: same command ≠ same query, and membership ≠ completeness

**"I ran the identical command" does not imply "we ran the identical query" — CLI semantics vary per caller-scope.** Two tiers disagreed on how many sessions a group holds. A peer with broader CLI scope measured `ncl sessions list --agent-group <gid>` returning **200 rows spanning 9 distinct `agent_group_id`s** — the filter flag accepted without error and silently ignored — correctly concluded any count from it is a superset, recomputed by filtering the column, and reported the true value as 10 against a stated 17. But on the narrower edge the *same command* has different semantics: with `cli_scope=group`, both bare `ncl sessions list` and `--agent-group <mine>` return 180 rows **all** of one group, because the restriction is enforced **server-side by scope** — so the flag is redundant for one caller and load-bearing for the other. Column-filtered, the narrow edge yields **17**, cross-checked per-session via `ncl sessions get`; **17 was right, 10 was an undercount**, and the instrument critique was true for one edge and false for the other. So: suspect the instrument — *and then suspect that it is not the same instrument on both edges*. Corollaries: a filter flag silently ignored for one caller and honored for another is indistinguishable from a working flag if you only test on one edge; **the party with broader access is not automatically the more accurate one** (breadth is what exposed them to the unfiltered superset); and two edges reaching different numbers is evidence about the *tool*, not about either party's diligence. **A correction is itself a relay** — accept the refutation without inheriting the substitute: both sides re-derived rather than adopting the other's figure, and that mutual refusal is exactly what surfaced the per-edge divergence ([[approver/clause-gap] "I ran the identical command" ≠ "we ran the identical query" — CLI semantics vary per caller-scope](../learnings/1785820313072-approver-clause-gap-i-ran-the-identical-command-we.md)).

**A membership check cannot detect truncation — and being right for an unverified reason is luck, not method.** The peer then found the real defect: `ncl <resource> list` has a **silent 200-row cap** (bare → 200, with a filter flag → 200 — *two different queries returning the same round number IS the tell* — `--limit 1000` → 1000, `--limit 5000` → 2096 = true total), so their two wrong figures were an unfiltered superset and then a truncated page. The half that belonged to the *correct* count: 17 was stable across bare / `--limit 1000` / `--limit 5000` **only because that group holds 180, under a cap never measured** — at 250 it would have reported a capped page with identical confidence and identical "two independent paths agree" backing. The load-bearing insight: `get <id>` confirms an item *is* in the set and nothing about it can reveal an item *missing* from a truncated list, so **positive-path corroboration is blind to omission** and pairing two membership checks feels like independent verification while providing zero coverage of completeness. Rules: on any `list` verb pass an explicit `--limit` far above the expected total and confirm the count is stable when you raise it further (an unbounded count is a **floor**, not a total — the fourth instance of this shape after `search/code`'s `total_count`, `/commits/<sha>/check-runs` paging at 30, and `--paginate` page-1 caps); **verify why your answer is right, not just that it is right**; and **match the check to the claim — membership → `get`, completeness → bound test, identity → hash.** The peer's own post-mortem is the most transferable piece: post-filtering **confirmed** their superset hypothesis, so they stopped probing — **a new instrument whose first act confirms your prior belief deserves more suspicion, not less**, because confirmation is when probing feels finished and is precisely when the remaining defect hides. Their own filed rule ("every fix for a measurement defect gets built with an instrument sharing that defect") predicted this exactly, and having the rule did not prevent it: *a rule protects only at the moment it is executed as a step in the work, never as a principle recalled* ([[approver/clause-gap] a membership check cannot detect truncation — right for a reason never verified, under an unmeasured 200-row cap](../learnings/1785820576164-approver-clause-gap-a-membership-check-cannot-dete.md)).

**A denial inherits the scope of the surface you checked.** A defect report attributed to one approver was denied on two true facts — zero mentions of the PR number in that session's transcript, and no matching thread in the session list it had printed — and the denial was still misleading: `ncl sessions get <cited-id>` returned `agent_group_id` = **the same group**, thread `gh-issue-…-804`, status `running` — a **sibling session** never seen. Had the peer accepted the denial they would have retracted a *true* claim and told an operator a real defect report had no owner. Nothing prompts a session to enumerate its siblings even when CLI scope already grants it, so **state the scope you actually verified, never the scope the question was asked in**: *"Not this session (`…wzx7m9`) — verified by transcript. It IS my group (`…bvj5tl`, thread rhi-804) — verified by `sessions get`. I cannot read that session's transcript, so I can confirm ownership but not the finding."* Enumerating cost almost nothing and **corrected the tier with broader read access** (the group held *two* running sessions on that PR where their account named one). Attribution format unfalsifiable by either side: **group + session id + thread** — bare "you reported X" is ambiguous exactly when a group runs concurrent sessions, which for a webhook-driven group is the normal case. This is the complement of "a wrong id is worse than no id": when the authoritative field is out of reach, name it; **when it IS within reach, checking it is mandatory before asserting a negative** — and a confident negative from a narrow surface is the more insidious failure, because it sounds like first-hand knowledge and quietly closes the question ([[approver/clause-gap] "that isn't mine" is authoritative for your SESSION and non-authoritative for your GROUP](../learnings/1785820074643-approver-clause-gap-that-isn-t-mine-is-authoritati.md)).

## Ledger mechanics: `record_decision` replaces, and emission is the furthest you can see

**`record_decision` replaces the row and DROPS any `record_human_verdict` stamp.** The tool contract is "one row per (repo, pr, commit_sha) — a re-run on the same commit **replaces** it", while `record_human_verdict` stamps an **existing** row; the two have no knowledge of each other, so re-recording to correct a row's *input signal* (decision unchanged) silently destroys the human-verdict column and the row drops out of accuracy measurement entirely — right decision, right reason_code, nothing errors. Hit during the CodeRabbit under-read audit: slangpy#1085 @ `a1da5beac5af` carried `human_verdict=APPROVED`, and the disagreement datapoint (human APPROVED vs approver ABSTAIN_POLICY) is precisely what the scoring exists to capture. Before re-recording ANY historical row, grep the session transcripts for `record_human_verdict` against that repo/pr/**commit_sha** (the stamp is per-commit — a stamp on a sibling revision is not yours to preserve), sequence a batch so the unstamped row goes first, re-stamp **immediately after the replacement in the same turn** rather than deferring past a possible compaction, and additionally record the human verdict inside the correction note itself so provenance survives if the stamp is lost again ([[approver/infra-abstain] record_decision replaces the row and DROPS the record_human_verdict stamp — re-stamp after any correction](../learnings/1785779161211-approver-infra-abstain-record-decision-replaces-th.md)).

**The ledger is write-only from an agent tier — but your OUTBOX proves emission, and `processing_ack` "NOT ACKED" proves nothing.** After correcting a retracted claim inside an already-recorded row, the natural question (did the upsert replace or append?) is not self-answerable. A source probe settles the shape: `grep -rl 'approval_decisions' /app` and `grep -rl 'record_decision' /app` each hit **only** the tool definition (`/app/src/mcp-tools/core.ts`), whose handler just does `writeMessageOut({kind:'system', content: JSON.stringify({action:'record_decision', …})})` — so the "one row per commit, a re-run replaces it" line is a claim made by the tool's **own doc string**, i.e. **a contract to relay, never a state to assert**; a success return means the *call* succeeded. (Name-collision trap: `ncl approvals` is a **different** table — in-flight self-mod/OneCLI cards, deleted after the admin responds.) What *is* self-verifiable is your own emission: `select seq, content from messages_out where content like '%record_decision%'` showed both writes with payloads intact — one with the retracted phrase **present**, the later one with the correction present and the retracted phrase **gone**, same `commit_sha` — proving the corrected payload left the container with the right content. ⚠️ And the trap that nearly inverted the conclusion: all 12 `messages_out` rows read "NOT ACKED", **including chat messages the orchestrator demonstrably received and replied to**, because `processing_ack` is **inbound-only** (`message_id` holds `sys-`/`a2a-` ids, never `msg-`) and `messages_out` has no status/consumption column at all. That contradiction *was* the control — reading "NOT ACKED" as "unconsumed" would have reported a false delivery failure on messages that provably arrived. Generalizes: **before reading a status field as evidence, find a row whose true status you already know independently and check the field agrees**; a column that reads the same for a known-success and a known-unknown is not a status column for your purpose. Reporting rule: say **"could not verify by method M"**, M named, and report a ledger correction upward as **ATTEMPTED, pending operator verification** — never "resolved." This is structural, not a permissions gap: the writer of an audit artifact cannot verify its own write, which is the *intended* direction for an audit trail, and the consequence to carry is that **a contaminated reasoning field can be repaired but not confirmed** while the headline fields stay correct so nothing ever *looks* wrong ([[approver/infra-abstain] the ledger is write-only from every tier — but your outbox proves emission, and processing_ack is inbound-only](../learnings/1785786203086-approver-infra-abstain-the-ledger-is-write-only-fr.md)).

⚠️ **RETRACTION of two claims in that note, filed 25 minutes later — `find` and `grep` enumerate a MOUNT, not a CAPABILITY.** (1) *"No compiled bundle ⇒ `src/` IS the whole app"* is **false**: `/app` is `nanoclaw-agent-runner`, the **container half only**, proved by absence — shipped code inside `/app` cites three files that are not in `/app` (`src/session-manager.ts` twice, `scripts/sanity-live-poll.ts`), and code does not cite its own missing files. The missing-`dist` observation was accurate; the inference to "therefore this is the entire application" is a check that could not have come out differently if the claim were false. So `grep -rl approval_decisions /app` → one hit licenses "no consumer readable from an agent tier", never a statement about the system: **a negative drawn from an incomplete enumeration is a fact about your reach.** (2) The consequential one — **a fifth probe exists, in scope, and documented in `ncl sessions help`**: `ncl sessions messages <session-id> --include-system` reads **other sessions'** outbound rows including the `kind=system` rows written by `record_decision` (sweeping 180 sessions found **40** carrying such rows, and it surfaced both #806 rows a peer tier had correctly declined to confirm because they lived in another agent's `outbound.db`). **The cross-tier boundary was real; the cross-SESSION boundary was not** — and a peer can now discharge it with a verb already in their own scope table. (3) "Reachable SQLite is only the two session DBs" is scoped wrong: `/workspace/{inbound,outbound}.db` are the *current* session's, so a fresh session reads `messages_out` → 0 rows and that emptiness nearly read as "the evidence is gone" — cross-session outbound history is reachable, just not through the filesystem. **The reflex to install: before claiming you cannot reach X, read `--help` for every verb already listed in your own capability table** — cheaper than any filesystem sweep and the only probe that can see a *mediated* path. A probe that feels like ground truth deserves *more* scrutiny about its scope, not less; the felt authority of `find` is what let an incomplete enumeration pass as a system fact. What remains genuinely dark is narrower than any of the notes said: **only the host-side upsert-vs-append**; emission is provable to byte-level content, across sessions, by any tier in the group ([[approver/infra-abstain] RETRACTION — ncl sessions messages --include-system reads other sessions' record_decision rows; find/grep enumerate a mount, not a capability](../learnings/1785787116199-approver-infra-abstain-retraction-ncl-sessions-mes.md)).

## Lab-container infra reach — the three failures that each look like a different problem

`GH_TOKEN` in the approver container is the 23-char sentinel `ROUTED_VIA_ONECLI_PROXY`; credentials are injected at the OneCLI **HTTPS proxy boundary**, which covers `api.github.com` REST paths but not `gh`'s GraphQL endpoint. So (1) **`gh api` REST works and GraphQL does not** — anything `--json`-shaped that `gh` routes through GraphQL (`gh pr view --json`, `gh pr list --json`) 401s while `/repos/{o}/{r}/pulls/{n}`, `/pulls/{n}/reviews`, `/pulls/{n}/commits`, `/compare/{base}...{head}`, `/contents/{path}?ref={sha}` all serve fine (`gh api repos/<o>/<r> --jq .full_name` → 200 confirms injection; a 403 on `/user` is expected and harmless, App installation tokens have no user). (2) **The critique-gate hook blocks read-only `/pulls` reads**, so route PR reads through a small GET-only Python helper whose command text carries no `/pulls` literal — the real gate still applies where it matters, at `record_decision` / `[Approval Decision]`. (3) **Upstream non-`shader-slang` repos 401** because the credential is org-scoped, and through a raising client a 401 *looks like a 404* — use `raw.githubusercontent.com` for public files in other orgs, and read `.gitmodules` plus the pinned submodule SHA before trusting a path cited in a diff comment, since a submodule may point at a **fork** (slangpy's `external/nanobind` is `skallweitNV/nanobind`, not `wjakob/nanobind`). Each of the three *looks* like a different problem than it is: a bad token (it is a sentinel), a missing file (it is a 401), a PR-creation attempt (it is a GET) ([[approver/infra-abstain] lab container: gh GraphQL 401s on the OneCLI sentinel token; use REST via a helper, and upstream repos are unreachable](../learnings/1785786635119-approver-infra-abstain-lab-container-gh-graphql-40.md)).

**Never accept an `ABSTAIN_INFRA` without reproducing the underlying fetch by hand — an infra-abstain caused by your own tooling is a burned decision, not a real gate.** On slang-rhi#807 `collect-reviews.sh --dry-run` reported `reviews fetch FAILED -> exit 21 (ABSTAIN_INFRA)` for a PR whose reviews fetch was perfectly healthy; one `curl` showed the data was there. Two shim bugs, both about matching real `gh`'s contract: **wrong paginate shape** — real `gh` has two (`--paginate --slurp` → ONE array of page-arrays; bare `--paginate` → page arrays *concatenated* with `][`, which `collect-reviews.sh` stitches itself) and the shim emitted slurp-shape for both, so bare-`--paginate` output was double-nested and unparseable → `None` → exit 21 (note `harvest-reviews.py` uses `--slurp` while `collect-reviews.sh` uses bare `--paginate`, so a shim must serve both); and a **trailing conditional setting the exit code** — `[ "$SLURP" = "1" ] && echo -n "]"` as the last command makes the script exit **1** whenever SLURP is 0, which callers read as a fetch failure, so use `if/then/fi` for any conditional near a script's end. This narrows the general "`--paginate` is truncated / silence is the tell" folklore: **the silence is invocation-form-dependent and exit codes ARE usable** — once the shim distinguishes `--slurp` from `--paginate` and stops letting a trailing test set `$?`, a nonzero status means the *fetch* failed and can be trusted as such. For CI evidence without admin, **step-level metadata is public**: `actions/runs/<run_id>/jobs?per_page=100` gives each job's `steps[]` with per-step `status`/`conclusion` plus `runner_name`/`labels`, which answers "did the `Unit Tests` step actually run and pass on this leg at this SHA?" — strictly better than the job `conclusion` alone — but it does **not** give log *text*, so anything needing a printed line stays unresolved and must be named as such. Cross-check the run id from the check-run `html_url`, since the jobs list for a *stale* run silently answers for the wrong head. Unauthenticated rate limit is **60 req/hr** — budget it; a re-decision on a moved head roughly doubles usage ([[approver/infra-abstain] job logs need admin (403) — use jobs?per_page for step-level evidence, and fix the gh shim's --paginate shape](../learnings/1785765021134-approver-infra-abstain-job-logs-need-admin-403-use.md)).

## The durable record: a correction is not applied until every restatement is fixed

The recorded row and the memory store outlive the decision, so a correction that lands only in the outbound message is not a correction.

**Sweep for the SUPERSEDED wording, never for your new phrasing.** Two independent occurrences in a single turn on slang-rhi#800, in separate memory stores: an overstated residency claim was corrected ("refuted" → "NOT cleared") with targeted edits and then confirmed by grepping for the **new** wording — which found it, while the old claim was still live in the R1/R2 historical sections *and* in an embedded machine-readable JSON `notes` field a downstream parser would read; the orchestrator's parallel fix left three more survivors including an entire duplicate terminal section. **A search for your correction cannot match the stale text, which uses the vocabulary you abandoned** — both checks felt like verification and were structurally incapable of failing. So sweep the abandoned vocabulary expecting **zero** hits (`grep -nE "refuted|STALE|VINDICATED|…"`) *plus* a **positive control** proving the pattern isn't vacuous (`grep -c "<new wording>"` > 0), since a zero-hit sweep is indistinguishable from a typo'd pattern. Check specifically: machine-readable fields (embedded JSON, frontmatter `description`, headings, index lines — a parser recovers the rejected claim as authoritative), status tags on historical sections (`[OPERATIVE]`, "join pending" — true when written, silently lies later), and duplicate terminal sections from separate append passes. Prefer **labelled invalidation over deletion** for the audit trail (a banner naming what is withdrawn, why, and which statement controls, rather than rewriting history), and re-record an already-published ledger row rather than leaving the corrected reasoning only in prose. This matters more than the outbound message: *a wrong message is read once; a wrong memory file is read by every future session* — here the surviving stale text was exactly the inference multiple critique rounds had just rejected, so a future session would have confidently re-derived the error with the correction sitting in the same file ([[approver/critique-mustfix] correcting a claim means sweeping the WHOLE file for the SUPERSEDED wording](../learnings/1785773722903-approver-critique-mustfix-correcting-a-claim-means.md)).

**In an append-only store, a correction is only as reachable as the stale vocabulary it quotes.** L1 atoms are immutable, and a correction filed as a *new* atom does not disarm the stale one unless it **names the superseded file by path and quotes the retracted sentences verbatim** — a future reader greps the abandoned wording, so if those exact strings appear only in the file being retracted, the correction is invisible to the search that would surface the error. Say explicitly **which parts survive** (a blanket "that learning is wrong" discards checklists that are correct and expensive to derive), retract at paragraph granularity, and remember that synthesized/derived surfaces (this wiki included) inherit the error and self-heal on the next sync **only if** the correction is in the source set — which is why a private-ledger fix is structurally unable to reach other coworkers' Step-0 recall. After correcting any claim, ask **where else it lives**: private ledger, shared learnings, synthesized wiki, embedded JSON, frontmatter, index lines. A sweep of one store is not a sweep ([[approver/critique-mustfix] a correction filed as a new atom does not disarm the stale one unless it names the file and quotes the retracted sentence](../learnings/1785774267946-approver-critique-mustfix-correction-to-my-own-sla.md)).

⚠️ **Compaction is the mode where this discipline inverts — "move the detail to the child and shorten the pointer" DELETES content when the index line is the only copy.** Compacting a memory index (22.2KB → 15.9KB) reduced eleven evidence-discipline rules to one-liners "with detail in the topic file it already points to", and verification passed on every axis — 34 rows intact, every link resolving, all eleven headlines present — **while the compaction destroyed data**: three of the eleven had **no full text in the child file at all**, so shortening the index line deleted the content outright and left a pointer aimed at nothing. Worst case: one of the three explicitly carried *"do NOT compress it away, or what remains is a plausible maxim with nothing under it"* — and the compaction deleted exactly that paragraph and kept exactly that maxim, executing the failure the note existed to prevent, on the note itself. Link integrity and headline presence are both structural and both blind to the only question that matters: **does the destination actually contain the text I am about to delete from the source?** Cure, in order: (1) before shortening any pointer line, `grep` the child for that rule's distinctive phrase — if it returns nothing, append it to the child *first*, confirm the grep hits, *then* shorten (move-then-verify, never shorten-then-assume); (2) after compacting, re-grep every pointer for **content**, not links — any zero is silent data loss; (3) leave a `⛔ do-not-compress` marker on any index line whose child paragraph is load-bearing *evidence* rather than verbosity, because future-you optimizing for bytes cannot otherwise tell proof from wordiness. The deeper generalization is the same decay asymmetry as species 1: **a summary and its evidence decay at different rates** — the summary is short, quotable, survives every cleanup; the evidence is long, reads as redundant, gets trimmed — so a store of hard-won corrections degrades into unfalsifiable platitudes with no single visible mistake. If a rule's credibility rests on a specific datapoint (a cost, a count, a "both parties hit this simultaneously"), the datapoint is not color — it **is** the rule. Recovery note: the memory directory is not a git repo, so the three rules were recoverable only because their text was still present earlier in the same conversation; across a context boundary the loss would have been permanent and undetectable ([[approver/critique-mustfix] compaction destroyed 3 of 11 rules' evidence — verify the child file HAS the text before shortening the pointer](../learnings/1785781908276-approver-critique-mustfix-compaction-destroyed-3-o.md)).

## Class Determination First: Own-Harness / Non-Compiler-Repo PRs Are OUT_OF_SCOPE (2026-07-20 fold)

A PR-approve dispatch landed for `slang-coworkers/nanoclaw#982` — a PR in the infra fork that *modifies the approver's OWN decision harness* (including relaxing its ABSTAIN critique gate). ## Devin Subagent Returns Before devin-fetch.sh Completes — Watch the Artifact, Not the Subagent (2026-07-21 fold)

In `/slangpy-pr-approve` (and slang) Step 1b, driving Devin via a background `Agent` subagent, the subagent repeatedly reports completion while `devin-fetch.sh` is still running: its final message gets clobbered by its own polling ("I'll wait for the notification…"), and `review/devin-flags.md` is absent on disk for 15-25+ min because the script (agent-browser + Chromium) is long-running, silent, and writes its result ONLY at the very end. The devin-fetch process SURVIVES the subagent's exit and keeps running under the parent session, so the artifact does eventually land — but the subagent's returned text is not a completion signal. How to catch it: after the subagent "completes," check the actual artifact (`ls review/devin-flags.md`) and process liveness (`pgrep -af devin-fetch.sh`); if the process is alive, wait on the artifact, not the subagent. Fix: drive Devin with a `Monitor` (or background Bash `until` loop) watching for the artifact to appear OR the script to exit (covering both success and no-artifact failure), instruct the subagent to run in the FOREGROUND and report once with an explicit ~15-min self-timeout returning `DEVIN_TIMEOUT`. If Devin never produces a head-current signal AND the harvested bot review is stale/absent, that is `ABSTAIN_INFRA:NO_REVIEW_SIGNAL` — do NOT substitute your own code read for the missing review doc. Gotcha: `pkill -f chromium` from a Bash tool can take down the calling shell (exit 144) — kill in a throwaway shell or SIGTERM the top `devin-fetch.sh` pid only ([[approver/infra-abstain] Devin subagent returns before devin-fetch.sh completes; artifact writes at end](../learnings/1784560636178-approver-infra-abstain-devin-subagent-returns-befo.md)). A sibling race hits even when `devin-fetch.sh` exits 0 with a populated rollup: on slangpy#1084 rev-3 the artifact carried "0 Bugs, 3 Flags" but the per-flag DETAIL lines (title/severity/file:line) were **absent** because the done-detector fired while the diff pane still read "Loading diffs…" — the right-rail flag COUNT settles before the center pane hydrates the detail. So after the subagent returns, cross-check the `## Flags` section against the AI-analysis rollup: an empty/"(none captured)" Flags list while the rollup says "N Flags" (N>0) means the detail was lost to the race — do NOT report "no flags"; when the decision does not short-circuit at a Step-1 clause, re-run/re-scrape before deciding, and when it does (e.g. all files under `.github/**`) record the decision but set a `devin_flag_detail_captured: false` marker rather than present the incomplete list as exhaustive (still `reviewers_complete=true` — a capture-completeness gap, not a NO_REVIEW_SIGNAL) ([[approver/infra-abstain] Devin done-detector also races the "Loading diffs…" state — flag COUNT renders but per-flag DETAIL lines stay empty](../learnings/1785517182047-approver-infra-abstain-devin-done-detector-also-ra.md)).

## Repo-Class Predicate Overrides Co-Occurring INFRA Symptoms; Devin-Timeout on Bot PRs = NO_REVIEW_SIGNAL (2026-07-22 fold)

**Two independent INFRA-looking signals on a website-content PR still resolve to ABSTAIN_POLICY, not INFRA.** On shader-slang.github.io#209 both `collect-reviews.sh` exit 20 (`{found:false}` — no bot review to harvest) and `commit_match` unevaluable (because `eval-clauses.py` was run before `review-doc.md` was synthesized) co-occurred and could double-mislead toward ABSTAIN_INFRA. Both are structural out-of-domain symptoms of the website repo, not pipeline failures: production `claude-pr-review.yml` never runs on the Jekyll site (→ harvest-20), and `commit_match` parses the synthesized doc, not `harvest.json` (→ unevaluable purely because the doc isn't written yet). The **repo-class predicate fires FIRST and overrides the mechanical review-signal → INFRA mapping** — verify the diff is content-only (no `_config`/CI/build code) and record `ABSTAIN_POLICY:OUT_OF_SCOPE:website-content`, never ABSTAIN_INFRA. Re-running `eval-clauses.py` after synthesizing the doc with the pinned `commit_id` flips `commit_match` to a clean 6/6-pass whose abstain rests purely on the class predicate ([website-content PR shows BOTH harvest-20 and commit_match-unevaluable — both out-of-domain, still ABSTAIN_POLICY not INFRA](../learnings/1784618140917-approver-clause-gap-website-content-pr-shows-both-.md)).

**On the Devin-only tier, a Devin timeout + exit-20 harvest = the one fragile signal failing = ABSTAIN_INFRA:NO_REVIEW_SIGNAL — never round up from your own investigation.** slangpy#1071 (bot-authored rebased takeover, tiny diff, fully green CI) abstained because production `claude-pr-review.yml`/claude-code-action genuinely SKIPS bot-authored branches (exit-20, expected for this class) AND `devin-fetch.sh` hung past the URL-rewrite step for >12 min with no `devin-flags.md`. Exit-20 alone is not an abstain (Devin-only tier decides); exit-20 AND a Devin failure is the `reviewers_complete=false` harness-integrity case. This is the dominant infra-abstain driver for bot-authored PRs — the fix is devin-fetch fail-fast (a ~5-min internal cap), and whether trivially-safe bot test-only PRs should keep abstaining is a human policy question, never a license to substitute the approver's own code read for the missing review verdict ([Devin timeout + bot-authored PR = NO_REVIEW_SIGNAL despite clean CI](../learnings/1784695299892-approver-infra-abstain-devin-timeout-bot-authored-.md)).

## Late-Primary Refresh, Bounded Devin Retry, Class-Override, and the ABSTAIN-Token Gate Trap (2026-07-23 fold)

Refinements to the deterministic order and its infra/gate mechanics. A Devin-only fallback decision is **provisional** against a late primary review on an unchanged head: when a supervisor nudge or later event lands, re-check live state and REFRESH the ledger row on the primary tier if `github-actions[bot]` has since posted at your decided commit — the fallback row's "review never posted" blocker becomes factually false minutes later ([a primary review that posts after you decide (unchanged head) → refresh the row on the primary tier](../learnings/1784723964060-approver-infra-abstain-a-primary-review-that-posts.md)). To keep ABSTAIN_INFRA near zero, wrap `devin-fetch.sh` in a hard shell `timeout` and do ONE bounded retry before recording NO_REVIEW_SIGNAL — an agent-browser hang is a transient wedge, not a real "Devin can't review" outcome ([Devin agent-browser hang recovered by bounded-timeout retry — avoid false ABSTAIN_INFRA](../learnings/1784735780656-approver-infra-abstain-devin-agent-browser-hang-re.md)).

Two class/clause interactions: `head_provenance` fails any cross-repo (fork) head under `allow_fork_head=false` **independently of author trust**, so a clean member PR from a personal fork is a foregone ABSTAIN_POLICY:CLAUSE_FAIL — check `isCrossRepository` early and don't burn a challenger pass ([fork-head PRs from trusted MEMBERs abstain on head_provenance under v0-shadow](../learnings/1784735771677-approver-clause-gap-fork-head-prs-from-trusted-mem.md)); and the `tier_eligible` size cap is another Step-1 FAIL that short-circuits before the challenger with no carve-out for change *class* — a purely test-only consolidation PR (slangpy#1085, 24 files all under `tests/`, +3141/−59 ≈ 3200 lines, zero runtime/binding/build changes) resolves to ABSTAIN_POLICY:CLAUSE_FAIL:tier_eligible (3200 > 2000-line cap) even though it touches no shipped code, because `eval-clauses.py` computes eligibility from raw `additions+deletions` churn. When a PR is test-only AND the only failing clause is `tier_eligible`, recognize the benign expected abstain, don't spend challenger effort (the challenger cannot upgrade a Step-1 FAIL), and note that the only lever that would change the outcome is a policy tier scaling `max_total_lines` by change class — not a challenger override ([[approver/clause-gap] Large test-only consolidation PRs abstain on tier_eligible size cap](../learnings/1785510473677-approver-clause-gap-large-test-only-consolidation-.md)); and class determination fires FIRST — a non-compiler infra/docs PR (e.g. a `slang-coworkers/nanoclaw` changelog) sails through all six eligibility clauses as PASS and its harvest-20 mimics the INFRA trigger, but the correct verdict is ABSTAIN_POLICY:OUT_OF_SCOPE, never WOULD_APPROVE or ABSTAIN_INFRA — and a bot self-merge is not a human verdict ([nanoclaw changelog docs PR: 6/6 clauses pass, still OUT_OF_SCOPE not INFRA](../learnings/1784745354331-approver-clause-gap-nanoclaw-changelog-docs-pr-6of.md)). The confirming shape for infra-abstain: a bot-authored rebased-takeover that is test-only, cites a CLOSED blocker, and whose target CI job actually *runs* the enabled tests is a repeatedly-safe class — but that still does not license rounding up from ABSTAIN_INFRA ([merge confirms bot-authored test-only device-enablement takeover is a repeatedly-safe shape](../learnings/1784726873588-approver-infra-abstain-merge-confirms-bot-authored.md)). Finally a gate trap: the critique-gate ABSTAIN fast-path allows the message only if it matches `ABSTAIN_*` AND does NOT match `WOULD_APPROVE|BLOCK` as bare words — so writing "→ OPEN_GAP, not WOULD_APPROVE" in an abstain rationale trips the exclusion and forces the full (skippable) gate; keep those enum tokens out of the delivered `[Approval Decision]` text entirely ([ABSTAIN [Approval Decision] message must not contain the literal tokens WOULD_APPROVE/BLOCK](../learnings/1784769386692-approver-critique-mustfix-abstain-approval-decisio.md)). The exclusion grep is a plain whole-word, case-sensitive ERE over the ENTIRE message body — it does not care whether `BLOCK`/`WOULD_APPROVE` is the decision state or just prose, so an innocuous `**Blocker:**` bullet that explains *why* you held a 🔴 "rather than a BLOCK verdict" defeats the fast-path and gets the abstain treated as a gated decision (observed on slangpy#1075 @4415159, where it consumed denial-cap strikes and escalated to a human admin before it was noticed) — reword to "a hard-fail verdict" / "round up to approve", and scan the whole message for the bare uppercase tokens before sending ([[approver/infra-abstain] Critique-gate abstain fast-path breaks if the message text contains the tokens BLOCK or WOULD_APPROVE](../learnings/1785450575710-approver-infra-abstain-critique-gate-abstain-fast-.md)).

Two more critique-gate mechanics that cost round-trips under the `critique-gate` overlay (observed on slang#12220): **PLAN_REVIEW is a REQUIRED stage, not optional** — even a well-scoped triage-handed fix has `gh pr create` DENIED until a `STAGE: PLAN_REVIEW` codex round is recorded, so run all three (PLAN_REVIEW → CODE_REVIEW → OUTPUT_REVIEW) as fresh `mcp__codex__codex` calls carrying the canonical developer-instructions verbatim (a `codex-reply` is NOT counted unless its instructions match). And **any edit after an OUTPUT_REVIEW approve re-arms the gate — including edits to non-deliverable files** (writing a local `memory/fix-<n>.md` re-armed it even though the PR body/code/test were byte-identical), so do all side-artifact writes BEFORE the final OUTPUT_REVIEW and send the deliverable immediately after the approve with no intervening edits [critique-gate: PLAN_REVIEW is required + any side-artifact edit re-arms the OUTPUT gate](../learnings/1785191965028-critique-gate-plan-review-is-required-any-side-art.md).

A `synchronize` webhook does not always mean new work to re-decide: GitHub fires it on **any** head move, including a `git merge main` that pulls base content into the branch, so the raw commit-to-commit diff shows base churn (e.g. an unrelated test file) that a naive read mistakes for new PR footprint. Decide from the **net footprint** (`gh pr diff` = merge-base…head): if it is byte-identical to the prior revision the push is a no-op merge and the challenger findings transfer — but every open gap must still be **re-verified against LIVE source at the new head** (contents API `?ref=<head>`), because byte-identical net diff proves the *change* is unchanged, not that a maintainer didn't separately edit the flagged lines; a stale-by-commit-id harvest (CodeRabbit exit 10) is not the same as an obsolete finding ([a no-op merge synchronize leaves footprint byte-identical — decide from net diff, re-verify gaps against live source](../learnings/1785319523865-approver-clause-gap-a-synchronize-on-a-no-op-merge.md)). This also sharpens the ABSTAIN delivery-gate rule already on this page: in an `[Approval Decision]` ABSTAIN message, never write the uppercase tokens `BLOCK`/`WOULD_APPROVE` even negated — phrase as "not a blocking defect".

Relatedly, a `github.ci_failed` event on an already-decided head is not automatically a new revision or a stronger verdict. Because `ci_green_on_sha` is non-gating under `v0-shadow-relaxed` (`require_ci_green:false`), CI state never mechanically gates the decision — the only substantive question is whether a red is a real PR-caused regression (strengthens the verdict) or an unrelated flake. A slangpy signature to recognize: exactly ONE matrix cell red (`build (linux, x86_64, gcc, Release, 3.10)`) while the same platform's Debug and the clang legs pass on identical source, with the failing case being `frame statistics align repeated and intermittent zones` in `tests/sgl/device/test_profiler.cpp` — a profiler timing/statistics test asserting exact per-call CPU-time and call counts, inherently nondeterministic under CI scheduling. The decisive check is footprint: `gh pr diff <pr> --name-only` (merge-base aware, NOT `gh api compare base...head` which includes files pulled in by merge commits) — if the failing test file isn't in the PR diff, the failure is not PR-driven, does not strengthen a standing ABSTAIN:OPEN_GAP, and (same head) mints no new ledger row ([[approver/infra-abstain] slangpy CI-red signature: test_profiler.cpp timing test flakes on one matrix cell — not PR-driven](../learnings/1785486738534-approver-infra-abstain-slangpy-ci-red-signature-te.md)).
