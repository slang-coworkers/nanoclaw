## TL;DR

Working on Slang's numeric interface tower (`IFloat`/`IReal`/`IFloatingPoint`, `__BuiltinFloatingPointType`) has non-obvious constraints:

- **Transcendentals (pow/exp/log/sqrt/sin/cos/...) are FREE functions constrained to `__BuiltinFloatingPointType`, NOT interface requirements.** `__BuiltinFloatingPointType` is `[sealed]`, scalar-only (float/half/double); `vector<float,N>` deliberately does not conform. `IFloat` exposes only arithmetic + `__init(float)` + `toFloat`, no element access, no transcendentals. `T:IFloat` fails `pow` with E39999. (DeepWiki falsely claims `pow` has IFloat overloads — verify constraint targets at source.)
- **A free-function forwarder over a NEW interface (`[OverloadRank(-10)] pow<T:IReal>`) fails at full codegen with E99997 circularity** — the forwarder joins every `pow(...)` overload set, and a witness body that calls `pow` depends on its own witness. Fix: route the witness through an internal intrinsic wrapper (`__powImpl<T:__BuiltinFloatingPointType>`) that is NOT overloaded with an IReal forwarder.
- **That same forwarder ALSO breaks `[ForwardDerivativeOf]` with E31148** — derivative resolution can't disambiguate two generic `pow` overloads (specificity-blind + generic early-return skips OverloadRank). Even one forwarder for any derivative-registered name triggers it.
- **Relaxing a core-module generic struct's element bound to a marker interface + moving arithmetic to an `extension`** works because core-module bodies are type-checked eagerly against the declared constraint — every member using `+-*/%` or an arithmetic-bound helper MUST move to the extension.
- **`[sealed]` on a marker interface does NOT cover binding an associated type directly to the bare interface** (`typealias Motion = rt::IRayMotion`) — the seal only rejects *new conformances*, so a closed-set switch can still hit `Invalid`.
- Repro without a GPU: transcendental/IFloat/conformance shapes reproduce on CPU/front-end; use fresh Release slangc and verify against source, not DeepWiki.
- The `slangi` bytecode interpreter (`//TEST:INTERPRET`) currently ABORTS (`E99997` VM-bytecode-gen unimplemented) on the generic-comparison intrinsic path over vector/matrix `T:IComparable`; reproduce GPU-free with `//TEST:COMPARE_COMPUTE(... -cpu)` instead — don't conclude "can't repro without a GPU" just because slangi chokes.

## Where transcendentals and IFloat conformance actually live

A user wanting one generic `pow` for scalar and vector float hits three walls, all rooted in the constraint target [transcendental math is on __BuiltinFloatingPointType, not IFloat](../learnings/1786995212826-slang-transcendental-math-pow-exp-log-is-on-builti.md). `T:__BuiltinFloatingPointType` is `[sealed]` and implemented only by float/half/double SCALARS (`core.meta.slang:922`); `vector<float,N>` does not conform → E38029. `T:IFloat` fails `pow` with E39999 because every transcendental is declared `__generic<T:__BuiltinFloatingPointType>` plus explicit vector/matrix overloads — **0** transcendental decls are constrained to IFloat vs **268** `__BuiltinFloatingPointType` usages; `IFloat` exposes only add/sub/mul/div/mod/neg/scale/toFloat + `__init(float)`, no element access. Two framings that kill plausible-but-wrong theories: `vector<T,N>` *does* conform to IFloat (arithmetic works) and `T(2.4)` under IFloat does not floor (so the #12311 IArithmetic-flooring bug is irrelevant); and DeepWiki's `genericPow<T:IFloat>` example is FALSE (it is exactly the E39999 case). The doc comment on `__BuiltinFloatingPointType` saying "use IFloat instead" is true for arithmetic, misleading for transcendentals. Unblock today with two same-named overloads (scalar `T:__BuiltinFloatingPointType` + `vector<T,N>`).

The detailed source survey for the FP interface tower (#12591) records the load-bearing facts [FP interface tower — where IFloat conformance lives](../learnings/1787610707697-slang-fp-interface-tower-where-ifloat-conformance-.md): `IFloat` (`core.meta.slang:304`) refines `IArithmetic, IDifferentiable` (IComparable comes via IArithmetic); every requirement is `[Differentiable]`. `__BuiltinFloatingPointType` (`:922`) is `[sealed][builtin][TreatAsDifferentiable]`, refines `__BuiltinRealType, IFloat, IFloatingPointCoopElement`, and adds exactly one own requirement, `static This getPi()`. Scalars satisfy IFloat inline in the codegen struct body; vector/matrix conform to IFloat only when the element `T:__BuiltinFloatingPointType` (explicit `extension` at `:2394`/`:2459`). All ~74 transcendental names are free functions constrained to `__BuiltinFloatingPointType`, only `getPi()` is an actual requirement. Aliasing IFloat has a small blast radius (18 hits in `*.meta.slang`), but note a C++ codegen string array `arithmeticInterfaces[]={"IArithmetic","IFloat"}` generates operator overloads, so a typealias name must resolve in that generic-constraint position. The `${ C++ $}`/`$(...)` meta mechanism is processed by `slang-generate`; regen with `cmake -E touch` + `generate_core_module_headers` + `slangc`.

## Free forwarders over a new interface: two distinct failures

Adding a user-facing interface that re-exposes an existing free intrinsic (giving `T:IReal` a `pow`) via an interface-method-forwards-to-free-function witness plus a `[OverloadRank(-10)] pow<T:IReal>` free forwarder fails at full codegen with `E99997 circularity during codegen` — only under `-target cpp`/export, so probes that don't force codegen give a false green [free forwarder causes E99997 codegen circularity](../learnings/1787612598330-slang-free-forwarder-over-a-new-interface-causes-e.md). Root cause: the free `pow<T:IReal>` joins the overload set at *every* `pow(...)` call site, and deciding whether it applies requires the very witness table being generated; a witness body calling `pow(this,y)` depends on its own witness → cycle. Distinct method names and wrapper indirection do NOT help (both verified). Fix: the witness must reach the backend through a spelling not overloaded with an IReal forwarder — an internal intrinsic wrapper `__powImpl<T:__BuiltinFloatingPointType>` whose body is the `__target_switch` directly (not a call to free `pow`); the vector witness must be bound on `__BuiltinFloatingPointType` (not `T:IReal`, else E38100 missing equals/lessThan). Also: an interface requirement default body cannot delegate to a `__BuiltinFloatingPointType`-constrained impl (`This` is only the interface → E39999); conformance must be per-conformer where `This` is concrete.

The same forwarder additionally breaks the core-module build with `E31148 cannot resolve derivative function` at the `[ForwardDerivativeOf(pow)]`/`[BackwardDerivativeOf(pow)]` registrations [free forwarder breaks ForwardDerivativeOf E31148](../learnings/1787615081614-slang-free-function-forwarder-over-a-new-interface.md). The mechanism (traced in `slang-check-overload.cpp`): `compareOverloadCandidateSpecificity` ties two generics with the same specialized-param-count (does not consider constraint tightness — explicit TODO), and `CompareOverloadCandidates` early-returns 0 when either candidate is `Generic`/`UnspecializedGeneric`, *before* reaching overload-rank — so `[OverloadRank(-10)]` is ignored during derivative-of resolution (it still works for ordinary call sites, which is why functions compute correctly, only the registration breaks). Even one such forwarder for any derivative-registered name (pow/exp/sin/...) triggers it. This is the same specificity-blind / generic-early-return machinery covered on the generics/overload page (see `[ForwardDerivativeOf]` shaped-vs-catchall). Fix options: fix specificity to prefer the tighter-constrained generic (maintainer-owned, wide blast radius); register derivatives on-primal via `[ForwardDerivative]`; or expose the interface op only as a method (`x.pow(y)`), which builds clean.

## Conditional conformance via extension; the sealing gap

Relaxing a core-module generic struct's element bound while keeping arithmetic behavior — `struct CoopVec<T:__BuiltinArithmeticType,N> : IArray<T>, IArithmetic` → `struct CoopVec<T:ICoopElement,...> : IArray<T>` + `extension<T:__BuiltinArithmeticType,N> CoopVec<T,N> : IArithmetic {...}` — is a block-relocation task governed by eager checking [CoopVec ICoopElement conditional-conformance refactor](../learnings/1787354644407-coopvec-icoopelement-conditional-conformance-refac.md). Slang type-checks core-module generic method bodies eagerly against the declared constraint, so EVERY member whose body uses `+-*/%!=<>` on T (or calls a helper bound on `__BuiltinArithmeticType`) MUST move to the extension — leaving it in the ICoopElement struct fails the bootstrap compile. What STAYS: `__init`, `fill`, subscript/getCount (the IArray surface returning T via a GetElement intrinsic), and all store/load families (whose bodies only index or call bare-generic helpers). An extension's `IArithmetic` conformance can be satisfied by ctors on the original struct body (don't duplicate them). Technique: a ~500-line relocation done with a content-ASSERTED Python transform (assert every boundary line's exact text) — a boundary error costs a 20-min core-module build.

`[sealed]` on a structural marker interface has a residual gap a `[sealed]` + concrete-struct regression test does not cover [sealing a marker interface does not cover bare-interface binding](../learnings/1787671627319-sealing-a-stdlib-marker-interface-does-not-cover-b.md): `[sealed]` rejects a *new conformance* from another module (`struct Custom : rt::IEnabledRayMotion {}` → E30830), but an associated type can be bound directly to the bare marker interface (`typealias Motion = rt::IRayMotion`) — this declares no new conformance so the seal never fires, and because the checker treats an interface as satisfying its own subtype constraint, the bind type-checks and can still reach a closed-set mapping → `Invalid` → the same `SLANG_ASSERT`. So "sealed + a struct-conformer test passes" does NOT prove the ICE is gone; the fix likely also needs a diagnostic in the mapping function or a check rejecting bare-marker-interface binding. Process note carried in the atom: on a fast-moving DRAFT PR, don't cite a bare head SHA — cite "files byte-identical between SHA X and head Y" so the report stays true as the branch moves.

## slangi Aborts on Vector/Matrix IComparable — Use -cpu COMPARE_COMPUTE

When reproducing a bug that goes through the generic comparison operators over `T : IComparable` on VECTOR/MATRIX types (e.g. #12720, invalid scalar ordering), the `slangi` bytecode interpreter (`//TEST:INTERPRET`) currently ABORTS with `error[E99997] ... InternalError: unimplemented: VM bytecode gen for inst` — it cannot lower the vector comparison intrinsic path (confirmed on master @2ec76d46e). This does NOT mean the bug can't be reproduced without a GPU: the CPU compute path works — `//TEST:COMPARE_COMPUTE(filecheck-buffer=CHECK):-output-using-type -cpu` with an `RWStructuredBuffer<int> outputBuffer`, writing the `(int)` cast of each generic comparison result and CHECKing the values, compiles and runs through the LLVM/clang CPU backend for a real runtime confirmation, and is often MORE complete than the interpreter for intrinsic-heavy generic code. Example that confirmed #12720: `genLess(float2(0,1),float2(0,2))`→0 and `genLess(float2(0,2),float2(0,1))`→0 (both false but unequal = broken order), `genEq(float2x2(9,0,0,0),float2x2(9,7,7,7))`→1 (matrix equals compares [0][0] only). Lesson: don't conclude "can't repro locally without a GPU" just because `slangi` chokes ([slangi interpreter aborts on vector IComparable path — use -cpu COMPARE_COMPUTE to repro generic comparison bugs](../learnings/1787614127545-slangi-interpreter-aborts-on-vector-icomparable-pa.md)).
