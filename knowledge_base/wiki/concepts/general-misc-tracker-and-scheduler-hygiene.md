# Tracker and Scheduler Hygiene

## TL;DR

- A carried-forward tracker records each item's **disposition** (active / de-escalated-monitor / retired), reasoning and who/when, plus a "do NOT re-flag" section. A human's evidence-backed de-escalation **overrides** what a fresh run re-derives from raw facts.
- **A tracker regrows unless a size rule is written into its header and protocol concept:** one-line roster (file < ~12k), new facts merged into items in per-subtopic detail files, never a dated `## <date> update` section (an okf_synth DOSSIER). An every-run overwrite regrows the same way if it copies long-lived items forward; carried state belongs in an update-in-place tracker.
- **Measure a cap in the unit it names** (`wc -c` is bytes; an emoji roster runs ~5% over its char count). **Re-check a sweep script's repo routing** whenever it is copied forward, shift its dates newest-first (chained `sed` shifts double-shift), and write partial deletions as anchored replacements.
- **Re-read the tracker file before reporting status**; a report's prose summary drifts from the file.
- An open P0 / ship-stopper appears in **every** daily report until terminal, carried from a persistent watch-list with freshly verified state; 24h fetch windows drop long-open items and never refresh attributes, so re-read `assignees` before repeating "unowned".
- Retire an entry only when the defect is resolved or a human de-escalates it. **An issue closed with no merged fix is not retired:** follow the fix PR's `closingIssuesReferences` and re-key, or track the fix PR itself.
- Full re-checks and post-gap catch-ups **batch-check every roster AND parked number** (closed entries linger in parked files; window sweeps miss closures with no linked PR). State-sweep detail-only numbers before trimming live history to meet a cap.
- **One un-fired `pending` occurrence freezes a whole recurrence** (the next occurrence is minted only when the current one completes). Re-arm with `update_task({taskId, processAfter})`.
- Raw-learnings sync and wiki-synth are independent pipelines; one can push while the other is frozen. Compare counts.
- A recurring task's liveness is its **own `last_run`/`next_run`/`runs`**, not the pinned session's `last_active`. Verify a task-field edit by sha256 of the live field, not a self-reported diff.
- **Production logic is the task row's `script` field, not the checked-in source.** A deploy is done only when `ncl tasks get` shows the new code. Into a double-quoted bash string, escape only `$` and backtick (and `"`).
- **Enforce hard safety carve-outs (do-not-rerun / do-not-touch) in the deterministic script gate**, not memory/prompt. Default sweep tasks to `new_session:true`; keep cross-fire state in files.
- **Durable scheduling is `ncl tasks create`** (`--recurrence '<cron>'` or `--process-after <ISO8601>`, optional `--script` guard); `mcp__nanoclaw__schedule_task` is unwired, and a `Monitor`/`run_in_background` watch dies with its session.
- **A gated task's prompt is conditional on the payload**, never asserting the gate's outcome. Test the gate with a scratch copy that injects a synthetic match.
- **A 24h report window lags the run day by one:** the Monday run covers Sunday. Judge a "still 0 on Monday" default on the last weekday window (the Saturday run) and act on Monday.
- **A `wakeAgent:false` gate consumes a ONE-SHOT task (ack'd `completed`), it does not defer it.** Never gate a one-shot on "wait until X"; wake it with the status in `data`, or use a recurring gated task the agent cancels.
- Bi-weekly cadence: a weekly cron guard that skips off-weeks.
- **A "skip now, the next fire will catch it" branch must survive everything that runs between fires**; else poll more often, dedupe per key per day, treat "overdue" as a finding, never read a fetch failure as "in progress".
- Nudge/supervisor scanners **fail closed** (a failed state fetch → skip/escalate, never OPEN) and validate the must-nudge predicate against true disposition, not a proxy.
- An entry wedged behind a gate leaves every recency window: add a **bounded, payload-independent staleness scan** of the state store, called from the per-wake prompt, not a bigger cap.
- **After tightening a verdict gate, back-audit EVERY entry it governs.** Before calling a past green verdict wrong, look for an earlier live read; a check that vanished with no push is `ci-vanished`.

## Trackers: disposition, one-line rosters, and size rules

A carried-forward tracker (watch-list, status board) records each item's **disposition**, reasoning and who/when, not just the item; otherwise a fresh session re-derives state from raw facts and re-raises alarms a human already dispositioned. Every entry leads with a Disposition line (active / de-escalated-monitor / retired), de-escalated items sit in a "do NOT re-flag" section, and the header states that a human's evidence-backed de-escalation overrides the raw window ([trackers carry disposition + reasoning](../learnings/1782461882511-recurring-trackers-must-carry-disposition-reasonin.md)).

Folding an oversize tracker does not fix it unless the fold installs a size rule. The slang-maintainer `watch-list.md` crossed the 16k OVERSIZE line five times in three weeks (09-11 → 09-30) despite per-subtopic detail files: daily runs wrote new facts into roster lines, the detail files fell ~9 days behind, and every fold reset the clock. What held: move roster facts into detail files (autodiff / correctness / CUDA-perf / diagnostics-design / ecosystem-CI / retired log), cut the roster to one-liners, and write a "roster size discipline" rule into both the tracker header and its protocol concept (new facts to the detail file; whole tracker under ~12k). Before pruning, check GitHub state for items in a detail file but not the roster; they usually dropped out because they closed (#13092, #13158) ([enforce a one-line roster rule](../learnings/1790743007196-okf-tracker-regrowth-enforce-a-one-line-roster-rul.md)).

Two more regrowth shapes. **Appending:** `okf_synth.py` classes any concept with ≥8 H2 and ≥12k chars as DOSSIER, valid `type` frontmatter or not, and `watch-list/carried-open-items.md` got there via dated `## 2026-10-17 update` / `## New 10-16` sections; the fix split it by subtopic, merged each dated fact into its item, dropped retired entries, and wrote "merge, never append dated sections" into its protocol ([dated sections make a DOSSIER](../learnings/1792240698328-okf-synthesis-dated-date-update-sections-turn-a-tr.md)). **Carrying forward in an overwrite:** the Slang Maintainer's `memory/pending-questions.md`, rewritten every Discord sweep, reached 13.5 KB / 8 H2 because each sweep copied multi-week issue drafts forward; overwriting resets the file, not what the writer carries. Cross-sweep items moved to an in-place tracker (`discord-issue-drafts.md`) and the snapshot is capped at 6 H2 ([overwrite snapshot regrows](../learnings/1792413180035-okf-an-overwrite-each-sweep-snapshot-regrows-into-.md)).

Measure caps in their own unit: `wc -c` counts bytes, and the emoji-heavy roster runs ~5% over its char count (11,974 chars = 12,564 bytes on 10-21), so trim to the byte cap. `retired.md` had regrown dated `## Retired 2026-10-0x` H2s (11 against <8); fold them into `**MM-DD sweep:**` bullets under one H2 per subtopic. Splitting a detail file (carried-ecosystem-ci → + carried-ci-nightly) means repointing every `[[...]]` link and updating `watch-list/index.md` ([wc -c counts bytes](../learnings/1792574037781-watch-list-size-checks-wc-c-counts-bytes-emoji-ros.md)).

⚠️ A report's prose summary drifts from the tracker's actual state: **re-read the tracker file before reporting status** rather than trusting a carried-forward narrative ([prose summaries drift](../learnings/1784153749839-watch-list-prose-summaries-drift-from-file-state-r.md)).

## Carrying, re-checking and retiring watch-list entries

An open P0 / ship-stopper fix appears in **every** daily maintainer report until merged/closed. A PR opened over 24h ago and still in review falls outside the 24h merge/open fetch window and silently drops off, so keep a persistent watch-list, read it at the start of every report, and carry each still-open entry with **freshly verified live state**. Retire only on merge/close or explicit human de-escalation ([carry open ship-stoppers until merged](../learnings/1781598056955-daily-maintainer-report-must-carry-open-ship-stopp.md)).

The converse failure is an entry nobody re-checks. The 2026-10-05 full re-check found three long-closed items (#12198, #12227, #12311/#12312) still in the parked-monitors file `watch-list-monitor.md`, which daily runs never read; every full re-check parses the parked file as well as the roster and checks each number against the REST open lists. Counts from a range-expanding parser (`#a–#b`) are not comparable with an earlier run that did not expand ranges ([full re-checks include parked monitors](../learnings/1791188752973-watch-list-full-re-checks-must-include-parked-moni.md)). Likewise after a scheduler gap: the 10-15 catch-up rebuilt its view from the window's merges and missed six roster items closed during the gap (closures with no linked PR never show in a merge sweep) until the 10-16 run batch-checked all ~250 numbers. Run one batched GraphQL check (`issueOrPullRequest(number:N){state closedAt}` aliases) over every roster and parked number before writing the report ([gap catch-ups state-check every number](../learnings/1792139950368-gap-catch-up-runs-must-state-check-every-watch-lis.md)). Detail files under `memory/watch-list/` keep the same residue: the retired log records a closed item but its detail bullet stays (a 2026-11-02 sweep found 14, some closed since 08-12). The cheap sweep batch-queries every detail-only number (d4.py, `detail_only_states.json`), prints ~80 chars of context per CLOSED/MERGED hit, and skips context already saying ✅ / closed / merged / retired / WNF / superseded; the rest are stale. Run it before trimming live history: dropping them pays for new text under the ~12k cap and stops readers treating closed items as open ([closed-state sweep of detail files](../learnings/1793609627891-watch-list-detail-files-find-stale-bullets-with-a-.md)).

A roster line's *attributes* go stale like its state. The slang roster carried "🚨 10-01 (unowned) — #13351 …" from 10-05 on, although #13351, #13359, #13361, #13362, #13364 and #13365 were assigned between 10-01 and 10-07 (jhelferty-nv, jkwak-work, jvepsalainen-nv): each daily sweep sees only its 24h window's events. When a line asserts "unowned", re-read current `assignees` (and `timelineItems(itemTypes:[ASSIGNED_EVENT])` for when) on every run. A bulk human triage pass (jkwak-work + jhelferty-nv, 11-02 17:00–20:00Z: ~121 issues assigned, ~86–93 milestoned) voided every 10-29 → 11-01 batch line's "N unowned" count at once, so compute owner counts from live state per batch number range ([unowned labels go stale](../learnings/1793695956513-watch-list-unowned-labels-go-stale-silently-re-rea.md)).

Re-check scripts guess repos, and copies carry stale routing: `reports/tmp10xx/wl/ext.py` filed any unprefixed `#N < 1000` under slang-rhi, so "vscode-ext #79" became slang-rhi #79; drop such entries or add a `slang-vscode-extension` prefix rule ([ext.py misreads vscode-ext #N](../learnings/1792486262354-graphql-timelineitems-since-totalcount-ignores-sin.md)). Sibling `wl/d4.py` routed by a hardcoded slangpy tuple, silently querying newer slangpy numbers against slang; the 10-21 fix routes by range (n<1000 → slang-rhi, n<2000 → slangpy, else slang) ([d4.py misroutes new numbers](../learnings/1792572844379-watch-list-d4-py-hardcoded-slangpy-list-misroutes-.md)). The generator can also corrupt its proposed file: the 10-28 `gen.py` re-wrapped an edited span by walking back to the previous `- ` bullet (`rfind('\n- ')`); on a non-bullet paragraph that crossed the blank line and `## ` heading and textwrap joined them into one bullet, which `check_diffs.py` passed as "intended". The 10-29 `gen2.py` re-wraps only line-start `- ` bullets, bounded at the next `- `, `#` or blank line, and inserts pre-formatted text verbatim (`@@RAW@@`); after generating, `grep -n '[^ ]  ## ' proposed/**/*.md` must print nothing [gen.py re-wrap can swallow an H2](../learnings/1793263634269-watch-list-gen-py-re-wrap-can-swallow-an-h2-headin.md). Rolling the scripts one day forward (11-07) adds two traps. Chained `sed` date shifts double-shift (`s/11-04/11-05/; s/11-05/11-06/` moves an 11-04 date two days), so shift newest-first (W1→W1+1, then W0→W0+1, then prev→prev+1), assert every `W0 =` is the intended stamp, and check non-window dates such as a commit `since:` filter separately. And `gen2.py`'s `new=''` deletion path strips the trailing newline without re-wrapping: deleting the end of a bullet joins the next bullet onto its line, deleting the end of a section drops the blank line before the next `## `, and double spaces remain. Write a partial deletion as a replacement anchored on the surrounding text (`"…residency). #1265 still unowned."` → `"…residency)."`) so the re-wrap runs, then check every H2 still has a blank line before it; deleting a whole bullet with `new=''` is safe ([Watch-list sweep scripts: date-shift order and partial deletions](../learnings/1794041384457-watch-list-sweep-scripts-date-shift-order-and-part.md)).

The opposite mistake is retiring on a close that fixed nothing: "close" means the defect is resolved, not `state: closed`. On 2026-10-18 the external reporter closed shader-slang/slang#13737 (combined-sampler `Load`/`GetDimensions` emitting invalid HLSL/WGSL/Metal) as `COMPLETED` with no comment while the fix, bot draft #13741, was unmerged with 0 reviews. When an issue closes without a merged `Fixes #N` PR, read the fix PR's `closingIssuesReferences` and re-key to another open linked issue (here #10522), or keep tracking the fix PR ([reporter-closed issue is still live](../learnings/1792399830239-slang-a-reporter-closed-issue-with-an-unmerged-fix.md)).

## Recurrence-advance and pipeline hygiene

⛔ A recurring task mints its NEXT occurrence only when the current one COMPLETES, so one un-fired `pending` row halts the series: all daily tasks froze at 07-03/07-04 while the 12-hourly supervise task stayed current. Re-arm with `update_task({taskId, processAfter})`. The two `knowledge_base` pipelines are independent: the daily raw-learnings sync (`knowledge_base sync ...` commits) pushes `shared/learnings/` but runs no wiki synth, so `wiki/` can be frozen behind a stalled wiki-synth task; compare counts on nv-coworkers. When folding uncovered learnings, first split "genuinely new" from "already in a concept page" (`grep -l <stem> wiki/concepts/`), and resolve every truncated stem to its real file before scripting `[[...]]` links, or they dangle ([stalls freeze the whole recurrence](../learnings/1783327563514-learnings-wiki-coverage-checker-miscounts-bracket-.md)).

## Task liveness, deployed scripts, and safety carve-outs

Read a recurring task's liveness from the **task's own `last_run`/`next_run`/`runs`** (scheduler-owned, monotonic, advancing only on a real dispatch), not its pinned session's `last_active`. A task pinned to the bare session (`thread_id: null`) routes output to per-incident child threads (`gh-issue-…`), so `last_active` reads days-stale ("dead cron") while `runs` climbs on-grid. Check task fields, then run-log/output-file mtimes, then session `last_active` (a weak hint). Confirm a script/prompt change with a **sha256 of the applied field**, not a self-reported "byte-diff matches" ([liveness is its own last_run](../learnings/1789251566343-a-scheduled-task-s-liveness-is-its-own-last-run-no.md)).

Production runs the task row's `script` field, not its source: the CI-babysitter's logic lives in `sweep-script-v2.mjs`, but production runs the `script` of `task-1776715487702-ftr4s6` (deployed with `ncl tasks update --id … --script "$(cat …)"`), so [committing the `.mjs` changes nothing by itself](../learnings/1789777475607-classifier-mjs-edits-silently-drift-from-the-live-.md); it drifted twice (once misclassifying a live PR for a day). A deploy is done only when `ncl tasks get --id <task>` shows the new function names in the live field. The JS sits in a double-quoted bash string (`node --input-type=module -e "<JS>"`), where bash consumes `\` only before `$`, `` ` ``, `"` or `\`, so the [correct recipe escapes ONLY `$`→`\$` and `` ` ``→`` \` ``](../learnings/1789808037997-ncl-tasks-script-deploy-escaping-only-and-backtick.md) (plus `"`→`\"`); doubling backslashes corrupts JS escapes like `\n`/`\d+`. Test with a real bash script file containing `printf '%s' "<escaped>"`, byte-diffed against the source (`X="$(cat file)"` is a false negative: substitution never reprocesses backslashes). Drift now self-detects: `stamp-hash.mjs` bakes `DEPLOYED_SOURCE_HASH` at deploy and `checkDeploymentDrift()` re-hashes the on-disk `.mjs` each fire, surfacing `data.driftCheck: {status:"ok"|"drift"|"unknown"}` plus gate 0e to self-remediate on `"drift"` ([driftCheck + gate 0e](../learnings/1789778044849-deployment-drift-is-now-self-detecting-for-the-ci-.md)).

A long-running sweep can act on **stale context**, so a carve-out (do-not-rerun / do-not-touch signature) in memory or the prompt silently fails to bind: memory reloads only at session start / compaction, and a `new_session:false` task never re-reads a carve-out written after its last compaction. Enforce every hard carve-out in the **deterministic pre-processing script gate**: a machine-readable exclusion file (job + test signature + tracked issue#) read every fire and filtered before any LLM classification, tied to the tracked regression's lifecycle (add when filed, remove when closed). Default cron/sweep tasks to `new_session:true` and keep cross-fire state in files ([carve-outs in the script gate](../learnings/1789248262100-enforce-scheduled-sweep-safety-carve-outs-in-the-d.md)).

## Durable scheduling and gate semantics

`mcp__nanoclaw__schedule_task` returns "No such tool available" in slang-fixer and is absent from the orchestrator's toolset, although base-nanoclaw and CLAUDE.md reference it. The working route is `ncl tasks` (`list, get, create, append-log, update, cancel, run, pause, resume, delete`, under group `cli_scope`): `create` takes `--prompt` (required), `--recurrence '<cron>'` or `--process-after <ISO8601>`, and an optional `--script` guard printing `{"wakeAgent":true|false,"data":{…}}` so cheap polls stay silent. These run from the group's system session and survive restarts; a `Monitor` / `run_in_background` watch dies with its session, so it suits only a current-session watch (e.g. 1–2h) ([schedule_task unwired, `ncl tasks create` works](../learnings/1789682983550-durable-scheduling-mcp-schedule-task-is-unwired-bu.md)).

A guarded task's prompt is static text delivered every fire, so "the gate returned wakeAgent=true, i.e. it found X" reads as true on every tick and misleads a parent reading task rows. Write it as a condition on the payload ("act only if `scriptOutput.data.matches` is non-empty, otherwise do nothing"), and verify the gate with a scratch copy injecting one synthetic match: it should wake once, dedup on the next tick, and touch no real state. Weekend merge-queue gaps freeze per-job denominators, so quote an expected date, not a tick count, for a threshold gate ([prompts must not assert the gate outcome](../learnings/1791148386903-scheduled-task-prompts-must-not-assert-the-gate-ou.md)).

Weekends also decide pre-recorded report defaults. The maintainer daily report covers the 24h ending 08:10Z on the run day, so the **Monday run covers Sunday** (Saturday covers Friday). A default like "if merge throughput is 0/5 again on the Mon 10-26 run, make one ask to the rotation primary" would be decided by a weekend window, where 0/5 says nothing. Judge such a condition on the last weekday window (the Saturday run) and record "condition met" there; weekend runs carry the line silently and the action executes on Monday (applied 2026-10-24) ([Monday's window is Sunday](../learnings/1792830645446-pre-recorded-if-still-0-on-monday-defaults-monday-.md)).

**A `wakeAgent:false` gate consumes a one-shot task; it does not defer it.** In the agent-runner, `applyPreTaskScripts` → `markScriptSkipped` writes `processing_ack.status = 'completed'` for a deliberate skip (`sqliteMarkScriptSkipped` in `container/agent-runner/src/mailbox/sqlite/operations.ts`); only `script-skip:error` re-arms. A recurring series resumes next tick, but a one-shot (`--process-after`, no `--recurrence`) is gone, with nothing going red. `rerun-13378-ci-after-gh-9912` (2026-10-05) was gated on githubstatus Actions == `operational` during a `major_outage`, which would have silently ended the #13378 rerun chain. Either always print `wakeAgent:true` with the status in `data` and let the agent defer (the fix applied), or use a recurring gated task the agent cancels after acting. Gate on whether work is progressing: githubstatus stayed `degraded_performance` after runners were already clearing queued jobs ([one-shot consumed by wakeAgent=false](../learnings/1791236533158-a-one-shot-task-gated-by-a-wakeagent-false-script-.md)).

Express every-other-week recurrence with a cron guard that fires weekly but **skips the off-weeks** ([bi-weekly via cron guard](../learnings/1781574732054-bi-weekly-every-other-week-scheduling-via-cron-gua.md)).

**"Skip now, catch later" branches must survive what runs between fires.** The once-daily 01:30Z release-CI checker returned `wakeAgent:false` for an in-flight pinned run and relied on a next-day `stale_pin` branch, but the 00:00Z trigger overwrote the pin first, so the branch never fired: the 2026-10-09..12 release nightlies all failed (finishing 01:34–02:01Z) and none was reported for four nights. Lateness and failure shared a cause (a cold LLVM build after a cache miss, ~94 extra minutes), so the hole hit exactly the runs most likely to be red. Before shipping a deferred branch, list what runs before the next fire; anything mutating the state it reads makes it unreachable. The fix polls hourly (01:30–23:30Z), dedupes each wake once per day per key with marker files, treats "overdue" as a finding, adds a last-fire-before-overwrite wake, and never lets a fetch failure look like "in progress" ([skip-now-catch-later must survive](../learnings/1791855993192-skip-now-catch-later-guard-branches-must-survive-w.md)).

## Nudge scanners and sweep work-sets

⛔ A nudge/supervisor scanner's work-set **fails closed**: treating a fetch error as "still open" re-nudges closed or archived chains, so a failed state read means "skip / escalate", never "assume live" ([failed fetch defaulting to OPEN](../learnings/1786150583873-a-failed-fetch-defaulting-to-open-resurrects-archi.md)). The counting counterpart: `scan.py` read an absent comment body as automation activity and inflated the must-nudge set to **146 vs 21**; validate the predicate against true disposition before dispatching ([scan.py inflated must_nudge](../learnings/1786149497107-scan-py-absent-body-read-as-automation-inflated-mu.md)).

A sweep's payload usually comes from recency windows: a top-N freshness floor, an activity window keyed on completed check-runs, and a capped full-scan tail. An entry stuck behind a manual-approval gate (a PR in `WAITING`/`PENDING`) never completes a check-run, so once it ages out of the floor and its frozen `updatedAt` sinks below the tail cap it silently drops out of **every** surface (PR #13071 went 7 days untouched while siblings reconfirmed every ~2h). A bigger cap chases a growing non-green population. Add a payload-**independent**, bounded scan over the tracker/state store that surfaces entries past a staleness threshold (e.g. top-8 most stale, so a backlog drains over several runs), called from the prompt/config delivered fresh every wake (not a static instructions file that reloads only on restart, nor a data-fetch script that should not touch the state file); this helper sat uncalled for days ([entries age out of every wake payload](../learnings/1790195655945-ci-babysitter-tracker-entries-silently-age-out-of-.md)).

## Verdict-gate back-audits

When the gate was tightened to require `check-ci=SUCCESS` for `resolved`, the first audit covered 30 entries and missed 6 open fork PRs whose heads never ran CI (0 check-runs, or only `action_required` / `pull_request_target` runs). The complete audit is cheap: loop over every `last_verdict=resolved` entry, drop MERGED/CLOSED, and call `check_ci_state(<live headRefOid>)` on the rest (~50 probes) ([back-audit the whole tracker](../learnings/1791807134236-back-audit-the-whole-tracker-after-tightening-a-ve.md)).

**Correction (supersedes that audit's #13451 finding).** The audit flagged #13451 ("payload checkCi=success", head with 0 check-runs) as unsupported. Wrong: the orchestrator had read 69 contexts with check-ci SUCCESS live; later the head had 0 check-runs and 0 workflow runs with unchanged `updatedAt`, so the runs were removed. Before calling a past green verdict a misclassification, look for an earlier live read of the same head. A head that lost check-ci with no push is `ci-vanished` (in `sweeplib.LABELS`), not `no-ci-never-ran`: never-ran needs a maintainer to trigger CI, vanished needs someone to find who deleted the runs. The verdict stays `no-ci` either way ([check-ci vanished with no push](../learnings/1791807339120-correction-a-pr-whose-check-ci-disappears-with-no-.md)).
