# Tracker and Scheduler Hygiene

## TL;DR

- A carried-forward tracker records each item's **disposition** (active / de-escalated-monitor / retired), reasoning and who/when, plus a "do NOT re-flag" section. A human's evidence-backed de-escalation **overrides** what a fresh run re-derives from raw facts.
- **A tracker regrows unless a size rule is written into its header and protocol concept:** one-line roster (< ~12k), new facts merged into items in per-subtopic detail files, never a dated `## <date> update` section. An every-run overwrite regrows too if it copies long-lived items forward; carried state belongs in an update-in-place tracker.
- **Measure a cap in the unit it names** (`wc -c` is bytes; an emoji roster runs ~5% over its char count). Re-check a sweep script's repo routing when it is copied forward, shift its dates newest-first, and write partial deletions as anchored replacements.
- **Re-read the tracker file before reporting status**; a report's prose summary drifts from the file.
- An open P0 / ship-stopper appears in **every** daily report until terminal, carried from a persistent watch-list with freshly verified state; 24h windows drop long-open items and never refresh attributes (re-read `assignees` before repeating "unowned").
- Retire an entry only when the defect is resolved or a human de-escalates it. **An issue closed with no merged fix is not retired:** follow the fix PR's `closingIssuesReferences` and re-key, or track the fix PR.
- Full re-checks and post-gap catch-ups **batch-check every roster AND parked number**; state-sweep detail-only numbers before trimming to a cap.
- **One un-fired `pending` occurrence freezes a whole recurrence.** Re-arm with `update_task({taskId, processAfter})`. Raw-learnings sync and wiki-synth are independent pipelines; compare counts.
- A recurring task's liveness is its **own `last_run`/`next_run`/`runs`**, not the pinned session's `last_active`. Verify a task-field edit by sha256 of the live field.
- **Production logic is the task row's `script` field, not the checked-in source;** a deploy is done only when `ncl tasks get` shows the new code. In a double-quoted bash string escape only `$`, backtick and `"`.
- **Enforce hard safety carve-outs in the deterministic script gate**, not memory/prompt. Default sweep tasks to `new_session:true`; keep cross-fire state in files.
- **Durable scheduling is `ncl tasks create`** (`--recurrence` or `--process-after`, optional `--script` guard); `mcp__nanoclaw__schedule_task` is unwired, and a `Monitor`/`run_in_background` watch dies with its session.
- **A gated task's prompt is conditional on the payload**, never asserting the gate's outcome. Test the gate with a scratch copy that injects a synthetic match.
- **A 24h report window lags the run day by one:** judge a "still 0 on Monday" default on the Saturday run, act Monday. "Before Monday" for `pr_report.py` = before the Mon 05:00Z weekly task. Near-cap detail file: move one whole H2 out.
- **A `wakeAgent:false` gate consumes a ONE-SHOT task (ack'd `completed`).** Wake it with the status in `data`, or use a recurring gated task the agent cancels. Bi-weekly cadence: a weekly cron guard that skips off-weeks.
- **A "skip now, the next fire will catch it" branch must survive everything that runs between fires**; else poll more often, dedupe per key per day, treat "overdue" as a finding.
- Nudge/supervisor scanners **fail closed** (failed state fetch → skip/escalate) and validate the must-nudge predicate against true disposition.
- An entry wedged behind a gate leaves every recency window: add a **bounded, payload-independent staleness scan** called from the per-wake prompt, not a bigger cap.
- **After tightening a verdict gate, back-audit EVERY entry it governs.** Before calling a past green verdict wrong, look for an earlier live read; a check that vanished with no push is `ci-vanished`.

## Trackers: disposition, one-line rosters, and size rules

A carried-forward tracker (watch-list, status board) records each item's **disposition**, reasoning and who/when; otherwise a fresh session re-derives state from raw facts and re-raises alarms a human already dispositioned. Each entry leads with a Disposition line, de-escalated items sit in a "do NOT re-flag" section, and the header states that a human's evidence-backed de-escalation overrides the raw window ([trackers carry disposition + reasoning](../learnings/1782461882511-recurring-trackers-must-carry-disposition-reasonin.md)).

A fold does not fix an oversize tracker unless it installs a size rule. The slang-maintainer `watch-list.md` crossed the 16k OVERSIZE line five times in three weeks (09-11 → 09-30) despite detail files: daily runs wrote new facts into roster lines, the detail files fell ~9 days behind, and every fold reset the clock. What held: roster facts moved to detail files, one-line roster entries, and a "roster size discipline" rule (new facts to the detail file; tracker under ~12k) written into the tracker header and its protocol concept. Before pruning, check GitHub state for detail-only items; they usually closed (#13092, #13158) ([enforce a one-line roster rule](../learnings/1790743007196-okf-tracker-regrowth-enforce-a-one-line-roster-rul.md)).

Two more regrowth shapes. **Appending:** `okf_synth.py` classes any concept with ≥8 H2 and ≥12k chars as DOSSIER regardless of frontmatter; `watch-list/carried-open-items.md` got there via dated `## 2026-10-17 update` sections, and the fix split it by subtopic, merged each dated fact into its item, and wrote "merge, never append dated sections" into its protocol ([dated sections make a DOSSIER](../learnings/1792240698328-okf-synthesis-dated-date-update-sections-turn-a-tr.md)). **Carrying forward in an overwrite:** the Slang Maintainer's `memory/pending-questions.md`, rewritten every Discord sweep, reached 13.5 KB / 8 H2 because each sweep copied multi-week drafts forward; they moved to an in-place tracker (`discord-issue-drafts.md`) and the snapshot is capped at 6 H2 ([overwrite snapshot regrows](../learnings/1792413180035-okf-an-overwrite-each-sweep-snapshot-regrows-into-.md)).

Measure caps in their own unit: `wc -c` counts bytes, and the emoji-heavy roster runs ~5% over its char count (11,974 chars = 12,564 bytes on 10-21). Dated `## Retired 2026-10-0x` H2s fold into `**MM-DD sweep:**` bullets under one H2 per subtopic; splitting a detail file means repointing every `[[...]]` link and `watch-list/index.md` ([wc -c counts bytes](../learnings/1792574037781-watch-list-size-checks-wc-c-counts-bytes-emoji-ros.md)). When a detail file cannot absorb a new fact under 12k (carried-diagnostics-design, 11,878 B on 11-08), move one whole H2 to a new file rather than over-trimming. In gen2 that is a RANGE edit from that H2 to the next with `new=''` plus an `@@NEW@@` entry built from the *memory* file's section text (in-section rewrites go there, or their anchors vanish); add it to `INTENDED_REMOVED`, assert it in the new file, and update `watch-list/index.md`, the roster header link and kin pointers ([move a whole H2](../learnings/1794127463880-watch-list-sweep-splitting-a-near-cap-detail-file-.md)).

⚠️ A report's prose summary drifts from the tracker's actual state: **re-read the tracker file before reporting status** ([prose summaries drift](../learnings/1784153749839-watch-list-prose-summaries-drift-from-file-state-r.md)).

## Carrying, re-checking and retiring watch-list entries

An open P0 / ship-stopper fix appears in **every** daily maintainer report until merged/closed. A PR still in review after 24h falls outside the fetch window and silently drops off, so read a persistent watch-list at the start of every report and carry each open entry with **freshly verified live state**; retire only on merge/close or explicit human de-escalation ([carry open ship-stoppers until merged](../learnings/1781598056955-daily-maintainer-report-must-carry-open-ship-stopp.md)).

The converse failure is an entry nobody re-checks. Every full re-check checks the parked-monitors file `watch-list-monitor.md` (unread by daily runs) as well as the roster against the REST open lists; on 2026-10-05 three long-closed items (#12198, #12227, #12311/#12312) had lingered there. A range-expanding parser's (`#a–#b`) counts are not comparable with a non-expanding run's ([full re-checks include parked monitors](../learnings/1791188752973-watch-list-full-re-checks-must-include-parked-moni.md)). After a scheduler gap, the 10-15 catch-up rebuilt its view from merges and missed six roster items closed with no linked PR; run one batched GraphQL check (`issueOrPullRequest(number:N){state closedAt}` aliases) over every roster and parked number (~250) before writing the report ([gap catch-ups state-check every number](../learnings/1792139950368-gap-catch-up-runs-must-state-check-every-watch-lis.md)). Detail files keep the same residue: the retired log records a closed item while its detail bullet stays (14 on 2026-11-02, some closed since 08-12). The cheap sweep batch-queries every detail-only number (d4.py, `detail_only_states.json`) and prints ~80 chars of context per CLOSED/MERGED hit not already marked ✅ / closed / merged / retired / WNF / superseded. Run it before trimming live history; dropping stale bullets pays for new text under the ~12k cap ([closed-state sweep of detail files](../learnings/1793609627891-watch-list-detail-files-find-stale-bullets-with-a-.md)).

A roster line's *attributes* go stale like its state. The slang roster carried "🚨 10-01 (unowned) — #13351 …" from 10-05 on, although #13351 and five siblings were assigned by 10-07; each daily sweep sees only its 24h window. When a line asserts "unowned", re-read `assignees` (and `timelineItems(itemTypes:[ASSIGNED_EVENT])`) every run. A bulk triage pass (11-02, ~121 issues assigned in 3h) voided every 10-29 → 11-01 batch line's "N unowned" count; compute owner counts from live state per batch range ([unowned labels go stale](../learnings/1793695956513-watch-list-unowned-labels-go-stale-silently-re-rea.md)).

Re-check scripts guess repos, and copies carry stale routing: `wl/ext.py` filed any unprefixed `#N < 1000` under slang-rhi ("vscode-ext #79" → slang-rhi #79); add a `slang-vscode-extension` prefix rule ([ext.py misreads vscode-ext #N](../learnings/1792486262354-graphql-timelineitems-since-totalcount-ignores-sin.md)). `wl/d4.py` routed by a hardcoded slangpy tuple, querying newer slangpy numbers against slang; it now routes by range (n<1000 → slang-rhi, n<2000 → slangpy, else slang) ([d4.py misroutes new numbers](../learnings/1792572844379-watch-list-d4-py-hardcoded-slangpy-list-misroutes-.md)). The generator can corrupt its output: the 10-28 `gen.py` re-wrapped an edit back to the previous `- ` (`rfind('\n- ')`), which from a non-bullet paragraph crossed a `## ` heading and joined both into one bullet that `check_diffs.py` passed. `gen2.py` re-wraps only line-start `- ` bullets, bounded at the next `- `, `#` or blank line, and inserts pre-formatted text verbatim (`@@RAW@@`); afterwards `grep -n '[^ ]  ## ' proposed/**/*.md` must print nothing [gen.py re-wrap can swallow an H2](../learnings/1793263634269-watch-list-gen-py-re-wrap-can-swallow-an-h2-headin.md). Rolling the scripts a day forward: chained `sed` date shifts double-shift (`s/11-04/11-05/; s/11-05/11-06/`), so shift newest-first, assert every `W0 =` stamp, and check non-window dates (a commit `since:`) separately. `gen2.py`'s `new=''` strips the trailing newline without re-wrapping, joining the next bullet onto the line or dropping the blank line before a `## `; write a partial deletion as an anchored replacement (`"…residency). #1265 still unowned."` → `"…residency)."`) and check every H2 keeps its blank line. Deleting a whole bullet with `new=''` is safe ([Watch-list sweep scripts: date-shift order and partial deletions](../learnings/1794041384457-watch-list-sweep-scripts-date-shift-order-and-part.md)).

The opposite mistake is retiring on a close that fixed nothing: "close" means the defect is resolved, not `state: closed`. On 2026-10-18 the reporter closed shader-slang/slang#13737 (combined-sampler `Load`/`GetDimensions` emitting invalid HLSL/WGSL/Metal) as `COMPLETED` while the fix, bot draft #13741, was unmerged with 0 reviews. When an issue closes without a merged `Fixes #N` PR, read the fix PR's `closingIssuesReferences` and re-key to another open linked issue (here #10522), or keep tracking the fix PR ([reporter-closed issue is still live](../learnings/1792399830239-slang-a-reporter-closed-issue-with-an-unmerged-fix.md)).

## Recurrence-advance and pipeline hygiene

⛔ A recurring task mints its NEXT occurrence only when the current one COMPLETES, so one un-fired `pending` row halts the series (all daily tasks froze at 07-03/07-04 while the 12-hourly supervise task stayed current); re-arm with `update_task({taskId, processAfter})`. The daily raw-learnings sync pushes `shared/learnings/` but runs no wiki synth, so `wiki/` can sit frozen behind a stalled wiki-synth task; compare counts on nv-coworkers. When folding uncovered learnings, split "genuinely new" from "already in a concept" (`grep -l <stem> wiki/concepts/`) and resolve truncated stems to real files before scripting `[[...]]` links ([stalls freeze the whole recurrence](../learnings/1783327563514-learnings-wiki-coverage-checker-miscounts-bracket-.md)).

## Task liveness, deployed scripts, and safety carve-outs

Read a recurring task's liveness from the **task's own `last_run`/`next_run`/`runs`** (scheduler-owned, advancing only on real dispatch). A task pinned to the bare session (`thread_id: null`) routes output to per-incident child threads (`gh-issue-…`), so the session's `last_active` reads days-stale ("dead cron") while `runs` climbs on-grid; check task fields, then run-log/output mtimes, and treat `last_active` as a weak hint. Confirm a script/prompt change by **sha256 of the applied field**, not a self-reported diff ([liveness is its own last_run](../learnings/1789251566343-a-scheduled-task-s-liveness-is-its-own-last-run-no.md)).

Production runs the task row's `script` field: the CI-babysitter's logic lives in `sweep-script-v2.mjs`, but production runs the `script` of `task-1776715487702-ftr4s6` (deployed with `ncl tasks update --id … --script "$(cat …)"`), so [committing the `.mjs` changes nothing by itself](../learnings/1789777475607-classifier-mjs-edits-silently-drift-from-the-live-.md); it drifted twice. A deploy is done when `ncl tasks get --id <task>` shows the new function names. The JS sits in a double-quoted bash string (`node --input-type=module -e "<JS>"`), where bash consumes `\` only before `$`, `` ` ``, `"` or `\`, so the [correct recipe escapes ONLY `$`→`\$` and `` ` ``→`` \` ``](../learnings/1789808037997-ncl-tasks-script-deploy-escaping-only-and-backtick.md) (plus `"`→`\"`); doubling backslashes corrupts `\n`/`\d+`. Test via a bash file running `printf '%s' "<escaped>"`, byte-diffed against the source. Drift now self-detects: `stamp-hash.mjs` bakes `DEPLOYED_SOURCE_HASH` at deploy, `checkDeploymentDrift()` re-hashes the on-disk `.mjs` each fire into `data.driftCheck: {status:"ok"|"drift"|"unknown"}`, and gate 0e self-remediates on `"drift"` ([driftCheck + gate 0e](../learnings/1789778044849-deployment-drift-is-now-self-detecting-for-the-ci-.md)).

A carve-out (do-not-rerun / do-not-touch signature) in memory or the prompt silently fails to bind a sweep acting on **stale context**: memory reloads only at session start / compaction, so a `new_session:false` task never sees a carve-out written after its last compaction. Enforce hard carve-outs in the **deterministic script gate**: a machine-readable exclusion file (job + test signature + tracked issue#) filtered every fire before any LLM classification, added when the regression is filed and removed when it closes. Default cron/sweep tasks to `new_session:true` and keep cross-fire state in files ([carve-outs in the script gate](../learnings/1789248262100-enforce-scheduled-sweep-safety-carve-outs-in-the-d.md)).

## Durable scheduling and gate semantics

`mcp__nanoclaw__schedule_task` returns "No such tool available" in slang-fixer and the orchestrator, despite docs referencing it. The working route is `ncl tasks` (under group `cli_scope`): `create` takes `--prompt` (required), `--recurrence '<cron>'` or `--process-after <ISO8601>`, and an optional `--script` guard printing `{"wakeAgent":true|false,"data":{…}}`; these survive restarts, while a `Monitor` / `run_in_background` watch dies with its session and suits only a short current-session watch ([schedule_task unwired, `ncl tasks create` works](../learnings/1789682983550-durable-scheduling-mcp-schedule-task-is-unwired-bu.md)).

A guarded task's prompt is static text delivered every fire, so "the gate found X" reads as true on every tick and misleads a parent reading task rows. Write it as a condition on the payload ("act only if `scriptOutput.data.matches` is non-empty"); verify the gate with a scratch copy injecting a synthetic match: wake once, dedup next tick, touch no real state. Weekend merge-queue gaps freeze per-job denominators, so quote a threshold gate's expected date, not a tick count ([prompts must not assert the gate outcome](../learnings/1791148386903-scheduled-task-prompts-must-not-assert-the-gate-ou.md)).

Weekends also decide pre-recorded report defaults. The daily report covers the 24h ending 08:10Z on the run day, so the **Monday run covers Sunday**, and "if merge throughput is 0/5 again on the Mon 10-26 run, ask the rotation primary" would be decided by a window where 0/5 says nothing. Judge it on the Saturday run, carry the line silently over the weekend, and act Monday ([Monday's window is Sunday](../learnings/1792830645446-pre-recorded-if-still-0-on-monday-defaults-monday-.md)). "Fix `pr_report.py` before Monday" means before the weekly PR-report task (`0 5 * * 1`, Mon 05:00Z), so Sunday's run is the last that can flag it. A truly empty weekend window (11-08: 0 merges in all 3 repos) is proven with the must-return controls (cumulative merged counts, the `mentions` control) and the run spent paying down file sizes ([Monday deadline = the 05:00Z weekly task](../learnings/1794127463880-watch-list-sweep-splitting-a-near-cap-detail-file-.md)).

**A `wakeAgent:false` gate consumes a one-shot task; it does not defer it.** `applyPreTaskScripts` → `markScriptSkipped` (`sqliteMarkScriptSkipped`, `container/agent-runner/src/mailbox/sqlite/operations.ts`) acks a deliberate skip as `completed`; only `script-skip:error` re-arms. A recurring series resumes next tick; a one-shot is silently gone: `rerun-13378-ci-after-gh-9912` (2026-10-05), gated on githubstatus Actions == `operational` during a `major_outage`, would have ended the #13378 rerun chain. Always print `wakeAgent:true` with the status in `data` and let the agent defer (the fix applied), or use a recurring gated task the agent cancels. Gate on whether work progresses: githubstatus stayed `degraded_performance` after runners were clearing queued jobs ([one-shot consumed by wakeAgent=false](../learnings/1791236533158-a-one-shot-task-gated-by-a-wakeagent-false-script-.md)). Express every-other-week recurrence with a cron guard that fires weekly but **skips the off-weeks** ([bi-weekly via cron guard](../learnings/1781574732054-bi-weekly-every-other-week-scheduling-via-cron-gua.md)).

**"Skip now, catch later" branches must survive what runs between fires.** The once-daily 01:30Z release-CI checker returned `wakeAgent:false` for an in-flight pinned run and relied on a next-day `stale_pin` branch, but the 00:00Z trigger overwrote the pin first: the 2026-10-09..12 release nightlies all failed (finishing 01:34–02:01Z) and none was reported for four nights. Lateness and failure shared a cause (a cold LLVM build), so the hole hit the runs most likely to be red. List what runs before the next fire; anything mutating its state makes the branch unreachable. The fix polls hourly (01:30–23:30Z), dedupes once per day per key with marker files, treats "overdue" as a finding, adds a last-fire-before-overwrite wake, and never reads a fetch failure as "in progress" ([skip-now-catch-later must survive](../learnings/1791855993192-skip-now-catch-later-guard-branches-must-survive-w.md)).

## Nudge scanners and sweep work-sets

⛔ A nudge/supervisor scanner's work-set **fails closed**: treating a fetch error as "still open" re-nudges closed or archived chains, so a failed state read means "skip / escalate" ([failed fetch defaulting to OPEN](../learnings/1786150583873-a-failed-fetch-defaulting-to-open-resurrects-archi.md)). `scan.py` read an absent comment body as automation activity and inflated the must-nudge set to **146 vs 21**; validate the predicate against true disposition ([scan.py inflated must_nudge](../learnings/1786149497107-scan-py-absent-body-read-as-automation-inflated-mu.md)).

A sweep's payload comes from recency windows (a top-N freshness floor, an activity window keyed on completed check-runs, a capped full-scan tail). A PR stuck in `WAITING`/`PENDING` behind a manual-approval gate never completes a check-run, so once its frozen `updatedAt` sinks below the tail cap it drops out of **every** surface (PR #13071 went 7 days untouched). A bigger cap chases a growing non-green population. Add a payload-**independent**, bounded scan of the state store surfacing entries past a staleness threshold (e.g. top-8 most stale), called from the prompt/config delivered fresh every wake, not a static instructions file or the data-fetch script; this helper sat uncalled for days ([entries age out of every wake payload](../learnings/1790195655945-ci-babysitter-tracker-entries-silently-age-out-of-.md)).

## Verdict-gate back-audits

When the gate was tightened to require `check-ci=SUCCESS` for `resolved`, the first audit covered 30 entries and missed 6 open fork PRs whose heads never ran CI (0 check-runs, or only `action_required` runs). The complete audit is cheap: every `last_verdict=resolved` entry, minus MERGED/CLOSED, gets `check_ci_state(<live headRefOid>)` (~50 probes) ([back-audit the whole tracker](../learnings/1791807134236-back-audit-the-whole-tracker-after-tightening-a-ve.md)).

**Correction (supersedes that audit's #13451 finding).** The audit flagged #13451 (head with 0 check-runs) as an unsupported `resolved`. Wrong: the orchestrator had read 69 contexts with check-ci SUCCESS live; the runs were later removed (0 check-runs and 0 workflow runs, unchanged `updatedAt`). Before calling a past green verdict wrong, look for an earlier live read of the same head. A head that lost check-ci with no push is `ci-vanished` (in `sweeplib.LABELS`), not `no-ci-never-ran`: never-ran needs a maintainer to trigger CI, vanished needs someone to find who deleted the runs; the verdict stays `no-ci` ([check-ci vanished with no push](../learnings/1791807339120-correction-a-pr-whose-check-ci-disappears-with-no-.md)).
