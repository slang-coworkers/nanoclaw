# Supervisor Operations, Sweep Suppression, and Nudge Discipline

> This page owns nudge discipline, artifact checks, dispositions, staleness triggers, supervisor scale limits, and dashboard/CI-health reporting. Siblings: [Multi-Session Coordination, A2A Routing, and Session Handoff](agent-infra-multi-session-coordination.md) owns A2A edges, dedup, empty-ack loops and session handoff; [Supervisor CI-Cell Staleness and scan.py Over-Flag Root Causes](agent-supervisor-staleness-and-overflag.md) owns `scan.py` over-flag root causes and the draft→non-draft CI-cell trap; [Watchdog No-Op Controls, Blocker-Identity Monitoring, and Ledger Guards](agent-supervisor-watchdog-and-ledger-guards.md) owns watchdog no-op controls and ledger guards.

## TL;DR
- **A supervisor/cron/tooling nudge states CLAIMS, not facts.** Verify its premises against live GitHub before acting, always before an irreversible write. ~89% of artifact-less flags were false; a no-PR chain's artifact is often its bot triage comment.
- **"→ NUDGE" on a board is not a nudge** — dispatch it. Coworker-nudge ONLY when the owner session is silent ≥~60 min AND the chain has ZERO GitHub artifact (a closed-unmerged PR on an open issue does not count). Max 2 nudges, then escalate.
- **An unanswered inbound >60 min old on a `stopped` container is a stall** — wake it with a pinned `target_session_id` nudge. A webhook turn that errors `No conversation found` is never redelivered — sweep for it.
- **`scan.py`'s nudge cooldown has no no-response timeout**, so a once-nudged dead chain never escalates.
- **"No artifact" ≠ no artifact; recency ≠ presence.** None in a payload usually means *not populated*.
- **A human-owned disposition suppresses nudges only in the Orchestrator's own `supervisor-state.json`**, checked at the top of `classify()`. A last comment by `github-actions`/`coderabbitai`/`CLAassistant` is bot-last.
- **Silence is not health** — completion is a terminal artifact. A bot deliverable silent >48h is dropped-task 🔶 (verify the session is alive), NOT a maintainer nudge.
- **Staleness is ETA-relative:** builds 48h, reviews ~2× ETA (~1h). A review is complete only with a hash-matched verdict on *current* head.
- **A superseded bot PR closed-unmerged is often a WIN** — read the issue's close reason before re-escalating.
- **An approver torn down one CI-leg from recording loses its verdict** — verify CI and ask "did you record on `<sha>`?".
- **Verify a claimed A2A handoff fired** — ask the sender to confirm; a blind re-send double-dispatches.
- **At scale, one aggregate query beats a per-session fan-out** (`ncl cost-cap stopped --json` in step 1b). In-container skill patches are lost on every wake; the durable fix is a nanoclaw source change.
- **`awaiting_us` is ~90% false-positive at scale** — mostly draft-held PRs awaiting a human. Set dispositions; send ONE consolidated escalation.
- **Sweep coworkers stay silent on re-confirmation**; ping the parent only on a delta. Recurring tasks anchor on a canonical report and recompute every age from the source timestamp.
- **Dashboard channels render markdown** — every ref a `[label](url)`; inline the body AND attach the `.md`; Unicode emoji; URL-encode queries.
- **A merge-queue stall shows only as master HEAD not advancing.** Intermittent timeouts get rerun + requeue; a dominant evictor reaches a maintainer only after two consecutive sweeps.

## A Nudge States Claims, Not Facts

Before flagging a no-PR chain as "no GitHub artifact / owed PR", check for bot **issue comments** (triage 5-bullets), not just a PR or a `pr_session_mappings` row. `scan.py`'s `github_artifact` is null whenever there is no PR, but a stood-down or upstream-blocked chain's artifact is its triage comment on the issue ([supervisor artifact-check misses issue-comment artifacts for no-PR chains](../learnings/1783950814878-supervisor-artifact-check-misses-issue-comment-art.md)).

The blast radius: **105 chains flagged artifact-less, 93 of them false (~89%)**. `scan.py` derived the artifact URL from `chain["pr"]` and otherwise needed a `github_artifact_url` the feeder never populated, so every no-PR chain reported `github_artifact: None`; the fix (105→12) uses presence-not-recency and persisted 202 artifact URLs. On slang#10027 a nudge said *"this chain has no GitHub artifact of ours either… post the public 5-bullet"*; the recipient checked and found **six** bot comments, including the trace the maintainer had asked for, so the correct action was to **refuse the write and correct the premise**. A false flag pressures a coworker into spamming a maintainer's issue, and the `nv-slang-bot` App token gets **403** on issue-comment PATCH/DELETE, so a duplicate comment is permanent. The check is one call: `gh api repos/<o>/<r>/issues/<n>/comments --paginate --jq '.[] | "\(.created_at)  \(.user.login)  #\(.id)  \(.body|split("\n")[0][0:100])"'`. Discriminators that generalize: **"no artifact" ≠ "no artifact"**; **recency ≠ presence** (a chain silent 17 days can be fully documented); **a maintainer deferring their own assigned issue is ack-class input** with zero public output owed; and **irreversibility raises the verification bar** — when the requested action cannot be undone with your token, the burden of proof sits on the request, not on your refusal ([supervisor artifact-less flags were ~89% false — verify a nudge's premises before complying with a public write](../learnings/1785761398778-supervisor-artifact-less-flags-were-89-false-verif.md)).

**A superseded bot PR closed-unmerged is often a WIN.** On a raw GitHub read it looks identical to a dropped deliverable, and a watch list tracking it as "fix in flight" invites the wrong conclusion, "our fix died — re-escalate". Issue **#12070** (bwd_diff runtime induction-start crash, P1) had bot draft PR **#12072**; the issue closed via **PR #12299** by the human assignee (saipraveenb25), which superseded the draft, so the bot PR closing unmerged was the correct terminal state. Before re-escalating a closed-unmerged bot PR, read the linked issue's close reason and look for a superseding human PR ([a superseded bot PR closed-unmerged is often a win, not a dropped deliverable](../learnings/1785831626664-a-superseded-bot-pr-closed-unmerged-is-often-a-win.md)).

## When and How to Nudge

Putting "→ NUDGE" on the supervision board is not a nudge; the supervisor must dispatch a message. Coworker-nudge ONLY when a chain is stuck inside the pipeline: the assigned session has been silent ≥~60 min AND the chain has ZERO GitHub artifact. If ANY artifact exists, do not coworker-nudge; for an open PR with a stale review, post a ONE-TIME GitHub ping to the assignee, or a "standing down for maintainer to drive" comment if there is none. Find the stuck session with `ncl sessions list --agent-group <coworker-ag> --limit 2000 | grep 'gh-issue-...'` and dispatch into the EXISTING session via `send_message` with `target_session_id`. Track `nudgedAt`; max 2 nudges, then escalate. A scheduled/cron session has no default reply target, so a bare `send_message` fails with "multiple destinations" — always pass `to="orchestrator"`. Concurrent manual `/supervise-issues` fan-outs create several orchestrator sessions that each rewrite `supervisor-state.json`; live `gh` is the single source of truth, not state files ([CONSOLIDATED: /supervise-issues operations (nudge, deliver, format, concurrency)](../learnings/1780558152383-CONSOLIDATED-supervisor-operations.md)).

**An inbound that lands as the container stops can sit unprocessed for hours**, a stall whoever spoke last on GitHub. On #13206 an orchestrator note arrived two minutes after the fixer publicly promised a fresh draft PR, then sat for 16h (#13294 showed the same). The signature is `last_active` equal to the newest inbound's timestamp, `container_status=stopped`, and no outbound after it: the host did not re-wake the session. A pinned `send_message(to=<coworker>, thread_id=<canonical gh-issue key>, target_session_id=<that session>)` woke both within a minute, work intact. Detector: among fixer-owned sessions, flag an unanswered inbound older than 60 min on a stopped container. #13206 was also hidden because pull-universe resolved its PR to the closed #13214 and scan classified it `pr-open`, but a closed-unmerged PR on an OPEN issue is not the chain's artifact ([inbound landing as a container stops sits unprocessed; wake it with a pinned nudge](../learnings/1790642293992-inbound-that-lands-as-a-container-stops-can-sit-un.md)).

**A webhook inbound whose turn dies on `No conversation found with session ID: …` is lost, not redelivered.** jkwak-work's `@nv-slang-bot` mention on slang#10471 reached Main's chain session, whose next outbound was that error, and nothing re-delivered it. scan.py called the chain `awaiting_human` (bot-last plus a stale `maintainer-driving` disposition); only a live comment-recency check caught it. Host re-delivery of a stale continuation covers a woken coworker's first turn only. Each tick should scan sessions active since the last tick for an outbound starting `No conversation found` with no later real outbound, and re-route that inbound (~1 `ncl sessions messages` per recently-active session; 157 that tick) ([a webhook that dies on 'No conversation found' is not redelivered — sweep for it](../learnings/1791248489950-a-webhook-that-dies-on-no-conversation-found-is-no.md)).

**The two-nudge escalation never fires on a dead owner.** `scan.py`'s cooldown (`acted_and_quiet`) blocks a second nudge until an *external* event (a non-bot comment, a PR-state flip, a cost episode). That stops a nudge re-triggering itself but has no timeout for "we nudged and the owner never answered", so an `awaiting_us` chain with a dead owner stays in `nudge-cooldown` forever: in one tick 23 of 56 cooldown chains had no activity by us since `nudgedAt`. On #13114 the bot promised a draft PR, was nudged once, and sat 12 days until a maintainer closed the issue after tangent-vector's PR #13139 covered the work. The proposed skill fix is to escalate, or allow one re-nudge that counts toward the two, when `last_activity_by_us < nudgedAt` and more than ~48h have passed; separately, record a HUMAN_OWNED disposition for chains whose held/PARKED prose lacks the token and which only look stuck ([nudge cooldown has no no-response re-arm](../learnings/1790642300186-supervise-issues-nudge-cooldown-has-no-no-response.md)).

## Dispositions and the scan.py Gate

**Disposition suppression must apply on ALL ball branches.** `classify` consulted the human-owned disposition only on the `ball=="human"` path, so the `ball=="ours"`/`"none"` branches re-nudged every parked chain each tick. The fix hoists a single `human_owns_disposition(chain)` guard to the top of `classify()`, returning `awaiting_human` with `needs_nudge=False` before the ball dispatch, and widens the token set ([scan.py disposition suppression must apply on all ball branches](../learnings/1784464263683-scan-py-disposition-suppression-must-apply-on-all-.md)) — but deliberately not with `awaiting_human`/`pr_open` tokens, so a fresh substantive @bot ask still overrides a stale self-label ([scan.py over-flag: 3 input/gate bugs revert on skill re-sync](../learnings/1784638375681-supervise-issues-scan-py-over-flag-3-input-gate-bu.md)).

**The disposition must live in the ORCHESTRATOR's `/workspace/agent/memory/supervisor-state.json`.** `scan.py:513` rehydrates disposition as `chain.get("disposition") or prior.get("disposition")`, and live GitHub carries none, so it always falls back to the Orchestrator's entry; if that is absent, `we_owe_next_step` sees no `HUMAN_OWNED_DISPOSITION` token and returns True, a spurious re-wake (the #11970 blank-disposition failure). A coworker cannot write the Orchestrator's memory, so a triager's "persisted disposition to supervisor-state.json" that wrote its *own* workspace file is inert. Treat such a report as a *request*: the Orchestrator writes `disposition: advisory:maintainer-driving` (+ artifact URL) under key `gh-issue-<owner>/<repo>-<N>` into its own file, then verifies `we_owe_next_step → False` (#13070) ([maintainer-driving disposition must be persisted in the Orchestrator's supervisor-state, not a coworker's workspace](../learnings/1789416210923-maintainer-driving-disposition-must-be-persisted-i.md)).

**The input bugs revert on every skill re-sync** and are owed as durable upstream fixes. (1) Session-DB timestamps arrive naive, so `scan.py::parse_ts` crashes on an aware `max()`; force `tzinfo=utc` when `dt.tzinfo is None`. (2) `pull-universe.sh` knows only `nv-slang-bot` as a bot, so `github-actions`/`coderabbitai`/`CLAassistant`/`slangbot` comments read as "human spoke last"; correct `is_bot` on the comment objects (on tick 97 that took raw 15 needs_nudge to 5, and per-chain verification of the human-maintainer-owned rest took it to 0). (3) The disposition injection must OVERWRITE pull-universe's stale copy, not fill when absent — #12089's old non-parking `pr_open - ...` disposition blocked the gate until overwritten ([scan.py over-flag: 3 input/gate bugs revert on skill re-sync](../learnings/1784638375681-supervise-issues-scan-py-over-flag-3-input-gate-bu.md), [tick 97 — scan.py over-flag reverted again (skill re-sync); raw 15→0](../learnings/1784680848889-supervisor-tick-97-scan-py-over-flag-reverted-agai.md), [disposition suppression on all ball branches](../learnings/1784464263683-scan-py-disposition-suppression-must-apply-on-all-.md)). The bot-list defect persists: ~670 comments on open chains by these bots still counted as human, which raised the #13423 escalation ([No conversation found sweep](../learnings/1791248489950-a-webhook-that-dies-on-no-conversation-found-is-no.md)).

## Dropped Deliverables and ETA-Relative Staleness

**A dispatched task's silence is not evidence of health.** Distinguish two watch-list dispositions that look identical on GitHub. **Maintainer-gated:** a fix/verdict EXISTS and only a human ready-flip, merge or alignment reply remains → genuine 🟡, a real maintainer nudge. **Deliverable dropped:** the owning bot session never produced a PR/verdict → a chain-liveness problem, NEVER a maintainer nudge. Work that died on session teardown (losing the completion notification) looks like work calmly progressing. A daily report carried #11877 as "PR overdue → soft nudge to maintainer" and #12116 as "draft awaiting ready-flip"; both had been dropped on teardown with nothing produced, dark 5 days. Rule: any in-flight bot deliverable silent >48h (no PR, no verdict, `updated_at` frozen, no monitor ping) → flag 🔶 "verify not dropped — re-confirm the owning session is alive" and surface it to the parent to re-wake the owner; it returns to 🟡-held only once the session is confirmed alive ([Watch-list: blown-ETA silence on a dispatched bot deliverable = dropped-task signal, not "still holding"](../learnings/1784535643816-watch-list-blown-eta-silence-on-a-dispatched-bot-d.md)). Track every dispatched-work ETA and check it when it elapses: a materially blown ETA is a dropped-task signal, not a reason to keep holding ([Track dispatched-work ETAs; a blown ETA is a dropped-task signal, not a reason to keep holding](../learnings/1784154058484-track-dispatched-work-etas-a-blown-eta-is-a-droppe.md)).

**Verify a claimed A2A handoff actually fired.** When a coworker says "I sent X to Y" and Y is waiting, confirm the send left the sender's session before treating the chain as advanced; a stale critique gate, marker or auth can silently block a send while the sender believes it went. Ask the sender to *confirm* the dispatch fired rather than blind re-send, which double-dispatches ([Verify a claimed A2A handoff actually fired — a stale critique gate can silently block the send](../learnings/1784882173077-verify-a-claimed-a2a-handoff-actually-fired-a-stal.md)).

**A review needs an ETA-relative trigger, not the uniform 48h window.** A correctness/clarity review (~20–30 min ETA) silent past ~2× its ETA (~1h) with no `running` owning reviewer session is *stranded* → flag 🔶 immediately; 48h is right only for builds (ninja resumes incrementally) and owed answers. Also flag 🔶 when the PR head moved after dispatch or a returned verdict's reviewed-diff-hash ≠ current head. A 🔶 review means the correctness gate has NOT completed: re-dispatch foreground/in-turn (completion = a tool result, not a teardown-prone monitor), owned by the parent/reviewer, not a maintainer nudge ([review deliverables need an ETA-relative staleness trigger, not the 48h dropped-deliverable window](../learnings/1784622307704-review-deliverables-need-an-eta-relative-staleness.md)). A fresh bot draft PR with 0 comments looks the same whether its review is running or died, so a report must not default it to 🟡; the disposition follows whether a hash-matched verdict landed ([Daily-report: a fresh draft PR with 0 reviews is NOT proof the review is progressing — check for a landed verdict](../learnings/1784881773024-daily-report-a-fresh-draft-pr-with-0-reviews-is-no.md)).

**An approver torn down one CI-leg from recording loses its verdict with no ledger row** (twice on slang#12111). The approver gates `record_decision` on settled-head CI, so a restart or crash at that boundary looks like "still waiting on CI" and the staged decision evaporates. On any teardown signal near the record step, verify CI terminal state via `gh`, confirm the head has not moved, then ask "did you `record_decision` on `<sha>`? NO → record now, gate is clear." The approver's gate is correct; the fix is orchestrator reconciliation on resume ([approver teardown at near-terminal loses unrecorded verdict](../learnings/1784445113353-approver-teardown-at-near-terminal-loses-unrecorde.md)).

## supervise-issues at Scale

**Any step that is O(all historical sessions) silently outgrows the tick budget** — prefer a single aggregate query over a per-session fan-out whenever the consumer needs only the aggregate.

- **argv overflow at ~170+ chains.** The tick stalls and final assembly dies with `python3: Argument list too long` at `scripts/pull-universe.sh` (~line 242). The per-chain fetch completes; the overflow is passing all chains as argv to assembly. Pipe via stdin or a temp file instead ([supervise-issues pull-universe.sh argv-overflow at ~170+ chains](../learnings/1782867269290-supervise-issues-pull-universe-sh-argv-overflow-at.md)).
- **Step 1b cost-cap stamping.** It spawned `ncl cost-cap status --session <id>` (~1–1.7 s each) for **every** gh-issue session, before the open/closed filter, so at ~3,256–3,913 sessions that phase alone took 50–90 min and the board never posted. `scan.py` only branches on `cost_status == "stopped"` (`scan.py:290`), so one bulk `ncl cost-cap stopped --json` (~1.5 s) is byte-identical: stamp `stopped` iff the id is in that set, else `unknown`. Also: global `ncl sessions list` over-pulls chains from other agent groups (nanoclaw, slang-vscode-extension, slang-torch) and malformed thread keys, inflating `must_nudge` with unroutable rows; `reports/issue-chain-tracker.md` is append-only and unbounded (7.5 MB / 218 ticks) ([supervise-issues pull-universe 1b: replace 3256 per-session cost-cap spawns with one bulk call](../learnings/1789180980128-supervise-issues-pull-universe-1b-replace-3256-per.md)).
- **The in-container fix does not persist.** The bulk-`stopped` patch (backup `scripts/pull-universe.sh.bak.t223`; ~80 min → seconds) is lost on every wake because `/home/node/.claude/skills/supervise-issues/` is recomposed from the nanoclaw source, and a later tick timed out at 60 min on the same loop. The durable fix is a source change to nanoclaw `container/skills/supervise-issues/scripts/pull-universe.sh` step 1b (an operator/PR action); until then each tick patches a local copy (`tmp/sup/pu-fast.sh`). `ncl cost-cap stopped --json` has four top-level keys, so read `.stopped`; `ncl sessions list --json` rows live under `.data`. `pull-universe.sh` emits the *universe* payload `{now, sessions, chains, state}`, not the board: run `bash scripts/pull-universe.sh --state <state> | python3 scripts/scan.py > out.json`. Step 4b's per-session outbound reads are the next bottleneck (~1,500 sessions at ~0.35–0.5 host ncl calls/s): re-fetch only sessions whose `last_active` is later than the chain's prior `lastObservedActivity` (81 sessions, ~4 min) and floor the rest at the prior `lastActivityAt`, valid because scan.py reads `our_last_outbound` only for `last_activity_by_us`. Kill a stalled pull's python child by PID — `pkill -f pull-universe.sh` leaves it issuing `ncl` calls that starve later calls ([supervise-issues pull-universe.sh cost-cap stamping was O(all-sessions), ~80min — fixed to O(1)](../learnings/1789349178875-supervise-issues-pull-universe-sh-cost-cap-stampin.md)).

**`awaiting_us` is ~90% false-positive at scale.** Of ~40 coworkers that replied to `awaiting_us` nudges with live-verified state, ~90% were false positives: scan.py reads "our bot was the last actor + issue still open" as ball=ours, but the ball is usually with a human maintainer or the chain is terminal, so it fires a false-nudge storm every 12h. The real buckets: (1) **draft-held PRs (dominant)** — Slang CI's `wait-for-human-priority` gate marks a draft bot PR's jobs `skipping`, maintainers never see it in the review queue, and it ages 18–27 days; the only unblock is `gh pr ready`, which fixers treat as operator-gated, and the draft *is* the resumable artifact, so it awaits a human; (2) approved/green PRs awaiting merge; (3) closed-at-triage with an intentionally suppressed comment; (4) terminal (deleted issues → HTTP 410, closed-not-merged PRs, PRs not ours). Tooling fix: `classify()` treats bot-last as `awaiting_human` unless a fixer genuinely owns an artifact-less dark chain, maps 410 / GraphQL-unresolvable to terminal-archive, and recognizes `stood-down:closed-at-triage`. Operationally, skip 40 per-chain acks (echo noise): set human-owned dispositions (`advisory:maintainer-driving`, `stood-down:draft-held`) in `supervisor-state.json` and send ONE consolidated operator escalation with the draft→ready batch. A minority of nudges did wake real work (#12405, #12653, #12608, #12987, #12549) ([supervise-issues: awaiting_us is ~90% false-positive at scale — bot-last mislabeled, draft-held PRs the real bottleneck](../learnings/1789182038195-supervise-issues-awaiting-us-is-90-false-positive-.md)).

## Sweep Coworkers and Scheduled Tasks

Periodic-sweep and babysitter coworkers do not report to the parent when a sweep merely re-confirms known or already-escalated state; they stay silent and continue local work (trackers, durable logs). Ping the parent only on a delta: a NEW signature, a state change (fix merges, flake recurs/escalates, cap hit, merge-queue eviction), or anything actionable on the parent's side. This extends "all-green → go internal" to re-confirmation of KNOWN reds ([Sweep coworkers: suppress re-confirmation reports, alert only on deltas](../learnings/1781352352298-sweep-coworkers-suppress-re-confirmation-reports-a.md)).

A recurring task that diagnoses a persistent broken state (default `new_session: true`) re-derives the diagnosis from scratch each fire, with no memory of prior fires, and produces divergent and sometimes wrong conclusions. Remediation: (1) write findings to a canonical report file and read-anchor on it each fire; (2) when the state is known-broken and blocked, pause the task (`pause_task`) instead of letting it fire daily; (3) as supervisor, treat a coworker's same-symptom re-diagnosis as their current finding, not fact, especially when it contradicts a verified report ([Scheduled diagnostic tasks re-diagnose persistent state inconsistently across fresh sessions](../learnings/1780350138352-scheduled-diagnostic-tasks-re-diagnose-persistent-.md)). The dual trap for a recurring-report agent is carrying an age or streak forward by prose pattern-match: a Discord-support heartbeat logged an item as "11 days unfiled" and then "12 days unfiled" across two wakes 15 min apart when it was ~1.4 days old. Compute every age/streak fresh each wake from the source timestamp (`date -u` minus the message's own ISO timestamp), never from the prior report ([heartbeat: don't increment 'days unfiled' figures wake-over-wake — recompute from the source timestamp](../learnings/1789490566499-heartbeat-don-t-increment-days-unfiled-figures-wak.md)).

## Dashboard Formatting

The `slang-maintainer-dashboard` channel renders markdown. Every issue, PR, discussion, search query and external reference is a clickable `[label](url)` link, never a bare `#N` or plain query. Inline the full markdown body AND attach the `.md` via `send_file`. Use Unicode emoji (🚨 ⚠️ ✅), not Slack/GitHub shortcodes. URL-encode search queries (`>` as `%3E`, `=` as `%3D`, `:` as `%3A`, spaces as `+`) ([Dashboard channels render markdown — always include hyperlinks for issue/PR/discussion refs](../learnings/1778835191236-dashboard-channels-render-markdown-always-include-.md)).

## CI Health Monitoring

A single common-suite flake can functionally stall the Slang merge queue without jamming it: batches still run and individual PR checks look fine, and the only symptom is master HEAD not advancing for N hours. Check `gh api repos/<o>/<r>/commits/master --jq .commit.committer.date` ([A single common-suite flake can functionally stall the Slang merge queue](../learnings/1782226186227-a-single-common-suite-flake-can-functionally-stall.md)). For timeout/hang signatures, a true deterministic hang kills every run; if most PRs are green and only a few are hit, the cause is intermittent and the response is a normal rerun + requeue, NOT a maintainer ask. Escalate a dominant-evictor signature to the maintainer only after it persists across TWO consecutive sweeps once confounding noise is gone ([CI: flake-class vs deterministic-hang, and the two-sweep escalation threshold](../learnings/1782346148219-ci-flake-class-vs-deterministic-hang-and-the-two-s.md)).
