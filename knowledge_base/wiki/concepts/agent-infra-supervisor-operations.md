# Supervisor Operations, Sweep Suppression, and Nudge Discipline

> **Split 2026-08-12** out of the over-cap *Multi-Session Coordination* page; re-split 2026-08-17. Siblings: [Multi-Session Coordination, A2A Routing, and Session Handoff](agent-infra-multi-session-coordination.md) and [scan.py Health, Watchdog No-Op Controls, and Ledger Guards](agent-infra-supervisor-operations-2.md). This page owns nudge discipline, artifact checks, staleness triggers, and dashboard/CI-health reporting. The `-2` sibling owns `scan.py` over-flag root causes, the draft→non-draft CI-cell trap, watchdog no-op controls, and ledger guards. The coordination sibling owns A2A edges, dedup, empty-ack loops, and session handoff.

## TL;DR
- **A supervisor/cron/tooling nudge states CLAIMS, not facts.** Verify its premises against live GitHub state before acting — and always before an outward-facing or irreversible write. ~89% of artifact-less flags measured false; a false flag pressures a coworker into spamming a maintainer's issue with an un-retractable comment.
- **Putting "→ NUDGE" on a board is not a nudge** — actually dispatch. Coworker-nudge ONLY when a chain is stuck *inside the pipeline*: assigned session silent ≥~60min AND ZERO GitHub artifact. If ANY artifact exists, do not coworker-nudge.
- **"No artifact" ≠ "no artifact":** absent/None in a monitoring payload usually means *not populated*, not *does not exist*. **Recency ≠ presence:** a chain silent 17 days can be fully documented — ask "is the public record adequate?", not "did we speak recently?".
- **Staleness triggers are ETA-relative, not uniform.** Builds: 48h (ninja resumes incrementally). Reviews: ~2× ETA (~1h). A review "complete" = a hash-matched verdict against *current* head, not merely "a verdict returned."
- **A dispatched task's silence is not evidence of health** — the completion signal is a terminal artifact, never the absence of bad news. Blown-ETA silence on a bot deliverable = dropped-task 🔶 (verify session alive), NOT a maintainer nudge.
- **A superseded bot PR closed-unmerged is often a WIN, not a dropped deliverable** — resolve against the issue's actual close reason (a human PR may have superseded it) before re-escalating.
- **An approver torn down one CI-leg from recording loses its verdict with no ledger row** — on any teardown signal near the record step, independently verify CI terminal state and ask "did you record on `<sha>`?".
- **Sweep coworkers stay silent on re-confirmation** — ping the parent only on a delta (new signature, state change, actionable item). Recurring diagnostic tasks re-derive from scratch each fire (`new_session:true`) — anchor on a canonical report file.
- **Dashboard channels render markdown** — every ref is a clickable `[label](url)`; inline the body AND attach the `.md`; Unicode emoji, not shortcodes; URL-encode search queries.
- See the [`-2` sibling](agent-infra-supervisor-operations-2.md) for `scan.py` over-flag root causes, the draft→non-draft CI-cell staleness trap, watchdog no-op controls, and append-only-ledger guard construction.

## Sweep Coworkers: Suppress Re-Confirmation Reports

For periodic-sweep / babysitter coworkers: do NOT send the parent a report when a sweep merely re-confirms already-known/already-escalated state. Stay silent and continue local work (update trackers, append durable logs) when the sweep only re-surfaces known reds ([Sweep coworkers: suppress re-confirmation reports, alert only on deltas](../learnings/1781352352298-sweep-coworkers-suppress-re-confirmation-reports-a.md)).

Ping the parent only on a delta: a NEW signature, a state change (fix merges, flake recurs/escalates, cap hit, merge-queue eviction), or anything actionable on the parent's side. This extends the "all-green → go internal" rule to also cover re-confirmation of KNOWN reds.

## Supervisor Operations (nudge, deliver, concurrency)

Putting "→ NUDGE" in the supervision board is NOT a nudge — the supervisor must actually dispatch a message. Coworker-nudge ONLY when a chain is stuck inside the pipeline: the assigned coworker session went silent ≥~60min AND the chain has produced ZERO GitHub artifact ([CONSOLIDATED: /supervise-issues operations (nudge, deliver, format, concurrency)](../learnings/1780558152383-CONSOLIDATED-supervisor-operations.md)).

If ANY GitHub artifact exists → do NOT coworker-nudge. For a PR open but review stale: post a ONE-TIME GitHub ping to the assignee; if no assignee, post a "standing down for maintainer to drive" comment.

Nudge mechanics: find the stuck session with `ncl sessions list --agent-group <coworker-ag> --limit 2000 | grep 'gh-issue-...'`; dispatch into the EXISTING session using `send_message` with `target_session_id`. Track `nudgedAt`; max 2 nudges then escalate.

A scheduled/cron session has no default reply target — bare `send_message` fails "multiple destinations." Always specify `to="orchestrator"`. Concurrent manual `/supervise-issues` fan-outs create multiple orchestrator sessions that each rewrite `supervisor-state.json`; live `gh` is the single source of truth, not state files.

## Scheduled Tasks: Anchor on Canonical Reports

A recurring scheduled task that diagnoses a persistent broken state (default `new_session: true`) re-derives the diagnosis from scratch on every fire with no memory of prior fires, producing divergent and sometimes wrong conclusions ([Scheduled diagnostic tasks re-diagnose persistent state inconsistently across fresh sessions](../learnings/1780350138352-scheduled-diagnostic-tasks-re-diagnose-persistent-.md)).

Remediation: (1) have the task write findings to a canonical report file and read-anchor on it each fire; (2) when underlying state is known-broken and blocked, pause the task (`pause_task`) rather than letting it fire daily; (3) as supervisor, treat a coworker's same-symptom re-diagnosis as their current finding, not fact — especially when it contradicts a verified report.

## Dashboard Formatting

The `slang-maintainer-dashboard` channel renders markdown. Every issue, PR, discussion, search query, and external reference must be a clickable `[label](url)` markdown link — never a bare `#N` or plain search query ([Dashboard channels render markdown — always include hyperlinks for issue/PR/discussion refs](../learnings/1778835191236-dashboard-channels-render-markdown-always-include-.md)). Inline the full markdown body AND attach the `.md` file via `send_file`. Use Unicode emoji (🚨 ⚠️ ✅), not Slack/GitHub shortcodes. URL-encode search queries (`>` as `%3E`, `=` as `%3D`, `:` as `%3A`, spaces as `+`).

## CI Health Monitoring

A single common-suite flake can functionally stall the Slang merge queue without hard-jamming it — batches still run and individual PR checks look fine; the symptom is only visible as "master HEAD hasn't advanced in N hours." Always check `gh api repos/<o>/<r>/commits/master --jq .commit.committer.date` to detect this ([A single common-suite flake can functionally stall the Slang merge queue](../learnings/1782226186227-a-single-common-suite-flake-can-functionally-stall.md)).

For timeout/hang signatures: a true deterministic hang kills every run. If most PRs are green and only a few get hit, the cause is intermittent — the correct response is normal rerun + requeue, NOT a maintainer ask. Escalate a dominant-evictor signature to the maintainer only after it persists across TWO consecutive sweeps once confounding noise is gone ([CI: flake-class vs deterministic-hang, and the two-sweep escalation threshold](../learnings/1782346148219-ci-flake-class-vs-deterministic-hang-and-the-two-s.md)).

## supervise-issues pull-universe.sh argv overflow at ~170+ chains

A `/supervise-issues` tick stalls and the final assembly dies with `python3: Argument list too long` at `scripts/pull-universe.sh` (~line 242) once the chain count reaches ~170+. The per-chain fetch completes fine; the overflow is passing all chains as argv to the assembly step. Fix by piping via stdin/a temp file instead of argv when the universe is large ([supervise-issues pull-universe.sh argv-overflow at ~170+ chains](../learnings/1782867269290-supervise-issues-pull-universe-sh-argv-overflow-at.md)).

## Supervisor Artifact-Check for No-PR Chains

Before flagging a no-PR chain as "no GitHub artifact / owed PR", check for **issue comments** by the bot (triage 5-bullets), not just a PR or a `pr_session_mappings` row — `scan.py`'s `github_artifact` is null whenever there's no PR, but a stood-down/upstream-blocked chain's artifact is its triage comment on the issue ([supervisor artifact-check misses issue-comment artifacts for no-PR chains](../learnings/1783950814878-supervisor-artifact-check-misses-issue-comment-art.md)).

**Blast radius measured (2026-08-04): ~89% of artifact-less flags were false, and the nudge's suggested remedy was strictly worse than silence.** A supervisor nudge on slang#10027 said *"this chain has no GitHub artifact of ours either… post the public 5-bullet so a human landing on the issue can see where it stands."* The recipient checked before posting: the issue already had **six** bot comments, including the exact code-path trace the maintainer had asked for — the correct action was to **refuse the write and correct the premise**. Root cause confirmed the 07-14 finding and sized it: `scan.py` derived the artifact URL from `chain["pr"]` and otherwise required a caller-supplied `github_artifact_url` the feeder never populated, so **every no-PR chain reported `github_artifact: None` regardless of how much public trail it had**. **105 chains flagged artifact-less, 93 of them false negatives (~89% of the rows carrying the board's most-repeated warning)**; now fixed (105→12) with presence-not-recency as the discriminator and 202 artifact URLs persisted. The governing rule: **a supervisor/cron/tooling nudge states claims, not facts** — verify its premises against live state before acting, and especially before an outward-facing write; the check is one call, `gh api repos/<o>/<r>/issues/<n>/comments --paginate --jq '.[] | "\(.created_at)  \(.user.login)  #\(.id)  \(.body|split("\n")[0][0:100])"'`. This matters more than a wrong dashboard cell because a false flag **pressures a coworker into spamming a maintainer's issue**, and for the `nv-slang-bot` App token issue-comment PATCH/DELETE is **403** — a 7th duplicate comment would have been permanent. Generalizable discriminators: **"no artifact" ≠ "no artifact"**; **recency ≠ presence**; **a maintainer deferring their own assigned issue is ack-class input** with zero public output owed; and **irreversibility raises the verification bar** — when the requested action can't be undone with your token, the burden of proof sits on the request, not on your refusal ([supervisor artifact-less flags were ~89% false — verify a nudge's premises before complying with a public write](../learnings/1785761398778-supervisor-artifact-less-flags-were-89-false-verif.md)).

**A superseded bot PR closed-unmerged is often a WIN, not a dropped deliverable.** A bot-authored draft PR that ends up **closed without merging** looks identical, on a raw GitHub read, to a dropped/abandoned deliverable — and if you track it on a watch list as "fix in flight" the natural (wrong) conclusion is "our fix died — re-escalate." Concrete case (2026-08-03, shader-slang/slang): issue **#12070** (bwd_diff runtime induction-start crash, P1) had bot draft PR **#12072**; on 08-03 the issue **closed** — but via **PR #12299** by the human assignee (saipraveenb25), which superseded the bot draft. The bot PR closing unmerged was the *correct terminal state*, not a loss. Before re-escalating a closed-unmerged bot PR, read the linked issue's close reason and check for a superseding human PR ([a superseded bot PR closed-unmerged is often a win, not a dropped deliverable](../learnings/1785831626664-a-superseded-bot-pr-closed-unmerged-is-often-a-win.md)).

## Reconciling Near-Terminal Approver Teardown + scan.py Disposition Suppression

Two supervisor/orchestrator reconciliation lessons. **(1) An approver torn down one CI-leg from recording loses its verdict with no ledger row** — observed twice on slang#12111. The approver stages its full decision but gates `record_decision` on settled-head CI; a container restart / monitor "stopped" / crash at that boundary looks identical to "still waiting on CI" from the orchestrator's side, and the decision evaporates. On any teardown signal after an approver reports it is near the record step, do NOT assume it recorded: independently verify CI terminal state via `gh`, confirm the head hasn't moved, then explicitly ask "did you `record_decision` on `<sha>`? NO→record now, gate is clear." The approver's gate is correct; the fix is orchestrator reconciliation on resume ([approver teardown at near-terminal loses unrecorded verdict](../learnings/1784445113353-approver-teardown-at-near-terminal-loses-unrecorde.md)). **(2) scan.py disposition suppression must apply on ALL ball branches** — `classify` only consulted the human-owned disposition on the `ball=="human"` path, so `ball=="ours"`/`"none"` branches re-nudged every parked chain each tick. Fix: hoist a single `human_owns_disposition(chain)` guard to the top of `classify()` (returns `awaiting_human`, `needs_nudge=False`) before the ball dispatch, and widen the token set. Two upstream gaps remain that the agent must backfill each tick: pull-universe mis-tags `github-actions`/`coderabbitai` as `is_bot:false`, and emits naive space-separated timestamps that crash scan.py's aware `max()` ([scan.py disposition suppression must apply on all ball branches](../learnings/1784464263683-scan-py-disposition-suppression-must-apply-on-all-.md)).

## Blown-ETA Silence on a Dispatched Bot Deliverable = Dropped-Task, Not "Still Holding"

Sharply distinguish two watch-list dispositions that look identical on GitHub. **"Maintainer-gated":** a fix/verdict EXISTS and only a human ready-flip/merge/alignment-reply remains → genuine 🟡, a real maintainer nudge. **"Deliverable dropped":** no PR/verdict was ever produced by the owning bot session → a chain-liveness problem, NEVER a maintainer nudge. The trap is that a dropped chain (fixer/reviewer work that died on session teardown, losing the completion notification) looks *identical* to one calmly progressing — open issue, no PR/verdict, quiet. On 2026-07-20 the daily report carried #11877 (a fixer's mid-build PR) and #12116 (a reviewer's re-run) as "PR overdue → soft nudge to maintainer" and "draft awaiting ready-flip"; both were actually dropped-on-teardown with nothing ever produced, and had been dark 5 days across a compaction gap. Rule: any in-flight bot deliverable silent >48h (no PR, no verdict, `updated_at` frozen, no monitor ping) → flag 🔶 "verify not dropped — re-confirm the owning session is alive" and surface to parent so it can re-wake the owning session; only after the session is confirmed alive does it return to 🟡-held ([Watch-list: blown-ETA silence on a dispatched bot deliverable = dropped-task signal, not "still holding"](../learnings/1784535643816-watch-list-blown-eta-silence-on-a-dispatched-bot-d.md)).

Track dispatched-work ETAs; a blown ETA is a dropped-task signal, not a reason to keep holding ([Track dispatched-work ETAs; a blown ETA is a dropped-task signal, not a reason to keep holding](../learnings/1784154058484-track-dispatched-work-etas-a-blown-eta-is-a-droppe.md)). And **verify a claimed A2A handoff actually fired** — when a coworker says "I sent X to Y" and Y is waiting, verify the send actually left the sender's session before treating the chain as advanced; a stale critique gate, marker, or auth can silently block a send while the sender believes it went. Ask the sender to *confirm* the dispatch fired (not blind re-send, which double-dispatches) ([Verify a claimed A2A handoff actually fired — a stale critique gate can silently block the send](../learnings/1784882173077-verify-a-claimed-a2a-handoff-actually-fired-a-stal.md)).

## ETA-Relative Review Staleness + Recurring scan.py Over-Flag

**A review deliverable needs an ETA-relative staleness trigger, not the uniform 48h dropped-deliverable window.** A review (correctness/clarity verdict, ~20-30 min ETA) silent past ~2× its ETA (~1h) with no `running` owning reviewer session is *stranded*, not running → flag 🔶 immediately; 48h is right only for builds (ninja resumes incrementally) and owed-answers. Also 🔶-flag a review when the PR head moved after dispatch, or a returned verdict's reviewed-diff-hash ≠ current head — "review complete" means a hash-matched verdict against current head, not merely "a verdict returned." 🔶 on a review means the correctness gate has NOT completed → the next action is re-dispatch foreground/in-turn (completion = tool result, not a teardown-prone monitor), owned by parent/reviewer, not a maintainer nudge ([review deliverables need an ETA-relative staleness trigger, not the 48h dropped-deliverable window](../learnings/1784622307704-review-deliverables-need-an-eta-relative-staleness.md)). A fresh bot-authored draft fix PR with 0 comments looks *identical on GitHub* to a review calmly in progress and to one that died on teardown — so a daily/maintainer report must NOT default such a PR to 🟡; the disposition is driven by whether a hash-matched verdict actually landed against current head ([Daily-report: a fresh draft PR with 0 reviews is NOT proof the review is progressing — check for a landed verdict](../learnings/1784881773024-daily-report-a-fresh-draft-pr-with-0-reviews-is-no.md)).

**The `/supervise-issues` scan.py over-flag reverts on every skill re-sync.** Three recurring input/gate bugs owed as durable upstream fixes: (1) `scan.py::parse_ts` crashes on naive session-DB timestamps — force `tzinfo=utc` when `dt.tzinfo is None`; (2) `pull-universe.sh` only knows `nv-slang-bot` as a bot, so `github-actions`/`coderabbitai`/`CLAassistant`/`slangbot` reviews read as "human spoke last" — correct `is_bot` on the comment objects and OVERWRITE (not fill-when-absent) the disposition; (3) the HUMAN_OWNED gate must sit at the TOP of `classify()` (returning `awaiting_human`) so a maintainer's own comment on a `maintainer-driving`/`pr_open` chain doesn't false-flip — but deliberately do NOT add `awaiting_human`/`pr_open` tokens, so a fresh substantive @bot ask still overrides a stale self-label ([scan.py over-flag: 3 input/gate bugs revert on skill re-sync](../learnings/1784638375681-supervise-issues-scan-py-over-flag-3-input-gate-bu.md), [tick 97 — scan.py over-flag reverted again (skill re-sync); raw 15→0](../learnings/1784680848889-supervisor-tick-97-scan-py-over-flag-reverted-agai.md)).
