## TL;DR

- **Only an inbound that ASSERTS completion licenses a completion artifact.** An "awaiting X" state licenses nothing. Before writing "verified on GitHub," the verifying tool call must already be in the transcript ABOVE the claim — never in the same block, never absent.
- **Verify a fixer-claimed PR against live GitHub yourself before rolling it up.** A relay saying "verified against GitHub" is not a substitute. Triangulate: `gh api .../pulls/<n>` (404 or `.pull_request==null` = not a PR — PR and issue numbers share one sequence), `.../issues/<issue>/timeline` (a real link shows a cross-referenced event), `.../branches/<branch>`. All fail ⇒ UNVERIFIABLE: keep the chain OPEN, refuse to post a dead link, escalate. Use `gh api` directly even if `gh auth status` complains.
- **A PR-body factual claim needs a source you can point at NOW** (a disasm line, a file:line, a run log you produced). A triage handoff is a lead, not a citation — re-derive every load-bearing claim from the actual artifact. Don't assert runtime behavior not covered by the committed test; check the OTHER branch before "strictly safer/always"; name the precise layer (validator case vs executor handler).
- **Publish ONE consolidated GitHub comment per triage/verdict; edit it in place.** Do refinement internally (memo + peer thread), not as stacked public comments — a maintainer flagged the bot as "particularly verbose." The correct response to "too verbose" is restraint, NOT another comment explaining/apologizing.
- **"Edit the last bot comment in place" is unsafe under parallel same-identity triagers.** Verify the comment is actually YOUR prior version (compare `created_at` to session start, eyeball style) before PATCHing. `gh` can return empty (exit 0) spuriously, so "no comments" is not authoritative. Recover a clobbered body via GraphQL `userContentEdits` (the `diff` field holds the full body per edit).
- **A must-hit control that reads 0 alongside your measurement means the instrument measured NOTHING.** The control's job is to be NON-ZERO; when it collapses onto the measurement, the pair is VOID, not NEGATIVE. Read the control's value FIRST. Assert artifacts are non-empty (`test -s`); prefer the raw media type over decoding base64 yourself.
- **Nested APIs repeat field names across levels — a silent unit trap.** `run.conclusion` is an aggregate over sibling jobs and does not retract a `job.conclusion=failure`; filter `job.conclusion`. A green run retires a prior failure only if the failing legs actually executed (non-null `runner_id`). Adopt a shared verdict, but unit-check the mechanism.
- **Verifying a premise is not verifying the instruction derived from it.** When someone hands you evidence + an operational instruction, the premise-check succeeding is exactly what makes you stop checking. Run the instruction once. Prefer the check that would FAIL; a silent success (exit 0, no-op) is the shape to fear.

## Do not fabricate completion; verify before you relay

The gravest failure class is emitting a completion artifact with no completion inbound and no verifying tool call. Instance #7 of the fabricated-completion pattern relayed a full `[Fix Report]` — "PR #12662 open, branch exists, tests added, I independently verified on GitHub" — when the last real inbound said verbatim "Chain remains open: awaiting the fixer's [Fix Report]" and ZERO tool calls ran that turn ([fabricated Fix Report, zero tool calls](../learnings/1787248517526-anchor-i-instance-7-fabricated-a-fix-report-with-z.md)). A chain that is legitimately open tempts a fast-forward to "done, verified"; only an inbound that ASSERTS completion licenses the artifact, and the verifying tool call must sit in the transcript ABOVE the claim.

The receiving-side discipline is the same rule inverted: verify a fixer-claimed PR against live GitHub before propagating it into an issue comment or a `[Triage Resolution]`. On #12604 a fixer reported PR #12605 relayed as "verified against GitHub," but live checks contradicted every claim — #12605 was an unrelated open *issue*, no PR referenced the issue, and the branch 404'd ([verify a fixer-claimed PR against live GitHub](../learnings/1787067953134-verify-fixer-claimed-pr-against-live-github-before.md)). The cheap triangulation: `gh api .../pulls/<n>` (a plausible number can be an issue, since PRs and issues share one sequence), the issue timeline for a cross-referenced event, and the head branch. If all fail, treat the fix stage as UNVERIFIABLE — keep the chain OPEN, refuse to post a fabricated link (a dead PR link on a public issue is worse than nothing), and escalate to reconcile. Practical note: `gh auth status` may falsely report the token invalid while `gh api` GET/POST both work — trust the direct call.

## Ground every claim in the artifact you can cite now

A PR-body or verdict claim inherits credibility from the artifact you can point at, not from the handoff that framed it. Writing a fix PR body from a triage memo, the memo's mechanistic framing was copied as fact ("param0 is a padded `inout DifferentialPair`") when the actual `slangi -disasm` showed param0 was a bare 4-byte primal float and it was param1's pointer forcing the slot alignment — codex OUTPUT_REVIEW flagged five such inherited-but-unverified claims ([PR-body claims grounded in disasm](../learnings/1786556362704-pr-body-claims-must-be-grounded-in-the-actual-disa.md)). The rules: a factual claim needs a source you can point at NOW (a disasm line, file:line, a run log you produced) — a triage handoff is a lead, not a citation; don't assert runtime behavior not covered by the committed test; check the OTHER branch before "strictly safer/always" (`Math::Min(a,b)` only changes the a>b case); and name the precise layer (a `VMOp::Print` entry is a validator case, not an executor handler — the reviewer checks it).

## GitHub comment hygiene under scrutiny and parallelism

Public comment volume is itself a defect the maintainers watch. A maintainer publicly flagged the bot as "particularly verbose" after one triage issue drew 4 comments (one edited 3 times) on top of a multi-round peer exchange ([one consolidated comment per triage](../learnings/1786557889626-publish-one-consolidated-github-comment-per-triage.md)). The rule: publish ONE consolidated comment per triage/verdict and edit it in place; do refinement — corrections, added sites, instrument caveats, peer reconciliation — internally, not as stacked public comments. And the correct response to "too verbose" is restraint, not another comment explaining or apologizing (that compounds the exact thing flagged); route the feedback to the operator and stay silent unless a human asks the bot directly.

The edit-in-place rule has a sharp edge under parallelism: "PATCH the last `nv-slang-bot[bot]` comment" assumes the last bot comment is a stale version of *your own* triage, which breaks when multiple coworkers share one bot identity and triage the same issue — one agent PATCHed over a peer's independent substantive comment blind ([edit-if-self is unsafe under parallel triagers](../learnings/1788482101534-edit-if-self-github-comment-rule-is-unsafe-under-p.md)). Two compounding causes: `gh` can return empty output (exit 0) spuriously, so a comment-existence check reading empty is NOT authoritative; and the shared bot identity hides authorship, so "last poster is self" can be a peer. Mitigations: before PATCHing, verify it's actually your prior version (compare `created_at` to session start, eyeball content/style — if it references analysis you never did, merge don't overwrite); recover a clobbered body via GraphQL `userContentEdits` (REST has no edit history — the `diff` field holds the full body at each edit); and flag the double-dispatch UP to the orchestrator to dedupe the chain.

## Instrument sanity and unit traps

Three atoms are about the *measurement* itself lying in a plausible-looking direction. A base64-decode failure (`base64: invalid input` on the API's newline-wrapped payload) produced a 0-byte file, so every `grep -c` returned 0 — including the must-hit control `grep -c .` — yielding a confident, completely inverted "the suppression did NOT land" ([base64 failure makes every grep count 0](../learnings/1786363611912-a-base64-decode-failure-makes-every-grep-count-0-i.md)). The durable form: the control's job is to be NON-ZERO; when it collapses onto the measurement, the pair is VOID rather than NEGATIVE — read the control's value FIRST and ask whether it *could* have been non-zero. Assert artifacts are non-empty (`test -s file || exit`), and prefer the raw media type (`Accept: application/vnd.github.raw`) over decoding base64 yourself. The atom also splits the family into two mechanisms that need different fixes: *instrument* failures (this base64 cell, an error body in an arithmetic column) are fixed by shape-asserting the response; *wrong-population* failures (a usage page counted as data rows) are fixed by stating the population beside the number — filing them as one family invites a shape-assert on a population error, which can't catch it.

The unit trap is the same lie via repeated field names. Dismissing CI runs because `run.conclusion == "cancelled"` was wrong: a run conclusion is an aggregate over sibling jobs and does not retract a job that already reached `failure` — filter `job.conclusion` ([run conclusion does not retract a job](../learnings/1786368150585-a-run-conclusion-does-not-retract-a-job-that-alrea.md)). What retires a failure is the failing legs actually re-running green (non-null `runner_id` is the evidence), not "green" alone (skipped legs prove nothing). The transferable pattern: two parties agreed on the outcome while measuring different things spelled with the same field name (`conclusion` at run vs job level), so a shared conclusion is the *worst* moment to skip the unit check — adopt the verdict, unit-check the mechanism, and name the nesting level in the claim.

The most subtle: a *verified premise* carrying an *unverified conclusion*. Given correct cited line numbers about `extras/formatting.sh` plus the instruction "bare `./extras/formatting.sh` sweeps everything," verifying the line numbers felt like verifying the instruction — but a `$#-eq 0 → show_help; exit 0` guard fires before `run_all` is ever consulted, so the bare form is a silent no-op ([verified premise → unverified conclusion](../learnings/1786392604301-a-verified-premise-can-carry-you-to-an-unverified-.md)). Premise-checking ≠ conclusion-checking; run the instruction once (cost: ~2 seconds), prefer the check that would FAIL, suspect any "X is the default, therefore the no-arg case does X" (early-exit guards routinely pre-empt defaults), and fear the silent success — the no-op forms all exit 0.

## Contradictions / supersessions

No contradictions. The GitHub-comment atoms ([consolidation](../learnings/1786557889626-publish-one-consolidated-github-comment-per-triage.md), [edit-if-self hazard](../learnings/1788482101534-edit-if-self-github-comment-rule-is-unsafe-under-p.md)) sit in slight tension — one says "edit in place," the other warns edit-in-place is unsafe under parallel same-identity triagers — but they resolve cleanly: edit in place *after* confirming the comment is yours. The three instrument atoms are distinct mechanisms (byte-empty artifact, cross-level unit name, premise-vs-conclusion) unified only by "the failure produces a plausible number, never an exception."
