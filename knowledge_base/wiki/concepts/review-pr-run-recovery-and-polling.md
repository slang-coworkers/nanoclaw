# PR Review Run Recovery and In-Turn Polling

Operational lessons for driving the three-reviewer Slang PR-review pipeline (Reviewer A = correctness `compose-and-run.sh`, B = Devin, C = clarity `run-clarity.sh`) on teardown-prone clusters: how to detect true completion, recover a stranded pass without a full ~25-min re-run, poll in-turn instead of via a background Monitor, avoid stale/cross-PR artifact contamination, and adapt the runners to off-repo PRs. Sibling pages carry the approver challenger catalog and the branch-delivery/diff-reading disciplines.

## TL;DR
- **Anchor completion Monitors to true exit markers, never generic tokens.** The runners `tee` the full `--output-format stream-json` to the log, so `error:`, `API Error`, `---` appear as benign reviewed-diff content. Filter on the wrapper's trailing `^Reviewer A … exited:` echo or the runner's guard lines `^!!! REVIEW-GUARD FAIL` / `^!!! CLARITY-INCOMPLETE`, plus an artifact-size floor.
- **On a teardown-prone cluster, drive completion with in-turn bounded blocking Bash polls, not a background `Monitor`.** A Monitor / `run_in_background` `until`-loop does NOT survive session teardown; the completion signal must be a tool result you are holding, not a background event you ended the turn to wait for.
- **`pgrep -f '<reviewer cmd>'` matches your OWN polling shell** — confirm real exit via the script's log epilogue, not pgrep alone.
- **Recover before re-running.** A stranded-but-completed reviewer's run-dir outputs survive; a budget-capped Reviewer A's full review is intact in the last top-level assistant message in `stream.jsonl`; a dead clarity run's raw candidates are recoverable from `stream.jsonl` Write inputs. Re-run only the genuinely-missing dimensions, in-turn, as direct `Agent()` calls.
- **Reviewer B (Devin): fresh unique out-dir per run, or verify `devin-flags.md` mtime.** A reused out-dir can smuggle stale flags from a completely different PR; a `run_in_background` wrapper's exit 0 reflects a trailing `echo`, not the script's real status — check `devin-error.txt`.
- **A FAILING guard on a job that exited 0 warrants a stream check before reporting failure** — "0 bytes / no review" can be a budget-cap death with the full review recoverable from `stream.jsonl`.
- **Raising the dollar cap is the wrong lever on a fan-out pipeline** — report spend-at-death and which passes completed; bump only for genuinely large diffs (35–40).
- **The runner scripts take flags, not the skill verb** — `bash scripts/run-clarity.sh --mode pr --pr N …` (drop the leading `run-clarity`); `compose-and-run.sh` behaves the same.
- **A wrong-PR integrity-fail is usually a shared-`tmp/` race, not a code bug** — isolate in a `git worktree`, trust the per-run `pr-diff.reference` + `final-review.md` footer hash, and find the run dir by `PR NUMBER:` in `prompt.txt`, not by mtime.
- **Reuse completed outputs when the head-delta is non-code-only** — diff what was reviewed vs current head at the CONTENT level (strip volatile `index <hash>` lines), not the commit level; a finding about a removed file is MOOT on the shipping head.
- **Enumerate PR feedback across the UNION of `reviews` + `reviewThreads` + issue `comments`** — blocking maintainer feedback often lives in issue comments per-node review filters drop. Scope the diff from `gh pr diff -R <repo>` (remote base), never a stale-local `git diff main...head`.

## Review-Completion Monitors: Anchor to Exit Markers, Not Streamed JSON

When arming a Monitor to detect completion of a backgrounded `slang-pr-review-runner`/`slang-clarity-review-runner`, do NOT grep for generic tokens like `error:`, `API Error`, or `---`: those runners `tee` the full `--output-format stream-json` to the log, so the reviewed diff and tool_results contain those substrings as benign content and fire a false "REVIEWER FAIL" mid-flight. Anchor the filter to markers that appear ONLY at true termination — the wrapper's trailing `^Reviewer A rerun exited:` echo, or the runner's real guard lines `^!!! REVIEW-GUARD FAIL` / `^!!! CLARITY-INCOMPLETE`. Also verify the artifact exists and clears a size floor (`final-review.md` present; `clarity-review.md` >~300B — a 227B "now let me write…" stub = interrupted mid-write). On a session-teardown `stopped` notification, confirm actual state via the exit-line + artifact check before assuming done or re-running; the runners auto-resolve the PR head via `gh pr view`, so a re-dispatch auto-pins to the current head ([review-completion Monitor: anchor filters to exit markers, not streamed JSON](../learnings/1784380841597-review-completion-monitor-anchor-filters-to-exit-m.md)).

## Recovering a Teardown-Stranded PR-Review Pass Without a Full Re-Run

When the orchestrated slang-pr-review runner (Reviewer A / `compose-and-run.sh`) is stranded by session teardown, a full ~25-min re-run is usually unnecessary — recover in layers. (1) **Salvage completed reviewers first:** Devin (B) artifacts persist at `/workspace/agent/review-<pr>/devin/devin-flags.md`; Clarity (C) run dirs can be GC'd after days, but if you already read `clarity-review.md` into context, reconstruct it into a file rather than re-running. (2) **Recover partial A verdicts from the dead run's `stream.jsonl`:** the first run's 600s inner background-wait ceiling often truncates AGGREGATION while the individual subagents already reported, so extract per-subagent `result` summaries (`python3` over the jsonl, filter `type=="result"` with `len(result)>60`) — 4/6 verdicts are usually recoverable verbatim. (3) **Re-run ONLY the missing dimensions in-turn** as direct `Agent()` calls, which complete in-turn with no teardown window, unlike background bash tasks that die on container recycle.

Two infra failure modes to root-cause rather than paper over: **REVIEW-GUARD FAIL (<500B final-review.md)** = inner `claude --print` hit the 600s ceiling → re-run with `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`; **INTEGRITY-FAIL "reviewed WRONG diff"** = a STALE `tmp/pr-diff.patch` from a prior review left in the repo root (the model's `gh pr diff > tmp/pr-diff.patch` was permission-denied so it never overwrote it) → `rm -f slang/tmp/pr-diff.patch` before re-running. Checkout gotcha: the local `/workspace/agent/slang` worktree usually sits on base master, not the PR head — `git fetch origin pull/<n>/head` then read via `git show <head>:<path>` to reason about real post-PR code ([Recovering a teardown-stranded PR-review pass without a full re-run](../learnings/1784536666918-recovering-a-teardown-stranded-pr-review-pass-with.md)).

**Fetch into a named ref you own — `git fetch origin pull/<n>/head:refs/pr/<n>` — and read from `refs/pr/<n>`, never from `FETCH_HEAD`:** the clone is shared by sibling sessions, so `FETCH_HEAD` may point at master by the time you use it, and a `git checkout FETCH_HEAD -- <paths>` against the wrong ref exits 0 with zero modified files (see the branch-delivery page's delivery-verification section for the full treatment and citation of this mutable-ref trap).

The per-subagent recovery is verbatim: each of the six `.claude/agents/*` subagents emits its final text into the run-dir's `stream.jsonl` before the parent finishes, so group assistant `content[].type=="text"` blocks by `subagent_type` and keep the last substantial (>200 char) block per subagent (typically 4/6 survive; only the parent's synthesis and the cut-off subagent are lost, so resolve that one open question from source rather than re-running a 30-min pass). Critical: run-dirs are named `pr-<UTC-timestamp>Z/`, NOT by PR number — identify the right one with `grep "PR NUMBER" <dir>/prompt.txt` (or check `pr-diff.reference` head), or a concurrent review of a *different* PR with a populated `final-review.md` gets mis-attributed to yours ([Slang PR-review: recover torn-down Reviewer A findings from stream.jsonl subagents](../learnings/1784828278697-slang-pr-review-recover-torn-down-reviewer-a-findi.md)).

## In-Turn Polling on Teardown-Prone Clusters; Fresh Devin Out-Dirs Per Run

**When a cluster has stranded a review on session teardown even once, drive reviewer completion with in-turn bounded blocking Bash polls, not a background `Monitor`.** Observed 3× on one cluster (#12116 ×2, #12162): a background monitor (even persistent) dies on container teardown and leaves the pipeline with no verdict reaching the parent, while the workflow's "end turn after dispatch" step assumes the monitor survives. The durable pattern: launch A/B/C detached, record run dirs to a stable `run-dirs.env` (survives teardown), then loop `pgrep` in a bounded `while` inside a single Bash call (~8-9 min) repeating across turns until all three exit — each blocking Bash call returns a real result to context, so progress is durable across turn boundaries. Gotcha: `pgrep -f 'compose-and-run.sh --mode pr --pr N'` matches your OWN polling shell's command line — confirm real exit via the script's log epilogue, not pgrep alone. And always re-confirm PR head before re-driving a stranded review (teardown + a fixer re-push can make it stale twice over) ([in-turn polling beats background Monitor on teardown-prone clusters](../learnings/1784625017836-slang-pr-review-in-turn-polling-beats-background-m.md)).

**Reviewer B (Devin): use a fresh, unique out-dir per run, or verify `devin-flags.md` mtime before trusting it.** On a Devin timeout `devin-fetch.sh` writes only `devin-error.txt` and leaves any pre-existing `devin-flags.md`/`devin-page.txt` untouched — so a reused shared out-dir can smuggle stale flags from a COMPLETELY DIFFERENT PR into `combined-review.md` (observed: reviewing #12186, the dir held Jul-2 flags about an unrelated glsl struct-initializer PR). Use `/workspace/agent/devin-out-<pr>-<ts>`, `ls -la` and confirm the flags file's mtime is from this run; if only `devin-error.txt` is fresh, mark Reviewer B skipped (do not cat the stale file); and a `run_in_background` wrapper reports exit 0 for a trailing `echo`, not the script's real status — check `devin-error.txt`, not the shell exit code ([Devin out-dir reuse can smuggle stale flags from a different PR](../learnings/1784697016109-devin-out-dir-reuse-can-smuggle-stale-flags-from-a.md)).

**In-turn polling, hardened.** When told to run a PR review "in-turn," dispatch the reviewers with `nohup … &` (they detach 20-40 min) but stay in the turn with **bounded blocking Bash calls** — short `while [ $(date +%s) -lt $end ]; do pgrep -f <reviewer>; sleep 25; done` loops (~8-9 min each) that RETURN as a tool result when the reviewers finish. A Monitor / `run_in_background` `until`-loop does NOT survive session teardown; that strand hit the reviewer cluster 5× (#12116 ×2, #12162, #12200-first, #12231-first). The completion signal must be a tool result you're holding, not a background event you ended the turn to wait for ([In-turn PR-review polling: bounded blocking Bash calls, never an armed background waiter](../learnings/1785143391944-in-turn-pr-review-polling-bounded-blocking-bash-ca.md)).

## Budget-Cap 0-Byte Recovery, Runner-Flag Invocation & tmp-Collision Isolation

**A FAILING guard on a job that exited 0 warrants a stream check before you report failure:** Reviewer A can produce its full final review and then hit `error_max_budget_usd` on the very last (file-write) turn, so `final-review.md` is absent → the REVIEW-GUARD reports "0 bytes / no substantive review" and the summarizer parses 0/0/0 — but the complete review is intact in the last top-level assistant message in `stream.jsonl` (recover it, don't re-run at ~$30/20min). Bump `--max-budget-usd` to 35-40 for large diffs; and confirm drift==0 by counting actual POST tool_use calls, not by grepping the model's quoted REVIEW.md protocol prose ([slang-pr-review Reviewer A: "0 bytes / no review produced" guard can be a lie when the run hit the budget cap — recover from stream](../learnings/1785186988820-slang-pr-review-reviewer-a-0-bytes-no-review-produ.md)).

**The runner scripts take flags, not the skill verb:** `slang-clarity-review-runner`'s `argument-hint` shows `run-clarity --mode pr …` but `run-clarity.sh` parses flags only and exits 1 on the leading `run-clarity` token — invoke `bash scripts/run-clarity.sh --mode pr --pr <N> --repo <owner/repo> …` (drop the verb); `compose-and-run.sh` behaves the same way ([slang-clarity-review-runner script takes flags, not a run-clarity subcommand](../learnings/1785192373525-slang-clarity-review-runner-script-takes-flags-not.md)).

**A wrong-PR integrity-fail is a shared-`tmp/` race, not a code bug:** `compose-and-run.sh` stages the diff into a fixed `$REPO_ROOT/tmp/`, so two concurrent runs on the same `/workspace/agent/slang` checkout clobber each other mid-flight and the integrity net refuses to emit `final-review.md` (leaving `INTEGRITY-FAIL.txt`). Fix = re-run Reviewer A in an isolated `git worktree add --detach wt-<PR>-reviewerA HEAD` with `REPO_ROOT` pointed at it (REVIEW.md + `.claude/agents/` are git-tracked, so a base-HEAD worktree has them); name it `wt-<num>-<tag>` so supervisor GC reaps it ([Reviewer A wrong-PR integrity fail: shared tmp/ staging collision between concurrent runs](../learnings/1785209892572-reviewer-a-wrong-pr-integrity-fail-shared-tmp-stag.md)).

### Reviewer-runner operational facts (#12262 / #12263 rounds)

**Reviewer A's `INTEGRITY-FAIL` can be a false positive**: its post-run guard reads the FIXED shared path `tmp/pr-diff.patch`, which a concurrent same-container run for a different PR overwrites — so it reports files from the wrong PR. Trust the per-run `<run_dir>/pr-diff.reference` and the `final-review.md` footer `reviewed: <sha> · diff sha256` (captured at start, not shared); also locate your run dir by matching `prompt.txt`'s `PR NUMBER:`, not by mtime ([Reviewer A INTEGRITY-FAIL can be a false positive from concurrent runs sharing tmp/pr-diff.patch](../learnings/1785338666942-reviewer-a-integrity-fail-can-be-a-false-positive-.md)).

**When gh auth is dead on a PUBLIC repo, don't fall back to patch mode** (it drops new files via `git commit -am` and aborts on stale untracked files) — build a tiny read-only `gh` shim over local git (`gh pr diff` → `git diff merge-base..head`, `gh pr view` → prebuilt json) first on PATH, then run the production `pr` mode unchanged; Devin/Reviewer B scrapes the public URL anonymously regardless ([gh-shim fallback for dead token on public repo (pr-mode review)](../learnings/1785339099440-gh-shim-fallback-for-dead-token-on-public-repo-pr-.md)).

**Reviewer C (clarity) can exhaust its turn budget right before the canonical write** — don't just re-run (same failure, GC's the worktree); recover the raw candidates from the run's `stream.jsonl` Write-tool inputs (`tmp/review-candidates/pr-<N>-*clarity.md`) and mark `reviewers_complete:false`; bumping the turn/budget cap does not help since investigation depth is the cost ([clarity reviewer C exhausts turn budget before canonical write — recover from stream](../learnings/1785339114704-clarity-reviewer-c-exhausts-turn-budget-before-can.md)).

**Patch-mode review of an OFF-HEAD patch flags false "no producer" bugs — reframe as an apply-order dependency, don't relay it as a defect.** When a fix is split across a pushable PR head and a separately-delivered patch (common when the bot's GitHub App token lacks the `workflows` scope, so `.github/workflows/*` changes can't be pushed and are handed to a maintainer as a `git apply` patch), reviewing that patch with `slang-pr-review-runner --mode patch` is misleading: patch mode applies the patch to a temp branch off `slang/master`, NOT off the PR head, so any part that DEPENDS on the head's changes looks broken. On slang#13021 the maintainer patch added a CI step asserting `install-metadata/third-party-notices/{cmark-COPYING,lz4-LICENSE,glslang-LICENSE.txt}` exist, and patch-mode Reviewer A reported a 🔴 "no install rule produces these files → fails every non-wasm Linux job" — because the producing `install(FILES … RENAME …)` rules live on the PR head (815525c225, CMakeLists 691–714), which the master+patch sandbox lacks. Before relaying such a 🔴, verify whether the PR head produces the artifacts the patch references (`gh api repos/O/R/contents/<file>?ref=<head>` or `gh pr diff`); if so, reframe it as an apply-order / integration dependency — the off-head patch must be applied ON TOP OF the PR branch (or landed together), never onto bare master, or CI reds 100% — and state that apply-order explicitly in the maintainer instruction (in #13021 the maintainer ultimately hand-applied both workflow files onto the head, putting producer + consumer on one commit and mooting the hazard). Corollary: an inlined patch pasted into a PR body can be malformed (hand-retyped hunk counts → `git apply: corrupt patch`) even when the generated `.patch` file is valid — `git apply --check` the exact bytes before inlining ([patch-mode review of an off-head patch flags false "no producer" bugs — reframe as apply-order dependency](../learnings/1789174390977-patch-mode-review-of-an-off-head-patch-flags-false.md)).

Two enumeration/diff disciplines: PR-feedback enumeration must query the UNION of `reviews`, `reviewThreads`, AND issue-level `comments` — substantive blocking feedback (e.g. szihs on #996) often lives in issue comments that per-node review filters drop ([PR review-feedback enumeration must query ALL comment types incl issue-comments](../learnings/1785353452935-pr-review-feedback-enumeration-must-query-all-comm.md)); and scope a diff from `gh pr diff <n> -R <repo>` (diffs against remote base), never a local `git diff main...head` whose stale local `main` can inflate a 1-file PR to 40 files — the `gh pr diff` sha256 is also the review's `diff_hash` ([use gh pr diff, not local git diff --stat (stale-main trap)](../learnings/1785357368357-slangpy-pr-review-use-gh-pr-diff-not-local-git-dif.md)).

## Resume-Reuse, Additive Nit Rounds, and Off-Repo Reviews

When a review "stranded" (the background Monitor died on session teardown) but the reviewer *processes* actually completed, their run-dir outputs (`final-review.md` / `clarity-review.md` / `devin-flags.md`) survive — before re-dispatching a fresh 3-reviewer pass on resume, check artifact survival AND diff *what was reviewed* vs *current head at the CONTENT level*, not the commit level. A rebase/amend changes blob hashes even when content is identical and GitHub `compare` shows a misleading "ahead=1 behind=1"; the right comparison extracts file-blocks from Reviewer A's saved `pr-diff.reference`, strips volatile `index <hash>` lines, and diffs against a similarly-normalized `gh pr diff`. Empty diff on the real code+test files ⇒ the prior review is valid for the current head (concrete win on #12200: reviewed `fcfcc00` vs shipping `e7dc2ba`, 9 files byte-identical, only delta a removed scratch file → reused all three outputs, saved ~25 min). A consequence to handle: any finding *about a removed file* becomes MOOT on the shipping head — subtract it from the live count and say so; and per parent instruction after a monitor-strand, run these reviews FOREGROUND/in-turn, never re-arm a background Monitor (that's the strand's root cause) ([Reuse completed reviewer outputs when head-delta is non-code-only](../learnings/1784882724986-reuse-completed-reviewer-outputs-when-head-delta-i.md)).

Even an already-approved fix's additive "do-while-in-file" nit round needs the same rigor: a test's *prose claim* needs a `CHECK`/`CHECK-NOT` backing it or the prose must be narrowed (codex OUTPUT_REVIEW flagged an unbacked "no whole-handle copy" claim as must-fix; fix = scoped `CHECK-NOT: OpVariable ... Function` + `CHECK-NOT: OpCopyMemory` between two CHECKs) — and codex catching a **false claim in a comment you authored yourself** is the highest-value critique (self-authored inaccuracies are hardest to catch solo; always re-run OUTPUT_REVIEW after comment edits — "comments only" is not "safe"). When a fix's mechanism handles N sibling types (`isNonCopyableOpaqueType` covers both RayQuery and HitObject), add a positive test per sibling — an untested path the *same code* miscompiles-then-fixes is where a future refactor silently regresses ([Additive review-nit rounds still need CHECK-NOT backing + accurate comments (codex catches self-authored false claims)](../learnings/1784884204062-additive-review-nit-rounds-still-need-check-not-ba.md)).

Reviewing a PR on a repo that is NOT the compiler (e.g. `shader-slang/slang-rhi`) breaks the runner skills: both Reviewer A (`compose-and-run.sh`) and Reviewer C (`run-clarity.sh`) hard-default `REPO_ROOT=/workspace/agent/slang` + `git checkout origin/master` (slang-rhi's default branch is `main`), `compose-and-run.sh` requires a `REVIEW.md` that slang-rhi lacks, and their compiler-domain `.claude/agents/*` / `slang-review-*` subagents don't fit an RHI (C++ graphics abstraction) codebase — pointing `--repo` at them reviews the wrong checkout or emits domain-mismatched noise. The adaptation that works (slang-rhi#802): fetch the PR head into a `wt-<pr>-review` worktree of the *real* slang-rhi checkout, run **Reviewer B (Devin) natively** (it's the one runner that transfers unchanged — reviews any public GitHub PR by URL), dispatch general-domain `Agent`s with repo-appropriate lenses for A (correctness) and C (clarity), personally verify the load-bearing claims, and merge into `combined-review.md` with the same 5-bullet + JSON block, flagging the repo-mismatch adaptation in the header for transparency ([slang-rhi PR review: A/C runner skills hard-target the compiler repo — adapt](../learnings/1784929061497-slang-rhi-pr-review-a-c-runner-skills-hard-target-.md)).
