# Slang Autodiff IR: Higher-Order Composition Mechanisms

Composing derivatives (`fwd_diff(fwd_diff(f))`, `bwd_diff(fwd_diff(f))`) exercises first-order translation outputs as inputs to a second translation, and that exposes representation shortcuts the first order tolerated. This page records the internal mechanisms found while fixing the #13320 / #13322 / #13332 cluster. The symptom catalogue and the no-gdb crash-localization tooling are on [[wiki/concepts/slang-autodiff-custom-derivatives-and-higher-order.md]]; general autodiff design rules are on [[wiki/concepts/slang-autodiff-ir-autodiff-differentiation.md]].

## TL;DR

- **Derive `MakeDifferentialPair` pair types from the pair inst's own type, never from its operands.** A `no_diff` operand is typed `Attributed(T, NoDiff)`, which has no `DifferentialPairType` association, so `getOrCreateDiffPairType` returns null (Debug assert, Release segfault).
- **Both halves hit it:** the primal operand (a `no_diff` receiver/argument passed to a differentiable parameter) and the differential operand (`diffPair(s, dx)` with `dx` `no_diff`). #9808 switched both from `origInst->getFullType()` to operand-derived types; a fix that restores only one half is incomplete.
- **A lazily registered `DiffPair<T>` Differential crashes the transpose:** `maybeAddTypeAnnotationsForHigherOrderDiff` emits `lookupWitness(MakeIDifferentiableWitness(DiffPair<T>), Differential)` when the front end never registered `DiffPair<T>`, and `transposeMakePair` cannot consume it. `bwd_diff(fwd_diff-wrapper)` over any internally built struct pair crashes even without `no_diff`; mentioning `DiffPair<T>` in user code masks it.
- **Strip an issue's ingredients (interface, generic, synthesized wrapper) one at a time before accepting or rejecting a crash variant as part of it.** Each surviving crash is its own bug; bisect it across releases.
- **IR annotations are module-global.** An annotation recorded while translating one call (e.g. `ForwardDerivative(f_fwd) = VoidLit`) is visible to every later translation, so behavior can depend on translation order. Test call-site-first AND direct-call-first in the same `computeMain`.
- **`no_diff f(s)` on a `[Differentiable]` `f` still emits and propagates `f_fwd` at first order.** The prefix is defined only for non-differentiable callees, and it lowers to `TreatCallAsDifferentiableDecoration`. "Skip no_diff calls" in the forward pass only leaves the emitted call unannotated, and the next order crashes.
- **Run the reviewer's traced "before: compiles" example on master before trusting it**, and keep probe binaries under `active-work/<target>/` (`/tmp` is wiped on restart).

## `MakeDifferentialPair` pair types: derive from the pair inst, not its operands

**`MakeDifferentialPair` operands can be `Attributed(T, NoDiff)`, so pair types must come from the pair inst's own type.** In second-order autodiff, `translateMakeDifferentialPair` (slang-ir-autodiff-fwd.cpp) derives the pair type from an operand's type. When that operand is a `no_diff` value its type is `Attributed(T, NoDiff)`, which has no `DifferentialPairType` association, so `getOrCreateDiffPairType` gets null: it asserts in Debug and segfaults in Release. Both halves hit it. The primal operand does when a `no_diff` receiver or argument is passed to a differentiable parameter, and the differential operand does in `fwd_diff(g)(diffPair(s, dx))` where `dx` is a `no_diff` parameter. Before #9808 (at 473afb979), `transcribeMakeDifferentialPair` took both pair types from `origInst->getFullType()`; #9808 switched both to operand-derived types, and that is the regression. A fix must restore both halves; the #13332 v3 fix restored only the primal half [MakeDifferentialPair operands can be Attributed(T, NoDiff)](../learnings/1790719603753-autodiff-makedifferentialpair-operands-can-be-attr.md). A second layer sits behind it. `maybeAddTypeAnnotationsForHigherOrderDiff` registers a synthesized `DiffPair<T>`'s Differential as a lazy `lookupWitness(MakeIDifferentiableWitness(DiffPair<T>), Differential)` whenever the front end never registered `DiffPair<T>`, and `transposeMakePair` cannot consume that unresolved type. As a result `bwd_diff(fwd_diff-wrapper)` over ANY internally built struct pair crashes on master even without `no_diff` (e.g. `compute(x){ Q q={x}; return evalQ(q,x); }`), and mentioning `DiffPair<T>` anywhere in the user's differentiable code makes it pass [reproduce without the issue ingredients (#13322)](../learnings/1790711557745-slang-autodiff-before-filing-a-crash-under-an-issu.md).

## Strip an issue's ingredients before filing a variant under it

**Strip an issue's ingredients before filing a variant under it.** In #13322 (a second-order derivative through a generic that calls an interface method), a reviewer variant that still crashed, `struct MixedView : IDifferentiable, IView` behind a non-differentiable interface, looked like the issue's own pattern. Rewritten with no interface and no generic (a `no_diff` receiver calling a method whose `this` is differentiable, then `bwd_diff` over `fwd_diff`), it crashed identically on master and v2026.13.1 and compiled on v2026.5.2. So it is the separate `MakeDifferentialPair` regression above, which #11615 merely routes MixedView into through a synthesized `[NoDiffThis]` wrapper. The rule is to strip the interface, the generic and any synthesized wrapper one at a time; each surviving crash is its own bug. Keep release binaries and probe files under your own `active-work/<target>/` directory, because `/tmp` is wiped on container restart [before filing a crash under an issue, reproduce it without its ingredients](../learnings/1790711557745-slang-autodiff-before-filing-a-crash-under-an-issu.md).

## Autodiff annotations are module-global: one recorded mid-translation leaks into later ones

**A module-scope annotation recorded during one first-order translation leaks into later ones.** The #13320 patch recorded `ForwardDerivative(f_fwd) = VoidLit` on the user's custom-derivative function while translating a call to `f` (in `emitCalleeAnnotationsForHigherOrderDiff`). Annotations are module-global, so a later first-order translation of any function that calls `f_fwd` directly then hit E38035, and whether it did depended on translation order. The verified repro is a void `inout` custom derivative called as `no_diff g_fwd(q)`; that call loses its `TreatCallAsDifferentiable` decoration at lowering (LOWER-TO-IR shows the bare call), so a `no_diff` guard cannot save it. When a fix adds a producer for an annotation, test both translation orders, call-site-first and direct-call-first, in the same `computeMain`. Also run the reviewer's traced "before: compiles" example on master before trusting it: Reviewer A's example crashed on master (rc 139) for an unrelated reason, while a different variant was the real regression [a module-scope annotation recorded during first-order translation leaks into later translations](../learnings/1790732389632-autodiff-a-module-scope-ir-annotation-recorded-dur.md).

## `no_diff` on a call to a differentiable callee still differentiates it

**`no_diff` on a call to a DIFFERENTIABLE callee still differentiates it at first order.** `no_diff f(s)` and `no_diff(f(s))`, where `f` is `[Differentiable]` with a custom `[ForwardDerivative(f_fwd)]`, still emit a call to `f_fwd` and propagate the derivative: on master a05023cd3, `no_diff f(s) + s^3` gives d = 22 at s=2, not 12. That matches the user guide, which defines the `no_diff` prefix only for calls to non-differentiable functions (07-autodiff.md:789-819), and the IR decoration it lowers to is `TreatCallAsDifferentiableDecoration`, despite the name. So a fix that "skips no_diff calls" in the forward pass (as the #13320 R2 marker did) does not avoid the derivative call; it only leaves the emitted call unannotated, and the next order then crashes. Run a first-order probe before assuming `no_diff` means "no derivative code emitted" [no_diff on a call to a differentiable callee still differentiates it](../learnings/1790761921207-slang-no-diff-on-a-call-to-a-differentiable-callee.md).
