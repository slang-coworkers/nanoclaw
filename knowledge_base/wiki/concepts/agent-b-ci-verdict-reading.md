## TL;DR

- **A run/suite `conclusion` is a rollup, not a test result.** A `conclusion: failure` can sit above **zero** failing check-runs (a cancelled gate job poisons the verdict); a `conclusion: success` can sit over a tree where nothing compiled (only `board-sync`/`reuse` jobs "succeeded"). **Read the children per-suite, and count non-skipped *build* jobs** — never trust the rollup.
- **`skipped`/`cancelled` both satisfy `status == "completed"`** and read as health to any status-only consumer. But `skipped` has 4+ distinct causes, most by-design (draft PR, path filter, `needs:` cascade, approval gate). **A job conclusion is not a cause** — bucketing all skips as "lost coverage" overstated one gap 28×. Read the enclosing `if:` of the *gating* job.
- **A rerun surfacing MORE failures did not reproduce them** — compare per-JOB failing sets, not per-run conclusion. An attempt whose only failure was the aggregator, or whose jobs have `steps == 0`, established no baseline in either direction.
- **`behind_by > 0` is not a rebase trigger.** Gate the remedy on PR `state` (a terminal PR reports its last failure forever) AND on whether the base touches anything in the **causal cone of your assertion** (your changed files *plus* what your tests read as output).
- **An unchanged CI run id on a terminal PR means dead, not stuck** — the signal inverts from "neglected, nudge harder."
- **Infra-vs-code:** empty `steps[]` + 404/410 logs + empty `runner_name` ⇒ infra kill; the reason lives only in the check-run *annotations* endpoint. `conclusion` does not encode the class.
- **A vendor status page is a lagging indicator** — measure your own queue, stratified by the gating class; recovery is stratified (cheap runners first, self-hosted GPU last).

## The rollup lies in both directions

**A check-suite / workflow-run `conclusion: failure` can sit above zero failing check-runs.** Confirmed mechanisms, none attributable to a diff: a cancelled gate job (`filter`, which every build/test job `needs:`) poisons the suite verdict — run-level `failure`, all downstream `skipped`, **zero failed**; a job dying at `Set up job` produces no verdict at all (`steps: []`, `runner_name: ""`); jobs stranded in `queued` keep the rollup unresolved with no red child. `cancelled` ≠ `failed`; a run-level `ci_failed` webhook says `failure` in all of these. **The property is per-SUITE, not per-COMMIT** — a commit head can show 3 real failing check-runs from *other* suites while the one run people care about has zero-failing-children, so cite the suite/run id or the same head refutes you. Before quoting, confirm the enumeration is complete (`collected == total_count`) — `--paginate` had 401'd mid-walk and returned 100 against a reported 122. And don't over-claim from head count: "confirmed on three heads" collapsed when two heads were the same actor's PRs and one had self-resolved — **the strengthener is the mechanism, not the tally.** [A check-suite conclusion=failure can sit above zero failing check-runs — read the children, and read them PER-SUITE not per-commit](wiki/learnings/1786050130429-a-check-suite-conclusion-failure-can-sit-above-zer.md)

The mirror danger: **green is the dangerous reading.** A rollup of `SKIPPED: 41 / SUCCESS: 4` where the four successes are `board-sync` ×2 and `reuse-compliance-check` ×2 is `conclusion: success` over a tree where nothing was compiled. For Slang specifically, **count non-skipped *build* jobs**, never the rollup verdict. [Check a citation separately from the conclusion it decorates](wiki/learnings/1786066006766-check-a-citation-separately-from-the-conclusion-it.md)

## A job conclusion is not a cause — split the untested bucket

`skipped` and `cancelled` both satisfy `status == "completed"` and read as health to a status-only consumer — true and worth keeping. But ranking that combined "untested" bucket by row count and escalating it overstated a gap ~37× in one sweep (418 rows reported; split was 407 skipped / 11 cancelled / 0 other — only the cancelled subset is lost coverage). The by-design skips: `retry-on-gpu-failure` (`if: failure() && merge_group && run_attempt < 3` — must skip on a green `pull_request` run) and pre-refactor workflow artifacts (`test-slang-rhi` rows on stale heads for a job that no longer exists). **Verify by reading the ENCLOSING CONDITION, not the job name.** The finding that survives: `completed` is not `ran` — a status-keyed health metric counts ~20% of its surface as passes when nothing executed. Before reporting any "N rows of X", open the gate for the top 2-3 contributors and ask whether that row is *supposed* to be there. [Split the untested CI bucket by conclusion: skipped is by-design, cancelled is lost coverage](wiki/learnings/1786170572229-split-the-untested-ci-bucket-by-conclusion-skipped.md)

A deeper decomposition confirmed the same trap at 28×: "313 of 744 `test-falcor` executions tested nothing" was really **11 of 744 (1.5%)**. Bucketing by *cause* rather than conclusion: TESTED 430, by-design 229 (draft + priority-yield + doc-only filter), supersede 53, cascade 20 (upstream **build** cancelled ⇒ falcor skipped as a *dependent*), waiting 1 (approval gate, `conclusion: null` — falls through every conclusion-keyed branch), genuine loss 11. **The biggest sub-trap: `filter` skipped ≠ infra failure** — a draft PR skips `filter` itself (`if: ... draft != true`) and everything cascades; resolving 3 runs → PRs → `draft=true` killed 129 rows of the claim. **Assert the buckets sum to the population** — a residual means an unhandled state, not rounding (the 744th row was a `waiting`/`null` job). And **frequency does not license quarantine for a *crashing* test** — a 6.3% crash rate (`0xC0000005`, image comparison disabled) is a memory-safety signal, not a flaky-image nuisance; cost data *ranks* a flake, only the failure mode *licenses* removing it. Read the issue's human comments before recommending a disposition. [A job conclusion is not a cause: 'skipped' has 4+ distinct causes, and reading them all as lost coverage overstated a gap 28x](wiki/learnings/1786222091299-a-job-conclusion-is-not-a-cause-skipped-has-4-dist.md)

## A rerun that surfaces more failures did not reproduce them

Attempt 1: `failure`, 1 failing job. Attempt 2 (rerun, same `head_sha`): `failure`, 4 failing jobs. The naive read — "reran, failed again, therefore reproduces, therefore real regression" — is backwards. Attempt 1's `filter` was never acquired by a runner (`steps: 0`, 404 log), so every `needs: [filter]` job `skipped`; attempt 1 tested **nothing** (0 success / 1 failure / 35 untested), its only "failure" the aggregator. Attempt 2 got 32 legs green and surfaced 3 *independent* failures on jobs attempt 1 never reached — **zero overlap.** The rerun revealed masked results; it did not reproduce a failure. **Reproduction is a claim about a signature on a job, not a run's rolled-up conclusion** — diff the failing-job *sets*. If the earlier attempt's failure was only the aggregate, or its jobs have `steps == 0`, it established no baseline. This error pushes toward "leave a green PR red" and is self-confirming (more failures feels like stronger evidence). Detector: count failing jobs per attempt; if the count went UP, ask what the earlier attempt executed. `run_attempt > 1` is no evidence alone, and `gh run rerun` returns rc=0 without incrementing the attempt — probe `run_attempt` against a baseline. [A rerun that surfaces MORE failures did not reproduce them — compare per-JOB, never per-run conclusion](wiki/learnings/1786083740698-a-rerun-that-surfaces-more-failures-did-not-reprod.md)

## behind_by is not a rebase trigger

Two independent gates are needed, and each alone makes the remedy a no-op:

**1. PR state must gate any remedy computed from a run.** A run resolved *by branch* can point at a PR closed for two weeks while the live draft is a different PR — a branch fronts several PRs across its life. Fetch `state`/`draft`/`merged` before computing a remedy. One sweep found **7 of 30** CI nudges pointing at non-OPEN PRs; it's not rare. [behind_by is not a rebase trigger — gate the remedy on PR state AND file overlap](wiki/learnings/1786021170788-behind-by-is-not-a-rebase-trigger-gate-the-remedy-.md)

**2. File overlap decides whether "behind" is material.** `behind_by` counts commits on the base, not conflicts and not invalidation. Compare the base's new files against your changed files from the **merge_base**; zero overlap ⇒ the existing green still binds. Caveat: overlap on `CMakeLists.txt`, a CI workflow, or a shared header can invalidate a green with no *source* overlap — read those hunks. A nudge naming a remedy is a claim about materiality, and materiality is measurable: ask *what would change if I did it?* (Cost of getting it wrong isn't zero: a rebase on a hand-off-complete draft re-runs CI and can dismiss a review.) Answering locally on a `--depth N` clone yields well-formed *wrong* ancestry counts — check `--is-shallow-repository` or use the `compare` API. [behind_by is not a rebase trigger — gate the remedy on PR state AND file overlap](wiki/learnings/1786021170788-behind-by-is-not-a-rebase-trigger-gate-the-remedy-.md)

**The overlap gate is necessary but not sufficient — overlap on what your TEST OBSERVES counts too.** For an emit-only / golden-output test, the base can touch none of your files yet edit the emitters your CHECK lines assert against. Counterexample: a diff of 2 files vs master's 1080, overlap NONE — but master touched `slang-emit-wgsl.cpp`/`slang-emit-metal.cpp` and the diff's regression test is a WGSL+Metal FileCheck. Ask two questions: does the base touch *my files*? and does it touch anything *my tests read as output* (emitters, preludes, golden/`.expected` files, capability tables, diagnostic text)? **Overlap is "did the base edit anything in the causal cone of the assertion I rely on"** — golden-output tests have a much wider cone than their filename suggests. Use `git diff --name-only` locally for the base side; the `compare` API caps `.files` at 300 and under-reports a large range. [behind_by overlap gate: overlap on what your TEST OBSERVES counts, not just on your changed files](wiki/learnings/1786029394195-behind-by-overlap-gate-overlap-on-what-your-test-o.md)

## An unchanged run id on a terminal PR means dead, not stuck

A CI-supervisor probe nudged "PR stale: same failure run id as last tick — rebase to re-dispatch." Every part was wrong. **Gate applicability BEFORE measuring staleness** — a closed/merged PR reports its last failure forever and re-nudges every tick (`gh pr view <n> --json state,mergedAt`; skip if not OPEN). **The signal inverts:** an identical run id across two ticks *feels* like "nobody re-dispatched → neglect → nudge harder," but on a terminal PR an unchanged run id is the signature of a **frozen artifact — dead (or CI never ran), not stuck.** Reading it as neglect turns a no-op into recurring work against a worker who can't act. Related: if two supervisor subsystems can act on the same resource (a GC probe and a CI probe), one must see the other's mutations or verify existence at dispatch (`git worktree list`); and don't put operator-gated actions (`gh pr ready`) in a worker nudge. A probe that fails toward "go ahead / act on it" deserves more scrutiny than one that fails loudly. [An unchanged CI run id on a terminal PR means dead, not stuck — gate applicability before measuring staleness](wiki/learnings/1786020942273-an-unchanged-ci-run-id-on-a-terminal-pr-means-dead.md)

## Infra-vs-code triage: the reason can be absent from every place you'd look

For an infrastructure-killed job, `GET /actions/jobs/<id>` returns `steps: []` and the logs endpoint returns **HTTP 404**. A triage of "find the first failed step, else read the log" returns nothing — indistinguishable from "no problem." The reason lives in exactly one place, the **check-run annotations** endpoint keyed by job id (`/check-runs/<job_id>/annotations`): `"The hosted runner lost communication with the server"` (died mid-job, `conclusion=failure`) or `"The job was not acquired by Runner of type hosted"` (never got a runner, `conclusion=cancelled`, `runner_name=""`). **Tell:** empty `runner_name` or `steps: []` ⇒ go to annotations. `conclusion` does not encode infra-vs-code — both `failure` and `cancelled` appear for infra, and a run-level `failure` can roll up a job-level `cancelled`. Corollaries from the same pass: a merge-queue commit's `committer.date` is minted at queue-entry, not land time (overstates staleness by the full queue-check duration); and a red merge_group run is not proof a red check can land — compare `head_sha`, the red attempt may have been evicted and re-formed green. [Infra-vs-code CI triage: empty steps[] + 404 logs means read check-run annotations](wiki/learnings/1786055179491-infra-vs-code-ci-triage-empty-steps-404-logs-means.md)

## Retention-expired reds are terminal-unclassifiable

A CI failure whose logs passed GitHub's ~7d retention (`.../jobs/<id>/logs` → rc=1, **HTTP 410**) is *permanently* unclassifiable. Record that verdict **once** with the verification date and skip it; re-downloading dead logs every sweep is pure recurring cost. One sweep: 17 of 22 failing PRs had reds ≥283h old at 410, generating 56 "log-expired" decline rows in 7 days — marking them `terminal_unclassifiable` cut triage load 22 PRs → 5. **Voiding condition:** a head-sha change (rebase/push) produces fresh runs with live logs — store that or the skip becomes permanent blindness. Scope boundary (a parent correction): auto-closing these was over-reach because **a ledger ranks cost, never value** — "burns a triage slot" is a cost measurement being used to justify closing someone's contribution; the legitimate fix touches only your own behaviour (skip it), and an informational nag must state the only remedy it can request (rebase). Keep the window attached to any frequency claim — "flaky infra was a non-factor" was true of this sweep's fresh reds and false of the week. [Mark retention-expired CI reds terminal-unclassifiable once — don't re-derive the same verdict every sweep](wiki/learnings/1786213458375-mark-retention-expired-ci-reds-terminal-unclassifi.md)

## A vendor status page is a lagging indicator

During a provider incident, don't decide whether to retry from the status page — measure your own **queue depth + median wait, stratified by the class you gate on.** At one probe the page hadn't updated in 32 minutes while the fleet degraded; the incident *prose* ("self-hosted runners may see errors when they register") named the fault class no status color conveys. The aggregate can improve while the gating class goes to zero: recovery is stratified (cheap hosted runners return first, self-hosted GPU pools last), so sampling the aggregate over-weights whichever class recovers fastest. **The trap inside the trap: `skipped` satisfies `status == "completed"`** — a recovery check phrased "did anything complete?" counts a skipped run as health. A recovery claim needs a terminal `success`/`failure` **in the gating class**; both `cancelled` and `skipped` mean UNTESTED. Two probes minutes apart beat one snapshot — a trend distinguishes draining from filling. [A vendor status page is a LAGGING indicator — measure the queue, stratified by the class you gate on](wiki/learnings/1786042035800-a-vendor-status-page-is-a-lagging-indicator-measur.md)

## A recovery gate must be control-tested in BOTH directions

A gate meant to fire on a fresh terminal `success` in the gating workflow (with `steps > 0`, so a cancelled gate job at `steps=0` can't read as recovery) **passed its negative control immediately** (silent on the degraded state — the reassuring result that invites you to stop) but **failed its positive control**: backdating the *threshold* to a window with three known-good greens left it silent, because `actions/workflows/<id>/runs?per_page=30` is ordered by run *creation* and 30 rows was a short *time* window reaching only after the greens. **Backdating a threshold variable does not widen an API window** — name which of the three rungs (mechanism / currency / window) you checked. For a "has X happened since T?" probe over a paginated listing, print the oldest timestamp your page reached and confirm T falls inside; a count of 0 from a short page is a statement about the window. Control-test every gate both ways — only the positive control proves it isn't degenerate.
