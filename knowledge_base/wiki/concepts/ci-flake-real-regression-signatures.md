# CI Flake Triage — Real-Regression Signatures Behind a Flake-Shaped Failure

Failures that *look* like infra flakes but are deterministic code or packaging breaks: short `test-slang` jobs hiding an `nvcc` compile error, the Sig-B JSON-RPC drop that turned out to be a JIT-teardown use-after-free, a peak-RSS metric that is a silent no-op on the wrong runner OS, upload-corrupt artifacts that survive rerun, the wrong artifact copy inspected, a stale GCC precompiled header masquerading as a cache flake, and pytest-xdist worker IDs that signal crash-respawns. The theme: before firing a rerun, prove the failure is transient — most of these are rerun-proof and the disposition is "block on the code/artifact fix," not "requeue."

## TL;DR

- **A short `test-slang` failure (<2 min) is not automatically a pre-test infra flake.** Windows GPU runners compile the PR's own CUDA `.cu` files with `nvcc` *after* the backend probes; grep the job for `errors detected|error:|exit code|Segmentation` and verify any INTERMITTENT verdict before rerunning.
- **Consistent failure on BOTH windows-debug and windows-release confirms multi-platform legitimacy** — a real code break, not a flake.
- **A real fix-gap can be correctly *detected* yet wrongly *attributed*.** Proving "the workaround isn't the fix" does NOT prove the *named mechanism* is the cause. Keep mechanism claims labeled "unproven" and defer to the path owner's attribution.
- **Attribute a flake to a fix by TREE ANCESTRY, not timestamps** — `compare/<fix-sha>...<headSha>` `.merge_base_commit.sha == fix-sha`; a rerun logged *after* the fix merged still re-runs the OLD head. For "did it recur on a fixed master?" enumerate `gh run list --event merge_group` since the merge — those trees contain the fix by construction.
- **Check the runner OS against a tool's capture-path dependency** — a Linux-only measurement path (`/usr/bin/time -v`) on a Windows-only runner is a silent no-op (`rss_kb: None`), not an error.
- **Before classifying "please add metric X" as new work, grep the tool for the metric field** (`grep -rn "rss\|getrusage\|resident"`) — the scaffold may already exist; the real work is portability + downstream surfacing, a different fixer briefing.
- **A zero-filled / corrupt binary in a test artifact is rerun-proof upload corruption** — `download-artifact` SHA256 passes because it is computed over the already-corrupt zip; only an author rebase/re-push regenerates the artifact. `gh run rerun --failed` re-runs only the failed test jobs and re-downloads the SAME corrupt artifact.
- **Inspect the artifact the failing *test* job actually consumes** — Slang test jobs download `slang-tests-<platform>` (~10 MB), NOT `slang-build-<platform>` (~90 MB); they carry separate dylib copies, and the build one can be valid Mach-O while the tests one is zero-filled.
- **Discriminator for uploaded-corrupt (rerun-proof) vs transient download glitch:** identical failing signature across 2+ attempts on *different fresh runners* = corruption; a real transient glitch varies.
- **`fiddle 'friend' outside class` on a GCC runner while MSVC builds clean = a stale GCC PCH, not a poisoned reused-workspace cache.** A code PR that only touches PCH inclusion turns the leg green — a one-time cache wipe would not. Disposition: log-as-left / no-rerun; framed as "blocked on the code fix landing (clears queue-wide on rebase)," not "wipe the runner cache."
- **pytest-xdist worker IDs above the launched worker count are crash-respawns** — a real-crash signal, not parallelism noise.

## Short `test-slang` Failures Can Hide a Compile Error, Not a Flake

A `test-slang` GPU job that fails in ~1 minute with all "Checking supported backends" probes green then exit 1 is NOT automatically a pre-test infra flake. Windows GPU runners compile the PR's own CUDA `.cu` test files with `nvcc` as a setup step *after* the backend probes but *before* the main batch — a compile error there produces a short job that mimics the "Common Test Setup" flake. On #11957 a classify-only subagent misread 17 real `nvcc` errors in the prelude as INTERMITTENT; consistent failure on BOTH windows-debug and windows-release confirms multi-platform legitimacy. For any short (<2 min) `test-slang` failure, grep the specific job for `errors detected|error:|exit code|Segmentation` and always verify a subagent's INTERMITTENT verdict before firing a rerun ([short test-slang failures can hide an nvcc compile error, not an infra flake](../learnings/1783743117364-short-test-slang-failures-can-hide-an-nvcc-compile.md)).

Related: a Windows GPU test job under 60 s often ran no tests at all (it died in a disk/artifact preflight), and a ~1–2 minute `test-slang` failure can be real `nvcc` errors compiling the PR's own `.cu` files after the backend probes. The same grep (`errors detected|error:|exit code|Segmentation`) separates "ran nothing" from "compiled and broke."

## Sig-B test-server JSON-RPC Drop: #11951 → the True Cause Is a JIT-Teardown UAF (#12114), Not AVX-512

The long-open Sig-B fingerprint tracked as **#11951** — a `JSON RPC failure: waitForResult()/hasMessage()` drop on `tests/compute/static-const-matrix-array.slang.3 syn (llvm)` (or the `static-const-vector-array` sibling), windows-*-gpu `test-slang`, ~99% of other tests passing — is NOT an IPC-layer bug. It manifests as the test-server *child* dying and the parent harness seeing only the generic `waitForResult()/hasMessage()` drop (the `.slang.3 syn (llvm)` victims are exactly the LLVM-synth/JIT codegen path).

The first hypothesis was an AVX-512 JIT SIGILL, worked around workflow-side. Those diagnostics still hold as *mechanics*: PR #12056 "Apply AVX-512 JIT workaround to all CI tests" (merged 2026-07-10, `01adc68f`) is **workflow-only**, exporting `SLANG_DISABLE_AVX512=1` in `ci-slang-test.yml` (line ~99) + `ci-slang-coverage-test.yml`; `pull_request` runs use the workflow from the PR **head tree**, not master, so check presence with `gh api repos/shader-slang/slang/contents/.github/workflows/ci-slang-test.yml?ref=<head-sha> --jq .content | base64 -d | grep SLANG_DISABLE_AVX512` (export absent → branch predates the fix → advise rebase, not rerun) ([Sig-B test-server JSON-RPC drop = AVX-512 JIT SIGILL (#11951 resolved by #12056)](../learnings/1784089175111-sig-b-test-server-json-rpc-drop-avx-512-jit-sigill.md)).

**Correction / supersession (2026-07-17):** the AVX-512-SIGILL attribution was **INCIDENTAL, not the fix.** The TRUE root cause of Sig-B is a **use-after-free in the LLVM JIT teardown**, fixed by PR #12114 (`bf7a78ab25f4`, merged 07-15 21:40Z); jkwak-work (who authored the fix and closed his own repro #12146) confirmed it, and a post-fix sweep found 8 failing merge-group runs containing #12114 with ZERO Sig-B recurrences → fully resolved. Two durable lessons carry more weight than the specific fix:

1. **A real fix-gap can be correctly *detected* yet wrongly *attributed*.** The earlier "flake still fires with `SLANG_DISABLE_AVX512` active" trifecta (export-active + genuine FAILED line + unrelated evicted PR) genuinely proved #12056 wasn't the fix, but "the workaround isn't the fix" does NOT prove the named mechanism (AVX-512 residual) is the cause. A nondeterministic teardown UAF manifests intermittently on ordinary runs and looks identical to a test-server drop, so keep mechanism claims labeled "unproven" and defer to the path owner's attribution.
2. **The clean discriminator for "is a flake fixed by PR X" is a tree-ancestry sweep, not a timestamp sweep.** A rerun logged *after* PR X merged re-runs the same OLD head, so for each candidate run get its `headSha` and check `gh api repos/OWNER/REPO/compare/<fix-sha>...<headSha> --jq .merge_base_commit.sha` (the fix is an ancestor iff `merge_base == fix-sha`); then grep `--log-failed` only on runs that provably CONTAIN the fix, and for "did it recur on a fixed master?" enumerate `gh run list --event merge_group` since the merge (those trees contain the fix by construction). When closing an escalation you opened with a wrong-but-honest hypothesis, post a NEW follow-up owning the arc rather than editing history ([Sig-B (11951) root cause was JIT-teardown UAF (#12114), not AVX-512 — a real fix-gap can still be mis-attributed](../learnings/1784320016828-sig-b-11951-root-cause-was-jit-teardown-uaf-12114-.md)).

## Check the Runner OS Against a Tool's Capture-Path Dependency — a Linux-Only Measurement on a Windows Runner Is a Silent No-Op

The compile-perf tracker's peak-RSS metric (#12112 bullet 1) is NOT greenfield: `tools/compile-perf/bench.py` (@c5d4d76e6) already detects GNU `/usr/bin/time -v` (`_detect_gnu_time`, :218), wraps every timed compile in it (`run_once`, :230-256), parses "Maximum resident set size" into `rss_kb` (:250-251), and stores it per-workload in results.json (:363-364, :391). But it is dead where it matters:

1. **Portability gap** — capture fires only when GNU `/usr/bin/time` exists, and BOTH perf CI workflows run on the **Windows** pool (`nightly-mdl-perf-test.yml`, `compile-perf-release-sweep.yml` → `labels: [Windows, X64, nvrgfx-perf-kernelvm-bridge]`) where `/usr/bin/time` is absent → `rss_kb` is silently `None` on the exact machine feeding shader-slang.org/slang-compile-perf (macOS BSD `time` also lacks that parsed line; it only ever populates on Linux dev hosts).
2. **Never surfaced** — nothing downstream reads `rss_kb` (`track.py:_point_metrics` :67-79, `trend.py`, `report.py`/`breakdown.py` all iterate only `r["timers"]`).

Reusable triage moves: before classifying a "please add metric X" tooling request as new work, grep the tool for the metric field name (`grep -rn "rss\|getrusage\|resident"`) — the scaffold may already exist and the real work is portability + downstream surfacing, a very different fixer briefing; and always check the CI runner OS (`grep runs-on/labels` in the workflow) against what the tool's capture path depends on — a Linux-only measurement path on a Windows-only runner is a silent no-op. (Contrast: `native/api-driver.cpp` genuinely has zero memory measurement, so #9817's "session-create memory delta" IS new work — add a getrusage/GetProcessMemoryInfo sample after `createGlobalSession` returns; note `bench.py:parse_timers` :34 only accepts `…ms` tokens so a non-ms metric needs a new emit/parse channel, and the tracker is stdlib-only by invariant so the Windows RSS path must be `ctypes`, not `psutil`.) ([compile-perf tracker already captures rss_kb but it's dead on the Windows perf runner and never surfaced](../learnings/1784095582129-compile-perf-tracker-already-captures-rss-kb-but-i.md)).

## Zero-Filled dylib = Rerun-Proof Upload Corruption — and Inspect the RIGHT Artifact

**The signature (slang PR #12216).** A `test-slang`/`test-slang-rhi` job fails almost instantly (~4 s, 3 launch attempts) at slang-test **startup** (not a test assertion) with `dyld: Library not loaded: @rpath/libslang-compiler.<ver>.dylib ... slice is not valid mach-o file`. Root cause: the packaged test artifact shipped a binary that is *bytewise all zeros* (`libslang-compiler.dylib` + `libslang.dylib` + two bins were zero-filled at the same size; valid siblings had proper Mach-O magic `cffaedfe`). It is NOT a runner download glitch — GitHub's `download-artifact` SHA256 digest PASSED, because the digest is computed over the already-corrupt zip, so the zero-fill happened at upload/packaging time on the build runner and the post-download check cannot catch it.

Disposition = **DECLINE rerun (rerun-proof)**: `gh run rerun --failed` re-runs only the failed *test* jobs and re-downloads the SAME corrupt artifact (the green build job isn't re-run), so it can never clear — the path to green is an author rebase/re-push that regenerates the build artifact. Confirm fast: `gh api .../actions/artifacts/<id>/zip > a.zip`, unzip, check magic bytes (`open(p,'rb').read(4).hex()` == `00000000`), and cross-check the build job + other platforms are green to rule out a real code break. Systemic advice: maintainers should add a post-build magic-bytes/`file` sanity check *before* upload ([Zero-filled dylib in test artifact = upload-corruption, rerun-proof](../learnings/1784923930083-zero-filled-dylib-in-test-artifact-upload-corrupti.md)).

**Crucial refinement — inspect the artifact the failing test job actually consumes.** The Slang test jobs download the small (~10 MB) `slang-tests-<platform>` artifact, NOT the large (~90 MB) `slang-build-<platform>` artifact — they carry **separate copies** of `libslang-compiler.<ver>.dylib`, and the build one can be a valid mach-o (`cffaedfe`) while the tests one is zero-filled garbage. On PR #12216 (run 30100795306), the first pass inspected the 93 MB `slang-build-*` dylib, found valid magic, and *wrongly fired a rerun* — only catching it against a prior-sweep tracker note and cancelling. The `slang-tests-macos-aarch64-clang-debug` dylib was 4161536 bytes of pure `0x00`, yet the download-artifact SHA256 check passed (upload-corrupt, same rerun-proof class). Discriminator for "uploaded-corrupt (rerun-proof)" vs "transient per-runner download glitch": the *identical* failing signature reproducing across 2+ consecutive attempts on *different fresh runners* is the tell — a real transient glitch varies. Same rerun-proof family as the #12022 expired-artifact lesson ([macOS test job downloads slang-tests-* artifact, not slang-build-*](../learnings/1784974553601-macos-test-job-downloads-slang-tests-artifact-not-.md)).

## `fiddle 'friend' outside class` on GCC = Stale PCH, Masquerading as a Cache Flake

A build failure with `slang-ir-insts.h.fiddle:13:22: error: 'friend' used outside of class` (+ `expected unqualified-id before 'private'/'public'` cascading into `invalid use of incomplete type 'IRBuilder'`) on a self-hosted **GCC** Linux runner — while windows-msvc + slang-native build the same tree clean — **looks like** a poisoned/dirty reused-runner workspace (a stale generated `.fiddle` header) inviting a "needs a manual `fiddle/` clean" conclusion. The real root cause (shader-slang/slang **#12227**, fixed by **#12233**) is a **stale GCC precompiled header** expanding FIDDLE-generated `private`/`friend` tokens at *namespace* scope.

The distinguisher — and the reason this belongs with the rerun-proof family: it is NOT runner hygiene, because a *code* PR that only touches PCH/header inclusion turns the leg green (which a one-time cache wipe would not), and `gh run rerun` reuses the same PCH → identical error, so the disposition is **log-as-left / no-rerun**; the difference from a plain flake is the *resolution framing* — "blocked on the code fix landing (clears queue-wide on rebase)," not "wipe the runner cache" ([fiddle:13 'friend' outside class on GCC runner = stale PCH, not poisoned cache](../learnings/1785060680645-fiddle-13-friend-outside-class-on-gcc-runner-stale.md)). See the build-infrastructure concept for the merged CMake fix (exclude `slang-compiler.h` from the GCC PCH, all-TU) and the surprising clean-build reproduction.

## pytest-xdist High Worker IDs Are Crash-Respawns

When a pytest-xdist run reports worker IDs (`gwN`) higher than the number of workers you launched, those high IDs are respawned workers — xdist restarts a worker after its process crashes, and the replacement takes the next free `gwN`. So a `gw12` in a 4-worker run is not extra parallelism; it is the visible tail of at least a handful of worker *crashes*, i.e. a real-failure signal to chase (segfault / OOM in the test process), not harness noise to rerun past ([pytest-xdist high gwN worker IDs are crash-respawns](../learnings/1781204283033-pytest-xdist-high-gwn-worker-ids-are-crash-respawn.md)).
