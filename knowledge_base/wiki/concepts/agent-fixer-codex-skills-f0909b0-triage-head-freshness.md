## TL;DR

- **A triage SHA / memo `file:line` is a timestamp, not current state.** On any active draft PR — especially a core-team member's own — the FIRST read-only step before build/plan/repro is `git fetch origin pull/<n>/head` then `git log <triage-SHA>..FETCH_HEAD --oneline` (and again restricted to the memo's target files). If a commit in that range touches them, read it — the author may have already fixed it, often in the commit *immediately after* the pinned SHA.
- **A stale checkout does not error — it silently reports a real-but-obsolete code shape.** Before triage code-reads, sync and pin: `git fetch origin master && git rev-parse HEAD origin/master`; if they differ, `git checkout origin/master` or read `origin/master:<path>` via `git show`/`git grep`. Put the verified SHA in the memo.
- **Before scoping a fix, verify the named symbols/feature actually exist on the checked-out HEAD** (`git log -S`, `git ls-tree`, `grep`, `git branch -a`). An issue that names files may describe work on an UNMERGED PR branch → verdict is *blocked-on-dependency* or "remaining work on the author's own PR, not independently actionable," never ready-for-fix.
- **On a well-scoped author-driven issue, search for an existing `Fixes #N` PR before assuming a fix must be built.** A companion PR opened seconds after the issue means triage flips from *dispatch fixer* to *verify the PR*. Verify it: fetch `pull/N/head` into a named ref, `git show` the files, and run the tests if binaries exist.
- **"Out of scope" / "already correct" claims in a triage handoff are hypotheses, not facts.** A report scoping a neighboring block OUT is a statement about the report's boundary, not a correctness certificate. If you'll say a block is fine, open it and check — otherwise say "out of scope, not evaluated." Surface any contradiction to the dispatcher as a separate flag; don't self-expand scope or stay silent.
- **When a downstream agent reverses your specific instruction with a fresh reading, spawn a read-only verification against current source** — neither accept nor reject from memory. Then correct the memo in place (strike the wrong finding with the verifying HEAD + date).
- **A landed fix + green multi-platform CI warrants a close recommendation** — continued caution creates avoidable maintainer toil. The evidence bar is "merged (not draft) + multi-platform green."
- Subagents hallucinate confident `file:line` citations; two conflicting reports about the same file is the tell. Never hand a fixer load-bearing pointers sourced only from a subagent digest — spot-verify the lines directly with `git show <ref>:file | grep -n`.

## The core failure: triage against stale state

Every atom on this page is a variant of one defect — asserting a code fact from a state that is no longer current — and the fixes converge on "re-verify at HEAD before acting." The most damaging instance escalated a *bogus* "maintainer must decide the semantics of `public`" question to a maintainer, because the triage subagents read a checkout at a commit that predated the relevant merge by minutes; on current master the decision was already shipped and there was one producer, not two ([stale checkout → phantom producer](../learnings/1787620127054-triage-against-stale-checkout-produced-a-phantom-p.md)). The discipline: sync and pin the SHA into the memo, and when an issue is a follow-up to a recently-merged PR, read that PR's diff FIRST — your working tree's footprint may already be stale. When you discover you posted a wrong escalation, patch the comment in place to retract explicitly and send an upstream correction; don't let a false public @-mention sit.

The same decay hits memo `file:line` findings, which are HEAD-relative. A memo written days earlier instructed a fixer to add `BFloat16` mapper cases to SPIR-V and CUDA emitters — but at the fixer's later HEAD both paths already diagnosed BFloat16 gracefully, and the SPIR-V header had no `BFloat16` constant to map to at all, so the instruction would have written dead code or fabricated a nonexistent constant ([memo file:line goes stale](../learnings/1787353491544-triage-memo-file-line-findings-go-stale-across-hea.md)). The generalizable sub-rule: "add the missing mapper case" has a hidden precondition — that a real mapping *exists*; for a genuinely target-unsupported value, a graceful diagnose+return is the correct handling, not a gap to fill. And when a downstream agent reverses your instruction with a fresh reading, spawn a read-only verification against current source rather than adjudicating from memory.

## Draft PRs move under you — the #12691 family

A tight cluster of atoms documents the same pattern on core-team member kaizhangNV's actively-developed draft PRs (the #12691 structural-ray-tracing family): the reported bug was ALREADY FIXED on-branch by the author before the fixer touched it, four times in one day. In the sharpest case the fix was the commit *immediately after* the SHA the triage memo pinned ([the fix is often the commit after the triage SHA](../learnings/1787671421853-12691-family-the-fix-is-often-the-commit-after-the.md)). Related sub-cases: a triage that *rejected* the issue's simpler capability-atom suggestion, only for the author to have already landed exactly that route correctly ([checkpoint SHA stale within minutes](../learnings/1787669533760-a-triage-checkpoint-sha-can-be-stale-within-minute.md)); and a mid-escalation to the operator for a "patch-their-draft go/no-go" that a HEAD check made moot in two read-only commands ([re-verify draft-PR at PR HEAD](../learnings/1787669928995-re-verify-a-triaged-draft-pr-issue-at-pr-head-befo.md)). The mandatory first step on any active-draft-PR-by-core-team issue: `git fetch origin pull/<n>/head` → `git log <triage-SHA>..FETCH_HEAD --oneline` → read the newest commit's diff+test. Chain conduct on these: report up, verify by ancestry + source read + diagnostic-severity check, and never open a competing PR or patch a core-team member's own active draft. A self-labeled "not run-confirmed / strong hypothesis" step in a memo (e.g. "the metal arm defeats a capability atom") is exactly the claim to re-verify — the author's committed test may assert the diagnostic fires via the very path the memo said couldn't catch it.

## Does the code even exist yet?

Two atoms sharpen HEAD-verification into an existence check. An issue that names specific files may describe work on an *unmerged* PR branch, not master. The entire structural-RT feature named in #12855 did not exist on master — it lived only in the author's draft PR — so a fixer against the mounted master checkout couldn't act, opening a PR against master would be nonsensical, and pushing to the author's branch would collide; the correct verdict is "remaining work on the author's own PR, not independently actionable" ([verify a feature exists on master](../learnings/1788212132503-triage-verify-a-feature-exists-on-master-before-di.md)). The test-coverage variant: an issue asking to "add unit tests for X" needs X to exist on master first — three symbols in #12845 were introduced by a still-OPEN PR, so `git log -S` on master returned nothing and the verdict is *blocked-on-dependency* ([test-coverage follow-up, verify symbols](../learnings/1788159619973-triage-a-test-coverage-follow-up-against-the-pr-th.md)). Both atoms also warn that subagents hallucinate confident `file:line` citations (the same agent gave both wrong and right names for the same file — two conflicting reports is the tell); use `git show <pr-branch>:<file>` to read not-yet-merged code for accurate pointers while still flagging the block, and spot-verify load-bearing lines yourself before handing them to a fixer. The test-coverage atom also carries reusable facts: `slang-static-unit-test` links the compiler statically so tests reach non-exported `extern` symbols but not `static`-qualified ones (drop the `static` + declare in an internal `source/slang` header — the sanctioned pattern), and `IRFixtureBuilder` builds only void functions.

## Existing fixes and close recommendations

Verifying HEAD also collapses work: check the *current* top-of-tree before classifying a perf/feature/regression ask as open, because the actual fix often landed under a different PR than the issue cites. The #10746 `__half2` ask pointed at a CLOSED PR, but native `__half2` SIMD arithmetic already existed at HEAD from a different merged PR, shrinking the live work to a docs fix ([check HEAD before treating a perf feature as open](../learnings/1787226156638-triage-check-head-before-treating-a-perf-feature-a.md)). (Corollary: DeepWiki indexes the default branch, so when it disagrees with an issue's "how it works today," it may be reporting the newer post-fix state — go verify source at HEAD.) On a well-scoped author-driven issue, search for an existing `Fixes #N` PR before assuming a fix must be produced — #12594 had a companion PR opened 52 seconds after the issue, flipping triage's job to *verify the PR + correct factual gaps* ([check for an author's self-implemented PR](../learnings/1787035926588-triage-check-for-an-author-s-self-implemented-pr-b.md)). Verify, don't just read: fetch `pull/N/head` into a named ref, `git show` the files, and run the tests if binaries exist (a raw `grep -rl` is not a coverage measurement — open the file). And when a fix has *merged* with green multi-platform CI, recommend closing rather than staying cautious — a maintainer explicitly noted the bot was "overly cautious about closing" and did it himself ([landed fix + green CI → recommend close](../learnings/1787475457470-triage-a-landed-fix-plus-green-multi-platform-ci-w.md)); maintainer time is the scarce resource, and the evidence bar is "merged + multi-platform green."

## Inherited scope/correctness claims are unverified

A distinct sub-family: a triage handoff mixes *the prescribed fix* (usually well-verified) with *incidental scope/correctness assertions about adjacent code* ("X is fine," "Y is out of scope") that are often NOT independently verified. On #12578 the handoff said an adjacent `DescriptorKind` enum block was "correct and out of scope" — it was actually stale (missing enumerators, a deprecated alias, drifted implicit values) ([triage handoff out-of-scope claim unverified](../learnings/1786985585404-a-triage-handoff-s-out-of-scope-already-correct-cl.md), [scoping-out is not a correctness certificate](../learnings/1786985585376-triage-trap-an-issue-scoping-something-out-is-not-.md)). "Not this issue's subject" ≠ "verified correct"; a report scoping a neighbor OUT is a boundary statement, not a claim you may inherit. Handle it cleanly: keep the approved PR tightly scoped, file the newly-found staleness as its OWN follow-up issue (don't expand an approved PR beyond its `Fixes` target), correct the false claim in place in your own verdict, and surface the contradiction to the triager as a separate flag with evidence — silence and silent over-reach are both wrong. (Note when two doc enums differ in kind — one `$()`-splices C++ constants and self-syncs, the other is a plain implicit-valued enum needing hand-updates — because it changes how the fix is made.)

## Contradictions / supersessions

No contradictions; the twelve atoms are one discipline observed across many issues, all pointing to "re-verify at current HEAD before asserting or dispatching." The draft-PR atoms ([#12691 family](../learnings/1787671421853-12691-family-the-fix-is-often-the-commit-after-the.md), [checkpoint SHA](../learnings/1787669533760-a-triage-checkpoint-sha-can-be-stale-within-minute.md), [re-verify at HEAD](../learnings/1787669928995-re-verify-a-triaged-draft-pr-issue-at-pr-head-befo.md)) are progressive refinements of the same pattern rather than competing claims.
