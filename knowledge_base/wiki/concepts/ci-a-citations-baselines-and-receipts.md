## TL;DR

- **Grep locates a citation; it does not validate one.** Before citing a site, read what it *asserts* — a negative test proving X fails contains X and matches every search for X. Compare the noun in your claim to the noun in your evidence.
- **Numbers copied from build/test output are BRANCH-relative by construction.** A line number lifted from a diagnostic, ninja `FAILED:` line, or traceback is a *branch* number and is wrong the moment it lands in base-relative prose. Convert it, or replace it with content.
- **A PR body must declare its citation baseline once, at the top.** Base-vs-branch offsets caused four false "wrong citation" corrections in one review — none would have been filed if the ref were stated.
- **Cite pre-existing / unchanged lines by CONTENT (symbol + quoted comment), never by line number.** Branch numbers are the *most* ephemeral ref and rot permanently into squash-merge commit messages. Prefer identity-based refs (content, symbol, blob hash) over position-based ones.
- **A citation-checking predicate is itself ref-sensitive** — "15/15 clean" is unfalsifiable unless it prints the ref it ran against.
- **Disputing a line citation on a branch you don't have: ask if the line is in their DIFF, not in your tree.** If the PR *adds* the line, "does this exist?" has different true answers on each side and every shared-corpus explanation fits.
- **If an action returns a receipt, cite the receipt** — never let prose stand where a message id / URL belongs. A detailed description of an artifact is not evidence it was transmitted.
- **"You conceded / you said X" is a quotation claim wearing a correction's clothes.** Grep the peer's artifact; do not recall it. A truncated read feels like a read.
- **A rebuild on mainline discards by default** — anything that existed only on the old head must be enumerated *from* the old head, never inferred from a diff whose baseline lacks it.

## A citation must be checked for what it ASSERTS

Drafting a public comment, a hand-written `extern "C"` shim's pointer cast was justified as "the same one every other reflection method performs internally." **Backwards** — the in-tree wrappers cast `this` → opaque handle; the shim casts the other direction. A grep for the reverse cast found two sites cited as precedent; a reviewer read what each *does*: one casts a `FunctionReflection*` to `VariableReflection*` specifically **to exercise the wrong-kind error path** (the next line asserts `== SLANG_E_INVALID_ARG`) — citing it as precedent would have inverted its meaning in public. **Grep locates a citation; it does not validate one.** A negative test is the sharpest case: a test proving X fails contains X and matches every search for X. Search results are token-presence evidence; "this code endorses X" is a claim about *intent and outcome* only reading settles. Cheapest guard: for every citation in a public artifact, ask *"what would this file look like if my claim were false?"* — for the unit test, "exactly like this," which is the tell. Same family as `permissions.push` answering an `issues:write` question — compare the noun in your claim to the noun in your evidence. [A citation must be checked for what it ASSERTS — a negative test matches every grep for the thing it proves fails](../learnings/1785903738449-a-citation-must-be-checked-for-what-it-asserts-a-n.md)

## Line numbers: branch-relative by construction, so declare the baseline

A build log, test output, or stack trace is **branch-relative by construction** — it was produced by compiling the tree you have checked out. Any line number lifted from it is a *branch* number and is wrong the moment it lands in base-relative prose. Worked case: `slang-diagnostics.lua:6161` was pasted verbatim from a deliberately-induced build failure into a PR body whose citations were all base-relative; at the declared merge base the site is `:6154` (the patch inserts +7 above it). Four readers argued about *other* citations without noticing this one, because a plausible-looking number attracts no scrutiny — only a ref-aware checker flagged it. Rules: never paste a line number from tool output into base-relative prose — convert it (`base = branch − net_insertions_above`) or replace it with content; suspect every number whose provenance is an error message; **a checker that doesn't name its ref is unfalsifiable** ("17/17 clean" says nothing; "17/17 clean against `ca76f8781a`" is refutable). Bonus: a string-substitution edit replacing a cited line with quoted text left the same message duplicated in consecutive sentences — sweep for duplicated quoted prose after any find/replace. [Numbers copied from build/test output are BRANCH-relative — converting them is a required step, not a nicety](../learnings/1785942255479-numbers-copied-from-build-test-output-are-branch-r.md)

The remedy at the PR-body level: **declare the baseline once, at the top.** Base-vs-branch offsets caused *four* false corrections in one review cycle (author measured against merge base; reviewers checked against branch or a moved master), costing more messages than any real defect:

| Cited | Author's ref | Reviewer's ref | Delta |
|---|---|---|---|
| `slang-diagnostics.lua:276` | base 276 | branch 283 | +7 |
| `slang-emit.cpp:3593` | base 3593 | branch 3608 | +15 |
| `slang-diagnostics.lua:6154` | base 6154 | author wrote branch 6161 | +7 |

Fixes in order of leverage: **(1)** declare the merge-base sha in the body (`Verify with git show <sha>:<path>, not a branch checkout`); **(2)** cite pre-existing lines in untouched files by content; **(3)** compute per-file offsets with `git diff --numstat`, don't estimate. Also check whether master moved (mid-review it advanced 6 commits) — the merge base (`git merge-base HEAD origin/master`) is the stable ref to declare, because it's what the diff is computed against. **The checker must record which ref it ran against** — making the predicate ref-aware immediately surfaced the author's own leaked branch number. [A PR body must declare its citation baseline — base-vs-branch line offsets caused four false corrections in one review](../learnings/1785942129840-a-pr-body-must-declare-its-citation-baseline-base-.md)

## Cite unchanged lines by content, not line number

For an *unchanged, pre-existing* line, cite content — not a line number. A load-bearing citation (a comment recording that diagnostic code 99996 was "moved from 99999 to avoid severity conflict") sat at master `:465` and PR-head `:472` (+7 from the PR's own added diagnostics). Two reviewers cited it two ways, both correct for their own ref; the first "use the branch number" correction was *also* wrong. **The branch number is the worst choice:** it breaks on any rebase or insertion above it (including by the PR itself), a future reader lands on *master* and finds unrelated code there, and on a squash-merge repo the PR body *becomes the commit message* — a branch-pinned pointer is embedded forever, guaranteed wrong. Cite the symbol + quoted comment text (both greppable, neither drifts); if a number is wanted, give master's and label it (`@master`). For lines the PR *does* change, branch numbers are fine — the diff is the context. The generalizable shape: **a pointer's stability is part of its correctness — prefer identity-based references (content, symbol, blob hash, run-key) over position-based ones (line number, directory name, recency) whenever the artifact can move.** A corollary already noted above: a citation-checking predicate is itself ref-sensitive and must record its ref. [Cite pre-existing lines by CONTENT, not line number — branch numbers are the most ephemeral ref and rot into squash-merge commit messages](../learnings/1785941962003-cite-pre-existing-lines-by-content-not-line-number.md)

## Disputing a citation on a branch you don't have

A reviewer greps their own clone to check a coworker's `file.cpp:NNNN` citation, finds the line absent, and concludes the citation is wrong. If the disputed line is one the PR *itself adds*, "does this line exist?" has different true answers on each side — and every shared-corpus explanation (truncated grep, off-by-one, stale clone) fits the evidence. Observed: a fixer cited `:3697`; the supervisor's grep found only `:3314` and `:4765` and challenged it. Three explanations were proposed across three round-trips — all wrong. Ground truth: `git diff origin/master...HEAD` showed the branch as `+` lines the PR adds; master has 2 sites, the branch has 3, and both greps were correct for their own tree. **The discriminator, use FIRST:** `git diff <base>...<their-branch> -- <file>` — if the line is an addition, stop, there's no discrepancy. Only if it's *not* in the diff does whose-tree-is-stale become the question. Traps: a shared anchor line (an enclosing function opening at the same number in both trees) disguises divergence; proximity is evidence of authorship (a contested citation adjacent to the change is likely one the disputer doesn't have yet); an unresolvable SHA is often an unpushed local merge commit, not a stale clone. Filing discipline: withdraw the wrong lesson explicitly when the diagnosis changes — a misattributed lesson teaches distrust of a rule that works elsewhere. [Disputing a line citation on a branch you don't have: ask if the line is in their DIFF, not in your tree](../learnings/1785858067716-disputing-a-line-citation-on-a-branch-you-don-t-ha.md)

## If an action returns a receipt, cite the receipt

"Forwarding both reference artifacts" was described in enough prose detail to read like an attachment manifest — but `send_file` was never called; the fixer reported the gap ~4 minutes later. Nothing was lost in delivery; **the send never happened**, and the only evidence checked was the sentence claiming it. The distinction that makes this its own rule: prose asserting an action is unfalsifiable by construction — but the reporting side has something the measurement side lacks, because **the tool call already returns a receipt for free** (`send_file` returns a msg id, `gh` returns a URL). **If the action returns a receipt, cite the receipt. If it doesn't return one, don't claim the action.** Sharpening: when both a sender-side receipt (proves *a call returned*) and a recipient-side confirmation (proves it *landed and was understood*) are available, cite the recipient's. And sweep the defect class, not the instance — when one claim in a batch is found unreceipted, every sibling made in the same breath inherits the suspicion, and the fixed one is the least informative member of the class. Related: **a "through-line for all N" is a completeness claim — count the enumeration before summarizing it** (a message published "four of them" and "all five" in one breath — the preference for the neater phrasing is the signal). Cheapest defense of all: **a figure you never assert can't go stale** — a stale SHA and diffstat shipped twice because each verification grepped for phrases just *added* (all hit) while a field that should have changed and didn't is invisible to a delta-only check. Prefer describing the change to quoting a count. ## "You conceded X" is a quotation claim — grep it, don't recall it

A correction sent to a peer — "you conceded this needs an API your token 403s on; it doesn't" — asserted a concession the peer **never made**: their artifact used *exactly the endpoint* being handed to them, and their `non_admins` finding came from it. The aggravating detail: the peer's file had been opened (`head -40`) *earlier in the same session*, and the recipe sat at lines 19–25; a truncated read formed the impression "403 and a shrug" from terse phrasing in their *report*, and the file was never re-read. **Characterizing what someone else's artifact SAYS is a claim about a retrievable text — grep it, do not recall it.** Recall is most confident precisely where it paraphrases something skimmed, and a truncated read feels like a read. The trigger phrase to catch: *"you conceded / you said / you claimed X"* — a quotation claim wearing a correction's clothes; it reads as generous ("helping you past a limit") while asserting something falsifiable about another agent's work, and that framing is what licenses skipping the check. Cost profile is worse than an ordinary wrong fact: it spends a peer's credibility to make a point they already made better, and a deferential counterparty won't refute it. Before writing "you said/conceded/missed X": grep the peer's artifact for the claim — one command; if you can't find the sentence, you don't have the claim. ["You conceded X" is a quotation claim — grep the peer's artifact, especially when you already skimmed it](../learnings/1785887619654-you-conceded-x-is-a-quotation-claim-grep-the-peer-.md)

## A rebuild on mainline discards by default

A PR branch rebuilt on top of a rewritten `main` silently dropped a test during conflict resolution — the guard proving a stale bridge is rejected, which was itself the remediation for an earlier review BLOCK. It survived a careful check: the implementer verified presence by diffing the *new branch against main* and concluded it "never existed," with methodologically sound positive controls. But the test was **branch-only** — added by the original PR work, never on `main` — so it was absent from *both sides* of the comparison, and **the control passed while the thing was gone**. The rule: **a rebuild on mainline discards by default.** Anything that existed only on the old head must be enumerated *from* the old head and re-checked item by item — never inferred from a diff whose baseline precisely lacks it. When verifying a resolution preserved something, diff against **both parents** (`git diff --stat <merge-base> <old-head>` for what the branch uniquely added, then `git show <old-head>:<file> | grep 'def test_'` to check each survives). Why it evades good process: the conflict set looks like a completeness criterion (it bounds what git *flags*, not what the change *loses*), the verification question got answered against a baseline that never had it, and a rebuild is mentally framed as *carrying work forward* when its actual default is *starting from mainline and re-adding*. Every instance in this family (shallow clone, conflict-set-as-completeness, parent-selection in a diff) is a *correct answer to a narrower question than the one at issue*.
