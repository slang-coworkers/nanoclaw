# Slang capability-check scope and the blast radius of core-intrinsic changes

When Slang's capability and stage checks fire (per function, per auto-discovered entry point, per session target); how changing the body of a public core-module intrinsic (adding a barrier, a `__stage_switch`, or a `__target_switch` case) breaks callers that compiled before; what happens when a gate is missing; and the E36120 nesting rule for same-target `__target_switch` cases. How `[require]` propagates through referenced declarations is on [Slang capability inference](slang-language-core-capability-inference.md).

## TL;DR

- **E36100/36101/36102 (conflicting capability) fire eagerly per function at `CapabilityChecked`, not per reachable entry point.** A never-called helper that calls a wgsl-only and a spirv-only function breaks every compile of its module (any `-entry`, any `-target`, even `-o x.slang-module`); importers get E39999. `-ignore-capabilities` suppresses it, `-restrictive-capability-check` does not. Fix: move the dispatch into the helper with `__target_switch`, a satisfiable disjunction.
- **`ISession::loadModule` validates every auto-discovered entry point against every session target.** With no explicit entry points, every `[shader]` function (and bare `[numthreads]` on non-CUDA targets) goes through `validateEntryPoint` over `linkage->targets`; E36107 is fatal and `loadModule` returns null, as does slangc without `-entry`. Since #13848 (2026-10-30) the check reads the TARGET option set, so IgnoreCapabilities in that target's `TargetDesc` silences it for that target only; the suppressed target can still emit invalid code with no error.
- **slangc has no per-target scope for capability or warning options**, and `loadModule`'s sink uses only the session set, so session-vs-target option bugs need a `slang-unit-test`.
- **When a public core-module function's body starts calling something with a stronger `[require]`, that is a source break.** Callers annotated only with a bare target (`[require(spirv)]`) newly get E36104. Test a bare-target caller on old and new binaries; label the PR `pr: breaking change`.
- **A barrier's `[require(..., memorybarrier)]` carries no stage.** Adding a workgroup barrier to a stage-agnostic intrinsic silently emits invalid fragment/vertex code (SPIR-V `OpControlBarrier` exits 0 unless validation is on). Wrap it in `__stage_switch { case compute: case _mesh: case _amplification: ...; default: ... }`. A barrier form in `default:` needs explicit CPU cases (`c`, `cpp`, `llvm`, `slangvm`).
- **`specializeStageSwitch` only touches functions an entry point or CUDA kernel reaches.** An unrooted `[CudaDeviceExport]` caller keeps `GetCurrentStage` and hits E99999 at emit; probe one whenever you add a `__stage_switch` to a core function.
- **`-target slangvm` has an empty target capability set.** Any reached `__target_switch` without `default:` gives E41011, even from a dead case. Inverting the switch does not help; adding slangvm to `getTargetCaps` breaks the INTERPRET suite.
- **A missing `[require]` lets an unsupported shape reach the emitter.** `Ptr<T>` ops have none, so user pointers on HLSL/WGSL emit invalid code or ICE on `nullptr` (no `PtrLit` case). Fix it with an upstream capability or IR check, not an emitter case.
- **An IR check walking a type's use list must also walk `RateQualified` wrappers (`@ConstExpr`) and must not report values only debug info keeps alive under `-g`.** Do not predict the emitter's fold rule (three such rules failed on #13856): remove side-effect-free debug-only values (users first, then DCE) before `collectMetadata`. Probe bool and `let` locals, multi-use values, pure chains, module-scope consts and side-effecting calls under `-g` and `-g -O0`.
- **A struct's `[require]` does not cover its `extension` blocks**, and capability checking skips property accessors. `Atomic<T>` ops reach emit on cpp/llvm (E99999/E99997, #14183); per-method `[require]` fails the core module (E36108, `atomic_reduce` includes cpp/llvm). CUDA/Torch emitters do not delegate to `CPPSourceEmitter`.
- **`cuda_sm_N_M` aliases also admit hlsl, glsl, metal, wgsl and cpp**; write `[require(cuda, cuda_sm_8_0)]` to restrict to CUDA, and tighten every dependent `[require]` too or the bootstrap fails.
- **Before calling a target "already broken on master", compile a minimal entry point**, not the PR's test file.
- **Prototype a requested intrinsic as a user-level `__target_switch` function** before touching the core module; never mark a void hint `[__readNone]`, or DCE deletes it.
- **Two `__target_switch` cases for the same target must have nested capability sets, or the core module fails with E36120.** A case's set includes the `[require]` of free helpers and non-generic static members it calls, not of GENERIC static members. `case hlsl:` also serves `hlsl_nvapi`, so put an NVAPI arm in a free helper with its own `[require]`. Revert-drill a reviewer's "just reuse/split" suggestion before forwarding it.

## Conflicting capabilities are checked per function, eagerly (E36100)

`_propagateRequirement` (slang-check-decl.cpp ~:21880) emits E36100/E36101/E36102 the first time a function's inferred capability set becomes invalid during semantic checking (`DeclCheckState::CapabilityChecked`), when the checker has no entry-point or reachability information. Consider a helper nobody calls:

```slang
[require(wgsl)]  uint wgslOnly(uint i);
[require(spirv)] uint spirvOnly(uint i);
uint helper(uint i) { return wgslOnly(i) + spirvOnly(i); }
```

Every compile of the module fails, whatever the `-entry` or `-target`, and importers get E39999; `__target_switch` is not the trigger (plain `[require]` callees do the same), and only `-ignore-capabilities` suppresses it. The clean workaround moves the dispatch into the helper, `__target_switch { case wgsl: return wgslOnly(i); case spirv: return spirvOnly(i); }`, a satisfiable disjunction. Side trap: `case spirv: __intrinsic_asm "Op..."` ICEs (E99997 "Unhandled local inst in spirv-emit"); the working form is `spirv_asm { result:$$uint = OpIAdd $i $i; }` [E36100 is eager per-function, not reachability-scoped](../learnings/1792071882191-e36100-conflicting-capability-is-eager-per-functio.md).

## `loadModule` validates every discovered entry point against every target (E36107)

`FrontEndCompileRequest::checkEntryPoints` (slang-check-shader.cpp ~:3228) validates only the explicit entry points when any exist (slangc `-entry`); otherwise `Module::_discoverEntryPoints` finds them. `ISession::loadModule` never has explicit requests, so every `[shader]` function, and every bare `[numthreads]` function on non-CUDA targets, goes through `validateEntryPoint`, which loops over `linkage->targets` (~:2552) and raises E36107 as a hard error; `loadSourceModuleImpl` then returns nullptr.

So a SPIR-V+WGSL session fails `loadModule` when one kernel is WGSL-incompatible, as does slangc without `-entry`. Since #13848 (merge 24285eecf, 2026-10-30) `validateEntryPointCapabilities` reports E36107 with `target->getOptionSet()` instead of `linkage->m_optionSet`, so IgnoreCapabilities in `TargetDesc::compilerOptionEntries` now silences it for that target only (the target set still inherits a session-level option). Verified on master 04d2726db with the #13638 repro: with the option on the WGSL target only, `loadModule` succeeds and both kernels compile for both targets; on the SPIR-V target only, `loadModule` still returns nullptr. Notes from before 2026-10-30 that say per-target IgnoreCapabilities "does not help" are outdated ([per-target IgnoreCapabilities silences E36107 since #13848](../learnings/1793884113467-per-target-ignorecapabilities-silences-e36107-sinc.md)). Suppression is not validity: either way (per-target or session-wide IgnoreCapabilities) WGSL for `RWByteAddressBuffer.InterlockedAdd` is `atomicAdd` on a plain `array<u32>`, which is invalid and is emitted with no error. Three verified workarounds: `RWStructuredBuffer<Atomic<uint>>` with `.add()`; an `#if` around the kernel with the macro set only in the WGSL session's `SessionDesc::preprocessorMacros`; or a separate module for the incompatible kernels [loadModule validates every auto-discovered entry point against every session target](../learnings/1792071692150-loadmodule-validates-every-auto-discovered-shader-.md).

**Session-versus-target option bugs can only be tested through the API (#13847, #13853).** slangc puts `-ignore-capabilities`, `-Wno-<id>`, `-warnings-disable` and `-W<id>` on the session option set (`slang-options.cpp` ~2960/2977, ~3228-3260), with no per-target scope. Two targets cannot differ either: two `-target hlsl` with different profiles give E00041, hlsl+glsl with different stages E00031. So a check reading the session set instead of the target set (E36107 until #13848, E36112 in #13853) needs a `slang-unit-test`, not a `.slang` test. Warnings split the same way: `Linkage::loadModule*` builds its DiagnosticSink only from the session set (`slang-session.cpp:208/255`), so `DisableWarning(s)` in `TargetDesc::compilerOptionEntries` does not silence a front-end warning such as E36112, while the same entry in `SessionDesc` does. Per-target IgnoreCapabilities is a different mechanism, because `maybeDiagnose` reads whichever option set it is passed. A quick harness: `g++ -std=c++17 x.cpp -I slang/include -L build/Debug/lib -lslang-compiler -Wl,-rpath,build/Debug/lib`, then `loadModuleFromSourceString` and count codes in the diagnostics blob [slangc has no per-target warning or IgnoreCapabilities options; TargetDesc warning disables miss loadModule](../learnings/1792686161044-slangc-cannot-express-per-target-ignorecapabilitie.md).

## Adding a barrier to a stage-agnostic core intrinsic

One change produced two independent failures: PR #13659 (for #13631) made `workgroupUniformLoad` in hlsl.meta.slang call `GroupMemoryBarrierWithGroupSync()` in its `default:` case.

**Capability side.** The barrier is `[require(cuda_glsl_hlsl_metal_spirv_wgsl, memorybarrier)]`, and inference propagates `memorybarrier` (sm_5_0_version: spirv_1_0 / _GLSL_330 / _cuda_sm_6_0 by target) to every caller. A user function annotated only `[require(spirv)]`, `[require(glsl)]`, `[require(cuda)]` or `[require(hlsl, compute)]` now fails with E36104 "uses undeclared capability", although master compiled it; `[require(spirv, memorybarrier)]` fixes the caller, and unannotated callers are unaffected. This is a source break, so the PR takes `pr: breaking change`; test a bare-target caller on old and new binaries before choosing the label. Because the barrier has no CPU case, a barrier form in `default:` (the fallback rather than a GPU allowlist) also needs `case c: case cpp: case llvm: case slangvm: return v;` [a core intrinsic that calls a barrier inherits its capability](../learnings/1792078114722-a-core-module-intrinsic-that-newly-calls-a-barrier.md).

**Stage side.** `memorybarrier` carries no stage, so capability checking cannot see that fragment and vertex callers now emit `OpControlBarrier Workgroup`. That SPIR-V is invalid (VUID-04682, 04637, 07321), yet slangc exits 0 unless `SLANG_RUN_SPIRV_VALIDATION=1` is set; DXC rejects ps_6_0 ("sync in a non-Compute/Amplification/Mesh/Node Shader"), and Metal gets `threadgroup_barrier` in a vertex function. Check one fragment and one vertex caller with SPIR-V validation on and with `-target dxil -profile ps_6_0`. The working fix wraps the barrier form in `__stage_switch { case compute: case _mesh: case _amplification: <barriers>; default: <plain form>; }`: fragment and vertex callers validate, mesh keeps both barriers, FileCheck lanes pass. Prior art: `__targetHasImplicitDerivatives` in hlsl.meta.slang [a core intrinsic that gains a workgroup barrier breaks non-compute callers](../learnings/1792082137751-a-core-module-intrinsic-that-gains-a-workgroup-bar.md).

## `__stage_switch` and unrooted exports (E99999)

`specializeStageSwitch` (slang-ir-specialize-stage-switch.cpp:136-138) specializes only the stage-specific functions an entry point or CUDA kernel can reach (`buildEntryPointReferenceGraph`). A `[CudaDeviceExport]` function no kernel calls keeps `GetCurrentStage` until emit, where it fails with E99999 "unexpected IR opcode during code emit". The gap predates #13659 (`WaveGetNumWaves` in an export already fails on master, with E41400), but adding a `__stage_switch` to a formerly stage-independent intrinsic exposes it for that intrinsic's callers, so probe an unrooted exported caller whenever you add one.

The same review produced a baseline rule: before calling a target "already broken on master", compile a minimal entry point for it. A host-cpp hang came from the PR's test file rather than the target, and that wrong baseline hid a real host-cpp regression for one round [a __stage_switch in a core intrinsic breaks unrooted CudaDeviceExport callers](../learnings/1792098552809-a-stage-switch-in-a-core-intrinsic-breaks-unrooted.md).

## Empty-capability targets: `slangvm` and E41011

`-target slangvm` (HostVM) has an empty target capability set, because `getTargetCaps` has no HostVM arm, so `case slangvm:` in core-module code is never selected. `specializeTargetSwitch(TargetRequest*, IRModule*)` specializes every function in the linked module, including callees only a dead case references. If any case of a `__target_switch` reaches `GroupMemoryBarrierWithGroupSync`, whose own switch has no `default:`, a slangvm compute entry point gets `E41011 __target_switch has no compatible target with current profile '{}'`.

Moving the barrier into an explicit `case hlsl:` with `default: return v;` does not help, and master reproduces the error with user code. Adding `HostVM→slangvm` to `getTargetCaps` fixes that probe but breaks 7 INTERPRET/slangvm suite tests with E36107, because `any_target` and the other aliases exclude slangvm. Run a probe and the full suite before proposing either change (confirmed on #13659 @3f73000) [inverting a __target_switch does not stop E41011 on slangvm](../learnings/1792087031963-inverting-a-target-switch-does-not-stop-e41011-on-.md).

## A missing gate: user pointers on HLSL/WGSL (#13632)

The reverse failure is a requirement that should exist and does not. On HLSL and WGSL three spellings abort with E99999 because neither emitter has a `case kIROp_PtrLit`: `p != nullptr`, `if (p)` (the peephole turns `CastPtrToBool` into a compare against a `PtrLit`, slang-ir-peephole.cpp:1187), and `static T* g = nullptr`. The cause is upstream: `Ptr<T>` operations in core.meta.slang carry no `[require]`, and no IR check rejects `AddressSpace::UserPointer` (0x100000001) on these targets. Without `nullptr` the same code exits 0 and emits invalid `ptr<, f32>` / `Ptr<float, 0ULL, 4294967297ULL, DefaultLayout >`, so an emitter case would only move the failure. This is not #12386's root cause (legalize-types E99997 on an empty-struct pointee). A check that walks only `IRFunc` bodies misses `PtrLit` uses in `IRGlobalVar` initializers, so walk `IRGlobalValueWithCode`. Worktree build notes from that session: `git submodule update --reference /workspace/agent/slang` fails because the main clone is shallow; copying its `external/*` into the worktree and deleting the copied `.git` gitlink files works; and `SLANG_ENABLE_TESTS=OFF` is required when `SLANG_ENABLE_SLANG_RHI=OFF` [PtrLit nullptr ICE on HLSL/WGSL: UserPointer gate missing](../learnings/1792135032187-ptrlit-nullptr-ice-on-hlsl-wgsl-userpointer-gate-m.md).

**The use-list check and `-g`.** PR #13856's IR check finds values by walking the use list of the hoisted `Ptr(T, UserPointer)` type, and two shapes break that. With `-g` (stripDebugInfo runs only at `-g0`) an otherwise-dead value stays alive because a `DebugValue` uses it; the C-like emitters print no debug insts and fold pure values, so master emits nothing for it, and a check reporting every surviving value fails a valid shader only in debug builds, so add a `-g` directive to such diagnostic tests. A `@ConstExpr` value (e.g. `(float*)16ULL` as a texel offset) has type `RateQualified(ConstExpr, Ptr(...))`, so its `typeUse` points at the wrapper; also walk `IRRateQualifiedType` globals whose `getValueType()` matches. In `//DIAGNOSTIC_TEST` parsing, another prefix's `//X:` or `/*X: */` lines count as source lines for the next prefix, so two prefixes cannot annotate one source line; give each its own line or entry point [IR checks walking a type's use list: -g DebugValue and @ConstExpr RateQualified traps](../learnings/1792641349111-ir-checks-walking-a-type-s-use-list-g-debugvalue-a.md).

**Predicting what the emitter drops does not work.** Three exemption rules modeled on the C-like emitter's fold decision each failed on #13856, letting E99999 through or reporting a valid shader. (1) Skipping transitively through pure users had no visited set (an `x = x*x` chain of 30 took 32 s) and was too wide, because a non-pointer value with more than one use or a use in another block is emitted as a temporary (`shouldFoldInstIntoUseSites`, slang-emit-c-like.cpp ~1745), so `uint64_t x = uint64_t((float*)a); x*=x;` under `-g` still printed `Ptr<...>`; and a side-effecting `[noinline]` call `f(nullptr)` read only by a `DebugValue` went unchecked and hit E99999. (2) "Pure, every use a debug inst, and a non-pointer value has exactly one use in its own block" misses `let b = gp == nullptr;`: lowering puts a `DebugVar` between the comparison and its `DebugValue` (slang-lower-to-ir.cpp ~11833), the fold-safety scan treats it as side-effecting (~1968), and the value is declared, so `bool b` and `let b` differ; it also false-positives at module scope, where a pure value is always folded (~1682) even when its debug use is in another block (`static const bool g = (float*)0 == nullptr;` under HLSL `-g`). (3) "Exempt only `T*`-typed values" (`FoldPolicy::Always` on pointer-less targets, ~1612) reports `static const bool g = (float*)0 == nullptr; let a = g;`.

What worked was making debug-only values disappear. A value is observed only by debug info if it has no side effects and every user is a debug inst or (memoized, recursively) such a value; a value still in progress counts as observed, so use cycles are kept. The pass removes those values with their users, users first, then runs `eliminateDeadCode` so the globals they read (`uniform float*`) go too, all BEFORE `collectMetadata`, or reflection still reports the removed buffer as used (the ordering trap of `usesBindlessResourceHeap` on [probe discipline](slang-compiler-probe-discipline-and-type-naming.md)). `-g` then reports and emits exactly what a non-`-g` build does; pin it with FileCheck `-NOT: Ptr<` under `-g` and a REFLECTION run checking `"used": 0` [for -g, make debug-only values disappear](../learnings/1792675059756-for-g-make-debug-only-values-disappear-instead-of-.md). Rule (2) shipped as a patch inside a reviewer's APPROVE_WITH_NITS and was pushed before a codex cross-check found the holes, so run codex on any verdict that ships a patch, and probe a `-g` exemption with a bool local, a `let` local, two debug uses, a pure chain, a module-scope const and a side-effecting call, each under `-g` and `-g -O0` [probe let locals and module-scope consts before proposing a -g exemption](../learnings/1792670333058-before-proposing-a-g-debug-only-exemption-rule-in-.md).

**The same gap hides behind an `extension`.** `struct Atomic<T>` carries `[require(cuda_glsl_hlsl_metal_spirv_wgsl)]` (`core.meta.slang:4188`), so its struct-body methods (load/store/exchange/compareExchange) give a clean E36107 on cpp and llvm, but the two `extension Atomic<T>` blocks (:4223 add/sub/min/max/reduce*, :4304 and/or/xor/inc/dec) do not repeat it, and their calls reach emit. At 6815ed82d, on cpp, shader-sharedlib and `-cpu`, only integer `add` and its wrappers (`reduceAdd`, `+=`) compile (to `_slang_atomic_add_*`); every other op/type is E99999 via `diagnoseUnhandledInst`, the LLVM CPU targets (`-target llvm-ir`, `host-object-code`) give E99997 for every extension op, and SPIR-V float/half/double `sub` is E99997 (#14173). Before accepting "X works on target T", run the census over methods × element types × the three storage forms (pointer, `RWStructuredBuffer`, groupshared), wrappers and compound operators included [Atomic<T> extension methods escape the struct [require]](../learnings/1793628220654-atomic-t-extension-methods-escape-the-struct-requi.md). Per-method `[require]` is not the whole front-end fix: putting `[require(cuda_glsl_hlsl_metal_spirv_wgsl)]` on sub/min/max/and/or/xor/increment/decrement fails the core-module build with E36108, because the `reduce*` wrappers carry `[require(atomic_reduce)]` and `atomic_reduce` includes `cpp` and `llvm` (`slang-capabilities.capdef:2282`). It needs an `atomic_reduce` split, and an emitter backstop (#14189's E55204) is still needed for type-dependent cases (float `add`), plain assignment to an `Atomic<T>` lvalue (lowers straight to `atomicStore`) and property accessors. A `[require(hlsl)]` function called from a getter compiles for spirv with no error, while a direct call gives E36107; the hypothesis is that `visitPropertyDecl` (`slang-check-decl.cpp:23053`) does not join the accessors' requirements into the `PropertyDecl` [emit-time diagnostics; Atomic<T> per-method [require] breaks core module](../learnings/1793634108094-emit-time-diagnostics-emitted-source-is-discarded-.md).

An independent probe on PR #14189 found the accessor gap from the GLSL side: `[require(hlsl)] uint f()` called from `property uint v { get { return f(); } }` compiles to GLSL with rc 0, while the call from an ordinary method gives E36107. So even the struct-body `Atomic<T>` methods reach the cpp emitter from an accessor; test that path before calling an emitter branch dead because "the capability check rejects it earlier". Two emitter facts decide where a backstop can live: `IRAtomicOperation` is the shared IR base of all 13 atomic ops, so one `as<IRAtomicOperation>(inst)` covers them; and `CUDASourceEmitter` and `TorchCppSourceEmitter` override `tryEmitInstStmtImpl` and return false at their default without delegating to `CPPSourceEmitter`, so a CPP-emitter diagnostic affects only cpp, shader-sharedlib and host-callable [property accessors skip capability checking; CUDA/Torch emitters don't delegate](../learnings/1793631988724-slang-property-accessors-skip-capability-checking-.md).

**A `[require]` can gate less than its name says.** In `slang-capabilities.capdef`, `cuda_sm_6_0 = _cuda_sm_6_0 | cuda_sm_5_0 | sm_4_1` and `cuda_sm_2_0 = ... | sm_4_0`, so every `cuda_sm_N_M` alias also allows hlsl, glsl, metal, wgsl and cpp; restrict to CUDA with `[require(cuda, cuda_sm_8_0)]`, as `hlsl.meta.slang`'s `[require(cuda, cuda_sm_6_0)]` does. Tightening a core type this way has blast radius: changing only BFloat16/FloatE4M3/FloatE5M2 in `core.meta.slang` to `[require(cuda, cuda_sm_8_x)]` (for #14159) fails the bootstrap with E36101/E36104/E36108, because the `extension CoopMat<BFloat16,...> : IArithmetic` methods (`hlsl.meta.slang` ~32190) use `[require(cuda_sm_8_0, cooperative_matrix)]`, `cooperative_matrix` includes `_sm_6_10 | metal`, and their `default:` static_assert arm references BFloat16. Changing those 9 requires to `[require(cuda, cuda_sm_8_0, cooperative_matrix)]` lets the build pass; bf16/fp8 on metal, hlsl, wgsl, glsl and cpp then report E36107 instead of compiling silently or failing with E99999, with no regressions in the related test suites on an L40S [`[require(cuda_sm_X_Y)]` is not CUDA-only](../learnings/1793616080352-slang-require-cuda-sm-x-y-is-not-cuda-only-tighten.md).

## Probing a requested intrinsic with a user-level `__target_switch` prototype

A request for a new core-module intrinsic can be tested without building Slang. Write it as a user-level function, `__target_switch { case spirv: spirv_asm { OpCapability X; OpExtension "..."; OpFoo $c }; case glsl: __requireTargetExtension("GL_..."); __intrinsic_asm "foo($0)"; case cuda: __intrinsic_asm "..."; default: return; }`, and compile it with the release slangc for every target under `SLANG_RUN_SPIRV_VALIDATION=1`. `spirv_asm` accepts any opcode in the embedded SPIRV-Headers grammar, so this shows whether "no IR or emitter change needed" is true. Opt-in gating is expressible today: `case <capatom>:` plus `default: return;` emits the capability only with `-capability <capatom>`. DCE pitfall: marking a void hint `[__readNone]` makes the call side-effect-free and DCE deletes it on every target. `spirv_asm` and GenericAsm count as side-effecting, an empty default body is inferred NoSideEffect, and argument side effects survive. An unknown `[[attr(...)]]` before a statement is only warning E31000 [probe intrinsic requests with a __target_switch prototype](../learnings/1792138323224-probe-new-spir-v-glsl-cuda-intrinsic-requests-with.md).

## Same-target `__target_switch` cases must nest (E36120)

Adding a multi-target function to `hlsl.meta.slang` (the SER fused `ReorderExecute` family, #13774 / #13785) runs into the core-module checker (slang-check-decl.cpp ~:22240-22400, `mergeNewCapability`/`compatibleMerge`). Two `__target_switch` cases for the SAME target, such as `spvShaderInvocationReorderNV` and `spirv`, must have nested capability sets, or the build fails with E36120 "capability cases conflict". A case's set is the case atom joined with the `[require]` of what its body calls, and revert drills settled which callees join [same-target cases need nested caps](../learnings/1792513930682-core-module-target-switch-same-target-cases-need-n.md), [the checker drops [require] only for generic static members](../learnings/1792523053545-slang-capability-checker-drops-require-only-for-ge.md):

- **A free function's `[require]` joins the case, and so does a non-generic static member called as `HitObject::name`.** A GENERIC static member's does not: moving a generic `spirv_asm` helper into `extension HitObject` breaks the core-module build with E36120 and E36104, because `visitStaticMemberExpr` never reaches `processDeclModifiers` for a `GenericAppDeclRef` (the inference gap on [Slang capability inference](slang-language-core-capability-inference.md)). Put generic target-specific helpers at file scope. (The first atom blamed static members in general; the later drill narrowed it to generic ones.)
- **`case hlsl:` also serves `hlsl_nvapi` targets.** `case hlsl_nvapi:` next to a DXR-only `case hlsl:` body, even an inline `static_assert(false, ...)`, gives E36120. Wrapping the NVAPI arm in a free helper with `[require(nvapi, ser_raygen)]` fixes it, as does one helper whose own switch lists `hlsl_nvapi` before `hlsl` (like `__hlslTraceRay`). Splitting the cases to call the two existing `HitObject::Invoke` overloads gives E41011 on DXR sm_6_9 and silently upgrades the profile to `hlsl_nvapi`; one free helper with both `[require(nvapi,…)]` and `[require(hlsl, ser_dxr_…)]` is needed.
- **A case that calls a stronger callee changes which case wins.** If an NV-sequence case calls a motion-only callee, wrap the sequence in a free helper with `[require(cuda_glsl_spirv, ser_motion_raygen)]` so plain `spvShaderInvocationReorderNV` still precedes `case spirv`. Otherwise NV targets silently pick the EXT case (NV ⊇ EXT) and emit an EXT op on `OpTypeHitObjectNV` (spirv-val: "Type must be OpTypeHitObjectEXT").
- **Prototype in a test file first.** The user-code checker is the same, so try the function and helpers in a `.slang` file against the existing slangc before the ~8 minute core-module rebuild.
- **Revert-drill a reviewer's simplification before forwarding it.** On #13785 both the correctness reviewer and the clarity pass proposed "reuse the existing helper / split the cases", and neither compiles.

The same PR found two runtime limits on the L40S render-test harness: with `-vk -rt`, HitObject TraceRay→Reorder→Invoke loses the device on both the EXT and the all-NV module (plain `TraceRay` and a NOP `ReorderExecute` pass); with `-cuda -rt`, OptiX rejects `optixInvoke` with "0 payload values configured", even for the pre-existing sequence [the checker drops [require] only for generic static members](../learnings/1792523053545-slang-capability-checker-drops-require-only-for-ge.md).
