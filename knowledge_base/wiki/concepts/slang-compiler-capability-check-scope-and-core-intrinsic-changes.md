# Slang capability-check scope and the blast radius of core-intrinsic changes

When Slang's capability and stage checks fire; how changing a public core-module intrinsic's body (a barrier, a `__stage_switch`, a `__target_switch` case) breaks callers that compiled before; missing gates; and the E36120 same-target nesting rule. How `[require]` propagates through referenced declarations is on [Slang capability inference](slang-language-core-capability-inference.md).

## TL;DR

- **E36100/36101/36102 (conflicting capability) fire eagerly per function at `CapabilityChecked`, not per reachable entry point**: a never-called helper calling a wgsl-only and a spirv-only function breaks every compile of its module. Only `-ignore-capabilities` suppresses it; fix with a `__target_switch` in the helper.
- **`ISession::loadModule` validates every auto-discovered entry point against every session target** (fatal E36107), as does slangc without `-entry`. Since #13848 (2026-10-30) a target's own IgnoreCapabilities silences it for that target only — which can still emit invalid code with no error.
- **slangc has no per-target scope for capability or warning options**, and `loadModule`'s sink uses only the session set: session-vs-target option bugs need a `slang-unit-test`.
- **A public core-module function that starts calling something with a stronger `[require]` is a source break**: bare-target callers (`[require(spirv)]`) get E36104. Test one on old and new binaries; label `pr: breaking change`. Inside the core module, `asuint`/`asfloat` pull in `shader5_sm_4_0` (bootstrap E36104); use `bit_cast`.
- **A barrier's `memorybarrier` requirement carries no stage**, so a workgroup barrier in a stage-agnostic intrinsic silently emits invalid fragment/vertex code: wrap it in `__stage_switch { case compute: case _mesh: case _amplification: ...; default: ... }`. A barrier form in `default:` needs CPU cases (`c`, `cpp`, `llvm`, `slangvm`).
- **`specializeStageSwitch` only touches functions an entry point or CUDA kernel reaches**: an unrooted `[CudaDeviceExport]` caller hits E99999; probe one whenever you add a `__stage_switch`.
- **`-target slangvm` has an empty capability set**: a reached `__target_switch` without `default:` gives E41011, even from a dead case.
- **A missing `[require]` lets an unsupported shape reach the emitter** (`Ptr<T>` on HLSL/WGSL): fix with an upstream capability or IR check, not an emitter case.
- **An IR check walking a type's use list must also walk `RateQualified` (`@ConstExpr`) wrappers and must ignore values only `-g` debug info keeps alive**: remove side-effect-free debug-only values (users first, then DCE) before `collectMetadata` instead of predicting the emitter's fold rule; probe the `-g` matrix under `-g` and `-g -O0`.
- **A struct's `[require]` does not cover its `extension` blocks, and capability checking skips property accessors** (`Atomic<T>` ops reach emit on cpp/llvm, #14183); per-method `[require]` fails the core module (E36108).
- **`cuda_sm_N_M` aliases also admit hlsl, glsl, metal, wgsl and cpp**: write `[require(cuda, cuda_sm_8_0)]` and tighten every dependent `[require]`.
- **Before calling a target "already broken on master", compile a minimal entry point**, not the PR's test file.
- **Prototype a requested intrinsic as a user-level `__target_switch` function**; never mark a void hint `[__readNone]` (DCE deletes it).
- **Same-target `__target_switch` cases must have nested capability sets, else E36120.** A case's set includes the `[require]` of free helpers and non-generic static members it calls, not GENERIC static members; `case hlsl:` also serves `hlsl_nvapi`. Revert-drill a reviewer's "just reuse/split" suggestion before forwarding it.

## Conflicting capabilities are checked per function, eagerly (E36100)

`_propagateRequirement` (slang-check-decl.cpp ~:21880) emits E36100/E36101/E36102 when a function's inferred set first becomes invalid at `DeclCheckState::CapabilityChecked`, with no entry-point or reachability information. Consider a helper nobody calls:

```slang
[require(wgsl)]  uint wgslOnly(uint i);
[require(spirv)] uint spirvOnly(uint i);
uint helper(uint i) { return wgslOnly(i) + spirvOnly(i); }
```

Every compile of the module fails, whatever the `-entry` or `-target` (even `-o x.slang-module`), and importers get E39999; plain `[require]` callees trigger it too; `-ignore-capabilities` suppresses it and `-restrictive-capability-check` does not. Move the dispatch into the helper: `__target_switch { case wgsl: return wgslOnly(i); case spirv: return spirvOnly(i); }`, a satisfiable disjunction. Side trap: `case spirv: __intrinsic_asm "Op..."` ICEs (E99997); use `spirv_asm { result:$$uint = OpIAdd $i $i; }` [E36100 is eager per-function](../learnings/1792071882191-e36100-conflicting-capability-is-eager-per-functio.md).

## `loadModule` validates every discovered entry point against every target (E36107)

`FrontEndCompileRequest::checkEntryPoints` (slang-check-shader.cpp ~:3228) validates only explicit entry points when any exist (slangc `-entry`), else those `Module::_discoverEntryPoints` finds. `ISession::loadModule` has no explicit requests, so every `[shader]` function (and bare `[numthreads]` off CUDA) goes through `validateEntryPoint`, looping over `linkage->targets` (~:2552); E36107 is fatal and `loadSourceModuleImpl` returns nullptr. One WGSL-incompatible kernel thus fails a SPIR-V+WGSL session's `loadModule`.

Since #13848 (merge 24285eecf, 2026-10-30) `validateEntryPointCapabilities` reports with `target->getOptionSet()` instead of `linkage->m_optionSet`, so IgnoreCapabilities in `TargetDesc::compilerOptionEntries` silences E36107 for that target only (the target set still inherits a session-level option). On master 04d2726db with the #13638 repro, the option on the WGSL target alone lets `loadModule` succeed; on the SPIR-V target alone it still returns nullptr. Notes from before 2026-10-30 saying per-target IgnoreCapabilities "does not help" are outdated ([per-target IgnoreCapabilities since #13848](../learnings/1793884113467-per-target-ignorecapabilities-silences-e36107-sinc.md)). Suppression is not validity: either way, WGSL for `RWByteAddressBuffer.InterlockedAdd` is `atomicAdd` on a plain `array<u32>`, invalid, with no error. Verified workarounds: `RWStructuredBuffer<Atomic<uint>>` with `.add()`; an `#if` around the kernel with the macro set only in the WGSL session's `SessionDesc::preprocessorMacros`; or a separate module for the incompatible kernels [every entry point × every target](../learnings/1792071692150-loadmodule-validates-every-auto-discovered-shader-.md).

**Session-versus-target option bugs need the API (#13847, #13853).** slangc puts `-ignore-capabilities`, `-Wno-<id>`, `-warnings-disable` and `-W<id>` on the session option set (`slang-options.cpp` ~2960/2977, ~3228-3260), and two targets cannot differ (two `-target hlsl` with different profiles give E00041, hlsl+glsl with different stages E00031), so a check reading the session set instead of the target set (E36107 until #13848, E36112 in #13853) needs a `slang-unit-test`. `Linkage::loadModule*` builds its DiagnosticSink only from the session set (`slang-session.cpp:208/255`), so `DisableWarning(s)` in `TargetDesc::compilerOptionEntries` does not silence a front-end warning such as E36112, while the same entry in `SessionDesc` does; per-target IgnoreCapabilities differs because `maybeDiagnose` reads whichever option set it is passed. Harness: `g++ -std=c++17 x.cpp -I slang/include -L build/Debug/lib -lslang-compiler -Wl,-rpath,build/Debug/lib`, then `loadModuleFromSourceString` and count codes in the diagnostics blob [session-only option scope](../learnings/1792686161044-slangc-cannot-express-per-target-ignorecapabilitie.md).

## Adding a barrier to a stage-agnostic core intrinsic (#13659)

PR #13659 (for #13631) made `workgroupUniformLoad` in hlsl.meta.slang call `GroupMemoryBarrierWithGroupSync()` in its `default:` case, which caused two independent failures.

**Capability side.** The barrier is `[require(cuda_glsl_hlsl_metal_spirv_wgsl, memorybarrier)]`, and inference propagates `memorybarrier` (sm_5_0_version) to every caller, so a user function annotated only `[require(spirv)]`, `[require(glsl)]`, `[require(cuda)]` or `[require(hlsl, compute)]` now gets E36104 "uses undeclared capability" (`[require(spirv, memorybarrier)]` fixes it; unannotated callers are unaffected). That is a source break: test a bare-target caller on old and new binaries and label `pr: breaking change`. The barrier has no CPU case, so a barrier form in `default:` (the fallback rather than a GPU allowlist) also needs `case c: case cpp: case llvm: case slangvm: return v;` [barrier capability is inherited](../learnings/1792078114722-a-core-module-intrinsic-that-newly-calls-a-barrier.md). The same inheritance breaks the core module itself: a core-module method that calls `asuint`/`asfloat` picks up `shader5_sm_4_0` (`GL_ARB_gpu_shader5`), and if the method's `[require]` does not declare it, the bootstrap fails with E36104. `bit_cast<uint>(x)` / `bit_cast<float>(u)` carries no capability requirement (precedent: `_NvInterlockedAddFp16x2` in hlsl.meta.slang) ([`asuint` in a core-module method needs `shader5_sm_4_0`](../learnings/1794137172205-exhaustive-diagnostic-test-annotate-both-the-error.md)).

**Stage side.** `memorybarrier` carries no stage, so capability checking cannot see fragment and vertex callers now emitting `OpControlBarrier Workgroup`. That SPIR-V is invalid (VUID-04682, 04637, 07321), yet slangc exits 0 unless `SLANG_RUN_SPIRV_VALIDATION=1`; DXC rejects ps_6_0; Metal gets `threadgroup_barrier` in a vertex function. Check a fragment and a vertex caller with SPIR-V validation on and with `-target dxil -profile ps_6_0`. The fix wraps the barrier form in `__stage_switch { case compute: case _mesh: case _amplification: <barriers>; default: <plain form>; }` (fragment and vertex callers validate; mesh keeps both barriers). Prior art: hlsl.meta.slang's `__targetHasImplicitDerivatives` [non-compute callers break silently](../learnings/1792082137751-a-core-module-intrinsic-that-gains-a-workgroup-bar.md).

## `__stage_switch` and unrooted exports (E99999)

`specializeStageSwitch` (slang-ir-specialize-stage-switch.cpp:136-138) specializes only the stage-specific functions an entry point or CUDA kernel can reach (`buildEntryPointReferenceGraph`), so a `[CudaDeviceExport]` function no kernel calls keeps `GetCurrentStage` until emit and fails with E99999 "unexpected IR opcode during code emit". The gap predates #13659 (`WaveGetNumWaves` in an export fails on master with E41400), but adding a `__stage_switch` to a stage-independent intrinsic exposes it to that intrinsic's callers. Baseline rule from the same review: before calling a target "already broken on master", compile a minimal entry point for it — a host-cpp hang came from the PR's test file, and that wrong baseline hid a real host-cpp regression for a round [unrooted CudaDeviceExport](../learnings/1792098552809-a-stage-switch-in-a-core-intrinsic-breaks-unrooted.md).

## Empty-capability targets: `slangvm` and E41011

`-target slangvm` (HostVM) has an empty target capability set because `getTargetCaps` has no HostVM arm, so `case slangvm:` in core-module code is never selected, while `specializeTargetSwitch(TargetRequest*, IRModule*)` specializes every function in the linked module, including callees only a dead case references. If any case reaches `GroupMemoryBarrierWithGroupSync`, whose own switch has no `default:`, a slangvm compute entry point gets `E41011 __target_switch has no compatible target with current profile '{}'`. Moving the barrier into `case hlsl:` with `default: return v;` does not help (master reproduces it with user code). Adding `HostVM→slangvm` to `getTargetCaps` fixes that probe but breaks 7 INTERPRET/slangvm tests with E36107, because `any_target` and the other aliases exclude slangvm. Run a probe and the full suite before proposing either (#13659 @3f73000) [inverting does not stop E41011](../learnings/1792087031963-inverting-a-target-switch-does-not-stop-e41011-on-.md).

## A missing gate: user pointers on HLSL/WGSL (#13632) and the `-g` traps

On HLSL and WGSL three spellings abort with E99999 because neither emitter has a `case kIROp_PtrLit`: `p != nullptr`, `if (p)` (the peephole turns `CastPtrToBool` into a compare against a `PtrLit`, slang-ir-peephole.cpp:1187), and `static T* g = nullptr`. The cause is upstream: `Ptr<T>` operations in core.meta.slang carry no `[require]`, and no IR check rejects `AddressSpace::UserPointer` (0x100000001) on these targets. Without `nullptr` the same code exits 0 and emits invalid `ptr<, f32>` / `Ptr<float, 0ULL, 4294967297ULL, DefaultLayout >`, so an emitter case would only move the failure. (#12386's root cause, legalize-types E99997 on an empty-struct pointee, is different.) A check walking only `IRFunc` bodies misses `PtrLit` uses in `IRGlobalVar` initializers, so walk `IRGlobalValueWithCode`. Worktree notes: `git submodule update --reference /workspace/agent/slang` fails (the main clone is shallow), so copy its `external/*` and delete the copied `.git` gitlinks; `SLANG_ENABLE_TESTS=OFF` is required when `SLANG_ENABLE_SLANG_RHI=OFF` [UserPointer gate missing](../learnings/1792135032187-ptrlit-nullptr-ice-on-hlsl-wgsl-userpointer-gate-m.md).

**The use-list check and `-g`.** PR #13856's IR check walks the use list of the hoisted `Ptr(T, UserPointer)` type. Under `-g` (stripDebugInfo runs only at `-g0`) a `DebugValue` keeps an otherwise-dead value alive; the C-like emitters print no debug insts and fold pure values, so master emits nothing for it, and a check reporting every surviving value fails a valid shader only in debug builds — add a `-g` directive to such diagnostic tests. A `@ConstExpr` value (e.g. `(float*)16ULL` as a texel offset) has type `RateQualified(ConstExpr, Ptr(...))`, so also walk `IRRateQualifiedType` globals whose `getValueType()` matches. In `//DIAGNOSTIC_TEST` parsing, another prefix's `//X:` or `/*X: */` lines count as source lines for the next prefix, so give each prefix its own line or entry point [use-list traps](../learnings/1792641349111-ir-checks-walking-a-type-s-use-list-g-debugvalue-a.md).

**Predicting what the emitter drops does not work**: three exemptions modeled on the C-like emitter's fold decision failed on #13856. (1) Transitive skipping through pure users had no visited set (a 30-long `x = x*x` chain took 32 s) and was too wide: a non-pointer value with several uses or a cross-block use is emitted as a temporary (`shouldFoldInstIntoUseSites`, slang-emit-c-like.cpp ~1745), so `uint64_t x = uint64_t((float*)a); x*=x;` under `-g` still printed `Ptr<...>`, and a side-effecting `[noinline]` `f(nullptr)` read only by a `DebugValue` hit E99999. (2) "Pure, every use a debug inst, and a non-pointer value has one use in its own block" misses `let b = gp == nullptr;` — lowering puts a `DebugVar` between the comparison and its `DebugValue` (slang-lower-to-ir.cpp ~11833), which the fold scan treats as side-effecting (~1968), so `bool b` and `let b` differ — and false-positives at module scope, where a pure value always folds (~1682) even with its debug use in another block (`static const bool g = (float*)0 == nullptr;` under HLSL `-g`). (3) "Exempt only `T*`-typed values" (`FoldPolicy::Always` on pointer-less targets, ~1612) reports `static const bool g = (float*)0 == nullptr; let a = g;`.

What worked was making debug-only values disappear. A value is debug-only if it has no side effects and every user is a debug inst or (memoized, recursively) such a value; in-progress values count as observed, so cycles are kept. Remove those users first, then run `eliminateDeadCode` so the globals they read (`uniform float*`) go too, all BEFORE `collectMetadata`, or reflection still reports the removed buffer as used (the `usesBindlessResourceHeap` ordering trap on [probe discipline](slang-compiler-probe-discipline-and-type-naming.md)). `-g` then reports and emits exactly what a non-`-g` build does; pin it with FileCheck `-NOT: Ptr<` under `-g` and a REFLECTION run checking `"used": 0` [make debug-only values disappear](../learnings/1792675059756-for-g-make-debug-only-values-disappear-instead-of-.md). Rule (2) shipped inside a reviewer's APPROVE_WITH_NITS before a codex cross-check found the holes, so run codex on any verdict that ships a patch, and probe a `-g` exemption with a bool local, a `let` local, two debug uses, a pure chain, a module-scope const and a side-effecting call, each under `-g` and `-g -O0` [-g probe matrix](../learnings/1792670333058-before-proposing-a-g-debug-only-exemption-rule-in-.md).

## Gates that cover less than they appear: `extension` blocks, accessors, `cuda_sm_*`

**`extension` blocks.** `struct Atomic<T>` carries `[require(cuda_glsl_hlsl_metal_spirv_wgsl)]` (`core.meta.slang:4188`), so its struct-body load/store/exchange/compareExchange give a clean E36107 on cpp and llvm, but the two `extension Atomic<T>` blocks (:4223 add/sub/min/max/reduce*, :4304 and/or/xor/inc/dec) do not repeat it, and their calls reach emit. At 6815ed82d on cpp, shader-sharedlib and `-cpu` only integer `add` and its wrappers (`reduceAdd`, `+=`) compile; every other op/type is E99999 (`diagnoseUnhandledInst`); the LLVM CPU targets (`-target llvm-ir`, `host-object-code`) give E99997 for every extension op; and SPIR-V float/half/double `sub` is E99997 (#14173). Before accepting "X works on target T", census methods × element types × the three storage forms (pointer, `RWStructuredBuffer`, groupshared), wrappers and compound operators included [extension methods escape the struct require](../learnings/1793628220654-atomic-t-extension-methods-escape-the-struct-requi.md). Per-method `[require(cuda_glsl_hlsl_metal_spirv_wgsl)]` on sub/min/max/and/or/xor/increment/decrement fails the core-module build with E36108, because the `reduce*` wrappers carry `[require(atomic_reduce)]` and `atomic_reduce` includes `cpp` and `llvm` (`slang-capabilities.capdef:2282`). It needs an `atomic_reduce` split, and an emitter backstop (#14189's E55204) is still needed for type-dependent cases (float `add`), plain assignment to an `Atomic<T>` lvalue (lowers to `atomicStore`) and accessors.

**Property accessors.** A `[require(hlsl)]` function called from a getter compiles for spirv with no error while a direct call gives E36107; the hypothesis is that `visitPropertyDecl` (`slang-check-decl.cpp:23053`) does not join the accessors' requirements into the `PropertyDecl` [per-method require breaks core module](../learnings/1793634108094-emit-time-diagnostics-emitted-source-is-discarded-.md). An independent PR #14189 probe confirmed it from GLSL: `[require(hlsl)] uint f()` called from `property uint v { get { return f(); } }` compiles with rc 0, while a call from an ordinary method gives E36107. So even struct-body `Atomic<T>` methods reach the cpp emitter via an accessor; test that path before calling an emitter branch dead. Where a backstop can live: `IRAtomicOperation` is the shared IR base of all 13 atomic ops, so one `as<IRAtomicOperation>(inst)` covers them; `CUDASourceEmitter` and `TorchCppSourceEmitter` override `tryEmitInstStmtImpl` and return false at their default without delegating to `CPPSourceEmitter`, so a CPP-emitter diagnostic covers only cpp, shader-sharedlib and host-callable [accessors skip capability checking](../learnings/1793631988724-slang-property-accessors-skip-capability-checking-.md).

**`cuda_sm_*` aliases.** In `slang-capabilities.capdef`, `cuda_sm_6_0 = _cuda_sm_6_0 | cuda_sm_5_0 | sm_4_1` and `cuda_sm_2_0 = ... | sm_4_0`, so every `cuda_sm_N_M` alias also allows hlsl, glsl, metal, wgsl and cpp; restrict to CUDA with `[require(cuda, cuda_sm_8_0)]`, as `hlsl.meta.slang`'s `[require(cuda, cuda_sm_6_0)]` does. Changing only BFloat16/FloatE4M3/FloatE5M2 in `core.meta.slang` to `[require(cuda, cuda_sm_8_x)]` (#14159) fails the bootstrap with E36101/E36104/E36108, because the `extension CoopMat<BFloat16,...> : IArithmetic` methods (`hlsl.meta.slang` ~32190) use `[require(cuda_sm_8_0, cooperative_matrix)]`, `cooperative_matrix` includes `_sm_6_10 | metal`, and their `default:` static_assert arm references BFloat16. Changing those 9 to `[require(cuda, cuda_sm_8_0, cooperative_matrix)]` builds, and bf16/fp8 on metal, hlsl, wgsl, glsl and cpp then report E36107 instead of compiling silently or E99999 (no regressions on an L40S) [`cuda_sm_X_Y` is not CUDA-only](../learnings/1793616080352-slang-require-cuda-sm-x-y-is-not-cuda-only-tighten.md).

## Probing a requested intrinsic with a user-level `__target_switch` prototype

Test a new core-module intrinsic request without building Slang: write it as a user-level function, `__target_switch { case spirv: spirv_asm { OpCapability X; OpExtension "..."; OpFoo $c }; case glsl: __requireTargetExtension("GL_..."); __intrinsic_asm "foo($0)"; case cuda: __intrinsic_asm "..."; default: return; }`, and compile it with the release slangc for every target under `SLANG_RUN_SPIRV_VALIDATION=1`. `spirv_asm` accepts any opcode in the embedded SPIRV-Headers grammar, so this tests "no IR or emitter change needed". Opt-in gating is expressible today: `case <capatom>:` plus `default: return;` emits the capability only with `-capability <capatom>`. DCE pitfall: `[__readNone]` on a void hint makes the call side-effect-free and DCE deletes it on every target; `spirv_asm` and GenericAsm count as side-effecting, an empty default body is inferred NoSideEffect, and argument side effects survive. An unknown `[[attr(...)]]` before a statement is only warning E31000 [prototype first](../learnings/1792138323224-probe-new-spir-v-glsl-cuda-intrinsic-requests-with.md).

## Same-target `__target_switch` cases must nest (E36120)

Adding a multi-target function to `hlsl.meta.slang` (SER fused `ReorderExecute`, #13774 / #13785) hits the core-module checker (slang-check-decl.cpp ~:22240-22400, `mergeNewCapability`/`compatibleMerge`): two `__target_switch` cases for the SAME target, such as `spvShaderInvocationReorderNV` and `spirv`, must have nested capability sets, or the build fails with E36120 "capability cases conflict". A case's set is the case atom joined with the `[require]` of what its body calls; revert drills settled which callees join [nested caps](../learnings/1792513930682-core-module-target-switch-same-target-cases-need-n.md), [generic static members only](../learnings/1792523053545-slang-capability-checker-drops-require-only-for-ge.md):

- **A free function's `[require]` joins the case, as does a non-generic static member called as `HitObject::name`; a GENERIC static member's does not.** Moving a generic `spirv_asm` helper into `extension HitObject` breaks the core-module build with E36120 and E36104, because `visitStaticMemberExpr` never reaches `processDeclModifiers` for a `GenericAppDeclRef` (the gap on [Slang capability inference](slang-language-core-capability-inference.md)); keep generic target-specific helpers at file scope. (An earlier atom blamed all static members; a later drill narrowed it.)
- **`case hlsl:` also serves `hlsl_nvapi` targets.** `case hlsl_nvapi:` beside a DXR-only `case hlsl:` body (even an inline `static_assert(false, ...)`) gives E36120. A free NVAPI helper with `[require(nvapi, ser_raygen)]` fixes it, as does one helper whose own switch lists `hlsl_nvapi` before `hlsl` (like `__hlslTraceRay`). Splitting the cases onto the two existing `HitObject::Invoke` overloads gives E41011 on DXR sm_6_9 and silently upgrades the profile to `hlsl_nvapi`; one free helper with both `[require(nvapi,…)]` and `[require(hlsl, ser_dxr_…)]` is needed.
- **A case that calls a stronger callee changes which case wins.** If an NV-sequence case calls a motion-only callee, wrap the sequence in a free helper with `[require(cuda_glsl_spirv, ser_motion_raygen)]` so plain `spvShaderInvocationReorderNV` still precedes `case spirv`; otherwise NV targets silently pick the EXT case (NV ⊇ EXT) and emit an EXT op on `OpTypeHitObjectNV` (spirv-val: "Type must be OpTypeHitObjectEXT").
- **Prototype in a `.slang` test file first** (same checker, existing slangc) before the ~8 minute core-module rebuild.
- **Revert-drill a reviewer's simplification before forwarding it**: on #13785 both the correctness reviewer and the clarity pass proposed "reuse the existing helper / split the cases", and neither compiles.

L40S render-test limits from the same PR: with `-vk -rt`, HitObject TraceRay→Reorder→Invoke loses the device on both the EXT and the all-NV module (plain `TraceRay` and a NOP `ReorderExecute` pass); with `-cuda -rt` OptiX rejects `optixInvoke` with "0 payload values configured", even for the pre-existing sequence [generic static members only](../learnings/1792523053545-slang-capability-checker-drops-require-only-for-ge.md).
