# Slang Backends Spirv 3 Incidents

## TL;DR
- These are dated incident write-ups; each names the PR/issue it came from. Read the section whose subject matches your symptom.
- Recurring shape: a SPIR-V symptom traced upstream to an IR pass, a capability set, or a downstream tool — not to emit.
- Before fixing an emit-side symptom, verify the premise (several entries here record a premise that was false).


## Capability/validation fixes: declare OpCapability inline, test with -target spirv

A `[require]` capability atom does **not** auto-emit `OpCapability` for `spirv_asm` builtin-loads — e.g. `RayCurrentTime()` emitted `BuiltIn CurrentRayTimeNV` but no `OpCapability RayTracingMotionBlurNV`, so spirv-val rejected the module (VUID-...-pCode-08737). Declare the capability **inline** in the `spirv_asm` block ([[require] capability atom does NOT auto-emit OpCapability for spirv_asm builtin-loads — declare it inline](../learnings/1782828754941-require-capability-atom-does-not-auto-emit-opcapab.md)). When writing the regression test for a SPIR-V *validation* fix (missing `OpCapability`/`OpExtension` that spirv-val or `vkCreateShaderModule` rejects), the test must use a real **`-target spirv`** directive so the module is actually validated — a `spirv_asm`-only or `-target spirv-asm` check can pass without exercising validation ([SPIR-V capability/validation fixes need a -target spirv test directive, not just spirv-asm](../learnings/1782833127380-spir-v-capability-validation-fixes-need-a-target-s.md)).

## Signature-derived VariablePointers capability must gate on [noinline], not hasUses()

When declaring a SPIR-V capability from a function's *signature type* (rather than a value/op site), gate it on the function surviving inlining — check `[noinline]` via `findDecoration`, not `hasUses()` — or you over-declare `VariablePointers` for a function that gets inlined away (driver bug #9061) ([Signature-derived SPIR-V VariablePointers must gate on [noinline], not hasUses() (driver bug #9061)](../learnings/1781023718622-signature-derived-spir-v-variablepointers-must-gat.md)).

## [require] atoms don't reach the codegen capability set (SS-class silent divergence)

Entry-point `[require(...)]` capability atoms do **not** update the SPIR-V codegen capability set, so source-level `[require]` silently diverges from what codegen decides — the version path has a partial compensation, bindless has none (#11631, commit 890f8bef5) ([Slang [require] capabilities never reach codegen cap set; version path has a partial compensation, bindless has none](../learnings/1781638061693-slang-require-capabilities-never-reach-codegen-cap.md)). Severity refinement: the `[require]`-drop is a **silent runtime-divergence (SS-class)** that only bites codegen-DECISION paths, not a wrong/invalid-SPIR-V emit ([slang#11631 severity: [require]-drop is a SILENT runtime-divergence (SS-class), and only hits codegen-DECISION caps](../learnings/1781686744418-slang-11631-severity-require-drop-is-a-silent-runt.md)). A `[require]` atom also does not auto-emit `OpCapability` for `spirv_asm` builtin-loads — declare it inline ([[require] capability atom does NOT auto-emit OpCapability for spirv_asm builtin-loads — declare it inline](../learnings/1782828754941-require-capability-atom-does-not-auto-emit-opcapab.md)).

## HitObject SM6.9+NVAPI: verify the premise before fixing (implies()-inert was WRONG)

A cautionary correction chain. First read: on `sm_6_9` + NVAPI SER, `HitObject` codegen emits an invalid mix because `CapabilitySet.implies()` is inert on disjunctive/abstract target caps ([Slang HitObject SM6.9+NVAPI invalid mix — CapabilitySet.implies() is inert on disjunctive/abstract target caps](../learnings/1782986638349-slang-hitobject-sm6-9-nvapi-invalid-mix-capability.md)). ## Direct SPIR-V emitter never emitted NoContraction (fp-mode precise was a no-op)

Slang's *direct* SPIR-V backend (`slang-emit-spirv.cpp`) never emitted the `NoContraction` decoration, so `-fp-mode precise` / `precise` were no-ops on `-target spirv` (#11933) ([Slang direct SPIR-V emitter never emits NoContraction — fp-mode/precise are no-ops there](../learnings/1783064216848-slang-direct-spir-v-emitter-never-emits-nocontract.md)). Fix: emit `NoContraction` at the `emitArithmetic` choke point for the precise fp-mode (PR #11935) ([Slang direct SPIR-V: emit NoContraction for -fp-mode precise at the emitArithmetic choke point (issue #11933)](../learnings/1783067747847-slang-direct-spir-v-emit-nocontraction-for-fp-mode.md)).

Because this landed on a specific release boundary, it seeds a recurring stale-version triage: **#12285** ("precise FMA compensated summation wrong unless the correction helper is `[noinline]`", reporter on Slang 2026.12) is a DUP of #11933 already fixed at ToT — the PR #11935 commit (`33f9ed0c`, closed #11933) first shipped in v2026.13, after the reporter's v2026.12, so in that build there were zero `NoContraction` decorations regardless of inlining and `[noinline]` "worked" only because the `OpFunctionCall` boundary is a driver optimization barrier. The reusable method that caught it: compile the reporter's exact repro on the current build and count the symptom (`grep -c NoContraction` = 0 on 2026.12 vs 32 at HEAD on a byte-identical instruction graph), then `git merge-base --is-ancestor <fix-commit> <release-tag>` to prove the fix is not in their version but is in a later one, then explicitly refute the tempting per-function mechanism (fp-mode is target-scoped — the only per-function `IRFloatingPointModeOverrideDecoration` producer is autodiff forcing `Fast`, never `Precise`, so inlining cannot drop a precise decoration that was never per-function). Verdict = resolve-without-a-PR (re-test on ≥ the fixing release; do not dispatch the fixer — an already-fixed bug risks a duplicate PR); note `NoContraction` belongs on the surrounding `OpFAdd`s, not on an already-fused `Fma`. Keep distinct from the still-open #12198 (per-*variable* `precise` qualifier in *default* fp-mode) — different root, don't cross-dedup ([#12285 = stale-version dup of #11933; verify against the release-tag boundary](../learnings/1785415514440-12285-stale-version-dup-of-11933-spir-v-precise-no.md)).

## spirv-opt crash suppressions are often droppable via the -O0 default

A test suppressed because it ABORTS inside `spirv-opt` can often have its expected-failure entry dropped simply because slang-test now defaults to `-O0` (PR #11805) — the crash never triggers at O0 — independent of any upstream spirv-tools fix ([spirv-opt crash suppressed via expected-failure list is often droppable via the -O0 default (PR #11805), independent of the upstream fix](../learnings/1783036168133-spirv-opt-crash-suppressed-via-expected-failure-li.md)).

On slang#12051, disassembled SPIR-V at HEAD `4d91d47b` settled the open design question: the per-use descriptor reload is an EMIT-TIME ARTIFACT, not a SPIR-V requirement. A `DescriptorHandle<T>` hoisted into a local (`Texture2D tex = texH;`) emits three `OpLoad` from the same `OpAccessChain` on the SPIR-V path (the user's local store is not honored), while HLSL loads once — and the reporter's `pinDescriptor()` (`OpCopyObject`) collapses it to a single `OpLoad` feeding all samples, proving one load is valid SPIR-V. ## slang#12051 DescriptorHandle NonUniform marker (an evolving investigation)

The #12051 perf work (coalesce per-use SPIR-V descriptor loads) turned on whether the coalescing pass needs a divergence guard, and the mechanism was corrected several times before landing. Two distinct clarifications preceded it. First, the per-use descriptor reload it targets is an **EMIT-TIME artifact, not a `shouldDuplicateInstAtUseSite` force-dup** as originally attributed: on the default SPIR-V path the `CastDescriptorHandleToResource` has already lowered to a single `getElement(__slang_resource_heap, index)` in the generic IR, and the triplication is introduced *during SPIR-V emission* (`legalizeIRForSPIRV` + the emit walk, `emitSPIRVFromIR` at `slang-emit-spirv.cpp:11913`) which runs AFTER the final `-dump-ir` snapshot — so the emit realizes one shared `OpAccessChain` (index math emitted once) plus an `OpLoad` re-emitted per use (measured 2 access-chains, 6 loads for 3 samples); `pinDescriptor()`/`OpCopyObject` collapses it to one `OpLoad`, proving the reload is emit strategy, not a validity requirement. The lever is thus in the emit/legalize path (materialize one `OpLoad` when the descriptor-load def dominates its uses), not the generic duplication helper ([CORRECTION #12051: descriptor reload is an EMIT-time OpLoad-per-use, verify emit not just IR](../learnings/1784075115135-correction-slang-12051-spir-v-descriptor-reload-is.md)).

The bigger correction chain concerns the **NonUniform divergence guard** the plan mandated ("dominance + INVARIANCE — don't coalesce divergent/`NonUniformResourceIndex` loads"). That guard turned out to be UNIMPLEMENTABLE and UNNECESSARY: at the coalescing site (`insertLoadAtLatestLocation`, `slang-ir-spirv-legalize.cpp`) uniform and divergent IR are byte-identical because the heap `getElement`'s index carries no `NonUniformResourceIndex` wrapper and no `IRSPIRVNonUniformResourceDecoration` — the `isNonUniform` signal the plan borrowed lives on a DIFFERENT path (the raw resource-array-param path at `:690`), so the guard would be dead code reading an absent signal. Coalescing divergent-hoisted loads is actually CORRECT, not a tolerated bug: per-LANE divergence (SIMD lanes read different descriptors — one load per lane is fine) is not per-ITERATION/temporal variance, a hoisted loop-invariant conversion is one `getElement` per lane correctly reused across N samples, and the already-shipping `spvDescriptorHeapEXT` path does exactly this (divergent-hoisted → 2 loads, 0 NonUniform decoration, valid spirv-val). The missing NonUniform *hint* is a pre-existing, documented-accepted gap (`tests/language-feature/descriptor-handle/desc-heap-nonuniform.slang:8-12`), so the fix is decoration-neutral; NonUniform-preservation on the DescriptorHandle path is a separate maintainer-owned follow-up (issue #12110, PR #12111) ([#12051 option-a: the invariance guard was over-specified](../learnings/1784081353064-slang-12051-option-a-the-invariance-guard-was-over.md), [#12051 DescriptorHandle divergent NonUniform marker stripped before SPIR-V legalize](../learnings/1784081063099-slang-12051-descriptorhandle-divergent-nonuniform-.md)).

A related pass-ordering nuance underpins the coalescing argument itself. When arguing why the existing redundancy/CSE pass can't already dedup the SPIR-V-legalization-inserted loads, get the pass ORDER exactly right — a common overclaim. Verified at HEAD (`slang-ir-spirv-legalize.cpp`): `legalizeIRForSPIRV` (:3380) calls `legalizeSPIRV` (:3141) FIRST — where `insertLoadAtLatestLocation` creates the per-use `OpLoad`s — and THEN `simplifyIRForSpirvLegalization` (:3388), whose fixpoint loop calls `removeRedundancyInFunc` (:3183). So `removeRedundancyInFunc` DOES run *after* the loads exist; the reason it still doesn't hoist descriptor-heap loads is NOT ordering but `isMovableInst`'s `kIROp_Load` case (`slang-ir.cpp:10042`), which returns movable only for `ConstantBufferType`/`ParameterBlockType` pointer types and rejects a descriptor-heap-element load. (The generic pre-SPIR-V GVN passes DO run before legalization and genuinely can't see the loads — but the correct answer to "why doesn't the *existing* redundancy pass hoist them" is the `isMovableInst` rejection in the post-legalization simplify loop.) Two related traps: `CastDescriptorHandleToResource` is force-duplicated by `shouldDuplicateInstAtUseSite` and is the lowering only for `spvBindlessTextureNV`, NOT the default `spirv` path (`__getDynamicResourceHeap[index]`) nor `spvDescriptorHeapEXT` (`__spirvLoadDescriptorFromHeap`); and `CastDynamicResource` IS movable in `isMovableInst` while `CastDescriptorHandleToResource` is NOT — don't lump them ([slang#12111 SPIR-V legalize pass ordering: removeRedundancyInFunc runs AFTER legalizeSPIRV inserts loads](../learnings/1784269362740-slang-12111-spir-v-legalize-pass-ordering-removere.md)).

**Contradictions / supersessions (within this narrative):** the earliest reading — "the `NonUniformResourceIndex` inst is essentially *never present* on this path; 0 insts / 0 decorations anywhere in `-dump-ir`; specialized away in specialize-function-call" — is WRONG as stated, though its *conclusion* (guard-drop is safe) held. The precise mechanism: the marker DOES exist early, on the pre-handle uint value (`%34 = nonUniformResourceIndex(%33)`), and is then **dropped by the `DescriptorHandle` construction round-trip** — `CastUInt2ToDescriptorHandle` ↔ `CastDescriptorHandleToUInt2` re-extracts the index as a plain swizzle (`%38`) that feeds the heap `getElement` UNMARKED. So it's "present early, dropped by the Cast round-trip," not "never there." Two methodology traps produced the sloppy earlier evidence: (1) a whole-dump `grep -c` for `nonUniformResourceIndex` is inflated by the capability-atom NAME colliding with the inst mnemonic in every function's capabilitySet decoration (166 hits mostly noise) — check the SPECIFIC operand (the `getElement` index def chain), not a raw grep; (2) `-dump-ir` starts its first snapshot too late (`### AFTER validateAndRemoveAssumeAddress`) to see an inst created and dropped in early AST→IR lowering, so "0 occurrences in `-dump-ir`" proves absence only from the first dumped pass onward. Combined with the emit-time lesson above, `-dump-ir` is blind on BOTH ends — very-early insts dropped before the first snapshot AND very-late emit/legalize mutations after the last — so a dump grep is a middle-of-pipeline view only; disassemble the output for late/emit questions and dump a specific early pass (or trace ops) for early-lowering questions ([#12051 CORRECTION — inst survives, round-trip drops it from heap index](../learnings/1784083614756-slang-12051-correction-descriptorhandle-nonuniform.md), [REFINEMENT #12051 — marker exists early then dropped by Cast round-trip; -dump-ir starts too late](../learnings/1784083913871-refinement-slang-12051-the-nonuniform-marker-exist.md)).
