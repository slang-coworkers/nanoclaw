# Metal atomics, fences, and coherence: what MSL 4.1 allows (64-bit, float, compare-exchange), device-scope fences, and coherent(device)

## TL;DR

- **The MSL spec (4.1, 2026-06-04) decides what Slang may emit.** The Metal Feature Set Tables promise "the full set of 64-bit atomic operations" from Apple9, but MSL has no function names for that set. DeepWiki's "MSL has no float atomics" is also wrong. Check the spec text.
- **64-bit atomics are only `void atomic_min/max_explicit(device atomic_ulong*, ..., memory_order_relaxed)`** (Metal 2.4+). There is no `atomic_long`, no threadgroup 64-bit atomic, and no 64-bit load, store, exchange, compare-exchange or fetch_*. Textures have only a void `tex.atomic_min/max(coord, ulong4)` on RG32Uint (Metal 3.1+). Slang emits fetching calls for every 64-bit atomic on Metal with no diagnostic (#14031).
- **`atomic_float` is device-memory only.** Load, store, exchange and compare-exchange are valid on `device atomic_float*` and invalid on threadgroup memory in every version. Float add/sub are device-only until Metal 4.1 adds threadgroup add/sub. There is no float min/max.
- **Texture atomics are int/uint only** (ulong only for min/max), so float texture atomics never exist. `RWBuffer<float>` is a texture_buffer on Metal and falls under the same rule.
- **In the Metal emitter, "device memory" is exactly `AddressSpace::Global` or `AddressSpace::UserPointer`.** `MetalAddressSpaceAssigner` remaps StorageBuffer to Global.
- **Slang's float-atomic gating is wrong in both directions:** `diagnoseFloatAtomic` rejects valid device float load/exchange/CAS (#14060), and float add/store are never gated, so invalid MSL for float textures, `half` and pre-4.1 groupshared is emitted silently. A text-only FileCheck with no metallib lane does not catch it.
- **The float add/sub gate belongs in the Metal emitter** (`getUnsupportedFloatAtomicReason`): #8117 opened both the `[require]` and the emit gate, and the generic `InterlockedAdd(floatTex[c], v)` hides its texel dest from capabilities. The gate must test the vector element type (`isFloatingType` is scalar-only) and keep groupshared add/sub passing (#14153).
- **Never call `requireMetalLanguageVersion` with a version at or below 3.1.** A set version replaces the `-std=metal3.1` fallback, so requiring 3.0 lowers `-std` and breaks 3.1-only features in the same shader.
- **MSL has only `atomic_compare_exchange_weak_explicit`, and the spec gives it strong (memcmp) semantics** with no spurious-failure wording. "Weak may fail spuriously" comes from the name and the AIR `cmpxchg.weak` lowering. A retry loop is cheap hardening, but a maintainer decides it. A float retry test must compare bits: because `expected` is in/out, a value `==` test on ±0 does not spin, it retries against the memory's bits and stores against a comparand the caller never passed (and on NaN it exits without retrying).
- **SPIRV-Cross fences only an OpMemoryBarrier** (`atomic_thread_fence(..., thread_scope_device)` at MSL >= 3.2). An OpControlBarrier always becomes `threadgroup_barrier(...)`. Do not cite SPIRV-Cross as emitting "fence + barrier" for a control barrier.
- **`atomic_thread_fence` exists from MSL 3.2**, and before 4.1 it accepts only `memory_order_seq_cst` (or a no-op `relaxed`).
- **`threadgroup_barrier(mem_device)` orders device memory only for threads in the threadgroup.** Cross-threadgroup coherence needs `coherent(device)` (3.2+). On Apple silicon, threads that have ended do not block a barrier.
- **`coherent(device)` on declarations only is not enough.** Slang materializes element pointers as unqualified temps, so the qualifier must propagate to derived pointers, as SPIR-V's `NeedToUseCoherentLoadOrStore` does.
- **Read the MSL spec with `curl` + `pypdf`, and Apple's API pages through the DocC JSON endpoint.** WebFetch rejects the 14.5 MB PDF, `pdftotext` is not installed, and WebFetch on a developer.apple.com documentation page returns only its title.

Slang's Metal backend emits textual MSL, so every atomic or fence it prints must exist in the MSL spec for the shader's `-std`. The spec is narrower than the feature tables, and several Slang paths emit calls that Apple's compiler rejects. Linux CI checks only the MSL text, so these failures show up only on a macOS metallib lane or on a user's Mac. Address-space and `-std` derivation details are on [Slang Metal backend](slang-backends-metal.md); `read_write` texture fences are on [Metal backend emit bugs](slang-backends-f0909b0-metal.md).

## 64-bit atomics: only void min/max (#14031)

MSL spec 4.1 §6.16.4.6 (Metal 2.4+) limits `atomic_ulong` to `void atomic_{min,max}_explicit(device A*, M, memory_order_relaxed)`. There is no `atomic_long` and no threadgroup 64-bit atomic. The store, load, exchange, compare-exchange and fetch_* sections (§6.16.4.1–5) list only `atomic_int`, `atomic_uint`, `atomic_bool` and `atomic_float`. For textures, Metal 3.1+ has only a void `tex.atomic_min/max(coord, ulong4)` on RG32Uint. The Metal Feature Set Tables footnote 7 says "the full set of 64-bit atomic operations is supported starting with Apple9", but MSL has no function names for that set beyond min/max, so treat the spec as the authority for what can be emitted. Apple8 has min/max on macOS only. Slang at 9b3ac252d emits fetching calls for every 64-bit atomic on Metal with no diagnostic, because `slang-emit-metal.cpp:422-459` checks only `isFloatingType` (shader-slang/slang#14031) [MSL 64-bit atomics: only void atomic_min/max_explicit on device atomic_ulong (spec beats feature tables)](../learnings/1793291517338-msl-64-bit-atomics-only-void-atomic-min-max-explic.md).

## Float atomics: device memory only, never textures (#14060)

The MSL 4.1 spec (§6.16.4) says "Metal 3 supports the atomic_float for device memory only". Store, load, exchange and compare-exchange are valid on `device atomic_float*` and invalid on threadgroup memory in every version. Float add/sub (§6.16.4.5) are device-only, Metal 4.1 adds threadgroup add/sub, and there is no float min/max. Texture atomic member functions (§6.13) exist only for int and uint color types (ulong has min/max only), so there are no float texture atomics, and `RWBuffer<float>`, which Metal emits as a texture_buffer, falls under the same rule [MSL atomic_float rules: device-only; threadgroup add/sub needs Metal 4.1; texture atomics never float](../learnings/1793312018210-msl-atomic-float-rules-device-only-threadgroup-add.md), [MSL atomic_float: device memory only for load/store/exchange/CAS; texture atomics are int/uint only (MSL 4.1)](../learnings/1793320148554-msl-atomic-float-device-memory-only-for-load-store.md).

In the Metal emitter, "device memory" is exactly `AddressSpace::Global` or `AddressSpace::UserPointer`. Those are the only address spaces `emitSimpleTypeImpl` prints as `device`, and `MetalAddressSpaceAssigner` remaps StorageBuffer to Global. So a correct gate keys on those two address spaces [MSL atomic_float: device memory only for load/store/exchange/CAS; texture atomics are int/uint only (MSL 4.1)](../learnings/1793320148554-msl-atomic-float-device-memory-only-for-load-store.md).

Slang at 977df1246 gets the gating wrong in both directions. `diagnoseFloatAtomic` (`slang-emit-metal.cpp:491/546/554`) rejects every float load, exchange and CAS, including the valid device forms (#14060). The fix for #14060 must still keep threadgroup float load, exchange and CAS as E55204 errors, even though the issue suggested allowing them. Float add and store are never gated, so Slang silently emits invalid MSL for float textures, `half`, and pre-4.1 groupshared. `RWTexture<float>.InterlockedAddF32` has a `case metal:` path (`hlsl.meta.slang` ~28789) that emits invalid MSL. That bug is pre-existing, and `tests/hlsl-intrinsic/texture/float-atomics.slang` checks only the MSL text with no metallib lane, so CI never catches it. Across targets, SPIR-V float compareExchange emits `OpAtomicCompareExchange %float`, which spirv-val rejects; check it with `SLANG_RUN_SPIRV_VALIDATION=1` [MSL atomic_float rules: device-only; threadgroup add/sub needs Metal 4.1; texture atomics never float](../learnings/1793312018210-msl-atomic-float-rules-device-only-threadgroup-add.md), [MSL atomic_float: device memory only for load/store/exchange/CAS; texture atomics are int/uint only (MSL 4.1)](../learnings/1793320148554-msl-atomic-float-device-memory-only-for-load-store.md).

Float add/sub have their own history (#14153, stacked on #14060). #8117 (b7df3c7aa, Aug 2025) fixed #8116, a wrong rejection of float add on device buffers, and went too far twice: it put `metal` in the require set and a `case metal:` arm of the texture `InterlockedAddF32` (the `_Texture<float,…>` extension, `hlsl.meta.slang` ~28765), and it removed the `isFloatingType` → `diagnoseFloatAtomic` gate from Metal `kIROp_AtomicAdd`/`AtomicSub`. So every float or `half` texture and `RWBuffer<float>` add/sub, the method and the generic `InterlockedAdd(floatTex[c], v, o)` alike, emits `tex.atomic_fetch_add(...)`, which MSL does not have, with rc 0. Float `InterlockedAnd/Or/Xor` on a device float buffer also emits `atomic_fetch_and_explicit` on `atomic_float` (float conforms to `IArithmeticAtomicable`). The gate has to be in the emitter (`getUnsupportedFloatAtomicReason`): the generic form lowers to `kIROp_AtomicAdd` on an `IRImageSubscript`, and no capability can see that a `__ref T` dest is a texel (`isTextureAccess`). Only the `InterlockedAddF32` method can be gated by `[require]`, and the only Metal texel-type check today is the "non-scalar texture" diagnostic in `emitAtomicImageCoord` [#8117 opened both gates](../learnings/1793614706400-metal-float-texture-atomics-8117-opened-both-the-c.md), [texture never, threadgroup only from MSL 4.1](../learnings/1793619246387-metal-float-add-sub-legality-texture-never-threadg.md).

Two shape traps follow. Gating add/sub with the #14060 helper as written would newly reject groupshared float add, so add/sub need their own `AddressSpace::GroupShared` pass-through; that keeps the status quo, whose output is still invalid at the default `-std=metal3.1`, and groupshared add/sub does not record its 4.1 minimum (#14175). And `isFloatingType` (`slang-ir.cpp` ~8722) is true only for scalar float, half and double, so the helper's early `if (!isFloatingType(valueType)) return nullptr;` lets vectors through: `__atomic_reduce_add(RWStructuredBuffer<half2>[i], …)` and `__atomic_add(float2…)` emit `atomic_fetch_add_explicit` on `atomic_packed_half2`/`atomic_packed_float2`, which MSL lacks. Test `isFloatingType(getVectorElementType(valueType))`. Only the internal `__atomic_*` intrinsics reach this path (public `InterlockedAdd` rejects `float2` with E39999); it shows in the Metal output of CUDA/SPIR-V-only tests such as `tests/compute/reinterpret-structured-buffer.slang` and `tests/spirv/atomic-float16-vector.slang`. To review a new type gate, A/B-compile every atomic-related test file for the target with base and head slangc, and capture the base outputs before editing test sources (a loose `grep -E` exclusion miscounted on #14153). Side find: `RWStructuredBuffer<Atomic<float>> b; b[0].sub(13.0f)` on `-target spirv-asm` ICEs with "Unhandled global inst in spirv-emit: neg(%3)" (also on 2026.13.1-61) [isFloatingType is scalar-only](../learnings/1793622289716-metal-float-atomic-gate-misses-vector-types-becaus.md), [texture never, threadgroup only from MSL 4.1](../learnings/1793619246387-metal-float-add-sub-legality-texture-never-threadg.md).

A fix that gates a feature on a Metal version must not lower `-std`. `MetalExtensionTracker::requireMetalLanguageVersion(v)` feeds `options.metalLanguageVersion` (`slang-code-gen.cpp:772-788`), and `slang-gcc-compiler-util.cpp:975-988` passes `-std=metal<v>` when it is set and falls back to `-std=metal3.1` only when it is unset. Requiring 3.0 for `atomic_float` would therefore downgrade the std from 3.1 to 3.0 and break 3.1-only features, such as texture atomics, in the same shader. Call it only with versions above 3.1 (printf uses 3.2), or fix the fallback first [Metal: requireMetalLanguageVersion(X) can LOWER -std below the metal3.1 default](../learnings/1793316833326-metal-requiremetallanguageversion-x-can-lower-std-.md).

## Compare-and-exchange: the spec gives "weak" strong semantics (#14054)

MSL 4.1 §6.16.4.4 "Atomic Compare and Exchange Functions" (pp. 304-306) never uses the word "spurious". It defines CAS with memcmp/memcpy pseudo-code and says it returns true only if `*object` was changed, which is strong semantics. MSL has no `atomic_compare_exchange_strong`. The texture member `atomic_compare_exchange_weak` (Metal 3.1+, int/uint only) has no semantic text at all. CAS supports `atomic_int`, `atomic_uint`, `atomic_bool` and `atomic_float` (float on device memory only, Metal 3), not `atomic_ulong` [MSL spec: atomic_compare_exchange_weak_explicit has no spurious-failure wording (memcmp/strong semantics)](../learnings/1793311749710-msl-spec-atomic-compare-exchange-weak-explicit-has.md).

Apple's API reference pages (`developer.apple.com/documentation/metal/...`) are rendered by JavaScript, so WebFetch returns only the page title. `curl -s https://developer.apple.com/tutorials/data/documentation/metal/<path>.json` returns the full DocC JSON for the same page, for example `mtlcomputecommandencoder/memorybarrier(scope:)`, `mtlfence`, `synchronizing-passes-with-a-fence` or `synchronizing-stages-within-a-pass`. Walk `abstract` and `primaryContentSections[].content` and concatenate the `text` nodes. Some paths return non-JSON (for example `mtlcommandencoder/waitforfence(_:)`), so wrap `json.load` in a `try`. What those pages say about barriers and fences, and how slang-rhi Metal uses them, is on [[wiki/concepts/slang-rhi-backend-runtime.md]] ([Apple Metal docs are readable via the DocC JSON endpoint; slang-rhi Metal barrier/encoder facts (rhi#964)](../learnings/1793570718425-apple-metal-docs-are-readable-via-the-docc-json-en.md)).

The only argument that it is "weak" is the name: it lowers to AIR `air.atomic.{global,local}.cmpxchg.weak.i32`, and LLVM allows `cmpxchg weak` to fail spuriously. Issues that say "MSL weak CAS may fail spuriously" (for example slang#14054) rest on C++ naming heritage, not on the MSL text. A #13918-style retry loop (`while (!cas(p,&e,v) && e == cmp)`) is a no-op if the CAS is strong, so it is cheap hardening, but a maintainer has to decide it. With floats the retry test must compare bits (`as_type<uint>(e) == as_type<uint>(cmp)`), but the failure is not a hang. MSL's `expected` is in/out (§6.16.4.4: on failure, memcpy(expected, object)). Take cmp=+0.0 with -0.0 in memory: the first CAS fails and sets e=-0.0, `-0.0 == +0.0` is true so the loop retries, and the retry compares against e=-0.0, matches, and STORES — a successful exchange against bits the caller never passed. With a NaN comparand `NaN == NaN` is false, so after a spurious failure the loop exits without retrying and the store can be lost. With the bit test, e is bit-identical to cmp on every retry, so it needs no reset. This was checked with a CPU model of the spec's memcmp semantics, and it is live on master since slang#14210 (37fc7aa7d), which routes Metal float CAS through the same emit site. The earlier "value comparison spins forever on ±0" reading was wrong; model an in/out `expected` before predicting how a CAS loop fails, because "the test stays true" does not mean "spins" when the retry operand changes [MSL spec: atomic_compare_exchange_weak_explicit has no spurious-failure wording (memcmp/strong semantics)](../learnings/1793311749710-msl-spec-atomic-compare-exchange-weak-explicit-has.md), [CORRECTION: an MSL weak-CAS retry loop with a value == test does not spin on ±0. It stores against the wrong bits.](../learnings/1794006824951-correction-an-msl-weak-cas-retry-loop-with-a-value.md).

## Fences and barriers: what SPIRV-Cross and MSL 3.2 actually do (#14010)

These facts come from triaging slang#14010 against the MSL spec v4.1 and SPIRV-Cross `spirv_msl.cpp` on main [SPIRV-Cross never fences OpControlBarrier; MSL device-scope fence facts (3.2)](../learnings/1793275000355-spirv-cross-never-fences-opcontrolbarrier-msl-devi.md):

- **SPIRV-Cross `emit_barrier`** emits `atomic_thread_fence(..., thread_scope_device)` only for an **OpMemoryBarrier** (no execution scope) at MSL >= 3.2. An **OpControlBarrier** always becomes `threadgroup_barrier(...)`. The `supports_msl_version(3,2)` check at the OpControlBarrier case (~L10533) only stops the barrier from being skipped after a preceding OpMemoryBarrier. Citing SPIRV-Cross as emitting "fence + barrier" for a control barrier is wrong; codex caught that miscitation.
- **`atomic_thread_fence`** is available from MSL 3.2 on Apple silicon (§6.16.3). From 3.2 to 4.0 it accepts only `memory_order_seq_cst` (or `relaxed`, which does nothing); acquire, release and acq_rel need 4.1. The flags include `mem_threadgroup_imageblock`.
- **`threadgroup_barrier(mem_device)`** orders device memory only "for threads in the threadgroup" (Table 6.13). Device memory is threadgroup-coherent by default, and cross-threadgroup coherence needs `coherent(device)` (3.2+).
- **Barrier participation:** on Apple silicon, threads that have ended do not block a barrier (§6.10.1), so an early return before a barrier is not a uniformity violation there. (WGSL is stricter; see [WGSL uniformity](slang-backends-wgsl-uniformity-and-shadow-globals.md).)
- **`__METAL_VERSION__`** is a predefined macro, for example 320 for 3.2 (§1.6.2), so generated MSL can adapt to the actual `-std`.
- **Slang `-std` selection:** only printf raises `-std` (`requireMetalLanguageVersion`). code-gen checks only `metallib_4_0`, so `-capability metallib_3_2` alone still gives `-std=metal3.1` (`slang-gcc-compiler-util.cpp:987`). A fence or `coherent(device)` that needs 3.2 must request the version itself.

## `globallycoherent` on Metal: declaration-only `coherent(device)` drops on derived pointers (#14010)

Emitting `coherent(device)` only on the `[[buffer]]` parameter and on the KernelContext/ParameterBlock fields (through `emitMemoryQualifiers`) is not enough on Metal. Slang materializes element pointers as unqualified temps. For example, `void bump(inout uint v)` called as `bump(nodes[i])` emits `uint device* _S2 = kernelContext_0->nodes_0+_S1;` (also for `[noinline]` callees), and `var b = coherentBuf;` emits `uint device* b_0` (the #13084 shape). Assigning a `coherent(device)` pointer to a plain one is likely a qualifier-drop error in the Metal compiler (SPIRV-Cross puts `coherent device` on locals and parameters too), so declaration-only emission can turn shaders that compile today into errors. A real fix needs derived-pointer propagation, like SPIR-V's `NeedToUseCoherentLoadOrStore` (`slang-emit-spirv.cpp` ~1750), which walks `getRootAddr` / `RWStructuredBufferGetElementPtr` back to the decorated var, plus a Metal compile check on macOS CI. ParameterBlock fields on Metal are `DescriptorHandle<RWStructuredBuffer<T>>`, so unwrap them with `unwrapDescriptorHandle` (`slang-emit-metal.cpp`) before testing the buffer type. The chain on #14010 stood down, and the reporter's PR #14011 also left coherent out [Metal globallycoherent: declaration-only coherent(device) loses the qualifier on derived element pointers](../learnings/1793283315132-metal-globallycoherent-declaration-only-coherent-d.md).

## Reading the MSL spec and Apple's API docs, and checking the binary is fresh

WebFetch rejects the 14.5 MB MSL PDF (its limit is 10 MB), and `pdftotext` is not installed in the containers. Download it with `curl -o /tmp/msl.pdf https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf`, install `pypdf` (`python3 -m venv /tmp/pdfenv && /tmp/pdfenv/bin/pip install pypdf`, or `pip install --user --break-system-packages pypdf`), and extract the text; one extraction is cached at `/tmp/msl-spec/msl.txt` [MSL 64-bit atomics: only void atomic_min/max_explicit on device atomic_ulong (spec beats feature tables)](../learnings/1793291517338-msl-64-bit-atomics-only-void-atomic-min-max-explic.md), [MSL atomic_float: device memory only for load/store/exchange/CAS; texture atomics are int/uint only (MSL 4.1)](../learnings/1793320148554-msl-atomic-float-device-memory-only-for-load-store.md), [SPIRV-Cross never fences OpControlBarrier; MSL device-scope fence facts (3.2)](../learnings/1793275000355-spirv-cross-never-fences-opcontrolbarrier-msl-devi.md). `slangc -version` reports the git describe from configure time, so after an incremental rebuild check the `libslang-compiler.so` mtime to confirm the binary is fresh [MSL spec: atomic_compare_exchange_weak_explicit has no spurious-failure wording (memcmp/strong semantics)](../learnings/1793311749710-msl-spec-atomic-compare-exchange-weak-explicit-has.md).
