## TL;DR

- **`slang-test` silently ignores misspelled or unrecognized directives.** Only the prefix `DISABLE_` is stripped; `//DISABLED_TEST`, `//TEST_DISABLED`, `//IGNORE_TEST` are inert text with no warning. The blast radius is bookkeeping (FileCheck labels + deliberate disables), not a correctness hole — but an intended-to-run test silenced by a typo would be invisible.
- **`slang-test -test-dir <dir> <path>` treats the trailing path as NOT a filter** — it prints `no tests run` and exits ~0. "No tests run" is a null from the instrument, not evidence a test passes. Run unfiltered and grep the failing list.
- **Three ways a Slang test passes without asserting anything:** `//CHECK-NOT:` is inert in `DIAGNOSTIC_TEST` (only real FileCheck honors it); even in FileCheck a `-NOT` only scans *after* its anchor; and `non-exhaustive` + zero `//CHECK:` lines asserts nothing. The one step that subsumes all three: **run every new test against the OLD binary and confirm it FAILS.**
- **The pre-fix reference binary needs its own control** — a copied `slangc` without its versioned `libslang-compiler.so` gives `rc=127` that reads like a clean pre-fix pass. Verify the reference *reproduces the defect*.
- **A green-locally-red-in-CI unit test is an ambient-env difference, not flake** — slang CI exports `SLANG_RUN_SPIRV_VALIDATION=1`, which aborts compiles against a fake `slang-glslang` that lacks `glslang_validateSPIRV`. Re-run the revert drill *under the CI env*.
- **A test's SPIR-V asm can be a hardcoded C++ string** (VK-GL-CTS `SpirVAsmSource`) — such a case cannot exercise Slang codegen no matter what its name says. CTS dispatch is by C++ overload, a compile-time fact.
- **slang-rhi diverges from slang:** no draft CI gate, clang-format 20.1.7, `main` branch, generator-dependent artifact path, and vacuous test passes from `#if SLANG_WIN64`-gated cases on Linux.

## Directives: inert spellings and non-filtering path args

`slang-test`'s directive parser strips only the literal prefix `DISABLE_`, then matches `TEST`/`DIAGNOSTIC_TEST`/etc.; anything else hits the unknown-command branch and is **skipped silently, no diagnostic**. So `//DISABLED_TEST` (a `D` where the recognized form has `_`) is inert — measured tree-wide as 52 files carrying test-directive-shaped commands the harness recognizes zero of. **Severity is bounded:** every inert token is either a FileCheck label (`CHECK`/`BUF`/`METAL` — ignored by the directive parser by design) or a deliberate disable; a sweep for the dangerous case (a directive whose author meant the test to *run*, silenced by the parser) found none. So report the *test-directive-shaped* subset as the defect count, never the raw inert-token count. This surfaced when two coworkers' residue counts differed by 2 — the delta was exactly the two files using `//DISABLED_TEST`; **when two counts differ by a small delta, enumerate the delta members before arguing methodology.** [slang-test silently ignores misspelled directives: only the prefix DISABLE_ is stripped](../learnings/1785964513711-slang-test-silently-ignores-misspelled-directives-.md) [slang-test silently ignores unrecognized directive spellings (DISABLED_TEST)](../learnings/1785967544526-slang-test-silently-ignores-unrecognized-directive.md)

`slang-test -test-dir docs/generated/tests <path>` treats the trailing path as **not a filter** — it prints `no tests run` and reads as "nothing failing there," the exact opposite of the truth. Only a bare-word (`stmt-throw`) errors loudly; the two path forms fail silently and cheerfully, even with the real CI flags added. `no tests run` is a **null from the instrument**, not a measurement of the subject, and is byte-identical to "ran and passed." Run the whole suite with no filter (the canonical invocation is in `.github/workflows/nightly-slang-test.yml`) and grep the failing list — that no-filter run is the positive control. Bonus: the generated suite reports ~34 failing tests on a clean checkout, so "the nightly is red" says nothing about whether *your* change broke something. ## Three ways a test passes without asserting — and the drill that catches all three

All three shipped green against a fixed compiler and would have shipped green against an unfixed one:

1. **`//CHECK-NOT:` is inert in `DIAGNOSTIC_TEST`.** `DIAGNOSTIC_TEST:SIMPLE(diag=CHECK)` uses slang-test's own annotation parser, whose marker is exactly `//CHECK:` (the colon is required deliberately, to avoid substring matching), so `//CHECK-NOT: x`.startsWith(`//CHECK:`) is false. Only `TEST:SIMPLE(filecheck=CHECK)` runs real LLVM FileCheck where `CHECK-NOT` works. Absence/ordering assertions belong in the filecheck test.
2. **Even in real FileCheck, `CHECK-NOT` only scans AFTER its anchor.** A `-NOT` on `Slang_FuncType` after a `computeMain` anchor is dead when the defect spelling is emitted near the *top* of the file, ahead of the entry point. Put each `-NOT` before its anchor, or drop the anchor; prove the mechanism with a control asserting `-NOT` on text that appears only above the anchor.
3. **`non-exhaustive` + zero annotations = assertion-free.** The harness's "Unnecessary 'non-exhaustive'" guard cannot catch it — it checks whether the flag was *warranted*, never whether the test *asserts* anything.

The one mechanical step that subsumes all three: **run every new test against the OLD binary and confirm it FAILS** (mine went 0/4, 0/3, ... pre-fix → all pass post-fix). But the **pre-fix binary needs its own control** — copying just `slangc` aside gives `rc=127` (needs the versioned `libslang-compiler.so.<version>`, stamped into the name), which reads like a clean pre-fix result but means "cannot execute." Absence of the fix's signal is satisfied equally by a correct pre-fix compiler and by a binary that never ran; the discriminator is the *defect being present*, so verify the reference reproduces the defect first. ## Green locally, red only in CI = ambient environment, not flake

A unit test passing locally and failing only in CI is almost never flake — it reads ambient environment your shell lacks. **slang CI exports `SLANG_RUN_SPIRV_VALIDATION=1`** (`ci-slang-test-container.yml` and siblings). So any unit test that installs a fake `slang-glslang` via `setSharedLibraryLoader` must export `glslang_validateSPIRV`, or every compile against the fake aborts before reaching what you were testing — the chain runs `validate` failure → `SpirvValidationFailed` (declared `internal(`, `Severity::Internal` sorts above `Fatal`) → `SLANG_ABORT_COMPILATION` immediately, so the failure surfaces far from its cause. The one-step local repro: `grep -rn "<VAR>" .github/workflows/` then `VAR=1 ./slang-test ...`. Fix by making the fake a complete-enough stand-in (export an accepting validator), not by using `ScopedEnvVar` to force the variable off. **Re-run the revert drill under the CI env** — mine still segfaulted 2/6 with the guard removed, which is what turned "not vacuous" into a fact; and check the explanation against *every* failing case, since two failure routes can share one cause while a third has a different one. Cost note: fixing a test defect after a maintainer approved dismisses the approval — explain it in a PR comment. ## A test's SPIR-V asm can be a hardcoded string — check the collection before triaging "codegen"

On #12364 a member filed a VK-GL-CTS failure as "a Slang SPIR-V codegen correctness issue" and had burned CI runs bisecting Slang. The failing case's qpa log shows a full SPIR-V module with `OpSource GLSL 450` and a `NonUniform` decoration — extremely tempting to reason about as compiler output. **It is a hardcoded C++ string literal** (`vktDescriptorSetsIndexingTests.cpp` builds it with `ostringstream <<`), registered into `initAsmPrograms` as a `SpirVAsmSource`. One fact explains every puzzling detail at once — when several log oddities each need a separate explanation, suspect a single upstream fact. **CTS dispatch is by C++ overload, a compile-time fact:** `GlslSource`/`HlslSource` reach the Slang call site; `SpirVAsmSource` reaches `assembleProgram`, which never calls Slang. So an asm-authored case cannot exercise Slang codegen regardless of its name — find which collection it registers into before accepting "CTS test X proves a Slang bug." The empirical closer ("Slang failed to load 11,545×, this test passed") is load-bearing *only* because there is no silent glslang fallback (`buildProgram` throws). Other reusable pieces: exclusion is not attribution (proving direct codegen is excluded does not identify the culprit); a `-Tail 1000` qpa dump is not suite-wide evidence; anchor substring greps (`grep -c "SLANG: "` matched the workflow's own env echo). [A test's SPIR-V asm can be a hardcoded C++ string — check the program-collection overload before triaging "codegen"](../learnings/1785929643051-a-test-s-spir-v-asm-can-be-a-hardcoded-c-string-ch.md)

## slang-rhi diverges from slang — don't port habits

Working slang-rhi with slang habits produces wrong actions. Four verified divergences: (1) **`ci.yml` has no draft gate** — CI auto-runs on draft PRs, so slang's "manually `gh workflow run` after every draft push" rule is redundant and actively harmful here (an extra confusing run). Check the workflow's actual trigger block per repo. (2) **clang-format is pinned 20.1.7** (from `.pre-commit-config.yaml`), not slang's 17; there is also a repo-local `tools/check_ascii_hook.py`. (3) **Default branch is `main`**, not `master`. (4) **Artifact path depends on the generator** — `AGENTS.md` documents the multi-config Ninja layout (`build/Debug/slang-rhi-tests`) but a Makefiles worktree puts it at `build/slang-rhi-tests`; confirm with `grep CMAKE_GENERATOR: build/CMakeCache.txt`. Bonus test-harness trap: `slang-rhi-tests -tc="texture-shared-cuda"` reports `0 passed | 0 failed | 831 skipped` / `SUCCESS!` — a vacuous pass, because the shared-CUDA cases are inside `#if SLANG_WIN64` and are not compiled into a Linux binary. Confirm registration with `-ltc` and pair an emptiable filter with a positive control. ## Unit-testing a non-exported internal: impossibility claims vs cost claims

"`IRModule::create` etc. aren't exported from `libslang.so`, so a test can't link them" is **false** — the first half is true (`nm -D` finds none), but `slang-unit-test` already solves exactly this: `tools/CMakeLists.txt:414-425` adds `slang-repro-validator.cpp` to `target_sources` and calls its non-exported free function directly, "without publishing an internal validator as part of the stable public ABI." So **to unit-test a non-exported Slang internal, add its `.cpp` to `slang-unit-test`'s `target_sources`** — sanctioned, in use, ABI-safe. The generalizable lesson: **downgrade every "impossible / can't / unreachable" to the cost claim it usually is.** "Cannot be done" is falsified by a single counter-example and reads as unresearched or self-serving; "could be done by recompiling a large TU into the test target; disproportionate for a two-line change" is a judgement a reviewer can weigh — same decision, same code, only the honesty of the framing differs, unless you actually searched for the mechanism and can cite the search. "No existing test does X" is a prompt to investigate (how does this target handle non-exported internals *at all*?), not a conclusion; and labelling a claim "reasoned, not verified" *raises* the bar on the reasoning, it doesn't lower it — the label invites a reader to trust the argument instead of the evidence, which here sat one file away.
