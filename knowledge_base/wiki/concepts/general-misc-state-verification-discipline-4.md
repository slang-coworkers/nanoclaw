# State Verification Discipline (part 4)

## TL;DR
- **A read of a live artifact is a MEASUREMENT WITH A TIMESTAMP, not a fact.** PR state, CI conclusion, draft/ready, review state, infra capability — all mutate. Re-probe before citing; a saved memo is a claim about a past instant.
- **A dispatch, a webhook, a nudge, and a timeout are all claims ABOUT state, never state.** Resolve live before acting on any of them. A timeout in particular describes a past instant and is not a decision.
- **Correcting the EXTENT of a claim about a mutable condition, while still stating it as a standing property, leaves the claim wrong.** Fix the tense too.
- **A matching sha does not establish a current reading.** Same-head is necessary, not sufficient — a check can have been re-run, evicted, or superseded since.
- **Verify the CI *conclusion*, not just draft+HEAD, before calling a chain terminal** — and check whether the "last activity" you are clocking is actually a terminal close.
- **A commit date is not a version, and not an edit time.** Read submodule pins by version, not by date; use `merged_at`, never a merge commit's `committer.date`, for when a PR landed.
- **Bot-filed and stale issues rot silently.** Re-verify every `file:line` against current main before relaying; a static-analysis pointer goes stale when the branch is gone, not just when the file changes.
- **A grep hit is a line, not a scope, and `grep -c` counts lines, not events.** A member cite names file, line **and** owner; a published count names the invocation that produced it — or is deleted.
- **A PR's changed-file list does not prove "not a regression."** Verify control-flow invariants against SOURCE, not against a triage memo or a reviewer's assertion.
- **Check ownership before driving anything.** Read issue comments and `head.repo.full_name`: a contributor-owned fork PR is not yours to park, close, or push. Stand down when a maintainer or contributor is driving.
- **Verify @-mention identity against the actual PR/commit author before posting** — a wrong mention is a public, unrecoverable error.
- **A corrupted tool-result turn taints its own verifications**; redo them in a clean turn rather than reasoning off the residue.
- **Post-compaction drift is real**: re-read state before autonomous action in a compacted session, because your premise may have been summarized away.
- **Recurring trackers must carry DISPOSITION, not just items**, and a daily report must carry open ship-stoppers — an item list with no disposition reads as handled.
- **Recurrence only advances on completion**, so a host event can orphan an overdue occurrence and freeze a whole daily series until a human notices. Watchdog the scheduler.
- **A verdict you already published is a past position, not a reason to skip re-checking.** A substantive new human comment re-opens a chain you closed.

## Fixing a Crash Can Be a Multi-Layer Cascade — Verify Each Layer, Stop at the Safe Boundary (2026-07-25 fold)

Fixing a "front-end crashes on X" issue often *unmasks* deeper layers the crash was hiding, so a clean triaged one-liner can turn into a multi-layer cascade — and a partial fix can be strictly worse than shipping less. slang#12210 (`[Differentiable]` on a property getter segfaults) became three layers: **L1** the filed crash (`getFuncType` cast a `PropertyDecl` parent to `CallableDecl` and null-deref'd — one-line gate); **L2** exposed by L1 (getter now rejected at the call site with E41022 because property accessors aren't registered for autodiff like subscript accessors — small fix, makes forward-diff work); **L3** exposed by L2 (`bwd_diff` asserts in the reverse-mode transform — property `apply_bwd` func type comes out missing the `this` receiver — NOT confidently root-caused). The decision rule that saved the ship: **L1+L2 without L3 is strictly worse than L1 alone** — they convert a clean E41022 diagnostic into an internal assert-crash on `bwd_diff` — so L2 was reverted and only L1 shipped (crash → clean diagnostic), deferring full support to a follow-up. Detection technique: after the crash fix builds, actually EXERCISE the feature the crash was blocking (run *both* `__fwd_diff` and `bwd_diff` through it, not just "does it compile"); compare against the working analog (subscript accessor) to tell "genuine feature gap" from "wiring bug"; and ground-truth layer sizing in the IR (`-dump-ir` param counts: property `apply_bwd` = 0 params vs subscript = 2), not in subagent speculation — two sizing passes gave two *different* wrong theories for L3, and the IR was the only reliable signal. Corollary to the "mirrors an existing working path" trap: verify the working path's mechanism actually matches your theory — the L3 theory ("add getThisParamType like RematFuncType") couldn't explain how the subscript's `apply_bwd` already gets its `this` when that resolver has no such code; that unexplained gap is the tell the root cause is elsewhere — don't ship on it ([Fixing a crash can be a multi-layer cascade — verify each layer before shipping, stop at the safe boundary](wiki/learnings/1785026926217-fixing-a-crash-can-be-a-multi-layer-cascade-verify.md)).


## Byte-Verify a Hand-Apply Patch by Post-Image Blob Hash (2026-07-28 fold)

The "review the actual source, not a reconstruction" invariant survives even when the branch is UN-fetchable (e.g. a `.github/workflows/*` App-`workflows`-permission wall or a worktree on another coworker's filesystem). Prove byte-identity to the committed HEAD without reading the fixer's disk: (1) confirm your clone's base file blob equals the patch's pre-image hash (`git rev-parse HEAD:<path>` vs the `index <pre>..<post>` line) — if equal, your working copy IS the fixer's pre-edit file; (2) apply the exact committed diff bytes (from the fixer's pasted `git show <sha>`); (3) `git hash-object <path>` on the result and compare to the stated post-image blob. A match is proof, not an eyeball. Load-bearing subtlety: always re-hash the CURRENT sha — when a fixer amends (e.g. to drop a redundant comment per review), the SHA and blob move, and that movement is exactly the tell that content changed. Concrete: #12062 twin `removeRequestedReviewers` hardening (base `dd6e011e56`, pre-image `a3bfb08f31`, committed `4147d58fb2`, post-image `f46f95ac14`) — applied diff → `git hash-object` returned `f46f95ac14…` == stated → clean APPROVE ([byte-verify a hand-apply patch by post-image blob hash](wiki/learnings/1785261494633-byte-verify-a-hand-apply-patch-by-post-image-blob-.md)).

Extend the file:line-verification discipline to **doc/spec paths a reporter cites**. Triaging #12261, a high-signal MEMBER reporter wrote the behavior "disagrees with the language reference (`docs/language-reference/statements-break-and-continue.md`)" — but that path does not exist at HEAD, and the actual `statements.md` is *silent* on the rule, not contradictory. Echoing "the impl contradicts the reference" would have been a false public claim; the honest framing ("the reference is silent/underspecified") also reframes the fix as a spec-gap opportunity. Treat a cited doc/spec path exactly like a code pointer: `[ -f <path> ]` and grep the actual reference for the rule before repeating "disagrees with the spec" — reporters' pointers drift ([verify a reporter's cited doc/spec path before repeating "impl disagrees with the reference"](wiki/learnings/1785320946422-verify-a-reporter-s-cited-doc-spec-path-before-rep.md)).


## Controls, discrimination, and proxy verification — part 1 — part 1/3

Everything above asks *is my source live and primary?* This section is the complementary question, learned mostly on 2026-08-03 across the slangpy#1087/#1088 + slang#11225 chain, the slang critique-gate fleet, and slang-rhi#800: **could this observation have come out differently if I were wrong?** Provenance discipline and method discipline are separate checks and you need both — the worst offenders below were all read from correct primary sources.

### The discrimination test — a signal that cannot separate the states you care about carries zero bits

Before an observation carries a conclusion, ask whether it would have looked different had the opposite been true; if not, no amount of careful sourcing rescues it ([the unifying diagnosis: a signal that cannot distinguish the states you care about](wiki/learnings/1785750713482-the-unifying-diagnosis-a-signal-that-cannot-distin.md)). **Absence claims need a positive control; presence claims mostly don't.** The canonical miss: `grep -c "DEEPEST SUBCASE: d3d12"` → 0 cited as "no d3d12 failures," when the same pattern on `vulkan` — where all 28 failures were — also returns 0, because doctest emits `DEEPEST SUBCASE STACK REACHED …` with the subcase name on the *following indented line*. The pattern matched nothing; the zero was unfalsifiable ([a grep returning 0 is only evidence if the same pattern returns non-zero for a known-present case](wiki/learnings/1785749557692-a-grep-returning-0-is-only-evidence-if-the-same-pa.md), [same rule, reviewer-side: run the positive control first](wiki/learnings/1785750137847-a-grep-returning-0-is-only-evidence-if-the-positiv.md); a third near-identical filing survives only as a [dedup pointer](wiki/learnings/1785749767697-a-grep-returning-0-is-only-evidence-if-the-same-pa.md)). Companion traps from the same corpus: **Windows runner logs are CRLF**, so `$`-anchored patterns silently return nothing on `windows.log` while working on `linux.log` — a *second* vacuous zero behind a plausible command (`tr -d '\r'` first, strip the ISO timestamp prefix); enumerate a diagnostic's *distinct* values rather than testing for one you predicted; prove completeness by matching the real header's count against the reported failure count; and CI logs are downloadable unauthenticated, so "gh isn't authenticated" never justifies accepting a relayed figure. Three refinements are worth as much as the base rule. **A log absence tells you WHAT, never WHY** — even a correctly-derived zero with a passing control cannot separate *ran-and-exited-early* from *never-a-step* from *excluded-by-an-`if:`*; resolve the cause at the workflow/build **definition**, and note that an enumeration bounds its claim to the surface that actually ran (a "complete fix" argument rested on 56 occurrences counted on the C++ test surface while the Python surface never compiled, making a second site unfindable by construction). **A count can be topically right and semantically empty** — `grep -c pytest` = 22 was entirely `pip install` chatter, 1 after filtering. And **a claim you have had to weaken twice is telling you the property is not verifiable in your environment** — say that outright instead of hedging a third time (`passed` → `no observed failure` → `consistent with, plus the alternative` is the tell). The test applies to citation *shapes*, not just patterns: a **line range** that straddles two constructs cannot discriminate "drifted guard" from "adjacent construct that needs none" — `:507-514` cited as a missing device term spanned a correct two-clause runtime guard and a separate `#if` preprocessor block, so the citation proved neither hypothesis ([run the discrimination test on line ranges too](wiki/learnings/1785751219892-run-the-discrimination-test-on-line-ranges-too-a-c.md)). It applies one level further out as **a correct probe pointed at the wrong observable**: corroboration needs a *causal path*, not an overlapping target set — a capability-set mutation and three layout branches sharing one call site read as one mechanism, but none of the branches reads the promoted capability, so an A/B measuring layout/offsets would have found no difference either way and reported "no flip" ([two mechanisms at one call site are not one mechanism — derive the measurement from what the mechanism mutates](wiki/learnings/1785752093299-two-mechanisms-at-one-call-site-are-not-one-mechan.md)). Finally, **the detector is itself a claim**: a duplicate-H1 scan using `grep -c "^# "` counted `#` bash comments inside fenced code as headings, and when a count surprises you on an artifact you believe is clean, suspect the counter first — the instinct to fix the artifact is what turns a detector bug into corrupted data ([a detection query is itself a claim needing a discrimination test](wiki/learnings/1785775510720-a-detection-query-is-itself-a-claim-needing-a-disc.md)). Two practices make all of this reviewable: prefer **two independent extraction methods** for any load-bearing claim, and **publish the extraction command alongside the finding** — a command gets run against inputs its author never had, which is how the vacuous grep was caught at all.

### Diagnose an instrument's blindness from its shape, before running it — a green result can be structurally incapable of red

The revert-drill above proves a test *can* fail; this cluster covers the checks that cannot, and which therefore manufacture their own supporting evidence. **When a check reads one element of an unordered or arbitrarily-ordered set, its passing carries no information** — diagnose that from the command's shape, since nothing prompts you to vary anything while a coincidence is reassuring you. `[ "$(git rev-parse HEAD)" = "$(cat .git/shallow | head -1)" ]` as a shallow-clone discriminator coincides whenever HEAD happens to sort first (`.git/shallow` is SHA-sorted); measured false-agreement was ~1/6 on a 6-entry fixture and a **coin flip** on a 2-entry one, and *the smallest, most natural fixture is the one most likely to lie to you* — both author and reviewer logged an agreeing run as confirmation before a deliberately-built larger fixture forced a second look ([a check that reads one element of an unordered set cannot be validated by running it](wiki/learnings/1785768953168-a-check-that-reads-one-element-of-an-unordered-set.md)). Those rates were then themselves an instance of the failure they described: `--depth` implies `--single-branch`, so the modal real shape (`clone --depth 1 --branch <pr-head>`) writes exactly one shallow entry and the bad check agrees **~always** — anyone reading "3/12" would wrongly conclude testing would have caught it. Second measured smell from the same amendment: **a check whose verdict an unrelated later operation can flip was never measuring its subject** (an extra `git fetch --depth 1` flipped it in 4 of 12 fixtures with HEAD untouched), and the stable form is `--is-shallow-repository` plus empty `git log -1 --format=%P` ([CORRECTION: the false-agreement rates were measured on a configuration nobody reaches by accident](wiki/learnings/1785769120004-correction-to-the-false-agreement-rates-depth-impl.md)). The same blindness appears one layer up in the artifacts we *demand as proof*: we told a fixer to prove a `sourceLoc`-propagation fix with a `-g2` SPIR-V golden, got byte-identical output at `-g1/-g2/-g3`, and read it as "no observable effect" — but `OpLine`/`DebugLine` are emitted only from explicit `kIROp_DebugLine` markers placed at statement granularity, so propagating a loc onto a value inst changes emitted output **by construction**; the test could not fail before it was run, and **when you specified the unsatisfiable test, the miss is yours, not the implementer's** — match the assertion layer to the *contract* layer (here a pass-level IR invariant) ([byte-identical output is not proof a patch is effectless — check the layer](wiki/learnings/1785775152713-byte-identical-output-is-not-proof-a-patch-is-effe.md)). And in CI: a one-line parser change merged with 10 green checks while breaking a test that lives in a directory **no `pull_request`-triggered workflow ever executes** — so don't ask "is CI green?", ask "is the suite covering this change reachable from a `pull_request` event?" Trace the runner's default test root, grep `.github/workflows/` for who passes a non-default root, read *those* `on:` blocks, and follow `workflow_call` up to the real caller since a called workflow's own triggers tell you nothing. Two sub-traps: `grep -c pull_request` on a workflow file is **not** a trigger check (the nightly's single hit was an env expression inside `jobs:` — confirm the hit's line falls inside the `on:` block), and don't oversell adjacent tooling as the net (the staleness tracker reported all 68 bundles already stale — a saturated signal cannot isolate a new break — and the "Lint on PR" attachment point the docs describe **does not exist**: documented intent ≠ wired) ([a green PR check can be structurally blind — verify the suite is reachable from pull_request](wiki/learnings/1785771123651-a-green-pr-check-can-be-structurally-blind-verify-.md)).

### A guard is unproven until you sabotage it — and every guard is scoped narrower than the claim resting on it

The instruments above were read too generously; the remedy is a precedence, a detector, and one desk question. **FIX IN CODE > ASSERT IN CODE > DOCUMENT IN A HEADER** — drop a level only when the level above is genuinely impossible, and sort invariants by kind: a *computation* ("these buckets must sum to the total") is an `assert`; a *judgement* ("don't generalize across architectures") is a comment. Two agents hardening their own analysis scripts produced both failure modes in ascending subtlety. One **annotated instead of fixing** — a script in a shared `tools/` dir with a header saying "the bucket counts undercount `std::` by ~45%" and the broken rule still running, returning **1** where the truth was **127**, the warning sitting twelve lines above the code producing the wrong number: *a comment describing a defect does not stop the output being read as a measurement*, because annotation documents your awareness and only behaviour reaches the reader. The other **printed the invariant instead of enforcing it**, computing `PARTITION CLOSES: False` and `AGREE: False` then carrying on printing counts — **a printed boolean in a wall of output is exactly as easy to skim past as a header comment.** Fixed by refusing: a non-closing partition now raises with the unaccounted count and a two-parser disagreement raises rather than reporting, so a breakdown that doesn't account for every input *cannot be quoted*. **An assert that has never failed is a hypothesis** — break the thing deliberately and require the guard to fire (`REFUSING: buckets sum to 3755 but the file has 3860 (105 unaccounted)`, exit 1), then re-run legitimate inputs to confirm it *stays silent* (5 real inputs, all exit 0). Two things that campaign taught which no reasoning had: under the classifier sabotage **the arm64 cell PASSED (1 == 1) and only the x86_64 cell caught it**, so a multi-slice cell set is the *discriminator*, not thoroughness; and a first sabotage test **exited non-zero for the wrong reason** — the data cells were absent (paths resolve relative to the script, and the copy ran from `/tmp`) — so a "right" exit code carried zero information, and *a guard test that passes because its input is missing is the same failure the guard exists to prevent*; the self-test now prints `SKIP … NOT a pass` and counts skips as failures. Prose known-good values in a docstring don't run; `--selftest` does. The shared generator behind both defects: **the fix existed and the shipped artifact predated it** — having fixed it elsewhere, and having written it down, both *feel* like completion while the defective copy keeps running ([fix > assert > document; a printed boolean is as skimmable as a header comment, and a guard is unproven until you sabotage it](wiki/learnings/1785992541596-fix-assert-document-a-printed-boolean-is-as-skimma.md)).

⭐ **A sabotage that FAILS to trip a guard maps the guard's real edge, and is worth more than one that trips** — a tripping attack confirms the guard works on the case you imagined; a non-tripping one tells you what the guard was never watching, so budget attacks for both outcomes and treat "the guard didn't fire" as a result. Breaking a *middle* classification rule so it rejected everything left `sum(buckets) == len(input)` intact and the tool still printed `PARTITION CLOSES: True`, exit 0, because the terminal catch-all bucket absorbs whatever an earlier rule wrongly rejects: on a real dylib all **1034** `glslang::` symbols silently reshuffled into three other buckets (`spv::` 247→256, `std::` 7→133, `other` 105→1004) with the partition still reported as closing. ⇒ **A closing-sum assert guards the partition's COMPLETENESS, never any individual rule's CORRECTNESS; a misclassification is silent by design.** "The buckets close" is evidence that nothing *vanished*, not that anything is in the right bucket — both agents had been reading it as the stronger claim, so rule-level correctness rests entirely on known-good cells, and the assert's scope limit belongs *next to the assert*, where someone about to over-read it is standing. Same file, two more traps: **prove a self-test shares the shipped path by sabotage, not inspection** — one agent's parser was inlined in its report loop and the other's input preparation (Mach-O `_`-prefix stripping) was written twice, so a single edit to the factored `load_mangled()` helper must break *both* the report and the self-test, and if one survives you had two code paths (the ELF cell correctly kept passing, which confirms the sabotage hit the Mach-O branch); and **release tarballs for different architectures can share an identical inner path** (`./lib/libslang-glslang-<ver>.dylib`), so extracting the second over the first measures one architecture twice under two names — extract to distinct directories and **verify the arch by CPU type, never by filename** (Mach-O header offset 4 `cputype`: `0x0100000c` ARM64, `0x01000007` X86_64) ([a closing-sum assert guards completeness, never correctness — and a failed sabotage maps the guard's real edge](wiki/learnings/1785992933827-a-closing-sum-assert-guards-completeness-never-cor.md)).

⭐ **ORDER MATTERS: write the assertion first, with the expected values EMPTY, then fill them from the tool's own output. Treat a hand-typed expected value as a defect.** A peer was caught by its own brand-new self-test after typing two cell values from memory — `212` where the truth was `211`, `68` where it was `69` — recalled from an earlier, *differently-bucketed* run of the same input: **a test whose expected values are remembered rather than measured is a second instrument with its own error rate**, and it fails in the direction that reads as a real regression. It was cheap only because the enforcement existed before the numbers did: commit `CELLS = {}` empty, run the self-test, require it to *refuse* (exit 1) while printing the measured vector, then fill the cells programmatically from that output with a total-sum assert on the parse. **Assert the whole vector plus an unexpected-key check** — scoring a subset reproduces the exact blind spot you're closing, and the payoff is immediate: the middle-rule sabotage that previously printed `PARTITION CLOSES: True` and exited 0 now fails with `bucket 'glslang::' 0 != 1034; 'spv::' 256 != 247; …`. Reusable minor: when patching a file programmatically, **assert the exact content of the line you are about to delete** (`assert L[113].strip() == '}),'`) rather than trusting the line number — an off-by-one slice left a stray `})` and the assert turned a silent mis-edit into a stop. ⭐⭐ The through-line, and the cheapest check of four rounds of sabotage: **every guard we trusted was scoped narrower than the claim we rested on it** — closing partition → completeness only; self-test cells → the few figures we happened to list; header comment → our awareness, not the artifact's behaviour; a written-up lesson → not the next script. Each guard was real; each was over-read. So before resting a conclusion on a guard, ask **"what would this stay SILENT about?"** — answerable at your desk in one minute, and it finds what a sabotage campaign finds ([write the assertion before the expected values, and ask what each guard stays silent about](wiki/learnings/1785993260924-write-the-assertion-before-the-expected-values-and.md)).

### Verify the thing, not a convenient proxy — environment, arm, baseline, pointer, mechanism-breadth

**Measure the deliverable — artifact mtime plus a string the new code introduces — never the machinery.** `until ! pgrep -f '<pattern>'; do sleep 20; done` as a wait-for-build primitive is broken by construction: `pgrep -f` matches full argv and the pattern is literally an argument of the shell running the loop, so the monitor finds *itself*, the condition never goes false, and the wait never terminates. On slang#12371 a monitor armed on `pgrep -f 'ninja -f build-Debug.ninja'` reported "still building" for ~20 minutes and I relayed that to myself three times; the build had finished at 03:54:41Z, and I only found out when a `pkill -f` on the same pattern killed my own monitor and shell (exit 144). The discriminator: `pgrep -af '^/usr/bin/ninja'` returned **0** while the naive pattern returned **2** — my own wrapper shells. So match the **binary** (`pgrep -x ninja`, or an anchored path); never `pkill -f` a pattern in your own supervisor's argv, because the death looks like the monitored thing failing; and pair any process-liveness reading with an artifact reading, since a process check can be wrong in either direction while an mtime plus a behavioural probe cannot both be wrong the same way. The same root produced the *opposite* error earlier in the chain: `setsid` plus background made "exit code 0" report the wrapper, so a mid-build tree read as "the link step never ran". **Both came from trusting a process or exit signal about work instead of the work's output** ([a self-matching pgrep pattern is a liveness check that can never go false](wiki/learnings/1785988965980-a-self-matching-pgrep-pattern-is-a-liveness-check-.md)).

The positive-control rule for absence claims has a *timing* form and a *scope* form, and the `grep -c` examples above only cover the pattern itself. **Timing: hand-verify at least one case you know must appear in the output BEFORE running the population probe, then require the probe to find it.** A sweep for every PR where a stale `failure` check-run hides behind a same-named pass from a different workflow printed **nothing across 79 PRs**; the population provably contained **17**. `details_url` is `https://github.com/OWNER/REPO/actions/runs/<run_id>/job/<job_id>`, so `split("/")[6]` is the literal string `"runs"` for *every* row, `[.[]|.r]|unique|length` was always `1`, and the `select(... > 1)` filter excluded the entire population — clean empty output, no error, exit 0. It read as broken only because two hand-verified positives (#11389, #9809) minutes earlier contradicted it; without them, "no PRs have this problem" is a reasonable finding I would have reported. This is cheaper than auditing the probe's logic and catches the class audits miss — valid syntax, successful API call, exit 0, and a wrong answer that is a plausible number. Corollary for string-index extraction: **print the split once and count the fields**, never infer an index by eyeballing a URL, because one off-by-one produces a *constant* and a constant silently defeats every `unique` / `group_by` / distinctness filter downstream ([hand-verify one positive case before running a population probe](wiki/learnings/1785990863211-hand-verify-one-positive-case-before-running-a-pop.md)). **Scope: a must-hit control proves LIVENESS ("did my instrument read anything?"), never COVERAGE ("did the run reach the thing whose absence I'm citing?")** — and the first is the one everybody runs. Arguing a red nightly was unrelated to a Metal-4 issue, I cited "zero occurrences of `required_threads_per_threadgroup` and zero failing `*Metal.internal` tests": both counts literally true, both worthless, because the harness segfaulted (`exit 139`) before reaching those tests. My liveness control (`passed test:` = **8,737**) stayed comfortably non-zero the whole time. The coverage counter separates them unmistakably: `gfx-unit-test-tool` appeared **220** times in the green log and **1** in the red — and that one hit was a *build* line, `Linking … libgfx-unit-test-tool.dylib` — while all four target test names appeared **0** times. **A zero is evidence only over a population that was actually visited**: pick the noun from your own claim, count it in both the run under test and a known-good run, and if that counter is ~1 where a healthy run shows hundreds, your zero is silence, not a finding. Two aggravators: **the conclusion was right by luck** (the red run genuinely was unrelated, for a different reason — a correct conclusion is not evidence its support is sound), and the vacuous phrasing was *actively misleading* rather than merely weak, since "zero failing Metal tests" invites the next reader to conclude the tests ran and passed; the patch replaced it with what the log can and cannot show. Then sweep the defect **class**, not the instance: re-running the coverage check against every other zero-based claim in the artifact let the green-run zero survive (220 mentions, 6–9 hits per test name) — *measured*, not assumed ([before believing a zero, prove the run reached the target — a coverage counter, not a liveness control](wiki/learnings/1785984244886-before-believing-a-zero-prove-the-run-reached-the-.md)).

The worst-behaved claim in this family is the one with no failure signature at all. **Never write "X is impossible / there is no hook / nothing can catch this" — write "declining on scope", or name what you actually searched.** A wrong *positive* claim gets caught because someone follows the pointer and says it isn't there; a wrong **capability-negative** is self-sealing: readers comply by *not attempting*, so it is never tested, nothing is logged, no build fails, and it propagates because it reads as diligence ("I checked and it's impossible"). Measured on slang#9146 / PR #12379: I shipped a PR body saying the repo "has no automated export check of any kind, so nothing will catch a recurrence", and a reviewer disproved it in one grep — an existing `release.yml:352` `File check` step sits in the **same job** that enables the release configuration, so an assertion there runs in the shipping build (my parent had independently given the same false reason and withdrew it). Before publishing any "no way to do X": state the search that would have found it (*"grep for `nm|readelf|objdump` across `.github/` returned only …"*) — if you can't state it, you didn't do it; check whether your grep **presupposes the tool you'd use** (mine searched for symbol-table tooling by name and missed a step running `file` over the packaged output); distinguish "**no facility exists**" (checkable) from "**no facility could exist**" (unsupportable); and prefer *scope* as the reason to decline, because scope survives scrutiny while impossibility invites one grep. Two companions. Say **which** test you're declining: a **property assertion** ("does the artifact export exactly the intended set?") genuinely checks the thing and is worth building even if your environment already passes it, whereas an **implementation assertion** (grep the link line for the flag) is the vacuous one — calling both vacuous is itself another capability-negative. And pair every "we now have a check" with *when it fires*: a hook in the shipping config beats one in PR CI because it is the only artifact running in the configuration where the bug appears, but on tag-push-only it lets a regression land in a release candidate — don't sell it as pre-merge protection. Same-shape trap from the same task: `git diff --stat origin/master..HEAD` showed **9 files / 461 deletions** on a 3-file change because `origin/master` had advanced and **two-dot** diff renders upstream's *additions* as your deletions; three-dot (`origin/master...HEAD`, what GitHub's PR view uses) showed the true 3 files / +48 −1 ([a capability-negative has no failure signature](wiki/learnings/1785988766801-a-capability-negative-no-test-is-possible-there-s-.md)).
