## TL;DR
- **A read of a live artifact is a MEASUREMENT WITH A TIMESTAMP, not a fact.** PR state, CI conclusion, draft/ready, review state, infra capability — all mutate. Re-probe before citing.
- **"Answer instantly" authorizes posting exactly the facts you verified at the precision you verified them** — never an extrapolated new *positive* capability claim. If the verified fact is a negative, the instant answer is that negative plus citations.
- **Verifying an ENFORCING gate needs a security-review mindset** — enumerate the cross-product of input conditions (combined-input bypass) and prove the build-wiring actually produces the artifact in the CI preset that invokes it.
- **Authorize a user-facing workaround only when verified in the USER's actual environment**, not a convenient proxy; an *adds-capability* claim needs environment-matched proof. Audit authorization provenance (does the quoted maintainer comment exist?) before repeating it in a public artifact — "verify it's clean" means read the CURRENT bytes.
- **On resume, live git/gh state beats the replayed transcript** — a later maintainer merge/comment supersedes an earlier bot commit; forward-commits-only, never force-push over a maintainer's merge.
- **Associate a CI run to THIS PR + head (displayTitle + head SHA) before crediting its conclusion** — cancelled ≠ pass ≠ stale; cross-repo `repository_dispatch` runs carry the downstream repo's head_sha, so match by PR-number in the title.
- **A census supplies a denominator; only a differential run supplies a ratio.** A ratio of two totals cannot be applied to a delta. A heterogeneous list cannot be validated by sampling — store stems, not full forms. Test a claimed capability gap before carrying it forward.
- **`gh pr view --json` 401s ONLY WHILE GraphQL IS DOWN** (gh routes it via GraphQL; REST stays healthy) — probe `gh api graphql -f query='{viewer{login}}'` first; the REST recipe is a fallback, not a requirement.

## Answer-Instantly Means Post Verified Facts, Not an Extrapolated Positive Claim (2026-07-21 fold)

A standing instruction to "answer a re-ask instantly" with citations in hand authorizes posting **exactly the facts you actually verified, at the precision you verified them** — it does NOT authorize extrapolating a *new positive capability claim* you haven't tested. On slang#11877 the verified fact was a *negative* ("the JS/WASM bindings expose no compiler-option surface"); "answer instantly" was misread as "produce a helpful-sounding answer fast," and a bot comment substituted a more satisfying *positive* ("`import glsl;` is a flag-free route that works from JavaScript") that went beyond — and actually contradicted — the verified negative. The reporter tested it, hit `E38201`, and refuted it publicly, forcing a correction. The discipline: if the verified fact is a negative, the instant answer is that negative plus its citations; any new positive capability claim ("this route works", "you can do X via Y") requires testing before posting — a repro, a source-traced path, or an existing cited fact — never an extrapolation to satisfy a fast-answer instruction ([Standing answer-instantly = post verified facts, never extrapolate a positive claim](../learnings/1784551466296-standing-answer-instantly-post-verified-facts-neve.md)).

## Verifying an ENFORCING Gate: Combined-Input Bypass + Build-Wiring Reachability (2026-07-21 fold)

Verify-at-head on a *tool that enforces* (a check that `exit 1`s to block a PR) needs the adversarial mindset of reviewing a security check — "how does this fail to fire / how does the bad input slip past?" — not "does the happy path read correctly?" Two recurring failure modes each pass a naive per-branch read, both learned from a live miss on slang#12157's IR-version-bump differ (PR #12158) that a verify-at-head pass approved and the reviewer+codex pipeline then reopened. **(1) Combined-input bypass.** The differ enforced "new IR instruction added ∧ version not bumped → fail" but had a `removedKeys > 0 → return 0` early-return that is individually defensible ("a rename shouldn't hard-block") — yet in *combination* (a PR that removes/renames anything AND independently adds a new instruction) the early-return let the new instruction ride in with no bump, silently defeating the exact case the gate exists to catch. Discipline: enumerate the *cross-product* of input conditions ({added} × {removed/renamed}) and confirm the enforced case still fires under every combination, especially where an early `return 0`/short-circuit precedes the enforcing branch; the fix here keyed on stable identity (instruction stable-ID absent from the base set = genuinely new) with no early return. **(2) Unproven build-wiring.** The tool was registered via a CMake `generator()` macro wiring it only under `all-generators`, which the default `cmake --workflow --preset debug` (the CI build the check runs in) does NOT pull — so the binary was never built in that path and the wrapper's `find` would be empty → `exit 1` on every PR (fail-closed the wrong way). The PR body's "built via all-generators dependency" claim was accepted, not proven. Discipline: when a check depends on a build artifact, prove the artifact is produced by the specific CI build/preset that invokes it (trace the dep graph or build it) — same class as "verify claimed artifacts," but for build-graph reachability; the fix was an explicit `add_dependencies(slang-test <tool>)` ([Verify-at-head: check enforce logic against COMBINED inputs + prove build-wiring, don't accept it](../learnings/1784568390472-verify-at-head-check-enforce-logic-against-combine.md), [Verify enforcing gates against combined-input cases + prove build-wiring](../learnings/1784568398186-verify-enforcing-gates-against-combined-input-case.md)).

## Environment-Matched Verification + Auditing Authorization Provenance Before It Reaches GitHub (2026-07-22 fold)

**Authorize a user-facing workaround claim only when verified in the USER's actual environment, not a convenient proxy.** On slang#11877/discussion#11840 a bot told an external user `import glsl;` is a flag-free route to GLSL matrix-operator semantics from the JS/wasm frontend; the claim was FALSE (`error E38201: 'glsl' module not available`). The fixer's "gate (b)" empirically confirmed it on the NATIVE built compiler (where the `glsl` module IS available) — proving "works when the module is registered," NOT "reachable from JS/wasm" (the actual question; `enableGLSL` defaults false and the wasm binding never exposes it). Before authorizing any workaround: match the verification environment to the CLAIM's environment (ask "was this verified in the user's exact frontend/flags/build, or a convenient one?"); hold an *adds-capability* claim ("X enables Y") to environment-matched proof (higher-risk than a *removes-capability* claim, since it strands the user if wrong); and rest a corrected bot claim on independent evidence (the user's own repro + the diagnostic text), not the same bot's say-so ([authorize external workaround claims only when verified in the USER's environment, not a convenient proxy](../learnings/1784627888989-authorize-external-workaround-claims-only-when-ver.md)).

**A relayed authorization can carry a fabricated maintainer attribution into public GitHub artifacts — audit the bytes, attribute policy to the actual authorizer.** On slang#12176 the orchestrator relayed a draft-PR authorization framed as a verbatim maintainer quote ("jkwak-work commented: 'create the README as a draft PR'") with a comment id that 404'd — the quote was manufactured, and the false attribution propagated into a public issue comment AND the PR body ("per the maintainer's go"). The trap: because the "maintainer's go" was believed when the downstream artifacts were written, the first "verify nothing fabricated reached GitHub" report wrongly said "clean" — only re-reading the live bytes (`gh api …/comments/<id> --jq .body`, `gh pr view --json body`) exposed it. Rules: verify authorization provenance (does the quoted comment actually exist?) before repeating it publicly; attribute a go-ahead that came from the relayer's judgment as "per the handoff / held pending maintainer review," never "the maintainer asked for X" unless their words are in a real inbound; "verify it's clean" means read the CURRENT bytes, not your memory of what you wrote; and fix on the right surface (your own comment → PATCH; the PR body → route to the fixer) ([a relayed authorization can carry a fabricated maintainer attribution into public GitHub artifacts — audit the bytes](../learnings/1784656869644-a-relayed-authorization-can-carry-a-fabricated-mai.md)). ⚠️ **`gh pr view --json` 401s ONLY WHILE GraphQL IS DOWN** (gh routes it via GraphQL; REST stays healthy) — ⛔**this was previously written as a standing property of the bot token, which is FALSE: refuted 2026-08-04, `gh pr view <n> --json isDraft,state,reviewDecision,mergeStateStatus,headRefOid` returned full JSON, exit 0.** **Probe `gh api graphql -f query='{viewer{login}}'` first**; if it answers, `--json` works and the REST recipe below is a fallback, not a requirement — use `gh api repos/<owner>/<repo>/pulls/<n> --jq '{draft,state,mergeable,mergeable_state}'` (REST is snake_case: `draft`/`mergeable_state`, not `isDraft`/`mergeStateStatus`), and get approval-on-head from `pulls/<n>/reviews` where `commit_id == .head.sha` — `reviewDecision` never establishes that an approval covers the current head.

## On Resume, Live git/gh State Beats the Replayed Transcript (2026-07-23 fold)

When a session resumes/replays older messages, live git/gh state can be days ahead of the transcript you're answering — before acting on a replayed instruction, verify with `git log origin/master..HEAD`, `gh pr view --json headRefOid,isDraft,state`, and latest comment timestamps; git/gh + your own memory are authoritative, the replayed transcript is a point-in-time snapshot and a later maintainer comment SUPERSEDES an earlier bot commit. Two hard constraints follow: a non-draft PR carrying a maintainer's merge commit is forward-commits-only (never force-push over their merge), and removing content is safe only when it's your OWN prior work the maintainer asked to remove. On #12178 the replayed "open a DRAFT / don't include X" would have force-pushed over a 07-22 maintainer merge and re-deleted blessed work — the stale-close safety net is to drop `Closes #N` from the PR body (not amend the commit) and reopen if needed ([on resume, git-gh state beats replayed transcript (stale-replay reconciliation)](../learnings/1784765800190-on-resume-git-gh-state-beats-replayed-transcript-s.md)). ⚠️ **`gh pr view --json` 401s ONLY WHILE GraphQL IS DOWN** (gh routes it via GraphQL; REST stays healthy) — ⛔**this was previously written as a standing property of the bot token, which is FALSE: refuted 2026-08-04, `gh pr view <n> --json isDraft,state,reviewDecision,mergeStateStatus,headRefOid` returned full JSON, exit 0.** **Probe `gh api graphql -f query='{viewer{login}}'` first**; if it answers, `--json` works and the REST recipe below is a fallback, not a requirement — use `gh api repos/<owner>/<repo>/pulls/<n> --jq '{draft,state,mergeable,mergeable_state}'` (REST is snake_case: `draft`/`mergeable_state`, not `isDraft`/`mergeStateStatus`), and get approval-on-head from `pulls/<n>/reviews` where `commit_id == .head.sha` — `reviewDecision` never establishes that an approval covers the current head.

## Associate a CI Run to THIS PR+Head Before Crediting Its Conclusion (2026-07-24 fold)

Before saying a check is "green/cleared" or "flake/stale," verify each run's *association* — its PR number (`displayTitle`) AND head SHA — not just its conclusion. On slang#12202 (twice) two distinct over-claims shared this root: "11319 passed / 0 failed = infra flake" was read from an *earlier/different attempt* than the one red on the current head, and "requeue cleared it" cited two `success` slangpy `repository_dispatch` runs that were actually for *other PRs* (#12190/#12206). Also distinguish red *causes* on a rollup: a `failure` commit-status can point to a run that was **`cancelled`** (superseded by head-churn), NOT a test failure — a cancelled run is this head's own run killed, neither a pass nor a stale-old-head artifact; clear it with ONE clean requeue allowed to run to completion. Rule: pull the specific run the failing status/check points to (`gh api .../commits/<sha>/statuses` or `/check-runs`, follow `target_url`), confirm its `displayTitle` names THIS PR and its head is THIS head, and read the actual `conclusion` (`success`/`cancelled`/`failure`). Cross-repo `repository_dispatch` runs (slang→slangpy) carry the *downstream* repo's head_sha, so match by PR-number in the title, not head_sha. For the orchestrator: a coworker's "all green / cleared" on a routed chain is a verdict — verify at claim-precision (the exact run, not the rollup summary) before relaying upward; two consecutive over-clean reports from one source warrant tightening ([Verify a CI run belongs to THIS PR/head before crediting its conclusion](../learnings/1784873907730-verify-a-ci-run-belongs-to-this-pr-head-before-cre.md)).

## Denominators, ratios, and sampled lists: five ways a correct measurement assembles into a wrong number (2026-08-11 fold)

**A census supplies a denominator; only a differential run supplies a ratio.** On the slang#12311 re-open, two tiers produced two coverage ratios — "fixes 1 of 4" and "2 of 4" — and **both were malformed from the same root**: a census was used as a denominator without asking whether each member was *eligible for the outcome*. The census was core-module interfaces declaring `__init(int)` but no `__init(float)` → 4 (`IArithmetic`, `ILogical`, `IInteger`, `ICoopElement`); one was fixed, hence "1 of 4". A peer correctly spotted that transitivity was ignored (interfaces deriving from `IArithmetic` get the fix for free) but then computed the replacement digit by **reading inheritance clauses instead of running the cases** → "2 of 4". Per-cell measurement against PRE and POST binaries with a passing control showed the fix cures **3** shapes, with `ITexelElement` and `IInteger` inheriting it. ⇒ A membership list bounds the question; the numerator has to come from executing each member, and reading the declaration that *should* imply the outcome is the same class of error as reading the census that *should* imply eligibility ([a census supplies a denominator; only a differential run supplies a ratio](../learnings/1786344197524-a-census-supplies-a-denominator-only-a-differentia.md)).

**A ratio of two TOTALS cannot be applied to a DELTA — and a correction can repeat the defect it is correcting.** A published "deserialized IR is ~20× its packed form" was a **bridging factor**: it glued two genuinely-measured endpoints (a `+4.56 MiB` growth in a serialized blob, a `+90.4 MiB` growth in peak RSS) with a factor nobody measured. A maintainer's RFC replaced it with a measured **3.10×** — and the first correction draft applied *that* to the same `+4.56 MiB` delta, got `+14 MiB`, and wrote "so ~76 MiB is unexplained." Invalid for a precise reason worth internalizing: 3.10× is a ratio of two **whole-module totals** (in-memory ÷ serialized), i.e. an **average**, and applying an average to *marginal* content assumes expansion is uniform across all content — never measured, and the in-window additions were a specific subsystem's interfaces plus a rewrite, i.e. exactly the content most likely to expand differently. It took three critique rounds to remove. ⇒ Before multiplying, ask whether the factor's numerator and denominator are the same *population* as the thing being scaled; a total-derived average has no license over a delta ([a ratio of two totals cannot be applied to a delta](../learnings/1786351696739-correcting-a-bridging-factor-a-ratio-of-two-totals.md)).

**A heterogeneous list cannot be validated by sampling — store stems, not full forms.** A substring-matched vocabulary of forbidden verbs was validated by running one real offending sentence through the predicate; it raised, and the list was declared tuned. The next day a differently-worded instance walked straight past it. The list **mixed** stems (`quarantin`) with full forms (`auto-close`), and the sample happened to hit a stem — `"auto-close" in "auto-closing"` is **False** on a one-character gerund gap, so the untested member lacked the very property the tested one had. The rule is stronger than "be robust to inflection": **a list whose members are heterogeneous in form cannot be validated by testing one member**, and making it homogeneous (all stems) is what *restores sampling as a valid test* — while a single later full-form addition silently destroys that property for the whole list. The deeper shape, a third instance in two sessions: **a correct result about ONE MEMBER read as a property of the MECHANISM**, and each time the sampled member was the well-behaved one, because you reach for the example already in hand ([a heterogeneous list cannot be validated by sampling](../learnings/1786351185283-a-heterogeneous-list-cannot-be-validated-by-sampli.md)).

**Test a claimed capability gap before carrying it into a second run.** A monitoring agent recorded "this seat cannot enumerate Discord forum threads (no token, no `discord_list_threads`)" and instructed the next run to report those channels as "cannot confirm, never quiet." A working bot token was **already on disk** (`/workspace/agent/memory/.discord-token`) and one `curl` to `GET /guilds/<id>/threads/active` returned HTTP 200 with 36 threads, `has_more: false` — and the *previous* day's own artifact documented the working recipe including a positive control. So the capability was recorded working on day N−2 and missing on day N−1, and **the pessimistic note won purely because it was newer**. Cost: two support threads unreported, one a user hitting a compiler bug whose fix PR had sat one approval short for 11 days. ⇒ Re-test any capability gap before carrying it forward (10 seconds), grep your own prior artifacts for a working recipe first, and treat a capability that **downgrades** between two consecutive notes as a claim to re-derive rather than inherit ([test a claimed capability gap before carrying it into a second run](../learnings/1786350645999-test-a-claimed-capability-gap-before-carrying-it-i.md)).

**Two operational shapes from the same discipline.** *Triaging a maintainer's architectural RFC* (slang#12447, lazy deserialization of core-module IR, 5 explicit open design questions + a DRAFT prototype): a triage draft verified every source anchor correctly and still had to be rewritten, because correct verification assembled into the **wrong genre** — sentences like "the assumption looks well-founded" / "so this is not a counterexample" are **verdicts on questions the maintainer reserved for himself**, and codex judged the comment "functions as an architectural mini-review." On an RFC, supply **source anchors, not answers**, and check whether the maintainer already published the number you are about to lecture them about ([triaging a maintainer's architectural RFC: source anchors, not answers](../learnings/1786350576341-triaging-a-maintainer-s-architectural-rfc-source-a.md)). *Splitting the daily PR report for Discord* (~9.5 KB body vs a 2000-char cap): the exit-code contract is load-bearing — run `pr_report.py 2>/dev/null` and branch on `$?` (`10` = report due, post it; `0` = quiet day, do **not** post; anything else = transient, do not post, next fire retries), with stderr excluded because it is per-repo progress chatter and the body starts after the `--- report ---` marker. Chunk at assignee-bullet boundaries (`- **`), knowing one assignee block can itself exceed the budget, and **verify by line-set comparison** rather than eyeballing ([splitting the Slang PR report for Discord: chunk at assignee boundaries and verify by line-set](../learnings/1786338436692-splitting-the-slang-pr-report-for-discord-chunk-at.md)).
