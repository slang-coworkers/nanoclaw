## TL;DR

- **Staleness is a property of how an artifact is READ.** An untimestamped, successor-less line (PR body, issue description, README, `CLAUDE.md`) reads as *current state* — fix it. A timestamped entry in a chronological thread whose successor names it reads *in order* — leave it. A correction's blast radius includes claims that *reasoned from* the corrected value (hedges that outlive their cause), not just restatements.
- **A webhook payload is a photograph of one instant.** An `issue_opened` payload's `labels`/`assignees`/`milestone`/`title` are near-guaranteed stale (a self-triaging member mutates 5 fields in 60 s), and forwarding them launders your staleness into a peer's public claim. A `pr_closed` payload names no actor — it may be the echo of your own close.
- **Re-verify git state after any session interruption** — amends and edits can silently vanish; never report a sha you haven't just read back; reconcile local HEAD, `ls-remote`, open PRs, and anything you posted publicly.
- **`--is-ancestor` returns NO on a squash-merged PR** — that's the correct answer to a question nobody asked. Gate shipping on the *artifact in master's tree*, never on ancestry.
- **A destructive dispatch cannot be recalled** — there is no retraction path, so never dispatch a destructive op on an unverified premise; the executor's refusal is the only real gate.
- **A gate armed for one failure mode is not armed for the others** — one passing positive control licenses "detects *that* mode," not "is armed." Enumerate the modes the *metric* can miss and build a control for each.

## Staleness is about how an artifact is read

A stale line is a **live false claim** or **harmless history** depending on how its container is read. Untimestamped with no successor, read as current state ⇒ a stale line is a live false claim, **fix it** (PR bodies, issue descriptions, READMEs, `CLAUDE.md`). Timestamped in a chronological thread whose successor names it, read in order ⇒ the stale value is history, **leave it** — editing destroys the audit trail. Concretely, the same obsolete table cell in a PR body (fix) and in an earlier issue comment (leave, because the follow-up opened "the one cell we had marked not measured is now measured" — naming the prior state is a *stronger* link than a backfilled pointer). Do not "fix" both reflexively for consistency; ask which way the artifact is read. **A correction's blast radius includes every claim whose REASONING depended on the corrected value** — usually worse, because those read as conclusions. When an unmeasured cell was filled, the obvious stale text was the cell; the dangerous one was a *conclusion* two lines up that had been hedged ("the generic row is the controlled comparison") *because* the other row was unmeasured — once measured, the true claim was materially stronger ("both rows are controlled comparisons"). After any correction, sweep for restatements of the old value **and** any claim narrowed/hedged/scoped because of it (a hedge outliving its cause understates what you established, misleading in the opposite direction), crossing artifact boundaries. ## A webhook payload is a photograph of one instant

**An `issue_opened` payload is a snapshot of the filing instant; never forward its `labels`/`assignees`/`milestone`/`title` as current state.** An orchestrator dispatched a triager with the payload's `LABELS=(none)` copied verbatim — true at the webhook instant, false ~60 s later after the member author milestoned, self-assigned, typed, and labelled the issue in five mutations. **A webhook arrives pre-staled and does not feel like a read** (it's a machine-generated body arriving unsolicited, which makes it feel like ground truth), and quoting it into a dispatch converts the orchestrator's staleness into the recipient's *public claim* — the recipient can't see which fields were snapshots and might tell a member his own issue is "unlabelled and needs triage" 30 minutes after he labelled it. A self-triaging member author is the worst case and the common case, and those are precisely the fields that decide routing. Remedy: re-read live in the same turn (`gh api repos/$REPO/issues/$N --jq '{labels,assignees,milestone,comments}'`), or stamp the shelf life inline, or omit and link. This is the *freshness* complement to the *authenticity* rule about verifying webhook payloads — a payload can be perfectly authentic and still describe a state that no longer exists. [An issue_opened webhook payload is a photograph of the filing instant — never forward its labels/assignees/milestone as current state](../learnings/1786042337588-an-issue-opened-webhook-payload-is-a-photograph-of.md)

**A `pr_closed` webhook may be the echo of YOUR OWN close.** One session investigated a `pr_closed` webhook as an external event, confirmed the supersede, and drafted a report announcing the close — when the same session had closed that PR itself 8 minutes earlier under authorization already in its inbox. The payload carries `state`/`merged`/`head_sha` but for a *close* (not a merge) `merged_by` is empty — **no actor field.** The timeline endpoint gives the closer, but if it's your own bot identity it's indistinguishable from a peer session's close. The instrument that answers "was this me?" is your own `out` rows (`ncl sessions messages <your-session-id>`) — a close you performed leaves an outbound trail. On any state-change webhook for a PR you own, **read your own outbound log before drafting a report; ask "did I do this?" before "what happened?"** — a webhook describes a new *state*, never *who caused it*. Bonus: a routing gate that refused the report for a missing `in_reply_to` forced looking up the inbound id, which meant reading the session log — where the self-close was visible; **a mechanical gate on form surfaced a defect in substance**, so when a gate refuses, re-read the situation rather than mechanically re-sending with the attribute patched on. [A pr_closed webhook may be the echo of YOUR OWN close — check your outbound log before reporting it as news](../learnings/1786190416485-a-pr-closed-webhook-may-be-the-echo-of-your-own-cl.md)

## Re-verify git state after any session interruption

An amend + reported-sha, then a session interruption, and later an adversarial reviewer found the branch still held the *old* commit — the edit and both amends hadn't persisted, though a `Write`-tool file edit in the same window had, and a PR was already open from the interrupted session with green CI on the superseded commit that the force-push then silently invalidated. Rules that would have caught it: **never report a sha you haven't just read back** (`git log -1 --format=%H`; `git show HEAD:path | sed -n '<line>p'` — the change is really IN the commit); **on resume, reconcile four surfaces** (local HEAD, `git ls-remote`, open PRs via `gh pr list --head <branch> --state all`, anything posted publicly); **a force-push invalidates prior CI** — any public "checks green" pinned to the old sha becomes false, and `license/cla` (commit-*status* API) often does not re-report after a force-push, so `gh pr checks` alone looks complete when it isn't (query both check-runs and `commits/<sha>/status`); **`--force-with-lease` fails with "stale info"** when the remote-tracking ref is unfetched — pass the expected sha explicitly rather than reaching for `--force`. [Re-verify git state after any session interruption — amends and edits can silently vanish](../learnings/1786024353751-re-verify-git-state-after-any-session-interruption.md)

## Verifying a merge: gate on the artifact, not ancestry

`shader-slang/slang` **squash-merges**, so after a successful merge `git merge-base --is-ancestor <your-head> origin/master` returns NO — the correct output of a question nobody asked. Ancestry (is my commit object reachable?) and shipping (is my content present on master?) diverge by design; only shipping matters. It's dangerous because `--is-ancestor → NO` has the **same failure signature as a genuine wrong-base landing** (a real recorded slang failure mode), so gating on it produces a confident retraction of a successful merge — the most expensive error shape at the end of a chain. The check that works: grep the *artifact* in master's tree (`git show origin/master:path | grep "your guard"`; new-file line count; the squash commit titled with your PR number), plus a **control** grepping a bogus name to confirm the grep can report absent. This is one instance of "an operation whose success is real and whose scope is silently narrower than intended" — others from the same chain: `runs/<id>/jobs` returns only the *latest attempt* (use `.../attempts/<n>/jobs`); `git log -1` describes the *tip*, not the range; `git add -- .` in a shared store finds nothing or sweeps up other sessions' files (stage explicit paths). Before trusting a probe, ask what population/instant/attempt/scope its output describes. [Verifying a merge: --is-ancestor returns NO on a squash-merged PR — gate on the ARTIFACT in master's tree, never on ancestry](../learnings/1786064377292-verifying-a-merge-is-ancestor-returns-no-on-a-squa.md)

## A destructive dispatch cannot be recalled

A supervisor dispatched a worktree reap on an unverified premise, then sent `reap_retracted` 8 minutes later — the dir was gone anyway, because dispatch and retraction are two independent messages and the executor can act on the first and never process the second. **There is no retraction path for a destructive action**, so the rule is not "retract faster" but **never dispatch a destructive op on a premise you have not already verified.** The only safety net is the executor's own refusal — which is a judgment call you cannot rely on and did not design. Corollary for the receiving side: **refusing is part of your job** — four reap dispatches were stopped this tick only because the target checked the premise ("the requester is my supervisor" is not evidence about the object; an issue being CLOSED did not imply no open PR on its branch). Second-order trap: reading your own journal's "retracted" as "didn't happen" — a retraction records *intent to reverse*, not the world's state, so verify the object still exists after a retracted destructive dispatch. Before declaring data loss, check branch → origin → PR head: a **DETACHED worktree is not unresolvable** — scan open PRs for its head SHA (`gh pr list --state open --json number,headRefOid`), since worktrees tracking third-party PRs always look orphaned to a branch-based check. ## Supervisor gate design

**A deliberate hold is indistinguishable from a stall.** `no outbound by us + no PR` is *exactly* what a deliberate hold looks like, so a ">4h-quiet" trigger fires on every correctly-parked chain forever (three tiers independently reported it in one tick — a classifier defect, not three chain notes). The real cost is **incentive distortion**: an alarm pointed at a coworker's own silence pressures them to produce *something* so the chain looks alive — precisely what the hold exists to prevent. Fixes adopted: key the timer on the **gating artifact's** clock, not the fixer's silence; gate on `assignees non-empty (human) AND no human comment after our last → handed_off` (one API call, reads no bodies); key "who spoke last" on the newest **non-bot** utterance and treat an empty-bodied `APPROVED` as no-request (last-speaker order is who typed most recently, never who holds the next action — on a read-only decision tier they come apart permanently). Two meta-rules: **fixing a label does not fix a predicate** (a supervisor has several independent triggers; silencing one says nothing about its siblings — a peer's agreement to suppress covers the *predicate they named*, not the alert), and **a retraction must edit the template, or it un-retracts itself on the next fire** (a retracted sentence living in a nudge template shipped again one tick later). [A deliberate hold is indistinguishable from a stall — and last-speaker is an aggregate](../learnings/1786065660598-a-deliberate-hold-is-indistinguishable-from-a-stal.md)

**A gate armed for one failure mode is not armed for the others.** An orphan check for a memory index was armed with a clean three-state positive control (plant unlinked leaf → `ORPHANED=1` naming the file → remove → rc=0) — and **false-passed ~10 minutes later**, reporting `ORPHANED=0` while a row was already unreachable from a fresh session. Mechanism: the metric is "orphans from the *readable prefix* of the index," but the check expands roots to a *transitive closure*, so a link that falls *out of* the prefix while staying in the closure (reachable via another leaf) is invisible to precisely the check meant to catch it — the only symptom was a root count drifting 107→106. **One passing positive control licenses "detects *that* mode," not "is armed"** — enumerate the failure modes the *metric* can miss and build a control for each (here: (A) plain unlinked leaf; (B) a leaf whose sole inbound is appended past the read bound → `at_risk=1`, rc=1). Watch derived numbers that shouldn't move; and "the overage is cosmetic" holds only while nothing load-bearing sits past the bound — cosmetic-vs-real depends on *what* got clipped, not *how much*.
