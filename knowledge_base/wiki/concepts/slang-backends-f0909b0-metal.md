# Metal backend — emit bugs, intrinsic-string codegen, argument buffers, groupshared, read_write texture fences, and GPU-free repro

## TL;DR

Metal backend bugs and the discipline for reproducing them without a Mac/GPU:

- **Most Metal bugs are GPU-free reproducible**: `slangc -target metal` on Linux shows emit-time crashes and wrong emission. "Metal is CI-only" holds for runtime behaviour only. Defeat folding/hoisting with a runtime, single-use operand.
- **Texture-intrinsic emit lives in the core-module intrinsic-string layer** (`hlsl.meta.slang` `__intrinsic_asm` + `slang-core-module-textures.cpp`), not mainly in `slang-emit-metal.cpp`; fix it there and keep the emitter dumb. Contrast controls (color vs depth, MS vs non-MS) decide the scope, not the reported type; a sibling backend's arm often already has the right guard.
- **`__intrinsic_asm` arms are pasted with no cast**, so a Metal arm hard-coding a narrower type (`as_type<half>` in `f16tof32`, `as_type<ushort>` in `f32tof16`) silently changes the declared type; it fails only where MSL won't convert implicitly. Grep for hard-coded `as_type<half`/`as_type<ushort` instead of `as_type<$TR>`.
- **C-style-cast cases in `tryEmitInstExprImpl` dropped precedence parens** (`(T*)p->field`), a family bug; the repro needs an inlined single-use cast.
- **The Metal argument-buffer tier is a runtime device capability**, not a compile-time choice: one portable struct compiles once and runs on both tiers. Don't bake a tier into the program.
- **DispatchMesh/amplification legalization is Metal-only via virtual dispatch** (a per-target override), not a call-site `if`. Intrinsic-asm threads values only via `$`-operands; bare identifiers emit verbatim and need the name in lexical scope.
- **A Metal binding test must use an index the fallback cannot hit.** An unbound MSL kernel argument takes the first available index, so check an explicit `register(tN)` past every earlier slot, with distinct t/s numbers to avoid E39001.
- **A mesh-shader repro must assign whole output structs**; per-field stores fire E56104 first and hide the real bug. #12883's four bugs landed as #12884, #12885, #12886, #12887.
- **Metal/CPU `groupshared` becomes an entry-point-local var**, so `canInstHaveSideEffectAtAddress` let barriers and callees forward/DSE across it; treat `AddressSpace::GroupShared` roots as globals but keep param roots exempt. Threadgroup declarations take no initializer; cite SPIRV-Cross, not the MSL spec.
- **Metal `access::read_write` textures need `fence()` before AND after every write** (Tint's design). The after-fence is MSL §6.13.17's read-after-write rule; the before-fence fixes Dawn crbug 417296309, which is write-after-read. Read the fixing commit before citing a bug for one hazard direction.
- **The fence pass runs after `legalizeImageSubscript`**, which turns partial texel stores into write→read→write. `fence()` is non-const, so wrap it by value for `ParameterBlock` textures. A texture atomic's leading fence goes before `getRootAddr` of its `ImageSubscript` address.
- **A new IR op on a texture-array element can force a whole-array copy in emit** via `canInstHaveSideEffectAtAddress`'s conservative default. A/B the callee form, not only the entry point.
- **A `-target metallib` lane rejects a kernel with more than 8 `access::read_write` textures** (array elements count individually); give that lane its own small entry point.
- **Ray query** lives on [Metal ray query](slang-backends-metal-ray-query.md) (only a `-target metallib` lane gives CI signal); **buffer element lowering** (packed vectors, layout-rule names, `ParameterBlock` matrices ignoring `column_major` since v2025.18.2; workaround `ConstantBuffer<S>` or `-matrix-layout-row-major`) lives on [Metal buffer element lowering](slang-backends-metal-buffer-lowering-and-layout-rules.md).
- **CI noise on Metal-only PRs**: Falcor-Perf (D3D12/Vulkan only) can never be caused by a Metal-only diff; priority-yield and "Artifact not found" are infra.

## Metal is GPU-free reproducible

Most Metal-backend bugs are visible in `slangc … -target metal` source emission with no GPU or macOS, crashes included: a null-deref during Metal source emission (a `[outputtopology("point")]` mesh passing a scalar `OutputIndices<uint,N>`) makes `slangc` SIGSEGV (exit 139) on the spot, and `SLANG_ASSERT=release-assert-only` with a prebuilt Debug `slangc` demos it in seconds. A wrong-emission bug that bites only for non-trivial operands is masked when a compile-time-constant index is folded or a multi-use sub-expression is hoisted to a temp, so drive the operand from a runtime value used once (an index from `SV_GroupIndex`). Emit the same shader with `-target spirv-asm` as the correct reference ([reproducing Metal-backend bugs locally without a GPU + the fold/hoist trap](../learnings/1788374380808-reproducing-metal-backend-bugs-locally-without-a-g.md)).

A release slangc is enough (`-target metal -stage mesh -entry main`). A mesh repro must assign whole output structs (`V v; v.pos = ...; verts[0] = v;`): a per-field store (`verts[0].pos = ...`) fires E56104 ("mesh output must be assigned as whole struct") first, and the #12883 point-topology segfault appears only with whole-struct assignment. On #12883 maintainers applied only `Metal`, `reproduced` and `Needs reporter feedback`, not `bug` or `mesh shader` ([Metal emit bugs reproduce on Linux; mesh repros need whole-struct output assignment](../learnings/1792155327352-metal-emit-bugs-reproduce-on-linux-mesh-repros-nee.md)). The four bugs landed as four PRs, each "Contributes to #12883": #12886 (b92d8bcf3: mesh index precedence plus the point-topology null deref, `slang-emit-metal.cpp`), #12885 (mesh user semantics, `fixFieldSemanticsOfFlatStruct` in `slang-ir-legalize-varying-params.cpp`), #12884 (`SV_InstanceID` = `instance_id - base_instance`) and #12887 (DispatchMesh-in-helper inlining, below). Linux repro of the last: put `DispatchMesh(1,1,1,p)` in a helper called from an `[shader("amplification")]` entry point and compile with `-stage amplification`; on v2026.16.1 the helper references `_slang_mesh_payload`, which only the entry point declares ([#12883 Metal mesh index fix was PR #12886](../learnings/1792402411704-12883-metal-mesh-index-fix-was-pr-12886-not-only-1.md)).

## Texture-intrinsic emit bugs: run the contrast controls, fix in the core module

Metal read/gather/GetDimensions emission lives in the core-module intrinsic layer (`hlsl.meta.slang` `__intrinsic_asm` strings plus the `slang-core-module-textures.cpp` generator), the natural fix locus. A reporter grouped three emit bugs under one "depth-texture path"; color-texture controls showed that two are multisample-general. `Texture2DMS.Load` (color) also emits the invalid `int2` read coord, because the MS `Load` Metal branch passes coord `$1` raw while non-MS overloads wrap `vec<uint,2>((...).xy)`; `Texture2DMS.GetDimensions` (color) also emits `get_width(0)` with a LOD arg. Only the `DepthTexture2D.Gather` extra `metal::component(...)` is depth-specific. **Before accepting a shared-locus framing, run the contrast controls (color vs depth, MS vs non-MS, array vs non-array)**; a depth-scoped fix would leave color-MS broken ([Metal MS-texture emit: int2 read coord + get_width(lod) are multisample-general](../learnings/1786993599232-metal-ms-texture-emit-int2-read-coord-get-width-lo.md)).

`DepthTexture2D.Gather` emits `depth2d::gather(..., metal::component(0))`, but Metal's `depth2d::gather` takes no component argument, so the `.metal` fails to compile. The `__texture_gather`/`__texture_gather_offset` Metal arms in `hlsl.meta.slang` append `metal::component($n)` unconditionally, while the WGSL arm of the same function already omits the channel under `if (isShadow == 1)`; mirror that guard. **When triaging a per-target codegen bug, grep the other targets' arms of the same intrinsic**; a sibling backend often already has the guard. Trap: the public `Gather` template's `isShadow` is a generation-loop variable (Cmp vs plain), not the texture's depth flavour, so the guard belongs inside `__texture_gather`'s per-target arm. A `Texture2D` control emits a byte-identical gather line ([Metal depth-texture gather bug: WGSL branch already has the isShadow guard](../learnings/1786994230312-metal-depth-texture-gather-bug-wgsl-branch-already.md)).

`Texture2DMS`/`DepthTexture2DMS.GetDimensions` emits `get_width(0)` with a LOD argument that MS textures reject. `TextureTypeInfo::writeGetDimensionFunctions()` hard-codes `metalMipLevel = "0"` across 6 sites; the mip-info overload is skipped for MS textures, so `includeMipInfo` stays 0 and the override to `"$1"` never runs. The one-line fix is `metalMipLevel = isMultisample ? "" : "0";`. The report named only `DepthTexture2DMS`, but the trigger is `isMultisample`, which only the per-flavour control matrix reveals ([Metal GetDimensions on multisample textures emits invalid get_width(0) lod arg](../learnings/1786994294348-metal-getdimensions-on-multisample-textures-emits-.md)).

The emitter pastes `__intrinsic_asm` text as-is and never inserts a cast (`emitIntrinsicCallExprImpl` in `slang-emit-c-like.cpp`), so a Metal arm whose expression has a narrower MSL type than the Slang declaration silently gives callers the narrower type. `float f16tof32(uint)` emits `as_type<half>(...)` (#13653) and its mirror `uint f32tof16(float)` emits `as_type<ushort>(...)` (hlsl.meta.slang:11520). Both compile cleanly, so a compile-only check misses them; they fail where MSL won't convert implicitly, such as the ambiguous `min(half, float)`. Find them by grepping Metal arms that hard-code a type (`as_type<half`, `as_type<ushort`) instead of `as_type<$TR>`. Vector overloads through `VECTOR_MAP_UNARY` are safe, because each element is assigned into the declared vector type [Metal __intrinsic_asm can emit a narrower MSL type than declared](../learnings/1792075407123-metal-intrinsic-asm-can-emit-a-narrower-msl-type-t.md).

## "Unknown addressspace" from a ref accessor is a lower-to-IR bug

Not every Metal `Unknown addressspace encountered` abort belongs to the address-space pass family. For a `[mutating] ref` accessor, `visitReturnStmt` has no ref-accessor case, so `return _v;` loads the pointer and the emitted helper returns `Int` while the function type says `Ptr(Int)`. One producer root gives four target symptoms: a Metal abort (the canary), an invalid SPIR-V module, and silent lost writes on HLSL/GLSL/WGSL. Triage: check whether the offending function's return matches its declared pointer-return type before assuming the address-space seeding family ([Metal 'Unknown addressspace' from ref accessor is a lower-to-ir return-value bug](../learnings/1786484201483-metal-unknown-addressspace-from-ref-accessor-is-a-.md)).

## C-style-cast precedence parens: a family bug in tryEmitInstExprImpl

`MetalSourceEmitter::tryEmitInstExprImpl` special-cases several ops that emit a C-style cast `(T)(operand)` and then `return true` without `maybeEmitParens`, so `inOuterPrec` is ignored and the parens are dropped when the cast is the base of a postfix `->`/`.`: `(T*)p->field` instead of `((T*)p)->field`, which native Metal rejects. The pointer `kIROp_BitCast`, `kIROp_CastDescriptorHandleToUInt64` and `kIROp_CastUInt64ToDescriptorHandle` cases share the defect. The generic `slang-emit-c-like.cpp` already has the right pattern: a C-style cast is `EmitOp::Prefix`, member access emits its base at `EmitOp::Postfix`, and `Prefix < Postfix`, so `maybeEmitParens(outerPrec, getInfo(EmitOp::Prefix))` adds the parens ([Metal emitter C-style-cast cases drop precedence parens (family bug)](../learnings/1787659804370-metal-emitter-c-style-cast-cases-drop-precedence-p.md)).

The fix (slang#12732 / PR #12741, merged) carried test lessons. The bug needs the cast inlined as the base of `->` (a named local hoists it), so use a single-use expression (`outputBuffer[3] = bit_cast<Data*>(q)->value;`). `maybeEmitParens` is not strict-precedence-only (it also forces parens in bitwise, logical, relational and equality contexts), so describe the result as "follows the emitter's precedence policy". FileCheck must assert the closing boundary (`))->value`), not only the opening `((Data`, and must be shown to reject the buggy emit ([Metal cast-paren bug: repro needs an INLINED cast; Falcor-Perf/priority-yield CI is infra](../learnings/1788298129501-metal-cast-paren-bug-repro-needs-an-inlined-cast-f.md)). For an approver this class is low-risk: parenthesization through the shared precedence machinery adds parens only in tighter-than-Prefix contexts, so output is byte-identical in statement and assignment contexts and untouched COUNT tests don't regress. A CHECK for the new boundary plus green Metal check-runs is enough; an unconditional token change still needs a full COUNT audit ([Merge-join #12741: Metal precedence-wrapping is low-risk for the COUNT-test class](../learnings/1788298167079-approver-human-disagreement-merge-join-12741-metal.md)).

## Argument buffers and DispatchMesh legalization

Metal tier-1 vs tier-2 argument buffers is a runtime device capability (`MTLDevice.argumentBuffersSupport`), not a compile-time or MSL-version choice: tier-1 is a universal baseline, tier is a GPU-family attribute, and a portable argument-buffer struct compiles once and runs on both tiers while the host adapts. Slang already emits one MSL form regardless of tier; baking a tier in forfeits that. The layout encoding already stores one offset per `LayoutResourceKind` per field, so it can hold a byte offset and a slot offset; the gap is production (the default Metal PB ruleset emits only slots, the tier-2 ruleset only Uniform bytes). The principled fix is one argument-buffer-contents ruleset returning both per field. Smell to watch: calling front-end layout rules from IR lowering or linking (master `slang-lower-to-ir.cpp` has none); when byte layout must be produced after the front end, carry the rule choice as an IR type operand and derive it in an IR pass, as `ConstantBuffer<T,Layout>` does ([Metal argument-buffer tier is runtime, not compile-time](../learnings/1787595516314-metal-argument-buffer-tier-is-runtime-not-compile-.md)).

DispatchMesh (amplification) legalization is Metal-only through virtual dispatch: `legalizeAmplificationStageEntryPoint` is a `virtual` with an empty base body, overridden only by `LegalizeMetalEntryPointContext` (WGSL inherits the no-op; CPU/CUDA use free functions). So a "generic"-named legalization function can be single-target; look for a per-target override. `__intrinsic_asm` substitution threads values only through `$0..$N` (the IR call's operands); bare identifiers such as Metal's `_slang_mesh_payload` and `_slang_mgp` are emitted verbatim and need that exact name in lexical scope (they resolve through synthesized `IRParam`s carrying `IRExternCppDecoration`). To expose an entry-point value to a helper, thread it as an `IRCall` operand or inline the helper (`performForceInlining` runs before emit); inlining to bring a value into scope is an established pattern, which is how the #12887 fix works ([Metal DispatchMesh legalization: intrinsic-asm operand-vs-name threading, virtual-dispatch target gating](../learnings/1788394097476-metal-dispatchmesh-legalization-intrinsic-asm-oper.md)).

## Binding tests: Metal's first-available-index fallback hides a dropped attribute (#12294)

MSL 4.1 §5.2.1 gives a kernel argument without an explicit `[[buffer(N)]]`/`[[texture(N)]]`/`[[sampler(N)]]` "the first available location index". A FileCheck that requires only some binding attribute, or one at index 0, can therefore pass when the emitter drops the attribute, because the fallback lands in the slot the layout chose. Give the resource an explicit `register(tN)`/`register(sN)` past everything declared before it and check the red-before-fix run. On slang#12294 the first choice, `t8`, still coincided, because two unbound 4-element texture arrays already filled slots 0-7. `register(t8)` with `register(s8)` on arrays also raises E39001 (overlap in the Vulkan binding space) even when targeting Metal, so use distinct numbers (`t16`/`s12` worked). Codex OUTPUT_REVIEW caught both ([Metal binding tests: zero-based indices can pass on a buggy emitter](../learnings/1790695616872-metal-binding-tests-zero-based-indices-can-pass-on.md)). The same PR's `-target metallib` smoke line has its own false-green: see [slang-test-output-assertions-and-truncated-runs](slang-test-output-assertions-and-truncated-runs.md).

## `groupshared` on Metal: a function-local var, and threadgroup declarations take no initializer (#13409)

On Metal and CPU targets, `introduceExplicitGlobalContext` (slang-ir-explicit-global-context.cpp:556-575) turns each `groupshared` global into an entry-point-local `var` with `AddressSpace::GroupShared`; other GPU targets keep an `IRGlobalVar`, and CUDA deliberately skips the hoist. `canInstHaveSideEffectAtAddress` (slang-ir-util.cpp ~1442, `kIROp_Call` arm) skips its "an opaque call may write anything" check when the root is a child of the function, so a `GroupMemoryBarrierWithGroupSync()` (no arguments) or a `[noinline]` callee writing the slot through KernelContext is treated as not modifying it. Three consumers miscompile: `tryRemoveRedundantLoad` (forwarding), `simplifyForEmit` `processLoadUse` (re-load moved past a barrier) and `tryRemoveRedundantStore` (DSE). To triage "load moved across a barrier", compare `-dump-ir` after `simplifyNonSSAIR` with the final IR; if the final IR still has the right store, the re-load comes from `simplifyForEmit` (the emitter's fold check uses `mightHaveSideEffects`, which the barrier blocks). The safe prototype treats roots whose pointer type has `AddressSpace::GroupShared` as globals in that arm. The broader inversion, "only private local vars are immune", breaks `inout` copy-in/copy-out: after `undoParameterCopy` an `inout` is a pointer param, and `x = t; barrier; return x` would re-read another thread's value, so param roots need an exemption. The same predicate also forwards through a pointer loaded inside the function (`uint* q = cb.p; *q = 1; w(); outb = *q` gives 1) on all targets including SPIR-V (#13412); its other unsound exemptions (escaped locals, pure callees) are on [Slang IR passes](../concepts/misc-f0909b7-slang-ir-optimization.md) [Metal/CPU groupshared is a function-local var after introduceExplicitGlobalContext](../learnings/1790967869022-metal-cpu-groupshared-is-a-function-local-var-afte.md).

The issue's second bug is the C-like emitter folding a store into the `threadgroup` declaration. It reproduces only when the variable is read later, for example by an atomic (`s = tid.x; barrier; InterlockedAdd(s,1,old);` gives `threadgroup uint s_0 = tid_0.x;`); a plain store with no later read is removed as dead code, and `-g` also hides the fold. Don't cite the MSL spec for "no initializer on threadgroup vars": v4.1 §4.4 (p.120-121) only shows uninitialized declarations and no sentence forbids `threadgroup T x = v;` (web quotes of "cannot be declared and initialized at the same time" are older or OpenCL-style wording). Cite SPIRV-Cross `spirv_msl.cpp:3868` (main aa217aeb6c9f), "Cannot directly initialize threadgroup variables. Need fixup hooks.", which emits the initializer as a separate assignment. Without a Metal toolchain, a `-target metallib` test on macOS CI is the only real proof [MSL spec doesn't state the no-initializer-on-threadgroup rule](../learnings/1790984185438-the-msl-spec-doesn-t-state-the-no-initializer-on-t.md).

## `read_write` texture fences: before and after every write (#13771, PR #13792)

Consider a compute shader that writes an `RWTexture2D` texel and later reads it in the same thread. MSL 4.1 §6.13.17 (p.288) says `fence()` makes a thread's writes to an `access::read_write` texture visible to its later reads, and master (7251cc60b) emits no fence on Metal (#13771). Prior art: Tint fences before and after every read_write-texture store (`builtin_polyfill.cc`); SPIRV-Cross fences before every read (`readwrite_texture_fences`, default true) [Metal read_write textures: same-thread write→read needs tex.fence()](../learnings/1792504235695-metal-read-write-textures-same-thread-write-read-n.md). That atom also read Dawn's crbug 417296309 as a read-after-write failure, which is wrong.

The crbug is write-after-read. Dawn commit 974d12830e9c, "[msl] Insert a fence BEFORE writes to read-write storage textures", fixed it at a time when Tint already fenced after every write. In Dawn's StorageTextureTests.cpp, `ReadWriteStorageTexture_WriteAfterReadHazard` is the "Test for" the crbug and `..._ReadAfterWriteHazard` is only "related to" it. Both tests reliably fail with no fences on Apple M1, so both hazards are real, but a trailing fence alone does not fix the filed bug. PR #13792 first cited the crbug for the trailing fence; a reviewer caught it, and the design became Tint's: a fence before and after every write, about two per write (dropping redundant ones is a follow-up). Before citing a bug as evidence for one hazard direction, read its fixing commit: "test for X" and "related to X" are different claims [CORRECTION: Dawn crbug 417296309 is write-after-read](../learnings/1792540687406-correction-dawn-crbug-417296309-is-the-write-after.md), [Metal texture fences need a leading fence too](../learnings/1792548264444-metal-texture-fences-need-a-leading-fence-too-dawn.md), [Inserting an IR inst before a texture atomic](../learnings/1792539684337-inserting-an-ir-inst-before-a-texture-atomic-go-be.md).

Three Slang-specific facts shape the pass:

- **Pass order.** `legalizeImageSubscript` (slang-emit.cpp:2474) runs after `legalizeIRForMetal` (:2413) and turns a partial texel store (`t[p].x = a; t[p].y = b;`) into write→read→write, so Slang creates the hazard even when user code never reads. PR #13792's fence pass runs right after `legalizeImageSubscript` and covers every `ImageStore` and every non-load texture atomic; a pass inside `legalizeIRForMetal` would miss those writes. `RWBuffer`'s Metal write is a separate string intrinsic (hlsl.meta.slang:20672), not `ImageStore` [Metal read_write textures need tex.fence()](../learnings/1792504235695-metal-read-write-textures-same-thread-write-read-n.md), [Metal texture fence(): non-const member](../learnings/1792529444711-metal-texture-fence-non-const-member-wrap-it-by-va.md).
- **`fence()` is a non-const member** (§6.13.17, checked against the Apple PDF). A `ParameterBlock` texture is emitted through a `constant` pointer (`pb_1->t_0`), where a direct `.fence()` is a non-const call on a const object. Tint emits `const_cast<T thread&>(tex).fence()` (crbug 365570202); SPIRV-Cross emits a by-value `template<typename ImageT> void spvImageFence(ImageT img) { img.fence(); }`. PR #13792 uses the by-value form as a `_slang_textureFence` prelude helper (`ensurePrelude`) [Metal texture fence(): non-const member](../learnings/1792529444711-metal-texture-fence-non-const-member-wrap-it-by-va.md).
- **A texture atomic's leading fence goes before the address chain.** The atomic's pointer operand is an `ImageSubscript` (plus a GEP chain) between the texture value and the atomic, and the Metal emitter prints the atomic and its address together, so `builder.setInsertBefore(atomicInst)` breaks dominance and Metal emit fails with an internal error (E99999 near the `InterlockedAdd`). Insert before `getRootAddr(atomic->getOperand(0))`; `ImageStore` takes the texture directly, so `setInsertBefore(store)` is fine [Inserting an IR inst before a texture atomic](../learnings/1792539684337-inserting-an-ir-inst-before-a-texture-atomic-go-be.md), [Metal texture fences need a leading fence too](../learnings/1792548264444-metal-texture-fences-need-a-leading-fence-too-dawn.md).

**A new op on a texture-array element can force a whole-array copy.** A fence on `arr[i]` gives `getElement(load(kc.arr), i)` a second use. `simplifyForEmit`'s `processLoadUse` copies a load to each use site only when `canInstHaveSideEffectAtAddress` says nothing in between can touch the load's address, and `ImageStore` and texture atomics fell through to `default: mightHaveSideEffects()`, which is true. The emitter then materialized `texture2d<...> _S1[] = kc->arr_0;`, a whole handle-array copy that is invalid MSL for an unsized array (master already makes it whenever an element has two uses). The fix (2604cf7) returns false when the instruction writes only texel memory (an `ImageStore`, a texel atomic whose root address is an `ImageSubscript`, or the fence) and the queried address has an `isResourceType` type, since a texel never holds a resource handle; other addresses keep the conservative answer, and SPIR-V/GLSL/HLSL output for those shapes was byte-identical to master. Any new IR instruction taking a resource value can change fold and copy decisions in emit, so A/B the callee form too; entry points read globals directly and hide the problem [A new IR op on a texture-array element can force a whole-array copy](../learnings/1792534127005-a-new-ir-op-that-takes-a-texture-array-element-as-.md), [Metal texture fence(): non-const member](../learnings/1792529444711-metal-texture-fence-non-const-member-wrap-it-by-va.md).

**A metallib test lane can bind at most 8 `access::read_write` textures.** On PR #13792 (Apple M4, Xcode 26.5) the `-target metallib` lane failed with "number of textures with read_write access exceeds maximum supported (8)". The kernel bound 11; an array counts once per element (`tiles[4]` is 4), and two arguments inside a parameter block (argument buffer) did not appear to count. The Linux `-target metal` text lanes never see the limit. Give the metallib lane its own small entry point (`-entry metallibMain`, at most 8 read_write textures), keep the big kernel for the filecheck lanes, and count by grepping `access::read_write` in the emitted `[[kernel]]` signature, element by element. Merge trap from the same PR: master changed `k_minSupportedModuleVersion`/`k_maxSupportedModuleVersion` to 37/37 while the PR's appended op also bumped max to 37, so the resolution was max 38, min 37; after merging master, re-check the module-version tail and the stable-name id [Apple Metal rejects a kernel with more than 8 access::read_write textures — keep metallib test kernels small](../learnings/1793272321100-apple-metal-rejects-a-kernel-with-more-than-8-acce.md).
