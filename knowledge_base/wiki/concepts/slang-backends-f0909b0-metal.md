# Metal backend — emit bugs, intrinsic-string codegen, argument buffers, groupshared, read_write texture fences, and GPU-free repro

## TL;DR

Metal backend bugs and the discipline for reproducing them without a Mac/GPU:

- **Most Metal bugs are GPU-free reproducible**: `slangc -target metal` on Linux shows emit-time crashes and wrong emission. "Metal is CI-only" holds for runtime behaviour only. Defeat folding/hoisting with a runtime, single-use operand.
- **Texture-intrinsic emit lives in the core-module intrinsic-string layer** (`hlsl.meta.slang` `__intrinsic_asm` + `slang-core-module-textures.cpp`), not mainly in `slang-emit-metal.cpp`; fix it there and keep the emitter dumb. Contrast controls (color vs depth, MS vs non-MS) decide the scope; a sibling backend's arm often has the right guard.
- **`__intrinsic_asm` arms are pasted with no cast**, so a Metal arm hard-coding a narrower type (`as_type<half>` in `f16tof32`, `as_type<ushort>` in `f32tof16`) silently changes the declared type. Grep for hard-coded `as_type<half`/`as_type<ushort` instead of `as_type<$TR>`.
- **C-style-cast cases in `tryEmitInstExprImpl` dropped precedence parens** (`(T*)p->field`), a family bug; the repro needs an inlined single-use cast.
- **The Metal argument-buffer tier is a runtime device capability**, not a compile-time choice: one portable struct compiles once and runs on both tiers. Don't bake a tier into the program.
- **DispatchMesh/amplification legalization is Metal-only via virtual dispatch** (a per-target override), not a call-site `if`. Intrinsic-asm threads values only via `$`-operands; bare identifiers emit verbatim and need the name in lexical scope.
- **A Metal binding test must use an index the fallback cannot hit.** An unbound MSL kernel argument takes the first available index, so check an explicit `register(tN)` past every earlier slot, with distinct t/s numbers to avoid E39001.
- **Metal/CPU `groupshared` becomes an entry-point-local var**, so `canInstHaveSideEffectAtAddress` let barriers and callees forward/DSE across it; treat `AddressSpace::GroupShared` roots as globals but keep param roots exempt. Threadgroup declarations take no initializer; cite SPIRV-Cross, not the MSL spec.
- **`-dump-ir`'s last dump precedes `simplifyForEmit`**, which is never dumped: a correct final dump with wrong emitted order points at `processLoadUse`. In Metal helpers groupshared is reached through a `kernelContext` load inside the function, which the local-root exemption also wrongly trusts (#14345).
- **Metal `access::read_write` textures need `fence()` before AND after every write** (Tint's design). The after-fence is MSL §6.13.17's read-after-write rule; the before-fence fixes Dawn crbug 417296309, which is write-after-read. Read the fixing commit before citing a bug for one hazard direction.
- **The fence pass runs after `legalizeImageSubscript`**, which turns partial texel stores into write→read→write. `fence()` is non-const, so wrap it by value for `ParameterBlock` textures. A texture atomic's leading fence goes before `getRootAddr` of its `ImageSubscript` address.
- **A new IR op on a texture-array element can force a whole-array copy in emit** via `canInstHaveSideEffectAtAddress`'s conservative default. A/B the callee form, not only the entry point.
- **A `-target metallib` lane rejects a kernel with more than 8 `access::read_write` textures** (array elements count individually); give that lane its own small entry point.
- **Ray query** lives on [Metal ray query](slang-backends-metal-ray-query.md) (only a `-target metallib` lane gives CI signal); **buffer element lowering** (packed vectors, layout-rule names, `ParameterBlock` matrices ignoring `column_major` since v2025.18.2; workaround `ConstantBuffer<S>` or `-matrix-layout-row-major`) lives on [Metal buffer element lowering](slang-backends-metal-buffer-lowering-and-layout-rules.md).
- **CI noise on Metal-only PRs**: Falcor-Perf (D3D12/Vulkan only) can never be caused by a Metal-only diff; priority-yield and "Artifact not found" are infra.

## Metal is GPU-free reproducible

Most Metal-backend bugs, crashes included, show in `slangc … -target metal` source emission with no GPU or macOS: a null-deref in Metal emit (a `[outputtopology("point")]` mesh passing a scalar `OutputIndices<uint,N>`) makes `slangc` SIGSEGV (exit 139). A wrong-emission bug that bites only for non-trivial operands is masked when a constant index is folded or a multi-use sub-expression is hoisted to a temp, so drive the operand from a runtime value used once (an index from `SV_GroupIndex`), and emit `-target spirv-asm` as the correct reference ([reproducing Metal-backend bugs locally without a GPU + the fold/hoist trap](../learnings/1788374380808-reproducing-metal-backend-bugs-locally-without-a-g.md)). To check that emitted MSL *compiles* without Apple's `metal`, strip `[[...]]` attributes, `#define device`, typedef `uint`/`uint2`/`uint3` as clang `ext_vector_type`, and run `clang++ -std=c++17 -fsyntax-only -include shim.h`; on #14151 it reproduced Apple's exact "subscripted value is not an array, pointer, or vector" errors, though it misses constant out-of-range vector subscripts ([Metal SV legalization is parameter-order dependent](../learnings/1793614842007-metal-sv-legalization-is-parameter-order-dependent.md)).

## Texture-intrinsic emit bugs: run the contrast controls, fix in the core module

Metal read/gather/GetDimensions emission lives in the core-module intrinsic layer (`hlsl.meta.slang` `__intrinsic_asm` strings plus the `slang-core-module-textures.cpp` generator), the natural fix locus. A reporter grouped three emit bugs under one "depth-texture path"; color-texture controls showed two are multisample-general. `Texture2DMS.Load` (color) also emits the invalid `int2` read coord, because the MS `Load` Metal branch passes coord `$1` raw while non-MS overloads wrap `vec<uint,2>((...).xy)`, and `Texture2DMS.GetDimensions` (color) also emits `get_width(0)` with a LOD arg. Only the `DepthTexture2D.Gather` extra `metal::component(...)` is depth-specific. **Before accepting a shared-locus framing, run the contrast controls (color vs depth, MS vs non-MS, array vs non-array)**; a depth-scoped fix would leave color-MS broken ([Metal MS-texture emit: int2 read coord + get_width(lod) are multisample-general](../learnings/1786993599232-metal-ms-texture-emit-int2-read-coord-get-width-lo.md)).

`DepthTexture2D.Gather` emits `depth2d::gather(..., metal::component(0))`, but Metal's `depth2d::gather` takes no component argument. The `__texture_gather`/`__texture_gather_offset` Metal arms append `metal::component($n)` unconditionally, while the WGSL arm already omits the channel under `if (isShadow == 1)`; mirror that guard. **When triaging a per-target codegen bug, grep the other targets' arms of the same intrinsic.** Trap: the public `Gather` template's `isShadow` is a generation-loop variable (Cmp vs plain), not the texture's depth flavour, so the guard belongs inside `__texture_gather`'s per-target arm ([Metal depth-texture gather bug: WGSL branch already has the isShadow guard](../learnings/1786994230312-metal-depth-texture-gather-bug-wgsl-branch-already.md)).

`Texture2DMS`/`DepthTexture2DMS.GetDimensions` emits `get_width(0)` with a LOD argument MS textures reject. `TextureTypeInfo::writeGetDimensionFunctions()` hard-codes `metalMipLevel = "0"` across 6 sites; the mip-info overload is skipped for MS textures, so `includeMipInfo` stays 0 and the `"$1"` override never runs. The fix is `metalMipLevel = isMultisample ? "" : "0";`. The report named only `DepthTexture2DMS`, but the trigger is `isMultisample`, which only the per-flavour control matrix reveals ([Metal GetDimensions on multisample textures emits invalid get_width(0) lod arg](../learnings/1786994294348-metal-getdimensions-on-multisample-textures-emits-.md)).

The emitter pastes `__intrinsic_asm` text as-is and never inserts a cast (`emitIntrinsicCallExprImpl` in `slang-emit-c-like.cpp`), so a Metal arm with a narrower MSL type than the Slang declaration silently gives callers the narrower type: `float f16tof32(uint)` emits `as_type<half>(...)` (#13653) and `uint f32tof16(float)` emits `as_type<ushort>(...)` (hlsl.meta.slang:11520). Both compile cleanly; they fail where MSL won't convert implicitly, such as the ambiguous `min(half, float)`. Vector overloads through `VECTOR_MAP_UNARY` are safe, because each element is assigned into the declared vector type [Metal __intrinsic_asm can emit a narrower MSL type than declared](../learnings/1792075407123-metal-intrinsic-asm-can-emit-a-narrower-msl-type-t.md).

## "Unknown addressspace" from a ref accessor is a lower-to-IR bug

Not every Metal `Unknown addressspace encountered` abort belongs to the address-space pass family. For a `[mutating] ref` accessor, `visitReturnStmt` has no ref-accessor case, so `return _v;` loads the pointer and the helper returns `Int` while the function type says `Ptr(Int)`. One producer root gives four symptoms: a Metal abort (the canary), invalid SPIR-V, and silent lost writes on HLSL/GLSL/WGSL. Check whether the function's return matches its declared pointer-return type before assuming the address-space family ([Metal 'Unknown addressspace' from ref accessor is a lower-to-ir return-value bug](../learnings/1786484201483-metal-unknown-addressspace-from-ref-accessor-is-a-.md)).

## C-style-cast precedence parens: a family bug in tryEmitInstExprImpl

`MetalSourceEmitter::tryEmitInstExprImpl` special-cases several ops that emit a C-style cast `(T)(operand)` and `return true` without `maybeEmitParens`, so `inOuterPrec` is ignored and the parens drop when the cast is the base of `->`/`.`: `(T*)p->field` instead of `((T*)p)->field`, which native Metal rejects. The pointer `kIROp_BitCast`, `kIROp_CastDescriptorHandleToUInt64` and `kIROp_CastUInt64ToDescriptorHandle` cases share it. The generic `slang-emit-c-like.cpp` pattern is right: a C-style cast is `EmitOp::Prefix`, member access emits its base at `EmitOp::Postfix`, and `Prefix < Postfix`, so `maybeEmitParens(outerPrec, getInfo(EmitOp::Prefix))` adds them ([Metal emitter C-style-cast cases drop precedence parens (family bug)](../learnings/1787659804370-metal-emitter-c-style-cast-cases-drop-precedence-p.md)).

The fix (slang#12732 / PR #12741) carried test lessons. The bug needs the cast inlined as the base of `->` (a named local hoists it), so use a single-use expression (`outputBuffer[3] = bit_cast<Data*>(q)->value;`). `maybeEmitParens` also forces parens in bitwise, logical, relational and equality contexts, so describe the result as "follows the emitter's precedence policy". FileCheck must assert the closing boundary (`))->value`), not only `((Data`, and be shown to reject the buggy emit ([Metal cast-paren bug: repro needs an INLINED cast](../learnings/1788298129501-metal-cast-paren-bug-repro-needs-an-inlined-cast-f.md)). For an approver this class is low-risk: the shared precedence machinery adds parens only in tighter-than-Prefix contexts, so statement and assignment output is byte-identical and untouched COUNT tests don't regress. A CHECK for the new boundary plus green Metal check-runs is enough; an unconditional token change still needs a full COUNT audit ([#12741: Metal precedence-wrapping is low-risk for the COUNT-test class](../learnings/1788298167079-approver-human-disagreement-merge-join-12741-metal.md)).

## Argument buffers and DispatchMesh legalization

Metal tier-1 vs tier-2 argument buffers is a runtime device capability (`MTLDevice.argumentBuffersSupport`), not a compile-time or MSL-version choice: tier-1 is a universal baseline, tier is a GPU-family attribute, and a portable argument-buffer struct compiles once and runs on both while the host adapts. Slang already emits one MSL form regardless of tier. The layout encoding stores one offset per `LayoutResourceKind` per field, so it can hold a byte and a slot offset; the gap is production (the default Metal PB ruleset emits only slots, the tier-2 ruleset only Uniform bytes). The principled fix is one argument-buffer-contents ruleset returning both. Smell: calling front-end layout rules from IR lowering or linking; when byte layout must come after the front end, carry the rule choice as an IR type operand and derive it in an IR pass, as `ConstantBuffer<T,Layout>` does ([Metal argument-buffer tier is runtime, not compile-time](../learnings/1787595516314-metal-argument-buffer-tier-is-runtime-not-compile-.md)).

DispatchMesh (amplification) legalization is Metal-only through virtual dispatch: `legalizeAmplificationStageEntryPoint` is a `virtual` with an empty base body, overridden only by `LegalizeMetalEntryPointContext` (WGSL inherits the no-op; CPU/CUDA use free functions), so a "generic"-named legalization can be single-target. `__intrinsic_asm` substitution threads values only through `$0..$N` (the IR call's operands); bare identifiers such as `_slang_mesh_payload` and `_slang_mgp` are emitted verbatim and need that name in lexical scope (they resolve through synthesized `IRParam`s with `IRExternCppDecoration`). To expose an entry-point value to a helper, thread it as an `IRCall` operand or inline the helper (`performForceInlining` runs before emit), as the #12887 fix does ([Metal DispatchMesh legalization: intrinsic-asm operand-vs-name threading](../learnings/1788394097476-metal-dispatchmesh-legalization-intrinsic-asm-oper.md)).

## Binding tests: Metal's first-available-index fallback hides a dropped attribute (#12294)

MSL 4.1 §5.2.1 gives a kernel argument without an explicit `[[buffer(N)]]`/`[[texture(N)]]`/`[[sampler(N)]]` "the first available location index", so a FileCheck requiring only some binding attribute, or one at index 0, can pass when the emitter drops it. Give the resource an explicit `register(tN)`/`register(sN)` past everything declared before it and check the red-before-fix run. On slang#12294 the first choice, `t8`, still coincided, because two unbound 4-element texture arrays filled slots 0-7, and `register(t8)` with `register(s8)` on arrays raises E39001 (Vulkan binding-space overlap) even targeting Metal, so use distinct numbers (`t16`/`s12`). Codex OUTPUT_REVIEW caught both ([Metal binding tests: zero-based indices can pass on a buggy emitter](../learnings/1790695616872-metal-binding-tests-zero-based-indices-can-pass-on.md)). The same PR's `-target metallib` smoke line has its own false-green: see [slang-test-output-assertions-and-truncated-runs](slang-test-output-assertions-and-truncated-runs.md).

## `groupshared` on Metal: a function-local var, and threadgroup declarations take no initializer (#13409)

On Metal and CPU, `introduceExplicitGlobalContext` (slang-ir-explicit-global-context.cpp:556-575) turns each `groupshared` global into an entry-point-local `var` with `AddressSpace::GroupShared`; other GPU targets keep an `IRGlobalVar`, and CUDA skips the hoist. `canInstHaveSideEffectAtAddress` (slang-ir-util.cpp, `kIROp_Call` arm) skips its "an opaque call may write anything" check when the root is a child of the function, so a no-argument `GroupMemoryBarrierWithGroupSync()` or a `[noinline]` callee writing the slot through KernelContext is treated as not modifying it. Three consumers miscompile: `tryRemoveRedundantLoad` (forwarding), `simplifyForEmit` `processLoadUse` (re-load moved past a barrier) and `tryRemoveRedundantStore` (DSE). The safe prototype treats roots whose pointer type has `AddressSpace::GroupShared` as globals in that arm. The broader inversion, "only private local vars are immune", breaks `inout` copy-in/copy-out: after `undoParameterCopy` an `inout` is a pointer param, and `x = t; barrier; return x` would re-read another thread's value, so param roots need an exemption. The predicate also forwards through a pointer loaded inside the function (`uint* q = cb.p; *q = 1; w(); outb = *q` gives 1) on all targets including SPIR-V (#13412); its other unsound exemptions (escaped locals, pure callees) are on [Slang IR passes](../concepts/misc-f0909b7-slang-ir-optimization.md) [Metal/CPU groupshared is a function-local var after introduceExplicitGlobalContext](../learnings/1790967869022-metal-cpu-groupshared-is-a-function-local-var-afte.md).

**The helper variant (#14345), and why the final dump can look right.** The last pass `slangc -dump-ir` shows (`checkUnsupportedInst`) runs BEFORE `simplifyForEmit` (`slang-emit.cpp:3131`), which is never dumped. So a correctly ordered final dump with wrongly ordered text points at `processLoadUse` (`slang-ir-simplify-for-emit.cpp:127`), which moves a load to its use whenever `canInstHaveSideEffectAtAddress` returns false; the C-like emitter's fold check stops at any side-effecting call and is not the suspect. In a Metal helper groupshared is reached through `load(kernelContext->sh)`; that pointer load is the root and lives inside the function, so the Call arm's local-root exemption (`slang-ir-util.cpp:1648`) lets a no-argument barrier pass. Draft PR #13421 (`isGroupSharedAddr(root) && isChildInstOf(root, func)` → true) fixes it, confirmed by a revert drill, as does #13431. Tooling: in a new `/workspace/agent/slang` worktree, run `git -c protocol.file.allow=always submodule update --init --recursive` (submodule URLs are local paths; plain update fails with "transport 'file' not allowed"); the shared Debug build's `-version` string can be stale even when ninja is a no-op, so trust the no-op plus the binary mtime ([-dump-ir's last dump is before simplifyForEmit](../learnings/1793881673347-dump-ir-s-last-dump-is-before-simplifyforemit-a-co.md)).

The issue's second bug is the C-like emitter folding a store into the `threadgroup` declaration. It reproduces only when the variable is read later, e.g. by an atomic (`s = tid.x; barrier; InterlockedAdd(s,1,old);` gives `threadgroup uint s_0 = tid_0.x;`); a store with no later read is removed as dead, and `-g` also hides the fold. Don't cite the MSL spec for "no initializer on threadgroup vars": v4.1 §4.4 (p.120-121) only shows uninitialized declarations and forbids nothing. Cite SPIRV-Cross `spirv_msl.cpp:3868`, "Cannot directly initialize threadgroup variables. Need fixup hooks.", which emits the initializer as a separate assignment. Without a Metal toolchain, a `-target metallib` test on macOS CI is the only real proof [MSL spec doesn't state the no-initializer-on-threadgroup rule](../learnings/1790984185438-the-msl-spec-doesn-t-state-the-no-initializer-on-t.md).

## `read_write` texture fences: before and after every write (#13771, PR #13792)

Consider a compute shader that writes an `RWTexture2D` texel and later reads it in the same thread. MSL 4.1 §6.13.17 (p.288) says `fence()` makes a thread's writes to an `access::read_write` texture visible to its later reads, and master (7251cc60b) emits no fence on Metal (#13771). Prior art: Tint fences before and after every read_write-texture store; SPIRV-Cross fences before every read (`readwrite_texture_fences`, default true) [Metal read_write textures: same-thread write→read needs tex.fence()](../learnings/1792504235695-metal-read-write-textures-same-thread-write-read-n.md). That atom also read Dawn's crbug 417296309 as read-after-write, which is wrong.

The crbug is write-after-read. Dawn commit 974d12830e9c, "[msl] Insert a fence BEFORE writes to read-write storage textures", fixed it when Tint already fenced after every write. In Dawn's StorageTextureTests.cpp, `ReadWriteStorageTexture_WriteAfterReadHazard` is the "Test for" the crbug and `..._ReadAfterWriteHazard` is only "related to" it; both fail with no fences on Apple M1, so both hazards are real, but a trailing fence alone does not fix the filed bug. PR #13792 first cited the crbug for the trailing fence; a reviewer caught it, and the design became Tint's: a fence before and after every write. Before citing a bug for one hazard direction, read its fixing commit: "test for X" and "related to X" are different claims [CORRECTION: Dawn crbug 417296309 is write-after-read](../learnings/1792540687406-correction-dawn-crbug-417296309-is-the-write-after.md), [Metal texture fences need a leading fence too](../learnings/1792548264444-metal-texture-fences-need-a-leading-fence-too-dawn.md).

Three Slang-specific facts shape the pass:

- **Pass order.** `legalizeImageSubscript` (slang-emit.cpp:2474) runs after `legalizeIRForMetal` (:2413) and turns a partial texel store (`t[p].x = a; t[p].y = b;`) into write→read→write, so Slang creates the hazard even when user code never reads. PR #13792's fence pass runs right after `legalizeImageSubscript` and covers every `ImageStore` and non-load texture atomic; a pass inside `legalizeIRForMetal` would miss those writes. `RWBuffer`'s Metal write is a separate string intrinsic (hlsl.meta.slang:20672), not `ImageStore` [Metal read_write textures need tex.fence()](../learnings/1792504235695-metal-read-write-textures-same-thread-write-read-n.md).
- **`fence()` is a non-const member** (§6.13.17). A `ParameterBlock` texture is emitted through a `constant` pointer (`pb_1->t_0`), where `.fence()` is a non-const call on a const object. Tint emits `const_cast<T thread&>(tex).fence()` (crbug 365570202); SPIRV-Cross a by-value `template<typename ImageT> void spvImageFence(ImageT img) { img.fence(); }`. PR #13792 uses the by-value form as a `_slang_textureFence` prelude helper (`ensurePrelude`) [Metal texture fence(): non-const member](../learnings/1792529444711-metal-texture-fence-non-const-member-wrap-it-by-va.md).
- **A texture atomic's leading fence goes before the address chain.** The atomic's pointer operand is an `ImageSubscript` (plus a GEP chain) between the texture and the atomic, and the Metal emitter prints the atomic and its address together, so `builder.setInsertBefore(atomicInst)` breaks dominance and Metal emit fails with E99999 near the `InterlockedAdd`. Insert before `getRootAddr(atomic->getOperand(0))`; `ImageStore` takes the texture directly, so `setInsertBefore(store)` is fine [Inserting an IR inst before a texture atomic](../learnings/1792539684337-inserting-an-ir-inst-before-a-texture-atomic-go-be.md).

**A new op on a texture-array element can force a whole-array copy.** A fence on `arr[i]` gives `getElement(load(kc.arr), i)` a second use. `simplifyForEmit`'s `processLoadUse` copies a load to each use only when `canInstHaveSideEffectAtAddress` says nothing in between can touch its address, and `ImageStore` and texture atomics fell through to `default: mightHaveSideEffects()` (true). The emitter then materialized `texture2d<...> _S1[] = kc->arr_0;`, a whole handle-array copy, invalid MSL for an unsized array (master already makes it whenever an element has two uses). The fix (2604cf7) returns false when the instruction writes only texel memory (an `ImageStore`, a texel atomic rooted at an `ImageSubscript`, or the fence) and the queried address has an `isResourceType` type, since a texel never holds a resource handle. Any new IR instruction taking a resource value can change emit's fold and copy decisions, so A/B the callee form too; entry points read globals directly and hide the problem [A new IR op on a texture-array element can force a whole-array copy](../learnings/1792534127005-a-new-ir-op-that-takes-a-texture-array-element-as-.md).

**A metallib test lane can bind at most 8 `access::read_write` textures.** On PR #13792 the `-target metallib` lane failed with "number of textures with read_write access exceeds maximum supported (8)". The kernel bound 11; an array counts per element (`tiles[4]` is 4), and two arguments inside a parameter block did not appear to count. Linux `-target metal` text lanes never see it. Give the metallib lane its own small entry point (`-entry metallibMain`, ≤8 read_write textures), keep the big kernel for the filecheck lanes, and count by grepping `access::read_write` in the emitted `[[kernel]]` signature. Merge trap: master changed `k_minSupportedModuleVersion`/`k_maxSupportedModuleVersion` to 37/37 while the PR's appended op also bumped max to 37, so the resolution was max 38, min 37; after merging master, re-check the module-version tail and the stable-name id [Apple Metal rejects a kernel with more than 8 access::read_write textures](../learnings/1793272321100-apple-metal-rejects-a-kernel-with-more-than-8-acce.md).
