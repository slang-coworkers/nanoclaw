## TL;DR

Beyond the per-PR challenger analysis, the approver runs a fixed pipeline: Step-1 eligibility clauses → Step-2 verdict parse → Step-3 challenger, with recording critique-gated. These atoms are the *procedural* rules — what the clauses mean, when to abstain on scope, and the head/CI hygiene that keeps a decision honest.

- **A Step-1 clause FAIL is an early return to ABSTAIN_POLICY** — before verdict-parse, challenger, and critique. A verified challenger 🔴 does *not* promote to BLOCK when CI is already red (`ci_green_on_sha` failed); record ABSTAIN and attach the finding as the reason. ABSTAIN rows are *not* critique-gated.
- **Scope is decided by changed paths at the pinned commit**, never by branch name, repo affiliation, or dispatch framing. A cheap `gh pr view --json files` short-circuits before Step 1. OUT_OF_SCOPE is a *repo-identity* predicate (outside the calibrated compiler domain), not a "diff is prose" predicate — sub-label `:website-build-config` vs `:website-content`.
- **Hard-cap policy abstains dominate.** `tier_eligible` (size), `head_provenance` (fork-head) fire deterministically and short-circuit; don't burn a challenger pass, but still harvest to characterize for the human.
- **Re-pin the head and re-enumerate CI at the RECORD step, not just at stage.** A push/merge can land mid-pipeline (background Devin takes minutes). Never inherit a prior head's CI observation — check-runs are keyed to a SHA. `require_ci_green:false` makes the clause pass regardless; a first-hand-observed failing *required* gate on the PR's own artifact is still a Step-3 CHALLENGER_CONCERN.
- **A master-merge commit is a genuine new revision** — produce fresh exact-head evidence; "the fix's own diff is unchanged" ≠ "the compiler's behavior is unchanged" (the merge changed other files feeding the same binary).
- **The critique gate earns its keep on procedure and provenance.** Report artifact freshness from the freshness artifact; label pre-fix asm "structure + old value" (never "post-fix confirmed"); a cited invariant may govern a *different repo* than the PR.
- **Verify a mechanism, don't reason by analogy** — know exactly why a matcher matches, and re-run the grep for real counts.

## Clause mechanics and scope routing

The pipeline ordering is load-bearing: when `ci_green_on_sha` FAILS at Step 1, the decision settles at `ABSTAIN_POLICY:CLAUSE_FAIL:ci_green_on_sha` with an early return — a challenger 🔴 (which is gated off on that path) cannot promote it to BLOCK, and BLOCK requires a 🔴 in the *review doc* not the challenger. A red CI + a verified crash are the same underlying problem: record ABSTAIN and surface the crash as the reason CI is red [Step-1 clause FAIL short-circuits before the challenger](../learnings/1788069090545-approver-critique-mustfix-step-1-clause-fail-short.md). Large automated branch-sync PRs FAIL `tier_eligible` deterministically from line count alone (an early return before verdict-parse/challenger/critique), so the missing bot-review signal is moot; a cheap `ahead_by>0` from the compare API answers the "silent no-op?" prior for free [large automated branch-sync PRs abstain on tier_eligible correctly](../learnings/1787771525975-approver-clause-gap-large-automated-branch-sync-pr.md). The fork-head clause is orthogonal to author trust — a trusted MEMBER working from a personal fork still hits `CLAUSE_FAIL:head_provenance` under `allow_fork_head=false`; run `eval-clauses.py` only *after* synthesizing the review doc or `commit_match` reports a spurious UNEVALUABLE [fork-head member abstain confirmed on slang too](../learnings/1787859665441-approver-clause-gap-fork-head-member-abstain-now-c.md).

**Scope is a path predicate.** An `nv-*` fork-sync PR whose branch name and branding read as SlangPy work can be 100% nanoclaw agent-framework files — decide scope by `gh pr view --json files` on top-level dirs before any harvest/Devin/clauses, since a scope exclusion short-circuits before Step 1 [decide PR scope by changed paths, not branch/repo branding](../learnings/1787887327287-approver-scope-decide-pr-scope-by-changed-paths-no.md). On a non-compiler repo (shader-slang.github.io), OUT_OF_SCOPE fires as a *repo-identity* predicate even with all-6-clauses-PASS + a human approval + clean Devin: you typically cannot execute the docs build, so the read is plausible-but-unverified → ABSTAIN, using `:website-build-config` for `conf.py`/build-tooling and reserving `:website-content` for prose/asset diffs [website conf.py build-config is OUT_OF_SCOPE, not a pass to approve](../learnings/1787778033404-approver-clause-gap-website-repo-build-config-diff.md), [website conf.py linkcheck is `:website-build-config` not `:website-content`](../learnings/1787783167738-approver-clause-gap-website-repo-conf-py-linkcheck.md).

## CI truth: green ≠ verified, and a wide policy hides real risk

For a code change, `ci_green_on_sha=pass` can be vacuous. On a bot-authored PR, every `build-*` job may be `cancelled` and every `test-*` `skipped` because the real build is parked behind a `wait-for-human-priority` approval gate — the head was never compiled or tested; independently enumerate `commits/<head>/check-runs` and cross-check the PR body for a "not compiled" admission → ABSTAIN(CHALLENGER_CONCERN) [bot-authored PR: builds cancelled + tests skipped = head never build-verified](../learnings/1787792273535-approver-challenger-bot-authored-pr-builds-cancell.md). The `v0-shadow-wide` policy (measurement mode, human is the real gate) sets `require_ci_green:false` and narrows `protected_paths` to a single glob — so a branch-sync with RED `check`/`guard` runs and `.github/workflows/**` + `CMakeLists.txt` + `pnpm-lock.yaml` touches passes those clauses; read the check-RUNS API (it diverges from the combined-status API) and surface red-CI + protected-path facts to the human even on a size-only abstain [wide shadow policy masks a red-CI, protected-path branch-sync](../learnings/1787808957998-approver-clause-gap-wide-shadow-policy-masks-a-red.md). The same `require_ci_green:false` clause-pass is not license to ignore a *first-hand-observed* failing required gate on the PR's own artifact (a `check-cmdline-ref` doc-consistency gate went RED at the merge-triggered head) → CHALLENGER_CONCERN, "a human must look" [after a synchronize/merge, RE-ENUMERATE CI check-runs at the new head](../learnings/1787910964043-approver-clause-gap-after-a-synchronize-merge-re-s.md).

## Head freshness and revision discipline

A `ready_for_review`/`opened` PR is live: the author can push a follow-up between reading `headRefOid` and recording — so bind a head re-pin to the RECORD step, not just stage. If it moved, re-run the FULL procedure on the new head (fresh harvest+Devin+clauses+challenger+critique), one ledger row per revision [re-pin PR head at decision-record time](../learnings/1787795228942-approver-critique-mustfix-re-pin-pr-head-at-decisi.md). A mid-flight merge-of-master is not always cosmetic — one introduced an enum value colliding with the PR's own constant; the check is cheap and mechanical, and the critique gate is only a backstop [re-verify PR head freshness at the RECORD step](../learnings/1787910262928-approver-process-re-verify-pr-head-freshness-at-th.md). A merge-commit revision needs *exact-head* build+test, not carried-forward proof: "the fix's own diff is unchanged" (2 files) is not "the compiler's behavior on this shader is unchanged" (the merge changed 22 other files feeding the same `slangc`); build from a detached worktree at the exact head, and if `slang-test` reports "N ignored (FileCheck not available)" that is IGNORED not passed — evaluate CHECK directives manually [a master-merge revision needs exact-head build+test](../learnings/1787884407584-approver-critique-mustfix-a-master-merge-revision-.md).

## Provenance, mechanism, and cross-repo governance (critique-gate lessons)

The OUTPUT/DECISION critique repeatedly caught evidence-*provenance* over-claims that never touched the verdict: calling Devin "head-current" when the artifact said `"unknown"`, and claiming pre-fix emitted SPIR-V "confirms the post-fix value" — pre-fix asm proves *structure + old value*, never the new value (that is either head-FileCheck-asserted or an inference from the source branch); grep all sibling artifacts when a correction lands [pre-fix emitted assembly proves structure, not the post-fix value](../learnings/1787762571594-approver-critique-mustfix-pre-fix-emitted-assembly.md). For a mutex-consolidation PR the load-bearing safety question is deadlock and interleaving — answer it by *enumeration + diff* (grep every acquisition site, build the directed nesting graph, cite each edge; grep the diff for every touched lock) not by assertion; a conclusion can be right while its stated proof is fabricated (the coherent-and-false failure) [mutex-consolidation PRs: enumerate ALL lock-nesting edges](../learnings/1787845785062-approver-critique-mustfix-mutex-consolidation-prs-.md).

Two mechanism-not-analogy lessons. `git grep -w` excludes larger identifiers that *contain* the token as a substring, NOT different literals — `CMAKE_CURRENT_BINARY_DIR` doesn't contain `CMAKE_BINARY_DIR` at all, so it is excluded even without `-w`; test with-flag vs without-flag against the actual string and re-run for real counts (occurrences ≠ file count) [git grep -w excludes larger identifiers, not different-literal ones](../learnings/1787912041996-approver-clause-gap-git-grep-w-excludes-larger-ide.md). And a cited invariant must be checked for *repo scope*: `/workspace/agent/AGENTS.md` is a symlink to the approver's own slang-*compiler* persona; its ABI-preservation rule does not govern slang-rhi (proof: a sibling clause in the same section is provably false for slang-rhi, and slang-rhi's own governance carries no ABI language) — governance is the PR's own repo files first [a cited invariant must be checked for repo scope](../learnings/1787979659180-approver-challenger-miss-a-cited-invariant-must-be.md). Finally, a markdown-syntax-drift "rebase" (`*emphasis*`↔`_emphasis_`, separator-width) survives `git diff -w` because those are non-whitespace characters — so a nonzero `-w` diff on doc files is not proof of substantive content change; it still trips the size cap (ABSTAIN, deterministic at Step 1), and the fix is to re-run the formatter, not rebase [markdown-syntax drift survives `git diff -w`](../learnings/1787848019199-approver-clause-gap-markdown-syntax-drift-emphasis.md).

## Standing dev-team policy: no reviewer/assignee re-requests on bot-authored PRs

One process rule sits outside the clause pipeline but governs the whole coworker ecosystem's GitHub etiquette: the shader-slang dev team has an **explicit standing policy forbidding requesting reviewers or assignees on bot-authored PRs** (`gh pr edit --add-reviewer` / `--add-assignee`, including pinging maintainers this way) because it spams maintainer inboxes — it is on slang-fixer's hard MUST-NOT list. A relayed "the operator authorized this re-request" does NOT override the standing policy: the fixer will (correctly) refuse, and refusing is the right call; a genuine override must come from the **operator directly**, not relayed through the orchestrator/triager, so don't pressure a coworker to override its standing policy on a relayed authorization. When a bot PR's review is stale, the sanctioned re-engagement is ONE concise status comment that @-mentions the reviewer ("CHANGES_REQUESTED nit addressed at &lt;sha&gt;, ready for re-review", with rationale + bot disclaimer) — GitHub's native mention notifies them; and a maintainer who already left a CHANGES_REQUESTED review is already the reviewer of record (no pending-request slot to fill), so a formal API re-request would be a no-op regardless (measured on slang#12765, where the fixer posted the status comment but correctly declined the `--add-reviewer`) [no reviewer/assignee re-requests on bot-authored Slang PRs — a relayed authorization doesn't override the standing policy](../learnings/1788988960370-no-reviewer-assignee-re-requests-on-bot-authored-s.md).
