# Slang Compiler: C/COM API Ownership & Front-End Guard/Cast Bugs

This page covers the Slang C/COM API's two ownership conventions (why `loadModule` returns a BORROWED pointer), an uninitialized host-VM `PathInfo::type` that surfaces as an aarch64-only interpreter result, a family of front-end declaration/lexing guard-and-cast bugs whose common shape is "the check is one layer off / too narrow," reuse of canonical immutable-location/opaque-type predicates, an IR positional-accessor trap, and a `defer` parser scope leak.

## TL;DR
- Discipline unchanged: when a crash disagrees with a stated ownership model or a decoder/guard premise, read the source at the call site — don't trust DeepWiki or a generic rule. Fix the producer of a bad shape, not the consumer.
- Slang's COM-lite API is NOT uniformly "returned interface is caller-owned." `ISession::loadModule`/`loadModuleFromSource`/`loadModuleFromBlob`/`getLoadedModule` return a BORROWED `IModule*` (session-owned, refcount unchanged) — releasing it drops the session's own ref → double-free at teardown. `T**` out-params (`link`, `getTargetCode`, entry-point/composite creation) are OWNED — release once. Teardown order matters, ending in `slang_shutdown()`.
- The session caches a module whose IR lowering (not semantic checking) failed. A second `loadModule` of the same name returns it with no diagnostic, and codegen then asserts in `slang-ir-link.cpp`. slangc never loads twice, so test session-cache claims through the C++ API.
- Slang API threading: specialization and `link()` need external synchronization; only the codegen methods are concurrent. The Linkage op-mutex cannot simply be split front/back, because both halves insert into the shared ASTBuilder hash-cons cache.
- `getCurrentASTBuilder()` is thread_local and only the global-session thread has a default. New front-end code reached from `ComponentType::specialize` runs outside the `SLANG_AST_BUILDER_RAII` scope, so it needs its own RAII or it segfaults on a worker thread. Probe such a claim with a GENERIC instantiation (`S<float4>`) on a `std::thread`; a non-generic struct takes the `DirectDeclRef` path and is a false negative.
- Moving per-object state (a lock, a buffer) to `thread_local` changes three things. (1) Keying: a "one active buffer" rule that is per object needs a per-thread list keyed by object, not one scratch per thread. (2) Teardown: a `thread_local` with a destructor is gone before static destructors and earlier-constructed thread_locals run, so code reachable from them needs a trivially-destructible late path. (3) Retention: memory abandoned by destroyed objects now lives as long as the thread. Measure RSS against master, and check identity (pointer and size), not just the key.
- An aarch64-only wrong result in a `//TEST:INTERPRET` (slangi) autodiff test is host-VM serialization UB from an uninitialized `PathInfo::type`, NOT specific to the differentiated op shown in the CHECK. Deterministic-across-all-aarch64 is expected (cold zero-pages), not evidence against UB.
- Front-end guard/cast family, common shape "the check is one layer off / too narrow": `DeclRef::as<U>()` does NOT validate the target type (it rewraps and returns non-null) — use `as<U>(rawDecl)` or `declRef.is<U>()`. When triaging "X isn't diagnosed," check whether the low-level utility already rejects X and it's a routing/guard gap one layer up (lexer continuation byte, `#language glsl` version).
- Reuse canonical predicates rather than hand-rolling a narrow switch: `isPointerToImmutableLocation(IRInst*)` and `isOpaqueType(IRType*, IRType**)` already cover the whole address-only/opaque-type class (RW-alias exclusions, OptiX-SBT case, transitively-containing structs).
- A by-value struct copy left after `transformParamsToConstRef` is the `updateCallSites` temp, not the callee's copy. It is required when SSA folded the copy into a load of a variable the callee also writes through `inout`; it is only waste for a distinct, unmodified, non-escaping local.
- Adding/splitting a `ParamPassingMode` (e.g. `RefWriteOnly`): grep every raw `hasModifier<Out|InOut|Ref|Const>` read — `validateEntryPoint` picked SV-semantic direction from raw modifiers at four sites — and route through `getParamPassingMode` (mesh output types are an explicit exception).
- For any IR op, verify how the *builder* emits it before trusting a FIDDLE positional accessor — schema and builder can diverge (`MakeVectorFromScalar` declares 3 operands but is built with 1, so `getScalarValue()` reads OOB; the scalar is `getOperand(0)`).
- `defer <bare-decl>;` leaks scope because the parser opens none; single-statement `if`/`while` bodies leak identically but only `defer` crashes (scope-exit relocation of the `IRVar`). Fix in the parser (open a nested scope), not downstream.

## Slang C/COM API Has TWO Ownership Conventions — `loadModule` Returns a BORROWED Pointer

Slang's COM-lite API is NOT uniformly "returned interface is caller-owned / release it." **(a) BORROWED bare-pointer returns — do NOT release:** `ISession::loadModule`/`loadModuleFromSource`/`loadModuleFromBlob`/`getLoadedModule` return a bare `slang::IModule*` whose refcount is *unchanged* for the caller — the `Linkage`/session owns the only strong references and frees the module when the *session* is released (proof: `asExternal(Module*)` is a plain `static_cast` with no `addRef`; DeepWiki wrongly claims it increments). An FFI caller that releases a `loadModule` result drops the session's own ref → double-free / heap corruption at teardown. **(b) OWNED `T**` out-params — release once:** `link()`, `getTargetCode()`, `getEntryPointCode()`, `createCompositeComponentType()`, `findEntryPointByName()`, `getDefinedEntryPoint()` transfer ownership via `.detach()`; blobs are per-call allocations. Teardown recipe: don't release `loadModule` handles → release blobs/entry-points/composites you created → release session → release global session → `slang_shutdown()` (frees process-global SPIR-V grammar/RTTI/capability tables). Meta-lesson: when a crash disagrees with a stated ownership model, read the source at the call site — don't trust DeepWiki or the generic "COM caller owns returns" rule [Slang C/COM API: loadModule returns a BORROWED IModule*, not caller-owned](../learnings/1785172765216-slang-c-com-api-loadmodule-returns-a-borrowed-imod.md).

The session's module cache keeps a module whose IR lowering failed. `Linkage::loadParsedModule` (`slang-session.cpp:1173-1188`) removes a module from `mapPathToLoadedModule` / `mapNameToLoadedModules` only when *semantic checking* added errors. A diagnostic raised during `generateIRForTranslationUnit` (E40008 `invalid-l-value-for-ref-parameter`, for example `float g(__ref float2 x)` called as `g(v.zx)`) leaves the module cached. So the first `session->loadModule("m")` returns null with the error, and the second returns the cached module with no diagnostic: `link()` succeeds and `getEntryPointCode` fails with E99997 `assert failure: slang-ir-link.cpp(399): c->value.ptrVal == nullptr`. Master reproduces it; it predates #13809, the PR under review when it was found. slangc never takes the second-load path, so test any session-cache claim through the API (a 40-line C++ probe that calls loadModule twice, linked to `build/Release/lib/libslang.so` with `-Wl,-rpath`). The probe also refuted a reviewer's prediction that this path "compiles silently with OpUndef". A side lesson for note→error escalation PRs: a message-only `//CHECK: ^^^ <message>` annotation matches at any severity, so pin the new severity with an `error E<code>` annotation [loadModule caches modules whose IR lowering failed](../learnings/1792579806821-session-loadmodule-caches-modules-whose-ir-lowerin.md).

## The API's Threading Contract: Linkage Op-Mutex Sites and the Front/Back Split (#13455)

The ownership rules above have a concurrency counterpart, documented in docs/user-guide/08-compiling.md:1035-1046: specialization and `link()` require external synchronization, and only the five codegen methods are concurrent. Triage at master 5cb03fa5f found `Linkage::m_componentTypeOperationMutex` (slang-session.h:246) taken at six sites (getSemanticsForReflection, createCompositeComponentType, COM specialize, link, getTargetProgram, getOrCreateLayout), while `Linkage::specializeType` takes none and getSemanticsForReflection locks only the swap of its cached context, then runs SemanticsVisitor unlocked. Splitting the lock into front-end and back-end halves races rather than deadlocks: the linkage ASTBuilder's hash-cons `m_cachedNodes` is a plain Dictionary (ast-builder.h:238) that both specialize and layout (getType/substitute, getTupleType, mangling, createIRModuleForLayout) insert into. The race evidence to cite in a reply is the layout→ASTBuilder path, re-verified at 653bfdee: `TargetProgram::getOrCreateLayout` (slang-parameter-binding.cpp:~4841) reaches `ASTBuilder::getTupleType` (:2703) and `getOrCreate<>`, which write the unlocked `m_cachedNodes`, while `ComponentType::specialize` (slang-linkable.cpp:~470) runs `SemanticsVisitor::CheckTerm` on the same ASTBuilder. link → fillRequirements does loop over the same `CompositeComponentType::create` that createComposite runs, but a direct ASTBuilder write on that path is unconfirmed; read slang-linkable-impls.cpp before claiming it ([cite layout→ASTBuilder, not link(), as the race evidence](../learnings/1792660287709-slang-13455-lock-split-cite-layout-astbuilder-not-.md)). Real contention sits in getOrCreateLayout, which locks even when the layout is cached, so every getEntryPointCode/getTargetCode result-cache miss serializes there via getOrCreateIRModuleForLayout (lower-to-ir.cpp:16584); an unlocked fast path is wrong because `m_layout` is published before `m_irModuleForLayout` ([Linkage op-mutex: front/back split races on ASTBuilder; getOrCreateLayout locks even when cached](../learnings/1791314287042-slang-linkage-op-mutex-front-back-split-races-on-a.md)).

## Worker-Thread AST Builder: `SLANG_AST_BUILDER_RAII` in Code Reached from `specialize` (#13538)

`getCurrentASTBuilder()` is thread_local, and only the thread that created the global session gets a default builder (slang-global-session.cpp:70). Front-end entry points scope it with `SLANG_AST_BUILDER_RAII`, but `EndToEndCompileRequest::executeActionsInner` → `createSpecializedGlobalAndEntryPointsComponentType` → the internal `ComponentType::specialize(args, count, sink)` overload runs outside that scope. A new check added there that reaches `getCurrentASTBuilder()` (on #13538, `getTrailingUnsizedArrayElement` → `_getMemberDeclRef`) gets a null builder on a worker thread and segfaults in `ASTBuilder::_getOrCreateImpl(this=0x0)`. The fix puts `SLANG_AST_BUILDER_RAII(linkage->getASTBuilder())` at the top of the new function, the same pattern as `EntryPoint::_validateSpecializationArgsImpl`, and the regression test is a unit test that compiles on a `std::thread` (wrapping the deprecated `ICompileRequest` calls in `SLANG_ALLOW_DEPRECATED_BEGIN/END`) [new front-end code reached from ComponentType::specialize needs its own SLANG_AST_BUILDER_RAII](../learnings/1792060186315-slang-new-front-end-code-reached-from-componenttyp.md).

The repro shape decides whether the crash shows at all. `getMemberDeclRef` short-circuits on a `DirectDeclRef` parent without touching the builder, so a non-generic `struct S { float4 a; float4 x[]; }` passes. Only a generic instantiation builds a `MemberDeclRef` that needs the builder: `struct S<T> { float4 a; T x[]; }` with `-specialize S<float4>` gave rc 139 at 1ce058b and rc 0 on master. Same-thread runs and slangc never show it, so drive `ICompileRequest::compile` on a `std::thread` with `addEntryPointEx(..., {"S<float4>"})` or `setGlobalGenericArgs`. A reviewer on #13538 r4 dismissed the Security finding as "not reproduced" from a single non-generic probe. When a claim names a code path, check which `DeclRef` subclass the probe input actually takes before refuting it [null-AST-builder repros need a GENERIC struct](../learnings/1792061760327-null-ast-builder-repros-need-a-generic-struct-non-.md).

## Moving Per-Object State to `thread_local`: Keying, Exit-Time Teardown, and Retention (#13786 / PR #13818)

Consider `AppendBufferWriter` in `source/core/slang-writer.cpp`. Each writer owned a mutex and an append buffer, and slang#13786 reported the mutex as misused. PR #13818 replaced both with thread-local scratch. Every reviewer pass (Reviewer A with 6 subagents, Devin, the clarity pass, codex) missed at least one of the three lifetime regressions below. Peer review and measurement found them.

**Key the thread-local state by object.** `ISlangWriter`'s "one active append buffer" rule is per writer, so `begin(A); begin(B); end(B); end(A)` on one thread is legal. With a single per-thread scratch, B's `setCount` reallocates A's live buffer. The fix is a `thread_local` list of `{writer, buffer}` entries, each its own allocation. Detach the entry before calling `write()`, so that a re-entrant append from inside `write()` gets a fresh buffer. A revert drill confirmed that the test catches the bug. A lookup keyed only by owner (`find(this)`) is not proof of ownership: it also matches the calling thread's own abandoned entry, so a wrong-thread `end` consumed it and wrote another thread's buffer. A "wrong thread → error" contract needs an identity check on the buffer pointer and size, not just "entry missing". In Release `SLANG_ASSERT` is `SLANG_ASSUME`/`[[assume]]`, so `SLANG_ASSERT(!"msg"); return err;` is UB for reachable misuse; use a plain error return ([thread-local append buffer must be keyed by writer](../learnings/1792583953497-thread-local-append-buffer-must-be-keyed-by-writer.md), [moving per-object storage to thread_local changes memory lifetime](../learnings/1792600018777-moving-per-object-storage-to-thread-local-changes-.md), [moving buffer ownership from object to thread changes lifetime](../learnings/1792602883492-moving-buffer-ownership-from-object-to-thread-chan.md)).

**A `thread_local` with a destructor is unsafe for code that may run from exit-time destructors.** On a given thread, destructors still run after that thread's function-local `thread_local`s are destroyed: static objects at process exit on the main thread, and earlier-constructed `thread_local`s at thread exit. Function-static writers such as `_getDefaultWriter` are destroyed after the main thread's thread_locals. If such a destructor prints through the writer, `beginAppendBuffer` runs `List::add` on destroyed storage; the PR head segfaulted where master returned OK. For the same reason a writer destructor cannot simply clean up its entry, because that may create thread-local state during teardown. The ASan/LSan-clean shape has three parts. A holder's destructor sets a trivially-destructible `thread_local bool destroyed`. After that flag is set, calls use a heap instance reached through a trivially-destructible `thread_local T*`, freed when idle. And the table is looked up again after any callback (`write()`), because a re-entrant late call can free the late instance; ASan caught that heap-use-after-free in a first draft. A per-thread allocation that is never freed is flagged by CI LSan (`ci-slang-sanitizer.yml` uses `detect_leaks=1`). A 20-line probe linked against `build/Release/lib/libcore.a` (add `-isystem external/unordered_dense/include`, or take the flags from `compile_commands.json`) checks both cases fast. Variant 1 is `static struct X { ~X(){ static NullWriter w(IsStatic); WriterHelper(&w).print("x"); } } g;` plus one print in `main`. Variant 2 is a `thread_local` whose destructor prints, constructed before the thread's first print ([a thread_local with a destructor is unsafe for code that may run from exit-time destructors](../learnings/1792591120086-a-thread-local-with-a-destructor-is-unsafe-for-cod.md), [moving buffer ownership from object to thread changes lifetime](../learnings/1792602883492-moving-buffer-ownership-from-object-to-thread-chan.md)).

**Retention moves from the object's lifetime to the thread's.** In R2 the buffer lived in a `thread_local` table keyed by writer address, plus a reused `spare`. Reviewers A and C passed it as correct; Devin flagged the retention, and a VmRSS probe against master confirmed it. 200 writers that each abandon 1 MiB and are then destroyed cost +205 MB (master +20 KB, because it freed the buffer with the writer). One 64 MiB append left the spare holding 64 MB for the life of the thread (master 0). When a PR moves storage from an object to `thread_local` or static scope, compare the object-destroyed case and the large-one-off case with an RSS probe against master. Clean up from the object's destructor only through a find-without-create accessor, and cap any reused spare (4 KiB). Build any master baseline probe with master's header too; mixing headers gives a bogus stack-buffer-overflow. About 10% of ASan runs of `std::thread` probes in this container hang at exit (exit 124, DEADLYSIGNAL) on master code as well; that is a toolchain artifact, so judge hangs from non-ASan runs. The standalone libcore.a probe technique is also on [Build tooling: testing a PR's effect locally](ci-b-build-tooling-local-testing.md) ([moving per-object storage to thread_local changes memory lifetime: measure RSS vs master](../learnings/1792600018777-moving-per-object-storage-to-thread-local-changes-.md), [moving buffer ownership from object to thread changes lifetime — measure retention and teardown](../learnings/1792602883492-moving-buffer-ownership-from-object-to-thread-chan.md)).

## Host-VM PathInfo::type Is Uninitialized — an aarch64-only `0 0` in an INTERPRET Autodiff Test (#12871)

For an aarch64-only wrong result in a `//TEST:INTERPRET` (slangi) autodiff test — e.g. `9 6 0 0 9 6` vs x86_64's `9 6 -9 -6 9 6` in `tests/autodiff/unary-plus-diff.slang`, where the zeroed values are the primal+tangent of `fwd_diff` through unary `-` — do NOT anchor on the specific differentiated op shown in the CHECK. The root cause is uninitialized `PathInfo::type` (`enum class Type : uint8_t`, no default init, `source/compiler-core/slang-source-loc.h:125`, read by `hasFoundPath()` ~l.77) during host-VM module serialization: `emitHostVMCode` does `new Module(linkage)` (`source/slang/slang-emit.cpp:3728`) and never sets a PathInfo before `serialize()`. That read happens ONCE PER slangi/INTERPRET invocation at module-serialization level, entirely upstream of and independent from whether the shader used a user `IFloat.neg()` or a builtin-scalar `-`. So the earlier #12871 assumption — that a builtin-scalar `-` mirror sidesteps the bug (it was filed against user `IFloat.neg()`) — is WRONG: ANY sufficiently-complex INTERPRET autodiff program can trip it on aarch64, and #12879 (`Type type = Type::Unknown;`) greens all of them, not just the neg() repro. Deterministic-across-all-aarch64-jobs is expected (cold zero-pages), not evidence against UB; which value gets zeroed is a downstream artifact of the corrupted serialization [#12871 host-VM PathInfo::type UB is not neg()-specific — hits builtin-scalar autodiff too](../learnings/1788537147888-12871-host-vm-pathinfo-type-ub-is-not-neg-specific.md).

## Front-End Guard/Cast Bugs: Property Accessors, #language, and the Lexer Continuation Byte

Three front-end declaration/lexing bugs triaged this day share a "the check is one layer off / too narrow" shape. A `[Differentiable]` (or `[TreatAsDifferentiable]`) on a struct **property** accessor segfaults slangc with no diagnostic (`#12210`), while a `[Differentiable]` *subscript* accessor is fine — so it's purely front-end header checking, not autodiff/IR. Root cause: `getFuncType` (`slang-syntax.cpp:1122`) branches `if (as<SubscriptDecl>(parent) || as<PropertyDecl>(parent))` then casts `parent.as<CallableDecl>()`, but `SubscriptDecl : CallableDecl` (has index params — the reason the branch exists) whereas `PropertyDecl : ContainerDecl` is NOT a CallableDecl. The load-bearing lesson: **`DeclRef::as<U>()` does NOT validate the target type** — it rewraps the same `declRefBase` and returns a non-null DeclRef even when the underlying decl isn't a `U`, so `if (declRef.as<CallableDecl>())` is a no-op guard; use `as<U>(rawDecl)` or `declRef.is<U>()` to actually test. Regression from PR #5922 which added the `|| as<PropertyDecl>` arm; fix restricts the param-prepend to `SubscriptDecl` only ([Differentiable property accessor segfaults getFuncType — PropertyDecl is not a CallableDecl](../learnings/1784883686572-differentiable-property-accessor-segfaults-getfunc.md)). Similarly, `#language glsl <n>` (`slang-preprocessor.cpp` `HandleLanguageDirective`) validates the version token only via `isValidSlangLanguageVersion`, never `isValidGLSLVersion`, so `#language glsl 460` errors E15207 while `#language glsl 2025` passes and then silently re-overrides the language back to Slang — the correct GLSL selector is `#version <n>`; the issue body's "PR #X will take care of this" was a **dedup gate**: checking the referenced PR's diff confirmed it net-satisfied the complaint (verdict = tracked-by-PR, no separate dispatch) ([#language glsl version mis-validates against Slang versions (not isValidGLSLVersion)](../learnings/1784916319659-language-glsl-version-mis-validates-against-slang-.md)). And the lexer silently accepts a lone UTF-8 **continuation byte** (0x80–0xBF, no lead byte, `#12222`) — but the instinct "the decoder doesn't handle it" is wrong: `getUnicodePointFromUTF8` already rejects a leading continuation byte; the bug is the branch guard `isUtf8LeadingByte` (`0xC0–0xFF` only) at `slang-lexer.cpp:267/:350` being too narrow, so the byte never enters the (correct) decode branch and falls through to identifier lexing. Fix at the guard (the producer of the branch decision), not the already-correct decoder nor the consumer; broadening to `isUtf8LeadingByte(c) || isUtf8ContinuationByte(c)` lets the existing E10006 emission fire — the general method being "when triaging 'X isn't diagnosed', check whether the low-level utility already rejects X and it's a routing/guard gap one layer up" ([Slang lexer lone-continuation-byte gap is a guard-narrowness bug, not a decoder gap](../learnings/1784917194691-slang-lexer-lone-continuation-byte-gap-is-a-guard-.md)).

## Reuse Canonical Immutable-Location / Opaque-Type Predicates, Don't Hand-Roll

When a fix must recognize "address-only / non-copyable / immutable-location" types across the whole class (ParameterBlock, ConstantBuffer, read-only StructuredBuffer/ByteAddressBuffer, read-only textures, samplers, and structs transitively containing them), reuse the existing canonical predicates rather than writing a new switch: `isPointerToImmutableLocation(IRInst*)` (`slang-ir-util.cpp:3105`, walks element-access chains and correctly excludes RW-alias + the OptiX-SBT case #10188) and `isOpaqueType(IRType*, IRType**)` (`slang-legalize-types.cpp:257`, recursive/cycle-safe, covers structs transitively containing resources). On slang#8002, `slang-ir-transform-params-to-constref.cpp:186 isLoadFromImmutableAddress` hand-rolls a narrow switch (ConstantBuffer/BorrowInParam/ParameterBlock only) that predates/duplicates `isPointerToImmutableLocation` — swapping it in gets full coverage in one source of truth. A subtle related mechanic: `lowerGlobalShaderParam` wraps a global param as `LoweredValInfo::simple(irParam)` even though the comment says the SSA value is a *pointer*; `tryGetAddress` has no `Flavor::Simple` case, so a global resource/PB param never presents as a Ptr and forces the by-ref temp path, emitting a bare `store(v, %g)` that `undoParameterCopy` (which matches `store(v, load(orig))`) misses [slang: reuse isPointerToImmutableLocation / isOpaqueType for constref copy-elision (do not hand-roll)](../learnings/1785194352818-slang-reuse-ispointertoimmutablelocation-isopaquet.md).

A whole-struct copy that survives `transformParamsToConstRef` is usually not a missed elision. By then the callee already takes `T*`; the copy is the call-site temp that `updateCallSites` (`slang-ir-transform-params-to-constref.cpp:243-246`) makes for any argument that is not a load from a ConstantBuffer/ParameterBlock/BorrowIn root. Check aliasing before calling it waste. SSA often folds `T copy = orig;` into `load(%orig)`, so if `orig` is also passed `inout` and the callee writes it, the temp is the snapshot the semantics require. The temp is merely conservative only when the argument loads a distinct, unmodified, non-escaping local; on #13108 dropping it in that case removed 3 KB of spills. `-dump-ir-before transformParamsToConstRef` shows the folded shape [the leftover copy is its own call-site temp and is often required](../learnings/1791924437877-transformparamstoconstref-leftover-copy-is-its-own.md). On master 653bfdeef (2026-10-22) the #13108 repro still emits `State_0 _S7 = original_1; readFields_0(&_S7, &original_1);` for `-target cuda`; the dump shows the SSA argument is `load(%original1)`, so `updateCallSites` (~243) makes a whole temp, and some snapshot is required because the callee writes `original.a`. A standalone nvcc harness on the L40S gives 16,18 for inputs 11,5, so the output is correct and only performance is affected; the eval container has no slang-test, so use the harness for runtime checks (recipe on [slangc target output](slangc-target-output-and-obfuscation.md)). The reply named the pass, said the values are correct, gave the plan to copy only the fields the callee reads, and invited the reporter to open a PR for their candidate [#13108 copy is a call-site temp; GPU result verified 16,18](../learnings/1792650204812-13108-reply-eval-copy-is-a-call-site-temp-from-tra.md).

## Changing a ParamPassingMode: Route Every Direction Decision Through `getParamPassingMode`

The same "one layer off" shape appears when a `ParamPassingMode` is added or split (e.g. `RefWriteOnly` for `__ref_writeonly`). Overload resolution, coercion and lowering are not the only consumers: `validateEntryPoint` in `slang-check-shader.cpp` picked a parameter's semantic direction from `hasModifier<InOutModifier>()` / `hasModifier<OutModifier>()` / `hasModifier<RefModifier>()` at four sites (SV semantic validation, depth-output collection, varying-type direction labels, the SV_Position output scan). So `__ref_writeonly uint : SV_GroupIndex` in compute was accepted and `SV_StencilRef` rejected — the reverse of `out` — with the full suite green; only a codex CODE_REVIEW caught it. The fix (tangent-vector's direction on #13406) queries the effective mode via `getParamPassingMode(param)`, with one explicit exception: the effective mode maps `MeshOutputType` (`out vertices V v[3]`, `OutputVertices<V,3>`) to `In`, so a direction helper must treat mesh output types as outputs. Compiling any `__ref` entry-point parameter to SPIR-V/GLSL hits a pre-existing assert in `slang-ir-glsl-legalize.cpp` (also on master), so semantic-direction tests need `-no-codegen`. Before declaring a passing-mode change complete, run `rg 'hasModifier<(Out|InOut|Ref|Const)Modifier>|findModifier<(Out|InOut|Ref|Const)Modifier>' source/slang` and route each parameter-mode decision through `getParamPassingMode` ([grep every direct Out/InOut/Ref modifier read, incl. entry-point validation](../learnings/1791611645970-changing-a-parampassingmode-grep-every-direct-out-.md)). The witness-synthesis clone loop and `ParameterDirectionInfo` are the other re-derivation sites; see [[wiki/concepts/slang-language-core-requirement-witness-synthesis.md]].

## IR Trap: Trust the Builder's Operand Count, Not a Generated Positional Accessor

**Trust the builder's operand count, not a generated positional accessor.** `kIROp_MakeVectorFromScalar` declares a THREE-operand Lua schema `{elementType, elementCount, scalarValue}`, so FIDDLE emits `getScalarValue() → getOperand(2)`; but every builder creates it with a SINGLE operand (`emitIntrinsicInst(..., 1, &scalarValue)`), and every existing consumer reads the scalar via `getOperand(0)`. Calling `getScalarValue()` therefore reads two `IRUse` slots past the array — asserts in Debug, wild pointer in Release — reachable from a module-scope splat like `static const uint3 g = (uint3)float3(3.0);` ([MakeVectorFromScalar getScalarValue reads getOperand(2) but builder emits 1 operand](../learnings/1785334765218-makevectorfromscalar-getscalarvalue-reads-getopera.md), [scalar is getOperand(0), NOT getScalarValue()](../learnings/1785335653192-makevectorfromscalar-scalar-is-getoperand-0-not-ge.md)). General rule: for any IR op, verify how the *builder* emits it before trusting a positional accessor — schema and builder can diverge.

## defer Bare Non-Block Decl Leaks Scope → IR-Lowering Segfault (#12266)

**Single-statement-body scope leak → defer-specific crash (#12266).** `Parser::ParseDeferStatement()` calls `ParseStatement()` without `pushScopeAndSetParent()`, so `defer uint i = 1;` leaks `i` into the enclosing function scope (name lookup then resolves it, suppressing `E30015`); IR lowering places the `IRVar` in the defer block, which `lowerDefer` relocates to scope-exit, so a reference before scope-exit derefs a stale value → segfault. `if(c) uint i=1;` / `while(...)` bodies leak identically but only `defer` crashes (the relocation). Fix = open a nested scope in the parser (mirror `parseBlockStatement`); the already-correct block form `defer { uint i=1; }` is the proof ([defer bare non-block decl leaks scope → IR-lowering segfault](../learnings/1785345383314-slang-defer-bare-non-block-decl-leaks-scope-ir-low.md)).
