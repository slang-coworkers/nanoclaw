# Slang Generics & Type System

Slang specializes generics from argument types via the IR pipeline, solving type parameters from call/index arguments and enforcing interface conformance at compile time. This page covers generic specialization, inference, and overload resolution; the type-system representation topics (witness tables, extensions, coercion, visibility, codegen) live in [[wiki/concepts/slang-language-generics-and-type-system-2.md]].

## TL;DR

- A type parameter that appears ONLY in return position cannot be inferred — the checker solves from index/call arguments alone (E39999). Return-position-only generic subscripts are a dead end.
- `E39999 "could not specialize generic"` has an extensible tagged-union failure-reason mechanism; focused codes (E30438 arity, E30439 unsolved param, E38029 conformance) reuse it. Arity diagnostics must range-check against defaulted trailing params, not total count.
- The generic-arg comparison fence (`<`/`>` inside generic arg lists) is half-built: `>`/`>=` are gated via `genericDepth`, `<`/`<=` are not, and `genericDepth` never resets inside `( )` so the parens escape hatch is broken.
- `hasModifier` on generic/static methods resolves via `getDecl()` to the inner `FuncDecl`, not the wrapping `GenericDecl` — attribute checks work without special unwrapping.
- Any-value-inference recursion has only a partial pointer-case guard; the `IRSpecialize`-operand path bypasses it (stack overflow). The `makeConditionalValue` ICE (#11782) needs only a plain un-monomorphized enclosing generic — try that before exotic specialization-leak hypotheses.
- Literal coercion into a constrained generic param resolves against the INTERFACE's visible ctors BEFORE specialization: `(T)0.25` for `T:IArithmetic` floors to 0 because `IArithmetic` has `__init(int)` but no `__init(float)`. Fix fork: add `__init(float)` (breaking) vs defer literal conversion to specialization.
- Interface `__init` requirements CANNOT have default bodies (E30317 — method-only). To add a value-preserving numeric-conversion init to an arithmetic interface, use a BARE `__init(...)` requirement (satisfied per-conformer via witness synthesis, source-non-breaking).
- The #11493 builtin-operator fast path (`convertToBuiltinArithmeticOp`) rewrites builtin arithmetic/comparison/bitwise/shift/unary ops on builtin scalar/vector/matrix operands BEFORE overload resolution, silently bypassing valid in-scope user operator overloads (no diagnostic). Recurring "fast path fires/declines when it shouldn't" defect class.
- Per-candidate overload-failure diagnostics (#12035) reuse #7857's machinery — only the type-coercion rejection reason is surfaced today; arity/inaccessibility/generic-constraint/direction reasons are not stored per-candidate. `AddOverloadCandidateInner` eagerly prunes strictly-worse candidates before the decision point, so any "warn X was chosen over Y" feature must capture the loser at the choke-point (and suppress `isFromCoreModule` matches).
- Generic entry-point `-specialize` couldn't see extension conformances in the primary command-line source file (E38029) — the primary TU never enters `loadedModulesList`. SHIPPED fix (#12052): scope the specialization context to `getModule()` + `getModuleDependencies()`.
- `static_assert(false)` in a `switch(T.kind)` arm of a generic `export`/customizable function fires UNCONDITIONALLY at generic type-check (T symbolic), not per-specialization. Diagnose "unsupported on this target" at the IR-emit consumer where the type is concrete.

## Generic Specialization and Inference

Slang specializes generics from argument types at the call site. A type parameter that appears **only in return position** cannot be inferred — the checker solves from index or call arguments alone ([Slang generic __subscript cannot infer a return-position-only type param from coercion target (E39999)](wiki/learnings/1781222181614-slang-generic-subscript-cannot-infer-a-return-posi.md), [CORRECTION: ResourceDescriptorHeap Approach A (return-position generic subscript) is a dead end — E39999](wiki/learnings/1781222607198-correction-resourcedescriptorheap-approach-a-retur.md)). The `E39999 "could not specialize generic"` diagnostic has an extensible failure-reason mechanism (tagged union `GenericArgumentInferenceFailure`) added in PR #11571 and extended in PR #11656 with three new focused codes (E30438 arity, E30439 unsolved param, E38029 conformance not satisfied) ([slang E39999 'could not specialize generic' has an extensible failure-reason mechanism (PR #11571)](wiki/learnings/1781684668464-slang-e39999-could-not-specialize-generic-has-an-e.md), [slang #11643 RESOLVED — focused generic-specialization diagnostics landed (PR #11656), 3 of ~9 sites done](wiki/learnings/1781729215980-slang-11643-resolved-focused-generic-specializatio.md)). Arity diagnostics must range-check against defaulted trailing parameters, not compare against total count ([Slang generic-arg arity diagnostics must range-check against defaulted params](wiki/learnings/1781753229607-slang-generic-arg-arity-diagnostics-must-range-che.md)).

The generic-arg comparison fence (`<`/`>` inside generic argument lists) is half-implemented: `>` and `>=` are already gated via `genericDepth` in `GetOpLevel`, but `<` and `<=` are not. Crucially, `genericDepth` is never reset inside `( )` sub-expressions, so the parenthesized escape hatch does not work today for already-banned operators ([Slang generic-arg comparison fence is half-built; parens escape hatch is broken](wiki/learnings/1780512896132-slang-generic-arg-comparison-fence-is-half-built-p.md)).

`hasModifier` on generic/static methods resolves via `getDecl()` to the inner `FuncDecl`, not the wrapping `GenericDecl`, so attribute checks work on generic methods without special unwrapping ([Slang: hasModifier on generic/static methods resolves via getDecl() to inner FuncDecl; verify GPU-only attribute cases with a CPU generic proxy](wiki/learnings/1780497220869-slang-hasmodifier-on-generic-static-methods-resolv.md)).

Any-value-inference recursion (`_findDependenciesOfTypeInSet`) has only a pointer-case guard from PR #10686, not a general visited-set. A self-referencing generic used through an interface still causes a stack overflow because `IRSpecialize` operands bypass the guard ([Slang any-value-inference recursion: #10686 pointer guard is partial; IRSpecialize-operand path bypasses it](wiki/learnings/1780353989621-slang-any-value-inference-recursion-10686-pointer-.md)). An un-monomorphized enclosing generic is also enough to leave a `Conditional<T,flag>` value unlowered: the `Unhandled local inst: makeConditionalValue` ICE (#11782) reproduces from nothing more exotic than a plain generic `outer<T>` (never monomorphized in the single-compile AOT path) that calls an inner `<let flag:bool>` with a *literal* bool — no autodiff, higher-order params, or set-specialization needed. When a "flag stays symbolic past `lowerConditionalType`" ICE resists isolation, try the plainest un-monomorphized outer generic before reaching for exotic specialization-leak hypotheses ([Conditional-flag ICE #11782 needs only a plain un-monomorphized enclosing generic](wiki/learnings/1784793304583-conditional-flag-ice-11782-repros-need-only-a-plai.md)).

Literal coercion into a constrained generic type parameter resolves against the *interface's* visible constructors at generic-check time — before specialization — which can silently destroy the value: `(T)0.25` in `T f<T:IArithmetic>()` returns `0.0` for `T=float` (#12311), because `IArithmetic` (core.meta.slang) declares only `__init(int)`/`__init(This)` and has NO `__init(float)` (unlike `IFloat`), so the float literal is implicitly converted float→int (0.25 floored to 0, with a `warning E30081` that always names `int` as the target regardless of the eventual instantiation), and that folded `0` is baked into the generalized IR and re-widened to `T` at specialization. Specialization/emit are *victims* — the bug is the front-end coercion path (`visitTypeCastExpr`→`_coerce`→`lookupConstructorsInType`) and fires for `(T)0.25`, `(T)0.25f`, and `T(0.25)` alike. The fix is a maintainer design fork: (A) add `__init(float)` to `IArithmetic` (symmetric with `IFloat`/`IInteger`, but adds a new REQUIREMENT to a public core interface → likely language-breaking for user conformers) vs (B) defer the literal conversion for a constrained generic param to specialization (non-breaking but delicate) ([Generic (T)float-literal cast floors to 0 — IArithmetic lacks __init(float)](wiki/learnings/1785559222590-generic-t-float-literal-cast-floors-to-0-iarithmet.md)).

A follow-up constraint surfaces when pursuing fork (A): an interface may carry a **default body on a METHOD requirement** (a silent conformer inherits it — see `tests/language-feature/interfaces/default-method.slang`), but this does **NOT** extend to `__init` — a defaulted-body constructor requirement inside an `interface` is rejected at core-module compile with `error[E30317]: interface requirement has body` ("non-method interface requirement cannot have a body"). So adding `__init(float)` to `IArithmetic` must use a **bare** requirement `__init(float val);`, not `__init(float val){ this = This(int(val)); }`. The bare form is doubly right here: (1) it's the ONLY value-preserving mechanism, because a bare requirement is satisfied **per-conformer**, so a `float`/`IFloat` type binds its OWN `__init(float)` and keeps float precision — an interface-PROVIDED default body would route through `int(val)` and re-introduce the floor bug in generic context; (2) it stays **source-non-breaking**, since builtin `int`/`vector<int,N>`/CoopVec/CoopMat AND a user `struct : IArithmetic` declaring only `__init(int)` all auto-satisfy the new requirement via **witness synthesis** (the checker synthesizes `__init(float)` from the available float→int conversion; verified by green core-module compile + a MyNumber-only-`__init(int)` test returning the truncated value). Serialized-module / witness-layout ABI compat of an added requirement is a separate maintainer-level question. General rule: to add a numeric-conversion init to an arithmetic interface, use a bare `__init(...)` requirement — default bodies are method-only ([Slang interface: __init requirements cannot have default bodies (E30317)](wiki/learnings/1785565100286-slang-interface-init-requirements-cannot-have-defa.md)).

## Builtin-operator fast path silently bypasses user overloads (#11493)

PR #11493 (`61ad43dbc`, first in v2026.11) added `SemanticsExprVisitor::convertToBuiltinArithmeticOp` (`slang-check-expr.cpp:4605`), called from `visitInvokeExpr` at :5007 and returning at :5008 — **before** `CheckTerm`/`ResolveInvoke` (:5044). For a builtin arithmetic/comparison/bitwise/shift/unary operator on builtin scalar/vector/matrix operands it rewrites the expr to a `BuiltinOperatorExpr` and skips overload resolution entirely, so ANY user overload of a builtin operator on builtin operand types is silently ignored — no diagnostic (discussion #11840: a ~2-year-old global `operator*(float4x4,float4x4)` stopped taking precedence after upgrading 2026.9→2026.11). Since #11493's stated goal is "byte-identical codegen", silently overriding a valid in-scope user overload is an unintended semantic regression. The fast path already defers matrix operators in GLSL operator scope (:4634-4637, :4723-4730), but the analogous "defer when a non-core user `operator OP` for the operand types is in scope" case was not handled; fix direction is a *cheap* in-scope-overload check that preserves the common no-overload fast path. This is a recurring "fast path fires/declines when it shouldn't" defect class (cf. the earlier float-bitwise → E39999 decline) ([Slang #11493 builtin-operator fast path silently bypasses user operator overloads on builtin scalar/vector/matrix types](wiki/learnings/1782894605011-slang-11493-builtin-operator-fast-path-silently-by.md)).

## Per-Candidate Overload-Failure Diagnostics (#12035) Reuse #7857's Machinery

The "explain why each overload candidate was rejected" DX ask (#12035) is NOT greenfield — issue #7857 already built most of the per-candidate machinery. The `OverloadCandidate` struct (`slang-check-impl.h:377-456`) carries a coarse per-candidate `Status` enum (Unchecked → ArityChecked → FixityChecked → TypeChecked → DirectionChecked → VisibilityChecked → Applicable, + GenericArgumentInferenceFailed), the first un-coercible arg (`argMismatchArgIndex/ExpectedType/ActualType`, recorded in `recordArgMismatch` @ `slang-check-overload.cpp:877-886`, only when bare types differ — skips l-value/inout qualifier-only mismatches), `conversionCostSum` (the existing ranking metric for *applicable* candidates), and `genericInferenceFailure`. The "no applicable overload" emitter (`:3520-3611`) already sorts `bestCandidates` by status and prints `argument N does not match: expected 'X', got 'Y'` per candidate when an arg mismatch was recorded. The GAP: only the type-coercion rejection reason is surfaced — arity mismatch (count recomputed but not stored per-candidate), inaccessibility (`InvisibleOverloadCandidate` note E40014 exists but only in the *ambiguous* branch @ :3692, never the no-applicable branch), failed generic constraint, and direction/inout mismatch all show just the bare signature. Diagnostic text lives in `source/slang/slang-diagnostics.lua:3896-3958` (rich struct-based, not the legacy defs header); `bestCandidates` holds only the tied-furthest-progressing set (`AddOverloadCandidateInner` @ :2461-2540 filters strictly-worse out), so a full "rank ALL candidates by proximity" feature may need candidate-retention changes on the hot resolution path. So #12035 splits cleanly: (A) fix-ready near-term slice = emit the remaining rejection reasons reusing the #7857 pattern; (B) design-gated = true proximity ranking needs a heuristic-definition decision ([slang#12035 overload-failure diagnostics — #7857 already built most of the per-candidate machinery](wiki/learnings/1783656901958-slang-12035-overload-failure-diagnostics-7857-alre.md)).

The same aggressive-pruning structure gates a different feature ask (#12284: warn when an imported module's better-matching overload silently rebinds a call that needed implicit conversion): `AddOverloadCandidateInner` **eagerly prunes** — a strictly-better candidate `fastRemoveAt`s the worse existing ones and a strictly-worse new candidate is dropped outright, and the single winner is only finalized much later at `CompleteOverloadCandidate`. So in the issue's scenario — local `fn(int)` (uint→int, non-zero cost) vs imported `fn(uint)` (exact, cost 0) — the losing local candidate is discarded *before* the decision point, and any "detect the winner is cross-module and a local candidate lost" feature must record contributing candidate modules AT the choke-point, before pruning, not at winner selection. Such a cross-module warning must also suppress `isFromCoreModule()` matches or it fires on nearly every implicit-conversion stdlib call (`lerp`, texture ops). The transferable rule: when triaging a "warn/diagnose when overload X was chosen over Y" feature, first check whether the loser survives to the decision point — Slang's resolver prunes so aggressively the info you'd diagnose on is usually already gone unless captured upstream ([slang-12284-overload-pruning-discards-beaten-local-candidate](wiki/learnings/1785405718177-slang-12284-overload-pruning-discards-beaten-local.md)).

## Generic Entry-Point -specialize Can't See Primary-File Extension Conformances (#12049)

`slangc file.slang -entry g -specialize float` on `void g<T:IDenorm>(...)` emits E38029 when `float:IDenorm` is supplied by an `extension` *in the same command-line source file*. Root cause: `EntryPoint::_validateSpecializationArgsImpl` builds its context with `m_module = nullptr`, so `getCandidateExtensionsForTypeDecl` takes the "ad-hoc/API" branch that enumerates extensions only from `m_linkage->loadedModulesList` -- and the primary command-line TU is never added to that list (it goes into the request-local `loadedModules` dict). Discriminator (verified empirically, not just reasoned): moving the same interface+extension into an *imported* module makes E38029 disappear. Recommended fix: scope the specialization context to `EntryPoint::getModule()` AND seed that module's own extensions (the `m_module`-set branch adds only imported modules, an asymmetry vs `_addDeclAssociationsFromModule` that is itself a cleanup candidate) -- reject "just add the primary TU to loadedModulesList" (broad reflection/import blast radius) ([slang#12049 -- generic entry-point -specialize can't see primary-file extension conformances](wiki/learnings/1783701731376-slang-12049-generic-entry-point-specialize-can-t-s.md)). This triaged Approach A landed verbatim: PR #12052 (merged 2026-07-16) scopes the conformance context to `getModule()` + `getModuleDependencies()` ([slang#12049 SHIPPED — Approach A confirmed: entry-point -specialize conformance scoped to getModule()+getModuleDependencies()](wiki/learnings/1784167461042-slang-12049-shipped-approach-a-confirmed-entry-poi.md)).

## static_assert(false) in a switch(T.kind) Arm Fires Eagerly for Generic export Functions

While fixing `defaultGetDescriptorFromHandle` in hlsl.meta.slang (#12185), a `static_assert(false, ...)` placed inside a `switch(T.kind)` case of a generic `[ForceInline]` function was expected to fire only per-specialization — it worked for a concrete call site, but a test's OWN `export T getDescriptorFromHandle<T:IOpaqueDescriptor>(...)` wrapper broke: compiling a generic `export` function type-checks its body with `T` SYMBOLIC, so `switch(T.kind)` can't fold and the `static_assert(false)` fires UNCONDITIONALLY (E41400) even for supported kinds. The existing `static_assert(false)` at :27778 is fine because it sits in `default:` of `switch(bindlessOptions)` where `bindlessOptions` is a `constexpr` function param (always concrete). Rule: do NOT use `static_assert(false, ...)` in a `switch(T.kind)`/generic-`static const` arm of anything compilable generically (especially `export` or a user-redeclarable customization point) — it fires at the generic type-check, not per-specialization. For "this kind is unsupported on this target," emit the diagnostic at the CONSUMER (IR emit) where the type is concrete; a plain `if (T.kind == X) return ...; else ...` is safe (both arms type-check generically). Method lesson: always run the REPORTER's exact repro, not just your own minimal test — the export-wrapper path only appeared in their `desc-handle-default.slang` ([static_assert(false) in a switch(T.kind) arm fires EAGERLY for generic export functions](wiki/learnings/1784691233062-static-assert-false-in-a-switch-t-kind-arm-fires-e.md)).
