# SlangPy CI, Triage, Build, and Runtime

Operational knowledge for working with slangpy's CI system, triaging GitHub issues, understanding runtime/API behavior, and building from source. Covers flake patterns, rerun authority, the slang bundling model, buffer layout gotchas, and the fixer-container build environment.

## CI Flakes and Infra Failures

### Crash Dump Re-symbolization
When triaging a slangpy CI abort whose message is buried under crashpad symbolizer noise (`elf_dynamic_array_reader.h:64 tag not found` spam), the highest-leverage first action is to download the failing run's `crash-reports-${os}-${platform}-${compiler}-${config}` artifact and re-symbolize the `.dmp` locally with full symbols (e.g., `minidump-stackwalk` against a debug build of the same sha).

Slangpy's CI already uploads minidumps via `.github/workflows/ci.yml:228-234` (`Upload Crashpad Reports` step) when the matrix has the `crashpad` flag. The `.dmp` + `.txt` + `.json` files are present in the artifact; what's missing is inline readable output in the job log. The on-the-fly stackwalk in `slangpy/testing/crashpad.py:_postprocess_reports` (~lines 105-145) is shallow, and stderr from the aborting worker gets buried by symbolizer warnings. Only works when `matrix.flags` contains `crashpad`. [slangpy CI flake triage: re-symbolize the existing .dmp before designing fixes](../learnings/1779545587070-slangpy-ci-flake-triage-re-symbolize-the-existing-.md)

### GPU OOM (Shared nvrgfx Runner)
**Signature:** `SlangPy Tests` fails with `cuMemAlloc ... CUDA_ERROR_OUT_OF_MEMORY`, `RuntimeError: Failed to create device!`, and pytest-xdist `replacing crashed worker gwN`. Hundreds of tests fail while thousands pass, spanning unrelated files (test_dtypes, test_buffer, test_reflection2, test_torchintegration). That spread + resource-exhaustion errors = intermittent GPU contention, NOT a code regression.

**Root cause:** the job runs `pytest slangpy/tests -vra -n auto --maxprocesses=4` → up to 4 concurrent workers, each creating CUDA + Vulkan device contexts on ONE shared `nvrgfx` Linux GPU. Reruns re-contend on the same saturated GPU and often re-fail. The real lever is maintainer-side: cap GPU-job concurrency, lower `--maxprocesses`, or add a per-job GPU-memory budget. [SlangPy CI flake: shared nvrgfx GPU runner CUDA OOM](../learnings/1781122096821-slangpy-ci-flake-shared-nvrgfx-gpu-runner-cuda-oom.md)

### cpu-shader-llvm shader.o Build Failure
**Symptom (observed 2026-06-09 on slang PR #11424):** slangpy `ci-latest-slang` `build-pr` jobs fail on both Linux and Windows building the `cpu-shader-llvm` example — the `shader.o` generation step does not mark `FAILED:` but the object is absent at link time. Commit `bbc4b0278` added `set_source_files_properties(... GENERATED TRUE)` to fix a Ninja race; that fix is insufficient: reliably broken 2/2 in slangpy's high-parallelism subproject build.

This looks PR-specific but isn't: other slang PRs were green the same day because their slang head was on older master that didn't build this example at all. As PRs rebase onto current master, they start hitting this. Don't fold an example-CMake/build fix into an unrelated PR; reruns won't help. A PR blocked only by this is "blocked by infra," not unmergeable on its own merits. [SlangPy Tests red = cpu-shader-llvm shader.o build failure (master infra, not your PR)](../learnings/1781008254667-slangpy-tests-red-cpu-shader-llvm-shader-o-build-f.md)

### GPU Memory Leak Claims (#115/#608/#827)
Empirical investigation on an L40S (46GB) with debug layers on found that documented leaks #115 (functional API), #608 (command-encoder), and #827 (torch-interop) do NOT reproduce at current HEAD. The real pytest suite shows VRAM as a STEP FUNCTION — jumps when a heavier test group runs then plateaus flat — not a monotonic climb.

**Conclusion:** the pytest-xdist CUDA-OOM cascade is **peak concurrent VRAM = workers × per-worker high-water-mark** on a VRAM-limited runner, not a runaway leak. Real fixes: right-size runner VRAM, or lower per-worker peak. Distinguish a LEAK (monotonic climb on a repeated identical op) from HIGH-WATER-MARK working set (step-function that plateaus). Reusable probe at `/workspace/agent/leak_probe.py`. [slangpy GPU mem-leak #115/#608 don't reproduce at HEAD; CI OOM is concurrent-peak high-water-mark, not a leak](../learnings/1782324497848-slangpy-gpu-mem-leak-115-608-don-t-reproduce-at-he.md)

Reconfirmed rigorously on #1024 (L40S 46GB): micro-repros of the suspected leak issues (single-process, VRAM sampled per-iter via `nvidia-smi`) were **flat after warm-up** (0 growth over 5k–20k iters), while a real CUDA suite slice with whole-session sampling showed the **step function** — VRAM jumps when a heavier test group runs then holds flat — classic high-water-mark working set (~5GB for one CUDA-only worker). CI's `pytest -n auto --maxprocesses=4` opens CUDA+Vulkan(+D3D12)+torch per worker over the full suite, so peak ≈ 4 × per-worker peak easily exceeds a modest CI GPU and the first failed alloc cascades. Actionable: right-size runner VRAM to ≥ `maxprocesses × per-worker peak` + headroom (zero wall-clock cost); a `--maxprocesses` cut is a wall-clock-costly stopgap maintainers rejected — measure per-worker high-water FIRST. Side finding: Vulkan+CUDA-interop (`enable_cuda_interop`) throws `SLANG_FAIL` on `command_encoder->finish()` on L40S — a functional error adjacent to #929/#823, not a leak ([CI GPU-OOM that passes on rerun is usually peak concurrent VRAM, not a leak](../learnings/1782896626067-ci-gpu-oom-that-passes-on-rerun-is-usually-peak-co.md)).

### SlangPy Tests pre-commit: --all-files trap
slangpy-samples CI (`.github/workflows/pre-commit.yml`) runs `pre-commit run --all-files`. One pre-existing violation anywhere in the tree (e.g., a file missing a trailing newline) reds the `pre-commit` job on EVERY PR, regardless of what that PR touches. Fix is a standalone 1-byte EOF-newline PR off `main`. Verification without GPU: `python3 -m venv /tmp/pcvenv && /tmp/pcvenv/bin/pip install pre-commit`, then `/tmp/pcvenv/bin/pre-commit run end-of-file-fixer --files <f>`. [slangpy-samples CI pre-commit runs --all-files; a single un-newlined file reds every PR](../learnings/1781609083456-slangpy-samples-ci-pre-commit-runs-all-files-a-sin.md)

## Rerun Authority and the 403 Boundary

### SlangPy Tests on slang PRs: where the run lives (historical rerun block, now lifted)
When a `shader-slang/slang` PR's only failing check is the cross-repo **SlangPy Tests** job, the actual run lives in `shader-slang/slangpy` (triggered via `repository_dispatch`) — that locating fact still holds and is how you find the run id to inspect or rerun. Historically `gh run rerun <id> --repo shader-slang/slangpy --failed` returned "Must have admin rights to Repository," read at the time as GitHub's structural rule that `repository_dispatch`-triggered runs need repo-admin rights (and treated as distinct from the actions:write gateway 403). **That rejection no longer reproduces** — see the supersession above. [SlangPy Tests failures on slang PRs are not bot-rerunnable (admin-rights boundary — superseded)](../learnings/1782166177663-slangpy-tests-failures-on-slang-prs-are-not-bot-re.md)

### SUPERSEDED (2026-08-03): cross-repo `gh run rerun` on slangpy now WORKS

**The two subsections below are historically accurate but their operative conclusion is dead — stop applying it.** Re-probed on slang PR #12116, whose only red was the cross-repo `SlangPy Tests` status (slang-side head `5c0e69c0` fully green) pointing at slangpy run `30808650114`: `gh run rerun 30808650114 --repo shader-slang/slangpy --failed` returned exit 0 and `run_attempt` incremented **1 → 2**. The old `Must have admin rights to Repository` rejection did not reproduce. Two premises collapsed with it: the gateway-scoping story as a *live* blocker, and the inference that all-false `permissions` on `shader-slang/slangpy` implied the bot couldn't act there — log reads always worked anyway. **Permissions introspection is a poor proxy for capability: probe the actual operation.**

**The methodological keeper: exit 0 is NOT proof a rerun fired — the `run_attempt` increment is.** Under the OneCLI gateway a call can fail server-side and still surface exit 0 depending on invocation form (the same laundering that produces phantom-green sweeps: `gh ... | jq` reports jq's status, not gh's). After *any* rerun, cross-repo or not, re-read the run and confirm the attempt counter moved — two independent facts beat one:

```bash
gh api repos/shader-slang/slangpy/actions/runs/<id> --jq '{status,conclusion,attempt:.run_attempt}'
```

**How to classify slangpy reds now.** Don't auto-file them as "bot-can't-rerun / log-as-left"; classify the *signature* first. Genuinely intermittent (dep-fetch 5xx, network, single-platform transient) → **rerun it** under the normal 3/PR/day cap, then verify the attempt increment. Deterministic or known-owned (setup-python toolcache, a capability/diagnostic break like slang#11225's E36121, an author-owned code break) → still no rerun, but **for the determinism reason, not the permissions one**: a rerun cannot fix a deterministic failure. Keeping the two straight matters precisely because the permissions premise evaporated and the determinism one didn't. Transient signature worth recognizing — a DXC prebuilt fetch 500 (`downloading '.../dxc_2026_02_20.zip' failed … CMake Error at download-dxc-populate.cmake:163`, then `ninja: error: loading 'build-Release.ninja'`) fails at **CMake configure**, so zero tests run and there are no assertion counts to reason about; note it is raised from `FetchDXC.cmake`, a **different code path** from the `FetchedSharedLibrary.cmake` that slang PR #12323 fixes — one root cause, two uncovered call sites ([cross-repo `gh run rerun` on slangpy now works — verify via `run_attempt`, not exit code](../learnings/1785773902337-cross-repo-gh-run-rerun-on-shader-slang-slangpy-no.md)).

### The Gateway PAT-routing Collision (RETRACTION context)
An earlier note framed the slangpy rerun block as a "flat permission boundary / babysitter scope gap." That was wrong. The "Must have admin rights to Repository" message is also the surface of the **OneCLI gateway PAT-routing collision**: a read-only nv-slang-bot user PAT shadows the App token (which already has `actions:write`). The 2026-06-17 fix scoped the App-token secret to `/repos/shader-slang/slang/actions/*` only, so slangpy (and slang-rhi) still collide. ## Issue Triage Patterns

### Check if Already Implemented
When triaging a SlangPy "feature request" that cites file:line pointers, grep the CURRENT checkout for the feature's named symbol BEFORE mapping a solution space. Sub-task issues filed under an umbrella effort frequently lag the code — the umbrella PR closes the sub-task's substance without closing the issue. If the feature is already wired and tested, the verdict is needs-decision, not ready-for-fix. [SlangPy triage: grep the issue's named symbols in HEAD first — the feature may already be shipped](../learnings/1781015340808-slangpy-triage-grep-the-issue-s-named-symbols-in-h.md)

Concrete case (#844, "configurable thread group size / 2D tile dispatch / groupshared cooperative kernels"): most of it is ALREADY implemented on the normal (non-`.dispatch()`) call path — `FunctionNode.call_group_shape(shape)` (`slangpy/core/function.py`) drives `[numthreads(call_group_size,1,1)]` codegen (the "internal 32,1,1" is only the default, and IS overridable), and generated `compute_main` exposes `SV_DispatchThreadID`/`SV_GroupID`/`SV_GroupIndex` accessed via `CallShapeInfo`, so one tile maps to one thread group and `groupshared` cooperative code is correct WHEN `call_group_shape` is set (footgun: hand-writing groupshared tile code WITHOUT it gives silent shared-memory corruption — a missing-API-usage, not a bug). Related: the `.dispatch()` + `torch.Tensor` gap (#832) ERRORS cleanly (a ~5-line lazy-init mirror would fix it), BUT maintainer mkeshavaNV directed NOT to add features to `.dispatch()` (slated for removal, gated on the #768 raw-dispatch redesign) ([slangpy call_group_shape already provides tile/groupshared dispatch (issue #844)](../learnings/1783522957219-slangpy-call-group-shape-already-provides-tile-gro.md)).

### Stale Line References Signal Possible Merge
When triaging a slangpy GitHub issue citing specific line ranges, first check whether those refs still match the current file. If the file is far shorter/different, that is a staleness signal. Run `gh pr list -R shader-slang/slangpy --state merged --search "<feature keywords>"` filtered to dates after the issue's `createdAt`. [slangpy triage: stale line-refs in an issue signal it may already be implemented — check merged PRs first](../learnings/1781015582617-slangpy-triage-stale-line-refs-in-an-issue-signal-.md)

### CUDA Codegen Issues: Search slang Core First
For any slangpy issue about a missing GPU-codegen capability (texture formats, intrinsics, target-specific behavior), run `gh pr list -R shader-slang/slang --search "<topic>" --state all` BEFORE assuming a slang-rhi patch-handoff or writing a slangpy fix. The fix may already exist in flight in the core compiler. 

Concrete case (#808, "CUDA backend lacks format conversion for surface/texture writes"): CUDA `surf*Dwrite` does raw byte writes; float→normalized/packed-int conversion must be emitted into device code at the write site → only the Slang compiler's CUDA codegen can do it. slang-rhi's `format-conversion.h` pack/unpack are CPU-side only. The fix (shader-slang/slang PR #11090, "CUDA surface format conversion prototype") was already in-flight in core. [slangpy #808 CUDA texture format conversion: fix is upstream slang PR #11090, not slang-rhi](../learnings/1781015966794-slangpy-808-cuda-texture-format-conversion-fix-is-.md)

### Tracking Issues for Collaborator PRs
If an issue is a tracking issue for an already-open collaborator PR, park the fix-forward (do NOT dispatch slang-fixer — a bot PR would duplicate/conflict). Still do everything else: HEAD-verify claims, set Issue Type, post the 5-bullet verdict, and flag whether the linked PRs carry `Closes #N`. [Slang CUDA: __constant__-vs-.param codegen check + slangpy-type repro substitution](../learnings/1782457879561-slang-cuda-constant-vs-param-codegen-check-slangpy.md)

## Runtime and API Behavior

### Python `id()` Does Not Reflect C++ IModule* Identity
When a reporter says "slangpy returns distinct `IModule` instances" and shows Python `id(m)` differing across `session.load_module(...)` calls, do NOT treat that as evidence of a slang-core bug. Slangpy mints a fresh Python wrapper proxy for every `load_module` call even when the underlying C++ `IModule*` is the same. To verify actual C++ behavior, compare `IModule*` pointers directly in a standalone C++ program. `Linkage::loadModule` returns `asExternal(module)` which is just `static_cast<slang::IModule*>(Module*)` — no wrapping. The cache works correctly via `findOrImportModule`. [slangpy Python id() ≠ C++ IModule* identity](../learnings/1779891890025-slangpy-python-id-c-imodule-identity.md)

### `create_buffer` Struct Size is a Silent Footgun
`device.create_buffer(element_count=n, struct_size=K)` allocates exactly `n*K` bytes and NEVER reconciles `K` against the Slang-emitted device-side element stride. The stride that indexes `buffer[i]` in-shader is baked into the compiled backend code by Slang codegen per target. If `struct_size` is smaller than the device stride on some target, you get silent out-of-bounds — the debug layer does NOT catch this. Symptom: correct on one backend, corrupted on another.

**Escape hatch:** use `resource_type_layout=program.reflection.<bufferParam>` instead of `struct_size=`. SlangPy then derives `struct_size = element_type_layout()->stride()` — the per-target reflected stride (`src/sgl/device/resource.cpp:66-91`). This is the only host-side way to get a backend-correct allocation; a hard-coded number is a guess. [SlangPy create_buffer struct_size is a silent backend-layout footgun — use resource_type_layout](../learnings/1780598190908-slangpy-create-buffer-struct-size-is-a-silent-back.md)

### Slang Version: Bundled via SGL_SLANG_VERSION
slangpy bundles Slang by downloading a prebuilt release via CMake FetchContent. The version is set in `slangpy/external/CMakeLists.txt`: `set(SGL_SLANG_VERSION "<ver>" ...)`. slang-rhi reuses slangpy's Slang (`SLANG_RHI_FETCH_SLANG OFF`). To override with a local build: `SGL_LOCAL_SLANG=ON` + `SGL_LOCAL_SLANG_DIR`. Authoritative runtime check: `import slangpy; print(slangpy.SLANG_BUILD_TAG)`. slangpy-samples does NOT pin a Slang version — it runs against whatever installed `slangpy` provides. [slangpy bundles Slang via SGL_SLANG_VERSION; samples don't pin it; runtime check is slangpy.SLANG_BUILD_TAG](../learnings/1781166935218-slangpy-bundles-slang-via-sgl-slang-version-sample.md)

**"Deferred until the upstream Slang fix ships" gates on the PIN, not on a wheel release** — read it as "wait for the next slangpy wheel" and you will re-add a test that still fails for the original reason. Because the bundle is a **release tarball** pinned by `SGL_SLANG_VERSION` (`external/CMakeLists.txt:85`), and the pin moves only when someone bumps it, the pin **lags badly**: on 2026-08-03 it was still `2026.12`, last bumped 2026-06-30 (#1037) — five Slang releases behind. A wheel cut on any given day bundles whatever the pin says, not the newest Slang. So the gate is a **three-stage chain and each stage needs its own check**: (1) *merge* — `gh api repos/shader-slang/slang/pulls/N --jq '.merged, .merge_commit_sha'`; (2) *a tag CONTAINING the merge commit* — **not** merely "a newer tag exists": `gh api repos/shader-slang/slang/compare/<tag>...<merge_sha> --jq '.status'` must return `behind` or `identical` (`ahead` means the commit is NOT in that tag — concretely slang#12299's `546ad18f` merged 08-03T21:28Z and was 25 commits *ahead* of `v2026.14.1`, the newest tag, hence in no released tarball); (3) *the slangpy pin bump* — the actual gate, read via `gh api repos/shader-slang/slangpy/contents/external/CMakeLists.txt --jq '.content' | base64 -d | grep SGL_SLANG_VERSION`, runtime equivalent `python -c "import slangpy; print(slangpy.SLANG_BUILD_TAG)"` (bound in `src/slangpy_ext/slangpy_ext.cpp:114` from `spGetBuildTagString()`).

**You usually don't have to wait for any of it to verify.** `.github/workflows/ci-latest-slang.yml` builds slangpy `main` against Slang **master** — nightly 01:00 UTC cron, `workflow_dispatch` with `slang_branch`, and `repository_dispatch` from Slang PRs, the last firing per-PR (slang#12299 got runs `30836651948` and `30848628629`, both green including the GPU `Unit Tests (Python)` step, *before* it merged). Checking for an existing cross-repo run against the upstream PR is the cheapest possible confirmation that a fix works with slangpy; local equivalent is `SGL_LOCAL_SLANG=ON -DSGL_LOCAL_SLANG_DIR=<slang>`. Mind the lane difference: `build-pr` (repository_dispatch) is a reduced Linux+Windows Release matrix, while the nightly `build` also covers Debug and macOS — a green cross-repo run is real evidence, not full-matrix evidence. Corollary for chain reports: **"fixed upstream" and "available to slangpy" are separated by two unbounded human steps — say which one you mean** ([deferred-on-upstream work gates on the SGL_SLANG_VERSION pin, not on a wheel release](../learnings/1785800138090-slangpy-deferred-on-upstream-work-gates-on-the-sgl.md)).

### CUDA Constant vs Param Codegen
A no-GPU discriminator for the CUDA entry-point-args vs `ParameterBlock` lowering: compile two variants with `slangc -target cuda -profile cs_6_0 -entry main` and grep the emitted `.cu`. Entry-point-args land in the `.param` bank — slow serial `ld.param` chain for runtime-indexed resource arrays. `ParameterBlock<CallData>` wrapper emits `extern "C" __constant__ GlobalParams_0 SLANG_globalParams` — fast `ld.const` path. `grep -c '__constant__ SLANG_globalParams' out.cu` is the fast/slow tell.

Note: `RWTensor<T,N>` is a SlangPy type, NOT core Slang — substitute `RWStructuredBuffer<float> bufs[N]` indexed at runtime to reproduce the mechanism standalone. Be explicit that this is a mechanism-only repro if you didn't run the perf benchmark. [Slang CUDA: __constant__-vs-.param codegen check + slangpy-type repro substitution](../learnings/1782457879561-slang-cuda-constant-vs-param-codegen-check-slangpy.md)

## Building SlangPy from Source (Fixer Container)

Building the slangpy native extension on an L40S linux-gcc Ninja Multi-Config box:

- **Needs `python3-dev`/`python3.11-dev`** (admin `install_packages` apt). Without it, CMake `find_package(Python ... Development.Module)` fails. nvcc is NOT required (CUDA backend uses the driver API at runtime).
- **PEP-668:** every `pip install` needs `--break-system-packages`. `python3 tools/ci.py install-slangpy-torch` fails because its internal `pip install wheel` omits the flag — install the torch bridge manually: `pip install --break-system-packages wheel && pip install --break-system-packages --no-build-isolation ./src/slangpy_torch`.
- **After a container rebuild**, the image's pip site-packages reset — reinstall `requirements-dev.txt` with `--break-system-packages`. The `/workspace` worktree persists across rebuild; pip packages do not.
- **Interrupted (ENOSPC) submodule checkout** leaves a gitlink with an empty working tree that `git submodule update --init` skips. Fix: `git submodule update --init --force --recursive`.
- **Build only `slangpy_ext`** (`cmake --build build/linux-gcc --config Release --target slangpy_ext`, ~304 steps) to skip heavy C++ test/example binaries. `build/buildtrees` (vcpkg intermediates) is regenerable — safe to `rm -rf` after configure to reclaim ~765MB. [Building slangpy from source in the fixer container: python3-dev, PEP-668, torch bridge, submodule/ENOSPC gotchas](../learnings/1782324519820-building-slangpy-from-source-in-the-fixer-containe.md)

Building the full C++ `sgl` layer (linux-gcc-debug, e.g. for the doctest `sgl_tests` / profiler suite) adds two non-obvious deps: the `data` git submodule (`slangpy-data.git`) is a REQUIRED unconditional PUBLIC link dep via `cmrc_add_resource_library(sgl_data ...)`, and its two fonts are git-LFS files — with git-lfs absent the checkout holds only ~131-byte pointer stubs, so ninja fails on `Inconsolata-Regular.ttf` BEFORE any source compiles (an INFRA gap, not your code); init without the smudge filter (`git -c filter.lfs.smudge= submodule update --init data`) then fetch the real binaries via GitHub's LFS batch API and verify with `file *.ttf` / byte sizes (Montserrat 197624 B, Inconsolata 101752 B), not mere existence [SlangPy C++ build needs data submodule + LFS fonts (git-lfs absent)](../learnings/1784867803689-slangpy-c-build-needs-data-submodule-lfs-fonts-git.md). The final `.pyi` stubgen targets (nanobind stubgen + `tools/postprocess_stub.py`) then import the built module and need `numpy`+`libcst` (`pip install --user --break-system-packages numpy libcst`) — but they run AFTER all C++ link succeeds, so a `ModuleNotFoundError` there means the binaries (libsgl.so + sgl_tests) are already built [SlangPy C++ build needs the `data` LFS submodule + numpy/libcst for stubgen](../learnings/1784868284126-slangpy-c-build-needs-the-data-lfs-submodule-numpy.md).

**CORRECTION to that reassurance — the stubgen failure is a FALSE-GREEN trap for `sgl_tests`.** "It runs after all C++ link succeeds" holds for `libsgl.so`, but **not** for the test binary: without `numpy`/`libcst`, `cmake --build --preset linux-gcc-debug` fails at the `.pyi` stub step and **aborts ninja BEFORE the `sgl_tests` link**. So your changes compile (`profiler.cpp.o` is fresh), `sgl_tests` is never relinked, the *old* binary stays on disk, and running it "passes" — against pre-change code. That is worse than a plain build failure, because the build looks like it hit only the known-ignorable error while the tests silently exercise stale code (observed concretely: an `sgl_tests` binary **10 days older than HEAD** still passing the very tests a fix was supposed to change). Fix: build the test target explicitly so the link happens before the stub step can abort the graph — `cmake --build --preset linux-gcc-debug --target sgl_tests` — and since `sgl_tests` links `libsgl.so` dynamically, make sure the `sgl` target relinked too. **Mandatory check before trusting ANY test number:** stamp `date '+%F %T'` before the build, then `ls -l --time-style=full-iso build/linux-gcc/Debug/sgl_tests build/linux-gcc/Debug/libsgl.so` and require **both** mtimes newer than the baseline; if not, you have no valid binary and must not report results. Checking the `.o` is not sufficient — the object can be fresh while the executable is stale. (Companion facts: the pre-existing full-suite failures in this environment are the 5 Git-LFS fixture cases — 3 in `test_dds_file.cpp`, 2 in `test_texture_loader.cpp` — from unmaterialized LFS pointer stubs, not regressions; and grepping doctest output for failing test names can surface `platform/environment`, which merely prints a `MESSAGE` header and passes in isolation.) ([stubgen failure aborts ninja before linking `sgl_tests` — use `--target sgl_tests` and verify mtimes](../learnings/1785774319630-slangpy-stubgen-failure-aborts-ninja-before-linkin.md))

## Crashing Regression Tests, Native-SIGSEGV Testing & CI Flake (2026-07-13 fold)

**A deliberately-crashing test hangs CI even when it passes locally.** If a SlangPy Python test intentionally triggers a native crash (SIGSEGV/SIGABRT) — e.g. a regression tripwire for a known-crashing GPU path — it will HANG the "Unit Tests (Python)" CI step for hours (2h+ linux/windows, 6h macOS), not crash cleanly. SlangPy's CI unit-test lanes build with the `crashpad` flag and `slangpy/testing/plugin.py` starts the Crashpad handler at `pytest_sessionstart` (gated on `spy.crashpad.is_supported()`); Crashpad intercepts the crash to capture a minidump and wedges the run. It does NOT reproduce on a local dev build where crashpad is disabled — so "passes locally, hangs in CI" is the signature. Diagnosis tell: Build + C++ tests pass, only "Unit Tests (Python)" is stuck `in_progress` with a multi-hour duration. Fix: guard the test with `if spy.crashpad.is_supported(): pytest.skip(...)` so it only runs on non-Crashpad builds; keep non-crashing controls always-on. Subprocess isolation stops a SIGSEGV from killing the pytest worker but does NOT stop a process-level crash handler from intercepting it ([a test that deliberately crashes (SIGSEGV) hangs SlangPy CI because Crashpad intercepts it](../learnings/1783909321657-a-test-that-deliberately-crashes-sigsegv-hangs-sla.md)).

**The pattern to regression-test a native SIGSEGV under pytest** (used for slangpy#1051 / slang#12070, `test_diff_loop_runtime_start.py`): run the crashing call in an ISOLATED SUBPROCESS (the test file doubles as the worker via `if __name__ == "__main__": os._exit(_child_main(...))`; `os._exit` avoids teardown perturbing the exit code); the parent asserts on returncode (a signal death is a NEGATIVE returncode, `-signal.SIGSEGV == -11`, not shell 139); use TARGETED `@pytest.mark.xfail(raises=_KnownCrash, strict=True)` so a clean exit (fix landed) becomes an XPASS hard-failure forcing marker removal; bracket the crash with FLUSHED `PHASE:begin`/`PHASE:end` prints so a crash in setup/teardown is surfaced not masked; compute the "fixed but wrong" oracle in numpy with a NON-SQUARE shape; gate to POSIX. A SIGSEGV discards block-buffered stdout — capture generated shaders with `python -u` or `SLANGPY_PRINT_GENERATED_SHADERS=1` ([regression-testing a native SIGSEGV under pytest (subprocess + strict xfail + phase bracket)](../learnings/1783875908806-regression-testing-a-native-sigsegv-under-pytest-s.md)).

**Matrix-vector grad tests flake on GFX pipelines.** `test_pytorch.py::test_tensor_interfaces[DeviceType.d3d12]` fails intermittently in Windows CI (`AssertionError: Tensor deviates by <large N>`) while 5120+ tests pass and the build succeeds — it is flaky, not a real regression. Confirm fast: the same test's `[cuda]`/`[vulkan]` variants PASS in the same run, and the sibling `test_tensor_arguments` (same helper, same grad assertion) is explicitly `pytest.skip("Test currently unreliable on GFX pipelines")` — maintainer-documented unreliability. `nv-slang-bot` CANNOT `gh run rerun --failed` (`Must have admin rights`), so a human must re-run or push a no-op. Triage rule: a single-test Python failure on ONE backend, where other backends of that test pass + it's green on the PR base + your change is backend-agnostic, is flaky CI — report, don't hunt ([slangpy CI: test_tensor_interfaces[d3d12] and matrix-vector grad tests are flaky on GFX pipelines](../learnings/1783887861915-slangpy-ci-test-tensor-interfaces-d3d12-and-matrix.md)).

## downstream_args Plumbing to Downstream Compilers (#1058, PR #1061)

`SlangCompilerOptions.downstream_args` (and `link_options.downstream_args`) are forwarded to Slang via `session_options.add(CompilerOptionName::DownstreamArgs, "<tag>", arg)` where `<tag>` is the SlangPassThrough name of the downstream compiler. Only **DXC** (`"dxc"`, d3d12) and **NVRTC** (`"nvrtc"`, cuda) accept pass-through args; Vulkan/Metal/WGPU/CPU have no consuming downstream compiler. Before PR #1061 the forwarding was hardcoded `if (device_type == DeviceType::d3d12)` with the `"dxc"` tag in BOTH the compile path (`create_session`, `src/sgl/device/shader.cpp:322`) and link path (`ShaderProgram::link`, ~:1540), so on CUDA the args were accepted at the Python dict→struct layer (`src/slangpy_ext/device/shader.cpp:27`, no validation) then **silently dropped** — e.g. `downstream_args=["--use_fast_math"]` had zero effect. Key distinction: `floating_point_mode` is a FIRST-CLASS Slang option applied unconditionally per-target (`shader.cpp:397`), which is why `floating_point_mode=fast` always worked on CUDA — a different mechanism. Fix = add a CUDA branch forwarding via `add(DownstreamArgs, "nvrtc", arg)` (CLI `-Xnvrtc`); the `"nvrtc"` tag was already proven in-tree by the auto OptiX-include forwarding ([SlangPy downstream_args forwarded only to DXC (d3d12) and NVRTC (cuda)](../learnings/1783909862147-slangpy-downstream-args-forwarded-only-to-dxc-d3d1.md), [slangpy downstream_args only forwarded for D3D12 (dropped on CUDA/NVRTC)](../learnings/1783910132054-slangpy-downstream-args-only-forwarded-for-d3d12-d.md)).

**Testing the fix requires an actual dispatch — NVRTC codegen is deferred to first dispatch.** For a CUDA device (SLANG_PTX target), NVRTC downstream compilation does NOT run at `session.link_program()` or `device.create_compute_kernel()` (which only reads reflection). The compute pipeline is created lazily in `ComputeKernel::pipeline()` (`kernel.cpp:35-40`), invoked only on the first `kernel.dispatch(...)`. So a test that verifies a downstream arg reaches NVRTC — or that a bogus arg is rejected — MUST create an output buffer and call `dispatch`; a test that stops at `create_compute_kernel` silently never runs NVRTC (this bit PR #1061: first version asserted a bogus flag raised at create and CI failed "DID NOT RAISE"). A pipeline-time NVRTC/RHI failure surfaces as Python `RuntimeError` (via `SLANG_RHI_CALL`→`SGL_THROW`), NOT `spy.SlangCompileError`; `pytest.raises(RuntimeError)` covers both ([SlangPy CUDA/NVRTC codegen is deferred to first dispatch — tests must dispatch to catch downstream-arg errors](../learnings/1783912568549-slangpy-cuda-nvrtc-codegen-is-deferred-to-first-di.md)).

**Editing a `///` docstring on a struct field in `src/sgl/device/shader.h` does NOT reach Python users automatically.** Python docstrings come from `src/slangpy_ext/py_doc.h`, a checked-in generated file (pybind11_mkdoc), regenerated by the `slangpy_pydoc` CMake target (`src/slangpy_ext/CMakeLists.txt:227`) which needs a full build + vcpkg include dir. If you can't run that target, hand-edit `py_doc.h` to match (entries look like `static const char *__doc_sgl_SlangCompilerOptions_<field> = R"doc(...)doc";`, ~70-col reflow, ASCII, no trailing whitespace — it's in the pre-commit `exclude:` list so clang-format won't touch it). A review WILL catch the desync if you only edit `shader.h` (found on #1058 / PR #1061) ([SlangPy py_doc.h must be updated when editing SlangCompilerOptions docstrings](../learnings/1783909847856-slangpy-py-doc-h-must-be-updated-when-editing-slan.md)).

## sgl_tests Teardown Exit-Code Flake and CI-Hang Corrections (2026-07-14 fold)

The `sgl_tests` teardown exit-code flake (#1062) is a distinct class: doctest prints a green `[doctest] Status: SUCCESS!` then the *process* exits nonzero during post-`main` teardown (`static_shutdown`/`close_all_devices` GPU-resource destruction), which `tools/ci.py`'s `run_command` turns into a `RuntimeError` reddening the cross-repo *SlangPy Tests* check on unrelated slang PRs ([sgl_tests exit-code flake root cause + tracking issue #1062](../learnings/1783930954720-sgl-tests-exit-code-flake-root-cause-tracking-issu.md)). The candidate fix is `std::fflush(nullptr); std::_Exit(result)` to bypass teardown ([#1062: no minidump, post-main teardown, fix with std::_Exit](../learnings/1783932346816-sgl-tests-exit-code-flake-1062-no-minidump-exists-.md)), but two evidence legs need correcting: crashpad is neither producing a minidump NOR armed in the C++ binary, so an empty `.crashpad/reports/` says nothing about fault location ([CORRECTION: crashpad is not armed; empty reports/ uninformative](../learnings/1783932949420-correction-to-1062-learning-crashpad-is-not-armed-.md)), and `_Exit` suppresses the (CI-disabled, non-blocking) LeakSanitizer end-of-run report ([_Exit fix #1064 suppresses LeakSanitizer report](../learnings/1783932699675-sgl-tests-exit-fix-1064-suppresses-leaksanitizer-e.md)). Maintainer @skallweitNV **rejected exit-code masking** — a teardown flake needs a root-cause fix, not `_Exit(result)` ([maintainer rejected exit-code masking](../learnings/1783937217747-sgl-tests-exit-code-flake-maintainer-rejected-exit.md)). Two related CI-hang corrections: a deliberately-crashing GPU test lands in an unkillable D-state process, so hard-guard on the CI env instead of probing crashpad ([CORRECTION: crashing GPU test wedges CI (unkillable)](../learnings/1783931282447-correction-a-deliberately-crashing-gpu-test-wedges.md)); and the separate slangpy#1051/#1053 6-hour hang was ultimately the known **CUDA-OOM cascade** from `pytest -n auto` opening 4 concurrent GPU contexts, NOT the crash-test ([CORRECTION #2: 6h hang was CUDA-OOM cascade](../learnings/1783974986070-correction-2-slangpy-1051-pr-1053-the-6h-ci-hang-w.md)). The same PR #1063 (self-merged, CodeRabbit Major findings unresolved) also carried a `ProfilerImpl::drain()` snapshot-ordering race (#1072): the async collector snapshotted the per-thread CPU event queues BEFORE `sealed_frame_events` under separate mutex scopes, so a producer could publish a zone and seal its frame in the unlocked window → the marker was consumed ahead of its zone and the frame finalized with zones missing — thread-count-INDEPENDENT (both the macOS cross-thread and Windows single-thread GPU tests fail on it) [SlangPy profiler PR #1063 also had a drain() snapshot-ordering race (#1072)](../learnings/1784869755509-slangpy-profiler-pr-1063-also-had-a-drain-snapshot.md). The #1072 fix (PR #1073, +14/−5) reorders the two snapshots — `sealed_frame_events` under `sealed_frame_mutex` FIRST, then acquire-load `write_index` — and its soundness rests on a C++ happens-before / release-sequence argument (the acq-rel RMW chain on `global_frame` synchronizes each zone-releaser with the sealer); the two cited regression guards PRE-EXIST on main and are probabilistic (they only catch #1072 if the collector drains in the exact race window), so a green run corroborates but does not prove — the memory-model argument is the real proof and the PR added NO deterministic test (verdict: APPROVE_WITH_NITS, nit = coverage) [SGL profiler drain() #1072 fix — snapshot reorder + why its guard tests are probabilistic](../learnings/1784870556172-sgl-profiler-drain-1072-fix-snapshot-reorder-why-i.md).

**And the reorder does NOT make `flush()` deterministic — a separate barrier gap covers only 1 of the collector's 3 input channels.** `Profiler::flush()` documents (`src/sgl/utils/profiler.h:476`) that it blocks "until the collector consumes events published before this call and publishes both snapshot products," but the implementation snapshots watermarks only from each thread's ring `write_index` (`profiler.cpp:~1710`) and `flush_targets_satisfied()` checks only `read_index >= flush_targets[i]` (`~1616-1629`). `drain()` has **three** independent inputs: the per-thread lock-free CPU/zone ring queues (*the only one in the barrier*), `sealed_frame_events` (frame markers, under `sealed_frame_mutex`), and `pending_gpu_results` (pushed at `~1046`/`~1289` under `gpu_result_mutex`). Channels 2 and 3 don't participate, so a frame marker or GPU result published before `flush()` returns can be missed — the collector snapshots a side queue, the event is published, and `flush()` still returns once the CPU watermark is met, leaving frame statistics incomplete until some later collector iteration. Consequence: `tests/sgl/device/test_profiler.cpp` *"device close settles pending frame statistics"* stays timing-dependent **even after** the #1072/#1073 fix — the reorder guarantees ordering only *within* one drain pass and cannot force another pass for a side-channel publication a pass already missed. Two constraints for anyone fixing it: the **GPU watermark must cover already-*published* results only** (waiting on *unresolved* queries exceeds the documented "published before this call" contract and can block indefinitely when a query never resolves; `tick()` is what moves resolved results into `pending_gpu_results` and is documented as not waiting — `profiler.h:471-474`), and an **"expected zone count" scheme must count `push()` successes, not zone attachments** (`ThreadData::push()` returns false and bumps `drop_count` when the ring is full, `~326-328`, but `end_zone` **discards that return value** at `~2186` and unconditionally calls `release_zone_from_global_frame` at `~2188`, so a dropped zone still decrements the frame's live-zone count and an attachment-based count would wait forever for an event never published). Diagnosed by skallweitNV, the profiler's author, on PR #1073 and verified first-hand against source ([profiler `flush()` barrier covers only 1 of 3 collector input channels](../learnings/1785769306938-slangpy-profiler-flush-barrier-covers-only-1-of-3-.md)).

## In-Container GPU Validation: CUDA Works, Vulkan Autodiff Fails (2026-07-28 fold)

The slangpy-fixer container DOES have a usable GPU (NVIDIA L40S, CUDA 12.7) — always probe `nvidia-smi` before claiming "no GPU backend." But **backend choice matters for differentiable validation**: `spy.Device(type=spy.DeviceType.cuda)` runs forward AND backward (`.bwds`) correctly (a minimal `RWDiffTensor<float,1>` + `.store` backprop gives the analytically exact gradient), while the default `spy.Device()` resolves to **Vulkan** on this box and its auto-generated `bwd_diff` kernel fails with `NVVM compilation failed: 1` / `command_encoder->finish ... error -13`. Forward-only Vulkan is fine — only the differentiable backward codegen fails, and it's a slangpy-0.43 autodiff-on-Vulkan toolchain issue in-container, NOT a shader-migration defect (the module compiles cleanly on both). So to functionally validate a differentiable slangpy sample, explicitly select CUDA; module-load (compile check) works on both backends and is the strongest content-agnostic signal a migration is correct. Setup notes: `pip install slangpy` (pins 0.43.1, ~92MB wheel → use `--retries 5 --timeout 120`), `pip install pillow` (use `PIL.Image.open` directly — imageio's backend discovery is flaky in-container), and slangpy-samples image assets are git-LFS pointers fetched via the LFS batch API. ## load_program Capability-Checks the Whole Module, and the Cross-Repo Guard-Prerequisite (2026-08-01 fold)

`device.load_program("mod.slang", ["one_entry_point"])` capability-checks **every** `[shader]` entry point in the module at load time — not lazily per requested function — so a single target-unsupported sibling EP sinks the whole load (confirmed on CI run 30564544350: requesting a CUDA-clean `copy_byte_address_buffer` still tripped `E36107: entrypoint 'copy_buffer_uint' uses features not available for 'cuda'` → `E39999 import failed`). DeepWiki's "lazy per-function" claim is wrong for this path — trust the CI logs. The idiomatic fix guards the offending EP's whole declaration with the SGL-injected per-target macro (`#ifndef __TARGET_CUDA__ … #endif`, injected at `src/sgl/device/shader.cpp:486-496`, applied by the preprocessor *before* the front-end capability check so the guarded EP never reaches E36107); in-repo precedent is `src/sgl/device/blit.slang:61-86` ([SlangPy load_program capability-checks ALL entry points in a module at load](../learnings/1785443278231-slangpy-load-program-capability-checks-all-entry-p.md)). That guard can be the **prerequisite** that unblocks an upstream slang PR, not a follow-up: when `SlangPy Tests` is a `required=True` check on the slang PR and the CI dispatch (`ci-latest-slang.yml`) checks out slangpy fixtures from slangpy **main** while building slang from the PR ref, the slang PR cannot merge until the slangpy-side guard is already on slangpy main (observed slang#12289 → slangpy#1083). Sequence it as two decoupled stages: land the guard immediately (pin-independent — its own CI builds slang from master with no E36107 yet, and the offending variant is already `pytest.skip`ped, so it is a green no-op today), and defer the `SGL_SLANG_VERSION` pin bump (`external/CMakeLists.txt:85`) until the slang fix ships in a release **tag** (slangpy pulls a prebuilt release tarball, not a commit SHA) ([a slangpy test-fixture guard can be the PREREQUISITE that unblocks an upstream slang PR's required check](../learnings/1785478041840-a-slangpy-test-fixture-guard-can-be-the-prerequisi.md)).

## An Intended-Breaking Slang Diagnostic (E36121 / `hlsl_nvapi`) and How to Prove the Downstream Guard (2026-08-03 fold)

The `load_program`/E36107 pattern above has a sibling that is the cleanest worked example of a **legitimate cross-repo break**: slang PR #11225 ("Capabilities: error on capabilities incompatible with compilation target", fixes #4422, author zangold-nv, labeled `pr: breaking change`) turned its cross-repo `SlangPy Tests` status red with 28 identical

```
error[E36121]: requested capability 'hlsl_nvapi' is incompatible with compilation target 'spirv'
error[E39999]: import failed due to compilation error
fatal error[E40003]: compilation ceased
```

on **both** linux-gcc and windows-msvc, on **both** attempts. `sgl_tests`: 172 passed / 28 failed / 3 skipped — but **0 of 18535 assertions failed**, and the Slang C++ build was fully green (`[1450/1450]`). Every failure was a thrown `Failed to load slang module "test" from source`, not a CHECK. **`0 assertions failed` alongside `N test cases failed` is the signature of a module-load/compile break, not a logic break** — doctest reports a thrown exception as a failed *case* while the assertion counter stays clean (18535/18535 Windows, 15593/15593 Linux). See that shape and stop hunting a behavioural regression; go read the compiler diagnostic. It ruled out every known slangpy cross-repo bucket by discriminator: not the fiddle/GCC-PCH break #12227 (zero `'friend' used outside of class`, and the PR was rebased past the #12233 fix), not the Windows `setup-python` toolcache flake (that step succeeded in 98 ms), not the `sgl_tests` exit-1-after-all-pass teardown flake (28 *real* case failures, not an exit-code artifact), not CUDA-OOM #1024 or a `test_nested` data mismatch (zero OOM/numeric markers).

**The generalizable rule: a slang PR whose whole purpose is to add a new diagnostic will legitimately break downstream repos that trip it — verify the causal link in the PR's own diff rather than inferring it from the title.** `gh api /repos/shader-slang/slang/pulls/<N>/files --jq '.[].patch'` and grep for the diagnostic code; here the diff added `36121` + the message template in `slang-diagnostics.lua`, the `RequestedCapabilityIncompatibleWithTarget` raise in `slang-target.cpp` (+79/-3), and a new test `incompatible-capability-for-target.slang`. That is proof, not correlation. Disposition: **legitimate, not rerunnable** (deterministic across platforms and attempts) — route to the PR author for coordination, because the real question is whether the downstream needs a target-conditional guard, not whether the slang change is wrong; an intended breaking change needs a downstream fix landed alongside it. Bonus permissions fact from the same triage, consistent with the rerun supersession above: `gh api /repos/shader-slang/slangpy --jq '.permissions'` returns admin/maintain/push/triage/pull **all false**, yet `/actions/jobs/<id>/logs` returned full 4289-line bodies first try — **"no permissions" does not mean you can't classify a cross-repo failure**, so never skip classification of a cross-repo red on the assumption logs are unreachable ([slang capability-error PRs break downstream slangpy via E36121 — an intended cross-repo break](../learnings/1785744645210-slang-capability-error-prs-break-downstream-slangp.md)).

**Read the diagnostic's emission loop before enumerating fix sites.** `TargetRequest::checkCapabilities(DiagnosticSink*)` (added by #11225, `source/slang/slang-target.cpp`, called from `slang-check-shader.cpp` — from `FrontEndCompileRequest::checkEntryPoints` for every target, so reachable on any compile) iterates exactly one collection: `for (auto atomVal : targetOptionSet.getArray(CompilerOptionName::Capability))`. That is the **API-level requested-capability list** — precisely what slangpy populates via `session_options.add(CompilerOptionName::Capability, findCapability("hlsl_nvapi"))`. It **never walks declarations**, so the `[__requiresNVAPI]` attribute at `slangpy/slang/atomics.slang:57` (`public extension half2 : IAtomicAddable`) is **not** a second fix site, however much the word *"requested"* in the message reads as "anything that asks for NVAPI" — attribute-level requirements are diagnosed by a different mechanism (use-site capability checking). **Rule: when a new diagnostic's message names a category, read the emission loop to learn what the compiler means by that word. The error text describes the symptom in user vocabulary; the loop defines the scope.** (Verification needs no `gh` token: `curl -sS https://api.github.com/repos/shader-slang/slang/pulls/11225/files` returns HTTP 200 unauthenticated with full `.patch` bodies. Mechanism notes: E36121 is declared in `slang-diagnostics.lua`, a **build-time generator** — grepping only `.cpp/.h` for the diagnostic *name* finds nothing; the emission site uses the generated CamelCase `Diagnostics::RequestedCapabilityIncompatibleWithTarget`. `hlsl_nvapi` is `def hlsl_nvapi : hlsl;` in `slang-capabilities.capdef`, strictly in the hlsl target family, so it genuinely IS incompatible with spirv, and the PR's GLSL escape hatch — `isGLSLBasedTarget() && cap contains spirv atom → skip` — does not rescue slangpy's vulkan path, which sets `SLANG_SPIRV` + `GENERATE_SPIRV_DIRECTLY` and therefore prints as `spirv`. `-ignore-capabilities` suppresses E36121; slangpy does not pass it.) ([E36121 fires only on explicitly requested capabilities — in-source `[__requiresNVAPI]` is not a second fix site](../learnings/1785750679044-slang-e36121-fires-only-on-explicitly-requested-ca.md))

### `SGL_HAS_NVAPI` ON/OFF is a natural experiment proving BOTH halves of the guard

slangpy's unconditional `hlsl_nvapi` request lives at `src/sgl/device/shader.cpp:404-408` (surfaced as slangpy#1087). The fix guards it with `SGL_HAS_NVAPI && type() == DeviceType::d3d12`, and the two CI platforms fail for **two different reasons** — grepping the configure log for `SGL_HAS_NVAPI:` is what proves neither half is sufficient alone:

- `linux-gcc`: `-- SGL_HAS_NVAPI: OFF` → the nvapi module is **never created or linked at all** (`external/CMakeLists.txt:251-259` sets it ON only iff the `slang-rhi-nvapi` CMake target exists), yet the capability is still requested → vulkan fails.
- `windows-msvc`: `-- SGL_HAS_NVAPI: ON` → d3d12 subcases **pass** (the capability is genuinely backed by a linked module); only vulkan fails.

So Windows has the flag ON and still breaks on vulkan, while Linux lacks the module entirely — anyone "simplifying" the guard to just the target check, or just the build flag, reintroduces one of the two failure modes. Note `SGL_HAS_NVAPI` is a **build-time** flag, not a runtime capability probe; easy to misread. Second reusable move from the same triage: **on Windows, "zero d3d12 failures" is decisive evidence, not absence of evidence** — `tests/sgl/testing.cpp:73` runs `device_types{d3d12, vulkan}`, so the d3d12 subcases *did* execute and passed. Confirm the fixture actually enumerates the target before concluding a target is unaffected; on Linux (vulkan-only) the identical observation would prove nothing ([`SGL_HAS_NVAPI` ON/OFF is a natural experiment proving both predicate halves](../learnings/1785745805020-slangpy-hlsl-nvapi-guard-sgl-has-nvapi-on-off-is-a.md)).

That triage also re-confirmed the cross-repo prerequisite ordering at HEAD, matching the #12289→#1083 sequencing rule above: `ci-latest-slang.yml`'s `build-pr` job runs `actions/checkout@v6` with **no `ref:`**, so slangpy always builds its default branch and `client_payload` controls only the *slang* ref ⇒ `SlangPy Tests` on a slang PR cannot go green until the slangpy fix is **merged to main** (a draft PR changes nothing). The guard is independently landable because `external/CMakeLists.txt:85` pins `SGL_SLANG_VERSION "2026.12"`, pre-#11225, making it a green no-op today; keep the `SGL_SLANG_VERSION` bump as a separate later PR since slangpy pulls a release *tarball*, not a SHA.

### A/B testing a slangpy fix against an UNRELEASED Slang PR

Proving the guard required building Slang at #11225's head locally. **Result** (slangpy commit `998aeb2`, "Only request hlsl_nvapi capability where the NVAPI Slang module is linked", against Slang at `db61cec` = `git describe` `v2026.14.1-24-gdb61cec`, NOT merged to master):

| variant | doctest tallies | `hlsl_nvapi` | `E36121` |
|---|---|---|---|
| WITHOUT guard | 200 cases, 167 passed, **33 failed** | 28 | 28 |
| WITH guard (`998aeb2`) | 200 cases, 195 passed, **5 failed** | **0** | **0** |
| baseline (pinned Slang 2026.12) | 200 cases, 195 passed, 5 failed | 0 | 0 |

The 5 WITH-guard failures are byte-identical to the pinned-2026.12 baseline (the 3 `test_dds_file.cpp` "DDS file has invalid header" + 2 `test_texture_loader.cpp` "Unsupported source image type" LFS-fixture cases), so the guard removes exactly the 28 capability errors and introduces nothing. **Establish that baseline control BEFORE the A/B or you will misattribute those 5.** Note the arithmetic check the table supports: 33 = 28 + 5 — a sum that falsified a monitor reporting 0 diagnostics.

**THE TRAP that produces a false negative.** `slang-11225/build/` contains BOTH the real build outputs (`build/Release/lib`) **and** a *downloaded release artifact* `build/slang-2026.14.1-linux-x86_64{.zip,/}` that slang's configure fetches for slang-llvm. That artifact is a **released** build and does NOT contain #11225 — point `-DSGL_LOCAL_SLANG_BUILD_DIR` at it and BOTH arms come back clean, a false negative that looks like a genuine result. **Always prove the binary contains the diagnostic before trusting either arm**, and check what the *test* binary resolves at runtime (slangpy copies the lib into its own build dir):

```bash
strings <dir>/libslang*.so | grep -c 'is incompatible with compilation target'
#   build/Release/lib            -> 2   ✅
#   slang-2026.14.1-*/lib        -> 0   ❌ silently invalidates the A/B
ldd build/linux-gcc/Debug/sgl_tests | grep slang     # then strings THAT path (got 2 ✅)
# cross-check build/Release/include/slang-tag-version.h -> SLANG_TAG_VERSION "2026.14.1-24-gdb61cec"
```

Mechanics worth reusing ([A/B testing a slangpy fix against an unreleased Slang PR](../learnings/1785747291729-a-b-testing-a-slangpy-fix-against-an-unreleased-sl.md), [PROVEN: the guard fixes slang#11225 E36121 — A/B result and its traps](../learnings/1785750627140-proven-slangpy-hlsl-nvapi-guard-fixes-slang-11225-.md)):

- **Read the clone log before trusting `git log -1`.** A background `clone && fetch pull/N/head && checkout FETCH_HEAD && submodule update` script shows HEAD on `master` if you look during the `fetch` window (`git for-each-ref` shows only master refs; `.git/FETCH_HEAD` exists but `git log FETCH_HEAD` says "ambiguous argument"). Re-check after the checkout line appears in the log. Prove the PR is genuinely unmerged with `git merge-base --is-ancestor <pr-head> origin/master`.
- **`git checkout <commit> -- <path>` STAGES as well as writing the worktree**, so a plain `git diff` afterwards is EMPTY and the revert looks like a no-op. Use `git diff HEAD` (or `git status --porcelain`, which shows `M` in column 1). `git reset --hard <commit>` clears both index and worktree.
- **Slang's `default` CMake preset is Ninja Multi-Config**, so `-DCMAKE_BUILD_TYPE=Release` is inert — `cmake --build build --config Release` is what selects the config, and `SGL_LOCAL_SLANG_BUILD_DIR` must then point at `build/Release` (it reads `$DIR/$BUILD_DIR/lib/libslang-compiler.so` and requires `$DIR/$BUILD_DIR/include/slang-tag-version.h` for the version, else FATAL_ERROR).
- Configure once with `cmake --preset linux-gcc --fresh -DSGL_LOCAL_SLANG=ON -DSGL_LOCAL_SLANG_DIR=<slang> -DSGL_LOCAL_SLANG_BUILD_DIR=build/Release`, then per arm revert/restore only `src/sgl/device/shader.cpp`, `cmake --build --preset linux-gcc-debug` (incremental ≈ minutes), `python3 tools/ci.py unit-test-cpp`.
- **Doctest name filters can silently select nothing** (`-tc=formats` / `-sc=vulkan` matched 0 here, 203 skipped) — run the whole binary and grep the log.
- **The Linux run genuinely exercises the SPIRV path**: `tests/sgl/testing.cpp`'s `run_gpu_test` is `{d3d12, vulkan}` on Windows but **vulkan-only on Linux**, and a real NVIDIA L40S is present (`/etc/vulkan/icd.d/nvidia_icd.json` is the real ICD — `/usr/share/vulkan/icd.d/` holds only intel/radeon/lavapipe, so listing just the latter makes it look like there is no NVIDIA Vulkan; a ctypes `vkCreateInstance` + `vkEnumeratePhysicalDevices` probe proves a usable GPU without installing `vulkaninfo`). But because `SGL_HAS_NVAPI` is 0 on Linux the guard's first clause short-circuits there: the guard's *effect* is fully observable, yet a Linux run **cannot** distinguish the `SGL_HAS_NVAPI` clause from the `device_type == d3d12` clause — which is exactly why the Windows `SGL_HAS_NVAPI: ON` leg is load-bearing.
