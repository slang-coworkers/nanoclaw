# Slang SPIR-V entry points, varyings, and execution modes

How the SPIR-V backend assigns varying locations, carries interpolation modes, emits depth and topology execution modes, lets `spirv_asm` reference entry points, and shares module-scope interface variables between entry points. Entry-point renaming and the attribute-to-execution-mode recipe are on [[wiki/concepts/slang-backends-spirv.md]]; GLSL-side varying legalization is on [[wiki/concepts/slang-backends-glsl-entry-point-and-varying-legalization.md]].

## TL;DR

- `SV_Target<N>` is the only varying semantic whose suffix is an absolute GLSL/SPIR-V location. User-defined suffixes are names, so locations follow declaration order; never genericize suffix→location (that path is WGSL/Metal-only).
- `[[vk::location(N)]]` on a struct FIELD of a varying parameter is an offset inside the struct in every stage (measured at fef74e3c6, #14366); only an explicit Location on a whole parameter is absolute, and DXC and glslang treat field Locations as absolute. Every consumer sums VarLayout offsets from parameter to leaf, so the producer-side fix anchors any layout whose subtree has an explicit field at offset 0 and touches no consumer. DeepWiki's "field Locations are absolute" is wrong; measure.
- DXC's reference rule for hull/domain locations: HS outputs and DS inputs (per-patch and per-control-point alike) are sorted by semantic string and numbered from one shared counter before unused DS inputs are dropped, so the two stages agree whatever the DS parameter order.
- Since #13923 a varying can carry two `IRInterpolationModeDecoration`s (`centroid noperspective`), so a first-only `findDecoration` test is order-dependent, and direct SPIR-V and GLSL legalize fail on opposite modifier orders. Triage both orders on all three paths.
- One module-scope `Input` variable may serve entry points of different stages (a vertex EP reading it, a fragment EP interpolating it). A sharing check compares locations, never stages.
- A new IR instruction or decoration needs a `k_maxSupportedModuleVersion` bump; the stable-names CI check does not catch a missing one.
- The direct SPIR-V and GLSL paths diverge on depth execution modes: GLSL drops the directional mode, and the direct path collapses to `DepthReplacing` when two depth builtins coexist. Check both with `-emit-spirv-via-glsl`.
- The hull/domain output-topology arm handles only a subset; `Line` falls through to the mesh arm and emits an invalid `OutputLinesEXT`.
- In `spirv_asm`, `__entryPoint` is special-cased only for `OpExecutionMode`; `OpExecutionModeId __entryPoint` ICEs (E99997). Write `OpExecutionModeId $main <Mode> $specConst` inside each entry point (direct SPIR-V only).
- `VulkanBindShift` through the C++ API packs `kind << 24 | set` with u=0, s=1, t=2, b=3.
- Hull/domain Locations must come from one shared, non-overlapping numbering: base the hull patch-constant Locations on the front-end result layout (PR #14335), not on the per-leaf `usedBindingIndex` set; glslang rejects overlapping patch/per-vertex Locations, and spirv-val never checks HS↔DS agreement.
- Even after #14335 the hull and domain agree only for a patch-first domain or a Location-free control point; a domain with no `OutputPatch` numbers patch constants from 0 like a patch-first one.
- The entry-point result layout has two producers (front-end lowering and `translateGlobalVaryingVar` for global `out`s, which loses the aggregate offset/size). Probe both, and A/B the whole text-target test corpus for shared layout changes.
- Probe before "fixing" a first-only decoration reader: `PerVertex` readers are safe for valid programs. For `SV_Barycentrics`, direct SPIR-V should follow the builtin GLSL legalization already chose (`IRImportDecoration`), as `sv_position` does.

## Varying locations

`SV_Target<N>` is the only varying semantic that both consumes a GLSL/SPIR-V location and carries a suffix naming an absolute slot. In `processEntryPointVaryingParameter` (`slang-parameter-binding.cpp` ~:2064), it alone takes the `Output` layout; every other `SV_`/`NV_` semantic is a builtin with direction mask 0. In #11944, `systemValueSemanticIndex` is stored but never read, so an out-of-order `SV_TargetN` gets its location from declaration order. User-defined suffixes (TEXCOORD0, COLOR1) are name disambiguators: GLSL/SPIR-V assign those locations in declaration order, and HLSL matches stages by name. Deriving locations from those suffixes would break inter-stage matching, so the fix applies to SV_Target only. The `SV_TARGET<N>→LOCATION_<N>` translation in `fixFieldSemanticsOfFlatStruct` (`slang-ir-legalize-varying-params.cpp:3730`) runs only for Metal and WGSL. GLSL/SPIR-V read the VarLayout `index` in emit (`slang-emit-spirv.cpp:3445-3465`) ([SV_Target-N is the only absolute-location semantic](../learnings/1784321038825-slang-sv-target-n-is-the-only-varying-semantic-enc.md)).

**Explicit `[[vk::location]]` on a struct field is struct-relative (#14366).** Consider `vsMain(A a, B b)` where a field of `B` carries `[[vk::location(5)]]`. Measured on master fef74e3c6, that field lands at Location 6, not 5, in every stage (VS, FS, domain): `slang-parameter-binding.cpp:2849-2878` gives the field its own index inside the struct, and `endLayout` (:3186-3228) then gives the struct parameter a sequential base. Only an explicit Location on a WHOLE parameter is absolute, and the hull patch-constant output ignores the attribute entirely (`slang-ir-glsl-legalize.cpp:1210`). DeepWiki says field Locations are "absolute", which is wrong for Slang; measure instead. The reference compilers do treat them as absolute: DXC 1.8.2505 `-spirv` does, but errors on partial explicit assignment ("partial explicit stage input location assignment via vk::location(X) unsupported") and on duplicates; glslang 16.6.0 (HLSL input) does, auto-numbers implicit fields from 0 ignoring the explicit ones, and does not diagnose duplicates. Tooling: DXC v1.9.2609 for Linux needs GLIBC 2.38, which the containers lack, so use the v1.8.2505 tarball; the glslang main-tot release tarball works; a new `git worktree` of `/workspace/agent/slang` needs `git -c protocol.file.allow=always -c submodule."external/WindowsToolchain".update=none submodule update --init --recursive`; and `-target spirv-asm` needs target `slang-glslang` built as well as `slangc` [vk::location on a struct field is struct-relative in every stage](../learnings/1793987956975-vk-location-on-a-struct-field-is-struct-relative-i.md).

Making the field Location absolute needs no consumer change. Reflection, `createGLSLGlobalVaryingsImpl` (`slang-ir-glsl-legalize.cpp` ~:2308) and `slang-ir-legalize-varying-params.cpp` (~:3202, ~:3536) all compute a leaf's Location by summing VarLayout offsets from the parameter down to the leaf, so the fix anchors every layout whose subtree has a field carrying its own attribute at offset 0 in its parent; the field offsets are then absolute, and `endLayout` reserves the explicit leaves before it gap-fills the implicit members and the implicit fields of anchored structs. The traps `/code-review` found on that change: apply the logic only to `VaryingInput`/`VaryingOutput` (the entry-point result also carries Uniform offsets on CPU/CUDA, and entry-point descriptor kinds keep the old single-set path); a geometry-shader `triangle T v[3]` input is per vertex but sized elem×3 by the front end, so an explicit Location on it reserves the element count only, or two consecutive explicit GS arrays falsely overlap; `vk::index` makes overlapping Locations legal only for fragment `VaryingOutput` (dual-source blending); overlap diagnostics should name the path (`s1.x` vs `s2.x`), since one struct used for two parameters otherwise prints the same name twice; `isVaryingResourceKind` is declared in `slang-ir-insts.h` but never defined, so a static function of that name fails to compile; and `translateGlobalVaryingVar` places global `in` variables after the LAST parameter's end, which with gap-fill can land on an explicit field (VUID-08721), so the IR side must start them at the max end over all parameters — the front end cannot fix that alone. The A/B that held up compiles every test file with a `[shader("vertex|fragment|hull|domain|geometry|mesh")]` entry point and no vk::location through base and new slangc to spirv-asm/glsl/metal/wgsl plus `-reflection-json`, each binary in its own output dir with the same file names so stderr paths compare equal [Slang varying layout: make explicit field vk::location absolute by anchoring at offset 0 (path-sum invariant)](../learnings/1793999288631-slang-varying-layout-make-explicit-field-vk-locati.md).

**Hull/domain locations: DXC's reference rule.** For tessellation location bugs (for example slang#14334), DXC's SPIR-V backend is the reference. `finalizeStageIOLocationsForASingleEntryPoint` in DXC's `DeclResultIdMapper.cpp` sorts the HS outputs and the DS inputs, both the per-patch `Patch` variables and the per-control-point ones, alphabetically by semantic string and numbers them from ONE shared `Location` counter. It assigns the numbers before it drops unused DS inputs, so the gaps stay, and the HS and DS agree whatever order the DS declares its parameters in. A DXC binary that runs in the coworker containers is on [[wiki/concepts/slang-tooling-dxc-prebuilts-and-cmake.md]] ([HS/DS SPIR-V location rule](../learnings/1793858475820-dxc-linux-binary-that-runs-on-debian-12-glibc-2-36.md)).

Slang breaks that agreement on the hull side. In `slang-ir-glsl-legalize.cpp`, `createVarLayoutForLegalizedGlobalParam` (~:1049) adds every legalized leaf's binding index to `context->usedBindingIndex[kind]`, system values included, and `createGLSLGlobalVaryings` defaults the index to 0 when there is no layout offset, so a hull `SV_Position` reserves slot 0. Since PR #13078 the patch-constant base is `usedBindingIndex[VaryingOutput].getLSBZero()`, so an SV-only control-point output pushes the patch-constant user fields to Location 1, while the domain, which takes front-end layout in declaration order and never consults `usedBindingIndex`, puts them at 0 (#14334). The tools disagree on whether patch and per-vertex locations share a namespace: SPIRV-Tools keeps separate `patch_locations_*` sets, glslang's `checkLocationRange` chooses the set only by in/out (a patch out and a per-vertex out at one Location collide in GLSL), and DXC uses its one shared counter. Shared, non-overlapping numbering is therefore the only scheme valid everywhere; a separate per-patch space from 0 passes spirv-val but breaks GLSL. spirv-val does not check HS↔DS agreement, so compare the two compiles yourself ([system values pollute usedBindingIndex](../learnings/1793859027855-tessellation-hs-ds-location-system-values-pollute-.md)). The per-leaf set is the wrong source altogether: it also records only the first slot of a multi-Location leaf (`float4x4` → 1) and `getLSBZero` can land in an explicit `[[vk::location]]` gap. The fix for #14334 (PR #14335) bases the hull patch-constant Locations on the hull result's front-end `VaryingOutput` offset plus type size (`entryPointLayout->getResultLayout()`), the same layout rules the domain uses for `OutputPatch<CP,N>` and the patch input. "Skip builtins in the set" is a trap: it regresses `CP { float4 pos : SV_Position; [[vk::location(1)]] float3 n : NORMAL; }`, where master reached base 2 only because the builtin wrongly filled slot 0. There is no HS/DS GPU harness (slang-rhi's Vulkan backend has no tessellation pipeline state and maps HULL/DOMAIN to the opposite VK stages, `vk-utils.cpp:705-712`; render-test has no tessellation case), so A/B against a saved master `slangc` + `lib/*.so`; anchor FileCheck as `{{^}}patch{{$}}`, since `patch` also matches `patch_m_0` ([read the front-end result layout](../learnings/1793864339897-hull-patch-constant-location-base-read-the-front-e.md)).

**What #14335 still leaves unequal, and the second result-layout producer.** After #14335 the hull's patch-constant base is the END of the hull result's `VaryingOutput` layout, while the domain numbers its varying inputs in declaration order (`SimpleScopeLayoutBuilder`, first-fit) and `HLSLPatchType` counts as one element, not N. The stages agree only when (a) the domain declares `OutputPatch<CP,N>` before the patch-constant struct, or (b) the control point uses no Location (builtins only, such as `SV_Position`/`SV_ClipDistance`). A domain with NO `OutputPatch` numbers patch constants from 0 exactly like a patch-first domain: `CP {SV_Position; float3 n : NORMAL}` gives hull 1/2 vs domain 0/1 on master and after the fix; the issue repro worked only because its CP was `SV_Position`-only. Pre-existing on master: hull `out` params fail spirv-val (OpStore type mismatch) and `-emit-spirv-via-glsl` fails in glslang for every hull ([domain without OutputPatch = patch-first domain](../learnings/1793866112050-hull-domain-patch-constant-locations-a-domain-with.md)). The result layout itself has TWO producers: `lowerEntryPointResultLayout` (front end) and `translateGlobalVaryingVar` (`slang-ir-translate-global-varying-var.cpp`), which for a `void` hull writing global `out` variables replaces it with a synthesized struct layout whose fields keep offsets but whose aggregate has no `VaryingOutput` offset or size, so R1 of #14335 read base 0 and a maintainer caught it after 13 CP-shape probes passed. Any IR consumer of `getResultLayout()` must probe a function result AND the same outputs written through globals (implicit, `layout(location)`, array, matrix, `SV_` variants). Cheap net for shared layout code: a corpus A/B running every `//TEST` SIMPLE/CROSS_COMPILE command (~3700) through old and new slangc and diffing; map `-target spirv` to `spirv-asm` first (binary decoded as text compares "equal" and proves nothing) and normalize `-g` OpStrings that embed the `-I` path ([probe GLSL-style global `out` entry points too](../learnings/1793922992103-when-a-change-reads-an-entry-point-s-result-layout.md)).

**One Input variable can serve entry points of different stages (#13687, PR #13726).** When several entry points must share one real module-scope `Input` variable, for example a global passed to GLSL `interpolateAt*`, which needs the address of an Input variable, check only that its location matches. Do not check the stage: one `OpVariable Input` may be listed by a vertex entry point that reads it directly and by a fragment entry point that interpolates it. That shape was valid on master, and a stage-equality check wrongly rejected it. To make an AST-only call-site requirement visible to IR passes, lower the attribute (`[__GLSLRequireShaderInputParameter(n)]`) to an IR decoration on the function; a trigger such as "the global's address is passed to any call" also fires on valid `__constref` calls. The same PR added an IR decoration, which also needs `k_maxSupportedModuleVersion` incremented in `source/slang/slang-ir.h` with a one-line comment beside the existing ones (`docs/design/backwards-compat-for-ir-modules.md`, "When to Update Module Version"); the stable-names CI check does not catch a missing bump, and peer review did. Run that check locally by building lua out of tree (`cp -r external/lua /tmp/lua && make -C /tmp/lua MYCFLAGS=-DLUA_USE_POSIX MYLIBS=`), then `/tmp/lua/lua extras/check-ir-stable-names.lua check` ([adding an IR opcode needs a module-version bump; one SPIR-V Input var can serve EPs of different stages](../learnings/1792218658955-slang-adding-an-ir-opcode-needs-a-module-version-b.md)). The full nine-site recipe for a new entry-point attribute and execution mode is on [[wiki/concepts/slang-backends-spirv.md]].

## Interpolation modes: two decorations per varying since #13923

Since #13923 (v2026.21) a varying can carry TWO `IRInterpolationModeDecoration`s, one for the mode and one for centroid/sample, as in `centroid noperspective`. Any consumer that calls `findDecoration<IRInterpolationModeDecoration>()` and then tests `getMode() == X` sees only the first one, so its answer depends on the modifier order. The order is also mirrored between paths. `addDecoration` inserts at the head, so the original parameter holds the decorations in reverse source order. `createVarLayoutForLegalizedGlobalParam` (`slang-ir-glsl-legalize.cpp` ~1083) copies them onto the new global with `addDecoration` again, which reverses them back to source order. Direct SPIR-V reads the copied global and GLSL legalize reads the original parameter or field key, so the two paths fail on OPPOSITE modifier orders. A reporter who says "GLSL is correct" may have tried only one order. This was found on #14333 (`SV_Barycentrics`: `slang-emit-spirv.cpp:8114`, `slang-ir-glsl-legalize.cpp:957`). To triage an interpolation-mode bug, test both modifier orders on direct SPIR-V, `-target glsl` and `-emit-spirv-via-glsl`. Before calling it a regression, check whether the combination was legal before v2026.21: it used to be E31202 ([interpolation decorations: first-only findDecoration is order-dependent](../learnings/1793858499107-slang-ir-interpolation-decorations-first-only-find.md)).

**Not every first-only reader is a bug: probe first.** The #14365 review flagged the first-decoration-only `PerVertex` checks (`slang-emit-glsl.cpp:1927`, `slang-ir-spirv-legalize.cpp:461`) as the same order bug, but for valid programs they are safe: with `GetAttributeAtVertex`, GLSL legalization builds a separate global carrying `[PerVertex]` and no interpolation-mode decoration, so `pervertex centroid` and `centroid pervertex` emit byte-identical GLSL and SPIR-V. Order matters only when a `pervertex` input is read directly (GLSL `c[3]` vs `c`), a shape that is already invalid with a lone `pervertex` (glslang cannot convert the array to vec4, and rejects `pervertexEXT centroid` as "one auxiliary qualifier"). Probe before asking a fixer to "migrate the remaining first-only readers" ([PerVertex first-only readers are safe](../learnings/1793921273376-pervertex-first-only-decoration-readers-are-safe-f.md)).

**`SV_Barycentrics`: one decision point, and the gaps beyond #14333.** GLSL legalization already records the builtin it chose as an `IRImportDecoration` on the global (`slang-ir-glsl-legalize.cpp` ~1106, e.g. `gl_BaryCoordNoPerspEXT`), and direct SPIR-V `maybeEmitSystemVal` already follows that name for `sv_position` (`slang-emit-spirv.cpp` ~7890) and `sv_shadingrate` (~8159). Doing the same for barycentrics collapses the two decision points into one and fixes the nested divergence (`noperspective PSIn i` with a `centroid ... : SV_Barycentrics` field gives Persp on direct SPIR-V and NoPersp on GLSL, because GLSL legalize walks every outer param while the SPIR-V global gets only the innermost decl's decorations); the prototype was 4 lines and kept rasterization + cross-compile 158/158, and the choice was left to the maintainer on draft #14365. Pre-existing gaps on master 10c8807b1: `centroid`/`sample` are never emitted on the barycentric builtins on any path, even a lone always-legal `centroid`, although VK_KHR_fragment_shader_barycentric allows them; a fix needs a design for `getBuiltinGlobalVar` (`slang-emit-spirv.cpp`), which shares one variable per (builtin, storage class, isFlat, type) key and adds only Flat, while Vulkan forbids the same BuiltIn twice in one entry-point interface. HLSL drops `noperspective` from an `SV_Barycentrics` entry-point PARAMETER but keeps it on a struct FIELD, and Metal emits `[[barycentric_coord]]` with no no-perspective qualifier. A/B note: `slang-test -bindir <other build>` silently IGNORED the cuda tests; run the other build's own `slang-test` ([SV_Barycentrics pre-existing gaps](../learnings/1793919322362-slang-sv-barycentrics-pre-existing-gaps-beyond-143.md), [direct SPIR-V can reuse GLSL's barycentric choice](../learnings/1793921273376-pervertex-first-only-decoration-readers-are-safe-f.md)).

## Depth and topology execution modes

**Depth.** For `SV_DepthGreaterEqual`/`SV_DepthLessEqual`, the direct SPIR-V path emits `DepthReplacing` plus `DepthGreater`/`DepthLess`, while the GLSL/via-GLSL path drops the directional mode. On the direct path, when two depth-affecting builtins coexist (e.g. `SV_Depth` + `SV_DepthGreaterEqual`), `maybeEmitEntryPointDepthReplacingExecutionMode` collapses to `DepthReplacing` only, through its `else if (mode != thisMode)` conflict branch ([GLSL drops directional mode](../learnings/1782165817624-slang-sv-depth-greater-less-equal-direct-spir-v-co.md), [direct path also drops via conflict branch](../learnings/1782211031715-slang-direct-spir-v-depth-mode-also-dropped-via-co.md)). In `slang-ir-glsl-legalize.cpp`, gate a new entry-point system-value decoration on `kind == LayoutResourceKind::VaryingOutput`, as `sv_position` does (~478-498), and add the op to `isSimpleDecoration` (`slang-ir.cpp` ~86) so duplicates collapse. For depth this is only defense-in-depth: depth semantics are setter-only in `core.meta.slang` (E30702), so the inout double-attach can't happen ([VaryingOutput gating](../learnings/1782175454099-glsl-legalize-per-entry-point-system-value-decorat.md)).

**Output topology (hull/domain).** The `kIROp_OutputTopologyDecoration` hull/domain arm handles only TriangleCW/TriangleCCW/Point. `Line` falls through to the mesh arm and emits `OutputLinesEXT`, which is invalid on tessellation stages. For isoline, `Line` should be a no-op because `OpExecutionMode Isolines` already implies it, and the fallback needs a stage guard ([hull/domain topology subset](../learnings/1780253722562-slang-spir-v-output-topology-hull-domain-arm-only-.md)).

## `spirv_asm` execution modes: `__entryPoint` works only for `OpExecutionMode`

In `spirv_asm`, `OpExecutionMode __entryPoint <Mode> ...` is special-cased (`slang-emit-spirv.cpp` ~11924): it is emitted once for EVERY entry point that references the enclosing function, so it works from a shared helper. `OpExecutionModeId` is not special-cased. It takes the generic path, where `__entryPoint` hits `SLANG_UNREACHABLE` "Unhandled case in emitSPIRVAsm" (E99997). For Id modes such as `OpacityMicromapIdKHR`, write `OpExecutionModeId $main <Mode> $specConst` inside each entry point: `$main` is an ordinary function-value reference emitted verbatim, and a `[vk::constant_id(N)] const bool` referenced as `$name` becomes an `OpSpecConstant` with SpecId that spirv-val accepts as the Id operand. This works on direct SPIR-V only; `-target glsl` and `-emit-spirv-via-glsl` ICE on these blocks ("unexpected IR opcode" / "circularity during codegen"). DeepWiki says `__entryPoint` works for execution modes and is tested; that is wrong for `OpExecutionModeId`, and `tests/` has no such test (#13438, master 6ba151dcf) ([spirv_asm OpExecutionModeId: $entryName works, __entryPoint ICEs](../learnings/1791207151155-spirv-asm-opexecutionmodeid-entryname-works-entryp.md)).

## Binding shifts through the API

**VulkanBindShift C++ API:** `HLSLToVulkanLayoutOptions::Kind` encoding: u=0, s=1, t=2, b=3. Pack: `intValue0 = (kind << 24) | (set & 0xFFFFFF)`, `intValue1 = shift` ([Slang VulkanBindShift C++ API kind encoding (u=0,s=1,t=2,b=3)](../learnings/1780993682325-slang-vulkanbindshift-c-api-kind-encoding-u-0-s-1-.md)).
