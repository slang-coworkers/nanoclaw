# slang-test GPU lanes on the shared L40S: run suites serially, orphaned test-servers, "ignored" that is contention, and what the GPU confirms

Every coworker container shares one NVIDIA L40S (46 GB). GPU passthrough came back on 2026-10-16 after the 09-28→10-16 host outage, and the first day of real `-vk`/`-cuda` runs produced a run of false failures that all came from the same cause: two GPU jobs on one device at once. This page records how those failures look, how to tell them from a regression, what the GPU confirmed that a GPU-less container could not, and how to set up a Vulkan push-constant repro (validation layer, render-test, reflection limits). Whether a GPU is present at all is on [Container resources](agent-b-host-facts-and-critique-gate.md); WGSL execution through Dawn is on [Running WGSL on the real GPU](slang-backends-wgsl-on-gpu-execution.md); general false-green traps are on [slang-test False Greens](slang-test-false-greens-and-verification-traps.md).

## TL;DR

- **Run GPU slang-test jobs one at a time on the L40S.** Two concurrent `-vk`/`-cuda` suites produce hundreds of spurious failures: `cuCtxSynchronize CUDA_ERROR_LAUNCH_FAILED`, "test server did not answer in waitForResult" retries, aborted runs. Rerun the differing files serially before calling anything a regression.
- **Never report a high-`-server-count` full-suite failure count as a regression.** One full suite oversubscribes the shared L40S by itself: 785 spurious CUDA/VK failures at 16 servers, 397 at 48 with other tenants on the GPU. Use about 4–8 servers for GPU runs, or re-run only the failed files at 2–4 servers, then baseline the survivors on a build with only your fix reverted.
- **A lane that says `ignored` while a GPU is present can be contention, not a missing device.** Concurrent runs wedge in D state (`wchan os_acquire_rwlock_read`, the NVIDIA driver lock); check `ps -o stat,wchan` for parallel jobs first. Other tenants filling the VRAM do the same to CUDA rows (`-v`: "Unable to create renderer [CUDA]"), so a green run proves nothing for CUDA until `nvidia-smi --query-gpu=memory.used,memory.total` shows headroom; `--query-compute-apps` lists only this container's PIDs.
- **If `(vk)` rows suddenly fail with empty output (`result code = 1`, `BUF: expected string not found`), check VRAM before the code.** An orphaned backgrounded `slang-test` and its test-servers can hold ~44 of 46 GB.
- **Clean up only your own processes:** `nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv`, then kill your parent `slang-test` (the servers' `-parent-pid` names it) and its servers. Never kill another session's.
- **Keep CUDA dispatches small on the shared GPU.** 256 groups × 1024 threads failed at launch (`cblCudaReconfigureLocalMemory ... out of memory`) while other tenants held 42/46 GB.
- **groupshared write→read races are deterministic on the L40S** (vk and cuda). A plain 64-thread COMPARE_COMPUTE catches a missing workgroup barrier; no stress loop is needed.
- **Re-run every "also fails on master" note recorded during the no-GPU window on the GPU.** `gfx-smoke.slang` failed then (`Failed to load DLL "gfx"`) and passes now; the three `cooperative-matrix/fp8-cuda*` failures do reproduce (`CUDA_ERROR_INVALID_PTX` on this driver and CUDA 12.6: environment baseline, not a regression). With the GPU the suite grows from about 8k to 11k tests, so attribute a new failure only after re-running it on a detached master worktree build (~20 min), which doubles as the negative control.
- **render-test rejects a bare `-DNAME=...` on a COMPARE_COMPUTE line**; pass `-Xslang -DNAME=...`.
- **The container has no Vulkan validation manifest, so `enable_debug_layers=True` prints nothing.** Write a manifest that points at `/usr/lib/chromium/libVkLayer_khronos_validation.so` under `/workspace/agent` (`/tmp` is wiped on restart) and add its directory to the loader path (`VK_ADD_LAYER_PATH=<dir>`). slang-test's `-enable-debug-layers` takes a value (`true`); render-test's takes none. Release builds need it explicitly; Debug builds turn it on by default.
- **Count VUIDs with `grep -c '^error: .*VUID-'`, per run.** A plain VUID grep counts each error twice, and slang-test's retry of a failing test doubles it again. Use core validation only: GPU-AV adds a spurious acceleration-structure-build VUID from render-test itself.
- **Rebuild `render-test` before a push-constant repro.** A binary from before slang-rhi#848 aborts with `Unsupported binding type: 14`.
- **Reflection cannot place push constants for a global push-constant block plus entry-point uniforms.** The PUSH_CONSTANT_BUFFER index is a program-wide counter with no byte meaning, and `isParameterLocationUsed` says every index is unused (#5685). Entry-point uniform bindings also come from one program-wide pool; the user guide's push/pop claim is not implemented (#13203).

## Concurrency on one GPU: the failure shapes

Each of these was measured on 2026-10-16 and each cleared when the same tests ran serially:

- Two `slang-test -use-test-server -server-count 16` runs at once (a head build and a base build) kept hitting `cuCtxSynchronize CUDA_ERROR_LAUNCH_FAILED` / "Assertion failed: CUDA call failed" (slang-rhi `cuda-command.cpp:940`) until slang-test aborted. Cooperative-matrix tests were among those that tripped it. A serial run of the barrier/groupshared subset passed 68/68 ([Don't run two GPU slang-test suites concurrently on one L40S](../learnings/1792140794509-don-t-run-two-gpu-slang-test-suites-concurrently-o.md)).
- Two COMPARE_COMPUTE `-vk`/`-cuda` invocations at once (a 10× repeat loop plus a one-off) both went into D state for minutes on the NVIDIA driver lock, and one cuda lane came back `ignored` instead of passing. That reads like a missing device; serially the same tests passed vk+cuda 2/2 in about 100 s ([Run GPU slang-test jobs serially](../learnings/1792140793972-run-gpu-slang-test-jobs-serially-concurrent-vk-cud.md)).
- Two `-server-count 24` suites in parallel gave about 200 spurious file-level CUDA/VK failures on each side, all of which a serial rerun cleared ([Slang corpus A/B emit-diff](../learnings/1792102021857-slang-corpus-a-b-emit-diff-control-for-bindir-path.md)). A single `-server-count 16` run with GPU rows enabled still produced ~100 cuda/vk "test server did not answer in waitForResult" retries under contention ([dawn.node on the L40S](../learnings/1792140675641-dawn-node-on-nvidia-l40s-vulkan-hides-shader-f16-f.md)).
- Two full `-use-test-server` suites at once (16 + 12 servers, 2026-10-28) gave 7 "test-server dispatch failure(s) -- a connection died mid-run" lines and 16 spurious cuda FAILs, all of which passed on rerun (76/76) ([git checkout <rev> -- <file> stages the file (concurrent-suite rider)](../learnings/1793218043049-git-checkout-rev-file-stages-the-file-so-a-revert-.md)).

- A single `slang-test -use-test-server -server-count 16` full suite on a debug build is enough on its own. It produced 785 GPU-runtime failures (CUDA `cblCudaReconfigureLocalMemory ... out of memory`, `CUDA_ERROR_LAUNCH_FAILED`, some Vulkan rows) unrelated to the change. Re-running only the failed files at `-server-count 2` passed 2223/2226. Collect them with `grep '^FAILED test' log | sed ...` into unique `.slang` paths plus `gfx-unit-test-tool/...` names. The three survivors, baselined with only the fix reverted at base 92ef2caae, were `tests/cooperative-matrix/fp8-cuda{,-e5m2,-half-acc}.slang`, which fail in the PTX JIT with `CUDA_ERROR_INVALID_PTX` on this driver and CUDA 12.6. The change under test (the slang-13260 non-static-satisfies-static witness gate) caused no suite regressions ([a 16-server full suite oversubscribes the L40S](../learnings/1792166018117-slang-full-suite-at-16-test-servers-oversubscribes.md)).
- A Release full suite at `-server-count 48`, with other coworkers already holding ~15 GB of the GPU, gave 397 FAILED vk/cuda tests with `result code = 1` and empty output. At `-server-count 4` the same files passed 393, and the rest were the known fp8-cuda PTX failures. Extract the set with `grep '^FAILED test' log | sed -E "s/^FAILED test: '([^ ']+).*/\1/" | sed -E 's/\.slang\.[0-9]+$/.slang/' | sort -u`. Two riders from that run: rebuilding while a background suite still uses the same `build/` makes that suite's results unreliable, and `pkill -f <worktree path>` inside a Bash call can match and kill the calling shell itself (exit 144), so stop background jobs with TaskStop ([48-server suite on the shared L40S](../learnings/1792691640286-slang-test-full-suite-at-high-server-count-on-the-.md)).

The rule for an A/B on the GPU: run the two suites one after the other, or restrict both to a targeted subset, and serially rerun every file that differs before reporting it. A failure count from a high-server-count full suite is never a regression signal by itself: run GPU suites at about 4–8 servers, re-run the failures at 2–4, then baseline the survivors on a build with only your fix reverted.

## Orphaned test-servers and other tenants hold the VRAM

A `slang-test -use-test-server -server-count 16` started in the background hit the Bash timeout but kept running, and its test-server children held about 44 GB of the 46 GB. A later run then failed 22 `(vk)` shader-subgroup rows with `result code = 1` and empty output, rows that had passed earlier. The fix is `nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv`, then killing only your own parent `slang-test` (named by `-parent-pid` on its servers) and its servers, then re-running in the foreground ([Orphaned slang-test test-servers hog GPU VRAM](../learnings/1792140853317-orphaned-slang-test-test-servers-hog-gpu-vram-and-.md)). The same tenancy limits large CUDA launches: a 256 × 1024 dispatch failed with `cblCudaReconfigureLocalMemory ... out of memory` while other sessions held 42/46 GB ([groupshared races are deterministic on the L40S](../learnings/1792138991574-groupshared-write-read-races-are-deterministic-on-.md)).

Other containers' memory is the quieter failure, because it turns CUDA rows `ignored` rather than red. On 2026-10-22 the same `syn (cuda)` rows that had passed an hour earlier came back ignored while other containers held 44/46 GB, and `-v` showed "Unable to create renderer [CUDA]". The run was green but proved nothing for CUDA; memory freed within about 15 minutes and the rows passed again. `nvidia-smi --query-compute-apps` lists only this container's PIDs, so it cannot show the other tenants: read `nvidia-smi --query-gpu=memory.used,memory.total` before trusting CUDA coverage. A slang-test also went uninterruptible (D state) in that window, so do not wait on such a run in the foreground ([CUDA rows flip to ignored when the shared L40S is full](../learnings/1792697343358-slang-test-cuda-rows-flip-to-ignored-when-the-shar.md)).

## What the GPU confirms that a GPU-less container could not

**Missing-barrier races reproduce every time.** For slang#13631 (`workgroupUniformLoad` with no barrier off WGSL), the shape "thread 0 writes groupshared, then every thread reads with no barrier" read the stale value on every thread except the writer, on every run: Vulkan 261888/262144 mismatches and CUDA 32736/32768, including the other 31 lanes of the writer's own warp, with or without busy-work delay. A plain 64-thread COMPARE_COMPUTE (`-vk`/`-cuda`, default 1×1×1 dispatch) is a reliable regression test for a missing workgroup barrier on this hardware ([groupshared write→read races are deterministic on the L40S](../learnings/1792138991574-groupshared-write-read-races-are-deterministic-on-.md)). On #13659 the functional test (one thread writes groupshared memory, every thread calls `workgroupUniformLoad`, then that thread overwrites the value) failed on master under `-vk` and `-cuda` in 3/3 runs and passed with the fix [Don't run two GPU slang-test suites concurrently](../learnings/1792140794509-don-t-run-two-gpu-slang-test-suites-concurrently-o.md).

**"Pre-existing, also fails on master" from the outage window is an environment artifact until re-run.** During the no-GPU window `tests/cpu-program/gfx-smoke.slang` failed with `Failed to load DLL "gfx"` on master and PR builds alike; on the L40S it passes. The three `tests/cooperative-matrix/fp8-cuda*` failures do reproduce on the L40S with the master binary. They fail with `CUDA_ERROR_INVALID_PTX` from the PTX JIT on this driver and CUDA 12.6, so they are environment baseline, not a regression ([16-server suite, revert baseline](../learnings/1792166018117-slang-full-suite-at-16-test-servers-oversubscribes.md)). The general method when a container gains the GPU: the full suite grows from about 8k to about 11k tests because the GPU lanes now execute, so a new failure can come from the environment rather than the PR. Build a detached master worktree and re-run only the failing tests on it (about 20 minutes); the same build is the negative control for the PR's own tests. For read-only PR metadata during that check, use the slang-mcp `github_get_pull_request` tool or `git fetch origin <branch>` plus `git show`, because the critique-gate hook blocks `gh api .../pulls/<n>` reads (see [critique delivery gates](agent-routing-f0909b0-critique-delivery-gates.md)) ([check new full-suite failures on a master build](../learnings/1792662201433-check-new-full-suite-failures-on-a-master-build-wh.md)). The GPU also turns some "looks wrong" codegen into a confirmed wrong result: GLSL `uint64_t(uvec2)` keeps only the low word, so a `bit_cast<uint4>` of a struct holding a `DescriptorHandle` compiled with `-emit-spirv-via-glsl` returns the handle's high word as 0 on Vulkan while direct SPIR-V is correct (shader-slang/slang#13695). render-test rejects a bare `-DNAME=...` on a COMPARE_COMPUTE line; pass it as `-Xslang -DNAME=...` ([re-run "also fails on master" failures on the GPU](../learnings/1792140798870-slang-re-run-also-fails-on-master-failures-on-the-.md)).

## Vulkan push-constant repros: a validation layer, a fresh render-test, and what reflection cannot tell the host

Consider a SlangPy module with a module-scope `[[vk::push_constant]]` block, dispatched on Vulkan (slangpy#1232, followed up as slang#13713 and slang-rhi#915, 2026-10-16). Reproducing it on the L40S needs three things the container does not give you by default.

**A validation layer.** Coworker containers have no Khronos validation manifest, so `spy.Device(enable_debug_layers=True)` prints nothing: the loader never finds the layer. The layer binary is present at `/usr/lib/chromium/libVkLayer_khronos_validation.so`. Write a manifest such as `/workspace/agent/tools/vklayer/VkLayer_khronos_validation.json` (`file_format_version` 1.2.0, `name` `VK_LAYER_KHRONOS_validation`, `library_path` set to that .so, `api_version` 1.3.250) and point the loader at its directory. Keep it under `/workspace/agent`, not `/tmp`: `/tmp` is wiped when the container restarts ([SlangPy against a local Slang commit](../learnings/1792536990284-running-slangpy-against-a-local-slang-commit-isola.md)). Two environment forms both worked. With `VK_LAYER_PATH=<dir> VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`, slang-test prints the layer output in a `debug layer = {` block. With `VK_ADD_LAYER_PATH=<dir> VK_LOADER_LAYERS_ENABLE='*validation'`, slang-rhi logs real VUIDs as `[rhi] driver: error` ([Vulkan validation layer in coworker containers](../learnings/1792172122995-vulkan-validation-layer-in-coworker-containers-sla.md), [Vulkan push-constant GPU repro](../learnings/1792167218740-vulkan-push-constant-gpu-repro-rebuild-render-test.md)).

The same layer gives slang-test render-test VUIDs, which is how slang#13824 (a read-only `Texture2D.Handle` bound as a storage image, VUID-VkWriteDescriptorSet-descriptorType-00339; the cause is on [descriptor-handle reflection](slang-language-core-descriptor-handle-capabilities-and-reflection.md)) was reproduced on the L40S. `/usr/share/vulkan/explicit_layer.d` holds only the INTEL_nullhw and MESA_overlay layers. A full manifest is `{"file_format_version":"1.2.0","layer":{"name":"VK_LAYER_KHRONOS_validation","type":"GLOBAL","library_path":"/usr/lib/chromium/libVkLayer_khronos_validation.so","api_version":"1.3.0","implementation_version":"1","description":"chromium VVL"}}`; both `api_version` 1.3.0 and 1.3.290 load. Then run `VK_ADD_LAYER_PATH=<dir> XDG_RUNTIME_DIR=/tmp ./build/Release/bin/slang-test -enable-debug-layers true <test>`, and `VK_LOADER_DEBUG=layer` confirms the layer loaded. VUIDs appear in a `debug layer = {` block, most fully under `-v` ([Khronos validation layer via chromium's .so](../learnings/1792613432297-khronos-vulkan-validation-layer-in-the-coworker-co.md), [write your own manifest](../learnings/1792617340264-vulkan-validation-layer-in-coworker-containers-chr.md), [validation layer manifest trick](../learnings/1792608693780-render-test-descriptorhandle-access-is-none-on-uin.md)). The flag differs between the two tools. slang-test's `-enable-debug-layers` takes a value (`tools/slang-test/options.cpp` ~647), so `-enable-debug-layers true` is correct there, and a bare flag directly before the test path swallows the path as its value. render-test's flag takes none, so a `true` after it fails with "unexpected positional arg"; slang-test passes the bare flag to render-test for you. Debug builds of slang-test enable the layers by default; Release builds do not. Two counting traps make VUID totals look larger than they are. A plain `grep -o 'VUID-…'` counts each error twice, because the "The Vulkan spec states…" line repeats the VUID, and slang-test's automatic retry of a failing test doubles the count again. So count with `grep -c '^error: .*VUID-'` and report the count per run. Use core validation only: GPU-AV (`VK_LAYER_ENABLES=VK_VALIDATION_FEATURE_ENABLE_GPU_ASSISTED_EXT`) adds a spurious VUID-vkCmdBuildAccelerationStructuresKHR-pInfos-12281 from render-test's own acceleration-structure build ([same](../learnings/1792617340264-vulkan-validation-layer-in-coworker-containers-chr.md)).

**A current render-test.** A render-test built before slang-rhi#848 aborts on push-constant tests with `Assertion failed: Unsupported binding type: 14` in `vk-shader-object.cpp`. Rebuild with `cmake --build --preset debug --target render-test slang-test` (the target is `render-test`, not `render-test-tool`). After that, `//TEST_INPUT:set push.a = {...}` binds a global `[[vk::push_constant]]` block by name ([Vulkan push-constant GPU repro](../learnings/1792167218740-vulkan-push-constant-gpu-repro-rebuild-render-test.md)).

**What works and what breaks** (SlangPy, Slang 2026.19, validation on):
- **Fine:** resource-only kernels, plain `uniform` globals, and `ConstantBuffer` globals next to the push constant. All give correct values with 0 VUIDs.
- **Broken:** kernels that also take entry-point uniforms fail VUID-VkPipelineLayoutCreateInfo-pPushConstantRanges-00292 and layout-10069, and return garbage. A global `ParameterBlock` fails VUID-...-layout-07988 when the push constant would be alone in set 0, and the ParameterBlock is shifted (slang#12349; the phantom-set mechanism is on [[wiki/concepts/slang-a-diagnostics-reflection-spec.md]]) ([module push-constant matrix](../learnings/1792172122995-vulkan-validation-layer-in-coworker-containers-sla.md)).

**Why the entry-point-uniform case cannot be fixed from reflection alone.** When a global push-constant block and entry-point uniforms are used together, reflection gives the global PUSH_CONSTANT_BUFFER index 0 and the entry-point parameters index 1. That index comes from one counter shared by the whole program and has no byte meaning: in SPIR-V each block starts at Offset 0. `IMetadata::isParameterLocationUsed(PUSH_CONSTANT_BUFFER, …)` returns used=false for every index, even for blocks the entry point uses (#5685). So a host cannot place the ranges correctly from reflection, and slang-rhi's offset-by-sum (`addAllPushConstantRangesRec`) puts the entry-point data at +16 ([what Slang reflection reports](../learnings/1792167218740-vulkan-push-constant-gpu-repro-rebuild-render-test.md)).

Descriptor bindings follow the same program-wide rule. The user guide (`docs/user-guide/02-conventional-features.md:872-873` on master 60a7c8c8; older notes cite 945-947; from docs PR #3459) says compute entry-point `uniform` parameters are "pushed" and "popped", so the next entry point reuses the same binding slots. The code does not do this. `slang-parameter-binding.cpp` gives every entry point its range from one program-wide pool (`visitEntryPoint` :3984, `completeBindingsForParameterImpl` :1612/:1802), and `removePerEntryPointParameterKinds` (:3334) resets only the varying, ShaderRecord, HitAttributes and existential kinds between entry points. A C++ harness that composes module + EP1 + EP2 measured this on v2026.5 and v2026.19: EP2's `getVarLayout()->getOffset(DescriptorTableSlot)` is 3 on Vulkan and 1 per register class on HLSL, and `isParameterLocationUsed` returns true only for the absolute location (raw index + EP offset). To see it, run `slangc file.slang -target spirv-asm` with no `-entry`: the second entry point's bindings follow the first one's. Compiling one entry point per `-entry` hides the problem. No option controls the overlap (#13203; proposals #13210/#13211) ([user guide push/pop claim is not implemented](../learnings/1792158083909-user-guide-s-compute-entry-point-uniform-push-pop-.md)). The behavior is unchanged on v2026.20: SPIR-V 0/1/2 then 3/4/5, HLSL b0/t0/u0 then b1/t1/u1, and the guide's own computeMain1/computeMain2 example gets b1/b2 in HLSL. `-reflection-json` hides the offset because it prints only the relative indices (0/1/2 for both entry points), so read `EntryPointReflection::getVarLayout()->getOffset(category)` through the API. Two repro tips: `SamplerState()` cannot be default-constructed (E39999), and TextureCube `Load` takes an `int4` ([#13203 still on v2026.20](../learnings/1792307527386-13203-entry-point-binding-growth-still-on-v2026-20.md)).

**Reflection-consumer traps in sgl.** sgl's `TypeReflection.ParameterCategory` enum used to stop at 19, but a ParameterBlock on Vulkan reports 20 (`sub_element_register_space`). Binding `parameter_category` without extending the enum makes nanobind raise `ValueError` for every ParameterBlock. Use `categories` (`getCategoryCount`/`getCategoryByIndex`) instead: a push-constant struct that holds a resource reports `mixed` from `parameter_category`, so that check alone misses it ([sgl ParameterCategory](../learnings/1792172122995-vulkan-validation-layer-in-coworker-containers-sla.md)). And `slangc -reflection-json /dev/null` fails with E00004; write the JSON to a real file (the special-file gate is on [[wiki/concepts/slang-tooling-f0909b0-slangc-cli-behavior.md]]) ([Vulkan push-constant GPU repro](../learnings/1792167218740-vulkan-push-constant-gpu-repro-rebuild-render-test.md)).
