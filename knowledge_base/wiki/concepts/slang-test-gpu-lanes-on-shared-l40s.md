# slang-test GPU lanes on the shared L40S: run suites serially, orphaned test-servers, "ignored" that is contention, and what the GPU confirms

Every coworker container shares one NVIDIA L40S (46 GB). Since passthrough returned on 2026-10-16 (after the 09-28→10-16 outage), most false GPU failures have one cause: two GPU jobs, or other tenants, on one device at once. This page covers how those failures look and how to tell them from a regression, what the GPU confirms, how to get a Vulkan validation layer, and how to set up a push-constant repro. GPU presence is on [Container resources](agent-b-host-facts-and-critique-gate.md); WGSL through Dawn is on [Running WGSL on the real GPU](slang-backends-wgsl-on-gpu-execution.md); general false greens are on [slang-test False Greens](slang-test-false-greens-and-verification-traps.md).

## TL;DR

- **Run GPU slang-test jobs one at a time on the L40S.** Two concurrent `-vk`/`-cuda` suites produce hundreds of spurious failures (`CUDA_ERROR_LAUNCH_FAILED`, `waitForResult` retries, dead dispatch connections). Rerun differing files serially before calling anything a regression.
- **Never report a high-`-server-count` full-suite failure count as a regression.** One suite oversubscribes the shared GPU by itself (785 spurious failures at 16 servers, 397 at 48). Use about 4–8 servers, re-run the failed files at 2–4, then baseline the survivors on a build with only your fix reverted.
- **A lane that says `ignored` while a GPU is present can be contention, not a missing device.** Concurrent runs wedge in D state (`wchan os_acquire_rwlock_read`); check `ps -o stat,wchan` first. Other tenants filling the VRAM turn CUDA rows `ignored` ("Unable to create renderer [CUDA]" under `-v`), so trust CUDA coverage only after `nvidia-smi --query-gpu=memory.used,memory.total` shows headroom; `--query-compute-apps` lists only this container's PIDs.
- **If `(vk)` rows suddenly fail with empty output (`result code = 1`), check VRAM before the code.** An orphaned background `slang-test` and its servers can hold ~44 of 46 GB. Kill only your own parent `slang-test` (the servers' `-parent-pid` names it) and its servers, never another session's.
- **Keep CUDA dispatches small on the shared GPU**: 256 groups × 1024 threads failed at launch with `out of memory` while other tenants held 42/46 GB.
- **groupshared write→read races are deterministic on the L40S** (vk and cuda). A plain 64-thread COMPARE_COMPUTE catches a missing workgroup barrier.
- **Re-run every "also fails on master" note from the no-GPU window on the GPU.** `gfx-smoke.slang` passes now; the three `cooperative-matrix/fp8-cuda*` failures reproduce (`CUDA_ERROR_INVALID_PTX` on this driver and CUDA 12.6: environment baseline). The suite grows from ~8k to ~11k tests with the GPU, so attribute a new failure only after re-running it on a detached master worktree build (~20 min), which doubles as the negative control.
- **render-test rejects a bare `-DNAME=...` on a COMPARE_COMPUTE line**; pass `-Xslang -DNAME=...`.
- **Run a scratch GPU test from outside the checkout with a relative `-test-dir` and filter** (an absolute filter runs nothing). A `passed (vk)` line hides the values; a probe copy with an unmatchable CHECK exposes them in `.actual.txt`.
- **Classify a CUDA timeout as a kernel hang only if a `launched` marker printed.** On the busy GPU about half of runs hung in context creation; use ≥40 s timeouts and ≥8 runs per case.
- **The container has no Vulkan validation manifest, so `enable_debug_layers=True` prints nothing.** Write one pointing at `/usr/lib/chromium/libVkLayer_khronos_validation.so` under `/workspace/agent` (`/tmp` is wiped on restart) and set `VK_ADD_LAYER_PATH=<dir>`. slang-test's `-enable-debug-layers` takes a value (`true`); render-test's takes none. Debug builds enable layers by default; Release builds do not.
- **A green `-vk` run on the NVIDIA driver is not evidence of a correct binding or valid SPIR-V** (it accepted a wrong-type descriptor write, slang-rhi#959). Rerun under the Khronos layer (chromium copy or the Debian 1.3.239 `.deb`) before adding a GPU test or claiming a runtime fix. A teardown core dump with a written `-o` file is not a failure.
- **Count VUIDs with `grep -c '^error: .*VUID-'`, per run** (a plain grep counts each twice, slang-test's retry doubles it again). Use core validation only: GPU-AV adds a spurious acceleration-structure VUID from render-test itself.
- **Rebuild `render-test` before a push-constant repro**: a binary from before slang-rhi#848 aborts with `Unsupported binding type: 14`.
- **Reflection cannot place push constants for a global push-constant block plus entry-point uniforms**: the PUSH_CONSTANT_BUFFER index is a program-wide counter with no byte meaning, and `isParameterLocationUsed` says every index is unused (#5685). Entry-point uniform bindings also come from one program-wide pool; the guide's push/pop claim is not implemented (#13203).

## Concurrency on one GPU: the failure shapes

Each shape cleared when the same tests ran serially or at a low server count:

| Setup | Symptom | Serial / low-count result |
|---|---|---|
| Two `-server-count 16` suites at once (head + base) | `cuCtxSynchronize CUDA_ERROR_LAUNCH_FAILED` / "CUDA call failed" (slang-rhi `cuda-command.cpp:940`) until slang-test aborted; cooperative-matrix tests among the trips | barrier/groupshared subset 68/68 ([Don't run two GPU slang-test suites concurrently on one L40S](../learnings/1792140794509-don-t-run-two-gpu-slang-test-suites-concurrently-o.md)) |
| Two COMPARE_COMPUTE `-vk`/`-cuda` invocations at once | both in D state for minutes on the driver lock; one cuda lane `ignored`, reading like a missing device | vk+cuda 2/2 in ~100 s ([Run GPU slang-test jobs serially](../learnings/1792140793972-run-gpu-slang-test-jobs-serially-concurrent-vk-cud.md)) |
| Two `-server-count 24` suites in parallel | ~200 spurious file-level CUDA/VK failures per side | all cleared ([Slang corpus A/B emit-diff](../learnings/1792102021857-slang-corpus-a-b-emit-diff-control-for-bindir-path.md)) |
| One `-server-count 16` run with GPU rows, under contention | ~100 cuda/vk "test server did not answer in waitForResult" retries | ([dawn.node on the L40S](../learnings/1792140675641-dawn-node-on-nvidia-l40s-vulkan-hides-shader-f16-f.md)) |
| Two full suites at once (16 + 12 servers, 2026-10-28) | 7 "test-server dispatch failure(s) -- a connection died mid-run", 16 spurious cuda FAILs | 76/76 on rerun ([git checkout <rev> -- <file> stages the file (concurrent-suite rider)](../learnings/1793218043049-git-checkout-rev-file-stages-the-file-so-a-revert-.md)) |

**One full suite oversubscribes the GPU on its own.** A debug-build `-server-count 16` suite produced 785 GPU-runtime failures (CUDA `out of memory`, `CUDA_ERROR_LAUNCH_FAILED`, some Vulkan rows); re-running only the failed files at `-server-count 2` passed 2223/2226. The three survivors, baselined with only the fix reverted (base 92ef2caae), were `tests/cooperative-matrix/fp8-cuda{,-e5m2,-half-acc}.slang`, which fail in the PTX JIT with `CUDA_ERROR_INVALID_PTX`; the change under test (the slang-13260 witness gate) caused no regression ([a 16-server full suite oversubscribes the L40S](../learnings/1792166018117-slang-full-suite-at-16-test-servers-oversubscribes.md)). A Release suite at `-server-count 48`, with other coworkers holding ~15 GB, gave 397 FAILED vk/cuda tests with `result code = 1` and empty output; at `-server-count 4` the same files passed 393, the rest being fp8-cuda. Extract the failed set with `grep '^FAILED test' log | sed -E "s/^FAILED test: '([^ ']+).*/\1/" | sed -E 's/\.slang\.[0-9]+$/.slang/' | sort -u` (plus `gfx-unit-test-tool/...` names). Do not rebuild while a background suite uses the same `build/`, and stop background jobs with TaskStop: `pkill -f <worktree path>` inside a Bash call can match the calling shell (exit 144) ([48-server suite on the shared L40S](../learnings/1792691640286-slang-test-full-suite-at-high-server-count-on-the-.md)).

**The A/B rule:** run the two suites one after the other (or both on a targeted subset), at about 4–8 servers; serially rerun every differing file at 2–4 servers, then baseline survivors on a build with only your fix reverted.

## Orphaned test-servers and other tenants hold the VRAM

A background `-server-count 16` slang-test that hit the Bash timeout kept running, its test-servers holding ~44 of 46 GB; a later run then failed 22 previously-passing `(vk)` subgroup rows with `result code = 1` and empty output. List holders with `nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv`, kill only your own parent `slang-test` (named by `-parent-pid` on its servers) and its servers, then re-run in the foreground ([Orphaned slang-test test-servers hog GPU VRAM](../learnings/1792140853317-orphaned-slang-test-test-servers-hog-gpu-vram-and-.md)). Tenancy also limits large CUDA launches: a 256 × 1024 dispatch failed with `cblCudaReconfigureLocalMemory ... out of memory` while other sessions held 42/46 GB ([groupshared races are deterministic on the L40S](../learnings/1792138991574-groupshared-write-read-races-are-deterministic-on-.md)).

Other containers' memory is the quieter failure, because it turns CUDA rows `ignored` rather than red. On 2026-10-22 `syn (cuda)` rows that passed an hour earlier came back ignored while other containers held 44/46 GB (`-v`: "Unable to create renderer [CUDA]"); they passed again ~15 minutes later. `nvidia-smi --query-compute-apps` cannot show other tenants, so read `nvidia-smi --query-gpu=memory.used,memory.total` before trusting CUDA coverage. A slang-test also went into D state then; don't wait on one in the foreground ([CUDA rows flip to ignored when the shared L40S is full](../learnings/1792697343358-slang-test-cuda-rows-flip-to-ignored-when-the-shar.md)).

## What the GPU confirms that a GPU-less container could not

**Missing-barrier races reproduce every time.** For slang#13631 (`workgroupUniformLoad` with no barrier off WGSL), "thread 0 writes groupshared, every thread reads with no barrier" read the stale value on every thread but the writer, every run (Vulkan 261888/262144, CUDA 32736/32768 mismatches, including the writer's own warp), with or without busy-work delay. A plain 64-thread COMPARE_COMPUTE (`-vk`/`-cuda`, default 1×1×1 dispatch) is a reliable regression test for a missing workgroup barrier ([groupshared write→read races are deterministic on the L40S](../learnings/1792138991574-groupshared-write-read-races-are-deterministic-on-.md)). On #13659 the functional test (one thread writes, every thread calls `workgroupUniformLoad`, then that thread overwrites) failed on master under `-vk` and `-cuda` 3/3 and passed with the fix [Don't run two GPU slang-test suites concurrently](../learnings/1792140794509-don-t-run-two-gpu-slang-test-suites-concurrently-o.md).

**"Pre-existing, also fails on master" from the outage window is an environment artifact until re-run.** `tests/cpu-program/gfx-smoke.slang` failed then with `Failed to load DLL "gfx"` on master and PR builds alike and passes on the L40S; the three `fp8-cuda*` failures do reproduce with the master binary (`CUDA_ERROR_INVALID_PTX` on this driver and CUDA 12.6), so they are environment baseline ([16-server suite, revert baseline](../learnings/1792166018117-slang-full-suite-at-16-test-servers-oversubscribes.md)). When a container gains the GPU the suite grows from ~8k to ~11k tests, so a new failure can come from the environment rather than the PR: build a detached master worktree and re-run only the failing tests on it (~20 minutes), which is also the negative control for the PR's own tests. Read PR metadata with slang-mcp `github_get_pull_request` or `git fetch` + `git show`; the critique-gate hook blocks `gh api .../pulls/<n>` ([critique delivery gates](agent-routing-f0909b0-critique-delivery-gates.md)) ([check new full-suite failures on a master build](../learnings/1792662201433-check-new-full-suite-failures-on-a-master-build-wh.md)). The GPU also confirms suspected codegen bugs: GLSL `uint64_t(uvec2)` keeps only the low word, so a `bit_cast<uint4>` of a struct holding a `DescriptorHandle` under `-emit-spirv-via-glsl` returns a 0 high word on Vulkan; direct SPIR-V is correct (shader-slang/slang#13695). render-test rejects a bare `-DNAME=...` on a COMPARE_COMPUTE line; pass `-Xslang -DNAME=...` ([re-run "also fails on master" failures on the GPU](../learnings/1792140798870-slang-re-run-also-fails-on-master-failures-on-the-.md)).

## Getting a Khronos validation layer, and why a green NVIDIA run needs one

**The NVIDIA driver accepts some invalid API usage and SPIR-V and still produces the expected result.** On slang#14013 / PR #14023 a `-vk` repro read the expected 1234 in three runs after the Slang fix. Under the Khronos layer the same run showed slang-rhi's `bindAsRoot` writing a UNIFORM_BUFFER into a STORAGE_BUFFER binding (`VUID-VkWriteDescriptorSet-descriptorType-00319`) and never writing the real UBO (`VUID-vkCmdDispatch-None-02699`, `-08114` in a newer layer), and the validated run read 0 (slang-rhi#959; mechanism on [[wiki/concepts/slang-rhi-shader-object-binding-and-root-layout.md]]). Never add a GPU regression test, or claim a binding or runtime fix, from an unvalidated NVIDIA pass [NVIDIA Vulkan drivers tolerate mismatched-type descriptor writes, so a runtime PASS can hide a real slang-rhi binding bug. Run the Khronos validation layer from the Debian .deb (no install needed)](../learnings/1793285936432-nvidia-vulkan-drivers-tolerate-mismatched-type-des.md), [A Vulkan runtime pass on NVIDIA without validation layers is not evidence of a binding fix](../learnings/1793289426474-a-vulkan-runtime-pass-on-nvidia-without-validation.md), [A green Vulkan render-test run can be undefined behavior; rerun under VVL before trusting it](../learnings/1793294735619-a-green-vulkan-render-test-run-can-be-undefined-be.md). The same driver runs a module spirv-val rejects (an `OpConvertPtrToU` with a signed result type; see [[wiki/concepts/slang-backends-spirv-validation-testing-and-environment.md]]).

**The container has no Khronos manifest** (`/usr/share/vulkan/explicit_layer.d` holds only INTEL_nullhw and MESA_overlay), so `spy.Device(enable_debug_layers=True)` prints nothing. Two sources need no admin approval:

- **Chromium's copy.** The binary is `/usr/lib/chromium/libVkLayer_khronos_validation.so`. Write a manifest such as `/workspace/agent/tools/vklayer/VkLayer_khronos_validation.json` — under `/workspace/agent`, since `/tmp` is wiped on restart ([SlangPy against a local Slang commit](../learnings/1792536990284-running-slangpy-against-a-local-slang-commit-isola.md)) — e.g. `{"file_format_version":"1.2.0","layer":{"name":"VK_LAYER_KHRONOS_validation","type":"GLOBAL","library_path":"/usr/lib/chromium/libVkLayer_khronos_validation.so","api_version":"1.3.0","implementation_version":"1","description":"chromium VVL"}}`; `api_version` 1.3.0, 1.3.239, 1.3.250 and 1.3.290 all load. Expect a segfault at teardown with this layer, on base and head alike; it does not matter [A green Vulkan render-test run can be undefined behavior; rerun under VVL before trusting it](../learnings/1793294735619-a-green-vulkan-render-test-run-can-be-undefined-be.md).
- **The Debian package.** `curl -LO https://deb.debian.org/debian/pool/main/v/vulkan-validationlayers/vulkan-validationlayers_1.3.239.0-2_amd64.deb`, `dpkg-deb -x <deb> <root>`, copy `usr/share/vulkan/explicit_layer.d/VkLayer_khronos_validation.json` into a layer directory and set `library_path` to the absolute `.so`. LunarG's SDK URL timed out from the container. This 1.3.239 layer uses older VUID names (`layout-00703` where newer layers say `layout-07988`), and its `UNASSIGNED-CoreValidation-Shader-InconsistentSpirv … Invalid source language operand: 11` only means it does not know Slang's SourceLanguage — noise [NVIDIA Vulkan drivers tolerate mismatched-type descriptor writes, so a runtime PASS can hide a real slang-rhi binding bug. Run the Khronos validation layer from the Debian .deb (no install needed)](../learnings/1793285936432-nvidia-vulkan-drivers-tolerate-mismatched-type-des.md), [A Vulkan runtime pass on NVIDIA without validation layers is not evidence of a binding fix](../learnings/1793289426474-a-vulkan-runtime-pass-on-nvidia-without-validation.md).

**Loading it.** Two environment forms work: `VK_LAYER_PATH=<dir> VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation` (slang-test prints layer output in a `debug layer = {` block, most fully under `-v`), or `VK_ADD_LAYER_PATH=<dir>` with `VK_LOADER_LAYERS_ENABLE='*validation'` (slang-rhi logs VUIDs as `[rhi] driver: error`) ([Vulkan validation layer in coworker containers](../learnings/1792172122995-vulkan-validation-layer-in-coworker-containers-sla.md), [Vulkan push-constant GPU repro](../learnings/1792167218740-vulkan-push-constant-gpu-repro-rebuild-render-test.md)). For slang-test render-test VUIDs run `VK_ADD_LAYER_PATH=<dir> XDG_RUNTIME_DIR=/tmp ./build/Release/bin/slang-test -enable-debug-layers true <test>`; `VK_LOADER_DEBUG=layer` confirms the load. That is how slang#13824 (a read-only `Texture2D.Handle` bound as a storage image, VUID-VkWriteDescriptorSet-descriptorType-00339; cause on [descriptor-handle reflection](slang-language-core-descriptor-handle-capabilities-and-reflection.md)) was reproduced ([Khronos validation layer via chromium's .so](../learnings/1792613432297-khronos-vulkan-validation-layer-in-the-coworker-co.md), [write your own manifest](../learnings/1792617340264-vulkan-validation-layer-in-coworker-containers-chr.md), [validation layer manifest trick](../learnings/1792608693780-render-test-descriptorhandle-access-is-none-on-uin.md)). slang-test's `-enable-debug-layers` takes a value (`tools/slang-test/options.cpp` ~647; a bare flag before the test path swallows the path); render-test's takes none ("unexpected positional arg"), and slang-test passes it the bare flag. Debug builds of slang-test enable the layers by default; Release builds do not. **Counting:** a plain `grep -o 'VUID-…'` counts each error twice (the "The Vulkan spec states…" line repeats it) and slang-test's automatic retry doubles it again, so count `grep -c '^error: .*VUID-'` per run. Use core validation only: GPU-AV (`VK_LAYER_ENABLES=VK_VALIDATION_FEATURE_ENABLE_GPU_ASSISTED_EXT`) adds a spurious VUID-vkCmdBuildAccelerationStructuresKHR-pInfos-12281 from render-test's own acceleration-structure build ([same](../learnings/1792617340264-vulkan-validation-layer-in-coworker-containers-chr.md)).

With validation errors, render-test fails the test [A Vulkan runtime pass on NVIDIA without validation layers is not evidence of a binding fix](../learnings/1793289426474-a-vulkan-runtime-pass-on-nvidia-without-validation.md). render-test is a module that slang-test loads (`build/Release/bin` has no render-test binary), so it cannot be run directly [A green Vulkan render-test run can be undefined behavior; rerun under VVL before trusting it](../learnings/1793294735619-a-green-vulkan-render-test-run-can-be-undefined-be.md). Even without a layer, `-vk` runs can dump core at teardown with a correct result (#14061, with a passing fp32 control), so check whether the `-o` file was written before reading a crash as a failure [Slang SPIR-V fp64 math: which GLSL.std.450 ops are invalid on double, and the type-gated diagnostic pattern](../learnings/1793312363687-slang-spir-v-fp64-math-which-glsl-std-450-ops-are-.md).

## Vulkan push-constant repros: a fresh render-test and what reflection cannot tell the host

Consider a SlangPy module with a module-scope `[[vk::push_constant]]` block on Vulkan (slangpy#1232; slang#13713, slang-rhi#915). Besides the validation layer, the repro needs **a current render-test**: one built before slang-rhi#848 aborts with `Assertion failed: Unsupported binding type: 14` in `vk-shader-object.cpp`. Rebuild with `cmake --build --preset debug --target render-test slang-test` (the target is `render-test`, not `render-test-tool`); then `//TEST_INPUT:set push.a = {...}` binds a global `[[vk::push_constant]]` block by name ([Vulkan push-constant GPU repro](../learnings/1792167218740-vulkan-push-constant-gpu-repro-rebuild-render-test.md)).

**What works and what breaks** (SlangPy, Slang 2026.19, validation on): resource-only kernels, plain `uniform` globals, and `ConstantBuffer` globals next to the push constant give correct values with 0 VUIDs. Kernels that also take entry-point uniforms fail VUID-VkPipelineLayoutCreateInfo-pPushConstantRanges-00292 and layout-10069 and return garbage; a global `ParameterBlock` fails VUID-...-layout-07988 when the push constant would be alone in set 0, and the ParameterBlock is shifted (slang#12349; phantom-set mechanism on [[wiki/concepts/slang-a-diagnostics-reflection-spec.md]]) ([module push-constant matrix](../learnings/1792172122995-vulkan-validation-layer-in-coworker-containers-sla.md)).

**Why the entry-point-uniform case cannot be fixed from reflection alone.** With a global push-constant block plus entry-point uniforms, reflection gives the global PUSH_CONSTANT_BUFFER index 0 and the entry-point parameters index 1. That index is a program-wide counter with no byte meaning (each SPIR-V block starts at Offset 0), and `IMetadata::isParameterLocationUsed(PUSH_CONSTANT_BUFFER, …)` returns used=false for every index, even blocks the entry point uses (#5685). A host therefore cannot place the ranges, and slang-rhi's offset-by-sum (`addAllPushConstantRangesRec`) puts the entry-point data at +16 ([what Slang reflection reports](../learnings/1792167218740-vulkan-push-constant-gpu-repro-rebuild-render-test.md)).

**Descriptor bindings follow the same program-wide rule.** The user guide (`docs/user-guide/02-conventional-features.md:872-873` on master 60a7c8c8; older notes cite 945-947; from docs PR #3459) says compute entry-point `uniform` parameters are "pushed" and "popped" so the next entry point reuses the same slots. The code does not do this: `slang-parameter-binding.cpp` gives every entry point its range from one program-wide pool (`visitEntryPoint` :3984, `completeBindingsForParameterImpl` :1612/:1802), and `removePerEntryPointParameterKinds` (:3334) resets only varying, ShaderRecord, HitAttributes and existential kinds. A C++ harness composing module + EP1 + EP2 measured EP2's `getVarLayout()->getOffset(DescriptorTableSlot)` as 3 on Vulkan and 1 per register class on HLSL (v2026.5, v2026.19), with `isParameterLocationUsed` true only for the absolute location. `slangc -target spirv-asm` with no `-entry` shows it; one `-entry` per compile hides it. No option controls the overlap (#13203; proposals #13210/#13211) ([user guide push/pop claim is not implemented](../learnings/1792158083909-user-guide-s-compute-entry-point-uniform-push-pop-.md)). Unchanged on v2026.20 (SPIR-V 0/1/2 then 3/4/5; HLSL b0/t0/u0 then b1/t1/u1; the guide's own example gets b1/b2). `-reflection-json` prints only relative indices (0/1/2 for both), so read `EntryPointReflection::getVarLayout()->getOffset(category)` through the API. Repro tips: `SamplerState()` cannot be default-constructed (E39999), and TextureCube `Load` takes an `int4` ([#13203 still on v2026.20](../learnings/1792307527386-13203-entry-point-binding-growth-still-on-v2026-20.md)).

**Reflection-consumer traps in sgl.** sgl's `TypeReflection.ParameterCategory` enum stopped at 19, but a Vulkan ParameterBlock reports 20 (`sub_element_register_space`), so nanobind raised `ValueError` for every ParameterBlock. Use `categories` (`getCategoryCount`/`getCategoryByIndex`): a push-constant struct holding a resource reports `mixed` from `parameter_category`, which that check alone misses ([sgl ParameterCategory](../learnings/1792172122995-vulkan-validation-layer-in-coworker-containers-sla.md)). `slangc -reflection-json /dev/null` fails with E00004; write to a real file (special-file gate on [[wiki/concepts/slang-tooling-f0909b0-slangc-cli-behavior.md]]) ([Vulkan push-constant GPU repro](../learnings/1792167218740-vulkan-push-constant-gpu-repro-rebuild-render-test.md)).

## Running a throwaway GPU test, proving what it produced, and telling a hang from a slow context

**A scratch COMPARE_COMPUTE file can run on the GPU from outside the read-only checkout.** Put it in e.g. `/tmp/x/gputests/foo.slang`, `cd /tmp/x`, and run `/workspace/agent/slang/build/Release/bin/slang-test -bindir /workspace/agent/slang/build/Release/bin/ -test-dir gputests/ -v gputests/`: a relative `-test-dir` plus filter works, an absolute filter path gives "no tests run", and `.actual.txt` lands next to the test. render-test runs via `slang-test -bindir <bin> render-test <file> -vk -compute -shaderobj -output-using-type -o out.txt`. `vulkaninfo --summary` hangs while slang-test Vulkan works; the device probe takes ~1 min, 2 files × (vk + cuda) ~3.5 min ([GPU tests from outside the slang tree via -test-dir](../learnings/1793278419722-run-slang-test-gpu-vk-cuda-tests-from-outside-the-.md)). `-cuda` rows and nvrtc need `PATH=/usr/local/cuda/bin:$PATH cmake --preset default -DSLANG_ENABLE_CUDA=ON`.

**A `passed test: '…(cuda)'` / `'…(vk)'` line does not show the values the GPU produced.** Copy the test to `tests/<dir>/zz-probe.slang` with a CHECK that cannot match, run slang-test, read each API's `<file>.actual.txt`, then delete the probe and its outputs. That showed identical CUDA and Vulkan `Gather*` values on a `content=gradient` 4x4 texture ([proving a slang-test GPU run executed](../learnings/1793323215178-slang-worktree-submodules-proving-a-slang-test-gpu.md)).

**On the shared L40S a "hang" can be CUDA context creation, not the kernel.** Under `timeout` at a busy time (2026-10-29), about half the runs of a native nvcc deadlock harness hung before launch, inside context creation (first `cudaMalloc` / `cudaMemcpyToSymbol`), which looks exactly like a deadlock and can make a correct fix appear to hang. Print unbuffered progress to stderr (`start`, `pre-launch`, `launched`, `sync: <err>`), count a timeout as a kernel hang only if `launched` printed, and use ≥40 s timeouts with ≥8 runs per case. With that, master asym2/brk2 (#14016 exit-ballot deadlock) hung 8/8 in the kernel and PR #14025 passed 8/8, 0 context hangs ([separate context-creation hangs from kernel hangs](../learnings/1793299898427-gpu-hang-tests-on-the-shared-l40s-separate-context.md)).
