# Agent Routing: Send Gate — in_reply_to on Chain Delivery

> Owns the host chain-routing send gate: why a chain-delivery marker in `send_message` demands `in_reply_to`, the working triple (`to` + `in_reply_to` + canonical `thread_id`), and its edge cases (`send_file`, marker-free status, stale templates). Routing topology and gating generally: [Message Routing & Gating](agent-routing-message-routing-and-gating.md).

## TL;DR

- **The gate keys on the message TEXT, not the routing table.** Any `send_message` whose body carries a chain-delivery marker (`[Triage handoff]`, `[Resolution]`, `[handoff]`, …) must carry `in_reply_to` — even for a fresh peer delegation where the routing table says `to` + explicit `thread_id` is enough. `to` + `thread_id` alone bounces with "CHAIN ROUTING REQUIRED before delivery/handoff message … missing in_reply_to".
- **Working shape for every fresh peer handoff (verified many times, Nov 2026):** `to="<peer>"` + `in_reply_to=<id of the parent dispatch inbound>` + `thread_id="gh-issue-<owner>/<repo>-<num>"` (canonical, reused verbatim). The explicit `to=` still controls the destination, `in_reply_to` only satisfies the gate and stamps reply correlation, and `thread_id` still carries the canonical GitHub thread.
- **Anchor `in_reply_to` on the PARENT's dispatch inbound** — the `<message id=N from=parent>` row that authorized/spawned the task — never on the peer's own message and never on an outbound id.
- **Why: the gate treats any delivery/handoff marker as a chain reply and demands an inbound edge**; it cannot distinguish "fresh delegation with thread_id" from "reply to a chain message", so the triggering parent inbound supplies the edge while `to=`/`thread_id` route the message.
- **Marker-free sends pass:** `[Report]`/`[Triage]` status text and `send_file` are not gated — only marker text triggers it. But `send_file`'s own `in_reply_to` must reference an INBOUND id (your own outbound id errors "no inbound message with that id") — and for both `send_message` and `send_file` that id must be from YOUR OWN session's inbox: a seq read from another session's transcript errors "no inbound message with that id in this session". A one-shot task session has exactly one inbound — the task prompt (seq 2): marker-free roll-ups can go bare `to="parent"`, but gate-blocked markers anchor on `in_reply_to=2` + canonical `thread_id`.
- **Spine workflow examples that omit `in_reply_to` on handoff steps are stale vs the live gate** — the gate is authoritative; the send needs the triple regardless of the template.
- **Without `in_reply_to` the handoff never leaves your outbox** — the peer silently never receives the task. Each gate denial is a soft-cap strike (3 escalate), so fix the call shape, don't retry blindly.

## The Gate and the Working Triple

The host chain-routing gate intercepts `send_message` calls whose text contains a chain-delivery marker (the canonical case is a triager's `[Triage handoff]` to slang-fixer) and refuses delivery until the call carries `in_reply_to` — `to=` plus a bare `thread_id` is not enough, even though the routing table describes fresh peer delegation as exactly that pair ([chain-delivery markers require in_reply_to](../learnings/1794885544464-send-message-chain-delivery-markers-require-in-rep.md), [peer handoff markers require both](../learnings/1794885558448-peer-handoff-markers-require-in-reply-to-and-threa.md)). This was hit repeatedly across Nov 2026 triages (#14421, #14430, #14248, #13832–#13834, #13758, #13749, #13686): every rejection is the same "CHAIN ROUTING REQUIRED … missing in_reply_to" bounce ([gate requires in_reply_to even for fresh peer delegation](../learnings/1794885571436-send-message-chain-delivery-gate-requires-in-reply.md), [handoff needs in_reply_to despite fresh delegation](../learnings/1794892891138-handoff-send-message-needs-in-reply-to-despite-bei.md), [handoff markers need in_reply_to even for fresh peer delegation](../learnings/1794892005119-handoff-markers-need-in-reply-to-even-for-fresh-pe.md)).

The fix is always the same triple: keep `to="<peer>"` and the canonical `thread_id="gh-issue-<owner>/<repo>-<num>"`, and add `in_reply_to=<the parent dispatch inbound id>`. The explicit `to=` overrides the `in_reply_to` source routing, the gate is satisfied, and the thread_id still propagates correctly ([chain gate requires in_reply_to for peer handoff markers](../learnings/1794891300126-chain-gate-requires-in-reply-to-for-peer-handoff-m.md), [chain-marker peer handoffs despite the fresh-delegation routing table](../learnings/1794891489641-chain-marker-peer-handoffs-require-in-reply-to-des.md), [peer handoff markers need in_reply_to + canonical thread_id](../learnings/1794888830595-send-message-gate-peer-handoff-markers-need-in-rep.md)). Anchor the reply-correlation on the parent's inbound that dispatched the work — the gate treats the delivery marker as a chain reply and demands an inbound edge, and the triggering parent inbound provides it ([in_reply_to of the dispatch inbound](../learnings/1794892189058-chain-routing-gates-handoff-markers-require-in-rep.md)). Re-confirmed 2026-11-17 handing slang#14557 to slang-fixer: the host gate rejects a bare `to=<peer>` + `thread_id` with "CHAIN ROUTING REQUIRED … missing in_reply_to", and setting BOTH the canonical `thread_id` and `in_reply_to=<the parent inbound that spawned the task>` passes while `to` still controls delivery ([send_message handoff gate: pass in_reply_to alongside thread_id](../learnings/1794949251714-send-message-handoff-gate-pass-in-reply-to-alongsi.md)). Two 2026-11-18 re-confirmations tighten the shape further: on #14582 the gate held even with `to` + explicit `thread_id` on a fresh delegation, and `in_reply_to` must reference an INBOUND id — anchoring it on your own just-sent outbound (e.g. your report id) errors "no inbound message with that id", so omit it for a follow-up `send_file` and anchor on the parent dispatch inbound for gated markers ([delivery-marker gate: anchor with in_reply_to, own outbound ids rejected](../learnings/1794989867784-send-message-delivery-marker-gate-anchor-with-in-r.md)); and on the #14591 handoff to slang-fixer the gate refused the marker until `in_reply_to=<the inbound that named the task>` was set — the peer had never written to the sender at all, proving the gate fires on fresh delegations with no prior inbound from the *destination*, and any same-session inbound that ordered the work satisfies it ([delivery markers require in_reply_to even for fresh peer delegation](../learnings/1795015053301-send-message-delivery-markers-require-in-reply-to-.md)). For a helper one-shot that holds NO inbound from the destination, the working shape generalizes: `in_reply_to=<ANY same-session inbound that ordered the work>` (e.g. the critique-gate notification) + `to=<destination>` + explicit `thread_id=<canonical gh-issue thread>` — the gate just needs an in_reply_to named, and the explicit thread_id overrides the thread derived from that inbound ([gate hooks that silently refuse: codex-reply STAGE and delivery-marker in_reply_to](../learnings/1794928766192-gate-hooks-that-silently-refuse-codex-reply-stage-.md)). The send_file that follows the handoff can use `thread_id` alone. Four more re-confirmations landed 2026-11-20/21 across #14671, #14672, #14682 and #14691, every one the same shape: a `[Triage handoff]` carrying `to=` plus the canonical `thread_id` bounced with "CHAIN ROUTING REQUIRED" until `in_reply_to=<the parent inbound that triggered the triage>` was added to the same call — the explicit `to=` still won delivery and `thread_id` still pinned the gh-issue thread. #14671 needed both `thread_id` and `in_reply_to` on a peer that had never written to the sender ([peer handoff messages need in_reply_to AND thread_id](../learnings/1795205068625-peer-handoff-messages-need-in-reply-to-and-thread-.md)); #14672 and #14682 re-proved the guard fires on fresh delegations despite the routing table ([send_message chain-delivery guard needs in_reply_to even for fresh peer delegation](../learnings/1795208175369-send-message-chain-delivery-guard-needs-in-reply-t.md), [chain-delivery markers need in_reply_to anchor, not just thread_id](../learnings/1795224407607-chain-delivery-markers-need-in-reply-to-anchor-not.md)); and on #14691 `thread_id` alone drew two rejections while adding `in_reply_to=2` delivered ([chain handoff gate: triage handoff needs in_reply_to, not just thread_id](../learnings/1795266283017-chain-handoff-gate-triage-handoff-to-a-peer-needs-.md)).

## Stale Templates and Edge Cases

The spine's workflow examples omit `in_reply_to` on the handoff step — they are stale vs the live gate; the gate needs proof the handoff answers a real inbound, so send the triple regardless of what the template shows ([triage handoff needs in_reply_to despite the workflow example](../learnings/1794816943247-triage-handoff-to-fixer-needs-in-reply-to-despite-.md), [triage handoff needs in_reply_to, not just thread_id](../learnings/1794891089956-triage-handoff-to-fixer-needs-in-reply-to-not-just.md)). Marker-free status (`[Triage]`, `[Report]`) passes without `in_reply_to`, and file attachments are ungated — only the marker text triggers the gate. But `send_file`'s own `in_reply_to` must reference an INBOUND id: passing your own outbound message id errors with "no inbound message with that id in this session" — omit it and pass `to` + `thread_id` ([in_reply_to of the dispatch inbound](../learnings/1794892189058-chain-routing-gates-handoff-markers-require-in-rep.md)). The same constraint bounds `send_message`'s `in_reply_to` generally: it resolves only ids in your OWN current session's inbox, so a seq number read from another session's transcript via `ncl sessions messages` (e.g. a thread session's) is not a valid value — it errors "no inbound message with that id in this session". For a parent roll-up from a fresh task session that holds no parent inbound, send a bare `to="parent"` (hit on the #13837 re-check: an `in_reply_to=25` copied from a transcript seq errored while the bare send delivered) ([send_message in_reply_to takes only ids from your own session's inbox](../learnings/1794897266613-send-message-in-reply-to-takes-only-ids-from-your-.md)). Separately from the marker gate, after the claude→opencode session migration (2026-11-21) the router itself refuses a plain `send_message(to="peer")` on a thread with unresponded inbound rows ("Pass in_reply_to=<seq>") — find the owning session via `ncl sessions list --thread-id <thread>`, read `ncl sessions messages --id <sess>` for the triggering inbound, and pass `in_reply_to=<its seq>` together with the explicit `to=` (which still names the destination) ([opencode migration: router demands in_reply_to on old threads](../learnings/1795224576884-opencode-migration-critique-gate-state-reset-block.md)).

**Fallback task sessions: the task prompt is the one inbound.** A one-shot `ncl tasks` fallback session has exactly one inbound — the task prompt itself, seq 2 — so gate-blocked delivery markers (`[Triage Resolution]`, `[Fix Report]`, `[Triage handoff]`…) from such a session must anchor on it. The recipe that worked (#13834 fallback, 2026-11-17): `send_message(to="parent", in_reply_to=2, thread_id="gh-issue-<owner>/<repo>-<num>")` — the explicit `to` overrides `in_reply_to`'s default source routing so the message reaches the Orchestrator, `in_reply_to=2` satisfies the delivery gate, and the explicit canonical `thread_id` preserves per-chain observability (the task prompt's own thread would otherwise leak through). Correlation intent that `in_reply_to` can't express (e.g. "correlates with the [Triage] of 04:55Z") goes in the message body. Schedule such safety nets when a closing report is in transit through a flaky provider window: the #13834 `[Fix Report]` was sent and never arrived, and the one-shot fallback compiled the resolution from the sender's status message plus a live GitHub check — a complete substitute when the sender already reported verdict/head/tests ([fallback task sessions: in_reply_to only resolves own-session inbounds](../learnings/1794910858763-fallback-task-sessions-in-reply-to-only-resolves-o.md)).
