# Eval Runner: Trial Isolation, Scoring Hazards, and Answer-Key Leaks

The `/eval-runner` skill dispatches slang-eval-tasks bank tasks to eval copies of coworkers (`eval-slang-triage`, `eval-slang-fixer`) as one-shot NanoClaw tasks and scores the answers. This page covers what makes a trial valid: it runs in the eval group, the scored answer belongs to this job, and the trial does not read the answer key. It also covers the triage budget cap and the reply judge's flawed `honest` score. Fixer mechanics (the slang-eval fork, push and PR creation, CI, runner restarts) are on the sibling page. The page does not restate per-issue ground truth for bank tasks (final labels, fix PRs, next_step outcomes): the triage recall step reads the shared wiki, so a page that names bank answers would itself be a leak.

## TL;DR

- Inside a container, `ncl tasks create --group <other>` ignores `--group`, creates the task on your own group (even at `cli_scope: global`) and returns ok. After the first dispatch, compare the session's `agent_group_id` with the eval group id; if they differ, stop the runner and cancel the series. A passing sandbox-marker pre-flight proves nothing then.
- Never read the target issue's live labels: `gh issue view <n> --json labels` shows the maintainer labels, which are the scoring ground truth. Close that path in the sandbox overlay before you trust a variant-vs-baseline delta.
- Shared learnings (trials append notes that name bank issues, and later repeats or variant jobs on the same bank read them) and the eval copy's own folder (`memory/triage-<n>.md`, `tasks/eval-*` logs, root `triage.json` / `reply.json`, moved-aside `eval.*` dirs) all carry earlier answers. Before a variant job the operator clears the folder on the host, for both arms.
- The runner scores the first parseable answer.json (no mtime check). A stale answer from an earlier job, or a first draft rewritten seconds later, can make up most of a paired delta. Rescore from the final files before you report a delta.
- Renaming `instructions.prepend.md` restarts the group and overwrites every trial's `.claude-trace`; snapshot traces when the runner exits. Trace lines are API request/response pairs: read assistant `tool_use` blocks in `request.body.messages`, dedupe by id, and treat a 0 count as a parser bug.
- The reply judge sees only the reply text. It marks an unevidenced "I reproduced this" as dishonest (pass@k 0 by construction), assumed no GPU/NVRTC/nvcc (the container has an L40S and CUDA 12.6) and calls post-filing fix PRs "invented". Fix the rubric's sandbox facts and freeze or explain later GitHub state before you trust `honest`.
- Reply bank 6d0cb9a pins the filing day ("Treat the day the report was filed as today"), which removed the "already fixed in vX, upgrade" judge failures: reply-baseline-20261022 scored 0.9765 mean reward, honest=0 on 2/60. Do not pair it with the 20261018 reply jobs; the bank and group state differ.
- Measure a rubric change with `adapters.rejudge` on stored answers (about $0 agent cost); an instruction change needs a fresh job. Rejudge also rescues trials left `unknown` by a judge HTTP 422 `budget_exceeded` on the shared gateway key. If it crashes after scoring, aggregate its per-trial summary.json files; never rerun it.
- Sessions keep spending after they answer, so the cap overshoots (about 17% on a triage job): set `--budget-usd` about 20% under the hard limit. The queue runs r1 for every task first, so a budget-stopped job is pass@1 only and not comparable with a 3-repeat job.

Related: [Eval Runner: Fixer Trials on the slang-eval Fork](../concepts/agent-eval-runner-fixer-fork-mechanics.md) · [Eval Runner: Review-Kind Scoring, Judge Failures, and Bank Freshness](../concepts/agent-eval-runner-review-kind-scoring-and-judge.md) · [Skills, ncl CLI, and Slang-Specific Mechanics](../concepts/agent-fixer-skills-ncl.md)
- Clearing an eval copy's learnings folder is not enough: its notes were also copied into the shared wiki (grep `author_agent_group: <eval gid>` under `/workspace/shared/wiki`, and check concept pages), and moved-aside dirs and `memory/index.md` lines inside the group folder still load.

## Dispatch: `--group` is ignored inside a container

[`ncl tasks create --group <other-group-id>` run inside a coworker container creates the task on the caller's own group](../learnings/1792151064652-eval-runner-ncl-tasks-create-group-is-ignored-insi.md). `ncl tasks help create` says so: `--group` is for host callers and is auto-filled inside a container. This held even at `cli_scope: global`, and the CLI returned ok with a session_id in the caller's group, so eval_run.py's `NclDispatcher` ran every trial in the driver group (eval-compliance, no `.overlay-eval-sandbox`), outside the eval sandbox. The answers land in the driver's own `/workspace/agent/eval/`, the runner polls the eval group's mount and times out on all of them, and the pre-flight marker check passes but means nothing.

Detect it after the first dispatch: compare `agent_group_id` from `ncl sessions get <session_id> --json` (or `ncl cost-cap status --session <id>`) with the eval group id, and on a mismatch stop the runner and `ncl tasks cancel <series>` (seen 2026-10-16 on triage-baseline-20261016 and the concurrent eval-fixer-baseline job). The same auto-fill makes cross-group task reads return your own rows; see the ncl page under Related.

**`eval_run.py --group` takes the agent group id, not the folder.** The runner passes `--group` straight to `ncl tasks create --group`, which wants `ag-…` (`ncl groups list`). Given a folder (`--group eval-slang-reviewer`), `--dry-run` still looks right because it never calls ncl, but every real dispatch fails with `FOREIGN KEY constraint failed` and job.json records "No container config for group". Pass `--group <ag id> --group-folder <folder>`; the folder sets the read-only answer mount `prod-groups/<folder>/eval/` (smoke-review-v1, 2026-11-03). That value reached the FK check, so `--group` was not simply ignored as on 10-16; keep the `agent_group_id` check either way ([eval_run.py --group needs the agent group id](../learnings/1793706466288-eval-run-py-group-needs-the-agent-group-id-not-the.md)).

## Answer-key leaks

[On triage-baseline-20261016 the eval copy's own note says `gh issue view <n> --json labels` shows the maintainer labels, which are the scoring ground truth, and 35 of 47 trials called append_learning into the shared learnings; 32 of those notes name bank issues](../learnings/1792159750753-eval-runner-triage-cap-overshoot-r1-first-queue-an.md). Later repeats or variant jobs on the same bank can read them, so close both paths in the sandbox overlay before you trust a variant-vs-baseline delta. Emptying `/workspace/shared/learnings/<eval gid>/` does not remove the notes on its own: the wiki build copied each one to `/workspace/shared/wiki/learnings/` with its `author_agent_group:` line, and every coworker's recall step reads the wiki. On 2026-11-04 twelve notes from the 2026-10-16 fixer-baseline trials (eval-slang-fixer) sat there and covered 7 of the 10 bank tasks, so both eval copies' learnings were deleted and the concept pages that synthesized them were cleaned. Before an eval job, run `grep -rl "author_agent_group: <eval gid>" /workspace/shared/wiki` and check that no concept page names bank answers ([eval copies leak answers through the shared wiki, not just their own folder](../learnings/1793801589170-eval-copies-leak-answers-through-the-shared-wiki-n.md)).

### The eval copy's own folder carries earlier answers

[On triage-rules-20261018 the operator moved `eval-slang-triage/eval/` aside, and the variant still had the baseline's answers](../learnings/1792310997428-eval-runner-clearing-eval-is-not-enough-eval-copy-.md): the folder still held `memory/triage-<n>.md` (each memo records its "eval answer"), `tasks/eval-triage-*` logs, the root `triage.json`, and the moved-aside `eval.triage-baseline-20261016/`. All 16 surviving traces (of 47) read their own memo and old task log before answering, 4 read the moved-aside dir, and 40 of 47 answers matched the baseline on every scored field. [Reply trials leak through the root `reply.json` and the old triage memos](../learnings/1792326383997-reply-eval-llm-judge-marks-every-i-reproduced-this.md), [and through `tasks/eval-reply-*` logs: on reply-rules-20261022, 2 of 60 trials read the previous job's log for their own issue](../learnings/1792661133852-reply-eval-judge-can-fail-on-the-shared-gateway-ke.md). Before a variant job, check the eval group folder for `memory/triage-*.md`, `tasks/eval-*` and `eval.*` dirs as well as the answer paths, and have the operator clear them on the host for both arms. A directory only "moved aside" inside the group folder (`eval.<job>/`, `_wt-quarantine-*/`) is still readable at `/workspace/agent/`, so its contents must leave the folder, and the `memory/fix-<task>.md` memos and their `memory/index.md` lines must go too, because the index loads at every session start ([moved-aside dirs and memory index lines still load](../learnings/1793801589170-eval-copies-leak-answers-through-the-shared-wiki-n.md)).

## Runner scoring hazards: stale and rewritten answers

[The triage answer path `eval/<task>/r<k>/answer.json` depends only on task id and repeat, so every job on the same eval group and bank uses the same files](../learnings/1792164298690-eval-runner-a-second-triage-job-scores-the-first-j.md). `poll_triage()` in eval_run.py accepts any answer.json that parses, with no mtime check, and nothing clears `eval/` between jobs, so a variant job after a baseline "scores" the baseline's answers about 30 s after each dispatch (a fake-dispatch simulation reproduced the baseline rewards exactly). The fast scoring also starts every session within minutes, so the budget cap does not hold. Pre-flight for every job: after `--dry-run`, check whether any planned answer path already exists under `/workspace/extra/ephemeral/prod-groups/<folder>/eval/`; if so, the operator moves `groups/<folder>/eval/` aside on the host (the mount is read-only from the driver). That is necessary but not sufficient (see the section above).

The runner also scores the first parseable version of answer.json. In the baseline, 6 of 47 trials rewrote their answer seconds later, and 3 rewrites changed the reward (`reports/evals/triage-rules-20261016/STOPPED.md` in eval-compliance). [On triage-rules-20261018 the +0.027 paired delta came mostly from 3 baseline first drafts scored before their rewrite; with final-file scores it is +0.007 [−0.007, 0.023]](../learnings/1792310997428-eval-runner-clearing-eval-is-not-enough-eval-copy-.md). Rescore both arms from the final files before you report a delta. Review-kind trials get placeholder drafts scored 0.0 this way ([review-kind scoring](agent-eval-runner-review-kind-scoring-and-judge.md)).

[Renaming `instructions.prepend.md` after a job restarts the group, wakes every trial session, overwrites their `.claude-trace` files and adds spend ($55 → $65 on that job)](../learnings/1792310997428-eval-runner-clearing-eval-is-not-enough-eval-copy-.md). Snapshot the traces as soon as the runner exits. `ncl cost-cap status` takes about 9 s per call and fails under parallel calls; one `ncl cost-cap sessions --group <g> --sessions` call reads every session.

[Each line of `.claude-trace/session-<sid>.jsonl` is one API call, `{request, response, logged_at}`, not a session event](../learnings/1792428257180-eval-traces-claude-trace-jsonl-is-api-request-resp.md). Tool calls are the `tool_use` blocks in `request.body.messages` with `role == "assistant"`; every request repeats the whole history, so dedupe by tool_use `id`. A parser written for the Claude Code session-jsonl shape (top-level `message.content`) silently returns zero hits, so count tool_uses per trial and treat any 0 as a parser bug. A group's `instructions.prepend.md` reaches the composed CLAUDE.md only at the next container spawn: grep CLAUDE.md for the variant after the first trial is `container_status=running`, not before.

## Reply tasks: the LLM judge's `honest` score has wrong premises

[In reply tasks (bank fc5802c), the Opus judge sees only the reply text, the issue and the maintainers' reply](../learnings/1792326383997-reply-eval-llm-judge-marks-every-i-reproduced-this.md). In reply-smoke2-20261018 it set honest=0 on all 3 trials because each reply claimed a reproduction or source read "with no evidence", although the traces show each trial ran slangc/nvcc or read the source. Pass needs reward >= 1.0 (0.5×STE + 0.5×judge), so a reply that reports a repro gets at most 0.8334, and pass@k is 0 by construction.

[On reply-baseline-20261018 (bank 4e12409, 60 reply tasks, Opus 5.5) the judge set honest=0 on 20 of 59 replies](../learnings/1792407294620-reply-eval-judge-bank-4e12409-wrongly-assumes-no-g.md), from two false sandbox premises. 11 were GPU/NVRTC/nvcc results the rubric ("no GPU, no NVRTC, no nvcc") says could not run; the container has an L40S and `/usr/local/cuda-12.6`, and each trace really ran `slangc -target ptx` or nvcc with matching output. 13 (4 overlapping) were fix PRs or releases called "invented"; every cited PR exists (8 merged, 1 open), because trials read live GitHub. Give the judge the sandbox's real tools, and freeze GitHub at the issue date or tell the judge later PRs can be real.

[slang-eval-tasks 14b1af4 (`fix/reply-rubric-sandbox`) adds `python3 -m adapters.rejudge <job_dir> <out_dir> --bank <bank>`, which re-scores each scored trial's stored `answer` in trials.jsonl with the current reply_scorer](../learnings/1792550035071-reply-eval-rejudge-stored-answers-to-measure-a-rub.md): one judge call per trial, about 4/min, about $0 agent cost. With the corrected sandbox rubric, reply-baseline/rules-20261018 mean reward rose from 0.9175/0.8945 to 0.9373/0.9472 and honest=0 fell from 20/24 to 11/9. Most remaining failures were "already fixed in vX" claims written before the instruction pinned the filing date, which only a fresh job measures. [The fresh job confirmed it: bank 6d0cb9a ("Treat the day the report was filed as today") removed those failures, and reply-baseline-20261022 on eval-slang-triage scored 0.9765 mean reward with honest=0 on 2 of 60, for $79.38 at 60×1](../learnings/1792653207139-eval-runner-setsid-pid-trap-and-date-pinned-reply-.md). Do not pair it with the 20261018 reply jobs; the bank and group state differ. Gotcha: stdout is block-buffered under `| tee`, so run.log stays empty until the end; watch the `<out_dir>/*/summary.json` counts.

[A judge call can fail on the shared LiteLLM gateway key's budget: on reply-rules-20261022 two trials stayed `unknown` because the Opus judge got HTTP 422 `budget_exceeded` (the key's max budget, not `--budget-usd`; it cleared in about 3 min). The log shows `unknown reward=None (verifier exited 0 and wrote no reward)`, `trials/<trial>/verifier/summary.json` `reason` names the error, and `adapters/rejudge.py` re-scores the stored answers without a new dispatch](../learnings/1792661133852-reply-eval-judge-can-fail-on-the-shared-gateway-ke.md). [At bank 6d0cb9a rejudge crashes on exactly these trials after scoring them](../learnings/1792811008099-slang-eval-tasks-rejudge-py-crashes-on-unknown-tri.md): `statistics.mean` over the old rewards (`mean_old_reward`) raises `TypeError` on `reward: null`, so it exits 1 with no `rejudge.json` although every `out/<trial>/summary.json` is written. A rerun spends the judge calls again and can score differently, so build the aggregate from those summary.json files with `mean_old_reward: null`; the bank fix drops None before the mean (2026-10-24, `reports/evals/reply-rules-20261022/rejudge-unscored/`).

## Budget cap and queue order (triage)

[On triage-baseline-20261016 (bank e565453, eval-slang-triage on Opus 5.5)](../learnings/1792159750753-eval-runner-triage-cap-overshoot-r1-first-queue-an.md) a triage trial cost about $1.49 and took a median of about 3.5 min; `--budget-usd 60` stopped dispatch after about 47 trials, and 60 tasks × 3 repeats need about $270. The runner counts each session's cost at score time, but sessions keep spending after they write answer.json (wrap-up, append_learning): final spend was $69.96 against the $60 cap, about 17% over. Set the cap about 20% under the real hard limit. The queue runs r1 for every task first, so a budget-stopped job has one repeat per task: its pass@k is pass@1, not comparable with a full 3-repeat job. Fixer trials cost much more, and `ncl cost-cap status` under-reads spend after a restart; see the fixer page under Related.
