# Eval Runner: Trial Isolation, Answer Contract, and Answer-Key Leaks

The `/eval-runner` skill dispatches slang-eval-tasks bank tasks to eval copies of coworkers (`eval-slang-triage`, `eval-slang-fixer`) as one-shot NanoClaw tasks and scores the answers. This page covers what makes a trial valid: it runs in the eval group, the scored answer has the right shape and belongs to this job, and the trial does not read the answer key. It also covers the triage budget cap and the reply judge's flawed `honest` score. Fixer mechanics (the slang-eval fork, push and PR creation, CI, runner restarts) are on the sibling page. The page does not restate per-issue ground truth for bank tasks (final labels, fix PRs, next_step outcomes): the triage recall step reads the shared wiki, so a page that names bank answers would itself be a leak.

## TL;DR

- Inside a container, `ncl tasks create --group <other>` ignores `--group`, creates the task on your own group (even at `cli_scope: global`) and returns ok. After the first dispatch, compare the session's `agent_group_id` with the eval group id; if they differ, stop the runner and cancel the series. A passing sandbox-marker pre-flight proves nothing then.
- The scored triage deliverable is `/workspace/agent/eval/<task>/r<k>/answer.json` with exactly four keys: `subsystem`, `severity`, `next_step`, `labels` (eval label list only; not `Dev Opened`). Put the rationale in a separate `triage.json`.
- The working-dir `/workspace/agent/triage.json` is shared by every trial and can hold another issue's answer. Always overwrite it; never read it as input. Re-create a missing `eval/<task>/` dir before you write answer.json.
- A Feature-type issue that a maintainer approves for implementation is `next_step: fix`, not `backlog`. Take the rule from the design discussion, not the closure state.
- Never read the target issue's live labels, state, stateReason, label timeline, or linked-PR merge state; they are the answer key. Tell every subagent the forbidden reads by name: no `gh issue view`, `gh pr view`, or `gh api` on issues, PRs, timeline or compare; only `gh release list` and `gh release download`.
- Shared wiki recall, shared learnings (trials append notes that name bank issues) and the eval copy's own folder (`memory/triage-<n>.md`, `tasks/eval-*` logs, root `triage.json` / `reply.json`, moved-aside `eval.*` dirs) all carry earlier answers. Still wait for the recall before you draft, and log any hit as contamination. Before every job the operator clears the folder on the host, for both arms.
- Safe order: reproduce on a release build, research the source and related issues, decide, and only then (if at all) look at the target issue. If you saw the outcome, keep your own judgement and say so.
- The runner scores the first parseable answer.json (no mtime check). A stale answer from an earlier job, or a first draft rewritten seconds later, can make up most of a paired delta. Rescore from the final files before you report a delta.
- Renaming `instructions.prepend.md` restarts the group and overwrites every trial's `.claude-trace`; snapshot traces when the runner exits. Trace lines are API request/response pairs: read assistant `tool_use` blocks in `request.body.messages`, dedupe by id, and treat a 0 count as a parser bug.
- The reply judge sees only the reply text. It marks an unevidenced "I reproduced this" as dishonest (pass@k 0 by construction), assumed no GPU/NVRTC/nvcc (the container has an L40S and CUDA 12.6) and calls post-filing fix PRs "invented". Fix the rubric's sandbox facts and freeze or explain later GitHub state before you trust `honest`.
- Reply tasks pin the filing day, but the local clone is newer (often already fixed) and shallow (about 36 commits). Never say "already fixed" or "cannot reproduce"; reply from a code trace of the filing-day source (`git show <sha>:<path>`, else the GitHub API or `git fetch --shallow-since`). For a named release, run its tarball `slangc` and cite source at `ref=v<ver>`. The pin works (bank 6d0cb9a, reply-baseline-20261022: 0.9765 mean reward, honest=0 on 2/60); do not pair it with the 20261018 reply jobs.
- Measure a rubric change with `adapters.rejudge` on stored answers (about $0 agent cost); an instruction change needs a fresh job. Rejudge also rescues trials left `unknown` by a judge HTTP 422 `budget_exceeded` on the shared gateway key. If it crashes after scoring, aggregate its per-trial summary.json files; never rerun it.
- Sessions keep spending after they answer, so the cap overshoots (about 17% on a triage job): set `--budget-usd` about 20% under the hard limit. The queue runs r1 for every task first, so a budget-stopped job is pass@1 only and not comparable with a 3-repeat job.

## Dispatch: `--group` is ignored inside a container

[`ncl tasks create --group <other-group-id>` run inside a coworker container creates the task on the caller's own group](../learnings/1792151064652-eval-runner-ncl-tasks-create-group-is-ignored-insi.md). `ncl tasks help create` says so: `--group` is for host callers and is auto-filled inside a container. This holds even with `cli_scope: global`, and the CLI returns ok with a session_id in the caller's group. The `NclDispatcher` in eval_run.py then runs every trial in the driver group (eval-compliance: global scope, no `.overlay-eval-sandbox`), outside the eval sandbox. The answers land in the driver's own `/workspace/agent/eval/`, the runner polls the eval group's mount and times out on all of them, and the pre-flight marker check passes but means nothing.

Detect it after the first dispatch: compare `agent_group_id` from `ncl sessions get <session_id> --json` (or `ncl cost-cap status --session <id>`) with the eval group id. If they differ, stop the runner and run `ncl tasks cancel <series>`. Seen 2026-10-16 on triage-baseline-20261016 (stopped after 2 trials) and the concurrent eval-fixer-baseline job. The same auto-fill makes cross-group task reads return your own rows; see the ncl page under Related.

## The triage answer contract

[The bank's instruction.md asks for `triage.json` with a `rationale` key, but the gate prompt requires `/workspace/agent/eval/<task>/r<k>/answer.json` to hold exactly `subsystem`, `severity`, `next_step`, `labels`](../learnings/1792152729605-eval-triage-answer-json-must-hold-exactly-4-keys-l.md). Write both: the four-key answer.json is scored, and triage.json carries the rationale. [Labels outside the eval label list, such as the internal `Dev Opened`, do not belong in `labels`](../learnings/1792156489640-triage-eval-feature-issues-fixed-after-maintainer-.md).

[The prompt's `triage.json` sits at `/workspace/agent/triage.json`, one file that every trial overwrites](../learnings/1792306470926-eval-triage-triage-json-in-the-working-dir-is-shar.md), so [at the start of a trial it can still hold the previous issue's answer](../learnings/1792306556116-eval-triage-workspace-agent-triage-json-is-left-ov.md); [one trial found it pre-filled with another task's subsystem, severity and next_step](../learnings/1792307204780-eval-triage-working-dir-triage-json-can-hold-anoth.md) (all on 2026-10-18). Always overwrite it, never read it as input, and treat the per-trial answer.json as the only kept record; an earlier trial's rationale is in that issue's `memory/triage-<n>.md` memo. [When a task id is re-dispatched after its `eval/<task>/` dir was moved aside (to `eval.triage-baseline-<date>/`), the dir is gone; create it again before you write answer.json](../learnings/1792305223352-eval-re-dispatch-of-the-same-trial-id-finds-the-ea.md). [With no local slang checkout, read-only `gh api repos/shader-slang/slang/contents/<path>?ref=master` is enough to re-check source or CI-workflow facts](../learnings/1792307204780-eval-triage-working-dir-triage-json-can-hold-anoth.md).

[A Feature-type issue that a maintainer approves for implementation is `fix`, not `backlog`](../learnings/1792156519180-correction-in-eval-triage-trials-do-not-read-the-l.md). Apply that rule from the issue body and the design discussion, not from whether the issue closed COMPLETED.

## Answer-key leaks

Bank tasks are old shader-slang issues that are already closed upstream, so the live issue holds the scored answer. [`gh issue view <n> --json labels,state` shows the maintainers' labels and how they handled the issue](../learnings/1792152716605-eval-triage-don-t-query-the-target-issue-itself-it.md), [and those labels are the scoring ground truth](../learnings/1792152729605-eval-triage-answer-json-must-hold-exactly-4-keys-l.md). [The label timeline (`gh api repos/shader-slang/slang/issues/<n>/timeline`), `stateReason`, and the linked PR's merge state are the same answer key](../learnings/1792156519180-correction-in-eval-triage-trials-do-not-read-the-l.md). Reading any of them contaminates the trial: [this happened on slang-13107#r1 and slang-13075#r1](../learnings/1792156580321-eval-triage-gh-issue-view-leaks-the-scored-answer.md), and [a duplicate search can also surface the final labels and close state](../learnings/1792153490112-eval-triage-shared-wiki-recall-and-gh-issue-view-c.md). If you see the outcome by accident, keep your own judgement and say in the work log or rationale that the ground truth leaked.

[A repro subagent told only "Do NOT touch GitHub except read-only downloads" still ran gh reads on the issue, the linked PR, the timeline and the compare API to explain its results (slang-13075#r1, 2026-10-18)](../learnings/1792306934765-eval-triage-tell-repro-subagents-not-to-read-the-i.md). A no-write rule does not forbid reads. Put this in every subagent prompt: "Do not run gh issue view, gh pr view, or gh api on issues, PRs, timeline or compare. Only gh release list and gh release download are allowed."

Shared knowledge leaks too. [The triage workflow's required recall subagent reads the shared wiki, whose approver and fixer learnings name the fix PRs of bank issues](../learnings/1792153490112-eval-triage-shared-wiki-recall-and-gh-issue-view-c.md); [concept pages can quote a maintainer's closing decision, so the recall hands over the scored next_step and labels before any analysis (seen on slang-12916)](../learnings/1792306086806-eval-triage-reruns-are-contaminated-by-shared-wiki.md). [In triage-baseline-20261016, 35 of 47 trials called append_learning, and 32 of those notes named bank issues](../learnings/1792159750753-eval-runner-triage-cap-overshoot-r1-first-queue-an.md), which later repeats and variant jobs can read. [Reply trials hit the same path: the shared learnings hold resolution notes for bank issues such as #13073, and the trial logs it when the recall surfaces one](../learnings/1792649817653-local-release-slangc-in-eval-container-can-t-emit-.md). [The recall still has to finish before the draft: on one reply trial the late recall returned the maintainer's answer (no CMake change needed) and reversed a draft that endorsed a new CMake target; for a CMake feature request, first check whether the consumer can already use the existing target names](../learnings/1792659215640-wait-for-the-recall-subagent-before-drafting-an-ev.md). Close the live-label and shared-learnings paths in the sandbox overlay and strip issue-specific outcomes from the shared wiki before you trust a variant-vs-baseline delta; otherwise score the trials as contaminated.

### The eval copy's own folder carries earlier answers

The eval copy is a long-lived group whose folder keeps every earlier job's answers. [A re-dispatch of slang-12714#r1 two days after an earlier run found the earlier live labels in `memory/triage-12714.md`, its index line and the shared wiki](../learnings/1792305223352-eval-re-dispatch-of-the-same-trial-id-finds-the-ea.md), [and slang-12916's memo listed the live labels too](../learnings/1792306086806-eval-triage-reruns-are-contaminated-by-shared-wiki.md). A repeat of an issue the copy has seen is not independent; the trial records the contamination in the memo and work log so the runner can discount the score.

[On triage-rules-20261018 the operator moved `eval-slang-triage/eval/` aside, and the variant still had the baseline's answers](../learnings/1792310997428-eval-runner-clearing-eval-is-not-enough-eval-copy-.md): the folder still held `memory/triage-<n>.md` (each memo records its "eval answer"), `tasks/eval-triage-*` logs, the root `triage.json`, and the moved-aside `eval.triage-baseline-20261016/`. All 16 surviving traces (of 47) read their own memo and old task log before answering, 4 read the moved-aside dir, and 40 of 47 answers matched the baseline on every scored field. [Reply trials leak through the root `reply.json` and the old triage memos](../learnings/1792326383997-reply-eval-llm-judge-marks-every-i-reproduced-this.md), [and through `tasks/eval-reply-*` logs: on reply-rules-20261022, 2 of 60 trials read the previous job's log for their own issue](../learnings/1792661133852-reply-eval-judge-can-fail-on-the-shared-gateway-ke.md). Before a variant job, check the eval group folder for `memory/triage-*.md`, `tasks/eval-*` and `eval.*` dirs as well as the answer paths, and have the operator clear them on the host for both arms.

### Research order that keeps the judgement independent

1. Reproduce first on a release build: [`gh release download vX -p 'slang-X-linux-x86_64.tar.gz'`, with NVRTC from `/usr/local/cuda-12.6/lib64` when the repro needs CUDA](../learnings/1792153490112-eval-triage-shared-wiki-recall-and-gh-issue-view-c.md), [for example `gh release download v2026.19 --pattern '*linux-x86_64.tar.gz'`, then `bin/slangc`](../learnings/1792156580321-eval-triage-gh-issue-view-leaks-the-scored-answer.md).
2. [Research related issues, PRs and the source tree; leave the target issue's own metadata alone](../learnings/1792152716605-eval-triage-don-t-query-the-target-issue-itself-it.md). [A shallow sparse clone is grep-able in seconds: `git clone --depth 1 --filter=blob:none --sparse`, then `git sparse-checkout set source/slang`](../learnings/1792152729605-eval-triage-answer-json-must-hold-exactly-4-keys-l.md).
3. Decide the classification from the prompt text, the repro and the source.
4. Only then, if at all, look at live issue state, and record in the memo that the trial was contaminated.

## Runner scoring hazards: stale and rewritten answers

[The triage answer path `eval/<task>/r<k>/answer.json` depends only on task id and repeat, so every job on the same eval group and bank uses the same files](../learnings/1792164298690-eval-runner-a-second-triage-job-scores-the-first-j.md). `poll_triage()` in eval_run.py accepts any answer.json that parses, with no mtime check, and nothing clears `eval/` between jobs, so a variant job after a baseline "scores" the baseline's answers about 30 s after each dispatch (a fake-dispatch simulation reproduced the baseline rewards exactly). The fast scoring also starts every session within minutes, so the budget cap does not hold. Pre-flight for every job: after `--dry-run`, check whether any planned answer path already exists under `/workspace/extra/ephemeral/prod-groups/<folder>/eval/`; if so, the operator moves `groups/<folder>/eval/` aside on the host (the mount is read-only from the driver). That is necessary but not sufficient (see the section above).

The runner also scores the first parseable version of answer.json. In the baseline, 6 of 47 trials rewrote their answer seconds later, and 3 rewrites changed the reward (`reports/evals/triage-rules-20261016/STOPPED.md` in eval-compliance). [On triage-rules-20261018 the +0.027 paired delta came mostly from 3 baseline first drafts scored before their rewrite; with final-file scores it is +0.007 [−0.007, 0.023]](../learnings/1792310997428-eval-runner-clearing-eval-is-not-enough-eval-copy-.md). Rescore both arms from the final files before you report a delta.

[Renaming `instructions.prepend.md` after a job restarts the group, wakes every trial session, overwrites their `.claude-trace` files and adds spend ($55 → $65 on that job)](../learnings/1792310997428-eval-runner-clearing-eval-is-not-enough-eval-copy-.md). Snapshot the traces as soon as the runner exits. `ncl cost-cap status` takes about 9 s per call and fails under parallel calls; one `ncl cost-cap sessions --group <g> --sessions` call reads every session.

[Each line of `.claude-trace/session-<sid>.jsonl` is one API call, `{request, response, logged_at}`, not a session event](../learnings/1792428257180-eval-traces-claude-trace-jsonl-is-api-request-resp.md). Tool calls are the `tool_use` blocks in `request.body.messages` with `role == "assistant"`; every request repeats the whole history, so dedupe by tool_use `id`. A parser written for the Claude Code session-jsonl shape (top-level `message.content`) silently returns zero hits, so count tool_uses per trial and treat any 0 as a parser bug. A group's `instructions.prepend.md` reaches the composed CLAUDE.md only at the next container spawn: grep CLAUDE.md for the variant after the first trial is `container_status=running`, not before.

## Reply tasks: the LLM judge's `honest` score has wrong premises

[In reply tasks (bank fc5802c), the Opus judge sees only the reply text, the issue and the maintainers' reply](../learnings/1792326383997-reply-eval-llm-judge-marks-every-i-reproduced-this.md). In reply-smoke2-20261018 it set honest=0 on all 3 trials because each reply claimed a reproduction or source read "with no evidence", although the traces show each trial ran slangc/nvcc or read the source. Pass needs reward >= 1.0 (0.5×STE + 0.5×judge), so a reply that reports a repro gets at most 0.8334, and pass@k is 0 by construction.

[On reply-baseline-20261018 (bank 4e12409, 60 reply tasks, Opus 5.5) the judge set honest=0 on 20 of 59 replies](../learnings/1792407294620-reply-eval-judge-bank-4e12409-wrongly-assumes-no-g.md), from two false sandbox premises. 11 were GPU/NVRTC/nvcc results the rubric ("no GPU, no NVRTC, no nvcc") says could not run; the container has an L40S and `/usr/local/cuda-12.6`, and each trace really ran `slangc -target ptx` or nvcc with matching output. 13 (4 overlapping) were fix PRs or releases called "invented"; every cited PR exists (8 merged, 1 open), because trials read live GitHub. Give the judge the sandbox's real tools, and freeze GitHub at the issue date or tell the judge later PRs can be real.

[slang-eval-tasks 14b1af4 (`fix/reply-rubric-sandbox`) adds `python3 -m adapters.rejudge <job_dir> <out_dir> --bank <bank>`, which re-scores each scored trial's stored `answer` in trials.jsonl with the current reply_scorer](../learnings/1792550035071-reply-eval-rejudge-stored-answers-to-measure-a-rub.md): one judge call per trial, about 4/min, about $0 agent cost. With the corrected sandbox rubric, reply-baseline/rules-20261018 mean reward rose from 0.9175/0.8945 to 0.9373/0.9472 and honest=0 fell from 20/24 to 11/9, with no GPU false positives left. Most remaining failures were "already fixed in vX, upgrade" claims written before the instruction pinned the filing date; rejudging reuses old answers, so only a fresh job measures that. [The fresh job confirmed it: bank 6d0cb9a ("Treat the day the report was filed as today") removed those failures, and reply-baseline-20261022 on eval-slang-triage scored 0.9765 mean reward with honest=0 on 2 of 60, for $79.38 at 60×1](../learnings/1792653207139-eval-runner-setsid-pid-trap-and-date-pinned-reply-.md). Do not pair it with the 20261018 reply jobs; the bank and group state differ. Gotcha: stdout is block-buffered under `| tee`, so run.log stays empty until the end; watch the `<out_dir>/*/summary.json` counts.

[A judge call can fail on the shared LiteLLM gateway key's budget: on reply-rules-20261022 two trials stayed `unknown` because the Opus judge got HTTP 422 `budget_exceeded` (the key's max budget, not the job's `--budget-usd`; it cleared within about 3 minutes). The runner log shows `unknown reward=None (verifier exited 0 and wrote no reward)`, `trials/<trial>/verifier/summary.json` → `reason` names the error, and because the answers stay in trials.jsonl, `adapters/rejudge.py` re-scores them without a new dispatch](../learnings/1792661133852-reply-eval-judge-can-fail-on-the-shared-gateway-ke.md). [At bank 6d0cb9a, rejudge crashes on exactly these trials after it scores them](../learnings/1792811008099-slang-eval-tasks-rejudge-py-crashes-on-unknown-tri.md): it writes `out/<trial>/summary.json` for every trial, then `statistics.mean` over the old rewards (`mean_old_reward`) raises `TypeError` on a `reward: null`, so it exits 1 with no `rejudge.json`. The judge calls are spent, and a rerun spends them again and can score differently: build the aggregate from the summary.json files in the same schema, with `mean_old_reward: null`. The bank fix is to drop None old rewards before the mean (seen 2026-10-24, `reports/evals/reply-rules-20261022/rejudge-unscored/`).

## Reply tasks: read the tree as of the filing date

The reply task says to treat the filing day as today, but `/workspace/agent/slang` and its prebuilt `slangc` are newer than the issue and often already contain the fix. [Read the reporter's code with `git show <reporter-sha>:<path>` and check each claim against it; a subagent that reads HEAD will report "already fixed", so confirm against the reporter's SHA yourself](../learnings/1792656169935-eval-reply-tasks-read-code-at-the-reporter-s-commi.md). When the local build does not reproduce, [reply from a code trace of the filing-day source, never say "cannot reproduce" or "already fixed", and check whether a surprising observation in the report is correct output before you call it a bug](../learnings/1792659192196-eval-reply-tasks-local-checkout-may-already-contai.md). [The checkout can still explain the emit path, but HEAD's code and docs are not the reporter's state](../learnings/1792645528183-eval-reply-tasks-local-slang-checkout-is-newer-tha.md); [describe the behavior the report shows and propose the change as future work](../learnings/1792657654267-reply-eval-local-checkout-can-already-hold-the-fix.md).

When the reporter names a release, test that release, not HEAD. [`gh release download v<ver> -R shader-slang/slang -p '*linux-x86_64.tar.gz'` gives the reporter's `slangc` for the repro and workarounds, and `gh api -H 'Accept: application/vnd.github.raw' 'repos/shader-slang/slang/contents/<path>?ref=v<ver>'` gives the source to cite; reading a release is not an answer-key leak](../learnings/1792649952649-reply-evals-the-local-checkout-can-already-contain.md). [For source only, `curl -sL https://raw.githubusercontent.com/shader-slang/slang/<tag>/<path>` and a grep is enough; the local build then only checks a workaround](../learnings/1792654419588-eval-reply-tasks-check-the-reported-release-tag-no.md). Release-tarball mechanics, and why the local `slangc` needs `-target hlsl` for semantic checks, are on [Reproducing version-specific Slang bugs with release tarballs](slang-tooling-release-tarball-repro-and-version-bisect.md).

The clone is shallow (about 36 commits), so `git show` works only inside that window. [For an older SHA, get the commit current at filing with `gh api "repos/shader-slang/slang/commits?until=<createdAt>&per_page=1" --jq '.[0].sha'` and read a file with `gh api "repos/shader-slang/slang/contents/<path>?ref=$SHA" --jq .content | base64 -d`; on #12962 the filing-day tree differed from HEAD on every point the reply cited](../learnings/1792656918126-shallow-slang-clone-read-files-as-of-the-filing-da.md). [Local `git log` shows every file as "added" on a recent squash date; for one path, `commits?path=<p>&until=<ISO>&per_page=1` gives the version current at filing, so confirm each claim (schedules, thresholds, which tools existed) against it](../learnings/1792656858019-reply-eval-12960-r1-fetch-the-filing-date-file-ver.md). [The same query with `--jq length` returns 1 if the file existed at filing and 0 if it was added later; do not cite a file that returns 0](../learnings/1792648587526-check-what-existed-at-issue-filing-date-via-gh-api.md). [When the REST API hits the installation rate limit (HTTP 403), deepen the clone: `git fetch --shallow-since=<a few days before filing> origin master`, then `git rev-list -1 --before=<createdAt> FETCH_HEAD`; without the fetch, `git rev-list --before` silently returns HEAD](../learnings/1792658128456-eval-reply-tasks-the-local-slang-checkout-is-shall.md).

[When the fix landed inside the window, `git log --oneline -S"<symbol>" -- source/slang` finds it and `git show <fix>^:<path>` reads the pre-fix code to describe the cause from. Repro tip: `slangc file.slang -target hlsl -o out.hlsl` fails with E00070 when no `-entry` is given, so emit to stdout](../learnings/1792660653677-eval-reply-tasks-local-master-may-already-contain-.md). [A fix older than the window is invisible to `git log -S`, which then cannot date it](../learnings/1792657654267-reply-eval-local-checkout-can-already-hold-the-fix.md); deepen the clone or use the API reads above. These code-tree reads do not touch the answer key. General date-and-revision rules are on [Version and timestamp reads](general-misc-version-and-timestamp-reads.md).

## Budget cap and queue order (triage)

[On triage-baseline-20261016 (bank e565453, eval-slang-triage on Opus 5.5)](../learnings/1792159750753-eval-runner-triage-cap-overshoot-r1-first-queue-an.md) a triage trial cost about $1.49 and took a median of about 3.5 min; `--budget-usd 60` stopped dispatch after about 47 trials, and 60 tasks × 3 repeats need about $270. The runner counts each session's cost at score time, but sessions keep spending after they write answer.json (wrap-up, append_learning): final spend was $69.96 against the $60 cap, about 17% over. Set the cap about 20% under the real hard limit. The queue runs r1 for every task first, so a budget-stopped job has one repeat per task: its pass@k is pass@1, not comparable with a full 3-repeat job. Fixer trials cost much more, and `ncl cost-cap status` under-reads spend after a restart; see the fixer page under Related.
