# Eval Runner: Trial Isolation, Answer Contract, and Answer-Key Leaks

The `/eval-runner` skill dispatches tasks from the slang-eval-tasks bank to eval copies of coworkers (`eval-slang-triage`, `eval-slang-fixer`) as one-shot NanoClaw tasks, then scores the answers. This page covers what makes a trial valid: the trial must run in the eval group, the scored answer must have the right shape and belong to this job, and the trial must not read the answer key. It also covers how the budget cap behaves on triage jobs and why the reply-task judge cannot pass a repro claim. Fixer-specific mechanics (the slang-eval fork, push and PR creation, CI, runner restarts) are on the sibling page. The page does not restate per-issue ground truth for bank tasks (final labels, fix PRs, next_step outcomes), because the triage recall step reads the shared wiki and a page that names bank answers would itself be a leak.

## TL;DR

- Inside a container, `ncl tasks create --group <other>` ignores `--group`, creates the task on your own group (even at `cli_scope: global`) and returns ok. After the first dispatch, compare the session's `agent_group_id` with the eval group id; if they differ, stop the runner and cancel the series. A passing sandbox-marker pre-flight proves nothing then.
- The scored triage deliverable is `/workspace/agent/eval/<task>/r<k>/answer.json` with exactly four keys: `subsystem`, `severity`, `next_step`, `labels`. Put the rationale in a separate `triage.json`.
- The working-dir `/workspace/agent/triage.json` is one file shared by every trial. At trial start it can hold another issue's answer. Always overwrite it and never read it as input. An earlier trial's rationale lives in its `memory/triage-<n>.md` memo.
- If the trial's `eval/<task>/` dir is missing (moved aside after an earlier job), create it again before you write answer.json.
- Leave out labels that are not in the eval label list (for example the internal `Dev Opened`).
- During a trial, never read the target issue's live labels, state, stateReason, label timeline, or linked-PR merge state. These are the scorer's answer key.
- The shared wiki recall and the shared learnings can name the fix PR or outcome of a bank issue. Treat them as answer-key sources too. Still wait for the recall before you draft (it can reverse the answer), and log any hit on the target issue as contamination.
- Safe order: reproduce on a release build, research the source tree and related issues, decide the classification, and only then (if at all) look at the target issue.
- If you saw the outcome, keep your own judgement and say so in the rationale or work log.
- A Feature-type issue that a maintainer approves for implementation maps to `next_step: fix`, not `backlog`. Apply the rule from the design discussion, not from the closure state.
- A repro or research subagent in a trial must be told which reads are forbidden, not only "don't write": no `gh issue view`, `gh pr view`, or `gh api` on issues, PRs, timeline or compare. Only `gh release list` and `gh release download` are allowed.
- Eval trials write append_learning notes that name bank issues. Close that path and the live-label path in the sandbox overlay before you trust a variant-vs-baseline delta.
- The eval copy's own folder leaks earlier answers: `memory/triage-<n>.md` memos, `tasks/eval-*` logs, root `triage.json` / `reply.json`, moved-aside `eval.*` dirs, and the answer paths themselves (task id + repeat only; nothing clears `eval/`). Before every job the operator clears all of them on the host, for both arms. A repeat of a task the copy has seen is not independent; record the contamination.
- The runner scores the first parseable answer.json. A trial that rewrites its answer seconds later can get a different reward than the one recorded, and a few such first drafts can make up most of a paired delta. Rescore from the final files before you report a delta.
- Renaming `instructions.prepend.md` restarts the group, wakes every trial session, overwrites their `.claude-trace` files and adds spend. Snapshot the traces as soon as the runner exits.
- The reply-eval LLM judge sees only the reply text, marks any unevidenced "I reproduced this" as dishonest (pass@k 0 by construction), assumes no GPU/NVRTC/nvcc (the container has an L40S and CUDA 12.6) and calls post-filing fix PRs "invented". Fix the rubric's sandbox facts and freeze or explain later GitHub state before trusting `honest`.
- Reply tasks pin the filing day, but the local slang clone and build are newer (often already fixed) and shallow (about 36 commits). Never tell the reporter "already fixed" or "cannot reproduce"; reply from a code trace of the filing-day source. Read it with `git show <reporter-sha>:<path>` inside the window, else the GitHub API (`commits?until=` for the SHA, `contents?ref=` for a file, `commits?path=&until=` with `--jq length` for existence), or `git fetch --shallow-since` when the API returns 403. Verify a HEAD-reading subagent's "already fixed" yourself. When the reporter names a release, run that release's tarball `slangc` and cite source at `ref=v<ver>`.
- The filing-date pin works: on reply bank 6d0cb9a the "already fixed, upgrade" judge failures are gone (reply-baseline-20261022: 0.9765 mean reward, honest=0 on 2/60). Do not pair it with the 20261018 reply jobs.
- Measure a rubric change with `adapters.rejudge` on stored answers (about $0 agent cost); an instruction change needs a fresh job. Rejudge also rescues a trial left `unknown reward=None` by a judge HTTP 422 `budget_exceeded` on the shared gateway key (not the job cap; see `verifier/summary.json` → `reason`).
- `.claude-trace` jsonl lines are API request/response pairs: read `tool_use` blocks from assistant messages in `request.body.messages`, dedupe by id, and treat a 0 tool_use count as a parser bug.
- Sessions keep spending after they write their answer, so the cap overshoots (about 17% on a triage job). Set `--budget-usd` about 20% under the real hard limit.
- The queue runs r1 for every task first. A budget-stopped job has one repeat per task: its pass@k is pass@1, and it cannot be compared with a full 3-repeat job.

## Dispatch: `--group` is ignored inside a container

[`ncl tasks create --group <other-group-id>` run inside a coworker container creates the task on the caller's own group](../learnings/1792151064652-eval-runner-ncl-tasks-create-group-is-ignored-insi.md). `ncl tasks help create` says so: `--group` is for host callers and is auto-filled to your own group inside a container. This holds even with `cli_scope: global`, and the CLI returns ok with a session_id that belongs to the caller's group.

For `/eval-runner`, the `NclDispatcher` in eval_run.py then runs every trial in the driver group (eval-compliance: global scope, no `.overlay-eval-sandbox`). The eval group's sandbox is bypassed. The answers land in the driver's own `/workspace/agent/eval/`, and the runner, which polls the eval group's mount, times out on all of them. The pre-flight marker check passes but means nothing.

Detect it after the first dispatch: run `ncl sessions get <session_id> --json` (or `ncl cost-cap status --session <id>`) and compare `agent_group_id` with the eval group id. If they differ, stop the runner and run `ncl tasks cancel <series>`. Seen on 2026-10-16 on triage-baseline-20261016 (stopped after 2 trials) and on the concurrent eval-fixer-baseline job. The same auto-fill makes cross-group task reads return your own rows; see the ncl page under Related.

## The triage answer contract

[The bank's instruction.md asks for `triage.json` with a `rationale` key, but the gate prompt requires `/workspace/agent/eval/<task>/r<k>/answer.json` to hold exactly `subsystem`, `severity`, `next_step`, `labels`](../learnings/1792152729605-eval-triage-answer-json-must-hold-exactly-4-keys-l.md). Write both files. The four-key answer.json is the scored deliverable, and triage.json carries the rationale. [Labels outside the eval label list, such as the internal `Dev Opened`, do not belong in `labels`](../learnings/1792156489640-triage-eval-feature-issues-fixed-after-maintainer-.md).

The working-dir triage.json is not per trial. [The prompt's `triage.json` sits at `/workspace/agent/triage.json`, one file that every trial overwrites](../learnings/1792306470926-eval-triage-triage-json-in-the-working-dir-is-shar.md), so [at the start of a trial it can still hold the previous issue's answer](../learnings/1792306556116-eval-triage-workspace-agent-triage-json-is-left-ov.md); [one trial found it pre-filled with another task's subsystem, severity and next_step](../learnings/1792307204780-eval-triage-working-dir-triage-json-can-hold-anoth.md). All three cases were seen on 2026-10-18. Always overwrite it, never read it as input, and treat the per-trial answer.json as the only kept record. A reviewer who needs an earlier trial's rationale reads that issue's `memory/triage-<n>.md` memo. [When a task id is re-dispatched after its `eval/<task>/` dir was moved aside (to `eval.triage-baseline-<date>/`), the dir is gone; create it again before you write answer.json](../learnings/1792305223352-eval-re-dispatch-of-the-same-trial-id-finds-the-ea.md). [With no local slang checkout, read-only `gh api repos/shader-slang/slang/contents/<path>?ref=master` is enough to re-check source or CI-workflow facts](../learnings/1792307204780-eval-triage-working-dir-triage-json-can-hold-anoth.md).

[A Feature-type issue that a maintainer approves for implementation is `fix`, not `backlog`](../learnings/1792156519180-correction-in-eval-triage-trials-do-not-read-the-l.md). Apply that rule from the issue body and the design discussion, not from whether the issue closed COMPLETED.

## Answer-key leaks

Bank tasks are built from old shader-slang issues that are already closed upstream, so the live issue holds the answer the trial is scored against. [`gh issue view <n> --json labels,state` shows the maintainers' labels and how they handled the issue](../learnings/1792152716605-eval-triage-don-t-query-the-target-issue-itself-it.md), [and those labels are the scoring ground truth](../learnings/1792152729605-eval-triage-answer-json-must-hold-exactly-4-keys-l.md). [The label timeline (`gh api repos/shader-slang/slang/issues/<n>/timeline`), `stateReason`, and the linked PR's merge state belong to the same answer key](../learnings/1792156519180-correction-in-eval-triage-trials-do-not-read-the-l.md). Reading any of them contaminates the trial. [This happened on slang-13107#r1 and slang-13075#r1](../learnings/1792156580321-eval-triage-gh-issue-view-leaks-the-scored-answer.md). [A duplicate search can also surface the final labels and close state](../learnings/1792153490112-eval-triage-shared-wiki-recall-and-gh-issue-view-c.md), and [the eval copy's own note confirms that `gh issue view <n> --json labels` shows the scoring ground truth](../learnings/1792159750753-eval-runner-triage-cap-overshoot-r1-first-queue-an.md). If you see the outcome by accident, keep your own judgement and say in the work log or rationale that the ground truth leaked.

Subagents leak the same way. [A repro subagent told only "Do NOT touch GitHub except read-only downloads" still ran gh reads on the issue, the linked PR, the timeline and the compare API to explain its results (slang-13075#r1, 2026-10-18)](../learnings/1792306934765-eval-triage-tell-repro-subagents-not-to-read-the-i.md). A no-write rule does not forbid reads. Name the forbidden reads in every subagent prompt: "Do not run gh issue view, gh pr view, or gh api on issues, PRs, timeline or compare. Only gh release list and gh release download are allowed."

Two shared-knowledge paths leak as well. [The triage workflow requires a recall subagent, and it reads the shared wiki, whose approver and fixer learnings name the fix PRs of bank issues](../learnings/1792153490112-eval-triage-shared-wiki-recall-and-gh-issue-view-c.md). [In triage-baseline-20261016, 35 of 47 trials called append_learning into the shared learnings, and 32 of those notes named bank issues](../learnings/1792159750753-eval-runner-triage-cap-overshoot-r1-first-queue-an.md). Later repeats or variant jobs on the same bank can read them. [Shared wiki concept pages can also quote a maintainer's closing decision on a bank issue, so the mandatory recall step hands the eval copy the scored next_step and labels before any analysis (seen on slang-12916)](../learnings/1792306086806-eval-triage-reruns-are-contaminated-by-shared-wiki.md). [Reply trials hit the same path: the shared learnings hold resolution notes for bank issues such as #13073, the recall subagent can surface them, and the trial logs it when that happens](../learnings/1792649817653-local-release-slangc-in-eval-container-can-t-emit-.md). [The recall still has to finish before the draft: on one reply trial a draft endorsing a new CMake target was rewritten when the late recall returned the maintainer's answer to the same issue (no CMake change needed). Recall is cheap and can reverse a recommendation; for a CMake feature request, first check whether the consumer can already depend on the existing target names](../learnings/1792659215640-wait-for-the-recall-subagent-before-drafting-an-ev.md). In a scored trial such a hit is the answer key, so the trial logs it as contamination. Close both the live-label path and the shared-learnings path in the sandbox overlay, and strip issue-specific outcomes from the shared wiki, before you trust a variant-vs-baseline delta. Otherwise score those trials as contaminated.

### The eval copy's own folder carries earlier answers

The eval copy is a long-lived group, and its own folder keeps every earlier job's answers. [A re-dispatch of slang-12714#r1 two days after an earlier run of the same trial id found the earlier live labels in the memo `memory/triage-12714.md`, its index line and the shared wiki](../learnings/1792305223352-eval-re-dispatch-of-the-same-trial-id-finds-the-ea.md), [and slang-12916's memo listed the live labels too](../learnings/1792306086806-eval-triage-reruns-are-contaminated-by-shared-wiki.md). A repeat trial of an issue the eval copy has seen before is therefore not independent; the trial records the contamination in the memo and the work log so the runner can discount the score.

[On triage-rules-20261018 the operator moved `eval-slang-triage/eval/` aside, and the variant still had the baseline's answers](../learnings/1792310997428-eval-runner-clearing-eval-is-not-enough-eval-copy-.md). The group folder still held `memory/triage-<n>.md` (each memo records its "eval answer"), `tasks/eval-triage-*` logs, the root `triage.json`, and the moved-aside `eval.triage-baseline-20261016/` dir. Of 47 trial traces, 16 survived; all 16 read their own memo and old task log before writing answer.json, and 4 read the moved-aside dir. 40 of 47 answers matched the baseline's final answer on every scored field. [Reply trials leak the same way through the root `reply.json` and the old triage memos](../learnings/1792326383997-reply-eval-llm-judge-marks-every-i-reproduced-this.md). [Reply jobs also leave `tasks/eval-reply-*` logs in the eval group, and on reply-rules-20261022 2 of 60 trials read the previous job's log for their own issue](../learnings/1792661133852-reply-eval-judge-can-fail-on-the-shared-gateway-ke.md). Before a variant job, check the eval group folder for `memory/triage-*.md`, `tasks/eval-*` and `eval.*` dirs as well as the answer paths, and have the operator clear them on the host for both arms.

### Research order that keeps the judgement independent

1. Reproduce first on a release build. [Use `gh release download vX -p 'slang-X-linux-x86_64.tar.gz'`, with NVRTC from `/usr/local/cuda-12.6/lib64` when the repro needs CUDA](../learnings/1792153490112-eval-triage-shared-wiki-recall-and-gh-issue-view-c.md), [for example `gh release download v2026.19 --pattern '*linux-x86_64.tar.gz'` and then `bin/slangc`](../learnings/1792156580321-eval-triage-gh-issue-view-leaks-the-scored-answer.md).
2. [Research related issues and PRs and the source tree, and leave the target issue's own metadata alone](../learnings/1792152716605-eval-triage-don-t-query-the-target-issue-itself-it.md). [A shallow sparse clone gives a grep-able tree in seconds: `git clone --depth 1 --filter=blob:none --sparse`, then `git sparse-checkout set source/slang`](../learnings/1792152729605-eval-triage-answer-json-must-hold-exactly-4-keys-l.md).
3. Decide the classification from the prompt text, the repro and the source.
4. Only then, if at all, look at live issue state. If you did, record in the memo that the trial was contaminated.

## Runner scoring hazards: stale and rewritten answers

[The triage answer path `eval/<task>/r<k>/answer.json` depends only on task id and repeat, so every job on the same eval group and bank uses the same files](../learnings/1792164298690-eval-runner-a-second-triage-job-scores-the-first-j.md). `poll_triage()` in eval_run.py accepts any answer.json that parses, with no mtime check, and nothing clears `eval/` between jobs. A variant job run after a baseline job therefore "scores" the baseline's answers about 30 s after each dispatch. A fake-dispatch simulation reproduced the baseline rewards exactly. The fast scoring also lets the runner start every session within minutes, so the budget cap does not hold.

Pre-flight for every job: after `--dry-run`, check whether any planned answer path already exists under `/workspace/extra/ephemeral/prod-groups/<folder>/eval/`. If one does, the operator must move `groups/<folder>/eval/` aside on the host first, because the mount is read-only from the driver. Moving `eval/` aside is necessary but not sufficient; the memos, task logs and moved-aside dirs in the same folder leak too (see the section above).

A related race: the runner scores the first parseable version of answer.json. In the baseline, 6 of 47 trials rewrote their answer seconds later, and 3 of those rewrites changed the reward. Evidence: `reports/evals/triage-rules-20261016/STOPPED.md` in eval-compliance. [On triage-rules-20261018 the runner's +0.027 paired delta came mostly from 3 baseline first drafts scored before their rewrite; with final-file scores the delta is +0.007 [−0.007, 0.023]](../learnings/1792310997428-eval-runner-clearing-eval-is-not-enough-eval-copy-.md). Rescore both arms from the final files before you report a delta.

[Renaming `instructions.prepend.md` after a job restarts the group. The restart wakes every trial session, overwrites their `.claude-trace` files and adds spend ($55 → $65 on that job)](../learnings/1792310997428-eval-runner-clearing-eval-is-not-enough-eval-copy-.md). Snapshot the traces as soon as the runner exits. `ncl cost-cap status` takes about 9 s per call and fails under parallel calls; one `ncl cost-cap sessions --group <g> --sessions` call reads every session instead.

[Each line of `.claude-trace/session-<sid>.jsonl` is one API call, `{request, response, logged_at}`, not a session event](../learnings/1792428257180-eval-traces-claude-trace-jsonl-is-api-request-resp.md). The trial's tool calls are the `tool_use` blocks inside `request.body.messages` with `role == "assistant"`; every request repeats the whole history, so dedupe by tool_use `id`. A parser written for the Claude Code session-jsonl shape (top-level `message.content`) silently returns zero hits for everything, so count tool_uses per trial and treat any 0 as a parser bug. The same note: a group's `instructions.prepend.md` reaches the composed CLAUDE.md (under `## Additional Instructions`) only when the next container spawns, so check that a variant reached the agents by grepping CLAUDE.md after the first trial is `container_status=running`, not before.

## Reply tasks: the LLM judge's `honest` score has wrong premises

[In slang-eval-tasks reply tasks (bank fc5802c), the Opus judge sees only the reply text, the issue and the maintainers' reply](../learnings/1792326383997-reply-eval-llm-judge-marks-every-i-reproduced-this.md). In reply-smoke2-20261018 it set honest=0 on all 3 trials, each time because the reply claimed a reproduction or a source read "with no evidence", although the traces show each trial really ran slangc/nvcc or read the source. Pass needs reward >= 1.0 (0.5×STE + 0.5×judge), so the best reward for a reply that reports a repro is 0.8334 and pass@k is 0 by construction.

The judge also carries two false premises about the sandbox. [On reply-baseline-20261018 (bank 4e12409, 60 reply tasks, Opus 5.5) it set honest=0 on 20 of 59 replies](../learnings/1792407294620-reply-eval-judge-bank-4e12409-wrongly-assumes-no-g.md). 11 were GPU/NVRTC/nvcc results "the assistant could not have run", because the rubric says "no GPU, no NVRTC, no nvcc"; the eval container has an L40S and `/usr/local/cuda-12.6`, and every one of those traces really ran `slangc -target ptx` or nvcc with matching output. 13 (4 overlapping) were fix PRs or releases called "invented"; every cited PR exists (8 merged, 1 open), because trials read live GitHub and see fixes merged after the maintainers' first reply. So give the judge the sandbox's real tools, and either freeze GitHub at the issue date or tell the judge later PRs can be real, before trusting `honest`.

A rubric change can be measured without new trials. [slang-eval-tasks 14b1af4 (`fix/reply-rubric-sandbox`) adds `python3 -m adapters.rejudge <job_dir> <out_dir> --bank <bank>`, which re-scores the stored `answer` of each scored trial in trials.jsonl with the current reply_scorer](../learnings/1792550035071-reply-eval-rejudge-stored-answers-to-measure-a-rub.md): one judge call per trial, about 4/min, about $0 agent cost. With the corrected sandbox rubric (GPU/NVRTC/nvcc can exist), reply-baseline/rules-20261018 mean reward rose from 0.9175/0.8945 to 0.9373/0.9472 and honest=0 fell from 20/24 to 11/9, with no GPU false positives left. Most remaining failures are "already fixed in vX, upgrade" claims written before the instruction pinned the filing date; only a fresh job can measure that instruction change, because rejudging reuses the old answers. [That fresh job confirmed it: reply bank 6d0cb9a ("Treat the day the report was filed as today") removed the "already fixed / upgrade" failures, and reply-baseline-20261022 on eval-slang-triage scored 0.9765 mean reward with honest=0 on 2 of 60, for $79.38 at 60×1](../learnings/1792653207139-eval-runner-setsid-pid-trap-and-date-pinned-reply-.md). Do not pair it with the 20261018 reply jobs, because the bank and the group state differ. Gotcha: stdout is block-buffered under `| tee`, so run.log stays empty until the end; watch the `<out_dir>/*/summary.json` counts instead.

[A judge call can also fail on the shared LiteLLM gateway key's budget: on reply-rules-20261022 two trials stayed `unknown` because the Opus judge got HTTP 422 `budget_exceeded` (the key's max budget, not the job's `--budget-usd`; it cleared within about 3 minutes). The runner log shows `unknown reward=None (verifier exited 0 and wrote no reward)`, and `trials/<trial>/verifier/summary.json` → `reason` names the error. The answers stay in trials.jsonl, so `adapters/rejudge.py` re-scores them without a new dispatch](../learnings/1792661133852-reply-eval-judge-can-fail-on-the-shared-gateway-ke.md).

## Reply tasks: read the tree as of the filing date

The reply task tells the trial to treat the filing day as today, but `/workspace/agent/slang` and its prebuilt `slangc` are newer than the issue and often already contain the fix (seen on many bank issues). [Read the code the reporter had with `git show <reporter-sha>:<path>` and check each claim against it. A subagent that reads HEAD will report "already fixed", so confirm against the reporter's SHA yourself](../learnings/1792656169935-eval-reply-tasks-read-code-at-the-reporter-s-commi.md). When the local build does not reproduce, [write the reply from a code trace of the filing-day source and never say "cannot reproduce" or "already fixed". Check whether a surprising observation in the report is correct output before you call it a bug](../learnings/1792659192196-eval-reply-tasks-local-checkout-may-already-contai.md). [The checkout can still explain the emit path, but HEAD's code and docs are not the reporter's state](../learnings/1792645528183-eval-reply-tasks-local-slang-checkout-is-newer-tha.md); [describe the behavior the report shows and propose the change as future work](../learnings/1792657654267-reply-eval-local-checkout-can-already-hold-the-fix.md).

When the reporter names a release, test against that release, not HEAD. [`gh release download v<ver> -R shader-slang/slang -p '*linux-x86_64.tar.gz'` gives the reporter's `slangc` for the repro and the workarounds, and `gh api -H 'Accept: application/vnd.github.raw' 'repos/shader-slang/slang/contents/<path>?ref=v<ver>'` gives the source to cite. Reading a release is not an answer-key leak](../learnings/1792649952649-reply-evals-the-local-checkout-can-already-contain.md). [When only the source is needed, `curl -sL https://raw.githubusercontent.com/shader-slang/slang/<tag>/<path>` and a grep is enough; the local build then only checks a workaround](../learnings/1792654419588-eval-reply-tasks-check-the-reported-release-tag-no.md). The release-tarball mechanics, and why the container's local `slangc` needs `-target hlsl` for semantic checks, are on [Reproducing version-specific Slang bugs with release tarballs](slang-tooling-release-tarball-repro-and-version-bisect.md).

The clone is shallow (about 36 commits), so `git show` works only for a SHA inside that window. [For an older SHA, take the commit current at filing from `gh api "repos/shader-slang/slang/commits?until=<createdAt>&per_page=1" --jq '.[0].sha'` and read a file at it with `gh api "repos/shader-slang/slang/contents/<path>?ref=$SHA" --jq .content | base64 -d`. On #12962 the filing-day tree differed from HEAD on every point the reply cited](../learnings/1792656918126-shallow-slang-clone-read-files-as-of-the-filing-da.md). [Local `git log` misleads as well: it shows every file as "added" on a recent squash date. For one path, `commits?path=<p>&until=<ISO>&per_page=1` gives the version current at filing; confirm each claim (schedules, thresholds, which tools existed) against that version](../learnings/1792656858019-reply-eval-12960-r1-fetch-the-filing-date-file-ver.md). [The same query with `--jq length` returns 1 if the file existed at filing and 0 if it was added later; a filing-day reply must not cite a file that returns 0](../learnings/1792648587526-check-what-existed-at-issue-filing-date-via-gh-api.md). [When the REST API hits the installation rate limit (HTTP 403), deepen the clone instead: `git fetch --shallow-since=<a few days before filing> origin master`, then `git rev-list -1 --before=<createdAt> FETCH_HEAD`. Without the fetch, `git rev-list --before` silently returns HEAD](../learnings/1792658128456-eval-reply-tasks-the-local-slang-checkout-is-shall.md).

[When the fix landed inside the window, `git log --oneline -S"<symbol>" -- source/slang` finds it, and `git show <fix>^:<path>` reads the code before the fix; describe the cause from that state. Repro tip from the same trial: `slangc file.slang -target hlsl -o out.hlsl` fails with E00070 when no `-entry` is given, so emit to stdout](../learnings/1792660653677-eval-reply-tasks-local-master-may-already-contain-.md). [A fix older than the window is invisible to `git log -S`, which then cannot date it](../learnings/1792657654267-reply-eval-local-checkout-can-already-hold-the-fix.md); deepen the clone or use the API reads above. These code-tree reads do not touch the answer key (the target issue's labels, timeline or linked PRs). The general date-and-revision rules are on [Version and timestamp reads](general-misc-version-and-timestamp-reads.md).

## Budget cap and queue order (triage)

[Numbers from triage-baseline-20261016 (bank e565453, eval-slang-triage on Opus 5.5)](../learnings/1792159750753-eval-runner-triage-cap-overshoot-r1-first-queue-an.md): a triage trial costs about $1.49 and takes a median of about 3.5 min. `--budget-usd 60` stopped dispatch after about 47 trials. 60 tasks × 3 repeats need about $270.

The runner counts each session's cost at score time, but sessions keep spending after they write answer.json (wrap-up, append_learning). The final spend was $69.96 against the $60 cap, about 17% over. Set the cap about 20% under the real hard limit.

The queue runs r1 for every task first. A budget-stopped job therefore has one repeat per task. Its pass@k is pass@1, and it cannot be compared with a full 3-repeat job. Fixer trials cost much more per trial, and `ncl cost-cap status` under-reads spend after a restart; see the fixer page under Related.
