## TL;DR

Almost every text you are handed — a PR body, an issue body, a checkbox, a "ported to X" banner, a "not ours to fix" verdict, an assignee field — is a claim *about* a specific artifact at a specific ref/time. Resolve the reference and re-derive from primary source; a stale claim reads as the *safe* one and terminates inquiry while wearing the clothes of diligence.

- **Verify head yourself; don't transcribe the handoff.** A stale claim can be *partly* true ("only this one was actually removed" beats a flat "the claim was wrong"), and a stale figure can be *arithmetically correct* at head — check before calling a number wrong.
- **A file path / checkbox / present-tense verb in an issue is a claim about a REF.** Resolve it on `master` *and* the referenced PR head; a bot can write in the present tense about unmerged code.
- **"Not ours to fix" / "not agent-actionable" is a self-sealing verdict** — nobody re-derives a dead end, so it silently becomes ground truth. Hold it to a bug-claim evidence bar: name the field, name the check.
- **A per-item property checked on one item is how a wrong "all"-claim hides** — the newest artifact reading clean while `any()` over the set fails.
- **Sweeping a class can destroy its one TRUE member** — classify each member, never bulk-replace.

## Verify head yourself; the stale claim can be partly true

When told a PR description has gone stale, re-derive **every** claim from the source at head instead of transcribing the handoff — even a careful handoff can miss a nuance that changes the correction. On slangpy#1078 a "guards removed from three tests" claim was framed as 0/3 true; reading `git show <head>:...` showed it was **1/3 true** (one test genuinely has no guard and passes on Metal), and "only this one was actually removed" is more useful to a maintainer than a flat "wrong." Related discipline from the same case: a stale figure can be *arithmetically correct at head* ("36 passed, 2 skipped" survived three commits because the new guards fire only on backends a Linux run doesn't exercise) — check before calling a number wrong; keep the *historical* issue reference (it explains the retarget); and before asserting a sibling PR "fixes" something, fetch its state (`gh pr view --json state,isDraft,body`) ([Stale PR bodies: verify head yourself, and check whether a "removed guard" claim is partly true](wiki/learnings/1785857581077-stale-pr-bodies-verify-head-yourself-and-check-whe.md)).

## An issue's file paths, checkboxes, and present-tense verbs are claims about a ref

**A bot-filed issue can be written in the present tense about UNMERGED code.** On slang#12339, an issue named a function and a test file that existed only on an open *draft* PR — `git grep <symbol> HEAD` → 0 (non-zero control → 9), neither cited test file present on master. The claims were specific, correctly spelled, cited real line numbers — they read as *more* verified than vague prose. The issue was written from inside the PR's working context, where the files genuinely exist; present tense was true for the author and false for every later reader. **The word "now" is a tell** ("the resolution *now* does X" — now on which ref?); resolve each cited path with `git ls-tree -r --name-only <ref>` on master *and* the PR head ([A bot-filed issue can be written in the present tense about UNMERGED code — check the branch before triaging its claims](wiki/learnings/1785945785507-a-bot-filed-issue-can-be-written-in-the-present-te.md)).

**An unchecked ticket checkbox is a claim about the checkbox, not the code.** Scrubbing slangpy#768 (four items, all boxes empty), not one state matched what the empty boxes implied: item 1 was fully implemented (landed a month after filing, nobody revisited to tick it), items 2–3 existed but in the very path the issue said to *retire* rather than the one it asked to port *into*, and item 4's capability worked while its *specified mechanism* was absent (the token had 0 hits in implementation, all 29 in tests). Check each box against source independently; check *which path* the capability lives in, not just whether it exists; separate capability from specified mechanism (grep implementation vs tests separately); date features with `git log -S` *after* confirming the clone isn't shallow; and verify handed leads before repeating them (a plausible lead that matches your expectation is the one you'll forget to check) ([An unchecked ticket checkbox is a claim about the checkbox, not the code](wiki/learnings/1785959982102-an-unchecked-ticket-checkbox-is-a-claim-about-the-.md)).

**A merged "disable the flaky test" PR title is a claim you must diff against the failure set.** slangpy PR #1076 "Temporarily disable intermittent profiler tests" applied `skip()` to cases at `:332`/`:598` — but the cases actually failing in CI were `:228`/`:511`, a *disjoint set*, because the mitigation was written from the root-cause *issue* rather than from the *logs*. The flake continued for 8 days while everyone read the title and assumed it was handled (evicting approved slang PRs from the merge queue via a required cross-repo status). When a "disable the flaky test" PR merges, diff the set it disabled against the set observed failing; and prefer `doctest::may_fail()` over `skip()` for a flaky-but-meaningful test — `may_fail` still runs and prints the case, so a mis-target stays visible instead of silently invisible ([A test-disabling mitigation can skip the wrong cases — verify the skip set against the failure set, not the issue title](wiki/learnings/1785891583972-a-test-disabling-mitigation-can-skip-the-wrong-cas.md)).

**A "duplicated, ported to X" banner is a claim about ANOTHER repo** — always open the named counterpart. A slang test defers to a slang-rhi file that has been `#if 0 // TODO port` with **zero test cases for ~2 years**: two files can each point at the other as the live one and both be dead. Combined with the `#if 0` inner-block census trap and the shallow-clone provenance caveat, this triage produced "9 of 11 genuinely ported, 2 dead" where the naive instrument would have alleged a systemic 12-file hole ([A "duplicated, ported to X" banner is a claim about ANOTHER repo — check whether X is live, counting cases outside the disabled region](wiki/learnings/1785960800819-a-duplicated-ported-to-x-banner-is-a-claim-about-a.md)).

**Verify the assignee field; don't inherit it from the request.** Asked to scrub an issue because "assignee X has stepped away", the actual sole assignee was someone else — X had reassigned it and unassigned himself five months earlier. The requester describes an *org change*, not a field value; `gh issue view --json assignees` gives current state, `.../issues/N/timeline` gives the `assigned`/`unassigned` events that explain *why* it moved. An orphaned-work sweep needs an explicit negative (enumerate every remote branch by the departing author — a branch with *no PR at all* won't surface from any PR listing), and a sibling bot session's overlapping conclusion is a *lead, not evidence* ([Staleness scrubs: verify the assignee field, don't inherit it from the request](wiki/learnings/1785958453635-staleness-scrubs-verify-the-assignee-field-don-t-i.md)).

## Self-sealing verdicts: "not ours to fix"

**"Not agent-actionable" / "not ours to fix" needs the same evidence standard as a bug claim.** slangpy PR #1054 sat blocked three weeks on a pending `license/cla` check recorded as "an org-side allowlist matter, awaiting a maintainer" — asserted, propagated across four roll-ups, never checked. One API call settled it: 7 of 8 commits were authored under a bare *User* identity instead of the bot *App* identity — entirely ours to fix, and re-authoring flipped the check the instant the history landed. This class is uniquely expensive because a wrong bug claim gets caught when something downstream fails, while a wrong "someone else must fix this" *ends* inquiry: it reads as diligence, it is self-sealing (every echo makes it more established without adding a check), and nobody re-derives a dead end. Cheap detectors: *can you name the field?*, *did the mechanism ever get stated?*, *watch for a blocker that never changes state* — age is a smell, re-derive on a timer not a nudge ([A blocker labeled "not agent-actionable" needs the same evidence standard as a bug claim](wiki/learnings/1785887980846-a-blocker-labeled-not-agent-actionable-needs-the-s.md), ["Not ours to fix" is a self-sealing verdict — hold it to the same evidence bar as a bug claim](wiki/learnings/1785892420987-not-ours-to-fix-is-a-self-sealing-verdict-hold-it-.md)).

Two instrument corollaries recur across this CLA chain and belong with any staleness scrub:

- **A symbol-level grep misleads in both directions.** `main` had a `requires_grad` field and `API_VERSION 8`, so the fix looked landed-and-superseded — but the field was in the extraction struct, not the cache signature the bug keys on. Grep the *use site that matters*, not the symbol's presence (same superseded-PR incident cited below).
- **Positive-control an absence before believing it**, and check the whole set: a grep returning empty read as "the fix isn't there" when the real cause was an unfetched git object (`git cat-file -t <sha>` → `Not a valid object name`); and `[.[].author.id] | unique` over *all* commits catches a bad-identity run that a check of only the newest (App-authored) commit misses. **A per-item property checked on one item is the standard way a wrong "all"-claim hides.**

Before paying an expensive unblock (a force-push that dismisses an approval, a risky rebase), first check whether upstream already changed the code — the cost/benefit you were handed may be stale. slangpy#1054 had started *conflicting with main* (a later PR rewrote the same code), which dissolves a "just rewrite commit identities" plan; and a superficial symbol grep gives the wrong answer *both* ways. Report a branch-protection risk you *cannot* read (`403 Resource not accessible by integration`) as an unverified risk rather than asserting it ([Check whether a stalled PR was superseded before paying any cost to unblock it](wiki/learnings/1785887439570-check-whether-a-stalled-pr-was-superseded-before-p.md)).

## The corollary that saved several of these: audit credit and self-reports too

**Cross-container claims are symmetric** — never publish a peer's filesystem figure as measured, and never record their quotation as *verified*; mark it **attributed**. The receiving half is what lets a bad figure into your store wearing the label "confirmed", and the dangerous case is exculpatory evidence that ends an uncomfortable thread (developed in full on the correction-discipline page).

**A path-addressed observation is scoped to one container at one moment** — existence, size, mtime; only the *mechanism* generalizes. When one agent found no worktree-claim sentinel and framed it as an architectural hole, a peer reported `active-work/` didn't exist in *its* container at all — and checking its own container *inverted the diagnosis*: the directory existed with 37 claims on a shared volume, so the mechanism worked and the real defect was *compliance* (a live session pushed a shared branch with no claim). Had either generalized from one container, the real defect would have been invisible. The correct form of such a report is the peer's: *"I can't settle this from here; the mechanism is worth checking on your side."* And every collision signal is point-in-time — check three (sentinel, `git status` in the target tree, reflog vs your own history), because each misses a different collision shape, and a quiet reading licenses *proceeding carefully*, never *concluding the target is unowned* ([CORRECTION — the worktree sentinel mechanism WORKS and is shared; the gap was compliance. Check three signals, not one](wiki/learnings/1785869801803-correction-the-worktree-sentinel-mechanism-works-a.md)).

**Sweeping a class can destroy its one TRUE member.** A peer found three post-refutation seals in one file, retracted two as rotten, and was one command from deleting the third — which was *right*, while its own newer "solved" line was the over-wide one. What separated them was measuring the specific claim, not matching the pattern: a seal after its refutation is *suspicious, not condemned* — classify each member, never bulk-replace (the sweep's momentum supplies false confidence, like the recipe-vs-description split that spares the occurrence *describing* a defect). And **a relayed claim can arrive one notch wider than the sender's evidence**: an adopted "the unit is codepoints/1024" overwrote the author's own *measured* narrower caveat ("codepoints vs UTF-16 indistinguishable; only BYTES is decisively rejected") that sat 56 lines away — when a peer's claim lands on a topic your store already covers, diff it against your own note before adopting, because adoption *feels* like corroboration when it is overwriting ([Sweeping a class can destroy its one TRUE member - and a relayed claim can arrive one notch wider than the sender's evidence](wiki/learnings/1785960857081-sweeping-a-class-can-destroy-its-one-true-member-a.md)).
