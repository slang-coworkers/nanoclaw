# Reviewer Pipeline Operations

How the approver *sources* its review input: harvesting the production (PRIMARY) review, polling for it to settle, reading Devin (Reviewer B) coverage, distinguishing skipped from pending check-runs, and consuming a delegated reviewer-coworker's review doc. It also covers running Reviewer A and C from the coordinator (run isolation, guard false positives, stub and hung runs) and verifying Reviewer A's claims before relaying them. These are the mechanics of the review-input pipeline that feeds the decision — separate from the decision itself (see [approver and CI operational notes](review-pr-approver-and-ci-operational-notes.md)).

## TL;DR
- **`harvest-reviews.py` exit 0 is not "the PRIMARY review was read."** The secondary bot (`coderabbitai[bot]`) is fast and posts first; a clean exit can mean the harvest selected the secondary while the primary `github-actions[bot]` production review was still `in_progress`. Confirm which tier was harvested before deciding.
- **When the primary review is still in flight, WAIT and RE-HARVEST — do not settle for the fallback tier.** A fresh production review can post minutes after your first harvest and flip both the tier and the severity of a synchronize revision.
- **A STALE-only first harvest is recoverable.** Exit-10 (STALE ONLY) after a fresh master-merge push means the newest primary review is against the pre-merge commit; re-harvest at the settled head recovers a head-current PRIMARY.
- **`skipped` ≠ `pending`.** The skipped `Claude Code Assistant` check-run is NOT the `Claude PR Review` job; confirm the actual workflow state via `gh run view` before concluding the production review is absent and falling to a lower tier.
- **Devin commit-status `unknown` ≠ "up to date."** After a synchronize, an `unknown` status may mean Devin's analysis does not cover the settled head — treat it as uncovered, not clean.
- **A delegated reviewer-coworker doc must carry `commit_id` + `_approver_result`.** Omitting either makes `commit_match` unevaluable and forces ABSTAIN_INFRA — a pure staging defect that can cost a decision on an otherwise-clean PR.
- **A staging/infra defect is fixed at the producer, not worked around downstream.** The commit_id-omission was resolved by retiring the delegate path (Option 1), not by an open "stamp the handoff" task.
- **Patch-mode review runners used `git commit -am`, which drops files the patch creates** (usually the regression test) from the reviewed diff and leaves them untracked in the shared checkout. Both runners now stage with `git apply --index` (local patch, 2026-09-29); verify with `git log -1 --stat` on the temp branch, run Reviewer A in its own worktree when the shared checkout is dirty, and don't treat an early fixer attachment as a review request.
- **Isolate every Reviewer A run in a private `REPO_ROOT` worktree.** Concurrent runs on the shared checkout still clobber each other's staged diff (Oct 2026). An INTEGRITY-FAIL can also be a false positive from a later concurrent overwrite or a 100%-similarity rename; sha-match `pr-diff.reference` against `gh pr diff` before discarding a review.
- **On claude 2.1.296 the inner lead routinely ends its turn with its subagents in the background, leaving a stub.** Salvage completed `task_notification` summaries, then dispatch the REVIEW.md lenses yourself and report `reviewers_complete=false`.
- **`run-clarity.sh` can hang silently** (idle CPU, no stream events, no `.done`); detect it by stream mtime plus a CPU-time delta, kill it, and substitute A's in-run clarity candidate pass.
- **Verify A's claims before relaying them:** reproduce "traced, not reproduced" findings under `ulimit`+`timeout` on head and merge-base builds (the shared checkout's build can be weeks stale), confirm "CI green" is not an all-skipped run, and map each commit to the review round that actually covered it.

## Harvesting the production (PRIMARY) review: tiers, polling, and re-harvest

The harvest step selects a review to feed the decision from a tiered set: the PRIMARY production review (`github-actions[bot]`, the claude-code-action job) is preferred; `coderabbitai[bot]` is a SECONDARY fallback. The trap is that a clean exit code does not tell you which tier you got. On a freshly-opened PR the secondary posts first (CodeRabbit is fast), so `harvest-reviews.py` can return exit 0 having harvested CodeRabbit while the primary production review's check-run is still `in_progress` — the correct response is to WAIT and re-harvest for the primary, never settle for the fallback tier ([[approver/infra-abstain] harvest exit-0 on SECONDARY (CodeRabbit) while production review check-run still in_progress = wait + re-harvest, don't settle for fallback tier](../learnings/1784113859103-approver-infra-abstain-harvest-exit-0-on-secondary.md); [[approver/infra-abstain] harvest exit-0 can pick CodeRabbit secondary while the primary prod review is still in_progress — re-harvest, do not settle](../learnings/1784117112458-approver-infra-abstain-harvest-exit-0-can-pick-cod.md)).

The same "harvest too early" hazard bites on a synchronize revision: harvesting right after the debounced settled head can find only the STALE R1 production review and fall to CodeRabbit fallback, when a fresh production review posts minutes later and would flip the tier (and severity). Re-harvest before deciding a synchronize ([[approver/critique-mustfix] Re-harvest before deciding a synchronize revision — a fresh production review can post minutes after your harvest and flip the tier (and severity)](../learnings/1784149553897-approver-critique-mustfix-re-harvest-before-decidi.md)). A STALE-only harvest is not a dead end: after a fresh post-master-merge head, the first harvest can return exit-10 (STALE ONLY) because the newest `github-actions[bot]` review targets the pre-merge commit — re-harvesting at the settled head recovers the head-current PRIMARY (the slang#12064 class, exit-10 variant) ([[approver/challenger-miss] Re-harvest recovers head-current PRIMARY after a STALE-only first harvest (slang#12064 class, exit-10 variant)](../learnings/1784166433977-approver-challenger-miss-re-harvest-recovers-head-.md)).

## Distinguishing a skipped check-run from a pending one

Before falling to a lower reviewer tier on the belief that the production review is absent, confirm the actual job state. The skipped `Claude Code Assistant` check-run is NOT the `Claude PR Review` job — a skip on one is not evidence the other did not run. Confirm via `gh run view` on the workflow before treating "review skipped" as "review pending" and downgrading the tier ([[approver/infra-abstain] 'review skipped' vs 'review pending' — the skipped `Claude Code Assistant` check-run is NOT the `Claude PR Review` job; confirm via `gh run view` on the workflow before falling to a lower tier](../learnings/1784126153691-approver-infra-abstain-review-skipped-vs-review-pe.md)).

## Devin (Reviewer B): commit-status coverage after a synchronize

`devin-fetch.sh` can return exit 0 with a commit-status of `unknown` — which is NOT the same as "Analysis is up to date." After a synchronize adds new content (e.g. a large test migration on top of the original code), an `unknown` status means Devin's analysis may not cover the settled head. Treat unknown as uncovered rather than clean, and re-verify at the current head ([[approver/challenger-miss] Devin commit-status unknown means it may not cover the settled head after a synchronize](../learnings/1784156846935-approver-challenger-miss-devin-commit-status-unkno.md)).

## The delegated reviewer-coworker doc contract (commit_id / _approver_result)

When a reviewer-coworker (a delegated reviewer) produces the review doc the approver consumes, that doc must carry the contract-required `commit_id` and `_approver_result` fields. Omitting either leaves `commit_match` UNEVALUABLE, which forces ABSTAIN_INFRA — a purely mechanical staging defect, not a finding about the code ([[approver/infra-abstain] reviewer-coworker review-doc omits contract-required commit_id + _approver_result → commit_match UNEVALUABLE → ABSTAIN_INFRA](../learnings/1784186159657-approver-infra-abstain-reviewer-coworker-review-do.md)). The calibration cost of that defect is concrete: the commit_id-omission ABSTAIN on slang#12055 merged-APPROVED at the exact decided head with the gap merged over — the staging defect spent a decision on a clean PR ([[approver/infra-abstain] JOIN: commit_id-omission infra-abstain (slang#12055) merged-APPROVED at exact decided head, gap merged over — the staging defect cost a decision on a clean PR](../learnings/1784197707754-approver-infra-abstain-join-commit-id-omission-inf.md)). The right resolution is at the producer, not a downstream workaround: the slang#12055 commit_id-omission was FIXED via Option 1 (the delegate path was retired), NOT left as an open "stamp the handoff" task ([[approver/infra-abstain] CORRECTION+SUPERSEDES — slang#12055 commit_id-omission abstain is FIXED via Option 1 (delegate path retired), NOT an open 'stamp the handoff' task](../learnings/1784197928722-approver-infra-abstain-correction-supersedes-slang.md)).

## Patch-mode reviews: new files, a dirty shared checkout, and early attachments

Three traps surfaced in the slang#13273 session (2026-09-27). First, patch mode leaves out new files: `slang-pr-review-runner/scripts/compose-and-run.sh:113` and `slang-clarity-review-runner/scripts/run-clarity.sh:185` both run `git apply` and then `git commit -am`, and `-a` stages only tracked files, so a file the patch creates (usually the new `tests/...slang` regression test) stays untracked and is missing from the diff Reviewers A and C review; after applying `fix-13273.patch`, `tests/bugs/gh-13273.slang` was still `??`. The fix is to stage the patch through the index. On 2026-09-29 both scripts were patched locally (backups at `*.bak-20260929`) to `git apply --index --whitespace=nowarn "$PATCH_FILE"` followed by `git commit -q -m ...`; since that is a local edit to the installed skill copy, check each run rather than assume it: `git log -1 --stat` on the temp branch must list the new test files ([clarity/review runner patch mode dropped NEW files; fixed with git apply --index](../learnings/1790689917834-slang-pr-review-runner-clarity-runner-patch-mode-d.md)). Second, the same bug leaks: the untracked files a patch created stay behind in `/workspace/agent/slang` after the run (6 such leftovers were found on 2026-09-29), and later `origin/master` checkouts then fail with "untracked working tree files would be overwritten". That is why Reviewer A's patch mode aborts within seconds when the shared checkout holds untracked files that also exist on `origin/master`: `git checkout -b patch-review-* origin/master` refuses to overwrite them. Run it in its own worktree instead (`git worktree add --detach /workspace/agent/wt-<N>-revA origin/master`, then `REPO_ROOT=/workspace/agent/wt-<N>-revA compose-and-run.sh ...`), and leave the untracked files alone, since they belong to someone else. Third, an attachment from slang-fixer is not a review request unless the message says so: the fixer sends the patch and PR body ahead of time while its codex-critique gate is pending, and the auto-route hook still starts `/slang-pr-review`, so read what the message asks for before starting; the explicit request follows once the gate clears [slang-reviewer: patch mode drops new files; unrequested fixer attachments aren't review requests](../learnings/1790504316526-slang-reviewer-patch-mode-drops-new-files-unreques.md). A container restart during any of this kills the background reviewer and build processes; relaunch them and keep the turn open until they finish (see [run survival](review-pr-reviewer-run-survival.md)).

## Reviewer A run hygiene: isolation, guard false positives, and stub runs (Oct 2026)

**Concurrent A runs on the shared checkout review the wrong PR.** `compose-and-run.sh` defaults `REPO_ROOT=/workspace/agent/slang` and, at start, `rm -f`s and re-stages `tmp/{pr-diff.patch,pr-files.txt,context.json}` there, so a second session's A run deletes and overwrites the first run's diff mid-flight. It was still recurring in October 2026: on 2026-10-10 #13561 (03:56) was clobbered by #13562 (04:01), and a day earlier a clobbered run cost ~$24 and 2.5 h before anyone noticed. The post-run guard catches it with `INTEGRITY-FAIL: reviewed diff != PR N files` plus `REVIEW-GUARD FAIL: final review is <500 bytes`, but only after the money is spent. Prevention is a private master worktree per A run: `git -C /workspace/agent/slang worktree add -f --detach /workspace/agent/wt-<pr>-revA origin/master`, then `REPO_ROOT=/workspace/agent/wt-<pr>-revA bash …/compose-and-run.sh --mode pr …`. The script honours `REPO_ROOT`, and REVIEW.md plus `.claude/agents` come along with the checkout; Reviewer C already isolates itself in `wt-clarity-*` ([concurrent A runs clobber each other in the shared checkout (#13561/#13562)](../learnings/1791605773844-slang-pr-review-runner-concurrent-reviewer-a-runs-.md)). The full history and adjudication recipe is on [Reviewer-A integrity & concurrency](review-process-f0909b0-reviewer-a-integrity-concurrency.md).

**An INTEGRITY-FAIL is not proof the review is wrong.** The guard compares whatever the shared `tmp/pr-diff.patch` holds at exit, not what the run actually read. On #13562 R2 a #13570 run started ~25 min later re-staged the shared files, and a valid review exited with INTEGRITY-FAIL. Triage before discarding: (1) read `<run_dir>/INTEGRITY-FAIL.txt` and `cat $REPO_ROOT/tmp/context.json`; if `pr` names another PR, compare its mtime with your run's start; (2) check that the `final-review.md` footer `diff sha256` matches `gh pr diff <N> | sha256sum` and that `<run_dir>/pr-diff.reference` hashes the same; (3) grep `stream.jsonl` for the foreign PR's files (on #13562 one subagent noticed the swap after a context reset and labelled its output with a provenance warning). If all three check out, keep the review and say so in the report rather than spend another ~$24 re-running ([INTEGRITY-FAIL false positive from a concurrent overwrite of slang/tmp (#13562)](../learnings/1791679608034-reviewer-a-integrity-fail-can-be-a-false-positive-.md)).

**A pure rename trips the same guard with no concurrency at all.** The guard (around `compose-and-run.sh:189`) builds the reviewed file list from `+++ b/` lines and compares it with `gh pr view --json files`. A `similarity index 100%` rename has no `+++ b/` line, so #13541 (a `findings/*.yaml` moved into `findings/filed/`) reported "review targeted the WRONG diff" for a correct review. Compare the sha256 of `<run_dir>/pr-diff.reference` with `gh pr diff <N>`; if they match and `INTEGRITY-FAIL.txt` differs only by renamed paths, the review is valid. The guard fix is to also collect `rename to` paths, or to use `git diff --name-only`. The same run's first attempt had died at the inner background-wait ceiling with a sub-500-byte `final-review.md`; the re-run used `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` after `rm -f slang/tmp/pr-diff.patch` ([INTEGRITY-FAIL is a false positive for 100%-similarity renames (#13541)](../learnings/1791540040251-slang-pr-review-runner-integrity-fail-is-a-false-p.md)).

**On claude 2.1.296 the inner lead ending its turn was the common case.** On 2026-10-10 nearly every A run produced a 70–200-byte `final-review.md` and REVIEW-GUARD FAIL (#13559 twice, #13561 three times, one of two #13562 runs; the other wrote 7.4 KB, so it is intermittent but frequent). `stream.jsonl` shows the coordinator dispatching the REVIEW.md subagents with `run_in_background=true`, as REVIEW.md:102 instructs, then ending its turn (`stop_reason: end_turn`, ~42 turns, ~$11–12) with "All six reviewers are still running…". Print mode then stops every subagent (`[Request interrupted by user]`, `task_notification status=stopped`, empty `subagents/`), and relaunching reproduces it. First salvage any subagent that finished before the turn ended: its `type=system, subtype=task_notification, status=completed` record carries the full report in `.summary` (on #13559 run 1 only docs and cross-backend had finished). Then stop re-running and dispatch the REVIEW.md subagent types (`cross-backend-reviewer`, `test-coverage-reviewer`, `code-quality-reviewer`, `ir-correctness-reviewer`, …) yourself via `Agent()`, pointed at a PR-head worktree plus `/tmp/pr<N>.diff`. Synthesize A's section yourself, label it "reconstructed: inner CLI failed", and report `reviewers_complete=false`, backed by your own verification build. The root fix, not yet made, is for the inner `claude --print` to block on its background tasks before its final turn, or for REVIEW.md to dispatch in the foreground in print mode ([inner CLI ends its turn with background subagents running (#13559)](../learnings/1791598985744-reviewer-a-fails-when-inner-cli-ends-its-turn-with.md); [claude 2.1.296 stubs final-review.md every time; dispatch the subagents yourself](../learnings/1791609455637-reviewer-a-claude-2-1-296-ends-turn-while-its-back.md)). The earlier mitigations (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`, `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`) are on [run survival](review-pr-reviewer-run-survival.md). A side trap in that verification build: a fresh `cmake --preset default` release build can lack `build/Release/lib/libslang-llvm.so`, and slang-test then silently ignores every filecheck test ("FileCheck is not available"), so a 14-test file reports 1/1 passed. Copy the library from another recent `wt-*-verify` build and always read the "N tests ignored" count.

**Reviewer C's inner CLI can hang without exiting.** On #13563 both `run-clarity.sh` attempts sat idle for over 15 min with near-zero CPU and no new `stream.jsonl` events, one after a permission-denied `gh api | awk` pipe and one after a plain Grep result. Because the process never exits, the `.done` sentinel never appears and an `until [ -f C.done ]` wait blocks forever. Detect the stall from the `stream.jsonl` mtime plus a `/proc/<pid>/stat` utime+stime delta over 20 s, and kill the inner claude PID (match `readlink /proc/<pid>/cwd` against the `wt-clarity-*` dir). Recovery: Reviewer A's run already includes a REVIEW.md-required "Clarity candidate pass" subagent that runs the same seven slang-review-* skills and writes `<A REPO_ROOT>/tmp/review-candidates/pr-<N>-clarity-workflow.md`; use it as Reviewer C's section with a substitution note. A's subagent `/tmp` output files vanish before compose-and-run preserves them, so pull summaries from `task_notification.summary` in `stream.jsonl` ([run-clarity.sh inner CLI can hang silently; fall back to A's clarity subagent (#13563)](../learnings/1791613028821-run-clarity-sh-inner-cli-can-hang-silently-after-a.md)).

## Verifying Reviewer A's claims before relaying them

**Reproduce every "traced, not reproduced" finding under resource caps.** On #13538 r3 A reported a 🔴 "hang" in `getTrailingUnsizedArrayElement` (no depth cap) that it had traced in source but not run, for `struct LoopTail<each T> { float4 x[]; LoopTail<T,int> next; } uniform LoopTail<int> g;`. Under `ulimit -v 8000000; timeout 90 slangc …` it was real but different: a segfault after ~32 s (rc 139) as substitution kept minting new types, against clean errors in 0 s on master, so a regression. In the same round A's "missed error for a non-[shader] entry point" was wrong: E31215 was measured. So reproduce any finding marked "not run" with an 8 GB ulimit and a 60–90 s timeout on both a head build and a master build, and relay only the measured result. Re-check `gh pr view --json headRefOid` right before sending the verdict: on #13538 the fixer pushed 4 commits during the merge step and the main gap was already fixed ([traced-not-reproduced can be real; run it with ulimit+timeout](../learnings/1791542333563-reviewer-a-traced-not-reproduced-can-be-real-alway.md)).

**The shared checkout's build is not a master baseline.** `/workspace/agent/slang/build/Release/bin/slangc` can be weeks older than its checkout (2026-10-09: checkout at 6818f2ac5, binary from Sep 15), and probes against it produced false regressions: a subscript `ref`-accessor write on a `const` receiver gave E30011 on the stale build, while the PR and the real merge-base build both accept it. Before citing "master gives X", compare the binary's `stat -c %y` with `git log -1`, and prefer an existing `wt-*-master` build at the PR's exact `git merge-base HEAD origin/master`. The same note records a Reviewer B salvage: when `devin-fetch.sh` times out after the page has rendered, `agent-browser snapshot` exposes the Bugs/Flags rows (titles plus file:line) as button nodes that `innerText` misses ([stale /workspace/agent/slang build; use a merge-base baseline](../learnings/1791547396073-slang-review-workspace-agent-slang-build-can-be-we.md)).

**"Rebase clean" does not mean "the reviewer saw this code".** Reopening a held fix as a PR, a fixer told its reviewer "rebase of the fix you reviewed (R2); no code changed since", backed by `git range-diff`. The rebase claim was true, but a third commit, an r3 follow-up applied after the R2 review, had never been reviewed; the reviewer caught it by diffing the PR against the R2 patch. `range-diff` proves only that the rebase preserved content. Before saying "you already reviewed this", map each commit to the review round that covered it, and keep a `reviewed-at:` sha in the fix memory ([rebase clean ≠ reviewer saw this code](../learnings/1791580984851-rebase-clean-reviewer-saw-this-code-check-which-re.md)).

**Verify A's CI claims yourself; "green" can mean every job was skipped.** On #13570, a bot-authored draft, `final-review.md` said "CI is green on head" and cited the GCC 11.4/13.3 jobs. In fact the `pull_request` run had skipped every job, and the `workflow_dispatch` run sat in `waiting` with `wait-for-human-priority` and `check-ci` failed and every build/test job skipped. Check with `gh run view <id> --json status,conclusion,jobs --jq '[.jobs[]|select(.conclusion!="skipped")]'`; a run that is green because everything was skipped is no evidence. Two side notes from that review: a naive grep of Reviewer C's `tool-uses.jsonl` for `slang-review-post-github` false-hits drift when C merely reads or parses the post script (its `parse_candidates` call is read-only), so confirm drift by checking that the PR's reviews and review comments did not change; and when GCC bugzilla and sourceware block WebFetch, `https://www.mail-archive.com/search?l=[REDACTED-EMAIL]&q=subject:"<bug#>"` and `gh api 'search/commits?q=repo:gcc-mirror/gcc+<bug#>'` recover backport evidence (GCC PR108900, the `__LINE__` off-by-one after an `#include` at 0x50000000 locations, is fixed in 14.3 via r14-11679) ([verify Reviewer A's CI-green claim; bot PRs often skip every job](../learnings/1791680727889-slang-pr-review-verify-reviewer-a-s-ci-green-claim.md)).
