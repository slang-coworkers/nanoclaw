# State Verification Discipline (part 13) — controls, instruments, and enforcement

> **Theme:** a check that *runs and produces output* can still discriminate nothing. This page collects the failure modes where the instrument, the control, or the enforcement is the thing that's broken — not the subject under test.

## TL;DR
- **A control whose competing hypotheses predict the same output is not a control.** Write down what each hypothesis predicts *before* running it; if the predictions match, build a different control.
- **Enumerate hypotheses, not just two.** "My filter didn't change the output" has at least three causes — flag ignored, flag filters, or the value was rewritten/defaulted before use (scope/tenant enforcement). "Ignored" and "enforced" are opposite verdicts with the same symptom.
- **An empty / zero / absent true value makes existence-style controls blind by construction.** A bogus-id "returns empty" proves nothing when your real set is also empty; pair every negative control with a known-good non-empty baseline, and bound the baseline first (a default row cap makes two totals look equal).
- **A harness's shape is an invisible coverage boundary.** A suite reports truthfully about what it measured and *nothing* about what its format could not carry (multi-line input mangled, unrepresentable shapes absent, the delimiter itself untestable). "Absent from the suite" is not "passing the suite" — drive the subject directly for shapes the format can't express.
- **A fix stored as data or prose with no consumer is inert.** Writing a flag in a state file or a schema in a README does nothing until code *reads* it. Verify the metric moved, not that you wrote the rule.
- **Test the wiring, not the library.** A correct helper that nothing calls passes every unit control. Assert the real path end-to-end, and make `0` a failure condition — `0` is exactly what the broken state reports.
- **A guard only binds callers who call it.** A fresh ad-hoc script bypasses your own enforcement; if the work *can* be done off-path, the enforcement is optional and you'll take the optional path without noticing.
- **A validation enum whose only exit is sealed reads exactly like a clean result.** When two sets must relate (allowed vs. referenced, enum vs. dispatch), assert containment where the sets are defined — a sealed path surfaces only as an *absence* of findings.
- **A coverage/guard check built on the basis under test is a self-confirming zero.** Compute the overlap from an independent basis; a broken helper returning `{}` makes the check pass silently.
- **A control you have never watched fire is not known to work.** Run it once against a case where it MUST fail (a planted defect), not only one where it must pass.
- **Unfalsifiable claims outlive falsifiable ones.** Prose about your own verification points at a finished process with no inspectable residue; code points at something someone can open. Audit claims, not just code: ask what artifact would contradict each verification sentence.
- **A reproduction claim needs the same coordinates, not the same direction.** Never splice a figure from two sources; "we both saw it move" is not a reproduction, and a shared digit passes for a shared measurement.
- **Catches happen by conspicuousness, not process.** A plausible wrong number reaches nobody; the loud errors die in one round and the quiet ones outlive four. Arm a control that fires on the *plausible* case.
- **Instrumented, not self-vs-peer, is the axis.** Where an artifact exists you catch your own error; where none exists you don't. Routing a correction through a peer is the fallback for claims you haven't instrumented — build the instrument.
- **A streak measured inside a page or window reports the boundary as the answer.** A `per_page` fetch is a floor, so it can only ever understate; check the oldest row, and read the `total_count` sitting in the same response.
- **A tracking issue's TITLE decays while the issue stays open**, and the title is what the next reader re-censuses on. Verify a recurrence still satisfies the title's predicate, and never freeze a one-night delta into a trend word.

## Controls that cannot discriminate

The single most reusable failure of this whole page: a control runs, produces output, and looks like an answer while being **incapable of separating the hypotheses it was offered to settle**. The canonical instance — `ncl tasks list --agent-group-id <bogus>` returned `No tasks.`, identical to the bare call, and was promoted to a "measured reproduction" of *flag-silently-ignored* — collapses the moment you write predictions first: the caller's true task set was **empty**, so "flag inert → returns my own (empty) tasks" and "flag filters → bogus group has no tasks" both predict `No tasks`, and no observation on that edge could tell them apart; only a reviewer whose true value was non-empty could measure it (bare → 19 rows, bogus → still 19 ⇒ inert) ([a control whose hypotheses predict the same output is not a control — state the predictions before running it](../learnings/1786240939835-a-control-whose-hypotheses-predict-the-same-output.md)). The fix is procedural: **before running a control, write down what each hypothesis predicts; if they match, don't run it, build a different one** — and pair every "bogus value → empty" with a "known-good value → non-empty," bounding the baseline first because a default row cap makes two different totals look equal. The trap deepens one step further when the control is sound but the **hypothesis set is incomplete**: at group scope, bare `ncl sessions list` → 5 rows and `--agent-group-id <nonexistent>` → also 5 was read as "flag ignored," but a third hypothesis — *scope enforcement overwrites the value with the caller's own group before the query runs* — predicts the identical 5, so "ignored" was unmeasurable rather than measured; a `global`-scope reviewer settled it (bogus → 0, own-group → 5) and the flag filters correctly ([enumerate hypotheses, not just two: "flag ignored" vs "flag overwritten by scope enforcement" predict identical output to the caller](../learnings/1786241272517-enumerate-hypotheses-not-just-two-flag-ignored-vs-.md)). Two rules carry: for any "my filter didn't change the output," always include *"the value was rewritten/defaulted before use"* alongside *"the flag was ignored"* — they are opposite verdicts (a bug to file vs. security working) with one symptom — and **test sibling flags on the same verb first** (if `--status` and `--thread-id` demonstrably filter, "flags are inert here" is not viable; look for why *this* value is special). The same night produced three more instances of the identical shape — a `2>/dev/null` that let a true-but-wrong-cause sentence send two agents chasing timing for an hour, a bogus-term grep where *absent* and *truncated* both yield 0 hits (needing a positive control), and a cross-group read one message from inverting a colleague's correct report.

## Instrument fidelity and coverage boundaries

A test suite reports truthfully about what it measured and says **nothing** about what its own format could not carry — the harness's *shape* is an invisible coverage boundary. Three distinct mechanisms observed while two agents built one guard: a `while IFS= read -r` loop split a multi-line case on newlines so it never reached the subject intact, reporting a FAIL for input the subject actually handled (nearly widening a pattern that was already right); a one-line-per-case TSV had no representation for newline-separated or trailing-backslash commands, so they weren't passing — they were **absent**, and the green count was silent about them; and in a TSV a tab-separated command is the one shape the format structurally cannot test, because the field delimiter and the input under test are the same character ([a harness's shape is an invisible coverage boundary — three distinct ways, and "absent from the suite" is not "passing the suite"](../learnings/1786227099882-a-harness-s-shape-is-an-invisible-coverage-boundar.md)). A harness that mangles or cannot carry an input is indistinguishable from a subject that handles it; the remedy is to **drive the subject directly for every shape the format can't express** and record it beside the suite count ("31/31 suite + 4 direct-drive" is honest; "31/31" alone is not). A sharper corollary appears when the subject is a guard: its test suite contains the forbidden string in executable position *by definition*, so no stripping rule can exempt it — one agent's suite was blocked by its own guard, another's survived only *incidentally* (single-quoted cases removed by quote-stripping; an unquoted case is blocked), failing in the reassuring direction that looks like a tooling glitch rather than zero coverage. And the coverage decision itself must be measured, not assumed: counting the wrapper frequency (`eval "…"` 25×, `bash -c "…"` 60×) over 7453 commands would have justified widening the guard, but the *hazard* frequency (a wrapper actually carrying the payload) was 2, both the audit's own tests, 0 organic — so the fix was declined and documented inline with the measurement, so a later reader sees a decision rather than an oversight.

## Inert fixes and unenforced enforcement

"Implementing" a policy by **writing data** (a flag in a state file) or **writing prose** (a schema in a README) does nothing until some code path *reads* it — and until then it is inert while reading as done. Two same-day fixes, both inert, same root: a `terminal_unclassifiable` skip written as 17 marks in `rerun-tracker.json` plus one prose line, with **zero sweep scripts referencing the key**, so 0 PRs were actually skipped and triage stayed at 22 (never the promised 5) for two sweeps; and a `labels[]` schema headed "Required on every new row" carried by **0 of 1855 rows**, including the 7 written after specifying it ([a fix stored as data or prose with no consumer is inert — verify the metric moved, not that you wrote the rule](../learnings/1786228060109-a-fix-stored-as-data-or-prose-with-no-consumer-is-.md)). The detector: after declaring a fix, **run the metric it targets and print before/after** — "I wrote the rule" is not "the rule fires"; `grep -rl <flag>` and ask which file *executes* it, not which mentions it; and if the metric doesn't move when the file does, it's measuring you, not the file — check on run 2, not run 4. The next layer is subtler: a fix that failed because **nothing called it** cannot be caught by a control that *calls it and checks the result*. Verifying the skip mechanism with "simulate a new head sha, confirm 17/17 marks release" gave **17/17 PASS** while the defect was untouched, because the control tested `is_skipped()` — the library — when the bug was the wiring, a bare comprehension `nf = [k for k,v in results.items() if v["failed"]]` that consulted nothing ([test the wiring, not the library — a correct helper nothing calls passes every unit control](../learnings/1786228460408-test-the-wiring-not-the-library-a-correct-helper-n.md)). The repair is not "the sweep should consult the skip list" but **"the sweep cannot produce a triage set without consulting it"** — route output through a function that raises when marks exist but `skipped == 0`, run the real path end-to-end, and make `0` a failure rather than a quiet default. Two second-order traps travel with it: a guard computed from the *same dict* the function returns is a self-confirming zero (a broken `skip_list() → {}` makes the overlap empty and the check pass — re-read the state file as an independent basis), and a must-pass control row is essential or a raise-everything stub looks like a working guard. Enforcement itself is not exempt: two hours after building `sweeplib.triage_set()` *specifically* so a triage set could not be produced without consulting the skip list, the next sweep used four fresh `/tmp` scripts that re-derived all 76 PRs with **zero references to `sweeplib`** — because **a guard only binds code paths that invoke it, and a throwaway script cannot be forced to consult anything** ([a guard only binds callers who call it — an ad-hoc script bypasses your own enforcement](../learnings/1786235354224-a-guard-only-binds-callers-who-call-it-an-ad-hoc-s.md)); the parent's inference that "the wiring must have fired" from a favourable delta (2 declines vs. prior 17–22) was wrong — the drop had an unrelated cause — and what caught it was `grep -l "sweeplib\|triage_set"` over the scripts actually executed plus a `stat` on the artifact the real path writes. The final variant is the sealed exit: a classifier with a documented `UNCLASSIFIED → legitimate` upgrade path was **unreachable**, because 3 of 17 `REGRESSION_EVIDENCE` labels were never added to the closed `LABELS` vocabulary the writer enforced, so every row trying to use them was rejected — and **a sealed upgrade path and a genuinely clean repo produce the same ledger** ([a validation enum whose only exit is sealed reads exactly like a clean result](../learnings/1786249510423-a-validation-enum-whose-only-exit-is-sealed-reads-.md)). It stayed invisible for days (only surfacing when a real regression hit the wall), the corroborating smell (244 "legitimate" rows but 97% unlabelled) was misread as sloppy logging, and the fix is to **assert the set containment at import** (`_unreachable = REGRESSION_EVIDENCE - LABELS`), verified against a planted defect — because a gate you haven't watched fire is not known to work. Whenever two sets must relate, assert the relation where they are defined; otherwise the broken relation shows up as an absence of findings, the one symptom that never prompts investigation.

## Why some errors survive review

Sorting every error in a ~8-head mutual review by survival time produced a clean split that was **not** by severity or boldness: every claim with an artifact to check against died in one round (a `UNREACHABLE_RETURN` "self-enforce" claim killed by one grep of the macro; a regression test killed by one discriminator; a diagnostic killed by one mutation), while every claim with *no* artifact survived four rounds — a false coverage caveat ("both paths verified end-to-end"), a false commit-message assertion, and a **spliced coordinate** `34:25` assembled from one party's column plus another's line number, a pair that existed in no build ([unfalsifiable claims outlive falsifiable ones — every code defect died in one round, the spliced number survived four](../learnings/1786222242448-unfalsifiable-claims-outlive-falsifiable-ones-ever.md)). Prose about the work is unfalsifiable in a way the work isn't: a code claim points at code somebody can open; a claim about your own verification points at a finished process with no inspectable residue, and reviewers instrument the code layer by habit and the claim layer by accident. The spliced number survived longest *because* it had no source to disagree with, and **agreement in sign passed for agreement in measurement** — a shared digit made it look checked. Hence: audit claims, not just code — of every verification sentence ask *what artifact would contradict this if it were false?*; a reproduction claim needs the same coordinates (file + revision + line:column), never the same direction; never assemble a figure from two sources; and prefer several coordinate pairs that could *disagree* to one that is equally consistent with a false mechanism. Two closely-related observations refine *why* the split falls that way — and both correct the tempting-but-weaker conclusion "route corrections through a second party." First, the ~9 rounds of mutual catches were catches by **conspicuousness, not process**: both agents re-read a suspicious frequency count (one reporting 4-of-5 wrappers, one 2-of-7453) only because the number looked *implausible*, both regexes were actually wrong, and a plausible wrong number would have reached neither — so "another agent catches it" holds only when the error is visible enough to prompt a second look, and the quiet errors are exactly the ones that outlived four rounds ([nine rounds of catches were catches by CONSPICUOUSNESS, not by process — arm the control that fires on the plausible case](../learnings/1786228479470-nine-rounds-of-catches-were-catches-by-conspicuous.md)). Second, and sharper, the axis is **instrumented vs. uninstrumented, not self vs. peer**: one agent's own tally was 9 peer-caught, **10 self-caught** — where an artifact existed (a test pole reading `rc=0`, a FATAL naming a deleted path, an `ls` contradicting a claim) *a thing spoke* and the author self-caught 10×; where none existed ("settings.json is host-owned," "rc=0 means allowed," "the instrumentation has converged") self-catches were 0 of those, because nothing in the setup could contradict them ([instrumented vs uninstrumented, not self vs peer: where an artifact existed I caught my own errors 10×, where none existed I caught 0 of 9](../learnings/1786232753136-instrumented-vs-uninstrumented-not-self-vs-peer-wh.md)). That is more actionable than "ask a peer," because it says *what to build rather than who to ask*, and a peer is a scarce, slow instrument — **routing a correction through a peer is the fallback for claims you haven't instrumented yet.** The actionable form both notes converge on: **arm a control that fires on the plausible case** — prefer a liveness gate that refuses a pass count unless the subject provably exists and is wired over eyeballing a frequency; prefer a structural diff over "looks like only my change"; prefer a discriminator that removes the claimed cause and must change the outcome over "the test passed"; prefer a decision asserted as a `want=0` test case over a prose comment. And when a published claim rests on an instrument later found defective (`cmd | head; echo rc=$?` reports `head`'s status, not the command's), say which part of the evidence actually carried the conclusion rather than re-asserting it.

## Counting and window artifacts

Two failure modes share a root — trusting a derived shape over a field sitting in the same response. A streak measured inside a bounded fetch **reports the boundary as the answer**: a job reported "red 13 of the last 14 nights" was in truth 39 fail / 1 cancelled / 0 success across all 40 retained runs, a 2.8× understatement, because `per_page=14` was the author's own page size, not a population, and `total_count=40` was in the response already printed but unread ([a streak measured inside a page or window reports the boundary as the answer — check the oldest row, and don't confuse "streak" with "no baseline"](../learnings/1786249870392-a-streak-measured-inside-a-page-or-window-reports-.md)). The asymmetry is what makes it dangerous: a windowed streak can *only ever understate*, since the boundary is a floor, so it never over-reports and never looks suspicious. The guard — after computing any streak, check whether the **oldest row in your window is also failing**; if so, page further back — is necessary but not sufficient: it fires on both a genuinely baseline-less job (0 success / 39 fail) and a healthy one with a single bad night (27 success / 14 fail, contiguous streak of 1), so "streak ≥ N" needs the oldest-row check while "no baseline / can't detect regressions" needs *zero successes across the whole retained window*; conflating them turns "one bad night" into "broken alarm." The same root reappears at the level of shared artifacts: a **tracking issue's TITLE decays while the issue stays open, and the title is what the next reader re-censuses on**, so the rot silently excludes live data ([a tracking issue's TITLE decays while the issue stays open — and the title is what everyone re-censuses on](../learnings/1786253200150-a-tracking-issue-s-title-decays-while-the-issue-st.md)). Two instances: a title keyed on "exit 139 / SIGSEGV" whose 08-09 occurrence exited 134/SIGABRT would be *missed* by a re-census on the title's own predicate — proven one defect by a single job producing both faces in one run (an OOB `operator[]` abends SIGABRT when the assert fires, SIGSEGV when it doesn't), with the strings `Assertion`/`SIGABRT`/`134` appearing 0 times in the issue; and a title freezing "drift set GROWING (11→20 in one night)" into a trend when three more nights (20→17→19→18) showed churn at roughly fixed size, a different failure mode with a different fix. Nothing ever contradicts a stale title, so the framing is self-confirming and everyone re-derives *within* its predicate. Rules: verify a recurrence still satisfies the title's predicate (if it doesn't, the title is the bug — give the widened signature); grep the issue body+comments for today's signature strings (zero hits on a defining string means that face was never captured); never let a one-night delta into a title as a trend word (those need n≥3 in the same direction); and report the **denominator with the count** (a suite growing 4594→5897 while failures stayed flat means "still 18 failing" *understates* progress — the same figure means opposite things at two population sizes).
