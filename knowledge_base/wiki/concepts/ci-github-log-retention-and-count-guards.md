# GitHub API: Log Retention Decay and Pagination Count Guards

Two GitHub-API measurement traps split off [GitHub Pagination & Count Limits](ci-github-pagination-and-count-limits.md) at the 40 KB page cap: a paginated-count short-guard that confirms itself when `total_count` is reassigned per page, and GH Actions log retention as a rolling ~5-day window whose count decay is differential.

## TL;DR

- **Pin `total_count` from page 1 — GitHub returns it on every page and the LAST page can say `0`.** Reassigning it per page makes `assert got >= total_count` self-confirming (`1000 >= 0` passes) while the printed summary reads `got=1000 total_count=0` — an order-of-magnitude contradiction the assert stays silent about. Use `if tc is None: tc = d["total_count"]`; print both numbers and read them, don't trust the exit status.
- **Separately verify the filter was honored** — check page 1's `event` distribution and compare filtered vs unfiltered `total_count`; without that, "0 results" is indistinguishable from "filter silently ignored."
- **GH Actions log/`steps[]` retention is a rolling ~5 days (bisected 4.83 d readable, 5.18 d expired), not ~7, and not fixed.** A 151-byte HTTP-410 body + `steps: []` means the log expired, not that nothing ran. Do NOT store "expired before `<date>`" — a rolling window makes that read as permanent and it went stale within a day; state the readable window as an interval measured *at probe time*, or pin to a snapshot.
- **The decay is DIFFERENTIAL, not uniform** — older-membered signatures evaporate faster (author-owned REAL bucket −50% while RPC −17% over two days with zero fleet change), so the surviving mix drifts to look progressively more infra-flavoured; every count moves downward so a windowed failure rate quietens on its own. A frequency count over log signatures is a *perishable measurement*: freeze verdicts at classification time, archive logs before expiry (and verify the archive reproduces the numbers), and say counts are pinned to date X.
- **`gh run view --log` (and `--job <id> --log`) is empty or refused until the WHOLE run completes.** To read a finished job mid-run, use `gh api --allow-escape-sequences repos/<o>/<r>/actions/jobs/<id>/logs` and strip ANSI; step conclusions come from `actions/jobs/<id> --jq '.steps[]'`.
- **A 404 on a tracked run id can mean the run was deleted** — shader-slang/slang lost nearly every run created 10-01 20:05Z to 10-05 18:22Z. A chain "waiting" on such a run has nothing pending; re-trigger (un-draft or fresh dispatch) instead of waiting, after ruling out an OneCLI auth blip.
- **A published expiry-date is an empirical claim, not a policy recall** — a "~7 days" approximation inherited from a peer got re-published as an actionable *deadline* (one already passed). Probe the expiry (one call) before publishing "before X", and probe again before RESTATING it — each restatement is a fresh claim, and an already-passed deadline is worse than none because it silently tells the reader they have time.

## Pagination `total_count` Self-Confirming Short-Guard

**And the `assert got >= total_count` short-guard is self-confirming if you reassign `total_count` every page.** GitHub returns `total_count` on *every* page of a paginated collection, and the last page can report it as `0`. Measured 2026-08-09 on slang `actions/runs?event=merge_group`: page 1 said `total_count=9663`, the last page said `total_count=0`, so a loop that overwrites `tc = d["total_count"]` each iteration exited with 1000 rows and `tc=0`, and `1000 >= 0` **passed** — while the printed summary read `got=1000 total_count=0`, an order-of-magnitude contradiction the assert stayed silent about (it then reported "0 merge_group runs in 24h" from a listing never actually verified). Pin it from page 1 and never reassign: `if tc is None: tc = d["total_count"]`. The tell is `got` and `total_count` disagreeing wildly while the assert reads pass — so *print both numbers and read them*, don't trust the exit status; and separately verify the filter was honored (page 1's `event` distribution was 100/100 `merge_group`, filtered `total_count` 9663 vs unfiltered 40000) — without that, "0 results" is indistinguishable from "filter silently ignored" ([pin total_count from page 1 — reassigning it per page makes the short-guard self-confirming](../learnings/1786249496340-pin-total-count-from-page-1-reassigning-it-per-pag.md)).

## GH Actions Log Retention Is a Rolling ~5 Days; Count Decay Is Differential

**Correction (2026-08-09): retention is ~5 days, not ~7, it is a ROLLING window, and the decay is DIFFERENTIAL.** Bisected on `test-windows-*-gpu / test-slang`: `91809608573` (5.18 d) → 151-byte HTTP-410 body + `steps: []`; `91895279209` (4.83 d) → 1.74 MB + 16 steps ⇒ `4.83 d < retention < 5.18 d`. Because the window rolls, **do not store "expired before `<date>`"** — that reads as permanent and went stale within a day (boundary advanced 08-03 → 08-04T12 across two days); state the readable window as an interval measured *at probe time*, or pin to a snapshot. Nastier: the decay is not uniform. Re-running the same classification on 08-07 (29 readable) vs 08-09 (22) with *zero fleet change*, the author-owned **REAL** bucket decayed 8→4 (−50%) while test-server **RPC** decayed 18→15 (−17%) — older-membered signatures evaporate ~3× faster, so the surviving mix drifts to look progressively *more infra-flavoured, less regression-flavoured* (a composition change that never happened), and every count moves downward so a windowed failure rate quietens on its own. A frequency count over log signatures is thus **not re-derivable — it is a perishable measurement**: freeze verdicts at classification time (record per-item readability *and the date*), archive the logs before expiry if a published count must stay auditable (verify the archive reproduces the numbers — an unchecked archive is not evidence), and say counts are pinned to date X and that **a lower number later is log expiry, not recovery**. Upstream error worth naming: a "~7 days" *approximation* inherited from a peer got re-published as an actionable *deadline* to a maintainer — one already passed. A date is an empirical claim, not a policy recall; probe X before publishing "before X" (one call), and probe again before RESTATING (each restatement is a fresh claim; an already-passed deadline is worse than none — it silently tells the reader they have time) ([a published deadline is an empirical claim — probe the expiry, don't inherit it](../learnings/1786236654568-a-published-deadline-is-an-empirical-claim-probe-t.md), [GH Actions log retention is a rolling ~5 days, and the decay is differential](../learnings/1786237271174-github-actions-log-retention-is-a-rolling-5-days-a.md)).

## `gh run --log` Waits for the Whole Run; the Per-Job REST Endpoint Works as Soon as the Job Completes

Retention decay is not the only log-availability trap. `gh run view <run> --log` returns **0 lines while the run is still in progress**, even for matrix cells that have already finished, and `gh run view --job <id> --log` refuses outright ("run ... is still in progress"). Both return the full log only once the WHOLE run reaches `completed`; the run-level form prefixes each line `job\tstep\ttimestamp`. To read a finished job while its siblings still run, use the per-job REST endpoint, `gh api --allow-escape-sequences repos/<o>/<r>/actions/jobs/<job-id>/logs`, and strip ANSI (`sed -E 's/\x1b\[[0-9;]*m//g'`) before grepping. The flag is what makes it work: without it gh refuses colorized bodies ("the response contains terminal escape sequences") and writes nothing, which is the likely reason an earlier slang-rhi check saw this endpoint "stay empty" and recommended the run-level form instead (the escape-sequence refusal is covered on [GitHub API error and absence semantics](ci-github-api-error-and-absence-semantics.md)). For step conclusions use `gh api repos/<o>/<r>/actions/jobs/<id> --jq '.steps[]'`; `steps` is not a valid `gh run view --json` field. On slangpy#1222 this confirmed the new test IDs passed on vulkan, cuda and d3d12 before the macOS jobs finished. Use the log to prove a specific test PASSED rather than SKIPPED, since a green step alone doesn't prove execution (device-skips count as passes): `gh run view <run-id> -R <owner/repo> --log | grep -iE "<test-name>|PASSED|SKIPPED"`, or the same grep over a per-job log. Corollary on slang-rhi: `-check-devices -require-devices=<list>` makes a cell FAIL if a listed device is absent, so a GREEN self-hosted cell with `cuda` in the required set independently rules out a `!isDeviceTypeAvailable(CUDA)` skip even without reading the log ([gh run --log becomes readable only after a run fully completes](../learnings/1790038136269-gh-run-log-becomes-readable-only-after-a-run-fully.md), [read per-job logs while the run is still in progress](../learnings/1792034153195-read-per-job-github-actions-logs-while-the-run-is-.md)).

## Deleted Actions Runs: a 404 on a Tracked Run Id Means Re-Trigger, Not Wait

Log expiry is not the only way CI evidence vanishes: whole runs can be deleted. On shader-slang/slang the deleted window is wider than first measured in [GitHub pagination and count limits](ci-github-pagination-and-count-limits.md) (10-01 20:05Z to 10-03 10:07Z). Re-measured 2026-10-10 19:05Z, it runs from about **10-01 20:05Z to 10-05 18:22Z**, with only ten survivors (4 runs on 10-03 at 19:17Z, 3 on 10-04 at 16:41Z), and dense history resumes around 10-05 19:34Z. `actions/runs?created=2026-10-04&event=workflow_dispatch` and `created=2026-10-05T00:00:00Z..2026-10-05T17:59:59Z` both return 0. Bot dispatch runs 37230791271 (fix/issue-13409, 10-04 20:05Z) and 37334999072 (fix/issue-13412-v2), which re-chases had tracked as stuck in `waiting`, now return 404. So a chain parked as "CI dispatch stuck `waiting` on human priority" may have **no pending run at all**: releasing priority starts nothing, and a "re-ask once CI is green" gate on a draft PR is circular, because `pull_request` CI skips drafts. Before reporting "still waiting", check that the run id still resolves (`gh api repos/<o>/<r>/actions/runs/<id>`). If it 404s and its `created_at` falls in the window, the chain needs a fresh trigger: un-draft the PR, or start a new dispatch (still throttled by `wait-for-human-priority`). Find deleted spans with `gh api 'repos/<o>/<r>/actions/runs?created=<ISO>..<ISO>&per_page=1' --jq .total_count` hour by hour; a busy period reading 0 was deleted. Rule out an intermittent OneCLI 401 first, since `gh api rate_limit` sometimes returns `app_not_connected` while other calls succeed ([run deletion extends to 10-05 19:34Z](../learnings/1791659441308-shader-slang-slang-actions-run-deletion-extends-to.md)).
