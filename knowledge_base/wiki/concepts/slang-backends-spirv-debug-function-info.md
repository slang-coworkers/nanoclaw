# Slang SPIR-V DebugFunction / NonSemantic debug-info

The NonSemantic.Shader.DebugInfo `DebugFunction`/`DebugFunctionDefinition` family (PR #13237 decoupling work, Sep 2026) has three separable layers: the IR representation (`IRDebugFunction` and its `DebugFuncDecoration`), the SPIR-V emit consumer (`emitDebugFunction` in `slang-emit-spirv.cpp`), and the IR passes that *clone* debug decorations onto new functions (autodiff `copyDebugInfo`, out-parameter lowering). Bugs recur here precisely because these layers are conflated. Companion pipeline/`-g2` detail lives in [[wiki/concepts/slang-backends-spirv-2-pipeline.md]] (the `#11982/#11983/#11984` producer cluster).

## TL;DR

- **`IRDebugFunction` DOES carry a `parentScope` operand at HEAD** — operand layout is `getName()`=0, `getLine()`=1, `getCol()`=2, `getFile()`=3, `getDebugType()`=4, `getParentScope()`=5 (`slang-ir-insts.h`). Scope is IR-carried now, not purely emit-derived; the earlier "carries no scope operand" claim is stale. Re-verify operand layouts against the current tree — operands get appended over time.
- **`getDebugType()` returns a raw `IRType` (the function's `IRFuncType`), NOT a NonSemantic debug-type record.** The `DebugTypeFunction` record is an emit-time artifact derived from that raw operand. Don't infer an operand's kind from an accessor's name — read the construction site.
- **A `DebugFunction` record binds to EXACTLY ONE `DebugFunctionDefinition`** (NonSemantic invariant; spirv-tools rejects multiple-per-record). When adding a "definition already emitted" dedup, **key it on the `DebugFunction` record, not the `spvFunc`/OpFunction body** — several distinct `OpFunction`s can share one record.
- **A bare `cloneDecoration` of `DebugFuncDecoration` (empty `IRCloneEnv`) shares the `IRDebugFunction` by reference, not deep-copy** — `findCloneForOperand` leaves unmapped global operands unchanged. The new function points at the *original's* record. This is a recurring **producer-side** class.
- **Consequence of shared records is debug-info QUALITY (misleading names / stale types), not a miscompile and not invalid SPIR-V.** The emitter's per-record dedup guard prevents the invalid two-definitions-per-record case. Latent whenever the sharing producer only feeds a non-SPIR-V target (C-like/Metal emitters skip `DebugFuncDecoration`).
- **Producer-side fix = `fixUpDebugFuncType(IRFunc*)`** (`slang-ir.cpp`): if the func's data type differs from the record's `getDebugType()`, mint a fresh distinct `IRDebugFunction` (preserving name/line/col/file/scope) and swap the decoration — fixes BOTH the sharing AND a stale debug type in one call.
- **NonSemantic debug info is NOT validated by spirv-val** — these defects ship silently at rc=0; only a GPU debugger (RenderDoc/Nsight) notices. Reproduce/confirm by source trace or by grepping the ext-inst stream, never by trusting a clean spirv-val.
- **fwd_diff of a CONCRETE generic specialization does NOT hit `copyDebugInfo`'s generic path** — a concrete `fwd_diff(gen<float>)` resolves to a module-scope `IRFunc` first, so no hoisted name-hint-less `IRGeneric` reaches `copyDebugInfo`. Check generic-vs-concrete before flagging an autodiff-of-generics debug-info abort.

## IRDebugFunction representation (operands are IR-carried)

At HEAD (`afeaf511c`), `struct IRDebugFunction` (`source/slang/slang-ir-insts.h:2810-2827`) carries a **`getParentScope()` = operand 5** (`getOperandCount() > 5 ? getOperand(5) : nullptr`), which supersedes the older "IRDebugFunction carries no scope operand, scope derived at emit" finding — scope is now stored in IR ([IRDebugFunction DOES have a parentScope operand at HEAD (supersedes the "no scope operand" learning)](../learnings/1790169317334-irdebugfunction-does-have-a-parentscope-operand-at.md)). The only parent scope produced is the `DebugCompilationUnit` of the source file the function is defined in, so an imported function resolves to its OWN module's CU (not the entry point's); it is null only at Minimal debug level, for `#line`-remapped source with no CU, or for a pre-operand IR blob. Separately, the `getDebugType()` operand (index 4) is a **raw `IRType`** — the function's `IRFuncType` — NOT a NonSemantic debug-type record, despite the accessor name; both construction sites (`slang-lower-to-ir.cpp:15039`, and `fixUpDebugFuncType` in `slang-ir.cpp:860-880` which compares via `isTypeEqual(funcType, as<IRType>(oldDebugFunc->getDebugType()))`) hand the raw type through, and the `DebugTypeFunction` record is derived at emit ([IRDebugFunction.getDebugType() returns a raw IRType, not a debug-type record](../learnings/1790164801529-irdebugfunction-getdebugtype-returns-a-raw-irtype-.md)). Implication for any IR pass that constructs/clones an `IRDebugFunction` (e.g. giving each autodiff derivative its own record): pass the function's raw `func->getDataType()` (never a hand-built debug-type record — that would introduce a second representation and mismatch `isTypeEqual`), COPY the source's `parentScope` operand to keep the correct CU, and `setInsertBefore(destFunc)` so the record shares the derivative's scope (a derivative may still be nested in an `IRGeneric` when the pass runs).

## Emit consumer: decouple the per-body definition from the per-record cache

`emitDebugFunction` (`slang-emit-spirv.cpp`) conflates two SPIR-V insts with different lifetimes under one memoization: the once-per-`IRDebugFunction` `DebugFunction` RECORD, and the once-per-`OpFunction`-body `DebugFunctionDefinition` (the ExtInst binding the record to the `OpFunction`, gated `if(firstBlock && spvFunc)`). In **slang#13235** (regression from PR #13175 "Restore caller debug scopes after inlining"), a function with an *inlined callee* emits the record but NO definition: #13175 inserts a caller-scope-restore `DebugScope(<caller's own DebugFunction>)` into the inlined-into function; the first-block DebugVar backing-declaration loop runs BEFORE the per-function debug emit, and a DebugVar following a restore-scope makes `findDebugScope`→`ensureInst(callerDebugFunc)` emit the record BARE via the global path (`firstBlock=nullptr` → no definition) and cache it; the later per-function call then hits the record-cache early-return and skips the definition. A function with no inlined callee has no preceding DebugScope, so nothing pre-caches and both emit. The fix is at the emit **consumer** (the restore-scope IR is correct/needed): emit the definition even on a record cache-hit when `firstBlock`/`spvFunc` are real, tracking "definition emitted for this OpFunction" separately; reordering the per-function emit before the DebugVar loop is fragile and misplaces the required OpVariables (correct order: OpVariables → DebugFunctionDefinition → DebugScope → DebugLine). This missing-definition symptom has recurred via other triggers (#9806 `__include`, fixed PR #9986) ([SPIR-V DebugFunctionDefinition dropped when a callee is inlined (emitDebugFunction record/definition cache conflation)](../learnings/1790151769234-spir-v-debugfunctiondefinition-dropped-when-a-call.md)).

**PR #13237's dedup must key on the record, not the body.** The merged fix keys a `HashSet<SpvInst*>` on `spvFunc` to guarantee "≤1 definition per OpFunction body." That enforces one invariant but MISSES the separate one — "one record binds to one body" — when several distinct `OpFunction`s **share one `IRDebugFunction`** (see the producer class below): each shared body then emits its own definition referencing the ONE record → N definitions per record, which spirv-tools' `val_ext_inst_debug_test.cpp` treats as invalid. Verified: a loop-based reverse-autodiff `-g2 -O0` case (differentiated fn inlining a `[ForceInline]` callee + a local after the call) produced 2 definitions per record with body-keying, 1 with record-keying ([SPIR-V DebugFunctionDefinition dedup must key on the DebugFunction record, not the OpFunction body](../learnings/1790162568589-spir-v-debugfunctiondefinition-dedup-must-key-on-t.md)). The per-`spvFunc` guard and the shared-record gap were missed by all three PR reviewers and the reviewer's own read; the **codex critique gate** caught it — a reviewer's `[Resolution]` sign-off should pass the critique gate BEFORE delivery (a `[GATE AUDIT] … gate skipped` warning means signing off without the second opinion), and when the gate returns `revise` after delivery, correct the record honestly rather than defending the premature claim ([SPIR-V DebugFunctionDefinition decoupling (PR #13237) — a per-spvFunc uniqueness guard misses shared IRDebugFunction across autodiff-cloned funcs](../learnings/1790161516199-spir-v-debugfunctiondefinition-decoupling-pr-13237.md)).

## Producer class: bare `cloneDecoration` shares one `IRDebugFunction` across functions

A `cloneDecoration(&cloneEnv, decor, newFunc, ...)` with an **empty** clone env reproduces a `DebugFuncDecoration` but leaves its operand-0 `IRDebugFunction` as a **shared reference** (`findCloneForOperand` returns unmapped global operands unchanged), so `newFunc` points at the original's record. `DebugFuncDecoration` carries the record as operand-0 (`slang-ir-insts.lua`, `getDebugFunc()`), so any bare clone shares it. Two producers exhibit this at master `6eb89786c`: autodiff `copyDebugInfo` (`slang-ir-autodiff.cpp:1355-1374`, clones `kIROp_DebugFuncDecoration` at :1366-1368) → **#13238 / draft PR #13239** (reverse-mode makes `s_apply_`/`s_bwdProp_`/`s_remat_` from one `targetFunc`, `slang-ir-autodiff-rev.cpp:~409`); and out-parameter lowering `transferFunctionDecorations` (`slang-ir-lower-out-parameters.cpp:387-390`) → **#13251** (sibling, latent) ([Shared IRDebugFunction via bare cloneDecoration is a recurring quality-only class; fix producer-side with fixUpDebugFuncType](../learnings/1790223703724-shared-irdebugfunction-via-bare-clonedecoration-is.md), [Bare cloneDecoration of DebugFuncDecoration re-references (not deep-copies) the IRDebugFunction — same shared-record shape at multiple producers](../learnings/1790223022890-bare-clonedecoration-of-debugfuncdecoration-re-ref.md)).

Whether the sharing is a **live bug** depends on whether the original function *survives*: if the pass removes/replaces the original (only one live reference) the sharing is transient/harmless; if both stay alive (out-param lowering keeps the original when hoisted `uniform` params carry `IREntryPointParamDecoration`s referencing it) you get two live functions sharing one record → misleading debug names, and — because the replacement wrapper has a **different signature** — a stale debug type. The severity is **debug-info QUALITY (P3), never a miscompile / never invalid SPIR-V**: the emitter caches per-`IRDebugFunction` inst AND dedups the per-body definition per record (emitter comment at `slang-emit-spirv.cpp:10819-10822` documents exactly this reverse-mode-autodiff sharing), so the residual is only stale names/types; C-like/Metal emitters don't consume `DebugFuncDecoration` at all, so a sharing producer wired only to a non-SPIR-V target (out-param lowering is Metal-only via `legalizeShaderOutputParamsForMetal`) is fully latent. Triage discipline: don't over-severity a shared-record report, don't mark `reproduced` without a wired SPIR-V path (it is source-trace-confirmable only), and place the fix producer-side. The in-tree producer-side fix is **`fixUpDebugFuncType(newFunc)`** (`slang-ir.cpp:854-884`): when the func's data type differs from the record's `getDebugType()` it mints a FRESH distinct `IRDebugFunction` (preserving name/line/col/file/scope), removes the old decoration, adds a new one — breaking the sharing AND refreshing the stale type in one call, early-returning when the type is unchanged. Its sole caller today is specialization (`slang-ir-specialize.cpp:2600`); the natural fix for a new producer is to call it right after the decoration copy. (For an autodiff derivative — a genuinely different function — build a fresh record with its own name instead, PR #13239's approach; `fixUpDebugFuncType` keeps the source name, correct when the wrapper is the same source function ABI-rewritten.) Cluster: #13235 (emit-consumer, MERGED PR #13237) / #13238 (autodiff producer, draft PR #13239) / #13251 (out-param-lowering producer).

## Review-scoping: concrete generic specialization is module-scope, not a nested generic

A plausible-but-usually-wrong autodiff debug-info 🔴: "fwd_diff of a named generic at `-g2` aborts because `copyDebugInfo` gets a hoisted, name-hint-less `IRGeneric` as destFunc while srcFunc has a hint (firing the no-name-hint assert)." For a CONCRETE call like `fwd_diff(genPoly<float>)` this is wrong: `specialize(genPoly, float)` resolves to a MODULE-SCOPE cloned `IRFunc` first (non-module-scope translation is rejected at `slang-ir-translate.cpp:430`; `slang-ir-specialize.cpp:4094` clones beside the module-scope specialization), so in `maybeTranslateForwardDerivative` (`slang-ir-autodiff-fwd.cpp:3518`) the generic-base branch (`base = getGenericReturnVal(base)`) is NOT taken, `targetFunc` is a module-scope `IRFunc`, `findOuterGeneric(fwdDiffFunc)` is null, `hoistValueFromGeneric` returns the `IRFunc`, and `copyDebugInfo` takes the `if (nameHint)` branch — the release assert is never reached. When reviewing autodiff-of-generics claims, always check generic-vs-concrete: a concrete specialization is a module-scope func, not a nested generic ([Autodiff: fwd_diff of a CONCRETE generic specialization does not hit copyDebugInfo's generic path](../learnings/1790220192127-autodiff-fwd-diff-of-a-concrete-generic-specializa.md)).

## Tooling trap

`awk 'length>100'` for column checks counts **bytes**; an em-dash `—` is 3 bytes / 1 char, so it false-flags ≤100-column comment lines as over-length. `clang-format` (display columns) is the authority — if it reports NO CHANGES, the line is within the limit.
