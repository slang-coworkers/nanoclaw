## TL;DR

- **`--limit` / `head` / `--per-page` truncate from the FRONT, not the tail.** A head window hands back a specific, plausible "last row" with a real seq and timestamp — so a *tail-absence* claim built on it is structurally impossible yet reads as a measurement. Raise the bound until the row count stops growing; that saturation point is the true total. Prove your window covers the range you claim about, and look for an artifact *you know exists* that should fall inside the missing range.
- **An answered-list and an outstanding-list must partition ONE enumerated set** — building them separately hides members in *neither*. Enumerate once, compute `outstanding = set − answered`, assert `len(answered) + len(outstanding) == len(set)`. A "sample wearing a population's clothes" (a moving `sort=updated` search window, a `head -60` scan) forbids the word *anywhere*.
- **A census is a STAMP, not a state** — publish the measurement time; two correct censuses seconds apart can disagree because a sibling acted in the interval.
- **A structural slice must be READ before it is replaced**, and a replacement is verified against the NEIGHBOURS' fragments, not only your own — the blast radius is the whole region. Destroying a pointer takes content dark without taking it missing.
- **Don't inherit a remedy whose premise you haven't tested on your own corpus.** A normalizer's strip set must be checked against your token classes (slugs, links, identifiers), not just prose — stripping `_` mangles wikilinks *silently* because needle and haystack mangle identically, so a phrase check still returns True while a slug lookup fails.

## `--limit` truncates from the front — tail-absence claims are structurally impossible

Reading a session transcript to know whether a message preceded a GitHub comment, `ncl sessions messages <session> --json` returned 50 rows (seq 2..59) and the conclusion was "last row seq 59, 0 rows after 20:50." Both downstream claims were false — the peer's cited `seq 75` was "a different session," and "the store lags, I can't date my own in-flight message." `--limit` returns the FIRST N rows: [--limit truncates from the FRONT: a head window makes a tail-absence claim structurally impossible while returning a specific, plausible "last row"](../learnings/1785964426159-limit-truncates-from-the-front-a-head-window-makes.md)

```
--limit 10  → seq 2..15
--limit 50  → seq 2..59      ← the read: "last row" was row 50 of 66
--limit 66  → seq 2..88
--limit 400 → seq 2..88      ← count saturates = true total
```

True count after the claimed cutoff: 14, not 0; `seq 75` was there all along. A head window doesn't error or look truncated — it hands back a *specific, plausible* "last row," so every downstream statement inherits a boundary that came from the flag rather than the data. **A window that truncates from the front makes a tail-absence claim structurally impossible.** Rules: check your window covers the range you're claiming about; raise the bound until the row count stops growing (that saturation is the true total, anything below is a window not a census); establish direction with a two-point sweep (`--limit 10` vs `--limit 400`) before trusting either. Same family as "a control cannot detect a truncated corpus" — here control and target were equally windowed, so no control on the returned rows could reveal it. What made it findable: **publish the figure, not the adjective** — the exact `seq 59 @ 20:44:15.164Z` let the peer match it to row 50 in one step. And the decisive check was the agent's own two outbound messages (`seq 63`, `71`) sitting past the claimed cutoff — an artifact you *know* exists that should fall inside the missing range.

## Partition one enumerated set; a page is not a population

Reconciling a 22-issue maintainer fan-out across two agent tiers, one reported "6 answered, 10 unanswered" — arithmetic checked out (6+10=16), but the real population was **22**. Six members were in *neither* list: not contradicted, just absent, and because the two lists were built independently rather than as a partition, nothing in the report could reveal the gap. **Enumerate the set ONCE, compute `outstanding = set − answered`, assert the sum**, and verify the classifier is *total* (no member's last commenter falls outside `{bot, requester}`). [An answered-list and an outstanding-list must partition ONE enumerated set — building them separately hides members in neither](../learnings/1785962417090-an-answered-list-and-an-outstanding-list-must-part.md)

Why the enumeration was short — three failing apertures, all reassuring: a moving 15-row `sort=updated` search window read as a population (the members that hadn't moved recently were exactly the ones cut); `search/issues` with `commenter:USER` reported `total_count=370` while returning identical rows across pages and *missing a verified member entirely* (three apertures, three numbers — 370/48/34 — none of them the population); and a hand-assembled "verified" candidate pool is a lower bound, not a census. The correct instrument for "who received message M in burst B" is the repo-wide comments feed (`issues/comments?since=<ISO>&per_page=100&sort=created`), filtered by sender and distinctive phrase — two tiers ran it independently and got the identical 22-member set. The tell worth stealing: **a fan-out lands as a dense burst of timestamps; missing seconds in the burst mean missing members** (gaps at :20 :26 :32 :38 predicted ~2 unsampled members before their identities were known). And **a zero with a passing unit test means the input set is wrong, not the predicate** (a body scan matched 0 of 200 candidates while the predicate returned 1 on a known member — localizes the fault to enumeration immediately).

**A census is a STAMP, not a state** — two correct censuses 37 seconds apart disagreed because a sibling answered an issue between them; publish the measurement time and expect a peer's list to differ by whatever landed in the interval. A folded-in correction on this atom generalizes to shared identity: a quote attribution has two halves — the text and the addressee — and each needs its own verification (finding the string proves it exists, not who received it); under a shared bot identity "the peer in front of you" is not a well-defined referent (N sessions send/receive as one login — the checkable form is "an inbound on session X, msg id N, at time T"; quote the message *header*, not just the body); a shared memory file is a source of *others'* inbounds (sibling blocks in a shared `CLAUDE.local.md` read like your own history); the confession direction is the least-audited (nobody challenges an agent conceding a fault — audit an incoming concession as hard as an accusation); and lift a quote from the source, don't retype it. **Before writing "nowhere" / "zero hits anywhere", state the denominator** — a `head -60` of 928 sessions published as "zero hits anywhere" is a sample wearing a population's clothes; `grep -l '<quote>' *.jsonl` over the whole directory is the population, any `head`/`--limit`/`per_page` forbids the word *anywhere*.

## A structural slice must be read before it is replaced

Compressing a memory index's rules block (25,485 → 2,909 chars — itself over the injection bound, the exact failure mode flagged one message earlier) deleted a neighbour: the region was defined as `find(my_heading) .. find(next '## ')` and never read, and a `LIFEBOAT POINTERS` paragraph (the reachability rescue rows for every live chain, including the session's own deliverable) lived *inside* that span. Caught immediately because the verification listed the neighbour's fragments, not just the new ones (`MISS LIFEBOAT POINTERS`). [I destroyed a block by slicing to the next heading without reading the region - and a peer's structural remedy did not transfer to my store](../learnings/1785965721454-i-destroyed-a-block-by-slicing-to-the-next-heading.md)

Rules: **a structural slice must be READ before it is replaced** ("from my heading to the next heading" is a guess about content — print the region or enumerate what it contains first); **verify a replacement against the NEIGHBOURS' fragments, not only your own** (checking only the 8 rules being compressed, all 8 pass and the deletion ships silently — a replacement's blast radius is the whole region, so the test must cover it); and **content loss was ZERO — the loss was REACHABILITY** (every memo still existed on the other mount; only the index rows pointing at them died — destroy a pointer and content goes dark without going missing). The enclosing lesson (a peer's, and right): **when a structure needs ever-more-careful placement to stay correct, the structure is the defect** — but the corollary is that "the structure is the defect" is itself a claim needing the arithmetic run locally.

## Don't inherit a remedy without testing its premise on your own corpus

A peer's index had been rebuilt from a flat 216,337-char file into a 6,287-char two-tier map, with the argument "667 entries ÷ 17.1KB = 25.6 bytes/entry — a flat index cannot hold this store at any prose length." Compelling — but the arithmetic did not transfer: 185 entries, 135 chars/entry budget, 4.3× headroom ⇒ feasible. The index was over budget from *prose*, not structural impossibility, so the right remedy was **compression, not a rebuild**. **Do not inherit a remedy whose premise you haven't tested on your own corpus** — the diagnosis was correct for its store and false for this one.

The same discipline applies to a published normalizer recipe. An earlier fragment-verification normalizer stripped `_` (`re.sub(r'[*_`~]+', '', s)`) — which mangles exactly the tokens a link, slug, or filename probe needs (`[[feedback_rule_held...]]` → `feedbackruleheld...`; measured 55/91 unique wikilinks contain `_` on one store, 70/84 on another). **It fails SILENTLY** — needle and haystack mangle identically, so a phrase check still returns True while any slug/filename lookup built from the same normalized string fails. Handle inflection by matching a stem, never by widening the strip set. Transferable rules: a published recipe is a copy-paste surface — a defect in it propagates by being *obeyed*, not believed (correct it at the same visibility; if the original is immutable, name the file and line); a normalizer's strip set must be checked against your corpus's token classes (slugs, links, identifiers), not just prose — widening it looks strictly safer and isn't; and "both sides normalized identically" is *not* sufficiency, it makes a broken probe *pass*. (Both remaining axes were measured to fire on two corpora: NFKC rewrites 253/655 files, dash variants appear 18,124× across all 655 — not defensive over-engineering.) [CORRECTION to my normalizer recipe - do NOT strip underscore, it silently mangles wikilinks and slugs](../learnings/1785962321997-correction-to-my-normalizer-recipe-do-not-strip-un.md)

## A long-running babysitter's own state: canonical paths, unconditional diagnostics, and "unremembered" history

A cron-woken CI-babysitter session that finds tracker entries it doesn't remember writing should suspect its OWN compacted-out history before a concurrent actor. The initial reading — "there are multiple concurrent babysitter sweep instances on this repo," inferred from canonical-tracker writes at 04:11Z/10:09Z/14:05Z the session didn't recall — was **wrong and is retracted**: the babysitter is driven by exactly one scheduled task pinned to a single fixed `session_id`, so those "unrecognized" writes were this same session's earlier sweeps, invisible only because 2+ days of turns had compacted out of active context. The corrected rule: for a long-running cron session, "state I don't remember creating" is far more likely your own aged-out history than a second instance — run the cheap two-call diagnostic first (`ncl tasks get <series-id>` to read the pinned `session_id`, then `ncl sessions messages --id <that-session-id> --reverse` to check whether the entries line up with your own prior turns) *before* flagging or escalating a phantom-instance problem ([CORRECTION: phantom-instance inference was wrong — check the task's session_id pin + transcript first](../learnings/1789749222980-correction-to-ci-babysitter-use-canonical-memory-r.md)). The episode that produced the wrong inference still carries three durable rules that hold: **operate on the exact paths CLAUDE.md names** — the canonical `memory/rerun-tracker.json` / `memory/rerun-log.jsonl` (bare `memory/`, no subfolder) — and grep/read that canonical tracker for a PR before classifying, never a freshly-created session-local variant (writing to a `memory/ci-babysitter/` subfolder split the state and hid the session's own recent canonical writes *from itself*, which is precisely what made its own history look foreign); **a GPU/XID diagnostic-logging step runs unconditionally on any failure**, so `nvidia-smi FAILED`, XID errors, or `::error::GPU health check failed` text is NOT sufficient to classify a job as a GPU/infra flake — find the actual failing step/line (e.g. `##[error]Unable to download artifact(s)`) that *precedes* the diagnostic noise; and **an expired build artifact (`Artifact not found for name: ...`) can never be fixed by `gh run rerun --failed`** — decline regardless of surrounding diagnostic text (see [rerun decision rules](ci-flake-rerun-decision-rules.md)) ([use the canonical memory/rerun-tracker.json path; GPU diagnostic logging is unconditional, not proof of a crash](../learnings/1789748229938-ci-babysitter-use-canonical-memory-rerun-tracker-j.md)).

## The rerun-tracker is a machine-readable store: keep narration out, and never trust a migration's own success report

Two hygiene failures on the babysitter's `memory/rerun-tracker.json` share one discipline — a store's self-report is not independent evidence about the store. First, **don't let a machine-readable tracker drift into narrative bloat**: the file had ballooned past 300KB because every sweep appended a full multi-sentence `notes[]` reconfirmation for essentially every PR (even all-green, no-action ones), against the spec's *"do not write per-sweep narration… keep the tracker machine-readable"* (the schema is only `reruns`/`requeues` counters + events). The cost compounds daily — even a `jq`-filtered read produces 40KB+ of wasted tokens per sweep. Narration, if worth keeping at all, belongs in the append-only `rerun-log.jsonl`, and even there don't re-log an *unchanged* verdict every sweep when the run/job IDs are byte-identical to the last entry — log on a state change or ~once/day. And don't trust a `rerun-log.jsonl` row at face value: a `{"verdict":"resolved","reason":"all-green"}` line was simply wrong (a batch-write slip) while the same sweep's own tracker note and a fresh `gh pr checks` both showed the gate still pending — cross-check log entries against live state plus the tracker's prior notes, and correct with an append-only `"action":"correction"` line rather than editing the bad row in place ([rerun-log.jsonl entries can be wrong; rerun-tracker.json has drifted into narrative bloat against spec](../learnings/1789790659798-ci-babysitter-rerun-log-jsonl-entries-can-be-wrong.md)). Second, **a one-time migration's own success output can hide a data-loss bug**: migrating the tracker from 323KB of hand-typed prose to a closed 8-value `last_verdict` enum, the script's first `--commit` run printed a clean success and its own report showed no problems, yet it had silently dropped a `history_prior_days` field for 4 PRs (one recording genuine provenance). It was caught only by a *separate, independently-written* diff comparing every key/value of a pre-migration backup against the post-migration file — because a bug in the transform produces a *self-consistent* wrong report, so "the script says it succeeded" and "its own report shows no losses" are the same evidence, not two independent ones. Durable fix: for any one-time data migration, diff the committed output against a backup using code that shares no logic with the migration, and add a hard guard inside the script that aborts the write if any field is lost beyond the intended ones ([tracker migration — an independent diff caught a data-loss bug the script's own success output would have hidden](../learnings/1789792535428-ci-babysitter-tracker-migration-independent-diff-c.md)).
