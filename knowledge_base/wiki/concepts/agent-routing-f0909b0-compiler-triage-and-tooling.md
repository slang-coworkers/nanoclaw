## TL;DR

- A diagnostic gated to entry points only is an ICE escape hatch: route a bad value through a NON-entry helper and the clean diagnostic never fires, the malformed inst survives to emit, and you get a raw cross-target ICE. Fix belongs in the pass that should have diagnosed/lowered the inst away, NEVER a `case` in the emitter. A code comment claiming "the downstream safety net will catch it" must be VERIFIED to produce a clean diagnostic, not an ICE.
- A "spirv-emit ICE" report is often a CROSS-TARGET ICE class — always run the per-target matrix; the reporter's target is just the one they tried.
- Fix a multi-pass crash with a validation pass + error gate BEFORE the transform passes (mirroring `diagnoseCircularConformances` + its `getErrorCount()!=0` gate), not per-site guards: `DiagnosticSink` does not dedup (two per-site guards emit the same diagnostic twice) and there is no error-gate between passes in a target's switch arm, so guarding one site just moves the crash to a different unguarded site downstream.
- Scope a fix by the decoration/attribute you check; test EVERY reported cell on EVERY reported target (a combined-attribute case can crash on one target and not another). An unmerged sibling draft is not a dependency you can lean on.
- A tracking issue split from in-flight work describes the FIX branch, not master — verify the diagnostic actually shipped (census the code family with a control). A split-off defect's reachability can be GATED behind the parent's fix, so `reproduced` is honest only with provenance ("measured with #NNNN's fix applied").
- When a fix proposes to "gate a decoration arm per-target," first check whether that IR decoration is a SHARED representation used by both user intent and compiler-inserted must-happen transforms. If so, the principled fix is a producer-side marker distinguishing intent, not a consumer-side gate.
- A "only N producers, we touch M of them" census is necessary but NOT sufficient for a per-origin gate: also check every producer SKIPPED/guarded when the decoration is already present (`if (!isInline)`, `if (!...findModifier<X>())`) — those are where one decoration silently absorbs a second, load-bearing reason. Provenance ⇒ purpose only if the attribute is the SOLE reason.
- A local fix to a SKILL-embedded generated tool self-reverts: the skill's Step-0 rewrites the script from the still-unfixed embedded copy on the next run. The durable fix edits the embedded script + prose + test in the canonical SKILL.md; a coworker skill that must reach multiple groups needs a real `container/skills/<name>/` home, or it has no propagation path.
- The `nv-slang-bot[bot]` App token cannot push `.github/workflows/*.yml` (no `workflows` scope) but CAN push `.github/actions/**/action.yml` composite actions. Fix the pushable composite action in the bot PR; document the identical `ci.yml` edit as a maintainer follow-up rather than blocking the whole PR.

## Diagnostic gates, ICE families, and where a compiler fix belongs

The recurring Slang triage shape is a malformed inst that reaches emit because the diagnostic that should have caught it was scoped too narrowly. An empty existential passed to a NON-entry-point helper that dynamically dispatches produced a cross-target ICE (spirv E99997 "Unhandled local inst", hlsl/glsl/metal/wgsl E99999, cuda exit 0) — because `diagnoseUnresolvedLookupWitnesses` scans only entry points (`if (!isEntryPoint(func)) continue;`), so routing the value through a non-entry helper hides the unresolved dispatch, which survives as a `FuncType` inst with a runtime operand and reaches the emitLocalInst default case ([entry-point-only diagnostic gate is an ICE escape hatch](../learnings/1786494483979-unhandled-local-inst-ice-family-entry-point-only-d.md)). The smoking gun was a code comment anticipating the escape ("the ICE still fires and points at the same source location") whose assumption was FALSE — a comment claiming a downstream safety net catches something must be verified to produce a *clean diagnostic*, not an ICE. Two transferable rules: a "spirv-emit ICE" is often a cross-target ICE class (run the per-target matrix; the reporter's target is just the one they tried), and the fix belongs in the pass that should have diagnosed/lowered the inst away, never a `case` in the emitter.

The idiomatic fix for a multi-pass crash is a validation pass + error gate BEFORE the transform passes, not per-site guards. A bodyless `[CudaKernel]` SIGSEGV recurred because there is no `getErrorCount()` gate between passes in a target's switch arm, so guarding one site (the `:1122` guard) just moved the crash to a different unguarded site (`generateCppBindingForFunc:394`), and `DiagnosticSink` does not dedup so two per-site guards emit the same diagnostic twice ([bodyless-kernel SIGSEGV must gate before all pytorch/cuda passes](../learnings/1786714887238-bodyless-kernel-sigsegv-fix-must-gate-before-all-p.md)). Mirror `diagnoseCircularConformances` (iterate funcs, diagnose bad ones, `if (sink->getErrorCount()!=0) return SLANG_FAIL;`) so downstream passes assume the invariant and stay unguarded. Scope hygiene comes from the decoration you check, and you must test EVERY reported cell on EVERY reported target — one triage tested a combined attribute only on `-target cuda` and missed the `-target torch` crash. And a tracking issue split from in-flight work describes the *fix* branch, not master: #12562's body claimed a diagnostic "now diagnosed as E58004" that exists nowhere at head (the 58xxx range ends at 58003), and its repro is only *observable* once the parent #12498 fix is applied — so `reproduced` is honest only with provenance, and the fix must be sequenced after the parent lands ([a follow-up issue split from a chain can describe a diagnostic that doesn't exist yet](../learnings/1786806563010-triage-12562-a-follow-up-issue-split-from-a-chain-.md)). Census a diagnostic-code family with a control before repeating the claim publicly.

## Shared IR decorations: gate the producer, not the consumer

Two closely-linked triage findings on slang#12623 (deferring user `[ForceInline]` to NVRTC on CUDA) establish a general rule about gating IR decorations. `kIROp_ForceInlineDecoration` is a **shared** op with no discriminating marker — added both by the user `[ForceInline]` lowering AND by compiler passes that REQUIRE the inlining to happen (constexpr-param auto-inline, buffer element pack/unpack, fuse-satcoop, bitfield accessors) — so a CUDA-wide skip of the arm defers those too and produces invalid CUDA; any deferral needs a NEW marker at the single user lowering site ([ForceInline is a shared IR decoration — deferral must gate only user-intent](../learnings/1787146185871-forceinline-is-a-shared-ir-decoration-cuda-forcein.md)). The companion refutes the tempting census-based safety argument: "exactly 1 user producer + ~20 compiler ones, gate only the user arm" is TRUE but NOT sufficient, because a per-origin gate is safe only if *provenance ⇒ purpose* — and the constexpr-rate-param force-inline is wrapped `if (!isInline)`, which the user branch already set, so for `[ForceInline] void f(constexpr int n)` the user's decoration is silently doing double duty as the compiler's correctness-inline, and gating "defer when user-marked" drops that guarantee ([a single-user-producer census does not clear a per-origin gate](../learnings/1787149294286-a-single-user-producer-census-does-not-clear-a-per.md)). When a change gates/defers/strips a decoration by origin, additionally grep every insertion site for `if (!isInline)` / `if (!...findModifier<X>())` guards — those are where one decoration absorbs a second load-bearing reason — and the principled fix is producer-side: make the compiler add its OWN decoration for the real reason regardless of the user attribute. (Also reusable: to check whether a new IR op can ride along onto compiler-built functions, audit every `for (auto d : inst->getDecorations())` clone loop — in Slang they are all op-filtered, so a new op only propagates where a `case` is explicitly added.)

## Where a coworker fix must live to propagate

Two tooling-propagation facts. A local fix to a SKILL-embedded generated tool self-reverts: okf-synthesis's SKILL.md instructs the agent to rewrite the embedded script "verbatim … overwrite each run so SKILL.md stays the source of truth," so a fix to the generated `okf_synth.py` survives only until the next fold, and okf-synthesis has no `container/skills/` home in the repo (unlike its committed siblings) so there is no propagation path to other groups at all ([a local coworker-skill fix is clobbered by the skill's own Step-0 rewrite](../learnings/1787117960695-a-local-coworker-skill-fix-is-clobbered-by-the-ski.md)). The durable fix edits the embedded script + prose + test in the canonical SKILL.md, and a multi-group coworker skill needs a real repo home; before relaying "general fix, free for all groups," verify the change lives in the source every group writes from, not one group's generated copy. Finally, a push-permission fact: the `nv-slang-bot[bot]` App token cannot push `.github/workflows/*.yml` (lacks the `workflows` scope — "refusing to allow a GitHub App to create or update workflow") but CAN push `.github/actions/**/action.yml` composite actions ([App token cannot push .github/workflows but CAN push .github/actions](../learnings/1787124772122-nv-slang-bot-app-token-cannot-push-github-workflow.md)). Since the cross-repo "SlangPy Tests" check runs via a composite action with its own upload/test steps, fix the pushable composite action in the bot PR and document the identical `ci.yml` edit as a maintainer follow-up rather than blocking the whole PR on the workflow-file half.
