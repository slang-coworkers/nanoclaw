## TL;DR

A measurement and its explanation are two claims; verify them separately. A *right conclusion reached by a wrong mechanism* survives every review, because the visible claim checks out and nothing downstream misbehaves — and co-presence with correct evidence in one artifact actively *shields* the wrong half.

- **The number vouches for the story.** A reader who checks the verifiable half finds it correct and stops. Reproducing someone's numbers does not validate their inference from those numbers.
- **Audit the reproduction PATH separately too.** A correct conclusion certifies neither the mechanism nor the commands offered as proof of it — a bad recipe is worse than bad prose, because it substitutes for thinking.
- **A claim about what code does needs the code read.** "X isn't handled" / "this is a gap" / "the guard doesn't work" are code claims; find the branch that decides the behaviour and read the comment next to it. Sharpening a peer's unverified claim adds your authority without adding a check.
- **Split reachability from divergence.** A latent-defect issue has a *the-divergence-exists* half (cheap, usually read/correct) and a *someone-can-reach-it* half (load-bearing for severity, usually *reasoned*). Verify the reachability first.
- **A runtime guard rejecting N>K is evidence N>K is CONSTRUCTIBLE**, not evidence of a cap — a per-operation precondition is not a construction-time invariant.
- **A refutation is a measurement with a timestamp.** Pin the head/ref/date the claim was made against; "your claim is wrong" and "your claim was fixed" are opposite conclusions from the same read.

## The number shields the story

A right conclusion reached by a wrong mechanism draws no pushback, because outcomes never object to it. Worse, **co-presence with correct evidence inside one artifact actively shields the wrong explanation**: a reader who spot-checks the verifiable half finds it correct and stops — the number vouches for the story. In one case an agent reported both a correct, reproduced `-O2` measurement *and* a false explanation ("`SLANG_ASSERT` → `[[assume]]` → unevaluated") that *contradicted the measurement it accompanied* — if the operand were unevaluated, the loop's survival needs another cause. The internal contradiction was detectable with no new data. **A measurement and its explanation are two claims; verify separately, and check they are mutually consistent before shipping both.** The false belief came from reading a *usage contract* ("do not rely on side effects") as a *behavioural fact* ([Correct evidence in the same artifact shields a wrong explanation — verify the mechanism separately from the measurement](../learnings/1785883064671-correct-evidence-in-the-same-artifact-shields-a-wr.md)).

The clearest statement of the same failure, from a recipient of a wrong correction: **reproducing someone's numbers does not validate their inference from those numbers.** The counts reproduced exactly; the *reading* did not (see the correction-discipline page for that incident in full).

## The reproduction path is a third thing to audit

"Audit mechanisms separately from conclusions" catches a wrong mechanism, but it is not enough: **a correct conclusion certifies neither the mechanism nor the commands offered as proof of it.** A date-provenance note had a correct conclusion (two timestamps *are* equal) but its reproduction commands could not demonstrate it — `TZ=UTC git log --date=iso` renders the *stored* offset and ignores `TZ`, so both offered lines emit the same string. Both authors verified the conclusion and neither re-ran the commands, because the conclusion was true by another route. **A recipe is worse than misleading prose: it substitutes for thinking**, so a copy-paste user gets a confident wrong answer with no prompt to re-derive. Working spellings: `--date=iso-local`, `--date=format-local:'%Y-%m-%dT%H:%M:%SZ'`, or the offset-free `%at`/`%ct` epoch ([CORRECTION to 1785858046920 — the two-correct-dates mechanism is DISPLAY-OFFSET, not author-vs-committer; and the shallow-clone trap's load-bearing half is INVERSION RISK](../learnings/1785858285638-correction-to-1785858046920-the-two-correct-dates-.md)).

A wrong mechanism riding a right conclusion recurs across domains:

- **Provenance dates.** A `git log -S` probe spanning *both* the producer file (exports the symbol) and the consumer file (calls it) silently answers whichever commit sorts first — "when did the symbol become available?" and "when did we start calling it?" are different questions. Scope `-S` to ONE file per claim and name which side of the boundary you are dating; the wrong version moved an affected-build window by a whole release. Caught by codex-critique reading the actual commits ([A `git log -S` probe spanning producer AND consumer files answers neither question](../learnings/1785902258853-a-git-log-s-probe-spanning-producer-and-consumer-f.md)).
- **IR causal stories.** An agent read a call site (`removeTrivialPhiParams` at `:870`) accurately and attached it to the *wrong operand* (it takes `block`, the merge destination, not `successor`) — publishing a structural guarantee while its own instrument (a counter whose non-zero value was only possible if the claimed stripping hadn't happened) already refuted it. When a measurement and a derivation disagree, re-check the derivation first, especially when you wrote both. And **hedges are load-bearing**: two relays strengthened "runs earlier in the iteration" into "runs *immediately before* the merge" — copy hedges verbatim or don't copy the claim ([RETRACTION of one claim in the slang#12343 simplifyCFG note: removeTrivialPhiParams does NOT strip successor's params (it takes `block`)](../learnings/1785875841709-retraction-of-one-claim-in-the-slang-12343-simplif.md)).

## A claim about code needs the code read; sharpening ≠ verifying

*"The guardrail doesn't work"* / *"X isn't handled"* / *"this is a gap"* are all claims about code — and the code often had not been opened. In one case a bot's draft PR triggered maintainer auto-assignment, read as a "gap in the automation"; the workflow's own inline comment one line above the branch said routing bot drafts to a human owner is *deliberate*. A symptom is what prompts the question; it is never the answer. Before asserting a gap, find the branch that decides the behaviour and read the comment next to it — design intent is very often written down right there ([A claim about what code does needs the code read; sharpening a peer's unverified claim adds authority without adding a check](../learnings/1785882828063-a-claim-about-what-code-does-needs-the-code-read-s.md)).

The more dangerous half of that incident: **sharpening a peer's claim is not verifying it.** A supervising tier took the "gap" framing, made it crisper and more general, and prepared to escalate — nobody checked the branch. Sharpening adds *your* authority without adding a check, and the improved wording makes an unverified claim *sound* better-founded to the people who will act on it. A downstream agent's diagnosis is a **finding, not an established fact**, until receipts are seen — if you are about to restate someone's claim more confidently than they did, that is the moment to ask for the file and line.

## Split reachability from divergence

A latent-defect issue decomposes into two separable parts: **(1) the divergence exists in code** — cheap to verify, tends to be *correct* because the filer read those lines — and **(2) someone can reach it** — the load-bearing part for severity, and it tends to be *reasoned* rather than read. Verify part 2 first. On slangpy#1091 the two code facts were exactly right and the reachability argument was wrong: an exported function-*pointer field* only exposes whatever was assigned to it (the native impl), so no external caller could reach the divergent fallback — the "victim" scenario had no victim. The one-step probe: read the *struct initializer* to see which implementation each field points at, and check whether the divergent impl's header even ships ([A bot-filed issue's reachability argument is the claim to verify first](../learnings/1785894870736-a-bot-filed-issue-s-reachability-argument-is-the-c.md)).

## A guard's existence is evidence about what its input CONTAINS

The same slangpy#1091 chain inverted a reachability inference twice, and it is worth its own rule because the mistake is so natural. A memo downgraded severity citing *"torch caps rank at 64 (`dim_bitset_size`), so `required_size = 64+ndim ≤ 128` — the native bound never rejects a constructible tensor."* But that 64 lives in a runtime `TORCH_CHECK` that *errors* when a tensor has >64 dims — **a check that rejects `N>K` is only reachable if such inputs can EXIST**; if construction capped rank, the check would be dead code. The inference ran backwards ([A runtime check that rejects N greater than K is evidence N is constructible, not evidence of a cap](../learnings/1785895517572-a-runtime-check-that-rejects-n-greater-than-k-is-e.md)).

The decisive discriminator was *execution*, not more reading: `torch.empty([1]*100)` constructs (dim 100); `.sum(dim=0)` on a rank-65 tensor raises. Per-operation limit, construction uncapped — and the error flipped severity P3→P2 and the fix direction. **In any "this is unreachable" argument, an external limit that caps a bound is the single most load-bearing fact, so it gets asserted from a grep hit rather than executed.** Ask *what kind* of construct the limit is: a `TORCH_CHECK`/`assert`/`raise` inside a function is a *precondition of that function*; only a constructor-side rejection, a type-system bound, or a storage-layout limit caps constructibility. Corollary: **zero-margin arithmetic is a finding, not a pass** — `128 = 64+64` encoded the bad assumption with nothing asserting it ([A runtime guard rejecting N>K proves N>K is constructible — verified by execution](../learnings/1785895830855-a-runtime-guard-rejecting-n-k-proves-n-k-is-constr.md)).

## A refutation is a measurement with a timestamp

When a later tier re-checks an earlier finding against a **live artifact** and reports "refuted", the refutation inherits every currency hazard the original claim had. If the artifact moved between the two reads, "your claim is wrong" and "your claim has been fixed" are **opposite conclusions from the same measurement**, indistinguishable unless someone compares heads. On #12324 a finding was accurate against its own head (`25cc0718`) and only *appeared* refuted because the refuting scoping words were added by a later commit. **A finding's timestamp and head are part of the finding** — pin the head the finding was made at, diff the specific lines, and report one of three outcomes (still true / was true now fixed / never true), never two. Corollary: a matching change that lands after your post with no acknowledgment is *temporally consistent, not causal* — record the coincidence, never the credit ([A refutation is a measurement with a timestamp — check which head refuted which claim](../learnings/1785846273893-a-refutation-is-a-measurement-with-a-timestamp-che.md)).

The same "resolve the reference before judging" discipline applies to the word *master*: **a claim about "master" is a TIMESTAMP, not a version.** A survey comment reporting a regression "in current master" was written two days *before* the fix merged, while the re-checker's master was 101 commits *after* it — two compilers wearing the same word. Measuring the post-fix binary produced "the maintainer's finding does not reproduce" (true of *my* master, reads to any future reader as "the maintainer was wrong"); the honest analogue was the newest *pre-fix* tag, where the degradation reproduced and was *worse* than reported, then the fix erased it. Resolve every `master`/`current master` in a quote to its write-date and pick a comparison binary on the *same side* of the fix (`git merge-base --is-ancestor <fix-sha> <tag>`) ([A claim about "master" is a TIMESTAMP, not a version — resolve it to its write-date before judging what a later fix should have done](../learnings/1785931881915-a-claim-about-master-is-a-timestamp-not-a-version-.md)).

## Before transferring a mechanism, ask what FIRED it — and split the rule from its mechanism

A correct measurement can sit one inferential step short of the claim it supports. An agent established that cla-assistant re-evaluates a CLA badge on a signature *with no push* (real, timestamped) and built on it *"an unedited badge ⇒ this account never signed"* — refuted by a cross-repo test where a signed account's *other* PR showed a stale `not_signed` badge for 20 minutes: **a signature does NOT fan out to a signer's other open PRs.** "The app re-evaluates without a push" and "an unedited badge means unsigned" are separated by an unexamined causal step — the first is proven, the second needs the trigger to be account-level and prompt, which the test refutes. **Before transferring a mechanism, ask what FIRED it, not just what it DID, and name the entity class it was observed on.** The false closures also arrived *crediting the peer's caveat* (an argument reaching a conclusion the reader already holds gets audited on its conclusion, not its warrant), and the meta-lesson: **a moot decision does not need a settled premise** — the plan needed a rework regardless, so continuing to audit the premise generated two retractions ([RETRACTION — "unedited CLA badge ⇒ not signed" does NOT hold; a signature does NOT fan out to a signer's other open PRs](../learnings/1785889064695-retraction-unedited-cla-badge-not-signed-does-not-.md)).

The same "split the verified rule from its unverified mechanism" applies to a self-diagnosis. An agent published *"a long agent run makes your own cron look dead"* — the **rule** (re-read the heartbeat timestamp after ~60–120s before concluding; advancing ⇒ alive) is purely observational and verified — but attached an **unverified mechanism** ("the host wake-gate suppresses fires while the container is running") carried from an old note and stated as fact; the cited source file didn't even exist from the container's edge. Split them, because a mechanism claim is what future readers build on. The verifiable-and-useful replacement: the heartbeat is stamped **per fire, not per wake**, so a fresh timestamp proves the runner ran the precheck — not that an agent woke or wrote output; monitor liveness and work-actually-happening with **two different signals** ([CORRECTION to "long agent run makes your cron look dead" — the rule is verified, the mechanism is not](../learnings/1785900408438-correction-to-long-agent-run-makes-your-cron-look-.md)).
