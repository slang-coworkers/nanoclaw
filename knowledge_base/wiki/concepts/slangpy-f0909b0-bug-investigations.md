## TL;DR

Root-cause investigations crossing the slangpy → slang-rhi → slang boundary:

- **#222 (AMD-Windows autodiff grads wrong)** is a slang-rhi bug: it advertises float-atomic-ADD off the BASE atomics bit, so on RDNA2 iGPUs Slang legally emits `OpAtomicFAddEXT` and the driver mis-executes. `[72,0,0,0]` = every gradient atomic-added into element 0 (scatter-address bug), not zero gradients; "always 0" matched only D3D12.
- **#665 ("Failed to get binding data")** is upstream slang-rhi, D3D12-only, and silently swallowed (bare `return;` skips the dispatch): fixed-pool exhaustion under slangpy's zero-backpressure submits, not a leak. The maintainer's A/B pinned the per-command-buffer 4 MiB constant-buffer pool (slang-rhi#844), not the descriptor heap static triage suspected.
- **CPU-backend dispatch regression (#1136/#1137)**: the slang-rhi CPU device alone leaves `maxComputeDispatchThreadGroups` at `{0,0,0}`, so PR #995's clamp yields 0 → throw. Durable fix: Metal's `0xFFFFFFFF` sentinel; a slangpy fallback must cover X, Y and the generator. Crossing a Y row on CPU costs only ~3–5 s/case.
- **Current-device stack (slang#13558)**: `publish()` pushes every device, `shutdown()` pops only the top, so closing the older of two devices first leaves a dangling `Device*` (UBSan invalid vptr / segfault). Serial pytest only; read the nightly sanitizer log first.
- **`ComputeKernel.dispatch(**kwargs)` and cursor dict writes ignore non-field keys (slangpy#1231)**: a misplaced global or misspelled key stays unbound (CPU segfault, CUDA later readback failure, Vulkan no-op). The approved fix (PR #1234) checks in the shared `cursor_utils.h` dict-to-struct writer, not the dispatch lambda.
- **SHADER_PATH**: since #1183 the binding lambdas prepend `slangpy.SHADER_PATH` unconditionally (never C++ core); module-level `spy.create_slang_session()` and a no-device `spy.App()` bypass it (slangpy#1238).
- **Cross-repo triage**: a vendored dep in `external/` is not proof of integration (check call sites); stale architecture-refactor issues are prime silently-fixed orphans; DeepWiki gets "does X inherit Y" confidently wrong.
- **Static struct members (slangpy#126)** are absent from `Type.fields` and silently dropped by `InstanceList`; detect them via `DeclReflection`.
- **`GridArg.__slangpy_load<D>` indexes `int[N]` with `D`**, safe only because explicit `.map()` on a grid is rejected; adding `reduce_type` needs indexing by `N` or `assert D == N`.
- **A direct-bound struct/dict argument never runs its fields' `gen_calldata`**, so a leaf-marshall check misses tensors inside parameter structs. Walk `binding.children` in the `direct_bind` branch; test new checks with a direct-bound struct.

## #222 — AMD-Windows autodiff gradients: a scatter-address bug, root-caused to slang-rhi

slangpy#222 "AD doesn't work, gradients are always 0" (AMD RX 6600 / Win11) framed it as zero gradients, but the numbers say otherwise. On the docs `polynomial` example the correct grad is `[12,16,20,24]` (sum 72); the reporter's AMD iGPU produced **Vulkan `[72,0,0,0]`** and **D3D12 `[0,0,0,0]`**. `[72,0,0,0]` means every gradient was computed and atomic-added into element 0, a scatter *address* bug. "Always 0" matched only D3D12 (the real diagnosis sat in an unlinked Discord thread). A discrete AMD 9070 XT on Linux was correct (scope: the AMD-Windows driver). A title or label is a claim: compute what a nearby defect would produce and check the numbers [#222 title wrong](../learnings/1786461616442-slangpy-222-title-is-wrong-amd-windows-grads-colla.md).

The Vulkan arm is a **slang-rhi** bug. In `src/vulkan/vk-device.cpp:822-830` the `SIMPLE_EXTENSION_FEATURE` macro (gated on the `s.m` bit) is instantiated with `m = shaderBufferFloat32Atomics` (BASE float atomics) but pushes `Capability::SPV_EXT_shader_atomic_float_add`; `shaderBufferFloat32AtomicAdd` is never read. On a device with base atomics but no AtomicAdd (RDNA2 iGPU), Slang legally emits `OpAtomicFAddEXT` (no runtime fallback once the profile carries the atom) and the driver silently mis-executes. **Coarse-feature trap:** `Feature::AtomicFloat` is one bit set off the base atomics bit, so a SlangPy `hasFeature(Feature::AtomicFloat)` guard would still pass on an add-less device; the fix needs finer granularity in slang-rhi. A capability atom in a SPIR-V profile is not evidence the device supports the op (check vulkaninfo); root-causing Vulkan doesn't root-cause the D3D12 arm; the fix is cross-repo (upstream draft via the slang chain, back via a pin bump) [#222 root cause](../learnings/1786485429694-slangpy-222-root-cause-slang-rhi-advertises-float-.md).

## #665 "Failed to get binding data" — D3D12-only fixed-pool exhaustion, silently swallowed

`[ERROR] (rhi) layer: Failed to get binding data` (slangpy#665, D3D12 training loops) is upstream slang-rhi. `command-buffer.cpp` `writeComputeState`/`writeRenderState`/`writeRayTracingState` log it when `getBindingData()` fails, then bare `return;` without writing the pipeline command: the dispatch is skipped and results are silently wrong. SlangPy has zero backpressure (`NativeCallData::exec` makes a fresh encoder per dispatch; `submit_command_buffer` never waits) while arenas are reclaimed only at fence retirement, so a tight loop outpaces reclamation on a FIXED D3D12 pool. Not a leak (CUDA/Vulkan analogues are high-water-mark). Workaround: `device.wait_for_idle()` (or periodic `wait_for_submit(id)`) in the loop [#665 swallowed](../learnings/1787226423616-slangpy-665-failed-to-get-binding-data-descriptor-.md).

The error is **structurally D3D12-only**: the log line is backend-agnostic, but the failure reaching it (`getBindingData` → `BindingDataBuilder::bindAsRoot` returning SLANG_FAILED) comes only from D3D12's fixed shader-visible heaps; Vulkan's `DescriptorSetAllocator` grows pools on demand and CUDA uses a growable `ArenaAllocator`. Repro on Windows/D3D12 (`step_05_latent_texture.py`) logging `device.report_heaps()` per iteration, not Linux [#665 D3D12-only](../learnings/1787763717844-slangpy-665-failed-to-get-binding-data-is-structur.md).

How the resource was found is the lesson. Static triage first suspected the descriptor heaps: CBV/SRV/UAV holds 1,000,000 but the **sampler heap 2,048**, so a Texture2D+Sampler-per-dispatch kernel would exhaust it ~500× sooner [sampler heap hypothesis](../learnings/1787226766619-slangpy-665-d3d12-sampler-heap-is-the-tight-bottle.md). The maintainer's runtime A/B (constant-buffer page size 4 MiB → 64 KiB let 10 frames complete; baseline failed at frame 2) instead pinned the **per-command-buffer 4 MiB constant-buffer pool** (slang-rhi#844): mechanism *shape* right, *resource* wrong. Without a runtime repro, state the shape confidently and label the resource a hypothesis; an A/B page-size experiment discriminates pools; and re-read the latest issue comments before posting, since a sibling `nv-slang-bot` session may have re-asserted the wrong hypothesis as the last bot word (shared-bot-identity hazard, confirmed live) [shape right, resource wrong](../learnings/1788354683528-slangpy-665-static-triage-got-the-mechanism-shape-.md).

## CPU-backend dispatch regression (#1136/#1137/#1138)

In slangpy 0.43.0 every `DeviceType.cpu` dispatch throws `RuntimeError: Device reports zero compute dispatch groups in X` (`slangpy.cpp:103`; 0.42.0 fine; GPU unaffected). The slang-rhi CPU device is the **only** backend that never populates `DeviceLimits::maxComputeDispatchThreadGroups`, and `DeviceLimits` has no default initializers, so it stays `{0,0,0}`; PR #995's clamp computes `min(0, huge) == 0` and `SGL_CHECK(dispatch_groups_x > 0)` throws. The durable fix mirrors Metal's `0xffffffff` ×3 sentinel for a backend with no hardware grid bound. Relaxing only the slangpy `SGL_CHECK` is a trap: the throw moves to the Y check (also 0), and `generator.py` emits `dispatch_group_x_stride = 0`, corrupting the group-id flatten. A slangpy fallback must cover X, Y and the generator; the RHI fix covers all three [#1136 zero limit](../learnings/1788474155417-slangpy-cpu-backend-zero-device-dispatch-limit-bre.md).

Fix PR #1137 surfaced pytest facts. `plugin.py`'s `pytest_runtest_setup` treats a test as a *device* test only if it has a `device_type` parameter (else SKIPPED under any `--device-types`), so a CPU-specific test is `@pytest.mark.parametrize("device_type", [DeviceType.cpu])`. `DEFAULT_DEVICE_TYPES` never includes cpu, which is why the regression shipped. The slangpy fallback (0 = unbounded: X→ceiling, Y→UINT32_MAX) is a provable no-op once rhi reports a real limit. slang-rhi disables CPU only in its OWN Linux test harness, not as a slangpy runtime restriction. With the throw removed, `test_pass_float_array` SEGFAULTS in CPU array marshalling, a separate pre-existing defect [#1137 pytest](../learnings/1788480806317-slangpy-cpu-dispatch-zero-devicelimits-stale-local.md).

Review of #1137 asked for CPU coverage crossing a **second physical Y dispatch row** (~67.1M threads: 2097151 groups × 32). The sentinel-marker tests in `test_large_dispatches.py` ran ~3–5 s per case on CPU debug, so the fix added `DeviceType.cpu` to their parametrization, computed the expected row stride with `resolve_max_dispatch_groups_x()`, and treated `limits.y == 0` as unbounded instead of skipping. A mutation check (restoring the zero-stride generator) failed the grid and `call_group` cases, so the tests pin the codegen wiring. PR-body delivery-gate limits are on [the delivery-gates page](agent-routing-f0909b2-critique-and-delivery-gates.md) [Y row is cheap](../learnings/1791353262348-cpu-large-dispatch-coverage-in-slangpy-crossing-th.md).

The unmasked segfault (slangpy#1138) is a layer-localization exercise: `float first(float x[3])` called with a Python list segfaults on `DeviceType.cpu` but works on every GPU backend. Ruled out: slangpy_ext marshalling (backend-agnostic; bounds guards *throw*) and slang-rhi CPU binding (generic ordinary-data memcpy). What remains CPU-unique is the compiler's host-callable compile and the layout it reports for a fixed-size `float[N]` uniform; a reflection probe printing `getElementCount()`/`getElementStride(UNIFORM)`/offset confirms it (zero or garbage = CPU-target layout bug). "GPU works, CPU crashes" with an opaque-bytes RHI path and a backend-agnostic slangpy path ⇒ compiler CPU-target bug, fixed at the legalizer/consumer, not by rejecting the shape upstream [#1138 localization](../learnings/1788481634992-localizing-a-cpu-only-slangpy-segfault-to-a-layer-.md).

## Current-device stack: auto-push plus top-only pop leaves a dangling `Device*` (slang#13558)

SlangPy keeps a thread-local `std::vector<Device*>` current-device stack (main ce68ef8): `Device::publish()` pushes *every* created device, but `Device::shutdown()` pops only when `back() == this`. Closing the OLDER of two live devices first, as `helpers.close_leaked_devices` does (it walks `get_created_devices()` in creation order), leaves its freed pointer in the stack. The next `spy.pop_current_device()` / `current_device()` hands it to nanobind, whose `typeid(*ptr)` (`nb_cast.h:492`) yields a UBSan "invalid vptr", a segfault, or an `Object::set_self_py ... already present` abort. Trigger: `test_compiler_profiles.py::test_cuda_profile_cache` (two `with spy.Device()` in a loop), crashing later in `test_device_api.py`. A first device also survives Python rebinding, since its default `SlangSession` holds a strong `ref<Device>` until `close()`. It crashes only in **serial** pytest (nightly `sanitizers.yml`, or local `pytest slangpy/tests`); GPU CI's xdist splits the two tests across processes. For a crash that looks platform-specific, read the nightly serial asan-ubsan log first (symbolized UBSan frame, exact stop point) [dangling Device*](../learnings/1791595717857-slangpy-current-device-stack-auto-push-top-only-po.md).

## `ComputeKernel.dispatch` and cursor dict writes silently drop unknown keys (slangpy#1231)

`kernel.dispatch(thread_count, buf=b)` for a global `buf` (which belongs in `vars=`) raises nothing and leaves `buf` unbound; so does a misspelled `vars` key. The dict-to-struct write (`src/slangpy_ext/device/cursor_utils.h:798-810`, numpy twin :553-565) loops over the struct's FIELDS checking `dict.contains(name)`, so non-field keys are never visited. Effect by backend (L40S, main b89a3827 and 0.43.1): CPU segfaults; CUDA's dispatch returns no error, then the next readback fails with `CUDA_ERROR_ILLEGAL_ADDRESS` and shutdown aborts ("Failed to reset slang-rhi task pool"); Vulkan is a silent no-op. No unbound-resource check exists in SGL, slangpy, or slang-rhi's CPU/CUDA/Vulkan backends (slang-rhi#901: WebGPU only). `kernel.reflection.find_field(n).is_valid()` holds only for globals, `kernel.reflection[<entry>].find_field(n)` only for entry-point params (`slangpy/testing/helpers.py:413` routes names this way). Triage first recommended the dispatch lambda, fearing that `Function.set()` uniforms, `dispatchdata.py` and marshalls like `builtin/tensor.py:169` rely on the permissive loop [#1231 keys dropped](../learnings/1792162048265-slangpy-computekernel-dispatch-shadercursor-dict-w.md). The maintainer's design review on PR #1234 (ccummingsNV, 2026-10-29; approved 11-04) put the check in the shared writer instead, plus its `write_from_numpy` twin: a fast path counts the fields it writes, and if the dict has more keys a slow pass names them ("No field named ..."). A dispatch-side dict walk skipped `WriteConverterTable.write` for the top-level object, and the shared check covers every `ShaderCursor.write(dict)` caller. An L40S sweep (Vulkan+CUDA, `tests/device` and `slangpy_tests`) found no existing caller hitting the new error; the one silent drop it caught was in a test. Read the current PR before reusing the dispatch-only advice [fix lives in cursor_utils.h](../learnings/1794236212823-slangpy-1231-fix-lives-in-the-shared-cursor-utils-.md).

## Triage discipline: silently-fixed orphans, unintegrated vendored deps, and DeepWiki

Verify against primary source before treating an issue as open work or trusting a confident claim.

**Check upstream first for `external/slang-rhi` meta-issues.** slangpy#805 ("apply allocator improvements across all slang-rhi backends") is largely solved upstream: D3D12MA is merged and wired, but VMA is vendored (`external/vma/`) yet NOT wired; the Vulkan backend still calls raw `vkAllocateMemory()`, with the heap wiring stuck in a stale OPEN PR. A vendored dependency is not proof of integration (grep `src/vulkan/` for `vmaCreate`/`VmaAllocator`). For a cross-repo meta-issue the triage output is "no SlangPy PR possible; escalate upstream coordination + priority", never a fixer patching `external/slang-rhi` from a SlangPy PR [#805 upstream](../learnings/1787226230030-allocator-meta-issue-slangpy-805-is-largely-alread.md).

**A stale architecture-refactor issue is a prime silently-fixed candidate.** slangpy#795 ("move tensor types from extension layer into core SGL") is a fixed-not-closed orphan: the nanobind-free `Tensor` + `TensorDesc` exist on `main` (the doc comment "This class deliberately contains no language-binding dependency" is verbatim the issue's goal), landed by three PRs in its milestone with 0 cross-references. DeepWiki and subagents said "already done" with the NEW names while the issue used OLD ones; that mismatch is the tell. Re-derive from primary source (0 old names in `src/`, `git log -S` on a non-shallow checkout, `gh api issues/<n>/timeline`) before publishing [#795 orphan](../learnings/1787226338570-slangpy-795-tensor-move-already-landed-silently-fi.md).

**DeepWiki gets "does X inherit/propagate Y" confidently wrong.** For slangpy#886 it claimed `device.create_slang_session()` "inherits the include paths from the Device's default SlangSession if add_default_include_paths is True". It did not: the binding called straight through with its own `SlangSessionDesc`, `add_default_include_paths` only adds `platform::runtime_directory()/"shaders"`, and only the Python `create_device` wrapper injected `SHADER_PATH`, seeding just the device's *default* session. The clean fix inherits `device.slang_session.desc.compiler_options.include_paths` [#886 DeepWiki wrong](../learnings/1787226621145-slangpy-create-slang-session-does-not-inherit-devi.md).

## SHADER_PATH default include paths (#886, #1177 → #1183; gaps in #1238)

**One injection point was the root cause.** #1177 is the raw-constructor twin of #886: `spy.Device()` (native class, empty `SlangCompilerOptions{}` by default) + `spy.Tensor.from_numpy(...)` failed with `SlangCompileError: cannot open file 'slangpy.slang'` via `Device::builtin_layout()` → `load_module("slangpy")`, while `spy.create_device()` worked because its Python wrapper (`slangpy/core/utils.py`) was the ONLY place prepending `SHADER_PATH` (the `slangpy/slang` dir); While #886's design was held, the interim plan was an actionable error at `_get_lookup_module` (`slangpy/reflection/lookup.py`, the narrowest spot holding both device and `SHADER_PATH`) [#1177/#886 one root cause](../learnings/1790019427102-slangpy-spy-device-vs-create-device-shader-path-in.md).

**The right layer is the nanobind binding lambda, not the C++ core.** PR #1182 merged the default session's include paths with the caller's in the binding lambda. Core `Device::create_slang_session` is wrong: the default session bootstraps through it while `m_slang_session` is still being assigned, so core inheritance would deref a null/half-set `slang_session()`. Inherited paths go first so user paths don't shadow defaults on a filename collision; dedup is lexical `std::filesystem::path operator==` (canonicalizing touches the FS and changes symlink semantics; duplicates are harmless). #1182 left the free function `spy.create_slang_session()` un-inherited (maintainer scope guard) [binding lambda](../learnings/1790111150088-slangpy-create-slang-session-include-path-inherita.md).

**Current truth: PR #1183 superseded #1182 and #1178 (both closed unmerged).** It fixes #886 + #1177 with the broad default-on design @ccummingsNV / @kaizhangNV asked for (no opt-out kwarg). A file-local `std::vector<std::filesystem::path> g_default_slang_include_paths` (anonymous namespace in `src/slangpy_ext/device/device.cpp`) is set once at import by `_set_default_slang_include_paths([SHADER_PATH])` from `slangpy/__init__.py`: SHADER_PATH is a Python-package path, so Python registers it and core SGL stays package-agnostic. `prepend_default_slang_include_paths()` (defaults-first, dedup via `std::find`) runs **unconditionally**, not gated on `add_default_include_paths`, at three binding sites: both `Device` ctor bindings (the `DeviceDesc` one takes the desc BY VALUE so a caller-owned desc isn't mutated) and `device.create_slang_session`. `create_device`'s manual prepend was removed; sessions get only the global default, not device-specific paths. **Pyright scope gotcha:** a bare `pyright slangpy/<file>.py` reports `reportUndefinedVariable` for runtime-injected native symbols, but CI ignores it because `pyproject.toml [tool.pyright] include = ["./src","./tools","./examples"]` excludes `slangpy/`; judge CI impact by the `include` roots [#1183 unified](../learnings/1790185684802-slangpy-1183-unified-shader-path-default-include-p.md).

**Paths that bypass #1183 (slangpy#1238).** The prepend helper (`device.cpp:279-302`) runs only inside binding lambdas (the `Device` ctor bindings and `Device.create_slang_session`). Two public paths reach core SGL instead, get `include_paths == []`, and fail `import slangpy;` with E00001 `cannot open file 'slangpy.slang'` (main e7bb2242, Vulkan and CUDA on the L40S):
1. Module-level `spy.create_slang_session()` and `spy.create_slang_session(SlangSessionDesc)` (a lambda and a direct `nb::overload_cast<SlangSessionDesc>`) go to SGL `create_slang_session` → `current_device()->create_slang_session()`. A `with device:` scope doesn't help (#1183 scoped this path out). Fix: call the helper in the lambda, and replace the direct `overload_cast` with a by-value `SlangSessionDesc` wrapper lambda that prepends to `desc.compiler_options`.
2. `spy.App()`, `spy.App(spy.AppDesc())` and `spy.App({})` with no device: both overloads (`src/slangpy_ext/app/app.cpp`) pass null, and `src/sgl/app/app.cpp:16` calls core `Device::create()` with a default `DeviceDesc`, so `app.device.load_module*` and `spy.Module.load_from_source(app.device, ...)` fail. `App` is headless, so it reproduces in a container. Fix: give the helper external linkage and a shared header, and build a prepended `DeviceDesc` in both overloads when no device is passed.

Workarounds: `device.create_slang_session()`, `App(device=spy.create_device(...))`, or `include_paths=[spy.SHADER_PATH]`. An `App` regression test needs a `device_type` parameter (else skipped under `--device-types`; see [SlangPy build/CI toolchain](slangpy-f0909b0-build-ci-toolchain.md)) and a fresh device per `App`, since `sgl::App::~App()` closes even a caller-supplied device. DeepWiki (2026-10-20) still claims `create_device` prepends `SHADER_PATH` in Python, which #1183 removed [module-level create_slang_session](../learnings/1792463190116-slangpy-module-level-spy-create-slang-session-stil.md), [App() default device](../learnings/1792463898060-slangpy-spy-app-default-device-misses-shader-path-.md), [both paths bypass](../learnings/1792464645928-slangpy-1183-shader-path-prepend-is-bypassed-by-fr.md), [device_type tests; App() closes device](../learnings/1792466654227-slangpy-tests-no-device-type-param-skipped-under-d.md).

## Static struct members are invisible to `Type.fields` (slangpy#126)

`Struct.struct.fields` (native `StructType::build_fields`, `src/sgl/refl/type.cpp`) comes from Slang's `TypeReflection::fields()`, which excludes static members, so `static const int b = 5;` is absent. A dict argument naming it fails clearly ("has no field 'b'", `boundvariable.py`), but `InstanceList.__setattr__` (`instance.py`) silently stores it as a Python attribute. To tell a static member from a typo, walk `device.load_module(path).module_decl.find_first_child_of_kind(DeclReflection.Kind.struct, "Test").children` and test `c.as_variable().has_modifier(ModifierID.static)`. `spy.Module(...).device_module.module_decl` raises for composed modules, so walk `device_module.source_modules` or add a native helper. Since Slang #7993 (2025-07-30) `static const T x;` without an initializer is load-time error E31225, so old repros fail at `Module.load_from_file` [static members](../learnings/1792065039736-slangpy-detecting-static-struct-members-type-field.md).

## `GridArg`: explicit `.map()` is rejected, so `D == N` always holds (slangpy#1254 review)

In `slangpy/slang/gridarg.slang`, `GridArg<let N>.__slangpy_load<let D>` indexes the struct-sized `int[N] offset/stride` with the method's `D`. That is safe today because no public path makes `D ≠ N`: `GridArgMarshall.resolve_dimensionality` returns `self.dims` (the kernel gets `ContextND<dims>`), `resolve_type` accepts only `VectorizeGridArgTo<..., dims>`, and an explicit `func.map((0,1,2))(grid(...))` fails with `ValueError: ... RuntimeError('Not implemented … slangpy.h:267 reduce_type')` because `GridArgMarshall` doesn't override `reduce_type`. Adding `reduce_type` breaks the invariant: index with `N` or assert `D == N`. Ad-hoc probes of the in-tree build: `PYTHONPATH=. .venv/bin/python /tmp/x.py` from `/workspace/agent/slangpy` [GridArg D == N](../learnings/1793369152075-slangpy-gridarg-explicit-map-is-rejected-and-d-n-a.md).

## Direct-bound struct arguments skip their fields' `gen_calldata` (slangpy#1263)

A struct or dict argument is direct-bound when it has call dimensionality 0, read access, and every child is direct-bound (`StructMarshall.can_direct_bind`, `slangpy/builtin/struct.py`); a tensor child is direct-bound when its target is an explicit `ITensorType`, such as a `DiffTensor<half,1> t;` field. For such a binding, `slangpy/core/generator.py` (`_emit_call_data_code`, via `_emit_type_and_struct`) emits only `binding.vector_type.full_name` without recursing, so the children's `gen_calldata` never runs (the vectorized struct path does run it), and any validation in a leaf marshall's `gen_calldata` is bypassed for tensors inside parameter structs. On PR #1263 the fp16-atomic guard (see [[wiki/concepts/slang-rhi-backend-runtime.md]]) caught top-level and vectorized-struct half DiffTensors, but `struct S { DiffTensor<half,1> t; float scale; }` passed as `{"t": tensor, "scale": 3.0}` slipped through and Vulkan `bwds` failed with `RuntimeError: basic_string::_M_construct null not valid`. The fix walks `binding.children` in the `direct_bind` branch and checks `ITensorType` leaves, with a local import because `tensorcommon` → `slangpy.bindings` → `boundvariable` → `core.generator` would cycle. When testing a new per-argument check, probe one struct whose other fields are scalars (direct-bound) and one with a vectorized field [direct-bound skip](../learnings/1793852099467-slangpy-direct-bound-struct-args-skip-the-leaf-mar.md), [walk binding.children](../learnings/1793854474612-slangpy-direct-bound-structs-skip-their-fields-mar.md).
