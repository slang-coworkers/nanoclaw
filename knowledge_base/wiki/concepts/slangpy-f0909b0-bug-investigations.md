## TL;DR

Root-cause investigations that repeatedly cross the slangpy → slang-rhi → slang boundary. Recurring findings:

- **#222 (AMD-Windows autodiff grads wrong)** is a slang-rhi bug, not Slang-core or an AMD driver bug: slang-rhi advertises float-atomic-ADD off the BASE atomics device bit, so on RDNA2 iGPUs Slang legally emits `OpAtomicFAddEXT` and the driver mis-executes. `[72,0,0,0]` = all gradients computed then atomic-added into element 0 (a scatter-address bug), NOT zero gradients; the "always 0" title matched only D3D12.
- **#665 ("Failed to get binding data")** is upstream slang-rhi, D3D12-only, and silently swallowed (bare `return;` skips the dispatch → wrong results, no throw): fixed-pool exhaustion under slangpy's zero-backpressure per-dispatch submit, NOT a leak. Static triage got the mechanism shape right but the resource wrong: the maintainer's A/B pinned the per-command-buffer 4 MiB constant-buffer pool (slang-rhi#844), not the descriptor heap.
- **CPU-backend dispatch regression (#1136/#1137)**: the slang-rhi CPU device alone never populates `DeviceLimits::maxComputeDispatchThreadGroups` (`{0,0,0}`), so PR #995's clamp computes `min(0, ceiling)=0` → throw. Durable fix: Metal's `0xFFFFFFFF` sentinel in slang-rhi; a slangpy fallback must cover X, Y and the generator. Crossing a physical Y row on CPU (~67M threads) costs ~3–5 s/case, so parametrize large-dispatch tests on cpu.
- **Current-device stack (slang#13558)**: `Device::publish()` pushes every device but `shutdown()` pops only the top, so closing the older of two live devices first leaves a dangling `Device*` that nanobind dereferences (UBSan invalid vptr / segfault). Serial pytest only (nightly sanitizers), not xdist CI; read that job's log first.
- **`ComputeKernel.dispatch(**kwargs)` and cursor dict writes ignore non-field keys (slangpy#1231)**: a global passed outside `vars=` or a misspelled key stays unbound (CPU segfaults, CUDA fails at the next readback, Vulkan does nothing). Fix it in the dispatch lambda; other callers rely on the permissive shared writer.
- **SHADER_PATH**: since #1183 (superseding #1182/#1178 for #886/#1177) the binding lambdas prepend `slangpy.SHADER_PATH` unconditionally, never C++ core; module-level `spy.create_slang_session()` and a no-device `spy.App()` bypass it (slangpy#1238).
- **Triage discipline for cross-repo meta-issues**: a vendored dep in `external/` is not proof it is integrated (verify call sites); a stale architecture-refactor issue is a prime silently-fixed orphan (verify closing PRs + the cross-reference timeline); DeepWiki confidently gets "does X inherit/propagate Y" wrong — verify against source.
- **Static struct members (slangpy#126)** are absent from `Type.fields`, and an `InstanceList` silently drops them; detect them through `DeclReflection`.
- **`GridArg.__slangpy_load<D>` indexes `int[N]` with `D`; safe only because explicit `.map()` on a grid is rejected** (no `reduce_type` override). Adding `reduce_type` to `GridArgMarshall` must come with indexing by `N` or an assert `D == N`.
- **A direct-bound struct/dict argument never runs its fields' marshall `gen_calldata`**, so a per-argument check placed in a leaf marshall (e.g. `tensorcommon.gen_calldata`) silently misses tensors inside parameter structs. Run it over `binding.children` in the `direct_bind` branch, and test every new marshall-level check with a direct-bound struct.

## #222 — AMD-Windows autodiff gradients: a scatter-address bug, root-caused to slang-rhi

slangpy#222 "AD doesn't work, gradients are always 0" (AMD RX 6600 / Win11) framed the bug as zero gradients, but the numbers say otherwise. On the docs `polynomial` example the correct grad is `[12,16,20,24]` (sum 72); Shannon's AMD iGPU produced **Vulkan `[72,0,0,0]`** and **D3D12 `[0,0,0,0]`**. `[72,0,0,0]` means every gradient was computed and then atomic-added into element 0, a scatter *address* bug (`12+16+20+24==72`). "Always 0" matched only D3D12 (the real diagnosis sat in an unlinked Discord thread). A discrete AMD 9070 XT on Linux was correct: the scope is the AMD-Windows driver, not all AMD. A title or label is a claim to verify: compute what a nearby defect would produce and check the actual numbers [#222 title is wrong](../learnings/1786461616442-slangpy-222-title-is-wrong-amd-windows-grads-colla.md).

The Vulkan arm is a **slang-rhi** bug. In `src/vulkan/vk-device.cpp:822-830` the `SIMPLE_EXTENSION_FEATURE` macro (body gated on the `s.m` device-feature bit) is instantiated with `m = shaderBufferFloat32Atomics` (BASE float atomics: load/store/exchange) but pushes `Capability::SPV_EXT_shader_atomic_float_add`; the specific `shaderBufferFloat32AtomicAdd` bit is never read. On a device with base atomics but no AtomicAdd (RDNA2 iGPU), Slang is told atomic-add is supported, legally emits `OpAtomicFAddEXT` (no runtime check or fallback once the profile carries the atom), and the driver silently mis-executes. **Coarse-feature trap:** `Feature::AtomicFloat` is one bit set off the base atomics bit, so a SlangPy `hasFeature(Feature::AtomicFloat)` guard would still pass on an add-less device; the fix needs finer granularity in slang-rhi. A capability atom in a SPIR-V profile is not evidence the device supports the op (vulkaninfo beats inference-from-symptom), root-causing Vulkan doesn't root-cause the separate D3D12 arm, and the fix is cross-repo (upstream draft through the slang chain, back via a pin bump) [#222 root cause](../learnings/1786485429694-slangpy-222-root-cause-slang-rhi-advertises-float-.md).

## #665 "Failed to get binding data" — D3D12-only fixed-pool exhaustion, silently swallowed

`[ERROR] (rhi) layer: Failed to get binding data` (slangpy#665, D3D12 training loops) is upstream slang-rhi, not SlangPy or the compiler. `command-buffer.cpp` `writeComputeState`/`writeRenderState`/`writeRayTracingState` log it when `getBindingData()` fails, then bare `return;` without writing the pipeline command: the dispatch is skipped and execution continues, so results are silently wrong instead of an exception. SlangPy provides zero backpressure (`NativeCallData::exec` creates a fresh command encoder per dispatch and `submit_command_buffer` never waits), while arenas are reclaimed only when the tracking fence retires the submission, so a tight loop accumulates in-flight buffers faster than they retire. Workaround: `device.wait_for_idle()` (or periodic `wait_for_submit(id)`) in the loop. Not a leak (reclamation is fence-driven; CUDA/Vulkan analogues are high-water-mark): allocation outpaces fence-based reclamation on a FIXED D3D12 pool [#665 silently swallowed](../learnings/1787226423616-slangpy-665-failed-to-get-binding-data-descriptor-.md).

The error is **structurally D3D12-only**: the log line is in a backend-agnostic encoder path, but the failure reaching it (`getBindingData` → `BindingDataBuilder::bindAsRoot` returning SLANG_FAILED) comes only from D3D12's fixed shader-visible heaps: Vulkan's `DescriptorSetAllocator` grows pools on demand, and CUDA has no shader-visible heap (a growable `ArenaAllocator`). Don't attempt a Linux/CUDA/Vulkan repro; use Windows/D3D12 (`step_05_latent_texture.py`) and log `device.report_heaps()` per iteration [#665 is structurally D3D12-only](../learnings/1787763717844-slangpy-665-failed-to-get-binding-data-is-structur.md).

How the exhausted resource was found is the lesson. The first hypothesis was the descriptor heaps: D3D12's CBV/SRV/UAV heap holds 1,000,000 but the **sampler heap 2,048**, so a Texture2D+Sampler-per-dispatch kernel would exhaust the sampler heap ~500× sooner [#665 sampler heap is the tight bottleneck](../learnings/1787226766619-slangpy-665-d3d12-sampler-heap-is-the-tight-bottle.md). The maintainer's runtime A/B (constant-buffer page size 4 MiB → 64 KiB let 10 frames complete; baseline failed at frame 2) instead pinned the **per-command-buffer 4 MiB constant-buffer pool** (slang-rhi#844). Static reading got the mechanism *shape* right but the *resource* wrong. So without a runtime repro, state the shape confidently and label the resource a hypothesis; an A/B page-size experiment discriminates between pools; and re-read the latest issue comments before posting, since a sibling `nv-slang-bot` session may have re-asserted the wrong hypothesis as the last bot word (shared-bot-identity hazard, confirmed live) [#665 shape right, resource wrong](../learnings/1788354683528-slangpy-665-static-triage-got-the-mechanism-shape-.md).

## CPU-backend dispatch regression (#1136/#1137/#1138)

In slangpy 0.43.0 every compute dispatch on `DeviceType.cpu` throws `RuntimeError: Device reports zero compute dispatch groups in X` at `slangpy.cpp:103` (0.42.0 was fine; GPU backends unaffected). The slang-rhi CPU device is the **only** backend that never populates `DeviceLimits::maxComputeDispatchThreadGroups`, and `DeviceLimits` has no default member initializers, so it stays `{0,0,0}`; PR #995's large-dispatch clamp computes `min(0, huge) == 0` and `SGL_CHECK(dispatch_groups_x > 0)` throws. The durable fix mirrors Metal's `{0xffffffff, 0xffffffff, 0xffffffff}` sentinel for a backend with no hardware grid bound. Relaxing only the slangpy `SGL_CHECK` is a trap: the throw moves to the sibling Y check (also 0), and `generator.py` emits `dispatch_group_x_stride = 0`, corrupting the group-id flatten. A slangpy fallback must cover X, Y and the generator; the RHI fix covers all three [#1136 CPU backend zero dispatch limit](../learnings/1788474155417-slangpy-cpu-backend-zero-device-dispatch-limit-bre.md).

Fix PR #1137 surfaced reusable pytest facts. `plugin.py`'s `pytest_runtest_setup` treats a test as a *device* test only if it has a `device_type` parameter; otherwise it is SKIPPED under any `--device-types` selection, so a CPU-specific test is `@pytest.mark.parametrize("device_type", [DeviceType.cpu])`. `DEFAULT_DEVICE_TYPES` never includes cpu, which is why the regression shipped. The slangpy fallback (0 = unbounded: X→ceiling, Y→UINT32_MAX) is a provable no-op once rhi reports a real limit. slang-rhi disables CPU only in its OWN Linux test harness ("Known issues with CPU backend on linux"), not as a slangpy runtime restriction. With the throw removed, `test_pass_float_array` SEGFAULTS in CPU array marshalling, a separate pre-existing defect [#1136/#1137 pytest classification](../learnings/1788480806317-slangpy-cpu-dispatch-zero-devicelimits-stale-local.md).

Review of #1137 asked for CPU coverage crossing a **second physical Y dispatch row** (~67.1M logical threads with the fallback: 2097151 groups × 32). That looked too slow, but the sentinel-marker tests in `test_large_dispatches.py` ran ~3–5 s per case on a CPU debug build, so the fix added `DeviceType.cpu` to their parametrization, computed the expected row stride with `resolve_max_dispatch_groups_x()`, and treated `limits.y == 0` as unbounded instead of skipping. A mutation check (restoring the zero-stride generator) failed the grid and `call_group` cases, so the tests pin the codegen wiring. PR-body delivery-gate limits (`gh pr edit --body-file` ≤1000 chars, ≤2 lines per `##`) are on [the delivery-gates page](agent-routing-f0909b2-critique-and-delivery-gates.md) [crossing the Y row is cheap](../learnings/1791353262348-cpu-large-dispatch-coverage-in-slangpy-crossing-th.md).

The unmasked segfault (slangpy#1138) is a layer-localization exercise: `float first(float x[3])` called with a Python list segfaults on `DeviceType.cpu` but works on every GPU backend. slangpy_ext marshalling is ruled out (reflection-driven and backend-agnostic; bounds guards *throw*), as is slang-rhi CPU binding (the uniform rides the generic ordinary-data memcpy). What remains CPU-unique is the compiler's host-callable compile and the layout it reports for a fixed-size `float[N]` uniform. The cheapest confirmation is a reflection probe printing `getElementCount()`/`getElementStride(UNIFORM)`/offset; zero or garbage confirms a CPU-target layout bug. "GPU works, CPU crashes" with an opaque-bytes RHI path and a backend-agnostic slangpy path ⇒ compiler CPU-target bug, fixed at the legalizer/consumer, not by rejecting the shape upstream [#1138 layer localization](../learnings/1788481634992-localizing-a-cpu-only-slangpy-segfault-to-a-layer-.md).

## Current-device stack: auto-push plus top-only pop leaves a dangling `Device*` (slang#13558)

SlangPy (main ce68ef8) keeps a thread-local `std::vector<Device*>` current-device stack: `Device::publish()` pushes *every* created device, but `Device::shutdown()` pops only when `back() == this`. Closing the OLDER of two live devices first, as `helpers.close_leaked_devices` does (it walks `get_created_devices()` in creation order), leaves its freed pointer in the stack. The next `spy.pop_current_device()` / `current_device()` hands it to nanobind, whose `typeid(*ptr)` in `type_caster_base<sgl::Device>::from_cpp` (`nb_cast.h:492`) yields a UBSan "invalid vptr", a segfault, or an `Object::set_self_py ... already present` abort. Trigger: `test_compiler_profiles.py::test_cuda_profile_cache` (two `with spy.Device()` in a loop), crashing later in `test_device_api.py`'s `empty_device_stack`. A first device also survives Python rebinding, since its default `SlangSession` holds a strong `ref<Device>` until `close()`. The crash appears only in **serial** pytest (the nightly `sanitizers.yml` job, or a local `pytest slangpy/tests`); GPU CI's xdist `--parallel` splits the two tests across processes. For a SlangPy crash that looks platform-specific, read the nightly serial asan-ubsan log first: it has a symbolized UBSan frame and the exact stop point ([dangling Device*](../learnings/1791595717857-slangpy-current-device-stack-auto-push-top-only-po.md)).

## `ComputeKernel.dispatch` and cursor dict writes silently drop unknown keys (slangpy#1231)

`kernel.dispatch(thread_count, buf=b)` for a global `buf` (which belongs in `vars=`) raises no error and leaves `buf` unbound; so does a misspelled `vars` key. The dict-to-struct write in `src/slangpy_ext/device/cursor_utils.h:798-810` (numpy twin at :553-565) loops over the struct's FIELDS and checks `dict.contains(name)`, so non-field keys are never visited. The effect depends on the backend (L40S/Linux, main b89a3827 and 0.43.1): CPU segfaults; CUDA's dispatch returns no error, then the next readback fails with `CUDA_ERROR_ILLEGAL_ADDRESS` and shutdown aborts with "Failed to reset slang-rhi task pool"; Vulkan is a silent no-op. No unbound-resource check exists in SGL, slangpy, or slang-rhi's CPU/CUDA/Vulkan backends (slang-rhi#901 adds one for WebGPU only). `kernel.reflection.find_field(n).is_valid()` is true only for globals and `kernel.reflection[<entry>].find_field(n).is_valid()` only for entry-point parameters; `slangpy/testing/helpers.py:413` already routes names this way. Fix it in the dispatch lambda, not the shared cursor writer: `Function.set()` uniforms, `dispatchdata.py` and marshalls like `builtin/tensor.py:169` (plain uniforms into a diff-tensor cursor) rely on the permissive loop [#1231 unknown keys dropped](../learnings/1792162048265-slangpy-computekernel-dispatch-shadercursor-dict-w.md).

## Triage discipline: silently-fixed orphans, unintegrated vendored deps, and DeepWiki

Verify against primary source before treating an issue as open work or trusting a confident claim.

**Check upstream first for `external/slang-rhi` meta-issues.** slangpy#805 ("apply allocator improvements across all slang-rhi backends") is largely solved upstream: D3D12MA is merged and wired, but VMA is vendored (`external/vma/`) yet NOT wired; the Vulkan backend still calls raw `vkAllocateMemory()`, with the heap wiring stuck in a stale OPEN PR. A vendored dependency is not proof of integration (grep the call sites, here `src/vulkan/` for `vmaCreate`/`VmaAllocator`). For a cross-repo meta-issue the triage output is "no SlangPy PR possible; escalate upstream coordination + priority", never a fixer patching `external/slang-rhi` from a SlangPy PR [#805 solved upstream](../learnings/1787226230030-allocator-meta-issue-slangpy-805-is-largely-alread.md).

**A stale architecture-refactor issue is a prime silently-fixed candidate.** slangpy#795 ("move tensor types from extension layer into core SGL") is a fixed-not-closed orphan: the nanobind-free `Tensor` + `TensorDesc` already exist on `main` (the doc comment "This class deliberately contains no language-binding dependency" is verbatim the issue's goal), landed by three PRs in the issue's milestone with 0 cross-references. DeepWiki and subagents said "already done" with the NEW names while the issue used OLD ones: that mismatch is the tell. Re-derive from primary source (0 old names in `src/`, `git log -S`, `gh api issues/<n>/timeline`) before publishing, and check checkout shallowness first so `git log -S` dating is reliable [#795 silently-fixed orphan](../learnings/1787226338570-slangpy-795-tensor-move-already-landed-silently-fi.md).

**DeepWiki gets "does X inherit/propagate Y" confidently wrong.** For slangpy#886 it claimed `device.create_slang_session()` "inherits the include paths from the Device's default SlangSession if add_default_include_paths is True". It did not: the binding called straight through with its own `SlangSessionDesc`, `add_default_include_paths` only adds `platform::runtime_directory()/"shaders"` (not the package dir), and only the Python `create_device` wrapper injected `SHADER_PATH`, seeding just the device's *default* session. The clean fix inherits `device.slang_session.desc.compiler_options.include_paths` [#886 DeepWiki wrong](../learnings/1787226621145-slangpy-create-slang-session-does-not-inherit-devi.md).

## SHADER_PATH default include paths (#886, #1177 → #1183; gaps in #1238)

**One injection point was the root cause.** #1177 is the raw-constructor twin of #886: `spy.Device()` (the native SGL class, `src/slangpy_ext/device/device.cpp:513-539`, defaulting to an empty `SlangCompilerOptions{}`) + `spy.Tensor.from_numpy(...)` failed with `SlangCompileError: cannot open file 'slangpy.slang'` via `Device::builtin_layout()` → `load_module("slangpy")` (`src/sgl/device/shader.cpp:1040`), while `spy.create_device()` worked because its Python wrapper (`slangpy/core/utils.py:41,52-58`) was the ONLY place prepending `SHADER_PATH` (the `slangpy/slang` dir); even `AGENTS.md`'s "Functional API" example used the failing `spy.Device()`. While #886's design was held, the plan was a narrow #1177 fix: an actionable error + docs, re-raised at `_get_lookup_module` (`slangpy/reflection/lookup.py:34-35`, the narrowest spot holding both device and `SHADER_PATH`) ([#1177/#886 share one root cause](../learnings/1790019427102-slangpy-spy-device-vs-create-device-shader-path-in.md)).

**The right layer is the nanobind binding lambda, not the C++ core.** PR #1182 merged `self->slang_session()->desc().compiler_options.include_paths` with the caller's paths in the binding lambda (`src/slangpy_ext/device/device.cpp` ~1072). Core `Device::create_slang_session` (`src/sgl/device/device.cpp:784`) is wrong: the default session bootstraps through it at `:428` while `m_slang_session` is still being assigned, so core inheritance would deref a null/half-set `slang_session()`. Inherited paths go first (the wrapper's `[pkg/slang] + user` order) so user paths don't shadow defaults on a filename collision; dedup is lexical `std::filesystem::path operator==` (canonicalizing touches the FS and changes symlink/relative semantics; duplicates are harmless). #1182 deliberately left the free function `spy.create_slang_session()` un-inherited (maintainer scope guard) ([#886 fix belongs in the binding lambda](../learnings/1790111150088-slangpy-create-slang-session-include-path-inherita.md)).

**Current truth: PR #1183 superseded #1182 and #1178 (both closed unmerged).** "Add slangpy shader path to devices and sessions by default" fixes #886 + #1177 with the broad default-on design @ccummingsNV / @kaizhangNV asked for (no opt-out kwarg), resolving #886's held `inherit_default_include_paths` question. A file-local `std::vector<std::filesystem::path> g_default_slang_include_paths` (anonymous namespace in `src/slangpy_ext/device/device.cpp`) is set once at import by the module-level binding `_set_default_slang_include_paths([SHADER_PATH])`, called from `slangpy/__init__.py`: SHADER_PATH is a Python-package path, so Python registers it and core SGL stays package-agnostic. `prepend_default_slang_include_paths()` (defaults-first, dedup via `std::find`) runs **unconditionally**, not gated on `add_default_include_paths`, at three binding sites: both `Device` ctor bindings (the `DeviceDesc` one takes the desc BY VALUE so a caller-owned desc isn't mutated) and `device.create_slang_session`. `create_device`'s manual prepend was removed (single source of truth); sessions get only the global default, not device-specific custom paths. **Pyright scope gotcha:** a bare `pyright slangpy/<file>.py` reports `reportUndefinedVariable` for runtime-injected native symbols (`_set_default_slang_include_paths`, `Device`), but CI ignores it because `pyproject.toml [tool.pyright] include = ["./src","./tools","./examples"]` excludes `slangpy/`; judge CI impact by the `include` roots ([#1183 unified mechanism; pyright scope](../learnings/1790185684802-slangpy-1183-unified-shader-path-default-include-p.md)).

**Paths that bypass #1183 (slangpy#1238).** The prepend helper (`device.cpp:279-302`) runs only inside binding lambdas: the `Device` ctor bindings (`:570`, `:631`) and `Device.create_slang_session` (`:1117`). Two public paths reach core SGL instead, get `include_paths == []`, and fail `import slangpy;` with E00001 `cannot open file 'slangpy.slang'` (main e7bb2242, Vulkan and CUDA on the L40S):
1. Module-level `spy.create_slang_session()` and `spy.create_slang_session(SlangSessionDesc)` (`:1767-1791`; a lambda and a direct `nb::overload_cast<SlangSessionDesc>`) go to SGL `create_slang_session` → `current_device()->create_slang_session()` (`src/sgl/device/device.cpp:1804-1806`). A `with device:` scope doesn't help; #1183's PR body calls this path out of scope. Fix: call the helper in the lambda, and replace the direct `overload_cast` with a by-value `SlangSessionDesc` wrapper lambda that prepends to `desc.compiler_options`.
2. `spy.App()`, `spy.App(spy.AppDesc())` and `spy.App({})` with no device: both overloads (`src/slangpy_ext/app/app.cpp:73` `nb::init<AppDesc>`, `:76-82` `device=None`) pass null, and `src/sgl/app/app.cpp:16` calls core `Device::create()` with a default `DeviceDesc`, so `app.device.load_module*` and `spy.Module.load_from_source(app.device, ...)` fail. `App` is headless (only `AppWindow::AppWindow`, `sgl/app/app.cpp:71`, opens a window), so it reproduces in a container. Fix: give the helper external linkage and a shared header, and build a prepended `DeviceDesc` in both overloads when no device is passed.

Working today: `device.create_slang_session()`, `app.device.create_slang_session()`, `App(device=spy.create_device(...))`, or `include_paths=[spy.SHADER_PATH]`. A regression test for the `App` path needs a `device_type` parameter or it is skipped under `--device-types` (see [SlangPy build/CI toolchain](slangpy-f0909b0-build-ci-toolchain.md)), and a fresh device per `App`, because `sgl::App::~App()` calls `m_device->close()` even on a caller-supplied device. DeepWiki (2026-10-20) still claims `create_device` prepends `SHADER_PATH` in Python, which #1183 removed ([module-level create_slang_session misses SHADER_PATH](../learnings/1792463190116-slangpy-module-level-spy-create-slang-session-stil.md), [App() default device misses SHADER_PATH](../learnings/1792463898060-slangpy-spy-app-default-device-misses-shader-path-.md), [#1183 prepend bypassed by both paths](../learnings/1792464645928-slangpy-1183-shader-path-prepend-is-bypassed-by-fr.md), [device_type tests; App() closes its device](../learnings/1792466654227-slangpy-tests-no-device-type-param-skipped-under-d.md)).

## Static struct members are invisible to `Type.fields` (slangpy#126)

SlangPy's `Struct.struct.fields` (native `StructType::build_fields`, `src/sgl/refl/type.cpp` ~671) comes from Slang's `TypeReflection::fields()`, which excludes static members, so `static const int b = 5;` is absent. A dict argument naming it fails clearly ("has no field 'b'", `boundvariable.py` ~316), but `InstanceList.__setattr__` (`instance.py` ~87-100) silently stores it as a Python attribute. To tell a static member from a typo, walk `device.load_module(path).module_decl.find_first_child_of_kind(DeclReflection.Kind.struct, "Test").children` and test `c.as_variable().has_modifier(ModifierID.static)`. `spy.Module(...).device_module.module_decl` raises "module_decl() is not supported for composed modules" (`shader.cpp` ~1204), so walk `device_module.source_modules` or add a native helper. Since Slang #7993 (2025-07-30) `static const T x;` with no initializer is load-time error E31225, so old repros fail at `Module.load_from_file` [static struct members](../learnings/1792065039736-slangpy-detecting-static-struct-members-type-field.md).

## `GridArg`: explicit `.map()` is rejected, so `D == N` always holds (slangpy#1254 review)

In `slangpy/slang/gridarg.slang`, `GridArg<let N>.__slangpy_load<let D>` indexes the struct-sized `int[N] offset/stride` with the method's `D`. That is safe today because no public path makes `D ≠ N`: `GridArgMarshall.resolve_dimensionality` returns `self.dims` (so the implicit `vector_mapping` has length `dims` and the kernel gets `ContextND<dims>`), `resolve_type` accepts only `VectorizeGridArgTo<..., dims>`, and an explicit `func.map((0,1,2))(grid(...))` fails with `ValueError: Explicit vectorization raised exception: RuntimeError('Not implemented … slangpy.h:267 reduce_type')` because `GridArgMarshall` doesn't override `reduce_type`. Adding `reduce_type` there breaks the invariant: index with `N` or assert `D == N`. To probe the in-tree build ad hoc, run `PYTHONPATH=. .venv/bin/python /tmp/x.py` from `/workspace/agent/slangpy` (without `PYTHONPATH`, `ModuleNotFoundError: slangpy`) [GridArg explicit .map() rejected; D == N in __slangpy_load](../learnings/1793369152075-slangpy-gridarg-explicit-map-is-rejected-and-d-n-a.md).

## Direct-bound struct arguments skip their fields' `gen_calldata` (slangpy#1263)

A struct or dict argument is direct-bound when it has call dimensionality 0, read access, and every child is direct-bound (`StructMarshall.can_direct_bind`, `slangpy/builtin/struct.py`); a tensor child is direct-bound when its target is an explicit `ITensorType`, such as a `DiffTensor<half,1> t;` field. For such a binding, `slangpy/core/generator.py` (`_emit_call_data_code` ~:303, via `_emit_type_and_struct`) emits only `binding.vector_type.full_name` and does not recurse into the children, so their marshalls' `gen_calldata` never runs, while the vectorized (non-direct) struct path does run it. Any validation placed in a leaf marshall's `gen_calldata` is therefore bypassed for tensors inside parameter structs. On PR #1263 the fp16-atomic guard (see [[wiki/concepts/slang-rhi-backend-runtime.md]]) raised `ValueError` for top-level and vectorized-struct half DiffTensors, but `struct S { DiffTensor<half,1> t; float scale; }` passed as `{"t": tensor, "scale": 3.0}` slipped through and Vulkan `bwds` failed with `RuntimeError: basic_string::_M_construct null not valid`. The fix walks `binding.children` in the `direct_bind` branch and runs the check on `ITensorType` leaves, with a local import because `tensorcommon` → `slangpy.bindings` → `boundvariable` → `core.generator` would cycle. The slangpy-reviewer found it; when testing or reviewing a new per-argument check, probe one struct whose other fields are scalars (direct-bound) and one with a vectorized field (non-direct) ([direct-bound struct args skip the leaf marshalls' gen_calldata](../learnings/1793852099467-slangpy-direct-bound-struct-args-skip-the-leaf-mar.md), [fix pattern: walk binding.children](../learnings/1793854474612-slangpy-direct-bound-structs-skip-their-fields-mar.md)).
