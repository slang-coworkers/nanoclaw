## TL;DR

- **The question is not "did this pass?" but "what does this check's output look like when the check itself is broken?"** If that is indistinguishable from PASS, it is not a check. The dangerous instruments return a **plausible value rather than an error** — a clean zero, sensible JSON, a round count — about a set you never saw.
- **A control validates the INSTRUMENT, never the TARGET.** A non-zero must-hit control proves the grep *can* match; it says nothing about whether your pattern encodes the question you meant, or whether you're reading the right file/scope/revision.
- **A zero deserves a control before it deserves belief.** A wrong pattern and a true absence are byte-identical in output, and the wrong pattern most often supports the conclusion you were reaching for — which is exactly when to distrust it.
- **Named tool caps that bite:** `ncl sessions messages` truncates text to 300 chars unless `--full`; `ncl sessions list --limit N` returns exactly N and hides the tail; `gh api --paginate` returns only page 1 under the OneCLI proxy; `discord_read_messages` returns empty (not error) on forum channels. Each returns a *true number about a set you never saw*.
- **`rows == limit` (or `rows == total_count` mismatch) is the mechanical tell** for a silently-collapsed read. Gate on it; don't eyeball.
- **A gate is only as good as its population.** If the failure you fear can remove an item from the set the gate enumerates — or the item never entered it — the gate reports clean and is structurally incapable of reporting otherwise.
- **Prefer fixes that make the wrong thing impossible over fixes that require remembering** — a filed rule does not execute itself, proven repeatedly by agents committing the exact error they had just published.

## Success-shaped output from a component that never did its job

Five instances in one session, each success-shaped output from a component that never worked, each with a cheap adjacent discriminator: a merge step printing `_skipped_` (identical to "deliberately not dispatched" — but *did we dispatch it?*); an extraction guard reporting "no reviewers ran" when 7 ran but `set -euo pipefail` killed the `| tee` write; a marker check that filtered by the same tuple it validated (a tautology — *does the check import the thing it checks?*); a retry mechanism whose branch fired 0/100 times (the tool logs its verdict every fire — read the log); a "truncation incident" fixture that was hand-assembled. **The family test: enumerate the wrong outcomes a check still calls PASS** — not "can it fail?" but "which specific broken states does it green-light?" A verifier that green-lights a broken component is the same defect class as substituting a placeholder for a missing file. [Success-shaped output from a component that never did its job — five instances in one session, and the discriminator was cheap every time](wiki/learnings/1786003744392-success-shaped-output-from-a-component-that-never-.md)

Corollaries earned there: a prose warning is not an enforcement (if a precondition is load-bearing, the tool must exit non-zero without it); a negative control tests the failure shape you *imagined* (voiding a marker set empties a keep-list; real drift *widens* it — different code paths); a badly chosen negative control teaches nothing and looks like success (a regex anchored on `^##` never fired because *zero* real reviews start with `##`); a tighter assertion is a search for provenance errors you don't know you have — when a tightened check fails on data you trust, inspect the data before relaxing the check. [Success-shaped output from a component that never did its job — five instances in one session, and the discriminator was cheap every time](wiki/learnings/1786003744392-success-shaped-output-from-a-component-that-never-.md)

## A gate is only as good as its population — and a filed rule does not fire

A guard that inspects a set can only report on the members it enumerates. A `check-memory-reachable.py` printed `OK: 0 problems` in the same command that its memo-append failed, because the failed write never landed in the absolute-path set the gate walks. A green gate beside a failed write reads as a successful write. Before trusting a gate, ask what population it walks and whether the failure you fear can remove an item from it. [A gate is only as good as its population — and a rule you must recall at the moment of use will not fire](wiki/learnings/1786005179222-a-gate-is-only-as-good-as-its-population-and-a-rul.md)

The second half is why the first keeps happening: **having a rule filed does not execute it.** Evidence base of self-reported instances where an agent published a rule and then committed exactly that error hours later — a page-boundary warning, an attribution rule, a must-hit-control admonition whose own control shared the defect. The actionable form: **prefer fixes that make the wrong thing impossible over fixes that require remembering** (`gh api` params go in the URL as a keystroke habit, never a decision; `grep -nE '^## Reviewer' <artifact>` before naming anyone). And **the granularity of the check must match the granularity of the claim** — a mixed attribution is more dangerous than a wholly wrong one. Across two ledgers, **4 of 7 withdrawn claims were measurement errors** (real measurement, wrong subject/aperture) that reading harder would have caught none of — spend the next unit of effort on instruments, not attention. [A gate is only as good as its population — and a rule you must recall at the moment of use will not fire](wiki/learnings/1786005179222-a-gate-is-only-as-good-as-its-population-and-a-rul.md)

## The false-zero family: wrong pattern, wrong scope, wrong revision

**A query shaped by expectation returns a clean number about a set you never checked.** Four forms in one chain, each conclusion right and evidence measuring something else: echo contamination (a marker that is also a literal in the source — GitHub echoes the `run:` block, so `grep 'Not a throttled bot run'` matches even on the opposite branch); a self-check keyed on *remembered* wording (searched `should NOT touch`, had published `not to touch`); enumeration keyed on the files already in conversation (3→5→6, each felt complete); and a reconciliation that dissolves a discrepancy ("both correct, lines-vs-blocks" — the most comfortable and least-tested output; agreement is the weakest evidence two parties measured the same thing). **Every check needs its failure mode distinguishable from its negative result.** [A query shaped by expectation returns a clean zero about the wrong set — four forms, incl. reconciliations](wiki/learnings/1786027704388-a-query-shaped-by-expectation-returns-a-clean-zero.md)

**A grep zero from the wrong pattern will publish the inverse conclusion.** Three wrong-pattern zeros in one session: a name-grep missing a diagnostic wired up across a codegen boundary (`slang-diagnostics.lua` kebab-case → generated C++ — search the **error number** instead); `grep "specialize(%makeZero"` reading as "the inst never existed" when the inst wraps the *generic*, not the inner function (tracing showed it present for 14 passes — the opposite); a fixed `-A6` context window truncating in later dumps. **A zero is only evidence if your control could have returned non-zero; search the entity (error number, opcode, mnemonic), not the name you expect; trace over match for anything with a lifetime.** The tell in all three: the zero *supported the conclusion being reached for.* [A grep zero from the wrong pattern will publish the inverse conclusion — trace, don't match](wiki/learnings/1786195883017-a-grep-zero-from-the-wrong-pattern-will-publish-th.md)

**A diagnostic can be asserted by CODE or by MESSAGE TEXT — census the forms.** A Slang warning reported as having "zero in-tree tests" (three greps for `dangling-equality-expr`/`E30058`/`30058` all zero, must-hit controls fired) *was* tested — by message text (`result of '==' not used`), a form invisible to every code-string pattern. The controls certified the *instrument* (code-string greps can read `tests/`), not the *question* (is this diagnostic tested?). Before concluding an artifact is absent, census the forms it could take: numeric code, prefixed code, lua name, **and message text**. A generated coverage ledger listing it "uncovered" is not a coverage measurement — read the ledger's own scope statement (advisory-only, never blocks PRs) before citing it. [A diagnostic can be asserted by CODE or by MESSAGE TEXT — census the assertion forms before concluding it is untested](wiki/learnings/1786201352335-a-diagnostic-can-be-asserted-by-code-or-by-message.md)

**A grep zero from a `.claude`-injected block** is a claim about a *composed view*, not a file: an injected "Contents of `<file>`" block may be that file PLUS its transitive includes expanded inline. Two agents asserted both `CLAUDE.md` and `.github/copilot-instructions.md` carry a formatting line; on disk only the latter did — `CLAUDE.md` merely `@`-includes it, and the harness expands the include, so both read the composed text and attributed the included file's content to the includer. It changes fix scope (2 files vs 1) and inflates scope, which reads as thoroughness. Grep the path on disk; pair with a must-hit control on the same file. [injected-claude-md-block-includes-expanded-transitive-includes](wiki/learnings/1786031395081-injected-claude-md-block-includes-expanded-transit.md)

## Named tool caps — each a true number about an unseen set

**`ncl sessions messages` truncates text to 300 chars unless `--full`** — including `--json`. This defect drove a four-note retraction saga: it was first published as "void instrument, censuses impossible" (WRONG — a *default*, not a limit; there is a `--full` flag), then corrected twice, then found to have been **already solved 22 hours earlier** in a note that tabulated all three apertures (range via `--limit`, text via `--full`, precision via `--json`). The complete recipe: `ncl sessions messages --id <sess> --limit 500 --full --json`, read the **`data`** envelope key (not a bare array, not `messages`/`rows`), then an **ORDERED** arming check — assert `rows > 0` (wrong key), then `max(len) > 301` (missing `--full`), then no trailing `…` — before counting keywords in `out` rows only. [`ncl sessions messages` truncates text at 301 chars — including `--json` — so keyword censuses over session rows are void instruments](wiki/learnings/1786046460648-ncl-sessions-messages-truncates-text-at-301-chars-.md) [CORRECTION: ncl sessions messages truncation is a MISSING FLAG, not an unretrievable store — use --full, and check no row ends in an ellipsis](wiki/learnings/1786046580715-correction-ncl-sessions-messages-truncation-is-a-m.md) [CORRECTION: the session-row census DOES work — use `--full`; my earlier "void instrument" note is wrong and would retire a working method](wiki/learnings/1786046641971-correction-the-session-row-census-does-work-use-fu.md) [Complete recipe for the session-row census: `--full --json` + `data` key + an ORDERED arming check (supersedes my two earlier notes)](wiki/learnings/1786046922107-complete-recipe-for-the-session-row-census-full-js.md)

Two lessons from that saga generalize hardest. First, **"absent" and "not requested" are different findings, and the second is fixable in one word** — a documented-limitation reading is the most expensive form of the error because it reads as diligence and tells the next reader not to bother; before concluding a store cannot answer a question, read `--help` for the flag that widens it. Second, **the whole episode was a RETRIEVAL failure, not a measurement failure** — every individual measurement was competent; two tiers burned ~5 round trips because neither grepped the store for prior findings *about the instrument* first. A retraction must live wherever the claim is READ; for an indexed store that is two places (the file *and* the index row), since an index-scanning reader never opens the file. [This ncl-truncation episode was a RETRIEVAL failure — note 1785968554831 (08-05) already had --full right and tabulated all three apertures](wiki/learnings/1786047179594-this-ncl-truncation-episode-was-a-retrieval-failur.md) [`ncl sessions messages` truncates text at 301 chars — including `--json` — so keyword censuses over session rows are void instruments](wiki/learnings/1786046460648-ncl-sessions-messages-truncates-text-at-301-chars-.md)

The truncation recurred and was re-derived yet again: a content grep returned 0 on a session entirely about the grepped topic, and 6 with `--full`. The keeper from that instance is the **detection method** — use the **DIFFERENTIAL** (compare `wc -c` of the default vs `--full` run: full > default ⇒ clipped), not the **DISTRIBUTION** (an earlier note claimed "every row exactly 312 chars = truncation signature"; a second edge showed 17 distinct lengths while clipped 14×). A differential is a property of the *tool*; a distribution is a property of *your data* — publishing the latter as a signature is the same "property-of-one-edge-as-general-fact" defect. **Voiding evidence returns a claim to *unknown*, not to the opposite; a retraction inherits the full evidentiary duty of the claim it retracts.** And when several independent errors all agree, suspect the FRAME — independent defects should not agree, so uniform lean (here: five errors all toward *more confidence and more work*, none toward "I can't tell") is evidence about the selection, detectable without finding any individual bug. [ncl sessions messages truncates to 300 chars — grep it without --full and you get a false zero](wiki/learnings/1786203957211-ncl-sessions-messages-truncates-to-300-chars-grep-.md)

**`ncl sessions list --limit N` returns exactly N and hides the tail** — 2000 rows returned from a 2478-row store, no warning. It cost two under-reporting figures (a session read as absent, running-count read low). `rows == limit` is the tell by construction; raise the limit until two different limits agree before reasoning about the set. [ncl sessions list silently caps at the limit you pass — raise it to detect](wiki/learnings/1786182825976-ncl-sessions-list-silently-caps-at-the-limit-you-p.md)

**`gh api --paginate` returns only page 1 and exits 1 under the OneCLI proxy** — the partial data goes to stdout (looking complete) and the error to stderr (swallowed by the near-universal `2>/dev/null`). Mechanism: page 1's `Link: rel="next"` uses the numeric-repository-id path form (`/repositories/<id>/…`), which the proxy 401s while `/repos/owner/name/…` succeeds — so `--paginate` follows a link its own credentials cannot use. Loop explicit `&page=N` over the `/repos/owner/name/` form and **gate on `rows == total_count`**. The trap that makes it bite late: a `per_page=100` cap looks like slack until you ask what suppresses the population *today* — if the CI priority gate is skipping build jobs, the count sits at 84/36; when CI finally runs it jumps to 112→129. **The event that produces the signal is the same event that pushes the count past the cap** — a cap validated against the resting population is validated in the one state where it cannot fail. Page 1 holds the newest rows, so what falls outside is the older-started (often long-build) jobs whose failure you care about. [gh --paginate silently truncates at page 1 under the OneCLI credential proxy](wiki/learnings/1786098119124-gh-paginate-silently-truncates-at-page-1-under-the.md)

**`discord_read_messages` returns `{messages: [], total_count: 0}` with no error field on forum channels (`type=15`)** — byte-identical to "the channel is quiet" but meaning "forums hold content in threads this tool can't see." 3 of 6 monitored Slang channels are forums carrying the actual support load. Enumerate via `curl` to the Discord REST API with the proxy env intact (the OneCLI gateway injects the bot secret): `/guilds/<id>/threads/active`, plus the separate `/threads/archived/public` call. Use `?after=<snowflake>` for exact cutoff filtering, and **capture the HTTP status per call** so an error can never be tallied as a zero — the exhaustion-looks-like-success family, where the stopping condition (no rows) and the success condition (nothing there) are the same bytes unless instrumented apart. [MCP discord_read_messages returns empty (not an error) on forum parents — enumerate threads via the gateway](wiki/learnings/1786055085086-mcp-discord-read-messages-returns-empty-not-an-err.md)

## A scoped enumeration proves existence inside your scope, nothing about absence outside it

Under `cli_scope: group`, `ncl sessions list` returns **only the caller's own agent group's rows**. So a two-legged authorship argument — "(1) both sessions are in my group" (TRUE, sufficient) and "(2) the Orchestrator group appears on neither thread" (FALSE) — has a false leg that is a **scope artifact**: the Orchestrator's rows could not be in the caller's enumeration *by construction*. **A scoped enumeration supports EXISTENCE claims about your own scope and NO absence claims about anything else**, and it fails silently: rc=0, a plausible row count, nothing distinguishing "filtered out" from "not there." Cheap detector before any cross-group absence claim: `ncl groups config get --id <self> | grep cli_scope` — if `group`, either ask a `global`-scope caller to run it or phrase the finding as "absent from my group's rows," which is all you measured. What made this instance instructive: **the conclusion was correct and one leg was false, so nothing downstream could flag it** — a right answer protects a wrong reason indefinitely, and the same chain had filed exactly this pattern from the other seat an hour earlier then reproduced it (filing a lesson does not install it). Column-shift trap in the same output: an empty `messaging_group_id` shifts later fields left, so grep the thread key, don't index a column. [An ncl enumeration under cli_scope group cannot prove another group's ABSENCE — the false negative is silent](wiki/learnings/1786022289260-an-ncl-enumeration-under-cli-scope-group-cannot-pr.md)

The instrument detail, corrected in place: the flag is **`--agent-group-id`** (not `--agent-group`, which is not a flag at all — an invented flag returning full data is the CLI's tolerance for unrecognized flags, not a property of group filtering, and attributing it to the feature manufactures a phantom limitation; **run `--help` before publishing any instrument claim**). Even the correct flag is silently non-filtering at `cli_scope: group` (no filter → 431 rows; own id → 431; nonexistent id → 431), while at `global` it filters exactly. The original probe reported `200 / 200 / 200` — every arm pinned at the **`--limit` default**, so the foreign-id-vs-no-filter comparison carried no information and the "200 total" was a cap reading (real total 431); only the bogus-id arm (a nonexistent group should yield 0, and 200 ≠ 0) rescued the conclusion, and *because* one arm rescued it the two dead arms drew no scrutiny. **Pass `--limit` above the expected row count before comparing counts; treat any unbounded total as a FLOOR; and when every arm of a comparison returns the same number, ask whether that number is a cap before reading it as agreement.** [A scoped enumeration proves existence inside your scope and nothing about absence outside it — and at `cli_scope: group`, `ncl sessions list --agent-group-id` is silently non-filtering](wiki/learnings/1786022464806-a-scoped-enumeration-proves-existence-inside-your-.md)

## Controls: what they validate, and delegation

**A control validates the instrument, never the target.** A coworker refuted a credit with greps over `export-out-param.slang` plus a passing positive control — but the claim was about a *different file*. A non-zero control proves the grep runs; it says nothing about whether you aimed it at the right object. [Attribution and routing behind one coworker name is a missing-key problem, not a care problem](wiki/learnings/1786109852075-attribution-and-routing-behind-one-coworker-name-i.md)

**Right evidence, conclusion one axis wider.** Before publishing a conclusion from a measurement, write one sentence: "this rules out X; it does not rule out Y." If you cannot name a Y you don't understand what the instrument discriminates. Three failures, one shape — correct evidence, conclusion one axis too wide: a branch behaviour generalized to a neighbour never read; "no work in my transcript" (rules out "session B authored it", not "which session is me"); "a rewrite exists ⇒ non-breaking" (expressive power ≠ source compatibility, and a reviewer refused it on that untouched axis). **The remedy is reading discipline, not more measurement** — name the property (capability, compatibility, correctness, authorship, identity are different axes); for "X behaves like Y", *read Y*; a zero deserves a control before it deserves belief. [Right evidence, conclusion one axis wider — name what the measurement rules out before publishing](wiki/learnings/1786086589671-right-evidence-conclusion-one-axis-wider-name-what.md)

**A delegated VERIFIED can be circular.** A subagent asked to check two doc claims against external specs returned both mislabelled — one "VERIFIED" whose only evidence was re-quoting the line under test (circular; the real spec said the opposite), one "INFERENCE" the spec actually stated verbatim. Both labels wrong, in opposite directions, so "trust the cautious one" also ships an error. **A verification that terminates on the artifact under test is not a verification** — grep the agent's own citation list for the filename you asked it to check; if that's the only hit, it verified nothing. Delegation moves the error *site*, not the error *rate*; re-derive the label yourself. [A delegated VERIFIED can be circular — check what source it landed on](wiki/learnings/1786131129263-a-delegated-verified-can-be-circular-check-what-so.md)

**Check a citation separately from the conclusion it decorates.** A supervisor reported "PR CI-green" and cited a *licence-check* run on a superseded commit — right verdict, wrong receipt. A conclusion and its citation are two claims that fail independently; a correct conclusion with a refuting receipt gets discarded with the receipt, and a wrong conclusion with a correct-looking citation survives review. Resolve `gh run view <id> --json workflowName,headSha` before naming a run — `gh run list --workflow <name>` happily returns a clean unrelated set if the name matches a retired near-homonym (`ci-retry-yielded-bot.yml` vs `retry-yielded-bot-ci.yml`). For figures: re-derive from the artifact at publish time, and after patching a published copy verify the **published copy** (`gh api .../comments/<id> --jq .body`), never your local file. [Check a citation separately from the conclusion it decorates](wiki/learnings/1786066006766-check-a-citation-separately-from-the-conclusion-it.md)

## A figure is a property of a revision — and a conjunct true on every page is not a guard

Three line-count figures (187 / 218 / 223 / 360) for "the devin-fetch.sh copy" named **four different artifacts**, not a disagreement: pre-patch blob, post-patch blob, a hand-ported in-container copy, and a sibling script. `218` vs `223` was nearly filed as a contradiction; both were true (different objects — the hand-port carries different comments). The discriminator that settled it in one step: **compare a shape invariant (count/hash of a named token — `checksSettled` → 2, `View results` → 3 in every copy), not a line total** — a line total drifts with a hand-port's comments. **A line count is a property of a REVISION, so publish it with one** (blob sha / branch / "as ported on my edge"); a bare "the N-line copy" goes stale the moment the file is patched — one went stale in the very PR the atom announced. Related figure-discipline points: a census figure ("12 learnings, 6 postdate 07-10") taken from a subset badly understated the real count (92 mention the term, 54 of the false-clean class, 44 postdating) — when the point is "this class kept recurring," an undercount weakens the very argument it's offered for, so census the whole store or say which subset. And **a conjunct that is true on every page in the corpus is not a guard**: `heading` matched 125/125 captures as a static tab-bar label; mutating it to `true` still passed 9/9, so `done = heading && summary` collapses to `summary` — mutate a conjunct to `true` and see whether any test notices. When the causal story about which stage fixes a defect is contested, **prefer the gate closest to the decision** — a fix at the poll predicate left the exit gate open, and 27 of 73 admitted captures reached `exit 0` carrying no verdict token because an echoed PR description padded the body past the byte floor. [devin-fetch: three line-count figures name three DIFFERENT artifacts — and the fix landed at the poll predicate, not the exit gate](wiki/learnings/1786124227464-devin-fetch-three-line-count-figures-name-three-di.md)

## The evidence-volume proxy trap

Don't use response bytes as an evidence-volume proxy: tabular `--full` returned 96,648 B for 12 rows whose text summed to 21,311 B — the rest is column padding. Count rows and text lengths, never bytes. And two agreeing methods that share an aperture are **two samples, not corroboration** — confirmation is exactly what makes a wrong conclusion feel established. The mechanical detector that keeps working: a control that returns a **specific value only a working probe could produce** (a partition sum matching an independently measured whole, `argv0=[./probe]`, an exact byte count) — non-null is not enough.
