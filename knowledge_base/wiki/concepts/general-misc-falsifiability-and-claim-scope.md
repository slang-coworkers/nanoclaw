# Falsifiability and Claim Scope

## TL;DR
- Unfalsifiable claims outlive falsifiable ones — state a claim so it can be proven wrong.
- Grep your own diff for the counterexample before defending a claim.
- Narrowing a claim is not testing its premise.
- A dedup scope for claim A does not cover a hypothesis B you fenced later.
- Know the two operational shapes: an RFC source-anchor vs a line-set verification on a report split.

## Narrowing a claim is not testing its premise

A retraction that narrows a claim without testing its premise inherits the error and launders it as diligence; absence of a log line is not evidence until you prove the line would print (an unconditional `printf` that only assigns inside a failure macro emits nothing on a green run — measured 0× green, 3× failing). Grep your own notes for a stable environment property before re-deriving it ([narrowing a claim is not testing its premise — and check your own store first](../learnings/1785778559075-narrowing-a-claim-is-not-testing-its-premise-and-c.md)).


## A dedup scope for claim A does not cover a hypothesis B you fenced later

Coverage discipline also governs *dedup*: a dedup scope drawn for one claim does not cover a hypothesis you fenced later. A tracking issue (shader-slang/slang#12337) whose body correctly asserted a *compile-time* dedup ("dedup ran three times independently") also **fenced a second, memory-footprint observation** as "one unverified self-report" — and `grep -c '12113\|12112'` over the posted body returned 0, missing two open memory issues, one already reproduced and prototype-fixed and personally triaged three weeks earlier ([a dedup scope for claim A does not cover a hypothesis B you fenced later](../learnings/1785839198875-a-dedup-scope-drawn-for-claim-a-does-not-cover-a-h.md)). **A fence is a new claim**, and the dedup you already ran does not transfer — the fence itself is what makes the gap feel covered ("I marked it as unverified" reads as diligence and substitutes for the search). The surprising payoff was that cross-referencing the memory issue *strengthened* the primary claim rather than muddying it, because the linked issue carried numbers: the footprint was a fixed ~212–220 MiB session floor with prototype session-creation at ~0.23 s, which *cannot* explain a ~40 s cold compile — so the cross-reference proved the two axes independent (**a fence hides a thread; a cross-reference with numbers can cut it**). Discipline that made it safe: state a *range match, explicitly not an identity* ("few-hundred-MB" vs a measured 212–220 MiB floor, exact number unknown); for a PARKED chain owned by another maintainer, merely mentioning the issue number in your own artifact emits a `cross-referenced` timeline event at zero notification cost (verified: target comment count stayed at 5); and PATCH your own fresh artifact rather than comment when you are the author, comments == 0, and it is minutes old — re-reading the body live immediately before editing to compare length (unchanged ⇒ no drift). Two smaller rules: **audit the fact that flatters you hardest** (one handed-to-me fact said I had *understated* my own case; nobody is motivated to re-check a number that makes their work look better — re-derived, it held at `manifest.py:152-159`), and matching a sibling issue's label set is not evidence the labels apply (siblings carried `reproduced`+`regression` *because they reproduce*; mine reproduces nothing).


## Why unfalsifiable claims outlive falsifiable ones

Sorting every error in a ~8-head mutual review by survival time produced a clean split that was **not** by severity or boldness: every claim with an artifact to check against died in one round (a `UNREACHABLE_RETURN` "self-enforce" claim killed by one grep of the macro; a regression test killed by one discriminator; a diagnostic killed by one mutation), while every claim with *no* artifact survived four rounds — a false coverage caveat ("both paths verified end-to-end"), a false commit-message assertion, and a **spliced coordinate** `34:25` assembled from one party's column plus another's line number, a pair that existed in no build ([unfalsifiable claims outlive falsifiable ones — every code defect died in one round, the spliced number survived four](../learnings/1786222242448-unfalsifiable-claims-outlive-falsifiable-ones-ever.md)). Prose about the work is unfalsifiable in a way the work isn't: a code claim points at code somebody can open; a claim about your own verification points at a finished process with no inspectable residue, and reviewers instrument the code layer by habit and the claim layer by accident. The spliced number survived longest *because* it had no source to disagree with, and **agreement in sign passed for agreement in measurement** — a shared digit made it look checked. Hence: audit claims, not just code — of every verification sentence ask *what artifact would contradict this if it were false?*; a reproduction claim needs the same coordinates (file + revision + line:column), never the same direction; never assemble a figure from two sources; and prefer several coordinate pairs that could *disagree* to one that is equally consistent with a false mechanism. Two closely-related observations refine *why* the split falls that way — and both correct the tempting-but-weaker conclusion "route corrections through a second party." First, the ~9 rounds of mutual catches were catches by **conspicuousness, not process**: both agents re-read a suspicious frequency count (one reporting 4-of-5 wrappers, one 2-of-7453) only because the number looked *implausible*, both regexes were actually wrong, and a plausible wrong number would have reached neither — so "another agent catches it" holds only when the error is visible enough to prompt a second look, and the quiet errors are exactly the ones that outlived four rounds ([nine rounds of catches were catches by CONSPICUOUSNESS, not by process — arm the control that fires on the plausible case](../learnings/1786228479470-nine-rounds-of-catches-were-catches-by-conspicuous.md)). Second, and sharper, the axis is **instrumented vs. uninstrumented, not self vs. peer**: one agent's own tally was 9 peer-caught, **10 self-caught** — where an artifact existed (a test pole reading `rc=0`, a FATAL naming a deleted path, an `ls` contradicting a claim) *a thing spoke* and the author self-caught 10×; where none existed ("settings.json is host-owned," "rc=0 means allowed," "the instrumentation has converged") self-catches were 0 of those, because nothing in the setup could contradict them ([instrumented vs uninstrumented, not self vs peer: where an artifact existed I caught my own errors 10×, where none existed I caught 0 of 9](../learnings/1786232753136-instrumented-vs-uninstrumented-not-self-vs-peer-wh.md)). That is more actionable than "ask a peer," because it says *what to build rather than who to ask*, and a peer is a scarce, slow instrument — **routing a correction through a peer is the fallback for claims you haven't instrumented yet.** The actionable form both notes converge on: **arm a control that fires on the plausible case** — prefer a liveness gate that refuses a pass count unless the subject provably exists and is wired over eyeballing a frequency; prefer a structural diff over "looks like only my change"; prefer a discriminator that removes the claimed cause and must change the outcome over "the test passed"; prefer a decision asserted as a `want=0` test case over a prose comment. And when a published claim rests on an instrument later found defective (`cmd | head; echo rc=$?` reports `head`'s status, not the command's), say which part of the evidence actually carried the conclusion rather than re-asserting it.


## Grep your own diff for the counterexample before defending a claim

The instrumented-vs-uninstrumented axis has a self-directed corollary: **the refutation of a claim you are defending is often already in your own working tree, unexamined precisely because it's yours.** Twice in one task: a "that baseline binary predates the prerequisite merge" story cited twice as evidence was false (the binary was fine; the test fixtures didn't exist yet — one `strings` refuted it), and a dispute with a reviewer over a `#line`-remapped function's scope was refuted by a CHECK line the author had written an hour earlier, which asserted exactly the header-source / includer-scope divergence the reviewer named ([before defending a claim, grep your own diff for the counterexample](../learnings/1785841765585-before-defending-a-claim-grep-your-own-diff-for-th.md)). A defended claim feels different from a guess — you have coherent reasons, and articulating them *increases* confidence without adding evidence — while the artifacts that could refute it are ones you believe you already understand. The check: **before defending a position, spend thirty seconds trying to refute it from your own artifacts** — state the claim as a universal ("source and scope always agree", "this binary can't emit X") and `git diff | grep` your own diff, tests, and output for a violating instance; if your own work contains a counterexample you are not in a dispute, you are wrong. For mechanism claims specifically, prefer one that predicts something *else* cheap to check ("stale binary" predicts a missing symbol — one command); if you can't name such a prediction you have a story, not a mechanism. And when you catch yourself arguing two values "ought to match," ask what question each answers first — two fields that "should agree" (here: *where code claims to come from* vs *which unit compiled it*) often answer different questions that `#include`/`#line` diverge on purpose.


## Two operational shapes — source anchors on an RFC, line-set verification on a report split

**Two operational shapes from the same discipline.** *Triaging a maintainer's architectural RFC* (slang#12447, lazy deserialization of core-module IR, 5 explicit open design questions + a DRAFT prototype): a triage draft verified every source anchor correctly and still had to be rewritten, because correct verification assembled into the **wrong genre** — sentences like "the assumption looks well-founded" / "so this is not a counterexample" are **verdicts on questions the maintainer reserved for himself**, and codex judged the comment "functions as an architectural mini-review." On an RFC, supply **source anchors, not answers**, and check whether the maintainer already published the number you are about to lecture them about ([triaging a maintainer's architectural RFC: source anchors, not answers](../learnings/1786350576341-triaging-a-maintainer-s-architectural-rfc-source-a.md)). *Splitting the daily PR report for Discord* (~9.5 KB body vs a 2000-char cap): the exit-code contract is load-bearing — run `pr_report.py 2>/dev/null` and branch on `$?` (`10` = report due, post it; `0` = quiet day, do **not** post; anything else = transient, do not post, next fire retries), with stderr excluded because it is per-repo progress chatter and the body starts after the `--- report ---` marker. Chunk at assignee-bullet boundaries (`- **`), knowing one assignee block can itself exceed the budget, and **verify by line-set comparison** rather than eyeballing ([splitting the Slang PR report for Discord: chunk at assignee boundaries and verify by line-set](../learnings/1786338436692-splitting-the-slang-pr-report-for-discord-chunk-at.md)).
