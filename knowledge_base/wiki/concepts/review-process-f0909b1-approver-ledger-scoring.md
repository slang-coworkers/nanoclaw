## TL;DR

Beyond deciding, the approver must record an auditable ledger row and survive two critique gates
(DECISION_REVIEW on the derivation, OUTPUT_REVIEW on the deliverable). This cluster covers the
mechanics that cost extra critique rounds, the commit-graph facts a decision must not misstate, and
how an abstain/approve is SCORED once the human outcome joins.

Mechanics that recur:

- **Finalize the PR-body disclaimer BEFORE OUTPUT_REVIEW.** The gate binds `approve` to a sha256 of
  the reviewed artifact and re-hashes at send time; appending the mandatory bot-transparency footer
  after approval invalidates the hash and blocks the next marker-bearing send.
- **The deliverable's tense is bound to its SEND moment.** "Decision recorded" written before
  `record_decision` runs is a past-tense claim about a future state ⇒ OUTPUT_REVIEW must-fix.
- **Keep the human verdict OUT of the review-doc**, and pass `record_decision` the full `clauses` +
  `challenger` objects (an absent reason_code is OMITTED/null, never prose).
- **The critique round only records from a fresh `mcp__codex__codex` call carrying the verbatim
  `/codex-critique` developer-instructions** (sentinel-checked); a hand-written block or a
  `codex-reply` does not count toward the gate.
- **"rebase vs merge" / "merge branch main" are commit-GRAPH claims** — verify with
  `commits/<sha>.parents`, not inferred from "head moved + PR files unchanged"; clauses use the
  base…head merge-base (three-dot) diff; on a master-merge, compare PR-owned blob SHAs.

Scoring rules:

- A **substantive-gap abstain (OPEN_GAP)** is falsified by "did a human approve with the gap intact /
  did it ship untouched?" A **review-state abstain** (deferring to a live un-dismissed human block) is
  NOT falsified by a same-head merge — the correct outcome IS the human lifting their own block. These
  are distinct; do not apply the falsifiable-reading rule to a formal-state deferral.
- A false abstain is the ACCEPTABLE failure mode of a shadow-mode approver; a predicted infra
  false-negative that joins APPROVED with zero code misses is the gate working, not a miss.

## Critique-gate and record_decision mechanics

The disclaimer-ordering trap (slang#12488 / PR #12576): the OUTPUT_REVIEW `### Attested` block binds
the approve to a sha256 of the reviewed PR-body file, and the delivery gate re-hashes at send time.
Running OUTPUT_REVIEW, getting `approve`, THEN appending the required `🤖 Generated by an automated
Slang coworker…` subscript invalidates the hash ⇒ "1 edit(s) recorded since the last critique round"
blocks the next `[Fix Report]`/`[Fix Review Request]` send. Finalize the PR body COMPLETELY —
disclaimer included — before OUTPUT_REVIEW. Same atom records the gate mechanics: only a fresh
`mcp__codex__codex` call with a literal `STAGE: <NAME>` line + the verbatim developer-instructions
block records a verdict; a `codex-reply` re-verify does not flip it; and `.slang`/`.meta.slang` files
are not processed by `extras/formatting.sh`
([append the mandatory bot-disclaimer to the PR body BEFORE running OUTPUT_REVIEW](../learnings/1786966778361-append-the-mandatory-bot-disclaimer-to-the-pr-body.md)).

The deliverable-tense trap (slang#12665): the `[Approval Decision]` deliverable is drafted for
OUTPUT_REVIEW BEFORE `record_decision` runs (the skill sequence is record → then send), so any
past-tense "Decision recorded / posted / done" is a claim about a future state — codex flags it as
unsupported by the artifacts. The Status bullet must describe the state at SEND time (record happens
immediately before delivery), or name the sequence explicitly. Grep the draft for past-tense verbs
about your own actions and confirm each names a state that exists when the reviewer reads it
([OUTPUT_REVIEW deliverable status must describe send-time state, not pre-assert the record](../learnings/1787257450968-approver-critique-mustfix-output-review-deliverabl.md)).

Three discipline slips worth a pre-critique checklist (slang#12670): (1) the human verdict leaked into
the review-doc's verdict rationale — the review doc must derive from harvested-bot/Devin evidence
ALONE, with human signal + CI under headings explicitly marked "calibration/join only"; (2)
`record_decision` omitted the mandatory `clauses` + `challenger` fields (and an absent reason_code must
be OMITTED/null, not "(none)"); (3) "human maintainer" over-claimed a role only established as
"non-bot repository reviewer." Plus the meta-slip: hand-written developer-instructions did NOT record
the round — invoke the critique via the `/codex-critique` skill's developer-instructions VERBATIM
([keep the human verdict OUT of the review-doc; record_decision needs clauses+challenger; don't inflate "non-bot reviewer" to "maintainer"](../learnings/1787348853728-approver-critique-mustfix-keep-the-human-verdict-o.md)).

A distinct gate hazard: DECISION_REVIEW comment-hygiene on the AUTHOR's source can force an
UNRESOLVABLE must-fix. On slang#12182 the on-merits call was WOULD_APPROVE but codex held a must-fix
across 3 rounds on comment hygiene in the author's PR source — nits that are not a 🔴 (no BLOCK) and not
an OPEN_GAP, which the approver CANNOT revise (it never edits PR source), so the only reachable state is
ABSTAIN_POLICY:CRITIQUE_MUSTFIX, a likely FALSE abstain. The DECISION_REVIEW input is meant to review
the DERIVATION, not re-review author code style; scope the prompt explicitly and do not override an
independent reviewer's persisted must-fix to force an approve — abstain and surface loudly, then join
against the human outcome
([DECISION_REVIEW comment-hygiene on the AUTHOR's source can force an unresolvable must-fix → ABSTAIN:CRITIQUE_MUSTFIX](../learnings/1787875976045-approver-critique-mustfix-decision-review-comment-.md)).
And when a critique's must-fix rests on procedure-literalism while lacking a fleet correction (the exit-21
case), rebut with evidence and escalate the procedure conflict rather than silently overriding — a
critique is a strong prior, not an authority on the fleet's corrected procedure.

## Commit-graph facts a decision must not misstate

"rebase" vs "merge" is a claim about the commit GRAPH, not something to infer from surface signals. On
slang#12347 all 13 PR blobs were byte-identical and a gap was correctly unaddressed, but the base-update
was labeled a "PURE REBASE" — DECISION_REVIEW showed the new head was a MERGE commit (two parents +
"Merge branch 'master'"). "Head moved but PR files unchanged" is consistent with BOTH a rebase and a
master-into-branch merge; the distinguishing evidence is `gh api repos/O/N/commits/<sha> --jq '.parents'`
(two parents ⇒ merge; one ⇒ rebase/ff) plus `compare/<old>...<new>`. Same atom's second lesson: review
non-determinism does not resolve an unchanged code property — a gap the review stops mentioning is not a
gap that went away; re-derive from the code, and a review's 🔴 label is a claim, not proof
([rebase vs merge is a commit-GRAPH claim — verify with commits/<sha>.parents](../learnings/1787169787544-approver-rebase-vs-merge-is-a-commit-graph-claim-v.md)).

Clauses evaluate on the merge-base, so a merge head does not poison them. On slangpy#1080 the head was a
"Merge branch 'main'" landed via `synchronize`; a raw last-reviewed…head compare pulls in ALL of main's
intervening changes (protected paths, over the size cap) — but `eval-clauses.py` computes changed paths
as `compare/{base_ref}...{sha}` (three-dot / merge-base), the PR's contribution relative to its fork
point, so a merge-from-main that only fast-forwards the base (`behind_by 0`) contributes zero net new
paths. Use `compare/{base}...{head}` or `gh pr diff`, never `{last-reviewed-sha}...{head}`, when
eyeballing a merge head — the trap is a human second-guessing a correct clause off the wrong compare
([a "Merge branch main" PR head does not poison path/size clauses — the clause uses base...head merge-base](../learnings/1787167542059-approver-clause-gap-a-merge-branch-main-pr-head-do.md)).

On a `synchronize` that is a master-merge, the reliable test for "did the PR's own code change" is
per-file blob SHA identity for the PR-owned paths (`gh api .../contents/<path>?ref=<OLD> --jq .sha` vs
`?ref=<NEW>`). If the blobs match, the reviewed code is byte-identical and the from-source analysis
transfers exactly — but still run the FULL procedure keyed to the new commit (one ledger row per revision
commit; prior turns are context, not evidence). Bonus: a master-merge often makes a previously-stale
production bot review head-current, upgrading a fallback decision to primary tier
([master-merge synchronize — check PR-owned blob SHAs, don't re-review unchanged code](../learnings/1787556599410-approver-confirmed-safe-master-merge-synchronize-c.md)).
The blob-diff cuts both ways as a challenger tool: on slang#12649 rev 3 the production review flipped its
verdict from "🟡 coverage gap" to "✅ Clean" on tests that were BYTE-IDENTICAL between rev 2 and rev 3 —
a softened STANCE about unchanged code, not new evidence. Diff the ARTIFACTS (test-file blob shas), not
the review prose; a verdict moving in your preferred direction on unchanged code is the most seductive
false signal
([a reviewer flipping a 🟡 gap to ✅ on byte-identical tests is a softened stance, not new evidence](../learnings/1787337456577-approver-challenger-miss-a-reviewer-flipping-a-gap.md)).
The same predicate discipline defeats a cosmetic "addresses review" revision: on slang#12679 R2 a
prettier comment and a greener bot verdict tempted a flip from a prior abstain, but the gap's PREDICATE
("was the documented remedy — regenerate-from-source — performed?") was still NO; cosmetic/observability
improvements do not satisfy a remedy requiring a structural change, and be maximally skeptical of a
rationale that conveniently reverses your own prior call
([a nicer-looking "addresses review" revision can improve cosmetics without performing the remedy](../learnings/1787310479768-approver-challenger-miss-a-nicer-looking-addresses.md)).

## Scoring the outcome: which abstains are falsified by a merge

The central scoring distinction (finalized across the #12631 corrections). A SUBSTANTIVE-GAP abstain
(OPEN_GAP: "this code has a gap") is falsified by "did a human approve with the gap intact / did the gap
ship untouched?" — a same-head merge with the gap present means the abstain leaned conservative. A
REVIEW-STATE abstain (deferring to a live, un-dismissed human CHANGES_REQUESTED) is a DIFFERENT kind: the
correct outcome IS the human lifting or maintaining their own block, so when they re-review→APPROVE and it
merges, the abstain is NOT falsified — deferring was the only safe move; it would only be wrong if the
block had not actually been standing (verify that — it stays disagreeable there). This is NOT the retracted
"a human looked = correct" frame, which is un-disagreeable
([#12631 scoring, final: a review-STATE abstain cleared by the maintainer's own re-review is NOT falsified by a same-head merge](../learnings/1787253706112-approver-human-disagreement-12631-scoring-final-a-.md)).
The paired correction fixed the CHALLENGER MISS underneath it: an auto-approver that reads review
states/bodies but never `issues/N/comments` is blind to author↔maintainer discussion — on #12631 the
maintainer's "why is this needed?" was answered in an issue comment ~20h before the R2 decision, so
"unaddressed in the diff" ≠ "unaddressed"
([CORRECTION to #12631: the necessity question WAS answered in an issue comment ~20h before the decision](../learnings/1787253506012-approver-challenger-miss-correction-to-12631-join-.md)).

The tier itself can move a persisting defect from BLOCK to ABSTAIN across revisions: on slang#12693 a
verified coverage regression persisted byte-identically at R2, yet R1 (fallback tier, Devin's 🔴 sole
signal ⇒ review doc carried a 🔴 ⇒ "any 🔴 ⇒ BLOCK") was correctly BLOCK and R2 (primary tier, production
review ✅ Clean + head-current Devin retracted its 🔴 ⇒ no 🔴 in the doc) was correctly ABSTAIN. BLOCK binds
to a 🔴 IN THE REVIEW DOC, not the approver's standalone source finding; re-run the FULL procedure per
revision and keep one ledger row per commit_sha
([the same persisting defect can move BLOCK→ABSTAIN across revisions when the review TIER changes](../learnings/1787607867164-approver-human-disagreement-the-same-persisting-de.md)).

A false abstain is the ACCEPTABLE failure mode. On slang#12548 R2 the approver ABSTAINED over a Devin
"Potential Bug" it had DISPROVEN (CUDA prelude is `#include`d not inlined; CI passed all three directives
on the exact head), and the human merged unchanged — scored a FALSE ABSTAIN, but the SAFE error: the
Step-3 guard (can't self-clear a 🔴) exists to stop rationalizing away REAL bugs and here fired on a
false-positive. The lesson is NOT "clear 🔴s more aggressively"; the transferable signals are that Devin's
false-positive rate on FileCheck/emit-shape reasoning drives over-conservative abstains, and the test's own
passing CI run on the exact head is the strongest disproof of a "test always fails" claim
([ABSTAIN over a DISPROVEN Devin bug — human merged unchanged (#12548 R2)](../learnings/1787667117958-approver-human-disagreement-abstain-over-a-disprov.md)).
And a correct abstain that later joins APPROVED is not a miss: slang#12666 confirmed via merge join that
three ABSTAINs (two NO_REVIEW_SIGNAL, one OPEN_GAP) had ZERO code misses — the R3 NO_REVIEW_SIGNAL was the
explicitly-predicted infra false-negative, validating that the infra-abstain taxonomy calibrates correctly
and that NOT rounding up kept the shadow-mode measurement honest
([CONFIRMED via merge join: #12666 NO_REVIEW_SIGNAL abstain → human APPROVED, 0 code misses across 3 abstains](../learnings/1787766330537-approver-infra-abstain-confirmed-via-merge-join-12.md)).

Finally, an authority-ordering fact for the fixer/writer side of the loop: a maintainer's explicit,
repeated naming request overrides an automated reviewer's semantic objection (the maintainer owns naming) —
honor the name and neutralize the reviewer's substantive point in the comment instead; and each GitHub
comment POST re-arms the critique-on-deliver gate, so batch thread replies into one call and use
`codex-reply` with a sha256 re-confirmation between batches
([maintainer naming request overrides automated-reviewer semantic objection](../learnings/1787619515509-maintainer-naming-request-overrides-automated-revi.md)).
