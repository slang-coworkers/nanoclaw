# PR-Approver: Devin Artifact Races, Bounded Retry, ABSTAIN-Token Gate & Adequacy-as-Step-3

This page covers the operational mechanics of running Devin in the approver's Step-1b review-signal harvest — why the Devin subagent's returned text is never a completion signal, how to bound and retry a transient agent-browser hang, when a late primary review makes a fallback row stale — plus the critique-gate delivery traps (the bare-token exclusion, the required PLAN_REVIEW stage, the re-arming OUTPUT gate), the footprint discipline that separates real PR footprint from merge/CI noise, and the boundary rule that adequacy judgments are Step-3 challenger probes, never Step-1 clauses — with the durability lesson that the writable `SKILL.md` is not the durable home for the fix.

Sibling page: [class-override & calibration](review-approver-class-override-calibration.md) — repo-class predicate overrides co-occurring INFRA symptoms, Devin-timeout-on-bot-PRs = NO_REVIEW_SIGNAL, and the #12322 / #12246 calibration cluster.

## TL;DR

- The Devin subagent's returned text is NOT a completion signal. `devin-fetch.sh` (agent-browser + Chromium) is long-running, silent, and writes its result only at the very end; the process survives the subagent's exit under the parent session. After the subagent "completes," check the artifact (`ls review/devin-flags.md`) and process liveness (`pgrep -af devin-fetch.sh`) — if alive, wait on the artifact, not the subagent. Drive it with a `Monitor`/background `until` loop that watches for the artifact OR the script exit (covering success and no-artifact failure).
- The `devin-flags.md` artifact is unreliable in three distinct ways: it can be absent for 15-25+ min while the script runs; it can exit 0 with a flag COUNT but empty per-flag DETAIL (the done-detector races the "Loading diffs…" hydrate); and its `## Flags` section can be empty while Devin found flags (the bulk being the PR-description render). Cross-check `## Flags` against the AI-analysis rollup, and read `devin-page.txt` — never trust `devin-flags.md` alone.
- An agent-browser hang is a transient wedge, not a "Devin can't review" outcome. Wrap `devin-fetch.sh` in a hard shell `timeout` and do ONE bounded retry before recording `NO_REVIEW_SIGNAL`; on a bot-authored dep-bump re-sync, give Devin a FRESH attempt.
- A Devin-only fallback decision is PROVISIONAL against a late primary review on an unchanged head. On a nudge or later event, re-check live state and REFRESH the ledger row on the primary tier if `github-actions[bot]` has since posted at your decided commit — the fallback's "review never posted" blocker goes factually false.
- Never put the bare uppercase tokens `WOULD_APPROVE` or `BLOCK` anywhere in an ABSTAIN `[Approval Decision]` message — even negated, even in a `**Blocker:**` prose bullet. The critique-gate fast-path exclusion is a whole-word, case-sensitive ERE over the ENTIRE body; a match forces the full gate and can consume denial-cap strikes. Reword to "a hard-fail verdict" / "round up to approve" and scan the whole message before sending.
- `PLAN_REVIEW` is a REQUIRED critique-gate stage — `gh pr create` is DENIED until a `STAGE: PLAN_REVIEW` codex round is recorded. Run all three (PLAN_REVIEW → CODE_REVIEW → OUTPUT_REVIEW) as fresh `mcp__codex__codex` calls carrying the canonical developer-instructions verbatim; a `codex-reply` is not counted unless its instructions match.
- ANY edit after an OUTPUT_REVIEW approve re-arms the gate — including edits to non-deliverable files (a local `memory/fix-<n>.md` write re-armed it with byte-identical PR/code/test). Do all side-artifact writes BEFORE the final OUTPUT_REVIEW; send the deliverable immediately after the approve with no intervening edits.
- Decide from the NET footprint, not the raw commit-to-commit diff. A `synchronize` fires on any head move including a `git merge main`; a byte-identical net diff (`gh pr diff` = merge-base…head) means the push is a no-op merge and challenger findings transfer — but every open gap must still be re-verified against LIVE source at the new head. A `ci_failed` on an already-decided head is a flake unless the failing test file is in `gh pr diff --name-only` (merge-base aware, not `gh api compare base...head`).
- Adequacy is judgment, so it is Step-3, never Step-1. No deterministic clause covers (or can cover) test-plan adequacy; encoded as a clause it lands `unevaluable` ⇒ a spurious `ABSTAIN_INFRA` on every PR. Route "the reviewer should ask X" to the Step-3 challenger regardless of upstream framing.
- The dead-flag Step-3 probe is a BOTH-DIRECTIONS control scoped to NEW flag + NEW gate; exempt widening-only changes (false→true broadening is monotone). A missing trigger-present control is `ABSTAIN_POLICY:OPEN_GAP`, not a nit. Treat inbound findings as hypotheses — a correct prospective hazard is routinely mis-stated as a shipped defect.
- The writable skill file is not the durable one. Grep `.external-skills.json` before editing under `/home/node/.claude/skills/`; if listed it is re-synced away silently. The durable home is the group overlay `.instructions.md`; confirm by grepping the recomposed `CLAUDE.md` after a restart — writability is not durability.

## Devin Subagent Returns Before the Artifact — Watch the Artifact, Not the Subagent

In `/slangpy-pr-approve` (and slang) Step 1b, driving Devin via a background `Agent` subagent, the subagent repeatedly reports completion while `devin-fetch.sh` is still running: its final message gets clobbered by its own polling ("I'll wait for the notification…"), and `review/devin-flags.md` is absent on disk for 15-25+ min because the script (agent-browser + Chromium) is long-running, silent, and writes its result ONLY at the very end. The `devin-fetch` process SURVIVES the subagent's exit and keeps running under the parent session, so the artifact does eventually land — but the subagent's returned text is not a completion signal. How to catch it: after the subagent "completes," check the actual artifact (`ls review/devin-flags.md`) and process liveness (`pgrep -af devin-fetch.sh`); if the process is alive, wait on the artifact, not the subagent. Fix: drive Devin with a `Monitor` (or background Bash `until` loop) watching for the artifact to appear OR the script to exit (covering both success and no-artifact failure), instruct the subagent to run in the FOREGROUND and report once with an explicit ~15-min self-timeout returning `DEVIN_TIMEOUT`. If Devin never produces a head-current signal AND the harvested bot review is stale/absent, that is `ABSTAIN_INFRA:NO_REVIEW_SIGNAL` — do NOT substitute your own code read for the missing review doc. Gotcha: `pkill -f chromium` from a Bash tool can take down the calling shell (exit 144) — kill in a throwaway shell or SIGTERM the top `devin-fetch.sh` pid only ([Devin subagent returns before devin-fetch.sh completes; artifact writes at end](../learnings/1784560636178-approver-infra-abstain-devin-subagent-returns-befo.md)).

The artifact is unreliable in two further ways even when `devin-fetch.sh` exits cleanly, so a single read of `devin-flags.md` is never enough:

- **The done-detector races the "Loading diffs…" hydrate.** On slangpy#1084 rev-3 the artifact exited 0 with a populated rollup carrying "0 Bugs, 3 Flags" but the per-flag DETAIL lines (title/severity/file:line) were **absent** — the done-detector fired while the diff pane still read "Loading diffs…", because the right-rail flag COUNT settles before the center pane hydrates the detail. After the subagent returns, cross-check the `## Flags` section against the AI-analysis rollup: an empty/"(none captured)" Flags list while the rollup says "N Flags" (N>0) means the detail was lost to the race — do NOT report "no flags". When the decision does not short-circuit at a Step-1 clause, re-run/re-scrape before deciding; when it does (e.g. all files under `.github/**`) record the decision but set a `devin_flag_detail_captured: false` marker rather than present the incomplete list as exhaustive (still `reviewers_complete=true` — a capture-completeness gap, not a NO_REVIEW_SIGNAL) ([Devin done-detector also races the "Loading diffs…" state — flag COUNT renders but per-flag DETAIL lines stay empty](../learnings/1785517182047-approver-infra-abstain-devin-done-detector-also-ra.md)).
- **The `## Flags` section can be empty while Devin found flags.** On #12246 `devin-fetch.sh` exited **0** and wrote `review/devin-flags.md` (5,065 bytes) whose `## Flags` section was **completely empty** while Devin had in fact reported findings — the file's bulk was Devin's rendering of the PR *description*, not findings. **Read `devin-page.txt` (the page dump from the same fetch), never trust `devin-flags.md` alone**; the flag detail is in the page dump even when the flags file is empty ([devin-fetch.sh Flags section can be EMPTY while Devin found flags — read devin-page.txt](../learnings/1785837002567-approver-infra-abstain-devin-fetch-sh-flags-sectio.md)).

## Bounded Devin Retry, Fresh-Attempt-on-Resync, and Late-Primary Refresh

To keep `ABSTAIN_INFRA` near zero, treat an agent-browser hang as a transient wedge, not a real "Devin can't review" outcome: wrap `devin-fetch.sh` in a hard shell `timeout` and do ONE bounded retry before recording `NO_REVIEW_SIGNAL` ([Devin agent-browser hang recovered by bounded-timeout retry — avoid false ABSTAIN_INFRA](../learnings/1784735780656-approver-infra-abstain-devin-agent-browser-hang-re.md)). The same "a prior timeout is transient" logic applies at re-sync time: on a bot-authored dependency bump that re-syncs, give Devin a FRESH attempt rather than inheriting the earlier timeout ([re-sync on a bot-authored dep bump: give Devin a FRESH attempt](../learnings/1784323039030-approver-challenger-re-sync-on-a-bot-authored-dep-.md)) — a call vindicated when the fresh-Devin-on-resync WOULD_APPROVE was upheld by the human merge on PR 11892 R2 ([fresh-Devin-on-resync WOULD_APPROVE vindicated by human merge](../learnings/1784332096924-approver-human-agreement-fresh-devin-on-resync-wou.md)).

A Devin-only fallback decision is **provisional** against a late primary review on an unchanged head. When a supervisor nudge or a later event lands, re-check live state and REFRESH the ledger row on the primary tier if `github-actions[bot]` has since posted at your decided commit — the fallback row's "review never posted" blocker becomes factually false minutes later, so the row must be updated rather than left standing on a now-false premise ([a primary review that posts after you decide (unchanged head) → refresh the row on the primary tier](../learnings/1784723964060-approver-infra-abstain-a-primary-review-that-posts.md)).

## The ABSTAIN-Token Gate Trap and Critique-Gate Mechanics

The critique-gate ABSTAIN fast-path allows the delivered message only if it matches `ABSTAIN_*` AND does NOT match `WOULD_APPROVE|BLOCK` as bare words — so writing "→ OPEN_GAP, not WOULD_APPROVE" in an abstain rationale trips the exclusion and forces the full (skippable) gate; keep those enum tokens out of the delivered `[Approval Decision]` text entirely ([ABSTAIN [Approval Decision] message must not contain the literal tokens WOULD_APPROVE/BLOCK](../learnings/1784769386692-approver-critique-mustfix-abstain-approval-decisio.md)). The exclusion grep is a plain whole-word, case-sensitive ERE over the ENTIRE message body — it does not care whether `BLOCK`/`WOULD_APPROVE` is the decision state or just prose, so an innocuous `**Blocker:**` bullet that explains *why* you held a 🔴 "rather than a BLOCK verdict" defeats the fast-path and gets the abstain treated as a gated decision (observed on slangpy#1075 @4415159, where it consumed denial-cap strikes and escalated to a human admin before it was noticed) — reword to "a hard-fail verdict" / "round up to approve", and scan the whole message for the bare uppercase tokens before sending ([Critique-gate abstain fast-path breaks if the message text contains the tokens BLOCK or WOULD_APPROVE](../learnings/1785450575710-approver-infra-abstain-critique-gate-abstain-fast-.md)).

Two more critique-gate mechanics that cost round-trips under the `critique-gate` overlay (observed on slang#12220): **PLAN_REVIEW is a REQUIRED stage, not optional** — even a well-scoped triage-handed fix has `gh pr create` DENIED until a `STAGE: PLAN_REVIEW` codex round is recorded, so run all three (PLAN_REVIEW → CODE_REVIEW → OUTPUT_REVIEW) as fresh `mcp__codex__codex` calls carrying the canonical developer-instructions verbatim (a `codex-reply` is NOT counted unless its instructions match). And **any edit after an OUTPUT_REVIEW approve re-arms the gate — including edits to non-deliverable files** (writing a local `memory/fix-<n>.md` re-armed it even though the PR body/code/test were byte-identical), so do all side-artifact writes BEFORE the final OUTPUT_REVIEW and send the deliverable immediately after the approve with no intervening edits ([critique-gate: PLAN_REVIEW is required + any side-artifact edit re-arms the OUTPUT gate](../learnings/1785191965028-critique-gate-plan-review-is-required-any-side-art.md)).

## Footprint, Not Raw Diff — No-Op Merges and CI-Red on a Decided Head

A `synchronize` webhook does not always mean new work to re-decide: GitHub fires it on **any** head move, including a `git merge main` that pulls base content into the branch, so the raw commit-to-commit diff shows base churn (e.g. an unrelated test file) that a naive read mistakes for new PR footprint. Decide from the **net footprint** (`gh pr diff` = merge-base…head): if it is byte-identical to the prior revision the push is a no-op merge and the challenger findings transfer — but every open gap must still be **re-verified against LIVE source at the new head** (contents API `?ref=<head>`), because byte-identical net diff proves the *change* is unchanged, not that a maintainer didn't separately edit the flagged lines; a stale-by-commit-id harvest (CodeRabbit exit 10) is not the same as an obsolete finding ([a no-op merge synchronize leaves footprint byte-identical — decide from net diff, re-verify gaps against live source](../learnings/1785319523865-approver-clause-gap-a-synchronize-on-a-no-op-merge.md)).

The same footprint discipline governs a `github.ci_failed` event on an already-decided head — it is not automatically a new revision or a stronger verdict. Because `ci_green_on_sha` is non-gating under `v0-shadow-relaxed` (`require_ci_green:false`), CI state never mechanically gates the decision — the only substantive question is whether a red is a real PR-caused regression (strengthens the verdict) or an unrelated flake. A slangpy signature to recognize: exactly ONE matrix cell red (`build (linux, x86_64, gcc, Release, 3.10)`) while the same platform's Debug and the clang legs pass on identical source, with the failing case being `frame statistics align repeated and intermittent zones` in `tests/sgl/device/test_profiler.cpp` — a profiler timing/statistics test asserting exact per-call CPU-time and call counts, inherently nondeterministic under CI scheduling. The decisive check is footprint: `gh pr diff <pr> --name-only` (merge-base aware, NOT `gh api compare base...head` which includes files pulled in by merge commits) — if the failing test file isn't in the PR diff, the failure is not PR-driven, does not strengthen a standing `ABSTAIN:OPEN_GAP`, and (same head) mints no new ledger row ([slangpy CI-red signature: test_profiler.cpp timing test flakes on one matrix cell — not PR-driven](../learnings/1785486738534-approver-infra-abstain-slangpy-ci-red-signature-te.md)).

## Adequacy Judgments Are Step-3, Never Step-1 — And the Writable Skill File Is Not the Durable One

**No deterministic clause covers test-plan adequacy and none *can*; route any "the reviewer should ask X" request to Step 3 regardless of how it was framed upstream.** `eval-clauses.py` is data-only by construction (`eval-clauses.py:5-6`: it never judges the code and never reasons) — each of its six clauses (`author_trust`, `head_provenance`, `commit_match`, `ci_green_on_sha`, `no_protected_paths`, `tier_eligible`, plus size caps) is a mechanical predicate over PR metadata and changed paths at the pinned commit. "Does this PR's test plan contain a trigger-present control?" needs a diff read to find each new flag and locate its setter — judgment over code. Encoded as a clause it lands `unevaluable` ⇒ a spurious **ABSTAIN_INFRA on every PR**, corrupting the infra-abstain rate that is a quality gate driven to ~0; the advice would have degraded every decision, not merely missed its target. The Step-1/Step-3 boundary is **data vs judgment**, and an inbound framing ("file this against whatever clause covers adequacy") does not move it.

The second half of the same correction is about *where the fix lives*: **the writable skill file is the obvious target and the wrong one.** `/home/node/.claude/skills/{slang,slangpy}-pr-approver/SKILL.md` is writable, but `.external-skills.json` lists both (and 17 siblings) as synced from `shader-slang/slang-skills@main`, so local edits are re-synced away silently, with no error — the same cost recorded when a `supervise-issues` `scan.py` fix had to be re-derived by hand across six ticks because it reverted on every re-sync. The durable home is the group overlay **`/workspace/agent/.instructions.md`**, which composes verbatim into `CLAUDE.md`'s `## Additional Instructions` (headers demoted `##`→`####`); verified unchanged mtime across ~26 days of restarts, with the adopted probe block reappearing at `CLAUDE.md:559-579` after the restart that applied it. Guards: before editing anything under `/home/node/.claude/skills/`, grep `.external-skills.json` for that skill name — present ⇒ the edit is ephemeral; confirm durability the honest way by grepping the *recomposed* `CLAUDE.md` for your text after a restart, because **writability is not durability**; and anything that must reach *every* consumer of the skill is an upstream PR to `shader-slang/slang-skills`, not N drifting overlays ([adequacy has no deterministic clause — the both-directions control is a Step-3 probe, and its durable home is `.instructions.md`, not the synced `SKILL.md`](../learnings/1785828782431-approver-clause-gap-test-plan-adequacy-has-no-dete.md)).

**The probe that replaces the impossible clause is scoped to NEW flag + NEW gate, and must exempt widening-only changes or it becomes a false-abstain generator.** The defect shape: a flag declared and gated on but never set, so the guarded work never happens on any input while every artifact an approval pipeline consumes stays green — byte-identical output is green *by construction* (skipped work changes nothing), tests pass (none asserted the work happened), no reviewer objects (nobody looks for an unsatisfiable condition). `tests/hlsl/lower-lvalue-cast-skip.slang` (slang#12088) says it in its own comment: skip-vs-run "is a compile-time-only property that is not observable in emitted output," so the skip-direction test and the revert drill both stay green *more* easily when the flag is dead. The Step-3 form is a **both-directions control** — condition false → path skipped, *and* condition true → path taken and observably did its job — backed by four checks, cheapest first, per new flag: (1) **setter exists** — grep the whole tree for the identifier, not just the scan switch; a write anywhere refutes "dead"; (2) **order** — the scan must run before the gated work (in slang the flag struct is a plain aggregate of *uninitialized* bools, `slang-code-gen.h:52-88`, verified 34 bools with zero member initializers, reset only at `slang-emit.cpp:1047`, so a read before that is **indeterminate**, not false); (3) **jobs, not passes** — read the whole `processModule` (`lowerUntaggedUnionTypes::processModule`, `slang-ir-lower-dynamic-dispatch-insts.cpp:745-756`, carries a second unconditional job at `:755`, `replaceNoneTypeElementWithVoidType()`); (4) **a trigger-present control per job**, but check for a pre-existing one before calling it missing (`late-capability-requirement-{bad,missing,conditional,conditional-fail}.slang` are already the present-direction control for `lateRequireCapability`; #12088 added only the skip baseline). Missing ⇒ `ABSTAIN_POLICY:OPEN_GAP`, explicitly not a nit; diagnostic-bearing passes are the worst case, because the loss is a **missing error**, invisible to any codegen byte-comparison. The exemption: **widening-only changes** — no new flag, only new `case` labels broadening an existing flag false→true — are monotone, cannot create a dead flag and cannot skip a needed pass (precedent slang#12050 @`4c507cb94ca3`: WOULD_APPROVE, merged unchanged by a maintainer). Finally, treat inbound findings as hypotheses: verification at `0864e60e635ef39d4c25e5e57747d909f1c05edd` found all 34 flags had setters and no `assumeAddress`/`untaggedUnion` flag on any of 964 remote refs or in history, so the dispatch was a correct *prospective* hazard for a batch-2 PR that was never written, mis-stated as a shipped defect — one subagent changed the adopted wording from "a defect shipped" to "a hazard to gate on," which is what the probe actually keys off ([the dead-flag probe belongs in Step 3, not Step 1 — scope to NEW flag + NEW gate, exempt widening-only changes](../learnings/1785829409706-approver-clause-gap-a-gate-pr-probe-belongs-in-ste.md)).
