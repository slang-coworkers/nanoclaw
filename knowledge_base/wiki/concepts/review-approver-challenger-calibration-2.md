## False-positive refutations: a refuted 🔴 does not become WOULD_APPROVE

Devin (or any automated reviewer) can raise a plausible 🔴 that source inspection **narrows**. ⚠️ **The slang-rhi#800 example below is NOT a clean refutation — it is the page's cautionary case, corrected twice (2026-08-03) and rewritten in place here.** On slang-rhi#800 Devin flagged an indirect-dispatch residency crash "missing useResource". The Metal two-category taxonomy is correct and still the right first move — a resource passed *directly* to an encoder method (including `dispatchThreadgroups(indirectBuffer,...)`) is auto-resident, `useResource` is needed ONLY for GPU-addresses dereferenced inside argument buffers, and the codebase calls `addUsedResource` only in the arg-buffer-writing path — but the taxonomy was **not sufficient to clear the finding**, so "refuted" overstated it. Correct status of record: **NOT-BLOCK but NOT-CLEARED** ([[approver/challenger-miss-averted] Metal direct-encoder-operand — CORRECTED twice: not a clean refutation, and the residency polarity was inverted](wiki/learnings/1784338866210-approver-challenger-miss-averted-metal-direct-enco.md)). Crucially: a refuted 🔴 does NOT justify BLOCK, but shadow mode never rounds a doc's 🔴 up to WOULD_APPROVE either — so the decision is `ABSTAIN_POLICY:CHALLENGER_CONCERN`. Trace the exact residency/mechanism category before blocking on an automated reviewer's claim — and then check that the mechanism you traced bears on the *path the finding is about*.

> ⚠️ **WITHDRAWN COROLLARY (rewritten in place, 2026-08-03) — do not read a "the fallback merged unverified" claim anywhere on this page.** The earlier text here asserted that *the `!m_hasResidencySet` **fallback** was the unverified/uncovered path, and that only a run with `SLANG_RHI_METAL_NO_RESIDENCY_SET` would close it.* **Both halves are withdrawn.** `m_hasResidencySet = true` is set **only** inside `else if (supportsFamily(MTL::GPUFamilyApple6))` (`metal-device.cpp` L121, verified at merged `d8c609ef`); the hosted `Apple Paravirtual device` on `macos-26-arm64` is Apple Silicon but **does not expose Apple6**, and a sibling job on that image logs the terminal-`else` `GPUFamilyApple6 not supported; using per-encoder useResource fallback`. ⇒ **CI runs the FALLBACK by default**, so the fallback is the path that actually executed and is very likely covered by the passing `compute-indirect*.metal` cases; the **residency-SET path is the uncovered one** and needs Apple6 hardware CI does not have. ❌ Never cite `SLANG_RHI_METAL_NO_RESIDENCY_SET` as the missing artifact — CI is already on that path; the missing artifact is an **Apple6 run** ([[approver/calibration] a caveat can be wrong toward EXCESS caution — the "unverified config" CI runs by default, and the sibling-job trick that settles it](wiki/learnings/1785778241162-approver-calibration-a-caveat-can-be-wrong-in-the-.md), [[approver/challenger-miss] a diagnostic captured only on the FAILURE path cannot be read from a green log — CI runs the `!m_hasResidencySet` fallback](wiki/learnings/1785778085689-approver-challenger-miss-a-diagnostic-captured-onl.md)). Two supporting claims are withdrawn with it: *"every buffer is registered via `registerResource` regardless"* — `registerResource` (`metal-device.cpp:608`) does **all** its work inside `if (m_hasResidencySet)` (`:611`), so it covers only the residency-set path, i.e. the one never in question; and *"zero `[Info]` lines in either log"* — those messages are `DebugMessageType::Info` routed to doctest `INFO()`, flushed only on failure or `-v` (`tests/testing.cpp:209-219`), and `debugCallbackOutput` is assigned **only** inside `RETURN_NOT_AVAILABLE` (`:884`), so the silence was uninformative by construction. What survives from the original write-up: the five-step coverage-closing checklist (below) and the residency *taxonomy* as a first move. `unresolved` was accurate; **which** path was unresolved was inverted.
>
> **Two durable lessons from the withdrawal itself.** (1) **Narrowing a claim is not testing its premise** — "the fallback is unexercised" was retracted and rewritten as "unverified": weaker, same direction, same untested premise (*which path does CI take?*). A retraction that narrows without testing the premise inherits the error and launders it as diligence; legitimate retraction changes the **direction** or names the **artifact that would settle it** ([[approver/challenger-miss] narrowing a claim is not testing its premise — and the correct fact was already in my own store](wiki/learnings/1785778812255-approver-challenger-miss-narrowing-a-claim-is-not-.md)). (2) **A feature-tier name is not a capability check** — "Apple Silicon" is not "Apple6"; verify the predicate the code branches on, not the marketing tier it resembles ([[approver/calibration] closing a coverage gap can UNCOVER a new one — and clause (a) "the map is dead code on Apple-Silicon runners" is FALSE](wiki/learnings/1785776756858-approver-calibration-closing-a-coverage-gap-can-un.md)). One unauthenticated `curl` of a public job log would have settled it before either version was recorded.
>
> For the archetype of a genuinely refuted 🔴, use the slangpy#1082 or pinned-head-absence cases below, not this one. Retraction filed on the root atom (`learnings/1784338866210-…`); the parent calibration atom carries its own `RETRACTED IN PART` + `POLARITY CORRECTION` banners ([[approver/calibration] slang-rhi#800 — an execution-coverage OPEN_GAP is CLOSABLE (with the residency corollary retracted in place)](wiki/learnings/1785770830139-approver-calibration-slang-rhi-800-an-execution-co.md)).

The asymmetry is the whole point and the DECISION_REVIEW gate enforces it: on slangpy#1082 @3a266be (Devin the sole head-current signal) a Devin 🔴 at `torch_bridge_impl.cpp:126` was refuted as a clear false positive (native pre-check `required_size=64+ndim`; torch rank ≤64; both production callers pass a 128-byte buffer) and WOULD_APPROVE was drafted — the gate returned must-fix, because the challenger's refutation legitimately downgrades a would-be BLOCK to ABSTAIN but is NOT license to round UP. When the head-current review doc carries any 🔴 — especially when it is your ONLY head-current signal — the ceiling is ABSTAIN; approve requires a doc clean of 🔴 on its own terms, not a 🔴 you personally talked down. Two accuracy traps codex also caught here: "only N in-tree callers" is often wrong for an exposed ABI (a ctypes test called the exported fn-ptr with `required_size-1`), and a decision-moving external fact ("torch max rank = 64") pulled from a *prior session's* deepwiki check must be re-pinned or labeled not-independently-verified in the current session ([[approver/challenger-miss] A head-current 🔴 caps the decision at ABSTAIN even when you're sure it's a false positive — never round up to approve](wiki/learnings/1785495112092-approver-challenger-miss-a-head-current-caps-the-d.md)).


## The prior fixer learning can PREDICT the correct fix shape

When the fixer who triaged an issue left a durable learning about *what the principled fix should look like*, Step-0 recall surfaces it as the sharpest challenger prior. On slang#11665 (reject operator names on vars/params) the recall learning predicted the fix must reject at the single choke point (`UnwrapDeclarator`) gated by an opt-in, sparing legit operator functions — and the PR did exactly that, letting the challenger verify the diff *matches the predicted shape* rather than re-derive from scratch ([[approver/human-agreement] fixer-issue-learning-predicts-correct-fix-shape-clears-challenger](wiki/learnings/1784307794563-approver-human-agreement-fixer-issue-learning-pred.md)). Grep the learnings for the issue number FIRST on any fixer PR you (or a peer) previously triaged.


## A standing human CHANGES_REQUESTED caps at ABSTAIN — never round up

`eval-clauses.py` has NO clause for human-review-state, so a standing unresolved maintainer CHANGES_REQUESTED on the current head is invisible to Steps 1–2 — the challenger MUST run `gh pr view --json reviewDecision,reviews`. On slang#11136 the doc verdict was APPROVE with 0 bugs, Devin independently *confirmed* the fix, and the code was verified correct in source — yet the standing CHANGES_REQUESTED caps the decision at `ABSTAIN_POLICY:CHALLENGER_CONCERN` (only the requesting maintainer can clear their own request) ([[approver/challenger] standing human CHANGES_REQUESTED vetoes WOULD_APPROVE regardless of clean doc](wiki/learnings/1784326394685-approver-challenger-standing-human-changes-request.md)). Distinguish carefully: a **DISMISSED** review WITHDRAWS a (here non-blocking COMMENTED) review, leaving no active human review — it does NOT block WOULD_APPROVE, unlike a standing CHANGES_REQUESTED (slang#12133 R3) ([[approver/challenger] module-version-bump synchronize (k_maxSupportedModuleVersion): audit value/lockstep/additivity against the design docs; DISMISSED human review is not a CHANGES_REQUESTED veto — slang#12133 R3](wiki/learnings/1784343540068-approver-challenger-module-version-bump-synchroniz.md)). Beware framing drift — decide from harvested state, not the dispatch's "disputing vs complying" characterization.

**A same-head human APPROVAL is a JOIN signal, not a reason to flip your gap.** If you let a visible human approval upgrade your independent read you stop being an independent check and the agreement statistic becomes meaningless. On #12144 R2 a maintainer had APPROVED the exact head while the approver's independent read was ABSTAIN(OPEN_GAP): the calibrated outcome is `ABSTAIN_POLICY:OPEN_GAP` decision row AND a separately-recorded `human_verdict=APPROVED` = a healthy **withhold-on-SAFE agreement**, NOT a collapsed WOULD_APPROVE ([[approver/human-agreement] A same-head human APPROVAL is a JOIN signal, not a reason to flip your OPEN_GAP to WOULD_APPROVE](wiki/learnings/1784281316765-approver-human-agreement-a-same-head-human-approva.md)). Decide first with the human verdict walled off; record it only after, purely for calibration.


## Legitimate within-session flips and converging loops

Not every re-eval is a hold. A CI-proven BLOCK flips cleanly to WOULD_APPROVE when the fixer's next commit is a **test-only, CI-proven-green fix of your exact next-action**: on #11595 the BLOCK'd E41303 diagnostic broke `gh-9931.slang.1`; R5 fixed the test's false alignment promise with all 9 compiler files byte-identical R4→R5 (diagnostic still stands, not weakened) and the specific previously-red sub-test now `passed` — a VINDICATED BLOCK (SUPERSEDED_CHANGES_REQUESTED), and recording WOULD_APPROVE is the honest call, not "backing down" ([[approver/human-agreement] BLOCK→WOULD_APPROVE flips clean when the fixer's next commit is a test-only, CI-proven-green fix of your exact next-action](wiki/learnings/1784270379814-approver-human-agreement-block-would-approve-flips.md)). A **converging multi-synchronize loop** (each push adopts the reviewer's most recent concrete ask) reliably ends in a same-head APPROVE — #12034 ran 5 revisions and merged at the exact R5 head with the maintainer's approval ([[approver/human-agreement] confirmed: a multi-synchronize fixer↔maintainer review loop that converges (each rev adopts the reviewer's ask) reliably ends in a same-head APPROVE — WOULD_APPROVE on each settled rev is safe](wiki/learnings/1784308481321-approver-human-agreement-confirmed-a-multi-synchro.md)); `REVIEW_REQUIRED` from auto-dismiss-on-push is not a withhold reason, only a standing CHANGES_REQUESTED is. A **review-response cleanup revision** (comment trim + if-chain→switch) carries the prior revision's verified safety forward once you prove the emit body is byte-identical and the refactor is logically equivalent — but don't overclaim "N green / 0 red" while legs are still pending (codex DECISION_REVIEW catches this) ([[approver/challenger] synchronize cleanup-only revision: verify delta semantics-preserving (byte-diff emit body + refactor equivalence), carry prior safety forward, don't overclaim unsettled CI — slang#12133 R2](wiki/learnings/1784338540772-approver-challenger-synchronize-cleanup-only-revis.md)).


## Human-agreement vindications (the calibration record)

Merged-at-exact-head + independent (non-self) human approval = clean AGREEMENT, and several outcomes confirmed the conservative-lean bar:

- **#12140 `-Og`** MERGED at the exact decided head with the subtractive-guard + no-C++ future-proofing gaps *shipped unaddressed* — confirming they were reviewer notes, not blockers, and CLEAR was correct ([[approver/human-agreement] #12140 -Og debug-build MERGED at decided head — subtractive-guard + no-C++ future-proofing-gap clear VINDICATED](wiki/learnings/1784292544219-approver-human-agreement-12140-og-debug-build-merg.md)).
- **Downstream test-fix unblocks a shadow-BLOCK.** slang-rhi#799 (the `float4(float2,1.f,1.f)` fix for #12141's break) — verify the diff-line vs the break site named in the prior BLOCK, confirm semantic equivalence (splat vs tail-pad), and approve it STANDALONE (don't gate the downstream fix on the core PR — that inverts the dependency) ([[approver/human-agreement] downstream test-fix that unblocks a prior shadow-BLOCK — verify diff-line vs break site, then WOULD_APPROVE](wiki/learnings/1784282766770-approver-human-agreement-downstream-test-fix-that-.md)).
- **A confirmed human-DISAGREEMENT that vindicated the ABSTAIN.** slang#12031's ref-subscript-accessor autodiff silently returns a 0 gradient (the emitted `-target cpp` forward-derivative hardcodes `{ ..., 0.0f }`); the shadow ABSTAIN_INFRA/CHALLENGER_INCOMPLETE (runtime probe outran the merge) was correctly cautious — a WOULD_APPROVE would have been a false-safe on a real silent-wrong-gradient. "Unsupported" boundaries must ERROR, not silent-zero ([[approver/human-disagreement] confirmed: differentiating a read through a user-defined ref subscript accessor silently returns a 0 gradient (slang, experimental)](wiki/learnings/1784293272824-approver-human-disagreement-confirmed-differentiat.md)).
- **The #12141 full-arc (BLOCK→BLOCK→ABSTAIN→merge).** The vec4 3-elem-init deprecation ran R1 BLOCK (static_assert disable broke bundled slang-rhi shaders) → R2 BLOCK (success-path `forwardDiagnostics()` leaked E30081, broke `integer_pack.slang`) → R3 ABSTAIN_POLICY/OPEN_GAP (E30081 fixed via test casts but the raw `diagnoseRaw` re-emission still bypassed per-id `-Wno-*` suppression), then MERGED 5 commits PAST the R3 head (csyonghe APPROVED, a maintainer ≠ author) — the initial write-up framed this as end-to-end agreement with the author implementing the exact next-action, and the canonical takeaway is that the right fix layer for a "sub-sink captures then re-emits diagnostics" bug is the **sink construction** (does the child sink inherit the parent's severity-override map?), plus join-SHA-first (always diff decided-head → merged-head) [[approver/human-agreement] full-arc vindication: R3 ABSTAIN(OPEN_GAP) merged only AFTER the author implemented the exact next-action (copy sink severity-overrides + add -Wno test); BLOCK→BLOCK→ABSTAIN→merge](wiki/learnings/1784838040864-approver-human-agreement-full-arc-vindication-r3-a.md). **NOTE:** this account is corrected/partly-superseded — see Contradictions/supersessions below; the closure was PARTIAL and an ABSTAIN row is not "agreement" [[approver/human-agreement] CORRECTION to full-arc-vindication #12141: PARTIAL gap closure (suppression-bypass fixed, broad-forwarding retained), not "whole gap fixed" or "end-to-end agreement"](wiki/learnings/1784838665378-approver-human-agreement-correction-to-full-arc-vi.md).

## The slang-rhi over-conservative streak: five losses, the partition that resized the fix, and the win that broke it (2026-08-11 fold)

**The record, joined against human outcomes.** Across slang-rhi import/coverage PRs the abstain rate was **over-conservative at n=3 and then worse**: #813 @`abec21d2fdb4` ABSTAIN(OPEN_GAP) → APPROVED and merged unchanged; #814 @`7b4a6f2ecaac` ABSTAIN(CHALLENGER_CONCERN) → APPROVED, merged intact; #815 @`b50b53c4d1ac` ABSTAIN(OPEN_GAP) → APPROVED with byte-identical content. Same repo, same author (`fknfilewalker`), same code-owner approving two of three, **zero wins**. The join was airtight because the *files were hashed* rather than the SHA trusted — #815 synchronized between decision and approval, which normally reads as "he approved a fix", but per-file hashes showed the reviewed bytes were unchanged. At n=1 a loss is noise about one PR; **at n=3 consecutive with zero wins the finding is about the BAR**, and the honest move is to escalate the bar as a *policy question* rather than quietly loosen the derivation, because a self-loosened bar is invisible to the calibration record that detected the problem ([3-for-3 over-conservative — at n=3 the finding is about the BAR](wiki/learnings/1786342881662-approver-human-disagreement-3-for-3-over-conservat.md)).

**But the count that justified the proposed carve-out did not survive partitioning.** Six consecutive abstain rows were offered as evidence for one policy carve-out (author-declared WIP with clean artifacts). Partitioned by reason code: #813-R1 `OPEN_GAP` (untested validation branch), #814-R1 `ABSTAIN_INFRA` (harness gap), #814-R2 `CHALLENGER_CONCERN`, #815-R1 and #815-R2 `OPEN_GAP` (untested validation branch), #811-R1 `NO_REVIEW_SIGNAL` (harness gap), #811-R2 `CHALLENGER_CONCERN` (the WIP case). **The carve-out covers exactly one of six rows.** The real cluster is three untested-validation-branch calls — a different question entirely — plus two harness gaps that no bar change can touch. ⇒ **Partition a count by the mechanism the fix addresses before publishing it as evidence for that fix; if the partition is uneven, the count is not the evidence.** And n=1 cannot establish a rate, so the WIP change has to be argued on principle (author intent belongs in the report, not the verdict) rather than as a measured loss rate ([partition a count by the mechanism before using it as evidence](wiki/learnings/1786351744859-partition-a-count-by-the-mechanism-before-using-it.md)).

**The WIP case on its principle.** On slang-rhi#811 @`2a3524d8` every artifact said approve — 6/6 eligibility clauses, fully green CI with all four wrapper-bearing Debug legs executing the regression across 7 backends, CodeRabbit clean at the pinned head, zero 🔴, both nits cleared — and the abstain rested on one signal: the author had commented *"Removed review requests for now. Work in progress."* and dropped both human reviewers 45 s earlier. Five days later a maintainer approved and merged it independently (`mergedBy=skallweitNV`, `author=jvepsalainen-nv`, `reviewDecision=APPROVED`), with per-file `sha256` identical to the decided head. **"The author isn't ready for review" ≠ "the code isn't ready to merge":** a WIP declaration is evidence about *who wants to look*, not about *what they would find*. Author intent belongs in the report's next-action, never in the verdict ([an author's WIP declaration is evidence about who wants to look](wiki/learnings/1786346987860-approver-human-disagreement-an-author-s-wip-declar.md)).

**#817 is the sharpest case, and its first write-up over-claimed — read the surviving half.** Five consecutive `ABSTAIN_POLICY / OPEN_GAP` rows across five heads were joined when `skallweitNV` merged bytes **byte-identical** to what was abstained on (`vk-surface.cpp` `bcdcece338ed`, `vk-device.cpp` `73ef1ed20899` on `main` after merge). The initial reading — "false abstain, loss #7" — is **withdrawn**: the merge was an approval by someone who never saw the finding, and *an approval that never saw the finding is not a refutation of it*. What survives, and is the genuinely useful half: **the predicate was shown to ask the wrong question, never to produce a wrong answer on a real configuration** — the gap was real but was never established to FIRE; **an abstain must price severity, not just uncertainty** (reachability and silence were cited five times while severity stayed low and unmeasured); and **a verdict that totals only risks systematically under-approves**, because the fix's demonstrated benefit (a real SRGB bug) never went on the scale. The meta-error is instructive on its own: the finding was rounded **down** into a self-scored loss, so over-correction can masquerade as rigor in either direction ([RETRACTION of the #817 false-abstain claim — an approval that never saw the finding is not a refutation](wiki/learnings/1786348876090-approver-false-safe-retraction-of-my-own-817-false.md)).

**What broke the streak was replacing an unfalsifiable question with a falsifiable one.** slang-rhi#819 (native-handle invalid-input coverage, `skallweitNV`) had the classic abstain-bait shape — a bot finding saying a new test "doesn't actually prove the fix" — and was recorded `WOULD_APPROVE` @`4aaef9010fa6`, then merged unchanged at that exact head ⇒ **AGREEMENT**, and a guilty control that passed. The substitution:

> ❌ *"Could a human usefully look at this?"* — scores an abstain **correct** whatever the human decides, so it can never be wrong and never calibrates.
> ✅ *"What outcome would prove an ABSTAIN here WRONG?"* — names the observable (merged unchanged at my head) before the decision, so the row is falsifiable when the join lands.

Keep the falsifiable form as the standing pre-record question; it is what converted a 4-for-4 losing streak into a scored win ([slang-rhi#819 WOULD_APPROVE→MERGED unchanged: the guilty control that PASSED](wiki/learnings/1786347066549-approver-calibration-slang-rhi-819-would-approve-m.md)).

## The slang-rhi #817 Chain: Six Calibration Traps From One PR (2026-08-14 fold)

The #817 SRGB-fix chain (the byte-identical-merge case above) produced a dense run of calibration errors, most of them running toward *excess* caution. **A fix that closes YOUR OWN finding is the least-scrutinized diff you will read.** At R0 the approver abstained (`OPEN_GAP`) because two new `TextureUsage` bits weren't validated; the author's next push added exactly those two checks, and the approver read them, confirmed both existed, and proposed WOULD_APPROVE — but `DECISION_REVIEW` caught that the new `CopySource` check was itself **wrong**. Two failures in one paragraph: relief at seeing your gap addressed suppresses scrutiny of *how*, and **a per-item predicate needs a per-item check** — confirming N checks exist is not confirming each check is correct ([a fix that closes your own finding is the least-scrutinized diff; a per-item predicate needs a per-item check](wiki/learnings/1786273668817-approver-challenger-miss-a-fix-that-closes-your-ow.md)). **A disclosed evidence gap is not a closed one.** The approver wrote that green CI was "partially discriminating" for a `vk-surface.cpp` change (all three surface tests use `config={}`⇒default path, which the PR changed), while in the *same paragraph* disclosing "I did NOT read job logs for a per-test tally" — then argued from the green anyway. Disclosing a gap does not license reasoning past it; read the log or don't lean on it ([slang-rhi surface tests always skip in CI — a disclosed evidence gap is not a closed one](wiki/learnings/1786273693553-approver-calibration-slang-rhi-surface-tests-alway.md)).

**Consequence severity scales urgency, not epistemic class.** The approver found a provably-wrong predicate (a check testing a `FormatSupport` flag derived from `linearTilingFeatures` against an *optimal*-tiled swapchain image, silently stripping capability) and drafted **BLOCK / RED_BUG**; the critique reversed it to **ABSTAIN_POLICY / OPEN_GAP** and was right — the third leg (does any real device answer the two tiling fields differently for a selectable format?) was never measured. That a bug's *consequence* is severe (silent capability strip) raises how urgently you'd want it fixed, not the epistemic class of a claim resting on an unmeasured trigger; the refutation was written into the approver's own rationale ("does any real device…") and ignored ([consequence severity scales urgency, not epistemic class — I drafted BLOCK on an unmeasured trigger](wiki/learnings/1786279519823-approver-calibration-consequence-severity-scales-u.md)). **Unreproducible evidence raises confidence, never recorded class** — the same commit cycled BLOCK→ABSTAIN→BLOCK→ABSTAIN (final `ABSTAIN_POLICY/OPEN_GAP`) because two of three legs were source-verified but the third was a population question about real device behavior that stayed unreproduced; an abstain, not a block, is the honest class while a leg is unmeasurable from your seat ([unreproducible evidence raises confidence, never recorded class — BLOCK twice on one commit, reversed twice](wiki/learnings/1786283443026-approver-calibration-unreproducible-evidence-raise.md)).

**Retractions, hedges, and self-criticisms are the least-audited class of claim** — three errors in one PR all pointed toward *excess* caution and nearly survived because erring against your own interest reads as rigour. An unverified hedge ("these flags are also consulted for non-image paths") implied in-tree consumers the approver never checked; enumerated, the only consumer was the one file under discussion, so the fix was cleaner than the hedge implied. Audit a hedge/retraction as hard as a finding ([retractions, hedges and self-criticisms are the least-audited class of claim — over-caution WAS the error](wiki/learnings/1786285724438-approver-calibration-retractions-hedges-and-self-c.md)). **An undisclosed threshold makes a number uncheckable, and a successful retry never identifies the blocker.** A peer's population measurement to close an evidence gap had two claims wrong in ways only re-running caught: counts that didn't reconcile ("262 of 448 pairs" vs the approver's `264/24/160`), traced to an **undisclosed epsilon** (`if d > 0.05` noise-rejection filtered silently); and an access theory ("the data source 403s a plain fetch, UA block") that didn't reproduce — a bare `curl` with no UA returned 200. Publish the threshold with the number, and prove an access claim with the failing call, not a successful retry ([an undisclosed threshold makes a number uncheckable, and a successful retry never identifies the blocker](wiki/learnings/1786285523638-approver-clause-gap-an-undisclosed-threshold-makes.md)).
