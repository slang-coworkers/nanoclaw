# Slang Compiler Internals: Parser, IR, Types, and Language Semantics

This page covers internal compiler mechanics: parsing, IR builder source location stamping, type interning and dual-representation bugs, module import/re-export semantics, autodiff parameter conventions, platform macros, and runtime data structure gotchas.

⚠️ **This page is over the 40 KB page cap (~121 KB) and its tail may be truncated on read.** The TL;DR below carries the durable rules so they survive a bounded read; a subtopic split is pending.

## TL;DR

- **`SLANG_ASSERT` compiles to `SLANG_ASSUME` (a UB license) in release, not a runtime check** — never pair `SLANG_ASSERT(x)` with a runtime `if (x)` fallback on the same `x` (the optimizer may delete the guard); use `SLANG_RELEASE_ASSERT` to fail loudly, or keep only the `if`. And **`SLANG_ASSERT=release-assert-only` suppresses the very assertion you are retesting**, giving a false "fixed" verdict.
- **In `include/slang.h` endianness fails loudly (`#error`) but pointer size fails SILENTLY** — `SLANG_PTR_IS_32 = (SLANG_PTR_IS_64 ^ 1)`, so any non-whitelisted 64-bit arch (rv64, LoongArch64, s390x, MIPS64) silently gets a 32-bit `SlangInt` and corrupts the public ABI. Add the symmetric guard; don't delete the whitelist.
- **`ISession::loadModule`/`loadModuleFromSource`/`loadModuleFromBlob`/`getLoadedModule` return a BORROWED `IModule*` — never release it** (`asExternal` is a plain `static_cast`, no addRef; DeepWiki is wrong). `link()`, `getTargetCode()`, `getEntryPointCode()`, `createCompositeComponentType()`, `findEntryPointByName()` transfer ownership via `.detach()` and must be released once.
- **Appending fields to a versioned public struct via inheritance makes it non-standard-layout, so `offsetof` is only conditionally-supported** — `is_trivially_copyable` + `sizeof(D) > sizeof(B)` do NOT prove B is a byte-prefix of D.
- **Keep terminal `CountOf`/`Count`/`NUM_*` sentinels IMPLICIT and restore textual-order == value-order** — a `static_assert(CountOf == SomeOption + 1)` checks adjacency to one enumerator, **not uniqueness** (observed: `CompilerOptionName::CountOf == SPIRVUnifiedDescriptorHeapStride == 154`).
- **`kIROp_MakeVectorFromScalar`'s generated `getScalarValue()` reads `getOperand(2)` but every builder emits ONE operand** — read the scalar via `getOperand(0)`. Generally: **verify how the BUILDER emits an op before trusting a positional accessor**; schema and builder diverge.
- **`findAttrs<T>()` returns only the FIRST CONTIGUOUS RUN of `T` operands**, so a new `IRAttr` subtype emitted inside the per-kind size loop truncates `getSizeAttrs()` (→ `slotCount=0`, miscompiled existential binding) — emit new attr types in a separate pass after all size attrs.
- **Order `as<derived>` before `as<base>` in any AST classification cascade** — `VarExpr`/`MemberExpr`/`StaticMemberExpr` all derive from `DeclRefExpr`, so a leading `as<DeclRefExpr>` makes the MemberExpr branch dead code. **`DeclRef::as<U>()` does NOT validate the target type** (it rewraps the same `declRefBase` and returns non-null for the wrong decl) — use `as<U>(rawDecl)` or `declRef.is<U>()`.
- **Slang builds modifier lists in REVERSE declaration order, so `findModifier<T>()` returns the LAST-written attribute** — verify "which duplicate modifier wins" empirically, never from source order. `-dump-ast` is unmaintained.
- **`ASTBuilder::getOrCreate<T>` keys on syntax class AND operands**, so `getOrCreate<ThisType>(base)` and `getOrCreate<DeclRefType>(base)` are distinct `Type*` for one base — when a logical type interns differently by access path, **fix the representation canonicalization, not the divergence site** (a 2-file fix was superseded by a 44-file canonicalization).
- **Any pass gated on a TYPE opcode is fragile: const-folding can delete the type while leaving an op that still needs the pass** — a stranded `CastEnumToInt` reached emit as E99999 because `calcRequiredLoweringPassSet` flagged only `kIROp_EnumType`. Gate on the cast opcodes too.
- **The requested-capability array has five readers OUTSIDE `getTargetCaps()`**, so "the cooked set is identical ⇒ inert" is false — removing an entry can flip `descriptor_handle` auto-promotion on metal/cuda/wgpu/cpu. **Derive an A/B from what the mechanism actually mutates (accept/reject + diagnostics), not layout/size, or you get a false null.**
- **`-capability` affects only target-compatibility checking, never per-function self-consistency** — public functions must declare `[require(...)]`; a dropped `[require]` is a silent runtime divergence that bites only codegen-decision capabilities.
- **Confine the empty-struct fix to `IREmptyTypeLegalizationContext` / consumer-side `isSimpleType`** — a global `removeEmptyStructFields` pass is CI-rejected (it strips zero-size empties that `Conditional<T,false>`/`Optional` need), and producer-side `addPublicDecoration` removal is the wrong layer (plain `public` functions then emit `static`). **When a change deletes a decoration at its producer, inventory every consumer.**
- **Entry-point / varying-parameter / reflection layout fixes belong in the front-end AST before layout generation, not a back-end post-link rebuild** — and don't hand-roll recursion; the layout walk re-enters per-node resolution and `Val::resolve()` already recurses.
- **Escape VALIDATION must ride the decode layer, not the token scan pass** — `getFileNameTokenValue` deliberately never decodes escapes (`\` is a Windows separator), so scan-pass `\u`/`\U` validation broke `#include "dir\utility\f.slangh"`. Separately, `getStringLiteralTokenValue`'s inline hex decoder is **missing `+10` for a–f/A–F**; fix the too-narrow guard, not the already-correct utility.
- **Never conditionally skip `RECORD_OUTPUT` in `source/slang-record-replay/`** — the stream is fixed-schema at the call level, so one skipped output desynchronizes every subsequent call on playback. `ReplayContext` registries are raw/**non-owning** (DeepWiki says otherwise), so the replay path leaks by construction.
- **`canCoerce` viability probes call with `outExpr == nullptr`**, so a `return true` nested inside `if (outExpr)` yields false negatives (init-lists work in var-decls but fail as arguments).
- **Slang platform macros are value-style and always defined (0 on inactive platforms), so `#ifdef SLANG_OSX` is unconditionally true** — and a presence→value conversion silently narrows (iOS dropped since `SLANG_OSX==0` there); use `SLANG_APPLE_FAMILY`. **The default optimization level is `Default` (1), not `None`** — detect an explicit `-O` via `hasOption(CompilerOptionName::Optimization)`.
- **`CompilerOptionSet::buildHash`'s `Int` branch drops `v.intValue2`**, so `-fvk-bind-globals`, `VulkanBindShift(All)` and `-trace-coverage-binding` collide on the key feeding BOTH the shader cache and `.slang-module` freshness. The binary-module up-to-date check is **digest-based, not mtime-based**.
- **Flipping the default `-g` level silently changes TEXTUAL codegen, not just SPIR-V** — `IRDebugLine` has side effects so `shouldFoldInstIntoUseSites` refuses to fold across it; sweep non-SPIR-V goldens, and note **a `SLANG_UNIMPLEMENTED` default arm weaponizes any newly-surviving inst class into a hard crash**.
- **A missing statement terminator makes the compiler REJECT valid code too, not just over-accept** — `ParseThrowStatement` omits `ReadToken(Semicolon)`, so `if (c) throw 1; else return 2;` fails with E20001+E30015. **Always test the unbraced if/else shape, and prove a parse by reading EMITTED CODE, not error text.** Same class: `ParseDeferStatement` opens no scope, so `defer uint i = 1;` leaks `i` and IR relocation turns it into a segfault.
- **Layout POLICY is coded twice with ZERO shared code** — SPIR-V `Offset`/`MatrixStride`/`ArrayStride` use the IR path (`slang-ir-layout.cpp`), reflection uses `IRTypeLayout`, so **which path the consumer reads decides where the bug is fixed**. The IR path deliberately omits C tail padding (whitelist it in differential checks), and an `SV_Target<N>` VarLayout `index` must be patched in **two** places in `slang-parameter-binding.cpp`.
- **Module import semantics:** `using namespace N;` is lookup-local and never re-exported; the `parentDecl == moduleDecl` conjunct is load-bearing via plain transitive `import`; global `type_param` names are NOT merged across imports. **`#include`'d files get an `IRDebugSource` but NO `IRDebugCompilationUnit`** (only the preprocessor sets `setIncludedFile()`), which kills any `DebugSource → CU` map — **verify every X in scope actually HAS a Y before recommending an X→Y lookup**.
- **Reverse-mode autodiff shapes a differentiable `out T y` as a bare `in T.Differential` with no primal writeback** — forward mode's `out DifferentialPair<T>` intuition does not transfer. NRVO for by-value opaque returns must be scoped to genuinely-opaque handles, **not all `[__NonCopyableType]`** (that also covers bit-copyable tagged structs; aliasing them regresses `defer`, `x = f(x)`, and throwing partial writes).
- **`validateEntryPoint` validates each param in isolation with no cross-param aggregation** — a duplicate-SV check must fire for system values only and skip output-only-by-type params in the InOut branch or `inout TriangleStream<T>` self-collides. **E38052 "VS has no SV_Position" is an intentional heuristic false positive** (VS→GS is known-legit; escape hatch `-warnings-disable 38052`).
- **Reuse the canonical predicates instead of hand-rolling** — `isPointerToImmutableLocation` (excludes RW-alias and the OptiX-SBT case) and `isOpaqueType` (recursive/cycle-safe) predate the narrow hand-rolled switches that duplicate them.
- **`Slang::String` is copy-on-write with a shallow copy ctor** — to share across threads force a deep copy with `String(x.getUnownedSlice())` under the producer's lock. On macOS, **hidden visibility silently breaks catching `Slang::Exception` BY TYPE across dylibs** (libc++abi keys on RTTI identity).
- **A probe's scope, not your confidence, bounds the claim** — enumerate readers with a named runnable grep before declaring anything inert; spot-check load-bearing subagent claims (one reported "6 calls" where grep returns zero); **EMIT AND GREP before any cross-target codegen claim**; check whether an intervening rewrite deleted the cited lines (`git log -S`) before investigating a stale pointer; and prefer *"could not verify by method M"* over any capability-negative — `find`/`grep` enumerate a MOUNT, not a capability.
- **Test presence, not a proxy for presence** — an artifact checker keyed on PR-existence flagged 105 chains of which 93 were false (they had issue comments), and keying on *recency* instead re-breaks exactly the correctly-parked chains. Before re-reporting a chain as parked, search all-state PRs referencing the issue and re-verify at HEAD.

## Lexer: Hex-Digit Decoder Bug

`getStringLiteralTokenValue` in `slang-lexer.cpp` has an inline hex-digit decoder that is missing `+10` for letter hex digits (a–f, A–F), causing string literals with hex escape letters to silently produce wrong byte values. Char literals use a separate correct utility ([slang-lexer.cpp has a duplicate hex-digit decoder with an off-by-ten bug](../learnings/1779805764133-slang-lexer-cpp-has-a-duplicate-hex-digit-decoder-.md)).

## Parser: ParseDeclName Shared by Func and Var

`ParseDeclName` is shared between function and variable declarators, so `int operator+ = 10;` is silently accepted as a variable named `operator+`. Function-vs-variable disambiguation happens later at the commit point; the fix belongs at `CompleteVarDecl`, not the shared name reader ([slang ParseDeclName shared by func and var declarators accepts operator names](../learnings/1781823315708-slang-parsedeclname-shared-by-func-and-var-declara.md)).

The `parseTypeDef` function only handles the leading-array form, causing `typedef int arr[2];` (C/HLSL trailing-array form) to fail with an unexpected-integer-literal error. The principled fix is shared declarator machinery rather than patching the typedef-specific path ([Slang typedef trailing-array parse gap (parseTypeDef vs declarator machinery)](../learnings/1781218629168-slang-typedef-trailing-array-parse-gap-parsetypede.md)).

**A missing terminator in one statement parser also makes the compiler REJECT valid code.** Each statement parse fn owns its own terminator — the dispatch framework never consumes semicolons — and `ParseThrowStatement` (`slang-parser.cpp:7580-7587`, #12326 @`53b76e6d3`) returns straight after `ParseExpression()` with no `ReadToken(TokenType::Semicolon)`, unlike every sibling (`return` :7567, `break` :7547, `continue` :7556, `discard` :6949, expression stmt :7596; `defer` :7571 also omits it but *correctly*, since it parses a nested Stmt carrying its own terminator). The framing everyone reaches for is "the compiler accepts too much," and it is only half the story: `if (n < 0) throw 1; else return 2;` is **rejected** at HEAD (`E20001` + `E30015 undefined identifier 'else'`), because `parseIfStatement` (:7381-7386) gets the ThrowStmt back with the `;` unconsumed, so the following `LookAheadToken("else")` sees `;` and the else never attaches — the leftover `;` becomes a sibling EmptyStmt that orphans trailing clauses. So when triaging any missing-terminator issue, always test the unbraced `if/else` shape. Two claims must also stay separate: requiring the `;` does **not** tighten the expression bound — greedy `ParseExpression()` line absorption is generic to Slang's newline-insensitive grammar, and `return`, which already requires `;`, absorbs identically (`return x` ⏎ `- 5;` emits `x_0 - int(5)`); the `;` requirement converts a *silent* misparse into an honest diagnostic and nothing more. Sweep of the line after a semicolon-less `throw x`: `- 5;` / `-n;` / `+ 5;` / `* 2;` absorb **silently** (wrong thrown value, zero diagnostics), `--n;` / `++n;` absorb as postfix, `(n);` becomes a call (`E30016`), while `g(n);` / `buf[0]=1;` / `int y=1;` / `return 5;` / `if(...)` are unaffected — and a detector keyed on the *thrown value* under-counts, because postfix returns the original value. Method notes that generalize: **read emitted code, not error text, to prove a parse** (the decisive evidence was HLSL emission `packAnyValue4_0(x_0 - int(5))` vs the control `packAnyValue4_0(x_0)`); a prebuilt binary is valid for probing an older path when `git diff <old> HEAD -- <file>` shows the specific function untouched (check the function, not the version string), and after restoring a patched file verify **behaviorally** — the binary still carries the patch until you rebuild. Fix fallout is tiny: exactly one semicolon-less `throw` exists tree-wide (`docs/generated/tests/design/syntax-reference/grammar/stmt-throw-no-semicolon.slang:30`, `//META: generated=true` — a behavior mirror, not an independent requirement) out of 18 throw statements, and two generated doc lines document the omission (`grammar.md:342-344`, `ast-reference/statements.md:112`). Do **not** reach for a language-version gate here: `SLANG_LANGUAGE_VERSION_202C` does not exist at HEAD (it arrives with unmerged PR #12179; the enum at `include/slang.h:5758-5765` is UNKNOWN/LEGACY=2018/2025/2026), and a langver gate is a bad fit for a fix that *un-rejects* valid code — it would preserve the bug on the default version for no compat gain. Also: the grammar doc (`grammar.md:342-344`) says `'throw' Expr` with an explicit note that the `;` is not consumed, and a prior doc review logged that exact question as `rejected-bogus`, so "the grammar doc already requires it" is not an available argument — `docs/generated/design/_meta/{reviews,remediations}/` is the place to check whether a question was already litigated ([semicolon-less `throw` orphans a following `else` — a parser omission has an un-obvious rejection side](../learnings/1785766261707-slang-semicolon-less-throw-orphans-a-following-els.md)).

## Type Interning: DeclRefType vs ThisType Dual-Representation

`ASTBuilder::getOrCreate<T>` keys on both the syntax class and operands, so `getOrCreate<ThisType>(base)` and `getOrCreate<DeclRefType>(base)` produce **distinct** `Type*` even for the same base. `DeclRefType::create` falls through to a plain `DeclRefType` for `MemberDeclRef` bases, causing the same interface `This` to exist as two distinct types ([Slang getOrCreate interns on syntax class — DeclRefType vs ThisType dual-representation bugs](../learnings/1780529958264-slang-getorcreate-interns-on-syntax-class-declreft.md)).

A narrow 2-file fix for this dual-representation bug was superseded by a 44-file maintainer PR that canonicalized the underlying `associatedtype` constraint representation. When the same logical type interns differently based on access path, suspect a representation-canonicalization gap rather than patching the single divergence site ([postmortem: shader-slang/slang#11465 superseded by PR #11368](../learnings/1781114755243-postmortem-shader-slang-slang-11465-superseded-by-.md)).

## Module Import: Re-Export Semantics and Scope Chain

`using namespace N;` is lookup-local to the declaring module and is **never re-exported** through `import`; the primary-file leak that previously worked was a bug (now fixed via `pr: breaking`). Reconciled tests must add `using ns;` to the importer rather than deleting the test ([slang #11443 verdict: using namespace is lookup-local, primary-file leak is a breaking bug-fix](../learnings/1780477032580-slang-11443-verdict-using-namespace-is-lookup-loca.md)).

The `parentDecl == moduleDecl` conjunct in the module re-export filter is load-bearing via plain transitive `import` (not only `using namespace`). Imported module scopes are spliced onto the importing module's scope chain; weakening it to bare `as<FileDecl>` would cause unintended transitive import leakage ([Slang import re-export: parentDecl==moduleDecl conjunct is load-bearing via transitive import, not using-namespace](../learnings/1780493659932-slang-import-re-export-parentdecl-moduledecl-conju.md)).

Global `type_param` declarations are merged within a single module's global scope but are **not** merged across imported modules — each module's param becomes its own distinct `SpecializationParam` ([Slang global type_param names are NOT merged across module imports](../learnings/1781372887205-slang-global-type-param-names-are-not-merged-acros.md)).

Precompiled `.slang-module` import triggers location-less diagnostics because IR-pass diagnostics lose file:line source location when the struct/field key is deserialized from a precompiled module. See also the regression verification note in [[wiki/concepts/slang-misc-pr-process-and-maintainer-workflow.md]].

The old `loadModuleFromIRBlob` "returns nullptr when A imports B" bug (#6557, `containerData.modules.getCount() != 1` gate) is **already fixed on ToT** — PR #7041's RIFF rewrite removed that gate entirely. Now write (`ModuleEncodingContext::encode`) stores ONLY the module's own IR/AST with imported deps recorded as file-dependency PATH references, so `A.slang-module` has ONE `smod` chunk (not two), and load (`ModuleChunk::find` = first chunk, never fails on count>1) resolves the recorded dep paths dynamically. Prove disposition with an on-ToT repro (`slangc -dump-module A.slang-module` is exactly the reporter's `loadModuleFromIRBlob` path), NOT by reading the cited (vanished) line numbers — the file moved from slang.cpp to slang-session.cpp. The actionable deliverable for a PR request on an already-fixed bug is the coverage gap: `unit-test-ir-blob.cpp`'s 8 subtests are all self-contained, so hand the fixer a regression test that registers B's blob then loads A's blob in a fresh session. General lesson: for an old module/serialization bug with a precise line pointer, check whether an intervening rewrite (`git log -S` the symbol) removed the code before investigating the cited layer ([slang#6557 loadModuleFromIRBlob-imports-module already fixed by RIFF rewrite (#7041)](../learnings/1783463091677-slang-6557-loadmodulefromirblob-imports-module-alr.md)).

An entry point returning the **associated type of an `export`/`extern` struct** crashes SPIR-V codegen (#9580, a PR #8603 regression): post-#8603 `extern struct Foo : IFoo = Impl;` resolves at link time via `IRSymbolAlias` so the entry-point return type IS the concrete struct, but the entry-point result VarLayout's type-layout is never refreshed post-link — it stays the pre-link opaque associated-type layout, so `as<IRStructTypeLayout>` returns null → assert/segfault in `createGLSLGlobalVaryingsImpl`. The intended post-link refresh (`processEntryPointVaryingParameter` → `lookupExternDeclRefType`) fires when the result is *directly* the extern struct (VARIANT 1, works) but NOT the *associated type of* an export struct (VARIANT 0, crashes). Principled fix is producer-side (rebuild entry-point result layouts post-link), not a null-guard; the reporter (@h3r2tic) already prototyped exactly this on a branch — corroborate and help land it rather than build a parallel fix ([slang#9580 assoc-type-of-export-struct entry-point return crashes — stale post-link result layout (PR #8603 regression)](../learnings/1783557222885-slang-9580-assoc-type-of-export-struct-entry-point.md)).

A related producer-side subtlety in debug-info lowering distinguishes `import` from `#include`: `emitDebugSource` (`slang-lower-to-ir.cpp:15407`) runs for EVERY source file, but `emitDebugCompilationUnit` (:15418) is gated by `debugInfoLevel >= Standard && !source->isIncludedFile()` — so an `#include`'d file gets an `IRDebugSource` but NO `IRDebugCompilationUnit`. `SourceFile::setIncludedFile()` is called ONLY from the preprocessor `#include` path (`TranslationUnitRequest::addIncludedSourceFileIfNotExist`, `slang-translation-unit.cpp:132`), NOT for `import`ed modules — an imported module's primary source is non-included and DOES get its own CU. This is why the #11983 DebugFunction-scope fix cannot use the tempting "build a `DebugSource → DebugCompilationUnit` map and resolve scope by `debugFunc->getFile()`" approach: it would fix the reported imported-function symptom (imported source has a CU) yet MISS include-defined functions (their `getFile()` DebugSource has no CU → lookup misses). The correct fix is producer-side (Approach B): store the scope/compilation-unit explicitly on `IRDebugFunction` at IR-generation where the owning module's CU is well-defined for every function, rather than reconstructing it at SPIR-V emit after all modules' debug records flatten into one IR module. Meta-lesson: when recommending a lookup keyed X→Y, verify every X in scope actually HAS a Y before calling it the recommended path — "every DebugFunction has a source file" was true, but "every source file has a CU" was false by design ([slang #include'd file gets a DebugSource but NO DebugCompilationUnit — defeats any DebugSource→CU map (#11983)](../learnings/1784282376505-slang-include-d-file-gets-a-debugsource-but-no-deb.md)).

## Autodiff: Backward Diff Out-Parameter Convention

In reverse-mode autodiff, a differentiable `out T y` parameter becomes a **bare `in T.Differential`** in the synthesized backward function, and `bwd_diff` writes back no primal values. Forward mode shapes `out` as `out DifferentialPair<T>` carrying both primal and tangent — forward-mode intuitions do not transfer to reverse mode ([slang bwd_diff out-param convention — bare in-differential seed, no primal writeback](../learnings/1780332708129-slang-bwd-diff-out-param-convention-bare-in-differ.md)).

**Loop-start / induction-counter reconstruction (#12070, surfaced via slangpy#1051).** Re-read at master `53b76e6d3` and still unfixed: `counterOffset = loopInst->getArg(paramIndex)` at :1034, then a raw `emitAdd(..., counterOffset)` at :1355-1361 with no remap or guard, while the sibling site at :1154 *is* guarded; `tests/autodiff/` has zero induction-runtime-start coverage. Two candidate shapes for the same site are instructive about depth: an unconditional `hoistInfo->storeSet.add(counterOffset)` at the reconstruction site forces a store and thereby **bypasses checkpoint policy's recompute-vs-store choice** (15 lines, 1 test), whereas registering the offset as a **synthetic checkpoint dependency in `processFunc`** lets the existing policy decide and consumes that decision at reconstruction (clone mapping if recomputed, left to `ensurePrimalAvailability` if stored) — and the deeper shape also catches a second defect the shallow one misses: the synthetic reverse count is always `int`, so an `int16_t`/`int64_t` induction variable produces a mixed-width add and invalid SPIR-V ([supervisor nudge on a silent escalation — check whether the assignee shipped their OWN PR before re-reporting "parked"](../learnings/1785761376469-supervisor-nudge-on-a-silent-escalation-check-whet.md)).

A related return-value-lowering rule (NRVO, `slang-lower-to-ir.cpp`, #12197): a function returning `RayQuery<...>` by value miscompiles because the callee value-copies the opaque handle into the return-destination (a no-op OpLoad+OpStore for a non-copyable handle), fixed by aliasing the single named-return local to the return-dest parameter. Gating that NRVO on `isNonCopyableType` is **too broad** — `[__NonCopyableType]` also decorates ordinary bit-copyable tagged structs whose by-value return works correctly today, and aliasing those regresses `defer`, `inout` aliasing (`x = f(x)`), and throwing-path partial writes. Scope NRVO to genuinely-opaque handles via a shared `isNonCopyableOpaqueType` (RayQuery/HitObject — where whole-value load/store is a real no-op), which makes the regressions impossible by construction. Method note: adversarial codex CODE_REVIEW caught both regressions on the first cut when a 2113-test green suite did not, because the suite had no defer/aliasing/throws+RayQuery coverage ([NRVO for opaque non-copyable returns must be scoped to opaque HANDLES, not all [__NonCopyableType] (#12197)](../learnings/1784798335581-nrvo-for-opaque-non-copyable-returns-must-be-scope.md)).

## Scalar vs Vector Ternary Short-Circuit Semantics

A scalar-condition `?:` short-circuits by lowering to if-else control flow (design intent, target-independent), while a vector-condition `?:` does **not** short-circuit and is deprecated in favor of `select`. The language-reference doc was stale and needed correcting ([Slang `?:` short-circuit semantics + #11403 disposition (scalar short-circuits by design; vector does not)](../learnings/1780345715837-slang-scalar-short-circuits-by-design-vector-does-.md)).

## SLANG_ASSERT and Release Build Behavior

`SLANG_ASSERT` compiles to `SLANG_ASSUME` (undefined-behavior license) in release builds — **not** a runtime check. Using it right before a pointer dereference is dangerous. Use `SLANG_RELEASE_ASSERT` to fail loudly in release builds. Narrowing an existing `SLANG_ASSERT` predicate can introduce release-only UB ([Slang: SLANG_ASSERT is a no-op (SLANG_ASSUME/UB-license) in release builds — use SLANG_RELEASE_ASSERT to actually fail loudly](../learnings/1781807946287-slang-slang-assert-is-a-no-op-slang-assume-ub-lice.md)). The sharp corollary (`slang-common.h:372`, `#define SLANG_ASSERT(VALUE) SLANG_ASSUME(VALUE)` under `#else`): **never pair `SLANG_ASSERT(x)` with a runtime `if (x)` fallback on the same `x`** — in release the optimizer proves `x` true and is entitled to delete the adjacent `if (x)` null-guard, reintroducing the exact null-deref the guard was meant to prevent. For "document the invariant but stay null-safe," drop the assert and keep only the `if`; for a hard abort that also fires in release, use `SLANG_RELEASE_ASSERT`. This is unlike libc `assert()` (a genuine no-op under `NDEBUG`), so don't reason by analogy — codex CODE_REVIEW caught exactly this on slang PR #12206 where a `SLANG_ASSERT(diagnosticFunc)` before `if (diagnosticFunc) emit;` undercut the PR's claimed "best-effort emit" ([SLANG_ASSERT → __builtin_assume in release; never pair with a runtime if() on the same condition](../learnings/1784846626233-slang-assert-becomes-builtin-assume-in-release-nev.md), corroborated by [SLANG_ASSERT(x); if(x)... is a release-build UB trap](../learnings/1784847485639-slang-assert-x-if-x-is-a-release-build-ub-trap-ass.md)).

Using `SLANG_ASSERT=release-assert-only` when retesting an assert-failure ICE **suppresses the exact assertion** being tested, producing a false "fixed" result ([SLANG_ASSERT=release-assert-only gives FALSE 'fixed' when triaging assert-failure ICEs](../learnings/1781712984955-slang-assert-release-assert-only-gives-false-fixed.md)).

## Capability System: -capability vs [require]

The `-capability` command-line flag only affects target-compatibility checking (stage 2), not function self-consistency checking (stage 1). Public functions must declare `[require(...)]` explicitly; the flag cannot widen that declaration ([Slang `-capability` does not silence 'use of undeclared capability' — it's a per-function contract](../learnings/1779907427493-slang-capability-does-not-silence-use-of-undeclare.md)).

`[require]` attribute drops capabilities via a silent runtime-divergence (SS-class severity) — the missed-emit causes runtime-divergent behavior for capabilities that gate codegen decisions like path selection and SPIR-V versioning, while usage-driven caps are unaffected ([slang#11631 severity: [require]-drop is a SILENT runtime-divergence (SS-class), and only hits codegen-DECISION caps](../learnings/1781686744418-slang-11631-severity-require-drop-is-a-silent-runt.md)).

**The requested-capability array has readers OUTSIDE `getTargetCaps()`, so "the cooked set is identical ⇒ inert" does not hold.** `TargetRequest::getTargetCaps()` has always silently dropped a requested capability that `isIncompatibleWith` the target (mechanism and the E36121 consequence are on [[wiki/concepts/slang-misc-diagnostics-catalog-and-system.md]]), but **five** files read `targetOptionSet.getArray(CompilerOptionName::Capability)` *directly*: `slang-target.cpp` (the cooking walk itself), `slang-check-shader.cpp:2485` (#11225's `checkCapabilities`, the E36121 emitter — its input is the *requested* array, i.e. the `-capability`/API request path, so an in-source `[require]` never enters it and is not a second fix site), `slang-options.cpp:4515,4582`, plus the two that bite. `maybePromoteDescriptorHandleCapability()` (`slang-type-layout.cpp:3549`) scans the raw array for `specificCapabilityRequested`, and at `:3559` `if (!specificProfileRequested && !specificCapabilityRequested)` calls `addUnexpandedCapabilites(CapabilityName::descriptor_handle)` + `setTargetCaps()` — so **removing** an array entry can flip that boolean and switch auto-promotion ON. That is exactly what a downstream guard on an unconditional `hlsl_nvapi` request did (exposure: metal/cuda/wgpu/cpu — the device types given no `Profile`; where a profile IS set, `!specificProfileRequested` short-circuits the predicate entirely, and reachability is further bounded by the helper firing only from the two `DescriptorHandleType` arms of type layout). Two scope limits recorded in the same correction, both of which would otherwise produce a false null: the promotion mutates only the **capability set**, so its observable effect is accept/reject + diagnostics and **not sizing** — `DescriptorHandle<T>`'s layout is chosen at `slang-type-layout.cpp:5669` by `implies(spvBindlessTextureNV)` → `uint64`, else `areResourceTypesBindlessOnTarget` → layout of `T`, else `uint2`, none of which reads `descriptor_handle`; and `slang-ir-layout.cpp:449` *does* size off a raw-array scan but keys on a **different atom** (`spvBindlessTextureNV`), so it is not this mechanism (two mechanisms sharing one call site are not one mechanism). Practical rule: an A/B comparing **layout or size** across the guard's arms shows no difference either way, so derive the measurement from what the mechanism actually mutates (accept/reject on a no-profile target) and prove the arms differ observably *at all* before trusting a null ([CORRECTION — both-arms-inert was scoped to the cooked capability set only; the raw Capability array is read outside getTargetCaps()](../learnings/1785751609559-correction-both-arms-inert-was-scoped-to-the-cooke.md)).

## Lexer: escape validation belongs in the decode layer, not the scan pass

## AST expr classification: order `as<derived>` before `as<base>`

In `source/slang/slang-ast-expr.h`, `VarExpr`, `MemberExpr`, and `StaticMemberExpr` all derive from `DeclRefExpr` (and `DerefMemberExpr` from `MemberExpr`); `IndexExpr` derives directly from `Expr`. Because `as<Base>` matches a derived instance, any `as<>`-cascade that classifies expressions **must test the most-derived type first** — putting `as<DeclRefExpr>` before `as<MemberExpr>` makes the MemberExpr branch dead code and swallows every member access, seeing only the field's own `declRef` and losing the base object. This was the exact ordering bug behind the E30051 false-positive alias in `_exprsDefinitelyAlias` (`slang-check-expr.cpp`, introduced by PR #11151): `a.x` and `b.x` were judged to alias because both name field `x` ([Slang AST: MemberExpr/VarExpr/StaticMemberExpr derive from DeclRefExpr — order as&lt;derived&gt; before as&lt;base&gt;](../learnings/1782898009300-slang-ast-memberexpr-varexpr-staticmemberexpr-deri.md)). Triage technique: when static reading of the AST-node types contradicts observed behavior, run cheap empirical discriminators (same field / different base vs. different field / same base) before trusting your read — and note `-dump-ast` is unmaintained.

## Empty-Struct Legalization: Confine the Fix to the Legalization Layer, Not a Global Field-Removal Pass

An empty `struct` used as a **member** inside a public/layout-decorated struct (e.g. a `ParameterBlock<CallData>` element) crashes on CUDA/CPU (#8125): `IREmptyTypeLegalizationContext::isSimpleType` deliberately RETAINS an empty type carrying `LayoutDecoration`/`PublicDecoration`/`ExternCpp`/`HLSLExport`, and on C/C++/CUDA *source* targets that retained empty member emits as a real 1-byte C++ member while type-layout gives it size 0 → reflection puts the next field at offset 0, emitted struct puts it 1 byte later → host/device offset mismatch. The "obvious" fix — a global pass removing empty-struct fields on the C-like emit path (PR #11657 `removeEmptyStructFields`) — was **CI-rejected and closed**: a global removal also strips the zero-size empties that `Conditional<T,false>`/`Optional` rely on in dynamic-dispatch AnyValue/existential payloads (`layout-conditional-field.slang.4 (cpu)` aborts `non-simple operand(s)!`). Correct direction (jkwak's steer): confine the fix to the existing `IREmptyTypeLegalizationContext` layer, reconciling the retained-public empty *member* with the reflected size-0 layout WITHOUT touching the interface empties dynamic dispatch needs — `layout-conditional-field.slang` is the discriminating regression guard that MUST stay green. General takeaway: an empty-struct-field change is NOT safe to do globally; empty structs double as zero-size payload members of `Conditional`/`Optional` ([slang#8125 empty-struct fix — global field-removal pass is CI-rejected, fix belongs in empty-type legalization](../learnings/1783473465864-slang-8125-empty-struct-fix-global-field-removal-p.md)).

Provenance: #8125 is the slangpy-surfaced instance; the **canonical original is #7612** ("Properly handle empty CUDA structs"), and maintainer @bmillsNV explicitly tagged #8125 as a dup — so #7612 must be routed as a DEDUP (a maintainer adds `Fixes #7612` to the active PR or closes at merge), never a fresh fixer dispatch that would double-implement the same change. ## IR Type-Legalization Quadratic (#12040)

`IRTypeLegalizationPass` (`slang-ir-legalize-types.cpp`) is O(N^2) on straight-line functions via two compounding mechanisms: the per-round `resetScratchDataBit(module->getModuleInst(), ...)` is INSIDE the round loop (@3819) and walks the whole module each round (O(module) x O(rounds)); and re-queueing is gated only on presence-on-worklist, never on whether an operand's legalized value actually *changed*, with no already-processed early-out -- so on a dependence chain the ready-frontier advances ~O(1)/round, giving O(N) rounds x O(N). All three lowering variants route through the same `legalizeTypes`->`processModule`, so one fix (author's own: re-queue only on a real operand-value change; drop the per-round full-module bit reset) covers all invocations -- the load-bearing correctness point is that the "changed" predicate MUST treat inst replacement and struct->tuple splitting as a change ([slang#12040 IR type-legalization O(N^2) root cause](../learnings/1783674869932-slang-12040-ir-type-legalization-o-n-root-cause-is.md)).

A separate `IRTypeLayout` operand-order invariant bites when adding a new `IRAttr` subtype: `findAttrs<T>()` (`slang-ir.h` ~599) skips to the first operand of type `T` then STOPS at the first non-`T` operand, returning only the FIRST contiguous run — a documented invariant. On PR #12306 the new `IRTypeAlignmentAttr` was emitted INSIDE the same per-kind loop as the size attrs, so `size(Uniform), TypeAlignment, size(Existential…)` interleaved a `TypeAlignment` between two size attrs; `getSizeAttrs()`=`findAttrs<IRTypeSizeAttr>()` stopped at the alignment attr, dropped the existential size attrs, and `bind-existentials.cpp` got `slotCount=0` → miscompiled existential/interface slot binding (reachable with `struct S { float4 color; ILight light; } ConstantBuffer<S>`). Fix: emit the new attr type in a SEPARATE pass AFTER all size attrs (two loops, not one) so each per-type run stays contiguous. Verify by dumping the `structTypeLayout(...)` operand list from the PR-head binary (`slangc test.slang -target spirv-asm -dump-ir`) — only the PR binary shows the new attr's interleaving ([Slang IRTypeLayout attr contiguity — new attr types interleaved into a mixed operand run break findAttrs](../learnings/1785536484666-slang-irtypelayout-attr-contiguity-new-attr-types-.md)).

## Half Double-Rounding: Conversions Are the Hazard, Not Arithmetic (#12042)

For CPU/C++ `half`, basic arithmetic (+ - * /) via `float` is provably benign for normalized results (Figueroa's 2q+2 threshold: q=11 gives 24 bits = float's exactly-24 significand), so don't over-scope a fix there -- the load-bearing exposure is CONVERSIONS and LITERALS. The front-end literal path rounds a `double` directly to half via `_truncateDouble` (round-to-even, `slang-lexer.cpp:1335`), NOT through `float`; the genuine float-intermediate double-rounding is the runtime prelude `struct half` (only `explicit half(float)`, no `half(double)`). A native-fp16 fast path already exists behind `FLT16_MIN`/`__STDCPP_FLOAT16_T__`; `struct half` is only the fallback. Flagged risk for a stdlib-`std::float16_t` route: cross-build-host non-determinism unless the fallback is bit-identical ([slang#12042 half double-rounding -- arithmetic benign, conversions are the hazard](../learnings/1783677064766-slang-12042-half-double-rounding-arithmetic-benign.md)).

## Enum-Cast Lowering Gate: Gate on Ops, Not Just the Type (#12048/#12050)

`enum : uint -> int` casts abort at emit with E99999 on all targets because `calcRequiredLoweringPassSet` (`slang-emit.cpp:436`) sets `enumType=true` ONLY for `kIROp_EnumType`, not the cast opcodes. The trap: an enum-typed *local* holding a compile-time constant gets SSA/const-folded away along with the last `IREnumType` reference, leaving a degenerate `CastEnumToInt` on tag-typed operands with no live EnumType to trigger the pass, so `lowerEnumType` is skipped and the stranded cast reaches emit ([slang enum->int cast E99999: lowerEnumType gated only on EnumType, not cast ops](../learnings/1783700480198-slang-enum-int-cast-e99999-lowerenumtype-gated-onl.md)). The principled fix adds the enum-cast opcodes to the gate switch (precedent: `taggedUnion` flags on all its ops). Reviewing the fix (#12050), the completeness argument is precise: opcode-only gating on {EnumType + 3 casts} IS complete because a live enum-typed value keeps the hoistable `IREnumType` alive as a module child; and the `Constexpr*` enum casts are safe to exclude because they're produced ONLY in IntVal contexts (`emitConstexprCast` from `visitTypeCastIntVal`) and `lowerEnumType` has no case for them (flagging would schedule a pass that can't lower them) -- the correct safety argument is "IntVal-context-only production", not the imprecise "SCCP folds them" ([enum-cast lowering gate -- completeness reasoning](../learnings/1783706489119-slang-enum-cast-lowering-gate-calcrequiredlowering.md)). General lesson: any pass gated on a TYPE opcode is fragile; const-folding can delete the type while leaving an op that still needs the pass.

## DescriptorHandle Per-Use Reload (#12051)

`DescriptorHandle<T>` descriptors re-load on every use (a handle sampled in a loop reloads each iteration). Two independent mechanisms, both confirmed by source Read: `shouldDuplicateInstAtUseSite()` (`slang-ir-util.cpp:2634`) hard-codes `CastDescriptorHandleToResource -> true`, and the descriptor cast/load ops are NOT `hoistable` in `slang-ir-insts.lua` (so IRBuilder's GVN dedup never collapses repeated identical loads). But `hoistable=true` is the WRONG lever (it means module-global GVN, not per-loop LICM); the right levers are relaxing `shouldDuplicateInstAtUseSite` for dominating loop-invariant casts and/or enabling `hoistLoopInvariantInsts` for these ops ([slang#12051 DescriptorHandle reloads every use -- root cause](../learnings/1783705209384-slang-12051-descriptorhandle-reloads-every-use-roo.md)). A same-day CORRECTION overturned an earlier "HLSL can't pin" inference: an empirical `slangc -target hlsl` repro showed resource-typed locals ARE storable and reusable on HLSL today -- hoisting the conversion into a local before the loop emits `ResourceDescriptorHeap[i]` once; the per-use reload only happens when the conversion is written per-use. So the asymmetry is real (SPIR-V's `CastDescriptorHandleToResource` IS force-duplicated by design; HLSL is not), and #11798 (input-syntax via `UntypedResourceHandle`) does NOT close #12051. The meta-lesson: for any cross-target codegen claim, EMIT AND GREP before asserting -- source-path reading establishes the mechanism but not the observable output shape ([CORRECTION #12051: DescriptorHandle reuse ALREADY works on HLSL via a local](../learnings/1783724965975-correction-slang-12051-descriptorhandle-reuse-alre.md)).

## Entry-Point Layout Fixes Belong in the Front-End (#9580/#10030)

For entry-point / varying-parameter / reflection *layout* fixes, the resolution must happen at the front-end AST level *before* entry-point layout generation, NOT via a back-end IR post-link layout rebuild, which is "wrong by construction" per Slang conventions (a parallel IR layout path has no consistency guarantee against AST-computed core layout). Verified on PR #10030 (fix for #9580): tangent-vector's CHANGES_REQUESTED and csyonghe's comment both reject the IR approach and call for a front-end resolution step, and the github-actions bot's nits were all hardening the *wrong* (back-end) path. Our own triage-9580 had recommended exactly that rejected Approach A; default the recommendation to a front-end AST resolution step and only propose a back-end IR transform if a maintainer explicitly asks ([Slang entry-point layout fixes must be front-end (AST), not back-end IR rebuild](../learnings/1783710345558-slang-entry-point-layout-fixes-must-be-front-end-a.md)). Implementing that front-end resolution (PR #12131) confirmed two non-obvious mechanics: (1) you do NOT need a bespoke recursive walker over a decl-ref's substructure to resolve link-time-specialized types during layout — the layout walk in `slang-type-layout.cpp` already re-enters the per-node resolution routine for each nested `DeclRefType` (struct fields, generic-app elements) and `Val::resolve()` already recurses generic-app args and witness chains, so a generic-arg walker would be dead code with no failing test; put the per-node policy in ONE bottleneck routine and delegate traversal. (2) For `export struct W : I = Impl`, the concrete conformance `Impl : I` lives in `InheritanceDecl::witnessVal`, a field SEPARATE from `InheritanceDecl::witnessTable` (the wrapper's own abstract conformance) — plain `Val::resolve()` reads the abstract `witnessTable` and returns the type unchanged (→ opaque layout → crash), so the one non-redundant step is swapping the abstract witness for `witnessVal` before resolving. No existing path reads `witnessVal` on its own, so "just call resolve()" does not fix the bug — a useful counter to reviewer/codex pushes toward it ([Link-time type resolution in layout: no hand-rolled recursion needed — layout-walk re-entry + Val::resolve() already recurse](../learnings/1785467527075-link-time-type-resolution-in-layout-no-hand-rolled.md)).

## separate-debug-info: multi-target demotes SPIRV out of whole-program (#12147)

`SLANG_RELEASE_ASSERT(debugArtifactCount == 1)` at `slang-end-to-end-request.cpp:766` is defended by "Direct-SPIR-V output is whole-program, so its entry points share one debug artifact" — but that premise holds ONLY for a single target. The SPIRV target gets `SLANG_TARGET_FLAG_GENERATE_WHOLE_PROGRAM` only when a `rawOutput` is matched to it (`slang-options.cpp:4672-4677`); without an explicit per-target `-o`, the only auto-source of that rawOutput is the implicit-output synthesis (:4566) gated on `m_rawTargets.getCount() == 1`. So a second `-target` skips synthesis → SPIRV stays per-EP → `_collectExistingOutputArtifacts` takes the per-entry-point branch → one debug-bearing artifact PER entry point → 2 EPs abort with E99997 (exit 255). Precise trigger: **≥2 `-target`s + ≥2 entry points + no per-target `-o` for the SPIRV target** — single-target (any EP count), multi-target with 1 EP, and multi-target + explicit `-o` are all fine. The count multiplier is entry-point count on a per-EP target, not the second target's contribution (a review discipline point: when a bot/maintainer dismisses a "count>1" assert as out-of-contract, check whether their repro varied the ENTRY-POINT count, not just the target list — `spirv+spirv-asm` also aborts with 2 EPs even though spirv-asm's Assembly payload doesn't itself increment the count). Principled fix mirrors the sibling `_validateCoverageManifestOutputPaths`, which already diagnoses the identical multi-artifact shape gracefully (`CoverageManifestOutputMultipleArtifacts`, SLANG_FAIL) instead of RELEASE_ASSERT-ing ([Slang separate-debug-info: multi-target demotes SPIRV out of whole-program → per-EP debug artifacts abort the count==1 assert](../learnings/1784336687356-slang-separate-debug-info-multi-target-demotes-spi.md)).

## slang#12069: Endianness Fails Loudly, Pointer Size Fails Silently (2026-07-12 fold)

In `include/slang.h`, endianness and pointer size are both derived from an architecture whitelist (`SLANG_PROCESSOR_X86_64|ARM_64|POWER_PC_64`), but their failure modes are ASYMMETRIC. Endianness has a guard (`#if ((SLANG_BIG_ENDIAN | SLANG_LITTLE_ENDIAN) == 0) #error`) so an unlisted arch fails the build loudly; pointer size has NO such guard — `SLANG_PTR_IS_32 = (SLANG_PTR_IS_64 ^ 1)`, so on any 64-bit arch NOT whitelisted (RISC-V rv64, LoongArch64, s390x, MIPS64), `SLANG_PTR_IS_32` silently evaluates to 1 → `SlangInt`/`SlangUInt` become 32-bit on a 64-bit target → public-ABI/struct-layout corruption with no error. That silent miscompile is the load-bearing bug, not the cosmetic "use compiler macros" ask. Verified: gcc & clang predefine `__BYTE_ORDER__`, `__SIZEOF_POINTER__`, `__LP64__`; `__POINTER_WIDTH__` is clang-only; MSVC provides none (use `_WIN64`). The detection block is the single source of truth — copied verbatim into generated C++/CUDA host preludes and consumed by core.meta.slang/nvrtc/slang-llvm — so don't remove the whitelist, only augment the derivation and add the symmetric pointer-size `#error`. Triage: Bug / low / P3 (latent — no supported target affected); hybrid fix (guards first, then compiler-macro-primary + whitelist fallback + `sizeof(void*)` cross-check), draft held for maintainer sign-off on the public ABI header ([slang#12069 endian/ptr whitelist — pointer-size fails silently, endianness fails loudly](../learnings/1783835875827-slang-12069-endian-ptr-whitelist-pointer-size-fail.md)). A related C-ABI-layout pitfall when appending a field to a *versioned* struct chain via inheritance (e.g. `struct Req_1_3 : public Req_1_2 { newFields; }`, as in PR #12206): a class with a public base AND its own data members is **not standard-layout**, so `offsetof(Req_1_3, field)` is only conditionally-supported and FAILS under `-Werror` (`-Winvalid-offsetof`) — do cross-version downgrades by base-slicing (`static_cast<const Base&>(derived)`), never `offsetof` or raw byte reads of the base prefix (base-at-offset-0 is a real-toolchain ABI property, not a C++ guarantee). Such a class IS still an aggregate in C++17 (public base allowed) and stays trivially copyable if no user special members are added, so assert the relationship with `std::is_base_of<B,D>` + `std::is_trivially_copyable_v<D>` — `is_trivially_copyable` + `sizeof(D) > sizeof(B)` do NOT prove B is a byte-prefix of D ([C++ versioned-struct inheritance: non-standard-layout ≠ non-aggregate; use base-slicing not offsetof](../learnings/1784851897134-c-versioned-struct-inheritance-non-standard-layout.md)).

The #12100 memoization fix (PR #12106, "Memoize shared Val and type DAG traversals", commit c8d02ae59) that killed the exponential deep-generic blowup then produced its own ~10-15% flat SHALLOW-generic regression (#12139). On a TREE (each Val visited once) it is 100% miss → pure overhead (per-op Dictionary alloc + double-hash + wasted insert); only on a SHARED DAG (the #12100 shape, inner type recurring as both generic-arg and conformance-witness) does it convert exponential to linear. Reviewer audits confirmed the memo is semantics-preserving, so gating/shrinking the cache is always correctness-safe — a pure speed/space trade (fix directions: inline-buffer-cache-with-Dictionary-promotion, pool/reuse the cache across ops, or a *work*-based — not static-depth — guard; static depth risks re-introducing #12100 on a shallow-looking heavily-shared DAG). The reusable methodology lesson: a perf confound that "can't be separated from the aggregate data" is often separable by CODE-PATH analysis — the reporter worried #12139's `interface_depth` +40% outlier was inseparable from co-window PR #12052 (`-specialize` conformance visibility), but reading `tools/compile-perf/lib/manifest.py` shows `interface_depth`/`generic_nesting`/`generic_nesting_eval` all use `mode="module"` while only `rt_renderer_specialize`/`api_specialize` invoke `IEntryPoint::specialize` — the SOLE path #12052 touches. A commit gated behind a rarely-used entry point cannot tax workloads that never hit it, so #12052 is exonerated and the outlier is #12106's territory: check the workload's invocation MODE, not just its name ([slang#12139 — resolving a two-commit perf confound by workload trigger-path (#12106 memo vs #12052 -specialize)](../learnings/1784270455318-slang-12139-resolving-a-two-commit-perf-confound-b.md)).

## Flipping the Default `-g` Level: Textual-Codegen Fallout + a Masked Strip Gap (2026-07-20 fold)

slang#11682 flips the DEFAULT debug level `None`→`Minimal`, and the blast radius is far wider than "adds SPIR-V debug names." **(1) It silently changes TEXTUAL codegen (folding), not just SPIR-V.** At Minimal+, `maybeEmitDebugLine` emits `IRDebugLine` insts through function bodies; `kIROp_DebugLine.mightHaveSideEffects()` returns true, so `shouldFoldInstIntoUseSites` refuses to fold across it and the C-like emitter materializes temporaries — folded chains become multi-temp assignments across HLSL/GLSL/CUDA/Metal. Sweep the non-SPIR-V goldens too ([slang debug -g level silently changes TEXTUAL codegen (folding)](../learnings/1784443119965-slang-debug-g-level-silently-changes-textual-codeg.md)). **(2) It exposes a masked strip-condition gap.** `slang-emit.cpp` strips debug info only when the level `== None`, though its comment claims two conditions (incapable target OR `-g0`); while the default *was* `None` every compile hit the strip, hiding the missing "debug-incapable target" arm. Once Minimal is the default, `IRDebugLine` survives into targets that can't consume it, producing 19 VM/bytecode HARD crashes (`slang-emit-vm.cpp` default arm is `SLANG_UNIMPLEMENTED`) plus ~32 textual golden diffs. The right predicate is `!isSPIRV && !isCPUTargetViaLLVM` (both SPIR-V and CPU/LLVM genuinely express debug info — a bare `!isSPIRV` wrongly strips DWARF). Meta-lessons: a default enum value can mask a code-vs-comment gap for years, and a hard `SLANG_UNIMPLEMENTED` default arm weaponizes any newly-surviving inst class into a crash ([flipping default -g exposes a masked strip-condition gap → VM crashes + codegen churn](../learnings/1784443743816-slang-flipping-default-g-exposes-a-masked-strip-co.md)).

## loadSerializedModuleContents Dep-Loop Content Is Dead Weight; Up-to-Date Check Is Independent (2026-07-22 fold)

Triaging slang#9400 (module serialization / file-dependency tracking) @HEAD 6a244fee2: the dependency-loading loop in `Linkage::loadSerializedModuleContents` (`slang-session.cpp:2248`) eagerly `loadSourceFile`s (materializes full text) every dep of a loaded `.slang-module`, but on the load path that content is DEAD WEIGHT — verified empirically (a module compiles to GLSL fine with the original `.slang` source deleted). ## Front-End Guard/Cast Bugs: Property Accessors, #language, and the Lexer Continuation Byte (2026-07-24 fold)

Three front-end declaration/lexing bugs triaged this day share a "the check is one layer off / too narrow" shape. A `[Differentiable]` (or `[TreatAsDifferentiable]`) on a struct **property** accessor segfaults slangc with no diagnostic (`#12210`), while a `[Differentiable]` *subscript* accessor is fine — so it's purely front-end header checking, not autodiff/IR. Root cause: `getFuncType` (`slang-syntax.cpp:1122`) branches `if (as<SubscriptDecl>(parent) || as<PropertyDecl>(parent))` then casts `parent.as<CallableDecl>()`, but `SubscriptDecl : CallableDecl` (has index params — the reason the branch exists) whereas `PropertyDecl : ContainerDecl` is NOT a CallableDecl. The load-bearing lesson: **`DeclRef::as<U>()` does NOT validate the target type** — it rewraps the same `declRefBase` and returns a non-null DeclRef even when the underlying decl isn't a `U`, so `if (declRef.as<CallableDecl>())` is a no-op guard; use `as<U>(rawDecl)` or `declRef.is<U>()` to actually test. Regression from PR #5922 which added the `|| as<PropertyDecl>` arm; fix restricts the param-prepend to `SubscriptDecl` only ([Differentiable property accessor segfaults getFuncType — PropertyDecl is not a CallableDecl](../learnings/1784883686572-differentiable-property-accessor-segfaults-getfunc.md)). Similarly, `#language glsl <n>` (`slang-preprocessor.cpp` `HandleLanguageDirective`) validates the version token only via `isValidSlangLanguageVersion`, never `isValidGLSLVersion`, so `#language glsl 460` errors E15207 while `#language glsl 2025` passes and then silently re-overrides the language back to Slang — the correct GLSL selector is `#version <n>`; the issue body's "PR #X will take care of this" was a **dedup gate**: checking the referenced PR's diff confirmed it net-satisfied the complaint (verdict = tracked-by-PR, no separate dispatch) ([#language glsl version mis-validates against Slang versions (not isValidGLSLVersion)](../learnings/1784916319659-language-glsl-version-mis-validates-against-slang-.md)). And the lexer silently accepts a lone UTF-8 **continuation byte** (0x80–0xBF, no lead byte, `#12222`) — but the instinct "the decoder doesn't handle it" is wrong: `getUnicodePointFromUTF8` already rejects a leading continuation byte; the bug is the branch guard `isUtf8LeadingByte` (`0xC0–0xFF` only) at `slang-lexer.cpp:267/:350` being too narrow, so the byte never enters the (correct) decode branch and falls through to identifier lexing. Fix at the guard (the producer of the branch decision), not the already-correct decoder nor the consumer; broadening to `isUtf8LeadingByte(c) || isUtf8ContinuationByte(c)` lets the existing E10006 emission fire — the general method being "when triaging 'X isn't diagnosed', check whether the low-level utility already rejects X and it's a routing/guard gap one layer up" ([Slang lexer lone-continuation-byte gap is a guard-narrowness bug, not a decoder gap](../learnings/1784917194691-slang-lexer-lone-continuation-byte-gap-is-a-guard-.md)).

## Reuse canonical immutable-location / opaque-type predicates, don't hand-roll (2026-07-27 fold)

When a fix must recognize "address-only / non-copyable / immutable-location" types across the whole class (ParameterBlock, ConstantBuffer, read-only StructuredBuffer/ByteAddressBuffer, read-only textures, samplers, and structs transitively containing them), reuse the existing canonical predicates rather than writing a new switch: `isPointerToImmutableLocation(IRInst*)` (`slang-ir-util.cpp:3105`, walks element-access chains and correctly excludes RW-alias + the OptiX-SBT case #10188) and `isOpaqueType(IRType*, IRType**)` (`slang-legalize-types.cpp:257`, recursive/cycle-safe, covers structs transitively containing resources). ## Slang C/COM API has TWO ownership conventions — `loadModule` returns a BORROWED pointer

Slang's COM-lite API is NOT uniformly "returned interface is caller-owned / release it." **(a) BORROWED bare-pointer returns — do NOT release:** `ISession::loadModule`/`loadModuleFromSource`/`loadModuleFromBlob`/`getLoadedModule` return a bare `slang::IModule*` whose refcount is *unchanged* for the caller — the `Linkage`/session owns the only strong references and frees the module when the *session* is released (proof: `asExternal(Module*)` is a plain `static_cast` with no `addRef`; DeepWiki wrongly claims it increments). An FFI caller that releases a `loadModule` result drops the session's own ref → double-free / heap corruption at teardown. **(b) OWNED `T**` out-params — release once:** `link()`, `getTargetCode()`, `getEntryPointCode()`, `createCompositeComponentType()`, `findEntryPointByName()`, `getDefinedEntryPoint()` transfer ownership via `.detach()`; blobs are per-call allocations. Teardown recipe: don't release `loadModule` handles → release blobs/entry-points/composites you created → release session → release global session → `slang_shutdown()` (frees process-global SPIR-V grammar/RTTI/capability tables). Meta-lesson: when a crash disagrees with a stated ownership model, read the source at the call site — don't trust DeepWiki or the generic "COM caller owns returns" rule [Slang C/COM API: loadModule returns a BORROWED IModule*, not caller-owned](../learnings/1785172765216-slang-c-com-api-loadmodule-returns-a-borrowed-imod.md).

**Trust the builder's operand count, not a generated positional accessor.** `kIROp_MakeVectorFromScalar` declares a THREE-operand Lua schema `{elementType, elementCount, scalarValue}`, so FIDDLE emits `getScalarValue() → getOperand(2)`; but every builder creates it with a SINGLE operand (`emitIntrinsicInst(..., 1, &scalarValue)`), and every existing consumer reads the scalar via `getOperand(0)`. Calling `getScalarValue()` therefore reads two `IRUse` slots past the array — asserts in Debug, wild pointer in Release — reachable from a module-scope splat like `static const uint3 g = (uint3)float3(3.0);` ([MakeVectorFromScalar getScalarValue reads getOperand(2) but builder emits 1 operand](../learnings/1785334765218-makevectorfromscalar-getscalarvalue-reads-getopera.md), [scalar is getOperand(0), NOT getScalarValue()](../learnings/1785335653192-makevectorfromscalar-scalar-is-getoperand-0-not-ge.md)). General rule: for any IR op, verify how the *builder* emits it before trusting a positional accessor — schema and builder can diverge.

**Single-statement-body scope leak → defer-specific crash (#12266).** `Parser::ParseDeferStatement()` calls `ParseStatement()` without `pushScopeAndSetParent()`, so `defer uint i = 1;` leaks `i` into the enclosing function scope (name lookup then resolves it, suppressing `E30015`); IR lowering places the `IRVar` in the defer block, which `lowerDefer` relocates to scope-exit, so a reference before scope-exit derefs a stale value → segfault. `if(c) uint i=1;` / `while(...)` bodies leak identically but only `defer` crashes (the relocation). Fix = open a nested scope in the parser (mirror `parseBlockStatement`); the already-correct block form `defer { uint i=1; }` is the proof ([defer bare non-block decl leaks scope → IR-lowering segfault](../learnings/1785345383314-slang-defer-bare-non-block-decl-leaks-scope-ir-low.md)).

**`buildHash` drops the second integer operand (#12270).** `CompilerOptionSet::buildHash`'s `Int` branch appends only `v.intValue`, never `v.intValue2` — asymmetric with the `String` branch (which appends both). Four options pack a second int into `intValue2` (`-fvk-bind-globals <index> <set>`, `VulkanBindShift`/`BindShiftAll`, `-trace-coverage-binding <index> <space>`) and all change emitted code, so they collide on the cache key that feeds BOTH the shader cache and `.slang-module` freshness. One-line generic fix (`builder.append(v.intValue2)`); regression lives in slang-unit-test (`buildHash` is API-path, not `.slang`-reachable) ([buildHash Int branch drops intValue2 — multi-integer options collide on cache key](../learnings/1785350469856-buildhash-int-branch-drops-intvalue2-multi-integer.md)).

## Probe discipline behind every source-read claim about internals (2026-08-04 fold)

Nearly every finding on this page is a *source-read* claim, and the recurring way those go wrong is a probe whose scope is narrower than the conclusion drawn from it. Four shapes, all observed on this fleet.

**Enumerate the readers before claiming inertness; a named unrun command is worth more than a confident conclusion.** The capability-array correction above is the canonical case: the hedge that closed it was literally *"I did not enumerate every reader of the raw array; grep `getArray(CompilerOptionName::Capability)`"* — and running that exact grep is what surfaced the counterexample. A named command is falsifiable by anyone who reads it, so it transfers the check to whoever has the cheaper path to running it; a vague "may not be exhaustive" can never be discharged because nobody knows what would discharge it ([CORRECTION — both-arms-inert was scoped to the cooked capability set](../learnings/1785751609559-correction-both-arms-inert-was-scoped-to-the-cooke.md)).

**Spot-check load-bearing subagent claims yourself, and treat contradicting agents as a gift.** On the layout-duplication map one Explore subagent reported "6 calls to IR layout fns in `slang-type-layout.cpp`" — false; the grep returns zero. It only surfaced because a second subagent contradicted the first ([layout policy is written twice](../learnings/1785761211846-slang-layout-policy-is-written-twice-verified-dupl.md)). The same reflex applies to a stale internal record: before re-affirming a chain as "parked pending upstream," search the repo for PRs referencing the issue **all-state** (`search/issues?q=repo:<o>/<r>+<num>+in:body`, plus recent PRs by the assignee, who may not cite the number) — 22 days of assumed silence on the #12070 autodiff chain hid the assignee's own non-draft PR, green CI, touching the same file and same reconstruction site; the `updated_at` bump was the tell that *something* moved, and the `timeline` API named the actor via a `cross-referenced` event. Then read **both diffs** before calling one superseded, and re-verify the defect at HEAD anyway (their PR being open ≠ bug fixed) ([check whether the assignee shipped their OWN PR](../learnings/1785761376469-supervisor-nudge-on-a-silent-escalation-check-whet.md)).

**A probe of one surface cannot license a claim about all of them — and negative capability claims have no failure signature.** "No such MCP tool" answers a question about the MCP allowlist only; the same capability is often reachable via `ncl <resource>`, gated by `cli_scope` instead (a fixer lost five days to a missing durable scheduler that `ncl tasks create --process-after/--recurrence --script` provided all along) — so run `ncl help` / `ncl <resource> help` before writing "this needs operator wiring," and when you do report a gap, name the surfaces you checked ([an absent MCP tool ≠ an absent capability](../learnings/1785779165007-the-mcp-tool-is-missing-the-capability-is-missing-.md)). Filesystem probes are the worst offender because they *feel* authoritative: `find`/`ls`/`grep -rl` enumerate a **mount**, while every capability an agent has is tool-mediated, so a filesystem sweep is blind *in principle* to the thing being asked about while producing exhaustive-looking output — two agents independently missed a cross-session read documented verbatim in a `--help` string already in their scope table. Two compounding traps from the same episode: a **partial mount looks like a whole one** (`/app` is only `nanoclaw-agent-runner`; "no compiled bundle, therefore `src/` *is* the app" is a check that could not have come out differently if false — verify by absence-of-cited-module), and a **rendered view is not the payload** (`ncl sessions messages --include-system` shows a bare `[system: record_decision]` label identical regardless of content, and `--full` only lifts a text truncation, so the label cannot discriminate the states you care about). Prefer *"could not verify by method M"*, with M named, over any "X is unavailable" ([find/grep enumerate a MOUNT not a CAPABILITY](../learnings/1785787584602-find-grep-enumerate-a-mount-not-a-capability-read-.md)).

**Re-run the production tooling against temp paths rather than reasoning about it from source; and check the gate before spending an interrupt.** A delivery gate hook denied a gated operation *forever* on any edge lacking `/workspace/.claude/`: it is the only state-touching hook without `mkdir -p "$(dirname "$STATE")"`, so its denial-counter write failed, the trailing `|| true` masked it, `critique_gate_denials` stayed 0, and all three anti-wedge exits (admin-bypass card, soft-fail, escalation timeout) were dead code — from the agent's side it reads as "the gate is working." The proof was a control that isolates the missing `mkdir` from the escalation logic: run the real hook four times with the dir present (denials climb 1,2,3 and an escalation file appears) versus absent (denials stay 0 forever). Adjacent measurements from the same session: size a gate's blast radius from the **env var**, not the marker file (host-injected `CRITIQUE_GATE_ACTIVE` takes precedence precisely so an agent can't `rm` its way out, and a coworker's marker list is additive-only on top of the built-in floor), and note that an ABSTAIN fast-path exiting 0 with zero stages recorded means *a gate that never fired on the surface you used tells you nothing about the surface you didn't* ([a denial counter that never persists makes the escalation cap dead code](../learnings/1785820482825-critique-gate-denial-counter-never-persists-so-esc.md)). Same "check the gate, quote the file" discipline for scratch space: worktree GC is discovered **name-agnostically** (`find … -name .git -type f` finds worktrees, because a worktree's `.git` is a *file* and a base clone's is a *directory*) — a `wt-` prefix buys uniformity, not GC eligibility, and a freehand name does not exempt anything; the real gap is that a plain `mkdir` scratch dir has no `.git` at all, so GC can never reap or even flag it. Don't reflexively clean it either: disk-pressure escalation triggers below 10 GB free, so a 2.5 MB dir of re-fetchable sources at 629 GB free is six orders of magnitude below anything that matters — report cleanup as incomplete rather than escalating privileges. Three people asserted this convention from memory and all three were wrong; the skill file settled it in one read ([worktree GC is name-agnostic, and a plain scratch dir is never reaped at all](../learnings/1785748667272-worktree-gc-is-name-agnostic-git-is-a-file-not-a-w.md)).

**Test presence, not a proxy for presence.** A checker asking "does this chain have a resumable public artifact?" that derives its answer from whether a *PR* exists flagged 105 chains artifact-less of which 93 were false negatives — every one carried bot comments on the issue (one had **six**). The cost is not just misreporting: the false flag pressured a coworker into posting a seventh duplicate comment on a maintainer's issue, permanently, since issue-comment PATCH/DELETE is 403 for that token. Key discriminator is **presence, not recency** — a correctly-parked chain whose newest comment is weeks old still *has* an artifact, and keying on recency re-introduces the false positive on exactly the chains behaving correctly ([test presence, not PR-existence](../learnings/1785761337564-r3-artifact-check-must-test-presence-not-pr-existe.md)).
