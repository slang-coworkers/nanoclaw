## TL;DR

- Treat each revision as a full fresh decision — prior turns are context, never evidence. When a webhook says one signal changed (draft→ready, rebase, synchronize), do NOT diff-patch your prior decision by editing out the named signal: re-fetch the head, re-pull the WHOLE diff, re-run every clause, because the author may have changed far more than the event announced.
- When pushes outrun run time, **settle-then-gate**: gate only the current live HEAD (`gh pr view --json headRefOid`); if HEAD moves mid-run, finish and record that head anyway. Re-pin at the start of each run and re-verify HEAD before recording. One authoritative verdict per head that survives long enough beats chasing every webhook.
- Re-gating by "did they fix the specific thing I flagged?" is the wrong frame. Re-enumerate the COMPLETE `check-runs` set at the new head and read every job the PR adds by name — a root-cause fix can fix config A, leave config B red for an unrelated reason, and regress config C. Guarding one instance of a failure class rarely covers the class; grep for sibling tests with the same trigger.
- Run a FRESH Devin per head; a bug classification can flip between heads even on byte-identical code (Devin's bug bucket is not deterministic across runs). Decide from the current head's own run every time.
- For any downstream/red CI status that touches a decision, READ THE FAILING JOB LOG (run-level `actions/runs/<id>/logs` zip; grep the failing job's file), quote the exact error. A "probably infra" you can't cite is a caveat, not a finding; a plausibility guess can be right yet unverified, and a peer's specific attribution can be confidently wrong.
- Classify a change by its FAILURE DIRECTION, not surface resemblance to "a gate." Narrowing an existing capability advertisement, or a new writer on an existing gate, is not a new-flag+new-gate — the dead-flag / trigger-present-control probe does not apply and demanding it would false-abstain.
- A new gate/flag/lint demands a **positive control**, never a green CI — a check that never fires also passes. Check out the head, inject the exact hazard the gate targets into an unrelated file, run the real entry point, confirm it errors, revert, confirm it passes.
- On a gate-tightening PR, read the leaf trust predicate: "what is the weakest thing this now trusts, and can a USER spell it?" A purity/side-effect proxy keyed on a user-spellable decoration re-opens the suppressed-diagnostic bug. A silently-suppressed correctness diagnostic is the highest-weight blast radius (no codegen comparison can see a missing error).
- A doc-🔴 mandates BLOCK at Step 2 before the challenger runs. When DECISION_REVIEW establishes the 🔴 is a false positive, the terminal is **ABSTAIN_POLICY / CRITIQUE_MUSTFIX** — never record BLOCK, never upgrade to WOULD_APPROVE (the procedure forbids upgrading a doc-🔴 by investigation). Cross-check every Devin citation's line numbers against the head individually — one report can mix fresh and stale findings.
- A must-fix on a **diff-context** line (no `+`/`-` prefix) is advisory, not an abstain trigger — it's outside both the change and the read-only approver's edit surface. Contest on the critique thread; don't reflexively route a clean WOULD_APPROVE to ABSTAIN.
- Codex comment-hygiene on the PR *author's* source is out-of-gate-scope: the gate checks YOUR derivation, not the PR's merge-worthiness. Unresolved ⇒ ABSTAIN_POLICY:CRITIQUE_MUSTFIX escalated, never a forced WOULD_APPROVE — a likely false-abstain is the honest signal the gate's scope needs tightening.
- A well-engineered prototype with an author-documented residual in the same failure direction, or self-declaring "not merge-ready / pending maintainer direction," is an OPEN_GAP hand-off — don't round it up to approve and don't BLOCK an author transparently asking a design question.
- Separate "does this lane gate the PR?" from "did the guarded work run and pass?": a `workflow_dispatch`-only lane is not a PR gate but a manual dispatch on the head can still exercise it; a lane red because the sanitizer found a real race is guarded-work-working, but red-on-arrival is its own OPEN_GAP.
- A reusable-workflow caller's `needs:`/`environment:` gates the ENTIRE invocation; changing a caller silently changes timing/inputs of EVERY inner job. A path allow-list answers "can this reach the secret?", never "which runs now produce an artifact?" — evaluate credential×egress gate pairs as boolean algebra per trigger.
- Dampen repeat re-dispatch on a churning size-capped PR: a deterministic `CLAUSE_FAIL:tier_eligible` short-circuits before the challenger runs, so a per-push session on the same over-cap sweep is wasted compute — re-dispatch only when the outcome could change.
- Human approval is calibration, never a clause input — an ABSTAIN on a head that gets reworked rather than shipped is the system working; don't score a later merge of a DIFFERENT head against an earlier revision's abstain.

## Every revision is a fresh decision — don't diff-patch, settle-then-gate

The skill's "re-run the FULL procedure per revision; prior turns are context, never evidence" is load-bearing precisely where the temptation to carry forward is strongest. A draft→ready transition invites "cross off the draft signal, keep the others, re-decide" — but between draft and ready an author had rebased and reworked a PR from 7 files to 3, so all three prior signals were moot against the *new* diff ([a draft PR can be REWORKED before ready — re-gate the whole diff](../learnings/1786636805279-approver-calibration-a-draft-pr-can-be-reworked-be.md)). Do not diff-patch by editing out the named signal; re-fetch the head and re-run every clause. When pushes outrun run time (a 6-revision rapid-push chain where each run took ~1h), converge on **settle-then-gate**: gate only the current live HEAD, and if HEAD moves mid-run finish and record that head anyway, producing exactly one authoritative verdict on the head that actually merges ([settle-then-gate resolved a 6-revision treadmill](../learnings/1786653190234-approver-challenger-confirmed-slang-rhi-831-lavapi.md)). Dampen the opposite waste too: on a churning size-capped PR where the approver already recorded a deterministic `CLAUSE_FAIL:tier_eligible` (short-circuits before the challenger/Devin/critique run), do not wake a fresh session per intermediate head — re-dispatch only when the outcome could actually change (diff drops under the cap, a different clause fails, a human requests review) ([dampen repeat re-dispatch on a churning size-capped PR](../learnings/1786519685407-dampen-repeat-approver-re-dispatch-on-a-churning-s.md)). And human approval is calibration, never a clause input — an ABSTAIN on a head that is reworked rather than shipped is the system working; never score a later merge of a *different* head against an earlier abstain row.

Re-gating a fix means re-enumerating, not cross-checking the prior failure. "Did they fix what I flagged? yes → approve" is the wrong frame: on a CI-coverage PR, re-enumerate the complete `check-runs` set at the new head and read every job the PR adds by name, because a root-cause fix can fix config A while leaving config B red for an unrelated reason AND regressing config C — one PR went from 2/4 red to 3/4 red even though its fix was genuine ([a fix that resolves the specific prior failure can still be OPEN_GAP](../learnings/1786482471984-approver-challenger-miss-re-gate-a-fix-that-resolv.md)). Guarding one instance of a failure class rarely covers the class (grep for sibling tests with the same trigger). Run a fresh Devin per head: byte-identical code drew opposite bug classifications on two runs because Devin's bug bucket is not deterministic, so decide from the current head's own run ([re-gate on the settled head with a FRESH Devin run; read the log](../learnings/1786506953129-approver-challenger-re-gate-on-the-settled-head-wi.md)). For any downstream red CI that touches the decision, fetch the run-level logs zip and quote the exact failing step — a plausibility guess ("no mechanism for a render change to break SlangPy ⇒ infra") can be right yet unverified, and a peer's specific attribution (an `optix-dev` submodule 503) can be confidently wrong when the truth is a different `optix_8_0` binary-SDK download 503. A "probably infra" you can't cite is a caveat, not a finding.

## Classify by failure direction; a green CI is not a positive control

The recurring calibration error is treating any diff that touches a conditional as "a gate" and demanding a trigger-present control. Classify by **failure direction**: narrowing an existing capability advertisement (wrapping an already-present `addCapability` in a stricter `if`) has no new bool, no scan-order hazard, and its worst case is under-advertising bounded by a trusted primitive — it is not a new-flag+new-gate, and demanding a dead-flag probe would false-abstain ([narrowing an existing capability advertisement is not a new-flag+new-gate](../learnings/1786608219702-approver-confirmed-narrowing-an-existing-capabilit.md)). Conversely, when a change genuinely adds a gate/flag/lint, a green CI is not evidence it works — a check that never fires also passes. The positive-control drill (check out the head, inject the exact hazard into an unrelated file, run the real entry point, confirm exit 1, revert, confirm exit 0) is what distinguishes a live gate from a dead one, applied to a lint gate exactly as to a compiler pass ([docs-tooling PR that adds a self-guarding lint gate + ships its own positive control → WOULD_APPROVE](../learnings/1786611682135-approver-human-agreement-docs-tooling-pr-that-adds.md)). On a gate-*tightening* PR, even after the positive control passes, read the leaf trust predicate: "what is the weakest thing this now trusts, and can a USER spell it?" — a purity proxy keyed on a user-spellable `__target_intrinsic` re-opens the suppressed-diagnostic bug in the pathological direction, and a silently-suppressed correctness diagnostic is the highest-weight blast radius because no codegen comparison can see a missing error ([gate-tightening PR with an author-documented residual → OPEN_GAP](../learnings/1786606593859-approver-challenger-gate-tightening-pr-with-an-aut.md)). Such a PR — a sound conservative step that documents and tracks its residual and self-declares "pending maintainer direction" — is an OPEN_GAP hand-off, neither rounded up to approve nor BLOCKed.

Two more classification subtleties. A "callback fires per diagnostic" contract is only as good as the sink's dispatch: Slang's callback fires only from the *rich* path, gated by `AlwaysGenerateRichDiagnostics` which is not default — so a permanent public-API doc overstating delivery is an OPEN_GAP, and a unit test firing only typed sema errors masks the gap ([Slang diagnostic callbacks only fire on the rich path](../learnings/1786610745798-approver-challenger-slang-diagnostic-callbacks-onl.md)). And a path allow-list on an artifact upload answers "can this glob reach the secret?" — never "which runs now produce an artifact?": the real question is what the step's GATE changed, evaluated as boolean algebra against every credential-materializing step's gate on each trigger (remember `null == ''` is TRUE in Actions), because a safety invariant can live in the *relationship between two gates* that the PR never touches ([a path allow-list answers the wrong question — gate-algebra complement](../learnings/1786458679258-approver-challenger-miss-a-path-allow-list-answers.md)). When you clear a step, name the dimensions it has and say which one you checked — a check whose construction can only return "clean" is worth zero bits.

## Scope of the gate, doc-🔴 routing, and reusable-workflow blast radius

Know what the critique gate is chartered to check: YOUR derivation (clauses from data, verdict parse, tier, challenger), not the PR author's source. A must-fix on a **diff-context** line (no `+`/`-` prefix) targets code the author never touched and the read-only approver can't edit — it is at most advisory; contest on the critique thread with citations rather than routing a clean WOULD_APPROVE to ABSTAIN ([a gate must-fix on a diff-context line is advisory](../learnings/1786637412115-approver-critique-mustfix-a-gate-must-fix-on-a-dif.md)). But when codex's *only* surviving must-fixes are about the PR author's comment hygiene and you've fixed all derivation items, that is out-of-gate-scope and structurally unactionable (you never edit the PR) — the terminal is ABSTAIN_POLICY:CRITIQUE_MUSTFIX escalated, never a forced WOULD_APPROVE; the likely false-abstain is the honest signal the gate's scope needs tightening ([codex comment-hygiene on the author's source is out-of-gate-scope](../learnings/1786829275508-approver-critique-mustfix-codex-comment-hygiene-on.md)). Doc-🔴 routing is deterministic: a 🔴 mandates BLOCK at Step 2 before the challenger runs, so when DECISION_REVIEW establishes the 🔴 is a false positive (byte-identical code across a Devin bug-classification flip; unreachable-by-construction) the terminal is ABSTAIN_POLICY:CRITIQUE_MUSTFIX — do not record BLOCK and do not upgrade to WOULD_APPROVE — and cross-check every Devin citation's line numbers individually because one report can mix fresh and stale findings ([a Devin false-positive 🔴 routes via ABSTAIN(CRITIQUE_MUSTFIX), not BLOCK](../learnings/1787089849470-approver-challenger-miss-averted-a-devin-false-pos.md)).

Two workflow-topology blast-radius rules. Separate "does this lane gate the PR?" from "did the guarded work run and pass?": a `workflow_dispatch`-only lane is not a PR gate, but a manual dispatch on the head can still exercise it — so a tsan lane that goes red by *detecting a genuine race* has its guarded work working (trigger-present control satisfied), yet lands red-on-arrival, which is its own OPEN_GAP-class human call ([a workflow_dispatch-only lane can be exercised AND red-on-arrival](../learnings/1787000610246-approver-challenger-miss-a-workflow-dispatch-only-.md)). And a reusable-workflow *caller* job's `needs:`/`environment:` gates the ENTIRE invocation as one unit, so a PR that reroutes one inner job's artifact behind a new gate silently changes the timing/inputs of every OTHER inner job — the diff and description scope-blind you to the siblings, so open the called workflow and enumerate ALL its jobs ([rewiring a reusable-workflow caller affects EVERY inner job](../learnings/1787143613008-approver-challenger-miss-rewiring-a-reusable-workf.md)). Finally, this whole discipline has a policy-scope prerequisite: a carry-forward gate names an INVARIANT, and evaluating it means testing its PREMISE (was the failure still unreachable, or now prevented by any mechanism?), not enforcing the specific remedy you sketched — enforcing the remedy over the invariant produces false OPEN_GAPs on correct designs and reads as rigour ([evaluating a carry-forward gate means testing its PREMISE, not enforcing your remedy](../learnings/1786368918553-approver-clause-gap-evaluating-a-carry-forward-gat.md)). This also frames the production-review-tier calibration: the production `Claude PR Review` is `paths:`-gated to compiler dirs, so an `extras/**`-only PR legitimately gets zero review run and the fallback tier is correct — distinguish *never-triggered* (list the workflow's runs for the head; zero ⇒ path-filtered) from *pending* (a run exists in_progress ⇒ wait) ([production Claude PR Review is paths-gated to compiler dirs](../learnings/1786963629074-approver-challenger-production-claude-pr-review-is.md)).
