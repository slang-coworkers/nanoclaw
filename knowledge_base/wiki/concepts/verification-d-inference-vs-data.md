## TL;DR

- **Verifying a claim's data is not verifying its inference.** A claim arriving as *(measurement, therefore conclusion)* is two deliverables; confirming the measurement creates a strong feeling of having validated the whole thing. Ask explicitly: *does the conclusion follow, and what else could produce this same data?*
- **A check whose output is identical across sanctioned and unsanctioned causes is not evidence.** If a command returns the same result whether or not the cause was authorized, running it tells you nothing — you need the authorization record, not a better query.
- **A remedy claim needs its own instrument.** Measuring the fault tells you nothing about what fixes it. "The box passes other jobs" ⇏ "a restart is a no-op." Scope-of-fault, scope-of-routing, scope-of-remedy are three independent facts.
- **A field that yields the same value in opposite cases is a prompt to measure, not a finding.** `mergeStateStatus: BEHIND` says only "the base moved" — the overlap burden is entirely yours.
- **A description broad enough to cover two symptoms is a hypothesis of common cause, not a demonstration of one.** Coverage is what an abstract description always has; a claim that survives the refutation of every mechanism under it is unfalsifiable, not robust.
- **Vary one axis at a time** — a fix that works is not evidence for the mechanism you attribute it to when your winning query changed two things at once.
- **Authorship ≠ ownership.** Who wrote round N is read from the artifact; who receives round N+1 is decided by the routing key. A correct attribution with a wrong ownership inference looks exactly like careful work.
- **A surviving guard is ambiguous evidence** — unfixed bug vs un-reverted cleanup. Verify the guard's stated removal condition at the source.
- **A plausible mechanism can override a correct instinct that has no story attached** — be most suspicious of a surprising claim that arrives with a good reason.

## Verifying the data is not verifying the inference

On a PR review, a peer argued a CI failure was unrelated to the diff on this leg: "the crash is isolated among nine passing near-identical siblings — a codegen regression would not spare nine and kill one." Two agents independently "confirmed" it — and both checked only the **counts** (one even repaired a broken sibling-isolation grep, re-measured with a control, and verified 7 passed / 1 failed: sound measurement). Then each passed the **conclusion** through as though checked, and it returned to the originator as independent agreement. **The inference doesn't hold**: an input-specific defect in shared code hits one variant and spares its siblings, because different shader inputs take different paths through the same compiler code. Sibling isolation *localizes* a failure; it does not *exonerate* a shared code path [Verifying a claim's data is not verifying its inference — how three agents manufactured consensus on a non-sequitur](wiki/learnings/1785968479015-verifying-a-claim-s-data-is-not-verifying-its-infe.md).

The rule: when a claim arrives as *(measurement, therefore conclusion)*, they are two deliverables. Confirming the measurement — especially after repairing your own instrument to do it — feels like validating the whole claim. Ask *what else could produce this same data?* **Large N makes a non-sequitur feel measured**: nine greens read as nine confirmations when they are one weak inference repeated; the apparent evidential weight scaled with the sibling count while the logical support stayed at zero. **Practical guard:** when you confirm someone's claim, say *which part* you confirmed ("counts verified: 7 passed, 1 failed; I have not evaluated whether that implies non-reachability") — one extra clause that stops the laundering. And keep the load-bearing legs separated by strength, so a reviewer knocking out a weak corroborating leg doesn't take the conclusion with it.

## A check identical across authorized and unauthorized causes is not evidence

If a command returns the same result whether the cause was sanctioned or not, running it cannot tell you which happened — you need the authorization record. `git merge-base --is-ancestor <old-head> <new-head> → false` was read as "the force-push destroyed the old head," but the push was an **authorized commit re-author** (fixing a CLA identity), and re-authoring rewrites every SHA by construction — so `false` is the *expected signature of the sanctioned operation*. The exit code is byte-identical for "rewritten exactly as approved" and "work lost"; root cause was a lost authorization record, not a bad query [A check whose output is identical across sanctioned and unsanctioned causes is not evidence](wiki/learnings/1785969553816-a-check-whose-output-is-identical-across-sanctione.md) [Correction: re-authoring commits changes every SHA — `--is-ancestor false` is not evidence of a discarded head](wiki/learnings/1785968989554-correction-re-authoring-commits-changes-every-sha-.md).

The discriminator that *does* work: compare the two heads' commit subjects and per-commit file stats (`git log --format='%h %an %s' main..OLD` vs `..NEW`, plus `git show --stat`). Same subjects + same touched files + different author field = re-authored, history preserved. Any history-rewriting operation (rebase, amend, filter-branch, author fix, squash) produces the same `--is-ancestor` false positive. Adjacent identical-output traps on that chain:
- `git log -S` on a **shallow clone** returns a confident single wrong answer, shape-identical to the correct answer on a full clone — check `git rev-parse --is-shallow-repository` first.
- `--is-ancestor` also returns `false` when an object simply **isn't in your clone** — positive-control with `git cat-file -t <sha>`.
- Grepping a public artifact for your own prior claim finds it even when struck through, because a correction usually *quotes* what it refutes — read the newest comment first, grep `REFUTED|CORRECTED|Superseded|~~`, *then* your text.

The structural lesson: durable authorizations belong in the artifact (a PR comment, an issue note), never solely in a session — a container outage deleted the record that made a push legitimate, and a context-poor agent invented a culprit from the gap. A learning about your own conduct written after a context loss must be checked against the transcript before filing, or a false incident report becomes precedent.

## A remedy claim needs its own instrument

Measuring the fault tells you nothing about what fixes it. A self-hosted runner failed `spirv-val [0/866]` while all 866 shaders compiled; the issue carried a section "Why a reboot won't help" asserting a restart was a no-op — and **the maintainer's fix was restarting the runner service** (a long-lived process had cached a `PATH` pointing at a since-deleted VulkanSDK directory). The two controls run (same-job/other-runners → rules out code; other-job/same-host → rules out machine) genuinely could not see the real axis, *stale inherited environment*, which is uniform across the host and manifests only where a dependency was removed — so a passing sibling job was fully consistent with the fault [A remedy claim needs its own instrument — box health says nothing about a service's cached environment](wiki/learnings/1785966230683-a-remedy-claim-needs-its-own-instrument-box-health.md).

This was the *second* remedy-from-defect error on one chain: earlier, "a rerun will land on the same bad box ⇒ reruns are futile" was refuted by one unread line — `runs-on:` is a pool. **Scope-of-fault, scope-of-routing, and scope-of-remedy are three independent facts, each needing its own evidence.** Two further findings from that chain:
- **Label every claim by its evidence, not your confidence** — the label determines the damage when you are wrong. A "hypothesis, reason it isn't proven stated" (VS 17→18, wrong) cost zero because it routed to someone with box access; a flat "this is explicitly *not* a reboot request" (wrong) shaped the entire ask toward depool/reprovision.
- **Observability bias in hypothesis selection:** two toolchain changes landed in the onset window; the team latched onto the one whose env vars the logs happened to *print*. When an onset window contains one visible change, ask what would be *invisible* to your instruments before treating the visible one as leading. And **when the cause is unknown, ask for investigation or the cheapest reversible action, never a named heavy remedy.**

## A status field that yields the same value in opposite cases is a prompt to measure

GitHub's `mergeStateStatus: BEHIND` (and `behind_by > 0`) says only *the base moved* — it carries no information about whether the base's new commits interact with your change, so the same cell yields opposite correct verdicts. On two PRs the same night: #12401 (1 upstream commit, zero file overlap → don't rebase) and #11820 (282 upstream commits, 36 touching the PR's files, one introducing a warning-level *sentinel* that didn't exist at the merge-base and lands squarely in the causal cone of the PR's `diag=CHECK` tests → rebase mandatory; the old green did not describe the code under review). **Treat a status-field-derived recommendation as a prompt to measure: ask what the field would say in the opposite case — if the answer is "the same thing," it is not evidence** [A rebase nudge keyed on mergeStateStatus=BEHIND is not evidence — the field cannot distinguish opposite answers](wiki/learnings/1786065871286-a-rebase-nudge-keyed-on-mergestatestatus-behind-is.md).

Measure overlap two ways: `git log --oneline <merge_base>..origin/master -- <changed files>` (direct), and — because filenames miss it — whether the base touches anything your **tests observe as output** (emitters, preludes, goldens, `.expected`, capability tables, diagnostic text). A FileCheck / `diag=CHECK` / COMPARE test is a contract with a producer not in your diff, so its causal cone is far wider than its filename. `git merge-tree --write-tree` detects textual conflicts but is *blind to semantic collisions* like the sentinel — a clean auto-merge is not a valid green. The same false-positive family covers deriving a chain's PR from an assumed branch name (`fix/issue-N` when the real branch was `dev/fixer/...`, so absence-of-lookup read as absence-of-PR), "small worktree ⇒ stalled" for a config-only change, and a CI check count read without pinning the SHA + timestamp (the same static head read 29/29 then 30/30 as automation accumulated a check) [Verification-signal false positives: derived-branch PR lookup, worktree size, and unstable CI check counts](wiki/learnings/1786065512759-verification-signal-false-positives-derived-branch.md).

## A shared description is a hypothesis of common cause, not a demonstration

"A freshly built Slang binary cannot resolve a DLL or exported symbol on this box" was published as the artifact that *worked*, covering both `spirv-val 0/866` and a nightly `failed to load slang.dll`. But the two symptoms had two different causes (a stale `PATH` from a deleted SDK vs a nine-month-old `slang.dll → slang-compiler.dll` rename), and the timing check refutes common cause outright — a nine-month-old rename cannot produce a sharp onset. **Two symptoms sharing a plausible description is a HYPOTHESIS about common cause, not a demonstration of one**; coverage is exactly what a sufficiently abstract description always has. And the epistemic inversion: presenting "the description survived even though every mechanism guess under it was wrong" as a *virtue* is backwards — a claim that survives the refutation of every mechanism beneath it is **unfalsifiable at the level it was stated**, the property to be suspicious of. The test for common cause is not "does one description fit both" but whether the limbs are coupled in time and mechanism [CORRECTION — two symptoms sharing a description is a hypothesis, not a unified defect](wiki/learnings/1785966354315-correction-two-symptoms-sharing-a-description-is-a.md).

The related distinction between *verified* and *unfalsified*: a "cost is irreplaceable" leg was measurable and measured (4 findings each in exactly 1 file — true), while a "still cheaply fixable" leg is a counterfactual about future effort that no probe can falsify — it holds *by construction of the situation*, unfalsified rather than verified. **When a mechanism survives, ask whether it survived a test or merely evaded one** — "still standing" is not strength when nothing in the toolkit could have knocked it down [Verified vs unfalsified are different states - and a position FAIL on one phrasing is not a FAIL on the rule](wiki/learnings/1785965205844-verified-vs-unfalsified-are-different-states-and-a.md).

## Vary one axis at a time; find the branch, not just the symptom

A dedup query's winning form differed from its failing ones in *two* ways at once (new vocabulary *and* no `in:body`), and the author credited the variable he had been thinking about rather than isolating either. **A fix that works is not evidence for the mechanism you attribute it to** — vary one axis at a time, or you publish the wrong cause with a genuinely working remedy attached. A wrong mechanism riding a correct conclusion draws no pushback from outcomes, because nothing downstream misbehaves.

"Why did this work over there?" has two very different answers — *it satisfied the check* or *it never ran the check* — and only the second tells you the blast radius. Text targets weren't *passing* the `-o /dev/null` path-type validation; they **bypassed** it (the text write path never consults `getPathType` at all), which is why every test in the related PR used a text target and *could never have caught the bug* — the suite's silence was structural, not evidence of correctness. When some inputs escape a failure, find the branch and confirm whether the passing side executes the same validation [CORRECTION to the `-o /dev/null` learning — the text path BYPASSES the check, it doesn't pass it](wiki/learnings/1785968207000-correction-to-the-o-dev-null-learning-the-text-pat.md).

## Authorship is not ownership; a surviving guard is ambiguous

**Who wrote round N** is measured from the artifact (disclaimer wording, commit author, transcript role, sentinel/worktree presence); **who receives round N+1** is decided by the routing table. Correctly determining that two prior bot comments were written by a *slangpy* tier (the "automated SlangPy coworker" disclaimer) was sound — but using that to conclude the chain needed re-keying to slangpy was wrong: webhook routing is *by repo*, so `shader-slang/slang` maps to the current tier regardless of who drove earlier rounds. A correct attribution + wrong ownership inference looks exactly like careful work and survives self-review, because the cited evidence is real. **Before proposing a re-key/re-route/handoff, ask what the router keys on — not who did this last time.** (Policy corollary from the same exchange: retracting your own stale blocker on someone else's PR is correct and low-cost — a stale blocker costs the maintainer more than a wrong comment costs you.) [Authorship ≠ ownership: a disclaimer/path identifies who wrote a past round, never who receives the next one](wiki/learnings/1786067911253-authorship-ownership-a-disclaimer-path-identifies-.md)

**A surviving guard is ambiguous evidence** — it proves someone *once* had the problem but does not distinguish (1) the bug is still live (guard is load-bearing) from (2) the bug was fixed upstream and nobody deleted the guard (stale debris). Case 2 was true on slangpy#274: the upstream fix had landed and shipped in the pinned Slang, but the PR referenced the issue by bare URL with no `Fixes`/`Closes` keyword, so it never auto-linked and never resurfaced. What disambiguates is *not* readable from the guard — check its stated removal condition independently (the cited issue's state, the commit that landed, containment in the pinned version). And when a guard's comment describes its own scope, read the *predicate* — the comment drifts ("filter out all bool tests" while the predicate excluded exactly one of seven) [A surviving guard is ambiguous evidence: unfixed bug vs. un-reverted cleanup](wiki/learnings/1785967745181-a-surviving-guard-is-ambiguous-evidence-unfixed-bu.md).

## A plausible mechanism can override a correct instinct

"The symbol is exported" never implies "this code path is reachable" — two reviewers both confirmed a function was a member of an exported struct and neither checked *which pointer it was initialized with*, then the wrong reachability claim went into a public issue. The meta-rule: **a plausible mechanism can override a correct instinct that has no story attached.** One party's instinct said "internal-only" (right), the other supplied a persuasive mechanism (wrong), and the instinct lost. When someone hands you a mechanism that contradicts your instinct, treat it as a hypothesis to test — be most suspicious of a surprising claim that arrives *with* a good reason, because the reason is what switches off the implausibility check that would otherwise have caught it.

The `--is-ancestor`/re-author case also yields two operational git rules: **read a remote head, never retype it** (`--force-with-lease=<ref>:<sha>` with a *remembered* SHA fails closed on your own typo; get the value from `git ls-remote`), and diff a candidate against the **reviewed head**, not `main` (9 files vs 50 — the delta that mattered had silently dropped two tests).

## Falsifying one contract is not "no remedy exists"

Measuring that bare text outside `<message>` blocks *delivers* on an a2a edge (four bare-text turns arrived as `kind=chat` rows, re-framed as first-class messages with ids and senders) refuted one *contract* — the harness-injected "text outside `<message>` is scratchpad" — but the author drew the wider conclusion "no non-delivering form exists" and stopped. Running the same grep on the *project* instruction files found a different, untested contract: scratchpad is the `<internal>` tag, marked "not delivered." **A disproof closed the search for a remedy** — "bare text is delivered" and "no non-delivering form exists" are different claims, the second spanning the whole mechanism space and needing its own enumeration. Same family: rigour about one instrument's blindness substituting for looking for other instruments. And a correctly-scoped caveat ("I have not tested my own edge") marked an untested boundary and then made it feel handled — **a scope caveat should carry the command that would close it**, so the boundary reads as an open action [CORRECTION to the scratchpad-delivers finding: two contracts disagree — <internal> may be the non-delivering form, and the disproof closed the search for it](wiki/learnings/1785965570328-correction-to-the-scratchpad-delivers-finding-two-.md).
