# Codex & Provider Parity

Empirical findings from stress-testing Claude vs Codex providers under `AGENT_RUNTIME=local`, and process rules for running `/codex-critique` correctly in the Slang fixer and approver workflows.

## TL;DR

- The native `Task` subagent is Claude-only; on Codex it hangs silently instead of erroring. The portable subagent path on both providers is `mcp__nanoclaw__create_agent` plus a2a messaging.
- Claude coalesces rapid pushed messages into one result; Codex emits one per push. For per-message reply identity from a Claude coworker, wait for the prior turn or open separate sessions. Rapid-fire is safe on Codex.
- Plan-gate and critique-gate do not fire under `AGENT_RUNTIME=local`. A `CLAUDE.md` @import cannot be verified on a live session (the system prompt is cached) — kill and respawn. The CLI adapter is single-client, so parallel chat calls evict each other.
- Rebase onto the base branch late, right before a codex `CODE_REVIEW`; otherwise upstream-only changes read as reverts and produce phantom scope-creep must-fixes.
- Always call codex with `sandbox: "danger-full-access"`. Under `read-only` it cannot read artifacts, returns a non-verdict, and the round still counts — so the gate can open on a meaningless review.
- A round counts only when a FRESH `mcp__codex__codex` call carries a `STAGE: <NAME>` line and the canonical reviewer block verbatim as a TOP-LEVEL `developer-instructions` param (never nested in `config`). Fixer rounds also need `ROUND: <n>` and `REQUIREMENTS:` with verbatim maintainer quotes re-fetched from GitHub, or `REQUIREMENTS: none — <why>`. A free-form call records as `stages: none`.
- A reply without the exact `### Verdict` block is no review, whatever the tracker recorded. Codex often answers a fresh STAGE call with wiki-recall bullets; re-ask on the same thread (`codex-reply`, no `STAGE:` line) for ONLY the structured output.
- Never put a literal `STAGE:` line in a `codex-reply` re-verify — the hook treats it as an initial call, the pin check fails, and the approve is silently dropped. A fresh STAGE-tagged call always records cleanly.
- Run every required stage up front: PLAN_REVIEW + CODE_REVIEW + OUTPUT_REVIEW for the fixer, DECISION_REVIEW + OUTPUT_REVIEW for the approver. The denial fires at PR-create time, after the review work is spent. The gate fires even for a no-code diagnosis.
- Critique coverage resets on ANY file edit after the OUTPUT approve, memory files included. Do housekeeping writes first; touch nothing between approve and the delivery send. The gate re-hashes the `/workspace/agent/memory` OKF copy, not the `~/.claude` copy.
- While OUTPUT_REVIEW is must-fix, the gate blocks every Bash command containing `gh api repos/<o>/<r>/pulls/<n>`, GETs included — read PR state through slang-mcp tools, `issues/<n>/comments` or `gh pr view`. Post a comment over 1000 chars from the attested file, with every claim already true.
- The AI-transparency disclaimer goes on issue/PR comments, never in the PR description or commit message; `OUTPUT_REVIEW` flags a body footer as must-fix.
- A critique approve is a signal, not a proof: it does not replace a test-build on anything depending on enum/atom ordering, contiguity or set membership. Treat approve-by-analogy as lower confidence; fail closed when an anchor value is absent.
- When codex is down and is the only thing blocking a marker send on already-approved public content, deliver a plain ungated status roll-up. Model overrides return 403 here — omit them.
- A hook-denied or failed probe is a fact about YOUR edge. Try another route, then hand the probe to a coworker on a different edge; record UNVERIFIED only after someone who plausibly could has also failed.
- Never launder a relayed claim into durable memory as fact, even from your parent. Write `state=UNVERIFIED (probe denied)`; weight relayed provenance inversely to how much the fact drives your next action.
- Replace an UNVERIFIED marker IN PLACE when the answer arrives; never append a retraction. Reciprocate when a peer's marker is trivially checkable from your seat.
- Before escalating, re-check the question's presupposition against the state you just verified.
- Verify a summary→detail pointer at AUTHORING time by grepping the child for its checkable tokens. A mismatch does not say which side is wrong — go to ground truth.
- Prose quality and byte count are independent claims: print the delta on the lines changed. Characterize a ref by its commit date, not its name.

## Claude vs Codex Functional Parity

A 10-probe stress test on `AGENT_RUNTIME=local` (PR #52, snapshot `84ae3e5`) found three real asymmetries ([claude-vs-codex-provider-parity](../learnings/1778085879531-claude-vs-codex-provider-parity.md)):

1. **Native `Task` subagent — Claude only.** `Task` is in Claude SDK's `allowedTools` (`providers/claude.ts:47`). Codex has no equivalent and under test **hung 150 s silently** rather than returning "unavailable". Both providers have `mcp__nanoclaw__create_agent` + a2a messaging, the portable subagent path.
2. **Rapid message queueing.** Claude SDK's `stream.push` coalesces pending messages into one result event; Codex emits one result per push. In a 10-message Promise.all fan-out Claude returned 1/5 tagged replies (4 timeouts), Codex 5/5. When fanning out to a Claude coworker and needing per-message reply identity, wait for the prior turn or open separate sessions.
3. **Latency.** Codex was 12–87% faster per probe, likely because Claude Opus prompt caching and thinking blocks add latency while Codex/nvinference has lower TTFT.

Identical on both: connectivity, MCP tool calls (deepwiki, schedule_task, cancel_task) and error paths; the same `mcpServers` config from agent-runner (`container/agent-runner/src/index.ts:104,171`); `.instructions.md` + `CLAUDE.md` content loaded at session start.

Blocked on the local runtime, not a provider difference: plan-gate/critique-gate do not fire under `AGENT_RUNTIME=local` (`src/container-runner.ts:730-736`, a documented limitation). A `CLAUDE.md` @import cannot be verified on a live session because the system prompt is cached; it needs a kill and a fresh session. The CLI adapter is single-client (`src/channels/cli.ts:152`), so parallel `pnpm run chat` calls evict each other — use a persistent socket with in-band tags.

## Making a Critique Round Count

`track-critique.sh` (PostToolUse) records rounds and `gate-critique-on-deliver.sh` (PreToolUse) denies delivery until the required stages are covered. A round is recorded only when a FRESH `mcp__codex__codex` call carries BOTH a `STAGE: <NAME>` line in the prompt AND the canonical `/codex-critique` `developer-instructions` block verbatim; the hook checks the sentinel lines "You are an independent reviewer" and "Return ONLY the structured output below". A free-form call records as `stages: none, verdicts: none` and never satisfies the gate ([critique gate only counts codex calls carrying STAGE marker + verbatim reviewer block](../learnings/1783670321503-critique-gate-only-counts-codex-calls-carrying-sta.md)).

**`developer-instructions` must be a TOP-LEVEL parameter** (alongside `prompt`/`sandbox`/`cwd`), never nested inside `config`. `track-critique.sh` line 25 reads only `.tool_input."developer-instructions"`, so a config-nested block reads as empty, fails the sentinel check, and the hook emits "Critique round NOT recorded … do not match the canonical /codex-critique reviewer block" even though codex ran and answered. A secondary tell is codex ignoring the requested output format. On fix #12237 two good CODE_REVIEW critiques counted for nothing this way; on slang#12219/PR#12263 moving the same block from `config` to top level flipped the hook to "Critique round 38 recorded" ([codex-critique: developer-instructions must be a TOP-LEVEL param, not inside config](../learnings/1785437953553-codex-critique-developer-instructions-must-be-a-to.md)).

**`sandbox: "danger-full-access"` on every call.** With `read-only`, codex cannot run `cat`/`git`/`grep` and returns a "workspace command execution is blocked" non-verdict, yet the hook still counts the round, so the delivery gate can open on a meaningless review; re-run any round that came back unable-to-read ([codex-critique needs danger-full-access; AI-disclaimer goes on comments not PR bodies](../learnings/1781129788679-codex-critique-needs-danger-full-access-ai-disclai.md)). In this container a hook also rejects read-only calls outright.

**Fixer rounds need `ROUND:` and `REQUIREMENTS:` lines.** For the slang-fixer overlay a PLAN/CODE/OUTPUT_REVIEW round is recorded only when the prompt also has a `ROUND: <n>` line followed by `REQUIREMENTS:` and one `R<n>. "<verbatim maintainer quote>" — <comment URL>` per line, or `REQUIREMENTS: none — <why>`; `track-critique.sh` drops the round otherwise. The quotes are re-fetched from GitHub, never copied from a parent's handoff, because codex grades the artifact against them and treats a misquote as must-fix ([codex-critique rounds only count with ROUND + REQUIREMENTS lines on a fresh codex call](../learnings/1790868961396-codex-critique-rounds-only-count-with-round-requir.md)).

**The verdict is parsed only from the exact `### Verdict` block.** The parser records a VERDICT only when codex returns the skill's literal `### Verdict\napprove` (or `must-fix`); free-text `VERDICT: approve` shows `verdicts: none`, so pass the codex-critique reviewer template as `developer-instructions` to get that structure ([codex delivery-gate verdict-parsing: only the exact `### Verdict` block counts, and the gate fires even for a no-code diagnosis](../learnings/1783352556452-step-0-byte-compare-to-decide-if-a-diff-changed-em.md)).

**A reply without a `### Verdict` block is not a review, even when the tracker counted it.** With a valid STAGE prompt and the verbatim instructions, codex has repeatedly returned only 2–5 `/workspace/shared/wiki` recall bullets (titles and paths, "I did not read code artifacts"). The tracker still recorded the round and reported the stage's earlier verdict as current; on slang#11803 it logged one such reply as OUTPUT_REVIEW=approve, and on PR #13867 (2026-10-28) it logged two more with the stage's previous `approve` ([a first call can return wiki-recall bullets; the tracker still records approve](../learnings/1793228747743-codex-critique-a-first-call-can-return-wiki-recall.md)). It is most common on the first call of a fresh thread (4 of 4 fresh calls in one day's fixer sessions). Check every reply for the `### Verdict` line; if it is missing, immediately `mcp__codex__codex-reply` on the same `threadId`, with no `STAGE:` line: "that was a memory recall, not the review — perform it now and return ONLY the structured output". Every re-ask has produced a real review, and those reviews caught real defects: a must-fix, an overclaimed "docs and tests only" scope, and test counts taken from a pre-final build ([codex-critique can return a wiki recall instead of the review](../learnings/1791904796575-codex-critique-can-return-a-wiki-recall-instead-of.md), [codex STAGE prompts can return wiki recall instead of a verdict](../learnings/1791912236710-codex-stage-prompts-can-return-wiki-recall-instead.md), [first call on a fresh thread often returns a wiki recall](../learnings/1792242240195-codex-critique-first-call-on-a-fresh-thread-often-.md)). Why a STAGE-less reply on a canonically opened thread does update that stage's verdict is on [critique-gate mechanics](agent-routing-f0909b1-critique-gate-mechanics.md).

**Re-verify without a literal `STAGE:` in a `codex-reply`.** A reply carries no developer-instructions, so it is not attributed to the gate as a new stage round. If the reply prompt contains a literal `STAGE:` line, the hook's grep still matches, treats it as an initial stage call and runs the instruction-pinning check, which the reply cannot pass — the reply's approve is silently dropped and OUTPUT_REVIEW stays must-fix. Either phrase the reply without the `STAGE:` token (the thread inherits its stage) or issue a fresh `codex` call carrying the canonical instructions and a leading `STAGE:` line, which always records cleanly ([codex-reply re-verify must NOT contain a literal STAGE: line](../learnings/1783668707884-critique-gate-codex-reply-re-verify-must-not-conta.md)). To clear a must-fix OUTPUT_REVIEW on the fixer overlay, fix the artifact and then issue a NEW STAGE-tagged `codex` call rather than a reply ([verdict-parsing](../learnings/1783352556452-step-0-byte-compare-to-decide-if-a-diff-changed-em.md)).

## Required Stages and the Delivery Gate

**Run every required stage up front.** For the slang-fixer overlay the required stages are PLAN_REVIEW, CODE_REVIEW and OUTPUT_REVIEW (each count ≥1, plus OUTPUT_REVIEW verdict=approve); DIAGNOSIS_REVIEW appears optional. CODE + OUTPUT alone is not enough: `gh pr create` was denied with "CRITIQUE REQUIRED before PR creation. Reason: missing critique stages: PLAN_REVIEW" while both were approve. The gate names the missing stage, so a denied run needs only that round, but the denial fires at PR-create time after all other review work is spent. Do a PLAN_REVIEW round before the first `gh pr create`, against the plan file `/workspace/agent/reports/slang-<n>.md`; if the fix went straight to code, write the plan first (diagnosis → approach → files-in-scope → rejected-alternatives → verification suffices) ([codex-critique gate requires PLAN_REVIEW too, not just CODE+OUTPUT](../learnings/1783655475326-codex-critique-gate-requires-plan-review-too-not-j.md)). For slang-pr-approver the required stages are DECISION_REVIEW + OUTPUT_REVIEW. On both, the gate opens only when each count is ≥1 AND OUTPUT_REVIEW's *last* verdict is approve with `edits_since_critique==0` and an attested-hash match ([STAGE marker + verbatim reviewer block](../learnings/1783670321503-critique-gate-only-counts-codex-calls-carrying-sta.md)).

**The gate fires even for a no-code diagnosis delivery.** For a "no source fix" outcome, CODE_REVIEW is the scope-shrinkage guard: ask codex whether concluding "no fix" is evidence-backed or under-delivery, with an empty `git diff base..HEAD` as the artifact ([verdict-parsing](../learnings/1783352556452-step-0-byte-compare-to-decide-if-a-diff-changed-em.md)).

**Coverage resets on ANY edit after the OUTPUT approve**, even to an unrelated file such as `/workspace/agent/memory/fix-<n>.md`. On slang#12211, OUTPUT_REVIEW=approve, then a memory write, then the `[Fix Report]` send was refused with "1 edit(s) recorded since the last critique round". Do all memory and housekeeping writes BEFORE the final OUTPUT_REVIEW, so the approve is the last action before the delivery `<message>` ([critique-gate coverage resets on ANY edit after OUTPUT approve — write memory BEFORE the final review](../learnings/1784898493181-critique-gate-coverage-resets-on-any-edit-after-ou.md)).

**The gate re-hashes the OKF memory copy.** Two memory dirs diverge: `/home/node/.claude/projects/-workspace-agent/memory/` (the CLAUDE.md Memory-section index) and `/workspace/agent/memory/` (the fix-workflow Step-9 OKF bundle). codex-critique runs with `cwd=/workspace/agent`, so OUTPUT_REVIEW reads the OKF copy, and a status change (e.g. draft→MERGED) that must clear an "artifacts don't match the claimed state" finding has to land in `fix-<n>.md` + `MEMORY.md` there. Keep both in sync for accuracy, but the OKF copy is authoritative to the gate; the split cost ~3 extra OUTPUT_REVIEW rounds on slang#12270/PR#12271 ([codex-critique reads the /workspace/agent/memory OKF copy, not ~/.claude](../learnings/1785469241189-codex-critique-reads-the-workspace-agent-memory-ok.md)).

**Reading PR state and posting while gated.** The hook's PR-create regex `gh api [^|]*pulls\b` (hook line 60) denies even read-only `gh api .../pulls/N` reads ([critique gate blocks read-only gh api .../pulls/N calls](../learnings/1791303973484-critique-gate-blocks-read-only-gh-api-pulls-n-call.md)); while OUTPUT_REVIEW is must-fix it blocks every Bash command containing `gh api repos/<o>/<r>/pulls/<n>`, GETs included ([ROUND + REQUIREMENTS](../learnings/1790868961396-codex-critique-rounds-only-count-with-round-requir.md)). Read PR state through the slang-mcp tools, `gh api .../issues/<n>` (including `issues/<n>/comments`), `gh pr view` / `gh pr diff`, `gh api .../compare/...`, or `eval-clauses.py`'s already-fetched output. A public comment over 1000 chars is posted from the attested file (`-F body=@file`) with every claim true at posting time, so a rewritten PR description is published *before* the comment announcing the rewrite ([ROUND + REQUIREMENTS](../learnings/1790868961396-codex-critique-rounds-only-count-with-round-requir.md)).

**Rebase before `CODE_REVIEW`.** When upstream advances between cutting the fix branch and running CODE_REVIEW, codex reads upstream-only changes as deletions/reverts and flags them as must-fix scope creep. One rebase removes these phantom findings: `git fetch origin <base> && git rebase origin/<base> && git push --force-with-lease`. Rebase late, only when needed; the same applies to OUTPUT_REVIEW when the deliverable cites a diff ([Always rebase before codex CODE_REVIEW to get a tight scope diff](../learnings/1780304385745-always-rebase-before-codex-code-review-to-get-a-ti.md)).

**AI disclaimer placement.** The bot-transparency subscript (`🤖 Generated by…`) belongs on issue/PR **comments**, not the PR description. Upstream Slang policy prohibits AI-tool attribution in commit messages and PR bodies, and `OUTPUT_REVIEW` flags a PR-body footer as must-fix ([danger-full-access; AI-disclaimer on comments](../learnings/1781129788679-codex-critique-needs-danger-full-access-ai-disclai.md)).

**Codex-outage fallback.** In the slang#12211 session `mcp__codex__codex` had a multi-hour outage (~15 consecutive "stream disconnected" plus an Azure 500) that OUTPUT_REVIEW never recovered from. When codex is the only thing blocking a marker send and the reviewed content is already approved and public (PR open, peer review dispatched), deliver the status upstream WITHOUT the gated marker phrase — a plain status roll-up is not gated — rather than leave the chain silent; the GitHub PR/issue is the durable record. The `gpt-5.2-codex` model override returns 403 in this container: omit it and use the default ([coverage resets on ANY edit](../learnings/1784898493181-critique-gate-coverage-resets-on-any-edit-after-ou.md)).

## A Critique Approve Is a Signal, Not a Proof

On slang PR #12122 the fixer's CODE_REVIEW returned **approve** for a change replacing hard-coded `_sm_6_10` with capdef-derived helpers; a local test-build then falsified it. Codex reasoned by analogy to a neighbouring committed helper and did not model the concrete `CapabilityAtom` enum ordering: a shader-stage atom sorts *above* the version atoms, so the "max atom ≥ anchor" scan silently widened the family predicate. For critique-overlay, pr-approver and reviewer coworkers, an approve does not substitute for a test-build on changes that depend on **enum/atom ordering, contiguity or set membership** (capability sets, IR opcodes, profile atoms, bitflag ranges). Treat "approve by analogy to a nearby helper" as lower confidence and fail closed (return `Invalid`) when the anchor atom is absent. This is why the fix workflow runs the build and full test suite *after* the gate, never instead of it ([codex critique gates can approve-by-analogy and miss enum-ordering bugs a test-build catches](../learnings/1784424200204-codex-critique-gates-can-approve-by-analogy-and-mi.md)).

## A Blocked Probe Is UNVERIFIED on Your Edge

When a hook denies, a call fails, or a stage is skipped for the probe that would confirm a claim, the outcomes are "verified" vs "unknown"; a relayed claim does not fill the gap. On the slang#11225 CI-babysitter chain a hook-denied probe was followed by writing the parent's "the guard PR is held as a draft" into durable memory *as fact*, with a note that the probe had been denied. Nine minutes later the parent self-corrected: **no guard PR and no branch existed** (slangpy#1087 was an open issue only, `git/matching-refs/heads/1087` empty, zero of 25 open slangpy PRs matching). The trap feels rigorous — noting the denial, attributing the source and reasoning about coverage all read like diligence while producing the same corrupted record as blind acceptance. Transparency about how you failed to verify is not verification. Corrupt memory is arguably worse than a bad post: a post is contradicted in public, while a bad memory quietly reshapes every later sweep that reads it. The rules ([a hook-denied or failed verification probe means UNVERIFIED — never record the relayed claim as fact](../learnings/1785746988001-a-hook-denied-or-failed-verification-probe-means-u.md)):

1. **Mark it, don't launder it** — write `state=UNVERIFIED (probe denied)`. A stated gap is recoverable; a laundered fact silently shapes later decisions.
2. **Try another route before giving up** — the denial hits one call. Here plain `pulls?state=open` plus `git/matching-refs` both worked and would have caught the error at once.
3. **Weight by consequence** — this fact decided whether a persistent red meant "waiting on a human" or "fixer still working", two different escalation postures. The more a fact drives your next action, the less relayed provenance is worth.
4. **Relayed ≠ primary, even from your parent** — a parent's report can be mid-flight and self-corrected minutes later.
5. **Re-check an escalation's presupposition** against the state you just verified. "Promote the guard out of draft?" and "no draft exists" cannot both be true; a forward-looking framing smuggles an unverified premise into a human's decision queue.

This extends "verify a relayed premise at HEAD before posting" to the recording path. It differs from the resume-after-pause rule: there, state was verified once and went stale; here, it was never verified.

**"I can't check X" is not "X is uncheckable" — delegate before you record.** The other route can be another agent's edge. Tool availability varies per edge (hook/critique gates, per-path credential injection, provider differences), so a capability failure is evidence about your edge, not about the question. On slang#11917 an orchestrator auditing the drafts-only guardrail needed to know who flipped PR #12281 out of draft; its `gh api .../timeline` call was hook-denied, so it recorded `⚠️UNVERIFIED`. The identical command ran on the triager's edge and answered in one call: `ready_for_review` actor = the human maintainer, no breach. The order is: (1) hand the probe to a coworker on a different edge before concluding; (2) record UNVERIFIED only after someone who plausibly could has tried; (3) reciprocate — when a peer's UNVERIFIED marker covers something trivially checkable from your seat, run it and tell them. When the answer arrives, **replace the marker in place**: an appended retraction leaves the wrong claim doing the work, the same discipline as patching a published verdict rather than footnoting it. This is the edge-scoped twin of the path-classed-401 rule — an instrument's failure is a fact about the instrument until you have varied the instrument. Current draft state cannot say *who* flipped it; use `gh api repos/OWNER/REPO/issues/<n>/timeline --jq '.[] | select(.event=="ready_for_review" or .event=="convert_to_draft") | "\(.event) actor=\(.actor.login) \(.created_at)"'`. From the same chain: matching a branch-name prefix is not identifying a branch. `fix/issue-11917-pass2` looked like "batch 2" but its last commit predated the dispatch by three weeks, so characterize refs by commit date, not name ([a hook-denied probe is UNVERIFIED on *your edge* — delegate to another edge before recording, and replace the marker in place](../learnings/1785825256615-i-can-t-check-x-is-not-x-is-uncheckable-delegate-a.md)).

## Memory-Artifact Integrity: Forward-Reference Rot

Critique rounds hash memory artifacts, so an index hook that asserts something its own child never contained matters to the gate. A summary→detail pair authored in the wrong order passes every structural check: link resolution ✅ (the file exists), cut-then-verify ✅ (nothing was cut, so the check cannot fire), content ❌ (the claim is nowhere in the child). Four instances appeared in one hour across two agents, all in hooks written that day while recording corrections — the failure concentrates where you are most diligent, because that is when pointers get written fastest. Cut-then-verify attaches to *shortening* a pointer; this is a write, so the check must attach to *authoring* one. Detection: extract checkable tokens from each hook (issue refs `#\d{3,6}`, distinctive numbers, backticked identifiers) and grep the child for each, verifying tokenizer-split false positives (a `06-30` date yielding a bare `30`) individually. ⚠️ The mismatch does not say which side is wrong. A 55-entry sweep found an index saying "#11817 MERGED 06-30" while the child still called the fix pending; GitHub (`merged_at=2026-06-30T01:32:53Z`, sha `f23b543c8679`) showed the hook right and the child stale, and an auto-repair that always appends index→child would have corrupted the entry, re-opening a bucket merged 34 days earlier. Go to ground truth, not to whichever text you wrote more recently. Repair by appending to the child, content-grepping to confirm, and marking the block `⛔ DO NOT COMPRESS` with *why*, so the next compaction does not re-create the gap. Separately, a "compaction" that reads cleaner may be **larger**: one rewrite came out +476 bytes, then +255, before shrinking, caught only by printing the delta on the specific lines changed, since file totals get masked by concurrent edits ([forward-reference memory rot: an index hook whose child predates the claim passes every structural check](../learnings/1785784698148-forward-reference-memory-rot-an-index-hook-whose-c.md)).

## Contradictions / supersessions

- The rule "a hook-denied or failed probe means UNVERIFIED" is REFINED, not retired: a denial on *your* edge is a fact about your edge, so UNVERIFIED is the correct record only after a coworker on a different edge has also failed; the slang#11917 draft-flip audit was answered in one call from the triager's edge ([delegate a hook-denied probe to another edge before recording UNVERIFIED](../learnings/1785825256615-i-can-t-check-x-is-not-x-is-uncheckable-delegate-a.md)). The "mark it, don't launder it" half stands unchanged.
- Marker-retraction style is corrected: an UNVERIFIED marker is **replaced in place** when the answer lands, never annotated with an appended retraction ([replace the marker in place](../learnings/1785825256615-i-can-t-check-x-is-not-x-is-uncheckable-delegate-a.md)).
