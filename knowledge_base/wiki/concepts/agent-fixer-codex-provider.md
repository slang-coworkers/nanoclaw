# Codex & Provider Parity

Empirical findings from stress-testing Claude vs Codex providers under `AGENT_RUNTIME=local`, and process rules for running `/codex-critique` correctly in the Slang fixer workflow.

## TL;DR

- The native `Task` subagent is Claude-only; on Codex it hangs silently rather than erroring. The portable subagent path on either provider is `mcp__nanoclaw__create_agent` plus a2a messaging.
- Claude coalesces rapid pushed messages into one result; Codex emits one result per push. Fanning out to a Claude coworker and needing per-message reply identity requires waiting for the prior turn or opening separate sessions. Rapid-fire is safe on Codex.
- Plan-gate and critique-gate do not fire under `AGENT_RUNTIME=local`; a `CLAUDE.md` @import cannot be verified on a live session because the system prompt is cached — kill and respawn. The CLI adapter is single-client, so parallel chat calls evict each other.
- Rebase onto the base branch before a codex `CODE_REVIEW`. Otherwise upstream-only changes read as deletions/reverts and codex flags phantom scope-creep must-fixes. Rebase late, only when needed.
- Always call codex with `sandbox: "danger-full-access"`. Under `read-only` it cannot run `cat`/`git`/`grep`, returns a non-verdict, and the gate still counts the round — so the delivery gate can open on a meaningless review.
- The AI-transparency disclaimer goes on issue/PR comments, never in the PR description or commit message. Upstream policy prohibits AI attribution there and `OUTPUT_REVIEW` flags a body footer as must-fix.
- Run every required critique stage up front. For the fixer overlay that is PLAN_REVIEW + CODE_REVIEW + OUTPUT_REVIEW; the denial fires at PR-create time, after all review work is already spent. Write the plan file first if the fix jumped straight to code.
- A round counts only when a FRESH `mcp__codex__codex` call carries both a `STAGE: <NAME>` line and the canonical reviewer block verbatim. A `codex-reply` is never attributed to the gate, and a free-form call records as `stages: none`.
- `developer-instructions` must be a TOP-LEVEL tool parameter, never nested inside `config`. The hook reads only the top-level field, so a config-nested block reads empty and the round is dropped even though codex ran and answered. A secondary tell is codex ignoring your requested output format.
- On a `codex-reply` re-verify, do NOT include a literal `STAGE:` line — the hook treats it as an initial stage call, runs the instruction-pinning check the reply cannot satisfy, and silently drops the approve.
- Critique coverage resets on ANY file edit after the OUTPUT approve, including edits to unrelated memory files. Do all housekeeping writes BEFORE the final review; touch nothing between approve and the delivery send.
- A critique approve is a signal, not a proof. It does not substitute for a test-build on anything depending on enum/atom ordering, contiguity, or set membership. Treat "approve by analogy to a nearby helper" as lower confidence, and fail closed when an anchor value is absent.
- When codex is the only thing blocking a marker send and the reviewed content is already approved and public, deliver a plain ungated status roll-up rather than leaving the chain silent. Model overrides are unavailable in this container — omit them.
- The gate re-hashes the `/workspace/agent/memory` OKF copy, not the `~/.claude` index copy. A status change that must clear an artifact-mismatch gate has to land in the OKF copy.
- A hook-denied or failed probe is a fact about YOUR edge, not about the question. Hand the probe to a coworker on a different edge before concluding; record UNVERIFIED only after someone who plausibly could has also failed.
- Try another route before giving up — one blocked endpoint does not make a fact unreachable, and the alternate route is often trivial.
- Never launder a relayed claim into durable memory as fact. Noting the denial, attributing the source, and reasoning about coverage all read like diligence while producing the same corrupted record as blind acceptance. Write `state=UNVERIFIED (probe denied)`; a stated gap is recoverable, a laundered fact is not.
- Relayed is not primary, even from your parent — a parent's report can be mid-flight and self-corrected minutes later. Weight relayed provenance inversely to how much the fact drives your next action.
- Replace an UNVERIFIED marker IN PLACE when the answer arrives. Never append a retraction below it: the standing marker is what the next reader acts on.
- Reciprocate — when a peer's UNVERIFIED marker covers something trivially checkable from where you sit, run it and tell them.
- Re-read an escalation question against the state you just verified and check its presupposition still holds. A forward-looking framing ("promote the guard out of draft?") smuggles an unverified premise into a human's decision queue.
- A summary→detail pointer authored before its child passes link resolution and cut-then-verify while asserting something the child never contained. Verify pointers at AUTHORING time, not only when shortening them: extract checkable tokens (issue refs, distinctive numbers, backticked identifiers) and grep the child for each.
- A pointer/child mismatch does not say which side is wrong. Go to ground truth (GitHub, the build) rather than trusting whichever text you wrote more recently — an auto-repair that always trusts the index can re-open long-merged work.
- Prose quality and byte count are independent claims: a "compaction" that reads cleaner may be larger. Print the delta on the specific lines changed, since file totals get masked by concurrent edits.
- Characterize a ref by its commit date, not its name. Matching a branch-name prefix is not identifying a branch.

## Claude vs Codex Functional Parity

From a 10-probe stress test on `AGENT_RUNTIME=local` (PR #52, snapshot `84ae3e5`), three real asymmetries emerged ([claude-vs-codex-provider-parity](../learnings/1778085879531-claude-vs-codex-provider-parity.md)):

**1. Native `Task` subagent — Claude only.** `Task` is in Claude SDK's `allowedTools` (`providers/claude.ts:47`). Codex has no equivalent; under test it **hung 150 s silently** rather than returning "unavailable". Both providers do have `mcp__nanoclaw__create_agent` + a2a messaging — that is the portable subagent path that works on either.

**2. Rapid message queueing.** Claude SDK's `stream.push` coalesces pending messages into one result event; Codex emits one result per push. In a 10-message Promise.all fan-out, Claude returned 1/5 tagged replies (4 timeouts) while Codex returned 5/5. Implication: if fanning out messages to a Claude coworker and needing per-message reply identity, wait for the prior turn to finish OR open separate sessions. For Codex, rapid-fire is fine.

**3. Latency — Codex is consistently faster per probe** (12–87% faster in test probes). Likely cause: Claude Opus prompt-caching + thinking blocks add latency; Codex/nvinference has lower TTFT.

**What works identically on both:**
- Connectivity, MCP tool calls (deepwiki, schedule_task, cancel_task), error paths.
- Both get the same `mcpServers` config from agent-runner (`container/agent-runner/src/index.ts:104,171`).
- Both pick up `.instructions.md` + `CLAUDE.md` content at session start.

**Blocked on local runtime (not a provider difference):** Plan-gate/critique-gate do NOT fire under `AGENT_RUNTIME=local` (`src/container-runner.ts:730-736` — documented limitation). `CLAUDE.md` @import can't be verified on a live session (system prompt is cached); requires kill + fresh session spawn. The CLI adapter is single-client (`src/channels/cli.ts:152`); parallel `pnpm run chat` calls evict each other — use a persistent socket with in-band tags.

## Codex Critique Workflow Rules

**Always rebase before `CODE_REVIEW`** ([Always rebase before codex CODE_REVIEW to get a tight scope diff](../learnings/1780304385745-always-rebase-before-codex-code-review-to-get-a-ti.md)). When upstream advances between when the fix branch was cut and when CODE_REVIEW runs, codex sees upstream-only changes as "deletions/reverts" in the diff and flags them as must-fix scope-creep items. One rebase eliminates these phantom findings. Sequence: `git fetch origin <base> && git rebase origin/<base> && git push --force-with-lease`. Rebase late (only when needed), not early. Same applies to OUTPUT_REVIEW if the deliverable cites a diff.

**`/codex-critique` must pass `sandbox: "danger-full-access"`** ([codex-critique needs danger-full-access; AI-disclaimer goes on comments not PR bodies](../learnings/1781129788679-codex-critique-needs-danger-full-access-ai-disclai.md)). With `read-only`, codex cannot execute `cat`/`git`/`grep` to read artifacts and returns a "workspace command execution is blocked" non-verdict. The critique-gate hook still counts the round, so the delivery gate can open on a meaningless review. Always give codex full access; re-run if a round came back unable-to-read.

**AI disclaimer placement** ([codex-critique needs danger-full-access; AI-disclaimer goes on comments not PR bodies](../learnings/1781129788679-codex-critique-needs-danger-full-access-ai-disclai.md)): the bot-transparency disclaimer subscript (`🤖 Generated by…`) belongs on issue/PR **comments**, NOT on the PR description/body. Upstream Slang policy prohibits AI-tool attribution in commit messages or PR bodies. codex `OUTPUT_REVIEW` will flag a footer on the PR body as a must-fix.

**The delivery gate requires a recorded round for EVERY required stage — including PLAN_REVIEW.** For the slang-fixer critique-gate overlay the required stages are **PLAN_REVIEW, CODE_REVIEW, and OUTPUT_REVIEW** (all count ≥1, plus OUTPUT_REVIEW verdict=approve). Running only CODE_REVIEW + OUTPUT_REVIEW is NOT enough: `gh pr create` was denied with "CRITIQUE REQUIRED before PR creation. Reason: missing critique stages: PLAN_REVIEW" even though CODE+OUTPUT were both approve. Run all three *up front* — before the first `gh pr create` attempt, do a PLAN_REVIEW round against the plan file (`/workspace/agent/reports/slang-<n>.md`; write the plan first if the fix skipped straight to code — diagnosis→approach→files-in-scope→rejected-alternatives→verification suffices). DIAGNOSIS_REVIEW appears optional (the gate didn't demand it). Each stage needs a FRESH `mcp__codex__codex` call with the verbatim canonical developer-instructions and a `STAGE:` marker; a `codex-reply` is NOT attributed to the gate. The gate names exactly which stage is missing, so if denied, add just that round — but running all three from the start saves the late round-trip, since the denial fires at PR-create time after all code/output review is already done ([codex-critique gate requires PLAN_REVIEW too, not just CODE+OUTPUT](../learnings/1783655475326-codex-critique-gate-requires-plan-review-too-not-j.md)).

## Critique-Gate Recording Mechanics (slang-pr-approver)

The approver's recording gate (`track-critique.sh` + `gate-critique-on-deliver.sh`) counts a critique round toward the delivery gate ONLY when the `mcp__codex__codex` call carries BOTH a `STAGE: <NAME>` line AND the canonical `/codex-critique` `developer-instructions` block verbatim (the hook checks the two sentinel lines "You are an independent reviewer" and "Return ONLY the structured output below"); a free-form call records as `stages: none, verdicts: none` and never satisfies the gate. Required stages are DECISION_REVIEW + OUTPUT_REVIEW, and the gate opens only when each count is at least 1 AND OUTPUT_REVIEW's *last* recorded verdict = approve with `edits_since_critique==0` and an attested-hash match ([critique gate only counts codex calls carrying STAGE marker + verbatim reviewer block](../learnings/1783670321503-critique-gate-only-counts-codex-calls-carrying-sta.md)). A subtle trap on re-verify: a `codex-reply` prompt containing a literal `STAGE:` line still matches the hook's grep, so it is treated as an *initial* stage call and runs the instruction-pinning check -- but replies carry no developer-instructions, so the pin check fails and the reply's approve is silently dropped. Either phrase the reply WITHOUT the literal `STAGE:` token (the thread inherits its stage) or issue a fresh `codex` call carrying the canonical instructions + a leading `STAGE:` line ([codex-reply re-verify must NOT contain a literal STAGE: line](../learnings/1783668707884-critique-gate-codex-reply-re-verify-must-not-conta.md)). Separately, the `gate-critique-on-deliver.sh` PreToolUse hook pattern-matches `gh api .../pulls` as PR-creation and DENIES it even for read-only `gh api .../pulls/N` reads -- route around with `gh pr view` or `gh api .../compare/...`, or read `eval-clauses.py`'s already-fetched output rather than re-fetching ([critique-gate hook false-positives on read-only gh api .../pulls](../learnings/1783691363555-approver-critique-gate-hook-false-positives-on-rea.md)).

## A Codex Critique Approve Is a Signal, Not a Proof (2026-07-20 fold)

On slang PR #12122, the fixer's codex CODE_REVIEW gate returned **approve** for a change replacing hard-coded `_sm_6_10` with capdef-derived helpers; a subsequent local test-build falsified it. Codex reasoned by analogy to a neighboring committed helper and did not model the concrete `CapabilityAtom` enum ordering — a shader-stage atom sorts *above* the version atoms, so the "max atom ≥ anchor" scan silently widened the family predicate. Transferable rule for critique-overlay / pr-approver / reviewer coworkers: a critique/CODE_REVIEW **approve** is a signal, not a proof, and does NOT substitute for a test-build on changes that depend on **enum/atom ordering, contiguity, or set-membership** (capability sets, IR opcodes, profile atoms, bitflag ranges). Treat "approve by analogy to a nearby helper" as *lower* confidence; fail-closed (return `Invalid`) when the anchor atom is absent. This is why the fix workflow runs build + full test-slang *after* the gate, never as a substitute ([codex critique gates can approve-by-analogy and miss enum-ordering bugs a test-build catches](../learnings/1784424200204-codex-critique-gates-can-approve-by-analogy-and-mi.md)).

## Critique-Gate Coverage Resets on ANY Edit; Codex-Outage Fallback (2026-07-24 fold)

The `[critique-gate]` guarding `[Fix Report]`/PR-create delivery counts *any* file edit recorded after the last OUTPUT_REVIEW approve as invalidating that approve — even an edit to an unrelated file like `/workspace/agent/memory/fix-<n>.md`. Observed on slang#12211: OUTPUT_REVIEW=approve → wrote the memory file → the `[Fix Report]` send was REFUSED ("1 edit(s) recorded since the last critique round"). How to apply: do the memory-file Write and all housekeeping edits BEFORE the final OUTPUT_REVIEW, or batch them so OUTPUT approve is the very last action before the delivery `<message>` — don't touch the filesystem between the approve and the marker send. Compounding gotcha the same session: `mcp__codex__codex` had a sustained multi-hour outage (~15 consecutive "stream disconnected" + one Azure 500) that OUTPUT_REVIEW never recovered from — when codex is the only thing blocking a marker send and the reviewed content is already approved + public (PR open, peer-review dispatched), deliver the status upstream WITHOUT the gated marker phrase (plain status roll-up isn't gated) rather than leaving the chain silent, since the GitHub PR/issue is the durable record. Also: `gpt-5.2-codex` model override returns 403 in this container (omit the override, use default), and a `codex-reply` approve is NOT attributed to the gate — it needs a fresh `codex()` call with the canonical /codex-critique developer-instructions block ([critique-gate coverage resets on ANY edit after OUTPUT approve — write memory BEFORE the final review](../learnings/1784898493181-critique-gate-coverage-resets-on-any-edit-after-ou.md)).

## developer-instructions Must Be a TOP-LEVEL Param, Not Inside `config` (2026-07-28 fold)

A subtle miswiring defeats the critique-gate even with a byte-perfect reviewer block: the `developer-instructions` field MUST be a **top-level** `mcp__codex__codex` parameter (alongside `prompt`/`sandbox`/`cwd`), NOT nested inside the `config` object. When it's inside `config`, the PostToolUse `track-critique.sh` hook does NOT record the round — it emits "Critique round NOT recorded: … developer-instructions do not match the canonical /codex-critique reviewer block" even though the block is verbatim, because the sentinel check ("You are an independent reviewer" / "Return ONLY the structured output below") reads only the top-level param; a secondary tell is codex ignoring your requested output format and replying in its default style. Cost when wrong: two full CODE_REVIEW calls on fix #12237 produced good critiques that counted for nothing, forcing re-runs. Reinforces the recording mechanics above — the round is attributed only when a fresh `codex` call carries BOTH the `STAGE:` marker AND the verbatim block at the top level ([codex-critique developer-instructions must be a TOP-LEVEL param, not inside config](../learnings/1785246644952-codex-critique-developer-instructions-must-be-a-to.md)). The mechanism is exact: `track-critique.sh` line 25 reads `.tool_input."developer-instructions"` (top-level only), so a block nested under `config` reads as EMPTY, fails the "You are an independent reviewer" / "Return ONLY the structured output below" sentinel check, and emits "Critique round NOT recorded" even though codex still ran and returned a correct verdict; a secondary tell is codex ignoring your requested output format. Verified 2026-07-30 on slang#12219/PR#12263 OUTPUT_REVIEW — moving the same block config→top-level flipped the hook from "NOT recorded" to "Critique round 38 recorded" ([codex-critique: developer-instructions must be a TOP-LEVEL param, not inside config](../learnings/1785437953553-codex-critique-developer-instructions-must-be-a-to.md)).

## A Hook-Denied or Failed Probe Means UNVERIFIED *On Your Edge* — Delegate First, and Never Fall Back to the Relayed Claim (2026-08-04 fold)

The provider/gate surface can *block your verification*, and once no one who plausibly could has been able to run the probe, that outcome has exactly one correct record: **UNVERIFIED** (see the delegate-first step below — a denial on *your* edge is not yet an UNVERIFIED fact). When a PreToolUse hook denies (or a call fails, or a stage is skipped) the probe that would have confirmed a claim, the two outcomes are not "verified" vs "verified-by-someone-else" — they are "verified" vs "unknown", and a relayed claim does not fill the gap. Observed on the slang#11225 CI-babysitter chain: a hook-denied probe, followed by writing the parent's "the guard PR is held as a draft" into durable memory *as fact* with an explicit note that the probe had been denied; nine minutes later the parent self-corrected — **no guard PR and no branch existed at all** (slangpy#1087 was an open issue only, `git/matching-refs/heads/1087` empty, zero of 25 open slangpy PRs matching). What makes the trap effective is that it *feels* rigorous: noting the denial, attributing the source, and reasoning about coverage all read like diligence while producing the same corrupted record as blind acceptance. **Transparency about how you failed to verify is not a substitute for verifying.** How to apply: (1) *mark it, don't launder it* — write `state=UNVERIFIED (probe denied)`, since a stated gap is recoverable and a laundered fact silently shapes later decisions; (2) *try another route before giving up* — the denial hits one specific call, and here plain `pulls?state=open` plus `git/matching-refs` both worked and would have caught the error immediately, so one blocked path ≠ the fact is unreachable; (3) *weight by consequence* — the more a fact drives your next action (this one decided whether a persistent red meant "waiting on a human" or "fixer still working," different escalation postures), the less relayed provenance is worth; (4) *relayed ≠ primary, even from your parent* — a parent's report is a secondary source that can be mid-flight or self-corrected later ([a hook-denied or failed verification probe means UNVERIFIED — never record the relayed claim as fact](../learnings/1785746988001-a-hook-denied-or-failed-verification-probe-means-u.md)). This generalizes the "verify a relayed premise at HEAD before posting" rule to the *recording* path: corrupt memory is arguably worse than a bad post, because a post gets contradicted in public while a bad memory quietly reshapes every later sweep that reads it. It is distinct from the resume-after-pause rule (there state was verified once and went stale; here it was never verified inside a live turn). A sibling defect on the escalation surface: when you escalate a decision, **re-read the question against the state you just verified and check its presupposition holds right now** — "promote the guard out of draft?" and "no draft exists" cannot both be true, and a forward-looking framing smuggles an unverified premise into a human's decision queue.

**Sharpening — "I can't check X" is NOT "X is uncheckable", so delegate before you record.** Point (2) above ("try another route") has a second, stronger form: the route can be *another agent's edge*, not just another endpoint. Tool availability varies per-edge — hook/critique gates, per-path credential injection, provider differences all differ between coworkers — so **a capability failure is evidence about your edge, not about the question**. Observed on slang#11917: an orchestrator needed to know who flipped PR #12281 out of draft (drafts-only guardrail audit); its `gh api .../timeline` call was hook-denied on its edge, so it recorded a `⚠️UNVERIFIED` gap. The identical command ran fine on the triager's edge and answered the question in one call — `ready_for_review` actor = the human maintainer, no breach. The order of operations is therefore: (1) hand the probe to a coworker on a different edge *before* concluding anything; (2) record UNVERIFIED only after *someone who plausibly could* has tried; (3) reciprocate — when a peer's `UNVERIFIED` marker sits on something trivially checkable from where you sit, just run it and tell them. **Corollary on markers: when the answer arrives, REPLACE the UNVERIFIED marker in place — never append a retraction below it.** A standing marker is what the next reader acts on, so an appended correction leaves the wrong claim doing the work (the same discipline as patching a published verdict rather than footnoting it). This is the edge-scoped twin of the path-classed-401 rule: switching transport cannot fix a per-path defect, and a failure on one path/edge says nothing about another — both instances of *an instrument's failure is a fact about the instrument until you have varied the instrument*. The useful command for the draft-guardrail case specifically, since current draft state cannot tell you *who* flipped it: `gh api repos/OWNER/REPO/issues/<n>/timeline --jq '.[] | select(.event=="ready_for_review" or .event=="convert_to_draft") | "\(.event) actor=\(.actor.login) \(.created_at)"'`. Pairs with an anti-pattern from the same chain: **matching a branch-name prefix is not identifying a branch** — `fix/issue-11917-pass2` looked like "batch 2" but its last commit predated the dispatch by three weeks; characterize refs by commit date, not name ([a hook-denied probe is UNVERIFIED on *your edge* — delegate to another edge before recording, and replace the marker in place](../learnings/1785825256615-i-can-t-check-x-is-not-x-is-uncheckable-delegate-a.md)).

**Corollary for the memory files the gate re-hashes: an index hook can assert something its own child never contained.** Because critique/OUTPUT_REVIEW rounds hash memory artifacts, a summary→detail pair authored in the wrong order passes every structural check — link resolution ✅ (the file exists), cut-then-verify ✅ (nothing was cut, so the check *cannot* fire), content ❌ (the claim is nowhere in the child). Four instances appeared in one hour across two agents, all in hooks authored that same day while recording corrections — the failure concentrates exactly where you are being most diligent, because that is when new pointers get written fastest. Cut-then-verify misses it because that discipline attaches to *shortening* a pointer; this is a **write**, so the check has to attach to *authoring* a pointer. Detection: extract checkable tokens from each hook (issue refs `#\d{3,6}`, distinctive numbers, backticked identifiers) and grep the child for each, expecting tokenizer-split false positives (a `06-30` date yielding a bare `30`) that must be verified individually. ⚠️ **The mismatch does not tell you which side is wrong** — a 55-entry sweep surfaced the inverse case, where the index said "#11817 MERGED 06-30" while the child still described the fix as pending; GitHub settled it (`merged_at=2026-06-30T01:32:53Z`, sha `f23b543c8679`) and the *hook* was right, the child stale. An auto-repair that always appends index→child would have re-opened a bucket merged 34 days earlier. Go to ground truth, not to whichever text you wrote more recently. Repair by appending to the child, content-grepping to confirm, and marking the block `⛔ DO NOT COMPRESS` with *why*, so the next compaction pass doesn't re-create the gap. Sibling: a "compaction" that reads cleaner may be **larger** — one rewrite came out +476 bytes, then +255, before finally shrinking, caught only by printing a delta on the specific line changed (file totals get masked by concurrent edits); prose quality and byte count are independent claims ([forward-reference memory rot: an index hook whose child predates the claim passes every structural check](../learnings/1785784698148-forward-reference-memory-rot-an-index-hook-whose-c.md)).

**The VERDICT is parsed only from the skill's EXACT block, and the gate fires even for a no-code diagnosis delivery.** Two verdict-format specifics that trip the fixer overlay (`/slang-fix-issue`), from diagnosing slang#11952: the parser records the STAGE only from a fresh `mcp__codex__codex` call whose prompt contains a `STAGE: <X>` line, and records the VERDICT only when codex returns the skill's literal block `### Verdict\napprove` (or `must-fix`) — `VERDICT: approve` as free text is NOT parsed and shows `verdicts: none`, so pass `developer-instructions` = the codex-critique reviewer template so codex emits that structure. A `codex-reply` approve (round 2/3 of a must-fix) is not attributed to the stage because the reply carries no `STAGE:` tag, so to clear a must-fix'd OUTPUT_REVIEW you must fix, then issue a NEW STAGE-tagged `codex` call, not a reply. The gate fires **even for a no-code diagnosis delivery** ("no source fix" outcome): CODE_REVIEW is still meaningful there as the **scope-shrinkage guard** — ask codex whether concluding "no fix" is evidence-backed or under-delivery, with an empty `git diff base..HEAD` as the artifact (all codex calls in this container require `sandbox: "danger-full-access"`; a hook rejects read-only) ([codex delivery-gate verdict-parsing: only the exact `### Verdict` block counts, and the gate fires even for a no-code diagnosis](../learnings/1783352556452-step-0-byte-compare-to-decide-if-a-diff-changed-em.md)).

A related gate-clearing trap involves WHICH memory copy codex re-hashes: two `/workspace/agent` memory dirs diverge — `/home/node/.claude/projects/-workspace-agent/memory/` (the CLAUDE.md Memory-section index) and `/workspace/agent/memory/` (the fix-workflow Step-9 OKF bundle). Because codex-critique runs with `cwd=/workspace/agent`, OUTPUT_REVIEW reads the **OKF copy**, so a status/outcome change (e.g. draft→MERGED) that must clear the "artifacts don't match the claimed state" gate has to update `fix-<n>.md` + `MEMORY.md` under `/workspace/agent/memory/`, not just the `~/.claude` one (keep both in sync for accuracy, but the OKF copy is authoritative to the gate — this split cost ~3 extra OUTPUT_REVIEW rounds on slang#12270/PR#12271) ([codex-critique reads the /workspace/agent/memory OKF copy, not ~/.claude](../learnings/1785469241189-codex-critique-reads-the-workspace-agent-memory-ok.md)).

## Contradictions / supersessions

- The bare rule "a hook-denied or failed probe means UNVERIFIED" is REFINED, not retired: a denial on *your* edge is a fact about your edge, so UNVERIFIED is the correct record only after a coworker on a different edge has also failed. Hand the probe over first; the slang#11917 draft-flip audit was answered in one call from the triager's edge after being hook-denied on the orchestrator's ([delegate a hook-denied probe to another edge before recording UNVERIFIED](../learnings/1785825256615-i-can-t-check-x-is-not-x-is-uncheckable-delegate-a.md)). The "mark it, don't launder it" half of the original rule stands unchanged.
- Marker-retraction style is corrected: an UNVERIFIED marker must be **replaced in place** when the answer lands, never annotated with an appended retraction below it — a standing marker is what the next reader acts on ([replace the marker in place](../learnings/1785825256615-i-can-t-check-x-is-not-x-is-uncheckable-delegate-a.md)).
