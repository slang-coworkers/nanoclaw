## TL;DR

- **Diagnose CI failures via the unauthenticated job-logs endpoint** — `.../actions/jobs/<job_id>/logs` returns the full plaintext log (root cause at the *tail*, not near a grep for the step name). If all N runs on a saturated page fall in your window, N is a floor.
- **A `Check Submodule Pointers` failure across every merge candidate is usually not a bad pin** — upstream may have moved its default branch (mimalloc → `main3`); the fix is a `branch =` override, not a pin bump.
- **A `cancelled` CI conclusion is often self-inflicted** — `workflow_dispatch` re-dispatch on the same ref cancels the prior run. Only the newest run on the ref is authoritative; read `status` alongside `conclusion`.
- **A retry/priority gate can be decorative**: the 12h anti-starvation age-out never fires (a rerun flips `triggering_actor` and skips the gate); a retry loop's 16h lookback is a **hard drop**, stranding runs forever while reporting green. Ask what is on the LHS of a threshold *at the moment the compare runs*.
- **Runtime asserts are not spelled `SLANG_ASSERT` in CI logs** — they're `assert failure:|InternalError|E99997`. A pattern that can never match makes every real regression look like infra.
- **A checked-in "no GPU" claim is guidance, not a measurement** — run the capability's own one-liner.
- **PR-approver**: a rebase re-scopes every count and inverts staleness discriminators; state the compare range with the number; slangpy submodule-bump PRs can reach the approver with ZERO review coverage.

## Reading CI: the log endpoint, submodule pins, and self-inflicted cancels

**The unauthenticated job-logs endpoint gives root cause without a token.** `curl .../actions/runs?status=failure&per_page=15` → run list; `.../runs/<id>/jobs` → per-job `conclusion` + `steps[]` (filter `conclusion not in (success, skipped)` for the failing step); **`.../actions/jobs/<job_id>/logs` returns HTTP 200 plaintext unauthenticated** — the step most people skip, turning "N runs red" into a root cause in one call. Gotchas: the failing output is at the *tail* (the step-name marker isn't in the body — `tail -30` beats grep); if all N runs on `per_page=N` fall in your window, **N is a floor, not a count** (page saturated). And an invalid `GH_TOKEN` in the environment makes `curl` return 401 even with `env -u GH_TOKEN` — unauthenticated `git ls-remote`/`git fetch` against public repos is the reliable path for ref/submodule questions. [Diagnosing shader-slang CI failures: unauthenticated job-logs endpoint gives root cause](../learnings/1786003916352-diagnosing-shader-slang-ci-failures-unauthenticate.md)

**A `Check Submodule Pointers` failure on every merge candidate is usually not a bad pin.** When it blocked the whole queue, `external/mimalloc`'s pin `8c532c32` was exactly tag `v2.1.7` (immutable, legitimate) — but microsoft/mimalloc **moved its default branch to `main3`** (the v3 line), and `extras/check-submodule-commits.sh` resolves the tracked ref as the remote's *default branch* when `.gitmodules` has no `branch =` override. v2.1.7 is reachable from `main` but not `main3`, so the check's verdict is correct while its premise silently became wrong. **Fix: add `branch = main` for `external/mimalloc`** (exact precedent: `external/lua` carries `branch = v5.4` for the same reason) — do NOT "fix" it by bumping to a v3 commit (a dependency upgrade nobody asked for). Any submodule tracking a maintenance line while upstream's default advances breaks this with no change on our side; `git ls-remote --symref <url> HEAD` before believing "pin not reachable." [Slang CI: mimalloc submodule pin check fails because upstream default branch moved to main3](../learnings/1786004159453-slang-ci-mimalloc-submodule-pin-check-fails-becaus.md)

**A `cancelled` conclusion is often self-inflicted bookkeeping.** `ci.yml:9-11` keys concurrency on `workflow + ref` with `cancel-in-progress` true for every event except `push` (including `workflow_dispatch`) — so a manual re-dispatch on the same ref cancels the previous dispatch. Before treating `conclusion == "cancelled"` as a signal, check `event` and whether a *later* run exists in the same concurrency group; **only the newest run on the ref is authoritative.** Second, independent trap: a run can sit `status=queued, conclusion=null` for over an hour, and `conclusion` is empty for *both* "still queued" and "no result" — always read `status` alongside it, and timestamp the reading (a CI observation at a SHA expires even though the source at that SHA doesn't). Attributing a concurrency-group cancellation to a person or to infra invents a cause. [A `cancelled` CI conclusion on shader-slang/slang is often self-inflicted: workflow_dispatch cancels the prior dispatch on the same ref](../learnings/1786048474695-a-cancelled-ci-conclusion-on-shader-slang-slang-is.md)

**`ci.yml` already has a doc-only GPU skip** (a `filter` job at `:14-49`, `merge_group`-aware by design) — don't propose adding one; propose *calibrating* its two miscalibrated edges (under-inclusive: `.gitmodules` isn't in the allowlist so a submodule-pin change draws the full GPU matrix; over-broad: a generated doc hits an explicit force-run clause). "The skip exists and its edges are miscalibrated" is far harder to reject than "the filter is broken." Trap that cost a wrong caveat: "`paths:` filters are ignored for `merge_group`" is true in general but **does not apply to `ci.yml`, which declares no `paths:` filter at all** — a general fact plus a specific artifact you haven't opened is a confident wrong claim. [slang ci.yml already has a doc-only GPU skip (filter job, ci.yml:14-49) — two miscalibrated edges](../learnings/1786019244861-slang-ci-yml-already-has-a-doc-only-gpu-skip-filte.md)

## Retry and priority gates that read as guarantees but are inert

**The 12h anti-starvation age-out never fires.** A published claim — "`wait-for-priority.py --max-yield-hours 12` measures from fixed `created_at`, so a starved bot dispatch ages out and escalates at ~12h, self-healing, no human action owed" — has every code citation accurate and its behavioural conclusion wrong. The escalation branch is unreachable on both arms: attempt 1 (bot dispatch) is the run's first job, started 0.2–0.4 min after `created_at` (the `>=12` compare is false every time); attempt ≥2 (rerun) flips `triggering_actor` from `nv-slang-bot[bot]` to `github-actions[bot]`, so `IS_THROTTLED_BOT` is false and the gate script exits without ever computing age. ⭐ **A bound evaluated only at instants when the measured quantity is structurally ~0 is decorative and reads as a guarantee — for any threshold, ask what is on the left-hand side at the moments the compare actually runs.** And `actor` vs `triggering_actor` are different fields that a rerun *splits*. Do not tell anyone a starved bot dispatch "will age out at 12h." [RETRACTION: the slang CI 12h anti-starvation age-out never fires (a rerun skips the gate)](../learnings/1786023780798-retraction-the-slang-ci-12h-anti-starvation-age-ou.md)

**A retry workflow's lookback window is a HARD DROP, not a backoff.** `ci-retry-yielded-bot.yml` passes `--lookback-hours 16` to `retry-yielded-bot-ci.py`, whose `yielded_bot_candidates()` does `if created_at < cutoff: continue` — once a yielded run is older than 16h it is *never a candidate again*. Measured: 66 bot `ci.yml` runs permanently stranded, oldest 53 days. The in-repo comment reads as if handled ("lookback (16) must stay above max-yield (12) so a run ages out and escalates") but **the two windows do not compose** — escalation only fires when the gate re-runs, and a run that is never rerun never re-evaluates. **A "recent-window" filter in a remediation loop silently converts a transient backlog into a permanent one, and the loop reports success the whole time (doing nothing is a successful run).** Two catch-it checks: look at `run_attempt` on the things the loop should fix (all sat at `attempt=1`; its own green runs prove nothing), and run the *superseded* control before calling it a leak (6 of 8 flagged stale runs were legitimately superseded on the same branch). Correct action is a maintainer report, not firing 66 reruns. [A retry workflow's lookback window is a HARD DROP, not a backoff — 66 slang bot CI runs stranded up to 53 days](../learnings/1786299672864-a-retry-workflow-s-lookback-window-is-a-hard-drop-.md)

**Slack between two scheduled jobs is a real parameter worth measuring.** Slang release CI runs 41–52 min; an 01:30 UTC "did the nightly run?" check normally has 36–48 min margin, but a single 28-min dispatch jitter took it to 14. If the check catches the run mid-flight it sees `status=in_progress, conclusion=null` — a third state that a `conclusion`-keyed guard reads as a false regression. Filter for run *existence* day-granularly, handle `in_progress` as pending, and if reporting "no dispatch today" include the age of the newest run (a single point-in-time check can't distinguish a late dispatch from a dead dispatcher). A margin you have never measured is a margin you are assuming. [Slang release CI: 41-52 min duration means an 01:30 liveness check has only ~40 min slack — dispatch jitter can leave the run in flight](../learnings/1786067341533-slang-release-ci-41-52-min-duration-means-an-01-30.md)

## Reading assertions and failures out of CI logs

**Runtime asserts are not spelled `SLANG_ASSERT` in CI logs.** Grepping for `SLANG_ASSERT|SLANG_UNEXPECTED|Assertion failed` returns 0 on every log, including ones full of real compiler asserts — Slang emits them as `error[E99997]: ... assert failure: <file>(<line>): <expr>`. Use `assert failure:|InternalError|E99997` (verified: literal-token pattern → 0, corrected → 24 on one job). This matters more than a grep nit: "zero assertions" is the load-bearing premise for classifying a failure as infra/flake rather than a real regression, so a pattern that can never match makes **every** real regression look like infra. Two adjacent traps in the opposite direction (they inflate "real failure"): `[Failed]:` (unit-test framework) and `failed(pending retry)` both precede a later `passed test` on retry — a raw count of check-failure lines is not a failure count. **Require the terminal per-test outcome, and pair every zero with a control grep that must hit.** [Slang runtime asserts are not spelled SLANG_ASSERT in CI logs](../learnings/1786070123355-slang-runtime-asserts-are-not-spelled-slang-assert.md)

**A checked-in "no GPU" claim is guidance, not a measurement.** `shader-slang/slang/.github/copilot-instructions.md` states the environment has no GPU — FALSE on the slang-coworker fleet (`nvidia-smi -L` → L40S; `slang-test` runs `-vk`/`-cuda` for real, only `dx11` is `ignored`). That file describes an *intended* upstream/Copilot sandbox, but being checked-in, maintained, and auto-loaded via `CLAUDE.md`'s include makes a stale claim more persuasive, not more true. A coworker used it as fact to challenge a verified `3/3` local result. **Never publish a capability-negative from a document — run the capability's own one-liner.** And distinguish `ignored` from `passed` with a paired negative control: corrupt the expected value and confirm the target *fails individually* — an `ignored` target keeps "passing" under that mutation, an executed one flips to FAILED. [A checked-in "no GPU" claim is guidance, not a measurement — the slang fleet HAS an L40S](../learnings/1786191092039-a-checked-in-no-gpu-claim-is-guidance-not-a-measur.md)

## Fetching primary GPU specs

Four access gotchas that masquerade as "not documented": (1) `registry.khronos.org` 403s WebFetch — use `curl` through the gateway proxy (don't unset the proxy; WebFetch's own UA/headers were the problem). (2) The CUDA guide was restructured — the index 301-redirects and has zero `atomicAdd`; atomics live on a subpage (a fetch of the root returning `count=0` is a wrong-corpus null, not "undocumented"; follow `-L` and print `%{url_effective}`). (3) The Metal spec is a PDF — use a venv with pypdf; the governing sentence often sits on the section-intro page, not the per-function page. (4) **Per-function tables often DON'T state old-vs-new — the section prose does** (GLSL/Metal atomics state "return the original value read" in the §-intro, not the row). **Grep the section heading, not just the identifier.** Result banked: SPIR-V/GLSL/HLSL/CUDA/Metal/WGSL atomics *all* return the OLD/pre-operation value — uniform across targets, so a Slang atomic lowering can map onto any without an old-vs-new fixup. [Fetching Khronos/CUDA/Metal specs: WebFetch 403s, and the CUDA guide moved](../learnings/1786181912850-fetching-khronos-cuda-metal-specs-webfetch-403s-an.md)

## PR-approver review discipline

**A rebase re-scopes every count and inverts staleness discriminators.** Two tiers argued 22 vs 24 files on slangpy#1090 whose actual PR-level count is **6** — both numbers described the *submodule* compare, and the rebase had dropped the `external/slang-rhi` gitlink from the PR's diff entirely, so the whole dispute was about a population no longer under review. Three ways a rebase silently re-scopes prior conclusions: (1) counts change *population*, not just value — single-commit (`parents[0]...head`), PR-level (`main...head`), and submodule (`old...new`) all answer to "the file count," so **state the range with the number, always** (two ranges can even *both* return "6 files" while measuring different things); (2) staleness discriminators can invert (pre-rebase a stale analysis *missed* the gitlink, post-rebase *rendering* one proves staleness) — re-derive polarity each round; (3) "N heads stale" becomes ill-defined (report "pinned sha not in current history"). The right instrument for "does a prior finding survive a rebase" is **per-file blob-SHA comparison** (byte-identical ⇒ applies verbatim; changed ⇒ re-read that file only), not re-reasoning. And **name the vulnerable step, not the whole tool**: `eval-clauses.py` correctly diffed `base_ref...sha`; the defect was a human hand-feeding it a diverged list. [[approver/clause-gap] A rebase re-scopes every count and inverts staleness discriminators — post-rebase slangpy#1090 has 6 files/218 lines and NO gitlink, so 22-vs-24 was the wrong population entirely](../learnings/1786178662147-approver-clause-gap-a-rebase-re-scopes-every-count.md)

The companion challenger-miss: resolving that same dispute, the "we were both looking at X" explanation was itself a membership claim that went untested *because* it explained the agreement. The 22-file list was the diverged *slangpy* compare (zero submodule-internal paths, one gitlink entry), not the submodule compare — same wrong-range diagnosis, wrong wrong-range. Two agents committed the identical error one round apart, both having filed the "count the hits" rule that same week — **a rule that asks you to remember at the moment of writing cannot fire, because that moment is exactly when attention is on the sentence rather than the evidence** (`cat -n` and read the last line off the output is the version that can't fail). And a finding can be right and inapplicable at once (D3 "gitlink defeats size clauses" is correct but not instantiated post-rebase); saying which is the honest form. [[approver/challenger-miss] "We were both looking at X" is itself a membership claim — the 22-file list was the diverged slangpy compare, not the submodule compare, and four distinct ranges all answer to "the file count"](../learnings/1786179047581-approver-challenger-miss-we-were-both-looking-at-x.md)

**A slangpy PR can reach the approver with ZERO usable review signal**, each source failing for a different individually-plausible reason: production Claude review `completed/skipped`; CodeRabbit path-excludes `external/**` (exactly where submodule pointers live, so it structurally cannot review a submodule bump); Devin auth-fails. Their blind spots have **non-overlapping blind spots that happen to align on submodule-bump PRs** — and the bump's real footprint was far wider than the PR's CUDA-titled framing (unreviewed Vulkan and Metal changes rode along). To catch it: **treat an `external/**`/submodule pointer line as a coverage question, not a one-line change** — expand it (`gh api repos/<owner>/<sub>/compare/<old>...<new> --jq '{ahead,behind,files}'`), check the bump against the PR's stated scope, read CodeRabbit's own "Files ignored due to path filters" block, and when all sources are absent/failed record `ABSTAIN_INFRA:NO_REVIEW_SIGNAL` with a per-source inventory (which source, which state, which evidence) so the human knows *which* coverage is missing. [[approver/infra-abstain] slangpy PRs can have ZERO review sources: Claude skipped + CodeRabbit path-excludes external/** + Devin auth-fails](../learnings/1786117872301-approver-infra-abstain-slangpy-prs-can-have-zero-r.md)

## Compensating transactions and scratch-dir hygiene

**A refund on an unwitnessed outcome trades one leak for its mirror image.** When a quota/capacity system compensates a reservation on failure, check what the failure predicate covers: a boolean `posted` that is `False` for *both* "server refused" and "client timed out" conflates *refused* with *unknown*, and refunding on unknown means a delivered unit costs nothing (measured on nanoclaw#1123 Discord reply-capacity: post-fix 4 delivered, 0 charged, 4 rows asserting failure). **For any compensating transaction, enumerate the outcome space as {succeeded, failed, UNKNOWN} — never as a boolean** (two-valued settlement forces the unknown case optimistically in one direction, a bug in the other); the honest fix is a third terminal state or an idempotency key. And **judge the trade, don't just report the bug** — here the new leak (over-serving a thread whose replies land) is strictly less harmful than the one fixed (silencing a thread that answered nothing), so recommend the direction, not the naive "charge on timeout." Measuring the BASE in the same constructed scenario is what separates "introduced" from "inherited." [A refund on an unwitnessed outcome trades one leak for its mirror image](../learnings/1786026461724-a-refund-on-an-unwitnessed-outcome-trades-one-leak.md)

**A per-issue scratch dir is not per-session.** Namespacing `scratch-12387/` by *issue number* — on a fleet where several sessions work one issue under one bot identity — is namespacing by the thing we have in common, so a second session's `cat > probe.cpp` destroyed a sibling's source. `mkdir -p` succeeds silently either way, so the collision was invisible. Namespace scratch by issue **and** session (`scratch-12387-triage/`), and before writing into a scratch dir you didn't create *this session*, `ls -la` it first (an mtime predating your session start is somebody's working state). Filing the rule did not stop the repeat — the guard has to be a habit at write time, not a principle in a notes file. [A per-issue scratch dir is not per-session: I overwrote a sibling's probe.cpp](../learnings/1786006048902-a-per-issue-scratch-dir-is-not-per-session-i-overw.md)
