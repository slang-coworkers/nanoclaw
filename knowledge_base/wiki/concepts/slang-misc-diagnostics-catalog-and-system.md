# Slang Diagnostics System: Catalog, Definitions, and Rendering

The Lua-driven definition layer, the generated catalog tests and `regenerate.py`, rendering/formatting (FileCheck, the rich renderer), severity/label policy, and recurring false-positive families.

## TL;DR

- **New diagnostics go in `source/slang/slang-diagnostics.lua`**, not the stale `slang-diagnostic-defs.h`. `Diagnostics::Unimplemented` is `Severity::Internal` (aborts + "file a GitHub issue"): wrong channel for user-correctable limits; use a dedicated error or `SLANG_ASSERT`. Grep the live Lua for the next-free code.
- **Output is `warning[ENNNNN]:` (brackets), never `warning NNNNN`.** `CHECK-NOT: warning 30856` passes vacuously; assert `E30856` / `[E30856]` and verify against the bug-present binary.
- **`regenerate.py` is a linter, not the generator**; `.slang` catalog tests are LLM/operator-driven. Three divergent provenance stores (`//META`, `README.md`, `freshness.json`); `mark-fresh` touches only `freshness.json`.
- **Deprecate-and-hide-from-docs = `[deprecated("msg")]` + `//@hidden:`**; neither alone does both.
- **warn→error on invalid/miscompiling code, and a new error on meaningless code (`row_major int x;` → E39026), are `pr: non-breaking`**: list the newly rejected forms and let the maintainer escalate (breaking = valid code users rely on, or ABI). A `check-pr-label` failure right after a label swap is a race. warn→error-by-version is a call-site if/else on `languageVersion` (no per-diagnostic knob); a 202c *error* form needs `SLANG_LANGUAGE_VERSION_202C` (OPEN PR only), a pure warning needs no atom.
- **A severity promotion needs a test that pins SEVERITY in never-emitted code**; message-only CHECKs pass either way.
- **"Is it breaking?" is a measurement**: master-vs-PR repro table, classified against the proposal; the label is the maintainer's.
- **Adjudicate "false-positive warning?" by diffing emitted target code**; run the discriminating control before relaying a mechanism (E36108 'llvm' was alias membership, not a linked-library leak).
- **API-path option bugs can't be `.slang` tests** (the CLI path is immune). `applySettingsToDiagnosticSink` double-applies, and an empty option set (the linked *composite*'s, not the module's) clobbers with defaults. Write a GPU-free `slang-unit-test`.
- **E36110/E36108 false positive on a public interface impl calling a portable stdlib fn** (`normalize`, #12755): inference is target-agnostic and a Public decl's set is clamped. Spurious = extra TARGET the impl merely supports; legit = extra SUB-CAP needed within a shared target.
- **E30082 (float→double) tags only scalar `double.__init(float)`**; vector/matrix go through one untagged generic init and warn silently (#12930); key off the concrete element `BaseType` at the coercion site. Its float-literal exemption is syntactic (a paren or `?:` around the literal warns), and since #11513 the lexer stores unsuffixed literals already float-rounded, so a value-exactness check needs the raw token text (#14057).
- Worked incident case studies are on the companion page (see end).

## Lua-Driven Diagnostic Definitions

New compiler diagnostics are added to `source/slang/slang-diagnostics.lua`, **not** the stale `slang-diagnostic-defs.h`. The parser accepts both `[attr]` and `[[attr]]` syntax; no-arg marker attributes need only two edits (`.meta.slang` + `.h`) ([Slang diagnostics are Lua-driven (slang-diagnostics.lua), not slang-diagnostic-defs.h](../learnings/1786010193246-slang-diagnostics-moved-from-slang-diagnostic-defs.md)).

`Diagnostics::Unimplemented` carries `Severity::Internal`, which triggers `SLANG_ABORT_COMPILATION` with a "file a GitHub issue" message, so it is wrong for user-correctable limitations; use a dedicated error diagnostic or `SLANG_ASSERT` ([Slang Diagnostics::Unimplemented is Severity::Internal — aborts compilation, wrong channel for user-actionable errors](../learnings/1781784301760-slang-diagnostics-unimplemented-is-severity-intern.md)).

Codes cited in issues/PRs go stale when the author's stacked branches have not landed; grep the live `slang-diagnostics.lua` for the next-free code ([Slang shader-coverage: 64-bit counter feasibility + diagnostic-numbering caveat (issue #11452)](../learnings/1780489631750-slang-shader-coverage-64-bit-counter-feasibility-d.md)).

## Diagnostics Catalog and regenerate.py

Generated catalog tests have **three divergent provenance stores**: per-file `//META`, bundle `README.md`, and `freshness.json`. `regenerate.py mark-fresh` updates only `freshness.json`, so hand-editing a `.slang` file also requires bumping its `//META` block ([Slang diagnostics-catalog generated tests have 3 divergent provenance stores; hand-fix must bump .slang META](../learnings/1780352287480-slang-diagnostics-catalog-generated-tests-have-3-d.md)).

`doc_section_digest` has inconsistent semantics (39 files share one hash, 224 hold all-zero placeholders), no deterministic Python computation, and an undefined per-section anchor meaning; naive LLM backfill manufactures unverifiable digests ([slang 11410 doc_section_digest backfill is not trivial — semantics underspecified, no deterministic Python computation](../learnings/1780354236062-slang-11410-doc-section-digest-backfill-is-not-tri.md)). Bundle-level drift detection lives in `_classify`/`cmd_list_stale`, not `cmd_verify`, and per-entry source pinning already exists at the CHECK level via lint rules, making `doc_section_digest` redundant ([slang #11410: catalog drift lives in _classify/cmd_list_stale (not cmd_verify) + per-entry CHECK-pin already exists](../learnings/1780355704625-slang-11410-catalog-drift-lives-in-classify-cmd-li.md)).

`regenerate.py` validates and lints generated tests but **does not generate them**; generation is LLM/operator-driven via prompt files. A warn-only lint guard scoped with `if not is_catalog:` silently misses placeholders reintroduced onto catalog files ([Slang diagnostics-catalog: regenerate.py is lint/tooling, not the generator](../learnings/1780358048390-slang-diagnostics-catalog-regenerate-py-is-lint-to.md)). The stale E30055 catalog test uses GNU elvis syntax (`b ?: 0.0`), which Slang doesn't support, so it is a parse error rather than a silent pass; the fix surface is the generation prompt, not `slang-diagnostics.lua` ([slang #11407 stale 30055 catalog test is a syntax error, not just scalar; fix surface is the gen prompt not slang-diagnostics.lua](../learnings/1780347335365-slang-11407-stale-30055-catalog-test-is-a-syntax-e.md)).

## stdlib Deprecation: Two Separate Mechanisms

Deprecating a core-module function AND hiding it from the generated online docs combines `[deprecated("message")]` (compiler warning) with the `//@hidden:` line-comment pragma (doc exclusion); neither alone does both ([Slang stdlib: deprecate-and-hide-from-docs = [deprecated()] + //@hidden: (two separate mechanisms)](../learnings/1780918035054-slang-stdlib-deprecate-and-hide-from-docs-deprecat.md)). The parsed token is `"hidden:"` (no `@`), and ByteAddressBuffer deprecation must cover all three buffer type variants ([Slang core-module: deprecate-but-hide-from-online-docs is achievable today](../learnings/1780943246982-slang-core-module-deprecate-but-hide-from-online-d.md)).

## FileCheck Format: `warning[ECODE]`, Not `warning NNNNN`

Slang renders diagnostics as `warning[ENNNNN]:` (brackets). A `// CHECK-NOT: warning 30856` (or `warning 41012`) never matches the real text and passes vacuously, asserting nothing. Assert `CHECK-NOT: E30856`, `[E30856]` or `warning[41012]`, and verify by running the bug-present binary ([Slang warnings render as warning[ECODE] — CHECK-NOT: warning NNNNN is vacuous](../learnings/1780600389554-slang-warnings-render-as-warning-ecode-check-not-w.md)).

## Pragma Warning Scope Across Files

Each `__include`d module file gets a fresh preprocessor whose `absoluteSourceLocCounter` starts at 0, causing **cross-file absolute-location collisions** in the shared `WarningStateTracker` timeline. Also, `addPragmaPop` restores all diagnostic IDs on pop (not just those the push/pop touched), which can shadow root-file disables ([Slang cross-file #pragma warning scope breaks via absolute-loc collision](../learnings/1780594750097-slang-cross-file-pragma-warning-scope-breaks-via-a.md)).

## Rich Diagnostic Renderer and Callback API

The rich renderer has two known bugs: a zero-width EOF span duplicates the last character (color path only), and codepoint-based columns are indexed by byte offsets, corrupting multibyte characters ([slang rich diagnostic renderer mishandles zero-width EOF span and byte-vs-codepoint columns](../learnings/1782151944896-slang-rich-diagnostic-renderer-mishandles-zero-wid.md)). `SlangDiagnosticCallback` has no severity parameter and covers only the legacy compile path; severity exists internally but is flattened at the public boundary, and the maintainer roadmap is the Rich Diagnostics rewrite, not bolt-ons ([Slang diagnostic-callback API: legacy + severity-less; diagnostics roadmap is the Rich Diagnostics rewrite](../learnings/1782215106250-slang-diagnostic-callback-api-legacy-severity-less.md)).

**The render layer already supports SourceRange, so a range-underline feature is not a rendering change** (#10476). `DiagnosticSpan` is `{ SourceRange range; String message; }`, and `makeLayoutSpan` underlines the full range when `begin != end`, falling back to a single-token caret when `begin == end`. The range is flattened in the authoring/plumbing layer: the DSL `getLocationExpr` maps every typed location to ONE SourceLoc, and codegen emits `result.primarySpan.range = SourceRange{<single loc>}` (the single-arg ctor makes begin==end) — that is the choke point. "Span accepts a SourceRange" is a small additive DSL+codegen change; "AST/IR insts *store* SourceRange" (~668 / ~313 sites + serialization) is a large representation change for separate maintainer-designed follow-ups ([slang rich-diagnostics render layer already supports SourceRange; only authoring/plumbing collapses to one loc](../learnings/1783523470770-slang-rich-diagnostics-render-layer-already-suppor.md)).

**Adding a multi-mode type-display flag** (e.g. type-alias "aka" annotations): copy the `DiagnosticColor` option pattern and put mode-dependent decoration in the diagnostics formatter, where the sink is reachable, not in `Type::toText`, which has no sink context ([Slang: adding a diagnostic type-display flag — DiagnosticColor template + toText has no sink context](../learnings/1782215211806-slang-adding-a-diagnostic-type-display-flag-diagno.md)).

## Severity Changes and PR Labels

**warn→error and newly diagnosing meaningless code are non-breaking.** Breaking means breaking valid code or ABI. The maintainer reverted a `pr: breaking change` label to `pr: non-breaking` for a `[[vk::location]]` misuse escalation (#6216), and a warn→error on invalid/miscompiling code may keep its original warning-class label even when it becomes a hard error in some contexts ([warn→error on an invalid *misuse* can still be labeled pr: non-breaking (maintainer call, slang #6216)](../learnings/1782716774890-warn-error-on-an-invalid-misuse-can-still-be-label.md)). `spirv_asm` escalations follow it: #12506 (E29118) shipped `pr: non-breaking`, as does PR #13809's E29103 note→error (open as of 2026-10-22). A brand-new error on code with no possible effect is the same: #12992 made `row_major int x;` (a layout keyword on a non-matrix, previously ignored) report E39026; the bot labeled it `pr: breaking change` (a peer reviewer agreed, citing #12840) and jkwak-work relabeled it `pr: non-breaking` ("the braking cases don't seem like a properly cases to worry about"). Default: label `pr: non-breaking`, list the newly rejected forms in the PR body, and let the maintainer escalate; reserve `pr: breaking change` for ABI/API changes or rejecting code real users plausibly rely on. CI trap: during a maintainer label swap, `check-pr-label` can run between unlabel and label, fail, and fire a `github.ci_failed` webhook that passes on the automatic rerun a minute later; compare `issues/<n>/events` label timestamps with the check-run `started_at` before treating it as real ([newly diagnosing meaningless code is pr: non-breaking](../learnings/1790877742239-slang-pr-label-newly-diagnosing-meaningless-code-i.md)).

**A severity promotion needs a test that pins the SEVERITY, in code that is never emitted.** When a diagnostic moves from `standalone_note`/`warning` to `err` (spirv_asm E29103, #13809), an existing DIAGNOSTIC_TEST whose CHECKs match only message text passes under both severities. Annotate severity and code together (`^^^ error E29xxx`), and add a case where the bad code is never emitted (an unused function, or a `__target_switch` `case spirv:` arm compiled with `-target hlsl`) — the only place behavior visibly changes, since emitted code usually crashed before. Prove the pins FAIL on master with master's own build: the atom suggests `slang-test -bindir <master>/build/Debug/bin`, but `-bindir` does not switch the compiler for SIMPLE or COMPARE_COMPUTE runs (see [Release-Build Divergences](slang-build-release-divergences-and-sanitizers.md)), so run master's `slang-test` from the master tree root ([pin the SEVERITY in never-emitted code](../learnings/1792580635936-promoting-a-slang-diagnostic-note-error-pin-the-se.md)).

**warn→error by language version is a call-site if/else**, picking the error-struct or the warning-struct; there is no per-diagnostic warnings-as-errors knob. Copy the `volatile` modifier (`slang-parser.cpp:10284-10296`): ERROR `RemovedModifierUsage` when `languageVersion >= SLANG_LANGUAGE_VERSION_2026`, else WARNING `DeprecatedModifierUsage` when `>= 2025`, reading `parser->currentModule->languageVersion`. `UnintendedEmptyStatement` (code **20101**, a `warning(...)` at `slang-diagnostics.lua:979-984`) is emitted **entirely in the parser**: `Parser::ParseStatement(Stmt* parentStmt)` fires it only when `as<IfStmt>(parentStmt)`, and a bare `;` parses to a fieldless `EmptyStmt` sentinel (`{}` → `BlockStmt`), so `as<EmptyStmt>` distinguishes a stray semicolon with no false positives on empty blocks. for/while/do/catch/defer are silent only because their body-parse sites call `ParseStatement()` with no parent; threading the parent (or post-checking the returned `EmptyStmt`) there is the single extension hook (#12296). A 202c-gated *error* form depends on `SLANG_LANGUAGE_VERSION_202C`, which exists only in OPEN PR #12179; a pure-*warning* extension needs no version atom and ships independently ([Empty-statement lint (UnintendedEmptyStatement 20101) is a parser check keyed on parent-stmt type](../learnings/1785434273353-empty-statement-lint-unintendedemptystatement-2010.md)).

**"Is it breaking?" is answered from the compiler, not the design's intent.** On #13537 a maintainer asked "so this could be a breaking change? By design it shouldn't be". A first draft said "no" and called every break intended; OUTPUT_REVIEW found three errors: the quoted repros were existing code that compiles on master and fails on the PR (so "yes, as implemented"); "the integer format param was never documented" was false, since the old alias carried `/// @param format` (grep the BASE commit's doc comments, not only `docs/`); and a test edit was attributed to the wrong root cause (read the actual diff line first). Method: write 5-8 minimal repros, compile each on a master control build and the PR build, tabulate exit codes and error text, classify each break against the proposal as explicitly covered, a consequence of the design, or not covered, and leave the label to the maintainer (["is it breaking?": answer from the compiler, not the design doc](../learnings/1791569984990-is-it-breaking-answer-from-the-compiler-not-from-t.md)).

## validateEntryPoint Has No Cross-Entry-Point SV Aggregation

For "Slang accepts conflicting/duplicate system-value semantics" bugs (#11855 multiple depth outputs; umbrella #6319) the front-end gap is **structural**: `validateEntryPoint` validates SV semantics per parameter, so a conflict that exists only between two params is invisible. Closing it needs an aggregation pass, not a per-case special ([Slang validateEntryPoint validates SV semantics per-param with NO cross-entry-point aggregation (#11855)](../learnings/1782860967918-slang-validateentrypoint-validates-sv-semantics-pe.md)).

## C++ API Option Plumbing: the Empty-Option-Set Clobber (DiagnosticColor)

Setting `CompilerOptionName::DiagnosticColor = ALWAYS` via `SessionDesc::compilerOptionEntries` colored only pre-codegen diagnostics; target-stage ones came out ASCII, while CLI `-diagnostic-color always` worked for both (#11890/#11891, HEAD f490a52aa). `ComponentType::getTargetArtifact` layers two option sets onto one sink in sequence — `linkage->m_optionSet` (holding the API value), then the component's own `m_optionSet` — and `applySettingsToDiagnosticSink` applies color UNCONDITIONALLY while `getIntOption` returns the default (AUTO) for an absent option, so the empty second layer clobbers ALWAYS with AUTO (→ `isConsole()` → no color on an in-memory blob). Fix: guard on presence, `if (options.hasOption(CompilerOptionName::DiagnosticColor))` ([Slang API compiler-options: applySettingsToDiagnosticSink double-apply clobbers with defaults; API-path bugs need slang-unit-test not .slang](../learnings/1782929205990-slang-api-compiler-options-applysettingstodiagnost.md)).

**Which set is empty:** not the loaded module's — `Module`'s ctor copies `linkage->m_optionSet` (`slang-module.cpp:27`), which is why module-load diagnostics ARE colored — but the linked **composite**'s: `CompositeComponentType`'s ctor (`slang-linkable-impls.cpp:48`) does not copy linkage options and is populated only by `linkWithOptions()`, and `getTargetCode` runs through that composite ([CORRECTION to #11890 diagnostic-color learning: the empty option set is the COMPOSITE component's, not the loaded module's](../learnings/1782933741329-correction-to-11890-diagnostic-color-learning-the-.md)). `hasOption` reliability is **path-specific**: on `getEntryPointCode`, keys like Optimization are force-materialized to their default (so `hasOption(Optimization)` false-positives), but on the `getTargetCode` composite path `DiagnosticColor` is genuinely absent-vs-set, so the guard is a real signal; a revert-drill unit test (set K non-default in an earlier layer, assert it survives the empty layer) falsifies force-materialization cleanly ([hasOption(DiagnosticColor) IS reliable on the getTargetCode composite path (unlike Optimization on getEntryPointCode)](../learnings/1782934361227-hasoption-diagnosticcolor-is-reliable-on-the-getta.md)).

**Testing:** such an API-path bug CANNOT be a `.slang` slang-test (the CLI color path bypasses the double-apply). Write a GPU-free `slang-unit-test` that sets the option in `SessionDesc`, `loadModuleFromSourceString`s a shader producing a target-stage diagnostic, calls `getTargetCode`, and asserts the blob contains an ANSI escape `\x1b[`.

## False Positives: Adjudication and Known Families

**Adjudicate by diffing emitted code.** When a maintainer disputes whether a diagnostic (e.g. uninitialized-field E41021) is real or spurious, compile the divergent cases and **diff the emitted target code**; output behavior settles what argument about intent does not ([1783019615446-adjudicate-false-positive-warning-disp](../learnings/1783019615446-adjudicate-false-positive-warning-disputes-by-diff.md)).

**E41017 (uninitialized global) on `export __global __extern_cpp` host globals (#12006, a #11989 spinoff).** `checkUninitializedGlobals` warns on globals whose value the host supplies at runtime (the documented "set a global via host code" pattern). Its exemption set covers `IRSemanticDecoration`/`IRGlobalInputDecoration`/`IRVulkanHitAttributesDecoration` but not `IRExternCppDecoration`, which belongs there. Exempting is false-negative-safe: the diagnostic fires only with NO init block AND NO `Store` use. Predicate width (bare `IRExternCppDecoration` vs. that AND export linkage) is a maintainer call ([slang#12006 E41017 false-positive on export __global __extern_cpp host-provided globals](../learnings/1783545729206-slang-12006-e41017-false-positive-on-export-global.md)).

**E36108 'llvm' is alias membership, not a linked-library leak (#12007, a #11989 spinoff).** `[require(sm_6_0)]` + a GPU-only op reports "dependencies not compatible on target 'llvm'" even for `-target spirv`. "llvm is auto-available because slang-llvm is linked" is WRONG, refuted by two controls (it reproduces on a Debug slangc with no libslang-llvm.so; `[require(spirv_1_3)]` + the same op compiles clean). The `sm_6_0` alias lists cpp+llvm as target disjuncts, and the public-decl consistency check requires the body to be implementable on EVERY named disjunct; `llvm` is named only because it is highest-ordered among the failing atoms. Fix: narrow to `[require(spirv, sm_6_0)]` at use sites (zero-risk) vs. drop cpp/llvm from the `sm_*_version` aliases (high blast radius). Run the 30-second discriminating control before relaying a plausible mechanism ([slang#12007 E36108 'llvm' false-positive is the sm_6_0 alias listing cpp/llvm, NOT auto-available-because-linked](../learnings/1783547031032-slang-12007-e36108-llvm-false-positive-is-the-sm-6.md)).

## E36110/E36108 Interface-Conformance False Positive (#12755)

The same target-agnostic inference root produces a spurious interface-conformance failure: a `public struct` implementing a `public interface`, whose method calls a portable stdlib fn like `normalize`, fails with **E36110** ("uses capability 'cuda_sm_2_0' that is incompatable with the interface requirement") or **E36108** ("dependencies not compatible on target 'llvm'") even for `-target hlsl`; dropping `normalize` fixes it, and a non-exported impl compiles fine.

Root cause (source-verified on master): stdlib fns advertise the targets they WORK ON, not what they NEED — `normalize` is `[require(cpp_cuda_glsl_hlsl_metal_spirv_wgsl_llvm, sm_4_0_version)]` and `sm_4_0_version` includes `_cuda_sm_2_0`. Front-end inference is target-agnostic (`_propagateRequirement` UNION-joins every callee's full `[require]` across ALL targets; `-target` applies only in later IR passes), so the cuda atom reaches the impl's inferred set. Public/internal asymmetry (`slang-check-decl.cpp:20975-21020`): a non-empty inferred `[require]` on a Public decl is CLAMPED to declared caps and the witness-table check (`checkCapabilityRequirement(MustHaveEqualAbstractAtoms, ...)`, `:~21168`) fires; an internal decl takes the JOIN path, whose gate needs an `ExplicitlyDeclaredCapabilityModifier`. In Slang 2026+ a member inherits its parent's visibility, so a `public struct`'s method is Public without its own keyword. E36108 and E36110 are one defect routed by `hasTargetAtom`: E36108 on a target-set COUNT mismatch (extra bare TARGET atoms, `slang-capability.cpp:1459-1477`), E36110 on an extra SUB-CAP within a shared target (per-stage loop, `:1537`).

**Discriminator:** an extra abstract-TARGET atom the impl merely SUPPORTS is spurious (must not fail); an extra SUB-CAP the impl NEEDS within a shared target is legit (must keep failing, e.g. `capability2.slang`'s `spvGroupNonUniformArithmetic` within spirv). Scoped fix on the witness-table path: explicit-`[require]` impls keep `MustHaveEqualAbstractAtoms`; inferred-only impls use `AvailableCanHaveSubsetOfAbstractAtoms` against the requirement PROJECTED to the requested compile targets, falling back to strict with no concrete targets (module precompile / language-server `SLANG_TARGET_UNKNOWN`). `isTargetVersionAtom` (`slang-capability.cpp:167`) covers spirv/metal/hlsl/glsl but omits cuda SM atoms, so a version-vs-feature cut is unsound. Repro on master with a hand-written public interface + public struct (no structural-RT module): an arithmetic body compiles clean, a `normalize` body yields E36108 ([E36110/E36108 false positive: public interface impl calling portable stdlib fn inherits its full cross-target [require]](../learnings/1787690962502-e36110-e36108-false-positive-public-interface-impl.md), [E36108/E36110 interface-conformance false positive: target-agnostic inferred caps treated as impl contract](../learnings/1787698928314-e36108-e36110-interface-conformance-false-positive.md)).

## E30082 float→double Tags Only Scalar Conversions (#12930)

**E30082** ("implicit float→double conversion") is emitted in `SemanticsVisitor::_coerce` (`slang-check-conversion.cpp:2883-2892`) only when `site == CoercionSite::Argument`, the chosen conversion initializer carries `kBuiltinConversion_FloatToDouble` (via `getImplicitConversionBuiltinKind`, `:336-344`), and `fromExpr` is not a `FloatingPointLiteralExpr`. That tag is stamped only on the per-pair SCALAR `double.__init(float)` from the base-type meta-loop (`core.meta.slang:1213-1224`, 2-arg `__implicit_conversion($(cost), $(builtinConversionKind))`). Vector and matrix conversions use ONE generic init (`vector<T,N>`'s `__generic<U:__BuiltinFloatingPointType> __init(vector<U,N> other)`, `core.meta.slang:2412-2417`, plus matrix/coop-vector analogs) with a 1-arg `__implicit_conversion($(cost))`, so the kind defaults to `kBuiltinConversion_Unknown` and they warn SILENTLY. Tagging the generic init is wrong: it covers every float-family element conversion (including double→float narrowing and half→float). The principled fix reads the CONCRETE element `BaseType` at the emission site (peel `VectorExpressionType`/`MatrixExpressionType` to the element `BasicExpressionType`; warn when from==`BaseType::Float` && to==`BaseType::Double`), covering scalar/vector/matrix uniformly and retiring the scalar-only tag machinery. Decl-level conversion-kind tags in `core.meta.slang` work only for non-generic per-pair inits; a diagnostic covering aggregates keys off concrete types at the coercion site. E30082 had no test coverage (diagnostics-catalog) ([E30082 float→double warning only tags scalar conversions; generic vector/matrix inits can't carry the tag](../learnings/1788791945839-e30082-float-double-warning-only-tags-scalar-conve.md)).

**The literal exemption is syntactic, so a wrapper defeats it (#14057).** E30082 is a performance warning: it fires only at `CoercionSite::Argument` and skips a `fromExpr` that is a bare `FloatingPointLiteralExpr` (`slang-check-conversion.cpp` ~:3006-3015 on current master). Any wrapper around the literal therefore warns [E30082 literal exemption is syntactic; unsuffixed float literals are rounded at lex time](../learnings/1793311782255-e30082-literal-exemption-is-syntactic-unsuffixed-f.md):

- `takeD((10e+16))` warns, because the literal is inside a ParenExpr.
- `takeD(c ? 10e+16 : 1.0)` warns, because the `float` `?:` expression is what gets converted, not the literal; it warns even when the value is exact.
- `takeD(10e+16)`, `d * 10e+16`, `double x = 10e+16;`, assignment and return are all silent.
- `-lit` stays a bare literal, because the parser folds the minus into a new literal (`slang-parser.cpp` ~:10279).

Since #11513 (2026-06) the lexer parses an unsuffixed or `f` decimal literal directly as `float` (`slang-lexer.cpp` ~:1332), so `FloatingPointLiteralExpr::value` is already rounded, and a check of whether the value is exact in `float` needs the raw `LiteralExpr::token` text, which is not a FIDDLE field. Builds before #11513 (2026.10.2, 2026.11) emit the same rounded CUDA value, so this is not a regression. For a value-based conversion warning, the precedent is E40016 IntegerConstantOverflow in the same `_coerce` block (~:2884), which runs for the Argument, Initializer, Assignment and Return sites and skips the core module [E30082 literal exemption is syntactic; unsuffixed float literals are rounded at lex time](../learnings/1793311782255-e30082-literal-exemption-is-syntactic-unsuffixed-f.md).
