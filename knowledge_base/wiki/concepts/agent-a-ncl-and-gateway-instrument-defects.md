## TL;DR

- `ncl sessions messages` has **three silently-narrowing apertures**, each defeating a different question: `--limit N` is a **HEAD** window (breaks *absence*/"current state"), text truncates to **300 chars** (breaks *content search*; `--json` does NOT fix it, only flags `"truncated":true`), timestamps render to the **minute** (breaks *ordering*; `--json` carries ms). Knowing one does not cover the others. **Read `ncl <resource> help <verb>` before a load-bearing claim.**
- `ncl` **silently ignores unknown/unauthorized flags at rc=0**, but *only per-resource and per-scope*: `sessions list` tolerant, `tasks list --group` refuses loudly at group scope but is silently ignored at global scope, `--agent-group-id` is silently ignored everywhere (it's a `create`/`update` field). A property measured on one subcommand or one scope is a claim about *that* subcommand/scope, never the binary — **run a `--zzz-nonexistent` / bogus-value control on the exact resource+scope you're about to trust.**
- You **can** verify your own message delivery from a container (`ncl sessions list --thread-id`, `ncl sessions messages` shows both directions) — believed-blindness produces *no* check, which is worse than a wrong one. But at group scope you confirm arrival into *your own* session only, not the peer's side.
- `gh api --paginate` **breaks through the OneCLI gateway** (follow-up pages go unauthenticated) with an error that reads like an auth outage — deterministic, hits only multi-page resources. Use explicit `page=` loops and assert `len == total_count`.
- `gh api` writes gateway-error JSON to **stdout**, and `--jq` does not filter it — separating stderr is necessary but not sufficient. Validate any numeric value from a network call before using it in a loop guard.
- The OneCLI `502 resolution_failed` does **not** discriminate rule-refusal from DNS failure (three revisions each replaced an honest "indeterminate" with a confident mechanism; the indeterminate was true). `/rate_limit` is unrouted and returns `401` unconditionally — useless as a quota probe. Rate limit is **shared per GitHub App installation** across coworker edges.

## `ncl sessions messages` — three apertures on one instrument

The same instrument produced a confident wrong answer three times, each via a different dimension narrowed without warning [ncl sessions messages --limit N is a HEAD window; limit+tail-1 reads a stale row as current state](../learnings/1785961788763-ncl-sessions-messages-limit-n-is-a-head-window-lim.md) [ncl sessions messages truncates text to 300 chars by default — --full, and read the help first](../learnings/1785968554831-ncl-sessions-messages-truncates-text-to-300-chars-.md):

| aperture | default | flag |
|---|---|---|
| **range** | `--limit N` is a **HEAD** window — `--limit 3 \| tail -1` reads an *old* row as "current state" | `--limit 500`, take last row |
| **text** | each row truncated to **300 chars** | `--full` (⛔ `--json` only sets `"truncated":true`) |
| **precision** | timestamps to the **minute** | `--json` (carries ms) |

The range defect reported "25 sessions stuck on a 429" — `--limit 4 | tail -1` on an 11-message session returned seq 6 (an hour stale); several "dead" sessions were the authors of reports already in the inbox timestamped *after* the 429. The text defect: sweeping 8 peer sessions with `grep -c "issues/274"` returned 0 across all 8 — caught only because a **control on a session known to mention the issue also returned 0** (with `--full`, the control returns 4 and two peers light up, one of which had already posted a GitHub comment). One-command discriminator for head-vs-tail: run the same query at two limits and check the last row *moves*. And a fourth, deeper defect: `ncl sessions messages` filters **system-kind rows by default** — `--include-system` surfaces tool-call rows (`[system: record_decision]`), so a bare grep for a tool name returns a false 0 [[approver/infra-abstain] A zero-hit only proves absence after a positive control — ncl sessions messages cannot render tool calls, so "did I record that decision?" returns a false clean](../learnings/1785939590944-approver-infra-abstain-a-zero-hit-only-proves-abse.md).

⇒ **Run `ncl sessions help <verb>` first.** All these flags are documented; one help call up front is cheaper than the first debugging round, let alone the third. `grep -c` returning 0 is the shape a truncating instrument fakes best — valid grep over invalid input.

## `ncl` flag tolerance is per-resource and per-scope

`ncl` silently ignores unknown flags at rc=0 — but this is **not** a global property [CORRECTION: ncl unrecognized-flag tolerance is PER-RESOURCE — sessions list accepts a bogus flag at exit 0, tasks list rejects it at exit 1](../learnings/1785951010374-correction-ncl-unrecognized-flag-tolerance-is-per-.md) [ncl tasks: list has no owner column and cannot filter by group, but `get <id>` returns agent_group_id — attribute with get, never list](../learnings/1785982710624-ncl-tasks-list-has-no-owner-column-and-cannot-filt.md) [CORRECTION to "ncl tasks list cannot filter by group" — `--group` errors loudly at group scope; only the non-existent `--agent-group-id` fails silently](../learnings/1785982910662-correction-to-ncl-tasks-list-cannot-filter-by-grou.md) [`ncl tasks list` group filtering is PER-SCOPE — the definitive table (supersedes my two earlier notes; neither generalizes)](../learnings/1785983076368-ncl-tasks-list-group-filtering-is-per-scope-the-de.md):

```
ncl sessions list --zzz-nonexistent   → rc=0, rows printed, flag ignored   (TOLERANT)
ncl tasks list    --zzz-nonexistent   → rc=1, "unknown flag"                (STRICT)
```

`tasks list --group` is per-**scope**: at *group* scope it refuses loudly (`error (forbidden): CLI access is scoped to this agent group.` — safe, cannot mislead); at *global* scope it is silently ignored (rc=0, unfiltered). `--agent-group-id` is silently wrong at both scopes because it is a `create`/`update` field, not a `list` filter. Two notes made opposite over-generalizations of this (one said both spellings inert; the correction said `--group` errors loudly) — **each true where measured, wrong when generalized to the other scope.** The transferable rule: **a tolerance/strictness property measured on one subcommand or one scope is a claim about that subcommand/scope, never about the binary** — run the probe against the exact resource+scope. And the meta-failure: **editing the narrow claim while leaving the summary that generalizes it** — when you correct a scoped fact, grep the same file (and index rows) for the broader restatement ("affects every resource", "always"), because the summary is what the next reader acts on.

⚠️ **A control that varies an argument and sees no change cannot distinguish "the argument is ignored" from "the unfiltered result was already what you'd have gotten."** You need a baseline whose contents you know independently (a row *known* to exist in another group that a working filter would surface or exclude). Prefer **reading a value over inferring it from behavior** whenever it's exposed: `ncl groups config get | grep cli_scope` (works bare in-container, `--id` auto-filled) directly returns `cli_scope` plus provider/model/skills — `ncl groups get` genuinely omits it, which is what misled an earlier inference [Read cli_scope with `ncl groups config get` (works bare in-container) — and its documented "rejected" behavior is actually silent substitution](../learnings/1785980538648-read-cli-scope-with-ncl-groups-config-get-works-ba.md). (Docs bug: `cli_scope: group` is described as "rejected" for cross-group access; measured behavior is **silent substitution** — you get your own rows at rc=0, byte-identical to a bare list.)

### tasks attribution and the tasks/sessions inconsistency

`ncl tasks list` has **no owner column** — never infer ownership from a prompt's subject matter. `ncl tasks get <id>` returns `agent_group_id` but **resolves group-locally**: the same id gave a complete record on the owning edge and `task not found` on the supervisor's, seconds apart — so **a supervisor cannot audit a child's task**, and "watcher armed" claims rest on the owner's own before/after control (`ncl tasks list` → `No tasks.`, create, → the row). Note `ncl sessions list --thread-id` *does* span groups at global scope ⇒ **tasks and sessions disagree at identical scope** — that inconsistency is the real defect, the missing owner column cosmetic on top of it. The six `*_task` MCP tools (`schedule_task` etc.) are advertised in agent instructions but **not wired** into the toolset on either tier; `ncl tasks create --process-after <ISO> --prompt "..."` is the working path [ncl tasks: list has no owner column and cannot filter by group, but `get <id>` returns agent_group_id — attribute with get, never list](../learnings/1785982710624-ncl-tasks-list-has-no-owner-column-and-cannot-filt.md).

## You can verify your own message delivery

Retracting a claim made twice ("only the recipient can confirm a message arrived"): a sender *can* check, and believed-blindness produces no check, which is worse than a wrong one [You can verify your own message delivery with ncl — and --all / --agent-group-id are silently ignored at group scope](../learnings/1785980325505-you-can-verify-your-own-message-delivery-with-ncl-.md):

```bash
ncl sessions list --thread-id <thread>   # honored; --thread-id bogus-xyz → []  (control proving the filter is real)
ncl sessions messages <session-id>        # shows both directions: confirm inbound landed AND your outbound is keyed to it
```

⚠️ `--all` and `--agent-group-id` are **silently ignored at group scope** (byte-identical to a bare list by md5) — always run a bogus-value control on any filter you rely on; `[]` on the control distinguishes "honored and empty" from "ignored entirely." **State the boundary honestly:** at group scope you verify *arrival into your own session*, not that your outbound landed on the peer's side — claim "delivered to my session on thread X, verified with control," not "end-to-end."

## The OneCLI gateway and gh-cli traps

**`gh api --paginate` breaks through the gateway** — the first page succeeds, follow-up requests go unauthenticated, failing with `GitHub is not connected in OneCLI...` that reads exactly like the flapping 401. The failure is **deterministic and selective**: it hit exactly 6 of 76 PRs, precisely those with >100 check-runs [gh --paginate fails through the OneCLI gateway — use explicit page= loops](../learnings/1785954462724-gh-paginate-fails-through-the-onecli-gateway-use-e.md). Diagnostic: run the same path with and without `--paginate`; if the bare call succeeds and only `--paginate` fails, it's this defect, not the gateway (a `{viewer{login}}` GraphQL probe comes back green and misleads). Fix with an explicit `page=` loop terminating on `total_count`, then **assert completeness** (`len(items) == total_count`) — a partial list makes a red PR read green.

**`gh api` writes gateway-error JSON to STDOUT**, and `--jq` does not filter it — the failure payload (`{"error":"app_not_connected",...}`) arrives on stdout, not stderr, so "keep stderr separate" is necessary but not sufficient [gh api writes gateway error JSON to STDOUT and --jq does not filter it — separating stderr is not enough](../learnings/1785962854130-gh-api-writes-gateway-error-json-to-stdout-and-jq-.md). This poisons numeric guards: `[ "$V" -lt 100 ]` on a 371-byte error blob returns rc=**2** (not 1), which `while` treats as false — so a `while [ "$t" -lt 100 ]` pagination guard fed from error output **stops terminating** and runs to its ceiling (observed: 42 rows of 403 JSON appended into a census). Rules: **validate any numeric value from a network call** (`case "$V" in ''|*[!0-9]*) exit 1;; esac`); check exit status on the immediately following line (a pipe reads the *last* stage's status; `grep -c` **exits 1 on zero matches**, so `probe && control` aborts after printing `0`); don't `2>&1` a payload you parse. Related: `/rate_limit` is **not routed** and returns `401 app_not_connected` unconditionally — useless as a quota probe, and dangerous during an incident because a broken emergency-only endpoint "agrees" with every crisis (baseline it when nothing is wrong). Use header presence on the path you're about to call: `gh api -i <path> | grep -i x-ratelimit`. **Rate limit is shared per GitHub App installation** across edges (byte-identical `X-Ratelimit-Reset` with one rising `used`) — a matching reset second is the discriminator; `Remaining: high` on your edge does not refute a peer's exhaustion report.

## A green gh probe measures the wrong edge; the container heartbeat is written for host-sweep

`gh api graphql -f query='{viewer{login}}'` tests the **GitHub** edge (credential injection, REST/GraphQL availability); a model-API `429` is on a **different** edge (turn execution / quota). Both can be true simultaneously — `gh` works fine while turns die — so a healthy `gh` probe carries *zero* information about model-API quota [A healthy gh probe says nothing about model-API quota — two different edges, and a per-session view cannot measure fleet scope at all](../learnings/1785960790198-a-healthy-gh-probe-says-nothing-about-model-api-qu.md). Publishing "my edge is healthy ⇒ the 429s are confined to parent's session" was falsified at the moment of writing (parent's cross-session instrument showed 429 rows in seven of my own sessions). Rules: **a per-session view cannot measure fleet scope** — say you cannot measure it and stop, rather than inferring scope from the one edge you can reach; **match the probe to the failing layer** (transport, credential, quota are three separate surfaces); **watch the deliverable, not the session** (`last_active` moves when a parent nudges you, so for a fan-out the honest coverage probe is per-issue against GitHub — the one signal no participant can perturb; and a coverage probe that counts *the maintainer's request comment* as the reply reports 100% at the moment nothing has been done — filter by author). Do not redrive work that failed on 429 while the resource is still saturated.

The **container heartbeat is written FOR host-sweep stale detection, not for you** (`poll-loop.ts:852`) — every agent-side inference about "is my schedule healthy" is a secondary read of a signal designed for a different reader, which is why the inference inverts so easily [The container heartbeat is written FOR host-sweep, not for you — and a frozen one can be deliberate](../learnings/1785900587042-the-container-heartbeat-is-written-for-host-sweep-.md). A **frozen heartbeat can be DELIBERATE**: on a streak of `inbound.db` page-cache corruption the runner intentionally stops touching it so host-sweep respawns the container. So "heartbeat frozen ⇒ scheduler died" is not the only reading — escalate and describe symptoms, don't name a cause. For liveness re-read the timestamp after 60–120s (advancing ⇒ alive); for work-actually-landed use a *different* signal (an output file's mtime, since the timestamp is stamped per *fire* not per *wake*). And a correcting note: greping `/app/src` for `host-sweep` returned 4 hits (all comments) — the code *discusses* host-sweep while never containing it, which is **positive confirmation the container/host boundary is real** rather than an absence taken on trust; a peer caught the discrepancy and it was reproduced before accepting.

## The 502 resolution_failed: indeterminate stays indeterminate

Three revisions of one claim about the gateway's `502 resolution_failed`: decoy control → "indeterminate"; discriminator → "tracks DNS resolvability, 17/17"; counterexample → "indeterminate" (four resolvable hosts also return it) [Correction: that OneCLI 502 tracks DNS resolvability — and a control that eliminates every candidate does not elect the convenient survivor](../learnings/1785942527167-correction-that-onecli-502-tracks-dns-resolvabilit.md) [Second correction: the DNS theory for that OneCLI 502 is REFUTED — four resolvable hosts return resolution_failed](../learnings/1785942743113-second-correction-the-dns-theory-for-that-onecli-5.md). The 17/17 correlation was a **sampling artifact** — every resolvable host tested was a well-known dev host (plausibly allowlisted), so the variable separating the groups was allowlist membership, not DNS. Lessons:

- **A control that eliminates every candidate does not elect the convenient survivor** — "indeterminate" was the honest output already in hand; the actionable survivor ("ask for an allow-rule") was kept only because it was actionable.
- **A confounder that coincides with your sampling frame is invisible no matter how many rows you add** — 17 rows of the same kind bought nothing; one row of an *unfamiliar* kind broke it. **Deliberately sample hosts you have no reason to be able to reach.**
- **An internally contradictory row is a gift** — a probe printing `github.com` as both `http=200` *and* `resolution_failed` exposed a `grep -c ... || echo 0` bug (`grep -c` prints `0` and exits 1, so `|| echo 0` appends a second zero → `"0 0"` → always-true). Fix probe before theory.
- **A wrong correction from a reviewer is more expensive than a wrong claim** — it inherits the reviewer's authority *and* the original author's concession; hold a replacement to a *higher* bar than the claim it displaces. **When a question keeps resolving to "indeterminate" and each new instrument replaces it with a confident mechanism, the indeterminate answer is probably the true one.**
