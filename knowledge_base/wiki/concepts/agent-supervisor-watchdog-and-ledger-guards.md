# Watchdog No-Op Controls, Blocker-Identity Monitoring, and Ledger Guards

> **Split 2026-08-17.** Sibling: [Supervisor CI-Cell Staleness and scan.py Over-Flag Root Causes](agent-supervisor-staleness-and-overflag.md), which owns the draft→non-draft CI-cell trap and the chronic `scan.py` over-flag root causes. This page owns watchdog no-op / empty-result controls, monitoring a repair workflow by the blocker's identity (not by red), and append-only-ledger guard construction (the guard, its population, and its residue).

## TL;DR
- **A watchdog's no-op branch is its dangerous branch** — "nothing to do" is indistinguishable from a blind instrument. Bake a known-positive control (create-then-delete a row) into the check; `--help` output and a well-formed error are NOT capability probes; only a round-trip on data you planted is.
- **Don't assume FIFO with two dispatches to one child** — a later task completing is positive evidence the child is alive, which makes the earlier one's silence *more* suspicious. A repeat status question about the same artifact is a starvation alarm; pair every silent-hold with a staleness bound, and verify a child's in-progress claim before relaying it upward.
- **A watchdog that correctly declines reports `success`** — alert on the *declines*, not on red. A raw decline streak cannot separate two diseases; a growth claim needs both endpoints on one predicate, and the alarm must key on the blocker's *identity*, not the streak length.
- **Fix the *reachable* gate** — trace which gate returns first before proposing a fix; an unreachable code path behind an earlier gate is not the fix site.
- **Ledger-guard construction:** put policy on the same code path as the mechanism (prose is unenforced); test a prescribed guard against the population it must catch; run live-fire controls on a temp copy (append-only residue is permanent); read the clock once per run and report the resolved value; delete via the full key tuple; require *non-empty* where a field feeds a ranking.

## A Watchdog's No-Op Branch Is Its Dangerous Branch — Control the Empty Result

Two failure modes at the same seam: a supervisor that concludes "nothing to do" and exits silently, where "nothing to do" is indistinguishable from a broken instrument or a dropped handoff.

**An empty scheduler task list needs a create-probe control before you call it a true empty.** The scheduler-watchdog task says: call `list_tasks`, find any task whose next-fire `at=` is >10 min in the past, re-arm it. On 2026-08-04 the list came back `No tasks.` fleet-wide, across every filter — while **two scheduled tasks had just fired to create the very session doing the reading**. "Zero tasks exist" and "two tasks just fired" cannot both be true. Probes that did NOT discriminate — all returned `No tasks.`/not-found: `ncl tasks list`/`--all`/`--status pending`/`--json`; `--group <id>`; `ncl tasks get --id <derived>`. The discriminating probe is a **positive control that plants a row you know exists**:

```bash
ncl tasks create --name "watchdog-control-probe" \
  --prompt "Control probe — delete me." --process-after "2027-01-01T00:00:00Z"
ncl tasks list --all          # → shows the probe, "in 150d", pending
ncl tasks delete --id watchdog-control-probe-00f1
```

The list saw it instantly ⇒ the instrument works ⇒ the empty list is a TRUE empty. Generalized: for any watchdog whose trigger is "the list is empty / the count is zero / nothing is overdue", **the no-op branch is the dangerous branch** — it is indistinguishable from a broken query and exits silently, so a blind instrument issues a clean bill of health forever. Bake a create-then-delete (or any known-positive) control into the check itself. **`--help` output and a well-formed error are not capability probes; only a round-trip on data you planted is** ([an empty scheduler task list needs a create-probe control before you call it a true empty](../learnings/1785824186159-an-empty-scheduler-task-list-needs-a-create-probe-.md)).

**When two dispatches are in flight to one child, explicitly check for starvation — the later one can overtake the earlier.** On the slang#11917 pass-gating epic two batches went to the same child two days apart: **batch-2** (07-28) → no branch, no PR, 7 days later; **batch-3** (07-30 01:12) → PR #12281 opened ~2h later, approved 08-03. The issue author asked about batch-2 **twice** before anyone noticed. Every tier behaved "correctly": the child reported "fixer building draft PR" (true at the time), that was relayed upward without verification, and the "hold without polling" discipline took over — right for suppressing noise, but **it has no deadline**, so a dropped handoff and healthy in-progress work emit the same signal: nothing. Rules: do **not** assume FIFO — ask which dispatch produced an artifact, because **a later task completing is positive evidence the child is alive, which makes the earlier one's silence more suspicious, not less**; **a repeat question about the same artifact is a starvation alarm**; **pair every silent-hold with a staleness bound**; and **verify a child's in-progress claim before relaying it upward**. Ground-truth calls:

```bash
# Does the branch exist at all? (REST — works when `gh pr list` GraphQL 401s)
gh api "repos/O/R/git/matching-refs/heads/fix/issue-<N>" --jq '.[] | "\(.ref)  \(.object.sha)"'
# Any PR in ANY state referencing the issue?  → MCP github_search_issues q="repo:O/R is:pr <N> in:title"
# Is a found branch real work or a stale leftover?
gh api "repos/O/R/compare/master...<sha>" --jq '"status=\(.status) ahead=\(.ahead_by) behind=\(.behind_by)"'
```

**Matching the name prefix is not enough** — `fix/issue-11917` looked like a hit but was the merged #11920 slice from a month earlier, `diverged` and 208 commits behind master ([two dispatches to one child: check for starvation, because silence reads identically to progress](../learnings/1785824876739-two-dispatches-to-one-child-check-for-starvation-b.md)).

## Monitoring a Repair Workflow: Alert on the Blocker's Identity, Not on Red (2026-08-13 fold)

Monitoring the hourly `ci-retry-yielded-bot` repair job exposed a family of monitoring traps. **A watchdog that correctly declines reports `success`** — the workflow's job is to *not* rerun bot CI while human CI is active, so every fire logs `success` with "CI is still active … not rerunning"; a monitor keyed on red conclusion sees a healthy-looking histogram over a genuinely stuck condition, so alert on the *declines*, not on failures ([A watchdog that correctly declines reports success — alert on declines, not on red](../learnings/1786296254567-a-watchdog-that-correctly-declines-reports-success.md)). But **a raw decline streak cannot separate two diseases**: an early "streak grew 16→44, worsening" claim was three defects at once — the two endpoints counted different predicates (one trigger arm silently dropped), both were page-bounded floors (the true streak was 277, found only by paginating), and — the finding no count would have caught — the conclusion field was *constant while the mechanism changed underneath it*: 40h-earlier declines were ordinary CI contention (`still active (8 run)`), today's were wedged on an approval gate holding zero runners (`(2 run)`). Same field, same verb, different disease; a growth claim needs both endpoints on one predicate, and the alarm must key on the blocker's *identity*, not the streak length ([A constant conclusion field can hide a changed mechanism: 277 "declines" were two different diseases](../learnings/1786296545684-a-constant-conclusion-field-can-hide-a-changed-mec.md), [A streak count cannot separate two diseases — alarm on the blocker's identity](../learnings/1786296763575-a-streak-count-cannot-separate-two-diseases-alarm-.md)). And when you find the real defect, fix the *reachable* gate: an earlier note blamed the retry script's `--lookback-hours 16` hard-drop (66 runs stranded 53 days) — but that code is **unreachable behind an earlier `ACTIVE_STATUSES`/`any_active_ci` gate** that returns first, so the lookback fix would have changed nothing; trace which gate returns first before proposing a fix ([CORRECTION to the yielded-bot lookback finding: the lookback is UNREACHABLE behind an earlier gate — fix ACTIVE_STATUSES first](../learnings/1786300033438-correction-to-the-yielded-bot-lookback-finding-the.md)).

## Building Guards for an Append-Only Ledger: the Guard, Its Population, and Its Residue (2026-08-13 fold)

Instrumenting the CI-babysitter's append-only rerun ledger produced a set of guard-construction rules. **A recorded policy limit that only binds when recalled is as reliable as an unenforced schema — none:** a "don't recommend discarding a unit whose value this data can't see" rule lived in a README no script reads, and the next sweep reproduced the shape one layer up (auto-close of idle PRs); move policy onto a consumer the actor cannot avoid, and name the *shape* it guards ([A scope boundary stored as prose is unenforced — put policy on the same code path as mechanism](../learnings/1786314434522-a-scope-boundary-stored-as-prose-is-unenforced-put.md)). **Test a prescribed guard against the population it must catch before adopting it:** `audit_summary_rows`, named as "the only mechanism that can see a bypassed row," filters to `result=="sweep_summary"` (0.7% of rows) while the bypassed rows carried `result:"left"` — a detector on the wrong population returns a clean report, worse than none because it retires the question ([Test a prescribed guard against the population it must catch — "run it unconditionally" is worthless if it can't see the defect](../learnings/1786314802358-test-a-prescribed-guard-against-the-population-it-.md)). **A live-fire control belongs on a temp copy:** proving a guard fires means writing input that trips it, and in an append-only artifact that input can never be withdrawn — planted rows became permanent findings, and *future-dated* ones scheduled a wedge with none of the reasoning in context; point the path constant at a tempfile for the control ([A live-fire control belongs on a temp copy — proving a guard fires leaves permanent residue in an append-only artifact](../learnings/1786315108736-a-live-fire-control-belongs-on-a-temp-copy-proving.md)). **A guard defined against "now" must read the clock once per run and report the resolved value** — a per-row clock read makes one file return two answers, and a future-dated row pushes a *currency* metric forward (stale looks current), failing toward reassurance; report `newest_real_row` excluding future stamps ([A guard defined against "now" must read the clock once per run and report it — per-row reads make the same file return two answers](../learnings/1786316206459-a-guard-defined-against-now-must-read-the-clock-on.md)). Two schema traps: **a `pop()` of the wrong key prints a benign `False`, not an error** — a multi-key schema plus a single-key deletion silently leaves a stale mark (delete via the key tuple) ([A pop() of the wrong key prints a benign False, not an error — verify which mark key an entry actually carries](../learnings/1786306718517-a-pop-of-the-wrong-key-prints-a-benign-false-not-a.md)); and **a ledger can enforce `labels[]` and still have zero labelled rows** — `[]` passes a "field present" check while carrying no information, so all 40 reruns ranked over an empty vocabulary and the only signature route was free-text (which once turned "52 rows/11 PRs" into a true count of 3); require *non-empty* where the field feeds a ranking ([A rerun ledger can enforce labels[] and still have zero labelled reruns — check the population your ranking describes](../learnings/1786292075724-a-rerun-ledger-can-enforce-labels-and-still-have-z.md)).
