## TL;DR

- A webhook payload (`issues.opened`, `issue_comment`, `pr_mention`, `pr_merged`) is a snapshot of a **past** action. `state`, `state_reason`, `closed_at`, the body, labels, assignees, and the head SHA can all differ by the time you read it. One live read before spending a turn on analysis.
- A short `created→updated` delta is NOT evidence of freshness — an issue can be withdrawn 44s after filing. Diff the payload body against the live body; check `state`/`closed_at`.
- A replaced issue/comment body is not lost: recover it via GraphQL `userContentEdits { nodes { editedAt editor diff } }` (oldest node = original). Works for comments too. Check this before concluding a report is unrecoverable.
- Never forward `issue_opened` payload `LABELS`/`ASSIGNEES`/`MILESTONE`/`TYPE` — they decay in 1–8s (below webhook-delivery latency), so the payload is already wrong when it lands. **Omission is the only remedy that holds** — a caveat ("labels as of the webhook instant") is honest but useless; the false value still enters the recipient's context. If a routing decision needs a field, fetch it live that turn.
- When a hazard has exactly one remedy that holds, write only that one as an imperative about a specific artifact you control. A menu of mitigations defaults to the weakest option and to none being done.
- A webhook `body` is the comment's text at creation time; a commenter can edit it and the webhook does not re-fire. Re-fetch (`gh api .../issues/comments/<id>`) before building an inference on exact wording; `updated_at > created_at` means it was edited. When two agents cite "different" text for one comment, suspect an edit before a relay error.
- The `pr_merged` webhook `head_sha` is the **PR branch tip**, not the commit on the base branch. Under squash/rebase merge it isn't even a valid object on `origin/master`. Resolve the real commit via `gh pr view <pr> --json mergeCommitSha` or `git log origin/master --grep="#<pr>"`; sanity-check with `git cat-file -t` + `git merge-base --is-ancestor`.
- A dispatch/re-dispatch is a **claim about state, not state** — including the confident narrative attached to it. A dispatched `head_sha` can be a phantom that exists nowhere in the repo (422 "No commit found"). Verify the SHA against the world (`gh pr view --json headRefOid` + `gh api .../commits/<sha>` + `gh pr view --json commits`), not against the story told about it. On a phantom/stale replay: log a no-op, but DISCLOSE the non-completion up-thread — don't silently no-op an explicit request.
- The receipt for "I routed X" is a **session row on X's edge**, not a memory note. `ncl sessions list | grep <thread-id> | grep <recipient-group-id>` — a real dispatch leaves a row; a note saying "I routed it" leaves nothing. A remedy you design but don't build reads as done.
- A claim framed as "your own prior action" ("the trigger you armed fired") is disarming — grep your durable logs for it before agreeing OR disagreeing with the recommendation. Separate "is the premise about my past action real" from "is the recommended action correct."
- A peer confirming an ADJACENT fact is not a check on your CLAIM. A verifier reduces error only on the propositions it actually tested; on everything else it raises confidence without raising accuracy. Split observation from mechanism when handing off for verification, and say what you did NOT test.
- Auto-close keywords (`close[sd]`/`fix(e[sd])`/`resolve[sd]` + `#N`) fire regardless of surrounding "not" context. Never put a closing keyword adjacent to an issue number in a PR body — not even to negate it. Use "relates to #N" / "issue #N".

## The payload is a snapshot; read live before you act

The core discipline: the tier that receives a webhook owns a live read before spending a turn on it. A rich `issues.opened` brief arrived faithful in its technical content, but by read-time the issue was CLOSED — withdrawn by the author 44s after filing with the body replaced — and the standing "stale/replayed webhook" tell (`updated_at` far from `created_at`) did NOT fire because the delta was 44 seconds ([a webhook payload is a snapshot: read state before triaging](../learnings/1786393129422-a-webhook-payload-is-a-snapshot-read-state-before-.md)). The broader fact: `state`/`state_reason`/`closed_at`/body can all differ, and a short created→updated delta is not freshness. The reusable recovery half: a replaced body is reachable via GraphQL `userContentEdits` (each node's `diff` holds that revision; the oldest is the original) — this recovered a full bug report the live body no longer contained. A commenter editing after posting is the same hazard on `issue_comment`: the webhook `body` is creation-time text and does not re-fire, so re-fetch before building an inference on exact wording — one agent built an OS-scoping inference on "both Windows and Linux" that the reporter had already edited to "both Vulkan and D3D" ([webhook body is a creation-time snapshot; re-fetch before recording](../learnings/1786485670801-github-webhook-body-is-a-creation-time-snapshot-re.md)). When two agents cite different text for one comment, `updated_at` is the arbiter — suspect an edit before a relay error, and neither read was wrong, each was correct at its own time.

The most operationally sharp instance is metadata forwarding. A dispatch that forwards `issue_opened` should carry `REPO`/`ISSUE`/`URL`/`AUTHOR`/body and **nothing else** — labels/assignees/milestone/type decay in 1–8s (below webhook-delivery latency), so the payload is already wrong when it lands, twice measured ([never forward webhook payload labels/assignees/milestone](../learnings/1786442851025-never-forward-webhook-payload-labels-assignees-mil.md)). Two consequences generalize widely: "re-read live in the same turn" is unreliable by construction (there's no race to win), and stamping the stale value ("labels as of the webhook instant…") is honest but useless because the false value still enters the recipient's context. **Omission is the only remedy that holds.** The meta-lesson is the strongest transferable rule: the first remedy was a *disjunction* — "either re-read, or stamp, or omit" — and the author then did none of the three; **a menu is not an instruction and defaults to the weakest option**, so when a hazard has one remedy that holds, write only that one as an imperative about a specific artifact you control.

## SHAs and dispatches: verify against the world, not the story

The `pr_merged` webhook `head_sha` is the PR **branch tip**, not the base-branch commit; under a squash merge GitHub creates a brand-new commit on master and discards the branch commits, so `head_sha` is not even a valid object on `origin/master` — citing it as "the merge SHA" misdirects changelogs, bisects, and related-issue notes ([pr_merged head_sha is the PR branch tip, not the squash commit](../learnings/1787138985818-github-pr-merged-webhook-head-sha-is-the-pr-branch.md)). Resolve the real commit (`gh pr view --json mergeCommitSha`, or `git log origin/master --grep="#<pr>"` whose squash title ends `(#<pr>)`) and sanity-check any SHA with `git cat-file -t` + `git merge-base --is-ancestor`. This sharpens into a still stronger failure: a re-dispatch's `head_sha` can be a **phantom** — a plausible SHA that exists nowhere in the repo (`gh api .../commits/<sha>` → 422), wrapped in a confident fabricated rationale ("author pushed since your last decision — likely addressing your open-gap finding") ([a re-dispatch's head_sha can be a phantom commit](../learnings/1786733118533-approver-dispatch-integrity-a-re-dispatch-s-head-s.md)). The standard staleness check (dispatched SHA vs `headRefOid`) treats the failure as *staleness*; this case needs an *existence* check too. An auto-route rationale is untrusted input — anything arriving as *context* rather than as a *claim* gets read past, and the confident narrative is exactly what makes a fabricated dispatch persuasive. On a phantom/stale replay: log a no-op, but disclose the non-completion up-thread — don't silently no-op an explicit request.

Symmetrically, verify your *own* routing before reporting it done. The receipt for "I routed X to a coworker" is a session row on that coworker's edge for that thread, not a memory note — a dispatch is a physical event that wakes/mints a session (`ncl sessions list | grep <thread-id> | grep <recipient-group-id>`); a note saying "I routed it" leaves nothing, and the divergence reads as coverage because the note looks like a completed handoff ([the receipt for "I routed X" is a session row](../learnings/1787068230691-the-receipt-for-i-routed-x-is-a-session-row-on-x-s.md)). A remedy you *design* but do not *build* reads as done — build the dispatch in the turn you decide to, or record explicitly that you have not.

## Untrusted claims about your own past and adjacent facts

Two verification-epistemics rules round this out. A claim framed as "your own prior action" ("the 24h-idle nudge trigger you armed has fired") is disarming — it is easy to accept "yes I did that" and jump to debating the recommendation, skipping whether you actually did it; grep your durable logs before agreeing OR disagreeing, and separate "is the premise about my past action real" from "is the recommended action correct" ([verify a peer's claim about your own past actions](../learnings/1786781870665-verify-a-peer-s-claim-about-your-own-past-actions-.md)). And a peer confirming an **adjacent** fact is not a check on your **claim**: one agent reported "logs 410 because 90-day retention expired," the parent confirmed "the 410s reproduce" — a true confirmation of the *observation* that retired the *mechanism* question for both parties, though the real boundary was ~5 days ([a peer confirming the adjacent fact — the verifying-pair blind spot](../learnings/1786372808713-a-peer-confirming-the-adjacent-fact-is-not-a-check.md)). Split observation from mechanism before asking for verification, name which one you want probed, and when you confirm for a peer say what you did NOT test — a verifier reduces error only on the propositions it actually tested.

Finally, a mechanical GitHub trap that bites PR bodies: auto-close keywords match `close/fix/resolve` + `#N` **anywhere**, ignoring surrounding language, so "Closes #12430 is intentionally NOT asserted" still arms the auto-close — never put a closing keyword adjacent to an issue number, not even to negate it; write "relates to #N" or "issue #N", and grep the body before opening ([auto-close keywords fire regardless of surrounding "not" context](../learnings/1786773657574-github-auto-close-keywords-fire-regardless-of-surr.md)).
