# Discord message limits, reading replies and feedback state, and the compliance check

## TL;DR

`mcp__slang-mcp__discord_send_message` rejects content over **2000 characters** (standard non-Nitro Discord) with `400 error code 50035: Invalid Form Body`. Budget for 2000 from the start; do not trust the ceiling the first error reports.

- The real ceiling is **2000**, not 4000. A first over-length attempt can report `Must be 4000 or fewer` — misleading; re-trimming to ~3900 just burns another round trip. Split to **under ~1900 chars per message** on the first attempt.
- Count with `python3 -c "print(len(open('f.md').read()))"`, **not `wc -c`** — `wc -c` counts bytes, and em-dashes / `⚠️` / arrows are multi-byte, so it overstates length. Discord counts UTF-16 code units, so Python `len()` is the closer proxy (emoji outside the BMP count as 2).
- The mandatory summon footer (~135 chars) is non-negotiable — subtract it first, leaving ~1865 for content.
- When trimming, cut prose clauses and keep **file:line citations + issue links** — users can follow a link, not recover a dropped fact.
- For long answers, prefer splitting into a follow-up message in the thread over deleting substance.
- **Replies to a bot post often live in a thread whose channel ID is the post's message ID.** Read `discord_read_messages(channel_id=<bot msg id>)`; a 404 "Unknown Channel" means no thread. The parent channel shows only a short starter line that repeats the bot post, so a parent-only read misses the answers. A recurring ask (the maintainer rotation) can be answered in an earlier ask's thread: read the previous asks' threads too.
- **A Discord REST 5xx (e.g. 504 "Gateway time-out") on a control read is transient, not "no messages".** Retry each 5xx once before recording a control failure; the sweep helper `dc.py` retries only 429.
- **A green Resolved button means the owner clicked Resolved, and that click pauses the bot.** `feedback:resolved` is `style` 2 (grey) until clicked, then `style` 3 (green) with `edited_timestamp` set to the click time. An owner follow-up posted before the click can be left unanswered; relay it by hand.
- **The compliance check reads the bot's Discord posts poorly**: its converter now reads the `filtered` wrapper (save inline tool output mechanically from the session transcript, never retyped), the bot posts as `SlangMaintainerBot` (so `--author nv-slang-bot` gives an empty-pass R10 "OK 0/0"), and its GitHub searches 400 on a raw `>` in `created:>=`. Exit code 1 can hide UNKNOWN rules; read `complete` in `latest.json`.
- **A Discord username is not a GitHub login.** Map both handles through `memory/github-to-discord.json` (keyed by Discord author `id`) before calling a question unanswered or planning a relay, and resolve a login with GraphQL `user(login:)` before trusting an `author:<discord-name>` zero: `author:h7per` hits an unrelated empty account (h7per = H7perus; sirspate = jhelferty-nv).

## Details

The `4000` in a first-attempt error is not the budget — one investigator burned ~6 rounds of iterative trimming (2299 → 2233 → … → 2000) assuming the Nitro/bot ceiling. Two attempts can even return *two different limits under the same error code 50035* (4000 then 2000). Treat 2000 as the hard cap and split accordingly. See [discord_send_message caps content at 2000 chars, not 4000](../learnings/1786006619395-discord-send-message-caps-content-at-2000-chars-no.md) and [Discord message limit is 2000 chars, not 4000 — the API error message lies on the first try](../learnings/1786006634390-discord-message-limit-is-2000-chars-not-4000-the-a.md).

**Multi-part answers with feedback buttons:** a mid-sequence rejection can leave a partially-delivered answer in the thread, so order the sends with `add_feedback_buttons: false` on parts 1..N-1 and `true` only on the **final** part — the Resolved/Helpful buttons then attach to a complete answer, and the recorded `reply_message_id` lands the reader at the end of the sequence. "Send success" for a split reply means *every* part returned a real `message_id`; verify each response before appending a handled row (a failure on part 3 of 3 still means the user got an incomplete answer).

## Reading replies and feedback state on bot posts

**A human answer to a bot post is usually in a thread on that post, not in the channel.** Discord gives a thread opened on a message the same ID as the message, so `discord_read_messages(channel_id=<bot message id>)` reads it, and a 404 "Unknown Channel" means nobody opened one. In the parent channel the thread appears only as a short human-authored starter line that repeats the start of the bot post (for example "Slang Maintainer rotation: who will be"), with no answer text. Reading only the parent channel missed two maintainer-rotation answers in #slang-committers (2026-08-18 and 2026-10-12). Resolve `<@discord-id>` mentions in those answers with the slang-maintainer group's `memory/github-to-discord.json` ([Discord replies to a bot post often live in a thread keyed by the post's message ID](../learnings/1792411346636-discord-replies-to-a-bot-post-often-live-in-a-thre.md)). The answer can also land in an OLDER ask's thread. The 2026-10-27 rotation answer (kaizhang_52840 naming the maintainer and the backup for 10-27 → 11-09) was posted in the thread of the 2026-10-12 ask (`1559174022111957013`), while the current 2026-10-26 ask still had no thread (404). A read of only the current ask's thread would have reported "unanswered". So reconcile a rotation by reading the current ask's thread AND the previous asks' threads with `messages?after=<window start>`, and diff `/guilds/{id}/threads/active`: a changed `message_count` on an old ask's thread is the tell ([rotation answers can land in the previous ask's thread](../learnings/1793176596468-rotation-answers-can-land-in-the-previous-ask-s-di.md)). This is the same "wrong kind of object" false-empty as a forum channel's `[]` from `/messages` ([GitHub & platform API instrument traps](../concepts/general-misc-a-github-api-instruments.md)).

**A 5xx on a control read is a transient error, not an empty or failed read; retry it once.** The maintainer sweep's `dc.py` REST helper (`reports/tmp10xx/discord/`) retries only on 429 and returns any other HTTP error as `{'_err': code}`. On 2026-10-30 two control reads (the slangd thread and the App thread) came back 504 "Gateway time-out" from discord.com, which a sweep would record as a broken control or "no messages"; one retry returned the known tails. Retry each 5xx once before recording a control failure or an empty thread, or add 5xx to `dc.py`'s retry loop ([Discord REST sweeps: retry an HTTP 504 before you call a control read failed](../learnings/1793348691217-discord-rest-sweeps-retry-an-http-504-before-you-c.md)).

**The Resolved button records its own click, and the click pauses the bot.** On a support-bot answer the `feedback:resolved` component is `style` 2 (grey) by default and `style` 3 (green) after a Resolved click, and the message's `edited_timestamp` moves to the click time. In the 2026-10-20 scan all 8 green Resolved buttons across 50 threads sat on edited messages, so a sweeper without access to the feedback log can infer Resolved clicks by diffing component styles between days. The side effect matters more: because a Resolved click pauses the bot, an owner follow-up posted before the click can go unanswered (plokie, thread 1561802016903405779: follow-up at 10-19T20:13Z, no bot reply, Resolved at about 04:16Z). Check each green-Resolved thread for a trailing owner message and relay it by hand. In the same sweep, one Bash call that chained several `gh api ... --jq` commands was hook-denied ("Blocked by hook"), so run one `gh` call per Bash invocation ([a green Resolved button means the owner paused the bot](../learnings/1792485276891-discord-bot-answers-a-green-resolved-button-means-.md)).

## Reading the bot's own posts for the compliance check

The compliance-check converter `scripts/discord_export_from_json.py` could not read `mcp__slang-mcp__discord_read_messages` output in mid-October 2026; by 2026-10-26 it reads both shapes described below [compliance-check: save inline discord_read_messages output byte-exact from the session transcript](../learnings/1792995656071-compliance-check-save-inline-discord-read-messages.md). The tool returns `{"filtered": {"channel_id": ..., "messages": [...], "total_count": N}}`, sometimes wrapped in an MCP `[{"type":"text","text": ...}]` block, while the converter unwraps only a top-level `messages`/`result`/`data`/`items` key, so `--inspect` exits 2 ("no message array found", then a JSONL fallback error). Messages carry no per-message `channel_id` (`--channel-id` covers it), the bot flag is a top-level `is_bot` with `author` a plain string (the converter reads `author.bot`/`msg.bot`), and the `--author` value is wrong. In the three watched channels (1352357976878481468, 1305995870046650368, 1303735244108595330) the only bot author is `SlangMaintainerBot` (author_id 1352501374021140480), which posts the weekly "Slang Community PR Report" (often split into `(part k/N)` posts) and the maintainer-rotation message; nothing posts as `nv-slang-bot`. While the converter lacked the `filtered` wrapper and `is_bot`, R10 (discord-thread) stayed UNKNOWN; now that records convert, `--author nv-slang-bot` writes 0 of them and R10 reports "OK 0/0", an empty pass that proves nothing. If those posts belong to the fleet, convert with `--author SlangMaintainerBot` (or `--author bot`); on 2026-10-16, 7 of its 10 posts in the window would fail R10. Hand-written records are forbidden by the skill. One `discord_read_messages` call with limit=100 reaches back more than 30 days in each of the three channels, so one call per channel is enough. A tool response over the inline limit (~50 KB observed 2026-10-26) is saved by the harness under `~/.claude/projects/<proj>/<session>/tool-results/`; `cp` that file byte for byte. A smaller response comes back inline: never retype it with Write, but extract it mechanically from the session transcript `/home/node/.claude/projects/-workspace-agent/<session>.jsonl` (find the `tool_use` whose input has the channel_id, take the matching `tool_result` text block, `json.loads` it to validate, then write it) [compliance-check: save inline discord_read_messages output byte-exact from the session transcript](../learnings/1792995656071-compliance-check-save-inline-discord-read-messages.md). The 2026-10-26 run also showed R7 with 8 judge items 'unknown' ("judge reply had no JSON verdict"): the replies were empty or cut off mid-reason, which looks like a max_tokens truncation in `AnthropicMessagesJudge`, not the judge budget (211/250 used); R7 still reads DRIFT because failures outrank undecided items [discord_export_from_json.py cannot read discord_read_messages output](../learnings/1792145488222-compliance-check-discord-export-from-json-py-canno.md) [the bot poster is SlangMaintainerBot; nv-slang-bot matches nothing](../learnings/1792151261703-compliance-check-discord-author-filter-nv-slang-bo.md). Do not read the run's result from the exit code: `compliance_check.py` computes `code = 1 if failures else (2 if unknown else 0)`, so a run with both failures and UNKNOWN rules exits 1, the same as a complete run with failures; check `complete` in `latest.json` [same atom](../learnings/1792151261703-compliance-check-discord-author-filter-nv-slang-bo.md).

The same run's GitHub side failed for a URL-encoding reason. `compliance_check.py`'s `gh_command()` builds the URL with `urllib.parse.urlencode(params, safe=":/+>=<")`, so `created:>=2026-09-16` goes out with a raw `>`, and GitHub `search/issues` answers HTTP 400; `%3E`, `%3E%3D` or the range form `created:2026-09-16..*` answer 200. All nine searches failed, R1, R2/R3, R5, R7 and R9 went UNKNOWN with 0 items, and R8 covered only comments. The fix is a skill-script change, dropping `>` and `<` from `safe=`; check with `gh api --method GET "search/issues?q=repo:shader-slang/slang+is:pr+author:app/nv-slang-bot+created:%3E%3D2026-09-16&per_page=1"` [compliance_check.py GitHub searches return HTTP 400](../learnings/1792145809721-compliance-check-py-github-searches-return-http-40.md).

Rule R9 asks for a `bot` label on bot PRs and issues, but shader-slang/slang has no such label: on 2026-10-29 `gh api repos/shader-slang/slang/labels/bot` returned 404, and the recent bot-filed issues (#13972–#13994) carry none. Creating the label is a repository-admin action, so a coworker does not create it; it reports the gap to the operator, and an R9 miss on slang is that standing gap, not a per-post defect [shader-slang/slang has no `bot` label; slang-test needs the test under tests/](../learnings/1793295931890-shader-slang-slang-has-no-bot-label-slang-test-nee.md).

## Mapping Discord handles to GitHub logins

A Discord username is not a GitHub login, so an `author:<discord-name>` search can return a clean zero about the wrong account. Discord user h7per (id 232213633839398921) is GitHub **H7perus**: they linked github.com/H7perus/GPUNN in #slang-support thread 1501184709172924466, and H7perus filed slang#10265, #10979, #9999, #9891 and #9855 (all descriptor-heap or compile-time topics). But `author:h7per` resolves to an unrelated account `H7PER` with no issues or PRs, so every "author:h7per = 0" check in the Discord sweeps up to 2026-10-28 was vacuous; the right query is `org:shader-slang author:H7perus` plus `involves:H7perus`. Before trusting an `author:<discord-username>` negative, resolve the login with GraphQL `user(login:"...")` (null means no such user; otherwise check its issue and PR counts) and look for a GitHub link the person posted on Discord. The 2026-10-29 pass found that sirspate, jaspersgames, tombadilllo and tessfactor have no GitHub account by that name (tessfactor is tangent-vector), that mattov→MattOV, riebeck→Riebeck and Tombadillo have never filed an issue, and that CrossVR, externalhost0, HildarTheDorf, fknfilewalker, BarabasGitHub, DouglasPotesta, Plokie and ims21 resolve to active accounts [Discord h7per = GitHub H7perus; author:<discord-name> searches can hit the wrong account](../learnings/1793261887553-discord-h7per-github-h7perus-author-discord-name-s.md).

The maintained mapping is `memory/github-to-discord.json`, keyed by the Discord author `id`, not the username. It maps both `jhelferty-nv` and `sirspate` to Discord ID 117490599833108481, so Discord sirspate is GitHub jhelferty-nv (James Helferty); authorship corroborates it, since slang#12656 ("Add slang-package", the package-manager prototype sirspate discusses in #slang-discussion) is committed by James Helferty. Skipping the lookup produced a wrong carry: the sweeps listed "tessfactor → sirspate (slangd config file), 12 d unanswered; ping sirspate with jhelferty-nv's slang-vscode-extension#78 comment", but that 10-23 comment was sirspate's own reply, so the question was already partly answered on GitHub. So we map both handles through the file before calling a Discord question "unanswered" or planning a relay between two people [Discord sirspate = GitHub jhelferty-nv (James Helferty); check github-to-discord.json before "relay to X"](../learnings/1793262133027-discord-sirspate-github-jhelferty-nv-james-helfert.md).
