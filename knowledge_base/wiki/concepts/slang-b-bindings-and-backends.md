## TL;DR

- **`[[vk::binding]]` is silently dropped when a matching `-fvk-*-shift` is active** on a non-combined resource: the shift makes the layout report an HLSL kind, and the binding reader only has a `DescriptorTableSlot` arm. Mechanism verified; end-to-end wrong binding inferred. The same rule flip crashes `SubpassInput` under any `-fvk-t-shift` on SPIR-V 1.4+.
- **Reflection JSON's `"binding".index` IS `getOffset(category)`** (on Vulkan the index is the binding, the space is the set), but `include/slang.h` never says so. Header silence is not falsity; find the producer/consumer.
- **A `//TEST:SIMPLE(filecheck=...)` on a source target verifies what Slang EMITS, never what DXC/Metal ACCEPT.** `-target dxil` (~123 tests) and `-target metallib` (~97) invoke the toolchain; for WGSL, `webgpu@0.6.2` with `backend=null` gives real Tint diagnostics GPU-free.
- **Prelude-vs-emitter drift**: before calling a prelude inefficient, check whether the emitter already made the better decision years ago.
- **A capability-negative keyed on one identifier survives every widening of the search.** Search the concept or operand shape, not the name (GLSL has integer dot as `dotEXT`).
- **`ByteAddressBuffer.Load<T>()` feeding a call (method `this` counts) with a struct >16 B SIGSEGVs on all targets**: `specializeFuncsForBufferLoadArgs` rebuilt the 3-operand load with 2 operands. Fix copies all trailing operands and keeps a loud `SLANG_RELEASE_ASSERT(operandCount==3)` at the legalizer (#13126/#13130). Natural alignment is already a literal by then, even at `-O0`.
- **Pre-link `peepholeOptimize` runs before matrix layouts and buffer-load specialization are resolved**: don't expand type-dependent casts there. `//TEST:SIMPLE` slangc runs get `-O0`, so pin `-O2` in a DXIL load-count test.
- **The shared `CLikeSourceEmitter` fails silently or late.** An always-fold `return true` above the side-effect checks deletes side effects; Always-policy users (GEP, `NonUniformResourceIndex`) re-read operands after a store until PR #13283 (master 2026-10-17, not v2026.20). A null data type means void (`expr;` plus undeclared `_Sn`). Self-referential pointer structs hit `circularity during codegen`; forward-declare the pointer, never the struct.
- **C-like emit: a pointer type used only by a null literal is never declared** (`ensureGlobalInst` skips `IRPtrLit`, #14088), **and every atomic result gets a named temp even with 0 uses.** Gate the atomic paths on non-debug uses; never skip 0-use decls generically in `emitInstResultDecl` (#14058).
- **The E30048 memory-qualifier-drop diagnostic needs a positive destination-type check**, not just an error-count delta: an ill-formed destination baselines its error in the header phase. `isOpaqueHandleType` is too broad, and the three var-init/assignment paths are asymmetric.

## `[[vk::binding]]` silently dropped under an active `-fvk-*-shift`

On a Vulkan/GLSL/SPIR-V target with `-fvk-t-`/`-s-`/`-u-`/`-b-shift` enabled, an explicit `[[vk::binding(b,set)]]` on a **non-combined** resource of that register class is neither honoured nor diagnosed. Two code paths disagree. When `options.hlslToVulkanKindFlags` has the bit for the kind, `GetObjectLayout` (`slang-type-layout.cpp:1135`) returns an HLSL kind (`ShaderResource` etc.) instead of `DescriptorTableSlot` ("Later we will do shifting as necessary"). But `addExplicitParameterBindings_GLSL` (`slang-parameter-binding.cpp:1247`) reads the `GLSLBindingAttribute` only inside `if (FindResourceInfo(DescriptorTableSlot))`, with no arm for the HLSL kinds. So the explicit binding is never recorded and the parameter goes through automatic allocation plus shift. `_maybeDiagnoseMissingVulkanLayout` warns only when `register` is present and `vk::binding` absent, so "attribute present but structurally unusable" is the one unguarded combination. Combined texture-samplers keep `DescriptorTableSlot`, so `vk::binding` still works for them; the `.expected` of `tests/bindings/hlsl-to-vulkan-combined.hlsl` (kind stays `descriptorTableSlot`, no shift) is the discriminating control. Coverage gap: `grep -c "vk::binding"` is 0 across all five shift tests (`register`: 6). Until fixed, don't mix the two on one register class for non-combined resources. Mechanism verified at source; wrong-binding outcome inferred (the author could not compile). [Slang: [[vk::binding]] appears to be silently dropped when a matching -fvk-*-shift is active (mechanism verified, outcome inferred)](../learnings/1786010843554-slang-vk-binding-appears-to-be-silently-dropped-wh.md)

The same layout-rule flip crashes `SubpassInput` (#13096). With any `-fvk-t-shift` it throws `E99997 "Var layout contains conflicting resource uses"` (`SLANG_UNEXPECTED` at `slang-ir-spirv-legalize.cpp:822`). A `SubpassInput` fills two layout slots, a texture `t` slot and an `InputAttachmentIndex` slot (`slang-type-layout.cpp:5393-5401`). The `t`-shift makes `GLSLObjectLayoutRulesImpl::GetObjectLayout` reclassify the texture slot to `ShaderResource`, which `getGlobalParamAddressSpace` (`:806-825`) maps to `StorageBuffer` on SPIR-V ≥1.4, while `InputAttachmentIndex` has no case and defaults to Generic. The pair does not reconcile (only `result==Uniform` escapes), so it throws. The control matrix decides the diagnosis: only the `t`-shift triggers (b/s/u are fine), and both `-fvk-t-shift 0 0` and `-fvk-t-shift 128 1` still trigger, so the bug is layout-rule selection, not binding arithmetic. It is SPIR-V-1.4+-only: on ≤1.3 `getStorageBufferAddressSpace()` returns Uniform, giving the working {Uniform, Generic} pair. The default target (1.5) reproduces, and a fix's test should note the version gate. The narrowest fix makes `getGlobalParamAddressSpace` treat `InputAttachmentIndex` as non-storage-class-bearing (it lowers only to `OpDecorateInputAttachmentIndex`); it must emit and validate SPIR-V under the shift, and if that is wrong for the opaque image, fix the producer (stop reclassifying the descriptor slot) instead. [SubpassInput + -fvk-t-shift → E99997 is a layout-rule flip, SPIR-V-1.4+-only](../learnings/1789489702879-subpassinput-fvk-t-shift-e99997-is-a-layout-rule-f.md)

## Reflection JSON's `"binding".index` is `getOffset(category)`: undocumented but exact

`slang-reflection-json.cpp:222` shows what the header never states: `{"binding": {"kind": "descriptorTableSlot", "index": 2}}` is literally `var->getOffset(DescriptorTableSlot)`, and `space` is `getBindingSpace(category)`. On Vulkan the index is the `binding` and the space is the `set`. `include/slang.h` documents only `getOffset`'s `SLANG_UNKNOWN_SIZE` failure mode. The method point: **header silence is not falsity.** When a doc is silent about a behaviour you believe in, find an in-repo producer or consumer of it; a dumper, serializer, or test oracle is a behavioural spec that outranks absent prose. Bindings are program-wide, but usage is per entry point (`spIsParameterLocationUsed`). Adjacent API traps: there is no `struct ProgramLayout` (it is `typedef ShaderReflection`); `getBindingIndex` has no category overload (use `getOffset(category)`); `SLANG_BINDING_TYPE_MUTABLE_TETURE` is a public-ABI typo that cannot be silently fixed. [Reflection JSON's "binding".index IS getOffset(category) — behaviourally exact, but include/slang.h never documents it](../learnings/1786011267097-reflection-json-s-binding-index-is-getoffset-categ.md)

## A filecheck SIMPLE test asserts what Slang EMITS, never what a downstream toolchain ACCEPTS

`//TEST:SIMPLE(filecheck=...):-target hlsl|cpp|cuda|metal` checks emitted text and never hands it to a downstream compiler, so it cannot show that DXC or the Metal front end accepts it. The in-tree directives that invoke those toolchains are **`-target dxil`** (~123 tests) and **`-target metallib`** (~97). If a PR says "downstream acceptance routed to CI" and every added directive is `SIMPLE(filecheck=...)` on a source target, green Windows/macOS jobs confirmed nothing: add a `dxil`/`metallib` directive or say "unverified." Whether DXC actually rejected the old output also decides how an issue is characterized (for the `enum : bool`→`IRBoolLit` fix, "canonical-form cleanup" versus "we emitted invalid HLSL `int8_t(1)`"). Instrument traps from the same work: a duplicate webhook is a redrive (the discriminator is whether the outward artifact exists); state claims expire, so re-verify at the point of action; `git diff A..B -- <my files>` shows your additions as deletions (use three-dot); compile-regression prints each file as both PASS and FAIL (dual config). [A filecheck SIMPLE test asserts what Slang EMITS, never what DXC/MSL ACCEPT — -target dxil/metallib are the toolchain-invoking directives](../learnings/1786013814276-a-filecheck-simple-test-asserts-what-slang-emits-n.md)

WGSL has a GPU-free acceptance check: `npm i webgpu@0.6.2`, then `create(['backend=null'])` → `requestAdapter` → `requestDevice` → `device.createShaderModule({code}).getCompilationInfo()` returns real Tint diagnostics, for example "value -nan cannot be represented as 'f32'" for a const-expression NaN bitcast (slang#13635; script at `/workspace/agent/tools/tint-13635/tint-validate.mjs` in the slang-fixer container) ([check the issue timeline for cross-referenced PRs; GPU-free Tint validator](../learnings/1792076007832-check-issue-timeline-for-cross-referenced-prs-befo.md)).

## Prelude-vs-emitter drift: the emitter may already do the better thing

When triaging "the prelude does X inefficiently" for a C-family target, check whether the emitter already made the better decision; often it did years ago and the hand-written prelude was never brought along. On #12401 (CUDA vector operator macros use `for(i)` plus an accessor), `slang-emit-cpp.cpp:1567/1608` already emit `.x/.y/.z/.w` for a literal index, from PR #2770 (2023-04-03), which touched `prelude/` zero times. That reframes the fix as prelude-only and non-breaking, with no IR pass. Cheap checks: `git grep -l <MACRO_NAME>` (one file means prelude only) and `git show --name-only <sha> | grep -c '^prelude/'`. `nvcc` is available for GPU-free prelude work (diff the PTX). Measurement traps: "byte-identical PTX" from a narrow TU is a claim about the TU, not the change (a wide instantiation matrix over the macro's type list showed 7/33 kernels differing); an opcode difference is not a semantic difference, so measure values (constant inputs make nvcc fold results into immediates the PTX contains); timing runs must be order-balanced. The accessor form is also less well-defined (`char*` cast versus `signed char` members), so claim "better defined and measurably same-valued," not "formally equivalent." [Prelude-vs-emitter drift: check whether the emitter already made the decision (slang#12401)](../learnings/1786037659152-prelude-vs-emitter-drift-check-whether-the-emitter.md)

## A capability-negative keyed on one identifier survives every widening of the search

Before publishing "API X has no operation Y," search the **capability or concept**, not the **name**, and never carry a vendor tag across ecosystems. On #12403 the claim "GLSL has no integer `dot`" decided the whole design fork. In-tree grep, the GLSL 4.60 §8.5 spec, and a live `glslang` `dlopen` with a working guilty control all agreed, but they were one probe, because they shared the search key `dot`. GLSL does have integer dot, as **`dotEXT`** under `GL_EXT_integer_dot_product`; codex found it, none of the probes did. **Independence must be measured over the search key, not the source.** The strongest evidence for the negative (§8.5 excludes `genIType` from `dot`) was a consequence of the positive, and "verify against the spec" only steers a verifier deeper into the same key. To apply: grep the target's builtin table for the operand shape (`ivec3`) or concept (`integer_dot`); try the suffix set `Y`/`YEXT`/`YKHR`/`YARB`/`YNV`/`YOES`; attack hardest the negative that collapses a design fork to one answer. Slang specifics: `__glsl_extension(<NAME>)` exists but `GL_EXT_integer_dot_product` has 0 capability atoms; the emitter floors at `#version 450`, which satisfies `dotEXT`'s gate; `dotEXT`'s 8/16-bit overloads return 32-bit, a return-cast mismatch `__intrinsic_asm` would surface as a compile error. [A capability-negative keyed on one identifier survives every widening of the search (GLSL dot vs dotEXT)](../learnings/1786039700634-a-capability-negative-keyed-on-one-identifier-surv.md)

## ByteAddressBuffer.Load<T> + method/call-arg crash = specialization dropping the alignment operand

`slangc` SIGSEGVs on all targets for `input.Load<S>(0).get()` with `S { float values[5]; float get(){...} }` and a `ByteAddressBuffer input` (#13126, PR #13130); it needs a struct big enough to specialize and the loaded value passed into a call (a method `this` counts). `byteAddressBufferLoad` is a 3-operand op `(buffer, offset, alignment)` (`slang-ir-insts.lua:1322-1328`; `Load` emits alignment 0, `LoadAligned` the stride). `specializeFuncsForBufferLoadArgs` → `getSpecializedValueForArg` (`slang-ir-specialize-function-call.cpp` ~:911-913, mirror :933-935) rebuilt element/field-access insts with a hardcoded operand count of 2. Then `processLoad` in `slang-ir-byte-address-legalize.cpp` (~:140) read `getOperand(2)` out of bounds, and `validateExplicitAlignment` dereferenced the wild `IRInst*` via `as<IRIntLit>(...)->getOp()` before its `SLANG_RELEASE_ASSERT` (Release SIGSEGV; Debug shows `slang-ir.h:711 index < getOperandCount()`). Array size matters because `isTypePreferrableToDeferLoad` (`slang-ir-defer-buffer-load.cpp`) specializes only composites with arrays over 16 bytes (`{float[5]}`=20 B qualifies, `{float[4]}`=16 B does not). The producer-side fix copies all trailing operands via `oldArg->getOperandCount()` and keys the specialization cache on them (otherwise `LoadAligned` miscompiles depending on source order), plus a loud `SLANG_RELEASE_ASSERT(operandCount==3)` at the legalizer, not a tolerant guard: the legalizer's own 2-operand loads at `:999` are terminal output never re-fed through `processLoad`. #8547 introduced the drop; #11595's explicit-alignment check made it fatal ([ByteAddressBuffer.Load<T>() + method/call-arg crash = specialization dropping the alignment operand](../learnings/1789577999587-byteaddressbuffer-load-lt-t-gt-method-call-arg-cra.md)).

A module-scope assert on the preserved operand (`SLANG_RELEASE_ASSERT(!getParentFunc(trailingOperand))`) looked unsafe for the single-arg `T LoadAligned<T>(uint location)` (`hlsl.meta.slang:490-492`). It forwards `__naturalAlignmentOf<T>()`, which lowers to `kIROp_GetNaturalAlignment`, a function-local, non-hoistable inst (`slang-ir-insts.lua:1377`); peephole skips it inside a generic (`slang-ir-peephole.cpp:1841`), and `-O0` runs no peephole before this pass ([ByteAddressBufferLoad alignment operand: natural-alignment overload is function-local until peephole](../learnings/1789579501578-byteaddressbufferload-alignment-operand-natural-al.md)). That concern is a false alarm: generic specialization and type legalization resolve `GetNaturalAlignment` on the concrete type to a module-scope literal before `specializeFuncsForBufferLoadArgs`, even at `-O0` and inside a user generic (`slangc … -O0 -dump-ir-after specializeFuncsForBufferLoadArgs` shows `4 : UInt` and no `getNaturalAlignment`). Keep the loud assert, since a fallback would be dead code, and prove non-reachability with `-dump-ir-after` plus an `-O0` regression arm ([Natural-alignment LoadAligned's alignment is folded to a literal before buffer-load-arg specialization](../learnings/1789580976960-natural-alignment-loadaligned-s-alignment-is-folde.md)). Triage rule: for any "buffer `Load<T>`/`Store<T>` + method or call-arg → crash", suspect a specialization or clone pass dropping a trailing operand, and check operand counts with `-dump-ir-after specializeFuncsForBufferLoadArgs`. DeepWiki wrongly says the load has no alignment operand; the lua definition and `hlsl.meta.slang` are authoritative.

**Pre-link peephole runs before buffer-load specialization can see the shape.** `peepholeOptimize` also runs during lower-to-IR (`PeepholeOptimizationOptions::getPrelinking()` in `slang-lower-to-ir.cpp`), before `specializeMatrixLayout` resolves `Unknown` matrix layouts. PR #13378 round 1 expanded an array `BuiltinCast` element by element there; that copied arrays whose layouts later proved identical and blocked `specializeFuncsForBufferLoadArgs`, taking a 64-bone cbuffer from 4 to 256 `cbufferLoadLegacy`. The fix keeps the cast as one instruction, lowers it in a late pass after buffer-load specialization, and lets the specializer see through value-preserving wrappers such as `CastDynamicResource`. Measuring traps: slang-test passes `-O0` to `//TEST:SIMPLE` slangc runs, and DXC at `-O0` emits ~3× the cbuffer loads of `-O2`, so pin `-O2`; `grep -c cbufferLoadLegacy` also counts the `declare`, so count `call` lines; an exhaustive `DIAGNOSTIC_TEST` needs an annotation for the second labelled diagnostic that E30019/E30047 each emit on the same span ([peephole runs pre-link: don't expand type-dependent casts there; SIMPLE uses -O0](../learnings/1790926336121-slang-peephole-runs-pre-link-don-t-expand-type-dep.md)).

## C-like emitter hazards: silent folds, null types, declaration cycles, and unused temps

Each hazard in the shared `CLikeSourceEmitter` (`slang-emit-c-like.cpp`) hits every text target (GLSL, HLSL, Metal, WGSL, CUDA, C++) while direct SPIR-V usually escapes, so one text-target probe does not cover the others.

**An always-fold rule placed above the side-effect checks deletes side effects.** In `shouldFoldInstIntoUseSites` the pointer-type early `return true` runs before the `!inst->hasUses()` check. On a target without pointer types (GLSL), an unused pointer-typed inst is "folded into zero use sites": never emitted, side effects lost, no diagnostic. Examples (#13414, fixed by #13410's `canHoldPtrTypeInTemporary`): an ignored `[noinline] int* f()` call, and `RWByteAddressBuffer.Store(off, ptr)`, whose legalized `RWStructuredBufferStore` takes the stored value's type as its result type. Any early `return true` above those checks has the same hazard. When reviewing an always-fold rule, probe an unused, side-effecting inst of the affected type; a GLSL-output sweep of master versus head over `tests/**/*.slang` (~2.8k compile) is a cheap way to find behaviour changes ([always-fold of pointer types drops unused side-effecting insts](../learnings/1790980787322-c-like-emitter-always-fold-of-pointer-types-also-d.md)).

**`NonUniformResourceIndex` is an always-folded user too, so it had the #13273 fold-order bug (#13548).** `shouldFoldInstIntoUseSites` (`:1556`) always folds `kIROp_NonUniformResourceIndex`, and the side-effect scan (:1869-1881) reached only the operand's direct user. So `load(%a)` folded into the NURI, the NURI was emitted at a later `store`, and the load was re-read after `store(%a)`: in `a = NonUniformResourceIndex(b); b = NonUniformResourceIndex(a);` the second assignment reads the new `a`. HLSL, GLSL, CUDA and C++ were wrong since at least 2025.1; direct SPIR-V was right. Unlike the GEP case, a `-cpu` COMPARE_COMPUTE test reproduces it (1,1 vs 1,0). The narrow `if (user->getOp() == kIROp_NonUniformResourceIndex) return false;` of #13539 would also fix it, but it changes three CUDA goldens (`nonuniformres-array-of-textures.4`, `nonuniformres-nested-rwstructuredbuf.4`, `unbounded-array-of-array-syntax.1`) and covers only one op ([NonUniformResourceIndex is an always-folded user too: #13273 fold-order bug class](../learnings/1791574480804-nonuniformresourceindex-is-an-always-folded-user-t.md)). What merged is the transitive fold legality of PR #13283 (the `getFoldPolicy` split on [[wiki/concepts/slang-a-compiler-internals.md]]), on 2026-10-17, after v2026.20 was tagged; it closes #13548 and adds `tests/bugs/gh-13548.slang`. Master 68438b5e1 emits `uint _S1 = b_0; uint _S2 = a_0; a_0 = NonUniformResourceIndex(_S1); ...` and fixes the #13273 `s.top` repro on GLSL, HLSL, Metal and WGSL; `isSafeToFoldIntoUseSites` now recurses into `FoldPolicy::Always` users (~:1929-1959) ([#13273 master build confirms fix](../learnings/1792426436559-13273-master-build-confirms-fix-emits-int-s1-s-top.md)). On v2026.20 and earlier, apply `NonUniformResourceIndex` at the resource index (`t[NonUniformResourceIndex(a)]`), which emits correctly; copying into new locals (`uint na = NURI(a); a = na;`) does not help, because SSA collapses the copies ([#13548 fixed by #13283, index-site workaround](../learnings/1792406922339-13548-nonuniformresourceindex-swap-miscompile-fixe.md)). Per-release status is on [[wiki/concepts/slang-tooling-release-tarball-repro-and-version-bisect.md]].

**A null data type means void.** `emitInstResultDecl` returns early when `inst->getDataType()` is null, the legitimate marker for void insts (`emitStore` and `emitReturn` build insts with a nullptr type). A pass that builds a value-producing inst with a null type therefore makes every text emitter print `expr;` with uses referencing an undeclared `_Sn`, and nothing diagnoses it: `-validate-ir` checks a type only when present. In #13380 / PR #13381 the VectorReshape peephole passed `as<IRVectorType>(scalarType)` (null) to `emitSwizzle`; only WGSL broke, because only its std140 cbuffer policy packs scalar arrays into `vec4` and reads them back through `vectorReshape(vec4->f32)`. The `-dump-ir` tell is `let %N : _ = ...`. The fix asserts at the builder, `SLANG_RELEASE_ASSERT(type)` in `IRBuilder::emitSwizzle` (a release assert, because `SLANG_ASSERT` becomes `SLANG_ASSUME` in Release; see slang-b-compiler-internals); for vector→scalar, reuse `IRBuilder::emitVectorReshape` ([a null data type means void to the C-like emitters](../learnings/1790912037059-slang-ir-a-null-data-type-means-void-to-the-c-like.md)).

**Self-referential pointer structs: break the cycle at the pointer.** `struct N { float v; N* next; }` reached through a pointer first (`cbuffer C { N* p; }`) aborts with E99997 `circularity during codegen` on GLSL, HLSL, Metal, CUDA, C++ and WGSL, since at least v2025.1; direct SPIR-V compiles it with `OpTypeForwardPointer` (#13396). `computeEmitActions` orders declarations by DFS, and the `kIROp_PtrType` arm of `ensureInstOperandsRec` relaxes to ForwardDeclaration only when the pointee is already open, which covers N→Ptr(N) but not Ptr(N)→N→Ptr(N). When that arm fires it downgrades all the pointer's operands, so an IntLit operand reaches `SLANG_UNREACHABLE("emit forward declaration")` in `emitForwardDeclaration`, the symptom when the struct is reached first (`cbuffer C { N n; }`). The prototyped fix forward-declares the pointer on the cycle and schedules its definition after the pointee closes. Deferring the pointee is wrong: GLSL has no struct forward declarations (glslang rejects `struct N;`; that variant broke 11 via-GLSL tests), whereas `layout(buffer_reference) buffer BufferPointer_N;` is legal. `CPPSourceEmitter::_emitForwardDeclarations` filters by op and must allow any new case; WGSL needs separate handling (no forward declarations; pointers already spelled `ptr<, T>`). To dump the cycle without gdb, temporarily add a `List<IRInst*> openStack` to `ComputeEmitActionsContext` and print it with `getIROpInfo(op).name` at the circularity check ([self-referential pointer structs crash every source target](../learnings/1790943808591-c-like-emit-ordering-self-referential-pointer-stru.md)).

**A literal's type is never scheduled for declaration.** The early `if (as<IRPtrLit>(inst)) return;` in `ensureGlobalInst` (added in #3561) skips the literal and its type. That was harmless while the literal never named its type (`nullptr`, or GLSL's old invalid `0`), but GLSL now spells it `BufferPointer_X(0UL)`, so a pointer type reachable only through a null literal is undeclared and glslang fails with "no matching overloaded function". Consider `float4* f = nullptr; out = int(uint64_t(f));` with nothing else of type `float4*`. The fix (#14088) calls `ensureInstOperand(ctx, inst->getFullType())` in that branch, gated to `SourceLanguage::GLSL` so other targets' output is unchanged. To catch the class, test a literal whose type has no other user [CLikeSourceEmitter::ensureGlobalInst skips an IRPtrLit's type — a pointer type used only by a null literal is never declared](../learnings/1793335984103-clikesourceemitter-ensureglobalinst-skips-an-irptr.md).

**A discarded atomic result still gets a named temp, and a generic skip in `emitInstResultDecl` is unsafe (#14058).** A discarded atomic RMW result has 0 uses at emit, but the atomic branch of `tryEmitInstStmtImpl` on Metal, GLSL, CUDA and WGSL still calls `emitInstResultDecl`; HLSL hand-rolls `T name; InterlockedX(dst, v, name)`. Metal's default warnings flag the temp `-Wunused-variable`; nvcc 12.6 is silent. Skipping the decl for every 0-use inst is wrong: SwizzleSet (~3453) and UpdateElement (~3530) write to `name` after the decl; GetDimensions, the AtomicLoad deref, the Metal image `….x` and WGSL `atomicCompareExchangeWeak(...).old_value` would leave non-call expression statements (`-Wunused-value` in clang, even `f().x;` without `-Wall`; hard errors in WGSL); and it never reaches the HLSL atomics. Gate each atomic path on non-debug uses and drop the texture `.x` too. No `hasNonDebugUse` helper exists yet (`isDebugInfoInst` is at `slang-ir-util.h:752`), and PR #14044 already adds a Metal `emitAtomicCall(…, bool returnsValue)` lambda with this skip path. DeepWiki wrongly claims `emitInstStmt` already skips the temp; check the emitted text [C-like emit: 0-use atomic results still get a named temp; a generic skip in emitInstResultDecl is unsafe](../learnings/1793312005041-c-like-emit-0-use-atomic-results-still-get-a-named.md).

## Memory-qualifier-drop diagnostic (E30048): a positive destination-type check is required

A checker diagnostic at a binding/copy boundary (the E30048 memory-qualifier-drop check, #13084) cannot be gated only on "the error count did not increase after `coerce`". If the destination type is ill-formed (`UndefinedType x = coherentBuf;`), its resolution error is emitted in the header phase and is already in the body-phase baseline; `coerce()` then accepts the `ErrorType` target with no new diagnostic, so the gate passes and E30048 fires spuriously (verified for both `int x = coherentBuf;` and `UndefinedType x = coherentBuf;`). The fix also requires the destination decl's type to be the expected kind, a resource handle. Two more traps. `isOpaqueHandleType(Type*)` (`slang-check-decl.cpp`) is broader than "read/write memory resource": it matches samplers, parameter groups, `RaytracingAccelerationStructureType` (a subclass of `UntypedBufferResourceType`), and patch/stream/mesh I/O, so use a dedicated predicate listing exactly the coherent read/write handle types. And the three var-init/assignment paths are asymmetric: `checkVarDeclCommon` (explicit init) and `checkAssignWithCheckedOperands` (assignment) carry the `if (initExpr->type.isWriteOnly) diagnose(ReadingFromWriteOnly)` (E30119) read-legality check, but `deriveVarTypeFromInitExpr` (type-inferred `var x = ...`) does not, so a `writeonly` source gives E30119 on the first two paths but E30048 (or nothing, pre-fix) on the third; `deriveVarTypeFromInitExpr` also assigns `varDecl->type.type` late (after CheckExpr and maybeOpenRef), so a destination-type check there must run after that assignment. Process lesson: codex CODE_REVIEW caught all of these after a peer review returned APPROVE_WITH_NITS (0 bugs), so run codex even after peer approval, and give it the full small file (a truncated `sed` excerpt caused a false must-fix) ([Memory-qualifier-drop diagnostic: destination-type check needed beyond an error-count gate](../learnings/1789543242916-memory-qualifier-drop-diagnostic-destination-type-.md)).
