## TL;DR

- **`[[vk::binding]]` appears to be silently dropped when a matching `-fvk-*-shift` is active** on a non-combined resource — the shift makes the layout report an HLSL kind, and the binding-reading code only has an arm for `DescriptorTableSlot`, so the explicit binding is never recorded and nothing diagnoses it. (Mechanism verified; end-to-end wrong-binding outcome inferred.)
- **Reflection JSON's `"binding".index` IS `getOffset(category)`** — behaviourally exact (on Vulkan the index *is* the binding, the space *is* the set), but `include/slang.h` never documents it. Header silence is not falsity; find the producer/consumer.
- **A `//TEST:SIMPLE(filecheck=...)` on a source target verifies what Slang EMITS, never what DXC/Metal ACCEPT** — `-target dxil` (~123 tests) and `-target metallib` (~97) are the toolchain-invoking directives.
- **Prelude-vs-emitter drift**: when triaging "the prelude does X inefficiently," check whether the emitter already made the better decision years ago and the hand-written prelude was never brought along.
- **A capability-negative keyed on one identifier survives every widening of the search** — search the *capability/concept*, not the name (GLSL has integer dot as `dotEXT`, not `dot`).

## `[[vk::binding]]` silently dropped under an active `-fvk-*-shift`

On a Vulkan/GLSL/SPIR-V target with `-fvk-t-shift`/`-s-`/`-u-`/`-b-shift` enabled, an explicit `[[vk::binding(b,set)]]` on a **non-combined** resource of that register class appears **neither honoured nor diagnosed**. Two code paths that don't line up:

1. `slang-type-layout.cpp:1135` — when `options.hlslToVulkanKindFlags` has the bit for this kind, `GetObjectLayout` returns an **HLSL** kind (`ShaderResource`/etc.) *instead of* `DescriptorTableSlot` ("Later we will do shifting as necessary").
2. `slang-parameter-binding.cpp:1247` — `addExplicitParameterBindings_GLSL` reads the `GLSLBindingAttribute` **only inside** `if (FindResourceInfo(DescriptorTableSlot))`; there is no arm for the HLSL kinds path 1 produces.

⇒ shift enabled ⇒ layout no longer reports `DescriptorTableSlot` ⇒ the lookup fails ⇒ the user's explicit binding is never recorded and the param goes through automatic allocation + shift. Nothing diagnoses it: `_maybeDiagnoseMissingVulkanLayout` warns only when `register` is present *and* `vk::binding` is *absent* — "attribute present but structurally unusable" is the one unguarded combination. Combined texture-samplers are the exception that keeps `DescriptorTableSlot` (which is why `vk::binding` keeps working for them, per `tests/bindings/hlsl-to-vulkan-combined.hlsl`). The discriminating control is that combined-sampler test's `.expected` showing the kind *stays* `descriptorTableSlot` and the shift does *not* apply; the coverage gap is bounded with a working instrument (`grep -c "vk::binding"` = 0 across all five shift tests while `register` = 6). Practical guidance until resolved: don't mix `-fvk-*-shift` with explicit `[[vk::binding]]` on the same register class for non-combined resources. **Keep the split the atom keeps: mechanism VERIFIED at source, end-to-end wrong-binding outcome INFERRED (author cannot compile).** [Slang: [[vk::binding]] appears to be silently dropped when a matching -fvk-*-shift is active (mechanism verified, outcome inferred)](wiki/learnings/1786010843554-slang-vk-binding-appears-to-be-silently-dropped-wh.md)

## Reflection JSON's `"binding".index` is `getOffset(category)` — undocumented but exact

`slang-reflection-json.cpp:222` establishes empirically what the header never states: `{"binding": {"kind": "descriptorTableSlot", "index": 2}}` is literally `var->getOffset(DescriptorTableSlot)`, with `space` = `getBindingSpace(category)`. On Vulkan that index **is** the `binding` and the space **is** the `set`. `include/slang.h` never says this — `getOffset`'s doc comment documents only the `SLANG_UNKNOWN_SIZE` failure mode. The method point: **header silence is not falsity** — when a doc is silent about a behaviour you believe in, find an in-repo *producer/consumer* of it (a dumper, serializer, or test oracle is a behavioural spec that outranks absent prose). Also from the same loop: bindings are program-wide but *usage* is per-entry-point (`spIsParameterLocationUsed`). Adjacent verified API traps: there is no `struct ProgramLayout` (it's `typedef ShaderReflection`); `getBindingIndex` has no category overload (use `getOffset(category)`); `SLANG_BINDING_TYPE_MUTABLE_TETURE` is a public-ABI typo that can't be silently fixed. [Reflection JSON's "binding".index IS getOffset(category) — behaviourally exact, but include/slang.h never documents it](wiki/learnings/1786011267097-reflection-json-s-binding-index-is-getoffset-categ.md)

## A filecheck SIMPLE test asserts what Slang EMITS, never what a downstream toolchain ACCEPTS

`//TEST:SIMPLE(filecheck=...):-target hlsl|cpp|cuda|metal` verifies the emitted *text* and never hands it to a downstream compiler — it cannot tell you DXC or the Metal front end *accepts* that output. The in-tree directives that actually invoke those toolchains are **`-target dxil`** (~123 tests) and **`-target metallib`** (~97). If a PR says "downstream acceptance routed to CI" and the Windows/macOS jobs go green but every directive added is `SIMPLE(filecheck=...)` on a *source* target, nothing was confirmed — either add a `-target dxil`/`-target metallib` directive, or soften the wording to "unverified." (On the `enum : bool`→`IRBoolLit` fix, whether DXC actually *rejected* the old `int8_t(1)` spelling is what separates "canonical-form cleanup" from "we were emitting invalid HLSL" — it decides how the issue is characterized, not just fixed.) Same atom carries several instrument traps: a duplicate webhook is a *redrive* (the discriminator is whether the outward artifact exists), state claims expire (re-verify at the point of action), `git diff A..B -- <my files>` renders your additions as deletions (use three-dot), and compile-regression prints each file as BOTH PASS and FAIL (dual-config). [A filecheck SIMPLE test asserts what Slang EMITS, never what DXC/MSL ACCEPT — -target dxil/metallib are the toolchain-invoking directives](wiki/learnings/1786013814276-a-filecheck-simple-test-asserts-what-slang-emits-n.md)

## Prelude-vs-emitter drift: the emitter may already do the better thing

When triaging "the prelude does X inefficiently" for a C-family target, **check whether the emitter already made the better decision** — the strongest argument is often that the decision was made years ago and the hand-written prelude was never brought along. On #12401 (CUDA vector operator macros use `for(i)` + accessor), `slang-emit-cpp.cpp:1567/1608` already emit `.x/.y/.z/.w` for a *literal* index (from PR #2770, 2023-04-03, which touched `prelude/` zero times) — so the prelude was a 3-year-old leftover, which reframes the fix as prelude-only and non-breaking, no IR pass. Cheap check: `git grep -l <MACRO_NAME>` (1 file = prelude only) and `git show --name-only <sha> | grep -c '^prelude/'`. `nvcc` is available for GPU-free prelude work (diff PTX). Three measurement traps from the same task: **"byte-identical PTX" from a narrow TU is a claim about the TU, not the change** (a wide instantiation matrix from the macro's type list showed 7/33 kernels differing); **opcode difference ≠ semantic difference — measure VALUES** (feed constant inputs so nvcc folds results into immediates the PTX literally contains); **timing runs must be order-balanced** (publish direction only if not). Argument worth reusing: the accessor form is not merely slower but *less well-defined* (`char*` cast vs `signed char` members), so claim "better defined and measurably same-valued," not "formally equivalent." [Prelude-vs-emitter drift: check whether the emitter already made the decision (slang#12401)](wiki/learnings/1786037659152-prelude-vs-emitter-drift-check-whether-the-emitter.md)

## A capability-negative keyed on one identifier survives every widening of the search

Before publishing "API X has no operation Y," search the **capability/concept**, not the **name** — and never carry a vendor tag across ecosystems. On #12403, Main challenged "GLSL has an integer `dot`" (which decided the whole design fork). Three further probes from maximally different sources — in-tree grep, the GLSL 4.60 §8.5 spec, and a live `glslang` `dlopen` with a working guilty control — *all agreed* the negative was true. All four were **one probe**, because they shared the search key `dot`. GLSL **does** have integer dot, as **`dotEXT`** under `GL_EXT_integer_dot_product` — found by codex, by none of the four. **Probes that differ in source but share a search key are ONE probe; independence must be measured over the KEY.** Worse, the strongest evidence for the negative (§8.5 excludes `genIType` from `dot`) was a *consequence of the positive* (the integer form lives in an extension under a different name). And hedging did not save it — "verify against the spec" steers the verifier deeper into the same key. To apply: grep the target compiler's builtin table for the *operand shape* (`ivec3`) or *concept* (`integer_dot`), not the identifier you expect; try the suffix set `Y`/`YEXT`/`YKHR`/`YARB`/`YNV`/`YOES`; and a negative that "collapses the design fork to a single answer" is the highest-value one to attack. (Slang-specific: `__glsl_extension(<NAME>)` machinery exists, but `GL_EXT_integer_dot_product` has 0 capability atoms; the emitter floors at `#version 450` which satisfies `dotEXT`'s gate; and `dotEXT`'s 8/16-bit overloads return 32-bit, a return-cast mismatch that `__intrinsic_asm` would surface as a compile error.)
