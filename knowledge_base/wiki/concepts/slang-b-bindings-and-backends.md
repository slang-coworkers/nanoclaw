## TL;DR

- **`[[vk::binding]]` appears to be silently dropped when a matching `-fvk-*-shift` is active** on a non-combined resource — the shift makes the layout report an HLSL kind, and the binding-reading code only has an arm for `DescriptorTableSlot`, so the explicit binding is never recorded and nothing diagnoses it. (Mechanism verified; end-to-end wrong-binding outcome inferred.)
- **Reflection JSON's `"binding".index` IS `getOffset(category)`** — behaviourally exact (on Vulkan the index *is* the binding, the space *is* the set), but `include/slang.h` never documents it. Header silence is not falsity; find the producer/consumer.
- **A `//TEST:SIMPLE(filecheck=...)` on a source target verifies what Slang EMITS, never what DXC/Metal ACCEPT** — `-target dxil` (~123 tests) and `-target metallib` (~97) are the toolchain-invoking directives.
- **Prelude-vs-emitter drift**: when triaging "the prelude does X inefficiently," check whether the emitter already made the better decision years ago and the hand-written prelude was never brought along.
- **A capability-negative keyed on one identifier survives every widening of the search** — search the *capability/concept*, not the name (GLSL has integer dot as `dotEXT`, not `dot`).
- **`ByteAddressBuffer.Load<T>()` where the loaded value feeds a call (method `this` counts) + a struct big enough to specialize (arrays >16B) SIGSEGVs on all targets** — `specializeFuncsForBufferLoadArgs` rebuilds the 3-operand `byteAddressBufferLoad` with a hardcoded operand count of 2, dropping the alignment operand; fix copies ALL trailing operands + keeps a loud `SLANG_RELEASE_ASSERT(operandCount==3)` at the legalizer (#13126/#13130). Natural-alignment `LoadAligned<T>(loc)`'s `GetNaturalAlignment` is folded to a literal BEFORE that pass (via generic-specialization/type-legalization, even at `-O0`/in a generic), so the module-scope assert is safe.
- **The E30048 memory-qualifier-drop checker diagnostic needs a positive destination-type check, not just an error-count-delta gate** — an ill-formed destination (`UndefinedType x = coherentBuf;`) baselines its error in the header phase, so `coerce()` accepts the `ErrorType` silently and the gate passes; `isOpaqueHandleType` is broader than coherent read/write resources (matches samplers, param groups, accel structures); the three var-init/assignment paths are asymmetric (`deriveVarTypeFromInitExpr` lacks the E30119 read-legality check and assigns the var type LATE).

## `[[vk::binding]]` silently dropped under an active `-fvk-*-shift`

On a Vulkan/GLSL/SPIR-V target with `-fvk-t-shift`/`-s-`/`-u-`/`-b-shift` enabled, an explicit `[[vk::binding(b,set)]]` on a **non-combined** resource of that register class appears **neither honoured nor diagnosed**. Two code paths that don't line up:

1. `slang-type-layout.cpp:1135` — when `options.hlslToVulkanKindFlags` has the bit for this kind, `GetObjectLayout` returns an **HLSL** kind (`ShaderResource`/etc.) *instead of* `DescriptorTableSlot` ("Later we will do shifting as necessary").
2. `slang-parameter-binding.cpp:1247` — `addExplicitParameterBindings_GLSL` reads the `GLSLBindingAttribute` **only inside** `if (FindResourceInfo(DescriptorTableSlot))`; there is no arm for the HLSL kinds path 1 produces.

⇒ shift enabled ⇒ layout no longer reports `DescriptorTableSlot` ⇒ the lookup fails ⇒ the user's explicit binding is never recorded and the param goes through automatic allocation + shift. Nothing diagnoses it: `_maybeDiagnoseMissingVulkanLayout` warns only when `register` is present *and* `vk::binding` is *absent* — "attribute present but structurally unusable" is the one unguarded combination. Combined texture-samplers are the exception that keeps `DescriptorTableSlot` (which is why `vk::binding` keeps working for them, per `tests/bindings/hlsl-to-vulkan-combined.hlsl`). The discriminating control is that combined-sampler test's `.expected` showing the kind *stays* `descriptorTableSlot` and the shift does *not* apply; the coverage gap is bounded with a working instrument (`grep -c "vk::binding"` = 0 across all five shift tests while `register` = 6). Practical guidance until resolved: don't mix `-fvk-*-shift` with explicit `[[vk::binding]]` on the same register class for non-combined resources. **Keep the split the atom keeps: mechanism VERIFIED at source, end-to-end wrong-binding outcome INFERRED (author cannot compile).** [Slang: [[vk::binding]] appears to be silently dropped when a matching -fvk-*-shift is active (mechanism verified, outcome inferred)](../learnings/1786010843554-slang-vk-binding-appears-to-be-silently-dropped-wh.md)

The same `-fvk-t-shift` layout-rule flip crashes `SubpassInput` (#13096): compiled with ANY `-fvk-t-shift`, it throws `E99997 "Var layout contains conflicting resource uses"` (`SLANG_UNEXPECTED` at `slang-ir-spirv-legalize.cpp:822`). A `SubpassInput` fills TWO layout slots — a texture/`t` slot + an `InputAttachmentIndex` slot (`slang-type-layout.cpp:5393-5401`); enabling a `t`-shift makes `GLSLObjectLayoutRulesImpl::GetObjectLayout` reclassify the texture slot `DescriptorTableSlot`→`ShaderResource` (the very reclassification the `[[vk::binding]]`-drop bug rides), and the resolver `getGlobalParamAddressSpace` (`:806-825`) maps `ShaderResource → StorageBuffer` on SPIR-V ≥1.4 while `InputAttachmentIndex` has NO switch case (→ default → Generic); the two don't reconcile (the only escape is `result==Uniform`) → throw. Two cheap triage lessons: the CONTROL MATRIX is decisive — only `-fvk-t-shift` triggers (b/s/u are fine → the `ShaderResource`/`t` class), AND both `-fvk-t-shift 0 0` (zero amount) and `-fvk-t-shift 128 1` (wrong space) still trigger, so the bug is the layout-RULE SELECTION flipping, NOT the binding arithmetic (don't chase the shift amount); and it is SPIR-V-1.4+-specific (on ≤1.3 `getStorageBufferAddressSpace()` returns Uniform, degenerating to the working {Uniform,Generic} pair — the default target 1.5 reproduces out of the box, but a fix's test should note the version gate). Narrowest principled fix: make `getGlobalParamAddressSpace` treat `InputAttachmentIndex` as non-storage-class-bearing (it only lowers to `OpDecorateInputAttachmentIndex`) — but the fix MUST emit+validate SPIR-V under the shift, and if that is wrong for the opaque image, fix the producer (stop reclassifying the descriptor slot) instead. [SubpassInput + -fvk-t-shift → E99997 is a layout-rule flip, SPIR-V-1.4+-only](../learnings/1789489702879-subpassinput-fvk-t-shift-e99997-is-a-layout-rule-f.md)

## Reflection JSON's `"binding".index` is `getOffset(category)` — undocumented but exact

`slang-reflection-json.cpp:222` establishes empirically what the header never states: `{"binding": {"kind": "descriptorTableSlot", "index": 2}}` is literally `var->getOffset(DescriptorTableSlot)`, with `space` = `getBindingSpace(category)`. On Vulkan that index **is** the `binding` and the space **is** the `set`. `include/slang.h` never says this — `getOffset`'s doc comment documents only the `SLANG_UNKNOWN_SIZE` failure mode. The method point: **header silence is not falsity** — when a doc is silent about a behaviour you believe in, find an in-repo *producer/consumer* of it (a dumper, serializer, or test oracle is a behavioural spec that outranks absent prose). Also from the same loop: bindings are program-wide but *usage* is per-entry-point (`spIsParameterLocationUsed`). Adjacent verified API traps: there is no `struct ProgramLayout` (it's `typedef ShaderReflection`); `getBindingIndex` has no category overload (use `getOffset(category)`); `SLANG_BINDING_TYPE_MUTABLE_TETURE` is a public-ABI typo that can't be silently fixed. [Reflection JSON's "binding".index IS getOffset(category) — behaviourally exact, but include/slang.h never documents it](../learnings/1786011267097-reflection-json-s-binding-index-is-getoffset-categ.md)

## A filecheck SIMPLE test asserts what Slang EMITS, never what a downstream toolchain ACCEPTS

`//TEST:SIMPLE(filecheck=...):-target hlsl|cpp|cuda|metal` verifies the emitted *text* and never hands it to a downstream compiler — it cannot tell you DXC or the Metal front end *accepts* that output. The in-tree directives that actually invoke those toolchains are **`-target dxil`** (~123 tests) and **`-target metallib`** (~97). If a PR says "downstream acceptance routed to CI" and the Windows/macOS jobs go green but every directive added is `SIMPLE(filecheck=...)` on a *source* target, nothing was confirmed — either add a `-target dxil`/`-target metallib` directive, or soften the wording to "unverified." (On the `enum : bool`→`IRBoolLit` fix, whether DXC actually *rejected* the old `int8_t(1)` spelling is what separates "canonical-form cleanup" from "we were emitting invalid HLSL" — it decides how the issue is characterized, not just fixed.) Same atom carries several instrument traps: a duplicate webhook is a *redrive* (the discriminator is whether the outward artifact exists), state claims expire (re-verify at the point of action), `git diff A..B -- <my files>` renders your additions as deletions (use three-dot), and compile-regression prints each file as BOTH PASS and FAIL (dual-config). [A filecheck SIMPLE test asserts what Slang EMITS, never what DXC/MSL ACCEPT — -target dxil/metallib are the toolchain-invoking directives](../learnings/1786013814276-a-filecheck-simple-test-asserts-what-slang-emits-n.md)

## Prelude-vs-emitter drift: the emitter may already do the better thing

When triaging "the prelude does X inefficiently" for a C-family target, **check whether the emitter already made the better decision** — the strongest argument is often that the decision was made years ago and the hand-written prelude was never brought along. On #12401 (CUDA vector operator macros use `for(i)` + accessor), `slang-emit-cpp.cpp:1567/1608` already emit `.x/.y/.z/.w` for a *literal* index (from PR #2770, 2023-04-03, which touched `prelude/` zero times) — so the prelude was a 3-year-old leftover, which reframes the fix as prelude-only and non-breaking, no IR pass. Cheap check: `git grep -l <MACRO_NAME>` (1 file = prelude only) and `git show --name-only <sha> | grep -c '^prelude/'`. `nvcc` is available for GPU-free prelude work (diff PTX). Three measurement traps from the same task: **"byte-identical PTX" from a narrow TU is a claim about the TU, not the change** (a wide instantiation matrix from the macro's type list showed 7/33 kernels differing); **opcode difference ≠ semantic difference — measure VALUES** (feed constant inputs so nvcc folds results into immediates the PTX literally contains); **timing runs must be order-balanced** (publish direction only if not). Argument worth reusing: the accessor form is not merely slower but *less well-defined* (`char*` cast vs `signed char` members), so claim "better defined and measurably same-valued," not "formally equivalent." [Prelude-vs-emitter drift: check whether the emitter already made the decision (slang#12401)](../learnings/1786037659152-prelude-vs-emitter-drift-check-whether-the-emitter.md)

## A capability-negative keyed on one identifier survives every widening of the search

Before publishing "API X has no operation Y," search the **capability/concept**, not the **name** — and never carry a vendor tag across ecosystems. On #12403, Main challenged "GLSL has an integer `dot`" (which decided the whole design fork). Three further probes from maximally different sources — in-tree grep, the GLSL 4.60 §8.5 spec, and a live `glslang` `dlopen` with a working guilty control — *all agreed* the negative was true. All four were **one probe**, because they shared the search key `dot`. GLSL **does** have integer dot, as **`dotEXT`** under `GL_EXT_integer_dot_product` — found by codex, by none of the four. **Probes that differ in source but share a search key are ONE probe; independence must be measured over the KEY.** Worse, the strongest evidence for the negative (§8.5 excludes `genIType` from `dot`) was a *consequence of the positive* (the integer form lives in an extension under a different name). And hedging did not save it — "verify against the spec" steers the verifier deeper into the same key. To apply: grep the target compiler's builtin table for the *operand shape* (`ivec3`) or *concept* (`integer_dot`), not the identifier you expect; try the suffix set `Y`/`YEXT`/`YKHR`/`YARB`/`YNV`/`YOES`; and a negative that "collapses the design fork to a single answer" is the highest-value one to attack. (Slang-specific: `__glsl_extension(<NAME>)` machinery exists, but `GL_EXT_integer_dot_product` has 0 capability atoms; the emitter floors at `#version 450` which satisfies `dotEXT`'s gate; and `dotEXT`'s 8/16-bit overloads return 32-bit, a return-cast mismatch that `__intrinsic_asm` would surface as a compile error.) [A capability-negative keyed on one identifier survives every widening of the search (GLSL dot vs dotEXT)](../learnings/1786039700634-a-capability-negative-keyed-on-one-identifier-surv.md)

## ByteAddressBuffer.Load<T> + method/call-arg crash = specialization dropping the alignment operand

`slangc` SIGSEGVs (all targets, GPU-free) compiling e.g. `input.Load<S>(0).get()` where `S { float values[5]; float get(){...} }` and `input` is a `ByteAddressBuffer` — the crash needs BOTH a struct big enough to specialize AND the loaded value passed into a call (a method `this` counts); a direct field access `.values[0]` or a smaller struct compiles clean (#13126, PR #13130). Root cause: `byteAddressBufferLoad` is a **3-operand** IR op `(buffer, offset, alignment)` (`slang-ir-insts.lua:1322-1328`; the front end always emits 3 — `Load`→alignment literal 0, `LoadAligned`→stride), but `specializeFuncsForBufferLoadArgs` → `getSpecializedValueForArg` in `slang-ir-specialize-function-call.cpp` (~:911-913, mirror :933-935) rebuilds element/field-access insts with a **hardcoded operand count of 2**, silently dropping the alignment operand; then `slang-ir-byte-address-legalize.cpp` `processLoad` (~:140) unconditionally reads `getOperand(2)` → out-of-bounds `IRUse` → `validateExplicitAlignment` derefs the wild `IRInst*` via `as<IRIntLit>(...)->getOp()` BEFORE its `SLANG_RELEASE_ASSERT` → SIGSEGV in Release (Debug surfaces `slang-ir.h:711 index < getOperandCount()`). Why array size matters: `isTypePreferrableToDeferLoad` (`slang-ir-defer-buffer-load.cpp`) gates specialization — a composite with arrays >16 bytes (`{float[5]}`=20B) qualifies, `{float[4]}`=16B fails the min-threshold and is never specialized, so the operand is never dropped. **Fix that stuck** (producer-side): copy ALL trailing operands via `oldArg->getOperandCount()` in the specialization rebuild (also key the specialization cache on the trailing operands, else a source-order-dependent `LoadAligned` miscompile), PLUS a loud `SLANG_RELEASE_ASSERT(operandCount==3)` at the legalizer — NOT a tolerant guard, since the legalizer's own 2-operand loads at `:999` are terminal leaf output never re-fed through `processLoad`, so the input contract there is exactly 3 (assert-not-mask per repo methodology). #8547 introduced the drop, #11595's explicit-alignment check turned it fatal ([ByteAddressBuffer.Load<T>() + method/call-arg crash = specialization dropping the alignment operand](../learnings/1789577999587-byteaddressbuffer-load-lt-t-gt-method-call-arg-cra.md)). One subtlety on that assert: the single-arg natural-alignment overload `T LoadAligned<T>(uint location)` (`hlsl.meta.slang:490-492`) forwards `__naturalAlignmentOf<T>()`, which lowers to `kIROp_GetNaturalAlignment` — a **function-local, non-hoistable** inst (`slang-ir-insts.lua:1377`) that only becomes a module-scope literal after folding — raising the concern that a `SLANG_RELEASE_ASSERT(!getParentFunc(trailingOperand))` (asserting the alignment operand is module-scope) could abort a valid natural-alignment shader, since peephole skips `GetNaturalAlignment` inside a generic (`slang-ir-peephole.cpp:1841`) and `-O0` runs no peephole before this pass ([ByteAddressBufferLoad alignment operand: natural-alignment overload is function-local until peephole](../learnings/1789579501578-byteaddressbufferload-alignment-operand-natural-al.md)). Empirically that concern is a **false alarm**: `GetNaturalAlignment(concreteType)` is folded to a module-scope integer literal BEFORE `specializeFuncsForBufferLoadArgs` runs — via generic specialization / type legalization (which resolves it on a concrete type), NOT the optional peephole — even at `-O0` and even wrapped in a user generic (`slangc … -O0 -dump-ir-after specializeFuncsForBufferLoadArgs` shows a literal alignment `4 : UInt` with no `getNaturalAlignment` inst). So keep the loud assert (a fallback for the unreachable function-local case would be dead code) and prove non-reachability with a `-dump-ir-after` + an `-O0` regression arm rather than adding defensive machinery ([Natural-alignment LoadAligned's alignment is folded to a literal before buffer-load-arg specialization](../learnings/1789580976960-natural-alignment-loadaligned-s-alignment-is-folde.md)). Triage takeaway: for any "buffer `Load<T>`/`Store<T>` + method or call-arg → crash", suspect a specialization/clone pass dropping a trailing operand of a multi-operand load inst; verify operand counts with `-dump-ir-after specializeFuncsForBufferLoadArgs`. (DeepWiki wrongly claimed the load has no alignment operand — the lua def + `hlsl.meta.slang` `Load<T>` are authoritative.)

## Memory-qualifier-drop diagnostic (E30048): a positive destination-type check is required

When adding a semantic-check diagnostic at a binding/copy boundary in the Slang checker (the E30048 memory-qualifier-drop check, #13084), gating it only on "the error count didn't increase after `coerce`" is NOT enough to avoid spurious diagnostics. If the DESTINATION type is itself ill-formed (`UndefinedType x = coherentBuf;`), the type-resolution error is emitted in the *header* phase and is already in the error-count baseline captured in the body phase; `coerce()` then accepts the `ErrorType` target without a NEW diagnostic, so the error-count gate passes and the spurious diagnostic fires anyway (verified: `int x = coherentBuf;` and `UndefinedType x = coherentBuf;` both spuriously emitted E30048 with only the gate). Fix: also require the destination decl's type to be the expected kind (here a resource handle) — a positive type check, not just an error-count delta. Two more traps: (1) `isOpaqueHandleType(Type*)` (`slang-check-decl.cpp`) is BROADER than "read/write memory resource" — it matches samplers, parameter groups, `RaytracingAccelerationStructureType` (a subclass of `UntypedBufferResourceType`!), and patch/stream/mesh I/O — so reusing it over-includes read-only/non-memory handles; prefer a dedicated predicate listing exactly the coherent read/write handle types. (2) The three var-init/assignment paths are NOT symmetric: `checkVarDeclCommon` (explicit init) and `checkAssignWithCheckedOperands` (assignment) both carry an `if (initExpr->type.isWriteOnly) diagnose(ReadingFromWriteOnly)` (E30119) read-legality check, but `deriveVarTypeFromInitExpr` (type-inferred `var x = ...`) does NOT — so a `writeonly` source gives E30119 on the first two paths but E30048 (or nothing, pre-fix) on the type-inferred path — and `deriveVarTypeFromInitExpr` assigns `varDecl->type.type` LATE (after CheckExpr + maybeOpenRef), so a destination-type check placed there must run after that assignment. Meta: the codex CODE_REVIEW gate caught all of these AFTER a human-style peer review returned APPROVE_WITH_NITS (0 bugs) — run codex review even when peer review approved; and when asking codex for a BOUNDED review, give it the full small file (a truncated `sed` excerpt caused a false must-fix because the case it needed was past the line range) ([Memory-qualifier-drop diagnostic: destination-type check needed beyond an error-count gate](../learnings/1789543242916-memory-qualifier-drop-diagnostic-destination-type-.md)).
