# Slang Test — Output Assertions and Truncated Runs

This page covers the ways a slang-test run can go **green while asserting nothing about a failing compile or a curtailed run**: output-path and exit-status assertions (`-o /dev/null` passing on a failing compile, `-g` making `result code = 0` self-match, `-o -` vs dropping `-o`), the bare-`grep -c` / `OpString` self-match counting trap, and the `100% of tests passed` fake-pass on a run truncated by the consecutive-failure breaker (the `failed(pending retry)` grep, and why you must never store the denominator). FileCheck authoring, `CHECK-NOT` regions, and opt-level plumbing live in the sibling page [Slang Test — FileCheck Authoring and Opt-Levels](slang-test-filecheck-authoring-and-opt-levels.md). Directive authoring is in [part 1](slang-misc-test-harness.md); running the harness and its false greens are in [slang-test False Greens and Verification Discipline](slang-test-false-greens-and-verification-traps.md).

## TL;DR

- **Never write a dump-based FileCheck test to `-o /dev/null`.** It is Windows-invalid (`error[E00004]`, exit 255) yet `-dump-ir` already printed the matched text, so the test stays GREEN. Use `-o -` plus a status assertion.
- **`-o -` and dropping `-o` are not equivalent — with `-g`, dropping `-o` flips the driver into `-whole-program` mode**, silently changing what is compiled. Prefer `-o -`.
- **A bug that needs several entry points in ONE module hides from slangc-to-stdout and from a plain `//TEST:SIMPLE`** — both generate code one entry point at a time. `-o <file>` or `-whole-program` emits one module (Metal SIMPLE already does); render-test always compiles `computeMain` alone and ignores `-entry`, so no COMPARE_COMPUTE test can exercise two-entry-point emission, and a test mixing SIMPLE legs with a COMPARE_COMPUTE leg must name its entry `computeMain` (else E38000).
- **Write `result code = {{0}}`, not `result code = 0`.** Under `-g` the IR dump embeds the whole source, so the literal matches its own comment echoed back and passes even when the real exit was 255. `{{N}}` is evaluated as a regex; `{N}` is the inert spelling.
- **The IR dump / `OpString` self-match is the same family** — the whole source, including your `//CHECK` lines, lands in the dump, so a `CHECK-NOT` or positive `CHECK-DAG` can match its own echoed comment with no real instruction present. Break the literal and anchor on the opcode.
- **Never count with a bare `grep -c '<Op>'`** — it counts your own comment lines echoed in the `OpString`. Use `grep -cE 'OpExtInst.*<Op>'`.
- **A `CHECK: <decl-name>` on a spirv/glsl SIMPLE lane passes on a failed compile** — stderr is in the buffer and the dumped module still has the `OpName`. Check the lowered op, put `CHECK: result code = 0` first, and run with `SLANG_RUN_SPIRV_VALIDATION=1` (CI sets it; local runs don't).
- **`//TEST:SIMPLE(filecheck=…)` never checks the result code.** Downstream compilers (metallib) quote the source line in their errors, so `LIB: computeMain` matches a failed compile. Use a success-only pattern (`define void @computeMain`) or assert `result code = {{0}}`. A NOT-only lane (`X-NOT: error :`) gates on nothing — it passes when slangc itself fails; always pair a NOT with a positive anchor.
- **A `-NOT` after a stdout match never sees stderr.** The buffer order is result code, stderr, stdout, so `X: <emitted code>` followed by `X-NOT: <diagnostic>` cannot fail. Assert "no diagnostics" with an annotation-free `//DIAGNOSTIC_TEST:SIMPLE(diag=X):`, or put the NOT before the first stdout match.
- **Reproduce the Windows `-o /dev/null` failure on Linux with `-dump-ir -o /nonexistent-dir/out.spv`** — same `E00004`, exit 255, IR still dumped, test still green. That is the negative control for any `result code` assertion.
- **`slang-test` reports `100% of tests passed (264/264)` on a run TRUNCATED by its consecutive-failure breaker** — disqualifying failures never *enter* the total (`PendingRetry` prints before `m_totalTestCount++`), so the percentage is arithmetically true and answers a different question.
- **The percentage prints to stdout while the bail notice `fprintf(stderr,…)`s**, so `cmd 2>/dev/null | grep '% of tests passed'` discards the disqualifying fact by construction.
- **Grep `2>&1` for `% of tests passed|Stopped scheduling|Skipping retries|failed\(pending retry\)|failing tests`.** `failed(pending retry)` is the load-bearing term (stdout, fired 265× on a real truncated run) and validated both directions.
- **Never store a per-directory total as a constant** — a stored count silently ages. Derive the expected value in the same session, or run a two-sided neuter→run→restore→run drill that never needs the absolute number.
- **Never use `$?`** — `slang-test` exits 0 even with failing tests. And a positive control that returns zero is telling you the control is wrong, not that the world is clean.
- **Under `-output-using-type`, anchor buffer checks to the value line.** The dump opens `type: uint32_t` and then prints ONE value per line, so a bare `// BUF: 2` matches the `2` inside `uint32_t` and passes when the real value is `1`, while a one-line `CHECK: 3.0, 1.0` never matches and fails on correct values. Write `// BUF: type: uint32_t` then one `// BUF-NEXT: {{^}}2{{$}}` per value, and read `<test>.actual.txt` before trusting a PASS or FAIL.
- **Prove a regression test fails on master with master's own `slang-test`, run from that tree's root.** `-bindir <other>/bin` does not switch the compiler under test for SIMPLE or COMPARE_COMPUTE tests (the invoked slang-test loads its own libslang through RUNPATH). Include one test known to fail on master and confirm it fails.
- **Ask of every new test: what would have to break for this to stay green?** If the answer includes "the compile fails," the test needs a status assertion.
- **DIAGNOSTIC_TEST has no negative directive.** `parseAnnotations` recognizes only `//PREFIX:` and `/*PREFIX:`, so `//PREFIX-NOT: E36107` is silently inert and a `non-exhaustive` test passes while the diagnostic fires (17 test files carried such lines on 2026-10-12). Assert absence with an exhaustive DIAGNOSTIC_TEST that has no annotations, or with a filecheck test.
- **`// CHECK:` with a space between `//` and `CHECK` is inert in a DIAGNOSTIC_TEST too** — the marker is built as `"//" << prefix << ":"`. Pin an error code in a caret annotation (`^^^^ error E39033`), and mutate the code to prove the row is live.

## Output paths and status assertions: `-o /dev/null` passes on a failing compile; `-g` makes `result code = 0` self-match (2026-08-04 fold)

**Never write a dump-based FileCheck test to `-o /dev/null`.** This supersedes an earlier note calling it "the idiomatic pattern" for `-dump-ir` tests — it is an anti-pattern, fixed repo-wide in #12333 / PR #12334. `/dev/null` is not a valid output path on **Windows**, so slangc reports `error[E00004]: cannot write output file` and returns a non-zero code (−1/255), yet the test still **passes**: `-dump-ir` prints the IR the assertions match *before* codegen reaches the failing write, and FileCheck only checks text it was told to look for, so a nonzero result code is invisible unless asserted. Net effect is a test that appears to guard a behavior but would keep passing if the compiler stopped working on that path entirely — on one platform, silently, permanently. Caught by pdeayton-nv in review on #12281, not by CI ([dump-based FileCheck tests need `-o -` and an explicit `result code = 0`](../learnings/1785775051459-dump-based-filecheck-tests-need-o-and-an-explicit-.md)). Use **`-o -`** (stdout, valid on every host) and pin the exit status. Note `-o -` and *dropping* `-o` are **not** equivalent: both make the backend run when the test has an entry point and are byte-identical for plain tests, but **with `-g`, dropping `-o` flips the driver into `-whole-program` mode** (visible verbatim in the `-g`-embedded debug string), silently changing what is compiled — prefer `-o -`.

**And the status assertion itself has an inert spelling.** `slang-test` builds the FileCheck buffer as `result code = <N>` / `standard error = {…}` / `standard output = {…}` (`slang-test-main.cpp:1876`), so `// PREFIX: result code = 0` normally pins the exit status — but under `-g` the IR dump embeds the whole source file in `DebugSource("<path>", "<file text>")` insts, so the literal matches **its own comment echoed back inside the dump** and passes even when the real first line is `result code = 255`. Measured: `result code = 0` passed on both a healthy and a forced-failing compile; `result code = {{0}}` passed healthy and **failed** on the failing compile. Break the literal — `{{…}}` is a FileCheck regex, so it matches the digit without the pattern text containing the digit that would self-match. (A reviewer confidently claimed `{{0}}` means literal `{0}`; disproven by control — `{0}` passes on a healthy compile, i.e. it *is* the inert spelling, and `{{1}}` fails on an exit-0 compile, so `{{N}}` is evaluated as a regex.) This is the same family as the known `-g2` `OpString` self-match trap one layer earlier (IR dump, not emitted SPIR-V), where the whole source including `//CHECK` lines lands in an `OpString`: a `CHECK-NOT: DebugGlobalVariable` matches its own comment text, and a positive `CHECK-DAG: DebugGlobalVariable {{.*}} %payload` can pass on the echoed comment with no real instruction present — confirm the hazard is live with `slangc … | grep -o 'CHECK-DAG: <your text>'` returning your own line, and fix by breaking the literal and anchoring on the opcode (`OpExtInst {{.*}} Debug{{Global}}Variable`). **Corollary: never count with a bare `grep -c '<Op>'`** — it counts the test file's own comment lines echoed in the `OpString`, which inflated a figure published to a maintainer (claimed 3 debug records; the real answer was 1); use `grep -cE 'OpExtInst.*<Op>'` ([FileCheck tests that pass without testing anything: bounded CHECK-NOT and OpString self-match](../learnings/1785779116844-filecheck-tests-that-pass-without-testing-anything.md), [never use `-o /dev/null` in slang tests — and `-g` makes `result code` assertions self-match](../learnings/1785787436624-never-use-o-dev-null-in-slang-tests-and-g-makes-re.md)).

Reproduce the Windows failure on Linux with no Windows box: substitute an unwritable path (`-dump-ir -o /nonexistent-dir/out.spv`) — same `E00004`, exit 255, IR still fully dumped, test still green. That is the negative control for any `result code` assertion you add. **Known latent instance:** `tests/autodiff/func-extension/subscript-accessor.slang` still carries the `-o /dev/null` pattern (surfaced to pdeayton-nv, deliberately out of scope on #12281) — a cheap standalone fix for whoever next touches that area. The unifying question for any new test: *"what would have to break for this to stay green?"* — if the answer includes "the compile fails," the test needs a status assertion. And remember the ambient inert mode underneath all of this: with the `slang-llvm` library unavailable, `filecheck=` tests report `TestResult::Ignored`, not failed (`slang-test-main.cpp:815-822`, "Ignore if FileCheck is not available"), so a whole suite can look green while asserting nothing. `FileCheck` is not on `PATH` in the container and never needs to be — slang-test loads it in-process from `libslang-llvm.so`, which **is** present in the shared full build's `build/Debug/lib/`, so it is normally live there. A fresh worktree built with only the `slangc`/`slang-test` targets lacks it, and its filecheck lanes all go `ignored` until you copy the lib in (details on [Verification discipline](misc-f0909b5-verification-discipline-and-tooling.md); [SIMPLE(filecheck=) lanes ignored without libslang-llvm.so](../learnings/1791609372518-slang-test-silently-ignores-simple-filecheck-lanes.md)). Either way the verification is the same and takes one edit: break an assertion on purpose and confirm RED before trusting any green run.

**A bug that needs several entry points in one module needs a one-module compile to show.** Consider #13687, where global `in`/`out` varyings are shared by two entry points. `slangc x.slang -target wgsl` writing to stdout and a plain `//TEST:SIMPLE` both generate code one entry point at a time, so neither shows the bug; `-o <file>` or `-whole-program` emits one module, and Metal SIMPLE lanes already do. render-test (COMPARE_COMPUTE) always compiles `computeMain` alone (`-entry` is parsed and ignored, `-no-default-entry-point` asserts), so a GPU runtime test cannot exercise two-entry-point single-module emission at all. The same fact bites a test that mixes SIMPLE legs with a `//TEST(compute, vulkan):COMPARE_COMPUTE(...)` leg: with the entry named `main`, adding `-entry main` to the COMPARE_COMPUTE directive changes nothing and the leg fails with E38000 "no function found matching entry point name 'computeMain'", so name the entry `computeMain` ([COMPARE_COMPUTE ignores -entry](../learnings/1792488875310-slang-test-compare-compute-ignores-entry-codex-cri.md)). The compiler side of the same bug: `translateGlobalVaryingVar` emitted `GlobalVariableShadowingGlobalParameterDecoration(param, global, key)`, which lets `slang-ir-glsl-legalize.cpp` rewrite every use of the global, module-wide, to one entry point's Input var. That is correct only when exactly one entry point reaches the global; otherwise a shared struct `in` gives VUID-08721 and a scalar silently reads the wrong location, and none of the 3,158 tests that run with SPIR-V validation covered it ([multi-entry-point bugs: stdout and SIMPLE compile one entry point at a time](../learnings/1792198835891-slang-multi-entry-point-bugs-slangc-stdout-and-sla.md)).

## `100% of tests passed` on a TRUNCATED run — the `failed(pending retry)` grep, and never store the denominator

The `Ignored`/vacuous-green mode above is not the only way this harness turns a non-result into green. `slang-test` also reports a clean `100% of tests passed (264/264)` on a run **truncated by its consecutive-failure breaker**, because the disqualifying failures never *enter* the total rather than being subtracted from it. Verified in source at master `0864e60e6`: `slang-test-main.cpp:5121` early-returns while `stopSchedulingTests` is set, so remaining tests are never scheduled and never reach the reporter; a `PendingRetry` result prints `failed(pending retry) '<name>'` and returns **before** `m_totalTestCount++` (`test-reporter.cpp:368-372`, incremented `:378`) — *"don't count it in any statistics yet"* — and once the breaker fires, retries are skipped so those failures are counted **nowhere**; `runTotal = rawTotal - ignoredCount` (`:694`), percentage printed `:713`. Only `ignoredCount` is a real subtraction, so `264/264` is *arithmetically true* and merely answers a different question than the one you asked — a self-consistent number is far harder to distrust than a lopsided ratio, which is exactly what makes a percentage-grep feel safe. The stream split makes the naive grep fail *by construction*, not by luck: the percentage prints to **stdout** while the bail notice `fprintf(stderr, …)`s (`slang-test-main.cpp:6131-6137`), so `cmd 2>/dev/null | grep '% of tests passed'` discards the disqualifying fact. Watch **both** numbers in `100% of tests passed (264/264), 94 tests ignored` (the `Ignored` path and the breaker path are independent green-manufacturers), and never use `$?` — `slang-test` exits 0 even with failing tests ([`100% of tests passed` on a truncated run: measure the baseline in-session, not a stored constant; the exact accounting](../learnings/1785837790090-correction-slang-test-denominator-check-measure-th.md)).

The **validated** safe pattern — proven on real output in both directions, not reasoned — is `slang-test ... 2>&1 | grep -E '% of tests passed|Stopped scheduling|Skipping retries|failed\(pending retry\)|failing tests'`. `failed(pending retry)` is the **load-bearing** term and the one most likely missing from anyone else's pattern: it fired **265 times** on a real truncated run versus one line for the bail notice, and it prints to **stdout** (`test-reporter.cpp:371`), so it survives exactly the stderr-dropping pipeline that causes the problem. Validation caught its own trap — the first attempt returned **zero matches** because it was pointed at a build log with no test output; *a positive control that returns zero is telling you the control is wrong, not that the world is clean.* On a healthy run the same pattern surfaces only the `689/689` pass line, so it does not false-alarm — a pattern that fires on the bad case but also the good is useless, and both directions matter ([the `failed(pending retry)` grep for the slang-test fake-pass, proven both directions](../learnings/1785838168354-validated-grep-for-the-slang-test-fake-pass-failed.md)). Deeper discipline: **never store a per-directory total as a constant** — remembering `dynamic-dispatch=689`, `interfaces=71`, etc. is itself the defect this warns against, since a stored constant silently ages (hunting a phantom regression after the suite grows, passing a truncated run after it shrinks). Derive the expected value in the same session (baseline before, again after, compare), or run a two-sided drill (neuter → run → restore → run), which is *structurally immune* because it never needs the right absolute number, only that the two runs differ. **A derived-in-session expected value beats a stored one, because a stored one becomes another thing that can be wrong without announcing it.**

## `-output-using-type` buffer checks: the type header matches a bare digit

A COMPARE_COMPUTE test with `-output-using-type` gets a buffer dump, written to `<test>.actual.txt`, that begins with a type header, `type: uint32_t`, and then prints **one value per line** (`type: float`, `3.000000`, `1.000000`). The line layout fails in the opposite direction from the header: a comma-joined `// CHECK: 3.0, 1.0` never matches, so the test reports FAILED even when every value is right, which during #13611 triage nearly got an open PR misreported as failing. Write one `CHECK`/`CHECK-NEXT` per value and read `.actual.txt` before trusting either verdict ([filecheck-buffer prints one value per line](../learnings/1791922190410-slang-test-filecheck-buffer-prints-one-value-per-l.md)). (The same triage's compiler finding: an existential `DifferentialPair` through dynamic dispatch gets a wrong tangent offset when the conformers' sizes differ, because typeflow's `makeInfoForConcreteType` has no `DifferentialPair` case; equal-size conformers hide it, a regression from #9808.) FileCheck matches substrings, so `// BUF: 2` finds the `2` in `uint32_t` and the test passes whatever the kernel wrote. On slang#13412 a regression test whose real output on master was `1` still passed this way. Anchor past the header and pin the whole value line: `// BUF: type: uint32_t` then `// BUF-NEXT: {{^}}2{{$}}`. The signed form fails the same way and more confusingly: on PR #13503 `// CHECK: 2` matched the `2` inside `type: int32_t`, so the following `CHECK-NEXT` was checked against the wrong line and failed with a misleading message; anchor with `// CHECK: type: int32_t` then `// CHECK-NEXT: <value>` ([caret blocks; int32_t header matches bare CHECK digits](../learnings/1791411328355-diagnostic-test-caret-columns-use-check-blocks-for.md)). The same review turned up the harness's other half of the A/B: `slang-test -bindir <other-build>/bin tests/x.slang` still runs the invoking tree's compiler, so master "passed" a test it actually fails. Copy the test into the other worktree and run that tree's own `./build/Release/bin/slang-test` from its root (mechanism on [Release-Build Divergences](slang-build-release-divergences-and-sanitizers.md)). It recurred twice more. On #13700 R4, `./build/Debug/bin/slang-test -bindir build/Debug-baseline/bin tests/...` kept the head compiler for compute and SIMPLE tests, so a test that cannot pass on master "passed" ([`-bindir` does not switch COMPARE_COMPUTE tests](../learnings/1792215112632-slang-test-bindir-does-not-switch-compare-compute-.md)); on #13687 the reason was confirmed: the invoked slang-test still loads its own libslang through RUNPATH ([`-bindir` loads the caller's libslang](../learnings/1792198835891-slang-multi-entry-point-bugs-slangc-stdout-and-sla.md)). Run the baseline's own binary (`build/Debug-baseline/bin/slang-test tests/...`) and include one test known to fail on master as a control that must fail. (The #13700 IR finding from the same round: a value that dominates a `LoadFromUninitializedMemory` (freeze) can still be poison, e.g. `select(c, 1, poison)`, so refining all uses of a frozen value to `d` needs a `d` with an established non-poison guarantee, such as an IR literal outside any function or an `IRGlobalParam` without `IRDefaultValueDecoration`; dominance alone is not enough.) Two lane facts from the same test: render-test counts a warning in stderr (e.g. E41016, uninitialized variable) as a lane failure, and a CPU lane loads the whole module, so one barrier entry point anywhere in the file fails the CPU lane with E36107 ([`BUF: 2` matches `uint32_t`; `-bindir` is not an A/B](../learnings/1791162065748-slang-test-filecheck-buf-2-vacuously-matches-type-.md)).

## Contradictions / supersessions

- **`slang-test`'s process exit code as a pass/fail signal** — it returned **0 on a FAILED test**, and exits 0 even with failing tests in a truncated run. Parse the `FAILED test:` / `% of tests passed` / `failed(pending retry)` lines, never `$?`.
- **"6 tests committed" as a coverage figure** — narrowed in place under *Counting Assertion-Bearing Tests* in [slang-test False Greens and Verification Discipline](slang-test-false-greens-and-verification-traps.md): count assertion-bearing tests only (3 of the 6 files), and name the single discriminating case rather than letting a file count stand in for power.

## SIMPLE+filecheck never gates on the result code: downstream-compile checks need success-only patterns

A `//TEST:SIMPLE(filecheck=X): -target metallib` test passes whenever its pattern matches anywhere in the FileCheck buffer, whatever the compile returned. In `tools/slang-test/slang-test-main.cpp`, `runSimpleTest` calls `_validateOutput(..., forceFailure=false, ...)`, and the FileCheck branch returns `_fileCheckTest(...)` without reading `result code` (~989-991, 3234-3238). Downstream compiler errors quote the offending source line (Metal goes through the GCC-style diagnostic parser), so a weak pattern such as `// LIB: computeMain` also matches the error output for a *rejected* kernel signature, and the test goes green on a failed compile. Use a pattern that can only appear in successful output: `// METALLIB: define void @computeMain` (`tests/metal/simple-compute.slang:22`, `barrier.slang:8`) or a lowered intrinsic name such as `sample_compare_depth_2d`. The same caution applies to every SIMPLE directive meant to prove a downstream compile succeeded: a green macOS "metallib passed" line is not proof unless the pattern appears only in successful output. Found on slang PR #12294 R2, where the R1 report had relayed the weak evidence as proof ([SIMPLE+filecheck never gates on the result code; metallib `LIB: computeMain` passes on a failed compile](../learnings/1790702677475-slang-test-simple-filecheck-never-gates-on-the-res.md), [SIMPLE+FileCheck ignores the compile result: use success-only patterns (slang-reviewer, #12294)](../learnings/1790704590796-slang-test-simple-filecheck-ignores-the-compile-re.md)). This is the same gap as the `CHECK-NOT`-only case on [slang-b-test-harness](slang-b-test-harness.md): pair every FileCheck with positive evidence of success, either a success-only pattern or a `result code = {{0}}` line as above.

The same gap has two more shapes, both measured. **(a) A failing slangc is not a failing lane.** `getOutput` only prints `result code = N` plus stderr into the buffer being FileChecked, so a weak positive such as `// X: <entryName>` passes even after Apple's compiler rejected the MSL (#13413 R1) — gate the lane with `// X: result code = 0` (or `{{0}}` under `-g`) plus `// X: define {{.*}} @<entry>` ([SIMPLE filecheck lanes ignore slangc's exit code; macOS CI ignores ray-query Metal runtime lanes](../learnings/1790977463190-slang-test-simple-filecheck-lanes-ignore-slangc-s-.md)). **(b) A NOT-only lane gates on nothing.** `// PREFIX-NOT: error :` with no positive check passed on a throwaway test where `-entry doesNotExist` made slangc fail, while a NOT that does match failed (so FileCheck was running): Slang's own diagnostics print `error[E38000]: …`, only downstream-compiler errors use the `<file>(<line>): error <code>:` shape, and the `failed to load downstream compiler` path is *ignored*, not failed. Pair the NOT with `// PREFIX: result code = 0` (as `tests/metal/mesh-index-expression.slang:13` does) or a positive anchor such as `METALLIB: @entryName`; seen three times (#12294 R2, #13413 R1, #13421 G2), so check every new `-target metallib` lane for it ([a NOT-only `X-NOT: error :` lane passes when slangc itself fails](../learnings/1791009233810-a-not-only-x-not-error-filecheck-lane-passes-when-.md)). **(c) A CHECK on a declaration name proves nothing on SPIR-V/GLSL.** On #13507 `bit-cast-resource-array.slang` (`//TEST:SIMPLE(filecheck=CHECK): -target spirv`, one `// CHECK: bitsBuffer`) passed 22/22 locally but fails under `SLANG_RUN_SPIRV_VALIDATION=1`, which CI exports (`ci-slang-test.yml:152`): the FileCheck buffer includes stderr, and the module dumped on a validation failure still contains `OpName %bitsBuffer`. The cast (`Texture2D[2]`→`uint64_t[2]`) was invalid on every target — an `OpBitcast` of an image, GLSL `uint64_t(texture2D)`, HLSL E99999. So check the lowered operation rather than a name, put `CHECK: result code = 0` first (it precedes the emitted source in the buffer, so order the checks that way) or add `CHECK-NOT: error` — without the colon, since a validation failure prints `internal error 99999:` and `CHECK-NOT: error:` never fires on it ([false-greens page](slang-test-false-greens-and-verification-traps.md)) — re-run spirv/glsl SIMPLE lanes with `SLANG_RUN_SPIRV_VALIDATION=1 slang-test <dir>`, and try `-emit-spirv-via-glsl` for glslang's opinion on the GLSL row ([CHECK on a decl name passes on failed compiles](../learnings/1791426372496-slang-test-simple-check-decl-name-passes-on-failed.md); [filecheck=A,B is one prefix; `result code = 0` first](../learnings/1791427324960-slang-test-filecheck-a-b-is-one-prefix-the-second-.md)). A related CI-coverage trap from the first atom: the macOS runners do not report the `ray-query` render feature, so every `//TEST(compute, metal):COMPARE_COMPUTE_EX … -render-feature ray-query` lane is IGNORED there (e.g. `tests/metal/ray-query-intrinsics.slang.2 (mtl)` on master, run 37043131359) — for Metal ray-query the metallib compile is the only check against Apple's toolchain, so don't describe the runtime lane as a CI hardware check. Confirm a lane's CI status with `gh run view <run> -R shader-slang/slang --job <id> --log | grep <test>` (`gh api …/jobs/<id>/logs` returned 410 through the proxy).

**(d) A `-NOT` placed after a stdout match never sees stderr.** The buffer is built as `result code`, then `standard error = {…}`, then `standard output = {…}` (`slang-test-main.cpp:2222-2230`), and a `-NOT` scans only the region after the preceding positive match. Consider this pair from a CUDA texture test:

```
//FLOAT: tex2DLod<float4
//FLOAT-NOT: static assertion failed
```

The positive match lands in stdout, so the `-NOT` scans only the stdout after it and never reaches the stderr above, where the diagnostic would print. A real `static_assert` failure would also suppress the positive match, so the pair can never fail on the NOT. The vacuous pattern sits in `tests/diagnostics/cuda-half-texture-sample-level.slang` and was copied into #13559's SampleGrad test. To assert "no diagnostics", use an annotation-free `//DIAGNOSTIC_TEST:SIMPLE(diag=X):` on the same entry point; exhaustive mode fails on any unannotated diagnostic. The other option is to move the `-NOT` above the first stdout match so its region covers stderr. A leading `-NOT` only scans up to the first positive match, so a whole-file negative needs its own `filecheck=` prefix ([`[noRefInline]` test: whole-file negatives need their own prefix](../learnings/1791604550352-slang-noinline-does-not-keep-a-ref-helper-use-nore.md)). The same sibling test cites "#12185", an unrelated spvBindlessTextureNV issue, so check a citation with `gh api` before copying it into a new test. On #13559 the slang-pr-review-runner Reviewer A CLI also died three runs in a row (it ends its turn with background subagents still running, and they get stopped); running the read-only cross-backend, documentation-accuracy, and test-coverage reviewers directly on a saved diff was a workable stand-in ([a `-NOT` after a stdout match never checks stderr](../learnings/1791607903034-slang-test-simple-a-not-on-a-diagnostic-placed-aft.md); [`-NOT` after stdout never sees diagnostics; verify copied citations](../learnings/1791608967955-slang-test-not-checks-after-a-stdout-match-never-s.md)).

## DIAGNOSTIC_TEST annotations the parser never sees: `-NOT` lines and `// CHECK:` with a space

`parseAnnotations` in `tools/slang-test/diagnostic-annotation-util.cpp` looks only for `//PREFIX:` and `/*PREFIX:` markers (the colon is required) and has no negative-check handling. A line like `//SCOPE-NOT: E36107` is therefore ignored, and under `non-exhaustive` the test passes even when the diagnostic fires. In `tests/diagnostics/capability-generic-struct-entrypoint-param.slang` the SCOPE case passes on master although slangc emits E36107 for `mainScope` (via `Foo.init`). The #13579 triage found 17 test files with inert `-NOT` lines under DIAGNOSTIC_TEST prefixes. To assert that a diagnostic is absent, use an exhaustive DIAGNOSTIC_TEST with no annotations (any diagnostic then fails it), or a filecheck-based test [DIAGNOSTIC_TEST has no -NOT directive](../learnings/1791842377952-diagnostic-test-has-no-not-directive-prefix-not-li.md). The capability-propagation finding from the same triage is on [[wiki/concepts/slangc-target-coverage-and-capabilities.md]].

The same marker rule makes a spaced annotation inert. The parser builds the marker as `"//" << prefix << ":"`, so only `//CHECK:` or `/*CHECK:` with no space between the comment opener and the prefix matches. A line like `// CHECK: error[E39033]` matches nothing and asserts nothing: on shader-slang/slang#13724 R1 the test still passed after the code was changed to `E12345` or to bogus text. To assert an error code, put it in a caret annotation such as `^^^^ error E39033` (see `docs/diagnostics.md`). In review, when a diagnostic test claims to pin a code, mutate the code and re-run ([`// CHECK:` with a space is silently ignored](../learnings/1792198981359-slang-test-diagnostic-test-check-with-a-space-is-s.md)). (This is a different trap from a space AFTER the colon, `//CHECK: ^^^`, which shifts the caret columns; that one is on [slang-test False Greens](slang-test-false-greens-and-verification-traps.md).)
