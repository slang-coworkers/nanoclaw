## TL;DR
- **Every reviewer fails toward CLEAN.** Devin exit 0 is not a signal; Reviewer A can emit a 0-byte or budget-capped output; Reviewer C can skip environmentally. **Verify each reviewer produced findings before treating "no findings" as a result** — an absent reviewer and a clean reviewer are byte-identical downstream.
- **Watch the ARTIFACT, not the subagent.** A Devin subagent returns before `devin-fetch.sh` finishes; a detached reviewer's completion is proven by its exit marker, never by streamed JSON. Anchor monitors to exit markers.
- **Read the full page dump, not the summary file.** `devin-flags.md` can have an EMPTY `## Flags` section while `devin-page.txt` from the same run shows real findings — synthesizing from the summary records a false "0 findings" and carries a false-clean prior into the challenger.
- **Reviewer A needs an isolated checkout.** Fleet contention on a shared repo root corrupts runs; `$30` is too low a budget cap and produces silent truncation. Use fresh per-run out-dirs to avoid `/tmp` collisions.
- **Two bots agreeing measures shared priors, not correctness.** Independent bots flagging the same item is weak corroboration; read the human review thread before scoring any structure/maintainability gap.
- **A bot finding a named maintainer already overruled ON THIS PR is not an open gap** — but **lead with the technical grounds**, never the maintainer's preference. Maintainer preference is supporting context; a repo guideline is not cleared by taste alone.
- **A refuted 🔴 does not become WOULD_APPROVE**, and a standing human `CHANGES_REQUESTED` caps the verdict at ABSTAIN. Never round up.
- **A mid-iteration `diff_hash` mismatch is expected under debounce**, not a bug. Pin the head, byte-prove reviews against it, and re-verify a stale secondary reviewer's flags at the current head.
- **Re-review scope: redesign gaps and self-recommended nits do not reset the pipeline.** Additive nit rounds are fine; a full re-run is not.
- **The review signal is endpoint-split across three surfaces** (`pulls/N/reviews`, `pulls/N/comments`, `issues/N/comments`) and the harvest reads one. That split is a property of GitHub's data model, so **every consumer inherits the blind spot independently — fixing one instance is not fixing the class.**
- **A GitHub post gates on the literal marker, not on prose.** Post only in COMMENT state; never APPROVE/REQUEST_CHANGES from a runner.
- **Empirical probes can test the wrong sub-case.** A probe that varies the intended factor while holding the confound constant reads as decisive and proves nothing — name the factor and the confound before citing a control.
- **In an artifact where claims cite `file:line`, the UNCITED SENTENCE IS THE DEFECT** — in a document whose norm is citation, the citation outlier is where an inference got restated as an observation. Run that self-check mechanically over your own draft.
- **Recording is not routing.** Documenting a blocking infra defect any number of times never reaches a file only an operator can edit. The record serves the next agent; the escalation serves the fix — do both.
- **A stale webhook dispatch on an already-decided PR is a no-op plus a report, never a re-decision.** `record_decision` is idempotent per `(repo, pr, sha)`, so re-deciding CLOBBERS a human-joined calibration row with a verdict contaminated by post-hoc information.

## Reviewer B (Devin) and C (Clarity) Environmental Skips Don't Block the Verdict

Two reviewers can be *environmentally* blocked in the reviewer container in ways a retry cannot fix — distinct from the transient-socket / premature-scrape failures above. **Reviewer B (Devin) Chrome cannot launch**: `devin-fetch.sh` fails at the Chrome launch step (`Chrome exited early … without writing DevToolsActivePort`, root cause `Failed to connect to the bus: … /run/dbus/system_bus_socket: No such file or directory`), exit 1 — not the exit-2 auth-wall or exit-3 timeout. This is a missing-dbus / headless-Chrome-deps image gap, so retrying is pointless; mark B `_skipped: agent-browser Chrome cannot launch (no dbus, infra)_`, note the missing portability lens in the `[Review Verdict]`, and (if Devin coverage is later required) raise an `install_packages` request for headless-Chrome + dbus. Note the background-task wrapper can report the *launcher* exit as 0 while the inner script wrote `REVIEWER_B_EXIT=1` and produced no `devin-flags.md` — check for the actual output file, not the completion notification's exit code ([Devin (Reviewer B) agent-browser Chrome fails in reviewer container — no DBus socket](../learnings/1783618070602-devin-reviewer-b-agent-browser-chrome-fails-in-rev.md), [Reviewer B (Devin) fails at Chrome launch in reviewer container — no dbus](../learnings/1783630449263-reviewer-b-devin-fails-at-chrome-launch-in-reviewe.md)).

**Reviewer C (Clarity) sandbox blocks file writes**: `run-clarity` can exit rc=1 with `CLARITY-INCOMPLETE: clarity-review.md is <N>B (floor 500B)`, the ~199B output being just the orchestrator's "Now I'll launch the four review agents…" message — the inner `claude --print` session's Bash sandbox denied *all* file writes (`>`, `tee`, `dd`, `python open('w')`, even `echo` to `/tmp`), a wall of `permission_denials` in `stream.jsonl`. The clarity pipeline stages the diff to a file and writes candidate markdown as its core mechanism, so with writes blocked its subagents can't function. Reviewer A survives the same container because it stages into an isolated dir (`tmp/iso-<pr>-review/pr-diff.patch`) whose path the C sandbox doesn't deny. This is deterministic, not transient: mark C `_skipped: clarity pipeline blocked by inner-CLI sandbox file-write denial_` and proceed on A ([Clarity reviewer (Reviewer C) fails when inner CLI sandbox blocks file writes](../learnings/1783627611526-clarity-reviewer-reviewer-c-fails-when-inner-cli-s.md)).

The honesty rule for the panel: **`reviewers_complete = (A complete) && (B complete) && (C complete) && drift==0`** — a dispatched-but-skipped reviewer (including a Devin environmental skip) makes the honest value `false`, telling the approver to treat the run as harness-incomplete (→ lean ABSTAIN). Do not set `true` while B is skipped; add a `reviewer_status` sub-object (`{A_correctness, B_devin, C_clarity: complete|skipped_*|failed}`) so the consumer sees exactly which reviewer is missing rather than inferring from a bare boolean ([combined-review RESULT_JSON: reviewers_complete=false when ANY dispatched reviewer is skipped](../learnings/1783631862638-combined-review-result-json-reviewers-complete-fal.md)).


## Mid-Iteration diff_hash Mismatch Is Expected Under Debounce, Not a Bug

When a PR branch iterates *during* a review run and Reviewer A finishes against an earlier commit than Reviewer C (debounce path: A left running on an inert push while only C re-ran against the newer HEAD), the combined report ends with A and C on different SHAs. RESULT_JSON's `diff_hash` is built from **Reviewer A's** diff-integrity marker, so it pins A's commit — not the current HEAD the header otherwise pins. Downstream, `slang-pr-approver`'s Step-2 `commit_match` clause flags this (observed #12029: `diff_hash 7b7416a65fb9` = A's commit `43c9a077`; current HEAD `ac959d7` had diff `b62b992e4341`). This is expected under the debounce protocol, not a pipeline bug — **call it out in the combined-report header** (which SHA each reviewer ran, and that A is N inert pushes behind C). Only re-run A against the final SHA (~$20 / ~20–30 min) if the delta is *material*; for a behaviorally-inert delta, document the gap. Related: fork-head PRs (a maintainer's own `saipraveenb25/slang`) hit the approver's `head_provenance` clause under `allow_fork_head=false` → ABSTAIN_POLICY before any code-facing step — expected for maintainer-owned PRs; a human approves those ([Mid-iteration PR: combined-review diff_hash mismatches pinned HEAD → approver Step-2 flag](../learnings/1783631632879-mid-iteration-pr-combined-review-diff-hash-reviewe.md)).


## slangpy PR-Review GitHub Post Gates on the Literal Marker, Not Prose

In `/slangpy-pr-review`, the COMMENT-state GitHub post (step 5) is gated on the **literal `<github-post-authorized />` marker** appearing in the dispatch text — not on a prose "go ahead, post it." If the parent authorizes posting in words but omits the marker, the reviewer correctly does NOT post (step 5 is a no-op; the verdict already went out via `send_file` in step 4). This is working as designed: the marker is machine-checkable proof that a human tagged `@nv-slang-bot` (an explicit GitHub-reply invitation), and prose from a coworker/orchestrator is not that proof — it keeps the bot's GitHub footprint tied to explicit human invitation. Unblock by re-sending the instruction *with* the marker. Observed on slangpy-samples#52 (Jul 2026): prose-only authorization gated the post OFF; re-send with the marker → posted as `event=COMMENT` (verified `COMMENTED`). Bonus on that PR: for a Git-LFS-tracked asset, the diff shows only a `+2/−2` pointer change (oid + size) — to verify actual image content, fetch the object via the LFS batch API (`POST https://github.com/<owner>/<repo>.git/info/lfs/objects/batch`, `operation:download`) with `gh auth token` and check sha256 == pointer oid; `gh api .../contents/<path>` returns the 131-byte pointer, not the image ([slangpy-pr-review GitHub post gates on literal marker, not prose](../learnings/1783639327701-slangpy-pr-review-github-post-gates-on-literal-mar.md)).



## Severity Calibration: Benign-Output, Doc-vs-Behavior, and Maintainer Labels (2026-08-01 fold)

Three related calibration lessons on how hard to rate a finding. First, a **"benign / produces valid output" call must hold on every reachable emit target** — type/IR-shape validity is target-specific. On slang #11917 batch-3 / PR #12281 an early-out change *kept* a public empty struct that master stripped; the fixer, peer reviewer, triage, and codex all concurred "benign" on the strength of "a 0-member `OpTypeStruct` is valid SPIR-V" — true for direct SPIR-V, but empty structs are **illegal GLSL syntax**, so `-emit-spirv-via-glsl` made glslang fail where master compiled. Before rating an emit-affecting change benign, enumerate the reachable targets (HLSL, GLSL/`-emit-spirv-via-glsl`, direct SPIR-V, Metal, WGSL, CUDA/PTX, CPU) and prefer an adversarial cross-target probe over reasoning from one backend; "valid on the target I checked" ≠ "valid everywhere it's emitted," and empty aggregates / bool-typed constants / pointer-as-param are common target-divergent shapes ([benign/valid-output severity calls must check every reachable emit target](../learnings/1785449256204-benign-valid-output-severity-calls-must-check-ever.md)).

Second, a **doc-vs-behavior conflict on a maintainer-owned design point is a QUESTION/GAP for maintainer intent, not an autonomous BLOCK.** On slang #8125 / PR #12304, review empirically (and correctly) traced that removing `IRPublicDecoration` at lowering makes plain-`public` CPU/CUDA functions emit `static`, contradicting `docs/cpu-target.md:210` — and rated it BLOCKING. jkwak then approved and flipped it ready himself: the `public` keyword "is supposed to do nothing" (a csyonghe Code-Review-meeting decision), so the behavior change was intended and the *doc* was the stale artifact. The technical rigor (empirical before/after against the base binary, predicate/consumer traces, exact doc citation) was right and load-bearing — only the severity was one notch too hard. Ask "could a maintainer have intended this contract change?" — a keyword's meaning, emit convention, or visibility policy → surface as a high-signal QUESTION with the doc conflict as evidence, verdict deferred to maintainer, especially when the maintainer dictated the approach; reserve REQUEST_CHANGES strength for changes wrong *regardless* of intent (memory safety, silent miscompile, an ABI guarantee the PR claims to preserve). The orchestrator/fixer should re-frame such a BLOCK downstream as a neutral intent question (offer the branches), not act on it ([doc-vs-behavior conflict is a QUESTION/GAP for maintainer intent, not an autonomous BLOCK](../learnings/1785539717795-severity-calibration-doc-vs-behavior-conflict-is-a.md), [doc-vs-behavior conflict on a maintainer-owned design point is a QUESTION, not a BLOCK](../learnings/1785539785590-review-severity-doc-vs-behavior-conflict-on-a-main.md)).

Third, a **maintainer-applied label (or Type/milestone) can encode the direction they are driving toward, not the current-diff state** — so verify scope currency before flagging a "mismatch." On slang #12120 / PR #12195 the `pr: breaking change` label looked wrong against a still-default-OFF (technically non-breaking) HEAD, but jkwak had applied it himself after superseding the original scope toward default-ON; the label deliberately led the code. Human triage is authoritative — never overwrite it; before surfacing a label discrepancy, pull the applier + timestamp and check whether a later maintainer comment superseded the framing your directive holds, and if you still raise it, frame it as "HEAD is X, label says Y — intentional forward-looking, or worth a look?" not "wrong label" ([maintainer labels can encode intended future direction — verify scope currency before flagging a mismatch](../learnings/1785540385736-maintainer-labels-can-encode-intended-future-direc.md)).

## A Bot's Verdict Covers Only the Files It Read — Extension-Based Default Excludes

The fail-toward-CLEAN family has a **coverage** dimension distinct from the harness failures above: a review bot can read the PR successfully, post a well-formed verdict, and never have opened the file the PR is actually about. **CodeRabbit excludes `**/*.map` by default, and that default lives in the tool, not the repo** — `.coderabbit.yaml:22-25` on shader-slang/slang filters only `!build/**` and `!external/**`; `*.map` appears nowhere in it. Measured on slang PR #12379 (2026-08-06), the processing notice read *"Files ignored due to path filters (1) · `source/slang-glslang/slang-glslang.map` is excluded by `!**/*.map`"* followed by *"Files selected for processing (2)"* — against a **3-file** PR whose omitted file was the GNU ld **version script defining the shared module's entire public ABI**, i.e. the substance of the fix. The default is presumably aimed at JavaScript/CSS **source maps**, where skipping generated output is correct; it collides with hand-maintained linker version scripts, symbol lists, and export lists that conventionally share the extension.

**Why this is worse than an ordinary review gap.** A wrong or missing version-script entry **does not fail the build** — the symbol is simply absent from the dynamic symbol table and the failure surfaces at `dlopen`/`dlsym` time in the consumer, which on that PR dereferences the resulting null unguarded (`source/compiler-core/slang-glslang-compiler.cpp:426`), so a dropped export **crashes rather than diagnoses**. Meanwhile the bot still posts a verdict computed from the files it *did* read, and a reader who sees "CodeRabbit reviewed this PR" reasonably infers full coverage. **The exclusion is disclosed — inside a collapsed `<details>` block, worded as routine housekeeping**, which is arguably worse than silence: it manufactures a paper trail that looks like transparency while nobody reads it.

Detector and rules. **Compare "files selected for processing" against the PR's changed-file count** — the mismatch is stated outright in the notice; it only has to be read. `git ls-files | grep '\.map$'` on that master returned **0**, so the PR introduced the repo's first file of an ignored class and nobody in the project had prior reason to know the gap existed — meaning the absence of past incidents is no evidence of coverage. If a repo has or gains a hand-written `.map`-class file, **add an explicit un-exclude to `.coderabbit.yaml`** (path filters are additive over the defaults, so the built-in `!**/*.map` needs a counter-pattern). When such a file is in a PR, do not treat any bot review as coverage of it: derive the export set independently **three ways — the map, the producer that defines the exports, and every consumer `dlsym`/`findFuncByName` against the module — and require all three sets to match exactly.** This generalizes past CodeRabbit: **any review tool with extension-based default excludes carries this blind-spot class**, so when a PR's substance sits in an unusual file type, diff the tool's file list against the PR's before crediting its verdict ([CodeRabbit ignores `*.map` by default, so linker version scripts go unreviewed](../learnings/1785991860433-coderabbit-ignores-map-by-default-linker-version-s.md)).

## A Brief Scoped to the Bug Still Owes a Read of the Fix's Open Threads

When a brief scopes you to "confirm these facts about the bug," the unasked question is whether the **fix** contains its own instance of the same bug class. **Read the fix PR's *unresolved* review threads before deciding the pre-merge priority.** On slang #12376 (fossil OOB reads) and fix PR #12354, both of the issue's load-bearing facts were verified carefully and the public verdict led with a bookkeeping question (a missing regression test) — while the PR's validating walk, the change whose entire purpose is *"prove every location a consumer can reach lies inside the blob,"* had a constructible bypass flagged in a thread still `isResolved=false` / `isOutdated=false` **23 hours and 7 commits later**. Mechanism: `kNullOffset = -1`; `_readRelativePtr()` decides null from the **raw** stored offset (`raw == 0`) but returns the **computed** target `offset + raw`, and the call sites compare that computed value against the sentinel and skip validation. Raw `-1 - D` is non-zero and fits `int32_t` for every realistic offset `D`, so the computed result is exactly `-1`: the walk treats a live pointer as null and never validates its target, while the consumer's `get()` — which nulls only on raw `_offset == 0` — resolves `base - 1` and dereferences it.

Two reusable pieces. **In-band sentinels inside a validator are a bug class of their own:** if the validator's null test and the consumer's null test are computed from *different* values (one from the raw field, one from a derived address), a crafted input can satisfy one and not the other. The invariant to check is literal — *does the validator's null test match the consumer's null test exactly?* And **model the arithmetic instead of trusting the algebra:** a 20-line script over realistic offsets, carrying two controls (genuine nulls must still map to the sentinel; ordinary forward pointers must *not* collide), converts "this looks constructible" into "constructible at D = 0, 4, 12, 28, 32, 160, 3840, …" — cheap, and it is what licenses publishing a confirmed defect rather than a suspicion. Credit belongs where the finding originated: that thread was found by a review bot, not by the verifier, and **the public text must say so.** Re-deriving someone else's finding and presenting it as yours is the same defect as re-deriving their control and framing it as a refutation of them, and it is the citation-discipline failure the uncited-sentence self-check above is meant to catch ([read the fix PR's open review threads, not just the issue's facts](../learnings/1785985363443-scoped-to-verify-the-bug-read-the-fix-s-open-revie.md)).
