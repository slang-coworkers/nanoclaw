# Supervisor CI-Cell Staleness and scan.py Over-Flag Root Causes

> **Split 2026-08-17.** Sibling: [Watchdog No-Op Controls, Blocker-Identity Monitoring, and Ledger Guards](agent-supervisor-watchdog-and-ledger-guards.md), which owns the watchdog empty-result control, monitor-on-blocker-identity, and append-only-ledger guard construction. This page owns the draft→non-draft CI-cell staleness trap and the chronic 70+ `scan.py` over-flag root causes (both of which revert on skill re-sync).

## TL;DR
- **A non-draft PR's authoritative CI run is the `pull_request` run on HEAD**, not a stale `workflow_dispatch` run from when it was a draft. Re-confirm latest-run + draft-status before acting on a stored CI cell; a rebase nudge on a `BLOCKED`/`REVIEW_REQUIRED` PR whose real CI is green is noise.
- **scan.py over-flags revert on every skill re-sync** — the durable home for the `parse_ts` tz-crash, the too-deep `HUMAN_OWNED` gate, and the bare-numeric-signature (502/503/504) false-positive is an upstream PR to the supervise-issues skill, not a per-tick hand-patch.
- **The two chronic root causes:** (1) a `parse_ts` timezone crash that zeroes the tick output entirely (naive SQLite timestamps compared against aware ones), and (2) a `HUMAN_OWNED` disposition gate buried too deep in `classify()`, so parked chains leaked into `needs_nudge`. Lifting the gate to the top plus tz-normalizing dropped raw `must_nudge` 70 → 1.
- **A substring signature for an error class must be anchored to error syntax, never bare digits** — GitHub comment ids are 10 digits, so ~a third contain `502`/`503`/`504` by chance; require co-occurrence with an errorish marker (`and`, not `or`), or match `\b(HTTP|status)\s*50[234]\b`.
- **When a classifier's cheapest signature is also the most common accidental substring, it will mostly report accidents** — a false `transient` on a terminal chain manufactures a phantom nudge row via the bounce limb.

## Supervisor CI Cell Goes Stale When a PR Flips Draft→Non-Draft

The supervisor's §2b CI read stores a per-chain CI cell, but the *authoritative* CI signal depends on the PR's draft status — and a stored cell from a prior tick can be stale if that status changed since. Fix PRs normally sit in **draft** and drive CI by `workflow_dispatch`, so §2b takes "latest non-skipped `workflow_dispatch` run for `fix/issue-<num>`" as the signal. But once a PR flips to **non-draft**, the `wait-for-human-priority` gate no longer yields — yet a stale `workflow_dispatch` run dispatched *while it was still a draft* stays the "latest workflow_dispatch" and can carry a `failure` conclusion from flaky jobs. On a non-draft PR the authoritative run is the **`pull_request`** run on the same HEAD. Incident (Tick 102, slang #12120 / PR #12195): a stored `❌` (workflow_dispatch, draft-era) fired a rebase nudge — but the `pull_request` run on the same HEAD was green, and the PR was `BLOCKED`/`REVIEW_REQUIRED` on human review, NOT CI. Apply: (1) when non-draft, prefer the latest non-skipped `pull_request` run's conclusion; (2) don't act on a stored CI cell without re-confirming the run is still latest AND the draft-status hasn't changed; (3) a rebase nudge on a `BLOCKED`/`REVIEW_REQUIRED` PR whose real CI is green is noise ([Supervisor CI cell goes stale when a PR flips draft→non-draft](../learnings/1784982853601-supervisor-ci-cell-goes-stale-when-pr-flips-draft-.md)).

## The Chronic 70+ Over-Flag Had Two Root Causes in scan.py, Both Revert on Skill Re-Sync

The supervisor's `supervise-issues/scripts/scan.py` over-flagged ~70 chains as `needs_nudge` for 5+ consecutive ticks, each tick re-diagnosing the same two bugs by hand because the fix reverts on every skill re-sync. **(1) `parse_ts` timezone crash (fatal EVERY tick):** `pull-universe.sh` emits `our_last_outbound` as naive SQLite `YYYY-MM-DD HH:MM:SS` (no `Z`) for ~59 chains; `datetime.fromisoformat` returns a naive datetime → `TypeError: can't compare offset-naive and offset-aware` in the `max()` inside `compute_last_activity_by_us`, producing ZERO output and a dead tick. Fix: in `parse_ts`, `if dt.tzinfo is None: dt = dt.replace(tzinfo=timezone.utc)`. **(2) `HUMAN_OWNED` disposition gate too deep:** the gate lived only inside `we_owe_next_step` (the bot-last `ball=='human'` path), so `ball=='ours'`/`ball=='none'` *parked* chains leaked into `needs_nudge`. Fix: lift the gate to the very top of `classify()`. Also widen `HUMAN_OWNED_DISPOSITION` with the descriptive tokens the state file actually uses (`maintainer-owned`, `design-gated`, `parked`, `superseded`, `held for`) but NOT bare `pr_open`/`awaiting_human` prefixes. Result: raw `must_nudge` 70 → 1 honestly, + 3 regression tests. **Both scan.py edits AND the still-owed `pull-universe.sh` fixes revert on skill re-sync — the durable home is an upstream PR to the supervise-issues skill** ([supervise scan.py: durable fix for chronic 70+ over-flag (parse_ts tz + HUMAN_OWNED gate lift)](../learnings/1785112718566-supervise-scan-py-durable-fix-for-chronic-70-over-.md)).

**A fourth input bug in the same feeder: bare numeric transient signatures (502/503/504) false-positive on GitHub comment IDs.** `scripts/pull-universe.sh::classify_error_text` lists bare `"502"`, `"503"`, `"504"` in `_TRANSIENT_SIGNATURES`, and the `is_errorish` guard is **or**-ed with the signature scan, so any outbound text containing those three digits *anywhere* (including inside a URL or comment id) is classified `transient`. Observed at tick 87: `gh-issue-shader-slang/slang-12219` was flagged `transient` on the match `504` inside comment id `5150492632` — while the outbound was a normal `[Loop closed]` report on a **terminal** chain. `last_outbound_error_class ∈ (transient|unknown)` is the **bounce limb** of `scan.py`, so a false positive manufactures a phantom nudge row on a finished chain; since GitHub comment ids are 10 digits, ~a third of all links contain one of these substrings by chance. Fix: require numeric signatures to co-occur with an errorish marker (`and`, not `or`), or match `\b(HTTP|status)\s*50[234]\b`. **A substring signature for an error class must be anchored to error syntax, never bare digits** — when a classifier's cheapest signature is also the most common accidental substring, it will mostly report accidents ([supervise-issues: bare numeric transient signatures (502/503/504) false-positive on GitHub comment IDs](../learnings/1785802540595-supervise-issues-bare-numeric-transient-signatures.md)).
