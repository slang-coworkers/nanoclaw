# Supervisor CI-Cell Staleness and scan.py Over-Flag Root Causes

> **Split 2026-08-17.** Sibling: [Watchdog No-Op Controls, Blocker-Identity Monitoring, and Ledger Guards](agent-supervisor-watchdog-and-ledger-guards.md), which owns the watchdog empty-result control, monitor-on-blocker-identity, and append-only-ledger guard construction. This page owns the draft→non-draft CI-cell staleness trap and the chronic 70+ `scan.py` over-flag root causes (both of which revert on skill re-sync).

## TL;DR
- **A non-draft PR's authoritative CI run is the `pull_request` run on HEAD**, not a stale `workflow_dispatch` run from when it was a draft. Re-confirm latest-run + draft-status before acting on a stored CI cell; a rebase nudge on a `BLOCKED`/`REVIEW_REQUIRED` PR whose real CI is green is noise.
- **scan.py over-flags revert on every skill re-sync** — the durable home for the `parse_ts` tz-crash, the too-deep `HUMAN_OWNED` gate, and the bare-numeric-signature (502/503/504) false-positive is an upstream PR to the supervise-issues skill, not a per-tick hand-patch.
- **The two chronic root causes:** (1) a `parse_ts` timezone crash that zeroes the tick output entirely (naive SQLite timestamps compared against aware ones), and (2) a `HUMAN_OWNED` disposition gate buried too deep in `classify()`, so parked chains leaked into `needs_nudge`. Lifting the gate to the top plus tz-normalizing dropped raw `must_nudge` 70 → 1.
- **A substring signature for an error class must be anchored to error syntax, never bare digits** — GitHub comment ids are 10 digits, so ~a third contain `502`/`503`/`504` by chance; require co-occurrence with an errorish marker (`and`, not `or`), or match `\b(HTTP|status)\s*50[234]\b`.
- **When a classifier's cheapest signature is also the most common accidental substring, it will mostly report accidents** — a false `transient` on a terminal chain manufactures a phantom nudge row via the bounce limb.

## Supervisor CI Cell Goes Stale When a PR Flips Draft→Non-Draft

The supervisor's §2b CI read stores a per-chain CI cell, but the *authoritative* CI signal depends on the PR's draft status — and a stored cell from a prior tick can be stale if that status changed since. Fix PRs normally sit in **draft** and drive CI by `workflow_dispatch`, so §2b takes "latest non-skipped `workflow_dispatch` run for `fix/issue-<num>`" as the signal. But once a PR flips to **non-draft**, the `wait-for-human-priority` gate no longer yields — yet a stale `workflow_dispatch` run dispatched *while it was still a draft* stays the "latest workflow_dispatch" and can carry a `failure` conclusion from flaky jobs. On a non-draft PR the authoritative run is the **`pull_request`** run on the same HEAD. Incident (Tick 102, slang #12120 / PR #12195): a stored `❌` (workflow_dispatch, draft-era) fired a rebase nudge — but the `pull_request` run on the same HEAD was green, and the PR was `BLOCKED`/`REVIEW_REQUIRED` on human review, NOT CI. Apply: (1) when non-draft, prefer the latest non-skipped `pull_request` run's conclusion; (2) don't act on a stored CI cell without re-confirming the run is still latest AND the draft-status hasn't changed; (3) a rebase nudge on a `BLOCKED`/`REVIEW_REQUIRED` PR whose real CI is green is noise ([Supervisor CI cell goes stale when a PR flips draft→non-draft](../learnings/1784982853601-supervisor-ci-cell-goes-stale-when-pr-flips-draft-.md)).

## The Chronic 70+ Over-Flag Had Two Root Causes in scan.py, Both Revert on Skill Re-Sync

The supervisor's `supervise-issues/scripts/scan.py` over-flagged ~70 chains as `needs_nudge` for 5+ consecutive ticks, each tick re-diagnosing the same two bugs by hand because the fix reverts on every skill re-sync. **(1) `parse_ts` timezone crash (fatal EVERY tick):** `pull-universe.sh` emits `our_last_outbound` as naive SQLite `YYYY-MM-DD HH:MM:SS` (no `Z`) for ~59 chains; `datetime.fromisoformat` returns a naive datetime → `TypeError: can't compare offset-naive and offset-aware` in the `max()` inside `compute_last_activity_by_us`, producing ZERO output and a dead tick. Fix: in `parse_ts`, `if dt.tzinfo is None: dt = dt.replace(tzinfo=timezone.utc)`. **(2) `HUMAN_OWNED` disposition gate too deep:** the gate lived only inside `we_owe_next_step` (the bot-last `ball=='human'` path), so `ball=='ours'`/`ball=='none'` *parked* chains leaked into `needs_nudge`. Fix: lift the gate to the very top of `classify()`. Also widen `HUMAN_OWNED_DISPOSITION` with the descriptive tokens the state file actually uses (`maintainer-owned`, `design-gated`, `parked`, `superseded`, `held for`) but NOT bare `pr_open`/`awaiting_human` prefixes. Result: raw `must_nudge` 70 → 1 honestly, + 3 regression tests. **Both scan.py edits AND the still-owed `pull-universe.sh` fixes revert on skill re-sync — the durable home is an upstream PR to the supervise-issues skill** ([supervise scan.py: durable fix for chronic 70+ over-flag (parse_ts tz + HUMAN_OWNED gate lift)](../learnings/1785112718566-supervise-scan-py-durable-fix-for-chronic-70-over-.md)).

**A fourth input bug in the same feeder: bare numeric transient signatures (502/503/504) false-positive on GitHub comment IDs.** `scripts/pull-universe.sh::classify_error_text` lists bare `"502"`, `"503"`, `"504"` in `_TRANSIENT_SIGNATURES`, and the `is_errorish` guard is **or**-ed with the signature scan, so any outbound text containing those three digits *anywhere* (including inside a URL or comment id) is classified `transient`. Observed at tick 87: `gh-issue-shader-slang/slang-12219` was flagged `transient` on the match `504` inside comment id `5150492632` — while the outbound was a normal `[Loop closed]` report on a **terminal** chain. `last_outbound_error_class ∈ (transient|unknown)` is the **bounce limb** of `scan.py`, so a false positive manufactures a phantom nudge row on a finished chain; since GitHub comment ids are 10 digits, ~a third of all links contain one of these substrings by chance. Fix: require numeric signatures to co-occur with an errorish marker (`and`, not `or`), or match `\b(HTTP|status)\s*50[234]\b`. **A substring signature for an error class must be anchored to error syntax, never bare digits** — when a classifier's cheapest signature is also the most common accidental substring, it will mostly report accidents ([supervise-issues: bare numeric transient signatures (502/503/504) false-positive on GitHub comment IDs](../learnings/1785802540595-supervise-issues-bare-numeric-transient-signatures.md)).

**A distinct `awaiting_us` false-positive: automation posted under a HUMAN GitHub login.** `scan.py::is_bot_author` keys on the login (`nv-slang-bot`, `coderabbitai[bot]`, …), so it correctly discounts bot-login comments but does NOT catch *automated* posts authored under a genuinely-human account. Measured Tick 222 (2026-09-13, slang#12821 / PR #12823): the chain was classified `awaiting_us` (human-spoke-last, `action=nudge`) but the "last human comment" was a `jhelferty-nv` PR-board-sync marker explicitly labeled *"do not reply to this comment"* (plus a `coderabbitai[bot]` "review skipped" notice), not a real human ask — so a BEHIND-but-mergeable draft correctly `awaiting_human` read as human-last → false `awaiting_us` → a wasted nudge. This is separate from the incomplete-bot-list case (github-actions/coderabbitai read as human because they're not in `is_bot`): here the login IS human, only the *body* is automation. Durable fix for the scan maintainer: extend the filter to ignore comments whose body carries an automation marker (`"do not reply to this comment"`, a PR-board-sync signature) even from a human login, OR maintain an `AUTOMATION_LOGINS` set (add `jhelferty-nv` board-sync). Until then, a tick that nudges a lone `awaiting_us` PR chain should expect the fixer may correctly report a bot-from-human-account false-positive — net-useful (it forces a verify) but it inflates `must_nudge` ([Supervisor scan.py false-positive awaiting_us: bot posts from human GitHub accounts](../learnings/1789307828198-supervisor-scan-py-false-positive-awaiting-us-bot-.md)).

**The supervise-issues stall-detector can fire a recurring 12h "a human commented last on PR #N and it is unanswered" nudge when the only comment is `coderabbitai[bot]`.** Two causes: the detector likely filters by "not *our* bot" rather than "not *any* bot," so a third-party bot (CodeRabbit) counts as human; and CodeRabbit edits its own comment after posting (its `updated_at` bumps hours later), so it sorts as most-recent activity past your last push. Consequence: a settled, correctly-held draft gets nudged as stalled every cycle forever — no GitHub state change clears it because the "human comment" is really a bot. Fixer action: do NOT dismiss a stall-nudge's "human comment" claim from memory — verify at source each cycle (`gh api repos/<o>/<r>/issues/<n>/comments --jq '.[]|{user:.user.login,type:.user.type}'`, plus `pulls/<n>/comments` and `pulls/<n>/reviews`), since a real human comment can arrive between nudges; if it's still only a bot, report the misclassification UP so the detector owner can exclude `user.type == "Bot"` (the fixer can't patch the detector from group scope). ([Stall-detector misreads CodeRabbit bot comment as 'human commented last'](../learnings/1789521699352-stall-detector-misreads-coderabbit-bot-comment-as-.md))

**A slangpy-specific over-flag: `pull-universe.sh`'s PR-resolution assumes the *slang* fixer's naming, so every slangpy-fixer draft-PR chain mis-flags as `awaiting_us`.** The slangpy-fixer names branches `dev/slangpy-fixer/<issue>` and writes the fully-qualified closing keyword `Fixes shader-slang/slangpy#<n>`, but both of pull-universe's resolvers assume slang conventions: the branch-convention match requires `head == fix/issue-{issue}` (or `fix/issue-{issue}-…`), and the `Fixes` regex requires a **bare** `#N` immediately after the keyword (`(?:Fixes|Closes|Resolves)\s+#(\d+)`) — so `dev/slangpy-fixer/*` never matches and `shader-slang/slangpy` between `Fixes ` and `#` defeats the regex. Both paths fail → chain resolves to `pr: None` → the fixer-owned no-PR carve-out → `awaiting_us` nudge, systematically for *every* slangpy-fixer draft-PR chain (slang chains are unaffected). Durable fix for the scan maintainer: broaden both resolvers (accept `dev/<fixer-folder>/<issue>` and owner/repo-qualified `Fixes`, i.e. `(?:[\w.-]+/[\w.-]+)?#(\d+)`), or better, prefer GitHub's own `closingIssuesReferences` (GraphQL, which links draft PRs regardless of branch/body spelling) and fall back to the regex only when empty ([supervise-issues scan mis-flags slangpy-fixer draft-PR chains as awaiting_us](../learnings/1789867842533-supervise-issues-scan-mis-flags-slangpy-fixer-draf.md)). A compounding GitHub-side cause even when the resolvers match: a **draft** PR's `Fixes` keyword produces only a `cross-referenced` timeline event, NOT a `connected` one (GitHub's "linked PR that will close this issue" fires on ready, not draft) — so a closure-detection check that greps the timeline for `connected` (or ignores draft PRs) reports "no linked PR" even though the draft auto-closes the issue on merge; the check should treat a draft PR with a closing keyword as "linked," not "missing" ([draft bot PR + Fixes keyword yields only a cross-referenced, not connected, issue link](../learnings/1789867707854-draft-bot-pr-fixes-keyword-yields-only-a-cross-ref.md)). For a fixer *receiving* such a nudge: it is NOT authoritative about GitHub state — verify live (`gh pr view <n> --json state,isDraft,statusCheckRollup`, the issue timeline for `cross-referenced`/`connected`) and respond from that, never close the issue or self-promote/merge the PR on the nudge (draft→ready and merge are human gates; a green, peer-reviewed, correctly-held draft means the blocker is a human gate — say so and hold), and leave a state snapshot at `/workspace/agent/reports/<n>.md` so a restarted session and the supervisor's artifact check both find something concrete ([a supervisor "no PR / no resumable artifact" nudge can be a false positive — verify live state, never close/merge on it](../learnings/1789867916485-a-supervisor-no-pr-no-resumable-artifact-nudge-can.md)).

**A Tick-238 census (7 of 9 nudges were false positives / design-holds) enumerates four `awaiting_us` gaps, most fixable in `scan.py`.** (1) **`bot_logins` under-specified** — it defaults to only `nv-slang-bot[bot]`/`nv-slang-bot`, so `coderabbitai`/`coderabbitai[bot]` and `github-actions`/`github-actions[bot]` (board-sync + CI comments, many literally "do not reply") count as HUMAN and fire "human spoke last, unanswered" on pure bot chatter — the same incomplete-bot-list root as the CodeRabbit stall-detector case above; add them to the bot set (or a distinct board/CI-bot ignore-list). (2) **A maintainer APPROVE review with no change-requests is scored as an unanswered ask** (#13165: an "LGTM" review, `review_comments:[]`) — treat an APPROVE with no inline comments as `awaiting_human` (merge-gated), not `awaiting_us`. (3) **Adjudicated hold-silent comments re-fire every tick** (#13203, #13177: design comments already adjudicated "no-post" hours earlier, no @-bot mention/ask) because the adjudication isn't visible to scan — persist a per-comment "adjudicated no-post" marker (comment id) in supervisor-state and suppress re-flag until a NEWER human comment lands, and/or down-weight comments that don't @-mention the bot and carry no question/gap/request. (4) **Design-gated holds nudge on their first tick** (#13198/#13208/#13209, fixer instructed "context-only, await go/no-go") because the held disposition wasn't yet journaled — journal the `advisory:maintainer-driving`/`stood-down` disposition into supervisor-state at DISPATCH time, not on first supervisor nudge ([supervise-issues scan.py awaiting_us false-positive modes — Tick 238, 7 of 9 nudges](../learnings/1790044307828-supervise-issues-scan-py-awaiting-us-false-positiv.md)).
