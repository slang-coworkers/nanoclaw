## TL;DR

Slang's SPIR-V capability system decides whether an emitted instruction is legal, but it does NOT decide whether the instruction is emitted — the IR does. Key facts:

- **Capabilities gate diagnostics, not codegen.** If a shader uses float atomic-add, Slang emits `OpAtomicFAddEXT` regardless of the target profile; a missing capability atom is (by default) an implicit-upgrade *warning*, not a refusal, and there is NO CAS/CompareExchange emulation fallback. Only `-restrictive-capability-check` turns it into a hard error.
- **Capability-declaration-completeness fixes** (a decoration/op needs a cap the module never declared) are additive-only and low-risk: they can only add an `OpCapability` line. Confirm the exact decoration→capability pairing against `spirv.core.grammar.json`, that it is a single emit site, and that the test's positive control does not self-declare the cap via a system value.
- **Capability atoms carry transitive implications.** A version alias (`spirv_1_5`) bundles extension atoms; a bare extension implies a version floor. To classify "did the user request a version vs an extension," test the **non-implied LEAF atoms** (`newSetWithoutImpliedAtoms`), never the closure. `def X : Y` means X implies Y; siblings sharing a parent do NOT imply each other.
- **Storage-class / bit-width caps** must be split per storage class: `RWStructuredBuffer<uint8_t>` needs narrow `StorageBuffer8BitAccess`, not broad `UniformAndStorageBuffer8BitAccess`. The narrow enumerants are already vendored in `spirv.h` (generated, not capdef) — no submodule bump needed. Enforce narrow↔broad subsumption at the ONE funnel (`requireSPIRVCapability`), not by coordinating arms. Watch: `-profile spirv_1_3` uses legacy `BufferBlock`/`Uniform` encoding and hides the modern-path bug.
- **Stage restriction via capability atoms is unreliable when a `__target_switch` has a permissive/empty `case metal: break;` arm** — it re-admits stages for body-INFERRED caps. But an explicit `[require]` on a PUBLIC decl *replaces* the caller-visible set, so it IS sufficient there; the dedicated call-graph check is only forced when the rule can't be a public-decl `[require]`.
- **slang-rhi capability accounting is SPIR-V-neutral** under the default (non-restrictive) profile — fixing which Vulkan bit advertises a cap does not change emitted SPIR-V. The vk.xml `<spirvcapability><enable>` table is authority; one Vulkan bit can enable TWO SPIR-V caps.
- **Availability = the intrinsic's `[require]` target set AND its `__target_switch` case bodies** — widen both together or the fix is half-done.

## Capabilities gate diagnostics, not whether an instruction is emitted

The load-bearing mental model, verified repeatedly across these atoms: **Slang emits SPIR-V ops from the IR (what the shader used), and the target profile's capability set only decides error/warning/clean — not whether the op appears.** For a float `InterlockedAddF32` on an `RWByteAddressBuffer`, the path is `getSpvAtomicOp → SpvOpAtomicFAddEXT` and `ensureAtomicCapability` *unconditionally* requires `SpvCapabilityAtomicFloat32AddEXT` plus the `SPV_EXT_shader_atomic_float_add` extension; there is no CAS/CompareExchange emulation fallback, so a missing capability yields a compile error, not silent emulation ([float atomic-add hard-requires the capability](../learnings/1786470707558-slang-spir-v-float-atomic-add-hard-requires-the-ca.md)). Measured directly on the slang-rhi side, the capability atom being PRESENT vs ABSENT in the profile produces **byte-identical SPIR-V** (both emit `OpAtomicFAddEXT`, only differing by an `E41012 profile implicitly upgraded` warning) because slang-rhi passes no `-restrictive-capability-check` — an unsatisfied capability is an implicit upgrade, not a refusal ([slang-rhi capability push is SPIR-V-neutral](../learnings/1786511622280-slang-rhi-capability-push-is-spir-v-neutral-under-.md)). A corollary triage lesson: Slang's SPIR-V output is a function of the declared target + capability profile, NOT the physical GPU, so "diff the NVIDIA-GPU SPIR-V vs the AMD-GPU SPIR-V" is a category error; the only device axis is capability-set-dependent codegen, forceable at compile time with no GPU.

## Capability-declaration-completeness: a low-risk additive shape

A recurring safe shape is a target emitter that emits a decoration/instruction whose spec entry requires a capability the module never declared, so validation rejects it (e.g. `OpDecorate ... Sample` requires `SampleRateShading` but only `Shader` was declared). The fix declares the missing cap at the emit site via the idempotent funnel `requireSPIRVCapability(...)`. This is low-risk because it is **additive-only** (can only ADD an `OpCapability` line — cannot regress a byte-identical codegen expectation), uses an established funnel, and (usually) is a single emit site. The real diligence is on the TEST: it must be a positive control that does NOT use a system value that self-declares the same cap (e.g. `SV_SampleIndex`/`SV_VulkanSamplePosition` self-declare `SampleRateShading`), and it must use a `-target spirv` binary directive so validation actually runs. This shape was confirmed merged-unchanged by a maintainer for slang#12467 ([SPIR-V capability-declaration completeness fixes are low-risk](../learnings/1786496880243-approver-confirmed-safe-spir-v-capability-declarat.md)).

Availability of an intrinsic is a *two-part* contract: for a SER `HitObject` accessor rejected with `E36107` on `-target spirv`, the accessor declared only `[require(hlsl,…)]`+`[require(cuda,…)]` and a hlsl+cuda-only `__target_switch` — missing both `[require(glsl_spirv,…)]` and the `case spvShaderInvocationReorderNV/EXT` bodies. **The fix is always two parts together: widen the `[require]` target set AND add the matching `__target_switch` cases** (each SER accessor needs a separate NV and EXT case); widening `[require]` alone leaves the emit path absent ([HitObject SPIR-V accessor gaps](../learnings/1786768951062-hitobject-spir-v-accessor-gaps-check-require-targe.md)).

## Capability atoms carry transitive implications — classify over leaves

Slang capability atoms form a closure under `def X : Y` (X requires/implies Y). This breaks intuitive membership tests. When narrowing the GLSL-target SPIRV exemption in `TargetRequest::checkCapabilities()`, the intuitive predicate "exempt only if every SPIRV-family atom is an `isSpirvVersionAtom`" is empirically WRONG and regresses `spirv_1_5`: a version alias like `spirv_1_5` does not expand to version atoms alone — its closure BUNDLES extension atoms (`SPV_EXT_*`), while a bare extension request implies a version floor. In the flattened closure a version request and an extension request are indistinguishable. The correct discriminator is the **non-implied LEAF set** (`newSetWithoutImpliedAtoms()`): a version alias keeps its version atom as a surviving leaf, whereas a bare extension implies its version floor *away*, so "a version was requested iff a version leaf survives" ([separate a SPIRV version alias from a bare extension by leaf atoms](../learnings/1787578480991-slang-capability-separate-a-spirv-version-alias-fr.md)).

The same implication structure is confirmed in slang-rhi's coop-matrix2 work: reporting a child cap (`spvCooperativeMatrixReductionsNV`) transitively implies its parent (`SPV_NV_cooperative_matrix2`), so slang-rhi need not push the parent extension atom when a sub-cap is set — but **siblings sharing a parent do NOT imply each other** (`spvTensorAddressingNV` and `spvCooperativeMatrixTensorAddressingNV` both need the parent but neither implies the other). And the vk.xml `<spirvcapability name="X"><enable ... feature="bit">` table is the authority for which Vulkan feature bit enables which SPIR-V capability — it is not always 1:1: the single `cooperativeMatrixTensorAddressing` bit enables BOTH `TensorAddressingNV` and `CooperativeMatrixTensorAddressingNV`, so pushing only one leaves `TensorView`/`TensorLayout` shaders passing `-render-feature` gating but failing SPIR-V compilation ([slang-rhi coop-matrix2: one Vulkan bit can enable TWO SPIR-V caps](../learnings/1788377110401-slang-rhi-coop-matrix2-one-vulkan-bit-can-enable-t.md)).

**Over-broad exemptions are a real bug class.** A "these are handled elsewhere so don't flag them" exemption is only safe over exactly what the *other* path transforms — not the whole family the membership test matches. In slang#11225, `checkCapabilities` exempted a cap on a GLSL target when its set contains `spirv` (ALL spirv-family caps), but the sibling `getTargetCaps()` only auto-converts spirv *version* atoms — so a spirv *extension* cap on a GLSL target is exempted from the diagnostic yet silently dropped with no error, which is the exact bug the PR exists to fix. Read the elsewhere-path and compare the two sets element-wise; a superset match means silently-dropped input (OPEN_GAP, under-diagnosis) ([capability-target GLSL exemption is over-broad](../learnings/1786732724988-approver-challenger-miss-capability-target-glsl-ex.md)).

## Storage-class / bit-width capabilities: split per class, subsume at the funnel

When Slang emits an over-broad `UniformAndStorageBuffer8BitAccess` where narrow `StorageBuffer8BitAccess` suffices (slang#9910: `RWStructuredBuffer<uint8_t>` rejected on devices exposing only `storageBuffer8BitAccess`), the root cause is a **storage-class coalescing bug, not a missing atom**. The narrow enumerants (`StorageBuffer8BitAccess=4448`, `...16BitAccess=4433`) are already vendored in the generated `spirv.h` (NOT a capdef atom — nothing to regenerate). The bug is in `requireCapabilitiesForType(IRType*, SpvStorageClass)` (`slang-emit-spirv.cpp` ~:10269), whose 8/16-bit arm coalesces `Uniform` and `StorageBuffer` into one `case` and hard-codes the broad cap; the `PushConstant` arm is already correctly split (`StoragePushConstant8/16`) — use it as the model ([over-broad SPIR-V 8/16-bit storage capability is a coalescing bug](../learnings/1787690827436-over-broad-spir-v-8-16-bit-storage-capability-is-a.md)).

Two subtleties for the fixer. First, **enforce subsumption at the single insertion point**: `requireCapabilitiesForType` is called lazily per pointer-type emission, so its `Uniform` and `StorageBuffer` arms fire in emission order, not source order — an initial fix that coordinated the two arms leaked BOTH caps when a struct is bound through a ConstantBuffer AND a RWStructuredBuffer with the uniform access emitted first. The robust fix enforces the invariant at the ONE funnel every cap goes through (`requireSPIRVCapability`): skip a narrow request when its broad superset is present, and retract a subsumed narrow when adding the broad — order-independent, single source of truth, with the narrow↔broad pairing in one helper (`getStorageBufferCapabilityPair`). Also note the narrow cap ALSO covers legacy SSBOs (`Uniform` + `BufferBlock`-decorated), so "Uniform class ⇒ broad cap" is false ([SPIR-V storage capability subsumption must be enforced at the single insertion point](../learnings/1788166383343-spir-v-storage-capability-subsumption-must-be-enfo.md)). Second, **the SPIR-V version profile changes the storage class and can HIDE the bug**: `-profile spirv_1_3` emits an SSBO with the legacy `BufferBlock`+`Uniform` encoding (where the broad cap is genuinely correct), while default/`spirv_1_5` uses modern `Block`+`StorageBuffer` (where narrow is minimal). A storage-buffer capability test must therefore use default/1.5+, not 1.3, or it never exercises the buggy modern path ([SPIR-V storage-buffer cap bugs: -profile spirv_1_3 hides them](../learnings/1787699257464-spir-v-storage-buffer-cap-bugs-profile-spirv-1-3-u.md)).

## Stage restriction: capability atom vs dedicated call-graph check

Slang's structural ray-tracing checker rejects stage-illegal use only when `capabilities->isIncompatibleWith(getAtomFromStage(stage))` is true, and `isIncompatibleWith` returns "compatible" if ANY target key shares ANY intersecting stage. A stdlib wrapper whose body is `__target_switch { case metal: break; default: <native>; }` leaves an UNCONSTRAINED `metal` entry (empty break body ⇒ metal target with all stages). Since Metal legitimately pairs e.g. `_anyhit + metal`, the join finds a match under the `metal` key and no diagnostic fires — even though the intrinsic's own `[require]` propagated. This is why `callShader` uses a dedicated call-graph reachability check instead of a capability atom ([capability isIncompatibleWith is defeated by an unconstrained target arm](../learnings/1787668797917-slang-capability-isincompatiblewith-is-defeated-by.md)).

That first atom **over-generalized**, and its own author corrected it: the Metal-arm escape only applies to the **body-INFERRED** capability set. For a **public declaration**, an explicit `[require]` *REPLACES* the caller-visible set outright (it is not joined with body-inferred caps): `slang-check-decl.cpp` public-decl branch sets `inferredCapabilityRequirements = frozenDeclaredCaps`. So for slang#12740, `kaizhangNV` simply added `[require(structural_raytracing_trace)]` (a capdef atom excluding anyhit on every arm) to all 8 public `RayTracer.trace` overloads, and the generic check fired correctly — no dedicated call-graph check needed. **Net rule: if the API is a PUBLIC decl, an explicit `[require]` atom is sufficient and simplest; the dedicated-check pattern is only forced when the restriction can't be expressed as a `[require]` on a public decl (like callShader)** ([CORRECTION: capability Metal-arm escape applies to INFERRED caps only](../learnings/1787671921753-correction-capability-metal-arm-escape-applies-to-.md)).
