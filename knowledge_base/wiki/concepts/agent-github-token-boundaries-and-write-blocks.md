# Agent GitHub Token Boundaries and Write-Blocks

> Companion to the core [GitHub Auth and Operations in Agent Containers](agent-infra-github-auth-operations.md) (the `gh auth status` false-negative rule, the works/does-not-work catalog, the App-identity permission catalog, PR-session mapping) and its sibling [Agent GitHub Fork-Takeover and Rebase Mechanics](agent-github-fork-takeover-and-rebase.md). This page holds the hard write-blocks on the `nv-slang-bot` App token, reviewing/triaging under an invalid token, the empty-list-looks-like-success trap, and the (resolved) 07-16/07-17 auth-outage contradiction.

## TL;DR

- The `nv-slang-bot` **App installation token** carries hard, durable write-blocks — not transient — on **GitHub Discussions** and **`.github/workflows/*`**, plus it has no user identity. Issue/PR comments and normal file pushes still work.
- **Discussions:** `addDiscussionComment` → `FORBIDDEN: Resource not accessible by integration`. Retry gives the same error. To answer a Discussion thread, post on the *linked issue* and tell the human the discussion surface is unreachable.
- **Workflows:** pushing `.github/workflows/*` is rejected — `refusing to allow a GitHub App to create or update workflow … without 'workflows' permission`. Don't retry: deliver the workflow as a ready-to-apply patch (fenced YAML + a note a human must commit it), and flag workflow-scoped fixes as maintainer-only at triage.
- **Reviewing/triaging still works under an invalid / `placeholder` `GH_TOKEN`.** `git ls-remote` / `git fetch origin <head-branch>` and unauthenticated REST reads succeed; only GitHub *writes* are blocked. Review the fetchable head branch by name (`git diff <merge-base> <branch>`); degrade writes to `send_file` to parent — never fabricate a "posted" status.
- **An unauth 404 on `pulls/<n>` within ~1 min of PR creation is a replication-cache false alarm**, not proof the PR is absent — confirm with an authenticated query.
- **A human-cred merge during a bot `actions:write` outage is NOT bot write recovery.** Re-probe with an actual bot write (`gh run rerun --failed`, exit 0); never infer recovery from a merge or queue movement.
- **An empty list (`total_count:0`) is a successful-looking empty response, not an error.** On a repo that always has open issues it is a tool-malfunction signal, not "zero new issues" — cross-check via the unauthenticated GitHub REST API.
- **The 07-16/07-17 "GitHub auth outage" is RESOLVED** — do NOT carry forward any "auth / actions / GraphQL / git-push is down" or "hold read-only" assumption. Keep the REST-vs-actions-vs-GraphQL split and the empty-list trap as *diagnostic techniques* for a future problem; re-diagnose from scratch if a new 401 cluster appears.

## The Discussions Write-Block

Confirmed 2026-07-16: the `nv-slang-bot` GitHub **App** installation lacks the **Discussions: write** permission ([nv-slang-bot GitHub App CANNOT post to Discussions (addDiscussionComment → FORBIDDEN)](../learnings/1784185128581-nv-slang-bot-github-app-cannot-post-to-discussions.md)). The `addDiscussionComment` GraphQL mutation returns `FORBIDDEN: Resource not accessible by integration` — Discussions are outside the App's permission scope, unlike issues/PRs which it comments on freely. This is a hard block, not transient: retry gives the same error. Consequence: to answer a user thread that lives on a *Discussion* (e.g. discussion #11840), post the answer on the linked *issue* (the discussion→issue cross-reference surfaces it) and tell the human the discussion surface is unreachable. This is orthogonal to the `gh auth status` false-negative — issue/PR writes still work ([nv-slang-bot App token CANNOT write to GitHub Discussions (only issues/PRs)](../learnings/1784542479875-nv-slang-bot-app-token-cannot-write-to-github-disc.md)).

## The Workflow-File Push Block — Deliver CI as a Patch

The `nv-slang-bot` App token **cannot push files under `.github/workflows/`** — the push is rejected with `refusing to allow a GitHub App to create or update workflow .github/workflows/<name>.yml without 'workflows' permission`. This is a hard, durable limitation: the token simply lacks the `workflows` permission, so it also cannot open PRs that touch `.github/workflows/*` ([nv-slang-bot App lacks 'workflows' permission — cannot open PRs touching .github/workflows/*](../learnings/1784154056053-nv-slang-bot-app-lacks-workflows-permission-cannot.md)). Normal file pushes and `gh` issue/PR-comment ops work fine; only the `workflows` scope is missing. Don't burn time retrying — deliver the workflow as a ready-to-apply artifact (fenced YAML + a note that a human must commit it) in a PR/issue comment and ask a maintainer to land it or grant the scope. A maintainer will policy-close a coworker-bot workflow PR anyway, so flag workflow-scoped fixes as maintainer-only at triage.

Two verified slangpy-samples CI corollaries shape any workflow you hand off: its example suite (`tests/examples/test_examples.py`) creates a real GPU device and **cannot run on GitHub-hosted runners** (slangpy fails on software Vulkan/llvmpipe → `Failed to create device!`) — GPU CI needs a self-hosted runner (`runs-on: {group: nvrgfx, labels: [Linux, X64]}`); and its `.npz` expected-output fixtures are **Git LFS** objects, so checkout must use `actions/checkout@v4` with `lfs: true` or tests get 129-byte pointer files ([Bot App token CANNOT push .github/workflows/* — deliver CI as a patch; slangpy-samples GPU-runner + LFS constraints](../learnings/1785048496087-bot-app-token-cannot-push-github-workflows-missing.md)).

## Reviewing and Triaging Under an Invalid / Placeholder Token

When `GH_TOKEN` is literally `placeholder` (len 8), `gh auth status` fails "token is invalid" and `gh pr view` returns "Could not resolve to a PullRequest" — but `git ls-remote origin` and `git fetch origin <head-branch>` still succeed (the remote URL embeds `x-access-token:placeholder@…` and the public repo allows anonymous git read), and unauthenticated `curl https://api.github.com/repos/…` works for public issues/PRs (60 req/hr). So review the fetchable **head branch by name** via `git diff <merge-base> <branch>`; only GitHub *writes* are blocked — degrade to `send_file` to parent, never fabricate a "posted" status ([PR review under invalid GH_TOKEN — review the fetchable branch, don't stall](../learnings/1784595260519-pr-review-under-invalid-gh-token-review-the-fetcha.md)).

**Important correction to the anon-fallback:** do NOT read an unauthenticated 404 on `pulls/<n>` (while repo + issue return 200) as proof the PR was never opened. Observed on #12168: the PR *was* real (draft, created 00:54:36Z); the anon probe ~30s later hit GitHub's replication/cache window where the branch had propagated to the anonymous read path but the PR object had not. An **authenticated** query resolved it cleanly. Corrected rule: an unauth 404 within ~1 min of PR creation is most likely propagation lag — review the fetchable head branch and flag it up-chain as "PR not visible on the anon path yet — confirm via an authenticated query," not "PR never opened" ([Correction — unauth GitHub 404 right after PR creation is a replication-cache false alarm](../learnings/1784595649737-correction-unauth-github-404-right-after-pr-creati.md)).

## Human-Cred Merge ≠ Bot Write Recovery

During a bot `actions:write` outage (OneCLI GitHub disconnect / gateway 403), a PR flipping to MERGED is NOT evidence the write path recovered — a human maintainer can merge on their own creds while the bot is still 403'd. To confirm recovery, re-probe with an ACTUAL bot write (`gh run rerun --failed` on a genuine flake) and check exit 0; never infer recovery from a merge or queue movement, which humans / GitHub-auto can drive ([human-cred PR merge during an actions:write outage ≠ bot write recovery](../learnings/1784736496164-human-cred-pr-merge-during-actions-write-outage-bo.md)).

## The Empty-List-Looks-Like-Success Trap

When a list/search tool (an MCP `github_list_issues` / `github_search_issues`, or `gh` returning empty via an invalid token) returns `{"issues": [], "total_count": 0}`, that is a *successful-looking empty response*, not an error — and on a repo that always has open issues (shader-slang/slang), `total_count:0` is a tool-malfunction signal, NOT "zero new issues." Never report "no new issues" off an empty list without cross-checking. The durable fallback is the **unauthenticated GitHub REST API**, which returns real data for issues/PRs/actions with no token: `curl -s "https://api.github.com/repos/shader-slang/slang/issues?state=open&sort=created&direction=desc&per_page=40"` (filter out entries with a `pull_request` key), `.../pulls?state=closed&sort=updated&...` for merged PRs, `.../actions/runs?status=failure&...` for CI failures, and `curl -s https://raw.githubusercontent.com/shader-slang/slang-ci-analytics/main/health_snapshots.jsonl | tail -1` for the CI-health snapshot. Its value is independence from a flaky MCP server — keep it as a general resilience technique ([slang-mcp degraded: use unauth GitHub REST fallback for daily report](../learnings/1784276460761-slang-mcp-degraded-use-unauth-github-rest-fallback.md)).

## Contradiction Resolved — the 07-16/07-17 "auth outage" is fixed

The 07-16/07-17 "GitHub gateway 401 split" diagnostic and the earlier `slang-mcp` degraded note were filed during a **transient migration credential regression on 2026-07-16/07-17 that is now FIXED** — do NOT carry forward any "GitHub auth / actions / GraphQL / git-push is down" or "hold read-only" assumption. Root cause (dashboard-admin, 07-17): the App-token refresh cron silently died because `gh` was not installed on the newly-migrated host, so with no `gh` the refresh step failed and the github.com App token expired hourly — every `actions` API and GraphQL call then 401'd `Bad credentials`, and the 07-17 write-path "Must-have-admin-rights" symptom was the same expired-token cause, not a privilege problem. Fix: `gh` 2.96 installed on the host, the refresh cron guarded so it won't silently no-op on a missing dependency, and git-push split into non-overlapping secrets (`/shader-slang/slang*` App token + `/slang-coworkers/<repo>*` USER PAT). Verified recovered 07-17 ~11:47Z: `gh api graphql '{viewer{login}}'` → `nv-slang-bot[bot]`, `actions/runs .total_count` → 40000, `gh run list` works, both git-push targets succeed. **Read-only hold is LIFTED** — resume full CI sweeps, reruns, and requeues; do not defer classification citing this outage. Keep the REST-vs-actions-vs-GraphQL split (and the empty-list trap above) as *diagnostic techniques* for characterizing a future cred/gateway problem, but treat them as probe methods, not a current state — and if a future 401 cluster appears, re-diagnose from scratch (which paths fail? is the refresh cron alive / is `gh` present?) rather than assuming this specific outage recurred ([CORRECTION: GitHub gateway actions/GraphQL 401 outage (07-16) is RESOLVED 07-17 — do NOT hold read-only](../learnings/1784288884629-correction-github-gateway-actions-graphql-401-outa.md), [CORRECTION: gh/token/gateway auth was NOT broken on 2026-07-17 (transient cred regression, now fixed)](../learnings/1784288847791-correction-gh-token-gateway-auth-was-not-broken-on.md)). A truly-flaky `slang-mcp` server is a *separate* problem to diagnose independently — an `Upstream MCP server unavailable` from `slang-mcp` tools is an MCP-server issue, unrelated to the (now-fixed) GitHub credential.
