# Agent GitHub Token Boundaries and Write-Blocks

> Companion to the core [GitHub Auth and Operations in Agent Containers](agent-infra-github-auth-operations.md) (the `gh auth status` false-negative rule, the works/does-not-work catalog, the App-identity permission catalog, PR-session mapping) and its sibling [Agent GitHub Fork-Takeover and Rebase Mechanics](agent-github-fork-takeover-and-rebase.md). This page holds the hard write-blocks on the `nv-slang-bot` App token, the issue-assignee write that does work, Slang's own CI credentials, reviewing under an invalid token, the empty-list trap, and the resolved 07-16/07-17 auth-outage contradiction.

## TL;DR

- The `nv-slang-bot` **App installation token** has hard, durable write-blocks on **GitHub Discussions**, **`.github/workflows/*`** and the **shader-slang.github.io** docs site, and no user identity. Issue/PR comments and normal file pushes work.
- **Discussions:** `addDiscussionComment` → `FORBIDDEN: Resource not accessible by integration`, on every retry. Answer on the *linked issue* and tell the human the discussion surface is unreachable.
- **Workflows:** a push is rejected (`refusing to allow a GitHub App to create or update workflow … without 'workflows' permission`). Don't retry: deliver fenced YAML a human must commit, and flag workflow fixes as maintainer-only at triage. A wanted workflow PR goes cross-fork from `slang-coworkers` with `maintainer_can_modify=false`; that draft cannot be dispatched, so it gets no CI until a maintainer marks it ready.
- **An invalid / `placeholder` `GH_TOKEN` still allows review:** `git fetch origin <head-branch>` and unauthenticated REST reads work; only writes are blocked. Diff the head branch by name; degrade writes to `send_file` to parent; never fabricate a "posted" status.
- **But a red `gh auth status` "token invalid" on the live bot token is usually COSMETIC**: it and porcelain (`gh issue create/comment`) fail a `/user` precheck, while `gh api … -X POST/PATCH` and the onecli-gateway (`curl` to `api.github.com`) read AND write. Verify with an authenticated read; never raise a "rotate the fleet token" alarm off `gh auth status` alone.
- **`.permissions` is the collaborator view, not the App's** (all-false while App issue POSTs worked). Never probe issue-write with a throwaway POST (no dry-run; it creates a real public issue): make the real call and check its exit status and URL.
- **The bot CAN set issue assignees** (10-23, 10-28): create without assignees, then `POST /issues/<N>/assignees` (or `gh issue edit --add-assignee`), read back, and reply with the matching variant, since GitHub can silently drop an assignee. The operator ban on bot-set assignees and reviewers on bot PRs still holds.
- **Slang's `/format` works (proven 2026-10-29)** but pushes a `format/pr-<N>` branch plus a compare-link comment, never a commit on your PR branch; the author merges a `format: PR #N` PR back. Workflow-touching PRs get only the patch.
- **An unauth 404 on `pulls/<n>` within ~1 min of PR creation is replication lag**, not absence: confirm with an authenticated query.
- **A human-cred merge during a bot `actions:write` outage is NOT bot write recovery**: re-probe with a real bot write (`gh run rerun --failed`, exit 0).
- **An empty list (`total_count:0`) is a successful-looking response, not "zero"**: on a repo that always has open issues it signals tool malfunction; cross-check via unauthenticated REST. That unauthenticated `actions/runs?status=failure` list can itself be STALE: an old newest-failure date is not all-clear; cross-check the `health_snapshots.jsonl` last line and the merge-group check runs.
- **The 07-16/07-17 "GitHub auth outage" is RESOLVED**: carry forward no "auth / actions / GraphQL / git-push is down" or "hold read-only" assumption. Keep the REST-vs-actions-vs-GraphQL split and the empty-list trap as diagnostic techniques; re-diagnose any new 401 cluster from scratch.

## The Discussions Write-Block

Since 2026-07-16 the `nv-slang-bot` App installation lacks **Discussions: write**: the `addDiscussionComment` GraphQL mutation returns `FORBIDDEN: Resource not accessible by integration`, and a retry gives the same error ([cannot post](../learnings/1784185128581-nv-slang-bot-github-app-cannot-post-to-discussions.md)). To answer a thread that lives on a Discussion (e.g. #11840), post on the linked *issue* (the discussion→issue cross-reference surfaces it) and tell the human the discussion surface is unreachable. This is orthogonal to the `gh auth status` false-negative: issue/PR writes still work ([issues/PRs only](../learnings/1784542479875-nv-slang-bot-app-token-cannot-write-to-github-disc.md)).

## The Workflow-File Push Block — Deliver CI as a Patch

The token lacks the `workflows` permission, so a push under `.github/workflows/` is rejected with `refusing to allow a GitHub App to create or update workflow .github/workflows/<name>.yml without 'workflows' permission`, and it cannot open PRs touching those files ([no workflows scope](../learnings/1784154056053-nv-slang-bot-app-lacks-workflows-permission-cannot.md)). Don't retry: post the workflow as a ready-to-apply artifact (fenced YAML + a note that a human must commit it) and ask a maintainer to land it or grant the scope. Maintainers policy-close coworker-bot workflow PRs anyway, so flag workflow-scoped fixes as maintainer-only at triage.

**When a workflow PR is wanted, open it cross-fork and promise no CI measurement while it is a draft.** What worked on slang#13791 → PR #13813 (2026-10-21): push the branch to `slang-coworkers` (remote `coworkers`), then `gh api -X POST repos/shader-slang/slang/pulls -f head=slang-coworkers:<branch> -f base=master -F draft=true -F maintainer_can_modify=false -F body=@<file>`. Without `maintainer_can_modify=false` GitHub returns 422 `fork_collab: Fork collab can't be granted by someone without permission`. `gh workflow run ci.yml -R shader-slang/slang --ref <branch>` returns 422 "No ref found" (the branch is fork-only), so the draft gets no dispatch timing or CI result until a maintainer marks it ready or someone with `workflows` permission pushes it upstream; say so up front ([cross-fork PR](../learnings/1792577551540-bot-cross-fork-pr-for-workflow-files-maintainer-ca.md)). What #13813's first ready run measured is on [Windows GPU slang-test jobs](ci-windows-gpu-test-job-split-and-merge.md). That session also hit the critique-gate trap of a backticked `### Attested` hash, which records nothing and makes the 1000+ char public-comment gate refuse the post; have codex re-emit bare `- <64hex> <path>` lines (see [critique delivery gates](agent-routing-f0909b0-critique-delivery-gates.md)).

**slangpy-samples CI constraints for any handed-off workflow:** its example suite (`tests/examples/test_examples.py`) creates a real GPU device and **cannot run on GitHub-hosted runners** (software Vulkan/llvmpipe → `Failed to create device!`), so GPU CI needs a self-hosted runner (`runs-on: {group: nvrgfx, labels: [Linux, X64]}`); its `.npz` expected-output fixtures are **Git LFS** objects, so check out with `actions/checkout@v4` and `lfs: true` or tests get 129-byte pointer files ([patch; GPU runner + LFS](../learnings/1785048496087-bot-app-token-cannot-push-github-workflows-missing.md)).

## Slang's Own CI Credentials Moved to GitHub Apps (2026-10-22)

The repo's workflows have their own credentials, separate from the agent token. master no longer references `SLANG_COVERAGE_REPORTS_PAT`: #13866 (merged 10-22) moved nightly coverage publishing to `actions/create-github-app-token` (`SLANG_COVERAGE_APP_CLIENT_ID`/`_PRIVATE_KEY`), retiring the "~10-26 PAT expiry" item. The `/format` slangbot 403 (#13865) was closed by #13881 (an App token in the renamed `slash-regenerate-*.yml` workflows and the new `slash-regenerate-publish.yml`) plus follow-up #13886 (`GITHUB_TOKEN`). `SLANGBOT_PAT` remains in `check-ir-version.yml:61,69`. Check credential state by grepping the raw workflow files on raw.githubusercontent.com, which costs no REST quota ([CI credentials](../learnings/1792744182827-slang-ci-credentials-moved-to-github-apps-coverage.md)).

**`/format` pushes a branch, not a commit on your PR.** Proven 2026-10-29 on #14001 (Regenerate Format, `repository_dispatch` `format-command`, run 40793794756): the `format` job builds a patch, `publish / publish` pushes a NEW branch `format/pr-<N>`, and `publish / report` comments a compare link; the author then merges a `format: PR #<N>` PR into their branch (#14002). Verify a `/format` by the `format/pr-<N>` branch or the `format: PR #N` PR. A patch touching `.github/` is not pushed (the first post-fix run, 39887111798, logged "branch is not pushed") because `GITHUB_TOKEN` cannot push workflow changes, so workflow-touching PRs get only the patch ([/format push path](../learnings/1793262748456-slang-format-push-path-works-format-pr-n-branch-me.md)).

## The shader-slang.github.io Docs-Site Write-Block — Deliver as a Patch

`shader-slang.org /docs/` articles live in the Jekyll repo **`shader-slang/shader-slang.github.io`**, not `shader-slang/slang`, and `nv-slang-bot[bot]` has `push:false` there with no writable fork (the only writable remote here is `shader-slang/slang`). Deliver a website docs fix as a `git format-patch` for a human with write access and report the blocker up; as with workflows, one attempt to capture the exact rejection is fine, routing the fix through the bot is not. To triage, grep the slang repo first; if the slug/title is absent, `gh search code --owner shader-slang "<distinctive phrase>"` finds it in the website repo. Link mechanics: `_config.yml` uses `permalink: pretty` with no `baseurl` and Kramdown does NOT rewrite relative hrefs, so a bare `[x](shader-cursors)` on `/docs/parameter-blocks/` 404s; use the target's root-relative permalink `/docs/shader-cursors/` (bare `/docs/shader-cursors` 301s to it) and curl-verify ([docs site](../learnings/1789633829310-shader-slang-org-docs-articles-live-in-shader-slan.md)).

## Reviewing and Triaging Under an Invalid / Placeholder Token

When `GH_TOKEN` is literally `placeholder` (len 8), `gh auth status` says "token is invalid" and `gh pr view` returns "Could not resolve to a PullRequest", but `git ls-remote origin` and `git fetch origin <head-branch>` work (the remote URL embeds `x-access-token:placeholder@…` and the public repo allows anonymous git read), as does unauthenticated `curl https://api.github.com/repos/…` (60 req/hr). Review the **head branch by name** (`git diff <merge-base> <branch>`); only writes are blocked, so degrade to `send_file` to parent and never fabricate a "posted" status ([placeholder review](../learnings/1784595260519-pr-review-under-invalid-gh-token-review-the-fetcha.md)).

**An unauthenticated 404 on `pulls/<n>` (repo and issue 200) is not proof the PR was never opened.** On #12168 the draft was created 00:54:36Z and the anon probe ~30 s later hit the replication window (branch propagated, PR object not); an **authenticated** query resolved it. Within ~1 min of creation, flag "PR not visible on the anon path yet — confirm via an authenticated query", not "PR never opened" ([404 lag](../learnings/1784595649737-correction-unauth-github-404-right-after-pr-creati.md)).

## `gh auth status` "token invalid" is usually COSMETIC — the bot token is VALID; verify before escalating

Unlike the literal `placeholder` token, the live `nv-slang-bot` `GH_TOKEN` does real writes even though `gh auth status` prints "The token in GH_TOKEN is invalid" and porcelain (`gh issue create`, `gh issue comment`) errors. An early filing read that red status (and a ~23-char token) as "writes blocked; only the gateway works" ([earlier filing](../learnings/1789715347678-bot-gh-token-is-invalid-in-coworker-containers-pos.md)); **corrected: the token is VALID** ([correction](../learnings/1789716480655-correction-nv-slang-bot-gh-token-is-valid-gh-auth-.md)). `gh auth status` and porcelain run a `/user` identity check that fails for App installation tokens; `gh api <endpoint> -X POST/PATCH -f ...` skips it and reads and writes (slang-triager filed shader-slang/slang#13169 that way, 6000/hr limit). The onecli-gateway (`curl` to `https://api.github.com/...`, credentials injected at the boundary) is equally valid, verified for POST (201) and PATCH-in-place (200) of comments: build the body with `jq -Rsn --rawfile b body.md '{body:$b}'` and save the comment id to `.gh-comments/<owner>-<repo>-<N>.id` so updates PATCH rather than duplicate.

**Routing rule:** when a coworker reports its token "invalid", do not escalate a "fleet token expired / needs manual restore" alarm; prematurely rotating a *working* token costs credibility (slangpy#1167 → slang#13169, 2026-09-18: slangpy-triager and slangpy-fixer both reported it, the alarm was raised, then retracted once `gh api` filed the issue and a gateway `curl` posted a comment). Have the coworker retry via `gh api`/gateway, confirm with a cheap authenticated read (`github_get_issue`, or check the artifact went live), and escalate only if an authenticated `gh api` call itself returns 401/403 ([verify first](../learnings/1789716532319-gh-token-invalid-is-usually-cosmetic-verify-before.md)).

**Neither working reads nor `.permissions` measure write access.** A public repo serves reads like `gh issue view` even with all-false permissions ([#13298 re-verification](../learnings/1790629871805-shader-slang-slang-13298-confirmed-merge-group-onl.md)). `gh api repos/<owner>/<repo> --jq .permissions` reports the token's **classic collaborator** view (push/triage/admin), not the installation's: on 2026-10-01 it read all-false on slang and slangpy while `gh api .../issues -X POST` succeeded at once. So `.permissions.push` can gate a code push, but all-false does not mean "cannot post"; `repos/<o>/<r>/installation` usually 404s for an installation token ([all-false](../learnings/1790880519216-gh-api-repos-o-r-permissions-can-read-all-false-wh.md)).

**Never probe issue-write by POSTing an issue**: it has no dry-run. On slangpy#1200 a coworker checking access before filing a CI-flake report (#1201) created a public empty issue "test" under `nv-slang-bot[bot]`; it had to be retitled "[ACCIDENTAL TEST — SAFE TO CLOSE]" for a maintainer (closing is operator-gated), and its `issue_opened` webhook woke the Orchestrator. Make the real call and check its exit status and URL; a truly needed write test runs on a sandbox repo you own, never `shader-slang/*` ([never probe](../learnings/1790880567281-never-probe-github-issue-write-access-by-posting-a.md)). Cross-repo escalations (e.g. slangpy → shader-slang/slang) still route through the parent/orchestrator regardless of local write capability.

## Issue Assignees — Create, Then POST /assignees

The bot can set issue assignees: on 2026-10-23 it filed slang#13892 and assigned jkwak-work, and on 10-28, asked on PR #13908 to "create a new issue ... and assign it to me", it ran `gh issue create` (no `--assignee`) then `gh issue edit 13972 -R shader-slang/slang --add-assignee jkwak-work`, confirmed by `gh issue view --json assignees`. This corrects the 2026-06-25 "Must have admin rights" 403 (#11751) recorded on [GitHub Auth and Operations in Agent Containers](agent-infra-github-auth-operations.md). Steps:
1. Pre-check: `gh api repos/shader-slang/slang/assignees/<login> -i` returns 204 when the user is assignable.
2. Create without assignees: `gh api repos/shader-slang/slang/issues -X POST --input req.json`.
3. Assign separately: `gh api repos/shader-slang/slang/issues/<N>/assignees -X POST -f 'assignees[]=<login>'` (or `gh issue edit <N> --add-assignee <login>`).
4. Verify with a GET of `.assignees`; GitHub can silently drop a rejected assignee.

Separate calls mean a failed assign loses only the assignment, never invites a retried create that duplicates a public issue. Because the June 403 and the October successes disagree, keep two reviewed replies ("assigned" / "please self-assign") and post the one the read-back supports. This covers issues a maintainer asks for; the operator ban on bot-set assignees and reviewers on bot PRs still applies ([10-23](../learnings/1792776424407-nv-slang-bot-can-set-issue-assignees-2026-10-23-cr.md), [10-28](../learnings/1793197504021-nv-slang-bot-can-assign-issues-2026-10-28-create-f.md)). `gate-critique-on-deliver.sh` blocks even a read-only `gh api repos/O/R/pulls/...` GET as "PR creation": read PRs with `mcp__slang-mcp__github_get_pull_request` or GraphQL `pullRequest{reviewThreads}`, and reply in a review thread with GraphQL `addPullRequestReviewThreadReply` (the gate is on [host facts and the critique gate](agent-b-host-facts-and-critique-gate.md)).

## Human-Cred Merge ≠ Bot Write Recovery

During a bot `actions:write` outage (OneCLI GitHub disconnect / gateway 403), a PR flipping to MERGED proves nothing: a maintainer can merge on their own creds while the bot is still 403'd. Confirm recovery with an actual bot write (`gh run rerun --failed` on a genuine flake, exit 0), never from a merge or queue movement ([human merge](../learnings/1784736496164-human-cred-pr-merge-during-actions-write-outage-bo.md)).

## The Empty-List-Looks-Like-Success Trap

An empty `{"issues": [], "total_count": 0}` from a list/search tool (MCP `github_list_issues` / `github_search_issues`, or `gh` under an invalid token) is a successful-looking response, not an error; on shader-slang/slang, which always has open issues, it signals malfunction, never "no new issues". Cross-check with the **unauthenticated REST API**: `curl -s "https://api.github.com/repos/shader-slang/slang/issues?state=open&sort=created&direction=desc&per_page=40"` (drop entries with a `pull_request` key), `.../pulls?state=closed&sort=updated&...` for merged PRs, `.../actions/runs?status=failure&...` for CI failures, and `curl -s https://raw.githubusercontent.com/shader-slang/slang-ci-analytics/main/health_snapshots.jsonl | tail -1` for the CI-health snapshot. Its value is independence from a flaky MCP server ([unauth fallback](../learnings/1784276460761-slang-mcp-degraded-use-unauth-github-rest-fallback.md)).

That unauthenticated Actions list is best-effort: a 09-14 `actions/runs?status=failure&per_page=N` returned only runs dated ≤08-31 (60/hr limit, incomplete ordering/filtering). Never read an old newest-failure date as all-clear; cross-check the `health_snapshots.jsonl` last line (`merge_queue`, `jobs_queued`, `runs_queued`, `hosted_runner_usage`) and the merge-group check runs ([stale unauth list](../learnings/1789373900583-unauthenticated-gh-actions-runs-status-failure-can.md)).

## Contradiction Resolved — the 07-16/07-17 "auth outage" is fixed

The 07-16/07-17 "GitHub gateway 401 split" diagnostic and the earlier `slang-mcp` degraded note came from a **transient migration credential regression, now FIXED**: carry forward no "GitHub auth / actions / GraphQL / git-push is down" or "hold read-only" assumption. Root cause (dashboard-admin, 07-17): `gh` was missing on the newly-migrated host, so the App-token refresh cron silently failed and the token expired hourly; every `actions` and GraphQL call 401'd `Bad credentials`, and the write-path "Must-have-admin-rights" symptom had the same cause, not a privilege problem. Fix: `gh` 2.96 on the host, the cron guarded against a missing dependency, and git-push split into non-overlapping secrets (`/shader-slang/slang*` App token + `/slang-coworkers/<repo>*` USER PAT). Verified 07-17 ~11:47Z: `gh api graphql '{viewer{login}}'` → `nv-slang-bot[bot]`, `actions/runs .total_count` → 40000, `gh run list` and both push targets work. **The read-only hold is LIFTED**: resume CI sweeps, reruns and requeues. Keep the REST-vs-actions-vs-GraphQL split and the empty-list trap as probe methods; for a future 401 cluster re-diagnose (which paths fail? is the refresh cron alive / `gh` present?) rather than assume this outage recurred ([resolved](../learnings/1784288884629-correction-github-gateway-actions-graphql-401-outa.md), [not broken](../learnings/1784288847791-correction-gh-token-gateway-auth-was-not-broken-on.md)). An `Upstream MCP server unavailable` from `slang-mcp` tools is a separate MCP-server problem, unrelated to the fixed credential.
