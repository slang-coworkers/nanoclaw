# Slang Parameter Binding and Layout

## TL;DR
- The `vk::binding` entry-point diagnostic predicate keys off an AST type that must match the binder's layout-kind contract; it misfires on struct-of-resources entry params (#11861 mirrors #11857).
- Single-kind exclusion guards in `slang-parameter-binding` (e.g. `InputAttachmentIndex` falsely reserving descriptor set 0) are correct-but-fragile — reviewers reliably ask for a **shared predicate** covering all non-descriptor-set kinds.
- `validateEntryPoint`/`validateSystemValueSemantic` validates each param's SV in isolation with **no cross-param aggregation** — the shared gap behind several checks. #6319 (exact duplicate) and #11863 (depth-overlap) are complementary, not duplicates.
- A duplicate-SV check must fire for **system values only**; its collision key's **output binding space** is the hard part (classic = empty space, mesh = by CATEGORY, geometry = per-STREAM), with an `inout TriangleStream<T>` double-collection landmine.
- E38052 "VS has no SV_Position output" is an **intentional heuristic false-positive** (VS→GS/tess/mesh is known-legit); `-warnings-disable 38052` is the documented escape hatch.
- The `SV_Target<N>` resource `index` is set in **TWO** places in `slang-parameter-binding.cpp` — patch both.
- GLSL varying layout counts every vector as one Location, so `double3/4` and 64-bit-integer 3/4-vectors (and arrays and matrices of them) get half the Locations Vulkan requires (#13427). Fix `GetVectorLayout` in the GLSL varying rules and, separately, the hull patch-constant IR layout. Until then, users can assign `[[vk::location(N)]]` explicitly, leaving two Locations per wide vector.
- Layout POLICY is written **twice**: `slang-type-layout.cpp` and `slang-ir-layout.cpp` share NO code. SPIR-V layout decorations use the **IR path**, not reflection `IRTypeLayout`. The two are not 1:1, so "just unify them" is capped in value.
- The IR rule `Natural` encodes as the same op as user `ScalarDataLayout`, so a per-target change to scalar rounding also hits natural buffers unless a separate internal op is added. Concrete `sizeof`/`alignof` are target-independent AST constants.
- Natural layout is computed twice too: concrete `sizeof` folds in `ASTNaturalLayoutContext`, generic `sizeof(T)` in IR layout. They disagree on `bool` (1 vs 4 bytes) and, before #13864, on static members, because `AggTypeDecl::getFields()` includes statics (use `MemberFilterStyle::Instance`). Compare `sizeof(S)` with a generic `gsz<S>()`.
- `static_assert` is evaluated on IR after specialization, so it accepts `sizeof(X, Std430DataLayout)` but cannot prove a front-end fold; pin that with a generic value arg (`SizeTag<sizeof(S)>`, E30019 if unfolded).
- **Natural layout already rounds array strides** (`S{double;int}`: size 12, stride 16), so only a nested struct moving later fields tells natural from rounded rules; a `LoadAligned` promise must be a power of two (E41301).
- On CPU/CUDA the varying layout rules ARE the uniform rules, so a global-scope `in`/`out` takes uniform bytes in reflection; the emitted `GlobalParams` must collect it too or every later offset shifts silently. Layout field keys for a global var must be the var itself, not a module-scope load.
- Bitfield packing is decided at semantic check from the linkage options and baked into a precompiled module; the importing session's flags do not change it.
- E31215 (unsized type in a constant buffer) checks only EXPLICIT `ConstantBuffer`/`ParameterBlock` elements, so an unsized `uniform T x[]` at global or entry-point scope lands in the implicit GlobalParams/EntryPointParams with infinite size: the next field gets Offset 0 and SPIR-V fails VUID-04680 (#13530).
- No existing classifier answers "does this element carry ordinary uniform bytes?": the `Opaque` tag fires on any resource field (mixed structs slip through), `isUniformParameterType` accepts pointers, `isOpaqueHandleType` misses `__DynamicResource`/`SubpassInput`, interface elements are existential data, and a generic `T` is decidable only after entry-point specialization.
- `GLSLBufferModifier` has no producer (GLSL `buffer` parses to a `GLSLShaderStorageBuffer<…>` var), so every guard testing it is dead code; ask for a reaching test or its removal.
- A zero-width bitfield becomes the first member of the next backing group; under MSB-first packing its getter reads -1 when the next field is negative.
- Check bitfield layout without a GPU or MSVC: `-target cpp` output plus g++ `__attribute__((ms_struct))` as an MSVC-layout emulation.

Covers `slang-parameter-binding` predicates, entry-point SV validation, varying Locations, the type-layout vs ir-layout POLICY duplication, implicit-uniform-buffer checks, and bitfield packing.

## `vk::binding` Parameter-Binding Predicates: Single-Kind Guards Are Correct-but-Fragile

A cluster of regressions from #11712 sits in `slang-parameter-binding`. The `vk::binding` entry-point diagnostic predicate keys off an AST type that must match the binder's layout-kind contract ([predicate must match binder's layout-kind contract](../learnings/1782864612564-vk-binding-entry-point-diagnostic-predicate-ast-ty.md)), and the same predicate misfires on a struct-of-resources entry param (#11861, mirroring #11857) ([#11861 mirror of #11857](../learnings/1782871594193-slang-11861-vk-binding-on-struct-of-resources-entr.md)). Single-kind exclusion guards — e.g. `InputAttachmentIndex` falsely reserving descriptor set 0, although it lowers to `OpDecorateInputAttachmentIndex` and is not a descriptor set — are correct but fragile; reviewers reliably ask for a shared predicate covering all non-descriptor-set kinds ([single-kind guards are fragile](../learnings/1782879563848-single-kind-exclusion-guards-in-slang-parameter-bi.md)).

## `validateEntryPoint` System-Value Validation: Dedup Keying, VS→GS False Positive, Output Binding Space

The front-end entry-point validator (`validateEntryPoint`/`validateSystemValueSemantic`, `slang-check-shader.cpp`) checks each param's SV semantic in isolation with **no cross-param aggregation**. Two duplicate-detection concerns share this function and neither subsumes the other: #6319 is an **exact duplicate** (same SV name+index+direction on 2+ params), while PR #11863 handles **overlap** (distinct depth-output names lowering to the same builtin). An independent #6319 PR only textually conflicts with #11863's aggregation block and must coordinate the new diagnostic code ([#6319 vs #11863 are complementary](../learnings/1782900707997-slang-6319-dedup-pr-11863-is-related-not-duplicate.md)).

A duplicate-SV diagnostic must fire for **system values only** (post-linking `fixFieldSemanticsOfFlatStruct` legitimately re-indexes overlapping *user* semantics), and the collision key's **output binding space** is the hard part: classic stages use an empty space key, mesh keys by output CATEGORY (not parameter position), and geometry keys by the STREAM PARAMETER. Landmine: `inout TriangleStream<T>` streams get double-collected (the input and output calls both force-resolve to Output) → spurious self-collision unless the InOut branch skips output-only-by-type params ([output-binding-space keying + inout-stream hazard](../learnings/1782911038880-entry-point-duplicate-system-value-check-output-bi.md)).

Separately, the E38052 "vertex shader has no output with SV_Position" warning (PR #10971) is an **intentional heuristic false-positive**: it is gated only on `stage == Vertex` with no pipeline-pairing awareness, its in-code comment names VS→GS/tess/mesh as legitimate-but-undetected, and `-warnings-disable 38052` is the documented escape hatch. E38052 on a VS→GS shader is not a clear bug ([E38052 is an intentional false-positive](../learnings/1782910937014-e38052-vs-missing-sv-position-is-an-intentional-he.md)).

## Varying Locations: the SV_Target Index Is Set in Two Places, and 64-bit Vectors Are Undercounted

When deriving a fragment `SV_Target<N>` output's GLSL/SPIR-V `layout(location=N)` from the render-target index (#11944), note the VarLayout resource `index` is set in **two** places in `slang-parameter-binding.cpp`; patch both, or one path stays stale ([SV_Target fix lives in TWO places](../learnings/1783263604045-sv-target-location-fix-lives-in-two-places-in-slan.md)).

How many Locations a varying consumes is wrong for wide 64-bit vectors (#13427). `DefaultVaryingLayoutRulesImpl::GetVectorLayout` (`slang-type-layout.cpp:1035-1045`) ignores the element type and `GLSLVaryingLayoutRulesImpl` (:1048) inherits it, so every vector counts as one Location. Vulkan requires two for `double3`, `double4`, `int64_t3`, `uint64_t4` (a 64-bit scalar, `double2`, `int64_t2` correctly take one), and arrays and matrices inherit the undercount (`double4x4` gets 4 instead of 8). spirv-val reports 08721 on vertex/fragment inputs and 08722 on outputs, geometry output included; mesh outputs are numbered the same wrong way but not flagged. Overriding `GetVectorLayout` in the GLSL varying rules (>16 bytes → 2 Locations) fixes every front-end shape, changes reflection with it, leaves HLSL identical, and passed 3208/3209 in the test subsets. It does not reach the hull patch-constant OUTPUT path: `createPatchConstantFuncResultTypeLayout` (`slang-ir-glsl-legalize.cpp`) builds its own IR layout with leaf size `fromRaw(1)`, so a front-end-only fix leaves hull and domain disagreeing — layout policy coded twice again. For expected numbers use DXC `-spirv` via the dxcspv harness at `/workspace/agent/scratch-13324`; the local libslang-glslang does not expose `--auto-map-locations` [64-bit varying Location counts](../learnings/1791134194001-vulkan-64-bit-varying-location-counts-slang-glsl-v.md). Until fixed, explicit locations are a user workaround that passes spirv-val on v2026.20: `struct VSOut { [[vk::location(0)]] double3 head; [[vk::location(2)]] float3 after; }`; without them `head` gets Location 0, `after` 1, and spirv-val fails VUID-08722 [explicit vk::location workaround](../learnings/1792427087126-explicit-vk-location-works-around-slang-64-bit-vec.md). That atom's E00100 note on the in-container `build/Release` slangc is outdated: on 2026-10-22 (tree 653bfdeef) it emitted `-target spirv`/`spirv-asm`, reproduced VUID-08722 with `SLANG_RUN_SPIRV_VALIDATION=1`, and validated the workaround, so try it before downloading a release tarball [container Release slangc emits SPIR-V](../learnings/1792659932300-container-release-slangc-now-emits-spir-v-directly.md).

## Layout POLICY Itself Is Written Twice: type-layout vs ir-layout Share No Code

Verified by source read at master `53b76e6d3` (#12316 tech-debt triage): `slang-ir-layout.cpp` does not include `slang-type-layout.h`, nor vice versa, and grepping `getSizeAndAlignment|IRTypeLayoutRules` in `slang-type-layout.cpp` returns zero hits — no shared policy helper exists. The same rules are coded twice: D3D constant-buffer 16-byte straddling (`slang-type-layout.cpp:587-595` `registerSize=16`/`startRegister`/`endRegister` vs `slang-ir-layout.cpp:769-776` `offset/16`/`currentChunk`/`endChunk`); std140 16-byte composite align (`Std140LayoutRulesImpl::BeginStructLayout` :518-524 vs `Std140LayoutRules::alignCompositeElement` :843-848); vec3 special-casing (`GetVectorLayout` :302/416/704/813 vs `getVectorSizeAndAlignment` :811-821/850-860/721-746). They are **not 1:1**, so "just unify them" is capped in value: the front end has 9 `LayoutRulesFamilyImpl` families / 28+ rule structs (`getDefaultLayoutRulesFamilyForTarget` :2949) and also carries resource/register/descriptor-slot usage, unbounded `LayoutSize`, existential slots, matrix layout MODES and target-category remapping; the IR side has 7 bytes-only rule singletons (:640-908: Natural/C/CUDA/ConstantBuffer/Std430/Std140/LLVM) with 3 virtuals (`alignCompositeElement`, `getVectorSizeAndAlignment`, `adjustOffset`). Only the uniform/bytes subset is common.

**Which path a consumer reads decides where a stride/offset bug is fixed.** SPIR-V layout decorations use the **IR path**, not reflection `IRTypeLayout`: member `Offset` via `getOffset(m_targetRequest, IRTypeLayoutRules::get(layoutRuleName), field, &offset)` (`slang-emit-spirv.cpp:7014`), `MatrixStride` :7036-7043, `ArrayStride` :2007/:2032 (emitted :2585, :2806). Other IR-path consumers (call count): emit-llvm 26, emit-vm 25, ir-byte-address-legalize 20, emit-spirv 15, ir-lower-buffer-element-type 12, ir-legalize-varying-params 11, emit-wgsl 8. `IRTypeLayout` (lowered at `_lowerTypeLayoutCommon`, `slang-lower-to-ir.cpp:16023`) feeds reflection plus parameter-binding/legalization. A deliberate divergence NOT to "fix": the IR path does not round struct size up to alignment (no C tail padding, :40-44), so a differential check must whitelist that plus matrix modes and resource kinds. The IR path memo-caches on the type (read `findSizeAndAlignmentDecorationForLayout` :535; write `kIROp_SizeAndAlignmentDecoration` :571-582; field `kIROp_OffsetDecoration` :180-194). Don't propose deleting the IR path: at `RWByteAddressBuffer.Load<T>()` the concrete `T` isn't known where AST layout is computed, and front-end layout runs before IR exists ([layout policy written twice — duplication map](../learnings/1785761211846-slang-layout-policy-is-written-twice-verified-dupl.md)).

**Changing what "scalar layout" means per target hits three traps** (#12714's `-layout-rules-version 202c` rounding, PR #13300):

1. The IR rule `Natural` and user `ScalarDataLayout` share one op: `getOpFromTypeLayoutRuleName(Natural)` returns `kIROp_ScalarBufferLayoutType`, which user `ScalarDataLayout` also lowers to on buffers and `Ptr<T,..,L>`, so a version-aware decoder also rounds non-scalar natural buffers (e.g. `-fvk-use-dx-layout` structured buffers) through their element pointers. PR #13300 adds an internal `NaturalBufferLayoutType` op emitted only on rounding targets, so IR elsewhere stays byte-identical.
2. The DX-layout block in `getTypeLayoutRuleNameForBuffer` returns `Natural` for pointers before the pointer branch is reached, while reflection lays pointees out as scalar; they agreed only because natural == scalar. User pointers and StorageBuffer element pointers both carry `DefaultBufferLayoutType` (not a null layout), so tell them apart by `AddressSpace::UserPointer`.
3. `sizeof`/`alignof` fold to target-independent AST constants (`SizeOfIntVal` in `slang-ast-val.cpp`, `ASTNaturalLayoutContext` in lower-to-ir), so they cannot follow a per-target rule; ByteAddressBuffer `Load<T>` uses natural rules too.

Tooling: `slangc -reflection-json <file>` prints reflection in the REFLECTION-test format; the generated `command-line-slangc-reference.md` has trailing spaces on ~900 lines that CI byte-compares, so don't trim them ([Natural doubles as ScalarDataLayout's op; sizeof target-independent](../learnings/1790635577609-slang-layout-ir-rule-natural-doubles-as-user-scala.md)).

Testing a rounding change needs a type whose layout actually differs. `IRTypeLayoutRules::getNatural()` already gives array stride alignUp(size, align): `S{double x; int y;}` has size 12 but stride 16, so `S[N]` does NOT distinguish natural from rounded. A difference shows only when a nested struct moves later fields — `U{S z; float w;}` (`w`@12 vs @16) or `T{S a; float b[3];}` (stride 24 vs 32). The byte-address aligned-array path (`isWideAccessAligned`) needs `promisedAlignment % (stride*count) == 0`, and E41301 requires a power-of-two promise, so `LoadAligned<U[2]>` with a rounded 48-byte size never takes the typed path; pick a type whose rounded array size is a power of two. Oracle: DXC's HLSL `sizeof(T)` (v1.9.2602, `-HV 2021`) includes struct rounding (`sizeof({S; float})` = 24); DXC runs locally via the `libdxcompiler.so` in `build/Debug/lib` plus headers in `build/_deps/dxc_source-src/include` — a 20-line `IDxcCompiler3` driver suffices ([natural layout already rounds array strides; BAB promises pow2](../learnings/1790769300394-slang-ir-natural-layout-already-rounds-array-strid.md)).

**Natural layout is also computed twice, and concrete and generic `sizeof` disagree.** A concrete `sizeof`/`alignof` folds in the front end through `ASTNaturalLayoutContext::_calcSizeImpl` (callers `SizeOfIntVal`/`AlignOfIntVal::tryFoldOrNull`, `visitSizeOfLikeExpr`). A generic `sizeof(T)`, IR layout and reflection use the lowered IR struct after specialization, as does any struct the AST layout cannot size (a field or static of type `Ptr<T>`, `uintptr_t`, `SamplerState` or its own type). The engines differ in two known ways:

1. **Static members.** `AggTypeDecl::getFields()` (`slang-ast-decl.h:448`) is `getMembersOfType<VarDecl>()` and includes `static` members; the instance-only form is the DeclRef overload `getFields(astBuilder, declRef, MemberFilterStyle::Instance)` (`slang-syntax.h:383`, i.e. `!hasModifier<HLSLStaticModifier>()`). DeepWiki confidently says the opposite; read the source. `_calcSizeImpl` therefore counted statics (#13858); PR #13864 filters them, and since inheritance re-enters the same loop, base structs are fixed too ([AST natural layout counts statics; DeepWiki wrong](../learnings/1792661288757-slang-ast-natural-layout-counts-static-struct-memb.md)). Three other "instance storage" callers had the same bug at 0bd71cd709: `doStructFieldsHaveSemanticImpl` (`slang-check-shader.cpp:1558`; a static makes an entry-point struct param with `SV_DispatchThreadID` count as uniform, E38040), `_typeTransitivelyContainsOpaqueHandleImpl` (`slang-check-decl.cpp:23229`; `Optional<S>` rejected with E30902 when S has a `static SamplerState`) and `_astTypeIncludesDynamicDispatch` (`:18183`; a `ref` accessor rejected with E52012 when S has a static interface-typed member) ([getFields() includes statics — 4 callers](../learnings/1792669589818-aggtypedecl-getfields-includes-static-members-4-fr.md)).
2. **`bool`.** The front end sizes `bool` from `BaseTypeInfo` (`slang-base-type-info.cpp:9`, 1 byte, align 1); IR natural layout uses `BASE(Bool, 4)` (`slang-ir-layout.cpp:129`, not overridden by `NaturalLayoutRules`). So `struct B { bool b; }` has concrete `sizeof` 1 but generic 4 on master (HLSL and CUDA, 0bd71cd709), and any change letting more structs fold in the front end makes bool-field answers inconsistent: #13864 moves `{static S shared; bool flag;}` from 4 to 1. Probe a bool-field variant when reviewing a natural-layout change. Changing the front-end value is not drop-in: `tests/hlsl-intrinsic/size-of/align-of-generic.slang` expects front-end `alignof(bool)` = 1, and the user guide documents `sizeof(bool)` as target-dependent (4 on HLSL/GLSL, 1 on CUDA) ([front-end bool 1 byte, IR natural 4](../learnings/1792687332003-slang-front-end-natural-layout-sizes-bool-as-1-byt.md)).

Oracles: compare `sizeof(S)` against `uint gsz<T>() { return sizeof(T); }` called as `gsz<S>()`; the generic call defers to IR layout, so they disagree whenever the engines diverge. `static_assert(sizeof(X, Std430DataLayout) == N)` works: the natural/scalar-only check at `slang-check-expr.cpp:3010` limits only checker constant folding (array sizes, generic value args), whereas `static_assert` lowers to an IR inst that `checkStaticAssert` (`slang-emit.cpp:2173`) evaluates after specialization, once IR `SizeOf` is folded with the real rules. On #13864 (Release 0118fe2194) `== 8` passed on cpu/vk/cuda/llvm, `== 12` gave E41400 on all four, and `-minimum-slang-optimization` gave no E41402. The same IR fallback means `static_assert` does not prove the front end folded: `struct S { static S shared; float x; }` passes `static_assert(sizeof(S) == 4)`, array sizes and runtime checks on the unpatched build too. Pin the front-end fold with a generic value argument, `SizeTag<sizeof(S)> t; takesSizeTag4(t);` with `void takesSizeTag4(SizeTag<4>)`, which gives E30019 when the fold does not happen ([static_assert is evaluated in IR](../learnings/1792680419848-correction-static-assert-sizeof-x-std430datalayout.md)).

## Global-Scope Varyings: Layout Field Keys and Uniform Bytes on CPU/CUDA (#9078, PR #13467)

A GLSL global `out vec4 f;` used to abort Metal/CPU/CUDA (and experimental SPIR-V) in `introduceExplicitGlobalContext` with "no outer func at use site for global" (#9078). In `lowerTypeLayout` (slang-lower-to-ir.cpp) the struct-field layout key came from `getSimpleVal(ensureDecl(decl))`, which for a `Flavor::Ptr` global var emits a module-scope `load(%f)` used as the key, while `createIRModuleForLayout` keys on `materialize(...).val`, the var itself. The global parameter group's element and offset-element layouts therefore disagreed, and a pass walking only one of them (`collectGlobalUniformParameters`) missed the load. After the key fix the two `structFieldLayout(%var, L)` insts are identical hoistables and dedupe, so a "re-key all uses" loop is defensive only (check with `-dump-ir-before collectGlobalUniformParameters`). Removing the stray loads reorders GLSL/HLSL/WGSL global declarations, which can break order-checking FileCheck tests ([getSimpleVal on a global var emits a module-scope load](../learnings/1791330554022-slang-ir-layout-field-keys-getsimpleval-on-a-globa.md)).

The fix exposes a second disagreement. On CPU and CUDA, `getVaryingInputRules()`/`getVaryingOutputRules()` return the ordinary uniform rules (slang-type-layout.cpp ~2278, ~2545), so a global `in`/`out` (GLSL `out vec4 o;`, or Slang `in uint3 tid : SV_DispatchThreadID;`) gets Uniform bytes in `ScopeLayoutBuilder::_addParameter`, shifting every later global in reflection, resource handles included. If `collectGlobalUniformParameters` skips the varying, the emitted `GlobalParams` uses natural C offsets and silently mismatches reflection. A `COMPARE_COMPUTE(filecheck-buffer=CHECK):-cpu -compute -entry computeMain -source-language glsl -output-using-type` test with `RWStructuredBuffer; out vec4 o; uniform vec4 u;` shows it (reads 0.0 instead of `u`); use `-source-language glsl`, since `-allow-glsl` is deprecated and its warning fails the stderr match. On master these shapes SEGFAULT in Release because `SLANG_ASSERT(globalParam)` is only `SLANG_ASSUME` there ([GLSL global in/out on CPU/CUDA gets uniform bytes](../learnings/1791335346005-glsl-global-in-out-on-cpu-cuda-layout-gives-unifor.md)).

## Unsized Arrays in Implicit Uniform Buffers: the E31215 Gate and Its Classifiers (#13530, PR #13538)

At master f6238cee3 the E31215 check (`slang-check-decl.cpp:3805-3824`) is gated on `getConstantBufferElementType` (`slang-check-conformance.cpp:635`), which matches only an explicit `ConstantBuffer` or `ParameterBlock`. So `uniform float4 x[]` at global scope, or as an entry-point `uniform` param, is never checked: it is packed into the implicit GlobalParams/EntryPointParams with infinite size, the next field lands at Offset 0, reflection reports an "unbounded" offset, and SPIR-V fails VUID-04680 (#13530). DeepWiki wrongly claims E31215 covers GlobalParams ([E31215 skips implicit uniform buffers](../learnings/1791490940298-slang-e31215-unsized-type-in-constant-buffer-skips.md)).

Extending the check needs a predicate for "does this element hold ordinary uniform bytes?", which no existing classifier answers. `isOpaqueHandleType` as the resource exemption misses `__DynamicResource[]` and `SubpassInput[]` (5 tests regress). The proposed replacement `isUniformParameterType(elem) || doesTypeHaveTag(elem, TypeTag::Opaque)` misclassifies both ways:

- `Opaque` is set if ANY field is a resource, so `struct M { Texture2D t; float4 v; }` is exempted while `v` stays in GlobalParams as `M_0 m_0[]` (VUID-04680; DXC "array dimensions must be explicit").
- `isUniformParameterType` returns true for `PtrType`, but `float4* ps[]` is an unsized array of addresses in uniform memory and asserts in SPIR-V emit (`slang-emit-spirv.cpp` ~8953).
- Interface-typed elements are existentials, i.e. ordinary data: unsized `uniform IFoo xs[]` asserts `!isInfinite()` in type layout.
- A generic `T` element is classifiable only after entry-point specialization, where `EntryPoint::_validateSpecializationArgsImpl` holds the specialized DeclRef.

The same PR fixed two crashes in `getTrailingUnsizedArrayElement` (`slang-check-decl.cpp`): a null-deref for a struct whose own members are all static (`struct D : Base { static int k; }` in a cbuffer segfaults) and an infinite loop when the last field has an error type (`struct S { float4 x[]; Undefined y; }` in a cbuffer hangs) ([Opaque tag and isUniformParameterType misclassify](../learnings/1791508227251-slang-unsized-array-classifiers-opaque-tag-and-isu.md)).

Review of #13538 also found a dead guard. `GLSLBufferModifier` (`slang-ast-modifier.h`) is never created: no `_makeParseModifier("buffer", …)` entry or meta-file syntax produces it. GLSL `buffer` goes through `parseGLSLShaderStorageBufferDecl` (`slang-parser.cpp` ~6164), which builds a `GLSLShaderStorageBuffer<…>`-typed variable; `getConstantBufferElementType` already excludes that type and `isUniformParameterType` treats it as a resource. A revert drill removing the PR's `!varDecl->hasModifier<GLSLBufferModifier>()` conjunct passed 378/378 (tests/glsl-intrinsic, tests/glsl, tests/bugs/13306, the PR tests), and the pre-existing checks at `slang-check-decl.cpp:3051` and `slang-lower-to-ir.cpp:12507` are equally unreachable. A new guard on this modifier needs a reaching test, or removal ([GLSLBufferModifier has no producer](../learnings/1791516340522-glslbuffermodifier-has-no-producer-guards-that-tes.md)).

## Bitfields: Packing Is Fixed at Semantic Check and Baked Into Modules

Bitfield offsets are decided at semantic check, not per target. `SemanticsDeclAttributesVisitor::visitStructDecl` (`slang-check-decl.cpp` ~20922) reads the packing rule from the *linkage* option set and stores it in `BitFieldModifier::offset` → `IRBitFieldAccessorDecoration`. So (verified on #13296, where `-msvc-style-bitfield-packing` packs MSB-first although MSVC packs LSB-first) a `.slang-module` built with the flag stays MSB-first when imported into a session without it; an option change or deprecation warning reaches only whoever builds the module. Any new `CompilerOptionName` also needs its own case in `writeCommandLineArgs` (`slang-compiler-options.cpp`), which re-emits options into the SPIR-V/LLVM debug command line and omits an option by default ([bitfield packing baked into modules; gcc ms_struct oracle](../learnings/1790625408306-slang-bitfield-packing-is-baked-into-precompiled-m.md)).

Zero-width fields (`T x : 0`) show how the checker groups backings (`slang-check-decl.cpp` ~21088-21111; #13299 at master d78c8ace9): it closes the current group and adds the zero-width field as the FIRST member of the next, so its type sets the size of the next `$bit_field_backing_N`. In default mode a following bitfield shares that backing; in MSVC mode the field gets an empty backing of its own when the next field's type size differs; a trailing zero-width field, or consecutive ones, each get a whole backing word. No spelling is portable: Slang rejects the unnamed C/C++ form `uint32_t : 0;` with E20001 (`slang-parser.cpp` ~2632-2645), and C/C++ reject named zero-width fields. Under legacy MSB-first packing the zero-width field gets offset == backingWidth, so its getter is `int32_t(backing) >> 31` and reads -1 whenever the next field in the backing is negative; `tests/language-feature/bitfield/msvc-zero-width.slang` uses a positive value and misses this, and LSB-first rules read 0. The checker picks only backing types and bit offsets; byte offsets come later from per-target type layout, so a storage-less alignment barrier has no representation today ([zero-width bitfields; MSB-first signed readback bug](../learnings/1790631718776-slang-zero-width-bitfields-layout-vs-native-and-a-.md)).

**A GPU-free, MSVC-free layout oracle** serves both: compile variants with `-target cpp` (the emitted `struct S_0` backings plus setter masks give the layout; `g++ -I prelude` runs the .cpp). To ask "does Slang match MSVC host layout", compile `struct __attribute__((ms_struct)) S {...}` with g++/clang (gcc's MSVC-layout emulation, not native MSVC), memcpy to bytes, and compare with the Slang masks. The synthesized backing word's initialization rules are on [[wiki/concepts/slang-compiler-frontend-and-checking.md]].
