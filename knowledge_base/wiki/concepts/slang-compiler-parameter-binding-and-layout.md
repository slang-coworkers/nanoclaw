# Slang Parameter Binding and Layout

## TL;DR
- `vk::binding` entry-point predicates must match the binder's layout-kind contract (misfire on struct-of-resources params, #11861/#11857); single-kind exclusion guards are fragile — reviewers ask for one **shared predicate**.
- `validateEntryPoint` checks each SV in isolation (**no cross-param aggregation**); #6319 (exact duplicate) and #11863 (overlap) are complementary. A duplicate-SV key needs the output binding space (classic empty, mesh CATEGORY, geometry STREAM).
- E38052 (VS without SV_Position) is an **intentional false-positive**; `-warnings-disable 38052`. `SV_Target<N>`'s `index` is set in **TWO** places.
- GLSL varying layout gives `double3/4` and 64-bit-int 3/4-vectors one Location instead of two (#13427); fix `GetVectorLayout` AND the hull patch-constant IR layout. Workaround: explicit `[[vk::location(N)]]`.
- Layout POLICY is written **twice**: `slang-type-layout.cpp` and `slang-ir-layout.cpp` share NO code and are not 1:1. SPIR-V layout decorations use the **IR path**, not reflection `IRTypeLayout`.
- `[vk::offset]` is read only by IR layout, so reflection reported the natural offset, and master applied it off-Vulkan too. PR #14108 gates IR layout to `isKhronosTarget`; a reflection-affecting layout attribute needs the same target gate in both engines.
- Each entry point's `uniform` params form their own PushConstant block at Offset 0 (#9643), so stages alias under VK_EXT_descriptor_heap. Share one `[[vk::push_constant]]` struct, or put `[vk::offset]` on a struct param's first field (E31002 on the param itself).
- IR rule `Natural` encodes as the same op as user `ScalarDataLayout`; a per-target scalar change also hits natural buffers unless a separate op is added. Concrete `sizeof`/`alignof` are target-independent AST constants.
- Natural layout is computed twice: concrete `sizeof` in `ASTNaturalLayoutContext`, generic `sizeof(T)` in IR. They disagree on `bool` (1 vs 4) and, before #13864, on statics (`getFields()` includes them; use `MemberFilterStyle::Instance`). Compare `sizeof(S)` with `gsz<S>()`.
- `static_assert` is IR-evaluated after specialization: it accepts `sizeof(X, Std430DataLayout)` but cannot prove a front-end fold; pin that with `SizeTag<sizeof(S)>` (E30019 if unfolded).
- Natural layout already rounds array strides (`S{double;int}`: size 12, stride 16); only a nested struct shifting later fields distinguishes rounded rules. `LoadAligned` promises must be powers of two (E41301).
- On CPU/CUDA varying rules ARE the uniform rules, so a global `in`/`out` takes uniform bytes in reflection; `GlobalParams` must collect it or later offsets shift. A global var's layout field key must be the var, not a module-scope load.
- E31215 checks only EXPLICIT `ConstantBuffer`/`ParameterBlock`, so an unsized `uniform T x[]` in implicit GlobalParams/EntryPointParams gets infinite size and the next field Offset 0 (VUID-04680, #13530).
- No classifier answers "does this element carry uniform bytes?" (`Opaque` tag, `isUniformParameterType`, `isOpaqueHandleType` all misfire; generic `T` decidable only after specialization).
- `GLSLBufferModifier` has no producer; guards testing it are dead code.
- Bitfield packing is fixed at check time and baked into modules; zero-width fields open the next backing (MSB-first getter reads -1). Oracle: `-target cpp` + g++ `ms_struct`.

## `vk::binding` Parameter-Binding Predicates

A cluster of regressions from #11712 sits in `slang-parameter-binding`. The `vk::binding` entry-point diagnostic predicate keys off an AST type that must match the binder's layout-kind contract ([predicate must match binder's layout-kind contract](../learnings/1782864612564-vk-binding-entry-point-diagnostic-predicate-ast-ty.md)); it misfires on a struct-of-resources entry param (#11861, mirroring #11857) ([#11861 mirror of #11857](../learnings/1782871594193-slang-11861-vk-binding-on-struct-of-resources-entr.md)). Single-kind exclusion guards — e.g. `InputAttachmentIndex` falsely reserving set 0, though it lowers to `OpDecorateInputAttachmentIndex` — are correct but fragile; reviewers ask for one predicate covering all non-descriptor-set kinds ([single-kind guards are fragile](../learnings/1782879563848-single-kind-exclusion-guards-in-slang-parameter-bi.md)).

## `validateEntryPoint` System-Value Validation

`validateEntryPoint`/`validateSystemValueSemantic` (`slang-check-shader.cpp`) checks each param's SV semantic in isolation, with no cross-param aggregation. Two duplicate checks share it and neither subsumes the other: #6319 is an **exact duplicate** (same SV name+index+direction on 2+ params); PR #11863 handles **overlap** (distinct depth-output names lowering to one builtin). A #6319 PR only textually conflicts with #11863's aggregation block and must coordinate the diagnostic code ([#6319 vs #11863 are complementary](../learnings/1782900707997-slang-6319-dedup-pr-11863-is-related-not-duplicate.md)).

A duplicate-SV diagnostic fires for **system values only** (post-linking `fixFieldSemanticsOfFlatStruct` legitimately re-indexes overlapping *user* semantics). The hard part is the key's **output binding space**: empty for classic stages, output CATEGORY for mesh (not parameter position), STREAM PARAMETER for geometry. Landmine: `inout TriangleStream<T>` is double-collected (input and output calls both force-resolve to Output), causing a spurious self-collision unless the InOut branch skips output-only-by-type params ([output-binding-space keying + inout-stream hazard](../learnings/1782911038880-entry-point-duplicate-system-value-check-output-bi.md)).

E38052 "vertex shader has no output with SV_Position" (PR #10971) is an **intentional heuristic false-positive**: gated only on `stage == Vertex`, its comment names VS→GS/tess/mesh as legitimate-but-undetected, and `-warnings-disable 38052` is documented. On a VS→GS shader it is not a clear bug ([E38052 is an intentional false-positive](../learnings/1782910937014-e38052-vs-missing-sv-position-is-an-intentional-he.md)).

## Varying Locations: SV_Target Index and 64-bit Vectors

When deriving a fragment `SV_Target<N>` output's `layout(location=N)` from the render-target index (#11944), the VarLayout resource `index` is set in **two** places in `slang-parameter-binding.cpp`; patch both ([SV_Target fix lives in TWO places](../learnings/1783263604045-sv-target-location-fix-lives-in-two-places-in-slan.md)).

Wide 64-bit vectors get too few Locations (#13427). `DefaultVaryingLayoutRulesImpl::GetVectorLayout` (`slang-type-layout.cpp:1035-1045`) ignores the element type and `GLSLVaryingLayoutRulesImpl` (:1048) inherits it, so every vector is one Location. Vulkan needs two for `double3`, `double4`, `int64_t3`, `uint64_t4` (64-bit scalars and 2-vectors take one); arrays and matrices inherit the undercount (`double4x4` gets 4, not 8). spirv-val reports 08721 on inputs and 08722 on outputs (geometry too; mesh outputs are misnumbered but unflagged). Overriding `GetVectorLayout` in the GLSL varying rules (>16 bytes → 2) fixes every front-end shape and reflection, leaves HLSL unchanged and passed 3208/3209 subsets, but not the hull patch-constant OUTPUT path: `createPatchConstantFuncResultTypeLayout` (`slang-ir-glsl-legalize.cpp`) builds its own IR layout with leaf size `fromRaw(1)`, so hull and domain disagree. Oracle: DXC `-spirv` (dxcspv harness, `/workspace/agent/scratch-13324`) [64-bit varying Location counts](../learnings/1791134194001-vulkan-64-bit-varying-location-counts-slang-glsl-v.md). User workaround (spirv-val clean on v2026.20): `struct VSOut { [[vk::location(0)]] double3 head; [[vk::location(2)]] float3 after; }`; without it `after` gets Location 1 and fails VUID-08722 [explicit vk::location workaround](../learnings/1792427087126-explicit-vk-location-works-around-slang-64-bit-vec.md). That atom's E00100 note is outdated: the in-container `build/Release` slangc (653bfdeef) emits SPIR-V, reproduces 08722 and validates the workaround — try it before downloading a release [container Release slangc emits SPIR-V](../learnings/1792659932300-container-release-slangc-now-emits-spir-v-directly.md).

## Layout POLICY Is Written Twice: type-layout vs ir-layout

At `53b76e6d3` (#12316) the two files share no header or policy helper. Rules coded twice include D3D cbuffer 16-byte straddling (`slang-type-layout.cpp:587-595` vs `slang-ir-layout.cpp:769-776`), std140 composite align (`Std140LayoutRulesImpl::BeginStructLayout` vs `Std140LayoutRules::alignCompositeElement`) and vec3 handling (`GetVectorLayout` vs `getVectorSizeAndAlignment`). They are **not 1:1**, so unifying is capped in value: the front end has 9 `LayoutRulesFamilyImpl` families / 28+ rule structs (`getDefaultLayoutRulesFamilyForTarget` :2949) and also tracks resource/register/descriptor slots, unbounded `LayoutSize`, existential slots, matrix layout MODES and target-category remapping; the IR side has 7 bytes-only singletons (:640-908: Natural/C/CUDA/ConstantBuffer/Std430/Std140/LLVM) with 3 virtuals (`alignCompositeElement`, `getVectorSizeAndAlignment`, `adjustOffset`). Only the uniform-bytes subset is common.

**Which path a consumer reads decides where a stride/offset bug is fixed.** SPIR-V layout decorations use the **IR path**: member `Offset` via `getOffset(m_targetRequest, IRTypeLayoutRules::get(layoutRuleName), field, &offset)` (`slang-emit-spirv.cpp:7014`), `MatrixStride` :7036-7043, `ArrayStride` :2007/:2032. Emit-llvm/vm/wgsl and the byte-address, buffer-element and varying legalizers also use it. `IRTypeLayout` (`_lowerTypeLayoutCommon`, `slang-lower-to-ir.cpp:16023`) feeds reflection plus parameter binding/legalization. A deliberate divergence: the IR path does not round struct size up to alignment (no C tail padding, :40-44), so a differential check must whitelist that plus matrix modes and resource kinds. The IR path memo-caches on the type (`kIROp_SizeAndAlignmentDecoration` :571-582, `kIROp_OffsetDecoration` :180-194). The IR path cannot be deleted: at `RWByteAddressBuffer.Load<T>()` the concrete `T` is unknown where AST layout runs, and front-end layout runs before IR exists ([layout policy written twice — duplication map](../learnings/1785761211846-slang-layout-policy-is-written-twice-verified-dupl.md)).

**Changing "scalar layout" per target hits three traps** (#12714's `-layout-rules-version 202c` rounding, PR #13300):

1. `getOpFromTypeLayoutRuleName(Natural)` returns `kIROp_ScalarBufferLayoutType`, the op user `ScalarDataLayout` also lowers to on buffers and `Ptr<T,..,L>`, so a version-aware decoder also rounds non-scalar natural buffers (e.g. `-fvk-use-dx-layout` structured buffers). PR #13300 adds an internal `NaturalBufferLayoutType` emitted only on rounding targets, keeping other IR byte-identical.
2. The DX-layout block in `getTypeLayoutRuleNameForBuffer` returns `Natural` for pointers before the pointer branch, while reflection lays pointees out as scalar; they agreed only because natural == scalar. User and StorageBuffer element pointers both carry `DefaultBufferLayoutType`; distinguish them by `AddressSpace::UserPointer`.
3. `sizeof`/`alignof` fold to target-independent AST constants (`SizeOfIntVal`, `ASTNaturalLayoutContext`), so cannot follow a per-target rule; ByteAddressBuffer `Load<T>` uses natural rules too.

Tooling: `slangc -reflection-json` prints REFLECTION-test format; don't trim trailing spaces in `command-line-slangc-reference.md` (CI byte-compares) ([Natural doubles as ScalarDataLayout's op; sizeof target-independent](../learnings/1790635577609-slang-layout-ir-rule-natural-doubles-as-user-scala.md)).

Testing a rounding change needs a type whose layout differs. `IRTypeLayoutRules::getNatural()` already gives array stride alignUp(size, align): `S{double x; int y;}` is size 12, stride 16, so `S[N]` does not distinguish. Only a nested struct moving later fields does — `U{S z; float w;}` (`w`@12 vs @16) or `T{S a; float b[3];}` (stride 24 vs 32). The aligned-array byte-address path (`isWideAccessAligned`) needs `promisedAlignment % (stride*count) == 0` and E41301 requires a power-of-two promise, so `LoadAligned<U[2]>` (rounded 48 bytes) never takes the typed path; pick a power-of-two rounded size. Oracle: DXC HLSL `sizeof(T)` (v1.9.2602, `-HV 2021`) includes struct rounding (`sizeof({S; float})` = 24); a 20-line `IDxcCompiler3` driver against `build/Debug/lib/libdxcompiler.so` and `build/_deps/dxc_source-src/include` runs it locally ([natural layout already rounds array strides; BAB promises pow2](../learnings/1790769300394-slang-ir-natural-layout-already-rounds-array-strid.md)).

**Natural layout is computed twice, and concrete and generic `sizeof` disagree.** Concrete `sizeof`/`alignof` fold through `ASTNaturalLayoutContext::_calcSizeImpl` (via `SizeOfIntVal`/`AlignOfIntVal::tryFoldOrNull`, `visitSizeOfLikeExpr`). Generic `sizeof(T)`, IR layout and reflection use the lowered IR struct after specialization, as does any struct AST layout cannot size (a field or static of `Ptr<T>`, `uintptr_t`, `SamplerState` or its own type). Two known differences:

1. **Statics.** `AggTypeDecl::getFields()` (`slang-ast-decl.h:448`) is `getMembersOfType<VarDecl>()` and includes `static` members; the instance-only form is `getFields(astBuilder, declRef, MemberFilterStyle::Instance)` (`slang-syntax.h:383`). DeepWiki says the opposite; read the source. `_calcSizeImpl` counted statics (#13858); PR #13864 filters them, fixing base structs too since inheritance re-enters the loop ([AST natural layout counts statics; DeepWiki wrong](../learnings/1792661288757-slang-ast-natural-layout-counts-static-struct-memb.md)). Three other instance-storage callers had the bug at 0bd71cd709: `doStructFieldsHaveSemanticImpl` (`slang-check-shader.cpp:1558`; a static makes an `SV_DispatchThreadID` struct param count as uniform, E38040), `_typeTransitivelyContainsOpaqueHandleImpl` (`slang-check-decl.cpp:23229`; `Optional<S>` gets E30902 when S has a `static SamplerState`) and `_astTypeIncludesDynamicDispatch` (`:18183`; a `ref` accessor gets E52012 when S has a static interface member) ([getFields() includes statics — 4 callers](../learnings/1792669589818-aggtypedecl-getfields-includes-static-members-4-fr.md)).
2. **`bool`.** The front end sizes `bool` from `BaseTypeInfo` (`slang-base-type-info.cpp:9`, 1 byte); IR natural layout uses `BASE(Bool, 4)` (`slang-ir-layout.cpp:129`). So `struct B { bool b; }` has concrete `sizeof` 1 but generic 4 (HLSL and CUDA, 0bd71cd709), and any change letting more structs fold in the front end flips bool-field answers: #13864 moves `{static S shared; bool flag;}` from 4 to 1. Probe a bool variant when reviewing natural-layout changes. Changing the front-end value is not drop-in: `align-of-generic.slang` expects `alignof(bool)` = 1 and the guide calls `sizeof(bool)` target-dependent ([front-end bool 1 byte, IR natural 4](../learnings/1792687332003-slang-front-end-natural-layout-sizes-bool-as-1-byt.md)).

Oracles: compare `sizeof(S)` against `uint gsz<T>() { return sizeof(T); }` called as `gsz<S>()` (IR layout). `static_assert(sizeof(X, Std430DataLayout) == N)` works: the natural/scalar-only check at `slang-check-expr.cpp:3010` limits only checker constant folding, while `static_assert` lowers to an IR inst `checkStaticAssert` (`slang-emit.cpp:2173`) evaluates after IR `SizeOf` folds with real rules (on #13864 `== 8` passed on cpu/vk/cuda/llvm, `== 12` gave E41400). By the same fallback `static_assert` cannot prove the front end folded: `struct S { static S shared; float x; }` passes `static_assert(sizeof(S) == 4)` on the unpatched build. Pin the fold with a generic value argument, `SizeTag<sizeof(S)> t; takesSizeTag4(t);` with `void takesSizeTag4(SizeTag<4>)`, which gives E30019 when unfolded ([static_assert is evaluated in IR](../learnings/1792680419848-correction-static-assert-sizeof-x-std430datalayout.md)).

**`[vk::offset(N)]` is read by the IR engine only.** `VkStructOffsetAttribute` → `IRVkStructOffsetDecoration` is consumed by `IRTypeLayoutRules::calcSizeAndAlignment` (`slang-ir-layout.cpp:161`) and GLSL emit (`slang-emit-glsl.cpp:274`); front-end layout (`ScopeLayoutBuilder`) handles only `packoffset`. So on master 0cea409 `-reflection-json` and the reflection API report the natural offset (often 0) while SPIR-V carries `Offset N`, under std430, C and scalar rules alike ([vk::offset reaches SPIR-V but not reflection](../learnings/1793388961985-vk-offset-reaches-spir-v-but-not-reflection-a-per-.md)). IR layout also applied it on *every* target despite the doc's "no effect on other targets": for `struct S { int a; [vk::offset(16)] int b; }`, HLSL/Metal/CUDA/C++ `ByteAddressBuffer.Load<S>` read `b` at 16 while `ConstantBuffer<S>`/`StructuredBuffer<S>` (native structs) read it at 4, WGSL emitted `@align(16)` against a reflected 4, and `sizeof(S)` folds to 8. PR #14108 (#9643) makes reflection honour it and gates IR layout to `isKhronosTarget`; Khronos output stays byte-identical, multi-target included (the per-rule SizeAndAlignment cache does not leak across targets). Without spirv-dis, `Offset`s are `OpMemberDecorate` (opcode 72) with decoration 35 ([IR vk::offset honoured off-Vulkan](../learnings/1793400225781-ir-layout-vk-offset-was-honoured-off-vulkan-while-.md)). A layout attribute that starts affecting reflection must be gated identically in both engines. A `-vk` COMPARE_COMPUTE test checks reflection-vs-SPIR-V on GPU: render-test writes entry-point `uniform`s at reflection offsets into a block of reflected size (revert drill: wrong reflection reads 3,0,0; too small a size crashes). Gotchas: `//TEST_INPUT:` must start at column 0, and `CHECK: 3` matches inside `type: int32_t` — anchor on the type line, then `CHECK-NEXT` ([layout attributes need one target gate](../learnings/1793397649663-slang-layout-attributes-reflection-and-ir-layout-m.md)).

## Entry-Point Push Constants Alias at Offset 0 (#9643)

Each entry point's `uniform` params become their own `PushConstant` block at `Offset 0` (a vertex `{float2, float2}` takes bytes 0-15, a fragment `DescriptorHandle<Sampler2D>` 0-7). Per-stage push ranges hid this, but VK_EXT_descriptor_heap's `vkCmdPushDataEXT`/`VkPushDataInfoEXT` has only `offset` + `data`, no stageFlags, so stages alias. #9643 has no maintainer design yet (advice: put all push constants in one place). Workarounds, clean under `SLANG_RUN_SPIRV_VALIDATION=1` (positive control: a global push block plus an entry-point `uniform` in one entry point fires VUID-06674):
- one `struct PushData { ...; DescriptorHandle<Sampler2D> tex; }` as `[[vk::push_constant]] ConstantBuffer<PushData> pd;` in both entry points (Offset 0/8/16), or the same `uniform PushData pd` in both ([entry-point push constants alias](../learnings/1793349219262-entry-point-push-constants-all-start-at-offset-0-w.md));
- a struct param whose first field has `[vk::offset]`: `struct FragPC { [vk::offset(8)] uint a; uint b; }; float4 fs(..., uniform FragPC pc)` lands at 8/12. `[vk::offset]` on the param itself is E31002 (gate at `slang-check-modifier.cpp:1541-1544` accepts only struct members; a #9643 comment shows relaxing it works);
- one global `[vk::push_constant]` block per stage (E39033 does not fire).
The last two lose the nested offset in GLSL output, and reflection reports 0 until PR #14108 ([vk::offset reaches SPIR-V but not reflection](../learnings/1793388961985-vk-offset-reaches-spir-v-but-not-reflection-a-per-.md)).

## Global-Scope Varyings: Layout Field Keys and Uniform Bytes on CPU/CUDA (#9078, PR #13467)

A GLSL global `out vec4 f;` aborted Metal/CPU/CUDA in `introduceExplicitGlobalContext` ("no outer func at use site", #9078). In `lowerTypeLayout` the struct-field layout key came from `getSimpleVal(ensureDecl(decl))`, which for a `Flavor::Ptr` global emits a module-scope `load(%f)`, while `createIRModuleForLayout` keys on `materialize(...).val`, the var itself. The global group's element and offset-element layouts disagreed, and `collectGlobalUniformParameters`, walking one of them, missed the load. After the key fix the two `structFieldLayout(%var, L)` insts dedupe as identical hoistables, so a "re-key all uses" loop is only defensive (check with `-dump-ir-before collectGlobalUniformParameters`). Removing the stray loads reorders GLSL/HLSL/WGSL globals, which can break order-checking FileCheck tests ([getSimpleVal on a global var emits a module-scope load](../learnings/1791330554022-slang-ir-layout-field-keys-getsimpleval-on-a-globa.md)).

That fix exposes a second disagreement. On CPU and CUDA, `getVaryingInputRules()`/`getVaryingOutputRules()` return the uniform rules (`slang-type-layout.cpp` ~2278, ~2545), so a global `in`/`out` (GLSL `out vec4 o;`, or Slang `in uint3 tid : SV_DispatchThreadID;`) gets Uniform bytes in `ScopeLayoutBuilder::_addParameter`, shifting every later global in reflection, resource handles included. If `collectGlobalUniformParameters` skips the varying, `GlobalParams` uses natural C offsets and silently mismatches. Repro: `COMPARE_COMPUTE(filecheck-buffer=CHECK):-cpu -compute -entry computeMain -source-language glsl -output-using-type` with `RWStructuredBuffer; out vec4 o; uniform vec4 u;` reads 0.0 instead of `u` (`-allow-glsl` is deprecated and its warning fails the stderr match). On master these shapes SEGFAULT in Release because `SLANG_ASSERT(globalParam)` is only `SLANG_ASSUME` there ([GLSL global in/out on CPU/CUDA gets uniform bytes](../learnings/1791335346005-glsl-global-in-out-on-cpu-cuda-layout-gives-unifor.md)).

## Unsized Arrays in Implicit Uniform Buffers: E31215 and Its Classifiers (#13530, PR #13538)

At master f6238cee3 the E31215 check (`slang-check-decl.cpp:3805-3824`) is gated on `getConstantBufferElementType` (`slang-check-conformance.cpp:635`), which matches only explicit `ConstantBuffer`/`ParameterBlock`. So `uniform float4 x[]` at global scope or as an entry-point param is never checked: it packs into implicit GlobalParams/EntryPointParams with infinite size, the next field lands at Offset 0, reflection reports an "unbounded" offset, and SPIR-V fails VUID-04680. DeepWiki wrongly claims E31215 covers GlobalParams ([E31215 skips implicit uniform buffers](../learnings/1791490940298-slang-e31215-unsized-type-in-constant-buffer-skips.md)).

Extending the check needs a "holds ordinary uniform bytes?" predicate that no classifier provides. `isOpaqueHandleType` as the exemption misses `__DynamicResource[]` and `SubpassInput[]` (5 tests regress). The proposed `isUniformParameterType(elem) || doesTypeHaveTag(elem, TypeTag::Opaque)` misclassifies both ways:

- `Opaque` is set if ANY field is a resource, so `struct M { Texture2D t; float4 v; }` is exempted while `v` stays in GlobalParams as `M_0 m_0[]` (VUID-04680; DXC "array dimensions must be explicit").
- `isUniformParameterType` is true for `PtrType`, but `float4* ps[]` is an unsized array of addresses in uniform memory and asserts in SPIR-V emit (`slang-emit-spirv.cpp` ~8953).
- Interface-typed elements are existentials (ordinary data): unsized `uniform IFoo xs[]` asserts `!isInfinite()`.
- A generic `T` is classifiable only after entry-point specialization (`EntryPoint::_validateSpecializationArgsImpl` holds the specialized DeclRef).

The PR also fixed two crashes in `getTrailingUnsizedArrayElement`: a null-deref when a struct's own members are all static (`struct D : Base { static int k; }` in a cbuffer) and an infinite loop when the last field has an error type (`struct S { float4 x[]; Undefined y; }`) ([Opaque tag and isUniformParameterType misclassify](../learnings/1791508227251-slang-unsized-array-classifiers-opaque-tag-and-isu.md)).

Review of #13538 found a dead guard: `GLSLBufferModifier` (`slang-ast-modifier.h`) is never created — no `_makeParseModifier("buffer", …)` or meta syntax produces it. GLSL `buffer` goes through `parseGLSLShaderStorageBufferDecl` (`slang-parser.cpp` ~6164), building a `GLSLShaderStorageBuffer<…>` variable that `getConstantBufferElementType` already excludes and `isUniformParameterType` treats as a resource. Removing the PR's `hasModifier<GLSLBufferModifier>` conjunct passed 378/378; the older checks at `slang-check-decl.cpp:3051` and `slang-lower-to-ir.cpp:12507` are equally unreachable. A guard on this modifier needs a reaching test, or removal ([GLSLBufferModifier has no producer](../learnings/1791516340522-glslbuffermodifier-has-no-producer-guards-that-tes.md)).

## Bitfields: Packing Is Fixed at Semantic Check and Baked Into Modules

Bitfield offsets are decided at semantic check, not per target. `SemanticsDeclAttributesVisitor::visitStructDecl` (`slang-check-decl.cpp` ~20922) reads the packing rule from the *linkage* options into `BitFieldModifier::offset` → `IRBitFieldAccessorDecoration`. So (verified on #13296, where `-msvc-style-bitfield-packing` packs MSB-first though MSVC packs LSB-first) a `.slang-module` built with the flag stays MSB-first when imported without it; an option change or deprecation warning reaches only the module's builder. Any new `CompilerOptionName` also needs its own case in `writeCommandLineArgs` (`slang-compiler-options.cpp`), which re-emits options into the SPIR-V/LLVM debug command line and omits unknown ones ([bitfield packing baked into modules; gcc ms_struct oracle](../learnings/1790625408306-slang-bitfield-packing-is-baked-into-precompiled-m.md)).

Zero-width fields (`T x : 0`; `slang-check-decl.cpp` ~21088-21111, #13299 at d78c8ace9) close the current group and become the FIRST member of the next, so their type sizes the next `$bit_field_backing_N`. In default mode a following bitfield shares that backing; in MSVC mode the field gets an empty backing when the next field's type size differs; trailing or consecutive zero-width fields each get a whole word. No spelling is portable: Slang rejects unnamed `uint32_t : 0;` with E20001 (`slang-parser.cpp` ~2632-2645), and C/C++ reject named zero-width fields. Under legacy MSB-first packing the field's offset == backingWidth, so its getter is `int32_t(backing) >> 31` and reads -1 when the next field is negative; `tests/language-feature/bitfield/msvc-zero-width.slang` uses a positive value and misses this (LSB-first reads 0). The checker picks only backing types and bit offsets; byte offsets come from per-target layout, so a storage-less alignment barrier is unrepresentable ([zero-width bitfields; MSB-first signed readback bug](../learnings/1790631718776-slang-zero-width-bitfields-layout-vs-native-and-a-.md)).

**GPU-free, MSVC-free layout oracle:** compile variants with `-target cpp` (the emitted `struct S_0` backings and setter masks give the layout; `g++ -I prelude` runs it). For "does Slang match MSVC host layout", compile `struct __attribute__((ms_struct)) S {...}` with g++/clang (an MSVC-layout emulation), memcpy to bytes, and compare with the Slang masks. Backing-word initialization rules are on [[wiki/concepts/slang-compiler-frontend-and-checking.md]].
