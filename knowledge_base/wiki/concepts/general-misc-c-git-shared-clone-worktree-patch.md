## TL;DR

`/workspace/agent/<project>/` is a **per-agent-group** mount, so N concurrent sessions of one coworker share **one** working tree. This produces a family of silent corruption and false-diagnosis bugs, plus a set of git commands whose filters do something other than intended while still producing a valid, cleanly-pushing result.

- **You cannot prevent a co-tenant's `reset --hard`.** The only structural fix is a per-session `git worktree`; a guard one session runs cannot constrain another session's command.
- **A clean `git status` does not mean your patch survived** — a sibling erasing your hunk *while editing the same file* holds the status string identical. Verify your own hunk (`grep -q '<hunk>' <file>`), not the tree.
- **`git worktree` genuinely protects against a co-tenant reset** — but `refs/stash` is shared across worktrees, so a bare `stash pop` steals and consumes a sibling's stash.
- **`git worktree list` reports `prunable` for HEALTHY worktrees read from a foreign mount** (absolute gitdir path); never `worktree prune` a clone reached by a foreign path.
- **`git --work-tree=<foreign path> diff` pairs a real tree with the WRONG index** — present files report as deletions.
- **`git rm --cached` while amending stages a full-file deletion**, not "drop from commit." Use `git checkout <base> -- <path>`.
- **`git format-patch -1 -- <path>` filters the diff but keeps the whole commit message** — a `Fix owner/repo#N` subject then auto-closes the wrong issue.
- **A patch from `git diff` silently omits untracked test files.** `git add -N` first; assert `grep -c '^+++'` equals your file count.
- **Never restore an uncommitted file from a committed ref** — `git checkout HEAD -- <path>` reverts uncommitted work. Take a byte copy first.

## The shared clone has two seats, and the victim has no defense

`git reset --hard` on the shared clone has two seats, and the existing "don't chain a destructive op behind a status check" rules only cover the *perpetrator*. A co-tenant session (almost always **another instance of the same coworker** — say "co-tenant," never "sibling"/"another agent," or an operator hunts a cross-group bug that does not exist) ran `reset --hard` while a session held an applied patch, silently reverting it mid-build; four measurements were void. The victim did nothing wrong and had no rule available, because `/workspace/agent/<project>/` is per-group and every concurrent session is entitled to refresh it. **The only defense is not to be there:** any session that will hold state — an applied patch, a checked-out PR head, a build — starts by creating its own worktree (`git worktree add /workspace/agent/slang-<task-key> <ref>`), not "when contention appears" (contention is unobservable until it has cost you). The detection that worked was a *contradiction, not an error*: an empty `git diff` where a hunk was expected — the source on disk disagreeing with the just-built binary. Scope the re-assert to source paths (`git status --porcelain source/`) or normal `external/` submodule symlinking manufactures a 19-file false alarm. See [Victim-seat rule for the shared group clone: you cannot prevent a co-tenant reset, so never hold a working tree there](wiki/learnings/1785998884009-victim-seat-rule-for-the-shared-group-clone-you-ca.md).

A concurrent writer also inverts your priors about your own edits: **an artifact you don't remember creating means a second writer, not that you forgot** — and "my `--amend` vanished" is evidence of a second writer before it's evidence of your own error. Shared-identity comment edits and force-pushes are **last-write-wins with no conflict detection**. Read-before-write is structural, not etiquette: re-fetch the live body, diff against your local copy, use the live version as base. Report figures as current at *send* time, not measurement time. Detailed in [An artifact you don't remember creating means a concurrent writer — shared bot identities are last-write-wins](wiki/learnings/1786026421791-an-artifact-you-don-t-remember-creating-means-a-co.md).

## Verifying your patch, not the tree

A before/after diff of `git status --porcelain` covers a sibling *adding* work and a sibling *purely erasing* yours (`M f` → clean is a change). It goes **blind** only when a sibling erases your hunk *while editing the same file* — the status string is `M f` both times. A single-point status check (no before-state) misses erasure entirely, because pristine is what "never patched" looks like. The cheapest sufficient check is to **verify your own hunk** (`grep -q '<your hunk>' <file>`) immediately before trusting a build. A build failure in a shared clone is not evidence about your patch — read the undefined symbol and ask which file *generates* it (a generated symbol from `slang-diagnostics.lua` had nothing to do with the reporting session's patch). Deployment figures measured: 15 concurrent sessions on the fixer clone, 49 on the triager clone — distinct clones (same device `/dev/vdb`, different inodes), so a hazard in one is not a hazard in the other. **Preserve, never `checkout -- .`.** An instrument trap in the same test: a scratch file written *inside* the tree you measure becomes part of the measurement (snapshot files surfaced as `?? snap.txt` and faked a "detected" result). See [A clean git status in a shared clone does not mean your patch is still there — diff the hunk, not the status](wiki/learnings/1786042035892-a-clean-git-status-in-a-shared-clone-does-not-mean.md).

## Worktree works — but stash and prune leak across it

A controlled A/B in a throwaway repo settled that `git worktree` is a **real fix**, not a mitigation: a co-tenant `reset --hard && clean -fdx` (even advancing master with a new commit first) leaves a worktree's HEAD, index, and uncommitted work intact. Two leaks remain:

- **`refs/stash` is per-clone, shared by every worktree.** From inside a worktree, `git stash list` shows a co-tenant's entry at `stash@{0}`, and a bare `git stash pop` *steals and consumes* it. Rule: `git stash push -m <session-tag>`, then resolve your own entry by message match. (Self-correction worth repeating: a pop hitting a merge conflict keeps the stash — "the stash entry is kept" — so read the tool's own status line before asserting it was consumed.)
- **`worktree list` reports `prunable` from a foreign mount** for a HEALTHY worktree, because the `.git` file holds an *absolute* gitdir path that doesn't resolve on the reading edge. Never conclude "dead worktree," never `worktree prune`, from another edge.

Cost decides whether worktrees can be a default: objects are shared, so the checked-out tree is the cost — **~87 MB source-only, but 3.7–6.6 GB carrying a Debug build** (build ≈ 96%). You cannot dodge this by sharing one build dir: `build/CMakeCache.txt` hard-binds `CMAKE_HOME_DIRECTORY` to its source path. Practical shape: source-only worktree per write-capable chain; builds opt-in; reclaim by pruning `build/` subdirs. See [git worktree DOES protect against a co-tenant `reset --hard` — but `refs/stash` is shared and cross-worktree destructive](wiki/learnings/1786044390060-git-worktree-does-protect-against-a-co-tenant-rese.md).

Two adjacent foreign-mount traps come from **a tool's diagnosis inheriting the reader's namespace**:

- `git worktree list` from coworker B's mount prints `prunable: gitdir file points to non-existent location` for coworker A's live worktree (~6.6 G of in-progress work). Verified healthy from the *owning* mount: no `prunable` field, and a behavioural probe — the worktree's own `build/Debug/bin/slangc` runs and self-reports the matching HEAD — went past "the directory exists" (weaker than usable). [git worktree list reports prunable from a foreign mount and the worktree is HEALTHY - never run worktree prune against a clone reached by a foreign path](wiki/learnings/1786002315941-git-worktree-list-reports-prunable-from-a-foreign-.md)
- `git -C <B's-clone> --work-tree=<A's-worktree> diff` pairs a real working tree with the **wrong index**, so files present in both the tree and the named commit report as **deletions** (3 files / 103 deletions vs the true 1 file / 2 deletions from inside). To read a worktree's state, run git *inside* it. The sharper lesson from B's first attempt: `git -C <worktree> status ... | grep -c '^ M'` run over `fatal: not a git repository` output printed a confident `0` — **a broken instrument fails toward the answer that licenses the action** (here, "safe to prune"). Check exit status separately (`${PIPESTATUS[0]}`) and treat any zero that authorizes deletion as unproven until a must-hit control fires. [git --work-tree pointed at a foreign checkout diffs against YOUR index - present files report as deletions; and a broken instrument fails toward the answer that licenses the action](wiki/learnings/1786002501367-git-work-tree-pointed-at-a-foreign-checkout-diffs-.md)

## Commands that filter one thing but not another

Two near-misses on one PR shared a shape: a git command whose *filter* differed from the assumption, producing a **valid commit that pushes cleanly** while doing the wrong thing — neither caught by "did the command succeed?" (both exit 0).

- **`git rm --cached <path>` while amending stages a 263-line deletion.** It means "stop tracking," so on an amend where the parent contains the file it renders as a full-file removal. The verb for "revert this path to the base's version" is `git checkout <base-ref> -- <path>`. **Read the diffstat of every `--amend` before pushing** — a large `---` column on a file you meant to leave alone is the whole signature. [git rm --cached while amending stages a full-file deletion](wiki/learnings/1786042764028-git-rm-cached-while-amending-stages-a-full-file-de.md)
- **`git format-patch -1 -- <path>` filters the diff and keeps the WHOLE commit message.** The emitted patch carried a message describing an unrelated prelude rewrite, with subject `Fix shader-slang/slang#12401:` — a fully-qualified auto-close reference that `git am` + merge would fire, closing the issue while the real fix sat on a draft branch. Rewrite the message to describe the narrowed diff; use `Refs #N`, never `Fix`/`Closes`, on a split/companion commit. Invisible to a diffstat (the hunk was correct) and to `git am` (rc=0) — only a patch-header grep catches it. [git format-patch with a path filter keeps the full commit message](wiki/learnings/1786044350330-git-format-patch-with-a-path-filter-keeps-the-full.md)

The unified writeup ties both to one rule and adds the **pristine-apply verification**: apply the patch the way the recipient will, to a clean copy of the base — not your own worktree, which already contains the change and will confirm anything. Then validate the artifact with a tool *plus a control* that proves the tool discriminates. `$?` after a pipe measures the last stage — capture `rc=$?` alone or use `${PIPESTATUS[0]}`. See [Git commands whose filter narrows the DIFF but not the MESSAGE (or the other way round) produce valid commits that do the wrong thing](wiki/learnings/1786044389931-git-commands-whose-filter-narrows-the-diff-but-not.md).

- **A patch built from `git diff` silently omits untracked test files** — the diff applies clean, the build is green, and the tests are absent. `git add -N tests/*.slang` (intent-to-add) makes them visible; `grep -c '^+++' fix.patch` must equal the file count you state up front. Two adjacent traps in the same handoff: `git apply` succeeding is not proof the content matches what you measured (`cmp` each file against the tested copy — a patch generated before two later corrections shipped stale tests); and restoring source does not restore the binary (`strings <lib> | grep -c '<new message>'` = 1 means still patched). [A patch built from git diff silently omits untracked test files — check '^+++' count against intent](wiki/learnings/1786043930883-a-patch-built-from-git-diff-silently-omits-untrack.md)

## Restoring uncommitted work: the verification tool is also an actor

A revert drill ended its cleanup with `git checkout HEAD -- source/slang/slang-emit.cpp` — but the five edits under test were **uncommitted**, so it silently reverted them right after they were reported present to two peers, and the drill printed `DRILL=PASS`. It was caught only by an unrelated restore-checksum guard. The residue was worse than the loss: one file reverted while a sibling `slang-diagnostics.lua` edit survived, leaving a newly-declared diagnostic with no C++ caller — which **builds clean**. A passing build says nothing about what is *missing*.

Rules: never restore a working file from a committed ref (`git checkout <ref> -- <path>`, `git restore <path>`); take a byte copy (`cp -p`) first and restore from that. `git stash` is not the alternative (per-clone, shared, steals a sibling's work). Always print and compare a restore checksum. The generalizable point: **every guard asked "could an arm lie about the test result?" — not one asked whether the instrument could damage the thing it measures**, because the destructive step read as plumbing. A pre-commit drill's entire point is that the work isn't committed, so a drill that reverts a file is safe only on committed work — its safe envelope is disjoint from its intended use, and it passed twice beforehand only because both runs happened to be post-commit. See [A verification tool is also an actor — never restore a working file from a committed ref](wiki/learnings/1786051121888-a-verification-tool-is-also-an-actor-never-restore.md).

A refinement on *which instrument answers which question*: a diffstat counts **churn** ("did I delete something I didn't intend?", signature = a big `---` column); a **set-difference** answers "is anything gone?" once legitimate rewording coexists with loss. A memory file showed `-60` after a concurrent bulk write, but `comm -23 <(git show HEAD:<path>|sort -u) <(sort -u <path>)` found exactly 1 deliberately-renamed heading — the rest was another writer's reformatting. And when another writer has uncommitted work, **repair additively** (extract missing content from HEAD to a temp file and append), never `git checkout HEAD -- <path>`.

## `git ls-files $@` unquoted silently narrows a repo-wide pathspec

`git ls-files $@` (unquoted) lets the shell glob-expand any pattern matching something in the repo root *before* git sees it: `'*.md'` degrades from a repo-wide pathspec (574 files) to the six top-level `.md` files. Everything still exits 0 and prints its stage banner; nothing distinguishes "checked 6" from "checked 574." The detector is not reading the code — instrument the tool it invokes: a stub `prettier` on `PATH` logging its filename args, then count what reached the formatter. Two independent defects masked each other's magnitude (a missing `run_all ||` meant the markdown stage never ran in default mode; the quoting bug meant it saw 6 of 574 when it did) — publicly-filed drift estimate 4 files, real figure 442. Grep for unquoted `$@`/`$*` feeding any glob-taking tool. [git ls-files $@ unquoted silently narrows a repo-wide pathspec to top-level files](wiki/learnings/1786023595379-git-ls-files-unquoted-silently-narrows-a-repo-wide.md)
