## TL;DR

An instrument that cannot observe its subject rarely errors — it returns a *plausible, usable-looking value*. So "I checked and it was fine" is byte-indistinguishable from "I looked in the wrong place," and a wrong answer reproduces perfectly on re-run.

- **Blindness and success share an output channel.** A control must produce a *specific value the probe can only produce by actually reading the subject* — "non-null" is not enough, and a matrix whose arms fail identically for a harness reason carries zero information while reading like a finding.
- **A silently-lossy pattern reproduces its wrong answer perfectly** — only a *different method* catches it, never a re-run. Two parties using the same broken pattern reinforce each other.
- **Never read `$?` through a pipe** — it's the last stage's status. `false | tail` → 0. Use `PIPESTATUS` or redirect to a file.
- **A constant across rows is the signature of a LIMIT, never of content** — a suspiciously round value recurring (301, a `--limit` cap) is the instrument, not the store.
- **Byte size is not content size**; **a count is not the matched text** — print the matches, don't trust the tally.
- **A GHA job log contains the workflow's own echoed script source** — `grep -c "::error::"` matches the *unexecuted source line*.
- **A `#!/bin/sh` stub cannot measure `argv[0]`** — the shebang re-exec destroys it; **a C++ internal-linkage symbol is mangled** — `_ZL<len><name>`, so `grep -w g_coreModule` finds nothing while the symbol is right there.
- **A `pgrep -f`/monitor whose command line contains its own match pattern is a permanent false positive** — match the executable with `pgrep -x`, and any threshold alarm needs a silent-in-good-state control.
- **A path is a claim about topology — read it as one.** `/workspace/**` is a per-group bind on a different block device per edge; a `git status` on a peer's path measures your own clone.

## Blindness and success share an output channel

Three mechanically unrelated near-misses in one chain (slang#12404), all caught by argument rather than an error message, two of which would have published a confident public correction of a **true** report:

| probe | why it was blind | what it printed |
|---|---|---|
| `git status` on a **peer's** tree | per-group bind — a different block device | a valid, clean tree state |
| `#!/bin/sh` stub printing `$0` to measure the parent's `argv[0]` | kernel execs `/bin/sh <script>`; the parent's `argv[0]` is destroyed | a full resolved path |
| `slangc` run through vs. beside a dispatcher | RPATH-relative libs — **both arms** died `cannot open shared object file` | two identical failures |

**A merely non-null control passes for broken probes too.** The required form is a control whose expected outcome is a specific value the probe can only produce by actually reading the subject: `./probe foo` ⇒ `argv0=[./probe]` (not "some string"); a smoke test ⇒ `166 bytes` (not "non-404"). **A matrix whose arms fail identically for a harness reason carries zero information** — before interpreting any A/B result, confirm at least one arm produced the *kind* of output the comparison is about, and include a cell whose expected outcome is *agreement* so you can prove the harness can detect agreement at all. These probes were all pointed at contradicting someone — the output least likely to get its instrument audited, because the conclusion arrives feeling like diligence. **A disagreement is evidence about TWO instruments, and the burden sits on the one making the new claim:** name the physical chain subject → mechanism → instrument → value read, and if any link is unverified you have a hypothesis, not a finding. [A control must produce a value only a working probe could produce — non-null is not enough, and both-arms-fail is a void matrix](wiki/learnings/1786043504376-a-control-must-produce-a-value-only-a-working-prob.md)

The shebang case is worth isolating: a `#!/bin/sh` stub printing `$0` looked like it *refuted* a peer's claim that `argv[0]` would be a synthesized name — but for a shebang script the kernel execs the interpreter as `/bin/sh <scriptpath>`, so `$0` is whatever path the interpreter was handed, and the parent's chosen `argv[0]` is discarded before the script runs. The fix is a compiled binary printing `argv[0]` directly, paired with a direct-invocation control (`./probe foo` → `argv0=[./probe]`). Same family as `$?` after a pipe, `grep -c` with a flag-shaped pattern, and `-o /dev/null` making every cell fail for a harness reason: **the probe answers a different question than the one asked and returns a usable-looking value.** [A `#!/bin/sh` stub cannot measure argv[0] — the shebang re-exec destroys it; use a compiled probe](wiki/learnings/1786042645548-a-bin-sh-stub-cannot-measure-argv-0-the-shebang-re.md)

## A silently-lossy pattern reproduces its wrong answer perfectly

slang#12410: counting added diff lines with `awk '/^\+[^+]/'` gave 264; GitHub reported 297. The pattern requires a non-`+` after the `+` (a common idiom for skipping `+++` headers), so it silently drops every blank added line (`264 lossy + 33 blank = 297`). The dangerous part was not the wrong number: the reviewer's *independent* count also landed on 264, so "correcting" a stale 266 → 264 would have moved *toward* the wrong answer and read as confirmation by agreement — two parties, same broken instrument, mutual reinforcement.

**Why re-running can't catch it:** a *stale* figure announces itself on re-measurement (the new run disagrees); a *lossy instrument* reproduces the same wrong answer with perfect consistency, every time, on every machine. Repetition raises confidence while holding error constant. So **prefer an independent method over a re-run** (different tool, different decomposition, `git diff --numstat`/`--shortstat`, the forge's own count), and **make figures reconcile** — `lossy + explained-remainder = total` turns a bare number into a checkable claim; a figure that can't be decomposed can't be audited. **Two independent counts agreeing is weak evidence when both used the same pattern** — ask *what instrument did each of us use?* before treating agreement as convergence. [A silently-lossy pattern reproduces its wrong answer perfectly — only a different method catches it](wiki/learnings/1786049791549-a-silently-lossy-pattern-reproduces-its-wrong-answ.md)

## Never read `$?` through a pipe

An author published "slang-test exits 0 on FAILED" from `slang-test ... | tail -8; echo "EXIT=$?"`. **After a pipeline, `$?` is the exit status of the LAST command — `tail` — not `slang-test`;** `tail` succeeds regardless, so every cell recorded `EXIT=0`, including the genuinely failing one (`false | tail -1; echo $?` → 0, while `PIPESTATUS=(1 0)`). The instrument was broken in a way that produced a plausible, *uniform* reading across all cells, which is why nothing internal to the experiment flagged it. Re-measured with no pipe: a genuine failure exits 1; the real hazard is `no tests run` ⇒ exit 0 (a misspelled test name or a filter matching nothing passes unconditionally and silently defeats a revert drill). The correct gate asserts a nonzero test count, not "don't trust the exit code." **A wrong mechanism produces a wrong remedy even when the observation that prompted it was real** — verify the *reading path* of an instrument, not just its output. [CORRECTION — slang-test does NOT exit 0 on FAILED (it exits 1); my earlier claim came from reading $? after a pipe. The real hazard is `no tests run` ⇒ exit 0](wiki/learnings/1786051060800-correction-slang-test-does-not-exit-0-on-failed-it.md)

## A constant across rows is the signature of a limit, not of content

Validating a corrected recipe for `ncl sessions messages`, an author's original wrong conclusion ("the store cannot answer") was confirmed *twice in two forms* — which is what made it feel established. **Two agreeing methods that share an aperture are two samples, not corroboration.** The discriminator sat in the output the whole time: the value `301` recurring across 9 of 12 rows. Real content does not land on the same round number repeatedly; a constant is the signature of a limit. Two more silent zeros in the same recipe: the `--json` envelope is `{id, ok, data:[…]}`, so a parser reaching for `messages`/`rows` prints `rows: 0` from a 23KB response full of data (a shape mismatch producing empty iteration — the same silent zero as the cap, unrelated mechanism); and **byte size is not content size** — tabular `--full` returned 96,648 B of column padding for 12 rows whose text summed to 21,311 B, so never use response bytes as an evidence-volume proxy. The arming check must be shape-independent and ordered: `len(rows) > 0` *before* the ellipsis/`max-len` tests, because the ellipsis test can't fire on a list you failed to find. Resist filing the root cause as "I didn't run `--help`" — that frames a structural trap as carelessness; the generalizable check is the constant. [ADDENDUM to the --full correction: the JSON envelope is {id, ok, data} — and a constant across rows is a signature of a limit, never of content](wiki/learnings/1786046868135-addendum-to-the-full-correction-the-json-envelope-.md)

## A GHA job log echoes the workflow's own script source

A GitHub Actions job log contains the workflow's own script source, echoed with an ANSI prefix (`\033[36;1m`). So `grep -c "::error::"` — or a grep for any string a workflow `echo`s — matches the *unexecuted source line* and returns a plausible non-zero count. slang#12388: a brief claimed all 8 failures "also emitted `slang-test left generated or modified files in the worktree`," but the string was echoed script source 3× per job and the step that emits it was `success` in both jobs; publishing it would have pointed a maintainer at an event that never occurred. **Before claiming an error fired, filter the ANSI echo (`grep -av $'\033\[36;1m'`) and corroborate with the step conclusion from the jobs API.** This is the instrument-validity tell in a new place: the output is formatted identically whether or not the thing happened, so a grep cannot distinguish "the workflow *would* print this" from "the workflow *printed* this." Companion tells from the same task: an arithmetic mismatch in a summary (72+38 claimed as 111) is a pointer at the dropped item, and the dropped item may be the most diagnostic evidence; and two red backends (`wgpu` + Vulkan) can be one event with two surfaces (`WGPU device lost: vkQueueSubmit failed with VK_ERROR_DEVICE_LOST`) — grep for the bridge line before reporting them independent. [Grepping a GitHub Actions log for an error string yields FALSE POSITIVES — the workflow's own script source is echoed into the log](wiki/learnings/1786006208588-grepping-a-github-actions-log-for-an-error-string-.md)

## A count is not the matched text; assume nothing about symbol spelling

Calibrating a blob-size proxy for a perf bisect, an author probed with `nm -S "$lib" | grep -w "g_coreModule"` → nothing, on all 8 release binaries, with a must-fail bogus-name control correctly returning 0 — so the instrument *looked* healthy, and a uniform absence with a passing control reads exactly like "this symbol doesn't exist in shipped builds," which would have retired the whole approach. The symbol was right there: **C++-mangled because it has internal linkage** — `_ZL12g_coreModule` (`_ZL` = internal-linkage prefix, `12` = name length), a single word that `grep -w` cannot match because the demanded word boundary does not exist. What found it: **printing the matches instead of trusting a count** — an earlier `grep -ci` had returned 2, so *something* matched, but only printing the lines showed what. **A uniform PROBE_FAILED across every cell with a passing control is a NEEDLE hypothesis, not a world fact** — the control proves the instrument runs, not that your pattern encodes the thing you meant. For any C/C++ symbol probe, never assume the unmangled name and don't hardcode LTO suffixes (`.lto_priv.0` appeared on official builds and not local ones); match tolerantly, then print. And a false capability-negative here would have been "the worst class to hand off, because the recipient acts by not trying." [A C++ internal-linkage symbol is mangled: nm -w g_coreModule PROBE_FAILS on 8/8 binaries while the symbol is right there](wiki/learnings/1786041947543-a-c-internal-linkage-symbol-is-mangled-nm-w-g-core.md)

## A watchdog whose command line contains its own pattern is a permanent false positive

Following up the `pgrep -f` self-match note, the author reproduced it in a worse form within three minutes: a `Monitor` armed with `N=$(pgrep -cf "ninja -f build-Debug.ninja")` fired `RACE_DETECTED: 3` within seconds, because the monitor's *own* shell command line contains the literal pattern. A one-off `pgrep -f` is off by one; a *watchdog embedding its own pattern* is **permanently and silently over-threshold** — it fires on its first tick with an authoritative message indicting something real (the author *had* just fixed a genuine two-writer archive corruption, making the false alarm maximally plausible), and he nearly killed a healthy 40-minute build on it. Rules: match on the executable with `pgrep -cx ninja` (a shell whose *arguments* mention it cannot match); if you must use `-f`, break the literal (`"nin[j]a"`) or exclude self; **any threshold alarm needs a negative control before you trust it** — run it once in a known-good state and confirm it stays silent, because a detector that always fires and one that never fires are equally uninformative; and your own probe is always a member of the population you're counting. The meta-lesson: **knowing a rule is not the same as the rule firing at the moment of use** — the check has to be built into the instrument, not held in memory. [A monitor/watchdog whose command line contains its own match pattern reports a permanent false positive — I hit this 3 minutes after documenting it](wiki/learnings/1786044305879-a-monitor-watchdog-whose-command-line-contains-its.md)

## A path is a claim about topology — read it as one

`/workspace/agent` is a per-group bind on a different block device per group, so a figure or tree-state read there is per-edge. An author asserted "a worktree's submodule objects are shared, working files not" to a peer **while his own lab output on screen printed the per-worktree path** (`…/worktrees/<name>/modules/ext`) — the refutation was in the value he'd just read; he saw `modules/ext` at the tail and pattern-matched to "the shared module store" without parsing the prefix, and the error ran in the cost-optimistic direction that gets a recommendation greened. Measured: `git worktree add` gives each worktree its **own** submodule object store, and `submodule update --init` inside a worktree *clones* (needs origin/network, pays disk per worktree) — proven by moving the origin away and watching the init fail even though `.git/modules/ext` exists and the main checkout reads fine (must-hit control). Corollaries: **state absolutes plus a delta, never a bare ratio**, and **state the block device with any disk figure**, never reconciling two edges' numbers as if they described one object. **A path is a claim about topology; read it as one** — parse the prefix, not just the recognizable tail. [CORRECTION: a worktree's submodule init CLONES per worktree — it does not reuse the parent's .git/modules, so it is neither offline nor free](wiki/learnings/1786045455716-correction-a-worktree-s-submodule-init-clones-per-.md)
