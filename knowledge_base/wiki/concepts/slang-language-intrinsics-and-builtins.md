# Slang Intrinsics & Builtins

Slang exposes GPU intrinsics and builtin types as core-module declarations (`core.meta.slang`, `hlsl.meta.slang`, `glsl.meta.slang`). Most bugs here come from how they map to each target at emit time and from their capability atoms.

## TL;DR

- **`$TR` in an `__intrinsic_asm` string emits the call's RETURN type; `$T<n>` emits operand n's type and unwraps a texture operand to its element type.** Use `$TR` whenever the result type must be spelled.
- **Dot-form `__intrinsic_asm ".Method"` on a `void` method discards a value-returning target op.** `[mutating]` only makes `this` inout; capture the value explicitly (`this = __hlslSplat(t);`, precedent `__hlslLoadBAB`).
- **The `$P` prefix expander switches on `argType->getOp()` and has no vector case**, so a generic `min`/`max` specialized on a vector (or matrix) hits `default: SLANG_UNEXPECTED` (E99997); concrete overloads work via `VECTOR_MAP_BINARY`.
- **A `default:`-arm diagnostic catches only element types with NO prefix**; prefixed vector element types lacking a vector prelude helper (`intptr_t`, `int16_t`) slip through to "undeclared identifier".
- **Builtin vector/matrix types ARE `DeclRefType<StructDecl>`**, so init-list coercion goes through `createInvokeExprForExplicitCtor`; its viability must not depend on `outExpr` (`canCoerce` probes with null).
- **`float4(float2 xy, 1.f)` does NOT tail-pad to `(x,y,1,0)`**; the scalar splats to `float2(1,1)` giving `(x,y,1,1)`. The semantics-preserving rewrite is `float4(xy, 1.f, 1.f)`.
- **`|`/`&`/`^` work on `[Flags]` enums (via `ILogical`) but `|=`/`&=`/`^=` do not** (table constrained on `__BuiltinLogicalType`). Add generic compound operators over `T : ILogical` with `[OverloadRank(-10)]`.
- **The builtin-operator fast path shadows a user operator on builtin operands; the maintainer wants that to be an ERROR**, not honored.
- **When a check must mirror another site, SHARE the predicate** rather than re-implementing it with a `// matches X` comment; harden it with explicit cases plus `SLANG_UNEXPECTED`.
- **`static_assert` is a builtin intrinsic function, valid only inside a function body**; at global scope any `ident(...)` mis-parses as a declaration.
- **A gather offset must branch on CONSTNESS**: `ConstOffset` for compile-time constants, `Offset`+`ImageGatherExtended` for runtime. A negated constant folds to a constant, so never assert `Offset`+capability for it.
- **A `groupshared T[N]` PARAMETER lowered by-value loses TGSM on DXIL** (per-thread `alloca`, no `addrspace(3)`). Fix at the parameter-lowering producer (`BorrowInOut`), not address-space recovery; detect GPU-free with `slangc -target dxil-asm`.
- **Only the (GroupShared, parameter) arm of the variable-pointers signature walk is a fail-without-fix test**; document why other arms are untested instead of adding passing tests.
- **An instantiation-dependent capability cannot be a static `[require]`**; gate `__requireTargetExtension(...)` on the generic at emit time and keep a non-extension base atom in `[require]` (precedent `GetDimensions`).
- **E41012 for a `[require]` ATTRIBUTE comes from the AST check in `slang-check-shader.cpp`, not the IR `LateRequireCapability` pass** (which handles only the `__requireCapability` statement).
- **When changing a capability atom on a texture method, also audit the `glsl.meta.slang` `texelFetch` wrappers**, which carry their own `[require]`.
- **Renaming a shared capability atom is not behavior-neutral: ADD a new atom and RE-POINT.** Atom names are user-exposed; a new public alias needs `///` docs and a doc regen.
- **The `GL_EXT_texture_shadow_lod` BIAS boundary is narrower than the explicit-LOD boundary**; do not reuse the LOD shape list for bias forms.
- **Derive a family's latest-version atom with `getElements()[count-2]`**; `-1` is the stage atom. Internal capability predicates lack `SLANG_API`, so test them through `.slang` behavior.
- **Statement-level `__requireCapability` and compound `alias` capabilities already exist; there is no generic `IRRequireTargetCapability` op**, and generic-parameter-dependent `[require]` is unsupported. A capability RFC under owner debate is not fix-eligible.
- **On CPU/LLVM, `half` is always the fallback `struct half` with only `explicit operator float()`**, so `(int8_t)half` fails. Add explicit scalar conversion operators; do not switch to native `_Float16`.

## `__intrinsic_asm` markers and dot-form methods

The marker `$TR` emits the call's return type (`m_callInst->getDataType()`), while `$T<n>` emits operand n's type and unwraps an `IRTextureType` operand to its element type, which is the source of texture-intrinsic element-vs-vector bugs. On #12276, `Texture2D<float>.Gather` on CUDA emitted `tex2Dgather<$T0>` = `tex2Dgather<float>` and assigned the scalar into the promised `float4`, causing an NVRTC constructor error. The fix is `tex2Dgather<$TR>`, which yields exactly `vector<T.Element,4>` (precedent: the `llvm bitcast` intrinsic uses `$TR`). Reproduce with `slangc -target ptx` and grep `tex2Dgather<...>` ([$TR marker emits the call return type](../learnings/1785372605179-intrinsic-asm-tr-marker-emits-the-call-return-type.md)).

In `hlsl.meta.slang`, a dot-prefix `__intrinsic_asm ".Method"` on a `[mutating] void` method emits `receiver.Method(args)` as a bare statement and discards its value. On #12059 the HLSL target op `dx::linalg::Matrix::Splat(T)` is value-returning, so `CoopMat.fill(t)` emitted `C_0.Splat(0.0f);`, left the destination uninitialized, and crashed at PSO creation (`clear()` and the scalar `__init` funnel through it). Other targets were correct. The fix follows `__hlslLoadBAB`: an `internal static This` helper wrapping `$TR::Splat($0)`, with the HLSL case `this = __hlslSplat(t);`. Editing `hlsl.meta.slang` needs the core-module-header regen ([HLSL CoopMat fill/Splat dot-form discards value](../learnings/1783725139961-slang-12059-hlsl-coopmat-fill-splat-dot-form-intri.md)).

## The `$P` prefix expander and generic vector/matrix `min`/`max` (#11075, PR #12249)

A generic `T:IFloat`/`IComparable` `min`/`max` specialized on a vector ICEs with E99997 on `-target cpp`/`cuda` (regression from #9593). Concrete `min(float3,float3)` works because the concrete `vector<T,N>` overloads decompose element-wise via `VECTOR_MAP_BINARY`; the generic path emits a single whole-vector `$P_min`, and `case 'P'` in `slang-intrinsic-expand.cpp` switches on `argType->getOp()` with no `kIROp_VectorType` case. A meta.slang-only fix fails; the authorized fix unwraps `IRVectorType` to its element before the switch, adds vector-arity prelude helpers (CPU `template<int N>`, CUDA explicit 2/3/4), and folds the `kIROp_IsVector` peephole on the pre-unwrap type. Gotchas: `slang-embed` follows `#include`, so prelude edits need a fresh worktree to re-embed; an include-order trap forces a `Vector<T,N>` forward-decl at the scalar-intrinsics tail; `__isVector<T>()` works in a COMPARE_COMPUTE test; a draft-PR `gh workflow run ci.yml` shows a benign priority-yield "failure" ([$P prefix + vector min/max fix layer](../learnings/1785207760204-slang-p-prefix-vector-min-max-fix-layer-prelude-em.md)).

The matrix sibling is the same crash through the same path (`extension matrix<T,N,M,L>:IFloat` → `$P_max` → the patched `case 'P'` unwraps only vectors, so a matrix falls to `default:`). It is pre-existing and outside the vector scope, so blocking on it is a scope judgment; three reviewers agreed the `$P` widening rests on an unstated invariant ([matrix sibling crash left by vector fix](../learnings/1785210150352-slang-p-vector-min-max-fix-leaves-matrix-sibling-c.md)). In round 2 the fixer added an `E55215` diagnostic in the `default:` arm, but it catches only element types with no `$P` prefix. Vector element types with a recognized prefix but no vector helper (`intptr_t`→IPTR, `int16_t`→I16, reachable via `vector<intptr_t,N>:IInteger`) slip past into a downstream "undeclared identifier" error, and the PR claim that "IPTR/UPTR are not vector element types" is false. Verdict: APPROVE_WITH_NITS on that exotic residual ([E55215 misses prefix-having element types](../learnings/1785214611295-slang-12249-round-2-e55215-diagnostic-misses-prefi.md)).

## Builtin vector types and constructor resolution

`vector<float,3>` and the other builtin vector/matrix types are `DeclRefType<StructDecl>` (`isDeclRefTypeOf<StructDecl>(float3)` is true). Init-list-to-vector coercion therefore goes through `createInvokeExprForExplicitCtor` (the struct explicit-ctor branch of `_coerceInitializerList`), not `createCtorInvokeExprForAbstractType`. On #11730 the viability `return true` inside `createInvokeExprForExplicitCtor` was nested under `if (outExpr)`; since the overload-resolution `canCoerce` probe passes `outExpr == nullptr`, `{float2, float}` failed as a function argument while succeeding in a declaration. The fix un-nests it so viability is reported independently of `outExpr` ([builtin vector is a DeclRefType&lt;StructDecl&gt;](../learnings/1782733705823-slang-11730-builtin-vector-is-a-declreftype-lt-str.md)).

`float4(float2 barycentrics, 1.f)` compiles today not by tail-padding to `(x,y,1,0)` but by splatting `1.f` to `float2(1,1)` (cost `kConversionCost_ScalarToVector`) and resolving `__init(vector<T,2> xy, vector<T,2> zw)` (`core.meta.slang:2796`) → `(x,y,1,1)`. The slang-rhi#798 fix is `float4(barycentrics, 1.f, 1.f)`, which resolves `__init(vector<T,2> xy, T z, T w)` (`:2784`) to the identical result; `1.f, 1.f` rather than `1.f, 0.f` keeps this ray-tracing test validating the same thing. That one-liner unblocks shadow-BLOCK'd #12141, whose `static_assert(false)` disables the `(vec2,T)`/`(T,vec2)` ctors for `vector<T,4>` and would otherwise turn the 3-component call into E41400 ([float4(float2,1.f) splat vs tail-pad](../learnings/1784281175141-slang-rhi-798-float4-float2-1-f-splat-vs-tail-pad-.md)). The same design-gated divergence is #12093; see [[wiki/concepts/slang-language-generics-and-type-system.md]].

## Builtin operators: fast path, shared predicates, and flag enums

Since #11493, `convertToBuiltinArithmeticOp` (`slang-check-expr.cpp`) rewrites `a OP b` on builtin scalar/vector/matrix operands to a `BuiltinOperatorExpr` before overload resolution, silently dropping a user `operator*(float4x4,float4x4)` (#11877). The maintainer wants such a declaration to be an error rather than honored ([fast path: maintainer wants ERROR not honor](../learnings/1784156401458-slang-11493-fast-path-user-operator-on-builtin-ope.md)).

PR #12162 (`pr: breaking change`) adds that declaration-site diagnostic, which must reject exactly what the fast path shadows. Reviewers made it a high-priority gate that the per-operator element-eligibility ladder (bitwise/shift→int; equality→int|float|bool; logical-not→bool; arithmetic→int|float), written three times (fast-path binary, fast-path unary, the new check), become one shared predicate `isBuiltinOperationKindEligibleForBaseType(BuiltinOperationKind, BaseType)` co-located with `getBuiltinOperationKindFromString` and reachable from all callers (e.g. on `SemanticsVisitor`). Writing "// matches X" is the signal to extract; harden with explicit cases plus `[[noreturn]]` `SLANG_UNEXPECTED`, not a plausible `default:`. The genuinely new branch (the instance-method `this`-receiver operand logic) is where tests are most needed, and extracting into a widely included header means a broad recompile plus regression sweep (4294/4294, behavior-neutral) ([share the mirrored predicate](../learnings/1784627727954-slang-when-a-check-must-mirror-the-fast-path-share.md)).

Binary `|`, `&`, `^` work on `[Flags]` enums because enums conform to `ILogical` and those ops are generic over `T : ILogical`. The compound forms are generated from the `kCompoundBinaryOps` table constrained on `__BuiltinLogicalType`, which enums do not conform to. The fix adds generic `operator|=/&=/^=` over `T : ILogical` in `core.meta.slang` with `[OverloadRank(-10)]` to avoid ambiguity for builtin integers (which conform to both). `a |= b` resolves by overload lookup of a named function, not a checker desugar ([flag-enum compound-assign gap](../learnings/1781621242788-slang-flag-enum-compound-assign-gap-ilogical-vs-bu.md)).

## `static_assert` is function-body only (#13208)

`static_assert(cond, msg)` is a builtin intrinsic function (`core.meta.slang:493`, `__intrinsic_op(kIROp_StaticAssert)`, marked `@experimetal`), not a parser keyword, so it is valid only as an expression-statement inside a function body. At module scope the parser accepts only declarations (`parseDecls`→`ParseDeclWithModifiers`): `static_assert` is consumed as a type name, `(` commits to a function declarator, and the arguments fail the parameter grammar with a misleading `unexpected '(', expected ')'`. Module scope has no decl→expr backtrack (function bodies get one via `parseStatement`), so any global `ident(...)` mis-parses this way; `ident` directly followed by `(` never starts a valid declaration, a usable signal for a tailored diagnostic. Any-scope support is #6136 (register a syntax-decl plus a module-level `kIROp_StaticAssert`; the emit-time checker already recurses the module inst) ([static_assert is function-body only](../learnings/1790019025315-slang-static-assert-is-a-builtin-intrinsic-fn-func.md)).

## Texture gather: `ConstOffset` vs `Offset` (#9382)

`Texture2D.Gather(s, uv, int2(2,1))` emits SPIR-V `Offset` plus `OpCapability ImageGatherExtended` instead of `ConstOffset`. Switching `hlsl.meta.slang` to `ConstOffset` wholesale is unsafe because the GLSL `textureGatherOffset` path can supply a runtime offset through the same intrinsic, producing invalid SPIR-V; the fix branches on constness. Two stale draft PRs exist ([naive ConstOffset fix unsafe](../learnings/1781713033202-slang-9382-gather-constoffset-naive-fix-unsafe-two.md)). A negated constant offset (`-int2(2,1)`) is `Neg(MakeVector(...))` at spirv-legalize but a later pass folds it to `int2(-2,-1)`, so it takes `ConstOffset` while the capability declaration lingers as a pre-existing limitation; a test asserting `Offset`+capability for it would lock in the bug ([negated constant offset folds](../learnings/1781731175811-slang-9382-negated-constant-gather-offset-int2-2-1.md)).

## GroupShared / TGSM on DXIL (#10641)

A `groupshared T scratch[N]` parameter, unlike a global, was lowered by-value (`In`) in `getExplicitlyDeclaredParamPassingMode`, producing a per-thread `alloca` with no `addrspace(3)` in DXIL, so cross-thread sharing silently failed; SPIR-V keeps a real `Workgroup` pointer parameter and was unaffected ([groupshared param lowered by-value](../learnings/1782228288994-groupshared-array-parameter-lowered-by-value-loses.md)). PR #11709 lowers bare `groupshared` params (`HLSLGroupSharedModifier`, no `InModifier`) to `BorrowInOut`, and the HLSL emitter strips the DXC-illegal `groupshared inout` combination except for mesh-shader payload params, which also carry `IRGroupSharedRate` but require `in payload`. Extending `specializeAddressSpace` to DXIL (Approach B) was empirically falsified as the fix layer ([fix is by-reference lowering](../learnings/1782228568362-slang-10641-groupshared-array-param-bug-fix-is-by-.md)). The GPU-free repro is `slangc -target dxil-asm`: zero `addrspace(3)` globals plus `alloca [N x ...]` proves broken codegen, and a plain groupshared global is the positive control ([detect TGSM bugs without a GPU](../learnings/1782216962036-detect-groupshared-tgsm-codegen-bugs-on-dxil-witho.md)).

## Variable pointers (SPIR-V, PR #11521)

`requireFunctionTypeCapabilitiesIfNeeded(IRFuncType*)`, called from `emitFunc`, forwards the result type and each parameter type to `requireVariableBufferCapabilityIfNeeded`, declaring `SPV_KHR_variable_pointers`/`VariablePointers` for a `Workgroup`/`StorageBuffer` pointer that survives only in a non-inlined function's signature. Only (GroupShared, parameter) is a fail-without-fix regression test: the result-type arm is covered by `emitCall` and the `StorageBuffer` arm by `emitGetOffsetPtr`/`emitGetElement`, so extra tests would pass without the fix; document that instead ([only (GroupShared, parameter) is fail-without-fix](../learnings/1780972705906-slang-variable-pointers-signature-walk-fix-only-gr.md)).

## Capability atoms on texture methods and E41012

An instantiation-dependent capability (bare vs. combined sampler) cannot be a static `[require]`, because `[require]` cannot reference a generic `let isCombined`. Model it at emit time with `__requireTargetExtension(...)` gated on the generic and a non-extension base atom (`texture_sm_4_1`) in `[require]`, as `GetDimensions` does. `Texture.Load`'s unconditional `[require(..., texture_sm_4_1_samplerless)]` was out of sync with its already-gated `if(isCombined==0)` GLSL emission, firing a spurious `warning E41012 (ProfileImplicitlyUpgraded)` on combined samplers under an explicit `-profile` even though `GL_EXT_samplerless_texture_functions` was correctly omitted ([spurious E41012 from static require](../learnings/1782889962730-spurious-e41012-profile-upgrade-warning-static-req.md)). That warning originates in the AST check at `slang-check-shader.cpp:2222/2244` (gated on `specificCapabilityRequested || specificProfileRequested`), not the IR `LateRequireCapability` pass, which handles only the `__requireCapability` statement; the AST path cannot observe generic lets like `isCombined` ([E41012 comes from slang-check-shader.cpp](../learnings/1782895560951-e41012-from-a-require-attribute-comes-from-slang-c.md)).

Because the AST check fires for any `[require]`-annotated inlined FuncDecl, editing only `.Load`/subscript in `hlsl.meta.slang` is incomplete: the `texelFetch(...)` wrappers in `glsl.meta.slang` (~:2767–2863) are `[ForceInline]`, carry their own samplerless `[require]`, and several are hardcoded-combined. Run `grep texture_sm_4_1_samplerless source/slang/glsl.meta.slang` and decide explicitly whether the fix extends to them. Dropping an atom from a stdlib `[require]` can also flip generated `-restrictive-capability-check` negative tests red→green; those are "DO NOT EDIT", so fix the generator and regenerate ([also check glsl.meta texelFetch wrappers](../learnings/1782898835005-fixing-a-capability-require-atom-on-a-texture-meth.md)).

## Shadow-texture capability atoms (#12244)

The `GL_EXT_texture_shadow_lod` bias-form boundary is narrower than the explicit-LOD boundary, so the `texture_shadowlod_ext` LOD shape list must not be reused for bias forms. Bias `texture(...)`/`textureOffset(...)` is core GLSL 1.50 for `sampler1D/1DArray/2DShadow` and `samplerCubeShadow`; the extension adds only the `sampler2DArrayShadow`/`samplerCubeArrayShadow` bias variants, and `textureGrad*` on shadow samplers is entirely core. Per DXC hctdb, `SampleCmpLevel` is SM6.7 and `SampleCmpBias`/`SampleCmpGrad` SM6.8 ([bias boundary ≠ LOD boundary](../learnings/1785190567550-gl-ext-texture-shadow-lod-bias-form-boundary-expli.md)). Renaming `texture_shadowlod`→`texture_shadow` is wrong because that atom is shared: besides ~14 `SampleCmp*` `[require]` sites it gates ~57 GLSL `textureLod`/`texture` overloads. The correct move adds `texture_shadow`/`texture_shadowbias` (defined equal to current expansions, pure regrouping) and re-points only the SampleCmp methods. Atom names are user-exposed (in `[require(...)]`, diagnostics and the generated capability-atoms doc), so a new public alias needs `///` doc comments and a doc regen ([rename = re-point](../learnings/1785192528373-samplecmp-capability-atom-rename-re-point-not-rena.md)).

## Capability system internals

To derive a family's latest version atom from a `_*_latest` capdef alias (instead of hard-coding `_sm_6_10`), mirror `getLatestSpirvAtom()`/`getLatestMetalAtom()` exactly: `elements[elements.getCount() - 2]`. A version alias's materialized `CapabilitySet` includes a stage atom, and stage atoms sort above all version atoms in `getElements()`. A "max atom ≥ family anchor" scan grabs the stage atom and widens the family predicate to other families' atoms; a "walk up contiguously until a gap" scan segfaults (`UIntSet::contains` past the populated range). `isSpirvExtensionAtom` and the family range predicates are internal `namespace Slang` functions without `SLANG_API`, so a `slang-unit-test` caller fails to link; test via a `.slang` test ([latest-version atom = count-2](../learnings/1784424625402-slang-capability-latest-version-atom-helper-must-u.md)).

Facts that shape any capability RFC triage (#9210, verified @33f9ed0ce): statement-level requirements already exist as `__requireCapability(...)` → `RequireCapabilityStmt`; there is no generic `IRRequireTargetCapability` op (only GLSL/WGSL-extension decorations plus `LateRequireCapability`), so a general "require this atom for this target" op is net-new; the `[require]` attribute is `RequireCapabilityAttribute`, propagated by `_propagateRequirement` with the caller-⊇-callee check `CapabilitySet::checkCapabilityRequirement`; `CapabilitySet` is a disjunction of conjunctions nested `CapabilityTargetSets → CapabilityStageSets → CapabilityAtomSet`; compound capabilities already exist as `alias` in `slang-capabilities.capdef`. Defects #11631 (`[require]` atoms don't reach the codegen cap set) and #11903 (`implies(atom)` inert on disjunctive caps) corroborate the RFC, and generic-parameter-dependent `[require]` is genuinely unsupported. While subsystem owners are mid-debate, such an issue is not fix-eligible: park it and post a neutral 5-bullet recording both directions, with no fixer dispatch ([capability RFC #9210 facts](../learnings/1783523347890-slang-capability-rfc-9210-current-system-facts-tha.md)).

## CPU/LLVM `half`: no half→integer conversion (#11996)

`SLANG_LLVM` gates out the native `_Float16` block in `prelude/slang-cpp-scalar-intrinsics.h`, so on CPU/LLVM `half` is always the fallback `struct half`, which declares only `explicit operator float()`. The emitter lowers `(int8_t)half` to one `kIROp_CastFloatToInt` and emits `int8_t(halfValue)`, which fails (`cannot convert 'half' to 'int8_t' without a conversion operator`), while `(int8_t)(float)h` compiles: an explicit `operator float()` does not chain through a single cast to a non-float scalar. Approach A adds `explicit` conversion operators (int8/16/32/64 signed and unsigned, double, bool) to the fallback struct, each via `load()`. Native `_Float16` on the LLVM path is rejected (unsupported on some host triples, high blast radius) ([CPU half has only operator float](../learnings/1783511746989-slang-cpu-half-struct-has-only-operator-float-half.md)).
