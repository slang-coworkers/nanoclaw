# GitHub Query Confidence & Cheap Structural Gates

A whole family of `gh`/GitHub queries return a **clean, confident number about the wrong population** — a prefix aggregate, a page, a badge, a misspelled workflow name, a blank stdout on content that exists. The cure is twofold: prefer the field that *states* the cause over one you interpret by elimination, and reach for a cheap structural gate (artifact expiry, run id, timeline) before you read a single log line.

## TL;DR

- **The GitHub search `base:` qualifier matches branch names by PREFIX, not equality** — `base:nv-slang` counts PRs against `nv-slang`, `nv-slang-release`, and every `nv-slang*` branch. Any count from `search/issues?q=…base:X` is a prefix aggregate; pin the exact branch a different way.
- **`review:approved` / `review:required` search is always 0 on a repo with no required-review rule** (they key off `reviewDecision`, null there) — slang returned 0 with approved PRs open. Count `reviews`/`latestReviews` states; `review:none` still works.
- **A low failure count can be a population artifact** — shader-slang Issue Onboard fails only for `Source = Internal` (team-member-filed) issues on the Sprint path (#12982 `iterationId` `ID!`/`String` mismatch), so few red runs ≠ fixed. Split runs by the input class that reaches the failing path.
- **"Nothing tracks this failure" needs merged PRs checked, not only issues** — a test-only PR can fix a nightly red that never got an issue.
- **GraphQL `ref.compare(headRef:)` returns `NOT_FOUND` (null, not 0 behind) for a fork-headed PR** — it resolves same-repo branches only. Use REST `compare/master...<headRefOid>` for fork heads, and label any substitute metric.
- **A search query is not the link graph** — `in:body` cannot see a PR that links an issue via a comment (or a commit message / branch name); use the issue `/timeline` `cross-referenced` events when you need every linking PR.
- **A combined-status `SUCCESS` can mean zero CI ran** — a review bot's status context satisfies the aggregate `/status` badge. "Nothing red" and "CI ran and passed" are different claims; count the runs, don't read the badge.
- **A zero-row `gh run list --workflow <name>.yml` is byte-identical to a dead workflow** — a misspelled name returns empty + rc 0. Verify the workflow file name at source before reading empty as "the workflow stopped running".
- **`gh issue view … --comments` can exit 0 with empty stdout on content that exists** — cross-check REST before reading a blank as "no comments".
- **`gh pr comment` (GraphQL) can fail where `gh api repos/…/issues/N/comments` (REST) succeeds with the same token** — retry the REST issue-comment path before concluding you lack permission.
- **A field that names the cause beats three that bracket it by elimination** — `reviewDecision` returns `REVIEW_REQUIRED` directly with no silent-failure mode (on repos that require reviews; without that rule it is null); elimination is only as sound as your enumeration of blockers. Use elimination to corroborate, not to conclude.
- **Artifact expiry is a cheap, decisive rerun-futility gate** — one `artifacts?per_page=100 --jq 'expired'` call decides rerunnability structurally with no log reading (54% of red PRs in one sweep were past retention).
- **A bounded `updated:A..B` search is not a past-window recount** — it holds only items whose LAST update is in the window. Query `updated:>=A` and filter rows by their own timestamps; `reviewed-by:X` + `updated:` does not prove X acted in the window. One `X-RateLimit-Remaining` reading through OneCLI is not the whole budget (two alternating series seen).
- **On slang an author push auto-dismisses approvals** — read `ReviewDismissedEvent` before reporting "no human review" or a reviewer change of mind; the ask is usually "re-approve", not "find a reviewer".
- **A rollup state is not a CI verdict.** A fork PR with unapproved CI rolls up only ~8 non-CI contexts while the `CI` suite sits at `ACTION_REQUIRED`: SUCCESS there is not green, and FAILURE is usually the `review` check alone. List the non-success contexts before writing "CI red"; filter a "CI failing" label to required checks.
- **A shared environment gate is not a queue** — two runs with identical job tallies are the easiest pair to conflate. Match a run by id/head/event, never by "same 38/39 tally".

## GitHub-query shapes that report a confident number about a set you never queried (2026-08-13 fold)

A cluster of query-instrument traps measured on `shader-slang/slang` and `slang-coworkers/nanoclaw`, each producing a clean answer about the wrong population. **The GitHub search `base:` qualifier matches branch names by PREFIX, not equality** — `base:nv-slang` counted 199 merged PRs against `nv-slang`, `nv-slang-release`, and every other `nv-slang*` branch; any PR count derived from `search/issues?q=…base:X` is a prefix aggregate, so pin the exact branch a different way ([GitHub search base: qualifier matches branch names by PREFIX, not equality](../learnings/1786300758362-github-search-base-qualifier-matches-branch-names-.md)). **The `review:approved` and `review:required` qualifiers return 0 on a repo with no required-review rule.** They key off `reviewDecision`, which GitHub leaves null on every PR unless a branch rule requires a review. shader-slang/slang's master has no such rule (its only ruleset covers deletion, non-fast-forward and Copilot review), so `is:pr is:open review:approved` returned 0 on 2026-10-22 while #13782 had an APPROVED review. Count approvals from `reviews`/`latestReviews` states instead. `review:none` does still work: it matches PRs with no APPROVED or CHANGES_REQUESTED review, so PRs with only bot COMMENTED reviews are included (73 of 100 sampled). When the REST core quota is spent, the same answers come from GraphQL, which has its own budget: `ref.compare(headRef:)` gives behindBy/aheadBy and `repository.rulesets(includeParents:true)` gives the branch rules, while classic `branchProtectionRules` is FORBIDDEN to the integration ([`review:approved` is always 0 without a required-review rule](../learnings/1792659016028-github-search-review-approved-is-always-0-on-repos.md)). **`ref.compare(headRef:)` only resolves branches in the same repository.** In a 2026-10-24 watch-list sweep, `repository{ ref(qualifiedName:"refs/heads/master"){ compare(headRef:"<branch>"){behindBy} } }` returned `NOT_FOUND: Could not resolve head ref '<branch>'` and a null field for the fork-headed PRs #13370, #13181 and #12665, while the bot PRs #12200, #13328 and #12162 (branches in shader-slang/slang) worked. A null here is not "0 behind". For a fork head use REST `GET /repos/shader-slang/slang/compare/master...<headRefOid>` (a bare SHA resolves across forks), or report merges since the last update (`is:pr is:merged merged:>=<updatedAt>` issueCount) under that label; don't mix the two metrics in one "behind" column without saying which is which ([GraphQL compare(headRef:) is NOT_FOUND for fork heads](../learnings/1792830642441-graphql-ref-compare-headref-returns-not-found-for-.md)). **A search query is not the link graph:** `search/issues?q=…N in:body` found 1 PR linking an issue while the issue's `/timeline` `cross-referenced` events found 2 — the second linked via a *PR comment*, invisible to a body-text query (as a link in a commit message or branch name would also be); use the timeline when you need every linking PR ([A search query is not the link graph — in:body cannot see a PR that links via a comment](../learnings/1786311106654-a-search-query-is-not-the-link-graph-in-body-canno.md)). **A combined-status `SUCCESS` can mean zero CI ran:** on #11475 a failure-oriented sweep tagged the PR green (fail=0) while `actions/runs?head_sha=…` and `check-runs` were both `total_count=0` — a review bot's status context satisfied the aggregate `/status` badge; "nothing red" and "CI ran and passed" are different claims, so count the runs, don't read the badge ([A combined-status SUCCESS can mean zero CI ran — review bots satisfy the green check](../learnings/1786320593038-a-combined-status-success-can-mean-zero-ci-ran-rev.md)). **A rollup state is not a CI verdict either.** `statusCheckRollup.state` aggregates whatever contexts exist, required or not. On an external fork PR whose PR CI has not been approved, the rollup covers only about 8 non-CI contexts while the `CI` suite sits at `ACTION_REQUIRED`, so the state comes from those alone, in either direction. It reads SUCCESS right after an author push, and that head is not green ([Watch-list: check ReviewDismissedEvent before calling a carried PR 'no human review'](../learnings/1792917254126-watch-list-check-reviewdismissedevent-before-calli.md)). It reads FAILURE when the single red context is the `review` check and no build or test ran: #13613, #13901, #13905, #13943, #13945 and #13950 on 2026-10-26; maintainer PR #13898 (59 contexts) also read FAILURE from `review` alone ([Fork-PR rollup FAILURE on slang is usually only the `review` check, not red CI](../learnings/1793003524466-fork-pr-rollup-failure-on-slang-is-usually-only-th.md)). So list the non-success contexts before writing "CI red": if `review` is the only one, write "PR CI not approved" (fork) or "all checks pass except `review`". A red `review` is the Claude PR Review harness, which can fail on pure infra (see [bot-review harvest](review-process-f0909b1-bot-review-harvest.md)); to audit a "CI failing" label against required checks only, see [gh CLI status signals](ci-gh-cli-status-and-merge-signals.md). **A zero-row `gh run list --workflow <name>.yml` is byte-identical to a workflow that stopped running** — a misspelled name (`retry-yielded-bot-ci.yml` for the real `ci-retry-yielded-bot.yml`) returns empty + rc 0; verify the workflow file name at source before reading an empty result as "the workflow is dead" ([A zero-row gh query about a misspelled workflow name is an instrument failure, not a dead workflow](../learnings/1786320828994-a-zero-row-gh-query-about-a-misspelled-workflow-na.md)). **`gh issue view … --comments` can exit 0 with empty stdout on an object that has content** — the same issue read fine via REST; cross-check REST before reading a blank as "no comments" ([gh issue view can exit 0 with empty stdout on a read that has content — cross-check with REST before reading a blank as an answer](../learnings/1786308347913-gh-issue-view-can-exit-0-with-empty-stdout-on-a-re.md)). **`gh pr comment` (GraphQL) can fail where `gh api repos/…/issues/N/comments` (REST) succeeds with the same token** — when a GraphQL write 403/errors, retry the REST issue-comment path before concluding you lack permission ([gh pr comment (GraphQL) can fail where REST issues/comments succeeds — same token](../learnings/1786351785011-gh-pr-comment-graphql-can-fail-where-rest-issues-c.md)). **A low failure count can come from a failure that only one population can trigger.** shader-slang's Issue Onboard workflow fails only for issues filed by team members, because only that path sets the Sprint field and hits the #12982 GraphQL `iterationId` `ID!`/`String` mismatch. Bot-filed and external issues onboard cleanly, so a mostly-green run history does not mean the bug is fixed. Before reading the count as a trend, split the runs by filer class ([Actions runs API: URL-encode created>=; Issue Onboard fails only for team-member-filed issues](../learnings/1790842481850-github-actions-runs-api-url-encode-created-filter-.md)). The failing class is the one the workflow labels `Source = Internal`. When `Issue Onboard` fails on the `onboard / onboard` step, grep the job log for `set Source = Internal` and `Type mismatch on variable $iteration and argument iterationId (ID! / String)`. Both present means it is this Sprint-iteration bug, the one fix PR #12982 ("ci: pass Sprint iteration ids as GraphQL String") targets, which has been open and blocked since 09-09. It is not a one-off step error. On 10-05 and 10-06 every Source=Internal onboard failed and every non-Internal onboard succeeded, because non-Internal issues skip the Sprint mutation. The same sweep had a related absence trap. The agentic Nightly Slang Test failures from 10-02 to 10-07 were stale tests, not compiler bugs, and the test-only PR #13454 fixed them without any tracking issue ever being opened. So before reporting that nothing tracks a nightly failure, check merged PRs (a `compare` on master) as well as issues ([Issue Onboard failures on Source=Internal issues = the #12982 GraphQL iteration bug](../learnings/1791361321427-issue-onboard-failures-on-source-internal-issues-t.md)).

**A bounded `updated:A..B` search is not a recount of a past window.** It returns only items whose LAST update falls in A..B, so a PR touched again after B drops out even when it had in-window activity. On 2026-10-25 a bounded review scan missed 3 PRs created in the window and updated 3 min after it, and its control on the previous day's window found 8 reviews where there were 15. Query `updated:>=A` and filter each review/comment row by its own timestamp; `created:`/`closed:` ranges are safe because those fields do not move. The same trap sits in `reviewed-by:X` / `commenter:X` combined with `updated:`: it matches PRs X ever reviewed that were updated in the window, which does not show X acted in the window; use timestamped review/comment rows or REST `/issues/events` by actor. Rate-limit headers mislead a sweep the same way. Through the OneCLI proxy, REST `X-RateLimit-Remaining` alternated between two series in one sweep (about 2000 falling and about 5850), most likely two rotated credentials, so one reading is not the whole budget ([GitHub search updated:A..B is not a past-window recount; OneCLI REST quota shows two buckets](../learnings/1792916903048-github-search-updated-a-b-is-not-a-past-window-rec.md)). And a helper that sleeps when `X-RateLimit-Remaining < 250` must skip that floor for the `search` resource (limit 30/min), or every search call sleeps until reset ([Weekly CMake Options run lasts ~4 h and blinds the CI Health snapshots](../learnings/1792916619171-weekly-cmake-options-run-lasts-4-h-and-blinds-the-.md)).

## Prefer the field that STATES the cause; and cheap structural gates before log-reading (2026-08-13 fold)

**A field that names the cause beats three that bracket it by elimination.** Two PRs showed `mergeable_state=blocked` (a summary string with several possible causes); a peer correctly eliminated conflicts/CI/approvals to leave "review required" — but GraphQL `pullRequest.reviewDecision` returns `REVIEW_REQUIRED` directly, with no silent-failure mode. Elimination is only as sound as your enumeration of blockers and yields a confident wrong answer when one is unenumerated; prefer a conclusion-stating field and use elimination only to corroborate it. Usable-on-slang detail: `baseRef.branchProtectionRule` returns `FORBIDDEN` for the bot token, but `reviewDecision` on the same query is readable — query them separately so the `errors[]` block (which makes `gh` exit 1) doesn't hide the field that came back ([A field that states the cause beats three that bracket it — elimination fails silently on a blocker you didn't enumerate](../learnings/1786292455927-a-field-that-states-the-cause-beats-three-that-bra.md)). **Artifact expiry is a cheap, decisive rerun-futility gate** — before classifying a CI red, one call `actions/runs/<id>/artifacts?per_page=100 --jq 'expired'` decides rerunnability structurally with no log reading; 54% of red PRs in one sweep were past artifact retention and structurally un-rerunnable ([Artifact expiry is a cheap, decisive rerun-futility gate (54% of red PRs)](../learnings/1786313988703-artifact-expiry-is-a-cheap-decisive-rerun-futility.md)). **A shared environment gate is not a queue:** two CI runs with identical job tallies are the easiest pair to conflate — an upstream note claimed clearing run A "also unblocks #12435", but they were two distinct runs (different events, heads, PRs); match a run by id/head/event, never by "same 38/39 tally" ([A shared environment gate is not a queue — and two runs with identical job tallies are the easiest pair to merge into one](../learnings/1786307264759-a-shared-environment-gate-is-not-a-queue-and-two-r.md)).

**A falling approval count, or a PR with "no human review", needs the dismissal events read first.** On shader-slang/slang an author's push auto-dismisses earlier approvals (stale-review dismissal), so an "approved but not merged" count can fall with no reviewer action: it went 9 → 5 on 2026-10-25 when four external approvals (#13663, #13764, #13848, #13855) were dismissed within 30 min by the authors pushing exactly the fixes the reviewers asked for. The maintainer watch list had carried #12665 for about two months as "READY, no reviewer requested", yet its timeline shows an APPROVED review on 08-24 and a `ReviewDismissedEvent` (actor = the pushing author, `previousReviewState` APPROVED) 20 s after the author's 08-25 commit, so the right ask was "rebase + re-approve (same reviewer)", not "find a reviewer". The event states the cause directly: `pullRequest(number:N){timelineItems(itemTypes:[REVIEW_DISMISSED_EVENT,PULL_REQUEST_REVIEW]){nodes{... on ReviewDismissedEvent{createdAt actor{login} previousReviewState review{author{login}}}}}}`, and a `reviews` row in state `DISMISSED` is the same signal. Check it before reporting a reviewer change of mind ([Watch-list: check ReviewDismissedEvent before calling a carried PR 'no human review'](../learnings/1792917254126-watch-list-check-reviewdismissedevent-before-calli.md), [GitHub search updated:A..B is not a past-window recount; OneCLI REST quota shows two buckets](../learnings/1792916903048-github-search-updated-a-b-is-not-a-past-window-rec.md)).
