# Slang Compiler: Descriptor-Heap, DescriptorHandle, Entry-Point Layout, and Debug-Info Lowering

## TL;DR
- **`lowerBitCast` runs only if the module already has a `BitCast`**, so compiler-generated DescriptorHandle casts (AnyValue marshalling, byte-address legalization) ICE only alongside an unrelated user `bit_cast`. A new early-out in `processBitCast` must sit below the E41202 size check, or size-mismatched casts lose their diagnostic and miscompile.
- **Descriptor-heap `[noinline]` texture params: reuse the hoistable heap global**, not parameterize the texture through the noinline boundary.
- **`DescriptorHandle<T>` re-loads on every use**: `shouldDuplicateInstAtUseSite()` hard-codes `CastDescriptorHandleToResource → true`, and the descriptor cast/load ops are NOT `hoistable`. `hoistable=true` is the WRONG lever (module-global GVN, not per-loop LICM); the right levers are relaxing `shouldDuplicateInstAtUseSite` for dominating loop-invariant casts and/or enabling `hoistLoopInvariantInsts`.
- **The reload asymmetry is real: SPIR-V force-duplicates the cast by design; HLSL already reuses via a hoisted local.** #11798 (input syntax) does NOT close #12051. Meta-lesson: EMIT AND GREP before any cross-target codegen claim.
- **Entry-point / varying-parameter / reflection layout fixes belong in the front-end AST BEFORE entry-point layout generation, not a back-end post-link IR rebuild** — a parallel IR layout path is "wrong by construction" (no consistency guarantee against AST layout).
- **Don't hand-roll recursion for link-time type resolution in layout** — the layout walk already re-enters per-node resolution and `Val::resolve()` recurses. The one non-redundant step for `export struct W : I = Impl` is swapping the abstract `witnessTable` for the concrete `witnessVal` before resolving.
- **The `debugArtifactCount == 1` premise ("Direct-SPIR-V is whole-program") holds only for a SINGLE target.** Precise abort trigger: ≥2 `-target`s + ≥2 entry points + no per-target `-o` for the SPIRV target → E99997. Fix by diagnosing the multi-artifact shape gracefully. The count multiplier is entry-point count, not the second target.
- `lowerCombinedTextureSamplers` rewrites layouts only for top-level combined-sampler globals; nested and entry-point samplers lose their bindings on Metal/HLSL/WGSL (#13272). Separately, `getLoweredTypeInfo` lowers ANY texture type, so a plain `Texture2D` is retyped module-wide (#13326); the `legalize-types.cpp:3503` assert has both producers — never dedup on its text.
- IR layout insts are deduplicated and parent-relative: build new layouts and swap the decoration; never `removeAndDeallocate` the old ones — they may be a struct's field layout too.
- Link-time `extern`/`export static const` values reach layout/reflection only when the initializer is a bare int/bool literal; an enum or non-literal initializer gets no `tryFoldIntVal` map entry, so a `Conditional<Resource, cond>` silently loses its bindings while the IR still resolves the value (#13419). Even a resolved extern stays symbolic inside `+`/`-`/`*` (`PolynomialIntVal` has no link-time resolve; only `?:`/`==` resolve), so `[numthreads(V + 4,1,1)]` reflects as `[0,1,1]`.
- Link-time associated-type layout has an export-side gap (#9580, fixed by #12131) and an extern-side gap (#8957/#13276, draft #10877); both come from `lookupExternDeclRefType` checking the `AssocTypeDecl` instead of the lookup source.
- **Matrix loads through SPIR-V *untyped* pointers are spec-correct when the access chain's Base Type is a struct** (rev-4 provenance): Slang's heap-CB emission is sanctioned, so #14541's L40S transpose is an NVIDIA driver bug; spirv-val certifies the producer, never execution semantics.
- **`-embed-downstream-ir` blobs bake only `export` functions, and the globals they reference bake with the MODULE's layout** — a consuming program can hit a dxc "Resource overlap" (#4846); explicit `register()` is the workaround.

## Descriptor-heap [noinline] texture params: reuse the hoistable heap global

Approach-A fix for descriptor-heap `[noinline]` texture params (#11498, root cause of #11496, PR #11502): **reuse the hoistable heap global** rather than parameterizing the texture through the noinline boundary ([1780769595819-approach-a-fix-for-descriptor-heap-noi](../learnings/1780769595819-approach-a-fix-for-descriptor-heap-noinline-textur.md)).

## DescriptorHandle Per-Use Reload (#12051)

`DescriptorHandle<T>` descriptors re-load on every use (a handle sampled in a loop reloads each iteration). Two independent mechanisms: `shouldDuplicateInstAtUseSite()` (`slang-ir-util.cpp:2634`) hard-codes `CastDescriptorHandleToResource -> true`, and the descriptor cast/load ops are NOT `hoistable` in `slang-ir-insts.lua` (so IRBuilder's GVN never collapses repeated loads). But `hoistable=true` is the WRONG lever (module-global GVN, not per-loop LICM); the right levers are relaxing `shouldDuplicateInstAtUseSite` for dominating loop-invariant casts and/or enabling `hoistLoopInvariantInsts` ([slang#12051 DescriptorHandle reloads every use -- root cause](../learnings/1783705209384-slang-12051-descriptorhandle-reloads-every-use-roo.md)). A same-day CORRECTION overturned an earlier "HLSL can't pin" inference: an empirical `slangc -target hlsl` repro showed resource-typed locals ARE storable on HLSL today — hoisting the conversion into a local before the loop emits `ResourceDescriptorHeap[i]` once. So the asymmetry is real (SPIR-V's `CastDescriptorHandleToResource` IS force-duplicated by design; HLSL is not), and #11798 (input-syntax via `UntypedResourceHandle`) does NOT close #12051. Meta-lesson: for any cross-target codegen claim, EMIT AND GREP before asserting — source-path reading establishes the mechanism but not the observable output shape ([CORRECTION #12051: DescriptorHandle reuse ALREADY works on HLSL via a local](../learnings/1783724965975-correction-slang-12051-descriptorhandle-reuse-alre.md)).

## `lowerBitCast` and `DescriptorHandle`: Gating, Generated Casts, and the Size Check (#13633 / PR #13679)

`lowerBitCast` runs only when `requiredLoweringPassSet.bitcast` is set, and that flag is set when the module contains any `BitCast`. Two later passes also create `BitCast`s involving a `DescriptorHandle`: AnyValue marshalling (reinterpret and dynamic dispatch) emits `uintN <-> DH` on CUDA and CPU, and byte-address-buffer legalization emits `u64 <-> DH` on WGSL and Metal. Those generated casts reach `readObject`'s "Unable to generate bit_cast code" ICE only when the shader also contains an unrelated user `bit_cast` that turned the pass on, so a repro needs both. The PR #13679 fix has two parts: a user-cast diagnostic (E41206) before `generateAnyValueMarshallingFunctions` (so every `BitCast` it sees came from source), and in `processBitCast`, leaving a cast with a bare DH on one side to the target's own bit cast. Two traps: do not `SLANG_ASSERT(areResourceTypesBindlessOnTarget)` in that early-out (the WGSL byte-address casts reach it and WGSL is not bindless), and `isResourceType()` also matches arrays of resources, so exempt only a bare operand ([compiler-generated DescriptorHandle BitCasts only ICE when an unrelated user bit_cast exists](../learnings/1792093864763-slang-compiler-generated-descriptorhandle-bitcasts.md)).

Where the new early-out sits matters. In `processBitCast`, the "ignore cases we cannot handle" early returns (resource, pointer-like, sampler, structured buffer) come before the `fromTypeSize.size != toTypeSize.size` → E41202 check. Adding `IRDescriptorHandleType` to that list makes a size-mismatched user cast such as `bit_cast<uint>(DescriptorHandle<Texture2D>)` skip E41202 — it then fails as E99999 on SPIR-V/HLSL and silently reads out of bounds on CUDA, C++, Metal, WGSL and GLSL. Put the size check above the new early return; the compiler-generated casts are size-equal, so they still pass. To catch the regression, probe `bit_cast<uint>(X)` and `bit_cast<uint4>(X)` against master, which gives E41202 on all seven targets [early-return guards in processBitCast must sit below the E41202 size check](../learnings/1792097444426-early-return-guards-in-lowerbitcast-processbitcast.md). How the handle-to-integer cast is lowered on non-bindless targets (`CastDescriptorHandleToUInt2`/`UInt64`) is on [DescriptorHandle emit on bindless and non-bindless targets](slang-backends-descriptor-handle-emit-and-bindless-targets.md).

## Entry-Point Layout Fixes Belong in the Front-End (#9580/#10030)

For entry-point / varying-parameter / reflection *layout* fixes, the resolution must happen at the front-end AST level *before* entry-point layout generation, NOT via a back-end IR post-link layout rebuild, which is "wrong by construction" (a parallel IR layout path has no consistency guarantee against AST-computed core layout). Verified on PR #10030 (fix for #9580): tangent-vector's CHANGES_REQUESTED and csyonghe's comment both reject the IR approach, and the bot's nits were all hardening the *wrong* (back-end) path. Our own triage-9580 had recommended exactly that rejected Approach A; default to a front-end AST resolution step and only propose a back-end IR transform if a maintainer explicitly asks ([Slang entry-point layout fixes must be front-end (AST), not back-end IR rebuild](../learnings/1783710345558-slang-entry-point-layout-fixes-must-be-front-end-a.md)). Implementing that front-end resolution (PR #12131) confirmed two non-obvious mechanics: (1) you do NOT need a bespoke recursive walker over a decl-ref's substructure to resolve link-time-specialized types during layout — the layout walk already re-enters per-node resolution for each nested `DeclRefType` and `Val::resolve()` already recurses generic-app args and witness chains, so a generic-arg walker would be dead code; put the per-node policy in ONE bottleneck routine. (2) For `export struct W : I = Impl`, the concrete conformance `Impl : I` lives in `InheritanceDecl::witnessVal`, SEPARATE from `InheritanceDecl::witnessTable` (the wrapper's own abstract conformance) — plain `Val::resolve()` reads the abstract `witnessTable` and returns the type unchanged (→ opaque layout → crash), so the one non-redundant step is swapping the abstract witness for `witnessVal` before resolving. No existing path reads `witnessVal` on its own, so "just call resolve()" does not fix the bug ([Link-time type resolution in layout: no hand-rolled recursion needed](../learnings/1785467527075-link-time-type-resolution-in-layout-no-hand-rolled.md)).

The link-time case has two distinct gaps. When an entry-point parameter or return type is an associated type looked up through a link-time struct (`X.Assoc`), the **export side** (#9580) has the lookup source in the same module, `export struct X : I = Impl`, and PR #12131's `resolveLinkTimeWrapperMemberType` fixes it. The **extern side** (#8957, #13276) has `extern struct X : I;` with the export in another module, and #12131 skips it; draft PR #10877 adds a `LookupDeclRef` branch to `lookupExternDeclRefType` that resolves the lookup source through `externTypeMap`, verified on master fd923329e. Shared root cause: `lookupExternDeclRefType` (`slang-type-layout.cpp:6589`) checks the extern modifier on `declRef.getDecl()` (the `AssocTypeDecl`) instead of the lookup source, so layout falls into the `AssocTypeDecl` branch and yields a zero-size layout. For a ray-tracing payload that is a silent SPIR-V miscompile: the payload becomes a `Private` variable instead of `IncomingRayPayloadKHR`, and spirv-opt's ADCE empties the body at `-O1`; CUDA reports E99999 and reflection shows `kind: None` with no binding. The one-variable control: the same entry point looked up through the export decl in one module, which #12131 fixes while the two-module extern form stays broken. DeepWiki was wrong twice here: `lookupExternDeclRefType` does not resolve `X.Assoc` via `X`, and `maybeCopyLayoutInformationToParameters` only copies layouts after IR linking (`slang-ir-link.cpp:1075`) [Link-time associated types: extern-side vs export-side lookup are different layout gaps](../learnings/1790573149484-link-time-associated-types-extern-side-vs-export-s.md).

Link-time *values* have a parallel gap. Layout and reflection resolve `extern`/`export static const` values through `ComponentType::tryFoldIntVal` (`slang-linkable.cpp:1259`), which reads a map built from each `varDecl->val`, silently skipping declarations whose `val` is null. `val` is set in two places and both miss common shapes: the header fold (`slang-check-decl.cpp:2782`) runs before the initializer is checked and only for a `BasicExpressionType` (so only a bare literal folds), and the body fallback `_validateCircularVarDefinition` returns null for an enum and, for an extern int or bool, a `DeclRefIntVal` pointing back at the declaration itself. Consider `extern static const Mode m = Mode.On;` (also `= 1 + 0;`, `= ONE;`, `= int(1u);`, `bool b = T;`). Each of these leaves a `Conditional<Resource, cond>` with an empty layout: no binding on any target, an empty struct in reflection, unknown link-time array sizes. The IR side still resolves the value (Off gives E41027), so codegen looks fine while the bindings vanish (#13419, master 6ba151dcf). Widening the :2782 gate to enums alone does not help (the initializer is still unchecked there). A working prototype link-time-folds the CHECKED initializer in `SemanticsDeclBodyVisitor::checkVarDeclCommon` for const extern/export declarations with `isValidCompileTimeConstantType`; its side effect is a doubled E39999 on circular declarations [extern static const link-time folding only works for bare-literal int/bool initializers](../learnings/1790993221985-extern-static-const-link-time-folding-only-works-f.md).

A resolved extern can still vanish inside arithmetic. `tryFoldIntVal` calls `IntVal::linkTimeResolve`, and only `DeclRefIntVal`, `TypeCastIntVal` and `BuiltinOperationIntVal` override `_linkTimeResolveOverride`. `PolynomialIntVal` (what `+`, `-` and `*` fold into) has no override, so with `extern static const int V;` the expression `V + 4` stays symbolic at layout time while `?:` and `==` resolve. On master f6238cee3, `[numthreads(V + 4,1,1)]` emits SPIR-V LocalSize 7 but reflection reports threadGroupSize `[0,1,1]`, and `Conditional<ConstantBuffer<float>, (V + 1) == 4>` loses its binding. A prototype override fixed both: resolve each factor's param, multiply the constants out, refold with `PolynomialIntValBuilder`. Attribute arguments split the same way: `[[vk::binding]]`, `[[vk::location]]`, `vk::index` and `vk::offset` fold with CompileTime and reject externs (E39999), while `[numthreads]`, WaveSize and MaxIters use `checkLinkTimeConstantIntVal` plus `IntVal*` (#13534) [PolynomialIntVal has no link-time resolve: `extern + N` fails at layout/reflection](../learnings/1791496164580-polynomialintval-has-no-link-time-resolve-extern-n.md).

On the IR side, an attribute operand that is a link-time expression is folded only by the first `simplifyIR` (`slang-emit.cpp:1494`), after `checkEntryPointDecorations` (`slang-emit.cpp:1366`) — which is why #14095's `[WaveSize]` CUDA/WGSL checks miss such operands. A repro needs an operand that really stays arithmetic: `kBase * 1` normalizes to a bare DeclRef that linking literalizes before the check; use `kHalf * 2` with `extern static const int kHalf` [link-time repro: x*1 folds early, use x*2](../learnings/1793375479117-slang-link-time-repro-x-1-folds-early-use-x-2.md).

## Combined texture-sampler lowering: nested/entry-point bindings lost (#13272) and plain textures retyped (#13326)

Consider `uniform Sampler2D a, b` entry params with `-target metal`, or a global `struct S { Sampler2D x; }; S g;`. `lowerCombinedTextureSamplers` (`slang-ir-lower-combined-texture-sampler.cpp:159-215`) rebuilds the var layout only for a global parameter whose own (array-unwrapped) type is a combined sampler, but its final type swap (`:316-320`) replaces the combined type with `{texture, sampler}` everywhere, struct fields included, leaving those field layouts flat. Entry-point `uniform Sampler2D` parameters are hit too, because `collectEntryPointUniformParams` has already made them fields of the synthesized `%entryPointParams` struct. In Release the split parameters come out with no `[[texture]]`/`[[sampler]]` (Metal), no `register(t/s)` (HLSL) and no `@binding` (WGSL); in Debug, `slang-ir-legalize-types.cpp(3503)` asserts — a good canary. SPIR-V and GLSL are unaffected (the pass does not run there). Open PR #10607 diagnoses the same mechanism but patches it with a consumer-side fallback in `declareVars`; the idiomatic fix is a producer-side recursive layout rewrite. #10117's exact repro no longer reproduces as of 3649fb982 [lowerCombinedTextureSamplers only fixes layouts of top-level Sampler2D globals](../learnings/1790497207427-lowercombinedtexturesamplers-only-fixes-layouts-of.md).

Writing that rewrite exposes a second trap: IR layout insts (`IRVarLayout`, `IRTypeLayout`, field attrs) are hoistable and deduplicated by operands, and var-layout offsets are parent-relative — a top-level global's var layout (absolute `t1`/`s1`) can be the very same inst as a struct's field var layout (relative offset 1). With `Sampler2D top0, top1; struct S { Sampler2D a, b; } S g;`, deleting `top0`/`top1`'s old var layouts after swapping their `LayoutDecoration` detached `g.a`/`g.b`'s field layouts — `removeAndDeallocate` calls `removeArguments` and `removeFromParent` even with live users, so `g.a`/`g.b` both emitted at `t2`/`s2`, silently. When rewriting layouts, build new ones and swap the decoration, and leave the old insts for DCE. To find the hidden user, walk `varLayout->firstUse`; it shows up as `structFieldLayout`. Note also that `getFieldLayout` (`slang-legalize-types.cpp`) reads a `ParameterGroupTypeLayout` through its `offsetElementTypeLayout`, not its `elementVarLayout`, so a rewrite must update both [IR layout insts are deduplicated: never removeAndDeallocate an "old" layout after rebuilding](../learnings/1790502693181-ir-layout-insts-are-deduplicated-never-removeandde.md).

The same pass has a third, independent bug: it can retype PLAIN textures (#13326, a v2025.21 regression from #8856; v2025.20 is correct). `getLoweredTypeInfo` (`:28`) does `as<IRTextureTypeBase>` with no `isCombined()` check, and the `CastDescriptorHandleToResource` branch (`:264`) calls it with the cast's result type. On targets where `.Handle` is still a `DescriptorHandle` when this pass runs (Metal and `-target cpp`), that result type is the plain `Texture2D`, so the pass builds a `{texture, sampler}` struct for it, and the final `replaceUsesWith` loop retypes every plain `Texture2D` in the module (IR types are hash-consed). Unrelated globals such as `Texture2D t[2]` keep their flat layouts and hit the same `:3503` assert; a combined `Sampler2D` is needed only as a trigger. The fix classifies with the file's own `isCombinedTextureSamplerType` (292/292 pass). So the `:3503` assert has at least two producers in this pass — never dedup on its text alone. More generally, when type X is corrupted only if an unrelated type Y is also present, suspect a module-wide `replaceUsesWith` on a hash-consed type (confirm with `-dump-ir-before/-after <pass>`) [lowerCombinedTextureSamplers: getLoweredTypeInfo lowers ANY texture type (#13326)](../learnings/1790707213244-lowercombinedtexturesamplers-getloweredtypeinfo-lo.md).

## separate-debug-info: multi-target demotes SPIRV out of whole-program (#12147)

`SLANG_RELEASE_ASSERT(debugArtifactCount == 1)` at `slang-end-to-end-request.cpp:766` is defended by "Direct-SPIR-V output is whole-program, so its entry points share one debug artifact" — the premise holds ONLY for a single target. The SPIRV target gets `SLANG_TARGET_FLAG_GENERATE_WHOLE_PROGRAM` only when a `rawOutput` is matched to it (`slang-options.cpp:4672-4677`); without an explicit per-target `-o`, the only auto-source is the implicit-output synthesis (:4566) gated on `m_rawTargets.getCount() == 1`. So a second `-target` skips synthesis → SPIRV stays per-EP → one debug-bearing artifact PER entry point → 2 EPs abort with E99997 (exit 255). Precise trigger: **≥2 `-target`s + ≥2 entry points + no per-target `-o` for the SPIRV target** — single-target (any EP count), multi-target with 1 EP, and multi-target + explicit `-o` are all fine. The count multiplier is entry-point count, not the second target (review discipline: when a bot/maintainer dismisses a "count>1" assert as out-of-contract, check whether their repro varied the ENTRY-POINT count, not just the target list — `spirv+spirv-asm` also aborts with 2 EPs). Principled fix mirrors the sibling `_validateCoverageManifestOutputPaths`, which already diagnoses the identical multi-artifact shape gracefully ([Slang separate-debug-info: multi-target demotes SPIRV out of whole-program → per-EP debug artifacts abort the count==1 assert](../learnings/1784336687356-slang-separate-debug-info-multi-target-demotes-spi.md)).

**`DescriptorKind` is a COARSE proxy for a type's IR representation — gate NV-bindless `uint64` encodability on the IR type, not the kind.** Whether a `DescriptorHandle<T>` is a native `uint64` bindless handle under `spvBindlessTextureNV` is decided by `isBindlessTextureNVEncodableResourceType` = `as<IRTextureType>(t) || as<IRSamplerStateTypeBase>(t)`. Meta-code testing `T.kind == DescriptorKind.Texture|...` instead is wrong: `SubpassInput` declares `kind=Texture` but lowers to `IRSubpassInputType`, and `TextureBuffer<T>` declares `kind=UniformTexelBuffer` but lowers to `IRTextureBufferType` — neither is `IRTextureType`, so routing them to `__castDescriptorHandleToResource<T>` aborts (#13070/PR #13086). Fix that worked: a per-type `static const bool isBindlessTextureNVEncodable` requirement on `IOpaqueDescriptor`, `true` only for genuinely `IRTextureType` instances ([DescriptorKind is a coarse proxy for NV-bindless uint64 representation — gate on the IR type](../learnings/1789559398644-descriptorkind-is-a-coarse-proxy-for-nv-bindless-u.md)).

**Slang's SPIR-V bindless descriptor-heap binding INDICES are hardcoded per preset, not CLI-reassignable.** The two preset enums live in `hlsl.meta.slang` (`DefaultVkBindlessBindings`, `VkMutableBindlessBindings`); the `BindlessDescriptorOptions` preset (default `VkMutable`) picks the enum via a switch, and the index flows to lowering as a `constexpr` → `DescriptorTableSlot` offset. `-bindless-space-index` configures ONLY the descriptor set/space (a *preferred* space — if occupied Slang picks the next free and warns), never the binding number. DXC's `-fvk-bind-resource-heap`/`-fvk-bind-sampler-heap` are NOT supported; unknown options hard-error ([Slang bindless heap binding indices are preset-fixed, not CLI-configurable](../learnings/1789582349574-slang-bindless-heap-binding-indices-are-preset-fix.md)).

## SPIR-V untyped-pointer matrix layout is spec-correct (#14541); embedded-blob bindings carry the module's layout (#4846)

Matrix loads through SPIR-V *untyped* pointers get their layout from struct-member decorations via provenance — SPV_KHR_untyped_pointers rev 4 §2.16.2 requires any untyped pointer accessed as a matrix to be the result of an access chain whose **Base Type is a structure**; the "as-if OpTypePointer" clause then makes the load inherit that member's RowMajor/MatrixStride (any other reading makes the rev-4 rule vacuous — structs are SPIR-V's only layout-carrying construct). Slang's heap-ConstantBuffer emission (`OpBufferPointerEXT` → `OpUntypedAccessChainKHR` with Block-struct Base Type, member RowMajor+MatrixStride 16 → `OpLoad %mat4v4float`) is exactly this sanctioned form, so the L40S transposed-reads + VK_ERROR_DEVICE_LOST (driver 595.91.07; Mesa Xe2 correct) is an **NVIDIA driver bug, not wrong codegen**. Corollaries: at stride 16 a 4×4 row/col-major reading covers the same 64 bytes, so a transpose can never be an addressing/stride fault; spirv-val passing is compatible with driver misbehavior because it certifies the producer, never execution semantics. Also: release slangc needs `LD_LIBRARY_PATH=build/Debug/lib` for `-target spirv-asm` / SLANG_RUN_SPIRV_VALIDATION [SPV untyped-pointer matrix layout: rev-4 provenance rule makes Slang's heap-CB emission spec-correct](../learnings/1795027509199-spv-untyped-pointer-matrix-layout-rev-4-provenance.md).

Embedded downstream-IR blobs (`-embed-downstream-ir`) bake only functions declared `export` (or `public export`) — a `public`-only function embeds NOTHING (measured at master 4a1d62c5b: `public float twice()` → 1816 B empty DXBC skeleton). Global shader parameters bake into the blob **only when referenced by an embedded `export` function**, and they bake with the MODULE's own binding layout — which can collide with the consuming program's (#4846: loud dxc "Resource ... overlap" error; explicit `register()` is the workaround). Library-profile SPIR-V (lib_6_3) final binaries carry no OpDecorate Binding/DescriptorSet in ANY case — bindings live in reflection, assigned at runtime link; don't misread that as a collision. Blob archaeology: `.slang-module` files embed DXBC/SPIR-V blobs verbatim — scan for the magic and parse with python struct instead of hunting for a dxc CLI [export (not public) gates -embed-downstream-ir blob content; globals bake only via export fns](../learnings/1795035874649-slang-export-not-public-gates-embed-downstream-ir-.md).
