# Slang Compiler: Descriptor-Heap, DescriptorHandle, Entry-Point Layout, and Debug-Info Lowering

This page covers descriptor and layout lowering: descriptor-heap `[noinline]` texture params, `DescriptorHandle` per-use reload, why entry-point/reflection layout fixes belong in the front-end, and the `separate-debug-info` multi-target whole-program demotion.

## TL;DR
- **Descriptor-heap `[noinline]` texture params: reuse the hoistable heap global** rather than parameterizing the texture through the noinline boundary.
- **`DescriptorHandle<T>` re-loads on every use** via two independent mechanisms: `shouldDuplicateInstAtUseSite()` hard-codes `CastDescriptorHandleToResource → true`, and the descriptor cast/load ops are NOT `hoistable`. `hoistable=true` is the WRONG lever (it means module-global GVN, not per-loop LICM) — the right levers are relaxing `shouldDuplicateInstAtUseSite` for dominating loop-invariant casts and/or enabling `hoistLoopInvariantInsts`.
- **The reload asymmetry is real: SPIR-V force-duplicates the cast by design; HLSL already reuses via a hoisted local** (`ResourceDescriptorHeap[i]` emitted once). #11798 (`UntypedResourceHandle` input syntax) does NOT close #12051. Meta-lesson: EMIT AND GREP before any cross-target codegen claim.
- **Entry-point / varying-parameter / reflection layout fixes belong in the front-end AST BEFORE entry-point layout generation, not a back-end post-link IR rebuild** — a parallel IR layout path is "wrong by construction" (no consistency guarantee against AST-computed core layout). Default the recommendation to a front-end AST resolution step.
- **Don't hand-roll recursion for link-time type resolution in layout** — the layout walk already re-enters per-node resolution and `Val::resolve()` recurses. The one non-redundant step for `export struct W : I = Impl` is swapping the abstract `InheritanceDecl::witnessTable` for the concrete `InheritanceDecl::witnessVal` before resolving (plain `resolve()` reads the abstract witness → opaque layout → crash).
- **A `SLANG_RELEASE_ASSERT(debugArtifactCount == 1)` premise ("Direct-SPIR-V is whole-program") holds only for a SINGLE target.** Precise abort trigger: ≥2 `-target`s + ≥2 entry points + no per-target `-o` for the SPIRV target → SPIRV stays per-EP → one debug-bearing artifact per entry point → E99997. Fix by diagnosing the multi-artifact shape gracefully (mirror `_validateCoverageManifestOutputPaths` / `SLANG_FAIL`), not by asserting. The count multiplier is entry-point count, not the second target.

## Descriptor-heap [noinline] texture params: reuse the hoistable heap global

Approach-A fix for descriptor-heap `[noinline]` texture params (#11498, root cause of #11496, fixed in PR #11502): **reuse the hoistable heap global** rather than parameterizing the texture through the noinline boundary ([1780769595819-approach-a-fix-for-descriptor-heap-noi](../learnings/1780769595819-approach-a-fix-for-descriptor-heap-noinline-textur.md)).

## DescriptorHandle Per-Use Reload (#12051)

`DescriptorHandle<T>` descriptors re-load on every use (a handle sampled in a loop reloads each iteration). Two independent mechanisms, both confirmed by source Read: `shouldDuplicateInstAtUseSite()` (`slang-ir-util.cpp:2634`) hard-codes `CastDescriptorHandleToResource -> true`, and the descriptor cast/load ops are NOT `hoistable` in `slang-ir-insts.lua` (so IRBuilder's GVN dedup never collapses repeated identical loads). But `hoistable=true` is the WRONG lever (it means module-global GVN, not per-loop LICM); the right levers are relaxing `shouldDuplicateInstAtUseSite` for dominating loop-invariant casts and/or enabling `hoistLoopInvariantInsts` for these ops ([slang#12051 DescriptorHandle reloads every use -- root cause](../learnings/1783705209384-slang-12051-descriptorhandle-reloads-every-use-roo.md)). A same-day CORRECTION overturned an earlier "HLSL can't pin" inference: an empirical `slangc -target hlsl` repro showed resource-typed locals ARE storable and reusable on HLSL today -- hoisting the conversion into a local before the loop emits `ResourceDescriptorHeap[i]` once; the per-use reload only happens when the conversion is written per-use. So the asymmetry is real (SPIR-V's `CastDescriptorHandleToResource` IS force-duplicated by design; HLSL is not), and #11798 (input-syntax via `UntypedResourceHandle`) does NOT close #12051. The meta-lesson: for any cross-target codegen claim, EMIT AND GREP before asserting -- source-path reading establishes the mechanism but not the observable output shape ([CORRECTION #12051: DescriptorHandle reuse ALREADY works on HLSL via a local](../learnings/1783724965975-correction-slang-12051-descriptorhandle-reuse-alre.md)).

## Entry-Point Layout Fixes Belong in the Front-End (#9580/#10030)

For entry-point / varying-parameter / reflection *layout* fixes, the resolution must happen at the front-end AST level *before* entry-point layout generation, NOT via a back-end IR post-link layout rebuild, which is "wrong by construction" per Slang conventions (a parallel IR layout path has no consistency guarantee against AST-computed core layout). Verified on PR #10030 (fix for #9580): tangent-vector's CHANGES_REQUESTED and csyonghe's comment both reject the IR approach and call for a front-end resolution step, and the github-actions bot's nits were all hardening the *wrong* (back-end) path. Our own triage-9580 had recommended exactly that rejected Approach A; default the recommendation to a front-end AST resolution step and only propose a back-end IR transform if a maintainer explicitly asks ([Slang entry-point layout fixes must be front-end (AST), not back-end IR rebuild](../learnings/1783710345558-slang-entry-point-layout-fixes-must-be-front-end-a.md)). Implementing that front-end resolution (PR #12131) confirmed two non-obvious mechanics: (1) you do NOT need a bespoke recursive walker over a decl-ref's substructure to resolve link-time-specialized types during layout — the layout walk in `slang-type-layout.cpp` already re-enters the per-node resolution routine for each nested `DeclRefType` (struct fields, generic-app elements) and `Val::resolve()` already recurses generic-app args and witness chains, so a generic-arg walker would be dead code with no failing test; put the per-node policy in ONE bottleneck routine and delegate traversal. (2) For `export struct W : I = Impl`, the concrete conformance `Impl : I` lives in `InheritanceDecl::witnessVal`, a field SEPARATE from `InheritanceDecl::witnessTable` (the wrapper's own abstract conformance) — plain `Val::resolve()` reads the abstract `witnessTable` and returns the type unchanged (→ opaque layout → crash), so the one non-redundant step is swapping the abstract witness for `witnessVal` before resolving. No existing path reads `witnessVal` on its own, so "just call resolve()" does not fix the bug — a useful counter to reviewer/codex pushes toward it ([Link-time type resolution in layout: no hand-rolled recursion needed — layout-walk re-entry + Val::resolve() already recurse](../learnings/1785467527075-link-time-type-resolution-in-layout-no-hand-rolled.md)).

## separate-debug-info: multi-target demotes SPIRV out of whole-program (#12147)

`SLANG_RELEASE_ASSERT(debugArtifactCount == 1)` at `slang-end-to-end-request.cpp:766` is defended by "Direct-SPIR-V output is whole-program, so its entry points share one debug artifact" — but that premise holds ONLY for a single target. The SPIRV target gets `SLANG_TARGET_FLAG_GENERATE_WHOLE_PROGRAM` only when a `rawOutput` is matched to it (`slang-options.cpp:4672-4677`); without an explicit per-target `-o`, the only auto-source of that rawOutput is the implicit-output synthesis (:4566) gated on `m_rawTargets.getCount() == 1`. So a second `-target` skips synthesis → SPIRV stays per-EP → `_collectExistingOutputArtifacts` takes the per-entry-point branch → one debug-bearing artifact PER entry point → 2 EPs abort with E99997 (exit 255). Precise trigger: **≥2 `-target`s + ≥2 entry points + no per-target `-o` for the SPIRV target** — single-target (any EP count), multi-target with 1 EP, and multi-target + explicit `-o` are all fine. The count multiplier is entry-point count on a per-EP target, not the second target's contribution (a review discipline point: when a bot/maintainer dismisses a "count>1" assert as out-of-contract, check whether their repro varied the ENTRY-POINT count, not just the target list — `spirv+spirv-asm` also aborts with 2 EPs even though spirv-asm's Assembly payload doesn't itself increment the count). Principled fix mirrors the sibling `_validateCoverageManifestOutputPaths`, which already diagnoses the identical multi-artifact shape gracefully (`CoverageManifestOutputMultipleArtifacts`, SLANG_FAIL) instead of RELEASE_ASSERT-ing ([Slang separate-debug-info: multi-target demotes SPIRV out of whole-program → per-EP debug artifacts abort the count==1 assert](../learnings/1784336687356-slang-separate-debug-info-multi-target-demotes-spi.md)).
