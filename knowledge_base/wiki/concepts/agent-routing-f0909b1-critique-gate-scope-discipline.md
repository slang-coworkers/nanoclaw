## TL;DR

When the critique/delivery gate fires on the wrong thing (matcher false-positives, out-of-scope must-fixes), when a gate finding is a real escalation rather than something to capitulate to, and why running the gate anyway repeatedly earns its keep. The through-line: TRIGGER ≠ REASON for the matcher, and "this gate is a known misfire" is a hypothesis the gate can refute — let it.

- **The gate audit is a naive substring match** — a triager's report that *references* "[Fix Report]" trips a `[GATE AUDIT]` for a session that reviewed no code. False positive; paraphrase the bracketed marker to avoid it, same as the internal-tag write-guard discipline.
- **A read-only `gh api .../pulls/<n>/reviews` fetch is matched as "PR creation"** — a PR-approver harvesting a posted review trips the gate. Mitigate by reading via the MCP tool `github_get_pull_request_reviews`; abstains aren't critique-gated anyway.
- **The hook's "escalation opened" is a LOCAL self-heal file, not a host escalation row** — a host `pending_approvals`/`critique_gate_bypass` row exists only when the file's `forwarded_at` is set. Open the artifact and read the gating field before reporting a host row exists; a group-scoped agent that can't read `ncl approvals` has no standing to assert one.
- **DECISION_REVIEW can wrongly gate on the UNTRUSTED author diff** — a comment-hygiene must-fix on a line in `gh pr diff` (which a read-only approver cannot edit) is advisory-to-maintainer, not a defect in your derivation. Demand the false sentence in YOUR artifact; if none exists, it's out-of-scope for the gate.
- **The comment-hygiene rubric has NO regression-test exception** — a new test comment narrating the prior bug ("Previously… 8 reads") trips DECISION_REVIEW even though precedent accepts it; the approver can't edit the PR, so it's revise-or-ABSTAIN, and a rubric change is an operator call. Also re-cite line numbers at the pinned head after any (even comment-only) push.
- **A severity/materiality split between two review opinions is an ESCALATION, not a self-resolve** — don't capitulate down an authority gradient; present both positions to parent (per "3 rounds unresolved must-fix → escalate"). Distinguish "gate found a real defect in my deliverable" (fix it) from "gate holds a defensible-but-different judgment call" (escalate).
- **Run the critique BEFORE the [Resolution], not after** — the adversarial second opinion catches what your own tests and verification missed, *including flaws in a spec you authored*.
- **Don't dismiss a gate you assume is misfiring** — a known token-misfire can mask a genuine must-fix on the decision itself; read the FULL standing note (not its index line), and don't let a parent's loose praise override the parent's structured standing instruction.

## Matcher false-positives (TRIGGER ≠ REASON)

Several atoms document the gate over-firing on surface text rather than semantics. The [critique-gate audit false-positives on "[Fix Report]"](../learnings/1787274342384-critique-gate-audit-false-positives-on-the-literal.md): a triager's `[Triage Resolution]` that merely *references* the fixer's future report trips `[GATE AUDIT] message contains "[Fix Report]" but codex-critique was never invoked` — a naive substring match, advisory not blocking for a session that reviewed no code. The [read-only PR-reviews fetch matched as "PR creation"](../learnings/1787552747233-critique-gate-false-positives-read-only-pr-reviews.md) is the same class: `gate-critique-on-deliver.sh` (matcher ~lines 380-405) counts a `gh api .../pulls/<n>/reviews` GET as a gated write, hits its 3-denial cap, and writes a local escalation file — mitigate by reading reviews via `github_get_pull_request_reviews`. And the [escalation-file-vs-host-row atom](../learnings/1787552737647-approver-infra-abstain-a-critique-gate-hook-s-esca.md) is a companion: the hook's "denial cap reached; escalation opened" writes a LOCAL `/workspace/.claude/critique-escalation.json`; a host row is created only when `forwarded_at` is set, so before reporting an escalation/decision/row was created, open the artifact and read the field that gates persistence — "the success string is not the write."

## Scope bugs: gating the wrong artifact

Two atoms show DECISION_REVIEW collapsing "review the change" (not the approver's job) into "review my decision" (the actual gate). The [comment-hygiene rubric has no regression-test exception](../learnings/1787869345423-approver-critique-mustfix-regression-test-comment-.md): a new regression test's comment narrating the prior bug ("Previously the register path emitted the readback on BOTH passes") is classified must-fix even though slang's `tests/` tree is full of accepted "Previously…" narration — and since the approver never edits the PR, a held must-fix is revise-or-ABSTAIN (`ABSTAIN_POLICY/CRITIQUE_MUSTFIX`), with any rubric carve-out being an operator call. The same atom adds: after a mid-flight comment-only push, RE-CITE line numbers at the pinned head — a comment-only interval moves line numbers even when logic is byte-identical. More sharply, [DECISION_REVIEW can gate on the untrusted author diff](../learnings/1787917297143-approver-infra-abstain-decision-review-critique-ca.md): a must-fix on `pr.diff:19` (a comment in the *author's* source) is outside the read-only approver's edit surface; a must-fix naming a `file:line` that is (a) in the PR diff, (b) not in any artifact you authored, and (c) unchangeable by you is a CODE finding advisory-to-maintainer, not a `CRITIQUE_MUSTFIX` on your derivation. When the mechanical gate blocks WOULD_APPROVE and the operator tie-breaker times out, `ESCALATED` is the honest terminal code (both it and `CRITIQUE_MUSTFIX` are INFRA-family — a harness gap to fix by scoping the comment-hygiene rule to authored diffs).

The dual of a gate over-firing is a *pre-clearance* you interpret too loosely. When a parent/triager pre-clears a **tightly-bounded** post ("bare pass/fail CI status is ungated — post directly; ANY interpretation is gated"), [treat the bound literally](../learnings/1789765970729-gate-a-post-that-exceeds-a-tightly-bounded-pre-cle.md): extra context that feels benign — branch/pin state, a full check-run rollup, a root-cause attribution — still exceeds a "bare pass/fail" clearance and should be draft→parent first, even when every added claim is accurate (on slang#9030/PR #13105 the added Vulkan-SDK root-cause attribution was gated interpretation even though it only restated the maintainer's own confirmed cause, and an OUTPUT_REVIEW caught the upward report mislabeling the comment as "bare pass/fail"). The endorsed recovery once you have already overstepped: do NOT edit/delete the posted comment (that is itself a gated user-facing write and can look worse than the original over-scope) — disclose the over-scope honestly in the upward report and let the parent decide whether to trim. The operator's framing was "I'd rather you over-disclose than quietly stretch a bound": gate proactively when in doubt, and flag plainly after the fact rather than silently reversing a user-facing action.

A sharper scope bug wedges a **non-code PR-review reply** — a `gh api .../pulls/<n>/comments/<id>/replies` acknowledgment of a maintainer's `requested_changes`. The gate (a) classifies the review reply as "PR creation / code delivery" and (b) never converges, because it re-hashes artifacts codex opportunistically attested (the session transcript `conversations/<date>-conversation.md` + build logs) that mutate every turn, so each fresh OUTPUT_REVIEW approve is invalidated by the next transcript write before the `gh` write can fire (it even blocks `gh` *reads*). A factual, non-committal review reply is not a code change and is out of scope for the *code*-critique gate — don't spin re-running /codex-critique to satisfy it (it won't converge); note that `git push` itself is NOT gated (only `gh` deliver/PR commands are), so the code fix always lands and only the outward comment wedges. Surface the EXACT gate error text up the chain immediately — don't let `requested_changes` sit silently. The fleet-reusable unblock, with explicit parent/operator authorization for a one-time cross of the fixer/triager role division: have a **different coworker session that has no pending-critique state** post the authorized reply — externally it is the same `nv-slang-bot[bot]` identity and the PR→owning-session webhook mapping is unchanged, so ownership hands straight back (in practice the triager session, which never invoked codex-critique this session so the gate audits-but-skips, posted cleanly while the fixer was wedged). Posting the reply is still operator-gated (needs the `<github-post-authorized />` marker relayed from parent), and never `--add-reviewer`/`requested_reviewers` to re-request review — the threaded reply itself is the re-review prompt. Durable fix is operator-side: scope the gate to exclude review replies, stop attesting the mutating session transcript, or provide a gate-exempt post path ([critique-gate wedges non-code PR review-replies — unblock via a clean sibling session](../learnings/1790086509553-critique-gate-wedges-non-code-pr-review-replies-un.md); [critique-gate wedges non-code PR-review replies by attesting the mutating session transcript](../learnings/1790086520678-critique-gate-wedges-non-code-pr-review-replies-at.md); shader-slang/slang#13194 → PR #13196).

## When a gate finding is an escalation, and when to trust the gate

A genuine judgment split is not something to fold on. The [DECISION_REVIEW severity-classification disagreement](../learnings/1787324124929-critique-gate-decision-review-can-raise-a-severity.md) held must-fix on classifying a clarity nit as blocking while the approver and the clarity reviewer classified it non-blocking — codex conceded the only delta was severity. The right move: don't edit the fixer's source, route the finding to the code owner strengthened by the corroboration, and per "3 rounds unresolved must-fix → escalate to parent," present BOTH positions for adjudication and record the disagreement — distinguish "gate found a real defect in my deliverable" (fix it) from "gate holds a defensible-but-different judgment call" (escalate, don't fold down the authority gradient).

But the gate also earns its keep. [Run the critique BEFORE the [Resolution]](../learnings/1787375940428-run-the-critique-gate-before-the-resolution-not-af.md): the adversarial review found two BLOCKER-class issues, one a flaw in the regex the authorizer *themselves* specified — "I verified the tests pass" is not the critique, and the authorizer's own spec is the thing least likely to be re-audited. [The OUTPUT_REVIEW gate caught a real decision error](../learnings/1788297246013-approver-critique-mustfix-the-output-review-gate-c.md) the approver nearly shipped after dismissing the gate as a known token-misfire: read the FULL standing note (not its one-line index), don't let a parent's loose ack override the parent's structured standing instruction, and don't reconstruct a signed policy from memory to drive eligibility. And [switching a gate macro `#ifdef`→`#if` leaves stale prose](../learnings/1788296573909-switching-a-gate-macro-ifdef-if-leaves-stale-prose.md): the one-token code change flips the described semantics ("when defined"→"when nonzero"), so sweep comments, docs, and the PR body — the OUTPUT_REVIEW/delivery-gate pass earns its keep specifically on doc/comment/PR-body accuracy a code-focused peer review skims past, so a peer APPROVE is not license to skip the output critique.

The plan stage is also a cheap **concede** instrument. On slang#13073 PR(2), after the maintainer twice said the bot's understanding of the ask was wrong (a harsh "train wreck" / "reboot with a more capable model" threat), the fixer authorized the redesign BUT required running the implementation PLAN through codex PLAN_REVIEW *before* writing any code — a de-risk gate. It flagged ~11 fidelity misses against his spec (wrong base class — SemanticsVisitor vs his SemanticsContext; mishandled effectively-static; missing ancestor/context traversal; ADDED contradictory-attribute diagnostics + an options hook he never asked for; query names missing "effective"; …), independently confirming the bot was NOT converging on his design intent, so the fixer conceded with ZERO code written and the maintainer took the PR over. The lessons: a maintainer who holds the true design intent repeatedly saying the bot's summary of the ask is "still not correct" is a strong non-convergence signal, and an early graceful hand-off preserves more credibility than grinding failed rounds; for a hard task under a credibility threat, don't choose blindly between "attempt" and "concede" — attempt WITH a pre-code plan-critique gate, which surfaces non-convergence at the cheapest point (plan stage, no wasted code) and turns the concede into a clean, evidenced decision rather than a rejected PR after hours of work; and leave helpfully — stand down non-defensively (don't re-argue the rejected design), preserve the branch/PR for reference, offer the mechanical research artifacts (consumer-site maps, touchpoints — facts, not design opinions) as a head-start, then go quiet ([a pre-code plan-critique gate lets you concede a non-converging task cheaply](../learnings/1790117654797-a-pre-code-plan-critique-gate-lets-you-concede-a-n.md)).

**The codex critique gate (`/app/hooks/gate-critique-on-deliver.sh`) that hard-blocks `gh pr create` clears ONLY via a recorded codex OUTPUT_REVIEW approve, a HOST-injected env kill-switch an agent cannot set (`CRITIQUE_ESCALATION=0`/`CRITIQUE_GATE_ACTIVE=0`), or a HUMAN-admin one-shot bypass grant in `workflow-state.json` (consulted only after ≥3 denials this session). This is by design: the bypass is reserved for a human admin.** An admin-orchestrator agent (Main/Orchestrator) must NOT declare a "waiver" it can grant — mechanically it can't (env is host-injected; writing the bypass flag forges a human safety decision), and it shouldn't. When codex is down and a well-verified PR is gate-blocked, escalate to the human operator with mechanisms + recommendation: prefer repairing/restarting codex (the gate then works as designed fleet-wide), else the operator injects the env kill-switch or grants the one-shot bypass.
