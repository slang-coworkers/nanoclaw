## TL;DR

Correctness of SPIR-V for varyings, pointers, and subgroup ops, plus the buffer-element copy that hangs drivers:

- **Partially-initialized entry-point output struct**: an unwritten field gets a spurious `OpStore` of an undefined value. Fix at the copy site in `slang-ir-glsl-legalize.cpp` (`assign` iterates every field and unconditionally `emitFieldExtract`+store), NOT the emitter. The undef arrives in TWO shapes (`OpUndef` and a genuine `OpLoad` from an unwritten `OpVariable`); a peephole comment claiming "the backend re-elides it on SPIR-V" is FALSE.
- **Tessellation per-patch varyings**: the direct SPIR-V backend emits `SpvDecorationPatch` only for the tess-factor builtins, so USER per-patch data (`float3 Lines[8] : PATCH_LINE`) gets no `Patch` and collides at Location 0 → `VUID-08722`. `Patch` puts a var in a SEPARATE location space, so it ALONE fixes the single-field case, but multi-field needs span-aware per-patch numbering. HS↔DS cross-stage location mismatch is a front-end (parameter-binding) issue in a different layer, out of scope for the emit fix.
- **Pointer-to-sized-array ArrayStride**: a `Ptr<T[N]>` in a buffer becomes TWO distinct SPIR-V pointer types — the struct-wrapper pointer (whole-array stride, for `p[i]`/`p+1`) and the raw-array pointer (element stride, for `(*p)[i]`). Widening the element-stride branch from `IRUnsizedArrayType`→`IRArrayTypeBase` fixes dynamic-index reads. "ArrayStride == whole array size" is a common wrong intuition.
- **Wave/ballot ops can't be CSE'd by `removeRedundancy`** — they have no dedicated IR opcode (inline `spirv_asm`, zero operands on the `IRSPIRVAsm` parent) and are deliberately non-movable (marking them movable would let loop-invariant hoisting move a ballot across control flow where the active-lane mask differs — a correctness bug). A safe dedup is a hand-rolled SAME-basic-block pass fencing on `kIROp_Call` unconditionally.
- **A non-mutating method on a big-array structured-buffer element copies the whole element** into a Function-storage local (`this` is by-value for copyable types), producing a 16 MB `OpVariable`+`OpCopyLogical` that hangs the driver's pipeline compiler. `[mutating]`/`[constref]` (pointer `this`) are clean.

## Partially-initialized output struct: skip the spurious store at the copy site

For a vertex/fragment entry point returning a struct with some fields never written (`VOut o; o.color=...; return o;`, `o.uv` unwritten), the emitted SPIR-V/GLSL still stores an undefined value into the unwritten field's varying — the varying stays correctly declared in `OpEntryPoint` (Location N), only the store is spurious. The root cause and fix layer is `slang-ir-glsl-legalize.cpp` (the SPIR-V *and* GLSL return→varying-output path; the CPU/CUDA path in `slang-ir-legalize-varying-params.cpp` explicitly defers varying structs here): `rewriteReturnToOutputStore` replaces `return o` with `assign(resultGlobal, ...)`, and `assign` iterates every struct field and does an unconditional `emitFieldExtract`+store with no "was this field written" check. Fix at this copy site (skip a field's store when its value is provably undefined), not the emitter. Two gotchas: the undef arrives in TWO shapes — a `LoadFromUninitializedMemory` (→ `OpUndef`) OR a genuine `OpLoad` from an un-promoted `Function`-storage `OpVariable` never stored to — so a fix checking only for `IRUndefined` at emit misses the load-from-var shape; and the peephole comment claiming "on SPIR-V the backend re-elides it" is false (`emitStore` emits `OpStore` unconditionally with no undef guard, and DCE keeps it because a `kIROp_Store` is conservatively side-effecting) ([partially-init entry-point output struct: unwritten field gets a spurious store](../learnings/1787692089803-partially-init-entry-point-output-struct-unwritten.md)).

## Tessellation patch decoration: separate location space, necessary but not always sufficient

The direct SPIR-V backend (`-emit-spirv-directly`) applies `SpvDecorationPatch` in exactly ONE place — `getBuiltinGlobalVar`, gated on the `TessLevelInner`/`TessLevelOuter` builtins (i.e. only `SV_TessFactor`/`SV_InsideTessFactor`). A hull patch-constant function that returns USER per-patch data (e.g. `float3 Lines[8] : PATCH_LINE`) gets that field legalized into an ordinary varying with NO per-patch marker, so it never receives `Patch`; worse, its Location is drawn from the SAME per-direction counter as per-control-point varyings, so it collides at Location 0 and `spirv-val` fails `VUID-StandaloneSpirv-OpEntryPoint-08722` while `slangc` exits 0 (silent bad output). Missing `Patch` is therefore both a correctness bug AND the cause of the collision. There is no first-class per-patch IR decoration; the recommended fix mirrors `kIROp_PerVertexDecoration` — a new `kIROp_PatchDecoration` (producer in glsl-legalize, consumer emitting `SpvDecorationPatch` in the `emitGlobalParam` decoration loop) — plus a separate location counter ([direct SPIR-V emits Patch decoration only for SV tess-factor builtins](../learnings/1787638721070-direct-spir-v-emits-patch-decoration-only-for-sv-t.md), [SPIR-V patch-constant user varyings: Patch decoration necessary but not sufficient](../learnings/1787670044220-spir-v-patch-constant-user-varyings-patch-decorati.md)).

The SPIR-V validator tracks `Patch`-decorated interface vars in separate location sets (`patch_locations_index0/1`) from per-vertex vars, so a Patch var and a non-Patch var can both sit at Location 0 without triggering `VUID-08722`. That means **adding `Patch` ALONE fixes the standalone spirv-val failure** for the single-field case (moves the var into the patch location space); a separate location *counter* is only needed for the second half — HS output ↔ DS input location-number consistency, which spirv-val does NOT check standalone ([SPIR-V Patch decoration puts a variable in a SEPARATE location space](../learnings/1787639466581-spir-v-patch-decoration-puts-a-variable-in-a-separ.md)). But the deeper empirical follow-up refines this: with TWO user patch fields, both fall through to Location 0 and both get `Patch`+`Location 0` → still `VUID-08722` (collision *within* patch space, and `float3 Lines[8]` consumes 8 consecutive locations) — so multi-field needs span-aware sequential numbering. The producer bug is a fall-through, not a shared counter: in `createPatchConstantFuncResultTypeLayout` a user semantic like `PATCH_LINE` has an `IRSemanticDecoration`, enters the outer `if(hasSemantic)`, fails the inner `sv_` test, and hits neither offset path → defaults to Location 0. Domain classification should be `stage==Domain && !as<IRHLSLPatchType>(valueType)` + the existing `!systemValueInfo` guard, NOT field-name heuristics; and codex-critique's 3 "blocking" findings were all reproduced with discriminating probes and all real — a verification-of-critique step is cheap insurance ([SPIR-V patch-constant user varyings: Patch decoration necessary but not sufficient](../learnings/1787670044220-spir-v-patch-constant-user-varyings-patch-decorati.md)).

The HS↔DS location mismatch is genuinely a *different layer*. Per-control-point location numbering is computed in TWO places: the DOMAIN side draws all varying inputs (per-control-point `OutputPatch<T,N>` AND per-patch `patchData`) from ONE shared VaryingInput counter in the FRONT-END `slang-parameter-binding.cpp`, while the HULL side numbers the per-patch OUTPUT separately from 0 in the IR pass `createPatchConstantFuncResultTypeLayout`. So a front-end-only change to give DS per-patch its own namespace would not touch HS numbering — making HS==DS requires coordinating BOTH layers. `LayoutResourceKind` is a PUBLIC ABI-stable enum with no per-patch kind (adding one is an ABI change), but the front-end can already distinguish per-patch vs per-control-point at binding time via `HLSLPatchType` ([tessellation per-patch location numbering is split across two layers](../learnings/1787676067552-tessellation-per-patch-location-numbering-is-split.md)).

## Pointer-to-sized-array ArrayStride: two pointer types, two strides

A user-written `Ptr<T[N]>`/`LayoutPtr<T[N]>` inside a buffer is lowered by `lowerBufferElementTypeToStorageType` into `Ptr<struct { T[N]; }>` — the raw array becomes a struct-wrapped member. So the emitted SPIR-V has TWO distinct pointer types needing DIFFERENT ArrayStrides: (1) the pointer to the `OpTypeStruct { T[N] }` wrapper, used for whole-object stepping (`p[i]` yielding a whole `T[N]`, `p+1`) via `OpPtrAccessChain`, whose stride must be the whole-array size (64 for `float4[4]`) — a struct pointee, unchanged by the fix; and (2) the pointer to the raw array type, appearing only mid-access-chain as the base of element-indexing `OpAccessChain` (`(*p)[i]`), whose ArrayStride must be the ELEMENT stride (16 for `float4[4]`). Pre-fix the raw-array pointer wrongly carried 64, so drivers computed `base + i*64` instead of `base + i*16` on a DYNAMIC index → wrong memory (constant indices fold to a fixed offset and never multiply by this stride — the classic "switch-version works, dynamic-index glitches" symptom). The fix widens the guard `as<IRUnsizedArrayType>`→`as<IRArrayTypeBase>` so pointers to *sized* arrays also take the element-stride path. Reuse the array type's own ArrayStride (element stride ≠ element size in std140) ([SPIR-V pointer-to-sized-array ArrayStride: two distinct pointer types carry different strides](../learnings/1788199529800-spir-v-pointer-to-sized-array-arraystride-two-dist.md)). This fix (slang#12698) was confirmed merged-unchanged and is a SHIP-AS-IS shape: widen an existing element-stride branch to cover more array pointee types, guarded by a deterministic emission FileCheck at a layer proven correct by the access-chain graph (whole-object stepping uses the wrapper pointer, the retargeted raw pointer only feeds element-indexing) ([CONFIRMED safe: SPIR-V pointer-ArrayStride element-vs-object-size fix](../learnings/1788305234160-approver-human-agreement-confirmed-safe-spir-v-poi.md)).

## Wave/ballot CSE and the big-array `this`-copy driver hang

Two identical `OpGroupNonUniformBallot` on the same predicate survive to SPIR-V because wave intrinsics have NO SPIR-V ballot IR opcode — they are `[ForceInline]` stdlib funcs whose SPIR-V case is an inline `spirv_asm` block, and after inlining are opaque `IRSPIRVAsm` parents with ZERO operands (content in child insts), so `IRInstKey`/`DeduplicateContext` can't tell two ballot blocks apart. `removeRedundancy` deliberately EXCLUDES spirv_asm/wave ops via `isMovableInst` (they're treated as side-effecting; `SPIRVAsmOperandInst` is deliberately non-hoistable). The load-bearing safety constraint: an `OpGroupNonUniformBallot` result depends on the IMPLICIT active-lane mask, which is not a function argument — so you must NOT mark it pure/hoistable or add it to `isMovableInst` (that also drives loop-invariant hoisting, which would move a ballot across control flow where the active set differs → wrong results, not just perf). A correct CSE is a hand-rolled SAME-basic-block pass: identical predicate operand (by pointer identity), no intervening active-mask-changing op, fence `kIROp_Call` UNCONDITIONALLY (a `[__readNone]` callee can still demote/terminate a lane), use `mightHaveSideEffects()` for the rest, and whitelist only the read-only mask consumer (`OpGroupNonUniformBallotBitCount`); also check operand KIND before `getValue()` (SPIR-V pseudo-ops like `__truncate` have no int value and assert). Runtime impact is small (drivers already CSE same-block ballots) → low priority ([Slang SPIR-V wave ballots can't be CSE'd — safe dedup is same-basic-block only](../learnings/1788170428806-slang-spir-v-wave-ballots-can-t-be-cse-d-and-why-t.md), [SPIR-V ballot/wave-op CSE: why removeRedundancy can't do it, and the fences needed](../learnings/1788195684163-spir-v-ballot-wave-op-cse-why-removeredundancy-can.md)).

A separate but instructive perf/correctness cliff: `vkCreateComputePipelines` HANGS (NVIDIA) when a *non-mutating* member method is called on an `RWStructuredBuffer<T>` element where `T` holds a huge fixed array (`uint values[1<<22]`). The SPIR-V validates; the hang is driver-side and scales with array size. Root cause (found by disassembling, not source-guessing): a non-mutating method's implicit `this` is passed by value (`kDefaultModeForImplicitThisParam = In`, `[nonmutating]`→`In`), and `adjustParamPassingModeBasedOnParamType` only upgrades `In`→`BorrowIn` (pointer) for NON-copyable types — a big `uint[N]` is copyable, so `this` stays by-value, emitting a 16 MB Function-storage `OpVariable` + whole-array `OpLoad`+`OpCopyLogical`+`OpStore`. `[mutating]`→`BorrowInOut` and `[constref]`→`BorrowIn` (pointer `this`) are clean, and free functions narrow via `specializeFuncsForBufferLoadArgs`/`deferBufferLoad` which trace to a global param — the implicit-`this` local var breaks that chain. `[ForceInline]` does NOT fix it (inlining leaves the dynamically-indexed Function-local), and it is not size-dependent in the compiler (size 1024 also copies — "1024 works" is driver tolerance, not a compiler change). Principled fix: stop materializing a by-value copy for `this`/large `In` params when the arg is an addressable buffer/global chain ([non-mutating method on structured-buffer element copies whole element → driver pipeline hang](../learnings/1787807693317-non-mutating-method-on-structured-buffer-element-c.md)).

## Varying-parameter semantics: dual representation (layout vs IR struct-field decoration)

Slang carries a varying parameter's semantic in **two** representations, and the divergence between them is a bug class (#12997: a Metal mesh-vs-fragment `[[user(...)]]` name mismatch). (1) **Verbatim** — an `IRSemanticDecoration` attached to IR struct-type *fields* during AST→IR lowering (`addSemanticDecoration`, `slang-lower-to-ir.cpp:3235` / `:13034`), storing the source spelling **as-written with index = -1** (no name/index split), e.g. `"TEXCOORD1"`. (2) **Normalized** — the `(name, index)` pair in the entry point's `VarLayout` (`setUserSemantic`, `:16591`; parameter binding uppercases + splits trailing digits first). They diverge whenever a code path bypasses the reconciling pass.

The reconciling pass `fixFieldSemanticsOfFlatStruct` (`slang-ir-legalize-varying-params.cpp:3800-3980`) runs **only inside `LegalizeShaderEntryPointContext`, subclassed only by Metal + WGSL** — it canonicalizes field decorations and additionally owns three overlap/offset de-dup jobs (`_returnNonOverlappingAttributeIndex`, `_replaceAttributeOfLayout`, `IRUserSemanticAttr` index reassign, plus the `oldLayoutDecorToNew` remap). Paths that bypass it — e.g. mesh vertex/prim structs lifted into `metal::mesh<>` by `legalizeMeshStageEntryPoint` — keep the verbatim form → drift like `BAR`/`BAR_1`.

**Emit-consumer map for the field-level `IRSemanticDecoration`** (sizes any "audit every consumer"): HLSL (`slang-emit-hlsl.cpp:2225`) reads it directly; WGSL (`slang-emit-wgsl.cpp:294`) → `@location(index)`; Metal (`slang-emit-metal.cpp:1699/1709`) is **layout-first** and only *falls back* to the field decoration when `!hasSemantic` — that fallback is exactly what mesh legalization bypasses to produce #12997; SPIR-V (`slang-emit-spirv.cpp:6908/6917`) reads it reflection-only (`shouldEmitSPIRVReflectionInfo()`); GLSL and CUDA do NOT read it (they source varying semantics from VarLayout by declaration order).

**Intended proper design (maintainer / #12998):** semantics should NOT be attached to IR struct fields at all (legacy mis-feature). The entry-point layout/reflection data is the **single source of truth**; flatten/elaborate + normalize aggregate varyings **early** (where reflection info is produced), not in a late IR legalization pass, and have every IR pass + emitter read from the layout. Two gotchas for any semantic-normalization work: (a) the front-end treats BOTH `sv_` AND `nv_` prefixes as system-value (`slang-parameter-binding.cpp:2024`, on a lowercased name) — do not claim "only SV_ is a system value", and preserve `NV_`; (b) overlapping/duplicate normalized semantics (`TEXCOORD` + `TexCoord0` → both `("TEXCOORD",0)`) are currently silently re-indexed — no duplicate-user-semantic diagnostic exists today (only SV checks in `slang-check-shader.cpp`); maintainers want it diagnosed ([varying-parameter semantics live in two representations; layout-only is the intended design](../learnings/1789075704249-slang-varying-parameter-semantics-live-in-two-repr.md), [dual representation + emit-consumer map @ HEAD 578d571f9](../learnings/1789076180779-varying-param-semantics-dual-representation-emit-c.md)).
