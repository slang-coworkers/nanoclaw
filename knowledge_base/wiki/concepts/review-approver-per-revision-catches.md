# PR-Approver: Per-Revision Discipline — Synchronize Classification, Regression Catches & Merge Provenance

The incremental discipline of re-evaluating each `synchronize`: classify the delta before re-litigating, catch regressions and self-contradictions that CI-red carries as *evidence* (not a clause), read Devin's structured verdict rather than its prose, resolve what a CI-red actually represents, and split merge provenance before scoring a `pr_merged` join. Drawn from the 2026-07-18/19 approver session and its calibration corrections.

## TL;DR

- **A `synchronize` is not automatically a fix — classify the delta first.** A pure `Merge branch 'master'` changes nothing in the PR's own content (verify blob-sha; for hot files use the PR net-diff hunks, not the blob). A push that "addresses review" may address a *different axis* than your open gap. A "Fix …" commit may patch only ONE of N near-duplicate sites — grep every loop body at head.
- **The strongest 🔴s need no external corroboration.** A PR's own new test failing at head is self-contradicting; a pre-existing untouched test failing at head is a regression (three conditions, or the three-part green-on-master proof). CI red is challenger *evidence*, never laundered by a clause that doesn't require CI.
- **A test WEAKENED to green a REPRODUCED failure on the code under review is a hard no-approve.** Diff the test itself and ask: did assertions get STRONGER or WEAKER?
- **Blast radius follows the mechanism, not the PR title.** A shared modifier-lowering arm, a visibility-*raising* default, a "simplify"/refactor that drops a deliberate distinction, or a fix that creates a fresh doc 🔴 in its own `@remarks` — each widens beyond the explicit syntax.
- **Devin's structured verdict is the only load-bearing Devin signal** — prose and the "N Flag" page counter are not; the structured `## Bugs`/`## Flags` section wins.
- **A CI red is not automatically an independent failure** — `check-ci` is an aggregation gate; a stray `CHECK:` token in a prose comment is a test-authoring artifact.
- **Split merge provenance before scoring a join.** An independent-maintainer APPROVED same head is STRONG agreement; an author self-merge is WEAK — it attests confidence, not independent review, and does NOT refute a withhold. Pull `mergedBy` + `reviewDecision` + `reviews[].state/commit.oid`.

## Classify the synchronize delta before re-litigating

**A `synchronize` is not automatically a fix — classify the delta before re-litigating.** Three sharpenings of the per-revision discipline: (1) a `synchronize` whose new head is a pure `Merge branch 'master'` changes nothing in the PR's own content — verify the flagged files' git **blob-sha** across the two heads (`gh api contents/<path>?ref=<sha> --jq .sha`) plus `additions/deletions/changedFiles`; identical blob ⇒ any prior finding persists verbatim, re-BLOCK/re-hold without re-deriving ([[approver/calibration] A "synchronize" that is a pure master-merge fixes nothing — verify blob-sha equality before assuming a re-push addressed prior findings](../learnings/1784366423621-approver-calibration-a-synchronize-that-is-a-pure-.md)). (2) For a master-merge on a PR with **hot files**, whole-file blob SHAs will differ because master independently edited those files — the authoritative check is the PR **net-diff hunks** (`gh pr diff`), not the blob; and the operative human signal is the APPROVED review's `commit.oid`, read it (don't infer the association from `submittedAt` vs `committedDate` ordering) ([[approver/challenger] master-merge synchronize: verify fix net-diff byte-identical … check the APPROVED review's commit.oid — slang#12133 R4](../learnings/1784383023678-approver-challenger-master-merge-synchronize-verif.md)). (3) A push that "addresses review" may address a **different axis** than your open gap — re-run the challenger against the SPECIFIC gap that drove the prior withhold (diff the exact code region, check a test now covers YOUR trigger shape, check the maintainer decision you were waiting on actually landed); "new test added" / "comment resolved" is about whatever the reviewer asked, which may be orthogonal ([[approver/calibration] A synchronize addressing a different review axis does not close your open gap](../learnings/1784421277721-approver-calibration-a-synchronize-addressing-a-di.md)). (4) A "Fix …" commit may patch only ONE of N near-duplicate call sites — on slangpy#1075 R7 the exact off-by-one fix (`(i+1) % BATCH_SIZE` + `device->wait()`) landed on `create_textures` while the structurally-identical sibling `create_texture_array` kept BOTH the old form AND no `device->wait()`; the inconsistency is itself a tell that the author knew the fix and didn't propagate it. Never infer "gap fixed" from a commit message or one reviewer no longer flagging it — grep the whole file for the pattern and read EVERY loop body at head, blob-SHA-comparing the reviewed file for material-vs-no-op. Calibration nuance: when a second reviewer (CodeRabbit) later corroborates Devin AND supplies the missing mechanism (per-item `generate_mips()` inside the unwaited batch loop), that falsifies a "maybe it doesn't hit the mechanism" hedge and confirms the gap is real and reachable — but a load/driver-dependent resource-exhaustion RACE that can't be reproduced still stays OPEN_GAP (a hard-fail needs a VERIFIED, ideally reproduced, defect), don't round a firmed-up gap up OR down ([[approver/challenger] Partial-fix revision: one sibling patched, the other left inconsistent — verify EACH call site, don't assume a fix propagated](../learnings/1785490973077-approver-challenger-partial-fix-revision-one-sibli.md)). The mirror on the CI side: a forwarded CI *failure* is stamped with the head it ran against — resolve its `head_sha` (`gh api check-suites/<id> --jq .head_sha`) vs your pinned settled head before treating it as live; on a fast-moving PR the author may have pushed past the failure ([[approver/calibration] forwarded-CI-failure-suite-may-be-at-superseded-head](../learnings/1784416965336-approver-calibration-forwarded-ci-failure-suite-ma.md)). And "head advanced past your verdict" is frequently just **master-catchup** (`behind_by:0`, commits are other already-merged PRs) — diff the delta and confirm the PR's OWN load-bearing files are byte-identical before spending a full re-harvest+re-Devin+CI cycle; a mid-chain design *revert* resets the verdict (evaluate the reverted-to design on its own merits) ([[approver/human-agreement] Full-chain vindication: BLOCK→fix→APPROVE held through merge; and "head advanced" is often just master-catchup](../learnings/1784420055611-approver-human-agreement-full-chain-vindication-bl.md)).

**A `synchronize` webhook can fire with an UNCHANGED head — verify `head.sha` before re-running the full procedure.** The orchestrator relayed "PR #12885 ready again (synchronize — new commits since your R2 at dd42b964)" but the head was STILL `dd42b964` (a duplicate/late webhook, a same-content force-push producing an identical SHA, or a CI re-run — the "new commits" text is not authoritative). FIRST on any re-review of a PR you already decided, fetch the authoritative head (`gh api repos/<o>/<r>/pulls/<n> --jq .head.sha`) and compare to your last decision's `commit_sha`; if unchanged, the append-only ledger already has your row (re-recording is a no-op), the signal cannot differ, and re-running harvest+Devin+critique would burn ~$1-2 for a guaranteed-identical decision — report the no-op up (the R-n verdict stands), do NOT emit a duplicate `[Approval Decision]`, and flag the spurious synchronize upstream ([a synchronize webhook can fire with an unchanged head — verify head.sha first](../learnings/1789091958980-approver-infra-a-synchronize-webhook-can-fire-with.md)).

**A title/description/upstream-reference change is not a diff change, and an upstream "fine to short-circuit" authorization is conditional — always re-read the changed FILES on every synchronize.** Two lessons from the slangpy#1135 companion-PR arc. (a) On R1–R3 the PR TITLE flipped from "for slang#12840" to "for slang#12986" (the upstream companion was re-created: fork #12840 CLOSED unmerged, superseded by same-repo #12986 MERGED, same `int`→`MatrixLayoutMode` retype), yet `base...head` was BYTE-IDENTICAL across all three heads (same 2-line retype, same blob index hashes) — the new heads were pure "Merge branch 'main'". A different upstream PR number does NOT imply a different local diff: on any title/reference change, re-read `gh pr diff` at the new head and compare blob index hashes to what you last evaluated, and independently confirm the referenced upstream PR is the same change and its state (`gh pr view <n> --json title,state,labels`) ([a companion PR's upstream-reference change is not a diff change — verify the diff, not the title](../learnings/1789112010267-approver-challenger-miss-a-companion-pr-s-upstream.md)). (b) On R4 the orchestrator explicitly said it was "fine to short-circuit if this head is another such merge" — but it was NOT: the new head "Bump SGL_SLANG_VERSION to 2026.17.1" added a THIRD changed file, `external/CMakeLists.txt` (a PROTECTED path), and DISMISSED both prior human approvals (reviewDecision→REVIEW_REQUIRED). Author-standing conditions (author_trust) persist across syncs, but per-revision conditions (no_protected_paths, tier caps, ci) can flip; a parent's "short-circuit IF another merge" is conditional — the confirmation is yours to PERFORM, not assume. The mandatory cheap first read on every synchronize is `gh pr view <pr> --json changedFiles,additions,deletions,headRefOid,reviewDecision` + `gh pr diff`, comparing the changed-file SET and blob hashes: byte-identical blobs + same file set ⇒ genuine no-op (short-circuit safe); a new/changed file, a new path, or a reviewDecision flip ⇒ run the full procedure, and headline the revision-specific clause (`no_protected_paths` for a build-file pin bump) so the ledger shows what CHANGED, recording the standing author_trust condition alongside ([a synchronize re-decide can change scope — always re-read changed FILES, even when authorized to short-circuit](../learnings/1789119022538-approver-clause-gap-a-synchronize-re-decide-can-ch.md)). Positive control for a companion PR to a merged breaking change: the Slang-side cherry-pick — `ci-slangpy-trigger-test.yml` sets `SLANGPY_CHERRY_PICK_PR`, so every Slang "SlangPy Tests" run merges the companion into SlangPy before building against master-Slang; if the breaking-change PR merged with those green, the retype is exercised green against the real change (a genuine positive control, though slangpy's OWN CI stays red-by-design until the `SGL_SLANG_VERSION` pin bumps to a release containing the enum).

## Regression & self-contradiction BLOCK catches — the strongest 🔴s need no external corroboration

A failing test the PR *itself adds* (its FileCheck oracle vs its own emitted output) is self-contradicting: either the code is wrong or the spec-of-record is wrong, and it is the strongest possible 🔴 — do NOT downgrade to ABSTAIN just because a relaxed `ci_green_on_sha` clause "passes" (clause-pass governs eligibility; CI red is challenger *evidence*, never laundered by a clause that doesn't require CI) ([[approver/challenger] PR's own new feature test failing at head is a self-contradicting RED_BUG](../learnings/1784431283917-approver-challenger-pr-s-own-new-feature-test-fail.md)). A **pre-existing untouched** test failing at the pinned head is a regression even without a master baseline when three conditions hold — the test predates the PR, the PR doesn't modify it, and the diff touches exactly the path the test exercises ([[approver/calibration] pre-existing-untouched-test-failing-at-head-is-regression-even-without-base-green](../learnings/1784420632496-approver-calibration-pre-existing-untouched-test-f.md)); when you CAN reach master, the airtight three-part proof is untouched-in-diff + present-and-failing-at-master? no + new-symbol-absent-on-master → provably green on master, red at head ([[approver/calibration] pre-existing untouched test regressing (green on master) = confirmed blast radius, not a flake](../learnings/1784431292789-approver-calibration-pre-existing-untouched-test-r.md)). A **tests-only** revision after a BLOCK can turn CI green while leaving a CI-invisible code 🔴 untouched — diff the code-file blobs; if byte-identical the revision did not address the code defect, re-verify the 🔴 stands and don't let now-green CI launder it ([[approver/challenger] tests-only revision can turn CI green without touching the buggy code — diff the code blob, don't trust green](../learnings/1784436534792-approver-challenger-tests-only-revision-can-turn-c.md)). The most dangerous variant: a test WEAKENED to green a *reproduced* failure on the exact code under review. slangpy#1075 finally added the reviewer-requested 33-texture batched-upload regression test that FAILED deterministically on Metal (both Release+Debug, real texel mismatches `-93 == 0`) while Linux/Windows passed; the very next push, titled "Make batched upload regression portable", greened CI by DELETING the mip loop so it compared only mip-0 (the directly-uploaded base data that matched) — the generated mips that actually diverged are no longer asserted. A naive "gap fixed + test added + CI green → approve" is a false-safe: the green was manufactured by narrowing the assertion to exclude exactly the thing that failed, on the path both Devin (🔴) and CodeRabbit (Major) flagged. Whenever a revision adds/edits a test on the reviewed path, diff the test itself (`gh api commits/<sha> --jq '.files[]|select(.filename|test("test"))|.patch'`) and ask: did the assertions get STRONGER (more coverage) or WEAKER (fewer levels/fields)? A `memcmp` narrowed to a subset right after that assertion failed for real is the tell — cross-reference the failing job log at the prior head, and a consistent 2-cell same-platform failure in the PR's OWN new test with real data mismatches is a reproduced regression, not a 1/12 timing flake ([[approver/false-safe] A test weakened to green a REPRODUCED failure on the code under review is a hard no-approve signal — read the test diff, not just the green](../learnings/1785493071728-approver-false-safe-a-test-weakened-to-green-a-rep.md)). Beyond the diff: a narrow-looking change to a **shared per-modifier/per-attribute dispatch arm** has blast radius = union of ALL producers of that modifier, not the syntax in the PR title — grep for every synthetic producer (compiler options like `-no-mangle`, desugaring, parser/checker stamping) before WOULD_APPROVE; a Step-0 recall-predicted-shape match confirms INTENT but says nothing about unintended collateral scope ([[approver/challenger] shared-modifier-lowering-arm-change-has-blast-radius-beyond-explicit-syntax](../learnings/1784420619202-approver-challenger-shared-modifier-lowering-arm-c.md)). A **visibility-*raising*** default change is dangerous exactly where a cap-check would newly fire — grep every reader that *compares* visibilities (`UseOfLessVisibleType`/E30604, ctor-synthesis) because a public struct with a less-visible field type that compiled at 2025 can newly hard-error at 2026; new green tests only cover shapes the author thought of ([[approver/challenger] visibility-elevation feature must probe the UseOfLessVisibleType cap-check](../learnings/1784417628061-approver-challenger-visibility-elevation-feature-m.md)). A **"simplify"/refactor** revision that preserves the headline fix can silently drop a DELIBERATE distinction the removed abstraction encoded — diff the removed type/helper's semantics, not just the target fix (an `OutputDestination{isStdout}`→plain-`String` collapse re-introduced a spurious diagnostic) ([[approver/challenger-miss] a "simplify"/refactor revision can preserve the headline fix while silently regressing a sibling correctness distinction](../learnings/1784381039011-approver-challenger-miss-a-simplify-refactor-revis.md)). And a fix that narrows behavior for a target class can create a **fresh doc 🔴** in the very `@remarks`/comment the PR added earlier — re-scan the revision's full non-code diff for prose still describing the pre-fix behavior; "old 🔴 resolved" and "no new 🔴" are two separate checks ([[approver/challenger] a fix that resolves the flagged bug can introduce a new one in its own doc/comment change](../learnings/1784440929327-approver-challenger-a-fix-that-resolves-the-flagge.md)).

## Devin's structured verdict is the only load-bearing Devin signal — prose and page-counters are not

Devin's free-text summary can confidently describe features NOT in the diff (it absorbs the PR *description's* over-claims as if verified) — load-bear only on the structured `## Bugs`/`## Flags` counts, spot-check any capability claim against `gh pr diff`, and caveat the doc when prose is refuted ([[approver/challenger] devin-prose-unreliable-trust-only-structured-verdict](../learnings/1784390121609-approver-challenger-devin-prose-unreliable-trust-o.md)). Extend the same distrust to the page's `N Flag` header counter: it can read `1 Flag` while the parsed `## Flags` section says `(none reported)` — the structured section wins (it's what the synthesis parses); reconcile or annotate rather than propagate ([[approver/challenger] Devin page "N Flag" counter can disagree with the structured flags section — trust the structured verdict](../learnings/1784417635185-approver-challenger-devin-page-n-flag-counter-can-.md)).

## Don't take a CI red at face value — resolve what it represents

`check-ci` is slang's aggregation/gating job (`jq` over the `needs` context, `exit 1` if any dependency ≠ success), so a `check-ci` failure is a downstream reflection of some other leg, never an independent signal — read its log for the named dependency and triage only the real leg; counting it double-counts one failure ([[approver/calibration] check-ci-is-aggregation-gate-not-independent-failure](../learnings/1784420509811-approver-calibration-check-ci-is-aggregation-gate-.md)). And a FileCheck failure whose "expected string" is English prose is usually a **test-authoring artifact**, not a code defect: LLVM FileCheck parses a literal `CHECK:` token *anywhere* on a line including backticked prose comments, registering a phantom directive that fires early and masks the real assertion — the fix is rewording the comment, the code was correct all along ([[approver/calibration] a stray `CHECK:` token inside a prose comment is a test-authoring failure that masquerades as a code defect](../learnings/1784436545771-approver-calibration-a-stray-check-token-inside-a-.md)).

## A behavior-inert build-warning fix clears on the affected green legs

An "initialize-to-default to silence `-Werror=maybe-uninitialized`" PR looks like it could alter behavior, but when it sits behind a `SLANG_RETURN_ON_FAIL`-style result-returning helper that writes the out-param only on the success path and the caller returns on failure before reading it, the initializer is runtime-inert — the diagnostic is a genuine `-Og` data-flow false-positive across the helper-call boundary. Verify (a) the initializer is a valid existing enum member and (b) the helper's write-gate; then green on the exact affected legs (esp. the one that failed pre-fix) is sufficient challenger evidence, because the only realistic failure is a CI-visible build break, not a silent miscompile. Classify protected paths from the changed-file list, not a misleading branch name ([[approver/calibration] uninit-var -Og -Werror fix behind result-returning helper is behavior-inert](../learnings/1784389774470-approver-calibration-uninit-var-og-werror-fix-behi.md)).

## A recalled fix-shape prediction is the strongest challenger prior — but a checklist to VERIFY, not a substitute

When Step-0 recall surfaces a prior triage of the SAME issue the PR fixes, the recalled fix prediction becomes a concrete axis-by-axis diff checklist against source at the pinned head — the match (plus clean clauses + head-current Devin + green CI legs) is what justifies WOULD_APPROVE on a thin tier; a DEVIATION from the prediction is exactly the signal recall exists to surface ([[approver/calibration] recall-predicted-fix-shape-verify-diff-matches-prediction](../learnings/1784417192285-approver-calibration-recall-predicted-fix-shape-ve.md)).

## Human-agreement calibration — split merge provenance before scoring a `pr_merged` join

The `record_human_verdict` mapping stamps APPROVED on any merge, but the *signal strength* depends on WHO merged: an **independent-maintainer APPROVED same head** (reviewer ≠ author) is STRONG agreement, whereas an **author self-merge** (or a merge with only bot+author COMMENTED) is WEAK — it attests "the author was confident," not "an independent reviewer weighed your concern," especially when the concern was CI-invisible and shadow-mode never posted it. Pull `mergedBy` + `reviewDecision` + `reviews[].state/commit.oid`, never just `merged=true` ([[approver/human-agreement] author self-merge with no independent review is a weak agreement signal](../learnings/1784392147522-approver-human-agreement-author-self-merge-with-no.md)). This corrected an over-conservative read of slang#12147: the first pass framed the self-merge as evidence the R5 ABSTAIN was "over-conservative," but a self-merge does NOT refute a withhold — do not "learn" to lower your bar from one ([[approver/human-agreement] CORRECTION to slang#12147 calibration: it was an AUTHOR SELF-MERGE (weak signal)](../learnings/1784386500014-approver-human-agreement-correction-to-slang-12147.md)); the calibration point that stands is to grade a false-**POSITIVE** (over-rejection) by TRIGGER-LIKELIHOOD × BLAST-RADIUS, reserving ABSTAIN for plausible-everyday-trigger false-positives or any false-**NEGATIVE** ([[approver/human-disagreement] ABSTAIN over a pathological-only false-positive diagnostic; maintainer merged with it](../learnings/1784386401932-approver-human-disagreement-abstain-over-a-patholo.md), [[approver/human-agreement] author self-merge is a WEAK 'APPROVED' signal — a shadow-mode ABSTAIN … is vindicated (not refuted)](../learnings/1784386435249-approver-human-agreement-author-self-merge-is-a-we.md)). The strong-agreement archetype landed on slang#12133: WOULD_APPROVE @R4 == merged head, jkwak-work gave an explicit APPROVED and merged the same SHA — a 4-revision chain of known-shape deltas whose prior verified safety carried forward every time ([[approver/human-agreement] slang#12133 MERGED-agreement vindicated across 4 revisions](../learnings/1784391254624-approver-human-agreement-slang-12133-merged-agreem.md)). The safe-direction DISAGREEMENT archetype landed on slang#11471: a maintainer merged over two shadow BLOCK 🔴s (an example-only assert + an untrusted-input-only DoS) — vindicated on correctness (the eventual production review confirmed both verbatim), the disagreement was on blocking-*threshold* (blast-radius/code-location/threat-model), not correctness; annotate that severity axis so the join reads as expected, don't soften the BLOCK ([[approver/human-disagreement] Maintainer merged over a production-review 🔴 (example-only assert + untrusted-input DoS)](../learnings/1784391272446-approver-human-disagreement-maintainer-merged-over.md)).

## Don't clear a 🟡 gap without reading the exact precondition / scope / path

Four DECISION_REVIEW/challenger catches on one theme — a gap looked clearable until the *exact* condition was read:

- **Reused a `*Flat*`/`*Simple*` helper at a new call site → verify it establishes the precondition the way existing callers do.** slang#12885 reused `fixFieldSemanticsOfFlatStruct` (walks only top-level `getFields()`) on lifted mesh output structs, but sibling callers run `maybeFlattenNestedStructs(...)` first while the new mesh calls (`:4721`/`:4754`) invoke the flat-only helper directly on a possibly-nested struct — so a nested indexed user semantic stays un-canonicalized on the mesh side (the PR's own bug class, for nested structs). Grep all call sites and diff what each does BEFORE the call; a new site skipping a shared setup step is an asymmetry → likely gap. NOT a regression (pre-PR was un-canonicalized both ways) → OPEN_GAP, not BLOCK ([reused flat-only helper at a new call site — verify it flattens first](../learnings/1789078899092-approver-challenger-pattern-reused-flat-only-helpe.md)).
- **A limitation documented for one target does NOT transfer to the target under review.** On the same PR a nested-mesh gap was cleared as "`_createLegalVaryingVal` documents a missing varying-struct case" — but that comment scopes the limitation to "the targets that require this pass (currently CPU and CUDA)", says nothing about Metal, so the nested Metal case is reachable → OPEN_GAP. Read the exact scope of an unsupported-ness claim against the source comment, not a deepwiki paraphrase (which dropped the CPU/CUDA scope) ([don't clear a Metal nested-struct gap via _createLegalVaryingVal — its limitation is CPU/CUDA-only](../learnings/1789078910689-approver-critique-mustfix-don-t-clear-a-metal-nest.md)).
- **`attribute_syntax` `///` doc comments are public-facing output, not cosmetic.** `DocMarkdownWriter::writeAttribute` renders an attribute's `///` markup into the public attribute-reference docs, one page per `AttributeDecl` — so a new attribute/alias (slang#12907 `[OutputTopology]`) with a stage-inaccurate comment (`triangle_cw`/`triangle_ccw`, rejected for `Stage::Mesh`) generates a NEW user-facing page with wrong info; a "verbatim copy of an existing comment" mitigation doesn't neutralize it (the `+` lines are newly authored). Verify a doc comment against the attribute's real validation before clearing → OPEN_GAP ([attribute_syntax doc comments are public-facing, not cosmetic](../learnings/1789079662110-approver-critique-mustfix-attribute-syntax-doc-com.md)).
- **A "both orders converge" equivalence often holds only for 32-bit types.** On slang#12884 (SV_InstanceID on Metal) an order-sensitivity gap was cleared as "both orders converge to `int(i)-int(base)`" — but DECISION_REVIEW flagged the equivalence holds ONLY for 32-bit; check front-end narrow-integer admissibility before clearing an SV-legalization order gap ([SV legalization order-gaps: check front-end narrow-integer admissibility before clearing](../learnings/1789087706199-approver-critique-mustfix-sv-legalization-order-ga.md)).

## Contradictions / supersessions

- A verified 🔴 is NEVER downgraded to WOULD_APPROVE by an author self-merge — a self-merge is a WEAK signal, not a refutation. This supersedes the "maintainer merged ⇒ my ABSTAIN was over-conservative" framing of the slang#12147 pathological-false-positive read.
- "Green CI ⇒ safe" holds ONLY for CI-catchable failure classes (build breaks); for codegen/logic/miscompile PRs green CI is blind, and combined-status is non-causal in both directions. CI red is challenger *evidence*, never laundered by a clause that doesn't require CI green.
- A recall-predicted fix-shape match confirms INTENT, not collateral scope — it is a checklist to verify, never a substitute for enumerating the blast radius.
