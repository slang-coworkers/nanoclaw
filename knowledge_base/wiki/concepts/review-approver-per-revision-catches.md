# PR-Approver: Per-Revision Discipline — Synchronize Classification, Regression Catches & Merge Provenance

The incremental discipline of re-evaluating each `synchronize`: classify the delta before re-litigating, catch regressions and self-contradictions that CI-red carries as *evidence* (not a clause), read Devin's structured verdict rather than its prose, resolve what a CI-red actually represents, and split merge provenance before scoring a `pr_merged` join. Drawn from the 2026-07-18/19 approver session and its calibration corrections.

## TL;DR

- **A `synchronize` is not automatically a fix — classify the delta first.** Fetch `head.sha` (webhooks fire with an unchanged head). A pure `Merge branch 'master'` changes nothing in the PR's own content (verify blob-sha; for hot files use the PR net-diff hunks). A push that "addresses review" may address a *different axis* than your open gap. A "Fix …" commit may patch only ONE of N near-duplicate sites — grep every loop body at head.
- **Always re-read the changed FILES on every synchronize, even when told to short-circuit.** A title/upstream-reference change is not a diff change, and a new head can add a protected path or dismiss approvals. Author-standing conditions persist across syncs; per-revision conditions (`no_protected_paths`, tier caps, CI) can flip.
- **The strongest 🔴s need no external corroboration.** A PR's own new test failing at head is self-contradicting; a pre-existing untouched test failing at head is a regression (three conditions, or the three-part green-on-master proof). CI red is challenger *evidence*, never laundered by a clause that doesn't require CI.
- **A test WEAKENED to green a REPRODUCED failure on the code under review is a hard no-approve.** Diff the test itself and ask: did assertions get STRONGER or WEAKER? A tests-only revision can green CI while the code 🔴 stands.
- **Blast radius follows the mechanism, not the PR title.** A shared modifier-lowering arm, a visibility-*raising* default, a "simplify"/refactor that drops a deliberate distinction, or a fix that creates a fresh doc 🔴 in its own `@remarks` — each widens beyond the explicit syntax.
- **Don't clear a 🟡 gap without reading the exact precondition, scope, or path** — a reused flat-only helper, a limitation scoped to other targets, a public-facing `///` attribute doc, a 32-bit-only equivalence.
- **Devin's structured verdict is the only load-bearing Devin signal** — prose and the "N Flag" page counter are not; the structured `## Bugs`/`## Flags` section wins.
- **A CI red is not automatically an independent failure** — `check-ci` is an aggregation gate; a stray `CHECK:` token in a prose comment is a test-authoring artifact; a forwarded failure may be at a superseded head.
- **Split merge provenance before scoring a join.** An independent-maintainer APPROVED same head is STRONG agreement; an author self-merge is WEAK — it attests confidence, not independent review, and does NOT refute a withhold. Pull `mergedBy` + `reviewDecision` + `reviews[].state/commit.oid/submittedAt`.

## Classify the synchronize delta before re-litigating

**Verify the head first.** A `synchronize` webhook can fire with an UNCHANGED head: the orchestrator relayed "PR #12885 ready again (new commits since your R2 at dd42b964)" but the head was still `dd42b964` (a duplicate/late webhook, a same-content force-push, or a CI re-run — the "new commits" text is not authoritative). On any re-review fetch `gh api repos/<o>/<r>/pulls/<n> --jq .head.sha` and compare to your last decision's `commit_sha`. If unchanged, the append-only ledger already holds your row and the signal cannot differ; re-running harvest+Devin+critique burns ~$1-2 for an identical decision. Report the no-op up (the R-n verdict stands), emit no duplicate `[Approval Decision]`, and flag the spurious synchronize ([a synchronize webhook can fire with an unchanged head — verify head.sha first](../learnings/1789091958980-approver-infra-a-synchronize-webhook-can-fire-with.md)).

**Classify what the new head changed.**
1. A pure `Merge branch 'master'` changes nothing in the PR's own content. Compare the flagged files' git **blob-sha** across heads (`gh api contents/<path>?ref=<sha> --jq .sha`) plus `additions/deletions/changedFiles`; an identical blob means any prior finding persists verbatim — re-BLOCK/re-hold without re-deriving ([a pure master-merge synchronize fixes nothing](../learnings/1784366423621-approver-calibration-a-synchronize-that-is-a-pure-.md)).
2. On a PR with **hot files**, master independently edits them, so whole-file blobs differ; the authoritative check is the PR **net-diff hunks** (`gh pr diff`). The operative human signal is the APPROVED review's `commit.oid` — read it rather than inferring it from `submittedAt` vs `committedDate` ([master-merge synchronize: verify fix net-diff byte-identical; check the APPROVED review's commit.oid — slang#12133 R4](../learnings/1784383023678-approver-challenger-master-merge-synchronize-verif.md)).
3. A push that "addresses review" may address a **different axis** than your open gap. Re-run the challenger against the SPECIFIC gap that drove the withhold: diff that code region, check a test now covers YOUR trigger shape, check the maintainer decision you awaited actually landed. "New test added"/"comment resolved" is about whatever that reviewer asked ([a synchronize addressing a different review axis does not close your open gap](../learnings/1784421277721-approver-calibration-a-synchronize-addressing-a-di.md)).
4. A "Fix …" commit may patch only ONE of N near-duplicate sites. On slangpy#1075 R7 the off-by-one fix (`(i+1) % BATCH_SIZE` + `device->wait()`) landed on `create_textures` while the identical sibling `create_texture_array` kept the old form and no `device->wait()` — the inconsistency itself shows the author knew the fix and didn't propagate it. Never infer "gap fixed" from a commit message or one reviewer going quiet; grep the file for the pattern and read EVERY loop body at head. When a second reviewer (CodeRabbit) later corroborates Devin and supplies the mechanism (per-item `generate_mips()` inside the unwaited batch loop), the gap is confirmed real and reachable — but a load/driver-dependent race that can't be reproduced stays OPEN_GAP (a hard-fail needs a verified, ideally reproduced, defect); round a firmed-up gap neither up nor down ([partial-fix revision: one sibling patched, the other left inconsistent](../learnings/1785490973077-approver-challenger-partial-fix-revision-one-sibli.md)).

**CI and catch-up deltas.** A forwarded CI *failure* is stamped with the head it ran against — resolve `gh api check-suites/<id> --jq .head_sha` against your pinned head before treating it as live; on a fast-moving PR the author may have pushed past it ([forwarded CI-failure suite may be at a superseded head](../learnings/1784416965336-approver-calibration-forwarded-ci-failure-suite-ma.md)). "Head advanced past your verdict" is often just **master-catchup** (`behind_by:0`, the commits are other merged PRs): confirm the PR's OWN load-bearing files are byte-identical before a full re-harvest+re-Devin+CI cycle. A mid-chain design *revert* resets the verdict — evaluate the reverted-to design on its merits ([full-chain vindication BLOCK→fix→APPROVE; "head advanced" is often master-catchup](../learnings/1784420055611-approver-human-agreement-full-chain-vindication-bl.md)).

**A title/reference change is not a diff change, and a "fine to short-circuit" authorization is conditional.** On slangpy#1135 R1–R3 the title flipped from "for slang#12840" to "for slang#12986" (fork #12840 closed unmerged, superseded by same-repo #12986 merged, same `int`→`MatrixLayoutMode` retype), yet `base...head` stayed byte-identical — the new heads were pure "Merge branch 'main'". On a reference change, re-read `gh pr diff` and compare blob index hashes, and independently confirm the referenced upstream PR is the same change and its state (`gh pr view <n> --json title,state,labels`) ([a companion PR's upstream-reference change is not a diff change](../learnings/1789112010267-approver-challenger-miss-a-companion-pr-s-upstream.md)). On R4 the orchestrator said it was "fine to short-circuit if this head is another such merge" — but the head "Bump SGL_SLANG_VERSION to 2026.17.1" added a third file, the PROTECTED `external/CMakeLists.txt`, and dismissed both human approvals (reviewDecision→REVIEW_REQUIRED). Author-standing conditions (`author_trust`) persist across syncs, but per-revision conditions (`no_protected_paths`, tier caps, `ci`) can flip, so a parent's "short-circuit IF another merge" is a confirmation for you to perform, not assume. The mandatory cheap first read on every synchronize is `gh pr view <pr> --json changedFiles,additions,deletions,headRefOid,reviewDecision` + `gh pr diff`, comparing the changed-file SET and blob hashes: same set and identical blobs ⇒ genuine no-op; a new file/path or a reviewDecision flip ⇒ the full procedure, headlining the revision-specific clause (`no_protected_paths` for a pin bump) beside the standing `author_trust` condition ([a synchronize re-decide can change scope — always re-read changed FILES](../learnings/1789119022538-approver-clause-gap-a-synchronize-re-decide-can-ch.md)). Positive control for a companion PR to a merged breaking change: `ci-slangpy-trigger-test.yml` sets `SLANGPY_CHERRY_PICK_PR`, so every Slang "SlangPy Tests" run merges the companion into SlangPy before building against master-Slang. If the breaking change merged with those green, the retype is exercised against the real change, though slangpy's own CI stays red-by-design until `SGL_SLANG_VERSION` pins a release containing the enum.

## Regression & self-contradiction BLOCK catches

**Self-contradiction.** A failing test the PR *itself adds* (its FileCheck oracle vs its own output) means the code or the spec-of-record is wrong — the strongest possible 🔴. Do not downgrade to ABSTAIN because a relaxed `ci_green_on_sha` clause "passes": clause-pass governs eligibility; CI red is challenger evidence ([PR's own new feature test failing at head is a self-contradicting RED_BUG](../learnings/1784431283917-approver-challenger-pr-s-own-new-feature-test-fail.md)).

**Regression of an untouched test.** A pre-existing test failing at the pinned head is a regression even without a master baseline when it predates the PR, the PR doesn't modify it, and the diff touches exactly the path it exercises ([pre-existing untouched test failing at head is a regression even without base green](../learnings/1784420632496-approver-calibration-pre-existing-untouched-test-f.md)). With master reachable, the airtight proof is untouched-in-diff + not failing at master + new symbol absent on master → green on master, red at head ([pre-existing untouched test green on master = confirmed blast radius, not a flake](../learnings/1784431292789-approver-calibration-pre-existing-untouched-test-r.md)).

**Greened CI that didn't fix the code.** A **tests-only** revision after a BLOCK can turn CI green while a CI-invisible code 🔴 stands — if the code-file blobs are byte-identical the defect is unaddressed; don't let green launder it ([tests-only revision can turn CI green without touching the buggy code](../learnings/1784436534792-approver-challenger-tests-only-revision-can-turn-c.md)). Worse is a test WEAKENED to green a *reproduced* failure. slangpy#1075 added the reviewer-requested 33-texture batched-upload regression test, which failed deterministically on Metal (Release and Debug, real texel mismatches `-93 == 0`) while Linux/Windows passed. The next push, "Make batched upload regression portable", greened CI by deleting the mip loop so only mip-0 (the directly uploaded data) was compared — the generated mips that diverged are no longer asserted, on the path Devin (🔴) and CodeRabbit (Major) both flagged. Whenever a revision edits a test on the reviewed path, diff the test (`gh api commits/<sha> --jq '.files[]|select(.filename|test("test"))|.patch'`) and ask whether assertions got stronger or weaker; a `memcmp` narrowed right after it failed for real is the tell — cross-reference the failing job log at the prior head. A consistent 2-cell same-platform failure in the PR's own new test with real data mismatches is a reproduced regression, not a 1/12 timing flake ([a test weakened to green a REPRODUCED failure is a hard no-approve](../learnings/1785493071728-approver-false-safe-a-test-weakened-to-green-a-rep.md)).

**Blast radius beyond the diff.**
- A narrow change to a **shared per-modifier/per-attribute dispatch arm** has blast radius = every producer of that modifier — grep synthetic producers (`-no-mangle`, desugaring, parser/checker stamping) before WOULD_APPROVE; a recall-predicted-shape match confirms intent, not collateral scope ([shared modifier-lowering arm change has blast radius beyond explicit syntax](../learnings/1784420619202-approver-challenger-shared-modifier-lowering-arm-c.md)).
- A **visibility-*raising*** default is dangerous exactly where a cap-check newly fires: grep every reader that compares visibilities (`UseOfLessVisibleType`/E30604, ctor synthesis) — a public struct with a less-visible field type valid at 2025 can hard-error at 2026, and new green tests cover only shapes the author imagined ([visibility-elevation feature must probe the UseOfLessVisibleType cap-check](../learnings/1784417628061-approver-challenger-visibility-elevation-feature-m.md)).
- A **"simplify"/refactor** that keeps the headline fix can drop a deliberate distinction the removed abstraction encoded — diff the removed helper's semantics (an `OutputDestination{isStdout}`→plain-`String` collapse re-introduced a spurious diagnostic) ([a "simplify"/refactor revision can silently regress a sibling distinction](../learnings/1784381039011-approver-challenger-miss-a-simplify-refactor-revis.md)).
- A fix that narrows behavior can create a **fresh doc 🔴** in the `@remarks` the PR added earlier — re-scan the full non-code diff for prose describing pre-fix behavior; "old 🔴 resolved" and "no new 🔴" are separate checks ([a fix that resolves the flagged bug can introduce a new one in its own doc change](../learnings/1784440929327-approver-challenger-a-fix-that-resolves-the-flagge.md)).

## Don't clear a 🟡 gap without reading the exact precondition / scope / path

- **A reused `*Flat*`/`*Simple*` helper at a new call site must get its precondition the way existing callers do.** slang#12885 reused `fixFieldSemanticsOfFlatStruct` (top-level `getFields()` only) on lifted mesh output structs; sibling callers run `maybeFlattenNestedStructs(...)` first, but the new mesh calls (`:4721`/`:4754`) pass a possibly-nested struct, leaving a nested indexed semantic un-canonicalized. Grep all call sites and diff what each does before the call; a new site skipping a shared setup step is an asymmetry and a likely gap. Not a regression (pre-PR was un-canonicalized both ways) → OPEN_GAP, not BLOCK ([reused flat-only helper at a new call site — verify it flattens first](../learnings/1789078899092-approver-challenger-pattern-reused-flat-only-helpe.md)).
- **A limitation documented for one target does not transfer.** On the same PR a nested-mesh gap was cleared because `_createLegalVaryingVal` "documents a missing varying-struct case" — but the comment scopes it to "the targets that require this pass (currently CPU and CUDA)"; the nested Metal case is reachable → OPEN_GAP. Read the source comment's exact scope, not a deepwiki paraphrase ([don't clear a Metal nested-struct gap via _createLegalVaryingVal](../learnings/1789078910689-approver-critique-mustfix-don-t-clear-a-metal-nest.md)).
- **`attribute_syntax` `///` doc comments are public output.** `DocMarkdownWriter::writeAttribute` renders them into one attribute-reference page per `AttributeDecl`, so slang#12907's new `[OutputTopology]` with stage-inaccurate `triangle_cw`/`triangle_ccw` (rejected for `Stage::Mesh`) ships wrong user-facing docs; "verbatim copy of an existing comment" doesn't neutralize newly authored `+` lines. Verify against the attribute's real validation → OPEN_GAP ([attribute_syntax doc comments are public-facing, not cosmetic](../learnings/1789079662110-approver-critique-mustfix-attribute-syntax-doc-com.md)).
- **"Both orders converge" often holds only for 32-bit types.** On slang#12884 (SV_InstanceID on Metal) an order gap was cleared as "both converge to `int(i)-int(base)`"; that holds only for 32-bit — check front-end narrow-integer admissibility first ([SV legalization order-gaps: check narrow-integer admissibility](../learnings/1789087706199-approver-critique-mustfix-sv-legalization-order-ga.md)).

## Reading the evidence: Devin, CI reds, inert fixes, recall

**Devin.** Devin's free-text summary can confidently describe features NOT in the diff (it absorbs the PR description's over-claims); load-bear only on the structured `## Bugs`/`## Flags` counts, spot-check capability claims against `gh pr diff`, and caveat refuted prose ([Devin prose unreliable — trust only the structured verdict](../learnings/1784390121609-approver-challenger-devin-prose-unreliable-trust-o.md)). The page's `N Flag` header can read `1 Flag` while the parsed `## Flags` says `(none reported)` — the structured section wins ([Devin "N Flag" counter can disagree with the structured flags section](../learnings/1784417635185-approver-challenger-devin-page-n-flag-counter-can-.md)).

**CI reds.** `check-ci` is slang's aggregation job (`jq` over `needs`, `exit 1` if any dependency ≠ success), so its failure only reflects another leg — read its log for the named dependency; counting it double-counts ([check-ci is an aggregation gate, not an independent failure](../learnings/1784420509811-approver-calibration-check-ci-is-aggregation-gate-.md)). A FileCheck failure whose "expected string" is English prose is usually a test-authoring artifact: FileCheck parses a literal `CHECK:` token anywhere on a line, including backticked prose comments, so a phantom directive fires early and masks the real assertion; reword the comment ([a stray `CHECK:` token in a prose comment masquerades as a code defect](../learnings/1784436545771-approver-calibration-a-stray-check-token-inside-a-.md)).

**Behavior-inert warning fixes.** An "initialize to silence `-Werror=maybe-uninitialized`" change behind a `SLANG_RETURN_ON_FAIL`-style helper that writes the out-param only on success (the caller returns before reading it on failure) is runtime-inert — a genuine `-Og` data-flow false positive. Verify the initializer is a valid enum member and the helper's write-gate; then green on the affected legs (esp. the one that failed pre-fix) suffices, because the only realistic failure is a build break. Classify protected paths from the changed-file list, not the branch name ([uninit-var -Og -Werror fix behind a result-returning helper is behavior-inert](../learnings/1784389774470-approver-calibration-uninit-var-og-werror-fix-behi.md)).

**Recall.** When Step-0 recall surfaces a prior triage of the issue the PR fixes, the predicted fix shape becomes an axis-by-axis checklist against source at the pinned head; a match (plus clean clauses, head-current Devin, green legs) justifies WOULD_APPROVE on a thin tier, and a deviation is exactly the signal recall exists to surface ([recall-predicted fix shape: verify the diff matches](../learnings/1784417192285-approver-calibration-recall-predicted-fix-shape-ve.md)).

## Human-agreement calibration — split merge provenance before scoring a `pr_merged` join

`record_human_verdict` stamps APPROVED on any merge, but strength depends on who merged: an **independent-maintainer APPROVED same head** is STRONG agreement; an **author self-merge** (or only bot+author COMMENTED) is WEAK — it attests the author's confidence, not that anyone weighed your concern, especially a CI-invisible one shadow mode never posted. Pull `mergedBy` + `reviewDecision` + `reviews[].state/commit.oid`, never just `merged=true` ([author self-merge with no independent review is a weak agreement signal](../learnings/1784392147522-approver-human-agreement-author-self-merge-with-no.md)). A matching `commit.oid` alone is not "same head": when a base-branch merge doesn't dismiss an approval, GitHub rewrites the review's commit to the new head (#13849), so also require `submittedAt` later than the head's committer date, and score a carried-forward approval as approval of the earlier diff ([the review commit field can move forward to a later head](../learnings/1793176871441-github-review-commit-field-can-move-forward-to-a-l.md)).

On slang#12147 the first pass read a self-merge as evidence the R5 ABSTAIN was over-conservative; a self-merge does NOT refute a withhold, so don't lower your bar from one ([CORRECTION: slang#12147 was an author self-merge](../learnings/1784386500014-approver-human-agreement-correction-to-slang-12147.md)). The standing point: grade a false-**positive** (over-rejection) by trigger-likelihood × blast-radius, reserving ABSTAIN for plausible-everyday-trigger false positives or any false-**negative** ([ABSTAIN over a pathological-only false-positive diagnostic](../learnings/1784386401932-approver-human-disagreement-abstain-over-a-patholo.md), [author self-merge is a WEAK APPROVED — a shadow ABSTAIN is vindicated, not refuted](../learnings/1784386435249-approver-human-agreement-author-self-merge-is-a-we.md)). Strong-agreement archetype: slang#12133, WOULD_APPROVE @R4 == merged head, jkwak-work APPROVED and merged the same SHA after a 4-revision chain of known-shape deltas whose verified safety carried forward each time ([slang#12133 merged-agreement vindicated across 4 revisions](../learnings/1784391254624-approver-human-agreement-slang-12133-merged-agreem.md)). Safe-direction disagreement archetype: slang#11471, a maintainer merged over two shadow BLOCK 🔴s (an example-only assert, an untrusted-input-only DoS); production review later confirmed both verbatim, so the disagreement was on blocking threshold (blast radius, code location, threat model), not correctness — annotate that axis, don't soften the BLOCK ([maintainer merged over a production-review 🔴](../learnings/1784391272446-approver-human-disagreement-maintainer-merged-over.md)).

## Contradictions / supersessions

- A verified 🔴 is NEVER downgraded to WOULD_APPROVE by an author self-merge — a self-merge is WEAK, not a refutation. This supersedes the "maintainer merged ⇒ my ABSTAIN was over-conservative" reading of slang#12147.
- "Green CI ⇒ safe" holds ONLY for CI-catchable failure classes (build breaks); for codegen/logic/miscompile PRs green CI is blind, and combined status is non-causal in both directions. CI red is challenger evidence, never laundered by a clause that doesn't require CI green.
- A recall-predicted fix-shape match confirms INTENT, not collateral scope.
