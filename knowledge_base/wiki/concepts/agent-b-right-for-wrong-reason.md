## TL;DR

- **A conclusion surviving every revision is not evidence its current explanation is sound.** A reader checks a claim against the outcome, sees agreement, and stops — so a correct verdict protects a wrong mechanism indefinitely. Audit the mechanism each time it *changes*, not only when the verdict changes.
- **The load-bearing condition in a compound guard is routinely not the one that looks safety-critical.** Enumerate what each condition actually excludes, find the live test that breaks, and read its severity. Intuition is not evidence.
- **Relocating a condition can silently swap the OBJECT.** Same method name on a different receiver (`TargetProgram` vs `TargetRequest`) is a different measurement. Audit the condition's *operands*, not the flag's consumers — a complete answer to the wrong question is indistinguishable from safety.
- **A test passing for the WRONG REASON is worse than a vacuous one** — every routine check comes back green. Add a *discriminating control*: vary the property the test claims is load-bearing and require the outcome to change. Observing the outcome is not observing the mechanism.
- **A rule that fits the symptom is not a diagnosis.** A true general rule ("a rebase invalidates every `file:line`") applied to the wrong case produces a confident false accusation. Check the cheap concrete alternative (a constant offset) first.
- **A delegate reads HEAD by default** — any "the PR fails to handle X" claim must be re-checked against the diff, and is refuted for free if X's file is in the PR's changed-file list.
- **Cite the enclosing function, not just the line**, and read the lines *around* a citation — an adjacent maintainer comment converts a measurement into a design fact.
- **Record dispositions per claim, not per candidate** — a bundled "correct observation + incorrect remedy" logged as "Applied" loses the declined half, which is exactly what gets re-litigated.

## Being right for the wrong reason

**A conclusion surviving every revision is not evidence the current explanation is sound.** On one PR the verdict (*core-module `functype` uses don't trip the new diagnostic*) was correct throughout while its explanation was wrong three times, each proposed as a correction of the last — because every revision preserved the verdict, two bad mechanisms passed review. **Audit the mechanism each time it changes.** The most transferable move from that exchange: the bad mechanism was found only by asking the reviewer to *attack* the claim ("I want this attacked, not confirmed") — **the shape of the review request determines which errors are findable**; a confirm-shaped request would have approved it. Same PR produced the sister lesson that **a rule fitting the symptom is not a diagnosis**: a stale-line-number accusation reasoned from a true rule (a rebase invalidates every `file:line`) when both numbers were correct — one was the line *in the file* (357), the other *in the diff* (145), a constant 208 offset sitting right there to check. A bare `:NNN` is meaningless without naming diff-vs-file (and which diff, since `git diff` output carries header lines a UI may not count); in a PR body, cite the **file**. [A conclusion surviving every revision is not evidence its current explanation is sound — and a rule that fits the symptom is not a diagnosis](wiki/learnings/1786083921780-a-conclusion-surviving-every-revision-is-not-evide.md)

**A false counter-example holds up the wrong conclusion — worse than a missing one**, because it actively props up the wrong answer and draws credibility from "having been checked once." A "working spelling" reporting `9.0`/`6.0`, treated as the one datum contradicting an emerging conclusion, traced to a getter test with no existential type argument anywhere — never a counter-example. It survived three agents and two dispatches; what killed it was someone going to *look at the artifact* rather than restating memory. The property that made the worst instances dangerous: **they returned a plausible, reassuring answer rather than an error** (`--is-ancestor` on a shallow clone; a stale binary exiting 0; a probe exiting 0 because DCE removed the call). Two operational rules that caught things: before a finding leaves your hands, ask *what is the strongest thing a PASS here could be hiding* — if the answer is "the stage I care about never ran," the pass isn't evidence (a probe exited 0 with zero `diffPair` in the generated code — dead-coded; re-running with the value consumed made the conclusion evidence). And **a type error is not a clean pass** — `E30019`/`E99997` before reaching the pass under test is inconclusive; `E99997` is a *wrapper* for any internal error, so the message text is the identity, and deduping on the code makes distinct defects look like one regression. Narrow the trigger before filing (a *concrete-signature* static requirement is diagnosed correctly; the real trigger needed an associated type — reproducing from a pure user interface lifted it out of autodiff so a maintainer wouldn't deprioritize it). [A false counter-example holds up the wrong conclusion — and the worst instruments answer confidently about a scope you never checked](wiki/learnings/1786194845056-a-false-counter-example-holds-up-the-wrong-conclus.md)

## Guards and gates: enumerate what each condition excludes

**The load-bearing condition in a compound guard is routinely not the one that looks safety-critical.** For `isKhronosTarget(target) && stage == Stage::Fragment && isSVTargetSemantic(v)`, the prior was `isKhronosTarget` (documented as "a perfect gate"); measured, `Stage::Fragment` was load-bearing and `isKhronosTarget` *cannot* save the breaking case because SPIR-V is itself a Khronos target — that gate is true exactly when the damage occurs. Run the check: enumerate what each condition excludes separately (a condition excluding nothing reachable is decoration; one uniquely excluding one shape is load-bearing); look upstream for the real classifier (a guard often re-filters something filtered three functions away — *that* duplicate is droppable); **name the failing test, then read its severity** (`err(` vs `warning(` — the *adjacent* diagnostic was a warning, so glancing at the neighbour supports the wrong claim; adjacency is not evidence); treat an inner guard whose removal *manufactures* the state it tests (a `findOrAddResourceInfo`-style call) as never cosmetic. Measuring buys a third option neither side proposed: keep both gates but replace the exact-string match with the generic prefix test — killing the special case the maintainer objected to while keeping the semantics. [The load-bearing condition in a compound guard is routinely not the one that looks safety-critical](wiki/learnings/1786024286724-the-load-bearing-condition-in-a-compound-guard-is-.md)

**Relocating a gate can silently swap the OBJECT.** Moving `!target->getOptionSet().shouldPerformMinimumOptimizations()` from a call site into a pass kept the method name and option name but changed the receiver — `TargetProgram`'s option set is `overrideWith`/`inheritFrom`-layered, so an option supplied via `linkWithOptions` is visible on `TargetProgram` and invisible on `TargetRequest`, and the pass's diagnostics would fire for API callers no `.slang` test directive can reach. The author enumerated the five gated sites twice and a reviewer confirmed the count — **both right about which checks are gated while the gate read the wrong object; a complete answer to the wrong question is indistinguishable from safety.** When you relocate a condition, the population to audit is **the condition's operands**, not the flag's consumers: diff the *receiver*, not just the predicate. An "effective settings" object layered over a base is the canonical trap (the base is reachable from the derived object, so the wrong choice compiles and is usually correct, diverging only on the untested path). Fix at the signature, and cover the divergent path with a CPU-only unit test even when no directive reaches it. Also: a **fresh** reviewer thread found this after a long thread had approved the change twice — a long converging review shares its blind spots rather than accumulating independence. [Relocating a gate: substituting an accessor can silently swap the OBJECT](wiki/learnings/1786114268925-relocating-a-gate-substituting-an-accessor-can-sil.md)

## Tests: outcome is not mechanism

**A test passing for the WRONG REASON is worse than a vacuous one** — every routine check comes back green. A companion test claimed to pin a *second* code path (existential legalization) reaching a shared arm; `slang-test` passed, the direct `slangc` run gave the right diagnostic at the right line, mutation-testing the message text failed the test (not vacuous), removing `non-exhaustive` still passed (nothing suppressed) — **and it still didn't test what it claimed**, because on `-target cuda` the existential-legalization context is never constructed and the empty `struct Impl` reached the arm via the *same* empty-type path as its sibling. The discriminator: vary the claimed-load-bearing property — `Impl WITH a data member` on cuda → exit 0 (claim refuted); `Impl EMPTY` → the diagnostic (passes via emptiness). **Mutation testing proves the assertion is connected to the output, not that the input exercises the intended mechanism; observing the outcome is not observing the mechanism.** For any test whose value depends on *which* path produced the result, add a discriminating control: a variant removing the claimed cause that must produce a different outcome. And check the obvious repair works before proposing it (retargeting to `spirv` failed earlier with a different error — the shape needed rethinking, not a flag change). [A test passing for the WRONG REASON is worse than a vacuous one — every routine check comes back green](wiki/learnings/1786217652424-a-test-passing-for-the-wrong-reason-is-worse-than-.md)

## Delegation reads the base tree

**A delegate's finding about a PR must be checked against the DIFF, not the base — it reads HEAD by default.** A subagent sent to explore a compiler at a local clone (master) returned a confident "second, independent bug in the PR" — but the PR's diff contained exactly the one-line addition the agent said was missing; it had grepped the file at HEAD, where the case is legitimately absent because the whole opcode is new in the PR. Findings about *existing* code are fine; findings about *what the change omits* are the dangerous class, because the agent cannot see the change. **The tell is cheap: if a delegate says the PR ignores file F, check whether F is in the PR's changed-file list first** — a one-line hunk in the file being called unhandled is a contradiction visible without reading anything. Mitigation: pass the diff into the delegate's prompt, or treat every "the PR fails to..." claim as unverified. [A delegate's finding about a PR must be checked against the DIFF, not the base — it will read HEAD by default](wiki/learnings/1786085513564-a-delegate-s-finding-about-a-pr-must-be-checked-ag.md)

## Citations locate evidence but don't scope it

**Cite the enclosing function, not just the line.** Reporting `slang-check-expr.cpp:3849` (a `// TODO` where a value-shapedness check belongs) is accurate but under-informative; naming it inside `SemanticsVisitor::CheckExpr` (the general expression-check entry point) yields both a stronger claim (the TODO is the last statement before `return`, so the step is *entirely absent*, not partial) and a measurable scope caution (`grep -c 'CheckExpr('` = 25 call sites, so implementing it changes what every expression context accepts — which lets a report offer a narrow alternative without prescribing either). A `file:line` locates evidence but does not scope it: run `awk` for the enclosing function, then count its call sites; the line proves the finding, the function and its fan-out tell the reader what fixing it costs, and reviewers act on the second. Naming the function is also what lets you say *which* fix would be wrong (the obvious ambiguity-check patch cannot fire by construction). [Cite the enclosing function, not just the line — a bare line number hides the blast radius](wiki/learnings/1786183366163-cite-the-enclosing-function-not-just-the-line-a-ba.md)

**Read the lines AROUND a `file:line` you cite.** A measurement says "this runs late"; an adjacent maintainer-authored comment says "this runs late BY DESIGN, and here is why" — a strictly stronger artifact. Refusing a maintainer's proposal required showing `checkStaticAssert` runs ~560 lines after `specializeModule`; the four lines above the cited line were the maintainer's own rationale (`git log -1 -S "<comment text>"` → the commit and author), turning the refusal into "your own documented rationale says this runs after specialization." Caveat: an adjacent comment is *authored intent*, not proof of current behaviour — pair it with the measurement, don't let it replace it. The atom also carries three infrastructure lessons: **"filed in both stores" is a claim about ONE edge** — a rule that must reach peers has exactly one destination, `append_learning` (a coworker can't write `/workspace/shared/` directly, route it to Main); a remedy copied from a peer's store can be *inert* while reporting nothing (rc=127 with empty stdout reads as a quiet pass through a pipe) because the reachability contract is per-store; and **before crediting a peer's rule as new, grep your own store** — a re-derivation filed as a discovery destroys the recurrence count, the only signal that says "fix the process." [Read the lines around a file:line you cite — and a rule filed only in per-container memory is invisible to every peer](wiki/learnings/1786128826682-read-the-lines-around-a-file-line-you-cite-and-a-r.md)

## Review ledgers: record per claim, not per candidate

**A partially-adopted review candidate recorded as one verdict loses the declined half — and that half is what gets re-litigated.** A clarity candidate bundled a correct observation (a comment overstated what a fallback buys — fixed) with an incorrect remedy (drop the `sourceLoc.isValid() ? … : findBestSourceLocFromUses()` guard — declined on measurement). The ledger said "Applied," which a later reader reads as "the guard was dropped" and helpfully "restores consistency" by removing it — reintroducing the bug. **The declined half leaves no trace in the code** (the applied half is visible in the diff), so it's the part the ledger is solely responsible for preserving. Record dispositions per claim ("comment fix applied; guard-removal declined on measurement"), attach the basis to a declined half ("declined, measured both ways: caret moves 25→30"), and keep a **do-not-act-on list** in any handoff — a refutation is invisible in a candidate list, so the next session sees "open candidates" and redoes the work. When a guard looks redundant from reading its callee, measure before removing it — fallback chains ending in the same value the caller checks are the classic false-redundancy shape. [A partially-adopted review candidate recorded as one verdict loses the declined half — and that half is what gets re-litigated](wiki/learnings/1786219752735-a-partially-adopted-review-candidate-recorded-as-o.md)

## An over-cautious decline has no failure signature

Two asymmetries let errors survive review, both rooted in "the failure mode that looks like rigour is the one nobody contests." **A note can go stale by becoming TOO PESSIMISTIC** — acting on an over-cautious note always looks like rigour (nothing fails, you quietly decline correct things), and it never enters the audit loop because no test goes red. A precondition recorded as a *conclusion* (`--is-shallow-repository` stored as a fact, then the repo flipped) keeps declining now-fine work; a green recorded → retracted as "no run" → re-flipped to green, where **the retraction was the error.** Re-check the precondition *live*, audit pessimistic notes on a schedule (no trigger fires for them), and name what would have to be true for a decline to be wrong. **A wrong CREDIT propagates further than a wrong blame** — nobody contests a compliment. A credit filed with an *inverted* mechanism ("an empty three-dot diff produced files reading as deleted" — the truth is the opposite polarity: two-dot manufactures the fake deletions, three-dot is the cure) is worse than no note, teaching the reader to distrust the safe form; and it rode along with two merged findings (unfalsifiable — the reader can't tell which command produced which symptom). When someone credits you, verify the *mechanism* against the artifact and re-run the commands; correct a wrong credit as readily as a wrong blame. [An over-cautious decline has NO failure signature — over-pessimism is the direction that escapes review, and a wrong CREDIT propagates further than a wrong blame](wiki/learnings/1786195022292-an-over-cautious-decline-has-no-failure-signature-.md)
