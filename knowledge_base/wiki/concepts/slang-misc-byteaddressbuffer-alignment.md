# Slang ByteAddressBuffer Alignment and Legalization

The `ByteAddressBuffer` (BAB) family has alignment semantics that differ by overload form, and the #11545 fixes span four interdependent slices. This page covers the alignment invariants, stride vs alignment, and the legalization pipeline.

## TL;DR
- Alignment and stride are different properties: a `float3`/`vec3` element has a 12-byte size but a 16-byte stride in most layouts, and conflating them is the recurring bug in this area.
- **On SPIR-V/GLSL, a plain `Load<float3>(addr)`/`Store<float3>` at a nonzero multiple of 12 touches the wrong bytes** (#13603): the structured-buffer translation divides the byte offset by the natural stride (12), but the aliased vec3 array has `ArrayStride` 16. Use address 0 in float3 byte-address docs and tests, or pin HLSL only.
- BAB alignment semantics differ per access form (scalar vs vector vs struct) — check the form, not just the element type.
- Scalar block layout changes `ArrayStride`; a fix validated only under the default layout can regress under it.
- Verify byte-address / HLSL-profile changes at an explicit `-profile cs_5_0`, not just `-target hlsl` — the profile, not the target, selects the code path.
- The #11545 work was staged in four slices; a change touching one slice needs the others re-checked before it is called complete.
- **Never group `bool` when splitting byte-address vectors** (#11803): `vector<bool,N>` sub-access is invalid SPIR-V (`OpTypeBool` in StorageBuffer, E99999) and silently wrong on CPU/CUDA (2-byte `sizeof` vs 4-byte BAB stride). Return width 1 for `IRBoolType` in the group-width chooser, and probe new splits per element type with a `-cpu` readback.
- **Single-arg `LoadAligned<T>(loc)` passes `__naturalAlignmentOf<T>()` (`kIROp_GetNaturalAlignment`), which `specializeGenericImpl`'s `simplifyFunc` folds to an `IRIntLit` at every -O level** once `T` is concrete (`maybeSpecializeFoldableInst` has no case for it). Every alignment reaching `specializeFuncsForBufferLoadArgs` is a literal (spec constants are rejected earlier with E40013).
- **`kIROp_ByteAddressBufferLoad` is missing from `mightHaveSideEffects`' side-effect-free list, so DCE keeps every unused leaf load** from `legalizeByteAddressBufferOps`, at every -O level (GLSL/SPIR-V escape because their leaves become `StructuredBufferLoad`). PR #13764 adds the case; it also lets `simplifyCFG` delete an empty BAB spin-wait loop, as master already does for `RWStructuredBuffer`. Probe spin-wait, load-then-store ordering and DCE on any `mightHaveSideEffects` change.
- **On SPIR-V the BAB→StructuredBuffer rewrite converts only BAB params it sees used.** Under `-preserve-params` DCE keeps every global_param, and before #14045 a `RasterizerOrderedByteAddressBuffer` used only via `GetDimensions`/`Interlocked*` skipped the pass gate; both reach emit as raw BAB and ICE. GLSL emits BAB natively and hides it.
- **Templated `ByteAddressBuffer.Load<T>` works at SM 6.0 with `-HV 2018`** (DXC's own `raw_buf3.hlsl` RUN line). SM 6.2 is the 16-bit-types boundary, which search summaries conflate with it. Take capability boundaries from a primary source.
- **An untemplated `.Store(off, val)` deduces `T` from the value's spelling:** DXC makes a bare `42.0` float, and C++/CUDA spell double infinity with a float macro, so constant double/half stores become 4-byte writes. `-target hlsl` defaults to DX 5.1; moving `useBitCastFromUInt`'s `<= DX_5_0` threshold needs a maintainer.
- **For an HLSL overload/deduction bug, propose typing the literal first** (the maintainer merged the `L`-suffix fix #14322 over call-site `Store<T >` templating); mention call-site templating only as an alternative. `half` literals and the inf/NaN arms are still untyped.
- **DXC rejects explicit template arguments on `RasterizerOrderedByteAddressBuffer` `Load`/`Store`** (not on `RWByteAddressBuffer`), so templated byte-address emit must special-case ROV.

## Alignment semantics by form, and the stride-vs-alignment bug

The single-arg `LoadAligned<T>(uint)` and `StoreAligned<T>` overloads originally passed `__naturalStrideOf<T>()` as alignment; on current master (60a7c8c88) they pass `__naturalAlignmentOf<T>()` (folding section below). The alignment parameter is informational on HLSL but meaningful for SPIR-V/Metal/WGSL lowering. The unsuffixed `Store2/3/4(addr, valueN, alignment)` forms are aligned stores under an unsuffixed name ([single-arg aligned forms](../learnings/1780768566167-slang-byteaddressbuffer-single-arg-aligned-forms-u.md)).

Forwarding the **stride** as alignment gives `float3` an alignment of 12, non-power-of-two, the root of the WGSL pow2-alignment errors behind #11505/#11545 ([STRIDE as alignment](../learnings/1781030980541-slang-byteaddressbuffer-implicit-loadaligned-t-off.md)). A naive pow2 check on `LoadAligned`'s alignment operand would therefore break every `float3` load, which couples #11545 point 4 with the #11505 API-surface cleanup ([naive pow2 check](../learnings/1781158312869-slang-byte-address-a-naive-pow2-alignment-check-br.md)).

The same 12-vs-16 mismatch corrupts plain, no-promise loads on SPIR-V and GLSL on master (#13603, related to closed #9931). With `translateToStructuredBufferOps`, `emitSimpleLoad`/`emitSimpleStore` (`slang-ir-byte-address-legalize.cpp`) turn the byte offset into an element index by dividing by the natural stride, 12 for `float3`, but the aliased vec3 runtime array is declared with `ArrayStride` 16, so `Load<float3>(12)` reads bytes 16–27 instead of 12–23. Plain `Load` accepts a whole `float3` at any literal multiple of 12, so no diagnostic stops it. Until fixed, write float3 byte-address examples and tests at address 0 or pin them to HLSL, so they do not enshrine the wrong bytes ([#13603](../learnings/1791904799552-slang-spir-v-glsl-plain-byteaddressbuffer-load-flo.md)).

## The four-slice plan (#11545)

- **Slice 1**: implicit LoadAligned natural-alignment infrastructure (`getNaturalAlignment` in IR ops).
- **Slice 2**: pow2-alignment validation error. Diagnostic 41303 cannot live here, because the single-arg forwarder still passes natural STRIDE and would false-reject valid 3-component loads; carrying 41303 in Slice 2 is a confirmed band-aid (prior ruling re-verified at a84f48e62 post-#11594) ([41303 ruling](../learnings/1781776078394-slang-11591-11590-prior-41303-to-slice-3-ruling-17.md)).
- **Slice 3 (#11592)**: only partially blocks on Slice 1, a non-obvious dependency ([4 slices](../learnings/1781315409904-slang-11545-alignment-work-split-into-4-slices-sli.md)).
- **Slice 4 (#11593)**: chunked widest-power-of-two sub-vector load/store tier for values wider than the maximum atomic width. It belongs in `slang-ir-byte-address-legalize.cpp`, must be vector-specific, recomputes alignment per chunk, and needs the prior slices first ([chunked codegen](../learnings/1781315228593-slang-11593-chunked-byte-address-codegen-insertion.md)).

Pow2-alignment validation must ship in the same PR as switching the implicit single-arg forms to natural alignment, or every 3-component load hits the new error ([same PR](../learnings/1781133163629-slang-11545-pow2-alignment-validation-must-fix-imp.md)).

## Scalar block layout and ArrayStride

`VK_EXT_scalar_block_layout` is required by the declared SPIR-V `ArrayStride` decoration (validated at pipeline creation), **not** by how loads are emitted: scalarized loads over a `float3[]@12` declaration still need the device feature. For portability, declare a scalar `float[]` array ([ArrayStride forces it](../learnings/1782722840826-slang-scalar-block-layout-is-forced-by-the-arrayst.md)).

## Verify at `-profile cs_5_0`, not just `-target hlsl`

A byte-address (or any HLSL-profile-sensitive) change can pass every `-target hlsl`/`spirv` check yet break the **fxc / DX ≤ 5.0** path, which sets `byteAddressBufferOptions.useBitCastFromUInt = true` (`profile.getFamily()==DX && version <= DX_5_0`). fxc-era HLSL has no templated `.Load<T>`/`.Store<T>`, so such accesses must lower to untemplated `uint` `Load()`/`Store()` + `asfloat`/`asuint`. On slang#11803 the chunker split a partially aligned `float4`@8 into typed `float2` sub-chunks — fine on modern HLSL, fxc-uncompilable at cs_5_0, and CI-invisible because feature tests had no profile. Compile a repro at `-target hlsl -profile cs_5_0`, check for no templated `Load<`/`Store<` and no typed vectors, and add a cs_5_0 regression test. The vector `useBitCastFromUInt` branch is dead for concrete-element-count vectors (fxc-compat relies on scalarizing), so fall back to `emitLegalSequenceLoad/Store` when the flag is set rather than chunking ([cs_5_0](../learnings/1784438217128-byte-address-hlsl-profile-changes-verify-at-profil.md)).

**Never `replaceUsesWith` on a shared type inst (#12265).** `InterlockedAdd` on a `RWByteAddressBuffer` passed into a helper silently corrupts `Load`/`Store` indexing on CPU/C++. `getEquivalentStructuredBuffer`'s IRParam branch does `babType->replaceUsesWith(structuredBufferType)`, but IR types are **deduplicated**, so the one shared `RWByteAddressBuffer` type inst becomes `RWStructuredBuffer<uint32_t>` **module-wide**, and byte-address `Load`/`Store` keep offsets never divided by the stride. Only CPU/C++ shows it, because that target gates off the offset→index `÷ stride` rewrite; the global-param branch, which creates a *separate* structured-buffer global, is the contrast. Build a per-use cast/view at the use site instead ([shared type-inst mutation](../learnings/1785339952123-rwbyteaddressbuffer-atomic-via-helper-flips-whole-.md)).

## Splitting byte-address vectors: never group `bool` (#11803)

PR #11803 groups partially aligned BAB accesses into typed sub-vectors (e.g. `float4`@8 → 2×`float2`, via `emitLegalGroupedVectorLoad/Store` and `chooseGroupWidth`). `bool` must stay per-component: it is a logical type with a 4-byte BAB stride. All three automated reviewers missed this; only probing `bool` element types and a CPU runtime test found it.

- **SPIR-V:** `vector<bool,2>` becomes a `StructuredBuffer<bool2>` that `KhronosTargetBufferElementTypeLoweringPolicy::needsElementLowering` (`slang-ir-lower-buffer-element-type.cpp`) never lowers, since it matches only *scalar* `IRBoolType`: `OpTypeBool` in `StorageBuffer`, E99999 under `SLANG_RUN_SPIRV_VALIDATION=1` and silent invalid output without it.
- **CPU:** `Load<Vector<bool,2>>` reads `sizeof` = 2 bytes, so `[1 0 1 1 | 0 1 0 1]` reads back as `1 0 1 0 0 0 0 0`. **CUDA:** `Load<bool2>` does `memcpy(2)`, the same mismatch.

Fix at the producer: width 1 for `IRBoolType` in the group-width chooser. Fully wide `LoadAligned<bool4>(loc, 16)` and `RWStructuredBuffer<bool2>` are already invalid SPIR-V on master; unwrapping vectors in `needsElementLowering` fixes SPIR-V but not CPU/CUDA. For any BAB width or vectorization change, probe `bool4` at alignment 8, plain `Load<bool4>(8)`, `bool2x4`, `bool4[2]` and bool struct fields under SPIR-V validation, plus half and 64-bit types, and add a `COMPARE_COMPUTE -cpu` test with asymmetric per-component data; FileCheck tests counting `Load<float2>` cannot catch wrong offsets or order ([exclude bool](../learnings/1791865205035-bab-vector-grouping-must-exclude-bool-vector-bool-.md), [never group bool](../learnings/1791869567632-splitting-byte-address-vectors-into-sub-vectors-ne.md)).

## Who folds `__naturalAlignmentOf<T>()`: `specializeGenericImpl`

`LoadAligned<T>(loc)`'s `__naturalAlignmentOf<T>()` lowers to `kIROp_GetNaturalAlignment`, folded to an `IRIntLit` during `specializeModule` at every -O level, including `-O0`. Not by `SpecializationContext::maybeSpecializeFoldableInst`: `maybeSpecializeInst` has no case for it and its `default` returns false. A gdb breakpoint on the peephole's `kIROp_GetNaturalAlignment` case (slang-ir-peephole.cpp ~1860) shows the path `maybeSpecializeInst` → `maybeSpecializeGeneric` → `specializeGeneric` → `specializeGenericImpl` (slang-ir-specialize.cpp ~4157) → `simplifyFunc(..., IRSimplificationOptions::getFast)` → `peepholeOptimize` → `processInst`; `specializeGenericImpl` simplifies each specialized `IRFunc`, and the peephole skips only while the body is inside an unspecialized generic (`isInGeneric`). Gdb-confirmed by two coworkers on #13130 ([fold path](../learnings/1792266470378-slang-naturalalignmentof-t-is-folded-by-specialize.md), [link-time literals](../learnings/1792266993304-slang-getnaturalalignment-is-folded-by-specializeg.md)).

So every alignment shape reaching `specializeFuncsForBufferLoadArgs` is an `IRIntLit` — `static const`, constant arithmetic, a `let A` generic value parameter, an interface `static const` via `T.kAlign`, and a link-time `extern static const` from a separately compiled `.slang-module` — and spec constants are rejected earlier with E40013, so `SLANG_RELEASE_ASSERT(as<IRIntLit>(op))` is safe there. To drill the link-time case pass the main source too, as slang-test does (`slangc main.slang -r main.slang-module -r lib.slang-module ...`); `-r` modules plus `-entry computeMain` alone fails with E30015/E38000.

Two general techniques. To find which pass folds X, `gdb -batch` with a pending breakpoint on the peephole case and `commands; bt 12; continue; end`, on a tiny `-O0` repro; the pass list is not enough, since folds happen inside other passes' helpers. To prove in FileCheck that two specialized clones carry *different* literals (e.g. 16 and 4), anchor past call-site noise (`CHECK: func %main`, then `CHECK: func %<first clone>`) and `CHECK-DAG` each value; `CHECK-NOT` covers only the gap before the next match, and FileCheck cannot compare captures for inequality. Show the test fails on a negative input (equal values).

## Dead leaf loads survive: `ByteAddressBufferLoad` is not side-effect free (#13739)

`legalizeByteAddressBufferOps` splits `Load<T>`/`Load4` into one leaf `byteAddressBufferLoad` per word (WGSL, Metal) or per field (HLSL, CUDA, CPU). On 60a7c8c88 `IRInst::mightHaveSideEffects` (slang-ir.cpp ~9627) lists `kIROp_StructuredBufferLoad`, `kIROp_RWStructuredBufferLoad` and `kIROp_Load` as side-effect free but not `kIROp_ByteAddressBufferLoad`, which falls to `return true`, so DCE keeps every unused leaf at every -O level. GLSL/SPIR-V escape only because `translateToStructuredBufferOps` makes the leaves `StructuredBufferLoad`; an unused scalar `Load<uint>` disappears only because its `[__readNone]` call goes before inlining. Adding the case cut the struct repro from 17 loads to 1 with unchanged results; the full suite's 3 failures were FileCheck tests expecting named temporaries (`T x = buf.Load<T>(o);`), since single-use loads now fold into their user. When a wrapper goes but its leaf stays, check the leaf opcode's `mightHaveSideEffects` case before suspecting the lowering ([not side-effect free](../learnings/1792260159578-byteaddressbufferload-is-not-in-mighthavesideeffec.md)).

The change has a second consumer: `doesLoopHasSideEffect` (`slang-ir-simplify-cfg.cpp:158`) skips side-effect-free insts, so with PR #13764 a loop that only loads and branches is dead. `while (flag.Load<uint>(0) == 0) {}` on a `globallycoherent RWByteAddressBuffer` disappears on WGSL, Metal, CUDA and HLSL (the HLSL `Load(int)` spelling survives via intrinsic asm). Not a new bug class: master already deletes the same loop for a `globallycoherent RWStructuredBuffer` everywhere. A loop survives if it has a barrier, an atomic, or a loaded value used afterwards. On any `mightHaveSideEffects` change, probe a spin-wait, a load-then-store to the same word, and DCE ([spin-wait deletion](../learnings/1792501905990-making-a-load-op-side-effect-free-also-lets-simpli.md)).

## Templated `Load<T>` is SM 6.0, not SM 6.2

A web-search summary claimed templated `ByteAddressBuffer.Load<T>()` needs SM 6.2, and it nearly went to a maintainer as a gap in Slang's fxc gate. False: DXC's own `tools/clang/test/HLSLFileCheck/hlsl/objects/ByteAddressBuffer/raw_buf3.hlsl` runs `%dxc -E main -T ps_6_0 -HV 2018` with `.Load<float>`, `<float2>`, `<float4>` and `<double2>`. SM 6.2 is the boundary for 16-bit scalar types (`-enable-16bit-types`). So the `useBitCastFromUInt` (DX ≤ 5.0) split is right for SM 6.x; whether SM 5.1 is right is a separate, unverified fxc question. Take "needs SM X" from a primary source (the compiler's test RUN lines, release notes); fetch a critique's cited counterexample, and when a premise collapses, re-audit what you changed because of it ([SM 6.0](../learnings/1791856275861-dxc-templated-byteaddressbuffer-load-t-works-at-sm.md)).

## HLSL byte-address stores: `T` deduced from the value's spelling, and the ROV exception (#14259)

The base C-like emitter writes a byte-address store as `.Store(off, val)` with no `<T>`, so dxc, the C++ compiler or nvrtc deduce `T` from the value's spelling. DXC (cs_6_6) makes an unsuffixed `42.0` a `float` only in template deduction: `buf.Store(0U, 42.0)` emits `rawBufferStore.f32`, while `WaveActiveSum(0.1)` emits `waveActiveOp.f64`. Before PR #14322 Slang suffixed only float literals, so a constant `Store<double>`/`Store<half>` became a 4-byte f32 store (the half one clobbering the next 2 bytes); integer literals were already typed. Of the two proposed fixes — template the call site (`Store<T >`, PR #14276) or type the literal (HLSL `L` suffix, PR #14322) — the maintainer (skiminki-nv) merged the literal fix (4a6758601) and is weighing strongly typed HLSL literals everywhere (e.g. `int(4)`), with compile time their concern. Now `float` gets `f` and `double` `L`; `half` literals (no `h`) and the inf/NaN arms (`(1.0f / 0.0f)` for every width) are still untyped. For the next HLSL overload/deduction bug, propose the literal fix first, call-site templating only as an alternative ([literal spelling preferred](../learnings/1793899082636-hlsl-literal-type-bugs-maintainer-prefers-fixing-t.md)). Strongly typed integer literals have their own DXC trap (`0L` is `uint` while `1L` is `int`, so an int zero needs `int(0)`); see [[wiki/concepts/slang-tooling-dxc-prebuilts-and-cmake.md]].

Two code traps on this path: the HLSL `kIROp_ByteAddressBufferStore` override (slang-emit-hlsl.cpp ~1505) reads `inst->getDataType()`, void for a store, so its uint `.Store`/`.StoreN` fast path never runs; and slang-ir-insts.lua lists operands `{buffer, offset, value, alignment}` while the builder uses `{buffer, offset, alignment, value}`, so `IRByteAddressBufferStore::getValue()` returns the alignment (use `getOperand(getOperandCount()-1)`) ([bare-literal deduction](../learnings/1793743040440-dxc-deduces-float-from-a-bare-hlsl-literal-only-in.md)). C++ and CUDA share the inf/NaN trap: double infinity is `SLANG_INFINITY`, a float macro (slang-cpp-prelude.h:62, slang-cuda-prelude.h:53), so "their literals are typed" is not safe triage; add cpu and cuda runtime legs with a sentinel-filled buffer. `-target hlsl` defaults to DX 5.1, so raising `useBitCastFromUInt` to `<= DX_5_1` would flip ALL default HLSL byte-address output to uint + `asfloat` (a maintainer decision); master already emits templated `Load<float4 >` at cs_5_0/5_1 where legalization leaves the access alone. HLSL groups `Store3` only at multiples of 12, where SPIR-V misplaces `float3` (#13603), so pin `Store3` in a text-only entry ([DX 5.1 default](../learnings/1793748574524-slang-default-target-hlsl-profile-is-dx-5-1-bab-st.md)).

**ROV buffers reject templating.** DXC 1.9 accepts `RWByteAddressBuffer.Store<T>`/`Load<T>` but rejects explicit template arguments on `RasterizerOrderedByteAddressBuffer` ("Explicit template arguments on intrinsic Store are not supported"; likewise `Load`), so emit that writes `Load<T >`/`Store<T >` must special-case `IRHLSLRasterizerOrderedByteAddressBufferType`. An untemplated ROV store with the value cast to its own type deduces correctly: `rov.Store(0U, double(42.0))` gives `rawBufferStore.f64`, `half(1.5)` `.f16`. ROV `Load<T>` is already broken on master (#14282). No test put a non-uint ROV store through DXIL before PR #14276, so CI cannot catch it, and Reviewer A, Devin and a clarity pass all missed it. Check with a fragment shader: `-target hlsl -profile ps_6_6`, then `-pass-through dxc -stage fragment -profile ps_6_6 -target dxil-assembly` (an ROV in compute fails DXIL validation for an unrelated reason; local DXC setup is on [[wiki/concepts/slangc-target-output-and-obfuscation.md]]) ([no templated ROV methods](../learnings/1793756899721-dxc-has-no-templated-methods-on-rasterizerorderedb.md), [explicit args rejected](../learnings/1793751394553-dxc-rejects-explicit-template-args-on-rasterizeror.md)).

## The BAB→StructuredBuffer rewrite converts only params it sees used: SPIR-V ICEs (#14039, #14045)

On SPIR-V, `legalizeByteAddressBufferOps` (`processModule` ~:51) creates the `StructuredBuffer<T>` replacement for a BAB `global_param` lazily, only from a load, a store or a `GetEquivalentStructuredBuffer` use. A BAB param the pass never sees reaches SPIR-V emit raw and ICEs with "Unhandled global inst in spirv-emit" (slang-emit-spirv.cpp ~:3070); GLSL emits BAB natively and hides both producers:

- **`-preserve-params` (#14039).** DCE's `keepGlobalParamsAlive` (slang-emit.cpp ~:1491, slang-ir-dce.cpp ~:616) keeps EVERY global_param under this option, not just `[keepAlive]` ones, so any unused BAB, RWBAB, BAB array or leftover ParameterBlock BAB field survives unconverted, and a USED `ByteAddressBuffer arr[2]` keeps its old `Array(BAB)` param alive through a dead stale `getElement`. PR #9742 (#9262) covered only the used, non-array case. Quick probe: diff the param's type "AFTER legalizeByteAddressBufferOps" between used and unused variants ([-preserve-params](../learnings/1793296132985-preserve-params-byteaddressbuffer-on-spir-v-bab-sb.md)).
- **The pass gate.** On master 0cd957ba9 `calcRequiredLoweringPassSet` (slang-emit.cpp) set `byteAddressBuffer` only for BAB/RWBAB types or BAB Load/Store ops. A `RasterizerOrderedByteAddressBuffer` used only via `GetDimensions`/`InterlockedAdd` lowers to `GetEquivalentStructuredBuffer` with no load or store, so the pass never ran and SPIR-V failed with `E99997 Unhandled global inst in spirv-emit: RasterizerOrderedByteAddressBuffer` (GLSL/HLSL fine). Repro: fragment shader with `RasterizerOrderedByteAddressBuffer buf; uint d; buf.GetDimensions(d); buf.InterlockedAdd(0,1,o);` at `-target spirv-asm`. PR #14045 fixes it as a side effect by matching `IRByteAddressBufferTypeBase` ([ROV pass gate](../learnings/1793304188842-rasterizerorderedbyteaddressbuffer-used-only-via-g.md)).

To test either in a COMPARE_COMPUTE, pass slangc options as `-Xslang -preserve-params` (render-test rejects a bare option); render-test already adds `-Xslang -O0`, so use `-Xslang -O2` for an optimized row. Without clang-format 17 on PATH, `python3 -m pip install --target /workspace/agent/.tools/cf clang-format==17.0.6` provides `.tools/cf/clang_format/data/bin/clang-format` for `--dry-run --Werror` (same atom).
