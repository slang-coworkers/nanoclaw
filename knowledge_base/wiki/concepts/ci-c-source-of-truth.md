## TL;DR

Half of CI/build errors are reading a stale, cached, or wrong-scoped copy of something that has a live authoritative source elsewhere. The fix is to name the authoritative source, re-read it at reply time, and label the unit of every number.

- **`git origin/<branch>` is a local cache**, not a live view of the remote — never cite it for what is pushed. Use `git ls-remote origin refs/heads/<branch>`, and remember `git fetch origin <branch>` can exit 0 while leaving the tracking ref stale (master-only refspec).
- **Re-read the target file at HEAD before replying about a delivered diff** — CI workflows migrate under you (a byte-size change is a cheap tripwire). Retract loudly and early; a patch that can't apply but *looks* actionable costs the maintainer more than none.
- **A vendored dependency's real source under `build/_deps/` is the authoritative spelling** — and it may disagree with the spec proposal. Emit the version *actually pinned*.
- **A doc comment's coordinate space is a claim; the underlying extension spec decides it.** Read the `__target_switch` body — no transform ⇒ the spec's space wins whatever the comment says.
- **A derived deadline is a carried value; every push voids it.** Store the re-derivation command beside the value, not just the number.
- **Cite policy, never capability.** A capability-negative has no failure signature (readers comply by not attempting), so a stale environment claim laundered into a fresh artifact can sit correct-sounding for months.
- **A reconciliation can inherit the unit bug it resolves.** Never compare MB to MiB by bare numerals; re-derive disagreeing census counts, don't reconcile them; a front-end defect measured per-target understates itself.
- **INDEX.md is a build output**, not a maintained file — a retraction banner must live *in the leaf* (row labels are creation-time filename slugs); route in-place edits to whoever owns the store.

## Caches that look like live data

`git origin/<branch>` is a snapshot from the last fetch in *this* worktree. Checking for unpushed work, `git log origin/<branch>..HEAD` reported 7 commits — several pushed hours earlier and confirmed on GitHub — because the tracking ref was stale; `git ls-remote` showed the real tip, and after `git fetch` the true count was 1. It bites hardest exactly where it matters most (deciding whether to push): an inflated unpushed count invites "just push everything," which is the wrong move if the push has a cost (superseding a CI run, resetting a timer). It survives casual scrutiny because the commits it lists are real, in the right order, on the right branch — only the pushed/unpushed boundary is wrong. For any claim about what the remote has, `git ls-remote origin refs/heads/<branch>` (one call, no side effects) or fetch first. General shape: a query whose name suggests the remote but whose data is local. [git origin/branch is a local cache — never cite it for what is pushed](wiki/learnings/1786196186804-git-origin-branch-is-a-local-cache-never-cite-it-f.md)

A CI workflow is not a stable target — it is edited by other people while your chain is open, so re-read the target file at HEAD and `git log` the path before replying about a delivered diff. A diff wrapping a `falcor-image-test` step sat ~19 hours while commit `eea5b2753` replaced that job wholesale (Windows→Linux bridge, body now `run: /opt/slang-ci/run-external-ci` — a runner-side binary, not a tracked file), making the patch's entire mechanism unimplementable; it was caught only by an incidental `grep` returning `rc=1`. Rules: re-read + `git log --oneline -- <path>` + `git log -S'<anchor>' -- <path>` (seconds); a file's byte size changing is a cheap tripwire (5,600→3,456 B was the tell); the staler your delivery, the higher the risk; and retract loudly and early — lead the reply with the invalidation. The migration also silently split a rate population (pre-boundary Windows 4/22 vs post-boundary Linux 1/15), so a single "1 in 7.4 today" figure straddles a config change and describes neither regime — split at the change and say so; "signature not observed since migration" over 15 runs whose logs *cannot name tests* is an instrument blind by construction, not a fix. (A same-host pass/fail pair killed a SLANGWIN5-specific host story directly.) [Re-read the target file at HEAD before replying about a delivered diff — CI workflows migrate under you](wiki/learnings/1786132634125-re-read-the-target-file-at-head-before-replying-ab.md)

A derived CI deadline is a carried value — every push voids it. Deriving 12h/16h yield deadlines three times in one session (because each push created a new run with `age 0.0h`) silently voided every timestamp and run id just computed; a stale deadline reads exactly like a fresh one. Derive *after* your last push, or store the *re-derivation command* beside the value (`git ls-remote origin refs/heads/<branch>`), not just the SHA. Two adjacent traps in the same session: `gh workflow run` RESETS the yield clock (`created_at` resets) while `gh run rerun` inherits the aged `created_at` (so recovery for a yielded run is *rerun*, not fresh dispatch); and `git fetch origin <branch>` can exit 0 leaving the tracking ref stale if the clone's refspec is master-only — `git ls-remote` is the authoritative read (distinguish this from a two-mounts trap with `git rev-parse --show-toplevel` + `--git-common-dir`). [A CI deadline is a carried value — every push voids it, and a 403 is not "no rule"](wiki/learnings/1786109673796-a-ci-deadline-is-a-carried-value-every-push-voids-.md)

## The authoritative source for a spelling or a space

A vendored dependency's real source under `build/_deps/` is the authoritative spelling — and it may disagree with the spec proposal. Asked for the exact DXC spelling of a `dx::linalg::ComponentType` enumerator (which slang must emit byte-exact), two sources disagreed: the hlsl-specs proposal spelled `BFloat16 = 23` (verified by *census* on raw bytes — 7× `BFloat16`, 1× `Bfloat16`; a `WebFetch` *summary* invented "value 23" inline), while the pinned DXC `v1.9.2602` source under `build/_deps/dxc_source-src/` ends its `ComponentType` at `F8_E5M2 = 22` — the enumerator does not exist in the pinned version, and that absence is itself the finding. A grep hit in a header may be a *comment* — print the surrounding lines before concluding a symbol is declared. When proposal and shipped dependency disagree, the emitted string must follow the version *actually pinned* (precedent: slang emits `F8_E4M3`, shipped-DXC's spelling, over the proposal's `F8_E4M3FN`), and the answer needs a version/timestamp. [A vendored dependency header in build/_deps is the authoritative spelling source — and it may disagree with the spec proposal](wiki/learnings/1786049836308-a-vendored-dependency-header-in-build-deps-is-the-.md)

A doc comment's coordinate space is a *claim*; the underlying extension spec decides it. A slang stdlib comment said `{Candidate,Committed}GetIntersectionTriangleVertexPositions()` returns positions "in world space" — it's *object* space (Vulkan-Docs), because the method lowers straight to the KHR op with no transform. The nastiest kind of doc bug: trusting it gives correct results for identity-transform instances (the first scene anyone tests) and only breaks once instances get transforms. Method rule: for any intrinsic returning positions/directions/matrices, the coordinate space belongs to the underlying spec unless the wrapper applies a transform — read the `__target_switch` body. Related: DeepWiki and GitHub code search both failed on this because the member names are *macro-generated* (`$(ccName)` interpolation) and `hlsl.meta.slang` (1.24 MB) is over GitHub's index limit — grep the generator pattern, not the spelling users type, and "code search found nothing" is not evidence of absence for that file. [A doc comment's coordinate space is a claim; the extension spec decides it](wiki/learnings/1786130561966-a-doc-comment-s-coordinate-space-is-a-claim-the-ex.md)

## Cite policy, never capability

State the *policy* reason, not the *capability* reason. A peer's "closing an issue is hook-blocked for us" was measured false on the actual settings (zero hooks reference `state=closed`), and traced to a five-week-old line in the peer's own store, lifted into a fresh leaf and rendered as present-tense capability. The honest reason neither tier closes a duplicate is *recommend ≠ execute; closing is a maintainer action* — which survives any tooling change. A capability-negative is uniquely durable because it has *no failure signature*: readers comply by not attempting, and a non-attempt logs nothing (no error, no denied call), so it can sit correct-sounding for months where a capability-*positive* fails loudly the first time someone relies on it. Corollaries: writing a stale environment claim into a fresh artifact *launders* it (carry the timestamp — "returned FORBIDDEN at `<time>`; re-probe before relying"); fix it at the source leaf, not where it surfaced; and distinguish the mechanism you *measured* from the outcome you're *inferring* ("untested by design, not by capability"). [Cite policy, never capability — a capability-negative has no failure signature because readers comply by not attempting](wiki/learnings/1786199814402-cite-policy-never-capability-a-capability-negative.md)

## Units, reconciliation, and re-deriving census counts

A reconciliation can inherit the same unit bug it resolves. Two figures for core-module blob growth (+60.5% `.rodata` *section* vs ×1.96 *symbol*) were both correct — a section understates a symbol it contains — while a third (1.88) was wrong (MiB over MB). But the reconciliation's own headline "the deltas agree within 1.08%: +4.61 MB vs +4.56 MiB" carried the *same* defect: those agree only as bare numbers (as labeled, 3.72% apart, which would make the section grow *less* than its contents). Containment is a free physical constraint — a section's growth must be ≥ a symbol inside it — and solving for the residual (container − contents) at both endpoints is a strong unit discriminator. Never compare MB to MiB by bare numerals (1.0486× fakes a ~4.9% error); audit a reconciliation's *own* arithmetic before adopting it, because the conclusion can survive while the reasoning is defective, which is exactly why it's adopted uncritically. [A reconciliation can inherit the same unit bug it resolves — check MB vs MiB on the agreement figure too](wiki/learnings/1786042397017-a-reconciliation-can-inherit-the-same-unit-bug-it-.md)

A wrong-unit read can make a peer's *reproducible* figure look unreproducible. About to publish "could not reproduce X's 695 codes, so I don't rely on it" (a mild correction) after measuring 625 — but the file was a TSV whose rows begin with a sequential index, so the peer's unit was *catalog rows* (`grep -c '^[0-9]'` = 695) and mine was *unique numeric tokens*. Two correct measurements of different quantities look identical to a near-miss caused by error, and the demote-the-claim move silently converts a sound peer figure into a doubted one — before publishing "I could not reproduce X," open the artifact and determine what unit the number is *of*. Re-deriving a census rather than reconciling its total surfaced something neither figure captured (three non-keyword hits were line continuations of multi-line expressions, not statements). [A wrong-unit read can make a peer's reproducible figure look unreproducible](wiki/learnings/1786184395044-a-wrong-unit-read-can-make-a-peer-s-reproducible-f.md)

A front-end defect measured per-target *understates itself*. A "bare unparenthesized function name is silently dropped" finding was located in the *checker* (`slang-check-expr.cpp`, which by construction predicts every backend) but shipped evidence from only HLSL+SPIR-V — reading to a maintainer as a narrower bug than exists; the real scope is all six backends *and* user-defined functions (a `barrier|Barrier` grep reads false-0 on CUDA/GLSL — build the per-target token table). When the mechanism is target-independent, measure one per backend family or state the scope limit out loud. Prefer a *demonstration* to an *argument*: `[NoDiscard] int f(); f();` errors while `f;` is silent — the adjacent mechanism failing on this input, stronger than citing a precedent. And when two sound measurements of "the same" number disagree (547 vs 456 vs 564 bare `IDENTIFIER;` lines), the disagreement is information about the *instruments* — re-derive from the definition; don't average, don't pick, don't reconcile. A count without its corpus definition is unfalsifiable; a write-scope gap belongs to the coworker owning that surface; and `gh api user`→`.permissions` all-false is a known false negative for `issues:write`. [A front-end defect measured per-target understates itself — plus: re-derive disagreeing census counts, never reconcile them](wiki/learnings/1786184939283-a-front-end-defect-measured-per-target-understates.md)

## The learnings index is itself a build output

`/workspace/shared/learnings/INDEX.md` is *regenerated*, not maintained — hand-editing a row does not persist (33 of 36 operator annotations vanished after an unrelated `append_learning`). An index row's label is the *filename slug* baked in at creation; the generator never re-derives it from a leaf, so *nothing written into a leaf afterwards ever reaches its index row*. Consequences: a *correction* is durable only if it names what it corrects in its own opening line (a new leaf, so you control its text at write time); a *warning on a superseded leaf* is not achievable after the fact by a container coworker (`EROFS` blocks the edit, the row is regenerated) — but *is* achievable by whoever holds write access to `/workspace/shared/` (Main), who can edit the leaf in place and `build` propagates it. Route a wrong claim in a published leaf to that owner as an in-place edit rather than stacking an appended correction that leaves the bad artifact intact. Write the first version assuming you'll never amend it: don't publish a load-bearing claim you're unsure of, and before designating yourself the owner of a fix, verify the fix survives (`stat` your write target after an unrelated write — check whether it's source or derived). [INDEX.md is a build output derived from leaf openings — a retraction banner must be IN the leaf, and EROFS means you must get it right on first write](wiki/learnings/1786172024659-index-md-is-a-build-output-derived-from-leaf-openi.md)

A partial fix rail is not a verdict, and a defect re-recorded as lessons is not a countermeasure. `devin-fetch.sh` exited 0 without scraping Devin's verdict from two causes (a done-guard accepting GitHub's `Checks n/m` CI counter for any n/m; nothing ever clicking "View results") — both now fixed and tested in the nanoclaw copy (PR #1145), still open in the slang copy which has *no git home*. The transferable lesson: **12 shared learnings recorded this exact false-clean over ~3 months, six of them *after* the last commit to touch the file** — the class was being re-recorded as lessons while the artifact went unchanged. A learning that names a defect is an observation; only an edit to the file that executes is a countermeasure — when you're writing the Nth atom about one defect, the correct action is a diff, not an N+1th atom. The fix must not regress the fix it replaces (the `Checks n/m` branch was added deliberately to stop false timeouts, pinned as a named regression target), and a guard test must be *armed* before trusted (2/9 fail on the pre-patch script, 9/9 after — a test that has never failed on demand is decoration). Interim rule while any copy is unfixed: `devin-fetch.sh` exit 0 means the scrape succeeded, never that an analysis was obtained — matters most on the Devin-only tier, reached exactly when no bot review exists to contradict a fabricated all-clear; check your own copy (`grep -c checksSettled`, `grep -ci 'view results'`). [devin-fetch done-guard: a partial CI rail is not a verdict — the class stayed open for 12 recorded instances because the fix was never wired into the artifact](wiki/learnings/1786121384159-devin-fetch-done-guard-a-partial-ci-rail-is-not-a-.md)
