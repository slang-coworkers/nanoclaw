## TL;DR

- `record_decision` returns "Decision recorded: …" while the host separately denies the append with "no approval-ledger writers are configured (set `APPROVAL_LEDGER_WRITERS`)". **No `approval_decisions` row is written.** The success string is a claim about the *tool*, not about persisted state.
- The two facts arrive on **different channels**: the success string is emitted by the tool wrapper; the allow/deny is enforced host-side against a capability list and surfaced as a separate system notification, possibly a turn later. An agent reading only the tool result books a phantom write.
- This is a **standing configuration defect**, not a flake — observed across ≥18 distinct PRs and three repos while `APPROVAL_LEDGER_WRITERS` remained unset. Every affected session under-reports by the *same* mechanism, so it looks less frequent than it is.
- The `ABSTAIN_*` relaxation path does **not** rescue it — the blocker is the missing config, not the critique gate; an abstain is denied exactly like a `WOULD_APPROVE`.
- Cheap pre-check: `env | grep APPROVAL_LEDGER_WRITERS` (empty ⇒ appends will be denied). Never treat a tool's success string as proof of persistence; verify the capability or read the row back.
- Keep a local durable artifact (`work/<pr>-<sha12>/decision.md`) with all decision fields, banner the true ledger state (`NOT RECORDED (host-denied)`), report upstream once with the exact backfill target, and replay later (idempotent per `(repo, pr, commit_sha)`).
- Escalate the **rate** (denials per hour of decision work), not the count of documented instances — the count grows when you *document*, not when the defect *recurs*, and it is fixable only by an operator editing the config.
- An infra-abstain atom must carry mechanism **and** the qualified PR id (`slang-rhi#826`, never "this PR" or a bare `826`) — the aggregation that matters is `denial-mechanism ∧ pr-id`, an intersection that an atom naming only one half is invisible to.

## The success string is not the write

The defect is reported near-verbatim across sessions. [record_decision returned "Decision recorded" while the host DENIED the append](../learnings/1786388048797-approver-infra-abstain-record-decision-returned-de.md) and [record_decision can print SUCCESS while the host DENIES the ledger append](../learnings/1786400575644-approver-infra-abstain-record-decision-can-print-s.md) establish the core: the write path and the reporting path disagree, and only the host notification is authoritative about host state. The second frames it precisely as the **false-positive mirror** of a false capability-negative — a false capability-*positive* has no observable failure signature at the time; everything looks like it worked and the gap only surfaces at join time, when the reason is long gone. The remedy sequence: treat the decision as NOT RECORDED, write full fields to `work/<pr>-<sha12>/decision.md` with a `⚠️ LEDGER STATE: NOT RECORDED (host-denied)` banner, escalate to the operator to set the config, replay afterward (idempotent), and report upstream stating the ledger state — an unrecorded decision that is *reported* is recoverable; a silently-unrecorded one is not.

## Standing defect, not a flake — and the ABSTAIN path does not save it

[Ledger denial recurs on slang#12452 (≥18th PR)](../learnings/1786390621900-approver-infra-abstain-ledger-denial-recurs-on-sla.md) adds two facts: the `ABSTAIN_*` relaxation path (which skips the critique gate) does **not** rescue the append — the blocker is the missing `APPROVAL_LEDGER_WRITERS` config, so an abstain is denied like any approve; and the denial arrives on a different channel than the call, so reading only tool results records a phantom write. It also fixes the reporting form: **quote the PR list, never the file count** — the file count is self-referential (each leaf documenting the defect joins the set it counts, so it grows when you *write*, not when the defect *recurs*). [record_decision returns "Decision recorded" while the host denies it](../learnings/1786428994507-approver-infra-abstain-record-decision-returns-dec.md) reinforces the "escalate the rate, not the count" framing and that this is an operator-fixable config gap, not a per-PR incident — "reporting it as another per-PR backfill note is what has let it persist across a dozen PRs."

## The filing seam: mechanism ∧ qualified PR id

Two atoms from the same slang-rhi#826 session diagnose a *filing* defect that hid the defect's true size. [slang-rhi#826 — ledger append DENIED on all 5 attempts](../learnings/1786418224963-approver-infra-abstain-slang-rhi-826-ledger-append.md) records that five learnings were written during that PR yet **none was greppable as a #826 denial** — the 826 atoms discussed the *lessons* and the denial atoms discussed the *mechanism*, so the intersection `denial-mechanism ∧ pr-id` was empty and the fleet floor undercounted 826 entirely. [An infra-abstain atom must carry mechanism AND qualified PR id](../learnings/1786418431919-approver-infra-abstain-an-infra-atom-must-carry-me.md) states the rule and its verification trap: a two-stage `rg -l … | xargs rg -l …` pipeline returned a false zero (a single-file probe immediately found `slangpy#1097`), so a `while read -r f` loop over a saved file list gave the correct answer. When a two-stage pipeline returns a suspiciously round zero, re-run stage 2 on one known-positive input before believing it — here that would have converted a filing defect of one's own into a false accusation against the whole store. Both atoms insist on repo-qualifying the id (`slang#826` ≠ `slang-rhi#826`, and a bare `826` collides with line numbers and byte counts) and on `rg --multiline` because atoms hard-wrap mid-phrase.

## Reporting form

State counts as **`≥N, own-session only`**, never as a bare ordinal — every edge counts privately, so any one agent's number is a lower bound on a fleet total, and presenting "5 attempts" as complete invites the undercount. The operator-actionable figure is the **rate** (dropped decisions per hour of decision work): a count grows silently with fleet size, while a rate says how much signal is being lost per unit of work. And recording is not routing — no amount of documentation reaches a config file only an operator can edit, so escalate *as well as* record, every time.
