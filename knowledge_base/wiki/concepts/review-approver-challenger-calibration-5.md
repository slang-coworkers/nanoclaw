## Design-Fragility False-Safe + Temporary-Test-Disable Calibration (2026-07-28 fold)

Two more merge-join data points that sharpen the challenger bar from opposite sides. **The false-safe: PR #12098 (Memoize Val substitutions) WOULD_APPROVE but the author closed it unmerged for a redesigned successor #12106.** The challenger cleared "gap #4 — transient `substitutionCache`-pointer threaded on `SubstitutionSet`" as "undemonstrated future-proofing," but csyonghe's live COMMENTED review probed that exact wiring ("field appears never initialized to non-null — how is this supposed to work?") and the successor removed it entirely (environment-local cache). The lesson: when a review doc's gaps include a **design/representation** concern (a transient mutable pointer bolted onto an interned/canonical value type, a stack-pointer lifetime/escape, a second parallel representation), the challenger must NOT clear it merely because "no test triggers it" — a green harness cannot prove a representation is principled; escalate to CHALLENGER_CONCERN → ABSTAIN, and treat a maintainer's "how is this supposed to work?" COMMENTED review as a soft-negative even absent CHANGES_REQUESTED. Interning-safety ≠ design-soundness ([approver false-safe PR12098 — challenger cleared the exact cache-wiring axis the maintainer probed; design-fragility gaps aren't advisory](wiki/learnings/1785272574884-approver-false-safe-pr12098-would-approve-but-auth.md)).

The same representation-concern discipline vindicated an ABSTAIN on slang#12095 (autodiff promotion placement). CodeRabbit raised a secondary 🔴 the primary review missed: `promoteOperandsToTargetType`/`transposeArithmetic` reconstructed a forward-block `newInst` referencing a primal `newOperand` placed at `oldLoc` in the REVERSE block — a transient invalid-SSA / dominance shape. Holding at ABSTAIN_POLICY:CHALLENGER_CONCERN @`485ba73b` (not rounding up on the FP narrative) meant the head never got a false-safe; the author then landed exactly one commit ("Preserve SSA when promoting autodiff operands") DELETING the reconstructed-inst path, with a comment stating the very invariant the old code violated, and kaizhangNV APPROVED only the revised head `ede2eab8` (nobody approved the decision head) — so on the `pr_merged` join, diff-decision-head-vs-merged-head FIRST: the head moved by one SSA-fix commit, `record_human_verdict(485ba73b)=CHANGES_REQUESTED`, ABSTAIN VINDICATED (do-not-round-up class), not over-caution ([[approver/human-agreement] PR-12095 ABSTAIN-CHALLENGER_CONCERN-VINDICATED: unproven-🔴-fixed-before-merge, decision-head-not-the-merged-head](wiki/learnings/1785436774423-approver-human-agreement-pr-12095-abstain-challeng.md)). The challenger-side lesson is sharper: the *lean* toward false-positive ("the reconstructed container is a throwaway never actually transposed; the block is `removeAndDeallocate()`'d later") was WRONG even though the policy of holding-at-ABSTAIN saved the decision. "The bad shape is deleted before it matters" is NOT a proof of safety — it assumes no intervening pass observes it AND that the author intended it, both unproven; a dominance violation in SSA IR is a representation bug regardless of whether one downstream path tolerates it (fix the producer). Raise plausibility weight on cross-block operand-placement 🔴s in autodiff transpose specifically — differential-vs-primal insts belong in different blocks, so any reconstruction referencing both is a dominance smell; the correct read is "likely real," strengthening toward the same ABSTAIN with a truer rationale ([[approver/challenger-miss] transient-invalid-SSA in IR reconstruction is NOT auto-benign: "throwaway container never transposed" lean was WRONG on slang#12095](wiki/learnings/1785436795717-approver-challenger-miss-transient-invalid-ssa-in-.md)).

**Lock-scope-reduction fixes shift a race onto the callee, and an abstain on a *resolvable* dependency-behavior question is a deferral, not a verdict.** slangpy#1081 (`Logger::log` deadlock fix) narrows a mutex to snapshot shared state then releases it before invoking `output->write()` (which can take the GIL) — reads obviously-correct and CI-green, but removes the serialization that lock was incidentally giving to every callee, and the PR even added a header contract ("outputs must support calls from multiple threads") without making the built-in Console/File/DebugConsole outputs satisfy it. For any diff that reduces a lock's scope or moves a call outside a lock, don't stop at "the deadlock is gone" — ask *what did that lock serialize, and is every callee now safe to run concurrently?* and read the concrete callee implementations at head, not the interface (also check the snapshot itself: copying refcounted handles under the lock is safe only if the refcount is atomic — verified `Object::m_state` is `std::atomic`) ([[approver/challenger-miss] Lock-scope-reduction fixes shift a race onto the callee — probe callee thread-safety](wiki/learnings/1785412873218-approver-challenger-miss-lock-scope-reduction-fixe.md)). Crucially, the "can concurrent writes garble output?" uncertainty was *resolvable* and the R0 ABSTAIN had merely not resolved it: reading the pinned dependency's source (fmt `@40626af8` = v11.2.0: `vprint_buffered` formats into a `memory_buffer` then a SINGLE `fwrite`, flockfile held across format+write) proved each `fmt::print(FILE*,…)` is byte-atomic on the POSIX/buffered path, so concurrent writes can only reorder whole lines, not garble them — which flipped R0→R1 WOULD_APPROVE (the synchronize was doc-only, .cpp byte-identical, so the flip came from *completing the investigation*, not a code change) and the human MEMBER approved the same head. For "can concurrent calls to this sink corrupt output?" questions, read the sink library's source AT THE VERSION THE REPO PINS (fetch raw via `raw.githubusercontent.com` since a repo-scoped token 401s cross-org), and scope the proof honestly — the Windows console/`OutputDebugStringA` paths were left "per-message integrity unproven", not silently generalized ([[approver/challenger-miss] Resolve a concurrency-atomicity gap by reading the dependency's source at its pin, not by guessing — fmt::print is per-line atomic](wiki/learnings/1785421065093-approver-challenger-miss-resolve-a-concurrency-ato.md)).

**The human-disagreement (correct-abstain calibration): slangpy#1076** whole-`TEST_CASE` `doctest::skip()` of two flaky profiler tests — shadow = ABSTAIN_POLICY/OPEN_GAP (the skip also dropped deterministic cross-thread frame-rejection coverage as collateral), human = maintainer merged unchanged with a tracked re-enable (#1077). This is the abstain-vs-merge procedure WORKING, not a false-safe (that label is reserved for WOULD_APPROVE → CHANGES_REQUESTED). For the CLASS of *maintainer-authored, temporary, tracked test-disables*, the bundled-coverage gap is a **legitimate but low-severity OPEN_GAP** informed maintainers routinely accept — keep flagging it (never round up), but frame it as "confirm this temporary trade-off," weighted to the lenient end, since the alternative (leave CI flaking) is worse ([approver/human-disagreement — temporary maintainer test-disable: bundled-coverage OPEN_GAP is real but low-severity; maintainers merge the trade-off](wiki/learnings/1785282531686-approver-human-disagreement-temporary-maintainer-a.md)). Another abstained-where-approved (again milder than a false-safe): slangpy#1082 R4 @`c4ae890` had 0 Devin 🔴 + green CI, but the DECISION_REVIEW gate held an OPEN_GAP on the new `NativeTorchTensorDiffPair` cache-signature keying only the *primal* tensor's signature when both primal+grad exist, so a matching-primal/differing-grad pair could collide. The human (ccummingsNV) merged, and post-merge tracing showed why they were right: in the real autograd dispatch a diff-pair's grad is ALWAYS either `create_zeros_like_tensor(primal)` or the upstream `grad_output` (torch autograd shape invariant), so grad dtype/shape tracks primal and the divergent case isn't reachable. The transferable lesson for a cache-key change that keys on ONE of a multi-tensor aggregate: the superset question ("can the OTHER members diverge in a dispatch-relevant dimension?") must be answered from the CONSTRUCTION path, not the key-builder — trace where the un-keyed field is set before calling it OPEN_GAP; had the `autograd_backward` construction been traced during the challenger (not post-merge) it might have cleared to advisory. Still the *good* failure direction (a human looks) — and Devin run-to-run severity variance is real (the same byte-identical `:126` was 🔴 in R2/R3, informational in R4), so reason from the code, not one run's label ([[approver/human-disagreement] Abstained on a diff-pair cache-key OPEN_GAP (primal-only keying); human merged — invariant held at runtime](wiki/learnings/1785504649372-approver-human-disagreement-abstained-on-a-diff-pa.md)).

Two more human-agreement/disagreement calibration points. **Agreement (full-arc):** #12152 (hpp compute-wrapper prototypes) was decided WOULD_APPROVE on the Devin-only tier and MERGED at the exact decision head after a non-author maintainer approved byte-identically — the WOULD_APPROVE path is calibrated when (a) Step-0 recall predicted the fix shape and the diff matches it axis-for-axis at the pinned head, (b) a guard provably scopes the change to one target, and (c) a reproducing FileCheck test is green on the relevant CI legs ([recall-predicted hpp-emitter fix WOULD_APPROVE vindicated full-arc](wiki/learnings/1785339839478-approver-human-agreement-recall-predicted-hpp-emit.md)). **Disagreement (directionally-correct):** on fork Metal-codegen PR #12142 my ABSTAIN(OPEN_GAP) — the validating `-target metal` test never ran (fork CI stuck at `action_required`, green status false) — met a domain maintainer's APPROVE-on-inspection at the same commit. This is the CONSERVATIVE direction (ABSTAIN vs APPROVE), the opposite of a false-safe, and is exactly the designed route-to-human; do NOT round this class up to WOULD_APPROVE. The only thing that closes the gap is the test actually running — expert approval resolves the PR but doesn't retroactively make "test unrun" false ([fork codegen PR with unrun validating test — ABSTAIN(OPEN_GAP) vs human APPROVE is directionally-correct, not a miss](wiki/learnings/1785353094549-approver-human-disagreement-fork-codegen-pr-with-u.md)).

**A safely-approvable class: the sibling-repo package version bump.** A single-line `pyproject.toml`/`setup.cfg`/`package.json` version bump by a MEMBER on a `bump-vX.Y.Z` branch (rebuild/test wheels against the latest Slang release) is WOULD_APPROVE on the Devin-only fallback — harvest exit 20 here is EXPECTED and correct (production claude-code-action genuinely skips version-bump PRs), NOT a NO_REVIEW_SIGNAL. But probe two version-bump risk classes every time: (1) **second version source-of-truth desync** — code-search the repo at head for the old string and `__version__`, confirming the version lives in exactly one place (slang-torch's `__version__` in `compile.py` is `from torch import __version__`, unrelated); (2) **fetched-dependency version/hash pin desync** — does the diff touch a pin a bump silently invalidates (cf. slang-rhi's CMake `SLANG_VERSION STREQUAL SLANG_HASH_VERSION` guard)? `pyproject.toml` is not a protected path, blast radius is package-metadata-only, and the build job actually producing the wheels is execution-verified packaging ([[approver/human-agreement] slang-torch version-bump PR — Devin-only fallback WOULD_APPROVE, harvest exit 20 is correct (production skips)](wiki/learnings/1785530795140-approver-human-agreement-slang-torch-version-bump-.md)). Confirmed on the join: slang-torch#49 (1.3.21→1.3.22) merged byte-identical at the exact decided SHA — but `mergedBy=jhelferty-nv` is the author with `reviews:[]`, so the agreement is SOFT (author self-merge, zero independent review); it vindicates the *class* (the risk-class challenger probes are the real safety net, not a human gate) but must not be counted as "a maintainer independently agreed" — always pull `mergedBy`+`reviews`+`reviewDecision`, not just the merged SHA ([[approver/human-agreement] slang-torch#49 v1.3.22 WOULD_APPROVE — MERGED byte-identical @decided SHA (author self-merge, soft signal)](wiki/learnings/1785537154821-approver-human-agreement-slang-torch-49-v1-3-22-wo.md)).

**Protected-path board-sync ABSTAINs vindicate cleanly by maintainer merge — with a class-invariance check on head-move.** slangpy-samples#57 (three revisions, all `.github/**` thin callers + a `zizmor.yml`) stayed ABSTAIN_POLICY:no_protected_paths and merged at exactly the R2 decision commit `df17e0f2` after jkwak-work APPROVED with zero follow-ups — an expected-agreement shape (abstain-deferred-to-human → approved-unmodified); the abstain is the *win*, not a coverage loss, since the human approved without changing a line and `nv-slang-bot` lacks the `workflows` permission to push these anyway ([[approver/confirmed] Protected-path-only board-sync onboarding PR → ABSTAIN_POLICY was correctly calibrated (merged unchanged)](wiki/learnings/1785536628434-approver-confirmed-protected-path-only-board-sync-.md)). slang-rhi#804 sharpens the join discipline: it merged 2 commits PAST the R3 decision head with an INDEPENDENT jkwak-work approval (not a bare self-merge) — join-SHA-first caught the head-move, but the decisive extra step is **check whether the moved head stayed in the SAME decision class**: both follow-ups were still `.github/**`, so re-deciding at the merged head yields the identical ABSTAIN and the head-move is calibration-neutral; contrast slang#12095 where a post-decision commit DELETED the exact flagged code, crossing a class boundary and making WOULD_APPROVE@decided-SHA a would-be false-safe. On any `pr_merged` join where the head moved, pull the intervening commits' changed paths and ask "would my clause/verdict have changed at the merged head?" ([[approver/human-agreement] protected-path ABSTAIN survives workflow-only follow-up commits — class-invariance check on join](wiki/learnings/1785536765566-approver-human-agreement-protected-path-abstain-su.md)).

**A human APPROVE over a SHADOW-ONLY finding is NOT evidence the finding was wrong — and a merge AT your decision head means nothing was fixed.** On slangpy#1075 the ABSTAIN_POLICY:OPEN_GAP (R9 @`d001b2b`, the weakened-mip-assertion / Metal cross-layer divergence) met tdavidovicNV's empty-bodied APPROVED ~5 min later and a self-merge at the *same* head `d001b2b` — no intervening commits, the concern shipped unaddressed. Since we run shadow mode and never post, the maintainer had no visibility into the finding; the naive lesson "my ABSTAIN, their APPROVE ⇒ I'm over-conservative, relax" is exactly the wrong update, because it trains the approver to rubber-stamp whatever humans merge. Still `record_human_verdict(APPROVED)` honestly, but classify it as **divergence WITHOUT informed disagreement** (check the approval body — empty here; any comment referencing the concern; any follow-up commit — none): it is neither vindication nor a false-safe, and never a reason to lower the gap/test-integrity bar. On a `pr_merged` join always `gh pr view --json headRefOid,mergeCommit,mergedAt` and compare the merged head to your decision commit BEFORE declaring "vindicated" — if they're equal, no fixes were applied post-decision ([[approver/human-disagreement] Human APPROVED over a shadow-only ABSTAIN — a merge over an unposted finding is NOT evidence the finding was wrong; don't relax the bar](wiki/learnings/1785493492602-approver-human-disagreement-human-approved-over-a-.md)). This rule exists precisely because an earlier write-up of this same PR got it backwards — it invented an "intervening fix" narrative claiming the PR merged at a *later* head with both gaps fixed between, scored as a vindicated AGREEMENT. That is factually wrong and was **RETRACTED**: the PR merged at the same head over the shadow-only finding, and the regression test it cited as "proof the loop worked" is the very test narrowed to mip-0 to green a reproduced Metal failure ([[approver/human-disagreement] RETRACTION of the slangpy#1075 "ABSTAIN vindicated" learning — it was factually wrong; the PR merged AT my decision head over a shadow-only finding](wiki/learnings/1785493972914-approver-human-disagreement-retraction-of-the-slan.md)); the retracted file itself is tombstoned DO-NOT-USE and superseded by the retraction and the authoritative human-disagreement learning ([[RETRACTED — DO NOT USE] slangpy#1075 "ABSTAIN vindicated" — factually wrong; superseded](wiki/learnings/1785493520816-approver-human-agreement-slangpy-1075-abstain-vind.md)). Meta-lesson: celebratory "vindicated" write-ups drift into overclaiming — run the merged-head-vs-decision-head check before writing any `pr_merged` calibration learning.


## Challenger misses of the RELEVANCE class: a true premise that cannot bear on the path in question (2026-08-03 fold)

The 2026-08-03 slang-rhi cluster surfaced a failure family the existing checks are structurally blind to. Every prior challenger discipline on this page interrogates whether a claim is **true** — right file, right line, right commit, claim matches source. These misses were all **true and irrelevant**, and that is worse: a wrong argument gets caught by provenance checking, while a mis-scoped one *passes every check we run*.

**The archetype: read the enclosing guard of every cited line.** On slang-rhi#800 the residency 🔴 was cleared three revisions running on the ground that "EVERY buffer is globally registered via `registerResource` at creation (`metal-buffer.cpp:86`), so it is resident regardless." The finding was about devices **without** a residency set; `registerResource` does all its work inside `if (m_hasResidencySet)` (`metal-device.cpp:611`). So the argument used residency-set-path registration to argue the *fallback* was safe — not a weak argument about the fallback, one that **cannot bear on the fallback at all**. Circular, not merely mis-scoped, and it survived three revisions while being cited as an independent second ground each time, because an argument decorated with real `file:line` reads as mechanism-grounded and a reviewer spot-checking citations confirms them and moves on. The control is two questions, not one — (1) *is it true?* (provenance) and (2) *does it bear on the path in question?* (relevance: name the specific configuration/branch/state the conclusion is about, then check the cited mechanism actually operates in that state). Question 2 is cheap and mechanical for guarded code: `sed -n '<line-20>,<line>p' file.cpp | grep -nE "if \(|else|#if"`; if the guard is `X` and the claim is about `!X`, the citation is inadmissible regardless of correctness. A second-order trap on the way out: a correction that writes "`metal-device.cpp:611-618` adds it to the set" is *true* and **omits the gate**, letting the next reader reconstruct unconditional registration from the correction itself — retract the **mechanism** separately from the **inference**, and state the guard, not just the line range ([[approver/challenger-miss] an argument that cites real file:line but cannot bear on the path — the argument-side twin of the non-discriminating signal](wiki/learnings/1785775240063-approver-challenger-miss-an-argument-that-cites-re.md)).

**"An earlier diagnostic already rejects this" needs the mandatory-path proof, not the diagnostic's existence.** On slang#11118 (`Atomic<T>` as `[__NonCopyableType]` + transitive `typeContainsNonCopyableImpl`) the production bot flagged the new depth cap returning the permissive `false`; the challenger cleared it as pure future-proofing on the theory that the front end rejects anything that deep — an independent critique proved that wrong and the gap became the *principal* ABSTAIN ground. E39997 (`kMaxTypeNestingDepth=128`) is raised by **specific walkers each carrying its own `recursionDepth`** (`slang-check-shader.cpp:604/1307/1509/1645`, `slang-type-layout.cpp:5320`, `slang-check-expr.cpp:2020/2725`, `slang-check-decl.cpp:3173`) — there is no single gate every declaration passes, and E39999 covers inheritance *cycles* only, not a valid deeply-nested acyclic generic struct. Two ordered questions for any diff adding a **bounded** recursive predicate: **which direction does the fallthrough fail** (write out what the cap's return value *means* to every caller — if the permissive value routes to pre-fix behavior, the guard reintroduces the bug at the boundary instead of erroring), and **is the upstream rejection a universal gate or a per-walker counter** (`grep -rn <CAP_CONSTANT> source/` and check whether any site lies on the *mandatory* path to the new code; per-walker `recursionDepth` parameters are the tell). A comment justifying `X` in `if (depth >= CAP) return X;` by asserting which programs are "valid" — here "valid programs have finite-depth struct layouts" — is itself a defect: finite and valid does not imply shallower than a fixed 128 ([[approver/challenger-miss] a depth cap returning the PERMISSIVE value fails OPEN into the very bug the PR fixes; E39997 is not a universal front-end gate](wiki/learnings/1785745165071-approver-challenger-miss-a-depth-recursion-cap-tha.md)).

**"That shape is degenerate / nobody writes that" is a testable claim about behavior, not a licence to clear — compile it.** On slang#12246 (a `pr: breaking change` rejecting non-integer `switch` conditions) I derived WOULD_APPROVE and was overturned at DECISION_REVIEW → ABSTAIN_POLICY:OPEN_GAP, because I cleared a Devin over-rejection flag on the *inferred* premise that a `switch` with no case labels "selects `default` unconditionally ⇒ semantically a no-op ⇒ nobody depends on it." Two probes the critique provoked falsified it: a selector with a side effect + a working default body emits observable HLSL buffer writes at baseline and hits E30607 at head, and `T : IInteger` `default:`-only compiles clean at baseline and is rejected at head — a type parameter *constrained to be an integer* refused for not being one. A no-case-label `switch` is not a no-op: the selector expression is still evaluated (arbitrary side effects), the default body still executes (real control flow), and only the selector's *value* is unused. For any "no-op" control-flow claim, enumerate the three independent parts — is the condition still evaluated (1), does any body still run (2), is the value used (3) — because side effects live in (1)+(2) and a claim that only (3) is dead does not make them dead ([a "no case labels ⇒ semantic no-op" premise was FALSE and overturned my WOULD_APPROVE](wiki/learnings/1785837956189-approver-challenger-miss-no-case-labels-semantic-n.md)). Two aggravating traps to carry: my negative-evidence sweep searched `default:`-only across 196 switches and reported "zero instances" as if exhaustive — it missed empty-body, side-effecting-selector, and constrained-generic variants, so a scope-limited grep reported as a count reads as coverage of the class it doesn't cover; and when a change narrows what's accepted, probe the **constrained-generic** case explicitly, because a predicate keyed on the type's *representation* (`BasicExpressionType`/`EnumDecl`) rather than its *constraints* rejects parameters whose constraints already guarantee the property — the most defensible-looking member of the newly-broken set. A code owner's APPROVE at the pinned head settles the *intended* fork (reject-vs-coerce), not an *undiscussed* narrowing the PR body never mentions; treating a sign-off on the intended change as a sign-off on an unintended side effect is exactly rounding up.

**Citation-uniformity is a mechanical self-check: in an artifact where claims cite `file:line`, the UNCITED sentence is the defect.** The #12246 miss above and a co-occurring orchestrator miss shared one signature — an uncited load-bearing sentence sitting among file:line-cited reads (mine: "no case labels ⇒ no-op"; the orchestrator's: "PASSING spirv-val [0/866] with zero diagnostic text", inferred from a summary line while the log actually held 1732 `- PASS` paired 1:1 with 1732 `- FAIL`). Both authors had been rigorous in the *alarming* direction — re-deriving a bot-authored flake table, constructing off-diagonal CI controls — which is the trap: **peripheral rigor manufactures confidence in the unmeasured centre, and the uncited sentence is the centre.** Run one awk pass over your own draft flagging paragraphs with no `file.ext:NN`, no backtick command, no 6-digit id, and no `N/M` ratio; headings show up correctly-uncited, and what you hunt is a *substantive claim* in that list. It is a grep, not a vigilance rule, and it fired on its own author (an uncited "the predicate is exactly integer-or-enum" — instrumented, the predicate accepts integer-**or-bool**-or-enum at `slang-check-decl.cpp:12038`, cosmetically harmless but imprecise and uncited, which is the point). Two companions: **a replacement rationale is a NEW claim needing its own instrument** — when "runner-scoped to SLANGWIN5" was refuted it was replaced with "the defect reproduces across branches so a rerun re-tests nothing", *also* false and uncited, reading as corrected only because it was newer (being a fix for a known error is not evidence for the fix); and a `runs-on` label set means **scope-of-fault and scope-of-routing are independent** — never infer a dispatch property (which host runs it, whether a rerun helps) from a defect property (where the fault reproduces) ([the uncited sentence is the defect — a mechanical citation-uniformity self-check](wiki/learnings/1785839025292-approver-critique-mustfix-citation-uniformity-in-a.md)).

**A plausible defect found while hunting is the easiest thing to over-credit — run the fix as a counterfactual.** The empty `## Flags` section in a Devin artifact was attributed to `devin-fetch.sh:157` splitting on a real-newline pattern against JSON-quoted `innerText`, and called "confirmed empirically" on the strength of `wc -l` = 1. Decoding first and re-running the *exact* split still yields one part, and `flags?` occurs **zero** times in the scraped page decoded or not — a decode cannot conjure a marker never captured. Actual cause: the done-poll was satisfied *solely* by the `Checks\s*\d+/\d+` CI counter, so the script scraped a page whose Flags panel had not rendered; the flags-toggle click found no matching button and silently no-oped under `|| true`. The missing decode is a **real but latent second bug**, and collapsing two independent defects into one causal story is the error. Before attributing a missing extraction to a *parser*, prove the input contained the thing to extract (`grep -ociE 'flags?' devin-page.txt` → 0 ⇒ capture problem, NOT parse problem), then run the fix as a counterfactual and confirm it changes the outcome ([[approver/challenger-miss] I mis-attributed the empty-Flags defect to the missing json.loads — the real cause is scraping before the panel renders](wiki/learnings/1785787630832-approver-challenger-miss-i-mis-attributed-the-empt.md)). The underlying tool defect stands on its own and is a **review-input integrity** issue, not a nit: `devin-fetch.sh` exited 0 with an empty flags section on slangpy#1090 while Devin had produced **2 Investigate flags** — one of two review sources silently zeroed. Treat "Devin exit 0 + zero flags" as **suspicious, never clean**: a genuinely clean run still renders a `No flags`/`0 Flags` token, so an *absent* flags summary means the scrape was early. Cheap assertion — no `\d+ Flags?`, no `No flags`, no `Analysis complete` ⇒ INCONCLUSIVE (ABSTAIN_INFRA), and auth-gated per-flag detail bodies ("115 lines left") are real signals whose rationale is unavailable: probe each yourself, never record them as cleared ([[approver/challenger] devin-fetch.sh false-clean: a `Checks N/M` readiness branch plus JSON-quoted innerText](wiki/learnings/1785786175123-approver-challenger-devin-fetch-sh-false-clean-che.md)).

**"Pending at poll end" is "not proven yet", never "absent."** Two approver rows recorded `0/0/0` with docs affirmatively stating no CodeRabbit signal existed — and in both the review had landed *before the doc was written* (slangpy#1085: last poll 15:03:39 exit 22 pending, review 15:04:52, doc 15:06:22, with 4 🟠 Major findings sitting on `pulls/N/comments`; slangpy#1063: harvest exit **20** = "genuine skip, none pending", review 9 minutes later). Exit 22 correctly said "pending, review imminent" and the *last* iteration's result was then treated as durable through the following 2m43s; exit 20 is worse because there is no imminence signal at all — `PENDING_STATUS_RE` matches a *pending commit status*, so a bot that hasn't posted its status yet, or posts green without a review object, fires exit 20 and looks authoritative. The two failure modes multiply: because both docs concluded "no review at all", nothing prompted the manual `pulls/N/comments` read that saved every other affected row. Rules: **re-probe X immediately before committing any artifact whose content depends on "X was not available"**; `status green ≠ harvestable review` and no-status-yet ≠ no-review-coming; and phrase every negative finding with its observation time — "CodeRabbit status was pending as of 15:03:39" is auditable, "there is no CodeRabbit signal" is a different, stronger, and here false claim ([[approver/challenger-miss] a poll that ends "pending" means "not proven yet", not "does not exist"](wiki/learnings/1785779216968-approver-challenger-miss-a-poll-that-ends-pending-.md)). The same discipline applies to the reporting side: report the **LAST** occurrence plus the size of the clean run after it, never the first — "first seen 06-24" and "last seen 07-19, then 557 clean files" support opposite decisions from the same data — and remember that a silence in **commentary** is not a silence in the **phenomenon** (log mentions measure who complained, not what occurred) ([[approver/calibration] report the LAST occurrence plus the clean run after it; a silence in commentary is not a silence in the phenomenon](wiki/learnings/1785822559259-approver-calibration-report-the-last-occurrence-pl.md)).
