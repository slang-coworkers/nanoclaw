## TL;DR

- **Single-arg `T(x)` is treated as a coercion `(T)x`, not a ctor overload.** For a `class` this is wrong and aborts lowering; the correct carve-out is *construction-only* (`isDeclRefTypeOf<ClassDecl>(targetType) && (as<NewExpr>(expr) || !targetType->equals(arg->type))`) — a blanket class exclusion regresses identity casts `(C)c`, and gating only on differing-arg-type silently bypasses a user copy ctor for `new C(c)`.
- **Class reference types can't run under `-cpu` COMPARE_COMPUTE or `slangi`** (no `RefPtr` on the LLVM host path; VM segfaults on heap class objects). `//TEST:EXECUTABLE:` (C++ prelude, has `RefPtr`) is the only local path that executes a class.
- **AST classifiers keyed on node type have sharp hierarchy traps:** `InvokeExpr && !OperatorExpr` silently admits every cast; a post-check `as<AssignExpr>` catches `=` but MISSES `+=` (compound assign lowers to an `InvokeExpr`); `BuiltinOperatorExpr` is NOT an `OperatorExpr`. Capture the syntactic shape *before* `CheckExpr` rewrites it.
- **Adding a `ParamPassingMode`/param-type IR op has a completeness checklist far beyond the obvious wiring** — `-Wno-switch` means a missing enum case is a silent runtime default, never a build error. Grep every mirror site (`kIROp_RefParamType`, `ParamPassingMode::Ref`) and classify each.
- **`__constref` and `borrow` are the same internal mode** (`ParamPassingMode::BorrowIn` already exists); only the surface keyword is missing. `BorrowIn` ≠ "readonly ref" — it is an immutable borrow, may copy-into-temp.
- **A whitelist is only correct against the mapping that feeds it** — verify a storage-class/returnable set against BOTH the external validator rule AND the internal emit mapping (`AddressSpace`→`SpvStorageClass`).
- **The PyTorch/CUDA binding pass has a 4-site null-first-block crash class:** a bodyless `[TorchEntryPoint]`/`[CudaKernel]`/`[AutoPyBindCUDA]` decl reaches emit and derefs `func->getFirstBlock()->...`. Per-pass `isDefinition()` guards must cover ALL sibling sites (an earlier pass on the same target crashes first); the root fix is a checker-level rejection.
- **Don't inherit a precedent's severity/gate.** Nesting deny-by-default shipped as a hard error; modifier deny-by-default cannot (100+ silently-tolerated node types) — it needs warning-first + a version gate.

## The single-arg class coercion saga (#12485 → #12519)

Four atoms trace one fix through review rounds and are best read together. shader-slang/slang#12485: `new C(x)`/`C(x)` on a `class` aborted with "could not resolve target declaration for call" because `ResolveInvoke` treats a 1-arg call on a type name `T(x)` as a coercion `(T)x` via `_coerce`, not a ctor overload — for a class, `_coerce` builds a cast, the class/`new` matchup fires E30066 into a *temp* sink, then `_coerce` still returns true so the error-typed expr aborts lowering. The naive fix excludes `ClassDecl` from the fast-path [class types can't run cpu + single-arg coercion trap](../learnings/1786587930985-slang-class-types-can-t-run-under-cpu-compare-comp.md). But a **blanket** exclusion regresses class identity casts `(C)c`/`C(c)` where the arg is already `C` — previously a valid no-op, now E30066 — verified against two independent unfixed binaries (not a rebuild artifact) with a struct-identity-cast control still passing [class identity cast regresses](../learnings/1786589858732-class-identity-cast-c-c-c-c-regresses-when-classde.md). Narrowing to "exclude only when arg type differs" then swings the other way: `new C(existing)` with a user `__init(C other)` is misclassified as identity → the copy ctor is silently bypassed [narrow to construction only](../learnings/1786592881454-excluding-a-class-from-slang-s-single-arg-coercion.md). The correct condition treats *any* `new` as construction: `isClassConstruction = isDeclRefTypeOf<ClassDecl>(targetType) && (as<NewExpr>(expr) || !targetType->equals(arg[0]->type))`, verified empirically to fix the identity-cast regression AND a **latent `new C(c)` miscompile** that silently folded to identity on unfixed master (value 5 not 1005) [round-2 construction-only carve-out](../learnings/1786593371517-slang-12519-round-2-construction-only-carve-out-fi.md).

The saga carries transferable method lessons. Class reference types can only be *executed* locally via `//TEST:EXECUTABLE:` — `-cpu` COMPARE_COMPUTE has no `RefPtr`, and `slangi` segfaults on heap class objects (its `.expected` file is gitignored, `git add -f` it) [class types can't run cpu](../learnings/1786587930985-slang-class-types-can-t-run-under-cpu-compare-comp.md). A verification that only tests distinct-arity ctors passes silently through *both* the identity-cast and copy-ctor bugs — the newly-activated overload path needs a competing-candidate + same-type-arg case with an observable ctor (`__init(C other){ v = other.v + 1000; }`) [narrow to construction only](../learnings/1786592881454-excluding-a-class-from-slang-s-single-arg-coercion.md). And a control-flow theory ("falls through to `_coerceInitializerList`") was wrong and had to be corrected by fprintf-instrumenting the actual binary — `_coerce`'s success-with-error-expr return is counterintuitive; instrument, don't infer, when the path is load-bearing [class types can't run cpu](../learnings/1786587930985-slang-class-types-can-t-run-under-cpu-compare-comp.md). Devin caught the identity-cast regression while nv-slang-bot dropped it at 25% confidence as "intended" — a miscall, so verify A/B reviewer disagreements empirically before trusting a drop [class identity cast regresses](../learnings/1786589858732-class-identity-cast-c-c-c-c-regresses-when-classde.md).

## AST-classifier hierarchy traps (expression-statement diagnostics)

Two atoms from the #12428 diagnostic family expose how AST node-type checks silently misclassify. The idiom `as<InvokeExpr>(e) && !as<OperatorExpr>(e)` for "a genuine call" is wrong: a cast `(int)x` is an `InvokeExpr` (via `TypeCastExpr`) and is NOT an `OperatorExpr`, so the idiom admits every cast — exclude `TypeCastExpr` explicitly [expr-statement classifier admits casts](../learnings/1786628675117-slang-expr-statement-classifier-invokeexpr-operato.md). Symmetrically, a discarded-result carve-out specified as "the peeled expr is an `AssignExpr`" catches `=` but MISSES `+=`: the parser builds only plain `=` as `AssignExpr`, while `+=`/`-=` become an `operator+=` `InvokeExpr`/`InfixExpr` — the carve-out must key on the assignment *family* by operator [discarded-result carve-out misses +=](../learnings/1786618264260-discarded-result-carve-out-post-check-as-lt-assign.md). Both atoms flag a second hazard: `BuiltinOperatorExpr` is a *distinct* base (not an `OperatorExpr`), and `CheckExpr` rewrites some operators (`==`, potentially builtin `++`/`--`/compound-assign) onto it — so a post-`CheckExpr` syntactic classifier can false-positive on rewritten forms; capture the shape before `CheckExpr` [expr-statement classifier](../learnings/1786628675117-slang-expr-statement-classifier-invokeexpr-operato.md). The discarded-result atom also records live language-version facts (`SLANG_LANGUAGE_VERSION_202C = 2027` is merged, `LATEST=2026`; new diagnostics are Lua-driven; a `warning[E309xx]` `CHECK-NOT` must match `[E309xx]` not `warning 309xx` or it passes vacuously) [discarded-result carve-out](../learnings/1786618264260-discarded-result-carve-out-post-check-as-lt-assign.md).

## Parameter-passing modes and representation completeness

`__constref` and `borrow` are surface synonyms for one already-existing internal mode: `ParamPassingMode::BorrowIn`, `BorrowModifier`, and `IRBorrowInParamType` all exist; only the parser keyword `borrow` is missing, so "retire `__constref`" is a keyword+rename consolidation, not a feature. `BorrowIn` ≠ "readonly ref" — it is an immutable borrow that may be implemented by copy-into-temp, distinct from aliased mutable `Ref` [__constref vs borrow](../learnings/1786747414720-slang-constref-vs-borrow-mode-already-exists-only-.md). Adding a *new* `ParamPassingMode`/param-type IR op has a completeness checklist that the build will NOT enforce: `-Wno-switch` is set, so a missing enum case is a silent runtime default, never a compile error. Beyond the obvious wiring, five site classes silently mishandle a new mode — `slang-ir.h.lua` `excluded_types` (generated-vs-hand-written builder collision, the one caught pre-build), `isWrapperType`, `isPtrLikeOrHandleType`, `setFuncTypeIntoRequirementDecl` (`default: break` drops the mode → param becomes `In`), and two backward-autodiff switches. Find them all by grepping every mirror site (`kIROp_RefParamType`, `ParamPassingMode::Ref`) and classifying each front-end/structural vs late-codegen [ParamPassingMode completeness checklist](../learnings/1786886292433-adding-a-parampassingmode-param-type-ir-op-the-ful.md). Representation-only tests must leave new-mode functions DCE-unreferenced (a reachable one hits `unhandled type for C/C++ emit`) and confirm the front-end ran via `-dump-ir` mangled names [same](../learnings/1786886292433-adding-a-parampassingmode-param-type-ir-op-the-ful.md).

Splitting a shared base out of `GenericDecl` (adding `ParameterizedDecl` under `GenericDecl` + a new `TemplateDecl`) is ABI-safe because AST serialization is base-then-derived and **name-agnostic** — the intermediate class name is not in the byte stream, only the field sequence, and there is no hand-maintained AST stable-name registry (unlike IR). Three companion facts: `CompleteDecl` special-cases the inner-wrapping parent (generalize `as<GenericDecl>` → `as<ParameterizedDecl>`); visitor fallback auto-chains up the hierarchy so an unchecked `TemplateDecl` is a safe no-op; and `template` must stay a legal identifier (gate parsing on HLSL mode + a following `<`, don't reserve it) [ParameterizedDecl base split](../learnings/1786747451039-slang-parameterizeddecl-base-split-serialization-c.md). A "permitted set" whitelist (e.g. which pointer address spaces may be a function result under SPIR-V Logical) is only complete against the mapping that feeds it: verify from BOTH the external validator rule (`external/spirv-tools/.../validate_function.cpp`) AND the internal emit mapping (`addressSpaceToStorageClass`), because two enum values can collapse to one SPIR-V class and a class may be spelled differently (`UserPointer`, not "PhysicalStorageBuffer") [storage-class returnable whitelist](../learnings/1786887728177-verify-a-storage-class-returnable-whitelist-agains.md).

**Rollout severity is not inheritable.** Both the nesting allow-list and the modifier allow-list invert allow-by-default to deny-by-default, but they diverge: nesting shipped as a hard error with no version gate (a nesting violation is almost always genuinely invalid), while the modifier check *cannot* flip straight to error because 100+ node types flow through it and real programs carry silently-tolerated no-op modifiers — so a blanket hard error is breaking and needs warning-first + a language-version gate. Verify whether a precedent's inputs were "almost always invalid" vs "often historically tolerated" before assuming its severity is safe [nesting vs modifier deny-by-default](../learnings/1786785549456-nesting-deny-by-default-shipped-as-hard-error-modi.md).

## The PyTorch/CUDA binding-pass bodyless-crash class

Five atoms converge on one crash class in `source/slang/slang-ir-pytorch-cpp-binding.cpp`: a body-less function carrying `[CudaKernel]`/`[TorchEntryPoint]`/`[AutoPyBindCUDA]` reaches the emit passes and null-derefs `func->getFirstBlock()->...` (SIGSEGV, zero diagnostics), because the front end (`checkCudaKernelAttribute`) imposes no body requirement. There are **four distinct sites**, and treating any one as "the" bug is the trap — `generateCppBindingForFunc:394`, `lowerBuiltinTypesForKernelEntryPoints:1122`, `generateDerivativeWrappers:1416/:1482`, and `generateCUDAWrapperForFunc:1055` (a *different* mechanism: null dispatch-arg after E56001) [4-site crash class](../learnings/1786580792355-slang-pytorch-cpp-binding-pass-bodyless-kernel-dec.md). The **load-bearing dedup lesson**: a per-pass `isDefinition()` guard added to `generateCppBindingForFunc` (PR #12514, #12512) structurally cannot cover `:1122` — pass order runs `lowerBuiltinTypesForKernelEntryPoints` *first*, and `-target cuda` never runs `generatePyTorchCppBinding` at all; verify which pass runs on which target and grep the fix PR's diff for the specific function name before ruling a sibling covered [4-site crash class](../learnings/1786580792355-slang-pytorch-cpp-binding-pass-bodyless-kernel-dec.md) [bodyless crash spans multiple passes](../learnings/1786579719656-bodyless-kernel-decorated-funcs-crash-in-multiple-.md) [bodyless TorchEntryPoint decl SIGSEGV](../learnings/1786573560084-slang-pytorch-binding-pass-bodyless-torchentrypoin.md). The principled fix closes all four at once at the semantic-checker level (reject bodyless kernel decls), at the cost of possibly over-rejecting legitimate external/intrinsic decls — a maintainer scope call.

A neighboring atom demonstrates verifying-not-pattern-matching a reviewer's "same bug class" hypothesis: a WITH-BODY `[TorchEntryPoint]` with an unmappable param does NOT crash (it diagnoses E55102/E55101 cleanly, and the transiently-malformed FuncType is harmless because loop 2 re-runs before any consumer reads it), but the *bodyless* declaration does — refuting the stated trigger while surfacing the genuine adjacent bug [unmappable param doesn't crash, bodyless does](../learnings/1786572329515-torch-torchentrypoint-unmappable-param-does-not-cr.md). The AutoPyBindCUDA null-deref (#12483) is the sibling *null-type-after-diagnostic* mechanism: fix at the **producer** (bail with `removeAndDeallocate()` so the abandoned func never gets the decoration the binding worklist keys on) plus `SLANG_ASSERT(sink->getErrorCount() > 0)` at the bail to make "diagnose-then-abort" self-checking; a `//DIAGNOSTIC_TEST` won't catch a crash (matches only stderr) — use `//TEST:SIMPLE(filecheck=CHECK)` asserting `result code = -1` + the diagnostic [AutoPyBindCUDA null-deref-after-diagnostic](../learnings/1786558315964-autopybindcuda-null-deref-after-diagnostic-fix-at-.md). Finally, a prelude gotcha in the same torch pipeline: a free function in `slang-cpp-scalar-intrinsics.h` naming `Vector<T,N>` must sit **outside** the `SLANG_PRELUDE_NAMESPACE` block — under torch that macro is defined empty (`namespace {` = anonymous), so a `Vector` forward-declared inside becomes a distinct anonymous-namespace type → ambiguous unqualified `Vector` → broken generated PyTorch C++, invisible to a plain debug build [prelude free-functions Vector namespace trap](../learnings/1786772458436-prelude-free-functions-taking-vector-must-sit-outs.md).
