# Agent GitHub Fork-Takeover and Rebase Mechanics

> Companion to the core [GitHub Auth and Operations in Agent Containers](agent-infra-github-auth-operations.md) and its sibling [Agent GitHub Token Boundaries and Write-Blocks](agent-github-token-boundaries-and-write-blocks.md) (Discussions/workflow write-blocks, invalid-token review, the empty-list trap, and the resolved auth-outage contradiction). This page holds PR takeover from a contributor's personal fork, App-installation-token auth and push mechanics, updating a behind, approved or auto-merge-armed PR (merge-in, approval dismissal, stacked-PR retargets), and the unauthenticated-REST-read fallback / 07-17 diagnostic remainder.

## TL;DR

- **On a contributor's PERSONAL fork the `nv-slang-bot[bot]` App token CANNOT push, even with `maintainerCanModify: true`** — that flag grants push to maintainer *users*, not to the bot App token. Push to **origin** (e.g. shader-slang/slangpy) directly, where the bot has push rights.
- **Takeover mechanic:** cherry-pick the residual commits onto current `origin/main` in a fresh worktree (PRESERVES the original author, unlike a squash) → push the new branch to origin → `gh pr create --draft` a fresh bot-owned PR → call `report_pr_created` → comment "Supersedes #<old>" on the original (do NOT close it — recommend, let the maintainer decide).
- **Verify each dropped hunk is on main verbatim** (`git show origin/main:<file>`) before dropping it in a rebase-takeover — keeps the diff minimal.
- **A draft→ready flip is normally operator-gated**, but an explicit maintainer request on the PR + parent authorization lifts that gate for that specific PR (merge stays human/CI-gated); CI runs on draft PRs too.
- **On `slangpy-samples`/`slangpy` the `GH_TOKEN` is a GitHub App installation token:** `gh auth status` "token invalid" and `gh api user` 403 are EXPECTED (no user identity), and `--jq .permissions` returns all-false and is unreliable — but `gh issue comment`, comment PATCH, and git push work where the App has scope. Use `https://x-access-token:${GH_TOKEN}@github.com/...` for git.
- **Fleet rule (2026-10-23): bring a `BEHIND` or `dirty` PR up to date by merging master (or `main`) into the branch and plain-pushing. Never rebase + force-push.** A force-push rewrites the history that reviewers, bots and review threads are anchored to, and it is a destructive op that needs explicit authorization. In reports write "needs a master merge", not "needs a rebase".
- **Any push after a human approval can cost it.** shader-slang/slang dismisses stale approvals on push: a cosmetic commit dismissed one (#12880), and so did a merge-master push (#12820), though one merge-update kept its approval (#12988). Bundle every nit before a human approves; push afterwards only when a reviewer requires it or the branch must be updated to merge.
- **An approved PR with auto-merge armed that is `dirty` or `behind` never merges, and nothing flags it** (it reads as `awaiting_human`, with CI green). Sweep armed PRs' `mergeable_state` every supervisor tick over REST and nudge the owning fixer session (pinned) to merge master.
- **After pushing to an auto-merge-armed PR, a dismissed approval does not mean "needs re-approval".** GitHub can still enqueue it under the maintainer who armed it. Wait about a minute and check `mergeQueueEntry` and the `added_to_merge_queue` timeline event before reporting a human blocker.
- **A text-clean merge is not a correct merge.** Merging main can flip the meaning of your PR's own lines (slang-rhi#884 `RefPtr`→`InternalRefPtr`), and retargeting a stacked PR after its base squash-merges can bring back a file the base deleted. Grep your added lines for the changed API, and require `git diff --name-only origin/master HEAD` to list exactly your own files.
- **When `gh` suddenly 401s "Bad credentials," the discriminating probe is REST-core-read vs actions/GraphQL** — unauthenticated REST reads can stay up while actions/GraphQL are down, so unauth REST is the read fallback that survives a partial gateway failure. (The 07-16/07-17 outage this came from is RESOLVED — treat the split as diagnostic technique, not current state.)

## PR Takeover From a Contributor's Personal Fork: Bot Pushes to origin, Not the Fork

When taking over a slangpy PR whose head branch lives on a maintainer's PERSONAL fork (e.g. `jhelferty-nv/slangpy`), the `nv-slang-bot[bot]` App token CANNOT push to that fork even when `maintainerCanModify: true` — that flag grants push to maintainer *users*, not to the bot App token (push fails `Authentication failed for '.../jhelferty-nv/slangpy.git'`). Correct prod takeover mechanic (origin = shader-slang/slangpy directly, where the bot has push rights): (1) cherry-pick the residual commits onto current `origin/main` in a fresh worktree — this PRESERVES the original author, unlike a squash; (2) push the new branch to `origin`; (3) `gh pr create --draft` a fresh bot-owned PR, call `report_pr_created`, and comment "Supersedes #<old>" on the original (do NOT close it — recommend, let the maintainer decide). Dropping already-landed hunks during a rebase-takeover keeps the diff minimal — verify each dropped hunk is on main verbatim (`git show origin/main:<file>`) first. A draft→ready flip is normally operator-gated, but an explicit maintainer request on the PR + parent authorization lifts that gate for that specific PR (merge stays human/CI-gated), and CI runs on draft PRs too ([PR takeover from a contributor's personal fork: bot pushes to origin, not the fork](../learnings/1784692103088-pr-takeover-from-a-contributor-s-personal-fork-bot.md)).

## App-Installation-Token Auth and Push Mechanics

On `slangpy-samples`/`slangpy` from the fixer container the `GH_TOKEN` is a **GitHub App installation token**: `gh auth status` reports "token invalid" and `gh api user` 403s as EXPECTED (the App has no user identity), and `--jq .permissions` returns all-false and is unreliable — but `gh issue comment`, comment PATCH, and git push all work where the App has scope. Use `https://x-access-token:${GH_TOKEN}@github.com/...` for git. The same source cleared a stale, red (out-of-date) samples branch with `git rebase origin/main` and a force-push; under the fleet rule below, update such a branch by merging `origin/main` in and plain-pushing instead. Only when a force-push is explicitly authorized, verify the rebase with `git patch-id --stable` (identical patch-id = no content drift) and push with `--force-with-lease=<branch>:<old-sha>` ([slangpy-samples auth + rebase mechanics (App installation token)](../learnings/1784768440116-slangpy-samples-auth-rebase-mechanics-app-installa.md)).

## The Unauth REST Fallback and the 07-17 Diagnostic Remainder

When `gh` calls suddenly 401 "Bad credentials," the discriminating probe is **REST-core-read vs actions/GraphQL**: core REST reads (issues, PRs, repo metadata) can keep working via the unauthenticated path even while the `actions` API and GraphQL calls 401 — so unauthenticated REST is the read fallback that survives a partial gateway/credential failure, and the pattern of which paths fail is what characterizes the problem ([GitHub gateway 401 split: actions+GraphQL down, REST reads OK (diagnostic)](../learnings/1784216892956-github-gateway-401-split-actions-graphql-down-rest.md)).

### This specific outage is RESOLVED

The 07-16/07-17 outage this diagnostic came from is **FIXED** — the App-token refresh cron had silently died on a missing `gh` on the newly-migrated host, so the github.com App token expired hourly and every `actions`/GraphQL call 401'd `Bad credentials`; `gh` 2.96 + a guarded refresh cron + git-push split into non-overlapping secrets restored it (verified recovered 07-17 ~11:47Z). Do NOT hold read-only or assume actions/GraphQL are down. Keep the REST-vs-actions-vs-GraphQL split above as a *diagnostic technique* for a future problem, not a current state, and re-diagnose any new 401 cluster from scratch (which paths fail? is the refresh cron alive / is `gh` present?). Full correction and receipts live on the sibling [Agent GitHub Token Boundaries and Write-Blocks](agent-github-token-boundaries-and-write-blocks.md) page.

## Updating a PR: Merge Master In, Approval Dismissal, and Auto-Merge

**To clear `mergeStateStatus=BEHIND` (or `dirty`) on any PR, merge `origin/master` INTO the branch and push (non-force); do NOT rebase.** This is the fleet rule (parent correction 2026-10-23, shader-slang/slang#13778), not only an approved-PR courtesy. A force-push rewrites history that reviewers and bots are anchored to: CodeRabbit, the explain-diff comment keyed on the head SHA, and review threads. It also counts as a destructive op that needs explicit authorization. In triage and status reports, write "needs a master merge" rather than "needs a rebase", so the fixer is not pointed at the wrong action ([update a behind PR by merging master, not rebase + force-push](../learnings/1792760590201-update-a-behind-pr-by-merging-master-not-rebase-fo.md)). The slang repo requires up-to-date branches, so an approved PR cannot merge until this is done. A merge commit is fast-forward-ahead of the remote branch, so a plain `git push` works with no destructive force-push, and the push AUTO-RERUNS CI on the merged sha (`BEHIND → BLOCKED` pending CI, then mergeable once green). Updating your own fix branch is an allowed code push (not merge/`gh pr ready`/comment), so no operator approval is needed. Watch submodule gitlinks: merging master brings pointer bumps that show as ` M` in `git status`; that is cosmetic and safe, because the merge commit already records master's pointers (do not `git add` them, which would revert the gitlink) ([Clearing mergeStateStatus=BEHIND on an approved PR: merge master in (don't rebase) — preserves approval, no force-push](../learnings/1789535383508-clearing-mergestatestatus-behind-on-an-approved-pr.md)).

**shader-slang/slang has "dismiss stale approvals on push" enabled, so treat any push after a human approval as costing it.** On #12880 a 3-line inline-comment removal silently dismissed maintainer approval of 063478d8a0 and flipped `reviewDecision` back to `REVIEW_REQUIRED` ([shader-slang/slang dismisses human PR approvals on ANY new commit — never push post-approval](../learnings/1789630473550-shader-slang-slang-dismisses-human-pr-approvals-on.md)). A merge-master update is not reliably exempt. On #12988 (2026-09-15) the approval survived it and `reviewDecision` stayed `APPROVED` ([merge master in, don't rebase](../learnings/1789535383508-clearing-mergestatestatus-behind-on-an-approved-pr.md)), but on #12820 (2026-10-15, a `dirty` PR, so the merge carried conflict resolution) the bot's merge-master push logged `review_dismissed` and `reviewDecision=null`. What separates the two cases is untested. Rules: once a human approval lands, do NOT push further commits unless a reviewer requires a code change or the branch must be updated to merge; bundle every nit, including codex/critique fixes, BEFORE the human reviews; defer a COSMETIC must-fix raised after approval. If a dismissal happens on a PR without auto-merge, recover with a plain comment to the approver giving the exact non-behavioral delta (`git diff <approved>..<head> --stat`) and asking for a quick re-approve; do NOT `--add-reviewer`.

**An approved bot PR with auto-merge armed can sit `dirty` or `behind` for weeks, and no classifier flags it.** `scan.py` classifies by who spoke last, so a maintainer APPROVE plus auto-merge reads as `awaiting_human`, and `ci.py` shows ✅ because `DIRTY` isn't `BEHIND`. Supervisor tick 283 (2026-10-15) found three on slang: #13537 (dirty, 28 behind); #13171 (approved 10-12, 66 behind, its only CI run yielded at `wait-for-human-priority` and was never retried); and #12820 (approved 2026-09-03, dirty, 281 behind, stuck six weeks). So every supervisor tick, sweep open PRs with `auto_merge` set and read `mergeable_state`, using REST because `gh pr list` GraphQL often 502s: `gh api 'repos/<o>/<r>/pulls?state=open&per_page=100&page=N' --jq '.[]|select(.auto_merge!=null)|.number'`, then `gh api repos/<o>/<r>/pulls/<n> --jq .mergeable_state`. For each `dirty`/`behind` hit, nudge the owning fixer (the `pr-mappings` session, pinned with `target_session_id`) to merge master with a merge commit and push, which also re-triggers CI. All three fixers acked within 2 minutes of a pinned nudge ([approved bot PR with auto-merge armed can silently never merge](../learnings/1792024370868-approved-bot-pr-with-auto-merge-armed-can-silently.md)).

**After pushing to an auto-merge-armed PR, the approval dismissal is not the next blocker.** On #12820, about 70 s after the dismissal GitHub still logged `added_to_merge_queue`, credited to the maintainer who had armed auto-merge, and the PR merged through the queue with no re-approval. A posted "needs maintainer re-approval" comment had to be edited in place. So wait about a minute after the push, then check GraphQL `pullRequest { mergeQueueEntry { state position } }` and the issue timeline for `added_to_merge_queue`; if the PR is enqueued, the next step is the queue's checks, not a human ([pushing to an auto-merge-armed PR dismisses the approval but GitHub still enqueues it](../learnings/1792025781326-pushing-to-an-auto-merge-armed-pr-dismisses-the-ap.md)).

**A merge that git reports as clean can still be wrong, in two ways.** First, it can change what your PR's own lines mean. "Auto-merged cleanly" only says the hunks did not overlap textually. On a long-lived slang-rhi branch, main's slang-rhi#884 changed `CommandBuffer::m_trackedObjects` from `std::set<RefPtr<RefObject>>` to `std::set<InternalRefPtr<RefObject>>`; an internal ref keeps the object alive but NOT its device (`getLifetimeOwner`). The PR's pre-existing `retainResource<CommandQueue>(cmd.destQueue)` merged with no conflict, but now retained a PEER device's queue without pinning that device, so the queue could outlive its device. The fix was to stop retaining a pointer replay never dereferences. After merging an ownership, lifetime or semantics change from main, grep your PR's added lines for the changed API (`retainResource`, `RefPtr`, `returnComPtr`, …) and re-derive what each one now means; fix compile breaks in your own tests too (here the test's local `std::set` type had to change), and prove the fix with a revert drill (re-add the old line, the new test fails) ([a text-clean merge can change what your pre-existing line means — slang-rhi #884 InternalRefPtr](../learnings/1791713431371-a-text-clean-merge-can-change-what-your-pre-existi.md)). Second, it can resurrect a file. When stacked PR B (built on A's branch) is retargeted to master after A squash-merges, `git merge origin/master` may report no conflicts and still keep a file A deleted late on its branch: B's earlier merge of A's branch brought the file in, master's squash never had it, so git keeps B's copy. On slang #13384, `matrix-layout-array-coerce-rejected.slang` came back this way. Before committing that merge, run `git diff --name-only origin/master HEAD`; the list must be exactly B's own files, so `git rm` anything else the squash commit doesn't contain, then confirm with `gh pr diff <n> --name-only` ([retargeting a stacked PR after its base squash-merges: deleted files can come back](../learnings/1792018373845-retargeting-a-stacked-pr-after-its-base-squash-mer.md)).
