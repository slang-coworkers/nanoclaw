# Slang's mimalloc integration

## TL;DR

- **One `mimalloc-static` serves the whole build.** Slang's `external/mimalloc` feeds both `slang-compiler` (`SLANG_ENABLE_MIMALLOC`) and SPIRV-Tools (`SLANG_ENABLE_SPIRV_TOOLS_MIMALLOC`). The `mimalloc_revision` in `external/spirv-tools/DEPS` is never read by CMake.
- **The global override is C++-only.** `mimalloc-new-delete.h` replaces `operator new`/`delete`, not `malloc`/`free`. Slang core's raw C allocation sites stay on the system allocator. So enabling the override cross-platform is a mixed-allocator policy decision, not a mechanical change, and "mimalloc for Slang core" is not a turn-key reuse of the SPIRV-Tools integration.
- **mimalloc is now a SHA-pinned submodule.** When a hardening ask says "turn a silent fetch into an error", vendor the source first. v2.5.2 is reachable only from upstream `dev2`, so keep `branch = v2.5.2` in `.gitmodules`.
- **mimalloc >= v2.3.0 with `MI_OVERRIDE` on defines `operator new`/`delete` in Windows /MT static builds**, which gives LNK2005. Fix: a directory-scope `set(MI_OVERRIDE OFF)` before `add_subdirectory(spirv-tools)`. Because CMP0077 is NEW, it shadows both the option and a cache value.
- **A static mimalloc inside a DLL keeps its arenas after FreeLibrary** (+1 GiB reserved per load cycle) unless `mi_option_destroy_on_exit` is enabled from `DllMain(DLL_PROCESS_DETACH, lpReserved == NULL)`.
- **A "routine" 2.x bump hides behaviour changes.** From v2.1.7 to v2.5.2:
  - MSVC silently loses the 10 aligned new/delete overrides unless the including TU gets `/Zc:__cplusplus`. `/permissive-` is not enough.
  - arm64 gets an armv8.1 ISA floor, because `MI_OPT_ARCH` is forced on. `set(MI_NO_OPT_ARCH ON)` keeps the old baseline.
  - Single-config Debug adds `MI_DEBUG=2`. It beats Slang's `MI_DEBUG=1` because CMake sorts definitions. `set(MI_DEBUG ON)` before mimalloc is added fixes it.
  - Windows init moved to CRT/TLS callbacks. Comments that say mimalloc registers an `FlsAlloc` destructor are now stale.
- **Verify every dependency-version claim by tag yourself.** Use a blobless clone, `git show <tag>:<file>`, and a small CMake model project whose defines you read from the generated ninja file. It takes about a minute. `gh api` on `microsoft/*` returns 401 from coworker containers, so use `git ls-remote` and WebFetch instead.

## Scope: the override is C++-only, and "mimalloc for core" is a policy question

"Use mimalloc for Slang core" (#11925) is **not** a turn-key reuse of the existing SPIRV-Tools mimalloc dependency, because the mechanism does not transfer ([mimalloc 'for Slang core' is not a turn-key reuse of the SPIRV-Tools integration](../learnings/1783058024375-mimalloc-for-slang-core-is-not-a-turn-key-reuse-of.md)).

PR #12036 added a new `SLANG_ENABLE_MIMALLOC` override. It is distinct from the long-existing `SLANG_ENABLE_SPIRV_TOOLS_MIMALLOC` (on master since #8419). Always cross-check merge state with `gh pr view --json mergedAt`: a code-reader that read the old option wrongly concluded #12036 had merged. The new option wires `mimalloc-new-delete.h`, which **overrides only C++ `operator new`/`delete`, NOT C allocation**. Slang core has about 24 raw `::malloc`/`::free`/`::realloc`/`posix_memalign` sites across about 12 files. Examples are `StandardAllocator` at `slang-allocator.h:41,45` (the default `List<T>` allocator), `slang-blob.h`, `slang-memory-arena.cpp`, `ScopedAllocation` and aligned-alloc. A new/delete-only override that leaves those C paths on the system allocator is a **mixed-allocator hazard**: memory from mimalloc's `operator new` freed by the system `::free` corrupts the heap. That is why upstream SPIRV-Tools forces `MI_OVERRIDE=0` off Windows, and why #12036 defaults ON only for shared MSVC Windows builds. Extending it cross-platform (#12101) is a per-platform ABI and default-on **policy decision**, not a mechanical fix. The choices are operator-override-only opt-in, full mimalloc-for-core (Mechanism B of #11925), or Windows-only ([mimalloc global new-delete override is C++-only — raw C alloc sites are the cross-platform blocker (#12101/#12036)](../learnings/1784052930371-mimalloc-global-new-delete-override-is-c-only-raw-.md)).

## Sourcing and pinning

At HEAD, `external/mimalloc` is a normal SHA-pinned git submodule (`.gitmodules:67-69`). It is added from `external/CMakeLists.txt` behind the internal `SLANG_BUILD_MIMALLOC`, which is on when `SLANG_ENABLE_MIMALLOC` or SPIRV-Tools mimalloc is on ([external/ deps at HEAD: mimalloc is now a real submodule](../learnings/1784655012400-external-deps-at-head-lua-is-consumed-slang-fiddle.md)). Cite HEAD for this, not the older download-fetch description.

Before that, mimalloc was Slang's only configure-time-download dependency. It was fetched on demand with `git clone --depth 1 --branch v2.1.7 ... OUTPUT_QUIET ERROR_QUIET` (`external/CMakeLists.txt:268-281`), which resolves a mutable tag silently, and post-#12036 that checkout replaced global new/delete for the whole compiler DLL. The #12102 ask was "promote the silent fetch to a `FATAL_ERROR`". The triage lesson still applies: the one-liner is not standalone. `SLANG_ENABLE_SPIRV_TOOLS_MIMALLOC` defaulted ON on Windows, so a bare `FATAL_ERROR` without vendoring would break fresh Windows clones. And an error that fires only on download *failure* does not close the hole, because a moved-tag fetch still succeeds. The principled fix couples both: **vendor as a SHA-pinned submodule, then delete the fetch and error on missing source** ([mimalloc is Slang's only configure-time-download dep; making it an error is gated on submodule-vendoring first (#12102)](../learnings/1784053617554-mimalloc-is-slang-s-only-configure-time-download-d.md)).

When bumping the pin, check which upstream branch carries the tag. v2.5.2 (`2406cc5f`) is reachable only from `dev2`, not from the default branch `main3`, so `.gitmodules` keeps `branch = v2.5.2`. `gh api` on `microsoft/*` returns 401 from coworker containers, so use plain `git ls-remote` plus a blobless clone, and WebFetch for the releases page ([mimalloc v2.1.7→v2.5.2 bump: silent MSVC aligned-new loss, arm64 ISA floor, Windows init moved](../learnings/1792692531203-mimalloc-v2-1-7-v2-5-2-bump-silent-msvc-aligned-ne.md)). mimalloc tags are annotated: dereference them with `git ls-remote <repo> 'refs/tags/vX.Y.Z^{}'`, and decode the version from `MI_MALLOC_VERSION` in `include/mimalloc.h` (20302 = v2.3.2) ([slang external/mimalloc feeds SPIRV-Tools' build](../learnings/1784083959740-slang-external-mimalloc-feeds-spirv-tools-build-sp.md)).

## There is exactly one mimalloc in a Slang build

When SPIRV-Tools is built as a subdirectory inside Slang, it does NOT fetch its own mimalloc. Slang's `external/CMakeLists.txt` sets `mimalloc_SOURCE_DIR = ${MIMALLOC_PATH}` and `SPIRV_TOOLS_USE_MIMALLOC` before `add_subdirectory(spirv-tools)`, and SPIRV-Tools' CMake then does `set(MIMALLOC_DIR ${mimalloc_SOURCE_DIR})` and `add_subdirectory(...)`. Both link the same single `mimalloc-static` target. Its name is unchanged across 2.1.7, 2.3.2 and 3.3.2, so #12036's `target_link_libraries(slang PRIVATE mimalloc-static)` is version-agnostic. The `mimalloc_revision` in `external/spirv-tools/DEPS` is a gclient/gn field that CMake never reads, so "match whatever spirv-tools uses" means reading DEPS for reference only. Pinning Slang's `external/mimalloc` to a different commit than DEPS names is NOT a two-versions mismatch. A perf regression measured in both 2.3.2 and 3.3.2 once reconciled the pin back to v2.1.7 `8c532c32c3`, the original pre-#12036 pin ([slang external/mimalloc feeds SPIRV-Tools' build; spirv-tools DEPS is NOT a CMake input](../learnings/1784083959740-slang-external-mimalloc-feeds-spirv-tools-build-sp.md)). One source does not mean one copy at run time: with `SLANG_ENABLE_MIMALLOC=ON` (v2.5.2 branch, Debug, x86_64) that single `mimalloc-static` is linked into about 10 DSOs and executables (libslang-compiler, libslang-glslang, libgfx, libplatform, the test tools, slangc, slang-test). A Debug test run then prints many `mimalloc: error: mi_free: pointer does not point to a valid heap space` lines while the tests pass; memory allocated by one static copy and freed by another is the unverified suspect ([grep impl-Debug.ninja; mimalloc in ~10 DSOs](../learnings/1792697247314-slang-ninja-multi-config-grep-impl-debug-ninja-not.md)).

## mimalloc >= v2.3.0 breaks the Windows /MT link when `MI_OVERRIDE` is on (#13827, fix PR #13850)

microsoft/mimalloc#1075 (commit 09e73bfc, first in v2.3.0) made two changes. CMake now adds `MI_MALLOC_OVERRIDE` to `mimalloc-static` on every platform; v2.1.7 and v2.2.4 add it only `if(NOT WIN32)`. And the `src/alloc-override.c` guard changed from `!_WIN32` to `!defined(_DLL)`. MSVC compiles mimalloc as C++, so under /MT `alloc.obj` now defines global `operator new`/`delete` and replaces CRT `malloc`/`free`/`_aligned_*`. Every TU that includes `mimalloc-new-delete.h` (Slang's `source/slang/slang-mimalloc.cpp`, SPIRV-Tools' `source/mimalloc.cpp`) then fails with LNK2005. The shared `mimalloc-static` is created by SPIRV-Tools, which does `push_variable(MI_OVERRIDE 0)` only off Windows. Slang's own `MI_OVERRIDE OFF` (external/CMakeLists.txt:352) sits in a `NOT TARGET mimalloc-static` fallback that never runs on default Windows. The fix is a directory-scope `set(MI_OVERRIDE OFF)` before `add_subdirectory(spirv-tools)`. Because CMP0077 NEW is set at top level, that normal variable shadows both mimalloc's `option()` and a cache `-DMI_OVERRIDE=ON`. A comment saying the option "only matters for v2.3.0+" is wrong: even in v2.1.7, `MI_OVERRIDE` affects the shared `mimalloc` target (which Slang does not link) and adds `-fno-builtin-malloc` on Clang/GNU ([mimalloc >=2.3 static lib defines operator new on Windows /MT when MI_OVERRIDE=ON](../learnings/1792625455919-mimalloc-2-3-static-lib-defines-operator-new-on-wi.md), [mimalloc v2.3.0+ makes MI_OVERRIDE affect Windows static builds; verify dependency-version claims by tag yourself](../learnings/1792631657927-mimalloc-v2-3-0-makes-mi-override-affect-windows-s.md)).

Linux cannot show the Slang failure as-is, because SPIRV-Tools forces `MI_OVERRIDE=0` there. To reproduce on Linux, copy `external/spirv-tools` outside the tree, delete the `if (NOT WIN32) push/pop_variable(MI_OVERRIDE …)` pair, and configure with `-DSLANG_OVERRIDE_SPIRV_TOOLS_PATH=<parent-of-copy>` (plus `-DSLANG_OVERRIDE_MIMALLOC_PATH=<dir containing mimalloc/>` for a newer allocator). GNU ld then reports the same duplicate `operator new/delete` that MSVC reports as LNK2005. A smaller model is v2.5.2 `mimalloc-static` built with `MI_OVERRIDE=ON` and linked with a TU that includes `mimalloc-new-delete.h`, which gives 20 multiple-definition errors. A Linux build with mimalloc enabled prints about 33 `mimalloc: error … not a valid heap space` lines at slangc runtime both before and after the fix; that is pre-existing noise, not a regression signal ([Model SPIRV-Tools' Windows mimalloc branch on Linux to reproduce /MT duplicate-operator links](../learnings/1792630125136-model-spirv-tools-windows-mimalloc-branch-on-linux.md)). On #13850 the reviewer inner CLIs could not fetch upstream sources and marked the version claims "unverified". Checking them takes about a minute with the method in [Verifying a mimalloc claim](#verifying-a-mimalloc-claim-without-the-target-compiler) ([verify dependency-version claims by tag yourself](../learnings/1792631657927-mimalloc-v2-3-0-makes-mi-override-affect-windows-s.md)).

## A static mimalloc in a DLL never unmaps its arenas on FreeLibrary (#13828)

Slang links mimalloc v2.1.7 statically into slang-compiler.dll (`SLANG_ENABLE_MIMALLOC`, default on for Windows+MSVC+SHARED) and into slang-glslang.dll (through SPIRV-Tools-opt, `SLANG_ENABLE_SPIRV_TOOLS_MIMALLOC`). As a static lib, v2.1.7 registers `atexit(mi_process_done)` (init.c:534). On FreeLibrary that does `FlsFree` and a forced collect, but it unmaps arenas only when `mi_option_destroy_on_exit` is set (`_mi_arena_unsafe_destroy_all`, arena.c:693-724), and it skips other live threads' heaps (init.c:451). A Linux dlopen/dlclose harness measured +1 GiB reserved per cycle (the `arena_reserve` default) plus committed pages for each live host thread. The fix is a `DllMain` that calls `mi_option_enable(mi_option_destroy_on_exit)` on `DLL_PROCESS_DETACH` with `lpReserved == NULL`; growth then drops to about 8 KiB per extra thread per cycle (`mi_thread_data_t` from `_mi_os_alloc`). The timing works because the MSVC CRT runs DllMain, then static destructors, then atexit functions, so `mi_process_done` sees the option after static destructors have freed their memory. Process exit (`lpReserved != NULL`) stays untouched. Harness: build mimalloc with `-DMI_OVERRIDE=OFF -DMI_BUILD_STATIC=ON -DCMAKE_POSITION_INDEPENDENT_CODE=ON` and link it into a .so with `-Wl,--exclude-libs,ALL` ([mimalloc v2.1.7 static-in-DLL: FreeLibrary never unmaps arenas unless destroy_on_exit is set from DllMain](../learnings/1792626537030-mimalloc-v2-1-7-static-in-dll-freelibrary-never-un.md)). Two more v2.1.7 source facts from the #13867 review bound that fix. `mi_process_done` always calls `FlsFree(mi_fls_key)` (init.c:631 → prim/windows/prim.c:638-642), so unloading the DLL leaves no dangling FLS destructor, and the `isUnclosable` comment's claim that Slang's mimalloc never frees its FLS index does not match the source [CI SLANG_RUN_SPIRV_VALIDATION + mimalloc FLS](../learnings/1792682583662-slang-test-ci-exports-slang-run-spirv-validation-1.md). The `atexit(&mi_process_done)` registration from a `.CRT$XIU` initializer exists only under `_MSC_VER`; MinGW/GCC uses `__attribute__((constructor))` (init.c:706-710), which is not ordered before C++ static constructors, so the DllMain fix is provably safe only for MSVC/clang-cl [CI SLANG_RUN_SPIRV_VALIDATION + mimalloc MinGW atexit](../learnings/1792684928939-slang-ci-exports-slang-run-spirv-validation-1-a-o0.md). The v2.5.2 init changes below move this teardown path, so re-run the harness after a bump instead of assuming the fix carries over.

## v2.1.7 → v2.5.2: hidden behaviour changes in a "routine" bump (#13875, PR #13879)

Each of these was checked with `git show <tag>:<file>` in a blobless clone.

**MSVC silently loses the aligned new/delete overrides.** Upstream commit 7f76037a (2026-07, v2.4.x and later) changed the guard at `include/mimalloc-new-delete.h:51` from `__cplusplus > 201402L || defined(__cpp_aligned_new)` to `&&`. MSVC reports `__cplusplus == 199711L` unless `/Zc:__cplusplus` is passed, and `/permissive-` does not enable it. Neither Slang nor SPIRV-Tools passes the flag, so every TU that includes the header (Slang's `source/slang/slang-mimalloc.cpp`, and SPIRV-Tools' `source/mimalloc.cpp` in SPIRV-Tools-opt and SPIRV-Tools-diff) stops overriding the 10 aligned overloads. The pairs stay matched with the CRT, so nothing crashes, but over-aligned allocations bypass mimalloc. `dev2`, `main3` and v3.5.4 all keep `&&`. PR #13879 adds a per-file `COMPILE_OPTIONS "$<$<CXX_COMPILER_ID:MSVC>:/Zc:__cplusplus>"` with `SKIP_PRECOMPILE_HEADERS ON`, and reaches the submodule file with `set_source_files_properties(... TARGET_DIRECTORY SPIRV-Tools-opt SPIRV-Tools-diff ...)` ([mimalloc >= 2.5 (since 7f76037a) drops aligned operator new/delete on MSVC unless /Zc:__cplusplus](../learnings/1792701407276-mimalloc-2-5-since-7f76037a-drops-aligned-operator.md), [mimalloc v2.1.7→v2.5.2 bump](../learnings/1792692531203-mimalloc-v2-1-7-v2-5-2-bump-silent-msvc-aligned-ne.md)).

**arm64 builds get a higher ISA floor.** v2.5.2 `CMakeLists.txt:161-165` forces `MI_OPT_ARCH` ON on arm64 unless `MI_NO_OPT_ARCH` is set, and then adds `/arch:armv8.1` (MSVC, not clang-cl) or `-march=armv8.1-a` to the mimalloc sources. v2.1.7 added no arch flags. `set(MI_NO_OPT_ARCH ON)` before mimalloc is added keeps the old baseline ([mimalloc v2.1.7→v2.5.2 bump](../learnings/1792692531203-mimalloc-v2-1-7-v2-5-2-bump-silent-msvc-aligned-ne.md), [mimalloc >= 2.5 drops aligned operator new/delete on MSVC](../learnings/1792701407276-mimalloc-2-5-since-7f76037a-drops-aligned-operator.md)).

**Single-config Debug gets `MI_DEBUG=2`, which overrides Slang's `MI_DEBUG=1`.** v2.5.2 `CMakeLists.txt:326-330` adds `MI_DEBUG=2` to `mi_defines` when `CMAKE_BUILD_TYPE MATCHES "Debug"`; v2.1.7 added only `MI_DEBUG=3`, and only for `MI_DEBUG_FULL`. Slang sets `$<$<CONFIG:Debug>:MI_DEBUG=1>` on `mimalloc-static` (`external/CMakeLists.txt` about line 368). In a `-G Ninja -DCMAKE_BUILD_TYPE=Debug` build the compile line becomes `-DMI_DEBUG=1 -DMI_DEBUG=2`. CMake keeps compile definitions in a sorted set, so level 2 wins and each of the 16 mimalloc sources warns "MI_DEBUG redefined". Adding Slang's define later does not help, because generators emit definitions sorted rather than in call order; `-dM -E` on a command from `ninja -t commands` shows `#define MI_DEBUG 2` ([CMake sorts compile definitions](../learnings/1792707403738-cmake-sorts-compile-definitions-a-later-target-com.md)). The fix, tested in a model project, is `if(CMAKE_BUILD_TYPE MATCHES "Debug" AND NOT MI_DEBUG_FULL) set(MI_DEBUG ON) endif()` before mimalloc is added; mimalloc's `elseif(MI_DEBUG)` branch then emits `MI_DEBUG=1`, which agrees with Slang. Multi-config generators (Slang's presets and CI) are not affected, but they hide a trap: with `CMAKE_BUILD_TYPE` empty, mimalloc forces its directory-scoped `CMAKE_BUILD_TYPE` to Release, so `MI_BUILD_RELEASE` is defined in every config, Debug included. The v2.5.2 `types.h:71` default is then `MI_DEBUG 0`. Slang's generator expression defines `MI_DEBUG` explicitly, and that is the only reason Debug keeps level 1 ([mimalloc v2.5.2 adds MI_DEBUG=2 in single-config Debug, overriding Slang's MI_DEBUG=1; multi-config forces MI_BUILD_RELEASE](../learnings/1792703100008-mimalloc-v2-5-2-adds-mi-debug-2-in-single-config-d.md)).

**Windows init and teardown moved.** v2.1.7 used `.CRT$XIU` and then `atexit(mi_process_done)` in `src/init.c`. v2.5.2 defaults to `MI_WIN_INIT_USE_CRT_TLS` in `src/prim/windows/prim.c`: a `.CRT$XIB` initializer calls `atexit(mi_crt_done)` for DLLs only, and TLS callbacks (`DLL_THREAD_DETACH`) handle threads and EXE detach. FLS is used only under the deprecated `MI_WIN_USE_FLS`, so any Slang comment that says mimalloc registers an `FlsAlloc` destructor (for example in `slang-platform.cpp` and the unclosable-library unit test) became stale with the bump. `mi_option_enable(destroy_on_exit)` (value 1) still tears memory down; the new value 2 or higher skips automatic process-done entirely (`init.c:732-735`). On MinGW, the CRT_TLS path applies only if `$ENV{MSYSTEM}` is `UCRT64` at configure time; otherwise it uses `__attribute__((constructor/destructor))` in `src/prim/prim.c` ([mimalloc v2.1.7→v2.5.2 bump](../learnings/1792692531203-mimalloc-v2-1-7-v2-5-2-bump-silent-msvc-aligned-ne.md), [mimalloc v2.5.2 adds MI_DEBUG=2](../learnings/1792703100008-mimalloc-v2-5-2-adds-mi-debug-2-in-single-config-d.md)).

**What did not change.** None of the options Slang sets (`MI_OVERRIDE`, `MI_BUILD_*`, `MI_INSTALL_TOPLEVEL`, `MI_DEBUG_FULL`) was renamed or removed. `MI_DEBUG` is now an option (default OFF), so the `MI_DEBUG=1` generator expression still works. `MI_USE_CXX` is now a "DEFAULT" string, but v2.1.7 already forced C++ for MSVC (CMakeLists.txt:103-105), so only clang-cl changes ([mimalloc v2.1.7→v2.5.2 bump](../learnings/1792692531203-mimalloc-v2-1-7-v2-5-2-bump-silent-msvc-aligned-ne.md)).

## Verifying a mimalloc claim without the target compiler

Clone with `git clone --filter=blob:none`, then either `git show <tag>:CMakeLists.txt` or `git worktree add <dir> <tag>`. Build a small (about 15-line) CMake model project that adds mimalloc the way Slang does, and read the effective defines without compiling: `ninja -t commands mimalloc-static`, `get_target_property(mimalloc-static COMPILE_DEFINITIONS)`, or a grep for `-DMI_*` in the `alloc.c.o` rule of `<build>/CMakeFiles/impl-Debug.ninja` (Ninja Multi-Config) ([mimalloc v2.5.2 adds MI_DEBUG=2](../learnings/1792703100008-mimalloc-v2-5-2-adds-mi-debug-2-in-single-config-d.md), [verify dependency-version claims by tag yourself](../learnings/1792631657927-mimalloc-v2-3-0-makes-mi-override-affect-windows-s.md)). To check where an MSVC-only per-source option lands from Linux, temporarily swap the generator expression to `$<$<CXX_COMPILER_ID:GNU>:-DPROBE=1>`, configure into a scratch directory, and grep `CMakeFiles/impl-Debug.ninja` for the objects that carry `PROBE` ([mimalloc >= 2.5 drops aligned operator new/delete on MSVC](../learnings/1792701407276-mimalloc-2-5-since-7f76037a-drops-aligned-operator.md)).
