# GitHub PR and Bot Operations

Rules and failure modes for the `nv-slang-bot` GitHub App on `shader-slang/slang`: commit identity, PR ownership, permission walls, merge queue, issue/PR close and linkage hygiene, and conflict resolution.

## TL;DR

- **Commit identity:** author email `274397474+nv-slang-bot[bot]@users.noreply.github.com` (Bot User ID, not App ID 3311378); exactly one co-author trailer at the operator's verified `nvidia.com` address. Read `feedback_commit_author.md` before a session's first commit.
- **A bare `nv-slang-bot@users.noreply.github.com` maps to unsigned User 286953280** → `license/cla` fails, `BLOCKED`. Causes: a container restart resetting `user.email`, or a `git -c user.*` override. Run plain `git commit`; check `git log --format='%an <%ae>' origin/<base>..HEAD` before pushing. Repair by re-authoring (never revert — CLA scans every commit) and an operator-gated force-push.
- **A `fix/issue-<N>` branch name does NOT prove a PR is ours** — humans use it on forks. Settle it with `gh api .../pulls/<n> --jq '{author:.user.login, head_repo:.head.repo.full_name}'`, testing the author suffix-tolerantly. CI on someone else's PR is not our signal; a verified bot PR's regression IS ours — flag it to the parent for fixer dispatch.
- **Dev↔Prod is an intentional A/B test** (both `nv-slang-bot[bot]`; dev `fix/issue-*`, prod `dev/slang-fixer/*`). Never consolidate, close duplicates, or push onto a prod branch.
- **Workflows wall:** the App lacks `workflows` write, so a push whose tip tree differs in `.github/workflows/*` is rejected even if our commits touch none; `--dry-run`/`ls-remote` give false positives. It also blocks enqueueing workflow-touching PRs.
- **Merge queue:** the bot cannot enqueue ANY PR (audit `left`; `gh run rerun --failed` works). Concurrent appends to one public enum collide (`duplicate case value`) — renumber above the highest claimed value.
- **Never close issues/PRs** — a PreToolUse hook hard-blocks `gh issue close`, GraphQL `closeIssue(` and `state=closed`, even when a maintainer asks and the parent approves, and refuses any Bash text containing the command. Post "ready to close; a maintainer can close it"; a human closes.
- **Only a PR body keyword auto-closes** (`close[sd]`/`fix(e[sd])`/`resolve[sd]` + optional `owner/repo` + `#N`) — not the title, not the commit subject. Never write `fixes #N` in prose about another PR. Verify `closingIssuesReferences` before, and issue state after, merge; a zero-hit grep needs a positive control.
- **Check for an existing fix PR at triage time AND right before posting or opening a PR.** `gh issue view <n> --json closedByPullRequestsReferences` lists keyword-linked PRs at once; `gh pr list --search` lags by minutes. Add `gh pr list --author <reporter> --state all` for unlinked ones; upstream, search open PRs by function/file and by the reporter.
- **An overlapping PR is a claim to test, not to trust.** Build its head in a detached worktree and run your own repros and regression tests on it before ceding your bug or reporting "no change"; it often fixes only part of the set.
- **If another PR lands your fix first:** merge master, resolve the shared file to master's version, keep only what still adds coverage, and rewrite the title, description and explanation.
- **`CHANGES_REQUESTED` with a positive body and no inline comments = decline-to-merge**, not an edit request.
- **Before pushing a conflict fix after `@copilot resolve the merge conflicts`, fetch** — adopt Copilot's equivalent commit.
- **A recurring conflict on an approved PR can mean a competing fix merged** — surface close-vs-rework, don't mechanically resolve.
- **A master merge after a follow-up landed is a semantic conflict**; cleanly auto-merged hunks can reintroduce the replaced convention. If master fixed the same bug differently, read master's test and default to it.
- **`--force-with-lease` `stale info` with no competing push = stale or missing remote-tracking ref**; lease explicitly against `FETCH_HEAD`.
- **The App cannot open a PR into a personal fork via `gh pr create`**; fall back to a master-based draft PR plus a cherry-pick recipe.

## Bot identity and commit authorship

The App ID (`3311378`) appears in webhook/installation contexts; the commit author email must embed the Bot **User ID** — `274397474+nv-slang-bot[bot]@users.noreply.github.com` — or commits get a ghost avatar. Each bot commit carries exactly one co-author trailer crediting the operator at their verified `nvidia.com` address; a fabricated id can resolve to another user ([authorship](../learnings/1780558703304-CONSOLIDATED-github-commit-authorship.md)). Read the `feedback_commit_author.md` memory file before the first commit: one incident shipped four wrong-email commits and needed a 31-commit `filter-branch` rewrite ([read feedback files](../learnings/1779895141195-read-auto-memory-feedback-files-before-authoring-c.md)).

A bare `nv-slang-bot@users.noreply.github.com` (not the account-scoped `<numericId>+<login>@…` form) attributes commits to standalone User `nv-slang-bot` (id `286953280`, CLA unsigned): CLA-assistant reports "N of M committers signed" and `mergeStateStatus=BLOCKED`. Two causes recur. A container restart can reset `git config user.email`, so only post-restart commits regress — diagnose with `git log --format='%h %ae' <branch> --not origin/master`; durable fix is pinning the container's default identity ([scoped noreply](../learnings/1789476879264-bot-commits-must-use-the-account-associated-norepl.md)). And a per-commit `git -c user.name=… -c user.email=…` override beats a correct worktree default: slang#13305 ([`-c` breaks CLA](../learnings/1790645515788-ops-cla-breaks-with-git-c-user-name-c-user-email-c.md)), then #13421 and #12116, where commits 5–9 with the override went pending (12 bot PRs affected) ([never override](../learnings/1791405237001-bot-commits-never-override-git-identity-with-c-use.md)). Never pass `-c user.*`; check authors before pushing. Repair is an operator decision: sign the CLA for 286953280, or set the scoped email and `user.name "nv-slang-bot[bot]"`, re-author (`git commit --amend --reset-author --no-edit` or an `--exec` rebase) and `git push --force-with-lease` after explicit authorization, which loses review context and resets CI. A revert or superseding commit does not help — CLA scans every PR commit — and a squash merge keeps the author. Sweep classification of a pending CLA: [nv-slang-bot identities and the license/cla gate](../concepts/slang-a-bot-cla-identity.md).

## PR ownership classification

Humans (e.g. `szihs`) use `fix/issue-<N>` on their own forks. A PR is ours only if the author is our bot AND the head repo is upstream; otherwise it is watch-only — no push, comment, reaction or CI action. In June the board nearly closed szihs's #11242 (`fix/issue-11002` on `szihs/slang`) and mislabelled his #11234 as ours ([branch ≠ proof](../learnings/1780903497625-bot-owned-vs-human-contributor-pr-fix-issue-branch.md), [fork branch fools](../learnings/1780903498636-branch-name-fix-issue-n-on-an-external-fork-can-fo.md)). One call settles it:

```bash
gh api repos/<o>/<r>/pulls/<n> --jq '{author:.user.login, head_repo:.head.repo.full_name}'
# head_repo != <upstream>  ⇒  fork PR, not ours
```

Test the author suffix-tolerantly: this REST path returns bare `nv-slang-bot` (see the [companion state-verification page](general-misc-github-state-verification-and-bot-hygiene.md)), so strict `[bot]` equality fails closed on our PRs while a branch-name check fails open on others'. On 2026-08-04 a supervisor tick saw a `❌ stale` CI cell for `fix/issue-11004` — `gh run list --branch` keys on branch name only — and nudged the fixer to rebase #11234, again `szihs/slang`. The CI cell was right; the ownership inference was wrong: a branch name authenticates the NAME, never the OWNER, and CI staleness on someone else's PR is not our signal. Read the assigned coworker's history before nudging — the fixer had stood down on both PRs in June with a recorded reason, and contradicting that needs new evidence. A restored capability (`gh` REST) does not re-check premises; re-run them ([head_repo + author](../learnings/1785803367777-a-fix-issue-n-branch-on-a-fork-is-not-ours-resolve.md)).

Conversely, a verified bot PR's regression is ours. In the 2026-09-30 sweep #11709 (`fix/issue-10641`, nv-slang-bot) showed a deterministic ASan SEGV in `Slang::List<ValNodeOperand>::operator[]` across all 13 `test-slang` jobs yet was reported as "needs author attention". Check `gh pr view <n> --json author,headRefName` plus `head_repo` before writing a regression bullet: bot PRs go to the parent for fixer dispatch, only human PRs stay with their author ([route to parent](../learnings/1790734170020-bot-authored-pr-regressions-route-to-parent-not-au.md)).

## Dev↔Prod A/B test separation

Two NanoClaw instances run the slang pipeline on the same live issues as `nv-slang-bot[bot]`, an intentional comparison: don't consolidate or close duplicates, and never push onto a prod (`dev/slang-fixer/*`) branch — it contaminates the data point. All `nv-slang-bot`-authored PRs (including `dev/trelby/*`) are dev-owned and eligible for management actions ([dev↔prod A/B](../learnings/1780558152382-CONSOLIDATED-dev-prod-ab-pr-conventions.md)).

## Workflows permission wall and the merge queue

The App lacks `workflows` write. GitHub compares old vs new tip trees, so a rebase or merge push onto a branch whose tip differs in `.github/workflows/*` is rejected even when our commits touch no workflow file ([stale branch](../learnings/1780567931645-bot-can-t-update-a-stale-pr-branch-when-master-cha.md), [rebased branch](../learnings/1780568708582-bot-can-t-push-rebased-branches-carrying-github-wo.md)). `git push --dry-run` and `git ls-remote` succeed anyway; only a real `--force-with-lease` push confirms ([dry-run false positive](../learnings/1780572980623-git-push-dry-run-is-a-false-positive-for-the-githu.md)). Stripping workflow files to match the old tip is harmful (a squash would revert master's workflow changes); the fix is the permission (org decision) or a human push. The wall also blocks enqueueing a workflow-touching PR, since the queue builds a merge commit carrying the workflow diff ([enqueue second blocker](../learnings/1782727631172-bot-enqueue-of-workflow-touching-prs-has-a-second-.md)).

The bot cannot enqueue ANY PR: `enqueuePullRequest` fails with "not authorized to push to this branch" regardless of authorship, and an apparent auto-requeue is GitHub's own behaviour. Audit action `left`; `gh run rerun --failed` still works ([enqueue blocked](../learnings/1782260121429-bot-enqueuepullrequest-blocked-for-all-prs-not-jus.md)). Two PRs appending to one public enum (`CompilerOptionName`) can each pass CI and still collide in the queue with `duplicate case value`: dequeue via GraphQL `dequeuePullRequest` (gh has no verb), renumber above the highest value claimed across master and the queue-mate, merge master and plain-push (fleet rule is merge, not rebase + force-push; see [Agent GitHub Fork-Takeover and Rebase Mechanics](agent-github-fork-takeover-and-rebase.md)), then wait for a maintainer requeue ([enum collision](../learnings/1782535032557-merge-queue-duplicate-case-enum-collision-two-conc.md)).

## Issue and PR close restrictions

Coworkers never close issues or PRs, not even obvious duplicates. On slang#11719 the bot closed a duplicate of #11568 via GraphQL `closeIssue` (REST `state_reason` PATCH 403s for the App) and maintainer szihs objected: "You should always surface such requests to a human maintainer." Post the verified verdict as a recommendation; if a human objects to a close, re-open and acknowledge ([don't close](../learnings/1782280210918-do-not-autonomously-close-issues-prs-surface-to-a-.md)). The backstop is deterministic: `detectIssueClose()` + `preToolUseHook` in `container/agent-runner/src/providers/claude.ts` blocks `gh issue close`, GraphQL `closeIssue(` and `gh api …/issues/<n> … state=closed`; `gh pr close` is not matched; opt-out `NANOCLAW_ALLOW_ISSUE_CLOSE=1` is unset everywhere ([tool backstop](../learnings/1782270000000-coworkers-must-not-close-github-issues-tool-backstop.md)). It holds even on a maintainer's request with parent approval (slang#12897, 2026-11-06: "Blocked by hook"), and because it matches command text, any Bash call merely containing it (a memory-file edit, a grep) is refused — write such notes with the Edit tool. Verify the fix on master (merge-queue CI log, `gh run view --job <id> --log | grep "passed test"`), reply that the issue is ready and a maintainer can close it, and report up; never write "closing as completed" before a close has succeeded ([hook-blocked on request](../learnings/1793985994981-slang-fixer-cannot-close-issues-closing-is-hook-bl.md)).

## Issue↔PR linkage verification

Auto-close accepts `close/closes/closed`, `fix/fixes/fixed`, `resolve/resolves/resolved` + `#N`, including the qualified cross-repo form (`Fixes shader-slang/slang-rhi#772`); a verifier greps the full set and allows an optional `owner/repo` ([all keywords](../learnings/1781178144676-verify-issue-pr-linkage-with-all-github-auto-close.md), [cross-repo form](../learnings/1781072527758-fixes-closes-link-verification-must-accept-the-qua.md)). Only body-parsed `closingIssuesReferences` close — not a title `Fix #11856`, not the squash commit subject. PR #11866 merged the right fix, but its body keyword pointed at already-closed #11720, so #11856 stayed OPEN while the fixer reported the chain terminal ([closing ref mismatch](../learnings/1782936185036-verify-a-fix-pr-s-closing-reference-matches-the-tr.md)). Incidental prose like `PR #11785 ("...", fixes #11720)` is likewise taken as this PR's closing reference. Put `Closes #<this-issue>` in the body and describe other PRs with plain `#N`; verify `gh pr view <n> --json closingIssuesReferences` after opening and `gh issue view <tracked> --json state` after merge. If a merged fix leaves the issue OPEN, the closest coworker comments flagging the mis-reference so a maintainer closes it ([prose hijack](../learnings/1782951523566-pr-description-prose-fixes-n-closes-the-wrong-issu.md)). A zero-hit keyword audit needs a positive control — an over-anchored grep (`$` against CRLF) returns a confident empty — so run the pattern on a body known to carry the keyword, and prefer GitHub's computed `closingIssuesReferences` over text matching ([positive control](../learnings/1785770932836-the-control-is-the-counterfactual-question-not-a-b.md)).

## Existing-fix checks and review signals

Maintainers often open a fix within minutes of filing, unannounced, so triage and the fixer first check for an open fix PR; the original check was `gh pr list --search "Fixes #<num>"` ([check existing fix](../learnings/1781241842104-check-for-an-existing-fix-pr-before-fixing-or-recommending.md)). That search-index path lags: at triage of slang#14156 it missed the reporter's #14164, opened ~10 min earlier with `Fixes #14156`, costing a 4-day hold. `gh issue view <N> -R <repo> --json closedByPullRequestsReferences` lists every keyword-linked PR immediately; add `gh pr list --author <reporter> --state all --limit 15` for PRs that do not link the issue. On a fork PR, CI / Check Formatting / REUSE show `action_required` until a maintainer approves workflows, so "no CI failures" there means "CI did not run" ([closedByPullRequestsReferences](../learnings/1793960105088-find-a-reporter-s-fix-pr-via-closedbypullrequestsr.md)). Run the check at triage AND again just before posting or `gh pr create`: on #14390 the reporter opened #14391 seven minutes after triage and only a codex OUTPUT_REVIEW note caught it hours later ([re-check before create](../learnings/1794016313091-worktree-hazards-origin-master-is-shared-and-moves.md)). If one exists, stand down silently.

Upstream, linked-PR timelines are not enough: on slang#13230 the bot called its patch "the first proposed fix" for KhronosGroup/SPIRV-Tools#6711, but the reporter had opened SPIRV-Tools#6885 twelve days earlier. Search the upstream repo's open PRs by function/file name and by the reporter and maintainers; a caveat like "unlinked work can't be excluded" means run the search. When `gh api` to KhronosGroup returns 401, WebFetch `https://github.com/<org>/<repo>/pulls?q=is:pr+<term>` or fetch `refs/pull/*/head` ([search upstream](../learnings/1790642860153-before-claiming-no-upstream-fix-exists-search-upst.md)).

**Overlapping in-flight PRs: build them, then decide.** An issue can show no activity while an assignee's PR for a sibling issue fixes its repro anyway: draft #14358 (for #14101) clears #14214's E56004 on SPIR-V/GLSL, but WGSL/Metal still fail and the constant is not folded. On a parked re-check, list the assignees' recent PRs (`gh pr list --author <assignee>`), build any touching the same files in a separate worktree, and re-run the repro set before reporting "no change" ([build overlapping PRs](../learnings/1793982195717-check-overlapping-in-flight-prs-by-building-them-a.md)). Likewise, before agreeing that someone's PR is "the same fix" as yours, run YOUR regression tests and repro on their head. #14346 (vs our #13421, groupshared ordering) fixed #14345 and every #13412 pointer/buffer shape but left all 10 entry-point cases of #13409 broken, because Metal and CPU materialize groupshared as an entry-point-local `IRVar` via `introduceExplicitGlobalContext` and its "local var ⇒ thread-private" exemption still covers it. 13 test variants on their head confirmed the diff-reading prediction in ~15 min, so only the issue it really fixes moved (`Fixes` → "Related to #N (fixed by #M)"). Run them from an untracked dir in a detached worktree at their head, not stacked on their branch ([test before ceding](../learnings/1794007177309-before-ceding-a-bug-to-an-overlapping-pr-run-your-.md)).

A `CHANGES_REQUESTED` review with a positive or neutral body and zero inline comments is a decline-to-merge: fetch `/reviews` and `/comments` first, then reply once acknowledging the verdict and close the chain upstream with no code change ([decline-to-merge](../learnings/1782512263705-changes-requested-with-a-looks-good-body-and-zero-.md)).

## Conflict resolution

**Copilot race.** After a maintainer comments `@copilot resolve the merge conflicts` on a bot PR, Copilot may push too. `git fetch` first; if its resolution is equivalent, `git reset --hard` to it and fast-forward only incremental fixes, never force-push over it ([Copilot race](../learnings/1782711499913-copilot-may-resolve-conflicts-on-bot-authored-prs-.md)).

**Recurring conflict = possible supersession.** On slang#11664 our approved #11665 kept re-conflicting because a narrower rival #11775 had merged and closed the issue (both used diagnostic code 20020). Check issue state and merged rivals (`gh pr list --search "<issue#>" --state merged`) before resolving; don't resolve mechanically or close our PR; surface close-vs-rework with a scope comparison, and if reworking, target only the residual cases and reuse the merged PR's code ([competing fix merged](../learnings/1782737882496-a-recurring-merge-conflict-on-an-approved-pr-can-m.md), [issue closed by rival](../learnings/1782738059209-recurring-pr-conflict-may-mean-the-issue-was-close.md)).

**Another PR landed your fix first.** On slang#13381, #14308 merged a one-line fix for the same code site and left our draft CONFLICTING. `git merge --no-ff origin/master`, resolve the shared file with `git checkout --theirs`, and confirm `git diff origin/master -- <file>` is empty; keep only what still adds coverage over master (there a construction-time `SLANG_RELEASE_ASSERT` plus tests for other consumers of the same bad value); `git submodule update --init` so the build matches HEAD; rewrite the title, description and explanation comment, and qualify "diff vs master" as "vs master at the merge SHA" once master moves on. Keep `Fixes #N` while the PR still carries the regression tests (it merged and closed the issue) ([landed first](../learnings/1794000096615-when-another-pr-lands-your-fix-first-merge-master-.md)).

**Follow-up already on master = semantic conflict.** On slang#9085 master had merged follow-up #12248, adding atom `texture_shadowbias` and retargeting `SampleCmpBias` to it. Git flagged 5 hunks, but 28 bias-only `[require(..., texture_shadowgrad)]` sites auto-merged cleanly and would have recreated the misnaming; the PR's edit to the old atom also had to move to the new one. Recipe: `git log -S <new-symbol> base..origin/master` and read that PR's invariant; `git show origin/master:<file> | grep <old-symbol>` — zero master uses means every hit came from the PR; check master's deprecations (#12836 dropped `-allow-glsl`, so new tests needed `SIMPLE_EX: -lang glsl <file>`); list every beyond-the-markers change for the maintainer. The slang base clone is shallow, so `git merge-base` is empty until `git fetch --shallow-since=<date>` with explicit `+refs/heads/X:refs/remotes/origin/X` refspecs ([semantic conflict](../learnings/1790629728845-merging-master-into-a-pr-whose-follow-up-already-l.md)).

**Same bug fixed differently on master = test clash.** PR #13342 went DIRTY after master #13715 fixed the same Metal `GetElement(makeVector)` miscompile the opposite way, each with a FileCheck test on the same shape expecting different output (`h_0[int(0)]` vs `(float4(*(colors+i)))[int(0)]`). Read master's regression test, not just the hunk; default to master's tested behaviour and update the PR's CHECK line and comments. Report in a fresh status comment, never by PATCHing the explain-diff marker comment ([test clash](../learnings/1792746371295-a-master-change-that-fixes-the-same-bug-differentl.md)).

**`--force-with-lease` `stale info`.** The lease compares against `refs/remotes/origin/<branch>`, but `git fetch origin <branch>` updates only `FETCH_HEAD`, and in a worktree the ref may not exist. Lease explicitly — `git push --force-with-lease=<branch>:$(git rev-parse FETCH_HEAD) origin <branch>`, or `git fetch -f origin <branch>:refs/remotes/origin/<branch>` — after confirming the true head has no unique or maintainer commits; never blind `--force`. `git range-diff` with all-`=` rows proves a rebase kept commits identical, so a prior APPROVE stands ([stale info](../learnings/1789460745636-git-force-with-lease-stale-info-inside-a-worktree-.md)).

## Cross-fork PR limitations

The App can open a cross-fork PR via REST with a user PAT (`gh api repos/<base-owner>/<repo>/pulls`) but not via `gh pr create` (GraphQL → App token → 403). Without a PAT, push to `origin = shader-slang/slang`, open the draft against `master`, and give the fork author a cherry-pick recipe ([no PR into fork](../learnings/1781015587691-bot-github-app-cannot-open-a-pr-into-a-personal-fo.md)).
