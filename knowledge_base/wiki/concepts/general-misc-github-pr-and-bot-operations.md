# GitHub PR and Bot Operations

Rules, failure modes, and operational patterns for the `nv-slang-bot` GitHub App interacting with the `shader-slang/slang` repository: PR creation, branch ownership, merge queue, permissions walls, bot identity, and issue/PR close hygiene.

## Bot Identity and Commit Authorship

Commits render with a real avatar only when the author email uses the bot's **User ID** (not the App ID). These are two different numbers: the App ID (`3311378`) appears in webhook/installation contexts while the Bot User ID (`274397474`) is what the commit author email must embed (`274397474+nv-slang-bot[bot]@users.noreply.github.com`). Using the wrong number produces ghost-avatar commits. Every bot commit must also carry exactly one co-author trailer crediting the operator at their verified corporate `nvidia.com` address — never a fabricated numeric id, which can silently resolve to a different GitHub user. ([CONSOLIDATED: GitHub commit authorship for the bot (correct author email; never fabricate trailer ids)](../learnings/1780558703304-CONSOLIDATED-github-commit-authorship.md))

Before the first commit of any session, read the `feedback_commit_author.md` memory file rather than relying on in-session recollection — in one incident four commits shipped with the wrong email, requiring a 31-commit `filter-branch` rewrite and force-push. ([Read auto-memory feedback files before authoring commits — don't trust your own knowledge of email/identity formats](../learnings/1779895141195-read-auto-memory-feedback-files-before-authoring-c.md))

## PR Ownership Classification

A `fix/issue-<N>` branch name does NOT prove a PR is bot-authored. Human NVIDIA engineers (e.g. `szihs`) use the same naming convention on their own forks. Before treating any PR as bot-owned, verify both: (1) the author is our bot identity and (2) the head repo is the upstream, not a fork. If either check fails, the PR is human-owned and the correct posture is watch-only — no push, no comment, no CI action. ([Bot-owned vs human-contributor PR: fix/issue-* branch name is NOT proof of ownership](../learnings/1780903497625-bot-owned-vs-human-contributor-pr-fix-issue-branch.md), [Branch name fix/issue-N on an external fork can fool 'ours' PR classification](../learnings/1780903498636-branch-name-fix-issue-n-on-an-external-fork-can-fo.md))

**One call settles ownership — and the fields are `head_repo` + `author`, never the branch name:**

```bash
gh api repos/<o>/<r>/pulls/<n> --jq '{author:.user.login, head_repo:.head.repo.full_name}'
# head_repo != <upstream>  ⇒  fork PR, not ours
```

Note the author test must be written suffix-tolerantly, not as `login == "nv-slang-bot[bot]"` — this REST path returns the bare `nv-slang-bot` (see the login-form section below), so a strict `[bot]`-suffix equality check *fails closed* on our own PRs while a branch-name check *fails open* on other people's. Live 2026-08-04 incident: a supervisor tick recovered a `❌ stale` CI cell for `fix/issue-11004` and nudged the fixer to rebase PR **#11234** — which is `author: szihs`, `head_repo: szihs/slang`, an issue filed by `undefdev` and assigned to `saipraveenb25`. The branch-name collision with our own convention was pure coincidence. Four rules fall out ([a `fix/issue-N` branch on a FORK is not ours — resolve by head_repo + author](../learnings/1785803367777-a-fix-issue-n-branch-on-a-fork-is-not-ours-resolve.md)):

- **`gh run list --branch fix/issue-<N>` keys on branch name only** and happily returns runs for an identically-named branch on a *fork*. The resulting CI cell is *correct* — the run really did fail. The cell was never the error; **the ownership inference was.** A correct measurement over an unverified scope is still a wrong conclusion (same family as *"a citation authenticates the LOCATION, never the SCOPE"*; here, **a branch name authenticates the NAME, never the OWNER**).
- **CI staleness on someone else's PR is not our signal.** Never dispatch a rebase/CI remedy from a branch-name match alone.
- **Check the assigned coworker's own history before nudging it about a chain.** The fixer had already caught this exact trap in June, stood down on #11234 (and #11242 for #11002), and recorded the reason; a supervisor nudge contradicting a recorded stand-down needs *new evidence*, not a fresh metric. Reading the session history is what caught it — and a stale-session wake error (`No conversation found with session ID …`) is a **prompt to read the session**, not a self-healing hiccup to wait out.
- **Restoring a capability does not restore unchecked premises.** Recovering `gh` REST made the tick fast, and the speed went straight into acting on a cell whose ownership had never been checked. After an instrument comes back, re-run the *premises*, not just the measurement.

## Dev↔Prod A/B Test Separation

Two NanoClaw instances run the slang pipeline against the same live issues, both as `nv-slang-bot[bot]`. This is an intentional A/B comparison — do not consolidate or close duplicates. The dev instance uses `fix/issue-*` branches; prod uses `dev/slang-fixer/*`. Never push commits onto a prod-instance PR branch, as that contaminates the A/B data point. All `nv-slang-bot`-authored PRs (including `dev/trelby/*` branches) are dev-instance–owned and eligible for management actions. ([CONSOLIDATED: dev↔prod duplicate PRs are an intentional A/B test](../learnings/1780558152382-CONSOLIDATED-dev-prod-ab-pr-conventions.md))

## Workflows Permission Wall

The `nv-slang-bot` GitHub App lacks the `workflows` write permission. Any push (rebase or merge) onto a branch whose tip carries `.github/workflows/*` changes will be rejected at the ref-level — even if the bot's own commits touch zero workflow files — because GitHub compares the old vs. new tip trees. `git push --dry-run` and `git ls-remote` are **false positives**: they succeed even though the real push will fail. The only way to confirm push capability is to attempt the real push with `--force-with-lease`. Stripping workflow files to match the old tip is harmful because a squash-merge would then silently revert master's workflow changes. Resolution requires either granting the App `workflows` permission (org-wide decision) or having a human push the rebased commits. ([Bot can't update a stale PR branch when master changed .github/workflows (App lacks workflows perm)](../learnings/1780567931645-bot-can-t-update-a-stale-pr-branch-when-master-cha.md), [Bot can't push rebased branches carrying .github/workflows changes](../learnings/1780568708582-bot-can-t-push-rebased-branches-carrying-github-wo.md), [git push --dry-run is a false-positive for the GitHub-App workflows-permission wall](../learnings/1780572980623-git-push-dry-run-is-a-false-positive-for-the-githu.md))

This same wall applies to the merge queue: `enqueuePullRequest` for PRs touching `.github/workflows/*` is blocked even if the general enqueue block is later lifted, because the queue builds a merge commit including the workflow diff. ([Bot enqueue of workflow-touching PRs has a second blocker (workflows permission)](../learnings/1782727631172-bot-enqueue-of-workflow-touching-prs-has-a-second-.md))

## Merge Queue Blocks and Enum Collisions

The bot cannot enqueue ANY PR (fork or same-repo) to the merge queue — `enqueuePullRequest` is rejected with "not authorized to push to this branch" regardless of PR authorship. When GitHub appears to auto-requeue a bot PR, that is GitHub's own behavior. The correct audit action is `action:"left"` and rely on GitHub-auto or maintainer manual requeue. `gh run rerun --failed` still works for CI reruns. ([Bot enqueuePullRequest blocked for ALL PRs, not just forks](../learnings/1782260121429-bot-enqueuepullrequest-blocked-for-all-prs-not-jus.md))

Two PRs appending to the same public enum (`CompilerOptionName`) can collide in the merge queue with a `duplicate case value` compile error even when both pass CI individually. The fix is to renumber your enumerator above the highest claimed value across master and the active queue-mate. Dequeue first via GraphQL `dequeuePullRequest` (gh has no dequeue verb), then rebase and push with `--force-with-lease`, and wait for a maintainer requeue. ([Merge-queue duplicate-case enum collision: two concurrent PRs appending to the same public enum](../learnings/1782535032557-merge-queue-duplicate-case-enum-collision-two-conc.md))

## Issue and PR Close Restrictions

Coworkers must not close GitHub issues — not even obvious duplicates. Closing is a human-maintainer privilege. The correct action is to post a verified verdict/duplicate cross-link as a comment and leave the close to a human. A deterministic backstop in `container/agent-runner/src/providers/claude.ts` (`detectIssueClose()` + `preToolUseHook`) hard-blocks `gh issue close`, GraphQL `closeIssue(`, and `gh api .../issues/<n>...state=closed` at the tool boundary, independent of what the model was told. ([Coworkers must not close GitHub issues — deterministic tool backstop](../learnings/1782270000000-coworkers-must-not-close-github-issues-tool-backstop.md), [Do NOT autonomously close issues/PRs — surface to a human maintainer](../learnings/1782280210918-do-not-autonomously-close-issues-prs-surface-to-a-.md))

## Copilot Conflict Resolution Race

When a maintainer comments `@copilot resolve the merge conflicts` on a bot-authored PR, GitHub's Copilot agent can also act on the same branch. Before pushing your own conflict resolution, `git fetch` the PR branch to check whether Copilot already pushed. If its resolution is equivalent, `git reset --hard` to the remote tip (adopting Copilot's commit) and add only incremental fixes as a fast-forward push — do not force-push your sibling merge over Copilot's identical resolution. ([@copilot may resolve conflicts on bot-authored PRs — check remote tip before pushing your own](../learnings/1782711499913-copilot-may-resolve-conflicts-on-bot-authored-prs-.md))

## Recurring Merge Conflicts as Supersession Signal

When a maintainer asks to resolve a merge conflict on an approved PR and the conflict recurs — especially with a duplicate diagnostic code or symbol-uniqueness collision — check first whether a competing PR already merged and closed the underlying issue. Mechanically resolving such a conflict re-fixes a closed issue and may produce a build error from duplicate definitions. Surface a close-vs-rework decision to the maintainer rather than force-resolving. ([A recurring merge conflict on an approved PR can mean a competing fix merged — check before resolving](../learnings/1782737882496-a-recurring-merge-conflict-on-an-approved-pr-can-m.md), [Recurring PR conflict may mean the issue was closed by a competing merged PR](../learnings/1782738059209-recurring-pr-conflict-may-mean-the-issue-was-close.md))

## Cross-Fork PR Limitations

The GitHub App can create a cross-fork PR via the REST API with a user PAT (`gh api repos/<base-owner>/<repo>/pulls`), but NOT via `gh pr create` (GraphQL → App token → 403). When no user PAT is available, the fallback is to push to `origin = shader-slang/slang` and open the draft PR against `master`, providing the fork author a cherry-pick recipe. ([Bot (GitHub App) cannot open a PR into a personal fork — use master-base + cherry-pick fallback](../learnings/1781015587691-bot-github-app-cannot-open-a-pr-into-a-personal-fo.md))

## Issue↔PR Linkage Verification

GitHub auto-closes a linked issue on merge for any of `close/closes/closed`, `fix/fixes/fixed`, `resolve/resolves/resolved` followed by `#N`. When verifying PR body linkage, grep for the full keyword set — not just `Fixes`. Also accept the fully-qualified cross-repo form (`Fixes shader-slang/slang-rhi#772`), which requires a pattern allowing an optional `owner/repo` qualifier between keyword and `#`. ([Fixes/Closes link verification must accept the qualified cross-repo form](../learnings/1781072527758-fixes-closes-link-verification-must-accept-the-qua.md), [Verify issue↔PR linkage with ALL GitHub auto-close keywords, not just 'Fixes](../learnings/1781178144676-verify-issue-pr-linkage-with-all-github-auto-close.md))

Two failure modes on the same #11856 incident sharpen this. (1) A PR **title** like `Fix #11856` does NOT auto-close the issue — only a **body** keyword does — nor does the squash merge **commit subject**; auto-close uses only the body-parsed `closingIssuesReferences`. PR #11866 merged the correct fix but its body carried a closing keyword for the unrelated already-closed `#11720`, so #11856 silently stayed OPEN while the fixer reported the chain terminal — caught only by verifying the merge with `gh` ([Verify a fix PR's closing reference matches the tracked issue, not just the title](../learnings/1782936185036-verify-a-fix-pr-s-closing-reference-matches-the-tr.md)). (2) Worse, an *incidental* `fixes #N` in PR-body prose describing a **different** PR (`PR #11785 ("...", fixes #11720)`) gets hijacked by GitHub's linkifier as a closing reference for the current PR → `closingIssuesReferences = [#11720]` → the merge closes nothing new. Rules: put the literal `Closes #<this-issue>` in the PR **body**; NEVER write `fixes/closes/resolves #N` in prose when merely describing another PR/issue (use plain `#N` — "PR #11785 which addressed #11720"); after opening, verify `gh pr view <n> --json closingIssuesReferences` shows the intended issue, and after merge verify `gh issue view <tracked> --json state` is CLOSED. If a fix merged but the tracked issue lingers OPEN, have the closest-to-the-state coworker post a merge-landed comment flagging the mis-reference so a **maintainer** closes it — never auto-close (the `gh issue close` PreToolUse hook blocks the bot anyway) ([PR-description prose fixes-N closes the wrong issue and blocks auto-close](../learnings/1782951523566-pr-description-prose-fixes-n-closes-the-wrong-issu.md)).

**When you audit a PR body for these keywords, the audit itself needs a positive control.** A grep over a fetched PR body is exactly the shape that returns a confident empty for reasons unrelated to the body: an over-anchored pattern (`$`-anchored against CRLF line endings silently matches nothing) reads as "no closing keyword present" — the same false-absence class as the check-runs and doctest cases catalogued under the counterfactual-control rule below. Before recording a linkage verdict from a zero-hit grep, run the pattern against a body you *know* carries the keyword and confirm it returns non-zero; and prefer resolving the question with the state GitHub itself computed (`gh pr view <n> --json closingIssuesReferences`) over any text match ([the control is the counterfactual question — a null result is evidence only if the instrument demonstrably works](../learnings/1785770932836-the-control-is-the-counterfactual-question-not-a-b.md)).

## force-with-lease Stale Remote-Tracking Refs

`git push --force-with-lease` can fail with `stale info` even when nobody else pushed because `git fetch origin <branch>` only updates `FETCH_HEAD`, not `refs/remotes/origin/<branch>`. Fix: `git fetch -f origin <branch>:refs/remotes/origin/<branch>` to force-refresh the remote-tracking ref, then lease against the true head SHA. Use `git range-diff` to verify a rebase preserves an existing approval. ([force-with-lease 'stale info' — refresh the remote-tracking ref first](../learnings/1782765717544-force-with-lease-stale-info-refresh-the-remote-tra.md))

## Existing Fix PR Check

Before triage recommends a fix — and as a fixer's first step before branching — check whether a fix PR is already open. A maintainer often files an issue and opens a fix PR within minutes with no announcement on the issue. Use `gh pr list --search "Fixes #<num>"` (not `gh search prs`, which has indexing lag) as the detection mechanism. If an open PR already references the issue (especially authored by the reporter/a maintainer), stand down and do not post a redundant bot comment. ([Check for an existing fix PR before recommending OR implementing a fix (esp. maintainer-filed issues)](../learnings/1781241842104-check-for-an-existing-fix-pr-before-fixing-or-recommending.md))

## CHANGES_REQUESTED as Decline Signal

A `CHANGES_REQUESTED` review with an approving/neutral body and zero inline comments is a decline-to-merge signal, not a request for code changes. Before treating it as an edit request, fetch the review body and inline comments (`gh api repos/<o>/<r>/pulls/<n>/reviews` + `/comments`). If the body is positive and comments are empty, reply once acknowledging the no-merge verdict and close the chain upstream with no code change. ([CHANGES_REQUESTED with a 'looks good' body and zero inline comments is a no-merge signal, not an edit request](../learnings/1782512263705-changes-requested-with-a-looks-good-body-and-zero-.md))

## Bot Comment Login Form & Content-Correction Hygiene (2026-07-13 fold)

The "edit if last commenter is self, else post fresh" guard commonly tests `if [ "$LOGIN" = "nv-slang-bot[bot]" ]`, but `gh api repos/<r>/issues/<n>/comments --jq '.[-1].user.login'` returns **`nv-slang-bot`** (NO `[bot]` suffix) for the bot's own comments via the REST issues/comments API — so the guard NEVER matches and every "refresh the 5-bullet" step POSTs a new comment instead of PATCHing (observed on #1052: three near-identical triage comments piled up). Match `nv-slang-bot` (bare) or use a suffix-tolerant test (`case "$LOGIN" in nv-slang-bot|nv-slang-bot\[bot\]) PATCH ;; *) POST ;; esac`); the `[bot]` form appears in GraphQL/events but not this REST path — verify with `--jq '.[-1].user.login'` before trusting either. This affects ALL `*-github` skills carrying the `[bot]`-suffixed guard ([gh API comment login is 'nv-slang-bot' not 'nv-slang-bot[bot]' — edit-if-self guard mismatch](../learnings/1783878154169-gh-api-comment-login-is-nv-slang-bot-not-nv-slang-.md)).

The edit-in-place hygiene rule extends to **content corrections**: when you've posted a causal claim/verdict as CONFIRMED and a later stage in the chain refutes exactly that claim, you MUST patch your own comment in-place to mark the refuted detail and defer to the authoritative write-up — the reader hits the top comment first, and a stale CONFIRMED claim contradicting a correct cross-link below it makes the public trail internally inconsistent. Edit ONLY your own comment id; keep the parts that survived (a verified workaround); point to the authoritative source rather than re-litigating. Observed on slangpy#1055: the triager's top comment stated "vector/scalar divide is the trigger" as CONFIRMED; the upstream re-verify refined it to "the LOOP is the trigger, not the divide" (slang#12071), and the triager proactively re-PATCHed to mark that causal detail refuted while leaving the other tier's cross-link comment untouched ([patch your own posted comment when a downstream refinement refutes it](../learnings/1783885801139-patch-your-own-posted-comment-when-a-downstream-re.md)).

## Reading GitHub State: Endpoint, Filter, and Window Traps (2026-08-03/04 fold)

Every over-reported red, phantom-green sweep, and "we already covered that" mistake in this family comes from the same shape: a query that is *correct* over a scope you never stated. Four concrete instruments.

**`commits/<sha>/check-runs` returns HISTORY, not current state — pass `filter=latest`.** Without it you get *every attempt of every check*, so a check that failed on attempt 1 and passed on attempt 2 still reads `conclusion:"failure"` and a healthy PR looks red. The symptom is subtle because it is *over*-reporting: you never notice a missing failure, you just burn a rerun (or a merge-queue requeue decision) on a phantom one, and the tracker then claims a flake existed where none did. It is the mirror image of the `gh pr checks` phantom-*green* mode (GraphQL-backed, so it 401s to "no failures" when stderr is swallowed).

```bash
gh api "repos/OWNER/REPO/commits/$sha/check-runs?per_page=100&filter=latest"   # one row per check
```

Two companions from the same sweep: **`--paginate` is not a safe default on this endpoint** — it concatenates JSON objects rather than merging arrays, so a bare `.check_runs[]` filter dies on page 2 (slurp with `jq -s '[.[]|.check_runs[]?]'` or pass explicit `?page=N`), and it has been observed to **401 on page 2+ while page 1 succeeds**, i.e. a silent 100-item cap — reconcile any enumeration against a `total_count`, never against the length of a filtered page. And **a "FAILED test" line is not automatically the failure**: slang-test retries internally and prints `failed(pending retry)` first, so grep the terminal `FAILED test:` form and check that the `N failing tests` count agrees with how many you extracted ([check-runs without filter=latest: stale attempts read as live reds](../learnings/1785787855263-github-check-runs-filter-latest-or-stale-attempts-.md)).

**`per_page` on the Actions API applies AFTER the filter, so adding a filter WIDENS your time window.** Verified on `shader-slang/slang` workflow `106587263` (`release.yml`): `runs?per_page=100` gave 100 rows = 84 dispatch + 16 push spanning 05-19..08-04 with 71 bot-among-dispatch; `runs?per_page=100&event=workflow_dispatch` gave 100 dispatch rows spanning 05-09..08-04 with 82. Both agents measured "how many dispatches are the bot's"; **both numbers are right**, because `71/84` and `82/100` describe different populations — the `event=` filter bought 16 more dispatch runs and 10 extra days of history in the same 100 rows (`total_count=251`, so neither is all-time). Rule: **a count over a paginated Actions query is a count over `(filter, page-cap)` jointly, never over "the workflow"** — state the window with the number or the number is unfalsifiable, and two agents comparing counts must compare *windows* first (re-run each other's exact query before concluding anything about correctness). This **amends** the standing rule *"two impossible numbers ⇒ one instrument is defective; RESOLVE, don't bridge"*, which here produced a wrong accusation that a peer's `82/84` was broken: enumerate three causes before blaming one — (a) a defective instrument, (b) different scopes/windows, (c) different entities being counted (runs vs SHAs vs tags). Only (a) justifies calling something broken. Cause (c) was live in the same exchange: over 98 tag runs, `88 ahead / 10 diverged` vs a peer's `89 / 9`, because one tag has **two runs at two SHAs** (97 distinct SHAs across 98 runs) so tag-name counts and run counts legitimately differ. Free self-check when quoting a breakdown: **verify the parts sum to the whole inside one query** — a breakdown that doesn't sum is the cheapest possible signal that you spliced two windows together ([Actions per_page is post-filter — two correct counts can disagree without either instrument being defective](../learnings/1785809671526-github-actions-per-page-is-post-filter-adding-even.md)).

**A bot review's findings table cites DIFF-relative lines — match findings by SYMBOL, never by line number.** On slang#11118 an existing `github-actions[bot]` review listed `slang-lower-to-ir.cpp:193`, which is line 193 *of the PR diff*; in the head file it is `:3721`. A dispatch read the table, failed to match `:3721`, and concluded the depth-cap finding was absent — instructing a delta post that would have publicly told a maintainer their review missed its own headline finding (it was row 3 of that very table, and the review's summary line named it), in the same comment that was retracting one of its other gaps. Procedure before claiming any finding is new/absent: fetch the body (`gh api repos/$R/pulls/$N/reviews/$ID --jq '.body'`), grep it by **symbol/mechanism** (`grep -in "kMaxTypeNestingDepth\|depth-cap\|permissive"`) since symbol names are stable across the diff/head coordinate systems and line numbers are not, resolve any suspected mapping explicitly (`sed -n '193p' pr.diff` and `sed -n '3721p' head-file.cpp` must print the same statement), and claim "not covered" only on a **zero-hit symbol grep** — that is how the genuinely uncovered finding was identified. Corollary for the delta's own citations: fetch each file **at the pinned head SHA** (`gh api ".../contents/<path>?ref=<sha>" | base64 -d`) and verify every cited line with `sed -n 'Np'` before posting ([bot-review finding tables cite diff-relative lines — match by symbol](../learnings/1785748040931-bot-review-finding-tables-cite-diff-relative-lines.md)).

**CodeRabbit's findings live on `pulls/N/comments`, not `reviews[].body` — and the under-read fires on a SUCCESSFUL harvest.** Harvest tooling that tallies severity markers in the review *body* systematically under-reads CodeRabbit, whose body is frequently status boilerplate only (`Actionable comments posted: 11` plus a collapsed config block, zero severity markers) while all findings sit inline one endpoint away. Exit 0, body retrieved, markers tallied → **0 findings**, with 11 real ones (2 Major) unexamined and no error to investigate. Evidence (slang-rhi#803, 2026-08-03): review `4816225157` @ `2fc21a3` was scored "clean 0/0/0" against 2 🟠 Major / 3 🟡 / 6 🔵; the next round only *appeared* non-clean because CodeRabbit happened to inline one Major into the body that time — **formatting luck, not correctness**. Not a bot-filter bug: the harvest's exact-match allowlist works and harvested `coderabbitai[bot]` verbatim. Four fixes: (1) also tally `pulls/N/comments`; (2) treat `Actionable comments posted: N` with N>0 and zero body markers as a hard **"findings are elsewhere"** flag, never as clean — that single check converts a silent under-read into a loud one; (3) use **`original_commit_id`, not `commit_id`**, for provenance, because GitHub *rewrites* inline comments' `commit_id` as the head advances (8 of the 11 findings now report the head three revisions later); (4) **status green ≠ a harvestable review** — at a later revision CodeRabbit's check was green but produced *no review object*, updating its walkthrough comment instead; absence of a review is not absence of a bot pass. Scope: the `slang-pr-approver` and `slangpy-pr-approver` harvest scripts are byte-identical, and **slangpy is exposed worse** because CodeRabbit is often its only review signal — past slangpy rows reporting 0 CodeRabbit findings are worth auditing. Same-incident discipline note: **a timeout is a statement about a past instant, not the present** — an exit-22 that was correct when computed at 07:04:49 was reported as a verdict at 07:12:04 though the review landed 07:07:42; **re-probe at the last moment before committing an artifact that depends on a "not yet available" result** ([CodeRabbit findings live on pulls/N/comments, not reviews[].body](../learnings/1785778143329-coderabbit-findings-live-on-pulls-n-comments-not-r.md)).

## The Control Is the Counterfactual Question, Not a Blocklist

Across one debugging chain, **nine** separate signals looked like evidence but could not have come out differently. The decisive case inverts the sign of the first, which is what proves the control must be a *question you ask*, not a *list of patterns you avoid*. The token was doctest's `DEEPEST SUBCASE: d3d12`: in the morning as a **negative** ("zero occurrences ⇒ no d3d12 failures" — the count was 0 because that single-line form never appears; doctest prints a multi-line `DEEPEST SUBCASE STACK REACHED` header, and `vulkan`/`cuda` also returned 0), and in the afternoon as a **positive** ("its absence in a green run ⇒ the d3d12 arm is clean" — doctest emits that block *only while logging failures*, so in a 0-failure run its absence is structurally guaranteed). One string, opposite signs, zero information either time. A curated blocklist of "patterns that burned us" would have flagged the morning use and waved the afternoon one straight through. The question that catches both:

> **Could this have come out differently if my hypothesis were false?**

If no, you have a tautology wearing the costume of evidence. The same chain produced the whole family: a grep whose pattern never matches anything; a `$`-anchored pattern against a CRLF log (silently empty); `grep -c` of a tool name that only counts `pip install` chatter; a downloaded release artifact standing in for a source build (both A/B arms clean); a monitor grepping a file the instant it appears, before content is written (0 = "empty" and 0 = "no repro", indistinguishable); a stale symlink predating the build; `--depth 1` masking a fetch failure as a slow compile; a line range spanning two constructs; and a probe aimed at the wrong observable (comparing *layout* to test a change that mutates only the *capability set*). Provenance ("is this primary source?") catches **none** of these — several were read directly from primary source. Only method does ([the control is the counterfactual question, not a blocklist](../learnings/1785770932836-the-control-is-the-counterfactual-question-not-a-b.md)).

Two shapes from the same chain are worth naming separately because they are not log-probes, so a reader scanning for grep-shaped mistakes skips past them. **A wrong premise supporting a right conclusion** is the hardest member of the family: *"`#if` structurally cannot take a device term"* is false (a `#if` body can nest a runtime `if` — in-repo precedent at `src/sgl/device/helpers.cpp:64`/`:67`), but the conclusion it supported was correct on other grounds, so nothing downstream looked wrong and it cleared three tiers, one of which passed it on explicitly *because the conclusion matched what it already believed*. So ask the counterfactual question of the **premise**, not only of the conclusion; **agreement with a prior belief is the condition under which the check gets skipped, not corroboration**; and note this false absolute was produced *while correcting someone else's overclaim* (distrust "structurally cannot"/"impossible"/"always" in your own output, especially right after "actually, no"). Second: **a decision whose presupposition cannot be false** — an escalation asked a human *"should we promote the draft?"* when the asker had already verified no draft existed. No possible answer applied, and it is worse than a bad log line because it puts a non-existent decision into a human's queue: **when escalating, re-read the question against the state you just verified and confirm its presupposition holds *now***.

Practical form of the control: (1) before believing an absence, run the same probe against a case you *know* is present and confirm non-zero — no positive control, no negative result; (2) before believing a null A/B, confirm the two arms differ in *some* observable way, else you cannot distinguish "no effect" from "not testing the effect"; (3) derive the observable from what the mechanism actually mutates (capability-set change ⇒ check accept/reject and diagnostics; layout change ⇒ check sizes and offsets); (4) use arithmetic as an independent check — "33 failures = 28 diagnostics + 5 known-unrelated" falsified a monitor that reported 0 diagnostics, i.e. arithmetic caught what the purpose-built tooling missed.

## Read-Only Subagent Types Do NOT Prevent GitHub Writes

The `Explore` subagent grant is *"All tools except Agent, Artifact, ExitPlanMode, Edit, Write, NotebookEdit"* — **`Bash` is not in the exclusion list.** So an `Explore` agent can run `gh api ... --method POST`, `git push`, or `curl -X POST`. The exclusions are local-filesystem writers only: **`Explore` is read-only with respect to your files; it is not read-only with respect to the world.** Both the name and the "read-only search agent" description imply more than the grant delivers, and a standing directive to prefer `Explore` so that overstep is "physically impossible" states a *mechanism that is wrong*, even though preferring `Explore` remains good practice.

What that cost: three `Explore` agents were dispatched to investigate an issue; an `nv-slang-bot[bot]` comment then appeared on that issue mid-session that the dispatching agent had not written in any turn of its own. It reasoned *"my agents were `Explore`-typed, therefore no `gh` write surface, therefore unlikely source"* and escalated upward that **another tier may be able to write to issues it holds** — a routing/duplication hazard. The parent checked the grant and corrected it. Two facts closed it: the comment's timestamp fell inside the agent's own turn gap, and **a subagent's `gh` write produces no session outbound row**, so a self-inflicted write is *indistinguishable on the session record* from a write by another actor; the timeline showed a single `performed_via_github_app: nv-slang-bot` identity, no second app, no other session. Still not *proven* (there is no per-subagent write log) — but the stated reason for ruling it out was unsupported, and the escalation rested on it. **The bias worth naming:** of two candidate explanations, the one that left its own apparatus blameless got escalated, because "a different tier is writing to my surfaces" is someone else's infrastructure problem while "my own subagent wrote it" is mine. **When a mystery artifact appears on a surface you control, enumerate self-inflicted causes first and read the tool grant before reporting an external cause.**

Do this instead: (1) **read the grant before reasoning from a type name** — `Bash` present ⇒ network writes possible, whatever the type is called; (2) **put the constraint in the prompt, because the type will not enforce it** — every read-only dispatch carries, verbatim, *"READ-ONLY: do not write to GitHub or any external service (no `gh ... --method POST/PATCH/PUT/DELETE`, no `git push`, no `curl -X POST`), do not build, do not send messages or dispatch peers. Report findings only."*; (3) **prefer `Explore` anyway** — it still removes `Edit`/`Write`/`NotebookEdit` and cannot spawn further agents, blocking the local-file and fan-out overstep classes; just don't credit it with network isolation; (4) **on an unexplained artifact**, read it before touching anything, consolidate by PATCH if it is substantively correct rather than adding a duplicate, then report the anomaly *with its uncertainty intact* ("cause unidentified", not "another tier did it"). Same root as the `curl`-vs-`gh` false capability negative and the fabricated `Read`: **an instrument's label is not a measurement of its behaviour** — name the property you need, then verify that property specifically ([`Explore` is read-only for FILES, not the NETWORK — Bash is retained, so it can post to GitHub](../learnings/1785804791695-the-explore-subagent-type-is-read-only-for-files-n.md)).

## Tracker Hygiene: Coexistence Is a Third Memory Defect

The `pr_session_mappings` / tracker discipline above assumes an index entry is either right or stale. There is a worse third mode: **coexistence** — the same issue/PR appearing twice, once correctly marked dead/closed/superseded and once as a surviving older line still describing it as *live work with a proposed approach*. The stale copy silently defeats the correct one, because a fresh context that reads the live-work line has no reason to keep scanning for a contradicting entry. That is strictly worse than having no entry: with no entry you investigate; with a plausible stale entry you execute. Concretely (slang fleet index, 2026-08-03) `#11682` appeared on two lines — one correctly marked **DEAD** (closed by someone else's PR #12201) and a leftover fix-log line still proposing an approach. The DEAD marker was present, accurate, and **ineffective**, because the duplicate was equally readable and more actionable-sounding; it was found only while compacting the index for size, i.e. by accident.

Rules: **dedupe by identifier, not by vibe** — grep the *number* (`#11682`, `PR 12201`) across the whole index before trusting or writing an entry, and treat two hits on one identifier as a defect until proven otherwise (a cross-reference is legitimate; a second *status* line never is). **When you mark something dead, delete or fold the old live-work line in the same edit** — a DEAD marker beside a surviving stale entry is a half-fix that reads as a full one. **Status is single-valued:** an identifier may appear in many places as context, but exactly one line may assert its *state*, or the two will eventually disagree with no way to tell which is newer. **Compaction is a detection opportunity, not janitorial work** — budget for "what did shrinking this reveal?". Pairs with the other index hazard: a rule stored **without its precondition** (e.g. "a green run is weak evidence" filed without the refactor boundary condition) can license exactly the wrong inference. Same family — **a partially-correct memory entry can be net negative**, and only reading it adversarially reveals that. The question to ask of any index: *if two lines about this disagreed, which would a fresh context act on?* ([a correct DEAD marker plus a stale live-work duplicate is worse than no entry](../learnings/1785797594644-a-correct-dead-marker-plus-a-stale-live-work-dupli.md))

### Any "N:" Next to an Enumeration Is Derived Data — Recompute, Never Increment

The duplicate-entry defect above has a quieter sibling on the same indexes: **a stated count maintained by incrementing**. Instructing each writer to "append your rows and bump N" makes N a *maintained* value, and increments accumulate error silently, because nobody re-derives it. Measured on the 2026-08-04 audit of every `wiki/concepts/*.md` footer: **19 of 47 pages** had stated-N drift, including pages with **no edits that day** (`review-pr-practices` 273→274, `slang-backends-spirv` 162→160, `slang-misc-build-infrastructure-and-tooling` 60→55, `slang-autodiff-ir-autodiff-differentiation` 40→37) — so the drift predates any single run. The same audit found **8 duplicate citation rows across 5 pages**: the same learning cited twice in one footer with *differently-worded* descriptions, near-identical enough to read as two distinct sources and inflate apparent coverage. Dedupe by keeping the **more informative** row (the one carrying the issue/PR number) — a blind "keep first" silently discards the better description. Generalized rule: **any "N:" adjacent to an enumeration is derived data — never trust it, never increment it, always recompute it**, and never trust a writer's report about arithmetic it performed on its own work.

Two method points travel with it. **N independent self-reports do not compose into a coverage claim.** Every fold agent validated only its own slice and truthfully reported "footer counts match"; the cross-cutting facts — drift on untouched pages, duplicates inherited from *earlier* folds — were visible only to a global recount, so per-agent verification cannot catch either class no matter how honest each agent is. And **a checker can be defective in a way that manufactures exactly the finding you expected**: the first row-counter used here was

```bash
awk '/^\*\*Source learnings \(/{flag=1;next} flag&&/^- \[/{c++} flag&&!/^- \[/&&NF{exit} END{print c+0}'
```

whose `!/^- \[/&&NF{exit}` clause stops at the first non-row line — but real footers carry wrapped entries and interleaved blanks, so it counted a *prefix* and reported mismatches on correct pages. It was tempting precisely because it produced the expected result (same family as the counterfactual-control rule above: it could not have come out any other way). Prefer an instrument with an **internal control**, so a parse failure announces itself instead of arriving as content:

```bash
rows=$(awk '/^\*\*Source learnings \(/{flag=1;next} flag&&/^- \[/{c++} END{print c+0}' "$f")
uniq=$(awk '/^\*\*Source learnings \(/{flag=1;next} flag&&/^- \[/{print}' "$f" \
        | grep -oP 'wiki/learnings/\K[^)]+' | sort -u | wc -l)
```

`rows == uniq` is self-validating: divergence means either a parse failure or a duplicate. The durable fix is to make the number derived — have the generator recompute `**Source learnings (N):**` and frontmatter `source_count` from the deduped stem set on every run and drop duplicate rows (keeping the longest description); until that lands, every fold needs a **global** recount pass, because telling agents to bump N will keep producing drift ([footer counts drift chronically — recompute N, and duplicate citation rows hide inside it](../learnings/1785825237204-learnings-wiki-footer-counts-drift-chronically-the.md)).
