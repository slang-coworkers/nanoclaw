# GitHub PR and Bot Operations

Rules and failure modes for the `nv-slang-bot` GitHub App on `shader-slang/slang`: commit identity, PR ownership, permission walls, merge queue, issue/PR close and linkage hygiene, and conflict resolution.

## TL;DR

- **Commit identity:** author email `274397474+nv-slang-bot[bot]@users.noreply.github.com` (Bot **User ID** 274397474, not App ID 3311378). Exactly one co-author trailer, at the operator's verified `nvidia.com` address — never a fabricated numeric id. Read `feedback_commit_author.md` before a session's first commit.
- **A bare `nv-slang-bot@users.noreply.github.com` maps to the unsigned standalone User 286953280**, so `license/cla` fails and `mergeStateStatus=BLOCKED`. Causes: a container restart resetting `git config user.email`, or a `git -c user.name/-c user.email` override. Run plain `git commit`; check `git log --format='%an <%ae>' origin/<base>..HEAD` before pushing. To repair, re-author (never revert — CLA scans every commit) and force-push, an operator-gated step.
- **A `fix/issue-<N>` branch name does NOT prove a PR is ours** — humans use it on forks. Settle it with `gh api .../pulls/<n> --jq '{author:.user.login, head_repo:.head.repo.full_name}'`, testing the author suffix-tolerantly. CI on someone else's PR is not our signal; a verified bot PR's regression IS ours — flag it to the parent for fixer dispatch.
- **Dev↔Prod is an intentional A/B test** (both `nv-slang-bot[bot]`; dev `fix/issue-*`, prod `dev/slang-fixer/*`). Never consolidate, close duplicates, or push onto a prod branch.
- **Workflows wall:** the App lacks `workflows` write, so any push whose tip tree differs in `.github/workflows/*` is rejected, even if our commits touch none. `--dry-run`/`ls-remote` give false positives; only a real push confirms. The wall also blocks enqueueing workflow-touching PRs.
- **Merge queue:** the bot cannot enqueue ANY PR. Audit action `left`; rely on GitHub-auto or maintainer requeue. `gh run rerun --failed` works. Concurrent appends to one public enum collide (`duplicate case value`) — renumber above the highest claimed value.
- **Never close issues/PRs** — a PreToolUse hook hard-blocks `gh issue close`, GraphQL `closeIssue(` and `state=closed`. Post the verdict/cross-link; a human closes.
- **Only a PR body keyword auto-closes** (`close[sd]`/`fix(e[sd])`/`resolve[sd]` + optional `owner/repo` + `#N`) — not the title, not the commit subject. Never write `fixes #N` in prose about another PR. Verify `closingIssuesReferences` before, and issue state after, merge; a zero-hit grep needs a positive control.
- **Check for an existing fix PR before recommending or implementing** (`gh pr list --search "Fixes #<n>"`); upstream, search open PRs by function/file and by the reporter — unlinked fixes are common.
- **`CHANGES_REQUESTED` with a positive body and no inline comments = decline-to-merge**, not an edit request.
- **Before pushing a conflict fix after `@copilot resolve the merge conflicts`, fetch** — adopt Copilot's equivalent commit.
- **A recurring conflict on an approved PR can mean a competing fix merged** — surface close-vs-rework, don't mechanically resolve.
- **A master merge after a follow-up landed is a semantic conflict**; cleanly auto-merged hunks can reintroduce the replaced convention. If master fixed the same bug differently, read master's test and default to it.
- **`--force-with-lease` `stale info` with no competing push = stale or missing remote-tracking ref**; lease explicitly against `FETCH_HEAD`.
- **The App cannot open a PR into a personal fork via `gh pr create`**; fall back to a master-based draft PR plus a cherry-pick recipe.

## Bot identity and commit authorship

Two numbers are easily confused: the App ID (`3311378`) appears in webhook/installation contexts, while the commit author email must embed the Bot **User ID**: `274397474+nv-slang-bot[bot]@users.noreply.github.com`. The wrong number yields ghost-avatar commits. Each bot commit carries exactly one co-author trailer crediting the operator at their verified `nvidia.com` address; a fabricated numeric id can silently resolve to another GitHub user ([CONSOLIDATED: GitHub commit authorship](../learnings/1780558703304-CONSOLIDATED-github-commit-authorship.md)). Read the `feedback_commit_author.md` memory file before the first commit rather than trusting recollection — one incident shipped four wrong-email commits and needed a 31-commit `filter-branch` rewrite ([Read auto-memory feedback files before authoring commits](../learnings/1779895141195-read-auto-memory-feedback-files-before-authoring-c.md)).

The email must be the real address or the **account-scoped** noreply form `<numericId>+<login>@users.noreply.github.com`. A bare `nv-slang-bot@users.noreply.github.com` does not associate the commit with the App, so CLA-assistant reports an unsigned committer ("N of M committers signed") and flips `mergeStateStatus=BLOCKED` even though the CLA is signed. A container restart can reset `git config user.email`, so only post-restart commits regress; diagnose with `git log --format='%h %ae' <branch> --not origin/master`. Fix: set `user.email` to the scoped form and `user.name "nv-slang-bot[bot]"`, re-author (`git commit --amend --reset-author --no-edit`, or an `--exec` rebase), then `git push --force-with-lease` after explicit session authorization. A revert or superseding commit does not help, because CLA scans every PR commit. Durable fix: pin the container's default git identity ([bot commits must use the account-associated noreply email](../learnings/1789476879264-bot-commits-must-use-the-account-associated-norepl.md)).

A per-commit override breaks a correct default the same way. On slang#13305, `git -c user.name="nv-slang-bot" -c user.email="nv-slang-bot@users.noreply.github.com" commit` produced an unregistered author although the worktree already held the registered identity ([CLA breaks with `git -c user.name/-c user.email`](../learnings/1790645515788-ops-cla-breaks-with-git-c-user-name-c-user-email-c.md)). It recurred on #13421 and #12116 (commits 1–4 passed, 5–9 with the override went pending; 12 bot PRs affected). The bare email attributes commits to standalone User `nv-slang-bot` (id `286953280`, CLA unsigned). Never pass `-c user.*`; check authors before pushing. After the fact it is an operator decision — sign the CLA for 286953280, or re-author and force-push (loses review context, resets CI); a squash merge keeps the author, so it is no escape ([bot commits: never override git identity, CLA pending on user id 286953280](../learnings/1791405237001-bot-commits-never-override-git-identity-with-c-use.md)). How a sweep classifies such a pending CLA: [nv-slang-bot identities and the license/cla gate](../concepts/slang-a-bot-cla-identity.md).

## PR ownership classification

Human NVIDIA engineers (e.g. `szihs`) use the `fix/issue-<N>` convention on their own forks. Before treating a PR as bot-owned verify both the author (our bot) and the head repo (upstream, not a fork); if either fails the PR is human-owned and watch-only — no push, comment, reaction or CI action. In June the board nearly closed szihs's #11242 (`fix/issue-11002` on `szihs/slang`) and mislabelled his #11234 (`fix/issue-11004`) as ours ([Bot-owned vs human-contributor PR: branch name is NOT proof](../learnings/1780903497625-bot-owned-vs-human-contributor-pr-fix-issue-branch.md), [Branch name fix/issue-N on an external fork can fool 'ours' classification](../learnings/1780903498636-branch-name-fix-issue-n-on-an-external-fork-can-fo.md)).

One call settles ownership:

```bash
gh api repos/<o>/<r>/pulls/<n> --jq '{author:.user.login, head_repo:.head.repo.full_name}'
# head_repo != <upstream>  ⇒  fork PR, not ours
```

Test the author suffix-tolerantly: this REST path returns bare `nv-slang-bot` (see the [companion state-verification page](general-misc-github-state-verification-and-bot-hygiene.md)), so strict `[bot]` equality fails closed on our PRs while a branch-name check fails open on others'. On 2026-08-04 a supervisor tick recovered a `❌ stale` CI cell for `fix/issue-11004` and nudged the fixer to rebase #11234 — again `szihs/slang`. Lessons ([a `fix/issue-N` branch on a FORK is not ours — resolve by head_repo + author](../learnings/1785803367777-a-fix-issue-n-branch-on-a-fork-is-not-ours-resolve.md)):

- `gh run list --branch fix/issue-<N>` keys on branch name only and returns runs from a same-named fork branch. The CI cell was correct; the ownership inference was wrong. A branch name authenticates the NAME, never the OWNER.
- CI staleness on someone else's PR is not our signal; never dispatch a remedy from a branch match alone.
- Read the assigned coworker's history before nudging: the fixer had already stood down on #11234 and #11242 in June with a recorded reason, and contradicting a recorded stand-down needs new evidence. A stale-session wake error (`No conversation found with session ID …`) is a prompt to read the session.
- Restoring a capability (here `gh` REST) does not restore unchecked premises; re-run the premises, not only the measurement.

The converse: a verified bot PR's regression is ours to route. In the 2026-09-30 sweep, #11709 (`fix/issue-10641`, by nv-slang-bot) showed a deterministic ASan SEGV in `Slang::List<ValNodeOperand>::operator[]` across all 13 `test-slang` jobs and was reported as "needs author attention"; it was already routed to slang-fixer. Check `gh pr view <n> --json author,headRefName` plus `head_repo` before writing a regression bullet: bot PRs go to the parent for fixer dispatch, only human PRs stay with their author ([Bot-authored PR regressions route to parent, not "author attention"](../learnings/1790734170020-bot-authored-pr-regressions-route-to-parent-not-au.md)).

## Dev↔Prod A/B test separation

Two NanoClaw instances run the slang pipeline on the same live issues, both as `nv-slang-bot[bot]`, as an intentional comparison: don't consolidate or close duplicates. Dev uses `fix/issue-*`, prod `dev/slang-fixer/*`; never push onto a prod PR branch, which contaminates the data point. All `nv-slang-bot`-authored PRs (including `dev/trelby/*`) are dev-owned and eligible for management actions ([CONSOLIDATED: dev↔prod duplicate PRs are an intentional A/B test](../learnings/1780558152382-CONSOLIDATED-dev-prod-ab-pr-conventions.md)).

## Workflows permission wall and the merge queue

The App lacks `workflows` write. GitHub compares old vs new tip trees, so a rebase or merge push onto a branch whose tip carries `.github/workflows/*` changes is rejected even when our commits touch no workflow file ([Bot can't update a stale PR branch when master changed .github/workflows](../learnings/1780567931645-bot-can-t-update-a-stale-pr-branch-when-master-cha.md), [Bot can't push rebased branches carrying .github/workflows changes](../learnings/1780568708582-bot-can-t-push-rebased-branches-carrying-github-wo.md)). `git push --dry-run` and `git ls-remote` succeed anyway; only a real `--force-with-lease` push confirms ([git push --dry-run is a false positive for the workflows wall](../learnings/1780572980623-git-push-dry-run-is-a-false-positive-for-the-githu.md)). Stripping workflow files to match the old tip is harmful (a squash would revert master's workflow changes); resolution is granting the permission (org decision) or a human push. The same wall blocks enqueueing a workflow-touching PR even if the general enqueue block were lifted, since the queue builds a merge commit with the workflow diff ([Bot enqueue of workflow-touching PRs has a second blocker](../learnings/1782727631172-bot-enqueue-of-workflow-touching-prs-has-a-second-.md)).

The bot cannot enqueue ANY PR: `enqueuePullRequest` fails with "not authorized to push to this branch" regardless of authorship. An apparent auto-requeue is GitHub's own behaviour. Audit action `left`; `gh run rerun --failed` still works ([Bot enqueuePullRequest blocked for ALL PRs](../learnings/1782260121429-bot-enqueuepullrequest-blocked-for-all-prs-not-jus.md)). Two PRs appending to one public enum (`CompilerOptionName`) can each pass CI and still collide in the queue with `duplicate case value`. Renumber above the highest value claimed across master and the queue-mate: dequeue via GraphQL `dequeuePullRequest` (gh has no verb), merge master and plain-push (fleet rule is merge, not rebase + force-push; see [Agent GitHub Fork-Takeover and Rebase Mechanics](agent-github-fork-takeover-and-rebase.md)), then wait for a maintainer requeue ([Merge-queue duplicate-case enum collision](../learnings/1782535032557-merge-queue-duplicate-case-enum-collision-two-conc.md)).

## Issue and PR close restrictions

Coworkers never close issues or PRs, not even obvious duplicates. On slang#11719 the bot closed a duplicate of #11568 via GraphQL `closeIssue` (REST `state_reason` PATCH 403s for the App); maintainer szihs objected: "You should always surface such requests to a human maintainer." Post the verified verdict/cross-link framed as a recommendation; if a human objects to a close, re-open and acknowledge ([Do NOT autonomously close issues/PRs](../learnings/1782280210918-do-not-autonomously-close-issues-prs-surface-to-a-.md)). The backstop is deterministic: `detectIssueClose()` + `preToolUseHook` in `container/agent-runner/src/providers/claude.ts` blocks `gh issue close`, GraphQL `closeIssue(` and `gh api …/issues/<n> … state=closed` regardless of instructions; `gh pr close` is not matched; opt-out env `NANOCLAW_ALLOW_ISSUE_CLOSE=1` is unset everywhere ([Coworkers must not close GitHub issues — deterministic tool backstop](../learnings/1782270000000-coworkers-must-not-close-github-issues-tool-backstop.md)).

## Issue↔PR linkage verification

Auto-close accepts `close/closes/closed`, `fix/fixes/fixed`, `resolve/resolves/resolved` + `#N`, and the qualified cross-repo form (`Fixes shader-slang/slang-rhi#772`); a verifier must grep the full set and allow an optional `owner/repo` ([Verify issue↔PR linkage with ALL auto-close keywords](../learnings/1781178144676-verify-issue-pr-linkage-with-all-github-auto-close.md), [Fixes/Closes verification must accept the qualified cross-repo form](../learnings/1781072527758-fixes-closes-link-verification-must-accept-the-qua.md)).

The #11856 incident showed two traps. A title `Fix #11856` does not auto-close, nor does the squash commit subject — only body-parsed `closingIssuesReferences`. PR #11866 merged the right fix, but its body's keyword pointed at already-closed #11720, so #11856 stayed OPEN while the fixer reported the chain terminal ([Verify a fix PR's closing reference matches the tracked issue](../learnings/1782936185036-verify-a-fix-pr-s-closing-reference-matches-the-tr.md)). And incidental prose like `PR #11785 ("...", fixes #11720)` is hijacked by the linkifier as this PR's closing reference. Rules: put `Closes #<this-issue>` in the body; describe other PRs with plain `#N`; verify `gh pr view <n> --json closingIssuesReferences` after opening and `gh issue view <tracked> --json state` after merge. If a merged fix leaves the issue OPEN, the closest coworker comments flagging the mis-reference so a maintainer closes it ([PR-description prose fixes-N closes the wrong issue](../learnings/1782951523566-pr-description-prose-fixes-n-closes-the-wrong-issu.md)).

A keyword audit needs a positive control: an over-anchored grep (`$` against CRLF) returns a confident empty. Before recording a verdict from zero hits, run the pattern on a body known to carry the keyword, and prefer GitHub's computed `closingIssuesReferences` over text matching ([the control is the counterfactual question](../learnings/1785770932836-the-control-is-the-counterfactual-question-not-a-b.md)).

## Existing-fix checks and review signals

Before triage recommends a fix — and as the fixer's first step — check for an open fix PR. Maintainers often file an issue and open a fix within minutes without announcing it. Use `gh pr list --search "Fixes #<num>"` (not `gh search prs`, which lags); if one exists, stand down without a redundant comment ([Check for an existing fix PR before recommending OR implementing](../learnings/1781241842104-check-for-an-existing-fix-pr-before-fixing-or-recommending.md)). Upstream, linked-PR timelines are not enough. Before saying "no upstream fix", search the upstream repo's open PRs by function/file name and by the reporter and maintainers. On slang#13230 the bot called its patch "the first proposed fix" for KhronosGroup/SPIRV-Tools#6711, but the reporter (jkwak-work) had opened SPIRV-Tools#6885 twelve days earlier, and a maintainer wasted time opening shader-slang/SPIRV-Tools#16 from ours. A caveat like "unlinked work can't be excluded" means run the search. When `gh api` to KhronosGroup returns 401, use WebFetch on `https://github.com/<org>/<repo>/pulls?q=is:pr+<term>` or fetch `refs/pull/*/head` ([before claiming "no upstream fix exists", search upstream PRs](../learnings/1790642860153-before-claiming-no-upstream-fix-exists-search-upst.md)).

A `CHANGES_REQUESTED` review with a positive or neutral body and zero inline comments is a decline-to-merge. Fetch `/reviews` and `/comments` first; if so, reply once acknowledging the verdict and close the chain upstream with no code change ([CHANGES_REQUESTED with a 'looks good' body and zero inline comments](../learnings/1782512263705-changes-requested-with-a-looks-good-body-and-zero-.md)).

## Conflict resolution

**Copilot race.** After a maintainer comments `@copilot resolve the merge conflicts` on a bot PR, Copilot may push too. `git fetch` first; if its resolution is equivalent, `git reset --hard` to it and fast-forward only incremental fixes, never force-push over it ([@copilot may resolve conflicts on bot-authored PRs](../learnings/1782711499913-copilot-may-resolve-conflicts-on-bot-authored-prs-.md)).

**Recurring conflict = possible supersession.** On slang#11664 our approved #11665 kept re-conflicting because expipiplus1's narrower #11775 had merged and closed the issue; both used diagnostic code 20020, which the uniqueness check would reject. Check issue state and merged rivals (`gh pr list --search "<issue#>" --state merged`) before resolving; don't resolve mechanically or close our PR; surface close-vs-rework with a scope comparison; if reworking, target only the residual cases and reuse the merged PR's code ([A recurring merge conflict on an approved PR can mean a competing fix merged](../learnings/1782737882496-a-recurring-merge-conflict-on-an-approved-pr-can-m.md), [Recurring PR conflict may mean the issue was closed by a competing PR](../learnings/1782738059209-recurring-pr-conflict-may-mean-the-issue-was-close.md)).

**Follow-up already on master = semantic conflict.** On slang#9085 master had merged follow-up #12248, adding atom `texture_shadowbias` and retargeting `SampleCmpBias` to it. Git flagged 5 hunks, but 28 bias-only `[require(..., texture_shadowgrad)]` sites auto-merged cleanly and would have recreated the misnaming; the PR's edit to the old atom (dropping `| GL_EXT_texture_shadow_lod`) also had to move to the new one. Recipe: `git log -S <new-symbol> base..origin/master` and read that PR's invariant; `git show origin/master:<file> | grep <old-symbol>` — zero master uses means every hit came from the PR; check master's deprecations (#12836 dropped `-allow-glsl`, so new tests needed `SIMPLE_EX: -lang glsl <file>`); list every beyond-the-markers change for the maintainer. The slang base clone is shallow, so `git merge-base` is empty until `git fetch --shallow-since=<date>` with explicit `+refs/heads/X:refs/remotes/origin/X` refspecs ([merging master into a PR whose follow-up already landed](../learnings/1790629728845-merging-master-into-a-pr-whose-follow-up-already-l.md)).

**Same bug fixed differently on master = test clash.** PR #13342 went DIRTY after master #13715 changed the same `GetElement(makeVector)` loop; both fixed one Metal miscompile (the old fold took a whole `packed_*` operand as lane 0) in opposite ways, each with a FileCheck test on the same shape expecting different output (`h_0[int(0)]` vs `(float4(*(colors+i)))[int(0)]`). Read master's regression test, not just the hunk; default to master's tested behaviour and update the PR's CHECK line and comments. Report in a fresh status comment; never PATCH the explain-diff marker comment (`<!-- explain-diff-html:comment ... -->`) ([a master change that fixes the same bug differently is a test clash](../learnings/1792746371295-a-master-change-that-fixes-the-same-bug-differentl.md)).

**`--force-with-lease` `stale info`.** The lease compares against `refs/remotes/origin/<branch>`, but plain `git fetch origin <branch>` updates only `FETCH_HEAD`, and in a `git worktree` the ref may not exist (`unknown revision` right after `git push -u`). Lease explicitly: `git push --force-with-lease=<branch>:$(git rev-parse FETCH_HEAD) origin <branch>`, or `git fetch -f origin <branch>:refs/remotes/origin/<branch>`. Confirm the true head has no unique or maintainer commits first; never blind `--force`. `git range-diff` with all-`=` rows proves a rebase kept commits identical, so a prior APPROVE stands ([force-with-lease "stale info" inside a worktree](../learnings/1789460745636-git-force-with-lease-stale-info-inside-a-worktree-.md)).

## Cross-fork PR limitations

The App can open a cross-fork PR via REST with a user PAT (`gh api repos/<base-owner>/<repo>/pulls`) but not via `gh pr create` (GraphQL → App token → 403). Without a PAT, push to `origin = shader-slang/slang`, open the draft against `master`, and give the fork author a cherry-pick recipe ([Bot (GitHub App) cannot open a PR into a personal fork](../learnings/1781015587691-bot-github-app-cannot-open-a-pr-into-a-personal-fo.md)).
