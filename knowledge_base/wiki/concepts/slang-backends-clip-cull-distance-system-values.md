# Slang SV_ClipDistance / SV_CullDistance: DXC packing, the GLSL shared-array path, Metal [[clip_distance]], and how to verify changes

HLSL clip and cull distances are semantic-indexed values (`SV_ClipDistance0`, `SV_ClipDistance1`, ...) that each target stores in a different shape: one float array per stage and direction on SPIR-V/GLSL (`gl_ClipDistance[]`, `gl_CullDistance[]`), and a `[[clip_distance]]` member that is a `float` or native `float[n]` on Metal. This page records the reference rule DXC uses, where Slang diverges from it, what the in-flight fixes slang#13931 (PR #13939, GLSL/SPIR-V vectors) and slang#13934 (PR #13940, Metal) learned, and the verification practice that caught their bugs. Both PRs were still open on 2026-10-26.

## TL;DR

- **DXC is the reference layout.** In/out × clip/cull are four separate groups. Within a group, semantic indices are sorted, each index's offset is the running sum of the component counts before it, gaps are compacted, and elements must be float.
- **Slang base (52e29ab43) diverges:** it uses the semantic index itself as the array index (`SV_ClipDistance0` + `SV_ClipDistance3` gives `gl_ClipDistance[4]` with [1],[2] unwritten), scalar `SV_CullDistance0/1` collide on one `gl_CullDistance =` write, and the front end accepts only `float`/`float[]`.
- **Lifting the front-end float check alone is wrong:** vectors then silently truncate to `.x`.
- **The shared-array path in `createSimpleGLSLGlobalVarying` serves every system value with `arrayIndex >= 0`** (SV_Coverage, NV_X_RIGHT). Gate clip/cull-only behavior on an explicit `GLSLSystemValueInfo` flag, never on "the type is a vector".
- **DXC-style compaction is a visible layout change:** a fragment shader that reads only `SV_ClipDistance1` sees a different element.
- **Mixed array and non-array clip values can silently alias.** The array path always starts its own `gl_ClipDistance` at element 0. If sizes differ, SPIR-V validation fails (VUID-...-09659). If sizes match, validation passes and one value overwrites the other.
- **GLSL can index an unsized builtin input array only with constants.** Slang never redeclares input `gl_ClipDistance` with a size, so a dynamic component index on a spread vector must load the vector into a temp and index that.
- **Hull patch-constant outputs are legalized after any entry-point pre-pass**, and geometry shaders visit one field once per stream. A counting pre-pass must cover the first and dedupe by declaration for the second.
- **Metal needs native C arrays with the attribute before the bound:** `float d [[clip_distance]] [N];`. `metal::array<T,N>` is a struct and is rejected. Native arrays are not assignable, so whole-array writes become per-element stores in IR.
- **Verification:** run every new test entry point through `-emit-spirv-via-glsl` as well as direct SPIR-V; probe matching and mismatched array sizes; A/B against an unmodified master build; run `/code-review` before pushing; trial-merge sibling PRs that touch the same legalizer; check sibling PRs for diagnostic-code collisions.

## The reference rule: how DXC packs clip/cull distances

DXC's rule lives in `tools/clang/lib/SPIRV/GlPerVertex.cpp`, `calculateClipCullDistanceArraySize` (~lines 483-512). It keeps four groups separate: input clip, input cull, output clip, output cull. Within each group it collects the semantic indices and sorts them ascending. Each index's offset is the running sum of the scalar component counts of the indices before it (a scalar counts 1, a vector or float array counts its components), and the array size is the total. Gaps are compacted, so scalar `SV_ClipDistance0` + `SV_ClipDistance3` map to `[0]` and `[1]` with size 2. Elements must be float. [DXC SPIR-V packing rule for SV_ClipDistance/SV_CullDistance vectors (and Slang's divergence)](../learnings/1792917335289-dxc-spir-v-packing-rule-for-sv-clipdistance-sv-cul.md)

## Slang's behavior before the fixes (base 52e29ab43)

Consider `float a : SV_ClipDistance0; float b : SV_ClipDistance3;`. The GLSL legalizer (`slang-ir-glsl-legalize.cpp:535-548`) uses the semantic index itself as the array index, so it emits `gl_ClipDistance[4]` and never writes `[1]` and `[2]`. `SV_CullDistance` gets no `arrayIndex` at all, so scalar `SV_CullDistance0` and `SV_CullDistance1` become two colliding `gl_CullDistance =` writes. The front end (`semantic sv_clipdistance`/`sv_culldistance` in `core.meta.slang`, added by #9260) accepts only `float` and `float[]`, which is why a `float2 : SV_ClipDistance0` is rejected with E30701 on every target (slang#13931). Lifting that check alone brings back silent `.x` truncation, because `convertMaterializedValue` converts the vector to a scalar. [DXC SPIR-V packing rule for SV_ClipDistance/SV_CullDistance vectors (and Slang's divergence)](../learnings/1792917335289-dxc-spir-v-packing-rule-for-sv-clipdistance-sv-cul.md)

On Metal the outputs come out with an empty `[[]]` attribute (slang#13934): their system-value entries set only `isSpecial`, and `ensureStructHasUserSemantic` still adds an empty-name decoration. The E30701 check rejects only vectors and int, so `half clip : SV_ClipDistance0` passes it. [DXC SPIR-V packing rule for SV_ClipDistance/SV_CullDistance vectors (and Slang's divergence)](../learnings/1792917335289-dxc-spir-v-packing-rule-for-sv-clipdistance-sv-cul.md) [Trial-merge sibling PRs that touch the same legalization code](../learnings/1792932359991-trial-merge-sibling-prs-that-touch-the-same-legali.md)

## Changing the GLSL/SPIR-V shared-array path (slang#13931, PR #13939)

Non-array clip/cull values go through the shared-global path: `createSimpleGLSLGlobalVarying` looks up `systemNameToGlobalMap` so that every `SV_ClipDistanceK` lands in one `gl_ClipDistance` global at its `arrayIndex`. That path serves every system value with `arrayIndex >= 0`, not only clip distance. In PR #13939, spreading a vector over consecutive elements by testing `as<IRVectorType>(legalizedParamType)` there also split NV_X_RIGHT's `float4` (`gl_PositionPerViewNV[1]`) into four float stores, silently. The principled gate is an explicit flag on `GLSLSystemValueInfo` that only the clip/cull entries set. The same review found a silent layout change: DXC-style compaction of scalar clip distances changes which element a fragment shader that reads only `SV_ClipDistance1` sees, so the compaction is a behavior change that must be stated, not a refactor. [GLSL legalizer: a shared-array system-value change must be checked against EVERY arrayIndex user (NV_X_RIGHT), and run /code-review before pushing](../learnings/1792924975071-glsl-legalizer-a-shared-array-system-value-change-.md)

A declared array, `float c[N] : SV_ClipDistanceK`, takes the declarator/array path instead, and that path always creates its own `gl_ClipDistance` global starting at element 0. When one signature mixes the two paths, the result depends on the sizes. If the arrays differ in size, direct SPIR-V gets two `BuiltIn ClipDistance` variables and fails validation with VUID-StandaloneSpirv-OpEntryPoint-09659, which is a loud failure. If the sizes match, for example `float c[2] : SV_ClipDistance0` + `float2 d : SV_ClipDistance2` under PR #13939's packing, the emitter ends up with one variable, validation passes, and `d` silently overwrites `c`; DXC would give `c`→[0..1] and `d`→[2..3]. `-emit-spirv-via-glsl` exposes it, because glslang rejects the GLSL redeclaration ("redeclaration of array with size"). Measured on #13939 head 3d18cf842. [Clip-distance globals: SPIR-V validation catches duplicates only when array sizes differ](../learnings/1792926418369-clip-distance-globals-spir-v-validation-catches-du.md)

A vector stored one component per element also changes how a dynamic component index lowers. `slang-emit-glsl.cpp` (`_maybeEmitGLSLBuiltin`) redeclares `gl_ClipDistance`/`gl_CullDistance` with a size only for outputs, so inputs stay unsized, and GLSL indexes an unsized builtin array only with constants. A `half2 : SV_ClipDistance1` fragment input indexed with `i` emitted `gl_ClipDistance[4 + i]`: direct SPIR-V validates it, glslang rejects it ("array must be redeclared with a size before being indexed with a variable"). The fix loads the whole vector into a temp and indexes the temp. This was a GLSL-only bug in #13939 R1 that three reviewers and the lead check all missed, because the test had only a `spirv-asm` run. Before that, `getSubscriptVal` had no `arrayIndex` case at all for a dynamic component index on a type-adapted `half` vector, which was an ICE. [Clip/cull review: run -emit-spirv-via-glsl on every new entry point, not just the headline ones](../learnings/1792932690177-clip-cull-review-run-emit-spirv-via-glsl-on-every-.md) [slang GLSL legalizer: a dynamic index on a vector spread over gl_ClipDistance must index a copy; reviewer patches are worth applying verbatim](../learnings/1792935283111-slang-glsl-legalizer-a-dynamic-index-on-a-vector-s.md) [GLSL legalizer: a shared-array system-value change must be checked against EVERY arrayIndex user (NV_X_RIGHT), and run /code-review before pushing](../learnings/1792924975071-glsl-legalizer-a-shared-array-system-value-change-.md)

An entry-point pre-pass that sizes the arrays by counting clip/cull declarations has two traps. Hull-shader patch-constant outputs are legalized through `invokePatchConstantFuncInHullShader` after any entry-point pre-pass has run, so a pre-pass that sees only the entry point misses them (an ICE in #13939). Geometry shaders visit the same struct field once per output stream, so the count must dedupe by declaration, or the pre-pass rejects valid two-stream shaders. [GLSL legalizer: a shared-array system-value change must be checked against EVERY arrayIndex user (NV_X_RIGHT), and run /code-review before pushing](../learnings/1792924975071-glsl-legalizer-a-shared-array-system-value-change-.md) [slang GLSL legalizer: a dynamic index on a vector spread over gl_ClipDistance must index a copy; reviewer patches are worth applying verbatim](../learnings/1792935283111-slang-glsl-legalizer-a-dynamic-index-on-a-vector-s.md)

`gl_CullDistance` on the GLSL path needs `#version 450`; glslang rejects both `ARB_cull_distance` and `GL_ARB_cull_distance` as extension names. [GLSL legalizer: a shared-array system-value change must be checked against EVERY arrayIndex user (NV_X_RIGHT), and run /code-review before pushing](../learnings/1792924975071-glsl-legalizer-a-shared-array-system-value-change-.md)

## Metal: `[[clip_distance]]` as a native C array (slang#13934, PR #13940)

MSL 4.1 Tables 5.4 (vertex outputs) and 2.11 (mesh vertex) type `[[clip_distance]]` as `float` or `float[n]`. Slang normally emits `metal::array<T,N>`, which is a struct, so it is the wrong type. The attribute goes between the name and the bound: `float d [[clip_distance]] [N];`. The form `float d[N] [[clip_distance]]` fails with "'clip_distance' attribute cannot be applied to types", and a second `[[clip_distance]]` member fails with "declaration with attribute 'clip_distance' already specified", so all clip distances must share one member. Native arrays are not assignable, so every whole-array write is lowered to per-element stores in IR. PR #13940 does this for the generated vertex result struct (stores and `makeStruct`) and for a Metal-only copy of the mesh vertex struct that is filled at `set_vertex`. [Metal [[clip_distance]] arrays must be native C arrays with the attribute before the bound](../learnings/1792927160902-metal-clip-distance-arrays-must-be-native-c-arrays.md)

Two traps in that lowering. In `slang-ir-legalize-varying-params.cpp`, WGSL entry-point params can still be `out` when `legalizeSystemValue` runs; "param ⇒ input" holds only for Metal, after `legalizeShaderOutputParamsForMetal`. And `MapStructToFlatStruct::_emitCopy` types its field accesses with the containing struct's type, so the array type must come from the field declaration, not from the copied value. [Metal [[clip_distance]] arrays must be native C arrays with the attribute before the bound](../learnings/1792927160902-metal-clip-distance-arrays-must-be-native-c-arrays.md)

## Verification practice for clip/cull changes

Direct-SPIR-V validation passing does not prove the GLSL path is valid, and a green `SLANG_RUN_SPIRV_VALIDATION` does not prove the layout is correct. When a legalizer change touches GLSL builtin arrays, run every new test entry point, not only the headline ones, through `-target spirv -emit-spirv-via-glsl` with a short loop, in addition to direct SPIR-V. When the change creates builtin array globals, probe mixed array and non-array signatures with matching sizes as well as mismatched ones. [Clip/cull review: run -emit-spirv-via-glsl on every new entry point, not just the headline ones](../learnings/1792932690177-clip-cull-review-run-emit-spirv-via-glsl-on-every-.md) [slang GLSL legalizer: a dynamic index on a vector spread over gl_ClipDistance must index a copy; reviewer patches are worth applying verbatim](../learnings/1792935283111-slang-glsl-legalizer-a-dynamic-index-on-a-vector-s.md) [Clip-distance globals: SPIR-V validation catches duplicates only when array sizes differ](../learnings/1792926418369-clip-distance-globals-spir-v-validation-catches-du.md)

A change to a shared-array system-value path must be checked against every `arrayIndex` user, not only the value being fixed. On #13939, `/code-review` at medium effort, run before pushing, caught the NV_X_RIGHT split, both ICEs, and the compaction layout change. All four were reproduced A/B against an unmodified master build, so keep a snapshot (`cp build/Debug/{bin,lib}`) before rebuilding. A `DIAGNOSTIC_TEST` needs an annotation for both the diagnostic title and its span message; `E5xxxx` alone does not match. In the last review round, the peer reviewer (slang-reviewer) attached tested remedy patches under "Tested remedy patches" in its review file; extracting them with awk, then `git apply --check` and apply, was the fastest way through. [GLSL legalizer: a shared-array system-value change must be checked against EVERY arrayIndex user (NV_X_RIGHT), and run /code-review before pushing](../learnings/1792924975071-glsl-legalizer-a-shared-array-system-value-change-.md) [slang GLSL legalizer: a dynamic index on a vector spread over gl_ClipDistance must index a copy; reviewer patches are worth applying verbatim](../learnings/1792935283111-slang-glsl-legalizer-a-dynamic-index-on-a-vector-s.md)

When one fixer has two open PRs on the same legalizer, run `git merge-tree` on them, then do a trial merge and build. For #13939 and #13940, which both change the Metal ClipDistance/CullDistance case in `slang-ir-legalize-varying-params.cpp`, that found three problems. First, both PRs added diagnostic E55219: `diagnostics.lua` merges cleanly, but uniqueness is enforced in `slang-diagnostics-helpers.lua:751`, so the second PR to land fails the build; check sibling fleet PRs for diagnostic-code collisions before opening a PR. Second, one PR passed the struct key instead of the field as `parentVar`; an `IRStructKey` has a null type (`createStructKey` passes nullptr), so the other PR's `isVectorTypedVarying(parentVar)` would null-deref in `getIRVectorElementSize`. Third, the mesh path matches semantic names by string and bypasses `getSystemValueInfo`, so it missed the other PR's guard and emitted invalid MSL silently after the merge.
