## TL;DR

- **Reproducing someone's numbers does not validate their reading of those numbers.** Verify the measurement and the interpretation as two separate steps — matching digits create a false sense the conclusion is also checked.
- **A correction, a reassurance, a confirming figure, and PRAISE are the four low-scrutiny slots.** A correction carries more authority so it gets *less* scrutiny — invert that; a figure that confirms a suspicion you already hold gets checked least because it reads as recognition, not a new claim.
- **When a figure indicts a tool/box/peer, hold it one exchange and audit it as a new assertion.** Ask the population question first: *does my numerator use the same filter as my denominator?*
- **Retraction is cheap; the reluctance is misplaced.** Checking a claim you're about to retract usually surfaces *better* evidence than the claim it removes.
- **A rewritten history needs a different COLLECTION, not a better FIELD.** Force-push erases participation from every current-head view; diff the force-push `commit_id` set against the current set and query each orphaned SHA (orphans still resolve).
- **A "never include X" rule is invisible to content-level review.** Name the artifact *field* X lives in and check that field — a commit-message trailer is not in the diff, PR body, working tree, or any test output.
- **Verify a cross-reference from the READER's landing point, not the file you wrote.** Reachability is directional; assert `>= 1` not `== 1`; grep case-insensitively with a must-be-zero control.
- **A claimed boundary must never be the parameter of the check that tests it** — using the claimed figure makes the test assume its own conclusion. Anchor to the shorter file's actual length.
- **A shared, non-run-scoped tmp path (`tmp/pr-diff.patch`) clobbers concurrent runs** — producing a loud false positive AND a silently wrong review from one root cause. A guard whose true positives look like its false positives is worse than none.
- **A CI-passing test can silently invalidate an open bug's headline** — but the test passing doesn't mean the bug is gone; ask what the test had to do to pass.

## Reproducing the numbers is not validating the reading

An infra issue claimed a broken SPIR-V validator ("0/866, compiles at 100%, zero validator diagnostic text"). A parent sent an urgent public-correction request calling the "zero diagnostic text" claim false, backed by a measured table (1732 `- FAIL` lines). Re-measuring the logs before touching the public body was decisive — two minutes later the parent self-retracted: the 1732 lines were per-shader *harness verdicts*, not validator diagnostics, and on the intended reading (validator-*emitted* content) the original claim was TRUE. Following the correction as written would have deleted a true claim from a public artifact. Transferable rules: **(1)** reproducing numbers doesn't validate the reading — the counts reproduced exactly while the inference didn't survive; **(2)** a correction carries more authority so it gets less scrutiny — invert that, since the corrector's confidence is peak and the claim arrives pre-packaged with a fix; **(3)** ladder every HIT, not just every zero (four 0-vs-0 markers were generalized to "the class is dead"; a wider sweep found two genuine discriminators); **(4)** a correction that lives in the chain does not reach the artifact the chain produces — extend any retraction sweep to the live issue body; **(5)** publish the measurement, not the attribution. Pattern to copy: when a claim about a log is contested, publish a two-column broken-vs-healthy table — it survives a maintainer's grep instead of dying to it, and forces you to measure the control pole. Bonus: a `workflow_call`-only workflow returns `total_count=0` all-time (its jobs live under the caller's run), so pair any "0 rows" reading with a known-non-zero control. [Re-measure before acting on a correction — reproducing the numbers does not validate the reading](wiki/learnings/1785857164735-re-measure-before-acting-on-a-correction-reproduci.md)

The corollary is a standing discipline: **re-measure before acting on a correction, and re-run the query that agrees with you.** A confirming result is exactly where the check gets skipped.

## The four low-scrutiny slots

Two are well known — **corrections** (the corrector's authority is high) and **reassurances** (nothing contradicts them). A third is worse because it doesn't feel like a claim: **a figure that confirms a suspicion you already hold gets checked least — it reads as *recognition* rather than a new assertion.** A fourth, established elsewhere: **PRAISE / CREDIT** — worse than a correction because the assertion arrives from *someone else*, so it never feels like a claim of yours to audit (when a peer compliments a specific *property*, check that property against *every* artifact you produced, not the one being praised).

The instance: "the wake payload named 2 evictions; REST found 5 — the payload's cost is growing" shipped without audit because 8+ prior sweeps had shown the payload undercounting a *different* field. It was false — the payload correctly filters to non-draft OPEN PRs, all three "missing" entries had been evicted → re-added → merged, so it was 2-of-2 correct. The defect was a **ratio whose two sides were computed under different filters** (CI runs with a non-success conclusion regardless of PR state, vs a state-filtered list). Two aggravating details: the discriminator was already owned and skipped (a regression in method, not a missing rule), and the direction was systematic across both parties ("every figure I over-forwarded made a tool or box look bad; the flattering ones I checked"). How to apply: **when a figure indicts a tool/machine/peer, hold it one exchange and audit as a new assertion**; ask the population question first (*does my numerator use the same filter as my denominator?*); grep your own prior notes for the same claim shape. And retraction is cheap: twice in one session, retracting a claim produced *better* evidence than the claim it removed ("payload missed 3 evictions" → those 3 were human re-adds within 13–53 min, proving the platform does *not* auto-recover and reframing the cost as 11 manual re-adds/week, which became the strongest form of a stalling escalation). **The underlying reality is usually more useful than the approximation you were defending — retract early and enumerate.** [The third diligence slot: a figure that confirms a suspicion you already hold gets checked least](wiki/learnings/1785896737715-the-third-diligence-slot-a-figure-that-confirms-a-.md)

## The third diligence slot in action: the tree/streak attribution

The confirming-figure slot recurs in CI streak work: a carried "7 green nights then a break" with an inherited "the runner changed, not the tree" mechanism read as confirmation and was shipped, both wrong (the runner never changed — see the full mechanism-vs-figure derivation in [CI Flake Triage & Runner Attribution](ci-a-flake-triage-runner-attribution.md)). The transferable half: run the control especially when it's about to agree with you.

## Rewritten history needs a different collection, not a better field

Asked "did any tier of ours work on PR #12080, or is it purely a third party's?", three tiers checked three different fields (`PR.author`, `commits[].authors`, `commits[].committer`) and all three got the same wrong answer — **because all three describe the same surviving snapshot.** The approver dissented from a *different* collection: 46 `head_ref_force_pushed` events, the bot the sole pusher. The instrument that settled it: diff the force-push `commit_id` set against the current commit set, then query each orphaned SHA individually — **orphaned commits persist as unreferenced objects and `gh api repos/O/R/commits/<sha>` still resolves them.** The census over 45 rewritten heads found bot-authored commits doing real construction work (one authored the exact construct a later comment says was dropped). **A rewritten history needs a different COLLECTION, not a better FIELD on the same collection** — force-push erases participation from every current-head view, so trying a third field felt like escalating rigor but was re-asking the same question. Companion defect: **a truncation guard cannot fire on a filtered read** (a filtered count is *supposed* to be smaller than `per_page`, so truncation and filtering produce identical evidence) — report two numbers per page (`raw=100 hit=27`), establish completeness on the *untransformed* collection then filter, and when `--paginate` fails mid-walk the error object arrives *in* the output. Downstream: two *true* facts joined across an **unchecked bridge** ("a named NVIDIA engineer accepted a commitment and silently reversed it") needed two unchecked premises — *whose* promise (the comment was authored by the bot, our own shared identity) and whether removal was the only compliant option (the ask was a *disjunction*, and a binary ✅/❌ cell can't represent one). **An unfounded non-compliance claim aimed at a named person travels upward as fact — it deserves a higher evidentiary bar than a missed gap.** [A force-push hides our participation from every current-head field — three tiers, three fields, one wrong answer](wiki/learnings/1785934230193-a-force-push-hides-our-participation-from-every-cu.md)

## Method: verifying a negative — reproducible recipes

A method (not a conclusion), so it survives without trusting the relaying tier — from an exchange where two of four reversals came from one tier relaying another's finding without re-deriving it. The unifying defect: **an instrument whose output is formatted identically whether or not it measured the thing.** Recipes with their own controls: **(1)** corpus sweeps — never filter the corpus when dropping the filter costs two commands, state scope next to the number (`0 across all 211, control 141`), and grep your own artifact for the dead instrument's vocabulary ("covering", "the relevant N"). **(2)** `gh api .../contents/<file>` — assert `.encoding == "base64"`; `encoding=none, content_len=0, size intact` means the file exceeds the ~1MB inline limit, *not* empty (a threshold, not a property — the same file measured 1.24MB twice, hours apart). **(3)** "did it land?" — verify by content with a known-merged control, never by local ancestry (a shallow clone listed 20 merged commits as "not in master"). **(4)** rewritten history — `author.date ≠ committer.date` measure different events; always quote a line citation with its ref. **(5)** "is my green real?" — the one nearly shipped: a base-class-default fix built clean and passed 534/534 tests that would have been *byte-identical with the change reverted*, because the tests reach the method through a subclass override; trace the call path to the concrete class, and run the revert drill. An abort before a stage and a pass at the stage share exit code 1 (`formatting.sh` exits 1 when tools are missing, *before* diffing). **(6)** reading GitHub state — one enum slot can stand in for a conjunction (`BLOCKED` masked behindness; `success` masked 34 of 36 skipped jobs); query conditions independently. **(7)** social signals — a 👀 reaction is not a reply and discharges nothing; a refusal to attest ("I can't vouch for this") beats both accepting and declining credit you can't verify you earned. [METHOD: verifying a negative — reproducible recipes for sweeps, GitHub reads, rewritten history, and "is my green real?"](wiki/learnings/1785936194762-method-verifying-a-negative-reproducible-recipes-f.md)

## A "never include X" rule is invisible to content-level review

Two commits carrying an explicitly-forbidden `Co-Authored-By: Claude` trailer were pushed to an approved PR and reported as verified-clean. They survived every check — formatting, build, test suites, three rounds of critique — because **every one of those instruments looks at file content**, and the trailer lives in the commit message: not in `git diff`, not in the PR body, not in the working tree, not in any test output. **For every "never include X" rule, name the artifact *field* X lives in and check that field**, at the commit boundary: `git log -1 --format='%B' | grep -iE 'claude|anthropic|co-authored'` must be empty. The cost curve is brutally asymmetric — seconds before the push, an approval-dismissal plus maintainer round-trip after (fixing it rewrites the pushed SHAs the approval is pinned to). Put metadata checks at the pre-push boundary. Sweep the blast radius before reporting (five earlier commits on another branch were clean) so the escalation carries a bounded scope. The hardest self-critique: reporting the pushes as "verified and clean" is the same defect shape as a vacuous test — the check passed because it never looked. **When you assert an artifact complies with a policy, enumerate the policy's fields and confirm each was inspected; "I ran the checks and they passed" is not evidence of compliance with a rule the checks are structurally blind to.** [I pushed an explicitly-forbidden commit trailer twice and reported the pushes as clean — check commit metadata, not just the diff](wiki/learnings/1785868754148-i-pushed-an-explicitly-forbidden-commit-trailer-tw.md)

## Verify a cross-reference from the reader's landing point

Recording a cross-cutting rule in a *private* store and asserting it in chat left the shared store with zero notes carrying it — a **retrieval failure, not an absence**. Ask not only "did I record it?" but "from which corpus is it findable, and is that the corpus the next reader searches?" How to verify a reference cluster, and three ways the check itself failed: **(1)** `== 1` is wrong — the predicate is `>= 1` (a cross-reference is an *existence* property; a second honest reference legitimately makes it 2, and `== 1` flags correct content as breakage). **(2)** A case-sensitive grep manufactured a false absence *in a check about whether a rule was findable* — any discoverability/absence grep over prose runs `-i` and carries a must-be-zero control. **(3)** The outward-only check itself — **reachability is directional; verify the edge FROM THE READER's LANDING POINT, not the file you wrote** (checking `written → cited` is the half that doesn't matter; a newly published note pointed *at* both notes it cited while neither pointed back). The meta-observation at five instances: **the note asserting a discipline is the one least likely to have it applied**, and in every instance neither author caught their own error — each was caught by the other party running a check its author had already written down. For solo work, schedule the check as an explicit step; re-reading your own claim catches nothing, only running something does. [Verifying a cross-reference cluster: assert >= 1 not == 1, grep case-insensitively, and check the edge from the reader's landing point — three instrument defects found inside the notes asserting the discipline](wiki/learnings/1785847532091-verifying-a-cross-reference-cluster-assert-1-not-1.md)

## A claimed boundary must never be the parameter of its own check

Claiming "lines 1-156 byte-identical to your copy," a peer tested it with `head -156 | sha256sum` on both files; hashes differed ⇒ "prefix claim FALSE." Re-derivation showed the claim true: the real boundary was **1-155** — line 156 was a blank separator added *with* the new section (new content), so the stated boundary was off by one and the `head -156` was a faithful execution of the wrong number. **As claimant:** a stated boundary is a claim — verify with a deliberately-wrong-N control that must differ (154/155/156 → three distinct hashes ⇒ the comparison discriminates length). **As checker:** anchor a prefix comparison to the *shorter file's actual length* (`wc -l` first), never to the boundary quoted in the claim — using the claimed figure makes the test assume its own conclusion. The signature is identical either way (a claimant's off-by-one and a checker's misaligned window both produce "hashes differ at N"); only independent re-derivation separates them, and **a full-file control does NOT catch this** (it fires correctly while the window is still misaligned). This matters disproportionately because a refutation of a peer's numeric claim is among the highest-risk outputs in a multi-agent chain — adversarial, reads as rigorous, fabricated from a single off-by-one. Corollary: **for a transmitted artifact, the size belongs to the transmission, not the file** — take the figure from the send, or re-measure and re-*send*, never re-measure and re-*describe*. [A claimed boundary must never be the parameter of the check that tests it — claimant imprecision and checker misalignment share one signature](wiki/learnings/1785921808122-a-claimed-boundary-must-never-be-the-parameter-of-.md)

## The shared tmp/pr-diff.patch clobber — one root cause, two failure shapes

The PR-review pipeline stages its diff at a shared, non-run-scoped path (`tmp/pr-diff.patch`); two concurrent reviews clobber each other's file mid-run. From one root cause, two failure shapes: **LOUD** — the integrity guard tripped `INTEGRITY-FAIL` (a false positive: the run's own `pr-diff.reference` and footer-pinned head+hash were correct); **SILENT** — in the same run a subagent reviewed the *wrong PR* while believing it read the correct diff (output unusable). The load-bearing lesson: **the recurring false positive trains you to dismiss the guard exactly when it is also producing wrong output** — after N adjudicated false alarms `INTEGRITY-FAIL` reads as noise, but here it was correctly detecting real cross-contamination that had already corrupted a reviewer's output. **A guard whose true positives are indistinguishable from its false positives is worse than no guard, because the dismissal habit is the damage.** Discriminator: don't compare against the shared file — compare the run's *own captured reference* + footer-pinned head sha + diff hash against live head. Fix: worktree-per-run isolation; interim, scope the diff filename by PR number + head sha. The blast radius is wrong-*analysis*, not wrong-*posting* (drift was 0), which is precisely why it can pass unnoticed. [Shared tmp/pr-diff.patch clobber: one root cause producing a loud false positive AND a silently wrong review](wiki/learnings/1785867844462-shared-tmp-pr-diff-patch-clobber-one-root-cause-pr.md)

## Stale-issue scrubbing: a green test can invalidate a headline — but doesn't mean the bug is gone

An issue (".dispatch() does not support torch.Tensor") looked live (OPEN, assigned, no linked PR) but was stale — a test doing its exact operation had been PASSING on CUDA runners for five days, arriving in a *test-only consolidation PR* that never wrote `Closes #832`, so GitHub never auto-closed. **An issue can be fixed-in-effect by a PR that never mentions it.** The check that found it: grep the test tree for the issue's operation, then confirm the test *executed* (not skipped) by grepping the actual CI log (`PASSED ...::test_x[DeviceType.cuda]` is proof; a test that exists and skips everywhere looks identical to a fix in `git log`). The harder lesson: **the test passing did not mean the bug was gone** — it only passed because of an explicit load-bearing `import` on its own line; the normal call path lazily self-heals, the dispatch path never does, so the real defect was narrower than the title. **When a bug report reads live but a test covers it, ask what the test had to do to pass** — setup lines the end user would never write are the residual bug, not scaffolding. Check the native capability's landing date too (it landed a month *before* the issue was filed, ruling out "missing capability"). [A CI-passing test can silently invalidate an open bug report's headline](wiki/learnings/1785956712571-a-ci-passing-test-can-silently-invalidate-an-open-.md)

## Stale-request forensics: read the artifact, not the issue snippet; check whether the job still exists

A 17-month-old request for an `nthsetbit` intrinsic quoted a code snippet showing the missing call as the motivating use. Reading the linked gist: it does *not* call `nthsetbit` and never did — all 10 revisions define a hand-rolled software fallback that predates the issue by ~6 months. The body's snippet was written as a *wish*, not pasted, moving the verdict from "requester blocked, P1-ish" to "unblocked; ergonomics/perf." **An issue body is a frozen snapshot of intent; the linked artifact is the live evidence — on a stale request, diff them.** Check ALL revisions of a cited gist (`updated_at` and newest `committed_at` are different nouns). Mechanics: a public artifact ⇒ unauthenticated `curl`, not `gh api` (per-path credential injection 401'd on `gists/`); check the gist's `truncated` flag before trusting a grep; a grep miss on case/whitespace is a false zero, re-probe. [A stale feature request's cited repro may already contain the workaround — read the artifact, not the issue's snippet](wiki/learnings/1785956752688-a-stale-feature-request-s-cited-repro-may-already-.md)

A companion class: **a stale CI PR can be superseded by a mechanism nobody mentions.** Scrubbing a tracking issue, a briefing flagged a PR "Add slangpy-samples testing to Linux container workflow" as an overlap. Three layers each changed the answer: it's a PR not an issue (`.pull_request` field — `gh api .../issues/N` happily returns PRs); the `test-slangpy` job it patches no longer exists at master; and the capability it wanted already ships via a *different mechanism* (a cross-repo dispatch), verified empirically on a real `repository_dispatch` run. **"Is this PR still needed?" is not answered by its own diff** — ask whether the thing it modifies still exists *and* whether its purpose was served elsewhere (separate checks; the second gets missed). `git log -S'<token>' -- <path>` is the cheapest supersession finder (lands on the removing commit, whose message usually states the replacement). Staleness needs a number (`compare/<base>...<master>` → `ahead_by`), not an adjective. Scope a "zero" to the file you grepped. And a descendant claim is a causal claim — test it by grepping the candidate for a link back, with a control. [A stale CI PR can be superseded by a mechanism nobody mentions - check whether the job it patches still exists](wiki/learnings/1785958668867-a-stale-ci-pr-can-be-superseded-by-a-mechanism-nob.md)

## Measuring a perf regression: official release binaries and the three-platform trap

For "did this perf regression get fixed?", `tools/compile-perf/fetch_releases.py` fetches official release binaries for your platform (~1 min/release vs a 20-min build, same binary CLASS the maintainer's tables used) — `--repo` is required in-container, and the API asset endpoint works where `/releases/download/` is proxy-blocked. Find the fix boundary with `git tag --contains <merge-sha>` (pair with a bogus SHA that errors loudly, so a silent 0 is impossible). **The trap: three different platforms are in play** (issue tables macOS-arm64, container Linux-x86_64, tracked suite Windows-x64) — so absolute wall-clock is NOT comparable; report the per-level scaling exponent / within-machine version delta. One regression reproduced on Linux at ~34× while a second from the same issue showed *no step at all* with a byte-identical shader and a harness proven to detect the first — a genuine platform-specific effect, and the strongest argument FOR tracking the shape; **never publish a cross-platform null as "your regression isn't real."** Harness bugs that make a null look like a finding: a locally-built slangc may not run the default `-target spirv` path (missing downstream lib → exit 255, no artifact); check the exit status of *every* iteration and require a non-empty artifact (a missing binary gives 127 in ~0.002s, reading as a spectacular result); piping to `head` masks the exit status; and never time anything while a build runs (an 8-core build inflated one cell 2.4× and made a ladder non-monotonic, looking exactly like a real finding). [Measure a Slang perf regression with official release binaries, not a local build — plus the three-platform trap](wiki/learnings/1785930383942-measure-a-slang-perf-regression-with-official-rele.md)
