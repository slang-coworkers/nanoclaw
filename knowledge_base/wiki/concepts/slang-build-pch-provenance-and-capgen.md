# Slang Build — PCH/FIDDLE Traps, Binary Provenance, and the Capability Generator

## TL;DR

- Stale GCC PCH snapshots FIDDLE macro state → ~400 bogus codegen errors that *look* like FIDDLE codegen bugs — the tell is a diagnostic `#include` chain starting `<command-line>` → `cmake_pch.hxx`. Workaround: delete the `.gch` and rebuild, or configure `-DSLANG_ENABLE_PCH=OFF`.
- The signature also reproduces in **clean GCC Release** builds — a *newly generated* PCH can be internally inconsistent in a highly-parallel clean build; "leftover .gch" is not the whole story.
- `SKIP_PRECOMPILE_HEADERS ON` is a **per-TU** property (compile that whole `.cpp` without the PCH) — it does NOT remove a particular header from the PCH content. Restate a CMake mechanism against the maintainer's mental model before shipping.
- The merged #12227 fix (PR #12233) is compiler-scoped PCH-header exclusion: keep FIDDLE-carrying `slang-compiler.h` out of the **GCC** PCH for *all* TUs, while MSVC/Clang keep the full PCH — strictly better-layered than a per-TU allowlist.
- Binary provenance: the core modules are compiled into `slangc`/`slang-bootstrap` at build time, so a **stale prebuilt `slangc` embeds the OLD core module** — a deterministic `tests/spirv` name/prefix mismatch whose emit-source diff vs master is empty is a provenance smell, not a regression.
- `slang-capability-generator`: EVERY non-`Abstract` `_`-prefixed atom (including `_*_latest`, no `alias` exemption) MUST have a matching public pair or the generator errors 20007 (only on clean regen → Windows-Release MSB8066).
- The generator **emits error diagnostics but returns exit 0** and writes output files before any error check (#12212) — key the fix on `getErrorCount()`, and verify tool-exit-code claims against source (and a run of the prebuilt binary), not DeepWiki.
- Companion page [[wiki/concepts/slang-build-cmake-packaging-and-generators.md]] covers CMake packaging, generator-target exclusion, `SLANG_USE_SYSTEM_*`, and WASM/npm packaging. Prior companion [[wiki/concepts/slang-misc-build-infrastructure-and-tooling.md]] covers CMake options, compiler flags, and downstream-compiler discovery.

This page collects the precompiled-header, binary-provenance, and capability-generator build traps: how a GCC `.gch` bakes in transient FIDDLE preprocessor state and misdiagnoses, what `SKIP_PRECOMPILE_HEADERS` actually does (and the merged #12227 fix), why a stale prebuilt `slangc` produces false `tests/spirv` failures, and the two coupled `slang-capability-generator` bugs (alias-pairing invariant + silent exit-0).

## Stale GCC PCH Snapshots FIDDLE Macro State → Bogus Codegen Errors; and What SKIP_PRECOMPILE_HEADERS Actually Does (2026-07-25 fold)

On GCC/Linux **Debug incremental** builds (Ninja Multi-Config, `SLANG_ENABLE_PCH=ON` by default), a stale precompiled header can produce ~400 bogus compile errors that *look* like FIDDLE codegen bugs — e.g. `expected unqualified-id before 'private'` inside `slang-ir-insts.h.fiddle`, cascading into incomplete-type errors for `IRFieldAddress`/`IRMakeStruct` — even though the generated `.fiddle` output is byte-identical to a clean machine (slang#12227). **The tell:** the diagnostic `#include` chain starts `<command-line>` → `cmake_pch.hxx`. Root cause (@HEAD 5281ccc66): the PCH headers (`slang-basic.h` + `slang-compiler.h`, `source/slang/CMakeLists.txt:263-264`) transitively pull in AST headers that each `#include` a `.fiddle`, and every `.fiddle` prologue redefines `FIDDLE`/`FIDDLEX`/`FIDDLEY` + `FIDDLE_<line>` macros keyed on `__LINE__` — so a `.gch` bakes in that transient preprocessor state. The build graph can't catch a stale/inconsistent `.gch` because invalidation is mtime-based but (1) `File::writeAllTextIfChanged` skips writes for identical content (unchanged `.fiddle` keep OLD mtimes), (2) `.fiddle` are declared `BYPRODUCTS` (mtimes not up-to-date markers; driven by an unconditionally-`touch`ed `.fiddle.stamp`), and (3) the PCH's dep on `slang-fiddle-output` is **order-only** — so `-Winvalid-pch` never fires (GCC considers the `.gch` structurally valid). Workaround: `rm build/source/slang/CMakeFiles/slang-common-objects.dir/Debug/cmake_pch.hxx.gch && cmake --build --preset debug`, or configure `-DSLANG_ENABLE_PCH=OFF`. Meta: two independent bugs get conflated — how a bad `.gch` is *created* (nondeterministic, undetermined) vs. how it *persists + mis-diagnoses* (fully understood); don't overclaim the causal chain to a maintainer. Parked build-system bug / P2, assignee jkwak-work (a PCH-speed-vs-robustness values call) ([Stale GCC PCH snapshots FIDDLE macro state → bogus codegen errors (slang#12227)](../learnings/1784991435802-stale-gcc-pch-snapshots-fiddle-macro-state-bogus-c.md)).

The fix-direction review turned on a non-obvious CMake distinction that cost a round (PR #12230): triage's "Approach A" was `set_source_files_properties(<tu>.cpp PROPERTIES SKIP_PRECOMPILE_HEADERS ON)`, mirroring the existing `slang-rich-diagnostics.cpp` precedent — but `SKIP_PRECOMPILE_HEADERS ON` is a **per-translation-unit** property that makes *that whole `.cpp`* compile WITHOUT `-include cmake_pch.hxx`; it does NOT remove any particular header (the generated `.fiddle`) from the PCH content. Maintainer jkwak-work's mental model was the *different* mechanism "exclude the FIDDLE generated files from the PCH" (keep `.fiddle` includes out of the PCH root, or clean up macro state after the last FIDDLE marker) — which preserves the PCH for all TUs and fixes the root fragility. A naive per-`.fiddle` `#undef` epilogue does NOT work (codex caught this): each `.fiddle` is `#include`d near the TOP of its header and its macros are consumed LATER by that header's own `FIDDLE(...)` sites, so undef-ing at the physical end removes them before their consumers run. Lesson: when a triage hands you a CMake "approach," restate what the mechanism *actually does* (per-TU skip vs per-file exclusion vs generator-side neutralization) and match it to what the maintainer's words imply before shipping — "make a PR with approach A" can still be the wrong mechanism ([SKIP_PRECOMPILE_HEADERS is per-TU, not "exclude a header from the PCH"](../learnings/1785019137366-skip-precompile-headers-is-per-tu-not-exclude-a-he.md)).

RESOLUTION (#12227 FIXED + MERGED as PR #12233, `1e0b3a441a`, maintainer jkwak-work, 2026-07-26) confirmed two ways the triage was directionally right but incompletely scoped. **(1) The failure is NOT limited to stale `.gch` from incremental builds** — the identical signature reproduced in **clean GCC Release** builds (SlangPy PR dispatches doing `git clean -ffdx` + fresh clone + `mkdir build`), so a *newly generated* PCH can be internally-inconsistent and consumed in the same highly-parallel clean build; "leftover .gch" was not the whole story. **(2) The winning fix is compiler-scoped PCH-header exclusion, not per-TU `SKIP_PRECOMPILE_HEADERS`.** Rather than compiling the two known-bad TUs without the PCH (a bounded allowlist that must grow), jkwak's merged fix keeps the FIDDLE-carrying `slang-compiler.h` out of the **GCC** PCH for *all* TUs by construction — `slang-basic.h` stays in the PCH for everyone, `slang-compiler.h` is PCH-included only for non-GNU compilers via `"$<$<NOT:$<CXX_COMPILER_ID:GNU>>:.../slang-compiler.h>"` — so MSVC/Clang keep the full PCH while GCC keeps FIDDLE macro state out of the PCH boundary (strictly better-layered than the per-TU allowlist). Chain note: triage verdict → jkwak authorized "approach A" → fixer built draft #12230 → jkwak pushed back (per-TU ≠ file-exclusion) → clean-Release evidence reframed #12230 as mitigation-not-root-cause → jkwak shipped (b) himself (#12233), auto-closing via `Fixes #N`; the bot chain's value was confirming the diagnosis + mitigation direction, and when a maintainer implements + merges their own fix, no bot GitHub comment is needed ([RESOLVED #12227: GCC PCH snapshots FIDDLE state — fix = exclude slang-compiler.h from the GCC PCH (all-TU), not per-TU SKIP_PRECOMPILE_HEADERS](../learnings/1785072236731-resolved-12227-gcc-pch-snapshots-fiddle-state-fix-.md)).

## Binary provenance: a stale prebuilt slangc embeds the OLD core module (2026-07-27 fold)

A **deterministic** `tests/spirv/*.slang` FileCheck failure with a fixed name/prefix mismatch (e.g. `internal-spirv-asm-opname-prefix.slang` emitting `OpName %dotResult` where it expects `%__dotResult`) looks like a real master regression but is often a **stale-binary artifact**. The core modules (`hlsl.meta.slang`, `core.meta.slang`, …) are compiled into `slangc`/`slang-bootstrap` **at build time**, so a binary on disk carries whatever core-module content existed at the commit it was built from — regardless of the corrected source/test on disk. When a fix changes both a core-module `.slang` file AND a test that pins its output (here #12108 / PR #12190, commit 72985f871), running the new test against a prebuilt binary built before the fix reproduces the OLD output → the test "fails" while `git diff origin/master HEAD` on the emit sources is empty. Triage fast (read-only, no full rebuild needed to DISMISS): grep the CURRENT `*.meta.slang` for the expected string, note the binary's `-v` build tag + mtime, find the fix commit via `git log`, and `git merge-base --is-ancestor <fix> <binary-sha>` — if NO, the binary predates the fix ⇒ stale, DISMISS. Gold-standard confirm rebuilds with core-module header regen (`cmake -E touch source/slang/hlsl.meta.slang` → `generate_core_module_headers`); skipping the touch leaves the bootstrap embedding OLD source silently. Rule of thumb: a deterministic (not flaky) `tests/spirv` mismatch whose emit-source diff vs master is empty is a binary-provenance smell, not a regression — verify on a fresh rebuild before filing [tests/spirv OpName-prefix failures from stale slangc = core-module embedding, not a regression (verify binary provenance first)](../learnings/1785167795738-tests-spirv-opname-prefix-failures-from-stale-slan.md) [Stale prebuilt slangc embeds old core module — false tests/spirv failures](../learnings/1785167843971-stale-prebuilt-slangc-embeds-old-core-module-false.md).

## slang-capability-generator: Alias-Pairing Invariant and Silent Exit-0 (2026-07-24 fold)

Two coupled tooling bugs around `slang-capability-generator` (`tools/slang-capability-generator/capability-generator-main.cpp`). First, `validateInternalAtomExternalAtomPair()` requires EVERY non-`Abstract` atom whose name starts with `_` to have a matching public (`_`-stripped) atom — the check is **universal, with no exemption for `alias` atoms or for `_*_latest`** — so adding `alias _FOO = ...;` without a public `alias FOO = ...;` is a latent build break (`#12211`: `_GLSL_latest`/`_sm_latest` unpaired → error 20007 → Windows-Release MSB8066). It slips past incremental CI because the invariant only fires on a *clean* capdef regeneration (incremental builds reuse cached generated headers); precedent for public "latest" aliases is `spirv_latest`/`metallib_latest`, and the `/// [Version]` doc comment must go on the PUBLIC alias for the generated capability-atoms doc (which you must regenerate in the same PR). Takeaway: when adding any internal `_atom`, add its public pair in the same edit or confirm one exists ([capdef internal _atom aliases (incl _*_latest) MUST have a public pair or generator errors 20007](../learnings/1784890869028-capdef-internal-atom-aliases-incl-latest-must-have.md)). Second, and the *root* of why #12211's bad capdef passed CI: the generator **emits error-severity diagnostics but returns exit 0 and writes its output files before any error check** (`#12212`). `validateInternalAtomExternalAtomPair()` returns void (only diagnoses), `parseDefs()` calls it then unconditionally `return SLANG_OK`, and `main()` writes files then `return 0` — Ninja keys off process status so invalid capdefs pass the full CI matrix. Fix pattern (matching `slang-fiddle` precedent): `if (m_sink->getErrorCount()) return SLANG_FAIL;` in `parseDefs()` (so `main()`'s existing `SLANG_FAILED` guard fires and file writes never happen), keying on **error count, not "any diagnostic"** (the doc-path diagnostic is a Warning that must stay non-fatal). Method note that recurred: DeepWiki answered *incorrectly* that `main()` returns 1 on validation failure — for concrete control-flow/exit-code claims, read the actual source (and run the prebuilt binary: append an unpaired alias to a temp capdef, run the generator, `echo $?` = 0 despite 3× error 20007), don't trust DeepWiki ([slang-capability-generator exits 0 despite error diagnostics (issue #12212) + verify tool-exit claims against source not DeepWiki](../learnings/1784891885921-slang-capability-generator-exits-0-despite-error-d.md)).
