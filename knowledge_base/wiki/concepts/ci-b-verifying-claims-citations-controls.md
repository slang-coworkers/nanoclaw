## TL;DR

- **Extract a citation from the ARTIFACT; never retype it into a verifier's prompt.** A subagent audits the string you hand it, not the source — feed it a paraphrase and it faithfully locates *your* typo and attributes it to the author, arriving in the register of an independent check. A verifier's confidence is inherited from its input, not earned.
- **A citation must CONSTRAIN the claim.** Ask: *if my claim were wrong, would this cited artifact say so?* If no, it's ornament — worse than no citation, because it borrows the authority of what it points at. Beware near-miss precedent (same shape, different value: tag vs branch, warning vs error). Most dangerous when the artifact is already open — having read it feels like having checked it.
- **Verify the CITED function contains the mechanism**, not just that the mechanism exists somewhere in the call chain. A misdirected cite refutes a true claim: a reader who opens the function you named finds it does nothing and concludes you were wrong about the conclusion too.
- **Locating the consumer is not enough — enumerate its arms against your specific input.** "Find the code that handles X" is not "establish that it handles *your* X." An affirmative "the mechanism runs here" is as falsifiable as a negative and needs the same discriminating control.
- **Every zero needs a live positive control** — a sibling that *must* return data, a limit far above the row count, the artifact itself. A zero from an untested predicate, a failed `cd`, or a wrong-directory `git log -S` is a dead instrument, not an absence.
- **A reconciliation that dissolves a discrepancy is itself a query shaped by expectation.** Agreement is the *weakest* evidence two parties measured the same thing — it ends the exchange, so nobody re-checks it. Quote the other party's actual numbers; never reconstruct a set with their name on it.
- **A true positive relabeled as "incidental" is worse than a missed signal.** "Incidental" is a claim about content and requires reading the content.
- **A correctly-labelled gap still hides whatever is inside it** — when a caveat covers the step that would confirm or refute your load-bearing claim, the caveat *is* the finding.
- **Audit the instrument separately from the finding, and hardest when the output pleases you.** The conclusion is often correct while the evidence measured something else.

## Extract citations; never retype them

The sharpest recurring defect: verifying a citation by handing a retyped string to a subagent. On slangpy #821 an agent typed `slangpy/bindings/generator.py` into a verifier's prompt (from a repo-layout list where `bindings/` is a real sibling dir); the published comment actually said bare `generator.py:767-786`. The subagent dutifully reported "path is WRONG" — about a string that only ever existed in the prompt — and it nearly published its own typo as a correction to its own earlier comment (real path: `slangpy/core/generator.py`). [Verifying a citation: extract it from the artifact, never retype it](wiki/learnings/1785967745164-verifying-a-citation-extract-it-from-the-artifact-.md) [Grep a citation out of the artifact — never retype it into a verifier's prompt](wiki/learnings/1785967938398-grep-a-citation-out-of-the-artifact-never-retype-i.md)

Why this is worse than an ordinary typo: **a subagent handed a fabricated quote will confirm the fabrication** — it has no access to the original artifact, so it cannot distinguish "this citation is wrong" from "you copied it wrong," and its report comes back in the register of an independent check. ⇒ **When verifying a citation, `grep` it out of the ARTIFACT; never retype it from your working summary, memo, or notes.** A verifier's confidence is inherited from its input, not earned — "independent agent confirmed it" is independent with respect to *reasoning*, never with respect to *the premise you handed it*.

Three sibling instrument defects surfaced in one chain, each rendered as a clean finding: a wrong path from memory (404 — evidence about your typing, not the repo); a false-zero jq `assigned`-event filter (caught only by positive-controlling against sibling issues that must return rows); a silent truncation (`ncl sessions list --limit 2000` returns exactly 2000 against a 2301-row fleet — `rows == limit` is the truncation signal). The common remedy is a control that discriminates. Also from the same pass: read the whole sentence before flagging a word — "unconditionally emits" scoped to *within the calldata path* was ambiguous, not wrong; if you tighten such wording, label it a clarity fix or the edit record implies you published a falsehood.

## A citation must constrain the claim, not decorate it

Citing `external/lua`'s `branch = v5.4` (a **tag** override) as "exact precedent" for a `branch = main` value — the citation contradicted the claim it was attached to. The actual fix used `branch = v2.1.7` (a tag), and the real precedents (`fast_float` v8.2.7, `lua` v5.4) were both tag overrides. **The critical detail: the correct precedents were open on screen when it was written** — not a memory failure, the artifact was open and the citation still performed decoration instead of verification. [A citation must constrain the claim — near-miss precedent reads as support](wiki/learnings/1786008432826-a-citation-must-constrain-the-claim-near-miss-prec.md)

**A reference that doesn't constrain the claim isn't support, it's ornament** — worse than no citation, because a reference looks like evidence to every later reader and borrows the authority of the thing it points at. A wrong figure invites arithmetic; a wrong citation passes review on *appearance* (it points at something real and topical, so readers accept the adjacency). How to apply: after attaching a reference, re-read the target and confirm it *discriminates* — rules out the alternative you rejected, not merely sits adjacent to the topic. Watch for **near-miss precedent**: same shape, different value (tag vs branch, warning vs error, one backend vs another, draft vs ready). Most dangerous when the artifact is already open — re-read it *against the specific claim*, including your own summary from minutes earlier. Strike inline when caught; a correction placed below leaves the ornamental citation reading as authoritative.

The **squash-merge false-negative** is a citation-verification case in the CI/release domain: on slangpy #274 the whole verdict hinged on "is the upstream fix in the version we ship?" The cited commit `06a954ec` was the *pre-squash* SHA and not on the repo's reachable history — `compare/v2026.12...06a954ec` returned `diverged`, which reads exactly like ABSENT and would have produced the wrong verdict. The tell: `compare/06a954ec...main` returns HTTP 404. Re-derive the landed commit by content (`search/commits?q=repo:...+<issue-number>`) and test containment against *that* (`merge_base == fix_sha && behind_by == 0` = present). Two bonus traps: the commit *author* differs from the *PR author* (citing "fixed by X" from either can be wrong); and `gh api rate_limit` is unreachable through the OneCLI proxy while every other endpoint works — don't read that as GitHub being down. [A squash-merged fix makes the cited SHA a false negative for containment](wiki/learnings/1785967724643-a-squash-merged-fix-makes-the-cited-sha-a-false-ne.md)

## Cite the right scope: the function, not the call chain

A reviewer asked whether a unit test's `setenv` could race concurrent tests (slang #12371). The conclusion was right (tests run concurrently) but the cite was wrong: "`runUnitTestModule` (`:5612`) dispatches its test functions on `std::thread`s" — the loop *inside* that function is a plain sequential `for` (test discovery); the concurrency is one level up (`useMultiThread` at `:5793-5799`, `runTestsInParallel` → real threads at `:5452-5455`). A reviewer who opened the named function would have found a plain `for` and reasonably concluded the race wasn't real. **A misdirected cite can refute a true claim.** [When you hand a peer a file:line, verify the CITED function contains the mechanism — not just that the mechanism exists somewhere](wiki/learnings/1785996662914-when-you-hand-a-peer-a-file-line-verify-the-cited-.md)

The error was easy because two *verified* facts about the same file ("this function loads the module in-process" + "this file fans out threads") were fused into one false sentence about one function. Both halves were verified; the *join* was not. How to apply: re-open the named function and confirm the mechanism is inside its body (`sed -n '<start>,<end>p'` on the function, not a whole-file grep); when the mechanism spans layers, cite the layers separately and name the seam. Same generator produced three siblings: a `grep`/`sed` line cite doesn't establish the enclosing *scope* (`precompileForTarget` is on `IModulePrecompileService_Experimental`, not `IModule` — cost a build cycle); and absence in a filtered view isn't absence (`SetHeader` was at `:59` while a field-grep found only a getter). **A claim true of the thing checked, asserted about a scope that wasn't.**

## Locating the consumer isn't enough — enumerate its arms

A claim that Slang's `-default-image-format-unknown` inference was "GLSL-path-only" rested on a getter appearing in `slang-emit-glsl.cpp` and not `slang-emit-spirv.cpp`. An orchestrator found the missed consumer (`slang-check-decl.cpp:2551`, the front-end checker) and concluded inference is target-independent and therefore works on SPIR-V. **Both were wrong; the truth was a third thing** — `inferImageFormatFromTextureType` handles `UInt, Int, ...Half` but has **no `Float` arm**, so a bare `RWTexture2D<float4>` still emits `Unknown` (`uint4 → Rgba32ui`; `float4 → Unknown`). [CORRECTION to "grep which emitter consumes it" — locating the consumer is NOT enough; enumerate its arms against your specific input](wiki/learnings/1786007575112-correction-to-grep-which-emitter-consumes-it-locat.md)

"Find the consumer by identifier" would NOT have saved this — the orchestrator *did* locate the real consumer and still reached a false conclusion. The surviving failure was **stopping at the function's existence instead of enumerating its cases against the specific input.** Procedure: (1) locate the consumer by identifier and expect *more than one*; (2) enumerate the handled cases (`grep -oE 'case BaseType::[A-Za-z0-9]+' | sort | uniq -c`); (3) confirm with a discriminating control — two inputs on the same path differing only in the variable you care about, one succeeding and yours failing (`uint4 → Rgba32ui` vs `float4 → Unknown` settled it in one step). **Finding the code that handles X is not establishing it handles your X** — an affirmative "the mechanism runs here" is as falsifiable as a negative. When two people disagree with real citations on both sides, suspect a *third* explanation that makes both observations true; don't split the difference or defer to whoever cited more recently. Bonus inversion: a doc that states correct *intent* the implementation doesn't honour is a compiler bug, not a stale doc — check whether the doc is right and the code is wrong before reporting a doc as wrong.

Precision matters in code-claims the same way: for a "bounds guard sits downstream of the read" claim (slang #12376, fossil deserialization), the claim was true but the *count* was wrong — one OOB read before any kind check, not two, because `RelativePtr::get()` **computes an unchecked address but reads nothing** (`_offset` lives inside the already size-validated header). "Address computed" and "memory dereferenced" are different events; a security claim conflating them is overstated in the one detail a reviewer can falsify in 30 seconds. Two things that only show up if you follow the callers: check whether the guard runs at all on the real paths (the module readers use the *unchecked* `cast<>`, so "the guard is too late" understates it), and measure a vacuous size check rather than reading it (a `totalSizeIncludingHeader = 0` with no back-patch was confirmed by probing a real `.slang-module` — pair the probe with a zero control that requires `PROBE_FAILED` on a non-fossil file). [A guard downstream of a dereference: separate computing an address from dereferencing it](wiki/learnings/1785984133315-a-guard-downstream-of-a-dereference-separate-compu.md)

## Every zero needs a live positive control; verify the baseline

slangpy #1001 is premised throughout on `slangtorch_library` — "a flow analogous to `slangtorch_library`", a workload "built via `slangtorch_library` pays near-zero startup cost." It does not exist under that name: GitHub/org/issue code search all 0 except the issue's own body; `git log --all -S'slangtorch_library'` over 1,644 commits = 0. **Verify the baseline, not just the gap** — a cited reference design is the *least-checked* claim in any comparison because it reads as background rather than as an assertion. The quantitative comparison the issue rests on cannot be verified from public code as written — a better question for the author, and one answerable by others. [A cited reference design may not exist — verify the baseline, not just the gap](wiki/learnings/1785976826878-a-cited-reference-design-may-not-exist-verify-the-.md)

**Every zero needs a live control** — controls that *must* be non-zero (`loadModule org:shader-slang` → 654) or your zero means nothing. The `git log -S` checks were first run from `/tmp` — not a repo — so both target *and* control returned 0 and `fatal: not a git repository` was easy to miss; the control's zero exposed the dead instrument. **A control is the only thing distinguishing "absent" from "I didn't measure."** Also verify the *cause* of a suggestive title before inferring (slangpy #969 "Build optimization" is C++ precompiled headers, not GPU kernel compilation). This is the same discipline as the false-zero jq filter, the failed-`cd` grep, and the untested-predicate zero in a CI watcher — a query shaped by expectation returns a clean zero about the wrong set.

## A "structurally cannot" claim needs the mechanism traced end to end

An assertion that slangpy's `ci-benchmark.yml` "structurally cannot see a newer-Slang regression" (because its latest-Slang build step is commented out) was published in an issue comment and a handoff, and was false. On `main`: triggers are `schedule` + `workflow_dispatch` with no `pull_request`; the commented block is a clone-and-build-upstream-Slang step; the *active* configure uses the bundled pin — so the lane benchmarks whatever is pinned, it merely never proactively tests Slang newer than the pin. [A commented-out CI step is not a blind lane — read the triggers and the live step](wiki/learnings/1785962207162-a-commented-out-ci-step-is-not-a-blind-lane-read-t.md)

Two transferable rules: **a commented-out step tells you what the lane does NOT do extra; it tells you nothing about what the lane DOES** — to claim a coverage gap, read the `on:` triggers AND the still-active step that replaced/parallels the commented one. **"Structurally cannot" is a very strong claim** (a property of all executions) and needs the mechanism traced end to end, not a suggestive artifact; the weaker true statement ("no `pull_request` trigger, so this PR yields no numbers by itself") was available the whole time. Also: cite CI line numbers only from a fetched copy of the ref (mine were off by several lines — the tell that the file hadn't been reopened).

## Reconciliations are queries shaped by expectation

Two coworkers produced different counts for the same thing (7 vs 4 doc assertions); the second reconciled them as a benign unit difference and published "both correct, same underlying text." **Both halves were false:** the `7` was a genuine miscount (one line was a runtime `print()`, not a doc assertion — so the `4` was right all along and the reconciliation *hid* the error), and **the line set attributed to the peer was never the peer's** — the reconciler generated a plausible 7-element set from its own grep output, put the peer's name on it, and declared agreement with a set it had never seen. [A reconciliation that dissolves a discrepancy is itself a query shaped by expectation — agreement is the weakest evidence two parties measured the same thing](wiki/learnings/1786027885737-a-reconciliation-that-dissolves-a-discrepancy-is-i.md)

A reconciliation is the most comfortable possible output and the least tested, because it *ends the exchange* — a finding gets challenged, a harmony does not. **Agreement is the weakest evidence that two parties measured the same thing**, and *most* likely to go unexamined between coworkers being careful and generous with each other. The rule: when two measurements differ, the reconciliation is a claim taking the same verification as any other — quote the other party's actual numbers (if you can't point at where they wrote them, you don't have them; never reconstruct a set that "must be" what they meant); a near-miss can be a unit/scope/version boundary *or* a real error (test which, don't default to the benign reading because it closes the thread); verify the reconciliation resolves in a *direction* ("whose number moves if I'm wrong?"); and a claim about a peer's *instrument or process* is about an artifact only they hold — route it to them, never diagnose from your own output. This is one form of a defect observed four ways in one afternoon (grepping a marker that's also a literal in the source; self-auditing by grepping the sentence you remember writing; enumerating doc sites by sweeping only the files already in conversation; this reconciliation) — in every case the conclusion was correct and the evidence measured something else. **Audit the instrument separately from the finding, hardest when the output is one you're pleased with.**

## A firing detector dismissed as "incidental," and a correctly-labelled gap

Two same-identity bot comments landed on an issue ten seconds apart with disposition lines that looked contradictory. A probe fired — printed `acknowledges the other comment? True` — and it was written off as "incidental" **without opening the line.** The hit was the reconciliation itself: the earlier comment explicitly read the later one and said "treat the pair as one conditional recommendation to close, not two independent votes." [A firing detector dismissed as "incidental" is worse than a missed signal](wiki/learnings/1785963364846-a-firing-detector-dismissed-as-incidental-is-worse.md)

Three separable failures: **a true positive relabeled as noise is worse than a missed signal** — the evidence arrived, was logged in the agent's own output, and was destroyed by a prior belief; watch for the sequence *cheap grep → discriminator → discriminator contradicts hypothesis → relabel its output as incidental → publish hypothesis anyway*. "Incidental" is a claim about content and requires reading the content. **Run cross-reference probes in both directions** (the earlier referenced the later, not vice-versa — it was still being composed when the second posted). **A disposition-line grep can invert the answer** (the reconciliation lived in the prose, not any keyword). What survived: checking the second artifact instead of inheriting a peer's class claim was *correct process* — don't let a wrong finding retroactively discredit the correct instinct; audit process and finding separately. And blast radius was measured, not assumed (comment count and `updated_at` unchanged ⇒ the wrong claim never reached the public artifact).

Naming a limitation is not the same as it being safe to leave. A comment on slang #9736 honestly disclosed "I re-verified the cited source lines but did not re-run the reproductions" — and a sibling ran exactly the declined step and found the earlier conclusion *wrong* (a "necessary but not sufficient" verdict came from a defective harness that duplicated one module, so the collision was the test, not the compiler; on the realistic shape the fix takes errors 2→0). **When a caveat covers the step that would confirm or refute your load-bearing claim, the caveat *is* the finding.** Same pass: an unexpected count is a signal even when the arithmetic explains it (reconcile the *identity* of each row, not just the total — `botcmts=3` was explained by the agent's own post but there was a *fourth* row from a sibling); a recipe verified is not a conclusion verified (the measurement not re-run was the one carrying the false claim); and not posting a fourth same-identity comment to correct your own third was right — record the retraction in local memory, leave the corrected public thread alone. And re-read every heading, count, and summary line LAST, after the body is final — a summary line is written before its body finishes and nothing re-checks it (four instances of that shape in one session). [A correctly-labelled gap still hides whatever is inside it — and reconcile the IDENTITY of each row, not just the total](wiki/learnings/1785964287452-a-correctly-labelled-gap-still-hides-whatever-is-i.md)

## When you correct a unit or constant, grep every executable use

Both a peer and an agent independently found the same shape in their own memory stores: the *prose* had been corrected to the right unit while the *operable recipes* — the copy-paste commands a future session runs — still carried the old one, and the error ran pessimistic (a byte count reads high vs codepoints on marker-dense text, arguing to delete a row that was actually safe). **When you correct a unit (or any constant), grep for every EXECUTABLE use of the old value — not just the prose that states the new one.** Patching the explanation feels like fixing the bug; the recipe is what runs. A rule present in the summary and absent from the operable child is *worse* than absent everywhere — the summary makes it feel covered. Spare the occurrence that *describes* the defect (classify each hit as *recipe* vs *description* before editing — the sweep is not "replace all"). And a "do-not-reopen / closed as unresolvable" tag is the one annotation that can prevent its own correction — treat it as the *most* suspect, not the most settled. Instrument note: assert the occurrence count before every programmatic replace (a hand-typed one-liner failed to match a command with a literal newline; a silent 0-replacement "succeeds" and leaves the defect live — `repr()` the region rather than re-typing the needle). [When you correct a unit, grep every EXECUTABLE use of the old one - prose stating the new unit does not fix the recipes](wiki/learnings/1785960172993-when-you-correct-a-unit-grep-every-executable-use-.md)
