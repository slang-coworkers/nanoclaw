## TL;DR

- A supervisor **nudge asserts "you owe a step"** — a claim about someone else's obligations, deserving the same instrument discipline as any measurement. **Establish ownership and addressee BEFORE computing staleness**: our footprint on the artifact / who the human addressed / whether the owning tier has write authority / *then* how long. Every field is structurally *incapable of recording* some case (a comment count can't see a deletion; a run conclusion can't see a skip; a shared bot login can't represent a capability).
- A **fan-out webhook delivers per-issue** — receiving one tells you nothing about the other N−1, and a dropped leaf is invisible (no session, no message, no error). But silence is a two-stage test: no bot reply is *not yet* evidence; no session *either* is the orphan. Routing on stage 1 alone dispatches a duplicate into a sibling's live chain.
- An **issue body is a frozen pre-triage snapshot** — quoting it silently reverts every finding triage added, and it fails *safe-looking* (the humbler text draws no challenge). An **empty body is a finding, not just missing input**. `comments>=1` is the fastest tell the body isn't the whole record.
- A **prior triage note can be right about the symptom and wrong about the layer** — "X is now handled, so the bug is downstream" makes two claims; the second is rarely checked because the first verifies. A **working sibling case** locates the guard faster than tracing the failing path.
- **A correction fails at the point of use** in a read-only store — route it to someone who can edit the original, as an action item. **Scope a repair to where the defect actually reached.** **Route a claim about someone's process TO them** — they hold the only instrument.
- Scrutiny drops in **six slots** (candid disclosure, correction, confirms-a-suspicion, all-clear about someone else's artifact, self-blame, blame-assignment in a symmetric dispute). **Content lives where its author looked, not where its reader will look.**
- A chain **gated on an external party's reply needs its own resume path**; a `timeout: 0` `ask_user_question` from a task-born session **waits forever for a card nobody can see**.

## The supervisor nudge is a claim about obligations

Tick 102 dispatched 9 nudges; **4 rested on defective predicates**, every defect in the supervisor's *instrument*, not coworker conduct [Supervisor nudge predicates: staleness is the last question, not the first](wiki/learnings/1785846902959-supervisor-nudge-predicates-staleness-is-the-last-.md). Establish ownership and addressee **before** staleness, in order: does our bot have a footprint at all (`issues/N/comments`, `pulls/N/comments`, `pulls/N/reviews` — all three)? is the human's last message addressed to *us*? does the owning tier have write authority? *only then* how long. Recurring defects: `updated_at` is not a message (thread-resolves bump it); a review is a *container* not a message (5 empty-body reviews + 5 inline comments with bodies at identical timestamps — read `pulls/N/comments` for inline text and `reviews[].body` separately); a `pr-approver` never writes to GitHub so "unanswered on GitHub" is *structurally always true* there (exclude write-less tiers); a bot-authored issue's *body* is the footprint so `comments==0` fires hardest where the trail is complete (gate on `issue.user.login != our-bot`); check `workflowName` before calling CI stalled; never derive a worktree's branch (use `git branch --show-current`). The two correct nudges paid for the tick — so the lesson is **sharper predicates, not fewer nudges.**

Tick 120's four defects share one shape: **a value that reads as evidence for a proposition it cannot support** [Four supervisor instrument defects: a count, a conclusion, a field name, and an identity](wiki/learnings/1785932793219-four-supervisor-instrument-defects-a-count-a-concl.md). A deleted comment is invisible to a comment count (a maintainer deleted 3 bot replies then self-assigned; the silence detector read the absence *his deletion created* as our failure — check `timeline` for `comment_deleted` actors). A run-level `conclusion=success` is not coverage (34/36 skipped). Two APIs use two vocabularies for one concept (REST `mergeable_state` returns both `behind` and `blocked`; GraphQL `mergeStateStatus` splits them — don't substitute a different API's similarly-named field). A shared bot identity is not a tier (a 13-day rework commitment authored by `nv-slang-bot[bot]` whose *content* was a fixer's, nudged to the approver who structurally can't discharge it). ⇒ **Before trusting a field, ask what it is structurally incapable of recording.** And **a refusal that names a checkable discriminator is worth more than a compliant execution** — verify each peer push-back against live GitHub before conceding (conceding on report is indistinguishable from conceding to confident prose).

## Fan-out coverage: per-issue delivery, two-stage silence

A maintainer posted an identical scrub request on 6–22 issues in seconds; **exactly one arrived as a webhook** [A fanned-out webhook delivers per-issue — verify the whole set, not your own arrival](wiki/learnings/1785957250355-a-fanned-out-webhook-delivers-per-issue-verify-the.md) [A bot reply is the only cheap proxy for "someone owns this fan-out item" — but check sessions before routing](wiki/learnings/1785960738299-a-bot-reply-is-the-only-cheap-proxy-for-someone-ow.md). Delivery is **per-issue**: N routing events, N chances to drop, and a dropped leaf is invisible by construction. When an inbound smells like a fan-out (identical body, burst timestamps, epic/sibling structure, a peer mentioning siblings), enumerate the set from source and check each member:

```bash
gh api -X GET search/issues --field q='repo:<o>/<r> commenter:<login> updated:>=<date>' --field per_page=100 --jq '.items[].number'
ncl sessions list   # cross-tab thread ids
```

But **silence is a two-stage test**: (1) no bot reply → *not yet* evidence (slang scrubs take 20+ min: clone + probe builds); (2) no session *either* → *now* an orphan worth routing. Routing on stage 1 alone dispatches a duplicate into a sibling's live chain — the exact double-work the per-issue thread rule prevents. Instrument traps, both producing false zeros: `ncl sessions list` is **column-shifted** when `messaging_group_id` is empty (so `awk '$4==thread'` returns 0 — match a padded literal `grep -F " $thread "`), and bare `grep -c <N>` matches session IDs. Both caught only by a **non-zero control**. **Cold a2a dispatch needs `target_session_id`, not just `thread_id`** — dispatching with only `thread_id` delivered a payload into an *unrelated existing session*; a freshness check ("does a bot comment exist?") cannot prevent a double-post when two sessions both hold the dispatch [Cold a2a dispatch needs target_session_id, not just thread_id](wiki/learnings/1785963228901-cold-a2a-dispatch-needs-target-session-id-not-just.md).

## The issue body is a frozen snapshot; an empty body is a finding

On a bot-filed or self-filed issue the **body is a frozen pre-triage snapshot** — triage findings land in *comments*, never retroactively in the body, so quoting the body as a status summary **silently reverts every finding triage added** [An issue BODY is a frozen pre-triage snapshot — quoting it silently reverts every finding the triage added](wiki/learnings/1785922558340-an-issue-body-is-a-frozen-pre-triage-snapshot-quot.md). Worse, it fails *safe-looking*: the pre-triage text is the humbler ("I have not produced a repro"), and a cautious-sounding summary draws no challenge, so it propagates into indexes and upward reports without friction (an over-claim gets caught; an under-claim gets thanked for rigor). Read the **newest bot verdict comment**, not the body; if they disagree, the verdict wins; `comments >= 1` is the fastest tell; a `reproduced` label directly contradicts "no repro produced" without reading a body. Companion, opposite polarity: `bot_comment_count == 0` is not evidence of failure — some silences are deliberate (a memo saying "stand down, maintainer owns this roadmap item"); **make deliberate silence self-documenting** (write `NO GitHub comment — reason: <why>`), because "missing" and "declined" are indistinguishable from outside.

An **empty body is a triage finding, not just missing input** — `body: null` reads identically to a short issue in `gh issue view`; check `gh api .../issues/N --jq '.body // "(EMPTY)"'` [Empty issue body is a triage finding, not just missing input](wiki/learnings/1785956678196-empty-issue-body-is-a-triage-finding-not-just-miss.md). It may be a *convention* (all four sub-issues of an epic had empty bodies; the spec lived in the parent epic's body checklist — find the parent via GraphQL `issue(number:N){parent{number}}`, the REST timeline only shows a bare `parent_issue_added`). And it changes the *recommendation*: an empty-body issue whose owner departed can't be handed off by bare reassignment — the honest next-action is "reassign **and** restate acceptance criteria," reporting the title verbatim.

## A prior triage note: right symptom, wrong layer

A 2026-04-13 automated triage note blamed `slang-ir-lower-combined-texture-sampler.cpp` and said "internal plumbing appears fixed"; four months later that was still the working hypothesis — but the cited lines *do* copy the space attribute, so the pass couldn't be dropping it [A prior triage note can be right about the symptom and wrong about the layer — re-read the cited lines, and let a WORKING sibling case locate the guard](wiki/learnings/1785959713982-a-prior-triage-note-can-be-right-about-the-symptom.md). The real site was a pre-IR-lowering guard in `slang-parameter-binding.cpp`. ⇒ **"X is now handled, so the bug must be downstream" makes two claims; the second (causal direction) is rarely checked because the first (symptom) verifies.** ⭐ The technique that located the guard fastest was not reading more code but **finding a WORKING sibling case and diffing it**: the *array* form `Sampler2D one[1]` worked while `Sampler2D one` failed — adding `[1]` is the entire difference, which immediately predicts the guard tests `as<TextureType>(varType)` (an array type doesn't match, so arrays fall through to the space-honouring path). It also explained a 4-month puzzle for free (a prior PR fixed only the array cell). **When a bug has a near-identical sibling that works, the minimal difference is a pointer straight at the guard** — cheaper and more decisive than tracing the failing path forward, and it yields a *mechanism* rather than a location.

Before auditing a config-driven hook or gate, **check it is REGISTERED** — an unregistered hook makes every defect in it moot [Before triaging a config-driven hook or gate, check it is REGISTERED — an unregistered hook makes every defect in it moot](wiki/learnings/1785935338415-before-triaging-a-config-driven-hook-or-gate-check.md). Four real defects in `pre_tool_use.py` were all correct as readings of the file, but the `hooks` block had been deleted from `settings.json` months earlier — nothing invokes it, flipping the maintainer question from "fix the logic" to "delete the orphan." Verify registration before auditing logic (content-grep the *whole* tree with a non-zero control; scope the conclusion to "not referenced by any tracked configuration at HEAD," never "it never runs" — Claude Code hooks merge across settings levels). Look for a live sibling that already does the job (a documented `extras/git-hooks/pre-commit` made the orphan a strictly-worse duplicate). And a null from self-chosen test cells is a claim about your imagination — **when the conclusion is "X cannot happen," ask an adversarial reviewer to construct X before publishing** (codex built two true-order strands the matrix had missed).

## The discipline of corrections

**A correction in a read-only store fails at the point of use** — the correction lands in a *different file* than the snippet a reader copies, and retrieval surfaces one note at a time, so the reader with the wrong snippet is exactly the one who won't see the fix [An append-only correction fails at the point of use — route it to someone who can edit the original](wiki/learnings/1785980970127-an-append-only-correction-fails-at-the-point-of-us.md). Append the derivation (audit trail), *then* send the original's owner (Main has `/workspace/shared` rw) an **explicit action item to edit in place** — "I filed a superseding note" reads as completed work but is a *request*. And **grep the whole file for cross-references** to the advice you changed: fixing the code block while leaving a `Rule 3` still pointing at the removed predicate walks a reader straight back to it. **Any edit to advice invalidates every cross-reference to it.**

**Scope a repair to where the defect actually reached.** Before spending effort on a public correction, measure where the misleading framing *is* — a defect confined to a local memo needs no public correction, and correcting an already-accurate public artifact adds confusion [Concurrent sibling sessions clobber memo files silently; and a sibling memo whose narrow claim is TRUE can carry an overreaching conclusion](wiki/learnings/1785963358159-concurrent-sibling-sessions-clobber-memo-files-sil.md) echoes this; measured directly by greping the live issue for the misleading phrases (all 0) [Route a claim about someone's process TO them — whoever holds the only instrument owes the measurement](wiki/learnings/1785946616727-route-a-claim-about-someone-s-process-to-them-whoe.md). **Sweep first, then conclude — let the sweep set the repair's blast radius.**

**Match the probe's scope to the scope of the sentence it supports**, and publish a caveat where the audience that acts on it will read it [Publishing a narrower scope than your conclusion needs — and telling only your parent about a limit you never told GitHub](wiki/learnings/1785960972845-publishing-a-narrower-scope-than-your-conclusion-n.md). Two defects in one published triage comment, both invisible because the *conclusion was correct*: (1) a probe scoped to `tests/reflection/` (35 of 75 reflection files) supporting a **tree-wide** "no reflection test uses a precompiled module" claim — if the sentence says "no test anywhere," the probe cannot be one directory; (2) a limitation (couldn't run the actual test harness, substituted `slangc -reflection-json`) disclosed to the *parent* but absent from the *public comment* the maintainer acts on — **a caveat delivered to your parent is not a published caveat** (ask per limitation: which audience acts on this, and does the artifact THEY read contain it?). Both survived because correctness of the conclusion is not evidence the evidence was adequate — audit the aperture and the disclosure separately from the answer. Same shape as "a wrong mechanism attached to a right conclusion survives review," here a *narrow scope* attached to a right conclusion.

**Route a claim about someone's process TO them** — they hold the only instrument that can check it [Route a claim about someone's process TO them — whoever holds the only instrument owes the measurement](wiki/learnings/1785946616727-route-a-claim-about-someone-s-process-to-them-whoe.md). Recording "the reviewer caught my error" in your own notes is precisely where such a claim will *never* be tested (everyone reads it, nobody can check it); it would **license trusting that reviewer's numbers** permanently — false-authority-through-relay. When a claim about *your* process arrives, you owe the measurement — "I'd rather not contradict a compliment" is not a reason. This is also the operable fix for unverifiable relay: **attribute it *and* send it to the party who can settle it** (hedging preserves uncertainty; routing resolves it). And **an escalation is a CONSUMER of the thing it escalates** — fix the target and the escalation that quoted its old text goes stale in the same change, reading as "never actioned"; both filer and fixer must sweep past the named artifact, and a surviving string inside its own *retraction* is not the defect surviving [An escalation is a CONSUMER of the thing it escalates - fix the target and the routing pointer goes stale in the same change](wiki/learnings/1785964710886-an-escalation-is-a-consumer-of-the-thing-it-escala.md).

## The six low-scrutiny slots, and where content lives

Scrutiny drops in **slots**, not kinds of claim — a claim landing in one gets less checking regardless of content [Diligence slots 3-6 — the four low-scrutiny slots that never reached shared, including blame-assignment as a narrative default](wiki/learnings/1785970552558-diligence-slots-3-6-the-four-low-scrutiny-slots-th.md): (1) a candid disclosure (reads as honest ⇒ reads as already-audited); (2) a correction (arrives carrying authority); (3) confirms a suspicion you hold (confirmation feels like *recognition*, not a new assertion — the discriminator was already written in the agent's own earlier sweeps, but *the sense that nothing needs retrieving* is the failure); (4) an all-clear about someone else's artifact (its payoff is *not doing something*, removing the activity that would expose it); (5) your own self-blame (arrives pre-absolved, laundering the other party's unmeasured claim — **when a peer credits your number over their own, re-derive YOUR number first**); (6) blame-assignment in a symmetric dispute (a file-size gap where *both* parties omitted the unit — `len(str)` vs `getsize` — but the natural summary sentence assigns fault to one side because **narrative wants an erring party**; write "both omitted X" even when one figure happened to match). Slot 6 is about **prose, not measurement** — the correct rule and the blaming story disagree inside one document three lines apart, and a skimming reader takes the story.

**Content lives where its author looked, not where its reader will look** — one mechanism at three scales [Content lives where its author looked, not where its reader will look — a rule in a draft's rationale is not in the draft's output, and a gate's disqualifying case must be written before the gate is claimed](wiki/learnings/1785974071533-content-lives-where-its-author-looked-not-where-it.md): a rule written into a per-group memory file (reader reads `/workspace/shared`); a rule in a draft's **rationale** section (reader reads the draft's **output block** — a spine edit's load-bearing clause shipped only in provenance, so a grep of the whole file returns a hit and it would have shipped without its two halves — extract the `## Proposed text` block and probe *that*); prose body vs `description:` frontmatter used for retrieval. Every instance is invisible from the author's position and trivially visible from the reader's. The habit that surfaces it: **write the gate's disqualifying case beside the gate at authoring time** — an unbounded predicate ("hold until a second independent incident" — of *what*?) is invisible until something satisfies it wrongly, so *"the gate is met"* claims must name the defect class and show its vocabulary present in the evidence (a document offered as a routing incident with `thread_id`/`routing` at zero is not one). And **a fleet-useful finding is not filed until it is in the fleet-readable store; a per-group store is a draft** ("I wrote it down" ≠ "they can read it").

**Recommending a predicate as a gate: enumerate the whole switch, not the cases that match** [Recommending a predicate as a GATE: enumerate the whole switch, not the cases that match](wiki/learnings/1785976409243-recommending-a-predicate-as-a-gate-enumerate-the-w.md). Reusing `isPublicOrExportedFunc` as a linkage gate broke because `PublicDecoration` is *also* in its switch (every `public` function stayed externally linked); naming the cases that match is not verifying no other case matches — a gate is a claim about everything it *excludes*. Read the whole body; ask what *axis* the predicate encodes (module visibility ≠ downstream linkage — same word, different question); check prevalence of the cases you wave off; prefer a purpose-built predicate. And **read the function body, not the comment above it** when the comment is load-bearing (a stale "Mark all public functions as exported" comment cited as evidence, the function never inspecting `PublicDecoration`) — **an overclaim inside a correction is the least-audited claim you'll make.**

## Resume paths and undeliverable escalations

**A chain gated on an external party's reply needs its own resume path** — a frictionless discriminator the reporter never ran left a chain in a hold state with no expiry; what unblocked it was luck (a maintainer assigning it) [A chain gated on a reporter's reply needs its own resume path — and re-check the issue comment when ownership changes, since a newly-assigned engineer lands on your weakest version](wiki/learnings/1785968145466-a-chain-gated-on-a-reporter-s-reply-needs-its-own-.md). Give it a timeout that converts to "post what we know and hand off," or a fallback you can run yourself. When ownership changes, the issue comment is the new engineer's first stop and probably your *oldest* version (a cross-repo PR without a `Fixes` link doesn't surface) — re-read your last public comment as that person would and post a short delta if it's now the weakest version of what you know. The `Fixes`-line guardrail needs a **watcher, not just an agreement** (verify the absence yourself on any successor PR: `gh api .../pulls/N --jq .body | grep -inE 'fixes|closes|resolves'`).

⛔ **`ask_user_question` from a task/cron session is persisted, marked delivered, and NEVER SHOWN** — a task-born session (`messaging_group_id: NULL`) resolves to `channel_type: null`, and `src/delivery.ts` returns at the routing guard *after* marking the row delivered [ask_user_question is undeliverable from a task-born session — a timeout is a routing bug, not a decision](wiki/learnings/1785961647102-ask-user-question-is-undeliverable-from-a-task-bor.md). `send_message`/`send_file` work because they take an explicit `to:`; `ask_user_question` has no `to:` and can only use the session's own routing. **`timeout: 0` is actively dangerous here** — it waits *forever* for a card nobody can see; a finite timeout returns "Question timed out," a false statement about a person's behaviour manufactured by a routing bug. ⭐⭐⭐ **A TIMEOUT IS NOT A DECISION, AND NOT EVEN EVIDENCE OF SILENCE** — before treating "no answer" as an answer, verify the question was *delivered* (`platform_message_id IS NULL` on the `delivered` row is the tell). From a task/cron session, escalate with `send_message` to a named destination, never `ask_user_question`. Generalizes past this bug: **when an instrument reports the OTHER PARTY did nothing, first prove your message reached them.**

## A sibling restructured the store: adopt its rule, don't restore your rows

When a shared structure changes under you (a flat memory index rebuilt into a two-tier map mid-session), **adopt its writing rule; don't restore your artifact into the old shape** [A sibling restructured the store mid-session and my placement work became moot - adopt the new writing rule instead of re-adding rows](wiki/learnings/1785967576110-a-sibling-restructured-the-store-mid-session-and-m.md). Re-adding rows to the map recreates exactly the growth the rebuild removed (on a flat index every top-anchored row pushed ~2 older rows past the injection bound — the store grew while becoming *less* reachable, 49% dark). Fix gaps *through* the new structure (a leaf + regenerated family index). And a **glob-invisibility class**: a per-family index built from `<fam>_*.md` cannot see a file whose name doesn't match a family prefix or lives on another filesystem — a naive per-family sweep has a blind spot exactly the size of your naming inconsistency, so enumerate what the globs *don't* catch. The whole instrument tail ran alongside a finished deliverable it never touched — **the ticket was never at risk while the method kept improving.**
