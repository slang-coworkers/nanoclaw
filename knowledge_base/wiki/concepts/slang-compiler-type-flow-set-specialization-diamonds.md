# Slang Compiler: Type-Flow Set-Specialization Diamonds (E33180) and analyzeCall Callee Lifetime

This page covers how the dynamic-dispatch type-flow pass (`slang-ir-typeflow-specialize.cpp` together with the translation context in `slang-ir-translate.cpp`) lowers a generic whose arguments are type or witness-table *sets*, why a "diamond" of call sites to one such generic produced a spurious E33180, a lifetime trap for the `callee` captured in `analyzeCall`, and the specialize-pass facts and adjacent bugs found while reworking PR #13387's per-conformance extension methods. The ExtractExistential crash family, dispatcher inlining, and the #13169 fixpoint hang are on [Slang Compiler: Type-Flow ExtractExistential, Gate-Relaxation Discipline](slang-compiler-type-flow-and-gate-discipline.md).

## TL;DR

- **A set-specialized generic is a `specialize(g, UntaggedUnion, WitnessTableSet)` that `specializeGenericWithSetArgs` lowers to a new function with set-tag parameters prepended.** Each call site must then pass the tags; `specializeCall` adds them only when the callee still resolves to the unlowered `Specialize`.
- **The #13817 diamond: one set-specialized callee reached both directly and from inside another set-specialized generic** (`mid(b)+leaf(b)`, where `mid<T>` calls `leaf<T>`) gave a false E33180 or an `index < getParamCount()` assert. Sibling shapes (`mid+mid2`, `leaf+leaf`, `mid+top`) pass.
- **Root cause (PR #13820): `_resolveInstRec` looked up the translation dictionary before its `isSetSpecializedGeneric` guard.** The hash-consed `Specialize` was memoized to the already-lowered function, so a later round skipped tag insertion. Fix: return a set-specialized `Specialize` unresolved before the dictionary lookup.
- **The failure is order-dependent:** it fires only when a direct call is lowered before the inner call inside the other set-specialized generic is analyzed.
- **`isSetSpecializedGeneric` accepts only generics whose return value is a `Func`.** A set-specialized witness-table generic (`Target<T> : ITarget` over a set) used as another generic's witness argument segfaults in `analyzeCall` (separate, open).
- **#13820 is still open (2026-10-24), and the diamond also fires with plain generics and with #13387's nested extension methods** when a direct call and a generic caller share identical specialization arguments. In legacy mode an E33180 can only come from `maybeSpecializeGeneric`'s null-result fallback or typeflow's escaped-`IRSpecialize` branch.
- **When you build a trigger matrix for a type-flow bug, vary the call-site topology** (direct vs nested, same vs different callee), not only the types.
- **`translationContext.resolveInst(callee)` can `removeAndDeallocate` the callee.** A module-scope `LookupWitnessMethod` on a concrete table goes through `specializeWitnessLookup`. Afterwards `callee->getParent()` is null and `isGlobalInst(callee)` segfaults; `getOp()` only seems to work because the IR arena never frees memory.
- **Review rule:** code that inspects the captured `callee` after a resolve must move before the resolve, or use the resolved value.
- **Witness-table entries from `lowerWitnessEntryValue` have a null type**, so `cast<IRFuncType>(entry->getDataType())` on a resolved entry can be null.
- **`CompilerDictionaryValue` operands are weak references**, so DCE can collect an intermediate inner generic between specialize rounds; re-specializing it later builds a duplicate function, and its `static` locals split.
- **Typeflow's no-context `specializeGeneric(inst)` builds a fresh `SpecializationContext`**: keep cross-call facts in IR decorations, not in context state.
- **Nested generics with set arguments crash with E99997 "unexpected set kind"** in `maybeSpecializeWitnessLookup`; flatten the inner generic before typeflow.
- **`removeUnusedGenericParam` can merge empty struct specializations into one IR type with distinct witness tables**, so witness pairing by `getConcreteType()` must tolerate duplicate types.
- **#13387 review: `static` locals still split with only one conformer**; a removed `-warnings-as-errors` can hide a fallback-path pass, so ask for a Slang 2025 variant.
- Debugging: `-dump-ir` stdout is lost on a segfault (use `SLANG_DEBUG_IR_BREAK=<debugUID>` for the creation stack; UIDs shift between instrumented and plain builds); with no gdb, an LD_PRELOAD SIGSEGV handler plus `addr2line` on the `.dwarf` file gives symbolized frames.
- Test-authoring traps: `X-NOT: error` matches slang-test's `standard error = {` header (use `X-NOT: error[`), and slang-test ignores `//TEST_INPUT` lines in `#include`d files.

## The diamond: a direct call and a nested call share one set-specialization (#13817)

Consider two `-conformance` registrations and a value `b` of type `IMaterial.BSDF` obtained from `createDynamicObject`. The program calls `mid(b)` and `leaf(b)`, where the generic `mid<T>` itself calls `leaf<T>`. Both `leaf` call sites end up as the same set-specialization of `leaf`: one directly in the entry point, one inside the set-specialized `mid`. This gives a spurious E33180 on master 965284957 and also on v2026.13.1, so the bug is long-standing. The order of the two calls does not matter at the source level, and the neighbouring shapes `mid(b)+mid2(b)`, `leaf(b)+leaf(b)` and `mid(b)+top(b)` all compile. In the IR after `specializeModule`, the lowered `mid` still contains `call specialize(leafGeneric, UntaggedUnion, <mid's SetTag param>)` instead of `call %leaf(tag, val)`. So the failure needs both a direct call site and an inner call site that share one set-specialization. A separate bug turned up in the same matrix: a set-specialized *witness-table* generic, such as `Target<T> : ITarget` with `T` ranging over a set, used as another generic's witness argument, segfaults in `analyzeCall`, because `isSetSpecializedGeneric` accepts only generics whose return value is a `Func`. A trigger matrix that varies only the types would miss both; vary the call-site topology as well ([type-flow diamond E33180: shared set-specialized callee reached directly and from inside another set-specialized generic](../learnings/1792582835074-type-flow-diamond-e33180-shared-set-specialized-ca.md)).

The root cause (fixed in PR #13820) is a memo hit in `_resolveInstRec` (slang-ir-translate.cpp). The function consulted the translation dictionary *before* its `isSetSpecializedGeneric` guard. When the direct call site's `specialize(g, UntaggedUnion, WitnessTableSet)` is lowered by `specializeGenericWithSetArgs`, the result (a function with tag parameters prepended) is memoized. Because `Specialize` insts are hash-consed, the inner call inside `mid` uses the same inst, and a later `specializeDynamicInsts` round resolves it straight to the lowered function. `specializeCall` then sees a plain function, never adds the tag arguments, and the compile either reports E33180 at the "escaped IRSpecialize" site or asserts `index < getParamCount()` because the arguments are off by one. It fails only when the direct call is lowered before the inner call is analyzed, which is why the topology, not the source order, decides it. The fix returns a set-specialized `Specialize` unresolved before the dictionary lookup, so every call site goes through `specializeCall`'s tag insertion ([translation-dict memo hit returned a set-specialized generic's lowered func](../learnings/1792595826314-slang-type-flow-translation-dict-memo-hit-returned.md)). The same function also decides which shapes may record structural fixed points; that is the mechanism behind the #13169 non-terminating fixpoint described on the companion page.

PR #13820 is still open as of 2026-10-24, and the diamond is not specific to associated types. On master, a plain `uint count<T:IValue>(T t)` reached by one dynamic value both directly (`count(v)`) and through another generic (`outer(v)`, where `outer<U>` calls `count(u)`) gives the same false E33180 from `specializeCall`'s escaped-`IRSpecialize` branch: the direct site's set specialization is materialized and replaces the `FuncSet` element that the generic caller's site sees ([Slang: removeUnusedGenericParam merges types whose witnesses differ; FileCheck -NEXT fails on slang-test HLSL](../learnings/1792845935161-slang-removeunusedgenericparam-merges-types-whose-.md)). The per-conformance extension methods of PR #13387 hit the same shape. In legacy mode, a nested method `extension<T:IValue> T { uint count<let Step:uint>() }` reached through `uint outer<U:IValue>(U u) { return u.count<1>(); }` and directly as `v.count<1>()` fails with E33180 pointing inside `outer`, although E33180 is a Slang 2025 rule. Each call alone compiles, and so does the pair with different inner arguments (`count<2>`). The PR head 41e6e4fbe, before the fixer's patches, fails on the same program with E99997, so round-2 patch 02585b8f3 did not regress it. In legacy mode an E33180 can only come from a mode-independent site: `maybeSpecializeGeneric`'s null-result fallback or typeflow's escaped-`IRSpecialize` branch. So when a PR claims generic-caller support, test the generic-caller path *and* a direct call with identical specialization arguments; a test whose two calls use different arguments (`count<1>` vs `count<3>`) never reaches the shared set specialization ([Per-conformance extension methods (#13387 R2): false legacy E33180 when a generic caller and a direct call share inner args](../learnings/1792843172926-per-conformance-extension-methods-13387-r2-false-l.md)).

## Per-conformance extension methods (#13387): specialize-pass mechanics and adjacent bugs

The rework of PR #13387 makes `extension<T : I> T` methods called on a dynamic object build one copy per conformer plus a dispatcher. (The SASS results for the whole-helper `[__specializePerConformance]` attribute are on the [companion page](slang-compiler-type-flow-and-gate-discipline.md).) The rework exposed four facts about the specialize and type-flow passes:

- **Compiler-dictionary values are weak.** `CompilerDictionaryValue` operands are weak references (`isWeakReferenceOperand` in slang-ir-dce.cpp). A static `specialize(specialize(g, A, wA), N)` creates an intermediate inner generic. That generic is unused after round 1, so DCE collects it. A later round that re-specializes the same `(g, A, wA)`, for example a dispatcher built after typeflow, gets a new intermediate and therefore a duplicate function, and a `static` local in that function splits into two counters. The fixer adds a keepAlive to the intermediate for the rest of the pass and removes it in the `SpecializationContext` destructor ([Slang specialize pass: compiler-dictionary values are weak, and typeflow uses fresh SpecializationContexts](../learnings/1792832560264-slang-specialize-pass-compiler-dictionary-values-a.md)).
- **Typeflow uses fresh `SpecializationContext`s.** Typeflow calls the no-context `specializeGeneric(inst)`, which builds a new context, so a cache or state kept in the context is invisible there. Facts that must survive across calls belong in the IR (a decoration on the synthesized inst), not in context dictionaries ([Slang specialize pass: compiler-dictionary values are weak, and typeflow uses fresh SpecializationContexts](../learnings/1792832560264-slang-specialize-pass-compiler-dictionary-values-a.md)).
- **Nested generics with set arguments crash.** `specialize(specialize(g, Tset, Wset), N)` fails with E99997 "unexpected set kind" in `maybeSpecializeWitnessLookup`. Flattening `g`'s inner generic into one generic before typeflow lets the existing set-specialization path handle it ([Slang specialize pass: compiler-dictionary values are weak, and typeflow uses fresh SpecializationContexts](../learnings/1792832560264-slang-specialize-pass-compiler-dictionary-values-a.md)). The same E99997 appears, before the PR too, when a `[Differentiable]` extension method is called on a dynamic object; adding `bwd_diff` turns it into a segfault ([Per-conformance extension methods (#13387 patch): static locals split with one conformer; adjacent pre-existing crashes](../learnings/1792835531089-per-conformance-extension-methods-13387-patch-stat.md)).
- **`removeUnusedGenericParam` merges types whose witnesses differ.** slang-ir-remove-unused-generic-param.cpp hoists a struct generic whose parameters are all unused to global scope. Empty specializations such as `Number<0>` and `Number<1>` of `struct Number<let N:uint> : ICode {}` then become one IR type, while their witness tables stay distinct, and typeflow gives `T` a single type with a witness set. Code that pairs witnesses by `getConcreteType()` must allow duplicate concrete types, or reject them only when several constraints must be correlated ([Slang: removeUnusedGenericParam merges types whose witnesses differ; FileCheck -NEXT fails on slang-test HLSL](../learnings/1792845935161-slang-removeunusedgenericparam-merges-types-whose-.md)).

A local review of fixer patch f4398e26a (L40S Release builds, compared with PR head 41e6e4fbe) found what the keepAlive does not cover and which neighbouring crashes predate the PR ([Per-conformance extension methods (#13387 patch): static locals split with one conformer; adjacent pre-existing crashes](../learnings/1792835531089-per-conformance-extension-methods-13387-patch-stat.md)):

- **Static locals still split with one conformer.** The design doc says that a per-type copy of a method with its own generic parameters shares its `static` locals with static calls. That holds with two or more conformers, but not with one. With only `A:IValue` registered, `value.count<3>()` (dynamic) then `a.count<3>()` (static) returns 3, 3 instead of 3, 6 on cpu and cuda. A non-nested method does share, and the PR head behaves the same.
- **Pre-existing crashes** (same at the PR head, in both language modes): `extension<T:IFoo> T : IBar` passed as `useBar<X:IBar>(dynamicIFoo)` segfaults, while a direct `dynamicIFoo.bar()` works; and the `[Differentiable]` E99997 above.
- **Front-end bug:** `extension<T:IOuter> T where T.Inner : IValue` makes every conformer fail with E38100 "missing interface member", so the witness-owner shape cannot be written as an extension.
- **Review technique:** a PR that removes `-warnings-as-errors <warning>` from a test can silently turn a success test into one that passes on the fallback path. Ask for a Slang 2025 variant (where the fallback is an error) or for structural checks.

## `analyzeCall`: the captured `callee` may already be deallocated

In `analyzeCall`, `translationContext.resolveInst(callee)` can `removeAndDeallocate` the call's callee. A module-scope `LookupWitnessMethod` on a concrete witness table is resolved through `specializeWitnessLookup` (slang-ir-translate.cpp:348), which replaces and removes it. After that, `callee->getParent()` is null and `isGlobalInst(callee)` segfaults. Reading `callee->getOp()` still returns a plausible value, but only because the IR arena never frees memory, so a probe that reads the op proves nothing. On #13820, `diagnoseIfSetSpecializedCalleeLacksTags` is correct only because `as<IRSpecialize>` short-circuits before anything else touches the stale pointer; instrumenting it with an unconditional `isGlobalInst(callee)` crashed three probes. When reviewing type-flow code, check every use of the captured `callee` after a resolve: move the inspection before the resolve, or use the resolved value ([typeflow analyzeCall: captured callee may already be removed after resolveInst](../learnings/1792602391041-typeflow-analyzecall-the-captured-callee-may-alrea.md)). A related null: witness-table entries produced by `lowerWitnessEntryValue` have a null type, so `cast<IRFuncType>(x->getDataType())` on a resolved witness entry can return null ([translation-dict memo hit returned a set-specialized generic's lowered func](../learnings/1792595826314-slang-type-flow-translation-dict-memo-hit-returned.md)).

## Debugging and test-authoring notes from the #13817 chain

- **Crashes lose the IR dump.** `-dump-ir` writes to stdout, which is lost on a segfault. Set `SLANG_DEBUG_IR_BREAK=<debugUID>` to get the creation stack of the inst instead. UIDs shift between instrumented and uninstrumented builds, so take the UID from the same binary ([translation-dict memo hit](../learnings/1792595826314-slang-type-flow-translation-dict-memo-hit-returned.md)).
- **No gdb in the reviewer container.** An LD_PRELOAD SIGSEGV handler that calls `backtrace` and `dladdr`, combined with `addr2line -e build/Release/lib/libslang-compiler.so.*.dwarf`, gives symbolized frames ([analyzeCall captured callee](../learnings/1792602391041-typeflow-analyzecall-the-captured-callee-may-alrea.md)).
- **FileCheck negatives.** `X-NOT: error` matches the literal `standard error = {` header that slang-test prints, so the check fails on a clean compile. Write `X-NOT: error[` ([translation-dict memo hit](../learnings/1792595826314-slang-type-flow-translation-dict-memo-hit-returned.md)).
- **Includes.** slang-test does not pick up `//TEST_INPUT` lines from `#include`d files. Inline them, or the test runs with empty buffers and fails on every API ([analyzeCall captured callee](../learnings/1792602391041-typeflow-analyzecall-the-captured-callee-may-alrea.md)).
- **Formatting.** `extras/formatting.sh` exits 1 and skips clang-format entirely when `clang-format` is not on PATH. Run `/usr/lib/llvm-17/bin/clang-format --style=file` directly ([translation-dict memo hit](../learnings/1792595826314-slang-type-flow-translation-dict-memo-hit-returned.md)).
