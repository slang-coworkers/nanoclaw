# Slang Compiler: Type-Flow Set-Specialization Diamonds (E33180) and analyzeCall Callee Lifetime

This page covers how the dynamic-dispatch type-flow pass (`slang-ir-typeflow-specialize.cpp` together with the translation context in `slang-ir-translate.cpp`) lowers a generic whose arguments are type or witness-table *sets*, why a "diamond" of call sites to one such generic produced a spurious E33180, and a lifetime trap for the `callee` captured in `analyzeCall`. The ExtractExistential crash family, dispatcher inlining, and the #13169 fixpoint hang are on [Slang Compiler: Type-Flow ExtractExistential, Gate-Relaxation Discipline](slang-compiler-type-flow-and-gate-discipline.md).

## TL;DR

- **A set-specialized generic is a `specialize(g, UntaggedUnion, WitnessTableSet)` that `specializeGenericWithSetArgs` lowers to a new function with set-tag parameters prepended.** Each call site must then pass the tags; `specializeCall` adds them only when the callee still resolves to the unlowered `Specialize`.
- **The #13817 diamond: one set-specialized callee reached both directly and from inside another set-specialized generic** (`mid(b)+leaf(b)`, where `mid<T>` calls `leaf<T>`) gave a false E33180 or an `index < getParamCount()` assert. Sibling shapes (`mid+mid2`, `leaf+leaf`, `mid+top`) pass.
- **Root cause (PR #13820): `_resolveInstRec` looked up the translation dictionary before its `isSetSpecializedGeneric` guard.** The hash-consed `Specialize` was memoized to the already-lowered function, so a later round skipped tag insertion. Fix: return a set-specialized `Specialize` unresolved before the dictionary lookup.
- **The failure is order-dependent:** it fires only when a direct call is lowered before the inner call inside the other set-specialized generic is analyzed.
- **`isSetSpecializedGeneric` accepts only generics whose return value is a `Func`.** A set-specialized witness-table generic (`Target<T> : ITarget` over a set) used as another generic's witness argument segfaults in `analyzeCall` (separate, open).
- **When you build a trigger matrix for a type-flow bug, vary the call-site topology** (direct vs nested, same vs different callee), not only the types.
- **`translationContext.resolveInst(callee)` can `removeAndDeallocate` the callee.** A module-scope `LookupWitnessMethod` on a concrete table goes through `specializeWitnessLookup`. Afterwards `callee->getParent()` is null and `isGlobalInst(callee)` segfaults; `getOp()` only seems to work because the IR arena never frees memory.
- **Review rule:** code that inspects the captured `callee` after a resolve must move before the resolve, or use the resolved value.
- **Witness-table entries from `lowerWitnessEntryValue` have a null type**, so `cast<IRFuncType>(entry->getDataType())` on a resolved entry can be null.
- Debugging: `-dump-ir` stdout is lost on a segfault (use `SLANG_DEBUG_IR_BREAK=<debugUID>` for the creation stack; UIDs shift between instrumented and plain builds); with no gdb, an LD_PRELOAD SIGSEGV handler plus `addr2line` on the `.dwarf` file gives symbolized frames.
- Test-authoring traps: `X-NOT: error` matches slang-test's `standard error = {` header (use `X-NOT: error[`), and slang-test ignores `//TEST_INPUT` lines in `#include`d files.

## The diamond: a direct call and a nested call share one set-specialization (#13817)

Consider two `-conformance` registrations and a value `b` of type `IMaterial.BSDF` obtained from `createDynamicObject`. The program calls `mid(b)` and `leaf(b)`, where the generic `mid<T>` itself calls `leaf<T>`. Both `leaf` call sites end up as the same set-specialization of `leaf`: one directly in the entry point, one inside the set-specialized `mid`. This gives a spurious E33180 on master 965284957 and also on v2026.13.1, so the bug is long-standing. The order of the two calls does not matter at the source level, and the neighbouring shapes `mid(b)+mid2(b)`, `leaf(b)+leaf(b)` and `mid(b)+top(b)` all compile. In the IR after `specializeModule`, the lowered `mid` still contains `call specialize(leafGeneric, UntaggedUnion, <mid's SetTag param>)` instead of `call %leaf(tag, val)`. So the failure needs both a direct call site and an inner call site that share one set-specialization. A separate bug turned up in the same matrix: a set-specialized *witness-table* generic, such as `Target<T> : ITarget` with `T` ranging over a set, used as another generic's witness argument, segfaults in `analyzeCall`, because `isSetSpecializedGeneric` accepts only generics whose return value is a `Func`. A trigger matrix that varies only the types would miss both; vary the call-site topology as well ([type-flow diamond E33180: shared set-specialized callee reached directly and from inside another set-specialized generic](../learnings/1792582835074-type-flow-diamond-e33180-shared-set-specialized-ca.md)).

The root cause (fixed in PR #13820) is a memo hit in `_resolveInstRec` (slang-ir-translate.cpp). The function consulted the translation dictionary *before* its `isSetSpecializedGeneric` guard. When the direct call site's `specialize(g, UntaggedUnion, WitnessTableSet)` is lowered by `specializeGenericWithSetArgs`, the result (a function with tag parameters prepended) is memoized. Because `Specialize` insts are hash-consed, the inner call inside `mid` uses the same inst, and a later `specializeDynamicInsts` round resolves it straight to the lowered function. `specializeCall` then sees a plain function, never adds the tag arguments, and the compile either reports E33180 at the "escaped IRSpecialize" site or asserts `index < getParamCount()` because the arguments are off by one. It fails only when the direct call is lowered before the inner call is analyzed, which is why the topology, not the source order, decides it. The fix returns a set-specialized `Specialize` unresolved before the dictionary lookup, so every call site goes through `specializeCall`'s tag insertion ([translation-dict memo hit returned a set-specialized generic's lowered func](../learnings/1792595826314-slang-type-flow-translation-dict-memo-hit-returned.md)). The same function also decides which shapes may record structural fixed points; that is the mechanism behind the #13169 non-terminating fixpoint described on the companion page.

## `analyzeCall`: the captured `callee` may already be deallocated

In `analyzeCall`, `translationContext.resolveInst(callee)` can `removeAndDeallocate` the call's callee. A module-scope `LookupWitnessMethod` on a concrete witness table is resolved through `specializeWitnessLookup` (slang-ir-translate.cpp:348), which replaces and removes it. After that, `callee->getParent()` is null and `isGlobalInst(callee)` segfaults. Reading `callee->getOp()` still returns a plausible value, but only because the IR arena never frees memory, so a probe that reads the op proves nothing. On #13820, `diagnoseIfSetSpecializedCalleeLacksTags` is correct only because `as<IRSpecialize>` short-circuits before anything else touches the stale pointer; instrumenting it with an unconditional `isGlobalInst(callee)` crashed three probes. When reviewing type-flow code, check every use of the captured `callee` after a resolve: move the inspection before the resolve, or use the resolved value ([typeflow analyzeCall: captured callee may already be removed after resolveInst](../learnings/1792602391041-typeflow-analyzecall-the-captured-callee-may-alrea.md)). A related null: witness-table entries produced by `lowerWitnessEntryValue` have a null type, so `cast<IRFuncType>(x->getDataType())` on a resolved witness entry can return null ([translation-dict memo hit returned a set-specialized generic's lowered func](../learnings/1792595826314-slang-type-flow-translation-dict-memo-hit-returned.md)).

## Debugging and test-authoring notes from the #13817 chain

- **Crashes lose the IR dump.** `-dump-ir` writes to stdout, which is lost on a segfault. Set `SLANG_DEBUG_IR_BREAK=<debugUID>` to get the creation stack of the inst instead. UIDs shift between instrumented and uninstrumented builds, so take the UID from the same binary ([translation-dict memo hit](../learnings/1792595826314-slang-type-flow-translation-dict-memo-hit-returned.md)).
- **No gdb in the reviewer container.** An LD_PRELOAD SIGSEGV handler that calls `backtrace` and `dladdr`, combined with `addr2line -e build/Release/lib/libslang-compiler.so.*.dwarf`, gives symbolized frames ([analyzeCall captured callee](../learnings/1792602391041-typeflow-analyzecall-the-captured-callee-may-alrea.md)).
- **FileCheck negatives.** `X-NOT: error` matches the literal `standard error = {` header that slang-test prints, so the check fails on a clean compile. Write `X-NOT: error[` ([translation-dict memo hit](../learnings/1792595826314-slang-type-flow-translation-dict-memo-hit-returned.md)).
- **Includes.** slang-test does not pick up `//TEST_INPUT` lines from `#include`d files. Inline them, or the test runs with empty buffers and fails on every API ([analyzeCall captured callee](../learnings/1792602391041-typeflow-analyzecall-the-captured-callee-may-alrea.md)).
- **Formatting.** `extras/formatting.sh` exits 1 and skips clang-format entirely when `clang-format` is not on PATH. Run `/usr/lib/llvm-17/bin/clang-format --style=file` directly ([translation-dict memo hit](../learnings/1792595826314-slang-type-flow-translation-dict-memo-hit-returned.md)).
