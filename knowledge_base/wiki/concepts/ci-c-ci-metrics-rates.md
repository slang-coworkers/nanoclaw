## TL;DR

Every CI-health number is a ratio over a population, and the population is where the errors hide. A rate is meaningless without its denominator's definition; a flake ranking is only as good as its bucket regexes; a per-host analysis is a category error on an autoscaled fleet.

- **Pin the denominator.** A failure rate is only comparable to a baseline measured over the *same* population (event type, workflow filter, branch, window, n). Same day/repo/API produced 9.1% vs 28.6% purely from denominator scope.
- **Take ratios over `success+failure` only.** Bucket four ways with `status` checked *before* `conclusion`: success / failure / cancelled+skipped (UNTESTED) / non-terminal. Folding UNTESTED into the denominator understates the rate toward "healthy."
- **`?filter=all` re-lists carried-over successes** under each new `run_attempt` with a fresh `job_id` — inflating success rates toward healthy. Dedupe on `(run_id, name, runner, started_at, completed_at)`; a distinct-`job_id` count is not an execution count.
- **Prove a runner name denotes a machine before per-host analysis.** Ephemeral autoscaled runners (`win-test-*`) are single-use nonces; per-host rates are undefined there. Lead with `runner_id` uniqueness + instance labels, not the name ratio.
- **Every bucket term must be a signature that can't appear in ordinary diagnostic prose.** A bare `runner` token inflated a flake class 8.5×; always report the unbucketed share and check subset/superset before ranking buckets as peers.
- **Verify a workflow is still active** by its newest `run_started_at` before using it as a rate basis; assert `got >= total_count` unconditionally on every paginated fetch, or a windowed filter turns a silent short-page into a plausible zero.

## Pin the denominator, and count only the tested

A failure-rate baseline is only meaningful together with the population it was measured over. A stored slang baseline of "42.3% merge-queue failure, `CI` workflow only, 07-18→08-06" was re-queried three ways on the *same day, same repo, same API*: aggregating all 8 `merge_group` workflows gave 9.1% (reading as dramatic improvement), filtering to `name=="CI"` gave 28.6% (unremarkable, inside the 25–50% band). Store the query *alongside* the number — event type, workflow filter, branch, window bounds, and n — and reproduce the filter before comparing. With n=7 conclusive runs in a day, no day-over-day claim is supportable; cite the multi-week baseline for trend and the daily figure only to say "not anomalous." Do not derive a percentage from a `merge_queue: {success, failure}` gauge in a snapshot log — observed *decreasing* across 24h, so it's a point-in-time window count, not a cumulative counter (and the "cumulative counter" annotation was also wrong). [Pin the denominator when comparing a CI rate to a stored baseline](../learnings/1786091003109-pin-the-denominator-when-comparing-a-ci-rate-to-a-.md)

The denominator must exclude jobs that tested nothing. Bucket four ways with `status` checked *before* `conclusion` — success / failure / cancelled+skipped (UNTESTED) / non-terminal — and take the ratio from `success+failure` only. Two related instrument defects on slang push the same direction (toward healthy, i.e. toward suppressing a quarantine ask): `?filter=all` on the jobs endpoint re-lists carried-over jobs that did *not* re-execute under each new `run_attempt`, with a fresh `job_id` but byte-identical `runner`/`started_at`/`completed_at`/`conclusion`. Since only *failed* jobs get re-executed, carry-over duplicates successes preferentially: undeduped 36/431=8.4%, deduped-on-execution 36/341=10.6%. The usual sanity checks miss it because every `job_id` is distinct — **a distinct-`job_id` count is not an execution count.** Dedupe key: `(run_id, name, runner, started_at, completed_at)`. Always ask which way an instrument error pushes your *recommendation*. [gh filter=all carry-over rows inflate CI success rates toward healthy](../learnings/1786070106710-gh-filter-all-carry-over-rows-inflate-ci-success-r.md)

## Per-host reasoning needs a persistent host

shader-slang/slang CI has **two runner fleets**, and host-keyed reasoning is a category error on one. Ephemeral autoscaled runners (`win-test-*`, `linux-test-*`, `linux-sm80plus-*`) carry single-use nonce names — 782 distinct names / 782 executions, zero reuse; sampled `runner_id`s were 196/196 distinct and monotonic with time. The VM is destroyed minutes after the job, so "depool this runner" is meaningless. Persistent runners (`SLANGWIN4`, `SLANGWIN5`, `SLANGWIN10X64-1`, `kernelvm-falcor-bridge`) recur and *do* support per-host rates. Filing "look at two named runners" cost a public correction because both VMs no longer existed; the durable ask targets the VM image / driver / GCP-T4 instance type. The one-line probe: `distinct names == executions` ⇒ the identifier is an execution id wearing a hostname — ask what a *second* occurrence would look like. But beware the tautology: hosted `runner_name` is literally `"GitHub Actions " + runner_id`, so a name-uniqueness ratio there is true by construction and proves nothing — lead with `runner_id` uniqueness + instance labels sampled at scale. [Prove a runner name denotes a machine before doing per-host CI analysis](../learnings/1786070084049-prove-a-runner-name-denotes-a-machine-before-doing.md)

A same-host pass/fail pair also kills a host-skew hypothesis directly (a run failing on SLANGWIN5 att1 and passing on SLANGWIN5 att2 refutes "SLANGWIN5-specific"); per-host *rates* over small n mostly reflect where the scheduler put the job. See [[wiki/concepts/ci-c-source-of-truth.md]] for that instance.

## Flake buckets: signatures, overlap, and the unbucketed share

A flake ranking is only as good as its bucket regexes, and three independent defects can all push the same way (here, toward recommending a quarantine over a nudge). (1) **A bare token matches prose, not signal**: a `runner-lost` bucket ending in a bare `runner` matched "runner SLANGWIN5", "passes on another runner", "no runner" — 17 reported = 2 real + 15 artifact (8.5× inflation), vaulting an infra class to #1. Every bucket term must be a signature that cannot appear in ordinary diagnostic prose; audit by printing ±45 chars around each match. (2) **Ranking a subset beside its superset**: `GBufferRTTexGrads` *is* a Falcor test (7 of 8 events also falcor), so they're one bucket and a member of it, not peers — compute pairwise overlap first; a multi-label sum ≠ event count means labels overlap. (3) **Report the unbucketed share**: 64% of events matched no bucket, and the largest cluster (a fixed spirv-val defect) hid there — a ranking that leaves the majority unclassified ranks your regex, not the repo. A rerun ledger also cannot support a signal-to-noise claim: it records only your *decisions*, so a real failure that correctly blocked a PR never becomes a rerun row — the true-positive count is structurally absent. Quarantine advice needs an independent basis. [A bare-token bucket regex inflated a flake ranking 8.5×; and check subset/superset before ranking buckets side by side](../learnings/1786206669441-a-bare-token-bucket-regex-inflated-a-flake-ranking.md)

Before escalating "N separate flake buckets share one root cause," grep for the cited function in *each* bucket's actual code path — a shared vocabulary ("CUDA", "host-pinned", "interop") is not evidence of a shared component. Escalating that three slang CUDA buckets shared one allocator defect was killed by one grep: shared-handle interop goes through `cuImportExternalMemory` and never reaches the host-pinned heap at all, and two of the three buckets were already filed with an independently-diagnosed *different* cause. Name the second member and verify it calls the cited function; if you can't show two buckets reaching the same file:line, you have one bucket and a hypothesis. Related self-inflicted errors: implying "page reuse" without reading the control flow (the failing `cuMemAllocHost` is only reached on a cache *miss*, pointing the opposite way), letting a combined population's recurrence stand in for the one member you proposed a cause for (re-deriving *membership* showed 1 confirmed occurrence, not "recurring across months"), and search the downstream repo's tracker before escalating — a bucket already filed with a different diagnosis is a strong signal your unifying story is wrong. [A shared vocabulary is not a shared code path — verify the second member calls the cited function](../learnings/1786134256554-a-shared-vocabulary-is-not-a-shared-code-path-veri.md)

That independent basis is a *live job cross-section*, not your own rerun ledger — and it has its own two traps. (1) **The workflow you name may be dormant**: `falcor-test.yml` had `total_count=11683` runs but its newest started 52 days ago; today's falcor failures come from the `test-falcor` *job inside `ci.yml`*. A huge `total_count` says nothing about whether a workflow still runs — probe the newest `run_started_at` first. (2) **A page cap produced a confident false zero**: a 12-page loop (`got=1200 < total_count=11683`) on a newest-first endpoint covered only back to mid-June, so a 7-day filter yielded `runs in last 7d: 0` at exit 0, reading as "healthy." Only an *unconditional* `got >= total_count` assert caught it. Correct measurement: `ci.yml` runs since a date, enumerate falcor jobs, bucket four ways — `UNTESTED_skipped`=260 + `UNTESTED_cancelled`=53 meant 313 of 744 executions tested nothing; folding them in would report ~3.6% instead of the true 6.3%. Host spread across SLANGWIN4 and SLANGWIN5 confirms host-agnostic ⇒ quarantine the test, don't depool a runner. Don't group your *own ledger* by check label to find "today's spike" — one sweep logging 17 stale rows under the flake's label manufactures a fake 23-hit spike that measures your sweep. [A dormant workflow makes its own red-rate measurement a false zero (falcor-test.yml vs ci.yml's test-falcor job)](../learnings/1786220895747-a-dormant-workflow-makes-its-own-red-rate-measurem.md)
