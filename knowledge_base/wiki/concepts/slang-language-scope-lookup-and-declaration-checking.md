# Slang Scope Lookup, Function-Local Types, and Declaration Checking

How the Slang checker resolves unqualified names by walking scopes in `_lookUpInScopes` (`slang-lookup.cpp`), plus declaration-checking rules from the same October 2026 front-end cluster: function-local types (#13435, PR #13718), extension bodies (#13721), `using namespace` ranking (#13750), walk continuation past a level with hits (#13888, PR #13889), self-referencing local initializers (#2958), the redeclaration check inferred-type decls skipped (#13876), the interface `EmptyDecl` skip, and declaration modifiers in a type position. Related: parser-time lookup and the `namespace A::B` reopen on [Slang Parser: tryParseGenericApp Classification and Parser-Time Lookup](../concepts/slang-language-parser-generic-app-and-lookup.md); the interface requirement loop on [Slang conformance checking: requirement enumeration and method-requirement witness synthesis](../concepts/slang-language-core-requirement-witness-synthesis.md); the first `checkTypeModifier` triage on [Slang Compiler Frontend and Semantic Checking](../concepts/slang-compiler-frontend-and-checking.md).

See also: [Slang Declaration-Order Scoping](../concepts/slang-language-declaration-order-scoping.md) — `hiddenFromLookup`, the shapes that read a later local (#14118, #14120), and HLSL `for`-init scoping (#14099).

## TL;DR

- A member of a struct declared in a function body must not resolve names to the enclosing function's parameters or non-static locals: Slang has no capture for local types (maintainer ruling on #13435; diagnose, E30015 is fine). Lambdas own capture.
- The boundary belongs in `_lookUpInScopes`, the producer: after the walk crosses an `AggTypeDeclBase` scope, `ScopeDecl`/`CallableDecl` scopes drop `ParamDecl` and non-static `isLocalVar` results. Filter Member breadcrumbs too (a local `cbuffer CB { int c; }` is a transparent local).
- When dropping a name empties a scope's result, stop the walk; continuing silently binds a shadowed global. C++ rejects that case, and `::x` still reaches the global.
- A post-lookup parent-function comparison misses a local `static const` initializer, because `getParentFunc` walks through the `AggTypeDecl`.
- `_isUncheckedLocalVar` filters by declaration order only; `isLocalVar` does not cover `ParamDecl`.
- Check any "C++ semantics" claim with `g++ -fsyntax-only` before writing it into a brief.
- An extension body sees its own scope, its lexical parents, and the target type's members — not the target's enclosing namespace/struct (`extension N::T { return nsValue; }` → E30015). Workarounds: `N::x`, `using namespace N;`, or write the extension inside `namespace N {}`. A fix changes which of global `v` / `N::v` binds, so it must choose an order and test it.
- `using namespace N;` puts N's scope on the same level as the directive's scope: for non-functions an inner-block `using` beats outer locals and globals and a same-level clash is ambiguous (E39999); for functions a global `g` beats `N::g`. Both differ from C++/DXC (#13750); a fix is a language-design decision.
- `using namespace` peers are ordered newest first: after `using namespace A; using namespace B;` the first hit (`result.item`) comes from B.
- `_lookUpInScopes` walks past a level with hits only if ANY collected decl is overloadable (PR #13889); the old `isOverloaded()` (2+ hits) test let same-named variables pull in, and sometimes bind, an outer decl. An ALL rule is wrong too.
- A lookup-termination change shows up through post-lookup filters (`refineLookup`, visibility, overload resolution), not `isOverloaded()`/`isValid()` consumers. Probe type scopes as well as namespaces.
- `let a = 1; { let a = a + 1; }` uses the outer `a` — the deliberate #2958 rule, pinned by the core module and tests. Changing it is source-breaking (umbrella #13719). A self-reference diagnostic must precede `getTypeForDeclRef`, which asserts `!_isUncheckedLocalVar`.
- Shadowing is barely diagnosed: E30515 covers only generic *type* params (widening it trips a core-module redeclaration that aborts bootstrap); a param/local shadowed by an inner block or `for` local is never diagnosed (`checkForRedeclaration` compares only same-`parentDecl` siblings).
- Inferred-type decls (untyped `let`/`var`, unsized array with initializer, `[UnscopedEnum]` case) used to jump past `ReadyForReference`, where the redeclaration check lives (#13876). Replaying it exposes parentless synthesized decls (`__optInner`; fix the producer). Unnamed cbuffer/tbuffer members need a per-scope pass, called from `visitBlockStmt` as well as the `DefinitionChecked` dispatch.
- `slang-diagnostics.lua` cannot vary severity by language version; the call site picks between two diagnostics with `isSlang202cOrLater()`.
- The interface requirement loop must skip `as<EmptyDecl>(maybeGetInner(member))` (`__generic<U> ;` is `GenericDecl { inner = EmptyDecl }`), before `ensureDecl` so attribute validation still runs.
- In `checkTypeModifier`, a non-`TypeModifier` reports E31201 `ModifierNotAllowed` (E99999 only for an unhandled `TypeModifier` subclass); `func f(x: inout int)` then gives E31201 + E30011 and needs a parser change.
- `dynamic_uniform` on a local gives E31201 although the uniformity guide allows locals; `isModifierAllowedOnDecl` admits only globals, struct fields and parameters.
- A codex CODE_REVIEW/OUTPUT_REVIEW reply can be a wiki-recall blurb; re-ask on the same `threadId` for the structured output.

## Function-local types must not see enclosing parameters or locals (#13435, PR #13718)

```slang
int f(int x)
{
    struct S { int get() { return x; } }   // must not bind the parameter x of f
    S s;
    return s.get();
}
```

Before PR #13718, `get` resolved `x` to `f`'s parameter: `_lookUpInScopes` walks `Scope->parent` from the method body through the block `ScopeDecl` into the `FuncDecl` with no boundary, and the only local filter, `_isUncheckedLocalVar`, handles declaration order (`isLocalVar` does not cover `ParamDecl`). Method bodies and field/`static const` initializers leak the same way, and lowering then references a value absent from the member's function — a silent miscompile (HLSL references undeclared `x_0`/`_S1`, SPIR-V fails "does not dominate", Debug ICEs in `typeflow-specialize.cpp:86`). The maintainer ruling (skiminki-nv, #13435, 2026-10-16): no capture for local types, diagnose the use (E30015 acceptable); capture belongs to lambdas. A post-lookup check comparing parent functions fails for a local `static const` initializer, since `getParentFunc` walks through the `AggTypeDecl` so `m_parentFunc` is the enclosing function [function-local types see enclosing locals/params through an unbounded scope walk](../learnings/1792157985562-slang-function-local-types-see-enclosing-locals-pa.md).

The fix is in lookup, the producer: `_lookUpInScopes` sets a flag after passing an `AggTypeDeclBase` scope (where `_doesScopeBlockUseOfEnclosingThisExpr` flips the `this` breadcrumb), and later `ScopeDecl`/`CallableDecl` scopes drop `ParamDecl` and non-static `isLocalVar` results. Two non-obvious details: (1) a function-local `cbuffer CB { int c; }` is a transparent local — `c` is found as the field and `CB` appears only in the Member breadcrumb, so the filter must check breadcrumbs; (2) if dropping empties the scope's result, `break`, or the walk binds a same-named global (g++/clang reject that; `::x` still reaches the global). Lambdas written in the function are unaffected: the synthesized `LambdaDecl` is not on the body's scope chain, which never crosses a type decl [the lookup boundary in `_lookUpInScopes`](../learnings/1792176216247-slang-function-local-types-must-not-see-enclosing-.md).

The shadowed case matches C++, contrary to a first #13435 triage memo: if a local-class member names `x` and both an enclosing local and a global `x` exist, lookup finds the local and rejects it (g++: "use of local variable with automatic storage from containing function"; clang: "reference to local variable 'x' declared in enclosing function"); `::x` reaches the global. Silently binding the global would be the divergence [C++ local class: a shadowed global is not reachable by unqualified name](../learnings/1792163585759-c-local-class-shadowed-global-is-not-reachable-by-.md).

## Extension bodies use lexical-only lookup (#13721)

```slang
namespace N { static const int nsValue = 1; struct T {} }
extension N::T { int get() { return nsValue; } }   // E30015
```

The `ExtensionDecl` branch of `_lookUpInScopes` (`slang-lookup.cpp:895-915`) does a member lookup on `getTargetType` but never searches the target decl's enclosing namespace or struct, so `extension Outer::Inner { return outerStatic; }` also fails even though a method in `Inner`'s own body sees `Outer`'s statics. `N::nsValue`, `using namespace N;`, or an extension written inside `namespace N {}` compile. Shadowing trap: with a global `v` and `N::v`, `extension N::T { return v; }` binds the global today, so a C++-style fix silently changes the binding and must choose and test an order. Nothing settles it: `lookup.md` in the spec is a placeholder, the #11577 namespace pre-pass comment (`slang-check-decl.cpp:5592-5623`) covers only the *header* of a file-scope `extension N::T`, no test uses a namespace-qualified target, and Slang does not parse out-of-line `void N::T::f() {}` [extension bodies use lexical-only lookup](../learnings/1792178854023-slang-extension-bodies-use-lexical-only-lookup-ext.md).

## `using namespace` ranks as a sibling of the directive's scope (#13750)

`visitUsingDecl` (`slang-check-decl.cpp:18744`) adds N's scope as a `nextSibling` of the directive's scope, and `_lookUpInScopes` (`slang-lookup.cpp:831`) treats siblings as one level. Non-function lookup stops at the first level with a hit (before PR #13889, only with exactly one hit — next section), so an inner-block `using namespace N;` makes `N.z` beat outer locals, enclosing-namespace members and globals, and a same-level clash is E39999: `using namespace N; int z; return z;` and `namespace T { using namespace N; static const int y; }` are ambiguous in Slang where C++/DXC pick the local or T's member. Functions rank the other way: the walk continues and `getScopeRank` prefers the closer parent, so a global `g` beats `N::g` where C++/DXC report ambiguity. Measured on HLSL input: the same `.hlsl` stores 1110 under Slang and 1430 under DXC 1.9 `-HV 2021`. Without a standalone DXC (scratch builds need GLIBC 2.38), run `slangc foo.hlsl -pass-through dxc -target dxil-asm -entry main -profile cs_6_0 -Xdxc -HV -Xdxc 2021` and grep `bufferStore.i32(i32 69,`. The user guide only says "to the current scope", so a fix is a maintainer language-design decision [`using namespace` ranks as a sibling of the directive's scope (#13750)](../learnings/1792429007729-slang-using-namespace-ranks-as-a-sibling-of-the-di.md).

## When the scope walk continues past a level with hits (#13888, PR #13889)

`_lookUpInScopes` (`slang-lookup.cpp:1019`) used to keep walking when `result.isOverloaded() || _isDeclOverloadable(result.item)`, and `isOverloaded()` only means `items.getCount() > 1`. So two same-named non-callable hits at one level (two `using namespace` siblings, two imported modules) pulled in every outer same-named decl: with variables `A::h`, `B::h` and a global `int h(int)`, `h(7)` silently calls `::h`, while one shadowing variable gives E30016. The fix (PR #13889, the issue author's rule) continues only if ANY collected decl is overloadable (checking the accumulated `result` equals checking the first-hit set); an ALL rule breaks mixed var+func — `f(1.5f)` rebinds from `::f(float)` to `B::f(int)`. Test gotchas: `getScopeRank` (`slang-check-overload.cpp:2217`) is calls-only and measures declaration-tree distance (prefers a global over a using-sibling), so don't filter ambiguity notes with it; and g++ lists the global as a real candidate when A and B are global namespaces (using-directive names count as declared in the nearest common enclosing namespace), so nest A and B in a namespace that lacks the outer decl [isOverloaded() continues the scope walk (#13888)](../learnings/1792752359896-slang-lookup-isoverloaded-continues-the-scope-walk.md).

The continuation also fires inside struct and extension scopes — a member plus the interface requirement it satisfies, or one `static const` in two extensions — and the "prefer non-extension" rule in `CompareLookupResultItems` can then pick the outer global: `return K;` in `extension E<int>` returned the global (100) instead of the member (2). `/code-review medium` found these type-scope cases, not the triage brief [the continuation also fires inside type scopes](../learnings/1792755685949-slang-lookup-isoverloaded-continuation-also-fires-.md).

Peer order decides what a test proves: `addSiblingScopeForContainerDecl` (`slang-check-expr.cpp:317-324`) inserts each scope right after the head, so `using namespace A; using namespace B;` gives Inner → B → A and `result.item` comes from the last directive. A test separating "any hit overloadable" from "first hit overloadable" must put the non-overloadable decl in the later directive, or a first-item-only helper still passes (drill D1; PR tests passed 3/3). Stopping earlier does not change `isOverloaded()`/`isValid()` consumers (2+ hits either way); the behaviour changes come from post-lookup filters: `refineLookup(mask)` in `_resolveOverloadedExprImpl` (two variables now hide an outer *type*, so `S s;`, `StructuredBuffer<S>` and parameter types go to E30060), the visibility filter (E30600), and overload resolution (two modules each exporting a `max` variable hide builtin `max(a,b)`). Probe all three, plus type scopes (member + requirement, two extensions, typealias + associatedtype) [peer order is reversed; refineLookup hides breaks](../learnings/1792757829971-slang-lookup-using-namespace-peer-order-is-reverse.md).

## A local's initializer that names itself binds the outer name (#2958)

`let a = 1; { let a = a + 1; }` silently uses the outer `a`, and a plain `let a = a;` gives E30015. This is deliberate: `visitBlockStmt` sets `hiddenFromLookup` on block locals (`slang-check-stmt.cpp:129-146`) and clears it only after `ensureDecl(DefinitionChecked)` (`:86-87`); `_isUncheckedLocalVar` (`slang-lookup.cpp:174`) skips the hidden local, and an untyped `let` also excludes itself via `withDeclToExcludeFromLookup` (`slang-check-decl.cpp:2673`). Commit cdfea42f1 (#2958, fixing #2936) replaced the older "used before its declaration" error. Pinned by `hlsl.meta.slang:9102` (`let value = bit_cast<uint64_t>(value);`), `tests/bugs/gh-2936.slang:42`, `tests/diagnostics/local-used-in-own-declaration.slang` and `multi-declarator.slang` (E30015), and `docs/generated/tests/design/name-resolution/scopes/block-decl-init-resolves-outer-same-name.slang`. DXC follows C++ (`int max = max(a, b)` → "called object type 'int' is not a function"). A C++-rule fix must report before `getTypeForDeclRef`, which asserts `!_isUncheckedLocalVar` (`slang-check-decl.cpp:1677`); changing the rule is source-breaking, a language-design/version-gating decision (#13720, #13674, umbrella #13719) [local self-reference binds the outer name by design](../learnings/1792178859050-slang-local-self-reference-in-initializer-binds-to.md).

## Shadowing diagnostics: E30515 covers only type params (#13752)

`void f(int p) { int p = 1; }` and `for (int i = 0; ...) { int i = 2; }` compile silently (DXC rejects both), because `checkForRedeclaration` (`slang-check-decl.cpp` ~:14817) compares only decls sharing a `parentDecl`: params belong to the `FuncDecl`, while the body and each `for` get their own `ScopeDecl`. The one shadowing diagnostic, E30515 (generic-param-shadows-outer-generic), in `visitGenericDecl` (`:5059-5089`), filters both sides with `as<GenericTypeParamDeclBase>`, so value generics (`let N:int`) are never checked. Swapping to `isGenericParam()` (`slang-ast-decl.h:1157`) is two lines with zero new hits in `tests/`, but fires once in the core module — `core.meta.slang:2242`, `extension<Access access> Ptr<void,access>` with `__generic<$(ptrTypeParameterList)>` redeclaring `access` — and the core module must build warning-free (`slang-global-session.cpp:1248`), so the same PR must rename it. For error-from-202c/warning-before, the call site chooses between two diagnostics with `isSlang202cOrLater()` since the Lua has no version-keyed severity [E30515 covers only type params; locals and params are never compared across scopes](../learnings/1792436893730-slang-shadowing-diagnostics-e30515-covers-only-typ.md). See also [Slang new semantic checks: unmarked compiler-made declarations and twice-visited bodies](../concepts/slang-language-synthesized-declarations-and-double-visits.md) — what a widened shadowing check (PR #14093) falsely reports on.

## Inferred-type declarations skip the redeclaration check (#13876, draft PR #13880)

`checkForRedeclaration` runs only in `SemanticsDeclRedeclarationVisitor`, dispatched on the transition to `ReadyForReference`. A var with no type expression gets its type from `deriveVarTypeFromInitExpr` (`slang-check-decl.cpp` ~:2702, plus :3027/:3072 for an unsized array with initializer), which calls `setCheckState(DefinitionChecked)` during SignatureChecked; `ensureDecl` continues from there, so the visitor never runs. Since it compares only with earlier same-name members, results are order-dependent: `{ int a = 1; let a = 2; }` is silent while the reverse gives E30200; `static const int a = 1; static const int a[] = {1,2};` is silent; an `[UnscopedEnum]` case (an untyped `static const` LetDecl, `slang-parser.cpp` ~:6123) collides silently with an earlier `static const x`. DXC 1.9 rejects all of them (compare via `slangc -pass-through dxc -target dxil -profile cs_6_0`). The fix replays `_dispatchDeclCheckingVisitor(decl, ReadyForReference, ctx)` after a jump, which exposed a producer bug: the parentless `__optInner` VarDecl `_coerce` creates for `Optional<T>`→`Optional<U>` stayed `Unchecked`, so the capability pass's `ensureDecl` aborted "decl has no parent" in 7 Optional tests; the producer fix sets `checkState = DefinitionChecked` like `moveTemp`. Grep `create<VarDecl>()` for parentless decls before any `ensureDecl`-level hook.

Unnamed cbuffer/tbuffer/GLSL-block members are a second gap: they live in a synthesized `ParameterGroup_*` struct marked `ImplicitParameterGroupElementTypeModifier` followed by a `__transparent` var; lookup expands them (a duplicate use gives E39999) but the redeclaration walk never compares them. With `-Gec`, `__transparent` moves to a `UniformParameterShadowVarDecl` after the renamed param, and a `gl_*` builtin block redeclaration keeps the marked struct but replaces the var with an `EmptyDecl`, so the marker alone does not mean visible members. What worked: one ordered pass per scope from the first transparent var, filtered with `DeclPassesLookupMask(Default)` (so synthesized `struct XAttribute` isn't flagged), leaving decls with an earlier same-name sibling to `checkForRedeclaration` so none gets two errors [ensureDecl skipped ReadyForReference for inferred-type decls; cbuffer members need a scope pass](../learnings/1792703651539-slang-ensuredecl-skipped-readyforreference-for-inf.md). Hooked into `_dispatchDeclCheckingVisitor`'s `DefinitionChecked` case, such a pass runs per `ContainerDecl` (modules, namespaces, aggregates, extensions, synthesized decls) but not for a function body's block scope: `BlockStmt::scopeDecl` is checked through `SemanticsStmtVisitor` (locals via `checkDeclAtDeclarationPoint` → `ensureDecl`; the scope decl is never dispatched). Add a call in `SemanticsStmtVisitor::visitBlockStmt` after `checkStmt(stmt->body)` — a function-local `cbuffer` lost its warning on PR #13880 until then, caught by the peer reviewer's probe [a per-container pass needs the block-statement path too](../learnings/1793195272647-slang-checker-a-per-container-pass-needs-the-block.md).

## Interface members: the `EmptyDecl` skip must unwrap `GenericDecl`

The ordinary-member requirement loop in `checkInterfaceConformance` (`slang-check-decl.cpp`) is a deny-list. `if (as<EmptyDecl>(member)) continue;` fixes `property T X { get; };` and `interface I { ; }` but misses `__generic<U> ;`, which parses as `GenericDecl { inner = EmptyDecl }` and still gives E38100 "does not provide required interface member ''" (note "see declaration of 'generic'"). The skip is `as<EmptyDecl>(maybeGetInner(member))`, matching IR lowering's `shouldDeclBeTreatedAsInterfaceRequirement`. Placed before `ensureDecl`, attribute validation still runs (`[ForceInline];` → E31002 via `ensureAllDeclsRec`). `/code-review medium` found the generic case in eval trial slang-13337#r1 [the EmptyDecl skip must unwrap GenericDecl](../learnings/1792178638025-interface-emptydecl-skip-must-unwrap-genericdecl-g.md).

## Declaration modifiers in a type position: E31201, not E99999

`property override float3 X`, `typealias A = public float`, `-> inline float`, `(override float)x`, `Box<extern float>`, `let x : static float` and HLSL `typedef precise int` all reach `checkTypeModifier` (`slang-check-expr.cpp` ~:9594) via `_parseTypeSpec` → `_applyModifiersToTypeSpec`, which by design puts all leading modifiers on a `ModifiedTypeExpr`. The fix is at the checker: `else if (!as<TypeModifier>(modifier))` reports `ModifierNotAllowed{.modifier}` (E31201), as in declaration position; E99999 remains only for an unhandled `TypeModifier` subclass (today only `GLSLBufferModifier`, which nothing produces). Side effect: documented `func f(x: inout int)` goes from E99999 to E31201 + E30011; supporting it needs a parser change keeping direction modifiers on the `ParamDecl` [checkTypeModifier: E99999 → E31201](../learnings/1792176331466-declaration-modifiers-in-type-position-checktypemo.md).

**In declaration position, `isModifierAllowedOnDecl` (`slang-check-modifier.cpp`) is the allow-list, and it can disagree with the docs.** `a1-05-uniformity.md:12` says `dynamic_uniform` marks "function parameters, struct fields or local variables", but the checker allows `DynamicUniformModifier` only on a global `VarDeclBase`, struct member or `ParamDecl` (~:1751, with the interpolation modifiers; unchanged on master 2026-10-21), so a local gives `error[E31201]` on v2026.20. Use a parameter or field; a global is accepted but silently ignored because `isDynamicUniformLocation` (`slang-ir-uniformity.cpp`) has no `GlobalVar` case (checked with a release tarball, [verify Discord/bot claims with the release tarball](../learnings/1792571968734-verify-discord-bot-slang-claims-with-the-release-s.md)). `asDynamicUniform(v)` is the opposite tool (treat a value as uniform). No upstream issue as of 2026-10-21; read the allow-list before repeating a docs claim [dynamic_uniform is rejected on locals despite the docs](../learnings/1792563496714-dynamic-uniform-is-rejected-on-local-variables-des.md).
