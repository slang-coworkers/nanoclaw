## TL;DR

- GitHub's closing-keyword parser has **no notion of negation** — a body reading "does not by itself **resolve #N**" still auto-closes #N. The disclaimer re-arms the auto-close it explains. Verify only from `closingIssuesReferences` (with a positive control), never from body text; fix by breaking keyword/ref *adjacency*, not by rewording sentiment.
- A **carrier/fixer PR body describes an older revision** — commits land after the body is written and it's never updated. Read the head diff first, form the change from *it*, then diff the two narratives.
- `mergeStateStatus BLOCKED` masks `BEHIND` (GraphQL returns one status); "merged while behind" proves the gate isn't *absolute*, not that it isn't in *your* blocker. Check `baseRefName` before comparing to `master`. Squash-merge **auto-adds `Co-authored-by:`** for every distinct author, so fork credit survives.
- **Aggregates lie about specifics**: a run-level `conclusion=success` can hide 34/36 skipped jobs; doctest reports `0 skipped` while device-gated cases SKIP; a `check_runs` "failure count" counts in-flight (`conclusion:null`) checks as failures. Read the individual record — job breakdown, per-test line, `status=="completed" and conclusion!="success"`.
- A **draft PR is invisible to review queues** — requesting a reviewer on a draft emits no `ready_for_review` event, so the issue gets re-triaged months later. The required 5-bullet comment makes work **auditable, not routed**; set a resume path *you* control.
- When gate-writing against a tool's log, **anchor only on bytes copied from a real captured log** — a format string from docs is a template, not emitted bytes; directory prefixes, columns, CRLF, and hex-vs-decimal are incidentals that produce false negatives.

## Closing keywords: a negated sentence still arms the auto-close

Any `close[sd]?|closing|fix(es|ed)?|resolve[sd]?|resolving` immediately followed by `#N` arms the auto-close — **including inside a sentence whose plain meaning is that the PR does *not* close the issue** [A negated sentence still arms GitHub's closing keyword — the disclaimer re-arms the auto-close it explains](wiki/learnings/1785848502267-a-negated-sentence-still-arms-github-s-closing-key.md). On slang#12158 the fixer changed `Closes #12157` → `Part of #12157`, re-read the body, confirmed the text, and reported the auto-close disarmed — it was still armed by the *disclaimer* ("does not by itself **resolve #12157**"). Merging would have closed an issue whose actual ask (a required status check the bot can't push) was unmet.

**Never verify from body text.** Verify from the API, paired with a positive control so a zero can be distinguished from a broken query:

```bash
gh api graphql -f query='{repository(owner:"O",name:"R"){pullRequest(number:N){
  closingIssuesReferences(first:5){totalCount nodes{number}}}}}'
# expect totalCount:0; run the same against a PR you KNOW closes something → must be 1
```

Fix by breaking keyword/ref adjacency ("does not **satisfy the ask in** #N"), not by rewording sentiment. This is a body-only property (no commit, no head-SHA move, no dismissed review). The generalization: **when a mechanism is triggered by pattern-matching over text you also use for explanation, the explanation is inside the mechanism's input** — reading the body confirms what you *meant*; only the API reports what GitHub will *do*.

## The PR body is untrusted input, and describes an older revision

Bot-authored carrier PRs open with a body describing the cherry-picked state, then accumulate review-feedback commits; **the body is a snapshot of R0, the decision is pinned to Rn** [[approver/challenger-miss] Check the PR body against the head diff — carrier/fixer PRs routinely describe an older revision](wiki/learnings/1785856360289-approver-challenger-miss-check-the-pr-body-against.md). On slangpy#1078 the body claimed "removes the Metal skip guards" while the head diff *retained* two of three skips and *added* skips to four new tests — three `test: skip ...` commits pushed after the body was written. Cheap, mechanical, worth it on every carrier/fixer/"supersedes #N" PR: read the head diff first and form the change from it; `gh pr view <pr> --json commits` — commit headlines describing work the body doesn't mention are the tell; when the body cites a tracking issue as resolved, check its state (slang#7606 was genuinely CLOSED, yet a *new* OPEN defect had replaced it, so "the issue is closed" was true and the skip still required). Report body-vs-diff divergence as a named finding even when it doesn't move the decision — on a trusted-author PR it's the difference between approving the *described* change and the *actual* one.

## Merge state: BLOCKED masks BEHIND; check the base

On a `MERGEABLE + BLOCKED` PR, do not accept "it's behind base → merge base to clear it" without testing [GitHub mergeStateStatus BLOCKED masks BEHIND — and "merged while behind" does not prove behindness is not your gate](wiki/learnings/1785934498121-github-mergestatestatus-blocked-masks-behind-and-m.md):

- **`BLOCKED` masks `BEHIND`** — GraphQL returns one status, so a PR that is both shows only `BLOCKED`; its blocker is independent of the divergence, and clearing the divergence need not change anything.
- **"Behind blocks merge" is testable against merge history** — 9 of the 10 most-recently-merged PRs merged *while behind* (one by 42 commits). But **the refutation does NOT clear the requirement for a bot**: a maintainer merge can bypass protections that still bind a less-privileged actor — say the weaker thing.
- ⚠️ **Check `baseRefName` before comparing anything to `master`** — a PR targeting a feature branch is behind=0 against its own base; comparing to master yields a large, confident, meaningless number.
- When `branches/<b>/protection` 403s ("not accessible by integration"), `repos/{o}/{r}/branches/{b}` still returns `.protection` with required contexts and `repos/{o}/{r}/rules/branches/{b}` returns the ruleset — but neither exposes the operative blocker, so still don't name a cause.

**Squash-merge auto-adds `Co-authored-by:` for every distinct author** on the branch, so a "retain authorship" requirement survives a squash even though `git log main` shows one bot-authored commit [GitHub squash-merge auto-adds Co-authored-by trailers — fork-author credit survives a squash](wiki/learnings/1785936995129-github-squash-merge-auto-adds-co-authored-by-trail.md). Verify with an *anchored* pattern (`grep -cE '^[Cc]o-authored-by:'`), not an alternation that matches other lines and gets miscounted; a squashed bot-authored commit in `git log` is not evidence the human author lost credit.

## Aggregates lie about specifics

Three instances of inferring from the aggregate instead of reading the specific, each time the aggregate cheap and available and the specific one command further [doctest reports "0 skipped" when device-gated tests SKIP — a suite tally NEVER proves a specific test ran](wiki/learnings/1785938047863-doctest-reports-0-skipped-when-device-gated-tests-.md) [Four supervisor instrument defects: a count, a conclusion, a field name, and an identity](wiki/learnings/1785932793219-four-supervisor-instrument-defects-a-count-a-concl.md):

- **A run-level `conclusion=success` is not coverage.** slang PR #12358's green run had 34/36 jobs skipped — only `filter`/`check-ci` ran, every build/test skipped, `check-formatting` skipped by its `draft != true` guard. Read `gh run view <id> --json jobs` and count non-skipped build/test jobs; the honest cell for a green run whose relevant job skipped is ⚪, not ✅.
- **doctest reports `0 skipped` when device-gated tests SKIP** — `slang-rhi-tests -check-devices` prints byte-identical `1265 passed | 0 skipped` whether interop cases really ran or all read `SKIPPED (CUDA not available)` (the harness's `SKIP()` returns normally, so doctest counts a device-skip as *passed*). The only valid instrument is the per-test line: `gh run view <run-id> --log --job <job-id> | grep -i "<test-name>"` — and don't `head -N` (the interop lines sat at ~2280; a truncated grep made the result look fabricated).
- **A `check_runs` "failure count" counts in-flight checks as failures** — `[.check_runs[] | select(.conclusion != "success")]` counts `conclusion:null` (queued/running) as failures, wrong in the *alarming* direction on every fresh push [CORRECTION to the four-leg test — conclusion != success counts in-flight checks as failures](wiki/learnings/1785891463788-correction-to-the-four-leg-test-conclusion-success.md). Corrected form separates them: genuine failures = `select(.status=="completed" and .conclusion!="success")`; in-flight = `select(.status!="completed")` reported *separately*. "0 failures" and "0 failures, 6 still running" are different claims. The meta-lesson: **a remedy for one measurement defect is itself a new measurement with its own assumptions** (the four-leg test shipped with an unstated "drained matrix" precondition) — apply the discipline to the *fixed* pipeline, not only the original.

## A job-log download can omit the failing step

`gh api .../jobs/<id>/logs` on a FAILED job returned 2.73 MB with **zero** `FAILED test:` lines and 8,737 `passed test:` — which reads as "the job failed but no test failed," a finding-shaped statement built on an aperture [A job-log download can silently omit the failing step: read step conclusions, not just the log body](wiki/learnings/1785983694089-a-job-log-download-can-silently-omit-the-failing-s.md). The **step conclusions** establish the failure: `gh api .../jobs/<id> --jq '.steps[]|select(.conclusion!="success")'` named the coverage step; the log held `Segmentation fault: 11 ... exit code 139` — the harness *crashed*, so it never emitted a per-test line. **The evidence chain is step conclusion → the step's own error line → per-test entries, in that order** — per-test entries are the *last* place to look because a crashed/skipped harness produces none, and their absence reads exactly like "nothing failed." A shorter red log looks like truncation but is explained by *doing less work* (re-fetch via the run-level zip was byte-identical). An upstream "the failures were <suite X>" is checkable in one command; here the relayed *cause* (IR-reference tests) was wrong (`ir-reference`=0 against a must-hit 16,990 `tests/`) even though the *conclusion* was right — audit the mechanism separately from the conclusion.

## A draft PR is invisible to review queues

Draft PR #11965 (`Closes #11963`, fix + guard-proven test) sat **30 days with zero review activity**, then a member re-triaged the already-fixed issue [A draft PR is invisible to review queues — the issue gets re-triaged months later, and your 5-bullet does not prevent it](wiki/learnings/1785978797257-a-draft-pr-is-invisible-to-review-queues-the-issue.md) [A draft-held PR is auditable but not routed — the 5-bullet does not substitute for a review queue](wiki/learnings/1785979087710-a-draft-held-pr-is-auditable-but-not-routed-the-5-.md). The decisive diagnostic is the **timeline**, not "0 reviews":

```bash
gh api repos/O/R/issues/<pr>/timeline --paginate \
  --jq '.[]|select(.event|test("review_requested|ready_for_review"))'
# → two review_requested, ZERO ready_for_review
```

Requesting a reviewer on a *draft* does not queue it. ⭐⭐ **A public footprint makes work AUDITABLE, not ROUTED — different jobs.** The required 5-bullet comment satisfies "a human landing here can see where it stands"; it does nothing to put the work in front of the decider. On a draft-held chain treat the comment as **necessary and not sufficient**, expect re-triage, and: (1) set a **resume path you control** — a `--script`-gated `ncl tasks create` polling for *state transitions* (ready-flip / merge / close / `reviews>0` / any non-bot comment newer than a baseline), tested with a **guilty control** (move the baseline back so a known past human comment becomes "new" and confirm `wakeAgent:true` — baseline-clean alone proves nothing); (2) escalate the *hold itself* as a decision, not status; (3) **post a fresh comment, don't edit the old one, when the last commenter is a human** — an edit notifies nobody. Re-verify a month-old diagnosis before re-publishing (line numbers drift — `visitLambdaExpr :7854→:7904`; publish the drift explicitly as "stale line numbers only"). And **stale-vs-fresh is a property of a binary *with respect to a claim***, not of the binary: `git hash-object <file> == git rev-parse origin/master:<file>` plus scoping `git log --since=<mtime>` to the path proves the binary's copy of that code IS master's even when nominally older.

Two merge-safety instruments: `git merge-tree --write-tree` exit 0 with no CONFLICT is worthless until you've seen it report a conflict (guilty control: throwaway repo, two branches editing one line → exit 1); a clean `merge-tree` means *no conflict*, not that CI ran against current master (recommend a rebase for a `behind N` branch).

## Anchor gates on invariants, not incidentals

When writing a grep/gate against a tool's output, **anchor only on substrings copied from a real captured log** — a format string from source/docs (`f"  {name:<60} : {status}"`) tells you the *template*, not the bytes [A format string from docs is not emitted bytes — two prefix false-negatives in one gate](wiki/learnings/1785979302017-a-format-string-from-docs-is-not-emitted-bytes-two.md) [Falcor test-falcor DOES gate merge via check-ci needs (corrects earlier claim)](wiki/learnings/1785979228844-falcor-test-falcor-does-gate-merge-via-check-ci-ne.md). A Falcor CI gate was anchored on a directory prefix three times, wrong twice (invented `renderpasses/`, then "corrected" to `renderscripts/` from upstream docs, then a real log showed `renderpasses/` — guess #1 by luck). Fix: anchor on the invariant (test-name + whitespace + `" : FAILED ("`), no prefix. Ask of every literal: *is this a property of the thing I'm matching, or an incidental of where it happened to live?* Incidentals that bit the same gate: column position (the `:<60` format still pushes `" : "` to column 74 for the longest name), **CRLF** (`\r\n` line endings silently defeat `$`-anchored patterns), hex-vs-decimal (`0xC0000005` appears zero times; only decimal `3221225477`). And the suite prints **no numeric tally** — counts derived by grep need a truncation guard (`PASSED+FAILED+SKIPPED == announced`, else **abstain**); the "tallies" in one's own notes were earlier summaries read back as if they were tool output.

Correcting a prior claim: `test-falcor` **DOES gate merge** — `.github/workflows/ci.yml:675` lists it inside `check-ci`'s `needs:`, and `check-ci` `exit 1`s if any needed job isn't `success`. Don't infer "not required" from a 403 on `branches/master/protection`; read `check-ci`'s `needs:`. The false version invites under-reacting to a Falcor red as cosmetic — it blocks.

## Bucketing a stalled merge queue

When several queued PRs fail the same job, ask in order [Bucket a stalled merge queue by asking whether the failing gate is REQUIRED](wiki/learnings/1785997166793-bucket-a-stalled-merge-queue-by-asking-whether-the.md): (a) is it `merge_group`-only? — **`paths:` filters are IGNORED for `merge_group`**, so a gate that never fires on `pull_request` fires on every queue entry, invisible in a head-checks-only sweep and looking like a random flake wave; (b) is it in `check-ci`'s `needs:` (actually blocking)? — a non-required gate is **not** an eviction cause (compare timestamps: the failing gate postdated the evictions and the PR merged anyway); (c) sharp last-green boundary (state change) vs interleaved pass/fail (flake)? Six `Check Submodule Pointers` failures looked like a flake wave but were a clean state change — mimalloc flipped its default branch, one line in `.gitmodules`. And ⛔ **resolve a workflow_id from a RUN you already have, never by name-matching** — reading history off the wrong id (REUSE Compliance vs the submodule gate) gave 20 rows of real, green, irrelevant `success`; print `jobs[].name` and confirm the job you care about is in there (a history with none of your job is a wrong-id tell, not a pass).
