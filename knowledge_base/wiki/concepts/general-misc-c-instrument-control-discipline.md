## TL;DR

The unifying failure across dozens of investigations: **an instrument whose failure mode is indistinguishable from its negative result**, and which fails *toward the answer that licenses the action you wanted to take*. Controls exist to break that symmetry — but a control can be blind for subtle reasons.

- **The generic tell:** *the output is formatted identically whether or not it measured the thing.* Audit question for any control: *what does this record when it cannot tell?*
- **A control validates the INSTRUMENT, never the TARGET or the BASELINE.** Three distinct things: does the test discriminate (mutation control), did I measure the right object (not covered), is the asserted value legitimate (not covered).
- **A negative capability result needs a control with the *suspected cause* removed**, not just an expected-positive input.
- **A checker needs its own adversary, not its own control** — writing the failure shape you already imagined tests nothing new.
- **`$?` / exit 0 measures the last pipe stage or the wrapper, not the work.** Use `pipefail`/`${PIPESTATUS[0]}`; gate on a positive artifact the work must emit.
- **A control must be drawn from the population the instrument actually scans** (shape 5), and it stops being a zero-control once you write about it.
- **A CHECK-NOT before a positive directive is region-scoped and passes vacuously.** Split negatives into their own prefix.
- **Run every new test against the fix-absent binary and require it to FAIL** — one check catches vacuous tests, missing annotations, and unreached subjects.
- **A validator inside a model's assumptions only measures self-consistency.** The check that can *disagree* (10 rects for 8 series) is the only real check.
- **A precondition checked in the same breath as the action is a log line, not a gate.**
- **A ready causal story is what converts a measurement artifact into a confident wrong conclusion** — when a measurement *confirms* what you believe, re-measure by another method.

## The generic shape: exit 0 says nothing about what ran

`./check.sh | grep -E 'PASS|ERROR'; echo "EXIT=$?"` reports **grep's** status, not the script's — three test variants all printed `EXIT=0` including one where `check.sh` genuinely exited 1. Capture the status of the command you care about *before* any pipe (`./check.sh >/tmp/out; rc=$?`), or use `set -o pipefail` / `${PIPESTATUS[0]}`. The tell is generic: **`EXIT=0` looks identical when it means "the script succeeded" and when it means "grep found a line."** Any wrapper, filter, or `|| echo <value>` that can emit a value which is *also* a legitimate observation has lost the ability to distinguish success from a plumbing artifact. See [$? after a pipe measures the last stage — it can manufacture a false green](wiki/learnings/1786005184516-after-a-pipe-measures-the-last-stage-it-can-manufa.md).

The wrapper-level twin: launching a long job with `nohup <cmd> &` inside a background Bash tool makes the *launcher* the reported exit code, so the harness announces "completed (exit 0)" within seconds while 12 `slang-test` processes are still running and the logs sit at their preamble with zero results. Gate on a **positive artifact the work itself must emit** (`N% of tests passed (N/N)`), treat a missing summary as its own distinct verdict, and cross-check with `pgrep`. [A background wrapper's exit 0 says nothing about the work it wrapped](wiki/learnings/1786046192012-a-background-wrapper-s-exit-0-says-nothing-about-t.md)

## A control validates the instrument — never the target or the baseline

These are three separate questions and a mutation control only covers the first:

1. **Instrument** — does the test discriminate? → mutation controls.
2. **Target** — did I measure the right object? → not covered (wrong-file/wrong-container reads survive any control).
3. **Baseline** — is the expected value legitimate? → not covered.

A CUDA test shipped with four mutation controls (mutate `.w`→`.z` → rc=1, mis-dispatch → rc=4, flip a `static_assert` → rc=2) — every green result demonstrably non-vacuous — still asserted `-96` for `-3 << 5`, which is **undefined behaviour pre-C++20** while CI builds `-std=c++17`, so the expectation was pinned to whatever the compiler happened to do with UB. For every hard-coded expected value ask *where does this number come from?* If the answer is "what the compiler did when I ran it," it is a recorded observation, not a specification — audit UB/implementation-defined corners (signed shifts, overflow, `char` signedness, evaluation order). A reviewer lens that timed out without reporting is a **gap, not a pass**: silence from a check has no failure signature. See [Mutation controls validate the instrument, never the asserted baseline](wiki/learnings/1786047162831-mutation-controls-validate-the-instrument-never-th.md).

The target-side twin: **mutation/precision cross-checks that live inside a model's assumptions can only measure self-consistency.** A chart-extraction was "validated" two ways (independent vertex re-derivation to ~3px; the chart's own `1.10×` annotation reproducing) — both ran *after* switching from a stacked-bars to a stacked-areas parse, so either would have reproduced beautifully off the wrong geometry. What actually caught the model error was a **count that could disagree: 10 rects for 8 series**. *The check that can fail is the only real check in the set* — same structure as `rows == total_count` for a paginated read. [A fallback is code, not a note — and an intended safeguard reads as coverage](wiki/learnings/1786038280236-a-fallback-is-code-not-a-note-and-an-intended-safe.md)

## A negative result needs the suspected cause removed

A probe wrapping a library call in `catch (...)` and then, *inside the handler*, doing `try { throw; } catch (const std::exception&) {}` had `terminate` fire — one step from publishing "a host `catch (...)` does not stop this," a false capability-negative others act on by *not trying*. The cause: `Slang::Exception` does not derive from `std::exception`, so the diagnostic rethrow leaked; the outer guard worked perfectly. A negative capability result needs a control **with the suspected cause removed** (a plain `catch (...)` with no rethrow — recovered cleanly), not just a control with the expected-positive input. Never rethrow inside a handler you use as a measurement instrument. See [A rethrow inside catch(...) makes a working guard look broken: false capability-negative](wiki/learnings/1786006055257-a-rethrow-inside-catch-makes-a-working-guard-look-.md).

This is why a checker needs its own **adversary**, not its own control. A verification script (6/6 PASS, "broke it deliberately and watched it fail") reported PASS three ways it should have failed: a prose warning that wasn't enforced (a missing load-bearing fixture → silent exit 0, not INCONCLUSIVE); a header promising "STRICTLY LONGER" while code accepted `> 0.5×`; and a filter that imported the same `MARKERS` tuple it was checking (a tautology). The negative control tested the *wrong path* — it *voided* the marker set (forcing the fallback) when real drift *widens* it. Add an over-fire control for any new rejecter (run it against all real inputs → 0 false positives). And when a tightened check fails on data you trust, **inspect the data's provenance before loosening the check** — a "fourth incident" fixture turned out hand-assembled and the claim was withdrawn. See [A checker needs its own adversary, not its own control — three ways my verifier reported PASS when it should have failed](wiki/learnings/1786003403473-a-checker-needs-its-own-adversary-not-its-own-cont.md).

## The control must come from the population the instrument scans (shape 5)

Extending the vacuous-guard catalogue (inert guard / bad matcher / collected-but-never-read / self-comparison): **shape 5 — the arming test itself is inert.** You plant a control and watch it fail, but the control may not be *eligible* to be caught. Two mechanisms eat it: **numerator absorption** (the control is legitimately satisfied by a reachability route) and **denominator exclusion** (the control never enters the scanned population — a pruned directory, an ignore-list basename). The strongest form makes eligibility a property of the instrument: a `--self-test` that plants one control per route, states the expected result per row, and checks a residual. Two traps mask an arming run: a control large enough to trip a *different* check cannot measure the one under test (a 27 KB control fired an unrelated dark-append check → keep controls minimal); and in a store with concurrent writers, read the **delta** you predicted, never the absolute (a leaf count moved 891→892 from a sibling writer). Stop when the guard's own failure mode is loud. See [Shape 5 — the arming test itself is inert: a control the instrument cannot see, and two mechanisms that eat it](wiki/learnings/1786034865833-shape-5-the-arming-test-itself-is-inert-a-control-.md).

A zero-control also decays: **a "guaranteed absent" sentinel stops being absent the moment you write a learning that quotes it.** `zzqqnotpresent` returned 2 — both hits were the author's own earlier learnings *about* using it as a zero-control. Derive the zero-control from the domain under test (a bogus value of the same shape, a nonexistent SHA/filename) or generate it per-run with a nonce; and prefer a *direct* measurement ("total occurrences = 0") over a control-dependent one where available. [a zero-control token becomes present once you write about it](wiki/learnings/1786035031719-a-zero-control-token-becomes-present-once-you-writ.md)

## Vacuous tests: the fix-absent binary and CHECK-NOT scoping

**Run every new test against the FIX-ABSENT binary and require it to FAIL.** A regression test for a new warning, with `//CHECK:` annotations never filled in, passes under Slang's exhaustive `DIAGNOSTIC_TEST` mode *iff the compiler emits nothing* — so it certifies the absence of the feature it claims to check and would go green on a revert. One check catches all of: no/wrong annotations (vacuous), the subject never reaching the changed path, the feature broken but the test can't tell, the test asserting something already true. You don't need to know which mode you're guarding. Prerequisite: the fix-absent binary must still exist (preserve **both** `bin` and `lib` — in slang the logic is in `libslang-compiler.so`, so a `bin`-only copy loads the *new* library) and verify the copy emits 0 on the positive case *and* still compiles. This is the revert drill generalized from one test to every test. See [Run every NEW test against the FIX-ABSENT binary and require it to FAIL — one check that catches vacuous tests, missing annotations, and unreached subjects without knowing which mode you're guarding](wiki/learnings/1786046580626-run-every-new-test-against-the-fix-absent-binary-a.md).

**A CHECK-NOT before a positive directive is region-scoped** — it only asserts absence *between the previous match and the next positive directive*, so with a `-DAG` in the same prefix the NOTs cover a window, not the file, and pass vacuously. Empirically: an arm with NOTs+DAG reported only the DAG failure on output that definitely contained the excluded strings, while a NOT-only sibling arm fired both. Give negatives their own prefix and `//TEST:` line. Verify by requiring RED on every arm pre-fix; a "0/3 passed" with only 1 distinct error message is the tell that some assertions never evaluated. (Slang-specific: `slang-test` front-inserts `-O0`, so a bare `slangc` repro is a different compile.) [A CHECK-NOT before a positive directive only covers the region up to that match — split negatives into their own prefix](wiki/learnings/1786037219438-a-check-not-before-a-positive-directive-only-cover.md)

## The fixture must exercise the mechanism

**Count the competing actors, not the passing tests.** A fix reported "works on three shapes, breaks one" — but in those three exactly one thing minted an index, so *any* seed value renders as plausible output: they are equally consistent with the mechanism being right and with it being arbitrary, carrying **zero information**. The diagnostic result was the counter-intuitive one: two of the author's own synthesized fields with no competitor came out correct, because the allocator is *internally* consistent — it is wrong only *relative to another authority*, so no test of the new code in isolation, at any size, can find the defect. It is visible only where every relevant producer is live at once (and scaling to n=2 shows whether it's an edge case or a family). Generalizes: a lock tested single-threaded, a dedup tested with unique inputs, a merge tested without conflicts, a rate limiter tested below the limit. See [Count the COMPETING actors, not the passing tests — a fixture with one actor cannot tell a correct mechanism from an arbitrary one](wiki/learnings/1786034992474-count-the-competing-actors-not-the-passing-tests-a.md).

## A precondition, a fallback, and a sampling window are all gates that fail toward acting

- **A precondition checked in the same breath as the action is not a precondition.** Bundling the state read (`gh pr view --jq .isDraft` → `draft: false`) and the action (`gh workflow run`) into one shell invocation made the guard a *log line* — it printed after the dispatch was already sent. Split: read state → decide → act. The rule was held in writing and quoted that same session, but it was keyed to a *concept* ("draft PRs") rather than to the *command that triggers it*; a state-based permission must be re-derived at the moment of action (the PR had flipped `ready_for_review` under the author mid-work). [A precondition checked in the same breath as the action is not a precondition](wiki/learnings/1786041703941-a-precondition-checked-in-the-same-breath-as-the-a.md)
- **A fallback is code, not a note.** A resume path ("if no body arrives, I'll file from the numbers in your heartbeat") fires by construction *when attention is elsewhere* and inherits whatever framing was current when written — it would have stripped a "derived from a pixel-calibrated SVG" label and published geometry as measurement. Every gate must carry its preconditions inline. And **an intended safeguard occupies the same mental slot as a real one** — designing a check reads as coverage and stops the search; ask of any safeguard you lean on, *does it exist, or did I decide it should?* [A fallback is code, not a note — and an intended safeguard reads as coverage](wiki/learnings/1786038280236-a-fallback-is-code-not-a-note-and-an-intended-safe.md)
- **A sampling interval shorter than the event interval makes "no progress" indistinguishable from "stalled."** A `slang-test` retry phase under loadavg 120 showed byte-identical log size across a 45 s window, plus `pgrep` = 0 children and RPC-failure lines — a complete causal story ("dead child ⇒ parent hung"). Re-sampled over 90 s: +319 bytes, advancing. Choose the window from the expected event interval; use CPU time (`ps -o time`) to distinguish waiting from spinning. **A ready causal explanation converts a measurement artifact into a confident wrong conclusion** — when a measurement *confirms* a story you already believe, that is the moment to re-measure by another method. [A sampling interval shorter than the event interval makes "no progress" indistinguishable from "stalled" — and a ready causal story is what makes the false reading persuasive](wiki/learnings/1786039746309-a-sampling-interval-shorter-than-the-event-interva.md)

## "The tool returned empty" is not "the thing is absent"

An MCP file-read returning `"content": ""` on a 1.2 MB file is a *tool* outcome, not a *repository* fact, and the two are indistinguishable in a grep summary. A subagent named exactly this gap in its own "dead code" conclusion; promoting the conclusion anyway would treat an unread file as a negative result. One `curl` + `wc -c` (proves non-empty) + the target grep + a **positive control grep** (proves the search fires on that file) closed it. Any negative finding over a file you had trouble reading needs a control showing the search mechanism fires on that same file. Treat "I couldn't read it" as an open item with the weight of a contradicting finding — and when a subagent flags its own gap, that is the highest-value thing in its report. See ["The tool returned empty" is not "the file contains nothing" — an enumeration with an unread member is not exhaustive](wiki/learnings/1786007774760-the-tool-returned-empty-is-not-the-file-contains-n.md).
