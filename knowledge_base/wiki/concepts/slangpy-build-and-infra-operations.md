# SlangPy Build from Source, Infra/Ops, downstream_args, and slangpy-samples Review

Operational knowledge for building SlangPy (native extension and the full C++ `sgl` layer) in the fixer container, the prod coworker-group infra layout, the `downstream_args` → downstream-compiler plumbing (#1058 / PR #1061), and reviewing the slangpy-samples repo family (PR #53).

## TL;DR
- **Building slangpy needs `python3-dev`/`python3.11-dev` and `--break-system-packages` on every pip call (PEP-668)** — `tools/ci.py install-slangpy-torch` fails because its internal `pip install wheel` omits the flag; nvcc is NOT required; pip site-packages reset on container rebuild; an ENOSPC-interrupted submodule needs `git submodule update --init --force --recursive`.
- **The full C++ `sgl` build requires the `data` submodule whose two fonts are git-LFS** — without git-lfs you get ~131-byte pointer stubs and ninja dies on `Inconsolata-Regular.ttf` before any source compiles. Verify byte sizes (Montserrat 197624 B, Inconsolata 101752 B), not mere existence.
- **A stubgen (`numpy`/`libcst`) failure aborts ninja BEFORE the `sgl_tests` link — a FALSE GREEN where a stale binary "passes" against pre-change code** (observed 10 days older than HEAD). Build `--target sgl_tests` explicitly and require both `sgl_tests` and `libsgl.so` mtimes newer than a pre-build `date` stamp; a fresh `.o` is not sufficient.
- **A local full `pytest slangpy/tests` has ~50 environmental failures** (bitmap/DDS/texture-loader tests reading git-lfs pointer files), and the main checkout's native `.so` is often older than its Python sources — compare `build/linux-gcc/git_version/git_version.h` with `git log -1` before using it as a baseline.
- **`downstream_args` reach only DXC (d3d12) and NVRTC (cuda), silently dropped elsewhere** — Vulkan/Metal/WGPU/CPU have no consuming downstream compiler; `floating_point_mode` is a first-class Slang option and a different mechanism.
- **NVRTC/CUDA downstream compilation is deferred to the first `kernel.dispatch(...)`, so a test stopping at `create_compute_kernel` never runs NVRTC** — dispatch with a real output buffer and expect `RuntimeError` (not `SlangCompileError`).
- **Editing a `///` docstring on a `SlangCompilerOptions` field in `shader.h` does NOT reach Python users** — Python docstrings come from the checked-in generated `src/slangpy_ext/py_doc.h`; a review catches the desync if only `shader.h` is edited.
- **On slangpy-samples, MDL material `.slang` files are generated/vendored — do NOT hand-review them**; verify LFS objects actually resolve (dangling pointer = non-runnable sample) and that examples→experiments renames lose no test coverage.
- **Agent containers have an NVIDIA L40S** (CUDA + NVIDIA Vulkan), and compute/Vulkan `cooperative_matrix` runs on it; the 2026-09-28→10-16 no-GPU window was a host passthrough outage, now fixed. Measure each session rather than calling the environment "GPU-less" or "GPU-ful" from a doc. Cooperative-VECTOR did not run on driver 565.x, which lacks `VK_NV_cooperative_vector`, and coop-vec kernels still COMPILE (slangc exit 0), so compile-only checks give false confidence — dispatch is where it dies.
- **Autodiff `.bwds()` repros run GPU-free on `DeviceType.cpu`** once the #1136 dispatch fix is in, but the cpp target cannot emit `InterlockedAddF32`: patch `atomics.slang` in a private package copy (single-thread repros only). To check another Slang pin, dump the generated kernel and compile it statically to HLSL with a matching `slangc`, under `timeout`.
- **Re-probe the GPU every session before writing "CPU only"**: `nvidia-smi -L` plus a `spy.Device(type=spy.DeviceType.<vulkan|cpu|cuda>)` loop. A carried "no GPU" note goes stale (it did after the 09-28→10-16 outage) and weakens a public verdict; a GPU that is really missing is an infra report, not a property of the environment. Bookworm lavapipe is not a fallback (slang-rhi always requests `VK_KHR_shader_non_semantic_info`, which it lacks), and a build dir configured with the GPU caches a `libcuda.so` path that breaks ninja once the driver is gone.
- **On prod, the 6 slang/slangpy coworker group dirs are symlinks into `/ephemeral`** — only untracked, gitignored coworker dirs are safe to symlink; move only while containers are STOPPED.
- **`PATCH` of an existing bot issue comment 403s on slangpy-samples while `POST` works** — design status updates as append-only fresh comments.
- **No root and no `python3-dev`? `apt-get download` + `dpkg -x` into `/tmp` and point `CPATH`/`Python_INCLUDE_DIR` at it**; build only `--target slangpy_ext` (~90 s), and copy the vcpkg binary into fresh worktrees.

## Building SlangPy from Source (Fixer Container)

Building the slangpy native extension on a linux-gcc Ninja Multi-Config box (recorded while an L40S was present; the build steps themselves don't need a GPU):

- **Needs `python3-dev`/`python3.11-dev`** (admin `install_packages` apt). Without it, CMake `find_package(Python ... Development.Module)` fails. nvcc is NOT required (CUDA backend uses the driver API at runtime).
- **PEP-668:** every `pip install` needs `--break-system-packages`. `python3 tools/ci.py install-slangpy-torch` fails because its internal `pip install wheel` omits the flag — install the torch bridge manually: `pip install --break-system-packages wheel && pip install --break-system-packages --no-build-isolation ./src/slangpy_torch`.
- **After a container rebuild**, the image's pip site-packages reset — reinstall `requirements-dev.txt` with `--break-system-packages`. The `/workspace` worktree persists across rebuild; pip packages do not.
- **Interrupted (ENOSPC) submodule checkout** leaves a gitlink with an empty working tree that `git submodule update --init` skips. Fix: `git submodule update --init --force --recursive`.
- **Build only `slangpy_ext`** (`cmake --build build/linux-gcc --config Release --target slangpy_ext`, ~304 steps) to skip heavy C++ test/example binaries. `build/buildtrees` (vcpkg intermediates) is regenerable — safe to `rm -rf` after configure to reclaim ~765MB. [Building slangpy from source in the fixer container: python3-dev, PEP-668, torch bridge, submodule/ENOSPC gotchas](../learnings/1782324519820-building-slangpy-from-source-in-the-fixer-containe.md)

Building the full C++ `sgl` layer (linux-gcc-debug, e.g. for the doctest `sgl_tests` / profiler suite) adds two non-obvious deps: the `data` git submodule (`slangpy-data.git`) is a REQUIRED unconditional PUBLIC link dep via `cmrc_add_resource_library(sgl_data ...)`, and its two fonts are git-LFS files — with git-lfs absent the checkout holds only ~131-byte pointer stubs, so ninja fails on `Inconsolata-Regular.ttf` BEFORE any source compiles (an INFRA gap, not your code); init without the smudge filter (`git -c filter.lfs.smudge= submodule update --init data`) then fetch the real binaries via GitHub's LFS batch API and verify with `file *.ttf` / byte sizes (Montserrat 197624 B, Inconsolata 101752 B), not mere existence [SlangPy C++ build needs data submodule + LFS fonts (git-lfs absent)](../learnings/1784867803689-slangpy-c-build-needs-data-submodule-lfs-fonts-git.md). The final `.pyi` stubgen targets (nanobind stubgen + `tools/postprocess_stub.py`) then import the built module and need `numpy`+`libcst` (`pip install --user --break-system-packages numpy libcst`) — but they run AFTER all C++ link succeeds, so a `ModuleNotFoundError` there means the binaries (libsgl.so + sgl_tests) are already built [SlangPy C++ build needs the `data` LFS submodule + numpy/libcst for stubgen](../learnings/1784868284126-slangpy-c-build-needs-the-data-lfs-submodule-numpy.md).

**CORRECTION to that reassurance — the stubgen failure is a FALSE-GREEN trap for `sgl_tests`.** "It runs after all C++ link succeeds" holds for `libsgl.so`, but **not** for the test binary: without `numpy`/`libcst`, `cmake --build --preset linux-gcc-debug` fails at the `.pyi` stub step and **aborts ninja BEFORE the `sgl_tests` link**. So your changes compile (`profiler.cpp.o` is fresh), `sgl_tests` is never relinked, the *old* binary stays on disk, and running it "passes" — against pre-change code. That is worse than a plain build failure, because the build looks like it hit only the known-ignorable error while the tests silently exercise stale code (observed concretely: an `sgl_tests` binary **10 days older than HEAD** still passing the very tests a fix was supposed to change). Fix: build the test target explicitly so the link happens before the stub step can abort the graph — `cmake --build --preset linux-gcc-debug --target sgl_tests` — and since `sgl_tests` links `libsgl.so` dynamically, make sure the `sgl` target relinked too. **Mandatory check before trusting ANY test number:** stamp `date '+%F %T'` before the build, then `ls -l --time-style=full-iso build/linux-gcc/Debug/sgl_tests build/linux-gcc/Debug/libsgl.so` and require **both** mtimes newer than the baseline; if not, you have no valid binary and must not report results. Checking the `.o` is not sufficient — the object can be fresh while the executable is stale. (Companion facts: the pre-existing full-suite failures in this environment are the 5 Git-LFS fixture cases — 3 in `test_dds_file.cpp`, 2 in `test_texture_loader.cpp` — from unmaterialized LFS pointer stubs, not regressions; and grepping doctest output for failing test names can surface `platform/environment`, which merely prints a `MESSAGE` header and passes in isolation.) ([stubgen failure aborts ninja before linking `sgl_tests` — use `--target sgl_tests` and verify mtimes](../learnings/1785774319630-slangpy-stubgen-failure-aborts-ninja-before-linkin.md))


For a small C++ change confined to ONE translation unit (e.g. a one-liner in `src/sgl/app/app.cpp`), you do NOT need a 20-min fresh `cmake` build in the worktree to prove it compiles — the main checkout already has a configured build with `build/pip/compile_commands.json`. Parse it, find the entry whose `file` ends with your changed source AND whose `output` is under the intended library's `.dir` (e.g. `sgl.dir`, not `slangpy_ext.dir` — the same source compiles into multiple targets), reuse that entry's exact `command` flags but (1) swap the input path to your worktree copy, (2) drop `-c`/`-o`, (3) add `-fsyntax-only`, and (4) `cd` to the entry's `directory` so relative `-I` resolve. That gives real compiler proof (full `-std=gnu++20 -Werror` + include/define set) in seconds, writing nothing to disk; delegate it to a subagent to keep build noise out of context. `-fsyntax-only` won't catch link errors, but for adding a defaulted arg to an existing overload (type-checked at the call site) it's conclusive — and GLFW/AppWindow code can't be unit-tested here anyway (`glfwInit` fails with empty `DISPLAY`), so cursor/window fixes are compile-only + manual verify ([fast compile-verify a single-TU C++ change via compile_commands.json — no full rebuild](../learnings/1789819901846-fast-compile-verify-a-single-tu-c-change-via-compi.md)).

### Verifying a Pure-Python Change Locally Without a GPU or Native Rebuild
A **pure-Python** SlangPy fix verifies end-to-end locally with no GPU and no native build. Use the prebuilt venv `/workspace/agent/slangpy-main-build-venv/bin/python` (has `numpy`; `pip install -q pytest` into it is fine and ephemeral) — but its `slangpy` lives in site-packages, so put your checkout FIRST on `PYTHONPATH` to test edited source (confirm `spy.__file__` points where you expect). `spy.DeviceType.cpu` works fully headless and exercises the functional API (`Tensor.from_numpy`, dispatch, etc.); `spy.Device(type=vulkan/cuda)` also *constructs* in-container — enough for tests whose failure is at Slang-session module resolution BEFORE any GPU dispatch (those pass locally without a real GPU). To run a git **worktree**'s source (worktrees lack build artifacts), copy the one gitignored native module across: `cp /workspace/agent/slangpy/slangpy/*.so <worktree>/slangpy/` (it is `slangpy_ext.cpython-311-*.so`) then `PYTHONPATH=<worktree> <venv>/python -m pytest ...`. Tests parametrize `@pytest.mark.parametrize("device_type", helpers.DEFAULT_DEVICE_TYPES)` (linux → `[vulkan, cuda]`; no test uses `cpu`), and `helpers.get_device` injects `[caller_module_path, SLANG_PATH]` include paths. Concrete win: slangpy#1177's raw-`Device()` SHADER_PATH fix (PR #1178) was reproduced pre-fix on the CPU device and re-verified with 8 pytest cases (incl. vulkan/cuda parametrizations) green — zero native builds ([test pure-Python SlangPy changes locally without a GPU (CPU backend + worktree .so)](../learnings/1790023108329-test-pure-python-slangpy-changes-locally-without-a.md)).

### Local Full-Suite pytest: Known Environmental Failures and the Stale Main-Checkout `.so`
Know three environment facts before you call a local `pytest slangpy/tests` result a regression. (1) The venv `/workspace/agent/slangpy-main-build-venv` lacks `deepdiff` (and pytest-timeout, pytest-xdist, imageio), so collection aborts on `test_declrefs.py` and `test_shapes.py`. Without touching the venv: `pip install --target /tmp/deps deepdiff imageio`, delete the numpy pip pulls into `/tmp/deps` (it would shadow the venv's), and add `/tmp/deps` to `PYTHONPATH`. (2) About 50 failures are git-lfs pointer files, not regressions: 51 of 53 files in `data/test_images/` are 130-byte pointers and git-lfs is not installed, so `test_bitmap.py` (png_read_bit_depth, dds_read, dds_detect_format), `test_bc_codec.py::test_load_and_decode_dds` and every `test_texture_loader.py` variant fail with "Unknown file format!", "DDS file has invalid header", "Unsupported source image type" or "Unsupported bitmap metadata format unknown". The expected tally on an L40S with vulkan+cuda is about 3633 passed / 50 failed / 599 skipped. In a worktree, copy real files from the main checkout's `data/` if you need them; the copy step in build scripts fixes only files the main checkout has materialized. (3) The main checkout's native module is often older than its Python sources, so it is no baseline until rebuilt. In the fixer container, `/workspace/agent/slangpy` sat at e7bb2242 with a `slangpy_ext` `.so` built Sep 22 from older source; HEAD's `slangpy/__init__.py` calls `_set_default_slang_include_paths`, which that `.so` does not export, so pytest dies in conftest with a NameError. In the reviewer container the checkout had pr-1182 (13f50dc) checked out but `.so` and `build/linux-gcc/Debug` (Slang 2026.17.1) built from da8844f, so `spy.create_device(type=...)` failed with `TypeError: DeviceDesc.__init__ ... Invoked with types: slangpy.DeviceDesc, slangpy.DeviceDesc`. Always compare `build/linux-gcc/git_version/git_version.h` with `git log -1` before trusting a run. To test without touching the checkout, `git archive <built sha> slangpy | tar -x -C /tmp/x`, symlink the checkout's `slangpy_ext` `.so` into `/tmp/x/slangpy/`, copy `slangpy/.build_dir`, and run with `PYTHONPATH=/tmp/x` ([local pytest: 50 LFS failures, missing dev deps, stale main-checkout .so](../learnings/1792466857244-slangpy-local-pytest-50-bitmap-dds-texture-failure.md), [reviewer main checkout .so is stale vs Python sources](../learnings/1792484603209-slangpy-reviewer-main-checkout-native-so-is-stale-.md), [worktree LFS-pointer failures](../learnings/1792466654227-slangpy-tests-no-device-type-param-skipped-under-d.md)).

### Running Autodiff `.bwds()` Repros GPU-Free on the CPU Device
Functional-API autodiff repros (`.bwds()`) also run with no GPU, on `spy.Device(DeviceType.cpu)`, provided the build carries the #1136 zero-dispatch-groups fix (4bf28e5b or later); lavapipe is no alternative (see below). One more obstacle remains: the CPU (cpp) target cannot emit `InterlockedAddF32`, so every DiffTensor gradient kernel dies with E99999 "unexpected IR opcode" at `atomics.slang:37`. Work around it in a PRIVATE COPY of the package (tar the `slangpy/` dir and put the copy on `PYTHONPATH`), replacing that line with `__target_switch { case cpp: buf.Store(addr, asuint(asfloat(buf.Load(addr)) + value)); default: buf.InterlockedAddF32(addr, value); }`. The replacement is not atomic, so it is valid for single-thread repros only. To check the same kernel against a different Slang pin without rebuilding the extension, set `SLANGPY_PRINT_GENERATED_SHADERS=1`, save the generated kernel and the user module as `.slang` files, run `slangc k.slang -I . -I <that slangpy version's slangpy/slang> -target hlsl -entry compute_main -stage compute`, and grep the output for `InterlockedAdd` (gradient accumulation) and `_grad_in` reads. The shader sources must match the `slangc` version (4bf28e5b sources fail on 2026.18.3 with E30019), and each `slangc` call needs a `timeout` wrapper because some combinations hang. Used for slangpy#1204, the downstream of slang#13301 ([SlangPy autodiff repros run GPU-free on DeviceType.cpu with one atomics.slang patch; static slangc HLSL check for other Slang pins](../learnings/1791189869324-slangpy-autodiff-repros-run-gpu-free-on-devicetype.md)).

**Without root and without `python3-dev`.** The coworker container lacks `Python.h` and the libxinerama/libxcursor/libxi dev headers and has no sudo, but `apt-get download` plus `dpkg -x` works unprivileged: point apt at `/tmp` state (`-o Dir::State::Lists=/tmp/apt/lists -o Dir::Cache=/tmp/apt/cache -o Debug::NoLocking=1 update`, then `download libpython3.11-dev python3.11-dev libxinerama-dev libxcursor-dev libxi-dev libxinerama1 libxcursor1 libxi6 libxfixes-dev libxrender-dev`), extract the python debs to `/tmp/pyheaders` and the X11 ones to `/tmp/x11prefix`, export `CPATH=/tmp/pyheaders/usr/include:/tmp/x11prefix/usr/include` (pyconfig.h includes `<x86_64-linux-gnu/python3.11/pyconfig.h>`), and configure `cmake --preset linux-gcc -DPython_EXECUTABLE=<venv>/bin/python -DPython_INCLUDE_DIR=/tmp/pyheaders/usr/include/python3.11 -DCMAKE_INCLUDE_PATH=/tmp/x11prefix/usr/include -DCMAKE_LIBRARY_PATH=/tmp/x11prefix/usr/lib/x86_64-linux-gnu`. `/tmp` is wiped between sessions, so redo the extraction each time. A clean Release `slangpy_ext` build takes about 90 s on 64 cores [building SlangPy in a non-root container](../learnings/1792142268329-building-slangpy-in-a-non-root-coworker-container-.md).

**Fresh worktree, fast.** Init submodules offline with `git -c protocol.file.allow=always -c submodule.<path>.url=/workspace/agent/slangpy/.git/modules/<path> submodule update --init`, repeating for the nested `nanobind/ext/robin_map` and `nanothread/ext/cmake-defaults`; copy the gitignored `external/vcpkg/vcpkg` bootstrap binary and `build/linux-gcc/vcpkg_installed` from the main checkout to skip the vcpkg bootstrap and dependency build. Build `--target slangpy_ext` (`cmake --build --preset linux-gcc-release --target slangpy_ext`): the full build fails in `examples/tinybc` on a pre-existing GCC 12 `-Werror=restrict` false positive. The `.so` lands in `<worktree>/slangpy/`, so `PYTHONPATH=<worktree>` is all a run needs [fast fresh-main build in the triage container](../learnings/1792064521058-slangpy-fast-fresh-main-build-repro-in-the-triage-.md), [non-root build](../learnings/1792142268329-building-slangpy-in-a-non-root-coworker-container-.md). (The device notes in the first atom, "only `DeviceType.cpu` works", describe the 09-28→10-16 passthrough outage, not the fleet.)

## Infra / Operations

### Prod Coworker Group Dirs Symlinked to /ephemeral
On prod, the 6 slang/slangpy coworker group dirs (`groups/slang-fixer`, `groups/slang-triager`, `groups/slang-reviewer`, `groups/slangpy-fixer`, `groups/slangpy-triager`, `groups/slangpy-reviewer`) are symlinks into `/ephemeral/prod-groups/<name>` (the 251G `/dev/vdb`), not real dirs on the OS disk. `initGroupFilesystem` follows symlinks via `fs.existsSync`, so symlinked dirs are not re-created on wake. Only untracked, gitignored coworker dirs are safe to symlink — `groups/main/` has a git-tracked file and must remain a real dir. Move only while the group's containers are STOPPED. [Prod's 6 slang/slangpy coworker group dirs are symlinked to /ephemeral](../learnings/1780720000000-prod-coworker-groups-symlinked-to-ephemeral.md)

### Bot Cannot Edit Issue Comments on slangpy-samples
`PATCH` an existing issue comment (even one the bot itself authored) on `shader-slang/slangpy-samples` returns HTTP 403 "Must have admin rights to Repository." `POST` a new comment works. When refreshing a triage/status comment, post a fresh incremental comment carrying only the delta instead of PATCHing. Likely applies to other shader-slang repos the bot writes to with the same token scope — assume edit is unavailable until proven otherwise; design updates as append-only fresh comments. [slangpy-samples: editing bot issue comments 403s ('admin rights') — use fresh comments, not PATCH-in-place](../learnings/1781603959329-slangpy-samples-editing-bot-issue-comments-403s-ad.md)

### Re-Probe the GPU Every Session, and Lavapipe Is Not a Fallback
Fleet containers have an NVIDIA L40S with CUDA and NVIDIA Vulkan ([containers have an NVIDIA L40S](../learnings/1792133264162-coworker-containers-have-an-nvidia-l40s-gpu-cuda-vulkan.md)), but presence has not always been stable: from 2026-09-28 to 10-16 a host passthrough bug (nanoclaw's `detectGpuMode` in `src/drivers/index.ts` only adds `--gpus`/`--runtime=nvidia` when the host process has `ENABLE_GPU=1` in its real environment or `/usr/bin/nvidia-smi` exists) left the slangpy fixer and triager containers with no `/dev/nvidia*`, `nvidia-smi`, NVIDIA ICD or `libcuda` (slangpy#1181; [Agent containers have no GPU since ~2026-09-28 (historical: 09-28→10-16 outage)](../learnings/1792089571497-agent-containers-have-no-gpu-since-2026-09-28-host.md)). A "no GPU" note carried over from such a session goes stale and does damage: slangpy #163 and #126 triage memos said "the container has no GPU, so only CPU was verified", and the #126 public comment carried that caveat, yet the next day `nvidia-smi -L` showed the L40S and the #126 repro gave identical results on Vulkan and CUDA, so the comment had to be edited in place. Before writing "CPU only", run `nvidia-smi -L` and a three-line device probe that loops `spy.Device(type=spy.DeviceType.vulkan / cpu / cuda)` (it is `spy.DeviceType`; `create_device` does not exist on current main). To re-verify an old CPU repro cheaply, `sed s/DeviceType.cpu/DeviceType.vulkan/` over the script and rerun it with `PYTHONPATH=<built worktree>`. If the GPU really is missing, report it as an infra problem rather than presenting it as a property of the environment ([slangpy triage: re-probe the GPU every session](../learnings/1792136253471-slangpy-triage-re-probe-the-gpu-every-session-a-no.md)). Debian bookworm's Mesa lavapipe (`mesa-vulkan-drivers` 22.3.6, llvmpipe on LLVM 15) cannot stand in for slangpy Vulkan work: slang-rhi pushes `VK_KHR_SHADER_NON_SEMANTIC_INFO_EXTENSION_NAME` unconditionally (`src/vulkan/vk-device.cpp:596`, pin `82c03494`) and this lavapipe does not expose it, so the loader rejects `vkCreateDevice` ("Device extension VK_KHR_shader_non_semantic_info not supported") and `spy.Device(type=vulkan)` raises "Failed to create device!" even though `enumerate_adapters` lists llvmpipe. The tempting "the crash is compile-time, so software Vulkan is fine" therefore needs a slang-rhi patch, and that patch changes the tested binary and possibly its emitted debug info. On any substitute hardware, run a positive control (the known-bad build must still reproduce) before trusting a negative. A Slang build dir configured while the GPU was present also caches `CUDA_cuda_driver_LIBRARY=/usr/lib/x86_64-linux-gnu/libcuda.so`; once the driver is gone ninja dies immediately with "libcuda.so, needed by libgfx.so, missing and no known rule to make it", so clear that cache entry or reconfigure before rebuilding. And when verifying that fix X resolved a CI failure, check the job log shows the test **PASSED**, because a skip or deselect is invisible at run level; use `gh run view <run> --job <id> --log`, since `gh api .../jobs/<id>/logs` refuses output containing escape sequences ([slangpy Vulkan tests can't use bookworm lavapipe; fleet GPU can vanish](../learnings/1790628362287-slangpy-vulkan-tests-can-t-use-debian-bookworm-lav.md), [lavapipe can't substitute for a GPU in SlangPy Vulkan tests](../learnings/1790628523920-lavapipe-can-t-substitute-for-a-gpu-in-slangpy-vul.md)).


## slangpy-samples Review: Vendored MDL, LFS Resolution, Zero-CI Experiments (PR #53)

Reusable facts for the slangpy-samples repo/PR family. MDL material `.slang` files (e.g. `mdl_ceramic_material.slang`, 3492 lines of Itanium-mangled machine-generated MDL target code) are vendored/generated -- do NOT hand-review them; only the tail hand-written `IMaterialInstance` wrapper (~190 lines) is glue. Verify LFS objects actually resolve (a dangling pointer = non-runnable sample): extract `oid`/`size` from the ~130-byte pointer files and POST to the repo's `info/lfs/objects/batch` endpoint -- `actions.download` present means the object exists. Zero CI is the norm for anything under `experiments/` (only `examples/` entries in `test_examples.py` get coverage), so an examples->experiments rename loses no coverage if the demo wasn't already a test entry -- check `git show main:tests/examples/test_examples.py` ([slangpy-samples utracer experiment (PR #53): MDL files are generated/vendored; verify LFS + rename cleanliness](../learnings/1783721228354-slangpy-samples-utracer-experiment-pr-53-mdl-files.md)). When verifying such PRs, measure the GPU rather than assume it. As of 2026-10-15 there is none (see above). When this was recorded `nvidia-smi` showed an NVIDIA L40S (driver 565.57.01, CUDA 12.7) and regular compute / Vulkan `cooperative_matrix` DID run; but cooperative-VECTOR code could not, because driver 565.x advertises `VK_NV_cooperative_matrix` but NOT `VK_NV_cooperative_vector`, so `has_feature(cooperative_vector)` is False on both Vulkan and CUDA and the shipped `test_coopvec.py` all-45 SKIP. CoopVec kernels still COMPILE (slangc exit 0), so compile-only checks give false confidence — dispatch is where it dies; say "the installed driver doesn't expose VK_NV_cooperative_vector," not "GPU-less" [This env HAS a GPU (NVIDIA L40S) — but coop-vec is NOT runnable (driver lacks VK_NV_cooperative_vector)](../learnings/1784831657952-this-env-has-a-gpu-nvidia-l40s-but-coop-vec-is-not.md).


## downstream_args Plumbing to Downstream Compilers (#1058, PR #1061)

`SlangCompilerOptions.downstream_args` (and `link_options.downstream_args`) are forwarded to Slang via `session_options.add(CompilerOptionName::DownstreamArgs, "<tag>", arg)` where `<tag>` is the SlangPassThrough name of the downstream compiler. Only **DXC** (`"dxc"`, d3d12) and **NVRTC** (`"nvrtc"`, cuda) accept pass-through args; Vulkan/Metal/WGPU/CPU have no consuming downstream compiler. Before PR #1061 the forwarding was hardcoded `if (device_type == DeviceType::d3d12)` with the `"dxc"` tag in BOTH the compile path (`create_session`, `src/sgl/device/shader.cpp:322`) and link path (`ShaderProgram::link`, ~:1540), so on CUDA the args were accepted at the Python dict→struct layer (`src/slangpy_ext/device/shader.cpp:27`, no validation) then **silently dropped** — e.g. `downstream_args=["--use_fast_math"]` had zero effect. Key distinction: `floating_point_mode` is a FIRST-CLASS Slang option applied unconditionally per-target (`shader.cpp:397`), which is why `floating_point_mode=fast` always worked on CUDA — a different mechanism. Fix = add a CUDA branch forwarding via `add(DownstreamArgs, "nvrtc", arg)` (CLI `-Xnvrtc`); the `"nvrtc"` tag was already proven in-tree by the auto OptiX-include forwarding ([slangpy downstream_args only forwarded for D3D12 (dropped on CUDA/NVRTC)](../learnings/1783910132054-slangpy-downstream-args-only-forwarded-for-d3d12-d.md)).

**Testing the fix requires an actual dispatch — NVRTC codegen is deferred to first dispatch.** For a CUDA device (SLANG_PTX target), NVRTC downstream compilation does NOT run at `session.link_program()` or `device.create_compute_kernel()` (which only reads reflection). The compute pipeline is created lazily in `ComputeKernel::pipeline()` (`kernel.cpp:35-40`), invoked only on the first `kernel.dispatch(...)`. So a test that verifies a downstream arg reaches NVRTC — or that a bogus arg is rejected — MUST create an output buffer and call `dispatch`; a test that stops at `create_compute_kernel` silently never runs NVRTC (this bit PR #1061: first version asserted a bogus flag raised at create and CI failed "DID NOT RAISE"). A pipeline-time NVRTC/RHI failure surfaces as Python `RuntimeError` (via `SLANG_RHI_CALL`→`SGL_THROW`), NOT `spy.SlangCompileError`; `pytest.raises(RuntimeError)` covers both ([SlangPy CUDA/NVRTC codegen is deferred to first dispatch — tests must dispatch to catch downstream-arg errors](../learnings/1783912568549-slangpy-cuda-nvrtc-codegen-is-deferred-to-first-di.md)).

**Editing a `///` docstring on a struct field in `src/sgl/device/shader.h` does NOT reach Python users automatically.** Python docstrings come from `src/slangpy_ext/py_doc.h`, a checked-in generated file (pybind11_mkdoc), regenerated by the `slangpy_pydoc` CMake target (`src/slangpy_ext/CMakeLists.txt:227`) which needs a full build + vcpkg include dir. If you can't run that target, hand-edit `py_doc.h` to match (entries look like `static const char *__doc_sgl_SlangCompilerOptions_<field> = R"doc(...)doc";`, ~70-col reflow, ASCII, no trailing whitespace — it's in the pre-commit `exclude:` list so clang-format won't touch it). A review WILL catch the desync if you only edit `shader.h` (found on #1058 / PR #1061) ([SlangPy py_doc.h must be updated when editing SlangCompilerOptions docstrings](../learnings/1783909847856-slangpy-py-doc-h-must-be-updated-when-editing-slan.md)).

**Adding a NEW nanobind-bound method/class needs its docstring symbol present in `py_doc.h` or the build breaks — a stronger constraint than the docstring-desync above.** The `D(...)` macro expands to `DOC(sgl, ...)` → `__doc_sgl_<Symbol>`; reference a `D(Device, new_method)` whose `__doc_sgl_Device_new_method` symbol is absent and the build fails at compile/link (not merely a cosmetic desync). Two safe options when the `slangpy_pydoc` mkdoc target is unavailable (it needs `pybind11_mkdoc` + clang ≥ 20.1.5 + libc++, usually NOT in the coworker env): (1) hand-add the `static const char *__doc_sgl_<Symbol> = R"doc(...)doc";` entries in the exact generated format (mirror an adjacent entry; fields ordered alphabetically) — minimal, reviewable, and py_doc.h is in the pre-commit global `exclude` so clang-format won't churn it; or (2) use `D_NA(Device, new_method)` which expands to the literal `"N/A"` (precedent at device.cpp bindings). Prefer (1) for user-facing APIs and flag that a maintainer can regenerate (PR #1158 / issue #1155) ([py_doc.h is committed+generated: hand-add DOC symbols or use D_NA when mkdoc is unavailable](../learnings/1789376759049-slangpy-py-doc-h-is-committed-generated-hand-add-d.md)). One naming trap when auditing a hand-edit for completeness: **mkdoc STRIPS the leading underscore from underscore-prefixed member/method names**, so the private `Device::_notify_command_recording_submitted` becomes `__doc_sgl_Device_notify_command_recording_submitted` (single `_` between `Device` and `notify`), NOT `__doc_sgl_Device__notify_...` — grepping the double-underscore form finds nothing and can make you wrongly conclude private `_notify_*` methods are undocumented. mkdoc emits empty-docstring entries (`R"doc()doc"`) for private data **members** and underscore-prefixed internal methods, but not for every private method uniformly; because these are empty docstrings on symbols no binding references, omitting them is cosmetic (no compile error, unlike a referenced `D(...)`) yet produces a spurious diff on the next regeneration — so for a PR adding a callback that mirrors siblings, prefer regenerating over hand-editing. (SGL lifecycle fact from the same work: `CommandEncoder::finish()` fires before-finish, then RHI finish, then sets `m_open=false` only on success — a failed or throwing finish leaves the encoder OPEN and retryable, so before-finish is NOT 1:1 with a recording, and `discarded` fires only on eventual destruction.) ([mkdoc strips the leading underscore from private symbol names in py_doc.h](../learnings/1789378366162-slangpy-py-doc-h-mkdoc-strips-leading-underscore-f.md))
