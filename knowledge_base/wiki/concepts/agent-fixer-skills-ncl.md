# Skills, ncl CLI, and Slang-Specific Mechanics

Operational notes for the `ncl` admin CLI (group lifecycle, task lifecycle, scope traps), slang-rhi CI behavior, and two Slang language/compiler mechanics that have caught fixers.

## TL;DR

- Bootstrap a new agent group with `mcp__nanoclaw__create_agent`, never `ncl groups create`: the CLI inserts only the `agent_groups` row, seeds no `container_configs` and wires no reverse destination, so later `config update` fails and the group is a zombie until a host restart backfills it.
- Cross-group `--id` enforcement is per-command: `groups config get/update --id <other>` is rejected at parse time for `group`-scoped callers, while `destinations add --target-id <other>` goes through approval normally. Assume nothing transfers between commands.
- An agent's `ncl groups restart --id <other>` restarts its OWN session and silently drops `--id`/`--message`; approval replay preserves `caller:'agent'`, so operator approval does not fix it. Cross-group restart must be run by the operator from the host shell.
- Prefer plain `ncl groups restart --id <target>` over `--message`, which writes `on_wake` to every running session in the group and can clobber an unrelated one. Re-hand resume context over normal a2a on the canonical thread instead.
- A one-shot scheduled task has two independently-live parts, trigger and payload. `cancel` retires only the trigger; the prompt survives and is immutable.
- Never re-arm a one-shot: that supplies the missing trigger to a live instruction whose side effects (a maintainer nudge, a comment, a push) are not idempotent.
- Create a one-shot in ONE call with its real `--prompt` and a FUTURE `--process-after`, then read it back before quoting its id. A placeholder prompt with a past due time fires within minutes and is consumed; `update` cannot revive it.
- A spent one-shot is byte-identical in `ncl tasks list` to an orphan: `status: pending`, `process_after` in the past, `completed_runs: 0` forever, because `runs` increments on completion. A past `process_after` is necessary but never sufficient evidence that a task still needs to run.
- Never build a repair/watchdog mechanism whose predicate is "looks unfinished". Ask what a SUCCESSFUL run leaves behind on the row you inspect; if nothing, that row cannot drive the repair.
- The run log (`ncl tasks append-log --id <t> --msg "…"`; the flag is `--msg`, not `--note`) is the only writable layer on a completed row and what a re-armed session reads. Never `delete`: it hard-deletes the series and its history.
- Distinguish `ncl`'s state-based refusals from its silent wrong-flag no-ops by running the same verb and flags against a live row as a positive control. Without it, "no live task matched" is indistinguishable from a flag typo.
- `ncl` silently accepts unknown flags on every verb *except* `tasks list`, returning the full unfiltered set at exit 0, so a plausible row count never proves a filter applied. The reliable test: a bogus value against a non-empty baseline should return zero rows; if it returns the full set, the flag is inert.
- Never use `--flag=value` with `ncl`; always space-separate. The whole token is read as one flag name: "unknown flag" on validating verbs, *silently ignored* (full unfiltered data, exit 0) on swallowing verbs. This syntax rule beats every output-based detector.
- `ncl tasks get <id>` is positional (`--series-id` exits 1). `database is locked` from `ncl` or `send_message` in a container is transient: wait ~5 s and retry once, unlike a 30 s timeout on every call (host wedge).
- Before trusting a scoping flag, run `ncl <resource> help <verb>` and confirm it is *declared on that verb*: `--id`/`--agent-group-id` are honored by `tasks get`/`sessions messages` but inert on `tasks list`. Don't carry a flag name from a sibling verb.
- From inside a container there is NO way to query another group's tasks, even for Main at `cli_scope=global`: every route (`--agent-group-id` swallowed, `--group` auto-filled over your own, `--all` identical to bare) returns your own rows at exit 0, and `task not found` for a peer's series id means nothing. Verify through the task's session (`ncl sessions get <sid>` → thread `system:tasks:<series>`); never recreate another group's timer.
- For content search, pass `ncl sessions messages --full` (the default truncates each row's text to ~300 chars, so grepping silently false-negatives). The `truncated` flag or a positive control only audits a read already taken without it.
- In a scheduled-task session, a `<message>` block in the final response is silently dropped ("task sessions send only via explicit tools"): report only via the explicit `send_message` tool. `ncl tasks list` showing "No tasks" is not proof of none.
- Report what your action actually touched: "cancelled it" removes the trigger, not the instruction. A guard belongs in the re-arming mechanism, the layer that stays load-bearing.
- A guard in a mechanism that has never fired has never been tested. Check its predicate against real data (a self-exclusion matching a substring absent from the actual ids is dead code that looks like coverage).
- `shader-slang/slang-rhi` runs its full CI matrix, tests included, on draft PRs (tests run inline in the `build (<os>, <arch>, <compiler>, <config>)` jobs), so no ready-flip is needed to validate a fix. The CI-babysitter sweep skips drafts, so watch them yourself.
- `-zero-initialize` force-adds `IDefaultInitializable` to every non-core struct with no exclusion for compiler-synthesized decls, collapsing a captured lambda's closure constructors to zero-arg `$init()`. Exclude `SynthesizedModifier` structs at the forcing site; keep it separate from the long-term IR-pass redesign.
- When a new public header under `include/` is included by `slang.h` and also needs its types, put `#include "slang.h"` OUTSIDE the header's own `#ifndef` guard, and use `#ifndef`, not `#pragma once`. Public `slang-*.h` headers auto-install via the CMake glob; verify with `g++ -fsyntax-only -Iinclude` on one-line TUs.
- Never stage the bundled conservative approval policy into a per-PR workspace `policy/` dir: it shadows the mounted relaxed policy and flips clauses to FAIL.

## ncl Group Lifecycle: Zombie Groups and Scope Enforcement

`ncl groups create` only inserts the `agent_groups` row ([ncl groups-create produces zombie groups; cross-group --id is parse-time-blocked](../learnings/1779254262878-ncl-groups-create-produces-zombie-groups-cross-gro.md)). It seeds no `container_configs` row, so a later `ncl groups config update --id <new>` fails with `"No container config for group: <id>"`, and it wires no reverse destination back to the creator. Use `mcp__nanoclaw__create_agent` (admin-only), which bundles seeding and bidirectional wiring. An `ncl`-created group may self-rescue via `src/backfill-container-configs.ts` on host restart, but cold start in the degraded state can take ~11 hours vs ~34 s warm on a properly wired group.

**Cross-group `--id` enforcement differs by command.** For `group`-scoped coworkers, `ncl groups config get/update --id <other>` is rejected at parse time (before the approval flow), while `ncl destinations add --target-id <other>` goes to approval normally (`--target-id` is a separate field). So a coworker can create and forward-wire a child group but can't configure it; admin drives `config update --id <child>`. Source: `src/cli/resources/groups.ts:60`, `src/cli/crud.ts:253-257`, `src/db/container-configs.ts`.

**An agent's `ncl groups restart --id <other-group>` cannot restart another group.** When `ctx.caller === 'agent'` the handler calls `killContainer(ctx.sessionId, …)`, killing the caller's own session and ignoring `--id`/`--message`; only a host caller reaches the group-wide `restartAgentGroupContainers`. Approval replay preserves `caller:'agent'`, so an operator-approved `restart --id <other> --message "…"` still misfires onto the requester's own session, which explains earlier "restart requested but nothing happened" symptoms (slang-fixer thrash-recovery on #12070/#12071/#12073). `mcp__nanoclaw__request_restart` also restarts only the caller. For a cross-group restart, escalate to the operator to run `ncl groups restart --id <target> [--message "<resume>"]` from the host shell. Prefer the plain form (kills only running containers; each respawns on its next inbound) over `--message`, which writes `on_wake` to every running session and can clobber an unrelated one; re-hand the resume memo over normal a2a on the canonical thread ([agent ncl restart can't target another group](../learnings/1783913779722-agent-ncl-restart-can-t-target-another-group.md)).

## ncl Task Lifecycle: Cancelling Retires the Trigger, Not the Payload

A one-shot scheduled task has **two independently-live parts, the trigger and the payload, and `cancel` reaches only the trigger** ([Cancelling a one-shot scheduled task removes the trigger, not the payload — and a spent row is immutable](../learnings/1786073581086-cancelling-a-one-shot-scheduled-task-removes-the-t.md)). The prompt survives cancellation and is immutable on a spent row: `ncl tasks update --id <spent> --prompt '<defused>'` refuses with `no live task matched: <spent>`, while a fabricated id returns `task not found`, proving the row exists but isn't live. That the refusal is state-based, not a wrong-flag no-op, has to be earned with a positive control: the same verb and flags on a *live* row (a no-op prompt rewrite returned `{"touched":1,"fields":["prompt"]}`).

**A spent one-shot is byte-identical to an orphan in `ncl tasks list`**: `status: pending`, `process_after` in the past, `completed_runs: 0` forever, because `runs` increments on completion and a successful fire leaves nothing on the row. A past `process_after` is necessary but not sufficient evidence that a task still needs to run; consult the run log or resolve the session first. Hence **never re-arm a one-shot**: re-arming supplies the missing trigger to a live instruction whose side effects (a maintainer nudge, a comment, a push) aren't idempotent, which is how a watchdog keyed on "looks unfinished" becomes the live path to a duplicate action someone forbade.

**Create a one-shot in a single call with its real `--prompt` and a future `--process-after`, then read it back (`ncl tasks list | grep <key>`) before quoting its series id.** On 2026-10-09 Main created one with `--prompt "x"` and a past due time, intending to update it right after; the host fired it ~2 minutes later, the run saw the placeholder and did nothing, and the task was consumed. The later `update` looked successful, but `get` returned `task not found`, and the chain whose re-chase timer id the operator had been given went untimed for ~4 hours. A one-shot that must re-arm says so in its own prompt ("create a fresh one-shot"), since nothing outside the fired run can restore it ([ncl one-shot task with placeholder prompt is consumed before you can update it](../learnings/1791533244463-ncl-one-shot-task-with-placeholder-prompt-is-consu.md)).

Two corollaries. The only writable layer on a completed row is the run log (`ncl tasks append-log --id <t> --msg "…"`; `--note` is rejected), and it is what a re-armed session reads, so a defusing note goes there, never through `delete`, which hard-deletes the series *and its history*, including the record that says "already fired". And the guard belongs in the **re-arming mechanism**, not the task; a guard that has never had to fire has never been tested: one watchdog's self-exclusion matched `scheduler-watchdog` while real series ids were `task-<digits>-<suffix>`, so it was dead across all 126 runs while reading as coverage.

**An approved scheduled-task fix isn't deployed until both fields are pushed.** A series has two independent fields: `prompt` (wake instructions) and `script` (the pre-task node/bash whose stdout becomes the wake JSON). A classifier fix in a local dev file, even dry-run-verified against live data, takes effect only after `ncl tasks update --id <series-id> --script "$(cat file)"` (plus `--prompt` if the wake text changes). Four consecutive CI-babysitter sweeps re-derived the same wrong "systemic break" verdict because a fix green-lit on 2026-09-15 was never deployed; each fresh session re-derived from scratch because the wake payload never carried the new field. After any script change, verify with `ncl tasks get --id <series-id>` that the live `script` contains the new function names (a byte-diff vs the dev copy is cheap). The update flag is `--id` (not `--series-id`, despite the `series_id` label in `get`/`list`); `--script "$(cat file)"` isn't re-scanned, and keep zero double-quotes in a `node -e` JS body to avoid two-layer escaping. If the LLM must *defer* to a new deterministic field rather than re-derive, that instruction goes into the `prompt` too (a new numbered gate); a `script`-only update adds data but doesn't stop a fresh session second-guessing it ([designed-and-approved fix ≠ deployed fix — scheduled task script/prompt are separate fields, both must be pushed](../learnings/1789533257062-designed-and-approved-fix-deployed-fix-scheduled-t.md)).

## ncl Flag Handling: Silent Swallowing, Inert Scoping Flags, and the `--flag=value` Trap

`ncl`'s flag parsing has one defect with four presentations, and it produced six wrong mechanism labels across two agents before settling; what follows survives every probe. It reads as a *filtering* problem but is a *parsing* one, so the operative test is never the output row count.

**Almost every verb silently accepts unknown flags and returns the FULL unfiltered set at exit 0** ([`tasks list` is the lone validating verb; everything else swallows](../learnings/1786242295161-inverted-headline-ncl-silently-accepts-arbitrary-f.md)). `ncl sessions list --zzz-fake xyz` returns rows md5-identical to bare `ncl sessions list`; `destinations`, `members`, `groups get`, `wirings`, `users`, `roles`, `approvals` behave the same. **`ncl tasks list` is the lone exception**: it errors `unknown flag` on anything it doesn't declare. A plausible result is therefore not evidence a flag applied; this nearly had one agent publish another agent's task count as its own, on a flag that never filtered.

**`--id` and `--agent-group-id` slip through even `tasks list`.** They are dispatcher-level scoping flags, consumed before a verb's allowlist sees them and acted on only where the verb declares them ([mechanism](../learnings/1786242584790-mechanism-found-for-the-ncl-flag-asymmetry-dispatc.md), [refined: honored only where declared](../learnings/1786242851046-refined-ncl-s-id-agent-group-id-are-globally-recog.md)): `ncl tasks get --id <bogus>` errors `task not found`, while `ncl tasks list --id xyz` returns the full set at exit 0. The **`--agent-group` vs `--agent-group-id` one-character split** (rejected vs swallowed) is the diagnostic that no per-verb-allowlist theory explains. It is scope-independent (identical at `group` and `global` scope), so host callers are equally exposed. Severity is high: the inert names are exactly the ones you'd reach for to *narrow* a query, and "your own complete data, exit 0, no warning" reads like a successful filtered query. The original note "`ncl tasks list` has a `--agent-group-id` filter" was wrong ([wrong — the flag doesn't exist on that verb; it's `--group`](../learnings/1786241587140-resolved-ncl-tasks-list-has-no-agent-group-id-flag.md)); flag names are per-verb, so check `help <verb>` rather than reuse a sibling's.

**From inside a container you cannot query another group's tasks, so don't make the cross-group claim** ([every route returns your own rows](../learnings/1786241921742-no-cross-group-task-query-exists-from-inside-a-con.md)). `--agent-group-id` is swallowed, `--group` is *"auto-filled to your own group inside a container"* (`ncl tasks help list`) so a foreign value is overwritten, and `--all` is byte-identical to bare. "`--group` fails loudly" holds only at `cli_scope=group` (`error (forbidden): CLI access is scoped to this agent group`); at global scope it returns your own rows at exit 0. That includes Main: at `cli_scope=global`, `ncl tasks get <peer-series>` still answers `task not found` and `list --all` drops every other group's rows, so the detector is that every returned row carries your own `agent_group_id`. Twice on 2026-10-15 (slang#13637, #13640) Main told slang-triager and the operator dashboard that the triager's one-shot re-check did not exist, and once armed a duplicate; both tasks were live, and a recreated timer fires twice. Verify through the **session projection**, which spans groups at global scope: `ncl sessions get <session_id>` (the owner pastes the id from its own `ncl tasks get`) should show thread `system:tasks:<series>` and the owner's `agent_group_id`. `ncl sessions list --thread-id system:tasks:<series>` also works, but a task on a legacy shared session (thread NULL) returns `[]` exactly as a fabricated id does, so `[]` proves nothing. Otherwise ask the owning coworker for its `ncl tasks get` output ([Main cannot see a peer group's tasks; verify via the task's session](../learnings/1792072157486-ncl-tasks-get-list-from-main-cannot-see-a-peer-gro.md), [scoped even for Main at global scope; detector: every row is your own group](../learnings/1792072189568-ncl-tasks-reads-from-inside-main-are-scoped-to-mai.md)).

Related: [Eval Runner: Trial Isolation, Answer Contract, and Answer-Key Leaks](../concepts/agent-eval-runner-trial-isolation-and-answer-leaks.md) (the same `--group` auto-fill silently sends `ncl tasks create` eval dispatches to the caller's own group).

**Never use `--flag=value` with `ncl`; always space-separate.** The whole token is read as one flag name ([syntax fact](../learnings/1786243340982-ncl-does-not-support-flag-value-syntax-anywhere-us.md)): validating verbs error `unknown flag --status=pending`, but the seven swallowing `list` verbs **silently ignore it — full unfiltered data, exit 0, empty stderr** ([re-scoped to HIGH severity](../learnings/1786243601219-re-scoped-high-severity-ncl-flag-value-is-silently.md)). `ncl sessions list --thread-id release-ci-nightly` filters to 1 row; `--thread-id=release-ci-nightly` returns all 5, md5-identical to bare. This outranks the flag-name findings because `--flag=value` is muscle memory from most CLIs. The worst presentation is a swallowing single-record `get` verb with auto-fill (group scope): `ncl groups get --id=TOTAL-GARBAGE-xyz` discards the token, auto-fill supplies the caller's own group, and a well-formed record for the **wrong identity** returns at exit 0, while the space form correctly refuses with `forbidden` ([fourth presentation](../learnings/1786243869582-fourth-presentation-of-the-ncl-equals-form-defect-.md)).

The remedy is the syntax rule, not a detector, because every output-based guard has a blind cell ([the guard is unsound under auto-fill](../learnings/1786244050796-correction-my-assert-returned-id-passed-id-guard-i.md)). "Assert the returned id equals the id you passed" passes precisely when a `cli_scope=group` agent queries its own group, the only query it may make, because auto-fill supplies the expected value; a run-both-forms differential is md5-identical at group scope for the same reason. A syntax prohibition needs no verb class, baseline or expected identity, and auto-fill can't defeat it. The bogus-value-vs-non-empty-baseline check stays useful for *list* filters (a bogus value should return zero rows; the full set means the flag is inert), but it is not the general remedy.

**Three smaller invocation facts.** `ncl tasks get` takes the series id positionally (`ncl tasks get t-2a6862`); `--series-id` is not a flag and exits 1. `ncl tasks create` prints JSON with no easy-to-grep id, so find the new series as the row with the smallest AGE in `ncl tasks list` (or give it a readable `--name`). Inside a coworker container, `ncl tasks list` and `mcp__nanoclaw__send_message` can fail with `database is locked` while another session writes the session DB: transient contention, so wait ~5 s and retry (the retry succeeded both times observed). That is not the host wedge, where every call, trivial reads included, times out at 30 s and retries don't help ([ncl and gateway instrument defects](agent-a-ncl-and-gateway-instrument-defects.md)) ([ncl/send_message 'database is locked' is transient; ncl tasks get takes a positional id](../learnings/1792857731218-ncl-send-message-database-is-locked-is-transient-n.md)).

## Scheduled-Task Sessions: Dropped `<message>` Blocks and Truncated Session Reads

Two traps for anything running on a cron/scheduled task, found while an agent audited its own instruments ([scheduled-task session traps](../learnings/1786240364490-scheduled-task-sessions-drop-message-blocks-silent.md)).

**In a scheduled-task session, a `<message to="…">` block in the final response is NOT delivered.** The runner logs `task sessions send only via explicit tools` and keeps the text as scratchpad, so it looks like a sent report while nobody receives it, and the *report about a failure* is what gets dropped. **In scheduled tasks, report only via the explicit `send_message` tool.** Likewise, `ncl tasks list` returning `No tasks` doesn't prove you have none; corroborate with `ncl sessions list` (a task-driven session shows as a row, often with an empty `messaging_group_id` and a `created_at` on the cron boundary).

**For session-content search, pass `ncl sessions messages --full`.** By default each row's `text` is truncated to ~300 chars (the cutoff is an output-mode artifact: 301 via `--json`, wider in table form), so grepping for content silently false-negatives. `--full` is the fix ([correction: `--full` is the remedy, not the `truncated`-flag workaround](../learnings/1786240671164-correction-ncl-sessions-messages-full-is-the-fix-f.md)): the content grep that returned 0 hits by default returned 1 with `--full`. The earlier advice to detect clipping via `truncated: true` was a workaround that reading `ncl sessions help messages` first would have avoided. Use the default output for `thread_id`, direction, timestamps and ordering; use `--full` whenever you grep the body.

## slang-rhi CI Runs on Draft PRs

`shader-slang/slang-rhi` runs its full CI build matrix on **draft PRs** ([slang-rhi runs full CI matrix (incl. tests) on draft PRs](../learnings/1781175866294-slang-rhi-runs-full-ci-matrix-incl-tests-on-draft-.md)), with tests inline in the `build` matrix jobs (`./slang-rhi-tests -check-devices`) and no separate test job. Headless containers can't build `slang-rhi-tests` locally (GLFW needs X11/RandR; `enum-strings.h` is build-generated), so CI is the only arbiter for runner-specific behavior (e.g. macOS Metal-timer). To validate a fix, watch the draft's `build (<os>, <arch>, <compiler>, <config>)` jobs; no ready-flip needed. The CI-babysitter sweep covers only non-draft PRs, so it won't report a draft's result.

## -zero-initialize and Synthesized Lambda Closures

The `-zero-initialize` forcing site is `SemanticsDeclBasesVisitor::visitStructDecl` at `source/slang/slang-check-decl.cpp:11424-11441` ([slang -zero-initialize forces IDefaultInitializable on ALL non-core structs (incl. synthesized closures) at slang-check-decl.cpp:11424](../learnings/1781240588042-slang-zero-initialize-forces-idefaultinitializable.md)). Under `getBoolOption(ZeroInitialize) && !isFromCoreModule(decl)` it force-adds `IDefaultInitializable` to ANY non-core struct, with no exclusion for compiler-generated decls. A captured lambda lowers to a synthesized `LambdaDecl` closure struct (`SynthesizedModifier`), whose constructor set then collapses to a zero-arg `$init()`, giving `error E39999: too many arguments to call` when captured values are passed. Fix: exclude `SynthesizedModifier` structs (or narrowly `!as<LambdaDecl>(decl)`) at the forcing site. slang#11573 "Reimplement -zero-initialize as an IR pass" is the long-term redesign; keep per-issue fixes to the targeted exclusion.

## Slang Public-Header Include Cycles

A new public header under `include/` that `slang.h` `#include`s and that needs `slang.h`'s types forms a mutual-include cycle ([Slang public-header include cycle: include slang.h OUTSIDE your own guard](../learnings/1782759769387-slang-public-header-include-cycle-include-slang-h-.md)). With `#pragma once` and `#include "slang.h"` inside its guard, including the new header first fails: the nested `slang.h` hits its own `#include "newheader.h"`, the guard suppresses re-entry, and the prototypes are never declared before `slang.h`'s wrappers need them.

Fix: put `#include "slang.h"` **before** the new header's own `#ifndef` guard. On a newheader-first include, the nested `slang.h` then re-enters the new header while `NEWHEADER_H` is still undefined and declares the prototypes ahead of the wrappers; `slang.h`'s own `#ifndef SLANG_H` breaks the recursion. Use the `#ifndef` convention, not `#pragma once`. Public headers auto-install via the `include/slang*.h` glob in `source/slang/CMakeLists.txt`, so a new `slang-*.h` needs no CMake edit. Verify with `g++ -std=c++17 -fsyntax-only -Iinclude` on one-line TUs per header.

## Approver: Don't Stage the Bundled Policy

On slang#12118 the approver copied the bundled `APPROVAL_POLICY.json` (`v0-shadow`, the conservative default next to `eval-clauses.py`) into the per-PR workspace `work/<pr>/policy/` during staging. It shadows the mounted `v0-shadow-relaxed` policy and flips clauses to FAIL, so never stage it there ([[approver/critique-mustfix] Do not stage the bundled v0-shadow policy into the workspace policy/ dir — it shadows the mounted v0-shadow-relaxed and flips clauses to FAIL](../learnings/1784117125434-approver-critique-mustfix-do-not-stage-the-bundled.md)).
