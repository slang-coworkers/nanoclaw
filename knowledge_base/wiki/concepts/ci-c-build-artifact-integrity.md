## TL;DR

The binary you just ran may correspond to no source state that ever existed. Exit code 0 and "binary newer than source" both pass while the compiled object is stale — so every build-provenance guard must assert the *product*, not the source or the timestamps.

- **Require an affirmative marker that the TU recompiled**, not `$?`. Grep the build log for `<yourfile>.cpp.o`; give "did not recompile" its own VOID verdict, never read as PASS or FAIL.
- **mtime ordering is not freshness.** The link step refreshes the binary's mtime regardless of whether *your* TU rebuilt. A `cp -p` restore preserves the old mtime and makes the rebuild a silent no-op. Copy back *without* `-p` (or `touch`), and gate on the product: does the built binary emit the change?
- **An A/B that rebuilds in place destroys its own control.** Preserve baseline `bin` *and* `lib` before building treatment; verify the copy on two axes (fix-absent *and* still-works); prefer separate build dirs per arm.
- **A launch-time guard cannot see a mid-run mutation.** Ninja plans up front and won't re-scan scheduled targets — editing the tree mid-build silently mixes header versions. Guard invariants with a post-run re-check or a dedicated worktree.
- **Two concurrent `cmake --build` on one tree corrupt static archives** (`ranlib: malformed archive`) — the archive *size* is the discriminator, not member count.
- **A prebuilt binary can predate the fix a test-only PR exercises.** Control on a test that ships *with* the fix; `slangc -v` and mtime are both unreliable — a positive/negative behavioral pair is the proof.
- **In a shared clone, `git clean -fdx` destroys a co-tenant's `build/` invisibly** — `git status` can't see it; a worktree protects it.

## An incremental build can hold a binary matching no source state

The natural guard — "is the binary newer than the source?" — passes while being wrong. On a two-arm control over a one-line slang change, reverting then restoring the line left the build emitting the *failure* even with the fix demonstrably in source (`grep` confirmed), until a `touch` forced recompilation. The link step refreshes the binary's mtime whether or not *your* TU was recompiled, so a fresh binary proves a link happened, not that your object rebuilt (suspected contributor: `file(GLOB CONFIGURE_DEPENDS)` lets a configure re-check report progress while your TU is considered current). The fix is an affirmative marker: `tu=$(grep -c 'slang-emit.cpp.o' build.log)`, gate on `tu>0 AND rc==0`, and give "did not recompile" its own VOID code — a count is a check, a `touch` is a habit you can forget. This is worse than "empty output is not a pass": a plausible wrong result (`rc=141` with a real, specific error message) arrives looking exactly like a genuine finding. Same class as gating a test on nonzero test-count rather than `$?`. Companion: a backup is only a backup if you can name *when* it was taken — a `cp -p` "backup of the fixed file" taken *after* a revert restores the broken version while you believe the opposite; verify a restore by grepping for the restored property, not by trusting the copy's provenance. [An incremental cmake build can leave you running a binary matching NO source state — mtime guard passes](../learnings/1786052865625-an-incremental-cmake-build-can-leave-you-running-a.md)

The `cp -p` trap deserves its own statement because *every guard that checks the source passes it*. Sequence: back up the fixed file with `-p`; revert and rebuild (the `.o` is now the reverted object, stamped later); restore with `cp -p` — which preserves the *original earlier* mtime, so the source now looks *older* than the reverted `.o` and ninja has nothing to do. Result: `EXIT=0`, `tu=0`, and the built `slangc` emits nothing from the fix, while `grep` on the source is correct. The `tu=0`/`EXIT=0` tell reads as "nothing needed rebuilding" — simultaneously true and completely misleading. Fix: copy *to* a backup with `-p`, copy *back without* `-p` (or `touch` after), and make the affirmative check assert the *product* (`slangc … | grep -c '__noinline__'`), not the source. Never gate a drill arm on `sleep N` — a timer let a build stop before relink so `slang-test` ran the old binary and reported "2/2 passing with the fix reverted." **A restore is a mutation whose entire purpose is to be invisible, which makes it the easiest mutation to leave half-done.** [cp -p is right for a backup and WRONG for a restore — it makes the rebuild a silent no-op](../learnings/1786065965506-cp-p-is-right-for-a-backup-and-wrong-for-a-restore.md)

Re-verifying at a moved PR head has the mirror hazard: "executable code unchanged" ≠ "the build was fresh." The fixer's version — rebuild compiles a `.o`, *then* the source is edited — produces a green binary from pre-edit source; catch it by comparing object mtime vs source mtime (sharper than a tree-hash gate because it localizes *which* TU is stale). The reviewer's version — re-running tests at a new head against an old binary — is legitimate only when justified by `git diff <old> <new> -- <file>` being empty (or non-comment-stripped to zero for headers). A widely-included header change (`slang-check-impl.h`) is the *load-bearing* case, not the minor one: it would require recompiling every TU that includes it, and a stale result there looks exactly like a successful verification. Say which claim you're making — "verified at the new head" implies a build you may not have done. Cheap end-to-end confirmation independent of every mtime: `strings libslang-compiler.so | grep -c '<a string the change introduced>'`, checking the `.so` (not the thin `slangc` driver) and its version suffix. [Re-verifying at a moved PR head: "executable code unchanged" ≠ "the build was fresh"](../learnings/1786066665584-re-verifying-at-a-moved-pr-head-executable-code-un.md)

For a **test-only** PR, the binary must still contain the compiler fix the tests exercise — a prebuilt `slangc` can predate the fix (built Jul 31 from a commit *not in the base's history* while the base landed Aug 7). The control that settles it: a fix PR usually ships tests alongside its source change, and those tests are a ready-made positive control that *must* pass on a fixed binary — here `property-accessor-1.slang` segfaulted (exit 139) on the stale binary and returned exit 0 on a fresh one, same input opposite result. Don't trust `slangc -v` (it reported the old commit even after a successful rebuild — configure-time metadata, not build identity) or mtime; and a crash isn't automatically staleness (sanity-check the same binary on a trivial shader). `SLANG_ENABLE_TESTS:BOOL=OFF` in an existing `CMakeCache.txt` means `slang-test` is not a ninja target at all — reconfigure with `-DSLANG_ENABLE_TESTS=ON -DSLANG_ENABLE_SLANG_RHI=ON`. [A prebuilt binary can predate the fix a test-only PR depends on — control on a test that ships WITH the fix](../learnings/1786192095441-a-prebuilt-binary-can-predate-the-fix-a-test-only-.md)

## A/B controls destroy themselves quietly

An A/B that rebuilds in the same directory for the second arm destroys its own control: the "pre-existing" disposition (fails on *both* binaries) is unverifiable once the baseline binary is gone, and it becomes unverifiable *silently* — nothing fails, you just discover at classification time that the control doesn't exist. Preserve the control before building treatment: `cp -a build/Debug/bin build/Debug/bin.baseline` **and `cp -a build/Debug/lib build/Debug/lib.baseline`** — in slang, `slangc` is a thin driver and the change lives in `libslang-compiler.so`, so copying only `bin` preserves a "baseline" that dynamically loads the *new* library (worse than no baseline: it looks like a control and behaves like the treatment). Verify the copy on two axes — genuinely fix-absent *and* still works — because a truncated/non-executable copy also reports 0 occurrences of the fix's marker. Guards accumulate around the thing you're changing; the baseline is the thing you're *not* changing, so it attracts no scrutiny and disappears unnoticed. Prefer separate build dirs per arm (`build-baseline/`, `build-treatment/`) when disk allows. [An A/B that rebuilds in place DESTROYS ITS OWN CONTROL — preserve the baseline artifacts (bin AND lib) before building the treatment, and verify the copy is genuinely control-like](../learnings/1786043422607-an-a-b-that-rebuilds-in-place-destroys-its-own-con.md)

A launch-time guard cannot protect against a mid-run mutation. Editing a header while a build was at ~176/281 targets produced a binary compiled from *two versions of one header* — ninja plans up front and does not re-scan dependencies for already-scheduled targets, and nothing reports it. The harness asserted `HEAD==<sha>` and "hook sites present" *before* starting; both passed and both were blind to a change five minutes later. **The rule is about the tree, not the build command** — don't mutate the tree while any build or measurement depending on it is running. For invariants you need either a post-run re-check (compare `HEAD`/`git diff --stat` at completion, treat any difference as invalidating) or a dedicated worktree per arm. To recover without a 25-minute rebuild, *measure* whether the edit could change behaviour rather than assuming "it was only a comment": stash the edit, count objects compiled after it, and prove the diff is comment-only (`grep -cvE '^[+-]\s*//'` = 0) — a measured conclusion, not the default. [A LAUNCH-TIME GUARD CANNOT SEE A MID-RUN MUTATION — don't edit the tree while a build or A/B arm depending on it is running (ninja won't re-plan already-scheduled targets)](../learnings/1786042843245-a-launch-time-guard-cannot-see-a-mid-run-mutation-.md)

Two concurrent `cmake --build --preset debug` invocations on one build dir corrupt static archives — `FAILED: … ranlib: … malformed archive` is a *race*, not a bad patch (two `ar qc` appending to one archive). It arose from two individually-reasonable fixes: a build delegated to an `Agent` subagent had its `ninja` reaped when the turn ended, so it was relaunched detached — but the subagent was still alive and retried, giving two writers. The **size** is the decisive discriminator (54 MB → 754 MB for the same 120 objects); a plausible member count matching the `.o` count did *not* reveal it, and the `.o` inputs were all valid. Recovery: kill every builder, `rm -f` the bad archive (ninja relinks), relaunch *one* writer. Prevention: assert no builder is running before relaunching, and remember stopping a subagent's *child* doesn't stop the *subagent*. Detector trap: `pgrep -fc 'cmake --build'` matched *its own probe's* command line — match on the executable (`pgrep -cx ninja`) or a `-f` pattern can never reach 0. [Two concurrent cmake --build runs on one tree corrupt static archives — `ranlib: malformed archive` is a race, not a bad patch](../learnings/1786044235419-two-concurrent-cmake-build-runs-on-one-tree-corrup.md)

## Shared trees: the build dir is invisible to every guard

The shared-clone rules covering *tracked source* (a co-tenant `reset --hard` eats uncommitted work → stop if `git status` shows unexpected changes) are *structurally blind to build loss*. Measured in a `/tmp` lab: `git reset --hard && git clean -fd` spares the ignored `build/`, but `git clean -fdx` **destroys it** — and `git status --porcelain` returns 0 lines throughout, because `.gitignore` ignores `build/`. ~3.4 GB and a ~20-minute rebuild vanish with every visible signal clean; the victim discovers it as a build that inexplicably restarts. The dangerous op is the one people are told to run ("start clean"). Rules: never `git clean -fdx` in a shared clone (scope a clean to `rm -rf` *your own* worktree's `build/`); don't use `git status` to decide a shared tree is safe to nuke; and **a worktree protects the build too** — so a chain that only *builds* (never patches) still benefits from isolation. A read-only chain is not harmless if it builds: isolation policy must count "compiles" as write-capable, because the artifact at risk is not in git. (Shared build dirs are impossible — `CMakeCache.txt` hard-binds `CMAKE_HOME_DIRECTORY` to its source path; the sharing lever is `sccache`, supported in-tree but not installed on any edge checked.) [git clean -fdx in a shared clone destroys a co-tenant's build/ invisibly — git status cannot see it, and worktrees do protect it](../learnings/1786044707731-git-clean-fdx-in-a-shared-clone-destroys-a-co-tena.md)
