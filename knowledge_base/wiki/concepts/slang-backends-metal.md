# Slang Metal Backend Deep Dives: Address Spaces, DescriptorHandle, MetalLib Versioning

## TL;DR

- **MSL rejects a pointer to a vector lane** (`&v[i]`, `&v.x`: "address of vector element requested") but accepts `((T device*)&v) + i`. Metal has no GetElementPtr override, so every atomic on a vector/packed-vector lane or matrix element fails; the fix is a Metal `tryEmitInstExprImpl` override mirroring CPP, not the `legalizeFuncBody` call-arg temp copy (a copy is not atomic).
- `"Unknown addressspace encountered."` (`slang-emit-metal.cpp:1363`) is a SHARED symptom of ≥2 producer bugs — never fold a new crash by message alone; IR-dump to see which producer left `Generic`; fix producer-side, never with an emitter fallback: fragment out-param (#11969, vertex-only out→return-struct lowering) vs an uncalled `export`/library function's by-reference param, which includes a by-value struct/array `in` that `transformParamsToConstRef` turns into `BorrowInParam(T, Generic)` (#11981, #14005; worklist seeded only from entry points). Crashes only in `-whole-program` with no `[shader]`, compiles with an entry point, HLSL fine ⇒ #11981.
- `metallib_latest` aliases the newest version (`metallib_4_0` since PR #10592); gate version-gated emit on the EFFECTIVE metal language version, not `metallib_latest`.
- #12096/#11999 share one root: slang-rhi infers `metallib_4_0` from `NS::ProcessInfo` OS major ≥ 26. The fix of record is the Slang-core `-std` ADVANCE (#12009: derive `-std=metalX.Y` from `metalLanguageVersion`), not a slang-rhi retreat. "Requires version X" is ambiguous between "toolchain can't" and "we didn't ASK" — try `-std=metalX.Y` before recommending a capability retreat.
- `-std` derivation (`slang-gcc-compiler-util.cpp` + `slang-code-gen.cpp`) is FEATURE-driven since PR #12250 (`MetalExtensionTracker`); a new `metallib_X_Y` needs only the capdef atom + a highest-implied-atom producer. A set version REPLACES the `-std=metal3.1` fallback, so `requireMetalLanguageVersion(v)` with v <= 3.1 lowers `-std`; require only versions above 3.1. `getTargetCaps()` returns by value: bind it to a local before a range-for over `getAtomSets()`, or a `metallib_4_0` pin silently drops to `-std=metal3.1` (#14010).
- Metal `DescriptorHandle<T>` emit is DONE (#10842); the gap is the slang-rhi RUNTIME (no `getDescriptorHandle` override, only ArgumentBufferTier2). Combined texture+sampler (128b) can't fit `DescriptorHandle::value` (uint64); separate handles can.
- `DescriptorHandle`-in-buffer (#11970) and uniform array-of-resource (#12291) are EMIT-layer filter/type-shape gaps, distinct from #10842's runtime gap and #7669's wrapper-swap binding loss. #11970: prefer the reporter's struct-wrap; #12291: `IRArrayType` matches no allowed `paramType` branch in `emitFuncParamLayoutImpl`.
- On Metal, `introduceExplicitGlobalContext` makes every global shader param a by-value kernel argument and stores it into `KernelContext`, so a bound `Texture2D[96]` is copied once per invocation and each use loads the whole field (#13894). CUDA and CPU index global arrays in place. Compare the same shader across targets before calling a symptom Metal-only.
- A GREEN macOS CI job does NOT mean Metal ran: `slang-rhi-tests -check-devices` exits 0 on unsupported. Grep the log for `Metal: not supported`; report "N registered, M executed"; a zero-hit grep needs a non-zero control (logs are column-padded).
- Metal `fmod` IS Remainder (MSL §6.6): trunc vs floor is the Modulus/Remainder discriminator.
- **`-target metal` ignores `-fp-mode`** (byte-identical MSL), drops `precise` with E56005, and Metal defaults to fast math. MSL `math_mode(safe)` still contracts; only `fp contract(off)` / `-ffp-contract=off` stops FMA fusion.
- Metal `mul(M,v)` → `v*M` is BY DESIGN and identical to SPIR-V (`OpVectorTimesMatrix`) — reject any "reverse the Metal mul operand order" fix. A Metal-vs-Vulkan transpose comes from layout modes (C-API default ROW_MAJOR vs `slangc` CLI COLUMN_MAJOR), host upload, or a Metal `ParameterBlock` matrix (layout ignored since v2025.18.2). `reproduced` needs a Metal GPU + host upload code.

Metal-only (`slang-emit-metal.cpp`, textual MSL) failure families: pointer address-space specialization, `DescriptorHandle` emission, MetalLib `-std=metalX.Y` derivation, uniform-param cbuffer wrapping, array-of-resource binding. WGSL and cross-target issues: [[wiki/concepts/slang-backends-wgsl-metal.md]]. MSL atomics (64-bit, float, compare-exchange), fences and `coherent(device)`: [[wiki/concepts/slang-backends-metal-atomics-fences-and-coherence.md]].

## Address-Space Crashes: "Unknown addressspace encountered"

`SLANG_UNEXPECTED("Unknown addressspace encountered.")` at `slang-emit-metal.cpp:1363` is the `default:` arm of the pointer-param address-space switch, hit by a pointer param still carrying `AddressSpace::Generic`. It has at least two upstream producers, so IR-dump the final pass and find which producer left `Generic`, and on which trigger, before folding a new crash into an existing issue ([≥2 root causes — don't fold by message](../learnings/1783459810353-metal-unknown-addressspace-encountered-has-2-disti.md)).

1. **Fragment entry-point out-param (#11969).** `legalizeEntryPointVaryingParamsForMetal` runs the out-param→return-struct conversion (`lowerOutParameters`) only for `Stage::Vertex`, so a fragment `out float4 : SV_Target` reaches emit as a pointer param. The machinery is already stage-agnostic (`wrapReturnValueInStruct` has a `Stage::Fragment` branch), so the fix drops the vertex-only gate; patching the emit switch would mask the producer bug ([fragment out-param crash](../learnings/1783421444820-metal-fragment-out-param-crash-out-return-struct-l.md)).
2. **Uncalled `export`/library function with a by-reference param (#11981, #14005).** `AddressSpaceContext::processModule` seeds its worklist only from `IREntryPointDecoration` funcs (`slang-ir-specialize-address-space.cpp:676`), so an `export` or `[DllExport]` function that nothing calls keeps `Generic` on every by-reference param. #11981 covered `out`/`inout`; #14005 shows a plain by-value struct or array `in` param crashes too, because `transformParamsToConstRef` (`slang-ir-transform-params-to-constref.cpp:346`) rewrites those for Metal, CPU, CUDA and SPIR-V into `BorrowInParam(T, Generic)`. An `export` from a precompiled `.slang-module` that the entry point never calls crashes the same way. The discriminator is export-linkage on a by-reference param, not "no entry point" (the auto-filed "add an entry point" workaround is wrong; verified by crossed controls). SPIR-V and WGSL treat `Generic` as Function storage and CPU/CUDA ignore it, so only Metal aborts (`slang-emit-metal.cpp:1469` on 2026-10-29 master). Skipping exports in `transformParamsToConstRef` is not a fix: Metal requires array params by reference (`slang-emit.cpp:2672`), and it leaves out/inout broken. The principled fix seeds exported functions in the address-space pass and defaults library-boundary by-ref params to `thread`/`ThreadLocal`. Bot draft PR #12014 has that design but, as of 2026-10-29, conflicts with #13648 ([trigger is export-linkage, not missing entry point](../learnings/1783460634599-metal-unknown-addressspace-on-export-out-inout-par.md), [by-value struct/array params of uncalled exports also trigger it (#14005)](../learnings/1793266542170-metal-unknown-addressspace-by-value-struct-array-p.md)).

Fast discriminators: crashes only in `-whole-program` with no `[shader]`, compiles once a concrete entry point is added, HLSL emits fine ⇒ #11981, not #11969. Pass internals behind item 2 (worklist roots, clone keys, the `newWorkList` hang) are on [IR address-space specialization](slang-compiler-ir-address-space-specialization.md).

## DescriptorHandle

### In-buffer emits illegal `device T* device*` (#11970)

On `-target metal`, `StructuredBuffer<DescriptorHandle<StructuredBuffer<uint>>>` emits `uint device* device* p [[buffer(0)]]`: Metal's `isResourceTypeBindless` always returns true, so the element `DescriptorHandle<R>` emits `R` directly and the outer `StructuredBuffer` binding adds another `device*`. `MetalPointerBufferElementTypeLoweringPolicy` already owns this shape, but its discovery filter `needsElementLowering` recurses only into `IRPtrType`/array/struct and never matches `IRDescriptorHandleType` — that filter gap is the fix layer. Prefer the reporter's struct-wrap (1-member struct, ABI byte-identical, covers buffer and texture) over lowering to UIntPtr, which can't handle the texture case. Arrays-of-resources are a separate FEATURE GAP (MSL has no native array-of-buffers/textures) under umbrella #10842 ([an existing pass owns the shape but its filter misses it](../learnings/1783421582372-metal-descriptorhandle-in-buffer-emits-illegal-dev.md)).

### #10842: compiler emit done, slang-rhi runtime is the gap

"DescriptorHandle support on Metal" is a slang-rhi RUNTIME gap. Emit is done at HEAD: `slang-emit-metal.cpp:148` unwraps `DescriptorHandle<T>` to T's native bindless layout, `CastDescriptorHandleToUInt64` exists, and the any-value bindless marshalling works. The RHI Metal backend has no `getDescriptorHandle` override (all inherit the `SLANG_E_NOT_AVAILABLE` base), advertises only `Feature::ArgumentBufferTier2` (not `Feature::Bindless`), and `git log -S getDescriptorHandle -- src/metal/` is empty; tracker #11540's "Metal bindless was added" meant emit, so verify the runtime empirically. The combined-texture-sampler limit is real: `DescriptorHandle::value` is one `uint64_t`, while Metal combined = texture `gpuResourceID` (64b) + sampler `gpuResourceID` (64b) (D3D12 fits only because its 32-bit heap indices pack 2-into-64); separate buffer/texture/sampler handles each fit. Fix shape (slang-rhi PR): `metal-bindless-descriptor-set.{h,cpp}`, `addFeature(Feature::Bindless)` gated on ArgumentBufferTier2, and `getDescriptorHandle` returning the RAW native 64-bit id (the arg buffer stores the id, not a heap index). It is GPU/macOS-only, so it relies on macOS CI; maintainer jhelferty-nv closed combined as won't-do ([compiler-emit DONE, runtime is the gap; combined won't fit](../learnings/1784918108597-metal-descriptorhandle-10842-compiler-emit-done-sl.md)).

## Uniform Resource Array Drops `[[buffer/texture(N)]]` (#12291)

`uniform MyTensor tensors[4]` with `MyTensor{StructuredBuffer<float> buf;}` emits a kernel arg `array<float device*, int(4)>` with no `[[buffer(N)]]` on `-target metal`, while SPIR-V (descriptor array + Binding) and CUDA are correct (motivating case: slangpy `Tensor<float,1>[4]`). `buf` is hoisted into one bare array-of-device-pointer param with no binding; `tensors_buf[i]` indexing is correct, so the defect is BINDING SHAPE ([unbound array-of-device-pointer](../learnings/1785418004751-metal-emits-unbound-array-of-device-pointer-for-un.md)). The reporter's site (`introduceExplicitGlobalContext`) is wrong: layout is correct (`createArrayLikeTypeLayout` keeps the `MetalBuffer` offset-kind ×count; Metal is not `_isDescriptorSlotLike`) and that pass clones type+layout faithfully. The drop is emit-only: `MetalSourceEmitter::emitFuncParamLayoutImpl` emits `[[buffer(N)]]` for `MetalBuffer` only when `paramType` is a pointer/structured-buffer/byte-address/param-group/AS type, and `IRArrayType` matches none (same gap for `MetalTexture` and `SamplerState`). VK differs because `slang-emit-spirv.cpp` decorates `Binding` by resource kind with no type-shape guard. A 4-way contrast (single/array × struct-wrapped/bare × buffer/texture) localizes the trigger without a rebuild ([emit-guard type-shape gap, not explicit-global-context](../learnings/1785419415403-metal-drops-buffer-texture-n-for-uniform-array-of-.md)). Open (needs macOS/`-target metallib`): admitting `IRArrayType` is clean for texture/sampler arrays (`array<texture2d,N> [[texture(k)]]` is native), but arrays of buffers are not valid direct kernel args (≤ Metal 3.1), so the buffer case likely needs argument-buffer legalization — consistent with #10842's FEATURE GAP.

## KernelContext Copies Bound Resource Arrays Per Invocation (#13894)

Issue #13894 (from PR #13473, at jkwak-work's request) asks who copies a bound resource array per invocation; checked at master d29325a:

- **Metal copies.** Every global shader param becomes a by-value kernel argument that `createContextForEntryPoint` stores into `KernelContext` (`slang-ir-explicit-global-context.cpp:545`), so a `Texture2D[96]` is copied per invocation, and `replaceUsesOfGlobalParam` loads the WHOLE field at each use (:651). A branch between that load and the `getElement` makes the C-like emitter write a whole-array temp; a `__constref` call site also gets a temp copy.
- **CUDA and CPU do not.** CUDA skips GlobalParam hoisting (:245, `__constant__ SLANG_globalParams`); CPU holds one `GlobalParams*`. Both index in place.
- **CUDA still copies an ENTRY-POINT array passed to a helper.** `uniform Texture2D[96]` passed to `f` emits `FixedArray<CUtexObject,96> _S6 = textures_0; f(&_S6)`. NVCC removes it when the helper inlines; with `[noinline]`, `ptxas -v` reports a 768-byte stack frame. nvcc 12.6 is at `/usr/local/cuda/bin` in prod containers; `-Xptxas -v` shows whether an emitted copy survives.

A Metal-only symptom does not show which layer is at fault; compare the same shader per target ([who copies bound resource arrays per invocation](../learnings/1792778820104-metal-vs-cuda-cpu-who-copies-bound-resource-arrays.md)). The same pass on WGSL, with a uniform-only hoisting policy: [[wiki/concepts/slang-backends-wgsl-uniformity-and-shadow-globals.md]].

## Pointer to a Vector Lane = Scalar Pointer Plus Offset (#13551)

Consider `InterlockedAdd(buf[i].v.x, 1)` with `v` a `uint4`. MSL follows clang ext_vector rules: `&v[i]` and `&v.x` fail with "address of vector element requested", while `((T device*)&v) + i` is accepted. With no Metal `GetElementPtr` override, a pointer-valued GEP into a vector or `MetalPackedVec` falls through to the C-like path (slang-emit-c-like.cpp:2875-2903) and emits `&base[i]`, breaking every vector-lane atomic on 2026-10 master (InterlockedAdd/CAS/Max/Exchange on `buf[i].v.x`, a groupshared `uint4` lane, a matrix element). `legalizeFuncBody` (metal-legalize.cpp:63-118) temp-copies vector-lane CALL arguments, which cannot serve atomics. A `tryEmitInstExprImpl` override emitting `((T as*)(base)) + i` fixes every shape and mirrors slang-emit-cpp.cpp:1610. Check without a Mac: `clang -fsyntax-only` on `typedef unsigned u4 __attribute__((ext_vector_type(4)));` with `&s->v[0]`. Separately, tests/functional/codegen.slang fails 0/7 on master f6238cee3 (stale serialized `slang.functional` module, E00131) — not a regression signal ([scalar pointer plus an offset](../learnings/1791581328674-metal-pointer-to-a-vector-lane-must-be-emitted-as-.md)).

## Metal 4.0 Attributes vs Sub-4.0 `-std` (#11985, #12096, #11999)

The emitter emitted the Metal-4.0-only kernel attribute `[[required_threads_per_threadgroup(...)]]` for the *default* Metal target, because its gate is `getTargetCaps().implies(metallib_4_0)` and `alias metallib_latest = metallib_4_0` (flipped from `3_1` by PR #10592), while the shader compiled against sub-4.0 (offline `metal -std=metal3.1`; slang-rhi passes only `Capability::metal`). Runners whose toolchain defaults below 4.0 reject it; the CI intermittency was runner Metal-version heterogeneity, not randomness. Watch for this emit-vs-`-std` mismatch on any new gated Metal/SPIR-V feature ([#11985 = 4.0 attribute vs sub-4.0 target](../learnings/1783470139599-slang-11985-macos-ci-flake-metal-4-0-attribute-emi.md)). That diagnosis was right; a later "macOS-26 driver race" reconciliation over-corrected ([CORRECTION: #11985 original diagnosis WAS right](../learnings/1784154087503-correction-slang-11985-original-emit-4-0-vs-std3-1.md)).

**#12096 and #11999 are one root.** On `macos-26` runners four Metal gfx tests fail at `createComputePipeline` with "'required_threads_per_threadgroup' attribute requires Metal language standard metal4.0 or higher" and pass on `macos-15`. jkwak-work merged the two issues, refuting a "distinct intermittency" triage: #11999's `gpu-printing` example is a compute kernel on the same `createComputePipeline` → `metallib_4_0` path, and it only looked intermittent because `runs-on: macos-latest` served a macos-15/macos-26 mix (pinning macos-15 in #12075 made #12096 deterministic). Classify by mechanism (pipeline stage, capability path), not surface signature ([#12096 ↔ #11999 share one root](../learnings/1784062178778-slang-12096-11999-share-the-same-metallib-4-0-from.md)). An earlier reclassification of #11999 as bot conflation was also wrong: the metal4.0 signature was the root cause, so never dismiss a signature without the reproducing environment ([CORRECTION #11999 signature WAS the root cause](../learnings/1784185814547-correction-slang-11999-the-conflated-metal4-0-sign.md)).

**Fix of record: ADVANCE the `-std`, not RETREAT the cap.** The first triage blamed slang-rhi, which derives the metallib ladder from the OS version (`metal-device.cpp:266`, `osVersion.majorVersion >= 26` → `metallib_4_0`, slang-rhi PR #795), assuming "macos-26 lacks metal4.0" and "slang core is correct". PR #12009 (`aba3cd7dd`) falsified both: macos-26 supports Metal 4.0, and the defect was Slang's downstream `-std=metal3.1` hardcode. `slang-gcc-compiler-util.cpp` now emits `-std=metalX.Y` from `DownstreamCompileOptions::metalLanguageVersion`, and `slang-code-gen.cpp` sets 4.0 under the emitter's own predicate, so emit gate and `-std` cannot diverge. Invoke with `-std=metal4.0` before recommending a retreat, and check "core is correct" at the downstream `-std` layer, not only the emitter. Coverage caveat: the four `gfx-unit-test-tool/*Metal.internal` tests run in Nightly Coverage, still pinned to macos-15 (#12075), and stay unconfirmed until the pin is removed ([#12096 fix is ADVANCE in Slang-core](../learnings/1784062749848-slang-12096-fix-is-advance-to-metal4-0-in-slang-co.md)). A later slang-rhi CI atom restating the retreat framing is superseded on fix direction and contributes only coverage/residency facts; #12096 stays open on the slang-rhi side, where the OS-version inference is unchanged.

## The `-std=metalX.Y` Derivation Already Exists (#12258, #12250, #14010)

The compiler half of a MetalLib-version request is usually already in place; check `slang-code-gen.cpp` and `slang-gcc-compiler-util.cpp` first. Since #12009, `slang-gcc-compiler-util.cpp` (~:975-988) builds `-std=metal<maj>.<min>` from `options.metalLanguageVersion`, with literal `-std=metal3.1` only the unset fallback. #12258 ("Upgrade Metal compiler support on Windows to MetalLib 3.2") therefore needed only the capdef atom plus a producer setting the version from the *highest implied* metallib atom (one source of truth, not an if/else ladder); a FileCheck extending `tests/metal/threadgroup-size.slang` (already contrasting `metallib_4_0` with `metallib_3_1`) verifies it without an Apple toolchain. The headline work (Windows Apple-Metal toolchain, Windows CI on a real `.metallib`, docs) is infra the bot cannot do, so the maintainer-authored issue stayed PARK-at-triaged with the fixer briefing on HOLD ([#12258 — only producer + capdef atom are the gap](../learnings/1785287353987-slang-12258-metallib-3-2-the-std-derivation-machin.md)).

PR #12250 ("Add Metal support for printf") rewired the whole producer, so a maintainer's "the atom landed" nudge calls for re-verifying the subsystem at HEAD. It added `metallib_3_2` (chain `3_1→3_2→4_0`) and made `slang-code-gen.cpp` (~:786-804) take the max of `implies(metallib_4_0)→4.0` and `MetalExtensionTracker::getRequiredMetalLanguageVersion()`. Emit features now drive `-std` (`kIROp_Printf` calls `requireMetalLanguageVersion(3,2)` → `-std=metal3.2 -fmetal-enable-logging`), checked toolchain-free by `unit-test-metal-compile-args.cpp` through `GCCDownstreamCompilerUtil::calcArgs`. The residual gap was latent: `-capability metallib_3_2` alone still emitted `-std=metal3.1`; surface such a gap rather than auto-dispatching a fixer ([#12258 re-triage — #12250 rewired the producer](../learnings/1785463484364-slang-12258-re-triage-metallib-3-2-atom-landed-act.md)). A requested version REPLACES the fallback rather than raising it, so `requireMetalLanguageVersion(3,0)` for `atomic_float` would lower `-std` and break 3.1-only texture atomics in the same shader; request only versions above 3.1, or fix the fallback first (details on [[wiki/concepts/slang-backends-metal-atomics-fences-and-coherence.md]]) [requireMetalLanguageVersion(X) can LOWER -std](../learnings/1793316833326-metal-requiremetallanguageversion-x-can-lower-std-.md).

#14010 generalized the selection-driven half, and a by-value temporary hid the change: `CodeGenContext::getTargetCaps()` (`slang-code-gen.h:159`) returns `CapabilitySet` by value, so in `for (auto atomSet : getTargetCaps().getAtomSets())` the temporary dies at the end of the range-init and the loop iterates nothing (no crash in Release); a `-capability metallib_4_0` pin dropped to `-std=metal3.1`. Bind the set to a local first, as the CUDA SM path (`slang-code-gen.cpp` ~:609) does. To observe the Metal command line on Linux, pass `-target metallib -metal-path <dir>`, where `<dir>/metal` is an sh script that for exactly `-v` prints `Apple metal version 32023.883 (metalfe-32023.883)` to stderr (`GCCDownstreamCompilerUtil::calcVersion` parses stderr) and otherwise appends `$*` to a log and writes the `-o` file; grep the log for `-std=metalX.Y` / `-fmetal-enable-logging`. A unit test uses a private `slang_createGlobalSession` plus `setDownstreamCompilerPath(SLANG_PASS_THROUGH_METAL, dir)` so the shared session is not redirected, and writes the script as `R"sh(...)sh"` because `"$(dirname "$0")"` contains `)"` [range-for over getTargetCaps().getAtomSets() iterates a destroyed temporary](../learnings/1793283310953-slang-code-gen-range-for-over-gettargetcaps-getato.md).

## CI Signal: A Green macOS Job Does Not Mean Metal Ran

A green `build (macos, aarch64, clang, *)` slang-rhi job proves only that Metal TUs compiled: `slang-rhi-tests -check-devices` reports unsupported devices and exits 0. Run `30804222761` / job `91655709489` logged `Metal: not supported (failed to get shader entry point code)` plus the #12096 metal4.0 diagnostic (toolchain `metal 32023.883`, Xcode-16-era), yet passed with every Metal test skipped. `macos-latest` now resolves to `macos-26-arm64` (read the log's `Image:` line), slang-rhi derives the capability from the OS version (`src/metal/metal-device.cpp:266`), and on these images OS version and Metal toolchain disagree. Grep `-check-devices` output for `Metal: supported` / `Metal: not supported`, call runtime coverage *pending* while #12096 is open, and treat `Vulkan: not supported (failed to create device)` on macOS the same way. The same log's `GPUFamilyApple6 not supported; using per-encoder useResource fallback` shows the hosted runner is on the `!m_hasResidencySet` fallback residency path, so CI does not represent typical Apple-Silicon hardware for residency-sensitive work ([`-check-devices` exits 0 on unsupported](../learnings/1785756797105-slang-rhi-macos-ci-a-green-macos-job-does-not-mean.md)).

**Registered is not executed, and a zero-hit grep needs a control.** That log is column-padded (`foo.metal<many spaces>SKIPPED`), so `\.metal (PASSED|SKIPPED)` with one space matches nothing; control `grep -c '\.metal'` → **209**, padded-aware `^\S+\.metal +SKIPPED` → **207**, `^\S+\.metal +(PASSED|FAILED)` → **0**. Run a broader control grep that must be non-zero before reporting any zero. `GPU_TEST_CASE` registers a case per flagged device even when unavailable (`SKIPPED (device not available)`), so a row proves enumeration, not a run. Report "N registered, M executed"; one artifact can support one claim (residency) but not another (coverage) ([registered ≠ executed](../learnings/1785779851246-registered-is-not-executed-207-skipped-metal-rows-.md)).

**Approver false-safe (PR #12130 @ a891de261b27, bot fixer PR for #12046, Devin-only tier):** a Metal intrinsic token-count change breaks untouched Metal COUNT tests, and the approver's `ci_green` clause is blind to check-runs ([approver false-safe](../learnings/1784164727628-approver-false-safe-metal-intrinsic-token-count-ch.md)).

## Math Semantics: fmod, fp-mode, mul

**`fmod` IS Remainder** (MSL spec §6.6): trunc vs floor is the Modulus/Remainder discriminator (#12046 follow-up; jkwak-work disputed the F3 finding 4x) ([Metal fmod IS Remainder](../learnings/1784148445380-metal-fmod-is-remainder-msl-spec-6-6-trunc-vs-floo.md)).

**`-fp-mode` is ignored; MSL "safe" math still contracts (#13689).** `-fp-mode default|precise|fast` produces byte-identical MSL on `-target metal` (e49310561). `MetalSourceEmitter::emitFrontMatterImpl` (`slang-emit-metal.cpp:1906`) never reads `getFloatingPointMode()`; the MetalAIR path's `GCCDownstreamCompilerUtil` `Precise` arm (`slang-gcc-compiler-util.cpp` ~:1076) adds no flag, so Metal's default fast math applies; `emitTempModifiers` drops per-variable `precise` with E56005. Reuse the SPIR-V emitter's per-variable precise propagation (`computePreciseInsts`, `slang-emit-spirv.cpp` ~:10645, PR #12208). In MSL (spec 4.1 §1.6.3), `math_mode(safe)` / `-fmetal-math-mode=safe` sets FP contract ON, which still fuses within a statement; disabling FMA fusion needs `#pragma METAL fp contract(off)`, `#pragma STDC FP_CONTRACT OFF` or `-ffp-contract=off`. `-fno-fast-math` = `-fmetal-math-fp32-functions=precise` + `-fmetal-math-mode=safe`. `#pragma METAL fp math_mode` appears to be Metal 3.2 (§9.1) vs Slang's default `-std=metal3.1`; check version gating before emitting it. WebFetch fails on the 14 MB spec PDF; curl it and use pypdf [Metal ignores -fp-mode; safe math still contracts](../learnings/1792136773455-metal-target-ignores-fp-mode-entirely-msl-safe-mat.md).

**`mul(M,v)` → `v*M` is by design and identical to SPIR-V (#13141, predecessor #4253).** The core-module intrinsic `mul(matrix<T,N,M>, vector<T,M>)` (`hlsl.meta.slang` ~:13871-13897) emits `($1 * $0)` on Metal (GLSL/WGSL swap the same way), `mul` on HLSL, and `OpVectorTimesMatrix result $right $left` on SPIR-V. The matrix emitted for Metal/GLSL/SPIR-V is effectively the transpose of the logical matrix, so `v * M_emitted` is the intended `M · v` (csyonghe on #4253: "Metal/GLSL 'column' = HLSL 'row'"; PR #4143). Operand order cannot distinguish correct SPIR-V from wrong Metal, so reject any "reverse the Metal mul operand order" fix. All targets read one target-agnostic `getMatrixLayoutMode()`, though Metal `ParameterBlock` matrices ignore it since v2025.18.2 (see [[wiki/concepts/slang-backends-metal-buffer-lowering-and-layout-rules.md]]). The real footgun: the C API default is ROW_MAJOR (`SessionDesc.defaultMatrixLayoutMode`) while the `slangc` CLI legacy default is COLUMN_MAJOR, for every target. A Metal-vs-Vulkan transpose almost always means different layout modes, or a host upload for the other major-ness (handled in IR by `lowerMatrixAddresses` and the col-major arms of `slang-ir-lower-buffer-element-type.cpp`, not in the multiply). `slangc -target metal` confirms the codegen shape GPU-free but not the rendering defect, so without a minimal repro, correct the misconception and ask for a minimal `.slang`, the per-backend layout mode and the host-upload code before dispatching a fixer. Related: #4253, #4537 (Metal ignored layout options, fixed 2024-07-19), #6031 (col-major access, host-side transpose) ([mul(M,v)→v*M is by-design](../learnings/1789601090289-metal-mul-m-v-v-m-is-by-design-and-identical-to-sp.md)).
