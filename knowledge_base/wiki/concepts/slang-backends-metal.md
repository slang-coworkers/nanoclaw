# Slang Metal Backend Deep Dives: Address Spaces, DescriptorHandle, MetalLib Versioning

## TL;DR

- **MSL rejects a pointer to a vector lane** (`&v[i]`, `&v.x`: "address of vector element requested") but accepts `((T device*)&v) + i`. Metal has no GetElementPtr override, so every atomic on a vector/packed-vector lane or matrix element fails; the fix is a Metal `tryEmitInstExprImpl` override mirroring CPP, not the `legalizeFuncBody` call-arg temp copy (a copy is not atomic).
- `"Unknown addressspace encountered."` (`slang-emit-metal.cpp:1363`) is a SHARED symptom of ≥2 producer bugs — never fold a new crash by message alone; IR-dump to see which producer left `Generic`; fix producer-side, never with an emitter fallback: fragment out-param (#11969, vertex-only out→return-struct lowering) vs export/library mutable-ref param (#11981, worklist seeded only from entry points). Crashes only in `-whole-program` with no `[shader]`, compiles with an entry point, HLSL fine ⇒ #11981.
- `metallib_latest` aliases the newest version (`metallib_4_0` since PR #10592); gate version-gated emit on the EFFECTIVE metal language version, not `metallib_latest`.
- #12096/#11999 share one root: slang-rhi infers `metallib_4_0` from `NS::ProcessInfo` OS major ≥ 26. The fix of record is the Slang-core `-std` ADVANCE (#12009: derive `-std=metalX.Y` from `metalLanguageVersion`), not a slang-rhi retreat. "Requires version X" is ambiguous between "toolchain can't" and "we didn't ASK" — try `-std=metalX.Y` before recommending a capability retreat.
- `-std` derivation (`slang-gcc-compiler-util.cpp` + `slang-code-gen.cpp`) is FEATURE-driven since PR #12250 (`MetalExtensionTracker`); a new `metallib_X_Y` needs only the capdef atom + a highest-implied-atom producer.
- Metal `DescriptorHandle<T>` emit is DONE (#10842); the gap is the slang-rhi RUNTIME (no `getDescriptorHandle` override, only ArgumentBufferTier2). Combined texture+sampler (128b) can't fit `DescriptorHandle::value` (uint64); separate handles can.
- `DescriptorHandle`-in-buffer (#11970) and uniform array-of-resource (#12291) are EMIT-layer filter/type-shape gaps, distinct from #10842's runtime gap and #7669's wrapper-swap binding loss. #11970: prefer the reporter's struct-wrap; #12291: `IRArrayType` matches no allowed `paramType` branch in `emitFuncParamLayoutImpl`.
- A GREEN macOS CI job does NOT mean Metal ran: `slang-rhi-tests -check-devices` exits 0 on unsupported. Grep the log for `Metal: not supported`; report "N registered, M executed"; a zero-hit grep needs a non-zero control (logs are column-padded).
- Metal `fmod` IS Remainder (MSL §6.6): trunc vs floor is the Modulus/Remainder discriminator.
- **`-target metal` ignores `-fp-mode`** (byte-identical MSL), drops `precise` with E56005, and Metal defaults to fast math. MSL `math_mode(safe)` still contracts; only `fp contract(off)` / `-ffp-contract=off` stops FMA fusion.
- Metal `mul(M,v)` → `v*M` is BY DESIGN and identical to SPIR-V (`OpVectorTimesMatrix`) — reject any "reverse the Metal mul operand order" fix. A Metal-vs-Vulkan transpose comes from layout modes (C-API default ROW_MAJOR vs `slangc` CLI COLUMN_MAJOR), host upload, or a Metal `ParameterBlock` matrix (layout ignored since v2025.18.2). `reproduced` needs a Metal GPU + host upload code.

Metal-only (`slang-emit-metal.cpp`, textual MSL) failure families: pointer address-space specialization, `DescriptorHandle` emission, MetalLib `-std=metalX.Y` derivation, uniform-param cbuffer wrapping, array-of-resource binding. WGSL and cross-target issues: [[wiki/concepts/slang-backends-wgsl-metal.md]].

## Address-Space Crashes: "Unknown addressspace encountered"

`SLANG_UNEXPECTED("Unknown addressspace encountered.")` at `slang-emit-metal.cpp:1363` (the `default:` arm of the pointer-param address-space switch, hit by a pointer param carrying `AddressSpace::Generic`) has at least two distinct upstream producers, so IR-dump the final pass and check which producer left `Generic`, and on which trigger surface, before folding a new crash into an existing issue ([Metal 'Unknown addressspace encountered' has ≥2 distinct root causes — don't fold by message](../learnings/1783459810353-metal-unknown-addressspace-encountered-has-2-disti.md)).

1. **Fragment entry-point out-param (#11969).** `legalizeEntryPointVaryingParamsForMetal` runs the out-param→return-struct conversion (`lowerOutParameters`) only for `Stage::Vertex`, so a fragment `out float4 : SV_Target` reaches the emit switch as a pointer param. The machinery is already stage-agnostic (`wrapReturnValueInStruct` has a `Stage::Fragment` branch); the fix drops the vertex-only gate instead of patching the emit switch, which would mask the producer bug ([Metal fragment out-param crash — out→return-struct lowering is vertex-only](../learnings/1783421444820-metal-fragment-out-param-crash-out-return-struct-l.md)).
2. **`export`/library out/inout param (#11981).** `AddressSpaceContext::processModule` seeds its worklist only from `IREntryPointDecoration` funcs, so an `export`/public function with a mutable-reference param has no caller to specialize from and keeps `Generic`. The discriminator is export-linkage on a mutable-ref param, not "no entry point" (the auto-filed "add an entry point" workaround is wrong; verified by crossed controls). WGSL/GLSL share the seeding gap, but only Metal's emitter treats an unspecialized `Generic` pointer as fatal; the principled fix seeds exports and defaults library-boundary mutable-ref params to `thread`/`ThreadLocal`, not an emitter fallback case ([Metal 'Unknown addressspace' on export out/inout params: trigger is export-linkage, not missing entry point](../learnings/1783460634599-metal-unknown-addressspace-on-export-out-inout-par.md)).

Fast discriminators: crashes only in `-whole-program` with no `[shader]`, compiles once a concrete entry point is added, HLSL emits fine ⇒ #11981, not #11969.

## DescriptorHandle

### In-buffer emits illegal `device T* device*` (#11970)

On `-target metal`, `StructuredBuffer<DescriptorHandle<StructuredBuffer<uint>>>` emits `uint device* device* p [[buffer(0)]]`: Metal's `isResourceTypeBindless` always returns true, so the element `DescriptorHandle<R>` emits `R` directly and the outer `StructuredBuffer` binding appends another `device*`. `MetalPointerBufferElementTypeLoweringPolicy` already owns this shape, but its discovery filter `needsElementLowering` recurses only into `IRPtrType`/array/struct and never matches `IRDescriptorHandleType` — that filter gap is the fix layer. Prefer the reporter's struct-wrap (1-member struct, ABI byte-identical, covers buffer and texture) over lowering to UIntPtr (can't handle the texture sub-case). Arrays-of-resources are a separate FEATURE GAP (no native array-of-buffers/textures in MSL) under umbrella #10842 ([Metal DescriptorHandle-in-buffer emits illegal device T* device* (#11970) — an existing pass owns the shape but its filter misses it](../learnings/1783421582372-metal-descriptorhandle-in-buffer-emits-illegal-dev.md)).

### #10842: compiler emit done, slang-rhi runtime is the gap

"DescriptorHandle support on Metal" is a slang-rhi RUNTIME gap, not a compiler gap. Emit is done at HEAD: `slang-emit-metal.cpp:148` unwraps `DescriptorHandle<T>` to T's native (bindless) layout, `CastDescriptorHandleToUInt64` exists, and the any-value bindless marshalling path works. The RHI Metal backend has zero `getDescriptorHandle` overrides (all inherit the `SLANG_E_NOT_AVAILABLE` base), advertises only `Feature::ArgumentBufferTier2` (not `Feature::Bindless`), and `git log -S getDescriptorHandle -- src/metal/` is empty. Tracker #11540's "Metal bindless was added" meant the emit side; verify the runtime empirically. The combined-texture-sampler "doesn't fit" constraint is real: `DescriptorHandle::value` is one `uint64_t`, and Metal combined = texture `gpuResourceID` (64b) + sampler `gpuResourceID` (64b) = 128b (D3D12 fits only because its 32-bit heap indices pack 2-into-64); separate buffer/texture/sampler each fit one 64-bit id. Fix shape (slang-rhi PR): `metal-bindless-descriptor-set.{h,cpp}`, `addFeature(Feature::Bindless)` gated on ArgumentBufferTier2, `getDescriptorHandle` returning the RAW native 64-bit id (the arg buffer stores the id directly, not a Vulkan/D3D12-style heap index). GPU/macOS-only, so it relies on macOS CI; maintainer jhelferty-nv closed combined as won't-do ([Metal DescriptorHandle #10842: compiler-emit DONE, slang-rhi runtime is the gap; combined won't-fit is real (64b)](../learnings/1784918108597-metal-descriptorhandle-10842-compiler-emit-done-sl.md)).

## Uniform Resource Array Drops `[[buffer/texture(N)]]` (#12291)

`uniform MyTensor tensors[4]` with `MyTensor{StructuredBuffer<float> buf;}` emits a kernel arg `array<float device*, int(4)>` with no `[[buffer(N)]]` on `-target metal`, while SPIR-V (descriptor array + Binding) and CUDA are correct (motivating case: slangpy `Tensor<float,1>[4]`). In the output, `buf` is removed and the element buffers are hoisted into one bare array-of-device-pointer param with no binding (siblings have one); `tensors_buf[i]` indexing is correct, so the defect is BINDING SHAPE, not index-dropping ([Metal emits unbound array-of-device-pointer for uniform array-of-resource](../learnings/1785418004751-metal-emits-unbound-array-of-device-pointer-for-un.md)). The reporter's site (`introduceExplicitGlobalContext`, `slang-ir-explicit-global-context.cpp`) is wrong: layout is correct (`createArrayLikeTypeLayout` keeps the `MetalBuffer` offset-kind ×count; Metal is not `_isDescriptorSlotLike`) and that pass clones type+layout faithfully. The drop is emit-only: `MetalSourceEmitter::emitFuncParamLayoutImpl` emits `[[buffer(N)]]` for `MetalBuffer` only when `paramType` is a pointer/structured-buffer/byte-address/param-group/AS type, and an `IRArrayType` matches none (same gap for `MetalTexture` and `SamplerState`). VK differs because `slang-emit-spirv.cpp` decorates `Binding` by resource kind with no type-shape guard. A 4-way contrast (single/array × struct-wrapped/bare × buffer/texture) localizes the trigger to the array shape in minutes, without a rebuild ([Metal drops the buffer/texture binding for a uniform array-of-resource — emit-guard type-shape gap, not explicit-global-context (#12291)](../learnings/1785419415403-metal-drops-buffer-texture-n-for-uniform-array-of-.md)). Open question (needs macOS/`-target metallib`): admitting `IRArrayType` in the guard is clean for texture/sampler arrays (`array<texture2d,N> [[texture(k)]]` is native), but arrays of buffers are not valid direct kernel args (≤ Metal 3.1), so the buffer case likely needs Metal argument-buffer legalization — consistent with #10842 tagging plain arrays-of-resources as a FEATURE GAP.

## Pointer to a Vector Lane = Scalar Pointer Plus Offset (#13551)

Consider `InterlockedAdd(buf[i].v.x, 1)`, where `v` is a `uint4`. MSL follows clang ext_vector rules: `&v[i]` and `&v.x` fail with "address of vector element requested", while `((T device*)&v) + i` is accepted. With no Metal `GetElementPtr` override, a pointer-valued GEP into a vector or `MetalPackedVec` falls through to the C-like path (slang-emit-c-like.cpp:2875-2903) and emits `&base[i]`, breaking every vector-lane atomic on 2026-10 master (InterlockedAdd/CAS/Max/Exchange on `buf[i].v.x`, a groupshared `uint4` lane, a matrix element). `legalizeFuncBody` (metal-legalize.cpp:63-118) temp-copies vector-lane CALL arguments, which cannot serve atomics. A `tryEmitInstExprImpl` override emitting `((T as*)(base)) + i` fixes all these shapes and mirrors slang-emit-cpp.cpp:1610. Check without a Mac: `clang -fsyntax-only` on `typedef unsigned u4 __attribute__((ext_vector_type(4)));` with `&s->v[0]`. Separately, tests/functional/codegen.slang fails 0/7 on master f6238cee3 (stale serialized `slang.functional` module, E00131) — not a regression signal ([Metal pointer to a vector lane must be a scalar pointer plus an offset](../learnings/1791581328674-metal-pointer-to-a-vector-lane-must-be-emitted-as-.md)).

## Metal 4.0 Attributes vs Sub-4.0 `-std` (#11985, #12096, #11999)

The emitter emits the Metal-4.0-only kernel attribute `[[required_threads_per_threadgroup(...)]]` for the *default* Metal target because the gate is `getTargetCaps().implies(metallib_4_0)` and `alias metallib_latest = metallib_4_0` (flipped from `3_1` by PR #10592), while the shader compiles against sub-4.0 (offline `metal -std=metal3.1`; slang-rhi passes only `Capability::metal`, no 4.0 language version). Any runner whose toolchain defaults below 4.0 rejects it; the CI intermittency is free-runner Metal-version heterogeneity, not randomness. Watch for this mismatch on any new gated Metal/SPIR-V feature ([slang#11985 macOS CI flake = Metal 4.0 attribute emitted vs sub-4.0 compile target](../learnings/1783470139599-slang-11985-macos-ci-flake-metal-4-0-attribute-emi.md)). This emit-4.0-vs-std-3.1 diagnosis was right; a later "macOS-26 driver race" reconciliation over-corrected (it corrects [[learning: slang#11985 Metal diagnosis was plausible-but-wrong: inferred attribute→gpu-printing link the log never supported]]) ([CORRECTION: slang#11985 original emit-4.0-vs-std3.1 diagnosis WAS right; "macOS-26 driver race" reconciliation over-corrected](../learnings/1784154087503-correction-slang-11985-original-emit-4-0-vs-std3-1.md)).

**#12096 and #11999 are one root.** #12096 is the formal Metal-4 slice of #11985: on `macos-26` runners four Metal gfx tests fail at `createComputePipeline` with `'required_threads_per_threadgroup' attribute requires Metal language standard metal4.0 or higher` (pass on `macos-15`). jkwak-work merged it with #11999, refuting a "distinct intermittency" triage: `gpu-printing` (#11999's example) is a `[shader("compute")]` kernel on the same `createComputePipeline` → `metallib_4_0` path; #11999's graphics examples passed `createDevice` on the same failing runner (not a device flake); and #11999 only looked intermittent because `runs-on: macos-latest` served a macos-15/macos-26 mix — pinning to macos-15 (#12075) made #12096 deterministic. Classify by mechanism (pipeline stage / capability path), not surface signature (intermittent/deterministic, silent/printed) ([#12096 ↔ #11999 share the same metallib_4_0-from-OS root](../learnings/1784062178778-slang-12096-11999-share-the-same-metallib-4-0-from.md)). An earlier reclassification of #11999 as bot conflation was wrong: the "conflated" metal4.0 signature was the root cause — verify CI logs, but don't dismiss a signature without the reproducing environment ([CORRECTION slang#11999 — the "conflated" metal4.0 signature WAS the root cause; don't dismiss without the reproducing env](../learnings/1784185814547-correction-slang-11999-the-conflated-metal4-0-sign.md)).

**Fix of record: ADVANCE the `-std`, not RETREAT the cap.** The first triage put the fix in slang-rhi (stop advertising `metallib_4_0` on macos-26), premised on `external/slang-rhi/src/metal/metal-device.cpp:266` deriving the metallib ladder purely from `NS::ProcessInfo operatingSystemVersion()` (`if (osVersion.majorVersion >= 26) addCapability(Capability::metallib_4_0)`, slang-rhi PR #795), plus "the macos-26 toolchain lacks metal4.0" and "slang core is correct". PR #12009 (`fix/issue-11999`, commit `aba3cd7dd`, verified green) falsified both: macos-26 genuinely supports Metal 4.0, and the defect was Slang's downstream `-std=metal3.1` hardcode rejecting its own correct 4.0 attribute. `slang-gcc-compiler-util.cpp:978-987` now emits `-std=metalX.Y` from `options.metalLanguageVersion` (new `SemanticVersion` field on `DownstreamCompileOptions`; master hardcoded 3.1 at `:973`), and the producer `slang-code-gen.cpp` sets 4.0 when `getTargetCaps().implies(metallib_4_0)` — the emitter's own predicate, so emit gate and `-std` cannot diverge. "Requires version X" is ambiguous between "toolchain can't" and "we didn't ask": invoke with `-std=metal4.0` before recommending a retreat. "Slang core is correct" had been checked against the emitter, not the downstream `-std` layer that was the bug site. Coverage caveat: #12009's green macOS jobs exercise the path via the re-enabled `gpu-printing` example, but the four `gfx-unit-test-tool/*Metal.internal` tests run in Nightly Coverage, still pinned to macos-15 (#12075), and stay unconfirmed until that pin is removed ([slang#12096 fix is ADVANCE-to-metal4.0 in Slang-core (-std derivation), NOT slang-rhi retreat](../learnings/1784062749848-slang-12096-fix-is-advance-to-metal4-0-in-slang-co.md)). A later slang-rhi CI atom restating the retreat framing is superseded on fix direction; it contributes only the coverage/residency facts below. #12096 is still open on the slang-rhi side, where the OS-version inference is unchanged.

## CI Signal: A Green macOS Job Does Not Mean Metal Ran

A green `build (macos, aarch64, clang, *)` slang-rhi job proves only that Metal TUs compiled: `slang-rhi-tests -check-devices` reports unsupported devices and exits 0, so a fully-skipped Metal backend looks like a passing one. Run `30804222761` / job `91655709489` logged `Metal: not supported (failed to get shader entry point code)` plus the #12096 `'required_threads_per_threadgroup' attribute requires Metal language standard metal4.0 or higher` diagnostic (toolchain `metal 32023.883`, Xcode-16-era), yet reported success with every Metal test skipped. `macos-latest` now resolves to the `macos-26-arm64` image (read the log's `Image:` line; never assume macOS 15), slang-rhi derives the capability from the OS version (`src/metal/metal-device.cpp:266`), and on these images the OS version and the Metal toolchain disagree. Grep the `-check-devices` output for `Metal: supported` / `Metal: not supported`, call runtime coverage *pending* while #12096 is open, and treat `Vulkan: not supported (failed to create device)` on macOS the same way. The same log's `GPUFamilyApple6 not supported; using per-encoder useResource fallback` shows the hosted runner uses Metal's `!m_hasResidencySet` fallback residency path, so CI does not represent typical Apple-Silicon hardware for residency-sensitive work ([a green slang-rhi macOS job does not mean Metal was tested — `-check-devices` exits 0 on unsupported](../learnings/1785756797105-slang-rhi-macos-ci-a-green-macos-job-does-not-mean.md)).

**Registered is not executed, and a zero-hit grep needs a control.** On that log, `\.metal (PASSED|SKIPPED)` with a single space matches nothing because the log is column-padded (`foo.metal<many spaces>SKIPPED`); the control `grep -c '\.metal'` → **209**, padded-aware `^\S+\.metal +SKIPPED` → **207**. Before reporting any zero, run a broader control grep that must be non-zero. Don't over-retract either: `^\S+\.metal +(PASSED|FAILED)` → **0**, and `GPU_TEST_CASE` registers a case per flagged device even when unavailable (printing `SKIPPED (device not available)`), so a row proves enumeration, not a run. Report "N registered, M executed"; one artifact can support one claim (residency) but not another (coverage) ([registered ≠ executed: 207 SKIPPED `.metal` rows vs 0 PASSED, and why a zero-hit grep needs a control](../learnings/1785779851246-registered-is-not-executed-207-skipped-metal-rows-.md)).

**Approver false-safe (PR #12130 @ a891de261b27, bot fixer PR for #12046, Devin-only tier):** a Metal intrinsic token-count change breaks untouched Metal COUNT tests, and the approver's `ci_green` clause is blind to check-runs ([[approver/false-safe] Metal intrinsic token-count change breaks untouched Metal COUNT tests; ci_green clause is blind to check-runs](../learnings/1784164727628-approver-false-safe-metal-intrinsic-token-count-ch.md)).

## Math Semantics: fmod, fp-mode, mul

**`fmod` IS Remainder** (MSL spec §6.6): trunc vs floor is the Modulus/Remainder discriminator (shader-slang/slang#12046 follow-up; jkwak-work disputed the F3 finding 4x) ([Metal fmod IS Remainder (MSL spec §6.6): trunc vs floor is the Modulus/Remainder discriminator](../learnings/1784148445380-metal-fmod-is-remainder-msl-spec-6-6-trunc-vs-floo.md)).

**`-fp-mode` is ignored; MSL "safe" math still contracts (#13689).** `-fp-mode default|precise|fast` produces byte-identical MSL on `-target metal` (e49310561). `MetalSourceEmitter::emitFrontMatterImpl` (`slang-emit-metal.cpp:1906`) never reads `getFloatingPointMode()`; the MetalAIR path goes through `GCCDownstreamCompilerUtil`, whose `Precise` arm (`slang-gcc-compiler-util.cpp` ~:1076) adds no flag, so Metal's default fast math applies; and `MetalSourceEmitter::emitTempModifiers` drops per-variable `precise` with E56005. Reuse the SPIR-V emitter's private per-variable precise propagation (`computePreciseInsts`, `slang-emit-spirv.cpp` ~:10645, PR #12208). In MSL (spec 4.1 §1.6.3), `math_mode(safe)` / `-fmetal-math-mode=safe` sets FP contract ON, which still fuses within a statement; disabling FMA fusion needs `#pragma METAL fp contract(off)`, `#pragma STDC FP_CONTRACT OFF` or `-ffp-contract=off`. `-fno-fast-math` equals `-fmetal-math-fp32-functions=precise` plus `-fmetal-math-mode=safe`. `#pragma METAL fp math_mode` appears to be Metal 3.2 (§9.1) vs Slang's default `-std=metal3.1`; check version gating before emitting it. WebFetch fails on the 14 MB spec PDF; curl it and use pypdf [Metal ignores -fp-mode; MSL safe math still contracts](../learnings/1792136773455-metal-target-ignores-fp-mode-entirely-msl-safe-mat.md).

**`mul(M,v)` → `v*M` is by design and identical to SPIR-V (#13141, 2024 predecessor #4253).** `mul(matrix<T,N,M>, vector<T,M>)` is a core-module intrinsic (`hlsl.meta.slang:13871-13897`) with a per-target `__target_switch`: Metal emits `"($1 * $0)"` (:13879), GLSL/WGSL swap the same way, HLSL uses `mul` (no swap), and SPIR-V emits `OpVectorTimesMatrix result $right $left` (:13881-83) — the same v·M order. The matrix Slang emits for Metal/GLSL/SPIR-V is effectively the transpose of the logical matrix, so `v * M_emitted` == the intended `M · v` (csyonghe on #4253: "Metal/GLSL 'column' = HLSL 'row'"; fix PR #4143 / commit 1dcd814f50, still intact). So operand order can never distinguish correct-SPIR-V from wrong-Metal; reject any "reverse the Metal mul operand order" fix. All targets read one target-agnostic `getMatrixLayoutMode()` (`slang-type-layout.cpp:3058,4296`), but Metal `ParameterBlock` matrices ignore it since v2025.18.2 (see [[wiki/concepts/slang-backends-metal-buffer-lowering-and-layout-rules.md]]). The real footgun: the C API default is ROW_MAJOR (`SessionDesc.defaultMatrixLayoutMode`, `slang.h:4452`) while the `slangc` CLI legacy default is COLUMN_MAJOR (`slang-end-to-end-request.cpp:1311-1313`), uniformly for all targets. A Metal-vs-Vulkan transpose almost always means (a) the builds used different layout modes or (b) the host uploaded bytes for the other major-ness (matrix storage, handled in IR lowering — `lowerMatrixAddresses` GetElementPtr index-swap + `slang-ir-lower-buffer-element-type.cpp` col-major arms — not the multiply). Confirm codegen shape GPU-free with `slangc -target metal`, but don't mark `reproduced` from it: the rendering defect needs a Metal GPU + the host upload code.
