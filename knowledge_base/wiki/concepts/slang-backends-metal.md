# Slang Metal Backend Deep Dives: Address Spaces, DescriptorHandle, MetalLib Versioning

The Metal (`slang-emit-metal.cpp`) backend is a textual MSL target with several deep-dive failure families that do not overlap with WGSL: pointer address-space specialization, `DescriptorHandle` buffer/texture emission, the MetalLib language-version (`-std=metalX.Y`) derivation ladder, uniform-param cbuffer wrapping, and array-of-resource binding. This page covers the Metal-only issues; WGSL-specific and cross-target (WGSL+Metal) emission issues live on the sibling page [[wiki/concepts/slang-backends-wgsl-metal.md]].

## TL;DR

- Metal's `"Unknown addressspace encountered."` throw (`slang-emit-metal.cpp:1363`, the pointer-param address-space switch `default:` arm) is a SHARED symptom of ≥2 distinct producer bugs — do NOT fold a new crash into an existing issue by message alone; IR-dump the final pass to see WHICH producer left `Generic`. Fragment out-param (#11969, vertex-only out→return-struct lowering) vs export/library mutable-ref param (#11981, worklist seeded only from entry points). Fast discriminators: crashes only in `-whole-program` with no `[shader]`, adding a concrete entry point compiles, HLSL emits fine ⇒ the library cause.
- The principled fix for an unspecialized-`Generic`-pointer crash is PRODUCER-side (seed the address-space worklist / drop a vertex-only gate), never an emitter fallback case that masks the producer bug.
- `metallib_latest` is aliased to the newest version (`metallib_4_0` since PR #10592); emitting a version-gated attribute against `metallib_latest` while the downstream `-std` is lower is a structural mismatch. Gate emit on the EFFECTIVE metal language version, not `metallib_latest`.
- #12096/#11999 root cause is the same `metallib_4_0`-from-OS-version inference (slang-rhi derives the cap from `NS::ProcessInfo` OS major ≥ 26). The FIX OF RECORD is the Slang-core `-std` ADVANCE (#12009: derive `-std=metalX.Y` from `metalLanguageVersion`), NOT a slang-rhi retreat. An error "requires version X" is ambiguous between "toolchain can't" and "we didn't ASK" — invoke with `-std=metalX.Y` before recommending a capability retreat.
- The `-std=metalX.Y` derivation machinery already exists (`slang-gcc-compiler-util.cpp` + `slang-code-gen.cpp`); PR #12250 (Metal printf) made it FEATURE-driven via `MetalExtensionTracker`. A new `metallib_X_Y` needs only the capdef atom + generalizing the producer to the highest-implied atom — not emitter/`-std`-assembler changes.
- Metal `DescriptorHandle<T>` compiler-emit is DONE at HEAD (#10842); the gap is the slang-rhi RUNTIME (no `getDescriptorHandle` override, advertises only ArgumentBufferTier2). Combined texture+sampler (128b) can't fit `DescriptorHandle::value` (uint64); separate handles are feasible.
- `DescriptorHandle`-in-buffer (#11970) and array-of-resource (#12291) are EMIT-layer filter/type-shape gaps, distinct from the #10842 runtime gap and #7669's wrapper-swap binding loss. Prefer the reporter's struct-wrap for #11970; #12291's `IRArrayType` matches no allowed `paramType` branch in `emitFuncParamLayoutImpl`.
- A GREEN macOS CI job does NOT mean Metal ran: `slang-rhi-tests -check-devices` exits 0 on unsupported, so a fully-skipped Metal backend looks identical to a passing one. Grep the log for `Metal: not supported`; report "N registered, M executed", never a bare pass. A zero-hit grep needs a non-zero control (logs are column-padded).
- Metal `fmod` IS Remainder (MSL §6.6): trunc vs floor is the Modulus/Remainder discriminator.

## Metal Address-Space Crashes: "Unknown addressspace encountered"

The Metal emitter throw `SLANG_UNEXPECTED("Unknown addressspace encountered.")` at `slang-emit-metal.cpp:1363` (the `default:` arm of the pointer-param address-space switch, hit when a pointer param carries `AddressSpace::Generic`) is a **shared symptom of at least two distinct upstream producer bugs** — do NOT fold a new Metal addrspace crash into an existing issue by message alone; IR-dump the final pass and check *which* producer left `Generic` and on *which* trigger surface ([Metal 'Unknown addressspace encountered' has ≥2 distinct root causes — don't fold by message](../learnings/1783459810353-metal-unknown-addressspace-encountered-has-2-disti.md)). (1) **Fragment entry-point out-param (#11969):** `legalizeEntryPointVaryingParamsForMetal` runs the out-param→return-struct conversion (`lowerOutParameters`) only for `Stage::Vertex`, so a fragment `out float4 : SV_Target` survives as a pointer-typed param into the emit switch. The conversion machinery is already stage-agnostic (`wrapReturnValueInStruct` even has a `Stage::Fragment` branch) — fix drops the vertex-only gate rather than patching the consumer emit switch (which would mask the producer bug) ([Metal fragment out-param crash — out→return-struct lowering is vertex-only](../learnings/1783421444820-metal-fragment-out-param-crash-out-return-struct-l.md)). (2) **`export`/library out/inout param (#11981):** `AddressSpaceContext::processModule` seeds its worklist ONLY from `IREntryPointDecoration` funcs, so an `export`/public function with a mutable-reference param has no caller to specialize its address space from and keeps `Generic` — the real discriminator is *export-linkage on a mutable-ref param*, NOT "no entry point" (the auto-filed "add an entry point" workaround is wrong; verified by crossed controls). WGSL/GLSL share the same worklist-seeding gap but only Metal *crashes* because only its emitter treats an unspecialized `Generic` pointer as fatal — so the principled fix is producer-side (seed exports + default library-boundary mutable-ref params to `thread`/`ThreadLocal`), not an emitter fallback case ([Metal 'Unknown addressspace' on export out/inout params: trigger is export-linkage, not missing entry point](../learnings/1783460634599-metal-unknown-addressspace-on-export-out-inout-par.md)). Fast discriminators between the two: does it crash only in `-whole-program` with no `[shader]`, does adding a concrete entry point make it compile, does HLSL emit fine? Yes-to-all ⇒ the library/worklist cause (#11981), not the entry-point varying-param cause (#11969).

## Metal DescriptorHandle-in-Buffer Emits Illegal `device T* device*` (#11970)

On `-target metal`, `StructuredBuffer<DescriptorHandle<StructuredBuffer<uint>>>` emits illegal MSL (`uint device* device* p [[buffer(0)]]`) because Metal's `isResourceTypeBindless` always returns true, so a `DescriptorHandle<R>` buffer *element* emits `R` directly and the outer `StructuredBuffer` binding appends another `device*`. A pass already owns exactly this shape — `MetalPointerBufferElementTypeLoweringPolicy` — but its discovery filter `needsElementLowering` recurses only into `IRPtrType`/array/struct and never matches `IRDescriptorHandleType`, so it never fires; that filter gap is the precise fix layer. Recommended shape is the reporter's struct-wrap (a 1-member struct, ABI byte-identical, covers both buffer and texture) rather than lowering to UIntPtr (which can't handle the texture sub-case). Keep this tractable descriptor fix distinct from arrays-of-resources on Metal, a genuine FEATURE GAP (no native array-of-buffers/textures in MSL) belonging to umbrella #10842 ([Metal DescriptorHandle-in-buffer emits illegal device T* device* (#11970) — an existing pass owns the shape but its filter misses it](../learnings/1783421582372-metal-descriptorhandle-in-buffer-emits-illegal-dev.md)).

## Metal 4.0-Only Attributes Emitted Against Sub-4.0 Target (#11985)

The Metal emitter emits the Metal-4.0-only kernel attribute `[[required_threads_per_threadgroup(...)]]` unconditionally for the *default* Metal target — the gate is `getTargetCaps().implies(metallib_4_0)` and `alias metallib_latest = metallib_4_0` (flipped from `3_1` by PR #10592) — while the shader is compiled against sub-4.0 (offline `metal -std=metal3.1`; slang-rhi passes only `Capability::metal` with no 4.0 language version). So emit says 4.0, target says <4.0, and it is rejected on any runner whose Metal toolchain defaults below 4.0 — the CI intermittency is free-runner Metal-version heterogeneity, not randomness. `metallib_latest` hardcoded to the newest version is a structural mismatch to watch on any new gated Metal/SPIR-V feature; the fix gates emit on the *effective* metal language version, not `metallib_latest` ([slang#11985 macOS CI flake = Metal 4.0 attribute emitted vs sub-4.0 compile target](../learnings/1783470139599-slang-11985-macos-ci-flake-metal-4-0-attribute-emi.md)).

### #12096 macos-26 Metal-4 regression: fix is ADVANCE the `-std`, not RETREAT the cap

**slang#12096** is the formal Metal-4 root-cause slice of #11985: on `macos-26` CI runners four Metal gfx tests fail at `createComputePipeline` with `'required_threads_per_threadgroup' attribute requires Metal language standard metal4.0 or higher` (pass on `macos-15`). It shares the SAME `metallib_4_0`-from-OS root as #11999 — the maintainer (jkwak-work) merged the two as one root problem, correctly refuting an earlier "distinct intermittency" triage: `gpu-printing` (the #11999 example) is a `[shader("compute")]` kernel that hits the exact same `createComputePipeline` → `metallib_4_0` path, the #11999 graphics examples PASSED past `createDevice` on the same failing runner (so it fails on the compute path, not a device flake), and #11999 only *looked* intermittent because `runs-on: macos-latest` served a macos-15/macos-26 mix — pinning to macos-15 (#12075) made #12096 deterministic. Triage lesson: weight *mechanism* (which pipeline stage / capability path) over *surface signature* (intermittent-vs-deterministic, silent-vs-printed) when classifying two failures as distinct ([#12096 ↔ #11999 share the same metallib_4_0-from-OS root](../learnings/1784062178778-slang-12096-11999-share-the-same-metallib-4-0-from.md)).

**Supersession — the first triage verdict was WRONG.** The initial verdict was "the fix belongs in slang-rhi (retreat: stop advertising `metallib_4_0` on macos-26, drop to 3.1)", premised on `external/slang-rhi/src/metal/metal-device.cpp:266` deriving the metallib ladder purely from `NS::ProcessInfo operatingSystemVersion()` (`if (osVersion.majorVersion >= 26) addCapability(Capability::metallib_4_0)`, introduced by slang-rhi PR #795) plus "the macos-26 toolchain LACKS metal4.0" and "slang core is correct, no core change" ([slang#12096 macos-26 Metal-4 fix belongs in slang-rhi (OS-version capability inference)](../learnings/1784051017162-slang-12096-macos-26-metal-4-fix-belongs-in-slang-.md)). **Both premises were falsified by the fix that actually landed** (PR #12009 on `fix/issue-11999`, commit `aba3cd7dd`, verified green): the RHI's per-OS 4.0 advertisement is *correct* (macos-26 genuinely supports Metal 4.0), and the defect is Slang's **downstream `-std=metal3.1` hardcode** rejecting its own correctly-emitted 4.0 attribute — a SLANG-CORE change, not a slang-rhi retreat. `slang-gcc-compiler-util.cpp:978-987` now emits `-std=metalX.Y` from `options.metalLanguageVersion` (master still hardcodes 3.1 at `:973`); the producer `slang-code-gen.cpp` sets `metalLanguageVersion = 4.0` when `getTargetCaps().implies(metallib_4_0)` — the same predicate the emitter uses, so emit-gate and downstream-`-std` cannot diverge (new `SemanticVersion metalLanguageVersion` field on `DownstreamCompileOptions`). Reusable lesson: an error "requires version X" is ambiguous between "toolchain can't do X" and "we didn't *ask* for X" — distinguish them (invoke with `-std=metal4.0` and see) before recommending a capability RETREAT; the fix that ADVANCES the request is often right where the retreat is wrong. Also, "slang core is correct" was verified only against the *emitter* (reactive, correct) but never against the *downstream-compile* `-std`-construction layer, which is also slang-core and was the actual bug site. Coverage caveat: #12009's green macOS jobs exercise the same compute→`createComputePipeline`→metal4.0 path via the re-enabled `gpu-printing` example, but the four specific `gfx-unit-test-tool/*Metal.internal` tests run in the Nightly Coverage workflow still pinned to macos-15 (#12075), so they aren't directly confirmed until that pin is removed ([slang#12096 fix is ADVANCE-to-metal4.0 in Slang-core (-std derivation), NOT slang-rhi retreat](../learnings/1784062749848-slang-12096-fix-is-advance-to-metal4-0-in-slang-co.md)).

## Metal DescriptorHandle (#10842): Compiler-Emit Done, slang-rhi Runtime Is the Gap (2026-07-24 fold)

"DescriptorHandle support on Metal" is a **slang-rhi RUNTIME** gap, not a compiler gap — two layers easy to conflate. The compiler/emit side is ALREADY DONE at HEAD: `slang-emit-metal.cpp:148` unwraps `DescriptorHandle<T>` to T's native (bindless) layout, `CastDescriptorHandleToUInt64` exists, and the any-value bindless marshalling path works — no compiler work needed. The RHI runtime side is the actual gap: the Metal backend has **zero** `getDescriptorHandle` overrides (all inherit the `SLANG_E_NOT_AVAILABLE` base), Metal advertises only `Feature::ArgumentBufferTier2`, not `Feature::Bindless`, and `git log -S getDescriptorHandle -- src/metal/` is empty (never landed). Beware a prior tracker (#11540) claiming "Metal bindless was added" — that was the EMIT side; verify the RHI runtime empirically. The **combined-texture-sampler "doesn't fit in expected bits" is a real constraint**: `DescriptorHandle::value` is a single `uint64_t`, and Metal combined = texture `gpuResourceID` (64b) + sampler `gpuResourceID` (64b) = 128b; D3D12 fits combined only because its handles are 32-bit heap indices packed 2-into-64, but Metal IDs are full 64-bit so the trick fails — separate buffer/texture/sampler each fit one 64-bit native id and are feasible. Fix shape (slang-rhi PR): `metal-bindless-descriptor-set.{h,cpp}`, `addFeature(Feature::Bindless)` gated on ArgumentBufferTier2, `getDescriptorHandle` returning the RAW native 64-bit id (Metal arg-buffer stores the id directly, NOT a Vulkan/D3D12-style allocated heap index); GPU/macOS-only → relies on macOS CI (maintainer jhelferty-nv closed combined as won't-do) ([Metal DescriptorHandle #10842: compiler-emit DONE, slang-rhi runtime is the gap; combined won't-fit is real (64b)](../learnings/1784918108597-metal-descriptorhandle-10842-compiler-emit-done-sl.md)).

## MetalLib-3.2 (#12258): the -std Derivation Machinery Already Exists (2026-07-28 fold)

Issue #12258 ("Upgrade Metal compiler support on Windows to MetalLib 3.2") reads as a five-part feature — toolchain upgrade + capability plumbing + `-std` flag + Windows CI + docs — but the hardest-sounding compiler piece is **already done**. Since PR #12009 (issue #12096), a general `-std=metalX.Y` derivation exists: `slang-gcc-compiler-util.cpp:978-988` builds `-std=metal<maj>.<min>` from `options.metalLanguageVersion` (literal `-std=metal3.1` is only the unset fallback), and the producer `slang-code-gen.cpp:782-786` sets the version — but only special-cases `metallib_4_0`, everything else falling through to 3.1 *by coincidence*. So the **code gap for a new `metallib_X_Y` is only**: (1) add the capdef atom (retarget the next atom to inherit it, regenerate the auto-doc), and (2) GENERALIZE the producer to set the version from the *highest implied* metallib atom (one source of truth, not a growing if/else ladder) — the emitter and `-std` assembler need NO change, and the two sub-tasks are coupled at the producer (adding the atom alone still emits `-std=metal3.1`). A source/emit-level FileCheck (extend `tests/metal/threadgroup-size.slang`, which already contrasts `-capability metallib_4_0` vs `metallib_3_1`) verifies it in CI *without* an Apple toolchain. What the bot CANNOT do is the headline: the Windows Apple-Metal toolchain upgrade, a Windows CI job producing/verifying a real `.metallib`, and the toolchain docs. Triage disposition (maintainer-authored + assigned to a named human jkiviluoto-nv + no bot @-mention + infra-gated headline) = PARK-at-triaged, hand the fixer a briefing but HOLD. Lesson: on any Metal `-std`/metallib-version request, check `slang-code-gen.cpp` + `slang-gcc-compiler-util.cpp` FIRST — most of the perceived work shipped with #12009 ([slang#12258 MetalLib-3.2 — the -std derivation machinery already exists; only the producer + capdef atom are the gap](../learnings/1785287353987-slang-12258-metallib-3-2-the-std-derivation-machin.md)).

### A green macOS job does NOT mean Metal was tested (the #12096 coverage consequence)

The still-open #12096 has an observability tail that invalidates most casual claims of Metal coverage. A green `build (macos, aarch64, clang, *)` job in **shader-slang/slang-rhi** proves only that the Metal translation units *compiled*: `slang-rhi-tests -check-devices` reports unsupported devices and **exits 0**, so an entirely-skipped Metal backend is indistinguishable from a passing one. Verified on run `30804222761` / job `91655709489` (2026-08-03), where the log carried `Metal: not supported (failed to get shader entry point code)` plus the exact `'required_threads_per_threadgroup' attribute requires Metal language standard metal4.0 or higher` diagnostic (toolchain `metal 32023.883`, i.e. Xcode-16-era) while the job itself reported **success** and every Metal test silently skipped. The chain is the #12096 one: `macos-latest` now resolves to the **`macos-26-arm64`** image (read the log's `Image:` line — never assume macOS 15), slang-rhi derives the capability from the *OS version* (`if (osVersion.majorVersion >= 26) addCapability(Capability::metallib_4_0)`, `src/metal/metal-device.cpp:266`), and the OS version and the actual Metal toolchain **disagree** on these images. Practical rules: never claim a Metal path is "covered by macOS CI" from a green checkmark — open the job log and grep the `-check-devices` output for `Metal: supported` / `Metal: not supported`; when shipping a Metal-only feature say explicitly that runtime coverage is *pending* while #12096 is open; apply the same caution to `Vulkan: not supported (failed to create device)` on macOS runners. Bonus from the same log: `GPUFamilyApple6 not supported; using per-encoder useResource fallback` means the hosted runner exercises Metal's **`!m_hasResidencySet` fallback** residency path, not the residency-set path — so CI does not represent typical Apple-Silicon hardware for anything residency-sensitive ([a green slang-rhi macOS job does not mean Metal was tested — `-check-devices` exits 0 on unsupported](../learnings/1785756797105-slang-rhi-macos-ci-a-green-macos-job-does-not-mean.md)).

**"Registered" is not "executed" — and a zero-hit grep needs a control.** Quantifying that skip on the same job log produced two measurement traps generic to doctest-style per-backend logs. (1) A pattern like `\.metal (PASSED|SKIPPED)` with a **single space** matches nothing, because the log is **column-padded** (`foo.metal<many spaces>SKIPPED`) — a fact about the regex read as a fact about the world. The control that settles it: `grep -c '\.metal'` → **209**; padded-aware `^\S+\.metal +SKIPPED` → **207**. Before reporting *any* zero, run a broader control grep that MUST be non-zero; if the control is also zero, the pattern is wrong or the file isn't what you think. (2) Don't over-retract in response: `^\S+\.metal +(PASSED|FAILED)` → **0**. `GPU_TEST_CASE` registers a case per flagged device whether or not the device is available, and unavailable devices still print `SKIPPED (device not available)` — so a row's existence proves **enumeration**, not execution. "**Ran** 0 Metal tests" was true and load-bearing; "zero `.metal` rows" was false. Always report the pair — **"N registered, M executed"** — which is exactly what lets one artifact be valid for one claim (the residency-mode/adapter-properties evidence above survives a run that executed nothing) and inadmissible for another (coverage) ([registered ≠ executed: 207 SKIPPED `.metal` rows vs 0 PASSED, and why a zero-hit grep needs a control](../learnings/1785779851246-registered-is-not-executed-207-skipped-metal-rows-.md)).

**Re-triage update (2026-07-31): the "metallib_3_2 atom landed" nudge actually meant PR #12250 ("Add Metal support for printf") rewired the whole `-std` producer.** When a maintainer names one change to re-triage against, re-verify the *whole subsystem* at HEAD — the named atom rode in with a larger rework. #12250 added the `metallib_3_2` capdef atom (chain `3_1→3_2→4_0`) AND generalized the producer (`slang-code-gen.cpp:786-804`) from special-casing only `metallib_4_0` to maxing `implies(metallib_4_0)→4.0` against an emitter-tracked `MetalExtensionTracker::getRequiredMetalLanguageVersion()`; emit features now drive `-std` (a `kIROp_Printf` calls `requireMetalLanguageVersion(3,2)` → `-std=metal3.2 -fmetal-enable-logging`), verifiable toolchain-free via `unit-test-metal-compile-args.cpp` asserting `GCCDownstreamCompilerUtil::calcArgs`. The subtle residual: the producer is now FEATURE-driven, not SELECTION-driven — `-capability metallib_3_2` ALONE (no 3.2 syntax) still emits `-std=metal3.1` (no `else if implies(metallib_3_2)` branch), which is exactly the issue's "pass -std=metal3.2 when selected" sub-task, but LATENT (no metal-3.2-only syntax exists today that isn't already feature-tracked); surface it rather than auto-dispatch a fixer, and the infra-owned Windows-toolchain/CI/docs bucket stays parked regardless ([slang#12258 re-triage — #12250 rewired the whole Metal -std producer; residual `-capability`-only selection gap is latent](../learnings/1785463484364-slang-12258-re-triage-metallib-3-2-atom-landed-act.md)).

## Metal Drops `[[buffer/texture(N)]]` for a Uniform ARRAY of Resource (#12291)

A `uniform` fixed-size array of resource-containing structs — e.g. `uniform MyTensor tensors[4]` with `MyTensor{StructuredBuffer<float> buf;}` — emits a kernel arg `array<float device*, int(4)>` with **no `[[buffer(N)]]`** on `-target metal`, while SPIR-V (descriptor array + Binding) and CUDA are correct (motivating case: slangpy `Tensor<float,1>[4]`, right on VK+CUDA, wrong on Metal). The emission tell, read straight from `slangc -target metal` output: the struct's `buf` field is removed, the element buffers are hoisted into one bare array-of-device-pointer param carrying no binding attribute while sibling params all have one; per-element indexing (`tensors_buf[i]`) is CORRECT, so the defect is BINDING SHAPE, not index-dropping ([Metal emits unbound array-of-device-pointer for uniform array-of-resource](../learnings/1785418004751-metal-emits-unbound-array-of-device-pointer-for-un.md)). The reporter's candidate site (`introduceExplicitGlobalContext` in `slang-ir-explicit-global-context.cpp`) was WRONG — source-tracing shows layout is correct (`createArrayLikeTypeLayout` keeps the `MetalBuffer` offset-kind ×count; Metal is not `_isDescriptorSlotLike`), the explicit-global-context pass clones type+layout faithfully, and the real drop is **emit-only**: `MetalSourceEmitter::emitFuncParamLayoutImpl` emits `[[buffer(N)]]` for `MetalBuffer` only when `paramType` is a pointer/structured-buffer/byte-address/param-group/AS type — an `IRArrayType` wrapper matches none, so the branch is silently skipped (same gap for `MetalTexture` and `SamplerState`). VK differs because `slang-emit-spirv.cpp` decorates `Binding` purely by resource-kind with no type-shape guard. A 4-way contrast matrix (single vs array, struct-wrapped vs bare, buffer vs texture) localizes the trigger to the ARRAY SHAPE for any resource kind (the struct wrapper is irrelevant) in minutes without a rebuild ([Metal drops the buffer/texture binding for a uniform array-of-resource — emit-guard type-shape gap, not explicit-global-context (#12291)](../learnings/1785419415403-metal-drops-buffer-texture-n-for-uniform-array-of-.md)). The load-bearing uncertainty (needs macOS/`-target metallib` verification): admitting `IRArrayType` in the emit guard is clean+complete for texture/sampler arrays (Metal natively supports `array<texture2d,N> [[texture(k)]]`), but **arrays of buffers are NOT valid direct kernel args (≤ Metal 3.1)**, so the reported buffer case likely must route through Metal argument-buffer legalization instead — consistent with the shared #10842 note tagging plain arrays-of-resources on Metal as a genuine FEATURE GAP (distinct from #10842's bindless `DescriptorHandle` runtime gap and #7669's wrapper-swap binding-loss).
