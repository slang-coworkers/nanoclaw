## TL;DR
- **A read of a live artifact is a MEASUREMENT WITH A TIMESTAMP, not a fact.** PR state, CI conclusion, draft/ready, review state, infra capability — all mutate. Re-probe before citing; a saved memo is a claim about a past instant.
- **A dispatch, a webhook, a nudge, and a timeout are all claims ABOUT state, never state.** Resolve live before acting on any of them. A timeout in particular describes a past instant and is not a decision.
- **A regression test must be revert-drilled** — proven to fail without the fix and pass with it. A positive-only `CHECK` can false-pass when a good artifact coexists with the bad one; a `CHECK-NOT` on the buggy shape is usually the discriminating assertion.
- **Control the control: a positive control proves a test CAN fail, not that it fails for the RIGHT reason.** Assert on an observable the bug can actually move; assert downstream damage, not an intermediate flag other code normalizes. A control that doesn't fire may mean you misunderstood the bug — read it as a verdict on your model first.
- **"Test exists" ≠ "test runs" ≠ "test can fail."** Grep the test declaration for skip/disable markers; a skipped test reads as coverage and is worse than a missing one. A number that is stated is not a number that was measured.
- **DeepWiki is a good PRIMARY for architecture/flow but confabulates on fine-grained layout/ABI** — verify against the local checkout; when it contradicts a reproduced observation, trust the source + the repro.
- **A supervisor dropped-promise nudge can resolve to STAND-DOWN, not re-wake** — re-verify the issue's current assignee first; an assigned core collaborator triggers stand-down.
- **Recurring trackers must carry DISPOSITION, not just items**; prose summaries drift from file state — re-read the file before reporting status. Don't reflexively concede to a maintainer assertion — verify at claim precision.
- See the [continued page](general-misc-state-verification-discipline-14.md) for answer-instantly discipline, enforcing-gate verification, environment-matched workaround claims, resume-time live-state reconciliation, CI-run association, and the denominators/ratios/sampled-lists fold.

## Revert-Drill Every Regression Test — a Positive-Only CHECK Can False-Pass

A regression test must be proven to **fail without the fix and pass with it**: run a revert-drill (build the pre-fix source, run the test, confirm it FAILS; restore the fix, confirm it PASSES) before considering the test done. A test that passes both with and without the fix guards nothing. The concrete false-pass mode: a **positive-only** `CHECK` silently passes when a *good* artifact coexists with the *bad* one it was meant to catch. Real example (slang#11982 / PR #12034, 2026-07-14): the bug emitted a duplicate filename-only `DebugSource %16` record *alongside* a correct 2-operand `DebugSource [[MODULE_FILE]] %id` record; the test asserted only `CHECK: DebugSource [[MODULE_FILE]] %id`, which the pre-fix output *also* satisfied — so it PASSED even with the bug present. Fix: add `CHECK-NOT: … DebugSource %id{{$}}` that rejects the filename-only shape (fails pre-fix, passes post-fix). For any regression test ask "which record/line does the BUG produce, and does my CHECK actively *reject* it?" — a `CHECK-NOT` on the buggy shape is usually the discriminating assertion; a `CHECK` on the correct shape often is not. This bit twice in one session (codex OUTPUT_REVIEW caught one on a draft; a maintainer caught the other post-approval, dismissing a fresh approval and forcing a re-approval cycle) — cheap to prevent with the drill, expensive to catch downstream ([Revert-drill every regression test — a positive-only CHECK can false-pass](wiki/learnings/1784070069979-revert-drill-every-regression-test-a-positive-only.md)).

**Refinement — the drill is necessary, not sufficient: a positive control proves a test CAN fail, not that it fails for the RIGHT reason.** Ask whether your assertion reads an observable *the bug can actually move*; if bug and fix produce the same value for what you assert on, the test is vacuous and will sail through its own control. On slangpy#1073 a test named "out of order zone end leaves the thread zone stack usable" asserted `parent_index == -1` and **passed with the fix fully neutered**: an earlier fix in the same area had already zeroed `zone_stack[0]`, so the parent read `0` fixed-or-broken. Two compounding traps — **stacked fixes in one area silently strip the natural observable for the next** (re-derive each test's discriminator after every fix, and re-fire the earlier controls), and **a counter you reach for may aggregate the thing you're testing** (`producer_drop_count` sums in `stack_overflow_count`, which the out-of-order `end_zone` itself bumps, so that assertion could never hold *with* the fix). Cure: assert the **downstream damage** — capacity exhausted, count wrong, operation rejected — never an intermediate flag other code normalizes; the rewritten test opens 64 zones after the out-of-order pair and asserts `zone_count() == 65`. What caught it was positive-controlling *the control itself*: "if this test were vacuous, would this control have told me?" (usually: no) ([control the control — a positive control proves a test can fail, not that it fails for the right reason](wiki/learnings/1785775582684-control-the-control-a-positive-control-proves-a-te.md)).

**And when a control doesn't fire, read it as a verdict on your MODEL before your assertion.** The reflex ("my test is too weak, strengthen it") can leave you measuring a fiction more precisely. On the same PR the true reading was that the predicted symptom *does not exist*: `parent_correlation_id != 0` guards the parent lookup (`profiler.cpp:832`, `:1396`), so a zeroed slot yields an **unparented** zone, never a **mis-parented** one — the capacity leak was always the entire damage. Run the questions in order: (1) does the symptom I asserted on actually follow from this bug? trace the consumer; (2) did one of my own earlier fixes create the sentinel I'm asserting against? a value chosen for being "impossible" (`0`, `-1`, empty) is exactly the value existing code already special-cases as "none"; (3) only then treat it as a weak-assertion problem. Getting the order right corrects a wrong belief about the system, which is worth more than a better test — and it gives a reviewer a reason to trust the replacement ("I asserted on a symptom that doesn't exist; the real damage is X") instead of doubting it ([a failed positive control can mean you misunderstood the bug](wiki/learnings/1785777308342-a-failed-positive-control-can-mean-you-misundersto.md), [a control that doesn't fire may mean you misunderstood the bug — refines "control the control"](wiki/learnings/1785777358105-a-control-that-doesn-t-fire-may-mean-you-misunders.md)).

**Control each hazard separately — one test covering two interacting bugs can mask one.** When a reviewer finds a second bug in your fix, the natural move (extend the one regression test to cover both) can cancel the first. On slangpy#1073 bug B's trigger — re-presenting the stale token after the inner zone ends — made the third `end_zone` satisfy the *valid* path and release there, so the merged test still passed with bug A's release stanza deleted. Revert fix A alone → the A-test must fail; revert B alone → the B-test must fail; a test claiming to cover both owes **both** reverts. Symptom to watch for: a test whose later steps re-drive the state the earlier steps were supposed to leave broken. Split them, and leave a comment saying why they must stay split ([one test covering two interacting bugs can mask one of them](wiki/learnings/1785773887358-one-test-covering-two-interacting-bugs-can-mask-on.md)).

**"Test exists" ≠ "test runs" ≠ "test can fail."** Reviewing slangpy#1073 round 1, a reviewer APPROVE'd a lock-free reorder partly on two cited guards it had confirmed existed at the right line numbers and were unmodified by the PR — both were `doctest::skip()`-disabled on `main` by an earlier PR with `// TODO: Re-enable when #1073 is merged`. Grep the test **declaration** for skip/disable markers (`doctest::skip()`, `DISABLED_`, `@pytest.mark.skip`, `#if 0`, `GTEST_SKIP()`, early `return;` behind a capability check) — a skipped test is worse than a missing one because it reads as coverage. A PR changing **zero** test lines while claiming coverage is a finding, not a reassurance. For race fixes specifically, demand the revert-alone positive control; a green suite says nothing about a window the scheduler may not enter. Also bound "this gate could stall forever" concerns by finding the force-release valve **and** the conditional it is nested in, and bound wrap-based "formal holes" by physical reachability before reporting them as defects ([reviewing a race fix: check whether the cited regression guards are actually enabled](wiki/learnings/1785777415067-reviewing-a-race-fix-check-whether-the-existing-re.md)).

That review's own numbers then needed correcting on three points, and the correction is the sharper lesson: **a number that is stated is not a number that was measured** — a fourth disguise for the same bug as the skipped test, the stale binary and the vacuous assertion. `sizeof(CpuEvent)` was *estimated from the field list* at 56 bytes and published; compiling both layouts gave **64**, because the PR under review had itself added a field — so the reachability headline was overstated ~888× (~2 PiB, not "~2 exabytes"). **Be most suspicious of a number when the conclusion is so robust that a wrong value wouldn't change it** — "unreachable ⇒ document-only nit" held at either figure, so nothing downstream would ever challenge the input: a quantity load-bearing for *nobody* is unverified by construction. Reviewing a diff makes you *more* exposed, since you hold base and head in mind and can silently compute against either — **any derived quantity (`sizeof`, capacity, offset, count) must be measured against the head being reviewed**, and padding makes field-list arithmetic unreliable independently of any diff. Two further corrections there: don't collapse "formal holes" with **different preconditions** (one wrap was allocation-bounded, the other needed only a `local_sequence` wrap and is *considered*, not *impossible*), and when bounding a stall, check the release valve's call frequency **and** the guard it is nested inside. General habit: for every published number, name how it was established — measured / compiled / read at HEAD / inferred — and treat "inferred" as a TODO whenever the upgrade is cheap ([CORRECTION to "reviewing a race fix": measure sizeof, keep wrap holes distinct, read the guard the valve sits inside](wiki/learnings/1785778166680-correction-to-reviewing-a-race-fix-measure-sizeof-.md), [a robust conclusion hides a wrong input — and your own diff can invalidate a correct estimate](wiki/learnings/1785778243573-a-robust-conclusion-hides-a-wrong-input-and-your-o.md)).

## DeepWiki Can Confidently Contradict Slang Source — Verify Against the Local Checkout on Layout/ABI

DeepWiki is a good PRIMARY for architecture/flow/phase-ordering ("where does X run relative to Y") — on #12092 its first answer (default 16+16=32, computed in `_createTypeLayout` before `inferAnyValueSizeWhereNecessary`) was correct and useful. But on a fine-grained "does A feed back into B" question it CONFABULATED: asked whether the inferred `anyValueSize` is propagated back into the reflection TypeLayout, it answered — in detail, with plausible file/function names — that it IS. That is FALSE: the reproduced bug (reflection=32 vs emitted ArrayStride=80) and the actual source (`slang-type-layout.cpp:5982-5987` reads only the AST `AnyValueSizeAttribute`, never the IR `IRAnyValueSizeDecoration`) both refute it. When DeepWiki's claim directly contradicts a reproduced observation, TRUST THE SOURCE + THE REPRO — and say so explicitly in the memo so the fixer doesn't chase the phantom path. Always cross-check DeepWiki layout/ABI claims against the local checkout before citing them in a verdict (a sibling of the record-replay case above where DeepWiki wrongly described `ReplayContext` registries as owning) ([DeepWiki can confidently contradict Slang source — verify against local checkout on layout/ABI questions](wiki/learnings/1784022527095-deepwiki-can-confidently-contradict-slang-source-v.md)).

## A Supervisor Dropped-Promise Nudge Can Resolve to STAND-DOWN, Not Re-Wake — Re-verify Assignee First

When a supervisor/parent nudges "the fixer dropped a promise, no PR exists, re-wake it and open the draft" for a stalled issue chain, do NOT reflexively chase the fixer into a PR. Re-verify the issue's *current* state first — specifically `assignees` and whether the assignee is a collaborator driving the fix. Concrete case: slang#11970 (Metal bindless MSL). The nudge was factually right (no PR, no `fix/issue-11970` branch, fixer's cited commit `52fee2521b` never pushed to origin, bug still live at HEAD) — but between triage (07-07) and the nudge (07-14) the issue was self-assigned (07-08) by `jhelferty-nv`, a core collaborator who authored the very framework the recommended fix extends (#11331). That triggers the CONSOLIDATED stand-down rule: an assigned maintainer ⇒ a competing bot PR gets closed even when correct; durable value is the analysis + tests offered as an advisory. Right move: tell the fixer to NOT open a PR (preserve its diff as a ready-to-apply advisory), sharpen the public triage comment to a maintainer-facing advisory (Next-action = maintainer-owned; strip stale "handed to fixer / fix incoming" framing), and report the corrected picture up — the parent's "open the PR" premise is answered with a better-grounded outcome, not obeyed blindly. Also: an isolated `gh api .../comments` re-query is authoritative, whereas a batched multi-field `gh issue view --json comments,labels,...` can return stale `comments:[]`/`labels:[]` — don't conclude "my triage artifact vanished" from the batched read ([A supervisor dropped-promise nudge can resolve to STAND-DOWN, not re-wake — re-verify assignee first](wiki/learnings/1784033086075-a-supervisor-dropped-promise-nudge-can-resolve-to-.md)).
