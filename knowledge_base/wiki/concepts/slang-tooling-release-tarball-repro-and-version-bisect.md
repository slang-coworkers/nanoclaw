# Reproducing version-specific Slang bugs with release tarballs, and bisecting across releases

Prebuilt Linux release tarballs answer "does version X have this bug?" without a CMake build. This page covers fetching and running them, CUDA/PTX triage, bisecting a C++ API regression by linking against each tarball, the pitfalls that fake a pass or a fail, and the measured per-issue version matrices.

## TL;DR

- A release tarball answers a version question in about a minute, with no build and no GPU: `gh release download v<ver> -R shader-slang/slang -p "slang-<ver>-linux-x86_64.tar.gz"` (or the asset `browser_download_url`), extract, run `bin/slangc` with `LD_LIBRARY_PATH=<dir>/lib`. On a glibc-2.36 host (Debian-12 coworker container) use the `-glibc-2.27` asset; the standard one needs GLIBC 2.38.
- Try the container's local `build/Release/bin/slangc` first for a master check. Builds before 2026-10-22 failed every SPIR-V compile (E00100/E52002); the 653bfdeef rebuild emits and validates SPIR-V. On E00100: a tarball for SPIR-V; local `-target hlsl`/`cuda`/`glsl` for front-end checks and bindings; `-target spirv -O0` for raw SPIR-V words.
- Linux tarballs ship no slang-tint: `-target wgsl` works, `wgsl-spirv-asm` fails. Validate WGSL with naga.
- Test at least the reporter's version and the latest release; for a fix or regression add the releases on either side. Run every target the report names and the nearby source variants. After a bracket, list the window's commits and name the trigger.
- Name the first fixed release with `git tag --contains <merge-sha>` in a full clone with tags, never by sampling two releases, and confirm on its tarball (patch releases get backports). A fix merged on a tag's day can miss it: compare times, not dates.
- The local `/workspace/agent/slang` clone is shallow (`git tag --contains`, `git log --grep` return nothing): use `gh pr view <n> --json mergedAt,mergeCommit` vs the tag time, or `compare/<sha>...<tag>` (`ahead` = contained). When the issue is off limits (eval triage), grep the `v<A>...v<B>` compare's subjects for "Fix #<n>: …".
- When the shared clone is shallow or cannot fetch (`bad object refs/remotes/...`, `failed to run repack`), don't repair it: `git clone --filter=blob:none --no-checkout https://github.com/shader-slang/slang.git /tmp/slang-bl` takes ~2 s, has full history, fetches blobs on demand (`git show <rev>:<path>`, `git log -S`), and spends no REST quota.
- Compare two releases' codegen by diffing `-target spirv-asm` with IDs normalized: `sed -E 's/%[A-Za-z0-9_]+/%X/g'`. Download tarballs from `github.com/.../releases/download/v<ver>/<asset>` (no API quota).
- Bisect library source without a clone: the contents API with `Accept: application/vnd.github.raw`, then grep.
- `-target ptx` runs NVRTC: a real CUDA compile check in seconds.
- C++ compilation-API bugs: link a tiny repro against each tarball (`-lslang-compiler`, or `-lslang`). A runtime result on release binaries beats "reproduced by code inspection".
- Exit codes mislead: an NVRTC error can exit 0; a Release crash is exit 139 with no ICE text; `| head` hides the exit code (`${PIPESTATUS[0]}`). `-skip-codegen`/`-target none` still run IR lowering. Old releases (v2025.1x) write nothing for `-o -`: write to a file.
- A crash report on a version older than the fix: tell the reporter to upgrade to the earliest fixed release. A failure on the fix release or later is probably a separate variant. Reporters on an affected release get the status plus a verified workaround (status table).
- A variant matrix on one release is a good acceptance test set for a fix. Re-check open issues on each new release.

## Fetching and running a release

Download that version's Linux tarball and run its `bin/slangc` with `LD_LIBRARY_PATH=<dir>/lib`. Fetch with `gh release download v<ver> -R shader-slang/slang -p "slang-<ver>-linux-x86_64.tar.gz"` or the asset's `browser_download_url` from `gh api repos/shader-slang/slang/releases/tags/v<ver>`; each version takes under a minute ([#12634 tarball](../learnings/1792152922166-repro-version-specific-slangc-bugs-from-release-ta.md), [#12633 before/after](../learnings/1792152959615-reproduce-pre-fix-slang-behavior-with-release-tarb.md)), a three-version bracket about two ([#12768](../learnings/1792154620818-12768-nested-swizzle-lvalue-did-work-on-v2024-1-34.md)). A wildcard `--pattern "*linux-x86_64.tar.gz"` also works ([#12640 v2026.19](../learnings/1792153782868-12640-interface-only-default-arg-crash-still-repro.md)). The same tarball (`-glibc-2.28` asset from `releases/latest`) is the quick check of a Discord or bot claim when the local clone is stale or unbuilt, about a minute against 20+ for a source build; `-o /dev/null` fails there with E00004 ([Discord/bot claims](../learnings/1792571968734-verify-discord-bot-slang-claims-with-the-release-s.md)).

On a glibc-2.36 host such as the Debian-12 coworker container, the standard tarball (and the dxc binaries cached in scratch dirs) needs GLIBC 2.38 and will not start; every release also publishes `slang-<ver>-linux-x86_64-glibc-2.27.tar.gz`, which runs there (`curl -sfL .../releases/download/v<ver>/<asset>` into /tmp). Two adjacent tags then pin a boundary in a minute: for #13931, v2026.1.1 compiles and v2026.1.2 rejects with E30701, pinning #9260; `-ignore-capabilities` suppresses that front-end system-value type check and shows what the backends would do ([glibc-2.27 tarballs](../learnings/1792917334487-bisect-old-slang-behavior-on-a-glibc-2-36-host-use.md)).

To bisect without running anything, fetch a source file at each tag and grep it: `gh api "repos/shader-slang/slang/contents/source/slang/hlsl.meta.slang?ref=v<tag>" -H "Accept: application/vnd.github.raw"` ([#12634 tarball](../learnings/1792152922166-repro-version-specific-slangc-bugs-from-release-ta.md)).

**Try the container's local build first; fall back to a tarball on E00100.** In the triage and eval containers `/workspace/agent/slang/build/Release/bin/slangc` is a ready master build (no slang-test beside it) that re-reproduces a non-SPIR-V codegen report in seconds (#13108: `-target cuda` still emits `State_0 _S7 = original_1;`) ([prebuilt master slangc](../learnings/1792425150374-eval-slang-triage-container-has-a-prebuilt-master-.md)). Its `-version` is fixed at configure time; check freshness with `git reflog` vs the build's mtime and `find source -newer <lib>` ([glibc-2.27 tarballs](../learnings/1792917334487-bisect-old-slang-behavior-on-a-glibc-2-36-host-use.md)). Builds up to the morning of 2026-10-22 could not load `slang-glslang`: `-target spirv` exited 255 with E00100 "failed to load downstream compiler 'spirv-opt'" (plus E99996 notes), and `spirv-asm` failed on 'spirv-dis' or with E52002 "pass-through compiler not found" ([E00100](../learnings/1792424186345-local-slang-release-build-fails-target-spirv-with-.md), [spirv-asm](../learnings/1792423080231-slang-12847-pr-12848-is-still-a-draft-local-master.md), [E52002](../learnings/1792422693293-local-release-slangc-may-fail-spir-v-with-e52002-u.md)). A release `lib/` on `LD_LIBRARY_PATH` does not help (the build wants unversioned `libslang-glslang-0.0.0.so`); a 0.0.0-named symlink to the release library works ([E52002](../learnings/1792422693293-local-release-slangc-may-fail-spir-v-with-e52002-u.md)). The 653bfdeef rebuild (2026-10-22) compiles `spirv` and `spirv-asm`, and with `SLANG_RUN_SPIRV_VALIDATION=1` reproduced #13427's VUID-08722 ([653bfdeef emits SPIR-V](../learnings/1792659932300-container-release-slangc-now-emits-spir-v-directly.md)). When a local binary still fails, pick by question:

- **SPIR-V output or validation:** the tarball's `bin/slangc` with `SLANG_RUN_SPIRV_VALIDATION=1`; it flags #13206's "may not return a logical pointer" on v2026.18 and v2026.20 ([#13206](../learnings/1792425910957-local-build-release-slangc-in-eval-containers-cann.md)).
- **Front-end fix, or proof a workaround compiles:** `-target hlsl -entry main -stage compute -o out.hlsl` (or CUDA) needs no downstream tool and still reports checker diagnostics (E39999, E30047/E30049); a clean compile proves the front end accepts the code. `-lang hlsl` applies only to inputs after it ([hlsl, E39999](../learnings/1792427056805-local-slang-master-release-build-cannot-target-spi.md), [hlsl, E30047](../learnings/1792649817653-local-release-slangc-in-eval-container-can-t-emit-.md)).
- **Vulkan binding numbers:** `-target glsl -entry A -entry B`, read `layout(binding = N)`; #13203 gives GLSL 0-5, HLSL b0/t0/u0 then b1/t1/u1 ([glsl bindings](../learnings/1792425746359-local-release-slangc-in-triage-container-cannot-em.md)).
- **SPIR-V content with no disassembler:** `-target spirv -O0 -o x.spv` loads nothing, since `-O0` skips spirv-opt (`spirv-asm`, validation and `-separate-debug-info` still load slang-glslang); #12987 compiles this way ([-O0](../learnings/1792424186345-local-slang-release-build-fails-target-spirv-with-.md)). Walk the words in Python: skip the 5-word header; opcode `w & 0xffff`, word count `w >> 16`; Capability 17, OpDecorate 71 (NoContraction = decoration 42), GroupNonUniformBallot 339, BallotBitCount 342, GroupNonUniformIAdd 349. This matched v2026.20's #13324 NoContraction counts ([NoContraction census](../learnings/1792426835220-local-slang-release-build-lacks-spirv-opt-spirv-di.md)), confirmed #12847 (two `OpGroupNonUniformBallot` on one predicate), and showed `WavePrefixSum`/`WaveActiveSum(uint(b))` emit two `OpGroupNonUniformIAdd` (ExclusiveScan, Reduce) and no ballot ([-O0 emits SPIR-V](../learnings/1792647523271-eval-container-local-slangc-can-emit-spir-v-with-t.md)).

Tarballs have their own gap: the Linux ones (checked v2026.17.1, v2026.19) ship no `libslang-tint`, so `-target wgsl-spirv-asm` fails (E00100 'tint' / E52002) while `-target wgsl` works, enough to diff WGSL text across versions (v2026.17.1 `for(;;)`; v2026.19 `loop` after PR #13071). A Linux local build lacks slang-tint too; validate with naga (`pip install wgpu`) ([no slang-tint](../learnings/1792403683977-slang-linux-release-tarballs-lack-slang-tint-so-ta.md)).

Two before/after examples. #12634: `Texture3D<float3>.SampleLevel` emits `tex3DLod<float3>` (NVRTC rejects it) in v2026.14.1, v2026.15 and v2026.16; v2026.17+ emit `_slang_vector_reshape<float,3,float,4>(tex3DLod<float4>(...))` and the PTX compiles (checked v2026.19) ([#12634 tarball](../learnings/1792152922166-repro-version-specific-slangc-bugs-from-release-ta.md)). The bug is wider: on v2026.14.1 every 3-component CUDA texture sample fails (`Sample`, `Texture2D<float3>.SampleLevel`, `int3`/`uint3`), and releases before v2026.16.1 fail, so the fix probably first ships in the untested v2026.16.1 ([#12634 scope](../learnings/1792400048814-slang-12634-scope-every-3-component-cuda-texture-s.md)); mechanism on [[wiki/concepts/misc-f0909b5-cuda-codegen-triage.md]]. #12633 (Texture2DMS on CUDA): v2026.16 emits the field with no type, v2026.19 reports E55215 ([#12633 before/after](../learnings/1792152959615-reproduce-pre-fix-slang-behavior-with-release-tarb.md)).

## Choosing the version bracket and finding the fix commit

Test the reporter's version and the latest release first ([CUDA/PTX triage](../learnings/1792153192040-fast-gpu-free-build-repro-compare-slang-release-bi.md)). To bracket a fix, find the fix commit (`git log -- <test>` where the history reaches it, else `gh pr view`) and pick the releases on either side from `gh release list` dates ([#12633 before/after](../learnings/1792152959615-reproduce-pre-fix-slang-behavior-with-release-tarb.md)).

Sampling two releases misnames the *first* fixed release: #12988 was recorded as v2026.18.3 but is in v2026.18.1 ([#12987 in v2026.18.1](../learnings/1792403199630-12987-local-struct-conformance-fix-first-ships-in-.md)), and #13070's fix (PR #13086) as v2026.19 though it is in v2026.18.3. List the containing tags with `git tag --contains <merge-sha>` after `git fetch --tags`, sorted by date, not name (lexicographic trap: [[wiki/concepts/general-misc-b-tooling-and-shell-traps.md]]), and confirm the earliest on its tarball, since patch releases often get backports ([git tag --contains](../learnings/1792424529371-find-the-first-fixed-slang-release-with-git-tag-co.md)). In the shallow `/workspace/agent/slang` clone both `git tag --contains` and `git log --grep` return nothing even for a fix on master; compare `gh pr view <n> --json mergedAt,mergeCommit` with the tag time (`git log -1 --format=%ci <tag>`), or ask `compare/<sha>...<tag>` (`ahead` = the tag contains it), then confirm with local master `slangc` and the release ([shallow checkout](../learnings/1792427616892-slang-checkout-is-shallow-find-fix-commits-with-gh.md), [#12852 compare check](../learnings/1792401919012-12852-workaround-on-v2026-16-1-loadmodulefromsourc.md)).

When you must not open the issue (in eval triage its labels and state are the answer key), bracket the first good release with tarballs and grep the window's commit subjects, since bot PRs are titled "Fix #<n>: …": `gh api repos/shader-slang/slang/compare/v<bad>...v<good> --jq '.commits[] | .sha[0:10] + " " + (.commit.message | split("\n")[0])' | grep -i "<keyword>"`. For #12632 (CUDA half `SampleLevel`; v2026.16 bad, v2026.16.1 good) that named PR #12643 ([fix PR without the issue](../learnings/1792304028705-find-the-fix-pr-for-an-issue-without-opening-the-i.md)).

A bracket narrows the search to a commit window, not one commit: #13273's v2025.18.1→v2025.18.2 window held 19 commits, two plausible; read each suspect's change to name the trigger ([#13273 bisect](../learnings/1792159067590-13273-emit-fold-reorder-regressed-v2025-18-1-v2025.md)).

**Fresh source and a codegen diff without REST quota.** The shared `/workspace/agent/slang` clone can be both shallow and broken: on 2026-10-27 its fetch failed with "bad object refs/remotes/origin/Sirox0/master; failed to run repack" and `origin/master` was stuck at 04-15. Leave it alone and make a blobless clone: `git clone --filter=blob:none --no-checkout https://github.com/shader-slang/slang.git /tmp/slang-bl` takes about 2 s, carries the full history, and fetches blobs on demand for `git show <rev>:<path>`, `git log -S` and per-path history. To check a "regressed between release X and Y" report, download both `github.com/shader-slang/slang/releases/download/v<ver>/slang-<ver>-linux-x86_64.tar.gz` assets (a plain download, no API quota), compile the same shader with each, and diff the `spirv-asm` after normalizing IDs with `sed -E 's/%[A-Za-z0-9_]+/%X/g'`, so that only real instruction changes remain. The tarballs also ship `include/` and `lib/libslang-compiler.so`, so the linked API probes below work from the same downloads ([blobless clone + cross-release codegen diff](../learnings/1793089764882-fast-fresh-slang-source-cross-release-codegen-diff.md)).

## CUDA/PTX triage with release binaries

`-target ptx` makes slangc call NVRTC, so a tarball is a real CUDA compile check with no build: errors such as "dynamic initialization is not supported for a `__device__` variable" appear in seconds. #12635 (nested static const arrays) fails on v2026.14.1 and passes on v2026.19 (PR #12688) ([CUDA/PTX triage](../learnings/1792153192040-fast-gpu-free-build-repro-compare-slang-release-bi.md)). Atoms disagree on whose NVRTC runs, the tarball's ([#12633 before/after](../learnings/1792152959615-reproduce-pre-fix-slang-behavior-with-release-tarb.md)) or the container's 12.6 at `/usr/local/cuda-12.6` ([CUDA/PTX triage](../learnings/1792153192040-fast-gpu-free-build-repro-compare-slang-release-bi.md)), so record the version with any PTX result.

## Bisecting C++ API regressions with a linked repro

Compilation-API bugs (`loadModuleFromSource` and similar) need no source build: compile a tiny repro against each extracted tarball, `g++ -std=c++17 repro.cpp -I<X>/include -L<X>/lib -lslang-compiler -Wl,-rpath,$PWD/<X>/lib` (`-lslang` when there is no `libslang-compiler.so`), about a minute per version. #12852 works on v2026.12.2, fails on v2026.16.1 with "assert failure: slang-session.cpp(56): blob", and is fixed on v2026.19 (PR #12853), stronger evidence than code inspection ([C++ API bisect](../learnings/1792154932443-bisect-slang-c-api-regressions-by-linking-a-tiny-r.md)). The fix (merge e81aa6be) first ships in v2026.17; master reads the file when `source` is null and reports E00001 for an unreadable path. On v2026.16.x, read the file yourself and call `ISession::loadModuleFromSourceString(name, path, text, &diag)`, which wraps `text` in a `StringBlob` so `SLANG_RELEASE_ASSERT(blob)` never fires ([#12852 workaround](../learnings/1792401919012-12852-workaround-on-v2026-16-1-loadmodulefromsourc.md)).

## Pitfalls: exit codes, hidden ICE text, and `-o -`

slangc can print an NVRTC error and exit 0: check the output file exists, or grep stderr ([CUDA/PTX triage](../learnings/1792153192040-fast-gpu-free-build-repro-compare-slang-release-bi.md)). Release builds omit the ICE text a debug build shows: #12640 is exit 139 with no message, so check `$?`, and `${PIPESTATUS[0]}` through `head` ([#12640 v2026.19](../learnings/1792153782868-12640-interface-only-default-arg-crash-still-repro.md)). Nor can a release binary name the crashing phase: #12640 also segfaults under `-target none` and `-skip-codegen`, but IR lowering (`addDirectCallArgs`, `SLANG_ASSERT(argExpr)` in `slang-lower-to-ir.cpp`) runs in both, so use a debug build or a backtrace ([#12640 v2026.20, -skip-codegen](../learnings/1792304859137-12640-still-segfaults-on-v2026-20-skip-codegen-doe.md); same trap on [Slang compiler crash triage](../concepts/misc-f0909b3-slang-compiler-crash-triage.md)). Older releases (v2025.1x) write nothing for `-o -`; in a cross-version bisect write to a file (`-o file.glsl`) or they score as failures ([#13273 bisect](../learnings/1792159067590-13273-emit-fold-reorder-regressed-v2025-18-1-v2025.md)).

**#12640 (interface-only default argument).** `interface IFoo { void func(float A = 1.0); }`, implemented by `Foo::func(float A)` with no default and called as `f.func()`, segfaults (exit 139, no message) on v2026.14.1 and v2026.19 for spirv and cuda; master still has a plain `SLANG_ASSERT(argExpr)` in `addDirectCallArgs` (`slang-lower-to-ir.cpp` near line 4615). An explicit argument, an implementation with its own default, and a call through a generic `T : IFoo` all compile ([#12640 v2026.19](../learnings/1792153782868-12640-interface-only-default-arg-crash-still-repro.md)); on v2026.20 the generic call emits `Foo_func_0(1.0f)`, so the default is right when the call stays on the requirement ([#12640 v2026.20](../learnings/1792304859137-12640-still-segfaults-on-v2026-20-skip-codegen-doe.md)).

**#12768 (nested swizzle lvalue).** `out.position.xyz.xyz = in.position.xyz;` (`-target glsl -stage vertex -entry vertexMain`): v2024.1.34 emits the correct `out_0.position_0.xyz = in_position_0.xyz;`; v2025.12.1 emits `position_0[3] = vec3` (HLSL `[int(3)]`, SPIR-V `OpCompositeInsert %v4float %v3 %b 3`); v2026.19 is fixed by PR #12769 (merged 2026-09-01). It is a true regression; the bad `.add(elementCount)` line fits the 2024-11-15 `ShortList` refactor (05903f708) ([#12768](../learnings/1792154620818-12768-nested-swizzle-lvalue-did-work-on-v2024-1-34.md)).

**#12987 (local-struct constrained-generic conformance).** A function-local `struct Op : IOp` with `apply<T : __BuiltinArithmeticType>` segfaults (rc=139) on v2026.17, v2026.17.1 and v2026.18 for spirv, hlsl and cuda. The first fixed release is **v2026.18.1**, not the v2026.18.3 first recorded from sampling only v2026.18 and v2026.18.3: fix `b3aa9bec5` (PR #12988) merged 2026-09-16, a day after v2026.18, and v2026.18.1, v2026.19 and v2026.20 compile it. An "upgrade to X" reply must name the earliest fixed release ([#12987 in v2026.18.1](../learnings/1792403199630-12987-local-struct-conformance-fix-first-ships-in-.md)). If it still fails on v2026.18.1+, check whether the local struct is generic (`Op<U>`): that is the separate bug #13092 (`lowerWitnessTable`), which #12988 does not fix ([two-stage crash](../learnings/1789483742996-function-local-interface-conformance-crashes-at-tw.md)).

**#13011 (optional-constraint ICE).** On v2026.19, `where optional T : X { return a + b; }` with `T` a struct depends on `X`: `__BuiltinFloatingPointType`, `IFloat`, `IInteger` give ICE E99997 ("Unexpected context type for parameter info retrieval", typeflow-specialize); `__BuiltinIntegerType` compiles silently to `a_0 + b_0` on a struct (#13061); `IArithmetic`, `ILogical`, `__BuiltinLogicalType` give the correct E39999. `-target hlsl` and `spirv` reproduce it with no GPU; the matrix is the acceptance set for a front-end fix ([#13011 matrix](../learnings/1792156239266-slang-13011-optional-constraint-ice-variant-matrix.md)). Master 68438b5e1 (2026-10-19) gives the same matrix; the maintainer placed the fix in the front-end lookup filter for optional constraints (`isWitnessUncheckedOptional`, `slang-check-expr.cpp:1344`), not a typeflow guard ([#13011 direction](../learnings/1792424334332-slang-13011-maintainer-direction-filter-lookups-re.md)). Until then `if (T is __BuiltinFloatingPointType) return a + b; return a;` compiles on v2026.20 for float and struct instantiations (HLSL `a_0 + b_0` for float, `return a_1` for the struct) ([#13011 workaround](../learnings/1792403257595-slang-13011-optional-constraint-ice-if-t-is-x-guar.md)).

**#13273 (emit fold reorder).** The C-like emitter re-reads `s.top` after `s.top -= 1` in `s.a[s.top]`; v2025.18.1 is right, v2025.18.2 wrong. Of the window's 19 commits, 54e1d02715 (#8619) is the trigger: it made `canAddressesPotentiallyAlias` (`slang-ir-util.cpp` ~1472) treat same-root, different-field access chains as no-alias, so `processLoadUse` in `simplifyForEmit` defers `load(gep)` past the store. That exposes an older bug: the emitter's fold check does not follow always-folded GEP/FieldAddress users (#8588, same window, only reorders generic parameters). Fix PR #13283 merged after the v2026.20 tag ([#13273 bisect](../learnings/1792159067590-13273-emit-fold-reorder-regressed-v2025-18-1-v2025.md)).
