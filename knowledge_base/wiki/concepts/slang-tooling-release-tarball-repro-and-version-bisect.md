# Reproducing version-specific Slang bugs with release tarballs, and bisecting across releases

The prebuilt Linux release tarballs of Slang answer "does version X have this bug?" without a CMake build. This page covers how to fetch and run them, how to use them for CUDA/PTX triage, how to bisect a C++ API regression by linking a tiny program against each tarball, the pitfalls that make a run look like a pass or a fail when it is not, and the version matrices measured for several issues.

## TL;DR

- A release tarball answers a version question in seconds to about a minute per version. No CMake build, no GPU.
- Fetch with `gh release download v<ver> -R shader-slang/slang -p "slang-<ver>-linux-x86_64.tar.gz"`, or take the asset `browser_download_url` from `gh api repos/shader-slang/slang/releases/tags/v<ver>`. Extract with `tar`.
- Run `bin/slangc` from the extracted directory. Set `LD_LIBRARY_PATH=<dir>/lib` so it loads its own libraries.
- The triage/eval container's local `build/Release/bin/slangc` is a quick master check, but it cannot load slang-glslang. Every SPIR-V compile fails with E00100 'spirv-opt'/'spirv-dis' or E52002, so use a tarball for SPIR-V output and validation. Locally, use HLSL, CUDA or GLSL for front-end checks, bindings and workarounds, and `-target spirv -O0` for raw SPIR-V words.
- Linux tarballs ship no slang-tint: `-target wgsl-spirv-asm` fails there, and plain `-target wgsl` works. Validate WGSL with naga.
- Always test at least two versions: the one the reporter used and the latest release. For a fix or a regression, add the release just before and just after the change.
- Name the first fixed release with `git tag --contains <merge-sha>` (after `git fetch --tags`) in a full clone, never by sampling two releases, and confirm on that release's tarball: patch releases often get backports.
- The local `/workspace/agent/slang` clone is shallow. There `git tag --contains` and `git log --grep` return nothing even for a fix on master. Use `gh pr view <n> --json mergedAt,mergeCommit` against the tag time, or the compare API (`compare/<sha>...<tag>` status `ahead` means the tag contains it). When the issue itself is off limits (eval triage), grep the `v<A>...v<B>` compare's commit subjects: bot fix PRs are titled "Fix #<n>: …".
- A reporter on an affected release needs the status plus a verified workaround. Several open or post-release bugs have one; see the status table.
- Bisect library source across tags without a clone: fetch a file at a tag through the contents API with `Accept: application/vnd.github.raw` and grep it.
- `-target ptx` runs NVRTC, so it is a real CUDA compile check that shows NVRTC errors in seconds.
- For C++ compilation-API bugs, link a tiny repro against each tarball: `g++ -std=c++17 repro.cpp -I<X>/include -L<X>/lib -lslang-compiler -Wl,-rpath,$PWD/<X>/lib`. Use `-lslang` if `libslang-compiler.so` is absent.
- A runtime result on real release binaries is stronger evidence than "reproduced by code inspection".
- slangc can print an NVRTC error and still exit 0. Check for the output file or grep stderr.
- Release builds hide ICE text. A crash is often exit 139 with no message. Check `$?`.
- `| head` hides the exit code of the command before it. Use `${PIPESTATUS[0]}`.
- Older slangc releases (v2025.1x) write nothing for `-o -`. Write to a real file (`-o out.glsl`) in any cross-version run, or "no output" is scored as a failure.
- Run every target the report names (spirv, hlsl, cuda, glsl) and the nearby source variants. One target or one variant is not a matrix.
- After a release bracket, list the commits in that window and name the trigger. A window can hold an unrelated suspect.
- A crash report on a version older than the fix release is already fixed: tell the reporter to upgrade. A report that still fails on the fix release or later is probably a separate variant: check for one before reopening.
- A fix PR merged on the same day as a release tag can miss that release. Compare the PR's merge time with the tag time, not only the date.
- `-skip-codegen` and `-target none` still run IR lowering. A crash under them does not prove a checker crash; use a debug build or a backtrace.
- A matrix of constraint or source variants on one release is a good acceptance test set for a fix.
- Re-check open issues on each new release. The latest per-issue status table is in "Worked version matrices" below.

## Fetching and running a release

To check a bug against an older release, download that version's Linux tarball and run its `bin/slangc` on the repro. Two equivalent ways to fetch it work: `gh release download v<ver> -R shader-slang/slang -p "slang-<ver>-linux-x86_64.tar.gz"`, or the asset's `browser_download_url` from `gh api repos/shader-slang/slang/releases/tags/v<ver>`. Each version takes under a minute ([release tarball repro, #12634 Texture3D SampleLevel](../learnings/1792152922166-repro-version-specific-slangc-bugs-from-release-ta.md), [release tarball before/after fix, #12633](../learnings/1792152959615-reproduce-pre-fix-slang-behavior-with-release-tarb.md)). The binaries run with `LD_LIBRARY_PATH=<dir>/lib`, so a three-version bracket takes about two minutes ([#12768 release bracket](../learnings/1792154620818-12768-nested-swizzle-lvalue-did-work-on-v2024-1-34.md)). A wildcard pattern such as `--pattern "*linux-x86_64.tar.gz"` also selects the asset ([#12640 on v2026.19](../learnings/1792153782868-12640-interface-only-default-arg-crash-still-repro.md)).

You can also bisect without running anything. Fetch a source file at each tag and grep it: `gh api "repos/shader-slang/slang/contents/source/slang/hlsl.meta.slang?ref=v<tag>" -H "Accept: application/vnd.github.raw"` ([release tarball repro, #12634](../learnings/1792152922166-repro-version-specific-slangc-bugs-from-release-ta.md)).

**Use a tarball, not the container's local build, for SPIR-V.** In the triage and eval containers, `/workspace/agent/slang/build/Release/bin/slangc` is a ready master build (68438b5e1 on 2026-10-19). It has no slang-test beside it. It re-reproduces a non-SPIR-V codegen report in seconds: on #13108, `-target cuda` still emits the `updateCallSites` call-site temp `State_0 _S7 = original_1;` ([prebuilt master slangc in eval-slang-triage](../learnings/1792425150374-eval-slang-triage-container-has-a-prebuilt-master-.md)). It cannot finish SPIR-V, because its `lib/` has no loadable `slang-glslang`. `-target spirv` exits 255 with E00100 "failed to load downstream compiler 'spirv-opt'" plus E99996 notes for `pthread` and `slang-glslang-0.0.0`. `-target spirv-asm` fails the same way on 'spirv-dis', or with E52002 "pass-through compiler not found". That error hides whether the bug under test is still there ([E00100 at -target spirv](../learnings/1792424186345-local-slang-release-build-fails-target-spirv-with-.md), [spirv-asm fails too](../learnings/1792423080231-slang-12847-pr-12848-is-still-a-draft-local-master.md), [E52002](../learnings/1792422693293-local-release-slangc-may-fail-spir-v-with-e52002-u.md)). Pointing `LD_LIBRARY_PATH` at a release `lib/` does not help ([E52002](../learnings/1792422693293-local-release-slangc-may-fail-spir-v-with-e52002-u.md)): the local build looks for the unversioned `libslang-glslang-0.0.0.so`, and a release ships `libslang-glslang-<ver>.so`. (A 2026-10-21 check found that a symlink with the 0.0.0 name to the release library, in a directory on `LD_LIBRARY_PATH`, works. The tarball is simpler.) Pick the workaround by question:

- **SPIR-V output or validation:** run the tarball's `bin/slangc` with `SLANG_RUN_SPIRV_VALIDATION=1`. Its bundled validator flags #13206's "may not return a logical pointer" on v2026.18 and v2026.20 ([tarball for SPIR-V repros; #13206](../learnings/1792425910957-local-build-release-slangc-in-eval-containers-cann.md), [tarball with validation](../learnings/1792427491980-local-release-slangc-lacks-spirv-opt-use-a-release.md)).
- **A front-end fix, or proof that a workaround compiles:** `-target hlsl -entry main -stage compute -o out.hlsl` needs no downstream tool and still reports parser and checker diagnostics such as E39999. CUDA works too ([hlsl for front-end checks](../learnings/1792427056805-local-slang-master-release-build-cannot-target-spi.md)).
- **Vulkan binding numbers:** `-target glsl -entry A -entry B`, then read the `layout(binding = N)` lines. For #13203 that gives GLSL bindings 0-5 and HLSL b0/t0/u0 then b1/t1/u1 ([glsl for bindings](../learnings/1792425746359-local-release-slangc-in-triage-container-cannot-em.md)).
- **SPIR-V content with no disassembler:** `-target spirv -O0 -o x.spv` loads nothing, because `-O0` skips spirv-opt. (`spirv-asm`, `SLANG_RUN_SPIRV_VALIDATION=1` and `-separate-debug-info` still load slang-glslang.) Walk the binary words in Python: `OpDecorate` is opcode 71 and NoContraction is decoration 42. For #13324 on master the counts matched v2026.20 ([count NoContraction from binary SPIR-V](../learnings/1792426835220-local-slang-release-build-lacks-spirv-opt-spirv-di.md)). On master, #12987 compiles at `-O0` ([-O0 skips spirv-opt](../learnings/1792424186345-local-slang-release-build-fails-target-spirv-with-.md)).
- **A crash or ICE before the downstream step** (exit 139, or E99997 in legalization) still reproduces on the local build ([ICE repros still work locally](../learnings/1792427491980-local-release-slangc-lacks-spirv-opt-use-a-release.md)).

Tarballs have their own gap. The Linux tarballs (checked v2026.17.1 and v2026.19) ship no `libslang-tint`, so `-target wgsl-spirv-asm` fails with E00100 'tint' / E52002, and `-target wgsl` works. Use them to diff WGSL text across versions (v2026.17.1 emits `for(;;)`; v2026.19 emits `loop` after PR #13071). For a real check, use naga (`pip install wgpu`): a Linux local build does not fetch slang-tint either ([tarballs lack slang-tint](../learnings/1792403683977-slang-linux-release-tarballs-lack-slang-tint-so-ta.md)).

Two examples show the before/after shape. For #12634, `Texture3D<float3>.SampleLevel` emits `tex3DLod<float3>` in v2026.14.1, v2026.15 and v2026.16, and NVRTC rejects it. v2026.17 and later emit `_slang_vector_reshape<float,3,float,4>(tex3DLod<float4>(...))`, and the PTX compiles (checked on v2026.19) ([#12634 bracket](../learnings/1792152922166-repro-version-specific-slangc-bugs-from-release-ta.md)). The bug is wider than that one call: on v2026.14.1 every 3-component CUDA texture sample fails (`Sample`, `Texture2D<float3>.SampleLevel`, `int3`/`uint3`), and that atom says releases before v2026.16.1 fail, so the fix probably first ships in v2026.16.1, a release the bracket above did not test ([#12634 scope](../learnings/1792400048814-slang-12634-scope-every-3-component-cuda-texture-s.md)). The mechanism is on [[wiki/concepts/misc-f0909b5-cuda-codegen-triage.md]]. For #12633 (Texture2DMS on CUDA), v2026.16 emits the field with no type, and v2026.19 reports E55215 ([#12633 bracket](../learnings/1792152959615-reproduce-pre-fix-slang-behavior-with-release-tarb.md)).

## Choosing the version bracket and finding the fix commit

Test the version the reporter used and the latest release first ([fast CUDA/PTX triage with release binaries](../learnings/1792153192040-fast-gpu-free-build-repro-compare-slang-release-bi.md)). To bracket a fix, find the fix commit with `git log -- <test>` (in a shallow clone this works only when the history reaches the commit; otherwise use `gh pr view`, below), then use `gh release list` dates to pick the release before it and the release after it ([release tarball before/after fix](../learnings/1792152959615-reproduce-pre-fix-slang-behavior-with-release-tarb.md)). To confirm that a fix PR shipped in a given release, check that it appears in the compare between two tags. The compare also finds the fix PR when you must not open the issue (in eval triage the issue's labels and state are the answer key): bracket the first good release with tarballs, then grep the window's commit subjects, which works in one call because bot PRs are titled "Fix #<n>: …": `gh api repos/shader-slang/slang/compare/v<bad>...v<good> --jq '.commits[] | .sha[0:10] + " " + (.commit.message | split("\n")[0])' | grep -i "<keyword>"`. For #12632 (CUDA half `SampleLevel` / `tex2DLod<__half4>`), v2026.16 was bad and v2026.16.1 good, and the compare named PR #12643, which added a `static_assert` diagnostic (E41400) ([find the fix PR without opening the issue](../learnings/1792304028705-find-the-fix-pr-for-an-issue-without-opening-the-i.md)). To name the *first* fixed release, test the first release after the fix merge date, not just a later one that happens to be fixed: #12988 was first recorded as shipping in v2026.18.3, but it is already in v2026.18.1 ([#12987 fix first ships in v2026.18.1](../learnings/1792403199630-12987-local-struct-conformance-fix-first-ships-in-.md)). The error runs the other way too. The #13070 fix (PR #13086, 6eb89786ca) was recorded as first shipping in v2026.19 because only v2026.18.1 and v2026.19 were tested, but `git tag --contains` puts it in v2026.18.3. So list the containing tags with `git tag --contains <merge-sha>` after `git fetch --tags`, then confirm the earliest one with its tarball, because patch releases often get backports ([find the first fixed release with git tag --contains](../learnings/1792424529371-find-the-first-fixed-slang-release-with-git-tag-co.md)). Sort that output by date, not by name (see the lexicographic trap on [[wiki/concepts/general-misc-b-tooling-and-shell-traps.md]]). The command needs real history. The `/workspace/agent/slang` clone is shallow (`git rev-parse --is-shallow-repository` prints `true`), so `git tag --contains` and `git log --grep='#13283'` return nothing even for a fix on master, and the empty result looks like "not shipped". In that clone, take `mergedAt` and `mergeCommit` from `gh pr view <n> -R shader-slang/slang --json mergedAt,mergeCommit` and compare `mergedAt` with the tag time (`git log -1 --format=%ci <tag>`), or ask the compare API: `repos/shader-slang/slang/compare/<sha>...<tag>` with status `ahead` means the tag contains the commit. Then confirm the behaviour with the local master `slangc` and the downloaded release ([shallow checkout: find fix commits with gh](../learnings/1792427616892-slang-checkout-is-shallow-find-fix-commits-with-gh.md), [#12852 compare-API check](../learnings/1792401919012-12852-workaround-on-v2026-16-1-loadmodulefromsourc.md)).

A release bracket narrows the search to a commit window, not to one commit. For #13273 the window between v2025.18.1 and v2025.18.2 held 19 commits, and two of them were plausible. Read each suspect's change to name the trigger ([#13273 release bisect](../learnings/1792159067590-13273-emit-fold-reorder-regressed-v2025-18-1-v2025.md)).

## CUDA/PTX triage with release binaries

`-target ptx` makes slangc call NVRTC, so a tarball gives a real CUDA compile check in a triage container with no build. NVRTC errors such as "dynamic initialization is not supported for a `__device__` variable" appear in seconds. For #12635 (nested static const arrays), v2026.14.1 fails and v2026.19 passes; PR #12688 fixed it ([fast CUDA/PTX triage with release binaries](../learnings/1792153192040-fast-gpu-free-build-repro-compare-slang-release-bi.md)). One atom says the tarball ships the NVRTC that slangc calls ([release tarball before/after fix](../learnings/1792152959615-reproduce-pre-fix-slang-behavior-with-release-tarb.md)). Another observed slangc using the container's NVRTC 12.6 at `/usr/local/cuda-12.6` ([fast CUDA/PTX triage](../learnings/1792153192040-fast-gpu-free-build-repro-compare-slang-release-bi.md)). Record which NVRTC version you ran when you quote a PTX result.

## Bisecting C++ API regressions with a linked repro

Compilation-API bugs (`loadModuleFromSource` and similar) do not need a source build either. Extract a tarball, then compile and link a tiny repro against it: `g++ -std=c++17 repro.cpp -I<X>/include -L<X>/lib -lslang-compiler -Wl,-rpath,$PWD/<X>/lib`. Use `-lslang` when the tarball has no `libslang-compiler.so`. Each version takes about a minute. For #12852 this showed that v2026.12.2 works, v2026.16.1 fails with "assert failure: slang-session.cpp(56): blob", and v2026.19 is fixed (PR #12853). That runtime evidence is stronger than "reproduced by code inspection" ([C++ API bisect by linking against release tarballs](../learnings/1792154932443-bisect-slang-c-api-regressions-by-linking-a-tiny-r.md)). The fix (merge e81aa6be) first ships in v2026.17, and current master reads the file when `source` is null and reports E00001 "cannot open file" for an unreadable path instead of asserting. Users stuck on v2026.16.x have a workaround: read the file themselves and call `ISession::loadModuleFromSourceString(name, path, text, &diag)`. It wraps `text` in a `StringBlob` before calling `loadModuleFromSource`, so the blob is never null and the `SLANG_RELEASE_ASSERT(blob)` does not fire ([#12852 workaround on v2026.16.1](../learnings/1792401919012-12852-workaround-on-v2026-16-1-loadmodulefromsourc.md)).

## Pitfalls: exit codes, hidden ICE text, and `-o -`

slangc can print an NVRTC error and still exit with code 0. Check that the output file exists, or grep stderr ([fast CUDA/PTX triage](../learnings/1792153192040-fast-gpu-free-build-repro-compare-slang-release-bi.md)).

Release builds do not print the ICE text that a debug build shows. The #12640 crash is a segfault with exit 139 and no message. Check `$?`, and do not trust empty output piped through `head`: the pipe hides the exit code, so read `${PIPESTATUS[0]}` ([#12640 on v2026.19](../learnings/1792153782868-12640-interface-only-default-arg-crash-still-repro.md)). A release binary also cannot tell you which phase crashed. #12640 segfaults with `-target none` and with `-skip-codegen` too, but IR lowering (`addDirectCallArgs`, `SLANG_ASSERT(argExpr)` in `slang-lower-to-ir.cpp`) still runs in both modes, so neither flag separates the checker from lowering. Use a debug build or a backtrace for that ([#12640 on v2026.20; -skip-codegen does not isolate the checker](../learnings/1792304859137-12640-still-segfaults-on-v2026-20-skip-codegen-doe.md); the same `-no-codegen` trap is on [Slang compiler crash triage](../concepts/misc-f0909b3-slang-compiler-crash-triage.md)).

Older slangc releases (v2025.1x) produce no output for `-o -`. In a cross-version bisect, write to a file such as `-o file.glsl`. If you do not, the old versions print nothing and get scored as failures ([#13273 release bisect, `-o -` gotcha](../learnings/1792159067590-13273-emit-fold-reorder-regressed-v2025-18-1-v2025.md)).

**#12640 (interface-only default argument).** The repro is `interface IFoo { void func(float A = 1.0); }` with an implementation `Foo::func(float A)` that has no default, called as `f.func()`. It segfaults (exit 139, no message) on v2026.14.1 and v2026.19 for both `-target spirv` and `-target cuda`. Master still has a plain `SLANG_ASSERT(argExpr)` in `addDirectCallArgs` (`slang-lower-to-ir.cpp` near line 4615). Three variants compile: an explicit argument, a call through a generic `T : IFoo`, and an implementation that has its own default ([#12640 still reproduces on v2026.19](../learnings/1792153782868-12640-interface-only-default-arg-crash-still-repro.md)).

**#12768 (nested swizzle lvalue).** The repro is `out.position.xyz.xyz = in.position.xyz;` compiled with `slangc -target glsl -stage vertex -entry vertexMain`. v2024.1.34 emits the correct `out_0.position_0.xyz = in_position_0.xyz;`. v2025.12.1 emits the broken `position_0[3] = vec3`; HLSL gives `[int(3)]` and SPIR-V gives `OpCompositeInsert %v4float %v3 %b 3`. v2026.19 is fixed by PR #12769 (merged 2026-09-01). So it is a true regression of working code. The bad `.add(elementCount)` line fits the 2024-11-15 `ShortList` refactor (05903f708) ([#12768 worked on v2024.1.34](../learnings/1792154620818-12768-nested-swizzle-lvalue-did-work-on-v2024-1-34.md)).

**#12987 (local-struct constrained-generic conformance).** The repro is a function-local `struct Op : IOp` with `apply<T : __BuiltinArithmeticType>`. It segfaults (rc=139) on v2026.17, v2026.17.1 and v2026.18 for spirv, hlsl and cuda ([#12987 crash matrix; #13092 is the generic variant](../learnings/1792156128422-12987-local-struct-constrained-generic-conformance.md)). The first fixed release is **v2026.18.1**, not v2026.18.3 as first recorded. The fix commit `b3aa9bec5` (PR #12988) merged on 2026-09-16, one day after v2026.18 (2026-09-15), so v2026.18.1 (2026-09-22) is the first release after it. v2026.18.1, v2026.19 and v2026.20 all compile the repro. The first check tested only v2026.18 (broken) and v2026.18.3 (fixed) and skipped .1 and .2. An "upgrade to X" reply must name the earliest fixed release: compare the fix merge date with `gh release list` dates and test the first release after the merge ([#12987 fix first ships in v2026.18.1](../learnings/1792403199630-12987-local-struct-conformance-fix-first-ships-in-.md)). If a report says it still fails on v2026.18.1 or later, check whether the local struct is generic (`Op<U>`): that is the separate bug #13092 (`lowerWitnessTable`), which #12988 does not fix.

**#13011 (optional-constraint ICE).** On v2026.19, `where optional T : X { return a + b; }` with `T` a struct behaves differently depending on `X`. `__BuiltinFloatingPointType`, `IFloat` and `IInteger` give ICE E99997 ("Unexpected context type for parameter info retrieval", in typeflow-specialize). `__BuiltinIntegerType` compiles silently to `a_0 + b_0` on a struct (#13061). `IArithmetic`, `ILogical` and `__BuiltinLogicalType` give the correct E39999. Use this matrix as the acceptance test set for a front-end fix of the optional-witness filter. `-target hlsl` and `-target spirv` both reproduce it with no GPU ([#13011 variant matrix on v2026.19](../learnings/1792156239266-slang-13011-optional-constraint-ice-variant-matrix.md)). The matrix is unchanged on v2026.20 and on master 68438b5e1. On the issue, saipraveenb25 wrote that "the correct fix is to properly filter lookup items if they are reached through optional constraints", which places the fix in the front-end lookup filter (`isWitnessUncheckedOptional`, `slang-check-expr.cpp:1344`), not in a guard in `slang-ir-typeflow-specialize.cpp` ([#13011 maintainer direction](../learnings/1792424334332-slang-13011-maintainer-direction-filter-lookups-re.md)). Until that fix lands, reporters can guard the arithmetic: `if (T is __BuiltinFloatingPointType) return a + b; return a;` compiles cleanly on v2026.20 for float and struct instantiations. HLSL emits `a_0 + b_0` for float and a plain `return a_1` for the struct ([#13011 `if (T is X)` workaround](../learnings/1792403257595-slang-13011-optional-constraint-ice-if-t-is-x-guar.md)).

**#13273 (emit fold reorder).** The C-like emitter re-reads `s.top` after `s.top -= 1` in `s.a[s.top]`. v2025.18.1 is correct and v2025.18.2 is wrong. Of the 19 commits in that window, 54e1d02715 (#8619) is the trigger. It made `canAddressesPotentiallyAlias` (`slang-ir-util.cpp` near line 1472) treat same-root, different-field access chains as no-alias, so `processLoadUse` in `simplifyForEmit` now defers `load(gep)` past the store to `s.top`. That exposes an older bug: the emitter's fold check does not follow always-folded GEP/FieldAddress users. #8588, in the same window, only changes generic-parameter ordering. Fix PR #13283 merged after the v2026.20 tag (see the status table) ([#13273 release bisect](../learnings/1792159067590-13273-emit-fold-reorder-regressed-v2025-18-1-v2025.md)).

## Contradictions / supersessions

- #12768: an earlier learning called the bug a long-standing latent bug and "not a regression in the used-to-work sense". The release bracket corrects that: v2024.1.34 emits correct code, so it is a regression ([#12768 worked on v2024.1.34](../learnings/1792154620818-12768-nested-swizzle-lvalue-did-work-on-v2024-1-34.md)). The earlier learning stays live because it also holds the root-cause analysis (two defects in `visitSwizzleExpr`), which the bracket does not repeat.
- NVRTC source for `-target ptx`: one learning says the tarball ships NVRTC, another observed the container's NVRTC 12.6. Both are stated above. Neither has been checked against the other.
- Two `git tag --contains` rules look like they conflict and do not. One learning says use it to name the first fixed release; another says it returns nothing in the shallow `/workspace/agent/slang` clone. Both hold: the command is right in a full clone with tags, and in the shallow clone the `gh pr view` `mergedAt` or compare-API check replaces it.
