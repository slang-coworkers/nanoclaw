# Reproducing version-specific Slang bugs with release tarballs, and bisecting across releases

The prebuilt Linux release tarballs of Slang answer "does version X have this bug?" without a CMake build. This page covers how to fetch and run them, how to use them for CUDA/PTX triage, how to bisect a C++ API regression by linking a tiny program against each tarball, the pitfalls that make a run look like a pass or a fail when it is not, and the version matrices measured for several issues.

## TL;DR

- A release tarball answers a version question in under a minute per version, with no CMake build and no GPU. Fetch with `gh release download v<ver> -R shader-slang/slang -p "slang-<ver>-linux-x86_64.tar.gz"` (or the asset `browser_download_url` from `gh api repos/shader-slang/slang/releases/tags/v<ver>`), extract, and run `bin/slangc` with `LD_LIBRARY_PATH=<dir>/lib`.
- The triage/eval container's local `build/Release/bin/slangc` is a quick master check; try it first. Builds before 2026-10-22 could not load slang-glslang (every SPIR-V compile failed with E00100 or E52002); the 653bfdeef rebuild emits and validates SPIR-V. On E00100, use a tarball for SPIR-V output and validation, and locally HLSL/CUDA/GLSL for front-end checks and bindings, or `-target spirv -O0` for raw SPIR-V words.
- Linux tarballs ship no slang-tint: `-target wgsl-spirv-asm` fails there, and plain `-target wgsl` works. Validate WGSL with naga.
- Always test at least two versions: the one the reporter used and the latest release. For a fix or a regression, add the release just before and just after the change.
- Name the first fixed release with `git tag --contains <merge-sha>` (after `git fetch --tags`) in a full clone, never by sampling two releases, and confirm on that release's tarball: patch releases often get backports.
- The local `/workspace/agent/slang` clone is shallow. There `git tag --contains` and `git log --grep` return nothing even for a fix on master. Use `gh pr view <n> --json mergedAt,mergeCommit` against the tag time, or the compare API (`compare/<sha>...<tag>` status `ahead` means the tag contains it). When the issue itself is off limits (eval triage), grep the `v<A>...v<B>` compare's commit subjects: bot fix PRs are titled "Fix #<n>: …".
- A reporter on an affected release needs the status plus a verified workaround. Several open or post-release bugs have one; see the status table.
- Bisect library source across tags without a clone: fetch a file at a tag through the contents API with `Accept: application/vnd.github.raw` and grep it.
- `-target ptx` runs NVRTC, so it is a real CUDA compile check that shows NVRTC errors in seconds.
- For C++ compilation-API bugs, link a tiny repro against each tarball: `g++ -std=c++17 repro.cpp -I<X>/include -L<X>/lib -lslang-compiler -Wl,-rpath,$PWD/<X>/lib`. Use `-lslang` if `libslang-compiler.so` is absent.
- A runtime result on real release binaries is stronger evidence than "reproduced by code inspection".
- Exit codes mislead: slangc can print an NVRTC error and exit 0 (check the output file or stderr), a Release crash is often exit 139 with no ICE text (check `$?`), and `| head` hides the exit code before it (use `${PIPESTATUS[0]}`).
- Older slangc releases (v2025.1x) write nothing for `-o -`. Write to a real file (`-o out.glsl`) in any cross-version run, or "no output" is scored as a failure.
- Run every target the report names (spirv, hlsl, cuda, glsl) and the nearby source variants. One target or one variant is not a matrix.
- After a release bracket, list the commits in that window and name the trigger. A window can hold an unrelated suspect.
- A crash report on a version older than the fix release is already fixed: tell the reporter to upgrade. A report that still fails on the fix release or later is probably a separate variant: check for one before reopening.
- A fix PR merged on the same day as a release tag can miss that release. Compare the PR's merge time with the tag time, not only the date.
- `-skip-codegen` and `-target none` still run IR lowering. A crash under them does not prove a checker crash; use a debug build or a backtrace.
- A matrix of constraint or source variants on one release is a good acceptance test set for a fix.
- Re-check open issues on each new release. The latest per-issue status table is in "Worked version matrices" below.

## Fetching and running a release

To check a bug against an older release, download that version's Linux tarball and run its `bin/slangc` on the repro. Two equivalent ways to fetch it work: `gh release download v<ver> -R shader-slang/slang -p "slang-<ver>-linux-x86_64.tar.gz"`, or the asset's `browser_download_url` from `gh api repos/shader-slang/slang/releases/tags/v<ver>`. Each version takes under a minute ([release tarball repro, #12634 Texture3D SampleLevel](../learnings/1792152922166-repro-version-specific-slangc-bugs-from-release-ta.md), [release tarball before/after fix, #12633](../learnings/1792152959615-reproduce-pre-fix-slang-behavior-with-release-tarb.md)). The binaries run with `LD_LIBRARY_PATH=<dir>/lib`, so a three-version bracket takes about two minutes ([#12768 release bracket](../learnings/1792154620818-12768-nested-swizzle-lvalue-did-work-on-v2024-1-34.md)). A wildcard pattern such as `--pattern "*linux-x86_64.tar.gz"` also selects the asset ([#12640 on v2026.19](../learnings/1792153782868-12640-interface-only-default-arg-crash-still-repro.md)).

You can also bisect without running anything. Fetch a source file at each tag and grep it: `gh api "repos/shader-slang/slang/contents/source/slang/hlsl.meta.slang?ref=v<tag>" -H "Accept: application/vnd.github.raw"` ([release tarball repro, #12634](../learnings/1792152922166-repro-version-specific-slangc-bugs-from-release-ta.md)).

**Try the container's local build first; fall back to a tarball on E00100.** In the triage and eval containers, `/workspace/agent/slang/build/Release/bin/slangc` is a ready master build with no slang-test beside it. It re-reproduces a non-SPIR-V codegen report in seconds (on #13108, `-target cuda` still emits the call-site temp `State_0 _S7 = original_1;`) ([prebuilt master slangc in eval-slang-triage](../learnings/1792425150374-eval-slang-triage-container-has-a-prebuilt-master-.md)). Builds up to the morning of 2026-10-22 had no loadable `slang-glslang`, so SPIR-V failed and hid whether the bug was still there: `-target spirv` exited 255 with E00100 "failed to load downstream compiler 'spirv-opt'" plus E99996 notes for `pthread` and `slang-glslang-0.0.0`, and `-target spirv-asm` failed on 'spirv-dis' or with E52002 "pass-through compiler not found" ([E00100 at -target spirv](../learnings/1792424186345-local-slang-release-build-fails-target-spirv-with-.md), [spirv-asm fails too](../learnings/1792423080231-slang-12847-pr-12848-is-still-a-draft-local-master.md), [E52002](../learnings/1792422693293-local-release-slangc-may-fail-spir-v-with-e52002-u.md)). A release `lib/` on `LD_LIBRARY_PATH` does not help, because the local build looks for the unversioned `libslang-glslang-0.0.0.so`; a 0.0.0-named symlink to the release library works (2026-10-21) ([E52002](../learnings/1792422693293-local-release-slangc-may-fail-spir-v-with-e52002-u.md)). The rebuilt binary at tree 653bfdeef (2026-10-22) compiles `-target spirv` and `spirv-asm` with no E00100, and with `SLANG_RUN_SPIRV_VALIDATION=1` it reproduced #13427's VUID-08722 directly ([local Release slangc now emits SPIR-V](../learnings/1792659932300-container-release-slangc-now-emits-spir-v-directly.md)). When a local binary still prints E00100 or E52002, pick the workaround by question:

- **SPIR-V output or validation:** the tarball's `bin/slangc` with `SLANG_RUN_SPIRV_VALIDATION=1`; its validator flags #13206's "may not return a logical pointer" on v2026.18 and v2026.20 ([tarball for SPIR-V repros; #13206](../learnings/1792425910957-local-build-release-slangc-in-eval-containers-cann.md)).
- **A front-end fix, or proof that a workaround compiles:** `-target hlsl -entry main -stage compute -o out.hlsl` (or CUDA) needs no downstream tool and still reports parser and checker diagnostics such as E39999 or E30047/E30049; a clean compile proves the front end accepts the code. `-lang hlsl` applies only to inputs after it ([hlsl for front-end checks](../learnings/1792427056805-local-slang-master-release-build-cannot-target-spi.md), [hlsl for E30047/E30049](../learnings/1792649817653-local-release-slangc-in-eval-container-can-t-emit-.md)).
- **Vulkan binding numbers:** `-target glsl -entry A -entry B`, then read `layout(binding = N)`; #13203 gives GLSL bindings 0-5 and HLSL b0/t0/u0 then b1/t1/u1 ([glsl for bindings](../learnings/1792425746359-local-release-slangc-in-triage-container-cannot-em.md)).
- **SPIR-V content with no disassembler:** `-target spirv -O0 -o x.spv` loads nothing, because `-O0` skips spirv-opt (`spirv-asm`, validation and `-separate-debug-info` still load slang-glslang). Walk the words in Python: skip the 5-word header; each instruction has opcode `w & 0xffff` and word count `w >> 16`. Opcodes: Capability 17, OpDecorate 71 (NoContraction is decoration 42), GroupNonUniformBallot 339, BallotBitCount 342, GroupNonUniformIAdd 349. On master this matched v2026.20's #13324 NoContraction counts ([count NoContraction from binary SPIR-V](../learnings/1792426835220-local-slang-release-build-lacks-spirv-opt-spirv-di.md)), confirmed #12847 (two `OpGroupNonUniformBallot` on one predicate), and showed `WavePrefixSum`/`WaveActiveSum(uint(b))` emit two `OpGroupNonUniformIAdd` (ExclusiveScan, Reduce) with no ballot ([-O0 emits SPIR-V](../learnings/1792647523271-eval-container-local-slangc-can-emit-spir-v-with-t.md)); #12987 compiles at `-O0` ([-O0 skips spirv-opt](../learnings/1792424186345-local-slang-release-build-fails-target-spirv-with-.md)).

Tarballs have their own gap. The Linux tarballs (checked v2026.17.1 and v2026.19) ship no `libslang-tint`, so `-target wgsl-spirv-asm` fails with E00100 'tint' / E52002, and `-target wgsl` works. Use them to diff WGSL text across versions (v2026.17.1 emits `for(;;)`; v2026.19 emits `loop` after PR #13071). For a real check, use naga (`pip install wgpu`): a Linux local build does not fetch slang-tint either ([tarballs lack slang-tint](../learnings/1792403683977-slang-linux-release-tarballs-lack-slang-tint-so-ta.md)).

Two examples show the before/after shape. For #12634, `Texture3D<float3>.SampleLevel` emits `tex3DLod<float3>` in v2026.14.1, v2026.15 and v2026.16, and NVRTC rejects it. v2026.17 and later emit `_slang_vector_reshape<float,3,float,4>(tex3DLod<float4>(...))`, and the PTX compiles (checked on v2026.19) ([#12634 bracket](../learnings/1792152922166-repro-version-specific-slangc-bugs-from-release-ta.md)). The bug is wider: on v2026.14.1 every 3-component CUDA texture sample fails (`Sample`, `Texture2D<float3>.SampleLevel`, `int3`/`uint3`), and releases before v2026.16.1 fail, so the fix probably first ships in v2026.16.1, which the bracket above did not test ([#12634 scope](../learnings/1792400048814-slang-12634-scope-every-3-component-cuda-texture-s.md)). The mechanism is on [[wiki/concepts/misc-f0909b5-cuda-codegen-triage.md]]. For #12633 (Texture2DMS on CUDA), v2026.16 emits the field with no type, and v2026.19 reports E55215 ([#12633 bracket](../learnings/1792152959615-reproduce-pre-fix-slang-behavior-with-release-tarb.md)).

## Choosing the version bracket and finding the fix commit

Test the version the reporter used and the latest release first ([fast CUDA/PTX triage with release binaries](../learnings/1792153192040-fast-gpu-free-build-repro-compare-slang-release-bi.md)). To bracket a fix, find the fix commit with `git log -- <test>` (in a shallow clone only if the history reaches it; otherwise `gh pr view`, below), then pick the releases before and after it from `gh release list` dates ([release tarball before/after fix](../learnings/1792152959615-reproduce-pre-fix-slang-behavior-with-release-tarb.md)). The tag compare confirms a fix PR shipped, and also finds the fix PR when you must not open the issue (in eval triage its labels and state are the answer key): bracket the first good release with tarballs, then grep the window's commit subjects, since bot PRs are titled "Fix #<n>: …": `gh api repos/shader-slang/slang/compare/v<bad>...v<good> --jq '.commits[] | .sha[0:10] + " " + (.commit.message | split("\n")[0])' | grep -i "<keyword>"`. For #12632 (CUDA half `SampleLevel`), v2026.16 was bad, v2026.16.1 good, and the compare named PR #12643 (an E41400 `static_assert` diagnostic) ([find the fix PR without opening the issue](../learnings/1792304028705-find-the-fix-pr-for-an-issue-without-opening-the-i.md)). Sampling two releases misnames the *first* fixed release: #12988 was recorded as v2026.18.3 but is already in v2026.18.1 ([#12987 fix first ships in v2026.18.1](../learnings/1792403199630-12987-local-struct-conformance-fix-first-ships-in-.md)), and the #13070 fix (PR #13086, 6eb89786ca) was recorded as v2026.19 although `git tag --contains` puts it in v2026.18.3. So list the containing tags with `git tag --contains <merge-sha>` after `git fetch --tags`, sorted by date rather than name (see the lexicographic trap on [[wiki/concepts/general-misc-b-tooling-and-shell-traps.md]]), and confirm the earliest with its tarball, because patch releases often get backports ([find the first fixed release with git tag --contains](../learnings/1792424529371-find-the-first-fixed-slang-release-with-git-tag-co.md)). The `/workspace/agent/slang` clone is shallow (`git rev-parse --is-shallow-repository`), so `git tag --contains` and `git log --grep='#13283'` return nothing even for a fix on master. There, compare `gh pr view <n> -R shader-slang/slang --json mergedAt,mergeCommit` with the tag time (`git log -1 --format=%ci <tag>`), or ask `repos/shader-slang/slang/compare/<sha>...<tag>` (status `ahead` means the tag contains the commit), then confirm the behaviour with the local master `slangc` and the release ([shallow checkout: find fix commits with gh](../learnings/1792427616892-slang-checkout-is-shallow-find-fix-commits-with-gh.md), [#12852 compare-API check](../learnings/1792401919012-12852-workaround-on-v2026-16-1-loadmodulefromsourc.md)).

A release bracket narrows the search to a commit window, not to one commit. For #13273 the window between v2025.18.1 and v2025.18.2 held 19 commits, and two of them were plausible. Read each suspect's change to name the trigger ([#13273 release bisect](../learnings/1792159067590-13273-emit-fold-reorder-regressed-v2025-18-1-v2025.md)).

## CUDA/PTX triage with release binaries

`-target ptx` makes slangc call NVRTC, so a tarball gives a real CUDA compile check in a triage container with no build. NVRTC errors such as "dynamic initialization is not supported for a `__device__` variable" appear in seconds. For #12635 (nested static const arrays), v2026.14.1 fails and v2026.19 passes; PR #12688 fixed it ([fast CUDA/PTX triage with release binaries](../learnings/1792153192040-fast-gpu-free-build-repro-compare-slang-release-bi.md)). Atoms disagree on whose NVRTC runs: the tarball's ([release tarball before/after fix](../learnings/1792152959615-reproduce-pre-fix-slang-behavior-with-release-tarb.md)) or the container's 12.6 at `/usr/local/cuda-12.6` ([fast CUDA/PTX triage](../learnings/1792153192040-fast-gpu-free-build-repro-compare-slang-release-bi.md)), so record the version with any PTX result.

## Bisecting C++ API regressions with a linked repro

Compilation-API bugs (`loadModuleFromSource` and similar) do not need a source build either. Extract a tarball, then compile and link a tiny repro against it: `g++ -std=c++17 repro.cpp -I<X>/include -L<X>/lib -lslang-compiler -Wl,-rpath,$PWD/<X>/lib`. Use `-lslang` when the tarball has no `libslang-compiler.so`. Each version takes about a minute. For #12852, v2026.12.2 works, v2026.16.1 fails with "assert failure: slang-session.cpp(56): blob", and v2026.19 is fixed (PR #12853), which is stronger evidence than code inspection ([C++ API bisect by linking against release tarballs](../learnings/1792154932443-bisect-slang-c-api-regressions-by-linking-a-tiny-r.md)). The fix (merge e81aa6be) first ships in v2026.17; master reads the file when `source` is null and reports E00001 for an unreadable path. On v2026.16.x, read the file yourself and call `ISession::loadModuleFromSourceString(name, path, text, &diag)`: it wraps `text` in a `StringBlob`, so the `SLANG_RELEASE_ASSERT(blob)` never fires ([#12852 workaround on v2026.16.1](../learnings/1792401919012-12852-workaround-on-v2026-16-1-loadmodulefromsourc.md)).

## Pitfalls: exit codes, hidden ICE text, and `-o -`

slangc can print an NVRTC error and still exit with code 0. Check that the output file exists, or grep stderr ([fast CUDA/PTX triage](../learnings/1792153192040-fast-gpu-free-build-repro-compare-slang-release-bi.md)).

Release builds do not print the ICE text that a debug build shows: the #12640 crash is exit 139 with no message. Check `$?`, and read `${PIPESTATUS[0]}` when piping through `head` ([#12640 on v2026.19](../learnings/1792153782868-12640-interface-only-default-arg-crash-still-repro.md)). A release binary also cannot tell you which phase crashed: #12640 segfaults with `-target none` and `-skip-codegen` too, but IR lowering (`addDirectCallArgs`, `SLANG_ASSERT(argExpr)` in `slang-lower-to-ir.cpp`) runs in both modes, so use a debug build or a backtrace ([#12640 on v2026.20; -skip-codegen does not isolate the checker](../learnings/1792304859137-12640-still-segfaults-on-v2026-20-skip-codegen-doe.md); the same `-no-codegen` trap is on [Slang compiler crash triage](../concepts/misc-f0909b3-slang-compiler-crash-triage.md)).

Older slangc releases (v2025.1x) produce no output for `-o -`. In a cross-version bisect, write to a file such as `-o file.glsl`, or the old versions print nothing and score as failures ([#13273 release bisect, `-o -` gotcha](../learnings/1792159067590-13273-emit-fold-reorder-regressed-v2025-18-1-v2025.md)). `-o /dev/null` fails too (E00004 cannot write output file). The same tarball (`slang-<ver>-linux-x86_64-glibc-2.28.tar.gz` from `releases/latest`) is the quick way to check a Discord or bot claim when the local clone is stale or unbuilt: about a minute, against 20+ minutes for a source build ([verify Discord/bot claims with the release tarball](../learnings/1792571968734-verify-discord-bot-slang-claims-with-the-release-s.md)).

**#12640 (interface-only default argument).** The repro is `interface IFoo { void func(float A = 1.0); }` with an implementation `Foo::func(float A)` that has no default, called as `f.func()`. It segfaults (exit 139, no message) on v2026.14.1 and v2026.19 for both `-target spirv` and `-target cuda`. Master still has a plain `SLANG_ASSERT(argExpr)` in `addDirectCallArgs` (`slang-lower-to-ir.cpp` near line 4615). Three variants compile: an explicit argument, a call through a generic `T : IFoo`, and an implementation that has its own default ([#12640 still reproduces on v2026.19](../learnings/1792153782868-12640-interface-only-default-arg-crash-still-repro.md)).

**#12768 (nested swizzle lvalue).** The repro is `out.position.xyz.xyz = in.position.xyz;` compiled with `slangc -target glsl -stage vertex -entry vertexMain`. v2024.1.34 emits the correct `out_0.position_0.xyz = in_position_0.xyz;`. v2025.12.1 emits the broken `position_0[3] = vec3`; HLSL gives `[int(3)]` and SPIR-V gives `OpCompositeInsert %v4float %v3 %b 3`. v2026.19 is fixed by PR #12769 (merged 2026-09-01). So it is a true regression of working code. The bad `.add(elementCount)` line fits the 2024-11-15 `ShortList` refactor (05903f708) ([#12768 worked on v2024.1.34](../learnings/1792154620818-12768-nested-swizzle-lvalue-did-work-on-v2024-1-34.md)).

**#12987 (local-struct constrained-generic conformance).** The repro is a function-local `struct Op : IOp` with `apply<T : __BuiltinArithmeticType>`. It segfaults (rc=139) on v2026.17, v2026.17.1 and v2026.18 for spirv, hlsl and cuda. The first fixed release is **v2026.18.1**, not v2026.18.3 as first recorded: fix `b3aa9bec5` (PR #12988) merged 2026-09-16, one day after v2026.18, and v2026.18.1, v2026.19 and v2026.20 all compile the repro. The first check sampled only v2026.18 and v2026.18.3. An "upgrade to X" reply must name the earliest fixed release, so test the first release after the merge ([#12987 fix first ships in v2026.18.1](../learnings/1792403199630-12987-local-struct-conformance-fix-first-ships-in-.md)). If a report says it still fails on v2026.18.1 or later, check whether the local struct is generic (`Op<U>`): that is the separate bug #13092 (`lowerWitnessTable`), which #12988 does not fix ([local conformance crashes at two stages](../learnings/1789483742996-function-local-interface-conformance-crashes-at-tw.md)).

**#13011 (optional-constraint ICE).** On v2026.19, `where optional T : X { return a + b; }` with `T` a struct behaves differently depending on `X`. `__BuiltinFloatingPointType`, `IFloat` and `IInteger` give ICE E99997 ("Unexpected context type for parameter info retrieval", in typeflow-specialize). `__BuiltinIntegerType` compiles silently to `a_0 + b_0` on a struct (#13061). `IArithmetic`, `ILogical` and `__BuiltinLogicalType` give the correct E39999. Use this matrix as the acceptance test set for a front-end fix of the optional-witness filter. `-target hlsl` and `-target spirv` both reproduce it with no GPU ([#13011 variant matrix on v2026.19](../learnings/1792156239266-slang-13011-optional-constraint-ice-variant-matrix.md)). The matrix is unchanged on v2026.20 and master 68438b5e1. The maintainer placed the fix in the front-end lookup filter (`isWitnessUncheckedOptional`, `slang-check-expr.cpp:1344`), not in typeflow-specialize ([#13011 maintainer direction](../learnings/1792424334332-slang-13011-maintainer-direction-filter-lookups-re.md)). Until it lands, `if (T is __BuiltinFloatingPointType) return a + b; return a;` compiles on v2026.20; HLSL emits `a_0 + b_0` for float and `return a_1` for the struct ([#13011 `if (T is X)` workaround](../learnings/1792403257595-slang-13011-optional-constraint-ice-if-t-is-x-guar.md)).

**#13273 (emit fold reorder).** The C-like emitter re-reads `s.top` after `s.top -= 1` in `s.a[s.top]`. v2025.18.1 is correct and v2025.18.2 is wrong. Of the 19 commits in that window, 54e1d02715 (#8619) is the trigger. It made `canAddressesPotentiallyAlias` (`slang-ir-util.cpp` near line 1472) treat same-root, different-field access chains as no-alias, so `processLoadUse` in `simplifyForEmit` now defers `load(gep)` past the store to `s.top`. That exposes an older bug: the emitter's fold check does not follow always-folded GEP/FieldAddress users (#8588, in the same window, only reorders generic parameters). Fix PR #13283 merged after the v2026.20 tag ([#13273 release bisect](../learnings/1792159067590-13273-emit-fold-reorder-regressed-v2025-18-1-v2025.md)).

## Contradictions / supersessions

- #12768: an earlier learning called the bug a long-standing latent bug and "not a regression in the used-to-work sense". The release bracket corrects that: v2024.1.34 emits correct code, so it is a regression ([#12768 worked on v2024.1.34](../learnings/1792154620818-12768-nested-swizzle-lvalue-did-work-on-v2024-1-34.md)). The earlier learning stays live because it also holds the root-cause analysis (two defects in `visitSwizzleExpr`), which the bracket does not repeat.
- Local Release slangc and SPIR-V: about ten learnings (2026-10-19 to the morning of 10-22) say it cannot load slang-glslang; a later 2026-10-22 rebuild (653bfdeef) can ([now emits SPIR-V](../learnings/1792659932300-container-release-slangc-now-emits-spir-v-directly.md)). Each dates one container build; check the binary in hand.
- Two `git tag --contains` rules look like they conflict and do not. One learning says use it to name the first fixed release; another says it returns nothing in the shallow `/workspace/agent/slang` clone. Both hold: the command is right in a full clone with tags, and in the shallow clone the `gh pr view` `mergedAt` or compare-API check replaces it.
