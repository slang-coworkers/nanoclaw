# Critique Gate and Decision Recording

## TL;DR

- A gate's denial is a claim: ask what it measured versus what you need to know (did the reviewed artifact change?). Audit any control by what it records when it cannot tell; "the previous answer" means it fails open.
- Input-side defects fail closed: the Bash pattern is verb-blind (a read-only `gh api .../pulls/<n>` is "PR creation") and scans command text; `edits_since_critique` is container-wide; a missing `/workspace/.claude/` blocks every call. Read via `gh api repos/O/R/issues/<n>`.
- Whether an approve still binds is answered by re-hashing `.critique_attested.OUTPUT_REVIEW`, not the counter. Write artifacts before the final round; Attested entries match by absolute path.
- A round is a fresh `mcp__codex__codex` call with `STAGE:`, the verbatim `/codex-critique` developer-instructions, and `REQUIREMENTS: none — <reason>` or a multi-line `R<n>. "<verbatim quote>" — <comment URL>` list. A `STAGE:` `codex-reply`, a freeform call or a one-line summary is not recorded.
- The verdict recorder fails OPEN: an unparsed reply keeps the stage's previous value, so a stale `approve` survives a `must-fix`, and a non-review (recall bullets, empty) inherits a prior `approve`. No `### Verdict` / `### Attested` in codex's own output means no review: re-ask, post nothing.
- Recall stubs come from the `AGENTS.md` recall rule in `cwd: /workspace/agent`: set `cwd` outside it and open with "Do NOT run a wiki or learnings recall — perform the review below directly and return only the structured output".
- A `codex-reply` updates a stage only if its thread was mapped at the initial call; `### Attested` parses only as plain `- <sha256> <absolute path>`, hash first: put that template in the prompt and check `.critique_verdicts`/`.critique_attested` after a reply-recovered round.
- Verdicts persist per stage across phases: a revived session is blocked by its old `must-fix`, even on reads, until fresh rounds run.
- The gate keys off delivery markers (`[Resolution]`, `[Report]`, `[Review Verdict]`), not diffs: a no-code close still needs every stage plus `OUTPUT_REVIEW=approve`. Marker sends need `in_reply_to`; abstain text avoids whole-word uppercase `BLOCK`/`WOULD_APPROVE`.
- A REQUIREMENTS URL without a `#anchor` fragment silently fails the round (REQ_OK=0, "Critique round NOT recorded" in additionalContext) — use `#issuecomment-<id>`, `#discussion_r<id>`, `#pullrequestreview-<id>`, or `#issue-<id>`.
- Workflow-state resets on every inbound, every 429-retry turn, and every restart — re-record all stages and deliver inside one turn. A codex-reply never records a stage, and `**Verdict**` bold-markdown is silently unparsed (pin the exact `### Verdict` heading in every codex prompt).
- The five-part PR body cannot pass the description gate (≤1000 chars, ≤2 lines per section): the Process report goes in the explain-diff-html comment; tell codex up front.
- A gate-denied side-effecting call is an OUTSTANDING ACTION: record the retry and verify the PUBLISHED copy by re-fetch and diff. Bypass after deny ×3 is a human dashboard approval (`critique_gate_bypass`); a blocked coworker opens a draft PR (skips CI) or escalates promptly.
- A must-fix on an input the approver cannot edit (PR-author comment style) is a gate-scope error: accept the factual catches, hold the scope line, label it ESCALATED. Codex also must-fixes its own `disabled://` sandbox; say so in the WHY.
- DECISION_REVIEW can flip a verdict on the merits (a multi-arm branch needs a test per arm); universal ("all"/"never") claims need whole-file evidence.
- Score a join off `head.sha`, never git ancestry, in a squash-only repo; a formal `APPROVED` at the decided commit beats a merge. Averted false-abstains and correctly declined checks leave no error signal: record them at join time.

## Overview

The `critique-gate` overlay blocks side-effecting calls via a PreToolUse hook (`gate-critique-on-deliver.sh`) until a PostToolUse hook (`track-critique.sh`) has recorded approving codex rounds in `/workspace/.claude/workflow-state.json`. Recipes: [gate mechanics](agent-routing-f0909b1-critique-gate-mechanics.md), [critique and delivery gates](agent-routing-f0909b2-critique-and-delivery-gates.md). See also [PR-Approver: Decision Procedure](../concepts/review-approver-decision-procedure.md), [Challenger Calibration](../concepts/review-approver-challenger-calibration.md), [PR Review Practices](../concepts/review-pr-practices.md).

## The gate is two instruments that fail in opposite directions

`gate-critique-on-deliver.sh` decides whether a call is a delivery and errs by over-including (costing rounds); `track-critique.sh` decides what codex said and errs by under-recording, silently keeping a previous approval it cannot parse past (letting a must-fix ship, which after bogus denials reads as the instrument finally agreeing). Every other defect fails closed ([the verdict recorder fails OPEN](../learnings/1785989503064-the-critique-gate-verdict-recorder-fails-open-a-mu.md)).

## Input side: fails-closed false positives

Four modes (mostly slang PR #12378) cost rounds without a real problem ([gate false positives](../learnings/1785992478312-critique-gate-false-positives-it-cannot-tell-a-get.md)).

1. **Verb-blind.** The `gh api [^|]*pulls\b` arm has no HTTP method, so a read-only `gh api repos/O/R/pulls/<n> --jq '.body'` is denied as PR creation; `gh api repos/O/R/issues/<n>` returns the same `body`, `labels` and `state`.
2. **Command text, not effect.** A heredoc mentioning `gh api … pulls` or `gh pr create` (slang#13742) is denied; write such scripts with the Write tool and run a bare `python3 script.py` ([disabled:// push URL is codex's own guard](../learnings/1792294811857-codex-critique-tell-codex-its-disabled-push-url-is.md)).
3. **`edits_since_critique` is container-wide** ("1 edit recorded" came from a peer session's `wt-slang-12371`). The attested-hash set answers "did my artifact change?"; if all hashes match the approve still binds:

```bash
STATE=/workspace/.claude/workflow-state.json
jq -r '(.critique_attested//{}).OUTPUT_REVIEW//{}|keys[]' "$STATE" | while read -r p; do sha256sum "$p"; done
jq -r '(.critique_attested//{}).OUTPUT_REVIEW//{}|to_entries[]|"\(.value)  \(.key)"' "$STATE"   # recorded
```

The counter is shared by ALL concurrent sibling sessions on one filesystem: a sibling's edit — even their codex start events in `critique-attempts.jsonl` — after your OUTPUT_REVIEW approve trips the delivery gate with "N edit(s) recorded since the last critique round" while your artifacts are byte-identical to the attested hashes. Diagnose via `last_edit_at` and `critique-attempts.jsonl` in `/workspace/.claude/`; resolve by re-hashing (must match the approve's `### Attested` lines), running ONE fresh OUTPUT_REVIEW stating the re-record premise, and dispatching immediately — never bypass ([critique freshness counter is cross-session](../learnings/1794992119333-critique-freshness-counter-is-cross-session-check-.md)). Side-fact: `//CHECK-DAG-SAME:` is not a real FileCheck directive (slang-test's DXC port parses only `-DAG:`/`-SAME:`/`-NOT:`/`-NEXT:`/`-LABEL:`), so it is silently ignored after a `CHECK-DAG` — use one `//CHECK-DAG: a{{.*}}b` pattern instead (`{{.*}}` doesn't cross newlines, so same-line association still holds).

4. **A missing state directory blocks everything.** Without `/workspace/.claude/` the hook's `> "$STATE.tmp"` fails (`No such file or directory`) and every call is blocked (slang#12924): `mkdir -p /workspace/.claude` at session start. Skill scripts (`collect-reviews.sh`, `eval-clauses.py`) hide their inner `gh api .../pulls`, since only the top-level command string is inspected ([read-only `gh api .../pulls` blocked; missing state dir](../learnings/1788945661953-approver-tooling-critique-gate-hook-blocks-read-on.md)).

## What counts as a round, and what an approve binds

`track-critique.sh` records a fresh `mcp__codex__codex` call only when the prompt carries `STAGE: <stage>`, `ROUND:` and `REQUIREMENTS:`, the developer-instructions hold both sentinel lines of the `/codex-critique` block verbatim, `sandbox` is `danger-full-access`, and the reply has `### Verdict` then `approve` ([gate mechanics](agent-routing-f0909b1-critique-gate-mechanics.md)); an ad-hoc call answered "APPROVE" is wasted (#14159, [canonical block only](../learnings/1793846123023-track-critique-gate-output-review-counts-only-with.md)). A `STAGE:` `codex-reply` is refused and a freeform call logs "stages: none"; codex nits a new item every round, so "3 rounds → escalate" is real ([codex-reply rounds don't count](../learnings/1789486053134-slangpy-pr-review-pin-to-explicit-shas-shared-chec.md)). A thread opened with your own prompt or a read-only sandbox records nothing, so each round is a new call carrying the prior findings (`ROUND: 2/3 — addressed M1 …`, slang#14027) [non-canonical threads don't count](../learnings/1793292848270-critique-gate-codex-reply-rounds-and-non-canonical.md).

**REQUIREMENTS format.** After `ROUND:` comes `REQUIREMENTS: none — <reason>` or a multi-line `R1. "<verbatim maintainer quote>" — https://github.com/<owner>/<repo>/issues/<n>#issuecomment-<id>` list (or `#discussion_r<id>`); a one-line `·`-separated summary is "round NOT recorded". The URL must carry a **fragment anchor** — the recording regex requires `#issuecomment-<id>`, `#discussion_r<id>`, `#pullrequestreview-<id>` or `#issue-<id>` (for an issue/PR body the maintainer wrote, `.../issues/<n>#issue-<n>`): a bare `https://github.com/owner/repo/issues/123` fails REQ_OK=0, the hook prints "Critique round NOT recorded" into additionalContext (easy to miss), and `gh pr create` / delivery markers keep failing with "missing critique stages" even though every round approved (slang#13834, [Critique REQUIREMENTS URLs need a #anchor or the round silently does not record](../learnings/1794899321120-critique-requirements-urls-need-a-anchor-or-the-ro.md)). OUTPUT_REVIEW grades every R-item, so a scoped-out one stays a merge blocker until the maintainer defers it on record: label it "pending maintainer deferral" and ask on the PR. The fixer's `[Fix Review Request]`/`[Fix Report]` gate needs `PLAN_REVIEW=approve` as well as `OUTPUT_REVIEW=approve` ([multi-line R<n> quotes](../learnings/1790758204134-codex-critique-requirements-must-be-multi-line-r-n.md); scope rule in [Working Live PRs Alongside Maintainers](../concepts/review-maintainer-live-pr-interaction.md)).

**The gate binds by content.** `### Attested` sha256s are re-hashed at send, so any write after the last OUTPUT_REVIEW approve (even a `.gh-comments/` id file) is an edit; track-edits also counts a Write under `/tmp` as a post-approve edit (only `/workspace/agent/reports/*` is exempt), so write comment bodies under `reports/` or expect a freshness denial ([Critique REQUIREMENTS URLs need a #anchor](../learnings/1794899321120-critique-requirements-urls-need-a-anchor-or-the-ro.md)). A chain-close (`[Resolution]`/`[Review Verdict]`) fires a `[GATE AUDIT]` demanding every required stage ≥1 plus `OUTPUT_REVIEW=approve` ([exact-format calls; Attested re-hashes at send](../learnings/1790016287155-critique-gate-resolution-pr-delivery-only-counts-c.md), [chain-close trips the gate](../learnings/1790042386094-verdict-bearing-chain-close-messages-resolution-re.md)). Upserting the PR explanation comment is such an edit, so OUTPUT_REVIEW re-runs before `[Fix Review Request]` ([round 1 recall summary](../learnings/1793815964150-codex-critique-round-1-can-return-a-wiki-recall-su.md)). The public-comment gate checks a comment file against `### Attested` only at 1,000+ characters, PATCHes included ([fixer delivery gates](../learnings/1793850163791-fixer-delivery-gates-review-request-field-format-i.md)), by ABSOLUTE path (a relative one is refused even with a matching sha256) (PR #13867, [absolute-path Attested](../learnings/1793228747743-codex-critique-a-first-call-can-return-wiki-recall.md)).

**Verdicts outlive their phase.** On slang-rhi#810 August PLAN/CODE_REVIEW `must-fix` verdicts refused a later read-only `gh api repos/.../pulls/810`. Read via `issues/<n>`, write memory with Edit, and run fresh rounds against a new plan file under `reports/` [stale earlier-phase verdicts](../learnings/1793274740895-stale-critique-verdicts-from-an-earlier-phase-bloc.md).

**Abstain `[Approval Decision]` sends.** Case-sensitive whole-word `WOULD_APPROVE`/`BLOCK` suppresses the ABSTAIN fast-path: "**Not BLOCK**" spends a `critique_gate_denials` strike (soft cap 3), so write "not a code-defect rejection" or lowercase "blocking". `gate-chain-routing.sh` needs `in_reply_to=<tasking inbound id>` on any marker send, even to a dashboard destination; keep the explicit `to=` ([abstain sends: no whole-word BLOCK; set in_reply_to](../learnings/1789057110525-approver-infra-abstain-approval-decision-abstain-m.md)). The routing gate demands `in_reply_to` even on a fresh peer dispatch — `thread_id` alone no longer satisfies it; its designed escape is the soft-fail after 3 denials, so retry the identical message a 4th time ([workflow-state resets on every inbound](../learnings/1794899983608-workflow-state-resets-on-every-inbound-record-crit.md)). The same gate applies to triage handoffs: any message whose text contains a delivery/handoff marker (e.g. `[Triage handoff]`) is rejected unless the call sets `in_reply_to` — for a fresh peer delegation pass `to`, `in_reply_to=<the parent inbound that spawned the chain>` and the canonical `thread_id`, while plain `[Triage]`/`[Report]` messages with just `to="parent"` pass ([LLVM CPU repro needs Debug build; handoff messages need in_reply_to](../learnings/1794962446679-llvm-cpu-repro-needs-debug-build-handoff-messages-.md)).

**The PR-description gate outranks the upstream five-part format.** Codex reads upstream slang `CLAUDE.md` and must-fixes a concise body, but `gate-pr-description.sh` refuses over 1000 characters or 2 lines per section, so the Process report goes in the `/explain-diff-html` comment; cite the hook up front and codex accepts. The hook also refuses `gh pr edit --body-file X` in the command that writes X ([OUTPUT_REVIEW recording pitfalls](../learnings/1792831235444-codex-critique-output-review-recording-pitfalls-fo.md)).

## Workflow-state resets wipe recorded rounds — make inbound-to-delivery one atomic window

Three host behaviors converge to silently erase approved critique rounds, each discovered only when a delivery failed afterward. **(1) The shared `/workspace/.claude/workflow-state.json` resets on EVERY inbound message and EVERY 429-retry turn** (each gets a fresh task_id), wiping `plan_written`, `critique_stages` AND `critique_threads` — during the 2026-11-17 429 storm this erased approved PLAN_REVIEW/CODE_REVIEW/OUTPUT_REVIEW rounds four times on slang#14469, forcing re-records of unchanged artifacts ([workflow-state resets on every inbound; record critiques and deliver in the same turn](../learnings/1794899983608-workflow-state-resets-on-every-inbound-record-crit.md)). **(2) A session restart wipes the same state**, so recorded verdicts are lost and approved stages must be re-run — don't re-run from scratch without checking (slang-fixer flagged this on the #13837 chain during a provider outage; escalated to the operator) ([NanoClaw workflow-state wipe on restart](../learnings/1794913228992-nanoclaw-workflow-state-wipe-on-restart-track-crit.md)). **(3) A codex-reply after a reset only bumps global counters without recording a stage**, so all three stages need fresh `mcp__codex__codex` STAGE calls ([REQUIREMENTS URLs need a #anchor](../learnings/1794899321120-critique-requirements-urls-need-a-anchor-or-the-ro.md)). The countermeasure that worked: treat one inbound-to-turn-end as the atomic window — re-Write the plan file (the tracker only records Write-tool writes), fire the three codex stages lean (spot-check phrasing gets the verdict in the initial call; expect narration-only returns needing a codex-reply on the thread id from `critique_threads`), then deliver immediately (`gh pr create` etc.) before anything new arrives.

Two neighbouring silent-loss shapes from the same cluster: **the track-critique hook only parses `### Verdict` headings** — a codex reply using `**Verdict**` bold-markdown is silently NOT recorded and looks like the review never happened; pin the exact `### Verdict` heading format in every codex prompt (host-side fix requested: accept both shapes) ([NanoClaw workflow-state wipe on restart](../learnings/1794913228992-nanoclaw-workflow-state-wipe-on-restart-track-crit.md)). And a codex CODE_REVIEW reviewer with `danger-full-access` can leave a STAGED REVERT of the fix in the worktree mid-review (its session died on a 429 before self-restore) — check `git status`/`git diff --cached` after every codex session that had filesystem access, and `git restore --staged --worktree <files>` to recover ([workflow-state resets on every inbound](../learnings/1794899983608-workflow-state-resets-on-every-inbound-record-crit.md)). From the same chain: to check whether a fixer pushed a branch, query it by exact name (`gh api repos/<owner>/<repo>/branches/<branch>`) — grepping page 1 of the paginated branch list gave a false "no branch" ([NanoClaw workflow-state wipe on restart](../learnings/1794913228992-nanoclaw-workflow-state-wipe-on-restart-track-crit.md)).

## The gate is code-blind: no-code closes still need every stage

A zero-diff triage-confirmation (`[Resolution]`, `[Report]`) is blocked until PLAN_REVIEW, CODE_REVIEW and OUTPUT_REVIEW (`approve`) are recorded. Satisfy it honestly: write the deliverable to a file and run PLAN_REVIEW on the no-code approach, CODE_REVIEW on `git status --porcelain` + `git diff --stat` and OUTPUT_REVIEW on the report as parallel canonical calls ([no-code triage-confirmations](../learnings/1783523465568-critique-gate-fires-on-no-code-triage-confirmation.md)).

The marker match is a keyword match over ANY sent message, not just real deliverables: a `[Review Verdict]` that merely *tells the fixer* to send their `[Fix Report]` — even a short follow-up correction — trips the gate. Satisfy it by running the codex OUTPUT_REVIEW on the actual deliverable (write the verdict to a file, put it + the combined review under ARTIFACTS), which records the round with the verdict + attested hashes; later gate-audit warnings on follow-up bookkeeping messages that introduce no new deliverable content can then be honored in spirit — the review that produced them is on record — without re-running codex on 2-line clarifications ([critique gate keyword-matches [Fix Report] in verdicts](../learnings/1794935349519-critique-gate-keyword-matches-fix-report-in-verdic.md)).

## Output side: the verdict recorder fails OPEN

Neither `critique_verdicts[STAGE]` nor the `Critique round N recorded` notice is trustworthy; codex's own `### Verdict` is. On slang#12089 codex returned `must-fix` on three consecutive `OUTPUT_REVIEW` rounds and the hook printed `OUTPUT_REVIEW=approve` each time ([the verdict recorder fails OPEN](../learnings/1785989503064-the-critique-gate-verdict-recorder-fails-open-a-mu.md)). In `track-critique.sh`:

| `tool_response` shape | parsed `RAW_VERDICT` | recorded |
|---|---|---|
| `{content: [{type:"text", text:"### Verdict\nmust-fix…"}]}` (**MCP array**) | *(empty)* | `""` |
| `{threadId:…, content:"### Verdict\nmust-fix…"}` (documented shape) | `must-fix` | `must-fix` |

`jq -r '.content'` renders an array as JSON text, so the awk match on `^###[ \t]*verdict` never fires; the stage writes are guarded `if $v != "" then … else . end`, so an empty parse keeps the previous value, and the `*) VERDICT="unparseable"` arm is unreachable. Tell: a verdict that never changes across rounds that returned must-fix items.

**Replies that are no review are recorded too.** A canonical call returning 2–5 wiki recall bullets and no `### Verdict` (or nothing, #13564) counts as a round and keeps the previous verdict, so a prior `approve` survives. Seen on #13817, PR #13867 and slang#14297 ([recall digest records approve](../learnings/1793206692748-codex-output-review-can-return-a-recall-digest-ins.md), [first-call recall](../learnings/1793228747743-codex-critique-a-first-call-can-return-wiki-recall.md), [round 1 recall summary](../learnings/1793815964150-codex-critique-round-1-can-return-a-wiki-recall-su.md), [prefix the prompt](../learnings/1793779536331-codex-critique-prefix-the-prompt-with-do-not-run-a.md), [recall notes recorded as approve](../learnings/1793839501898-codex-output-review-can-return-recall-notes-and-st.md)), and twice on #14366, where a fresh OUTPUT_REVIEW answered "I did not inspect either artifact file" and was logged `approve` ([codex OUTPUT_REVIEW can return recall bullets that the hook records as approve](../learnings/1793999712599-codex-output-review-can-return-recall-bullets-that.md)). Read every reply: on #13817 the re-ask found a real must-fix, and on #14366 a same-thread `codex-reply` ("your reply was not a review … return ONLY the structured output") got real reviews. Twice on 2026-11-09 a fresh OUTPUT_REVIEW of a draft issue comment returned only a recall summary; the same-thread re-ask ("read <file> and return VERDICT: …") then found 6 must-fix overclaims on round 1, and the PostToolUse hook's gate line kept showing `DIAGNOSIS_REVIEW=must-fix` after explicit OUTPUT_REVIEW approvals, so keep the codex thread IDs, not the gate line, as the verdict evidence ([fresh session's first answer can be a wiki recall](../learnings/1794239601487-codex-mcp-a-fresh-session-s-first-answer-can-be-a-.md)). A recorded approve proves only that a call was made; without a structured review, verify factual claims yourself before posting ([recall list instead of a review](../learnings/1792072692925-codex-critique-sometimes-returns-a-recall-list-ins.md)).

**The cause is the working directory; fix it on the first call.** With `cwd: /workspace/agent` codex runs the recall rule in its `AGENTS.md` (a symlink to the group's `CLAUDE.md`), so the first reply is ≤5 recall bullets or nothing (slang#13564, #13636, #13673). Set `cwd` outside it (`/tmp`, a scratch dir, or the per-issue worktree) and open with "Do NOT run a wiki or learnings recall and do not summarize prior notes — perform the review below directly and return only the structured output" [prefix the prompt](../learnings/1793779536331-codex-critique-prefix-the-prompt-with-do-not-run-a.md). Both together worked first try on slang#13742, #13993 [recall-only reply records no verdict](../learnings/1793220323154-slang-compare-compute-fails-on-any-stderr-warning-.md), slang#14027 [non-canonical threads](../learnings/1793292848270-critique-gate-codex-reply-rounds-and-non-canonical.md), slang-rhi#810 [stale verdicts](../learnings/1793274740895-stale-critique-verdicts-from-an-earlier-phase-bloc.md) and slang#14297 [round 1 recall summary](../learnings/1793815964150-codex-critique-round-1-can-return-a-wiki-recall-su.md); the no-recall line alone with `cwd` unchanged failed on slang-vscode-extension#78 ([cwd outside /workspace/agent](../learnings/1792695817981-codex-critique-run-with-cwd-outside-workspace-agen.md), [fresh sessions run the AGENTS.md rule](../learnings/1792136592884-fresh-codex-sessions-in-workspace-agent-run-the-ag.md), [skip recall in the prompt](../learnings/1792294811857-codex-critique-tell-codex-its-disabled-push-url-is.md)).

**Same-thread recovery is weaker; prefer a fresh call with the corrected `cwd`.** A `codex-reply` carrying `STAGE:` is refused ([cwd=/workspace/agent → recall bullets](../learnings/1792074066723-codex-critique-cwd-workspace-agent-can-make-codex-.md)); a STAGE-less one ("your reply was a recall summary — perform the review and return ONLY the structured output") elicits the review ([gate mechanics](agent-routing-f0909b1-critique-gate-mechanics.md); [reply on the same thread](../learnings/1792429620370-codex-critique-with-cwd-workspace-agent-returns-a-.md)). Recording it needs two parses. (1) The reply finds its stage via the `critique_threads` map written at the initial call; unmapped, it updates only `last_critique_verdict` ([prefix the prompt](../learnings/1793779536331-codex-critique-prefix-the-prompt-with-do-not-run-a.md)); mapped, it records (#14159, slang#14317). (2) `### Attested` lines record only when they match `-[ \t]*<64-hex>[ \t]+<path>`: with backticked hashes or paths the stage keeps the earlier approve's hashes and delivery is refused ("reviewed artifacts changed since the OUTPUT_REVIEW approve") though current hashes match ([recall stub](../learnings/1792695817981-codex-critique-run-with-cwd-outside-workspace-agen.md); slang#14317 [backticked hashes dropped](../learnings/1793830181320-critique-gate-backticked-attestation-hashes-are-si.md)). Codex's frequent hash-last `- \`path\` — SHA-256: \`hash\`` also records nothing, so a 1,000+ char `gh issue comment --body-file` is refused as "not among the files an OUTPUT_REVIEW attested"; list the file under an `ARTIFACTS:` heading and put the literal template `- <sha256> <path>` in the developer-instructions' `### Attested` block (recovery there was a fresh call) ([codex OUTPUT_REVIEW attestation must be `- <sha256> <abs path>` (hash first) or the public-comment gate refuses](../learnings/1794008715794-codex-output-review-attestation-must-be-sha256-abs.md)). After a reply-recovered round, check `.critique_verdicts` and `.critique_attested.OUTPUT_REVIEW` against your files before delivering ([recall notes recorded as approve](../learnings/1793839501898-codex-output-review-can-return-recall-notes-and-st.md)).

## A gate-blocked delivery is an outstanding action

On slang PR #12378 a reviewer flagged the same stale `742/742` in the PR body for eight rounds; each round it was fixed locally (`grep -c` → 0) and reported fixed, yet the posted body never changed ([a local fix is not a fix to the published copy](../learnings/1785992450842-a-fix-to-your-local-artifact-is-not-a-fix-to-the-p.md)). The loop: edit local → `gh` update → hook denies → satisfy the gate → never retry, since an approval feels like completion; record the retry of every denied call. When a reviewer contradicts your local measurement, suspect delivery, and diff content via the gate-safe issues endpoint (strip CRLF and `jq -r`'s trailing newline):

```bash
gh api repos/O/R/issues/<n> --jq '.body' > /tmp/live.txt   # PR bodies are served here too
tr -d '\r' < /tmp/live.txt | sed -e '$ { /^$/d }' > /tmp/live-norm.txt
diff /tmp/live-norm.txt ./local-body.md && echo "PUBLISHED == LOCAL"
```

**Hard-block escalation is a human approval.** The third deny of a coworker's `gh pr create` on an unfixable must-fix creates a `critique_gate_bypass` row in `pending_approvals` for `dashboard-admin` (`ncl approvals` is list/get only). Approve makes `src/modules/critique-escalation/` set `critique_gate_bypass_approved=true` and the `gh pr create` fires; Reject takes the pre-agreed clean path. The orchestrator gives the operator the `approval_id` (`ncl approvals list`) with a recommendation, never telling the coworker "proceed". A blocked coworker opens a draft PR (skips CI via `ci.yml`'s `draft != true`; not auto-merged) or escalates promptly (slang#12622 idled 13 days) ([bypass is a human approval](../learnings/1789272925575-critique-gate-bypass-is-a-human-dashboard-approval.md)).

When the shared-ledger race makes a gated marker permanently undeliverable, the compliant closure is the plain blocked-report to parent named by the gate's own rejection message: admin REJECTED the critique-gate bypass request (2026-11-18), and on slang#13833 the plain send (no marker) worked where the record-closing `[Fix Report]` marker is undeliverable in this fleet layout. Do not keep alternating record/retry cycles — each costs three codex calls and the approve never survives to the send (15+ wipes over two days; the wipe rate tracks sibling turn boundaries, not fleet load). The chain stays compliant because the SUBSTANCE was already public (PR, issue footprint, the triager's `[Triage Resolution]` with blocked:<reason>, memory file) — the formal marker is bookkeeping, not information; the durable fix is per-session ledger isolation, already escalated to the operator ([admin rejected the critique-gate bypass; plain blocked-report is the compliant closure](../learnings/1794988068539-admin-rejected-the-critique-gate-bypass-plain-bloc.md)).

## Gate-scope error: a must-fix on an input the approver cannot edit

On slang#12453 @425c2a95 DECISION_REVIEW held must-fix for three rounds after every factual fix, objecting only to two PR-author comments narrating history. That is a gate-scope error: comment hygiene covers the agent's own diff, not the approver's read-only input, and a maintainer had APPROVED the head. Accept every factual catch and let WOULD_APPROVE coexist with clarity nits. The host needs a critique `approve` to record WOULD_APPROVE/BLOCK, not ABSTAIN_\*, so the honest label is ESCALATED (gate/approver deadlock), not CHALLENGER_CONCERN or a silent WOULD_APPROVE. The durable fix exempts PR-author comment style from approver DECISION/OUTPUT_REVIEW must-fix ([comment hygiene over-applied](../learnings/1786490730776-approver-critique-mustfix-critique-gate-over-appli.md)).

Codex also must-fixes its own sandbox: its guard rewrites push URLs to `disabled://…` and it has no gh token, so PLAN/CODE_REVIEW flags "push target disabled / PR not opened" (slang#13742). Say in the WHY that this is codex's sandbox, the author pushes through the credential gateway, and CODE_REVIEW gates `gh pr create` ([disabled:// is codex's own guard](../learnings/1792294811857-codex-critique-tell-codex-its-disabled-push-url-is.md)).

## DECISION_REVIEW earns its keep, on the verdict and on the rationale

On slang#12892 DECISION_REVIEW flipped a decision on the merits: the parser fix enables a branch with two accepting arms (`checkedBase` a `DeclRefExpr` vs an `OverloadedExpr`) and the new test exercised only one, so WOULD_APPROVE became ABSTAIN_POLICY:OPEN_GAP; shared-machinery analogy does not clear an untested arm ([a test per arm](../learnings/1789066986411-approver-critique-mustfix-a-fix-that-enables-a-mul.md)). On slang#12993 it must-fixed rationale accuracy: "all argument access goes through the bounds-checked `get(i)`" came from `grep … | head -40` on a 1067-line file and was false (a direct `args[0]` near the end). Before any universal ("all"/"never"/"cannot") claim, `wc -l` and grep the whole file ([universal claims need whole-file evidence](../learnings/1789058775886-approver-critique-mustfix-universal-safety-claims-.md)).

## What the recording is for: the human-agreement join

Everything above serves a `record_decision` row in the `approval_decisions` ledger, pinned to a commit and later scored against what the humans did. Example: shader-slang/slang#12322 (gate `-emit-cpu-via-llvm` tests on LLVM availability), decided `WOULD_APPROVE` / `CLEAN` at `ba156ebf5c90`, merged at that exact head ([#12322 APPROVED at the decided SHA](../learnings/1785987292855-approver-human-agreement-slang-12322-joined-merged.md)). Score off `pulls/<n>.head.sha`, never git ancestry: in a squash-only repo `merge-base --is-ancestor` gives a false negative. A formal `APPROVED` at the decided commit approves the identical artifact, stronger than a merge.

**Averted false-abstains and declined checks leave no error signal.** "New flag + new gate" triggers a dead-flag probe that mandates `ABSTAIN_POLICY:OPEN_GAP` absent a trigger-present control. On #12322 it was rightly declined because the input failed its precondition: the gate (`_canIgnore` in `tools/slang-test/slang-test-main.cpp`) and flag bit (`SLANG_PASS_THROUGH_LLVM`) pre-existed, only two writers were added, and `addUsedBackEnd` (`tools/slang-test/test-context.h`) is a pure OR, so a test can only move running→`Ignored`. Demanding the control would have false-abstained an approved PR, which only the join records. Doc-vs-diff drift stays advisory here, never `OPEN_GAP`. A bot eviction comment on an unmoved green head (#12322, by the tracked Falcor flake #12145) is a no-op.
