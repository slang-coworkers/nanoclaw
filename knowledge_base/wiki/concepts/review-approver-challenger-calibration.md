# PR-Approver: Challenger CI-Gate, Verdict Calibration & Human Agreement

Once the deterministic clauses ([[wiki/concepts/review-approver-decision-procedure.md]]) pass and the review-doc verdict is parsed, Step 3 — the **adversarial challenger** — is where WOULD_APPROVE / ABSTAIN_POLICY(OPEN_GAP) / BLOCK are actually distinguished. The recurring theme: **the automated reviewers (production `github-actions[bot]`, CodeRabbit, Devin) do not build or run the test suites**, so a green review-doc verdict is blind to codegen-golden regressions, downstream-submodule breaks, and reachable release-asserts. The challenger's job is to pull the live CI check-runs, trace each red to cause, and read the source at the pinned head. This page collects the verified-BLOCK catches, the middle-rung ABSTAIN discriminators, the false-positive refutations, and the human-agreement calibration that validates the whole bar.

## The core CI-gate class: a green review-doc is blind to test regressions

A repeating BLOCK class — vindicated across #11595, #12130, #12106-R1, #12141 — is a **verified, deterministic, PR-caused break of a pre-existing CI-gated test** that the review-doc rated only nits. The challenger must harvest **check-runs at head** (not the combined-status glance) and read the failing job's failing STEP. Concrete instances:

- **Downstream submodule shaders test-slang never compiles.** slang#12141 disabled the `vector<T,4>` `(vec2,T)`/`(T,vec2)` initializers via `static_assert(false)`; the primary review was 🟡 APPROVE_WITH_NITS and Devin clean, all `test-slang` legs green — but the bundled `external/slang-rhi` submodule ships `test-ray-tracing-clusters.slang` with `float4(attribs.barycentrics, 1.f)` (a `float4(float2, scalar)`), which now hits the new E41400. Only `test-slang-rhi` compiles it, and it was RED. Any change to `core.meta.slang`/`hlsl.meta.slang` that *narrows what compiles* must be assumed to break downstream code until CI proves otherwise ([[approver/challenger-miss-averted] disabling a core-module init overload breaks bundled slang-rhi submodule shaders that test-slang never compiles](../learnings/1784270927259-approver-challenger-miss-averted-disabling-a-core-.md)).
- **Diagnostic-forwarding surfaces previously-swallowed warnings.** slang#12141 R2's `forwardDiagnostics()` on the constructor SUCCESS path re-emitted a long-standing `warning[E30081]` that broke pre-existing `tests/glsl/integer_pack.slang (vk)` — blast radius = *every input that already triggered that swallowed diagnostic*, living in tests that assert empty stderr. Critical calibration: a `.slang (vk)` test shows `conclusion=success` on a GPU-less runner because it is **`ignored`/skipped, not passed** — only a completed leg WITH the GPU counts ([[approver/challenger-miss-averted] a diagnostic-forwarding refactor that surfaces previously-swallowed warnings can break pre-existing empty-stderr tests](../learnings/1784304367382-approver-challenger-miss-averted-a-diagnostic-forw.md)).
- **A sanitizer-only link break.** slang#12136's new unit test touched the polymorphic internal `Slang::Session` via `asInternal()`; under `-fno-rtti` + the sanitizer's `-Wl,--no-undefined` the lazy-undefined `typeinfo for Slang::Session` became a hard link failure — RED on ONE of ~12 lanes only, so a per-lane check-runs scan is essential, and the leading `DWARF error: FORM value: 0x23` is benign noise (grep for `undefined reference|typeinfo`) ([[approver/challenger-miss-averted] A new unit test touching the polymorphic internal Slang::Session (via asInternal()) fails to link ONLY in the sanitizer job — -fno-rtti + -Wl,--no-undefined turns a lazy-undefined typeinfo into a hard build break](../learnings/1784271192351-approver-challenger-miss-averted-a-new-unit-test-t.md)).
- **A generic-predicate revision widens blast radius.** slang#12111 R1 approved a Layer-B fix (coalesce descriptor-heap loads in the SPIR-V legalizer, dominance-by-construction). The `synchronize` re-implemented the SAME fix as Layer A (make any `UniformConstant` load movable in the generic `isMovableInst`, so CSE collapses them) — reviewer-directed and Devin-clean, but it regressed unmodified `intrinsic-texture.slang.6/.7/.8` goldens because the predicate ALSO fires on plain sampler globals. A "move the same fix to a more generic layer" revision is a materially different change with a different blast radius → full fresh challenger + a live CI diff-vs-master, never a rubber-stamp ([[approver/challenger] Same-fix Layer-A (generic CSE) revision needs a fresh CI probe — broader blast radius than the Layer-B head you approved](../learnings/1784328018356-approver-challenger-same-fix-layer-a-generic-cse-r.md)).
- **A data-submodule pointer bump can turn CI red on UNTOUCHED tests — the review doc is blind to it.** slangpy#1082 had a clean-ish review doc (0 bugs, Devin nothing) but 6/12 build jobs red: unchanged `test_dds_file.cpp` threw "No such file" for `bc7-unorm-{nonsquare,3d}.dds` because the PR bumped the `data` submodule `4c24c797`→`6ecdf7c` and the new data commit had *removed* those fixtures. Treat any `160000`-mode / `Subproject commit` hunk as a first-class review surface: `require_ci_green=false` means the clause PASSES over red CI so look at the actual check-runs, pull a failed job log, and diff the submodule tree across the two refs (`gh api repos/<data-repo>/contents/<dir>?ref=<old>` vs `?ref=<new>`, or 404-probe the missing file) to attribute the break — a real trigger + real blast radius + no verified *code* 🔴 = ABSTAIN_POLICY:OPEN_GAP, never approve over red CI you've tied to the PR's own change ([[approver/challenger-ci-gate] Data-submodule bump can turn CI red on UNCHANGED tests — always diff the submodule tree](../learnings/1785426143619-approver-challenger-ci-gate-data-submodule-bump-ca.md)). The fix is symmetric and confirmable: on the re-review synchronize the author pushed one commit "Restore data submodule" reverting the pointer, `gh compare old...new` showed exactly ONE changed file (`data`), the restored ref contained the two fixtures again, and CI settled green 12/12 — a green re-run on a byte-identical-except-data diff cleanly retires that specific OPEN_GAP (but only after CI fully settles; don't decide on in-progress runs) ([[approver/challenger-ci-gate] Confirmed: reverting a data-submodule bump restores fixtures and turns CI green — the fix for the #1082-class OPEN_GAP](../learnings/1785495128502-approver-challenger-ci-gate-confirmed-reverting-a-.md)). The mirror-image trap on the same PR: a later `synchronize` that is a *merge of `main`* touched only unrelated files (texture_loader, a device test, CMakeLists) and left the flagged `torch_bridge_impl.cpp` byte-identical — so the prior Devin 🔴 recurred verbatim. "New push" ≠ "concern addressed": compute `gh api compare/<prevhead>...<newhead>`, and if the flagged path isn't in the delta the prior code-level disposition stands — say so and name what WOULD move it (a change to the flagged file, or a human sign-off) ([[approver/challenger-ci-gate] A main-merge synchronize can't clear a code-level 🔴 — diff the two heads before assuming the push addressed it](../learnings/1785496402847-approver-challenger-ci-gate-a-main-merge-synchroni.md)).

## Attribution: a PR that EXPOSES a pre-existing defect by changing global behavior owns it

On slang#12089 rev6 a capability-narrowing PR flipped the default HitObject type on `sm_6_9+hlsl_nvapi` from NVAPI to native `dx::HitObject`, but four LSS accessors keyed on a *different* capability were NOT re-gated → mixed-ABI HLSL, the exact defect class the PR exists to eliminate. The buggy lines are pre-existing and untouched — tempting to downgrade to ABSTAIN "latent" — but the PR is the *proximate cause*: it transformed those methods from matched-at-base to mixed-at-head by changing the type-selection predicate. A defect a PR exposes by changing global behavior is attributable → BLOCK ([[approver/challenger] A capability-narrowing PR can EXPOSE pre-existing mixed-ABI on sites it doesn't touch — flipping the default type re-gates behavior of unedited methods (attributable → BLOCK)](../learnings/1784310133019-approver-challenger-a-capability-narrowing-pr-can-.md)). The transferable check on any capability-narrowing / default-flipping PR: enumerate ALL methods on the affected type, not just the arms in the diff — a method whose `case hlsl:` emits a vendor intrinsic but is callable regardless of the resolved ABI is a mixed-ABI candidate under the new default.

## Reachable RELEASE_ASSERT is a RED_BUG — prove reachability at the producer

slang#12147's `SLANG_RELEASE_ASSERT(debugArtifactCount == 1)` aborts slangc on valid multi-entry-point input, while its sibling validator `_validateCoverageManifestOutputPaths` handles the same `>1` case with a graceful diagnostic — the asymmetry between two sibling validators is the smell ([[approver/challenger] RELEASE_ASSERT on a reachable multi-artifact count is a RED_BUG, not a valid impossible-shape guard](../learnings/1784316403221-approver-challenger-release-assert-on-a-reachable-.md)). The subtle part is the *trigger*: for a SINGLE SPIR-V target slang forces whole-program (count==1) on every path (no-`-o` synthesizes a stdout output gated on `m_rawTargets==1`), so the assert is reachable **only via multi-target ≥2 entry points + no per-target `-o`**, which sidesteps the single-target synthesis guard ([Slang separate-debug-info: multi-target demotes SPIRV out of whole-program → per-EP debug artifacts abort the count==1 assert](../learnings/1784336687356-slang-separate-debug-info-multi-target-demotes-spi.md) on the compiler-internals page). The recall subagents AND the production bot all CONVERGED on a wrong single-target trigger — **convergence is not correctness** — and a DECISION_REVIEW critique that adversarially hunts the gate the finders missed is what caught it; run it whenever the challenger overrides a lenient doc verdict on a reachability argument ([[approver/challenger-miss] single-vs-multi-target whole-program forcing hides the reachable RELEASE_ASSERT trigger](../learnings/1784333455962-approver-challenger-miss-single-vs-multi-target-wh.md)).

## The middle rung: green CI can still be a hold (ABSTAIN / OPEN_GAP)

A green-CI revision that fixes only the *symptom* rather than *scoping the root change* is a hold, not a WOULD_APPROVE. slang#12141 R3 added explicit casts to the ONE test E30081 broke, but left the over-broad `forwardDiagnostics()` unchanged — the latent surface remains for every other/future consumer, and a `diagnoseRaw` re-emission bypasses per-id `-Wno-*`/`#pragma warning` suppression by construction. Two challenger checks CI cannot do: did the fix scope the root change or just silence the symptom, and does the re-emission bypass user suppression → `ABSTAIN_POLICY:OPEN_GAP` (verified over-broad, plausible trigger, real blast radius, not false-negative-safe), the rung between BLOCK (no reproduced 🔴) and WOULD_APPROVE ([[approver/challenger-miss-averted] a test-cast workaround fixes the broken test but not the over-broad change; scope+suppression-bypass gaps are CI-invisible WOULD_APPROVE→ABSTAIN discriminators](../learnings/1784309271831-approver-challenger-miss-averted-a-test-cast-worka.md)). The calibration across one PR's three revisions — BLOCK (rhi break) → BLOCK (E30081 regression) → ABSTAIN/OPEN_GAP (contained but one latent scope gap) — shows the approver's job is to track the residual, not rubber-stamp "the last thing I flagged is fixed."

## When a gap CLEARS: is the worst realistic failure a build break CI catches, or a silent miscompile it wouldn't?

The decisive discriminator for clearing a speculative gap is the *failure class*. For a **build-flag / optimization-level PR** whose only risk is a CI-visible `-Werror` build break, complete + green CI on the exact affected config legs is sufficient to clear it — the failure would be a build error, not a silent runtime miscompile. slang#12140 (`-Og` for GCC/Clang debug) cleared a "`-Wmaybe-uninitialized` might break `-Werror`" gap because the affected debug legs were green at head, `-Wmaybe-uninitialized` is GCC-only (the "macOS Clang" framing was misdirected), and the blast radius is Debug+GCC/Clang only ([[approver/calibration] build-flag PR: clear a "-Werror CI break" gap by checking the affected config is actually green](../learnings/1784270606102-approver-calibration-build-flag-pr-clear-a-werror-.md)). Two extensions of the rule: a **subtractive guard** (`AND NOT MSVC`) relative to a prior CLEAN head can only *remove* a flag, never add it → cannot regress prior-green, so the verdict is ≥ prior without re-derivation; and a warning-coverage gap on a **pure-cmake PR that adds zero C++** clears as *future-proofing* (the PR introduces no uninitialized-variable risk itself) ([[approver/calibration] -Og debug-build guard: subtractive NOT-MSVC guard can't regress prior-green; -Wmaybe-uninitialized gap clears as future-proofing when PR adds no C++](../learnings/1784288671711-approver-calibration-og-debug-build-guard-subtract.md)). Contrast codegen/logic PRs where green CI ≠ safe — a miscompile passes all tests.

**False-negative-safe-by-construction exemptions approve.** For a diagnostic-suppression PR, don't ask "could this hide a bug?" in the abstract — trace the diagnostic's *fire conditions*. slang#12011's E41017 `__extern_cpp` exemption is safe because `checkUninitializedGlobals` only fires when a global has no in-module init AND no store, and the exemption predicate (`IRExternCppDecoration` + external linkage) is a strict subset of the documented host-provided-global pattern (value comes from outside the module by design) — plus a discriminator test proves the predicate is narrow ([[approver/calibration] E41017 __extern_cpp exemption is false-negative-safe by construction — approve the class](../learnings/1784288118508-approver-calibration-e41017-extern-cpp-exemption-i.md)).

A recurring backend-guard instance of the same class: wrapping ONE `[shader]` entry point of a shared multi-entry Slang test module in `#ifndef __TARGET_CUDA__` so the module stays loadable on CUDA for its siblings (Slang capability-checks all entry points at load time, so one unsupported `Buffer<T>`/`RWBuffer<T>` entry under E36107 takes the whole module down). Don't approve on the diff alone — two probes make it airtight: (1) **structural containment** — read the full file at head to confirm the `#ifndef`/`#endif` wraps ONLY the target entry point, no sibling accidentally stripped; and (2) the load-bearing **skip-before-load ordering** — the PR claims "no coverage loss because the guarded variant is already `pytest.skip`-ed on CUDA", so VERIFY the skip fires *before* the `load_program(..., ["copy_"+type])`; if it were after, stripping the entry point would turn a clean skip into an "entry point not found" error (a regression, not a no-op). On slangpy#1083 the skip at `test_buffer.py:76-77` precedes the load at L118-120, the macro was real in-repo precedent, and non-CUDA backends keep the entry point → WOULD_APPROVE on the Devin-only tier (production skips bot fixer branches → harvest exit 20) ([[approver/challenger-clean] CUDA preprocessor-guard on a shared Slang test module — verify skip-before-load ordering](../learnings/1785453364629-approver-challenger-clean-cuda-preprocessor-guard-.md)). This was CONFIRMED by merge: jkwak-work left a formal APPROVED and merged at the EXACT R2 head `a31e8af8` with zero follow-ups — clean agreement. A verdict-state nuance worth carrying: the human signal *evolved* (R1 COMMENTED "Looks good to me." + a nit → R2 APPROVED after the nit was addressed), and only the final state is the calibration truth — an early COMMENTED/LGTM is directionally positive but NOT a formal approve; always join the verdict to the commit it was submitted against and re-check reviews at the merged head ([[approver/challenger-clean] CONFIRMED by merge — CUDA preprocessor-guard on shared test module (slangpy#1083)](../learnings/1785462075111-approver-challenger-clean-confirmed-by-merge-cuda-.md)).

**Constness-selected SPIR-V operands: trace the *emitted* form.** slang#12133's Gather const-offset fix emits `ConstOffset` (legal only if the offset is an `OpConstant`/`OpConstantComposite`). "The helper detects constants" is not enough — verify the constant-hoisting pass (`maybeHoistConstructInstToGlobalScope`) actually moves the accepted shapes to global scope and that the classifier's accepted set ⊆ the hoister's hoistable set; when the PR's test is spirv-asm-only (no real `spirv-val`), this inspection IS the validation gate ([[approver/challenger] ConstOffset-safety hinges on constant-MakeVector hoisting (maybeHoistConstructInstToGlobalScope), verify it — slang#12133](../learnings/1784334175709-approver-challenger-constoffset-safety-hinges-on-c.md)).

## Real-hardware CI can substitute for a missing Devin — but only if it actually EXERCISED the code

On the slang-rhi fallback tier, slang-rhi runs the full test suite *inline in the build matrix on real GPU adapters*, so a timed-out Devin on a behavior-changing PR (#797 D3D12 timestamp resolve) doesn't force ABSTAIN — pull the CI *job logs* and grep for the PR's new test executing + PASSING on a real adapter (`hardware-device`, not `software-device`/`SKIPPED`) ([[approver/human-agreement] slang-rhi real-hardware CI substitutes for a timed-out Devin on backend-logic PRs](../learnings/1784271405834-approver-human-agreement-slang-rhi-real-hardware-c.md)). The mirror-image trap: a **support-claiming PR whose test is masked-out is compile-only, never executed**. slang-rhi#800 flipped `docs/api.md`'s Metal `dispatchComputeIndirect` cell to `yes` and added real Metal code with green CI — but the feature's `GPU_TEST_CASE(..., D3D12 | Vulkan | CUDA)` *excludes Metal*, so the macOS job compiled but never ran the new path; green CI proves it builds, not that it works → a genuine `OPEN_GAP` for a support-claiming PR ([[approver/clause-gap] Backend-support PR that flips a docs support-matrix cell but leaves the feature's test masked-out is compile-only, never executed](../learnings/1784338875078-approver-clause-gap-backend-support-pr-that-flips-.md)). And CI green in a decoupled component (a standalone Go tool in `extras/scaler` that no CMake/CI job builds) is *orthogonal* — it can't substitute for a missing review signal the way real-hardware CI does.

The masked-out-test class recurs even when the PR SHIPS a test: slang-rhi#801 (native Metal buffer import) shipped `test-buffer-from-handle.cpp` that calls the new Metal code, but its device mask was `GPU_TEST_CASE("buffer-from-handle", D3D12 | Vulkan)` — `Metal` omitted, so `GPU_TEST_CASE` (which registers one case per flagged device) registers NO Metal case, and the macOS job compiled but never executed the import path. (⚠️ The original write-up said the macOS runner "DOES run `-check-devices` on Metal hardware" — **withdrawn as stated**: the hosted `macos-latest`/`macos-26-arm64` adapter is an `Apple Paravirtual device`, and until slang-rhi#807 restored Metal device init it reported Metal *unsupported* and skipped every Metal case. A mask is a declaration of intent; whether a case runs is decided by the runner the job lands on ([[approver/challenger-miss] test-mask registration is not test execution — resolve the job's `runs-on` and open a log](../learnings/1785787084796-approver-challenger-miss-test-mask-registration-is.md)).) The `checkNoSilentGpuSkips()` guard doesn't catch it — it only flags a device with registered-but-zero-running tests, not a device with zero registered cases. So for any slang-rhi backend-specific PR, don't stop at "a test exists": **grep the test's `GPU_TEST_CASE(...)` mask and confirm the PR's target backend flag is IN it** — a Metal-only change tested only under `D3D12 | Vulkan` is OPEN_GAP (source-verified-correct doesn't round it up), same class as #800; next-action = add `Metal` to the mask or consciously accept the untested-on-Metal risk [[approver/challenger] slang-rhi Metal-only feature with test masked to D3D12|Vulkan = OPEN_GAP](../learnings/1784816143760-approver-challenger-slang-rhi-metal-only-feature-w.md).

A THIRD zero-coverage mode is compile-out via an unmerged-companion-ABI gate, distinct from both the runtime SKIP and the masked-out-test. slang-rhi#803 (CPU ray query) shipped a 1120-line impl + dedicated CPU tests + 30 CTS cases, but the whole CPU path — impl AND tests — is *compiled out* in merge-gating CI: the feature is gated behind `SLANG_RHI_ENABLE_CPU_RAY_QUERY`, whose default hinges on the fetched Slang package shipping `prelude/slang-cpp-ray-query.h`, a header that only exists in an OPEN companion PR (slang#12282) and is absent from the pinned `v2026.12.2` release → ABI_AVAILABLE=OFF → the test file is `target_sources`-gated out and the CTS device mask degrades `CPU|D3D12`→`D3D12`. So for any slang-rhi feature behind a `cmake_dependent_option` whose default hinges on a Slang-package header/ABI, check whether that header ships in the pinned `SLANG_RHI_FETCH_SLANG_VERSION`; if it only lives in an unmerged companion, the code+test are excluded from the build (compiled out, not merely runtime-SKIPPED), and the "CPU runs headlessly" counterweight must NOT round up — this is an OPEN_GAP, compounded here by fork-PR CI sitting at `action_required` (never ran) ([[approver/challenger] slang-rhi feature gated on unmerged companion Slang PR compiles out in CI — zero-coverage distinct from Metal-SKIP](../learnings/1785395617012-approver-challenger-slang-rhi-feature-gated-on-unm.md)). But when arguing "compiles out", verify it per-file/per-symbol, not categorically: a MIXED CMake toggle excludes only SOME files as whole `target_sources` while others compile UNCONDITIONALLY with internal `#ifdef`s — on #803 R2 the claim "all the feature's code is gone" was caught overbroad, because only `cpu-acceleration-structure.cpp` was whole-file-excluded while `cpu-command.cpp`'s flagged `cmdQueryAccelerationStructureProperties` compiled regardless of the toggle. `grep -n <file> CMakeLists.txt` to distinguish whole-source exclusion from internal-`#ifdef`, open the specific flagged line to confirm IT is inside the guard (count of macro occurrences is not enough), and state "compiled and registered" not "would exercise" unless the CI device is confirmed to run it — a subtly-false "don't worry, it all compiles out" premise could make a human dismiss a live finding ([[approver/challenger-miss] "compiles out" on a partially-gated feature must be verified per-file/per-symbol, not asserted categorically](../learnings/1785416472140-approver-challenger-miss-compiles-out-on-a-partial.md)).

## Combined-status ≠ causal: classify from individual check-runs traced to cause

The GitHub combined commit-status aggregates ALL contexts including non-causal cross-repo/downstream jobs. On the clean front-end PR #12131 combined-status was `failure` from a `test-falcor` image-diff flake (from a prior draft run) and a `SlangPy Tests` `test_profiler.cpp` CPU-timing assertion (Linux-only, passed on Windows) — neither reachable by the PR's code path ([[approver/calibration] combined-status-failure-from-non-causal-downstream-flakes](../learnings/1784329341037-approver-calibration-combined-status-failure-from-.md)). When `require_ci_green:false` defers, enumerate individual check-runs `--paginate`, confirm the repo's OWN core legs (especially the one running the PR's new tests) are `success`, and for each red trace the failing test — platform-asymmetric / timing / image-diff / downstream-renderer failures are non-causal-flake signals. The rule is symmetric: classify from check-runs traced to cause, never from combined-status alone, in EITHER direction (a green combined-status is equally untrustworthy — see #12130's metal-fmod miss). `SlangPy test_profiler.cpp` is a recurring non-causal flake for slang PRs.

## A stale secondary reviewer flags the pre-fix state — verify at head

On slang#12147 R4 (the fix revision) Devin ran ~5 min after the push and flagged the R1-R3 blocking bug verbatim at `:766` — but the assert was already gone; Devin analyzed a stale/cached snapshot, and its line number had shifted meaning across the revision (`:766` was now a harmless guard, the graceful diagnostic at `:798`) ([[approver/stale-secondary] Devin (secondary) reviews the pre-fix prefix state on a fresh-push revision — verify the flagged line against head source before trusting a bug flag](../learnings/1784343479716-approver-stale-secondary-devin-secondary-reviews-t.md)). Never accept a secondary bug flag on faith on a fresh-push revision: the PRIMARY tier harvested at the pinned head (matching `diff_hash`) is the verdict source, and open the flagged `file:line` at the pinned head, locating the construct by NAME not line. This is the flip side of the false-positive class below — a secondary flag is a hypothesis to verify at head, never a standalone reason to hold a BLOCK.

## False-positive refutations: a refuted 🔴 does not become WOULD_APPROVE

Devin (or any automated reviewer) can raise a plausible 🔴 that source inspection **narrows**. ⚠️ **The slang-rhi#800 example below is NOT a clean refutation — it is the page's cautionary case, corrected twice (2026-08-03) and rewritten in place here.** On slang-rhi#800 Devin flagged an indirect-dispatch residency crash "missing useResource". The Metal two-category taxonomy is correct and still the right first move — a resource passed *directly* to an encoder method (including `dispatchThreadgroups(indirectBuffer,...)`) is auto-resident, `useResource` is needed ONLY for GPU-addresses dereferenced inside argument buffers, and the codebase calls `addUsedResource` only in the arg-buffer-writing path — but the taxonomy was **not sufficient to clear the finding**, so "refuted" overstated it. Correct status of record: **NOT-BLOCK but NOT-CLEARED** ([[approver/challenger-miss-averted] Metal direct-encoder-operand — CORRECTED twice: not a clean refutation, and the residency polarity was inverted](../learnings/1784338866210-approver-challenger-miss-averted-metal-direct-enco.md)). Crucially: a refuted 🔴 does NOT justify BLOCK, but shadow mode never rounds a doc's 🔴 up to WOULD_APPROVE either — so the decision is `ABSTAIN_POLICY:CHALLENGER_CONCERN`. Trace the exact residency/mechanism category before blocking on an automated reviewer's claim — and then check that the mechanism you traced bears on the *path the finding is about*.

`eval-clauses.py` has NO clause for human-review-state, so a standing unresolved maintainer CHANGES_REQUESTED on the current head is invisible to Steps 1–2 — the challenger MUST run `gh pr view --json reviewDecision,reviews`. ## Legitimate within-session flips and converging loops

Not every re-eval is a hold. ## Incremental catches & calibration (2026-07-18/19 approver session)

**A `synchronize` is not automatically a fix — classify the delta before re-litigating.** Three sharpenings of the per-revision discipline: (1) a `synchronize` whose new head is a pure `Merge branch 'master'` changes nothing in the PR's own content — verify the flagged files' git **blob-sha** across the two heads (`gh api contents/<path>?ref=<sha> --jq .sha`) plus `additions/deletions/changedFiles`; identical blob ⇒ any prior finding persists verbatim, re-BLOCK/re-hold without re-deriving ([[approver/calibration] A "synchronize" that is a pure master-merge fixes nothing — verify blob-sha equality before assuming a re-push addressed prior findings](../learnings/1784366423621-approver-calibration-a-synchronize-that-is-a-pure-.md)). (2) For a master-merge on a PR with **hot files**, whole-file blob SHAs will differ because master independently edited those files — the authoritative check is the PR **net-diff hunks** (`gh pr diff`), not the blob; and the operative human signal is the APPROVED review's `commit.oid`, read it (don't infer the association from `submittedAt` vs `committedDate` ordering) ([[approver/challenger] master-merge synchronize: verify fix net-diff byte-identical … check the APPROVED review's commit.oid — slang#12133 R4](../learnings/1784383023678-approver-challenger-master-merge-synchronize-verif.md)). (3) A push that "addresses review" may address a **different axis** than your open gap — re-run the challenger against the SPECIFIC gap that drove the prior withhold (diff the exact code region, check a test now covers YOUR trigger shape, check the maintainer decision you were waiting on actually landed); "new test added" / "comment resolved" is about whatever the reviewer asked, which may be orthogonal ([[approver/calibration] A synchronize addressing a different review axis does not close your open gap](../learnings/1784421277721-approver-calibration-a-synchronize-addressing-a-di.md)). (4) A "Fix …" commit may patch only ONE of N near-duplicate call sites — on slangpy#1075 R7 the exact off-by-one fix (`(i+1) % BATCH_SIZE` + `device->wait()`) landed on `create_textures` while the structurally-identical sibling `create_texture_array` kept BOTH the old form AND no `device->wait()`; the inconsistency is itself a tell that the author knew the fix and didn't propagate it. Never infer "gap fixed" from a commit message or one reviewer no longer flagging it — grep the whole file for the pattern and read EVERY loop body at head, blob-SHA-comparing the reviewed file (`gh api contents/<path>?ref=<sha> --jq .sha`) for material-vs-no-op. Calibration nuance: when a second reviewer (CodeRabbit) later corroborates Devin AND supplies the missing mechanism (per-item `generate_mips()` inside the unwaited batch loop), that falsifies a "maybe it doesn't hit the mechanism" hedge and confirms the gap is real and reachable — but a load/driver-dependent resource-exhaustion RACE that can't be reproduced still stays OPEN_GAP (a hard-fail needs a VERIFIED, ideally reproduced, defect), don't round a firmed-up gap up OR down ([[approver/challenger] Partial-fix revision: one sibling patched, the other left inconsistent — verify EACH call site, don't assume a fix propagated](../learnings/1785490973077-approver-challenger-partial-fix-revision-one-sibli.md)). The mirror on the CI side: a forwarded CI *failure* is stamped with the head it ran against — resolve its `head_sha` (`gh api check-suites/<id> --jq .head_sha`) vs your pinned settled head before treating it as live; on a fast-moving PR the author may have pushed past the failure ([[approver/calibration] forwarded-CI-failure-suite-may-be-at-superseded-head](../learnings/1784416965336-approver-calibration-forwarded-ci-failure-suite-ma.md)). And "head advanced past your verdict" is frequently just **master-catchup** (`behind_by:0`, commits are other already-merged PRs) — diff the delta and confirm the PR's OWN load-bearing files are byte-identical before spending a full re-harvest+re-Devin+CI cycle; a mid-chain design *revert* resets the verdict (evaluate the reverted-to design on its own merits) ([[approver/human-agreement] Full-chain vindication: BLOCK→fix→APPROVE held through merge; and "head advanced" is often just master-catchup](../learnings/1784420055611-approver-human-agreement-full-chain-vindication-bl.md)).

**Regression / self-contradiction BLOCK catches — the strongest 🔴s need no external corroboration.** A failing test the PR *itself adds* (its FileCheck oracle vs its own emitted output) is self-contradicting: either the code is wrong or the spec-of-record is wrong, and it is the strongest possible 🔴 — do NOT downgrade to ABSTAIN just because a relaxed `ci_green_on_sha` clause "passes" (clause-pass governs eligibility; CI red is challenger *evidence*, never laundered by a clause that doesn't require CI) ([[approver/challenger] PR's own new feature test failing at head is a self-contradicting RED_BUG](../learnings/1784431283917-approver-challenger-pr-s-own-new-feature-test-fail.md)). A **pre-existing untouched** test failing at the pinned head is a regression even without a master baseline when three conditions hold — the test predates the PR, the PR doesn't modify it, and the diff touches exactly the path the test exercises ([[approver/calibration] pre-existing-untouched-test-failing-at-head-is-regression-even-without-base-green](../learnings/1784420632496-approver-calibration-pre-existing-untouched-test-f.md)); when you CAN reach master, the airtight three-part proof is untouched-in-diff + present-and-failing-at-master? no + new-symbol-absent-on-master → provably green on master, red at head ([[approver/calibration] pre-existing untouched test regressing (green on master) = confirmed blast radius, not a flake](../learnings/1784431292789-approver-calibration-pre-existing-untouched-test-r.md)). A **tests-only** revision after a BLOCK can turn CI green while leaving a CI-invisible code 🔴 untouched — diff the code-file blobs; if byte-identical the revision did not address the code defect, re-verify the 🔴 stands and don't let now-green CI launder it ([[approver/challenger] tests-only revision can turn CI green without touching the buggy code — diff the code blob, don't trust green](../learnings/1784436534792-approver-challenger-tests-only-revision-can-turn-c.md)). The most dangerous variant: a test WEAKENED to green a *reproduced* failure on the exact code under review. slangpy#1075 finally added the reviewer-requested 33-texture batched-upload regression test that FAILED deterministically on Metal (both Release+Debug, real texel mismatches `-93 == 0`) while Linux/Windows passed; the very next push, titled "Make batched upload regression portable", greened CI by DELETING the mip loop so it compared only mip-0 (the directly-uploaded base data that matched) — the generated mips that actually diverged are no longer asserted. A naive "gap fixed + test added + CI green → approve" is a false-safe: the green was manufactured by narrowing the assertion to exclude exactly the thing that failed, on the path both Devin (🔴) and CodeRabbit (Major) flagged. Whenever a revision adds/edits a test on the reviewed path, diff the test itself (`gh api commits/<sha> --jq '.files[]|select(.filename|test("test"))|.patch'`) and ask: did the assertions get STRONGER (more coverage) or WEAKER (fewer levels/fields)? A `memcmp` narrowed to a subset right after that assertion failed for real is the tell — cross-reference the failing job log at the prior head, and a consistent 2-cell same-platform failure in the PR's OWN new test with real data mismatches is a reproduced regression, not a 1/12 timing flake ([[approver/false-safe] A test weakened to green a REPRODUCED failure on the code under review is a hard no-approve signal — read the test diff, not just the green](../learnings/1785493071728-approver-false-safe-a-test-weakened-to-green-a-rep.md)). Beyond the diff: a narrow-looking change to a **shared per-modifier/per-attribute dispatch arm** has blast radius = union of ALL producers of that modifier, not the syntax in the PR title — grep for every synthetic producer (compiler options like `-no-mangle`, desugaring, parser/checker stamping) before WOULD_APPROVE; a Step-0 recall-predicted-shape match confirms INTENT but says nothing about unintended collateral scope ([[approver/challenger] shared-modifier-lowering-arm-change-has-blast-radius-beyond-explicit-syntax](../learnings/1784420619202-approver-challenger-shared-modifier-lowering-arm-c.md)). A **visibility-*raising*** default change is dangerous exactly where a cap-check would newly fire — grep every reader that *compares* visibilities (`UseOfLessVisibleType`/E30604, ctor-synthesis) because a public struct with a less-visible field type that compiled at 2025 can newly hard-error at 2026; new green tests only cover shapes the author thought of ([[approver/challenger] visibility-elevation feature must probe the UseOfLessVisibleType cap-check](../learnings/1784417628061-approver-challenger-visibility-elevation-feature-m.md)). A **"simplify"/refactor** revision that preserves the headline fix can silently drop a DELIBERATE distinction the removed abstraction encoded — diff the removed type/helper's semantics, not just the target fix (an `OutputDestination{isStdout}`→plain-`String` collapse re-introduced a spurious diagnostic) ([[approver/challenger-miss] a "simplify"/refactor revision can preserve the headline fix while silently regressing a sibling correctness distinction](../learnings/1784381039011-approver-challenger-miss-a-simplify-refactor-revis.md)). And a fix that narrows behavior for a target class can create a **fresh doc 🔴** in the very `@remarks`/comment the PR added earlier — re-scan the revision's full non-code diff for prose still describing the pre-fix behavior; "old 🔴 resolved" and "no new 🔴" are two separate checks ([[approver/challenger] a fix that resolves the flagged bug can introduce a new one in its own doc/comment change](../learnings/1784440929327-approver-challenger-a-fix-that-resolves-the-flagge.md)).

**Devin's structured verdict is the only load-bearing Devin signal — prose and page-counters are not.** Devin's free-text summary can confidently describe features NOT in the diff (it absorbs the PR *description's* over-claims as if verified) — load-bear only on the structured `## Bugs`/`## Flags` counts, spot-check any capability claim against `gh pr diff`, and caveat the doc when prose is refuted ([[approver/challenger] devin-prose-unreliable-trust-only-structured-verdict](../learnings/1784390121609-approver-challenger-devin-prose-unreliable-trust-o.md)). Extend the same distrust to the page's `N Flag` header counter: it can read `1 Flag` while the parsed `## Flags` section says `(none reported)` — the structured section wins (it's what the synthesis parses); reconcile or annotate rather than propagate ([[approver/challenger] Devin page "N Flag" counter can disagree with the structured flags section — trust the structured verdict](../learnings/1784417635185-approver-challenger-devin-page-n-flag-counter-can-.md)).

**Don't take a CI red at face value — resolve what it represents.** `check-ci` is slang's aggregation/gating job (`jq` over the `needs` context, `exit 1` if any dependency ≠ success), so a `check-ci` failure is a downstream reflection of some other leg, never an independent signal — read its log for the named dependency and triage only the real leg; counting it double-counts one failure ([[approver/calibration] check-ci-is-aggregation-gate-not-independent-failure](../learnings/1784420509811-approver-calibration-check-ci-is-aggregation-gate-.md)). And a FileCheck failure whose "expected string" is English prose is usually a **test-authoring artifact**, not a code defect: LLVM FileCheck parses a literal `CHECK:` token *anywhere* on a line including backticked prose comments, registering a phantom directive that fires early and masks the real assertion — the fix is rewording the comment, the code was correct all along ([[approver/calibration] a stray `CHECK:` token inside a prose comment is a test-authoring failure that masquerades as a code defect](../learnings/1784436545771-approver-calibration-a-stray-check-token-inside-a-.md)).

**A behavior-inert build-warning fix clears on the affected green legs.** An "initialize-to-default to silence `-Werror=maybe-uninitialized`" PR looks like it could alter behavior, but when it sits behind a `SLANG_RETURN_ON_FAIL`-style result-returning helper that writes the out-param only on the success path and the caller returns on failure before reading it, the initializer is runtime-inert — the diagnostic is a genuine `-Og` data-flow false-positive across the helper-call boundary. Verify (a) the initializer is a valid existing enum member and (b) the helper's write-gate; then green on the exact affected legs (esp. the one that failed pre-fix) is sufficient challenger evidence, because the only realistic failure is a CI-visible build break, not a silent miscompile. Classify protected paths from the changed-file list, not a misleading branch name ([[approver/calibration] uninit-var -Og -Werror fix behind result-returning helper is behavior-inert](../learnings/1784389774470-approver-calibration-uninit-var-og-werror-fix-behi.md)).

**A recalled fix-shape prediction is the strongest challenger prior — but a checklist to VERIFY, not a substitute.** When Step-0 recall surfaces a prior triage of the SAME issue the PR fixes, the recalled fix prediction becomes a concrete axis-by-axis diff checklist against source at the pinned head — the match (plus clean clauses + head-current Devin + green CI legs) is what justifies WOULD_APPROVE on a thin tier; a DEVIATION from the prediction is exactly the signal recall exists to surface ([[approver/calibration] recall-predicted-fix-shape-verify-diff-matches-prediction](../learnings/1784417192285-approver-calibration-recall-predicted-fix-shape-ve.md)).

## Standing-Bot 🔴 Refutation and Codegen-Fix Verification Without Running the Compiler (2026-07-20 fold)

## Empirical Re-Verification, Design-Scope ABSTAINs, and Merged-Join Corrections (2026-07-22 fold)

**When a `synchronize` touches the exact code your open gap depends on, build and reproduce — don't reason about the new form, and don't relay a peer's "unaffected."** On slang#12151 (public-by-default struct members, #9153) the E30604 `UseOfLessVisibleType` gap was empirically proven at head `044c1e1b09`; the code owner then simplified that very `getDeclVisibility` branch and pushed a new head. ## Merge-Join Calibration: Source-Verify Fixes, Substance-Equivalence, and the Multi-Revision False-Safe Guard (2026-07-23 fold)

Several merge-join calibrations sharpened how a shadow verdict is scored against the human outcome. The dominant rule: **verify a claimed fix in SOURCE at the settled head** — a fixer's later push can resolve a withhold, and a standing bot/Devin flag pointing at the now-fixed lines is REFUTED, not confirmed (the BLOCK→ABSTAIN→WOULD_APPROVE chain on #12125 was normal convergence, decided fresh each revision) ([verify a claimed fix in source at the settled head — a stale flag on fixed lines is refuted](../learnings/1784724233457-approver-challenger-verify-a-claimed-fix-in-source.md)). On merge joins where the merged head ≠ your recorded SHA, prove **substance-equivalence** by checksumming each head's own three-dot PR diff — master-merge commits move the head with zero change to the contribution, so the decision still holds; and `mergedBy ≠ author` + an independent APPROVED review = genuine agreement, not a self-merge ([WOULD_APPROVE vindicated — merged head byte-identical via master-merge syncs](../learnings/1784725443219-approver-human-agreement-would-approve-vindicated-.md)).

Withholds resolved by a human are **agreements, not conservative misses**: an ABSTAIN_POLICY on a standing `CHANGES_REQUESTED` that the maintainer later clears with a fresh APPROVED is the withhold working as designed ([ABSTAIN_POLICY on standing CR → human APPROVED = clean withhold resolution](../learnings/1784732395517-approver-human-agreement-abstain-policy-on-standin.md)), as is an ABSTAIN(OPEN_GAP) on an intended-but-design-undecided behavior that merges at your exact head with a formal Approve ([ABSTAIN(OPEN_GAP) on a maintainer-flagged design fork, then merged with a formal Approve = clean resolution](../learnings/1784756558331-approver-human-agreement-abstain-open-gap-on-a-mai.md)). A `tier_eligible` size-cap ABSTAIN on a large test-only consolidation is the same working-as-designed shape: slangpy#1085 (~3200 test-only lines) was ABSTAIN_POLICY:CLAUSE_FAIL:tier_eligible across R1/R2 and merged at the exact R2 head, the maintainer explicitly merging over known non-blocking nits ("fine for it to go ahead in… probably better just to get it in") — the size-cap abstain is a routing decision ("a human must weigh this"), not a code judgment, and the "enough coverage now vs perfect-but-delayed" call is exactly the trade-off a bot cannot make; record the plain ABSTAIN_POLICY, don't round a clean-looking test diff toward WOULD_APPROVE and don't mislabel it ABSTAIN_INFRA ([[approver/calibration] Large test-only consolidation abstained on size cap → human APPROVE-with-known-nits (cap vindicated)](../learnings/1785514761596-approver-calibration-large-test-only-consolidation.md)). ## Challenger misses of the RELEVANCE class: a true premise that cannot bear on the path in question (2026-08-03 fold)

The 2026-08-03 slang-rhi cluster surfaced a failure family the existing checks are structurally blind to. Every prior challenger discipline on this page interrogates whether a claim is **true** — right file, right line, right commit, claim matches source. These misses were all **true and irrelevant**, and that is worse: a wrong argument gets caught by provenance checking, while a mis-scoped one *passes every check we run*.

**The archetype: read the enclosing guard of every cited line.** On slang-rhi#800 the residency 🔴 was cleared three revisions running on the ground that "EVERY buffer is globally registered via `registerResource` at creation (`metal-buffer.cpp:86`), so it is resident regardless." The finding was about devices **without** a residency set; `registerResource` does all its work inside `if (m_hasResidencySet)` (`metal-device.cpp:611`). So the argument used residency-set-path registration to argue the *fallback* was safe — not a weak argument about the fallback, one that **cannot bear on the fallback at all**. Circular, not merely mis-scoped, and it survived three revisions while being cited as an independent second ground each time, because an argument decorated with real `file:line` reads as mechanism-grounded and a reviewer spot-checking citations confirms them and moves on. The control is two questions, not one — (1) *is it true?* (provenance) and (2) *does it bear on the path in question?* (relevance: name the specific configuration/branch/state the conclusion is about, then check the cited mechanism actually operates in that state). Question 2 is cheap and mechanical for guarded code: `sed -n '<line-20>,<line>p' file.cpp | grep -nE "if \(|else|#if"`; if the guard is `X` and the claim is about `!X`, the citation is inadmissible regardless of correctness. A second-order trap on the way out: a correction that writes "`metal-device.cpp:611-618` adds it to the set" is *true* and **omits the gate**, letting the next reader reconstruct unconditional registration from the correction itself — retract the **mechanism** separately from the **inference**, and state the guard, not just the line range ([[approver/challenger-miss] an argument that cites real file:line but cannot bear on the path — the argument-side twin of the non-discriminating signal](../learnings/1785775240063-approver-challenger-miss-an-argument-that-cites-re.md)).

**"An earlier diagnostic already rejects this" needs the mandatory-path proof, not the diagnostic's existence.** On slang#11118 (`Atomic<T>` as `[__NonCopyableType]` + transitive `typeContainsNonCopyableImpl`) the production bot flagged the new depth cap returning the permissive `false`; the challenger cleared it as pure future-proofing on the theory that the front end rejects anything that deep — an independent critique proved that wrong and the gap became the *principal* ABSTAIN ground. E39997 (`kMaxTypeNestingDepth=128`) is raised by **specific walkers each carrying its own `recursionDepth`** (`slang-check-shader.cpp:604/1307/1509/1645`, `slang-type-layout.cpp:5320`, `slang-check-expr.cpp:2020/2725`, `slang-check-decl.cpp:3173`) — there is no single gate every declaration passes, and E39999 covers inheritance *cycles* only, not a valid deeply-nested acyclic generic struct. Two ordered questions for any diff adding a **bounded** recursive predicate: **which direction does the fallthrough fail** (write out what the cap's return value *means* to every caller — if the permissive value routes to pre-fix behavior, the guard reintroduces the bug at the boundary instead of erroring), and **is the upstream rejection a universal gate or a per-walker counter** (`grep -rn <CAP_CONSTANT> source/` and check whether any site lies on the *mandatory* path to the new code; per-walker `recursionDepth` parameters are the tell). A comment justifying `X` in `if (depth >= CAP) return X;` by asserting which programs are "valid" — here "valid programs have finite-depth struct layouts" — is itself a defect: finite and valid does not imply shallower than a fixed 128 ([[approver/challenger-miss] a depth cap returning the PERMISSIVE value fails OPEN into the very bug the PR fixes; E39997 is not a universal front-end gate](../learnings/1785745165071-approver-challenger-miss-a-depth-recursion-cap-tha.md)).

**A plausible defect found while hunting is the easiest thing to over-credit — run the fix as a counterfactual.** The empty `## Flags` section in a Devin artifact was attributed to `devin-fetch.sh:157` splitting on a real-newline pattern against JSON-quoted `innerText`, and called "confirmed empirically" on the strength of `wc -l` = 1. Decoding first and re-running the *exact* split still yields one part, and `flags?` occurs **zero** times in the scraped page decoded or not — a decode cannot conjure a marker never captured. Actual cause: the done-poll was satisfied *solely* by the `Checks\s*\d+/\d+` CI counter, so the script scraped a page whose Flags panel had not rendered; the flags-toggle click found no matching button and silently no-oped under `|| true`. The missing decode is a **real but latent second bug**, and collapsing two independent defects into one causal story is the error. Before attributing a missing extraction to a *parser*, prove the input contained the thing to extract (`grep -ociE 'flags?' devin-page.txt` → 0 ⇒ capture problem, NOT parse problem), then run the fix as a counterfactual and confirm it changes the outcome ([[approver/challenger-miss] I mis-attributed the empty-Flags defect to the missing json.loads — the real cause is scraping before the panel renders](../learnings/1785787630832-approver-challenger-miss-i-mis-attributed-the-empt.md)). The underlying tool defect stands on its own and is a **review-input integrity** issue, not a nit: `devin-fetch.sh` exited 0 with an empty flags section on slangpy#1090 while Devin had produced **2 Investigate flags** — one of two review sources silently zeroed. Treat "Devin exit 0 + zero flags" as **suspicious, never clean**: a genuinely clean run still renders a `No flags`/`0 Flags` token, so an *absent* flags summary means the scrape was early. Cheap assertion — no `\d+ Flags?`, no `No flags`, no `Analysis complete` ⇒ INCONCLUSIVE (ABSTAIN_INFRA), and auth-gated per-flag detail bodies ("115 lines left") are real signals whose rationale is unavailable: probe each yourself, never record them as cleared ([[approver/challenger] devin-fetch.sh false-clean: a `Checks N/M` readiness branch plus JSON-quoted innerText](../learnings/1785786175123-approver-challenger-devin-fetch-sh-false-clean-che.md)).

**"Pending at poll end" is "not proven yet", never "absent."** Two approver rows recorded `0/0/0` with docs affirmatively stating no CodeRabbit signal existed — and in both the review had landed *before the doc was written* (slangpy#1085: last poll 15:03:39 exit 22 pending, review 15:04:52, doc 15:06:22, with 4 🟠 Major findings sitting on `pulls/N/comments`; slangpy#1063: harvest exit **20** = "genuine skip, none pending", review 9 minutes later). Exit 22 correctly said "pending, review imminent" and the *last* iteration's result was then treated as durable through the following 2m43s; exit 20 is worse because there is no imminence signal at all — `PENDING_STATUS_RE` matches a *pending commit status*, so a bot that hasn't posted its status yet, or posts green without a review object, fires exit 20 and looks authoritative. The two failure modes multiply: because both docs concluded "no review at all", nothing prompted the manual `pulls/N/comments` read that saved every other affected row. Rules: **re-probe X immediately before committing any artifact whose content depends on "X was not available"**; `status green ≠ harvestable review` and no-status-yet ≠ no-review-coming; and phrase every negative finding with its observation time — "CodeRabbit status was pending as of 15:03:39" is auditable, "there is no CodeRabbit signal" is a different, stronger, and here false claim ([[approver/challenger-miss] a poll that ends "pending" means "not proven yet", not "does not exist"](../learnings/1785779216968-approver-challenger-miss-a-poll-that-ends-pending-.md)). The same discipline applies to the reporting side: report the **LAST** occurrence plus the size of the clean run after it, never the first — "first seen 06-24" and "last seen 07-19, then 557 clean files" support opposite decisions from the same data — and remember that a silence in **commentary** is not a silence in the **phenomenon** (log mentions measure who complained, not what occurred) ([[approver/calibration] report the LAST occurrence plus the clean run after it; a silence in commentary is not a silence in the phenomenon](../learnings/1785822559259-approver-calibration-report-the-last-occurrence-pl.md)).

## The strongest anti-round-up datapoint: source-verified-correct code that FAILED once the backend actually ran

slang-rhi#802 (Metal bindless `DescriptorHandle`) is the series' decisive case *for* execution-coverage holds. It was held at ABSTAIN_POLICY/`OPEN_GAP` on a **pure coverage basis** — implementation source-verified correct and matching the slang#10842 fix-shape spec exactly, but its two new Metal cases SKIPPED on macOS CI, so zero execution coverage. That reads like pedantry when the source review is clean, and a plausible reviewer rounds it up. Then slang-rhi#807 fixed Metal device init, Metal began genuinely executing, and #802's next run turned red **on exactly the two cases held on** (17 + 60 assertion failures). Every mechanism was individually right — raw `getDeviceAddress()+offset`, `gpuResourceID()._impl`, the `static_assert` on `sizeof(MTL::ResourceID)`, the combined tex+sampler exclusion — and the composition still produced wrong data: **no amount of reading would have found this; only running it did.** Attribution was made airtight by counting `.metal` result rows on both branches (main post-#807: 205 rows, `bindless-*.metal` absent entirely; #802 branch: 207, both present and FAILING) — a delta of exactly 2 = the cases #802 registers, so the regression is introduced, not inherited. Two reusable discriminators: **Debug vs Release byte-identical as an ordered tuple** ⇒ deterministic logic/codegen bug, not UB and not a race; and **check the skip *reasons*, not the skip count** — none of the 76 remaining `.metal` skips was `device not available` (ray tracing 59, timestamp 12, combined tex-sampler 2), which is how you tell "feature-gated, fine" from "silently not running at all" ([[approver/calibration] slang-rhi#802 — a source-verified-CORRECT implementation still FAILED once Metal executed: exec-coverage holds are not pedantry](../learnings/1785766869937-approver-calibration-slang-rhi-802-a-source-verifi.md)).

**The mask-fix mirror: registration is not execution.** The #1090 report claimed a previously-identified coverage gap was "fixed upstream" citing the slang-rhi mask at the pinned submodule commit — the orchestrator re-derived it and the claim did not survive. Two propositions got conflated: *registered to run on Metal* (`GPU_TEST_CASE("buffer-from-handle", D3D12 | Vulkan | Metal)` at `11eefdc6` — true) and *actually executes on Metal in CI* (requires a runner with a real Metal GPU; `ci.yml:48-49` runs macos-aarch64 on `runs-on: macos-latest`). Direction of the error matters: a mask reads as *reassuring*, so this mode converts a live gap into a dismissed one — exactly the shape that turns an abstain into a false approve. State coverage claims at the strength actually established and label the residual in those words: "registered for Metal at `<sha>`; execution unconfirmed — no rhi CI log opened." **Never let a mask fix retire a coverage gap on its own** ([[approver/challenger-miss] test-mask registration is not test execution — resolve the job → `runs-on` → hardware, and prefer a run log over inference](../learnings/1785787084796-approver-challenger-miss-test-mask-registration-is.md)).

**Conversely, an execution-coverage gap IS closable — and closure is proven by the job LOG plus a per-backend tally delta, never by a green job.** `slang-rhi-tests` prints one row per (test, backend) and a fully-skipped backend still yields `Status: SUCCESS!`, so job conclusion carries no backend information in *either* direction. The five-step closing checklist, all cheap: (1) **pin log provenance** — grep `HEAD is now at`, confirm it names your pinned head; (2) **confirm the device initialized** — `Metal: supported` plus the `Features:`/`Capabilities:` block (a `Apple Paravirtual device` adapter is *fine*; paravirtual ≠ unsupported); (3) **grep the specific case names with the backend suffix** and require `PASSED`, never the aggregate; (4) **tally delta against the baseline branch** — Metal 129 PASSED/76 SKIPPED on main → 132/76 at head = exactly +3, matching the three newly-unmasked cases, which is the check that catches "enabled but silently still skipping" (a mask edit that didn't take shows +0); (5) **two legs independently** — Debug and Release each ran all three. Then ask whether the now-executing assertions are **load-bearing**, and say which case carries the weight: here `compareComputeResult` against GPU-written `{16,32,32,64}`/`{48}` on zero-initialized buffers does, while the `-zero` case expecting `{0}` from a zero-initialized buffer would also pass if the dispatch did nothing. A corollary on stale bot findings from the same PR: Devin's 🔴 "left untested" was refuted *by the commit under decision*, and the tell was in its own page text — a card-header diffstat of `2 files +8 −5` (the R1/R2 shape) against the PR's `3 files +11 −8`, plus a literal `Loading diffs…`. **Reconcile a bot's rendered diffstat against the pinned head's before honoring its findings**, and cross-check with a source that names its range explicitly (CodeRabbit stated `94a90b2a…bf135d7222a8`) ([[approver/calibration] slang-rhi#800 — an execution-coverage OPEN_GAP is CLOSABLE; the job log plus a per-backend tally delta is the proof](../learnings/1785770830139-approver-calibration-slang-rhi-800-an-execution-co.md)).

**But closing your prior gap does not mean the PR is covered — re-derive the gap against *this* revision's own new code.** slang-rhi#801 R1 abstained on a Metal-only import API masked to `D3D12|Vulkan`; R2 flipped the mask to include Metal **and rewrote the implementation** as an intrusive linked list. The mask edit genuinely worked (`buffer-from-handle.metal` PASSED both legs, tally 132→133, load-bearing content assertions) — and the now-passing test exercises the import path while provably never touching the new list. Do NOT diff your old withhold reason against the new evidence and stop: ask "which lines are new *here*, and what executes them?", tracing from the newly-changed lines FORWARD to an executing test rather than from the test backward to a green checkmark. A green test proves the path it covers, never the path a same-revision rewrite introduced. Corroboration worth trusting: CodeRabbit independently flagged the identical gap at the same head ("a regression in `insert` or `erase` for duplicate base addresses would still pass") — two reviewers converging from different directions on one uncovered surface is strong evidence the gap is real and not approver over-caution. Record the old gap explicitly CLOSED and the new one re-scoped, so the ledger shows progress rather than a repeated withhold ([[approver/calibration] closing a coverage gap can UNCOVER a new one — re-scope the gap to the revision's own new code](../learnings/1785776756858-approver-calibration-closing-a-coverage-gap-can-un.md)).

**A skip-based harness turns a removed assertion into a SILENT-GREEN regression, not a nit.** slang-rhi#807 (`Temporarily disable metallib_4_0 capability`) walked its only assertion about the disabled capability from `CHECK(hasCapability(metallib_4_0) == (macOSMajorVersion >= 26))` at base → `CHECK_FALSE(...)` at R1 (load-bearing) → **commented out entirely** at R2. Reading a commented-out line in a 2-file `+8/-3` maintainer mitigation as a cosmetic nit is wrong, because in a harness that converts *capability-probe failure* into *test skip* the guarded regression is invisible in CI: the availability probe compiles a trivial compute shader, failure → `RETURN_NOT_AVAILABLE` (`tests/testing.cpp:1002`) — the exact failure the upstream bug (slang#12325) produces — the device is marked unavailable, every Metal `GPU_TEST_CASE` resolves `SKIP("device not available")` (`:1124`), and the silent-skip guard **exempts** device types that were never available (`:1234-1240`). So re-enabling the capability while the bug is unfixed presents as green CI with zero Metal coverage, never a failure. Whenever a diff deletes or comments out an assertion, don't grade it on diff size or on the "temporary/maintainer/tracked" framing — ask **"if the condition this asserted regressed, what would CI do?"**, and note that guards which skip "unavailable" devices are structurally blind to bugs that *cause* unavailability (guard and bug share a trigger, so the guard can never fire on it). Severity stays LOW when the loss is confined to the workaround's self-pinning, but LOW ≠ clears the gap bar: the trigger is not unreachable when the TODO explicitly anticipates the re-enable ([[approver/challenger] a skip-based test harness makes a removed assertion a SILENT-GREEN regression](../learnings/1785764961019-approver-challenger-a-skip-based-test-harness-make.md)).

**The wrapper/import-API class, generalized.** For a thin binding exposing an externally-allocated GPU resource (slangpy#1090 `Device::create_buffer_from_native_handle`), two probes decide it. **(1) Validation lives in the backend, not the wrapper — go read it.** Devin's "no size validation against the native allocation" is true at the slangpy layer and **wrong as a finding**: slang-rhi's Metal backend checks handle type, null value, device match, *and* `desc.size > nativeBuffer->length()`, returning `SLANG_E_INVALID_ARG` which `SLANG_RHI_CALL` raises as a Python exception. A finding about a missing check is only real once you have read the layer that would perform it — and validation is often **uneven across backends** (Metal validated size; Vulkan and D3D12 type-checked only, so an oversized `desc` is accepted and can cause OOB access): enumerate every backend plus the base-class default. **(2) "CI green" on a wrapper PR usually means *compiles*, not *runs*** — the decisive gap was that the new path executed in **no test at any layer**, so check all three of (does this PR add a test / does one already exist / does any CI job execute the path on the target backend); green + zero executing tests on a path whose failure mode is memory corruption is an OPEN_GAP. Two cheap clears worth knowing: on a refactor-plus-feature diff, byte-diff the extracted helper against the original body before treating anything in it as new (that made CodeRabbit's 🟡 *pre-existing*), and "no lifetime tie to the native allocation" is the **design** of an import API when documented, not a defect — but confirm the retain/release side and that guards are `SGL_CHECK` (throws in release) not `SGL_ASSERT` (compiles to `{}`). And Step-0 recall is a **lead, not a verdict**: the recalled #801 mask gap read as re-reportable, the mask had since been widened — a recalled learning describes the revision it was written against, so re-verify its predicate at the pinned commit before it moves a decision ([[approver/challenger] native-handle import APIs — probe the backend layer, and check the path actually executes](../learnings/1785786230423-approver-challenger-native-handle-import-apis-prob.md)).

## Failure-signature discipline: parse the whole set, then change level of evidence

slang-rhi#802's red CI produced **three successive wrong characterizations from three reviewers**, and the progression is the lesson. Reviewer A, primed by a non-residency hypothesis (which predicts uniform garbage): "the buffers read **all zeros**." Reviewer B (the approver), primed by handle/slot plumbing (which predicts a coherent shift): "`result[i] == i` where `expected == i+1` — a neat off-by-one indexing shift." The truth across all 77 assertions is a **mixture** — 56 zero / 21 shifted, cross-tabbing 10/7 on `bindless-buffers.metal` and 46/14 on `bindless-textures.metal` — and the `result[i] == i` claim is not merely imprecise but **falsified**: at `logged: i := 0` the actual is `0.0`, `1.0`, `3.0` *and* `5.0`, so the value is not a function of `i` at all. Each reviewer read the head of a long list and pattern-matched it to the hypothesis they walked in with; the head happens to be all zeros, which is why one "confirmed" uniform zeros and the other latched onto the first shifted rows further down. The mechanical enabler: a 77-row failure list is long enough that nobody reads all of it by default, and short enough that it feels like you did. **Never characterize a multi-failure signature from a sample** — parse every row with a script, assert the row count matches the reported total, bucket, and cross-tab per test case before naming anything; and **test the functional claim you are about to make** (before writing "`result[i] == i`", group by `i` and check for a unique actual per `i` — multiple distinct actuals at one `i` kills it). Compare Debug vs Release as **ordered tuples**, not counts: equal counts prove little, a byte-identical ordered 77-tuple is what licenses "deterministic, not UB/race." A wrong signature steers the fixer at the wrong subsystem, so this is not bookkeeping ([[approver/challenger-miss] parse the WHOLE failure set before naming a signature — two reviewers read the same 77 assertions and each found the hypothesis they brought](../learnings/1785767276013-approver-challenger-miss-parse-the-whole-failure-s.md)).

The third characterization is the instructive one because it had **complete, correct observational data and still reached a false conclusion**: "the distribution is a mixture, therefore no single cause can explain it." One mechanism explains both classes — and it was not in the output at all. On Metal a top-level `uniform ....Handle` is emitted as an ordinary directly-bound parameter with its own `[[buffer(n)]]`/`[[texture(n)]]` slot (a deliberate upstream unwrap, `slang-emit-metal.cpp:148-152` at `v2026.12.2`, with a #11066 regression test *requiring* it), so values written via `setDescriptorHandle` are never read — the handles are **never bound at all**. Group rows by **assertion phase** and that single cause predicts the whole mixture: phase-1 reads → `0` (nothing bound); phase-2 read-backs → each RW resource's *unmodified seed* (writes never landed), e.g. `rwTexture1DArray L1` seeds `{3,4}`, observed `3,4`, expected `4,5`, which is why every shifted row is uniformly `diff == 1.00`. Two phases, one mechanism. **Every wrong reading came from interrogating the OUTPUT; the answer was in the INPUT CONTRACT** — and refining the observation *feels* like progress, each stop producing a more precise wrong answer than the last. Escalation rule, in order: group failures by assertion phase/target before inferring anything ("is this assertion observing a fresh read, or a read-back of something a prior step should have written?"); read the **test source**, not just its output; read the **actual interface the code receives** (for a shader, the emitted target source and its parameter list — `slangc test.slang -target metal -entry computeMain -stage compute`, cheap, no GPU, decisive here); only then name a signature or a cause. Corollary: **a heterogeneous signature does NOT imply a heterogeneous cause** — prefer the single-mechanism explanation until excluded, and exclude it by checking observation points, not by eyeballing the distribution's shape ([[approver/challenger] when a failure signature resists explanation, stop refining the observation and read the INPUT CONTRACT](../learnings/1785767986973-approver-challenger-when-a-failure-signature-resis.md)).

## Human-agreement joins: an approval is evidence about what the approver EXAMINED

Four joins from the same window sharpen the scoring rule that a human APPROVE is never a general safety certificate.

- **Compare `submitted_at` before crediting an approval with a finding.** On slang-rhi#807 `ccummingsNV` APPROVED the pinned head at `13:29:00Z` and CodeRabbit posted the actionable comment at `13:29:19Z` — **the approval predates the finding by 19 seconds**, a sequence invisible in GitHub's UI, which renders both as "on this commit" with no ordering cue. Two earlier reviews were `DISMISSED` against the prior head and carry no weight either. Never infer "a human considered finding X" from "a human approved": same-SHA is necessary and nowhere near sufficient, and sub-minute ordering is common when a bot re-reviews on a fresh push. Score the join against **byte content**, not line totals — the squash's `+8/-3` matched the recorded diff, but sha256-ing both changed files at the decided head vs the merge commit is what converted "probably the same" into a fact (`compare` alone showed `ahead_by 1 / behind_by 2`, which would not have proven identity). When `pulls/<n>/reviews` is hook-blocked, `issues/<n>/timeline` carries the same rows with `state` + `submitted_at` + `commit_id`. Recorded `human_verdict=APPROVED`: **conservative agreement, not a false-safe** — and the severity premise once filed as *unresolvable* (runner macOS version) was later resolved from the public job log (`Image: macos-26-arm64`), proving the deleted `CHECK_FALSE` was load-bearing, so the hold was substantively right and is now evidenced rather than lucky ([[approver/human-agreement] slang-rhi#807 — a fresh independent APPROVE that predated the finding by 19s; ABSTAIN scored as conservative agreement](../learnings/1785766473587-approver-human-agreement-slang-rhi-807-maintainer-.md)).
- **"The push satisfies the ask" is the maintainer's call, not the approver's.** slang-rhi#800 R3 was technically clean on every axis — 6/6 clauses, CodeRabbit clean on the incremental push, both Devin 🔴 resolved, and the zero-execution-coverage gap genuinely closed — leaving only `reviewDecision=CHANGES_REQUESTED` / `mergeStateStatus=BLOCKED` from skallweitNV's undismissed review. The dispatching orchestrator explicitly framed that review as *"likely stale-but-unwithdrawn — factor it as a **satisfied** request pending re-review"*, and the mapping ask→commit really was one-to-one. Held at ABSTAIN_POLICY(CHALLENGER_CONCERN) narrowed to the standing CR alone at 15:26:00Z; skallweitNV APPROVED the exact head at 15:26:51Z and merged 7s later at the decision SHA with zero intervening commits — the withhold resolving in **51 seconds**, exactly as designed (second independent instance of this arc after slang#11136). Only the author of a blocking review can clear it; inferring satisfaction substitutes your reading of a maintainer's intent for the maintainer's. Two sharpenings: a cleanly-satisfied ask **predicts a fast resolution** and calls for a *narrow* withhold — state plainly that the substance is clean and the sole blocker is review state, and do not pad it with re-litigated technical doubts to justify it; and **a tasking message's framing is recorded, never decisive** — record that you were asked, state you didn't adopt it, and why (the invariant's whole purpose is to not depend on whose judgement is being deferred to). Read the **live aggregate** `reviewDecision` via GraphQL, since the individual CR carries an old commit oid and looks stale while the aggregate correctly still reads `CHANGES_REQUESTED` at the new head ([[approver/human-agreement] second confirmation — holding at ABSTAIN over a standing undismissed CHANGES_REQUESTED resolved as clean agreement](../learnings/1785771033293-approver-human-agreement-second-confirmation-holdi.md)).
- **A merge landing mid-decision must not retro-fit the verdict — decide first, join second.** slang-rhi#801 merged while the decision for its head was still being derived: the reviewer holding the standing CR APPROVED the exact head and merged 8s later, arriving as a `pr_merged` webhook mid-investigation. Two anchoring hazards fire at once — the CR that would have capped at ABSTAIN evaporates, and knowing a domain expert approved makes WOULD_APPROVE feel safe. But the approval and the decision answer different questions: skallweitNV's objection was a *performance* ask ("lots of heap allocations where previously there were none") which the revision discharged, saying nothing about the execution-coverage gap on the rewritten data structure, which no human examined. Reach the decision on your own evidence, write it down, THEN weigh the merge as a join, and note the timestamp ordering in the challenger field so a later auditor can see it wasn't back-fitted. Compare the **content** of the human's objection to the dimension you're withholding on: if they differ, the approval doesn't touch your basis — a withhold more conservative than a human who examined a *different axis* is **policy-consistent withholding**, neither a false-safe nor clean agreement. Record per-commit, never roll up (R1 joined CHANGES_REQUESTED, R2 joined APPROVED, same PR). Bonus: the "branch protection is unverifiable, 403" caveat handed down was FALSE — `/branches/main/protection` 403s for an integration token while `/branches/main` returns the protection summary unauthenticated; **never inherit a caveat without trying a second access path** ([[approver/human-agreement] a merge landing mid-decision must not retro-fit the verdict](../learnings/1785776775891-approver-human-agreement-a-merge-landing-mid-decis.md)).
- **Deletion of flagged code before it earns an approval is a vindication signal, not a neutral head move.** On slang#11667 the ABSTAIN(OPEN_GAP) at `ad924934` flagged `findTargetOptionalType` (`slang-ir-lower-optional-type.cpp:185`) as a null-deref risk; maintainer `saipraveenb25` objected to the *same function* and overruled the whole approach — *"the fixes in the PR are compensating for an earlier regression in `isConcreteType()`, rather than fixing the producer of the bad type-flow information"* — and as merged, `isConcreteType` returns `true` for `IRStructType` unconditionally while the entire recovery helper and its `if (!info)` branch were **DELETED** (the file does not appear in the merged squash diff at all). The transferable rule: a helper whose job is to *recover information that should already have been present* — walking phi/branch args, users, substitution or witness chains to reconstruct a type, a generic argument, or a parent decl — is not primarily a null-safety risk, it is **evidence that an upstream producer emitted a malformed shape**, and the review question is "why does this input shape exist?" not "does this helper handle every case?". Both readings flag the same line, but the producer reading predicts what maintainers do: delete the helper, fix the producer. So when a diff adds a recovery/fallback on a *consumer* path (lowering, emit, legalization) guarded by `if (!x)` after a normal lookup returned nothing, name the producer and check whether it recently changed (`git log -S<producerFn>`), and treat "the producing pass regressed" as the leading hypothesis — that upgrades a coverage gap into a design objection. slang's own CLAUDE.md names this smell ("Context rediscovery by graph walking", "Consumer-side patching"), so on this repo **the methodology doc IS a calibration oracle**. Two joins now share the shape (slang#12095, slang#11667): head moved, flagged code DELETED rather than fixed, nobody had approved the pinned commit ⇒ the pinned row scores **CHANGES_REQUESTED**, not APPROVED-because-merged ([[approver/human-agreement] a consumer-side recovery helper is a producer-bug flag — vindicated on slang#11667](../learnings/1785782767710-approver-human-agreement-a-consumer-side-recovery-.md)).

**Scope-class predicates are about the REPO, not the diff's shape.** slang-rhi#806 (one-line README license correction "MIT" → "Apache 2.0 with LLVM Exception", bot-authored, harvest exit 20, all 6 clauses PASS) was byte-for-byte the shape that previously fired `ABSTAIN_POLICY:OUT_OF_SCOPE:<docs-class>` on nanoclaw#1007, website #204/#207/#208/#209 and neural-shading#15 — and reading the precedent *atoms* instead of the index summary showed every one of those fired on **repo-class** (non-compiler repo) or **conflict of interest**, never on "the diff happens to be docs." `shader-slang/slang-rhi` is in-domain across ~8 prior rows, and in-domain docs-shaped PRs were decided on merits in both directions (#12082 README glossary → WOULD_APPROVE; #12090 README inconsistency → ABSTAIN on a merits OPEN_GAP), so a docs-class abstain here would have invented a predicate precedent contradicts. Ask **"which feature actually fired in the precedent — repo identity, or diff content?"** and grep the precedent atoms for the *predicate*, not the outcome. What made WOULD_APPROVE legitimate rather than a round-up on "one docs line + a maintainer approved it": a license statement is a *checkable factual assertion*, so two independent authoritative sources were checked (`LICENSE:1` SPDX id and `.reuse/dep5` blanket `Files: *`), the **fix DIRECTION** was verified (`commits?path=LICENSE` showed exactly 2 commits, initial MIT → #111 Apache 2024-11-21, proving README was the stale artifact — correcting docs→LICENSE is the right layer, while reverting a shipped relicense would be a maintainer/legal call), the **whole file** was read rather than the diff (the #12090 failure mode: an untouched line elsewhere contradicting the edit), and a tree-grep with a live control probed *manifests* separately since a prose grep for "MIT license" misses `"license": "MIT"`. Join: merged at the exact head, skallweitNV (MEMBER, non-self vs the bot author) APPROVED with `commit_id == head`. Keep the OUT_OF_SCOPE families repo/COI-scoped (`website-content`, `course-materials-docs`, `approver-harness`, `nanoclaw-changelog-docs`) and do **not** add a bare "docs" family ([[approver/human-agreement] in-domain docs PR decides on MERITS — OUT_OF_SCOPE is a REPO-class predicate, not a "diff is docs" predicate](../learnings/1785784245128-approver-human-agreement-in-domain-docs-pr-decides.md)).

**"N sources agree" is a claim about PROVENANCE, not count.** The #806 phrase "two independent authoritative sources" was right in verdict and wrong in the word doing the work: `bc7657abfac8` (#111) wrote **both files in one commit**. It slipped past a challenger stage built to catch over-claims precisely because *checking a second source is the good habit* — it felt rigorous and produced two green results. **Independence is a property of the sources' causal history, not of their being two files**, and the catching check is one call (`commits?path=<B>` → length + oldest SHA) that was run on `LICENSE` and never on `dep5` — the asymmetry is the tell. Generalize past licenses by asking *what single event could make both wrong at once*: two files written by one commit; a claim in code and the same claim in its comment; a bot review and the PR body it summarized; two CI legs sharing a runner image, toolchain or cached artifact; a test asserting behavior the same commit implemented. **State the shared-failure event you ruled out, not the number of sources.** And on being caught, **re-describe rather than discard** — the live question was never "is Apache the correct value" but "was the relicense deliberate?", and shared origin in a commit whose whole purpose was REUSE compliance is *direct evidence of intent* and shows the change was repo-wide with README:14 the lone dissenter: weak for value-corroboration, strong for intent-and-scope, so the corrected framing was **stronger** than the retracted one. A refuted premise is not a refuted conclusion ([[approver/challenger-miss] "N sources agree" is a claim about provenance, not count — and the retraction must reach the recorded ledger field](../learnings/1785785616042-approver-challenger-miss-n-sources-agree-is-a-clai.md)).

## Retraction hygiene: a correction filed as a new atom does not disarm the stale one

The 08-03 slang-rhi sweep is this page's own worst case, and it generalizes into the strongest rule on the page. Three independent surfaces (the approver's #800 and #801 rows, the orchestrator's project notes, this concept page) each carried the residency-polarity error; each got a **new** correction atom; and the stale wording kept being read, because a correction filed alongside the error does not remove it from where readers land. What actually disarms it: **name the file and quote the superseded sentence verbatim**, then sweep for the *superseded* phrasing — grepping your fix cannot match the stale text it replaced. The sweep order that catches everything: headings → title/frontmatter → tables → index rows → prose → **serialized payloads** (`*.json`), and specifically the `challenger` field of an already-recorded `approval_decisions` row: prose artifacts are working notes, **the ledger row is the audit artifact of record**, and `record_decision` is idempotent per `(repo, pr, commit_sha)` so re-recording corrects in place rather than appending — there is no excuse for leaving it stale. Watch for surfaces a linter or concurrent process copied your text into (a mid-session restructure duplicated one index bullet into an archive file, and the stale copy survived two rounds of correcting the "original"), and re-run the critique stage afterward since post-approve edits invalidate the attestation hashes ([[approver/challenger-miss] the retraction's blast radius includes the RECORDED LEDGER ROW](../learnings/1785785616042-approver-challenger-miss-n-sources-agree-is-a-clai.md)).

Two supporting facts about *why* the error persisted through two retractions. First, **the failure was recall, not evidence-gathering**: two agents made the same error on the same fact in the same week while each already held a note recording it correctly — the approver's own `pr-802` row carried, marked `FACT`, the verbatim `GPUFamilyApple6 not supported; using per-encoder useResource fallback` line and the conclusion that CI exercises the fallback. Neither grepped. So **before asserting any environment/coverage premise, grep your own store for the distinguishing token** (here `Apple6`) — a premise about a *stable property of the CI environment* is exactly the kind of fact you have probably already established and forgotten, and it is cheaper than any log fetch. **Cross-check sibling rows in the same subsystem before filing**: two adjacent rows asserted **opposite defaults for the same flag**, and a 30-second grep would have surfaced the contradiction long before the human join did. Second, **label the evidence class whenever a citation becomes load-bearing for more than one chain** — calling job `91655709489` "the one job where the device check failed" conflated job-level failure with device-check failure (the job's conclusion was `success`) and a same-run observation with a cross-job environment inference (the line came from a different commit's log). The inference remains valid — same job name/label/adapter, and `GPUFamilyApple6` is a driver property of the adapter, independent of whether any shader compiled — but it must be **labelled** as an environment inference, or the next reader upgrades it to a direct observation for free ([[approver/challenger-miss] narrowing a claim is not testing its premise — and the correct fact was already in my own store (recall failure, not evidence failure)](../learnings/1785778812255-approver-challenger-miss-narrowing-a-claim-is-not-.md)).

And the mirror-image calibration that the whole episode teaches: **a caveat can be wrong in the direction of EXCESS caution, and that is still an error.** Most atoms on this page warn against rounding *up*; this is the other failure. Two rows recorded a configuration as "merged unverified" when CI had been running that exact configuration by default the whole time. Withholding on a question the evidence already answered is not free — it burns maintainer trust and, worse, **points attention at the wrong risk.** So run the mirror check on every caveat, not just every approval: *"what would I have to observe for this caveat to be UNNECESSARY — and have I looked for it?"* The standing rule of one adversarial retry before writing "could not determine" extends to retrying against the possibility that **the answer is favorable to the PR**. A config you call "unverified" deserves one direct check of what CI actually does by default — "needs a special env var to exercise" is a claim about CI's default, and CI defaults are cheap to read and frequently counter-intuitive (here "modern Apple Silicon ⇒ modern path" is exactly backwards on a Paravirtual device). And **when a green run cannot show you a diagnostic, look for the failing SIBLING job** rather than concluding the fact is unobtainable: same image, same adapter, different outcome — `Debug callback output` measured 0 in four green logs and **3** in the one job where the Metal device check failed. One failing sibling settled a question twice declared unsettleable. Check the *assignment* site, not just the print site, to know which runs can carry the value at all ([[approver/calibration] a caveat can be wrong toward EXCESS caution — the sibling-job trick](../learnings/1785778241162-approver-calibration-a-caveat-can-be-wrong-in-the-.md), [[approver/challenger-miss] a diagnostic captured ONLY on the failure path cannot be read from a green log](../learnings/1785778085689-approver-challenger-miss-a-diagnostic-captured-onl.md)). The generalized precondition, worth memorizing: **before inferring a runtime configuration from a missing log line, prove the line would be (a) generated, (b) captured, and (c) printed at that verbosity.** On slang-rhi that decomposes into two independent suppressors, either alone sufficient — `checkDeviceTypeAvailable` assigns `result.debugCallbackOutput` only inside `RETURN_NOT_AVAILABLE` (`tests/testing.cpp:884`) while the reporter's `printf` is unconditional (an unconditional print does not imply an unconditional value), and `Info`-severity messages route to doctest `INFO()`, flushed only on failure or `-v`. One more scoping rule from the same correction: **before calling a code path zero-coverage, grep for PRE-EXISTING tests that reach it** — coverage is a property of the test suite, not of the diff (seven `bind-pointers-*.metal` cases already exercised the path, one of them existing *specifically* to force the non-base-address resolve).
