# PR-Approver: Challenger CI-Gate, Verdict Calibration & Human Agreement

Once the deterministic clauses ([[wiki/concepts/review-approver-decision-procedure.md]]) pass and the review-doc verdict is parsed, Step 3 — the **adversarial challenger** — is where WOULD_APPROVE / ABSTAIN_POLICY(OPEN_GAP) / BLOCK are actually distinguished. The recurring theme: **the automated reviewers (production `github-actions[bot]`, CodeRabbit, Devin) do not build or run the test suites**, so a green review-doc verdict is blind to codegen-golden regressions, downstream-submodule breaks, and reachable release-asserts. The challenger's job is to pull the live CI check-runs, trace each red to cause, and read the source at the pinned head. This page collects the verified-BLOCK catches, the middle-rung ABSTAIN discriminators, the false-positive refutations, and the human-agreement calibration that validates the whole bar.

## The core CI-gate class: a green review-doc is blind to test regressions

A repeating BLOCK class — vindicated across #11595, #12130, #12106-R1, #12141 — is a **verified, deterministic, PR-caused break of a pre-existing CI-gated test** that the review-doc rated only nits. The challenger must harvest **check-runs at head** (not the combined-status glance) and read the failing job's failing STEP. Concrete instances:

- **Downstream submodule shaders test-slang never compiles.** slang#12141 disabled the `vector<T,4>` `(vec2,T)`/`(T,vec2)` initializers via `static_assert(false)`; the primary review was 🟡 APPROVE_WITH_NITS and Devin clean, all `test-slang` legs green — but the bundled `external/slang-rhi` submodule ships `test-ray-tracing-clusters.slang` with `float4(attribs.barycentrics, 1.f)` (a `float4(float2, scalar)`), which now hits the new E41400. Only `test-slang-rhi` compiles it, and it was RED. Any change to `core.meta.slang`/`hlsl.meta.slang` that *narrows what compiles* must be assumed to break downstream code until CI proves otherwise ([[approver/challenger-miss-averted] disabling a core-module init overload breaks bundled slang-rhi submodule shaders that test-slang never compiles](../learnings/1784270927259-approver-challenger-miss-averted-disabling-a-core-.md)).
- **Diagnostic-forwarding surfaces previously-swallowed warnings.** slang#12141 R2's `forwardDiagnostics()` on the constructor SUCCESS path re-emitted a long-standing `warning[E30081]` that broke pre-existing `tests/glsl/integer_pack.slang (vk)` — blast radius = *every input that already triggered that swallowed diagnostic*, living in tests that assert empty stderr. Critical calibration: a `.slang (vk)` test shows `conclusion=success` on a GPU-less runner because it is **`ignored`/skipped, not passed** — only a completed leg WITH the GPU counts ([[approver/challenger-miss-averted] a diagnostic-forwarding refactor that surfaces previously-swallowed warnings can break pre-existing empty-stderr tests](../learnings/1784304367382-approver-challenger-miss-averted-a-diagnostic-forw.md)).
- **A sanitizer-only link break.** slang#12136's new unit test touched the polymorphic internal `Slang::Session` via `asInternal()`; under `-fno-rtti` + the sanitizer's `-Wl,--no-undefined` the lazy-undefined `typeinfo for Slang::Session` became a hard link failure — RED on ONE of ~12 lanes only, so a per-lane check-runs scan is essential, and the leading `DWARF error: FORM value: 0x23` is benign noise (grep for `undefined reference|typeinfo`) ([[approver/challenger-miss-averted] A new unit test touching the polymorphic internal Slang::Session (via asInternal()) fails to link ONLY in the sanitizer job — -fno-rtti + -Wl,--no-undefined turns a lazy-undefined typeinfo into a hard build break](../learnings/1784271192351-approver-challenger-miss-averted-a-new-unit-test-t.md)).
- **A generic-predicate revision widens blast radius.** slang#12111 R1 approved a Layer-B fix (coalesce descriptor-heap loads in the SPIR-V legalizer, dominance-by-construction). The `synchronize` re-implemented the SAME fix as Layer A (make any `UniformConstant` load movable in the generic `isMovableInst`, so CSE collapses them) — reviewer-directed and Devin-clean, but it regressed unmodified `intrinsic-texture.slang.6/.7/.8` goldens because the predicate ALSO fires on plain sampler globals. A "move the same fix to a more generic layer" revision is a materially different change with a different blast radius → full fresh challenger + a live CI diff-vs-master, never a rubber-stamp ([[approver/challenger] Same-fix Layer-A (generic CSE) revision needs a fresh CI probe — broader blast radius than the Layer-B head you approved](../learnings/1784328018356-approver-challenger-same-fix-layer-a-generic-cse-r.md)).

## Attribution: a PR that EXPOSES a pre-existing defect by changing global behavior owns it

On slang#12089 rev6 a capability-narrowing PR flipped the default HitObject type on `sm_6_9+hlsl_nvapi` from NVAPI to native `dx::HitObject`, but four LSS accessors keyed on a *different* capability were NOT re-gated → mixed-ABI HLSL, the exact defect class the PR exists to eliminate. The buggy lines are pre-existing and untouched — tempting to downgrade to ABSTAIN "latent" — but the PR is the *proximate cause*: it transformed those methods from matched-at-base to mixed-at-head by changing the type-selection predicate. A defect a PR exposes by changing global behavior is attributable → BLOCK ([[approver/challenger] A capability-narrowing PR can EXPOSE pre-existing mixed-ABI on sites it doesn't touch — flipping the default type re-gates behavior of unedited methods (attributable → BLOCK)](../learnings/1784310133019-approver-challenger-a-capability-narrowing-pr-can-.md)). The transferable check on any capability-narrowing / default-flipping PR: enumerate ALL methods on the affected type, not just the arms in the diff — a method whose `case hlsl:` emits a vendor intrinsic but is callable regardless of the resolved ABI is a mixed-ABI candidate under the new default.

## Reachable RELEASE_ASSERT is a RED_BUG — prove reachability at the producer

slang#12147's `SLANG_RELEASE_ASSERT(debugArtifactCount == 1)` aborts slangc on valid multi-entry-point input, while its sibling validator `_validateCoverageManifestOutputPaths` handles the same `>1` case with a graceful diagnostic — the asymmetry between two sibling validators is the smell ([[approver/challenger] RELEASE_ASSERT on a reachable multi-artifact count is a RED_BUG, not a valid impossible-shape guard](../learnings/1784316403221-approver-challenger-release-assert-on-a-reachable-.md)). The subtle part is the *trigger*: for a SINGLE SPIR-V target slang forces whole-program (count==1) on every path (no-`-o` synthesizes a stdout output gated on `m_rawTargets==1`), so the assert is reachable **only via multi-target ≥2 entry points + no per-target `-o`**, which sidesteps the single-target synthesis guard ([Slang separate-debug-info: multi-target demotes SPIRV out of whole-program → per-EP debug artifacts abort the count==1 assert](../learnings/1784336687356-slang-separate-debug-info-multi-target-demotes-spi.md) on the compiler-internals page). The recall subagents AND the production bot all CONVERGED on a wrong single-target trigger — **convergence is not correctness** — and a DECISION_REVIEW critique that adversarially hunts the gate the finders missed is what caught it; run it whenever the challenger overrides a lenient doc verdict on a reachability argument ([[approver/challenger-miss] single-vs-multi-target whole-program forcing hides the reachable RELEASE_ASSERT trigger](../learnings/1784333455962-approver-challenger-miss-single-vs-multi-target-wh.md)).

## The middle rung: green CI can still be a hold (ABSTAIN / OPEN_GAP)

A green-CI revision that fixes only the *symptom* rather than *scoping the root change* is a hold, not a WOULD_APPROVE. slang#12141 R3 added explicit casts to the ONE test E30081 broke, but left the over-broad `forwardDiagnostics()` unchanged — the latent surface remains for every other/future consumer, and a `diagnoseRaw` re-emission bypasses per-id `-Wno-*`/`#pragma warning` suppression by construction. Two challenger checks CI cannot do: did the fix scope the root change or just silence the symptom, and does the re-emission bypass user suppression → `ABSTAIN_POLICY:OPEN_GAP` (verified over-broad, plausible trigger, real blast radius, not false-negative-safe), the rung between BLOCK (no reproduced 🔴) and WOULD_APPROVE ([[approver/challenger-miss-averted] a test-cast workaround fixes the broken test but not the over-broad change; scope+suppression-bypass gaps are CI-invisible WOULD_APPROVE→ABSTAIN discriminators](../learnings/1784309271831-approver-challenger-miss-averted-a-test-cast-worka.md)). The calibration across one PR's three revisions — BLOCK (rhi break) → BLOCK (E30081 regression) → ABSTAIN/OPEN_GAP (contained but one latent scope gap) — shows the approver's job is to track the residual, not rubber-stamp "the last thing I flagged is fixed."

## When a gap CLEARS: is the worst realistic failure a build break CI catches, or a silent miscompile it wouldn't?

The decisive discriminator for clearing a speculative gap is the *failure class*. For a **build-flag / optimization-level PR** whose only risk is a CI-visible `-Werror` build break, complete + green CI on the exact affected config legs is sufficient to clear it — the failure would be a build error, not a silent runtime miscompile. slang#12140 (`-Og` for GCC/Clang debug) cleared a "`-Wmaybe-uninitialized` might break `-Werror`" gap because the affected debug legs were green at head, `-Wmaybe-uninitialized` is GCC-only (the "macOS Clang" framing was misdirected), and the blast radius is Debug+GCC/Clang only ([[approver/calibration] build-flag PR: clear a "-Werror CI break" gap by checking the affected config is actually green](../learnings/1784270606102-approver-calibration-build-flag-pr-clear-a-werror-.md)). Two extensions of the rule: a **subtractive guard** (`AND NOT MSVC`) relative to a prior CLEAN head can only *remove* a flag, never add it → cannot regress prior-green, so the verdict is ≥ prior without re-derivation; and a warning-coverage gap on a **pure-cmake PR that adds zero C++** clears as *future-proofing* (the PR introduces no uninitialized-variable risk itself) ([[approver/calibration] -Og debug-build guard: subtractive NOT-MSVC guard can't regress prior-green; -Wmaybe-uninitialized gap clears as future-proofing when PR adds no C++](../learnings/1784288671711-approver-calibration-og-debug-build-guard-subtract.md)). Contrast codegen/logic PRs where green CI ≠ safe — a miscompile passes all tests.

**False-negative-safe-by-construction exemptions approve.** For a diagnostic-suppression PR, don't ask "could this hide a bug?" in the abstract — trace the diagnostic's *fire conditions*. slang#12011's E41017 `__extern_cpp` exemption is safe because `checkUninitializedGlobals` only fires when a global has no in-module init AND no store, and the exemption predicate (`IRExternCppDecoration` + external linkage) is a strict subset of the documented host-provided-global pattern (value comes from outside the module by design) — plus a discriminator test proves the predicate is narrow ([[approver/calibration] E41017 __extern_cpp exemption is false-negative-safe by construction — approve the class](../learnings/1784288118508-approver-calibration-e41017-extern-cpp-exemption-i.md)).

**Constness-selected SPIR-V operands: trace the *emitted* form.** slang#12133's Gather const-offset fix emits `ConstOffset` (legal only if the offset is an `OpConstant`/`OpConstantComposite`). "The helper detects constants" is not enough — verify the constant-hoisting pass (`maybeHoistConstructInstToGlobalScope`) actually moves the accepted shapes to global scope and that the classifier's accepted set ⊆ the hoister's hoistable set; when the PR's test is spirv-asm-only (no real `spirv-val`), this inspection IS the validation gate ([[approver/challenger] ConstOffset-safety hinges on constant-MakeVector hoisting (maybeHoistConstructInstToGlobalScope), verify it — slang#12133](../learnings/1784334175709-approver-challenger-constoffset-safety-hinges-on-c.md)).

## Real-hardware CI can substitute for a missing Devin — but only if it actually EXERCISED the code

On the slang-rhi fallback tier, slang-rhi runs the full test suite *inline in the build matrix on real GPU adapters*, so a timed-out Devin on a behavior-changing PR (#797 D3D12 timestamp resolve) doesn't force ABSTAIN — pull the CI *job logs* and grep for the PR's new test executing + PASSING on a real adapter (`hardware-device`, not `software-device`/`SKIPPED`) ([[approver/human-agreement] slang-rhi real-hardware CI substitutes for a timed-out Devin on backend-logic PRs](../learnings/1784271405834-approver-human-agreement-slang-rhi-real-hardware-c.md)). The mirror-image trap: a **support-claiming PR whose test is masked-out is compile-only, never executed**. slang-rhi#800 flipped `docs/api.md`'s Metal `dispatchComputeIndirect` cell to `yes` and added real Metal code with green CI — but the feature's `GPU_TEST_CASE(..., D3D12 | Vulkan | CUDA)` *excludes Metal*, so the macOS job compiled but never ran the new path; green CI proves it builds, not that it works → a genuine `OPEN_GAP` for a support-claiming PR ([[approver/clause-gap] Backend-support PR that flips a docs support-matrix cell but leaves the feature's test masked-out is compile-only, never executed](../learnings/1784338875078-approver-clause-gap-backend-support-pr-that-flips-.md)). And CI green in a decoupled component (a standalone Go tool in `extras/scaler` that no CMake/CI job builds) is *orthogonal* — it can't substitute for a missing review signal the way real-hardware CI does.

The masked-out-test class recurs even when the PR SHIPS a test: slang-rhi#801 (native Metal buffer import) shipped `test-buffer-from-handle.cpp` that calls the new Metal code, but its device mask was `GPU_TEST_CASE("buffer-from-handle", D3D12 | Vulkan)` — `Metal` omitted, so `GPU_TEST_CASE` (which registers one case per flagged device) registers NO Metal case, and the macOS Apple-Silicon CI (which DOES run `-check-devices` on Metal hardware) compiled but never executed the import path. The `checkNoSilentGpuSkips()` guard doesn't catch it — it only flags a device with registered-but-zero-running tests, not a device with zero registered cases. So for any slang-rhi backend-specific PR, don't stop at "a test exists": **grep the test's `GPU_TEST_CASE(...)` mask and confirm the PR's target backend flag is IN it** — a Metal-only change tested only under `D3D12 | Vulkan` is OPEN_GAP (source-verified-correct doesn't round it up), same class as #800; next-action = add `Metal` to the mask or consciously accept the untested-on-Metal risk [[approver/challenger] slang-rhi Metal-only feature with test masked to D3D12|Vulkan = OPEN_GAP](../learnings/1784816143760-approver-challenger-slang-rhi-metal-only-feature-w.md).

## Combined-status ≠ causal: classify from individual check-runs traced to cause

The GitHub combined commit-status aggregates ALL contexts including non-causal cross-repo/downstream jobs. On the clean front-end PR #12131 combined-status was `failure` from a `test-falcor` image-diff flake (from a prior draft run) and a `SlangPy Tests` `test_profiler.cpp` CPU-timing assertion (Linux-only, passed on Windows) — neither reachable by the PR's code path ([[approver/calibration] combined-status-failure-from-non-causal-downstream-flakes](../learnings/1784329341037-approver-calibration-combined-status-failure-from-.md)). When `require_ci_green:false` defers, enumerate individual check-runs `--paginate`, confirm the repo's OWN core legs (especially the one running the PR's new tests) are `success`, and for each red trace the failing test — platform-asymmetric / timing / image-diff / downstream-renderer failures are non-causal-flake signals. The rule is symmetric: classify from check-runs traced to cause, never from combined-status alone, in EITHER direction (a green combined-status is equally untrustworthy — see #12130's metal-fmod miss). `SlangPy test_profiler.cpp` is a recurring non-causal flake for slang PRs.

## A stale secondary reviewer flags the pre-fix state — verify at head

On slang#12147 R4 (the fix revision) Devin ran ~5 min after the push and flagged the R1-R3 blocking bug verbatim at `:766` — but the assert was already gone; Devin analyzed a stale/cached snapshot, and its line number had shifted meaning across the revision (`:766` was now a harmless guard, the graceful diagnostic at `:798`) ([[approver/stale-secondary] Devin (secondary) reviews the pre-fix prefix state on a fresh-push revision — verify the flagged line against head source before trusting a bug flag](../learnings/1784343479716-approver-stale-secondary-devin-secondary-reviews-t.md)). Never accept a secondary bug flag on faith on a fresh-push revision: the PRIMARY tier harvested at the pinned head (matching `diff_hash`) is the verdict source, and open the flagged `file:line` at the pinned head, locating the construct by NAME not line. This is the flip side of the false-positive class below — a secondary flag is a hypothesis to verify at head, never a standalone reason to hold a BLOCK.

## False-positive refutations: a refuted 🔴 does not become WOULD_APPROVE

Devin (or any automated reviewer) can raise a plausible 🔴 that source inspection refutes. On slang-rhi#800 Devin flagged an indirect-dispatch residency crash "missing useResource" — refuted because in Metal a resource passed *directly* to an encoder method (including `dispatchThreadgroups(indirectBuffer,...)`) is auto-resident; `useResource` is needed ONLY for GPU-addresses dereferenced inside argument buffers, and the codebase calls `addUsedResource` only in the arg-buffer-writing path ([[approver/challenger-miss-averted] Metal direct-encoder-operand needs no useResource — Devin residency false-positive](../learnings/1784338866210-approver-challenger-miss-averted-metal-direct-enco.md)). Crucially: a refuted 🔴 does NOT justify BLOCK, but shadow mode never rounds a doc's 🔴 up to WOULD_APPROVE either — so the decision is `ABSTAIN_POLICY:CHALLENGER_CONCERN` (here also carried by a genuine residual test-mask gap). Trace the exact residency/mechanism category before blocking on an automated reviewer's claim.

## The prior fixer learning can PREDICT the correct fix shape

When the fixer who triaged an issue left a durable learning about *what the principled fix should look like*, Step-0 recall surfaces it as the sharpest challenger prior. On slang#11665 (reject operator names on vars/params) the recall learning predicted the fix must reject at the single choke point (`UnwrapDeclarator`) gated by an opt-in, sparing legit operator functions — and the PR did exactly that, letting the challenger verify the diff *matches the predicted shape* rather than re-derive from scratch ([[approver/human-agreement] fixer-issue-learning-predicts-correct-fix-shape-clears-challenger](../learnings/1784307794563-approver-human-agreement-fixer-issue-learning-pred.md)). Grep the learnings for the issue number FIRST on any fixer PR you (or a peer) previously triaged.

## A standing human CHANGES_REQUESTED caps at ABSTAIN — never round up

`eval-clauses.py` has NO clause for human-review-state, so a standing unresolved maintainer CHANGES_REQUESTED on the current head is invisible to Steps 1–2 — the challenger MUST run `gh pr view --json reviewDecision,reviews`. On slang#11136 the doc verdict was APPROVE with 0 bugs, Devin independently *confirmed* the fix, and the code was verified correct in source — yet the standing CHANGES_REQUESTED caps the decision at `ABSTAIN_POLICY:CHALLENGER_CONCERN` (only the requesting maintainer can clear their own request) ([[approver/challenger] standing human CHANGES_REQUESTED vetoes WOULD_APPROVE regardless of clean doc](../learnings/1784326394685-approver-challenger-standing-human-changes-request.md)). Distinguish carefully: a **DISMISSED** review WITHDRAWS a (here non-blocking COMMENTED) review, leaving no active human review — it does NOT block WOULD_APPROVE, unlike a standing CHANGES_REQUESTED (slang#12133 R3) ([[approver/challenger] module-version-bump synchronize (k_maxSupportedModuleVersion): audit value/lockstep/additivity against the design docs; DISMISSED human review is not a CHANGES_REQUESTED veto — slang#12133 R3](../learnings/1784343540068-approver-challenger-module-version-bump-synchroniz.md)). Beware framing drift — decide from harvested state, not the dispatch's "disputing vs complying" characterization.

**A same-head human APPROVAL is a JOIN signal, not a reason to flip your gap.** If you let a visible human approval upgrade your independent read you stop being an independent check and the agreement statistic becomes meaningless. On #12144 R2 a maintainer had APPROVED the exact head while the approver's independent read was ABSTAIN(OPEN_GAP): the calibrated outcome is `ABSTAIN_POLICY:OPEN_GAP` decision row AND a separately-recorded `human_verdict=APPROVED` = a healthy **withhold-on-SAFE agreement**, NOT a collapsed WOULD_APPROVE ([[approver/human-agreement] A same-head human APPROVAL is a JOIN signal, not a reason to flip your OPEN_GAP to WOULD_APPROVE](../learnings/1784281316765-approver-human-agreement-a-same-head-human-approva.md)). Decide first with the human verdict walled off; record it only after, purely for calibration.

## Legitimate within-session flips and converging loops

Not every re-eval is a hold. A CI-proven BLOCK flips cleanly to WOULD_APPROVE when the fixer's next commit is a **test-only, CI-proven-green fix of your exact next-action**: on #11595 the BLOCK'd E41303 diagnostic broke `gh-9931.slang.1`; R5 fixed the test's false alignment promise with all 9 compiler files byte-identical R4→R5 (diagnostic still stands, not weakened) and the specific previously-red sub-test now `passed` — a VINDICATED BLOCK (SUPERSEDED_CHANGES_REQUESTED), and recording WOULD_APPROVE is the honest call, not "backing down" ([[approver/human-agreement] BLOCK→WOULD_APPROVE flips clean when the fixer's next commit is a test-only, CI-proven-green fix of your exact next-action](../learnings/1784270379814-approver-human-agreement-block-would-approve-flips.md)). A **converging multi-synchronize loop** (each push adopts the reviewer's most recent concrete ask) reliably ends in a same-head APPROVE — #12034 ran 5 revisions and merged at the exact R5 head with the maintainer's approval ([[approver/human-agreement] confirmed: a multi-synchronize fixer↔maintainer review loop that converges (each rev adopts the reviewer's ask) reliably ends in a same-head APPROVE — WOULD_APPROVE on each settled rev is safe](../learnings/1784308481321-approver-human-agreement-confirmed-a-multi-synchro.md)); `REVIEW_REQUIRED` from auto-dismiss-on-push is not a withhold reason, only a standing CHANGES_REQUESTED is. A **review-response cleanup revision** (comment trim + if-chain→switch) carries the prior revision's verified safety forward once you prove the emit body is byte-identical and the refactor is logically equivalent — but don't overclaim "N green / 0 red" while legs are still pending (codex DECISION_REVIEW catches this) ([[approver/challenger] synchronize cleanup-only revision: verify delta semantics-preserving (byte-diff emit body + refactor equivalence), carry prior safety forward, don't overclaim unsettled CI — slang#12133 R2](../learnings/1784338540772-approver-challenger-synchronize-cleanup-only-revis.md)).

## Human-agreement vindications (the calibration record)

Merged-at-exact-head + independent (non-self) human approval = clean AGREEMENT, and several outcomes confirmed the conservative-lean bar:

- **#12140 `-Og`** MERGED at the exact decided head with the subtractive-guard + no-C++ future-proofing gaps *shipped unaddressed* — confirming they were reviewer notes, not blockers, and CLEAR was correct ([[approver/human-agreement] #12140 -Og debug-build MERGED at decided head — subtractive-guard + no-C++ future-proofing-gap clear VINDICATED](../learnings/1784292544219-approver-human-agreement-12140-og-debug-build-merg.md)).
- **Downstream test-fix unblocks a shadow-BLOCK.** slang-rhi#799 (the `float4(float2,1.f,1.f)` fix for #12141's break) — verify the diff-line vs the break site named in the prior BLOCK, confirm semantic equivalence (splat vs tail-pad), and approve it STANDALONE (don't gate the downstream fix on the core PR — that inverts the dependency) ([[approver/human-agreement] downstream test-fix that unblocks a prior shadow-BLOCK — verify diff-line vs break site, then WOULD_APPROVE](../learnings/1784282766770-approver-human-agreement-downstream-test-fix-that-.md)).
- **A confirmed human-DISAGREEMENT that vindicated the ABSTAIN.** slang#12031's ref-subscript-accessor autodiff silently returns a 0 gradient (the emitted `-target cpp` forward-derivative hardcodes `{ ..., 0.0f }`); the shadow ABSTAIN_INFRA/CHALLENGER_INCOMPLETE (runtime probe outran the merge) was correctly cautious — a WOULD_APPROVE would have been a false-safe on a real silent-wrong-gradient. "Unsupported" boundaries must ERROR, not silent-zero ([[approver/human-disagreement] confirmed: differentiating a read through a user-defined ref subscript accessor silently returns a 0 gradient (slang, experimental)](../learnings/1784293272824-approver-human-disagreement-confirmed-differentiat.md)).
- **The #12141 full-arc (BLOCK→BLOCK→ABSTAIN→merge).** The vec4 3-elem-init deprecation ran R1 BLOCK (static_assert disable broke bundled slang-rhi shaders) → R2 BLOCK (success-path `forwardDiagnostics()` leaked E30081, broke `integer_pack.slang`) → R3 ABSTAIN_POLICY/OPEN_GAP (E30081 fixed via test casts but the raw `diagnoseRaw` re-emission still bypassed per-id `-Wno-*` suppression), then MERGED 5 commits PAST the R3 head (csyonghe APPROVED, a maintainer ≠ author) — the initial write-up framed this as end-to-end agreement with the author implementing the exact next-action, and the canonical takeaway is that the right fix layer for a "sub-sink captures then re-emits diagnostics" bug is the **sink construction** (does the child sink inherit the parent's severity-override map?), plus join-SHA-first (always diff decided-head → merged-head) [[approver/human-agreement] full-arc vindication: R3 ABSTAIN(OPEN_GAP) merged only AFTER the author implemented the exact next-action (copy sink severity-overrides + add -Wno test); BLOCK→BLOCK→ABSTAIN→merge](../learnings/1784838040864-approver-human-agreement-full-arc-vindication-r3-a.md). **NOTE:** this account is corrected/partly-superseded — see Contradictions/supersessions below; the closure was PARTIAL and an ABSTAIN row is not "agreement" [[approver/human-agreement] CORRECTION to full-arc-vindication #12141: PARTIAL gap closure (suppression-bypass fixed, broad-forwarding retained), not "whole gap fixed" or "end-to-end agreement"](../learnings/1784838665378-approver-human-agreement-correction-to-full-arc-vi.md).

## Incremental catches & calibration (2026-07-18/19 approver session)

**A `synchronize` is not automatically a fix — classify the delta before re-litigating.** Three sharpenings of the per-revision discipline: (1) a `synchronize` whose new head is a pure `Merge branch 'master'` changes nothing in the PR's own content — verify the flagged files' git **blob-sha** across the two heads (`gh api contents/<path>?ref=<sha> --jq .sha`) plus `additions/deletions/changedFiles`; identical blob ⇒ any prior finding persists verbatim, re-BLOCK/re-hold without re-deriving ([[approver/calibration] A "synchronize" that is a pure master-merge fixes nothing — verify blob-sha equality before assuming a re-push addressed prior findings](../learnings/1784366423621-approver-calibration-a-synchronize-that-is-a-pure-.md)). (2) For a master-merge on a PR with **hot files**, whole-file blob SHAs will differ because master independently edited those files — the authoritative check is the PR **net-diff hunks** (`gh pr diff`), not the blob; and the operative human signal is the APPROVED review's `commit.oid`, read it (don't infer the association from `submittedAt` vs `committedDate` ordering) ([[approver/challenger] master-merge synchronize: verify fix net-diff byte-identical … check the APPROVED review's commit.oid — slang#12133 R4](../learnings/1784383023678-approver-challenger-master-merge-synchronize-verif.md)). (3) A push that "addresses review" may address a **different axis** than your open gap — re-run the challenger against the SPECIFIC gap that drove the prior withhold (diff the exact code region, check a test now covers YOUR trigger shape, check the maintainer decision you were waiting on actually landed); "new test added" / "comment resolved" is about whatever the reviewer asked, which may be orthogonal ([[approver/calibration] A synchronize addressing a different review axis does not close your open gap](../learnings/1784421277721-approver-calibration-a-synchronize-addressing-a-di.md)). The mirror on the CI side: a forwarded CI *failure* is stamped with the head it ran against — resolve its `head_sha` (`gh api check-suites/<id> --jq .head_sha`) vs your pinned settled head before treating it as live; on a fast-moving PR the author may have pushed past the failure ([[approver/calibration] forwarded-CI-failure-suite-may-be-at-superseded-head](../learnings/1784416965336-approver-calibration-forwarded-ci-failure-suite-ma.md)). And "head advanced past your verdict" is frequently just **master-catchup** (`behind_by:0`, commits are other already-merged PRs) — diff the delta and confirm the PR's OWN load-bearing files are byte-identical before spending a full re-harvest+re-Devin+CI cycle; a mid-chain design *revert* resets the verdict (evaluate the reverted-to design on its own merits) ([[approver/human-agreement] Full-chain vindication: BLOCK→fix→APPROVE held through merge; and "head advanced" is often just master-catchup](../learnings/1784420055611-approver-human-agreement-full-chain-vindication-bl.md)).

**Regression / self-contradiction BLOCK catches — the strongest 🔴s need no external corroboration.** A failing test the PR *itself adds* (its FileCheck oracle vs its own emitted output) is self-contradicting: either the code is wrong or the spec-of-record is wrong, and it is the strongest possible 🔴 — do NOT downgrade to ABSTAIN just because a relaxed `ci_green_on_sha` clause "passes" (clause-pass governs eligibility; CI red is challenger *evidence*, never laundered by a clause that doesn't require CI) ([[approver/challenger] PR's own new feature test failing at head is a self-contradicting RED_BUG](../learnings/1784431283917-approver-challenger-pr-s-own-new-feature-test-fail.md)). A **pre-existing untouched** test failing at the pinned head is a regression even without a master baseline when three conditions hold — the test predates the PR, the PR doesn't modify it, and the diff touches exactly the path the test exercises ([[approver/calibration] pre-existing-untouched-test-failing-at-head-is-regression-even-without-base-green](../learnings/1784420632496-approver-calibration-pre-existing-untouched-test-f.md)); when you CAN reach master, the airtight three-part proof is untouched-in-diff + present-and-failing-at-master? no + new-symbol-absent-on-master → provably green on master, red at head ([[approver/calibration] pre-existing untouched test regressing (green on master) = confirmed blast radius, not a flake](../learnings/1784431292789-approver-calibration-pre-existing-untouched-test-r.md)). A **tests-only** revision after a BLOCK can turn CI green while leaving a CI-invisible code 🔴 untouched — diff the code-file blobs; if byte-identical the revision did not address the code defect, re-verify the 🔴 stands and don't let now-green CI launder it ([[approver/challenger] tests-only revision can turn CI green without touching the buggy code — diff the code blob, don't trust green](../learnings/1784436534792-approver-challenger-tests-only-revision-can-turn-c.md)). Beyond the diff: a narrow-looking change to a **shared per-modifier/per-attribute dispatch arm** has blast radius = union of ALL producers of that modifier, not the syntax in the PR title — grep for every synthetic producer (compiler options like `-no-mangle`, desugaring, parser/checker stamping) before WOULD_APPROVE; a Step-0 recall-predicted-shape match confirms INTENT but says nothing about unintended collateral scope ([[approver/challenger] shared-modifier-lowering-arm-change-has-blast-radius-beyond-explicit-syntax](../learnings/1784420619202-approver-challenger-shared-modifier-lowering-arm-c.md)). A **visibility-*raising*** default change is dangerous exactly where a cap-check would newly fire — grep every reader that *compares* visibilities (`UseOfLessVisibleType`/E30604, ctor-synthesis) because a public struct with a less-visible field type that compiled at 2025 can newly hard-error at 2026; new green tests only cover shapes the author thought of ([[approver/challenger] visibility-elevation feature must probe the UseOfLessVisibleType cap-check](../learnings/1784417628061-approver-challenger-visibility-elevation-feature-m.md)). A **"simplify"/refactor** revision that preserves the headline fix can silently drop a DELIBERATE distinction the removed abstraction encoded — diff the removed type/helper's semantics, not just the target fix (an `OutputDestination{isStdout}`→plain-`String` collapse re-introduced a spurious diagnostic) ([[approver/challenger-miss] a "simplify"/refactor revision can preserve the headline fix while silently regressing a sibling correctness distinction](../learnings/1784381039011-approver-challenger-miss-a-simplify-refactor-revis.md)). And a fix that narrows behavior for a target class can create a **fresh doc 🔴** in the very `@remarks`/comment the PR added earlier — re-scan the revision's full non-code diff for prose still describing the pre-fix behavior; "old 🔴 resolved" and "no new 🔴" are two separate checks ([[approver/challenger] a fix that resolves the flagged bug can introduce a new one in its own doc/comment change](../learnings/1784440929327-approver-challenger-a-fix-that-resolves-the-flagge.md)).

**Devin's structured verdict is the only load-bearing Devin signal — prose and page-counters are not.** Devin's free-text summary can confidently describe features NOT in the diff (it absorbs the PR *description's* over-claims as if verified) — load-bear only on the structured `## Bugs`/`## Flags` counts, spot-check any capability claim against `gh pr diff`, and caveat the doc when prose is refuted ([[approver/challenger] devin-prose-unreliable-trust-only-structured-verdict](../learnings/1784390121609-approver-challenger-devin-prose-unreliable-trust-o.md)). Extend the same distrust to the page's `N Flag` header counter: it can read `1 Flag` while the parsed `## Flags` section says `(none reported)` — the structured section wins (it's what the synthesis parses); reconcile or annotate rather than propagate ([[approver/challenger] Devin page "N Flag" counter can disagree with the structured flags section — trust the structured verdict](../learnings/1784417635185-approver-challenger-devin-page-n-flag-counter-can-.md)).

**Don't take a CI red at face value — resolve what it represents.** `check-ci` is slang's aggregation/gating job (`jq` over the `needs` context, `exit 1` if any dependency ≠ success), so a `check-ci` failure is a downstream reflection of some other leg, never an independent signal — read its log for the named dependency and triage only the real leg; counting it double-counts one failure ([[approver/calibration] check-ci-is-aggregation-gate-not-independent-failure](../learnings/1784420509811-approver-calibration-check-ci-is-aggregation-gate-.md)). And a FileCheck failure whose "expected string" is English prose is usually a **test-authoring artifact**, not a code defect: LLVM FileCheck parses a literal `CHECK:` token *anywhere* on a line including backticked prose comments, registering a phantom directive that fires early and masks the real assertion — the fix is rewording the comment, the code was correct all along ([[approver/calibration] a stray `CHECK:` token inside a prose comment is a test-authoring failure that masquerades as a code defect](../learnings/1784436545771-approver-calibration-a-stray-check-token-inside-a-.md)).

**A behavior-inert build-warning fix clears on the affected green legs.** An "initialize-to-default to silence `-Werror=maybe-uninitialized`" PR looks like it could alter behavior, but when it sits behind a `SLANG_RETURN_ON_FAIL`-style result-returning helper that writes the out-param only on the success path and the caller returns on failure before reading it, the initializer is runtime-inert — the diagnostic is a genuine `-Og` data-flow false-positive across the helper-call boundary. Verify (a) the initializer is a valid existing enum member and (b) the helper's write-gate; then green on the exact affected legs (esp. the one that failed pre-fix) is sufficient challenger evidence, because the only realistic failure is a CI-visible build break, not a silent miscompile. Classify protected paths from the changed-file list, not a misleading branch name ([[approver/calibration] uninit-var -Og -Werror fix behind result-returning helper is behavior-inert](../learnings/1784389774470-approver-calibration-uninit-var-og-werror-fix-behi.md)).

**A recalled fix-shape prediction is the strongest challenger prior — but a checklist to VERIFY, not a substitute.** When Step-0 recall surfaces a prior triage of the SAME issue the PR fixes, the recalled fix prediction becomes a concrete axis-by-axis diff checklist against source at the pinned head — the match (plus clean clauses + head-current Devin + green CI legs) is what justifies WOULD_APPROVE on a thin tier; a DEVIATION from the prediction is exactly the signal recall exists to surface ([[approver/calibration] recall-predicted-fix-shape-verify-diff-matches-prediction](../learnings/1784417192285-approver-calibration-recall-predicted-fix-shape-ve.md)).

**Human-agreement calibration — split merge provenance before scoring a `pr_merged` join.** The `record_human_verdict` mapping stamps APPROVED on any merge, but the *signal strength* depends on WHO merged: an **independent-maintainer APPROVED same head** (reviewer ≠ author) is STRONG agreement, whereas an **author self-merge** (or a merge with only bot+author COMMENTED) is WEAK — it attests "the author was confident," not "an independent reviewer weighed your concern," especially when the concern was CI-invisible and shadow-mode never posted it. Pull `mergedBy` + `reviewDecision` + `reviews[].state/commit.oid`, never just `merged=true` ([[approver/human-agreement] author self-merge with no independent review is a weak agreement signal](../learnings/1784392147522-approver-human-agreement-author-self-merge-with-no.md)). This corrected an over-conservative read of slang#12147: the first pass framed the self-merge as evidence the R5 ABSTAIN was "over-conservative," but a self-merge does NOT refute a withhold — do not "learn" to lower your bar from one ([[approver/human-agreement] CORRECTION to slang#12147 calibration: it was an AUTHOR SELF-MERGE (weak signal)](../learnings/1784386500014-approver-human-agreement-correction-to-slang-12147.md)); the calibration point that stands is to grade a false-**POSITIVE** (over-rejection) by TRIGGER-LIKELIHOOD × BLAST-RADIUS, reserving ABSTAIN for plausible-everyday-trigger false-positives or any false-**NEGATIVE** ([[approver/human-disagreement] ABSTAIN over a pathological-only false-positive diagnostic; maintainer merged with it](../learnings/1784386401932-approver-human-disagreement-abstain-over-a-patholo.md), [[approver/human-agreement] author self-merge is a WEAK 'APPROVED' signal — a shadow-mode ABSTAIN … is vindicated (not refuted)](../learnings/1784386435249-approver-human-agreement-author-self-merge-is-a-we.md)). The strong-agreement archetype landed on slang#12133: WOULD_APPROVE @R4 == merged head, jkwak-work gave an explicit APPROVED and merged the same SHA — a 4-revision chain of known-shape deltas whose prior verified safety carried forward every time ([[approver/human-agreement] slang#12133 MERGED-agreement vindicated across 4 revisions](../learnings/1784391254624-approver-human-agreement-slang-12133-merged-agreem.md)). The safe-direction DISAGREEMENT archetype landed on slang#11471: a maintainer merged over two shadow BLOCK 🔴s (an example-only assert + an untrusted-input-only DoS) — vindicated on correctness (the eventual production review confirmed both verbatim), the disagreement was on blocking-*threshold* (blast-radius/code-location/threat-model), not correctness; annotate that severity axis so the join reads as expected, don't soften the BLOCK ([[approver/human-disagreement] Maintainer merged over a production-review 🔴 (example-only assert + untrusted-input DoS)](../learnings/1784391272446-approver-human-disagreement-maintainer-merged-over.md)).

- A verified 🔴 is NEVER downgraded to WOULD_APPROVE by an author self-merge — a self-merge is a WEAK signal, not a refutation ([[approver/human-agreement] CORRECTION to slang#12147 calibration: it was an AUTHOR SELF-MERGE (weak signal)](../learnings/1784386500014-approver-human-agreement-correction-to-slang-12147.md), superseding the "maintainer merged ⇒ my ABSTAIN was over-conservative" framing of [[approver/human-disagreement] ABSTAIN over a pathological-only false-positive diagnostic](../learnings/1784386401932-approver-human-disagreement-abstain-over-a-patholo.md)).

## Standing-Bot 🔴 Refutation and Codegen-Fix Verification Without Running the Compiler (2026-07-20 fold)

Three challenger-stage calibrations from the slang#11803 and #12142 chains. **(1) A standing bot 🔴 is REFUTED, not honored, when the flagged text/code no longer exists at the pinned head.** Devin's bug list can LAG the latest commit (re-renders slowly / keys off a cached analysis), so a bug persists in the list after the code is fixed. The sole discriminator is whether the defect actually exists in source at the pinned head — re-fetch the exact file:line and grep the named phrase. This is NOT the "downgrade a CONFIRMED 🔴 by severity" error: refuting an ABSENT 🔴 is legitimate and required; honoring a label for a defect that no longer exists is a false-BLOCK ([a standing bot 🔴 is REFUTED when the flagged text no longer exists at the pinned head](../learnings/1784442969985-approver-challenger-a-standing-bot-is-refuted-not-.md)). **(2) A codegen fix whose only validating test never executed = OPEN_GAP, not WOULD_APPROVE.** External-fork PRs have their `CI` workflow maintainer-gated (`conclusion=action_required`, 0 jobs); the green *combined* status covers only CLA/CodeRabbit/trigger, not slang's build/test matrix. Pull `/actions/runs?head_sha=<sha>` and check the `CI` run's conclusion + job count — codegen change + unrun validating test + no local run path ⇒ ABSTAIN_POLICY/OPEN_GAP, never round up ([fork-PR codegen fix with unrun validating test → OPEN_GAP](../learnings/1784446531911-approver-challenger-fork-pr-codegen-fix-with-unrun.md)). **(3) But you CAN establish correctness-by-inspection** when the target can't run locally: align the change with pre-existing hand-written siblings as ground truth, prove before/after byte-identity to bound the blast radius, grep every use of a role-changed variable for completeness, and confirm the test corpus has no pre-existing test asserting the old form. This separates "is the code right?" (yes) from "has it been validated?" (no) — two axes driving different reason_codes ([verify a codegen fix by aligning with siblings + before/after byte-identity](../learnings/1784446552079-approver-challenger-verify-a-codegen-fix-by-aligni.md)).

## Confirmed-by-Merge: DDS Subresource-Math Fix (WOULD_APPROVE = APPROVED = MERGED) (2026-07-21 fold)

A calibration vindication worth recording as a *class*, not an instance. slangpy#1049 (DDS loader mipmap-pitch / 3D-depth fix): shadow decision WOULD_APPROVE @ 6fd917aa; human jhelferty-nv APPROVED the same head, then MERGED it 4 min later (7e8c09cb) with no follow-up commits between the decision head and the merged head — the strongest calibration signal (approve/approve/merge, zero diff between the read and the shipped change). The safely-approvable *class*: a small (~180-line) bug-fix to binary-asset subresource/offset/size math in an image/texture loader, where risk is silent wrong offsets rather than a crash. What made it approvable (probe these on similar changes): (1) **hand-verify every arithmetic test literal against the new code** — recompute expected offsets from the formula, don't trust "tests pass" (here mip clamp `max(1u,dim>>mip)` had to be on BOTH width and height or high mips give slice_pitch 0); (2) **the removed code was the bug** — deleting an override that recomputes *worse* (a rounding-buggy manual pitch calc that truncates for block-compressed) is a strong positive signal; (3) **verify the test-data git-submodule bump is merged to the data repo's default branch and contains the referenced files** (`gh api …/compare/main...<sha>` identical) — a human's CHANGES_REQUESTED here was exactly "use the merged data files"; (4) **3D `layer_count==1`** with depth folded into one subresource's `.size = slice_pitch*mip_depth`, not iterated as layers. Two process meta-lessons: a `synchronize` that is a pure "Merge branch 'main'" produces a new head SHA but a byte-identical PR-authored diff (`base...head`) — re-pin and record against the new SHA but the code investigation carries over; and the OUTPUT_REVIEW critique gate re-hashes attested artifacts at delivery, so ANY post-approve edit re-trips it (this PR took 5 rounds) — resolve the human-verdict commit alignment from review `commit` oids BEFORE drafting (never assume the human approved an earlier commit), write time-sensitive cautions as record-time-scoped ("CI was not green AT RECORD TIME; policy did not require it"), and batch all edits before the first OUTPUT_REVIEW ([[approver/human-disagreement] CONFIRMED agreement — DDS/texture subresource-math fix with exact-offset tests + merged data submodule](../learnings/1784561186392-approver-human-disagreement-confirmed-agreement-dd.md), [[approver/human-disagreement] CONFIRMED-by-merge — DDS subresource-math fix WOULD_APPROVE matched merge outcome](../learnings/1784561550592-approver-human-disagreement-confirmed-by-merge-dds.md)).

## Empirical Re-Verification, Design-Scope ABSTAINs, and Merged-Join Corrections (2026-07-22 fold)

**When a `synchronize` touches the exact code your open gap depends on, build and reproduce — don't reason about the new form, and don't relay a peer's "unaffected."** On slang#12151 (public-by-default struct members, #9153) the E30604 `UseOfLessVisibleType` gap was empirically proven at head `044c1e1b09`; the code owner then simplified that very `getDeclVisibility` branch and pushed a new head. A prior empirical repro does NOT transfer across a change to the same region — re-read the changed source at the new head and separate "empirical at old head" from "source-predicted at new head; fresh build = ground truth" ([a prior empirical repro doesn't transfer across a change to the same code region — re-verify at the new head](../learnings/1784657247208-a-prior-empirical-repro-doesn-t-transfer-across-a-.md)). The reliable move is to apply exactly that one change to a local clone, build slangc, and run the gap's trigger shape plus controls (pre-feature language version; the workaround) — a ~15-min build absorbed by a background subagent keeps it out of the decision session ([when a synchronize changes the exact code your open gap concerns, build and reproduce — don't reason about the new form](../learnings/1784658867738-approver-calibration-when-a-synchronize-changes-th.md)). Crucially, empirical confirmation moves the *evidence* axis (inspection < reproduction < independent re-reproduction), never the *class* axis: a proven-but-**intended**, opt-in, fail-safe behavior whose desirability is an unresolved maintainer design fork stays `ABSTAIN_POLICY:OPEN_GAP` — proving it occurs does not promote it to BLOCK (reserved for a verified 🔴 defect), and owner COMMENT-state "looks good" does not promote it to WOULD_APPROVE ([empirical confirmation strengthens the evidence, not the decision class — intended-but-design-undecided stays OPEN_GAP, not BLOCK](../learnings/1784658882005-approver-calibration-empirical-confirmation-of-a-f.md)).

**Design-scope objections and imported-decl gates on the #12156 hpp-export chain.** Two challenger lessons: (1) a "clear it as a benign dedup/plausibility" reflex missed a REAL regression — an `as<CallableDecl>(decl)` gate that added `HLSLExport`+`KeepAlive` did NOT exclude imported/bodyless `[__extern] __extern_cpp` decls, so a definition-less function became a keep-alive export root demanding a symbol that doesn't exist → `E45001 unresolved external symbol`. When a change adds a "retain + must-link" decoration in a path that also runs for imported/extern/bodyless decls, construct the concrete adversarial input (does this now demand a symbol with no local definition?) and prefer build/repro over deepwiki plausibility for any linking/DCE outcome; the correct gate is `as<CallableDecl>(decl) && !isImported` ([challenger miss — as-CallableDecl gate did not exclude imported bodyless fn → E45001](../learnings/1784665748345-approver-challenger-miss-as-callabledecl-gate-did-.md)). (2) When a fix makes input-class A behave identically to a class B that carries a known-latent bug, "A now inherits B's quirk, so benign" silently answers a DESIGN question with an approve — separate "is the equivalence a FACT?" (verifiable) from "is inheriting B's bug ACCEPTABLE?" (a maintainer scope call). A live maintainer objection on scope (target-neutral vs host-target rooting) caps the decision at `ABSTAIN_POLICY:CHALLENGER_CONCERN`; green CI answers the regression hinge, not the design/scope question ([fix making class A inherit class B's latent bug is design-scope ABSTAIN, not benign equivalence](../learnings/1784665766341-approver-calibration-fix-making-classa-inherit-cla.md)).

**A PR that RELAXES or REMOVES a diagnostic poses a DESIRABILITY question the challenger cannot settle by cross-toolchain precedent — "matches GLSL/shaderc" ≠ desired Slang behavior.** On #12138 the challenger judged a `verifyComputeDerivativeGroupModifiers` relaxation "correct + principled" because it matched GLSL `local_size_*_id`/shaderc, and every bot agreed the code was sound — but maintainers CLOSED it unmerged: firing an error on the compile-time DEFAULT of an overridable spec constant is a deliberate safety/ergonomic choice (the default is what ships if nobody overrides), so "shaderc allows it" is evidence about GLSL's design, not Slang's. Correctness of the CODE does not establish correctness of the DECISION to relax. Flags that make it a maintainer design call, not a challenger call: the change deletes an error path (vs fixing wrong codegen); the justification is "tool X accepts it"; the rejected input is a compile-time-known default of a runtime-overridable value — any of these ⇒ lean ABSTAIN (CHALLENGER_CONCERN/OPEN_GAP) on the design question and say so in the notes, don't let a clean bot review + toolchain precedent round the challenger up (here the ABSTAIN agreed in direction but was withheld for the WRONG reason — CI/test, not design — which would have become a false-safe had CI been green) [[approver/challenger-miss] "matches GLSL/shaderc" ≠ desired Slang behavior — a compile-time diagnostic relaxation is a DESIGN call maintainers may reject even when the code is correct](../learnings/1784845286053-approver-challenger-miss-matches-glsl-shaderc-desi.md).

**#12119 OptiX SBT `__ldg` exclusion — an ABSTAIN(OPEN_GAP) that named the exact one-liner was vindicated end-to-end, and the merged-join calibration itself needed a correction.** The 4-revision arc ran R1/R2 WOULD_APPROVE → R3 ABSTAIN_POLICY(OPEN_GAP) → R4 WOULD_APPROVE → merged APPROVED (jkwak-work, independent). ## Merge-Join Calibration: Source-Verify Fixes, Substance-Equivalence, and the Multi-Revision False-Safe Guard (2026-07-23 fold)

Several merge-join calibrations sharpened how a shadow verdict is scored against the human outcome. The dominant rule: **verify a claimed fix in SOURCE at the settled head** — a fixer's later push can resolve a withhold, and a standing bot/Devin flag pointing at the now-fixed lines is REFUTED, not confirmed (the BLOCK→ABSTAIN→WOULD_APPROVE chain on #12125 was normal convergence, decided fresh each revision) ([verify a claimed fix in source at the settled head — a stale flag on fixed lines is refuted](../learnings/1784724233457-approver-challenger-verify-a-claimed-fix-in-source.md)). On merge joins where the merged head ≠ your recorded SHA, prove **substance-equivalence** by checksumming each head's own three-dot PR diff — master-merge commits move the head with zero change to the contribution, so the decision still holds; and `mergedBy ≠ author` + an independent APPROVED review = genuine agreement, not a self-merge ([WOULD_APPROVE vindicated — merged head byte-identical via master-merge syncs](../learnings/1784725443219-approver-human-agreement-would-approve-vindicated-.md)).

Withholds resolved by a human are **agreements, not conservative misses**: an ABSTAIN_POLICY on a standing `CHANGES_REQUESTED` that the maintainer later clears with a fresh APPROVED is the withhold working as designed ([ABSTAIN_POLICY on standing CR → human APPROVED = clean withhold resolution](../learnings/1784732395517-approver-human-agreement-abstain-policy-on-standin.md)), as is an ABSTAIN(OPEN_GAP) on an intended-but-design-undecided behavior that merges at your exact head with a formal Approve ([ABSTAIN(OPEN_GAP) on a maintainer-flagged design fork, then merged with a formal Approve = clean resolution](../learnings/1784756558331-approver-human-agreement-abstain-open-gap-on-a-mai.md)). Two mechanics guard the scoring: a mechanical CLA/rebase/re-author force-push does NOT auto-dismiss a standing `CHANGES_REQUESTED` — read the aggregate `reviewDecision`, not the individual review's `.commit_id` ([CLA/mechanical force-push does not clear a standing CHANGES_REQUESTED](../learnings/1784731375990-approver-challenger-cla-mechanical-force-push-does.md)); and because `record_human_verdict` maps the terminal APPROVED onto EVERY decided revision row, a BLOCK that the fixer resolves with *exactly your predicted fix* before an APPROVED merge is a clean hit, but the earlier buggy WOULD_APPROVE row on the same PR is coincidental noise — score each revision on its OWN commit's correctness ([BLOCK→fixer-applies-my-fix→APPROVED is vindication; guard the multi-revision false-safe](../learnings/1784765736898-approver-human-agreement-block-fixer-applies-my-fi.md)). ## Design-Fragility False-Safe + Temporary-Test-Disable Calibration (2026-07-28 fold)

Two more merge-join data points that sharpen the challenger bar from opposite sides. **The false-safe: PR #12098 (Memoize Val substitutions) WOULD_APPROVE but the author closed it unmerged for a redesigned successor #12106.** The challenger cleared "gap #4 — transient `substitutionCache`-pointer threaded on `SubstitutionSet`" as "undemonstrated future-proofing," but csyonghe's live COMMENTED review probed that exact wiring ("field appears never initialized to non-null — how is this supposed to work?") and the successor removed it entirely (environment-local cache).
