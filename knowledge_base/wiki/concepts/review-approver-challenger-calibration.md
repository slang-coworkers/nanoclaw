# PR-Approver: Challenger CI-Gate, Verdict Calibration & Human Agreement

# PR-Approver: Challenger CI-Gate, Verdict Calibration & Human Agreement

Once the deterministic clauses ([[wiki/concepts/review-approver-decision-procedure.md]]) pass and the review-doc verdict is parsed, Step 3 — the **adversarial challenger** — is where WOULD_APPROVE / ABSTAIN_POLICY(OPEN_GAP) / BLOCK are actually distinguished. The recurring theme: **the automated reviewers (production `github-actions[bot]`, CodeRabbit, Devin) do not build or run the test suites**, so a green review-doc verdict is blind to codegen-golden regressions, downstream-submodule breaks, and reachable release-asserts. The challenger's job is to pull the live CI check-runs, trace each red to cause, and read the source at the pinned head. This page collects the verified-BLOCK catches, the middle-rung ABSTAIN discriminators, the false-positive refutations, and the human-agreement calibration that validates the whole bar.

## TL;DR


## The core CI-gate class: a green review-doc is blind to test regressions

A repeating BLOCK class — vindicated across #11595, #12130, #12106-R1, #12141 — is a **verified, deterministic, PR-caused break of a pre-existing CI-gated test** that the review-doc rated only nits. The challenger must harvest **check-runs at head** (not the combined-status glance) and read the failing job's failing STEP. Concrete instances:

- **Downstream submodule shaders test-slang never compiles.** slang#12141 disabled the `vector<T,4>` `(vec2,T)`/`(T,vec2)` initializers via `static_assert(false)`; the primary review was 🟡 APPROVE_WITH_NITS and Devin clean, all `test-slang` legs green — but the bundled `external/slang-rhi` submodule ships `test-ray-tracing-clusters.slang` with `float4(attribs.barycentrics, 1.f)` (a `float4(float2, scalar)`), which now hits the new E41400. Only `test-slang-rhi` compiles it, and it was RED. Any change to `core.meta.slang`/`hlsl.meta.slang` that *narrows what compiles* must be assumed to break downstream code until CI proves otherwise ([[approver/challenger-miss-averted] disabling a core-module init overload breaks bundled slang-rhi submodule shaders that test-slang never compiles](wiki/learnings/1784270927259-approver-challenger-miss-averted-disabling-a-core-.md)).
- **Diagnostic-forwarding surfaces previously-swallowed warnings.** slang#12141 R2's `forwardDiagnostics()` on the constructor SUCCESS path re-emitted a long-standing `warning[E30081]` that broke pre-existing `tests/glsl/integer_pack.slang (vk)` — blast radius = *every input that already triggered that swallowed diagnostic*, living in tests that assert empty stderr. Critical calibration: a `.slang (vk)` test shows `conclusion=success` on a GPU-less runner because it is **`ignored`/skipped, not passed** — only a completed leg WITH the GPU counts ([[approver/challenger-miss-averted] a diagnostic-forwarding refactor that surfaces previously-swallowed warnings can break pre-existing empty-stderr tests](wiki/learnings/1784304367382-approver-challenger-miss-averted-a-diagnostic-forw.md)).
- **A sanitizer-only link break.** slang#12136's new unit test touched the polymorphic internal `Slang::Session` via `asInternal()`; under `-fno-rtti` + the sanitizer's `-Wl,--no-undefined` the lazy-undefined `typeinfo for Slang::Session` became a hard link failure — RED on ONE of ~12 lanes only, so a per-lane check-runs scan is essential, and the leading `DWARF error: FORM value: 0x23` is benign noise (grep for `undefined reference|typeinfo`) ([[approver/challenger-miss-averted] A new unit test touching the polymorphic internal Slang::Session (via asInternal()) fails to link ONLY in the sanitizer job — -fno-rtti + -Wl,--no-undefined turns a lazy-undefined typeinfo into a hard build break](wiki/learnings/1784271192351-approver-challenger-miss-averted-a-new-unit-test-t.md)).
- **A generic-predicate revision widens blast radius.** slang#12111 R1 approved a Layer-B fix (coalesce descriptor-heap loads in the SPIR-V legalizer, dominance-by-construction). The `synchronize` re-implemented the SAME fix as Layer A (make any `UniformConstant` load movable in the generic `isMovableInst`, so CSE collapses them) — reviewer-directed and Devin-clean, but it regressed unmodified `intrinsic-texture.slang.6/.7/.8` goldens because the predicate ALSO fires on plain sampler globals. A "move the same fix to a more generic layer" revision is a materially different change with a different blast radius → full fresh challenger + a live CI diff-vs-master, never a rubber-stamp ([[approver/challenger] Same-fix Layer-A (generic CSE) revision needs a fresh CI probe — broader blast radius than the Layer-B head you approved](wiki/learnings/1784328018356-approver-challenger-same-fix-layer-a-generic-cse-r.md)).
- **A data-submodule pointer bump can turn CI red on UNTOUCHED tests — the review doc is blind to it.** slangpy#1082 had a clean-ish review doc (0 bugs, Devin nothing) but 6/12 build jobs red: unchanged `test_dds_file.cpp` threw "No such file" for `bc7-unorm-{nonsquare,3d}.dds` because the PR bumped the `data` submodule `4c24c797`→`6ecdf7c` and the new data commit had *removed* those fixtures. Treat any `160000`-mode / `Subproject commit` hunk as a first-class review surface: `require_ci_green=false` means the clause PASSES over red CI so look at the actual check-runs, pull a failed job log, and diff the submodule tree across the two refs (`gh api repos/<data-repo>/contents/<dir>?ref=<old>` vs `?ref=<new>`, or 404-probe the missing file) to attribute the break — a real trigger + real blast radius + no verified *code* 🔴 = ABSTAIN_POLICY:OPEN_GAP, never approve over red CI you've tied to the PR's own change ([[approver/challenger-ci-gate] Data-submodule bump can turn CI red on UNCHANGED tests — always diff the submodule tree](wiki/learnings/1785426143619-approver-challenger-ci-gate-data-submodule-bump-ca.md)). The fix is symmetric and confirmable: on the re-review synchronize the author pushed one commit "Restore data submodule" reverting the pointer, `gh compare old...new` showed exactly ONE changed file (`data`), the restored ref contained the two fixtures again, and CI settled green 12/12 — a green re-run on a byte-identical-except-data diff cleanly retires that specific OPEN_GAP (but only after CI fully settles; don't decide on in-progress runs) ([[approver/challenger-ci-gate] Confirmed: reverting a data-submodule bump restores fixtures and turns CI green — the fix for the #1082-class OPEN_GAP](wiki/learnings/1785495128502-approver-challenger-ci-gate-confirmed-reverting-a-.md)). The mirror-image trap on the same PR: a later `synchronize` that is a *merge of `main`* touched only unrelated files (texture_loader, a device test, CMakeLists) and left the flagged `torch_bridge_impl.cpp` byte-identical — so the prior Devin 🔴 recurred verbatim. "New push" ≠ "concern addressed": compute `gh api compare/<prevhead>...<newhead>`, and if the flagged path isn't in the delta the prior code-level disposition stands — say so and name what WOULD move it (a change to the flagged file, or a human sign-off) ([[approver/challenger-ci-gate] A main-merge synchronize can't clear a code-level 🔴 — diff the two heads before assuming the push addressed it](wiki/learnings/1785496402847-approver-challenger-ci-gate-a-main-merge-synchroni.md)).


## Attribution: a PR that EXPOSES a pre-existing defect by changing global behavior owns it

On slang#12089 rev6 a capability-narrowing PR flipped the default HitObject type on `sm_6_9+hlsl_nvapi` from NVAPI to native `dx::HitObject`, but four LSS accessors keyed on a *different* capability were NOT re-gated → mixed-ABI HLSL, the exact defect class the PR exists to eliminate. The buggy lines are pre-existing and untouched — tempting to downgrade to ABSTAIN "latent" — but the PR is the *proximate cause*: it transformed those methods from matched-at-base to mixed-at-head by changing the type-selection predicate. A defect a PR exposes by changing global behavior is attributable → BLOCK ([[approver/challenger] A capability-narrowing PR can EXPOSE pre-existing mixed-ABI on sites it doesn't touch — flipping the default type re-gates behavior of unedited methods (attributable → BLOCK)](wiki/learnings/1784310133019-approver-challenger-a-capability-narrowing-pr-can-.md)). The transferable check on any capability-narrowing / default-flipping PR: enumerate ALL methods on the affected type, not just the arms in the diff — a method whose `case hlsl:` emits a vendor intrinsic but is callable regardless of the resolved ABI is a mixed-ABI candidate under the new default.


## Reachable RELEASE_ASSERT is a RED_BUG — prove reachability at the producer

slang#12147's `SLANG_RELEASE_ASSERT(debugArtifactCount == 1)` aborts slangc on valid multi-entry-point input, while its sibling validator `_validateCoverageManifestOutputPaths` handles the same `>1` case with a graceful diagnostic — the asymmetry between two sibling validators is the smell ([[approver/challenger] RELEASE_ASSERT on a reachable multi-artifact count is a RED_BUG, not a valid impossible-shape guard](wiki/learnings/1784316403221-approver-challenger-release-assert-on-a-reachable-.md)). The subtle part is the *trigger*: for a SINGLE SPIR-V target slang forces whole-program (count==1) on every path (no-`-o` synthesizes a stdout output gated on `m_rawTargets==1`), so the assert is reachable **only via multi-target ≥2 entry points + no per-target `-o`**, which sidesteps the single-target synthesis guard ([Slang separate-debug-info: multi-target demotes SPIRV out of whole-program → per-EP debug artifacts abort the count==1 assert](wiki/learnings/1784336687356-slang-separate-debug-info-multi-target-demotes-spi.md) on the compiler-internals page). The recall subagents AND the production bot all CONVERGED on a wrong single-target trigger — **convergence is not correctness** — and a DECISION_REVIEW critique that adversarially hunts the gate the finders missed is what caught it; run it whenever the challenger overrides a lenient doc verdict on a reachability argument ([[approver/challenger-miss] single-vs-multi-target whole-program forcing hides the reachable RELEASE_ASSERT trigger](wiki/learnings/1784333455962-approver-challenger-miss-single-vs-multi-target-wh.md)).


## The middle rung: green CI can still be a hold (ABSTAIN / OPEN_GAP)

A green-CI revision that fixes only the *symptom* rather than *scoping the root change* is a hold, not a WOULD_APPROVE. slang#12141 R3 added explicit casts to the ONE test E30081 broke, but left the over-broad `forwardDiagnostics()` unchanged — the latent surface remains for every other/future consumer, and a `diagnoseRaw` re-emission bypasses per-id `-Wno-*`/`#pragma warning` suppression by construction. Two challenger checks CI cannot do: did the fix scope the root change or just silence the symptom, and does the re-emission bypass user suppression → `ABSTAIN_POLICY:OPEN_GAP` (verified over-broad, plausible trigger, real blast radius, not false-negative-safe), the rung between BLOCK (no reproduced 🔴) and WOULD_APPROVE ([[approver/challenger-miss-averted] a test-cast workaround fixes the broken test but not the over-broad change; scope+suppression-bypass gaps are CI-invisible WOULD_APPROVE→ABSTAIN discriminators](wiki/learnings/1784309271831-approver-challenger-miss-averted-a-test-cast-worka.md)). The calibration across one PR's three revisions — BLOCK (rhi break) → BLOCK (E30081 regression) → ABSTAIN/OPEN_GAP (contained but one latent scope gap) — shows the approver's job is to track the residual, not rubber-stamp "the last thing I flagged is fixed."


## When a gap CLEARS: is the worst realistic failure a build break CI catches, or a silent miscompile it wouldn't?

The decisive discriminator for clearing a speculative gap is the *failure class*. For a **build-flag / optimization-level PR** whose only risk is a CI-visible `-Werror` build break, complete + green CI on the exact affected config legs is sufficient to clear it — the failure would be a build error, not a silent runtime miscompile. slang#12140 (`-Og` for GCC/Clang debug) cleared a "`-Wmaybe-uninitialized` might break `-Werror`" gap because the affected debug legs were green at head, `-Wmaybe-uninitialized` is GCC-only (the "macOS Clang" framing was misdirected), and the blast radius is Debug+GCC/Clang only ([[approver/calibration] build-flag PR: clear a "-Werror CI break" gap by checking the affected config is actually green](wiki/learnings/1784270606102-approver-calibration-build-flag-pr-clear-a-werror-.md)). Two extensions of the rule: a **subtractive guard** (`AND NOT MSVC`) relative to a prior CLEAN head can only *remove* a flag, never add it → cannot regress prior-green, so the verdict is ≥ prior without re-derivation; and a warning-coverage gap on a **pure-cmake PR that adds zero C++** clears as *future-proofing* (the PR introduces no uninitialized-variable risk itself) ([[approver/calibration] -Og debug-build guard: subtractive NOT-MSVC guard can't regress prior-green; -Wmaybe-uninitialized gap clears as future-proofing when PR adds no C++](wiki/learnings/1784288671711-approver-calibration-og-debug-build-guard-subtract.md)). Contrast codegen/logic PRs where green CI ≠ safe — a miscompile passes all tests.

**False-negative-safe-by-construction exemptions approve.** For a diagnostic-suppression PR, don't ask "could this hide a bug?" in the abstract — trace the diagnostic's *fire conditions*. slang#12011's E41017 `__extern_cpp` exemption is safe because `checkUninitializedGlobals` only fires when a global has no in-module init AND no store, and the exemption predicate (`IRExternCppDecoration` + external linkage) is a strict subset of the documented host-provided-global pattern (value comes from outside the module by design) — plus a discriminator test proves the predicate is narrow ([[approver/calibration] E41017 __extern_cpp exemption is false-negative-safe by construction — approve the class](wiki/learnings/1784288118508-approver-calibration-e41017-extern-cpp-exemption-i.md)).

A recurring backend-guard instance of the same class: wrapping ONE `[shader]` entry point of a shared multi-entry Slang test module in `#ifndef __TARGET_CUDA__` so the module stays loadable on CUDA for its siblings (Slang capability-checks all entry points at load time, so one unsupported `Buffer<T>`/`RWBuffer<T>` entry under E36107 takes the whole module down). Don't approve on the diff alone — two probes make it airtight: (1) **structural containment** — read the full file at head to confirm the `#ifndef`/`#endif` wraps ONLY the target entry point, no sibling accidentally stripped; and (2) the load-bearing **skip-before-load ordering** — the PR claims "no coverage loss because the guarded variant is already `pytest.skip`-ed on CUDA", so VERIFY the skip fires *before* the `load_program(..., ["copy_"+type])`; if it were after, stripping the entry point would turn a clean skip into an "entry point not found" error (a regression, not a no-op). On slangpy#1083 the skip at `test_buffer.py:76-77` precedes the load at L118-120, the macro was real in-repo precedent, and non-CUDA backends keep the entry point → WOULD_APPROVE on the Devin-only tier (production skips bot fixer branches → harvest exit 20) ([[approver/challenger-clean] CUDA preprocessor-guard on a shared Slang test module — verify skip-before-load ordering](wiki/learnings/1785453364629-approver-challenger-clean-cuda-preprocessor-guard-.md)). This was CONFIRMED by merge: jkwak-work left a formal APPROVED and merged at the EXACT R2 head `a31e8af8` with zero follow-ups — clean agreement. A verdict-state nuance worth carrying: the human signal *evolved* (R1 COMMENTED "Looks good to me." + a nit → R2 APPROVED after the nit was addressed), and only the final state is the calibration truth — an early COMMENTED/LGTM is directionally positive but NOT a formal approve; always join the verdict to the commit it was submitted against and re-check reviews at the merged head ([[approver/challenger-clean] CONFIRMED by merge — CUDA preprocessor-guard on shared test module (slangpy#1083)](wiki/learnings/1785462075111-approver-challenger-clean-confirmed-by-merge-cuda-.md)).

**Constness-selected SPIR-V operands: trace the *emitted* form.** slang#12133's Gather const-offset fix emits `ConstOffset` (legal only if the offset is an `OpConstant`/`OpConstantComposite`). "The helper detects constants" is not enough — verify the constant-hoisting pass (`maybeHoistConstructInstToGlobalScope`) actually moves the accepted shapes to global scope and that the classifier's accepted set ⊆ the hoister's hoistable set; when the PR's test is spirv-asm-only (no real `spirv-val`), this inspection IS the validation gate ([[approver/challenger] ConstOffset-safety hinges on constant-MakeVector hoisting (maybeHoistConstructInstToGlobalScope), verify it — slang#12133](wiki/learnings/1784334175709-approver-challenger-constoffset-safety-hinges-on-c.md)).


## Real-hardware CI can substitute for a missing Devin — but only if it actually EXERCISED the code

On the slang-rhi fallback tier, slang-rhi runs the full test suite *inline in the build matrix on real GPU adapters*, so a timed-out Devin on a behavior-changing PR (#797 D3D12 timestamp resolve) doesn't force ABSTAIN — pull the CI *job logs* and grep for the PR's new test executing + PASSING on a real adapter (`hardware-device`, not `software-device`/`SKIPPED`) ([[approver/human-agreement] slang-rhi real-hardware CI substitutes for a timed-out Devin on backend-logic PRs](wiki/learnings/1784271405834-approver-human-agreement-slang-rhi-real-hardware-c.md)). The mirror-image trap: a **support-claiming PR whose test is masked-out is compile-only, never executed**. slang-rhi#800 flipped `docs/api.md`'s Metal `dispatchComputeIndirect` cell to `yes` and added real Metal code with green CI — but the feature's `GPU_TEST_CASE(..., D3D12 | Vulkan | CUDA)` *excludes Metal*, so the macOS job compiled but never ran the new path; green CI proves it builds, not that it works → a genuine `OPEN_GAP` for a support-claiming PR ([[approver/clause-gap] Backend-support PR that flips a docs support-matrix cell but leaves the feature's test masked-out is compile-only, never executed](wiki/learnings/1784338875078-approver-clause-gap-backend-support-pr-that-flips-.md)). And CI green in a decoupled component (a standalone Go tool in `extras/scaler` that no CMake/CI job builds) is *orthogonal* — it can't substitute for a missing review signal the way real-hardware CI does.

The masked-out-test class recurs even when the PR SHIPS a test: slang-rhi#801 (native Metal buffer import) shipped `test-buffer-from-handle.cpp` that calls the new Metal code, but its device mask was `GPU_TEST_CASE("buffer-from-handle", D3D12 | Vulkan)` — `Metal` omitted, so `GPU_TEST_CASE` (which registers one case per flagged device) registers NO Metal case, and the macOS job compiled but never executed the import path. (⚠️ The original write-up said the macOS runner "DOES run `-check-devices` on Metal hardware" — **withdrawn as stated**: the hosted `macos-latest`/`macos-26-arm64` adapter is an `Apple Paravirtual device`, and until slang-rhi#807 restored Metal device init it reported Metal *unsupported* and skipped every Metal case. A mask is a declaration of intent; whether a case runs is decided by the runner the job lands on ([[approver/challenger-miss] test-mask registration is not test execution — resolve the job's `runs-on` and open a log](wiki/learnings/1785787084796-approver-challenger-miss-test-mask-registration-is.md)).) The `checkNoSilentGpuSkips()` guard doesn't catch it — it only flags a device with registered-but-zero-running tests, not a device with zero registered cases. So for any slang-rhi backend-specific PR, don't stop at "a test exists": **grep the test's `GPU_TEST_CASE(...)` mask and confirm the PR's target backend flag is IN it** — a Metal-only change tested only under `D3D12 | Vulkan` is OPEN_GAP (source-verified-correct doesn't round it up), same class as #800; next-action = add `Metal` to the mask or consciously accept the untested-on-Metal risk [[approver/challenger] slang-rhi Metal-only feature with test masked to D3D12|Vulkan = OPEN_GAP](wiki/learnings/1784816143760-approver-challenger-slang-rhi-metal-only-feature-w.md).

A THIRD zero-coverage mode is compile-out via an unmerged-companion-ABI gate, distinct from both the runtime SKIP and the masked-out-test. slang-rhi#803 (CPU ray query) shipped a 1120-line impl + dedicated CPU tests + 30 CTS cases, but the whole CPU path — impl AND tests — is *compiled out* in merge-gating CI: the feature is gated behind `SLANG_RHI_ENABLE_CPU_RAY_QUERY`, whose default hinges on the fetched Slang package shipping `prelude/slang-cpp-ray-query.h`, a header that only exists in an OPEN companion PR (slang#12282) and is absent from the pinned `v2026.12.2` release → ABI_AVAILABLE=OFF → the test file is `target_sources`-gated out and the CTS device mask degrades `CPU|D3D12`→`D3D12`. So for any slang-rhi feature behind a `cmake_dependent_option` whose default hinges on a Slang-package header/ABI, check whether that header ships in the pinned `SLANG_RHI_FETCH_SLANG_VERSION`; if it only lives in an unmerged companion, the code+test are excluded from the build (compiled out, not merely runtime-SKIPPED), and the "CPU runs headlessly" counterweight must NOT round up — this is an OPEN_GAP, compounded here by fork-PR CI sitting at `action_required` (never ran) ([[approver/challenger] slang-rhi feature gated on unmerged companion Slang PR compiles out in CI — zero-coverage distinct from Metal-SKIP](wiki/learnings/1785395617012-approver-challenger-slang-rhi-feature-gated-on-unm.md)). But when arguing "compiles out", verify it per-file/per-symbol, not categorically: a MIXED CMake toggle excludes only SOME files as whole `target_sources` while others compile UNCONDITIONALLY with internal `#ifdef`s — on #803 R2 the claim "all the feature's code is gone" was caught overbroad, because only `cpu-acceleration-structure.cpp` was whole-file-excluded while `cpu-command.cpp`'s flagged `cmdQueryAccelerationStructureProperties` compiled regardless of the toggle. `grep -n <file> CMakeLists.txt` to distinguish whole-source exclusion from internal-`#ifdef`, open the specific flagged line to confirm IT is inside the guard (count of macro occurrences is not enough), and state "compiled and registered" not "would exercise" unless the CI device is confirmed to run it — a subtly-false "don't worry, it all compiles out" premise could make a human dismiss a live finding ([[approver/challenger-miss] "compiles out" on a partially-gated feature must be verified per-file/per-symbol, not asserted categorically](wiki/learnings/1785416472140-approver-challenger-miss-compiles-out-on-a-partial.md)).


## Combined-status ≠ causal: classify from individual check-runs traced to cause

The GitHub combined commit-status aggregates ALL contexts including non-causal cross-repo/downstream jobs. On the clean front-end PR #12131 combined-status was `failure` from a `test-falcor` image-diff flake (from a prior draft run) and a `SlangPy Tests` `test_profiler.cpp` CPU-timing assertion (Linux-only, passed on Windows) — neither reachable by the PR's code path ([[approver/calibration] combined-status-failure-from-non-causal-downstream-flakes](wiki/learnings/1784329341037-approver-calibration-combined-status-failure-from-.md)). When `require_ci_green:false` defers, enumerate individual check-runs `--paginate`, confirm the repo's OWN core legs (especially the one running the PR's new tests) are `success`, and for each red trace the failing test — platform-asymmetric / timing / image-diff / downstream-renderer failures are non-causal-flake signals. The rule is symmetric: classify from check-runs traced to cause, never from combined-status alone, in EITHER direction (a green combined-status is equally untrustworthy — see #12130's metal-fmod miss). `SlangPy test_profiler.cpp` is a recurring non-causal flake for slang PRs.


## A stale secondary reviewer flags the pre-fix state — verify at head

On slang#12147 R4 (the fix revision) Devin ran ~5 min after the push and flagged the R1-R3 blocking bug verbatim at `:766` — but the assert was already gone; Devin analyzed a stale/cached snapshot, and its line number had shifted meaning across the revision (`:766` was now a harmless guard, the graceful diagnostic at `:798`) ([[approver/stale-secondary] Devin (secondary) reviews the pre-fix prefix state on a fresh-push revision — verify the flagged line against head source before trusting a bug flag](wiki/learnings/1784343479716-approver-stale-secondary-devin-secondary-reviews-t.md)). Never accept a secondary bug flag on faith on a fresh-push revision: the PRIMARY tier harvested at the pinned head (matching `diff_hash`) is the verdict source, and open the flagged `file:line` at the pinned head, locating the construct by NAME not line. This is the flip side of the false-positive class below — a secondary flag is a hypothesis to verify at head, never a standalone reason to hold a BLOCK.
