# Slang Test Harness — Running slang-test, False Greens, and Verification Discipline

> **Part 2 of 3** of the Slang Test Harness synthesis (split 2026-08-08 to stay under the 40 KB read cap). Siblings: [part 1](slang-misc-test-harness.md) · [part 3](slang-misc-test-harness-3.md).

This part covers **running the harness and trusting its result**: the test-server false-green cluster, verbosity and reporter config, unit-testing harness internals, and the verification discipline (stale binaries, positive controls, discriminating tests) that keeps a green run from being meaningless. Directive authoring is in [part 1](slang-misc-test-harness.md); FileCheck mechanics are in [part 3](slang-misc-test-harness-3.md).

## TL;DR

- **Run `slang-test` from the repository root.** Parallel form: `./build/Release/bin/slang-test -use-test-server -server-count 8`. Single test: `slang-test tests/path/to/test.slang`. Unit tests: `slang-test slang-unit-test-tool/`.
- **Never use `$?` as the pass/fail signal — `slang-test`'s process exit code was 0 on a FAILED test.** Parse the `FAILED test:` / `% of tests passed` lines.
- **A unit test that crashes the test server was reported PASSED pre-PR #11753** (RPC death leaves `ExecuteResult resultCode=0` → Pass), so a test that "starts failing after #11753" is **crashing the server**; that PR only changed reporting.
- **The unit-test retry path in test-server mode also reports failures as passes (#11911)** — a green merge-queue or per-PR gate does **not** certify C++ unit-test health.
- **Device caching in `slang-test` silently defeats per-invocation debug-callback bridges** — a cached device reuses the prior callback wiring, so per-invocation regressions go undetected as false greens.
- **`slang-test` can crash at startup in-container while direct `slangc` runs fine** — don't read a harness crash as a compiler failure.
- **For a GPU-free test that must exercise real RHI device code (not a mock), create a real CPU-backend device inside a `gfx-unit-test` `SLANG_UNIT_TEST`.**
- **`-v failure` did not suppress passing tests in parallel (#12177)**: per-worker reporters kept the ctor-default verbosity. Fold reporter config into `TestReporter::init(const Options&)` so main and workers configure through one path.
- **CI greps `Supported backends:` at DEFAULT verbosity, so never suppress backend discovery unconditionally** — gate it on `verbosity >= Info`, accumulate names pre-parse and print after `Options::parse`, and leave `Not Supported` ungated.
- **The harness IS partially unit-testable** — specific `tools/slang-test/*.cpp` files are already compiled into `slang-unit-test`. Check field accessibility before accepting "monolithic, verify behaviorally" as a skip.
- **To unit-test an internal unexported `namespace Slang` free function, extract it into its own small self-contained TU** and add that TU to `slang-unit-test`'s `target_sources`. Do not export the symbol and do not add the heavy owning `.cpp`.
- **Replay recording folders collide under parallel test-servers** — the shared base dir plus a no-PID millisecond timestamp; a per-process base dir fixes the CI flake, collision-resistant names alone do not.
- **Prove the relink before reporting numbers: require `test_binary_mtime > build_start`.** A build exiting 0 can rebuild nothing, and a stale binary *passes* the very test you are validating.
- **Re-run suite pass-counts yourself for a PR body** — don't transcribe a build subagent's number.
- **Re-run any subagent's cited reproducer yourself, and anchor IR greps to the TYPE** (`kIROp_PseudoPtr`, `= *pseudo_ptr(`) so they can't match a mangled symbol name.
- **Negative-control every branch-coverage claim**: neuter the target branch, rebuild, re-run. If the test still passes, it does not isolate that branch — drop it rather than shipping it.
- **One positive control per HAZARD, not per fix.** When a fix converts leak into double-release, removing the fix proves nothing about the new mode; sabotage the specific new guard (`if (owned)` → `if (true)`) and extend the test so it has something to trip on.
- **Count assertion-bearing tests (a `//TEST:` directive plus CHECKs), not test files, and name which test carries the proof.** Support fixtures are inputs, not coverage.
- **Ask: in my test's configuration, does the fallback path produce the same answer as the fix?** If yes, that test cannot distinguish fixed from broken however precise its assertions look — construct the case where fallback and correct answer differ, and say in the PR that it is the discriminator.
- **A worktree-cleanliness-guard trip is not always author hygiene** — it can be the downstream symptom of a deterministic test that crashed mid-run. Grep the SAME run's log for `FAILED test:` / `COMPILE ERROR` / crash first.
- **`DIAGNOSTIC_TEST(diag=CHECK)` does catch a crash→diagnostic regression via empty stderr** (zero diagnostics fails the exhaustive check) — but only when diagnostic and crash are mutually exclusive. If the crash is downstream of the diagnostic, add a `SIMPLE` test asserting `result code = N`.
- **A fatal diagnostic suppresses codegen, so positive-compilation cases must live in a separate file.**
- **Stale auto-generated test bundles in `docs/generated/tests/` are usually compiler-driven** (diagnostic-text drift, IR mangled-name drift), so `regenerate.py list-stale` won't detect them. No hand-editing — route to the regeneration workflow.
- **A test shim for `ISlangSharedLibraryLoader` must match the bare logical name** (e.g. `"slang-llvm"`) — platform decoration happens after your shim sees the path.
- **Suspect RPC timeout and workload sizing before escalating a flaky test to a concurrency-contract design.**
- **A VM opcode validator and its executor must agree on the operand-section size convention**, or validation passes and execution crashes.
- **Treat two distinct flake signatures on one test file separately** — never label one "dominant" using the other's occurrence history.

## False Greens: Test-Server Crashes Reported as Pass

A unit test that crashes the test server is reported **PASSED** pre-PR #11753 ([slang-test false-green: a unit test that crashes the test-server is reported PASSED (#11751)](../learnings/1782398466162-slang-test-false-green-a-unit-test-that-crashes-th.md)). The root cause: an RPC/connection death leaves `ExecuteResult` at its default `resultCode=0` which maps to Pass. PR #11753 fixes slang-test to record RPC failures as Fail — so a test that "starts failing after #11753" is actually crashing the test server; the PR only changed reporting ([slang-test RPC-failure reporting (#11753): 'fails after the fix' ⇒ test-server crash](../learnings/1782397269166-slang-test-rpc-failure-reporting-11753-fails-after.md)).

## test-server retry false-green (#11911) — verify behaviorally; merge-green ≠ unit-test health

The unit-test retry path silently reports failed tests as passing in test-server mode (#11911), extending the false-green cluster (#11751/#11753) ([1783009679066-slang-test-test-server-retry-false-gre](../learnings/1783009679066-slang-test-test-server-retry-false-green-11911-gh-.md)). Fix these behaviorally, not by reading code — the Defect-A registry-drain repro is platform-dependent ([1783013967417-slang-test-harness-false-green-fixes-v](../learnings/1783013967417-slang-test-harness-false-green-fixes-verify-behavi.md)). Consequence for the whole fleet: **a green merge-queue / per-PR CI gate does NOT guarantee C++ unit-test health** until the #11911 fixes land (fix PR #11913 still open as of 07-05) ([1783239972308-slang-merge-queue-green-c-unit-test-he](../learnings/1783239972308-slang-merge-queue-green-c-unit-test-health-test-se.md)).

## slang-test verification traps: startup crash, device-cache false-greens, GPU-free CPU device

Several verification traps recur. (1) `slang-test` can crash at startup in-container while direct `slangc` runs fine — don't read the harness crash as a compiler failure, and beware a codex "revert-without-rebuild" false positive where the old binary is still on disk ([Slang verify gotchas: slang-test crashes at startup in-container; codex revert-without-rebuild false positive](../learnings/1782819445679-slang-verify-gotchas-slang-test-crashes-at-startup.md)). (2) Device caching in `slang-test` silently defeats per-invocation debug-callback bridges, producing **false greens** — a cached device reuses the prior callback wiring, so a regression in per-invocation setup goes undetected (regression from PR #11785) ([Device caching silently defeats per-invocation debug-callback bridges in slang-test (false greens)](../learnings/1782862613084-device-caching-silently-defeats-per-invocation-deb.md)). (3) For a GPU-free regression test that must exercise **real** RHI device code (not a mock), create a real **CPU-backend** device inside a `gfx-unit-test` `SLANG_UNIT_TEST` ([GPU-free render-test regression via a real CPU device in gfx-unit-test](../learnings/1782871389928-gpu-free-render-test-regression-via-a-real-cpu-dev.md)).

## slang-test -v Failure Verbosity Drift (#12177) + The Harness IS Partially Unit-Testable (2026-07-22 fold)

**`slang-test -v failure` still printed passing tests in parallel and always printed backend/render-API discovery — two independent causes, both in `tools/slang-test` (#12177).** (1) Worker-reporter config drift (same class as #11911): the single-run main reporter sets `m_verbosity` inline, but `runTestsInParallel`'s per-worker `TestReporter` only calls `init(...)` and keeps the ctor-default `Info`, so the `if (m_verbosity < Info)` passing-test gate never suppresses. The principled fix folds reporter config INTO `TestReporter::init(const Options&)` so main + workers configure through one path — killing the drift class for good (a new `slangTestReporterInitFromOptions` unit test pins it). (2) Ungated discovery: the `Supported backends:` block and `_getAvailableRenderApiFlags` `Check <api>:` prints write via raw `StdWriters::getOut()`. LOAD-BEARING gotcha: CI greps `Supported backends:` at DEFAULT verbosity (`common-test-setup/action.yml:94`), so gate discovery on `verbosity >= Info` (suppress only under Failure) — unconditional suppression breaks CI backend detection ([slang-test -v failure ignored in parallel + capability discovery; CI parses discovery output](../learnings/1784656410724-slang-test-v-failure-ignored-in-parallel-capabilit.md)). The merged fix (PR #12180, `Closes #12177`) added two triage-memo corrections worth carrying: a **pre-parse TIMING gotcha** — the `Supported backends:` block prints 70 lines BEFORE `Options::parse`, so an in-place `>= Info` gate is a no-op under `-v failure`; accumulate names pre-parse and print them gated AFTER parse (the `Check <api>:` prints are fine to gate in place, all post-parse) — and **`Not Supported` stays UNGATED** per maintainer review, since a missing backend is signal a `-v failure` user needs ([#12177 CLOSE-OUT: pre-parse timing + Not-Supported stays ungated](../learnings/1784683587359-12177-close-out-slang-test-verbosity-fix-merged-me.md)).

**The slang-test harness IS partially unit-testable — the "monolithic, verify behaviorally" blanket is overstated.** `tools/CMakeLists.txt:421` compiles `tools/slang-test/test-output-path-util.cpp` INTO the `slang-unit-test` module, with existing precedents (`unit-test-slang-test-output-path.cpp`, `unit-test-slang-test-optimization-options.cpp`) — so specific slang-test source files are already cross-compiled and unit-tested with no GPU/process spawn. Correct rule: the stdout/reporting-flow behavior (parallel worker output) still has no clean unit form, but a slang-test internal with public fields and a plain-struct input (e.g. `TestReporter::init(const Options&)`) CAN carry a `SLANG_UNIT_TEST` regression guard — add the .cpp to `slang-unit-test`'s `target_sources`, construct a non-default `Options`, call `init`, assert propagation. Don't accept "harness is monolithic, no test possible" as a blanket skip on a config-propagation fix — check field-accessibility first ([slang-test harness IS partially unit-testable (corrects "monolithic, verify behaviorally")](../learnings/1784664553168-slang-test-harness-is-partially-unit-testable-corr.md)).

## Replay-Recording Folder Collision Under Parallel Test-Servers (2026-07-24 fold)

`#12214`: the record-replay system's recording-folder naming has a parallel-process race with two facets. The *observed CI flake*: all replay unit tests share the relative base dir `.slang-replays-test`, and `ReplayContext::findLatestReplayFolder()` lists+sorts EVERY directory under the base with NO per-process ownership filter and returns `.getLast()` — so under `slang-test -use-test-server -server-count N` another concurrent test-server's lexicographically-newer folder gets returned, failing the `secondPath.endsWith(latest)` assertion (~15/96 forced runs). The *latent production collision* (same code): `generateTimestampFolderName()` is millisecond-precision with no process-unique component and combines with the shared base via a non-exclusive `Path::createDirectoryRecursive`, so same-ms recorders open the same `stream.bin`/`index.bin` — and this touches the production `.slang-replays` path too, since `findLatestReplayFolder` backs `loadLatestReplay()`. Fix directions at their layers: (A) collision-resistant names (append PID via existing `Process::getId()` + atomic-create-with-retry), (B) per-process test base dir `.slang-replays-test-<pid>` with cleanup — **B alone fixes the CI flakiness; A alone does NOT; A+B is the principled full fix.** Not a regression (latent since the initial replay system #9925). Method note: jkwak-work self-filed AND self-assigned → PARK-at-triaged, no auto-dispatch to fixer per standing directive ([Slang replay recording folders collide under parallel test-server processes (no PID in name)](../learnings/1784895262564-slang-replay-recording-folders-collide-under-paral.md)).

## Agentic Test Bundle Staleness

Stale auto-generated test bundles in `docs/generated/tests/` are often caused by **compiler diagnostic/IR changes**, not doc changes, so `regenerate.py list-stale` won't detect them. Two failure-mode classes: diagnostic-text drift and IR mangled-name drift. No hand-editing is permitted; route to the bundle regeneration workflow ([Agentic-test bundle staleness is often compiler-driven and list-stale won't catch it](../learnings/1782217764152-agentic-test-bundle-staleness-is-often-compiler-dr.md)).

## Shared Library Loader Test Shims

When writing a test shim for `ISlangSharedLibraryLoader`, match against the **bare logical name** (e.g. `"slang-llvm"`) because platform decoration happens inside `DefaultSharedLibraryLoader` after your shim sees the path — the bare name is identical on all platforms ([Slang loads downstream libs by logical name — test shims match the bare name cross-platform](../learnings/1780324906216-slang-loads-downstream-libs-by-logical-name-test-s.md)).

## Slangi VM: Validator and Executor Must Agree

When a VM opcode validator special-cases an operand's section (e.g. treating `kSlangByteCodeSectionStrings` as `sizeof(const char*)`), the executor for that opcode must mirror the same convention. Asymmetry causes validation to pass but execution to crash (e.g. printf with `%s` and string literals) ([Slangi VM validator and executor must agree on operand-section size convention](../learnings/1780413778599-slangi-vm-validator-and-executor-must-agree-on-ope.md)).

## Unit-testing an internal (unexported) free function: own-TU + dual-compile, not export (2026-07-27 fold)

When a `slang-unit-test` case needs to call an internal `namespace Slang` free function with no `SLANG_API`/visibility export, it will NOT link — the test module links `libslang-compiler.so` with `-Wl,--no-undefined`, so an unexported symbol is a hard `undefined reference` (hit on #12220 for `classifyCommandLineOption`/`writeCommandLineArgs`). Do NOT export the symbol (ABI creep the maintainers avoid), and do NOT add the whole owning `.cpp` to the test module (its heavy deps cascade into their own undefined references). The established pattern (mirrors `tools/CMakeLists.txt`'s treatment of `slang-repro-validator.cpp`): extract the function into its OWN small self-contained TU depending only on the type it needs — it auto-joins the DLL via the `slang_add_target` glob, and adding it to the `slang-unit-test` target's `target_sources(... PRIVATE ...)` recompiles the same source into the test module. No export, no DLL-boundary call. `slang-unit-test` has `INCLUDE_DIRECTORIES_PRIVATE ${slang_SOURCE_DIR}/source`, so the include is fine — the linkage is the only constraint; this only works if the extracted function is genuinely low-dependency, so design it that way [Unit-testing an internal (unexported) slang free function: own-TU + dual-compile, not export](../learnings/1785203787876-unit-testing-an-internal-unexported-slang-free-fun.md).

## Reproducer & Regression-Test Verification Discipline (2026-07-31 fold)

Three verification traps recur when a regression test or a subagent's repro is taken on faith. **(1) Negative control before trusting branch coverage.** A passing test meant to cover a *specific* code branch is not proof it exercises that branch — it may pass via a different always-present trigger. Temporarily neuter the target branch (e.g. `continue` instead of `return true`), rebuild, and re-run; if it STILL passes, the test doesn't isolate the branch. On PR #12281 a generic-empty-type test passed even with the `IRGeneric` branch of `hasEmptyTypeLegalizationWork` neutered — because any named empty struct is hoisted to module global scope and fires the struct-root scan regardless — so the misleading "generic coverage" test was dropped rather than shipped ([verify a test isolates its target branch with a negative control](../learnings/1785548777549-verify-a-test-isolates-its-target-branch-with-a-ne.md)). **(2) Re-run a subagent's cited reproducer yourself, and grep IR by TYPE not substring.** A subagent (Explore) reported a confident PseudoPtr reproducer it never actually ran — the source fails front-end E41019, and its "PseudoPtr count" came from `grep -i pseudo` matching the mangled *function name* `test_pseudo_ptr`, not `IRPseudoPtrType`. Always run the repro before trusting it, and anchor IR-type greps (`= *pseudo_ptr\(`, `kIROp_PseudoPtr`) so they can't match symbol/function names, sanity-checked against a known-positive line ([verify a subagent's reproducer by running it; grep the IR TYPE not a symbol substring](../learnings/1785548791828-verify-a-subagent-s-reproducer-by-running-it-grep-.md)). **(3) A worktree-cleanliness-guard failure can mask a real test failure.** A `slang-test left generated or modified files in the worktree` CI guard trip is not always benign author-cleanup — it can be the downstream symptom of a deterministic test that crashed/failed mid-run and left temp modules behind. On PR #12182 a leftover `moduleG6276.slang` was first classified as hygiene, but a fresh run exposed `optixMultipleDefinition.internal` failing deterministically on all three of linux-debug/release + windows. Grep the SAME run's test-slang log for `FAILED test:` / `COMPILE ERROR` / crash before stopping at "hygiene" — the severity flagged upstream can escalate from nit to a real multi-platform regression ([worktree-cleanliness-guard can mask a real test failure](../learnings/1785535887677-worktree-cleanliness-guard-can-mask-a-real-test-fa.md)).

## DIAGNOSTIC_TEST Caret Alignment + git-blame .mailmap Identity (2026-07-28 fold)

Two authoring gotchas for the slang-test **DIAGNOSTIC_TEST** matcher (distinct from LLVM FileCheck — it parses machine-readable diag output and runs even when FileCheck isn't installed). A `//CHECK:` prefix is exactly 8 chars, so carets must start at the char immediately after it — `//CHECK:^^^ E41000` puts the first caret at column 9, while `//CHECK: ^^^` (leading space) shifts every caret by one and fails with "Column position(s) don't match"; slang-test prints a "Suggested annotations you can copy" block on mismatch, so use it as ground truth and match by error CODE (`E41000`) rather than free-text message for precision. A parallel provenance trap when answering a maintainer "who wrote this?": `git blame`/`%aN` render the CURRENT name via `.mailmap` (shader-slang maps historical `Tim Foley` → `Theresa Foley`), so quote the name blame ACTUALLY shows (`%aN`, mailmap-applied), not the raw `%an`, since the maintainer runs blame themselves; find a comment's origin PR with `git log -1 <sha>` (subject usually carries `(#NNN)`) or the `git log -S '<text>' --reverse` pickaxe ([DIAGNOSTIC_TEST caret alignment + git-blame .mailmap identity (slang#12236/#12245)](../learnings/1785230187967-diagnostic-test-caret-alignment-git-blame-mailmap-.md)).

**A stale test binary can pass the very test you are validating — prove the relink before reporting numbers.** The cheap check is an mtime comparison: capture a timestamp before the build and require `test_binary_mtime > build_start`; refuse to report pass/fail numbers if it doesn't hold, and prefer that positive relink signal over inferring from a build command's exit 0 (a build can exit 0 having rebuilt nothing relevant — nothing to do, failed early, wrong target, wrong build dir). Observed on slangpy#1073: a `sgl_tests` binary sitting in the worktree was **10 days old** and still passed the cross-thread profiler test being used to validate a concurrency fix; the build subagent caught the stale mtime and refused to report. This is nastier than an ordinary stale-artifact bug because the stale binary *passes* (no error to investigate), the result is *plausible* (same test name, same suite, same expected numbers) so it survives review, and for a timing/concurrency fix it is doubly deceptive — those tests are nondeterministic, so "it passed" was weak evidence to begin with, and running a stale binary means you have *zero* signal while believing you have positive signal. Pair the freshness assertion with a flake probe (e.g. 30×); neither alone is evidence. The general test: *if my change hadn't been compiled in at all, would this still have gone green?* If yes, the PASS carries no information — and the same discipline applies to any cached/derived artifact you then measure (compiled binaries, generated docs, emitted shader assembly, lockfiles) ([a stale test binary can pass the very test you're validating](../learnings/1785772374507-a-stale-test-binary-can-pass-the-very-test-you-re-.md)).

**One positive control per HAZARD, not per fix — when your fix introduces a new failure mode, prove the test catches THAT one too.** A positive control proves a test can fail only for the hazard you disabled. On slangpy#1073 the fixer fixed a reference **leak** in `Profiler::end_zone` (an early return on zone-stack mismatch skipped `release_zone_from_global_frame`, so the frame never sealed → permanent wedge) — and the fix was itself buggy: releasing on *every* mismatch allowed the same reference to be released **twice** (reject `outer` while `inner` is open → releases; end `inner` → valid; re-present `outer` → now satisfies the *valid* path and releases again), and since `release_zone_from_global_frame` asserts `count > 0`, release builds underflow a packed counter and corrupt shared state. A leak had been converted into potential memory corruption; codex's adversarial review caught it. The remedy needed **two** controls: remove the release stanza (proves the test still catches the original leak) *and* weaken the new ownership guard to `true` (proves it catches the new double-release) — and the test had to be **extended** to re-present the rejected token, because control 2 has nothing to trip on otherwise. How to apply: enumerate hazards rather than fixes (leak, double-release/double-free, underflow, deadlock, stall) and give each its own control; **sabotage the specific guard** (`if (owned)` → `if (true)`), not the whole feature; if a control has nothing to trip on, the test is too narrow; and prefer fixes needing **no new state** (the sound shape here reused the existing zone-stack slot as the ownership marker, with `0` a safe "already released" sentinel since `correlation_id` is never 0). Watch for the class *"my fix converted failure mode A into failure mode B"* — common in reference counting, ring buffers and completion/finalization gates, and invisible to a control that only tests A ([one positive control per hazard](../learnings/1785773520364-one-positive-control-per-hazard-when-a-fix-introdu.md)).

Two regression-test mechanics for crash→diagnostic fixes. `//DIAGNOSTIC_TEST:SIMPLE(diag=CHECK):` robustly catches a crash-regression even though its path (`_diagnosticAnnotationTest`) parses only stderr diagnostics and ignores the process result code: the buggy compiler segfaults with **empty stderr / zero diagnostics**, so the exhaustive annotation check fails when the expected (e.g. `E30015`) has no match. This holds only when the diagnostic and the crash are mutually exclusive — true for a front-end error (`executeActionsInner` returns before `generateIR()` on non-zero error count); if the crash is *downstream* of the diagnostic, add a `SIMPLE` `.expected` test asserting `result code = N`. Also: a fatal diagnostic suppresses codegen, so positive-compilation cases must live in a separate file ([DIAGNOSTIC diag=CHECK catches a crash-regression via empty stderr](../learnings/1785349746955-diagnostic-diag-check-catches-a-crash-regression-v.md)). And treat pass/fail counts that go into a PR body as load-bearing: re-run the suite yourself rather than transcribing a build subagent's number (a subagent reported `defer/` as 39/39; a fresh run was 38/38 — 13 dx11 variants ignored) ([verify slang-test suite pass-counts from a fresh run, not a build subagent's number](../learnings/1785349753826-verify-slang-test-suite-pass-counts-from-a-fresh-r.md)).

**Count assertion-bearing tests, not test files — and name which one carries the proof.** A coverage claim inflates without anyone lying when the count is taken over the wrong scope: "6 tests committed" for a fix was really **3 assertion-bearing tests plus 3 support inputs** — an `__include`d file, an `#include`d helper, and a second top-level file passed on the command line. All 6 are real files `git add` counted; only 3 carry a `//TEST:` directive and CHECK lines. Support fixtures are necessary, but they are **inputs, not coverage**. Worse than the count: of the three real tests, two could pass while the feature was broken. The feature scoped a SPIR-V `DebugFunction` to its owning `DebugCompilationUnit`; when the lookup misses, emission falls back to a module-global scope **pinned to the entry-point CU** (PR #10907 for #10906) — so in a translation unit with a single compilation unit the broken fallback *coincides with the expected answer* and the test goes green either way. Only the **two-CU** test discriminates: with a second top-level file the fallback points at the *wrong* CU, so the assertion can only pass if real resolution ran. Two consequences: the second top-level file is a **discriminator, not a fixture** — a future editor pruning an "unused" support file silently destroys the only test with power, so say so in the PR body *and* in a comment in the test; and **say which test carries the proof**, because a reviewer who reads "6 tests" over-credits the coverage while "3 tests, of which the multi-CU one is the discriminating case; the other two corroborate" is both honest and more useful. Generalized authoring question whenever a feature has a fallback path: *in my test's configuration, does the fallback produce the same answer as the fix?* If yes, that test cannot distinguish fixed from broken however precise its assertions look — construct the case where fallback and correct answer *differ*. And a red baseline is necessary but not sufficient: confirm each test fails *for the reason you intend* (the assertion you care about, not a compile error or a path typo), preferring an **observed** signal over a by-construction argument, since by-construction is where vacuous passes hide ([count assertion-bearing tests, not test files — and name your discriminating test](../learnings/1785824059809-count-assertion-bearing-tests-not-test-files-and-n.md)).

**Backend codegen compile time IS separately measurable in-tree today — and a subagent's inverted bottom line is the generalizable tell.** At master `0864e60e6`, "is this user's slow compile front-end or backend?" is answerable with no compiler change by pointing the existing harness at the workload: `slangc -report-perf-benchmark` prints per-phase timers as `[*] <phase> <count> <ms>`, and `tools/compile-perf/breakdown.py:56` already lists **`emitEntryPointsSourceFromIR`** (the `SLANG_PROFILE` at `source/slang/slang-emit.cpp:2747`) as a named bucket under `generateOutput` — the `tools/compile-perf/README.md` tree is `compileInner → {frontEndExecute, generateOutput → {linkAndOptimizeIR → …, emitEntryPointsSourceFromIR}}`. An `Explore` subagent reported the exact opposite as its bottom line — "backend codegen time is NOT separately attributable… recommend updating `breakdown.py`'s TREE to include it" — one step from a public GitHub issue asking maintainers to build something already shipped, at a line the subagent itself cited. Why it inverted: it read that `SLANG_PROFILE` is a **flat** RAII timer recording no parent/child link (`slang-performance-profiler.cpp:10`, flat `OrderedDictionary`) and concluded the *tooling* cannot attribute — but nesting is **reconstructed downstream** by `breakdown.py`. **The tell: a claim about a CAPABILITY derived from reading a MECHANISM one layer below it.** The mechanism read can be perfectly correct and the capability claim still inverted; the cheap check is not "re-read the argument" but *run the tool / open the file the capability lives in* (here `grep -n emitEntryPointsSourceFromIR tools/compile-perf/breakdown.py`) — and a subagent's **bottom line** deserves more scrutiny than its file:line findings, because the findings are checkable and were right while the synthesis was wrong. Real caveat that survives: the profiler is flat, so a parent's time exceeds the sum of named children and `breakdown.py` surfaces the gap as `<parent> (self)` — a named leaf is trustworthy, but an *unnamed* hotspot needs the self-time residual to find ([backend-codegen compile time IS separately measurable (`-report-perf-benchmark` + `tools/compile-perf`); a subagent reported the opposite](../learnings/1785838127386-backend-codegen-compile-time-is-separately-measura.md)).

The through-line across all four of these — skipped test, stale binary, vacuous assertion, inert `CHECK-NOT` — is one bug in different disguises: **present but not exercising.** The general check that catches the whole family: name the defect, then name the assertion that fails when *only* that defect is reintroduced, and negative-control both directions (flip each negative to something known-present, expect RED; flip each positive to a name that doesn't exist, expect RED; restore and confirm green).
