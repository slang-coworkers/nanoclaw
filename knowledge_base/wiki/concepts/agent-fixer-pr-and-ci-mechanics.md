# Fixer PR Creation, Fork & CI Mechanics

## TL;DR

- **Fixer (`nv-slang-bot[bot]`) may push `fix/issue-<n>` direct to origin** (no fork; the CLAUDE.md "fork-only" wording is stale). PRs open as **DRAFT**; never self-flip to ready/merge (operator-gated).
- **Before reverting a non-draft PR state, verify the ACTOR via the timeline API** (`ready_for_review` event `.actor.login`) — revert only a *bot-authored* flip; a human maintainer's deliberate flip is left alone. Current draft state cannot answer this — only the timeline actor can.
- **PR bodies must carry `Closes #N` / `Fixes #N`** to auto-link (prose "also reported in #N" does not). Don't pass `--reviewer`; let CODEOWNERS auto-assign.
- **No AI attribution in any shader-slang commit** (slang, slang-rhi, slangpy), including throwaway `wip/reap/*` branches, and no "Generated with Claude Code" PR footer: the repo CLAUDE.md rule overrides the harness's `Co-Authored-By: Claude` reminder; the only co-author trailer is the operator's, at the verified address. Fix a slip with `git commit-tree` on the same tree + `--force-with-lease` (needs authorization), then prove the tree diff is empty. On a PR under review that force-push is off-limits and squash-merge keeps the trailer, so list every branch commit's trailers (`git log origin/master..HEAD --format='%h [%(trailers)]'`) before the first push; if one slipped through, ask the merger in the PR body to drop it.
- **Report up as soon as the push lands and the new CI run has started** (head SHA, run URL, gate state); never hold the report for an in-session CI watch — the session can end mid-watch and the report is lost. CI results arrive later via `github.ci_failed`.
- **`tools/gfx/` is legacy code paralleling `external/slang-rhi/`** — grep the twin first; in-tree tests only exercise slang-rhi, so state the coverage limit in the PR.
- **On a fork PR the failing check is rarely the real merge blocker** — check fork permissions (`gh api repos/<fork-owner>/<repo> --jq .permissions`, `maintainerCanModify`) first; if the binding blocker is human-owned and humans are engaged, default to **watch-only**.
- **For a `dirty` PR, name the conflicting files without a checkout:** fetch `pull/<N>/head` and run `git merge-tree --write-tree --name-only origin/<base> <ref>`, then `git log <merge-base>..origin/<base> -- <files>` for the causing commits. **A merge-conflicted PR gets no `on: pull_request` CI at all** (only `pull_request_target` workflows, CLA and CodeRabbit run), and the conflict can be submodule-pin-only, which a local merge-tree with submodule objects reports as clean. Check `actions/runs?branch=<head_ref>` and `mergeable_state` before calling CI green; only a rebase/merge restores CI.
- **Off-repo (slang-rhi) triage from the slang-triager container:** anonymous clone works (public), but `GH_TOKEN` may be invalid for writes — report the posting blocker up, don't write with a broken token. Bot cannot push `.github/workflows/*` — deliver as a maintainer-applied patch.
- **Devin done-detector races the AI-analysis render** — the right-rail `Analysis complete` populates before the analysis paragraph hydrates; guard on a non-`Generating...` paragraph.
- **Since 2026-10-05 `/explain-diff-html` (`upsert_pr_body.py`) writes the explanation as ONE PR comment, edited in place, and strips it from the description**, which stays concise (~5-15 lines; a squash merge copies it into git log). On a PR whose old body held the explanation only `Fixes #N` survives, so rewrite the concise description with `gh pr edit <n> --body-file`; the disclaimer goes on the explanation comment.
- **`upsert_pr_body.py` exit 5 "edited by nv-slang-bot" is usually our own edit:** GraphQL names a GitHub App editor `nv-slang-bot` (no `[bot]`), so the trusted-identity check misses it. Confirm the editor is our App (`__typename: Bot`, same databaseId as REST `user.id`), then re-run with `EXPLAIN_DIFF_ACTOR=nv-slang-bot`; never put a human's login there. Edit the explanation comment only through the script.
- **Never truncate `upsert_pr_body.py` output.** The deliver gate and the Stop hook learn that the explanation comment is fresh only by parsing the full `EXPLAIN_DIFF_RECEIPT {...}` line from stdout; through `cut`/`head -c`/`tail` the JSON fails to parse, `explained_head` stays old, and both keep blocking although GitHub is updated. Run it with no pipe and check `explain-diff-state.json`.
- **The description length check doesn't end a section at a blank line.** Every non-empty line after `**Risk.**` counts toward Risk, so give each trailing line (open question, Refs/Part of) its own bold label, and pre-check with `description_problems` before `gh pr edit`.
- **After merging master into a PR that marks macro-generated declarations, re-sweep the marks.** Taking master's hunk for a block that moved into a new macro silently drops your mark on it.
- **The critique gate keys off delivery markers, not off whether you wrote code** — it blocks even a no-code triage confirmation until PLAN/CODE/OUTPUT review stages are recorded. Satisfy it honestly: write the deliverable to a file, run `/codex-critique` per stage; the parser records STAGE only from a fresh STAGE-tagged `mcp__codex__codex` call and the verdict only from the exact `### Verdict\napprove` block. A `codex-reply` continuation round is never recorded: after a must-fix, run the fix round as a fresh `mcp__codex__codex` call with the canonical developer-instructions and `ROUND: n/3`.


The mechanics the `nv-slang-bot[bot]` fixer coworker operates under on `shader-slang/slang`: branch/push rights and PR-state hygiene, the `tools/gfx`↔`slang-rhi` twin, fork-PR CI blockers, the Devin done-detector race, and the codex critique gate. Triage classification/routing lives on [Triage Decisions](agent-fixer-triage-decisions.md); dispatch/coordination failure modes on [Fixer Dispatch & Coordination Failure Modes](agent-fixer-dispatch-coordination.md).

## Fixer PR Creation and Push Rights

The fixer authenticated as `nv-slang-bot[bot]` may push `fix/issue-<n>` branches **directly to `origin = shader-slang/slang`** — no fork is required ([slang-fixer can push fix/ branches direct to origin (fork-only rule does not apply)](../learnings/1780685454567-slang-fixer-can-push-fix-branches-direct-to-origin.md)). The older CLAUDE.md "fork-only" wording is stale. An earlier learning ([slang fixer PR push: szihs fork master is stale/divergent (lacks docs/generated framework) → GitHub-App 'workflows permission' rejection; jkwak fork auth fails](../learnings/1780357449295-slang-fixer-pr-push-szihs-fork-master-is-stale-div.md)) documents why the szihs fork path fails: `szihs/master` is far behind `origin/master`, and pushing a branch that spans the gap triggers a GitHub App `workflows` permission rejection when the diff includes `.github/workflows/` files; the diagnostic is `git diff --name-only szihs/master..HEAD | grep '^.github/workflows/'`. The patch fallback (`git format-patch origin/master --stdout`) remains the real-rejection path, not the no-fork default.

All fixer PRs must open as **DRAFT**. Fixers must never self-flip a PR to ready-for-review (`gh pr ready`) or merge it — those remain operator/maintainer-gated ([Fixers must not self-flip PRs to ready — enforce drafts-only](../learnings/1782464090006-fixers-must-not-self-flip-prs-to-ready-enforce-dra.md)). However, before directing a revert of a non-draft state, always verify the *actor* via the timeline API (`ready_for_review` event `.actor.login`) — a human maintainer may have flipped the PR intentionally ([Fixers must not self-flip PRs to ready — enforce drafts-only](../learnings/1782464328257-fixers-must-not-self-flip-prs-to-ready-enforce-dra.md)). Reverting a maintainer's deliberate decision is a worse breach than the (potentially nonexistent) bot violation. The corrected rule: revert only a **bot-authored** self-flip; leave human-flipped PRs alone. The audit is one call, and **current draft state cannot answer it — only the timeline actor can**: `gh api repos/O/R/issues/<n>/timeline --jq '.[] | select(.event=="ready_for_review" or .event=="convert_to_draft") | "\(.event) actor=\(.actor.login) \(.created_at)"'`. Confirming instance on PR #12281: the actor came back `pdeayton-nv` — a human flipped it, guardrail intact, nothing to revert ([draft-guardrail audit: use the timeline event actor, not current state](../learnings/1785825109539-a-dispatched-handoff-can-silently-die-verify-artif.md)).

PR bodies must include an explicit `Closes #N` / `Fixes #N` closing keyword to auto-link the issue ([Fixer PRs must use a Closes/Fixes #N closing keyword, not a prose issue reference](../learnings/1780562553886-fixer-prs-must-use-a-closes-fixes-n-closing-keywor.md)). Prose mentions like "also reported in #N" do not link. Backfill: `gh api -X PATCH repos/<o>/<r>/pulls/<pr> -f body="$(existing)\n\nCloses #<issue>"`. Do not pass `--reviewer` to `gh pr create`; let CODEOWNERS auto-assign.

**Commits carry no AI attribution — the repo rule beats the harness reminder.** In shader-slang repos (slang, slang-rhi, slangpy) no commit may carry `Co-Authored-By: Claude` or any other AI attribution, and no PR body may carry the "Generated with Claude Code" footer. The harness system-reminder asks for both, but it explicitly yields to the user's or repo's own CLAUDE.md, and both the slang repo CLAUDE.md ("Don't mention Claude on the commit message") and slang-fixer's own CLAUDE.md ("Never include Claude or AI-tool attribution in commit messages or PR bodies — upstream policy") forbid them. The rule covers every commit the bot pushes, not only PR commits: the parent confirmed on 2026-09-29 that throwaway `wip/reap/*` branches are in scope. Sibling bot branches (fix/issue-13409/13423/13426) carry no trailer, which is the quick sanity check. The slip keeps recurring because the reminder arrives fresh in every session: slang-fixer's worktree-GC pushed `wip/reap/fix/issue-12762` @ 3390dc16f9 with the trailer; two pushed commits on PR #11709 and three on PR #13378 carried it (a reviewer caught #13378); and a 2026-10-05 session pushed four such commits before any PR existed and then needed force-push authorization to rewrite them [No AI attribution in shader-slang commits; the repo rule overrides the harness reminder](../learnings/1790689864476-no-ai-attribution-in-shader-slang-commits-the-repo.md) [CLAUDE.md "no AI attribution" overrides the harness Co-Authored-By reminder](../learnings/1790718572444-claude-md-no-ai-attribution-overrides-the-harness-.md) [Session attribution reminder adds Co-Authored-By: Claude — check trailers at commit time](../learnings/1791166638297-session-attribution-reminder-adds-co-authored-by-c.md). **Prevention beats repair, because the repair is not always available.** Before the first push, list the trailers of every branch commit, not just the last one: `git log origin/master..HEAD --format='%h [%(trailers)]'` (why content-only checks never see a trailer is on [CI correction scrutiny](ci-a-correction-scrutiny-and-forensics.md)). If a trailer did get pushed and the bot owns the branch with no PR, rewrite only the messages and prove the trees are unchanged: either `NEW=$(git commit-tree <old>^{tree} -p <old>^ -m "<clean msg>")` then `git push --force-with-lease=refs/heads/<br>:<old-full-sha> origin $NEW:refs/heads/<br>` for one commit, or `git filter-branch -f --msg-filter '<strip line>' origin/master..HEAD` for a range; then `git diff <old> <new>` must be empty (or `HEAD^{tree}` must equal the old head's tree). Either way the force-push needs explicit authorization [shader-slang commits: repo no-AI-attribution rule beats the harness Co-Authored-By reminder (commit-tree repair recipe)](../learnings/1790689900100-shader-slang-commits-repo-no-ai-attribution-rule-b.md). On a PR under review the force-push is off-limits without explicit operator authorization, and GitHub's squash merge collects every `Co-authored-by` trailer into the squash commit, so if nobody acts the attribution lands on master: leave a note in the PR body asking the merger to drop the trailer. The one co-author trailer a bot commit carries credits the operator at the verified address; check it with `git log -1 --format=%B` before every push. An orchestrator can sweep open bot PRs with `gh pr view <n> --json commits --jq '[.commits[]|select((.messageBody//"")|test("(?i)co-authored-by:.*claude"))|.oid[0:10]]'`. If a reviewer or codex flags attribution, they are right [Harness Co-Authored-By reminder vs slang's no-AI-attribution rule: repo rule wins](../learnings/1791247512039-harness-co-authored-by-claude-attribution-reminder.md). The PR-description side of the same policy (the AI-transparency disclaimer belongs on comments, never in the body or a commit) is on [Codex provider](agent-fixer-codex-provider.md).

**`/explain-diff-html` puts the explanation in a PR comment, not the description (policy since 2026-10-05).** `upsert_pr_body.py` creates, or edits in place, ONE explanation comment and strips any explanation out of the description, which must stay concise (~5-15 lines, because a squash merge copies it into git log). The script still carries `Fixes #N` over, so on a PR whose old description held the explanation it leaves a near-empty body (it printed `NOTE: the PR description is 12 chars`, with only `Fixes #N` left), and you must then write the concise description yourself with `gh pr edit <n> --body-file`. A body that held only an `explain-diff-html:start…end` block comes out at about 123 characters (the Fixes and disclaimer lines), so write the Summary/Root cause/Tests/Risk description right after the upsert, or the PR is left with an empty description. Check that description against the length hook offline before running `gh pr edit`: `cd /home/node/.claude/skills/explain-diff-html/scripts && python3 -c "import upsert_pr_body as u; print(u.description_problems(open(F).read(),1000,2))"`. It applies the same rules as the PreToolUse gate, so a refused edit and its full-context retry are avoided ([pre-check a PR description against the length hook offline](../learnings/1791289373392-pre-check-a-pr-description-against-the-length-hook.md)). Know how it counts: `description_problems` treats a section as a `**Label.**` or `## Heading` line plus every following non-empty line, and a blank line does not close it, so an "Open question …" or "Refs #N / Part of #M" line after `**Risk.**` counts toward Risk and trips "Risk has 3 lines, max 2". Give each trailing line its own bold label (`**Open question (blocks merge).** …`, `**Issues.** Refs #…`). The 1,000-char budget excludes only the `<sub>` disclaimer and pure `Fixes #N`/`Closes #N` lines ([description limits: blank lines don't end a section; label trailer lines](../learnings/1791463595621-explain-diff-html-description-limits-blank-lines-d.md)). A separate merge hazard comes from the same PR: when you merge master into a PR that marks macro-generated declarations (e.g. `[__readNone]` in `diff.meta.slang`) and master has moved a block into a new macro, taking master's hunk silently drops your mark on the moved block, so after resolving, sweep that each anchor attribute still carries its required mark ([same atom](../learnings/1791463595621-explain-diff-html-description-limits-blank-lines-d.md)). The bot disclaimer belongs on the explanation comment too; OUTPUT_REVIEW flags it when missing. The older behaviour, where the script replaced the whole body (so the five-part sections had to be mapped into Background / Intuition / Code walkthrough) and re-appended `Fixes #N` plus the disclaimer below the explanation (duplicates on #13353), no longer applies. A `codex-reply` continuation round is not recorded by the critique gate, so after a must-fix, run the fix round as a fresh `mcp__codex__codex` call with the canonical developer-instructions and `ROUND: n/3` ([upsert_pr_body.py now writes the explanation as a PR comment and strips it from the description](../learnings/1791234547680-upsert-pr-body-py-now-writes-the-explanation-as-a-.md)).

**An exit 5 that names our own App as the editor is an identity-spelling mismatch, not a human edit.** Before overwriting the explanation comment, `upsert_pr_body.py` checks its seal; if the seal is broken it asks GraphQL's edit history who edited it and refuses (exit 5, writes nothing) unless that login is one of our trusted identities. GraphQL's `editor.login` names a GitHub App without the suffix (`nv-slang-bot`, `__typename: Bot`), while the actors file and REST use `nv-slang-bot[bot]`, so our own edit reads as foreign: "edited by nv-slang-bot … after this script last wrote it". The usual trigger is a hand edit of our own comment, such as a REST PATCH to add the disclaimer ([upsert_pr_body.py exit 5 on our own edit: GraphQL drops the [bot] suffix](../learnings/1791922521312-upsert-pr-body-py-exit-5-on-our-own-edit-graphql-d.md)). Verify before adopting: the comment's GraphQL `author { ... on Bot { databaseId } }` must equal the REST `user.id` of our App (274397474 for nv-slang-bot). Then re-run with `EXPLAIN_DIFF_ACTOR=nv-slang-bot`, which adopts the coworker's own identity and is what the script's refusal text allows; never put a human's login there ([explain-diff upsert: GraphQL names the App editor without [bot]](../learnings/1791939131464-explain-diff-upsert-graphql-names-the-app-editor-w.md), [also seen in a codex-critique session](../learnings/1791912236710-codex-stage-prompts-can-return-wiki-recall-instead.md)). To avoid the problem, edit the explanation comment only through the script, which appends the disclaimer itself when the body has no `<sub>` line. While investigating, keep in mind that `gate-critique-on-deliver.sh` treats any `gh api …pulls…` command, GETs and reactions on pull comments included, as PR creation, so do those reads and reactions through `gh api graphql` (the regex is described on [holds & authorization gates](agent-routing-holds-authorization-gates.md)).

**The hooks learn that the explanation comment was refreshed only from the `EXPLAIN_DIFF_RECEIPT` line, so that line must reach stdout whole.** Two hooks read it. The deliver gate (`gate-critique-on-deliver.sh`) uses `pr-auto-map.sh`, which parses the receipt from the command's stdout with `fromjson?`, and the explain-diff Stop hook (`gate-explain-on-stop.sh` → `lib/explain-diff-owed.sh`) parses the same `EXPLAIN_DIFF_RECEIPT {...json...}` line from the Bash tool output. Both then update `explained_head` in `/workspace/.claude/explain-diff-state.json`. If `upsert_pr_body.py` runs through `| tail -1 | cut -c1-200`, `cut -c1-N` or `head -c`, the script prints `EXPLAIN_DIFF_RECEIPT {"updated": true...}` and the comment on GitHub is updated, but the cut-short JSON does not parse and no receipt is recorded. The deliver gate then keeps refusing `[Fix Review Request]`/`[Fix Report]` with "explanation comment still explains head <old>", and the Stop hook blocks with "explanation comment is stale". Run the script as a plain command with no pipe on stdout. One session listed `| grep` among the forms that failed the deliver gate, while another cleared the Stop hook by re-running with only `| grep RECEIPT`; no pipe at all is the form both agree on. Check with `jq '.prs["owner/repo#N"].explained_head' /workspace/.claude/explain-diff-state.json` ([explain-diff gate only clears when the upsert receipt line reaches stdout untruncated](../learnings/1792155974206-explain-diff-gate-only-clears-when-the-upsert-rece.md), [never truncate the EXPLAIN_DIFF_RECEIPT line: the stop hook parses it from Bash output](../learnings/1792177961012-never-truncate-the-explain-diff-receipt-line-the-s.md)).

## tools/gfx Legacy Code and the slang-rhi Twin

`tools/gfx/` is legacy code that parallels `external/slang-rhi/` ([slang-fixer: tools/gfx/ is legacy code paralleling slang-rhi — fixes need to land in both, but in-tree tests only exercise slang-rhi](../learnings/1778749638138-slang-fixer-tools-gfx-is-legacy-code-paralleling-s.md)). All in-tree tests go through slang-rhi, so a regression test for a `tools/gfx/` bug cannot catch the runtime issue. When fixing a `tools/gfx/` symbol, always grep for the twin in `external/slang-rhi/src/` first — often slang-rhi is already patched and `tools/gfx/` just lags. State this coverage limitation plainly in the PR. A `.slang` compile-only filecheck can guard the language surface, but real runtime coverage requires downstream consumers' CI (e.g. Falcor's gfx integration tests).

## Failing Checks, Fork Permissions, and CI Mechanics

On fork-based PRs, separate the *failing check* from the *actual merge blocker* ([Failing check ≠ real blocker on fork-based PRs (triage to watch-only)](../learnings/1780903795100-failing-check-real-blocker-on-fork-based-prs-triag.md)). Check fork permissions first (`gh api repos/<fork-owner>/<repo> --jq .permissions` and `maintainerCanModify`). If the binding blocker is human-owned AND humans are engaged, default to watch-only.

Two checks make a fork-PR status report precise. When a PR shows `mergeable_state=dirty`, list the exact conflicting files without checking anything out: `git fetch origin main pull/<N>/head:refs/tmp/prN`, then `git merge-tree --write-tree --name-only origin/main refs/tmp/prN`, which prints the conflicted paths and `CONFLICT (content)` lines. Then `git log <merge-base>..origin/main -- <conflicted files>` names the main commits that cause the conflict, which is enough to tell a maintainer exactly where a rebase will hurt ([Predict PR merge conflicts locally with `git merge-tree --write-tree`](../learnings/1791895869568-predict-pr-merge-conflicts-locally-with-git-merge-.md)). And a PR with pushes can have no `ci` workflow run at all. The symptom is that each push triggers only `pull_request_target` workflows (slangpy "PR Maintenance"/board-sync), CLA and CodeRabbit, while `ci`/`checks` (`on: pull_request`) never run again: no run, no `action_required`, nothing to approve. The cause is a merge conflict, not the fork: GitHub's docs say "Workflows will not run on `pull_request` activity if the pull request has a merge conflict", and `pull_request_target` still runs. The conflict can be **submodule-only**. GitHub's server-side merge has no submodule objects, so when `main` bumps a submodule pin that the PR also changed, the PR becomes unmergeable even though a local `git merge-tree` with the submodule objects present reports a clean submodule fast-forward. Reproduce the server's view in a bare clone without submodule objects: `git merge-tree --write-tree <main> <head>` → `CONFLICT (submodule)`. On slangpy#1189 the last `ci` run was 09-29 12:14Z, #1188 (which bumped `external/slang-rhi`) merged at 12:39Z, and no later push got a `ci` run (an earlier reading of the same PR blamed fork pushes). Check `gh api repos/O/R/actions/workflows/ci.yml/runs?branch=<head-branch>` and `pulls/N --jq .mergeable_state` (`dirty`) before saying "CI is green". Only a rebase or merge brings CI back; meanwhile run the GPU tests locally for evidence ([GitHub pull_request CI silently stops on a merge-conflicted PR, incl. submodule-pin conflicts](../learnings/1792159824626-github-pull-request-ci-silently-stops-on-a-merge-c.md)). A clean `merge-tree` proves only that there is no textual conflict; its limits and the guilty control that proves it can report one are on [GitHub state & PR mechanics](agent-a-github-state-and-pr-mechanics.md).

For off-repo triage of slang-rhi issues from the slang-triager container: anonymous clone works (public repo), but GH_TOKEN may be invalid for write operations ([slang-rhi off-repo triage: anonymous clone works, GH_TOKEN invalid, no GPU](../learnings/1780307950462-slang-rhi-off-repo-triage-anonymous-clone-works-gh.md)). Report the posting blocker to the parent rather than attempting a write with a broken token.

Falcor CI tracking issues opened by `jkiviluoto-nv` are self-assigned CI-infrastructure work, not compiler bugs ([Falcor CI tracking issues from jkiviluoto-nv: park at triaged, cross-link the family](../learnings/1782222346038-falcor-ci-tracking-issues-from-jkiviluoto-nv-park-.md)). Park at triaged; do NOT forward to slang-fixer. Still post a verified 5-bullet (value: cross-linking the Falcor-CI family). The Falcor-CI improvement family: #11495 → #11600 → #9219, #9228, #11703.

The Falcor YML 3-file refactor (#11600) requires build-flag reconciliation — the two existing falcor workflows produce different cmake-flag artifacts ([slang#11600 falcor YML 3-file refactor — triage design notes](../learnings/1781365729972-slang-11600-falcor-yml-3-file-refactor-triage-desi.md)). The required-check aggregator job key must be exactly `check-falcor` (kebab-case), and the dispatcher must add `merge_group: types:[checks_requested]` to avoid deadlocking the merge queue. Bot cannot push `.github/workflows/*` — deliver as maintainer-applied patch.

When a `set -euo pipefail` CI script exits non-zero with no output and the logs cannot name the command (#13041 → PR #13352), add `trap 'status=$?; echo "::warning::… \"$BASH_COMMAND\" (line $LINENO) exited with status $status"; exit 0' ERR` **without** `set -E`. It then fires only where errexit would abort at top level, not on expected no-matches inside `$(...)`, which makes the next occurrence falsifiable: either a warning names the command, or a still-silent exit rules errexit out (shell or runner process) ([ERR-trap diagnostic for silent pipefail exits](../learnings/1790799595374-critique-gate-any-file-write-after-the-output-revi.md)).

**On a parent-requested rebase/force-push, report up the moment the push lands and the new CI run has started.** On a shader-slang bot PR the fixer pushed, dispatched `ci.yml`, and then held its 5-bullet report until a background CI watcher finished; the session ended mid-watch, the watcher was killed, no report was ever sent, and the parent had to re-chase 24 h later. The report should carry the new head SHA, the run URL, and the current gate state; CI outcomes arrive later as a `github.ci_failed` webhook, so waiting for them in-session buys nothing and risks losing the report. A related trap on the same run: a bot CI run can stop at `wait-for-human-priority` with `priority-gate-yielded`, which makes `check-ci` fail although no real job ran. That is a scheduling yield, not a code failure; `retry-yielded-bot-ci` reruns it only once the run is *completed* (see [GitHub bot & webhooks](agent-routing-github-bot-and-webhooks.md)). On a draft whose yielded run still sits `waiting` on the Falcor build approval gate, the script never fires (it treats `waiting` as active CI), approving the gate does not help, and a re-dispatch only yields again, so say so and leave it to a maintainer marking the PR ready or starting CI ([a priority-yielded draft dispatch is not rerun while it sits 'waiting'](../learnings/1793105473572-a-priority-yielded-bot-ci-yml-dispatch-on-a-draft-.md); rules on [rerun decision rules](ci-flake-rerun-decision-rules.md)) [Report up right after push+CI dispatch; don't gate the report on a long CI watch](../learnings/1790669062658-report-up-right-after-push-ci-dispatch-don-t-gate-.md).

## Devin Review Done-Detector False Positives

`slang-pr-review-runner`'s `devin-fetch.sh` can declare completion while the middle-pane AI-analysis paragraph still shows `Generating...` ([Devin Review done-detector races AI-analysis text render](../learnings/1779298338813-devin-review-done-detector-false-positives-on-all-.md)). Fix: extend `DONE_EXPR` to check that the "Devin's AI analysis" heading is followed by a non-`Generating...` paragraph. When `devin-flags.md` shows the `## AI Analysis` as "Generating...", recover by driving `agent-browser` to open each flag panel and re-scrape the body text.

## The Critique Gate Fires Even for No-Code Deliveries

The `gate-critique-on-deliver.sh` hook keys off delivery markers (`[Fix Report]`, `[Resolution]`, `[Report]`, `gh pr create`/`gh api .../pulls`), not off whether you wrote code — so it blocks even a NO-CODE triage-confirmation with zero diff until all three stages (PLAN_REVIEW, CODE_REVIEW, OUTPUT_REVIEW, the last = `approve`) are recorded. Satisfy it honestly rather than fighting it: write the deliverable to a file so codex has an artifact, then run `/codex-critique` once per stage — for CODE_REVIEW with no diff, frame it as the scope-shrinkage guard ("confirm zero-diff is correct/complete — did I silently drop an in-scope fix?", pointing codex at `git status --porcelain` + `git diff --stat`) ([Critique gate fires on no-code triage-confirmations too](../learnings/1783523465568-critique-gate-fires-on-no-code-triage-confirmation.md)). The **parser** is exact: it records the STAGE only from a FRESH `mcp__codex__codex` call whose prompt contains a `STAGE: <X>` line, and the VERDICT only when codex returns the skill's exact `### Verdict\napprove` block (free-text "VERDICT: approve" shows "verdicts: none"); a `codex-reply` (round 2/3 of a must-fix) carries no STAGE tag, so to clear a must-fix'd OUTPUT_REVIEW you must fix then issue a NEW STAGE-tagged call, and all codex calls in-container require `sandbox: "danger-full-access"`. This is closely tied to the STEP-0 byte-compare methodology for "did this diff change the emitted/serialized output?" that produces such no-code diagnoses ([STEP-0 byte-compare to decide if a diff changed emitted output; and codex delivery-gate verdict-parsing format](../learnings/1783352556452-step-0-byte-compare-to-decide-if-a-diff-changed-em.md)).
