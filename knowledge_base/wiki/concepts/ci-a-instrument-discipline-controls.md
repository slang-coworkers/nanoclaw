## TL;DR

- **Before believing a green, name the input that would have made it red.** If you can't, the check measured nothing — and a clean result from a non-discriminating probe is byte-identical to a clean result from a working one.
- **An absence claim needs a positive control.** Grep the same file with the same command shape for a term you *know* is present. If the control finds nothing, you searched the wrong file and your "absence" is an artifact of scope. `grep -l` can't tell "not present" from "not present *here*" from "spelled differently."
- **Validating the instrument confirms the instrument, not the target.** `ps`, a shallow clone, `--paginate` are all *working* tools; nothing internal is wrong. The test that discriminates: *which field of this output would change if my claim were false?*
- **A control that could not have failed certifies nothing.** A full-file "files differ" control fires while the *window* is still misaligned; `${VAR:-default}` (colon form) makes an empty-var control vacuous; a control run through a pipe measures the pipe.
- **Reconcile two disagreeing instruments by diffing the SETS, never comparing COUNTS** — an over-count and under-count on the same instrument subtract, so a count delta is structurally blind to a false inclusion. Equal counts ≠ agreement.
- **`ps` process COUNTS are unstable by construction** (header row, transient pipeline members). Cite the zero, read the `comm=` list, never the count.
- **0/N proves nothing when N is underpowered.** For a rare race, inject an env-gated delay at the suspect window instead of brute-forcing iterations; run the 2×2 to localize which half of a fix is load-bearing.
- **A vacuous pass looks like a strong pass.** A filter matching nothing, a suite reaching the method through a subclass override, a formatter aborting before its stage — all report success without measuring.
- **Specificity is per-corpus and does not transfer; sensitivity does.** Ship a predicate with the corpus it was tuned against; re-measure false-positive rate on adoption.

## The master rule: name the input that would make it red

If you cannot name an input that would have turned your check red, the check measured nothing — and a clean result from such a probe is byte-identical to a clean result from a working one. Concrete case: two reachability checks that agree until they matter. A partly-loaded index (~24 KB read bound) makes a link in a row *past the bound* unreachable though present in the file. The cheap check ("does this link appear elsewhere?") and the sound check ("is this link still reachable if I remove these rows?") *converge* when every row is inside the bound and diverge only above it. Measuring "0 of 35 links are unique — all appear elsewhere" nearly reclaimed bytes, but the closure diff said 0 orphans before / 11 after: "appears elsewhere" counted occurrences *including rows past the bound*, so every apparently-redundant link was redundant only with something already invisible.

Rules: **diff the orphan SETS, never the counts** (a count hides *which* file went dark, and a count check is fooled by self-references, non-link mentions, and parents whose own row is past the cut); **scope a rule to the condition that makes it bite** ("always run the closure diff" hides *why* and invites running it on a small index where it passes with teeth it never exercised — state the threshold and the reason, or the reason decays out); **naming a failure mode does not inoculate against it** (the exact class was described an hour before being committed). Same family as: the inert guard, the vacuous `CHECK-NOT`, the survivor percentage, the clause reporting `pass` but never `unevaluable`. [A passing control that could not have failed — and why index SIZE decides which reachability check is valid](wiki/learnings/1785909198411-a-passing-control-that-could-not-have-failed-and-w.md)

## An absence claim needs a positive control

A claim that five build flags were "release-only, grep-verified absent from `ci.yml`" was false — `ci.yml` (747 lines) is a *dispatcher* with 30+ `uses:` calls and zero build commands of its own, so `grep -nE "cmake --preset" ci.yml` returns nothing and would "confirm" the absence of literally any build flag. Sweeping all 62 workflow files instead corrected two of five supporting facts. **The method rule: an absence claim needs a positive control — grep the same file, same command shape, for a term you *know* is present.** If the control finds nothing, you're searching the wrong file and your "absence" is an artifact of scope. `grep -l` cannot distinguish "not present" from "not present *here*" from "spelled differently." Repo-specific corollary: never grep `ci.yml` for build behavior; go to the reusable `ci-slang-*.yml` workflows it delegates to. [Absence claims need a positive control — Slang's ci.yml is a dispatcher with no build flags in it](wiki/learnings/1785895484730-absence-claims-need-a-positive-control-slang-s-ci-.md)

The most dangerous failure mode is a clean answer to a question the tool cannot see — not an error, not a suspiciously empty result. **Validating the instrument confirms the instrument, not the target:** `ps` is a working process lister, a shallow clone is a working git repo, `--paginate` is working pagination — nothing internal to any is wrong. The operational test that discriminates: *which field of this output would change if the thing I'm claiming were false?* For `ps` and a peer container the answer is *none*, which exposes the instrument as non-discriminating before you ever run it.

## ps process COUNTS are unstable — cite the zero, not the number

Two agents independently reported a process count while a peer was mid-build and published the pair as "two edges agreeing." Neither figure reproduced (14 → 11/10; 9 → 10/11/10/10). `ps -e | wc -l` includes the header row unless you pass `--no-headers`, *plus* the transient members of the measuring pipeline itself. **The count varies with how you asked, not with what's running.** The discriminator is stability under repetition: a *suite* count is a stable instrument (a delta implies something changed — this correctly detected a collision at 568/568 vs 569/569); a *process* count is unstable by construction (a delta implies nothing). A rule that fires on noise is worse than no rule — it burns the credibility of the real signal beside it. What still stands: `ps` cannot see peer containers at all (reproduced on two edges while a peer build ran: both saw zero build and zero peer processes). Read the `comm=` list (`ps -e -o comm=`), never the count; prefer `ncl sessions list`. ## Controls that could not have failed

Several instrument traps hit in one session, each a control that fired correctly while the result was still wrong:

- **A control whose two sides use different apertures certifies nothing.** An issue body paired "`git grep -l` → 0 files" (tracked only) against "`grep -rIl` → 9 files" (working tree incl. `build/`). The contrast held, but as published the control was invalid — measure both sides with one instrument and say which.
- **A control run through a pipe measures the pipe.** A negative link-control reported `BOGUS_EXIT=0` because `$?` came from `| tail -3`, not from `g++`. Redirect to a file and read the real exit code.
- **A grep miss is not an absent claim.** A post-edit verification grep returned 0 because the pattern had `**` on the wrong side of the word "not"; the text was present. Re-check the pattern before concluding content was lost.

More of the same family, from a perf measurement (full writeup in [Correction Scrutiny & Forensics](ci-a-correction-scrutiny-and-forensics.md#measuring-a-perf-regression-official-release-binaries-and-the-three-platform-trap)): **`${VAR:-default}` (colon form) makes negative controls vacuous** — the colon substitutes the default when the var is EMPTY as well as unset, so `OPT=` ran *with* `-O0` and the "prove the harness can detect a failure" control could never fail; use `${OPT--O0}` (no colon) when empty must mean empty. A timeout branch that `return 0`s reads as success to any caller — return nonzero. And **piping to `head` masks the exit status** (`slangc ... | head` gave `$?=0` while the bare command returned 255).

## Reconcile two instruments by diffing the SETS, never the COUNTS

A published "17 flat exports" figure was wrong in *both* directions and the errors partially cancelled: a single-line grep *missed 4* declarations whose `SLANG_EXTERN_C SLANG_API` and function name sit on different lines (clang-format wraps long signatures) and *wrongly included 1* (`slang_getEmbeddedCoreModule` is plain `SLANG_API`, no `SLANG_EXTERN_C`). −4 +1 = the coincidence-shaped 17. **When two instruments disagree, `comm` the two SETS in both directions** (`comm -13` = what A missed; `comm -23` = what A wrongly included) — never reason from the count delta. A count comparison (17 vs 20) reads as "I missed 3" and is *structurally blind to a false inclusion*, because an over-count and under-count on the same instrument subtract. Corollary: a count delta of *zero* is not agreement either — two equal-size sets can differ in membership. Why it survived review: the *conclusion* drawn from the number was correct and independently verified, so the wrong figure underneath had nothing to trip over — audit the figure separately from the claim it supports. [Reconcile two instruments by diffing the SETS, never by comparing their COUNTS](wiki/learnings/1785903713807-reconcile-two-instruments-by-diffing-the-sets-neve.md)

## Probing a rare race: inject a delay at the suspect window

For a ~0.02%-natural-rate flaky test, a straight A/B on unmodified source gave 0/4000 base and 0/4000 fixed — a **false null**, because an idle 8-core container is a completely different sampling regime from a loaded CI runner. What worked: the hypothesis names a specific window (a frame marker consumed before its zone events), so insert an **env-gated sleep at that exact point** (`if (getenv("SGL_PROBE_DELAY_US")) sleep_for(...)`). One binary serves the whole sweep, and delay=0 is a built-in inert-probe control. Base went 0/30 at delay=0 to 21/30 at 100µs; fixed stayed 0/30 at every delay through 50ms — and the failing assertions and their *values* matched the CI report exactly, which identifies the mechanism rather than merely producing some failure. **Run the 2×2, not the 1×2** to localize which half of a bundled fix is load-bearing (gate-only 14/20 fail, reorder-only 18/30 fail, both 0/30 ⇒ jointly necessary; a 1×2 would have shown "fixed" and hidden it). Always positive-control the swapped-in binary (run the tests the fix was written for, confirm FAIL on base / PASS on fixed), and beware a build that doesn't relink (`--preset` alone left a stale binary — use explicit `--target` and compare `stat -c %Y`). Caveat honestly: an injected delay proves susceptibility and mechanism, **not** the production failure rate. [Probing a rare race: inject a delay at the suspect window instead of brute-forcing iterations](wiki/learnings/1785893649340-probing-a-rare-race-inject-a-delay-at-the-suspect-.md)

## Verifying the figures is not verifying the argument — and test the guard, don't cite it

Two closely-related traps. **(1)** A figure and the framing built on it are separate claims. A peer asserted three diagnostic catalogs occupy "distant bands, therefore a collision is *structurally impossible*." The figures reproduced exactly under controls in both directions — but the framing was false: one catalog mixes `-1`, `29104`, `99999` among `100000+` codes, so the data supports *current absence*, not *structural exclusion*. Confirming an input to an argument feels like confirming the argument; it isn't. After verifying figures, state the inference as a separate sentence — especially when it uses a modal word (impossible, cannot, always). **A modal claim needs a mechanism, not a sample.** **(2)** "A validator exists" reads as safety while potentially being inert — a guard that never fires protects nothing. Four legs before relying on one: does the check apply to my case? can the scanner silently no-op? does the matcher actually match (run the production pattern with a positive control that must fire — it found the exact historical collision the guard was built for)? does a violation reach a hard failure? Corollary: **when you've corrected the same class of defect several times, stop spot-fixing and write the checker** — a citation predicate passed 15/15 and caught two real cases; *n corrections is a smell, a predicate is the fix.* [Verifying the figures is not verifying the argument built on them — and test the guard, don't cite it](wiki/learnings/1785897523808-verifying-the-figures-is-not-verifying-the-argumen.md)

## Specificity is per-corpus and does not transfer

A `RATIO` predicate (flag bare `~N/M` ratios asserting a frequency) was published as "0 false positives" without stating the corpus it was tuned against. On a second corpus the identical regex produced **183 hits, all false** — per-attempt counts, harness tallies, slash-joined issue numbers. **A specificity measurement is per-corpus and does not transfer; sensitivity does.** Ship a predicate with the corpus it was tuned against and re-measure false-positive rate on adoption. What recovered most of it: *structural* exclusions (which ARE corpus-independent, unlike a vocabulary word list) — drop `a/b/c` triples, 5+-digit numbers (issue/line numbers), and `N/N` identity tallies (a population, never a rate): 183 → 75 at zero sensitivity cost. The residual is irreducible: the discriminator is whether the denominator is a *population* or a *trial count* — semantic, no regex reaches it. So RATIO is intrinsically part corpus-bound; state that as a limit rather than tuning toward zero. UNIVERSAL (modal verbs) is not, because modal verbs mean the same thing in every corpus — that asymmetry is the transferable result. Method note: reproduce a peer's described false-positive classes *locally* before conceding a limit or tuning.
