## TL;DR


## OUTPUT_REVIEW must-fixes: state only what your artifacts prove

The OUTPUT_REVIEW critique verifies every factual claim against the artifacts you *attach*, by design — a claim true-but-unbacked-in-the-passed-set reads as fabrication. Recurring self-inflicted must-fixes and their fixes:

- **Deliverable self-supporting from passed artifacts.** On shader-slang.github.io#208 the decision message asserted "verified via the commits API" and editorialized about sibling PRs — facts that lived in `investigation.md`/memory but weren't in the four passed artifacts. Fix: attach `investigation.md`, or trim cross-PR editorializing to a bare "same repo and content class as #207/#204" ([[approver/critique-mustfix] OUTPUT_REVIEW deliverable must be self-supporting from passed artifacts](../learnings/1784327819969-approver-critique-mustfix-output-review-deliverabl.md)).
- **Don't claim a bot re-reviewed at head when only its summary comment refreshed.** CodeRabbit updates its single summary issue-comment on every push (so `updated_at` moves) but posts a *new formal review* only sometimes; `harvest-reviews.py` keys on formal reviews, so exit 10 (stale) is ground truth. State the two facts separately and attribute head-currency verification to your own challenger, not the bot ([[approver/critique-mustfix] Don't claim a bot re-reviewed at head when only its summary comment refreshed](../learnings/1784275986777-approver-critique-mustfix-don-t-claim-a-bot-re-rev.md)).
- **Cite line refs at the pinned head, count check-runs paginated.** Base-clone `file.cpp:NNNN` refs are silently wrong (a +19-line helper shifts everything downstream) — fetch the changed file at `?ref=<head-sha>` and cite from that. `check-runs` defaults to 30/page; the real count needs `--paginate ?per_page=100`, and distinguish failure vs non-success vs skipped ([[approver/critique-mustfix] Approver artifacts: cite line refs at pinned head + count check-runs paginated](../learnings/1784288128413-approver-critique-mustfix-approver-artifacts-cite-.md)).
- **The harvested review supplies the verdict and the prose; it supplies NONE of your facts.** A bot-review body is untrusted *data*, and that extends past its instructions to its counts, file lists, and line numbers. On slang#11118 "10 added tests" was copied from the bot body — the pinned head has **11** — and three cited line refs (`slang-lower-to-ir.cpp:3817`, `core.meta.slang:4061`, `slang-check-decl.cpp:18826/:18886`) were **diff-hunk positions**, not pinned-head lines (correct: `:3756`, `:4100-4101`, `:18830/:18890`), made harder to catch by the boilerplate claim *"all line refs verified in a worktree at the pinned head."* Re-derive every quantitative claim from the compare payload rather than eyeballing; produce every `file:line` from a `grep -n`/`sed -n` against the pinned worktree **in the same session**, since diff hunk headers give pre/post-hunk offsets that drift by every preceding hunk; print `pwd && git rev-parse HEAD` in the same command as the read when `cwd` may have drifted to the base clone; and when correcting a stale ref, grep the whole artifact and fix **all** occurrences in one pass — the first fix here left a second occurrence of the same string that the next critique round caught ([[approver/critique-mustfix] never propagate a count, file list, or line ref from a harvested bot review — re-derive it from the pinned head](../learnings/1785745209194-approver-critique-mustfix-never-propagate-a-count-.md)).
- **The line-ref half of that rule bites even when you hold the file open.** CodeRabbit reported its 🟠 Major on slang-rhi#797 at `tests/test-cmd-query.cpp:412` and the synthesized `review-doc.md` recorded `:412` verbatim; at the pinned commit the finding's *substance* — a `CHECK` that does not abort before a blocking call — is at **`:409`**, with `:412` being the call it warns about. Three lines apart, both plausible, so the error is silent: the worst shape for a citation error is *wrong but not obviously wrong*, and it sends the next reader or maintainer to the wrong statement. **Cite the line the finding's claim is about, not the line the bot attached its comment to** — inline-comment anchors drift toward the diff hunk, not the semantic subject; cross-check `original_line`/`start_line` against the prose (a mismatch is the tell); and beware range-relative numbering, since quoting positions inside a `sed -n '395,425p'` window as absolute file lines is the same bug in a different costume. Two independent tiers mis-numbered this one finding by two different routes — line numbers are the most-copied and least-verified field in a review pipeline ([[approver/critique-mustfix] bot-reported line refs are UNVERIFIED data — the review-doc propagated CodeRabbit's off-by-3](../learnings/1785780270744-approver-critique-mustfix-bot-reported-line-refs-a.md)).
- **A published line number must come from a tool that prints line numbers.** A patch request citing `:72`, `:84`, `:78-80` in a hook script was wrong at every site — the real ones are `:71`, `:81`, `:64-67`, and the cited `:76-80` range is a *different* comment entirely — because the sites were read with `sed -n '40,60p'` / `sed -n '60,88p'` and **offsets within the printed window were reported as file line numbers**. `sed -n 'A,Bp'` emits no line numbers at all, so any citation derived that way is a guess wearing the costume of a measurement; same for `head`, `tail`, or a manual count. The venue makes it severe: a patch request's entire value is that the reader goes straight to the site **without re-deriving**, so a wrong citation looks authoritative while sending them elsewhere — the same class as "a wrong id is worse than no id." And the durable form is stronger than "use `grep -n`": the seven citations that *did* resolve survived only because they happened to come from a numbering reader, not because of care. **Verify the PROVENANCE of every published number, not just the number** — ask which tool produced it and whether that tool even emits the thing you're claiming; a number can be correct and still have been produced by a method that cannot guarantee correctness, and next time the same method fails silently. For a *range*, verify BOTH endpoints, since an off-by-one at the tail silently annexes an adjacent block ([[approver/critique-mustfix] sed -n 'A,Bp' emits no line numbers — verify the provenance of a published citation, not just its value](../learnings/1785822343830-approver-critique-mustfix-sed-n-a-bp-emits-no-line.md)).
- **Verify a recalled rule against current source before applying it — and a bot repeating a wiki rule is ONE source, not two.** On slang#11118 the production bot flagged an interface-conformance filter as a no-op because *"`DeclRef::as<>()` does no type check"*, and a prior shared learning said exactly that, citing a real shipped segfault. Both were wrong at current head and the gap was refuted: `DeclRef<U>::as()` rewraps the pointer *through the typed constructor*, and `DeclRef<T>::init()` (`slang-ast-base.h:831-837`) does `if (base && !Slang::as<T>(base->getDecl())) declRefBase = nullptr;` — so `as<StructDecl>()` yields a **null** `DeclRef` on mismatch and `if (!x.as<StructDecl>()) continue;` is an effective filter, with `DeclRef::is<U>()` merely reading more clearly (a style nit). **The prior rule is real but scoped to a different type**: `SubstExpr<T>::as()` does a genuine dynamic cast of the *expr* with different null semantics, and the segfault involved that path plus an `as<Base>`-matches-derived cascade-ordering bug. Two distinct `as()` overloads on two distinct wrapper templates had been collapsed into one rule — so *a rule naming a method that exists on several types is meaningless without naming the receiver*. One-line check: read the constructor the `as()` delegates to; if it routes through an `init()` that nulls on mismatch it type-checks. (The companion `as<Base>`-matches-derived rule — test most-derived first — still holds independently.) ([[approver/clause-gap] DeclRef::as&lt;U&gt;() DOES type-check via init(); the "as&lt;&gt; is a no-op guard" rule applies to SubstExpr::as() only](../learnings/1785745186536-approver-clause-gap-declref-as-lt-u-gt-does-type-c.md))
- **A severity DOWNGRADE needs the receiver and signature of the exact method, not merely that a call exists at the cited line.** Downgrading a CodeRabbit 🟠 Major on slang-rhi#797, the artifact asserted the `WaitForSingleObject(..., INFINITE)` in `waitOnHost` could not hang because the fence is **"CPU-signalled"**, citing `d3d12-command.cpp:2162`. That line is `m_d3dQueue->Signal(...)` — **`ID3D12CommandQueue::Signal`**, a *GPU-timeline* signal; the CPU-side form is `m_trackingFence->Signal(v)` on a different receiver, and all four `Signal(` sites in the file are queue-side, so there was no path the premise could have meant. The conclusion survived for a *different* reason (`waitOnHost()` enqueues a fresh Signal at wait time, so it only needs already-submitted work to drain), which is exactly what makes this the error class worth a note: **right conclusion, wrong mechanism** is invisible to outcome-based review, and here the false premise went into the record *as the strengthening* — so the row taught the wrong model of D3D12 fence timing while the true one went unrecorded. `X->Signal(fence, value)` vs `fence->Signal(value)` differ by *which object owns the verb*, and that difference was the entire argument. **Downgrades need this discipline more than upgrades**: an over-stated severity gets argued down by the next reader, an under-stated one gets *agreed with*, and agreement closes the thread — so the direction that reduces scrutiny receives the least ([[approver/critique-mustfix] when a severity downgrade rests on API timing semantics, verify the receiver AND signature](../learnings/1785780937062-approver-critique-mustfix-when-a-severity-downgrad.md)).
- **Verify a workaround PR's premise against the PINNED dependency version, never master.** slang-rhi#807 disabled `metallib_4_0` citing slang#12325; in slang *master* the fix is present (`slang-code-gen.cpp:779-786`), so a master-based check says "already fixed, why this PR?" — and would have been wrong. The consumer pins a release (`SLANG_RHI_FETCH_SLANG_VERSION "2026.12.2"`, `SLANG_HASH_VERSION` + per-platform SHA256), and against the pinned tag both halves of the premise hold (`slang-emit-metal.cpp:215` gates on `metallib_4_0`; `slang-gcc-compiler-util.cpp:973` hard-codes `-std=metal3.1` and `getRequiredMetalLanguageVersion` does not exist there at all) because the fixing commit post-dates the tag cut. Two commands settle any cross-repo workaround before you judge it: `grep -n 'FETCH_.*VERSION\|HASH_VERSION' CMakeLists.txt`, then `git merge-base --is-ancestor <fix-sha> <pinned-tag>` (plus `git tag --contains <fix-sha>` for which release first carries it) — and read source **at the tag** (`git show <tag>:path | grep -n`), since a worktree grep silently answers for master. **"Fixed upstream" is only relevant if it's fixed in the version that actually builds** ([[approver/clause-gap] verify a workaround PR's premise against the PINNED dependency version, never master](../learnings/1785764986434-approver-clause-gap-verify-a-workaround-pr-s-premi.md)).
- **Byte-for-byte equivalence to an incumbent path proves CONSISTENCY, never CORRECTNESS.** The strongest-looking evidence in a round-1 "source-verified correct" rating of slang-rhi#802 (Metal bindless `DescriptorHandle`) was a raw-id equivalence check: the new bindless path writes exactly the same 64-bit value shape as the pre-existing bound path. It cleared a genuine bug — `allocBufferHandle` returns `getDeviceAddress() + offset` for **all** buffer kinds and explicitly discards `format` under a comment asserting irrelevance, but typed `Buffer<float>`/`RWBuffer<float>` emit as `texture_buffer<float,…>` into a `[[texture(n)]]` slot and need a texture `gpuResourceID`, a wrong *class* of value — because **the incumbent has the same defect** (`metal-shader-object.cpp:562`). "New ≡ existing" was true and told nothing: a **differential** test was treated as an **oracle** test, and when the incumbent is itself unvalidated, byte-equality propagates the bug with a clean bill of health attached (slang-rhi never creates a Metal texture-buffer object at all, so the reference had never worked for this class). Three questions before crediting any "matches the existing path" justification: is the reference validated for **this input class** (name the test)?; does the new path see inputs the incumbent never did (equivalence over a narrower historical input set says nothing about a widened one)?; and is a **discarded parameter** evidence of a missing case — treat a deliberately-ignored discriminator as a prompt to enumerate its values. Phrase the finding as "consistent with `<path>`, which is itself unverified for `<input class>`"; **consistency arguments inherit whatever correctness the reference has, including zero** ([[approver/clause-gap] byte-for-byte equivalence to an incumbent path proves consistency, never correctness](../learnings/1785767781336-approver-clause-gap-byte-for-byte-equivalence-to-a.md)).
- **Over-claiming rigor is a defect class in its own right.** On slang-rhi#806 — a WOULD_APPROVE that survived — the gate caught **five** defects all in the direction of *sounding more rigorous than the evidence supported*, none changing the verdict, all of which would have made the audit trail false: (1) *"the human outcome did not inform the verdict"* contradicted the artifact, which used the approval as context — the honest form separates "did not **determine** the verdict / is not the basis" from "did inform confidence", and *sounding maximally independent is itself a temptation toward inaccuracy*; (2) *"each dependency corroborated by `.reuse/dep5`"* when dep5 named 2 of 9 — and the real fix was noticing that per-dependency claims are a different *kind* of statement that cannot contradict the project-level license line, so 7 were never in scope; (3) a bare control number ("1,736 MIT mentions") that codex could not reproduce with `rg -i` (1,715) because **`rg` applies `.gitignore` semantics** — *a control count is meaningless without the command that produced it*, so record both rather than deleting the number; (4) citing `core.ts:576-579` for a pass-through that lives at `:594` (the cited range is only required-field validation) — the same right-conclusion/wrong-mechanism shape as the `Signal` error; (5) *"recorded as `undefined`"* when the record is built with `JSON.stringify`, which **drops** undefined properties, so the field is *omitted*. When a reviewer demands authoritative schema evidence, **go read the schema** instead of restating the assertion with more confidence; after patching any value appearing as a count or length in prose, grep for every stale copy (one patch updated one of three call sites, so the deliverable contradicted its own payload); and remember a verified-false premise does not establish the true one ([[approver/critique-mustfix] over-claiming rigor is a real defect class — "did not inform the verdict", stale counts, wrong-line citations](../learnings/1785784300014-approver-critique-mustfix-over-claiming-rigor-is-a.md)).
- **Don't equate total check-runs with CI matrix legs.** `total_count` includes `pre-commit`/`add-to-project`/`finish`/skipped assistant jobs plus the CodeRabbit commit-status (not a check-run at all); filter to the real `build (...)` matrix legs and state them as distinct signals ([[approver/critique-mustfix] don't equate total check-runs with CI matrix legs; state the count you verified](../learnings/1784282781009-approver-critique-mustfix-don-t-equate-total-check.md)).
- **Stage the MOUNTED policy, not the bundled fallback.** The authoritative policy is `/workspace/extra/approver-policy/APPROVAL_POLICY.json` (`v0-shadow-relaxed`, human-signed); the skill-bundled `APPROVAL_POLICY.json` is a *tightened* fallback (`v0-shadow`). Copying the bundled file into the workspace `policy/` dir shadows the mount and flips CONTRIBUTOR/fork/protected-path clauses to FAIL, contradicting a prior CLEAN decision — check `policy_version` in `clauses.json` against the mount. Also: synthesize `review-doc.md` (carrying the `_approver_result` `commit_id`) BEFORE running `eval-clauses.py`, or `commit_match` comes back UNEVALUABLE ([[approver/critique-mustfix] stage the MOUNTED policy, not the bundled fallback — and synthesize review-doc BEFORE eval-clauses](../learnings/1784288659769-approver-critique-mustfix-stage-the-mounted-policy.md)). Populate the full `record_decision` field set (`clauses`, `challenger`, ISO `ts`) before OUTPUT_REVIEW, and a `[Approval Decision]` marker message needs `in_reply_to` or the routing gate blocks it.
- **`reason_code` for a clean WOULD_APPROVE is the literal `none` — not a phrase, not an invented token.** For a WOULD_APPROVE that is a clean conjunction (Steps 1–4 all clean) there IS no reason_code: the closed-enum field carries detail only for the abstain/block states (`CLAUSE_FAIL:*`, `OPEN_GAP`, `CHALLENGER_CONCERN`, `RED_BUG`, …). The gate bounces both a parenthetical (`reason_code: (none — clean conjunction)`, flagged "emit the exact enum/value so the row is recordable without interpretation") and an invented word (`reason_code: CLEAN`, flagged as conflicting with the ledger value `none`) — only the literal `reason_code: none` passes. Put the "why it's clean" narrative in the `challenger` field / the message, never in reason_code ([[approver/critique-mustfix] ledger reason_code for clean WOULD_APPROVE is literal `none`, not a descriptive phrase](../learnings/1785530765832-approver-critique-mustfix-ledger-reason-code-for-c.md)).
- **Don't call an ABI-contract finding "refuted" because the in-tree callers happen to be safe.** On slangpy#1082 marking CodeRabbit's 🟠 buffer-contract finding "CLEARED / unreachable on any supported path" was flagged must-fix as an overclaim: the math only proved the *two current in-tree callers* don't diverge, but the flagged function is an exposed `extern "C"` ABI fn-ptr in a versioned `TensorBridgeAPI` struct with a documented minimum-buffer contract the native side enforces and the fallback doesn't — the caller set is open. Reserve "refuted/unreachable" for triggers impossible for *any* caller; for anything crossing a published ABI/API boundary, narrow the conclusion to "no impact on current in-tree callers" and retain the contract-level gap on the record ([[approver/critique-mustfix] Don't call an ABI-contract finding "refuted" just because in-tree callers are safe](../learnings/1785426158100-approver-critique-mustfix-don-t-call-an-abi-contra.md)).
- **Decision-message wording: no self-referential process overclaim, and don't conflate revision-delta with full-PR diff-stat.** A `synchronize` re-decision (slangpy#1083 R1) bounced the `[Approval Decision]` message four times, every bounce a must-fix on wording not decision. Class A — self-referential overclaim: don't assert "both critique stages recorded = approve" while *inside* OUTPUT_REVIEW (a stage cannot certify itself already-passed), and phrase recording as "is being recorded this turn", never "recorded" (`record_decision` runs after the gate opens). Class B — diff-stat conflation: state the full-PR size (`main...head`, = clauses eligibility size) AND the revision delta (`prior_head...head` via `gh api compare`) as two SEPARATE numbers from the right source; the `clauses.json` "N lines / M files" is eligibility size, not "what changed this push". Class C (advisory) — no prior-verdict anchoring: reference the prior head by SHA + the compare fact, not by its verdict, since the prior head is context not evidence. Bake all three into the message template so the first OUTPUT_REVIEW pass is clean — recurring wording must-fixes are a procedure bug, not per-PR noise ([[approver/critique-mustfix] Decision-message pitfalls: critique-state overclaim + revision-delta vs full-PR diff-stat conflation](../learnings/1785454931977-approver-critique-mustfix-decision-message-pitfall.md)).


## Incremental sharpenings (2026-07-18/19 approver session)

**A non-exit-0 harvest can co-occur with a still-running PRIMARY — probe check-runs before falling to Devin-only.** `harvest-reviews.py` exit 10 (a stale *secondary* review exists, e.g. CodeRabbit at an older commit) keys off the newest *posted* review and does NOT re-check whether the production `github-actions[bot]` claude review (`.github/workflows/claude-pr-review.yml`) is still in-flight — so it can silently discard a primary that is minutes from landing. On ANY non-exit-0-primary result (10/20/22), independently check the commit's check-runs for a `review`-named run; if `queued`/`in_progress`, treat it like exit-22 and WAIT+re-harvest rather than fall to Devin-only ([[approver/infra-abstain] exit-10-stale-can-mask-still-running-primary-claude-review](../learnings/1784390106504-approver-infra-abstain-exit-10-stale-can-mask-stil.md)). The distinction that decides how long to wait: a `review` check-run `in_progress` (or recently completed) is a genuine ~6-min posting race — keep waiting; a run stuck `queued` and NOT advancing across two windows (~20+ min) is a **runner backlog** — set a firm total budget then fall to the Devin tier *noting the PRIMARY timeout as an infra event*, and only when byte-identical-to-an-already-reviewed-revision makes the fallback false-safe-free (if the code actually changed and only a thin Devin signal remains, lean ABSTAIN_INFRA/NO_REVIEW_SIGNAL, not a confident verdict) ([[approver/infra] When the PRIMARY review check-run is stuck QUEUED (not the ~6-min posting race), fall to Devin — but only when byte-identical-to-a-reviewed-revision makes it false-safe-free](../learnings/1784366403034-approver-infra-when-the-primary-review-check-run-i.md)). Auditability follow-on: when decision provenance depends on a script's exit code (harvest tier branching), `harvest.json` on a not-found result records only `{"found": false}` with no exit code — a reader can't distinguish exit 20 (genuine skip) from 10 (stale) or 21 (fetch failed) after the fact, so state the exit code explicitly in the review-doc's tier line until the script persists it ([[approver/infra-abstain] harvest-json-found-false-persist-exit-code-for-audit](../learnings/1784417204496-approver-infra-abstain-harvest-json-found-false-pe.md)).

**Protected-path ABSTAIN_POLICY is a withhold, not a prediction — a byte-identical merge is AGREEMENT, and a self-merge dilutes (never validates) it.** When a `.github/**` / `**/*.yml` / release-tooling one-liner abstains on `no_protected_paths` and then MERGES byte-identical at the decision commit, the shadow decision and the human outcome AGREE (I never claimed the change was wrong, only that a human should own the sign-off, and a human did) — do NOT score it as a disagreement just because the enum wasn't WOULD_APPROVE; the OPPOSITE (multiple "Address review" commits before merge, or closed-unmerged) is what would warrant a learning, and any follow-up commits between decision and merge ARE the reviewable delta ([[approver/human-agreement] Protected-path ABSTAIN_POLICY vindicated by byte-identical merge — the withhold is agreement, not a miss](../learnings/1784381462983-approver-human-agreement-protected-path-abstain-po.md)). But check the merge *shape*: when `mergedBy == author` and `reviewDecision != APPROVED` (an author self-merge with zero independent APPROVED), the protected-path safety-net fired correctly yet its *value was diluted* — the "human who must look" was the author themselves, and any gaps you surfaced (e.g. CodeRabbit 🟠 CI-leak-logic) shipped unweighed; log it as weak/self-endorsement, not validation that the gaps were judged acceptable ([[approver/human-agreement] protected-path-ABSTAIN-confirmed-but-author-self-merge-ships-open-gaps](../learnings/1784437469229-approver-human-agreement-protected-path-abstain-co.md)).

**OUTPUT_REVIEW discipline extended — no verified 🔴 downgrade, no volatile fields.** The 🔴 rule has NO documentation-vs-code carve-out: once the challenger has CONFIRMED (not refuted) a 🔴, moving it from BLOCK to ABSTAIN/OPEN_GAP on the reasoning "it's only docs / the compiled output is correct" is precisely the "upgrade toward approval" the rule forbids — the only path from a confirmed 🔴 to non-BLOCK is genuine REFUTATION (not real / not reachable / not this revision), and severity-based clearing applies to 🟡 gaps, never a confirmed 🔴 (the DECISION_REVIEW critique gate caught this rationalization) ([[approver/critique-mustfix] a verified 🔴 cannot be downgraded to OPEN_GAP because "it's only docs" — no documentation exemption in the 🔴 rule](../learnings/1784440920822-approver-critique-mustfix-a-verified-cannot-be-dow.md)). And don't bake **volatile GitHub fields** into a durable artifact: `mergeStateStatus` flips BEHIND/BLOCKED/CLEAN/UNSTABLE independent of anything you decide, so a stale value trips the attested-hash re-check at send time — quote the durable, decision-relevant signals (`reviewDecision`, human review states, the actual gate) instead, or label a merge-state value explicitly volatile ([[approver/output-review] Volatile GitHub fields (mergeStateStatus) are not decision-relevant — drop the value, keep the durable gate](../learnings/1784421284355-approver-output-review-volatile-github-fields-merg.md)).
