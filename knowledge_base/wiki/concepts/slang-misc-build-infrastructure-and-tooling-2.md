# Slang Build Infrastructure — Packaging, Generators, PCH, and Binary Provenance

## TL;DR

- `generator()` tools are `EXCLUDE_FROM_ALL` — the default/Debug preset does not build them; build the specific target when you need a generator.
- `SLANG_USE_SYSTEM_*` has no bundled fallback, and docs-of-record need per-cell verification (don't trust a summary table over the actual CMake).
- `slang-capability-generator` has an alias-pairing invariant and a silent exit-0 — a mispaired alias produces no error; verify the generated output.
- Stale GCC PCH snapshots FIDDLE macro state → bogus codegen errors; know what `SKIP_PRECOMPILE_HEADERS` actually does before relying on it.
- Binary provenance: a stale prebuilt `slangc` embeds the OLD core module — rebuild the bootstrap/core-module step, don't trust an old binary's behavior.
- Release packaging: WASM bypasses CPack; `slang-wasm` ships build artifacts but has no npm publish, so web-packaging asks are maintainer-infra, not compiler work.
- MSVC `/DEBUG` for Release PDBs silently disables `/OPT:REF` and `/OPT:ICF` (#12054).
- Companion page [[wiki/concepts/slang-misc-build-infrastructure-and-tooling.md]] covers CMake options, compiler flags, downstream-compiler discovery, and language-server config.

This page collects the dated incremental-fold build notes: release packaging (WASM/CPack), generator tools excluded from the default preset, the capability-generator alias-pairing invariant, stale-PCH FIDDLE-state codegen errors, and binary-provenance traps (a stale prebuilt `slangc` embedding the old core module). Companion to [[wiki/concepts/slang-misc-build-infrastructure-and-tooling.md]] (CMake options, compiler flags, downstream-compiler discovery).

## MSVC /DEBUG for Release PDBs Silently Disables /OPT:REF and /OPT:ICF (#12054)

Slang's default MSVC Release build loses dead-code elimination and identical-COMDAT folding (larger binaries, no functional change) because `SLANG_ENABLE_RELEASE_DEBUG_INFO` defaults ON, injecting `/DEBUG` into MSVC Release links -- and MSVC's linker flips `/OPT` defaults (`REF->NOREF`, `ICF->NOICF`) whenever `/DEBUG` is present, which Slang never re-asserts. The non-obvious wrinkle: `/DEBUG` implies `/INCREMENTAL`, under which `/OPT:REF|ICF` are silently ignored (LNK4075), so re-adding them only works with incremental OFF -- Release already carries `/INCREMENTAL:NO` (clean) but a fix that also touches RelWithDebInfo must guard against LNK4075. Verify MSVC-linker behavior against Microsoft's `/DEBUG` doc + a code trace, not DeepWiki ([slang#12054: MSVC /DEBUG for Release PDBs silently disables /OPT:REF and /OPT:ICF](wiki/learnings/1783729799704-slang-12054-msvc-debug-for-release-pdbs-silently-d.md)).

## Release Packaging: WASM Bypasses CPack (2026-07-14 fold)

Slang release packaging has two distinct edit sites, and the File-check step is not a validation gate. Platform ZIP/TGZ archives are built by CPack (files enter via `install(... COMPONENT metadata)` in `CMakeLists.txt`), but **WASM packages bypass CPack** entirely — so adding files to release archives (e.g. issue #12083's `LICENSES/` dir) requires touching both sites, and the release File-check step will not catch a WASM omission ([Slang release: WASM packages bypass CPack; File-check is not a validation gate](wiki/learnings/1783957891963-slang-release-wasm-packages-bypass-cpack-file-chec.md)).

### macOS release signing failure was a greedy version-parse bug, not an expired cert (#12143)

The macOS release build's "Sign and notarize binaries" failure starting at tag v2026.12.0.1 was framed by jkwak as an expired signing cert, but triage proved a **workflow version-parsing bug**. `release.yml:217` re-derives the version from the resolved dylib filename with a greedy regex `sed -E 's/.*\.0\.([0-9]+(\.[0-9]+)*)\.dylib$/\1/'`. The real file is `libslang-compiler.0.${SLANG_VERSION_NUMERIC}.dylib`, and `SLANG_VERSION_NUMERIC` accepts N dotted components; for a 4-component tag the file is `libslang-compiler.0.2026.12.0.1.dylib`, where greedy `.*\.0\.` matches through the interior `.0.` and extracts `version=1`, so the rebuilt binaries array points at a nonexistent `libslang-compiler.0.1.dylib` and the sign loop's else `exit 1`s **before** codesign runs. Latent since PR #8926; failures began exactly at the first 4-component tag. The `"0 valid identities found"` line is a **red herring** — it comes from `security find-identity -v` at :177, which runs before cert import (:189) and gives zero signal on cert validity because the job dies earlier. Immediate fix: anchor the parse on the fixed prefix, `sed -E 's/^libslang-compiler\.0\.(.*)\.dylib$/\1/'`. Two lessons this reinforces: (1) it's another workflow-file bug the bot can't PR (no `workflows` permission, same as #11985/#12062), so it routes to a human/maintainer, not slang-fixer — the same routing consequence already noted for the RelWithDebInfo/common-setup change above; (2) method — when a CI failure is framed as cause X, read the actual failing step's script and reproduce with a 30-second `sed` (the error string `0.1.dylib` itself encoded the real bug), rather than accepting the initial framing ([slang release.yml macOS signing: greedy version-parse breaks on 4-component tags](wiki/learnings/1784270564328-slang-release-yml-macos-signing-greedy-version-par.md)).

## generator() Tools Are EXCLUDE_FROM_ALL — Not Built by the Default/Debug Preset (2026-07-21 fold)

A tool registered via the `generator(...)` macro in `tools/CMakeLists.txt` is `EXCLUDE_FROM_ALL` and its only reverse-dependency is the `all-generators` custom target — which has no `ALL` keyword, so nothing in a normal build depends on it. `cmake --workflow --preset debug` (configure `default` + build the default `ALL`) does NOT build generator tools; the `generators` preset that builds `all-generators` runs only in the WASM/emscripten CI branch. Consequence: if a CI step (or the standard debug/release build) needs a generator tool's binary, it will be absent — `find build/generators -name <tool>` returns empty. Danger: a build subagent that runs `--target <tool>` explicitly produces it and masks the gap; only a plain default build reveals it. Verify a generator-backed CI step by doing a *plain* `cmake --build --preset debug --target slang-test` (NOT `--target <tool>`) and checking the binary appears. Fix (in-tree convention): make a real ALL-graph target depend on it. `REQUIRED_BY <t>` uses `add_dependencies(<t> …)` which requires `<t>` to already exist — the existing `REQUIRED_BY slang-test` precedents work because they're defined *after* the `slang-test` target (~:284), so a `generator()` call near the top of the file can't use it (configure error "Cannot add target-level dependencies to non-existent target slang-test"). Instead add `add_dependencies(slang-test <tool>)` *after* the slang-test definition (~:311), guarded `if(TARGET <tool> AND NOT SLANG_GENERATORS_PATH)` (generators are imported when cross-compiling). Found via slang#12157 — a CI enforce step called a generator tool a reviewer proved was never built in the debug path ([Slang generator() tools are EXCLUDE_FROM_ALL — not built by the default/debug preset](wiki/learnings/1784567879388-slang-generator-tools-are-exclude-from-all-not-bui.md)).

## SLANG_USE_SYSTEM_* Has No Bundled Fallback, and Docs-of-Record Need Per-Cell Verification (2026-07-23 fold)

Determine a "use system package" option's fallback behavior by reading the **`add_subdirectory` bundled-build gate**, not the `find_package` line: in Slang's `external/CMakeLists.txt` every `SLANG_USE_SYSTEM_<X>` follows `if(NOT SLANG_USE_SYSTEM_<X>) add_subdirectory(<x>) endif()`, so ON ⇒ bundled skipped **unconditionally** with NO fallback — `CONFIG QUIET` only suppresses the not-found *message*, it does not re-enable the submodule (a claim two independent sources got wrong, caught by codex reading the gate) ([SLANG_USE_SYSTEM_* has no bundled fallback — QUIET ≠ fallback; verify at the add_subdirectory gate](wiki/learnings/1784761099055-slang-use-system-has-no-bundled-fallback-quiet-fal.md)). Relatedly, docs-of-record PRs (licenses, dependency→output maps, submodule pin policy) draw many small factual rounds — verify **every cell** from the authoritative source, never analogy: read each dep's LICENSE/COPYING or source-header banner (dxc = NCSA in `dxcapi.h`; lua's MIT is at the END of `lua.h`), derive output mapping from actual `LINK_WITH_*`/`#include` consumers (metal-cpp/Vulkan-Headers feed tools/slang-rhi, not the compiler backend), and treat `.gitmodules` `branch =` as possibly a TAG (fast_float `v8.2.7`) not always a branch ([docs-of-record PRs (licenses/deps/pin-policy) need per-cell source verification](wiki/learnings/1784765808308-docs-of-record-prs-licenses-deps-pin-policy-need-p.md)).

Docs *routing* is likewise decided by the target folder: `docs/design/*.md` is HAND-maintained developer design notes (add a line to its `README.md` index; write against function/pass names, not line numbers) and is where a NEW canonical design doc belongs, whereas `docs/generated/design/**` is AUTO-GENERATED (front-matter `generated: true`) and hand-edits there are overwritten — so route "please document X" tasks to `docs/design/`, never to the generated tree (`docs/user-guide/a4-02-reference-capability-atoms.md` from `slang-capabilities.capdef` is similarly generated) ([docs/design is hand-maintained; docs/generated/design is regenerated — route new design docs to docs/design](wiki/learnings/1784830597951-slang-docs-routing-docs-design-is-hand-maintained-.md)).

## slang-capability-generator: Alias-Pairing Invariant and Silent Exit-0 (2026-07-24 fold)

Two coupled tooling bugs around `slang-capability-generator` (`tools/slang-capability-generator/capability-generator-main.cpp`). First, `validateInternalAtomExternalAtomPair()` requires EVERY non-`Abstract` atom whose name starts with `_` to have a matching public (`_`-stripped) atom — the check is **universal, with no exemption for `alias` atoms or for `_*_latest`** — so adding `alias _FOO = ...;` without a public `alias FOO = ...;` is a latent build break (`#12211`: `_GLSL_latest`/`_sm_latest` unpaired → error 20007 → Windows-Release MSB8066). It slips past incremental CI because the invariant only fires on a *clean* capdef regeneration (incremental builds reuse cached generated headers); precedent for public "latest" aliases is `spirv_latest`/`metallib_latest`, and the `/// [Version]` doc comment must go on the PUBLIC alias for the generated capability-atoms doc (which you must regenerate in the same PR). Takeaway: when adding any internal `_atom`, add its public pair in the same edit or confirm one exists ([capdef internal _atom aliases (incl _*_latest) MUST have a public pair or generator errors 20007](wiki/learnings/1784890869028-capdef-internal-atom-aliases-incl-latest-must-have.md)). Second, and the *root* of why #12211's bad capdef passed CI: the generator **emits error-severity diagnostics but returns exit 0 and writes its output files before any error check** (`#12212`). `validateInternalAtomExternalAtomPair()` returns void (only diagnoses), `parseDefs()` calls it then unconditionally `return SLANG_OK`, and `main()` writes files then `return 0` — Ninja keys off process status so invalid capdefs pass the full CI matrix. Fix pattern (matching `slang-fiddle` precedent): `if (m_sink->getErrorCount()) return SLANG_FAIL;` in `parseDefs()` (so `main()`'s existing `SLANG_FAILED` guard fires and file writes never happen), keying on **error count, not "any diagnostic"** (the doc-path diagnostic is a Warning that must stay non-fatal). Method note that recurred: DeepWiki answered *incorrectly* that `main()` returns 1 on validation failure — for concrete control-flow/exit-code claims, read the actual source (and run the prebuilt binary: append an unpaired alias to a temp capdef, run the generator, `echo $?` = 0 despite 3× error 20007), don't trust DeepWiki ([slang-capability-generator exits 0 despite error diagnostics (issue #12212) + verify tool-exit claims against source not DeepWiki](wiki/learnings/1784891885921-slang-capability-generator-exits-0-despite-error-d.md)).

## Stale GCC PCH Snapshots FIDDLE Macro State → Bogus Codegen Errors; and What SKIP_PRECOMPILE_HEADERS Actually Does (2026-07-25 fold)

On GCC/Linux **Debug incremental** builds (Ninja Multi-Config, `SLANG_ENABLE_PCH=ON` by default), a stale precompiled header can produce ~400 bogus compile errors that *look* like FIDDLE codegen bugs — e.g. `expected unqualified-id before 'private'` inside `slang-ir-insts.h.fiddle`, cascading into incomplete-type errors for `IRFieldAddress`/`IRMakeStruct` — even though the generated `.fiddle` output is byte-identical to a clean machine (slang#12227). **The tell:** the diagnostic `#include` chain starts `<command-line>` → `cmake_pch.hxx`. Root cause (@HEAD 5281ccc66): the PCH headers (`slang-basic.h` + `slang-compiler.h`, `source/slang/CMakeLists.txt:263-264`) transitively pull in AST headers that each `#include` a `.fiddle`, and every `.fiddle` prologue redefines `FIDDLE`/`FIDDLEX`/`FIDDLEY` + `FIDDLE_<line>` macros keyed on `__LINE__` — so a `.gch` bakes in that transient preprocessor state. The build graph can't catch a stale/inconsistent `.gch` because invalidation is mtime-based but (1) `File::writeAllTextIfChanged` skips writes for identical content (unchanged `.fiddle` keep OLD mtimes), (2) `.fiddle` are declared `BYPRODUCTS` (mtimes not up-to-date markers; driven by an unconditionally-`touch`ed `.fiddle.stamp`), and (3) the PCH's dep on `slang-fiddle-output` is **order-only** — so `-Winvalid-pch` never fires (GCC considers the `.gch` structurally valid). Workaround: `rm build/source/slang/CMakeFiles/slang-common-objects.dir/Debug/cmake_pch.hxx.gch && cmake --build --preset debug`, or configure `-DSLANG_ENABLE_PCH=OFF`. Meta: two independent bugs get conflated — how a bad `.gch` is *created* (nondeterministic, undetermined) vs. how it *persists + mis-diagnoses* (fully understood); don't overclaim the causal chain to a maintainer. Parked build-system bug / P2, assignee jkwak-work (a PCH-speed-vs-robustness values call) ([Stale GCC PCH snapshots FIDDLE macro state → bogus codegen errors (slang#12227)](wiki/learnings/1784991435802-stale-gcc-pch-snapshots-fiddle-macro-state-bogus-c.md)).

The fix-direction review turned on a non-obvious CMake distinction that cost a round (PR #12230): triage's "Approach A" was `set_source_files_properties(<tu>.cpp PROPERTIES SKIP_PRECOMPILE_HEADERS ON)`, mirroring the existing `slang-rich-diagnostics.cpp` precedent — but `SKIP_PRECOMPILE_HEADERS ON` is a **per-translation-unit** property that makes *that whole `.cpp`* compile WITHOUT `-include cmake_pch.hxx`; it does NOT remove any particular header (the generated `.fiddle`) from the PCH content. Maintainer jkwak-work's mental model was the *different* mechanism "exclude the FIDDLE generated files from the PCH" (keep `.fiddle` includes out of the PCH root, or clean up macro state after the last FIDDLE marker) — which preserves the PCH for all TUs and fixes the root fragility. A naive per-`.fiddle` `#undef` epilogue does NOT work (codex caught this): each `.fiddle` is `#include`d near the TOP of its header and its macros are consumed LATER by that header's own `FIDDLE(...)` sites, so undef-ing at the physical end removes them before their consumers run. Lesson: when a triage hands you a CMake "approach," restate what the mechanism *actually does* (per-TU skip vs per-file exclusion vs generator-side neutralization) and match it to what the maintainer's words imply before shipping — "make a PR with approach A" can still be the wrong mechanism ([SKIP_PRECOMPILE_HEADERS is per-TU, not "exclude a header from the PCH"](wiki/learnings/1785019137366-skip-precompile-headers-is-per-tu-not-exclude-a-he.md)).

RESOLUTION (#12227 FIXED + MERGED as PR #12233, `1e0b3a441a`, maintainer jkwak-work, 2026-07-26) confirmed two ways the triage was directionally right but incompletely scoped. **(1) The failure is NOT limited to stale `.gch` from incremental builds** — the identical signature reproduced in **clean GCC Release** builds (SlangPy PR dispatches doing `git clean -ffdx` + fresh clone + `mkdir build`), so a *newly generated* PCH can be internally-inconsistent and consumed in the same highly-parallel clean build; "leftover .gch" was not the whole story. **(2) The winning fix is compiler-scoped PCH-header exclusion, not per-TU `SKIP_PRECOMPILE_HEADERS`.** Rather than compiling the two known-bad TUs without the PCH (a bounded allowlist that must grow), jkwak's merged fix keeps the FIDDLE-carrying `slang-compiler.h` out of the **GCC** PCH for *all* TUs by construction — `slang-basic.h` stays in the PCH for everyone, `slang-compiler.h` is PCH-included only for non-GNU compilers via `"$<$<NOT:$<CXX_COMPILER_ID:GNU>>:.../slang-compiler.h>"` — so MSVC/Clang keep the full PCH while GCC keeps FIDDLE macro state out of the PCH boundary (strictly better-layered than the per-TU allowlist). Chain note: triage verdict → jkwak authorized "approach A" → fixer built draft #12230 → jkwak pushed back (per-TU ≠ file-exclusion) → clean-Release evidence reframed #12230 as mitigation-not-root-cause → jkwak shipped (b) himself (#12233), auto-closing via `Fixes #N`; the bot chain's value was confirming the diagnosis + mitigation direction, and when a maintainer implements + merges their own fix, no bot GitHub comment is needed ([RESOLVED #12227: GCC PCH snapshots FIDDLE state — fix = exclude slang-compiler.h from the GCC PCH (all-TU), not per-TU SKIP_PRECOMPILE_HEADERS](wiki/learnings/1785072236731-resolved-12227-gcc-pch-snapshots-fiddle-state-fix-.md)).

## Binary provenance: a stale prebuilt slangc embeds the OLD core module (2026-07-27 fold)

A **deterministic** `tests/spirv/*.slang` FileCheck failure with a fixed name/prefix mismatch (e.g. `internal-spirv-asm-opname-prefix.slang` emitting `OpName %dotResult` where it expects `%__dotResult`) looks like a real master regression but is often a **stale-binary artifact**. The core modules (`hlsl.meta.slang`, `core.meta.slang`, …) are compiled into `slangc`/`slang-bootstrap` **at build time**, so a binary on disk carries whatever core-module content existed at the commit it was built from — regardless of the corrected source/test on disk. When a fix changes both a core-module `.slang` file AND a test that pins its output (here #12108 / PR #12190, commit 72985f871), running the new test against a prebuilt binary built before the fix reproduces the OLD output → the test "fails" while `git diff origin/master HEAD` on the emit sources is empty. Triage fast (read-only, no full rebuild needed to DISMISS): grep the CURRENT `*.meta.slang` for the expected string, note the binary's `-v` build tag + mtime, find the fix commit via `git log`, and `git merge-base --is-ancestor <fix> <binary-sha>` — if NO, the binary predates the fix ⇒ stale, DISMISS. Gold-standard confirm rebuilds with core-module header regen (`cmake -E touch source/slang/hlsl.meta.slang` → `generate_core_module_headers`); skipping the touch leaves the bootstrap embedding OLD source silently. Rule of thumb: a deterministic (not flaky) `tests/spirv` mismatch whose emit-source diff vs master is empty is a binary-provenance smell, not a regression — verify on a fresh rebuild before filing [tests/spirv OpName-prefix failures from stale slangc = core-module embedding, not a regression (verify binary provenance first)](wiki/learnings/1785167795738-tests-spirv-opname-prefix-failures-from-stale-slan.md) [Stale prebuilt slangc embeds old core module — false tests/spirv failures](wiki/learnings/1785167843971-stale-prebuilt-slangc-embeds-old-core-module-false.md).

## slang-wasm ships build artifacts but has no npm publish — web-packaging asks are maintainer-infra, not compiler work (2026-08-03 fold)

A recurring class of web/bundler triage (e.g. #12317 "bundler plugins for the web") hinges on a build-infrastructure fact rather than a compiler capability: **`slang-wasm` already emits everything an npm package needs, but nothing publishes it.** `source/slang-wasm/CMakeLists.txt` links with `--emit-tsd interface.d.ts` + `-sEXPORT_ES6=1 -sMODULARIZE=1`, producing `slang-wasm.js` + `slang-wasm.wasm` + `interface.d.ts`; these are assembled *only* in `.github/workflows/release.yml` (tag-triggered, Linux-only) by manual `cp`/`zip` (~lines 283-292, an `exit 0` bypasses CPack) into `slang-<version>-wasm.zip`. There is **no `package.json` in the source tree** and **no `npm publish`/`NODE_AUTH_TOKEN`/`registry-url` anywhere in `.github/workflows/`** (grep = 0). So "publish `@shader-slang/slang-wasm` to npm" is a *packaging + maintainer-infra* task (npm scope + `NPM_TOKEN` secret + publish cadence) — classify as a design/policy gate and HOLD, don't forward to the fixer as a compiler change. Two adjacent facts sharpen the triage: reflection→TypeScript-type codegen is *already* feasible on the bound surface (`ProgramLayout.toJsonObject()` + `getGlobalParamsTypeLayout`/`VariableLayoutReflection`/`TypeReflection`, backed by `source/slang/slang-reflection-json.cpp`) so an unplugin needs no new C++ — but `createSession` takes only an int target and exposes no compiler-*option* surface, so anything needing compile flags first needs the binding widened; and WGSL/WebGPU is officially experimental/WIP (`README.md:118`,`:126`, `docs/user-guide/09-targets.md:419`) — a status one Explore subagent got backwards, so verify it by direct README read and carry the WIP hedge into the public verdict ([slang-wasm ships types but is not npm-published; publishing is CI-packaging not compiler work](wiki/learnings/1785699886372-slang-wasm-ships-types-but-is-not-npm-published-pu.md)). This is the same "read the build graph / workflow, don't infer capability from the binding" discipline as the [SLANG_USE_SYSTEM_* add_subdirectory-gate](wiki/learnings/1784761099055-slang-use-system-has-no-bundled-fallback-quiet-fal.md) and [binary-provenance](wiki/learnings/1785167795738-tests-spirv-opname-prefix-failures-from-stale-slan.md) folds above.
