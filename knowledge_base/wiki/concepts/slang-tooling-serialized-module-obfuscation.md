# Serialized-Module & Obfuscation Verification (.slang-module chunks, -obfuscate, stripping claims)

Slang serializes a compiled module into a RIFF-style container (`.slang-module`) built from named chunks — `ast `, `ir  `, `SHA1`, `fdep`. Claims about what `-obfuscate`, debug-info stripping, or a serialization flag actually *do* to that container are easy to get wrong: the surface tools (a whole-file byte count, the docs, DeepWiki) all give plausible-but-wrong answers. The discipline is to parse the container per chunk and read the source, not the prose.

## TL;DR

- To prove a stripping / exposure claim on a serialized `.slang-module`, parse the container **per chunk** — a whole-file byte or substring count cannot say *which* chunk holds a name, and turns a decisive result into an ambiguous ratio (6 vs 4 reads as "partially stripped" and means nothing).
- `-obfuscate` acts on the **`ir  ` chunk only**; the `ast ` chunk is byte-identical with and without it, so a non-`public` symbol name survives in the AST. The doc claim that `-obfuscate` strips AST information is **wrong** (missing visibility filter; standing TODO at `slang-serialize-ast.cpp:1871-1872`).
- Take the container header layout from the **source**, never a generic RIFF assumption: Slang list chunks carry a 12-byte header (`Chunk::Header` + a type `FourCC`) with 8-byte alignment, not the classic 2-byte-aligned 8-byte header. FourCCs are enumerated in `slang-serialize-types.h`.
- Run the flow the docs recommend for **shipping** (e.g. `-obfuscate -g` → `.zip`, extracted back out), not just the convenient bare `.slang-module`, or the finding gets waved off as the wrong invocation.
- A green suite while the defect exists is positive evidence of a **coverage gap** — strictly stronger than "grep found no test," because it demonstrates no existing test constrains the property.
- "A test exists" is not "a regression would be caught": grep for the failure path (`SLANG_FAIL`), not the check — a `printf`-and-return-success check covers nothing.
- Verify serialized-module properties against the **artifact**, not the issue's closed state or a doc. IR-without-AST emission is genuinely removed (`SerialOptionFlag{ASTModule,IRModule}` deleted, both loaders hard-fail on a missing AST chunk); function-body elision did land (`FunctionDeclBase::body` has no `FIDDLE()` marker, so it is not serialized).
- **Stale `.slang-module` binaries shadow edited source by default** — for the edited module AND every importer. Set `CompilerOptionName::UseUpToDateBinaryModule` (API-only) to get a content-SHA1 freshness check over all transitive sources with automatic fallback to source; write and load with identical search-path strings.
- **A session keys loaded modules by name and by path, and nothing unloads them.** Reloading under a new name needs a different path string too (same path → dictionary assert; same name → E38202). Hot reload = a fresh `ISession` on the same `IGlobalSession` (#4645 won't-fix).
- **Obfuscation source maps are reachable from the component API**, not only from the deprecated `ICompileRequest` as `a1-03-obfuscation.md` says: with `lineDirectiveMode = SLANG_LINE_DIRECTIVE_MODE_SOURCE_MAP`, `IComponentType::getResultAsFileSystem` and `IComponentType2::getEntryPointCompileResult` both return the map. slang-wasm binds neither.
- Documentation is not a behavior oracle, and a wiki/QA layer (DeepWiki) that repeats a doc's claim is not an independent second source.
- **`-obfuscate` must match between the module producer and the consumer session.** An obfuscated `.slang-module` loaded without `-obfuscate` asserts in the linker (`slang-ir-link.cpp(399)`), and the reverse asserts in `transform-params-to-constref` (`layoutDecoration`). The existing test passes `-obfuscate` on both sides, which hides it. A hash-or-not decision for linkage names must depend only on the declaration, never on a session flag.

## A stripping claim needs a per-chunk parse — a whole-file count cannot locate a leak

Triaging shader-slang/slang#7497 (test coverage for obfuscation / debug-info stripping) at master `0864e60e6` produced a live documentation-versus-behavior discrepancy: `docs/user-guide/a1-03-obfuscation.md:39` and `:69` both promise that `-obfuscate` strips AST information from a `.slang-module`, and **it does not**. Obfuscation acts on the **IR chunk only** — the `ast ` chunk is byte-identical with and without `-obfuscate` (2164 B both) and a non-`public` symbol name survives in it. Root cause is the missing visibility filter, matching the standing TODO at `source/slang/slang-serialize-ast.cpp:1871-1872`. DeepWiki repeats the doc's claim, so two nominally authoritative sources agreed and were both wrong ([parse the container per chunk to prove an exposure claim](../learnings/1785828868663-parse-the-container-per-chunk-to-prove-an-exposure.md)).

The transferable rule is the method that got there. The first probe was `open(f,'rb').read().count(b'internalFn')`, returning **6 vs 4** for plain versus obfuscated — which reads as "obfuscation partially worked" and is nearly useless: it cannot say *which* chunk holds the name, and a nonzero count may be coincidental data. The per-chunk parse turned that ambiguous ratio into a decisive result — names **gone** from `ir  ` (2164→1764 B), **fully present** in an untouched `ast `. Same data, opposite conclusion. Two traps inside the parse are worth stealing:

- **Take the container header layout from the source, not from a generic RIFF assumption.** The first two parsers emitted `size=1414744396` garbage — that is `'LIST'` read as a little-endian integer — because Slang list chunks carry a 12-byte header (`Chunk::Header` plus a type `FourCC`, `slang-riff.h:366,375`) with **8-byte** chunk alignment (`kChunkAlignment = 8`, `:130`), not the classic 2-byte-aligned 8-byte header. The FourCCs are enumerated at `slang-serialize-types.h:106-117`: `ast `, `ir  `, `SHA1`, `fdep`.
- **Run the flow the docs actually recommend for shipping, not just the convenient one.** Both the bare `.slang-module` and the documented `-obfuscate -g` → `.zip` path (extracting the module back out) leak. Testing only the bare form leaves the finding wavable as the wrong invocation.

Two coverage-argument rules came out of the same probe. **A green suite while the leak exists is positive evidence of a coverage gap:** `tests/serialization/` is 15/15 green and `tests/obfuscate/` 4/4 green *with* the leak present, which converts an absence-of-evidence argument ("grep found no test") into a demonstration that no existing test constrains the property — worth running the suite for exactly this reason when reporting a gap. And **"a test exists" is not "a regression would be caught":** `tools/slang-unit-test/unit-test-obfuscation-with-debug.cpp` looks like coverage for obfuscation in a shipped binary, but its debug-info check hard-fails with `SLANG_FAIL` (`:330-341`) while its obfuscation check only `printf`s a warning and returns success (`:349-352`). A subagent reported that file as both a covered item and a gap; hand-reading the assertion strength resolved it. Grep for the failure path, not the check.

For anyone chasing serialized-module questions from this area: emitting a module with IR but no AST is genuinely **removed** — `SerialOptionFlag{ASTModule,IRModule}` was deleted in `6231a6830` (PR #7483), zero hits tree-wide at HEAD, and both loaders hard-fail on a missing AST chunk (`slang-session.cpp:2174-2180`, `slang-global-session.cpp:659-665`), so restoring it is a write+read+API change rather than a flag flip. Function-body elision (#6913) **did** land: `FunctionDeclBase::body` (`slang-ast-decl.h:649`) has no `FIDDLE()` marker, so it is not serialized — verify the property, not the issue's closed state.

## Loading serialized modules: binary freshness and module identity in one session

**Stale `.slang-module` binaries silently shadow edited source by default.** Measured on v2026.19: `user.slang` imports `lib.slang`, both written with `IModule::writeToFile`, then `lib.slang` is edited and a new `ISession` loads `user`. With the default options the OLD output comes back: both stale binaries load and the edited source is ignored. Deleting one binary is not enough. Delete lib's and lib recompiles, but `user` still loads from its own stale binary; delete only user's and the stale lib binary still shadows the source. The fix is `CompilerOptionName::UseUpToDateBinaryModule` (API-only, default false, slang.h ~:1200). With it on, the loader calls `isBinaryModuleUpToDate` (slang-session.cpp ~:1424/:2025), which compares a SHA1 over the build tag, the option hash and the *content* (not mtime) of every transitive dependency source, and falls back to source on mismatch, so dependents are invalidated automatically without manual deletion. A binary written from the OLD session after the edit is still rejected, because its digest comes from the sources as they were at load time. The flag itself is excluded from `buildHash` (#6557), so toggling it never changes the digest. One observed caveat: binaries written with search paths `bin src` were rejected (recompiled from source, output still correct) when loaded with `./bin ./src` or absolute paths, so use identical search-path strings for write and load to get cache hits ([stale .slang-module binaries silently shadow edited source unless UseUpToDateBinaryModule](../learnings/1791678775900-slang-stale-slang-module-binaries-silently-shadow-.md)).

**A session keys loaded modules by name AND by path, and has no unload.** In one `ISession` on v2026.19, `loadModuleFromSourceString("lib_v2", <same path as the already-loaded lib>, src)` returns null with `assert failure: slang-dictionary.h(325): The key already exists in Dictionary`. The likely cause, inferred rather than debugged, is that `loadModuleFromBlob` checks only `mapNameToLoadedModules` (slang-session.cpp:299) while the duplicate canonical path trips `mapPathToLoadedModule.add` in `loadParsedModule` (~:1144). The same NAME with different content gives E38202 "module already loaded with different source". A new name with a different path string (a virtual name or a disk copy) loads, coexists with the original, and both can be linked into one composite program. Dependents bind by name: `import lib` keeps the old module and `import lib_v2` gets the new one. `IModule::getDependencyFilePath` returns the path you passed, so a virtual path stays virtual and the host has to keep its own module-to-file map. There is no unload or removal API (maintainer won't-fix, shader-slang/slang#4645); the recommended hot reload is a fresh `ISession` on the same `IGlobalSession`. Questions like this are settled in minutes with the release tarball and a ~40-line host program (`g++ -I include -L lib -lslang-compiler`) ([loading a module under a second name needs a different path string](../learnings/1791677141637-slang-loading-a-module-under-a-second-name-hot-rel.md)).

## Source maps: the component API returns them; the doc and slang-wasm lag

Consider a WGSL target compiled through the component API with `TargetDesc.lineDirectiveMode = SLANG_LINE_DIRECTIVE_MODE_SOURCE_MAP` (value 4). Measured on the v2026.20 release with a g++ probe, `IComponentType::getResultAsFileSystem(ep, target, &fs)` (slang.h:5569) returns an in-memory file system with the map at `associated/0/0.map`. `IComponentType2::getEntryPointCompileResult` (reached by `queryInterface` on the linked component) returns 3 items, and item 1 is the v3 JSON source map; that item order is not documented, so a caller should identify the map by content rather than rely on the index. `docs/user-guide/a1-03-obfuscation.md:187-193` still says that only the deprecated `ICompileRequest::getCompileRequestResultAsFileSystem` can do this, which is stale, the same doc-versus-artifact gap as the `-obfuscate` AST claim above. The slang-wasm bindings (`source/slang-wasm/slang-wasm-bindings.cpp:63-70`) expose none of these calls, so a WASM user can set `lineDirectiveMode: 4` but cannot read the map back [Slang WGSL source maps are reachable from the component API (docs say ICompileRequest-only)](../learnings/1793089758382-slang-wgsl-source-maps-are-reachable-from-the-comp.md).

## `-obfuscate` must match between module producer and consumer (#14000)

Observed on ToT c2e4351 (2026-10-29) while triaging shader-slang/slang#14000. A `.slang-module` built with `-obfuscate`, then loaded by a slangc session WITHOUT `-obfuscate`, asserts `slang-ir-link.cpp(399): c->value.ptrVal == nullptr`, even for a public `[shader]` entry point; it is the same assert as #12728. The reverse (a plain module, an `-obfuscate` consumer) asserts `slang-ir-transform-params-to-constref.cpp(463): layoutDecoration`. When both sides use the same flag, loading works. `tests/serialization/obfuscated-serialized-module-test.slang` passes `-obfuscate` on the consumer side too, so it hides the mismatch. The unverified hypothesis: `isLinkageNameObfuscated` (`slang-lower-to-ir.cpp:1555`) checks the SESSION flag, so the consumer's `createIRModuleForLayout` `[import(name)]` stubs get differently hashed names than the producer's exports, and `IRLayoutDecoration` never moves onto the definition. The lesson for any "hash linkage names" change is that the hash-or-not decision depends only on the declaration, never on a session flag. To find which RIFF chunk holds a name, scan offsets for the `ir  `/`ast ` tags against the string's offsets in Python; `strings` over the whole file cannot say (the per-chunk rule above) [-obfuscate must match between module producer and consumer](../learnings/1793234159574-slang-obfuscate-must-match-between-module-producer.md).
