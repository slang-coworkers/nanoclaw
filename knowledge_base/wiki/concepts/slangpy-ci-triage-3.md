# SlangPy CI, Triage, Build, and Runtime (part 3)

> **This page is part 3 of 3** of the SlangPy CI, Triage, Build, and Runtime synthesis (split 2026-08-11 to stay under the 40 KB read cap). Siblings: [part 1](slangpy-ci-triage.md), [part 2](slangpy-ci-triage-2.md). The TL;DR below is shared across all parts.

## TL;DR
- **SUPERSEDED (2026-08-03): cross-repo `gh run rerun <id> --repo shader-slang/slangpy --failed` now WORKS** — the old "Must have admin rights to Repository" block no longer reproduces, so rerun slangpy reds yourself under the normal 3/PR/day cap.
- **Exit 0 is NOT proof a rerun fired — the `run_attempt` increment is.** Re-read `gh api repos/shader-slang/slangpy/actions/runs/<id> --jq '{status,conclusion,attempt:.run_attempt}'`; piped forms (`gh … | jq`) report jq's status and launder gh failures into exit 0.
- **Classify a slangpy red by its signature's determinism, not by permissions** — intermittent (dep-fetch 5xx, DXC prebuilt fetch 500 at CMake configure from `FetchDXC.cmake`) → rerun; deterministic/author-owned (setup-python toolcache, `E36121`, code break) → no rerun, because a rerun cannot fix a deterministic failure.
- **All-false `.permissions` on `shader-slang/slangpy` does NOT mean you cannot act or read** — log reads always worked. **Probe the actual operation instead of introspecting permissions.**
- **RETRACTED framing: the old rerun 403 was the OneCLI gateway PAT-routing collision, not a missing scope** — a read-only user PAT shadowed the App token, which already has `actions:write`. Never ask an operator to "grant slangpy actions:write"; ask only to extend the scoped secret.
- **RETRACTED GPU-leak claims: #115/#608/#827 do not reproduce at HEAD.** The CUDA-OOM cascade is peak concurrent VRAM (`pytest -n auto --maxprocesses=4` × ~5 GB per worker), not a leak — distinguish a monotonic climb (leak) from a step function that plateaus (working set).
- **When A/B-ing against a local Slang build, `SGL_LOCAL_SLANG_BUILD_DIR` must point at `build/Release`, never the downloaded `build/slang-<ver>-linux-x86_64/` release artifact** — that artifact lacks the PR and makes BOTH arms come back clean, a false negative that looks like a real result. Prove it with `strings <dir>/libslang*.so | grep -c 'is incompatible with compilation target'` (2 = real, 0 = invalid) plus `ldd build/linux-gcc/Debug/sgl_tests | grep slang`.
- **Slang's `default` CMake preset is Ninja Multi-Config, so `-DCMAKE_BUILD_TYPE=Release` is inert** — `--config Release` is what selects the config.
- **Establish the pinned-Slang baseline control BEFORE any A/B or you will misattribute pre-existing failures** — the 5 residual `sgl_tests` failures are LFS-fixture cases (3 `test_dds_file.cpp` + 2 `test_texture_loader.cpp`); the arithmetic `33 = 28 + 5` is what falsified a monitor reporting 0 diagnostics.
- **`git checkout <commit> -- <path>` STAGES as well as writing the worktree, so a plain `git diff` is empty and the revert looks like a no-op** — use `git diff HEAD` / `git status --porcelain`, and prove a PR is unmerged with `git merge-base --is-ancestor <pr-head> origin/master`.
- **Doctest name filters can silently select nothing** (`-tc=formats` / `-sc=vulkan` matched 0, 203 skipped) — run the whole binary and grep the log.
- **A stubgen (`numpy`/`libcst`) failure aborts ninja BEFORE the `sgl_tests` link — a FALSE GREEN where a stale binary "passes" against pre-change code** (observed 10 days older than HEAD). Build `--target sgl_tests` explicitly and require both `sgl_tests` and `libsgl.so` mtimes newer than a pre-build `date` stamp; a fresh `.o` is not sufficient.
- **Building slangpy needs `python3-dev`/`python3.11-dev` and `--break-system-packages` on every pip call (PEP-668)** — `tools/ci.py install-slangpy-torch` fails because its internal `pip install wheel` omits the flag; nvcc is NOT required; pip site-packages reset on container rebuild; an ENOSPC-interrupted submodule needs `git submodule update --init --force --recursive`.
- **The full C++ `sgl` build requires the `data` submodule whose two fonts are git-LFS** — without git-lfs you get ~131-byte pointer stubs and ninja dies on `Inconsolata-Regular.ttf` before any source compiles. Verify byte sizes (Montserrat 197624 B, Inconsolata 101752 B), not mere existence.
- **`device.create_buffer(element_count=n, struct_size=K)` allocates `n*K` bytes and NEVER reconciles `K` against Slang's per-target device-side stride — silent out-of-bounds the debug layer will not catch.** Pass `resource_type_layout=program.reflection.<bufferParam>` so the reflected stride is used.
- **Python `id(m)` differing across `session.load_module(...)` calls is NOT evidence of an `IModule*` identity bug** — slangpy mints a fresh wrapper proxy per call; compare `IModule*` pointers in a standalone C++ program.
- **`device.load_program("mod.slang", ["one_ep"])` capability-checks EVERY `[shader]` entry point in the module at load time, not lazily per function** — one illegal EP sinks its clean siblings; guard the offending declaration with the SGL-injected `#ifndef __TARGET_CUDA__`.
- **`E36121` fires only on API-level requested capabilities** (`targetOptionSet.getArray(CompilerOptionName::Capability)`), never by walking declarations — so `[__requiresNVAPI]` is not a second fix site. Read a diagnostic's emission loop, not its wording.
- **`0 assertions failed` alongside N failed test cases is the signature of a module-load/compile break, not a logic regression** — go read the compiler diagnostic instead of hunting behavior.
- **`ci-latest-slang.yml`'s `build-pr` job runs `actions/checkout@v6` with no `ref:`, so slangpy always builds its DEFAULT branch** — a required `SlangPy Tests` check on a slang PR cannot go green until the slangpy-side fix is **merged to slangpy main**; a draft PR changes nothing.
- **"Deferred until the upstream Slang fix ships" gates on the `SGL_SLANG_VERSION` pin (`external/CMakeLists.txt:85`), not on a wheel release** — check three stages: merge, a tag CONTAINING the commit (`compare/<tag>...<sha> --jq '.status'` must be `behind`/`identical`, never `ahead`), then the pin bump. The pin lagged five releases.
- **The cheapest proof a slang fix works with slangpy is an existing cross-repo `ci-latest-slang` run** (nightly 01:00 UTC, `workflow_dispatch` with `slang_branch`, `repository_dispatch` per slang PR) — but `build-pr` is a reduced Linux+Windows Release matrix: real evidence, not full-matrix evidence.
- **`updatedAt - createdAt` from `gh run list` is NOT job duration** — a re-run keeps the original `created_at` while jobs start at `run_started_at`, so a `success` run can show 1255 min. Confirm with per-job durations.
- **Never call this environment "GPU-less" — an NVIDIA L40S is present and compute/Vulkan `cooperative_matrix` run.** Cooperative-VECTOR does not (driver 565.x lacks `VK_NV_cooperative_vector`), and **coop-vec kernels still COMPILE (slangc exit 0), so compile-only checks give false confidence** — dispatch is where it dies.
- **NVRTC/CUDA downstream compilation is deferred to the first `kernel.dispatch(...)`, so a test stopping at `create_compute_kernel` never runs NVRTC** — dispatch with a real output buffer and expect `RuntimeError`; `downstream_args` reach only DXC and NVRTC, silently dropped elsewhere.
- **A test that deliberately crashes (SIGSEGV/SIGABRT) HANGS the "Unit Tests (Python)" step for hours** because Crashpad intercepts it, while passing locally where crashpad is off — hard-guard on the CI env.
- **On slangpy-samples, `pre-commit run --all-files` means one pre-existing violation anywhere reds the `pre-commit` job on EVERY PR**, and **`PATCH` of an existing bot issue comment 403s while `POST` works** — design status updates as append-only fresh comments.
- **A single test can remove the shared D3D12 device and cascade into hundreds of "Failed to create device!" failures** indistinguishable from infra flake — grep for `Device removal has been triggered` and find the first-emitting test per xdist worker; "my tests passed" is meaningless if they ran before the poisoner.
- **Before mapping a solution space, grep HEAD for the feature's named symbols and check merged PRs** (stale line-refs are the staleness tell); for any GPU-codegen gap search `shader-slang/slang` PRs first — the fix often already lives in core.

## CI-Wedge gh-run Wall-Clock False Positives and the Coverage-Automation Gap (2026-07-23 fold)

Two SlangPy CI-triage gotchas. `updatedAt - createdAt` from `gh run list` is NOT reliable job duration: a re-run keeps the ORIGINAL `created_at` but jobs run at `run_started_at` (can be ~21h later), so a `success` run can show 1255min wall-clock — always confirm with `gh api .../actions/runs/<id> --jq '{created_at,run_started_at,run_attempt,conclusion}'` and per-JOB durations; and the #1070 hang is step-SPECIFIC (`Unit Tests (Python)` after `Unit Tests (C++)` ✓), distinct from a job that hits the same 6h timeout wedged on `Unit Tests (C++)` ([SlangPy CI wedge triage: gh run wall-clock false positives and step-level distinction](wiki/learnings/1784742134828-slangpy-ci-wedge-triage-gh-run-wall-clock-false-po.md)). And a verification-discipline note tied to coverage: as of 2026-07-22 SlangPy has NO Python coverage automation (`pytest-cov` declared but never invoked) so cited "84% baseline" numbers are manual-only; more load-bearing, when a maintainer says tests were "completed," DO NOT assume they're on `main` — on #782 the listed files lived in unmerged PR #928, caught by `gh pr list --search` + `git ls-tree -r HEAD`, not a subagent's file-existence check (which untracked leftovers fool; a shallow clone also breaks `git log --follow` provenance) ([SlangPy coverage automation status + verify completed claims vs main not PR branches](wiki/learnings/1784734562681-slangpy-coverage-automation-status-verify-complete.md)).


## In-Container GPU Validation: CUDA Works, Vulkan Autodiff Fails (2026-07-28 fold)

The slangpy-fixer container DOES have a usable GPU (NVIDIA L40S, CUDA 12.7) — always probe `nvidia-smi` before claiming "no GPU backend." But **backend choice matters for differentiable validation**: `spy.Device(type=spy.DeviceType.cuda)` runs forward AND backward (`.bwds`) correctly (a minimal `RWDiffTensor<float,1>` + `.store` backprop gives the analytically exact gradient), while the default `spy.Device()` resolves to **Vulkan** on this box and its auto-generated `bwd_diff` kernel fails with `NVVM compilation failed: 1` / `command_encoder->finish ... error -13`. Forward-only Vulkan is fine — only the differentiable backward codegen fails, and it's a slangpy-0.43 autodiff-on-Vulkan toolchain issue in-container, NOT a shader-migration defect (the module compiles cleanly on both). So to functionally validate a differentiable slangpy sample, explicitly select CUDA; module-load (compile check) works on both backends and is the strongest content-agnostic signal a migration is correct. Setup notes: `pip install slangpy` (pins 0.43.1, ~92MB wheel → use `--retries 5 --timeout 120`), `pip install pillow` (use `PIL.Image.open` directly — imageio's backend discovery is flaky in-container), and slangpy-samples image assets are git-LFS pointers fetched via the LFS batch API. Companion to the coop-vec note above ([slangpy GPU validation in coworker container: CUDA works, Vulkan autodiff fails with NVVM error](wiki/learnings/1785246704737-slangpy-gpu-validation-in-coworker-container-cuda-.md)).

A single SlangPy test can remove the shared D3D12 device and cascade into hundreds of "Failed to create device!" / "closed command list" failures across unrelated tests — indistinguishable from the known device-creation infra flake. To tell real-bug from flake, grep the log for `Device removal has been triggered` / `RemoveDevice` and find which test emits it **FIRST chronologically per xdist worker** — that is the culprit; later tests on the same worker are cascade victims, and "my tests passed" from a spot-check is meaningless if they ran *before* the poisoning test. Confirm by re-running the suspect once the poisoner is skipped. (Root cause here was a `shader_resource`-only tensor cleared on D3D12 — see the tensor-clear cluster on the Tensor API page.) ([D3D12 device-removal cascade can masquerade as CI infra flake — trace the FIRST failure, not a spot-check](wiki/learnings/1785359117251-d3d12-device-removal-cascade-can-masquerade-as-ci-.md)).


## load_program Capability-Checks the Whole Module, and the Cross-Repo Guard-Prerequisite (2026-08-01 fold)

`device.load_program("mod.slang", ["one_entry_point"])` capability-checks **every** `[shader]` entry point in the module at load time — not lazily per requested function — so a single target-unsupported sibling EP sinks the whole load (confirmed on CI run 30564544350: requesting a CUDA-clean `copy_byte_address_buffer` still tripped `E36107: entrypoint 'copy_buffer_uint' uses features not available for 'cuda'` → `E39999 import failed`). DeepWiki's "lazy per-function" claim is wrong for this path — trust the CI logs. The idiomatic fix guards the offending EP's whole declaration with the SGL-injected per-target macro (`#ifndef __TARGET_CUDA__ … #endif`, injected at `src/sgl/device/shader.cpp:486-496`, applied by the preprocessor *before* the front-end capability check so the guarded EP never reaches E36107); in-repo precedent is `src/sgl/device/blit.slang:61-86` ([SlangPy load_program capability-checks ALL entry points in a module at load](wiki/learnings/1785443278231-slangpy-load-program-capability-checks-all-entry-p.md)). That guard can be the **prerequisite** that unblocks an upstream slang PR, not a follow-up: when `SlangPy Tests` is a `required=True` check on the slang PR and the CI dispatch (`ci-latest-slang.yml`) checks out slangpy fixtures from slangpy **main** while building slang from the PR ref, the slang PR cannot merge until the slangpy-side guard is already on slangpy main (observed slang#12289 → slangpy#1083). Sequence it as two decoupled stages: land the guard immediately (pin-independent — its own CI builds slang from master with no E36107 yet, and the offending variant is already `pytest.skip`ped, so it is a green no-op today), and defer the `SGL_SLANG_VERSION` pin bump (`external/CMakeLists.txt:85`) until the slang fix ships in a release **tag** (slangpy pulls a prebuilt release tarball, not a commit SHA) ([a slangpy test-fixture guard can be the PREREQUISITE that unblocks an upstream slang PR's required check](wiki/learnings/1785478041840-a-slangpy-test-fixture-guard-can-be-the-prerequisi.md)).


## An Intended-Breaking Slang Diagnostic (E36121 / `hlsl_nvapi`) and How to Prove the Downstream Guard (2026-08-03 fold)

The `load_program`/E36107 pattern above has a sibling that is the cleanest worked example of a **legitimate cross-repo break**: slang PR #11225 ("Capabilities: error on capabilities incompatible with compilation target", fixes #4422, author zangold-nv, labeled `pr: breaking change`) turned its cross-repo `SlangPy Tests` status red with 28 identical

```
error[E36121]: requested capability 'hlsl_nvapi' is incompatible with compilation target 'spirv'
error[E39999]: import failed due to compilation error
fatal error[E40003]: compilation ceased
```

on **both** linux-gcc and windows-msvc, on **both** attempts. `sgl_tests`: 172 passed / 28 failed / 3 skipped — but **0 of 18535 assertions failed**, and the Slang C++ build was fully green (`[1450/1450]`). Every failure was a thrown `Failed to load slang module "test" from source`, not a CHECK. **`0 assertions failed` alongside `N test cases failed` is the signature of a module-load/compile break, not a logic break** — doctest reports a thrown exception as a failed *case* while the assertion counter stays clean (18535/18535 Windows, 15593/15593 Linux). See that shape and stop hunting a behavioural regression; go read the compiler diagnostic. It ruled out every known slangpy cross-repo bucket by discriminator: not the fiddle/GCC-PCH break #12227 (zero `'friend' used outside of class`, and the PR was rebased past the #12233 fix), not the Windows `setup-python` toolcache flake (that step succeeded in 98 ms), not the `sgl_tests` exit-1-after-all-pass teardown flake (28 *real* case failures, not an exit-code artifact), not CUDA-OOM #1024 or a `test_nested` data mismatch (zero OOM/numeric markers).

**The generalizable rule: a slang PR whose whole purpose is to add a new diagnostic will legitimately break downstream repos that trip it — verify the causal link in the PR's own diff rather than inferring it from the title.** `gh api /repos/shader-slang/slang/pulls/<N>/files --jq '.[].patch'` and grep for the diagnostic code; here the diff added `36121` + the message template in `slang-diagnostics.lua`, the `RequestedCapabilityIncompatibleWithTarget` raise in `slang-target.cpp` (+79/-3), and a new test `incompatible-capability-for-target.slang`. That is proof, not correlation. Disposition: **legitimate, not rerunnable** (deterministic across platforms and attempts) — route to the PR author for coordination, because the real question is whether the downstream needs a target-conditional guard, not whether the slang change is wrong; an intended breaking change needs a downstream fix landed alongside it. Bonus permissions fact from the same triage, consistent with the rerun supersession above: `gh api /repos/shader-slang/slangpy --jq '.permissions'` returns admin/maintain/push/triage/pull **all false**, yet `/actions/jobs/<id>/logs` returned full 4289-line bodies first try — **"no permissions" does not mean you can't classify a cross-repo failure**, so never skip classification of a cross-repo red on the assumption logs are unreachable ([slang capability-error PRs break downstream slangpy via E36121 — an intended cross-repo break](wiki/learnings/1785744645210-slang-capability-error-prs-break-downstream-slangp.md)).

**Read the diagnostic's emission loop before enumerating fix sites.** `TargetRequest::checkCapabilities(DiagnosticSink*)` (added by #11225, `source/slang/slang-target.cpp`, called from `slang-check-shader.cpp` — from `FrontEndCompileRequest::checkEntryPoints` for every target, so reachable on any compile) iterates exactly one collection: `for (auto atomVal : targetOptionSet.getArray(CompilerOptionName::Capability))`. That is the **API-level requested-capability list** — precisely what slangpy populates via `session_options.add(CompilerOptionName::Capability, findCapability("hlsl_nvapi"))`. It **never walks declarations**, so the `[__requiresNVAPI]` attribute at `slangpy/slang/atomics.slang:57` (`public extension half2 : IAtomicAddable`) is **not** a second fix site, however much the word *"requested"* in the message reads as "anything that asks for NVAPI" — attribute-level requirements are diagnosed by a different mechanism (use-site capability checking). **Rule: when a new diagnostic's message names a category, read the emission loop to learn what the compiler means by that word. The error text describes the symptom in user vocabulary; the loop defines the scope.** (Verification needs no `gh` token: `curl -sS https://api.github.com/repos/shader-slang/slang/pulls/11225/files` returns HTTP 200 unauthenticated with full `.patch` bodies. Mechanism notes: E36121 is declared in `slang-diagnostics.lua`, a **build-time generator** — grepping only `.cpp/.h` for the diagnostic *name* finds nothing; the emission site uses the generated CamelCase `Diagnostics::RequestedCapabilityIncompatibleWithTarget`. `hlsl_nvapi` is `def hlsl_nvapi : hlsl;` in `slang-capabilities.capdef`, strictly in the hlsl target family, so it genuinely IS incompatible with spirv, and the PR's GLSL escape hatch — `isGLSLBasedTarget() && cap contains spirv atom → skip` — does not rescue slangpy's vulkan path, which sets `SLANG_SPIRV` + `GENERATE_SPIRV_DIRECTLY` and therefore prints as `spirv`. `-ignore-capabilities` suppresses E36121; slangpy does not pass it.) ([E36121 fires only on explicitly requested capabilities — in-source `[__requiresNVAPI]` is not a second fix site](wiki/learnings/1785750679044-slang-e36121-fires-only-on-explicitly-requested-ca.md))

### `SGL_HAS_NVAPI` ON/OFF is a natural experiment proving BOTH halves of the guard

slangpy's unconditional `hlsl_nvapi` request lives at `src/sgl/device/shader.cpp:404-408` (surfaced as slangpy#1087). The fix guards it with `SGL_HAS_NVAPI && type() == DeviceType::d3d12`, and the two CI platforms fail for **two different reasons** — grepping the configure log for `SGL_HAS_NVAPI:` is what proves neither half is sufficient alone:

- `linux-gcc`: `-- SGL_HAS_NVAPI: OFF` → the nvapi module is **never created or linked at all** (`external/CMakeLists.txt:251-259` sets it ON only iff the `slang-rhi-nvapi` CMake target exists), yet the capability is still requested → vulkan fails.
- `windows-msvc`: `-- SGL_HAS_NVAPI: ON` → d3d12 subcases **pass** (the capability is genuinely backed by a linked module); only vulkan fails.

So Windows has the flag ON and still breaks on vulkan, while Linux lacks the module entirely — anyone "simplifying" the guard to just the target check, or just the build flag, reintroduces one of the two failure modes. Note `SGL_HAS_NVAPI` is a **build-time** flag, not a runtime capability probe; easy to misread. Second reusable move from the same triage: **on Windows, "zero d3d12 failures" is decisive evidence, not absence of evidence** — `tests/sgl/testing.cpp:73` runs `device_types{d3d12, vulkan}`, so the d3d12 subcases *did* execute and passed. Confirm the fixture actually enumerates the target before concluding a target is unaffected; on Linux (vulkan-only) the identical observation would prove nothing ([`SGL_HAS_NVAPI` ON/OFF is a natural experiment proving both predicate halves](wiki/learnings/1785745805020-slangpy-hlsl-nvapi-guard-sgl-has-nvapi-on-off-is-a.md)).

That triage also re-confirmed the cross-repo prerequisite ordering at HEAD, matching the #12289→#1083 sequencing rule above: `ci-latest-slang.yml`'s `build-pr` job runs `actions/checkout@v6` with **no `ref:`**, so slangpy always builds its default branch and `client_payload` controls only the *slang* ref ⇒ `SlangPy Tests` on a slang PR cannot go green until the slangpy fix is **merged to main** (a draft PR changes nothing). The guard is independently landable because `external/CMakeLists.txt:85` pins `SGL_SLANG_VERSION "2026.12"`, pre-#11225, making it a green no-op today; keep the `SGL_SLANG_VERSION` bump as a separate later PR since slangpy pulls a release *tarball*, not a SHA.

### A/B testing a slangpy fix against an UNRELEASED Slang PR

Proving the guard required building Slang at #11225's head locally. **Result** (slangpy commit `998aeb2`, "Only request hlsl_nvapi capability where the NVAPI Slang module is linked", against Slang at `db61cec` = `git describe` `v2026.14.1-24-gdb61cec`, NOT merged to master):

| variant | doctest tallies | `hlsl_nvapi` | `E36121` |
|---|---|---|---|
| WITHOUT guard | 200 cases, 167 passed, **33 failed** | 28 | 28 |
| WITH guard (`998aeb2`) | 200 cases, 195 passed, **5 failed** | **0** | **0** |
| baseline (pinned Slang 2026.12) | 200 cases, 195 passed, 5 failed | 0 | 0 |

The 5 WITH-guard failures are byte-identical to the pinned-2026.12 baseline (the 3 `test_dds_file.cpp` "DDS file has invalid header" + 2 `test_texture_loader.cpp` "Unsupported source image type" LFS-fixture cases), so the guard removes exactly the 28 capability errors and introduces nothing. **Establish that baseline control BEFORE the A/B or you will misattribute those 5.** Note the arithmetic check the table supports: 33 = 28 + 5 — a sum that falsified a monitor reporting 0 diagnostics.

**THE TRAP that produces a false negative.** `slang-11225/build/` contains BOTH the real build outputs (`build/Release/lib`) **and** a *downloaded release artifact* `build/slang-2026.14.1-linux-x86_64{.zip,/}` that slang's configure fetches for slang-llvm. That artifact is a **released** build and does NOT contain #11225 — point `-DSGL_LOCAL_SLANG_BUILD_DIR` at it and BOTH arms come back clean, a false negative that looks like a genuine result. **Always prove the binary contains the diagnostic before trusting either arm**, and check what the *test* binary resolves at runtime (slangpy copies the lib into its own build dir):

```bash
strings <dir>/libslang*.so | grep -c 'is incompatible with compilation target'
#   build/Release/lib            -> 2   ✅
#   slang-2026.14.1-*/lib        -> 0   ❌ silently invalidates the A/B
ldd build/linux-gcc/Debug/sgl_tests | grep slang     # then strings THAT path (got 2 ✅)
# cross-check build/Release/include/slang-tag-version.h -> SLANG_TAG_VERSION "2026.14.1-24-gdb61cec"
```

Mechanics worth reusing ([A/B testing a slangpy fix against an unreleased Slang PR](wiki/learnings/1785747291729-a-b-testing-a-slangpy-fix-against-an-unreleased-sl.md), [PROVEN: the guard fixes slang#11225 E36121 — A/B result and its traps](wiki/learnings/1785750627140-proven-slangpy-hlsl-nvapi-guard-fixes-slang-11225-.md)):

- **Read the clone log before trusting `git log -1`.** A background `clone && fetch pull/N/head && checkout FETCH_HEAD && submodule update` script shows HEAD on `master` if you look during the `fetch` window (`git for-each-ref` shows only master refs; `.git/FETCH_HEAD` exists but `git log FETCH_HEAD` says "ambiguous argument"). Re-check after the checkout line appears in the log. Prove the PR is genuinely unmerged with `git merge-base --is-ancestor <pr-head> origin/master`.
- **`git checkout <commit> -- <path>` STAGES as well as writing the worktree**, so a plain `git diff` afterwards is EMPTY and the revert looks like a no-op. Use `git diff HEAD` (or `git status --porcelain`, which shows `M` in column 1). `git reset --hard <commit>` clears both index and worktree.
- **Slang's `default` CMake preset is Ninja Multi-Config**, so `-DCMAKE_BUILD_TYPE=Release` is inert — `cmake --build build --config Release` is what selects the config, and `SGL_LOCAL_SLANG_BUILD_DIR` must then point at `build/Release` (it reads `$DIR/$BUILD_DIR/lib/libslang-compiler.so` and requires `$DIR/$BUILD_DIR/include/slang-tag-version.h` for the version, else FATAL_ERROR).
- Configure once with `cmake --preset linux-gcc --fresh -DSGL_LOCAL_SLANG=ON -DSGL_LOCAL_SLANG_DIR=<slang> -DSGL_LOCAL_SLANG_BUILD_DIR=build/Release`, then per arm revert/restore only `src/sgl/device/shader.cpp`, `cmake --build --preset linux-gcc-debug` (incremental ≈ minutes), `python3 tools/ci.py unit-test-cpp`.
- **Doctest name filters can silently select nothing** (`-tc=formats` / `-sc=vulkan` matched 0 here, 203 skipped) — run the whole binary and grep the log.
- **The Linux run genuinely exercises the SPIRV path**: `tests/sgl/testing.cpp`'s `run_gpu_test` is `{d3d12, vulkan}` on Windows but **vulkan-only on Linux**, and a real NVIDIA L40S is present (`/etc/vulkan/icd.d/nvidia_icd.json` is the real ICD — `/usr/share/vulkan/icd.d/` holds only intel/radeon/lavapipe, so listing just the latter makes it look like there is no NVIDIA Vulkan; a ctypes `vkCreateInstance` + `vkEnumeratePhysicalDevices` probe proves a usable GPU without installing `vulkaninfo`). But because `SGL_HAS_NVAPI` is 0 on Linux the guard's first clause short-circuits there: the guard's *effect* is fully observable, yet a Linux run **cannot** distinguish the `SGL_HAS_NVAPI` clause from the `device_type == d3d12` clause — which is exactly why the Windows `SGL_HAS_NVAPI: ON` leg is load-bearing.
