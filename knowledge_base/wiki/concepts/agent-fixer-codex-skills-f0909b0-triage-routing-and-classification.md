## TL;DR

- **The `/slang-triage-issue` "always forward to slang-fixer" step is a reflex to override, not a mandate.** The fixer wire exists for *writing/PR'ing code*. A read-only deliverable (post a comment, write a memo, answer a question) belongs to the analysis tier that can already produce it — adding a fixer hop buys nothing and re-introduces handoff-death.
- **Operator correction 2026-09-09: a `Dev Opened` label, a core-team author or a self-assignment does NOT exclude an issue.** Triage it and dispatch slang-fixer as for any actionable issue; the only per-issue exclusions are an existing human PR that fixes it, an explicit do-not-touch from a maintainer, or a fix that lands in a repo the bot cannot push to. The earlier blanket skip ('label + self-assignment IS the human triage, do NOT auto-dispatch the fixer') is RETIRED: it drove the bot PR rate on `Dev Opened` issues from 69% to 36% and the overall WIN rate from 69% to 38% (JUL vs AUG cohorts). Don't touch labels/Type the human set — that's over-reach against the standing "reign in the bot" signal. Still report up to close the chain and record a memo.
- **`Dev Opened` and `Dev Reviewed` no longer exist (deleted 2026-10-08 in slang, slangpy and slang-rhi).** `Dev Opened` was always bot-applied, never a triage signal, and its producer workflow is gone. For authorship use the Slang-All board "Source" field; for triage state use assignee and milestone.
- **slang `bot-ok` = the author opts the bot in.** It authorizes triage on a maintainer-filed, self-assigned issue and a slang-fixer draft PR when the fix is clear; a design-call issue gets triage plus a recommended direction, then stops. Without the label, such an issue stays held unless the author @-mentions the bot or the operator asks.
- **On a self-assigned lead's issue, look for the assignee's own PR before asking "should the bot open a draft PR?"** Search by PR author, since the issue timeline shows the link only once the PR references the issue.
- **Perf-epic / ops-infra sub-tasks (benchview, backtest harnesses, ingestion, alerting, runbooks) are ops/PM execution items, not compiler bugs.** Do NOT forward to the fixer (it can't run infra work); SUPPRESS the triage comment (core-team author + no repro); surface the suppression to the parent for override rather than silently skipping. Their only label is `perf`; don't add `CI Improvement`, `Infra`, bug or team labels.
- **Eval answers for perf-epic sub-tasks follow how each one closed.** Work delivered anywhere (an internal GitLab MR, an analysis comment plus sub-issues) is `fix` with `labels=[perf]`; a "Document X" task delivered as an analysis comment is still `fix`, not `document`. A sub-task tied to the old owner that closed during an owner change with no artifact is `close`. In the eval, `fix` means valid planned work the team does, not a bot fixer dispatch. A reply to one says what the repo has (or that the review is already in tree), points the rest to the downstream repo or the follow-on issue, and never promises a fixer PR. `tools/compile-perf/COVERAGE-ANALYSIS.md` was deleted by PR #13625; its content is in that dir's README.
- **Before triaging a "missing API" request, grep `docs/` for it.** The API may be documented but unimplemented (slang#13774 SER fused ops), which makes it an actionable "implement the documented design" handoff, not a park-for-design.
- **A COMPLETED close is not proof of delivery.** Look for the linked artifact, and check the epic timeline for a reassignment at the same moment.
- **Fabrication risk is a hard gate against auto-forwarding.** If a doc/methodology ask references infra the bot can't see (e.g. `benchview` has zero repo hits), a dispatched fixer would invent an undocumented schema. Refuse to auto-forward; check whether the methodology already has in-tree tooling that IS the raw material (map the ask onto existing scripts). Perf-epic deliverables can land outside the repo (internal GitLab), so "no in-repo scripts" does not prove the work is undone.
- **Perf and codegen-quality bugs get the Issue Type Performance, not the `perf` label.** Predict `reproduced` once a repro confirms, add a team label (`RTR`, `Falcor`) only when the motivation names that team, and skip `perf`, `SPIR-V` and `bug` without other evidence. next_step is `fix` when the issue is assigned or milestoned and a PR is in flight.
- **When a Slang-side test and a driver bug are mixed, label the in-repo defect.** Use `bug` + `Testing` + the backend and next_step `fix`; not `Vendor Driver Bug` or `Not a Slang Bug`. Keep the driver bug as a side note for an upstream report.
- **"Prepare for X runner" issues: run `git log -S '<runner label>'` and grep `.github/workflows` first.** CI has often moved already. These issues are Issue Type Build with sparse labels (none or `CI`) and close after a validation or update PR.
- **Language-design RFCs authored by a language lead need design sign-off before implementation — HOLD the fixer.** Triage fully (classify, ground every claim to file:line, phase the implementation), post a tight comment, then hand the go/no-go to the parent framed as "design-gated — release the fixer only on greenlight." Premature dispatch burns real effort (precedent: ~10 days on a withdrawn feature).
- **A feature request ("add target/option/API X") gets the existing-mechanism answer first.** If your own probe shows the consumer can already do it, say so; propose a new public surface only when nothing existing works, and keep design prescriptions out when an external contributor offered to implement.
- **A WIP-feature implementation gap is a Task, not a Bug.** `Bug` = incorrect behavior in *shipped* functionality; a hole in an unreleased/branch-only feature is `Task`. Defer to the maintainer's framing if they reframe it. shader-slang/slang has rich Issue Types (Task, Bug, Feature, Performance, Documentation, Refactoring, Build, DevRel, Testing, Language Maturity).
- **Constructive value-add without over-reach:** when a perf-epic planning sub-task names a specific *compiler component*, offer a source-inspection optimization survey (a `/slang-plan` research memo, NOT a fixer task) — on parent/owner go-ahead only. Offer it; don't dump it unsolicited on a MEMBER-watched planning issue.

## The routing question: is there code to write?

The through-line of this page is a single decision — *does this deliverable require writing code?* — and a recurring failure to answer it before invoking the fixer. The fixer's wire exists for authoring and PR'ing code; routing anything code-adjacent to it is the wrong shape for a read-only, no-code deliverable. When a maintainer asks for an *analysis* posted as a comment ("not ready to commit to a fix yet"), the analysis tier owns it via read-only research subagents — the `/slang-triage-issue` Step-3 pattern ([investigation-only stays in the analysis tier](../learnings/1788542147628-investigation-only-deliverables-stay-in-the-analys.md)). The cost of the reflexive fixer hop is concrete: on #12092 an analysis dispatched to a fixer session that died mid-response sat undelivered for ~24 days, then again ~1 week, because a dark handoff is byte-indistinguishable from work-in-progress. Producing the deliverable in-tier keeps ONE live session accountable end-to-end, so "is the work live?" has a checkable answer. Reserve the fixer wire for an *authorized fix*, post-analysis and maintainer-gated, routed THROUGH the tier that holds the chain. The corollary for the waiting party: to un-dark a stalled analysis chain, point the monitor at *your own tier's* posting event, not only at maintainer comments — the silence that matters is "no analysis produced," which your own guard can see.

## Whose issue is it? Core-team ownership skips

A large sub-family WAS "the human already triaged this, so the bot's job is minimal." That rule is retired (Operator correction 2026-09-09): a human-triaged `Dev Opened` issue is a well-specified fixer candidate, not an exclusion, and the fixer is dispatched unless a human PR already carries the fix ([Correction (operator 2026-09-09): Dev Opened and core-team tracking issues ARE in scope](../learnings/1788958700000-correction-dev-opened-and-core-team-tracking-issues-are-in-scope.md)). Historically, when an issue was authored by a core-team MEMBER/COLLABORATOR, self-assigned, and labeled `Dev Opened`, the core-team-skip rule was applied even to fully-specced engineering tasks — the label + self-assignment IS the human triage, and auto-dispatching the fixer to implement is over-reach against the standing "reign in the bot" signal (jhelferty-nv, #12586) ([core-team self-assigned → skip triage](../learnings/1788215669900-core-team-self-assigned-dev-opened-issue-skip-tria.md)). The bot's value on these is a *verified* internal disposition memo + an offer to produce a fixer briefing on explicit request — not autonomous implementation; still report up to close the chain and record the memo, just skip the GitHub-facing triage and the fixer forward. The premise under that old rule was also wrong: `Dev Opened` was never human triage. `.github/workflows/issue-add-labels.yml` (master e6be8dcdd, line 57) adds it automatically to every issue opened by a member of the `dev` team, and no tracked code reads it, so neither "human-set labels mean triage is complete" nor any routing rule should key on it. The maintained author signal is the Slang-All board "Source" field (issue-onboard.yml → issue-board-onboard.yml, #12854). That proposal (#13441) has since landed: PR #13500 removed `issue-add-labels.yml`, and on 2026-10-08 ~01:17Z jkwak-work deleted both the `Dev Opened` and `Dev Reviewed` labels in slang, slangpy and slang-rhi (`/labels/Dev%20Reviewed` now 404s). No routing or triage rule can key on either label any more; older notes that mention them describe history ([`Dev Opened` label is bot-applied, not a human-triage signal](../learnings/1791220010907-dev-opened-label-is-bot-applied-issue-add-labels-y.md), [Dev Reviewed / Dev Opened labels retired 2026-10-08](../learnings/1791448089783-shader-slang-dev-reviewed-dev-opened-labels-retire.md)).

Language-design RFCs sharpen this. When the issue is a language-design proposal authored by a language lead (e.g. tangent-vector / Theresa Foley), do NOT follow "always forward to fixer" — these need design sign-off before implementation ([design-RFC issues, hold the fixer](../learnings/1788909843006-design-rfc-issues-authored-by-a-language-lead-hold.md)). Triage fully and post a tight, value-adding comment (verify claims against HEAD with file:lines; note what's already implemented; never restate their proposal), then HOLD fixer dispatch and hand the go/no-go to the parent as "design-gated." The cautionary precedent: #12550, a tangent-vector RFC-style epic, WAS dispatched → ~10 days of parser+AST implementation and a draft PR → then WITHDRAWN by the maintainer after language-lead discussion. Dispatching a fixer to build a multi-phase language feature is resource-intensive and hard to reverse; it warrants explicit authorization.

A self-assigned lead who files a detailed design proposal often already has the PR up, so even the question "should the bot open a draft PR?" can be moot. On slang#13495 (2026-10-07) the bot asked it while tangent-vector's own PR #13497 had been open for 42 minutes; #13497 merged about 5 hours later with `Fixes #13495`. The issue timeline doesn't show such a PR until it links back, so right before posting the question run `gh pr list -R <repo> --author <assignee> --state all --search "<N>"`, searching by PR author rather than only by issue cross-references ([check for the assignee's own PR before asking a self-assigned lead about a bot PR](../learnings/1791493854161-check-for-the-assignee-s-own-pr-before-asking-a-se.md)).

On shader-slang/slang the author can now opt out of that hold explicitly. The `bot-ok` label (created 2026-10-21 22:23Z; pdeayton-nv applied it first, to #13827, #13828, #13830, #13841 and #13842) authorizes the bot to triage the issue and, in the operator's words, "bot-ok does authorize a bot PR, so handing off to slang-fixer is fine if there's a clear fix". Without it, a maintainer's filed-and-self-assigned item stays the author's own work item (the R6 / #13596 wait on human-filed issues) unless they @-mention the bot or the operator asks. So on a `bot-ok` issue Main dispatches slang-triager on the canonical `gh-issue-shader-slang/slang-<n>` thread with `<github-post-authorized />`, even when a maintainer filed and self-assigned it; the triager hands off to slang-fixer for a draft PR when the fix direction is clear (stated in the issue or confirmed by triage), and when it needs a design call posts the triage with a recommended direction and stops ([slang `bot-ok` label: author opts the bot in, including a bot PR when the fix is clear](../learnings/1792623822987-slang-bot-ok-label-author-opts-the-bot-in-includin.md)).

## The perf epic: ops work, fabrication risk, and Issue Types

The 2026-09-08 batch (epic #12941 + ~18 children #12942–#12959, all self-assigned, labelled `Dev Opened`+`perf` at filing; only `perf` remains now that `Dev Opened` is deleted) is the anchor for classifying non-compiler work. These sub-tasks are ops/infra/PM execution items — benchview DB clearing, backtest harnesses, ingestion, Slack alerting, runbooks, metric-schema definition — NOT compiler code bugs, so: classify Category=ops, do NOT forward to the fixer (it can't run benchview/infra work), SUPPRESS the triage comment per the core-team-author + no-repro skip rule (precedent #12867), leave labels/Type untouched, and surface the suppression to the parent for override ([perf-infra epic sub-tasks are non-actionable ops](../learnings/1788881515231-perf-infra-epic-sub-tasks-benchview-backtest-are-n.md)). A docs/process sub-task adds a fabrication gate: #12958 asked for "example queries for benchview data," but `benchview` has zero hits in the repo *or* the shared learnings, so a dispatched fixer would invent an undocumented schema — refusing to auto-forward avoids putting fabricated content on a member-owned deliverable ([docs/process deliverable — don't auto-forward](../learnings/1788881799057-triaging-a-docs-process-deliverable-self-assigned-.md)). That atom also gives a positive method: for any "document methodology X" triage, check whether the methodology already has in-tree tooling that IS the raw material (#12958's asks mapped almost 1:1 onto existing `tools/compile-perf/` scripts), so the right next-action pointer is a discoverable `docs/maintainers/` page cross-linking them, not net-new work.

The refinement for a sub-task that names a specific compiler component (e.g. #12962 "Document CUDA backend optimization opportunities"): the same suppress + no-fixer routing still applies, but the triager has a constructive value-add the pure-ops siblings lack — offer to produce a source-inspection optimization survey (no benchview access needed) as a `/slang-plan` research memo, dispatched only on parent/owner go-ahead ([perf-epic sub-task naming a compiler component](../learnings/1788881868519-perf-epic-sub-task-that-names-a-compiler-component.md)). Offer it; don't dump it unsolicited on a MEMBER-watched planning issue. In the event, the assignee wrote that survey themselves (see #12962 below).

How the epic's tasks were labelled and closed is the ground truth for eval triage of them. That is a separate question from bot routing: in the eval, next_step=`fix` means "valid planned work the team does", not "dispatch the fixer". The epic #12941 (benchview, Falcor2/MaterialX, nightly perf CI, alerting, backtesting) carries only `perf` plus Issue Type Performance. An assignee owns it and the work lives in its sub-issues (#13010 and #13034 closed; children #12942–#12959 on the Q4 2026 milestone). Maintainers did not add `CI Improvement` or `Infra`, so don't predict them. The eval's instruction.md shows a `rationale` key, but the sandbox gate's answer.json contract is exactly subsystem/severity/next_step/labels, so the rationale goes in the memo ([perf epic #12941 handled as active tracking work, label `perf` only](../learnings/1792155711726-eval-triage-perf-epic-12941-handled-as-active-trac.md)). The sub-tasks show these outcomes, and what a reply eval expects for each:

- **Delivered outside the repo → `fix`.** #12943 (Falcor2/MaterialX runtime perf scripts for benchview) and its siblings #12942 and #12944–#12948 carry only `perf`; nobody added bug, CI or Falcor labels. jvepsalainen-nv closed #12943 as COMPLETED with a link to Falcor2 GitLab MR !847, which is NVIDIA-internal. The deliverable can land outside shader-slang/slang, so "no in-repo scripts" does not prove the work is undone ([#12941 sub-tasks: `perf` only, closed through internal GitLab MRs](../learnings/1792155809962-perf-epic-12941-sub-tasks-label-is-only-perf-and-a.md)). A reply (not a triage answer) to such a sub-task matches the maintainers when it says three things: this is planned work, not a compiler bug; the repo has no runtime perf scripts (`tools/compile-perf/` measures compile time only, `ci-materialx-regression-test.yml` compiles shaders but records no timings, `ci-falcor2-perf-bridge-smoke.yml` only calls `/opt/slang-ci/run-external-ci` on a self-hosted runner); and the work goes in the Falcor2 repo and gets linked back, with the JSON following the schema issue #12942 (still open on 2026-10-19). It does not promise a slang-fixer PR ([reply eval for perf-epic sub-tasks: say what the repo has, point the work downstream](../learnings/1792402806375-reply-eval-for-perf-epic-sub-tasks-say-what-the-re.md)).
- **Refactor sub-task with the review already in the tree → reply "first part done, rest moves on".** For #12949 (and its follow-on #12954) the review is an in-tree artifact: the workloads sorted into categories (41, mostly SPIR-V or front end), the finding that the `emit_*` family shares one source (1.18x spread), and a "Proposed work" list (`-g`/`-O3` variants, `ParameterBlock` and other missing constructs, a buckets.py update for the detailed timers). PR #13009 added the `backend_loads/samplers/matrix_*` families to `lib/manifest.py` and `DETAILED_PERF_FLAG` to `bench.py`, and found the CUDA slowdown #13010. A reply that matches the maintainer says the first part is done (#13009, #13010), the rest moves to #12954, and the reporter has nothing to do; it does not promise a fixer PR ([reply eval #12949: compile-perf review and plan](../learnings/1792402878617-reply-eval-12949-compile-perf-review-and-plan-live.md)). Where the review lives changed: the maintainer's comment on #12949 points to `tools/compile-perf/COVERAGE-ANALYSIS.md`, but PR #13625 (master 68438b5e1, 2026-10-19) deleted that file at the maintainer's request and moved its content (41 workloads, the emit_* spread, the new families, the one-axis-per-workload note, #13010) into `tools/compile-perf/README.md`. Run `ls tools/compile-perf` before citing either file. Still true after #13625: no workload uses `-g`, `-O3` or `ParameterBlock`, and in #12954 only the "Refactoring complete" box is ticked ([COVERAGE-ANALYSIS.md was deleted by PR #13625; review now in README](../learnings/1792423973743-compile-perf-coverage-analysis-md-was-deleted-by-p.md)).
- **Superseded at an owner change → `close`.** #12960 ("initiative summary + stakeholder handoff") has only `perf`. jkiviluoto-nv closed it on 2026-09-29 as COMPLETED with the bare comment "Closing.", 4 minutes after reassigning the epic from expipiplus1 to jvepsalainen-nv. No document or PR is linked. A sub-task tied to the original owner that closes during an owner change with no artifact is superseded, not delivered. GitHub's COMPLETED stateReason is not proof that the work exists; check the epic timeline for a reassignment at the same time ([#12960 handoff sub-task closed at the owner change](../learnings/1792155909582-perf-epic-12960-handoff-sub-task-was-closed-at-the.md)).
- **"Document X" delivered as an analysis comment → `fix`, not `document`.** On 2026-09-14 jvepsalainen-nv delivered #12962 as one issue comment: the root cause (`introduceExplicitGlobalContext` produces N loads and the scan in `eliminateRedundantLoadStore` is O(n²)), fix PRs #13012 and #13013, the nvrtc share of compile time (22–57%), and sub-issues #13053–#13059. The issue closed COMPLETED 22 minutes later with only `perf`. jhelferty-nv had set Issue Type Documentation; the assignee changed it to Performance when the work was done, and that change is the maintainer's signal. No repo docs changed ([#12962 delivered as an issue comment plus sub-issues](../learnings/1792155999140-perf-epic-12962-cuda-opportunities-doc-task-was-de.md)).

Classification itself is a lever: a self-filed tracking item for an in-progress feature is a Task, not a Bug, because `Bug` means incorrect behavior in *shipped* functionality and a hole in a branch-only feature is not that ([WIP-feature gap is Task not Bug](../learnings/1788367713760-triage-type-wip-feature-implementation-gap-is-task.md)). Defer to the maintainer's framing when they reframe it (correcting a Type you set is not overwriting human triage — post a short ack). shader-slang/slang exposes a rich Issue-Type set beyond Bug/Feature (Task, Performance, Documentation, Refactoring, Build, DevRel, Testing, Language Maturity), fetched via `gh api graphql '{repository{issueTypes(first:20){nodes{id name description}}}}'` and cleared with `updateIssue(issueTypeId: <new>)`.

Performance is an Issue Type, not a label. Codegen-quality and missed-optimization bugs, where the output is correct but redundant (#12847 duplicate `OpGroupNonUniformBallot`, #12785 missed call CSE), got Issue Type **Performance** and no `perf` label. Their only labels were `reproduced`, added after the repro was confirmed (the bot adds it), plus `RTR` on #12785, which jhelferty-nv added for the MaterialX/RTR motivation. #12785 was then assigned and milestoned. For these issues predict `reproduced` once the repro confirms, add a team label (`RTR`, `Falcor`, ...) only when the motivation names that team, and leave out `perf`, `SPIR-V` and `bug` unless the thread shows them. next_step is `fix` when the issue is assigned or milestoned and a PR is in flight ([perf issues: Issue Type Performance, `reproduced` still applies](../learnings/1792154643877-slang-perf-issues-get-issue-type-performance-not-t.md), [perf/codegen-quality issues: Issue Type Performance, not `perf`](../learnings/1792154929449-slang-perf-codegen-quality-issues-get-issue-type-p.md)). The `perf` label marks the perf-infra epic and its sub-tasks, not perf bugs. To check a SPIR-V codegen repro without building, download a release tarball (`gh release download vX -R shader-slang/slang --pattern '*linux-x86_64.tar.gz'`) and run `bin/slangc x.hlsl -target spirv-asm -entry main -stage compute`.

## Non-compiler causes: test-vs-driver defects and runner migrations

When a Slang-side artifact is at fault next to a real driver bug, label the in-repo defect. In shader-slang/slang#12797, two descriptor-handle tests read bindless descriptors that were never written, which is UB, and crashed on lavapipe. A separate Mesa image-descriptor bug was also found. Maintainers labelled it `bug` + `Testing` + `Vulkan` and fixed the tests in PR #12800. They did not apply `Vendor Driver Bug` or `Not a Slang Bug`. So when the test, render-test or slang-rhi usage is at fault, triage as `fix` and label for the in-repo defect plus the backend; keep the driver bug as a side note for an upstream report ([triage labels when a test defect and a driver bug are mixed](../learnings/1792154714041-slang-triage-labels-when-a-test-defect-and-a-drive.md)).

Issues that paste a GitHub runner-image migration email ("Prepare for X runner") often describe a move CI has already made. Before you triage one, run `git log -S '<runner label>'` and grep `.github/workflows` for the label. On #13161 (VS2026 on `windows-11-arm`) the bare `windows-11-arm` label was never used: the native ARM64 jobs already ran on `windows-11-vs2026-arm` (PR #12687, merged 2026-08-26, three weeks before the issue was filed). CI builds with Ninja Multi-Config and `ilammy/msvc-dev-cmd` with no vsversion, so vswhere picks the newest VS and the image switch changes nothing. Windows aarch64 in `release.yml` and `cmake-options.yml` is cross-compiled on x64 `windows-latest`, so ARM image changes do not affect it. The sibling issues (#13288 Ubuntu 26, #11133 VS2026 cmake-options) are Issue Type Build with sparse labels (none or just `CI`), and were closed after a validation or update PR. One latent gap remains: the `vs2026` preset needs CMake 4.2 or newer, but `CMakePresets.json` declares 3.25 ([runner-migration issues: check git log first, CI already moved](../learnings/1792157281260-slang-runner-migration-prepare-for-x-runner-issues.md)).

## Feature requests: test the existing mechanism before recommending a new surface

When an issue asks for a new target, option or API, first check whether the consumer can already get the behavior with existing mechanisms, and if so say that publicly ("this is already expressible as follows", with a doc gap as the likely follow-up). Propose a new public surface only when existing mechanisms genuinely cannot express the request, leave the choice of surface to maintainers, and never publish a PR checklist that presupposes one. On slang#13275 (an aggregate `slang-all` CMake target for submodule consumers) the triage comment recommended a new INTERFACE target plus a checklist, although the triager's own probe had shown that `add_dependencies` on a consumer-side target already builds slang-glsl-module and slang-rt without slangc; maintainer jkwak-work then gave exactly that answer (link `slang`, add `add_dependencies(my-app slang-glsl-module slang-rt …)`, no Slang CMake change). The bot had to withdraw its recommendation by editing comment 5860680154 in place, after an external contributor had already opened draft PR #13448 along the recommended lines. When an external contributor has offered to implement, keep design prescriptions out of the bot's comment entirely ([triage feature requests: test the existing-mechanism answer before recommending new API/targets publicly](../learnings/1791250963495-triage-feature-requests-test-the-existing-mechanis.md)).

The opposite case also exists: the requested API is already designed and documented, but never implemented. On slang#13774 the reporter asked for new `HitObject` functions to reach the SER fused ops (OpHitObjectTraceReorderExecuteEXT / OpHitObjectReorderExecuteShaderEXT). `docs/shader-execution-reordering.md` (:50-54, :916-1010) already documents free functions `ReorderExecute` / `TraceReorderExecute` / `TraceMotionReorderExecute` with an `inout payload_t`, but `hlsl.meta.slang` never defined them (a call gives E30015 undefined identifier); only the GLSL half of SER PRs #9230/#9504 landed. That turns "feature request, park for naming/design direction" into an actionable "implement the documented API" handoff, because the names and signatures are already a merged design and need no maintainer bikeshedding. Check with `grep -rn '<FnName>' docs/`, `git grep` in the `*.meta.slang` files, and a compile of a call to the documented name ([grep docs/ before triaging a missing-API request](../learnings/1792503874053-before-triaging-a-missing-api-feature-request-grep.md)). The SPIR-V side of that issue is on [[wiki/concepts/slang-backends-spirv-capabilities-and-version-gating.md]].

## Contradictions / supersessions

No contradictions. [The compiler-component atom](../learnings/1788881868519-perf-epic-sub-task-that-names-a-compiler-component.md) explicitly *refines* [the pure-ops atom](../learnings/1788881515231-perf-infra-epic-sub-tasks-benchview-backtest-are-n.md) (same routing, plus a constructive survey offer). All seven converge on one rule: route by whether code must be written and by who owns the design decision, defaulting to *hold/suppress + surface to parent* rather than the workflow's default fixer-forward. An earlier wiki note said a missed optimization should not get `reproduced`; [#12785](../learnings/1792154643877-slang-perf-issues-get-issue-type-performance-not-t.md) shows the opposite: once a maintainer confirms the repro, `reproduced` stays. The bot-routing rule for perf-epic sub-tasks (no fixer, suppress the comment) and the eval's next_step=`fix` for delivered sub-tasks don't conflict: the first is about what the bot does, the second records how the team handled the task.
