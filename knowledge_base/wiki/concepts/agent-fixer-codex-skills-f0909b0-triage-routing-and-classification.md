## TL;DR

- **The `/slang-triage-issue` "always forward to slang-fixer" step is a reflex to override, not a mandate.** The fixer wire is for writing/PR'ing code. A read-only deliverable (comment, memo, answer) stays in the analysis tier that can produce it; a fixer hop only adds handoff-death.
- **A core-team author, a self-assignment or a milestone does NOT exclude an issue (operator, 2026-09-09).** Triage and dispatch slang-fixer as for any actionable issue. The only per-issue exclusions: a human PR already fixes it, a maintainer said no bots, or the fix lands in a repo the bot cannot push to (hand the plan to the owner). The old blanket core-team skip is retired: it cut the bot PR rate on those issues from 69% to 36% and the overall WIN rate from 69% to 38%. Don't touch labels/Type a human set.
- **`Dev Opened` and `Dev Reviewed` no longer exist (deleted 2026-10-08 in slang, slangpy, slang-rhi).** `Dev Opened` was always bot-applied, never a triage signal. For authorship use the Slang-All board "Source" field; for triage state use assignee and milestone.
- **slang `bot-ok` = the author opts the bot in**: triage on a maintainer-filed, self-assigned issue, plus a slang-fixer draft PR when the fix is clear; a design-call issue gets triage plus a recommended direction, then stops. Without the label such an issue stays held unless the author @-mentions the bot or the operator asks.
- **On a self-assigned lead's issue, look for the assignee's own PR before asking "should the bot open a draft PR?"** Search by PR author; the issue timeline shows the PR only once it references the issue.
- **Language-design RFCs by a language lead need design sign-off — HOLD the fixer.** Triage fully (file:line grounding, phased plan), post a tight comment, hand the go/no-go to the parent as "design-gated". Precedent: ~10 days spent on a withdrawn feature.
- **Perf-epic / ops-infra sub-tasks (benchview, backtests, ingestion, alerting, runbooks) are ops/PM items, not compiler bugs.** No fixer forward (it can't run infra), suppress the triage comment, surface the suppression to the parent. Their only label is `perf`.
- **Fabrication risk is a hard gate against auto-forwarding.** If an ask references infra the bot can't see (`benchview` has zero repo hits), a fixer would invent a schema. Map the ask onto existing in-tree tooling instead.
- **A perf sub-task naming a compiler component** gets the same routing plus an *offer* of a source-inspection survey (a `/slang-plan` memo) on parent/owner go-ahead only.
- **A WIP-feature gap is a Task, not a Bug** (`Bug` = wrong behavior in shipped functionality). Defer to a maintainer's reframing.
- **Feature request: give the existing-mechanism answer first.** Propose new public surface only when nothing existing works; no design prescriptions when an external contributor offered to implement.
- **Before triaging a "missing API" request, grep `docs/`.** A documented-but-unimplemented API is an actionable "implement the documented design" handoff, not a park-for-design.
- **When a later run supersedes the original triage comment, PATCH the original** (env line, measured results, dated edit note), keeping @mentions byte-identical.

## The routing question: is there code to write?

The through-line is one decision — *does this deliverable require writing code?* — and a recurring failure to ask it before invoking the fixer. When a maintainer asks for an *analysis* posted as a comment ("not ready to commit to a fix yet"), the analysis tier owns it via read-only research subagents, the `/slang-triage-issue` Step-3 pattern ([investigation-only stays in the analysis tier](../learnings/1788542147628-investigation-only-deliverables-stay-in-the-analys.md)). The reflexive fixer hop has a measured cost: on #12092 an analysis sent to a fixer session that died mid-response sat undelivered ~24 days, then again ~1 week, because a dark handoff looks exactly like work in progress. Keeping the deliverable in-tier keeps ONE live session accountable, so "is the work live?" has a checkable answer. Reserve the fixer for an *authorized fix*, post-analysis and maintainer-gated, routed through the tier that holds the chain. To un-dark a stalled analysis chain, monitor your own tier's posting event, not only maintainer comments.

## Whose issue is it? Core-team ownership and opt-in

The old rule — a core-team, self-assigned, `Dev Opened` issue is "already human-triaged", so skip the comment and the fixer — is retired. The operator's correction: such an issue is a well-specified fixer candidate; triage it and dispatch the fixer unless a human PR already carries the fix, a maintainer said no bots, or the fix is in a repo the bot can't push to (then hand the plan to the human owner rather than skipping silently). The skip had lived only in learnings and the wiki, so it is reversed there ([Correction (operator 2026-09-09): Dev Opened and core-team tracking issues ARE in scope](../learnings/1788958700000-correction-dev-opened-and-core-team-tracking-issues-are-in-scope.md)).

The premise under the old rule was also wrong. `.github/workflows/issue-add-labels.yml` (master e6be8dcdd, :57) added `Dev Opened` automatically to every issue opened by a `dev`-team member, and no tracked code read it; the maintained author signal is the Slang-All board "Source" field (issue-onboard.yml → issue-board-onboard.yml, #12854) ([`Dev Opened` label is bot-applied, not a human-triage signal](../learnings/1791220010907-dev-opened-label-is-bot-applied-issue-add-labels-y.md)). PR #13500 then removed the workflow, and on 2026-10-08 ~01:17Z jkwak-work deleted `Dev Opened` and `Dev Reviewed` in slang, slangpy and slang-rhi. Report side-effects: `-label:"Dev Reviewed"` now matches every open issue, so use unowned / no-milestone counts; the deletion put ~600 `unlabeled` events at one second into `/issues/events`, so page back past the window start; and `is:unmerged closed:` missed a closed draft PR (#11617), so count closed-unmerged PRs from REST `/pulls?state=closed` ([Dev Reviewed / Dev Opened labels retired 2026-10-08](../learnings/1791448089783-shader-slang-dev-reviewed-dev-opened-labels-retire.md)).

Language-design RFCs are the exception that still holds. When a language lead (e.g. tangent-vector) authors a design proposal, don't forward to the fixer: triage fully, verify claims against HEAD with file:lines, note what's already implemented without restating the proposal, then HOLD and hand the go/no-go to the parent as "design-gated". #12550, a tangent-vector RFC-style epic, WAS dispatched: ~10 days of parser+AST work and a draft PR, then WITHDRAWN after language-lead discussion ([design-RFC issues, hold the fixer](../learnings/1788909843006-design-rfc-issues-authored-by-a-language-lead-hold.md)).

A self-assigned lead who files a detailed proposal often already has the PR up. On slang#13495 the bot asked "should the bot open a draft PR?" while tangent-vector's #13497 had been open 42 minutes; it merged ~5 hours later with `Fixes #13495`. Right before asking, run `gh pr list -R <repo> --author <assignee> --state all --search "<N>"` ([check for the assignee's own PR before asking a self-assigned lead about a bot PR](../learnings/1791493854161-check-for-the-assignee-s-own-pr-before-asking-a-se.md)).

On shader-slang/slang the author can opt in explicitly. The `bot-ok` label (created 2026-10-21; pdeayton-nv first applied it to #13827, #13828, #13830, #13841, #13842) authorizes triage and, per the operator, "bot-ok does authorize a bot PR, so handing off to slang-fixer is fine if there's a clear fix". Without it, a maintainer's filed-and-self-assigned item stays their own work (the merged R6 itself is label-only, with no wait; see [triage decisions](agent-fixer-triage-decisions.md)) unless they @-mention the bot or the operator asks. On a `bot-ok` issue Main dispatches slang-triager on `gh-issue-shader-slang/slang-<n>` with `<github-post-authorized />`; the triager hands off to slang-fixer when the fix direction is clear (stated or confirmed by triage), and otherwise posts triage with a recommended direction and stops ([slang `bot-ok` label: author opts the bot in, including a bot PR when the fix is clear](../learnings/1792623822987-slang-bot-ok-label-author-opts-the-bot-in-includin.md)).

## The perf epic: ops work and fabrication risk

The 2026-09-08 batch (epic #12941 + children #12942–#12959, self-assigned, now labelled only `perf`) anchors how to classify non-compiler work. These are ops/infra/PM items — benchview DB clearing, backtest harnesses, ingestion, Slack alerting, runbooks, metric schemas — so: Category=ops, no fixer forward, suppress the triage comment (core-team author + no repro, precedent #12867), leave labels/Type alone, surface the suppression to the parent ([perf-infra epic sub-tasks are non-actionable ops](../learnings/1788881515231-perf-infra-epic-sub-tasks-benchview-backtest-are-n.md)). A docs/process sub-task adds a fabrication gate: #12958 asked for "example queries for benchview data", but `benchview` has zero hits in the repo or the learnings, so a fixer would invent a schema on a member-owned deliverable. The positive method: check whether in-tree tooling already IS the raw material — #12958's asks mapped almost 1:1 onto `tools/compile-perf/` scripts, so the right pointer is a `docs/maintainers/` page cross-linking them ([docs/process deliverable — don't auto-forward](../learnings/1788881799057-triaging-a-docs-process-deliverable-self-assigned-.md)).

A sub-task naming a compiler component (#12962 "Document CUDA backend optimization opportunities") gets the same routing, plus the offer of a source-inspection optimization survey (no benchview needed) as a `/slang-plan` memo on parent/owner go-ahead — offered, not dumped on a MEMBER-watched planning issue ([perf-epic sub-task naming a compiler component](../learnings/1788881868519-perf-epic-sub-task-that-names-a-compiler-component.md)). In the event the assignee wrote it themselves.

## Issue Types: Task vs Bug

A self-filed tracking item for an in-progress feature is a Task, not a Bug: `Bug` means wrong behavior in *shipped* functionality ([WIP-feature gap is Task not Bug](../learnings/1788367713760-triage-type-wip-feature-implementation-gap-is-task.md)). Defer to a maintainer's reframing with a short ack. shader-slang/slang's Issue Types (Task, Bug, Feature, Performance, Documentation, Refactoring, Build, DevRel, Testing, Language Maturity) come from `gh api graphql '{repository{issueTypes(first:20){nodes{id name description}}}}'`; set with `updateIssue(issueTypeId: <new>)`.

## Feature requests: existing mechanism first, then the docs

When an issue asks for a new target, option or API, first check whether existing mechanisms already do it and say so publicly (often with a doc gap as follow-up). Propose new surface only when nothing works, leave the surface choice to maintainers, never publish a checklist that presupposes one. On slang#13275 (aggregate `slang-all` CMake target) the bot recommended a new INTERFACE target although its own probe had shown consumer-side `add_dependencies(my-app slang-glsl-module slang-rt …)` already worked; jkwak-work gave exactly that answer, and the bot had to withdraw the recommendation in place (comment 5860680154) after an external contributor had opened draft PR #13448 along its lines ([triage feature requests: test the existing-mechanism answer before recommending new API/targets publicly](../learnings/1791250963495-triage-feature-requests-test-the-existing-mechanis.md)).

The opposite case: the API is designed and documented but never implemented. On slang#13774 (SER fused ops OpHitObjectTraceReorderExecuteEXT / OpHitObjectReorderExecuteShaderEXT), `docs/shader-execution-reordering.md` (:50-54, :916-1010) documents `ReorderExecute` / `TraceReorderExecute` / `TraceMotionReorderExecute` with an `inout payload_t`, but `hlsl.meta.slang` never defined them (E30015); only the GLSL half of SER PRs #9230/#9504 landed. A merged design needs no bikeshedding, so it's an actionable handoff. Check with `grep -rn '<FnName>' docs/`, `git grep` in `*.meta.slang`, and a compile of the documented call ([grep docs/ before triaging a missing-API request](../learnings/1792503874053-before-triaging-a-missing-api-feature-request-grep.md)). The SPIR-V side is on [[wiki/concepts/slang-backends-spirv-capabilities-and-version-gating.md]].

## Keeping the original triage comment current

On slangpy#163 a later delta posted real CUDA results, but the original triage comment still said "this runner has no GPU" and called the results predictions. Readers, including newly assigned engineers, land on the oldest, longest comment, so PATCH it too: fix the environment line, swap predictions for measurements, add a dated edit note, keep @mentions byte-identical (an edited mention does not re-notify). Same issue: with slangpy 0.43.1 on the L40S fleet, `Device.enumerate_adapters(DeviceType.wgpu)` returns `[]` while vulkan and cuda work, so WGSL-layout cases need slangc reflection or simulation ([correct the original triage comment in place when a later delta supersedes it](../learnings/1792809371629-correct-the-original-triage-comment-in-place-when-.md)).
