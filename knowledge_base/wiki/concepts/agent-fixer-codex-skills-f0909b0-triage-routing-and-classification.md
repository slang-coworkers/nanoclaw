## TL;DR

- **The `/slang-triage-issue` "always forward to slang-fixer" step is a reflex to override, not a mandate.** The fixer wire exists for *writing/PR'ing code*. A read-only deliverable (post a comment, write a memo, answer a question) belongs to the analysis tier that can already produce it — adding a fixer hop buys nothing and re-introduces handoff-death.
- **Operator correction 2026-09-09: a `Dev Opened` label, a core-team author or a self-assignment does NOT exclude an issue.** Triage it and dispatch slang-fixer as for any actionable issue; the only per-issue exclusions are an existing human PR that fixes it, an explicit do-not-touch from a maintainer, or a fix that lands in a repo the bot cannot push to ([Correction (operator 2026-09-09): Dev Opened and core-team tracking issues ARE in scope](../learnings/1788958700000-correction-dev-opened-and-core-team-tracking-issues-are-in-scope.md)). The earlier blanket skip ('label + self-assignment IS the human triage, do NOT auto-dispatch the fixer') is RETIRED: it drove the bot PR rate on `Dev Opened` issues from 69% to 36% and the overall WIN rate from 69% to 38% (JUL vs AUG cohorts). Don't touch labels/Type the human set — that's over-reach against the standing "reign in the bot" signal. Still report up to close the chain and record a memo.
- **`Dev Opened` and `Dev Reviewed` no longer exist (deleted 2026-10-08 in slang, slangpy and slang-rhi).** `Dev Opened` was always bot-applied, never a triage signal, and its producer workflow is gone. For authorship use the Slang-All board "Source" field; for triage state use assignee and milestone.
- **On a self-assigned lead's issue, look for the assignee's own PR before asking "should the bot open a draft PR?"** Search by PR author, since the issue timeline shows the link only once the PR references the issue.
- **Perf-epic / ops-infra sub-tasks (benchview, backtest harnesses, ingestion, alerting, runbooks) are ops/PM execution items, not compiler bugs.** Do NOT forward to the fixer (it can't run infra work); SUPPRESS the triage comment (core-team author + no repro); surface the suppression to the parent for override rather than silently skipping.
- **Fabrication risk is a hard gate against auto-forwarding.** If a doc/methodology ask references infra the bot can't see (e.g. `benchview` has zero repo hits), a dispatched fixer would invent an undocumented schema. Refuse to auto-forward; check whether the methodology already has in-tree tooling that IS the raw material (map the ask onto existing scripts).
- **Language-design RFCs authored by a language lead need design sign-off before implementation — HOLD the fixer.** Triage fully (classify, ground every claim to file:line, phase the implementation), post a tight comment, then hand the go/no-go to the parent framed as "design-gated — release the fixer only on greenlight." Premature dispatch burns real effort (precedent: ~10 days on a withdrawn feature).
- **A feature request ("add target/option/API X") gets the existing-mechanism answer first.** If your own probe shows the consumer can already do it, say so; propose a new public surface only when nothing existing works, and keep design prescriptions out when an external contributor offered to implement.
- **A WIP-feature implementation gap is a Task, not a Bug.** `Bug` = incorrect behavior in *shipped* functionality; a hole in an unreleased/branch-only feature is `Task`. Defer to the maintainer's framing if they reframe it. shader-slang/slang has rich Issue Types (Task, Bug, Feature, Performance, Documentation, Refactoring, Build, DevRel, Testing, Language Maturity).
- **Constructive value-add without over-reach:** when a perf-epic planning sub-task names a specific *compiler component*, offer a source-inspection optimization survey (a `/slang-plan` research memo, NOT a fixer task) — on parent/owner go-ahead only. Offer it; don't dump it unsolicited on a MEMBER-watched planning issue.

## The routing question: is there code to write?

The through-line of this page is a single decision — *does this deliverable require writing code?* — and a recurring failure to answer it before invoking the fixer. The fixer's wire exists for authoring and PR'ing code; routing anything code-adjacent to it is the wrong shape for a read-only, no-code deliverable. When a maintainer asks for an *analysis* posted as a comment ("not ready to commit to a fix yet"), the analysis tier owns it via read-only research subagents — the `/slang-triage-issue` Step-3 pattern ([investigation-only stays in the analysis tier](../learnings/1788542147628-investigation-only-deliverables-stay-in-the-analys.md)). The cost of the reflexive fixer hop is concrete: on #12092 an analysis dispatched to a fixer session that died mid-response sat undelivered for ~24 days, then again ~1 week, because a dark handoff is byte-indistinguishable from work-in-progress. Producing the deliverable in-tier keeps ONE live session accountable end-to-end, so "is the work live?" has a checkable answer. Reserve the fixer wire for an *authorized fix*, post-analysis and maintainer-gated, routed THROUGH the tier that holds the chain. The corollary for the waiting party: to un-dark a stalled analysis chain, point the monitor at *your own tier's* posting event, not only at maintainer comments — the silence that matters is "no analysis produced," which your own guard can see.

## Whose issue is it? Core-team ownership skips

A large sub-family WAS "the human already triaged this, so the bot's job is minimal." That rule is retired (Operator correction 2026-09-09): a human-triaged `Dev Opened` issue is a well-specified fixer candidate, not an exclusion, and the fixer is dispatched unless a human PR already carries the fix ([Correction (operator 2026-09-09): Dev Opened and core-team tracking issues ARE in scope](../learnings/1788958700000-correction-dev-opened-and-core-team-tracking-issues-are-in-scope.md)). Historically, when an issue was authored by a core-team MEMBER/COLLABORATOR, self-assigned, and labeled `Dev Opened`, the core-team-skip rule was applied even to fully-specced engineering tasks — the label + self-assignment IS the human triage, and auto-dispatching the fixer to implement is over-reach against the standing "reign in the bot" signal (jhelferty-nv, #12586) ([core-team self-assigned → skip triage](../learnings/1788215669900-core-team-self-assigned-dev-opened-issue-skip-tria.md)). The bot's value on these is a *verified* internal disposition memo + an offer to produce a fixer briefing on explicit request — not autonomous implementation; still report up to close the chain and record the memo, just skip the GitHub-facing triage and the fixer forward. The premise under that old rule was also wrong: `Dev Opened` was never human triage. `.github/workflows/issue-add-labels.yml` (master e6be8dcdd, line 57) adds it automatically to every issue opened by a member of the `dev` team, and no tracked code reads it, so neither "human-set labels mean triage is complete" nor any routing rule should key on it. The maintained author signal is the Slang-All board "Source" field (issue-onboard.yml → issue-board-onboard.yml, #12854). That proposal (#13441) has since landed: PR #13500 removed `issue-add-labels.yml`, and on 2026-10-08 ~01:17Z jkwak-work deleted both the `Dev Opened` and `Dev Reviewed` labels in slang, slangpy and slang-rhi (`/labels/Dev%20Reviewed` now 404s). No routing or triage rule can key on either label any more; older notes that mention them describe history ([`Dev Opened` label is bot-applied, not a human-triage signal](../learnings/1791220010907-dev-opened-label-is-bot-applied-issue-add-labels-y.md), [Dev Reviewed / Dev Opened labels retired 2026-10-08](../learnings/1791448089783-shader-slang-dev-reviewed-dev-opened-labels-retire.md)).

Language-design RFCs sharpen this. When the issue is a language-design proposal authored by a language lead (e.g. tangent-vector / Theresa Foley), do NOT follow "always forward to fixer" — these need design sign-off before implementation ([design-RFC issues, hold the fixer](../learnings/1788909843006-design-rfc-issues-authored-by-a-language-lead-hold.md)). Triage fully and post a tight, value-adding comment (verify claims against HEAD with file:lines; note what's already implemented; never restate their proposal), then HOLD fixer dispatch and hand the go/no-go to the parent as "design-gated." The cautionary precedent: #12550, a tangent-vector RFC-style epic, WAS dispatched → ~10 days of parser+AST implementation and a draft PR → then WITHDRAWN by the maintainer after language-lead discussion. Dispatching a fixer to build a multi-phase language feature is resource-intensive and hard to reverse; it warrants explicit authorization.

A self-assigned lead who files a detailed design proposal often already has the PR up, so even the question "should the bot open a draft PR?" can be moot. On slang#13495 (2026-10-07) the bot asked it while tangent-vector's own PR #13497 had been open for 42 minutes; #13497 merged about 5 hours later with `Fixes #13495`. The issue timeline doesn't show such a PR until it links back, so right before posting the question run `gh pr list -R <repo> --author <assignee> --state all --search "<N>"`, searching by PR author rather than only by issue cross-references ([check for the assignee's own PR before asking a self-assigned lead about a bot PR](../learnings/1791493854161-check-for-the-assignee-s-own-pr-before-asking-a-se.md)).

## The perf epic: ops work, fabrication risk, and Issue Types

The 2026-09-08 batch (epic #12941 + ~18 children #12942–#12959, all self-assigned, `Dev Opened`+`perf`) is the anchor for classifying non-compiler work. These sub-tasks are ops/infra/PM execution items — benchview DB clearing, backtest harnesses, ingestion, Slack alerting, runbooks, metric-schema definition — NOT compiler code bugs, so: classify Category=ops, do NOT forward to the fixer (it can't run benchview/infra work), SUPPRESS the triage comment per the core-team-author + no-repro skip rule (precedent #12867), leave labels/Type untouched, and surface the suppression to the parent for override ([perf-infra epic sub-tasks are non-actionable ops](../learnings/1788881515231-perf-infra-epic-sub-tasks-benchview-backtest-are-n.md)). A docs/process sub-task adds a fabrication gate: #12958 asked for "example queries for benchview data," but `benchview` has zero hits in the repo *or* the shared learnings, so a dispatched fixer would invent an undocumented schema — refusing to auto-forward avoids putting fabricated content on a member-owned deliverable ([docs/process deliverable — don't auto-forward](../learnings/1788881799057-triaging-a-docs-process-deliverable-self-assigned-.md)). That atom also gives a positive method: for any "document methodology X" triage, check whether the methodology already has in-tree tooling that IS the raw material (#12958's asks mapped almost 1:1 onto existing `tools/compile-perf/` scripts), so the right next-action pointer is a discoverable `docs/maintainers/` page cross-linking them, not net-new work.

The refinement for a sub-task that names a specific compiler component (e.g. #12962 "Document CUDA backend optimization opportunities"): the same suppress + no-fixer routing still applies, but the triager has a constructive value-add the pure-ops siblings lack — offer to produce a source-inspection optimization survey (no benchview access needed) as a `/slang-plan` research memo, dispatched only on parent/owner go-ahead ([perf-epic sub-task naming a compiler component](../learnings/1788881868519-perf-epic-sub-task-that-names-a-compiler-component.md)). Offer it; don't dump it unsolicited on a MEMBER-watched planning issue.

Classification itself is a lever: a self-filed tracking item for an in-progress feature is a Task, not a Bug, because `Bug` means incorrect behavior in *shipped* functionality and a hole in a branch-only feature is not that ([WIP-feature gap is Task not Bug](../learnings/1788367713760-triage-type-wip-feature-implementation-gap-is-task.md)). Defer to the maintainer's framing when they reframe it (correcting a Type you set is not overwriting human triage — post a short ack). shader-slang/slang exposes a rich Issue-Type set beyond Bug/Feature (Task, Performance, Documentation, Refactoring, Build, DevRel, Testing, Language Maturity), fetched via `gh api graphql '{repository{issueTypes(first:20){nodes{id name description}}}}'` and cleared with `updateIssue(issueTypeId: <new>)`.

## Feature requests: test the existing mechanism before recommending a new surface

When an issue asks for a new target, option or API, first check whether the consumer can already get the behavior with existing mechanisms, and if so say that publicly ("this is already expressible as follows", with a doc gap as the likely follow-up). Propose a new public surface only when existing mechanisms genuinely cannot express the request, leave the choice of surface to maintainers, and never publish a PR checklist that presupposes one. On slang#13275 (an aggregate `slang-all` CMake target for submodule consumers) the triage comment recommended a new INTERFACE target plus a checklist, although the triager's own probe had shown that `add_dependencies` on a consumer-side target already builds slang-glsl-module and slang-rt without slangc; maintainer jkwak-work then gave exactly that answer (link `slang`, add `add_dependencies(my-app slang-glsl-module slang-rt …)`, no Slang CMake change). The bot had to withdraw its recommendation by editing comment 5860680154 in place, after an external contributor had already opened draft PR #13448 along the recommended lines. When an external contributor has offered to implement, keep design prescriptions out of the bot's comment entirely ([triage feature requests: test the existing-mechanism answer before recommending new API/targets publicly](../learnings/1791250963495-triage-feature-requests-test-the-existing-mechanis.md)).

## Contradictions / supersessions

No contradictions. [The compiler-component atom](../learnings/1788881868519-perf-epic-sub-task-that-names-a-compiler-component.md) explicitly *refines* [the pure-ops atom](../learnings/1788881515231-perf-infra-epic-sub-tasks-benchview-backtest-are-n.md) (same routing, plus a constructive survey offer). All seven converge on one rule: route by whether code must be written and by who owns the design decision, defaulting to *hold/suppress + surface to parent* rather than the workflow's default fixer-forward.
