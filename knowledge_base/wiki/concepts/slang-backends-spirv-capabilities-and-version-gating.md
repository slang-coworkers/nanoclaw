# Slang SPIR-V capabilities, extensions, and version gating

How SPIR-V capabilities and extensions are declared in `slang-capabilities.capdef`, how emission is gated, how the emitted SPIR-V version header is chosen, and where `[require]` is (and is not) enforced. The emitter-level overview is on [[wiki/concepts/slang-backends-spirv.md]].

## TL;DR

- `slang-capabilities.capdef` is the single source of truth: one extension atom plus one capability atom, each with a `///` doc and an `[EXT]` tag. Generated enums are never hand-edited.
- A NEW capdef atom changes `slangc -h` and the capability-atom reference, so it trips both `check-cmdline-ref` and `check-capability-atoms-ref`; wait for both. Adding or reordering atoms is `pr: non-breaking`.
- Specify a capability through the API by STRING name (`entry.value.kind = String`, `stringValue0 = "spvGroupNonUniformArithmetic"`) or resolve it with `findCapability(name)`, never the internal generated `CapabilityName` int.
- Triage "add a capability bit" by grepping the vendored SPIRV-Headers first; a capdef atom is inert until something consumes it.
- Gate capability-conditional emit on `targetCaps.implies(CapabilityAtom::spvFooEXT)`, never `isSPIRV(...)` (which fires for every SPIR-V target).
- `[require]` atoms and capdef atoms never emit `OpCapability`/`OpExtension`: emission is always explicit emitter C++ (`ensureExtensionDeclaration`) or an inline `spirv_asm` declaration. Declare the capability inline for `spirv_asm` builtin loads.
- A SPIR-V validation fix needs a `-target spirv` test so spirv-val runs. A spec saying "requires X" does not mean bundled spirv-val enforces X; run the counterfactual.
- A capability that depends on operand constness needs a new backend IR op; Slang does not iterate inside `spirv_asm` blocks.
- Emitted SPIR-V version = max over the target format, explicit `-profile`/`-capability`, and public `spirv_1_x` require-decorations. A used function's `[require]` chain never raises it, and a GLSL-family profile implies a floor, not a pin.
- `-capability` silently raises the version past an explicit `-profile`: a version raise is always a compatible `CapabilitySet` join and `requireSpirvVersion` takes the max.
- A capdef floor edit alone cannot make a module valid; SER at 1.4 shipped as floor `_spirv_1_5`→`_spirv_1_4` plus a centrally declared PSB `OpExtension`.
- `spvShaderInvocationReorderNV` ⊇ `spvShaderInvocationReorderEXT`, so an EXT-only `__target_switch` case also matches NV targets (the GLSL SER fused functions emit an EXT op on `OpTypeHitObjectNV`).
- Entry-point `[require]` never reaches `getTargetCaps()`, the codegen cap set, or `specializeTargetSwitch`. That is a silent divergence on codegen-decision paths; honoring it needs per-entry-point specialization, not an emit patch.
- E36107 fires only on entry-point-reachable typed resources, and a method-level `[require]` on a case-less `__target_switch` is inert; the enforcing clause is the TYPE-level `[require]` on the shape struct.
- Revert-drill a capability predicate at HEAD with a rebuilt binary before building on a triage premise (#11903).

## Adding and registering a capability atom

**Adding a capability atom:** The single source of truth is `source/slang/slang-capabilities.capdef`. Two lines are needed per capability — an extension atom (`def SPV_EXT_foo : _spirv_1_0;`) and a capability atom (`def spvFooEXT : SPV_EXT_foo;`). Each requires `///` doc comment + `/// [EXT]` tag. The build runs `slang-capability-generator` to produce the C++ enum headers — never hand-edit those. Adding an atom also regenerates two checked-in docs: `docs/user-guide/a3-02-reference-capability-atoms.md` (alphabetical) and `docs/command-line-slangc-reference.md` (declaration order, byte-exact diff enforced by CI) ([Adding a SPIR-V capability atom to Slang (capdef recipe)](../learnings/1781120340432-adding-a-spir-v-capability-atom-to-slang-capdef-re.md), [Adding a SPIR-V capability atom — ADDENDUM (two generated docs + test -capability)](../learnings/1781122622446-adding-a-spir-v-capability-atom-addendum-two-gener.md)).

**Adding/reordering capdef atoms is `pr: non-breaking` — not an ABI break** (verified via #12244, MERGED): the public `SlangCapabilityID` is opaque, single-enumerator, and resolved by NAME at runtime via `ISession::findCapability(name)`; the generated `CapabilityName`/`CapabilityAtom` enums are internal-only, positional, and exposed by no public API, so inserting an atom mid-list shifts only internal ints. Carry the precision honestly: atoms ARE serialized by value into internal IR / `.slang-module` (`IRRequireCapabilityAtomDecoration` reads `intVal`), but that format is already not cross-version-stable (recompiled per compiler version), so every prior capdef add shifted these and none were breaking — claim "no public ABI break, consistent with module-versioning practice," not "never serialized by value" ([capability-atom rename PRs are ABI-safe (slang#12244)](../learnings/1785429130429-capability-atom-rename-prs-are-abi-safe-shadow-bia.md)).

**Specifying a capability through the compilation API:** the `CompilerOptionName::Capability` doc comment saying "intValue0 encodes a value from the CapabilityName enum" is a docs bug — `CapabilityName` is generated, internal, and not shipped in the SDK. The supported stable path is the STRING NAME: set `entry.value.kind = String` and `stringValue0 = "spvGroupNonUniformArithmetic"`, consumed at `TargetRequest::getTargetCaps()` via `findCapabilityName(...)`. Alternatively resolve the int at runtime with the public `IGlobalSession::findCapability(name)`. Do NOT recommend exposing `CapabilityName` publicly — raw ints are version-unstable by design (#12286) ([specify a capability via the compilation API by string name](../learnings/1785415625670-how-to-specify-a-capability-via-the-slang-compilat.md)).

**Triaging "add a SPIR-V capability bit" requests (#11538).** Grep `external/spirv-headers/include/spirv/unified1/spirv.h` first: the `SpvCapability*` operand is often already vendored and needs no submodule bump. A bare capdef atom is inert until a `[require(...)]` intrinsic or a C++ emit site consumes it ([capability-bit triage: vendored-operand check + inert-atom scoping](../learnings/1781116222932-triaging-an-quot-add-a-spir-v-capability-bit-quot-.md)). New `Spv*` enum constants resolve from the SPIRV-Headers package, NOT from the stale `external/spirv/spirv.h` ([new Spv* enum constants resolve from the SPIRV-Headers package](../learnings/1782322517394-slang-spir-v-emit-new-spv-enum-constants-resolve-f.md)).

## Emitting capabilities and extensions

**Gating emit on a capability atom.** The correct pattern is `targetCaps.implies(CapabilityAtom::spvFooEXT)`, following the precedent at `slang-emit-spirv.cpp:1692` (`CapabilityAtom::spvBindlessTextureNV`; about 8 sibling sites agree), with the extension string added inside the block by `ensureExtensionDeclaration`. Do NOT gate on `isSPIRV(...)`, which fires for every SPIR-V target, and do not gate on an extension-string atom where a capability atom exists. An earlier triage learning advised `isSPIRV()`; the correction supersedes it ([use implies(CapabilityAtom::spv*), NOT isSPIRV()](../learnings/1781123971590-correction-spir-v-capability-emit-gating-use-impli.md)). When adding a conditional capability for a stdlib `spirv_asm` intrinsic, choose from the option tree in [conditionally requiring a SPIR-V capability for a stdlib spirv_asm intrinsic — layer-choice tree](../learnings/1781974573249-conditionally-requiring-a-spir-v-capability-for-a-.md) (constexpr-only, post-hoc pass rewrite, new IR op, placeholder operand idiom).

**Capdef atoms never emit.** `determineSpirvVersion()` reads atoms only for the version floor and a few flags; every `OpExtension` comes from a hand-written `ensureExtensionDeclaration("SPV_...")`, and `-capability SPV_EXT_physical_storage_buffer` alone emits nothing. `SPV_KHR_physical_storage_buffer` is only an emit string, not a capdef atom ([capdef atoms never auto-emit an OpExtension](../learnings/1784120354355-slang-capdef-atoms-never-auto-emit-an-opextension-.md)).

**Inline capability for `spirv_asm` builtin loads.** `RayCurrentTime()` emitted `BuiltIn CurrentRayTimeNV` with no `OpCapability RayTracingMotionBlurNV`, so spirv-val rejected the module. Declare the capability inline in the `spirv_asm` block ([[require] doesn't emit OpCapability](../learnings/1782828754941-require-capability-atom-does-not-auto-emit-opcapab.md)). Test such a validation fix with a real `-target spirv` directive, because a `spirv-asm`-only check can pass without validating ([validation fixes need -target spirv](../learnings/1782833127380-spir-v-capability-validation-fixes-need-a-target-s.md)).

**Constness-conditional capability (#9382).** A constant `Gather` offset must use `ConstOffset` with no capability, while a runtime offset needs `Offset` + `ImageGatherExtended`. Maintainer rule: replace the `*.meta.slang` body with a new backend IR op that decides constness and capability; never iterate inside `spirv_asm` ([constness-conditional capability → new backend IR op](../learnings/1784164953340-conditional-spir-v-capability-by-operand-constness.md)).

**Signature-derived VariablePointers.** A capability derived from a signature type must gate on the function surviving inlining: check `[noinline]` via `findDecoration`, not `hasUses()`, or VariablePointers is over-declared (driver bug #9061) ([VariablePointers must gate on [noinline]](../learnings/1781023718622-signature-derived-spir-v-variablepointers-must-gat.md)). The value-site rules and what VariablePointers can and cannot lift are on [[wiki/concepts/slang-backends-spirv.md]].

**Conditionally requiring a capability for ray tracing:** To limit a shader to `SPV_KHR_ray_query` without pulling in `SPV_KHR_ray_tracing`, use `-capability spvRayQueryKHR` and verify no `TraceRay`/raygen path re-introduces the extension. The `RaytracingAccelerationStructure` type itself triggers a dual "any" requirement; post-PR #6615 dedup should collapse it to ray_query when only `RayQuery` usage exists ([Slang AS: forcing ray-query-only capability (avoid SPV_KHR_ray_tracing)](../learnings/1781905197543-slang-as-forcing-ray-query-only-capability-avoid-s.md)).

## The emitted SPIR-V version

**Emitted version.** `determineSpirvVersion` (slang-ir-spirv-legalize.cpp ~2482) takes a max over `getTargetCaps()` (format + explicit profile/capability) plus public `spirv_1_x` require-decorations. SER's internal `_spirv_1_5` is not matched, so a TraceRay shader under `-profile spirv_1_4` still emits 1.4. Build and run; don't infer ([[require] doesn't drive the version header](../learnings/1784157894453-entry-point-require-caps-do-not-drive-the-emitted-.md)). A `-profile` pins a version only when its family matches the target: use `profile.getFamily()`/`getVersion()` gated by `isSPIRV(format)`, not `isKhronosTarget`. `glsl_450` implies a 1.3 floor, not a pin ([GLSL-family -profile doesn't pin](../learnings/1784157903315-a-glsl-family-profile-does-not-pin-a-spir-v-output.md)).

**`-capability` silently raises the SPIR-V version past an explicit `-profile` (#12097/#12099):** `slangc -profile spirv_1_4 -capability spvShaderInvocationReorderNV` silently emits a `; Version: 1.5` header (exit 0, no diagnostic). Root cause: `-capability` atoms are folded into target caps in `TargetRequest::getTargetCaps()` (`slang-target.cpp:214-232`) via `if (!targetCap.isIncompatibleWith(toAdd)) targetCap.join(toAdd)`, and `CapabilitySet::isIncompatibleWith` (`slang-capability.cpp:487-512`) treats two sets as compatible whenever they share ANY target abstract node — `spirv_1_4` and `spirv_1_5` are the SAME SPIR-V target, so the join proceeds and `determineSpirvVersion` takes the MAX (`requireSpirvVersion` = `Math::Max`). A version *raise* is thus always a *compatible* join, never flagged. The missing prerequisite for any conflict diagnostic: nothing records whether the profile's concrete version was USER-EXPLICIT vs defaulted (default is `spirv_1_5`), so a CLI-conflict check (fix layer A at the `getTargetCaps` join with a fire-once DiagnosticSink; cleaner layer B at parse-time in `slang-options.cpp`) must add that flag first. This is a distinct layer from the code-implied capability errors E41012/E41013 (`slang-check-shader.cpp`, gated by `-restrictive-capability-check`); a CLI conflict wants an unconditional error. Correct discriminator: key off "capability has NO valid realization at the explicit version (extension paths included)", NOT "default realization exceeds version" ([-capability silently raises SPIR-V version past explicit -profile (#12099)](../learnings/1784052596356-why-capability-silently-raises-spir-v-version-past.md)).

The specific over-require driving #12097 is that the SER extensions are pinned to `_spirv_1_5` in the capdef: `slang-capabilities.capdef:624` `def SPV_EXT_shader_invocation_reorder : _spirv_1_5 + SPV_KHR_ray_tracing;` (NV inherits at `:629`, motion aliases at `:862`/`:867`) — a deliberate simplification per the source comment, even though SER is usable at 1.4 given a physical-storage-buffer extension. **A capdef `_spirv_1_5`→`_spirv_1_4` floor edit ALONE does NOT make the 1.4 module valid:** the SER emit path (`emitOpTypeHitObject*`, `slang-emit-spirv.cpp:2745-2762`) declares only the reorder `OpExtension`/`OpCapability`; the only site that emits `OpExtension "SPV_KHR_physical_storage_buffer"` is `requirePhysicalStorageAddressing()` and it fires only under `PhysicalStorageBuffer64` addressing (buffer_reference usage), which a plain SER raygen shader never triggers. So the 1.4 path emits no PSB extension. SER's spec dependency at 1.4 is `SPV_KHR_ray_tracing` plus one of {PSB extension, core 1.5}, but the bundled spirv-val accepts the module without PSB: the triage claim that it fails validation was overturned in PR #12115, which declares PSB anyway for spec-correctness ([SER at 1.4 without PSB: spirv-val accepts it](../learnings/1784102979347-correction-spir-v-ser-at-1-4-without-psb-bundled-s.md)). The 1.4 path must declare the PSB *extension* without switching the memory model away from `Logical GLSL450`. Note `SPV_KHR_physical_storage_buffer` is a hardcoded emit string, not a capdef atom (only `SPV_EXT_physical_storage_buffer : _spirv_1_3` exists); capdef disjunction (`|`) could model the "1.4+PSB OR core-1.5" rule but still needs the emission change ([SPIR-V SER capability over-requires 1.5; capdef floor edit alone insufficient (#12097)](../learnings/1784052492569-spir-v-ser-capability-over-requires-1-5-capdef-flo.md)). #12097 and #12099 are a paired "allow the 1.4 downgrade" vs "reject the conflicting `-profile`/`-capability` combo" issue set from the same author (jkwak-work) for the identical repro — when triaging one of a paired allow/reject set, flag the tension to the maintainer rather than silently picking a side.

**The shipped SER fix (#12097 → PR #12115)** has two parts: the capdef floor `_spirv_1_5`→`_spirv_1_4`, and `SPV_KHR_physical_storage_buffer` declared centrally in `requireSPIRVCapability` ([SER at 1.4 without PSB: spirv-val accepts it](../learnings/1784102979347-correction-spir-v-ser-at-1-4-without-psb-bundled-s.md)). Capability-floor PR checklist: added atom floors ≤ target; the guard reads effective `m_spvVersion`, not the profile; `ensureExtensionDeclaration` is idempotent; memory model stays `Logical GLSL450`; a spirv-val test ships ([SER 1.4 fix #12115: floor + PSB OpExtension both required](../learnings/1784139502358-approver-confirmed-safe-ser-spir-v-1-4-fix-12115-c.md)). A NEW atom changes `slangc -h` and the capability-atom reference (`docs/user-guide/a4-02-reference-capability-atoms.md`, formerly a3-02), so query both ref check-runs at the pinned head ([new capdef ATOM trips both ref checks](../learnings/1784139517684-approver-clause-gap-new-capdef-atom-not-just-floor.md)).

**SER fused ops and the NV ⊇ EXT capability overlap (slang#13774).** The documented free functions `ReorderExecute` / `TraceReorderExecute` / `TraceMotionReorderExecute` are missing from `hlsl.meta.slang` (only the GLSL half of #9230/#9504 landed; triage view on [[wiki/concepts/agent-fixer-codex-skills-f0909b0-triage-routing-and-classification.md]]). Three facts for whoever implements them. `slang-ir-ray-tracing-legalize.cpp:146-159` already knows the payload operand index of all three fused opcodes. An inline `spirv_asm` fused op needs a `[__vulkanRayPayload] static` payload variable; a plain local fails spirv-val with "payload must be a OpVariable of storage class RayPayloadKHR". And the existing GLSL fused functions under `-capability spvShaderInvocationReorderNV` emit the EXT op on an `OpTypeHitObjectNV`, which is invalid: `spvShaderInvocationReorderNV` ⊇ `spvShaderInvocationReorderEXT` (capdef:871), so an EXT-only `__target_switch` case also matches NV targets ([grep docs/ before triaging a missing-API request; SER fused-op facts](../learnings/1792503874053-before-triaging-a-missing-api-feature-request-grep.md)).

## Where `[require]` is enforced

**`[require]` never reaches codegen (#11631).** `[require(spirv_1_5)]` first failed to raise the version because `IRRequireCapabilityAtomDecoration` reached only the layout IR module and never the codegen module that `determineSpirvVersion()` scans; the fix calls `addEntryPointRequireCapabilityDecorations()` from codegen lowering and maps internal `_spirv_1_x` atoms ([#11631 correction: require atom stamped only on the layout module](../learnings/1781643037138-correction-to-11631-version-root-cause-require-ato.md)). More generally, Entry-point `[require(...)]` atoms never update the SPIR-V codegen cap set; the version path partly compensates, bindless does not ([[require] never reaches codegen cap set](../learnings/1781638061693-slang-require-capabilities-never-reach-codegen-cap.md)). Severity: a silent SS-class runtime divergence on codegen-DECISION caps only, never invalid SPIR-V ([#11631 severity](../learnings/1781686744418-slang-11631-severity-require-drop-is-a-silent-runt.md)). The bindless half: `specializeTargetSwitch` selects the bindless-vs-descriptor-heap accessor from *global* `getTargetCaps()` at module-link scope. The `implies(spvBindlessTextureNV)` gates in spirv-legalize/emit are downstream consumers ([bindless path is selected at specializeTargetSwitch](../learnings/1784780629812-slang-bindless-descriptor-heap-path-is-selected-at.md)). `[require]` lowers to an `IRRequireCapabilityAtomDecoration` that is never unioned into target caps. A version-scan-style emit fix would produce incoherent `uint64`-typed/`uint2`-accessed SPIR-V, so the fix is per-entry-point reachability specialization (#12196) ([entry-point [require] never reaches specializeTargetSwitch](../learnings/1784782055293-slang-12196-entry-point-require-never-reaches-spec.md)).

**Where a resource-`[require]` capability diagnostic actually fires (cross-target, from the #12274 follow-up):** E36107 fires only on **entry-point-reachable** typed resources, NOT on unreferenced globals — a declared-but-unused `Buffer<uint>` global passes on an excluded target, while an entry point *taking* a `Buffer<uint>` param fails; and because the check runs over ALL `[shader]` entry points at module load, one illegal EP sinks its clean siblings' `load_program` (trust the CI failure log over DeepWiki's design-doc reading of what trips the diagnostic) ([E36107 is entry-point-scoped, not all-declarations](../learnings/1785453629709-slang-e36107-capability-check-entry-point-scoped-n.md)). The enforcement layer is counterintuitive: the method-level `[require]` on an intrinsic (e.g. `_Texture.Load`) is **inert** when that method's body is a case-less `__target_switch` — a switch with no case for the active target infers an empty body → empty inferred capability set → trivially passes. The effective gate is the **TYPE-level `[require]` on the resource's shape struct** (for `Buffer<T>` = `_Texture<T,__ShapeBuffer,...>`, the `[require]` on `struct __ShapeBuffer`), so the Approach-A diagnose fix drops the incapable target from the TYPE's require list (mirroring WGSL PR #6585), NOT the method's — with the caveat not to drop a target that has a real prelude type (`cpp`'s gap is a missing `case cpp:`, implement-territory, not incapability) ([case-less `__target_switch`: the enforcing require-clause is on the TYPE, not the method](../learnings/1785418069559-case-less-target-switch-the-enforcing-require-is-o.md)).

**Verify a capability predicate at HEAD (HitObject SM6.9+NVAPI, #11903).** The triage claimed PR #11889's `implies(hlsl_nvapi)` guard is inert on sm_6_9; an instrumented, rebuilt slangc showed `implies(nvapi)=1`, so the fix was a no-op. Revert-drill the predicate, print the actual value, and don't repeat a triage's sub-claims ([verify a triage premise at HEAD](../learnings/1782991917563-verify-a-triage-s-predicate-premise-at-head-revert.md)). The wrong read came from a prebuilt pre-#11889 binary. Rebuild after any source refresh; don't trust `slangc -v` on incremental builds. The real bug is an ABI gap: the native-only 2-arg `HitObject::Invoke` binds `dx::HitObject::Invoke(NvHitObject)`, while NVAPI's Invoke takes 3 args ([CORRECTION: real bug is 2-arg Invoke ABI gap](../learnings/1782992753685-correction-slang-hitobject-sm6-9-nvapi-refutes-my-.md)).
