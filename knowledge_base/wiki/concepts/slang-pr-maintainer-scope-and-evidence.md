# Slang Maintainer Scope-vs-Design Approval, Evidence Discipline, and Draft-PR Footprint

## TL;DR

**Issue footprint and closing keywords**
- `Closes #N` / `Fixes #N` does NOT excuse a human-visible issue comment while the PR is a DRAFT — a draft neither auto-closes the issue nor surfaces the link.
- A discharged blocker line is actively wrong — refresh a published footprint on every state change; PATCH your own last comment in place (create-only token → ask the owning tier; never stack a duplicate).
- Audit a PR body for auto-close keywords UNANCHORED + case-insensitive, both reference forms, against the LIVE body — close/fix/resolve (+s/d) adjacent to `#N`; backticks and a trailing `'s` do NOT exempt a match. A check that cannot fail is not a check.
- Verify a replacement PR's closing reference resolves to an issue — a one-digit-off `Fixes #N` pointing at a PR links nothing.

**Maintainer decisions and policies**
- A maintainer's "create a PR" is SCOPE approval, not DESIGN approval — clean reviews don't change landing probability; keep the branch cheap, expect re-implementation.
- A correct fix can still be closed for scope — split a fix that cascades across subsystems into stacked PRs before the review spend; a breaking language change is gated by the maintainer's semantics review.
- CMake flag-override asks are usually an INITIALIZATION-layer problem (`*_FLAGS_<CONFIG>_INIT`, no FORCE), not a flag-ordering one — the general mechanism beats a per-flag "detect and skip."
- A by-design ruling can reverse on VERIFIED counter-evidence — record the RE-OPEN trigger when parking, verify at HEAD before relaying, surface back to the ruling maintainer with options, keep merge maintainer-gated.
- A wrong-code bug root-caused to a downstream compiler (NVRTC/NVCC, a driver) gets no Slang-side workaround — recommend an upstream bug report plus a user-side workaround.
- A perf/planning sub-task assigned to a core-team MEMBER usually self-serves — offer once to the parent, then hold; no GitHub post.
- The triage step-9 go/no-go gates the fixer/draft PR, not the triage comment — a maintainer-deferring triage comment stays up after a NO-GO.

**Evidence discipline**
- An empty read is ambiguous between "nothing" and "broken" — run a control query that MUST return data before reporting all-clear. `slang-mcp github_list_issues`/`github_get_discussions` false-empty; Discord forum parents read `[]` (use the guild active-threads API); `merged_at` is the broken field, not `is:merged`.
- `running` + fresh `last_active` is NOT evidence a session did anything — count its outbound rows; `out==0 && in>=1` is an unconditional awaiting_us.
- A reporter's suggested fix is a claim to test, not adopt; before advising "upgrade," verify a release containing the fix exists (`/releases/latest` vs the merge date — "build master" may be the only actionable advice).
- A "trivial" submodule pin bump is rarely trivial — state its true scope via REST compare and a clean local build; diff-only bots can't see inside `external/**`.

**Fixer PR mechanics**
- Cross-fork PRs into shader-slang/slang fail (`fork_collab`); push the branch to upstream and open a same-repo draft PR.
- No `Co-Authored-By: Claude` trailer on shader-slang repos — the project rule overrides the harness reminder; removing it after a push needs an authorized force-push (in a worktree, lease against FETCH_HEAD).

This page covers the *issue-facing* side of the Slang workflow. Companion to [[wiki/concepts/slang-misc-pr-process-and-maintainer-workflow.md]] (PR/review mechanics).

## `Closes #N` Does Not Excuse an Issue Footprint While the PR Is a Draft

A PR body's `Closes #N` / `Fixes #N` does not remove the need for a human-visible 5-bullet comment on the originating issue while that PR is a DRAFT: a draft neither auto-closes the issue nor surfaces its closing link prominently, so a human landing on the issue sees nothing — the silent-chain failure the draft-footprint rule prevents. "The PR is now the public artifact" only holds after the ready-flip; on slang-rhi#805 → draft #806, calling the footprint "moot given `Closes #805`" after a maintainer approved the draft was wrong and was corrected by the triage tier. **A discharged blocker line is actively wrong, not merely stale:** a footprint still saying "awaiting maintainer confirmation of the intended wording" after approval misinforms every later reader, so refresh it on each state change. If your bot was the last commenter, PATCH the existing comment (`repos/<owner>/<repo>/issues/comments/<id>`) instead of stacking a new one. Some bot tokens are **create-only** on issue comments (PATCH/DELETE 403); then do not self-post a second comment (the duplicate would be permanent) — ask the tier that owns the surface (usually triage, as last commenter) to update theirs ([Closes #N does not excuse an issue footprint while the PR is a draft](../learnings/1785751816891-closes-n-does-not-excuse-an-issue-footprint-while-.md)).

## Auditing Closing Keywords — Your Own PR Body and a Replacement PR's

**An anchored grep gives a false pass.** When a PR must *not* auto-close an issue (the functional fix landed in a sibling PR; the disposition is the maintainer's call), every closing keyword has to go. `grep -cE "^Closes #12110"` reported "0 `Closes` lines" while the live body still carried `…which fixes #12110's symptom…` (a trailing `'s` still matches, and it isn't at line start) and `Please resolve #12110 against #12263` (`resolve` is a keyword too). A heading written as ``**On `Closes #12110`.**`` also arms it — **backticks exempt nothing**. The keyword set is `close`/`closes`/`closed`, `fix`/`fixes`/`fixed`, `resolve`/`resolves`/`resolved`, each adjacent to `#N`, `owner/repo#N`, or a full issue URL, optionally colon-separated. Audit unanchored, case-insensitive, both reference forms, against the **live** body (`gh api repos/<owner>/<repo>/pulls/<n> --jq '.body'` — a local draft can be stale, or a `PATCH` can land differently than intended):

```bash
grep -n -i -E "\b(close[sd]?|fix(e[sd])?|resolve[sd]?)\b[[:space:]]*:?[[:space:]]*#[0-9]+" body.md
grep -n -i -E "\b(close[sd]?|fix(e[sd])?|resolve[sd]?)\b[[:space:]]*:?[[:space:]]*[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+#[0-9]+" body.md
```

Rephrase rather than delete the meaning ("addressing the symptom of #N", "the disposition of #N is yours to make explicitly", "Refs #N"). One surviving trigger auto-closes the issue on merge and silently overrides an explicit "please decide this yourself" ask — invisible until after merge. Same class as a vacuous FileCheck `CHECK-NOT`: **a verification that cannot fail is not a verification** — for an absence check, use the broadest pattern that could match, read the authoritative source, and confirm the check can fail on a known-positive input ([auditing a PR body for auto-close keywords: anchored grep gives a false pass](../learnings/1785756201206-auditing-a-pr-body-for-auto-close-keywords-anchore.md)).

The mirror-image check applies to **someone else's** PR: when a maintainer's replacement PR claims to fix your issue, verify the closing reference resolves. #12324's body said `Fixes #12233` — one digit off, and #12233 is an unrelated closed **PR**; closing keywords only auto-close *issues*, so it linked nothing and #12223 would have stayed open after the merge (the #12223 timeline had no `connected` event, only our own cross-reference). Flag it as a heads-up; never edit their PR ([a maintainer's "create a PR" is not acceptance of your shape](../learnings/1785767481211-a-maintainer-s-create-a-pr-is-not-acceptance-of-yo.md)).

## A Maintainer's "Create a PR" Is Scope Approval, Not Design Approval

**A go-ahead answers "should this be fixed, and roughly in which direction" — not "is your implementation the one that lands."** On slang#12223 (`-Og` in Debug builds broke debugging, a regression from #12140) we offered two options and skiminki-nv — the regressing PR's author — replied *"@nv-slang-bot Create a PR for Option 2"*. Draft #12234 implemented it exactly and passed three clean reviewer passes; a week later he **closed it unmerged** (*"It doesn't quite seem to be the right fix. PR #12324 is the next attempt"*) and fixed it at a deeper layer. Clean reviews do not change landing probability. When closed in favor of theirs, don't re-litigate — verify their replacement closes the issue, hand over what they'd want (edge cases, test matrix), reap your branch/worktree, close the chain ([a maintainer's "create a PR" is not acceptance of your shape](../learnings/1785767481211-a-maintainer-s-create-a-pr-is-not-acceptance-of-yo.md)).

**Direction adopted, shape rejected — and the shape lesson transfers** ([#12223 -Og debuggability: maintainer took the DIRECTION, rejected our SHAPE](../learnings/1785767658697-12223-og-debuggability-maintainer-took-the-directi.md)). Ours: `-Og` is a *target-level* option (`cmake/CompilerFlags.cmake:196`, `target_compile_options(… $<$<CONFIG:Debug>:-Og>)`) that lands after `CMAKE_CXX_FLAGS` (env `CXXFLAGS`) and `CMAKE_CXX_FLAGS_DEBUG`, so by last-`-O`-wins it clobbers a user's `-O0`; we skipped it when the user passed an `-O` token — ~3 lines that **suppress a symptom of the ordering**. His #12324 seeds `CMAKE_C/CXX_FLAGS_DEBUG_INIT` **before `enable_language()`**; `cmake_initialize_per_config_variable` sets the cache vars *without* `FORCE`, so any user/preset/toolchain value replaces the default and `CXXFLAGS`/`CFLAGS` are honored generally, with no appended flag left to suppress. **CMake flag-override asks are usually an initialization-layer problem, not an ordering problem:** if you are writing "detect what the user passed and skip our flag," make the flag a *default* (`*_FLAGS_<CONFIG>_INIT`, no `FORCE`). Facts: compile-line order is `CMAKE_CXX_FLAGS` → `CMAKE_CXX_FLAGS_<CONFIG>` → target `COMPILE_OPTIONS`, so env `CXXFLAGS` can **never** win a last-wins fight (Ninja Multi-Config/cmake 3.25/GCC 12: `CXXFLAGS='-O0 -g3'` + target `-Og` ⇒ `-O0 -g3 -g -Og`); `CMAKE_CXX_FLAGS_DEBUG` is just `-g`, **not** `-O0 -g` — an in-tree comment claiming otherwise (`CompilerFlags.cmake:180`) propagated into two memos before a probe caught it, so read the cache, not the comment. Process points that worked: **name the chosen layer and the rejected alternatives** in the PR description (invites the "wrong layer" objection during review, not after); and reproducing the compile line to show an override satisfies **both** opposed core members (the reporter wanted `-O0`; #12140's author called `-O0`-by-default a showstopper) turned "whose default wins" into "make it overridable" — which is when the maintainer asked for a PR. For build-system fixes, ask whether the bug is in the *value* or in *how it gets initialized*.

**A correct fix can also be closed for scope — which argues for stacked PRs before the review spend.** slang#12492 (fix for #12487/#9636) was peer-approved (APPROVE_WITH_NITS) and codex-approved, yet jvepsalainen-nv **closed it unmerged** and split it into #13151 (address-space fixpoint worklist reset, ready), #13152 (lower `ref` accessor returns as addresses, draft) and #13153 (unannotated `ref` implicit-mutation via one receiver-mode classification, draft on #13152): it "reached its cost ceiling and grew beyond a reviewable, principled scope" — not a correctness rejection. A root-cause fix that **cascades across subsystems** (here `visitReturnStmt` lowering, `this` passing-mode, the address-space fixpoint, type-inlining legalization, accessor mutability at 4 sites, a provenance diagnostic, regenerated target tests) should be **split up front** — the independent piece ships alone, the language-behavior change gets its own review, the lowering design stays draft; otherwise maintainers split it after the review spend is sunk. Also: prefer **targeted legalization over blanket pre-specialization inlining** for pointer-returning helpers on pointer-less targets (blanket was called "unsafe"); a diagnostic needing a parallel recursive type/AST walker is a smell; and peer + codex approval does not gate a breaking language change — the maintainer's semantics review does ([a correct Slang fix can still be closed for scope — split cascading fixes into stacked PRs early](../learnings/1789638837057-a-correct-slang-fix-can-still-be-closed-for-scope-.md)).

## Empty Reads and Fresh Timestamps Are Not Evidence of Silence

**An MCP read tool returning empty is ambiguous between "genuinely nothing" and "tool is broken" — before believing an all-clear, verify the tool is alive with a control query that MUST return data** (e.g. widen the window to 30 days). `slang-mcp`'s `github_list_issues` returns `total_count: 0` **unconditionally** (all three repos, with and without `since`), and `github_get_discussions` returns zero discussions **and** zero categories for `shader-slang/slang` while Discussions are active. Both fail silently: the day this was found, a daily sweep on `github_list_issues` hid **4 new slang issues** (one an SS-class silent-wrong-value bug) plus 10 untriaged ones. Use `github_search_issues` with an explicit query (`repo:shader-slang/slang is:issue is:open created:>=2026-08-01`), or a web fetch of `/discussions`. **A prior "`is:merged` is broken" conclusion was wrong and must not be carried forward:** `type:pr is:merged closed:>=2026-07-31` returned 12, `is:unmerged` 1, plain `closed:` 13 — exact complements. What misleads is that **`merged_at` is `null` on every search result, including merged PRs**: read merge state from `is:merged`/`is:unmerged` (or the `Fixes #N` auto-close), never `merged_at`, and for one PR spot-check that a file it added exists on the default branch. Discord support reads empty for days while sibling channels read fine are the same shape — a read-scope gap, not silence ([slang-mcp `github_list_issues` and `github_get_discussions` return FALSE EMPTIES; `merged_at` is the broken field, not `is:merged`](../learnings/1785744880116-slang-mcp-github-list-issues-and-github-get-discus.md)).

**The Discord half, re-confirmed on the 2026-09-24 maintainer daily report.** `#slang-support`/`#slangpy-support` are Discord **forum** channels, so `discord_read_messages` on the *parent* returns `[]` at HTTP 200 — indistinguishable from "quiet." Read the guild active-threads API — `GET https://discord.com/api/v10/guilds/1303735196696445038/threads/active` with the bot token at `/workspace/agent/memory/.discord-token` — then each thread id as a channel; that surfaced ~10 live human `#slang-support` threads recent reports had logged as "empty." Cross-check the thread count and control-read a populated text channel to prove the token is live. The same report saw `github_list_issues(state=OPEN)` false-empty on `slang-rhi` (0 vs 32 from a control `github_search_issues`), and the GitHub Actions default / `?status=failure` REST slice serving a months-old page — use `?event=schedule` or `/actions/workflows/<id>/runs` for real nightly / Issue-Onboard conclusions ([daily-report forum sweeps must use the guild active-threads API; `github_list_issues` can false-empty](../learnings/1790238085692-slang-daily-report-forum-sweeps-must-use-the-guild.md)).

**The chain-level form: a maintainer's triage request can sit unanswered for weeks behind a container that looks healthy.** On slang #8306 and #8785, `jkwak-work` pinged `@nv-slang-bot` for triage on 2026-07-18; both webhooks routed and a triager session was created for each, yet **17 days later** neither had a bot comment and each owning session held **one inbound, zero outbound** (confirmed via `ncl sessions messages --limit 200` and the GitHub reader). Every guard missed it: `container_status` was **`running`** (up, but never produced a turn); `last_active` was **fresh** because it advances on *host-side* touches; and with no PR or disposition the chains were invisible to PR- or state-shaped filters. **`running` + recent `last_active` is not evidence a session has done anything — count its outbound rows.** `out == 0 && in >= 1` on the owning session is an unconditional `awaiting_us`, independent of container status, `last_active` and the stale window — a *stronger* stuck signal than any silence threshold, since there is no prior output to measure silence against (special-case it; never feed a zero denominator to a ratio). Generally: **a health timestamp maintained by someone other than the worker measures the maintainer, not the work** — prefer a count of artifacts the worker itself produced ([a maintainer triage request can sit unanswered for weeks behind a running container with zero outbound](../learnings/1785802554126-a-maintainer-triage-request-can-sit-unanswered-for.md)).

## Maintainer Rulings and Standing Policies

**Verified counter-evidence can reverse a by-design ruling.** On slang#12226 (bindless `ConstantBuffer<T>` emitted StorageBuffer instead of Uniform), jkwak-work ruled it by-design citing an #11483 constraint; the reporter rebutted with a glslang `GL_EXT_descriptor_heap` shader (a Uniform heap buffer indexing a nested array, accepted by spirv-val); our fixer confirmed the mechanism; we surfaced it back; the maintainer **retracted ("I got it wrong on #11483"), prototyped the fix, and self-merged #12256**. Rules: (1) record the RE-OPEN trigger when you first park ("fresh substantive input → RE-OPEN") so a "looks done" chain is not no-op'd; (2) **verify the counter-evidence yourself at HEAD before relaying it** — an unverified refutation relayed as fact costs credibility; (3) neither silently accept NOR unilaterally overturn — surface it to the ruling maintainer, @-mentioned, as their decision to revise, with options (full fix / narrow interim / hold); (4) carry hedges honestly (a DeepWiki "storage classes must match" claim was flagged as hypothesis, then verified false against the spec; an earlier public "infeasible" statement was corrected in place). The bot opens the PR draft-only and ready+merge stays maintainer-gated — a maintainer self-merge satisfies that; "please make a PR" authorizes creation, not auto-merge ([surfacing verified counter-evidence to a maintainer can reverse a by-design ruling — don't silently accept OR unilaterally overturn](../learnings/1785278991541-surfacing-verified-counter-evidence-to-a-maintaine.md)).

**No Slang-side workaround for a wrong-code bug root-caused to a DOWNSTREAM compiler** (NVRTC/NVCC, a driver's shader compiler). On #12916, a CUDA wrong-code bug the reporter correctly attributed to the NVRTC/NVCC 13.3 device optimizer (Slang's emitted code semantically faithful), maintainer kaizhangNV declined even a clean, precedented WAR — "We shouldn't emit this WAR code in Slang… file a cuda compiler bug… the only WAR is to add this WAR code in the user code base" — and closed it as completed. Triage prior: recommend the two-track resolution — (a) a bug filed with the downstream compiler team, (b) a user-side source workaround as interim mitigation — rather than dispatching a fixer to build a compiler-side WAR. Sibling to the policy that Slang release packages exclude downstream compiler binaries: Slang avoids owning downstream tools' behavior ([Slang maintainer policy: no compiler-side workarounds for downstream compiler bugs](../learnings/1789500967936-slang-maintainer-policy-no-compiler-side-workaroun.md)).

**A benchview/perf-epic planning sub-task assigned to a core-team MEMBER usually self-serves — surface a value-add offer once to the parent, then HOLD.** On slang#12962 ("Document CUDA backend optimization opportunities", epic #12941), triage closed it as a non-actionable core-team planning deliverable (GitHub post suppressed) and offered a source-inspection CUDA-codegen survey; six days later the assignee (a MEMBER with the hardware) posted the completed deliverable — hardware-measured root causes, fix PRs #13012/#13013 (25x), seven sub-issues — strictly better than any source survey. Name the offer once, don't push it; if the owner delivers, withdraw it as moot and re-close with a positive [Resolution] — still no GitHub post (a bot note on the assignee's own analysis is noise) ([Perf-infra sub-task assignees often self-serve the deliverable — hold the survey offer](../learnings/1789378728615-perf-infra-sub-task-assignees-often-self-serve-the.md)).

**The triage step-9 go/no-go gates the fixer/draft-PR release, NOT the triage comment — they are separate artifacts.** Recurring crossover (#13058, #874, #13140): the step-9 comment is posted in normal flow, then a NO-GO/defer or "don't post — noise" directive arrives and reads as if the comment shouldn't exist. Operator-confirmed: a triage comment that DEFERS the fix decision to the maintainer ("assignee-owned vs bot draft PR — your call"), with no `@`-mention and the bot disclaimer, is right to post — even on an unsolicited `issue_opened` chain. Deleting an already-notified, substantive file:line comment reads worse than leaving it (deletion is a hard-to-reverse outward action). Hold the fixer; suppress the comment up front only under a standing operator "no post on unsolicited issue_opened" order ([Step-9 triage comment vs go/no-go: the decision gates the fixer/PR, not a deferring triage note](../learnings/1789599918617-step-9-triage-comment-vs-go-no-go-the-decision-gat.md)).

## Reporter Fixes, Upgrade Advice and Pin Bumps: Verify the Claim Before Relaying It

**A reporter's suggested fix is a claim to test, not adopt** — even from a repo MEMBER who root-caused correctly and "said it worked locally." slang#12440's `getStringHash`-on-a-non-literal SIGSEGV came with a named two-site fix (swap the unchecked `getStringLit()` C-cast for `as<IRStringLit>(getOperand(0))`), but building it is what reveals whether the two-line change rejects code that compiles correctly today; verify the patch against the repro and the surrounding surface before endorsing it ([A reporter's suggested fix is a claim to test, not adopt: build it — slang #12440's two-line fix rejected code that compiled correctly](../learnings/1786308399056-a-reporter-s-suggested-fix-is-a-claim-to-test-not-.md)). **Before advising "upgrade," verify a release containing the fix exists:** on a missing-SPIR-V-`NonUniform` miscompile the fix had merged, so "upgrade or build master" was advised, but the latest release (`v2026.14.1`, 2026-07-30) predated the merge, so only "build master" was actionable — check `/releases/latest` (and `/releases?per_page=5`) against the fix's merge date ([Before advising an upgrade, verify a release containing the fix exists](../learnings/1786312909042-before-advising-an-upgrade-verify-a-release-contai.md)).

**A "trivial" pin bump of a vendored submodule is rarely trivial.** slang#13105 (bump `external/slang-rhi` d6d31411→079b75b54c, delete a `cooperative-matrix-*` accept-with-warning WAR in `tools/render-test/options.cpp`) was described as "add 5 feature names" but was 6 commits / ~90 files, including public `include/slang-rhi.h` (+209/−24), a constant-buffer-pool → transient-buffer-heap rework, and opacity-micromap + push-constant features. Diff-only reviewers (nv-slang-bot / Reviewer A, CodeRabbit) cannot see inside `external/**`: state the true scope with `gh api repos/<owner>/<repo>/compare/<old>...<new> --jq '{ahead_by,files:[.files[].filename]}'` and prove compatibility with a clean local build of slangc + slang-test + render-test. The new pin FIXES the slang#12735 granularity trap — the old one checked one coarse `cooperativeMatrixWorkgroupScope` bit and pushed one coarse `Feature::CooperativeMatrix2` (a device missing a sub-bit RAN instead of SKIPPED); the new one detects each of 5 sub-features via its own Vulkan bit + SPIR-V capability. Removing the WAR is safe because `-render-feature` (singular) is a two-stage gate — unknown name → hard `SLANG_FAIL` at parse (allow-list = `SLANG_RHI_FEATURES` in the pinned header), recognized-but-unsupported → `SLANG_E_NOT_AVAILABLE` → test ignored — and the only cooperative-matrix tokens repo-wide are the 5 allow-listed names (no bare `cooperative-matrix-2`) ([079b75b54c fixes the cooperative-matrix-2 name-granularity trap; a "trivial pin bump" is rarely trivial — expand it via REST compare](../learnings/1789505298973-slang-rhi-079b75b54c-fixes-the-cooperative-matrix-.md)).

## Fixer-Bot PR Mechanics: Cross-Fork Is Blocked, Direct Upstream Push Works; No `Co-Authored-By`

In the slang-fixer prod env the git remote may be `coworkers = slang-coworkers/slang` (a fork, placeholder-token URL), and a **cross-fork** PR into shader-slang/slang is REJECTED with `fork_collab: Fork collab can't be granted by someone without permission` — via BOTH `gh pr create` (GraphQL) AND REST `gh api -X POST repos/shader-slang/slang/pulls -f head=slang-coworkers:...` (the `nv-slang-bot` App identity can't grant fork-collab and no user PAT is provisioned). The bot has **direct push rights to shader-slang/slang**, so push the branch straight to upstream and open a **same-repo** PR, matching the CLAUDE.md prod specifics (origin = shader-slang) even when the checked-out remote is the fork:

```
git push https://github.com/shader-slang/slang.git fix/issue-<n>:fix/issue-<n>
gh pr create --repo shader-slang/slang --base master --head fix/issue-<n> --draft --title ... --body-file ...
```

`clang-format` is not on PATH under that name; `/usr/bin/clang-format-17` (v17.0.6, the required version) is — symlink it into a temp dir on PATH before `./extras/formatting.sh --cpp` ([draft PR: cross-fork blocked, direct upstream push works](../learnings/1790099756100-slang-draft-pr-cross-fork-blocked-but-direct-upstr.md)).

Slang commits must **NOT** carry the `Co-Authored-By: Claude <noreply@anthropic.com>` trailer the harness system-reminder asks for. The Slang project instructions ("Don't mention Claude on the commit message"; coworker CLAUDE.md: no AI-tool attribution in commits or PR bodies — upstream policy) forbid it, and the reminder defers to project instructions. Omit it from every commit into shader-slang/slang, slangpy or slang-rhi (slangpy-reviewer flagged it on slangpy PR #1206). Removing it after a push needs a reword plus a force-push, which needs explicit session authorization even on your own `fix/issue-*` branch; without it, leave a squash-merge note asking the merger to drop the trailer ([coworker commits on shader-slang repos must not carry the Co-Authored-By trailer](../learnings/1791195802831-coworker-commits-on-shader-slang-repos-must-not-ca.md)). When an authorized rewrite runs in a worktree, a bare `--force-with-lease` can fail with "stale info" because the worktree has no `origin/<branch>` remote-tracking ref; `git fetch origin <branch>` and lease explicitly against `$(git rev-parse FETCH_HEAD)` ([same stale-info lease rejection in a worktree; lease explicitly against FETCH_HEAD](../learnings/1789460745636-git-force-with-lease-stale-info-inside-a-worktree-.md)). The trailer-check and repair recipes live on [Fixer PR Creation, Fork & CI Mechanics](agent-fixer-pr-and-ci-mechanics.md).
