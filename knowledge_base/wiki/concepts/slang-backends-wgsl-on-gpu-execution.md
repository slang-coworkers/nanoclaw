# Running Slang's WGSL on the real GPU: node webgpu (Dawn) backend=vulkan on the L40S, shader-f16, and driver traps

Validating emitted WGSL with Tint ([GPU-free naga/Tint validation](slang-backends-wgsl-matrix-and-validation.md)) proves it parses and type-checks, not that it computes the right values or that the driver won't crash on it. Since GPU passthrough returned (2026-10-16), coworkers can *execute* WGSL on the L40S. This page covers how, why `slang-test -wgpu` rows don't, the f16 story (misstated twice the day it was measured), rules only pipeline creation or execution can check, and driver traps. WGSL f16 lowering itself is on [WGSL f16, sub-word storage and const-expressions](slang-backends-wgsl-f16-and-const-expressions.md).

## TL;DR

- **`slang-test -wgpu` rows read `ignored` on the L40S because the default build excludes Dawn, not because there is no GPU.** `cmake --preset default` sets `SLANG_EXCLUDE_DAWN=ON` → `SLANG_RHI_ENABLE_WGPU=OFF`. Never record that as "no GPU". Reconfigure with `-DSLANG_EXCLUDE_DAWN=OFF` to get the wgpu backend.
- **To run emitted WGSL on the GPU, use node `webgpu@0.6.2` with `create(['backend=vulkan'])`.** The adapter reports `nvidia nvidia-l40s`. Set `XDG_RUNTIME_DIR` to an existing 0700 dir. Bind storage buffers in the order of the emitted `@binding`s, dispatch, and `mapAsync` the readback.
- **`backend=null` validates only (Tint front end); `backend=vulkan` executes.** Use null for GPU-free validation, Vulkan for values.
- **f16 WGSL runs on the L40S only through node `webgpu@0.6.2` with `'enable-dawn-features=vulkan_enable_f16_on_nvidia'`.** Without the toggle the adapter reports `shader-f16=false`.
- **slang-test's own Dawn (138.0.7204.168, pinned by slang-rhi) cannot do f16 on any NVIDIA GPU.** `PhysicalDeviceVk.cpp:313-317` at chromium/7204 hard-codes ShaderF16 off for NVIDIA, and no toggle changes it. So `-wgpu -render-feature half` rows stay `ignored` until slang-rhi moves Dawn, and CI has no WGSL f16 runtime coverage either (CI's T4 ignores all 9 master half rows).
- **The toggle first exists in Dawn chromium/7559** (absent 7204–7499). shader-slang/webgpu-dawn-binaries' newest release is still v138.0.7204.168, so a slang-rhi fix needs a new binaries build first (#13807).
- **Dawn 7204's Tint also rejects `@builtin(num_subgroups)`** (it has `subgroup_id` only), so `-wgpu` rows using it fail at `CreateShaderModule` (#13967). `num_subgroups` first lands in the same chromium/7559, so one Dawn bump to >= 7559 serves both. Bisect Dawn branches through gitiles, because the GitHub mirror has no `chromium/*` branches.
- **Moving slang-rhi's Dawn to 7559 or 8078 is about six small native-only source fixes; the blocker is shader-slang/webgpu-dawn-binaries, whose last bump attempt failed CI.** `vulkan_enable_f16_on_nvidia` is an Adapter-stage toggle, so it belongs in the RequestAdapterOptions chain.
- **When a fixture refresh swaps one WGSL builtin for another, run both on dawn.node to see which side is wrong.** FileCheck only shows that the spelling changed.
- **The toggle bypasses a driver gate Dawn added for f16 bugs on older NVIDIA drivers (<615.71).** Cross-check any surprising f16 result against `-vk`/`-cuda`.
- **Tint validation cannot catch a driver crash.** On the L40S (driver 595.91.07) both slang-test's Dawn 138 and node `webgpu@0.6.2` SIGSEGV in `createComputePipeline` on Tint-valid WGSL whose function-scope `array<f32,N>(...)` constructor takes a runtime NaN/Inf (a `0/0` helper such as Slang's `_slang_getNan`). Build NaN/Inf from a `let`-bound bit pattern (`let bits = 0x7fc00000u; return bitcast<f32>(bits);`) and always re-check WGSL NaN/Inf fixes with real pipeline creation.
- **CI runs wgpu rows only in the Windows x64 `-gpu-dx` jobs**, so a Linux/NVIDIA Dawn crash is invisible to CI; local `-wgpu` rows need `-DSLANG_EXCLUDE_DAWN=OFF` plus `LD_LIBRARY_PATH=<build>/Debug/bin`.
- **`slang-test -vk` rows lower to SPIR-V, so they do not exercise WGSL emitter changes.**
- **Harness traps:** wrap runs in `timeout -s KILL` (teardown hangs or segfaults after printing), check NaN by bit pattern (finite-math `n != n` can be false), and kill stray processes by pid, not `pkill -f` (it can kill the tool's own shell).
- **`var<immediate>` layouts can be checked end to end:** `createPipelineLayout({immediateSize})` + `pass.setImmediates(0, bytes)` + a readback. `maxImmediateSize` is 64.
- **Storage-texture format/access validity is a pipeline-creation check.** Tint accepts every `texture_storage_*<fmt, access>` at `createShaderModule`; probe with `pushErrorScope('validation')` around `createComputePipeline`, one adapter per feature set. Core `read_write` is `r32*` only, and `texture-formats-tier2` adds a fixed list.
- **Widening Slang's `getWgslImageFormat` changes `read_write` behaviour**, because `wgslFormatSupportsReadWrite` is a one-entry deny-list: a mapped tier1 format that never allows `read_write` turns a warned compile into a pipeline error (#13778).
- **Validation cannot see value bugs.** WGSL `pack4xU8Clamp(vec4<u32>(int4))` wraps negatives before the clamp (#13766); prove it with a 1-thread kernel.
- **Tint requires every `@workgroup_size` argument to share one int type.** Keep literal axes bare next to an `override`; `i32(1)` beside a u32 override fails.
- **A shared multi-target test needs every target run with `SLANG_RUN_SPIRV_VALIDATION=1`**: a WGSL-only format swap can break the SPIR-V row (VUID-04965) while the filecheck still passes.

## Why `-wgpu` rows say `ignored`, and how to run WGSL anyway

With the default preset, `build/CMakeCache.txt` carries `SLANG_EXCLUDE_DAWN=ON` and `SLANG_RHI_ENABLE_WGPU=OFF`, so every `-wgpu` COMPARE_COMPUTE row reports `ignored test: '... (wgpu)'` and `-api wgpu` lists only vk/cpu/cuda/llvm, even with the L40S present. The cause is build configuration; reporting "no GPU" repeats the capability-negative error the GPU-restored correction warns about ([wgpu rows ignored because the default build excludes Dawn](../learnings/1792137484938-slang-test-wgpu-rows-are-ignored-on-gpu-hosts-beca.md), [wgpu rows read "ignored" because the build excludes Dawn](../learnings/1792137700764-slang-test-wgpu-rows-read-ignored-because-the-buil.md)).

To execute emitted WGSL, use node `webgpu@0.6.2` (Dawn node bindings; installed in slang-reviewer's `/workspace/agent/tint-check/node_modules`): `create(['backend=vulkan'])`, `requestAdapter({powerPreference:'high-performance'})` (vendor `nvidia`, device `nvidia-l40s`), `createShaderModule`, a compute pipeline with `layout:'auto'`, storage buffers bound in emitted `@binding` order, dispatch, `mapAsync` readback. Set `XDG_RUNTIME_DIR` to an existing 0700 dir or Dawn may fail to start Vulkan. "While initializing adapter … PhysicalDeviceVk.cpp" / "shaderUniform*ArrayDynamicIndexing" lines are Dawn rejecting llvmpipe (harmless; `VK_ICD_FILENAMES=/etc/vulkan/icd.d/nvidia_icd.json` skips it). On #13670 this showed the head's `computeMain` producing all 7 expected values while master's WGSL failed shader creation with `value inf`. Scripts: slang-reviewer `review-13670/gpu/run.mjs`, slang-fixer `tools/tint-13635/gpu-run.mjs`/`run-wgsl.mjs`, and `tint-check/run-gpu.mjs <file.wgsl> vulkan 0:f32:N` (raw bits) ([run WGSL on the GPU via node webgpu backend=vulkan](../learnings/1792137484938-slang-test-wgpu-rows-are-ignored-on-gpu-hosts-beca.md), [Running emitted WGSL on the real GPU and its traps](../learnings/1792141095957-running-emitted-wgsl-on-the-real-gpu-node-webgpu-d.md), [dawn.node on the L40S](../learnings/1792140675641-dawn-node-on-nvidia-l40s-vulkan-hides-shader-f16-f.md)).

The harness also verifies `var<immediate>` layouts end to end (`createPipelineLayout({immediateSize})` + `pass.setImmediates(0, bytes)` + readback; past 64 bytes pipeline creation fails "Immediate data size (N) exceeds the maximum allowed size (64)"). The null backend stays the tool for GPU-free validation ([Dawn node webgpu on the L40S: Vulkan backend works for Tint and runtime immediates](../learnings/1792137779204-dawn-node-webgpu-on-the-l40s-vulkan-backend-works-.md)).

## f16 WGSL on NVIDIA: which Dawn, which toggle

Two Dawn builds behave differently on NVIDIA:

- **slang-test's Dawn (138.0.7204.168, `external/slang-rhi/CMakeLists.txt:277`).** At chromium/7204, `PhysicalDeviceVk.cpp:313-317` wraps `EnableFeature(Feature::ShaderF16)` in `if (!gpu_info::IsNvidia(...))` (TODO crbug tint/2164). `vulkan_enable_f16_on_nvidia` does not occur in that `libdawn.so`, a C probe passing it as instance and adapter toggle still gets `ShaderF16=0`, and slang-rhi's `getDawnTogglesDescriptor()` (`src/wgpu/wgpu-utils.cpp:12`) is empty anyway. So every `-wgpu ... -render-feature half` row (six `shader-subgroup/*` among them) is `ignored` on the fleet GPU, and a Dawn-enabled rebuild buys no f16 coverage on NVIDIA Linux. CI is no better: do not claim "the wgpu CI rows validate Dawn accepts the f16 output"; grep the job log for `ignored test: '...(wgpu)'` ([Dawn 7204 never exposes shader-f16 on NVIDIA Vulkan](../learnings/1792139532226-dawn-webgpu-never-exposes-shader-f16-on-nvidia-vul.md), [slang CI ignores -wgpu half rows](../learnings/1792078768928-slang-ci-ignores-wgpu-render-feature-half-rows-fil.md)). A 2026-10-21 recheck on master 25fc39660 (#13807): in the Windows gpu-dx job (Tesla T4, driver 581.80; run 39558022851) all 9 master `-wgpu` half rows are `ignored` while 813 other wgpu rows pass, with no reason printed. The chain has no wgpu-specific logic: slang-test → render-test `requiredFeatures` → slang-rhi `wgpu-device.cpp:256` (Half only if the Dawn device has ShaderF16) → Dawn's `!IsNvidia`. The toggle is absent from chromium/7204 through 7499 and present from 7559, where it is the only NVIDIA f16 gate (Dawn main: driver ≥ 615.71 OR the toggle); webgpu-dawn-binaries' newest release is still v138.0.7204.168, so a slang-rhi fix needs a new binaries build first. Quick probe: a 20-line C program against `build/<cfg>/bin/libdawn.so` calling `wgpuAdapterHasFeature(a, WGPUFeatureName_ShaderF16)`, including `<dawn/webgpu.h>` (from `build/_deps/dawn-src/include`). render-test is `librender-test-tool.so`, build target `render-test` ([Dawn NVIDIA f16 toggle first lands in chromium/7559](../learnings/1792571519251-dawn-nvidia-f16-toggle-first-lands-in-chromium-755.md)).
- **node `webgpu@0.6.2` (newer Dawn).** Dawn main refuses ShaderF16 on drivers older than 615.71 unless `vulkan_enable_f16_on_nvidia` is set (crbug 42251215). On the L40S (driver 595.91.07) `create(['backend=vulkan'])` gives `shader-f16=false`; adding `'enable-dawn-features=vulkan_enable_f16_on_nvidia'` gives `true`, and `requestDevice({requiredFeatures:['shader-f16']})` then runs `enable f16;` WGSL. slang-triager's `/workspace/agent/repro-13634/gap1-run.mjs` ran 336 BAB-half-load cases, PR vs masked, this way ([Dawn on NVIDIA Vulkan hides shader-f16 unless the toggle is set](../learnings/1792137941807-dawn-on-nvidia-vulkan-hides-shader-f16-unless-togg.md), [WGSL f16 on the L40S: slang-test's Dawn can't, node webgpu + toggle can](../learnings/1792142246327-correction-wgsl-f16-on-nvidia-l40s-slang-test-s-da.md)).

The toggle bypasses a gate Dawn added for f16 driver bugs, so cross-check a wrong f16 result on `-vk`/`-cuda` before blaming Slang. With `-DSLANG_EXCLUDE_DAWN=OFF`, `-vk` and `-cuda` rows run and pass and "Check wgpu,webgpu: Supported" prints; only half rows stay ignored ([-wgpu f16 tests on the L40S fleet](../learnings/1792141636725-correction-wgpu-f16-tests-on-the-l40s-fleet-vk-cud.md)).

Three 2026-10-16 atoms said f16 WGSL "can only be Tint-validated, not run", one citing `storageInputOutput16=false`; both claims are withdrawn (the limit is slang-test's Dawn 7204 and its hard-coded NVIDIA gate). ## Newer WGSL builtins on Dawn 7204, and what the Dawn bump costs (#13967, #13807)

The Dawn pin also limits WGSL language coverage. The Tint in slang-rhi's Dawn (v138.0.7204.168, still the newest binaries release on 2026-10-27) has `subgroup_id` but not `num_subgroups` in `builtin_value`, so `@builtin(num_subgroups)` fails `CreateShaderModule` with "expected builtin value name" under `slang-test -wgpu` (PR #13911's head; #13967). `num_subgroups` is absent at chromium/7204, 7390, 7499 and present at 7559, the branch where the f16 toggle appears, so one bump to >= 7559 unblocks #13807 and #13967. Bisect Dawn via gitiles (the GitHub mirror `google/dawn` has no `chromium/*` branches, so `raw.githubusercontent.com` 404s): `curl -sf "https://dawn.googlesource.com/dawn/+/refs/heads/chromium/<N>/src/tint/lang/core/core.def?format=TEXT" | base64 -d` [Dawn/Tint num_subgroups first lands in chromium/7559; slang-rhi's Dawn 7204 rejects it](../learnings/1793144297778-dawn-tint-num-subgroups-first-lands-in-chromium-75.md).

**The bump is small; the binaries build is the blocker.** Diffing `dawn.json` at chromium/7204, 7559 and 8078 against slang-rhi `src/wgpu` (main 314cfb5, 2026-10-29) shows that M144 (7559) and stable M156 (8078, 156.0.8078.73) need the same six native-only fixes, all from 7559: drop `x(GetInstanceCapabilities)` (`wgpu-api.h:24`); rename `*SetImmediateData` → `*SetImmediates`; replace `instanceDesc.capabilities.timedWaitAnyEnable` with the `TimedWaitAny` required feature (`wgpu-utils.cpp:41`); rename `WGPUShaderModuleWGSLDescriptor` → `WGPUShaderSourceWGSL` (`wgpu-shader-program.cpp:199`); add a `WGPUStringView` parameter to the QueueWorkDone lambda (`wgpu-command.cpp:1231`); update version and 6 hashes (`CMakeLists.txt:277-304`). `vulkan_enable_f16_on_nvidia` is a `ToggleStage::Adapter` toggle: ignored in the instance chain, applied in the RequestAdapterOptions chain (`wgpu-utils.cpp:68`), so one `getDawnTogglesDescriptor()` entry covers it. At 8078 NVIDIA f16 is still off below driver 615.71 without the toggle, and both the L40S (595.91) and CI's T4 (581.80) are below. `@builtin(num_subgroups)` needs `enable subgroups;` plus the `subgroup_id` language feature (`kShippedWithKillswitch`, on by default). shader-slang/webgpu-dawn-binaries has no release after v138.0.7204.168, and its last bump attempt (PR #6, M141, Oct 2025) failed all 6 CI jobs and was closed, so that build must go green first. Branch numbers: `chromiumdash.appspot.com/fetch_milestones?only_branched=true` [slang-rhi Dawn bump 7204→7559/8078 = ~6 small source fixes; vulkan_enable_f16_on_nvidia is an Adapter-stage toggle](../learnings/1793274271888-slang-rhi-dawn-bump-7204-7559-8078-6-small-source-.md).

**Until then, check new subgroup builtins on dawn.node, which also shows which side a fixture refresh got wrong.** The bundled slang-tint predates `subgroup_id`/`num_subgroups` (#13861), so `wgsl-spirv-asm` tests cannot exercise them; dawn.node on Vulkan validates and runs them. `/workspace/agent/tint-check/run-sg.mjs <file.wgsl> <entry> <nWords> <wgCount>` requests `subgroups` when available, binds binding 0 read_write and prints hex words (`XDG_RUNTIME_DIR=/tmp node run-sg.mjs …`). On #13887 R2, `WaveGetWaveIndex()+WaveGetNumWaves()` under `[numthreads(4,1,1)]` printed 1 with `num_subgroups` and 0x20 with the old `subgroup_size`, so the old fixture CHECK pinned the bug #13911 fixed; FileCheck shows only that the spelling changed [WGSL subgroup built-ins can be GPU-checked with dawn.node when slang-tint is too old](../learnings/1793263855658-wgsl-subgroup-built-ins-can-be-gpu-checked-with-da.md).

## Pipeline-creation probes: storage-texture formats, `@workgroup_size` overrides, and value bugs

Some WGSL rules are enforced only at pipeline creation, so shader-module checks (Tint null backend, naga) pass them. **Storage-texture format/access pairs are the main case**: Tint accepts every `texture_storage_*<fmt, access>`, and the spec puts the check at pipeline creation. Probe with node `webgpu@0.6.2` on Vulkan: `adapter.requestDevice({requiredFeatures:['texture-formats-tier1','texture-formats-tier2']})`, then `pushErrorScope('validation')` → `createShaderModule` + `createComputePipeline({layout:'auto'})` → `popErrorScope`; an adapter creates only one device, so use a new adapter per feature set. Dawn results (2026-10): core `read_write` is `r32*` only; tier2 adds `r8{unorm,uint,sint}`, `rgba8{unorm,uint,sint}`, `r16{uint,sint,float}`, `rgba16{uint,sint,float}`, `rgba32{uint,sint,float}`. `rg32float`, `rg32sint`, `bgra8unorm`, `rgba8snorm`, `rg16float`, `rg11b10ufloat`, `rgb10a2unorm` fail `read_write` even with tier2; tier1 formats with `write` need tier1. Default `maxStorageTexturesPerShaderStage` is 4 (adapter max 8): use one shader per format or raise `requiredLimits` (`scratch-13768/probe*.mjs`) [WebGPU storage format/access validation: probe on real Dawn](../learnings/1792502078451-webgpu-storage-format-access-validation-probe-on-r.md), [multi-target diagnostic test](../learnings/1792506746644-multi-target-diagnostic-test-a-format-valid-on-one.md).

Slang's format mapping is measured against that table. On #13768 / PR #13778, adding the 23 `texture_formats_tier1` cases to `getWgslImageFormat` looked like a data fix but changed `read_write` behaviour: `[format("rg8")] RWTexture2D` used to hit the default arm (warning E31105, `rgba32float, read_write`, accepted by tier2), and now emits `rg8unorm, read_write` with no diagnostic, because `wgslFormatSupportsReadWrite` is a one-entry deny-list (`rgba16f`); every device rejects it at pipeline creation. 17 of the 23 never allow `read_write` (only `r8*` and `r16{uint,sint,float}` do, with tier2). Extending the deny-list would break code that compiles today (a maintainer decision), so the PR changed only comments and its Risk line. When you widen a format mapping, check every consumer that branches on the mapped value [mapping a new texel format on WGSL can turn a warned read_write into a pipeline error](../learnings/1792516228144-mapping-a-new-texel-format-on-wgsl-can-silently-tu.md). The same PR hit a multi-target trap: `tests/diagnostics/image-format-unsupported-by-backend.slang` shares declarations across SPIR-V, GLSL and WGSL, and swapping its WGSL format from `rg8` to `r64ui` still passed because the filecheck matches only the warning line; with `SLANG_RUN_SPIRV_VALIDATION=1` (set in CI) the SPIR-V row fails VUID-StandaloneSpirv-Image-04965 and E99999, while `RWTexture2D<uint64_t>` passes SPIR-V but hits a WGSL `static_assert`. Fix: `#ifdef TARGET_WGSL` around the WGSL-only declaration, `-DTARGET_WGSL` only on the WGSL directive; run each target with validation and check exit codes [multi-target diagnostic test: a format valid on one backend may be invalid SPIR-V on another](../learnings/1792506746644-multi-target-diagnostic-test-a-format-valid-on-one.md).

**`@workgroup_size` arguments must share one integer type.** Tint rejects `override k:i32` with `1u`, `override k:u32` with `i32(1)`, and mixed i32/u32 overrides ("'@workgroup_size' arguments must be of the same type, either 'i32' or 'u32'"); bare abstract-int literals are fine. So an emitter printing spec-constant axes as overrides must keep literal axes bare (Slang's `emitInstExpr` prints `i32(1)`) and cast mixed-type spec constants. `pipeline constants:{0:N}` drives an override workgroup size end to end; `create([])` also gets Vulkan (`scratch-13767/run.mjs`, #13767). The SPIR-V side is a separate `WorkgroupSize()` cast bug on [Slang language semantics](slang-b-language-semantics.md) [WGSL @workgroup_size override args must share one int type](../learnings/1792502196007-wgsl-workgroup-size-override-args-must-share-one-i.md).

**Value bugs need execution.** On #13766, WGSL `packUint4x8Clamp(int32_t4)` was `pack4xU8Clamp(vec4<u32>($0))` (hlsl.meta.slang:35904): conversion precedes the clamp, so -1 becomes 255; other targets clamp in i32 (`packInt4x8(clamp(v,0,255))`). When a WGSL `__intrinsic_asm` casts to `vec4<u32>`/`u32` before a clamp or saturate, check the signed overloads. `pack-unpack.slang` has no negative lane and its `-wgpu` rows are `ignored` on Linux, so green CI says nothing; a 1-thread kernel through the node harness proves it (slang-triager `scratch-13766/run.mjs`). Side find: WGSL `D3DCOLORtoUBYTE4` emits `bitcast<vec4i>(pack4x8unorm(x))`, which Tint rejects [WGSL pack4xU8Clamp(vec4<u32>(int4)) wraps negatives](../learnings/1792501224839-wgsl-pack4xu8clamp-vec4-u32-int4-wraps-negatives-a.md).

## Driver and harness traps

- **The NVIDIA Vulkan driver segfaults on Tint-valid SPIR-V for a runtime NaN/Inf inside a local array constructor, in both Dawns.** On the L40S (driver 595.91.07), `fn h()->f32{let a=f32(0);let b=f32(0);return a/b;} … var k = array<f32,3>(h(), 2.0, 3.0); o[t.x] = k[t.x];` passes Tint, and `vkCreateComputePipelines` SIGSEGVs (null deref, `libnvidia-gpucomp` ← `libnvidia-glvkspirv`), also for `±1.0/0.0`; binding the call to a `let` first does not help. Constant indices, `vec4(_slang_getNan())`, scalar or finite-returning calls, element stores after declaration, a `var<private>` filled at entry, struct tables, nested/matrix/vector arrays and bit-pattern elements all run. Slang's direct SPIR-V (`OpConstantComposite` NaN) passes `slang-test -vk` [NVIDIA Vulkan driver segfaults on Tint SPIR-V](../learnings/1792141095836-nvidia-vulkan-driver-segfaults-on-tint-spir-v-for-.md), [Dawn 138 also segfaults on array<f32,N>(_slang_getNan(), …)](../learnings/1792143127973-dawn-138-on-nvidia-vulkan-l40s-segfaults-on-array-.md).
- **Slang emits that shape; the fix is a `let`-bound bit pattern.** Master emits it for a local `float a[3] = { myNan(), … }`, and #13669 (static NaN tables sunk into functions) routes static tables into it, while `static float g[N] = kT;` entry-init runs. Helpers written as `let bits = 0x7fc00000u; return bitcast<f32>(bits);` (Inf `0x7f800000u`/`0xff800000u`; f16 `bitcast<vec2<f16>>(bits).x` with `0x7e00`/`0x7c00`/`0xfc00`) avoid the crash: eight array/vec shapes ran 3/3 with exact bits. The `let` is load-bearing: `bitcast<f32>(0x7fc00000u)` on a literal is a const-expression Tint rejects ("value nan cannot be represented as 'f32'"), while `bitcast<f32>(select(0xff800000u, 0x7f800000u, p))` with runtime `p` is fine (#13669, #13680; probes in slang-reviewer `review-13669/probe/bits/`) [WGSL NaN/Inf: bitcast of a u32 must go through a let](../learnings/1792143602803-wgsl-nan-inf-bitcast-of-a-u32-must-go-through-a-le.md), [WGSL NaN/Inf: build from let-bound bit patterns](../learnings/1792146020374-wgsl-nan-inf-build-from-let-bound-bit-patterns-not.md).
- **A device run needs a trivial control in the same round, and CI will not see a Linux Dawn crash.** dawn.node crashes on lavapipe for every shader, so it can't cross-check there. CI runs wgpu rows only in Windows x64 `-gpu-dx` jobs (T4, Dawn over Vulkan). Local `-wgpu` rows need `-DSLANG_EXCLUDE_DAWN=OFF` plus `LD_LIBRARY_PATH=<build>/Debug/bin`, or the probe reports Not Supported and rows are silently ignored [Dawn 138 also segfaults](../learnings/1792143127973-dawn-138-on-nvidia-vulkan-l40s-segfaults-on-array-.md), [build from let-bound bit patterns](../learnings/1792146020374-wgsl-nan-inf-build-from-let-bound-bit-patterns-not.md).
- **Native backtrace from a node addon crash**: an `LD_PRELOAD` SIGSEGV handler (sigaction + backtrace + dladdr) plus `NODE_OPTIONS=--disable-wasm-trap-handler`, or node swallows the signal. `enable-dawn-features=dump_shaders` prints Tint's SPIR-V before pipeline creation [NVIDIA Vulkan driver segfaults on Tint SPIR-V](../learnings/1792141095836-nvidia-vulkan-driver-segfaults-on-tint-spir-v-for-.md).
- **Teardown hangs or segfaults after results print**: wrap in `timeout -s KILL`, read the output line.
- **Under WGSL's finite-math assumption `n != n` on a runtime NaN can be false**: check bit patterns, not `isnan`.
- **`slang-test -vk` rows lower to SPIR-V and do not exercise WGSL emitter changes.**
- **`pkill -f <pattern>` in a Bash tool call can kill the tool's own shell** (exit 144). Kill by pid [Running emitted WGSL on the real GPU and its traps](../learnings/1792141095957-running-emitted-wgsl-on-the-real-gpu-node-webgpu-d.md).

Running GPU slang-test suites concurrently is a separate source of false failures; see [slang-test GPU lanes on the shared L40S](slang-test-gpu-lanes-on-shared-l40s.md).
