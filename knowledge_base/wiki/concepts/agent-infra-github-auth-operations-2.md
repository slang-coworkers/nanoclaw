# GitHub Auth and Operations in Agent Containers (part 2)

> **Split 2026-08-17** out of the over-cap [GitHub Auth and Operations in Agent Containers](agent-infra-github-auth-operations.md). Part 1 owns the core `gh auth status` false-negative rule, the works/does-not-work catalog, the App-identity permission catalog, workflow-file push limits, PR-session mapping, and degraded-session fallbacks. This page holds the later incremental folds: the (resolved) 07-16/07-17 auth-outage diagnostics, the empty-list-looks-like-success trap, the Discussions write-block, PR-review-under-invalid-token, fork-PR takeover mechanics, and the third workflow-push boundary.

## TL;DR
- **The 07-16/07-17 "GitHub auth outage" is RESOLVED — do NOT carry forward any "auth/actions/GraphQL/git-push is down" or "hold read-only" assumption.** Root cause was an App-token refresh cron dying on a missing `gh`; fixed. Keep the REST-vs-actions-vs-GraphQL split as a *diagnostic technique* for a future problem, not a current state — re-diagnose from scratch if a new 401 cluster appears.
- **An empty list is a successful-looking empty response, not an error.** On a repo that always has open issues, `total_count:0` is a tool-malfunction signal, not "zero new issues." Cross-check via the unauthenticated GitHub REST API (no token needed for public issues/PRs/actions).
- **The `nv-slang-bot` App token CANNOT write to GitHub Discussions** (`addDiscussionComment` → FORBIDDEN, hard block) — post on the linked issue instead. Issue/PR writes still work.
- **The bot token CANNOT push `.github/workflows/*`** (missing `workflows` scope) — deliver the workflow as a ready-to-apply patch for a human to commit; a maintainer will policy-close a coworker-bot workflow PR anyway, so flag workflow-scoped fixes as maintainer-only at triage.
- **Reviewing/triaging still works under a `placeholder` `GH_TOKEN`** — `git ls-remote`/`git fetch` the head branch by name and unauth REST reads work; only writes are blocked. An unauth 404 on `pulls/<n>` within ~1 min of PR creation is a replication-cache false alarm, not proof the PR is absent.
- **A human-cred merge during a bot `actions:write` outage is NOT evidence the write path recovered** — re-probe with an actual bot write (`gh run rerun --failed`, exit 0).
- **On a contributor's PERSONAL fork the bot can't push even with `maintainerCanModify`** — cherry-pick residual commits onto `origin/main` (preserves author), push to origin, open a fresh bot PR, comment "Supersedes #N" (don't close).

## Resilience: the empty-list-looks-like-success trap and the unauth REST fallback

When a list/search tool (an MCP `github_list_issues` / `github_search_issues`, or `gh` returning empty via an invalid token) returns `{"issues": [], "total_count": 0}`, that is a *successful-looking empty response*, not an error — and on a repo that always has open issues (shader-slang/slang), `total_count:0` is a tool-malfunction signal, NOT "zero new issues." Never report "no new issues" off an empty list without cross-checking. The durable fallback is the **unauthenticated GitHub REST API**, which returns real data for issues/PRs/actions with no token: `curl -s "https://api.github.com/repos/shader-slang/slang/issues?state=open&sort=created&direction=desc&per_page=40"` (filter out entries with a `pull_request` key), `.../pulls?state=closed&sort=updated&...` for merged PRs, `.../actions/runs?status=failure&...` for CI failures, and `curl -s https://raw.githubusercontent.com/shader-slang/slang-ci-analytics/main/health_snapshots.jsonl | tail -1` for the CI-health snapshot. Its value is independence from a flaky MCP server — keep it as a general resilience technique ([slang-mcp degraded: use unauth GitHub REST fallback for daily report](wiki/learnings/1784276460761-slang-mcp-degraded-use-unauth-github-rest-fallback.md)).

## Contradictions / supersessions — the 07-16/07-17 "auth outage" claims are RESOLVED

The "GitHub gateway 401 split" diagnostic above (and the earlier `slang-mcp` degraded note) were filed during a **transient migration credential regression on 2026-07-16/07-17 that is now FIXED** — do NOT carry forward any "GitHub auth / actions / GraphQL / git-push is down" or "hold read-only" assumption. Root cause (dashboard-admin, 07-17): the App-token refresh cron silently died because `gh` was not installed on the newly-migrated host, so with no `gh` the refresh step failed and the github.com App token expired hourly — every `actions` API and GraphQL call then 401'd `Bad credentials`, and the 07-17 write-path "Must-have-admin-rights" symptom was the same expired-token cause, not a privilege problem. Fix: `gh` 2.96 installed on the host, the refresh cron guarded so it won't silently no-op on a missing dependency, and git-push split into non-overlapping secrets (`/shader-slang/slang*` App token + `/slang-coworkers/<repo>*` USER PAT). Verified recovered 07-17 ~11:47Z: `gh api graphql '{viewer{login}}'` → `nv-slang-bot[bot]`, `actions/runs .total_count` → 40000, `gh run list` works, both git-push targets succeed. **Read-only hold is LIFTED** — resume full CI sweeps, reruns, and requeues; do not defer classification citing this outage. Keep the REST-vs-actions-vs-GraphQL split (and the empty-list trap above) as *diagnostic techniques* for characterizing a future cred/gateway problem, but treat them as probe methods, not a current state — and if a future 401 cluster appears, re-diagnose from scratch (which paths fail? is the refresh cron alive / is `gh` present?) rather than assuming this specific outage recurred ([CORRECTION: GitHub gateway actions/GraphQL 401 outage (07-16) is RESOLVED 07-17 — do NOT hold read-only](wiki/learnings/1784288884629-correction-github-gateway-actions-graphql-401-outa.md), [CORRECTION: gh/token/gateway auth was NOT broken on 2026-07-17 (transient cred regression, now fixed)](wiki/learnings/1784288847791-correction-gh-token-gateway-auth-was-not-broken-on.md)). Note that a truly-flaky `slang-mcp` server is a *separate* problem to diagnose independently — an `Upstream MCP server unavailable` from `slang-mcp` tools is an MCP-server issue, unrelated to the (now-fixed) GitHub credential.

## Discussions Write-Block and Reviewing/Triaging Under an Invalid Token (2026-07-21 fold)

Two more hard boundaries on what the `nv-slang-bot` App token can and cannot do. **(1) It CANNOT write to GitHub Discussions.** The `addDiscussionComment` GraphQL mutation returns `FORBIDDEN: Resource not accessible by integration` — Discussions are outside the App's permission scope, unlike issues/PRs which it comments on freely. This is a hard block, not transient (retry gives the same error). Consequence: to answer a user thread that lives on a *Discussion* (e.g. discussion #11840), post the answer on the linked *issue* (the discussion→issue cross-reference surfaces it) and tell the human the discussion surface is unreachable. Note this is orthogonal to the `gh auth status` false-negative: issue/PR writes still work ([nv-slang-bot App token CANNOT write to GitHub Discussions (only issues/PRs)](wiki/learnings/1784542479875-nv-slang-bot-app-token-cannot-write-to-github-disc.md)). **(2) Reviewing/triaging still works with a `placeholder` `GH_TOKEN`.** When `GH_TOKEN` is literally `placeholder` (len 8), `gh auth status` fails "token is invalid" and `gh pr view` returns "Could not resolve to a PullRequest" — but `git ls-remote origin` and `git fetch origin <head-branch>` still succeed (the remote URL embeds `x-access-token:placeholder@…` and the public repo allows anonymous git read), and unauthenticated `curl https://api.github.com/repos/…` works for public issues/PRs (60 req/hr). So review the fetchable **head branch by name** via `git diff <merge-base> <branch>`; only GitHub *writes* are blocked (degrade to `send_file` to parent, never fabricate a "posted" status) ([PR review under invalid GH_TOKEN — review the fetchable branch, don't stall](wiki/learnings/1784595260519-pr-review-under-invalid-gh-token-review-the-fetcha.md)). **Important correction to the anon-fallback:** do NOT read an unauthenticated 404 on `pulls/<n>` (while repo + issue return 200) as proof the PR was never opened. Observed on #12168: the PR *was* real (draft, created 00:54:36Z); the anon probe ~30s later hit GitHub's replication/cache window where the branch had propagated to the anonymous read path but the PR object had not. An **authenticated** query resolved it cleanly. Corrected rule: an unauth 404 within ~1 min of PR creation is most likely propagation lag — review the fetchable head branch and flag it up-chain as "PR not visible on the anon path yet — confirm via an authenticated query," not "PR never opened" ([Correction — unauth GitHub 404 right after PR creation is a replication-cache false alarm](wiki/learnings/1784595649737-correction-unauth-github-404-right-after-pr-creati.md)).

## PR Takeover From a Contributor's Personal Fork: Bot Pushes to origin, Not the Fork (2026-07-22 fold)

When taking over a slangpy PR whose head branch lives on a maintainer's PERSONAL fork (e.g. `jhelferty-nv/slangpy`), the `nv-slang-bot[bot]` App token CANNOT push to that fork even when `maintainerCanModify: true` — that flag grants push to maintainer *users*, not to the bot App token (push fails `Authentication failed for '.../jhelferty-nv/slangpy.git'`). Correct prod takeover mechanic (origin = shader-slang/slangpy directly, where the bot has push rights): (1) cherry-pick the residual commits onto current `origin/main` in a fresh worktree — this PRESERVES the original author, unlike a squash; (2) push the new branch to `origin`; (3) `gh pr create --draft` a fresh bot-owned PR, call `report_pr_created`, and comment "Supersedes #<old>" on the original (do NOT close it — recommend, let the maintainer decide). Dropping already-landed hunks during a rebase-takeover keeps the diff minimal — verify each dropped hunk is on main verbatim (`git show origin/main:<file>`) first. Note a draft→ready flip is normally operator-gated, but an explicit maintainer request on the PR + parent authorization lifts that gate for that specific PR (merge stays human/CI-gated), and CI runs on draft PRs too ([PR takeover from a contributor's personal fork: bot pushes to origin, not the fork](wiki/learnings/1784692103088-pr-takeover-from-a-contributor-s-personal-fork-bot.md)).

## Human-Cred Merge ≠ Bot Write Recovery, and App-Installation-Token Rebase Mechanics (2026-07-23 fold)

During a bot `actions:write` outage (OneCLI GitHub disconnect / gateway 403), a PR flipping to MERGED is NOT evidence the write path recovered — a human maintainer can merge on their own creds while the bot is still 403'd. To confirm recovery, re-probe with an ACTUAL bot write (`gh run rerun --failed` on a genuine flake) and check exit 0; never infer recovery from a merge or queue movement, which humans/GitHub-auto can drive ([human-cred PR merge during an actions:write outage ≠ bot write recovery](wiki/learnings/1784736496164-human-cred-pr-merge-during-actions-write-outage-bo.md)). Separately, on `slangpy-samples`/`slangpy` from the fixer container the `GH_TOKEN` is a **GitHub App installation token**: `gh auth status` reports "token invalid" and `gh api user` 403s as EXPECTED (the App has no user identity), and `--jq .permissions` returns all-false and is unreliable — but `gh issue comment`, comment PATCH, and git push all work where the App has scope. Use `https://x-access-token:${GH_TOKEN}@github.com/...` for git, and clear stale-black-debt red with a clean `git rebase origin/main` verified by `git patch-id --stable` + `--force-with-lease=<branch>:<old-sha>` ([slangpy-samples auth + rebase mechanics (App installation token)](wiki/learnings/1784768440116-slangpy-samples-auth-rebase-mechanics-app-installa.md)).

## Third Hard Boundary: Bot Token CANNOT Push `.github/workflows/*` — Deliver CI as a Patch (2026-07-26 fold)

A third permission wall on the `nv-slang-bot` App token, alongside the Discussions-write and placeholder-token boundaries above: **it cannot push files under `.github/workflows/`** — the push is rejected with `refusing to allow a GitHub App to create or update workflow .github/workflows/<name>.yml without 'workflows' permission`. Normal file pushes and `gh` issue/PR-comment ops work fine; only the `workflows` permission scope is missing. Don't burn time retrying — deliver the workflow as a ready-to-apply artifact (fenced YAML + a note that a human must commit it) in a PR/issue comment and ask a maintainer to land it or grant the scope. Two verified slangpy-samples CI corollaries that shape any workflow you hand off: its example suite (`tests/examples/test_examples.py`) creates a real GPU device and **cannot run on GitHub-hosted runners** (slangpy fails on software Vulkan/llvmpipe → `Failed to create device!`) — GPU CI needs a self-hosted runner (`runs-on: {group: nvrgfx, labels: [Linux, X64]}`); and its `.npz` expected-output fixtures are **Git LFS** objects, so checkout must use `actions/checkout@v4` with `lfs: true` or tests get 129-byte pointer files ([Bot App token CANNOT push .github/workflows/* — deliver CI as a patch; slangpy-samples GPU-runner + LFS constraints](wiki/learnings/1785048496087-bot-app-token-cannot-push-github-workflows-missing.md)).
