# slang-rhi shader-object binding

How slang-rhi turns a root shader object plus Slang's reflection into API bindings on each draw or dispatch: how binding data is built, the D3D12 root signature and the Vulkan push-constant ranges it derives from reflection, and the global `$Globals` constant buffer, whose layout shape Slang and slang-rhi must agree on. Runtime lifetime, pool and device-creation facts stay on [[wiki/concepts/slang-rhi-backend-runtime.md]]. How to see a binding bug that the NVIDIA driver tolerates is on [[wiki/concepts/slang-test-gpu-lanes-on-shared-l40s.md]].

## TL;DR

- **Binding data is rebuilt on every draw and dispatch.** All seven backends' `bindAsRoot` allocate fresh binding data (each has the TODO "lookup the cache"). `BindingCache` only keeps data alive (a vector on Vulkan/WGPU, empty on D3D12/CUDA/CPU); it is not keyed by shader object, whatever DeepWiki says.
- **Before PR #950, `ShaderObject::finalize()` never set `m_finalized`**, so `isFinalized()` was always false and no `checkFinalized()` guard ever tripped.
- **A binding-data reuse or caching change must move resource-state requests out of the pointer-gated branch.** Vulkan `cmdSetComputeState`, D3D12 `setBindings`, and the render and ray-tracing paths call `requireBindingStates` only when the binding-data pointer changes, and neither pass begin/end nor `cmdCopyBuffer` resets `m_computeStateValid`. A cache that returns the same pointer skips the barrier after a copy into a bound buffer.
- **A cache keyed by the root object must hold its own reference.** The command list retains only the pipeline and the slot resources, not shader objects.
- **Doubling growth from capacity 0 stays 0.** `BindingDataBuilder` grows with `capacity *= 2`, and `ArenaAllocator::allocate(0)` reserves nothing, so a fix that starts capacity at 0 writes out of bounds. Guard with `cap = cap ? cap * 2 : N`. The layout counts are not the number of state entries written, and only `shader-object-large` exercises the grow path.
- **D3D12 takes a constant buffer's own CBV register from the element offset, not `containerOffset`, and then increments it.** Vulkan/WGPU use scope + sub-object + container. So global uniforms plus `ConstantBuffer` params get CBVs one register high (`b0,b2,b3`), and dx12 pipeline creation fails while vk/cuda pass. Split such render-test tests.
- **Slang writes the default `$Globals` CB binding onto the global scope var layout, while the fields keep absolute bindings.** This is right only when the CB lands at slot 0. An explicit binding at slot 0 shifts every cumulative offset walk and gives duplicate SPIR-V bindings (#14013). Moving the CB binding to `containerVarLayout` (PR #14023) changes slang-rhi's D3D12 root signatures, so audit rhi consumers before you call a reflection-shape change non-breaking.
- **slang-rhi `bindAsRoot` (Vulkan/WGPU) writes the global UBO at `BindingOffset{}` (binding 0)** (slang-rhi#959). With a storage buffer at binding 0 the write has the wrong descriptor type, and the NVIDIA driver accepts it. Only the validation layer reports it.
- **Slang puts every Vulkan push-constant block at Offset 0, but slang-rhi gives the ranges consecutive offsets**, so a global `[[vk::push_constant]]` plus entry-point uniforms reads the wrong bytes. Use a plain global `uniform` (UBO) instead, and check DeepWiki layout claims against slangc output.
- **Build a reflection walk harness for layout PRs.** About 30 lines of C++ against libslang that print scope, container and element offsets, built on base and head, turn "does reflection match codegen" into a direct diff.

## Binding data is rebuilt per dispatch (slang-rhi d2fc6bb)

These facts were verified on slang-rhi main d2fc6bb on 2026-10-29, while triaging slang-rhi#955. Every dispatch goes through `ComputePassEncoder::writeComputeState` → `CommandEncoder::prepareBindings` → the virtual `getBindingData` (`src/command-buffer.cpp:212-268`, `:948-972`). All seven backends' `bindAsRoot` allocate new binding data, each under the same TODO, "lookup the cache for existing binding data". `BindingCache` is not a lookup cache. DeepWiki says it is "keyed by shader object", which is wrong: on Vulkan and WGPU it is a `vector<BindingDataImpl*>` that only keeps data alive, and it is empty on D3D12, CUDA and CPU. `ShaderObject::finalize()` never set `m_finalized`, so `isFinalized()` was always false and the `checkFinalized()` setter guards never tripped; PR #950 fixes this [slang-rhi: binding data rebuilt per dispatch; finalize() no-op; reuse needs per-dispatch state requests (d2fc6bb)](../learnings/1793260702705-slang-rhi-binding-data-rebuilt-per-dispatch-finali.md). Each `bindAsRoot` allocates from the command-buffer arena, whose 1 MiB pages are kept across `reset()` [slang-rhi ArenaAllocator::allocate(0) + doubling growth = OOB write when capacity starts at 0](../learnings/1793260598733-slang-rhi-arenaallocator-allocate-0-doubling-growt.md).

Any reuse or caching change walks into a barrier trap. The Vulkan `cmdSetComputeState` calls `requireBindingStates` only inside `if (updateBindings)`, and that flag compares binding-data pointers (`vk-command.cpp:1048`, `:1058-1062`). D3D12 does the same through `setBindings`, and the render and ray-tracing paths (`:739`, `:786`, `:1110`) share the pattern. Neither begin/end compute pass nor `cmdCopyBuffer` resets `m_computeStateValid`. So a cache that returns the same pointer after a copy into a bound buffer silently skips the transition back, and the state requests must move out of the pointer-gated branch. The command list also does not retain the root object: it retains only the pipeline, and `trackResources` retains slot resources but not shader objects. A cache keyed by the root pointer must therefore hold its own reference [slang-rhi: binding data rebuilt per dispatch; finalize() no-op; reuse needs per-dispatch state requests (d2fc6bb)](../learnings/1793260702705-slang-rhi-binding-data-rebuilt-per-dispatch-finali.md).

## `BindingDataBuilder` growth: a zero capacity never doubles

In the Vulkan and D3D12 `BindingDataBuilder`, `writeBufferState` and `writeTextureState` grow with `capacity *= 2` (`vk-shader-object.cpp:195-229`, `d3d12-shader-object.cpp:39-67` at d2fc6bb). Suppose a fix sizes the initial capacity from the layout, or starts it lazily at 0. A zero capacity then stays zero, `ArenaAllocator::allocate(0)` reserves nothing, and `states[count++] = …` writes past the reservation. The guard is `cap = cap ? cap * 2 : N`; Metal's acceleration-structure growth is the precedent (`metal-shader-object.cpp:285-287`). The existing layout counts are not the number of state entries written either. Vulkan's `m_totalBindingCount` counts per range and skips ParameterBlocks, and D3D12's `m_totalCounts.resource` mixes buffers and textures. `shader-object-large` (D3D12 and Vulkan, 3073 buffers and 3072 textures) is the only test that exercises the grow path (slang-rhi#954 triage) [slang-rhi ArenaAllocator::allocate(0) + doubling growth = OOB write when capacity starts at 0](../learnings/1793260598733-slang-rhi-arenaallocator-allocate-0-doubling-growt.md).

## The global `$Globals` constant buffer: Slang's layout shape and slang-rhi#959 (#14013)

Consider a module whose first global takes an explicit binding at slot 0:

```slang
[[vk::binding(0)]] RWStructuredBuffer<uint> r;
struct S { Texture2D t; float f; }
uniform S s;
Texture2D u;
```

`slang-parameter-binding.cpp` (~:4787) writes the default global constant buffer's index and space onto `globalScopeVarLayout` itself, the var layout that `getGlobalParamsVarLayout()` returns. The global fields keep ABSOLUTE bindings, because `ScopeLayoutBuilder::_addParameter` records only Uniform usage and so never shifts the element. The numbers come out right only when the CB lands at 0. Here `r` takes slot 0, the scope offset becomes non-zero, and every documented cumulative walk (scope + element + field) shifts each resource. The IR legalizer adds up the same offsets, so SPIR-V gets a duplicate `Binding 3` for `globalParams.s.t` and `u`. That is a real miscompile, not just a reflection mismatch. `register(b0)` on a D3D cbuffer and `-fvk-bind-globals N S` trigger it the same way. The correct shape is a scope offset of 0 with the CB binding on `containerVarLayout`. Making the fields relative instead is impossible, because offsets are unsigned. The HLSL, GLSL and WGSL emitters already chain the container offset, while the SPIR-V and Metal emitters and ir-metadata read only the outer var layout. Separately, `spReflection_getGlobalConstantBufferBinding` looks only at the ConstantBuffer kind, so it always returns 0 on Vulkan [Slang global $Globals CB binding lives on the scope var layout — breaks offset walks AND legalized SPIR-V when an explicit binding takes slot 0 (#14013)](../learnings/1793278706004-slang-global-globals-cb-binding-lives-on-the-scope.md). The `-fvk-bind-globals` non-default-set collision is a different bug; it is on [[wiki/concepts/slangc-target-output-and-obfuscation.md]].

The runtime half is slang-rhi#959. Vulkan/WGPU `bindAsRoot` writes the root UBO at `BindingOffset{}`, binding 0, whatever reflection says (see its TODO) [Slang global $Globals CB binding lives on the scope var layout — breaks offset walks AND legalized SPIR-V when an explicit binding takes slot 0 (#14013)](../learnings/1793278706004-slang-global-globals-cb-binding-lives-on-the-scope.md). With the Slang fix (PR #14023), the issue's COMPARE_COMPUTE `-vk` repro went from 0 to the expected 1234, stably over 3 runs on the L40S. Under the Khronos validation layer, the same run reported `VUID-VkWriteDescriptorSet-descriptorType-00319` (a UNIFORM_BUFFER written into the STORAGE_BUFFER at binding 0) and `VUID-vkCmdDispatch-None-02699` (`-08114` in a newer layer): the real UBO binding was never written. With validation on, the result read 0. The NVIDIA driver accepted the invalid write, so the green run was undefined behaviour, and end-to-end runtime needs the rhi fix too [NVIDIA Vulkan drivers tolerate mismatched-type descriptor writes, so a runtime PASS can hide a real slang-rhi binding bug. Run the Khronos validation layer from the Debian .deb (no install needed)](../learnings/1793285936432-nvidia-vulkan-drivers-tolerate-mismatched-type-des.md), [A Vulkan runtime pass on NVIDIA without validation layers is not evidence of a binding fix](../learnings/1793289426474-a-vulkan-runtime-pass-on-nvidia-without-validation.md), [A green Vulkan render-test run can be undefined behavior; rerun under VVL before trusting it](../learnings/1793294735619-a-green-vulkan-render-test-run-can-be-undefined-be.md). For layout PRs, a ~30-line C++ harness that links libslang and prints the scope, container and element offsets, each field's walked absolute offset, and the `getDescriptorSet*` ranges turns "does reflection match codegen" into a direct diff when you build it against base and head. The reviewer's copy is `runs/probe-14023/refl/walk.cpp` in the slang-reviewer group [A green Vulkan render-test run can be undefined behavior; rerun under VVL before trusting it](../learnings/1793294735619-a-green-vulkan-render-test-run-can-be-undefined-be.md).

## D3D12 root signature: global uniforms plus `ConstantBuffer` params put CBVs one register high (slang#13824)

Consider a render-test compute shader with both a global `uniform` value and a `ConstantBuffer<T>` parameter, run on the dx12 lane. The HLSL uses `b0` for the implicit global constant buffer and `b1`, `b2` for the `ConstantBuffer` params, but slang-rhi builds a root signature with `b0,b2,b3`. `RootSignatureDescBuilder::addAsConstantBuffer` (`external/slang-rhi/src/d3d12/d3d12-shader-object-layout.cpp:644-667`, slang-rhi b856e635) adds the ordinary-data CBV and increments the CBV offset (`offsetForRangeType++`) before recursing, but for the global scope the sub-object offsets that reflection reports already count the implicit `b0`. `CreateComputePipelineState` then fails with "Shader CBV descriptor range (BaseShaderRegister=1, …) is not fully bound in root signature"; vk and cuda pass. The render-test workaround is not to mix global uniforms with `ConstantBuffer` params in one dx12 test, and to split it (PR #13829). The Linux container has no dx12, but a small C++ probe replaying the builder's register math over real Slang reflection (`IComponentType::getLayout`, `getSubObjectRangeOffset`, `getContainerVarLayout`/`getElementVarLayout`, `getDescriptorSetDescriptorRangeIndexOffset`) predicts the mismatch; for a `globalExistentialType __Dynamic`, specialize with `findTypeByName("__Dynamic")` first. Probe: `/workspace/agent/scratch-13824-fix/rsprobe/probe.cpp` in the slang-fixer container ([D3D12 CBVs one register high](../learnings/1792692825590-slang-rhi-d3d12-root-signature-global-uniforms-con.md)). The Vulkan counterpart is the push-constant section above.

At slang-rhi 314cfb5 the mechanism is exact. `addAsConstantBuffer` (`d3d12-shader-object-layout.cpp` ~:651-663) adds the CB's CBV range at `offsetForOrdinaryChildren`, which is the element offset, and then runs `offsetForRangeType++` (slang-rhi#289). The `containerOffset` passed in is not used for the CB's own register, whereas the Vulkan and WGPU layout builders use scope + sub-object + container. So the #14023 change, which moves the global CB's binding from the scope var layout onto `containerVarLayout`, changes D3D12 root signatures. By the root-signature arithmetic (not run), `ConstantBuffer<P> cb : register(b0)` plus a global uniform goes from `{b1,u0,b2}` (b0 missing, so pipeline creation fails) to `{b0,u0,b1}`, with the `$Globals` and `cb` data swapped. Audit consumers like this before you claim that a reflection-shape change is non-breaking [slang-rhi D3D12 registers the $Globals CBV from the ELEMENT offset, not the container](../learnings/1793289432497-slang-rhi-d3d12-registers-the-globals-cbv-from-the.md).

## Vulkan push-constant ranges: slang-rhi's offsets disagree with Slang's layout (slangpy#1232)

Consider a SlangPy kernel with a global `[[vk::push_constant]]` block and an entry-point `uniform float k`, dispatched on Vulkan (verified on the L40S with Slang 2026.19 and slang-rhi e0eeb428). Slang lays out every push-constant block at SPIR-V Offset 0, global and entry-point alike, and reports each with `pushConstantBuffer` index 0 in its own scope (the program-wide counter that numbers them 0 and 1 is on [[wiki/concepts/slang-test-gpu-lanes-on-shared-l40s.md]]). slang-rhi's `addAllPushConstantRangesRec` (`vk-shader-object-layout.cpp:907-916`) instead gives the ranges consecutive offsets, so the entry-point data is pushed after the global block while the shader reads it at 0, even when the shader never reads the global block: in a raw kernel, `k` read back the bits written to `push`. If the entry point reads both blocks, Slang emits two PushConstant interfaces, violating `VUID-StandaloneSpirv-OpEntryPoint-06674`, and slangc still exits 0 unless `SLANG_RUN_SPIRV_VALIDATION=1` is set. DeepWiki claimed Slang merges the blocks; slangc output shows it does not.

`ParameterBlock<T>` plus a global push constant breaks a second way: the set holding only the push constant becomes an empty descriptor set at index 0 (slang#12349), which the open draft slang-rhi#810 fixes (verified). A plain global `uniform T x;`, which becomes a descriptor-bound UBO, works on both SlangPy paths and is the workaround. To read the real `maxPushConstantsSize` without `vulkaninfo`, call `vkGetPhysicalDeviceProperties` through ctypes: the limits struct starts at byte 296 and `maxPushConstantsSize` is at byte 328 (256 on the L40S) ([push-constant offsets disagree](../learnings/1792164718700-vulkan-global-vk-push-constant-entry-point-uniform.md)).
