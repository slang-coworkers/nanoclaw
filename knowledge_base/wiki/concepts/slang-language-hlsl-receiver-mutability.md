# HLSL receiver mutability: default-inout `this`, immutable receivers, and call-site dialect rules

## TL;DR

- **Since #13615 (merged 2026-10-16, `pr: breaking change`, no compat flag, first release v2026.20) an HLSL-dialect method with no receiver specifier takes `this` as `inout` (BorrowInOut).** A trailing C++-style `const` or `[nonmutating]` selects `in`. `.slang` files keep the Slang default (`in`; `[mutating]` opts in), and synthesized functions stay `in`.
- **The side effect is #13964:** an unannotated HLSL method called on a non-l-value receiver (cbuffer, `ConstantBuffer<T>` and `$Globals` members, `StructuredBuffer` elements, `static const`, `const` locals, rvalues) fails with E30050. A call on a legacy `in` parameter warns E30068. An HLSL struct that conforms to an interface with an `in` receiver fails with E38105, because the synthesized witness wrapper calls the method on a read-only `this`.
- **DXC `-HV 2021` accepts all of these**, and also the #13073 write through a `RWStructuredBuffer` element. Restoring `in` as the HLSL default would bring #13073 back.
- **The workaround today is a trailing `const` or `[nonmutating]` on the method.**
- **The fix direction (PR #13966, open on 2026-10-28) keeps `inout` and decides at the call site.** A call `x.f()` with an immutable `x` and an `inout` receiver is accepted when the code that contains the call is HLSL, and the call passes a copy with no write-back. The decision never reads a property of the callee. A per-declaration callee bit was rejected by the maintainer.
- **General rule:** when a dialect relaxes a call-site legality rule, write the rule in terms of the code being checked, not in terms of a property attached to the callee. Declaration semantics (such as the default receiver mode, which is part of the signature) come from the defining translation unit. Call legality comes from the calling translation unit.
- **`getSourceLanguage()` is the language of the translation unit being checked.** A witness wrapper is checked in the conforming type's translation unit. Contexts without a translation unit return Unknown.
- **Resolve a candidate through its witness before you read its receiver mode.** An interface requirement can win overload resolution when the concrete `[mutating]` member fails the direction check.
- **Record the checker's decision on the call, and do not re-derive it in lowering.** Overloaded calls through implicit `this` never reach the receiver check.

## History: #13073 → #13232 → #13615

#13073 is resolved with no opt-in flag, so notes that assume `-fhlsl-methods-mutable-by-default` are stale. #13232 (merged 2026-10-07) records the effective `this` ParamInfo once, during signature checking (`checkEffectiveThisParamInfo`, slang-check-decl.cpp). #13615 (merged 2026-10-16) then makes HLSL-dialect methods take the receiver as `inout` by default. A trailing C++-style `const` selects `in`, and conflicting receiver specifiers are diagnosed. The bot PRs #13112 and #13213 were not used. So E30047/E30049 on an HLSL-source method first means checking whether the build predates #13615 [slang#13073 resolved: HLSL methods take this as inout by default, no compat flag](../learnings/1792156467633-slang-13073-resolved-hlsl-methods-take-this-as-ino.md).

The first release with #13615 is **v2026.20** (2026-10-19). On v2026.17.1 the #13073 repro (a struct method doing `++value`, called on a `RWStructuredBuffer` element) gives E30047+E30049 for `.slang`, `.hlsl` and `-lang hlsl`. On v2026.20 it compiles only as HLSL (`.hlsl` or `-lang hlsl`); a `.slang` file still gives E30047, because the Slang default is unchanged by design. The switch is `getDefaultReceiverParamMode` (slang-check-decl.cpp), which returns BorrowInOut when `getSourceLanguage() == SourceLanguage::HLSL`; non-`FuncDecl`s and synthesized functions (for example a lambda's `operator()`, which must satisfy core `IFunc`'s `in` requirement) stay `in`. A `const` method that mutates (`void f() const { ++value; }`) gives E30047. A release tarball (`gh release download v<ver> -R shader-slang/slang -p 'slang-<ver>-linux-x86_64.tar.gz'`) reproduces version behavior without a build [v2026.20 HLSL default-inout receivers: .slang still needs `[mutating]`, cbuffer calls need `const`](../learnings/1792403658015-slang-v2026-20-hlsl-default-inout-receivers-slang-.md).

## What #13615 broke: immutable receivers and `in`-receiver conformances (#13964)

Measured on 2026-10-27 at master 9a4817c88, against v2026.19 and DXC main 75fba61. Consider an HLSL struct `S` with a method `int get() { return v; }` and no specifier. Because `get` now takes `this` as BorrowInOut, every call on a receiver that is not an l-value fails the direction check in `TryCheckOverloadCandidateDirections` (slang-check-overload.cpp ~1089-1102) with E30050. That covers `gS.get()` on a cbuffer, `ConstantBuffer<S>` or `$Globals` member, `buf[i].get()` on a `StructuredBuffer<S>` element, `static const` and `const` locals, and rvalues such as `makeS().get()`. A call on a legacy `in` parameter warns E30068.

The same check also breaks conformance. Consider an HLSL struct that conforms to core `IComparable`, or to an interface imported from a Slang module, whose requirements take an `in` receiver. Witness synthesis builds a wrapper whose `this` is read-only. The wrapper then calls the struct's default-`inout` method, fails the same direction check, and conformance fails with E38105.

DXC behaves differently by language version. With `-HV 2021` it accepts all of the calls above and also the #13073 case (a method that writes `this` on a `RWStructuredBuffer` element). It rejects a write through an immutable receiver only late: a cbuffer gives an internal `cast<X>` crash and a `StructuredBuffer` gives a DXIL validation error. With `-HV 202x` DXC follows C++ const rules like current Slang, except that it allows rvalue receivers. So restoring `in` as the HLSL default would bring #13073 back. The DXC-2021-compatible fix keeps `inout` and accepts an immutable base by passing a copy with no write-back; `addArg` in slang-lower-to-ir.cpp (~3535-3655) already lowers that shape on its BorrowIn path. Until a fix lands, add a trailing `const` or `[nonmutating]` to the method [HLSL default-inout receivers (#13615) vs DXC: immutable-receiver calls and in-receiver interface conformance regress (#13964)](../learnings/1793137797352-hlsl-default-inout-receivers-13615-vs-dxc-immutabl.md).

## The relaxation belongs at the call site, not on the callee (#13966)

The first triage of #13964 proposed a callee-side bit, `ThisParamInfoAttribute::acceptsImmutableReceiverCopy`, set when the receiver mode came from the HLSL default. Maintainer tangent-vector rejected that design on PR #13966 ("decide based on the language where the call appears"). The current rule is: for a call `x.f(...)` where `x` is immutable and the effective receiver mode of `f` is `inout`, accept the call if the code that contains the call is being checked as HLSL. The language `f` was written in does not matter. As a result the callee needs no new serialized bit (a new AST field would also have cost a module-version bump), and the rule also covers `[mutating]` methods and Slang-authored callees called from HLSL. The check in `TryCheckOverloadCandidateDirections` reads the caller's `getSourceLanguage()` [Correction: dialect rules for receiver mutability go at the CALL SITE, not on the callee](../learnings/1793147147113-correction-dialect-rules-for-receiver-mutability-g.md).

`SemanticsContext::getSourceLanguage()` (slang-check-impl.h) returns the `sourceLanguage` of the translation unit whose shared context is active. There is one shared context per translation unit (`checkTranslationUnit`), and imported modules are checked in their own translation unit, so the value is the call site's dialect, not the callee module's. Witness-wrapper synthesis (`trySynthesizeMethodRequirementWitness`) checks the wrapper's call through `subVisitor(withSink(...))`, which copies the context. An HLSL struct that conforms to a core or Slang interface therefore has its wrapper call checked as HLSL, which is what fixes the E38105 case. Reflection and specialization contexts have no translation unit and return `SourceLanguage::Unknown` [Slang checker: getSourceLanguage() is the call site's dialect, including witness wrappers](../learnings/1793151491149-slang-checker-getsourcelanguage-is-the-call-site-s.md).

The two uses of `getSourceLanguage()` are consistent. `getDefaultReceiverParamMode` runs during signature checking in the method's own translation unit, so the receiver mode (part of the signature and the ABI) is fixed by the definer and is the same for every importer. The immutable-receiver relaxation is a legality rule about a call, so it reads the translation unit that contains the call.

## Overload-resolution traps for receiver policy

**An interface requirement can rescue a call that its concrete member rejects.** Member lookup on a concrete type returns both the member and the interface requirement it satisfies. `CompareOverloadCandidates` compares `status` before it applies the "prefer concrete over requirement" rule. So if the concrete candidate fails `TryCheckOverloadCandidateDirections` and the requirement passes, the requirement wins, and lowering resolves it through the witness back to the same concrete member. Consider `[mutating] int bump()` on a struct that conforms to an HLSL `interface ICounter { int bump(); }`, and the call `gC.bump()` on a cbuffer member. On master it gives E39999. The callee-bit revision of #13966 compiled it on a silent copy, because it read the policy of the requirement instead of the member. Under the final call-site rule the concrete `[mutating]` member is itself accepted from HLSL code, so this exact example no longer diverges, but the ordering still decides the outcome for any receiver policy that differs between a member and its requirement. The probe is to put an explicit-specifier method behind an interface written in the other dialect [HLSL interface requirement can rescue a call its concrete [mutating] member rejects](../learnings/1793145419526-hlsl-interface-requirement-can-rescue-a-call-its-c.md).

The remedy is to resolve the candidate before reading its receiver mode, so the check sees the function that lowering will actually call. Either use `DeclRef<Decl>(as<DeclRefBase>(funcDeclRef.declRefBase->resolve()))`, or, for a `LookupDeclRef` requirement, `tryLookUpRequirementWitness(astBuilder, lookupDeclRef->getWitness(), requirementDecl)`. When that yields a declRef, read the satisfying member; for an abstract witness, keep the requirement. A `[__ref]` witness of an `inout` requirement resolves to a BorrowInOut wrapper [Slang checker: getSourceLanguage() is the call site's dialect, including witness wrappers](../learnings/1793151491149-slang-checker-getsourcelanguage-is-the-call-site-s.md). When a reviewer reports a regression on such a PR, diff base against head on the reviewer's exact example before relaying it: on #13966 one reported E30067 "regression" also produced no diagnostic on master [HLSL interface requirement can rescue a call its concrete [mutating] member rejects](../learnings/1793145419526-hlsl-interface-requirement-can-rescue-a-call-its-c.md).

**Overloaded calls through implicit `this` skip the receiver direction check.** In `TryCheckOverloadCandidateDirections`, `context.baseExpr` is null for an overloaded call through implicit `this`. Consider `[mutating] void inc()` and `void inc(int)` on the same struct, with `inc()` called inside an `in` method. The receiver is never tested, and master lowers the call with a temporary and a write-back into the method's local copy of `this` (result 207 in the reviewer's repro). So a fix that changes receiver binding must not let lowering re-derive "the checker accepted a copy" from `!baseExpr->type.isLeftValue` plus a writable mode. Otherwise the unchecked calls silently change behavior (207 → 107) or hit asserts. PR #13966 records the checker's decision on the call instead, in a non-serialized `AppExprBase::passesImmutableReceiverCopy`, following the `originalFunctionExpr` precedent [Slang: overloaded calls through implicit `this` skip the receiver direction check](../learnings/1793156285072-slang-overloaded-calls-through-implicit-this-skip-.md).
