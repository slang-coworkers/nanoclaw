# CI Flake Triage — Classification and Known Signatures

Deciding whether a red Slang CI job is a flake or a legitimate author-owned failure, and the catalogue of recurring signatures with their per-signature disposition. The fleet these run on is [runner pools and infrastructure](ci-flake-runner-pools-and-infrastructure.md); *when a rerun helps at all* is [rerun decision rules](ci-flake-rerun-decision-rules.md).

## TL;DR

- **The rollup never carries the reason.** Read each check-run's `conclusion`, then open each failure's log (`actions/jobs/<job_id>/logs`) — `output.summary` is often `null`. The skip pattern alone cannot tell you WHY a check went red.
- **A CPU-job failure pins legitimacy.** `test-linux-release-gcc-x86_64-cpu / test-slang` never touches the GPU fleet — the same named test failing there *and* on GPU/macOS/Windows is a deterministic regression, not a GPU/infra flake.
- **Deterministic build/link errors are never rerunnable** (unless the stale-base exception applies): grep for `undefined reference`, `undefined symbol`, `typeinfo`, `error C####`, `LNK####`, `linker command failed`, `ninja: build stopped`, `FAILED:`. Never classify off the first "error" line — a benign `ld: DWARF error ... FORM value: 0x23` can precede the real cause.
- **Author-owned deterministic failures (no rerun clears them):** XPASS still listed in `expected-failure*.txt`; `check-cmdline-ref`; a merge-group `duplicate case value` collision with a green head; an aarch64-only `OpSource Slang` CHECK failure (fix is a `{{Slang|Unknown}}` relax).
- **Stale-base exception:** a build/link failure clearly unrelated to the PR's diff, where current main builds that job clean, is against a stale base — `gh run rerun --failed` re-checks-out against current main and should clear. Measure the base against the specific fix-introducing commit, not "behind master".
- **Auto-rerun-eligible signatures** (sole failure on an otherwise-green PR): slang-rhi cmd-query timing flake; Falcor single image-comparison diff; "Common Test Setup" pre-test flake (head checks); `texture-shared-cuda.vulkan` numeric flake; macOS-release `metal4.0` per-runner flake; macOS-debug `debug-do-while-locals.slang` SPIRV-Tools assert.
- **Do-NOT-rerun / escalate signatures:** Falcor "Unknown VCS root" (systemic infra); cooperative-vector hlsl-codegen DXC mismatch; `.slang-module` gen with `E99997`/SIGABRT (real assert); base-branch WASM `LanguageServerCore`/`WorkspaceVersion` link regression.
- **Bot-CI `ci_failed` with everything `skipped` + only `wait-for-human-priority`/`check-ci` failing is a priority-yield** — `retry-yielded-bot-ci.yml` self-heals it (narrowly: `--lookback-hours 16`, `--max-attempts 30` age-independent, skips superseded dispatches, reruns `--max-reruns 1` chosen oldest by `run_number`). Do NOT rerun.
- **A JSON-RPC (`waitForResult()`/`hasMessage()`) failure is a test-server child crash symptom, not an RPC-infra bug** — dedup by run id and separate the genuine harness flake from a PR's own crashing test and from GPU device-loss before counting.
- **slang-rhi OMM `VUID-10904` red on a submodule-bump PR is a likely Vulkan-SDK-1.4.341.1 validation-layer false positive, not a converter bug.** slang-rhi's own CI is green only because lavapipe SKIPs OMM tests. Fix is CI-side (pin/suppress the VUID) or an upstream VVL report — not slang-rhi code, and not rerun-clearable.
- **The nightly `agentic-tests` job is advisory doc-bundle drift, never a compiler regression** — it runs the doc-anchored `docs/generated/tests` corpus (not `tests/`), is non-blocking, and reds are golden-snapshot drift from breaking-change PRs; the fix is periodic bundle regeneration, not a tracking issue per drift.

## Classifying Failures: Flake vs. Legitimate

**Test duration is a fast signal.** A Windows GPU test job finishing in under ~60 s ran no tests — likely a disk-space preflight or artifact-download failure, not a test result (see [runner pools and infrastructure](ci-flake-runner-pools-and-infrastructure.md) and [rerun decision rules](ci-flake-rerun-decision-rules.md)).

**CPU-job failure pins legitimacy.** The CPU runner (`test-linux-release-gcc-x86_64-cpu / test-slang`) never touches the GPU fleet, so the same named test failing identically there AND on GPU/macOS/Windows jobs is a deterministic regression requiring author action, not a rerun ([CPU-job failure is the tell for real regression vs GPU flake](../learnings/1782296288354-ci-babysitter-cpu-job-failure-is-the-tell-for-real.md)).

**A pure-Python `extras/` change cannot break C++ build/GPU-test jobs.** If a Python-only PR's failing jobs are C++ builds, C++ static unit tests or GPU tests while `Check Python Scripts (Core Python Only)` and `Check Formatting` PASS, the failure is not the change: confirm via `--log-failed` — HTTP 504 downloads (sccache/OptiX tarballs), OOM, timeouts, cancellations are infra (do nothing); genuine compile/link errors or unit-test asserts are master breakage inherited via a `BEHIND` branch (rebase once master is green). Don't rebase a `BEHIND` branch mid-run — it cancels the matrix and can dismiss a fresh approval. A `nv-slang-bot[bot]` `workflow_dispatch` on a DRAFT bypasses the draft-skip but immediately priority-yields (matrix skipped, parked on `falcor-build-approval-gate`), so don't re-dispatch to "force" a matrix; the reliable run comes from a human marking the PR ready ([bot CI priority-yield + classifying failures on a pure-Python PR](../learnings/1790019959011-slang-bot-ci-priority-yield-classifying-ci-failure.md)).

**Deterministic build/link errors are never rerunnable** (except the stale-base case below). Grep the failed log for `undefined symbol`, `error C####`, `LNK####`, `FAILED:` (ninja) before calling a build failure flaky ([wasm build failures are usually real linker errors](../learnings/1780920419175-slang-ci-wasm-build-failures-are-usually-real-link.md)). **Don't classify off the first "error" line:** in a sanitizer/`-fno-rtti` link failure, `/usr/bin/ld: DWARF error: invalid or unhandled FORM value: 0x23` can sit just *before* the real cause. On PR #12136 a classify-only subagent hit the DWARF line, called it an intermittent linker flake, and recommended a futile rerun; two lines later were 4× `undefined reference to typeinfo for Slang::Session` from the PR's own new `-fno-rtti` file → `linker command failed` → `ninja: build stopped`. Grep `undefined reference`, `typeinfo`, `linker command failed`, `ninja: build stopped` and read around them (the `linker command failed` line names the unit, the lines above say why), and self-verify a subagent's rerun candidate against the raw log before firing ([a benign DWARF ld-note can mask the real undefined-reference cause](../learnings/1784347920752-a-benign-dwarf-ld-note-can-mask-the-real-undefined.md)).

**Stale-base exception:** if a build failure is clearly unrelated to the diff (e.g. a pure CI-YAML PR with C++ linker errors) AND current main builds clean for that job, the run is against a stale base — `gh run rerun --failed` re-checks-out `refs/pull/N/merge` against current main and should clear. Distinguish an active base break by a recent green run of the same job on another PR ([stale-base build/link failures are rerunnable](../learnings/1780985285213-ci-babysitter-stale-base-build-link-failures-are-r.md)).

**Measure base distance to the fix-introducing commit, not the tip — and re-run the cheap git probe before propagating a memory conclusion.** #12783, #13078 and #12992 shared `undefined identifier 'MatrixLayoutMode'` → E30624 → E30855. An earlier verdict called #13078 a real regression because `gh api compare` reported its base `ahead_by:24` of #12986 (which added the enum); that was **retracted**: `git merge-base --is-ancestor <pr-base> <fix-commit>` returned 1 and `git rev-list --left-right --count <pr-base>...<fix>` showed `17 3`, so all three are base-skewed needs-rebase (the `ahead_by` was likely swapped compare arguments). Git content is content-addressed, so "does this SHA contain the enum" is cheap to re-run; when a memory conclusion feeds an action (rerun, requeue, fixer handoff, escalation), re-run the probe yourself — detailed prose with run ids is no proxy for correctness. Two corollaries stand: a **single, explicitly authorized one-off rerun to classify flake vs deterministic** for a genuine anomaly doesn't violate "only rerun infra" (get sign-off; it spends CI), and touching a PR for any reason can surface a live `@nv-slang-bot` mention via `issues/<n>/comments` you weren't webhook-wired for ([Retraction: #13078 was base-skewed like #12783/#12992](../learnings/1789460715976-retraction-pr-13078-was-not-ahead-of-12986-it-was-.md)).

**Merge-group collisions are legitimate, not flakes.** A merge-group build error (e.g. `duplicate case value`) with green head checks means two queued PRs introduced the same enum value — a real conflict. Do NOT requeue; the author rebases and renumbers ([merge-group build break with green head = merge-time collision](../learnings/1782533107353-merge-group-build-break-with-green-head-merge-time.md)).

**XPASS (unexpected pass) is author-owned.** A test the PR fixes that is still listed in an `expected-failure*.txt` file reports XPASS as a failure, identically on CPU and every GPU platform. Do not rerun; the author removes it from the list ([XPASS is a deterministic author-owned CI failure](../learnings/1782360530038-xpass-is-a-deterministic-author-owned-ci-failure-n.md)). The lists differ by workflow, which matters when adding a key too: "Test Slang via glsl" in `ci-slang-test.yml` (Windows GPU) reads only `tests/expected-failure-via-glsl.txt`, while `ci-slang-test-container.yml` (Linux T4) also reads expected-failure-github/linux/linux-gpu, so a test failing in both the direct-SPIR-V and via-GLSL passes needs its key in both `expected-failure-github.txt` and `expected-failure-via-glsl.txt` ([via-GLSL expected-failure lists differ per workflow](../learnings/1791247356003-gh-api-job-logs-silently-empty-without-allow-escap.md)).

**check-cmdline-ref failures are always deterministic** and almost always caused by the PR itself (`slang-options.cpp` changed without regenerating docs, or a wrong doc edit), not master-wide staleness ([attributing check-cmdline-ref CI failures](../learnings/1782324937326-attributing-check-cmdline-ref-ci-failures-not-mast.md)).

**An aarch64-ONLY deterministic test-slang CHECK failure** (every aarch64 job red, x86_64 green) is very likely an env-dependent SPIR-V disassembly token: aarch64 `test-slang` jobs export `SLANG_USE_SPV_SOURCE_LANGUAGE_UNKNOWN=1` (a swiftshader workaround), so `OpSource` disassembles as `OpSource Unknown 1 …` there vs `OpSource Slang 1 …` on x86_64, and a FileCheck hardcoding `OpSource Slang` fails aarch64-only. Author-owned and not rerun-clearable; the fix is a test-only relax to `OpSource {{Slang|Unknown}} 1 …`, not a golden-shift — the emit is correct ([aarch64-only test-slang CHECK fail = env SPIR-V disasm token](../learnings/1784830954472-aarch64-only-test-slang-check-fails-env-token-not-.md)).

**The nightly `agentic-tests` job is advisory doc-bundle drift.** "Nightly Slang Test"'s sole job runs `slang-test -test-dir docs/generated/tests` — an LLM-generated, doc-anchored corpus that never blocks PRs and is not `tests/`. It drifts every time a breaking-change PR lands without regenerating its golden snapshots (IR-dump text, codegen output). Confirm the failing job is `agentic-tests`, pull `--log-failed` for the `N failing tests:` block, and diff each `// CHECK:` line against the "possible intended match here" line — usually a one-token golden diff (`0 : Int` vs `0 : Enum(Int)`) — then map each to a breaking-change PR via `compare/<last-green-sha>...<red-sha>`. If every failure maps to a disclosed PR and is snapshot-shaped (not crash/assert/unrelated wrong output), classify as bundle drift: the fix is periodic regeneration, not a tracking issue per instance (precedent #12351) ([nightly agentic-tests failures are advisory doc-bundle drift](../learnings/1789142798536-slang-nightly-agentic-tests-failures-are-advisory-.md)).

## Known Flake Signatures

**slang-rhi cmd-query timing flake** (`test-cmd-query.cpp:183: CHECK(durationGPU < durationCPU) is NOT correct!`, macOS aarch64): both durations can round equal (`7e-06 < 7e-06`), failing strict `<`. Auto-rerun eligible if it is the sole failure on an otherwise-green PR ([WASM link regression + slang-rhi timing flake signatures](../learnings/1780891496263-slang-ci-wasm-link-regression-slang-rhi-timing-fla.md), [mac-aarch64 RHI flake = cmd-query timing assert](../learnings/1781679288468-slang-11641-mac-aarch64-rhi-flake-cmd-query-timing.md)). The upstream fix (slang-rhi#775, `<=` + tolerance) only helps once slang's submodule pin includes it: `gh api repos/shader-slang/slang-rhi/compare/<fix-sha>...<pin-sha> --jq '{status,behind_by}'`. The sibling WASM signature — `build-linux-release-gcc-wasm / build` undefined symbols for `LanguageServerCore::*` / `WorkspaceVersion::*` — is a known base-branch break; do NOT rerun.

**Falcor image-test flake** (a single isolated image-comparison diff, e.g. `renderpasses/test_GBufferRTTexGrads_d3d12 : FAILED` on `build (windows, release, cl, x86_64)`): if the PR doesn't touch rendering, rerun with `gh run rerun <id> --failed` ([Falcor image-test flakes vs artifact-not-found](../learnings/1780762074181-slang-ci-falcor-image-test-flakes-vs-artifact-not-.md)).

**Falcor `Unknown VCS root`** (exit 1, "Error. Unknown VCS root") hits many independent PRs in one window — systemic infra. Do NOT rerun; record and surface to maintainers ([falcor-unit-test 'Unknown VCS root' is systemic infra](../learnings/1781136348152-slang-ci-falcor-unit-test-unknown-vcs-root-is-syst.md)).

**"Common Test Setup" pre-test failure** on Windows GPU runners (SLANG-WINDOWS-*): the job dies before any test runs and evicts PRs from the merge queue. Auto-rerun eligible for head checks; for merge-group evictions use Merge Queue Recovery. The bot cannot requeue fork PRs ("You're not authorized to push to this branch") ([Common Test Setup pre-test flake evicts PRs](../learnings/1781626237709-slang-ci-common-test-setup-pre-test-flake-evicts-p.md)).

**JSON-RPC failure** (`waitForResult()`/`hasMessage()`): the test-server child died mid-test (stdio EOF) — a crash symptom, not an RPC-infra bug; since PR #11753 fixed the `runUnitTestModule()` stale-pass bug, crashing unit tests record failure instead of silently passing ([JSON-RPC failure = test-server child crash](../learnings/1782407732117-slang-ci-json-rpc-failure-on-a-unit-test-test-serv.md)). The surface conflates (a) a genuine harness flake (CPU concurrency on aarch64), (b) GPU device-loss/faulty ICD killing the worker, and (c) the PR's own consistently failing test; dedup by run id and exclude (b) and (c) from the harness-flake count ([dedup by run id; JSON-RPC and Falcor symptoms conflate root causes](../learnings/1782598546890-flaky-ci-evidence-dedup-by-run-id-json-rpc-and-fal.md)).

**Bot-CI priority-yield** (`ci_failed`, every build/test job `skipped`, only `wait-for-human-priority` + `check-ci` failing): the bot CI yielded to higher-priority human CI and `retry-yielded-bot-ci.yml` self-heals it. Do NOT rerun — it re-enters the same gate ([bot-CI 'ci_failed' is often a priority-yield](../learnings/1781571803229-slang-bot-ci-ci-failed-is-often-a-priority-yield-s.md)).

⚠️ **Two refinements, both learned on a maintainer-facing report.** First, **the skip pattern cannot tell you why a check went red**: draft filtering explained a draft PR's 74 `skipped` check-runs, but the two `failure` conclusions were the priority gate yielding, and the skip pattern is identical under both explanations. Both had `output.summary: null`, so only `gh api repos/<o>/<r>/actions/jobs/<job_id>/logs` gave the reason (`##[error]priority-gate-yielded: higher-priority CI is active; ci-retry-yielded-bot will rerun this bot CI when quiet`). "Draft artifact" implies waiting for the ready-flip; the real cause self-heals. Second, **don't overstate the self-heal**: `ci-retry-yielded-bot` considers only runs within `--lookback-hours` (16), under `--max-attempts` (30, independent of age — `workflow_run: [completed]` triggers can burn attempts faster than hourly, hitting the cap before the 12 h `--max-yield-hours` escalation), skips runs superseded by a newer dispatch on the branch, and reruns `--max-reruns` (1) candidate per invocation, chosen **oldest** by `run_number`. The wrong mechanism leaves a maintainer waiting on something that never happens ([read CI conclusions and failing job logs](../learnings/1785784732188-read-ci-conclusions-and-failing-job-logs-the-skip-.md)).

**Cooperative-vector HLSL codegen** (`tests/cooperative-vector/matrix-mul-hlsl-codegen.slang.1` and `training-hlsl-codegen.slang.1` failing deterministically on `test-windows-release-cl-x86_64-gpu` across 8+ unrelated PRs): DXC version mismatch on that runner — do NOT rerun; classify "blocked on fix PR" ([cooperative-vector tests fail on Windows-release-GPU](../learnings/1780157118768-slang-ci-cooperative-vector-tests-fail-on-windows-.md)).

**`.slang-module` gen failure with `E99997` / SIGABRT** on debug builds: a deterministic in-process compiler assert = a real bug in the PR. Do NOT rerun. A silent exit 1 with no diagnostic is a transient bootstrap crash and is rerun-eligible ([.slang-module gen failure with E99997 = real bug](../learnings/1781720061070-slang-ci-slang-module-gen-failure-with-e99997-asse.md)).

**`texture-shared-cuda.vulkan` numeric flake** on `test-windows-release-cl-x86_64-gpu-rhi / test-slang-rhi`: a CUDA↔Vulkan interop tolerance failure (`CHECK_GE(result[i], expectedResult[i] - 0.01f)`, `external/slang-rhi/tests/testing.h:228`) while ~965/966 rhi cases pass and the suite is green on `windows-debug-gpu-rhi` and elsewhere. PR-agnostic (#11693, #11735, #11812, none touching interop): rerun `--failed` under the daily cap; the `check-ci` red is cascade. Systemic fix (maintainer): widen the tolerance or quarantine ([texture-shared-cuda.vulkan is a recurring slang-rhi interop flake](../learnings/1782936358409-texture-shared-cuda-vulkan-is-a-recurring-slang-rh.md)).

**slang-rhi OMM `VUID-10904` on a submodule-bump PR is a likely validation-layer false positive.** When a slang PR bumps `external/slang-rhi` onto an opacity-micromap commit (slang-rhi #853/#852), `test-linux-debug-gcc-x86_64-rhi / test-slang-rhi` can fail `opacity-micromap-build.vulkan` / `-trace.vulkan` with **VUID-vkCmdBuildAccelerationStructuresKHR-pInfos-10904** (`indexType` `NONE` requires `indexBuffer.deviceAddress == 0`). The converter is compliant: `AccelerationStructureBuildDescConverter::convert` (`src/vulkan/vk-acceleration-structure.cpp`) sets `indexType` and `indexBuffer` together in mutually exclusive branches, and the `NONE` branch leaves the value-initialized 0 buffer, so the naive `ommData.indexBuffer = {};` "fix" is a byte-level no-op. slang-rhi's Linux CI runs on **lavapipe**, which lacks `VK_EXT_opacity_micromap`, so the tests SKIP; slang's runs on real OMM hardware with validation on (and master often pins a pre-OMM slang-rhi, so it only surfaces on a bump). Best hypothesis: a **Vulkan SDK 1.4.341.1** layer false positive on the new VUID-10904/10905 case — fix CI-side (pin/bump the layer or suppress the VUID) or report upstream. Method: when a VUID won't reproduce on your VVL version, don't install the SDK if that rebuilds a shared container — **capture the exact struct bytes handed to the Vulkan call on real hardware**, and never hand a maintainer a second guessed fix-site ([slang-rhi OMM VUID-10904 is likely a VVL 1.4.341.1 false positive](../learnings/1789600998422-slang-rhi-omm-vuid-10904-ci-red-is-likely-a-vvl-1-.md)).

**macOS-release `test-slang` metal4.0 flake is per-runner infra.** `test-macos-release-clang-aarch64 / test-slang` fails with `'required_threads_per_threadgroup' attribute requires Metal language standard metal4.0 or higher` (often with `slang-unit-test-tool/replayStream*`) because some macos-release runners' Metal toolchain is too old. Confirm your own tests passed on that runner, macos-**debug** passes on the same code, and the same head shows success on one run and failure on another; then rerun (≤3×) ([macos-release test-slang metal4.0 flake is infra](../learnings/1783448021238-macos-release-test-slang-metal4-0-flake-is-infra-n.md)). If the signature is deterministic across runners, or an example step exits 255 with `gpu-printing` swallowing the error, it can be a real emit-vs-target capability bug (#11985) — grep for the masked `metal ...: error:` line first.

**`gpu-printing` macOS example flake (#11999) — verify the step, don't trust bot conflation.** On hosted macOS aarch64 the red step is often "Run Slang examples", where `gpu-printing` exits 255 with no output (silent `SLANG_FAIL`, likely an RHI null-return), while "Test Slang" in the same job is GREEN; the bot summary conflated it with a non-fatal metal4.0 gfx-unit-test message inside the green step. Map the red to a specific step and example before accepting a root cause, test determinism (pass and fail within an hour on static master = intermittent), and note "debug passes / release fails" is CI config (examples run only on `config==release && event==pull_request`) ([gpu-printing macOS flake — verify CI signature](../learnings/1783548983571-slang-11999-gpu-printing-macos-flake-verify-ci-sig.md)).

**`static-const-matrix-array.slang.3 syn (llvm)` RPC drop / SIGSEGV is env-specific and intermittent; harness retry is not a fix.** The synthesized LLVM-JIT variant crashes the test-server child (a JSON-RPC drop on GPU jobs, a SIGSEGV core dump on the CPU job). Retry/reconnect is a dead end — there is nothing to reconnect to — and in merge_group runs the test drops on both the initial pass and the harness retry, ending a hard FAILED that evicts the queue, while head runs that never trigger it stay green ("clears on rerun" yet still evicts). The shader is trivial; root-causing needs a Windows-debug, server-count-8 repro, so label it neither `reproduced` nor `not reproduced` and note the limitation ([static-const-matrix-array .3 syn(llvm) RPC drop](../learnings/1783340384337-static-const-matrix-array-3-syn-llvm-rpc-drop-harn.md)). #11951 Sig-B (GPU RPC drop) and #11955 (CPU SIGSEGV) converge on this test+variant and may be one bug in two process topologies, but keep them tracked separately until a backtrace confirms — CI uploads no symbolic core dump, so the evidence places the crash *at* this test, not its fault frame ([#11951 Sig-B and #11955 converge on static-const-matrix-array](../learnings/1783527380806-11951-sig-b-and-11955-cpu-sigsegv-converge-on-stat.md)).

**`debug-do-while-locals.slang` on macOS-debug-aarch64 is a SPIRV-Tools assert flake.** It fails only on `test-macos-debug-clang-aarch64 / test-slang` with `Assertion failed: (unique_id_ != 0), function unique_id, file instruction.h, line 251` — SPIRV-Tools code reached via debug-info SPIR-V emission — and slang-test's auto-retry doesn't always clear it. If it is the only failure and the PR doesn't touch debuginfo/SPIR-V emit, rerun `--failed` (≤3×); if it reproduces across reruns, report it as a pre-existing platform issue rather than blocking (PR #12504, run 34891043815) ([known flaky: debug-do-while-locals.slang on macOS-debug-aarch64](../learnings/1789420993765-known-flaky-ci-test-tests-debuginfo-debug-do-while.md)).
