## TL;DR

How the slang PR-approver's Step-1 eligibility clauses behave on bot-authored (`nv-slang-bot[bot]`) and fleet PRs, and how bot PRs are shepherded to merge. The recurring insight: for a bot-authored PR the *eligibility* verdict is usually a foregone conclusion knowable up front, independent of code quality — so evaluate the cheap clauses before spending the expensive Devin/challenger budget.

- **`nv-slang-bot[bot]` fixer PRs deterministically ABSTAIN on `author_trust`** — the bot's `authorAssociation` is `CONTRIBUTOR`, not in the v0-shadow trusted set `{COLLABORATOR, MEMBER, OWNER}`. A clause FAIL ⇒ `ABSTAIN_POLICY:CLAUSE_FAIL:author_trust` regardless of how clean the code is or how many humans approved. Run `eval-clauses.py` FIRST for a bot-authored PR; if `author_trust` fails, record and stop — no Devin subagent, no challenger.
- **Bot-authored PRs also force Devin-only tier** — production `claude-pr-review.yml` skips bot branches, so `collect-reviews.sh` exits 20 (`{"found":false}`); that is expected, not an infra abstain.
- **`tier_eligible` (the size cap) over-routes bot upstream-syncs** — a fast-forwardable `sync/upstream-*` branch counts upstream's already-reviewed work as decision surface, making every such sync a structural permanent abstain that a maintainer merges on sight with zero reviews. Recognize the shape (bot author + `behind_by 0` clean fast-forward + huge delta in vendored paths) and treat the clause outcome as the whole decision; don't loosen your own derivation to compensate.
- **The mounted policy version can flip eligibility mid-chain** — `v0-shadow-wide`→`v0-shadow` narrowing can change author_trust/tier_eligible pass↔fail on the same PR. Read `clauses.json.policy_version` and compare to the prior revision's; a clause-fail abstain that coincides with a verified 🔴 bug must headline the bug in the report even though the recorded verdict is ABSTAIN.
- **OUT_OF_SCOPE fires FIRST and has no scripted predicate** — a `slang-coworkers/nanoclaw` (fleet-infra) PR is out of the compiler domain the clauses are calibrated for; abstain on repo-class alone. Reserve the COI ground for changes to the approver's *own* decision instrument, not merely adjacent fleet tooling.
- **A completed, green, critique-approved bot PR sitting in draft is NOT stuck** — bot/coworker PRs stay draft; ready-flip and merge are maintainer/operator-gated. A timed-out operator ask for the ready-flip → PR stays draft is the CORRECT fail-safe.
- **A passive rebase-hold cannot gate a maintainer with merge rights** — holding a rebase only delays; a shepherd can merge master into the branch themselves. Escalate up your chain and state the gate in the PR body; don't rely on the hold.
- **`merged_at` is null for nv-slang-bot PRs regardless of merge status** — corroborate merge by reading the target file on `ref: master`, not the API's `merged_at`.

## The structural author_trust abstain

Two atoms independently establish that [`nv-slang-bot[bot]` fixer PRs deterministically ABSTAIN on `author_trust`](../learnings/1788210992079-approver-clause-gap-nv-slang-bot-fixer-prs-determi.md): `eval-clauses.py` reads `author_association = CONTRIBUTOR`, which is not in the v0-shadow trusted set, so every bot-authored PR short-circuits to `ABSTAIN_POLICY:CLAUSE_FAIL:author_trust` before the challenger runs — the Devin cleanliness never changes the decision, and the abstain row is excluded from agreement scoring. The [operational correction](../learnings/1788224841898-approver-clause-gap-bot-authored-nv-slang-bot-prs-.md) is a workflow-ordering fix: the nominal pipeline puts harvest+Devin before the clause check, but for a plainly-untrusted author, evaluate `author_trust` **first** — it is cheap and read-only, and a fail means the whole expensive Devin/challenger stage adds nothing to the recorded decision. Both note the same open policy question: whether the fleet's own `nv-slang-bot` identity should be a trusted author class, or whether "a human must still look at every bot-authored fix" is the intent. Until settled, the approver has zero auto-approval reach over its sibling coworkers' PRs.

## Size cap and policy-version flips

The `tier_eligible` size cap is the other structural gate. On a [bot-authored upstream-sync](../learnings/1787808971576-approver-clause-gap-bot-authored-upstream-sync-siz.md), raw churn is misleading — three-dot `base...head` was `ahead_by 730 / behind_by 0` (a clean fast-forward), so the +108k is upstream's already-reviewed work, not net-new. Under v0-shadow-wide the ONLY clause that fired was `tier_eligible`; `no_protected_paths` PASSED even though the sync edits `.github/workflows/*.yml` because the wide policy's protected glob is a single path — so probe protected-path exposure independently of whether the glob catches it. The [merge outcome confirmed the over-routing](../learnings/1787814836142-approver-clause-gap-merge-outcome-confirms-tier-el.md): the sync merged at the exact second decision SHA with zero reviews, the maintainer (who owns the sync tooling) merging on sight. The abstain is correct given the policy, but the predicate is imprecise for this shape — the right response is to escalate the bar question (the `n≥3` over-conservative-on-a-shape rule), never to loosen your own derivation.

Eligibility is not stable across a revision chain: [mid-chain policy tightening](../learnings/1788200996555-approver-clause-gap-mid-chain-policy-tightening-v0.md) (`v0-shadow-wide`→`v0-shadow`) can flip a prior-eligible PR to `CLAUSE_FAIL` — same PR, opposite eligibility, purely because the operator narrowed the policy between runs. A Step-1 clause FAIL forces an early-return ABSTAIN, so even a VERIFIED 🔴 defect found in Step-1b's Devin pass does not get recorded as a block-level verdict — do not improvise a block outside the gate order, but headline the verified defect in the challenger field and the upstream report so it isn't buried. Always read `clauses.json.policy_version` against the prior revision's.

## Out-of-scope, draft-hold, and merge authority

Repo-class scope fires before merits: [OUT_OF_SCOPE extends to nanoclaw coworker-MCP-tooling PRs](../learnings/1788261058400-approver-clause-gap-out-of-scope-extends-to-nanocl.md). A `slang-coworkers/nanoclaw` PR is fleet-infrastructure outside the shader-slang compiler domain the clauses are calibrated for; OUT_OF_SCOPE has no scripted predicate (recall it from precedent) and overrides the mechanical clause→outcome mapping and the harvest-20→NO_REVIEW_SIGNAL mapping. Ground the abstain on repo-class alone; reserve the COI ground for changes to the *instrument that produces the review signal* (harvest/collect-reviews/devin-fetch/eval-clauses/policy/skill) — a new *adjacent* fleet tool is not enough.

On shepherding: [bot/coworker PRs stay draft](../learnings/1787344144243-bot-coworker-prs-stay-draft-ready-flip-merge-are-m.md) — ready-flip (an outward-facing action triggering the full CI matrix) and merge are maintainer/operator-gated, not a fixer's or parent's call. A completed, green, critique-approved bot PR in draft is correctly parked awaiting the human shepherd, not stuck; a fixer's operator ask for the ready-flip timing out → stays draft is the correct fail-safe (don't retry or re-escalate). And [a passive rebase-hold cannot gate a maintainer](../learnings/1787888940678-a-passive-rebase-hold-cannot-gate-a-maintainer-wit.md): holding a rebase only delays a merge — a shepherd with `maintainerCanModify` + merge rights can merge master into the branch to clear BEHIND and auto-merge past your hold. The real levers are escalating up your chain and stating the gate prominently in the PR body, never disabling auto-merge or re-drafting. When corroborating any bot-PR merge, note that [`merged_at` is null for nv-slang-bot PRs](../learnings/1787994213721-github-get-issue-merged-at-is-null-for-nv-slang-bo.md) regardless of merge status — read the target file on `ref: master` via `github_get_file_contents` instead; `state:"closed"` + `closed_at` + expected code on master ⇒ merged.
