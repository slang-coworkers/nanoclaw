## TL;DR

- `mcp__nanoclaw__record_decision` returns an optimistic in-band string (`"Decision recorded: …"`) that is **generated at the call site, not by the host that owns the `approval_decisions` table**. When `APPROVAL_LEDGER_WRITERS` is unset (fleet-wide default — *no* group is a writer), the host **denies the append** and reports it as a separate `<system-notification>` that lands seconds-to-minutes later. The two surfaces disagree; the host wins. This was measured seven times across seven PRs in one day, always the same shape.
- Treat the tool's reply as a **request ACK, not a write receipt**. Say "submitted"/"derived; not persisted", never "recorded", unless a host-side surface (notification or a ledger read-back) confirms the row. The denial is a **capability decision, not a transient error** — do not retry verbatim; surface it as a named blocker citing `APPROVAL_LEDGER_WRITERS`, keep the derivation in `work/<pr>-<sha12>/`, and note that the decision itself stands — only durability failed.
- A denied append is worse than one lost row: it **silently disables the shadow-mode accuracy programme** (nothing to join a later human verdict onto), and it's invisible on the happy path.
- `record_human_verdict` is **unregistered / stale** — some sessions can't call it at all; the host auto-stamps the human verdict from the `pr_review` webhook keyed by delivery id. Don't build a two-step destructive+repair mitigation on a tool you haven't confirmed is available this session.
- A decision is **not delivered until BOTH `record_decision` AND the `[Approval Decision]` message fire** — a `synchronize` push can preempt the turn and strand the prior revision as uncommitted artifacts.
- **Artifacts don't travel by path.** A file you name in prose lives only on your filesystem; use `send_file`. "Copied to X" is delivery only if the recipient confirms X on *their* edge.
- **Never instruct the pr-approver to post to GitHub** — it has a hard no-GitHub-write invariant and will (correctly) refuse, costing a round-trip.

## The record_decision false-success family (measured 7×, one day)

The single most-repeated observation in this batch: `record_decision` prints success while the host denies the write. It reproduced on slang#12446 [[record_decision returns success while the host denies the append]](../learnings/1786436608459-approver-infra-abstain-record-decision-returns-dec.md), slang-rhi#598 [[the tool string is not proof of a write]](../learnings/1786436642533-approver-infra-abstain-record-decision-returns-dec.md), slangpy#1099 [[reports success in-band while the host denies]](../learnings/1786437439516-approver-infra-abstain-record-decision-reports-suc.md), slang#12439 [[never treat the tool reply as proof the row exists]](../learnings/1786455704768-approver-infra-abstain-record-decision-returns-a-s.md), slangpy#1100 [[no row is persisted]](../learnings/1786463030860-approver-infra-abstain-record-decision-returns-a-s.md), and slang#12449 [[echoes success but host denies]](../learnings/1786466412759-approver-infra-abstain-record-decision-echoes-succ.md).

The mechanism is identical every time and worth stating precisely: two different surfaces report on one write. The **tool result** is composed by the MCP shim on the call path, before and independent of the host capability check. The **host** enforces `APPROVAL_LEDGER_WRITERS` (an allow-list of agent groups) and reports the denial **asynchronously, framed as context** — not as a tool error — which is exactly the shape that gets read past. On slang-rhi#598 the author made three `record_decision` calls that all returned "Decision recorded" and only the last surfaced a visible denial; with no read access to the ledger, the earlier two were unverifiable. That is the generalizable warning: **every "recorded" reported upstream in a misconfigured environment is an unverified claim about a side-effect in another process.**

The transferable rule spans past this one tool: *does a success string come from the layer that INITIATES the write, or the layer that PERFORMS it?* An affirmative reply from the initiator is not evidence from the performer — the same shape as a green `else` branch reached by fall-through, where nothing had to succeed for the string to print [[a measurement pipeline that cannot be read back cannot be trusted to be recording — probe the sink, not the send]](../learnings/1786436642533-approver-infra-abstain-record-decision-returns-dec.md). Detection: scan for the denial vocabulary (`denied`, `not configured`, `capability`, `WRITERS`); read any notification arriving right after a write as being *about* that write; and when there is no read-back path, downgrade the word from "recorded" to "submitted."

**Response discipline** (consistent across all six): do not retry the identical call — a capability denial is not transient, and the ledger is append-only / first-write-wins per `(repo, pr, commit_sha)`, so a re-submit is safe (a harmless no-op) *only once the capability exists*, and a *different* decision for the same commit is refused rather than silently overwritten. Report the gap as a named blocker with the config key so the operator can act; preserve the full row locally (one author wrote `work/<pr>-<sha>/LEDGER-WRITE-DENIED.md` carrying decision, reason_code, clauses, critique verdicts, human-verdict join). Crucially, this is a **persistence-layer defect, not a PR property** — it must not be laundered into an `ABSTAIN_INFRA` *about the PR*; the PR's own decision stands on its artifacts.

Why it's urgent rather than cosmetic: because no row lands, the later human-verdict **join cannot happen** for that `(repo, pr, commit)`. Every decision made while the config is unset is lost to accuracy measurement — precisely the signal shadow mode exists to collect — and the loss is silent by construction. A shadow-mode programme that records nothing is a strictly worse failure than the misclassification debates it exists to settle.

## Human-verdict stamping is stale/absent — don't depend on a two-step repair

`record_human_verdict` **worked on 2026-08-03** (restored an `APPROVED` stamp after a row replacement) and **failed on 2026-08-11** with `No such tool available` — dropped from the allowlist by an intervening restart [[record_human_verdict vanished from the approver allowlist mid-flight]](../learnings/1786454952360-approver-infra-abstain-record-human-verdict-vanish.md). This breaks a previously-published mitigation ("re-record, then immediately re-stamp"): anyone following it now does the destructive half and silently fails the repair, leaving a *clean-looking* but wrong correction. The general rule: **a mitigation that depends on a second tool is only as good as that tool's current availability, and availability is per-session state, not a durable fact** — probe the repair tool before beginning any destructive+repair sequence. A more recent join confirms the host now **auto-stamps the human verdict from the `pr_review` webhook keyed by delivery id**, so the SKILL.md instruction to call `record_human_verdict` is stale; but note the compounding failure — if the original `record_decision` was denied, **there is no row to stamp onto**, so the ledger outage silently drops the calibration join too [[a human APPROVE at the ABSTAIN_INFRA head scores the recovered read]](../learnings/1786497895197-approver-human-disagreement-a-human-approve-at-the.md). Belt-and-braces that survives regardless: embed the human verdict inside the correction payload's own text.

## Decision atomicity: record + report is the only commit boundary

On slang-rhi#828, revision R0 was derived as BLOCK, DECISION_REVIEW-approved, with `decision.md` and a memory child written — but a `synchronize` push (R1) arrived as a new turn *before* `record_decision` or the `[Approval Decision]` message fired, so R0 has no ledger row and no upstream report [[a decision isn't delivered until record_decision + [Approval Decision] both fire]](../learnings/1786461685033-approver-process-a-decision-isn-t-delivered-until-.md). The lesson: writing `decision.md` / a memory child / passing critique is **not** "done." The pipeline has no commit boundary until both the ledger append and the delivery message fire; everything before is uncommitted work a new webhook can preempt, and a per-`(repo,pr,commit)` ledger means the new revision's turn does not inherit or flush the old one. Order every decision investigation → `decision.md` → memory → `record_decision` → `[Approval Decision]`, treat record+report as the atomic done, and on a resumed/preempted turn grep the transcript for whether `record_decision` fired for the prior head before assuming delivery — **a turn-level interruption is evidence about the turn, not the work** (the same session noted a Devin subagent that died on a 400 mid-run whose artifacts had already landed on disk — read them, don't treat the crash as a skip).

## Artifacts and GitHub: paths don't travel, and the approver never posts

Two delivery traps close the loop. First, **"durable copy" is ambiguous and only one reading is the point.** An approver filed a learning that a denied ledger write means the artifact must travel by `send_file`, not a path in prose — then within hours, on the same PR, wrote `join.md`, copied it to `/workspace/agent/approver-decisions/`, and reported it as durable; the peer replied it wasn't on their edge [[I re-committed the delivery error I had just written the learning about]](../learnings/1786454258490-approver-critique-mustfix-i-re-committed-the-deliv.md). The copy *felt* like durability because it produced a visible artifact, and "durable" reads as both *survives cleanup* and *readable by someone else* while only the second was meant. The fix is to **wire the rule to a decision point, not an error signal**: "BEFORE reporting any artifact as available to a peer: did I call `send_file` for this exact file, this turn?" — a rule that fires only on a failure message will not fire on the success path that still misses the goal, and `approver-decisions/` was a *peer-named* path adopted onto one's own filesystem (adopting a peer's path does not adopt their filesystem). (This referential dimension is developed further in the verification-discipline page.)

Second, **never route a "post the verdict to the PR" instruction to a `*-pr-approver`** [[never instruct the pr-approver to post to GitHub]](../learnings/1786489442083-never-instruct-the-pr-approver-to-post-to-github.md). The approver's hard invariant is: it never writes to GitHub (no comments/reviews/labels) and never dispatches another coworker. A posting instruction arrives as routing context, does not grant that authority, and the approver correctly refuses — costing a round-trip (measured on slang#12477, where it also abstained on `CLAUSE_FAIL:tier_eligible` for a 14,344-line diff). If a public footprint is wanted, route posting to the reviewer/fixer tier; for a shadow-mode ABSTAIN on an already-ready human PR, no forced comment is usually needed — shadow mode is non-gating telemetry and the production review bot's own review is the public footprint.
