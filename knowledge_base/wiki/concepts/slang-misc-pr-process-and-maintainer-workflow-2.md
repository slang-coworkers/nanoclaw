# Slang Issue Lifecycle, Draft-PR Footprint, and Maintainer-Decision Reversals

## TL;DR

- `Closes #N` / `Fixes #N` in a PR body does NOT excuse a human-visible issue comment while the PR is a DRAFT — a draft neither auto-closes the issue nor surfaces the link; keep the issue carrying the trail until ready-flip.
- A discharged blocker line is actively wrong, not just stale — refresh a published footprint on every state change; PATCH your prior comment in place rather than stacking a new one (some bot tokens are create-only → ask the owning tier).
- Audit a PR body for auto-close keywords UNANCHORED + case-insensitive, both reference forms, against the LIVE body — the full set is close/fix/resolve (+s/d) adjacent to `#N`; backticks and a trailing `'s` do NOT exempt a match. A check that cannot fail is not a check.
- A maintainer's "create a PR" is SCOPE approval, not DESIGN approval — clean reviews don't change landing probability; keep the branch cheap and expect they may re-implement at a deeper layer.
- Verify a replacement PR's closing reference actually resolves — a one-digit-off `Fixes #N` (pointing at a PR, not an issue) links nothing and leaves the issue open after merge.
- CMake flag-override asks are usually an INITIALIZATION-layer problem (`*_FLAGS_<CONFIG>_INIT`, no FORCE), not a flag-ordering one — the general mechanism beats a per-flag "detect and skip."
- An MCP read tool returning empty is ambiguous between "nothing" and "broken" — verify with a control query that MUST return data before reporting all-clear. `slang-mcp github_list_issues`/`github_get_discussions` return false empties; `merged_at` is the broken field, not `is:merged`.
- `running` + fresh `last_active` is NOT evidence a session did anything — count its outbound rows; `out==0 && in>=1` is an unconditional awaiting_us.
- A maintainer's by-design ruling can reverse on VERIFIED counter-evidence — record the RE-OPEN trigger when parking, verify-at-HEAD before relaying, surface back to the ruling maintainer with options, keep merge maintainer-gated.

This page covers the *issue-facing* side of the Slang workflow: keeping an issue's human-visible footprint correct while its PR is a draft, auditing PR bodies for auto-close keywords, distinguishing a maintainer's scope go-ahead from design approval, treating empty MCP reads as ambiguous rather than all-clear, and reversing a by-design ruling on verified counter-evidence. Companion to [[wiki/concepts/slang-misc-pr-process-and-maintainer-workflow.md]] (PR/review mechanics).

## `Closes #N` Does NOT Excuse an Issue Footprint While the PR Is a Draft (2026-08-04 fold)

A PR body's `Closes #N` / `Fixes #N` does **not** remove the need for a human-visible 5-bullet comment on the originating issue **while that PR is still a DRAFT** — keep the issue carrying the trail until the ready-flip. The auto-close, and the "the PR is now the public artifact, so the issue comment is redundant" reasoning, only take effect once the PR is non-draft: a draft PR neither auto-closes the linked issue nor surfaces its closing link as a prominent public artifact, so a human landing on the issue sees nothing — exactly the silent-chain failure the draft-footprint rule exists to prevent. Observed on slang-rhi#805 → draft PR #806: after a maintainer approved the draft, the suggestion that the issue footprint was "moot given `Closes #805`" was wrong and was corrected by the triage tier. **Corollary — a discharged blocker line is *actively wrong*, not merely stale:** a published footprint still asserting "awaiting maintainer confirmation of the intended wording" *after* the maintainer approved misinforms every subsequent reader, so refresh the footprint on state change rather than treating it as post-once. Edit-in-place hygiene: if your bot was the last commenter, PATCH the existing comment (`repos/<owner>/<repo>/issues/comments/<id>`) instead of stacking a new one — zero new notification noise, no duplicate. Some bot tokens are **create-only** on issue comments (PATCH/DELETE 403); when so, do **not** self-post a second comment (the duplicate would be permanent) — ask the tier that owns the surface (usually triage, as last commenter) to update theirs ([Closes #N does not excuse an issue footprint while the PR is a draft](../learnings/1785751816891-closes-n-does-not-excuse-an-issue-footprint-while-.md)).

**Auditing a PR body for auto-close keywords: an anchored grep gives a false pass.** When a PR must *not* auto-close an issue (the functional fix landed in a sibling PR; the disposition is the maintainer's call), every GitHub closing keyword has to go — and `grep -cE "^Closes #12110"` reported "0 `Closes` lines" while the live body still carried two live triggers: `…which fixes #12110's symptom…` (the trailing `'s` does **not** prevent matching, and it isn't at line start) and `Please resolve #12110 against #12263` (`resolve` is in the keyword set too). A section heading written as ``**On `Closes #12110`.**`` also arms it — **backticks do not exempt anything**. The full keyword set is `close`/`closes`/`closed`, `fix`/`fixes`/`fixed`, `resolve`/`resolves`/`resolved`, each adjacent to `#N`, `owner/repo#N`, or a full issue URL, optionally colon-separated. Audit **unanchored, case-insensitive, both reference forms**:

```bash
grep -n -i -E "\b(close[sd]?|fix(e[sd])?|resolve[sd]?)\b[[:space:]]*:?[[:space:]]*#[0-9]+" body.md
grep -n -i -E "\b(close[sd]?|fix(e[sd])?|resolve[sd]?)\b[[:space:]]*:?[[:space:]]*[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+#[0-9]+" body.md
```

…and run it against the **live** body (`gh api repos/<owner>/<repo>/pulls/<n> --jq '.body'`), since a local draft can be stale or a `PATCH` can land differently than intended. Rephrase rather than delete the meaning ("addressing the symptom of #N", "the disposition of #N is yours to make explicitly", "Refs #N"). Leaving one trigger means the issue auto-closes on merge and silently overrides an explicit "please decide this yourself" ask — the opposite of the intended outcome, invisible until after merge. Same class as a vacuous FileCheck `CHECK-NOT`: **a verification that cannot fail is not a verification** — when checking for the *absence* of something, use the broadest pattern that could match, read the authoritative source, and where possible confirm the check *can* fail against a known-positive input ([auditing a PR body for auto-close keywords: anchored grep gives a false pass](../learnings/1785756201206-auditing-a-pr-body-for-auto-close-keywords-anchore.md)).

The mirror-image check applies to **someone else's** PR: when a maintainer's replacement PR claims to fix your issue, verify the closing reference resolves. #12324's body said `Fixes #12233` — one digit off, and #12233 is an unrelated closed **PR**; closing keywords only auto-close *issues*, so it linked nothing and #12223 would have stayed open after the merge (confirmed via the #12223 timeline: no `connected` event, only our own cross-reference). Flag it as a heads-up; never edit their PR ([a maintainer's "create a PR" is not acceptance of your shape](../learnings/1785767481211-a-maintainer-s-create-a-pr-is-not-acceptance-of-yo.md)).

## A Maintainer's "Create a PR" Is Scope Approval, Not Design Approval (#12223)

**A go-ahead answers "should this be fixed, and roughly in which direction" — not "is your implementation the one that lands."** On slang#12223 (`-Og` in Debug builds broke debugging, a regression from PR #12140) we did the feasibility work, posted an offer with two options, and skiminki-nv — the author of the regressing PR — replied *"@nv-slang-bot Create a PR for Option 2"*. We implemented Option 2 exactly as scoped, opened draft PR #12234, and ran three reviewer passes, all clean. A week later he **closed it unmerged** (*"It doesn't quite seem to be the right fix. PR #12324 is the next attempt"*) and wrote his own fix at a deeper layer. **Clean reviews do not change landing probability** — treat maintainer authorization as scope approval, keep the branch cheap, and expect the maintainer may re-implement. When your PR is closed in favor of theirs, don't re-litigate: verify their replacement actually closes the issue, hand over anything you verified they'd want (edge cases, test matrix), reap your branch/worktree, and close out the chain ([a maintainer's "create a PR" is not acceptance of your shape](../learnings/1785767481211-a-maintainer-s-create-a-pr-is-not-acceptance-of-yo.md)).

The *why* is a reusable design lesson, not a process failure — **direction adopted, shape rejected** ([#12223 -Og debuggability: maintainer took the DIRECTION, rejected our SHAPE](../learnings/1785767658697-12223-og-debuggability-maintainer-took-the-directi.md)). Ours: `-Og` is injected as a *target-level* option (`cmake/CompilerFlags.cmake:196`, `target_compile_options(… $<$<CONFIG:Debug>:-Og>)`), which lands on the compile line *after* `CMAKE_CXX_FLAGS` (where env `CXXFLAGS` goes) and `CMAKE_CXX_FLAGS_DEBUG`, so by last-`-O`-wins the injected `-Og` clobbers a user's `-O0` — we conditionally *skipped* the injection when the user already supplied an `-O` token (~3 lines, works, but **suppresses a symptom of the flag ordering**). His #12324: seed `CMAKE_C/CXX_FLAGS_DEBUG_INIT` **before `enable_language()`**, so because `cmake_initialize_per_config_variable` sets the cache vars *without* `FORCE`, any user/preset/toolchain value simply **replaces** the default — `CXXFLAGS`/`CFLAGS` are then honored **generally**, not just for `-O`, and there is no appended flag left to suppress. Transferable: **CMake flag-override asks are usually an initialization-layer problem, not an ordering problem** — if you find yourself writing "detect what the user passed and skip our own flag," ask whether the flag should be a *default* (`*_FLAGS_<CONFIG>_INIT`, no `FORCE`); the general mechanism beats a per-flag special case and generalizes for free. Compile-line order is fixed and worth knowing: `CMAKE_CXX_FLAGS` → `CMAKE_CXX_FLAGS_<CONFIG>` → target `COMPILE_OPTIONS`, so env `CXXFLAGS` lands in the *first* slot and can **never** win a last-wins fight against anything appended later (verified empirically on Ninja Multi-Config/cmake 3.25/GCC 12: `CXXFLAGS='-O0 -g3'` + target `-Og` ⇒ `-O0 -g3 -g -Og`). Also `CMAKE_CXX_FLAGS_DEBUG` is just `-g`, **not** `-O0 -g` — the `-O0` is the compiler's implicit default, not a token CMake emits; an in-tree comment claiming otherwise (`CompilerFlags.cmake:180`) propagated into two of our memos before a probe caught it, so read the cache, not the comment. Two process points that worked: in the PR description **name the layer you chose and the alternatives you rejected, with reasons** (that invites the "wrong layer" objection during review rather than after), and note that framing the trade-off *empirically* dissolved a zero-sum fight — two core members were opposed (the reporter wanted `-O0`; #12140's author called `-O0`-by-default a showstopper), and reproducing the compile line to show that an override satisfies **both** moved it from "whose default wins" to "make it overridable," which is when the maintainer asked for a PR. For build-system/config fixes generally, ask whether the bug is in the *value* or in *how the value gets initialized*.

## An MCP Read Tool Returning Empty Is Not Evidence of Silence

`slang-mcp`'s `github_list_issues` returns `total_count: 0` **unconditionally** — verified against all three repos (`shader-slang/slang`, `slangpy`, `slang-rhi`), with and without a `since` filter, so it is not a filter artifact — and `github_get_discussions` likewise returns zero discussions **and** zero categories for `shader-slang/slang` while Discussions are demonstrably active. Both fail **silently**, producing a confident "nothing new" report: on the day this was found, a daily sweep built on `github_list_issues` hid **4 newly-created slang issues** (including an SS-class silent-wrong-value bug) plus 10 more untriaged ones. Workarounds: `github_search_issues` with an explicit query (`repo:shader-slang/slang is:issue is:open created:>=2026-08-01`) returns real, complete data; fall back to a web fetch of `/discussions`. Third correction, in the other direction: a prior session recorded "`is:merged` is broken, use the REST pulls/commits API" — **that conclusion was wrong and must not be carried forward.** Re-verified, `type:pr is:merged closed:>=2026-07-31` returned 12, `is:unmerged` returned 1, plain `closed:` returned 13 — exact complements, mutually corroborating. What actually misleads is that **`merged_at` is `null` on every search result, including confirmed-merged PRs**, which is almost certainly what produced the "is:merged is broken" belief. **Rule: determine merge state from the `is:merged`/`is:unmerged` filters (and/or the auto-close via `Fixes #N`), never from `merged_at`**; to be certain about a single PR, spot-check that a file it added now exists on the default branch. General lesson: an MCP read tool returning empty is ambiguous between "genuinely nothing" and "tool is broken," so for any report where empty means all-clear, **verify the tool is alive with a control query that MUST return data** — e.g. widen the window to 30 days — before believing the empty one. Same shape as `#slang-support`/`#slang-support-bot` reads coming back empty three days running while sibling channels read fine (a read-scope gap, not genuine silence) ([slang-mcp `github_list_issues` and `github_get_discussions` return FALSE EMPTIES; `merged_at` is the broken field, not `is:merged`](../learnings/1785744880116-slang-mcp-github-list-issues-and-github-get-discus.md)).

The same "silence is not evidence" failure has a chain-level form: **a maintainer's triage request can sit unanswered for weeks behind a container that looks perfectly healthy.** On slang #8306 and #8785 `jkwak-work` pinged `@nv-slang-bot` for triage on 2026-07-18; both webhooks routed correctly and a triager session was created for each, yet **17 days later both were completely unanswered** — no bot comment on either issue, and each owning session held exactly **one message (the inbound) and zero outbound**, confirmed on two independent instruments (`ncl sessions messages --limit 200` and the GitHub reader, where jkwak's request was still the last comment). Every existing guard missed it: `container_status` was **`running`** on both, so any liveness check keyed on the container read healthy — the container was up, it simply never produced a turn; `last_active` was **fresh** (hours old), because the session row's timestamp advances on *host-side* touches, so a by-us clock computed from session rows looked current while the true last outbound was **never**; and with no PR and no disposition the chains were invisible to every PR-shaped or state-shaped filter. **The rule: `running` + recent `last_active` is not evidence a session has done anything — count its outbound rows.** `out == 0 && in >= 1` on the owning session is an unconditional `awaiting_us`, independent of container status, `last_active` and the stale window, and it is a *stronger* stuck signal than any silence threshold because there is no prior output to measure silence against; treat it as a special case, never feed a zero denominator to a ratio. Generalizes past this fleet: **when a health metric is a timestamp maintained by someone other than the worker, it measures the maintainer, not the work** — prefer a counter of artifacts the worker itself produced ([a maintainer triage request can sit unanswered for weeks behind a running container with zero outbound](../learnings/1785802554126-a-maintainer-triage-request-can-sit-unanswered-for.md)).

## Surfacing Verified Counter-Evidence Can Reverse a By-Design Ruling (2026-07-28 fold)

A maintainer's by-design ruling is authoritative but not immune to new evidence. On slang#12226 (bindless `ConstantBuffer<T>` emitted StorageBuffer instead of Uniform), jkwak-work first ruled it by-design citing an #11483 constraint; the reporter rebutted with a glslang `GL_EXT_descriptor_heap` shader showing a Uniform heap buffer indexing a nested array accepted by spirv-val. The full arc — external report → reproduced → by-design ruling → substantive rebuttal → our fixer's investigation confirmed the mechanism → surfaced back to the maintainer → **maintainer retracted his own ruling ("I got it wrong on #11483"), prototyped the fix, greenlit + self-merged #12256** — turned a terminally-closed bug into a shipped fix. The reusable rules: (1) record the RE-OPEN trigger explicitly when you first park ("flag fails / fresh substantive input → RE-OPEN") so future-you acts instead of no-op'ing a "looks done" chain; (2) **verify the counter-evidence yourself at HEAD before relaying it** — relaying an unverified refutation to a maintainer as fact loses credibility; (3) neither silently accept NOR unilaterally overturn — surface the verified refutation back to the maintainer who made the call, framed as their decision to revise, with options (full fix / narrow interim / hold), and @-mention them; (4) carry hedges honestly (a DeepWiki "storage classes must match" claim was flagged as hypothesis then verified false against the spec, and an earlier public "infeasible" statement corrected in place). Guardrail that held: bot opens the PR draft/creation-only; ready+merge stayed maintainer-gated, and the maintainer self-merging fully satisfies it — "please make a PR" authorizes creation, not auto-merge ([surfacing verified counter-evidence to a maintainer can reverse a by-design ruling — don't silently accept OR unilaterally overturn](../learnings/1785278991541-surfacing-verified-counter-evidence-to-a-maintaine.md)).

## A reporter's fix is a claim to test, and an upgrade needs a release that contains it (2026-08-13 fold)

Two reporter/advice-facing rules. **A reporter's suggested fix is a claim to test, not adopt** — even from a repo MEMBER who root-caused correctly and "said it worked locally": slang#12440's `getStringHash`-on-a-non-literal SIGSEGV came with a named two-site fix (swap the unchecked `getStringLit()` C-cast for `as<IRStringLit>(getOperand(0))`), but building it is what reveals whether the two-line change rejects code that compiles correctly today; verify the reporter's patch against the repro and the surrounding surface before endorsing it ([A reporter's suggested fix is a claim to test, not adopt: build it — slang #12440's two-line fix rejected code that compiled correctly](../learnings/1786308399056-a-reporter-s-suggested-fix-is-a-claim-to-test-not-.md)). **Before advising "upgrade," verify a release containing the fix exists** — on a missing-SPIR-V-`NonUniform` miscompile, the fix had merged so "upgrade or build master" was advised, but the newest/latest release (`v2026.14.1`, 2026-07-30) predated the merge, so only "build master" was actionable; check `/releases/latest` (and `/releases?per_page=5`) against the fix's merge date before telling a user to upgrade ([Before advising an upgrade, verify a release containing the fix exists](../learnings/1786312909042-before-advising-an-upgrade-verify-a-release-contai.md)).
