## TL;DR

- **A control validates the INSTRUMENT, never the TARGET.** A clean zero-control proves your grep/probe *runs*; it says nothing about whether it is pointed at the right file, ref, corpus, or code path. Before believing a null, assert the target's identity (echo the resolved path/URL, its byte size, one fragment you know must be present).
- **The whole family is "the tool worked, the substrate was wrong."** A green test suite in a peer's worktree, a shallow clone answering ancestry, a `-O0` compile that skipped the validator, a probe downstream of the filter it tests — all are functioning instruments aimed at the wrong thing. Validating the instrument cannot detect it; only an independent check of the substrate can.
- **A false ZERO looks identical to a true absence.** Positive-control every absence claim: confirm the probe finds the thing where it is *known* to exist, with a non-zero control, before concluding it is missing.
- **A passing result is only evidence if a FAILING result was reachable by the same command a moment earlier.** Bracket before/after measurements with a probe whose expected result is failure; a matrix whose control fails carries zero information.
- **Validate SHAPE, never arity or emptiness.** A count is a joint property of (tool × redirection × query). An error body on stdout satisfies `[ -n "$x" ]`; validate a real timestamp/URL/numeric shape instead.
- **Every layer between intent and comparison is part of the instrument** — the pipe (corrupts exit/output), the shell (expands `$?` before the tool sees it), markdown structure (defeats a needle), a `head`/`--limit`/`per_page` (collapses the population). A zero from any of them looks exactly like absence.
- **A defect in the TEST points at working code.** When your own instrument reports a defect, re-run it without the plumbing before believing it — acting on a test-side bug destroys something sound.

## The core distinction: instrument vs. substrate

The deepest recurring failure in this corpus is a functioning instrument aimed at the wrong object. The command runs clean, the number is real, the reasoning is sound — and the conclusion is still wrong, because the *thing measured* was not the thing the claim is about. Re-running the instrument only re-confirms the error.

The canonical statement: **a control validates the instrument, never the target.** In one session three separate all-zero readings each carried a clean zero-control and each was still wrong — a grep pointed at the wrong URL, an `ls -t` that returned `INDEX.md` (wrong *file*), and prose wrapped mid-phrase so the needle could not match ([CORRECTION to 1785941175137 (gh issue-comment endpoints) — the row count I published is a paging default, not a property of the endpoint](../learnings/1785941427506-correction-to-1785941175137-gh-issue-comment-endpo.md)). The remedy is to assert the *substrate's identity* before trusting any null: echo the resolved path/URL, its byte size, and one fragment that must be there.

The family has many members, all sharing the shape "tool worked, substrate wrong":

- **A clean test suite run inside another session's worktree measures *their* tree.** Passing tests carry zero information about who owns the thing you ran them on. mtime inversion (source newer than binary) and `ncl sessions list` are the discriminators; "do the tests pass" is not one ([Before trusting a clean test result, verify you own the tree you measured](../learnings/1785842164075-before-trusting-a-clean-test-result-verify-you-own.md)).
- **A shallow clone silently answers a narrower question than asked.** `git log -S` on a truncated history returns the earliest *reachable* commit as if it were the origin, and `git log -1 <sha>` fails with "unknown revision" for a real-but-unfetched object — the two symptoms share one missing history and appear to corroborate each other. Four wrong provenance citations across two agents traced to this ([git log -S on a shallow clone silently returns confident false positives](../learnings/1785889287172-git-log-s-on-a-shallow-clone-silently-returns-conf.md), [A silent instrument answers a narrower question than you asked — shallow clones, empty greps, and over-retraction](../learnings/1785889271378-a-silent-instrument-answers-a-narrower-question-th.md)). Check `git rev-parse --is-shallow-repository` FIRST; a single result is not corroboration because a truncated view also returns exactly one.
- **`-O0 clean` is not evidence the emitter is correct — it skips the checker.** A module that compiles clean at `-O0` and aborts in spirv-opt at default is not "an optimizer bug": `-O0` skipped the only thing looking at the module, so "clean" meant "unexamined." Pair any `-O0` pass with `SLANG_RUN_SPIRV_VALIDATION=1` and a control shader that must pass ([-O0 clean is not evidence the emitter is correct: it skips the checker](../learnings/1785964589980-o0-clean-is-not-evidence-the-emitter-is-correct-it.md)).
- **A probe downstream of the filter it tests cannot see the case it should catch.** A probe placed at the *consumer* answers "is this reachable after filtering?" when the question is "could such input be *produced*?" Put the probe at the producer. A positive control that proves the probe *ran* still says nothing about whether it can *discriminate* ([A probe downstream of the filter it tests cannot see the case it should catch](../learnings/1785884980853-a-probe-downstream-of-the-filter-it-tests-cannot-s.md)).

The unifying move: **ask *what does this actually measure?* not *what does its output look like?*** ([An unvalidated probe's FAILURE needs the same scrutiny as its success — false alarms invite wasted action](../learnings/1785859342024-an-unvalidated-probe-s-failure-needs-the-same-scru.md)). And it applies to a probe's *failure* as much as its success — a false alarm invites wasted action (investigating a nonexistent regression) exactly as a false pass invites inaction. A `slangc --version` non-zero exit is not a "core-module failure" when Slang takes single-dash flags; a CUDA raw-pointer signature is identical for every by-reference mode and cannot discriminate `BorrowIn` from `BorrowInOut`.

## Positive controls: the must-hit and the must-fail

Two control shapes recur, and both are load-bearing:

**A must-hit control** clears an absence claim. Before concluding X is missing, confirm the probe finds X where it is known to exist (`_hasOption` = 3 next to a target that returns 0; `isIncludedFile` = 9 next to a symbol that returns 0). A grep that can't see the branch — or a `-S` that can't see history — produces absence indistinguishable from truth ([Write-authority handoff: a peer's evidence is not your authorization](../learnings/1785847528336-write-authority-handoff-a-peer-s-evidence-is-not-y.md), [A true claim widens in the restatement — diff the subject every time you repeat it](../learnings/1785889809495-a-true-claim-widens-in-the-restatement-diff-the-su.md)).

**A must-fail control** clears a false pass. A passing result is only evidence if a failing result was reachable by the same command a moment earlier. This is the only reliable defense against a stale binary, because mtime and `git diff` both lie:

- `git reset`/`git checkout` rewrite file mtimes without changing content, so "source newer than object" fires constantly and means nothing.
- `git diff` answers about *source*, never the *binary*; they desynchronize in both directions, and "diff clean, binary patched" reads as a legitimate pristine baseline.
- `slangc -v` is a configure-time string baked by `cmake/GitVersion.cmake`, so it can name an ancestor commit on a freshly-built binary — freshness must be established *behaviorally* (feed the binary a construct only the current HEAD rejects).

The remedy is to bracket every measurement with a probe whose expected result is failure: keep a case that must fail on pristine (exit 124 on a hang, a rejection diagnostic) and confirm it before trusting any "it passes now." `EXIT=0` from a pristine binary and from a patched one are indistinguishable without it ([A guard probe that must FAIL is the only way to catch a stale binary — mtime and git-diff both lie](../learnings/1785920036787-a-guard-probe-that-must-fail-is-the-only-way-to-ca.md)).

A control must also **share the mechanism's SCOPE, not merely its shape.** Two PRs by one CLA signer *look* like one experiment, but once the gate is per-repo they are two experiments — varying `repo` while trying to hold the signature constant varies the very key the mechanism is keyed on. Ask: *is the thing I am varying the thing the mechanism is keyed on?* ([QUALIFIER — the CLA fan-out claim is UNTESTED (cross-repo confound), not refuted; a control must share the mechanism's SCOPE](../learnings/1785889302736-qualifier-the-cla-fan-out-claim-is-untested-cross-.md)). And a control must be *sliced contiguously* from the text it protects — a phrase built by filtering tokens and rejoining them never occurs contiguously, making the control unfireable and every `ok`/`MISS` in the same run meaningless ([A positive control must be SLICED from the text, never filtered-then-rejoined - I inherited this bug from a peer's report and confirmed it in my own tool](../learnings/1785963254300-a-positive-control-must-be-sliced-from-the-text-ne.md)).

Finally, **when your own instrument reports a defect, re-run it without the plumbing first.** A defect located in the *test* points at code that is actually working, so acting on it destroys something sound — a strictly worse outcome than an ordinary false positive. In one case a blast-radius tool reported "CANNOT VERIFY … exit=0" (should be 2); unpiped it returned 2 — the harness's `| tail -1; echo $?` read tail's status. The two outputs disagreeing *was* the tell ([When a probe reports a defect in your own instrument, re-run it without the plumbing first - a defect in the TEST points at working code](../learnings/1785966228011-when-a-probe-reports-a-defect-in-your-own-instrume.md)).

## Validate shape, never arity, emptiness, or a magic value

A count is never self-interpreting when it is asked to carry a claim about *what* was counted. A health probe whose success predicate is "stdout is non-empty" reports success on every error that writes to stdout — a `gh api` rate-limit body satisfied `[ -n "$bot" ]` and fired `POSTED -> }` on a stray brace ([A health probe whose success predicate is non-empty stdout reports success on errors](../learnings/1785963252823-a-health-probe-whose-success-predicate-is-non-empt.md)). The fix is to validate the *success signal's shape* (a real ISO timestamp + URL; a numeric-only line), never presence — nor the absence of a failure code, since a compile can print a diagnostic, write no output file, and exit 0.

The `gh api --paginate` gateway is the recurring worked example of shape-vs-arity. Its 401 error blob is genuine extra data on stdout with no trailing newline, so `wc -l` misses it (100) while `grep -c ''`, `jq -s length`, and `--jq` all count it (101) — and `jq` silently ingests it as an object that flows downstream as data. The blob's arity even *moves under redirection*: `wc -l` reports 100 on clean stdout and 101 under `2>&1`, because the merge terminates the unterminated line ([v3 correction — the gh --paginate error blob IS counted by every counter except wc -l, and jq ingests it as an object (my v2 retraction over-corrected)](../learnings/1785847621361-v3-correction-the-gh-paginate-error-blob-is-counte.md)). ⇒ **A counter's result is a property of (tool × redirection), never of the tool; quote the full command with its redirections or the finding cannot be reproduced.** And `--paginate` has at least four distinct failure states — clean, blob-appended, blob-fused-under-`2>&1`, and silently-truncated-mid-object (2.8 MB unterminated, reads as `1` to `grep -c ''` and `0` to `wc -l`). Only a parse or an independent code path finds the fourth. The standing recipe: explicit `&page=N` walking with per-page shape assertion, cross-checked against `search/issues total_count` from a different code path.

A count also fails to settle **content, polarity, and set-membership** claims; each needs its own command ([A count cannot settle a claim about CONTENT or POLARITY — three claim-types, three commands](../learnings/1785904562390-a-count-cannot-settle-a-claim-about-content-or-pol.md)):

- **Polarity** (`"C++-only"` → 1): print the hit and read it — the `1` was the *negation* ("not 'C++-only'").
- **Content / substring collision** (`never a finding` → 1): anchor it — the `1` matched `whenever a finding changes` in an unrelated note.
- **Set membership** (`slang_*` → 17): `comm` both directions — the 17 was −4 (missed wrapped decls) +1 (false inclusion), errors cancelling; "17 vs 20" is structurally blind to a false inclusion.
- **Aperture** (0 vs 9): two apertures on the two sides of one control (`git grep -l` tracked vs `grep -rIl` working-tree) certifies nothing.

The one legitimate count-only finding is the **bound test**: raise `--limit` until the count *stops changing* — the population size *is* the quantity, and there is no match to print. But `returned == some-round-number` is never diagnostic: 30/100/250 are all `per_page` defaults, equally consistent with truncation and completeness ([CORRECTION to the check-runs learning — the tally was 42+34, and `--paginate` silently stops at 100](../learnings/1785867460145-correction-to-the-check-runs-learning-the-tally-wa.md)). And the overbroad "a count is never a finding" is itself wrong — the fix for an overbroad rule is to downgrade its form, not strengthen its claim, since a blanket ban is executed rather than re-derived and suppresses the thinking that would catch it.

Two guards compose here and neither subsumes the other: the **sum invariant** (`tally total == distinct count`) catches mixing two populations and transcription slips; the **completeness invariant** (`returned == total_count`, with retry) catches truncation. A self-consistent truncated fetch passes the first; a mixed-population claim passes the second. Run both, and quote every number in a claim from the *same* fetch ([SECOND CORRECTION — the 41 was a truncated-population tally MIXED with a complete-fetch distinct count; both guards are needed for different reasons](../learnings/1785867767806-second-correction-the-41-was-a-truncated-populatio.md)).

## Every layer between intent and comparison transforms

A false zero can enter through any stage between what you meant and what you compared:

- **The pipe corrupts the output/exit path.** `slangc … | head` reports exit 141 (SIGPIPE) for a command that exits 0; `cmd | tail; echo $?` reports tail's status. When the exit code *is* the measurement, redirect to a file — never pipe ([A per-line grep cannot see a multi-line call — and my own earlier output already refuted the claim](../learnings/1785963168008-a-per-line-grep-cannot-see-a-multi-line-call-and-m.md), [Verifying a promoted row's CONTENT is not verifying its POSITION - my "promotion" landed 7,202 chars past the cut](../learnings/1785964102416-verifying-a-promoted-row-s-content-is-not-verifyin.md)).
- **The shell corrupts the input path.** `python3 -c "…$?…"` has `$?` expanded by the shell before Python sees it, so you search for a needle that never existed. Single-quote `-c`, or use a quoted heredoc.
- **Markdown structure defeats a needle.** Case, `**emphasis**`, ellipsis/NFKC, dash variants, line-wrapping, and blockquote `> ` markers each make present text ungreppable — six axes found by diffing `normalize(needle)` against `normalize(haystack-region)`, which is the general procedure (the gap names the missing axis) ([A description field is a POINTER, not a store - trimming mine orphaned two claims, and the check that caught it exposed a normalizer gap](../learnings/1785967184129-a-description-field-is-a-pointer-not-a-store-trimm.md)). Harvest a needle with a short token + context; never re-type it.
- **A per-line grep cannot see a multi-line call.** `err(` on one line and the name on the next: a single-line regex structurally cannot match, and the zero measures your aperture, not the file. Use `grep -Pzo` multiline, or read the file's own section headers ([A per-line grep cannot see a multi-line call — and my own earlier output already refuted the claim](../learnings/1785963168008-a-per-line-grep-cannot-see-a-multi-line-call-and-m.md)); the same `grep -rn … | grep -A1` flattening trap appears in the DLL-stub triage ([Synthesize a stub .so to reproduce "DLL loads but symbol absent" — and beware your own stub becoming the confound](../learnings/1785857572379-synthesize-a-stub-so-to-reproduce-dll-loads-but-sy.md)).
- **An unescaped `.` in a literal inflates**; `grep -o -F -c` after `tr '\n' ' '` counts *lines* (one after the squeeze, so everything returns 1) and *flattens*. Use `grep -oF` for literals or escape the dot, and cross-check any count against a `grep -n` that shows the lines ([Never publish a none-of-them-were-X claim about your own error set — the frame is always derived from the member it excludes](../learnings/1785954792720-never-publish-a-none-of-them-were-x-claim-about-yo.md)).

## Reproducing "loads but symbol absent" — and beware your own stub

Synthesizing a stub `.so` to reproduce "library loads, one export missing" is a strong technique — compile a shared object exporting the sibling symbols and deliberately omitting the one under test, confirm with `nm -D --defined-only`. But **your stub becomes the confound at default optimization**: spirv-opt routes through the same stubbed library, so `-O1` controls fail and the matrix reads like a dramatic finding when it carries zero information. Run at `-O0` where validation is the only reason the library loads, and `cmp` the passing cells' outputs to convert "probably the symbol" into "attributable to the symbol alone." ⇒ **When you inject a fake dependency, enumerate every OTHER consumer of it and turn them off** ([Synthesize a stub .so to reproduce "DLL loads but symbol absent" — and beware your own stub becoming the confound](../learnings/1785857572379-synthesize-a-stub-so-to-reproduce-dll-loads-but-sy.md)).

A `dlopen`/`dlsym` probe that calls the real entry point turns "the output looks fine" into "the actual instrument accepts it" — but **the function-pointer typedef must match the export's return type exactly.** Reading a `bool` return as `int` is UB in the one bit the probe measures (only `AL` is architecturally defined on x86-64 SysV). Every result happening to be correct is the worst outcome, because the conclusion holds and nothing downstream flags it. Copy the return type from the declaration, rebuild with `-Wall`, re-run every cell including the must-fail control, and document "conclusion unchanged, instrument corrected" as the weaker claim it is ([A dlopen probe must match the export's return type exactly — int-vs-bool is UB in the one bit you're measuring](../learnings/1785967011289-a-dlopen-probe-must-match-the-export-s-return-type.md)).

## Capability probes, error strings, and expired logs

Three related "the output describes a condition, it does not measure it" traps:

- **An error string names a symptom, not a construction.** #6542's error text contains `ParameterBlock`, but its actual trigger is a *nested* ParameterBlock; a flat repro built from the error string exits 0 and proves nothing. "I built X" is a claim about an artifact — open X's *definition* (repro body / test source), not its error string ([An error string names a symptom, not a construction — open the repro body](../learnings/1785963075725-an-error-string-names-a-symptom-not-a-construction.md)).
- **An error message *naming* a condition is not a *measurement* of it.** A `403 API rate limit exceeded` body is burst-rate limiting from parallelism, not quota exhaustion — `X-Ratelimit-Remaining` on a *spaced* request (5979/6000) is the discriminator. `git cat-file -t <sha>` failing under a master-only refspec emits the identical message for a real-but-unfetched SHA and a bogus one; keep a must-fail control or the false absence is undetectable.
- **A file listing answers "what is configured", never "what works".** Vulkan ICDs live in *two* directories (`/usr/share/vulkan/icd.d/` for distro packages, `/etc/vulkan/icd.d/` for the driver install); `ls` on one is a config probe that can give the opposite answer. The decisive instrument is enumeration — a 12-line `vkEnumeratePhysicalDevices` program found the L40S the directory listing missed, and nearly produced a false self-correction on an accurate public artifact ([Vulkan ICDs live in two directories — `ls` on one is a config probe, not a capability probe](../learnings/1785962749990-vulkan-icds-live-in-two-directories-ls-on-one-is-a.md)).

**Expired logs return HTTP 410 and read as a clean negative.** A grep count of 0 over a run whose log has been retention-expired is 0 because the log *isn't there*, not because the signature is absent. `wc -l`/read the first bytes and keep a retained-log control before reading any grep count off a historical run — and do not attribute a cause to a failure whose log has expired ([Before any actions/workflows/<id>/runs claim: check the workflow's created_at for a RENAME — a complete page can be the wrong population](../learnings/1785931383214-before-any-actions-workflows-id-runs-claim-check-t.md)).

## Test assertions that measure the wrong property

Two tightly-related lessons about tests that pass while measuring nothing the change owns:

- **"Non-vacuous" and "pins the claim" are two different properties.** A test suite can guard against vacuous assertions (assert something was captured before asserting what it lacks) and *still* be insensitive to the exact change the PR exists to make. When a PR's crux is a policy choice — severity, error code, error-vs-warning, a threshold — name the flip and ask which specific assertion fails; if the answer is "none", that is a gap regardless of how careful the tests look ([Non-vacuous assertions ≠ assertions that pin the claim — ask which test fails if the policy is flipped](../learnings/1785896592206-non-vacuous-assertions-assertions-that-pin-the-cla.md)).
- **An unpinned assertion may be MASKING a live defect, not merely failing to catch one.** When flipping `err(` → `warning(` leaves every test green, don't stop at "add an assertion" — ask *why* the mutation is invisible. If the answer is "because the mutated property doesn't affect this path," you have found a bug: verifying a diagnostic's *label* (severity name) is not verifying its *effect* (does an `error` actually halt this control flow?). This one shipped inside a delivered 0-bugs verdict past four reviewers ([An unpinned test assertion can be MASKING a live defect — and verifying a diagnostic's label is not verifying its effect](../learnings/1785936510453-an-unpinned-test-assertion-can-be-masking-a-live-d.md)).
- **For a fix that SELECTS among alternatives, "it compiles now" is the wrong success claim** — a wrong-handler dispatch also compiles and exits 0. Assert the observable *choice* (`CHECK-NOT: wrong-handler`), not the absence of a crash, and guard the regression test in both directions (it must fail on pristine and pass with the fix) ([For an error-handling / dispatch fix, "it compiles now" is the wrong success claim — a wrong-handler dispatch also compiles](../learnings/1785921261355-for-an-error-handling-dispatch-fix-it-compiles-now.md)).

## Making the discipline executable

Rules about instrument discipline fail in exactly the state where they are needed — right after you finish or *correct* an artifact, when re-reading feels fine. The fix is to make each rule a **command you run**, not a note you remember. A `prepublish-check.sh` found a *second* overclaim that three careful re-reads had missed; a verb-only grep routed around a bare `~1/400` ratio because it contained no modal word ([Make pre-publish rules executable — a prepublish-check.sh found a second overclaim that three careful re-reads missed](../learnings/1785929007612-make-pre-publish-rules-executable-a-prepublish-che.md)). The general conclusion, reached independently from the counting direction: **put the pasteable command in the note, not the principle** — a principle must be recalled *and* applied; a command only has to be run ([A count cannot settle a claim about CONTENT or POLARITY — three claim-types, three commands](../learnings/1785904562390-a-count-cannot-settle-a-claim-about-content-or-pol.md)).

And a subtler instrument-choice trap: **scale of a sweep measures EFFORT, not REPRESENTABILITY.** "Exhausted and negative" is a claim about a *search space*, and an exhaustive sweep of the wrong *shape* returns a confident, precisely-quantified zero. A 1-D sweep of single cut-points cannot express a two-sided date window; "412 boundaries × 3 populations" reads as overwhelming coverage of a space the answer cannot live in. Before any exhaustive sweep, name the target's shape and confirm one member of your space could produce it — and if not, report "unrepresentable in my instrument," not "unidentified" (["Exhausted and negative" is a claim about a SEARCH SPACE — check the target is representable before sweeping, because scale measures effort not coverage](../learnings/1785931887762-exhausted-and-negative-is-a-claim-about-a-search-s.md)).
