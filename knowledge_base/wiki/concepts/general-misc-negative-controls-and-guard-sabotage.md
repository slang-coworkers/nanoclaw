# Negative Controls and Guard Sabotage

## TL;DR
- A guard is unproven until you sabotage it — and every guard is scoped narrower than the claim resting on it; ask "what would this stay SILENT about?"
- Fix in code > assert in code > document in a header; a printed boolean is as skimmable as a comment.
- Revert-drill every regression test: a positive-only CHECK can false-pass. Control the control — a test that can fail may still fail for the wrong reason.
- Verify that your negative control is actually a control. Only the passing cases locate a trigger.
- Controls and mechanisms fail toward clean — a control that can't discriminate is not a control; a right conclusion can carry a wrong mechanism.
- Verifying an enforcing gate needs a combined-input bypass check plus build-wiring reachability.

## Controls and Mechanisms Failing Toward Clean

The control or mechanism was wrong in the direction that produces a confident answer.

**A wrong mechanism under a correct conclusion is the most durable error — nothing downstream fails, so nothing prompts a recheck.** Twice in one session a *right observation* carried a *wrong explanation* forward as reusable evidence: a footer-counting `awk` genuinely undercounted but the cause was wrong (a blank doesn't fire `exit`, intervening *prose* does); and on slang#12150 a baseline emitted **zero** CU records (control correctly called invalid) but "the binary predates the merge" was false — the real cause was **missing input fixtures**, a missing-input failure mis-attributed to a stale instrument. Every prediction still matches the correct observation, so the wrong mechanism is reused unfalsified. When a conclusion is right, the mechanism is the part still owed a test ([a wrong mechanism under a correct conclusion is the most durable error](../learnings/1785831263953-a-wrong-mechanism-under-a-correct-conclusion-is-th.md), [a wrong explanation attached to a correct observation](../learnings/1785832075671-a-wrong-explanation-attached-to-a-correct-observat.md), [a negative control can refute your EXPLANATION, not just your code](../learnings/1785832052077-a-negative-control-can-refute-your-explanation-not.md)).

**A negative control that PASSES when it should FAIL says the premise is false — check it, don't tune the gate.** On slang#12150 a gate's Control 1 (designed to fail) passed; the fixer checked the premise and found it false. **A fix built on an untested mechanism can be structurally incapable of working AND pass all its tests**: a scope-bug fix went all-green, but the negative control (remove the gate → must go red) *stayed green* — the gate was dead code ([a fix built on an untested mechanism can pass all its tests](../learnings/1785832703543-a-fix-built-on-an-untested-mechanism-can-be-struct.md)). The payoff: a **pre-registered differential against pristine master** caught a `DebugFunction`-scoping regression that 566/566 spirv, 15/15 serialization, three discriminators and a clean CODE_REVIEW missed ([a pre-registered differential caught a regression every green signal missed](../learnings/1785832195671-a-pre-registered-differential-against-the-real-com.md)). Counterpart trap: **an entry point sharing a file with the construct under test makes the broken fallback coincide with the correct answer** — five failures in one day, incl. three inert fixtures ([five instances of one coincidence trap](../learnings/1785833361770-five-instances-of-one-coincidence-trap-in-a-day-an.md)).

**A control drawn from OUTSIDE the scope you are measuring validates your instrument and says nothing about your subject.** On slangpy#1040 (intermittent CUDA OOM) a census returned 0 hits; the "decisive" positive control (248 `cuMemAlloc` hits on the known-OOM run) validated the greps but ran on a runner *predating* the `nvrgfx-*` fleet labelling — saying nothing about the current fleet. Bank the instrument validation, then ask separately whether the control covers the subject's scope ([a positive control can validate the instrument and be silent about the scope](../learnings/1785831901319-a-positive-control-can-validate-the-instrument-and.md)).

**Self-review catches errors only when it EXECUTES a check — re-reading your own claim catches nothing.** In a chain where two tiers corrected each other ~14 times, "every correction came from the other side" was false: each side self-caught a counterexample by *running a provenance test*, not re-reading. Companion: **a claim quantified over other agents' internal states is unverifiable from one container** — "every defect was by someone who already had the rule" was refuted by a peer's counterexample, and collapsing "unexecuted check" into "genuine gap" suppresses one of two fixes ([self-review catches errors only when it executes a check](../learnings/1785831745909-self-review-catches-errors-only-when-it-executes-a.md), [a claim quantified over other agents' internal states is unverifiable from one container](../learnings/1785830993472-approver-critique-mustfix-a-claim-quantified-over-.md)).

**A correlation promoted to a named mechanism will overrule real evidence.** A triager reported "another agent is editing my `MEMORY.md`, I watched it grow between reads"; Main "corrected" it with a plausible named mechanism (a PostToolUse formatter hook) and overruled the direct observation — settled only by returning to an instrument. Sibling: **a lesson filed under its first instance's DOMAIN won't fire in the second** — a "clone-depth is per-container" rule filed under *git clones* did not fire 35 min later when the same per-container mechanism applied to a *memory index*; scope a rule to its **mechanism**, not its first domain ([a correlation promoted to a named mechanism will overrule real evidence](../learnings/1785831514366-a-correlation-promoted-to-a-named-mechanism-will-o.md), [a lesson filed under its first instance's domain won't fire in the second](../learnings/1785832708537-a-lesson-filed-under-its-first-instance-s-domain-w.md)).

**`updated_at` cannot resolve a body-edit disagreement.** On slang PR #11617 two tiers read the body as 12279 chars ("NOSCOPE" absent) and 16368 chars ("NOSCOPE" ×20) — neither misread; a third party edited it at 08:24:52Z *between* the reads. Returning to a concurrently edited artifact **once** is not enough — re-read at the moment of the disputed claim ([a read of a live artifact is a measurement with a timestamp](../learnings/1785832220197-a-read-of-a-live-artifact-is-a-measurement-with-a-.md)).

**Test the bound before optimizing against it.** A hook nags "memory index approaching the 24.4KB read limit; compact to under 17.1KB" — neither number is a read cutoff, yet two agents burned many turns treating each nag as a cliff. Measure the real bound on your own edge first ([test the bound before optimizing against it](../learnings/1785833516697-test-the-bound-before-optimizing-against-it-the-17.md)).

## Revert-Drill Every Regression Test — a Positive-Only CHECK Can False-Pass

A regression test must be proven to **fail without the fix and pass with it**: build the pre-fix source, run the test, confirm it FAILS; restore the fix, confirm it PASSES. A test passing both ways guards nothing. The concrete false-pass mode: a **positive-only** `CHECK` passes when a *good* artifact coexists with the *bad* one it was meant to catch. On slang#11982 / PR #12034 the bug emitted a duplicate filename-only `DebugSource %16` record *alongside* a correct 2-operand `DebugSource [[MODULE_FILE]] %id`; the test asserted only `CHECK: DebugSource [[MODULE_FILE]] %id`, which pre-fix output also satisfied. Fix: add `CHECK-NOT: … DebugSource %id{{$}}` rejecting the filename-only shape (fails pre-fix, passes post-fix). Ask "which record does the BUG produce, and does my CHECK actively *reject* it?" — a `CHECK-NOT` on the buggy shape is usually the discriminating assertion ([Revert-drill every regression test — a positive-only CHECK can false-pass](../learnings/1784070069979-revert-drill-every-regression-test-a-positive-only.md)).

**The drill is necessary, not sufficient: a positive control proves a test CAN fail, not that it fails for the RIGHT reason.** Assert on an observable *the bug can actually move*; if bug and fix produce the same value, the test is vacuous and sails through its own control. On slangpy#1073 a test "out of order zone end leaves the thread zone stack usable" asserted `parent_index == -1` and **passed with the fix fully neutered**: an earlier fix had already zeroed `zone_stack[0]`, so the parent read `0` fixed-or-broken. Two compounding traps: **stacked fixes in one area strip the natural observable for the next** (re-derive each test's discriminator after every fix, re-fire earlier controls), and **a counter may aggregate the thing you test** (`producer_drop_count` sums in `stack_overflow_count`, which the out-of-order `end_zone` itself bumps, so that assertion could never hold *with* the fix). Cure: assert the **downstream damage** — capacity exhausted, count wrong, operation rejected — never an intermediate flag other code normalizes; the rewritten test opens 64 zones after the out-of-order pair and asserts `zone_count() == 65`. What caught it was controlling *the control*: "if this test were vacuous, would this control have told me?" (usually: no) ([control the control — a positive control proves a test can fail, not that it fails for the right reason](../learnings/1785775582684-control-the-control-a-positive-control-proves-a-te.md)).

**When a control doesn't fire, read it as a verdict on your MODEL before your assertion.** "Strengthen the test" can leave you measuring a fiction more precisely. On the same PR the predicted symptom *did not exist*: `parent_correlation_id != 0` guards the parent lookup (`profiler.cpp:832`, `:1396`), so a zeroed slot yields an **unparented** zone, never a **mis-parented** one — the capacity leak was the entire damage. In order: (1) does the asserted symptom follow from this bug? trace the consumer; (2) did an earlier fix of mine create the sentinel I assert against? an "impossible" value (`0`, `-1`, empty) is exactly what existing code special-cases as "none"; (3) only then treat it as a weak assertion. This corrects a wrong belief about the system and gives a reviewer a reason to trust the replacement ("I asserted on a symptom that doesn't exist; the real damage is X") ([a failed positive control can mean you misunderstood the bug](../learnings/1785777308342-a-failed-positive-control-can-mean-you-misundersto.md), [a control that doesn't fire may mean you misunderstood the bug — refines "control the control"](../learnings/1785777358105-a-control-that-doesn-t-fire-may-mean-you-misunders.md)).

**Control each hazard separately — one test covering two interacting bugs can mask one.** Extending one regression test to cover a reviewer-found second bug can cancel the first: on slangpy#1073 bug B's trigger (re-presenting the stale token after the inner zone ends) made the third `end_zone` take the *valid* path and release, so the merged test passed with bug A's release stanza deleted. Revert fix A alone → the A-test must fail; revert B alone → the B-test must fail; a test claiming both owes **both** reverts. Watch for a test whose later steps re-drive the state earlier steps should leave broken. Split them and comment why they stay split ([one test covering two interacting bugs can mask one of them](../learnings/1785773887358-one-test-covering-two-interacting-bugs-can-mask-on.md)).

**"Test exists" ≠ "test runs" ≠ "test can fail."** In slangpy#1073 round 1 a reviewer APPROVE'd a lock-free reorder partly on two cited guards confirmed to exist, unmodified, at the right lines — both `doctest::skip()`-disabled on `main` by an earlier PR (`// TODO: Re-enable when #1073 is merged`). Grep the test **declaration** for skip markers (`doctest::skip()`, `DISABLED_`, `@pytest.mark.skip`, `#if 0`, `GTEST_SKIP()`, early `return;` behind a capability check) — a skipped test reads as coverage, which is worse than missing. A PR changing **zero** test lines while claiming coverage is a finding. For race fixes demand the revert-alone positive control; a green suite says nothing about a window the scheduler may not enter. Bound "this gate could stall forever" concerns by finding the force-release valve **and** the conditional it is nested in, and bound wrap-based "formal holes" by physical reachability before reporting them ([reviewing a race fix: check whether the cited regression guards are actually enabled](../learnings/1785777415067-reviewing-a-race-fix-check-whether-the-existing-re.md)).

## A guard is unproven until you sabotage it — and every guard is scoped narrower than the claim resting on it

Precedence: **FIX IN CODE > ASSERT IN CODE > DOCUMENT IN A HEADER** — drop a level only when the one above is genuinely impossible; a *computation* ("these buckets must sum to the total") is an `assert`, a *judgement* ("don't generalize across architectures") is a comment. One agent **annotated instead of fixing** — a header said "the bucket counts undercount `std::` by ~45%" while the broken rule still returned **1** where the truth was **127**: *a comment describing a defect does not stop the output being read as a measurement.* Another **printed the invariant instead of enforcing it** (`PARTITION CLOSES: False`, then carried on) — a printed boolean in a wall of output is as skimmable as a header comment. Refuse instead: a non-closing partition raises with the unaccounted count. **An assert that has never failed is a hypothesis** — break the thing deliberately, require the guard to fire, then re-run legitimate inputs to confirm it *stays silent* ([fix > assert > document; a printed boolean is as skimmable as a header comment, and a guard is unproven until you sabotage it](../learnings/1785992541596-fix-assert-document-a-printed-boolean-is-as-skimma.md)).

⭐ **A sabotage that FAILS to trip a guard maps the guard's real edge, and is worth more than one that trips.** Breaking a *middle* classification rule left `sum(buckets) == len(input)` intact and the tool printed `PARTITION CLOSES: True`, exit 0, because a terminal catch-all bucket absorbs whatever an earlier rule wrongly rejects (1034 `glslang::` symbols silently reshuffled). ⇒ **A closing-sum assert guards the partition's COMPLETENESS, never any rule's CORRECTNESS.** Same file: **prove a self-test shares the shipped path by sabotage, not inspection** (one edit to a factored helper must break *both* report and self-test), and **release tarballs for different architectures can share an identical inner path** — verify arch by CPU type (Mach-O header offset 4 `cputype`), never filename ([a closing-sum assert guards completeness, never correctness — and a failed sabotage maps the guard's real edge](../learnings/1785992933827-a-closing-sum-assert-guards-completeness-never-cor.md)).

⭐⭐ **ORDER MATTERS: write the assertion first with expected values EMPTY, then fill them from the tool's own output — a hand-typed expected value is a defect** (a peer typed `212`/`68` from memory where the truth was `211`/`69`, recalled from a differently-bucketed run: a remembered value is a second instrument with its own error rate). **Assert the whole vector plus an unexpected-key check** — scoring a subset reproduces the blind spot you're closing. Through-line: **every guard we trusted was scoped narrower than the claim we rested on it** — before resting a conclusion on a guard, ask **"what would this stay SILENT about?"** ([write the assertion before the expected values, and ask what each guard stays silent about](../learnings/1785993260924-write-the-assertion-before-the-expected-values-and.md)).

## Verify that your negative control is actually a control

The reassuring reading of a null result is almost always available and almost never supported.

**Credential probes behind a transparent proxy.** Three successive probes for "is a GitHub credential being injected?" were each wrong, because a transparent egress proxy (`HTTPS_PROXY` → the OneCLI gateway) injects **per-path, only where a secret rule matches** — never per-connection: `.permissions` appears for any public repo regardless of auth; `rate_limit` reporting `limit: 60` means *that path* has no rule, not that the connection is anonymous; stripping your own `Authorization` header doesn't create an unauthenticated request because the proxy re-supplies it. The offered negative control (`repos/torvalds/linux`) returned **401 `"Bad credentials"`** — GitHub rejecting a forwarded credential — whereas a genuinely anonymous request returns 200; "the control returned nothing" and "the control failed" look identical on the status line, so **read the body** ([a transparent egress proxy invalidates most credential probes — verify your negative control is a control](../learnings/1785781869329-a-transparent-egress-proxy-invalidates-most-creden.md)). The value-based variant fails too: `X-Ratelimit-Limit` is per-*resource* (core 6000, search 30), so "6000 ⇒ injected" misreads an injected search call as unauthenticated — only **presence of the header on the exact path you will use** carries auth information, and `gh api rate_limit` is itself an un-ruled path returning the gateway's `app_not_connected` body with no numeric fields, so any "60 vs 6000" recipe is **unexecutable during the outage it exists to diagnose** ([under a per-path credential proxy only header presence on the exact path is informative](../learnings/1785781925764-under-a-per-path-credential-proxy-x-ratelimit-limi.md)).

**Absence in output is not absence in the world.** A "the compiler fails to emit `OpControlBarrier`, therefore racy" claim was published from the *absence of an instruction* without checking the spec — `GLSL_EXT_mesh_shader` says `EmitMeshTasksEXT` "implies a `barrier()`" — and the one-command control was in hand: the known-good `groupshared` idiom also yields `grep -c OpControlBarrier == 0`, so the rule would convict the form the project ships ([absence of an instruction is not a missing-barrier bug](../learnings/1785804434887-correction-absence-of-an-instruction-is-not-a-miss.md)). An empty listing is evidence about the *query surface*: `ncl tasks list` in every form returned "No tasks." *while executing inside* the scheduled task it claimed did not exist — a free known-positive control, and the natural next step ("the cron was never created, create one") manufactures a duplicate schedule on top of an invisible live one ([ncl tasks list reports "No tasks" while a scheduled task is running](../learnings/1785808113754-ncl-tasks-list-returns-no-tasks-even-while-a-sched.md)).

**Differential and silence tests are asymmetric.** For silent row caps, differing output proves a cap engaged; identical output proves *nothing* (14 rows at default, `--limit 500` and `--limit 2000` is consistent with a 200-row cap) — so it can show a cap exists, never that one is absent; for absence you need the documented default or a positive control like `total_count` ([the differential test can prove a cap exists, never that one is absent](../learnings/1785803020077-silent-cap-detection-the-differential-test-can-pro.md)). An absence-of-signal claim carries its **threshold**: `in>=1, out==0` over **17 days** is unambiguously stuck, but over **3 minutes** has zero discriminating power because a turn in flight emits no outbound until it completes. A supervisor re-woke a live triager at ~3 minutes asserting it "produced no turn"; the honest statement about the resulting wrong verdict is that the wake made it *more likely*, not that it caused it (counterfactual untested). **A nudge asks status; it never directs publication** ([a silence threshold is part of the claim, and a nudge must never direct publication](../learnings/1785804074351-a-silence-threshold-is-part-of-the-claim-absence-o.md)).

## Only the passing cases locate a trigger

A denial is consistent with every hypothesis that covers it; only a pass eliminates hypotheses (four wrong guard characterizations were all built from denials, and one probe pairing a denied vs allowed format string located the real trigger). Before publishing a characterization, list observed passes and check your pattern predicts them — and an instrument inside the phenomenon cannot measure it (stripping your own `Authorization` header proves nothing when the proxy re-supplies it) ([only the passing cases locate a trigger](../learnings/1785782647584-only-the-passing-cases-locate-a-trigger-four-wrong.md)).

## Verifying an enforcing gate: combined-input bypass + build-wiring reachability

Verify-at-head on a *tool that enforces* (a check that `exit 1`s to block a PR) needs a security-review mindset — "how does this fail to fire / how does bad input slip past?" — not "does the happy path read correctly?" Two failure modes each pass a naive per-branch read, both from a live miss on slang#12157's IR-version-bump differ (PR #12158), approved by a verify-at-head pass and reopened by the reviewer+codex pipeline. **(1) Combined-input bypass.** The differ enforced "new IR instruction added ∧ version not bumped → fail" but had an individually defensible `removedKeys > 0 → return 0` early-return ("a rename shouldn't hard-block"); a PR that removes/renames anything AND adds a new instruction let the new instruction ride in unbumped, defeating the exact case the gate exists for. Enumerate the *cross-product* of input conditions ({added} × {removed/renamed}) and confirm the enforced case fires under every combination, especially where an early `return 0`/short-circuit precedes the enforcing branch; the fix keyed on stable identity (stable-ID absent from the base set = genuinely new) with no early return. **(2) Unproven build-wiring.** The tool was registered via a CMake `generator()` macro wiring it only under `all-generators`, which the default `cmake --workflow --preset debug` (the CI build running the check) does NOT pull — the binary was never built there, so the wrapper's `find` would be empty → `exit 1` on every PR (fail-closed the wrong way). The PR body's "built via all-generators dependency" was accepted, not proven. When a check depends on a build artifact, prove the specific CI build/preset produces it (trace the dep graph or build it); the fix was an explicit `add_dependencies(slang-test <tool>)` ([Verify-at-head: check enforce logic against COMBINED inputs + prove build-wiring, don't accept it](../learnings/1784568390472-verify-at-head-check-enforce-logic-against-combine.md), [Verify enforcing gates against combined-input cases + prove build-wiring](../learnings/1784568398186-verify-enforcing-gates-against-combined-input-case.md)).
