# Slang WGSL and Metal Backends: Textual Constructor-Syntax Targets

The WGSL (`slang-emit-wgsl.cpp`) and Metal (`slang-emit-metal.cpp`) backends are textual targets that, unlike HLSL, require constructor-syntax aggregate initializers and lack native combined samplers. Several codegen bugs span the WGSL/Metal/CUDA target family because they share the same `$N` positional intrinsic-string and value-indexability constraints. This page covers WGSL/Metal-specific emission issues.

## Static-Const Arrays Must Be var<private> for Runtime Indexing

In WGSL, a `const` is a compile-time value (≈C++ constexpr); the spec only lets a *value* of array type be indexed by a const-expression. A `static const` array indexed by a runtime value (e.g. `positions[SV_VertexID]`) emitted as WGSL `const` is rejected by naga/tint. The fix in `emitVarKeywordImpl` flips the keyword `const`→`var<private>` for module-scope array/matrix constants — yielding a runtime-indexable private var with a const-expression initializer ([WGSL emit: static-const arrays must be var<private> (not const) for runtime indexing](../learnings/1781624737396-wgsl-emit-static-const-arrays-must-be-var-private-.md)).

The conversion is safe as a type-based transform (no use-analysis needed) because `replaceGlobalConstants` inlines GlobalConstant values into uses before `simplifyIR`, and peephole folds constant-index reads away — so no `const` is left reading the now-`var<private>` array. A residual edge case (CSE-shared inner array both nested and independently runtime-indexed) is a documented known limitation, not a regression ([WGSL static-const-array review: replaceGlobalConstants false-positive + value-indexability rule](../learnings/1781639050403-wgsl-static-const-array-review-replaceglobalconsta.md)). The WGSL value-indexability rule: array values need const indexing, but vector/matrix values ARE runtime-indexable — so only `kIROp_ArrayType` globals need conversion.

When reviewing such PRs, the recurring false-positive "the converted `var<private>` is initialized from another `var<private>` → invalid WGSL" must be verified against the actual post-link IR — `replaceGlobalConstants` removes the `IRGlobalConstant`, so no GlobalConstant survives to emit ([WGSL static-const-array review: replaceGlobalConstants false-positive + value-indexability rule](../learnings/1781639050403-wgsl-static-const-array-review-replaceglobalconsta.md)).

## WGSL @location Return-0 Fallback Branch

On WGSL PRs adding a `resolveWGSLLocation`-style helper with an index-less `return 0` fallback, reviewers reliably suggest covering the fallback by adding a no-digit field (e.g. `: SV_TARGET`) alongside an indexed sibling (`: SV_TARGET2`). This is infeasible in one struct: a bare `SV_TARGET` and `SV_TARGET0` both resolve to `@location(0)`, an invalid WGSL collision. Covering the branch needs a separate struct, and declining the in-struct test is reasonable when the fallback is pre-existing behavior unchanged by the PR ([WGSL @location return-0 fallback branch can't be unit-tested in one struct](../learnings/1781663682498-wgsl-location-return-0-fallback-branch-can-t-be-un.md)).

## Combined-Sampler GetDimensions Off-By-One (WGSL/Metal/CUDA)

`Sampler2D<T>.GetDimensions(out0, out1)` miscompiles on WGSL (#11669), Metal, and likely CUDA: width is written to the sampler var, height to the first output, second output never written. SPIR-V and GLSL escape (SPIR-V has a dedicated combined variant; GLSL keeps native `sampler2D`).

Root cause: for targets without native combined samplers, `lowerCombinedTextureSamplers` splits `Sampler2D` into `struct{texture,sampler}`, so call operands become `[texture, sampler, out0, out1]`. The WGSL/Metal/CUDA `GetDimensions` intrinsic strings are C++-generated in `TextureTypeInfo::writeGetDimensionFunctions()` and reference operands positionally (`$0`=receiver, `$1`/`$2`=outputs), assuming the receiver is ONE operand. The combined-sampler compensation `m_argIndexOffset -= 1` fires only under the `$p` marker, which these strings never emit. This shares a root cause with HLSL #10522; the endorsed fix is a source/early-IR rewrite `combinedSampler.GetDimensions(...)` → `combinedSampler.__getTexture().GetDimensions(...)` that fixes all four targets at once. Triage tip: when a combined-sampler intrinsic miscompiles on one target, check the other `$N`-string targets ([Combined-sampler GetDimensions off-by-one (WGSL/Metal/CUDA) — shared root with HLSL #10522](../learnings/1781992589265-combined-sampler-getdimensions-off-by-one-wgsl-met.md)).

## Per-Target Buffer Stride (WGSL Outlier)

For `StructuredBuffer<float3, ScalarDataLayout>`, the stride is 12 bytes on D3D/HLSL, Vulkan/SPIR-V (requires the layout arg), CUDA, and Metal — but **WGSL hard-codes 16** in `slang-ir-lower-buffer-element-type.cpp` (an array of scalar/vector always converts to 16-byte-aligned vector). So `<float3, ScalarDataLayout>` cannot give tight 12-byte stride on WGSL. The workaround is `RWByteAddressBuffer.Load<float3>`/`.Store<float3>` with explicit 12-byte stride — decomposed into three scalar `f32` loads. The `scalarizeVectorLoadStore` flag is set for WGSL, Metal, and CPU-via-LLVM targets in `slang-emit.cpp` ([Slang per-target stride for `StructuredBuffer<float3, ScalarDataLayout>` — WGSL is the outlier](../learnings/1780177237717-slang-per-target-stride-for-structuredbuffer-float.md)).

## Wave Aggregate Intrinsics (CUDA/Metal FileCheck Trap)

When reviewing coverage/wave-aggregation PRs, a FileCheck `//CHECK-DAG: WaveActiveCountBits` on CUDA or Metal output is false confidence. Only `case hlsl:` emits the literal `WaveActiveCountBits`; CUDA lowers to `__popc(__ballot_sync(...))` and Metal to `_WaveCountBits(WaveActiveBallot(value))`. The literal token can appear in CUDA/Metal output only as the name of the force-kept `[KnownBuiltin]` definition, not as the per-marker increment. Correct checks: CUDA → `__ballot_sync`/`__popc`; Metal → `simd_ballot`/`popcount` (and `simd_is_first` for `WaveIsFirstLane`) ([Coverage wave-aggregate tests — CUDA/Metal FileCheck asserting `WaveActiveCountBits` literal passes for the wrong reason](../learnings/1780935575501-coverage-wave-aggregate-tests-cuda-metal-filecheck.md)).

## Metal Address-Space Crashes: "Unknown addressspace encountered"

The Metal emitter throw `SLANG_UNEXPECTED("Unknown addressspace encountered.")` at `slang-emit-metal.cpp:1363` (the `default:` arm of the pointer-param address-space switch, hit when a pointer param carries `AddressSpace::Generic`) is a **shared symptom of at least two distinct upstream producer bugs** — do NOT fold a new Metal addrspace crash into an existing issue by message alone; IR-dump the final pass and check *which* producer left `Generic` and on *which* trigger surface ([Metal 'Unknown addressspace encountered' has ≥2 distinct root causes — don't fold by message](../learnings/1783459810353-metal-unknown-addressspace-encountered-has-2-disti.md)). (1) **Fragment entry-point out-param (#11969):** `legalizeEntryPointVaryingParamsForMetal` runs the out-param→return-struct conversion (`lowerOutParameters`) only for `Stage::Vertex`, so a fragment `out float4 : SV_Target` survives as a pointer-typed param into the emit switch. The conversion machinery is already stage-agnostic (`wrapReturnValueInStruct` even has a `Stage::Fragment` branch) — fix drops the vertex-only gate rather than patching the consumer emit switch (which would mask the producer bug) ([Metal fragment out-param crash — out→return-struct lowering is vertex-only](../learnings/1783421444820-metal-fragment-out-param-crash-out-return-struct-l.md)). (2) **`export`/library out/inout param (#11981):** `AddressSpaceContext::processModule` seeds its worklist ONLY from `IREntryPointDecoration` funcs, so an `export`/public function with a mutable-reference param has no caller to specialize its address space from and keeps `Generic` — the real discriminator is *export-linkage on a mutable-ref param*, NOT "no entry point" (the auto-filed "add an entry point" workaround is wrong; verified by crossed controls). WGSL/GLSL share the same worklist-seeding gap but only Metal *crashes* because only its emitter treats an unspecialized `Generic` pointer as fatal — so the principled fix is producer-side (seed exports + default library-boundary mutable-ref params to `thread`/`ThreadLocal`), not an emitter fallback case ([Metal 'Unknown addressspace' on export out/inout params: trigger is export-linkage, not missing entry point](../learnings/1783460634599-metal-unknown-addressspace-on-export-out-inout-par.md)). Fast discriminators between the two: does it crash only in `-whole-program` with no `[shader]`, does adding a concrete entry point make it compile, does HLSL emit fine? Yes-to-all ⇒ the library/worklist cause (#11981), not the entry-point varying-param cause (#11969).

## Metal DescriptorHandle-in-Buffer Emits Illegal `device T* device*` (#11970)

On `-target metal`, `StructuredBuffer<DescriptorHandle<StructuredBuffer<uint>>>` emits illegal MSL (`uint device* device* p [[buffer(0)]]`) because Metal's `isResourceTypeBindless` always returns true, so a `DescriptorHandle<R>` buffer *element* emits `R` directly and the outer `StructuredBuffer` binding appends another `device*`. A pass already owns exactly this shape — `MetalPointerBufferElementTypeLoweringPolicy` — but its discovery filter `needsElementLowering` recurses only into `IRPtrType`/array/struct and never matches `IRDescriptorHandleType`, so it never fires; that filter gap is the precise fix layer. Recommended shape is the reporter's struct-wrap (a 1-member struct, ABI byte-identical, covers both buffer and texture) rather than lowering to UIntPtr (which can't handle the texture sub-case). Keep this tractable descriptor fix distinct from arrays-of-resources on Metal, a genuine FEATURE GAP (no native array-of-buffers/textures in MSL) belonging to umbrella #10842 ([Metal DescriptorHandle-in-buffer emits illegal device T* device* (#11970) — an existing pass owns the shape but its filter misses it](../learnings/1783421582372-metal-descriptorhandle-in-buffer-emits-illegal-dev.md)).

## Metal 4.0-Only Attributes Emitted Against Sub-4.0 Target (#11985)

The Metal emitter emits the Metal-4.0-only kernel attribute `[[required_threads_per_threadgroup(...)]]` unconditionally for the *default* Metal target — the gate is `getTargetCaps().implies(metallib_4_0)` and `alias metallib_latest = metallib_4_0` (flipped from `3_1` by PR #10592) — while the shader is compiled against sub-4.0 (offline `metal -std=metal3.1`; slang-rhi passes only `Capability::metal` with no 4.0 language version). So emit says 4.0, target says <4.0, and it is rejected on any runner whose Metal toolchain defaults below 4.0 — the CI intermittency is free-runner Metal-version heterogeneity, not randomness. `metallib_latest` hardcoded to the newest version is a structural mismatch to watch on any new gated Metal/SPIR-V feature; the fix gates emit on the *effective* metal language version, not `metallib_latest` ([slang#11985 macOS CI flake = Metal 4.0 attribute emitted vs sub-4.0 compile target](../learnings/1783470139599-slang-11985-macos-ci-flake-metal-4-0-attribute-emi.md)).

### #12096 macos-26 Metal-4 regression: fix is ADVANCE the `-std`, not RETREAT the cap

**slang#12096** is the formal Metal-4 root-cause slice of #11985: on `macos-26` CI runners four Metal gfx tests fail at `createComputePipeline` with `'required_threads_per_threadgroup' attribute requires Metal language standard metal4.0 or higher` (pass on `macos-15`). It shares the SAME `metallib_4_0`-from-OS root as #11999 — the maintainer (jkwak-work) merged the two as one root problem, correctly refuting an earlier "distinct intermittency" triage: `gpu-printing` (the #11999 example) is a `[shader("compute")]` kernel that hits the exact same `createComputePipeline` → `metallib_4_0` path, the #11999 graphics examples PASSED past `createDevice` on the same failing runner (so it fails on the compute path, not a device flake), and #11999 only *looked* intermittent because `runs-on: macos-latest` served a macos-15/macos-26 mix — pinning to macos-15 (#12075) made #12096 deterministic. Triage lesson: weight *mechanism* (which pipeline stage / capability path) over *surface signature* (intermittent-vs-deterministic, silent-vs-printed) when classifying two failures as distinct ([#12096 ↔ #11999 share the same metallib_4_0-from-OS root](../learnings/1784062178778-slang-12096-11999-share-the-same-metallib-4-0-from.md)).

**Supersession — the first triage verdict was WRONG.** The initial verdict was "the fix belongs in slang-rhi (retreat: stop advertising `metallib_4_0` on macos-26, drop to 3.1)", premised on `external/slang-rhi/src/metal/metal-device.cpp:266` deriving the metallib ladder purely from `NS::ProcessInfo operatingSystemVersion()` (`if (osVersion.majorVersion >= 26) addCapability(Capability::metallib_4_0)`, introduced by slang-rhi PR #795) plus "the macos-26 toolchain LACKS metal4.0" and "slang core is correct, no core change" ([slang#12096 macos-26 Metal-4 fix belongs in slang-rhi (OS-version capability inference)](../learnings/1784051017162-slang-12096-macos-26-metal-4-fix-belongs-in-slang-.md)). **Both premises were falsified by the fix that actually landed** (PR #12009 on `fix/issue-11999`, commit `aba3cd7dd`, verified green): the RHI's per-OS 4.0 advertisement is *correct* (macos-26 genuinely supports Metal 4.0), and the defect is Slang's **downstream `-std=metal3.1` hardcode** rejecting its own correctly-emitted 4.0 attribute — a SLANG-CORE change, not a slang-rhi retreat. `slang-gcc-compiler-util.cpp:978-987` now emits `-std=metalX.Y` from `options.metalLanguageVersion` (master still hardcodes 3.1 at `:973`); the producer `slang-code-gen.cpp` sets `metalLanguageVersion = 4.0` when `getTargetCaps().implies(metallib_4_0)` — the same predicate the emitter uses, so emit-gate and downstream-`-std` cannot diverge (new `SemanticVersion metalLanguageVersion` field on `DownstreamCompileOptions`). Reusable lesson: an error "requires version X" is ambiguous between "toolchain can't do X" and "we didn't *ask* for X" — distinguish them (invoke with `-std=metal4.0` and see) before recommending a capability RETREAT; the fix that ADVANCES the request is often right where the retreat is wrong. Also, "slang core is correct" was verified only against the *emitter* (reactive, correct) but never against the *downstream-compile* `-std`-construction layer, which is also slang-core and was the actual bug site. Coverage caveat: #12009's green macOS jobs exercise the same compute→`createComputePipeline`→metal4.0 path via the re-enabled `gpu-printing` example, but the four specific `gfx-unit-test-tool/*Metal.internal` tests run in the Nightly Coverage workflow still pinned to macos-15 (#12075), so they aren't directly confirmed until that pin is removed ([slang#12096 fix is ADVANCE-to-metal4.0 in Slang-core (-std derivation), NOT slang-rhi retreat](../learnings/1784062749848-slang-12096-fix-is-advance-to-metal4-0-in-slang-co.md)).

## General Cross-Target Lesson

WGSL is the "other constructor-syntax, no brace-init" textual target alongside GLSL. When a `-target glsl` text-output codegen bug appears (e.g. array brace init), check whether the WGSL emitter already solved the same shape — the override often exists in `slang-emit-wgsl.cpp` and just needs porting ([Slang per-target stride for `StructuredBuffer<float3, ScalarDataLayout>` — WGSL is the outlier](../learnings/1780177237717-slang-per-target-stride-for-structuredbuffer-float.md)).

## FP literal type suffixes (Metal outlier) + WGSL f16 already works

The Metal source emitter is the **lone** C-like backend that prints floating-point literals with **no** type suffix. `MetalSourceEmitter::emitSimpleValueImpl` (`slang-emit-metal.cpp:1128-1164`) omits the MSL `h`/`f` suffix, so a `half` literal like `61440.hf` degrades to a bare double — the fix mirrors the WGSL/HLSL path by appending the suffix ([Slang Metal backend emits FP literals with NO type suffix (issue #11837)](../learnings/1782814984950-slang-metal-backend-emits-fp-literals-with-no-type.md), [Metal emitter is the lone backend that omits FP literal type suffixes](../learnings/1782832643994-metal-emitter-is-the-lone-backend-that-omits-fp-li.md)). Separately, do **not** treat WGSL as missing 16-bit float support: verified at HEAD, the WGSL/WebGPU backend already fully supports `half`/`f16`; a "WGSL missing f16" report is almost always the 16-bit **integer** (`bit_cast<uint16_t>`) path surfacing E56103, a different gap ([WGSL f16 floats already work; E56103 is the 16-bit-INTEGER path (slang #11835)](../learnings/1782813507927-wgsl-f16-floats-already-work-e56103-is-the-16-bit-.md)).

## WGSL trailing switch-case break: valid-but-redundant, and version-dependent

Slang's WGSL emitter puts `break;` as the last statement of every switch `case`/`default`. A reporter called it invalid; first analysis said valid-but-redundant and downgraded #11946 to cosmetic ([WGSL trailing break in switch cases is VALID (redundant), not invalid — verify validator claims via DeepWiki when WebSearch is down](../learnings/1783296818057-wgsl-trailing-break-in-switch-cases-is-valid-redun.md)). That was then corrected: it **is** a real bug because **older naga rejects** it — verify validator claims across toolchain VERSIONS, not just current source ([CORRECTION: WGSL redundant switch-case break IS a real bug (older naga rejects) — verify across toolchain VERSIONS, not just current source](../learnings/1783300097186-correction-wgsl-redundant-switch-case-break-is-a-r.md)). The tempting suppression gate `!supportsSwitchFallThrough()` is **wrong**: HLSL/FXC also returns false yet still requires the break, so that predicate is not a proxy for 'target needs a switch-case break' ([1783300771712-slang-supportsswitchfallthrough-is-not](../learnings/1783300771712-slang-supportsswitchfallthrough-is-not-a-proxy-for.md)).
