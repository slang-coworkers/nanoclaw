# Slang WGSL Backend + Cross-Target Emission (WGSL/Metal Shared)

The WGSL (`slang-emit-wgsl.cpp`) backend is a textual target that, unlike HLSL, requires constructor-syntax aggregate initializers and lacks native combined samplers. Several codegen bugs span WGSL/Metal/CUDA because they share `$N` positional intrinsic strings and value-indexability constraints; this page covers those plus WGSL-specific emission. Metal-only deep dives (address spaces, `DescriptorHandle`, MetalLib versioning, array-of-resource, CI coverage) live on [[wiki/concepts/slang-backends-metal.md]]. Combined-sampler texture-only ops (`GetDimensions`, `Load`, subscript) on HLSL/Metal/WGSL are on [[wiki/concepts/slang-backends-hlsl-combined-sampler-texture-ops.md]].

## TL;DR

- WGSL `const` is compile-time and only array VALUES need const indexing, so a runtime-indexed `static const` array emits as `var<private>` (`kIROp_ArrayType` only, `emitVarKeywordImpl`). Safe: `replaceGlobalConstants` removes the GlobalConstant before emit.
- A WGSL `@location` return-0 fallback can't be tested in one struct: `SV_TARGET` and `SV_TARGET0` collide on `@location(0)`.
- WGSL trailing switch-case `break;` is a real bug (older naga rejects it); verify validator claims across toolchain VERSIONS. `!supportsSwitchFallThrough()` is the wrong gate. Unconditional loops emit `loop` since PR #13071.
- Tint's PreventInfiniteLoops adds a counter to every loop it cannot prove finite. Only a WGSL `for` with a `var` in the init, a `±1` constant update and a constant-bound first `if … break` passes; Slang's `loop` with the increment copied into the body never does (#13733). After counted-`for` emission (#13740), core-module `VECTOR_MAP_*` loops and the one-trip `[ForceInline]` wrapper around a callee containing a loop still get one (#13765).
- WGSL f16 floats work; "missing f16" is usually the 16-bit INTEGER path (E56103). Exception: f16 subgroup builtins vs the `slang-tint-0` pin's `subgroups_f16`.
- WGSL hard-codes a 16-byte stride for `StructuredBuffer<float3, ScalarDataLayout>` (12 elsewhere); use `RWByteAddressBuffer.Load<float3>`.
- `uniform S s; s.member.method()` copies all of `S` into a function-scope temp unless `deferBufferLoad` sinks the load, and that sink is gated by a size heuristic (> 16 bytes, and > 128 bytes or containing an array). A 128-byte array-free struct keeps the whole copy (#13732).
- Combined-sampler texture-only ops leak the sampler that `lowerCombinedTextureSamplers` injects. The `$q` marker (PR #11816) fixed `GetDimensions` on Metal/WGSL only; `Load` and the subscript still leak there and on HLSL (#13737). Details are on the combined-sampler page linked in the intro.
- `CHECK-DAG: WaveActiveCountBits` on CUDA/Metal is false confidence; check `__ballot_sync`/`__popc` (CUDA), `simd_ballot`/`popcount` (Metal).
- Nested output struct + a field lacking a user semantic segfaults Metal/WGSL: `ensureStructHasUserSemantic` indexes a stale layout by POSITION after `maybeFlattenNestedStructs`. Fix by KEY.
- WGSL `inout` arg from a global `static` → `ptr<private>` into `ptr<function>` (#12173): fix `legalizeCall`'s skip-list on IR op/scope.
- Metal alone omits FP-literal suffixes (`h`/`f`). For a `-target glsl` text bug, check whether the WGSL emitter already solved it.
- Adding a target to `[require]` needs a matching `__target_switch` `case`/`default`, or E36107 becomes an emit gap (#12165).
- groupshared-by-ref (#10641) breaks Metal, WGSL and CUDA differently; a green vk/HLSL/SPIR-V run clears none.
- Pointer address space is TYPE-LEVEL on Metal/WGSL (E30019) but PASS-INFERRED on SPIR-V (E58005/E58004). Metal/WGSL do support returning pointers; any "X can't reach Y" claim needs a named diagnostic + test or a repro.
- Metal wrapper swaps leak decorations: `EntryPointParams` cbuffer (#10675), `[[stage_in]]` on a helper (#13271), cloned param layouts breaking Metal AND CUDA. Strip at the producer. Callee-first `-entry vsB -entry vsA` hangs HLSL/GLSL/WGSL; use `timeout`.

Companion page [[wiki/concepts/slang-backends-wgsl-matrix-and-validation.md]] covers WGSL matrix-operator validity (negation, int64 matrices), the §3.9 template-list ambiguity in argument lists, and GPU-free naga-wasm validation.

## Static-Const Arrays Must Be var<private> for Runtime Indexing

In WGSL a `const` is a compile-time value (≈C++ constexpr), and the spec only lets a *value* of array type be indexed by a const-expression. A `static const` array indexed at runtime (e.g. `positions[SV_VertexID]`) and emitted as WGSL `const` is rejected by naga/tint, so `emitVarKeywordImpl` flips `const`→`var<private>` for module-scope array/matrix constants: a runtime-indexable private var with a const-expression initializer ([WGSL emit: static-const arrays must be var<private> (not const) for runtime indexing](../learnings/1781624737396-wgsl-emit-static-const-arrays-must-be-var-private-.md)).

Vector/matrix values ARE runtime-indexable, so only `kIROp_ArrayType` globals need conversion. The type-based transform needs no use-analysis: `replaceGlobalConstants` inlines GlobalConstant values into uses before `simplifyIR` and removes the `IRGlobalConstant`, and peephole folds constant-index reads, so no `const` reads the converted array. A CSE-shared inner array that is both nested and independently runtime-indexed is a documented known limitation, not a regression. The recurring review false-positive "the converted `var<private>` is initialized from another `var<private>` → invalid WGSL" must be checked against the post-link IR, where no GlobalConstant survives to emit ([WGSL static-const-array review: replaceGlobalConstants false-positive + value-indexability rule](../learnings/1781639050403-wgsl-static-const-array-review-replaceglobalconsta.md)).

## WGSL @location Return-0 Fallback Branch

Reviewers of a `resolveWGSLLocation`-style helper with an index-less `return 0` fallback often ask to cover it with `: SV_TARGET` beside `: SV_TARGET2`. That is infeasible in one struct: bare `SV_TARGET` and `SV_TARGET0` both resolve to `@location(0)`, an invalid WGSL collision. Coverage needs a separate struct, and declining is reasonable when the fallback is pre-existing behavior the PR doesn't change ([WGSL @location return-0 fallback branch can't be unit-tested in one struct](../learnings/1781663682498-wgsl-location-return-0-fallback-branch-can-t-be-un.md)).

## Per-Target Buffer Stride (WGSL Outlier)

`StructuredBuffer<float3, ScalarDataLayout>` has a 12-byte stride on D3D/HLSL, Vulkan/SPIR-V (layout arg required), CUDA and Metal, but **WGSL hard-codes 16** in `slang-ir-lower-buffer-element-type.cpp` (an array of scalar/vector always becomes a 16-byte-aligned vector). For a tight 12-byte stride on WGSL use `RWByteAddressBuffer.Load<float3>`/`.Store<float3>` (three scalar `f32` loads); the `scalarizeVectorLoadStore` flag is set for WGSL, Metal and CPU-via-LLVM in `slang-emit.cpp` ([Slang per-target stride for `StructuredBuffer<float3, ScalarDataLayout>` — WGSL is the outlier](../learnings/1780177237717-slang-per-target-stride-for-structuredbuffer-float.md)).

## Uniform-Struct Member Access Copies the Whole Struct Unless deferBufferLoad Sinks It (#13732)

Consider `uniform S s;` and a call `s.member.method()` on WGSL. `collectGlobalUniformParameters` (`slang-ir-collect-global-uniforms.cpp:364-366`) emits `load(fieldAddr(globalParams, s))`, which loads all of `S`. Only `deferBufferLoad` (`slang-ir-defer-buffer-load.cpp:240-245`) sinks that load to `load(fieldAddr(.., member))`, and it does so only when `isTypePreferrableToDeferLoad` (`:59-92`) is true: natural size above 16 bytes, and either above 128 bytes or containing an array. When the sink does not happen, `lowerBufferElementTypeToStorageType` (the load case of `deferStorageToLogicalCasts`, `slang-ir-lower-buffer-element-type.cpp:1351-1479`) builds a whole `S_std140` temp var on WGSL, or a `copyLogical` on SPIR-V, and passes `&tmp.member` to a callee already specialized to `BorrowInParam(Member_std140)` (`:1570-1578`). The boundary is exact: a 128-byte struct with no array keeps the whole copy, and a 132-byte one does not. The same heuristic gates `specializeFuncsForBufferLoadArgs`, see [[wiki/concepts/slang-b-bindings-and-backends.md]]. To find which pass makes two variants differ, dump `-dump-ir` for both, split them with `extras/split-ir-dump.py`, and diff `main` section by section; the first section that differs names the pass ([WGSL whole-uniform-struct copy is gated by deferBufferLoad's size heuristic](../learnings/1792249776321-wgsl-whole-uniform-struct-copy-is-gated-by-deferbu.md)).

## Wave Aggregate Intrinsics (CUDA/Metal FileCheck Trap)

In wave-aggregation tests, `//CHECK-DAG: WaveActiveCountBits` on CUDA/Metal output is false confidence: only `case hlsl:` emits it. CUDA lowers to `__popc(__ballot_sync(...))` and Metal to `_WaveCountBits(WaveActiveBallot(value))`; the token appears in their output only as the name of the force-kept `[KnownBuiltin]` definition, not the per-marker increment. Check CUDA for `__ballot_sync`/`__popc` and Metal for `simd_ballot`/`popcount` (`simd_is_first` for `WaveIsFirstLane`) ([Coverage wave-aggregate tests — CUDA/Metal FileCheck asserting `WaveActiveCountBits` literal passes for the wrong reason](../learnings/1780935575501-coverage-wave-aggregate-tests-cuda-metal-filecheck.md)).

## Textual-Emitter Parity: Constructor Syntax, FP Literal Suffixes, f16

WGSL is the "other constructor-syntax, no brace-init" textual target alongside GLSL. When a `-target glsl` text-output bug appears (e.g. array brace init), the override often already exists in `slang-emit-wgsl.cpp` and just needs porting ([Slang per-target stride for `StructuredBuffer<float3, ScalarDataLayout>` — WGSL is the outlier](../learnings/1780177237717-slang-per-target-stride-for-structuredbuffer-float.md)).

Metal is the **lone** C-like backend that prints FP literals with no type suffix: `MetalSourceEmitter::emitSimpleValueImpl` (`slang-emit-metal.cpp:1128-1164`) omits the MSL `h`/`f` suffix, so a `half` literal like `61440.hf` degrades to a bare double; the fix mirrors the WGSL/HLSL path (#11837) ([Slang Metal backend emits FP literals with NO type suffix (issue #11837)](../learnings/1782814984950-slang-metal-backend-emits-fp-literals-with-no-type.md), [Metal emitter is the lone backend that omits FP literal type suffixes](../learnings/1782832643994-metal-emitter-is-the-lone-backend-that-omits-fp-li.md)).

WGSL is not missing 16-bit floats: at HEAD the WGSL/WebGPU backend fully supports `half`/`f16`, and a "WGSL missing f16" report is almost always the 16-bit **integer** (`bit_cast<uint16_t>`) path surfacing E56103, a different gap (#11835) ([WGSL f16 floats already work; E56103 is the 16-bit-INTEGER path (slang #11835)](../learnings/1782813507927-wgsl-f16-floats-already-work-e56103-is-the-16-bit-.md)). The exception is f16-returning subgroup builtins: Dawn/Tint removed the `subgroups_f16` extension in April 2025, but slang's Windows test-only `slang-tint-0` pin (shader-slang/dawn 9255f960, Sept 2024) still requires it, so a test running f16 subgroup code through `-target wgsl-spirv*` cannot satisfy both ([Tint pin still requires subgroups_f16](../learnings/1792074066723-codex-critique-cwd-workspace-agent-can-make-codex-.md)).

## WGSL Control-Flow Emission: Trailing Switch-Case Break, Native `loop`, Tint's Loop Counter

Slang's WGSL emitter ends every switch `case`/`default` with `break;`. A first analysis called it valid-but-redundant and downgraded #11946 to cosmetic ([WGSL trailing break in switch cases is VALID (redundant) — verify validator claims via DeepWiki](../learnings/1783296818057-wgsl-trailing-break-in-switch-cases-is-valid-redun.md)). It **is** a real bug, because **older naga rejects** it: verify validator claims across toolchain VERSIONS, not just current source ([CORRECTION: WGSL redundant switch-case break IS a real bug (older naga rejects)](../learnings/1783300097186-correction-wgsl-redundant-switch-case-break-is-a-r.md)). The tempting gate `!supportsSwitchFallThrough()` is **wrong**: HLSL/FXC also returns false yet requires the break, so it is not a proxy for "target needs a switch-case break" ([supportsSwitchFallThrough is not a proxy](../learnings/1783300771712-slang-supportsswitchfallthrough-is-not-a-proxy-for.md)).

Until PR #13071 (merged 2026-09-28, for #13066), `CLikeSourceEmitter::emitRegion` hard-coded `for(;;)` for every `LoopRegion` (slang-emit-c-like.cpp:3794 at a90dfa31), and WGSL inherited it. The PR added a `getUnconditionalLoopHeader()` hook that `WGSLSourceEmitter` overrides to print `loop`; no `continuing {}` block is needed because the restructurer folds the condition into the body and emits no continue clause. Test: tests/wgsl/loop.slang; PR #13312 refreshed stale docs/generated tests. Labels: `WebGPU` + `GoodFirstBug` (reporter-offered enhancement; no `bug`/`reproduced`) ([WGSL loop emission: for(;;) changed to native loop by PR #13071](../learnings/1792156297428-wgsl-loop-emission-for-changed-to-native-loop-by-p.md)).

That loop shape has a cost on Tint, which #13733 reports as "loops are emitted with the increment in the body (no continuing/for), so Tint's robustness counter blocks unrolling; [unroll] is dropped". Slang never emits the IR continue block as a separate region: the restructurer copies it into the body at every `continue` and at the end of the body (`slang-ir-restructure.cpp:424-451`). Tint's robustness pass, PreventInfiniteLoops, adds a `4294967295` iteration counter to every loop it cannot prove finite, and the proof (`src/tint/lang/core/ir/analysis/loop_analysis.cc` in Dawn) is narrow. It skips a loop only when the index is an i32/u32 `var` in the `ir::Loop` Initializer, which only a WGSL `for` init fills (never `loop` or `while`); the only store to the index is `v = v + 1` or `v = v - 1` in the Continuing block; and the first `if` in the body (only loads and binaries may precede it) compares the index against a constant with `< > <= >=`, with a `break` in one arm. So `for (var p = 0; ; p = p + 1) { if (p <= 3) {} else { break; } … }` passes, with or without a `continue`. These still get the counter: a `var p` declared before `loop { … continuing { p = p + 1; } }`, a `break if` in `continuing`, any `while`, a store of a value computed in the body, and a runtime bound. Fourteen probe shapes confirmed this with node `webgpu` 0.6.2 and `create(['backend=vulkan','enable-dawn-features=dump_shaders'])`; grep the dump for `4294967295` to find the counter (harness: slang-triager `/workspace/agent/scratch-13733/dump.mjs`, with `node_modules` symlinked from `scratch-13666`) ([Tint PreventInfiniteLoops: only a `for` with var-in-init and a ±1 update is provably finite](../learnings/1792251784378-tint-preventinfiniteloops-only-a-wgsl-for-with-var.md)). Running WGSL through Dawn on the GPU is on [[wiki/concepts/slang-backends-wgsl-on-gpu-execution.md]].

Counted-`for` emission (PR #13740) does not remove every counter, because many loops come from the core module rather than user code (#13765). Vector overloads in `hlsl.meta.slang` with no `case wgsl:` arm fall through to `VECTOR_MAP_*` (hlsl.meta.slang:7957), a plain `for` with no `[ForceUnroll]` (the `glsl.meta.slang` copies of the macro do have it), so each such overload becomes a helper `loop` and gets a counter. #13740 cut the reporter's shader from 5 counters to 1. The survivor is the one-trip `loop { ...; break; }` wrapper that `inlineMultipleBlockFuncBody` (slang-ir-inline.cpp:821) puts around a `[ForceInline]` callee: on WGSL and GLSL it stays when the callee body contains a `for`, and goes when the body has only an `if`. To get no loop at all, use per-target `case wgsl:` arms or `[ForceUnroll]`; a vector bit test such as `(asuint(x) & 0x7fffffffu) > 0x7f800000u` on `vector<float,N>` compiles to a loop-free `bitcast<vec3<u32>>` compare [VECTOR_MAP loops and the inline one-trip wrapper leave a Tint counter](../learnings/1792502293606-wgsl-vector-map-loops-the-inline-one-trip-wrapper-.md). (Building that PR head in a fresh worktree failed on submodules with `--reference` to a shallow clone; `cp -a` of each `external/<sub>` from the main checkout fixed it.)

## Entry-Point Output-Struct Flatten Desyncs Var-Layout (Metal/WGSL Crash)

slang#8183: a vertex entry point whose OUTPUT struct has a nested-struct member and a field with no user semantic segfaults on `-target metal`/`-target wgsl` only, the two targets that run this legalization. `wrapReturnValueInStruct` captures the result layout for the original struct; `maybeFlattenNestedStructs` then adds leaf fields **without rebuilding the layout**, and `ensureStructHasUserSemantic` walks the flattened fields with a POSITIONAL index into the stale layout, null-dereferencing `findOffsetAttr` once the index passes the original field count. Fields that already have a semantic `continue` before the lookup, hence the missing-semantic requirement. Fix at the producer (rebuild/remap the flattened var-layout) and/or look up by field KEY with an assert; a bare null-check masks the desync and risks mis-assigned varyings. Reproduces on host with a Debug slangc: full case EXIT=139, explicit semantic → EXIT=0. Sibling to the #9580 front-end varying-layout crash ([Metal/WGSL entry-point output-struct flatten desyncs var-layout](../learnings/1784382530471-slang-metal-wgsl-entry-point-output-struct-flatten.md)).

## Metal fwidth E36107 and the `[require]` / `__target_switch` Pairing Rule

**`fwidth(float2)` on `-target metal` fails with E36107 from a stdlib capability-annotation bug, not a Metal derivative gap (#12165).** Metal has native `fwidth`, but only the SCALAR `fwidth` overload declares `metal`; the VECTOR (`glsl_hlsl_spirv_wgsl`) and MATRIX (`glsl_hlsl_spirv`) overloads omit it, so `fwidth(float2)` binds the vector overload and fails the front-end capability check (no GPU needed). The vector overload needs BOTH the atom in `[require]` AND `case metal: __intrinsic_asm "fwidth($0)";`, because its `__target_switch` has no `case metal:` and no `default:`; the matrix overload needs only the `[require]` fix, since its `default: MATRIX_MAP_UNARY` recurses to the Metal-capable scalar. Do NOT add `metal` to `fwidth_coarse`/`fwidth_fine`: they use `fragmentprocessing_derivativecontrol`, which deliberately omits Metal. E36107 triage: the atom genuinely excludes the target, or a per-function `[require]` is over-restrictive; read the atom def AND the `[require]`, and cross-check a semantic sibling that supports the target ([Metal fwidth E36107 — stdlib require-clause AND target-switch body both need the metal atom](../learnings/1784627957519-metal-fwidth-e36107-stdlib-require-clause-and-targ.md)).

The transferable rule: **the `[require]` edit and the body `case`/`default` are one atomic change** ([widening a [require] set needs the paired __target_switch case](../learnings/1785840965047-widening-a-require-target-set-is-only-half-the-fix.md)). When adding a target atom to an intrinsic's `[require]` in `*.meta.slang`, check that its `__target_switch` has a `case <target>:` or a `default:`; with neither, the edit turns a clear E36107 into an obscure unhandled-target emit failure or empty body. It is the inverse of the case-less-switch mechanic (#12274, `1785418069559`): with no arm for the target, a method-level `[require]` is **inert as a gate** on REMOVE (the empty body trivially passes; the type-level `[require]` gates) and **unhandled emit** on ADD, so read the body, not just the clause. #12165 was a wrong annotation: `ddx`/`ddy` carry `metal` on all three overloads, `fwidth ≡ abs(ddx) + abs(ddy)`, and the `fragmentprocessing` atom (`slang-capabilities.capdef:2344`) lists `fragment + metal`.

## WGSL inout/out Arg from a Global static: Address-Space Mismatch (#12173)

`legalizeCall` (`slang-ir-wgsl-legalize.cpp:14-72`) is the copy-in/copy-out bridge for by-ref args, but it skips the temp for `kIROp_Var/Param/GlobalParam/GlobalVar`. A global `static` is `kIROp_GlobalVar` (`private` a.s.), so it is passed directly as `ptr<private,…>` into a `ptr<function,…>` param, which naga/wgpu rejects (Slang compiles fine; emit-only, `slangc -target wgsl` reproduces, no GPU). Skipping block-local `kIROp_Var` is correct (already `Function`); the global-scope entries are the bug. `legalizeCall` runs BEFORE `specializeAddressSpaceForWGSL`, so the fix discriminates on IR op/scope, not WGSL address space: Approach A narrows the skip-list so global-scope pointer args take the temp path ([WGSL inout/out arg from global static → ptr address-space mismatch (legalizeCall skip-list gap)](../learnings/1784636859545-wgsl-inout-out-arg-from-global-static-ptr-address-.md)).

## Metal Entry-Point Wrapping and Decoration Repointing

**Uniform wrapping (#10675).** Metal wraps entry-point `uniform` params (including `uniform T*`) in a synthesized `EntryPointParams` cbuffer struct passed as one `constant*` `[[buffer(0)]]`, so a pointer param costs an extra hop (`entryPointParams->args->…`); SPIR-V routes them to a push constant with no wrapper. The divergence is `slang-parameter-binding.cpp:3420`: only `if (isKhronosTarget(...))` swaps to push-constant rules, so on Metal `needConstantBuffer` becomes true in `slang-ir-entry-point-uniforms.cpp:264` and every uniform param is wrapped. Both fix shapes are breaking (host-side binding layout shifts): (A) give a `uniform T*` its own Metal buffer index (mirrors SPIR-V, smaller) or (B) stop wrapping Metal entry-point uniforms (cleaner, large fall-out). PARKED for the assignee as a future-year-release decision; pinned by `tests/metal/entry-point-uniform-vertex-struct-output.slang` ([Metal wraps entry-point uniform params (incl pointers) in cbuffer; SPIR-V routes them to push constants](../learnings/1784653655393-metal-wraps-entry-point-uniform-params-incl-pointe.md)).

**Binding loss already fixed (#7669).** #7669 (Metal `StructuredBuffer` entry-point param loses its `[[buffer(0)]]` binding, folded into an uninitialized `KernelContext`) does NOT reproduce at HEAD: PR #11607 fixed it for the later-filed duplicate #11606, and #7669 stayed open only because the PR referenced the duplicate. Root cause is the wrapper-swap decoration-repointing family: `lowerOutParameters` creates a new entry-point wrapper but the hoisted-uniform `IREntryPointParamDecoration` still names the OLD func, so `introduceExplicitGlobalContext` drops the buffer; fixed by `retargetEntryPointParamDecorations()`. For any pre-2026.06 open issue, "refresh master + reproduce at HEAD" is load-bearing ([slang #7669 Metal StructuredBuffer binding loss already fixed by #11607 — verify-at-HEAD caught it](../learnings/1784753556178-slang-7669-metal-structuredbuffer-binding-loss-alr.md)).

**`[[stage_in]]` on a non-entry helper (#13271).** `lowerOutParameters` (reached through `legalizeShaderOutputParamsForMetal` for a vertex struct return or any out param) wraps the entry point and inlines the original only if its `useCount == 1` (slang-ir-lower-out-parameters.cpp:401). An entry-point `uniform` hoisted to a global carries an `IREntryPointParamDecoration` naming the original function, a second use, and `retargetEntryPointParamDecorations` re-points it only after the inline decision (legalize-varying-params.cpp:5450), so the original survives as a helper. Demotion strips only EntryPoint/KeepAlive, so the helper's params keep their VaryingInput `IRLayoutDecoration`, and `MetalSourceEmitter::emitFuncParamLayoutImpl` (slang-emit-metal.cpp:185) prints `[[stage_in]]` on a non-entry function (invalid MSL). `fixEntryPointCallsites` leaks the same way for an entry point called by another: its clone strips the function-level `kIROp_LayoutDecoration`, but `cloneInst` keeps each parameter's. SV_*-only tests (such as #11607's) cannot see this, since system values have no VaryingInput layout; use a user-semantic input (`float3 p : POSITION`). Three separate demotion decoration lists (fix-entrypoint-callsite.cpp, autodiff-fwd.cpp, lower-out-parameters.cpp) point to a producer-side "demote former entry point" helper, not an emitter gate ([Metal [[stage_in]] on a non-entry helper = former entry point not demoted (lowerOutParameters useCount gate)](../learnings/1790389765020-metal-stage-in-on-a-non-entry-helper-former-entry-.md)).

The fix moves the retarget inside `lowerOutParameters`, before that decision, so the original is inlined and deleted. That exposed a cascade: `EntryPointInfo::entryPointDecor` still pointed at the old function's `IREntryPointDecoration`. The old inline path worked only because it called `removeFromParent()` on that decoration (operands intact) before `removeAndDeallocate()` on the function; without it, `packStageInParameters` → `getProfile()` crashes on a null operand. Re-read the decoration from the returned wrapper, which `transferFunctionDecorations` clones onto it. To require a helper signature with no attributes at all, use the FileCheck pattern `{{^[^[]*}} vsB_0({{[^[]*}}){{$}}` ([lowerOutParameters: EntryPointInfo.entryPointDecor goes stale after the wrapper swap; retarget uniform decor before the inline decision](../learnings/1790394201978-metal-loweroutparameters-entrypointinfo-entrypoint.md)).

The `fixEntryPointCallsites` leak is not Metal-only. That pass (`slang-emit.cpp:2364`) runs for every target, and CUDA's `emitSimpleFuncParamsImpl` (`slang-emit-cuda.cpp:1597`) skips system-value params in the declaration while the call site still passes them: on master, `tests/spirv/nested-entrypoint.slang -target cuda -entry outerMain -entry innerMain` declares `innerMain_0()` but calls `innerMain_0(&_S2)`. Stripping the clone's param layouts at the producer (`removeParamLayoutDecorations` in #13284) fixes Metal attributes and CUDA signatures together. When fixing an IR shape for one emitter, grep every emitter that reads the same decoration (`getVarLayout(param)`) and add a test line per affected target [stale param layouts break CUDA too](../learnings/1790761751687-stale-entry-point-param-layouts-on-a-cloned-ordina.md), [CUDA signature mismatch fixed as a side effect of #13284](../learnings/1790758864251-slang-listing-the-callee-entry-point-first-hangs-h.md).

A separate hang on master (no filed issue) uses the same shape: vertex entry point `vsA` calls `vsB`, both returning a struct with `SV_Position`/`TEXCOORD` fields; `-target hlsl -entry vsB -entry vsA` (callee first) spins at 100% CPU for 6+ minutes. GLSL and WGSL hang the same way; Metal, SPIR-V and `-entry vsA` alone (0.3 s) are fine. Wrap slangc in `timeout 60` when cross-target diffing [callee-first entry-point order hangs HLSL/GLSL/WGSL](../learnings/1790758864251-slang-listing-the-callee-entry-point-first-hangs-h.md). ## groupshared-by-ref Multi-Backend Breakage (#10641)

Passing a bare `groupshared` array param **by reference** (#10641 / PR #11709) breaks three C-like backends differently, and a green vk/HLSL/SPIR-V run clears NONE of them. On Metal it is a silent abort in the address-space pass, not the emitter: the param's IR type is `RateQualified(GroupShared, BorrowInOutParam(Array))`, so `as<IRPtrTypeBase>(param->getFullType())` is null and the address space is never specialized; the fix is `getDataType()`/`setDataType()` (unwrap the rate first). On WGSL the callee MUST be inlined BEFORE `legalizeIRForWGSL`, or `legalizeCall`'s copy-in/out bridges a whole-array `var<workgroup>` copy, silently reintroducing the per-invocation copy #10641 removes; `WGSL-NOT: ptr<workgroup` misses it, so assert no whole-array copy and add a behavioral compute lane. Test the actual downstream compiler via a `-target ptx`/NVRTC lane, not just emitted source ([groupshared by-ref param: Metal addr-space + WGSL inline-ordering gotchas (#10641)](../learnings/1784756124264-groupshared-by-ref-param-metal-addr-space-wgsl-inl.md)).

## Pointer Address Space Is Type-Level on Metal/WGSL, Pass-Inferred on SPIR-V

The target's address-space model decides *when* a pointer conflict is caught. On **SPIR-V** a source `int*` is address-space-agnostic; the `specializeAddressSpace` IR pass assigns the storage class (Function/StorageBuffer/Workgroup/PhysicalStorageBuffer) later, so returning pointers in two address spaces is caught in/after that pass: E58005 (`conflicting-return-pointer-storage-classes`), and E58004 for non-returnable classes. On **Metal/WGSL** the address space is PART OF THE TYPE (`Ptr<T, Access, AddressSpace.Device|GroupShared|…, Layout>`), so the same conflict (a `uniform int*` device pointer on one path, a `__getAddress(groupshared)` threadgroup pointer on another) is a plain type mismatch, **E30019**, reported in semantic checking before the pass ever runs. Empirically, Metal allows returning pointers (a `uniform int*` passthrough and a same-address-space return compile). `__getAddress` (spelled-out `&`) works on Metal (`tests/metal/metal-pointer-params.slang`, `pointer-in-buffer-getaddress.slang`); on a **function-local** it gives E31160 ("cannot take the address of a function-local variable on this target"); on a structured-buffer subscript `buf[i]` it is a pre-existing frontend limitation on ALL targets (#10841); and `&gShared` (groupshared) in a Metal/WGSL/GLSL compute entry point can give E36107 ("unavailable features in entry point"), which is context-specific, not "no pointers on this target." Meta-lesson (maintainer-enforced): any "X cannot reach Y" claim in code/PR comments needs a citation or failing repro, not prose; name the enforcing diagnostic (with a test), or weaken it to "not attempted; covered by construction" ([Pointer address space is type-level on Metal/WGSL but pass-inferred on SPIR-V](../learnings/1789546490977-pointer-address-space-is-type-level-on-metal-wgsl-.md)).
