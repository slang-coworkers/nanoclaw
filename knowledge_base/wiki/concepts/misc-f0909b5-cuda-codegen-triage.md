## TL;DR

The CUDA/OptiX target has a recurring family of codegen defects where slangc exits 0 but emits source NVRTC rejects (or, worse, silently produces a wrong-memory or empty kernel). Several distinct bug shapes recur:

- **Silent misroute / silent-empty:** `shaderRecordEXT ConstantBuffer` at global scope is folded into `GlobalParams` instead of the SBT; empty-prelude "case-present-but-stub" bodies yield silent empty kernels — a third variant beyond the case-LESS and un-instantiated-template families.
- **Commented-out `static_assert(false)` stubs are silent dropped stores:** #8863 disabled them in `surf{1D,2D}Layeredwrite_convert` / `tex1Dfetch_int` because nvcc fires them uninstantiated; since v2025.21 these calls compile to nothing (#13554, #12630). Use a dependent `static_assert(sizeof(T) == 0, ...)`.
- **Type-name failures wear two faces:** when `calcTypeName` fails (e.g. `Texture2DMS`), a Debug build ICEs on a `kNullHandle` assert while a Release build emits a typeless field — reproduce on BOTH configs to get the pinpoint.
- **SampleGrad on CUDA** mirrors the SampleLevel case with `tex*Grad`, but 3D/cube gradients are `float4`, so Slang's float3 gradients need `make_float4(...)`; `cuda` must also join the `[require(...)]` set or E36107 fires.
- **Texture atomics on CUDA emit `atomicAdd(handle[coord], v)`** because the CUDA atomic emit cases never check `isTextureAccess()`; PTX `sured.b.add` assembles, `suatom` does not, so a value-returning atomic needs a CAS loop or a diagnostic.
- **Texture ops:** masked stores need the read-modify-write legalization already shipped on Metal/GLSL/SPIRV; a CUDA-local IR rewrite reusing the meta.slang accessors is the *principled* route (avoids a second source of truth for surf2D addressing). Element-vs-vector emit (`$T0`→`$TR`) fixes Gather but NOT SampleLevel (return-type shape differs). CUDA `tex*<T>` built-ins (`__nv_itex_trait`) cover char/short/int/long/float at widths 1, 2 and 4 only, with no 3-component type and no `__half`, so every 3-component sample needs a widen-and-truncate arm (#12634 hit all of them, not only `Texture3D<float3>.SampleLevel`). Half sampled reads (`tex2DLod<__half4>`) are unsupported by construction — diagnostic, not fix.
- **Array/matrix init:** a `__device__` global initializer must be a brace literal (even `makeMatrix(...)` of literals is dynamic init). CUDA/CPP arrays are `struct FixedArray<T,N>` needing TWO brace levels per dimension; nested static-const arrays emitted as dynamic `__device__` init (#12635, FIXED by #12688); a `static const` array of a *struct* instead localizes per-invocation (#13107, open) — the divergence is by ELEMENT TYPE via the `isSimpleConstantType` struct gap.
- **Immutable-load `__ldg` guard:** the `__constant__` launch-param group is classified immutable via the `kIROp_ConstantBufferType` type-case in `isPointerToImmutableLocation` (NOT `AddressSpace::Uniform`); `__ldg` needs a global address so the guard (#13091) skips it when `getRootAddr` roots at an `IRGlobalParam` of `IRUniformParameterGroupType`. `getRootAddr`'s peel-set suffices here (no acquisition cast, unlike the SBT case).
- **Silent name mismatch:** an entry point named `main` is renamed `main_0` at emit time on CPU/CUDA/Metal, after reflection recorded `main`, so a runtime lookup by `getNameOverride()` fails (#13264).
- **Right layer to reject unsupported types:** `checkUnsupportedInst`'s module-level global walk (IR types are hoisted + deduplicated), gated to the exact failing target — not a recursive struct-field descent, not an emit-layer helper with no SourceLoc.

Cross-cutting repro trick: `slangc -target cuda` emits CUDA C++ source with NO GPU (grep for the bad emit); `-target ptx` invokes NVRTC. A PTX repro is an NVRTC compile check that needs no GPU, so don't punt it as hardware-gated. Executing one is different, and agent containers can do it: they have an NVIDIA L40S with CUDA (plus CUDA 12.6 `nvcc`/`ptxas`/NVRTC), so runtime CUDA checks run locally. Confirm with `nvidia-smi -L` each session; the 2026-09-28→10-16 no-GPU window was a host passthrough outage, now fixed ([Agent containers have no GPU since ~2026-09-28 (historical: 09-28→10-16 outage)](../learnings/1792089571497-agent-containers-have-no-gpu-since-2026-09-28-host.md)).
- **NVRTC accepts only plain-literal leaves in a `__device__` constant table**: `make_float2`, `makeMatrix<>`, `__half(...)`, `SLANG_INFINITY` and builtin calls are rejected as dynamic initialization. Probe each leaf type on `-target ptx` before keeping more constants global.

## Silent miscompiles and silent-empty kernels

Two atoms document CUDA paths that produce no diagnostic and a wrong or empty result. `layout(shaderRecordEXT) ConstantBuffer<T> g;` at global scope is silently misrouted into `GlobalParams` and read via `__ldg` instead of `optixGetSbtDataPointer()`, because `getShaderRecordConstantBufferRules()` returns the ordinary layout family ("following HLSL's lead") and `collect-global-uniforms` filters only on `LayoutResourceKind::Uniform` — there is no `ShaderRecord` check ([CUDA ignores shaderRecordEXT on global ConstantBuffer](../learnings/1787171496782-cuda-ignores-shaderrecordext-on-global-constantbuf.md)). SPIR-V honors the same global, so the gap is CUDA-specific. Separately, the CUDA/PTX empty-prelude family gained a **third variant**: a `case cuda:` that IS present but whose template body is an empty stub — because the case exists, the catch-all `static_assert(false)` never fires, giving a silent empty kernel identical in symptom to the case-LESS variant but different in mechanism ([CUDA prelude empty-body third silent variant](../learnings/1787171580700-cuda-prelude-empty-body-a-third-silent-empty-varia.md)). The discriminator table: case-LESS → silent-empty; case-present + empty stub → silent-empty; case-present + declared-but-never-instantiated → loud undefined-symbol.

The stub family also has a variant that was silenced on purpose. #8863 (fixing #8862) commented out `static_assert(false, ...)` in empty CUDA prelude template stubs (`surf{1D,2D}Layeredwrite_convert`, `tex1Dfetch_int`), because nvcc and older clang fire a non-dependent `static_assert(false)` even when the template is never instantiated. Every call to these stubs has since been a silent no-op: NVVM deletes the store and slangc exits 0 (#13554, #12630). This has been silent since v2025.21; v2025.19 and v2025.20 failed loudly in NVRTC. The portable replacement is a dependent assert, `static_assert(sizeof(T) == 0, "...")`, which on nvcc 12.6 does not fire for an uninstantiated template and does fire once it is instantiated. Hardware facts for the layered-store fix: `sust.p.a2d` / `sust.p.a1d` (formatted layered surface store) assemble with ptxas 12.6 for sm_50-90 (SASS `SUST.P.2D_ARRAY`), and LLVM NVPTX defines `int_nvvm_sust_p_{1d,2d}_array_*`, even though the PTX ISA 9.4 syntax table lists `sust.p` only for 1d/2d/3d. Coordinates are `{layer, x, y, ignored}` for a2d and `{layer, x}` for a1d. `suld.p` was removed in PTX 3.0, so there is no formatted layered READ in hardware. The removal note covers only `suld.p` and `sust.p.{u32,s32,f32}`; `sust.p.b32` is current, contrary to draft #11090's plan doc ([commented-out static_assert(false) stubs turn loud failures into silent dropped stores](../learnings/1791590928570-cuda-prelude-commented-out-static-assert-false-stu.md)).

A subtler two-faced failure: when the CUDA/C++ emitter cannot compute a type name (`calcTypeName` fails for multisample `Texture2DMS`), `_getTypeName` leaves a `kNullHandle`. In **Debug** this fires `SLANG_ASSERT(handle != kNullHandle)` (an ICE, exit 255); in **Release** the assert is compiled out and the emitter writes a struct field with a name but no type, which NVRTC then rejects — so the same root cause looks like two separate bugs ([CUDA unsupported-type null-handle: Debug ICE vs Release typeless field](../learnings/1787173483661-cuda-unsupported-type-null-handle-same-bug-wears-t.md)). Reproduce on both configs — the Debug ICE gives the exact assert file:line the release symptom hides.

## The `__constant__` param-group immutable-load `__ldg` guard (#13091/#13088)

CUDA's immutable-load pass rewrites reads of immutable memory to `__ldg` (NVRTC `ld.global.nc`), but `__ldg` needs a *global* address, and the synthesized `SLANG_globalParams` launch-parameter group is constant-memory (`extern "C" __constant__`), not global — so an inline `__constant__` group field read was wrongly getting `__ldg`. PR #13091 (fixes #13088) added a guard in `slang-ir-cuda-immutable-load.cpp` that skips `__ldg` when `getRootAddr(load->getPtr())` is an `IRGlobalParam` of `IRUniformParameterGroupType`. The classification that *makes* the guard necessary is subtle and a triage memo plus two reviewers propagated a wrong mechanism: the group is NOT a pointer with `AddressSpace::Uniform`. Its IR is `%globalParams : ConstantBuffer(%GlobalParams) = global_param` — an `IRConstantBufferType` (an `IRUniformParameterGroupType`) — and an inline read is `load(get_field_addr(%globalParams, field))`, so `getRootAddr` peels FieldAddress/GetElementPtr to `%globalParams`. `isPointerToImmutableLocation` (slang-ir-util.cpp:3110-3162) then returns true through its **`kIROp_ConstantBufferType` type-switch case (~3137)**, which sits BEFORE the `IRPtrTypeBase` address-space branch (~3147-3160); because the root is a ConstantBuffer type (not a Ptr), the `AddressSpace::Uniform` case (~3154) is NEVER reached for this input. The immutability classification is *correct*; the discriminator the fix needs — "is it CUDA `__constant__`" — is recorded by no type/address-space marker, only by the emitter's rule (an `IRGlobalParam` of `IRUniformParameterGroupType` → `extern "C" __constant__`, `CUDASourceEmitter::emitParameterGroupImpl`; gate in `emitGlobalParam`), which is what the guard keys on. Structural coherence: the OptiX SBT root is ALSO `ConstantBuffer<>`-typed, so it too returns true at 3137 — which is why SBT is excluded earlier at 3116 (`isAddressIntoOptiXShaderBindingTable`, host-mutated between dispatches); two parallel exclusions of ConstantBuffer-typed immutable roots for different reasons ([__constant__ group is immutable via the ConstantBufferType type-case, not AddressSpace::Uniform](../learnings/1789474416332-cuda-constant-group-is-classified-immutable-via-co.md), [same, traced to the 3137 type-case before the AddressSpace branch](../learnings/1789474331137-inline-cuda-constant-group-loads-hit-ispointertoim.md)).

Reusing `getRootAddr` here (rather than mirroring the SBT `isAddressIntoOptiXShaderBindingTable` peel-*walker*) is correct even though prior art (#10188 false-safe → #12119) makes any `getRootAddr`-keyed guard suspect: `getRootAddr` peels only `{GetElementPtr, FieldAddress, NodeOutputRecordGetElementPtr}`, NOT `BitCast`/`GetOffsetPtr`/`Reinterpret`/`PtrCast`, so the question is whether a cast/offset can sit between the `Load` and the group and defeat it. It can't, for a structural reason: the #10188 SBT casts came from pointer ACQUISITION (`GetOptiXSbtDataPtr` reinterpreted to the element type — the cast getRootAddr couldn't peel, which is why #12119 keyed its walker on `GetOptiXSbtDataPtr` *inside* `isPointerToImmutableLocation`), whereas the `__constant__` group has NO acquisition cast — it is a direct `IRGlobalParam` accessed structurally via `FieldAddress`/`GetElementPtr`. CUDA also uses the Default buffer-element lowering policy + Natural layout, a near-no-op (identity for bool/8-64-bit/half-float-double/vectors; bool→int is SPIR-V-direct-only; row-major matrices identity), so no `CastStorageToLogical` is spliced into the access chain (identity members ⇒ the group is `continue`-skipped in lower-buffer-element-type). Adopt the SBT-style peel-walker only if CUDA ever legalizes a group field into a cast-bearing chain (a future `shouldUseDXLayout` → `D3DConstantBuffer` change would lower more matrices but still via FieldAddress/GetElementPtr — no new cast source). Review-craft note both reviewers flagged: pair a negative-only guard regression test with a positive test that exercises the guard's *false* branch — a `StructuredBuffer` positive case does NOT (it takes the unconditional `kIROp_StructuredBufferLoad` case, never reaching the `kIROp_Load` guard); use a `ConstantBuffer<T>`/`ParameterBlock` field read (a `kIROp_Load` rooted at a `Load`) instead ([getRootAddr peel-set is sufficient for the CUDA constant-param group, unlike the SBT peel-walker](../learnings/1789472511569-getrootaddr-is-sufficient-for-cuda-constant-param-.md)).

## Texture store/sample lowering

The masked-store bug (`gTex[i].w = 1.0f` on `RWTexture2D` emitting an invalid `handle[coord]->w`) reframes the "fix or diagnose?" question: the read-modify-write lowering (`legalizeImageSubscript`) is Slang's **accepted, shipped behavior** on Metal/GLSL/SPIRV, so a CUDA-only compile-time error would be an unprincipled cross-backend divergence ([CUDA masked texture store — fix-vs-diagnostic reframed by RMW precedent](../learnings/1787171977334-cuda-masked-texture-store-fix-vs-diagnostic-refram.md)). But "just add CUDA to the legalize switch" is insufficient because there are **two distinct IR representations** of a texture write: `kIROp_ImageLoad/Store` (rendered only by Metal/GLSL/SPIRV native handlers) versus calls to the meta.slang `__subscript` accessors (the ONLY path reaching surf2Dread/surf2Dwrite for CUDA). Adding CUDA to the switch would emit ops the CUDA emitter can't render AND re-derive all surf2D addressing that already lives once in meta.slang — a second source of truth. So a CUDA-local IR rewrite (`tmp=gTex[i]; tmp.w=v; gTex[i]=tmp;`) reusing the existing accessors is the MORE principled route for CUDA, the inverse of the other backends ([CUDA texture write has two IR representations](../learnings/1787172436124-cuda-texture-write-has-two-ir-representations-rmw-.md)).

Texture atomics fall through the same gap (#12636). `InterlockedAdd(RWTexture2D<uint>[c], v)` on CUDA/PTX emits `atomicAdd(handle[coord], v)` on a `CUsurfObject`, which NVRTC rejects. The texture `ref` accessor is `kIROp_ImageSubscript`; `legalizeImageSubscript` runs only for Metal, GLSL and SPIR-V (`slang-emit.cpp` ~2464) and handles only stores. The GLSL and Metal atomic emit cases check `isTextureAccess()`, but the CUDA `kIROp_Atomic*` cases (`slang-emit-cuda.cpp` ~800) do not, so the subscript reaches the generic `handle[coord]` path in `slang-emit-c-like.cpp`. The 2-arg and 3-arg overloads both fail, because they share one `hlsl.meta.slang` template. Hardware probe: nvcc 12.6 for sm_89 assembles inline PTX `sured.b.add.2d.u32.trap [s, {x*4, y}], v;` (x in bytes, as in the existing `surf2Dwrite` helpers), but rejects `suatom` as an unknown instruction, so the overload that returns the original value needs a CAS loop or a diagnostic. No enabled CUDA test covers texture atomics: `tests/compute/spirv-multisampled-array-texel-pointer-atomic.slang` has `DISABLE_TEST(cuda)` ([CUDA texture atomics: no ImageSubscript lowering; PTX sured works, suatom does not](../learnings/1792163961349-cuda-texture-atomics-no-imagesubscript-lowering-pt.md)).

Two element-vs-vector emit gaps: the `$T0`→`$TR` swap (call return-type vs texture element-type in `slang-intrinsic-expand.cpp`) fixes **Gather** (whose signature returns `vector<T.Element,4>`, so `$TR` = `float4`) but NOT **SampleLevel** (whose signature returns plain `T`, so `$TR` = the narrow `float3`) — SampleLevel must widen to a 4-component result independently, mirroring the SPIRV arm's `__sampledType(T)`+`__truncate` ([CUDA texture element-vs-vector: $T0→$TR fixes Gather but not SampleLevel](../learnings/1787219149444-cuda-texture-element-vs-vector-t0-tr-swap-fixes-ga.md)). The cause is CUDA's built-in type set. The texture-object built-ins (`tex1D/tex2D/tex2DLod/...<T>`) are gated by `__nv_itex_trait<T>` (CUDA 12.6 `texture_indirect_functions.h:66-104`), which specializes char, signed/unsigned char, short, ushort, int, uint, long, ulong and float, each as a scalar and as 1-, 2- and 4-component vectors. There is no 3-component type and no `__half`, so a reply or diagnostic that says "CUDA has no overload" should say "integer and float types, but not `__half`", not "float/int/uint only" (check with `grep -n "__nv_itex_trait<" .../texture_indirect_functions.h`) ([CUDA tex* built-ins type coverage](../learnings/1792421166308-cuda-tex-built-ins-type-coverage-char-short-int-lo.md)). Before the #12634 fix, every CUDA arm in `hlsl.meta.slang` passed `$T0` straight to `tex*<T>`, so NVRTC rejected every 3-component sample, not only the reported `Texture3D<float3>.SampleLevel`. On v2026.14.1 with NVRTC 12.6, `Sample` (`tex3D<float3>`), `Texture2D<float3>.SampleLevel` (`tex2DLod<float3>`) and `Texture3D<int3>`/`<uint3>` also fail (v2026.14.1 lines 3694-3722 for SampleLevel, about 1319 and 2581 for Sample). On those releases, declare the texture as `Texture3D<float4>` and use `.xyz` of the result. Releases before v2026.16.1 fail (an earlier bracket found v2026.16 bad and v2026.17 good); fixed releases emit `_slang_vector_reshape<float,3,float,4>(tex3DLod<float4>(...))`, and the release bracket is on [[wiki/concepts/slang-tooling-release-tarball-repro-and-version-bisect.md]] ([#12634 scope: every 3-component CUDA texture sample](../learnings/1792400048814-slang-12634-scope-every-3-component-cuda-texture-s.md)). And half `SampleLevel` (`tex2DLod<__half4>`) is the OPPOSITE resolution — a diagnostic, because `tex*Lod` are CUDA runtime built-ins with no `__half` overload and no half sampled-read conversion shim exists; the fix mirrors the half `.Load` diagnostic #12303 with a `static_assert(!__isHalf<T>())` guard ([CUDA half SampleLevel gap — sibling of Load gap #12277](../learnings/1787173327448-cuda-half-samplelevel-gap-tex2dlod-sibling-of-load.md)). Adjacent latent gaps (`Sample`, `SampleBias/Grad/Cmp`, `Gather`) share the emit shape.

To add a CUDA lowering for one of those Sample* methods, take the SampleLevel `cuda` case in hlsl.meta.slang (:2415 for combined, :4133 for separate-sampler) as the template. For SampleGrad, CUDA 12.6 `texture_indirect_functions.h` (:470-631) has every object form: `tex1DGrad`, `tex2DGrad`, `tex3DGrad`, `texCubemapGrad`, `tex1DLayeredGrad`, `tex2DLayeredGrad` and `texCubemapLayeredGrad`. The argument order matches `tex*Lod`, with `float level` replaced by `dPdx, dPdy`. 1D gradients are `float` and 2D are `float2`, but 3D and cube gradients are **`float4`**, so Slang's float3 gradients need `make_float4((g).x,(g).y,(g).z,0.0f)` in the `__intrinsic_asm`. The element-type set (`__nv_itex_trait`, :65-104) has no 3-component types and no `__half`, so reuse the `_slang_vector_reshape<E,3,E,4>` arms and the half `static_assert`. `cuda` must also be added to the first argument of `[require(...)]`, otherwise E36107 fires; under `-ignore-capabilities` a missing case compiles to an empty entry point instead (#13555). `-target ptx` runs NVRTC for real and is a GPU-free check: the output should contain `tex.grad.{1d,a1d,2d,a2d,3d,cube,acube}` (prototype for #13556) ([CUDA SampleGrad: tex*Grad mirrors tex*Lod, but 3D/cube gradients are float4](../learnings/1791589496861-cuda-samplegrad-tex-grad-mirrors-tex-lod-but-3d-cu.md)).

## Array init and constant-fold gaps

CUDA/CPP arrays are `struct FixedArray<T,N> { T m_data[N]; }`, so an aggregate initializer needs **two brace levels per array dimension** (outer for the struct, inner for `m_data`); a single brace relies on C++ brace-elision that works for flat arrays but mis-binds nested ones. This was masked for years because the emitter universally hoisted inner rows to named temps — the bug surfaces the moment you fold/inline rows ([CUDA-CPP arrays are struct FixedArray needing two brace levels](../learnings/1787343021129-cuda-cpp-arrays-are-struct-fixedarray-needing-two-.md)). Relatedly, a literal-only nested `static const int values[2][2]` fails NVRTC with "dynamic initialization not supported for a `__device__` variable" because `shouldFoldInstIntoUseSites` returns false for `MakeArray` (an explicit HACK), so each inner row is hoisted to its own `__device__` global and the outer array references them — which NVRTC treats as a runtime initializer. HLSL/GLSL/Metal/CPU accept a constant global referencing another; only CUDA's `__device__` rule forbids it. The fix precedent is WGSL PR #11628's `shouldFoldInstIntoUseSites` override folding a module-scope aggregate inline when all uses are constituents of another aggregate ([CUDA nested static-const arrays emit as dynamic __device__ init](../learnings/1787174886706-cuda-nested-static-const-arrays-emit-as-dynamic-de.md)). The same NVRTC rule covers vectors and matrices, and it is stricter than "all operands are literals": checked with nvcc 12.6 against the CUDA prelude, `__device__ static const Matrix<float,2,2> m = makeMatrix<float,2,2>(0.0f, 1.0f, 2.0f, 3.0f);` is rejected as dynamic initialization because `makeMatrix` is not constexpr, and so is a FixedArray literal of `makeMatrix(...)` elements; only the brace literal `Matrix<float,2,2>{0.0f, ...}` compiles (Slang already emits it for a same-layout `static const` matrix array). So any module-scope vector/matrix value that is not a plain literal (a cast such as `float3(int3(1,2,3))`, or a matrix layout change) breaks CUDA once it becomes a `__device__` global. The CPP/CUDA `shouldFoldInstIntoUseSites` override (slang-emit-cpp.cpp ~1954) deliberately refuses to fold casts, and relaxing that veto at emit only fixes function-local uses; device globals need the cast constant-folded in IR or printed as a brace literal (#13444) ([CUDA __device__ matrix/vector globals: only a brace literal is static init](../learnings/1791305634716-cuda-device-matrix-vector-globals-only-a-brace-lit.md)).

There are TWO distinct `static const` global-array bugs — don't conflate them. That nested-*literal* bug is #12635 (**FIXED** by merged PR #12688), and its symptom is a global-with-dynamic-`__device__`-init. A DISTINCT, still-open bug (#13107) diverges by ELEMENT TYPE, not nesting: a `static const` array of a *struct* (`Record{uint a,b;} recs[2]`) is emitted as a PER-INVOCATION LOCAL `FixedArray` reconstructed *inside* the kernel via synthesized `$init` ctor CALLS (`Record_x24init_0(1U,2U)`), never reaching global scope, while a scalar `static const uint[]` sibling stays `__device__ static const`. Two joint gaps: (1) `inlineGlobalConstantsForLegalization` runs unconditionally for CUDA/CPU-kernel (slang-emit.cpp:1934-1938, to avoid NVRTC-rejected dynamic `__device__` init), and its legality gate `GlobalInstLegalizationInliningContext::isSimpleConstantType` (slang-ir-legalize-global-values.cpp:251-270) accepts ONLY scalar/vector/matrix + arrays-of-those — a struct or array-of-struct hits `return false` at :268 → misclassified illegal-global → force-inlined into every user; (2) struct elements lower to synthesized `$init` ctor CALLS (checker `createInvokeExprForSynthesizedCtor` → `IRCall`), not `MakeStruct`, so the global brace-init folder `isInnerGlobalAggregate` (slang-emit-c-like.cpp:1461-1493, folds only MakeArray/MakeStruct/MakeArrayFromElement, never a Call) can't make them a compile-time-constant global. The complete fix needs BOTH: extend `isSimpleConstantType` to POD structs/arrays-of-struct (recurse fields, reject resource/pointer) AND fold constant synthesized-ctor calls → MakeStruct at module scope. The pass is CUDA/CPU-only ⇒ blast radius is the C-family emitter (CUDA/CPP/Torch share `CPPSourceEmitter`); SPIR-V/HLSL unaffected. GPU-free verify: `slangc t.slang -target cuda -o k.cu`, grep the `.cu` for `FixedArray`/`x24init` inside the kernel body vs `__device__ static const` at file scope ([CUDA static-const struct arrays localize via the isSimpleConstantType struct gap — distinct from #12635](../learnings/1789513281020-cuda-static-const-struct-arrays-localize-via-issim.md)).

**Widening global-constant admission exposes a third CUDA leaf-spelling limit.** When an IR change lets more module-scope constants stay global, the CUDA emitter writes them as `__device__ static const` brace initializers, and NVRTC (12.6) rejects some leaf spellings with "dynamic initialization is not supported for a __device__ variable" while DXC, SPIR-V and glslang accept the same values. Rejected on PR #13115: `make_float2(...)` (vector fields), `makeMatrix<T,R,C>(...)` (matrix fields), `__half(...)` (half fields; a plain `half` array is rejected even on master), `SLANG_INFINITY`, and any builtin call such as `F32_sqrt(...)`. `(0.0 / 0.0)` for NaN is accepted, and plain-typed arrays emit `float2 { 1.0f, 2.0f }`, which is fine. Probe each struct-field leaf type on `-target ptx` before widening admission: shader-slang/slang had zero tests with vector-, matrix- or half-field struct tables, so a corpus A/B sweep could not see this. If a constructor call is folded into `makeStruct` but the table still gets inlined, roll the fold back, or the per-invocation code changes and can leave stray element globals (a `const` in WGSL) [CUDA __device__ constant tables need plain-literal leaves](../learnings/1792139832211-slang-cuda-device-constant-tables-must-have-plain-.md). The general method lesson is on [Slang build in worktrees](slang-tooling-f0909b0-build-worktree-cmake.md) (A/B corpus coverage).

## Documentation accuracy for CUDA intrinsics

A doc/comment claiming CUDA `half2` arithmetic is "packed SIMD / one instruction per op" is FALSE on two counts and codex will block it: division is never packed (`__h2div` calls scalar `__hdiv` twice), and even `+ - * unary-` are architecture-gated (`NV_IF_ELSE_TARGET(NV_PROVIDES_SM_53, ...)`) — packed only on compute capability 5.3+, scalar fallback otherwise ([Documenting CUDA half2 packed SIMD needs a per-op and an SM_53 caveat](../learnings/1787236121791-documenting-cuda-half2-packed-simd-needs-both-a-pe.md)).

## The principled layer to reject an unsupported type

When rejecting an unsupported *type* on a target, put a `case kIROp_<Type>:` in the **module-level global walk** `checkUnsupportedInst(IRModule*, target, sink)`, NOT a recursive descent into struct fields — Slang IR types are hoisted to global scope and deduplicated, so a `Texture2DMS<float>` used anywhere appears as one top-level global inst and one `case` catches every use site with one diagnostic ([checkUnsupportedInst — reject unsupported types at the hoisted global](../learnings/1787278343860-checkunsupportedinst-reject-unsupported-types-at-t.md)). Gate to the exact failing target (`isCUDATarget`, not the broader `isKernelCPPOrCUDASourceTarget` which includes CPPSource where the type lowers fine — the #11659 over-broad-rejection trap). This is the same layer/shape as the #11297 `String`-on-kernel-target rejection.

## Entry point `main` is renamed at emit time, after reflection recorded it (#13264)

On CPU, CUDA (+PTX) and Metal, `CLikeSourceEmitter::maybeMakeEntryPointNameValid` (slang-emit-c-like.cpp:1130-1143, PR #7105) renames an entry point named `main` to a counter-suffixed name (`main_0`). The rename happens at emit time, after the per-target layout recorded the name, so `EntryPointReflection::getNameOverride()` still returns `main`, and runtimes that look up the kernel by that name fail: slang-rhi's CUDA `cuModuleGetFunction`, CPU `findSymbolAddressByName`, Metal `newFunction`, and the OptiX prefix+name. An explicit `renameEntryPoint("x")` does flow to the emitted symbol, because the linker writes it into `IREntryPointDecoration`. The rename itself is required (nvcc rejects a `__global__ main`), and no public API exposes the emitted symbol; DeepWiki wrongly claims `getNameOverride` returns it. A separate slang-rhi trap: CUDA `RootShaderObjectLayoutImpl::getEntryPointIndex` compares the override-derived lookup name against `getName()`, so any renamed entry point gets -1. A quick GPU harness is Slang API → `getEntryPointCode(SLANG_PTX)` → `cuModuleLoadData` → `cuModuleGetFunction(getNameOverride)` ([Slang renames entry main at emit time on CUDA/CPU/Metal; reflection never sees it](../learnings/1790318957835-slang-renames-entry-main-at-emit-time-on-cuda-cpu-.md)).
