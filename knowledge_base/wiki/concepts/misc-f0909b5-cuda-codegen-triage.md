## TL;DR

- The recurring CUDA/OptiX defect: slangc exits 0 but emits source NVRTC rejects, or a wrong-memory or empty kernel.
- GPU-free repro: `-target cuda` emits source to grep; `-target ptx` runs NVRTC (a compile check, never "hardware-gated"). Containers have an L40S + CUDA 12.6 for runtime checks (`nvidia-smi -L`).
- Silent paths: a global `shaderRecordEXT ConstantBuffer` is folded into `GlobalParams` instead of the SBT; an empty prelude stub (case-less, or case-present with an empty body) gives a silent empty kernel; the commented-out `static_assert(false)` stubs (#8863) have been silent dropped stores since v2025.21 — use a dependent `static_assert(sizeof(T) == 0, ...)`.
- A `calcTypeName` failure (e.g. `Texture2DMS`) is a Debug ICE on a `kNullHandle` assert but a typeless field in Release — reproduce on BOTH configs.
- Reject an unsupported type with a `case` in `checkUnsupportedInst`'s module-level global walk, gated to the exact failing target — not a struct-field descent or an emit helper.
- Masked texture stores: RMW is shipped on Metal/GLSL/SPIR-V, so CUDA gets it via a CUDA-local IR rewrite reusing the meta.slang accessors, not a CUDA-only error.
- Texture atomics emit `atomicAdd(handle[coord], v)` because the CUDA atomic emit cases never check `isTextureAccess()`; PTX `sured.b.add` assembles, `suatom` does not, so a value-returning atomic needs a CAS loop or a diagnostic.
- CUDA `tex*<T>` (`__nv_itex_trait`) covers char/short/int/long/float at widths 1, 2, 4 only — no 3-component type, no `__half`. Every 3-component sample needs a widen-and-truncate arm; `$T0`→`$TR` fixes Gather but not SampleLevel. Half sampled reads are a diagnostic (`static_assert(!__isHalf<T>())`), not a fix.
- SampleGrad mirrors SampleLevel with `tex*Grad`, but 3D/cube gradients are `float4`; `cuda` must join `[require(...)]` or E36107 fires.
- A `__device__` global initializer must be a brace literal with plain-literal leaves: `makeMatrix(...)`, `make_float2`, `__half(...)`, `SLANG_INFINITY`, builtin calls and casts are all dynamic init. Probe each leaf type on `-target ptx` before keeping more constants global.
- CUDA/CPP arrays are `struct FixedArray<T,N>`: two brace levels per dimension.
- Two distinct `static const` array bugs: nested literal arrays as dynamic `__device__` init (#12635, fixed by #12688) vs struct-element arrays localized per invocation (#13107, open; workaround: pack records into `uint2`/`uint4`).
- `__ldg` guard (#13091): the `__constant__` group is immutable via the `kIROp_ConstantBufferType` case of `isPointerToImmutableLocation`, NOT `AddressSpace::Uniform`; the guard keys on an `IRGlobalParam` of `IRUniformParameterGroupType` and `getRootAddr` suffices. Pair a negative guard test with a `ConstantBuffer` positive.
- Buffer ABI is pointer + `size_t count`; `SLANG_CUDA_STRUCTURED_BUFFER_NO_COUNT` changes the prelude but reflection still reports 16 bytes, so a pointer-only ABI must change the layout rules too.
- A `T*` pointee on CUDA is laid out with scalar rules (`struct { float a; float4 c; }` → size 20, align 4, `c` at 4) while nvcc gives the emitted struct size 32, align 16, `c` at 16; buffers and uniforms reflect CUDA rules correctly, so only the pointer path disagrees (`float2`/`float4` fields; `double` agrees).
- An entry point named `main` is renamed `main_0` at emit time after reflection recorded `main`, so runtime lookup by `getNameOverride()` fails (#13264).
- CUDA `half2` division is never packed, and packed `+ - * neg` exist only on SM 5.3+.

## Repro without (and with) a GPU

Most of these bugs are confirmed by grepping `-target cuda` output or compiling `-target ptx`. To run a kernel, agent containers have an NVIDIA L40S with CUDA 12.6 `nvcc`/`ptxas`/NVRTC; confirm with `nvidia-smi -L` each session; the 2026-09-28→10-16 no-GPU window was a host passthrough outage, now fixed ([operator correction: coworker containers have an NVIDIA L40S](../learnings/1792133264162-coworker-containers-have-an-nvidia-l40s-gpu-cuda-vulkan.md); historical: [no GPU since ~2026-09-28](../learnings/1792089571497-agent-containers-have-no-gpu-since-2026-09-28-host.md)).

## Silent miscompiles and silent-empty kernels

`layout(shaderRecordEXT) ConstantBuffer<T> g;` at global scope is silently misrouted into `GlobalParams` and read via `__ldg` instead of `optixGetSbtDataPointer()`: `getShaderRecordConstantBufferRules()` returns the ordinary layout family ("following HLSL's lead") and `collect-global-uniforms` filters only on `LayoutResourceKind::Uniform`, with no `ShaderRecord` check. SPIR-V honors the same global, so the gap is CUDA-specific ([CUDA ignores shaderRecordEXT on global ConstantBuffer](../learnings/1787171496782-cuda-ignores-shaderrecordext-on-global-constantbuf.md)).

The empty-prelude family has three mechanisms: case-LESS → silent-empty; case-present + empty stub body → silent-empty (the case exists, so the catch-all `static_assert(false)` never fires; e.g. #12630 `Texture1D.Load`); case-present + declared-but-never-instantiated → loud undefined-symbol ([CUDA prelude empty-body third silent variant](../learnings/1787171580700-cuda-prelude-empty-body-a-third-silent-empty-varia.md)).

One stub variant was silenced on purpose. #8863 (fixing #8862) commented out `static_assert(false, ...)` in `surf{1D,2D}Layeredwrite_convert` and `tex1Dfetch_int`, because nvcc and older clang fire a non-dependent `static_assert(false)` even for an uninstantiated template. Since v2025.21 every call is a silent no-op (NVVM deletes the store; #13554, #12630); v2025.19-20 failed loudly in NVRTC. The replacement is a dependent `static_assert(sizeof(T) == 0, "...")`, which nvcc 12.6 fires only on instantiation. For the layered-store fix: `sust.p.a2d` / `sust.p.a1d` assemble with ptxas 12.6 for sm_50-90 (SASS `SUST.P.2D_ARRAY`; LLVM `int_nvvm_sust_p_{1d,2d}_array_*`) though PTX ISA 9.4 lists `sust.p` only for 1d/2d/3d; coordinates are `{layer, x, y, ignored}` (a2d) and `{layer, x}` (a1d). `suld.p` was removed in PTX 3.0, so there is no formatted layered READ; the removal covers only `suld.p` and `sust.p.{u32,s32,f32}` — `sust.p.b32` is current, contrary to draft #11090's plan doc ([commented-out static_assert(false) stubs turn loud failures into silent dropped stores](../learnings/1791590928570-cuda-prelude-commented-out-static-assert-false-stu.md)).

When `calcTypeName` fails (multisample `Texture2DMS`), `_getTypeName` leaves a `kNullHandle`: Debug fires `SLANG_ASSERT(handle != kNullHandle)` (ICE, exit 255), Release compiles the assert out and writes a struct field with a name but no type, which NVRTC rejects. Same root cause, two apparent bugs; the Debug ICE gives the file:line the Release symptom hides ([CUDA unsupported-type null-handle: Debug ICE vs Release typeless field](../learnings/1787173483661-cuda-unsupported-type-null-handle-same-bug-wears-t.md)).

## The `__constant__` param-group immutable-load `__ldg` guard (#13091/#13088)

CUDA's immutable-load pass rewrites reads of immutable memory to `__ldg` (`ld.global.nc`), which needs a *global* address; the synthesized `SLANG_globalParams` group is `extern "C" __constant__`, so inline group-field reads were wrongly getting `__ldg`. PR #13091 added a guard in `slang-ir-cuda-immutable-load.cpp` that skips `__ldg` when `getRootAddr(load->getPtr())` is an `IRGlobalParam` of `IRUniformParameterGroupType`. A triage memo and two reviewers got the mechanism wrong: the group is NOT a pointer with `AddressSpace::Uniform`. Its IR is `%globalParams : ConstantBuffer(%GlobalParams) = global_param`, an inline read is `load(get_field_addr(%globalParams, field))`, and `getRootAddr` peels to `%globalParams`. `isPointerToImmutableLocation` (slang-ir-util.cpp:3110-3162) checks, in order: the SBT exclusion (3116), the op switch (GetStructuredBufferPtr / ImageSubscript…), then the type switch whose **`kIROp_ConstantBufferType` case (~3137)** returns true — before the `IRPtrTypeBase` address-space branch (~3147-3160), so the `AddressSpace::Uniform` case (~3154) is never reached for this input. The classification is correct; the "is it CUDA `__constant__`" discriminator lives only in the emitter rule (`CUDASourceEmitter::emitParameterGroupImpl`; gate in `emitGlobalParam`), which the guard mirrors. The OptiX SBT root is also `ConstantBuffer<>`-typed, hence its own exclusion at 3116 (host-mutated between dispatches). Trace the exact switch case that fires for the input's type before quoting a mechanism ([__constant__ group is immutable via the ConstantBufferType type-case, not AddressSpace::Uniform](../learnings/1789474416332-cuda-constant-group-is-classified-immutable-via-co.md), [same, traced to the 3137 type-case before the AddressSpace branch](../learnings/1789474331137-inline-cuda-constant-group-loads-hit-ispointertoim.md)).

Keying on `getRootAddr` is correct here even though prior art (#10188 false-safe → #12119) makes `getRootAddr`-keyed guards suspect. `getRootAddr` peels only `{GetElementPtr, FieldAddress, NodeOutputRecordGetElementPtr}`, not `BitCast`/`GetOffsetPtr`/`Reinterpret`/`PtrCast`. The #10188 SBT casts came from pointer ACQUISITION (`GetOptiXSbtDataPtr` reinterpreted to the element type), which is why #12119 keyed its walker on `GetOptiXSbtDataPtr`; the `__constant__` group has no acquisition cast — it is a direct `IRGlobalParam` reached via `FieldAddress`/`GetElementPtr`. CUDA's Default buffer-element lowering is a near-no-op, so no `CastStorageToLogical` enters the chain. Adopt the SBT-style peel-walker only if CUDA ever legalizes a group field into a cast-bearing chain. Test craft: a negative-only guard test needs a positive test that exercises the guard's *false* branch; a `StructuredBuffer` case does NOT (it takes the unconditional `kIROp_StructuredBufferLoad` case), so use a `ConstantBuffer<T>`/`ParameterBlock` field read ([getRootAddr peel-set is sufficient for the CUDA constant-param group, unlike the SBT peel-walker](../learnings/1789472511569-getrootaddr-is-sufficient-for-cuda-constant-param-.md)).

## Texture store, atomic and sample lowering

The masked-store bug (`gTex[i].w = 1.0f` on `RWTexture2D` emitting `handle[coord]->w`) is a fix, not a diagnostic: the RMW lowering (`legalizeImageSubscript`) is shipped behavior on Metal/GLSL/SPIR-V, so a CUDA-only error would be an unprincipled cross-backend divergence ([CUDA masked texture store — fix-vs-diagnostic reframed by RMW precedent](../learnings/1787171977334-cuda-masked-texture-store-fix-vs-diagnostic-refram.md)). Adding CUDA to the legalize switch is wrong, though: texture writes have two IR representations — `kIROp_ImageLoad/Store` (rendered only by the Metal/GLSL/SPIR-V handlers) and calls to the meta.slang `__subscript` accessors (the only path to surf2Dread/surf2Dwrite on CUDA). The switch would emit ops CUDA can't render and duplicate the surf2D addressing; a CUDA-local rewrite (`tmp=gTex[i]; tmp.w=v; gTex[i]=tmp;`) reusing the accessors is the principled route ([CUDA texture write has two IR representations](../learnings/1787172436124-cuda-texture-write-has-two-ir-representations-rmw-.md)).

Texture atomics fall through the same gap (#12636): `InterlockedAdd(RWTexture2D<uint>[c], v)` emits `atomicAdd(handle[coord], v)` on a `CUsurfObject`. The `ref` accessor is `kIROp_ImageSubscript`; `legalizeImageSubscript` runs only for Metal/GLSL/SPIR-V (`slang-emit.cpp` ~2464) and handles only stores; the GLSL and Metal atomic cases check `isTextureAccess()` but the CUDA `kIROp_Atomic*` cases (`slang-emit-cuda.cpp` ~800) do not, so the subscript reaches the generic `handle[coord]` path in `slang-emit-c-like.cpp`. Both overloads fail (one shared template). nvcc 12.6 / sm_89 assembles inline PTX `sured.b.add.2d.u32.trap [s, {x*4, y}], v;` (x in bytes, as in the `surf2Dwrite` helpers) but rejects `suatom`, so the value-returning overload needs a CAS loop or a diagnostic. No enabled CUDA test covers texture atomics (`tests/compute/spirv-multisampled-array-texel-pointer-atomic.slang` has `DISABLE_TEST(cuda)`) ([CUDA texture atomics: no ImageSubscript lowering; PTX sured works, suatom does not](../learnings/1792163961349-cuda-texture-atomics-no-imagesubscript-lowering-pt.md)).

Element-vs-vector emit: the `$T0`→`$TR` swap in `slang-intrinsic-expand.cpp` fixes **Gather** (returns `vector<T.Element,4>`, so `$TR` = `float4`) but NOT **SampleLevel** (returns plain `T`, so `$TR` = `float3`); SampleLevel must widen independently, mirroring SPIR-V's `__sampledType(T)` + `__truncate` ([CUDA texture element-vs-vector: $T0→$TR fixes Gather but not SampleLevel](../learnings/1787219149444-cuda-texture-element-vs-vector-t0-tr-swap-fixes-ga.md)). The cause is CUDA's built-in type set: `tex1D/tex2D/tex2DLod/...<T>` are gated by `__nv_itex_trait<T>` (CUDA 12.6 `texture_indirect_functions.h:66-104`), which specializes char, signed/unsigned char, short, ushort, int, uint, long, ulong and float as scalars and 1-, 2- and 4-vectors — no 3-component type and no `__half`. Say "integer and float types, but not `__half`", not "float/int/uint only" ([CUDA tex* built-ins type coverage](../learnings/1792421166308-cuda-tex-built-ins-type-coverage-char-short-int-lo.md)).

Before the #12634 fix every CUDA arm in `hlsl.meta.slang` passed `$T0` straight to `tex*<T>`, so NVRTC rejected every 3-component sample, not only the reported `Texture3D<float3>.SampleLevel`: on v2026.14.1 / NVRTC 12.6, `Sample` (`tex3D<float3>`), `Texture2D<float3>.SampleLevel` and `Texture3D<int3>`/`<uint3>` also fail (meta.slang ~3694-3722 SampleLevel, ~1319/~2581 Sample). Releases before v2026.16.1 fail; the workaround is `Texture3D<float4>` + `.xyz`; fixed releases emit `_slang_vector_reshape<float,3,float,4>(tex3DLod<float4>(...))`. The release bracket is on [[wiki/concepts/slang-tooling-release-tarball-repro-and-version-bisect.md]] ([#12634 scope: every 3-component CUDA texture sample](../learnings/1792400048814-slang-12634-scope-every-3-component-cuda-texture-s.md)).

Half `SampleLevel` (`tex2DLod<__half4>`) is the opposite resolution — a diagnostic, since `tex*Lod` have no `__half` overload and no half sampled-read shim exists; it mirrors the half `.Load` diagnostic #12303 with `static_assert(!__isHalf<T>())` ([CUDA half SampleLevel gap — sibling of Load gap #12277](../learnings/1787173327448-cuda-half-samplelevel-gap-tex2dlod-sibling-of-load.md)). That guard is on master by 653bfdeef (2026-10-22) in both SampleLevel `case cuda:` arms (`hlsl.meta.slang` ~2501, ~4219), documented at `docs/cuda-target.md:137` (#12632) ([local checkout is newer than the issue date](../learnings/1792645528183-eval-reply-tasks-local-slang-checkout-is-newer-tha.md)).

To add a CUDA lowering for a Sample* method, use the SampleLevel `cuda` case (hlsl.meta.slang :2415 combined, :4133 separate-sampler) as the template. For SampleGrad, CUDA 12.6 `texture_indirect_functions.h` (:470-631) has every `tex*Grad` object form (1D, 2D, 3D, cube, and their layered variants), with `tex*Lod`'s argument order and `float level` replaced by `dPdx, dPdy`. 1D gradients are `float`, 2D `float2`, but 3D and cube are **`float4`**, so float3 gradients need `make_float4((g).x,(g).y,(g).z,0.0f)` in the `__intrinsic_asm`; reuse the `_slang_vector_reshape<E,3,E,4>` arms and the half `static_assert`. Add `cuda` to the first `[require(...)]` argument or E36107 fires; under `-ignore-capabilities` a missing case compiles to an empty entry point (#13555). On `-target ptx` the output should contain `tex.grad.{1d,a1d,2d,a2d,3d,cube,acube}` (prototype for #13556) ([CUDA SampleGrad: tex*Grad mirrors tex*Lod, but 3D/cube gradients are float4](../learnings/1791589496861-cuda-samplegrad-tex-grad-mirrors-tex-lod-but-3d-cu.md)).

## Array init and constant-fold gaps

CUDA/CPP arrays are `struct FixedArray<T,N> { T m_data[N]; }`, so an aggregate initializer needs **two brace levels per dimension**; single braces rely on brace elision that works for flat arrays but mis-binds nested ones. It was masked by hoisting inner rows to named temps and surfaces once rows are folded/inlined ([CUDA-CPP arrays are struct FixedArray needing two brace levels](../learnings/1787343021129-cuda-cpp-arrays-are-struct-fixedarray-needing-two-.md)). A literal-only nested `static const int values[2][2]` fails NVRTC with "dynamic initialization not supported for a `__device__` variable" because `shouldFoldInstIntoUseSites` returns false for `MakeArray` (an explicit HACK): each row becomes its own `__device__` global referenced by the outer one. Only CUDA forbids a constant global referencing another. Precedent: WGSL PR #11628's `shouldFoldInstIntoUseSites` override folding a module-scope aggregate whose uses are all constituents of another aggregate ([CUDA nested static-const arrays emit as dynamic __device__ init](../learnings/1787174886706-cuda-nested-static-const-arrays-emit-as-dynamic-de.md)).

The rule is stricter than "all operands are literals". With nvcc 12.6 and the CUDA prelude, `__device__ static const Matrix<float,2,2> m = makeMatrix<float,2,2>(0.0f, 1.0f, 2.0f, 3.0f);` is dynamic init (`makeMatrix` is not constexpr), as is a FixedArray of `makeMatrix(...)` elements; only the brace literal `Matrix<float,2,2>{0.0f, ...}` compiles. So a module-scope vector/matrix that is not a plain literal (a cast such as `float3(int3(1,2,3))`, a matrix layout change) breaks CUDA once it is a `__device__` global. The CPP/CUDA `shouldFoldInstIntoUseSites` override (slang-emit-cpp.cpp ~1954) refuses to fold casts, and relaxing that veto fixes only function-local uses; device globals need the cast constant-folded in IR or printed as a brace literal (#13444) ([CUDA __device__ matrix/vector globals: only a brace literal is static init](../learnings/1791305634716-cuda-device-matrix-vector-globals-only-a-brace-lit.md)). The same limit hit PR #13115 when an IR change admitted more struct tables as globals: NVRTC 12.6 rejected `make_float2(...)`, `makeMatrix<T,R,C>(...)`, `__half(...)` (a plain `half` array is rejected even on master), `SLANG_INFINITY` and builtin calls like `F32_sqrt(...)`, while DXC/SPIR-V/glslang accept them; `(0.0 / 0.0)` for NaN and `float2 { 1.0f, 2.0f }` are fine. No slang test had vector-, matrix- or half-field struct tables, so a corpus A/B sweep missed it — probe each leaf type on `-target ptx`. If a ctor call is folded into `makeStruct` but the table still gets inlined, roll the fold back, or stray element globals can remain (a `const` in WGSL) [CUDA __device__ constant tables need plain-literal leaves](../learnings/1792139832211-slang-cuda-device-constant-tables-must-have-plain-.md). The A/B corpus coverage lesson is on [Slang build in worktrees](slang-tooling-f0909b0-build-worktree-cmake.md).

There are TWO distinct `static const` global-array bugs. The nested-*literal* one is #12635 (**FIXED** by PR #12688): a global with dynamic `__device__` init. The still-open #13107 diverges by ELEMENT TYPE: a `static const` array of a *struct* (`Record{uint a,b;} recs[2]`) becomes a per-invocation local `FixedArray` rebuilt inside the kernel via synthesized `$init` ctor calls (`Record_x24init_0(1U,2U)`), while a scalar `static const uint[]` sibling stays `__device__ static const`. Two joint gaps: (1) `inlineGlobalConstantsForLegalization` runs unconditionally for CUDA/CPU-kernel (slang-emit.cpp:1934-1938) and its gate `GlobalInstLegalizationInliningContext::isSimpleConstantType` (slang-ir-legalize-global-values.cpp:251-270) accepts only scalar/vector/matrix and arrays of those — a struct hits `return false` at :268 and is force-inlined into every user; (2) struct elements lower to `$init` `IRCall`s (checker `createInvokeExprForSynthesizedCtor`), not `MakeStruct`, and `isInnerGlobalAggregate` (slang-emit-c-like.cpp:1461-1493) folds only MakeArray/MakeStruct/MakeArrayFromElement. The fix needs BOTH: extend `isSimpleConstantType` to POD structs (recurse fields, reject resource/pointer) and fold constant ctor calls → MakeStruct at module scope. Blast radius is the C-family emitter (CUDA/CPP/Torch share `CPPSourceEmitter`). GPU-free verify: `slangc t.slang -target cuda -o k.cu`, grep for `FixedArray`/`x24init` in the kernel body vs `__device__ static const` at file scope ([CUDA static-const struct arrays localize via the isSimpleConstantType struct gap — distinct from #12635](../learnings/1789513281020-cuda-static-const-struct-arrays-localize-via-issim.md)). Rechecked on the reporter's commit b6e7d3b9 (Release, also -O3): `uint2`/`uint` tables stay at file scope, the struct table is inlined via `call Record.$init(...)`. **Workaround until #13107 is fixed:** pack each record into a vector (`uint2`, `uint4`), which `isSimpleConstantType` accepts ([slang#13107 workaround: vector-typed tables stay global on CUDA](../learnings/1792650089805-slang-13107-workaround-vector-typed-tables-stay-gl.md)).

## Documentation accuracy for CUDA intrinsics

A doc claim that CUDA `half2` arithmetic is "packed SIMD / one instruction per op" is false twice and codex will block it: division is never packed (`__h2div` calls scalar `__hdiv` twice), and `+ - * unary-` are gated by `NV_IF_ELSE_TARGET(NV_PROVIDES_SM_53, ...)` — packed only on SM 5.3+ ([Documenting CUDA half2 packed SIMD needs a per-op and an SM_53 caveat](../learnings/1787236121791-documenting-cuda-half2-packed-simd-needs-both-a-pe.md)).

## The principled layer to reject an unsupported type

Put a `case kIROp_<Type>:` in the module-level global walk `checkUnsupportedInst(IRModule*, target, sink)`, not a recursive descent into struct fields: IR types are hoisted and deduplicated, so a `Texture2DMS<float>` used anywhere is one top-level inst and one case catches every use with one diagnostic ([checkUnsupportedInst — reject unsupported types at the hoisted global](../learnings/1787278343860-checkunsupportedinst-reject-unsupported-types-at-t.md)). Gate to the exact failing target (`isCUDATarget`, not `isKernelCPPOrCUDASourceTarget`, which includes CPPSource where the type lowers fine — the #11659 over-broad-rejection trap). Same layer as the #11297 `String` rejection.

## CUDA layout vs reflection: the buffer ABI (`NO_COUNT`) and `T*` pointees

The prelude (`prelude/slang-cuda-prelude.h` ~2887, tree of 2026-10-22) defines `StructuredBuffer<T>` as `{ T* data; size_t count; }`; `SLANG_CUDA_STRUCTURED_BUFFER_NO_COUNT` drops `count` and with it bounds checks and `GetDimensions` (ByteAddressBuffers keep `sizeInBytes`). Reflection ignores the macro: `CUDAObjectLayoutRulesImpl` (`slang-type-layout.cpp` ~1668-1686) always reports 16 bytes (pointer + `CUDACount`) for structured, raw and append/consume buffers, so a host that sets the macro gets code whose layout disagrees with reflection. Unsized arrays are pointer+count too (~807). A pointer-only CUDA ABI request (e.g. #13397) must reach the layout rules, not only the prelude ([CUDA buffer ABI: prelude NO_COUNT macro and reflection layout disagree](../learnings/1792651922688-cuda-buffer-abi-prelude-no-count-macro-and-reflect.md)).

A second disagreement is on the pointer path. Measured on master 9b3ac252d with nvcc 12.6 on the L40S (sm_89): for `struct E3 { float a; float4 c; }` reached through `uniform E3* p` on `-target cuda`, Slang folds `sizeof(E3)` to 20 and `alignof(E3)` to 4, and the reflection JSON (`entryPoints[0].scope.parameters[i].type.valueType`) puts `c` at offset 4. nvcc lays out the emitted `struct E3_0 { float a_0; float4 c_0; }` as size 32, alignment 16, `c` at 16, and the kernel's own `&p[1]-&p[0]` is 32. `{float a; float2 b}` gives Slang 12/4 against nvcc 16/8; `double` fields agree. The same struct in a `StructuredBuffer` or as a uniform parameter is reflected with CUDA rules (`c` at 16), so only `T*` disagrees. The likely cause (an inference, not traced): the front end lays out `T*` pointees with `kScalarLayoutRulesImpl_` on every target (`slang-type-layout.cpp:5718-5745`) and the IR uses Natural rules for CUDA pointers and buffers (`slang-ir-lower-buffer-element-type.cpp:2501`), but CUDA emit uses the native 8/16-byte-aligned `float2`/`float4`. Metal avoids it by emitting an `X_natural_0` copy with `packed_float4`. DeepWiki claims the pointee uses `CUDALayoutRulesImpl`; the measurement shows that is wrong. To check, write `sizeof(T)`, `alignof(T)` and `(uint64_t)&p[1]-(uint64_t)&p[0]` from a kernel into a buffer and compare them with a host `sizeof` of the emitted struct compiled with `nvcc -I prelude`. Found while triaging #14032 (an `[Align(N)]` request); not filed as of 2026-10-29 [CUDA T* pointee layout (sizeof/alignof/reflection) disagrees with nvcc for float2/float4 fields](../learnings/1793294735930-cuda-t-pointee-layout-sizeof-alignof-reflection-di.md).

## Entry point `main` is renamed at emit time, after reflection recorded it (#13264)

On CPU, CUDA (+PTX) and Metal, `CLikeSourceEmitter::maybeMakeEntryPointNameValid` (slang-emit-c-like.cpp:1130-1143, PR #7105) renames `main` to `main_0` at emit time, after layout recorded the name, so `EntryPointReflection::getNameOverride()` still returns `main` and lookups fail: slang-rhi CUDA `cuModuleGetFunction`, CPU `findSymbolAddressByName`, Metal `newFunction`, the OptiX prefix+name. An explicit `renameEntryPoint("x")` does reach the symbol (the linker writes it into `IREntryPointDecoration`). The rename is required (nvcc rejects `__global__ main`); no public API exposes the emitted symbol (DeepWiki wrongly says `getNameOverride` does). Also, slang-rhi CUDA `RootShaderObjectLayoutImpl::getEntryPointIndex` compares the override-derived name to `getName()`, so a renamed entry point gets -1. GPU harness: `getEntryPointCode(SLANG_PTX)` → `cuModuleLoadData` → `cuModuleGetFunction(getNameOverride)` ([Slang renames entry main at emit time on CUDA/CPU/Metal; reflection never sees it](../learnings/1790318957835-slang-renames-entry-main-at-emit-time-on-cuda-cpu-.md)).
