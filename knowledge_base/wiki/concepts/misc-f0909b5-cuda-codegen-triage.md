## TL;DR

The CUDA/OptiX target has a recurring family of codegen defects where slangc exits 0 but emits source NVRTC rejects (or, worse, silently produces a wrong-memory or empty kernel). Several distinct bug shapes recur:

- **Silent misroute / silent-empty:** `shaderRecordEXT ConstantBuffer` at global scope is folded into `GlobalParams` instead of the SBT; empty-prelude "case-present-but-stub" bodies yield silent empty kernels — a third variant beyond the case-LESS and un-instantiated-template families.
- **Type-name failures wear two faces:** when `calcTypeName` fails (e.g. `Texture2DMS`), a Debug build ICEs on a `kNullHandle` assert while a Release build emits a typeless field — reproduce on BOTH configs to get the pinpoint.
- **Texture ops:** masked stores need the read-modify-write legalization already shipped on Metal/GLSL/SPIRV; a CUDA-local IR rewrite reusing the meta.slang accessors is the *principled* route (avoids a second source of truth for surf2D addressing). Element-vs-vector emit (`$T0`→`$TR`) fixes Gather but NOT SampleLevel (return-type shape differs). Half sampled reads (`tex2DLod<__half4>`) are unsupported by construction — diagnostic, not fix.
- **Array init:** CUDA/CPP arrays are `struct FixedArray<T,N>` needing TWO brace levels per dimension; nested static-const arrays emitted as dynamic `__device__` init (#12635, FIXED by #12688); a `static const` array of a *struct* instead localizes per-invocation (#13107, open) — the divergence is by ELEMENT TYPE via the `isSimpleConstantType` struct gap.
- **Immutable-load `__ldg` guard:** the `__constant__` launch-param group is classified immutable via the `kIROp_ConstantBufferType` type-case in `isPointerToImmutableLocation` (NOT `AddressSpace::Uniform`); `__ldg` needs a global address so the guard (#13091) skips it when `getRootAddr` roots at an `IRGlobalParam` of `IRUniformParameterGroupType`. `getRootAddr`'s peel-set suffices here (no acquisition cast, unlike the SBT case).
- **Right layer to reject unsupported types:** `checkUnsupportedInst`'s module-level global walk (IR types are hoisted + deduplicated), gated to the exact failing target — not a recursive struct-field descent, not an emit-layer helper with no SourceLoc.

Cross-cutting repro trick: `slangc -target cuda` emits CUDA C++ source with NO GPU (grep for the bad emit); `-target ptx` invokes NVRTC. The prod slang-fixer/triager container has an L40S + NVRTC 12.6, so PTX repros are real end-to-end checks — don't punt them as hardware-gated.

## Silent miscompiles and silent-empty kernels

Two atoms document CUDA paths that produce no diagnostic and a wrong or empty result. `layout(shaderRecordEXT) ConstantBuffer<T> g;` at global scope is silently misrouted into `GlobalParams` and read via `__ldg` instead of `optixGetSbtDataPointer()`, because `getShaderRecordConstantBufferRules()` returns the ordinary layout family ("following HLSL's lead") and `collect-global-uniforms` filters only on `LayoutResourceKind::Uniform` — there is no `ShaderRecord` check ([CUDA ignores shaderRecordEXT on global ConstantBuffer](../learnings/1787171496782-cuda-ignores-shaderrecordext-on-global-constantbuf.md)). SPIR-V honors the same global, so the gap is CUDA-specific. Separately, the CUDA/PTX empty-prelude family gained a **third variant**: a `case cuda:` that IS present but whose template body is an empty stub — because the case exists, the catch-all `static_assert(false)` never fires, giving a silent empty kernel identical in symptom to the case-LESS variant but different in mechanism ([CUDA prelude empty-body third silent variant](../learnings/1787171580700-cuda-prelude-empty-body-a-third-silent-empty-varia.md)). The discriminator table: case-LESS → silent-empty; case-present + empty stub → silent-empty; case-present + declared-but-never-instantiated → loud undefined-symbol.

A subtler two-faced failure: when the CUDA/C++ emitter cannot compute a type name (`calcTypeName` fails for multisample `Texture2DMS`), `_getTypeName` leaves a `kNullHandle`. In **Debug** this fires `SLANG_ASSERT(handle != kNullHandle)` (an ICE, exit 255); in **Release** the assert is compiled out and the emitter writes a struct field with a name but no type, which NVRTC then rejects — so the same root cause looks like two separate bugs ([CUDA unsupported-type null-handle: Debug ICE vs Release typeless field](../learnings/1787173483661-cuda-unsupported-type-null-handle-same-bug-wears-t.md)). Reproduce on both configs — the Debug ICE gives the exact assert file:line the release symptom hides.

## The `__constant__` param-group immutable-load `__ldg` guard (#13091/#13088)

CUDA's immutable-load pass rewrites reads of immutable memory to `__ldg` (NVRTC `ld.global.nc`), but `__ldg` needs a *global* address, and the synthesized `SLANG_globalParams` launch-parameter group is constant-memory (`extern "C" __constant__`), not global — so an inline `__constant__` group field read was wrongly getting `__ldg`. PR #13091 (fixes #13088) added a guard in `slang-ir-cuda-immutable-load.cpp` that skips `__ldg` when `getRootAddr(load->getPtr())` is an `IRGlobalParam` of `IRUniformParameterGroupType`. The classification that *makes* the guard necessary is subtle and a triage memo plus two reviewers propagated a wrong mechanism: the group is NOT a pointer with `AddressSpace::Uniform`. Its IR is `%globalParams : ConstantBuffer(%GlobalParams) = global_param` — an `IRConstantBufferType` (an `IRUniformParameterGroupType`) — and an inline read is `load(get_field_addr(%globalParams, field))`, so `getRootAddr` peels FieldAddress/GetElementPtr to `%globalParams`. `isPointerToImmutableLocation` (slang-ir-util.cpp:3110-3162) then returns true through its **`kIROp_ConstantBufferType` type-switch case (~3137)**, which sits BEFORE the `IRPtrTypeBase` address-space branch (~3147-3160); because the root is a ConstantBuffer type (not a Ptr), the `AddressSpace::Uniform` case (~3154) is NEVER reached for this input. The immutability classification is *correct*; the discriminator the fix needs — "is it CUDA `__constant__`" — is recorded by no type/address-space marker, only by the emitter's rule (an `IRGlobalParam` of `IRUniformParameterGroupType` → `extern "C" __constant__`, `CUDASourceEmitter::emitParameterGroupImpl`; gate in `emitGlobalParam`), which is what the guard keys on. Structural coherence: the OptiX SBT root is ALSO `ConstantBuffer<>`-typed, so it too returns true at 3137 — which is why SBT is excluded earlier at 3116 (`isAddressIntoOptiXShaderBindingTable`, host-mutated between dispatches); two parallel exclusions of ConstantBuffer-typed immutable roots for different reasons ([__constant__ group is immutable via the ConstantBufferType type-case, not AddressSpace::Uniform](../learnings/1789474416332-cuda-constant-group-is-classified-immutable-via-co.md), [same, traced to the 3137 type-case before the AddressSpace branch](../learnings/1789474331137-inline-cuda-constant-group-loads-hit-ispointertoim.md)).

Reusing `getRootAddr` here (rather than mirroring the SBT `isAddressIntoOptiXShaderBindingTable` peel-*walker*) is correct even though prior art (#10188 false-safe → #12119) makes any `getRootAddr`-keyed guard suspect: `getRootAddr` peels only `{GetElementPtr, FieldAddress, NodeOutputRecordGetElementPtr}`, NOT `BitCast`/`GetOffsetPtr`/`Reinterpret`/`PtrCast`, so the question is whether a cast/offset can sit between the `Load` and the group and defeat it. It can't, for a structural reason: the #10188 SBT casts came from pointer ACQUISITION (`GetOptiXSbtDataPtr` reinterpreted to the element type — the cast getRootAddr couldn't peel, which is why #12119 keyed its walker on `GetOptiXSbtDataPtr` *inside* `isPointerToImmutableLocation`), whereas the `__constant__` group has NO acquisition cast — it is a direct `IRGlobalParam` accessed structurally via `FieldAddress`/`GetElementPtr`. CUDA also uses the Default buffer-element lowering policy + Natural layout, a near-no-op (identity for bool/8-64-bit/half-float-double/vectors; bool→int is SPIR-V-direct-only; row-major matrices identity), so no `CastStorageToLogical` is spliced into the access chain (identity members ⇒ the group is `continue`-skipped in lower-buffer-element-type). Adopt the SBT-style peel-walker only if CUDA ever legalizes a group field into a cast-bearing chain (a future `shouldUseDXLayout` → `D3DConstantBuffer` change would lower more matrices but still via FieldAddress/GetElementPtr — no new cast source). Review-craft note both reviewers flagged: pair a negative-only guard regression test with a positive test that exercises the guard's *false* branch — a `StructuredBuffer` positive case does NOT (it takes the unconditional `kIROp_StructuredBufferLoad` case, never reaching the `kIROp_Load` guard); use a `ConstantBuffer<T>`/`ParameterBlock` field read (a `kIROp_Load` rooted at a `Load`) instead ([getRootAddr peel-set is sufficient for the CUDA constant-param group, unlike the SBT peel-walker](../learnings/1789472511569-getrootaddr-is-sufficient-for-cuda-constant-param-.md)).

## Texture store/sample lowering

The masked-store bug (`gTex[i].w = 1.0f` on `RWTexture2D` emitting an invalid `handle[coord]->w`) reframes the "fix or diagnose?" question: the read-modify-write lowering (`legalizeImageSubscript`) is Slang's **accepted, shipped behavior** on Metal/GLSL/SPIRV, so a CUDA-only compile-time error would be an unprincipled cross-backend divergence ([CUDA masked texture store — fix-vs-diagnostic reframed by RMW precedent](../learnings/1787171977334-cuda-masked-texture-store-fix-vs-diagnostic-refram.md)). But "just add CUDA to the legalize switch" is insufficient because there are **two distinct IR representations** of a texture write: `kIROp_ImageLoad/Store` (rendered only by Metal/GLSL/SPIRV native handlers) versus calls to the meta.slang `__subscript` accessors (the ONLY path reaching surf2Dread/surf2Dwrite for CUDA). Adding CUDA to the switch would emit ops the CUDA emitter can't render AND re-derive all surf2D addressing that already lives once in meta.slang — a second source of truth. So a CUDA-local IR rewrite (`tmp=gTex[i]; tmp.w=v; gTex[i]=tmp;`) reusing the existing accessors is the MORE principled route for CUDA, the inverse of the other backends ([CUDA texture write has two IR representations](../learnings/1787172436124-cuda-texture-write-has-two-ir-representations-rmw-.md)).

Two element-vs-vector emit gaps: the `$T0`→`$TR` swap (call return-type vs texture element-type in `slang-intrinsic-expand.cpp`) fixes **Gather** (whose signature returns `vector<T.Element,4>`, so `$TR` = `float4`) but NOT **SampleLevel** (whose signature returns plain `T`, so `$TR` = the narrow `float3`) — SampleLevel must widen to a 4-component result independently, mirroring the SPIRV arm's `__sampledType(T)`+`__truncate` ([CUDA texture element-vs-vector: $T0→$TR fixes Gather but not SampleLevel](../learnings/1787219149444-cuda-texture-element-vs-vector-t0-tr-swap-fixes-ga.md)). And half `SampleLevel` (`tex2DLod<__half4>`) is the OPPOSITE resolution — a diagnostic, because `tex*Lod` are CUDA runtime built-ins with no `__half` overload and no half sampled-read conversion shim exists; the fix mirrors the half `.Load` diagnostic #12303 with a `static_assert(!__isHalf<T>())` guard ([CUDA half SampleLevel gap — sibling of Load gap #12277](../learnings/1787173327448-cuda-half-samplelevel-gap-tex2dlod-sibling-of-load.md)). Adjacent latent gaps (`Sample`, `SampleBias/Grad/Cmp`, `Gather`) share the emit shape.

## Array init and constant-fold gaps

CUDA/CPP arrays are `struct FixedArray<T,N> { T m_data[N]; }`, so an aggregate initializer needs **two brace levels per array dimension** (outer for the struct, inner for `m_data`); a single brace relies on C++ brace-elision that works for flat arrays but mis-binds nested ones. This was masked for years because the emitter universally hoisted inner rows to named temps — the bug surfaces the moment you fold/inline rows ([CUDA-CPP arrays are struct FixedArray needing two brace levels](../learnings/1787343021129-cuda-cpp-arrays-are-struct-fixedarray-needing-two-.md)). Relatedly, a literal-only nested `static const int values[2][2]` fails NVRTC with "dynamic initialization not supported for a `__device__` variable" because `shouldFoldInstIntoUseSites` returns false for `MakeArray` (an explicit HACK), so each inner row is hoisted to its own `__device__` global and the outer array references them — which NVRTC treats as a runtime initializer. HLSL/GLSL/Metal/CPU accept a constant global referencing another; only CUDA's `__device__` rule forbids it. The fix precedent is WGSL PR #11628's `shouldFoldInstIntoUseSites` override folding a module-scope aggregate inline when all uses are constituents of another aggregate ([CUDA nested static-const arrays emit as dynamic __device__ init](../learnings/1787174886706-cuda-nested-static-const-arrays-emit-as-dynamic-de.md)).

There are TWO distinct `static const` global-array bugs — don't conflate them. That nested-*literal* bug is #12635 (**FIXED** by merged PR #12688), and its symptom is a global-with-dynamic-`__device__`-init. A DISTINCT, still-open bug (#13107) diverges by ELEMENT TYPE, not nesting: a `static const` array of a *struct* (`Record{uint a,b;} recs[2]`) is emitted as a PER-INVOCATION LOCAL `FixedArray` reconstructed *inside* the kernel via synthesized `$init` ctor CALLS (`Record_x24init_0(1U,2U)`), never reaching global scope, while a scalar `static const uint[]` sibling stays `__device__ static const`. Two joint gaps: (1) `inlineGlobalConstantsForLegalization` runs unconditionally for CUDA/CPU-kernel (slang-emit.cpp:1934-1938, to avoid NVRTC-rejected dynamic `__device__` init), and its legality gate `GlobalInstLegalizationInliningContext::isSimpleConstantType` (slang-ir-legalize-global-values.cpp:251-270) accepts ONLY scalar/vector/matrix + arrays-of-those — a struct or array-of-struct hits `return false` at :268 → misclassified illegal-global → force-inlined into every user; (2) struct elements lower to synthesized `$init` ctor CALLS (checker `createInvokeExprForSynthesizedCtor` → `IRCall`), not `MakeStruct`, so the global brace-init folder `isInnerGlobalAggregate` (slang-emit-c-like.cpp:1461-1493, folds only MakeArray/MakeStruct/MakeArrayFromElement, never a Call) can't make them a compile-time-constant global. The complete fix needs BOTH: extend `isSimpleConstantType` to POD structs/arrays-of-struct (recurse fields, reject resource/pointer) AND fold constant synthesized-ctor calls → MakeStruct at module scope. The pass is CUDA/CPU-only ⇒ blast radius is the C-family emitter (CUDA/CPP/Torch share `CPPSourceEmitter`); SPIR-V/HLSL unaffected. GPU-free verify: `slangc t.slang -target cuda -o k.cu`, grep the `.cu` for `FixedArray`/`x24init` inside the kernel body vs `__device__ static const` at file scope ([CUDA static-const struct arrays localize via the isSimpleConstantType struct gap — distinct from #12635](../learnings/1789513281020-cuda-static-const-struct-arrays-localize-via-issim.md)).

## Documentation accuracy for CUDA intrinsics

A doc/comment claiming CUDA `half2` arithmetic is "packed SIMD / one instruction per op" is FALSE on two counts and codex will block it: division is never packed (`__h2div` calls scalar `__hdiv` twice), and even `+ - * unary-` are architecture-gated (`NV_IF_ELSE_TARGET(NV_PROVIDES_SM_53, ...)`) — packed only on compute capability 5.3+, scalar fallback otherwise ([Documenting CUDA half2 packed SIMD needs a per-op and an SM_53 caveat](../learnings/1787236121791-documenting-cuda-half2-packed-simd-needs-both-a-pe.md)).

## The principled layer to reject an unsupported type

When rejecting an unsupported *type* on a target, put a `case kIROp_<Type>:` in the **module-level global walk** `checkUnsupportedInst(IRModule*, target, sink)`, NOT a recursive descent into struct fields — Slang IR types are hoisted to global scope and deduplicated, so a `Texture2DMS<float>` used anywhere appears as one top-level global inst and one `case` catches every use site with one diagnostic ([checkUnsupportedInst — reject unsupported types at the hoisted global](../learnings/1787278343860-checkunsupportedinst-reject-unsupported-types-at-t.md)). Gate to the exact failing target (`isCUDATarget`, not the broader `isKernelCPPOrCUDASourceTarget` which includes CPPSource where the type lowers fine — the #11659 over-broad-rejection trap). This is the same layer/shape as the #11297 `String`-on-kernel-target rejection.
