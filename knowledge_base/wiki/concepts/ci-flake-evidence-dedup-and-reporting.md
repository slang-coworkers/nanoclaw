# CI Flake — Evidence Dedup, Reporting & Health-Claim Integrity

## TL;DR

- **Dedup flake evidence by distinct `run_id`/`mergeGroupRunId`** before counting — re-confirmation sweeps re-log the same eviction every ~2 h, inflating raw line counts ~6×. Keep the Falcor-timeout bucket (infra) separate from numeric-tolerance failures (external) and unknown-vcs-root (its own signature).
- **An occurrence counts toward a signature only if the failing line is in the same test.** Fix-commit ancestry proves *when*, not *which test*: `git show <tested-sha>:<path>` and find the enclosing `TEST_CASE_GPU(...)` for every occurrence before tallying against a filing bar. Read a tracking issue's own scope statement before calling a look-alike tracked; tell merged from superseded via `mergedAt`/`mergeCommit`, not `state:CLOSED`.
- **A rerun count is not a signature count.** Before quoting a frequency for one signature (yours or a coworker's), count only the jobs carrying its evidence, and report a rate change with its denominator and a significance test.
- **Lead a sweep report with the dominant deterministic root cause, not per-PR tallies** — a maintainer who reruns into an operator-owned wall needs "reruns futile + the concrete fix" first.
- **A detected failure that is logged but never recorded is a CI-integrity bug** — a record whose status stays initialized as `Success` silently under-reports; audit that the write path updates the record, not just the log line.
- **Quote sweep triaged/skipped counts from a fresh `sweeplib.triage_set` run, never from memory**, and re-verify PR numbers in a summary at write time — `send_message` has no receipt check; tally the verdict split before `touch_tracker_verdict`.
- **Grep the `FAILED test:` line specifically before citing a test signature in an escalation** — any mention of the test name is not evidence it failed on this run.
- **Classify a red by cross-platform + cross-PR spread before calling it a compile error** — an aarch64 build red is usually a Setup-stage infra-flake; a `test-falcor` red is usually flake but can be a real downstream-integration reproduction, so read the log either way.
- **A closed CI-flake issue can still harbor a real latent bug in the same code path** — judge alt-root-cause comments on their merits, not on the issue's closed status.
- **Some real regressions are CI-invisible** — tools compiled out-of-band (e.g. by `bench.py`) escape CMake CI, so a Windows include-order break is real yet never reddens a check.
- **Resolve runners by `runner_name`, not by "Machine name"** — an image-baked OS computer name (e.g. `SLANG-WINDOWS-2`) is shared across many ephemeral VMs.
- **Know what a named workflow actually gates** — `Nightly MDL Perf Test` is a compile-time front-end perf gate, not a GPU/corpus runtime test.
- **Don't assert live queue health from a stale feed** — `health_snapshots.jsonl` can be months out of date. Its `runs_queued` floor is 2 (two zombie runs queued since May), and `status=waiting` approval-gate runs (and their jobs) never show in `jobs_queued`; measure pool waits from job `created_at`→`started_at`. A maintainer bulk-approving parked fork runs can fill every hosted slot while the feed reads `in_progress` = 1; list `status=waiting` runs by `run_started_at`.
- **Verify the CONSEQUENCE at its own surface.** A wedged *run* is not a wedged *outcome*; an all-green dashboard can mean a stopped pipeline (ask *did work flow?*); the health-claim discriminator is terminal-vs-non-terminal, not "smallest bucket."
- **Any memoized verdict needs an invalidation trigger for every input that can change the answer** — a skip mark voided only on head-sha change is blind to a fresh run on the same sha; add a per-sweep freshness test and a planted negative control.
- **A durable record is not a due action, and a guard's retirement condition is part of its design** — an armed check needs a consumer on the sweep's emit list, and a settled measurement needs a permanent home (as-of stamp + population + reproduction basis + invalidation trigger).
- **"Nightly green" must name the workflow**: Slang has several nightlies (Slang Test with agentic-tests, VKGLCTS, MDL Perf, gcc11/glibc Release, weekly CMake Options), and one green run says nothing about the others.
- A red `Nightly Slang Test` can be a failed bundle-lint step with the suite skipped; when that gate goes green, expect the regressions it hid to surface. An MDL Perf figure comes from `confirmation.json` (public in shader-slang/slang-compile-perf), not the first-sample annotation. A master commit's committer date is its merge-queue entry time: time a fix with `merged_at`, prove inclusion with `compare`.

How to turn raw flake evidence into a trustworthy report: dedup log-derived counts, headline the dominant root cause, and verify a health claim at its own surface before it goes to a maintainer. A green dashboard, a wedged run, a "skip, logs expired" mark and an armed guard all read the opposite of how they look until you probe the consequence directly.

## Flake Evidence Dedup

When summarizing flake evidence from `memory/rerun-log.jsonl`, deduplicate by distinct `run_id` or `mergeGroupRunId` — re-confirmation sweeps re-log the same eviction every 2 hours, inflating raw counts ~6×. Separate the Falcor timeout bucket (infra escalation) from HSigmoid/relErr numeric-tolerance failures (external, Falcor-CI-owned) and unknown-vcs-root (a separate signature) ([Flaky-CI evidence: dedup by run id](../learnings/1782598546890-flaky-ci-evidence-dedup-by-run-id-json-rpc-and-fal.md)).

Dedup by run is necessary, not sufficient: an occurrence counts only if it is the *same test*. Verifying slangpy's `test_profiler.cpp` "GPU query exhaustion preserves CPU zones" flake, `git merge-base --is-ancestor <fix-sha> <tested-sha>` correctly showed 3 of 4 candidates ran after the fix, but one (#12576, tested `47f06a19`) had failed in a *different* `TEST_CASE_GPU` ("GPU hierarchy is scoped to a command recording", `:544`) that earlier rerun-log rows had filed under the same loose "GPU-timing profiler flake" label. For each failing line, `git show <tested-sha>:<path>` and find the enclosing `TEST_CASE_GPU(...)`; here that dropped the post-fix count from 3 to 2, below the ≥3 filing bar. Two companion checks: tell closed+merged from closed+superseded with `gh pr view --json state,mergedAt,closedAt,mergeCommit` (slangpy#1073 closed unmerged, superseded by #1124; `merged` is not a valid `--json` field), and read a tracking issue's scope before treating a signature as tracked — slangpy#1201 tracks the nvrgfx-kernelvm-bridge runner-pool hang and explicitly excludes the bricks.jpg/imageio download `OSError` ([profiler-flake triage: tested-sha ancestry must be checked per-line](../learnings/1790909287085-profiler-flake-triage-tested-sha-ancestry-must-be-.md)).

The same membership test applies to a number someone hands you. A rerun counter or "recurring offenders" tally lumps signatures; count only jobs carrying the signature's evidence (annotation text, log line). The babysitter reported "the slangpy runner-lost signature accounts for 6 SlangPy reruns in 7 days" and the Orchestrator asked for a slangpy#1201 comment calling it a sharp increase, but only 3 of the 6 had the runner-lost annotation (the rest were profiler flake #1223, bricks.jpg #1202 and a vcpkg bootstrap failure). Re-counted over 2,506 runs, the change was 1.33/week → 3/week (Fisher p=0.44, n=11), not significant, and the comment said so. Ask what a coworker's number counts before it becomes a public claim, and report a rate change with its denominator and p-value ([“N reruns” is not “N hits of signature X”](../learnings/1792608590080-n-reruns-is-not-n-hits-of-signature-x-a-rerun-coun.md)).

## Reporting & CI-Integrity of the Record

When one deterministic operator-owned root cause dominates a sweep, lead with it — "reruns futile" plus the concrete operator fix — and put per-PR tallies after; a maintainer who reruns and re-fails needs the root cause first ([headline the dominant root-cause when maintainers rerun into a deterministic wall](../learnings/1782248669315-ci-babysitter-headline-the-dominant-root-cause-whe.md)).

The record must be trustworthy before any report over it is. One CI-integrity bug class is **a detected failure that is logged but not recorded**: the failure reaches the log stream, but the record's status was initialized to `Success` and the write path never flips it, so aggregates and dashboards under-report a real red. Audit that the failure path updates the record, not merely the log line ([CI-integrity bug: a detected failure is logged but not recorded](../learnings/1782392187766-ci-integrity-bug-class-a-detected-failure-is-logge.md)).

"Read actual source, don't draft from memory" applies to your **own** recent findings too. In one sweep the report body, written close to verification, correctly said #13043 was blocked by #13041, while the later advice line, paraphrased from recall, named #13042. When a summary asserts "PR #N is doing X", re-verify with `gh pr checks <N>` at write time, even minutes after verifying it ([double-check PR numbers before naming which PR has which failure](../learnings/1789424667165-ci-babysitter-double-check-pr-numbers-before-namin.md)). Sweep **counts** have their own instrument: one full scan told its parent "13 triaged / 47 skipped" from memory, while `sweeplib.triage_set(ci_state, live_shas)` on live rollups gave 38 triaged / 4 skipped and the on-disk `last-triage-receipt.json` was two months old. Only `append_row` on a summary row checks the receipt; a plain `send_message` has no guard. Run `triage_set` and quote its output before any count goes into a parent report, and tally the verdict split *before* `touch_tracker_verdict`, or new entries count as "reconfirmed" ([derive sweep triaged/skipped counts from sweeplib.triage_set](../learnings/1791223676043-derive-sweep-triaged-skipped-counts-from-sweeplib-.md)).

## Classification and Attribution Checks

- **Verify passed-vs-FAILED before citing a test signature in an escalation:** grep the run log for the `FAILED test:` line, not any mention of the test name ([verify passed-vs-FAILED before citing a test signature](../learnings/1784096353229-verify-passed-vs-failed-before-citing-a-test-signa.md)).
- **An aarch64 build red is usually a Setup-stage infra flake, not a compile error** (slang#12123, test-only single .cpp): classify by whether the red reproduces across platforms and unrelated PRs before concluding "compile error" ([aarch64 build red is usually Setup-stage infra-flake](../learnings/1784138142765-approver-challenger-miss-aarch64-build-red-on-a-sl.md)).
- **Don't reflex-classify `test-falcor` as flake.** On slang#12089 (HitObject SER-ABI re-gating) `test-falcor / Test (Falcor)` failed on revs 2–4 as the recurring external image flake; on rev5 that prior became "all infra/flake" without reading the log, but the downstream-integration job was reproducing the PR's own breaking change (E41011 on the re-gated capability surface) ([don't reflex-classify test-falcor as flake](../learnings/1784140075876-approver-challenger-miss-don-t-reflex-classify-tes.md)).
- **A real regression can be CI-invisible.** PR #12125 added `tools/compile-perf/native/api-driver.cpp` including `<psapi.h>` before `<windows.h>`; the tool is compiled out-of-band by `bench.py`, so the Windows include-order break is real yet no check goes red ([compile-perf native tools escape CMake CI](../learnings/1784147373872-approver-challenger-win-compile-perf-native-tools-.md)).
- **A closed CI-flake issue can harbor a real latent bug in the same path.** slang#11951 (`static-const-matrix-array.slang.3 syn (llvm)` RPC drop) closed after PR #12056 fixed the cause (AVX-512 illegal instruction in the LLVM JIT on virtualized hosts → test-server child crash → JSON-RPC drop); judge alt-root-cause comments on their merits (→ PR #12114) ([a closed CI-flake issue can harbor a real latent bug](../learnings/1784152131245-a-closed-ci-flake-issue-can-harbor-a-real-latent-b.md)).
- **`SLANG-WINDOWS-2` is an image-baked pool name, not a physical host.** On the Windows GPU tier (`["Windows","self-hosted","GCP-T4"]`, ci.yml:467–504) the log's `Machine name: 'SLANG-WINDOWS-2'` is shared by many ephemeral GCP-T4 VMs; resolve runners by `runner_name`, never "same physical runner" from a matching Machine name ([SLANG-WINDOWS-2 is an image-baked pool name](../learnings/1784161547411-slang-windows-2-is-an-image-baked-pool-name-not-a-.md)).
- **`Nightly MDL Perf Test` is a front-end compile-time perf gate**, not a GPU/correctness or MDL-corpus runtime test ([Nightly MDL Perf Test = compile-time perf gate](../learnings/1784184423207-nightly-mdl-perf-test-compile-time-perf-gate-not-a.md)).
- **`health_snapshots.jsonl` (slang-ci-analytics) can be months stale**, so the daily report's CI-health step must not assert live queue health from it ([health_snapshots.jsonl feed can be badly stale](../learnings/1784189757200-ci-health-snapshots-jsonl-feed-can-be-badly-stale-.md)).

## Verify the CONSEQUENCE at Its Own Surface

**A wedge is evidence of a wedged *run*, not a wedged *outcome*.** A `pages build and deployment` run stuck `queued` for 72 days was reported as "docs silently stale since May", but `GET /pages/builds` showed Pages built ten weeks *after* the run stalled. A system with more than one path to an outcome routes around a stalled run silently, so "this never finished" → "its product is stale" needs separate evidence, usually at a different endpoint ([a wedged run is evidence of a wedged run, not a wedged outcome](../learnings/1786264741786-a-wedged-run-is-evidence-of-a-wedged-run-not-a-wed.md)).

**An all-green CI dashboard can mean a stopped pipeline.** `jobs_queued:0, runs_queued:2, runners idle` looked healthy, but master hadn't advanced in >32 h, zero `merge_group` runs existed, and the one running job was `CI Health` observing itself — one environment-protection gate had wedged the estate into a self-sustaining yield/retry loop. Before calling a snapshot healthy, ask *did work flow?* (branch advance, merge-queue runs); check `GET /actions/runs/{id}/pending_deployments` on long-`waiting` runs (env gates don't surface as failures); classify each "failed" run by *which* jobs failed (gate/roll-up jobs failing with the rest skipped is a policy exit); and a zero denominator is undefined, not 0% ([an all-green CI dashboard can mean a stopped pipeline](../learnings/1786264150678-an-all-green-ci-dashboard-can-mean-a-stopped-pipel.md)).

**Know the health feed's baselines.** `runs_queued` sits at **2** because two slang runs have been stuck `queued` since May 2026 (26596502131, the stalled Pages run above, and 26435273307, `Falcor Tests`), so only a value above 2 means anything. The opposite blind spot is `status=waiting`: slang `CI` runs in that state (100+ on 10-05) are bot `fix/issue-*` `workflow_dispatch` runs parked at `falcor-build-approval-gate` (environment `falcor-ci`, team `ci-approvers`) — a human-approval backlog absent from `jobs_queued`. The snapshot counts only `queued`/`in_progress` runs, so jobs inside a `waiting` run are invisible too (an SM80 job waiting 77 min never showed); measure pool waits from each job's `created_at`→`started_at` in `/actions/jobs/{id}` ([snapshot misses jobs in waiting runs](../learnings/1792486355939-ci-sweep-snapshot-misses-jobs-in-waiting-runs-only.md)). That blind spot can hide full saturation: on 10-27 a maintainer started 34 parked fork `CI` runs (44 jobs each, 29 hosted) in 19 min, ~1,000 hosted jobs at once. For four hours the snapshots showed hosted `in_progress` = 1 (CI Health itself) while 26–158 `ubuntu-latest` jobs queued, board-sync jobs waited up to 232 min, and 15 CI Health runs were cancelled, leaving 78- and 114-min gaps — the approved runs' jobs filled the 60 hosted slots while their runs stayed `waiting`. Detect it by listing `status=waiting` runs with `triggering_actor` and `run_started_at` (a created-in-window list misses them), and read `pulls/N/commits`: a maintainer's web-flow "Merge branch 'master' into ..." is "Update branch", which starts a fresh 46-job run. Through OneCLI, urllib calls to `/orgs/...` and `repos/.../actions/...` go out anonymous (60/h, or 401); `search/repositories` and `search/issues` work ([bulk approval of parked fork CI runs saturates CI](../learnings/1793176887944-bulk-approval-of-parked-fork-ci-runs-saturates-sla.md)). For scheduling health checks: through OneCLI, `actions/runs?created=>=<ts>` returns an empty body (a JSON decode error) unless `>=` is encoded `%3E%3D`; the weekly `CMake Options` sweep runs Saturdays 08:00Z; and slangpy's scheduled `sanitizers` workflow has never been green (52/52 failed, slangpy#1130), so a red there is not news ([CI health queries: URL-encode created>=, runs_queued floor of 2](../learnings/1791188297214-ci-health-queries-url-encode-created-runs-queued-f.md)).

**The discriminator for a health claim beside a bucket table is terminal-vs-non-terminal, not "smallest bucket".** A `nonterminal 1` row *was* the blocker (a run parked on a deployment gate that retry logic counted as "still active"), while flagging singletons scored ~11% precision. Whoever is about to *act* on a health claim runs the probe — two independent readers missed it ([non-terminal is the cell a health claim rounds away](../learnings/1786264504844-non-terminal-is-the-cell-a-health-claim-rounds-awa.md)).

## Memoized Verdicts, Armed Checks, and Retiring Guards

A memoized verdict ("skip this PR, logs expired") voided only on **head-sha change** misses a fresh run on the *same* sha (label retrigger, deployment gate resolving, `merge_group` batch, manual `workflow_dispatch`), and the failure is invisible: a skip suppressing a real red and one correctly suppressing expired evidence both print `triaged=0`. Add a **freshness test** every sweep — per marked PR, compare `max(started_at)` of its failing runs against the pin date; a run inside the ~168 h retention window falsifies "evidence is gone" (it found 0 gap-hits at 08:00Z and 3 at 10:00Z the same day, so a clean result is not standing). Pair it with a **planted negative control** (`is_skipped(pr, pinned_sha)` True *and* `is_skipped(pr, 'f'*40)` False), since `skipped == len(marks)` is also what a guard hardwired to `True` produces ([a skip mark voided only by head-sha is blind to a fresh run](../learnings/1786263100539-a-skip-mark-voided-only-by-head-sha-is-blind-to-a-.md), [a sha-pinned skip mark has a freshness gap](../learnings/1786270442513-a-sha-pinned-skip-mark-has-a-freshness-gap-a-new-r.md)).

Generally, **any memoized verdict needs an invalidation trigger for every input that can change the answer.** Two relatives: *a durable record is not a due action* — an armed nightly-CI monitor with correct coverage resolved silently because no sweep step read it; a compaction-proof ledger note is durable, not due, until it is on the sweep's emit list. And *a guard's retirement condition is part of its design* — a figure protected by an armed check regressed a third time the moment the check correctly retired, because a settled measurement outlives its question and needs a permanent home (as-of stamp + population + reproduction basis + invalidation trigger) the guard's lifetime doesn't bound ([a durable record is not a due action](../learnings/1786257122553-a-durable-record-is-not-a-due-action-armed-checks-.md), [a guard's retirement condition is part of its design](../learnings/1786264054032-a-guard-s-retirement-condition-is-part-of-its-desi.md)).

## "Nightly Green" Names a Workflow, Not the Nightlies

shader-slang/slang schedules `Nightly Slang Test` (its `agentic-tests` job runs `docs/generated/tests`), `Nightly Slang VKGLCTS Test`, `Nightly MDL Perf Test` (`Check trend` fails on compile-time regressions against the trailing median), `ubuntu18-gcc11 Release`, `Linux glibc 2.28 Release`, and the weekly `CMake Options`. On 09-24 the maintainer seat reported "Nightly GREEN" from VKGLCTS alone and Main relayed it, while `Nightly Slang Test` had been red since 09-23 (`docs/generated/tests/design/ir-reference/metadata/debug-no-scope-emitted-without-operands.slang`) and MDL Perf went red on 09-24. Name the green workflow before saying or relaying "nightly green", and treat an unnamed one as unverified for every other workflow (["Nightly green" is per-workflow](../learnings/1790509221208-nightly-green-is-per-workflow-check-every-slang-ni.md)). The check works without GitHub auth (unauthenticated REST: 60 core requests/h, 10 searches/min): `actions/workflows/<id>/runs?per_page=10` per workflow, ids from `actions/runs?created=>=DATE&status=failure` (`curl -G --data-urlencode`, or the body is empty); `check-runs/<job_id>/annotations` for perf lines such as `backend_matrix_glsl/compileInner 1.11x`; `curl -L .../actions/jobs/<job_id>/logs` (302 → blob) to grep `FAILED test`; `compare/<last-green>...<first-red>` for suspects. Corroborate a "0 merged" search with master `commits?since=` and `actions/runs?event=merge_group` — an idle queue is not a failing one ([nightly green must enumerate every nightly; unauth REST fallback works](../learnings/1790509064349-slang-nightly-green-must-enumerate-every-nightly-w.md)).

**A red nightly needs reading before it is called a test failure.** On 10-08 step `Lint the agentic-tests bundles` failed (doc move #13439 produced 589 lint errors) and `Run agentic test suite` was skipped; the same move of the language reference to the spec repo left master-side broken links, so advisory `doc-gaps` reds from it are not the PR's (fix slang#13510; don't file a duplicate) ([checks_timed_out note; doc-gaps after the spec-repo move](../learnings/1791484800264-merge-queue-eviction-reason-checks-timed-out-group.md)). A skipped suite hides real failures: when the lint fix landed, an older stale WGSL CHECK from #13569 surfaced, so when a gating step goes green expect what it hid in the next step. MDL Perf per-night data is public in shader-slang/slang-compile-perf `daily/<date>-<sha>/{results.json,confirmation.json}` with no artifact download: list labels via `contents/daily` and fetch `https://raw.githubusercontent.com/shader-slang/slang-compile-perf/main/daily/<label>/results.json` (`timers.<Counter>.median`); `confirmation.json` holds baselines, thresholds, regressions and warnings. That showed the 10-16 `generic_builtin_operator` SemanticChecking step vanish after the #13537 revert (#13712): 46.78 → 56.44 → 46.44 ms ([MDL perf numbers are public; a red lint step can mask suite failures](../learnings/1792226254592-mdl-perf-numbers-are-public-in-slang-compile-perf-.md)). Quote `plan.regressions[].value` (confirmed), not the annotation's first sample (apiGetCode 33.4 ms annotated vs 23.6 ms confirmed). A master commit's `commit.committer.date` is when the PR *entered the merge queue* (#13439: 08:04Z vs `merged_at` 09:06Z), so use `pulls/<n>.merged_at` for time and `compare/<fix>...<nightly sha>` for ancestry ([merge-queue commit dates, nightly lint reds, MDL confirmation.json](../learnings/1791448556917-ci-health-merge-queue-commit-dates-and-the-1000-ru.md)).
