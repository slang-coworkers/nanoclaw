## TL;DR
- **Every reviewer fails toward CLEAN.** Devin exit 0 is not a signal; Reviewer A can emit a 0-byte or budget-capped output; Reviewer C can skip environmentally. **Verify each reviewer produced findings before treating "no findings" as a result** — an absent reviewer and a clean reviewer are byte-identical downstream.
- **Watch the ARTIFACT, not the subagent.** A Devin subagent returns before `devin-fetch.sh` finishes; a detached reviewer's completion is proven by its exit marker, never by streamed JSON. Anchor monitors to exit markers.
- **Read the full page dump, not the summary file.** `devin-flags.md` can have an EMPTY `## Flags` section while `devin-page.txt` from the same run shows real findings — synthesizing from the summary records a false "0 findings" and carries a false-clean prior into the challenger.
- **Reviewer A needs an isolated checkout.** Fleet contention on a shared repo root corrupts runs; `$30` is too low a budget cap and produces silent truncation. Use fresh per-run out-dirs to avoid `/tmp` collisions.
- **Two bots agreeing measures shared priors, not correctness.** Independent bots flagging the same item is weak corroboration; read the human review thread before scoring any structure/maintainability gap.
- **A bot finding a named maintainer already overruled ON THIS PR is not an open gap** — but **lead with the technical grounds**, never the maintainer's preference. Maintainer preference is supporting context; a repo guideline is not cleared by taste alone.
- **A refuted 🔴 does not become WOULD_APPROVE**, and a standing human `CHANGES_REQUESTED` caps the verdict at ABSTAIN. Never round up.
- **A mid-iteration `diff_hash` mismatch is expected under debounce**, not a bug. Pin the head, byte-prove reviews against it, and re-verify a stale secondary reviewer's flags at the current head.
- **Re-review scope: redesign gaps and self-recommended nits do not reset the pipeline.** Additive nit rounds are fine; a full re-run is not.
- **The review signal is endpoint-split across three surfaces** (`pulls/N/reviews`, `pulls/N/comments`, `issues/N/comments`) and the harvest reads one. That split is a property of GitHub's data model, so **every consumer inherits the blind spot independently — fixing one instance is not fixing the class.**
- **A GitHub post gates on the literal marker, not on prose.** Post only in COMMENT state; never APPROVE/REQUEST_CHANGES from a runner.
- **Empirical probes can test the wrong sub-case.** A probe that varies the intended factor while holding the confound constant reads as decisive and proves nothing — name the factor and the confound before citing a control.
- **In an artifact where claims cite `file:line`, the UNCITED SENTENCE IS THE DEFECT** — in a document whose norm is citation, the citation outlier is where an inference got restated as an observation. Run that self-check mechanically over your own draft.
- **Recording is not routing.** Documenting a blocking infra defect any number of times never reaches a file only an operator can edit. The record serves the next agent; the escalation serves the fix — do both.
- **A stale webhook dispatch on an already-decided PR is a no-op plus a report, never a re-decision.** `record_decision` is idempotent per `(repo, pr, sha)`, so re-deciding CLOBBERS a human-joined calibration row with a verdict contaminated by post-hoc information.
- **Read approval state from `latestOpinionatedReviews`, never `latestReviews`.** `latestReviews` is each reviewer's most-recent review *of any kind*, so a later COMMENTED from the same author makes a live APPROVED vanish. When an API offers two similarly-named collections, one is "most recent event" and the other "current state" — pick the one whose *definition* answers your question, and distrust any field whose name describes recency when you need state. Then check the verdict's bound commit: an APPROVED at an older commit is push-invalidated; a DISMISSED at a stale commit is not a dismissal at head.
- **Name the system a status belongs to before asserting the status.** "Approved" is meaningless without "approved *in what*". Internal review pipelines, codex stages, and peer coworker verdicts are real approvals and are **zero GitHub reviews** — a PR can carry eleven internal rounds and still read `reviewCount: 0 / reviewDecision: REVIEW_REQUIRED` to the maintainer whose queue it lands in. The honest split form ("3 internal pipelines approve; 0 GitHub reviews") is longer and strictly stronger, because the compressed form reads as overstated the instant anyone runs the query.
- **Local build + green tests are not delivery.** The heavier the local verification, the more it masquerades as shipping — a 20-minute compile produces a sense of completion a `git push` does not. "Corrected locally but undelivered" and "never corrected" are indistinguishable from outside your container. Discriminate with `git show HEAD:<path> | grep -c` vs `grep -c <path>`, then verify against the **remote object** after pushing.
- **A local grep, a clean `git status`, and a successful checkout all fail toward the answer you want.** Ask what the output would look like if the work had *not* landed; if it looks the same, you have not measured. A checkout of the wrong ref exits 0, and "0 files changed" is the expected output of both "wrong ref" and "already up to date" — so verify content arrived with a grep for a revision-unique marker whose expected count is non-zero.
- **Before merging or rebasing into a branch you authored, fast-forward the remote tip first.** A maintainer with write access can push to a bot branch, and a stale worktree gives no signal: clean status, your commit at HEAD, your branch name. Prove `git merge-base --is-ancestor HEAD origin/<branch>`, `--ff-only` the remote, and only then merge master. Compare the **index** (`git diff --cached origin/master --stat`), not the worktree, so stale submodule pointers don't ride in as accidental reverts.
- **"Nobody touched it in N days" is an inference from the wrong instrument.** `updatedAt` and your local `git log` can agree with each other and both be wrong about who last wrote to the branch. `git log -1 --format='%an' origin/<branch>` can invert "close as superseded" into "engaged maintainer, needs a merge".

## Recovering a Teardown-Stranded PR-Review Pass Without a Full Re-Run (2026-07-21 fold)

When the orchestrated slang-pr-review runner (Reviewer A / `compose-and-run.sh`) is stranded by session teardown, a full ~25-min re-run is usually unnecessary — recover in layers. (1) **Salvage completed reviewers first:** Devin (B) artifacts persist at `/workspace/agent/review-<pr>/devin/devin-flags.md`; Clarity (C) run dirs can be GC'd after days, but if you already read `clarity-review.md` into context, reconstruct it into a file rather than re-running. (2) **Recover partial A verdicts from the dead run's `stream.jsonl`:** the first run's 600s inner background-wait ceiling often truncates AGGREGATION while the individual subagents already reported, so extract per-subagent `result` summaries (`python3` over the jsonl, filter `type=="result"` with `len(result)>60`) — 4/6 verdicts are usually recoverable verbatim. (3) **Re-run ONLY the missing dimensions in-turn** as direct `Agent()` calls, which complete in-turn with no teardown window, unlike background bash tasks that die on container recycle. Two infra failure modes to root-cause rather than paper over: **REVIEW-GUARD FAIL (<500B final-review.md)** = inner `claude --print` hit the 600s ceiling → re-run with `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`; **INTEGRITY-FAIL "reviewed WRONG diff"** = a STALE `tmp/pr-diff.patch` from a prior review left in the repo root (the model's `gh pr diff > tmp/pr-diff.patch` was permission-denied so it never overwrote it) → `rm -f slang/tmp/pr-diff.patch` before re-running. Checkout gotcha: the local `/workspace/agent/slang` worktree usually sits on base master, not the PR head — `git fetch origin pull/<n>/head` then read via `git show <head>:<path>` to reason about real post-PR code ([Recovering a teardown-stranded PR-review pass without a full re-run](wiki/learnings/1784536666918-recovering-a-teardown-stranded-pr-review-pass-with.md)). **Fetch into a named ref you own — `git fetch origin pull/<n>/head:refs/pr/<n>` — and read from `refs/pr/<n>`, never from `FETCH_HEAD`:** the clone is shared by sibling sessions, so `FETCH_HEAD` may point at master by the time you use it, and a `git checkout FETCH_HEAD -- <paths>` against the wrong ref exits 0 with zero modified files (see the delivery-verification section below) [FETCH_HEAD is mutable and a checkout of the wrong ref fails silently](wiki/learnings/1786081698988-fetch-head-is-mutable-and-a-checkout-of-the-wrong-.md). The per-subagent recovery is verbatim: each of the six `.claude/agents/*` subagents emits its final text into the run-dir's `stream.jsonl` before the parent finishes, so group assistant `content[].type=="text"` blocks by `subagent_type` and keep the last substantial (>200 char) block per subagent (typically 4/6 survive; only the parent's synthesis and the cut-off subagent are lost, so resolve that one open question from source rather than re-running a 30-min pass). Critical: run-dirs are named `pr-<UTC-timestamp>Z/`, NOT by PR number — identify the right one with `grep "PR NUMBER" <dir>/prompt.txt` (or check `pr-diff.reference` head), or a concurrent review of a *different* PR with a populated `final-review.md` gets mis-attributed to yours [Slang PR-review: recover torn-down Reviewer A findings from stream.jsonl subagents](wiki/learnings/1784828278697-slang-pr-review-recover-torn-down-reviewer-a-findi.md).



## In-Turn Polling on Teardown-Prone Clusters; Fresh Devin Out-Dirs Per Run (2026-07-22 fold)

**When a cluster has stranded a review on session teardown even once, drive reviewer completion with in-turn bounded blocking Bash polls, not a background `Monitor`.** Observed 3× on one cluster (#12116 ×2, #12162): a background monitor (even persistent) dies on container teardown and leaves the pipeline with no verdict reaching the parent, while the workflow's "end turn after dispatch" step assumes the monitor survives. The durable pattern: launch A/B/C detached, record run dirs to a stable `run-dirs.env` (survives teardown), then loop `pgrep` in a bounded `while` inside a single Bash call (~8-9 min) repeating across turns until all three exit — each blocking Bash call returns a real result to context, so progress is durable across turn boundaries. Gotcha: `pgrep -f 'compose-and-run.sh --mode pr --pr N'` matches your OWN polling shell's command line — confirm real exit via the script's log epilogue, not pgrep alone. And always re-confirm PR head before re-driving a stranded review (teardown + a fixer re-push can make it stale twice over) ([in-turn polling beats background Monitor on teardown-prone clusters](wiki/learnings/1784625017836-slang-pr-review-in-turn-polling-beats-background-m.md)).

**Reviewer B (Devin): use a fresh, unique out-dir per run, or verify `devin-flags.md` mtime before trusting it.** On a Devin timeout `devin-fetch.sh` writes only `devin-error.txt` and leaves any pre-existing `devin-flags.md`/`devin-page.txt` untouched — so a reused shared out-dir can smuggle stale flags from a COMPLETELY DIFFERENT PR into `combined-review.md` (observed: reviewing #12186, the dir held Jul-2 flags about an unrelated glsl struct-initializer PR). Use `/workspace/agent/devin-out-<pr>-<ts>`, `ls -la` and confirm the flags file's mtime is from this run; if only `devin-error.txt` is fresh, mark Reviewer B skipped (do not cat the stale file); and a `run_in_background` wrapper reports exit 0 for a trailing `echo`, not the script's real status — check `devin-error.txt`, not the shell exit code ([Devin out-dir reuse can smuggle stale flags from a different PR](wiki/learnings/1784697016109-devin-out-dir-reuse-can-smuggle-stale-flags-from-a.md)).



## Resume-Reuse, Additive Nit Rounds, and Off-Repo Reviews (2026-07-24 fold)

When a review "stranded" (the background Monitor died on session teardown) but the reviewer *processes* actually completed, their run-dir outputs (`final-review.md` / `clarity-review.md` / `devin-flags.md`) survive — before re-dispatching a fresh 3-reviewer pass on resume, check artifact survival AND diff *what was reviewed* vs *current head at the CONTENT level*, not the commit level. A rebase/amend changes blob hashes even when content is identical and GitHub `compare` shows a misleading "ahead=1 behind=1"; the right comparison extracts file-blocks from Reviewer A's saved `pr-diff.reference`, strips volatile `index <hash>` lines, and diffs against a similarly-normalized `gh pr diff`. Empty diff on the real code+test files ⇒ the prior review is valid for the current head (concrete win on #12200: reviewed `fcfcc00` vs shipping `e7dc2ba`, 9 files byte-identical, only delta a removed scratch file → reused all three outputs, saved ~25 min). A consequence to handle: any finding *about a removed file* becomes MOOT on the shipping head — subtract it from the live count and say so; and per parent instruction after a monitor-strand, run these reviews FOREGROUND/in-turn, never re-arm a background Monitor (that's the strand's root cause) ([Reuse completed reviewer outputs when head-delta is non-code-only](wiki/learnings/1784882724986-reuse-completed-reviewer-outputs-when-head-delta-i.md)). Even an already-approved fix's additive "do-while-in-file" nit round needs the same rigor: a test's *prose claim* needs a `CHECK`/`CHECK-NOT` backing it or the prose must be narrowed (codex OUTPUT_REVIEW flagged an unbacked "no whole-handle copy" claim as must-fix; fix = scoped `CHECK-NOT: OpVariable ... Function` + `CHECK-NOT: OpCopyMemory` between two CHECKs) — and codex catching a **false claim in a comment you authored yourself** is the highest-value critique (self-authored inaccuracies are hardest to catch solo; always re-run OUTPUT_REVIEW after comment edits — "comments only" is not "safe"). When a fix's mechanism handles N sibling types (`isNonCopyableOpaqueType` covers both RayQuery and HitObject), add a positive test per sibling — an untested path the *same code* miscompiles-then-fixes is where a future refactor silently regresses ([Additive review-nit rounds still need CHECK-NOT backing + accurate comments (codex catches self-authored false claims)](wiki/learnings/1784884204062-additive-review-nit-rounds-still-need-check-not-ba.md)).

Reviewing a PR on a repo that is NOT the compiler (e.g. `shader-slang/slang-rhi`) breaks the runner skills: both Reviewer A (`compose-and-run.sh`) and Reviewer C (`run-clarity.sh`) hard-default `REPO_ROOT=/workspace/agent/slang` + `git checkout origin/master` (slang-rhi's default branch is `main`), `compose-and-run.sh` requires a `REVIEW.md` that slang-rhi lacks, and their compiler-domain `.claude/agents/*` / `slang-review-*` subagents don't fit an RHI (C++ graphics abstraction) codebase — pointing `--repo` at them reviews the wrong checkout or emits domain-mismatched noise. The adaptation that works (slang-rhi#802): fetch the PR head into a `wt-<pr>-review` worktree of the *real* slang-rhi checkout, run **Reviewer B (Devin) natively** (it's the one runner that transfers unchanged — reviews any public GitHub PR by URL), dispatch general-domain `Agent`s with repo-appropriate lenses for A (correctness) and C (clarity), personally verify the load-bearing claims, and merge into `combined-review.md` with the same 5-bullet + JSON block, flagging the repo-mismatch adaptation in the header for transparency ([slang-rhi PR review: A/C runner skills hard-target the compiler repo — adapt](wiki/learnings/1784929061497-slang-rhi-pr-review-a-c-runner-skills-hard-target-.md)).



## In-turn polling, budget-cap 0-byte recovery, runner-flag invocation & tmp-collision isolation (2026-07-27 fold)

Four more operational lessons hardened the pipeline. **Never end a foreground review on an armed background waiter.** When told to run a PR review "in-turn," dispatch the reviewers with `nohup … &` (they detach 20-40 min) but stay in the turn with **bounded blocking Bash calls** — short `while [ $(date +%s) -lt $end ]; do pgrep -f <reviewer>; sleep 25; done` loops (~8-9 min each) that RETURN as a tool result when the reviewers finish. A Monitor / `run_in_background` `until`-loop does NOT survive session teardown; that strand hit the reviewer cluster 5× (#12116 ×2, #12162, #12200-first, #12231-first). The completion signal must be a tool result you're holding, not a background event you ended the turn to wait for [In-turn PR-review polling: bounded blocking Bash calls, never an armed background waiter](wiki/learnings/1785143391944-in-turn-pr-review-polling-bounded-blocking-bash-ca.md). **A FAILING guard on a job that exited 0 warrants a stream check before you report failure:** Reviewer A can produce its full final review and then hit `error_max_budget_usd` on the very last (file-write) turn, so `final-review.md` is absent → the REVIEW-GUARD reports "0 bytes / no substantive review" and the summarizer parses 0/0/0 — but the complete review is intact in the last top-level assistant message in `stream.jsonl` (recover it, don't re-run at ~$30/20min). Bump `--max-budget-usd` to 35-40 for large diffs; and confirm drift==0 by counting actual POST tool_use calls, not by grepping the model's quoted REVIEW.md protocol prose [slang-pr-review Reviewer A: "0 bytes / no review produced" guard can be a lie when the run hit the budget cap — recover from stream](wiki/learnings/1785186988820-slang-pr-review-reviewer-a-0-bytes-no-review-produ.md). **The runner scripts take flags, not the skill verb:** `slang-clarity-review-runner`'s `argument-hint` shows `run-clarity --mode pr …` but `run-clarity.sh` parses flags only and exits 1 on the leading `run-clarity` token — invoke `bash scripts/run-clarity.sh --mode pr --pr <N> --repo <owner/repo> …` (drop the verb); `compose-and-run.sh` behaves the same way [slang-clarity-review-runner script takes flags, not a run-clarity subcommand](wiki/learnings/1785192373525-slang-clarity-review-runner-script-takes-flags-not.md). **A wrong-PR integrity-fail is a shared-`tmp/` race, not a code bug:** `compose-and-run.sh` stages the diff into a fixed `$REPO_ROOT/tmp/`, so two concurrent runs on the same `/workspace/agent/slang` checkout clobber each other mid-flight and the integrity net refuses to emit `final-review.md` (leaving `INTEGRITY-FAIL.txt`). Fix = re-run Reviewer A in an isolated `git worktree add --detach wt-<PR>-reviewerA HEAD` with `REPO_ROOT` pointed at it (REVIEW.md + `.claude/agents/` are git-tracked, so a base-HEAD worktree has them); name it `wt-<num>-<tag>` so supervisor GC reaps it [Reviewer A wrong-PR integrity fail: shared tmp/ staging collision between concurrent runs](wiki/learnings/1785209892572-reviewer-a-wrong-pr-integrity-fail-shared-tmp-stag.md).

Several reviewer-runner operational facts from the #12262/#12263 rounds. **Reviewer A's `INTEGRITY-FAIL` can be a false positive**: its post-run guard reads the FIXED shared path `tmp/pr-diff.patch`, which a concurrent same-container run for a different PR overwrites — so it reports files from the wrong PR. Trust the per-run `<run_dir>/pr-diff.reference` and the `final-review.md` footer `reviewed: <sha> · diff sha256` (captured at start, not shared); also locate your run dir by matching `prompt.txt`'s `PR NUMBER:`, not by mtime ([Reviewer A INTEGRITY-FAIL can be a false positive from concurrent runs sharing tmp/pr-diff.patch](wiki/learnings/1785338666942-reviewer-a-integrity-fail-can-be-a-false-positive-.md), builds on the shared-tmp collision entry above). **When gh auth is dead on a PUBLIC repo, don't fall back to patch mode** (it drops new files via `git commit -am` and aborts on stale untracked files) — build a tiny read-only `gh` shim over local git (`gh pr diff` → `git diff merge-base..head`, `gh pr view` → prebuilt json) first on PATH, then run the production `pr` mode unchanged; Devin/Reviewer B scrapes the public URL anonymously regardless ([gh-shim fallback for dead token on public repo (pr-mode review)](wiki/learnings/1785339099440-gh-shim-fallback-for-dead-token-on-public-repo-pr-.md)). **Reviewer C (clarity) can exhaust its turn budget right before the canonical write** — don't just re-run (same failure, GC's the worktree); recover the raw candidates from the run's `stream.jsonl` Write-tool inputs (`tmp/review-candidates/pr-<N>-*clarity.md`) and mark `reviewers_complete:false`; bumping the turn/budget cap does not help since investigation depth is the cost ([clarity reviewer C exhausts turn budget before canonical write — recover from stream](wiki/learnings/1785339114704-clarity-reviewer-c-exhausts-turn-budget-before-can.md)). Two enumeration/diff disciplines: PR-feedback enumeration must query the UNION of `reviews`, `reviewThreads`, AND issue-level `comments` — substantive blocking feedback (e.g. szihs on #996) often lives in issue comments that per-node review filters drop ([PR review-feedback enumeration must query ALL comment types incl issue-comments](wiki/learnings/1785353452935-pr-review-feedback-enumeration-must-query-all-comm.md)); and scope a diff from `gh pr diff <n> -R <repo>` (diffs against remote base), never a local `git diff main...head` whose stale local `main` can inflate a 1-file PR to 40 files — the `gh pr diff` sha256 is also the review's `diff_hash` ([use gh pr diff, not local git diff --stat (stale-main trap)](wiki/learnings/1785357368357-slangpy-pr-review-use-gh-pr-diff-not-local-git-dif.md)).


## Reading PR Approval State: `latestOpinionatedReviews`, and Naming the System (2026-08-05/06 fold)

Two failure modes turn "is this PR approved?" into a wrong answer: reading the right system with the wrong field, and reading the wrong system entirely.

**Field choice: `latestOpinionatedReviews`, never `latestReviews`.** `latestReviews` returns each reviewer's *single most recent* review of any kind, so if a maintainer APPROVED and later submitted a plain `COMMENTED` review (an inline note, a "thanks"), only the COMMENTED survives the collapse and **the APPROVED is absent entirely** — a session querying there concludes they never approved. Measured on shader-slang/slang#12186 with both reviews bound to the same current head: `latestReviews` gave `pdeayton COMMENTED (08-05)` while `latestOpinionatedReviews` gave `pdeayton APPROVED (08-03)`, same author, same PR. "Opinionated" means `APPROVED` / `CHANGES_REQUESTED` only; it is the field whose definition already *is* "each reviewer's live verdict," so prefer it over hand-filtering `/pulls/<n>/reviews` by author — filtering works but makes you re-implement "which verdict is live" yourself. If you do filter the full list, assert `rows == totalCount` before trusting a tally (a `--paginate --jq` filter applies **per page** and silently under-reports), and read each row's bound `commit`: an APPROVED at the current head has not been push-invalidated, one at an older commit has, and a `DISMISSED` at a *stale* commit is not a dismissal at head. **A later COMMENTED from the same author does not retract an APPROVED** [GitHub approval state: use latestOpinionatedReviews, never latestReviews — a later COMMENTED hides a live APPROVED](wiki/learnings/1786073602625-github-approval-state-use-latestopinionatedreviews.md). The generalizable form is worth more than the field name: when an API offers two similarly-named collections, one is usually "most recent event" and the other "current state," and **they disagree precisely in the interesting cases** — be suspicious of any field whose name describes *recency* when your question is about *state*. Same family as a field whose name implies a state but is not a test for it (`started_at` is populated on jobs that never started). Adjacent scope caveat: don't inherit a *route* from a higher-scoped peer without re-establishing its domain on your own edge — a cross-group `sessions list --thread-id` query a parent had verified returned `[]` at `cli_scope: group` because the flag set there has no `--group`/`--all`. **An empty result identical to your own negative control is a failed measurement, not a finding**: say "unmeasured from my edge," never "absent."

**System choice: name the system a status belongs to before asserting the status.** Arguing to flip a draft PR to ready-for-review, a session wrote that *"reviews are already in hand"* — citing a reviewer coworker's APPROVE_WITH_NITS over 11 rounds, codex approving across 3 stages / 24 rounds, and a triager's independent verification. Measured on the PR: `reviewCount: 0`, `reviewDecision: REVIEW_REQUIRED`, `reviewers: []`. All three approvals were **real**; none was a GitHub review event, and **only the GitHub one is what the maintainer sees** when the flip lands in their queue. The generator is substituting *the artifact you can see* (peer verdicts in your own message history) for *the artifact the audience reads* (review state on GitHub) — the same shape as citing a local file's content for the published copy, or inferring a handler's behavior from its presence in a dispatch table. "Approved" is meaningless without "approved *in what*": an internal pipeline and a GitHub review are different objects with different audiences, and only one of them gates anything upstream. The honest split — *"3 internal review pipelines approve; 0 GitHub reviews"* — is longer and strictly stronger, because **the compressed version reads as overstated the instant someone runs the query**, costing you the credibility of the rest of the argument. Compression that hides the weaker half is not concision [Internal pipeline approvals are not GitHub reviews — name the system a status belongs to before asserting it](wiki/learnings/1786074647297-internal-pipeline-approvals-are-not-github-reviews.md). From the same message, a companion discipline that generalizes past review state: a claim of the form *"a draft PR structurally cannot get CI coverage"* was drawn from **one** PR; a peer measured the fleet instead and found 3/3 drafts with zero non-skipped build/test jobs **plus one non-draft that DID get 30** — and named the confound the original lacked (the gate yields to higher-priority CI, so n=4 correlation cannot separate draft-status from queue contention). **"X structurally cannot Y" requires an instance of X that DID Y, or a read of the mechanism** — N more confirmations from the same arm is the cheapest-harness trap, covering one region N times.
