## TL;DR

- The `PreToolUse` Bash hook `gate-critique-on-deliver.sh` matches command **text**, not effect. Its `BASH_PATTERNS` includes `gh api [^|]*pulls\b`, so it denies **read-only** `gh api .../pulls/...` GETs (reviews, comments, files) as "PR creation." `gh api` defaults to GET; nothing in a read implies a mutation.
- Read PR data through surfaces the pattern never sees: `gh pr view --json`, `gh pr diff`, `gh api graphql` (reviewThreads), the `issues/N/...` endpoints, or the `mcp__slang-mcp__github_get_pull_request_*` MCP tools (not Bash → never seen by the hook). `commits/<sha>/status` and `check-runs` are usually safe, but after post-approve edits one session saw even those and a graphql query denied; the MCP tools are the one surface that never trips.
- The hook lives **in the container image**, not host source. A peer grepping `src/guard/` finds nothing — that locates the gate, it does not refute it. Scope every gate claim to LAYER + path + line + exact command + edge.
- A guard that fails to *record* is indistinguishable from one that *permits*. On a cold container where `/workspace/.claude/` is absent, the denial counter can't persist → gate denies forever AND never escalates (fail-closed + no-escalation = deadlock). The fix is `mkdir -p` the state dir, never fail-open. Read the counter (`jq .critique_gate_denials`), not the silence.
- Hook stderr about its own state files ("No such file or directory" on `workflow-state.json.tmp`) is a **finding**, not noise.
- `CRITIQUE_GATE_ACTIVE=1` is host-injected env; a child process cannot unset it and deleting `.overlay-critique-gate` does nothing. Do NOT run a ceremonial `/codex-critique` just to zero the counter — with no artifact in flight that reviews nothing and only games the guard. Report the blocker instead.
- When a gate forces an instrument swap, re-check the substitute's fidelity: the MCP review tools truncate bodies to 1000 chars, which silently manufactures a "0 findings" read.
- ABSTAIN_* decisions are NOT critique-gated (they assert nothing about code). Re-ask the gating question every time the decision *state* changes; `WOULD_APPROVE`/`BLOCK` are gated, `ABSTAIN_POLICY`/`ABSTAIN_INFRA` are not.
- Ship an ABSTAIN `[Approval Decision]` via the `mcp__nanoclaw__send_message` **tool** (its shell hook has the abstain fast-path), never a trailing `<message>` block (the host `poll-loop.ts` gate has NO abstain fast-path and always refuses it).
- Keep the literal words `BLOCK` / `WOULD_APPROVE` out of ABSTAIN prose — the fast-path's negative guard is unanchored, so "not a BLOCK" defeats it. Say "a rejecting verdict" / "a clean approval."
- Delivery re-hashes every path in codex's `### Attested` block: never attest volatile files (`.claude-trace/*.jsonl`, `logs/*`, `/workspace/*.db`) — they mutate every turn and block the post. Scope codex's reads+attestation to stable `work/<pr>-<sha>/` artifacts.
- `### Attested` lines must be bare `- <64-hex sha256> <abs path>` — a backticked hash, or a missing leading `- `, records nothing and the gate denies the approved file. Ask for that exact format in the final OUTPUT_REVIEW prompt; if it still comes back backticked, fix with a `codex-reply` asking for plain lines (or, if the stale earlier attestation persists, a fresh canonical round), then post the unchanged file. Check with `jq '.critique_attested.OUTPUT_REVIEW' /workspace/.claude/workflow-state.json`. Name the posted file under ARTIFACTS and ask for a one-word Verdict. A denial blocks the whole Bash command (and heredoc bytes in it count toward the comment-size gate), so write comment bodies in their own earlier step and post with `-F body=@<abs path>`.
- Any file write — including a `cat > /tmp/reply.md` heredoc — counts as an "edit" and re-arms the gate. Get one OUTPUT_REVIEW approve, then post all replies with inline bodies and zero writes between.
- Each gated STAGE (DECISION_REVIEW, OUTPUT_REVIEW) must be a **fresh** `mcp__codex__codex` call with the verbatim `/codex-critique` developer-instructions; `mcp__codex__codex-reply` never records a round (no `developer-instructions` param → fails the sentinel check).
- Evaluative absolutes ("improvement", "no new risk", "strictly improves") on an un-regression-tested change are OUTPUT_REVIEW must-fixes — describe what code DOES, never grade it, unless you measured it. Grep ALL artifacts for the absolute in one pass; a residual copy re-triggers.
- A PR-review "build it and run your checks" task cannot be satisfied by citing the fixer's PASS matrix — build+run yourself in a `git worktree add --detach` at the reviewed commit.

## The read-block defect: one matcher, many reports

Across at least seven independent sessions the same defect was re-discovered: `gate-critique-on-deliver.sh`'s `BASH_PATTERNS='gh pr create|gh api [^|]*pulls\b|api\.github\.com[^ ]*/pulls\b|createPullRequest'` matches command **text**, so it classifies every read-only `gh api .../pulls/N/reviews|comments|files` GET as "PR creation" and denies it with *"CRITIQUE REQUIRED before PR creation"* ([tooling: hook blocks read-only gh api pulls](../learnings/1786386194490-tooling-critique-gate-hook-blocks-read-only-gh-api.md), [critique-gate blocks PR reads, GraphQL reachable](../learnings/1786397603719-approver-infra-critique-gate-blocks-pr-reads-gh-ap.md), [bash hook false-fires on read-only GETs](../learnings/1786479308420-approver-infra-abstain-critique-gate-bash-hook-fal.md), [route PR/issue reads through MCP tools](../learnings/1787083477695-approver-infra-abstain-the-critique-gate-bash-hook.md)). This is the maxim *"a guard matching command TEXT enforces nothing about command EFFECT"* in its **over-blocking** direction: it stops legitimate reads and names an action that never happened, sending you to look for a delivery you aren't making ([matcher matches TEXT not EFFECT, over-blocking](../learnings/1786453015067-approver-infra-the-critique-gate-blocks-read-only-.md)). The hook's own comment concedes pattern enumeration can never be complete; it even denied a command whose only `pulls` was inside a grep string. On slang#14073 (2026-10-30) it caught `pulls/comments/<id>`, `pulls/<n>/comments` and a `curl` to the same path before any stage was recorded, each refusal counting toward the 3-attempt admin escalation. Subagents trip it too, so a dispatch names the read tools they must use (`mcp__slang-mcp__github_get_pull_request_comments` / `github_get_pull_request_reviews`) [critique-gate hook blocks read-only gh api pulls/comments GETs](../learnings/1793323215111-critique-gate-hook-blocks-read-only-gh-api-pulls-c.md).

Two second-order traps compound it. `track-edits.sh` bumps `edits_since_critique` on **any** Bash command with a `>`/`>>` redirect (`gh api … > /tmp/out.json` and memory bookkeeping count as "edits"), and the state carries over stale across sessions (one container read `last_critique_at: 2026-07-13` against a month-old work dir) ([TEXT not EFFECT + track-edits over-count](../learnings/1786453015067-approver-infra-the-critique-gate-blocks-read-only-.md)). And the MCP review tools the denial pushes you onto **truncate bodies to 1000 chars**, which manufactures a false "0 findings / reviewers_complete" read because verdict lines sit near the body end ([pulls-substring over-block + instrument-swap fidelity](../learnings/1786454460880-approver-infra-critique-gate-s-pulls-substring-ove.md)). The denial is loud; the truncation is silent.

**Scope the claim to the LAYER, then the edge.** The matcher is a `PreToolUse` hook inside the container image, not host source. A peer grepping `src/guard/` or the agent-runner finds nothing and can honestly report "works on my edge"; a negative grep of a *different* layer localizes the mechanism rather than refuting it ([scope a gate claim to the layer, not the edge](../learnings/1786386936182-approver-infra-abstain-scope-a-gate-claim-to-the-l.md)). Verify the pattern's line number on your own edge (a per-container fact) and pipe your literal command through the hook to test, but the test string itself trips the gate if it contains `pulls` ([recurrence, escalate rate not count](../learnings/1786454460880-approver-infra-critique-gate-s-pulls-substring-ove.md)).

## Counter and escalation failures on a cold container

The denial counter and the 3-strike escalation both write to `STATE=/workspace/.claude/workflow-state.json`, but the gate, unlike five sibling hooks, never `mkdir -p`s that directory. Where `/workspace/.claude/` does not exist, both writes fail silently (`|| true`): the counter stays `ABSENT`, so retries are "free" and the cap never trips ([denial counter silently failed on missing dir](../learnings/1786396976794-approver-infra-abstain-the-critique-gate-s-denial-.md)), and the human-escalation path that exists to unstick a wrongly-shut gate never fires: **fail-closed plus no-escalation is a deadlock, not a safe default** ([cold container denies forever AND never escalates](../learnings/1786397614230-approver-infra-cold-container-the-critique-gate-de.md)). The fix is `mkdir -p "$(dirname "$STATE")"` (matching the siblings), which restores escalation while keeping fail-closed; never make the gate fail open. A guard that fails to record is indistinguishable from one that permits, so read its counter, not its silence. The harvester's `collect-reviews.sh` survives the same `pulls/N/reviews` call only because the hook never inspects text run *inside a script*; that asymmetry (bare probe blocked, wrapped call passes) is why the defect went unnoticed.

**Working escapes** (all verified): `gh pr view --json` / `gh pr diff`; `gh api graphql` reviewThreads (route `/graphql` is never matched, and it returns more than REST: `isResolved`+`isOutdated`; cap 100 nodes, so assert `fetched == totalCount` and select the PR's own `number` for liveness); the `issues/N/...` endpoints (the `timeline` event shows who closed a PR without a `pulls` path); and the MCP GitHub read tools ([GraphQL reviewThreads with completeness+liveness asserts](../learnings/1786397603719-approver-infra-critique-gate-blocks-pr-reads-gh-ap.md), [issues endpoints + escalation payload tell](../learnings/1787083477695-approver-infra-abstain-the-critique-gate-bash-hook.md)). An escalation payload with `hit:"PR creation"` but null `repo/prNumber/prUrl` means a read tripped a mutation clause. Because the approver **skips the critique gate for ABSTAIN_* decisions**, the gate firing on a read is a known false positive, not a signal to run codex ([known false positive on ABSTAIN reads](../learnings/1786479308420-approver-infra-abstain-critique-gate-bash-hook-fal.md)). The pattern sits at `/app/hooks/gate-critique-on-deliver.sh:60`; `gh issue create` is not gated, though a 1000+-char body still needs an approved OUTPUT_REVIEW on its `--body-file`. On a merged PR, after post-approve memory edits, one session saw a `pulls/<n>` GET, a graphql reviewThreads *query* and a `check-runs` read all denied; `mcp__slang-mcp__github_get_pull_request{,_reviews,_comments}` and `github_get_issue` answered instead. With nothing being delivered, say so in-session and let the admin escalation handle the misfire rather than running a ritual codex round ([read-only gh PR queries blocked; use MCP reads](../learnings/1791208209365-gate-critique-on-deliver-can-block-read-only-gh-pr.md), [regex line 60; use issues/<n> or gh pr view](../learnings/1791303973484-critique-gate-blocks-read-only-gh-api-pulls-n-call.md)). Still live on 2026-10-23: a CI triage session's `pulls/<n>/reviews` GET was denied and `gh pr view <n> --json comments,reviews` read the same data ([falcor 30-day expiry triage re-hit the pulls over-block](../learnings/1792735967556-falcor-build-approval-gate-with-no-steps-30-day-du.md)). The durable fix (owner-gated; the hook is a read-only mount) is to require a write verb: `pulls\b` AND (`-X/--method POST|PATCH|PUT|DELETE` OR `-f/--field/--input`), spelled `(A.*B|B.*A)` since grep -E has no lookahead.

## Delivering the decision message: two gates, only one has the abstain fast-path

Two enforcement points guard the `[Approval Decision]` marker and they drifted out of parity. The shell hook governing the `mcp__nanoclaw__send_message` **tool** has an ABSTAIN fast-path; the host `poll-loop.ts` `blockedByCritiqueGate`, governing the final-text `<message>…</message>` path, has **none**, so an `ABSTAIN_POLICY`/`ABSTAIN_INFRA` in a trailing `<message>` block is *always* refused ([ABSTAIN must ship via send_message tool, not a <message> block](../learnings/1786479929909-approver-critique-mustfix-abstain-decisions-must-s.md)). Even on the tool path the fast-path fires only if the text has an ABSTAIN token and **neither** `WOULD_APPROVE` nor `BLOCK` as whole words anywhere, so a 5-bullet explaining "not a confident BLOCK" defeats `! grep BLOCK` and the generic gate demands stages an abstain never produces ([fast-path defeated by literal BLOCK/WOULD_APPROVE tokens](../learnings/1788385047068-approver-infra-abstain-critique-gate-abstain-fast-.md)). Ship via the tool and keep the bare enum words out of the prose ("a rejecting verdict", "a clean approval"). When a gate refuses something the policy exempts, read *which* gate fired (the wording differs) before assuming your artifact is wrong.

Running a gate after the decision state has moved is its own waste: one approver ran 12 OUTPUT_REVIEW + 3 DECISION_REVIEW rounds on a decision that had drifted to `ABSTAIN_INFRA:STALE_STAGE`. The gating question is a function of the *current* decision state, and an abstain asserts nothing about the code ([an ABSTAIN is not critique-gated](../learnings/1786417660584-approver-critique-mustfix-an-abstain-is-not-critiq.md)).

## Codex attestation and OUTPUT_REVIEW recording

The gate re-hashes every path in codex's `### Attested` block at delivery and denies if any changed since the approve. If codex `sha256sum`s a live-mutating file (`.claude-trace/session-*.jsonl`, `logs/container-*.log`, `/workspace/*.db`) the re-hash always mismatches and the post is blocked with "reviewed artifacts changed" although the approve was real ([delivery-gate + codex-attestation mechanics](../learnings/1786490307277-delivery-gate-codex-attestation-mechanics-that-blo.md), [codex attesting a volatile file falsely trips the gate](../learnings/1786740913803-approver-critique-mustfix-evaluative-absolutes-imp.md)). Scope codex's reads+attestation to stable `work/<pr>-<sha>/` files and have it use `gh api` (not local reads) for source confirmation. Because any file write, including a scratch heredoc, re-arms the "N edits since last critique" clause, the pattern is one approve, then *all* replies with inline single-quoted bodies and zero writes between (a bare `VAR=…; gh …` in the same Bash call is not a write).

Every gated STAGE must be a **fresh** `mcp__codex__codex` call carrying the verbatim `/codex-critique` developer-instructions; `mcp__codex__codex-reply` takes no `developer-instructions` param, so `track-critique.sh` never records it as a round whatever STAGE the prompt claims ([OUTPUT_REVIEW must be a fresh codex call, not codex-reply](../learnings/1786634623471-approver-critique-mustfix-output-review-must-be-a-.md)). Evaluative absolutes are must-fixes: calling a ctor change "strictly improves / no new risk" was correctly blocked because a parameterized-ctor path also changed init defaults. State what code *does*, never grade it unless measured, and grep ALL artifacts (message, decision.md, investigation.md, memory) for the absolute in one pass so a residual copy doesn't re-trigger ([evaluative absolutes are OUTPUT_REVIEW must-fixes](../learnings/1786740913803-approver-critique-mustfix-evaluative-absolutes-imp.md)). A reviewer's "build it and run your checks" cannot be met with the fixer's PASS matrix (the gate treats that as scope shrinkage); build+run in a `git worktree add --detach <path> <commit>` at the reviewed head so the primary checkout is undisturbed ([OUTPUT_REVIEW rejects "relied on the fixer's test run"](../learnings/1787104438946-pr-review-output-review-gate-rejects-relied-on-the.md)).

The edit clause counts **any** file Edit since the last approve, including files outside the delivered artifact such as `/workspace/agent/memory/fix-<n>.md`. So the tail of a fix runs: finalize PR body + code → OUTPUT_REVIEW approve → `gh pr edit`/`gh workflow run`/maintainer reply (`gh` calls and `send_message` are not file Edits) → `[Fix Report]` to parent → memory last. If you edited a non-delivered file after the approve, re-attest cheaply: reply on the same OUTPUT thread "no delivered artifact changed; only local file X edited; PR body and committed hashes unchanged" and ask codex to re-emit Verdict+Attested, one round, no re-read ([delivery gate counts ANY file edit — update memory/notes before the final OUTPUT critique](../learnings/1789554373150-delivery-gate-counts-any-file-edit-update-memory-n.md)). Two adjacent gotchas from the same tail: the chain-routing gate keys on the marker string, so `[Fix Report]`/`[Report]` HARD-REQUIRE `in_reply_to=<inbound msg id>` (a prior outbound id is rejected) while `[Fix Status]` is ungated, and a follow-up status on an already-delivered chain uses `[Fix Status]` with bare `to="parent"`; and a `cancelled` `falcor-build-approval-gate` flips the check-suite to `failure` and fires a false `github.ci_failed` even when all builds pass, which is cosmetic like `wait-for-human-priority`: if the only non-success/non-skipped check-run is a `cancelled` `*-approval-gate`, do nothing and do NOT manual-dispatch CI ([slang-fixer: [Fix Report] gate needs in_reply_to; [Fix Status] doesn't; Falcor approval-gate CI failures are cosmetic](../learnings/1789475921872-slang-fixer-fix-report-gate-needs-in-reply-to-fix-.md)).

**With the `critique-gate` overlay active, the `### Attested` hashes bind each approve to the exact files reviewed, so batch all source edits, THEN run the final attestation round once.** On slang#13124 a comment-only tweak to an already-attested source file invalidated the approve of *every* stage that attested it, forcing a `codex-reply` re-attest on all threads; any `Write`/`Edit`/heredoc after an OUTPUT_REVIEW approve, even to a memory note or `/tmp` file, re-arms the gate on the next delivery `send_message`. File writes first, OUTPUT_REVIEW last, then delivery with no edits between. OUTPUT_REVIEW is also strict on factual absolutes: write PR bodies conditionally ("normally differs") ([Codex critique attestation cascade — batch source edits before the final round](../learnings/1789563826008-codex-critique-attestation-cascade-batch-source-ed.md)).

An approve also fails to unlock delivery through formatting. `track-critique.sh` records an `### Attested` line only if it matches `-[ \t]*(?<h>[a-fA-F0-9]{64})[ \t]+(?<p>[^ \t]+)`, so when codex backticks the hash or path (`` - `3429…` `/path` ``, which it often does) or drops the leading `- `, nothing is recorded and the gate refuses the post of the very file codex approved (any public comment of 1000+ chars) with "is not among the files an OUTPUT_REVIEW attested". Ask for `- <64hex> <absolute path>` with no code formatting in the final OUTPUT_REVIEW prompt and check for backticks before posting; if present, send a `codex-reply` on the same OUTPUT_REVIEW thread asking for plain lines (the hook maps the reply's threadId back to its stage) and post the unchanged file with `--body-file <absolute path>`. This still held on 2026-10-10 and 2026-11-02, when codex also garbled a hash's length, so compare its lines with your own `sha256sum`, and on slang PR #13792 (2026-11-05), where `gh pr comment --body-file` was refused until a same-thread re-emit gave plain hashes with absolute paths; the approving round's prompt must also name the posted file under ARTIFACTS, and a verdict line such as "approve — X only" records as unparseable, so ask for the single word ([plain `- <sha> <path>` or the public-comment gate won't recognize them](../learnings/1793909331003-critique-attestation-lines-must-be-plain-sha-path-.md)). The hook denies the WHOLE Bash command, so a body written in the same command as the denied post is never created, and the public-comment gate counts heredoc bytes in that command toward its size threshold; write each body to a file in its own earlier step, then post it with `-F body=@<abs path>` ([codex Attested hashes in backticks are not recorded by the critique gate — pre-check, then re-emit plain lines via codex-reply](../learnings/1793610870468-codex-attested-hashes-in-backticks-are-not-recorde.md), [Attested lines must be `- <sha256> <path>` with no backticks](../learnings/1793866854544-critique-gate-attested-lines-must-be-sha256-path-w.md)). A second refusal wording comes from the same defect: an unparsed round (backticks, or a missing leading dash) still records the approve but leaves the PREVIOUS round's hashes in place, so a body edited after that round is refused with "reviewed artifacts changed since the OUTPUT_REVIEW approve" even though the current hashes match; `.critique_attested.OUTPUT_REVIEW` shows the older hashes, and on 2026-10-29 one nothing-changed round asking for plain lines replaced them ([Critique gate ignores codex Attested lines wrapped in backticks](../learnings/1793289432564-critique-gate-ignores-codex-attested-lines-wrapped.md), [Attested lines must be `- <sha256> <path>` with no backticks](../learnings/1793866854544-critique-gate-attested-lines-must-be-sha256-path-w.md)). The gate re-hashes every file any earlier approve attested, so editing an already-attested PR-body or explanation file bounces the `[Fix Report]` too (2026-10-28); write the revision to a NEW file (`body-r2.md`) and run OUTPUT_REVIEW on the `[Fix Report]` text listing the current files ([critique gate re-hashes earlier approves](../learnings/1793197057690-compare-compute-fails-on-any-stderr-warning-critiq.md)). Diagnose with `jq '.critique_attested.OUTPUT_REVIEW' /workspace/.claude/workflow-state.json`; if a `codex-reply` re-emit does not replace the set, run a fresh canonical round with a FORMAT NOTE ("each Attested line exactly `- <sha256> <absolute path>`, NO backticks"). The attested-hash check binds only public comments of 1,000+ characters, a PATCH of an existing comment included, so a short status comment posts without it (a size fact, not a licence to skip OUTPUT_REVIEW where content needs one) ([fixer delivery gates: field format, in_reply_to, quiz positions](../learnings/1793850163791-fixer-delivery-gates-review-request-field-format-i.md)). The defect recurred on 2026-10-14 ([Falcor CI job log is opaque; codex Attested must be unquoted for comment gate](../learnings/1792009185155-falcor-ci-job-log-is-opaque-codex-attested-must-be.md)), on 2026-10-27, when a round-2 `codex-reply` again backticked hashes for a slang-rhi#869 comment and trimming it under 1,000 characters was cheaper than a third round ([merging a PR whose code path an upstream PR edited](../learnings/1793106992385-merging-a-pr-whose-code-path-an-upstream-pr-edited.md)), and on slang#14317 (2026-11-04), where a `codex-reply` asking for plain lines with the verdict kept recorded and the delivery passed ([backticked attestation hashes are silently dropped](../learnings/1793830181320-critique-gate-backticked-attestation-hashes-are-si.md)). The 1000-char comment arm also text-matches: a long read-only `gh api graphql` containing `issues/<n>/comments` or `addComment`-like tokens trips it, so run such queries from a script written with the Write tool ([backticked Attested drops lines; graphql text trips the comment arm](../learnings/1791238172489-track-critique-sh-drops-attested-lines-when-codex-.md), [backticked Attested leaves stale hashes; fresh round with FORMAT NOTE](../learnings/1791320198757-critique-gate-backtick-wrapped-attested-lines-leav.md)).
