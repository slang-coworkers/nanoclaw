# Slang SPIR-V Backend: Emission, Capabilities, and Validation

The SPIR-V backend is Slang's primary Vulkan/Khronos target, implemented via a direct emitter (`slang-emit-spirv.cpp`) combined with a legalization pass (`slang-ir-spirv-legalize.cpp`) and the bundled `slang-glslang` module for `spirv-opt`. This page covers the core mechanisms for capability declaration, descriptor-heap emission, debug-info, atomics, and common pitfalls.

## Entry Points and Module-Level Emission

Slang's default SPIR-V behavior renames every entry point to `"main"` (a legacy from GLSL-via codegen). The flag `-fvk-use-entrypoint-name` (API: `VulkanUseEntryPointName`) preserves the source name. A non-obvious rule: Slang **auto-applies** `-fvk-use-entrypoint-name` when a module has more than one entry point (per PR #6260), so single-entry shaders still get renamed to `"main"` and fail `VkPipelineShaderStageCreateInfo` validation with VUID-VkPipelineShaderStageCreateInfo-pName-00707 unless the flag is passed uniformly ([Slang SPIR-V entry-point rename: auto-applies only with >1 entry point](../learnings/1779621920622-slang-spir-v-entry-point-rename-auto-applies-only-.md)).

The `[require(spirv_1_x)]` decoration that controls the emitted SPIR-V version must reach the **codegen IR module** (not only the layout/reflection module) via `addEntryPointRequireCapabilityDecorations()`. A secondary fix is also required: `determineSpirvVersion()` must match on internal `_spirv_1_x` atoms, not the public alias. Without both changes, `[require(spirv_1_5)]` leaves the SPIR-V at version 1.0 ([CORRECTION to #11631 version root cause: require atom stamped only on layout IR module, not the codegen module determineSpirvVersion runs on](../learnings/1781643037138-correction-to-11631-version-root-cause-require-ato.md)).

## Capability Declaration

**Adding a capability atom:** The single source of truth is `source/slang/slang-capabilities.capdef`. Two lines are needed per capability — an extension atom (`def SPV_EXT_foo : _spirv_1_0;`) and a capability atom (`def spvFooEXT : SPV_EXT_foo;`). Each requires `///` doc comment + `/// [EXT]` tag. The build runs `slang-capability-generator` to produce the C++ enum headers — never hand-edit those. Adding an atom also regenerates two checked-in docs: `docs/user-guide/a3-02-reference-capability-atoms.md` (alphabetical) and `docs/command-line-slangc-reference.md` (declaration order, byte-exact diff enforced by CI) ([Adding a SPIR-V capability atom to Slang (capdef recipe)](../learnings/1781120340432-adding-a-spir-v-capability-atom-to-slang-capdef-re.md), [Adding a SPIR-V capability atom — ADDENDUM (two generated docs + test -capability)](../learnings/1781122622446-adding-a-spir-v-capability-atom-addendum-two-gener.md)).

**Gating emit on a capability atom:** The correct pattern is `targetCaps.implies(CapabilityAtom::spvFooEXT)`. Do NOT gate on `isSPIRV(...)` (fires unconditionally for every SPIR-V target) and do NOT gate on extension-string atoms where a capability atom exists. The established precedent in `slang-emit-spirv.cpp:1692` gates on `CapabilityAtom::spvBindlessTextureNV`; ~8 sibling sites confirm this. An earlier triage learning incorrectly advised `isSPIRV()` — the correction is in [CORRECTION: SPIR-V capability emit-gating — use implies(CapabilityAtom::spv*), NOT isSPIRV()](../learnings/1781123971590-correction-spir-v-capability-emit-gating-use-impli.md). When adding a conditional capability for a stdlib `spirv_asm` intrinsic, see the option tree in [Conditionally requiring a SPIR-V capability for a stdlib spirv_asm intrinsic forces pass-level block manipulation — layer-choice tree](../learnings/1781974573249-conditionally-requiring-a-spir-v-capability-for-a-.md) (options: constexpr-only, post-hoc pass rewrite, new IR op, placeholder operand idiom).

**Triaging "add a capability" requests:** Check `external/spirv-headers/include/spirv/unified1/spirv.h` first — the `SpvCapability*` constant is usually already vendored. A bare capdef atom is inert until consumed by a `[require(...)]` intrinsic or C++ emit site ([Triaging an &quot;add a SPIR-V capability bit&quot; request — vendored-operand check + inert-atom scoping](../learnings/1781116222932-triaging-an-quot-add-a-spir-v-capability-bit-quot-.md)). New `Spv*` enum constants resolve from the SPIRV-Headers package, NOT from the stale `external/spirv/spirv.h` ([Slang SPIR-V emit: new Spv* enum constants resolve from the SPIRV-Headers package, not external/spirv/spirv.h](../learnings/1782322517394-slang-spir-v-emit-new-spv-enum-constants-resolve-f.md)).

**SPV_KHR_abort and multi-dependency chains:** `OpAbortKHR` is a block terminator (like OpKill) requiring both `SPV_KHR_abort` AND `SPV_KHR_constant_data` (for the `OpConstantDataKHR` message). New SPIR-V extension intrinsics must be modeled as terminators, not printf-parallel — after emitting the terminator, block emission must stop and unreachable code must be removed ([When planning a new SPIR-V opcode, check terminator-ness — not just value-producing-ness](../learnings/1781039584587-when-planning-a-new-spir-v-opcode-check-terminator.md), [SPV_KHR_abort transitively requires SPV_KHR_constant_data; message is OpConstantDataKHR not a runtime composite](../learnings/1782248897717-spv-khr-abort-transitively-requires-spv-khr-consta.md)).

**Conditionally requiring a capability for ray tracing:** To limit a shader to `SPV_KHR_ray_query` without pulling in `SPV_KHR_ray_tracing`, use `-capability spvRayQueryKHR` and verify no `TraceRay`/raygen path re-introduces the extension. The `RaytracingAccelerationStructure` type itself triggers a dual "any" requirement; post-PR #6615 dedup should collapse it to ray_query when only `RayQuery` usage exists ([Slang AS: forcing ray-query-only capability (avoid SPV_KHR_ray_tracing)](../learnings/1781905197543-slang-as-forcing-ray-query-only-capability-avoid-s.md)).

**`-capability` silently raises the SPIR-V version past an explicit `-profile` (#12097/#12099):** `slangc -profile spirv_1_4 -capability spvShaderInvocationReorderNV` silently emits a `; Version: 1.5` header (exit 0, no diagnostic). Root cause: `-capability` atoms are folded into target caps in `TargetRequest::getTargetCaps()` (`slang-target.cpp:214-232`) via `if (!targetCap.isIncompatibleWith(toAdd)) targetCap.join(toAdd)`, and `CapabilitySet::isIncompatibleWith` (`slang-capability.cpp:487-512`) treats two sets as compatible whenever they share ANY target abstract node — `spirv_1_4` and `spirv_1_5` are the SAME SPIR-V target, so the join proceeds and `determineSpirvVersion` takes the MAX (`requireSpirvVersion` = `Math::Max`). A version *raise* is thus always a *compatible* join, never flagged. The missing prerequisite for any conflict diagnostic: nothing records whether the profile's concrete version was USER-EXPLICIT vs defaulted (default is `spirv_1_5`), so a CLI-conflict check (fix layer A at the `getTargetCaps` join with a fire-once DiagnosticSink; cleaner layer B at parse-time in `slang-options.cpp`) must add that flag first. This is a distinct layer from the code-implied capability errors E41012/E41013 (`slang-check-shader.cpp`, gated by `-restrictive-capability-check`); a CLI conflict wants an unconditional error. Correct discriminator: key off "capability has NO valid realization at the explicit version (extension paths included)", NOT "default realization exceeds version" ([-capability silently raises SPIR-V version past explicit -profile (#12099)](../learnings/1784052596356-why-capability-silently-raises-spir-v-version-past.md)).

The specific over-require driving #12097 is that the SER extensions are pinned to `_spirv_1_5` in the capdef: `slang-capabilities.capdef:624` `def SPV_EXT_shader_invocation_reorder : _spirv_1_5 + SPV_KHR_ray_tracing;` (NV inherits at `:629`, motion aliases at `:862`/`:867`) — a deliberate simplification per the source comment, even though SER is usable at 1.4 given a physical-storage-buffer extension. **A capdef `_spirv_1_5`→`_spirv_1_4` floor edit ALONE does NOT make the 1.4 module valid:** the SER emit path (`emitOpTypeHitObject*`, `slang-emit-spirv.cpp:2745-2762`) declares only the reorder `OpExtension`/`OpCapability`; the only site that emits `OpExtension "SPV_KHR_physical_storage_buffer"` is `requirePhysicalStorageAddressing()` and it fires only under `PhysicalStorageBuffer64` addressing (buffer_reference usage), which a plain SER raygen shader never triggers. So the 1.4 path emits no PSB extension and spirv-val fails per SER's normative 1.4 dependency (1.4 + `SPV_KHR_ray_tracing` + one of {PSB extension, core 1.5}). The 1.4 path must declare the PSB *extension* without switching the memory model away from `Logical GLSL450`. Note `SPV_KHR_physical_storage_buffer` is a hardcoded emit string, not a capdef atom (only `SPV_EXT_physical_storage_buffer : _spirv_1_3` exists); capdef disjunction (`|`) could model the "1.4+PSB OR core-1.5" rule but still needs the emission change ([SPIR-V SER capability over-requires 1.5; capdef floor edit alone insufficient (#12097)](../learnings/1784052492569-spir-v-ser-capability-over-requires-1-5-capdef-flo.md)). #12097 and #12099 are a paired "allow the 1.4 downgrade" vs "reject the conflicting `-profile`/`-capability` combo" issue set from the same author (jkwak-work) for the identical repro — when triaging one of a paired allow/reject set, flag the tension to the maintainer rather than silently picking a side.

## Builtin Variables and Memory-Access Masks

`IRSPIRVAsmOperandBuiltinVar` is `hoistable=true` — cross-stage uses of the same builtin (e.g. compute + raygen sharing `SubgroupLocalInvocationId`) always collapse to a single inst via `_findOrEmitHoistableInst`. Adding a cache-key axis to `BuiltinSpvVarKey` for cross-stage differentiation is dead code under today's IR ([slang-spirv-asm-operand-builtinvar-is-hoistable-collapses-cross-stage](../learnings/1779617050641-slang-spirv-asm-operand-builtinvar-is-hoistable-co.md)).

The `getBuiltinGlobalVar` cache-hit trap: when adding a side-table like `m_volatileBuiltinGlobalVars` inside `getBuiltinGlobalVar`, populate it BEFORE the cache-hit early return. Otherwise the second call site that hits the cache misses the set entirely. Additionally, `spirv_asm` blocks bypass `emitLoad` — the `case SpvOpLoad:` branch in `emitSPIRVAsm` must also be extended ([slang-emit-spirv builtin-var cache and the volatile-set cache-hit trap](../learnings/1779612967874-slang-emit-spirv-builtin-var-cache-and-the-volatil.md)).

When injecting a memory-access mask (e.g. `Volatile`) into a `spirv_asm` OpLoad that already carries a user-supplied mask, emit ONE combined mask word, not two consecutive words. The scan for existing user masks must include both `kIROp_SPIRVAsmOperandLiteral` and `kIROp_SPIRVAsmOperandEnum` ([slang-emit-spirv-extra-memoryaccess-word-grammar-bug-pattern](../learnings/1779617068760-slang-emit-spirv-extra-memoryaccess-word-grammar-b.md)).

**Hoistable operand mutation rule:** Never mutate a `SPIRVAsmOperandEnum` or `SPIRVAsmOperandLiteral` in place — they are hoistable (value-numbered) and `setOperand` on them trips an assert at `slang-ir.cpp:179`. Build a fresh operand and repoint the non-hoistable consumer (`spvInst->setOperand(maskIndex+1, newOperand)`) ([Never mutate a hoistable SPIRVAsmOperand in place; repoint the consuming inst](../learnings/1781725591470-never-mutate-a-hoistable-spirvasmoperand-in-place-.md), [SPIR-V asm-operand legalization: hoistable operands + foldable≠constant pitfalls](../learnings/1781726667133-spir-v-asm-operand-legalization-hoistable-operands.md)).

## Descriptor Heap (spvDescriptorHeapEXT)

The `spvDescriptorHeapEXT` path uses `kIROp_SPIRVLoadDescriptorFromHeap` (not `IRCastDescriptorHandleToResource`). Four function-call specialization sites in `slang-ir-specialize-function-call.cpp` and `slang-ir-specialize-buffer-load-arg.cpp` originally accepted only the cast variant, causing a SIGSEGV (#11498) when the heap-EXT variant wasn't handled ([spvDescriptorHeapEXT path uses kIROp_SPIRVLoadDescriptorFromHeap, not IRCastDescriptorHandleToResource](../learnings/1780729707220-spvdescriptorheapext-path-uses-kirop-spirvloaddesc.md), [spvDescriptorHeapEXT path — fix function-call specialization allowlists, not the downstream pass](../learnings/1780733286644-spvdescriptorheapext-path-fix-function-call-specia.md)).

**Heap operand must not be parameterized:** The `heap` operand of `SPIRVLoadDescriptorFromHeap` is the module-scoped `kIROp_SPIRVResourceHeap` builtin global; at emit it materializes as `OpUntypedVariableKHR` in `UniformConstant`. Parameterizing it as a `uint` OpFunctionParameter makes the cloned callee's access-chain base a `uint` scalar — invalid SPIR-V. Correct shape: parameterize ONLY the index; put the heap in the specialization cache key but not `newArgs` ([spvDescriptorHeapEXT specialization fix: don't parameterize the heap global](../learnings/1780734760813-spvdescriptorheapext-specialization-fix-don-t-para.md), [SPIRVLoadDescriptorFromHeap heap operand is a pointer global at emit — never parameterize it in call-spec](../learnings/1780769340224-spirvloaddescriptorfromheap-heap-operand-is-a-poin.md)).

**ConstantBuffer via spvDescriptorHeapEXT crashes in emit (#11483):** A storage-class divergence (`getDescriptorHeapBufferStorageClass` maps ConstantBuffer to `Uniform` on pre-1.4, `StorageBuffer` on 1.4+) causes a crash in `emitDescriptorHeapLoad`. Unlike `StructuredBuffer`, the crash occurs even for scalar member access ([ConstantBuffer via spvDescriptorHeapEXT SIGSEGVs in SPIR-V emit (slang#11483)](../learnings/1780643259838-constantbuffer-via-spvdescriptorheapext-sigsegvs-i.md)). The related *miscompile* (nested-array members read back garbage, distinct from the crash) has the same root: the heap-CB fetch lowers to an `OpBufferPointerEXT` in the **`Uniform`** class when it must be **`StorageBuffer`** — the missing pointer-type `ArrayStride` is a correct downstream *symptom*, not the bug (Uniform uses logical addressing where stride lives on the array type). PR #11647's `processConstantBufferDescriptorHeapLoad` retypes the load to StorageBuffer; the self-failing regression guard is a static spirv-asm FileCheck asserting `OpTypePointer StorageBuffer` + `ArrayStride`, since a `StructuredBuffer.Handle` proxy is a false negative (it already lowers to StorageBuffer) and no runtime `COMPARE_COMPUTE` can heap-bind a `ConstantBuffer<T>.Handle` today ([Descriptor-heap ConstantBuffer miscompile = wrong storage class, not missing ArrayStride](../learnings/1783384030612-descriptor-heap-constantbuffer-miscompile-11483-wr.md)). This surface is a cluster of related-but-distinct defects (#11211 crash on param, #11647 wrong-data, #4472 still-open multidim-array assert); before asserting any crash/miscompile here repros, **rebuild slangc at true HEAD** — several fixes landed in 2026 and stale binaries/releases mislead, and a Discord/old-release report (#11980) on this surface should first get a ToT rebuild, not a fixer dispatch ([Descriptor-heap ConstantBuffer<T> SPIR-V crash cluster — 3 fixes landed, verify at ToT](../learnings/1783459628122-descriptor-heap-constantbuffer-t-spir-v-crash-clus.md)).

**AS descriptor stride:** When emitting `DescriptorHandle<RaytracingAccelerationStructure>`, drive the runtime-array element type from the LOAD type (`uint64`), not the resource type (`OpTypeAccelerationStructureKHR`). The AS size is opaque, so `OpConstantSizeOfEXT(OpTypeAccelerationStructureKHR)` gives a non-portable stride ([spvDescriptorHeapEXT stride is opaque for AS — load-type must drive runtime-array base type](../learnings/1779962007180-spvdescriptorheapext-stride-is-opaque-for-as-load-.md)).

**Atomic-dest validator false-negative (#11506):** `processImageSubscript` rewrites the atomic dest into `IRSPIRVLoadTexelPointerFromHeap` (AddressSpace::Image) AFTER atomic validation runs. `isValidAtomicDest` accepted `IRImageSubscript` but not the heap texel pointer — fix adds a one-liner. A separate spirv-val failure (#11130) for `format=Unknown` on bindless textures is a distinct independent bug ([slang spvDescriptorHeapEXT: atomic-dest validator rejects heap texel pointers (E41403)](../learnings/1780865902537-slang-spvdescriptorheapext-atomic-dest-validator-r.md), [Descriptor-heap texture atomics: E41403 validator gap (#11506) is separate from format-Unknown spirv-val (#11130)](../learnings/1780869756318-descriptor-heap-texture-atomics-e41403-validator-g.md)).

**Unified stride:** The descriptor-heap emits a DISTINCT `OpTypeRuntimeArray` per element type (cached on `(descriptorElementType, arrayStride)`). A symbolic max stride via `OpSpecConstantOp Select(UGreaterThan(...), ...)` over `OpConstantSizeOfEXT` values passes the bundled spirv-val ([spvDescriptorHeapEXT unified-stride: per-type arrays + symbolic-max construct (#11718)](../learnings/1782264945972-spvdescriptorheapext-unified-stride-per-type-array.md), [spirv-val accepts OpSpecConstantOp(max) over opaque OpConstantSizeOfEXT as an ArrayStrideIdEXT id](../learnings/1782271381546-spirv-val-accepts-opspecconstantop-max-over-opaque.md)).

## VariablePointers

`requireVariableBufferCapabilityIfNeeded` is called from value-materialization sites (var/phi/call/element-ptr/load), NOT from function-signature emission. A `Ptr<T, GroupShared>` that survives as a `[noinline]` function parameter emits a valid `OpTypeFunction %_ptr_Workgroup_T` but NO `OpCapability VariablePointers`. Fix: walk the function type in `emitFunc` and gate on `IRNoInlineDecoration` (not `hasUses()`) — inlined helpers retain uses but must not spuriously declare the cap, which triggers driver miscompile #9061 ([Slang SPIR-V variable-pointers cap is declared from value sites, not function signatures](../learnings/1780967438806-slang-spir-v-variable-pointers-cap-is-declared-fro.md), [Signature-derived SPIR-V VariablePointers must gate on [noinline], not hasUses() (driver bug #9061)](../learnings/1781023718622-signature-derived-spir-v-variablepointers-must-gat.md), [slang SPIR-V: isolating a signature-only VariablePointers cap repro (avoid value-site self-declare)](../learnings/1780970685981-slang-spir-v-isolating-a-signature-only-variablepo.md)).

## Atomics

The SPIR-V atomic emit has FOUR cross-layer gates keyed on address space. When adding an `AddressSpace` case, all four must be updated: (1) front-end l-value check E30047, (2) IR validator `isValidAtomicDest` E41403, (3) emitter `isAtomicableAddressSpace` (AtomicLoad/Store/Exchange only; fallback to non-atomic emitLoad/emitStore silently loses atomicity), (4) emitter `emitMemorySemanticMask` (missing case → `memoryClass=0` → VUID-10870). `AtomicAdd`/`Inc`/`Dec`/`CompareExchange` bypass gate 3 and always emit the atomic op ([SPIR-V atomic emit has TWO address-space gates — a per-address-space fix must touch both](../learnings/1782322436550-spir-v-atomic-emit-has-two-address-space-gates-a-p.md), [Slang SPIR-V atomic emission has 4 cross-layer gates keyed on address space — check all when reviewing atomic/VUID fixes](../learnings/1782346122322-slang-spir-v-atomic-emission-has-4-cross-layer-gat.md)).

**groupshared-by-reference regression:** Lowering a `groupshared T arr[N]` parameter by-reference (to fix D3D TGSM loss) creates a `Workgroup` pointer that cannot cross a SPIR-V function boundary without `VariablePointers`. Fix: extend `GLSLResourceReturnFunctionInliningPass::shouldInline` (Khronos-gated) to also inline callees with a `groupshared`-rate parameter, keyed on `as<IRGroupSharedRate>(param->getRate())` not the value type ([groupshared by-reference param regresses Khronos SPIR-V; fix is Khronos-gated inlining keyed on param RATE](../learnings/1782237919713-groupshared-by-reference-param-regresses-khronos-s.md)).

## spirv-opt / slang-glslang Integration

`slang-glslang` is Slang's SPIR-V backend library (bundles SPIRV-Tools including `spirv-opt`) — the name is misleading; it has nothing to do with GLSL. It is always a runtime-loaded MODULE, never static-linked. The correct fix for "missing slang-glslang in a static build" is a build-system change (provide the module), not making its load non-fatal ([slang-glslang/spirv-opt: gate the emit-path load to only-when-needed (masking vs. principled gating)](../learnings/1782152994624-slang-glslang-is-the-spir-v-backend-don-t-mask-its.md)).

`slangc -target spirv-asm` at default optimization (`OptimizationLevel::Default`) DOES run `spirv-opt` (specifically `CreatePrivateToLocalPass` et al.) — this is not the same as `-O0` ([slangc -target spirv-asm at default opt DOES run spirv-opt (private-to-local)](../learnings/1781714495665-slangc-target-spirv-asm-at-default-opt-does-run-sp.md)). The `-OX` levels are hand-unrolled pass *presets* (a `switch (optimizationLevel)` with ~40 `RegisterPass` calls in `slang-glslang.cpp:316`); to expose granular per-pass selection (#12204) the clean primitive is the bundled `spvtools::Optimizer::RegisterPassesFromFlags(flags)` (`external/spirv-tools/include/spirv-tools/optimizer.hpp:140`), which maps spirv-opt CLI-style flags to passes so no hand-maintained string→`Create*Pass` table is needed — the level crosses the slang↔slang-glslang C ABI as a versioned-request field, so a custom-pass string just adds a new `glslang_CompileRequest_1_3`. This safely exposes pass control without correctness risk (spirv-opt is size/perf-only), at the cost of tying the CLI surface to the bundled SPIRV-Tools version ([granular SpvOpt pass selection — RegisterPassesFromFlags is the clean primitive (#12204)](../learnings/1784829679560-granular-spvopt-pass-selection-registerpassesfromf.md)). The `private-to-local` pass demotes any `Private` variable used in exactly one function to `Function` storage, which breaks cross-call persistence for function-`static` locals. Fix: remove the two live registrations of `CreatePrivateToLocalPass` ([SPIR-V function-static state loss = SPIRV-Tools private-to-local (and how to CLI-repro)](../learnings/1781713084820-spir-v-function-static-state-loss-spirv-tools-priv.md)).

**spirv-opt load is fatal via real sink:** `createArtifactFromIR` unconditionally calls `getOrLoadDownstreamCompiler(SpirvOpt, getSink())`. If `slang-glslang` is absent, the sink is poisoned with E00100 before any output guard. Deliberately-optional callers pass `nullptr` sink ([slang downstream-compiler load: optional spirv-opt is fatal via real sink + half-wired GLSLANG gate](../learnings/1781799089141-slang-downstream-compiler-load-optional-spirv-opt-.md), [Slang downstream-compiler absence (spirv-opt/slang-glslang) IS unit-testable via setSharedLibraryLoader](../learnings/1781804734767-slang-downstream-compiler-absence-spirv-opt-slang-.md)). For opt-out via CMake escape-hatch, follow the `SLANG_ENABLE_SPIRV_OPT_MERGE_RETURN` pattern: `advanced_option`, compile definition wired through `CompilerFlags.cmake`, and `#if ... #endif` guards around ALL registrations including dead `#if 0` blocks ([slang-glslang: add an opt-out via dedicated CMake escape-hatch, not by deleting the pass](../learnings/1781975592365-slang-glslang-add-an-opt-out-via-dedicated-cmake-e.md)).

**fp8 scalar float constants abort in spirv-tools:** `GetWordsFromScalarFloatConstant` in `external/spirv-tools/source/opt/folding_rules.cpp` asserts `width == 16 || 32 || 64`; width-8 (fp8) is missing. The integer sibling handles width-8 correctly. Tracked as issue #11766 for an upstream fix; Slang-side workaround is expected-failure (#11744) ([fp8 scalar float constants abort in spirv-tools constant folding (width-8 gap)](../learnings/1782449605671-fp8-scalar-float-constants-abort-in-spirv-tools-co.md)).

## Debug Information

**-g0 does not zero all debug info:** `OpSource` is emitted unconditionally at `slang-emit-spirv.cpp:11838` without consulting the debug level. `OpName`/`OpMemberName` are emitted from `kIROp_NameHintDecoration` which also survives at g0. Neither is gated on `m_targetProgram->getOptionSet().getDebugInfoLevel()` ([slang -g0 doesn't zero SPIR-V debug info: OpSource/OpName bypass the IRDebug gating path](../learnings/1782145409789-slang-g0-doesn-t-zero-spir-v-debug-info-opsource-o.md)). Verified exhaustively for PR #11682/#12201, `-g0` (DebugInfoLevel::None) emits **exactly** three debug-adjacent instructions and nothing more: `OpSource`, `OpName`, and `OpMemberName` — while `OpLine`, the `OpString` from `DebugSource`, and `OpModuleProcessed` are all correctly absent (`OpLine` is gated to g1+, the IRDebug* insts only exist at g1+, `stripDebugInfo` removes only IRDebug* not name hints). This is SPIR-V-specific: DXIL/HLSL/Metal `-g0` genuinely emits nothing, so the help text "For SPIR-V, OpSource, OpName and OpMemberName are still emitted" is factually complete ([-g0/DebugInfoLevel::None emits exactly OpSource/OpName/OpMemberName in SPIR-V](../learnings/1784828289031-g0-debuginfolevel-none-emits-exactly-opsource-opna.md)).

**Synthesized `$init` constructors get full debug info** (issue #11550): synthesized ctors inherit the struct's source loc and their member-store stmts inherit field locs — both are lowered like user functions, giving them `DebugFunction`/`DebugScope` entries. Suppressing the function-level scope without also suppressing body `DebugLine`s leaves invalid NonSemantic debug SPIR-V. Gate on AST flavor (`SynthesizedDefault | SynthesizedMemberInit`) during lowering ([Slang: synthesized $init ctors get full source-level SPIR-V debug info (no synthesized-func filter)](../learnings/1781168370965-slang-synthesized-init-ctors-get-full-source-level.md)).

**User-defined `__init` lacks `this` in debug info** (issue #11565): a constructor's `this` is a synthesized local var (not an IRParam), so the debug-var pass doesn't pick it up. Fix: after emitting `thisVar` at `slang-lower-to-ir.cpp:13839`, add a "this" name hint + `IRDebugLocationDecoration` so the local-var loop emits it ([Slang: user-defined __init lacks `this` in SPIR-V debug info — root cause + fix site](../learnings/1781206942083-slang-user-defined-init-lacks-this-in-spir-v-debug.md)).

**Extension method debug names:** `ExtensionDecl` is anonymous (`getName()` returns null), so extension method name hints are emitted unqualified. Fix: redirect the `getNameForNameHint` recursion through the extended type's decl. Note: the name hint also feeds C-like emitter identifiers (HLSL/CUDA), not just SPIR-V debug names ([getNameForNameHint feeds C-like emitter identifiers (not just SPIR-V debug); ExtensionDecl is anonymous](../learnings/1781267563910-getnamefornamehint-feeds-c-like-emitter-identifier.md)).

## Varying-Parameter Location Assignment

`SV_Target<N>` is the ONLY varying semantic that both consumes a GLSL/SPIR-V `location` AND carries a numeric suffix that is an ABSOLUTE hardware slot which must equal that location. In `slang-parameter-binding.cpp` `processEntryPointVaryingParameter`, SV_Target takes `getSimpleVaryingParameterTypeLayout(...Output)` (:~2064) while all other `SV_`/`NV_` semantics take direction mask 0 → consume NO location (SV_Position/SV_Depth→`BuiltIn FragDepth`/SV_Coverage/SV_ClipDistance are builtins). The #11944 bug is that `systemValueSemanticIndex` is stored but never read into location allocation, so out-of-order `SV_TargetN` gets a declaration-order location ignoring N. User-defined semantics (TEXCOORD0/1, COLOR0/1) are the opposite: the suffix is a name disambiguator, not a slot — GLSL/SPIR-V assign their locations by DECLARATION ORDER and HLSL matches inter-stage by NAME, so the same varying struct used as VS-out and FS-in gets identical declaration-order locations on both sides. Genericizing suffix→location (as a PR reviewer proposed) would REGRESS user-defined varyings by desyncing inter-stage matching and inventing locations HLSL never assigns — the correct fix axis is "semantic encodes an absolute slot," i.e. SV_Target only. The `SV_TARGET<N>→LOCATION_<N>` by-index translation in `fixFieldSemanticsOfFlatStruct` (`slang-ir-legalize-varying-params.cpp:3730`) runs ONLY inside `LegalizeShaderEntryPointContext`, subclassed only by Metal + WGSL; GLSL/SPIR-V never use it and instead read the VarLayout resource `index` directly in emit (`slang-emit-spirv.cpp:3445-3465`) — so the suffix→location path is a WGSL/Metal-only concern ([slang SV_Target-N is the only varying semantic encoding an absolute GLSL/SPIR-V location](../learnings/1784321038825-slang-sv-target-n-is-the-only-varying-semantic-enc.md)).

## Miscellaneous SPIR-V Pitfalls

- **VulkanBindShift C++ API:** `HLSLToVulkanLayoutOptions::Kind` encoding: u=0, s=1, t=2, b=3. Pack: `intValue0 = (kind << 24) | (set & 0xFFFFFF)`, `intValue1 = shift` ([Slang VulkanBindShift C++ API kind encoding (u=0,s=1,t=2,b=3)](../learnings/1780993682325-slang-vulkanbindshift-c-api-kind-encoding-u-0-s-1-.md)).
- **SlangPy kernel abstraction:** Fully collapses to zero overhead in Slang SPIR-V at `-O3` — 0 `OpFunctionCall`, byte-identical to a hand-rolled kernel. Runtime index arithmetic (1 sdiv + 1 srem + strided loads) is design-inherent, not a codegen defect ([SlangPy generated-kernel abstraction fully folds in slang SPIR-V (-O3), but is deferred to nvrtc for CUDA target](../learnings/1781017004302-slangpy-generated-kernel-abstraction-fully-folds-i.md), [Measure SlangPy generated-kernel codegen quality GPU-free via slangc SPIR-V opcode census](../learnings/1781050949927-measure-slangpy-generated-kernel-codegen-quality-g.md)).
- **wgpu VUID errors come from Dawn/tint, not Slang:** VUID errors during `wgpu` variant tests are emitted by Dawn's internal tint regenerating SPIR-V from WGSL, not from Slang's emitter. Fingerprint: tint uses `uint` array-length constants; Slang uses `int` ([slang-test wgpu COMPARE_COMPUTE VUID errors come from Dawn's internal tint, not Slang's SPIR-V emitter](../learnings/1782499611532-slang-test-wgpu-compare-compute-vuid-errors-come-f.md)).
- **Conditional<T,b> ICE:** `Conditional<T,b>` with a non-literal `hasValue` param survives `lowerConditionalType` and reaches emit as `makeConditionalValue` → ICE. Root cause is an upstream producer (autodiff, dynamic dispatch, or higher-order params) leaking an unresolved generic value param ([Conditional&lt;T,b&gt; ICE: non-literal flag survives lowerConditionalType to spirv-emit](../learnings/1782485307814-conditional-lt-t-b-gt-ice-non-literal-flag-survive.md)).
- **Stale prebuilt slangc:** Check `slangc -v`'s `<sha>` against `git rev-parse HEAD` before trusting compiled output. Function-static SPIR-V storage bugs are masked by inlining and NOT reproducible via `slangc -target spirv-asm` at default opt ([Stale prebuilt slangc + inlining mask SPIR-V static-local bugs (verify-at-HEAD pitfalls)](../learnings/1781708255374-stale-prebuilt-slangc-inlining-mask-spir-v-static-.md)).
- **`OpCompositeConstruct` of logical-pointer array (#9062):** SPIR-V logical addressing forbids logical (StorageBuffer/Uniform/Workgroup) pointers as operands to `OpCompositeConstruct`. The resource-legalization passes that eliminate arrays-of-resources only inspect the array's *direct* element type (they `unwrapArray()` through nested arrays and check whether the unwrapped type is *directly* a resource) — they do **not** recurse into struct fields, so a `struct { RWStructuredBuffer buf; }` used as `MyPtr[2]` is invisible while a bare `RWStructuredBuffer[2]` is caught. Autodiff reliably materializes this shape (`Array<T,N> : IDifferentiablePtrType` → whole array wrapped as one `DifferentialPtrPair` → lowered to a struct), which is why the maintainer couldn't repro without autodiff; pass ordering is fine (resource legalization runs after autodiff) — the escape is *structural blindness*, not a timing gap ([OpCompositeConstruct of logical-pointer array escapes resource legalization (struct-field blindness)](../learnings/1783524098198-slang-9062-spir-v-opcompositeconstruct-of-logical-.md)).
- **`spirv_asm` named registers leak into `OpName` (#12002):** the emitter emits an `OpName` for *every* named `%id` register in a `spirv_asm` block, unconditionally (not gated on debug-info level). Texture-sample intrinsics in `hlsl.meta.slang` name their raw-sample register `%sampled`, so every texture sample emits `OpName ... "sampled"` regardless of caller variable names. For any "debug name on the wrong inst" claim, the decisive discriminator is a **rename drill**: rename the user's variable and recompile — if the disputed `OpName` follows the rename it's real propagation, if it stays it's an emitter-baked intrinsic name and the match was coincidence ([spirv_asm named registers leak into OpName; texture-sample intrinsic uses %sampled](../learnings/1783525064110-slang-12002-spirv-asm-named-registers-leak-into-op.md)).
- **Sampler-vs-texture `[noinline]` param asymmetry (#12004):** `isIllegalSPIRVParameterType` always specializes textures but only specializes samplers when they are *arrays* (a legacy compile-time-blowup guard, #3546), so a scalar `SamplerState` param stays by-value `OpTypeSampler` while the texture is passed by index and reloaded in the callee. Emission is symmetric — the by-value-vs-by-index location is decided entirely by the specialize step, not emit, so don't chase it in the emitter; fixes here MUST `spirv-val`, not just FileCheck ([sampler-vs-texture noinline SPIR-V param asymmetry — isIllegalSPIRVParameterType isArray gate](../learnings/1783527024741-slang-12004-sampler-vs-texture-noinline-spir-v-par.md)).
- **`double→bool` cast emits a 1-word `OpConstant` (#12019):** `emitFloatToIntCast`'s float→bool path calls `builder.getIntValue(fromType, 0)` with the *double* type, minting a `kIROp_IntLit` stamped with a float type; at emit `emitIntConstant` switches on the type, double hits `default:` → one 32-bit word, but a float64 `OpConstant` needs two → "says it has 4 words, found 5". Only double is structurally invalid (for float/half the 1-word path accidentally matches the IEEE bit pattern). Fix at the producing cast (`getFloatValue(fromType, 0.0)`, mirroring the correct bool→float sibling), not by special-casing `emitIntConstant` — an int-lit-with-float-type should never exist ([double→bool SPIR-V: getIntValue(floatType,0) mints int-lit with float type → 1-word OpConstant](../learnings/1783587817471-slang-12019-double-bool-spir-v-getintvalue-floatty.md)).
- **`spirv-opt --strip-debug` deletes `DebugBuildIdentifier` (#8681):** you cannot just replace the hand-rolled `stripDbgSpirvFromArtifact` with spirv-opt's strip passes — that function is the `-separate-debug-info` splitter and hand-rolls the strip precisely to keep the DBI ext-inst (the hash linking the stripped main module to its `.dbg.spv`). Both `CreateStripDebugInfoPass` and `CreateStripNonSemanticInfoPass` unconditionally kill the DBI; the correct shape is a hybrid where spirv-opt owns the bulk strip but a thin Slang shim exempts/re-injects the DBI + its OpString + the NonSemantic import — the DBI exemption is irreducible ([spirv-opt strip-debug deletes DebugBuildIdentifier — separate-debug-info needs a DBI shim](../learnings/1783556986544-slang-8681-spirv-opt-strip-debug-deletes-debugbuil.md)).
- **64-bit buffer indexing bifurcates (#11967):** direct concrete-buffer subscript (`RWStructuredBuffer<int>[uint64_t idx]`) preserves `UInt64` to `OpAccessChain` and works, but the interface-constrained `IArray<T>`/`IRWArray<T>.__subscript(int index)` path (core.meta.slang, hard `int`) silently truncates a `uint64_t` index to 32-bit (front-end `warning E30081`). The fix is to widen the IArray/IRWArray subscript *requirement* to a generic `TIndex`, mirroring the buffer/Ptr subscripts — with the caveat that widening an interface requirement can force `Array`/`vector`/`matrix` conformances to re-satisfy. A >2^32-element execution test is impractical (>8 GB buffer), so the E2E guard is necessarily a codegen FileCheck for `OpTypeInt 64` on `OpAccessChain` ([64-bit indexing works on direct subscript but IArray/IRWArray truncates to 32-bit](../learnings/1783415716330-slang-64-bit-buffer-indexing-works-on-direct-subsc.md)).
- **vec3 `OpConstantComposite` over-count is a downstream spirv-opt fold, NOT Slang emit (#12104):** `output[0] = (value<eps) ? 0 : (value/value)` for a runtime `float3` emits `OpConstantComposite %v3float %float_1 ×4` (4 constituents on a vec3 → spirv-val rejects). The maintainer's (jkwak) leads pointed at Slang's own `processConstructor`/`emitCompositeConstruct`/`MakeVector` — those are WRONG. Layer-isolation drill (reusable for any "invalid SPIR-V only at optimization" bug): (1) `-dump-ir` shows `div(%value,%value)` surviving intact through every pass → Slang IR isn't folding it; (2) `-O0` emits correct `OpFDiv` while default/`-O1/2/3` emits the malformed constant — the only pipeline delta is `slang-emit.cpp` routing SPIR-V through `PassThroughMode::SpirvOpt` (vendored `external/spirv-tools` spirv-opt @ v2026.3); (3) `-fp-mode precise` → clean `OpFDiv ; NoContraction`, `-fp-mode fast` → malformed, confirming an IEEE-unsafe `x/x→1` fold (0/0=NaN); (4) width sweep shows a HARDCODED 4 constituents (float2→4, float3→4, float4→4), NOT a vec4→vec3 result-type shrink — the vec2-with-4 case is the smoking gun. Slang's own peephole folds `v-v` correctly to a 3-constituent zero-vector and leaves `v*v` as `OpFMul`; only `v/v` (no `x/x→1` rule in slang-ir-peephole/sccp) reaches the vulnerable downstream fold. Fix options: (A, true root) fix `external/spirv-tools/source/opt/folding_rules.cpp` to use the result type's component count (upstream + submodule bump); (B, in-tree actionable now) add a fast-math-gated `x/x→1` Slang peephole fold producing a correctly-sized ones vector so spirv-opt never sees the vulnerable `OpFDiv %a %a`. An emit-time constituent-count assert in `emitOpConstantComposite` (which has no `constituent-count==element-count` check today, `slang-emit-spirv-ops.h:1417-1425`) is a useful general net that converts silent-invalid-output into a loud failure, but does NOT catch this bug — the malformed constant is minted post-emit in spirv-opt ([#12104 vec3 OpConstantComposite 4-constituent bug is in downstream spirv-opt, not Slang (x/x fold)](../learnings/1784072018251-slang-12104-vec3-opconstantcomposite-4-constituent.md)). An earlier repro-blocked triage of the same issue (jkwak's `float3(float2(1,1),1)` minimal case validates fine; ~11 minimal shapes on near-HEAD all emit a correct 3-constituent composite) correctly ruled out the sub-vector UNDER-count path (`processConstructor`'s flatten at `slang-ir-spirv-legalize.cpp:1795-1810` already handles that) and flagged a post-legalize fold (`simplifyIRForSpirvLegalization`) as the suspect — since superseded by the spirv-opt root cause above, but the standing `emitOpConstantComposite` count-assert recommendation still holds ([vec3 OpConstantComposite over-count — repro-blocked, post-legalize fold suspect (#12104)](../learnings/1784069141044-slang-spir-v-vec3-opconstantcomposite-over-count-r.md)).

## slang#12051 DescriptorHandle NonUniform marker (an evolving investigation)

The #12051 perf work (coalesce per-use SPIR-V descriptor loads) turned on whether the coalescing pass needs a divergence guard, and the mechanism was corrected several times before landing. Two distinct clarifications preceded it. First, the per-use descriptor reload it targets is an **EMIT-TIME artifact, not a `shouldDuplicateInstAtUseSite` force-dup** as originally attributed: on the default SPIR-V path the `CastDescriptorHandleToResource` has already lowered to a single `getElement(__slang_resource_heap, index)` in the generic IR, and the triplication is introduced *during SPIR-V emission* (`legalizeIRForSPIRV` + the emit walk, `emitSPIRVFromIR` at `slang-emit-spirv.cpp:11913`) which runs AFTER the final `-dump-ir` snapshot — so the emit realizes one shared `OpAccessChain` (index math emitted once) plus an `OpLoad` re-emitted per use (measured 2 access-chains, 6 loads for 3 samples); `pinDescriptor()`/`OpCopyObject` collapses it to one `OpLoad`, proving the reload is emit strategy, not a validity requirement. The lever is thus in the emit/legalize path (materialize one `OpLoad` when the descriptor-load def dominates its uses), not the generic duplication helper ([CORRECTION #12051: descriptor reload is an EMIT-time OpLoad-per-use, verify emit not just IR](../learnings/1784075115135-correction-slang-12051-spir-v-descriptor-reload-is.md)).

The bigger correction chain concerns the **NonUniform divergence guard** the plan mandated ("dominance + INVARIANCE — don't coalesce divergent/`NonUniformResourceIndex` loads"). That guard turned out to be UNIMPLEMENTABLE and UNNECESSARY: at the coalescing site (`insertLoadAtLatestLocation`, `slang-ir-spirv-legalize.cpp`) uniform and divergent IR are byte-identical because the heap `getElement`'s index carries no `NonUniformResourceIndex` wrapper and no `IRSPIRVNonUniformResourceDecoration` — the `isNonUniform` signal the plan borrowed lives on a DIFFERENT path (the raw resource-array-param path at `:690`), so the guard would be dead code reading an absent signal. Coalescing divergent-hoisted loads is actually CORRECT, not a tolerated bug: per-LANE divergence (SIMD lanes read different descriptors — one load per lane is fine) is not per-ITERATION/temporal variance, a hoisted loop-invariant conversion is one `getElement` per lane correctly reused across N samples, and the already-shipping `spvDescriptorHeapEXT` path does exactly this (divergent-hoisted → 2 loads, 0 NonUniform decoration, valid spirv-val). The missing NonUniform *hint* is a pre-existing, documented-accepted gap (`tests/language-feature/descriptor-handle/desc-heap-nonuniform.slang:8-12`), so the fix is decoration-neutral; NonUniform-preservation on the DescriptorHandle path is a separate maintainer-owned follow-up (issue #12110, PR #12111) ([#12051 option-a: the invariance guard was over-specified](../learnings/1784081353064-slang-12051-option-a-the-invariance-guard-was-over.md), [#12051 DescriptorHandle divergent NonUniform marker stripped before SPIR-V legalize](../learnings/1784081063099-slang-12051-descriptorhandle-divergent-nonuniform-.md)).

A related pass-ordering nuance underpins the coalescing argument itself. When arguing why the existing redundancy/CSE pass can't already dedup the SPIR-V-legalization-inserted loads, get the pass ORDER exactly right — a common overclaim. Verified at HEAD (`slang-ir-spirv-legalize.cpp`): `legalizeIRForSPIRV` (:3380) calls `legalizeSPIRV` (:3141) FIRST — where `insertLoadAtLatestLocation` creates the per-use `OpLoad`s — and THEN `simplifyIRForSpirvLegalization` (:3388), whose fixpoint loop calls `removeRedundancyInFunc` (:3183). So `removeRedundancyInFunc` DOES run *after* the loads exist; the reason it still doesn't hoist descriptor-heap loads is NOT ordering but `isMovableInst`'s `kIROp_Load` case (`slang-ir.cpp:10042`), which returns movable only for `ConstantBufferType`/`ParameterBlockType` pointer types and rejects a descriptor-heap-element load. (The generic pre-SPIR-V GVN passes DO run before legalization and genuinely can't see the loads — but the correct answer to "why doesn't the *existing* redundancy pass hoist them" is the `isMovableInst` rejection in the post-legalization simplify loop.) Two related traps: `CastDescriptorHandleToResource` is force-duplicated by `shouldDuplicateInstAtUseSite` and is the lowering only for `spvBindlessTextureNV`, NOT the default `spirv` path (`__getDynamicResourceHeap[index]`) nor `spvDescriptorHeapEXT` (`__spirvLoadDescriptorFromHeap`); and `CastDynamicResource` IS movable in `isMovableInst` while `CastDescriptorHandleToResource` is NOT — don't lump them ([slang#12111 SPIR-V legalize pass ordering: removeRedundancyInFunc runs AFTER legalizeSPIRV inserts loads](../learnings/1784269362740-slang-12111-spir-v-legalize-pass-ordering-removere.md)).

**Contradictions / supersessions (within this narrative):** the earliest reading — "the `NonUniformResourceIndex` inst is essentially *never present* on this path; 0 insts / 0 decorations anywhere in `-dump-ir`; specialized away in specialize-function-call" — is WRONG as stated, though its *conclusion* (guard-drop is safe) held. The precise mechanism: the marker DOES exist early, on the pre-handle uint value (`%34 = nonUniformResourceIndex(%33)`), and is then **dropped by the `DescriptorHandle` construction round-trip** — `CastUInt2ToDescriptorHandle` ↔ `CastDescriptorHandleToUInt2` re-extracts the index as a plain swizzle (`%38`) that feeds the heap `getElement` UNMARKED. So it's "present early, dropped by the Cast round-trip," not "never there." Two methodology traps produced the sloppy earlier evidence: (1) a whole-dump `grep -c` for `nonUniformResourceIndex` is inflated by the capability-atom NAME colliding with the inst mnemonic in every function's capabilitySet decoration (166 hits mostly noise) — check the SPECIFIC operand (the `getElement` index def chain), not a raw grep; (2) `-dump-ir` starts its first snapshot too late (`### AFTER validateAndRemoveAssumeAddress`) to see an inst created and dropped in early AST→IR lowering, so "0 occurrences in `-dump-ir`" proves absence only from the first dumped pass onward. Combined with the emit-time lesson above, `-dump-ir` is blind on BOTH ends — very-early insts dropped before the first snapshot AND very-late emit/legalize mutations after the last — so a dump grep is a middle-of-pipeline view only; disassemble the output for late/emit questions and dump a specific early pass (or trace ops) for early-lowering questions ([#12051 CORRECTION — inst survives, round-trip drops it from heap index](../learnings/1784083614756-slang-12051-correction-descriptorhandle-nonuniform.md), [REFINEMENT #12051 — marker exists early then dropped by Cast round-trip; -dump-ir starts too late](../learnings/1784083913871-refinement-slang-12051-the-nonuniform-marker-exist.md)).

## NonUniformResourceIndex Float-Pass DescriptorHandle Round-Trip: SPIR-V-Gated by Design (2026-07-21 fold)

The `floatNonUniformResourceIndex` pass (`slang-ir-float-non-uniform-resource-index.cpp`) has a deliberate target asymmetry that recurs as a reviewer flag. A new bool CLI flag appends cleanly (`CompilerOptionName::DebugInfoIncludeSource` before `CountOf`, `pr: non-breaking`) mirroring `-separate-debug-info` ([SPIR-V source-text embedding is gated at TWO layers (producer + consumer), both keyed on -g level](../learnings/1784666850986-slang-spir-v-source-text-embedding-is-gated-at-two.md)). First, there are **TWO `IRDebugSource` producers** — the per-source-file loop in `slang-lower-to-ir.cpp` (~15428) AND a per-location `getOrEmitDebugSource` (~9717) that the entry point's location decoration points at; widening content-embedding in one but not the other lets `emitCoreOpSource` emit `OpSource` with a `File` operand but EMPTY `Source` whenever the entry point's resolved `SourceFile*` differs from the file-loop's cached one, so thread `shouldIncludeSourceInDebugInfo()` into BOTH producers. Second, the **producer ternary is target-agnostic** — an unguarded SPIR-V-documented flag silently reaches the LLVM backend (`-target llvm -g1 -debug-info-include-source` embeds source where `-g1` alone would not), diverging from the `-separate-debug-info` precedent that warns per non-SPIRV target; gate the producer override on a SPIRV target and/or add a symmetric `...IgnoredForTarget` warning ([two IRDebugSource producers; the producer ternary is target-agnostic (#12181/#12202)](../learnings/1784822669473-slang-debug-info-include-source-12181-12202-second.md)). A related output-quality nit in the same rework: the `emitSource` path emits the long-standing bare fileless `OpSource <lang> <ver>` unconditionally *and then* the new per-file file-carrying `OpSource` records — but SPIRV-Tools' source extractor treats every `OpSource` as a file, so the bare one materializes a spurious empty `unnamed-0.hlsl`. spirv-val passes (multiple `OpSource` is legal), so this is invisible without a consumer-side check; restore mutual exclusivity by emitting the bare `OpSource` only in the no-embed/early-return branch. (The -g2/-g3 path is unaffected — its per-file records are NonSemantic `DebugSource`, not `OpSource`.) ([bare fileless OpSource coexisting with file-carrying OpSource → spurious 'unnamed' source (#12202)](../learnings/1784851566899-slang-spir-v-emitting-a-bare-fileless-opsource-alo.md)).

**`-O0` runs ZERO spirv-opt passes and is a faithful "no spirv-opt" proxy; spirv-opt is size/perf-only, not correctness.** The emit-path gate `needsOptimization = getOptimizationLevel() != None` maps `None` → downstream `None`, making `glslang_optimizeSPIRV` early-return; Slang self-legalizes via the always-on `legalizeIRForSPIRV`, independent of `-O`. For any spirv-opt-benefit study, state the caveats in the verdict: binary SIZE ≠ GPU runtime (the driver re-optimizes), the corpus must include LARGE real shaders (the 50-70% size win doesn't show on tests/-only corpora), and there is no existing size/perf regression harness (fresh tooling needed) ([-O0 is a faithful "no spirv-opt" proxy; spirv-opt is size/perf-only, not correctness](../learnings/1784653425624-o0-is-a-faithful-no-spirv-opt-proxy-spirv-opt-is-s.md)).

## DescriptorHandle Representation, [require]-Bindless Selection, and Precise/RayQuery Lowering (2026-07-23 fold)

A cluster of SPIR-V work on the `spvBindlessTextureNV` path this day pinned several load-bearing mechanisms. `DescriptorHandle<T>`'s SPIR-V representation is **capability-dependent**: `uint2` on the plain `spirv`/`glsl` path but a scalar `uint64` (`%ulong`) under `spvBindlessTextureNV`/`cuda`, so the AS cast in the bindless arm must be `RaytracingAccelerationStructure((uint64_t)handle)`, not the sibling `__asuint64((uint2)handle)` form which fails `spirv-val` on a scalar ([DescriptorHandle is uint64-native under spvBindlessTextureNV — and test a reviewer proposed-alt before agreeing](../learnings/1784762549887-descriptorhandle-is-uint64-native-under-spvbindles.md)). #12186's follow-up (make that width *kind-dependent* — uint64 only for texture/sampler kinds, uint2 for buffers/AS) generalizes to any "make a backend representation depend on a new discriminator" task: a capability-wide width decision is duplicated across MANY consumers (8 sites here — type emit, default-construct legalization, both byte-address cast selectors, IR layout, the sizeof/alignof peephole constant-fold that is easy to miss, plus AST layout + reflection), so grep every `implies(CapabilityAtom::X)`/`getUInt64Type` and run a dedicated PLAN_REVIEW pass hunting missed width sites; make the *classification* one IR predicate + a mirrored AST predicate rather than routing every site through one function. The highest-risk piece is the constant-emit path: `uint2`↔`uint64` casts emitted as identity aliases break under kind-dependent width — in a block emit a real `OpBitcast`, but at **module/global scope a constant `OpBitcast` is INVALID SPIR-V** ("Bitcast must appear in a block"), so you must materialize a correctly-typed constant by reading the operand's constant bits. Comparison/ordering ops must compare in the native representation (`lessThan` on uint2 ≠ packed-uint64 order) ([kind-dependent SPIR-V representation change: audit ALL width consumers + the constant-emit path (#12186)](../learnings/1784859574140-kind-dependent-spir-v-representation-change-audit-.md)). The deeper design lesson: the bindless-vs-descriptor-heap **accessor is selected at `specializeTargetSwitch`** reading *global* `getTargetCaps()` at module-link scope — the `implies(spvBindlessTextureNV)` gates in spirv-legalize/emit-spirv are downstream *consumers*, so touching them cannot honor a per-entry-point `[require]` ([bindless path is selected at specializeTargetSwitch, not the spirv-legalize gates](../learnings/1784780629812-slang-bindless-descriptor-heap-path-is-selected-at.md)), and entry-point `[require]` is lowered to an `IRRequireCapabilityAtomDecoration` never unioned into `getTargetCaps()` — honoring it needs per-entry-point reachability specialization, not a version-scan-style emit fix (which would yield incoherent `uint64`-typed/`uint2`-accessed SPIR-V) ([entry-point [require] never reaches specializeTargetSwitch — bindless half of #11631](../learnings/1784782055293-slang-12196-entry-point-require-never-reaches-spec.md)).

On diagnostics-in-legalize: a validation pass that renders a resource **type name** must run BEFORE `lowerBufferElementTypeToStorageType` erases it, but that early point still contains dead-after-`discard` code (a `[ForceInline]` helper not yet inlined) — the two goals trade off and the principled fix is to capture the type-name string early and defer only the emit ([diagnostic pass placement tradeoff: type-name rendering vs dead-code false-positives](../learnings/1784747930488-diagnostic-pass-placement-tradeoff-type-name-rende.md), extended by the E55215 post-OpKill triage in [slang-12191 E55215 post-OpKill dead-code diagnostic — capture the name early, defer the emit](../learnings/1784762307830-slang-12191-e55215-post-opkill-dead-code-diagnosti.md)). Two more relaxation/lowering traps: PR #12195's `-fvk-use-direct-resource-params` draws its gate as "any texture NOT rejected by GLSL" rather than "read-only texture," silently admitting FEEDBACK/UNKNOWN-access and (via a `unwrapArray` first) texture-array params — when a PR *relaxes* a rejection predicate, enumerate the full range of the discriminator ([SPIR-V direct-resource-param gate: relaxing isIllegalSPIRVParameterType leaks feedback/unknown/array textures](../learnings/1784772370437-spir-v-direct-resource-param-gate-relaxing-isilleg.md)); and `precise` is silently ignored on direct SPIR-V in DEFAULT fp-mode because `isFloatingPointModePrecise` reads only the global `-fp-mode`, never `IRPreciseDecoration`, so a complete fix must backward-propagate precise-ness through the FP fan-in before reusing the `maybeEmitNoContraction` choke point ([precise qualifier ignored on direct SPIR-V in default fp-mode — NoContraction gate reads global mode only](../learnings/1784785437426-precise-qualifier-ignored-on-direct-spir-v-in-defa.md)).

Two non-copyable-opaque **value-copy** ICEs share a root cause and belong to the same family as `#7455`/`#8002`: a `__constref ParameterBlock<T>` (or any opaque/resource type) gets temp-copied in `addArg` because `tryGetAddress` returns Simple-not-Ptr for a global, and the copy survives `processGlobalParam` (which only runs on `IRGlobalParam`) to ICE at emit — the fix belongs in IR copy-elision, NOT AST lowering (prior art PR #8008 was rejected 3× for the AST route) ([slang#8002 __constref ParameterBlock/opaque ICE — copied address-only value escapes global-only legalization](../learnings/1784754145569-slang-8002-constref-parameterblock-opaque-ice-copi.md)); and a plain function returning `RayQuery<...>` by value miscompiles because the callee inits a *fresh local* then value-copies the opaque handle into the return-dest — a bare `b = a` local copy miscompiles identically, so it is a general non-copyable value-copy defect, proven by **disassembling the actual output** to refute a confident-but-wrong source-only hypothesis ([RayQuery return-by-value miscompile = opaque value-copy, not missing return-dest transform (verify via disasm)](../learnings/1784785541306-rayquery-return-by-value-miscompile-opaque-value-c.md)). Finally, a tooling note for these fixes: prefixing internal `spirv_asm %registers` in `.meta.slang` must be brace-tracked and block-scoped — the same `%foo` tokens live in `__intrinsic_asm` LLVM/Metal strings that must NOT change, and a second generator (`slang-core-module-textures.cpp`'s C++ StringBuilder `spirv_asm`) is easy to miss ([renaming spirv_asm %registers in .meta.slang: block-scoped only, and core-module-textures.cpp is a second generator](../learnings/1784760040459-renaming-spirv-asm-registers-in-meta-slang-block-s.md)).

## Descriptor-Heap ConstantBuffer, Constant-Fold Width, and DebugEntryPoint Strings (2026-07-24/25 fold)

The `#12186` option-A rework (kind-dependent `uint2`/`uint64` `DescriptorHandle` width) closed out two of pdeayton's concerns with lessons that generalize past this PR. First, the "does the width conversion assert?" concern split into a **pre-existing gap** vs a PR-introduced edge: a module-scope `static const` handle initialized from a float/`bit_cast` source aborts at `emitGlobalInst` ("Unhandled global inst"), but the *same* `castFloatToInt` abort reproduces identically on master with no capability and no handle — so the A/B against a no-cap/no-handle control on master is what proves it's a general global-emit gap, not the PR's fault; the genuinely-new edge is the width-mismatch path hitting `tryGetConstantDescriptorHandleBits`'s missing cast case → `SLANG_RELEASE_ASSERT`. The principled layer is **SCCP** (`isEvaluableOpCode`, `slang-ir-sccp.cpp`), which runs at global scope before emit and already folds BitCast/CastFloatToInt but not MakeVector nor the DescriptorHandle casts — teaching it those retires both the bespoke walker and the assert ([slang#12186 option-a: layout change RESTORES cap-consistency; module-scope handle const from float/bitcast hits pre-existing global-emit gap](../learnings/1784912194039-slang-12186-option-a-layout-change-restores-cap-co.md)). A crucial repro caveat for any module-scope `static const` bug: the naive "declare + read into unused local" repro compiles clean because **DCE drops the unused global before emit** — the constant must be *observably consumed* (stored into a `RWStructuredBuffer` from the entry point) or a green compile falsely reads as "bug unreal"; also, a work item referencing symbols added by an *unmerged draft PR* (`tryGetConstantDescriptorHandleBits`) is not actionable on master — grep master for the symbol before treating it as ready-for-fix ([Module-scope static-const repros need the constant CONSUMED or DCE masks the bug](../learnings/1784915301574-module-scope-static-const-repros-need-the-constant.md)). Second, the Q2 "uint2 scalar layout — latent bug?" call was initially (wrongly) cleared as self-consistent by embedding the handle in a struct and matching std430 offsets — but in std430 `uint2` and `uint64` both align to 8, so the offsets *coincidentally* match and mask the bug. The maintainer's explicit two-arg query `alignof(T, Std430DataLayout)` fails on the PR (handle reports 4, `uint2` reports 8): the AlignOf/SizeOf **peephole** (`slang-ir-peephole.cpp`) resolves `layoutRules` correctly then calls `getNaturalSizeAndAlignment` hardcoded to natural rules, dropping the requested rule (invisible for uint64 where natural==std430, wrong for uint2). Durable rule: test the explicit `sizeof`/`alignof(T, LayoutRule)` query directly — struct offsets can coincidentally match and hide a query bug — and run a reviewer's exact minimal `static_assert` before an elaborate test of your own ([slang#12186 Q2 UPDATE: explicit alignof(T, Std430DataLayout) query CAN diverge from emitted struct layout — struct-embedding tests MASK it](../learnings/1784915310738-slang-12186-q2-update-explicit-alignof-t-std430dat.md)).

A distinct descriptor-heap ABI bug (`#12226`): a struct-typed `ConstantBuffer<T>` fetched via `ResourceDescriptorHeap[]` under `spvDescriptorHeapEXT` emits an `OpTypeBufferEXT` **StorageBuffer** (16B on the reporter's driver) instead of **Uniform** (8B) → 8 bytes of garbage. The naive "flip ConstantBuffer→Uniform in the heap path" fix is WRONG and regresses `#11483`: `processConstantBufferDescriptorHeapLoad` *deliberately* retypes struct/array heap ConstantBuffer loads to StorageBuffer (PR #11647, szihs) because a Uniform-class `OpBufferPointerEXT` carries no pointer-type `ArrayStride` (logical addressing), so nested-array offsets went undefined. The real defect is **conflating the descriptor *kind* fetched from the heap (an ABI fact — Uniform vs Storage, also sets the heap index stride via `OpConstantSizeOfEXT`) with the buffer-pointer *addressing class* (needs StorageBuffer for pointer ArrayStride)** ([Descriptor-heap ConstantBuffer StorageBuffer flip (#11647) is deliberate — descriptor kind vs pointer addressing class conflated](../learnings/1784939222858-descriptor-heap-constantbuffer-storagebuffer-flip-.md)). The remaining open question — must the two storage classes match? — was resolved by fetching the published `SPV_EXT_descriptor_heap` spec verbatim: `OpTypeBufferEXT` and `OpBufferPointerEXT`-result each carry a *separate* storage-class operand and **there is no normative rule requiring them to match** (the only place they coincide is a worked example, not a VUID; the `NonWritable` allowance explicitly contemplates a non-StorageBuffer result). DeepWiki claimed they must match — confidently wrong on this exact subsystem again — so "Approach B" (Uniform descriptor + StorageBuffer data pointer) is spec-legal; the residual question is a *device-ABI* one to confirm empirically with `SLANG_RUN_SPIRV_VALIDATION=1`, not a spec matching rule ([SPV_EXT_descriptor_heap: OpTypeBufferEXT and OpBufferPointerEXT storage classes are INDEPENDENT (no matching rule); DeepWiki wrong](../learnings/1784939925118-spv-ext-descriptor-heap-optypebufferext-and-opbuff.md)). Container tip recurring across these: `slangc -target spirv-asm` fails on the missing `slang-glslang` dylib — use `-O0 -target spirv -skip-spirv-validation` then disassemble with the in-tree `build/external/spirv-tools/.../spirv-dis`.

The RayQuery-return-by-value miscompile fix (`#12200`, closes `#12197`, SS/P1: opaque handle returned by value disconnects `OpRayQueryInitializeKHR` from `OpRayQueryProceedKHR` → `VK_ERROR_DEVICE_LOST`) landed as a scoped **NRVO** in `slang-lower-to-ir.cpp` — aliasing the named-return local to the return-destination out-param so the opaque handle builds in place, gated strictly to RayQuery/HitObject via `isNonCopyableOpaqueType` so it cannot regress the real by-value copy on DXIL. The 3-reviewer verdict was APPROVE_WITH_NITS / 0 bugs; the correctness crux (source-verified for a P1, not just relayed) is that NRVO elides only a provably-no-op whole-handle Load/Store layered on the pre-existing `maybeAddReturnDestinationParam` transform, with `findCommonReturnedLocalVar` bailing conservatively on any unrecognized statement ([PR #12200 RayQuery-return NRVO review — APPROVE_WITH_NITS, 0 bugs](../learnings/1784882737937-pr-12200-rayquery-return-nrvo-review-approve-with-.md)). Finally, the SPIR-V `DebugEntryPoint` command-line-string (`#12220`) has two independent accuracy bugs: `getDebugInfoCommandLineArgumentForEntryPoint` ends with a *literal* `sb << " -g2"` that never reads the requested level (so `-g3` still emits `-g2` despite an unused `getDebugInfoLevel()` accessor), and `writeCommandLineArgs` is a `switch(option.key)` with **no `default` case** that silently drops any un-cased option (`-lang`/`-profile`/`-gdwarf`/`-line-directive-mode` vanish while `-O0`/`-matrix-layout` survive). The command-line string is stored verbatim in the binary — grep it via `strings x.spv | grep -- '-target spirv'` without a disassembler; note `writeCommandLineArgs` also feeds the CPU/LLVM emit path but NOT the module-cache `buildHash`, so serializer edits don't change cache digests ([SPIR-V DebugEntryPoint command-line string: two roots (hardcoded -g2 + no-default serializer switch)](../learnings/1784915879616-spir-v-debugentrypoint-command-line-string-two-roo.md)).

## Descriptor-Heap Acceleration-Structure Diagnosis + std140 Array-vs-Matrix Red Herrings (2026-07-26 fold)

Two recurring SPIR-V descriptor-heap support questions, both traced end-to-end from Discord diagnosis threads. First, **`DescriptorHandle<RaytracingAccelerationStructure>` + `spvDescriptorHeapEXT` crashes are a supported, regression-tested path** on builds ≥ v2026.11 (`tests/spirv/descriptor-heap-acceleration-structure*.slang` cover both RayQuery/compute and TraceRay/raygen) — so a crash there is almost always host-side, not a compiler bug. Two values people conflate: the **handle `uint2`** (`(slotIndex, 0)`, `.x` a raw heap index, `.y` only the sampler index of a combined texture-sampler) vs the **heap slot contents** (the 8-byte AS *device address* from `vkGetAccelerationStructureDeviceAddressKHR`, NOT the opaque `VkAccelerationStructureKHR`). Decisive diagnosis order: dump `-target spirv-asm` and grep `OpConvertUToAccelerationStructureKHR` (missing → old build reading the opaque handle → DEVICE_LOST; present → compiler fine), then VK GPU-assisted validation, then bisect slot-0-works-but-≥1-crashes → AS stride mismatch (`-spirv-resource-heap-stride`, #11231/#11494, a silent miscompile) ([Diagnosing DescriptorHandle<RaytracingAccelerationStructure> + spvDescriptorHeapEXT crashes](../learnings/1785051051163-diagnosing-descriptorhandle-lt-raytracingaccelerat.md)). The crucial correction to the "slot holds a uint64 device address" fact: that describes the **shader-side lowering only** — the `SPV_EXT_descriptor_heap` `ResourceHeapEXT` heap is **driver-managed** (slang-rhi backs it with `VK_DESCRIPTOR_TYPE_MUTABLE_EXT` in a `BindlessDescriptorSet`), so you populate the AS slot via the **descriptor-write API** (`vkUpdateDescriptorSets` + `VkWriteDescriptorSetAccelerationStructureKHR`), NOT a raw `memcpy` of the address. The raw-uint64 model is literally true only for a plain app buffer (`RaytracingAccelerationStructure(myBuffer[i])`), which is why "direct address works but the EXT heap doesn't." Diagnostic tell: direct-address + textures-in-heap work but AS-in-heap fails at **index 0 with the correct `.x`** ⇒ the host is memcpy'ing where a descriptor write is required; the escape hatch is a user-provided `getDescriptorFromHandle` override fetching from an app `StructuredBuffer<uint64_t>` of AS addresses ([spvDescriptorHeapEXT AS heap is driver-managed — descriptor write, NOT raw memcpy](../learnings/1785056296611-spvdescriptorheapext-as-heap-is-driver-managed-des.md)).

Second, the **"`float4[N]` in a cbuffer reads garbage but swapping to `float2x4` fixes it (esp. after a slangc upgrade + col→row-major switch)"** report has a std140 layout half and a descriptor-heap half. Layout fact: in std140, `float4[2]` (16B stride, 32B total) is **byte-identical** to a *row-major* `float2x4` (2 rows × 16B), while a *column-major* `float2x4` is 64B — and matrix-layout mode (`-matrix-layout-row-major/-column-major`) changes only matrices, never arrays (arrays always follow the fixed 16-byte std140 stride). So if the row-major matrix reads correct values from the same bytes the array reads garbage from, the shader-side layout is NOT the difference — the col→row switch just made the matrix match how the host fills the buffer while the array stayed put; suspect a host-side packing mismatch, verified via `spirv-dis | grep -E "Offset|ArrayStride|MatrixStride"` ([std140: row-major float2x4 and float4[2] are byte-identical — matrix mode doesn't touch arrays](../learnings/1785073305394-std140-row-major-float2x4-and-float4-2-are-byte-id.md)). BUT if the same report mentions **descriptor heap / bindless / `spvDescriptorHeapEXT`**, the col→row switch is a red herring and this is bug **#11483**: a `ConstantBuffer<T>` fetched through the heap lowers to an `OpBufferPointerEXT` in the **`Uniform`** storage class, and `getPointerArrayStrideValue` emits pointer-type `ArrayStride` only for `PhysicalStorageBuffer`/`StorageBuffer` (0 for Uniform) → nested-array offsets undefined → garbage, while a matrix dodges it via MatrixStride (won't scale past 4 rows). Fixed by **#11647** (retypes the heap CB load to StorageBuffer — tell users to update *forward*), with a follow-on regression **#12226** (descriptor *kind* fetched as storage-buffer instead of uniform-buffer, see the #12226 ABI note above). Scalable workaround: fetch via `StructuredBuffer<T>`/`DescriptorHandle<StructuredBuffer<T>>` (already StorageBuffer with correct strides) ([Discord: float4[N]-in-struct garbage + matrix works + descriptor heap = bug #11483](../learnings/1785073991889-discord-float4-n-in-struct-reads-garbage-matrix-wo.md)).
