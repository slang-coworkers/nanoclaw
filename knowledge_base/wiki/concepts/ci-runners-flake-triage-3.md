# CI Runners & Flake Triage — Part 3: Logs, Artifacts & Instrument Limits

> **Part 3 of 4** of the CI Runners & Flake Triage synthesis (split 2026-08-08 to stay under the 40 KB read cap). Siblings: [part 1](ci-runners-flake-triage.md) · [part 2](ci-runners-flake-triage-2.md) · [part 4](ci-runners-flake-triage-4.md).

What the logs and artifacts can and cannot tell you: annotations that outlive expired logs, exit codes, the artifact the failing job actually consumes, upload corruption and stale precompiled headers, the base-rate sweep that stops a long-standing signature being filed as a fresh regression, and the greens that are vacuous.

## TL;DR

- **Establish the BASE RATE of the exact signature before filing N red nights as a regression window** — one "fresh 2-commit break" was 6 of 35 nights (~17%), four predating the window. "Both retries also failed" rules out only a transient blip.
- **Annotations outlive expired logs** — `/actions/jobs/<id>/logs` 410s after ~7 days, but `check-runs/<job_id>/annotations` still yields the `##[error]` lines including "Process completed with exit code N" (**139 = SIGSEGV**). The Actions job id doubles as the check-run id.
- **Green CI proves only what the matrix instantiated** — 13/13 green while the matrix pinned `python: ["3.10"]` and the fix sat behind `PY_VERSION_HEX >= 0x030b0000`; say "this green is vacuous" out loud.
- **Positive-control every zero** — a `total_count: 0` is only trustworthy after the identical query on a known-populated branch returns non-zero, proving the query shape works and the zero is not a malformed filter or a 403 surfacing as empty.
- **CI logs echo GPU-flake vocabulary as workflow SCRIPT text** (`::error::GPU health check failed… Re-run to get a new VM.`), so a keyword grep hits deterministic regressions that even instruct you to rerun — **selectivity (`327 passed | 1 failed`) and runner spread are the discriminators; keyword presence is not.**
- **Check the runner OS against the tool's capture path** — a peak-RSS capture keyed on GNU `/usr/bin/time -v` is a silent no-op on a Windows-only perf pool, yielding `rss_kb: None` rather than an error.
- **Inspect the artifact the failing job actually consumes** — slang test jobs download `slang-tests-<platform>` (~10 MB), not `slang-build-<platform>` (~90 MB). A zero-filled dylib passes the `download-artifact` SHA256 check and is **rerun-proof upload corruption**; the identical signature across attempts on fresh runners is the tell.
- **A flake is attributed to a fix by TREE ANCESTRY, not timestamps** — require `compare/<fix-sha>...<headSha>` `.merge_base_commit.sha == fix-sha`, or enumerate `gh run list --event merge_group` since the merge. A correctly *detected* fix-gap can still be wrongly *attributed* (Sig-B #11951 was AVX-512, then really a JIT-teardown UAF fixed by #12114) — label mechanism claims unproven.
- **Short jobs lie about being infra flakes** — a Windows GPU test job under 60 s ran no tests (disk/artifact preflight), and a ~1–2 minute `test-slang` failure can be real `nvcc` errors compiling the PR's own `.cu` files after the backend probes. Grep for `errors detected|error:|exit code|Segmentation`.
- **Wrong-polarity retraction: `SLANG_RHI_METAL_NO_RESIDENCY_SET` does not close the residency gap** — macOS CI already runs the fallback (no Apple6); the missing artifact is an Apple6 run.

## Short test-slang Failures Can Hide a Compile Error, Not a Flake

A `test-slang` GPU job that fails in ~1 minute with all "Checking supported backends" probes green then exit 1 is NOT automatically a pre-test infra flake. Windows GPU runners compile the PR's own CUDA `.cu` test files with `nvcc` as a setup step *after* the backend probes but *before* the main batch -- a compile error there produces a short job that mimics the "Common Test Setup" flake. On #11957 a classify-only subagent misread 17 real `nvcc` errors in the prelude as INTERMITTENT; consistent failure on BOTH windows-debug and windows-release confirms multi-platform legitimacy. For any short (<2min) test-slang failure, grep the specific job for `errors detected|error:|exit code|Segmentation` and always verify a subagent's INTERMITTENT verdict before firing a rerun ([short test-slang failures can hide an nvcc compile error, not an infra flake](../learnings/1783743117364-short-test-slang-failures-can-hide-an-nvcc-compile.md)).

## Sig-B test-server JSON-RPC Drop (#11951) — RESOLVED; TRUE root cause is a JIT-teardown UAF (#12114), not AVX-512 (2026-07-17 correction)

The long-open Sig-B fingerprint tracked as #11951 — a `JSON RPC failure: waitForResult()/hasMessage()` drop on `tests/compute/static-const-matrix-array.slang.3 syn (llvm)` (or the `static-const-vector-array` sibling), windows-*-gpu `test-slang`, ~99% of other tests passing — was NOT an IPC-layer bug. It manifests as the test-server *child* dying and the parent harness seeing only the generic `waitForResult()/hasMessage()` drop (the `.slang.3 syn (llvm)` victims are exactly the LLVM-synth/JIT codegen path). Diagnostics for applying the earlier AVX-512 workaround still hold as *mechanics*: PR #12056 "Apply AVX-512 JIT workaround to all CI tests" (merged 2026-07-10, `01adc68f`) is **workflow-only**, exporting `SLANG_DISABLE_AVX512=1` in `ci-slang-test.yml` (line ~99) + `ci-slang-coverage-test.yml`; `pull_request` runs use the workflow from the PR **head tree**, not master, so check presence with `gh api repos/shader-slang/slang/contents/.github/workflows/ci-slang-test.yml?ref=<head-sha> --jq .content | base64 -d | grep SLANG_DISABLE_AVX512` (export absent → branch predates the fix → advise rebase, not rerun) ([Sig-B test-server JSON-RPC drop = AVX-512 JIT SIGILL (#11951 resolved by #12056)](../learnings/1784089175111-sig-b-test-server-json-rpc-drop-avx-512-jit-sigill.md)).

**Correction / supersession (2026-07-17):** the AVX-512-SIGILL attribution above was **INCIDENTAL, not the fix.** The TRUE root cause of Sig-B is a **use-after-free in the LLVM JIT teardown**, fixed by PR #12114 (`bf7a78ab25f4`, merged 07-15 21:40Z); jkwak-work (who authored the fix and closed his own repro #12146) confirmed it, and a post-fix sweep found 8 failing merge-group runs containing #12114 with ZERO Sig-B recurrences → fully resolved. Two durable lessons carry more weight than the specific fix: (1) **a real fix-gap can be correctly *detected* yet wrongly *attributed*** — the earlier "flake still fires with `SLANG_DISABLE_AVX512` active" trifecta (export-active + genuine FAILED line + unrelated evicted PR) genuinely proved #12056 wasn't the fix, but "the workaround isn't the fix" does NOT prove the named mechanism (AVX-512 residual) is the cause; a nondeterministic teardown UAF manifests intermittently on ordinary runs and looks identical to a test-server drop, so keep mechanism claims labeled "unproven" and defer to the path owner's attribution. (2) **The clean discriminator for "is a flake fixed by PR X" is a tree-ancestry sweep, not a timestamp sweep** — a rerun logged *after* PR X merged re-runs the same OLD head, so for each candidate run get its `headSha` and check `gh api repos/OWNER/REPO/compare/<fix-sha>...<headSha> --jq .merge_base_commit.sha` (the fix is an ancestor iff `merge_base == fix-sha`); then grep `--log-failed` only on runs that provably CONTAIN the fix, and for "did it recur on a fixed master?" enumerate `gh run list --event merge_group` since the merge (those trees contain the fix by construction). When closing an escalation you opened with a wrong-but-honest hypothesis, post a NEW follow-up owning the arc rather than editing history ([Sig-B (11951) root cause was JIT-teardown UAF (#12114), not AVX-512 — a real fix-gap can still be mis-attributed](../learnings/1784320016828-sig-b-11951-root-cause-was-jit-teardown-uaf-12114-.md)).

## Check the Runner OS Against a Tool's Capture-Path Dependency — Linux-Only Measurement on a Windows Runner Is a Silent No-Op (2026-07-15 fold)

The compile-perf tracker's peak-RSS metric (#12112 bullet 1) is NOT greenfield: `tools/compile-perf/bench.py` (@c5d4d76e6) already detects GNU `/usr/bin/time -v` (`_detect_gnu_time`, :218), wraps every timed compile in it (`run_once`, :230-256), parses "Maximum resident set size" into `rss_kb` (:250-251), and stores it per-workload in results.json (:363-364,:391). But it is dead where it matters: (1) **portability gap** — capture fires only when GNU `/usr/bin/time` exists, and BOTH perf CI workflows run on the **Windows** pool (`nightly-mdl-perf-test.yml`, `compile-perf-release-sweep.yml` → `labels: [Windows, X64, nvrgfx-perf-kernelvm-bridge]`) where `/usr/bin/time` is absent → `rss_kb` is silently `None` on the exact machine feeding shader-slang.org/slang-compile-perf (macOS BSD `time` also lacks that parsed line; it only ever populates on Linux dev hosts); (2) **never surfaced** — nothing downstream reads `rss_kb` (`track.py:_point_metrics` :67-79, `trend.py`, `report.py`/`breakdown.py` all iterate only `r["timers"]`). Reusable triage moves: before classifying a "please add metric X" tooling request as new work, grep the tool for the metric field name (`grep -rn "rss\|getrusage\|resident"`) — the scaffold may already exist and the real work is portability + downstream surfacing, a very different fixer briefing; and always check the CI runner OS (`grep runs-on/labels` in the workflow) against what the tool's capture path depends on — a Linux-only measurement path on a Windows-only runner is a silent no-op. (Contrast: `native/api-driver.cpp` genuinely has zero memory measurement, so #9817's "session-create memory delta" IS new work — add a getrusage/GetProcessMemoryInfo sample after `createGlobalSession` returns; note `bench.py:parse_timers` :34 only accepts `…ms` tokens so a non-ms metric needs a new emit/parse channel, and the tracker is stdlib-only by invariant so the Windows RSS path must be `ctypes`, not `psutil`.) ([compile-perf tracker already captures rss_kb but it's dead on the Windows perf runner and never surfaced](../learnings/1784095582129-compile-perf-tracker-already-captures-rss-kb-but-i.md)).

## Zero-Filled dylib in Test Artifact = Upload-Corruption, Rerun-Proof (2026-07-24 fold)

Signature (slang PR #12216): a `test-slang`/`test-slang-rhi` job fails almost instantly (~4s, 3 launch attempts) at slang-test **startup** (not a test assertion) with `dyld: Library not loaded: @rpath/libslang-compiler.<ver>.dylib ... slice is not valid mach-o file`. Root cause: the packaged test artifact shipped a binary that is *bytewise all zeros* (`libslang-compiler.dylib` + `libslang.dylib` + two bins were zero-filled at the same size; valid siblings had proper Mach-O magic `cffaedfe`). It's NOT a runner download glitch — GitHub's `download-artifact` SHA256 digest PASSED, because the digest is computed over the already-corrupt zip, so the zero-fill happened at upload/packaging time on the build runner and the post-download check cannot catch it. Disposition = **DECLINE rerun (rerun-proof)**: `gh run rerun --failed` re-runs only the failed *test* jobs and re-downloads the SAME corrupt artifact (the green build job isn't re-run), so it can never clear — the path to green is an author rebase/re-push that regenerates the build artifact. Confirm fast: `gh api .../actions/artifacts/<id>/zip > a.zip`, unzip, check magic bytes (`open(p,'rb').read(4).hex()` == `00000000`), and cross-check the build job + other platforms are green to rule out a real code break. Systemic advice: maintainers should add a post-build magic-bytes/`file` sanity check *before* upload ([Zero-filled dylib in test artifact = upload-corruption, rerun-proof](../learnings/1784923930083-zero-filled-dylib-in-test-artifact-upload-corrupti.md)).

## Inspect the RIGHT Artifact — the macOS test job Downloads slang-tests-*, Not slang-build-* (2026-07-25 fold)

A crucial refinement of the zero-fill signature above: when confirming the corruption, verify the artifact the failing *test* job actually consumes. The Slang test jobs download the small (~10MB) `slang-tests-<platform>` artifact, NOT the large (~90MB) `slang-build-<platform>` artifact — they carry **separate copies** of `libslang-compiler.<ver>.dylib`, and the build one can be a valid mach-o (`cffaedfe`) while the tests one is zero-filled garbage. On PR #12216 (run 30100795306), the first pass inspected the 93MB `slang-build-*` dylib, found valid magic, and *wrongly fired a rerun* — only catching it against a prior-sweep tracker note and cancelling. The `slang-tests-macos-aarch64-clang-debug` dylib was 4161536 bytes of pure `0x00`, yet the download-artifact SHA256 check passed (upload-corrupt, same rerun-proof class). Discriminator for "uploaded-corrupt (rerun-proof)" vs "transient per-runner download glitch": the *identical* failing signature reproducing across 2+ consecutive attempts on *different fresh runners* is the tell — a real transient glitch varies. Same rerun-proof family as the #12022 expired-artifact lesson ([macOS test job downloads slang-tests-* artifact, not slang-build-*](../learnings/1784974553601-macos-test-job-downloads-slang-tests-artifact-not-.md)).

## `fiddle:13 'friend' outside class` on GCC = Stale PCH, Masquerading as Cache Flake (2026-07-26 fold)

A build failure with `slang-ir-insts.h.fiddle:13:22: error: 'friend' used outside of class` (+ `expected unqualified-id before 'private'/'public'` cascading into `invalid use of incomplete type 'IRBuilder'`) on a self-hosted **GCC** Linux runner — while windows-msvc + slang-native build the same tree clean — **looks like** a poisoned/dirty reused-runner workspace (a stale generated `.fiddle` header) inviting a "needs a manual `fiddle/` clean" conclusion. The real root cause (shader-slang/slang **#12227**, fixed by **#12233**) is a **stale GCC precompiled header** expanding FIDDLE-generated `private`/`friend` tokens at *namespace* scope. The distinguisher — and the reason this belongs with the rerun-proof family above: it is NOT runner hygiene, because a *code* PR that only touches PCH/header inclusion turns the leg green (which a one-time cache wipe would not), and `gh run rerun` reuses the same PCH → identical error, so the disposition is **log-as-left / no-rerun**; the difference from a plain flake is the *resolution framing* — "blocked on the code fix landing (clears queue-wide on rebase)," not "wipe the runner cache" ([fiddle:13 'friend' outside class on GCC runner = stale PCH, not poisoned cache](../learnings/1785060680645-fiddle-13-friend-outside-class-on-gcc-runner-stale.md)). See the build-infrastructure concept for the merged CMake fix (exclude `slang-compiler.h` from the GCC PCH, all-TU) and the surprising clean-build reproduction.

## Establish the BASE RATE Before Accepting a Regression Window (2026-08-04 fold)

Before accepting that N consecutive red nights = a new regression in a commit window, sweep the failure history far enough back to establish the **base rate of that exact signature**. Two red nights after a clean streak *look* like a fresh break while the same signature may have been recurring for weeks on unrelated commits. A `coverage-macos` `slang-test` segfault was relayed as a fresh 2-commit regression (failed 08-02 + 08-03, identical SHA, after a "6-night green streak", both retry attempts crashed); sweeping 35 nights found the identical signature on **6 of 35 nights (~17%), four of them on SHAs entirely predating the window**. Filing as framed would have sent someone bisecting an uninvolved 2-commit range (→ issue #12320).

**Technique: annotations outlive expired logs.** `GET /actions/jobs/<id>/logs` → HTTP 410 Gone and `/actions/jobs/<id>` returns an empty `steps: []` after retention, but annotations survive much longer — enough to fingerprint the *failure mode* across dozens of expired runs (limitation: no test output, so you cannot compare *which* test crashed):

```bash
gh api "repos/<o>/<r>/check-runs/<job_id>/annotations" \
  --jq '.[] | "\(.annotation_level)\t\(.message[0:80])"'
# yields the ##[error]/##[warning] lines incl. "Process completed with exit code N" (139 = SIGSEGV)
# the Actions job id doubles as the check-run id
```

Sweep pattern: `actions/workflows/<wf_id>/runs?per_page=60` filtered to `conclusion=="failure"`, then per run find the failing job id, pull its annotations, and record the exit code.

**Corollary: "both retries also failed" is NOT evidence of new causation** — it only rules out a *transient* blip. All four pre-window occurrences above also had both attempts crash, i.e. retry-resistance was a property of the long-standing crash. **Check whether your discriminator actually discriminates before leaning on it.** Also, when citing a line number from a crash publicly: **bash signal messages name the enclosing block, not the call** — `script.sh: line 306: 49522 Segmentation fault: 11 "$SLANG_TEST" …` pointed at the `fi` closing the block while the real invocation was line 94, a 212-line gap, because bash attributes an asynchronously-reaped child's signal to the enclosing compound statement. Resolve it against the **exact SHA the run used** (`git show <sha>:path | grep -n '<cmd text>'`) or you point a maintainer at unrelated code (here an `llvm-profdata merge`, implying a coverage-merge bug rather than a compiler crash) ([establish an intermittent CI failure's base rate before accepting a regression window](../learnings/1785746835066-establish-an-intermittent-ci-failure-s-base-rate-b.md)).

**Pin the event when harvesting "last success" for a release-CI range.** `release.yml` (id `106587263`) is fired by two events — `workflow_dispatch` (84 of 100 runs in the trailing window; 71 by `nv-slang-bot[bot]` at 00:00 UTC) and `push` on `v20*` tags (16) — so `runs?status=success&per_page=1` can pick a **tag** run as the range base. Add `&event=workflow_dispatch`. **But the intuitive mechanism story is wrong:** "a tag run's `head_sha` is off-branch, so `compare/<base>...<failure>` diverges" fails for 14 of 16 tag SHAs, which compare `ahead` of master (the tag was cut *from* master, so the range is well-formed); only **2/16 genuinely diverge** (release-branch backports and a throwaway `v2026.99.0.1-draft-signing-test`). Counterfactual: across all 8 failures in the window the unpinned base equalled the pinned base **8/8** — the defect has a **zero-incident history, a latent hazard rather than a past miscarriage**, and must not be described as having named innocent authors. The reason to fix it anyway is a 52-minute exposure window when the diverged signing-test tag was the latest success. Rules: pin the event; **echo the range endpoints in the failure report** (`run id`, `event`, `head_sha`, `head_branch` for *both* base and failure) so a reader can falsify the range instead of trusting it; check `compare/<base>...<head>` `.status` before it is load-bearing (want `ahead`/`identical` — `diverged` means say "no range available", because **reporting no range beats naming an innocent PR**); and **when you inherit a defect claim with a plausible mechanism attached, test the mechanism, not just the conclusion**, since a wrong mechanism sends someone hunting a nonexistent class of bug. Bonus baseline fact for liveness alarms: the dispatcher is **not** perfectly daily — `nv-slang-bot[bot]` missed 7 of 77 days (5 of them weekdays), so "a missing daily run" is not by itself evidence of an outage ([release-CI last-success harvest: pin event=workflow_dispatch, and know which hazard you're avoiding](../learnings/1785808857180-release-ci-last-success-harvest-pin-event-workflow.md)).

## Green Can Be Vacuous, and Keyword Hits Can Be Script Text (2026-08-04 fold)

Two ways a well-formed CI signal answers a narrower question than the one you asked.

**Green CI proves only what the matrix instantiated.** On slangpy#1068 (macOS cp311+ wheel link failure for `_PyFrame_GetLasti`) all 13 checks plus `license/cla` were green and a maintainer had approved — yet **nothing had compiled the affected code path**: `.github/workflows/ci.yml` pins the build matrix to `python: ["3.10"]` while `src/slangpy_ext/utils/profiler.cpp` gates the symbol behind `#if PY_VERSION_HEX >= 0x030b0000`, so every green build compiled the pre-3.11 `frame->f_lasti` arm. The authoritative check was the `wheels` workflow (matrix `cp39…cp314`), `workflow_dispatch:`-only, never run on the branch. Two cheap tells: **check-run names usually carry the matrix values** (`build (macos, aarch64, clang, Release, 3.10)`) — read them, not just the conclusion; and if the fix sits behind a version/platform `#if` or a generator expression like `$<$<PLATFORM_ID:Darwin>:…>`, find which matrix leg satisfies it. If none does, the green is **vacuous and should be said out loud on the PR**. **Positive-control the zero:** `actions/workflows/wheels.yml/runs?branch=<pr-branch>` returned `total_count: 0`, so the identical query was re-run with `branch=main` → `total_count: 7`, proving the query shape works and the zero is real rather than a malformed filter or a permissions 403 surfacing as an empty list. Mechanics for the follow-up comment: `gh api -X PATCH repos/<o>/<r>/issues/comments/<id> -F body=@file.md` edits in place (no second bot comment) — use `-F body=@file`, not `-f body="…"`, so multi-line markdown survives; a PATCH re-publishes the *whole* body, so re-verify the claims you're keeping, not just the ones you're adding, then assert `issues/<n>/comments | length` is unchanged to confirm you edited rather than stacked ([green CI can be vacuous — check the matrix pins the config your fix touches](../learnings/1785787665195-green-ci-can-be-vacuous-check-the-matrix-pins-the-.md)).

The same "enabled ≠ executed" trap has a hardware form worth pinning here, because two agents got its polarity backwards. In slang-rhi, `m_hasResidencySet = true` is assigned **only** inside `else if (m_device->supportsFamily(MTL::GPUFamilyApple6))` (`src/metal/metal-device.cpp` L121), and the GitHub-hosted `Apple Paravirtual device` on `macos-*-arm64` **lacks Apple6** — so **macOS CI runs the `!m_hasResidencySet` per-encoder `useResource` FALLBACK by default** (diagnostic at L145). The fallback is the **covered** path; the residency-**set** path is **uncovered** and needs Apple6 hardware CI does not have. ❌ **Do not cite `SLANG_RHI_METAL_NO_RESIDENCY_SET` as the artifact that closes a residency gap** — it forces the path CI already takes; the missing artifact is an Apple6 run. Corollaries: the buffer address map is live and `find()` does run (`resolvePointerFieldResidency`, `metal-shader-object.cpp:735`), evidenced by 7 passing `bind-pointers-*.metal` cases that *predate* the PRs judged against them; and **absence of the fallback log line proves nothing**, because `debugCallbackOutput` is assigned only inside `RETURN_NOT_AVAILABLE` (`tests/testing.cpp:884`) and can therefore appear only on a device-unavailable path ([Apple6 / m_hasResidencySet / NO_RESIDENCY_SET / useResource — macOS CI runs the Metal fallback](../learnings/1785779253773-apple6-m-hasresidencyset-no-residency-set-useresou.md)). That learning also carries a store-mechanics warning: `append_learning` **regenerates `INDEX.md` from filenames**, so a hand-authored canonical block added to it was silently destroyed within minutes — what survives regeneration is the **title** (→ filename slug → index line, truncated to ~50 chars), so front-load searchable tokens into the first ~50 characters and never rely on a hand-edit to a generated file. When the retrieval surface is machine-generated, the durable place for a fact is the field the generator reads, not the rendered output.

**CI logs echo GPU-flake strings as script text.** Slang GPU test job logs contain `echo "::error::GPU health check failed — this VM has a faulty GPU. Re-run to get a new VM."` and `echo "nvidia-smi FAILED (GPU may have crashed)"` **as workflow script text being printed**, not as fired errors. A keyword grep for the standard intermittent-flake vocabulary (`GPU health`, `faulty GPU`, `nvidia-smi FAILED`, `Re-run`) therefore hits jobs whose actual failure is a **deterministic code regression** — and the echoed text even *instructs* you to rerun. On PR #12182 the real failure was an OptiX device-symbol collision (`Symbol '_Z20RayPayload_x24init_0ii' was defined multiple times` → `OPTIX_ERROR_PIPELINE_LINK_ERROR`) reproducing on 8 distinct runners across Linux+Windows × debug+release × test-slang+test-slang-rhi; rerunning would have burned cap slots and masked a real break. Before accepting a GPU/infra keyword hit: (1) check whether the line sits inside an `echo`/`if` block of the workflow or is real tool output; (2) cross-check **selectivity** — infra failures take the whole job down while a code regression is surgical (`327 passed | 1 failed`, `41,119,710 / 41,119,711 assertions passed`; a device-lost/TDR never looks like that); (3) cross-check **runner spread** — the same failure on 8 runner IDs and 2 OSes is deterministic by definition, since infra flakes don't coordinate across a fleet. **Selectivity + runner spread are the reliable discriminators; keyword presence is not** ([CI logs echo GPU-flake strings as script text — grep alone misclassifies](../learnings/1785780840892-ci-logs-echo-gpu-flake-strings-as-script-text-grep.md)).

## Sweep-mechanism defects: memoization marks, audit denominators, ledger schema, and where a guard has to sit (2026-08-11 fold)

**A memoization mark's voiding condition must cover every field its verdict depends on — not just the obvious one.** The CI babysitter pins a skip mark to a failing PR's head sha: *skip re-derivation while `head_sha == pinned_sha`*. This is memoization, not quarantine — the red stands and CI keeps reporting it — and it is sound in principle because an author push produces fresh runs and voids the mark. Three distinct blind spots came out of asking **"what can this pin NOT see?"** rather than testing what it does see: (1) **log expiry** — a verdict of "unclassifiable, logs are 410" is a claim about *retention*, not about the sha, so it needs its own re-entry path or the skip becomes permanent blindness; (2) a mark whose pinned head moved is **unskippable** (already-known sibling); (3) the same inversion one field over, below. The generalizable form: enumerate the inputs the memoized verdict actually consumed, and give each one that can change independently of the key its own invalidation ([a memoization mark's voiding condition must cover every field its verdict depends on](../learnings/1786343345056-a-memoization-mark-s-voiding-condition-must-cover-.md)).

**An audit of "did you skip everything you should have?" must use the ELIGIBLE denominator, not the artifact count.** A ledger audit computed `expected = marks_on_disk` (26) and flagged a truthful `skipped=23` row. But the triage function only ever considers PRs whose current runs **terminally failed**, so a mark sitting on a non-terminal, cancelled-only, or green PR was never a skip candidate. The 3-mark "gap" was two PRs waiting on a deployment approval / a 76-day queued zombie run (`status != completed`, so `conclusion` is null) and one cancelled-only PR. Counting them as owed **manufactures a finding against a correct row** — the most expensive kind of instrument defect, because it produces work. ⇒ The denominator must be *"marks whose PR was eligible for the outcome"*, and any audit comparing a count against an artifact population owes an eligibility filter derived from the code being audited ([a skip-mark audit must not treat every mark as a skip candidate](../learnings/1786350251507-a-skip-mark-audit-must-not-treat-every-mark-as-a-s.md)).

**A schema violation and a substantive misclassification travel together — re-verify at source, don't restate.** Four ledger rows had bypassed the enforced writer (missing `labels[]`, or `verdict="legitimate"` with no evidence label). The tempting remedy is a correction row per line restating the original claim in valid form; **don't**. Re-verifying each claim at source, three held and the fourth did not — it asserted `verdict="legitimate"` while **its own reason text said "HTTP 410 Gone ⇒ cannot classify at source"**, and re-measuring both failing jobs (rc=1, 151-byte body = expired) forced a downgrade to `unclassifiable`. The direction matters: `legitimate` **closes** a question no evidence was ever available to answer, while `unclassifiable` keeps it open. A row that skipped the writer skipped the checks that would have caught the substance, so treat "bypassed the schema" as a **signal to re-derive the content**, never as a formatting task ([a schema violation and a substantive misclassification travel together](../learnings/1786343193221-a-schema-violation-and-a-substantive-misclassifica.md)).

**An acknowledged-exceptions list must be honoured by the gate that BLOCKS, not just the one that REPORTS.** `sweeplib.py` had a well-designed `ACKNOWLEDGED_ROWS` mechanism — hash-pinned exemptions for genuinely unrepairable findings (rows in an append-only ledger), with a deliberately closed `UNREPAIRABLE_REASONS = {"append-only-file"}` so "known, will fix" fails its own schema. The defect: `_ack_for()` had exactly **one** call site, inside `audit_summary_rows()`, and was never consulted by `audit_bypassed_rows()` — the function that actually blocks the sweep summary write. So a bypassing row in an append-only file could never stop gating: unrepairable by construction ⇒ permanently `ok=False`. That is the **always-firing-flag** defect, and a signal that cannot move carries no information while masking the *next* defect better than a `True` would. Two transferable points: wire the exemption into the **enforcing** path, not only the reporting one; and treat a permanently-failing gate as a defect in the gate, since a flag that never changes has stopped being a measurement ([an acknowledged-exceptions list must be honoured by the gate that BLOCKS](../learnings/1786343179420-an-acknowledged-exceptions-list-must-be-honoured-b.md)).

**A guard on the ledger write path leaves the report surface ungated — the advice reaches the human either way.** Enforcing a policy inside `append_row()` gates the *record* of a decision, not its *delivery*. The artifact a human acts on is the report — `send_message`, a PR comment, a Slack post — and no code sits between the reasoning and that surface. Measured: `_refuse_value_recommendation()` was implemented in `append_row()` to refuse any sweep summary recommending a discard (quarantine/disable/auto-close) after such a recommendation had been withdrawn on evidence; 8/8 controls passed, including the verbatim sentence previously shipped. **Four hours later the same quarantine recommendation went to the parent anyway** — because it went out as a message, never as a row. ⇒ When a policy is about *what a human may be told*, the guard belongs on the **delivery** path (or on both), and the control must exercise the surface the human reads ([a guard on the ledger write path leaves the report surface ungated](../learnings/1786328904632-a-guard-on-the-ledger-write-path-leaves-the-report.md)).

**A rule that only exists in prose cannot stop a mechanical counter that demands the opposite.** On supervisor tick 128 (290 in-flight chains) `scan.py` reported `must_nudge: 14`, and the skill carries a deliberately fails-loudly invariant — *"never report a tick as clean while `sent_nudges < must_nudge`"* — built so an LLM cannot narrate a nudge away. **Of those 14 rows, 0 were warranted.** The nudge ceiling (*"if a chain has been nudged twice with no response, escalate instead of nudging a third time"*) lived only in SKILL.md prose; `scan.py` never read `nudgedAt`, so `must_nudge` counted a chain's 8th nudge identically to its 1st — prior-nudge counts on the 14 rows were `4,5,5,5,4,6,6,4,3,0,7,4,5,2`, i.e. **13 of 14 already past the ceiling** — and the fails-loudly invariant then *demanded* the 8th. The shape to internalize: when an enforceable mechanism and an advisory rule disagree, **the mechanism wins and the prose is decorative**, so any limit you actually rely on has to be readable by the counter that enforces the opposite. A fails-loudly invariant amplifies this — it converts a stale prose rule into a mandate ([a rule that only exists in prose cannot stop a mechanical counter](../learnings/1786321998894-a-rule-that-only-exists-in-prose-cannot-stop-a-mec.md)).
