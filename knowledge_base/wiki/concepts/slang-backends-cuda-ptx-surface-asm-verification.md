# Slang CUDA/PTX: texture and surface intrinsics, verified with ptxas

Slang's CUDA prelude implements some surface operations as inline PTX asm, so a prelude PR's correctness depends on what `ptxas` accepts and on operand order. Neither shows up in Slang's own outputs: the `-target ptx` (NVRTC) path passes the asm text through without assembling it, and a `-target cuda` FileCheck sees only the unchanged call text. This page records the PTX facts and the GPU-free review method that settles such PRs, plus two rules that decide what a CUDA texture or surface lowering may assume: where a texture's format actually lives, and when an explicit sampler may be ignored. The broader CUDA emitter is on [[wiki/concepts/slang-backends-cuda-cpp.md]], and OptiX/NVRTC behavior is on [[wiki/concepts/slang-backends-f0909b0-cuda-optix.md]].

## TL;DR

- **Formatted `sust.p` with array geometry (`.a1d`/`.a2d`) is supported.** The PTX ISA grammar omits it, but the NVVM IR spec (§15.5.3) documents it and ptxas has a named feature gate: "sust.p with array geometry requires PTX ISA .version 4.1 or later". It assembles on every CUDA 11.7–13.4 × sm_50–sm_120 combination to SASS `SUST.P.{1D,2D}_ARRAY`.
- **Test PTX across toolkits and architectures without installing CUDA by downloading NVIDIA's PyPI wheels** (`nvidia-cuda-nvcc-cu11`/`-cu12`/13.x `nvidia-cuda-nvcc` for ptxas; 13.x `nvidia-cuda-cuobjdump` + `nvidia-cuda-nvdisasm` for sm_100/sm_120 SASS). Hand-written PTX needs each SM's minimum `.version`.
- **nvcc fills the ignored 4th coordinate of a layered 2D store with y, not 0**: `surf2DLayeredwrite(v, s, x, y, l)` emits `sust.b.a2d ... [s, {l, x, y, y}]`.
- **Review inline-asm prelude PRs by assembling the slangc PTX with `ptxas -arch=sm_XX`**, then map each data and coordinate register back to its `mov` immediate. That checks operand order for every specialization without a GPU.
- **Revert-drill trap:** a `-target cuda` FileCheck on a prelude-only fix passes on master too, because the call text is unchanged. Only the PTX lane discriminates.
- **A texture's format lives in two places.** `[format("...")]` becomes an `IRFormatDecoration`, not the `_Texture` `format` type argument, and only `resolveTextureFormat` (globals, GLSL/SPIR-V/WGSL) copies one into the other. CUDA `$C`/`$E`, GLSL layout and reflection read only the decoration, so a type-argument-only format gives a wrong CUDA surface stride. Test both spellings.
- **Never silently drop an explicit `SamplerState` on CUDA** (maintainer direction, #13559). `CUtexObject` carries its own sampler, so a separate-sampler overload stays E36107 on CUDA unless a maintainer agrees; lower only the combined `Sampler*` form.
- **The CUDA `Gather` arm is shared by the shadow and combined instantiations, and fits neither (#14071).** `Texture2D.GatherCmp` silently ignores the compare value, combined `Sampler2D.Gather` ICEs, and combined `Sampler2DShadow.GatherCmp` emits invalid CUDA. Prove a dropped argument by diffing two calls that differ only in it.
- **E36107 fires only from `[shader]`/`-entry` roots.** A `[CudaKernel]` or `[CudaDeviceExport]` caller of an intrinsic whose `[require]` excludes cuda compiles at exit 0 to an empty-bodied callee; probe both roots when reviewing a "make X a CUDA capability error" PR.
- **To test a patched CUDA prelude, rewrite the `#include` line of the slangc `.cu`.** It names the prelude by absolute path, so a search path alone does not swap it. In a dev build that path points into the source tree, so a prelude edit reaches slang-test's NVRTC lanes with no rebuild; mutation-drill prelude PRs that way, but not in a worktree whose suite is running.
- **`slangc -target cuda` exits 0 while emitting calls the prelude never defines.** Use `-target ptx` (local NVRTC) to see the failure. As of b00d9e482 `surf{1,2,3}Dwrite_convert` is specialized only for float/uint/int and their 2/4-vectors, and converting reads exist only for half formats under `SLANG_CUDA_ENABLE_HALF` (#13581 writes, #11088 reads).

## `sust.p` array geometry and layered coordinate order

The PTX ISA `sust` syntax table lists formatted `sust.p` only for the `.1d/.2d/.3d` geometries, which makes `sust.p.a1d`/`.a2d` look undocumented. ptxas disagrees: it carries a named feature, `Feature 'sust.p with array geometry' requires PTX ISA .version 4.1 or later`. Reproduce it by editing a slangc PTX file's header to `.version 4.0`: that version errors, while 5.0 through 8.5 pass. Treat the layered forms as supported: they are missing from the PTX ISA grammar, but the NVVM IR spec (§15.5.3) documents them. They assemble on ptxas 12.6 for sm_50 through sm_90, and a later sweep with hand-written PTX found that every combination of CUDA 11.7–13.4 and sm_50–sm_120 assembles and produces native `SUST.P.1D_ARRAY` / `SUST.P.2D_ARRAY`; the PTX version gate is the only restriction [test PTX across CUDA versions/SMs without a GPU via NVIDIA PyPI wheels](../learnings/1791993172494-test-ptx-across-cuda-versions-sms-without-a-gpu-vi.md).

For coordinate order, nvcc is the reference. `nvcc -arch=sm_86` on `surf2DLayeredwrite(v, s, x, y, l)` emits `sust.b.a2d ... [s, {l, x, y, y}]`: the layer comes first, and the ignored fourth coordinate repeats y rather than being 0. A prelude that mirrors nvcc's shape should match that layout ([ptxas gates sust.p array geometry on PTX ISA 4.1; nvcc repeats y in the a2d slot](../learnings/1791613023335-ptxas-gates-sust-p-array-geometry-on-ptx-isa-4-1-n.md)).

## Reviewing an inline-asm prelude PR without a GPU

`-target ptx` goes through NVRTC, which passes inline asm text through without assembling it, so a successful slangc PTX compile proves nothing about the asm. The method that works (PR #13563): compile the test with slangc to PTX, run `ptxas -arch=sm_XX` on that output for each architecture of interest, and then trace each data and coordinate register in the emitted `sust` back to the `mov` immediate that set it. That confirms both that the asm assembles and that operands land in the right slots for every specialization.

To widen the check beyond the locally installed toolkit, download the NVIDIA PyPI wheels instead of installing CUDA. For ptxas, `pip download --no-deps nvidia-cuda-nvcc-cu11==11.7.99` (or 11.8.89), `nvidia-cuda-nvcc-cu12==12.0.140`, `12.4.131` or `12.8.93`, and plain `nvidia-cuda-nvcc` for 13.x; unpack with `python3 -m zipfile -e <whl> .` and run `nvidia/cuda_nvcc/bin/ptxas` (or `nvidia/cu13/bin/ptxas`). Older cuobjdump cannot decode sm_100/sm_120 ("Cannot decode architecture 'SM120'"), so read that SASS with the 13.x `nvidia-cuda-cuobjdump` and `nvidia-cuda-nvdisasm` wheels, with nvdisasm's directory on `PATH`. Write the PTX by hand with each SM's minimum `.version` (sm_86 7.1, sm_89/90 7.8, sm_100 8.6, sm_120 8.7); otherwise every failure is just a version error [same](../learnings/1791993172494-test-ptx-across-cuda-versions-sms-without-a-gpu-vi.md).

When doing the revert drill for such a fix, pick the lane carefully. A `-target cuda` FileCheck on a prelude-only change passes on master as well, because the generated call text (`surf2DLayeredwrite(...)` or the prelude helper name) is unchanged; only the prelude body differs. The PTX lane, assembled or register-traced as above, is the one that tells the fixed build from master [same](../learnings/1791613023335-ptxas-gates-sust-p-array-geometry-on-ptx-isa-4-1-n.md).

## `-target cuda` exit 0 is not a compile check; `-target ptx` is

`slangc -target cuda` only emits CUDA source, so it exits 0 even when the emitted call has no prelude specialization, for example `surf2Dwrite_convert<ulonglong>` for an `RWTexture` of a 64-bit format. `-target ptx` runs the local NVRTC (12.6 here) and shows the real failure: "extern inline function … was referenced but not defined" for writes, and `identifier "surf2Dread_convert" is undefined` for reads. On master b00d9e482 the CUDA prelude specializes `surf{1,2,3}Dwrite_convert` only for float/uint/int and their 2- and 4-vectors, and the converting reads exist only for half formats under `SLANG_CUDA_ENABLE_HALF` (tracked as #13581 for writes and #11088 for reads). Separately, `[format]` recovery on CUDA misses array elements even with direct access, because `_findImageFormatDecoration` only handles `load(field_addr)` (#13580) [slangc -target cuda exit 0 hides NVRTC failures](../learnings/1791840267130-cuda-rwtexture-slangc-target-cuda-exit-0-hides-nvr.md). NVRTC still does not assemble inline asm, so for asm preludes the `ptxas` method above remains the check.

To test a patched prelude without rebuilding Slang, start from the `.cu` that `slangc -target cuda` emits. It includes the prelude by absolute path, so a search path alone does not swap it: rewrite the `#include` line to a relative name and pass `-I<dir>` to NVRTC [Slang CUDA prelude intptr_t typedefs break any CCCL header (e.g. cooperative_groups.h) on NVRTC 12.6](../learnings/1793291460496-slang-cuda-prelude-intptr-t-typedefs-break-any-ccc.md). Which prelude block a compute shader sees is on [[wiki/concepts/slang-backends-f0909b0-cuda-optix.md]]. A dev build makes the NVRTC side cheaper still: the `.cu` a dev slangc emits starts with `#include "<worktree>/prelude/slang-cuda-prelude.h"`, an absolute path into that build's source tree, and NVRTC reads the file when the test runs, so an edit to `prelude/slang-cuda-prelude.h` takes effect in `slang-test` CUDA lanes immediately, with no rebuild. On #14048 this turned each mutation drill into seconds instead of a ~10-minute build: copy the PR's prelude into a worktree that already has a Release build, break one branch (unsigned `atomicMin` → `atomicMax`), run the PR's test and the reviewer's remedy test, then restore with `git checkout prelude/slang-cuda-prelude.h`. Do not do this in a worktree whose full suite is running, because its CUDA tests would see the mutant. `-xslang -fp-mode -xslang fast` on a render-test `COMPARE_COMPUTE` line did not seem to reach NVRTC (an FTZ-dependent check passed in both builds), so test fast-math behavior with a hand-written nvcc harness built with `--use_fast_math` [Slang CUDA prelude is #included from the source tree by absolute path, so prelude edits can be mutation-tested without a rebuild](../learnings/1793325067731-slang-cuda-prelude-is-included-from-the-source-tre.md). Which inputs reach NVRTC but not an offline nvcc build is on [[wiki/concepts/slang-backends-cuda-nvrtc-vs-offline-nvcc.md]].

## Texture format: the `format` type argument vs the `[format]` decoration

Slang stores a texture's format in two representations, and its consumers do not agree on which one to read. `_Texture` has a `let format:int` generic parameter (hlsl.meta.slang:833), and the aliases expose it as the third argument, so `RWTexture2D<float, 0, 7>` is an r16f texture. The `[format("r16f")]` attribute is not translated into that argument: it lowers to an `IRFormatDecoration` on the variable, parameter or field key (slang-lower-to-ir.cpp:3218). The only bridge is `resolveTextureFormat` (slang-emit.cpp:2329-2336), which copies decoration → type, and only for globals on GLSL, SPIR-V and WGSL.

Checked at 6d38185bc, a format given only as the type argument is honored by SPIR-V emit but ignored by CUDA `$C`/`$E` (slang-intrinsic-expand.cpp:216-232, which reads only the decoration), so the surface stride is wrong; by the GLSL `layout(...)` qualifier; and by reflection, which uses `findModifier<FormatAttribute>`. Textures that differ only in the format argument are unrelated types: there is no coercion between them, assignment fails with E30019 in both directions, and the message prints both as `RWTexture2D<float>`. When probing a format bug, test both spellings [texture format lives in two representations that consumers read inconsistently](../learnings/1792002263831-slang-texture-format-lives-in-two-representations-.md). The decoration-only path is also why CUDA recovers `[format]` only from the resource's own inst or a load of a global field, which misses array elements (#13580 above) and parameters (the #12737 structural limitation on [[wiki/concepts/slang-compiler-crash-and-legalization-probes.md]]).

## Texture sampling on CUDA: an explicit `SamplerState` must not be dropped (#13559); the shared Gather arm and kernel-root capability gaps

A `CUtexObject` carries its own sampler state, so a CUDA lowering of a separate-sampler overload such as `Texture2D.SampleGrad(SamplerState s, ...)` has nowhere to pass `s`. PR #13559 lowered it anyway, never forwarding `$1` to `tex*Grad`, and maintainer jkwak-work rejected it: "We cannot just ignore the sampler when the user expect it to be used explicitly." His fix keeps `cuda` out of that overload's `[require]`, so it stays E36107 on CUDA, and lowers only the combined `Sampler*.SampleGrad(location, ...)`, which maps exactly onto `CUtexObject`. For new CUDA texture intrinsics, add a CUDA case to a separate-sampler overload only after a maintainer agrees. The existing `Sample`/`SampleLevel(SamplerState s, ...)` CUDA cases already drop `s` this way; that is pre-existing behaviour, not a pattern to copy. This narrows the earlier SampleGrad prototype advice on [[wiki/concepts/misc-f0909b5-cuda-codegen-triage.md]], which added `cuda` to the `[require]` set of both overloads. The explain-diff identity gotcha recorded in the same atom is covered on [[wiki/concepts/agent-fixer-pr-and-ci-mechanics.md]] [CUDA texture lowering must not silently drop an explicit SamplerState](../learnings/1791995178600-cuda-texture-lowering-must-not-silently-drop-an-ex.md).

**The CUDA `Gather` arm fits neither the shadow nor the combined form (#14071).** At master 1f0b33b86 the `case cuda:` arm of the Gather template (`hlsl.meta.slang` ~:5011/:5060, `tex2Dgather<$TR>($0, ($2).x, ($2).y$(componentArg))`) is shared by the isShadow=0/1 and isCombined=0/1 instantiations generated by the loop at :4968. `Texture2D.GatherCmp(SamplerComparisonState, uv, cmp)` therefore compiles on cuda/ptx but never uses `compareArg`: it is a plain red gather of raw texels, and two different compare values emit identical calls, a silent wrong result, while every `SampleCmp*` excludes cuda. Combined `Sampler2D.Gather(uv)` ICEs with E99997 (assert in `slang-intrinsic-expand.cpp(376)`, argIndex out of range), because the location is `$1` in the combined form, not `$2`. Combined `Sampler2DShadow.GatherCmp` emits the compare value as coordinates, which is invalid CUDA and fails in NVRTC on `-target ptx`. To prove an argument is silently dropped, compile two calls that differ only in that argument and diff the emitted call text. Under the #13559 ruling above, the separate-sampler overloads that drop `s` on CUDA today are `Sample`, `SampleLevel` and every `Gather*`; `SampleGrad`, `SampleBias` and `SampleCmp*` are E36107 [CUDA Gather arm in hlsl.meta.slang: GatherCmp drops compare value; combined Sampler2D.Gather ICEs](../learnings/1793318835739-cuda-gather-arm-in-hlsl-meta-slang-gathercmp-drops.md).

**A capability error does not reach `[CudaKernel]`/`[CudaDeviceExport]` roots.** Removing `cuda` from a core intrinsic's `[require]` (and its `case cuda:`) makes it E36107 only for `[shader]`/`-entry` entry points. A `[CudaKernel]` or `[CudaDeviceExport]` function that calls it compiles with exit 0 on `-target cuda` and `-target ptx`, and the callee becomes an empty body with no `return`, so its value is undefined and a store of the result is DCE'd. This was seen on #14079 (GatherCmp) on 2026-10-30, and `SampleCmp` already behaves this way on master 1f0b33b86. When reviewing any "make X a capability error on CUDA" PR, probe `[CudaDeviceExport] float4 f(Texture2D<float> t, SamplerComparisonState s, float2 uv) { return t.GatherCmp(s, uv, .75); }` and a `[CudaKernel]` variant and inspect the emitted `.cu`. Treat the result as a disclosure gap plus a follow-up issue for capability validation of kernel and export roots; it does not block the PR. The meta-template guard that drops the `case cuda:` is required, not dead code: a `case cuda:` inside a `__target_switch` whose `[require]` excludes cuda is E36101 (`visitTargetSwitchStmt`, `slang-check-decl.cpp` ~22513) [[CudaKernel]/[CudaDeviceExport] roots skip E36107: no-cuda [require] intrinsics compile to empty bodies](../learnings/1793325266713-cudakernel-cudadeviceexport-roots-skip-e36107-no-c.md).
