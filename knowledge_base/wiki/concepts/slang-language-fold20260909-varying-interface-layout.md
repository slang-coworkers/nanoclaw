# Slang Entry-Point Varying Interface: Location Layout & the Store Anchor

Two front-end/codegen facts about how entry-point varying inputs/outputs get their SPIR-V interface: how their interface LOCATIONS are numbered (the front-end layout engine), and how a varying output stays IN the `OpEntryPoint` interface at all (a reachable store is the anchor). Both surfaced from fixes where a naive change silently broke the interface.

## TL;DR

- Ordinary varying layout (SPIR-V interface locations) is allocated in the FRONT-END (`slang-parameter-binding.cpp`), independent of stage; a 64-bit-element matrix/wide vector is MIS-SIZED there → overlapping locations → `VUID-StandaloneSpirv-OpEntryPoint-08722` (#12726 neighborhood).
- A `double R×C` matrix needs `R × ceil(C·8/16)` locations (8 for `double4x4`) and a `double3`/`double4` needs 2 — the engine wrongly sizes them as if a location held a 64-bit element.
- An entry-point varying OUTPUT is in the `OpEntryPoint` interface ONLY via a store reachable from the entry point; removing an unwanted store makes the varying VANISH (no interface entry, no Location, no OpVariable). "Declared + no store" is NOT achievable by dropping the store — substitute a canonical uninitialized-read value and let the backend elide the undef store at -O1+.
- Test traps: slang-test forces `-O0` unless the test names its own `-O`; a trailing FileCheck `CHECK-NOT` only scans the tail region; ALWAYS confirm the regression test FAILS on the unfixed binary.
- Reviewer control: before accepting a critique's "your fix fails case X," test whether X fails on MASTER or on an unrelated stage — it separates your regression from a pre-existing orthogonal bug.

## 64-Bit Matrix/Vector Varyings Mis-Size Interface Locations (VUID-08722, #12726 neighborhood)

A `double4x4` (or any 64-bit-element matrix / wide vector) used as an ORDINARY varying — NOT tessellation, NOT patch — mis-numbers its SPIR-V interface locations and produces overlapping-location `VUID-StandaloneSpirv-OpEntryPoint-08722` (discovered while fixing #12726). Repro on a plain vertex shader, no patch involved: `struct VOut { float4 pos : SV_Position; double4x4 m : MTX; float2 after : AFTER; };` compiled with `-emit-spirv-directly -stage vertex` gives `m@Location 0` and `after@Location 4` (should be 8); with `SLANG_RUN_SPIRV_VALIDATION=1` → VUID-08722, exit 141. Root cause: the FRONT-END varying-layout engine (`slang-parameter-binding.cpp`, the VaryingInput/Output location allocation) sizes a `double4x4` as 4 locations, not 8 — it doesn't account for a location holding only 16 bytes (4×32-bit = 2×64-bit), so a 64-bit `R×C` matrix needs `R × ceil(C·8/16)` (=8 for 4x4) and a `double3`/`double4` vector needs 2 locations. This is independent of stage and of #12726: the #12726 IR-legalize span helper (`getVaryingLocationSpan` in `slang-ir-glsl-legalize.cpp`) computes the correct 16-byte-based span for the HULL patch-constant OUTPUT (so HS is right), but the DOMAIN input and all ordinary varyings go through the front-end path which still mis-sizes — so DS still overlaps, and fixing it everywhere requires correcting the front-end layout rule (a separate issue). Reviewer meta-lesson: when a critique flags "your fix fails case X" (an exotic `double4x4` patch field), test whether X fails on MASTER / on an unrelated stage first — a control (`double4x4` in a vertex shader) instantly separates "my regression" from a pre-existing orthogonal bug ([64-bit matrix/vector varyings mis-size interface locations in the front-end (VUID-08722), any stage](../learnings/1787677209465-64-bit-matrix-vector-varyings-mis-size-interface-l.md)).

## An Unwritten Entry-Point Varying Output: the Store IS the Interface Anchor (#12756)

Fixing a spurious store into a never-written varying OUTPUT (a partial-init returned struct, #12756), the naive "just skip the store" BREAKS the interface. A varying-output global lands in the SPIR-V `OpEntryPoint` interface ONLY if it's used as an operand reachable from the entry point (`buildEntryPointReferenceGraph`, `slang-ir-call-graph.cpp`), and it survives DCE only via that use (`keepGlobalParamsAlive` defaults FALSE = `-preserve-params`); the store is the sole anchor. Remove it and the varying vanishes entirely — no `OpEntryPoint` entry, no Location, no `OpVariable` (measured on BOTH SPIR-V and GLSL) — and the CURRENT buggy compiler keeps the varying declared precisely BECAUSE the bad store anchors it. So "declared + no store" is NOT achievable by dropping the store. The correct low-risk fix keeps the store but substitutes a canonical `emitLoadFromUninitializedMemory(fieldType)` for the uninitialized-read value; on SPIR-V at -O1+/default the backend then elides the `OpStore %x %OpUndef` → declared + no store (matches expected behavior). At -O0 the undef store remains (benign); GLSL keeps a store of a fresh uninit local. `[dependsOn(x)]` is NOT a shortcut here: DeepWiki claimed it keeps an entry-point output in the interface with no store, but a build FAILED for SPIR-V — `getFirstChild()` SKIPS decorations so `buildEntryPointReferenceGraph`'s `getChildren()` walk never sees it, and even after teaching the ref-graph + emit-spirv `ensureInst` + `[keepAlive]`, deeper spirv-legalize / translate-global-varying-var passes still prune it (4 coordinated changes insufficient; truly-no-store across all opt levels is a deep SPIR-V-pipeline rework, disproportionate for a P2). Two instrument traps that caused false-greens: (1) slang-test forces `-O0` by default unless the test names its own `-O` level (`addDefaultSlangOptimization` short-circuits on `hasSlangOptimizationArg`), so a store-elision fix only visible at -O1+ needs the test to specify `-O1`; (2) a trailing FileCheck `CHECK-NOT` after the last positive `CHECK` scans only the tail region — if the forbidden line sits earlier (e.g. the uv store emitted BETWEEN the color and gl_Position stores) the NOT misses it and the test passes on the BUGGY binary, so bracket the `-NOT` between two ordered positive matches that straddle the offending line, and ALWAYS confirm the regression test FAILS on the unfixed binary (copy it into a clean master checkout and run master's slang-test) ([Unwritten entry-point varying output: the store IS the interface anchor — don't skip it](../learnings/1788019476812-unwritten-entry-point-varying-output-the-store-is-.md)).
