# Slang conformance checking: requirement enumeration and method-requirement witness synthesis

## TL;DR

- **The checker's requirement loop is a DENY-list; IR lowering's `shouldDeclBeTreatedAsInterfaceRequirement` is an ALLOW-list.** Any member kind the nesting table allows in an interface but that is not a requirement makes them disagree. Today that is only `EmptyDecl`, from a stray `;`.
- **E38100 "does not provide required interface member ''" with an empty name means a stray `;`** in the interface body or one of its base interfaces (e.g. `property T X { get; };`).
- **Conformance synthesis wraps even a single lookup item in an `OverloadedExpr`, on purpose** (method, constructor and subscript paths). Re-checking a member expression re-runs lookup, which can pick the wrong thing. Replacing it with `createLookupResultExpr` makes `int foo;` or `int foo(int)` silently satisfy `int foo()`.
- **"A single-declaration name never becomes an `OverloadedExpr`" holds only for ordinary lookup**, not for conformance synthesis.
- **Code that consumes `OverloadedExpr::lookupResult2` must use `LookupResult`'s own API** (`getName()`, range-for) and gate ambiguity on `isOverloaded()` (`items.getCount() > 1`), not `isValid()` (checks `item`). Reading `items[0]` directly is wrong for both non-overloaded forms, where `items` is empty or has exactly one entry.
- **#13349: any same-name NON-callable member that satisfies a method requirement's lookup reaches `ResolveInvoke`'s no-callable tail and crashes** (E99997 Debug, segfault Release). PR #13353 (`isOverloaded()` tail check plus `LookupResult` accessors in `diagnoseAmbiguousReference`) turns every crashing shape into E38105, and either hunk alone fixes all of them.
- **`const` on a parameter is a binding modifier and `__ref`/`__constref` are passing modes, not types (maintainers, #13339)** — const-aware matching goes through the effective `ParameterPassingMode` (`RefReadOnly`/`RefReadWrite`), never a per-case matcher check; no spot fixes in this area.
- **Adding an input to the effective passing mode needs three updates**: the mode derivation, the witness-synthesis modifier clone loop (else synthesized forwarders get the wrong mode → spurious E38108), and IR `ParameterDirectionInfo` (else dispatch/autodiff wrappers disagree with witnesses). Grep every `switch` — `default:` absorbs new enumerators silently.
- **Prove a diagnostic fix leaves genuine ambiguity alone** with an overloaded non-callable name reaching the same tail (a global `int foo;` plus `namespace N { int foo; } using namespace N;` with `return foo();` gives E39999 + 2×E40011 before and after).

When a type declares conformance to an interface, `checkInterfaceConformance` (slang-check-decl.cpp) first decides which interface members count as requirements, and then, for each requirement without a direct match, `trySynthesizeMethodRequirementWitness` and its constructor/subscript siblings try to build a witness from member lookup. Two front-end bug families cluster at these two steps: a requirement-enumeration predicate that disagrees with IR lowering, and synthesis-built `OverloadedExpr`s that diagnostic helpers mis-read. Witness-table resolution and associated types are on [[wiki/concepts/slang-language-core-f0909b0-interfaces-witness-conformance.md]]; default arguments and default-method bodies are on [[wiki/concepts/slang-language-core-f0909b0-default-args-methods-visibility.md]].

## The requirement loop is a deny-list; the IR requirement predicate is an allow-list (#13337)

The last loop of `checkInterfaceConformance` (slang-check-decl.cpp ~:11652) treats EVERY interface member as a requirement except associated types, generic constraints, `InheritanceDecl` and `InterfaceDefaultImplDecl`. IR lowering's `shouldDeclBeTreatedAsInterfaceRequirement` (slang-lower-to-ir.cpp ~:1683) is an allow-list instead. The two disagree on any member kind that the nesting table allows in an interface but that is not a requirement. Today that is only `EmptyDecl`, produced by a stray `;` such as `property T X { get; };`: the checker raises a spurious E38100 "does not provide required interface member ''" with the note "see declaration of 'empty'" (#13337). typedef/typealias/using/nested struct in an interface are already rejected earlier with E30102, so they never reach this loop. A one-line `if (as<EmptyDecl>) continue;` fixes it, verified 2615/2615 on tests/language-feature + tests/diagnostics [checker requirement loop is a deny-list, IR requirement predicate is an allow-list](../learnings/1790757907963-slang-interface-conformance-checker-requirement-lo.md).

## Conformance synthesis builds single-item `OverloadedExpr`s on purpose

An earlier triage rule said a single-declaration name never becomes an `OverloadedExpr`. That holds for ordinary lookup (`createLookupResultExpr`, slang-check-expr.cpp:1088), but NOT for conformance synthesis: `trySynthesizeMethodRequirementWitness` (slang-check-decl.cpp:7700-7703) wraps the lookup result in an `OverloadedExpr` even when it holds a single item, and the constructor path (:8155) and subscript path (:8389) do the same. This is deliberate. When the synthesized member expression is checked, lookup runs again, and that can pick the wrong thing; in a prototype, swapping in `createLookupResultExpr` made `int foo;` and `int foo(int)` silently satisfy `int foo()`, and a `fwd_diff` witness in the core module failed. So the producer shape is valid, and the consumers must cope with it: code that reads `OverloadedExpr::lookupResult2` must use `LookupResult`'s own API (`getName()`, range-for) and gate ambiguity on `isOverloaded()`, not `isValid()` [single-item OverloadedExpr IS produced by conformance witness synthesis](../learnings/1790793365406-single-item-overloadedexpr-is-produced-by-conforma.md).

The crash instance is #13349. The `ResolveInvoke` tail (slang-check-overload.cpp:3966) gates on `isValid()`, and then `diagnoseAmbiguousReference` reads `items[0]` on an empty list, giving E99997 in Debug and a segfault in Release. It is triggered by a field, `static const` or property named like a method requirement, and the fix is 3 lines [same](../learnings/1790793365406-single-item-overloadedexpr-is-produced-by-conforma.md). The underlying distinction: `LookupResult::isValid()` checks `item`, and `isOverloaded()` checks `items.getCount() > 1`, so code that reads `items[0]` directly is wrong for both non-overloaded forms, where `items` is empty or has exactly 1 entry [#13349 has more trigger shapes](../learnings/1790800014367-13349-single-candidate-overloadedexpr-ice-more-tri.md).

## The #13349 trigger matrix and the PR #13353 fix

Beyond the field, `static const` and property cases, each of the following segfaults on master Release (rc 139), and every one reaches `ResolveInvoke`'s no-callable tail with a single-candidate `OverloadedExpr` built by `trySynthesizeMethodRequirementWitness`: a nested type named like the method requirement (`struct S : IFoo { struct foo { int x; }; }`); an array field against a requirement that takes a parameter (`int foo[4];` against `int foo(int)`); a conformance declared in an extension (`struct S { int foo; } extension S : IFoo {}`); an inherited field (`struct B { int foo; } struct S : B, IFoo {}`); and a field whose type has `operator()`. Some same-name shapes do not crash on master and already report E38105: a `typealias foo = int`, a generic requirement `int foo<T>(T)` against a field, and static requirements, because `removeNonStaticLookupItems` leaves `items.getCount()==1` [#13349 single-candidate OverloadedExpr ICE: more trigger shapes](../learnings/1790800014367-13349-single-candidate-overloadedexpr-ice-more-tri.md). A struct field named like a *defaulted* interface method requirement also segfaulted master during the PR #12249 overload probing (see [[wiki/concepts/slang-language-core-f0909b0-generics-overload-inference.md]]).

With PR #13353, where the tail check changes from `isValid()` to `isOverloaded()` and `diagnoseAmbiguousReference` uses the `LookupResult` accessors, every crashing shape gives E38105, and a requirement with a default body compiles instead. Either hunk alone fixes all of them. To check that the fix leaves genuine ambiguity unchanged, use an overloaded non-callable name that reaches the same tail: a global `int foo;` plus `namespace N { int foo; } using namespace N;` with `return foo();` gives E39999 plus 2×E40011 both before and after the fix [same](../learnings/1790800014367-13349-single-candidate-overloadedexpr-ice-more-tri.md).

## Signature matching and `const` / `__ref`: binding modifiers and passing modes, not types (#13339)

This section records the maintainers' stated design position (tangent-vector on shader-slang/slang#13339, 2026-09-30), not something verified in source. `const` on a function parameter does not change the function's signature; it only stops the body from assigning to that binding, so `void f(int x)` ≡ `void f(const int x)` and `void f(Ptr<int> x)` ≡ `void f(const Ptr<int> x)`. `const` is not meant to be a *type* modifier, so `const int*` should not be read as `Ptr<const int>` (they asked to be told if the parser now treats it as one). `__ref` / `__constref` are parameter-passing modes on the *parameter*, with no real `Ref<T>` type behind them; references are not meant to be user-exposed types, and `Ref<T>` in the core module was called a mistake. #13339 was filed on the premise that "`const __ref` is part of the requirement signature, so matching must compare it", which they called a misunderstanding or a symptom of a larger design mess around passing modes, references and `const`. They asked for a coherent top-down fix, not symptom-level spot fixes in this area [const is a binding modifier, __ref a passing mode](../learnings/1790789000537-slang-const-on-a-parameter-is-a-binding-modifier-r.md).

A follow-up the same day ("based on input from @jhelferty-nv") gave the near-term plan, which is theirs to own and not a go-ahead for us. `ParameterPassingMode`'s single `Ref` is replaced by `RefReadWrite`, `RefReadOnly` and `RefWriteOnly` (the last "for completeness"), and the logic that derives the *effective* passing mode takes `const` into account: `const` + `__ref` gives `RefReadOnly`, any other `__ref` / `groupshared` gives `RefReadWrite` (`const` + `groupshared` was only "I'm guessing", so unconfirmed). Requirement matching already compares passing modes, so a `RefReadWrite` vs `RefReadOnly` mismatch then fails to match with no extra check. Many consumers will not respect the new modes at first, and tangent-vector's in-progress PR making the `this` parameter's passing mode explicit overlaps this area [near-term plan: RefReadOnly/RefReadWrite](../learnings/1790789968180-slang-near-term-path-for-const-aware-ref-matching-.md).

When the effective passing mode does gain a new input (the #13339 work made `__ref` + `const` → `RefReadOnly`), two other places re-derive the mode and must learn the new input too. Witness synthesis is a second source of truth: the loop in slang-check-decl.cpp (~line 7346) that clones `InOut`/`Out`/`Borrow`/`Ref` modifiers onto the synthesized forwarder's parameters must also clone `ConstModifier`, or the forwarder for a `const __ref` requirement comes out `RefReadWrite` and every implementation that needs a forwarder (e.g. one with an extra defaulted parameter) is wrongly rejected with E38108. And the IR's `ParameterDirectionInfo` (slang-ir-util.h), which round-trips parameter types for dynamic-dispatch wrappers and autodiff, must carry any new part of the mode (the access qualifier), or wrappers silently disagree with witnesses. A `-dump-ir` FileCheck with an `IR-NOT` on the dropped form catches it (confirmed by a negative-control revert). When adding or removing an enumerator, grep every `switch`: with `-Wno-switch`, removing an enumerator turns stale `case` labels into compile errors, but `default:` branches silently absorb new ones [adding a ParamPassingMode component must update the witness-synthesis clone list](../learnings/1790868001044-slang-adding-a-component-to-a-parampassingmode-mus.md).

How to apply all three: if `const` has to affect matching, express it through the effective parameter-passing mode, never through a per-case read-only comparison in the matcher (e.g. a groupshared-only special case). Before filing an issue or writing a fix that assumes `const` or `__ref` is part of a type or signature, check that premise against the parser and checker and state it in the issue so a maintainer can reject it early. Before implementing the plan, ask who owns it and check it against the `this`-mode PR; when relaying it, keep their enum names exactly. A maintainer correction of a premise our shared bot identity filed gets a direct, brief answer with no fix proposal.
