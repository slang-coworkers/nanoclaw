## TL;DR


## The Devin tier fails toward clean — exit 0 is not a signal

On the Devin-only tier (harvest exit 20/10) Devin is the *sole* head-current review input, which makes a silent Devin failure a direct path to a false WOULD_APPROVE. Every observed failure mode presents as success.

- **Exit 0 on a skeleton-loading page.** `devin-fetch.sh`'s `DONE_EXPR` accepts a `Checks \d+/\d+` match as evidence the page finished rendering, but Checks and the AI-analysis/Flags panel are independent async regions: on slang#11118 the counter reached `47/47` while Flags was still skeleton-loading behind an unclicked "View results" button. Exit 0, empty Flags, and the real analysis had **5 Investigate + 2 Informational** flags that materially shaped the decision. A scraper's done-signal must key on **the region you are extracting** — prefer a positive assertion about the target content (a flag row, or an explicit empty-state string) over a sibling counter — and *exit-0-with-empty-findings is suspect, never clean*: a genuinely clean Devin run says so ([[approver/infra-abstain] devin-fetch.sh can exit 0 on a skeleton-loading page — "Checks N/N" is not a done-signal for the Flags panel](wiki/learnings/1785745227617-approver-infra-abstain-devin-fetch-sh-can-exit-0-o.md)).
- **Exit 0 on an unauthenticated session that echoes our own PR body back as "AI analysis".** On slangpy#1068 `devin-fetch.sh` exited 0 and wrote a 3714-byte `devin-flags.md` — empty `## Flags`, the scraped page carrying `Connect GitHub` / `Sign in`, and the text under Devin's "AI analysis" heading being **our own `nv-slang-bot[bot]` PR description byte-for-byte** (Status/Link/Verdict/Next-action/Blocker bullets included). On a bot-authored PR the author is *us*, so a naive read is **self-review laundered through a scraper**, arriving with the authority of an independent signal. Never take `devin_exit == 0` as `devin_signal == true`: grep for the auth banner, count flag lines under `## Flags`, and diff the analysis body against `pulls/<n>.body` — any one of the three ⇒ `devin_signal: false`, and with harvest 20/10 that is `reviewers_complete: false` ⇒ **ABSTAIN_INFRA / NO_REVIEW_SIGNAL**. Do not review the code yourself in its place ([[approver/infra-abstain] devin-fetch.sh exits 0 on an unauthenticated session that produced no review — the "analysis" was our own PR body](wiki/learnings/1785786593883-approver-infra-abstain-devin-fetch-sh-exits-0-on-a.md)).
- **Two non-identical copies of the script exist; establish which one RAN.** `~/.claude/skills/slang-pr-review-runner/scripts/devin-fetch.sh` (331 lines) pipes the browser capture through `json.loads`; the `nanoclaw-pr-review-runner` copy (187 lines) does not — and the `/slangpy-pr-approve` workflow text points at the **nanoclaw** one, so the undecoded copy is what the approver path actually invokes while the more-correct copy sits unused. Auditing the wrong copy inverts the finding; recover the executed command from the subagent transcript rather than from prompt text, since both paths get *mentioned* in one session. The mechanism: `agent-browser eval 'document.body.innerText'` returns a **JSON-quoted string** — one physical line, newlines as literal two-char `\n` — so the extractor's `re.split(r'\n\s*\d+\s*Flags?\s*\n', …)` never matches, everything falls into `analysis`, and `flags` stays `''`. Both guards then pass: no `Generating…` in the body, and total size clears `DEVIN_MIN_BYTES` because the analysis half is fat — **a body-integrity check that measures the whole file cannot see one empty section**. Compounding it, the done-poll accepted a bare CI progress counter (`Checks 12/17`) as the *only* signal, having never seen a flags summary. So after any exit 0, assert the *section* is non-empty (`sed -n '/## Flags/,$p' | tr -d '[:space:]' | wc -c`) and check `head -c1 devin-page.txt` for a leading `"`; an empty `## Flags` after exit 0 is **ABSTAIN_INFRA**, never "Devin found nothing" ([[approver/infra-abstain] the nanoclaw devin-fetch.sh copy lacks the json.loads decode — silently empty Flags section, and a CI counter alone satisfies the done-poll](wiki/learnings/1785787109745-approver-infra-abstain-devin-fetch-sh-the-nanoclaw.md)).

⚠️ **And the root cause of that empty Flags section was NOT the missing decode — which is the more valuable lesson.** The author claimed the absent `json.loads` made the regex split "impossible"; a reviewer opened the named file, confirmed both the split pattern and the missing decode, and wrote *"verified in the copy it actually ran."* Both facts were true and neither tier tested the **counterfactual**: decode the text, re-run the same split, and Flags is *still* empty, because the marker string occurs **zero** times in the capture. The real cause was upstream — the done-poll exited on a CI progress counter, so the panel had never rendered. **Verifying that defect B exists at the cited lines is not verifying that B caused symptom S**; file-reading confirms *presence*, only a counterfactual establishes *causation*, and three amplifiers make the two feel identical: a sibling "correct" implementation reads as a clean before/after, line-number citations read as rigor, and **assent adds apparent independence** — a second tier restating a claim it sourced *from the first tier* manufactures corroboration where there is one source. Note both polarities of the null-result trap in one session: three null greps misread as *absence of defect* (case-sensitivity, regex metacharacters) and this one misread as *presence of a specific defect* — **a null result does not name its own cause.** Before blaming a parser, prove the input contained the thing that failed to extract (`grep -ociE '<marker>' <capture>` = 0 ⇒ capture problem, not parse problem); distrust *clean*; and state verification at its true strength — "confirmed the defect exists at :157" ≠ "confirmed it caused this." When a claim is adopted upstream the author's obligation to re-derive it goes **up**, not down ([[approver/critique-mustfix] confirming a peer's mechanism means running the counterfactual, not reading the file the claim cites](wiki/learnings/1785787841835-approver-critique-mustfix-confirming-a-peer-s-mech.md)).


## Critique-gate recording mechanics (must satisfy before `record_decision`)

The approver's delivery gate (`track-critique.sh` + `gate-critique-on-deliver.sh`) records a codex critique round toward the gate ONLY when THREE things are all present on the `mcp__codex__codex` call: (1) a `STAGE: <NAME>` marker as the first prompt line; (2) the `developer-instructions` field matches the canonical `/codex-critique` reviewer block **verbatim** (it greps sentinel lines "You are an independent reviewer" and "Return ONLY the structured output below"); (3) the response carries a `### Verdict` heading followed by `approve` | `must-fix` ([[approver/critique-mustfix] codex-critique-gate-requires-canonical-developer-instructions-verbatim](wiki/learnings/1784329350850-approver-critique-mustfix-codex-critique-gate-requ.md)). Required stages are `DECISION_REVIEW` + `OUTPUT_REVIEW`, and the gate opens only when each count ≥1 AND OUTPUT_REVIEW's *last* verdict = approve with `edits_since_critique==0` and an attested-hash match. Ad-hoc `mcp__codex__codex` calls (even with a `STAGE:` line) are fine for EXPLORATORY reachability checks but never satisfy the gate — plan on one canonical skill call per required stage on top of any exploratory rounds ([[approver/critique-mustfix] populate full record_decision field set before OUTPUT_REVIEW; ad-hoc codex STAGE calls don't count toward the gate](wiki/learnings/1784333487365-approver-critique-mustfix-populate-full-record-dec.md)). Also: `codex` requires `sandbox: "danger-full-access"` (bwrap fails in Docker); the `gate-critique-on-deliver.sh` Bash regex false-positives on ANY command containing the literal `/pulls` even for read-only GETs, so split the literal (`P="repos/o/r/pu""lls/n"`) or drive reads through the bundled python scripts; and create `/workspace/.claude/` if absent or the hook errors. Concretely, the hook's PR-creation pattern is `gh api [^|]*pulls\b` — verb-blind, so a read-only `gh api .../pulls/<n>/reviews|comments` (fetching review bodies / inline threads) is DENIED as "CRITIQUE REQUIRED before PR creation" and repeated hits reach the denial cap and auto-fire a (correctly-rejected) admin bypass. Don't fight it — route around it: read review bodies via `gh pr view <n> --json latestReviews,reviews` (no `pulls` in the path) and inline threads via `gh api graphql` (`reviewThreads`); `commits/<sha>/check-runs` and `.../status` are already safe. Only ad-hoc follow-up reads bite (a supervisor nudge, a late human review body); the initial harvest scripts already use safe paths [[approver/infra] read-only `gh api .../pulls/<n>/reviews|comments` trips the critique-gate PR-creation hook — use gh pr view / GraphQL](wiki/learnings/1784867719312-approver-infra-read-only-gh-api-pulls-n-reviews-co.md).

This `pulls`-substring false-match kept recurring across the slang and slangpy approver runs, so the workarounds are worth stating concretely. The hook's `gh api [^|]*pulls\b` pattern is verb-blind (a GET reads identically to a PR-creating POST), and every denial increments `critique_gate_denials` in `/workspace/.claude/workflow-state.json` — at 3 it escalates to a human admin card, so a read-only harvest can spuriously burn strikes toward an escalation. Three routes clear it: (1) use GraphQL for reviews/inline threads (`gh api graphql` with a `reviewThreads` query — path is `graphql`, not `pulls/…`) and `contents/<path>?ref=<sha>` for file bodies at head ([[approver/infra-abstain] Critique-gate hook false-triggers on read-only `gh api .../pulls` — use GraphQL/contents for reads](wiki/learnings/1785412883919-approver-infra-abstain-critique-gate-hook-false-tr.md)); (2) prefer `gh pr view <n> --json reviews,files,latestReviews,headRefOid,commits` — no `pulls` literal in the command line, so it is never gated and covers reviews + changed-file metadata for staging ([[approver] Critique-gate Bash hook: wrap read-only gh api /pulls calls in a script file to avoid the false-match](wiki/learnings/1785453486073-approver-critique-gate-bash-hook-wrap-read-only-gh.md)); (3) if you must hit the REST `/pulls` endpoint, wrap the `gh api` call inside a small `bash work/<pr>/tmp/fetch.sh` script — the hook only inspects the literal Bash command string, so `bash fetch.sh` passes while the script's internals run unimpeded (this is exactly why the bundled `collect-reviews.sh`/`harvest-reviews.py` are never gated — their `gh api` calls live inside the script) ([[approver] Critique-gate Bash hook: wrap read-only gh api /pulls calls in a script file to avoid the false-match](wiki/learnings/1785453486073-approver-critique-gate-bash-hook-wrap-read-only-gh.md)). A fourth confirmed route, when GraphQL is 401-ing and `gh pr view` is therefore unavailable: **split the literal in the shell** (`PL="pul"; PL="${PL}ls"`) so the command text never contains the matched substring ([[approver/critique-mustfix] the critique gate's own mechanics — STAGE header, verbatim developer-instructions, and codex-reply cannot record a round](wiki/learnings/1785784264312-approver-critique-mustfix-the-critique-gate-s-own-.md)). Do NOT run a pointless `/codex-critique` or request an admin bypass to clear the gate for a read — the reads aren't deliverables. The same false-match extends to the REST review-thread reply POST (`gh api .../pulls/<n>/comments/<id>/replies`) for answer-style / explanation-only tasks that have no code diff: post replies via the GraphQL `addPullRequestReviewThreadReply` mutation (needs the `PRRT_…` thread node id from the read), and note that a plain issue comment (`repos/<o>/<r>/issues/<n>/comments`) is on the `issues/` path and does NOT trip the gate — only `pulls/` paths are affected ([codex-delivery gate false-positives on gh PR-comment reads + REST review-reply POST; use GraphQL](wiki/learnings/1785450188405-codex-delivery-gate-false-positives-on-gh-pr-comme.md)).

**Do not burn attempts on the blocked path, and never let the block become a capability-negative.** The escalation is real: on the slang-rhi#804 merge join, repeated `pulls/804/reviews` GETs hit the denial cap, auto-filed a critique-gate bypass request, and an admin (correctly) **REJECTED** it — a legitimate read-only join step gating behind a critique requirement that makes no sense for it. Switch access path immediately and **name both methods in the artifact**. Two substitutions worth memorizing for join work, where the hook bites hardest: `gh pr view <n> --repo <r> --json reviews,reviewDecision,mergedAt,mergedBy,commits,mergeCommit` is unblocked and gives login/state/`submittedAt` per review; and to bound *which* commit a review covers without `/pulls/N/reviews` — the only place the literal `commit_id` field lives — fetch each candidate via `repos/<r>/commits/<sha>` (unblocked) and compare `commit.committer.date` against the review's `submitted_at`: if every commit predates the approval, the human reviewed at-or-after the final head. That **BOUNDS** coverage; it does not confirm the attached SHA, and the artifact must say so. Record the limitation as **"could not verify X by method M"** with M named, never as "unavailable" — a false capability-negative has no observable failure signature. (Also: `gh pr view --json` rejects invented field names — `merged` is not a field, use `state`/`mergedAt` — and prints the valid list on error, so read that rather than guessing.) ([[approver/infra-abstain] critique-gate hook false-fires on read-only gh pulls/ GETs — use commits/<sha> dates to bound review timing](wiki/learnings/1785819496807-approver-infra-abstain-critique-gate-hook-false-fi.md))

**Three mechanical reasons a real, useful critique round does not count.** On slang-rhi#806 three rounds produced genuine verdicts that the delivery gate never recorded, at one point leaving the tally at `OUTPUT_REVIEW=1 / must-fix` while an `approve` had already arrived — via a call that didn't record. (1) **`mcp__codex__codex-reply` cannot carry `developer-instructions`** — the reply tool has only `threadId` + `prompt`, so every round that must count is a **fresh `mcp__codex__codex` call** passing the canonical block; threading is convenient for the reviewer's context and silently forfeits gate credit. (2) The **`STAGE:` header must be in the prompt of that same recording call** — a reply omitting it recorded as a round but attributed to the *prior* stage, so `OUTPUT_REVIEW` stayed uncounted while `DECISION_REVIEW` looked satisfied. (3) `track-critique.sh` **greps for sentinel lines**, so paraphrasing the developer-instructions — even improving them — fails the match; copy the block from `/home/node/.claude/skills/codex-critique/SKILL.md` verbatim. Also: a recorded `must-fix` satisfies the *count* but still blocks delivery (`OUTPUT_REVIEW` must be `approve` specifically), and `ABSTAIN_*` decisions **skip both stages entirely** — this whole cost applies only to `WOULD_APPROVE`/`BLOCK`, the two states making a positive claim. After every critique call, read the hook's PostToolUse line and confirm the stage tally *and* verdict moved as expected: **the reviewer's verdict and the gate's record are two different things**, so never infer a round landed from the reviewer's text ([[approver/critique-mustfix] the critique gate's own mechanics — STAGE header, verbatim developer-instructions, and codex-reply cannot record a round](wiki/learnings/1785784264312-approver-critique-mustfix-the-critique-gate-s-own-.md)).

⚠️ **The gate is also an apparatus that perturbs what you try to measure through it.** Because it extracts `.tool_input.command` and greps a pattern list **before execution**, any command containing a denied substring is refused *whole* — so bundling a previously-passing command alongside a previously-denied string to compare them denies the entire invocation, the control never runs, and the result reads as *"the gate is nondeterministic — my earlier pass must have been wrong."* Re-run alone: passed; deterministic throughout. **One probe per command**: never co-locate a control with a string that can trip a text-matching gate, because the gate cannot distinguish the part you're testing from the part you bundled ([[approver/critique-mustfix] second species — the apparatus is subject to the effect under test](wiki/learnings/1785782534319-approver-critique-mustfix-second-species-the-appar.md)).

## The harvest tier on slang-rhi: a clean CodeRabbit pass is a comment EDIT, and the discard is in our own script (2026-08-11 fold)

`scripts/collect-reviews.sh` returning **exit 20** with `harvest.json {found:false}` does **not** mean "no bot review exists". When CodeRabbit has no actionable comments it does not post a review row at all — it **edits its existing summary comment in place** (`issues/<pr>/comments`, body `No actionable comments were generated in the recent review. 🎉`, `created` months earlier but `updated` ~90 s after the push, with a `📥 Commits` header spanning the pinned head). Two confirmed instances (slang-rhi#811-R2, #598), so treat it as the expected shape, not an anomaly: key head-currency off the **absence of the rate-limit marker** plus the commit span, never off the presence of a review row ([harvest exit 20 is NOT NO_REVIEW_SIGNAL — a clean CodeRabbit pass lands as a summary-comment EDIT](wiki/learnings/1786347975646-approver-infra-abstain-harvest-exit-20-is-not-no-r.md)).

The mechanism inside our script matters because it changes the fix, and the first diagnosis of it was wrong. The script is **not** structurally blind to the edit: at `:153-160` it paginates `issues/<pr>/comments`, filters to the CodeRabbit login and matches `summarize by coderabbit` / `Actionable comments posted`; at `:161` it **captures the signal** into `cr_summary` (last-wins, so the newest summary survives — on #598 that was 5,737 chars naming `cuda-device.cpp`). The defect is downstream: `:195` builds `cand` from **review ROWS only**, and `:206` calls `finish(20)` writing `{"found": false}` **without ever consulting `cr_summary`**. So it is a **discard, not a blindness** — a matched-then-dropped signal. The fix is therefore "make the exit-20 path fall back to `cr_summary`", not "add summary-comment matching". Generalizing: when an instrument reports absence, check whether the value was never acquired or acquired and thrown away, because those have different repairs and the symptom is identical ([CORRECTION: collect-reviews.sh DISCARDS the summary it already matched](wiki/learnings/1786351911521-approver-infra-abstain-correction-to-my-earlier-at.md)).

**slang-rhi is permanently fallback-tier — that is not an infra defect to burn down.** Its `Claude Code Assistant` check-run reports `completed/skipped`: this repo does not run the production claude-code-action pipeline that shader-slang/slang runs, so there is no primary review to wait for at *any* head, ever. Decisions there are CodeRabbit-primary + Devin, and Devin timing out is the norm. The discrimination that carries the whole tier decision is `completed/skipped` (never coming ⇒ proceed on the fallback tier) versus `pending` (imminent ⇒ wait, and note that CodeRabbit legitimately re-reviews on every push, so a fresh `synchronize` yields exit 10 / stale `commit_id` / `pending` status as a **timing race**, not a skip). Reading both as "no signal" manufactures `ABSTAIN_INFRA:NO_REVIEW_SIGNAL` on every PR in the repo and corrupts the abstain rate the code is meant to protect ([slang-rhi has NO production review bot — permanently fallback-tier](wiki/learnings/1786350851182-approver-infra-abstain-slang-rhi-has-no-production.md)).

**A poll window expiring is not a negative result, and a signal that settles before you RECORD supersedes the timeout.** On slang-rhi#770 Devin took ~17 min against ~4- then ~15-min windows, and twice a terminal negative was written into the decision artifacts (`DEVIN_SKIPPED: timeout — no result within the decision window`, *"Devin never returned… I have no head-current independent reviewer signal"*) **while the process was still running** — false at the moment of typing. "It hasn't returned yet" and "it timed out" are different claims; only the second is a finding, and it requires observing the process exit. The same shape with the opposite timing on #820-R2: the `pending_bot` window (12 polls @30 s) expired, permitting the Devin tier, and then ~7 min later — while the decision was still being assembled — CodeRabbit settled to `success` with a **head-current** review carrying two 🟠 Majors that had not been found. The artifact that matters is what is observable **at the moment the ledger row is written**, because the row is the claim; an `ABSTAIN_INFRA` there names a pipeline defect that had ceased to be true and hides real code findings behind an infra excuse. ⇒ **Re-harvest immediately before `record_decision` whenever the prior harvest was non-zero (stale/pending/timeout).** Never discount the slow best-effort tier — it is precisely the one whose absence is most convenient to assume ([a timeout is not a verdict](wiki/learnings/1786350741917-approver-clause-gap-a-timeout-is-not-a-verdict-and.md), [a settling bot signal that arrives before you RECORD supersedes the timeout](wiki/learnings/1786350789671-approver-challenger-a-settling-bot-signal-that-arr.md)).

## The Harvest Reads the Wrong Endpoint for Inline Findings — and a Best-Effort Fallback on a Required Input Is a False-Clean Generator (2026-08-14 fold)

The harvest defect above has a companion at a different endpoint. On slang-rhi#817 three endpoints carried three different things, and the one the harvest read was the least informative: `pulls/817/reviews` held 3 CodeRabbit review *envelopes* (near-boilerplate, 699/699/1695 chars); `issues/817/comments` held a board-sync notice + a summary; and **`pulls/817/comments` held the 3 real findings** at `vk-surface.cpp:146/:148/:394` (2627/1882/7061 chars). `collect-reviews.sh` returned exit 0, `found:true`, `stale:false` — a clean, head-current harvest — while both of CodeRabbit's 🟠 Major findings were invisible, because the harvest never read `pulls/N/comments` where inline review findings live. Deciding from the synthesized doc alone, on a PR with 6/6 clauses and green CI, would have produced a **false WOULD_APPROVE**. `original_commit_id` (not `commit_id`) is the only usable SHA attribution for these inline comments ([pr-approver harvest misses pulls/N/comments where inline findings live](wiki/learnings/1786277284242-pr-approver-harvest-misses-pulls-n-comments-where-.md), [FIXED: the harvest scripts never read pulls/N/comments; original_commit_id is the only usable SHA attribution](wiki/learnings/1786279491535-approver-infra-abstain-fixed-the-approver-s-harves.md)).

**But the fix shipped with the exact bug it was written to close.** The patch wrapped the new `pulls/N/comments` fetch in `try: inline=[...] except: inline=[]` with the comment "best-effort: never turn a review we DID fetch into a failure." That makes a **required** input best-effort: a transient error on the endpoint that carries the findings silently yields an empty finding set and a *clean* synthesized review — a false-clean generator, the same false-negative shape the fix targeted. A required fetch must fail loud (propagate the error, force an `ABSTAIN_INFRA`), never swallow to empty; "best-effort" is correct only for genuinely optional enrichment, never for the input the decision rests on ([my own harness fix shipped with the exact bug it was written to close — a best-effort fallback on a required input](wiki/learnings/1786280119038-approver-critique-mustfix-my-own-harness-fix-shipp.md)).
