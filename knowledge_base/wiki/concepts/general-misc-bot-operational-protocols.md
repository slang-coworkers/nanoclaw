# Bot Operational Protocols and Maintainer Interactions

Operational rules governing how the bot interacts with maintainers and manages recurring workflows: PR watcher task design, self-scheduling restrictions, external dependency triage, design discussion etiquette, and latent defect filing policy.

## TL;DR
- **Put change-detection in a PR-watcher's `script` guard**, not its agent prompt — a "poll → end silently if unchanged" prompt still wakes a full session every fire. Key on state/isDraft/reviewDecision/counts/`ciFailed`, NOT `mergeStateStatus` (it flaps). Don't self-schedule a PR-watcher after `report_pr_created` — the webhook path already covers it.
- **Resolve a chat-reported bug against GitHub BEFORE proposing it as a new issue** — search by symptom, reporter username, and cited pass/file name. An already-filed-and-fixed bug reads as live when it's in the channel's recent-N window and the reporter self-retracted only partially.
- **In maintainer design discussions, be reticent** — contribute evidence, not opinions on direction; the maintainer decides.
- **Surface latent adjacent defects, don't file them speculatively** — a defect you noticed but didn't reproduce is a note to the maintainer, not a tracking issue.
- **Verified GitHub comments/labels are not operator-gated**; a PR ready-flip / merge is. Post the 5-bullet as closest-to-the-state without asking.
- **`nv-slang-bot` (no `[bot]` suffix) is the login; a comment under it may be another agent** — re-read the newest comment live before posting, and check the author before crediting a filing to an external party.
- **A retraction is not applied until you ask where else the claim lives** — sweep derived artifacts (shared files, PR bodies, sibling notes) for the superseded wording, not just the origin.

## PR Status Watcher Tasks: Put Detection in the Script Guard

A `schedule_task` PR-watcher whose agent prompt does "poll → compare → end turn silently if unchanged" still wakes a full agent session on every fire, and any stray scratchpad output leaks toward wired peers. The correct pattern is to put change-detection in the task's `script` parameter (the pre-agent guard), not the prompt. The script polls, compares against a state file on disk, and emits `{"wakeAgent": false}` when unchanged — the agent never runs on a no-op fire. Only a real delta sets `{"wakeAgent": true, "data": {...}}`. The comparison key should include state, isDraft, reviewDecision, review/comment counts, and a `ciFailed` boolean — but NOT `mergeStateStatus`, which flaps `UNKNOWN→BEHIND→CLEAN` with no real change and reintroduces spurious wakes. Pre-seed the state file with current state right after creating the task so the very first scheduled fire does not wake on `prev=null`. ([PR/status watcher tasks: use a pre-agent script guard with a state file, not a per-fire agent poll](../learnings/1780315991721-pr-status-watcher-tasks-use-a-pre-agent-script-gua.md))

## Don't Self-Schedule a PR-Watcher After report_pr_created

When a coworker opens a PR and calls `report_pr_created({ repo, pr_number })`, it must NOT also schedule its own recurring PR-watcher poll task. The host already routes future PR webhook events (review comments, CI status, merge) back to the owning session via the `pr_session_mappings` table that `report_pr_created` writes. A self-scheduled poller is fully redundant with that path. After `report_pr_created`, go fully idle — silence is the correct idle state. If a poller has already been scheduled, `list_tasks` → `cancel_task` it once the PR is open. ([Don't self-schedule a PR-watcher poller after report_pr_created](../learnings/1780339192513-don-t-self-schedule-a-pr-watcher-poller-after-repo.md))

## Triaging External-Dependency Tracking Issues

When triaging a "re-enable this test / remove this workaround once upstream is fixed" tracking issue, two cheap checks sharpen the verdict: (1) verify the suppression PR actually merged — the workaround-adding PR may still be open and not yet on master; (2) locate the concrete upstream tracker and fix PR via `gh issue/pr list -R <upstream> --search "<keywords>" --state all`. Also check for a companion issue filed at nearly the same time (bug-side tracker + cleanup follow-up). The correct verdict for these is enhancement/tracking, low/P3, "handed off — awaiting external dependency." Park the fixer-forward (root defect is upstream, nothing actionable on the Slang side) but still post the verified state on the issue with an ordered resumption trigger. ([Triaging external-dependency tracking issues (verify suppression PR is merged + locate upstream tracker/fix)](../learnings/1782449664675-triaging-external-dependency-tracking-issues-verif.md))

## In Maintainer Design Discussions, Be Reticent

When a GitHub issue or PR thread turns into a high-level design discussion among maintainers/developers, the bot should participate sparingly — contribute only high-value verified facts that are clearly wanted (ideally when directly asked or @-mentioned), not a comment on every turn. If a maintainer says any form of "stop responding / let us discuss / we'll ping you," comply immediately and silently — post nothing further, including no "understood, standing down" acknowledgment, which is itself the noise they are trying to remove. The respectful signal of compliance is silence. Re-engage only on an explicit @-mention of the bot, routed through the orchestrator — not on inferred convergence or an apparent "go ahead" from another participant. ([In maintainer design discussions, the bot should be reticent — and stand down instantly (and silently) when asked](../learnings/1782480236370-in-maintainer-design-discussions-the-bot-should-be.md))

A single maintainer's "go ahead, implement X" is NOT a converged directive when a second maintainer is actively objecting to that same direction and any change is gated on a third's sign-off — the bot NOT implementing is correct restraint, not a dropped/overdue chain. On #11631 pdeayton-nv told the bot to expand draft #11633, but tangent-vector objected and conditioned it on @csyonghe's blessing (which never came); expanding then would have implemented one maintainer's proposal over another's live objection, so #11633 correctly stayed version-half-only. Before flagging a directed-but-undelivered bot implementation as overdue, read the thread for (a) a second maintainer objecting and (b) an explicit approval gate — if either holds, the disposition is "design unconverged, maintainer-owned, do NOT nudge"; the genuine re-escalate condition is the design *converging* and THEN the implementation going silent ([Un-expanded bot task amid unconverged maintainer design debate = correct restraint, not a dropped chain](../learnings/1785399716488-un-expanded-bot-task-amid-unconverged-maintainer-d.md)).

The durable posture for a design fork is **surface-and-defer: never merge an intermediate approach; hold the PR as draft/unmerged through every pivot.** On #9401 (`-target hpp` docs mismatch) the chain ran a ~2-week compiler-change detour (jkwak steered it compiler-side → a target-neutral regression pdeayton caught → a host-scoped re-implementation → an `isPublic`-drop that conflicted with csyonghe's "`export`, not `public`, is the preserve trigger") and landed back EXACTLY on the original docs-only triage verdict — merged as a clean single docs commit (#12242) with nothing to unwind precisely because no intermediate compiler design had shipped. Two load-bearing corollaries: a "docs-only vs compiler-fix" triage call can be right even when a maintainer initially steers compiler-side (implement what they ask, but keep surfacing the regressions/gaps that may bring them back), and **CI-green never resolves a design-scope objection** — #12242 was green while the scope conflict was still open, and the approver's BLOCK on that scope question was vindicated by the human outcome, not the test suite ([Surface-and-defer on maintainer design forks: never merge an intermediate approach](../learnings/1785469148746-surface-and-defer-on-maintainer-design-forks-never.md)).

## Contributor Interactions: Warm Brevity, Ownership Signals, and Dedup Races

When a would-be contributor simply offers to raise a PR on a community issue ("I'd be happy to raise a pull request if that helps?"), reply with a SHORT, warm acknowledgment — "yes please, that'd be very welcome, happy to support you through it." Do NOT front-load a multi-paragraph technical triage dump or a separate proactive workaround comment: it misreads intent (someone volunteering to fix the root cause doesn't need a `SLANGC_PATH` workaround) and forces a maintainer to clean up the tone (slang-torch#46: @szihs apologized on the bot's behalf for jumping straight to a workaround "far longer than it needed to be"). Reserve the full technical playbook for the PR review itself, and when a maintainer has already responded to the contributor, don't add a bot comment on top — the maintainer owns the relationship ([Contributor PR offers get a brief warm yes, not a triage dump](../learnings/1783439199713-contributor-pr-offers-get-a-brief-warm-yes-not-a-t.md)).

A **contributor-authored** cleanup/tech-debt issue can get self-fixed concurrently — the person who filed "remove dead code X" is often about to delete X themselves. On #11928 the author opened their own PR covering both parts and self-merged it, closing the issue and stranding our maintainer-approved bot PR (a wasted fix+review cycle). Dedup-search is not one-and-done at triage: the fixer/triager should re-run `gh pr list -R <repo> --search "<file-or-keyword> in:title,body" --state all` (and `--search "author:<issue-author>"` when the author is a contributor) immediately before opening the bot PR. When a competing author/maintainer merge supersedes our approved PR, that's a terminal state that revises any "awaiting merge" resolution — refresh the artifact and send ONE corrected note; the triage still has value if the analysis matched the merged fix ("sound analysis, lost the authorship race") ([Contributor-authored cleanup issues can get self-fixed concurrently — dedup-search right before dispatching a bot fix](../learnings/1783416692832-contributor-authored-cleanup-issues-can-get-self-f.md)). A reusable ownership heuristic: when the same contributor authored a feature's tutorial PR, design doc, AND runtime tests, a companion "add an example" issue they file is almost certainly their own follow-up — treat the fixer handoff as OFFER-ONLY / hold-for-confirmation rather than autonomously writing ~1000 LOC (and note that a "largely assembly, code already exists" framing can be true for the dispatch machinery but false for the output tail that lives only in merged example hosts) ([Slang coverage examples: dispatch is reusable but manifest/LCOV tail is not in the unit tests](../learnings/1783455979540-slang-coverage-examples-dispatch-is-reusable-but-m.md)).

## Resolve a Chat-Reported Bug Against GitHub Before Proposing It as a New Issue

A Discord/Slack bug report that is *already filed and already fixed* can read as a live, unfiled defect — especially when the messages are still inside the channel's recent-N window (so they look current) and the reporter **self-retracted only partially**. On the 2026-08-04 slang sweep, `crossvr` (2026-07-29) reported that after `InterlockedAdd`, `slang-ir-byte-address-legalize` retyped **all** `RWByteAddressBuffer` to `RWStructuredBuffer<uint32_t>`, leaving byte offsets where element indices were expected → OOB reads. He then retracted the *regression* framing twice ("not a regression"; "seems to be intended behavior, false alarm") but **kept the silent-corruption concern going** — so the thread reads as "regression framing retracted, corruption claim still standing and unfiled," a compelling "should we file this?" shape. Reality: it was issue **#12265**, filed by the reporter the same day, **closed 2026-07-31 via merged PR #12267** — root cause exactly his hypothesis (`babType->replaceUsesWith(...)` on the shared, deduplicated type inst flipped every buffer), fix gated the `IRParam` branch on `translateToStructuredBufferOps`. **Before reporting any chat-sourced bug as new/unfiled, search the issue tracker** — by symptom keywords, by the reporter's username, and by the pass/file name they cite; a one-call `github_search_issues` is far cheaper than a false "needs a GitHub issue" ([resolve a chat-reported bug against GitHub before proposing it as a new issue](../learnings/1785831640500-resolve-a-chat-reported-bug-against-github-before-.md)).

## Docs-Discoverability Issues: A Clear Answer Can Be the Whole Fix

For a docs/discoverability issue, a genuinely clear, source-verified public answer is often the whole fix — the reporter (or a maintainer) may prefer to land the doc change themselves, in the file *they* consider canonical. On #12286 (how to specify a capability via the compilation API) triage posted the `CompilerOptionEntry` recipe and the fixer opened a small clarification PR (#12287), but the maintainer CLOSED the bot PR not-merged in favor of **#12295, authored by the original reporter himself** once he understood the answer. A bot PR closed-not-merged in favor of a contributor's own PR is a POSITIVE terminal outcome — ack graciously, stand down, do not contest — but the triager MUST refresh its in-place issue comment to point at the surviving PR and drop the dead one (verify both via `gh`: state, `mergedAt=null` for closed-not-merged, `closingIssuesReferences`) so the public footprint doesn't misdirect ([Answering a docs/discoverability issue clearly can prompt the reporter to self-fix — leave room for it](../learnings/1785435644251-answering-a-docs-discoverability-issue-clearly-can.md)). A related maintainer-taste rule from the same issue: user-facing "how do I do X via the API?" prose belongs in `docs/user-guide/` beside an existing example, NOT as an expanded comment on the public header `include/slang.h` — the header documents the API surface/ABI, not usage recipes. jkwak-work rejected the `include/slang.h` doc-comment expansion on #12287 ("This is not a user facing document") even after peer/codex review had APPROVED it, so the PR reverted the header change and stayed docs-only; a terse "see user guide" pointer may be OK, but don't grow header comments into tutorials, and note the review gates don't catch this taste call ([Header comments in include/slang.h are not the place for user-facing how-to docs (jkwak)](../learnings/1785425239946-header-comments-in-include-slang-h-are-not-the-pla.md)).

## Before a Cross-Cutting Fix, Grep Open PRs — Including Our Own Bot's

Before prototyping/proposing a fix that touches a shared IR pass (peephole, SCCP, simplify, legalize, lowering) — especially one a maintainer frames as "the more principled place" — grep the OPEN PR list for the same file and the same fold/op, INCLUDING PRs authored by our own bot identity across other sessions (`gh pr list -R <repo> --search "<filename> OR <op-name>" --state open --json number,title,author,files`). On #12110/#12116 a prototype peephole fold in `slang-ir-peephole.cpp` rediscovered work already in flight in **our own bot's PR #12263 from a different session**, which added the exact same fold. Two PRs adding the same rule conflict and confuse reviewers; the bot runs many parallel sessions, so "is anyone — including past-me — already doing this?" is a real question, and one `gh pr list` grep is far cheaper than a wrong-layer proposal. Corollary: when a maintainer says a fix "conflates a separate concern," treat it as a strong hint the separated concern already has (or should have) its own PR — look for it before defending your approach ([Before proposing a cross-cutting IR fix, check for an in-flight bot PR touching the same pass](../learnings/1785443375063-before-proposing-a-cross-cutting-ir-fix-check-for-.md)).

## On a PR Under Review: Incremental Commits + Merge Master, Never Force-Push a Rebase

When iterating on a PR that is under active review, bring the branch current and add changes via incremental commits + `git merge origin/master` — do NOT force-push a rebase (maintainer directive, jhelferty-nv). Rebasing mid-review rewrites history, which loses reviewers' incremental-diff view (a reviewer who saw commits 1–3 can no longer see "what changed since my last review") and guarantees dismissal of any live approval by rewriting every SHA, re-triggering a full CI rebuild. Apply: review-round edits → new commit on top (`git push`, no `--force`); branch behind master → `git merge origin/master` (a merge commit), not a rebase; reserve rebase/force-push for pre-review cleanup or an explicit maintainer squash request. This corrects the older per-round "amend + force-push" habit and applies to ALL PR work — observed repeatedly on 2026-07-31 (e.g. #12263, where a cleanup push dismissed pdeayton's fresh approval). When a branch is BEHIND but already approved, the cleanest path is often the maintainer's own GitHub "Update branch" merge rather than a bot rebase ([On a PR under review: incremental commits + merge master, never force-push a rebase](../learnings/1785520732879-on-a-pr-under-review-incremental-commits-merge-mas.md)).

## Latent Adjacent Defects: Surface, Don't File Speculatively

When triage uncovers a latent, adjacent defect (by code-reading) that is out of scope of the reported issue, and the reported issue is being resolved by an unmerged PR, do not speculatively open a separate tracking issue. Reasons: the covering PR may change the adjacent code's post-merge state (premature); a code-read flag is not a confirmed user-visible repro (unverified); and surfacing it in the public resolution comment ensures maintainers landing there already see it (not lost). File a fresh issue only if/when the covering PR merges AND the adjacent path still misbehaves with a verified repro. Never open speculatively — filing a new issue is a visible shared-state action that needs authorization anyway. ([Latent adjacent defect found by code-reading: don't file a speculative tracking issue while the covering fix is an unmerged PR](../learnings/1782156945737-latent-adjacent-defect-found-by-code-reading-don-t.md))

## Verified GitHub Comments/Labels Are Not Operator-Gated

On the shader-slang bot (nv-slang-bot), verified issue/PR **comments, labels, Type field, review replies, and emoji reactions post FREELY** on the bot's authority once the relevant state is checked at HEAD — they are NOT operator-gated. The narrow operator-gated set is only `gh pr ready`, `gh pr merge`, and never auto-closing issues/PRs (pushing code to your own `fix/issue-*` branch is also free). Restated by the orchestrator 2026-07-01 after a fixer *declined* posting a legitimate "fix in draft PR #N" note as if it were gated: holding back on legitimate GitHub posting is itself the failure mode — it starves issues/PRs of the public footprint humans need, and older per-fix notes claiming "PR/issue comments are operator-gated" are superseded. When a state change warrants a comment (the 5-bullet on PR-open / resolution / handoff, a review reply, a label, a reaction), just post it after verifying current state at HEAD — do NOT route through `ask_user_question` or hold for approval; reserve the approval flow for ready-flips, merges, and anything that would close an issue/PR ([Verified GitHub comments/labels are NOT operator-gated — only pr-ready/merge/auto-close are](../learnings/1782894060592-verified-github-comments-labels-are-not-operator-g.md)).

## Persist Parent-Agreed Gates and Ownership Claims; Edit-in-Place When Last Commenter (2026-07-12 fold)

Two protocols that survive respawn only if written to durable state. A parent-agreed timing gate ("hold the #12052 nudge until ~17:30Z") is BINDING — hold until X unless you surface what changed FIRST; the failure mode is post-respawn amnesia (a respawned session's `rerun-tracker.json` held the OLD plan while the later deferral was never persisted, firing the exact cry-wolf timing the deferral existed to skip). Persist any parent-agreed gate into the tracker immediately (a respawn sees only disk); a later agreement OVERRIDES an earlier tracker plan for the same PR ([persist parent-agreed timing gates; flag before acting early](../learnings/1783779488465-persist-parent-agreed-timing-gates-flag-before-act.md)). Same for ownership — when the parent says "I've got this," write it into the tracker (`owner:"PARENT"`, `do_not_re_escalate:true`) or two escalators ping the operator twice. And comment hygiene: if your bot was the most recent commenter on the SAME item, EDIT the existing comment (`gh api -X PATCH .../issues/comments/<id>`) rather than stacking a second; only post fresh when a human/other author commented in between ([edit-in-place when you were last commenter; persist parent ownership-claims to tracker](../learnings/1783807636828-edit-in-place-when-you-were-last-commenter-persist.md)).

## Correction Hygiene: A Retraction Is Not Applied Until You Ask Where Else the Claim Lives (2026-08-03/04 fold)

**Correcting is the highest-risk posture the bot occupies.** The failure is not "we were wrong once" — it is that a retraction issued in one place leaves the superseded claim standing everywhere a reader actually lands, and that the act of correcting someone else invites a fresh overclaim of your own.

**Enumerate surfaces before declaring a correction done.** On slang-rhi#800 both Main and `slang-pr-approver` retracted the same claim (that Devin's Metal residency 🔴 had been *refuted*) and both reported the chain closed. It wasn't: the retracted framing was still live on **seven** surfaces under `/workspace/shared/` feeding every coworker's Step-0 recall — the root learning atom (title *and* body), its `wiki/` mirror with its own frontmatter `title:`, a third `sources/` copy, **two** sections of a synthesized concept page (one presenting the case as the *archetype* of a false-positive refutation), `wiki/index.md` + topic pointer lines, and a later atom that had built on the retracted claim. Fixing one file left six teaching the error. The checklist: private notes → shared atoms → mirrored copies → synthesized wiki/concept pages → index and topic pointer lines → frontmatter `title:` → embedded JSON ([a correction is not applied until you ask where else the claim lives](../learnings/1785774600509-a-correction-is-not-applied-until-you-ask-where-el.md)).

Two mechanisms make this invisible to a normal self-check. **You grep your new wording** — a pattern that structurally cannot match the stale text (written in the old vocabulary); grep the **superseded terms**, and under append-only, quote the retracted sentences *verbatim* so a search for the old words lands on the fix. And **derived layers inherit and re-frame** — a corrected atom under a heading like `## False-positive refutations` still teaches the wrong lesson because framing/titles/index lines surface first; sweep headings, titles, tables, and index rows, not just prose.

**A correction has TWO verifications and they are different queries.** *Negative:* the superseded wording is gone from every surface (grep the **OLD** vocabulary). *Positive:* the replacement is **present** on every surface that needs it, including tiers you don't own (grep the **NEW** vocabulary). The negative half alone leaves a **hole rather than a wrong answer** — nothing contradicts an absent claim, so it survives review; and **a conclusion stated in a message is not a recorded surface**. **Retract at paragraph granularity** (on #800 the residency taxonomy survived; only the inference that it cleared the finding was retracted), and verify negative sweeps with a **positive control** (a zero-hit sweep proves nothing if the pattern is broken).

**Narrowing a claim is not testing its premise.** The #800 chain retracted "the fallback is unexercised" and rewrote it as "the fallback is unverified" — weaker, same direction, same untested premise (*which residency path does CI actually take?*). A retraction that narrows without testing the premise **inherits the error and launders it as diligence**; here the settling observation was one unauthenticated `curl` of a public job log. Ask what observation would settle it, and whether it is cheaply available, before recording either version.

**Correcting is when your own guard drops.** Two instances: (a) a false absolute (*"structurally cannot"*) produced *while correcting someone else's overclaim* — distrust "impossible"/"always"/"structurally cannot" in your own output, especially right after "actually, no." (b) On slang#8785 a self-correction fixed the headline rule but got its own worked example wrong, reasoning from **code shape** (two sites, same five steps, verified line-for-line) to "same assert fires on both targets" — when SPIR-V fails an *arity* assert upstream and Metal fails the *null* `payloadPtrType` assert: **one front-end root cause → two distinct downstream failure modes**, not "one null, two build configs." The first empirical run had printed both assert texts side by side, discarded when the tidier story was adopted — **when a neat mechanism contradicts a detail you already measured, the measurement wins**; verify per-target by *running each target*, not diffing source. "N signatures" is a hypothesis in both directions — over-count causes *and* under-count mechanisms are both live ([same code shape ≠ same failure mode](../learnings/1785804652829-correction-to-n-crash-signatures-learning-same-cod.md)). Instrument corollary: **check a prebuilt binary's mtime against the HEAD commit date before citing an assert's file:line** — a 5-hour-stale `slangc` reported `:5182` where current source has `:5235`.

Two ownership facts that shape the repair path: `/workspace/shared/` is **Main-write-only**, so a coworker that finds a stale shared claim can only report it — Main must treat such a report as a **work item, not an acknowledgement**; and a coworker whose own atom is wrong cannot edit it, so its correction must be filed as a new atom that *names the file it supersedes* and asks for the fold.

## `append_learning` Mechanics: the Title Becomes H1, and the INDEX Is Lossy

Two write-site rules for the shared-learnings store, both measured rather than assumed.

**Never start `content` with a heading.** `append_learning({title, content})` writes `# <title>` as **line 0** and appends `content` beneath it, so any `# Heading` at the top of `content` lands as a **second H1**. Proof it is the injected title and not author text: the filename slug is derived from the `title` argument, so compare it against each H1 — across 153 dup-H1 files, **153/153** slugs derive from the FIRST H1 and **0** from the second. Scale: 153 of 2025 files (~7.6%), many authors, months of timestamps; 16 are verbatim restatements and **137** are cases where the author wrote a *better, more specific* second heading than the title they passed — i.e. the common shape is not sloppiness but authors treating `content` as a standalone document. **Fix at the write site:** first line of `content` is `##` or prose; if the title isn't good enough to be the document's H1, fix the `title` argument. Not worth mass-repairing (cosmetic, both headings render, and a 153-file blind edit is a large risky write while the generator keeps producing more). Meta-note worth keeping: the bot was told this was "a generator bug, not your editing — you couldn't have prevented it." Half right, and the wrong half is the actionable half — **being absolved of a defect is not the same as the defect being unpreventable**, and the two framings predicted different filename-slug distributions, so the claim was testable for the cost of one command ([append_learning injects the title as H1 — never start content with a heading](../learnings/1785774989369-append-learning-injects-the-title-as-h1-never-star.md)).

**A standing gap note names a SYNTAX; the severity lives in the EDGES — characterize the population before scoping or triaging.** The `/learnings-wiki` daily-sync task description carries a KNOWN GAP saying "the 42 concept pages use `[[wiki/…]]` wiki-link syntax, which GitHub renders as literal text, not links." Read literally that says concept-page **citations** are dead in the published KB — i.e. the wiki's core navigation (concept → its source learnings) is broken. Measured on the published `knowledge_base/wiki` after sync #1062: **58 `[[wiki/...]]` occurrences across 48 files**, of which 47 are the per-page nav footer `[[wiki/index.md]]`, 9 are concept↔concept cross-links, 1 a topic link, and 1 sits inside a `learnings/` page *quoting* the syntax. Concept→learning citations rendering as dead `[[…]]`: **0**. Why: `finalize()` runs `_convert_obsidian_links()`, which rewrites the `[[wiki/learnings/…]]` form → markdown, but **only that prefix and only in `wiki/concepts/*.md`** — so the citation edges (the load-bearing ones, and the ones the coverage validator counts) are always converted while `[[wiki/index.md]]` and `[[wiki/concepts/…]]` fall outside the regex and survive. One command answers it: `grep -rho "\[\[wiki/[a-z]*[/.]" | sort | uniq -c`. "Citations are broken" and "47 nav footers are cosmetically dead" are the *same syntax fact* with wildly different priorities — so **triage by target kind, not by syntax**. The mechanical fix is the same depth-aware rule as the `](wiki/…)` fixup (subdir pages get `../`, root pages a bare path); the right fix is widening `_convert_obsidian_links()` to all three prefixes so the generator stops emitting them, rather than patching downstream every sync. Corollary in the same note: it said "42 concept pages" where there are **47** — **a count inside a standing instruction ages; recompute it rather than quoting it forward** ([the learnings-wiki obsidian-link gap is nav-only, not broken citations — characterize before scoping](../learnings/1785824164229-learnings-wiki-obsidian-link-gap-is-nav-only-not-b.md)).

**The generated `INDEX.md` title is lossy in three ways, so write for the loss and search for it.** The title→slug transform **strips punctuation** (`m_hasResidencySet` → `m hasresidencyset`, `SLANG_RHI_METAL_NO_RESIDENCY_SET` → `slang rhi metal no residency set`), **lowercases** (`Apple6` → `apple6`), and **truncates to ~50 chars**. Measured on one token-loaded entry: of four front-loaded identifiers only **one** literal search hit — `grep Apple6` → 1, `grep m_hasResidencySet` → **0**, `grep NO_RESIDENCY_SET` → **0**, `grep useResource` → **0** (cut at `useresou`). So *when searching*, grep the INDEX **case-insensitively, without punctuation, on a fragment** — searching the exact symbol you have in mind is precisely how you manufacture a false negative, and a false negative here reads as "no prior art," which is what caused the original inversion. *When writing*, put the distinctive **word stem** early (`apple6`, `residency`, `useresource`), assume ~50 chars and no punctuation, and verify after writing by grepping the normalized form rather than assuming the append worked. `INDEX.md` is **generated**, so hand-written blocks in it are destroyed by the next `append_learning` from anyone — the only durable channel is the title, and the title is normalized: **the fact must be findable via a lowercase, punctuation-free, <50-char fragment, or it is not findable at all** ([append_learning INDEX titles are normalized — grep case-insensitively without punctuation](../learnings/1785779281289-append-learning-index-titles-are-normalized-unders.md)). Related read-only-mount caveat: coworkers cannot verify a `[[slug]]` resolves, so they should quote the target's **title** in prose and let Main wire the link.
