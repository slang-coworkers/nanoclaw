## TL;DR

- **statusCheckRollup can report 0 failing while `commits/<sha>/check-runs` reports 2.** The rollup dedupes by job name and surfaces a `skipped` duplicate over a `failure`. For any negative/zero claim ("0 failing"), prefer the *enumerating* endpoint (`check-runs?per_page=100`), never the aggregating one.
- **A draft shader-slang PR can never get CI while the branch is active.** Draft PRs get no `pull_request` CI by design; the bot's `workflow_dispatch` runs yield to human priority; and each push disqualifies the prior yielded run from retry — so *responding attentively to review is what starves the CI you're waiting for.*
- **Release CI green always lags master, by design** — a merge queue means every master commit already has a `merge_group` CI run at its exact post-merge SHA. Escalate an uncovered commit only when its risk intersects what `release.yml` uniquely adds (LTO, macOS x86_64, Windows aarch64, system-LLVM).
- **Two shader-slang nightlies have adjacent ids, identical retained totals, and inverted meaning** — never quote a nightly figure without naming its workflow id. `36` is a retention floor, not streak age.
- **A whole-day ratio on a host that changed state mid-day is a window artifact** — the newest terminal rows carry the verdict; bucket `cancelled` as UNTESTED.
- **Grep log markers verbatim** — `spirv-val [ 0 / 866 ]` has inner spaces the compact form misses; a future `[ 0 / 866 ]` on a recovered host is a regression to re-open, not a silent rerun.

## Two API views of the same fact disagree — trust the enumerating one

On PR #12382 `gh pr view --json statusCheckRollup` reported 0 failures while `commits/<sha>/check-runs` reported 2 (`check-ci`, `wait-for-human-priority`). Each job name exists **twice** on the same head in different check suites — one `failure`, one `skipped` — and the rollup dedupes by name, surfacing the `skipped` one, so the failure vanishes from that view. Two dispatches on one head (an auto `pull_request` run plus a manual `workflow_dispatch`) reliably produce this shape. An empty rollup reads as "clean" — the most reassuring possible output, emitted in the same format whether or not anything failed. **The reusable half:** when two API views of the same fact disagree, the one that *dedupes or aggregates* is the one that can silently drop a value; prefer the enumerating endpoint for any negative/zero claim, and "0 failing" is a negative claim. Histogram first (`group_by(.conclusion)`), and `per_page=100` matters — the default page truncates a large matrix into a *different* false clean. Classify the failures: `check-ci` + `wait-for-human-priority` with all `build-*`/`test-*` skipped = benign priority yield; any `build-*`/`test-*` `failure` = real. ## Draft-PR CI starvation

"CI keeps yielding" on a **draft** shader-slang PR is not a transient queue state — it is structurally unreachable while the branch is active, from three facts verified at source: (1) a draft PR gets **no `pull_request` CI at all** — `ci.yml`'s `filter` job is gated on `draft != true` and all build/test jobs `needs: filter`, so those runs are `completed/skipped` (never read those skips as coverage *or* as a problem); (2) the bot's `workflow_dispatch` runs **yield to human priority** (`wait-for-human-priority: failure` + `check-ci: failure`, everything else skipped, reason `priority-gate-yielded`, benign); (3) **the retry never fires while the branch is active** — `retry-yielded-bot-ci.py`'s `has_newer_run_for_branch` skips any run with a higher `run_number` on the same branch, so **each push simultaneously creates a new yielded dispatch and permanently disqualifies the prior one.** The counter-intuitive consequence: *responding to review is what keeps resetting the retry clock* — five heads over ~1h (one a byte-identical commit-message amend) produced zero build/test jobs. How to apply: don't hand "nudge CI" to the fixer (route it to the operator as a draft-flip-or-quiet-window decision); a local build of the head is load-bearing (may be the only build evidence), stated at its true scope (one config is a smoke test, not the full matrix); prefer PR-description edits to commits while waiting; batch review responses into one push; and timestamp every CI reading. Enumeration trap: `gh run list --branch <b>` misses SHAs amended away (they're no longer on the branch) — count via `commits/<sha>/check-runs` per SHA from push history. ## Release CI lag is the designed steady state

Do not treat "master has N commits on top of the tested SHA" as a coverage hole. The 00:00 UTC release-CI dispatch builds whatever master HEAD is then; commits keep landing during the ~50-min run (gaps between 10 consecutive dispatches: 2,4,4,7,8,8,3,1,6,5 — median ~5, so a 1-commit gap is the *smallest* observed). It is deliberate and self-documented (`release.yml` triggers only on `workflow_dispatch` + `v20*` tags). **Slang runs a merge queue, so a master commit is never actually unverified** — every commit has a `merge_group`-event `CI` run at its exact post-merge SHA (36/36 green, verified on `ff45b15e`). Escalate an uncovered commit only when its risk intersects what `release.yml` *uniquely* adds (grep-verified absent from `ci.yml`): `SLANG_ENABLE_RELEASE_LTO=ON`, `--fresh` uncached builds, `USE_SYSTEM_LLVM`, macOS x86_64, Windows aarch64. A pure IR-pass/frontend change is fully exercised by the merge-queue run — no spot dispatch. Incidental corrections: release CI is ~50 min (not the "1-3 hours" role instructions claim), and a PR commit's `committer.date` (when the merge queue *built* the object) can precede real `merged_at` by hours — cite `merged_at` when ordering a merge against a CI run. [Slang release CI green always lags master — merge_group CI is the real per-commit gate](../learnings/1785894855097-slang-release-ci-green-always-lags-master-merge-gr.md)

## Nightly workflows: adjacent ids, inverted meaning; window-artifact ratios

**Never quote a shader-slang nightly figure without naming its workflow id.** Two nightlies have adjacent ids, the same retained total, and opposite meanings: `304423282` (Nightly Slang Test — single `agentic-tests` job, an LLM-generated doc-anchored suite, *not* the compiler suite) read 35 FAILURE, while `304423283` (Nightly Slang VKGLCTS Test) read 35 SUCCESS. An unlabelled "35 of 36" on either thread reads as its own opposite. Quote as `35/36 (workflow 304423283)`; `36` is a **retention floor**, not streak age (the Actions API can't distinguish "workflow created then" from "older history purged"). VKGLCTS is not a pool lottery — `runner_name` was SLANGWIN5 on 36/36 including the single red, so a streak-then-break isolates a change on that box. Two caveats that nearly became false public claims: residency is measured but the *cause* (the `vulkancts` label) is inferred; and `/actions/runs/<id>/logs` returns 403 unauthenticated, so any claim sourced from log text is *inherited* from whoever could read the logs — attribute it, never restate it as your own measurement. [Two shader-slang nightly workflows: adjacent ids, identical totals, inverted meaning](../learnings/1785882757450-two-shader-slang-nightly-workflows-adjacent-ids-id.md)

A **whole-day ratio on a host that changed state mid-day is a statement about the window, not current health.** On SLANGWIN5 the `spirv-val [ 0 / 866 ]` failure recovered ~21:45Z; the day-wide ratio (~19% pass) under-reports the recovery, a last-15-runs ratio (~50%) over-reports it, and both are arithmetically correct while misleading in opposite directions — the newest terminal rows are the actual signal. Bucket `cancelled` as **UNTESTED**, never as pass or fail. Two operational rules: grep the log marker **verbatim** — the emitted `spirv-val [ 0 / 866 ]` has inner spaces the fluent compact form (`spirv-val \[0/866\]`) misses, returning a confident zero; and a future `[ 0 / 866 ]` on this recovered host is a **regression of a closed issue — re-open it, don't silently rerun** (silent rerunning is how a resolved-then-regressed infra defect goes invisible). Verify recovery from job logs, not run-level `.conclusion`.
