# SlangPy Torch Autograd: Bridge, Cache Signature, and Grad-Buffer Binding

The SlangPy↔PyTorch autograd path is a thin marshalling layer over the Slang compiler's `bwd_diff`. A cluster of 2026-07 issues (#1051, #1052, #1055, #1056) mapped its two failure surfaces precisely: **(a) bugs in the *body* of a user's `[Differentiable]` function belong upstream in the Slang compiler, not SlangPy**, and **(b) SlangPy's own defects live in the CallData cache signature and dispatch-time grad-buffer binding**, not in kernel codegen. This page is the marshalling-layer companion to [[wiki/concepts/slang-autodiff-ir-autodiff-differentiation.md]] (the compiler-side transpose/loop bugs those issues escalated to).

## TL;DR

- **The delegation boundary:** SlangPy does no loop/induction/`MaxIters`/unroll handling — a `.bwds()` crash or wrong gradient that reproduces identically across Metal + CUDA + Vulkan **and** on both the pure-Tensor and torch paths is a single shared cause below SlangPy = the Slang compiler autodiff pass. Set Upstream-Slang=yes, escalate.
- **Diagnostic split for silently-wrong gradients:** does the SlangPy-generated code differ by the triggering variable (return arity, loop presence)? Backward codegen is structurally identical for scalar vs vector return, and the torch interop validates-then-passes-through `grad_output` unmodified (throws on mismatch), so a silent mis-scale cannot originate there → it's the compiler's reverse-mode transpose.
- **SlangPy's own two defect surfaces are the CallData cache signature and dispatch-time grad-buffer binding, never kernel codegen.**
- **Cache-key review lens: a cache key is correct iff it encodes a SUPERSET of what any dispatch-time frozen decision depends on.** Under-keying is the bug class (e.g. `[Dn,Sm]` omitting `requires_grad` froze `torch_autograd=False` → silent hook drop, #1052); over-keying only costs extra entries. Fix = append the grad bit to BOTH the native and fallback signature functions in lockstep.
- **A "grad" crash ≠ a silent hook drop.** #1056 crashes on the first call in a fresh process (no cache entry to mis-key) — the fault is dispatch-time buffer *binding*: the backward kernel scatters `_grad_out` unconditionally (bind is keyed on `CallMode`, not per-tensor `requires_grad`), but dispatch binds a grad buffer only for `requires_grad=True` inputs → dangling pointer.
- **A grad-buffer bind for a no-grad input must be UNCONDITIONAL, not CUDA-gated** — non-CUDA RAISES when a diff tensor lacks grad_out (strict path), CUDA faults (permissive path); both need the buffer. `PrimalTensor` (conforms to `IDiffTensor`, no `_grad_out`) is the principled zero-alloc fix over a scratch buffer, but needs `requires_grad` threaded into type resolution + kernel signature.
- **`has_grad_fields` is per-PARAMETER (set from the Slang type NAME), not per-tensor grad state** — a DeepWiki claim that a no-grad input binds `PrimalTensor` holds only for `CallMode.prim`, not backward.
- **Any signature-format change bumps `TENSOR_BRIDGE_API_VERSION`, and the second of two in-flight format PRs to merge bumps AGAIN** — the compat gate checks only api_version + struct size, so a same-number collision lets a stale bridge emit the wrong format silently (#1054 must go to v10 over #1162's v9).
- **Exercise BOTH bridge paths on any torch change:** native (`slangpy-torch` pip pkg) and Python fallback must produce byte-identical signatures. The `torch_bridge_mode` fixture auto-parametrizes; grep `D[0-9]+,S` to catch both bracketed and tuple signature-test forms. `device="cuda"` under a `device_type` parametrize is correct idiom (torch storage is CUDA, imported via `cuda_interop`), not CUDA-only masking.
- **A user-built output `diff_pair()` in explicit `.bwds()` gets its grad wired as written, never read (#1265):** `diff_pair` always sets `is_input=True`, so CUDA hits an illegal address and Vulkan returns zero input grads. Workaround: `NativeTorchTensorDiffPair(y, gy, -1, False)`. Coverage only through `debug_build_call_data` never dispatches and is not runtime coverage.
- **A new torch dtype needs an SGL `ScalarType` member first (bf16, #1260/#1261):** SGL's enum mirrors Slang's `SLANG_SCALAR_TYPE_*` and ended at 15, so Slang 2026.20's BFLOAT16=16 / FP8=17-18 raise `ValueError` on every `.scalar_type` read and index the `[COUNT]` cursor tables out of bounds. A torch-side mapping alone cannot work.
- **Run new-dtype torch tests on Vulkan in fallback mode:** the fallback bridge's copy helpers run only on non-CUDA devices, so CUDA-only runs never exercise them. Build the native `slangpy_torch` against a torch whose CUDA major matches local nvcc.
- **#827 scalar-return torch ICE (`WTensor<T,0>`):** `calldata.py` sets `return_type=torch.Tensor` unconditionally before `call_dimensionality`. Approach A (guard on `call_dim>0`) is INCOMPLETE — `call_dim==0` also covers aggregate returns (`float3 add_vectors`), so it regresses 16 tests; the discriminator must be "scalar element type at dim 0" (ScalarType), or adopt Approach B (0-D torch returns end-to-end, matching torch's own convention).

## Delegation boundary — bwds body bugs are upstream

SlangPy does NO loop/induction/`MaxIters`/unroll handling. For backward, `slangpy/core/generator.py::_emit_trampoline` (~L716) wraps the user fn in a `[Differentiable]` trampoline and `_emit_kernel_body` (~L878) emits `bwd_diff(_trampoline)`; the C++ `NativeCallData::exec` + `autograd_backward` are pure marshalling/dispatch. The user's function body is an opaque black box SlangPy cannot rewrite. **Triage signal:** a `.bwds()` crash or wrong-gradient that reproduces identically across Metal + CUDA + Vulkan AND on both the pure-Tensor and torch paths = a single shared cause below SlangPy = the Slang compiler autodiff pass. Set Upstream-Slang=yes, escalate ([SlangPy delegates all loop reverse-mode autodiff to the Slang compiler (bwd_diff) — bwds crashes are usually upstream](../learnings/1783873232594-slangpy-delegates-all-loop-reverse-mode-autodiff-t.md)).

The stronger source-traced version of this rule, for *silently-wrong* gradients: SlangPy's backward codegen is structurally identical for scalar vs vector return (same trampoline + single `bwd_diff` call, no multi-component special-casing — `generator.py:566-618,877`; `boundvariable.py:503-593`), and the torch interop passes `grad_output` through UNMODIFIED after a shape *validation* that would THROW on mismatch (`slangpy.cpp:542-609`) — so a silent mis-scale cannot originate there. The diagnostic split: does the SlangPy-generated code differ by the triggering variable (return arity, loop presence)? If not, and the torch path validates+passes-through, the bug is the compiler's reverse-mode transpose (case: #1055 → slang#12071; precedent: slang#12070) ([SlangPy vector-return autodiff bug triages to slang-core transpose, not front-end](../learnings/1783881108388-slangpy-vector-return-autodiff-bug-triages-to-slan.md)).

## Defect surface 1 — CallData cache signature (#1052, silent hook drop)

A `[Differentiable]` function called FIRST with torch tensors that don't require grad permanently drops the autograd hook: every later `requires_grad=True` call of the same ndim/dtype returns `grad_fn=None`, and `loss.backward()` fails. Silent. **Root cause:** the torch-tensor cache signature is `[Dn,Sm]` — ndim + scalar_type ONLY; `requires_grad` is read into the tensor-info struct but never written to the cache key (native `torch_bridge_impl.cpp:117-129`; fallback `bridge_fallback.py:88`). The autograd hook is gated at dispatch on the CACHED `call_data->is_torch_autograd()` flag, frozen at Phase-2 build time by `detect_torch_tensors` — so a no-grad first build caches `torch_autograd=False` under `[Dn,Sm]`, and same-shape grad calls hit it → hook bypassed. This explains the asymmetry: no-grad→grad broken, grad→grad OK, grad→no-grad OK ([slangpy torch call-data cache ignores requires_grad (autograd hook dropped)](../learnings/1783875433681-slangpy-torch-call-data-cache-ignores-requires-gra.md)).

**Fix (PR #1054):** append a grad bit to BOTH signature functions in lockstep, `[Dn,Sm]`→`[Dn,Sm,Gk]`. The review lens that settles correctness of any cache-key change: **a cache key is correct iff it encodes a superset of the information any dispatch-time frozen decision depends on.** Under-keying (key omits something a frozen flag depends on) is the bug class; over-keying only costs extra cache entries. A per-tensor grad bit is a strict superset of the call-level OR-reduce that gates the hook, so it's correct and simpler to land than a call-level bit ([SlangPy cache-key granularity review lens: key must be a superset of what dispatch gates](../learnings/1783879708151-slangpy-cache-key-granularity-review-lens-key-must.md)). **Version-bump collision (as of 2026-09-30):** main carries `TENSOR_BRIDGE_API_VERSION 9` from #1162 (merged 2026-09-15, the #1091 rank>64 fix), while draft #1054 also claims v9 for its different `[Dn,Sm,Gk,V...]` wire format and is now DIRTY. The compat gate (`src/slangpy_ext/utils/torch_bridge.h`) checks only `api_version` + `info_struct_size`, and a signature-format change leaves the struct size unchanged, so a rebased #1054 must bump to **10** or a stale bridge passes the gate while emitting the wrong format. Prior bumps: 6→7 #816, 7→8 #1082, 8→9 #1162. Rule: when two in-flight PRs both change the signature format, whichever merges second bumps again ([torch-bridge API version collides again: #1054 vs merged #1162 both claim v9](../learnings/1790742118142-slangpy-torch-bridge-api-version-collides-again-10.md)).

## Defect surface 2 — dispatch-time grad-buffer binding (#1056, hard CUDA abort)

A `[Differentiable]` fn with ≥2 `IDiffTensor` params called through torch aborts with `CUDA_ERROR_ILLEGAL_ADDRESS` in `.backward()` when only SOME inputs have `requires_grad=True` (yes/no & no/yes abort; yes/yes OK). **Root cause — two layers disagree.** In backward, EVERY `IDiffTensor` binds as `DiffTensor` (keyed on `CallMode`, NOT per-tensor `requires_grad` — `tensorcommon.py:163-175`), so the kernel scatters `_grad_out` unconditionally (`difftensor.slang:130-147`); on CUDA the atomic target is a raw `T*` (`atomics.slang:106-109`). But dispatch binds a grad buffer only for `requires_grad=True` inputs (`autograd_backward` sets `pair->grad = nb::none()`, `slangpy.cpp:568-577`), leaving the no-grad param's `_grad_out` a dangling device pointer the scatter faults on ([slangpy backward scatters _grad_out unconditionally but binds it only for requires_grad inputs (CUDA illegal address, #1056)](../learnings/1783881151114-slangpy-backward-scatters-grad-out-unconditionally.md)).

The verification lens for "does a no-grad diff tensor carry a grad buffer": the answer is driven by (a) the resolved Slang param type via call-mode and (b) the per-parameter `has_grad_fields` set solely from the type NAME (`slangpytensor.cpp:161-205`) — NOT per-tensor grad state. Per-tensor grad state only gates whether the grad_out field gets *written* at dispatch. A fixer's DeepWiki claim that a no-grad input binds `PrimalTensor` was wrong — that holds only for `CallMode.prim`, not backward ([Verifying slangpy backward grad binding: has_grad_fields is per-parameter (Slang type name), and DeepWiki's PrimalTensor claim is primal-pass-only](../learnings/1783881931096-verifying-slangpy-backward-grad-binding-has-grad-f.md)).

**Fix (PR #1057, Approach A, 1 line):** in the no-grad `else` branch bind `pair->grad = bridge.create_zeros_like_tensor(pair->primal)` (scratch, discarded) but still `input_grads.append(nb::none())` so torch reports no grad for that leaf. **NON-OBVIOUS: the bind must be UNCONDITIONAL, not CUDA-gated** — intuition (and a codex advisory) says "the crash is CUDA-specific, so only allocate on CUDA," but that empirically regresses Vulkan: `tensorcommon.py:153-161` RAISES on non-CUDA when a diff tensor lacks grad_out, so non-CUDA is the STRICT path and CUDA the permissive-but-crashes path — both need the buffer, for opposite reasons. Only the torch marshall silently skips the write; plain-Tensor/DiffTensorView fail LOUD (`SGL_CHECK`/`SGL_THROW`), so scope the fix torch-only ([slangpy #1056 fix — no-grad IDiffTensor backward needs a bound scratch grad buffer on ALL backends](../learnings/1783886043309-slangpy-1056-fix-no-grad-idifftensor-backward-need.md)).

**#1056 vs #1052 — verified DISTINCT:** #1052 is a *silent* hook drop from a mis-keyed cache (no crash, fixed by cache-signature change); #1056 *crashes on the first call in a fresh process* → no cache entry to mis-key → not fixed by #1054. A "grad" bug that crashes ≠ one that silently drops the hook: the crash lives in dispatch-time buffer *binding*, not cache selection ([slangpy backward scatters _grad_out unconditionally but binds it only for requires_grad inputs (CUDA illegal address, #1056)](../learnings/1783881151114-slangpy-backward-scatters-grad-out-unconditionally.md)).

**Output pairs built by the user bind their grad in the wrong direction (#1265, main 68d1e782).** `slangpy.diff_pair(primal, grad)` builds `NativeTorchTensorDiffPair(primal, grad)` with `is_input=True` and exposes no parameter to change it, and `create_torch_tensor_marshall` (`torchtensormarshall.py:327-330`) uses `is_input` to bind the grad as `d_out` (written) or `d_in` (read). So an output pair passed to an explicit `.bwds()` call, as `_result=diff_pair(y, gy)` or as an `out` parameter, never has its output grad bound for reading: CUDA aborts with an illegal memory access and Vulkan silently returns zero input gradients. `NativeTorchTensorDiffPair(y, gy, -1, False)` gives correct gradients. Autograd is unaffected, because it builds its output pairs itself with `is_input=false` (`slangpy.cpp:535`), and so is the documented DiffTensorView `diff_pair` form. The torch tests exercise this elementwise form only through `debug_build_call_data`, which never dispatches, so treat `debug_build_call_data`-only coverage as no runtime coverage ([torch diff_pair() is always is_input=True](../learnings/1793854899028-slangpy-torch-diff-pair-is-always-is-input-true-ou.md)).

## Verification environment — two bridge paths, sharp edges

Any torch-integration change must exercise BOTH bridge paths. The bridge has a **native** path (separate pip package `slangpy-torch`, built from `src/slangpy_torch/`) and a **Python fallback** (`bridge_fallback.py`); `tensor_bridge_get_signature` (native C) and `get_signature` (fallback) must stay byte-identical or the caches diverge. `TorchBridge::try_init` picks native-vs-fallback by trying `import slangpy_torch`; if absent, the functional-API torch path is GATED OFF unless `SLANGPY_ALLOW_TORCH_FALLBACK=1`. The `torch_bridge_mode` fixture (`slangpy/testing/plugin.py`) auto-parametrizes a test into both modes; a 2-backend × 3-combo test = 12 invocations on Linux ([slangpy torch fix verification: two bridge paths, native pkg build, env quirks (#1052)](../learnings/1783877917048-slangpy-torch-fix-verification-two-bridge-paths-na.md)).

**Signature-format test sites:** two tests assert the raw signature and a naive `grep [Dn,Sm]` misses one — `test_torch_bridge.py` asserts bracketed `[D2,S6]`; `test_torchintegration.py::test_torch_signature` asserts un-bracketed tuples like `("...", "D1,S6")`. Grep `D[0-9]+,S` to catch both ([slangpy torch fix verification: two bridge paths, native pkg build, env quirks (#1052)](../learnings/1783877917048-slangpy-torch-fix-verification-two-bridge-paths-na.md)).

**Test idiom that is NOT a bug:** `test_torchintegration.py` parametrizes over `DEVICE_TYPES` but always creates torch tensors with hardcoded `device="cuda"`. This is correct file-wide idiom — torch storage lives on CUDA; a non-CUDA slangpy backend imports it via `cuda_interop=True` external-memory sharing. Do NOT flag `device="cuda"` under a `device_type` parametrize as CUDA-only masking ([SlangPy torch-interop tests hardcode device=cuda even under non-CUDA parametrization](../learnings/1783886520730-slangpy-torch-interop-tests-hardcode-device-cuda-e.md)).

**Env quirks (container):** torch is not preinstalled in `.venv-slangpy`; a forced wheel swap needs `pip install --force-reinstall --no-deps torch --index-url .../cu126` (a plain reinstall is skipped as already satisfied). Register the worktree editable with `NO_CMAKE_BUILD=1 pip install -e . --no-build-isolation` to uninstall the site-packages shadow ([slangpy torch fix verification: two bridge paths, native pkg build, env quirks (#1052)](../learnings/1783877917048-slangpy-torch-fix-verification-two-bridge-paths-na.md)). The 2026-07 reason for cu126 (driver 565.x) is gone: on 2026-11-05 the driver is 595 (CUDA 13.2), and the constraint is the **native bridge build**, whose `CUDAExtension` refuses a CUDA major mismatch with the container's nvcc 12.6. The fixer found the default +cu130 wheel refused, installed `torch --index-url https://download.pytorch.org/whl/cu126`, and built with `CUDA_HOME=/usr/local/cuda-12.6 pip install . --no-build-isolation` from `src/slangpy_torch`; `import slangpy_torch` alone fails with `libc10.so` not found (import torch first), and `spy.is_torch_bridge_using_fallback() == False` confirms the native path ([bf16 fallback copy path; native build needs torch matching nvcc](../learnings/1793842659420-slangpy-torch-fallback-bridge-bf16-copy-path-only-.md)). The triager, by contrast, built a torch 2.15.0+cu132 wheel against nvcc 12.6 without complaint, in about 40 s, with `uv pip install --python <venv>/bin/python --no-build-isolation --no-deps --target <dir> src/slangpy_torch`. Building into `--target <dir>` lets one venv test both paths: put `<dir>` on `PYTHONPATH` for the native bridge and leave it off for the fallback. `uv pip install torch --index-url https://download.pytorch.org/whl/cu128 --extra-index-url https://pypi.org/simple` resolves 2.15.0+cu132 from PyPI, not a cu128 build, so check `torch.__version__` after installing ([scratch worktree: slangpy_torch into a --target dir](../learnings/1793838656591-fast-slangpy-scratch-worktree-clone-submodules-fro.md)).

**A green "native" bridge run is NOT native coverage unless the `slangpy_torch` ext is actually built.** The `torch_bridge_mode` fixture (`slangpy/testing/plugin.py:122-156`) parametrizes `["native","fallback"]` but forces the mode ONLY via `set_torch_bridge_python_fallback(False)`; when the native ext is absent `m_api == nullptr`, so `TorchBridge::get_signature` (`src/slangpy_ext/utils/torch_bridge.h:269-283`) takes the fallback branch **regardless of the force flag** — the "native" parametrization silently re-runs fallback, so a green "native" run on a host without the ext is not native coverage. Direct native-ABI tests sidestep this with `pytest.importorskip("slangpy_torch")` + a ctypes fn-pointer call, so they SKIP (not fail) when the ext is absent — a native-only `-8`/return-code contract can pass CI while never actually running unless a lane builds the CUDA ext. To empirically confirm native behavior you must build torch (cu126) + slangpy + the `slangpy_torch` CUDAExtension, a LARGE job (torch ~2.5GB download + full SGL/slangpy_ext compile) to budget deliberately. The `api_version` gate is exact-match: a mismatch sets `m_api=nullptr` ("incompatible") → Python fallback (fail-safe, no ABI crash, `torch_bridge.h:124-128`), so bump the version whenever `get_signature`'s result-code set changes, not just its string format ([torch-bridge native tests skip silently without the CUDA ext (PR #1162)](../learnings/1789423781506-slangpy-torch-bridge-native-tests-skip-silently-wi.md)).

## Adding a torch dtype: bf16 needs an SGL `ScalarType` member first (#1260/#1261)

The torch bridge has carried bf16 (code 15) since PR #814, and BFloat16 kernels run bit-exact on L40S CUDA and Vulkan with SlangPy-allocated tensors (Vulkan adds `spvBFloat16KHR` automatically), yet a Python-only torch dtype mapping cannot work. SGL's `TypeReflection::ScalarType` (`src/sgl/device/reflection.h:426`) takes its values from Slang's `SLANG_SCALAR_TYPE_*` and stopped at `uintptr`=15 (`COUNT`=16), while Slang 2026.20 added `BFLOAT16`=16, `FLOAT_E4M3`=17 and `FLOAT_E5M2`=18. Because the nanobind enum is not a flag enum, every `.scalar_type` / `slang_scalar_type` read on such a reflection raises `ValueError: 16 is not a valid ScalarType`, which hits the torch return path, `value.py` and `jupyter.py`. On the C++ side the read/write converter tables in `src/slangpy_ext/device/cursor_utils.h` are sized `[COUNT]` and indexed by the raw value without a bounds check, so values ≥ `COUNT` read past the end (UB; in the repro it landed on a neighbouring error handler). The repo's "Adding a new torch dtype" checklist (`.github/instructions/torchintegration.instructions.md:143`) also omits the SGL enum member and `SGL_ENUM_INFO`, `DataType`, `scalar_type_name` (`src/sgl/refl/type.cpp:144`), `get_scalar_type_cpu_size`, and `scalartype_to_dtype` (`src/slangpy_ext/func/tensor.cpp:17`) ([new Slang scalar types break SGL ScalarType](../learnings/1793838976078-slangpy-new-slang-scalar-types-bfloat16-16-fp8-17-.md), [bf16 fallback copy path; native build needs torch matching nvcc](../learnings/1793842659420-slangpy-torch-fallback-bridge-bf16-copy-path-only-.md)). The numpy side has the same "one map is half the fix" shape; see the two dtype maps on [[wiki/concepts/slang-a-slangpy.md]].

**The fallback bridge's copy helpers run only on non-CUDA devices.** `copy_to_buffer` / `copy_from_buffer` serve Vulkan/D3D12 interop; on a CUDA device the torch pointer is bound directly, so a dtype bug in them is invisible in CUDA-only runs. bf16 used the `__cuda_array_interface__` typestr `"<V2"`, which `torch.as_tensor()` rejects ("can't convert np.ndarray of type numpy.void"). The fix is `"<i2"` plus `.view(tensor.dtype)`, a reinterpret, because a plain int16 copy would convert the values. Always run new-dtype torch tests on Vulkan too, in fallback mode ([bf16 fallback copy path](../learnings/1793842659420-slangpy-torch-fallback-bridge-bf16-copy-path-only-.md)). Half-precision autodiff on Vulkan has a separate hazard, the missing fp16 atomic add, on [[wiki/concepts/slang-rhi-backend-runtime.md]].

## Scalar-return + torch-input: the `WTensor<T,0>` ICE and why Approach A is incomplete (#827)

slangpy #827 (originally a Vulkan+torch memory leak, reportedly fixed by #781) evolved into a **live compiler ICE at HEAD**: calling a scalar-returning Slang fn with a torch.Tensor arg on a non-CUDA backend emits `WTensor<T,0>` → `InternalError: didn't find tuple element`. Root cause chain: `calldata.py:207-208` sets `return_type = torch.Tensor` **unconditionally** when a torch tensor is present, *before* `call_dimensionality` is computed; `create_return_value_binding` only applies its `call_dim==0 → ValueRef` default when `return_type is None`, so scalar returns skip ValueRef; the torch marshall then builds `WTensor<T,0>` with zero-length shape/strides → the ICE. Regression from #759, latent since #362 [slangpy #827 evolved: torch scalar-return emits WTensor&lt;T,0&gt; → Slang ICE (live at HEAD)](../learnings/1785194003226-slangpy-827-evolved-torch-scalar-return-emits-wten.md). It's a semantics decision, not a pure bug: Approach A (guard the `return_type` default on `call_dim>0`) and Approach B (support 0-D torch returns end-to-end). **Approach A as specified is INCOMPLETE and regresses** — `call_dim==0` is NOT scalar-exclusive; it also covers whole-tensor/aggregate returns (`float3 add_vectors(...)`), so guarding on `call_dim>0` diverts those to ValueRefMarshall too and breaks 16 existing `test_torchintegration.py` cases (`save_for_backward can only save variables`). The correct discriminator is "scalar element type at dim 0" (ScalarType), not `call_dim>0`; and torch's own convention (verified torch 2.13) is that a logically-scalar op returns a **0-D torch.Tensor**, the consistency argument for Approach B. The ICE itself does not reproduce on every env (L40S CUDA/Vulkan native bridge compiles `WTensor<float,0>` fine), so it's compiler-version-specific [slangpy#827: Approach A (guard torch return on call_dim>0) regresses aggregate dim-0 returns](../learnings/1785197081443-slangpy-827-approach-a-guard-torch-return-on-call-.md).

The mixed-`requires_grad` backward crash refines the #1056/#1057 scratch-buffer fix above into its principled form. When a `[Differentiable]` function takes several `IDiffTensor` inputs but only some have `requires_grad=True`, the no-grad inputs still bind as `DiffTensor` (the choice is made by **call mode**, not per-tensor), whose kernel scatters `_grad_out` unconditionally — on CUDA the atomic buffer is a raw `T*`, so an unbound grad buffer faults; on non-CUDA it fails earlier at kernel-gen (two distinct failure modes, so a CUDA null-guard alone is insufficient). The zero-alloc fix is to bind the frozen input as **`PrimalTensor`** (conforms to `IDiffTensor`, carries no `_grad_out`, compiles grad writes to no-ops) rather than a throwaway zeroed buffer — but doing it properly means threading `requires_grad` into type resolution AND the kernel signature, since the torch signature (`[Dn,Sm]`) does not encode it and mixed/all-grad calls currently collide on the same backward kernel ([backward mixed requires_grad — PrimalTensor is the zero-alloc fix, not a scratch grad buffer](../learnings/1785320480003-slangpy-backward-mixed-requires-grad-primaltensor-.md)).
