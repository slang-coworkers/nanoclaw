# CI Build Tooling & Workflow Structure

How the Slang CI build system is structured: workflow files and their scope, the bot's workflow-permission wall, required checks, GPU test silencing with expected-failure lists, DISABLE build-only jobs, the Falcor build/test split, compile-time perf-CI, the check-cmdline-ref consolidation, and build-environment hazards (disk layout, submodule network fetches, release-CI regressions).

> Related pages: [CI Build: Git Checkout Depth & Submodule Pins](ci-build-git-checkout-and-submodule-pins.md) · [CI Build Process Detection and Concurrency](ci-build-process-detection-and-concurrency.md).

## TL;DR

- **`nv-slang-bot[bot]` cannot push `.github/workflows/*.yml`** (no App `workflows` permission; rejected at push time, even on its own branch), and maintainers close cross-fork workaround PRs on security policy. Plan a CI change from triage: ship source/tests/docs, hand the workflow edit up as a `git format-patch` or proposed YAML.
- **A check is "required" by being in `ci.yml`'s `check-ci.needs`**, not by branch-protection settings. Add a `pull_request` job that exits 1, then list it in `needs`; the `ci.yml` edit itself is maintainer-applied.
- **Draft PRs get no `pull_request` CI** (`filter` is gated on `draft != true`); marking ready runs full CI. A `workflow_dispatch` runs `filter` but classifies only the head commit, so a docs-only or big merge-commit head skips the whole matrix and still reads `success`.
- **GPU-test silencing is layered `-expected-failure-list` files**, matched by exact normalized path. An expected failure reclassifies a clean `SLANG_FAIL`; it cannot suppress a crash.
- **`-DSLANG_SLANG_LLVM_FLAVOR=DISABLE` jobs are build-only**, so "CI on a DISABLE configuration confirms it" is illusory for slang-test fixes.
- **`download-artifact@v4` is attempt-scoped**: `gh run rerun --failed` on a split build/test workflow reports "Artifact not found"; recover with a full rerun or a push.
- **Do not fold `regenerate-cmdline-ref.yml` into `ci.yml`**; its generate/apply split is a fork-security boundary.
- **An advisory CI script gets `continue-on-error: true` on its step**, not only per-probe `|| true`.
- **`ci-examples.sh` grades on exit code only**, and whole-repo `pre-commit` reds can be inherited from a red `main`; check `git diff --name-only origin/main` before owning a lint failure.
- **COMPARE_COMPUTE `filecheck-buffer` tests need `-output-using-type`**, or CI's cpu+llvm backend dumps hex while local gcc dumps decimal.
- **A clean git merge of `slang-diagnostics.lua` can still collide on a numeric code** and break every platform build; renumber above master's current max.
- **Before calling a build disk-blocked, `df` the actual build path** (`/workspace/agent` is a separate, larger volume than `/workspace`).
- **Missing release assets on one arch: trace the exact failing command** and bisect the workflow file's own history; macOS configure failures can come from slang-rhi's own network `FetchContent` of Vulkan-Headers.
- **nanoclaw `nv-*` sync-PR CI tests the composed state of every `nv-*` branch**, so an owned-set rename breaks every leaf sync PR until the nv-main sync lands.

## Workflow Permission Constraint

`nv-slang-bot[bot]` lacks the GitHub App `workflows` permission, so it cannot add or edit any `.github/workflows/*.yml`. A fix that needs a workflow edit goes to a human maintainer ([CI-workflow-file issues are not bot-actionable](../learnings/1780769352650-ci-workflow-file-issues-github-workflows-are-not-b.md)). The wall recurs: test silencing that needs both a `tests/*.txt` edit and a workflow conditional (the bot lands only the `.txt`, leaving dangling plumbing) ([Reconciling CI test-silencing follow-ups + the workflows-perm trap](../learnings/1780769333040-reconciling-slang-ci-test-silencing-follow-ups-exp.md)), the check-cmdline-ref consolidation ([check-cmdline-ref.yml → ci.yml consolidation (#11586) is low-risk](../learnings/1781310201311-slang-check-cmdline-ref-yml-ci-yml-consolidation-i.md)), and the Falcor build/test split ([Falcor CI build/test split (slang#11495): Approach C](../learnings/1780769330979-falcor-ci-build-test-split-slang-11495-approach-c-.md)). When the follow-up targets a contributor's still-open PR, recommend that the author amend it in place (they can edit workflows); do not ship a competing bot PR ([Contributor CI follow-up against own open PR → plan-only](../learnings/1780769335094-ci-follow-up-issue-filed-by-a-contributor-against-.md)).

**The push rejection is technical; the policy wall is fatal.** A bot can route around the push rejection through the `slang-coworkers/slang` fork (its App install has `workflows`) and a REST cross-fork PR (`gh api -X POST repos/shader-slang/slang/pulls -f head=slang-coworkers:<branch> ...`; `gh pr create` GraphQL fails "fork collab can't be granted"). Maintainers close such PRs unmerged on security policy. jkwak-work on #11989→PR #12001: *"coworker is not allowed to modify [workflow files] for security reasons. I will run an agent locally."* So the push rejection is the early tell that the fix is disallowed, not an obstacle to route around ([Coworker bots may not modify .github/workflows — flag before building](../learnings/1783546220222-coworker-bots-may-not-modify-github-workflows-flag.md), [Cross-fork workflow-file PR is policy-closed](../learnings/1783546977853-cross-fork-workflow-file-pr-opens-but-is-policy-cl.md)). Catch it at triage-scoping: when the change surface is or requires `.github/workflows/**` or `.github/actions/**`, mark the verdict maintainer-only and skip the fix cycle. Still triage, verify, recommend, and file spun-off *code* issues, which are landable (#11989 spun off compiler false-positive trackers #12006/#12007). If a bot PR already exists, annotate it maintainer-only and hand the diff over as a comment ([Workflow-file changes are policy-rejected — catch at triage](../learnings/1783546996023-workflow-file-changes-are-policy-rejected-for-cowo.md)).

**Plan for it from the start.** The rejection fires at push time, even on the bot's own fix branch (`refusing to allow a GitHub App to create or update workflow ... without workflows permission`). Only the non-workflow commits land, so a mixed commit costs a `git rm` + re-amend round-trip. Keep workflow commits separate. Push what the bot can (source, tests, docs). Hand the workflow change up as `git format-patch` output (for `git am`) or as proposed YAML in a PR-body `<details>` block, and say in the PR body that the CI change is proposed, not included. Do not build a verification plan on CI steps the bot cannot push (PR #13042's dropped `check-extras-scripts.yml`; #13079 for slang#13077) ([nv-slang-bot cannot push .github/workflows/ — deliver a format-patch](../learnings/1790375258801-nv-slang-bot-github-app-cannot-push-changes-under-.md)).

## Making a Slang CI Check "Required"

`ci.yml` registers one aggregate job in branch protection: `check-ci`. Its `needs:` list enumerates every build/test/lint job and fails if any needed job is not `success`. To make a new check blocking, (1) write a `pull_request`-event job that exits 1 on violation, then (2) add its name to `check-ci.needs` (precedents: `check-cmdline-ref`, `check-capability-atoms-ref`). Branch-protection settings do not change. The script change (e.g. an `--enforce` exit-1 mode under `extras/`) is bot-committable; the `ci.yml` job + `needs` edit is not, so deliver it as a maintainer-applied diff and note the split in the triage `next-action`. `check-inst-version-changes.sh` is advisory only because the script exits 0 and its poster runs `on: workflow_run` (no PR-head status). Prefer a dedicated cheap job over flipping the existing "Check Version Constants" build step, whose artifact upload lacks an `always()` guard ([making a slang CI check required = add a job to check-ci.needs](../learnings/1784430693229-making-a-slang-ci-check-required-add-a-job-to-chec.md)).

## Bot Draft PRs and CI

`ci.yml`'s `filter` job is gated `if: github.event_name != 'pull_request' || github.event.pull_request.draft != true`. On a draft PR, `filter` skips, `should-run` is never set, and every build/test job skips. The PR sits with `skipped` CI until a human marks it ready; the `ready_for_review` event fires a fresh `draft=false` event and full CI runs. A `workflow_dispatch` does run `filter`, but it classifies only the head commit (`BASE=HEAD^1`), so a docs-only or big merge-commit head skips the whole matrix with a `success` conclusion (see [CI Build Process Detection and Concurrency](ci-build-process-detection-and-concurrency.md)) ([Bot draft PRs get zero CI](../learnings/1781663343829-bot-draft-prs-get-zero-ci-on-shader-slang-slang-fi.md), [a docs-only head commit makes a dispatched run skip the whole matrix](../learnings/1791961955700-slang-ci-workflow-dispatch-skips-the-whole-matrix-.md)).

## GPU Test Silencing and Expected-Failure Lists

`.github/workflows/ci-slang-test.yml` layers cumulative `-expected-failure-list` flags:
- Always: `tests/expected-failure-github.txt`
- When `full-gpu-tests != true`: `tests/expected-failure-no-gpu.txt`
- Linux jobs: `tests/expected-failure-linux.txt`
- T4 GPU tier: `tests/expected-failure-linux-gpu.txt`

Linux aarch64 jobs (`test-linux-{debug,release}-gcc-aarch64`, `runs-on: ubuntu-24.04-arm`, `full-gpu-tests: false`) consume `expected-failure-no-gpu.txt`. macOS aarch64 is `full-gpu-tests: true` (Metal works) and does not. `tools/gfx-unit-test/gfx-test-util.cpp:265-269` already does `SLANG_IGNORE_TEST` when `getRHI()->createDevice()` fails, but that auto-skip misses the case where the Vulkan loader is present with no ICD: the instance creates, `vkEnumeratePhysicalDevices` returns 0, and the test fails past the skip point. That is why ~24 Vulkan tests are still listed ([How GPU unit tests are silenced on no-GPU / aarch64 runners](../learnings/1780769170873-slang-ci-how-gpu-requiring-unit-tests-are-silenced.md)).

A newly failing Vulkan unit test on a no-GPU runner goes in `tests/expected-failure-no-gpu.txt` under the `# Vulkan gfx-unit-tests require a Vulkan-capable GPU` block. First cross-check the x86_64 sanitizer job (also no-GPU, also consumes no-gpu.txt): if the test passes there, the failure is aarch64-Vulkan-specific, and no-gpu.txt is a slightly over-broad but harmless placement. `tools/slang-test/options.cpp:~519` matches entries against test names by exact normalized path, so a typo silently fails to match and CI stays red. An expected failure still runs the test and only reclassifies a clean `SLANG_FAIL` exit; it cannot suppress a crash/SIGSEGV of the worker ([Reconciling CI test-silencing follow-ups + the workflows-perm trap](../learnings/1780769333040-reconciling-slang-ci-test-silencing-follow-ups-exp.md)).

## DISABLE-Configured CI Jobs Are Build-Only

Jobs configured with `-DSLANG_SLANG_LLVM_FLAVOR=DISABLE` (`.github/workflows/cmake-options-build.yml`) stop at the build step and never run `slang-test`. The x86_64 test tiers consume artifacts shipped with slang-llvm, so they never exercise the absent-library path either. A claim that a slang-test startup/harness fix is "best confirmed by CI on a DISABLE configuration" is illusory. The cheap GPU-free guard is an assertion in the existing DISABLE build job: `./build/*/bin/slang-test -help | grep -q .` ([DISABLE CI jobs are build-only](../learnings/1780326708945-slang-disable-ci-jobs-are-build-only-no-slang-test.md)).

## Falcor CI Build/Test Split

PR #11495 split `falcor-test.yml`: the Slang build moves off the Falcor GPU runner (`[Windows, self-hosted, falcor]`) to the standard build pool (`[Windows, self-hosted, build]`), with handover via `upload-artifact@v4` → `download-artifact@v4` (artifact `slang-falcor-build-windows-release`). The free `windows-latest` runner was rejected because the build requires the CUDA toolkit (`SLANG_ENABLE_CUDA=1`), which GitHub-hosted images lack. LLVM-from-GCS needs no GCP auth to download (the bucket is publicly readable via plain `curl`); only the upload on `refs/heads/master` does. `download-artifact@v4` is attempt-scoped, so `gh run rerun --failed` on a test-only failure reports "Artifact not found" in every split workflow (`materialx-test.yml`, `ci-slang-test.yml`, `falcor-test.yml`); recover with a full rerun or an author push ([Falcor CI build/test split (slang#11495): Approach C](../learnings/1780769330979-falcor-ci-build-test-split-slang-11495-approach-c-.md)).

In-flight PR #11485 (`tools/benchmark/perf-suite/`) covers the same goal with synthetic stage-stress + MDL/DXR workloads driven by `slangc -report-perf-benchmark`. ## check-cmdline-ref Consolidation

`check-cmdline-ref.yml` can fold into `ci.yml` (issue #11586) at low risk. The `build-linux-release-gcc-x86_64` artifact (`slang-tests-linux-x86_64-gcc-release`, 1-day retention) already contains `bin/slangc`, and `check-ci` (`ci.yml` ~L298–362) has the `needs:` array and failure-condition pattern. Repoint the Generate step from `$bin_dir/slangc` to the downloaded artifact's `bin/` plus `chmod +x`; `slangc -help-style markdown` output does not depend on build flags. Do NOT touch `regenerate-cmdline-ref.yml`: it is the `/regenerate-cmdline-ref` comment auto-fix, split for fork security (generate runs untrusted PR code without bot secrets; a separate apply job commits via SLANGBOT_PAT). Folding or deleting it breaks the auto-fix and its security model ([check-cmdline-ref.yml → ci.yml consolidation (#11586) is low-risk](../learnings/1781310201311-slang-check-cmdline-ref-yml-ci-yml-consolidation-i.md)).

## Example-Grading and Whole-Repo Lint CI

**`ci-examples.sh` grades on exit code only.** `run_sample()` never scans stdout/stderr, so an example can print `warning[...]`/`error[...]`/`fatal error[...]` and stay green. The `reflection-api` example swallows a real `error[E36108]` + `fatal error[E40003]` because its `Result` is discarded and `execute()` always returns `SLANG_OK`. A diagnostics gate must grep `(warning|error|fatal error)\[...\]`, not just warnings. The skip mechanism (`--skip-file tests/expected-example-failure-github.txt`, regex `<os>:<platform>:<config>:<sample>`) is the template for an allowlist ([ci-examples.sh grades on exit code only](../learnings/1783471474036-slang-ci-examples-sh-grades-examples-on-exit-code-.md)).

**`slangpy-samples` CI runs `pre-commit --all-files`.** Every PR's status reflects the formatting of all files, so when `main` is red (e.g. `black` reformats ~8 pre-existing `.py` files) a PR that touches no Python inherits the red check. Before owning a `github.ci_failed`, find the failing hook and files (`gh run view --log-failed | grep -iE "Failed|reformatted|\.py"`), compare with `git diff --name-only origin/main`, and confirm `main` is already red. Document inherited debt; do not pull unrelated reformatting into a focused PR. Local `black --check` can pass while CI's pinned version fails ([slangpy-samples CI runs pre-commit --all-files](../learnings/1783525328477-slangpy-samples-ci-runs-pre-commit-all-files-inher.md)).

## Advisory CI Shell Scripts: `continue-on-error` at the Call Site

For a script that is advisory by construction (every branch exits 0, it only emits `::warning::`), the fix for "it crashed the build" is `continue-on-error: true` on the workflow step. Per-probe `|| true` fixes one probe at a time, and the next unguarded probe reintroduces the bug; `continue-on-error` makes "never gate the build" structural for every unenumerated failure (new probe, syntax error, segfault, `set -o` change), and the step still shows as failed in the Actions UI. Keep the `|| true` edits for a different reason: under `set -euo pipefail` they preserve the warnings of later checks. Do not over-build a regression test for such a script (an 82-line harness for a 141-line script was dropped in review). The `continue-on-error` line is a workflow edit, so the bot ships the `|| true` edits and hands the step change to a maintainer (#13041 → PR #13042) ([Advisory CI scripts: continue-on-error beats per-probe || true](../learnings/1789654672103-advisory-ci-shell-scripts-continue-on-error-beats-.md)).

## COMPARE_COMPUTE filecheck-buffer Portability

COMPARE_COMPUTE tests with `filecheck-buffer=CHECK` need `-output-using-type` in the directive. Without it, the LLVM JIT backend (`-api cpu+llvm`, used in CI) dumps raw hex words and the gcc/genericcpp backend (local) dumps decimal. Values > 9 expose the mismatch (`30` vs `1E`); values ≤ 9 hide it. A local `-cpu` pass does not guarantee CI ([COMPARE_COMPUTE filecheck-buffer: use -output-using-type](../learnings/1781271132976-compare-compute-filecheck-buffer-use-output-using-.md)).

## Diagnostic Code Collisions on Master-Merge

A new `source/slang/slang-diagnostics.lua` entry with an explicit numeric code can collide with a code another PR claimed after your base. Git merges the `.lua` cleanly, but the diagnostics generator fails and every platform `build` job breaks right after an "Update branch" / "Merge branch 'master'" commit. Check master's max with `git show origin/master:source/slang/slang-diagnostics.lua | grep -oE '\b55[0-9]{3}\b' | sort -n | tail` and renumber above it ([Diagnostic codes picked against a stale base collide on master-merge](../learnings/1782741439587-diagnostic-enum-codes-picked-against-a-stale-base-.md)).

## Build Volume and Disk Layout

The container has two volumes: `/workspace` → `/dev/vda1` (shared host volume, ~5–6G free) and `/workspace/agent` → `/dev/vdb` (per-agent, ~89G free, holds the clone and build tree). Before declaring a build disk-blocked, run `df -h --output=source,avail,pcent <actual-build-path>`, not bare `df /workspace` ([Per-agent build volume is /dev/vdb (/workspace/agent), not shared /workspace](../learnings/1780381892104-per-agent-build-volume-is-dev-vdb-workspace-agent-.md)). If `/dev/vdb` is full of sibling worktrees, build out-of-source on `/dev/vda1`: symlink the worktree's `build/` to `/workspace/build-<issue>` and set `TMPDIR=/workspace/build-<issue>/tmp` ([Disk-full build workaround: out-of-source build on /dev/vda1](../learnings/1781568134178-disk-full-build-workaround-out-of-source-build-on-.md)).

## Compiler Triage Caveats for Build/Fix Work

**DescriptorHandle→ConstantBuffer conversion is blocked by a ParameterGroupType guard.** `_coerce` in `source/slang/slang-check-conversion.cpp:2188-2195` fails any coercion whose target is a `ParameterGroupType` (`ConstantBufferType : UniformParameterGroupType : ParameterGroupType`) before the constructor-based implicit-conversion search. `RWStructuredBuffer` is not a ParameterGroupType, so it converts; that asymmetry is the bug. The generated `__init(DescriptorHandle<ConstantBuffer<T,L>>)` exists (`hlsl.meta.slang:27044`) and lowering works (`:27307`). Fix direction: carve DescriptorHandle sources out of line 2192, or remove/reorder the guard per its `:2190` TODO ([DescriptorHandle→ConstantBuffer conversion blocked in _coerce](../learnings/1782145502619-descriptorhandle-to-constantbuffer-implicit-conver.md)).

**Primary-file `using namespace` leaks through `import`.** The directive in a module's primary file is re-exported (importers see `Foo`'s members unqualified); in an `implementing`/`__include`d file it is not. Primary-file decls sit under the `ModuleDecl` scope, `__include`d files get a separate `FileDecl` scope, and `importModuleIntoScope` re-exports the module scope's direct-child sibling chain. Before proposing a behavior change, grep `tests/` for tests that assert current behavior: `tests/language-feature/namespaces/namespace-using/b.slang` depends on this leak ([Primary-file `using namespace` leaks through `import`](../learnings/1780476462894-slang-primary-file-using-namespace-leaks-through-i.md)).

## Release-CI Failures: Trace the Exact Command; Bisect the Workflow File

When a release is missing artifacts for one arch/platform only, do not assume a transient. Trace the exact failing command: moving a CI leg into a no-sudo container can break asset production asymmetrically (a step that needed root) while other arches stay green ([Release-asset asymmetry from a no-sudo container CI leg](../learnings/1782845136368-release-asset-asymmetry-from-moving-a-ci-leg-into-.md)). When a release run fails at a **Setup**/environment step, the culprit is almost always a CI-config change: bisect the workflow file's own git history, not the source-commit range since the last green run, which mis-blames an innocent PR ([Release-CI Setup failures: bisect the workflow file's history](../learnings/1782869849186-release-ci-setup-failures-bisect-the-workflow-file.md)).

## Vendored-Submodule FetchContent Is a Hidden Network Dependency

Slang macOS CI intermittently fails at **CMake configure** downloading Vulkan-Headers, although Slang core vendors them (`external/CMakeLists.txt` `add_subdirectory(vulkan)` → `Vulkan::Headers`, no download). The vendored **slang-rhi** submodule fetches its own copy (`FetchPackage(vulkan_headers URL .../Vulkan-Headers/archive/refs/tags/v1.4.347.zip)`, a `FetchContent` wrapper) under `if(SLANG_RHI_ENABLE_VULKAN)`, ON for Darwin, into a separate `slang-rhi-vulkan-headers` target. CI sets no `SLANG_GITHUB_TOKEN`, so the fetch is anonymous and rate-limited per IP; free macOS runners share NAT'd IP pools, hence intermittent 403/timeouts. General pattern: a vendored submodule that FetchContents a dependency the parent already vendors adds a token-less configure-time network dependency. The escape hatch `FETCHCONTENT_SOURCE_DIR_VULKAN_HEADERS=${CMAKE_SOURCE_DIR}/external/vulkan` is unsafe here: slang-rhi's Vulkan backend needs bfloat16/float8 symbols absent from the older vendored headers (VK_HEADER_VERSION 307), so the fetch stays load-bearing until the submodule is bumped or slang-rhi gains an `if(NOT TARGET Vulkan::Headers)` reuse. Vulkan-Headers is not SPIRV-Headers ([slang#11985: slang-rhi FetchContent-downloads Vulkan-Headers](../learnings/1783619348986-slang-11985-2nd-cause-slang-rhi-fetchcontent-downl.md)). Read the pin at the committed gitlink, not a stale working tree — see [Verify submodule pins at the gitlink, not the working tree](../learnings/1783621079268-verify-submodule-pins-at-the-gitlink-not-the-worki.md).

## Windows CI Crash Dumps Route via the Shared `ci-slang-test.yml`

For #12032 (Windows counterpart of Linux #10812 core-dump capture): Windows GPU test jobs (`test-windows-*-gpu`, self-hosted GCP-T4) run through the shared OS-agnostic `.github/workflows/ci-slang-test.yml` (default `shell: bash`, no artifact upload). The Linux capture lives in `ci-slang-test-container.yml` (`ulimit -c`, `/var/cores` bind-mount, "Capture core dump backtraces" `if: always()`) because Linux GPU tests are containerized. Windows runners are not, so the mechanism is WER LocalDumps (registry), added to the shared file under `if: runner.os == 'Windows'` with a `shell: pwsh` step. Preserve the security posture: Linux uploads only gdb-symbolized backtraces, never raw cores (they hold full process memory). The issue's `DumpType=2` full-dump + raw upload regresses that. Correct options: symbolize on-runner with `cdb` and upload only `.txt` (needs Debugging Tools + PDBs), or `DumpType=1` minidumps with a documented caveat; use `if: always()` + `if-no-files-found: ignore` over `if: failure()`. This is a pure workflow change, so the deliverable is a validated `git apply`-able diff as an issue comment, not a PR ([slang#12032 Windows CI crash-dump routing](../learnings/1783637017715-slang-12032-windows-ci-crash-dump-routes-via-ci-sl.md)).

## nanoclaw Sync-PR CI Composes All `nv-*` Branches

On `slang-coworkers/nanoclaw`, `ci.yml` does not test a sync PR into an `nv-*` base standalone: it merges every sibling `nv-*` branch into a composed state. `nv-main` is canonical for the owned set (`src/*`, `.github/**`, `scripts/**`, `container/agent-runner/**`, `docs/**`, config), which auto-resolves to nv-main on conflict; a conflict outside it fails loudly. So a refactor that renames or deletes owned-set files breaks every leaf sync PR until the nv-main sync PR lands. Observed: an "ncl tasks control plane" refactor (`insertTask`→`insertTaskRow`, deleted `scheduling/actions.ts`) was on the sync-PR heads but not the live tips, so each leaf merged live nv-main's pre-refactor `db.ts` + stale `actions.ts` over its own post-refactor `db.ts` and hit identical tsc errors while the nv-main PR was green. Diagnosis: tsc errors naming files absent from both the PR head and base trees came from a sibling branch (almost always nv-main). It is not a flake; `gh run rerun --failed` replays the same `github.sha`. Fix: merge the nv-main sync PR first, then re-run the leaves. These `github.pr_ready_for_review` webhooks are outside the shader-slang routing table and have no nanoclaw reviewer, so Main handles them ([nanoclaw sync-PR CI composes all nv-* branches](../learnings/1783633650284-nanoclaw-sync-pr-ci-composes-all-nv-branches-merge.md)).
