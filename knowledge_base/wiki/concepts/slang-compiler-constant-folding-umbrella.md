# Slang constant-folding umbrella (#14473) and compile-time-eval semantics

shader-slang/slang tracks all compile-time-eval work under a constant-folding umbrella hierarchy (created by skiminki-nv 2026-11-13): #14473 is the top-level "Compile-time evaluation umbrella", with sub-umbrellas #14476 (integer folding correctness), #14477 (constant-value/conversion diagnostics), #14478 (missing folds; holds #14468, SCCP not folding vector/matrix arithmetic on constant operands), #14479 (link-time/spec constants; #14348 CoopMat spec-const parented there), #14480 (static_assert/constexpr), #14481 (floating-point constants), #14482 (semantics/spec).

## TL;DR

- Triage routing: a new constant-folding/compile-time-eval issue should name its sub-umbrella in the triage comment so leaves get slotted. Sub-umbrellas are untyped and unlabeled; the convention so far is to add a `Diagnostics`-style topic label and leave Issue Type untouched.
- Constant-folding semantics are split across three folders that DISAGREE: the front-end IntVal folder, `tryConstantFoldExpr`, and IR SCCP. A fold-semantics fix (e.g. shift-mod-N) must touch all of them plus the diagnostic that encodes one engine's answer.
- Both folding engines must be repro'd on a fold bug: front-end `BuiltinOperationIntVal::tryFoldImpl` (slang-ast-val.cpp) and IR SCCP (slang-ir-sccp.cpp).
- The formal spec has NO constant-evaluation model — "compile-time constant expression" is undefined there; `#if` is admitted-undocumented. Policy gaps (int→float silent conversion) are front-end `_coerce` policy, not missing infra; SCCP has no DiagnosticSink, so const-expr conversion diagnostics belong in the front-end folder.
- Warning infra is complete (-Wall/-Wextra/-Wpedantic, -warnings-as-errors, #pragma warning); what's missing on #14477-class asks is policy thresholds, not machinery.
- Line anchors in older static_assert/constexpr notes drift fast; re-verify file:line before citing them publicly, and treat dispatch pointers to memory files as stale until verified.
- **An "expected X, got X" diagnostic (like #8479's false E30019) usually means two producer paths folded the same constant with different `ConstantIntVal` Type operands** — implicit-default args fold with the literal's own `Int` type, explicit args coerce to the param type, and IntVal printing omits the type so both sides read identical.
- **An `extern` var's `VarDeclBase::val` is NOT its initializer's fold by default** — the header-visitor fold runs on the unchecked initializer and the body-visitor fallback yields a self-referential `DeclRefIntVal` for non-CompileTime kinds (#14479 territory; slang#14549). Chained externs (`export extern static const int B = A + 1;`) can never resolve until the checked initializer is folded into `val` first.

## Three folders disagree on semantics

Verified at HEAD da04f0426 for #14482/#9374: shifts are the canonical example — the front-end IntVal folder masks the count `% 64` (slang-ast-val.cpp ~2228-2243), `tryConstantFoldExpr` masks (slang-check-expr.cpp ~2718-2741), but SCCP's `evalLsh`/`evalRsh` returns 0 / saturates to -1 (slang-ir-sccp.cpp ~776-839), and warning 41030 "always zero" encodes SCCP's semantics — a third de-facto semantics inside one diagnostic. Anyone implementing #9374's shift-mod-N must touch all four sites. The `#if` preprocessor path is fully divergent from the lexer path (details on [[wiki/concepts/slang-language-preprocessor-and-lexer.md]]): `stringToInt` = `strtoll` truncated to 32-bit `int`, only `0x` recognized, shifts unguarded 32-bit signed — the root cause of #13545. The formal spec (external/spec/specification/) has no constant-evaluation model: an open gap marker at declarations.md:538 asks for a definition of "compile-time constant expression", preprocessor.md:8 admits `#if` undocumented, and types.md:111's wrap-on-overflow statement doesn't mention shifts ([three folders disagree](../learnings/1794888485621-slang-constant-folding-semantics-three-folders-dis.md)).

Two default-generic-arg fold sites disagree on the Type operand the same way (#8479, "expected 'Payload<16>.Hit', got 'Payload<16>.Hit'", P2, reproduced on master 2026-11-18): `ConstantIntVal` carries (Type, value) operands, and the implicit-default path folds the literal with its own `Int` type (`ExtractGenericArgInteger(exp, nullptr)` via slang-check-type.cpp:398, plus the solver's `getGenericParamDefaultArgVal` slang-check-constraint.cpp:944) while the explicit-arg path coerces to the param type (slang-check-overload.cpp:579-592; `TypeCastIntVal` unification slang-check-constraint.cpp:3805). Same value + different Type operand → `Val::equals` fails, but IntVal printing omits the type, so the diagnostic shows identical names — the quick triage smell for any "expected X, got X" diagnostic is two producer paths folding the same constant with different Type operands [slang#8479 false E30019 root-caused to un-narrowed default-arg IntVals — two fold sites](../learnings/1795042876526-slang-8479-false-e30019-root-caused-to-un-narrowed.md).

## Link-time extern constants: val is a self-DeclRefIntVal, not the initializer fold (#14479)

For link-time/spec constants (sub-umbrella #14479), an `extern` var's `VarDeclBase::val` is NOT its initializer's fold by default. The header-visitor val-fold (slang-check-decl.cpp ~3119, `tryConstantFoldExpr(init, LinkTime)`) runs on the **not-yet-checked** initializer, so any initializer referencing another declaration folds to null; the body-visitor fallback `_validateCircularVarDefinition` then folds with `ConstantFoldingKind::SpecializationConstant`, whose extern branch (slang-check-expr.cpp `tryConstantFoldDeclRef` ~2845) returns a **self-referential DeclRefIntVal** for any non-CompileTime kind. The exported-constants map (`getMangledNameToIntValMap`) thus published extern→self, so chained externs (`export extern static const int B = A + 1;`) could never resolve — iterating `linkTimeResolve` to a fixpoint no-ops on `map[B]==B` (pointer-stable). The fix (PR #14549, commit 4efd55a48) has body `checkVarDeclCommon` fold the extern's CHECKED initializer (LinkTime kind) into `val` first; a *reference* to the extern still folds to the symbolic self-DeclRefIntVal, which keeps linked overrides re-selecting bindings [extern var val is a self-DeclRefIntVal, not the initializer fold](../learnings/1794933057856-slang-extern-var-val-is-a-self-declrefintval-not-t.md). If you touch extern constant values, check which ConstantFoldingKind the consumer folds with.
