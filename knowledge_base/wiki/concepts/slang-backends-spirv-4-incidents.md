## SPIR-V Float-Reassociation Precision Bug = Downstream spirv-opt, Not Slang IR (2026-07-20 fold)

slang#12160: `[ForceUnroll]` + `-target spirv` at default opt produced a numerically wrong result (an inexact folded constant `-0.999998987` replacing `(xmax - xmin)`). Root cause OVERTURNED the static-analysis hypothesis — it is NOT a Slang IR pass. `-dump-ir` keeps the arithmetic exactly as written; the IEEE-unsafe reassociation is done by the **bundled/vendored spirv-opt**, which runs ONLY when opt level > `-O0` (`needsOptimization = getOptimizationLevel() != None`). Its add/sub folding rules regroup `(a-b)-(b-k)` → `(a-b)+C` and fold `C` into one float constant → catastrophic cancellation when the true denominator is tiny; every such rule is gated on `IsFloatingPointFoldingAllowed()`, which returns true UNLESS the inst carries `NoContraction`. Fast GPU-free triage signature: `-O0` correct / `-O1+` buggy ⇒ fold is in spirv-opt; `-fp-mode precise` correct / default buggy ⇒ it's the `NoContraction` lever; `-dump-ir` still shows original arithmetic ⇒ Slang IR is innocent. Load-bearing for the verdict: default fp-mode emitting NO `NoContraction` is INTENTIONAL (established by #11933, with a regression test asserting `//DEFAULT-NOT: NoContraction`). Verdict pattern: "default is more permissive than users expect," not a clear code bug → advisory + `-fp-mode precise` workaround; escalate the "should DEFAULT permit reassociation?" design question, do NOT unilaterally flip the #11933 default ([SPIR-V float reassociation precision bug = downstream spirv-opt, not Slang IR](../learnings/1784504993349-slang-spir-v-float-reassociation-precision-bug-dow.md)).

## NonUniformResourceIndex Float-Pass DescriptorHandle Round-Trip: SPIR-V-Gated by Design (2026-07-21 fold)

The `floatNonUniformResourceIndex` pass (`slang-ir-float-non-uniform-resource-index.cpp`) has a deliberate target asymmetry that recurs as a reviewer flag. Draft PR #12116 (follow-up to the #12110/#12051 cluster) adds two SPIR-V-gated cases — `kIROp_CastUInt2ToDescriptorHandle` and `kIROp_MakeVector` — so the `NonUniformResourceIndex` wrapper floats across the DescriptorHandle round-trip (`makeVector(idx,0) → CastUInt2ToDescriptorHandle → CastDescriptorHandleToUInt2 → swizzle → getElement`) and reaches the heap-subscript index that the SPIR-V `OpDecorate NonUniform` machinery consumes, fixing a dropped decoration (VUID-RuntimeSpirv-None-10148) on the DEFAULT (no `spvDescriptorHeapEXT`) heap path. Reviewers (Devin, clarity-C001, cross-backend) reliably flag that these new cases carry `if (floatMode != SPIRV) break;` while sibling casts float unconditionally — but this is **not** a bug: the file-header design contract states textual mode (HLSL/GLSL/WGSL) intentionally emits NO decoration and treats `NonUniformResourceIndex`/`nonuniformEXT` as *hints* the downstream compiler propagates (the wrapper only needs to be *near* the index), whereas SPIR-V's `OpDecorate NonUniform` is position-specific and is the only consumer that needs the wrapper floated to the exact access index. So the correct adjudication is APPROVE_WITH_NITS, filing HLSL/GLSL round-trip floating as a pre-existing, unproven, separately-scoped follow-up ([slang #12116: NonUniform float-pass guard-asymmetry is a nit, not a bug](../learnings/1784536684181-slang-12116-nonuniform-float-pass-guard-asymmetry-.md)). Verified at ToT (6a244fee29): for BOTH the `ResourceDescriptorHeap[NonUniformResourceIndex(i)]` subscript and the `DescriptorHandle<T>.Handle` spellings, textual emit is identical and the marker lands **nested inside `uint2(...).x`** (HLSL `ResourceDescriptorHeap[uint2(NonUniformResourceIndex(tid.x), 0U).x]`, GLSL `nonuniformEXT` inside `uvec2(...)`), because `master`'s switch has no `MakeVector`/`CastUInt2ToDescriptorHandle` case at all. Whether DXC/glslang honor the flag from that nested position is a downstream/hardware semantic not reproducible GPU-less, so the right disposition for tracking items like #12161 is triaged → HOLD awaiting hardware verification, and any future textual-mode fix must be gated on a failing downstream test (bigger blast radius: HLSL/GLSL/Metal/CUDA/CPU) ([NonUniform on DescriptorHandle round-trip lands nested in uint2(...).x on textual targets (HLSL/GLSL) by design](../learnings/1784539603707-nonuniform-on-descriptorhandle-round-trip-lands-ne.md)).

## spvBindlessTextureNV Producer/Consumer Breadth Mismatch, Source-Text Embedding, and -O0 as a spirv-opt Proxy (2026-07-22 fold)

**`slangc -target spirv -capability spvBindlessTextureNV` on a non-image/sampler `DescriptorHandle<T>` aborts (`Unsupported result type for CastDescriptorHandleToResource`, E99997) because of a producer/consumer breadth mismatch, not an emit-only bug.** The producer arm `case spvBindlessTextureNV:` in `hlsl.meta.slang` (~27784) forwards EVERY descriptor kind to `__castDescriptorHandleToResource<T>` unconditionally, while every sibling arm (hlsl, spirv-glsl, spvDescriptorHeapEXT) `switch`es on `T.kind`; the consumer switch in `slang-emit-spirv.cpp` (~5121) handles only `kIROp_TextureType`/`kIROp_SamplerStateType` with `default → SLANG_UNEXPECTED`. Triage heuristic: when an emit-side `SLANG_UNEXPECTED` fires only under a specific `-capability`, check the core-module (`.meta.slang`) dispatch that PRODUCES the IR op — a capability arm forwarding all kinds to one op while siblings kind-dispatch is the classic over-broad producer; principled fix is producer-side kind-dispatch + hardening the emit `default` to a diagnostic (the AS conversion op `OpConvertUToAccelerationStructureKHR` already exists on the desc-heap path but consumes heap+index, not a bare uint64 handle) ([spvBindlessTextureNV DescriptorHandle abort — producer over-broadcasts to unhandled emit switch](../learnings/1784687930584-slang-12185-spvbindlesstexturenv-descriptorhandle-.md)). The follow-up fix taught a sharper rule: a legalization guard that mirrors the emitter's "encodable" accept-set MUST be a single shared predicate both call sites use — hand-maintained copies drift. Here the accept-set `kIROp_TextureType || kIROp_SamplerStateType` was WRONG (omitted `kIROp_SamplerComparisonStateType`, which registers as `DescriptorKind.Sampler` and IS encodable via `OpConvertUToSamplerNV`), so widening the guard alone turned an abort into a *wrong diagnostic*; extract `isBindlessTextureNVEncodableResourceType(IRType*)` (unwraps attributed types, matches `kIROp_TextureType || as<IRSamplerStateTypeBase>`) and add `case kIROp_SamplerComparisonStateType` to the emit switch — enumerate an op family via the `*TypeBase` class, never a leaf-op list ([emit-switch accept-set + a mirroring legalization guard must share ONE predicate — comparison-sampler drift](../learnings/1784697407327-emit-switch-accept-set-a-legalization-guard-that-m.md)).

**Whether shader INPUT SOURCE TEXT is embedded in SPIR-V (NonSemantic `DebugSource`/`DebugSourceContinued`) is decided at TWO layers, both keyed on `-g` level — there is no single hook (#12181).** Producer (IR gen, `slang-lower-to-ir.cpp:15425`): at `-g0` no `IRDebugSource` inst exists at all, `-g1` it exists with EMPTY content, only `-g2/-g3` stuff the source in; `DebugCompilationUnit` only at `>= Standard`. Consumer (`slang-emit-spirv.cpp:2164`, `case kIROp_DebugSource`): `Minimal` emits just the filename `OpString` and returns. So a feature to "embed source at a lower `-g` level / behind a flag" CANNOT flip the emit gate alone — it must thread through BOTH layers, and the `-g0`-with-source case additionally needs a minimal `DebugCompilationUnit`+`SPV_KHR_non_semantic_info` to stay spirv-val-clean. Don't confuse the plain `OpSource Slang 1` (language/version only, bypasses `-g0` gating). A new bool CLI flag appends cleanly (`CompilerOptionName::DebugInfoIncludeSource` before `CountOf`, `pr: non-breaking`) mirroring `-separate-debug-info` ([SPIR-V source-text embedding is gated at TWO layers (producer + consumer), both keyed on -g level](../learnings/1784666850986-slang-spir-v-source-text-embedding-is-gated-at-two.md)). Reviewing the actual `-debug-info-include-source` PR #12202 surfaced two more producer-side traps that the single most-scoped reviewer missed entirely. First, there are **TWO `IRDebugSource` producers** — the per-source-file loop in `slang-lower-to-ir.cpp` (~15428) AND a per-location `getOrEmitDebugSource` (~9717) that the entry point's location decoration points at; widening content-embedding in one but not the other lets `emitCoreOpSource` emit `OpSource` with a `File` operand but EMPTY `Source` whenever the entry point's resolved `SourceFile*` differs from the file-loop's cached one, so thread `shouldIncludeSourceInDebugInfo()` into BOTH producers. Second, the **producer ternary is target-agnostic** — an unguarded SPIR-V-documented flag silently reaches the LLVM backend (`-target llvm -g1 -debug-info-include-source` embeds source where `-g1` alone would not), diverging from the `-separate-debug-info` precedent that warns per non-SPIRV target; gate the producer override on a SPIRV target and/or add a symmetric `...IgnoredForTarget` warning ([two IRDebugSource producers; the producer ternary is target-agnostic (#12181/#12202)](../learnings/1784822669473-slang-debug-info-include-source-12181-12202-second.md)). A related output-quality nit in the same rework: the `emitSource` path emits the long-standing bare fileless `OpSource <lang> <ver>` unconditionally *and then* the new per-file file-carrying `OpSource` records — but SPIRV-Tools' source extractor treats every `OpSource` as a file, so the bare one materializes a spurious empty `unnamed-0.hlsl`. spirv-val passes (multiple `OpSource` is legal), so this is invisible without a consumer-side check; restore mutual exclusivity by emitting the bare `OpSource` only in the no-embed/early-return branch. (The -g2/-g3 path is unaffected — its per-file records are NonSemantic `DebugSource`, not `OpSource`.) ([bare fileless OpSource coexisting with file-carrying OpSource → spurious 'unnamed' source (#12202)](../learnings/1784851566899-slang-spir-v-emitting-a-bare-fileless-opsource-alo.md)).

**`-O0` runs ZERO spirv-opt passes and is a faithful "no spirv-opt" proxy; spirv-opt is size/perf-only, not correctness.** The emit-path gate `needsOptimization = getOptimizationLevel() != None` maps `None` → downstream `None`, making `glslang_optimizeSPIRV` early-return; Slang self-legalizes via the always-on `legalizeIRForSPIRV`, independent of `-O`. For any spirv-opt-benefit study, state the caveats in the verdict: binary SIZE ≠ GPU runtime (the driver re-optimizes), the corpus must include LARGE real shaders (the 50-70% size win doesn't show on tests/-only corpora), and there is no existing size/perf regression harness (fresh tooling needed) ([-O0 is a faithful "no spirv-opt" proxy; spirv-opt is size/perf-only, not correctness](../learnings/1784653425624-o0-is-a-faithful-no-spirv-opt-proxy-spirv-opt-is-s.md)).

## DescriptorHandle Representation, [require]-Bindless Selection, and Precise/RayQuery Lowering (2026-07-23 fold)

A cluster of SPIR-V work on the `spvBindlessTextureNV` path this day pinned several load-bearing mechanisms. `DescriptorHandle<T>`'s SPIR-V representation is **capability-dependent**: `uint2` on the plain `spirv`/`glsl` path but a scalar `uint64` (`%ulong`) under `spvBindlessTextureNV`/`cuda`, so the AS cast in the bindless arm must be `RaytracingAccelerationStructure((uint64_t)handle)`, not the sibling `__asuint64((uint2)handle)` form which fails `spirv-val` on a scalar ([DescriptorHandle is uint64-native under spvBindlessTextureNV — and test a reviewer proposed-alt before agreeing](../learnings/1784762549887-descriptorhandle-is-uint64-native-under-spvbindles.md)). #12186's follow-up (make that width *kind-dependent* — uint64 only for texture/sampler kinds, uint2 for buffers/AS) generalizes to any "make a backend representation depend on a new discriminator" task: a capability-wide width decision is duplicated across MANY consumers (8 sites here — type emit, default-construct legalization, both byte-address cast selectors, IR layout, the sizeof/alignof peephole constant-fold that is easy to miss, plus AST layout + reflection), so grep every `implies(CapabilityAtom::X)`/`getUInt64Type` and run a dedicated PLAN_REVIEW pass hunting missed width sites; make the *classification* one IR predicate + a mirrored AST predicate rather than routing every site through one function. The highest-risk piece is the constant-emit path: `uint2`↔`uint64` casts emitted as identity aliases break under kind-dependent width — in a block emit a real `OpBitcast`, but at **module/global scope a constant `OpBitcast` is INVALID SPIR-V** ("Bitcast must appear in a block"), so you must materialize a correctly-typed constant by reading the operand's constant bits. Comparison/ordering ops must compare in the native representation (`lessThan` on uint2 ≠ packed-uint64 order) ([kind-dependent SPIR-V representation change: audit ALL width consumers + the constant-emit path (#12186)](../learnings/1784859574140-kind-dependent-spir-v-representation-change-audit-.md)). The deeper design lesson: the bindless-vs-descriptor-heap **accessor is selected at `specializeTargetSwitch`** reading *global* `getTargetCaps()` at module-link scope — the `implies(spvBindlessTextureNV)` gates in spirv-legalize/emit-spirv are downstream *consumers*, so touching them cannot honor a per-entry-point `[require]` ([bindless path is selected at specializeTargetSwitch, not the spirv-legalize gates](../learnings/1784780629812-slang-bindless-descriptor-heap-path-is-selected-at.md)), and entry-point `[require]` is lowered to an `IRRequireCapabilityAtomDecoration` never unioned into `getTargetCaps()` — honoring it needs per-entry-point reachability specialization, not a version-scan-style emit fix (which would yield incoherent `uint64`-typed/`uint2`-accessed SPIR-V) ([entry-point [require] never reaches specializeTargetSwitch — bindless half of #11631](../learnings/1784782055293-slang-12196-entry-point-require-never-reaches-spec.md)).

On diagnostics-in-legalize: a validation pass that renders a resource **type name** must run BEFORE `lowerBufferElementTypeToStorageType` erases it, but that early point still contains dead-after-`discard` code (a `[ForceInline]` helper not yet inlined) — the two goals trade off and the principled fix is to capture the type-name string early and defer only the emit ([diagnostic pass placement tradeoff: type-name rendering vs dead-code false-positives](../learnings/1784747930488-diagnostic-pass-placement-tradeoff-type-name-rende.md), extended by the E55215 post-OpKill triage in [slang-12191 E55215 post-OpKill dead-code diagnostic — capture the name early, defer the emit](../learnings/1784762307830-slang-12191-e55215-post-opkill-dead-code-diagnosti.md)). Two more relaxation/lowering traps: PR #12195's `-fvk-use-direct-resource-params` draws its gate as "any texture NOT rejected by GLSL" rather than "read-only texture," silently admitting FEEDBACK/UNKNOWN-access and (via a `unwrapArray` first) texture-array params — when a PR *relaxes* a rejection predicate, enumerate the full range of the discriminator ([SPIR-V direct-resource-param gate: relaxing isIllegalSPIRVParameterType leaks feedback/unknown/array textures](../learnings/1784772370437-spir-v-direct-resource-param-gate-relaxing-isilleg.md)); and `precise` is silently ignored on direct SPIR-V in DEFAULT fp-mode because `isFloatingPointModePrecise` reads only the global `-fp-mode`, never `IRPreciseDecoration`, so a complete fix must backward-propagate precise-ness through the FP fan-in before reusing the `maybeEmitNoContraction` choke point ([precise qualifier ignored on direct SPIR-V in default fp-mode — NoContraction gate reads global mode only](../learnings/1784785437426-precise-qualifier-ignored-on-direct-spir-v-in-defa.md)).

Two non-copyable-opaque **value-copy** ICEs share a root cause and belong to the same family as `#7455`/`#8002`: a `__constref ParameterBlock<T>` (or any opaque/resource type) gets temp-copied in `addArg` because `tryGetAddress` returns Simple-not-Ptr for a global, and the copy survives `processGlobalParam` (which only runs on `IRGlobalParam`) to ICE at emit — the fix belongs in IR copy-elision, NOT AST lowering (prior art PR #8008 was rejected 3× for the AST route) ([slang#8002 __constref ParameterBlock/opaque ICE — copied address-only value escapes global-only legalization](../learnings/1784754145569-slang-8002-constref-parameterblock-opaque-ice-copi.md)); and a plain function returning `RayQuery<...>` by value miscompiles because the callee inits a *fresh local* then value-copies the opaque handle into the return-dest — a bare `b = a` local copy miscompiles identically, so it is a general non-copyable value-copy defect, proven by **disassembling the actual output** to refute a confident-but-wrong source-only hypothesis ([RayQuery return-by-value miscompile = opaque value-copy, not missing return-dest transform (verify via disasm)](../learnings/1784785541306-rayquery-return-by-value-miscompile-opaque-value-c.md)). Finally, a tooling note for these fixes: prefixing internal `spirv_asm %registers` in `.meta.slang` must be brace-tracked and block-scoped — the same `%foo` tokens live in `__intrinsic_asm` LLVM/Metal strings that must NOT change, and a second generator (`slang-core-module-textures.cpp`'s C++ StringBuilder `spirv_asm`) is easy to miss ([renaming spirv_asm %registers in .meta.slang: block-scoped only, and core-module-textures.cpp is a second generator](../learnings/1784760040459-renaming-spirv-asm-registers-in-meta-slang-block-s.md)).

## Descriptor-Heap Acceleration-Structure Diagnosis + std140 Array-vs-Matrix Red Herrings (2026-07-26 fold)

Two recurring SPIR-V descriptor-heap support questions, both traced end-to-end from Discord diagnosis threads. First, **`DescriptorHandle<RaytracingAccelerationStructure>` + `spvDescriptorHeapEXT` crashes are a supported, regression-tested path** on builds ≥ v2026.11 (`tests/spirv/descriptor-heap-acceleration-structure*.slang` cover both RayQuery/compute and TraceRay/raygen) — so a crash there is almost always host-side, not a compiler bug. Two values people conflate: the **handle `uint2`** (`(slotIndex, 0)`, `.x` a raw heap index, `.y` only the sampler index of a combined texture-sampler) vs the **heap slot contents** (the 8-byte AS *device address* from `vkGetAccelerationStructureDeviceAddressKHR`, NOT the opaque `VkAccelerationStructureKHR`). Decisive diagnosis order: dump `-target spirv-asm` and grep `OpConvertUToAccelerationStructureKHR` (missing → old build reading the opaque handle → DEVICE_LOST; present → compiler fine), then VK GPU-assisted validation, then bisect slot-0-works-but-≥1-crashes → AS stride mismatch (`-spirv-resource-heap-stride`, #11231/#11494, a silent miscompile) ([Diagnosing DescriptorHandle<RaytracingAccelerationStructure> + spvDescriptorHeapEXT crashes](../learnings/1785051051163-diagnosing-descriptorhandle-lt-raytracingaccelerat.md)). The crucial correction to the "slot holds a uint64 device address" fact: that describes the **shader-side lowering only** — the `SPV_EXT_descriptor_heap` `ResourceHeapEXT` heap is **driver-managed** (slang-rhi backs it with `VK_DESCRIPTOR_TYPE_MUTABLE_EXT` in a `BindlessDescriptorSet`), so you populate the AS slot via the **descriptor-write API** (`vkUpdateDescriptorSets` + `VkWriteDescriptorSetAccelerationStructureKHR`), NOT a raw `memcpy` of the address. The raw-uint64 model is literally true only for a plain app buffer (`RaytracingAccelerationStructure(myBuffer[i])`), which is why "direct address works but the EXT heap doesn't." Diagnostic tell: direct-address + textures-in-heap work but AS-in-heap fails at **index 0 with the correct `.x`** ⇒ the host is memcpy'ing where a descriptor write is required; the escape hatch is a user-provided `getDescriptorFromHandle` override fetching from an app `StructuredBuffer<uint64_t>` of AS addresses ([spvDescriptorHeapEXT AS heap is driver-managed — descriptor write, NOT raw memcpy](../learnings/1785056296611-spvdescriptorheapext-as-heap-is-driver-managed-des.md)).

Second, the **"`float4[N]` in a cbuffer reads garbage but swapping to `float2x4` fixes it (esp. after a slangc upgrade + col→row-major switch)"** report has a std140 layout half and a descriptor-heap half. Layout fact: in std140, `float4[2]` (16B stride, 32B total) is **byte-identical** to a *row-major* `float2x4` (2 rows × 16B), while a *column-major* `float2x4` is 64B — and matrix-layout mode (`-matrix-layout-row-major/-column-major`) changes only matrices, never arrays (arrays always follow the fixed 16-byte std140 stride). So if the row-major matrix reads correct values from the same bytes the array reads garbage from, the shader-side layout is NOT the difference — the col→row switch just made the matrix match how the host fills the buffer while the array stayed put; suspect a host-side packing mismatch, verified via `spirv-dis | grep -E "Offset|ArrayStride|MatrixStride"` ([std140: row-major float2x4 and float4[2] are byte-identical — matrix mode doesn't touch arrays](../learnings/1785073305394-std140-row-major-float2x4-and-float4-2-are-byte-id.md)). BUT if the same report mentions **descriptor heap / bindless / `spvDescriptorHeapEXT`**, the col→row switch is a red herring and this is bug **#11483**: a `ConstantBuffer<T>` fetched through the heap lowers to an `OpBufferPointerEXT` in the **`Uniform`** storage class, and `getPointerArrayStrideValue` emits pointer-type `ArrayStride` only for `PhysicalStorageBuffer`/`StorageBuffer` (0 for Uniform) → nested-array offsets undefined → garbage, while a matrix dodges it via MatrixStride (won't scale past 4 rows). Fixed by **#11647** (retypes the heap CB load to StorageBuffer — tell users to update *forward*), with a follow-on regression **#12226** (descriptor *kind* fetched as storage-buffer instead of uniform-buffer, see the #12226 ABI note above). Scalable workaround: fetch via `StructuredBuffer<T>`/`DescriptorHandle<StructuredBuffer<T>>` (already StorageBuffer with correct strides) ([Discord: float4[N]-in-struct garbage + matrix works + descriptor heap = bug #11483](../learnings/1785073991889-discord-float4-n-in-struct-reads-garbage-matrix-wo.md)).

## Suite-wide spirv-opt (-O3) revives dormant SPIRV-Tools asserts (#12247, 2026-07-27 fold)

The `-O0` default (PR #11805, `slang-glslang.cpp:275` early-out at `SLANG_OPTIMIZATION_LEVEL_NONE`) **masks** real spirv-opt aborts, it doesn't fix them — forcing `-O1/-O2/-O3` re-runs the same registered pass list and resurrects any latent assert. This is why #11766/#11767 (fp8 folding abort) were closed COMPLETED and the `scalar-fp8.slang (vk)` expected-failure removed (#11922): the abort stopped firing under `-O0`, not because SPIRV-Tools was fixed. So a "resolved" spirv-opt issue from the #11805 era may just be dormant, and #12247's suite-wide-opt scenario revives it. A debug-build `assert()`→`abort()` bypasses Slang's graceful `messageConsumer`/`SLANG_FAIL` path (which only catches a SOFT `Optimizer::Run()==false`), so on Windows a sibling test's hard abort masquerades as "exit code 3 / hang >60s / lost JSON-RPC worker" (Linux: clean SIGABRT 134) — verify each suspect standalone. Two live assert sites: fp8 (FloatE4M3/E5M2) + CoopVec<float> constants → `folding_rules.cpp:156/:3539` (float folder rejects width-8; the sibling INT folder at `:142` accepts it), and `spirv_asm{}` emitting `OpMemberDecorateIdEXT` → `aggressive_dead_code_elim_pass.cpp:1000 default: assert(false)`. Triage shortcut for a big "N tests fail under opt" list: compile a sample at `-O3` with the test's real `-entry`/`-stage` flags — EXIT 0 = benign FileCheck drift (opt legally rewrote output → fix is test-side), EXIT 134 = a real abort worth a sub-issue (~77 of 79 here were benign) [Suite-wide spirv-opt (-O3) revives dormant SPIRV-Tools asserts (#12247, revives #11766/#11767)](../learnings/1785203893114-suite-wide-spirv-opt-o3-revives-dormant-spirv-tool.md).

## Descriptor-Heap CB Typed-vs-Untyped Pointer + -g2 DebugLine Is Marker-Driven (2026-07-28 fold)

Two SPIR-V mechanisms pinned by the #12226 re-open investigation. First, the descriptor-heap `ConstantBuffer` **Uniform-vs-StorageBuffer** question resolves to a **typed-vs-untyped buffer-DATA pointer** distinction: Slang's `emitDescriptorHeapLoad` emits the buffer-data pointer as `OpBufferPointerEXT` whose Result Type is a **TYPED IRPtrType**, so field/element access becomes a typed `OpAccessChain` — and a typed pointer to an *array element* needs a pointer-type `ArrayStride`, emitted only for StorageBuffer/PhysStorageBuffer (which is why #11647 flipped struct-CB heap fetches to StorageBuffer). glslang instead uses an **untyped Uniform** data pointer + `OpUntypedAccessChainKHR` passing the block-struct type (stride from the type's decorations, logical addressing), so Uniform works with no pointer-ArrayStride. Two framing corrections: Slang ALREADY emits typed **Uniform** `OpBufferPointerEXT`+`OpAccessChain` for scalar/vector/matrix CB heap elements (validated), so "Uniform can't address a CB element" is false in general — it's specifically *array-element* addressing through a typed pointer; and the StorageBuffer flip is OVER-BROAD (`processConstantBufferDescriptorHeapLoad` gates on EVERY struct, even no-array structs) so it could be narrowed to structs actually containing arrays. The glslang-style untyped-Uniform path is spec-legal but NOT localized — Slang threads element-type + address-space solely through the typed IRPtrType across the whole legalize→emit pipeline (only 3 `OpUntypedAccessChainKHR` sites exist, none doing field/element access on buffer data), so it needs ~5-8 new untyped-aware consumers, an emitter-architecture extension rather than a class flip; jkwak's `-spirv-unified-descriptor-heap-stride` workaround fixes STRIDE, not descriptor KIND ([descriptor-heap ConstantBuffer: typed-vs-untyped OpBufferPointerEXT — Uniform IS possible via the untyped path but Slang's typed pipeline makes it non-local](../learnings/1785256702253-slang-descriptor-heap-constantbuffer-typed-vs-unty.md)).

Second, a debug-info fact with a hard testability consequence: **`-g2 DebugLine`/`-g1 OpLine` are emitted ONLY from explicit `IRDebugLine` MARKER instructions**, which the front-end places at STATEMENT granularity (`lowerStmt`→`maybeEmitDebugLine`, keyed to `stmt->loc`) — function-body value insts (`OpAccessChain`/`OpLoad`/etc.) do NOT independently emit a DebugLine from their own `sourceLoc`; they fall under the last statement marker. So propagating `sourceLoc` onto re-synthesized value insts (via `IRBuilderSourceLocRAII`) has ZERO effect on emitted SPIR-V debug lines — a revert-drill (`-g1/-g2/-g3 -emit-spirv-directly`) shows byte-identical output, making a "-g2 golden the fix changes" impossible for a pure value-inst sourceLoc fix. The only consumers that surface a value-inst's `sourceLoc` are diagnostic sites reading `inst->sourceLoc`/`findFirstUseLoc(inst)` (e.g. `slang-ir-check-unsupported-inst.cpp`); if none fires on the input, the hygiene fix has no writable test — surface that to the maintainer ("name the test that fails without the change") rather than shipping an untestable change, and verify the edit is actually in the binary (`slangc` links `libslang-compiler.so`; `-dump-ir` doesn't print locs) ([Slang -g2 DebugLine is statement-marker driven, not per-value-inst sourceLoc (#12192)](../learnings/1785275556385-slang-g2-debugline-is-statement-marker-driven-not-.md)).

## Four Consumer Guards for One Defect ⇒ the Hole Is in the Producer (#12186, 2026-08-03 fold)

The kind-dependent `DescriptorHandle` width work produced a clean instance of a general escalation rule. Four successive emit-time guards were written for what looked like one defect (`SLANG_UNIMPLEMENTED` → representation-mismatch diagnostic → operand-type diagnostic → operand-type + wrap-chain walk), each catching a *different* subset; guard #4 had to walk the operand graph to recover the initializer's width, which slang's own contributor guidance flags as a smell ("context rediscovery by graph walking … usually downstream repair"). The actual root is upstream and singular: in `hlsl.meta.slang` the handle read-back conversions (`extension uint2 { __init<T>(DescriptorHandle<T>) }` and its `uint64_t` sibling) are **capability-gated but not kind-gated**, so once the representation became kind-dependent, "build at width A, read at width B" became *expressible*. That one hole surfaced in ≥3 consumers — module-scope constant (invalid `OpIAdd %ulong` on a `%v2uint` → spirv-val error), function-scope cast (the runtime path compares representation-vs-named width, sees a match, forwards the wrong width), and inside descriptor-heap lowering (`((uint2)h).x` on a uint64 → `OpCompositeExtract %uint %ulong_… 0`, an extract on a scalar, tripping spirv-opt's `const_folding_rules.cpp:129: cc != nullptr` assert).

**Heuristic:** when the *second* guard for one logical defect misses a case, stop patching consumers and go find the producer — and if the same wrongness appears at module scope AND function scope AND inside a lowering pass, that is one upstream hole, not three bugs. Escalate the producer fix (especially when it is public `.meta.slang` surface needing maintainer approval) rather than self-directing a fifth consumer guard. Companion rule for choosing between a diagnostic and an assert at such a site: ask "can plausible user code reach this shape?" and **test it** rather than reasoning — both `DescriptorHandle` integer constructors are public and capability-permitted for every kind, so a fallback-texture-handle-packed-as-`uint2` shader reaches it, and an assert would have violated the issue's own "must not abort with an internal error" acceptance text. Reachable ⇒ diagnostic; unreachable ⇒ assert plus a written justification in the PR ([four consumer-side guards mean the root cause is upstream — kind-ungated handle read-back conversions](../learnings/1785776557998-cite-the-spec-not-a-summarizer-spv-nv-bindless-tex.md)).
