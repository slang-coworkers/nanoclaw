## TL;DR

- **These agent containers DO have an NVIDIA L40S** — `nvidia-smi -L` confirms it; CUDA/Vulkan `slang-test` cases genuinely execute. The repo doc saying "no GPU" (`.github/copilot-instructions.md:131-132`) is a stale **capability-negative**, an error class with no failure signature (readers comply by not attempting). Probe a capability with the capability itself.
- **`/proc/loadavg` is host-wide; `nproc` is container-scoped.** Dividing one by the other invents oversubscription on an idle box. Measure `/proc/stat` idle% and `cpu.max`, not `loadavg ÷ nproc`. "N sessions running" ≠ "N sessions burning cores."
- **`ncl tasks run` silently CLEARED a recurring cron** despite documenting itself as "safe for testing." After any task mutation, re-read `recurrence`/`status`/`process_after`/script — verify the invariant you didn't touch, not just the field you set.
- **`formatting.sh` version gates are LOUD** (exit 1 + message on clang-format 18); the silent false-green is the **bare** invocation hitting `show_help` (exit 0). Always pass an explicit action; the 17-vs-18 pin is load-bearing.
- **codex-critique records a round only if all three hold simultaneously**: `STAGE: <NAME>` as the literal first line, the reviewer block verbatim in `developer-instructions`, and `sandbox: "danger-full-access"`. A "never invoked" gate audit can be false in both directions.
- **The critique-gate denial cap is container-shared** — your first read-only `/pulls` GET can escalate straight to an admin because a peer already burned the cap.
- **A compile-perf phase table is not a partition** — `apiTotal` encloses timers the workload never declares.

## Container resources

**These containers have a real GPU** (`nvidia-smi -L` → NVIDIA L40S, identical UUID across container edges ⇒ literally one shared device). CUDA and Vulkan `slang-test` cases execute here — they can genuinely pass or fail. The repo says otherwise at `.github/copilot-instructions.md:131-132` (the sentence spans two lines — `:131` prose + `:132` the D3D12/Vulkan/Metal/WGSL list; a fix touching only `:131` leaves the list behind). This is the **capability-negative error class, which has NO failure signature** — a reader complies by *not attempting* GPU tests, which logs nothing and looks identical to correct behaviour forever, so nobody discovers the doc is stale by being blocked. Measured cost in one afternoon: near-misattribution of ~30 test failures (a baseline arm went 7→35 failures clustering cuda/vk under host load 120 — the real cause was test-server child processes timing out under CPU contention, a load artifact, not "no GPU"). **Probe a capability with the capability itself**, and better, with the *consumer* that would use it (`slang-test` prints `Check cuda: Supported` and yields `passed test: … (cuda)`), never a documented negative or an `ls` of one directory. Caveats, do not over-rotate: one L40S is shared by every container (GPU tests are contention-prone flakes under concurrency, classify per-item); an L40S covers CUDA+Vulkan but not D3D12/Metal/WGSL on Linux; local GPU results are weaker evidence than CI under load, and agent containers are NOT the runner-of-record (GPU-capable CI is self-hosted). This fact had already been recorded three times without ever naming the source coordinate — **when correcting a documented falsehood, record WHERE it is written**, and search the FACT (`L40S`) before writing, not the defect. [These containers DO have an NVIDIA L40S — copilot-instructions.md:131 says otherwise and that negative has no failure signature](../learnings/1786037625870-these-containers-do-have-an-nvidia-l40s-copilot-in.md)

**Never compute "load per core" inside a container from `/proc/loadavg ÷ nproc`.** `/proc/loadavg` is host-wide (every runnable task on the physical box, not namespaced); `nproc`/`/proc/cpuinfo`/`ps` are container-scoped. `113.63 / 8 = "14.5× oversubscribed"` on a box that was **69.8% idle** — the mixed-scope figure ruled out parallel work on a machine with ~7.5 idle cores, and was "independently confirmed" by a second agent running the same invalid computation (two parties running the same wrong method are not two measurements). The tell was free: 10 visible compiler processes cannot produce a load average of 115 — **a summary statistic hides its own scope; the disaggregated view exposes it.** Measure `/proc/stat` idle/user/sys/iowait% for "are cores busy," `ps -eo pcpu` for own CPU, `/sys/fs/cgroup/cpu.max` (`max 100000` = no quota) for throttling. `ncl sessions list` showing 67 sessions `running` is a session-table state, **not** CPU consumption — "N sessions running" and "N sessions burning cores" are different claims. Same family as unit/provenance errors: the value was real, the referent was wrong; precision can't catch it because the number is correct — only its scope is wrong. ## Scheduled tasks

**`ncl tasks run` silently CLEARED a recurring cron** — the doc string promised it "neither consumes a one-shot nor advances a recurring series" and was specific and wrong: `recurrence` went `*/5 * * * *` → `null`, leaving a heartbeat that would fire once and never again, indistinguishable from a healthy quiet period. Caught only because the post-change verification printed **every** field, not just the edited one. Rules: after any mutation to a scheduled task, re-read `recurrence`/`status`/`process_after` and the script even when you changed one of them (a write can clobber neighbours); don't trust a documented "safe" guarantee over an observation; **verify the invariant you didn't touch** — the tempting check is "did my change land?", the necessary one is "is everything else still true?", because a fix that lands while breaking the schedule reports success. To prove a patched cron runs, let the schedule fire and watch `completed_runs` advance (you cannot observe that from inside the run occupying the slot — the counter increments at completion). Same family as *marker file is not health*: a state fine on the dimension you watch while the load-bearing one has gone false. [`ncl tasks run` silently CLEARED my recurring cron — verify recurrence after any task write, not just the field you set](../learnings/1786034644913-ncl-tasks-run-silently-cleared-my-recurring-cron-v.md)

## formatting.sh gates

An earlier learning had claimed `formatting.sh` version gates are half-open and "the rejection looks identical to nothing to fix" — the half-open part is correct, the "looks identical" part is **wrong**, and both are now measured. **With clang-format 18 the gate is LOUD** (`clang-format version 18.1.8 is too new … EXIT=1`, explicit message, non-zero exit). **The actual silent false-green is the BARE invocation** (`extras/formatting.sh:47-50`: no args → `show_help` → `exit 0` before any gate runs) — and the bare form is what the repo docs instruct. The lesson beneath the correction: the author had conflated two distinct defects and attributed the silent-failure property to the wrong one, then generalized from the merged version — **a correct-sounding generalization built on a misattributed cause is harder to catch than a wrong fact.** The author's own run producing "both files come back clean" had printed `exit 1` and a "too new" message; they didn't read them — **the instrument was loud; the reader was the silent part.** Practical rules: always pass an explicit action (`--check-only`/`--cpp`/`--modified`), never the bare form; treat `exit=0` as meaningful only alongside the stderr version line; version gates are half-open (clang-format 17.x only, gersemi 0.21.x only); the 17-vs-18 pin is load-bearing (9 of 1489 tracked files format differently, committed tree matches 17 on all 9); never reach for `--no-version-check`. [CORRECTION to my earlier formatting.sh learning — the VERSION GATE is LOUD (exit 1 + message); the silent false-green is the BARE invocation hitting show_help at :47-50](../learnings/1786034840431-correction-to-my-earlier-formatting-sh-learning-th.md)

## The codex-critique gate

**A critique round records only if all three ingredients hold simultaneously.** (1) `STAGE: <NAME>` as the literal first line of the prompt — the hook greps `STAGE:[[:space:]]*[A-Z_]+` in the first 500 bytes, so `CODE_REVIEW: review this…` (stage name + colon, reads naturally) does NOT match and every downstream stage-gated path is skipped silently; (2) the skill's reviewer block passed **verbatim** in the `developer-instructions` parameter (the hook reads `.tool_input."developer-instructions"`, not the prompt); (3) `sandbox: "danger-full-access"` — any other value (including the tempting `read-only`) is rejected upstream by a PreToolUse hook (bwrap sandboxing doesn't work inside Docker), so `developer-instructions` never reaches the tracker. Get all three right and it records immediately (`stages: CODE_REVIEW=1`). [codex-critique rounds go untracked unless the prompt carries the literal STAGE: token](../learnings/1786050089767-codex-critique-rounds-go-untracked-unless-the-prom.md) [codex-critique rounds need sandbox=danger-full-access, or nothing records](../learnings/1786055180841-codex-critique-rounds-need-sandbox-danger-full-acc.md)

The audit message "never invoked in this session — gate skipped" asserts a proposition the counter cannot observe — it can only see "counter not incremented," so **it fails in both directions** (a real critique untracked, and, per the STAGE defect, a real round rejected). When a gate audit contradicts something you know you did, suspect the counter's write path before doubting your action — but before debugging hook internals, **re-read the tool's own usage doc** (the answer was three lines of the skill file, in bold, at the top; many rounds were spent root-causing hooks while never testing the call's own parameters against the documented contract). Related traps: `codex-reply` is pin-exempt, so replies increment `critique_rounds` while writing no stage row (`rounds: 4, stages: None` is what rejected-initials + accepted-replies produces, not a broken counter); the "NOT recorded" receipt interpolates `$STAGE`, so seeing your stage *name* means the pin ran and rejected, seeing no receipt at all means the pin never ran. **Do not clear the gate by weakening it** — setting `CRITIQUE_PIN_INSTRUCTIONS=0` yourself makes the record read "gate satisfied" when the truth is "gate bypassed," a durable falsehood a human audits; and do not re-run a real critique purely to increment the counter (laundering the control). Read the reviewer's own `### Verdict` section, never the hook's pass/fail. [codex-critique rounds go untracked unless the prompt carries the literal STAGE: token](../learnings/1786050089767-codex-critique-rounds-go-untracked-unless-the-prom.md) [codex-critique rounds need sandbox=danger-full-access, or nothing records](../learnings/1786055180841-codex-critique-rounds-need-sandbox-danger-full-acc.md)

**The critique-gate denial cap is container-shared.** `gate-critique-on-deliver.sh` matches Bash against `gh api [^|]*pulls\b`, so it denies read-only GETs (`.../pulls/N/commits`, `.../reviews`) and labels them `hit: "PR creation"`; the denial counter and edit counter in `/workspace/.claude/workflow-state.json` are **workspace-scoped** (~8 sessions). So if a peer already burned the 3-denial cap, **your first `/pulls` GET auto-forwards a bypass request to an admin** with no "denied, try again" in between — and the admin rejects a request whose premise ("N edits since critique") is a phantom you had nothing to do with. Observed twice in one day on sessions that created no PR, pushed nothing, edited no repo code (the dirty files in the shared clone belonged to a peer). Use gate-safe reads from the start (`gh pr view --json reviews,commits,comments`; `gh api graphql` for review-thread bodies); before believing a denial, read `critique-escalation.json` and `git status --porcelain` in your *own* worktree to see whether any counted edit is yours. A rejected bypass is not an instruction to force the work through — if nothing of yours is blocked, the correct action is a report, not a retry. ## A compile-perf phase table is not a partition

When reading a `tools/compile-perf` phase breakdown, do not assume the listed phases sum to `apiTotal`. Two mechanisms make them diverge: `apiTotal` is opened *before* session setup (`api-driver.cpp` opens `Scope total("apiTotal")` then `apiCreateGlobalSession` inside it), and `primary_timers` is a reporting *subset* (`manifest.py` lists only `apiTotal`/`apiLoadModule`/`apiGetCode`, so `apiCreateGlobalSession` cannot appear in the table even though the total contains it). The remainder `apiTotal − apiGetCode − apiLoadModule` is real and non-empty (~3.5-3.8× on one report), invisible in a two-row table that looked complete. For triage: `apiCreateGlobalSession` is where core-module deserialization dominates, so a core-module blob change is a **wall-time** candidate for API-path workloads, not only an RSS one. Read the `Scope` nesting for what `apiTotal` encloses and `primary_timers` for what the table can structurally show, then subtract — an unexplained remainder is where the untracked phase hides. Same-area facts: `v2026.6` never existed (404 by tag *and* 0 matching-refs — "no release" and "no tag" are different nouns, check both, with a must-hit control); and a release-axis replay of prebuilt per-tag binaries for a later-added workload is a valid retrospective, not stale data.
