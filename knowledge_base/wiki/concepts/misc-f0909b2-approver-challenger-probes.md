## TL;DR

- **A reviewer's finding defines a location, not a scope.** When a finding points at a lifetime, audit *every* non-owning member of the retained object; when it points at a depth-based predicate, audit *every* depth; when it names "both the X and Y path", verify each independently. The adversarial question is not "is this finding true?" but "what else of this kind is here that nobody asked about?"
- **A comment that asserts the exact safety property in question marks the spot to verify, not a reason to skip it.** ("Outlives this decoder…" — the module kept no such thing alive; a use-after-free.)
- **Before reporting any absence, ask what would have to be true for the probe to return non-zero.** If you can't name a realistic case, it's a tautology wearing a measurement's clothes. A submodule-absence grep over `compare/main...head` is *structurally zero* unless the PR changes the pointer relative to *its base* — a zero that carries no bits.
- **A count is uninterpretable without its instrument.** Two agents reporting "matches" from prose-described filters aren't reporting the same quantity; ship the literal (`grep -icE "<exact pattern>"`) beside the number. A pattern is a claim about a naming convention, and conventions aren't uniform even inside one directory (`bc_codec.cpp` matches `bc[0-9]`, `bc_types.h` doesn't).
- **"Pre-existing?" is settled by a base-blob diff, and it cuts BOTH ways** — it catches a newly-added defect you'd wave off, and exonerates a PR from a latent bug it merely restructures with identical gating. Diff against the PR *base commit*, not the prior revision, not the head in isolation.
- On a **rebased** revision the inter-head compare is mostly upstream noise; measure the PR's own surface as `compare/base...head` and read `ahead_by`/`behind_by` (behind_by→0 while merge_base advances *is* the rebase signature).
- **A negative mutation-test result indicts the mutation first** — reproduce the ORIGINAL bug's exact shape before concluding a self-check doesn't catch a regression.
- **A bot's "this gate is inverted / a no-op" finding is only as good as its reading of the return-value semantics** — open the predicate, confirm what true/false *mean* and the controlled variable's *default*, before crediting or blocking.
- **A correction is a new claim** — measure the replacement, never derive it from the thing you just disproved; low-stakes numbers are where correction discipline decays.

## A finding is a location, not a scope

The unifying challenger lesson: verify the claim you were handed and you have covered a *point*, not its *neighbourhood*. On slang#12446 (lazy IR body deserialization) a challenger correctly refuted a CodeRabbit dangling-data-view claim but missed two gaps the primary review found in the same file — a use-after-free on the raw `readContext` pointer eight lines above the field studied, and a depth-3 decoration whose children the deferral predicate never marks [[I traced one lifetime and stopped: a retained object's OTHER raw pointers need the same audit]](../learnings/1786437320065-approver-challenger-miss-i-traced-one-lifetime-and.md). The generalizable probes: when an object is newly made to *outlive the scope that built it*, the unit of audit is *every* non-owning member (grep the struct for `*` fields and references; for each ask who owns it and whether that owner outlives the retained object); and a predicate written in terms of a fixed depth is an assertion the tree is that shallow — test it against the deepest shape the data permits, not the shape the comment describes. Critically, **a comment that asserts the exact property in question is the highest-value thing to falsify** ("Outlives this decoder: it belongs to the read serializer…" — false), not a reassurance to read past. The same shape governs slang#12466: a CodeRabbit "apply to BOTH the differential-pair AND AnyValue paths" was cleared by proving the *AnyValue* branch was moved verbatim — but the finding also targeted a PR-**new** sibling branch, and a verbatim-move proof about one branch says nothing about a newly-added one beside it [["moved verbatim" refutes a regression, not a latent bug in NEW sibling code]](../learnings/1786496403182-approver-challenger-miss-moved-verbatim-refutes-a-.md). When a shape is gated on a pointer *subtype*, enumerate the full sibling set (`IRBorrowInParamType`/`IRRefParamType` are `IRPtrTypeBase` but not `IRBorrowInOutParamType`) so the init-guard and writeback-guard cover the same direction set; and green CI on the covered directions says nothing about the suspect branch.

## Negative evidence needs a positive control — that could actually fire

Two corrections chained on slangpy#1050 make the negative-control rule unusually sharp. The original miss: asserting `external/slang-rhi`: 0 matches over `compare/main...head` as a verified capability-negative clearing a submodule concern — but the pointer is identical on both sides at both revisions, so the zero **cancels by construction** and carries zero bits [[a submodule-absence probe against main is structurally zero]](../learnings/1786447289145-approver-challenger-miss-a-submodule-absence-probe.md). The correct reading is "the PR does not change the pointer relative to its base," never "the PR is unaffected by slang-rhi"; the blind-free probe compares the pointer at the head against the *previous revision's* head. The first correction then noted the positive control was **asserted, not executed** — a regex that silently fails to fire also returns 0, so "a texture-touching bump would have matched" must be *run*, both arms, one variable; and the pattern `bc[0-9]` has a false-zero gap (`bc_types.h` has an underscore, no digit) [[correction: the BC/texture regex has a false-zero gap; the positive control is now executed not asserted]](../learnings/1786447581475-approver-challenger-miss-correction-to-the-submodu.md). The second correction *retracted the attribution*: the 12-vs-13 count difference belonged to a pattern **reconstructed from prose** (`bc[0-9]`), not the one actually run (literal `bc`) — neither count was wrong, and "a count is uninterpretable without its instrument" is the durable rule [[RETRACTION — the bc_types false zero belongs to a pattern I reconstructed from prose]](../learnings/1786447743725-approver-challenger-miss-retraction-the-bc-types-f.md). Note the recursion the corrections name explicitly: *invoking* "negative evidence needs a positive control" as justification is itself the error the rule exists to prevent — the rule is satisfied by running the control, never by citing it. (Instrument aside repeated across all three: `gh api --jq` takes no `--arg`; inline the literal or pipe to a separate `jq`.)

## Rebase-aware diffs and base-blob attribution

Two atoms establish how to attribute a diff correctly. On a **rebased** revision, the natural `compare/<R2>...<R3>` between two heads reports everything the branch caught up on — 7 commits / 42 files including an unrelated submodule bump — while the PR's own surface vs its base is 27 files and doesn't include the submodule at all [[on a rebased revision the inter-head compare is mostly upstream noise]](../learnings/1786439567969-approver-challenger-miss-on-a-rebased-revision-the.md). The cheap discriminator is `ahead_by`/`behind_by` against the base: `behind_by` collapsing to 0 while `merge_base` advances *is* the rebase signature (push-only revisions keep the same merge_base). Failure modes with opposite signs: reviewing four upstream PRs' worth of borrowed code, or firing a well-precedented submodule-bump probe against a bump the PR doesn't own — a good prior pointed at the wrong diff. Always measure the PR's surface as `compare/<base_branch>...<head>` (the metric `eval-clauses.py` uses), and test membership by explicit filter (`jq '[.files[]|select(.filename|test("slang-rhi"))]|length'`), not by eyeballing — and verify a file-count change by set difference (`comm -13`), never arithmetic, since a count delta identifies a net, never the composition.

The positive counterpart is the **base-blob diff**, which settles "did this PR introduce or worsen it?" and cuts both ways [["pre-existing?" is settled by a base-blob diff, and it cuts BOTH ways]](../learnings/1786486818801-approver-challenger-confirmed-pre-existing-is-sett.md). On slang-rhi#831 R5 it caught a newly-added contract mismatch previously waved off as pre-existing (`action.yml` "pinned" → "the"), and exonerated the PR from a genuine latent VUID-violation path it merely restructured — the blob diff at base `632b0aee` proved `vk-heap.cpp` already gated on the enabled feature under the proc-only guard, so a refactor preserving identical gating conditions doesn't take ownership of a producer-side (`device.cpp`) bug on an untested path. The reliable answer comes from diffing the relevant lines against the **PR base commit** (`gh pr view --json baseRefOid`; read files at base via `contents?ref=<base>`), not the prior revision or the head alone. When base-diff shows semantics preserved and the risk lives in untouched producer code, it's advisory (flag a separate issue), not an OPEN_GAP for this PR.

## Verify a self-report and a bot finding by tracing the actual value

Two atoms discipline how you credit *claims*, not just code. A self-reported fix is verified by **reproducing the original bug's exact shape** before drawing any conclusion from a mutation — on slang#12125 R4 a first mutation (`if False:` on the inner guard) routed the zip into a still-returning branch and gave IMPORT OK, which was tempting to score as "the self-check doesn't catch the regression" but was the *mutation* being wrong; only restoring the true pre-fix shape (`os.name != "nt"` gating the whole block) reproduced the `AttributeError` [[verify an author's self-reported fix by reproducing the ORIGINAL bug shape — a negative mutation indicts the mutation first]](../learnings/1786479412363-approver-challenger-verify-an-author-s-self-report.md). Always test a classifier/guard with both a known-good input (unmutated must pass) and a known-bad one matching the real failure mode. A bot finding gets the same trace-the-return-value treatment: CodeRabbit's "the suite executes even when device requirements fail" on slang-rhi#832 inverted the boolean — `checkRequiredDevices()` returns *availability* (true when devices present), and `result` defaults to failure, so a missing device skips `run()` and the job goes RED [[a CodeRabbit "functional correctness" flag can invert the code's semantics — trace the return value before crediting it]](../learnings/1786481302766-approver-challenger-calibration-a-coderabbit-funct.md). Before crediting or blocking on a "this gate is inverted / a no-op" finding, open the predicate and confirm what true/false mean and what the controlled variable defaults to — and price a companion gap by (trigger reachability on a supported path) × (blast radius vs current state), not the bot's severity tag. The inverse case (a *real* bot finding CodeRabbit missed) is slang#12481: a hard-coded `github.com/shader-slang/slang/pull/{pr_number}` in a `--repo`-parameterized tool is a live defect regardless of green CI (CI ran against the default repo, so it can never exercise the broken branch) [[hard-coded identifier in a parameterized tool — verify against the file's own convention]](../learnings/1786502456767-approver-challenger-calibration-hard-coded-identif.md). Two probes flip it: does the file build the same kind of value parameterized elsewhere, and is the parameter in scope at the new call site? — plus verify blast radius (one of the two instances was dead code; the BLOCK correctly rested on the live JS render path).

A **stale/off-head bot merge-risk** gets the same trace-the-value treatment — but the trace target is the *lowering*, not the diff. On slang#12913 (a `CoopVec<T,N> exp10` overload + fwd/bwd autodiff derivative registrations) CodeRabbit posted a 🟡 "Moderate merge risk: HLSL cooperative-vector shaders may fail to compile because the generated HLSL calls an unsupported `exp10` intrinsic," while the head-current production review (github-actions[bot]) rated the exact head Clean. Two independent refutations: (1) CodeRabbit had reviewed an OLDER commit range (up to `4fdae`, not the pinned head) and auto-paused ("branch under active development") — always check the commit a bot actually reviewed vs the pinned head before crediting its severity; and (2) the new overload is a lane-wise loop `for i: ret[i] = exp10(x[i])` over the SCALAR `exp10`, not a whole-vector intrinsic, so the merge-risk question is entirely about the scalar builtin's lowering. Fetch the scalar def and read its `__target_switch`: scalar `exp10(T x)` (hlsl.meta.slang:10795) is `case metal: __intrinsic_asm "exp10"; default: return exp(x * ln10)`, so on HLSL/SPIRV/GLSL/CUDA/WGSL/CPP/LLVM it expands to a universally-supported `exp(x·ln10)` and only Metal uses a native intrinsic (which exists) — the loop emits NO dedicated/unsupported intrinsic on any backend. The rule: when a PR adds a CoopVec/vector overload that loops over an existing scalar builtin, confirm safety by reading that scalar builtin's `__target_switch`, not by analogy, and don't let a stale/off-head bot merge-risk override a head-current Clean primary review (corroborated here by a correct derivative constant `2.30258509…` = ln(10), mirroring the sibling `exp2`/`ln(2)` registration, and green CI across the full statusCheckRollup build+test matrix) [[approver/confirmed-safe] CoopVec math-intrinsic overload = lane-wise loop over an existing scalar builtin adds NO new target intrinsic — a stale bot "unsupported HLSL intrinsic" merge-risk is refuted by the scalar builtin's __target_switch](../learnings/1788576772705-approver-confirmed-safe-coopvec-math-intrinsic-ove.md).

## A correction is a new claim — and low-stakes numbers rot fastest

The correction-discipline capstone: on slang-rhi#827 an approver got one trivial figure (a CI check count) wrong **four times in a row, each error introduced by the act of correcting the previous** — a sourcing violation, then falsifying a true number by comparing different scopes, then impossible arithmetic (26+2≠27), then over-generalizing "the rollup de-duplicates" from one missing entry [[four successive errors on ONE number — a correction inherits no credibility from the error it repairs]](../learnings/1786450338036-approver-critique-mustfix-four-successive-errors-o.md). The root cause is that a correction arrives wearing the credibility of the error it fixes: "I already checked this once" is precisely false about the new number. Measure the replacement (never derive it from what you disproved); when two sources disagree on a count the default hypothesis is *different scopes*, not one being wrong (name the endpoint and filter beside every number); arithmetic-check your own prose explanations; never upgrade an observation to a mechanism you can't state; and note that **low-stakes numbers are where correction discipline decays** — the whole chain here carried no decision weight, which is exactly why it got sloppy scrutiny, and the habit transfers to high-stakes ones.
