## TL;DR

- **A clause PASS is ambiguous — "checked and clean" vs. "not checked" look identical.** Read each passing clause's *evidence string*, not just its status. Any "policy does not require X" or a path list that doesn't cover the changed files is an UNCHECKED dimension you now own in Step 3.
- **`no_protected_paths` does not cover `include/**`.** An ABI break (removed COM vtable slot under an unchanged GUID) is invisible to Step 1. On any `include/`-touching PR, grep the diff for removed `virtual`/`SLANG_MCALL`/`= 0;` and check whether the interface is externally implementable — if so, the affected population is un-enumerable ⇒ abstain.
- **Bot-authored fixer PRs (`nv-slang-bot[bot]`, `fix/issue-N`) deterministically resolve to `ABSTAIN_POLICY:CLAUSE_FAIL:author_trust`** under the bundled `v0-shadow` policy: the bot's `author_association` is CONTRIBUTOR, outside `{OWNER, MEMBER, COLLABORATOR}`. This is a Step-1 short-circuit (no challenger, no critique). It is a **policy** reason_code, not infra — never tag it CLAUSE_UNEVALUABLE.
- **An author_trust-only abstain on a clean bot-fixer PR that a trusted human already approved reliably merges unchanged.** It is a pure eligibility deferral, NOT a substance signal, a miss, or a false-safe. ABSTAIN rows are excluded from agreement scoring. Do NOT round these up to WOULD_APPROVE to "match" the human — the eligibility gate is the point.
- **`tier_eligible` (400-line cap) co-fires on test-heavy fixer PRs** where the churn is added regression tests around a small production fix. A size-cap abstain is a shadow-mode conservatism knob, not a risk signal.
- **"Pre-existing and out of scope" is TWO conditions, not one.** A sibling gap is not clearable when (a) the PR TITLE claims the general fix, (b) the linked triage named the siblings, or (c) you cannot prove the sibling output is unreachable. Any of those ⇒ OPEN_GAP / ABSTAIN.
- **"Retire enum value X" is complete only across EVERY consumer** — including untracked deployed-host enforcement code, not just the repo. `git grep` the repo AND read the host: if the host does no enum validation (pass-through), residual refs are dead-but-harmless; if it validates, they are a break.
- **A master-merge `synchronize` that leaves the PR's own files byte-identical rides the prior verdict** — but the re-decision is still FRESH: re-cite CURRENT-head evidence in every artifact, never "prior analysis carries."
- Don't re-escalate the empty policy mount per-PR; one standing operator escalation covers the whole class. Repeated merged-unchanged bot-fixer outcomes are the *calibration* for the standing "widen `trusted_associations`?" question.

## The clause engine and its blind spots

The slang/slangpy PR-approver runs `eval-clauses.py` as Step 1: a set of deterministic clauses over PR metadata that short-circuit to `ABSTAIN_POLICY` on any FAIL, before the challenger and the critique gate. The recurring danger is treating a clause PASS as a positive safety finding when it is actually a *non-check*. Two clauses fail this way: `no_protected_paths` passes vacuously because its path list is tuned for build/CI tampering (`.github/**`, `**/CMakeLists.txt`, `cmake/**`, `external/**`, YAML) and omits `include/**` — so removing six virtual methods from a public COM interface under a byte-identical GUID returned 6/6 PASS ([no_protected_paths misses include](../learnings/1786378413668-approver-clause-gap-no-protected-paths-misses-incl.md)). `ci_green_on_sha` likewise passes "because the policy does not require CI green." The rule that generalizes: read the passing clause's *evidence string*, and treat any "policy does not require X" or path-list-miss as a dimension Step 3 must evaluate manually.

Scope gaps are the other clause trap. When a PR touches ONE arm of a switch and structurally identical sibling arms carry the same unguarded pattern, "pre-existing and untouched by the diff" only clears the gap when the omission is *also* out of the PR's stated scope. A broad PR title ("Fix Metal pointer cast **precedence**") plus a linked triage that explicitly named the sibling arms turns a one-third fix into a scope question a human must resolve ([broad title → OPEN_GAP](../learnings/1787665262785-approver-clause-gap-a-broad-pr-title-a-triage-that.md)). "Pre-existing + out of scope" is two independent conditions; verify scope against the PR's own purpose AND the linked issue's recommended fix, not just what the diff physically touched.

Enum/state-retirement PRs need consumer enumeration across build artifacts. Retiring `ABSTAIN_INFRA` as a decision *state* looked complete under `git grep` at the PR head, but the enforcement surface (the `record_decision` tool schema + the critique gate) lives only in the deployed host build, untracked in the repo. The settling probe is to read the host: if it does no enum validation (trims and writes the string through), residual refs are dead-but-harmless; if it validates, the same residual is a break ([enum-retirement verify all consumers](../learnings/1786959542136-approver-challenger-enum-retirement-prs-verify-all.md)).

## The bot-fixer author_trust class

The single most-observed approver outcome is `ABSTAIN_POLICY:CLAUSE_FAIL:author_trust` on `nv-slang-bot[bot]` `fix/issue-N` branches. The bot's `author_association` is CONTRIBUTOR, which is not in the trusted set, so under the bundled `v0-shadow` fallback policy (the group policy mount `APPROVAL_POLICY.json` is absent) this clause FAILs and short-circuits before any review reasoning ([deterministic ABSTAIN on author_trust](../learnings/1788244635352-approver-calibration-bot-authored-fixer-prs-determ.md), [clause-gap empty mount](../learnings/1788286022204-approver-clause-gap-bot-authored-fixer-prs-determi.md)). It is the same empty-mount root cause as the fork-head `head_provenance` FAIL, a different clause: fork PRs fail `head_provenance`, bot same-repo PRs fail `author_trust`. This is a *policy* abstain ("working as intended"), never infra — do not re-escalate the mount per-PR, and short-circuit the Devin/challenger cycle early once you recognize the shape, since no review input can change a Step-1 author_trust FAIL.

The `tier_eligible` 400-line cap co-fires on this class for **test-coverage-heavy** fixer PRs, where the churn is dominated by added regression tests around a small production change ([tier_eligible on test-heavy PR](../learnings/1788432516069-approver-challenger-confirmed-safe-bot-authored-fi.md)). The size clause counts additions+deletions blind to blast radius, so a `tier_eligible` FAIL there is a weak risk signal — a shadow-mode conservatism knob, not "this PR is risky."

## Calibration from merge outcomes

Merge joins repeatedly confirm the class is a clean deferral, not a miss. Multiple bot-fixer PRs (#12538, #12576, #12741, #12870, #12853, #12863) merged **unchanged at the exact commit the approver abstained on**, with a MEMBER approval already on the head ([merged-unchanged eligibility deferral](../learnings/1788243194812-approver-human-agreement-merged-unchanged-confirms.md), [policy-calibration merge unchanged](../learnings/1788358932534-approver-policy-calibration-bot-authored-fixer-prs.md)). Because ABSTAIN asserts nothing about the code — it defers to a human — a later human APPROVE/merge is neither a false-safe nor a disagreement. The transferable rule: an author_trust-only abstain on a clean fixer PR a trusted human already approved is a *pure eligibility deferral*; do NOT round it to WOULD_APPROVE to match the human, and do NOT read merge-unchanged as an approver miss. The recurring merged-unchanged data is the evidence for the *standing* operator question of whether to widen `trusted_associations`, not a per-PR anomaly.

The challenger's job on these is bounded: forward fuzzy-reviewer flags, don't round them up to BLOCK. A Devin 🔴 pinned at a new-code line whose concern actually lives in untouched pre-existing/orthogonal code is a "forward, don't block" adjudication — confirmed when #12853 merged unchanged over exactly such a flag ([confirmed-safe Devin pre-existing](../learnings/1788267664165-approver-challenger-confirmed-safe-bot-authored-fi.md)). Escalating it to BLOCK would have obstructed a correct in-scope fix.

The counter-example that keeps the class honest: on #12848 the same author_trust abstain aligned with a *real* not-approve signal — a COMMENTED-state human review carrying an author-acknowledged rework request ("pass B is the band-aid to remove") ([human-disagreement real rework](../learnings/1788482760309-approver-human-disagreement-bot-fixer-author-trust.md)). Lessons: a COMMENTED-state review can carry REQUEST_CHANGES-shaped substance — read the inline `review_comments`, not just the state; when the review doc is Devin-only and Devin merely echoes the PR body, treat it as a description, not an audit. The author_trust abstain fired first and did not capture *why* a human should look, which is fine for shadow mode — but once the mount trusts bots and author_trust passes, the challenger must be the one to surface the open rework request as CHALLENGER_CONCERN, never round up.

## Revision chains: byte-identity rides, but re-cite fresh

A `synchronize` push is often a master-merge/rebase, not a content change. Detect it cheaply with `gh api .../compare/<prev_sha>...<new_head>` — if `behind_by=0` and every changed file is outside the PR's own diff-vs-base, the PR's own files are byte-identical and the substantive correctness reasoning is unchanged ([master-merge synchronize rides prior verdict](../learnings/1788889633662-approver-confirmed-safe-a-master-merge-synchronize.md)). But the re-decision is a FRESH decision per the revision-chain rule: byte-identity lets you reuse the same *probes*, it does NOT let you cite the prior verdict as evidence. Re-fetch current-head source, re-cite probes at the current head's file:line (they'll match), and purge every "prior analysis carries" / "Devin re-ran on the head" phrasing from investigation.md, decision.md, the dashboard message, and the 5-bullet — the DECISION_REVIEW gate correctly blocks residual carry-over wording. Procedure gotchas from the same case: run `eval-clauses.py` AFTER synthesizing review-doc.md (`commit_match` reads the commit_id embedded there), and the ledger is append-only one-row-per-(repo,pr,commit) so a new head is a new row.

## Contradictions / supersessions

No direct contradictions among these atoms; they reinforce one coherent policy model. The one *tension* to hold: the bot-fixer abstain is usually a benign eligibility deferral ([merged-unchanged](../learnings/1788243194812-approver-human-agreement-merged-unchanged-confirms.md)) but occasionally coincides with a real human rework request ([human-disagreement](../learnings/1788482760309-approver-human-disagreement-bot-fixer-author-trust.md)) — the abstain reason_code alone cannot distinguish them, so the substance still has to be read even when the terminal state is predetermined.
