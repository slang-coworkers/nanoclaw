# Slang capability inference: how [require] propagates through referenced declarations

Slang infers a function's capability requirements by walking the declarations it references and joining their `[require(...)]` sets; a `[require]` the walk never reaches is silently dropped (no E36107). Covered: the decl-ref walk in `slang-check-decl.cpp`, the generic-struct gap (#13579, PR #13616), the declaration-order bug (#14014), missing walks, and verification. Related: IR-pass target gating on [slangc Target Coverage & Capability Gating](slangc-target-coverage-and-capabilities.md); derivative `[require]` on [[wiki/concepts/slang-autodiff-require-and-variants.md]]; descriptor handles on [[wiki/concepts/slang-language-core-descriptor-handle-capabilities-and-reflection.md]]; builtin-type and struct-field gating (#10232, PR #14332) on [[wiki/concepts/slang-language-core-struct-field-and-type-capability-gating.md]]; where E36100/E36107 fire and core-intrinsic breaks on [capability-check scope](slang-compiler-capability-check-scope-and-core-intrinsic-changes.md).

## TL;DR

- **Inference reaches a type's `[require]` only through the decl-refs it walks.** `SemanticsDeclReferenceVisitor::visitVal` skips Decl-kind operands, so before PR #13616 a `GenericAppDeclRef` (`Foo<3>`) or member-of-generic decl-ref never contributed the struct's `[require]`; only `visitDirectDeclRef` did.
- **Hook a new path at the decl-ref level** (`visitGenericAppDeclRef` / `visitMemberDeclRef`), not `visitDeclRefType`: `Foo<3>.make()` reaches the visitor as a `MemberDeclRef` with no type node.
- **Put capability policy in `CapabilityDeclReferenceVisitor`**, not the shared `SemanticsDeclReferenceVisitor`, which also drives `CollectReferencedDeclsVisitor`.
- **Every `processReferencedDecl`/`processDeclModifiers` read of `inferredCapabilityRequirements` must follow `ensureDecl(decl, CapabilityChecked)`**, skipping decls that `isBeingChecked()`; otherwise an unchecked decl contributes null caps. On master this makes inference declaration-order dependent (#14014: `StructuredBuffer.getCount` ends with `{}`); on a new path the requirement is lost for good (decl-ref marked visited).
- **Match `StructDecl || EnumDecl`.** `StructDecl` alone misses generic enums and enums nested in a generic struct; full `AggTypeDecl` also takes in interfaces and associated types.
- **Do not change the exclusion set by module or magic-ness.** Processing every `DeclRefBase` breaks the core-module bootstrap; skipping `__intrinsic_type`/`__magic_type` also skips standard-module types with their own `[require]`; scoping to `isFromCoreModule` pulls stage-restricted view types into helper inference.
- **The "~50 core-module E36104" cost of propagating intrinsic types comes only from checking core-module consumers**, so a consumer-keyed skip builds every builtin module clean. It still rejects valid user code, because many core type `[require]`s describe only the main stage (`OutputPatch` omits the domain stage) — check coverage of every legal stage and target first.
- **Two walks are still missing:** `visitFunctionDeclBase` never visits `returnType`, and the base `visitStaticMemberExpr` never calls `processDeclModifiers`. So a generic static member's `[require]` never joins a `__target_switch` case, and `T::m()` through a generic parameter drops even an annotated requirement's caps. Read the walk before writing "general inference already covers X".
- **An unannotated interface requirement can never constrain an implementation:** `checkCapabilityRequirement` treats an empty side as a superset. Probe static vs instance vs existential calls, annotated and unannotated. To preview a "contract" fix, annotate the requirement with all targets under `-std 2026`: equal-atoms conformance gives E36119 on every target, while per-call-site inference rejects only the incompatible one.
- **A struct's members never feed its own set:** there is no `visitTypeDefDecl`, so a member `typealias` (or field type) contributes nothing to the struct's `[require]`. Don't fold them into `inferredCapabilityRequirements`, which members, extensions and conformances also read (new E36100/E36108/E36118, fatal E40002); charge member-typealias caps at the use site in `processReferencedDecl` (#13793). Field types: same use-site rule in open PR #14332 ([type and struct-field gating](../concepts/slang-language-core-struct-field-and-type-capability-gating.md)).
- **Making a type's `[require]` visible mostly surfaces E36108** on public `[require(X)]` functions (E36104 only for a superset of the declared target).
- **After any visitor change, run a full build with standard modules (`-- -k 0`) and grep every target's log for `(error|warning)[E…]`** (`neural` failed E36104 on #14014 after the core module was clean). Diff every SIMPLE directive's raw output with and without the change, and every declaration's inferred caps base vs head (env-gated dump).
- **Pin a parity fix with twin rows:** each generic row next to its non-generic twin in one exhaustive DIAGNOSTIC_TEST, master failing exactly the generic rows. Before calling a changed diagnostic a regression, run the non-generic twin on master.
- **A debug-only `SLANG_ASSERT` on a guard that a counting probe never hits beats a silent skip.**
- **Where checks fire** (E36100 per function, `loadModule` E36107 per target) and core-intrinsic breaks: [capability-check scope](slang-compiler-capability-check-scope-and-core-intrinsic-changes.md).

## The walk, and the generic decl-ref gap (#13579)

Inference visits each referenced declaration through `CapabilityDeclReferenceVisitor`, built on `SemanticsDeclReferenceVisitor`, whose `visitVal` skips Decl-kind operands. A `GenericAppDeclRef` (inner `StructDecl` is operand 0) or a member-of-generic decl-ref therefore never contributed the struct's `[require]` — why #13579's generic struct compiled while a non-generic one gave E36107. Processing every `DeclRefBase`'s `getDecl()` breaks the core-module bootstrap (57 errors); restricting it to user aggregates builds clean [visitVal skips Decl operands](../learnings/1791842377952-diagnostic-test-has-no-not-directive-prefix-not-li.md). PR #13616 adds `visitGenericAppDeclRef` and `visitMemberDeclRef`, both routing to `referenceStructOfDeclRef`.

## Hooking a new reference path

PR #13616 produced three rules [new-path rules](../learnings/1791933462633-slang-capability-inference-a-new-processreferenced.md):

1. **ensureDecl first.** `processReferencedDecl` calls `handleProcessFunc(decl, decl->inferredCapabilityRequirements, loc)`, evaluating the argument before `_propagateRequirement`'s own `ensureDecl`. A new path calls `ensureDecl(decl, CapabilityChecked)` itself, or a later-declared struct contributes null caps for good. Skip a decl whose `checkState.isBeingChecked()`, or a self-referencing type reports CyclicReference.
2. **Hook decl-refs, not types.** `Foo<3>.make()` arrives as `MemberDeclRef(make, GenericAppDeclRef(Foo, …))` with no type node.
3. **Policy belongs in `CapabilityDeclReferenceVisitor`:** the shared visitor also drives forward-reference and extension generic-param checks.

## The existing path reads stale caps: inference depends on declaration order (#14014)

The ensureDecl-first rule applies to existing paths too. `processReferencedDecl` (slang-check-decl.cpp ~:22154) and `processDeclModifiers` pass `decl->inferredCapabilityRequirements` as `nodeCaps` before `_propagateRequirement` (~:21989) runs `ensureDecl(CapabilityChecked)` (~:22005). For a not-yet-checked decl the stale null is what gets joined, so nothing is added (instrumented: the `isBeingChecked()` return never fired for the victims) [stale nodeCaps](../learnings/1793278807356-slang-capability-inference-stale-nodecaps-read-in-.md).

`StructuredBuffer.getCount` (hlsl.meta.slang ~:29629) and `Buffer<T>.getCount` (~:20753) end with caps `{}`: `visitInheritanceDecl` (~:22954) ensureDecl's each top-level witness impl when the struct's first member, its `: IArray<T>` InheritanceDecl, is checked — before `GetDimensions` has caps. `RWStructuredBuffer.getCount` escapes because its `IRWArray<T>` witness table nests getCount under an `$inheritance` sub-table, which that loop skips. Result: a silent miscompile — `Buffer<T>.getCount()` on `-target cpp` emitted an empty `GetDimensions` body [per-decl caps diff](../learnings/1793291900446-capability-checker-prs-diff-every-decl-s-inferred-.md).

Most user code escapes because the visitor reads a callee twice (`processReferencedDecl`, then `processDeclModifiers`) and the second read sees the first ensureDecl. A `this.method()` path reads once, so this compiles on master 01dcd3568 although `second` is HLSL-only [verify with standard modules](../learnings/1793287326326-capability-inference-fixes-must-be-verified-with-s.md):

```slang
struct Box<T> { uint first() { return this.second(); } [require(hlsl)] uint second() { return 1; } }
// called from a Metal entry point: compiles
```

The fix (ensureDecl before the read, skipped when `isBeingChecked()`) exposes hidden conflicts. The core bootstrap (aborts on any diagnostic, `Session::addBuiltinSource`) reports E36108 twice (matrix `WaveMaskPrefixMin/Max` are `[require(cuda_glsl_spirv)]` but call `WaveMultiPrefixExclusiveMin/Max`, `[require(glsl_spirv)]`) and E36120 (`HitObject::GetAttributes`' `hlsl_nvapi` case calls the later-declared, stage-restricted `__hlslGetAttributesFromHitObject`; plain `case hlsl` is not stage-restricted). With those two meta edits the bootstrap is clean and 5375 SIMPLE/DIAGNOSTIC_TEST runs show one delta, a new glsl E41012 in `saturated-cooperation/fuse-product.slang` [decl-order dependent](../learnings/1793280440990-slang-capability-inference-is-decl-order-dependent.md). The full build then fails in `neural`: public `linearTransform` `[require(cuda_metal_spirv)]` reaches `CoopMat.__init<U,R1>` `[require(cooperative_matrix_conversion)]` on SPIR-V → E36104. Side finding: master's DXR 1.3 `GetAttributes` emitted `attr = hit.GetAttributes();`, which DXC 1.9 rejects (hlsl-specs 0027 has `void GetAttributes(out attr_t)`); routing through `__hlslGetAttributesFromHitObject` emits `hit.GetAttributes(v)`.

## Which declarations to match: `StructDecl || EnumDecl`

PR #13616 first filtered `referenceStructOfDeclRef` on `as<StructDecl>`, leaving `[require(metal)] enum GE<let N:int>` and `Outer<3>.E` (enum in a generic struct) silent for HLSL while a non-generic `[require]` enum gives E36107. `StructDecl || EnumDecl` fixes both: core module clean, metal still compiles, 2912/2912 tests pass, a 4770-invocation SIMPLE byte-compare is clean. Devin caught the enum gap; the in-house reviewer filed only the member-function variant [StructDecl-only misses enums](../learnings/1791937885563-slang-capability-inference-a-structdecl-only-hook-.md).

Full `AggTypeDecl` was rejected because it covers interfaces and associated types: provenance notes move from the interface to `associatedtype A`, and `[require(hlsl)] struct S : IGen<int>` fires E36118 — not a regression, since master already emits it for the non-generic `S : ING` [run the twin first](../learnings/1791941121185-before-calling-a-new-capability-diagnostic-a-regre.md).

## Excluding intrinsic types: the scoping traps

Copying `collectGenericStructTypeUses`'s rule (skip `__magic_type`/`__intrinsic_type` aggregates) also skips standard-module intrinsic types with their own `[require]` (`[require(metal)]` `rt::MultiLevelAccelerationStructure<N>`), so dependent tests pass silently. Limiting the exclusion to `isFromCoreModule` decls propagates them but pulls stage-restricted view types (`[require(structural_raytracing_*)]` ClosestHitInput etc.) into helper inference: on fork kaizhangNV/slang@5dd28dd2e8 that moved/added E36100 and dropped one E36107 in 4 of 219 `tests/ray-tracing-2` directives. Fast fork build for `-no-codegen` checks: `-DSLANG_ENABLE_TESTS=OFF -DSLANG_ENABLE_DXIL=OFF -DSLANG_SLANG_LLVM_FLAVOR=DISABLE` (DXIL ON builds DXC from source; tests need `SLANG_ENABLE_SLANG_RHI`) [skipping __intrinsic_type](../learnings/1791852083392-capability-inference-fixes-that-skip-intrinsic-typ.md). Re-measured at cbd707f41 + #13616, only 1 of 261 `tests/ray-tracing-2` directives changed (`multilevel-acceleration-metal-only`, now E36107 as expected); the 4/219 drift did not reproduce [1/261 re-measure](../learnings/1793230221963-slang-test-silently-ignores-filecheck-tests-withou.md).

PR #13616 keeps core-module `__magic_type`/`__intrinsic_type` generics out of inference, citing "~50 core-module E36104" otherwise — a cost that comes only from core-module consumers. A consumer-keyed variant in `referenceAggTypeOfDeclRef` skips such a type only while the module being checked is core (`isFromCoreModule(getShared()->getModule()->getModuleDecl())`): core, glsl, neural, numerics, functional and workgraph build with 0 diagnostics, and `typeOnly<CoopVec<float,4>>()` now gets E36107 on metal and wgsl, where the type-keyed exclusion was silent. "Core module" means the compiler-embedded builtins (`m_isCoreModuleCode`), not `source/standard-modules`; the only non-core `[require]` intrinsic types upstream are the 10 experimental workgraph types. Separately, an empty-body node entry taking `DispatchNodeInputRecord<T>` ICEs on spirv on master (E99997 "unhandled stage") [consumer-keyed skip](../learnings/1793236364757-slang-capability-exclusions-key-core-module-consum.md).

A full byte-compare of that variant (reviewer drill "N2" on #13579) showed it is not yet safe: 5 tests newly failed, 3 rejecting valid code with E36107 — a domain shader taking `OutputPatch<…>` (`gh-8920-domain-shaders.slang`; `OutputPatch`'s `[require]`, hlsl.meta.slang ~6711, omits the domain stage) and compute code using `__SubpassImpl` (`gh-13070-handle-ordering-nonencodable.slang`). In the other 2, `stream-output-on-vertex` gains a `LineStream` E36107 beside its E38050, and in `tessellation-invalid-output-topology` an `OutputPatch` E36107 replaces the expected E50061. Many core type `[require]`s describe only the primary use. The "~50 E36104" is separate: core functions taking these types do not redeclare their requirements [core type require = main stage](../learnings/1793240821420-core-module-type-require-s-describe-the-main-stage.md).

## Walks inference still does not make

`SemanticsDeclCapabilityVisitor::visitFunctionDeclBase` walks parameters, body and parent aggregate, never `returnType`: a `[require(metal)] struct MN` named only by an entry point's return type (`MN main()`) compiles silently for HLSL; only `collectGenericStructTypeUses` in `validateEntryPoint` catches generic `MG<3> main()`. The base `visitStaticMemberExpr` dispatches only the decl-ref and never calls `processDeclModifiers`, so a `[require]` on the member of `G<3>.make()` is dropped; non-generic `S.make()` folds to `DirectDeclRef(make)` and is caught. The #13616 reviewer caught a comment claiming "general inference already covers" the return-type case [return type never walked](../learnings/1791953844275-slang-capability-inference-never-walks-a-function-.md).

The member-level case resisted two quick fixes on #13616 — `processDeclModifiers` in the base `visitStaticMemberExpr`, and including `__intrinsic_type` generics in the new hook; both broke the core build (E36104 at `coopVecLoad`, E36120). Inside the core module, a GENERIC static member called as `Type::name` from a `__target_switch` case does not join its `[require]` into the case (a free function or non-generic static member does), because `visitStaticMemberExpr` never reaches `processDeclModifiers` for a `GenericAppDeclRef`; the E36120 consequence is on [capability-check scope](slang-compiler-capability-check-scope-and-core-intrinsic-changes.md) [generic static members](../learnings/1792523053545-slang-capability-checker-drops-require-only-for-ge.md).

The same gap drops an interface requirement's caps through a generic parameter (#13995): `visitStaticMemberExpr` (:1205) never calls `processDeclModifiers` (`visitDeclRefExpr`/`visitMemberExpr` do), and in `forward<T:IFoo>` the `T::invoke` decl-ref is a `LookupDeclRef`, so `visitDirectDeclRef` never fires: `[require(anyhit)]` on `IFoo.invoke` is lost through `T::invoke()`, while `t.invoke()` and the existential form give E36107. Separately, an UNANNOTATED requirement can never constrain an implementation: `CapabilitySet::checkCapabilityRequirement` returns "superset" when either side is empty (`slang-capability.cpp:1468`), so removing the opt-in skip in `visitInheritanceDecl` (:22968) alone misses inferred-only implementations [T::m() drops caps](../learnings/1793227466477-slang-capability-inference-static-t-m-through-a-ge.md). To estimate an "impl ⊆ requirement even when unannotated" fix before building it, annotate the interface method `[require(cpp_cuda_glsl_hlsl_metal_spirv_wgsl)]` and compile under `-std 2026`. Conformance uses `MustHaveEqualAbstractAtoms`, so an implementation using a target-restricted intrinsic (`InterlockedAdd` on a `RWStructuredBuffer<int>` element excludes cpp and wgsl) gets E36119 ("'m' is missing 'cpp + wgsl'") on EVERY target, including valid HLSL and SPIR-V, whereas per-call-site inference rejects only the incompatible target [simulate a contract capability fix with an all-targets annotation](../learnings/1793562922071-simulate-a-contract-capability-fix-by-annotating-t.md).

## A struct's members never contribute to its own capability set

`SemanticsDeclCapabilityVisitor` (~:1445, TOT 7251cc60b) has no `visitTypeDefDecl`, so a `typealias` falls to `visitDecl {}` and its aliased type's `[require]` is ignored. A struct's `inferredCapabilityRequirements` comes from `visitContainerDecl` → `getDeclaredCapabilitySet` (~:22472-22532): only its own and parents' `[require]`. Members are never unioned in — not typealiases, not fields (`struct C { MetalOnly m; }` as `uniform C` compiles silently), not methods (charged at the call by design). `uniform Context.Element` still works because type resolution canonicalizes the alias first, and `[require]` is enforced on member access through the type (`input.e.x`). Generic associated-type use is silent too: `Input<T:IC>{ T.Element e; }` as `Input<Context>`, and `use<Context>()` with `T.Element x` (#13793) [members never contribute](../learnings/1792534898622-slang-capability-inference-typealias-members-and-s.md). A gated builtin in an unread field escapes as well: `struct S { float a; double b; }` through `RWStructuredBuffer<S>` with only `a` read escapes `double`'s `[require]`. Open PR #14332 joins field requirements where the struct is used, per specialization; its traps are on [type and struct-field gating](../concepts/slang-language-core-struct-field-and-type-capability-gating.md) [type gating is AST-time and misses unread fields](../learnings/1793819445773-slang-capability-gating-on-a-type-ast-time-rejects.md).

Folding member-typealias caps into that field breaks code that compiles on master, because it has four consumers: (a) users of the type (`processReferencedDecl`); (b) the struct's members, which inherit it as declared caps (`getDeclaredCapabilitySet`'s AggTypeDecl shortcut, the non-static parent join in `visitFunctionDeclBase`); (c) `visitExtensionDecl` / `_checkExtensionMemberCapConflict`; (d) `visitInheritanceDecl`'s subtype-vs-supertype check. Changing (b)-(d) gives new E36100 (`extension Context { [require(hlsl)] int get(); }`; an unused struct with a metal and an hlsl alias), E36118 (`struct Context : IFoo`, `[require(hlsl)][require(metal)] IFoo`) and E36108 (a `[require(hlsl)]` method). Walking `typealias L = List<Self>` (`List<T:I>`, `Self : I`) during the struct's own `CapabilityChecked` hits the InheritanceDecl→parent cycle → fatal E40002, missed by the 10.7k-test suite and caught by `/code-review medium`. The fix charges at the use site: when `processReferencedDecl` sees an AggTypeDecl, it also feeds each direct member `TypeDefDecl`'s caps (after `ensureDecl`) to `handleProcessFunc`, leaving the struct's own set untouched — "charged to users" and "inherited by members" stay separate. Run master and fix full suites serially: concurrent A/B runs gave ~460 spurious cuda/vk failures [charge at use site](../learnings/1792554070597-slang-capability-inference-folding-member-typealia.md).

## Breaking surface and verification

Making a type's `[require]` visible breaks user code mostly through E36108 (dependencies not compatible on target) on public `[require(X)]` functions; E36104 appears only when the type's set is a superset of the declared target, e.g. spirv plus an extension against plain spirv [StructDecl-only misses enums](../learnings/1791937885563-slang-capability-inference-a-structdecl-only-hook-.md).

**Build.** Visitor changes hit the core module first, so rebuild it and grep `build.log` for `(error|warning)[E…]` [new-path rules](../learnings/1791933462633-slang-capability-inference-a-new-processreferenced.md). Not enough on its own: on #14014 a scratch build with standard modules off missed the `neural` E36104. Run `cmake --build --preset debug -- -k 0` and grep `FAILED:` and `error[E` across all targets, including `slang-standard-module-*` [verify with standard modules](../learnings/1793287326326-capability-inference-fixes-must-be-verified-with-s.md).

**Byte-compare tests.** Before claiming a fix re-enables a test, diff every SIMPLE directive's raw output with and without the change [skipping __intrinsic_type](../learnings/1791852083392-capability-inference-fixes-that-skip-intrinsic-typ.md). For a whole suite, run all ~5,160 SIMPLE/DIAGNOSTIC_TEST invocations with both builds and diff `error|warning|note` lines. A drill binary copied from a Release `bin/`+`lib/` tree breaks OptiX header lookup (`tests/cuda/optix-*` diverge) [StructDecl-only misses enums](../learnings/1791937885563-slang-capability-inference-a-structdecl-only-hook-.md); a copied snapshot also changes prelude `#include` and debug-info paths/hashes and cannot load dxc, so categorize every remaining difference before calling it noise [core type require = main stage](../learnings/1793240821420-core-module-type-require-s-describe-the-main-stage.md).

**Diff every declaration's inferred caps, base vs head.** Patch a review-only, env-gated dump into `_dispatchDeclCheckingVisitor` after `SemanticsDeclCapabilityVisitor(shared).dispatch(decl)`: for each FunctionDeclBase, AggTypeDeclBase and PropertyDecl write `ASTPrinter::getDeclSignatureString`, parent chain, loc and `printDiagnosticArg(CapabilitySet{decl->inferredCapabilityRequirements})`, printing EMPTY/NULL/INVALID explicitly (the printer shows `{}` for both). Build base and head with `SLANG_REVIEW_DUMP_CAPS=<file> cmake --build` (builtin modules are checked at build time, ~19.5k decls) and diff by (signature, file). On #14024 this found 87 changed decls, including the `Buffer<T>.getCount()` cpp miscompile and a new E41012 on HLSL below sm_6_6 for DescriptorHandle deref (slang-reviewer `review-14024/dump-caps.py`). Test concrete-type calls: one through a generic interface constraint passes on both, since requirements are lost through interface calls (#13995) [per-decl caps diff](../learnings/1793291900446-capability-checker-prs-diff-every-decl-s-inferred-.md).

**Scratch builds.** Copy with `tar --exclude=./build --exclude=./.git`; configure `-DSLANG_VERSION_NUMERIC=2026.13.1 -DSLANG_SLANG_LLVM_FLAVOR=DISABLE`, tests/examples/GFX/RHI/slangd/replayer/CUDA/OptiX off: a 64-core release `slangc` build is ~190 s (incremental ~77 s) [stale nodeCaps](../learnings/1793278807356-slang-capability-inference-stale-nodecaps-read-in-.md). Without libslang-glslang, `-target spirv` fails with E00100 'spirv-opt'; copy `libslang-glslang-<ver>.so` from a full build into `build/Release/lib` [decl-order dependent](../learnings/1793280440990-slang-capability-inference-is-decl-order-dependent.md). In-process slang-test can segfault on cooperative-matrix GPU tests (use `-use-test-server`); SIMPLE rows with `-DNV_SHADER_EXTN_SLOT=u0` are silently ignored without external/nvapi, so drop the define (slangc still emits `NvGetAttributesFromHitObject` with `-capability hlsl_nvapi`) [verify with standard modules](../learnings/1793287326326-capability-inference-fixes-must-be-verified-with-s.md).

## Testing a parity fix: twin rows, and the twin before a regression claim

A fix like #13616 removes a dependence on whether a type is spelled generically. Reviewers accept tests as pinning it when each generic row sits beside its non-generic twin in one exhaustive DIAGNOSTIC_TEST and master fails exactly the generic rows: 18/33 on master, 33/33 with the fix [twin rows](../learnings/1791946199459-pin-a-generic-vs-non-generic-parity-fix-with-twin-.md).

The same framing decides whether a changed diagnostic is a regression: ask "does the generic spelling now match its non-generic twin on master?", not "is it new versus master?". On #13616 the fixer and a reviewing approver both called E36118 on `[require(hlsl)] struct S : IGen<int>` a regression, but master already gave it for `S : ING`. Put each probe shape in its own file: E36118 is reported per declaration for every struct in the file [run the twin first](../learnings/1791941121185-before-calling-a-new-capability-diagnostic-a-regre.md).

For a guard that should be impossible, a debug-only `SLANG_ASSERT` beats a silent skip once a counting probe shows it never fires (0 of 2,337 test files on #13616) [twin rows](../learnings/1791946199459-pin-a-generic-vs-non-generic-parity-fix-with-twin-.md).
