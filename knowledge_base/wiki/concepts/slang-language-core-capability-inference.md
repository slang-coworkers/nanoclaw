# Slang capability inference: how [require] propagates through referenced declarations

Slang infers a function's capability requirements by walking the declarations it references and joining their `[require(...)]` sets. A `[require]` that the walk never reaches is silently dropped: the code compiles for a target the type or function was restricted away from, with no E36107. This page covers the decl-ref walk in `slang-check-decl.cpp`, the generic-struct gap (#13579, fixed by PR #13616), the stale-caps declaration-order bug (#14014), the traps in hooking a new reference path, the walks inference still does not make, and how to verify and test such fixes. Related pages: target-family gating of IR passes on [slangc Target Coverage & Capability Gating](slangc-target-coverage-and-capabilities.md); derivative `[require]` threading on [[wiki/concepts/slang-autodiff-require-and-variants.md]]; descriptor-handle capability promotion on [[wiki/concepts/slang-language-core-descriptor-handle-capabilities-and-reflection.md]]; when E36100/E36107 fire (per function, per discovered entry point, per session target) and how a new barrier or `__stage_switch` in a core intrinsic breaks callers on [capability-check scope](slang-compiler-capability-check-scope-and-core-intrinsic-changes.md).

## TL;DR

- **Inference reaches a type's `[require]` only through the decl-refs it walks.** `SemanticsDeclReferenceVisitor::visitVal` skips Decl-kind operands, so before PR #13616 a `GenericAppDeclRef` (`Foo<3>`) or a member-of-generic decl-ref never contributed the struct's `[require]`; only `visitDirectDeclRef` did.
- **Hook a new path at the decl-ref level** (`visitGenericAppDeclRef` / `visitMemberDeclRef`), not at `visitDeclRefType`: a static member call `Foo<3>.make()` reaches the visitor as a `MemberDeclRef` with no type node.
- **Put capability policy in `CapabilityDeclReferenceVisitor`**, not the shared `SemanticsDeclReferenceVisitor`, which also drives `CollectReferencedDeclsVisitor` (forward-reference and extension generic-param checks).
- **Every `processReferencedDecl`/`processDeclModifiers` read of `inferredCapabilityRequirements` must follow `ensureDecl(decl, CapabilityChecked)`**, skipping decls whose check state `isBeingChecked()`. The caps argument is read before `_propagateRequirement` runs its own `ensureDecl`, so a decl not yet checked contributes null caps. On master this makes inference declaration-order dependent (#14014: `StructuredBuffer.getCount` ends with `{}`); on a new path the requirement is lost for good because the decl-ref is marked visited.
- **Match `StructDecl || EnumDecl`.** `StructDecl` alone misses generic enums and enums nested in a generic struct; full `AggTypeDecl` also takes in interfaces and associated types.
- **Do not change the exclusion set by module or magic-ness.** Processing every `DeclRefBase` breaks the core-module bootstrap; skipping `__intrinsic_type`/`__magic_type` also skips standard-module types with their own `[require]`; scoping to `isFromCoreModule` pulls stage-restricted view types into helper inference.
- **The "~50 core-module E36104" cost of propagating intrinsic types comes only from checking core-module consumers**, so a consumer-keyed skip builds every builtin module clean. It still rejects valid user code, because many core-module type `[require]`s describe only the type's main stage (`OutputPatch` omits the domain stage). Before propagating a core type's `[require]`, check it covers every legal stage and target.
- **Two walks are still missing:** `visitFunctionDeclBase` never visits `returnType`, and the base `visitStaticMemberExpr` never calls `processDeclModifiers`. So a generic static member's `[require]` never joins a `__target_switch` case, and `T::m()` through a generic parameter drops even an annotated requirement's caps. Read the walk before writing "general inference already covers X".
- **An unannotated interface requirement can never constrain an implementation:** `checkCapabilityRequirement` treats an empty side as a superset. Probe static vs instance vs existential calls, each with annotated and unannotated requirements.
- **A struct's members never feed its own set:** there is no `visitTypeDefDecl`, so a member `typealias` (and a field's type) contributes nothing to the struct's `[require]`. Do not fold them into `inferredCapabilityRequirements`, which members, extensions and conformances also read (new E36100/E36108/E36118, a fatal E40002 cycle); charge member-typealias caps at the use site in `processReferencedDecl` (#13793).
- **Making a type's `[require]` visible mostly surfaces E36108** on public `[require(X)]` functions; E36104 appears only when the type's set is a superset of the declared target.
- **After any visitor change, run a full build with standard modules (`-- -k 0`) and grep every target's log for `(error|warning)[E…]`,** not only the core-module bootstrap: the `neural` module failed E36104 on #14014 after the core module was clean. Diff every SIMPLE directive's raw output with and without the change before claiming a test is re-enabled, and diff every declaration's inferred caps base vs head (env-gated dump) to see which builtins changed; the test suite does not show it.
- **Pin a parity fix with twin rows:** each generic row next to its non-generic twin in one exhaustive DIAGNOSTIC_TEST, master failing exactly the generic rows. Before calling a changed diagnostic a regression, run the non-generic twin on master.
- **A debug-only `SLANG_ASSERT` on a guard that a counting probe never hits beats a silent skip.**
- **Where the checks fire, and core-intrinsic body changes** (E36100 per function, `loadModule` E36107 per target, barrier/`__stage_switch` source breaks): [capability-check scope](slang-compiler-capability-check-scope-and-core-intrinsic-changes.md).

## The walk, and the generic decl-ref gap (#13579)

Capability inference visits each referenced declaration through `CapabilityDeclReferenceVisitor`, built on the shared `SemanticsDeclReferenceVisitor`. `SemanticsDeclReferenceVisitor::visitVal` skips Decl-kind operands, so a `GenericAppDeclRef` (whose inner `StructDecl` is operand 0) or a member-of-generic decl-ref never contributes the struct's `[require]`; only `visitDirectDeclRef` does. That is why `[require]` on a generic struct was dropped in #13579 while the same attribute on a non-generic struct gave E36107. Processing every `DeclRefBase`'s `getDecl()` breaks the core-module bootstrap (57 errors), while restricting it to user aggregates builds clean [DIAGNOSTIC_TEST has no -NOT directive: `//PREFIX-NOT:` lines are silently inert](../learnings/1791842377952-diagnostic-test-has-no-not-directive-prefix-not-li.md). PR #13616 adds `CapabilityDeclReferenceVisitor::visitGenericAppDeclRef` and `visitMemberDeclRef`, both routing to `referenceStructOfDeclRef` [Slang capability inference: a new processReferencedDecl path must ensureDecl(CapabilityChecked) first, and hook decl-refs, not types](../learnings/1791933462633-slang-capability-inference-a-new-processreferenced.md).

## Hooking a new reference path

PR #13616 produced three rules [Slang capability inference: a new processReferencedDecl path must ensureDecl(CapabilityChecked) first, and hook decl-refs, not types](../learnings/1791933462633-slang-capability-inference-a-new-processreferenced.md):

1. **ensureDecl first.** `processReferencedDecl` calls `handleProcessFunc(decl, decl->inferredCapabilityRequirements, loc)`, and that capability argument is evaluated before `_propagateRequirement` runs its own `ensureDecl`. A new path therefore calls `ensureDecl(decl, CapabilityChecked)` itself; otherwise a struct declared later in the file contributes null caps, and because its decl-ref is now marked visited the requirement never comes back (the extension check documents the same trap). Mirror `_propagateRequirement`'s skip of a decl whose `checkState.isBeingChecked()`, or a self-referencing type reports a CyclicReference error.
2. **Hook decl-refs, not types.** `Foo<3>.make()` reaches the visitor as `MemberDeclRef(make, GenericAppDeclRef(Foo, …))` with no type node, so a `visitDeclRefType` hook never sees it.
3. **Policy belongs in `CapabilityDeclReferenceVisitor`.** `SemanticsDeclReferenceVisitor` also drives `CollectReferencedDeclsVisitor`, which implements the forward-reference and extension generic-parameter checks, so a change there alters unrelated diagnostics.

## The existing path reads stale caps: inference depends on declaration order (#14014)

The ensureDecl-first rule is not only for new paths. `CapabilityDeclReferenceVisitor::processReferencedDecl` (slang-check-decl.cpp ~:22154) and `processDeclModifiers` pass `decl->inferredCapabilityRequirements` as `nodeCaps` before `_propagateRequirement` (~:21989) runs `ensureDecl(CapabilityChecked)` (~:22005). If the referenced decl has not been capability-checked yet, `nodeCaps` is null; the ensureDecl computes the real set, but the stale null is what gets joined, so nothing is added and no provenance is recorded. Instrumentation showed the `isBeingChecked()` early return never fired for the victims, so this is not the cyclic skip [Slang capability inference: stale nodeCaps read in processReferencedDecl drops core-module requirements (not the cyclic skip)](../learnings/1793278807356-slang-capability-inference-stale-nodecaps-read-in-.md) [Slang capability inference is decl-order dependent; ensureDecl-before-read exposes 3 latent core-module errors (#14014)](../learnings/1793280440990-slang-capability-inference-is-decl-order-dependent.md).

Consider `StructuredBuffer.getCount` (hlsl.meta.slang ~:29629) and `Buffer<T>.getCount` (~:20753). Both end with caps `{}`. They are checked early because `visitInheritanceDecl` (~:22954) ensureDecl's each top-level witness impl when the struct's first member, its `: IArray<T>` InheritanceDecl, is checked, before the struct's `GetDimensions` member has caps. `RWStructuredBuffer.getCount` escapes: its `IRWArray<T>` witness table nests getCount under an `$inheritance` sub-table, which that loop skips, so it is checked later in source order [Slang capability inference: stale nodeCaps read in processReferencedDecl drops core-module requirements (not the cyclic skip)](../learnings/1793278807356-slang-capability-inference-stale-nodecaps-read-in-.md). The user-visible consequence is a silent miscompile: base `Buffer<T>.getCount()` on `-target cpp` emitted an empty `GetDimensions` body [Capability-checker PRs: diff every decl's inferred caps base vs head to find blast radius](../learnings/1793291900446-capability-checker-prs-diff-every-decl-s-inferred-.md).

Most user code escapes because the visitor reads a callee twice, once through the DeclRef in `processReferencedDecl` and again in `processDeclModifiers`, and the second read sees the first `_propagateRequirement`'s ensureDecl. A `this.method()` member path reads once, so this program is accepted on master 01dcd3568 although `second` is HLSL-only [Capability-inference fixes must be verified with standard modules built (neural E36104), not only the core-module bootstrap](../learnings/1793287326326-capability-inference-fixes-must-be-verified-with-s.md):

```slang
struct Box<T> { uint first() { return this.second(); } [require(hlsl)] uint second() { return 1; } }
// called from a Metal entry point: compiles
```

The fix (ensureDecl in the visitor before the read, skipped when `isBeingChecked()`) exposes conflicts the stale read hid. The core-module bootstrap, which aborts on any warning or error (`Session::addBuiltinSource`), reports E36108 twice (matrix `WaveMaskPrefixMin/Max` are `[require(cuda_glsl_spirv)]` but call matrix `WaveMultiPrefixExclusiveMin/Max`, which is `[require(glsl_spirv)]` only) and E36120 (in `HitObject::GetAttributes`' `__target_switch`, the `hlsl_nvapi` case calls the later-declared, stage-restricted `__hlslGetAttributesFromHitObject`, while the plain `case hlsl` intrinsic is not stage-restricted). With those two meta edits the bootstrap is clean, and a sweep of all 5375 SIMPLE/DIAGNOSTIC_TEST runs shows one real delta, a new E41012 warning in `saturated-cooperation/fuse-product.slang` for glsl [Slang capability inference is decl-order dependent; ensureDecl-before-read exposes 3 latent core-module errors (#14014)](../learnings/1793280440990-slang-capability-inference-is-decl-order-dependent.md). The full build then fails in the `neural` standard module: public `linearTransform` `[require(cuda_metal_spirv)]` reaches `CoopMat.__init<U,R1>` `[require(cooperative_matrix_conversion)]` on SPIR-V, which is E36104. Side finding: master's DXR 1.3 `HitObject::GetAttributes` emitted `attr = hit.GetAttributes();`, which DXC 1.9 rejects (hlsl-specs 0027 has `template<attr_t> void GetAttributes(out attr_t)`); routing through `__hlslGetAttributesFromHitObject` emits `hit.GetAttributes(v)` [Capability-inference fixes must be verified with standard modules built (neural E36104), not only the core-module bootstrap](../learnings/1793287326326-capability-inference-fixes-must-be-verified-with-s.md).

## Which declarations to match: `StructDecl || EnumDecl`

PR #13616 first filtered `referenceStructOfDeclRef` on `as<StructDecl>`. That leaves `[require(metal)] enum GE<let N:int>` and `Outer<3>.E` (an enum nested in a generic struct) silent for HLSL, while a non-generic `[require]` enum gives E36107. Widening to `StructDecl || EnumDecl` fixes both: the core module builds with no diagnostics, metal still compiles, 2912/2912 tests pass and a 4770-invocation SIMPLE byte-compare is clean. Devin caught the enum gap; the in-house correctness reviewer filed only the member-function variant [Slang capability inference: a StructDecl-only hook on GenericAppDeclRef misses generic enums](../learnings/1791937885563-slang-capability-inference-a-structdecl-only-hook-.md).

Full `AggTypeDecl` was rejected because it also covers interfaces and associated types: the associated-type provenance notes move from the interface to `associatedtype A`, and `[require(hlsl)] struct S : IGen<int>` fires E36118 [Slang capability inference: a new processReferencedDecl path must ensureDecl(CapabilityChecked) first, and hook decl-refs, not types](../learnings/1791933462633-slang-capability-inference-a-new-processreferenced.md). That E36118 is not a regression: master already emits it for the non-generic `[require(hlsl)] struct S : ING`, so the generic spelling now merely matches its twin (see the parity section) [Before calling a new capability diagnostic a regression, run the non-generic twin on master](../learnings/1791941121185-before-calling-a-new-capability-diagnostic-a-regre.md).

## Excluding intrinsic types: the scoping traps

Copying `collectGenericStructTypeUses`'s rule (skip `__magic_type`/`__intrinsic_type` aggregates) also skips standard-module types declared `__intrinsic_type(...)` with their own `[require]`, for example slang.raytracing's `rt::MultiLevelAccelerationStructure<N>` (`[require(metal)] __intrinsic_type(RaytracingAccelerationStructure)`), so tests that depend on them keep passing silently. Limiting the exclusion to core-module decls (`isFromCoreModule`) propagates them, but also pulls stage-restricted view types (`[require(structural_raytracing_*)]` ClosestHitInput and similar) into helper inference: on fork kaizhangNV/slang@5dd28dd2e8 that moved and added E36100 diagnostics and dropped one E36107 across 4 of 219 `tests/ray-tracing-2` directives. A fast fork build for `-no-codegen` checks is `-DSLANG_ENABLE_TESTS=OFF -DSLANG_ENABLE_DXIL=OFF -DSLANG_SLANG_LLVM_FLAVOR=DISABLE` (DXIL ON builds DXC from source; `SLANG_ENABLE_TESTS` requires `SLANG_ENABLE_SLANG_RHI`) [Capability-inference fixes that skip __intrinsic_type miss standard-module generic types too](../learnings/1791852083392-capability-inference-fixes-that-skip-intrinsic-typ.md). Re-measured at a later fork head (cbd707f41 + #13616, 2026-10-28), the same restriction changed the raw slangc output of only 1 of 261 `tests/ray-tracing-2` directives (`multilevel-acceleration-metal-only`, now emitting E36107 as the test expects), the core module still built clean, and the 4/219 drift did not reproduce [slang-test silently ignores filecheck tests without slang-llvm; borrow libslang-llvm.so via LD_LIBRARY_PATH](../learnings/1793230221963-slang-test-silently-ignores-filecheck-tests-withou.md).

PR #13616 keeps core-module `__magic_type`/`__intrinsic_type` generics out of inference, citing "~50 core-module E36104" when they are included. That cost comes only from checking core-module consumers. A consumer-keyed variant inside `referenceAggTypeOfDeclRef` skips such a type only while the module being checked is core (`isFromCoreModule(getShared()->getModule()->getModuleDecl())`), so the types now propagate into user code. With it the core, glsl, neural, numerics, functional and workgraph modules build with 0 diagnostics, and `typeOnly<CoopVec<float,4>>()` now gets E36107 on metal and wgsl, where the type-keyed exclusion was silent. "Core module" here means the compiler-embedded builtin modules (`m_isCoreModuleCode`, set in `slang-global-session.cpp`), not the standard modules under `source/standard-modules`; the only non-core `[require]` intrinsic types upstream are the 10 experimental workgraph types. Separately, an empty-body node entry taking `DispatchNodeInputRecord<T>` ICEs on spirv on master (E99997 "unhandled stage") [Slang capability exclusions: key "core-module consumers don't redeclare" on the consumer module, not the referenced type](../learnings/1793236364757-slang-capability-exclusions-key-core-module-consum.md).

A full byte-compare of that variant (reviewer drill "N2" on #13579) showed it is not safe yet. Every module built clean, but 5 existing tests newly failed, 3 of them rejecting valid code with E36107: a domain shader taking `OutputPatch<…>` (`tests/bugs/gh-8920-domain-shaders.slang`), because `OutputPatch`'s `[require]` (hlsl.meta.slang ~6711) does not cover the domain stage, and compute code using `__SubpassImpl` (`tests/language-feature/descriptor-handle/gh-13070-handle-ordering-nonencodable.slang`). In the other 2, `stream-output-on-vertex` gains a second E36107 for `LineStream` next to its E38050, and in the domain/metal run of `tessellation-invalid-output-topology` an `OutputPatch` E36107 replaces the expected E50061. 4 more runs pass but their notes move from the function to the type. Many core-module type `[require]`s describe only the type's primary use, so check one covers every legal stage and target before propagating it. The "~50 E36104" is a different problem: core functions that take these types do not redeclare the types' requirements [Core-module type [require]s describe the main stage, not every legal use — propagating them rejects valid code](../learnings/1793240821420-core-module-type-require-s-describe-the-main-stage.md).

## Walks inference still does not make

`SemanticsDeclCapabilityVisitor::visitFunctionDeclBase` walks the function's direct member decls (its parameters), its body and the parent aggregate, but never `returnType`. A `[require(metal)] struct MN` named only by an entry point's return type (`MN main()`) therefore compiles silently for HLSL; only `collectGenericStructTypeUses` in `validateEntryPoint` catches the generic form `MG<3> main()`. Separately, the base `visitStaticMemberExpr` dispatches only the decl-ref and never calls `processDeclModifiers`, so a `[require]` on the member itself of `G<3>.make()` is dropped; the non-generic `S.make()` folds to `DirectDeclRef(make)` and is caught. The PR #13616 reviewer caught a code comment claiming "general inference already covers" the return-type case [Slang capability inference never walks a function's return type; static member access skips processDeclModifiers](../learnings/1791953844275-slang-capability-inference-never-walks-a-function-.md).

The member-level case resisted two quick fixes on PR #13616: adding `processDeclModifiers` to the base `visitStaticMemberExpr`, and including `__intrinsic_type` generics in the new hook. Both broke the core-module build (E36104 at `coopVecLoad`, E36120) [Slang capability inference: a new processReferencedDecl path must ensureDecl(CapabilityChecked) first, and hook decl-refs, not types](../learnings/1791933462633-slang-capability-inference-a-new-processreferenced.md). The same gap shows up inside the core module: a GENERIC static member called as `Type::name` from a `__target_switch` case does not join its `[require]` into the case, while a free function or a non-generic static member does, because `visitStaticMemberExpr` never reaches `processDeclModifiers` for a `GenericAppDeclRef`. The E36120 consequence is on [capability-check scope](slang-compiler-capability-check-scope-and-core-intrinsic-changes.md) [Slang capability checker drops [require] only for GENERIC static members called as Type::name](../learnings/1792523053545-slang-capability-checker-drops-require-only-for-ge.md).

The same gap drops an interface requirement's caps when the call goes through a generic parameter (#13995, master dd307e436). `visitStaticMemberExpr` (:1205) never calls `processDeclModifiers`, which `visitDeclRefExpr` and `visitMemberExpr` (:1190/:1199) do, and inside `forward<T:IFoo>` the `T::invoke` decl-ref is a `LookupDeclRef`, so `visitDirectDeclRef` never fires either. So `[require(anyhit)]` on `IFoo.invoke` is lost through `T::invoke()`, while the instance form `t.invoke()` and the existential form give E36107. A second, separate rule: an UNANNOTATED requirement can never constrain an implementation, because `CapabilitySet::checkCapabilityRequirement` returns "superset" when either side is empty (`slang-capability.cpp:1468`); removing the opt-in skip in `visitInheritanceDecl` (:22968) alone therefore does not catch implementations whose requirements come only from inference. The call forms take different visitor paths, so a probe matrix tests static vs instance vs existential calls, each with an annotated and an unannotated requirement [Slang capability inference: static T::m() through a generic param drops even annotated requirement caps](../learnings/1793227466477-slang-capability-inference-static-t-m-through-a-ge.md).

## A struct's members never contribute to its own capability set

`SemanticsDeclCapabilityVisitor` (slang-check-decl.cpp ~:1445, TOT 7251cc60b) has no `visitTypeDefDecl`, so a `typealias` falls through to `visitDecl {}`: its aliased type is never walked, and a `[require]` written on the typealias is silently ignored. A struct's `inferredCapabilityRequirements` comes from `visitContainerDecl` → `getDeclaredCapabilitySet` (~:22472-22532), which reads only the struct's own and its parents' `[require]`. Members are never unioned in: not typealiases, not fields (`struct C { MetalOnly m; }` used as `uniform C` compiles silently), and not methods, which are charged at the call by design. `uniform Context.Element` still works, because type resolution canonicalizes the alias to its target before capability checking, and the `[require]` is enforced when a member access goes through the type (`input.e.x`). Generic associated-type use is silent too: `Input<T:IC>{ T.Element e; }` as `Input<Context>`, and `use<Context>()` with `T.Element x` (#13793) [Slang capability inference: typealias members and struct members never contribute to the struct's [require] set](../learnings/1792534898622-slang-capability-inference-typealias-members-and-s.md).

Folding member-typealias caps into that field breaks code that compiles on master, because the field has four consumers: (a) users of the type (`CapabilityDeclReferenceVisitor::processReferencedDecl`); (b) the struct's members, which inherit it as declared caps (the `getDeclaredCapabilitySet` AggTypeDecl shortcut plus the non-static parent join in `visitFunctionDeclBase`); (c) `visitExtensionDecl` / `_checkExtensionMemberCapConflict`; (d) `visitInheritanceDecl`'s subtype-vs-supertype check. Changing (b)-(d) gives new hard errors: `extension Context { [require(hlsl)] int get(); }` → E36100; `struct Context : IFoo` with a `[require(hlsl)][require(metal)] IFoo` → E36118; an unused struct with a metal alias and an hlsl alias → E36100; a `[require(hlsl)]` method in the body → E36108. Walking `typealias L = List<Self>` (with `List<T:I>`, `Self : I`) during the struct's own `CapabilityChecked` hits the InheritanceDecl→parent cycle and gives a fatal E40002; the full 10.7k-test suite missed that cycle (no test has `struct X : I { typealias A = G<X>; }` with `G<T:I>`), `/code-review medium` caught it. The approach that avoided all of these in local testing charges the caps at the use site: when `processReferencedDecl` sees an AggTypeDecl, it also feeds each direct member `TypeDefDecl`'s caps (after `ensureDecl`) to `handleProcessFunc`, leaving the struct's own set untouched. Keep the "charged to users" set and the "inherited by members" set separate. Run master and fix full suites serially: concurrent A/B runs gave ~460 spurious cuda/vk failures [Slang capability inference: folding member-typealias caps into a struct's inferred set breaks extensions/conformances/members — charge them at the use site](../learnings/1792554070597-slang-capability-inference-folding-member-typealia.md) [Slang capability inference: typealias members and struct members never contribute to the struct's [require] set](../learnings/1792534898622-slang-capability-inference-typealias-members-and-s.md).

## Breaking surface and verification

Making a type's `[require]` visible breaks user code mostly through E36108 (dependencies not compatible on target) on public `[require(X)]` functions, not E36104; E36104 shows up only when the type's set is a superset of the declared target, for example spirv plus an extension against plain spirv [Slang capability inference: a StructDecl-only hook on GenericAppDeclRef misses generic enums](../learnings/1791937885563-slang-capability-inference-a-structdecl-only-hook-.md).

**Build.** Any change to these visitors runs against the core module first, so rebuild it and grep `build.log` for `(error|warning)[E…]` [Slang capability inference: a new processReferencedDecl path must ensureDecl(CapabilityChecked) first, and hook decl-refs, not types](../learnings/1791933462633-slang-capability-inference-a-new-processreferenced.md). That is not enough: on #14014 the triage sweep used a scratch build with standard modules off and missed the `neural` E36104 above. Run `cmake --build --preset debug -- -k 0` and grep `FAILED:` and `error[E` across all targets, including `slang-standard-module-*` [Capability-inference fixes must be verified with standard modules built (neural E36104), not only the core-module bootstrap](../learnings/1793287326326-capability-inference-fixes-must-be-verified-with-s.md).

**Byte-compare tests.** Before claiming a capability fix re-enables a test, diff every SIMPLE directive's raw output with and without the change [Capability-inference fixes that skip __intrinsic_type miss standard-module generic types too](../learnings/1791852083392-capability-inference-fixes-that-skip-intrinsic-typ.md). For a whole-suite compare, run all ~5,160 SIMPLE/DIAGNOSTIC_TEST invocations with the two slangc builds and diff only the diagnostic lines (`error|warning|note`) [Core-module type [require]s describe the main stage, not every legal use — propagating them rejects valid code](../learnings/1793240821420-core-module-type-require-s-describe-the-main-stage.md). Do not keep a drill binary by copying a Release `bin/`+`lib/` tree elsewhere: OptiX header lookup breaks (`nvrtc: Failed to locate OptiX headers`) and `tests/cuda/optix-*` rows diverge spuriously [Slang capability inference: a StructDecl-only hook on GenericAppDeclRef misses generic enums](../learnings/1791937885563-slang-capability-inference-a-structdecl-only-hook-.md); a copied snapshot also changes prelude `#include` and debug-info command-line paths, cannot load dxc, and changes debug-info hashes, so categorize every remaining difference before calling it noise [Core-module type [require]s describe the main stage, not every legal use — propagating them rejects valid code](../learnings/1793240821420-core-module-type-require-s-describe-the-main-stage.md).

**Diff every declaration's inferred caps, base vs head.** The test suite does not show which builtins changed requirements. Patch a review-only, env-gated dump into `_dispatchDeclCheckingVisitor` right after `SemanticsDeclCapabilityVisitor(shared).dispatch(decl)`. For each FunctionDeclBase, AggTypeDeclBase and PropertyDecl, write `ASTPrinter::getDeclSignatureString`, the parent chain, a humane loc and `printDiagnosticArg(CapabilitySet{decl->inferredCapabilityRequirements})`, printing EMPTY/NULL/INVALID explicitly because the printer shows `{}` for both empty and invalid. Build base and head with `SLANG_REVIEW_DUMP_CAPS=<file> cmake --build`; the core, glsl, numerics and neural modules are capability-checked at build time, so the dump happens during the build (about 19.5k decls). Diff by (signature, file). On #14024 this found 87 changed decls, including the `Buffer<T>.getCount()` cpp miscompile above and a new E41012 on HLSL below sm_6_6 for DescriptorHandle deref; the script is slang-reviewer `review-14024/dump-caps.py`. ## Testing a parity fix: twin rows, and the twin before a regression claim

A fix like #13616 removes a dependence on whether a type is spelled generically. Reviewers accept the tests as pinning it when each generic row sits next to its non-generic twin in the same exhaustive DIAGNOSTIC_TEST and the master binary fails exactly the generic rows while passing every twin; on #13616 that was 18/33 on master and 33/33 with the fix [Pin a generic-vs-non-generic parity fix with twin rows, and check the twin before calling a diagnostic a regression](../learnings/1791946199459-pin-a-generic-vs-non-generic-parity-fix-with-twin-.md).

The same framing decides whether a changed diagnostic is a regression: ask "does the generic spelling now match its non-generic twin on master?", not "is it new versus master?". On #13616 both the fixer and a reviewing approver reported E36118 on `[require(hlsl)] struct S : IGen<int>` as a regression, but master already gave E36118 for `S : ING`, so it was parity. Put each probe shape in its own file: E36118 is reported per declaration for every struct in the file, so combining shapes makes the per-entry output misleading [Before calling a new capability diagnostic a regression, run the non-generic twin on master](../learnings/1791941121185-before-calling-a-new-capability-diagnostic-a-regre.md) [Pin a generic-vs-non-generic parity fix with twin rows, and check the twin before calling a diagnostic a regression](../learnings/1791946199459-pin-a-generic-vs-non-generic-parity-fix-with-twin-.md).

For a guard condition that should be impossible, a debug-only `SLANG_ASSERT` is preferable to a silent skip once a counting probe shows it never fires (0 of 2,337 test files on #13616), and reviewers accept it [Pin a generic-vs-non-generic parity fix with twin rows, and check the twin before calling a diagnostic a regression](../learnings/1791946199459-pin-a-generic-vs-non-generic-parity-fix-with-twin-.md).
