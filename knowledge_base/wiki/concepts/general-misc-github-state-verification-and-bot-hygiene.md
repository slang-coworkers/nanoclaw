# GitHub State Verification and Bot-Comment Hygiene

How the `nv-slang-bot` GitHub App reads and reports GitHub state without over- or under-counting: check-runs / Actions API traps, bot-review harvesting, the counterfactual-control discipline for absences, bot-comment edit-if-self hygiene, read-only subagent limits, and tracker/index hygiene.

## TL;DR

- **`commits/<sha>/check-runs` returns HISTORY — pass `filter=latest`** or a check that failed on attempt 1 and passed on 2 still reads `failure` and a healthy PR looks red. `--paginate` concatenates objects (not arrays) and can silently 401 on page 2+; reconcile against `total_count`, never a filtered page length.
- **`per_page` on the Actions API applies AFTER the filter**, so adding `event=` WIDENS your time window. A count over a paginated Actions query is a count over `(filter, page-cap)` jointly — state the window with the number. Two agents comparing counts must compare *windows* first.
- **Two impossible-looking numbers ⇒ enumerate three causes before blaming one:** (a) a defective instrument, (b) different scopes/windows, (c) different entities counted (runs vs SHAs vs tags). Only (a) justifies calling something broken. Free self-check: the parts must sum to the whole inside ONE query.
- **Bot-review finding tables cite DIFF-relative lines — match by SYMBOL, never line number.** Claim "not covered" only on a zero-hit symbol grep; verify your own citations at the pinned head SHA.
- **CodeRabbit findings live on `pulls/N/comments`, not `reviews[].body`.** An exit-0 harvest can score "0 findings" over 11 real ones. `Actionable comments posted: N>0` with zero body markers is a hard "findings are elsewhere" flag; use `original_commit_id` for provenance; green status ≠ a harvestable review.
- **The control is the counterfactual question: "could this have come out differently if my hypothesis were false?"** If no, it is a tautology wearing the costume of evidence. Ask it of the PREMISE too; agreement with a prior belief is when the check gets skipped.
- **`Explore` is read-only for FILES, not the NETWORK** — `Bash` is retained, so it can `gh api --method POST` / `git push`. Put the read-only constraint in the prompt verbatim; a subagent's `gh` write leaves no session outbound row, so enumerate self-inflicted causes first when a mystery artifact appears.
- **Bot-comment edit-if-self guard:** the REST issues/comments API returns `nv-slang-bot` (NO `[bot]` suffix); match suffix-tolerant or every "refresh" POSTs a duplicate. PATCH your own comment when a downstream refinement refutes it — and since edits notify nobody, also post a short new comment when the decision a maintainer is waiting on changed.
- **Review-body edits fire no webhook** — fetch the live review body at `/pulls/<pr>/reviews/<id>` before acting on or disputing what a review "said".
- **Classify a commenter bot-vs-human by asking GitHub (`author.__typename`), never by a hardcoded login set** — a closed-set membership test defaults everything outside it to the OPPOSITE class. A classification rule without its discriminator is prose; when a per-tick re-derived signal outranks a stored override, report that the SUPPRESSION failed.
- **`success` is not `effective`** — read a scheduled workflow's decision line, not its `conclusion`; watch for a self-suppressing remedy whose blocker is also its precondition. Enumerate the blocking set one query per status; re-fetch live state before quoting a log; `by …[bot]` is `triggering_actor`, not `actor`.
- **Any "N:" adjacent to an enumeration is derived data — recompute, never increment.** N self-reports don't compose into a coverage claim. A correct DEAD marker plus a stale live-work duplicate is worse than no entry — dedupe by identifier; status is single-valued.

## Bot Comment Login Form & Content-Correction Hygiene

**The edit-if-self guard must accept the bare login.** The "edit if last commenter is self, else post fresh" guard commonly tests `[ "$LOGIN" = "nv-slang-bot[bot]" ]`, but `gh api repos/<r>/issues/<n>/comments --jq '.[-1].user.login'` returns **`nv-slang-bot`** for the bot's own comments — the `[bot]` form appears in GraphQL/events, not this REST path. The guard never matches, so every "refresh the 5-bullet" step POSTs instead of PATCHing (three near-identical triage comments piled up on #1052). Use a suffix-tolerant test, `case "$LOGIN" in nv-slang-bot|nv-slang-bot\[bot\]) PATCH ;; *) POST ;; esac`, and verify the form with `--jq` before trusting either. Every `*-github` skill carrying the suffixed guard is affected ([gh API comment login is 'nv-slang-bot' not 'nv-slang-bot[bot]' — edit-if-self guard mismatch](../learnings/1783878154169-gh-api-comment-login-is-nv-slang-bot-not-nv-slang-.md)).

**Patch your own comment when a later stage refutes it; post a new one when the notified answer changes.** If you posted a causal claim as CONFIRMED and a downstream stage refutes exactly that claim, PATCH your own comment id in place: mark the refuted detail, keep what survived (e.g. a verified workaround), and point to the authoritative write-up rather than re-litigating. Readers hit the top comment first, and a stale CONFIRMED claim above a correct cross-link leaves the public trail internally inconsistent. On slangpy#1055 the triager's "vector/scalar divide is the trigger" was refined upstream (slang#12071) to "the LOOP is the trigger", and the triager re-PATCHed its own comment while leaving the other tier's cross-link untouched ([patch your own posted comment when a downstream refinement refutes it](../learnings/1783885801139-patch-your-own-posted-comment-when-a-downstream-re.md)). GitHub sends no notification for comment edits, so when the final answer reverses something a maintainer was already notified about, also post a short **new** comment; edit-only stays right for cosmetic fixes. On slangpy#1181 a patch from "30× repro running, will close" to "not closing, your call" left the stale promise in the maintainer's inbox; after a 1-line new comment, jkwak-work closed the issue within hours ([GitHub comment edits don't notify — post a new comment when the answer changes](../learnings/1790643438169-github-comment-edits-don-t-notify-post-a-new-comme.md)).

**Review-body edits are the inbound version of the same blind spot.** A maintainer can edit a submitted PR review's body, and GitHub fires no notification or webhook for it, so the `github.pr_review` payload you received can silently diverge from the live text. On #12647 the webhook delivered a `dist`/`dist-release` naming suggestion; the maintainer then edited the review to ask for `performance`, and the rename built from the webhook looked like the bot had ignored the request. Before acting on — or especially disputing — what a review said, fetch the live body: `gh api repos/<o>/<r>/pulls/<pr>/reviews/<review_id> --jq .body` (the path is under `/pulls/<pr>/reviews/<id>`; `/pulls/reviews/<id>` returns empty). If the live text contradicts the webhook, trust the live text and note the discrepancy neutrally rather than assuming the human erred ([GitHub review-body edits fire no webhook — verify live review text at source](../learnings/1789627631809-github-review-body-edits-fire-no-webhook-verify-li.md)).

**Classifying a commenter as bot-vs-human is a GitHub query, never a login-recognition test — a closed-set membership check defaults everything outside the set to the OPPOSITE class.** A supervisor watchdog nudged a PR chain with *"a non-bot review landed after you last spoke,"* citing `github-actions` and `coderabbitai`. The instrument classified with `bot_logins = {"nv-slang-bot[bot]", "nv-slang-bot"}`, so `not in bot_logins ⇒ human`: every third-party bot (`github-actions`, `coderabbitai`, dependabot, codecov) became a confident "human", and `compute_ball` read "human spoke last, unanswered" and fired. Re-scan: 135 comments across 8 chains mis-flagged; `must_nudge` dropped 16→14 once corrected, the two vanishing rows exactly the third-party-bot-last chains. Ask GitHub what an account *is* via `author.__typename` (`"Bot"` vs `"User"`):

```bash
gh api graphql -f query='{repository(owner:"O",name:"R"){pullRequest(number:N){
  timelineItems(last:25,itemTypes:[ISSUE_COMMENT,PULL_REQUEST_REVIEW]){nodes{
    ... on IssueComment{createdAt author{login __typename}}
    ... on PullRequestReview{createdAt author{login __typename} state}}}}}}'
```

Two companions. **A classification rule without its discriminator is prose, not an installed rule** — a memory saying "bot-authored comments are not routing inbounds" without recording *how to tell* reads like policy and behaves like a coin flip. And **a stored override does not beat a per-tick re-derived signal that outranks it**: the chain was already marked human-owned (`ballOverride: "human"`, persisted ~11.5 h earlier), yet the mis-flagged comment re-derived `ball: ours` that tick and won. When an automated nudge re-fires on a chain you closed, don't just refute the content — **report that the suppression failed**, since a derivation that outranks stored state fires forever and each refutation looks like progress. The negation owes the same check: "no human has spoken here" needs `__typename` too ([a closed-set membership test defaults everything outside the set to the opposite class — hardcoded bot_logins made every third-party bot a "human"](../learnings/1786236312884-a-closed-set-membership-test-defaults-everything-o.md)).

## Reading GitHub State: Endpoint, Filter, and Window Traps

Every over-reported red, phantom-green sweep, and "we already covered that" mistake in this family has one shape: a query that is *correct* over a scope you never stated.

**`commits/<sha>/check-runs` returns HISTORY, not current state — pass `filter=latest`.** Without it you get every attempt of every check, so a check that failed on attempt 1 and passed on attempt 2 still reads `conclusion:"failure"`. It *over*-reports — you burn a rerun or requeue on a phantom red and record a flake that never existed — the mirror of `gh pr checks`' phantom-*green* mode (GraphQL-backed, it 401s to "no failures" when stderr is swallowed).

```bash
gh api "repos/OWNER/REPO/commits/$sha/check-runs?per_page=100&filter=latest"   # one row per check
```

**`--paginate` is not a safe default here**: it concatenates JSON objects rather than merging arrays, so a bare `.check_runs[]` filter dies on page 2 (slurp with `jq -s '[.[]|.check_runs[]?]'` or pass explicit `?page=N`), and it has been observed to 401 on page 2+ while page 1 succeeds — a silent 100-item cap. Reconcile any enumeration against `total_count`. And **a "FAILED test" line is not automatically the failure**: slang-test retries internally and prints `failed(pending retry)` first, so grep the terminal `FAILED test:` form and check it agrees with the `N failing tests` count ([check-runs without filter=latest: stale attempts read as live reds](../learnings/1785787855263-github-check-runs-filter-latest-or-stale-attempts-.md)).

**`per_page` on the Actions API applies AFTER the filter, so adding a filter WIDENS the time window.** On `shader-slang/slang` `release.yml` (workflow `106587263`), `runs?per_page=100` gave 84 dispatch + 16 push rows (05-19..08-04) with 71 bot dispatches; `runs?per_page=100&event=workflow_dispatch` gave 100 dispatch rows (05-09..08-04) with 82. Both numbers were right — `71/84` and `82/100` describe different populations, and `total_count=251` means neither is all-time. **A count over a paginated Actions query is a count over `(filter, page-cap)` jointly**: state the window with the number, and re-run each other's exact query before judging correctness. This amends "two impossible numbers ⇒ one instrument is defective", which here produced a wrong accusation: enumerate (a) a defective instrument, (b) different scopes/windows, (c) different entities counted, and only (a) justifies "broken". Cause (c) was live in the same exchange — `88 ahead / 10 diverged` vs a peer's `89 / 9` over 98 tag runs, because one tag has two runs at two SHAs (97 distinct SHAs). Cheapest self-check: **a breakdown must sum to its whole inside one query**, or you spliced two windows ([Actions per_page is post-filter — two correct counts can disagree without either instrument being defective](../learnings/1785809671526-github-actions-per-page-is-post-filter-adding-even.md)).

**A bot review's findings table cites DIFF-relative lines — match findings by SYMBOL, never by line number.** On slang#11118 a `github-actions[bot]` review listed `slang-lower-to-ir.cpp:193`, line 193 *of the PR diff* (`:3721` in the head file). A dispatch failed to match `:3721`, concluded the depth-cap finding was absent, and instructed a delta post that would have told the maintainer their review missed its own headline finding (row 3 of that table). Before claiming a finding is new or absent: fetch the body (`gh api repos/$R/pulls/$N/reviews/$ID --jq '.body'`), grep it by symbol/mechanism (`grep -in "kMaxTypeNestingDepth\|depth-cap\|permissive"`), resolve any suspected mapping explicitly (`sed -n '193p' pr.diff` and `sed -n '3721p' head-file.cpp` must print the same statement), and claim "not covered" only on a **zero-hit symbol grep**. For your own delta's citations, fetch each file at the pinned head SHA (`gh api ".../contents/<path>?ref=<sha>" | base64 -d`) and verify every line with `sed -n 'Np'` ([bot-review finding tables cite diff-relative lines — match by symbol](../learnings/1785748040931-bot-review-finding-tables-cite-diff-relative-lines.md)).

**CodeRabbit's findings live on `pulls/N/comments`, not `reviews[].body` — and the under-read fires on a SUCCESSFUL harvest.** CodeRabbit's review body is often status boilerplate (`Actionable comments posted: 11` plus a collapsed config block, zero severity markers) with every finding inline one endpoint away, so a body-only tally exits 0 and reports 0 findings. On slang-rhi#803, review `4816225157` @ `2fc21a3` scored "clean 0/0/0" against 2 🟠 Major / 3 🟡 / 6 🔵; the next round looked non-clean only by formatting luck (one Major inlined into the body). Four fixes: (1) also tally `pulls/N/comments`; (2) treat `Actionable comments posted: N` with N>0 and zero body markers as a hard **"findings are elsewhere"** flag, never as clean; (3) use **`original_commit_id`**, not `commit_id`, for provenance — GitHub rewrites inline comments' `commit_id` as the head advances (8 of the 11 later reported a head three revisions newer); (4) **green status ≠ a harvestable review** — at a later revision CodeRabbit went green but updated its walkthrough comment instead of posting a review object. The `slang-pr-approver` and `slangpy-pr-approver` harvest scripts are byte-identical, and slangpy is exposed worse because CodeRabbit is often its only review signal, so past slangpy "0 CodeRabbit findings" rows merit audit. Rider: **a timeout describes a past instant** — an exit-22 computed at 07:04:49 was reported as a verdict at 07:12:04 though the review landed 07:07:42; re-probe immediately before committing an artifact that depends on a "not yet available" result ([CodeRabbit findings live on pulls/N/comments, not reviews[].body](../learnings/1785778143329-coderabbit-findings-live-on-pulls-n-comments-not-r.md)).

**`success` is not `effective` — read what a scheduled workflow *did* (its decision line), not its `conclusion`.** On shader-slang/slang (recurrence of #12391) `ci-retry-yielded-bot` returned `conclusion: success` hourly while doing nothing: its log read `CI is still active (1 run(s)); not rerunning bot CI. / active #30154`. The run it should have rerun (#30170) had yielded behind #30154, and #30154 was also the sole reason the retry early-exits — a **self-suppressing remedy** whose precondition is destroyed by the condition it remedies. Verified at source: `waiting ∈ ACTIVE_STATUSES` (`extras/ci/ci_priority_common.py:29`), and `retry-yielded-bot-ci.py:188` early-returns before the escalation path at `:198`. A remedy that no-ops every fire is indistinguishable from one that works by status alone; when a mechanism names its blocker, check whether that blocker is also its input (the `(1 run(s))` count is the cheap tell). Riders: **enumerate the blocking set one query per status printing `total_count`** (`requested` is in `ACTIVE_STATUSES` and easy to forget); **re-fetch each target's current state before quoting a log as live** ("8 of 8 yielded behind a non-terminal run" was really 1 of 8 — 7 were now `cancelled`, an ~8× overstatement); and **`by …[bot]` in a run log is `triggering_actor`, not `actor`** (misreading it would have inverted "defect" into "working as intended") ([a self-suppressing remedy: the blocker and the thing that would clear it are the same row](../learnings/1786245338669-a-self-suppressing-remedy-the-blocker-and-the-thin.md)).

## The Control Is the Counterfactual Question, Not a Blocklist

In one debugging chain, **nine** signals looked like evidence but could not have come out differently. The decisive case is doctest's `DEEPEST SUBCASE: d3d12`, used with opposite signs on one day: in the morning as a negative ("zero occurrences ⇒ no d3d12 failures" — but that single-line form never appears; doctest prints a multi-line `DEEPEST SUBCASE STACK REACHED` header, and `vulkan`/`cuda` also returned 0), and in the afternoon as a positive ("its absence in a green run ⇒ the d3d12 arm is clean" — doctest emits the block only while logging failures, so its absence in a 0-failure run is guaranteed). One string, zero information both times. A blocklist of "patterns that burned us" would have caught the morning use and waved the afternoon one through; the question catches both:

> **Could this have come out differently if my hypothesis were false?**

If no, it is a tautology wearing the costume of evidence. The rest of the family: a grep whose pattern never matches; a `$`-anchored pattern against a CRLF log; `grep -c` of a tool name that only counts `pip install` chatter; a downloaded release artifact standing in for a source build (both A/B arms clean); a monitor grepping a file before content is written; a stale symlink predating the build; `--depth 1` masking a fetch failure as a slow compile; a line range spanning two constructs; and a probe aimed at the wrong observable (comparing *layout* to test a change that mutates only the *capability set*). Provenance ("is this primary source?") catches none of these — several were read from primary source. Only method does ([the control is the counterfactual question, not a blocklist](../learnings/1785770932836-the-control-is-the-counterfactual-question-not-a-b.md)).

Two non-log shapes from the same chain. **A wrong premise supporting a right conclusion**: *"`#if` structurally cannot take a device term"* is false (a `#if` body can nest a runtime `if`; precedent at `src/sgl/device/helpers.cpp:64`/`:67`), but the conclusion was right on other grounds, so it cleared three tiers — one explicitly *because the conclusion matched what it already believed*. Ask the question of the **premise**, not only the conclusion; agreement with a prior belief is when the check gets skipped, not corroboration; and distrust "structurally cannot"/"impossible"/"always" in your own output, especially right after correcting someone else's overclaim. **A decision whose presupposition cannot be false**: an escalation asked a human *"should we promote the draft?"* after the asker had verified no draft existed, putting a non-existent decision in a human's queue — when escalating, re-read the question against the state you just verified.

Practical form: (1) before believing an absence, run the same probe on a case you *know* is present and confirm non-zero — no positive control, no negative result; (2) before believing a null A/B, confirm the arms differ in *some* observable way; (3) derive the observable from what the mechanism mutates (capability-set change ⇒ accept/reject and diagnostics; layout change ⇒ sizes and offsets); (4) use arithmetic as an independent check — "33 failures = 28 diagnostics + 5 known-unrelated" falsified a monitor reporting 0 diagnostics.

## Read-Only Subagent Types Do NOT Prevent GitHub Writes

The `Explore` grant is *"All tools except Agent, Artifact, ExitPlanMode, Edit, Write, NotebookEdit"* — `Bash` is retained, so an `Explore` agent can run `gh api ... --method POST`, `git push`, or `curl -X POST`. **`Explore` is read-only with respect to your files, not the world**; a directive that preferring `Explore` makes overstep "physically impossible" states a wrong mechanism (preferring it is still good practice).

The cost: after three `Explore` agents were dispatched on an issue, an `nv-slang-bot[bot]` comment appeared there that the dispatcher had not written. It reasoned "my agents were `Explore`-typed, so no `gh` write surface" and escalated that **another tier may be writing to issues it holds**; the parent read the grant and corrected it. The comment's timestamp fell inside the agent's own turn gap, the timeline showed a single `performed_via_github_app: nv-slang-bot` identity, and **a subagent's `gh` write produces no session outbound row**, so a self-inflicted write is indistinguishable on the session record from another actor's. The bias: the explanation leaving one's own apparatus blameless got escalated. **When a mystery artifact appears on a surface you control, enumerate self-inflicted causes first and read the tool grant before reporting an external cause.**

Instead: (1) **read the grant, not the type name** — `Bash` present ⇒ network writes possible; (2) **put the constraint in the prompt**, verbatim: *"READ-ONLY: do not write to GitHub or any external service (no `gh ... --method POST/PATCH/PUT/DELETE`, no `git push`, no `curl -X POST`), do not build, do not send messages or dispatch peers. Report findings only."*; (3) **prefer `Explore` anyway** — it blocks local-file writes and fan-out, just not the network; (4) **on an unexplained artifact**, read it first, consolidate by PATCH if it is substantively correct rather than adding a duplicate, and report it with its uncertainty intact ("cause unidentified", not "another tier did it"). Same root as the `curl`-vs-`gh` false capability negative and the fabricated `Read`: **an instrument's label is not a measurement of its behaviour** — name the property you need and verify that property ([`Explore` is read-only for FILES, not the NETWORK — Bash is retained, so it can post to GitHub](../learnings/1785804791695-the-explore-subagent-type-is-read-only-for-files-n.md)).

## Tracker Hygiene: Coexistence Is a Third Memory Defect

Beyond right and stale, an index entry has a worse third mode: **coexistence** — one issue/PR on two lines, one correctly marked dead/closed/superseded and one surviving older line still describing it as live work with a proposed approach. A fresh context that reads the live-work line has no reason to keep scanning, so the stale copy silently defeats the correct one — worse than no entry (with no entry you investigate; with a plausible stale one you execute). On the slang fleet index `#11682` appeared twice: once correctly **DEAD** (closed by someone else's PR #12201), once as a leftover fix-log line proposing an approach. The DEAD marker was accurate and ineffective, and was found only by accident while compacting the index for size.

Rules: **dedupe by identifier** — grep the number (`#11682`, `PR 12201`) across the whole index before trusting or writing an entry, and treat two hits as a defect until proven otherwise (a cross-reference is fine; a second *status* line never is). **When you mark something dead, delete or fold the old live-work line in the same edit** — a DEAD marker beside a stale entry is a half-fix that reads as a full one. **Status is single-valued**: exactly one line may assert an identifier's state. **Compaction is a detection opportunity** — budget for "what did shrinking this reveal?". A rule stored **without its precondition** (e.g. "a green run is weak evidence" filed without its refactor boundary condition) is the same hazard: a partially-correct memory entry can be net negative. Ask of any index: *if two lines about this disagreed, which would a fresh context act on?* ([a correct DEAD marker plus a stale live-work duplicate is worse than no entry](../learnings/1785797594644-a-correct-dead-marker-plus-a-stale-live-work-dupli.md))

### Any "N:" Next to an Enumeration Is Derived Data — Recompute, Never Increment

The quieter sibling is **a stated count maintained by incrementing**: "append your rows and bump N" makes N a maintained value whose error accumulates because nobody re-derives it. An audit of every `wiki/concepts/*.md` footer found stated-N drift on **19 of 47 pages**, including pages with no edits that day (`review-pr-practices` 273→274, `slang-backends-spirv` 162→160, `slang-misc-build-infrastructure-and-tooling` 60→55, `slang-autodiff-ir-autodiff-differentiation` 40→37), and **8 duplicate citation rows across 5 pages** — the same learning cited twice with differently-worded descriptions, inflating apparent coverage. Dedupe by keeping the **more informative** row (the one with the issue/PR number); blind "keep first" discards the better description. Rule: **any "N:" adjacent to an enumeration is derived data — never trust it, never increment it, always recompute it**, and never trust a writer's report about arithmetic on its own work.

**N independent self-reports do not compose into a coverage claim**: every fold agent truthfully reported "footer counts match" for its own slice, but drift on untouched pages and duplicates inherited from earlier folds were visible only to a global recount. And **a checker can manufacture exactly the finding you expected**: the first row-counter,

```bash
awk '/^\*\*Source learnings \(/{flag=1;next} flag&&/^- \[/{c++} flag&&!/^- \[/&&NF{exit} END{print c+0}'
```

exits at the first non-row line, so on footers with wrapped entries or blanks it counted a prefix and reported mismatches on correct pages — tempting precisely because it produced the expected result (the counterfactual-control failure above). Prefer an instrument with an **internal control**, so a parse failure announces itself:

```bash
rows=$(awk '/^\*\*Source learnings \(/{flag=1;next} flag&&/^- \[/{c++} END{print c+0}' "$f")
uniq=$(awk '/^\*\*Source learnings \(/{flag=1;next} flag&&/^- \[/{print}' "$f" \
        | grep -oP 'wiki/learnings/\K[^)]+' | sort -u | wc -l)
```

`rows == uniq` is self-validating: divergence means a parse failure or a duplicate. The durable fix is to have the generator recompute `**Source learnings (N):**` and frontmatter `source_count` from the deduped stem set on every run, dropping duplicate rows (keeping the longest description); until then every fold needs a global recount pass ([footer counts drift chronically — recompute N, and duplicate citation rows hide inside it](../learnings/1785825237204-learnings-wiki-footer-counts-drift-chronically-the.md)).
