# GitHub State Verification and Bot-Comment Hygiene

How the `nv-slang-bot` GitHub App reads and reports GitHub state without over- or under-counting: check-runs / Actions API traps, bot-review harvesting, the counterfactual-control discipline for absences, bot-comment edit-if-self hygiene, read-only subagent limits, and tracker/index hygiene.

## TL;DR

- **`commits/<sha>/check-runs` returns HISTORY — pass `filter=latest`** or a check that failed on attempt 1 and passed on 2 still reads `failure` and a healthy PR looks red. `--paginate` concatenates objects (not arrays) and can silently 401 on page 2+; reconcile against `total_count`, never a filtered page length.
- **`per_page` on the Actions API applies AFTER the filter**, so adding `event=` WIDENS your time window. A count over a paginated Actions query is a count over `(filter, page-cap)` jointly — state the window with the number or it is unfalsifiable. Two agents comparing counts must compare *windows* first.
- **Two impossible-looking numbers ⇒ enumerate three causes before blaming one:** (a) a defective instrument, (b) different scopes/windows, (c) different entities being counted (runs vs SHAs vs tags). Only (a) justifies calling something broken. Free self-check: verify the parts sum to the whole inside ONE query.
- **Bot-review finding tables cite DIFF-relative lines — match by SYMBOL, never line number.** Grep the review body by symbol/mechanism (stable across diff/head coordinates); claim "not covered" only on a zero-hit symbol grep; verify your own delta citations at the pinned head SHA.
- **CodeRabbit findings live on `pulls/N/comments`, not `reviews[].body`.** An exit-0 harvest can score "0 findings" over 11 real ones. Treat `Actionable comments posted: N>0` with zero body markers as a hard "findings are elsewhere" flag; use `original_commit_id` for provenance; green status ≠ a harvestable review.
- **The control is the counterfactual question: "could this have come out differently if my hypothesis were false?"** If no, it is a tautology wearing the costume of evidence — not a curated blocklist of patterns. Ask it of the PREMISE, not only the conclusion; agreement with a prior belief is when the check gets skipped.
- **`Explore` is read-only for FILES, not the NETWORK** — `Bash` is retained, so it can `gh api --method POST` / `git push`. Put the read-only constraint in the prompt verbatim; a subagent's `gh` write leaves no session outbound row, so enumerate self-inflicted causes first when a mystery artifact appears.
- **Bot-comment edit-if-self guard:** the REST issues/comments API returns `nv-slang-bot` (NO `[bot]` suffix); match bare or suffix-tolerant, or every "refresh" POSTs a duplicate. When a downstream refinement refutes a claim you posted as CONFIRMED, PATCH your own comment in place.
- **Any "N:" adjacent to an enumeration is derived data — recompute, never increment.** N self-reports don't compose into a coverage claim. A correct DEAD marker plus a stale live-work duplicate is worse than no entry — dedupe by identifier, status is single-valued.
- **Classify a commenter bot-vs-human by asking GitHub (`author.__typename` → "Bot"/"User"), never by a hardcoded login set** — a closed-set membership test defaults everything outside it to the OPPOSITE class, so a `bot_logins={nv-slang-bot,…}` check makes every third-party bot a "human" and fires false nudges. A classification rule without its discriminator is prose; a per-tick re-derived signal outranks a stored override, so report that the SUPPRESSION failed, not just that the content is wrong.
- **`success` is not `effective` — read what a scheduled workflow DID (its decision line), not its `conclusion` field.** A green retry that no-ops every fire is indistinguishable from one that works, by status alone; watch for a self-suppressing remedy whose blocker is also its own precondition. Enumerate the blocking set one query per status, re-fetch a target's live state before quoting a log, and read `by …[bot]` as `triggering_actor`, not `actor`.

## Bot Comment Login Form & Content-Correction Hygiene (2026-07-13 fold)

The "edit if last commenter is self, else post fresh" guard commonly tests `if [ "$LOGIN" = "nv-slang-bot[bot]" ]`, but `gh api repos/<r>/issues/<n>/comments --jq '.[-1].user.login'` returns **`nv-slang-bot`** (NO `[bot]` suffix) for the bot's own comments via the REST issues/comments API — so the guard NEVER matches and every "refresh the 5-bullet" step POSTs a new comment instead of PATCHing (observed on #1052: three near-identical triage comments piled up). Match `nv-slang-bot` (bare) or use a suffix-tolerant test (`case "$LOGIN" in nv-slang-bot|nv-slang-bot\[bot\]) PATCH ;; *) POST ;; esac`); the `[bot]` form appears in GraphQL/events but not this REST path — verify with `--jq '.[-1].user.login'` before trusting either. This affects ALL `*-github` skills carrying the `[bot]`-suffixed guard ([gh API comment login is 'nv-slang-bot' not 'nv-slang-bot[bot]' — edit-if-self guard mismatch](wiki/learnings/1783878154169-gh-api-comment-login-is-nv-slang-bot-not-nv-slang-.md)).

The edit-in-place hygiene rule extends to **content corrections**: when you've posted a causal claim/verdict as CONFIRMED and a later stage in the chain refutes exactly that claim, you MUST patch your own comment in-place to mark the refuted detail and defer to the authoritative write-up — the reader hits the top comment first, and a stale CONFIRMED claim contradicting a correct cross-link below it makes the public trail internally inconsistent. Edit ONLY your own comment id; keep the parts that survived (a verified workaround); point to the authoritative source rather than re-litigating. Observed on slangpy#1055: the triager's top comment stated "vector/scalar divide is the trigger" as CONFIRMED; the upstream re-verify refined it to "the LOOP is the trigger, not the divide" (slang#12071), and the triager proactively re-PATCHed to mark that causal detail refuted while leaving the other tier's cross-link comment untouched ([patch your own posted comment when a downstream refinement refutes it](wiki/learnings/1783885801139-patch-your-own-posted-comment-when-a-downstream-re.md)).

**Classifying a commenter as bot-vs-human is a GitHub query, never a login-recognition test — a closed-set membership check defaults everything outside the set to the OPPOSITE class.** A supervisor watchdog nudged a PR chain with *"a non-bot review landed after you last spoke,"* citing `github-actions` and `coderabbitai` — both bots. Root cause, measured in the instrument: bot classification came from a hardcoded set `bot_logins = {"nv-slang-bot[bot]", "nv-slang-bot"}`, so `not in bot_logins ⇒ human`, and every third-party bot (`github-actions`, `coderabbitai`, dependabot, codecov) became a "human" commenter with full confidence and no failure signature; `compute_ball` then read "human spoke last, unanswered" and fired. Blast radius on re-scan: 135 comments across 8 chains mis-flagged, `must_nudge` 16→14 once corrected, the two vanishing rows exactly the two third-party-bot-last chains. The discriminator is to **ask GitHub what an account *is*** — never infer from a login you recognize — via `author.__typename` (`"Bot"` for `github-actions`/`coderabbitai`/dependabot/codecov, `"User"` for a real maintainer):

```bash
gh api graphql -f query='{repository(owner:"O",name:"R"){pullRequest(number:N){
  timelineItems(last:25,itemTypes:[ISSUE_COMMENT,PULL_REQUEST_REVIEW]){nodes{
    ... on IssueComment{createdAt author{login __typename}}
    ... on PullRequestReview{createdAt author{login __typename} state}}}}}}'
```

Two companions travel with it. **A classification rule without its discriminator is prose, not an installed rule** — a memory that says *"bot-authored comments are not routing inbounds"* but never records *how to tell* a bot from a human reads like policy and behaves like a coin flip; recording the discriminator IS the rule. And **a stored override does not beat a per-tick re-derived signal that outranks it** — the chain was already marked human-owned (`disposition` + `ballOverride: "human"`, persisted ~11.5 h earlier) and it nudged anyway, because the mis-flagged comment re-derived `ball: ours` that tick and outranked the stored override. So when an automated nudge re-fires on a chain you already closed, don't just refute the content — **report that the *suppression* failed**, because a per-tick derivation that outranks stored state fires forever and each refutation looks like progress while changing nothing. The symmetry note: asserting the reverse ("no human has spoken here") owes the same `__typename` check — the claim and its negation share one failure mode ([a closed-set membership test defaults everything outside the set to the opposite class — hardcoded bot_logins made every third-party bot a "human"](wiki/learnings/1786236312884-a-closed-set-membership-test-defaults-everything-o.md)).

## Reading GitHub State: Endpoint, Filter, and Window Traps (2026-08-03/04 fold)

Every over-reported red, phantom-green sweep, and "we already covered that" mistake in this family comes from the same shape: a query that is *correct* over a scope you never stated. Four concrete instruments.

**`commits/<sha>/check-runs` returns HISTORY, not current state — pass `filter=latest`.** Without it you get *every attempt of every check*, so a check that failed on attempt 1 and passed on attempt 2 still reads `conclusion:"failure"` and a healthy PR looks red. The symptom is subtle because it is *over*-reporting: you never notice a missing failure, you just burn a rerun (or a merge-queue requeue decision) on a phantom one, and the tracker then claims a flake existed where none did. It is the mirror image of the `gh pr checks` phantom-*green* mode (GraphQL-backed, so it 401s to "no failures" when stderr is swallowed).

```bash
gh api "repos/OWNER/REPO/commits/$sha/check-runs?per_page=100&filter=latest"   # one row per check
```

Two companions from the same sweep: **`--paginate` is not a safe default on this endpoint** — it concatenates JSON objects rather than merging arrays, so a bare `.check_runs[]` filter dies on page 2 (slurp with `jq -s '[.[]|.check_runs[]?]'` or pass explicit `?page=N`), and it has been observed to **401 on page 2+ while page 1 succeeds**, i.e. a silent 100-item cap — reconcile any enumeration against a `total_count`, never against the length of a filtered page. And **a "FAILED test" line is not automatically the failure**: slang-test retries internally and prints `failed(pending retry)` first, so grep the terminal `FAILED test:` form and check that the `N failing tests` count agrees with how many you extracted ([check-runs without filter=latest: stale attempts read as live reds](wiki/learnings/1785787855263-github-check-runs-filter-latest-or-stale-attempts-.md)).

**`per_page` on the Actions API applies AFTER the filter, so adding a filter WIDENS your time window.** Verified on `shader-slang/slang` workflow `106587263` (`release.yml`): `runs?per_page=100` gave 100 rows = 84 dispatch + 16 push spanning 05-19..08-04 with 71 bot-among-dispatch; `runs?per_page=100&event=workflow_dispatch` gave 100 dispatch rows spanning 05-09..08-04 with 82. Both agents measured "how many dispatches are the bot's"; **both numbers are right**, because `71/84` and `82/100` describe different populations — the `event=` filter bought 16 more dispatch runs and 10 extra days of history in the same 100 rows (`total_count=251`, so neither is all-time). Rule: **a count over a paginated Actions query is a count over `(filter, page-cap)` jointly, never over "the workflow"** — state the window with the number or the number is unfalsifiable, and two agents comparing counts must compare *windows* first (re-run each other's exact query before concluding anything about correctness). This **amends** the standing rule *"two impossible numbers ⇒ one instrument is defective; RESOLVE, don't bridge"*, which here produced a wrong accusation that a peer's `82/84` was broken: enumerate three causes before blaming one — (a) a defective instrument, (b) different scopes/windows, (c) different entities being counted (runs vs SHAs vs tags). Only (a) justifies calling something broken. Cause (c) was live in the same exchange: over 98 tag runs, `88 ahead / 10 diverged` vs a peer's `89 / 9`, because one tag has **two runs at two SHAs** (97 distinct SHAs across 98 runs) so tag-name counts and run counts legitimately differ. Free self-check when quoting a breakdown: **verify the parts sum to the whole inside one query** — a breakdown that doesn't sum is the cheapest possible signal that you spliced two windows together ([Actions per_page is post-filter — two correct counts can disagree without either instrument being defective](wiki/learnings/1785809671526-github-actions-per-page-is-post-filter-adding-even.md)).

**A bot review's findings table cites DIFF-relative lines — match findings by SYMBOL, never by line number.** On slang#11118 an existing `github-actions[bot]` review listed `slang-lower-to-ir.cpp:193`, which is line 193 *of the PR diff*; in the head file it is `:3721`. A dispatch read the table, failed to match `:3721`, and concluded the depth-cap finding was absent — instructing a delta post that would have publicly told a maintainer their review missed its own headline finding (it was row 3 of that very table, and the review's summary line named it), in the same comment that was retracting one of its other gaps. Procedure before claiming any finding is new/absent: fetch the body (`gh api repos/$R/pulls/$N/reviews/$ID --jq '.body'`), grep it by **symbol/mechanism** (`grep -in "kMaxTypeNestingDepth\|depth-cap\|permissive"`) since symbol names are stable across the diff/head coordinate systems and line numbers are not, resolve any suspected mapping explicitly (`sed -n '193p' pr.diff` and `sed -n '3721p' head-file.cpp` must print the same statement), and claim "not covered" only on a **zero-hit symbol grep** — that is how the genuinely uncovered finding was identified. Corollary for the delta's own citations: fetch each file **at the pinned head SHA** (`gh api ".../contents/<path>?ref=<sha>" | base64 -d`) and verify every cited line with `sed -n 'Np'` before posting ([bot-review finding tables cite diff-relative lines — match by symbol](wiki/learnings/1785748040931-bot-review-finding-tables-cite-diff-relative-lines.md)).

**CodeRabbit's findings live on `pulls/N/comments`, not `reviews[].body` — and the under-read fires on a SUCCESSFUL harvest.** Harvest tooling that tallies severity markers in the review *body* systematically under-reads CodeRabbit, whose body is frequently status boilerplate only (`Actionable comments posted: 11` plus a collapsed config block, zero severity markers) while all findings sit inline one endpoint away. Exit 0, body retrieved, markers tallied → **0 findings**, with 11 real ones (2 Major) unexamined and no error to investigate. Evidence (slang-rhi#803, 2026-08-03): review `4816225157` @ `2fc21a3` was scored "clean 0/0/0" against 2 🟠 Major / 3 🟡 / 6 🔵; the next round only *appeared* non-clean because CodeRabbit happened to inline one Major into the body that time — **formatting luck, not correctness**. Not a bot-filter bug: the harvest's exact-match allowlist works and harvested `coderabbitai[bot]` verbatim. Four fixes: (1) also tally `pulls/N/comments`; (2) treat `Actionable comments posted: N` with N>0 and zero body markers as a hard **"findings are elsewhere"** flag, never as clean — that single check converts a silent under-read into a loud one; (3) use **`original_commit_id`, not `commit_id`**, for provenance, because GitHub *rewrites* inline comments' `commit_id` as the head advances (8 of the 11 findings now report the head three revisions later); (4) **status green ≠ a harvestable review** — at a later revision CodeRabbit's check was green but produced *no review object*, updating its walkthrough comment instead; absence of a review is not absence of a bot pass. Scope: the `slang-pr-approver` and `slangpy-pr-approver` harvest scripts are byte-identical, and **slangpy is exposed worse** because CodeRabbit is often its only review signal — past slangpy rows reporting 0 CodeRabbit findings are worth auditing. Same-incident discipline note: **a timeout is a statement about a past instant, not the present** — an exit-22 that was correct when computed at 07:04:49 was reported as a verdict at 07:12:04 though the review landed 07:07:42; **re-probe at the last moment before committing an artifact that depends on a "not yet available" result** ([CodeRabbit findings live on pulls/N/comments, not reviews[].body](wiki/learnings/1785778143329-coderabbit-findings-live-on-pulls-n-comments-not-r.md)).

**`success` is not `effective` — read what a scheduled workflow *did* (its decision line), not its `conclusion` field.** On shader-slang/slang CI (2026-08-09, recurrence of #12391) the `ci-retry-yielded-bot` workflow fired hourly and returned `conclusion: success` every time *while doing nothing* — its own log read `CI is still active (1 run(s)); not rerunning bot CI. / active #30154`. The run it would have rerun (#30170) yielded behind #30154, and #30154 was *also* the sole reason the retry early-exits — a **self-suppressing remedy** whose precondition is destroyed by the very condition it remedies (one parked environment approval both causes the harm and blocks its advertised fix). Verified at source, not inferred from timing: `waiting ∈ ACTIVE_STATUSES` (`extras/ci/ci_priority_common.py:29`), and `retry-yielded-bot-ci.py:188` early-returns *before* the escalation path at `:198` is ever reached. So a green scheduled workflow is not evidence of recovery — a remedy that no-ops on every fire is indistinguishable from one that works, by status alone; and when a mechanism names its blocker, check whether that blocker is also its own input (the count in the remedy's output, `(1 run(s))`, is the cheap tell). Three riders from the same incident: **enumerate the active/blocking set completely, one query per status printing `total_count`** (a partial sweep — `requested` is in `ACTIVE_STATUSES` but easy to forget — fabricates "many blockers" or "none" depending on which you omit); **re-fetch a target's current state before quoting a log as live** (a first read of "8 of 8 yielded behind a non-terminal run" collapsed to a real live radius of 1 of 8 once each target was re-fetched — 7 were `cancelled` now though `waiting` when the log was written, an ~8× overstatement); and **`by …[bot]` in a run log is `triggering_actor`, not `actor`** (reading it as the run's author here would have inverted "defect" into "feature working correctly") ([a self-suppressing remedy: the blocker and the thing that would clear it are the same row](wiki/learnings/1786245338669-a-self-suppressing-remedy-the-blocker-and-the-thin.md)).

## The Control Is the Counterfactual Question, Not a Blocklist

Across one debugging chain, **nine** separate signals looked like evidence but could not have come out differently. The decisive case inverts the sign of the first, which is what proves the control must be a *question you ask*, not a *list of patterns you avoid*. The token was doctest's `DEEPEST SUBCASE: d3d12`: in the morning as a **negative** ("zero occurrences ⇒ no d3d12 failures" — the count was 0 because that single-line form never appears; doctest prints a multi-line `DEEPEST SUBCASE STACK REACHED` header, and `vulkan`/`cuda` also returned 0), and in the afternoon as a **positive** ("its absence in a green run ⇒ the d3d12 arm is clean" — doctest emits that block *only while logging failures*, so in a 0-failure run its absence is structurally guaranteed). One string, opposite signs, zero information either time. A curated blocklist of "patterns that burned us" would have flagged the morning use and waved the afternoon one straight through. The question that catches both:

> **Could this have come out differently if my hypothesis were false?**

If no, you have a tautology wearing the costume of evidence. The same chain produced the whole family: a grep whose pattern never matches anything; a `$`-anchored pattern against a CRLF log (silently empty); `grep -c` of a tool name that only counts `pip install` chatter; a downloaded release artifact standing in for a source build (both A/B arms clean); a monitor grepping a file the instant it appears, before content is written (0 = "empty" and 0 = "no repro", indistinguishable); a stale symlink predating the build; `--depth 1` masking a fetch failure as a slow compile; a line range spanning two constructs; and a probe aimed at the wrong observable (comparing *layout* to test a change that mutates only the *capability set*). Provenance ("is this primary source?") catches **none** of these — several were read directly from primary source. Only method does ([the control is the counterfactual question, not a blocklist](wiki/learnings/1785770932836-the-control-is-the-counterfactual-question-not-a-b.md)).

Two shapes from the same chain are worth naming separately because they are not log-probes, so a reader scanning for grep-shaped mistakes skips past them. **A wrong premise supporting a right conclusion** is the hardest member of the family: *"`#if` structurally cannot take a device term"* is false (a `#if` body can nest a runtime `if` — in-repo precedent at `src/sgl/device/helpers.cpp:64`/`:67`), but the conclusion it supported was correct on other grounds, so nothing downstream looked wrong and it cleared three tiers, one of which passed it on explicitly *because the conclusion matched what it already believed*. So ask the counterfactual question of the **premise**, not only of the conclusion; **agreement with a prior belief is the condition under which the check gets skipped, not corroboration**; and note this false absolute was produced *while correcting someone else's overclaim* (distrust "structurally cannot"/"impossible"/"always" in your own output, especially right after "actually, no"). Second: **a decision whose presupposition cannot be false** — an escalation asked a human *"should we promote the draft?"* when the asker had already verified no draft existed. No possible answer applied, and it is worse than a bad log line because it puts a non-existent decision into a human's queue: **when escalating, re-read the question against the state you just verified and confirm its presupposition holds *now***.

Practical form of the control: (1) before believing an absence, run the same probe against a case you *know* is present and confirm non-zero — no positive control, no negative result; (2) before believing a null A/B, confirm the two arms differ in *some* observable way, else you cannot distinguish "no effect" from "not testing the effect"; (3) derive the observable from what the mechanism actually mutates (capability-set change ⇒ check accept/reject and diagnostics; layout change ⇒ check sizes and offsets); (4) use arithmetic as an independent check — "33 failures = 28 diagnostics + 5 known-unrelated" falsified a monitor that reported 0 diagnostics, i.e. arithmetic caught what the purpose-built tooling missed.

## Read-Only Subagent Types Do NOT Prevent GitHub Writes

The `Explore` subagent grant is *"All tools except Agent, Artifact, ExitPlanMode, Edit, Write, NotebookEdit"* — **`Bash` is not in the exclusion list.** So an `Explore` agent can run `gh api ... --method POST`, `git push`, or `curl -X POST`. The exclusions are local-filesystem writers only: **`Explore` is read-only with respect to your files; it is not read-only with respect to the world.** Both the name and the "read-only search agent" description imply more than the grant delivers, and a standing directive to prefer `Explore` so that overstep is "physically impossible" states a *mechanism that is wrong*, even though preferring `Explore` remains good practice.

What that cost: three `Explore` agents were dispatched to investigate an issue; an `nv-slang-bot[bot]` comment then appeared on that issue mid-session that the dispatching agent had not written in any turn of its own. It reasoned *"my agents were `Explore`-typed, therefore no `gh` write surface, therefore unlikely source"* and escalated upward that **another tier may be able to write to issues it holds** — a routing/duplication hazard. The parent checked the grant and corrected it. Two facts closed it: the comment's timestamp fell inside the agent's own turn gap, and **a subagent's `gh` write produces no session outbound row**, so a self-inflicted write is *indistinguishable on the session record* from a write by another actor; the timeline showed a single `performed_via_github_app: nv-slang-bot` identity, no second app, no other session. Still not *proven* (there is no per-subagent write log) — but the stated reason for ruling it out was unsupported, and the escalation rested on it. **The bias worth naming:** of two candidate explanations, the one that left its own apparatus blameless got escalated, because "a different tier is writing to my surfaces" is someone else's infrastructure problem while "my own subagent wrote it" is mine. **When a mystery artifact appears on a surface you control, enumerate self-inflicted causes first and read the tool grant before reporting an external cause.**

Do this instead: (1) **read the grant before reasoning from a type name** — `Bash` present ⇒ network writes possible, whatever the type is called; (2) **put the constraint in the prompt, because the type will not enforce it** — every read-only dispatch carries, verbatim, *"READ-ONLY: do not write to GitHub or any external service (no `gh ... --method POST/PATCH/PUT/DELETE`, no `git push`, no `curl -X POST`), do not build, do not send messages or dispatch peers. Report findings only."*; (3) **prefer `Explore` anyway** — it still removes `Edit`/`Write`/`NotebookEdit` and cannot spawn further agents, blocking the local-file and fan-out overstep classes; just don't credit it with network isolation; (4) **on an unexplained artifact**, read it before touching anything, consolidate by PATCH if it is substantively correct rather than adding a duplicate, then report the anomaly *with its uncertainty intact* ("cause unidentified", not "another tier did it"). Same root as the `curl`-vs-`gh` false capability negative and the fabricated `Read`: **an instrument's label is not a measurement of its behaviour** — name the property you need, then verify that property specifically ([`Explore` is read-only for FILES, not the NETWORK — Bash is retained, so it can post to GitHub](wiki/learnings/1785804791695-the-explore-subagent-type-is-read-only-for-files-n.md)).

## Tracker Hygiene: Coexistence Is a Third Memory Defect

The `pr_session_mappings` / tracker discipline above assumes an index entry is either right or stale. There is a worse third mode: **coexistence** — the same issue/PR appearing twice, once correctly marked dead/closed/superseded and once as a surviving older line still describing it as *live work with a proposed approach*. The stale copy silently defeats the correct one, because a fresh context that reads the live-work line has no reason to keep scanning for a contradicting entry. That is strictly worse than having no entry: with no entry you investigate; with a plausible stale entry you execute. Concretely (slang fleet index, 2026-08-03) `#11682` appeared on two lines — one correctly marked **DEAD** (closed by someone else's PR #12201) and a leftover fix-log line still proposing an approach. The DEAD marker was present, accurate, and **ineffective**, because the duplicate was equally readable and more actionable-sounding; it was found only while compacting the index for size, i.e. by accident.

Rules: **dedupe by identifier, not by vibe** — grep the *number* (`#11682`, `PR 12201`) across the whole index before trusting or writing an entry, and treat two hits on one identifier as a defect until proven otherwise (a cross-reference is legitimate; a second *status* line never is). **When you mark something dead, delete or fold the old live-work line in the same edit** — a DEAD marker beside a surviving stale entry is a half-fix that reads as a full one. **Status is single-valued:** an identifier may appear in many places as context, but exactly one line may assert its *state*, or the two will eventually disagree with no way to tell which is newer. **Compaction is a detection opportunity, not janitorial work** — budget for "what did shrinking this reveal?". Pairs with the other index hazard: a rule stored **without its precondition** (e.g. "a green run is weak evidence" filed without the refactor boundary condition) can license exactly the wrong inference. Same family — **a partially-correct memory entry can be net negative**, and only reading it adversarially reveals that. The question to ask of any index: *if two lines about this disagreed, which would a fresh context act on?* ([a correct DEAD marker plus a stale live-work duplicate is worse than no entry](wiki/learnings/1785797594644-a-correct-dead-marker-plus-a-stale-live-work-dupli.md))

### Any "N:" Next to an Enumeration Is Derived Data — Recompute, Never Increment

The duplicate-entry defect above has a quieter sibling on the same indexes: **a stated count maintained by incrementing**. Instructing each writer to "append your rows and bump N" makes N a *maintained* value, and increments accumulate error silently, because nobody re-derives it. Measured on the 2026-08-04 audit of every `wiki/concepts/*.md` footer: **19 of 47 pages** had stated-N drift, including pages with **no edits that day** (`review-pr-practices` 273→274, `slang-backends-spirv` 162→160, `slang-misc-build-infrastructure-and-tooling` 60→55, `slang-autodiff-ir-autodiff-differentiation` 40→37) — so the drift predates any single run. The same audit found **8 duplicate citation rows across 5 pages**: the same learning cited twice in one footer with *differently-worded* descriptions, near-identical enough to read as two distinct sources and inflate apparent coverage. Dedupe by keeping the **more informative** row (the one carrying the issue/PR number) — a blind "keep first" silently discards the better description. Generalized rule: **any "N:" adjacent to an enumeration is derived data — never trust it, never increment it, always recompute it**, and never trust a writer's report about arithmetic it performed on its own work.

Two method points travel with it. **N independent self-reports do not compose into a coverage claim.** Every fold agent validated only its own slice and truthfully reported "footer counts match"; the cross-cutting facts — drift on untouched pages, duplicates inherited from *earlier* folds — were visible only to a global recount, so per-agent verification cannot catch either class no matter how honest each agent is. And **a checker can be defective in a way that manufactures exactly the finding you expected**: the first row-counter used here was

```bash
awk '/^\*\*Source learnings \(/{flag=1;next} flag&&/^- \[/{c++} flag&&!/^- \[/&&NF{exit} END{print c+0}'
```

whose `!/^- \[/&&NF{exit}` clause stops at the first non-row line — but real footers carry wrapped entries and interleaved blanks, so it counted a *prefix* and reported mismatches on correct pages. It was tempting precisely because it produced the expected result (same family as the counterfactual-control rule above: it could not have come out any other way). Prefer an instrument with an **internal control**, so a parse failure announces itself instead of arriving as content:

```bash
rows=$(awk '/^\*\*Source learnings \(/{flag=1;next} flag&&/^- \[/{c++} END{print c+0}' "$f")
uniq=$(awk '/^\*\*Source learnings \(/{flag=1;next} flag&&/^- \[/{print}' "$f" \
        | grep -oP 'wiki/learnings/\K[^)]+' | sort -u | wc -l)
```

`rows == uniq` is self-validating: divergence means either a parse failure or a duplicate. The durable fix is to make the number derived — have the generator recompute `**Source learnings (N):**` and frontmatter `source_count` from the deduped stem set on every run and drop duplicate rows (keeping the longest description); until that lands, every fold needs a **global** recount pass, because telling agents to bump N will keep producing drift ([footer counts drift chronically — recompute N, and duplicate citation rows hide inside it](wiki/learnings/1785825237204-learnings-wiki-footer-counts-drift-chronically-the.md)).
