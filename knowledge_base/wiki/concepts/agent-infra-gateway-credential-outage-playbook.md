# Gateway Credential Outage Playbook: GitHub 401 fallback ladder and proxy bypass

> Related page: [GitHub Auth and Operations in Agent Containers](agent-infra-github-auth-operations.md) (steady-state auth: the sentinel `GH_TOKEN`, identity-probe false negatives, nv-slang-bot permissions). This page is the playbook for when the gateway's *stored GitHub credential itself* is dead — the fleet-wide 401 outage, not the everyday probe quirk.

## TL;DR

- A fleet-wide `gh` 401 "Bad credentials" with **no `connect_url`** is gateway credential rot: the proxy injects the stale token into every request it proxies — even unauthenticated curl — so `gh`, proxied curl, webfetch of api.github.com, and `git fetch` all fail together and identically. GitHub itself is fine; the failure is the proxy hop.
- Public reads still work by escaping the proxy entirely. Rung 1: anonymous REST via `curl -s --noproxy '*' https://api.github.com/...`. Rung 2: WebFetch of github.com HTML pages (issue bodies, search, releases, raw file contents).
- Bypassing the proxy needs **all four** proxy vars unset (`env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy`); unsetting only the uppercase pair still routes through the gateway and 401s.
- The local proxy hop answers `HTTP/1.1 200` to curl while the upstream GitHub response (the second header block) is 401 with an empty body — read both header blocks before concluding anything.
- Probe credential health with a **repo path** (`gh api repos/<o>/<r>`: 401 = outage, 200 = restored), never `gh api rate_limit` or `gh api user` — those paths have no credential mapped at the proxy and 401 even while writes work.
- Writes (comments, labels, pushes, reruns) stay blocked until the operator reconnects GitHub in the OneCLI dashboard. Report the 401 as an infra problem; never attempt `gh auth login`; never record "no GitHub access" as a durable fact.
- Never `env | grep PROXY` — the proxy URL contains the gateway credential.
- Anonymous rate limits: 60/h core, 10/min search (space search calls ~62 s apart). Direct egress rotates through a SNAT IP pool, so a 403 "rate limit exceeded" on one call may be followed by a fresh quota on the next — retry rather than declaring the hour exhausted.
- raw.githubusercontent.com returns **501** for suffix-range requests (`curl -r -2048`) both proxied and direct — fetch the whole file; `curl -sf | jq` masks the failure because jq exits 0 on empty input.

## Symptom and mechanism

When the OneCLI gateway's stored GitHub credential goes stale, every path that traverses the proxy fails the same way: `gh` reports "HTTP 401: Bad credentials" (GH_TOKEN), proxied curl gets the confusing double status — the local proxy hop returns `HTTP/1.1 200 OK` to curl while the upstream GitHub response in the second header block is `401 Unauthorized` with an EMPTY body, so there is no `connect_url` to surface per the onecli-gateway skill — and `git fetch` reports "Invalid username or token" ([proxy-200 wraps upstream-401](../learnings/1794811313128-gateway-github-cred-401-proxy-200-wraps-upstream-4.md)). The mechanism is that the proxy injects the dead token into ALL requests it proxies, including ones sent with no auth header at all, which is why even unauthenticated public-endpoint calls through the proxy 401 ([--noproxy bypasses the broken gateway proxy](../learnings/1794814832825-noproxy-bypasses-the-broken-gateway-proxy-anonymou.md), [bypass for reads, verify webhooks against live state](../learnings/1794814383013-broken-proxy-github-credential-bypass-for-reads-ve.md)). An early reading of this outage claimed credential rot killed ALL GitHub paths including unauthenticated API calls ([gateway GitHub credential rot kills all proxied GitHub paths](../learnings/1794813875984-gateway-github-credential-rot-kills-all-github-pat.md)); that was wrong — the failure is the proxy, not GitHub, and anonymous reads work once the proxy is bypassed (correction recorded in the lineage, see [--noproxy bypasses the broken gateway proxy](../learnings/1794814832825-noproxy-bypasses-the-broken-gateway-proxy-anonymou.md)). The same early reading contributed the durable pieces this playbook keeps: the bare "Bad credentials" 401 body carries no `connect_url`, so the only fix is the operator reconnecting GitHub in the OneCLI dashboard, and a `github.ci_failed` webhook arriving mid-outage should be checked for staleness (the commit checks page loads without auth) rather than classified blind. Only github.com HTML pages need no bypass at all — they fetch fine even while the API paths are dead.

## The fallback ladder (public reads only)

**Rung 1 — anonymous REST via proxy bypass.** `curl -s --noproxy '*' https://api.github.com/repos/<o>/<r>/issues/<n>` (and `/comments`, `/timeline`) gets normal anonymous access to public repos ([public reads still work with curl --noproxy](../learnings/1794804258790-github-gateway-401-public-reads-still-work-with-cu.md), [--noproxy bypasses the broken gateway proxy](../learnings/1794814832825-noproxy-bypasses-the-broken-gateway-proxy-anonymou.md)). Quote the `'*'` so the shell doesn't glob-expand it. Rate limits without auth: 60 req/h core per IP (reset time in `x-ratelimit-reset` — sleep to the reset and retry if limited) and **10/min search**, so space search calls about 62 s apart; for "does any PR reference #N", the issue `/timeline` `cross-referenced` events are authoritative and cost no search quota ([unauthenticated public reads via curl --noproxy](../learnings/1794804706876-github-gateway-401-fallback-unauthenticated-public.md)). The issue JSON `parent_issue_url` and the `/timeline` endpoint surface assign/label/umbrella actions humans take without commenting. `gh` cannot use this trick (it needs a real token); only raw curl or `git -c http.proxy=`-style bypasses work ([--noproxy bypasses the broken gateway proxy](../learnings/1794814832825-noproxy-bypasses-the-broken-gateway-proxy-anonymou.md)).

**Rung 2 — WebFetch of HTML pages.** When even anonymous REST is rate-limited, WebFetch still reads public GitHub: `https://github.com/<owner>/<repo>/issues/<n>` renders the full body, labels, state and comments; `/issues?q=...` search pages work; `https://github.com/<owner>/<repo>/releases` lists release tags; `https://raw.githubusercontent.com/<owner>/<repo>/<branch>/<path>` returns file contents ([read-only GitHub checks when gh returns 401](../learnings/1794804275066-read-only-github-checks-when-gh-returns-401.md), [webfetch HTML for issue reads](../learnings/1794816707017-github-outage-workarounds-webfetch-html-for-issue-.md)). Know the limits: a small model writes the summary, quotes are capped at ~125 characters, and responses are cached 15 minutes — enough to tell "did anyone reply?" apart, not enough for comment ids or exact text; ask it to quote lines verbatim ([fall back to WebFetch of the public issue page](../learnings/1794804249040-github-401-via-gateway-fall-back-to-webfetch-of-th.md)). Neither rung can write to GitHub.

## Bypass mechanics

Bypassing the OneCLI gateway for anonymous egress requires unsetting **all four** proxy vars: `env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy curl ...`. The lowercase pair is also set and also carries the gateway injection; unsetting only the uppercase pair (as several past heartbeats did) still sends the bad credential and produces a 401 that looks identical to the known gateway-credential gap — verified 2026-11-16, uppercase-only → 401, all four → 200 with full run JSON ([gateway bypass needs all four proxy vars unset](../learnings/1794818468173-gateway-bypass-needs-all-four-proxy-vars-unset-not.md)). Direct egress rotates through a SNAT IP pool (e.g. 184.198.146.249) where some IPs are rate-limit-starved by other tenants, so a 403 "rate limit exceeded" on one call can be followed by a fresh `remaining: 60` on the next; retry or accept partial data, and treat earlier "anonymous quota exhausted" readings as partly a measurement artifact of the shared egress ([gateway bypass needs all four proxy vars unset](../learnings/1794818468173-gateway-bypass-needs-all-four-proxy-vars-unset-not.md)). Never `env | grep PROXY` to debug this: the proxy URL itself contains the gateway credential ([public reads still work with curl --noproxy](../learnings/1794804258790-github-gateway-401-public-reads-still-work-with-cu.md)).

## Diagnosing: what exactly is broken

Probe credential health with a **repo path**, e.g. `gh api repos/shader-slang/slang` — 401 = outage, 200 = restored. Do NOT use `gh api rate_limit` or `gh api user`: those paths have no credential mapped at the proxy and return 401 even while writes work ([auth-probe paths for the GitHub gateway](../learnings/1794821332509-auth-probe-paths-for-the-github-gateway-repo-paths.md)). A two-step probe ladder separates credential rot from a real GitHub problem: `curl -s https://api.github.com/repos/<public-repo> -o /dev/null -w '%{http_code}'` → 401 means the proxied path is broken (a public repo should be 200 unauthenticated, so a proxied 401 is the injected credential, not GitHub); the same call with `--noproxy '*'` → 200 confirms credential rot with anonymous reads available ([gateway GitHub credential rot kills all proxied GitHub paths](../learnings/1794813875984-gateway-github-credential-rot-kills-all-github-pat.md), [--noproxy bypasses the broken gateway proxy](../learnings/1794814832825-noproxy-bypasses-the-broken-gateway-proxy-anonymou.md)). Before blaming credentials for a silently-empty fetch, check the transport: raw.githubusercontent.com's Varnish edge now returns HTTP 501 for suffix-range requests (`curl -r -2048`), both through the gateway and on direct egress, while a plain full-file GET of the same URL returns 200 — a `curl -sf | jq` pipeline masks this because jq exits 0 on empty input, so check `%{http_code}` first ([raw.githubusercontent 501 on suffix-range requests](../learnings/1794818886752-raw-githubusercontent-501-on-suffix-range-requests.md)).

## Heartbeat and precheck failure decoding

A heartbeat precheck failure is not always the credential. Three distinct causes observed 2026-11-16: (1) OneCLI's GitHub connection being *absent* makes api.github.com return 401 `app_not_connected` through the proxy, which the heartbeat reports as `workflow_failures.accumulator_failed` rather than a generic network failure — scoped raw egress (`env -u ... curl`) fetches public Actions data meanwhile, and the durable fix is reconnecting GitHub through OneCLI / `ncl groups connect` ([app_not_connected causes heartbeat accumulator failure](../learnings/1794810847235-github-onecli-app-not-connected-causes-heartbeat-a.md)); (2) credential rot proper — on the 07:04 UTC heartbeat the gateway still injected a bad credential while unauthenticated direct calls worked, so the same probe ladder above applies ([heartbeat 2026-11-16: broken GitHub API auth](../learnings/1794812730455-heartbeat-2026-11-16-broken-github-api-auth-and-a-.md)); (3) pure transport — the persistent `ci_health: fetch_failed` was the raw.githubusercontent 501 on the `-r -2048` suffix-range fetch, not the credential gap; fetch the whole file and `grep '^{' | tail -1` as before ([raw.githubusercontent 501 on suffix-range requests](../learnings/1794818886752-raw-githubusercontent-501-on-suffix-range-requests.md)). Separately, a single GitHub 502 while fetching one job can push the Slang CI Analytics scheduled run just over its 5% job-fetch error-rate gate (5.3%) and fail the whole workflow — read the `ci_job_collector.py` log line before treating that as a code break, and keep scheduled nightly failures separate from master health by classifying on the workflow-run `head_sha`, the check-runs on that head, and the specific failing job's log ([CI Analytics 5% gate can fail on one GitHub 502](../learnings/1794809520639-ci-analytics-5-gate-can-fail-on-one-github-502.md)). A queued Actions run can also hide a completed failed job (a run stayed `queued` for hours because one Linux ASan job had no runner while its Windows ASan job had already failed) — count "completed workflow failures" separately from "failed jobs inside a still-queued run" or a red job disappears from `status=failure` queries ([heartbeat 2026-11-16: broken GitHub API auth](../learnings/1794812730455-heartbeat-2026-11-16-broken-github-api-auth-and-a-.md)).

## Dispositioning webhooks and writes during an outage

A `github.ci_failed` webhook arriving while creds are down can usually be dispositioned with read-only anonymous access: `--noproxy` reads of the check-suite and the head commit's check-runs reveal deleted (404) or empty (`total_count: 0`) suites ⇒ stale webhook, ignore ([--noproxy bypasses the broken gateway proxy](../learnings/1794814832825-noproxy-bypasses-the-broken-gateway-proxy-anonymou.md)). Verify webhooks against live state before reacting: shader-slang/slang purges old workflow runs (Oct bot runs were 404 on Nov 16), so a webhook citing a month-old `head_sha` whose check suite 404s is a stale replay — check whether the maintainer has already moved past it ([bypass for reads, verify webhooks against live state](../learnings/1794814383013-broken-proxy-github-credential-bypass-for-reads-ve.md)); a webfetch of the commit's checks page (`github.com/<o>/<r>/commit/<sha>/checks`) loads without auth and reveals whether runs even exist. Writes still need the gateway: park the required GitHub write on a one-shot retry task (~6 h) and escalate once if creds are still bad ([proxy-200 wraps upstream-401](../learnings/1794811313128-gateway-github-cred-401-proxy-200-wraps-upstream-4.md)); remember a one-shot task is consumed by a `wakeAgent:false` fire, so wake in both branches (success and still-down) so the outcome gets reported, and `ncl tasks cancel <series-id>` as soon as the action lands out-of-band ([auth-probe paths for the GitHub gateway](../learnings/1794821332509-auth-probe-paths-for-the-github-gateway-repo-paths.md)). Report the outage itself to the operator as an infra problem — the fix is the operator reconnecting GitHub via the OneCLI dashboard, not anything container-side ([public reads still work with curl --noproxy](../learnings/1794804258790-github-gateway-401-public-reads-still-work-with-cu.md)).
