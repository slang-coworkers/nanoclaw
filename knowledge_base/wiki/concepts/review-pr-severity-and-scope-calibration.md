# PR Review Severity and Scope Calibration

## TL;DR
- **A re-review does two things:** confirm the round-1 findings are closed *and* look for NEW gaps the redesign introduced. A follow-up commit that *only* lands a nit the reviewer itself recommended needs a check that it landed, not a full three-reviewer re-run.
- **A "benign / produces valid output" call must hold on EVERY reachable emit target** — an empty struct is valid direct SPIR-V but illegal GLSL, so `-emit-spirv-via-glsl` breaks. Enumerate targets; prefer an adversarial cross-target probe.
- **A doc-vs-behavior conflict on a maintainer-owned design point is a high-signal QUESTION for maintainer intent, not an autonomous BLOCK.** Reserve REQUEST_CHANGES strength for changes wrong *regardless* of intent (memory safety, silent miscompile, a claimed-but-broken ABI guarantee).
- **A maintainer-applied label / Type / milestone can encode the direction they are driving toward**, not the current diff. Check applier + timestamp; frame a discrepancy as "HEAD is X, label says Y — intentional?", never "wrong label".
- **`must-fix`, `safety-critical`, `P0`, `blocker`, `miscompile` are claims about the world — attach the evidence in the same breath, or don't attach the label.** A label turns an unverified assertion into a work directive and survives relay better than its reasoning. Send labels down as "contingent: drill, don't honor"; a downstream tier that contradicts you on measurement is your most valuable instrument.
- **A comparative claim ("no worse than", "strictly better") needs a fixture where the compared outcomes differ on disk.** If the buggy answer coincides with the baseline, the repro cannot support the claim.
- **On an identity/aliasing fix, enumerate the identity axes and ask which one the QUESTION lives on.** Narrowing a candidate set is not making it unique.
- **A fix invisible to both the suite and the validator owes a REQUIRED regression test**, not an optional one.
- **A bot's verdict covers only the files it read.** CodeRabbit's built-in `!**/*.map` exclude can drop the file the PR is about; diff "files selected for processing" against the PR's changed-file count.
- **A brief scoped to "confirm the bug" still owes a read of the FIX PR's unresolved review threads.** In-band sentinels in a validator are their own bug class; model the arithmetic.
- **Coverage shape matters**: a test can pass while never entering the branch the fix changed (single-element vs wholesale array copy).
- **A flagged correctness gap in the mechanism the PR changes is in-scope**, never a follow-up; codegen review is execution-first (compile the shape + SPIR-V validation).
- **When a maintainer keeps calling a bot PR a rewrite, concede early** — stand down without restating the design.
- **A nudge is justified by deviation from the repo's base rate, never an absolute day count.** The draft interval resets the clock; read the timeline actor before reporting a dismissed approval.

## Overview

How hard to rate a finding, and how wide to scope a review — the two calibration axes that decide whether a review's output is trustworthy. Rating one notch too hard turns a maintainer question into an autonomous BLOCK; a severity label with no evidence becomes a work directive nobody audits; a review scoped too narrowly credits a verdict for files a bot never opened, or misses the fix's own instance of the bug class.

## Re-review Scope: Redesign Gaps and Self-Recommended Nits Don't Reset the Pipeline

When a fixer reworks a PR in response to feedback and re-requests review, the re-run must (1) confirm the round-1 findings are actually closed and (2) look for NEW gaps the redesign introduced ([Re-review after a PR redesign: check for gaps the redesign introduced, not just old ones closed](../learnings/1782873135829-re-review-after-a-pr-redesign-check-for-gaps-the-r.md)). When a follow-up commit *only* incorporates a nit the reviewer itself recommended (e.g. a doc comment from a Reviewer C clarity finding), do **not** re-run the full three-reviewer pipeline — verify the recommended change landed ([Reviewer: a self-recommended comment addition does not reset the PR review pipeline](../learnings/1782857285922-reviewer-a-self-recommended-comment-addition-does-.md)).

## Severity Calibration: Benign-Output, Doc-vs-Behavior, and Maintainer Labels

**"Benign / produces valid output" must hold on every reachable emit target.** On slang #11917 batch-3 / PR #12281 an early-out change *kept* a public empty struct that master stripped; the fixer, peer reviewer, triage and codex all called it benign because "a 0-member `OpTypeStruct` is valid SPIR-V" — true for direct SPIR-V, but empty structs are **illegal GLSL syntax**, so `-emit-spirv-via-glsl` made glslang fail where master compiled. Before rating an emit-affecting change benign, enumerate the reachable targets (HLSL, GLSL/`-emit-spirv-via-glsl`, direct SPIR-V, Metal, WGSL, CUDA/PTX, CPU) and prefer an adversarial cross-target probe over reasoning from one backend; empty aggregates, bool-typed constants and pointer-as-param are common target-divergent shapes ([benign/valid-output severity calls must check every reachable emit target](../learnings/1785449256204-benign-valid-output-severity-calls-must-check-ever.md)).

**A doc-vs-behavior conflict on a maintainer-owned design point is a QUESTION for maintainer intent, not an autonomous BLOCK.** On slang #8125 / PR #12304, review empirically (and correctly) traced that removing `IRPublicDecoration` at lowering makes plain-`public` CPU/CUDA functions emit `static`, contradicting `docs/cpu-target.md:210`, and rated it BLOCKING. jkwak then approved and flipped it ready himself: the `public` keyword "is supposed to do nothing" (a csyonghe Code-Review-meeting decision), so the behavior change was intended and the *doc* was stale. The rigor (empirical before/after against the base binary, predicate/consumer traces, exact doc citation) was right and load-bearing; only the severity was one notch too hard. Ask "could a maintainer have intended this contract change?" For a keyword's meaning, an emit convention or a visibility policy, surface a high-signal QUESTION with the doc conflict as evidence and defer the verdict to the maintainer, especially when the maintainer dictated the approach. Reserve REQUEST_CHANGES strength for changes wrong *regardless* of intent (memory safety, silent miscompile, an ABI guarantee the PR claims to preserve). The orchestrator/fixer re-frames such a BLOCK downstream as a neutral intent question (offer the branches) rather than acting on it ([doc-vs-behavior conflict is a QUESTION/GAP for maintainer intent, not an autonomous BLOCK](../learnings/1785539717795-severity-calibration-doc-vs-behavior-conflict-is-a.md), [doc-vs-behavior conflict on a maintainer-owned design point is a QUESTION, not a BLOCK](../learnings/1785539785590-review-severity-doc-vs-behavior-conflict-on-a-main.md)).

**A maintainer-applied label (or Type/milestone) can encode the direction they are driving toward**, not the current diff. On slang #12120 / PR #12195 the `pr: breaking change` label looked wrong against a still-default-OFF (technically non-breaking) HEAD, but jkwak had applied it himself after redirecting the scope toward default-ON; the label deliberately led the code. Human triage is authoritative — never overwrite it. Before surfacing a label discrepancy, pull the applier + timestamp and check whether a later maintainer comment superseded the framing your directive holds; if you still raise it, frame it as "HEAD is X, label says Y — intentional forward-looking, or worth a look?" ([maintainer labels can encode intended future direction — verify scope currency before flagging a mismatch](../learnings/1785540385736-maintainer-labels-can-encode-intended-future-direc.md)).

## The Severity Label Itself Is a Claim; a Comparative Claim Needs a Discriminating Fixture

**A severity label can supply authority where evidence is missing, so the claim is never evaluated.** On shader-slang/slang#11917 both of the worst errors in a long chain travelled under a label. One note asserted that a scan arm must enumerate four opcodes or it's a *stale-FALSE miscompile*; it was relayed verbatim in two dispatches and stored as **safety-critical**, then three successive mechanisms for it died and the conclusion did not survive. A second finding was asserted as **must-fix** twice with no evidence and was later demoted to defense-in-depth by a drill: the isolating shape existed, but a broader implication set the flag anyway, and a 60-test sweep found no instance of the isolating condition. An ordinary claim invites *"is that so?"*; a severity label invites *"what do we do about it?"*, converting an unverified assertion into a **work directive** that gets executed rather than audited. It **inverts the verification gradient** (the more urgent a finding sounds, the less anyone checks, because checking looks like obstructing) and **survives relay better than reasoning does** — mechanism detail is compressed away at each hop, `must-fix` never is. So **`must-fix`, `safety-critical`, `P0`, `blocker`, `miscompile` are claims about the world — attach the evidence in the same breath, or don't attach the label**; when you receive one, ask what measurement backs it before scheduling work. (This differs from a wrong mechanism riding a right conclusion, which draws no pushback because the conclusion is correct.) What saved the chain was the implementing tier **refusing a headline two tiers above it had requested**, running the drill anyway, and reporting the demotion upward — the hardest correction in a hierarchy, and the only reason nothing false reached the public artifact. When you send a labeled finding down, say the label is contingent and you want it drilled, not honored; a downstream tier that contradicts you on measurement is your most valuable instrument, and its willingness to do so can be protected or destroyed [a must-fix or safety-critical label is a claim owing the same evidence as any other](../learnings/1785828631090-a-must-fix-or-safety-critical-label-is-a-claim-owi.md).

**A comparative claim is a claim about a DIFFERENCE, so the fixture must separate the two outcomes being compared.** Reviewing a partial fix on slang#12150, a fixer graded an incomplete fix safe to ship — *"on pristine master every function gets the entry CU; with my change 3 of 4 become correct and the shared-header occurrence stays on the old fallback ⇒ strictly better, never worse"* — while its own trace said `tu-mod=bmod  common.h -> amod.slang ❌ should be bmod.slang`: resolution to the **wrong includer**, not a fallback. The repro put the entry point in `amod.slang`, one of the two includers, so amod's CU equalled the entry CU and the two outcomes were **byte-identical**: "fell back to the entry CU" (same as master) and "resolved to amod" (a confidently wrong specific file, arguably worse than master) could not be told apart. For debug info the second is worse — master emitted a known-generic fallback, the change a specific wrong file with nothing signalling doubt — which flips ship/hold. The discriminating configuration puts the entry point in a **third** file. Whenever the claim is "no worse than", "strictly better" or "regression-free", a repro where the buggy answer coincides with the baseline cannot support it, however carefully the trace was read; the same fixer had been bitten three times that morning by entry-point-pinned fallbacks coinciding with the correct answer.

**Identity bugs recur one axis finer, so enumerate the axes.** On the predecessor PR a reviewer caught *"an included `SourceFile` can be owned by a parent manager while its view lives in the TU's manager"* (an identity bug across **managers**, fixed); the new bug is the same defect across **occurrences**, since `findIncludingNonIncludedSourceFile` matches views by `SourceFile*`, so lowering module *B* finds module *A*'s view of the same header and walks back to A's includer. **`SourceFile*` is the wrong identity for a question about inclusion — only the include *occurrence* has an includer.** On any identity/aliasing fix, enumerate the axes (`file` · `file+manager` · `file+occurrence` · `file+TU` · …) and ask which axis **the question** lives on. **Narrowing a candidate set is not making it unique:** "only consider views whose initiating loc belongs to this TU" still leaves >1 candidate when two files in one module include the same header, so the check reads one element of an unordered set — it passes, order-dependently wrong, and cannot be validated by running it. If you choose "first occurrence", assert and justify it (with an include guard, only the first occurrence parsed the text that produced the decl) and test two includers in one TU. A **"ship narrower" fallback** (bail on ambiguity) is usually not cheaper than the full fix, because detecting ambiguity needs the same enumeration; and for debug info, **correct-or-silent beats sometimes-wrong**, since a wrong scope misleads a debugger while a generic one merely omits [a severity claim needs a repro that can distinguish "fell back" from "answered wrong"](../learnings/1785828537069-a-severity-claim-needs-a-repro-that-can-distinguis.md).

## A Fix Invisible to the Suite AND the Validator Owes a REQUIRED Regression Test

When an emit/codegen fix's output is indistinguishable to everything currently guarding the code — the full suite passes on both builds AND the format validator accepts both — the targeted regression test is a merge requirement, not a nice-to-have. On slang#13237 (SPIR-V debug info) the buggy body-keyed dedup build (`b42cf336`) and the fixed record-keyed build (`5706238`) both passed all 606 `tests/spirv/` and both had `spirv-val` rc=0, because the validator tolerates multiple `DebugFunctionDefinition`s per record; a future refactor back to body-keying would silently reintroduce the bug. "Documented in-code + one-time manual verification" is insufficient there; don't downgrade the test to optional because the suite is green — green proves nothing about this fix. For -g2 SPIR-V, ID-anchor the FileCheck (`CHECK-COUNT-1` capturing IDs, not matching source text) to dodge the embedded-`OpString` false match; the test stays GPU-free [A fix invisible to both the test suite AND the validator needs its regression test as a REQUIRED item, not optional](../learnings/1790162935737-a-fix-invisible-to-both-the-test-suite-and-the-val.md).

## A Bot's Verdict Covers Only the Files It Read — Extension-Based Default Excludes

A review bot can read the PR, post a well-formed verdict, and never open the file the PR is about. **CodeRabbit excludes `**/*.map` by default, and that default lives in the tool, not the repo**: shader-slang/slang's `.coderabbit.yaml:22-25` filters only `!build/**` and `!external/**`. On slang PR #12379 (2026-08-06) the notice read *"Files ignored due to path filters (1) · `source/slang-glslang/slang-glslang.map` is excluded by `!**/*.map`"* then *"Files selected for processing (2)"* — on a **3-file** PR whose omitted file was the GNU ld **version script defining the shared module's public ABI**, the substance of the fix. The default targets JavaScript/CSS source maps; it collides with hand-maintained linker version scripts, symbol lists and export lists that share the extension.

This is worse than an ordinary gap: a wrong or missing version-script entry **does not fail the build** — the symbol is simply absent from the dynamic symbol table, and on that PR the consumer dereferences the resulting null unguarded (`source/compiler-core/slang-glslang-compiler.cpp:426`), so a dropped export **crashes rather than diagnoses**. The exclusion is disclosed only inside a collapsed `<details>` block worded as housekeeping, a paper trail that looks like transparency while nobody reads it. **Compare "files selected for processing" against the PR's changed-file count.** `git ls-files | grep '\.map$'` on that master returned **0**, so the PR introduced the repo's first file of an ignored class; the absence of past incidents is no evidence of coverage. If a repo gains a hand-written `.map`-class file, add an explicit un-exclude to `.coderabbit.yaml` (path filters are additive over the defaults). When such a file is in a PR, don't treat any bot review as coverage of it: derive the export set three ways — the map, the producer that defines the exports, and every consumer `dlsym`/`findFuncByName` — and require all three to match. Any review tool with extension-based default excludes carries this blind spot ([CodeRabbit ignores `*.map` by default, so linker version scripts go unreviewed](../learnings/1785991860433-coderabbit-ignores-map-by-default-linker-version-s.md)).

## A Brief Scoped to the Bug Still Owes a Read of the Fix's Open Threads

When a brief scopes you to "confirm these facts about the bug," the unasked question is whether the **fix** contains its own instance of the same bug class, so read the fix PR's *unresolved* review threads before deciding pre-merge priority. On slang #12376 (fossil OOB reads) and fix PR #12354, both of the issue's facts were verified and the public verdict led with a missing regression test — while the PR's validating walk, whose purpose is to *"prove every location a consumer can reach lies inside the blob,"* had a constructible bypass flagged in a thread still `isResolved=false` / `isOutdated=false` 23 hours and 7 commits later. `kNullOffset = -1`; `_readRelativePtr()` decides null from the **raw** stored offset (`raw == 0`) but returns the **computed** target `offset + raw`, and the call sites compare that computed value against the sentinel and skip validation. Raw `-1 - D` is non-zero and fits `int32_t`, so the computed result is exactly `-1`: the walk treats a live pointer as null, while the consumer's `get()` (null only on raw `_offset == 0`) resolves `base - 1` and dereferences it.

**In-band sentinels inside a validator are a bug class of their own:** if the validator's null test and the consumer's are computed from different values (raw field vs derived address), a crafted input satisfies one and not the other — check that they match exactly. **Model the arithmetic instead of trusting the algebra:** a 20-line script over realistic offsets with two controls (genuine nulls still map to the sentinel; ordinary forward pointers don't collide) turns "looks constructible" into "constructible at D = 0, 4, 12, 28, 32, 160, 3840, …", which licenses publishing a confirmed defect. Credit the origin: that thread was found by a review bot, and the public text must say so; re-deriving someone else's finding and presenting it as yours is the same defect as re-deriving their control and framing it as a refutation of them ([read the fix PR's open review threads, not just the issue's facts](../learnings/1785985363443-scoped-to-verify-the-bug-read-the-fix-s-open-revie.md)).

## Before Nudging a Stalled PR, Compute the Repo Base Rate and Read the Timeline Actor

A "PR has been awaiting review for N days" premise fails several ways that look identical to a real stall, and the right output is often "post nothing"; on shader-slang/slang#12179 (2026-08-04) the conclusion flipped from "nudge warranted" to "post nothing" once each premise was checked [before nudging a stalled PR, compute the repo base rate and check the draft interval](../learnings/1785838727264-before-nudging-a-stalled-pr-compute-the-repo-base-.md):

1. **Age since creation is not reviewer-idle time — the draft interval resets the clock.** #12179 was "awaiting review since 07-23", but the timeline shows `convert_to_draft` 07-23 then `ready_for_review` 07-27, so the idle window was 8 days, not 14; and "last comment 07-23" held only for issue-level comments (the author left inline review replies on 07-27). Probe: `gh api "repos/O/R/issues/N/timeline?per_page=100" --jq '.[] | select(.event=="ready_for_review" or .event=="convert_to_draft" or .event=="review_dismissed")'`; the last `ready_for_review` starts the clock.
2. **"Idle N days" means nothing without the repo's base rate.** 32 of 53 open non-draft PRs (60%) were idle ≥8 days, so 8 days was the median condition and nudging the one PR you happen to be looking at is noise dressed as diligence (the same error as reading a 2-night CI failure cluster as a regression without the 35-run base rate). Two `gh api "repos/O/R/pulls?state=open&per_page=100"` calls (with and without a `select(.updated_at < "<cutoff>")` filter) compute it.
3. **Check whether the requested reviewer formally reviews at all**: `reviewed-by:<login>` can be 0 while `commenter:`/`author:` are in the hundreds, and the login may sit on dozens of review-requested PRs, so "hasn't reviewed in N days" is a queue-wide property.
4. **A dismissed approval can be the AUTHOR's own doing**: read the `review_dismissed` actor. An author dismissing his own approval while reworking knows re-review is needed — evidence against a nudge; "a dismissed review from <reviewer>" invites the false reading that a reviewer rejected something.
5. **`mergeable_state=blocked` with green CI = a missing approving review**, not breakage.

A nudge is justified by *deviation from this repo's norm*, never by an absolute day count; compute the norm first and let the answer be "post nothing".

## Coverage-Shape Scoping: a Single-Element Copy Exercises Only One Branch (lowerCopyLogical untyped-flavor fixes)

When reviewing a `lowerCopyLogical` "preserve untyped SPIR-V pointer flavor on derived addresses" fix (slang#13027 / #13022 — descriptor-heap `ConstantBuffer<T>` leaf-field reads emitting invalid `OpAccessChain` on an untyped base), check the test's coverage shape. `SomeStruct s = cb.arr[i];` copies one array ELEMENT: the `arr[i]` indexing lowers to a separate `getElementPtr` (retyped by the pre-existing worklist pass), and the following `copyLogical` has a STRUCT source type, so `lowerCopyLogicalWithDestImpl` enters only the struct-field branch (`emitFieldAddressKeepingFlavor`). The array-element branch (`emitElementAddressKeepingFlavor`, via `else if (auto srcArrayType = as<IRArrayType>(srcValType))`) is never exercised — neither its ≤16-element unroll nor the >16-element `emitLoopBlocks` sub-path (newly reachable on SPIR-V 1.4+ once the extra `lowerCopyLogical(module, onlyUntypedPtrOperand=true)` call is added). Drive it with a WHOLESALE array copy (`struct WithArray { int vals[20]; }` then `int local[20] = cb.vals;`), ideally one ≤16 and one >16 case. A `CHECK-NOT: OpTypePointer Uniform %int` passes only because every leaf is `int`; tighten to `CHECK-NOT: OpTypePointer Uniform` (descriptor-heap buffers use only `OpTypeUntypedPointerKHR` for Uniform). The new `*KeepingFlavor` helpers are necessary, not redundant with `processFieldAddress`/`processGetElementPtrImpl`, because of ORDERING: `lowerCopyLogical` runs after both `processWorkList()` drains in `processModule()`, so its addresses are never revisited; the complementary clarity ask is to document that ordering invariant at the call site ([reviewing lowerCopyLogical untyped-flavor fixes: single-element copy only tests the struct-field branch](../learnings/1789177486273-reviewing-lowercopylogical-untyped-flavor-fixes-si.md)).

## Scope-Deferral: A Correctness Gap in the Edited Mechanism Is In-Scope

The deferral line is **not** size but **"is this a correctness gap in the mechanism this PR changes, or an independent enhancement?"** A correctness gap in the code path you are editing is in-scope by definition — reproduce and close it, or prove it unreachable — never "later", especially once a reviewer or codex has flagged it; an independent enhancement needing its own design call is deferrable via a turnkey follow-up issue carrying the concrete example and the open design question. On slang#12563, in round 28 codex flagged a "via-call" gap — a pointer-returning call with NO pointer args (`int* pick(){ return &gShared; }`) never reconciles the call-result address space, because the `!hasSpecializableArg` early-`break` skips the only reconciliation site — and the fixer scoped it out; ~28 rounds of reading/layering/wording review followed, and the maintainer then found it **BLOCKING** by *running the compiler* (OpFunctionCall type mismatch → invalid SPIR-V, the simplest case of #12498, the issue the PR was meant to fix). Don't over-correct into defensive scope-creep; the fix is a sharper criterion, not "defer nothing". For codegen/SPIR-V changes verification is **execution-first** for reviewers as much as fixers: reading review is structurally blind to this class, so reproduce → fix → **compile the actual shape and run SPIR-V validation** ([a flagged correctness gap in the mechanism you're changing is in-scope, never a follow-up](../learnings/1789550935195-scope-defer-line-a-flagged-correctness-gap-in-the-.md)).

**The scope decision can also be "stop entirely".** When a maintainer repeatedly says "this isn't what I asked for" and signals a reboot on a stronger model, concede rather than grind a fix list; each round burns budget and goodwill. A fidelity gate (e.g. a codex PLAN_REVIEW) that keeps finding the plan still approximates the spec is itself the stop signal, to be reported upward rather than built. Stand down with a brief, non-defensive GitHub ack that does NOT restate the design, offer branch/PR disposition and the research note as a head-start, and let the orchestrator own the program-level response; report the stand-down to the parent as a plain status, not a `[Fix Report]`, or the critique-on-deliver gate demands an OUTPUT_REVIEW for a deliverable that doesn't exist ([when a maintainer keeps calling a bot PR a rewrite, concede early — don't grind rounds](../learnings/1790117615291-when-a-maintainer-keeps-calling-a-bot-pr-a-rewrite.md)).
