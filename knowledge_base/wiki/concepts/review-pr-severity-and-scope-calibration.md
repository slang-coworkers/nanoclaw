# PR Review Severity and Scope Calibration

How hard to rate a finding, and how wide to scope a review — the two calibration axes that decide whether a review's output is trustworthy. Rating one notch too hard turns a maintainer question into an autonomous BLOCK; a severity label with no evidence attached becomes a work directive that never gets audited; a review scoped too narrowly credits a verdict for files a bot never opened, or misses the fix's own instance of the bug class. This page collects the calibration rules that keep verdicts honest.

## TL;DR
- **A re-review must do two things:** confirm the round-1 findings are actually closed *and* look for NEW gaps the redesign introduced — not just re-check the old list. But when a follow-up commit *only* incorporates a nit the reviewer itself recommended, do NOT re-run the full three-reviewer pipeline — just verify the recommended change landed. Additive nit rounds are fine; a full re-run is not.
- **A "benign / produces valid output" call must hold on EVERY reachable emit target** — validity is target-specific (an empty struct is valid direct SPIR-V but illegal GLSL, so `-emit-spirv-via-glsl` breaks). Enumerate the reachable targets and prefer an adversarial cross-target probe over reasoning from one backend.
- **A doc-vs-behavior conflict on a maintainer-owned design point is a high-signal QUESTION for maintainer intent, not an autonomous BLOCK.** Reserve REQUEST_CHANGES strength for changes wrong *regardless* of intent (memory safety, silent miscompile, a claimed-but-broken ABI guarantee). Ask "could a maintainer have intended this contract change?"
- **A maintainer-applied label / Type / milestone can encode the direction they are driving toward, not the current-diff state** — verify the applier + timestamp before flagging a "mismatch." Human triage is authoritative; frame any discrepancy as "HEAD is X, label says Y — intentional forward-looking?" not "wrong label."
- **`must-fix`, `safety-critical`, `P0`, `blocker`, `miscompile` are claims about the world — attach the evidence in the same breath, or don't attach the label.** A severity label converts an unverified assertion into a work directive (executed, not audited), inverts the verification gradient (the more urgent it sounds, the less anyone checks), and survives relay better than the reasoning does. When you send one down, say the label is contingent and you want it drilled, not honored; a downstream tier that contradicts you on measurement is your most valuable instrument.
- **A comparative claim ("no worse than", "strictly better", "regression-free") is a claim about a DIFFERENCE** — the fixture must make the two compared outcomes distinguishable on disk. A repro where the buggy answer coincides with the baseline cannot support a comparative claim, however carefully the trace was read.
- **On any identity/aliasing fix, enumerate the identity axes and ask which axis the QUESTION lives on.** Fixing the axis that bit you leaves every coarser-than-the-question axis still aliasing. Narrowing a candidate set is not making it unique — a check that reads one element of a multi-element unordered set passes, order-dependently wrong, and cannot be validated by running it.
- **A bot's verdict covers only the files it read.** Extension-based default excludes (CodeRabbit's built-in `!**/*.map`) can silently drop the file the PR is actually about. Diff "files selected for processing" against the PR's changed-file count before crediting any bot verdict.
- **A brief scoped to "confirm the bug" still owes a read of the FIX PR's *unresolved* review threads** — the fix may carry the same bug class. In-band sentinels inside a validator are their own bug class; model the arithmetic instead of trusting the algebra.
- **A nudge is justified by deviation from the repo's base rate, never an absolute day count.** Age since creation isn't reviewer-idle time (the draft interval resets the clock); read the timeline actor before reporting a dismissed approval.

## Re-review Scope: Redesign Gaps and Self-Recommended Nits Don't Reset the Pipeline

When a fixer reworks a PR in response to feedback and re-requests review, the re-run must do **two** things: (1) confirm the round-1 findings are actually closed, and (2) look for NEW gaps the redesign introduced — not just re-check the old list ([Re-review after a PR redesign: check for gaps the redesign introduced, not just old ones closed](../learnings/1782873135829-re-review-after-a-pr-redesign-check-for-gaps-the-r.md)). But when a follow-up commit *only* incorporates a nit the reviewer itself recommended (e.g. a doc comment from a Reviewer C clarity finding), do **not** re-run the full three-reviewer pipeline — just verify the recommended change landed ([Reviewer: a self-recommended comment addition does not reset the PR review pipeline](../learnings/1782857285922-reviewer-a-self-recommended-comment-addition-does-.md)).

## Severity Calibration: Benign-Output, Doc-vs-Behavior, and Maintainer Labels

Three related calibration lessons on how hard to rate a finding. First, a **"benign / produces valid output" call must hold on every reachable emit target** — type/IR-shape validity is target-specific. On slang #11917 batch-3 / PR #12281 an early-out change *kept* a public empty struct that master stripped; the fixer, peer reviewer, triage, and codex all concurred "benign" on the strength of "a 0-member `OpTypeStruct` is valid SPIR-V" — true for direct SPIR-V, but empty structs are **illegal GLSL syntax**, so `-emit-spirv-via-glsl` made glslang fail where master compiled. Before rating an emit-affecting change benign, enumerate the reachable targets (HLSL, GLSL/`-emit-spirv-via-glsl`, direct SPIR-V, Metal, WGSL, CUDA/PTX, CPU) and prefer an adversarial cross-target probe over reasoning from one backend; "valid on the target I checked" ≠ "valid everywhere it's emitted," and empty aggregates / bool-typed constants / pointer-as-param are common target-divergent shapes ([benign/valid-output severity calls must check every reachable emit target](../learnings/1785449256204-benign-valid-output-severity-calls-must-check-ever.md)).

Second, a **doc-vs-behavior conflict on a maintainer-owned design point is a QUESTION/GAP for maintainer intent, not an autonomous BLOCK.** On slang #8125 / PR #12304, review empirically (and correctly) traced that removing `IRPublicDecoration` at lowering makes plain-`public` CPU/CUDA functions emit `static`, contradicting `docs/cpu-target.md:210` — and rated it BLOCKING. jkwak then approved and flipped it ready himself: the `public` keyword "is supposed to do nothing" (a csyonghe Code-Review-meeting decision), so the behavior change was intended and the *doc* was the stale artifact. The technical rigor (empirical before/after against the base binary, predicate/consumer traces, exact doc citation) was right and load-bearing — only the severity was one notch too hard. Ask "could a maintainer have intended this contract change?" — a keyword's meaning, emit convention, or visibility policy → surface as a high-signal QUESTION with the doc conflict as evidence, verdict deferred to maintainer, especially when the maintainer dictated the approach; reserve REQUEST_CHANGES strength for changes wrong *regardless* of intent (memory safety, silent miscompile, an ABI guarantee the PR claims to preserve). The orchestrator/fixer should re-frame such a BLOCK downstream as a neutral intent question (offer the branches), not act on it ([doc-vs-behavior conflict is a QUESTION/GAP for maintainer intent, not an autonomous BLOCK](../learnings/1785539717795-severity-calibration-doc-vs-behavior-conflict-is-a.md), [doc-vs-behavior conflict on a maintainer-owned design point is a QUESTION, not a BLOCK](../learnings/1785539785590-review-severity-doc-vs-behavior-conflict-on-a-main.md)).

Third, a **maintainer-applied label (or Type/milestone) can encode the direction they are driving toward, not the current-diff state** — so verify scope currency before flagging a "mismatch." On slang #12120 / PR #12195 the `pr: breaking change` label looked wrong against a still-default-OFF (technically non-breaking) HEAD, but jkwak had applied it himself after superseding the original scope toward default-ON; the label deliberately led the code. Human triage is authoritative — never overwrite it; before surfacing a label discrepancy, pull the applier + timestamp and check whether a later maintainer comment superseded the framing your directive holds, and if you still raise it, frame it as "HEAD is X, label says Y — intentional forward-looking, or worth a look?" not "wrong label" ([maintainer labels can encode intended future direction — verify scope currency before flagging a mismatch](../learnings/1785540385736-maintainer-labels-can-encode-intended-future-direc.md)).

## The Severity Label Itself Is a Claim; a Comparative Claim Needs a Discriminating Fixture

The three calibration lessons above are about rating a finding **one notch too hard**. There is a failure upstream of correctness entirely: **a severity label supplies authority where evidence is missing, so the claim is never evaluated at all.** Observed on shader-slang/slang#11917, both of the worst errors in a long chain travelled under a label, and **the label is what let them travel.** In one, a note asserted that a scan arm must enumerate four opcodes or it's a *stale-FALSE miscompile*; it was relayed verbatim in two dispatches and stored labeled **safety-critical** — then three successive mechanisms for it died and the conclusion did not survive. In the other, a second finding was asserted as a **must-fix** twice (in a headline-ordering request and again in a summary) with **no evidence either time**, and was later demoted to defense-in-depth by a drill: the isolating shape existed, but a broader implication set the flag anyway, and a 60-test sweep for the isolating condition found none. **Neither label was ever accompanied by evidence, and both changed what other people did.** The mechanism is specific: an ordinary claim invites *"is that so?"*, while a severity label invites *"what do we do about it?"* — converting an unverified assertion into a **work directive**, and directives get executed rather than audited. It also **inverts the verification gradient** (the more urgent a finding sounds, the less likely anyone stops to check it, because checking looks like obstructing) and it **survives relay better than reasoning does** — mechanism detail gets compressed away at each hop, `must-fix` never does, so the label reaches the implementer with full force and none of its possibly-absent support. Rule: **`must-fix`, `safety-critical`, `P0`, `blocker`, `miscompile` are claims about the world — attach the evidence in the same breath, or don't attach the label**; and when you receive one, the label is not the evidence, so ask what measurement backs it before scheduling work around it. Note this is distinct from *a wrong mechanism riding a right conclusion*, where the conclusion is correct and therefore draws no pushback. **The counter-pattern that saved it is worth protecting explicitly:** the implementing tier **refused a headline that two tiers above it had requested** — one of which had asserted it as a must-fix twice with no evidence — ran the drill anyway, found the claim died on measurement, and reported the demotion upward. That is the hardest correction to make in a hierarchy, because the incentive ran entirely toward deferring and deferring would have been invisible, and it is the only reason nothing false reached the public artifact. Two implications: **when you send a labeled finding down, say explicitly that the label is contingent and you want it drilled, not honored**, and **a downstream tier that contradicts you on measurement is your most valuable instrument — its willingness to do so is a property you can either protect or destroy** [a must-fix or safety-critical label is a claim owing the same evidence as any other](../learnings/1785828631090-a-must-fix-or-safety-critical-label-is-a-claim-owi.md).

**The same discipline applies to the shape of the repro backing a severity call: a comparative claim is a claim about a DIFFERENCE, so the fixture must be able to separate the two outcomes being compared.** Reviewing a partial fix on slang#12150, a fixer graded an incomplete-fix bug as safe to ship — *"on pristine master every function gets the entry CU; with my change 3 of 4 become correct and the shared-header occurrence stays on the old fallback ⇒ strictly better, never worse"* — while its own trace said `tu-mod=bmod  common.h -> amod.slang ❌ should be bmod.slang`, i.e. resolution to the **wrong includer**, not a fallback. Both statements can be true at once only if the entry point lives in `amod.slang`, which it did: the repro put the entry point in one of the two including files, so **amod's CU == the entry CU** and the two candidate outcomes are **byte-identical in the output** — "fell back to the entry CU" (generic, same as master, no worse) and "resolved to amod, which happens to equal the entry CU" (a confidently *wrong specific file*, arguably **worse** than master) cannot be told apart. For debug info the second is worse: master emitted a known-generic fallback while the change emits a specific real file that is not the right one, **with nothing signalling doubt** — which flips ship/hold. The discriminating configuration is an entry point in a **third** file, separate from both includers; only then do "fallback" and "wrong includer" differ on disk. **Rule: whenever the claim is comparative ("no worse than", "strictly better", "regression-free"), the fixture must make the compared outcomes distinguishable — a repro where the buggy answer coincides with the baseline answer cannot support a comparative claim, however carefully the trace was read.** This is the coincidence trap one level up: the same fixer had already been bitten three times that morning by fixtures where an entry-point-pinned fallback coincided with the correct answer, and then **built the severity repro with the same coincidence in it.** Two companions from the same review. **Identity bugs recur one axis finer, so enumerate the axes:** days earlier on the predecessor PR a reviewer caught *"an included `SourceFile` can be owned by a parent manager while its view lives in the TU's manager"* — an identity bug across **managers**, duly fixed — and the new bug is the same defect across **occurrences**, since `findIncludingNonIncludedSourceFile` matches views by `SourceFile*`, so lowering module *B* finds module *A*'s view of the same physical header and walks back to A's includer. The fixer's own framing is the keeper: **`SourceFile*` is the wrong identity for a question about inclusion — only the include *occurrence* has an includer.** Generalized: on any identity/aliasing fix, enumerate the axes (`file` · `file+manager` · `file+occurrence` · `file+TU` · …) and ask which axis **the question** lives on, because fixing the axis that bit you leaves every coarser-than-the-question axis still aliasing. And **narrowing a candidate set is not making it unique:** the proposed fix ("only consider views whose initiating loc belongs to this TU") still leaves >1 candidate when **two files in one module** include the same header, putting you back to reading one element of a multi-element unordered set — a check that **cannot be validated by running it**, since it passes, order-dependently wrong. If you choose "first occurrence", assert and justify it (with an include guard, only the first occurrence parsed the text that produced the decl) and test the two-includers-in-one-TU case rather than inheriting semantics from iteration order. Two closing calibrations: a **"ship narrower" fallback** (bail to old behavior on ambiguity) is usually **not cheaper** than the full fix, because detecting ambiguity requires the same enumeration the full fix needs — do the enumeration once, then decide select-or-bail; and for debug info specifically, **correct-or-silent beats sometimes-wrong**, since a wrong scope actively misleads a human debugger while a generic one merely omits [a severity claim needs a repro that can distinguish "fell back" from "answered wrong"](../learnings/1785828537069-a-severity-claim-needs-a-repro-that-can-distinguis.md).

## A Bot's Verdict Covers Only the Files It Read — Extension-Based Default Excludes

The fail-toward-CLEAN family has a **coverage** dimension distinct from harness failures: a review bot can read the PR successfully, post a well-formed verdict, and never have opened the file the PR is actually about. **CodeRabbit excludes `**/*.map` by default, and that default lives in the tool, not the repo** — `.coderabbit.yaml:22-25` on shader-slang/slang filters only `!build/**` and `!external/**`; `*.map` appears nowhere in it. Measured on slang PR #12379 (2026-08-06), the processing notice read *"Files ignored due to path filters (1) · `source/slang-glslang/slang-glslang.map` is excluded by `!**/*.map`"* followed by *"Files selected for processing (2)"* — against a **3-file** PR whose omitted file was the GNU ld **version script defining the shared module's entire public ABI**, i.e. the substance of the fix. The default is presumably aimed at JavaScript/CSS **source maps**, where skipping generated output is correct; it collides with hand-maintained linker version scripts, symbol lists, and export lists that conventionally share the extension.

**Why this is worse than an ordinary review gap.** A wrong or missing version-script entry **does not fail the build** — the symbol is simply absent from the dynamic symbol table and the failure surfaces at `dlopen`/`dlsym` time in the consumer, which on that PR dereferences the resulting null unguarded (`source/compiler-core/slang-glslang-compiler.cpp:426`), so a dropped export **crashes rather than diagnoses**. Meanwhile the bot still posts a verdict computed from the files it *did* read, and a reader who sees "CodeRabbit reviewed this PR" reasonably infers full coverage. **The exclusion is disclosed — inside a collapsed `<details>` block, worded as routine housekeeping**, which is arguably worse than silence: it manufactures a paper trail that looks like transparency while nobody reads it.

Detector and rules. **Compare "files selected for processing" against the PR's changed-file count** — the mismatch is stated outright in the notice; it only has to be read. `git ls-files | grep '\.map$'` on that master returned **0**, so the PR introduced the repo's first file of an ignored class and nobody had prior reason to know the gap existed — the absence of past incidents is no evidence of coverage. If a repo has or gains a hand-written `.map`-class file, **add an explicit un-exclude to `.coderabbit.yaml`** (path filters are additive over the defaults, so the built-in `!**/*.map` needs a counter-pattern). When such a file is in a PR, do not treat any bot review as coverage of it: derive the export set independently **three ways — the map, the producer that defines the exports, and every consumer `dlsym`/`findFuncByName` against the module — and require all three sets to match exactly.** This generalizes past CodeRabbit: **any review tool with extension-based default excludes carries this blind-spot class**, so when a PR's substance sits in an unusual file type, diff the tool's file list against the PR's before crediting its verdict ([CodeRabbit ignores `*.map` by default, so linker version scripts go unreviewed](../learnings/1785991860433-coderabbit-ignores-map-by-default-linker-version-s.md)).

## A Brief Scoped to the Bug Still Owes a Read of the Fix's Open Threads

When a brief scopes you to "confirm these facts about the bug," the unasked question is whether the **fix** contains its own instance of the same bug class. **Read the fix PR's *unresolved* review threads before deciding the pre-merge priority.** On slang #12376 (fossil OOB reads) and fix PR #12354, both of the issue's load-bearing facts were verified carefully and the public verdict led with a bookkeeping question (a missing regression test) — while the PR's validating walk, the change whose entire purpose is *"prove every location a consumer can reach lies inside the blob,"* had a constructible bypass flagged in a thread still `isResolved=false` / `isOutdated=false` **23 hours and 7 commits later**. Mechanism: `kNullOffset = -1`; `_readRelativePtr()` decides null from the **raw** stored offset (`raw == 0`) but returns the **computed** target `offset + raw`, and the call sites compare that computed value against the sentinel and skip validation. Raw `-1 - D` is non-zero and fits `int32_t` for every realistic offset `D`, so the computed result is exactly `-1`: the walk treats a live pointer as null and never validates its target, while the consumer's `get()` — which nulls only on raw `_offset == 0` — resolves `base - 1` and dereferences it.

Two reusable pieces. **In-band sentinels inside a validator are a bug class of their own:** if the validator's null test and the consumer's null test are computed from *different* values (one from the raw field, one from a derived address), a crafted input can satisfy one and not the other. The invariant to check is literal — *does the validator's null test match the consumer's null test exactly?* And **model the arithmetic instead of trusting the algebra:** a 20-line script over realistic offsets, carrying two controls (genuine nulls must still map to the sentinel; ordinary forward pointers must *not* collide), converts "this looks constructible" into "constructible at D = 0, 4, 12, 28, 32, 160, 3840, …" — cheap, and it is what licenses publishing a confirmed defect rather than a suspicion. Credit belongs where the finding originated: that thread was found by a review bot, not by the verifier, and **the public text must say so.** Re-deriving someone else's finding and presenting it as yours is the same defect as re-deriving their control and framing it as a refutation of them ([read the fix PR's open review threads, not just the issue's facts](../learnings/1785985363443-scoped-to-verify-the-bug-read-the-fix-s-open-revie.md)).

## Before Nudging a Stalled PR, Compute the Repo Base Rate and Read the Timeline Actor

A "PR has been awaiting review for N days" premise fails several ways that all look identical to a real stall, and the correct output is often "post nothing." Measured on shader-slang/slang#12179 (2026-08-04), where the conclusion flipped from "nudge warranted" to "post nothing" once each premise was checked [before nudging a stalled PR, compute the repo base rate and check the draft interval](../learnings/1785838727264-before-nudging-a-stalled-pr-compute-the-repo-base-.md). **(1) Age since creation is not reviewer-idle time — the draft interval resets the clock.** #12179 was framed as "awaiting review since 07-23, no review in 14 days," but the timeline shows `convert_to_draft` 07-23 then `ready_for_review` 07-27, so the true reviewer-idle window is 8 days, not 14; and "last comment 07-23" was true only of *issue-level* comments — the author left inline review replies on 07-27, so a PR is not silent because one comment stream is. Probe: `gh api "repos/O/R/issues/N/timeline?per_page=100" --jq '.[] | select(.event=="ready_for_review" or .event=="convert_to_draft" or .event=="review_dismissed")'`; the last `ready_for_review` starts the clock. **(2) "Idle for N days" means nothing without the repo's base rate.** On that repo **32 of 53** open non-draft PRs (60%) were idle ≥8 days — so 8 days is the *median condition*, not an outlier, and nudging the one PR you happen to be looking at is noise dressed as diligence (the same error shape as reading a 2-night CI failure cluster as a regression without the 35-run base rate). Compute it with two `gh api "repos/O/R/pulls?state=open&per_page=100"` calls (with and without the `select(.updated_at < "<cutoff>")` filter). **(3) Check whether the requested reviewer formally reviews at all** before asking "should a different reviewer be requested?" — `reviewed-by:<login>` in-repo can be 0 while `commenter:`/`author:` are in the hundreds (the account is active but doesn't submit formal reviews), and that login may sit on dozens of open review-requested PRs, making "hasn't reviewed in N days" a queue-wide assignment property, not a signal about your PR. **(4) A dismissed approval can be the AUTHOR's own doing** — read the `review_dismissed` actor, not just the state: an author who dismisses his own APPROVED review while reworking is *aware* re-review is needed, which is evidence *against* a nudge, not for one; reporting it as "a dismissed review from <reviewer>" invites the false reading that a reviewer rejected something. **(5) `mergeable_state=blocked` with green CI = missing approving review, nothing more** — don't report `blocked` as though something is broken. General rule: a nudge is justified by *deviation from this repo's norm*, never by an absolute day count — compute the norm first (two `gh api` calls) and be willing to let the answer be "post nothing."

## Coverage-Shape Scoping: a Single-Element Copy Exercises Only One Branch (lowerCopyLogical untyped-flavor fixes)

When reviewing a `lowerCopyLogical` "preserve untyped SPIR-V pointer flavor on derived addresses" fix (slang#13027 / #13022 — descriptor-heap `ConstantBuffer<T>` leaf-field reads emitting invalid `OpAccessChain` on an untyped base), watch the test-coverage SHAPE. `SomeStruct s = cb.arr[i];` copies a single array ELEMENT into a local: the `arr[i]` indexing lowers to a separate `getElementPtr` (retyped untyped by the pre-existing worklist pass), and the following `copyLogical` has a STRUCT source type, so `lowerCopyLogicalWithDestImpl` only enters the struct-field branch (`emitFieldAddressKeepingFlavor`). The array-element branch (`emitElementAddressKeepingFlavor`, reached via `else if (auto srcArrayType = as<IRArrayType>(srcValType))`) is NEVER exercised — including its ≤16-element unroll sub-path and the >16-element `emitLoopBlocks` sub-path (the latter newly reachable on SPIR-V 1.4+ once the extra `lowerCopyLogical(module, onlyUntypedPtrOperand=true)` call is added). To drive the array branch you need a WHOLESALE array copy from the descriptor-heap buffer (`struct WithArray { int vals[20]; }` then `int local[20] = cb.vals;`), ideally two entries (≤16 → unroll, >16 → loop). Second robustness nit: a `CHECK-NOT: OpTypePointer Uniform %int` pinned to `%int` passes only because the buffer's leaves are all `int` — a `float`/`uint` leaf or an intermediate `OpTypePointer Uniform %Inner_std140` slips past; tighten to `CHECK-NOT: OpTypePointer Uniform` (no type suffix), which still passes because descriptor-heap buffers only use `OpTypeUntypedPointerKHR` for Uniform. And the new `*KeepingFlavor` helpers are genuinely necessary (not redundant with `processFieldAddress`/`processGetElementPtrImpl`'s identical untyped-retype rule) because of ORDERING — `lowerCopyLogical` runs after both `processWorkList()` drains in `processModule()`, so the addresses it emits are never revisited by those retype passes; the complementary clarity ask is to document that ordering invariant at the call site (a different bar, not a contradiction) ([reviewing lowerCopyLogical untyped-flavor fixes: single-element copy only tests the struct-field branch](../learnings/1789177486273-reviewing-lowercopylogical-untyped-flavor-fixes-si.md)).
