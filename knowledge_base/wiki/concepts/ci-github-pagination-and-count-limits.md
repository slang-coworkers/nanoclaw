# GitHub Pagination & Count Limits — Silent Truncation, Size Caps & the 300-File Diff Cap

Every GitHub collection, search, and diff read has a cap, and none announces it: the array just ends, the count counts the wrong unit, the payload comes back empty-but-`200`, or the listing omits a live object. This page is the counting-and-completeness half of the GitHub/git instrument-limits family. Its sibling [GitHub API Error & Absence Semantics](ci-github-api-error-and-absence-semantics.md) covers the error-and-absence half (log bodies, summarizing tools, path-classed 401s, stale attempts). The measured cap table and endpoint-split defects live in [GitHub/git Instrument Limits — Caps, Silent Truncation & Endpoint Splits](../concepts/ci-github-instrument-limits.md).

## TL;DR
- **`gh api --paginate` (and `gh run list --limit 200`) can 401 `app_not_connected` on page 2+ under OneCLI and truncate silently**; any failure past item 100 reads GREEN. A transport fault, not an unlinked app: page explicitly with `?per_page=100&page=N`.
- **The silence is invocation-form dependent, and exit codes ARE usable**: bare `--paginate` and `--paginate --jq` exit 1; piping into `jq` (or `2>/dev/null`) launders it. Add `set -o pipefail`.
- **Reconcile on RAW page length, not your filtered count.** `/pulls`, `/issues`, `/commits` have no `total_count` to check against; their only terminator is a short page.
- **A pager that unwraps only a bare list or `items` returns `[]` on envelope endpoints** (`jobs`, `workflow_runs`, `workflows`), so a 50-job run reads "0 jobs". A list-endpoint 0 needs a `total_count` control; never overwrite a state file with an uncontrolled empty result.
- **GraphQL `totalCount` ignores the connection's filter arguments** (`since:` as well as `itemTypes:`): it is the all-time count. Test truncation by comparing `len(nodes)` with `first`, never `totalCount` with `len(nodes)`.
- **`actions/runs` pages through at most 1000 runs per query while reporting the true `total_count`**: slice `created=` into windows under 1000, check `fetched == total_count` per slice, and validate that ids are numeric (an error body on stdout becomes rows).
- **A repo-wide `actions/runs` `total_count: 0` is ambiguous** — the 1000-result cap, or deleted runs (slang 10-01 20:05Z to 10-03 10:07Z, ids 404). Re-slice and probe a known id: a cap clears in smaller slices, a deletion stays 0.
- **Not every proxy-shaped failure is the auth blip**: OneCLI 403s `Link: rel="next"` URLs `/repositories/<id>/...` (rewrite to `/repos/<owner>/<name>`); `gh pr list --limit 100 --json ...,mergeStateStatus` 502s (read it per PR). Read stderr before retrying.
- **`search/code` `total_count` counts MATCHES, not files** (`items[]` caps at 30/page) — and a count authenticates exactly one scope. Never cite a count from one scope as evidence about another.
- **`search/code` silently returns `total_count: 0` for files above ~384 KB** — biased toward the biggest files. Never use it for a denominator: search by ENTITY name, count locally with `git grep`.
- **`gh api .../contents/<path>` returns 200 with an EMPTY payload above the inline size cap** — an empty content field is not an absent string. Use `git show`.
- **The patch endpoint 406s above 300 files**, poisoning any grep-based scan of it — use `compare`, and pair every absence claim with two controls: a non-zero control on the artifact and a positive control on the pattern.
- **A `state=deleted` workflow is unlistable** — `GET /actions/workflows` omits it while still returning it by id; a `rows==total_count` bound-check passes on the incomplete set, certifying its own blind spot.
- **`review-requested:` includes team requests; `user-review-requested:` is direct only** (58 vs 32). Name the qualifier; read one person's direct requests from GraphQL `reviewRequests`. Settle counting conventions (does a 30-day CI expiry count as movement?) before parallel sweeps, or quote both readings.
- **The cheapest detector in this whole family: what would this output look like if the thing were absent? If the answer is "the same", it is not a measurement.**

## Pagination Truncates Silently — Reconcile, Don't Trust the Call

**`--paginate` under OneCLI fails on page 2 and later.** Through the OneCLI GitHub gateway, `gh api "<endpoint>?per_page=100" --paginate` fails past page 1 with an `app_not_connected` 401 body, while an explicit `?per_page=100&page=N` for the same page succeeds (`commits/<sha>/check-runs`, `total_count=131`: explicit `page=2` 6/6 OK, `--paginate` 4/4 FAIL, the second JSON document being the error). 6 of 54 PRs had more than 100 check-runs (up to 135), so a failing check on page 2 reads GREEN ([--paginate truncates at page 1](../learnings/1785766491651-gh-api-paginate-silently-truncates-at-page-1-under.md)). `gh run list --limit 200` paginates internally and hits the same 401. The fault is intermittent and transport-level — page 1 succeeds and a single-page retry works at once — so it is not an unlinked app and needs no `connect_url` ([page-2 401 via OneCLI](../learnings/1791244961881-gh-paginate-large-limit-can-401-app-not-connected-.md)). It also strikes mid-run: a `--paginate --jq` over slang's open `/pulls` returned 64 of 153 PRs with the error only on stderr, and the downstream `while read` loop counted 6 bot PRs with unsigned-identity commits instead of 12 ([partial results after a mid-run 401](../learnings/1791039860997-gh-api-paginate-can-return-partial-results-after-a.md)).

**Exit codes are usable; a pipe launders them.** The first write-up's "no non-zero exit" claim is wrong ([CORRECTION: invocation-form-dependent](../learnings/1785766871120-correction-to-the-paginate-truncation-note-the-sil.md)):

| form | exit | stdout |
|---|---|---|
| `gh api --paginate … --jq '…'` | **1** ✅ | 100 items **+ the error JSON as a data line** |
| `gh api --paginate … 2>/dev/null \| jq -s '…'` | **0** ❌ | silently truncated to 100 |
| same, plus `set -o pipefail` | **1** ✅ | truncated to 100 |
| bare `gh api --paginate` (no pipe) | **1** ✅ | — |

A pipeline reports jq's status (jq succeeded on the 100 items it got), and `.check_runs[]?` hides the bad shape a second time. Mitigations, most robust first: (1) reconcile against `total_count` (page 1 carries it); (2) keep the exit code (`--jq` or `set -o pipefail`), and still check shape, since `--jq` leaves the error on stdout; (3) `jq -e '.check_runs'` before extracting, keeping `?` for genuinely optional fields; (4) an explicit `?page=N` loop with per-page retry to a short page, failing loud on any failed page or count mismatch (`__PAGEFAIL__` / `__COUNT_MISMATCH__`), cross-checked against an independent figure such as the UI's PR count.

**Read stderr before retrying: two lookalikes are not the auth blip.** (a) For some endpoints (`/repos/shader-slang/slang/issues/events` past page ~8) GitHub's `Link: rel="next"` points at `https://api.github.com/repositories/<numeric-id>/...`, which OneCLI 403s (`app_not_connected`) while `/repos/<owner>/<name>/...` works in the same session. Page explicitly on the `/repos/...` path or rewrite the link (ids: slang 93882897, slangpy 912798934, slang-rhi 846627057) ([OneCLI 403s on /repositories/<id>/ pagination links](../learnings/1791449130477-onecli-proxy-403s-on-github-repositories-id-pagina.md)). (b) `gh pr list --state open --limit 100 --json number,isDraft,headRefOid,mergeStateStatus` on slang returns `HTTP 502 Bad Gateway (graphql)`; the list succeeds without `mergeStateStatus`, so read that field per PR with `gh pr view N --json statusCheckRollup,mergeStateStatus` ([gh pr list mergeStateStatus 502s at limit 100](../learnings/1791498547616-gh-pr-list-json-mergestatestatus-502s-at-limit-100.md)).

**`actions/runs` pages through at most 1000 runs while reporting the true `total_count`.** `GET /repos/O/R/actions/workflows/<wf>/runs?created=A..B` stops after pages 1-10 at `per_page=100`. slangpy's `ci-latest-slang.yml` runs once per slang PR via `repository_dispatch` (about 1,860 runs in 7 weeks), so one 7-week window returned only the newest 1000 and missed 3 of 5 flake occurrences. Slice `created=` into windows under 1000 and check `fetched == total_count` per slice. In the same sweep OneCLI page-2 error JSON and 502-body fragments landed on stdout as TSV rows, so page singly with retry, check ids are numeric, positive-control the grep on a known occurrence, and report "N found in M runs scanned / K errors" ([run listing caps at 1000](../learnings/1791404078372-github-actions-run-listing-caps-at-1000-per-query-.md)).

**A repo-wide `actions/runs` `total_count: 0` has two causes on shader-slang/slang.** *The cap:* a 24h `created=` window over the whole repo exceeds the 1000-result search cap and reports 0, so an all-run conclusion breakdown over it is partial, while `status=failure&created=...` stays under the cap and is complete ([merge-queue commit dates and the 1000-run cap](../learnings/1791448556917-ci-health-merge-queue-commit-dates-and-the-1000-ru.md)). *Deletion:* every run created 2026-10-01 20:05Z to 10-03 10:07Z is gone — `created=2026-10-02` returns 0 while neighbouring days carry 1–2.5k runs, and ids from the window (37029442825, 37044924072, 37045404089, 37055310934, all on `fix/issue-13391`) 404 on both `/actions/runs/<id>` and `/jobs`. Cause unknown (bulk deletion or retention purge). Such a 404 is not an auth fault and the run cannot be rerun or cancelled; re-trigger by un-drafting (`pull_request`) or a fresh dispatch (a bot `workflow_dispatch` is still throttled by `wait-for-human-priority`) ([Actions runs 10-01..10-03 deleted repo-wide](../learnings/1791454429233-shader-slang-slang-actions-runs-created-10-01-20-0.md)). To tell them apart, re-slice: a cap-induced 0 becomes real counts in smaller slices, a deletion stays 0; then probe a known id, where a 404 confirms deletion. A per-day probe (`gh api 'repos/<o>/<r>/actions/runs?created=<day>&per_page=1' --jq .total_count`) shows wider gaps: no slang runs 10-02→10-04 and 36 for 10-08→10-11 (normal ~940/day), so a failure streak counted back past 10-12 is unverifiable from the API ([MDL perf numbers are public; Actions API gaps](../learnings/1792226254592-mdl-perf-numbers-are-public-in-slang-compile-perf-.md)).

**Reconcile on RAW page length, not your filtered count.** `/pulls`, `/issues`, and `/commits` have no `total_count`; their only terminator is a short page. One call counting non-draft open PRs returned 54 — under 100, so nothing looked capped — but the truth was 76 non-draft of 233 open (raw pages 100, 100, 33). Filtering happens after truncation; the tell was a raw page length of exactly 100:

```bash
page=1
while :; do
  raw=$(gh api "repos/OWNER/REPO/pulls?state=open&per_page=100&page=$page")
  n=$(jq 'length' <<<"$raw")                                 # RAW length — the terminator
  jq -r '.[] | select(.draft==false) | .number' <<<"$raw"     # filtered output
  [ "$n" -lt 100 ] && break                                  # short page = done
  page=$((page+1))
done
```

This was missed while *verifying* someone else's number, hours after it had been written up; a wrong "correction" carries more authority than the original, so verification deserves the full method ([reconcile on RAW page length](../learnings/1785774447673-paginate-reconcile-on-raw-page-length-not-your-fil.md)).

**A home-grown pager can manufacture the zero.** The maintainer-sweep helper `pages()` (`reports/tmp10xx/gh/gh.py`) unwraps only a bare list or a dict with `items`. Envelope endpoints — `/actions/runs/{id}/jobs` (`{"total_count":N,"jobs":[...]}`), `workflow_runs`, `workflows` — come back `[]`, so a merge_group run with 50 jobs (48 success, 2 skipped) read "0 jobs". Read the named key (`get(...)['jobs']` with `per_page=100`) and compare its length with `total_count`; a 0 from a list endpoint is a finding only with that control beside it ([gh.py pages() returns 0 for the Actions jobs endpoint](../learnings/1792485327036-gh-py-pages-returns-0-for-actions-jobs-endpoint-fa.md)). A persisted false zero does more damage than a reported one: in the daily CI sweep (`reports/tmpMMDD/ci/`), `z1.py` calls `pages()` on `actions/runs`, gets `[]` with no error, and OVERWRITES `waiting.json` with empty lists, so the next day's left/arrived diff runs against nothing. Run `w1.py` after `z1.py`, or give `z1.py` the explicit loop `w1.py` uses ([z1.py wipes waiting.json](../learnings/1793003220665-ci-sweep-scripts-z1-py-pages-wipes-waiting-json-on.md)).

**The rule for every collection here:** ask "could this have come out short without me noticing?" and answer with a positive control (count vs server total, or loop to a short page). Same family as the GraphQL-401 phantom-green and a wake payload's `evicted: []` built from GraphQL during an outage (refuted by REST `actions/runs?event=merge_group`): a degraded transport yields a well-formed, plausible, empty-or-short answer.

## `total_count` Counts MATCHES, Not Files — and a Count Authenticates One Scope

`gh api search/code --jq '.total_count'` is a **match** count (a file with 3 hits contributes 3), and `items[]` caps at **30 per page** regardless of `per_page`, so `total_count` and the visible rows never correspond — the real defect behind a 932-vs-833 discrepancy that looked like a units mismatch. Count files by paginating and deduping paths:

```bash
gh api --paginate 'search/code?q=repo:OWNER/REPO+path:some/dir+"NEEDLE"&per_page=100' \
  --jq '.items[].path' | sort -u | wc -l
```

That returned **786**, matching a local `grep -rl` over the same scope; two agreeing instruments are worth the effort when a count goes to a maintainer. Rules from the same reconciliation ([total_count counts matches; one scope](../learnings/1785791779734-gh-api-search-code-total-count-counts-matches-not-.md)):
- **`--paginate` on `search/code` can inject error text into the data** (a rate-limit 403 body appended to stdout counted as six lines). Filter to the expected shape; a paginated total is a **floor** unless the sweep provably completed.
- **Pick ONE scope and never pair figures across scopes.** `/dev/null` under `docs/` = 788 files / 833 lines; under `docs/generated/tests` = 786 / 828. "786 files / 833 lines under `docs/`" pairs one scope's file count with the other's line count, and the wider scope added false positives (two shell scripts redirecting to `/dev/null`).
- **Two numbers that are arithmetically impossible together mean one instrument is defective — resolve it, don't bridge it.** N files with ≥1 match force ≥N lines, so 932 files / 833 lines cannot both be true; the contradiction is itself the evidence.
- **A mechanism that explains the DIRECTION of an error is not necessarily its cause.** A stale local snapshot fit the peer's inflated count perfectly, but that path did not exist in their container.

**Search qualifiers that look synonymous count different populations.** On shader-slang/slang, `review-requested:dshreiner-nv` also counts **team** requests (58) while `user-review-requested:dshreiner-nv` counts direct ones (32); name the qualifier in any trend report or day-over-day numbers are not comparable ([review-requested vs user-review-requested counts differ](../learnings/1791015886532-github-search-review-requested-vs-user-review-requ.md)). Neither is one person's direct requests (#14045 matched `review-requested:dshreiner-nv` with `reviewRequests` pdeayton-nv and team `dev`); read those from GraphQL `reviewRequests{requestedReviewer{... on User{login}}}`. The population also drifts with author habit: GitHub auto-requests dshreiner-nv on every new non-bot PR, and board sync (`github-actions`, default reviewer from the `default-reviewer` team since #13955) assigns a shepherd and removes dshreiner-nv only if the PR has no assignee yet. If the author self-assigns within 1–2 s (jkwak-work: #14052, #14065, #14097, #14098, #14104, slangpy #1253), dshreiner-nv stays requested; otherwise it is removed even when author == shepherd (#14051, #14068, #14113, slangpy #1252). So a "dshreiner-nv only" count grows with self-assigned PRs; test a PR by its `AssignedEvent` actor (author vs `github-actions`) and `ReviewRequestRemovedEvent` (hypothesis-grade: 12 PRs, workflow source unread) ([board sync skips PRs that already have an assignee](../learnings/1793436217668-slang-pr-board-sync-skips-prs-that-already-have-an.md)). Settle counting conventions before the run: a parked `falcor-ci` run expiring to `failure` at 30 days flips a PR's rollup PENDING→FAILURE with no timeline event or `updatedAt` change, and two parallel sweeps read it as "count 9" vs "held at 8". State the convention in the prompt, or quote both readings ([team requests; CI-expiry convention](../learnings/1793350061244-github-search-review-requested-user-also-matches-t.md)).

**A GraphQL connection's `totalCount` ignores the connection's own filter arguments.** `timelineItems(since: X, first: N){ totalCount nodes{...} }` filters `nodes` by `since` but returns the ALL-TIME `totalCount`, so "`totalCount > len(nodes)` ⇒ truncated" flags almost every old, busy item; test `len(nodes)` against N. It recurred on every sweep that used it: windowed lists peaked at 14 nodes against `first: 60` ([totalCount ignores since](../learnings/1792486262354-graphql-timelineitems-since-totalcount-ignores-sin.md)); slang#9808 reporting 443 ([rider](../learnings/1793003524466-fork-pr-rollup-failure-on-slang-is-usually-only-th.md)), again on the next sweep ([rider](../learnings/1793263634269-watch-list-gen-py-re-wrap-can-swallow-an-h2-headin.md)), then 445 with 0 nodes in the window ([check len(nodes) for truncation](../learnings/1793436330596-graphql-timelineitems-since-totalcount-ignores-sin.md)). The `itemTypes:` filter has the same defect (18 against an empty node list), recorded in [GitHub CLI/API instrument traps](../concepts/general-misc-c-github-cli-api-traps.md).

## Size Caps Return Empty Success — `search/code` and `contents`

**`search/code` returns `total_count: 0` for files above GitHub's ~384 KB index cap** — no error, no warning, no partial-results flag. A two-arm control on shader-slang/slang: arm A `"emitOpDecorate" filename:slang-emit-spirv.cpp` → **0** from the API, **45** from local `git grep -c`; arm B `IRInterpolationModeDecoration filename:slang-emit-metal.cpp` → **1** and **1**. Arm B proves the API and syntax work; `slang-emit-spirv.cpp` is **491,551 bytes**. The omission is biased toward the largest, emit-critical files an audit must cover. Check `stat -c %s <file>`; above ~384 KB assume it is not indexed ([search/code omits files over ~384KB](../learnings/1786079543367-github-search-code-silently-omits-files-over-384kb.md)).

Hence: **`search/code` cannot establish a denominator** — population counts, exhaustive enumerations, "N sites total", "nothing else does X". Counting reads of `IRInterpolationModeDecoration` for a PR's scoping argument, three instruments gave three wrong answers before local `git grep` gave 11: grepping `findDecoration<IRInterpolationModeDecoration>` → **6** (call-shape search missed four cast-shaped reads `(IRInterpolationModeDecoration*)dd`); reading six guessed files → **10**; `search/code` by entity name dropped the biggest file — worse, because it carried the authority of a systematic method. Both halves are required: **search by the ENTITY** (symbol name, not one syntax for touching it) **and count LOCALLY** in a fresh checkout. `git grep -c` counts matching lines, not occurrences (use `git grep -o <pat> | wc -l` when the number is load-bearing). If you must use `search/code`, pair each query with a **positive control** in the same file; a 0 on the control means the file isn't indexed.

**`gh api repos/<o>/<r>/contents/<path>?ref=<sha>` returns `200` with an empty (or `"none"`-encoded) content field above its inline size cap.** Nothing flags it, so a presence check (`--jq '.content' | base64 -d | grep 'ForceUnroll'` on a large `hlsl.meta.slang` at a PR head) fails toward **absent**, indistinguishable from a file lacking the string. Fetch the ref and read it locally (`git fetch <remote> <ref>`, then `git show <sha>:<path>`), or assert the payload is non-empty before trusting a negative ([contents empty above the size cap](../learnings/1786072032077-gh-api-contents-returns-empty-success-above-the-in.md)).

⇒ ⭐⭐⭐ **The cheapest detector in this family: what would this output look like if the thing were absent? If the answer is "the same", it is not a measurement.** It catches every case on this page — a size-capped empty payload, an unindexed file, a failed `cd` making the next `grep` a false zero, a too-narrow pattern, a capped or deduped listing, a probe whose flag never reaches the pass under test.

## Getting the Right Diff: the 300-File Patch Cap, and Two Controls on Every Absence Claim

GitHub's patch/diff media types **hard-fail at 300 files**, and `gh api` writes the error body into your output file:

```bash
gh api repos/O/R/pulls/N -H "Accept: application/vnd.github.v3.patch" > p.patch
grep -E '^\+' p.patch | grep -oiE '<email-regex>' | grep -c ''   # => 0   ("no PII!")
```

On a 391-file, +34524/−6378 PR that `0` came from a **337-byte** 406 body (`"the diff exceeded the maximum number of files (300)"`). **A scan of an error message looks identical to a clean scan**; only the byte count gave it away. The `compare` endpoint has no 300-file cap (`gh api repos/O/R/compare/<sha>^...<sha> -H "Accept: application/vnd.github.v3.diff"` → 3,194,375 bytes, `grep -cE '^\+'` = 34915, matching +34524 plus hunk headers); `pulls/N/files?per_page=100&page=K` enumerates paths, not line content.

**Pair every absence claim with two controls:** (1) a **non-zero control on the artifact** — `wc -c` / `grep -c ''` proving you scanned real content of the expected magnitude; (2) a **positive control on the pattern** — feed the regex a synthetic hit (`printf '+ contact [REDACTED-EMAIL] here\n' | grep -oiE …`). Without both, a 0 is an unfalsified guess. Print context for a secret-shaped hit before calling it a leak: `sk-[A-Za-z0-9_-]{20,}` fired twice on a filename in a `diff --git` header ([patch endpoint 406s above 300 files](../learnings/1785812823235-gh-patch-endpoint-406s-above-300-files-poisoning-g.md)).

## A `state=deleted` Workflow Is Unlistable — Enumeration Certifies Its Own Blind Spot

`GET /actions/workflows` omits `state=deleted` rows entirely, yet returns them by id. A rename mints a **new** workflow id and retires the old one to `deleted` (silently truncating its per-id run history), so the predecessor is reachable only by id or filename. The completeness check passes on the incomplete set: on slang the listing gave `total_count=82, rows=82, every row state=active` while deleted `287019999` (`Agentic Tests (Nightly)`) is live by id. To answer a rename question, fetch by id or by `.github/workflows/<path>.yml` directly ([deleted workflow is unlistable](../learnings/1786253658942-a-state-deleted-github-workflow-is-unlistable-zero.md), [bound-check passes anyway](../learnings/1786253873766-state-deleted-workflows-are-unlistable-and-the-row.md)).
