## TL;DR

Triaging a Slang compiler bug correctly means widening the reported trigger, matrixing targets with controls, and reading the *source* rather than docs or DeepWiki. Several concrete Slang facts and probe traps recur.

- **Same assert text ≠ same bug** — widen the trigger (each variation is one `sed`), matrix the targets, and control the non-firing cells.
- **A green test does not prove the capability premise** — read a submodule at the PINNED ref, not `main`.
- **A CLI flag's doc string tells you intent, not scope** — grep which emitter consumes it.
- **The declaration site gives the canonical name, not the accepted set** — check for alias tables and resolver normalization before calling a name wrong.
- **DeepWiki hallucinates plausible inference tables** — `RWTexture2D` format defaults to Unknown, not element-type-inferred.
- **A GPU test that FAILS instead of being IGNORED may be running on hardware that never advertised the feature** — enumerate device extensions.
- **A folded/all-literal cell proves nothing** — census the emitted instruction, source operands from a runtime buffer.
- **A monotonic registry needs a post-rebase UNIQUENESS check**, not just a conflict check.
- **Peel annotated tags with `^{}`** before comparing a tag to a submodule pin.
- **A green check depending on an external mutable input is not a durable green** — pin the ref.

## Widen the trigger, matrix the targets, control the non-firing cells

A shared internal-error string (`non-simple operand(s)!`) invites two opposite mistakes — closing a distinct bug as a dup, and treating a narrow title as the trigger. Two issues sharing the assert, file, and even the same written diagnosis showed **complementary opposite target profiles** (one fires on cuda+cpp only, the other on spirv only) ⇒ distinct bugs. **Widen the trigger before believing the title** (each variation is one `sed`: comparing two pointers with no `nullptr`, a merely-*containing*-empty pointee — plus genuine non-triggers proving the boundary). **Matrix the targets and control the non-firing cells** — other targets rejecting the shader with clean diagnostics reads like "only CUDA is broken," but a negative control (non-empty pointee) is rejected identically ⇒ those rejections are about the feature, not the bug. **Check "compiles fine" controls actually emitted the construct** (a pass can be DCE — read the emitted kernel). Regression claims need release-tag evidence, not `git log -S` (which bottoms out at a file rename). And search the artifact, not only the report's words (`empty struct in:title` surfaced the actual referent, 15 minutes earlier by the same reporter). See [Same assert text is not the same bug: widen the trigger and matrix the targets](../learnings/1786000135796-same-assert-text-is-not-the-same-bug-widen-the-tri.md).

Two coupled traps from a slangpy crash triage: **a one-axis sweep cannot attribute an asymmetry** (three attribute-tag arms all at CUDA saw `[CUDAKernel]` come back clean → "the trigger is `[shader("compute")]` specifically"; the 3×2 matrix refuted it — `[CUDAKernel]` segfaults on Vulkan, 3 of 4 tagged cells crash, the sampled cell was the lone exception). Narrowing *feels* like rigor, so nothing prompts a re-check — name the axes you held fixed and publish the cell you measured ("clean on CUDA"), not the rule you inferred. And **test a newly-found instrument defect against the anomaly before crediting it** — a real harness bug (`[CUDAKernel]` rejects non-void returns) was tempting to blame, but the anomaly *survived* the fix, so it wasn't the cause; crediting it would have retired a real target-dependent finding. Harness traps that manufacture a false "clean": bare `spy.Device(...)` omits the shader include path (dies before codegen), `defer_target_compilation` as a call kwarg is a phantom param — **a cell that "didn't crash" means nothing unless a control in the same run produced correct data.** See [A one-axis sweep cannot attribute an asymmetry, and a fresh instrument defect is a magnet for false blame](../learnings/1786030114471-a-one-axis-sweep-cannot-attribute-an-asymmetry-and.md).

## Read the source, the pinned ref, and the consuming emitter — not the docs

**A green test does not prove the capability premise.** A macOS Metal-4 CI passing was read as "the slang-rhi fix landed," but reading the submodule at its **pinned SHA** (not `main`, which had a stopgap) showed the OS-inference still live — the two repos were in opposite states on the same capability, and the green came from a slang-core change the verdict had argued against. A submodule claim must name a ref (read the gitlink, then read the file at that SHA); a passing test constrains the conjunction, not any one conjunct. (And a submodule clone is often shallow, so `git log -S` there yields a false origin — use the API for submodule provenance.) See [A green test does not prove the capability premise: check the submodule at the PINNED ref, not at main](../learnings/1785983712649-a-green-test-does-not-prove-the-capability-premise.md).

**A CLI flag's doc string tells you intent, not scope.** `-default-image-format-unknown` "forces Unknown instead of guessing" only on the via-GLSL path — two greps settle it (`getUseUnknownImageFormatAsDefault`: 1 in `slang-emit-glsl.cpp`, 0 in `slang-emit-spirv.cpp`), and on the default `-emit-spirv-directly` path a bare `RWTexture2D<float4>` is *already* Unknown, so the flag is a no-op there. Grep the accessor across consumers and state the path your claim applies to. Two second-order lessons: a wrong mechanism under correct advice still needs correcting (the user acts on the mechanism), and **don't inherit a subagent's hedge as a negative finding** ("my agent didn't verify `.Store`" — it's plainly declared at `hlsl.meta.slang:5244`). See [A CLI flag's description tells you intent, not scope — grep which emitter consumes it before asserting behaviour](../learnings/1786007073988-a-cli-flag-s-description-tells-you-intent-not-scop.md).

**The declaration site gives the canonical name, not the accepted set.** E39001's opt-out was "corrected" from `[allow("overlapping-bindings")]` to the declaration's `parameter-bindings-overlap` and logged as a caught defect — but *both work*: an alias table in a different file (`addAlias("overlappingBindings", ...)`) and resolver kebab↔camel normalization mean all four spellings resolve, and the checked-in test uses the hyphenated form. **A declaration establishes the canonical name; acceptance is decided by the lookup/resolution function** — a separate mechanism in a separate file. A real system usually accepts *more* spellings than it declares, so "that identifier looks made up" is a weak hypothesis; the cheapest disconfirming test when overruling a source is "is there a test using their value?" See [The declaration site gives the CANONICAL name, not the ACCEPTED SET — check for aliases and resolver normalization before calling a name wrong](../learnings/1786010457774-the-declaration-site-gives-the-canonical-name-not-.md).

**DeepWiki hallucinates plausible inference tables.** It claimed Slang infers the image format for `RWTexture2D<uint4>` (→ `Rgba32ui`); the source (`getSpvImageFormat()`) is a **declared-format passthrough** — with no attribute, all element types emit `Unknown` (dragging in `StorageImage*WithoutFormat` capabilities). The only real inference is from `unorm`/`snorm` modifiers. The tell was DeepWiki describing an inference table with no file:line for the table itself. For any claim that a compiler "infers" or "defaults," open the emit/check source and read the conditional. See [RWTexture2D image format defaults to Unknown regardless of element type (DeepWiki is wrong)](../learnings/1786006604858-rwtexture2d-image-format-defaults-to-unknown-regar.md).

## GPU capability probes: enumerate extensions, census emitted instructions

**A GPU test that FAILS instead of being IGNORED may be running on hardware that never advertised the feature.** `scalar-bf16.slang` returned wrong values on `-vk` because `VK_KHR_shader_bfloat16` is *not advertised by the driver* and the test doesn't gate on it, so it runs anyway and reports `FAILED` rather than `ignored`. An `ls` of ICD JSONs is a *config* probe; only `vkEnumerateDeviceExtensionProperties` + a **census** of names (not a `strcmp` against a hardcoded literal — the extension macro wasn't even in the installed header) is a *capability* probe. The one-line fix (`-capability spvBFloat16KHR -render-features bfloat16`) is a convention already in-tree — and it must be guarded (control: `-render-feature half`, which the device advertises, still runs, so the gate discriminates rather than masks). Two probe traps: a passing cell can be a *folded* cell (census the emitted instruction with `-target spirv-asm` before citing a pass); read back *exact bits* (`bit_cast<uint>`), not rounded values — that turned "some lanes wrong" into "IEEE binary16 widening, 4/4." See [A GPU test that FAILS instead of being IGNORED may be running on hardware that never advertised the feature — enumerate the device extensions before believing a wrong-value result](../learnings/1786023830257-a-gpu-test-that-fails-instead-of-being-ignored-may.md).

## Registries, tags, and external mutable inputs

**A monotonic registry needs a post-rebase UNIQUENESS check, not just a conflict check.** Any PR appending to a monotonically-assigned registry (`slang-ir-insts-stable-names.lua`, `CompilerOptionName`, `slang-diagnostics.lua`) can collide across a rebase, and a clean textual merge is actively dangerous — git resolves "both sides appended a line" without checking they picked *different numbers*. Run after every rebase: `grep -oE '= [0-9]+' <file> | ... | sort -n | uniq -d` (any output = duplicate ID). *The identity of a handle licenses nothing about the identity of what it points at* — re-derive at push. This is also why a **next-free ID check must scan OPEN PRs, not just master** — a code genuinely free at `origin/master` (with a passing positive control) was already claimed by an open PR; master is the set of *landed* claims, not all claims. Record *why* a non-obvious number was chosen. See [A monotonic registry needs a post-rebase UNIQUENESS check, not just a conflict check](../learnings/1786023171565-a-monotonic-registry-needs-a-post-rebase-uniquenes.md) and [A next-free diagnostic-code check must scan OPEN PRs, not just master](../learnings/1785983377640-a-next-free-diagnostic-code-check-must-scan-open-p.md).

**Peel annotated tags with `^{}` before comparing a tag to a submodule pin.** `ls-remote refs/tags/<t>` returns the tag *object* sha, not the commit — comparing that to a pin yields a confident, plausible-looking mismatch that reads as "the fix is wrong" when it's correct. `refs/tags/v2.1.7^{}` is the commit. Also: grep the sibling `.gitmodules` entries before proposing an edit (the tag-as-branch pattern was already established), and attribute one hop deeper than the trigger (the upstream default-branch rename was the *trigger*; the *defect* was a pin landed without a `branch =` line). **The thing that changed is not always the thing that's wrong.** See [Peel annotated tags with ^{} before comparing a tag to a submodule pin](../learnings/1785997419623-peel-annotated-tags-with-before-comparing-a-tag-to.md).

**A green check depending on an external mutable input is not a durable green.** A submodule pin-check passed while microsoft/mimalloc's default branch was `main`, then failed when they moved to `main3` — nothing on our side changed. When a check resolves a remote default branch, `latest`, a floating tag, or an unpinned action, the *absence* of an explicit override is a latent failure, not a durable pass; pin the ref explicitly even when it currently passes, and record *what it resolved to* in verification notes. A tag in `branch =` is the stronger fix (immutable) than a branch. See [A green check that depends on an external mutable input is not a durable green](../learnings/1786005179247-a-green-check-that-depends-on-an-external-mutable-.md).

## Precompilation over-fire, and the API-vs-CLI path

A test forcing `SLANG_RUN_SPIRV_VALIDATION="0"` around a library precompile was masking an upstream over-fire: `precompileForTarget` sets `EmbedDownstreamIR` but `shouldRunSPIRVValidation` never consults it, so with ambient validation on, *any* precompile-for-target is falsely rejected. **Treat a test workaround as a finding about the system until proven otherwise** — state which artifact the code believed it was operating on. The scope-settling method that beat all hand-reasoning: `git show $(git merge-base <pr> master):<file> | sed -n '/fn/,/^}/p'` showed the function byte-identical at merge-base and head ⇒ pre-existing, don't bundle. An **API-path repro outranks a CLI-path repro** (CLI-only is dismissible as a flag footgun). See [A test workaround can be masking an upstream over-fire — ask which artifact the code believed it was validating](../learnings/1785997176542-a-test-workaround-can-be-masking-an-upstream-over-.md).

This has a companion about *which path a green exercised*: **a passing test tells you the path worked, not which path ran.** Two tests passing with validation on "proved safe" flag-drops — but the CLI path (which `slang-test` drives, wrapped by an exception handler) exits 255 gracefully while the public API path (`precompileForTarget`, unwrapped) aborts with exit 134; had the wrapping gone the other way the flag-drops would be unsafe and the evidence would read identically. After a pass licenses a safety claim, name the entry point/path it exercised and confirm it's the one your claim covers. This is distinct from a vacuous test (which can't fail at all) — the test *did* fail on revert, so falsifiability was proven; the gap is one level up. See [A passing test tells you the path worked, not which path ran — right answer, unestablished warrant](../learnings/1786002689464-a-passing-test-tells-you-the-path-worked-not-which.md).
