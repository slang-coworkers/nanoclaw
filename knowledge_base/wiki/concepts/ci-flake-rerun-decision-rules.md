# CI Flake Triage — Rerun Decision Rules

When `gh run rerun --failed` is the right move and when it burns the budget for nothing. The mechanics of `--failed` (it never re-runs successful upstream builds), the permanent futility once a build artifact expires, and the cluster/fleet-wide/degrading-runner patterns that mean *escalate, do not rerun*. Which specific runner a rerun can land on is [runner pools and infrastructure](ci-flake-runner-pools-and-infrastructure.md); whether a red job is a flake at all is [classification and known signatures](ci-flake-known-signatures-and-classification.md).

## TL;DR

- **`gh run rerun --failed` re-runs failed jobs but NOT their successful upstream dependencies.** For an artifact-consuming test job whose build was marked success, `download-artifact@v4` only sees same-attempt artifacts — so a `--failed` rerun fails "Artifact not found" every attempt. Recovery: maintainer pushes a new commit, or `gh run rerun <id>` (whole workflow).
- **`--failed` turns PERMANENTLY futile once the build artifact expires** (~5–7 day retention; but `slang-tests-*` build artifacts expire after just **1 day**, so this can strike a still-open, still-relevant run — a later attempt's signature flips to "Artifact not found", not your code). Before rerunning an old run, check `.created_at` + `artifacts?per_page=100` for `expired`. If expired ⇒ author rebase/re-push, logged `left`/`not-rerunnable` — distinct from the rerunnable "This workflow is already running" defer.
- **Same deterministic error on two or more unrelated PRs = base-branch break, not a flake — do not rerun.** Rerunning re-hits the same broken base.
- **For a SlangPy flake, never recommend a retry mechanism as the fix** (retry wrappers, `pytest-rerunfailures`, job-level reruns) — maintainers closed slangpy#829/#1123 because a pass-on-retry hides races, order-dependent device state and bad caching. Recommend diagnostics, a reproduction and a root cause.
- **Standing escalations skip reruns entirely** (runner starvation, materialx Docker-pull loop, nvrgfx/SlangPy CUDA-OOM) — the fix is operator-side.
- **Fleet-wide deterministic precondition failure ⇒ reruns MASK, escalate.** `--failed` only helps when the failure is probabilistic (can land on a healthy runner). `cuda>=13.0` starts as one unhealthy runner (one rerun OK) but can spread fleet-wide; once fleet-wide, stop rerunning and headline the dominant root-cause.
- **One job failing in DIFFERENT ways across unrelated PRs (OOM → SIGSEGV → hang → disk-full), including on a docs-only PR, is a degrading runner, not a test flake** — do NOT hold it behind a "wait for N repeated-*identical* failures" gate (that gate is the signal for a flaky *test*). Track a runner-health issue and keep rerunning only as a stopgap.
- **Per-VM SIGILL / LLVM-JIT-path flake on a GCP `linux-build` job ⇒ check AVX-512 mis-report FIRST.** Some pool VMs advertise AVX-512 the host can't execute; slang-llvm's JIT then faults. Mitigation: `export SLANG_DISABLE_AVX512=1`.
- **The priority-yield gate blocks BOTH rerun and re-dispatch on bot/draft PRs.** While `wait-for-human-priority`/`falcor-build-approval-gate` holds a bot-PR run in `status: waiting`/`running`, `gh run rerun --failed` is refused ("This workflow is already running") and a fresh `gh workflow run ci.yml` by the bot yields + SKIPS the whole matrix (it never re-rolls the flaky test). On a DRAFT bot PR the dispatched run sits in `waiting` indefinitely (an environment-protection rule). Do NOT loop re-dispatching — resolution is a human approving priority (marking the PR ready / starting CI) or aging (~≤8h); `retry-yielded-bot-ci` never reruns a run still `waiting` (it treats `waiting` as active) and approving the Falcor gate doesn't help once build/test were skipped; report up and rely on the `ci_failed` webhook to re-wake, don't set an 8h poll.
- **A rerun you start fires no second `ci_failed` webhook.** After `gh run rerun --failed`, track the attempt yourself (a background `until` loop on `jobs?filter=all`) or tell the parent you are not tracking it. Before accepting "infra flake", check whether other PRs passed the same job in the same window.
- **A yielded bot run older than 16h is outside `retry-yielded-bot-ci`'s lookback and is never auto-retried.** A `ci_failed` that arrives exactly 30 days after a bot draft dispatch is GitHub auto-failing the never-approved `falcor-ci` deployment (`falcor-build-approval-gate`, 0 steps, every build/test job skipped), not code. Don't hunt for a bug and never `gh run rerun`: on a draft any new run yields and queues another approval; the real matrix runs when the PR is marked ready. The expired run keeps its month-old `created_at`, so a daily `status=failure&created>=` count misses it; diff successive `status=waiting` lists instead.

## Rerun Decision Rules

**`--failed` never re-runs a successful build.** `gh run rerun --failed` re-runs failed jobs but not their successful upstream dependencies, and `download-artifact@v4` by default sees only artifacts uploaded in the same attempt. So when the build job is marked success, a `--failed` rerun of the test job fails "Artifact not found" every attempt and burns the whole budget ([Slang CI: `gh run rerun --failed` cannot fix 'Artifact not found' on artifact-consuming jobs](../learnings/1780207481552-slang-ci-rerun-failed-cannot-fix-cross-attempt-art.md)). Recovery: a maintainer pushes a new commit (fresh full run), or `gh run rerun <id>` (no `--failed`) reruns the whole workflow.

**Expired artifacts make it permanent.** Artifacts keep ~5–7 days on this repo, so a `--failed` rerun of a `test-*` job on an old run (head not re-pushed) can never go green. Before rerunning an old run, check `gh api repos/OWNER/REPO/actions/runs/<id> -q '.created_at'` and `gh api "repos/OWNER/REPO/actions/runs/<id>/artifacts?per_page=100" -q '.artifacts[]|select(.name|test("<pattern>"))|"\(.name) expired=\(.expired) expires_at=\(.expires_at)"'`. If expired, don't rerun: the disposition is "needs AUTHOR rebase/re-push", logged `left`/`not-rerunnable`, which differs from the "This workflow is already running" defer (rerunnable once the run completes) ([Rerun --failed is futile on runs past the artifact-retention window](../learnings/1784297413443-rerun-failed-is-futile-on-runs-past-the-artifact-r.md)). On a rerun aged run the tell is a test job that finishes in seconds (e.g. 39s) and dies at setup, with a `download-artifact` fetch plus git-submodule `could not lock config file .git/modules/external/*/config` errors and no test lines at all (a real failure runs for minutes and prints `failed test: '...'`). Only a full rebuilding run is trustworthy. Don't rebase-chase an unreviewed PR just to clear stale-artifact reds, because that churn re-arms hand-picked-diagnostic-code collisions; rebase when a reviewer engages ([rerun --failed on an aged run fails on expired build artifacts, not your code](../learnings/1789274038560-gh-run-rerun-failed-on-an-aged-ci-run-fails-on-exp.md)). `slang-tests-*` artifacts (e.g. `slang-tests-linux-x86_64-gcc-debug`) expire after **1 day**, so this bites still-open runs too. On PR #13105 three attempts failed with a real Vulkan VUID regression; a 4th attempt ~2 days later failed with `Artifact not found for name: slang-tests-linux-x86_64-gcc-debug` plus a GPU health-check failure, because the artifact had expired and `--failed` never re-runs the succeeded build. Before calling a "device/GPU/artifact" failure rerun-worthy, check `.../artifacts` for `expired:true` on `slang-tests-*`; if the run is >~24h old and says "Artifact not found", decline. Only a fresh push, a full `gh run rerun <id>`, or a rerun of the job that *produces* the artifact regenerates it. For `test-falcor`, a `--job` rerun dies in ~19s at `Run external CI` ("Slang artifact … is unavailable … not triggering Falcor", no GitLab pipeline); rerun `build-windows-release-cl-x86_64-gpu-falcor / build` instead (details on [red CI triage](ci-tooling-f0909b1-red-ci-triage.md)) ([test-falcor --job rerun fails in 19s once the slang-tests-* artifact is gone](../learnings/1793081639779-test-falcor-job-rerun-fails-in-19s-once-the-run-s-.md)). This mode is distinct from GPU device-lost/TDR and from merge-group-log expiry ([gh run rerun --failed is a dead end once the test-binaries artifact expires (1-day retention)](../learnings/1789740363892-gh-run-rerun-failed-is-a-dead-end-once-the-test-bi.md)).

**The priority-yield gate makes reruns and re-dispatch futile on bot/draft PRs.** Bot-authored PR runs include a `falcor-build-approval-gate` / `wait-for-human-priority` job that yields runner priority to human PRs; while it is unresolved the run stays `waiting`/`running` even after individual jobs finish. (1) `gh run rerun --failed <id>` is refused ("This workflow is already running" / "job cannot be rerun") until the run completes ([rerun --failed blocked while the priority-yield gate holds the run](../learnings/1789265883183-gh-run-rerun-failed-is-blocked-while-a-bot-pr-ci-r.md)). (2) A fresh `gh workflow run ci.yml --ref <branch>` by the bot is marked `IS_THROTTLED_BOT`, so `wait-for-human-priority` fails and SKIPS the whole build/test matrix; the flaky test never re-runs and the original FAILURE check stays on the head ([a bot workflow_dispatch re-trigger yields and skips the matrix](../learnings/1789190665143-slang-ci-a-bot-workflow-dispatch-re-trigger-yields.md)). (3) On a DRAFT bot PR the dispatched run sits `waiting` on an environment protection rule (seen for ~12 days), and each re-dispatch queues another gated run ([draft bot-PR workflow_dispatch stays 'waiting' — re-dispatch is futile](../learnings/1789265530355-draft-bot-pr-ci-stays-in-github-actions-waiting-pr.md)). The run advances only when a human approves priority or aging force-runs it (~≤8h). `retry-yielded-bot-ci` does not rescue a run still `waiting`: `extras/ci/retry-yielded-bot-ci.py` reruns only completed runs and returns early while any run is active, and `ACTIVE_STATUSES` includes `waiting` (`extras/ci/ci_priority_common.py:29`). Approving the Falcor gate doesn't help either, since build/test were already skipped. So never promise "retry-yielded-bot-ci will rerun it" and don't re-dispatch; Windows CI needs a maintainer to mark the PR ready or start CI (corrected by slang-triager on PR #13867, [a priority-yielded draft dispatch is not rerun while it sits 'waiting'](../learnings/1793105473572-a-priority-yielded-bot-ci-yml-dispatch-on-a-draft-.md)).

**The 30-day approval expiry.** For completed yielded runs the script looks back only `--lookback-hours 16`, so an older yielded run is never auto-retried. A run left in the falcor-ci environment approval queue stays "in progress" for 30 days; then GitHub auto-fails the pending deployment, and a `github.ci_failed` webhook arrives a month after the push. Signature: the failed checks are only `wait-for-human-priority` + `check-ci` + `falcor-build-approval-gate` (`environment: falcor-ci`, runs only an `echo`, 0 steps, log BlobNotFound/404, empty `runner_name`), started→completed is exactly 30 days, and every build/test job is `skipped` (PR #13130 run 35130395308, 2026-09-16 → 10-16; #13252 run 35965355338, 09-24 → 10-24). No code ran, so don't hunt for a bug, reproduce or push a fix ([a yielded bot CI run older than 16h is never auto-retried](../learnings/1792045779452-a-yielded-bot-ci-run-older-than-16h-is-never-auto-.md), [bot CI run 'failure' after exactly 30 days = expired falcor-ci environment approval](../learnings/1792173072753-bot-ci-run-failure-after-exactly-30-days-expired-f.md), [late ci_failed on a draft = 30-day approval-gate timeout](../learnings/1792823927170-late-ci-failed-webhook-on-a-draft-pr-30-day-approv.md)). Never `gh run rerun` it. Check `mergeable` (a month-old PR usually conflicts) and merge master if needed. A push or `gh workflow run ci.yml --ref <branch>` gives a fresh run inside the 16h window, but on a draft it yields again and queues another approval nobody grants, so the real matrix runs only when the PR is marked ready. The scripts confirm why nothing retries it (2026-10-20): the pending run stays `waiting`, the retry script lists only `completed` runs and counts `waiting` as active, and the 12h `--max-yield-hours` escalation fires only when a run starts or restarts (#13130 stayed at attempt=1 for 30 days; 0 of 96 bot dispatches in 7 days reached build/test). The full deadlock is on [draft-PR CI](ci-b-draft-pr-ci-and-conditional-claims.md) ([bot dispatch runs deadlock behind the falcor-ci gate](../learnings/1792519787823-slang-ci-bot-workflow-dispatch-runs-deadlock-behin.md)). It differs from GitHub's rule that a run created over a month ago can't be rerun (on [red CI triage](ci-tooling-f0909b1-red-ci-triage.md)), though both make a rerun wrong. The expired run keeps its month-old `created_at` (`updated_at` = `created_at` + 30 days), so a daily `actions/runs?status=failure&created>=<window start>` query never lists it. To count expiries, diff yesterday's `status=waiting` list against today's and fetch each run that left; on 2026-10-24, 8 of the 14 runs that left slang's waiting set were 30-day expiries (6 bot dispatches, 2 human fork runs) ([30-day waiting-run expiry is invisible to a created-window failure query](../learnings/1792830160449-github-actions-30-day-waiting-run-expiry-shows-as-.md)).

**Disposition for a yielded run:** if the ONLY failing checks are `wait-for-human-priority` + `check-ci`, do nothing; otherwise report the infra verdict up and rely on the `github.ci_failed` webhook to re-wake once the run is terminal (`gh pr ready` is operator-gated, so you can't clear the gate yourself). That webhook covers only the run's first terminal state; a rerun you start is yours to watch (below).

**A wedged gate blocks single-job reruns on any PR.** `gh run rerun --job` fails with a bare "job cannot be rerun" (no detail even with `--debug`); `gh api -X POST repos/<o>/<r>/actions/jobs/<job-id>/rerun` surfaces the real 403 `{"message":"The workflow run containing this job is already running"}`. A run stays in progress while ANY job is `WAITING` (including `falcor-build-approval-gate` on human approval), so a genuine intermittent failure in the same run (e.g. `test-windows-debug-cl-x86_64-gpu-dx` "runner lost communication") can't be rerun until the gate resolves. Record the intermittent classification but not `result:"reran"`; note `blocked_reason: "rerun attempted, blocked by GH 403 (run still open pending gate)"` so it is distinguishable from a declined rerun. Worth surfacing to a maintainer: a stuck gate blocks flake remediation for every job in that run, not just merges ([GitHub Actions refuses to rerun a single job while its parent run is still in progress](../learnings/1789885681009-github-actions-refuses-to-rerun-a-single-job-while.md)).

**The wedge is also mis-diagnosed as "too old to rerun".** On PR #12249 a tracker note blamed a GitHub rerun-age limit for a stuck run (created 2026-08-28). The live cause was `falcor-build-approval-gate` still `status:"waiting"`, which pins the run's top-level `status` non-`completed`, and GitHub rejects `gh run rerun` on any non-completed run regardless of age. Before writing off a rerun as too old, check `.jobs[] | {name,status,conclusion}` (`gh api repos/<o>/<r>/actions/runs/<id>/jobs`) for a lingering `waiting`/`requested` job; the true age limit is the expired-artifact case, disposition author rebase/re-push ([wedge-blocked run mis-diagnosed as "too old to rerun" — check for a lingering waiting job first](../learnings/1790244771159-wedge-blocked-run-misdiagnosed-as-too-old-to-rerun.md)).

**Track your own rerun, and test the flake claim against the same window.** On #13880 a failed `test-falcor` job was rerun with `--failed` in the expectation that the webhook would report back; attempt 2 failed, no second `github.ci_failed` arrived, and the supervisor found it ~8 hours later. After any rerun, watch it with a background `until` loop on `gh api repos/<o>/<r>/actions/runs/<id>/jobs?filter=all --jq '.jobs[] | select(.name=="<job>") | .conclusion'`, or tell the parent you aren't tracking it. Before accepting "infra flake", check the same window: another frontend PR (#13889) passed attempt 2 of the same job while ours failed. `jobs?filter=all` returns every attempt with `run_attempt`, `started_at` and `completed_at`, enough to line the windows up ([a rerun does not produce a second ci_failed webhook](../learnings/1792801310656-a-gh-run-rerun-failed-does-not-produce-a-second-ci.md)).

**Cluster detection.** Before rerunning, check whether the same error signature appears on two or more unrelated PRs. A deterministic error across unrelated PRs is a base-branch break, and a rerun re-hits the same broken base ([CI babysitter: identical build error across unrelated PRs = base-branch break, not flake](../learnings/1780790667002-ci-babysitter-identical-build-error-across-unrelat.md)). (Windows disk-space failures cluster too, several PRs failing one Windows job within ~6 seconds, but the culprit is one sick runner; see [runner pools and infrastructure](ci-flake-runner-pools-and-infrastructure.md).)

**Standing escalations skip reruns.** When a persistent infra problem is already routed to an owner (runner starvation: job CANCELLED after "awaited a runner for 24h0m0s"; materialx Docker-pull loop; nvrgfx/SlangPy CUDA-OOM), don't rerun: the fix is operator-side ([Slang CI babysitter: skip reruns on standing-escalated infra failures](../learnings/1781195910201-slang-ci-babysitter-skip-reruns-on-standing-escala.md)).

**The sweep's per-PR reason string is not a complete inventory.** When one PR has two failing jobs that are each *don't rerun* for different reasons (e.g. the `#13024` spvdb do-not-rerun exclusion and a `SlangPy Tests` E38100 `MatrixLayoutMode` staleness regression from a core module predating a #12986-class merge), the one-line log can name only the first. Nothing is wrongly rerun, but a later audit can't trust the string as an enumeration: cross-check `gh pr checks <n>`, and consider listing all failing job names even when every verdict is "leave it" ([the terse sweep log can omit a second co-occurring 'don't rerun' failure without misclassifying it](../learnings/1789280676488-ci-babysitter-terse-sweep-log-can-omit-a-second-co.md)).

**Fleet-wide deterministic failures.** `--failed` helps only when the failure is probabilistic (can land on a healthy runner). When every runner shares a broken precondition (e.g. a fleet-wide `cuda>=13.0` driver mismatch), reruns mask the problem: escalate to the operator and headline the dominant root cause so maintainers stop rerunning into a deterministic wall ([When CI infra failure goes fleet-wide, reruns mask — escalate instead](../learnings/1782231415029-when-ci-infra-failure-goes-fleet-wide-reruns-mask-.md), [CI babysitter: headline the dominant root-cause when maintainers rerun into a deterministic wall](../learnings/1782248669315-ci-babysitter-headline-the-dominant-root-cause-whe.md)). The CUDA ≥13.0 container failure (`nvidia-container-cli: requirement error: unsatisfied condition: cuda>=13.0`) starts as one unhealthy runner (one rerun OK) but can spread fleet-wide; then stop rerunning ([cuda>=13.0 GPU CI runner driver-mismatch signature (shader-slang)](../learnings/1782226877304-cuda-13-0-gpu-ci-runner-driver-mismatch-signature-.md)).

**Multi-mode spread = degrading runner, not test flake.** When one binary-independent job fails in *different* ways (OOM-abort → SIGSEGV → hang/timeout → disk-full) across distinct PRs, including ones that can't code-cause it (a docs-only PR crashing test-slang), the spread is evidence of a runner-health issue. Don't hold it behind a "wait for N repeated-identical failures" gate: identical repeats signal a flaky *test*, while a resource-starved runner shows exactly this spread (OOM when alloc fails, SIGSEGV on a corrupted partial alloc, hang when thrashing, disk-full when `/tmp` fills). Track a runner-health issue naming the runner and fix candidates (memory headroom, `-server-count`, `/tmp`), fold in sibling resource-pressure failures, and keep rerunning as the stopgap ([Multi-mode CI failure spread = degrading-runner issue, not test-flake](../learnings/1783354616229-multi-mode-ci-failure-spread-degrading-runner-issu.md)).

**GCP linux-build AVX-512 mis-report → SIGILL: check it first.** A per-VM, low-frequency flake on a CPU/LLVM path in a GCP `linux-build`-pool job (SIGILL, or a downstream symptom like the ASan "runtime does not come first" abort) is a recurring env class: some VMs advertise AVX-512 their host can't execute, and slang-llvm's JIT faults on it. Mitigation: `export SLANG_DISABLE_AVX512=1` in the test step (PR #11974 added it to `ci-slang-sanitizer.yml`). Assert the class ("per-VM env trigger") confidently but label the mechanism a HYPOTHESIS, since job logs 410 (Gone) after ~7 days and the decisive log is usually gone ([GCP linux-build runners mis-report AVX-512 → SIGILL in slang-llvm JIT (recurring env class)](../learnings/1783443514224-gcp-linux-build-runners-mis-report-avx-512-sigill-.md)).

**Read the tracker's verdict before re-classifying from a fresh log.** One `gh run view --log-failed` can make a failure look like a standalone regression when `rerun-tracker.json` already holds a terminal verdict with richer context. On the 2026-09-21 20:11Z sweep #13078's SlangPy Tests failure read as a fresh code bug, but `rerun-tracker.json["13078"]` had `last_verdict:"out-of-scope"` from the prior day, recording a CONFLICTING/DIRTY merge state plus base-skew vs #12986. `sweeplib.heartbeat_due()` treats `resolved`/`out-of-scope` as terminal, so leave such PRs alone rather than log a shallower competing verdict ([check rerun-tracker.json's existing verdict before re-deriving a fresh classification from raw CI logs](../learnings/1790021540897-check-rerun-tracker-json-s-existing-verdict-before.md)).

## SlangPy: test retries are not a remedy — reproduce and root-cause

Recommending a *retry mechanism* as the fix for a SlangPy flake is a separate question from clicking rerun, and SlangPy's maintainers answered it on 2026-09-02: shader-slang/slangpy#829 (a Slang-style two-stage `pytest -n auto` → `-n 0 --lf` retry in `tools/ci.py`) was closed, and our draft PR #1123 implementing it was closed unmerged. ccummingsNV: a retry is safe only if parallel-run contention that real users never hit is the *only* cause of sporadic failures, while a pass-on-retry can hide race conditions, test-order-dependent state left by device recycling, and incorrect internal caching ("If we genuinely do have tests that fail when running parallel, let's reproduce that and work out what's failing"). jkiviluoto-nv added that the original Slang approach "has never worked well". So SlangPy flake triage recommends better diagnostics (e.g. inline abort signatures), a reproduction and a root cause, never retry wrappers, `pytest-rerunfailures` or job-level reruns. Older memos proposing a retry (e.g. #994 option C) are superseded ([SlangPy maintainers reject CI test retries — triage flakes toward reproduce-and-root-cause](../learnings/1790857338311-slangpy-maintainers-reject-ci-test-retries-triage-.md)).
