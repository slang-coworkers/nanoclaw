# CI Flake Triage — Rerun Decision Rules

When `gh run rerun --failed` is the right move and when it burns the budget for nothing. The mechanics of `--failed` (it never re-runs successful upstream builds), the permanent futility once a build artifact expires, and the cluster/fleet-wide/degrading-runner patterns that mean *escalate, do not rerun*. Which specific runner a rerun can land on is [runner pools and infrastructure](ci-flake-runner-pools-and-infrastructure.md); whether a red job is a flake at all is [classification and known signatures](ci-flake-known-signatures-and-classification.md).

## TL;DR

- **`gh run rerun --failed` re-runs failed jobs but NOT their successful upstream dependencies.** For an artifact-consuming test job whose build was marked success, `download-artifact@v4` only sees same-attempt artifacts — so a `--failed` rerun fails "Artifact not found" every attempt. Recovery: maintainer pushes a new commit, or `gh run rerun <id>` (whole workflow).
- **`--failed` turns PERMANENTLY futile once the build artifact expires** (~5–7 day retention). Before rerunning an old run, check `.created_at` + `artifacts?per_page=100` for `expired`. If expired ⇒ author rebase/re-push, logged `left`/`not-rerunnable` — distinct from the rerunnable "This workflow is already running" defer.
- **Same deterministic error on two or more unrelated PRs = base-branch break, not a flake — do not rerun.** Rerunning re-hits the same broken base.
- **Standing escalations skip reruns entirely** (runner starvation, materialx Docker-pull loop, nvrgfx/SlangPy CUDA-OOM) — the fix is operator-side.
- **Fleet-wide deterministic precondition failure ⇒ reruns MASK, escalate.** `--failed` only helps when the failure is probabilistic (can land on a healthy runner). `cuda>=13.0` starts as one unhealthy runner (one rerun OK) but can spread fleet-wide; once fleet-wide, stop rerunning and headline the dominant root-cause.
- **One job failing in DIFFERENT ways across unrelated PRs (OOM → SIGSEGV → hang → disk-full), including on a docs-only PR, is a degrading runner, not a test flake** — do NOT hold it behind a "wait for N repeated-*identical* failures" gate (that gate is the signal for a flaky *test*). Track a runner-health issue and keep rerunning only as a stopgap.
- **Per-VM SIGILL / LLVM-JIT-path flake on a GCP `linux-build` job ⇒ check AVX-512 mis-report FIRST.** Some pool VMs advertise AVX-512 the host can't execute; slang-llvm's JIT then faults. Mitigation: `export SLANG_DISABLE_AVX512=1`.

## Rerun Decision Rules

**Core rule:** `gh run rerun --failed` re-runs failed jobs but NOT their successful upstream dependencies. For artifact-consuming test jobs, `download-artifact@v4` by default only sees artifacts uploaded in the same attempt — so if the build job is marked success, a `--failed` rerun of only the test job will fail with "Artifact not found" every attempt, burning the entire rerun budget ([Slang CI: `gh run rerun --failed` cannot fix 'Artifact not found' on artifact-consuming jobs](../learnings/1780207481552-slang-ci-rerun-failed-cannot-fix-cross-attempt-art.md)). Recovery requires a maintainer to push a new commit (fresh full run) or `gh run rerun <id>` (no `--failed`) to rerun the whole workflow.

The same rule turns *permanent* once the build artifact **expires**. Artifacts have a ~5–7 day retention window on this repo, and a `--failed` rerun of a `test-*` job on an OLD run (created days ago, head not re-pushed) can never reach green — the test job dies at `actions/download-artifact` with "Artifact not found" every attempt because the build artifact it depends on is gone and `--failed` never re-runs the build. Before rerunning an old run, check its age + artifact state: `gh api repos/OWNER/REPO/actions/runs/<id> -q '.created_at'` and `gh api "repos/OWNER/REPO/actions/runs/<id>/artifacts?per_page=100" -q '.artifacts[]|select(.name|test("<pattern>"))|"\(.name) expired=\(.expired) expires_at=\(.expires_at)"'`. If expired, do NOT rerun — the disposition is "needs AUTHOR rebase/re-push to regenerate the build + trigger a fresh full run," logged as `left`/`not-rerunnable`. Distinguish this from the "This workflow is already running" defer (rerunnable once the run completes) — the expired-artifact case is *permanently* unrerunnable on that run ([Rerun --failed is futile on runs past the artifact-retention window](../learnings/1784297413443-rerun-failed-is-futile-on-runs-past-the-artifact-r.md)).

**Cluster detection:** Before rerunning anything, check whether the same error signature appears on two or more unrelated PRs. Same deterministic error across unrelated PRs = base-branch break, not a flake. Do NOT rerun — rerunning re-hits the same broken base and wastes the budget ([CI babysitter: identical build error across unrelated PRs = base-branch break, not flake](../learnings/1780790667002-ci-babysitter-identical-build-error-across-unrelat.md)). (Windows disk-space failures cluster the same way — several PRs failing one Windows job within ~6 seconds — but there the culprit is one sick runner, not the base; see [runner pools and infrastructure](ci-flake-runner-pools-and-infrastructure.md).)

**Standing escalations skip reruns entirely:** when a persistent infra problem is already routed to an infra owner (runner starvation: job CANCELLED after "awaited a runner for 24h0m0s"; materialx Docker-pull loop; nvrgfx/SlangPy CUDA-OOM), do NOT rerun — the fix is operator-side, not a retry ([Slang CI babysitter: skip reruns on standing-escalated infra failures](../learnings/1781195910201-slang-ci-babysitter-skip-reruns-on-standing-escala.md)).

**Fleet-wide deterministic failures:** a `--failed` rerun is only useful when the failure is probabilistic (can land on a different/healthy runner). When every runner in the fleet shares the same broken precondition (e.g. `cuda>=13.0` driver-mismatch fleet-wide), reruns mask the problem rather than fixing it — escalate to operator, and headline the dominant root-cause so maintainers stop rerunning into a deterministic wall ([When CI infra failure goes fleet-wide, reruns mask — escalate instead](../learnings/1782231415029-when-ci-infra-failure-goes-fleet-wide-reruns-mask-.md), [CI babysitter: headline the dominant root-cause when maintainers rerun into a deterministic wall](../learnings/1782248669315-ci-babysitter-headline-the-dominant-root-cause-whe.md)). The CUDA ≥13.0 container failure (`nvidia-container-cli: requirement error: unsatisfied condition: cuda>=13.0`) starts as a single unhealthy runner (one rerun OK) but can spread fleet-wide; once fleet-wide, stop rerunning ([cuda>=13.0 GPU CI runner driver-mismatch signature (shader-slang)](../learnings/1782226877304-cuda-13-0-gpu-ci-runner-driver-mismatch-signature-.md)).

**Multi-mode failure spread = degrading-runner, not test-flake.** When ONE binary-independent CI job fails intermittently in *different* ways (OOM-abort → SIGSEGV → HANG/timeout → disk-full) across multiple distinct PRs — including PRs that can't possibly code-cause it (a docs-only PR crashing test-slang) — that mode-spread is *evidence for* a runner-health/infra issue, not against it. Do NOT hold it under a "wait for N repeated-identical failures" gate: that gate exists to avoid conflating unrelated test flakes, and repeated-*identical* failures are the strong signal for a flaky *test*, but a runner starving on resources manifests precisely as a spread (OOM when alloc fails, SIGSEGV on a corrupted partial alloc, HANG when thrashing, disk-full when `/tmp` fills). File/track a runner-health issue naming the runner + fix candidates (memory headroom, `-server-count`, `/tmp`), fold in sibling resource-pressure failures, and keep rerunning as the stopgap ([Multi-mode CI failure spread = degrading-runner issue, not test-flake](../learnings/1783354616229-multi-mode-ci-failure-spread-degrading-runner-issu.md)).

**GCP linux-build runners mis-report AVX-512 → SIGILL — check FIRST for per-VM CPU-path flakes.** A per-VM, low-frequency flake on a CPU/LLVM test path in a GCP `linux-build`-pool job (surfacing as SIGILL, or a downstream symptom like the ASan "runtime does not come first" abort) is a recurring env class: some pool VMs mis-report AVX-512 their host can't execute, and slang-llvm's JIT then emits AVX-512 the host faults on. Mitigation is `export SLANG_DISABLE_AVX512=1` in the test step (PR #11974 added it to `ci-slang-sanitizer.yml`). For any per-VM SIGILL/LLVM-JIT-path flake, check AVX-512 mis-report FIRST before exotic causes; assert the *class* ("per-VM env trigger") confidently but label the specific mechanism a HYPOTHESIS — GitHub Actions job logs 410 (Gone) after ~7-day retention, so the decisive failing log is usually already gone ([GCP linux-build runners mis-report AVX-512 → SIGILL in slang-llvm JIT (recurring env class)](../learnings/1783443514224-gcp-linux-build-runners-mis-report-avx-512-sigill-.md)).
