# PR-Approver: False-Positive Refutation, Fix-Shape Prediction & Human-Review Gates

Step 3 of the approver — the adversarial challenger — has to distinguish WOULD_APPROVE from ABSTAIN_POLICY from BLOCK. This page collects the discipline for the *downgrade* direction: how to refute a stale or absent 🔴 without rounding it up to approve; how a prior fixer learning predicts the correct fix shape; how a standing human CHANGES_REQUESTED caps the decision; when a within-session BLOCK legitimately flips to WOULD_APPROVE; and how to verify a codegen fix by inspection when it can't run locally.

## TL;DR

- **A refuted 🔴 does not become WOULD_APPROVE.** Shadow mode never rounds a doc's 🔴 up. A challenger's refutation legitimately downgrades a would-be BLOCK to ABSTAIN, but is not license to round *up* — the ceiling stays ABSTAIN (`CHALLENGER_CONCERN`).
- **A head-current 🔴 caps the decision at ABSTAIN even when you're certain it's a false positive** — especially when it's your only head-current signal. Approve requires a doc clean of 🔴 on its own terms, not a 🔴 you personally talked down.
- **Narrowing a claim is not testing its premise.** A retraction that narrows without testing the premise inherits the error and launders it as diligence. Legitimate retraction changes the *direction* or names the *artifact* that would settle it. A feature-tier name ("Apple Silicon") is not a capability check ("Apple6") — verify the predicate the code branches on.
- **The prior fixer learning predicts the correct fix shape.** Grep the learnings for the issue number FIRST on any fixer PR you (or a peer) triaged; the recalled prediction is a diff checklist to verify axis-by-axis, and a deviation is the signal recall exists to surface.
- **A standing unresolved human CHANGES_REQUESTED caps at ABSTAIN regardless of a clean doc** — only the requester clears their own request. A DISMISSED review is NOT a standing CHANGES_REQUESTED. A same-head human APPROVAL is a JOIN signal for calibration, never a reason to flip your independent OPEN_GAP up.
- **Legitimate flips exist.** A CI-proven BLOCK flips clean to WOULD_APPROVE when the next commit is a test-only, CI-proven-green fix of your exact next-action. A converging multi-synchronize loop reliably ends in a same-head APPROVE. `REVIEW_REQUIRED` from auto-dismiss-on-push is not a withhold reason.
- **A standing bot 🔴 is REFUTED, not honored, when the flagged text no longer exists at the pinned head** — bot bug lists lag commits. Re-fetch the exact file:line and grep the named phrase. This is legitimate, unlike downgrading a *confirmed* 🔴 by severity.
- **Correctness ≠ validation.** A codegen fix whose only validating test never executed is OPEN_GAP, not WOULD_APPROVE. You CAN establish correctness-by-inspection (align with hand-written siblings, prove before/after byte-identity) — that answers "is it right?", never "was it validated?".

## False-positive refutations: a refuted 🔴 does not become WOULD_APPROVE

Devin (or any automated reviewer) can raise a plausible 🔴 that source inspection **narrows**. ⚠️ **The slang-rhi#800 example below is NOT a clean refutation — it is the page's cautionary case, corrected twice (2026-08-03) and rewritten in place here.** On slang-rhi#800 Devin flagged an indirect-dispatch residency crash "missing useResource". The Metal two-category taxonomy is correct and still the right first move — a resource passed *directly* to an encoder method (including `dispatchThreadgroups(indirectBuffer,...)`) is auto-resident, `useResource` is needed ONLY for GPU-addresses dereferenced inside argument buffers, and the codebase calls `addUsedResource` only in the arg-buffer-writing path — but the taxonomy was **not sufficient to clear the finding**, so "refuted" overstated it. Correct status of record: **NOT-BLOCK but NOT-CLEARED** ([[approver/challenger-miss-averted] Metal direct-encoder-operand — CORRECTED twice: not a clean refutation, and the residency polarity was inverted](../learnings/1784338866210-approver-challenger-miss-averted-metal-direct-enco.md)). Crucially: a refuted 🔴 does NOT justify BLOCK, but shadow mode never rounds a doc's 🔴 up to WOULD_APPROVE either — so the decision is `ABSTAIN_POLICY:CHALLENGER_CONCERN`. Trace the exact residency/mechanism category before blocking on an automated reviewer's claim — and then check that the mechanism you traced bears on the *path the finding is about*.

> ⚠️ **WITHDRAWN COROLLARY (rewritten in place, 2026-08-03) — do not read a "the fallback merged unverified" claim anywhere on this page.** The earlier text here asserted that *the `!m_hasResidencySet` **fallback** was the unverified/uncovered path, and that only a run with `SLANG_RHI_METAL_NO_RESIDENCY_SET` would close it.* **Both halves are withdrawn.** `m_hasResidencySet = true` is set **only** inside `else if (supportsFamily(MTL::GPUFamilyApple6))` (`metal-device.cpp` L121, verified at merged `d8c609ef`); the hosted `Apple Paravirtual device` on `macos-26-arm64` is Apple Silicon but **does not expose Apple6**, and a sibling job on that image logs the terminal-`else` `GPUFamilyApple6 not supported; using per-encoder useResource fallback`. ⇒ **CI runs the FALLBACK by default**, so the fallback is the path that actually executed and is very likely covered by the passing `compute-indirect*.metal` cases; the **residency-SET path is the uncovered one** and needs Apple6 hardware CI does not have. ❌ Never cite `SLANG_RHI_METAL_NO_RESIDENCY_SET` as the missing artifact — CI is already on that path; the missing artifact is an **Apple6 run** ([[approver/calibration] a caveat can be wrong toward EXCESS caution — the "unverified config" CI runs by default, and the sibling-job trick that settles it](../learnings/1785778241162-approver-calibration-a-caveat-can-be-wrong-in-the-.md), [[approver/challenger-miss] a diagnostic captured only on the FAILURE path cannot be read from a green log — CI runs the `!m_hasResidencySet` fallback](../learnings/1785778085689-approver-challenger-miss-a-diagnostic-captured-onl.md)). Two supporting claims are withdrawn with it: *"every buffer is registered via `registerResource` regardless"* — `registerResource` (`metal-device.cpp:608`) does **all** its work inside `if (m_hasResidencySet)` (`:611`), so it covers only the residency-set path, i.e. the one never in question; and *"zero `[Info]` lines in either log"* — those messages are `DebugMessageType::Info` routed to doctest `INFO()`, flushed only on failure or `-v` (`tests/testing.cpp:209-219`), and `debugCallbackOutput` is assigned **only** inside `RETURN_NOT_AVAILABLE` (`:884`), so the silence was uninformative by construction. What survives from the original write-up: the five-step coverage-closing checklist and the residency *taxonomy* as a first move. `unresolved` was accurate; **which** path was unresolved was inverted.
>
> **Two durable lessons from the withdrawal itself.** (1) **Narrowing a claim is not testing its premise** — "the fallback is unexercised" was retracted and rewritten as "unverified": weaker, same direction, same untested premise (*which path does CI take?*). A retraction that narrows without testing the premise inherits the error and launders it as diligence; legitimate retraction changes the **direction** or names the **artifact that would settle it** ([[approver/challenger-miss] narrowing a claim is not testing its premise — and the correct fact was already in my own store](../learnings/1785778812255-approver-challenger-miss-narrowing-a-claim-is-not-.md)). (2) **A feature-tier name is not a capability check** — "Apple Silicon" is not "Apple6"; verify the predicate the code branches on, not the marketing tier it resembles ([[approver/calibration] closing a coverage gap can UNCOVER a new one — and clause (a) "the map is dead code on Apple-Silicon runners" is FALSE](../learnings/1785776756858-approver-calibration-closing-a-coverage-gap-can-un.md)). One unauthenticated `curl` of a public job log would have settled it before either version was recorded.
>
> For the archetype of a genuinely refuted 🔴, use the slangpy#1082 or pinned-head-absence cases, not this one. Retraction filed on the root atom (`learnings/1784338866210-…`); the parent calibration atom carries its own `RETRACTED IN PART` + `POLARITY CORRECTION` banners ([[approver/calibration] slang-rhi#800 — an execution-coverage OPEN_GAP is CLOSABLE (with the residency corollary retracted in place)](../learnings/1785770830139-approver-calibration-slang-rhi-800-an-execution-co.md)).

The asymmetry is the whole point and the DECISION_REVIEW gate enforces it: on slangpy#1082 @3a266be (Devin the sole head-current signal) a Devin 🔴 at `torch_bridge_impl.cpp:126` was refuted as a clear false positive (native pre-check `required_size=64+ndim`; torch rank ≤64; both production callers pass a 128-byte buffer) and WOULD_APPROVE was drafted — the gate returned must-fix, because the challenger's refutation legitimately downgrades a would-be BLOCK to ABSTAIN but is NOT license to round UP. When the head-current review doc carries any 🔴 — especially when it is your ONLY head-current signal — the ceiling is ABSTAIN; approve requires a doc clean of 🔴 on its own terms, not a 🔴 you personally talked down. Two accuracy traps codex also caught here: "only N in-tree callers" is often wrong for an exposed ABI (a ctypes test called the exported fn-ptr with `required_size-1`), and a decision-moving external fact ("torch max rank = 64") pulled from a *prior session's* deepwiki check must be re-pinned or labeled not-independently-verified in the current session ([[approver/challenger-miss] A head-current 🔴 caps the decision at ABSTAIN even when you're sure it's a false positive — never round up to approve](../learnings/1785495112092-approver-challenger-miss-a-head-current-caps-the-d.md)).

## The prior fixer learning can PREDICT the correct fix shape

When the fixer who triaged an issue left a durable learning about *what the principled fix should look like*, Step-0 recall surfaces it as the sharpest challenger prior. On slang#11665 (reject operator names on vars/params) the recall learning predicted the fix must reject at the single choke point (`UnwrapDeclarator`) gated by an opt-in, sparing legit operator functions — and the PR did exactly that, letting the challenger verify the diff *matches the predicted shape* rather than re-derive from scratch ([[approver/human-agreement] fixer-issue-learning-predicts-correct-fix-shape-clears-challenger](../learnings/1784307794563-approver-human-agreement-fixer-issue-learning-pred.md)). Grep the learnings for the issue number FIRST on any fixer PR you (or a peer) previously triaged.

## A standing human CHANGES_REQUESTED caps at ABSTAIN — never round up

`eval-clauses.py` has NO clause for human-review-state, so a standing unresolved maintainer CHANGES_REQUESTED on the current head is invisible to Steps 1–2 — the challenger MUST run `gh pr view --json reviewDecision,reviews`. On slang#11136 the doc verdict was APPROVE with 0 bugs, Devin independently *confirmed* the fix, and the code was verified correct in source — yet the standing CHANGES_REQUESTED caps the decision at `ABSTAIN_POLICY:CHALLENGER_CONCERN` (only the requesting maintainer can clear their own request) ([[approver/challenger] standing human CHANGES_REQUESTED vetoes WOULD_APPROVE regardless of clean doc](../learnings/1784326394685-approver-challenger-standing-human-changes-request.md)). Distinguish carefully: a **DISMISSED** review WITHDRAWS a (here non-blocking COMMENTED) review, leaving no active human review — it does NOT block WOULD_APPROVE, unlike a standing CHANGES_REQUESTED (slang#12133 R3) ([[approver/challenger] module-version-bump synchronize (k_maxSupportedModuleVersion): audit value/lockstep/additivity against the design docs; DISMISSED human review is not a CHANGES_REQUESTED veto — slang#12133 R3](../learnings/1784343540068-approver-challenger-module-version-bump-synchroniz.md)). Beware framing drift — decide from harvested state, not the dispatch's "disputing vs complying" characterization.

**A same-head human APPROVAL is a JOIN signal, not a reason to flip your gap.** If you let a visible human approval upgrade your independent read you stop being an independent check and the agreement statistic becomes meaningless. On #12144 R2 a maintainer had APPROVED the exact head while the approver's independent read was ABSTAIN(OPEN_GAP): the calibrated outcome is `ABSTAIN_POLICY:OPEN_GAP` decision row AND a separately-recorded `human_verdict=APPROVED` = a healthy **withhold-on-SAFE agreement**, NOT a collapsed WOULD_APPROVE ([[approver/human-agreement] A same-head human APPROVAL is a JOIN signal, not a reason to flip your OPEN_GAP to WOULD_APPROVE](../learnings/1784281316765-approver-human-agreement-a-same-head-human-approva.md)). Decide first with the human verdict walled off; record it only after, purely for calibration.

## Legitimate within-session flips and converging loops

Not every re-eval is a hold. A CI-proven BLOCK flips cleanly to WOULD_APPROVE when the fixer's next commit is a **test-only, CI-proven-green fix of your exact next-action**: on #11595 the BLOCK'd E41303 diagnostic broke `gh-9931.slang.1`; R5 fixed the test's false alignment promise with all 9 compiler files byte-identical R4→R5 (diagnostic still stands, not weakened) and the specific previously-red sub-test now `passed` — a VINDICATED BLOCK (SUPERSEDED_CHANGES_REQUESTED), and recording WOULD_APPROVE is the honest call, not "backing down" ([[approver/human-agreement] BLOCK→WOULD_APPROVE flips clean when the fixer's next commit is a test-only, CI-proven-green fix of your exact next-action](../learnings/1784270379814-approver-human-agreement-block-would-approve-flips.md)). A **converging multi-synchronize loop** (each push adopts the reviewer's most recent concrete ask) reliably ends in a same-head APPROVE — #12034 ran 5 revisions and merged at the exact R5 head with the maintainer's approval ([[approver/human-agreement] confirmed: a multi-synchronize fixer↔maintainer review loop that converges (each rev adopts the reviewer's ask) reliably ends in a same-head APPROVE — WOULD_APPROVE on each settled rev is safe](../learnings/1784308481321-approver-human-agreement-confirmed-a-multi-synchro.md)); `REVIEW_REQUIRED` from auto-dismiss-on-push is not a withhold reason, only a standing CHANGES_REQUESTED is. A **review-response cleanup revision** (comment trim + if-chain→switch) carries the prior revision's verified safety forward once you prove the emit body is byte-identical and the refactor is logically equivalent — but don't overclaim "N green / 0 red" while legs are still pending (codex DECISION_REVIEW catches this) ([[approver/challenger] synchronize cleanup-only revision: verify delta semantics-preserving (byte-diff emit body + refactor equivalence), carry prior safety forward, don't overclaim unsettled CI — slang#12133 R2](../learnings/1784338540772-approver-challenger-synchronize-cleanup-only-revis.md)).

## Standing-bot 🔴 refutation & codegen-fix verification without running the compiler

Three challenger-stage calibrations from the slang#11803 and #12142 chains. **(1) A standing bot 🔴 is REFUTED, not honored, when the flagged text/code no longer exists at the pinned head.** Devin's bug list can LAG the latest commit (re-renders slowly / keys off a cached analysis), so a bug persists in the list after the code is fixed. The sole discriminator is whether the defect actually exists in source at the pinned head — re-fetch the exact file:line and grep the named phrase. This is NOT the "downgrade a CONFIRMED 🔴 by severity" error: refuting an ABSENT 🔴 is legitimate and required; honoring a label for a defect that no longer exists is a false-BLOCK ([a standing bot 🔴 is REFUTED when the flagged text no longer exists at the pinned head](../learnings/1784442969985-approver-challenger-a-standing-bot-is-refuted-not-.md)). **(2) A codegen fix whose only validating test never executed = OPEN_GAP, not WOULD_APPROVE.** External-fork PRs have their `CI` workflow maintainer-gated (`conclusion=action_required`, 0 jobs); the green *combined* status covers only CLA/CodeRabbit/trigger, not slang's build/test matrix. Pull `/actions/runs?head_sha=<sha>` and check the `CI` run's conclusion + job count — codegen change + unrun validating test + no local run path ⇒ ABSTAIN_POLICY/OPEN_GAP, never round up ([fork-PR codegen fix with unrun validating test → OPEN_GAP](../learnings/1784446531911-approver-challenger-fork-pr-codegen-fix-with-unrun.md)). **(3) But you CAN establish correctness-by-inspection** when the target can't run locally: align the change with pre-existing hand-written siblings as ground truth, prove before/after byte-identity to bound the blast radius, grep every use of a role-changed variable for completeness, and confirm the test corpus has no pre-existing test asserting the old form. This separates "is the code right?" (yes) from "has it been validated?" (no) — two axes driving different reason_codes ([verify a codegen fix by aligning with siblings + before/after byte-identity](../learnings/1784446552079-approver-challenger-verify-a-codegen-fix-by-aligni.md)).

## Contradictions / supersessions

- A refuted 🔴 does NOT round up to WOULD_APPROVE (shadow-mode never rounds up a doc's 🔴) — it lands `ABSTAIN_POLICY:CHALLENGER_CONCERN`. ⚠️ The slang-rhi#800 citation is **corrected**: that 🔴 was never cleanly refuted (NOT-BLOCK **but NOT-CLEARED**), so it exemplifies the *withhold*, not the refutation; symmetrically a same-head human APPROVAL does not flip an independent OPEN_GAP up.
- ⚠️ **WITHDRAWN — the slang-rhi#800/#801 residency corollary.** The sentence *"the `!m_hasResidencySet` **fallback** merged unverified — only a `SLANG_RHI_METAL_NO_RESIDENCY_SET` run closes it"* (and its #801 sibling *"the map is dead code because `m_hasResidencySet` is true on Apple-Silicon"*) is **withdrawn on both PRs**. Truth: `m_hasResidencySet` is set only under `supportsFamily(MTL::GPUFamilyApple6)`, the hosted Paravirtual adapter lacks Apple6, ⇒ **CI runs the FALLBACK by default**; the residency-SET path is the uncovered one and the missing artifact is an **Apple6 run**, never the env var. The two rows were *mutually inconsistent* (adjacent PRs, same subsystem, opposite defaults for one flag) — that inconsistency was the tell, and a 30-second grep of one's own adjacent notes would have exposed it before the join did. Neither decision changed (both stay ABSTAIN, both merged) — only the **basis**, which is the part future decisions reuse. **Meta-rule this establishes:** a correction filed as a NEW atom does **not** disarm the stale one. Only an edit that *names the file* and *quotes the superseded sentence* stops the next reader mining the old wording — so sweep for the SUPERSEDED phrasing (headings → title/frontmatter → tables → index rows → prose → serialized ledger payloads), never for your new phrasing, and re-record the `approval_decisions` row when the retraction touches its `challenger`/`clauses` field ([[approver/challenger-miss] "N sources agree" is a claim about provenance — and the retraction's blast radius includes the RECORDED LEDGER ROW](../learnings/1785785616042-approver-challenger-miss-n-sources-agree-is-a-clai.md)).
- A DISMISSED human review is NOT a standing CHANGES_REQUESTED — it does not cap at ABSTAIN, whereas an unresolved CHANGES_REQUESTED does.
