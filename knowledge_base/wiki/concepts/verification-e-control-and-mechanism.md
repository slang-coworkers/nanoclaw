## TL;DR

A control is only as good as what varies between its arms, and a mechanism is only established when it predicts what you actually observed:

- **A control that does not reproduce the shipped configuration can refute a real defect** — and it fails as a *clean, plausible null*, the direction you are least likely to re-check because refuting your own work feels like rigour.
- **When a check and its subject agree, that is the condition under which a broken check is invisible**, not confirmation. A predicate whose error is masked by a correct outcome accrues no evidence against itself and becomes self-certifying.
- **Presence-bisecting is not attribution.** "When did this code appear" ≠ "is this code what changed the behaviour." Enumerate rival causes in the window and HOLD THEM CONSTANT; the *expected-unaffected* control is the cell that earns its keep — and a control that *fails* is the only one that can overturn your framing.
- **Mutation testing catches a wrong-reason pass iff you mutate what your CLAIM names, not what your ASSERTION names.** Write the sentence you want true, then mutate its subject.
- **Group the corpus by the entity you're claiming about, and verify the grouping key VARIES** — a count with no grouping is a count of whatever the sort order handed you; a key that doesn't vary (a branch-head SHA) produces one group and looks like agreement.
- **A source comment is evidence about intent, never about this execution.** A satisfying mechanism suppresses the cheap check ("does this code run on my input?"); a proxy substituted for the artifact is wrong in the direction that matters.
- **A merge-group job failure is not an eviction**, and **related-by-symptom is not fixed-by** — the authoritative signal and the destructive action both need the artifact, not the proxy.

## A control that measures nothing certifies rather than tests

The most dangerous control failures produce **clean, plausible refutations of true findings.** Verifying a real fix (a probe that suppressed a diagnostic), an A/B where both arms printed the diagnostic concluded the fix was a no-op — but the control arm placed the probe *after* the library precompile while the shipped code probed *before* it, so the variable under test was held constant. "Your fix changes nothing" is exactly what a correct null looks like, and its failure mode was to make the author *retract a true finding*. Before trusting an A/B result, state which variable differs and verify the control arm reproduces the shipped configuration — ask "if I diffed my control arm against the real code, would it be identical?" Reconstruct the baseline from the actual artifact (`git checkout` the shipped file), not from a plausible-looking file no commit ever contained; a null result deserves the same scrutiny as a positive one [A control that does not reproduce the shipped configuration can refute a real defect](../learnings/1786193847896-a-control-that-does-not-reproduce-the-shipped-conf.md).

## The self-certifying defect: agreement is when a broken check is invisible

A predicate whose error is masked by a correct outcome accrues no evidence against itself. A supervisor check concluded "no human waiting" because the newest non-bot *issue comment* was null — but a maintainer had spoken through a **review body** 11 hours earlier, structurally invisible, since speaking through a review body is how maintainers normally speak. On that PR the false premise produced the *right* verdict (he deferred with no ask), so the defect is self-certifying: it keeps reporting "no human waiting" on exactly the PRs where a maintainer *has* asked and is ignored, and every sampled case looks fine. **When a check and its subject agree, that is not confirmation — it is the condition under which a broken check is invisible;** re-running a query that agrees with you is the only thing that surfaces the off-diagonal cell. The companion defects there: a gate that cannot spell the value it must match is not a gate (assert the gate fires on the real value, with a control that still fires), and a **paraphrased identifier is the signature of a claim about an artifact nobody opened** [A predicate whose error is masked by a correct outcome accrues no evidence against itself](../learnings/1786106313177-a-predicate-whose-error-is-masked-by-a-correct-out.md).

The same substitution recurs as "a signal's shape is not its content": a trailing bot comment read as "no answer exists" when it *was* the answer; a derived branch name (`fix/issue-1051`) read as "no PR exists" when the real branch was `dev/slangpy-fixer/1051`, nearly deleting the working copy of an open draft PR; "I fired the tool" reported three times without the tool ever being called. Before acting on any absence — no answer, no PR, no match, no artifact — ask *what exact object did I query, and is it the object I mean?* Resolve to the real identifier (actual branch, `head.sha`, comment body, artifact URL) before any decision that deletes, closes, escalates, or reports done; when a proxy is cheap to verify and the action is hard to reverse, verify [A signal's shape is not its content — verify the artifact, not the proxy](../learnings/1786194329076-a-signal-s-shape-is-not-its-content-verify-the-art.md).

A detector keyed on GitHub comment *order* re-fires forever when a human comment correctly needs no answer — no amount of replying changes GitHub's comment order, only a new GitHub comment can, so the fix belongs in **stored state**, not the reply. Don't delete a detector whose premise was true on some firings; suppress the instance. And "my message left" + "their state didn't change" ⇒ dropped message is valid **only if that state is actually derived from my message** — check the derivation before believing the drop [A detector keyed on GitHub comment order re-fires forever when a human comment correctly needs no answer — and "my reply left, your state didn't change" is not evidence of a dropped message](../learnings/1786194888549-a-detector-keyed-on-github-comment-order-re-fires-.md).

## Presence-bisecting is not attribution

Bisecting the *presence* of a guard answers "when did this code appear," never "is this code what changed the behaviour." Where a rival cause exists in the same failure class, presence-bisect attributes the symptom to the wrong commit. The fix: enumerate what else touched the area in the window, then either vary it or **hold it constant** (choose two-state endpoints that both have the rival commit as an ancestor, so it cannot account for a pre/post difference), build both, and run the repro. **The expected-unaffected control is the cell that earns its keep** — and when it *failed* (a second issue's reproducer, predicted immune, moved too), that failure was the real finding: the two were the same crash, the opposite of the "artifact of a partial fix" story the author had been handed. A control that fails is not a setback; it is the only cell that can overturn the framing you arrived with. Two-state hygiene: build at the boundary commit and its immediate parent, verify each binary carries the state via `slangc -v` *and* a source grep, and keep the pre-fix binary (once the fix ships, master can no longer reproduce the issue's own filed symptom) [A guard-presence bisect attributes a symptom change to the wrong commit unless rival causes are held constant](../learnings/1786204316355-a-guard-presence-bisect-attributes-a-symptom-chang.md).

## A source comment is evidence about intent, never about this execution

Two agents spent two days on an exact, well-controlled analysis of the **wrong code path** and put a design ruling to a maintainer on the strength of it — every figure correct, the edifice irrelevant. A source comment ("a physical pointer needs an untyped pointer if the element type is nothing") told them what the arm was *for*; it could not tell them the arm was *on the failing path*, yet it read as corroboration from the codebase itself. **A mechanism the code's own comments appear to endorse is the hardest kind to keep interrogating** — the missing step was never subtle (*does this code run on my input?*) and four rounds of increasingly precise measurement never asked it. And **a satisfying mechanism suppresses cheap checks**: the assert printed its operand flavor (`none` = "the value is nothing") the whole time, but once `createLegalPtrType` "explained" the symptom, the diagnostic stopped being something to read. Remedy: instrument the branch or delete it and see whether behaviour changes; before asking *who* produced the malformed shape, read *which* thing is malformed [A source comment is evidence about intent, never about this execution — and a satisfying mechanism suppresses cheap checks](../learnings/1786198336547-a-source-comment-is-evidence-about-intent-never-ab.md).

## Mutation testing catches a wrong-reason pass — if aimed at the CLAIM

Mutation catches a wrong-reason pass **iff you mutate the element your CLAIM names, not the element your ASSERTION names.** Mutating what the assertion names (the diagnostic) only shows the test is wired to *something*; mutating what the claim names (interface-ness vs emptiness — add a data member and watch the outcome flip) discriminates *which path* produced the outcome. They coincide only when your claim is about *whether*; they diverge whenever your claim is about *why*. Operative habit: **write down the sentence you want to be true, then mutate its subject** ("this fix stops the abort" → revert the fix; "this guard enforces the invariant" → defeat the guard, not the feature). The distinction that survives: a vacuous pass fails to test, but a **wrong-reason pass actively certifies** — green, stays green, nothing in the log ever looks off. And the meta-lesson: a rule can be stated correctly about its instance and wrongly about its domain, so the generalization needs its own check separate from the instance that produced it [CORRECTION: mutation testing does catch a wrong-reason pass — if you mutate what your CLAIM names, not what your ASSERTION names](../learnings/1786216749315-correction-mutation-testing-does-catch-a-wrong-rea.md).

## Group the corpus by the entity you're claiming about

A count with no grouping is a count of whatever the sort order handed you. A peer, in the *same message* that retired a mis-scoped item, asserted "the per-PR legs have a persistent ~61-62 test bed" from 5 sampled runs — all five of which resolved to **one PR**. The mis-scoping recurred *inside* the correction, by someone maximally alert to it: **vigilance does not prevent mis-scoping, because vigilance is not a grouping** — only the mechanical step works. Before quoting any rate/count/median: `group_by` the entity named in your claim; **verify the grouping key VARIES** (an identical `head_sha` across all successes and failures is branch-head metadata, and a key that doesn't vary produces one group that looks like agreement); note that stability across repeated samples of *one* item means that item is deterministic, not that the population shares its behaviour; and prefer the structural claim (disjoint job sets make aggregation invalid regardless of count) to the magnitude one, because the structure doesn't decay [Group the corpus by the entity you're claiming about before quoting any figure](../learnings/1786216773009-group-the-corpus-by-the-entity-you-re-claiming-abo.md).

## Two GitHub-shaped traps: the authoritative signal, and the destructive action

**A merge-group job failure is not an eviction.** GitHub can form a *new batch* for the same PR; if a later batch is green the PR merges and the earlier failing batch is superseded. The authoritative eviction signal is the `RemovedFromMergeQueueEvent` in the PR timeline (with its `reason` and `beforeCommit`), never the conclusion of a merge-group run — and batch branches are named after *one* PR in the batch, so resolve membership by matching `merge_commit_sha` against batch heads. A **window is not a property**: "caused 0 evictions" was true of a 26-hour window and false as a general sentence; before writing a zero as a verdict, name the window and check whether the stored claim you think you're refuting was measured on a different one [A merge-group job failure is not an eviction — a superseding green batch can still merge the PR](../learnings/1786091523426-a-merge-group-job-failure-is-not-an-eviction-a-sup.md).

**Related-by-symptom is not fixed-by.** A shared reproducer is *actively* misleading, not merely weak evidence — it is exactly what makes one issue look like the other's fix, and "X lists Y as its only related PR" is a co-occurrence, never a coverage claim. A closing keyword (`Fixes #N`) is a destructive action at merge time; before adding one, run *that issue's own repro* against the fixed binary and require the defect to be GONE — not "the shape is handled," not "same root area." A near-miss `Fixes #12372` would have auto-closed a live, reproduced bug on a target SPIR-V never in the fix's set. Companion: a timeout is not authorization — laundering a timed-out `ask_user_question` through another tier does not manufacture consent; escalate it as a blocked item with the content ready [Related-by-symptom is not fixed-by: two issues sharing a repro is the signal that invites a wrong `Fixes #N`](../learnings/1786106630195-related-by-symptom-is-not-fixed-by-two-issues-shar.md).
