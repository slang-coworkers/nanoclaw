## TL;DR

The `slang-pr-review-runner` (Reviewer A) wrapper (`compose-and-run.sh`) has two
recurring integrity hazards, both driven by a **shared, non-namespaced checkout**:

- **`INTEGRITY-FAIL` is often a FALSE POSITIVE from a clobbered shared `tmp/`.**
  Concurrent reviews of different PRs all stage into
  `/workspace/agent/slang/tmp/{pr-diff.patch,pr-files.txt,context.json}`. A second
  run (or a stale leftover from a prior run) overwrites them, so the post-run guard
  compares the review against the *other* PR's files. Do NOT dismiss it on the
  model's self-report, and do NOT discard the review on the guard's headline —
  **adjudicate by CONTENT with an independent measurement**: sha256 the run dir's
  `pr-diff.reference` against a fresh `gh pr diff <N>`, check the `final-review.md`
  footer `reviewed: <head> · diff sha256`, confirm the target PR's fingerprints
  saturate `stream.jsonl`, and `summarize.py` drift==0.
- **The race is routine and can corrupt more than the guard's input.** It fired on
  six PRs in four days and was still firing weeks later; some subagents read the
  wrong diff, a concurrent pr-mode run can `git checkout origin/master` under a
  branch-mode run, and sometimes every subagent refuses and no review is produced.
  Launch **every** Reviewer A run with `REPO_ROOT=<private wt-<N>-revA worktree>`
  (plus `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`); never run two A jobs on the
  shared checkout. Durable fix: the runner writes diff + context into `$RUN_DIR`.
- **The exit=1 guards are a family of over-firing heuristics** (INTEGRITY-FAIL,
  REVIEW-GUARD on infra wording such as a bare "socket") — read `final-review.md`
  before believing any of them.
- **The wrapper can report `success` with a dead review.** A 96-byte error-string
  artifact passed exit-status and existence checks; a truncated A can report a false
  `0/0/0` clean; the clarity runner can capture a trailing meta-message. Gate on a
  size floor (<500 B = failed), a content sniff, and a findings table; recover from
  `stream.jsonl` before re-running, and report `reviewers_complete:false`.
- **Patch mode's `git commit -am` drops NEW files** → a false "no test in patch" gap.

Liveness: **stream-static is NOT death.** Subagents run silent for minutes; gate the
terminal test on `final-review.md` (≥500 B) or the `{"type":"result"}` record.

Process discipline: **an `Edit` is not a delivered change until built + committed +
pushed** (`git ls-remote` confirms the SHA), and **reply IN-THREAD** to PR review
comments — except while the maintainer's review is still pending (the comment 404s):
then reply on the PR conversation, and re-fetch before pushing.

## INTEGRITY-FAIL: the shared-tmp false positive and how to adjudicate

`compose-and-run.sh`'s post-run guard re-reads the SHARED `$REPO_ROOT/tmp/pr-diff.patch` (`REPO_ROOT=/workspace/agent/slang` by default for all slang and slang-rhi runs) and compares its `+++ b/` file set with the live PR's files. The script clears the file at start, but nothing stops a concurrent run rewriting it mid-flight, so the guard reads the other PR's diff and mismatches. Adjudicate by CONTENT, never by the model's self-report or the guard headline; do **all** of: `sha256sum <run_dir>/pr-diff.reference` (the runner's own immutable capture at dispatch) == a fresh `gh pr diff <N>`; the `final-review.md` footer `reviewed:<sha>` == live `headRefOid` and its `diff sha256` matches; findings cite the requested PR's files (target fingerprints saturate `stream.jsonl` tool_use — wrong-PR hits are the model's own clobber-detection reads); `summarize.py <run_dir>` drift==0. If all agree the review is VALID and the guard's input was stale — keep `reviewers_complete:true` and document the rc=1 override with that evidence. On PR#12508 the guard listed PR#12509's VM files while 227 target hits beat 13 clobber-detection hits ([Reviewer-A INTEGRITY-FAIL is a false positive from a clobbered shared tmp — adjudicate by content](../learnings/1786557797524-reviewer-a-integrity-fail-can-be-a-false-positive-.md), [concurrent runner sessions collide on shared tmp → do all four checks before overriding rc=1](../learnings/1789518412257-concurrent-slang-pr-review-runner-sessions-collide.md)). Only Reviewer A is exposed — Reviewer B scrapes Devin, and Reviewer C self-isolates in its own run dir and `wt-clarity-*` worktree, making C an independent cross-check that the right diff was reviewed (on #13255 a concurrent slang-rhi run wrote its 133 KB diff into the shared patch mid-run, mtime inside the run, while A's footer matched the target head/diff from `tmp/context.json`) ([INTEGRITY-FAIL false alarm under concurrent cross-repo reviews — verify content before discarding](../learnings/1790235571363-slang-pr-review-runner-integrity-fail-can-be-a-fal.md)). When A exited nonzero, honest reporting is `reviewers_complete:false` **with the findings reported valid** plus a one-line run-note, never a discard (#13227 r2: `tmp/pr-diff.patch` held a diagnostics PR's files, the review correctly covered the CallShader/CUDA diff, footer hash `3714c8a3e0e3` matched) ([INTEGRITY-FAIL exit 1 can be a shared-checkout tmp race, not a wrong-diff review](../learnings/1790108064998-slang-pr-review-runner-integrity-guard-exit-1-can-.md)).

**The contamination need not be concurrent.** On slang#13239 round 2 a leftover slang-rhi `tmp/pr-diff.patch` from a PRIOR run sat in the slang checkout and false-tripped the guard while `pr-diff.reference` sha256 == the live diff; `grep '^+++ b/' /workspace/agent/slang/tmp/pr-diff.patch` showing another repo's files is the tell ([INTEGRITY-FAIL can be a false positive from a stale cross-repo tmp/pr-diff.patch](../learnings/1790220188333-slang-pr-review-integrity-fail-can-be-a-false-posi.md)).

**Why the review usually survives.** The inner CLI self-heals: subagents that read the clobbered diff bail ("pre-staged diff does not match the requested PR"), and the orchestrator isolates the correct diff into `tmp/iso-<pr>-review/pr-diff.patch` and re-runs them, while the post-run net still re-reads the stale shared file; Reviewer A's `pr-diff.reference` hash vs Reviewer C's run-dir-name hash is a quick cross-check ([slang-pr-review-runner INTEGRITY-FAIL self-heals via tmp/iso-<pr>/ while the post-run net still trips](../learnings/1789506920553-slang-pr-review-runner-integrity-fail-can-be-a-fal.md)). Also the model's sandbox denies `> tmp/pr-diff.patch` redirects, so subagents fall back to a live `gh pr diff <N>` for the actual review content ([the sandbox denies tmp/pr-diff.patch redirects so subagents review via live gh pr diff](../learnings/1789441851541-slang-pr-review-runner-integrity-fail-can-be-a-fal.md)). Clearing `/workspace/agent/slang/tmp/{pr-diff.patch,pr-files.txt,context.json}` before (re-)launch prevents wasting a full run; separately, a `API Error: 400 Invalid JSON payload` mid-run (twice on #12479) is transient — don't call it deterministic after 1–2 failures if a sibling reviewer on the same model succeeded ([Shared slang checkout tmp/ is a cross-review race — a concurrent PR clobbers your staging](../learnings/1786670089193-shared-slang-checkout-tmp-is-a-cross-review-race-a.md)).

**Self-healing is not guaranteed — the race is routine and reaches beyond the guard.** On #13331 a texture-sampler PR's diff replaced the patch mid-run; grep `final-review.md` and `tool-uses.jsonl` for the files `INTEGRITY-FAIL.txt` lists ([concurrent reviews race on shared slang/tmp/pr-diff.patch (#13331)](../learnings/1790716418006-concurrent-reviews-race-on-shared-slang-tmp-pr-dif.md)). On #13356 the file was overwritten 12 s before the check; for a per-subagent audit parse `stream.jsonl` tool_results for the `diff --git a/<file>` sets per `parent_tool_use_id` and read `tmp/context.json` (`pr`, `head_sha`, `diff_sha256`) ([integrity guard false-positives when sessions share tmp/pr-diff.patch (#13356)](../learnings/1790800379153-reviewer-a-diff-integrity-guard-false-positives-wh.md)). On #13538 r2 (2026-10-09) a concurrent #13541 run overwrote `tmp/pr-diff.patch` and `tmp/context.json` mid-run; quickest tells: `grep '"command": .*gh pr (diff|view)' <run_dir>/tool-uses.jsonl` shows only the requested PR, `cat slang/tmp/context.json` names the other PR, and the footer carries the right head SHA. The durable fix is for the runner to write diff and context into `$RUN_DIR` (as Reviewer C does) and the guard to check that copy ([INTEGRITY-FAIL false alarm from a concurrent review overwriting the shared tmp (#13538)](../learnings/1791530998165-reviewer-a-integrity-fail-can-be-a-false-alarm-fro.md)). On #13378 some subagents reviewed the wrong diff — compare the shared patch's mtime with your run start ([concurrent runs clobber the shared pr-diff.patch; some subagents read the wrong diff (#13378)](../learnings/1790904342903-concurrent-reviewer-a-runs-clobber-the-shared-slan.md)). On #13431 R2 every subagent refused ("staged diff does not match the PR under review") and no review was produced, after R1 had drawn a false INTEGRITY-FAIL ([#13431 subagents refuse the clobbered diff](../learnings/1791205564538-reviewer-a-shares-workspace-agent-slang-tmp-with-c.md)). And on 2026-09-30 a pr-mode run for #13284 ran `git checkout origin/master` under an active branch-mode run for `fix/issue-13263`, which silently read master sources; tells are `git -C /workspace/agent/slang log -1` showing master and a `transcripts/pr-*` dir you did not start ([branch/pr runs share /workspace/agent/slang across sessions — isolate with REPO_ROOT](../learnings/1790762958834-reviewer-a-branch-pr-runs-share-workspace-agent-sl.md)).

**Prevention is the default: a private worktree per run.** `git worktree add --detach /workspace/agent/wt-<N>-revA <head-sha or origin/master>` (no submodules; REVIEW.md and `.claude/agents` are tracked) then `REPO_ROOT=/workspace/agent/wt-<N>-revA CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0 bash compose-and-run.sh …` (the script honours `REPO_ROOT=${REPO_ROOT:-…}`; #13431 used `-f` and `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`). On #11387 R1 a concurrent #11709 run drew a false INTEGRITY-FAIL and wrong-diff subagent reports; the isolated rerun finished clean, and `BG_WAIT_CEILING_MS=0` is still required — without it R1 ended with an 88-byte `final-review.md` ([set REPO_ROOT to a private worktree (#11387)](../learnings/1790799086877-reviewer-a-set-repo-root-to-a-private-worktree-to-.md)). A `wt-867-revA-r2` re-review produced no INTEGRITY-FAIL with other reviews running. Head-advance caveat: a fixer can push mid-review, so after the pass re-read `gh pr view <pr> --json headRefOid` against the footer `reviewed: <sha>`; if they differ, `git diff <reviewed>..<current>` — a comments/rename-only delta still covers the new head (disclose it), a logic delta needs a re-run. `gh pr diff`'s sha shifts when base `main` moves, so confirm the right PR with the FILE-list check, not the sha ([isolated REPO_ROOT worktree prevents the shared-tmp race; verify reviewed-commit vs current head](../learnings/1789479957663-isolated-repo-root-worktree-prevents-the-pr-review.md)).

**The sibling `REVIEW-GUARD FAIL` false-trips the same way.** It flags "final review looks like an infrastructure error": a complete 137-line review tripped it because its coverage note said "the cross-backend and clarity passes terminated on transient API errors". Full Verdict + Findings table = false trip (use it); a <500 B stub with no verdict = real failure ([REVIEW-GUARD FAIL false-trips on infra-error wording inside a valid review](../learnings/1789512038521-slang-pr-review-runner-review-guard-fail-can-false.md)). The cause is `compose-and-run.sh:220-221`'s `grep -qiE 'API Error|socket|rate.?limit'`: a 12 KB review of slang#13295 about FIFOs, devices and sockets tripped it with all five subagents complete. Grep the hit and check `summarize.py`'s subagent table before re-running; the fix is to narrow to `socket connection( was)? closed`, as `run-clarity.sh:356` does ([REVIEW-GUARD false positive on the word 'socket' in a legitimate review](../learnings/1790645552774-reviewer-a-review-guard-false-positive-socket-in-a.md)).

## Wrapper success with a dead review, and the liveness test

Reviewer C on slang#12454 exited `subtype: "success"` with a 96-byte `clarity-review.md` reading `API Error: 400 Invalid JSON payload: unexpected end of data …` — a merge step trusting exit status or file existence ships an error string as a reviewer's voice, and "no findings" is indistinguishable from "died". Gate in order: (1) size floor (≥2 KB real, <500 B = failed); (2) content sniff (`grep -qE '^API Error|Invalid JSON payload|^Error:'`); (3) recover from `stream.jsonl` Write/Edit `tool_use` payloads, applying LATER Edits; (4) report `reviewers_complete:false` even if recovery is complete. Parsing: `message` is sometimes a string and `input` can be absent — guard with `isinstance(x, dict)` ([a reviewer wrapper can report success with a 96-byte error-string artifact](../learnings/1786388990762-a-reviewer-wrapper-can-report-success-with-a-96-by.md)).

The mirror error is declaring A dead too early: subagents run for **minutes** without writing the parent stream, and on #12479 a "STALLED — stream static 3x" (~90 s) monitor fired on a wrapper that completed 3 min later. Terminal test, in priority: (1) `final-review.md` ≥500 B → done; (2) `INTEGRITY-FAIL.txt` → adjudicate as above; (3) the `{"type":"result"}` record's `is_error`/`api_error_status`; (4) wrapper gone via `/proc/<pid>/cmdline` (not `pgrep -f`, which matches the monitor) and none of 1–3 → crash. A 5+ min static timeout is a backstop only ([Reviewer A stream going static is NOT death — subagents run silent for minutes](../learnings/1786670080197-reviewer-a-stream-going-static-is-not-death-subage.md)).

**Output extraction can grab the WRONG message at rc=0.** Both runners take the *last assistant TEXT message*. The clarity runner has captured a trailing meta-conclusion ("the complete workflow.md is in my prior message…") as a 10-line `clarity-review.md` while the 44 KB review sat earlier ([clarity runner captures a trailing meta-message; recover the body from stream.jsonl](../learnings/1789517911038-slang-clarity-review-runner-can-capture-a-trailing.md)), and a mid-workflow line when the final step **Wrote** the candidate file to `tmp/review-candidates/pr-<N>-clarity-workflow.md` instead of pasting it ([clarity runner Writes the review to a GC'd tmp/ file; recover it from the Write tool_use in stream.jsonl](../learnings/1789573892015-clarity-runner-reviewer-c-can-lose-its-output-to-a.md)). Both stubs clear the incomplete-guard, so no `CLARITY-INCOMPLETE` marker. Tell: `grep -c '### ' clarity-review.md`==0 (no `## Kept`/`## Review Body`). Don't re-run (~$3–4, ~20 min, and the `wt-clarity-*` worktree is GC'd fast); recover the largest assistant text turn with `## Review Body`/`## Kept`, or the Write `tool_use` content. Find YOUR run dir from the background log's `>>> output → <RUN_DIR>` line, not `ls -dt transcripts/pr-*` — a concurrently finishing run bumps its mtime above yours, and A's bare `pr-<ts>` dir name is the ambiguous one (clarity dirs embed the head SHA) ([identify a run dir from the bg log's "output →" line, not ls -dt](../learnings/1789507730747-slang-pr-review-runner-identify-a-run-dir-from-the.md)).

**A truncated Reviewer A reports a false `0/0/0` CLEAN.** When the inner `claude --print` dispatches its six subagents asynchronously and the session ends mid-synthesis, the final text is an intermediate line (*"…holding for cross-backend before I finalize the table"*) with no findings table, so `summarize.py` reports `0/0/0` and `Run state: success`. Check the terminal `result` event for that pattern (or a ~1–2 KB `final-review.md` that reads like reasoning, not `**Verdict**:` + Findings). Async subagent transcripts are symlinks cleared on churn, so just re-run (≈$17–21 — check first). Milder: code-quality, cross-backend and doc-accuracy subagents can refuse a sandbox-blocked staged patch; the orchestrator covers them itself — usable, but note reduced independence ([Reviewer A can truncate to a false 0/0/0 clean — verify the terminal result event finalized](../learnings/1790123188250-slang-pr-review-reviewer-a-can-truncate-to-a-false.md)).

## Patch-mode `git commit -am` drops NEW files → false "no test in patch" gap

In `compose-and-run.sh`'s *patch mode*, `git checkout -b patch-review-<ts> origin/master` → `git apply --whitespace=nowarn "$PATCH_FILE"` → `git commit -q -am …` drops every NEW file: `git apply` leaves them **untracked** and `-am` stages only tracked modifications/deletions, so the reviewed temp branch omits every `new file` hunk. Reviewer A then reports 🟡 "patch carries no regression test; tests exist in the tree but are untracked (`??`)" — the `??` is the fingerprint. Reviewer C commits the patch in a worktree and does review the tests, so A-says-no-test while C-reviews-tests means the artifact. Discount the gap, verify the tests in the patch or on the fixer's branch; the runner fix is `git add -A` before commit ([Patch-mode PR review: git commit -am drops NEW test files → false "no test in patch" gap](../learnings/1789333359114-patch-mode-pr-review-git-commit-am-drops-new-test-.md)).

## Process delivery: not real until pushed, and reply in-thread

Two maintainer-flagged failures on slang#12519. **An `Edit` is NOT a delivered change**: the author edited, posted "pushing shortly", and ended the turn; the head stayed old for ~4 hours. Run format → rebuild → verify tests → commit (amend) → push → confirm remote head == local HEAD in one session, and say "pushed as <sha>" only after `git ls-remote` confirms. **Reply IN-THREAD** via `gh api -X POST repos/<o>/<r>/pulls/<n>/comments/<review_comment_id>/replies`, not a top-level `gh pr comment`, which makes "addressed" and "acknowledged" look identical and leaves threads unresolvable. The critique gate re-fires on ANY GitHub write after N edits since the last OUTPUT_REVIEW — budget a review round before push+reply ([a code Edit is not delivered until built+committed+pushed; and reply IN-THREAD on PR review comments](../learnings/1786616755173-a-code-edit-is-not-delivered-until-built-committed.md)). Exception: a webhook can deliver an inline comment from a still-**pending** review; until submitted, `GET /repos/{o}/{r}/pulls/comments/{id}` 404s, GraphQL has no `reviewThread`, and the MCP reader omits it, so neither `/replies` nor `addPullRequestReviewThreadReply` works — reply on the PR conversation saying it answers their inline comment, or wait. Diff the webhook body against your edit to confirm it is verbatim, and re-fetch before pushing: on slang#13283 the shepherd had pushed the identical change (non-fast-forward); compare trees (`git diff --quiet mine theirs`) and reset to theirs ([a pending review's inline comment can't be replied to on its thread](../learnings/1792188156159-a-pending-github-review-s-inline-comment-can-t-be-.md)).
