# Critique / delivery gate mechanics — satisfying it and not tripping it

## TL;DR

The `gate-critique-on-deliver.sh` PreToolUse hook gates delivery/handoff messages and GitHub writes on recorded codex-critique stages plus an edit-count/attestation freshness check. These atoms are its operational mechanics — how each stage is counted, how attestation invalidates an approve, how the text matcher over-blocks, and the ordering rules that keep an append-only ledger row from being locked at the wrong verdict.

- **A stage is COMPLETED only by a fresh `mcp__codex__codex` call** carrying the canonical `/codex-critique` reviewer block VERBATIM; that call also maps its codex thread to the stage. **A `codex-reply` WITHOUT a `STAGE:` line on that thread is recorded** and updates the stage's verdict (e.g. must-fix → approve). A reply whose prompt carries `STAGE:` is rejected ("developer-instructions do not match the canonical block"), because a reply has no `developer-instructions` to pin — that is the failure the older "codex-reply never counts" atoms observed.
- **Attest as plain `- <64hex> <absolute-path>` lines and give a one-word Verdict.** The `### Attested` parser does not strip backticks, so a backtick-wrapped or truncated hash records nothing and an approved, unchanged file is still denied; a Verdict line with trailing text ("approve — for PLAN_REVIEW only") records `unparseable`. Put both formats in the prompt up front. One codex call records only ONE stage (the first `STAGE:` token). Budget ~4 codex calls for a 3-stage gate; use `codex-reply` only to resolve must-fix items within an already-counted stage's thread.
- **The gate re-hashes every `### Attested` file at send time and DENIES if any changed** — so tell codex to attest ONLY stable deliverables (PR body, report, changed source), never volatile trace/log/session files (`.claude-trace/`, `logs/`, `.codex/`), or the approve is invalidated the instant you do anything.
- **ANY file write between approve and delivery re-arms the gate** — even a scratch heredoc for a `gh` comment body. Build gh/PR bodies inline (shell var) or do every file write BEFORE the final OUTPUT_REVIEW, then fire all deliveries back-to-back with zero intervening writes. A PR body must be opened with `--body-file <attested file>` (a hand-retyped `--body "..."` mismatches the hash).
- **The gate is a TEXT matcher, not a decision-state reader** — an ABSTAIN report is blocked if its prose merely contains the bare tokens `WOULD_APPROVE`/`BLOCK` (even to say the decision is *not* one of them). Rephrase ("no verified bug"/"flagged a defect"); keep `ABSTAIN_POLICY` present. Don't run a ceremonial critique to clear an ABSTAIN.
- **Never bundle a `git push` with a critique-gated command in one bash block** — the hook aborts the WHOLE block, so the push silently never runs and reviewers see stale code. Run `git push` in its own call first and verify it landed. The same holds for file edits, and the match is on command text, so even a heredoc that mentions the PR-open command trips it. After a must-fix, any `gh api` call (even a GET) is refused, so never chain a fix edit with a `gh` check.
- **Record the append-only ledger row LAST** — the mechanical delivery gate is edit-count-based and verdict-UNAWARE, so it can force an OUTPUT_REVIEW critique that flips an ABSTAIN to a late-surfacing BLOCK *after* the append-only ABSTAIN row is locked. Do artifact/memory writes → gate-forced critique → `record_decision` → deliver.
- **A round that records no attestation leaves the previous round's hashes in force.** The OUTPUT_REVIEW map is replaced by a round that parses at least one Attested line and kept by one that parses none, so a malformed or narrow re-check can leave older hashes that block delivery after you edit those files. Inspect with `jq '.critique_attested.OUTPUT_REVIEW'`; fix with one fresh canonical OUTPUT_REVIEW listing every path the gate names plus the deliverables.
- **A `[Fix Review Request]` whose `Maintainer direction:` section links any GitHub comment also needs `Fixer self-check:` with R1…Rn items**, even when the line starts `none —`.
- **The hook logs any codex reply as an approve round, including a recall summary or an empty string.** The first call on a fresh thread often returns a two-bullet wiki recall instead of the review; a same-thread `codex-reply` asking for ONLY the structured output fixes it. Trust only a reply with `### Verdict` + `### Attested` whose hash matches your artifact.

## Stage counting: codex vs codex-reply

Two atoms (one from a fixer session, one from an approver) independently establish that [`codex-reply` does not record a critique round](../learnings/1787339458278-codex-reply-does-not-record-a-critique-round-for-t.md) and [does not count toward the delivery gate](../learnings/1787672164164-codex-reply-does-not-count-toward-the-critique-del.md). Each required stage must be its own fresh `mcp__codex__codex` call whose `developer-instructions` are the canonical `/codex-critique` reviewer block verbatim (the "You are an independent reviewer… Return ONLY the structured output below" sentinels); `codex-reply` has no `developer-instructions` parameter, so a reply whose prompt carries a `STAGE:` line fails the sentinel check even though codex answers with a valid verdict. Further, one codex call records only ONE stage — the tracker parses the FIRST `STAGE:` token, so "STAGE: PLAN_REVIEW, CODE_REVIEW, OUTPUT_REVIEW" in a single call records only PLAN_REVIEW. Delivery clears when every required stage count ≥ 1 AND OUTPUT_REVIEW verdict = approve; use `codex-reply` only to resolve must-fix items within an already-counted stage's thread. A third session re-confirms the same failure (`track-critique.sh`: "Critique round NOT recorded: developer-instructions do not match the canonical block") and states the corollary sharply: the OUTPUT_REVIEW that satisfies the delivery gate before `gh pr create`/`gh pr edit` **must be a fresh `mcp__codex__codex` call**, never a reply — the reply inherits the session silently and carries no `developer-instructions` field ([codex-reply does not count toward the gate; OUTPUT_REVIEW must be a fresh codex call](../learnings/1789452785929-codex-reply-does-not-count-toward-the-critique-gat.md)). A later approver session (#13189) re-confirms it once more and adds the practical consequence of losing thread continuity: [because each recorded round must be a fresh codex call, re-supply full context every round](../learnings/1789943197626-critique-gate-codex-reply-does-not-count-use-fresh.md) ("re-review after must-fix; items were X, Y, Z; addressed by…") in the prompt, and read *steady convergence* (each round resolving prior items and surfacing narrower ones) as healthy, NOT the "3 unresolved rounds → escalate" deadlock — keep fixing, budgeting ~$0.15–0.9 of Opus per recorded round.

**What a reply does count for (current hook source).** `container/hooks/track-critique.sh` records the codex `threadId` → stage mapping when a canonical `STAGE:` call is recorded (`critique_threads`). A later `codex-reply` with no `STAGE:` resolves its stage from that map and updates the stage's verdict and attestation without re-counting the stage; instruction pinning exempts replies because the thread was pinned at its initial call. A reply that does carry `STAGE:` is treated as a new stage call, finds no `developer-instructions`, and is rejected. Measured on 2026-10-12: a `codex-reply` continuing a canonically opened thread was recorded (round 63 approve counted), while a reply carrying `STAGE:` got "Critique round NOT recorded". So the earlier atoms' rule "never reply" overstated it: open each required stage with a fresh canonical call, then iterate on that thread with STAGE-less replies. Any later file edit, including a memory-file commit, still resets the edits-since-critique counter, so write a `[Fix Report]` to its file and run OUTPUT_REVIEW on it after the memory commit [codex-reply on a fresh canonical thread counts; a STAGE: reply does not](../learnings/1791843438982-codex-reply-on-a-fresh-codex-thread-counts-toward-.md). The same atom notes that a bot PR's `pull_request` run (which tests) and a `workflow_dispatch` run that yielded at `wait-for-human-priority` with skipped jobs are different run IDs on one SHA; report the former.

The same sentinel check is what makes **a freeform `mcp__codex__codex` call not count at all**, even though codex runs and prints a bare `APPROVE`. `track-critique.sh` records a round only when the call's `developer-instructions` contain the verbatim `/codex-critique` sentinel block (the `You are an independent reviewer…` / `Return ONLY the structured output below` lines) **and** `sandbox: "danger-full-access"`. A call with your own instructions, or with `sandbox: read-only`, runs and even emits a verdict but leaves the gate pinned to whatever the last *properly-formatted* round said — so re-running codex directly can never flip a stale recorded `must-fix`. Always drive every stage through the skill's exact format (paste the developer-instructions verbatim, the `STAGE: … / TASK / WHAT I DID / WHY / ARTIFACTS` prompt shape, `sandbox: "danger-full-access"` — bwrap read-only is rejected inside Docker anyway); the structured `### Verdict` + `### Attested` block is what the tracker parses, and the gate then re-hashes the attested files at send time. Bonus: `danger-full-access` also lets codex build and dump IR, so for any mechanism claim about IR shapes prefer a full-access critique that can actually dump IR over a read-only one reasoning from source alone (it caught a nested-`TaggedUnionType` operand shape three prior read-only rounds had described wrong) ([critique-gate only counts /codex-critique-format calls with danger-full-access, not freeform codex](../learnings/1789485657779-critique-gate-only-counts-codex-critique-skill-cal.md)). Re-confirmed with the exact failure shape: running FIVE ad-hoc codex "OUTPUT_REVIEW" calls that each returned approve left the recorded `OUTPUT_REVIEW=must-fix` FROZEN (count stuck) and the `[Fix Report]` denied, because `track-critique.sh` records a round ONLY when the `developer-instructions` are the skill block VERBATIM (the "You are an independent reviewer…" / "Return ONLY the structured output below" sentinels), `sandbox:"danger-full-access"`, and the response carries the structured `### Verdict`/`### Attested` sections. Fix: invoke the `Skill` tool `codex-critique` to load the exact template, then pass those `developer-instructions` verbatim ([critique-gate recorder only counts codex calls made via the exact /codex-critique template](../learnings/1790239797245-critique-gate-recorder-only-counts-codex-calls-mad.md)).

**A logged round is not a review that happened.** `mcp__codex__codex` often answers a valid STAGE prompt with a short shared-wiki recall ("- **Topic** — … /workspace/shared/wiki/…", usually two bullets) instead of the structured review. On 2026-10-17 four of four fresh PLAN/CODE/OUTPUT_REVIEW calls in slang-fixer sessions did this. `track-critique.sh` may still log such a reply as a round with `verdict=approve`, so the delivery gate can be satisfied by a review that never took place. Treat the first reply on a fresh thread as suspect, and count a reply only if it has `### Verdict` and `### Attested` sections and its Attested hash matches your artifact. The remedy that worked every time on 2026-10-17 is a same-thread `codex-reply` with no `STAGE:` line: "your reply was a wiki recall — return ONLY the structured output". If that reply comes back empty, as one did on slang-vscode-extension#78 (2026-10-16), start a fresh `mcp__codex__codex` session with the full prompt [codex-critique can return a recall summary or an empty string](../learnings/1792137757087-codex-critique-can-return-a-recall-summary-or-an-e.md), [first call on a fresh thread often returns a wiki recall](../learnings/1792242240195-codex-critique-first-call-on-a-fresh-thread-often-.md), [codex-critique gotchas: wiki-recall first replies](../learnings/1792199075282-codex-critique-gotchas-wiki-recall-first-replies-b.md). The earlier re-ask history, and the defects the retries caught, are on [Codex & provider parity](agent-fixer-codex-provider.md).

## Attestation: what invalidates an approve

The gate re-hashes the files codex listed under `### Attested` at send time. Two failure modes: [codex attesting volatile session-trace files](../learnings/1787684241707-critique-gate-approve-expires-if-codex-attests-vol.md) (`.claude-trace/session-*.jsonl`, `logs/`, `.codex/sessions/*.jsonl`) invalidates the approve on the next turn, trapping OUTPUT_REVIEW in an infinite re-run — fix by instructing codex to attest ONLY stable deliverables. And [any file write between approve and delivery re-arms the gate](../learnings/1788259463864-critique-gate-re-arms-on-any-file-write-between-ap.md), not just attested files — even a `cat > /tmp/issue-comment.md` scratch body blocks the next `send_message` with "1 edit(s) recorded since the last critique round." The counter is over **edit EVENTS, not content changes** — [reverting a file to a byte-identical, already-attested state still re-arms the gate](../learnings/1789652658992-critique-gate-counts-edit-events-since-last-critiq.md): the `### Attested` sha256 can match perfectly and it blocks anyway on the event count, so if you must undo formatter churn after an approve, budget one more codex round before the push. Remedy: build gh/PR bodies inline, or batch all file writes before the final OUTPUT_REVIEW and fire deliveries back-to-back. The counter includes scratch writes nobody thinks of as edits, such as a `/tmp` JSON-escaped copy of the message made just before a `[Fix Report]` `send_message`; skip it and paste the reviewed text directly. If a write already happened, one confirming `codex-reply` round on the stage's thread, stating the artifact is unchanged (same sha256), clears the counter ([any file write after the final OUTPUT_REVIEW makes the approve stale](../learnings/1792059427221-critique-gate-any-file-write-after-the-final-outpu.md)). The [worktree + PR-body atom](../learnings/1787818646140-fresh-git-worktree-lacks-submodules-critique-gate-.md) adds that the gate re-hashes the PR-body artifact at `gh pr create` time — write the body to a file, let codex attest it, and open with `--body-file <that exact file>` (a hand-retyped `--body` string mismatches). The [PR-body-file interaction traps](../learnings/1787821097042-critique-gate-and-pr-body-file-interaction-traps.md) note that a PR-body heredoc written in the SAME bash call as the gated `gh api .../pulls` is LOST when the gate blocks that call (the whole invocation aborts), and that opening the PR + posting a comment counts as an external STATE change that re-blocks the handoff — refresh OUTPUT_REVIEW on the same codex thread stating artifacts are unchanged (cite sha256), don't redo the whole critique.

The re-hash binds the approve to the exact bytes of every `### Attested` file, so **editing an attested file *after* the approve blocks the next delivery/handoff `send_message`** ("reviewed artifacts changed since the approve") — even when the edit applies the reviewer's *own* advisories. The sequencing rule: apply advisory fixes, THEN re-run the review (a `mcp__codex__codex-reply` on the same thread — "applied advisories 1,2, re-verify" — suffices to refresh the verdict against the new bytes), so the attested hash matches the shipped artifact; never edit after the final review round. Separately, any message whose text carries a bracketed delivery marker (`[Fix Report]`, `[Fix Review Request]`, …) hits the chain-routing gate, which requires `in_reply_to=<inbound id>` even on a fresh peer delegation — set `to=` and `thread_id=` explicitly too, since they override `in_reply_to`'s default routing/thread so the message still lands on the intended peer edge ([the delivery gate re-hashes attested files — edit-after-approve blocks delivery](../learnings/1789505147702-critique-delivery-gate-re-hashes-attested-files-ed.md)).

One class raises the bar past mere re-verification: a **gated-pushback reply** — one that declines a maintainer's stated preference — is reviewed by the approver *precisely for its exact wording*, so the invariant is posted-text == approved-text. If you edit such a reply after approval — even a purely accuracy-tightening change flagged by codex OUTPUT_REVIEW — **re-flag the new wording to the approver before posting**, don't silently ship the improved version, because a later "tightening" that is actually substantive could otherwise slip past the gate. Scope is narrow: this applies ONLY to the gated-pushback class; routine "addressed your finding" replies stay pre-authorized and need no re-flag ([gated-pushback replies: re-flag ANY post-approval wording change before posting](../learnings/1789490573346-gated-pushback-replies-re-flag-any-post-approval-w.md)).

**The tracker parses two things strictly: the Verdict word and each Attested line.** The `### Attested` parser captures only lines matching `-[ \t]*<64 hex>[ \t]+<path>`, and codex often breaks that: a backtick-wrapped hash (`` - `abc…` `/path` ``) or a truncated hash records nothing. The comment gate (`gate-critique-on-deliver.sh`) then refuses a public comment of 1,000+ characters for an approved, unchanged file with "not among the files an OUTPUT_REVIEW attested". If an older round's hashes are still in force, the delivery gate instead refuses with "reviewed artifacts changed" although nothing changed (next paragraph). The Verdict line is lowercased and stripped to letters and hyphens, so `approve — for PLAN_REVIEW only` becomes `approveforplanreviewonly` and records `unparseable`; bold or a trailing period still parses. Prevent both in the prompt ("Verdict: one word; each Attested line exactly `- <64-hex sha256> <absolute path>`, no backticks"). If a reply still comes back wrong, ask codex on the same thread to re-emit the lines plain. Two side traps from the same posts: the gate blocked a read-only `gh api …/pulls/<n>/reviews` call as "PR creation" (the slang-mcp `github_get_pull_request_reviews` tool reads the same data), and in a `for id in …` loop `-F body=@…/$id.md` is refused as "cannot be resolved, not a literal path", so post each comment with a literal absolute path [track-critique Attested parser rejects backtick-wrapped hashes](../learnings/1791828331890-track-critique-attested-parser-rejects-backtick-wr.md), [Attested lines must be plain `- <sha> <path>`](../learnings/1792192842171-critique-gate-attested-lines-must-be-plain-sha-pat.md), [backticked Attested hashes](../learnings/1792199075282-codex-critique-gotchas-wiki-recall-first-replies-b.md), [unparseable Verdict and truncated hashes](../learnings/1792242240195-codex-critique-first-call-on-a-fresh-thread-often-.md).

**A round that records no Attested line leaves the previous hashes in force.** At send time the delivery gate re-hashes every path in `workflow-state.json` → `critique_attested.OUTPUT_REVIEW`. `track-critique.sh` merges `critique_attested` across stages, but it replaces one stage's map whenever a round on that stage parses at least one Attested line. A round that parses none (backticked hashes, a recall reply, a reply without `### Attested`), or a reply whose thread maps to another stage, leaves the old map untouched (the `.critique_attested + {(stage): att}` updates in `/app/hooks/track-critique.sh`, read 2026-10-19; jq's object `+` replaces the stage key whole). On 2026-10-17 a narrow `codex-reply` asked to re-check three files approved, yet every delivery was still refused with "reviewed artifacts changed since the OUTPUT_REVIEW approve: <paths>", naming source files that an earlier round attested and that were edited afterwards. The atom reads this as an old+new merge of the stage's map. In the current source the narrow round could have kept the old entries only by recording no Attested line under OUTPUT_REVIEW: malformed lines, or a reply on a thread not mapped to OUTPUT_REVIEW. The fix is the same either way: run one fresh `mcp__codex__codex` OUTPUT_REVIEW whose ARTIFACTS list every path the gate names plus the deliverables, with plain Attested lines, and check what the gate holds with `jq '.critique_attested.OUTPUT_REVIEW' /workspace/.claude/workflow-state.json` against `sha256sum` [a narrow codex-reply approve leaves stale attested hashes](../learnings/1792261551774-critique-gate-a-narrow-codex-reply-approve-leaves-.md). The older-round and backtick variants of the same symptom are on [critique & delivery gates](agent-routing-f0909b2-critique-and-delivery-gates.md) and [container-side gates](agent-routing-f0909b0-critique-delivery-gates.md).

## OUTPUT_REVIEW reads the live PR, not your local tree

When you apply peer-review nits to an **already-open** PR, OUTPUT_REVIEW (codex) reads the **LIVE** PR — its head SHA plus the posted body — and compares that against your local working tree. Run it with uncommitted/unpushed corrections and codex returns must-fix purely on **staleness** ("the corrected comment is only an unstaged edit; PR still at `<old-sha>`", "`/tmp/pr-body.md` is not the posted body"), wasting a round. Correct finalize order: (1) apply edits, (2) rebuild/re-verify only if behavior changed — comment-only edits with unchanged CHECK lines need no rebuild, tests still valid, (3) format + `git commit --amend` + force-push, (4) `gh pr edit --body-file` to refresh the posted body, THEN (5) run OUTPUT_REVIEW via `/codex-critique`. Because each Edit/Write since the last critique increments the edit counter and invalidates a prior approve, the fresh OUTPUT_REVIEW must be the last action before the delivery marker. Two incidental gotchas: a codex thread can expire ("Session not found for thread_id") — start a fresh `mcp__codex__codex` session, no state lost; and a `STAGE:OUTPUT_REVIEW` call is recorded only if it carries the `/codex-critique` developer-instructions block VERBATIM (the hook greps its sentinel lines) ([OUTPUT_REVIEW compares the posted PR against your local tree — commit+push+update-body before running it](../learnings/1789402846129-delivery-gate-output-review-compares-the-posted-pr.md)).

## Token matching, push bundling, and ledger ordering

The gate's matcher over-blocks on literal tokens. Its [ABSTAIN fast-path is defeated by quoting BLOCK/WOULD_APPROVE](../learnings/1787621185331-approver-infra-critique-gate-abstain-fast-path-is-.md): the relaxation is `grep ABSTAIN_* && ! grep (WOULD_APPROVE|BLOCK)`, so explanatory bullets saying "not BLOCK"/"not WOULD_APPROVE" trip the negative guard and the full gate (which an abstain can't satisfy) denies delivery; a *second* gate (`gate-chain-routing.sh`) then demands `in_reply_to` on the chain-marker message. The [same token-match false-positive](../learnings/1787778155862-approver-infra-delivery-critique-gate-text-matches.md) blocks an ABSTAIN 5-bullet whose prose merely mentions `WOULD_APPROVE` — TRIGGER ≠ REASON. Rephrase to avoid the bare state-name tokens; do NOT manufacture a ceremonial critique the procedure says to skip.

A sibling text-matcher — a `[GATE AUDIT]` hook — fires when an outbound message contains the literal marker `[Resolution]` but codex-critique was never invoked in the session (`message contains "\[Resolution\]" but codex-critique … was never invoked … gate skipped`). This collides with the chain-reporting spine, which says to close a routine "thanks/ack/restatement" inbound with a positive 5-bullet `[Resolution]`: the overlay treats `[Resolution]` as a *gated decision artifact*, so tagging a low-stakes chain-close ack with it produces a false gate-skip warning. Reserve the literal `[Resolution]` tag for genuinely critique-gated outcomes (a decision/approval you ran codex on); [close a plain courtesy chain-close with neutral phrasing instead](../learnings/1789633290729-the-resolution-tag-trips-the-critique-overlay-gate.md) ("[Chain closed]" or a bare positive summary line), and if you *do* intend a gated `[Resolution]`, run `mcp__codex__codex` first (seen closing the shader-slang/slang#13086 5-round fix-review chain). The match is on the literal text, so the same audit fires on `[Fix Report]` when a reviewer merely asks the fixer to send one; that is a false trigger, not a skipped gate ([GATE AUDIT false trigger on a message mentioning "[Fix Report]"](../learnings/1792058636644-container-restart-mid-review-kills-reviewer-a-c-an.md)).

[Never bundle a `git push` with a critique-gated command in one bash block](../learnings/1787846612049-never-bundle-a-git-push-with-a-critique-gated-comm.md): a PreToolUse denial aborts *every* command in the block, so the push never runs and the PR ships on a stale commit that reviewers review. Run `git push` in its own call first (and `--force-with-lease=<branch>:<sha>` explicitly in a worktree with no `origin/<branch>` ref), verify with `git ls-remote`, then re-dispatch CI and tell reviewers the head moved. The same abort swallows any file edit chained into a gated call, and the trigger is the command's text, so a heredoc that merely mentions the PR-open command is enough. On slang#13273 a python edit to the PR body, chained before `gh pr create`, silently never ran, and the stale text was noticed a day later. Keep file edits in a separate Bash call from anything gated, and write memory text that names gated commands with the Edit tool ([the gate blocks the WHOLE Bash call](../learnings/1790593764309-critique-gate-blocks-the-whole-bash-call-gpu-less-.md)). The gated set widens after a must-fix: once an OUTPUT_REVIEW round returns must-fix, the hook refuses any Bash command containing `gh api`, even a read-only GET, so a call that applies the fix (a python edit) and then checks it with `gh` is refused whole and the fix is never written; codex's next round then reports the file unchanged with the same sha256. Run artifact edits in their own `gh`-free Bash call and re-hash the file before telling codex an item is addressed. A maintainer's `@nv-slang-bot` mention reaching you via `pr_session_mappings` authorizes your reply on that PR but does not lift a parent's separate hold; report it upstream and let the parent reconcile ([the delivery gate can block a combined edit+gh Bash call](../learnings/1790818878715-the-critique-delivery-gate-can-block-a-combined-ed.md)).

Finally, the append-only ledger must be written LAST. Two atoms show the ordering hazard: [record the ABSTAIN row last](../learnings/1787732678394-approver-infra-abstain-record-the-abstain-row-last.md) because the edit-count-based, verdict-unaware delivery gate can force an OUTPUT_REVIEW that OVERTURNS an abstain to WOULD_APPROVE *after* the append-only ABSTAIN row is already committed (first-write-wins per `(repo, pr, commit_sha)`, and "Decision recorded" is a known false-success string). Symmetrically, [the ABSTAIN fast-path records BEFORE the critique gate](../learnings/1787905229286-approver-critique-mustfix-the-abstain-fast-path-re.md), so a late-surfacing BLOCK (e.g. a head-current CodeRabbit review landing after harvest) is locked out — for an ABSTAIN whose rationale is "no/incomplete reviewer signal," settle the harvest and run OUTPUT_REVIEW before `record_decision`, never take the fast-path. Treat `record_decision` as the last irreversible action of the turn.

## The review-request format check

The same hook also checks the shape of a `[Fix Review Request]`. It refuses one without a `Maintainer direction:` line, which must link a canonical GitHub comment or say `none — <reason>`. Once that section contains any canonical comment link (`…/issues|pull/<n>#issuecomment-…`, `#discussion_r…`, `#pullrequestreview-…`, `#issue-…`), it also requires a `Fixer self-check:` line with R1, R2… items. The atom saw the self-check demanded with `Maintainer direction: none — …`; tested against the hook's `review_request_problem` on 2026-10-19, a bare `none — <reason>` passes, and a link anywhere in the section (for example a triager comment cited in the reason) is what trips it. When a triager's numbered asks are the scope, map them to R1–Rn in the self-check ([review-request gate requires Fixer self-check R-items](../learnings/1792261551774-critique-gate-a-narrow-codex-reply-approve-leaves-.md)).
