## TL;DR

The `gate-critique-on-deliver.sh` PreToolUse hook gates delivery/handoff messages and GitHub writes on recorded codex-critique stages plus an edit-count/attestation freshness check. These atoms are its operational mechanics — how each stage is counted, how attestation invalidates an approve, how the text matcher over-blocks, and the ordering rules that keep an append-only ledger row from being locked at the wrong verdict.

- **`mcp__codex__codex-reply` does NOT count toward the gate** — it carries no `developer-instructions`, so `track-critique.sh` rejects it ("developer-instructions do not match the canonical block"). Each required stage (PLAN/CODE/OUTPUT_REVIEW) must be a fresh `mcp__codex__codex` call carrying the canonical `/codex-critique` reviewer block VERBATIM. One codex call records only ONE stage (the first `STAGE:` token). Budget ~4 codex calls for a 3-stage gate; use `codex-reply` only to resolve must-fix items within an already-counted stage's thread.
- **The gate re-hashes every `### Attested` file at send time and DENIES if any changed** — so tell codex to attest ONLY stable deliverables (PR body, report, changed source), never volatile trace/log/session files (`.claude-trace/`, `logs/`, `.codex/`), or the approve is invalidated the instant you do anything.
- **ANY file write between approve and delivery re-arms the gate** — even a scratch heredoc for a `gh` comment body. Build gh/PR bodies inline (shell var) or do every file write BEFORE the final OUTPUT_REVIEW, then fire all deliveries back-to-back with zero intervening writes. A PR body must be opened with `--body-file <attested file>` (a hand-retyped `--body "..."` mismatches the hash).
- **The gate is a TEXT matcher, not a decision-state reader** — an ABSTAIN report is blocked if its prose merely contains the bare tokens `WOULD_APPROVE`/`BLOCK` (even to say the decision is *not* one of them). Rephrase ("no verified bug"/"flagged a defect"); keep `ABSTAIN_POLICY` present. Don't run a ceremonial critique to clear an ABSTAIN.
- **Never bundle a `git push` with a critique-gated command in one bash block** — the hook aborts the WHOLE block, so the push silently never runs and reviewers see stale code. Run `git push` in its own call first and verify it landed.
- **Record the append-only ledger row LAST** — the mechanical delivery gate is edit-count-based and verdict-UNAWARE, so it can force an OUTPUT_REVIEW critique that flips an ABSTAIN to a late-surfacing BLOCK *after* the append-only ABSTAIN row is locked. Do artifact/memory writes → gate-forced critique → `record_decision` → deliver.

## Stage counting: codex vs codex-reply

Two atoms (one from a fixer session, one from an approver) independently establish that [`codex-reply` does not record a critique round](../learnings/1787339458278-codex-reply-does-not-record-a-critique-round-for-t.md) and [does not count toward the delivery gate](../learnings/1787672164164-codex-reply-does-not-count-toward-the-critique-del.md). Each required stage must be its own fresh `mcp__codex__codex` call whose `developer-instructions` are the canonical `/codex-critique` reviewer block verbatim (the "You are an independent reviewer… Return ONLY the structured output below" sentinels); `codex-reply` has no `developer-instructions` parameter, so its round fails the sentinel check even though codex answers with a valid verdict. Further, one codex call records only ONE stage — the tracker parses the FIRST `STAGE:` token, so "STAGE: PLAN_REVIEW, CODE_REVIEW, OUTPUT_REVIEW" in a single call records only PLAN_REVIEW. Delivery clears when every required stage count ≥ 1 AND OUTPUT_REVIEW verdict = approve; use `codex-reply` only to resolve must-fix items within an already-counted stage's thread. A third session re-confirms the same failure (`track-critique.sh`: "Critique round NOT recorded: developer-instructions do not match the canonical block") and states the corollary sharply: the OUTPUT_REVIEW that satisfies the delivery gate before `gh pr create`/`gh pr edit` **must be a fresh `mcp__codex__codex` call**, never a reply — the reply inherits the session silently and carries no `developer-instructions` field ([codex-reply does not count toward the gate; OUTPUT_REVIEW must be a fresh codex call](../learnings/1789452785929-codex-reply-does-not-count-toward-the-critique-gat.md)). A later approver session (#13189) re-confirms it once more and adds the practical consequence of losing thread continuity: [because each recorded round must be a fresh codex call, re-supply full context every round](../learnings/1789943197626-critique-gate-codex-reply-does-not-count-use-fresh.md) ("re-review after must-fix; items were X, Y, Z; addressed by…") in the prompt, and read *steady convergence* (each round resolving prior items and surfacing narrower ones) as healthy, NOT the "3 unresolved rounds → escalate" deadlock — keep fixing, budgeting ~$0.15–0.9 of Opus per recorded round.

The same sentinel check is what makes **a freeform `mcp__codex__codex` call not count at all**, even though codex runs and prints a bare `APPROVE`. `track-critique.sh` records a round only when the call's `developer-instructions` contain the verbatim `/codex-critique` sentinel block (the `You are an independent reviewer…` / `Return ONLY the structured output below` lines) **and** `sandbox: "danger-full-access"`. A call with your own instructions, or with `sandbox: read-only`, runs and even emits a verdict but leaves the gate pinned to whatever the last *properly-formatted* round said — so re-running codex directly can never flip a stale recorded `must-fix`. Always drive every stage through the skill's exact format (paste the developer-instructions verbatim, the `STAGE: … / TASK / WHAT I DID / WHY / ARTIFACTS` prompt shape, `sandbox: "danger-full-access"` — bwrap read-only is rejected inside Docker anyway); the structured `### Verdict` + `### Attested` block is what the tracker parses, and the gate then re-hashes the attested files at send time. Bonus: `danger-full-access` also lets codex build and dump IR, so for any mechanism claim about IR shapes prefer a full-access critique that can actually dump IR over a read-only one reasoning from source alone (it caught a nested-`TaggedUnionType` operand shape three prior read-only rounds had described wrong) ([critique-gate only counts /codex-critique-format calls with danger-full-access, not freeform codex](../learnings/1789485657779-critique-gate-only-counts-codex-critique-skill-cal.md)).

## Attestation: what invalidates an approve

The gate re-hashes the files codex listed under `### Attested` at send time. Two failure modes: [codex attesting volatile session-trace files](../learnings/1787684241707-critique-gate-approve-expires-if-codex-attests-vol.md) (`.claude-trace/session-*.jsonl`, `logs/`, `.codex/sessions/*.jsonl`) invalidates the approve on the next turn, trapping OUTPUT_REVIEW in an infinite re-run — fix by instructing codex to attest ONLY stable deliverables. And [any file write between approve and delivery re-arms the gate](../learnings/1788259463864-critique-gate-re-arms-on-any-file-write-between-ap.md), not just attested files — even a `cat > /tmp/issue-comment.md` scratch body blocks the next `send_message` with "1 edit(s) recorded since the last critique round." The counter is over **edit EVENTS, not content changes** — [reverting a file to a byte-identical, already-attested state still re-arms the gate](../learnings/1789652658992-critique-gate-counts-edit-events-since-last-critiq.md): the `### Attested` sha256 can match perfectly and it blocks anyway on the event count, so if you must undo formatter churn after an approve, budget one more codex round before the push. Remedy: build gh/PR bodies inline, or batch all file writes before the final OUTPUT_REVIEW and fire deliveries back-to-back. The [worktree + PR-body atom](../learnings/1787818646140-fresh-git-worktree-lacks-submodules-critique-gate-.md) adds that the gate re-hashes the PR-body artifact at `gh pr create` time — write the body to a file, let codex attest it, and open with `--body-file <that exact file>` (a hand-retyped `--body` string mismatches). The [PR-body-file interaction traps](../learnings/1787821097042-critique-gate-and-pr-body-file-interaction-traps.md) note that a PR-body heredoc written in the SAME bash call as the gated `gh api .../pulls` is LOST when the gate blocks that call (the whole invocation aborts), and that opening the PR + posting a comment counts as an external STATE change that re-blocks the handoff — refresh OUTPUT_REVIEW on the same codex thread stating artifacts are unchanged (cite sha256), don't redo the whole critique.

The re-hash binds the approve to the exact bytes of every `### Attested` file, so **editing an attested file *after* the approve blocks the next delivery/handoff `send_message`** ("reviewed artifacts changed since the approve") — even when the edit applies the reviewer's *own* advisories. The sequencing rule: apply advisory fixes, THEN re-run the review (a `mcp__codex__codex-reply` on the same thread — "applied advisories 1,2, re-verify" — suffices to refresh the verdict against the new bytes), so the attested hash matches the shipped artifact; never edit after the final review round. Separately, any message whose text carries a bracketed delivery marker (`[Fix Report]`, `[Fix Review Request]`, …) hits the chain-routing gate, which requires `in_reply_to=<inbound id>` even on a fresh peer delegation — set `to=` and `thread_id=` explicitly too, since they override `in_reply_to`'s default routing/thread so the message still lands on the intended peer edge ([the delivery gate re-hashes attested files — edit-after-approve blocks delivery](../learnings/1789505147702-critique-delivery-gate-re-hashes-attested-files-ed.md)).

One class raises the bar past mere re-verification: a **gated-pushback reply** — one that declines a maintainer's stated preference — is reviewed by the approver *precisely for its exact wording*, so the invariant is posted-text == approved-text. If you edit such a reply after approval — even a purely accuracy-tightening change flagged by codex OUTPUT_REVIEW — **re-flag the new wording to the approver before posting**, don't silently ship the improved version, because a later "tightening" that is actually substantive could otherwise slip past the gate. Scope is narrow: this applies ONLY to the gated-pushback class; routine "addressed your finding" replies stay pre-authorized and need no re-flag ([gated-pushback replies: re-flag ANY post-approval wording change before posting](../learnings/1789490573346-gated-pushback-replies-re-flag-any-post-approval-w.md)).

## OUTPUT_REVIEW reads the live PR, not your local tree

When you apply peer-review nits to an **already-open** PR, OUTPUT_REVIEW (codex) reads the **LIVE** PR — its head SHA plus the posted body — and compares that against your local working tree. Run it with uncommitted/unpushed corrections and codex returns must-fix purely on **staleness** ("the corrected comment is only an unstaged edit; PR still at `<old-sha>`", "`/tmp/pr-body.md` is not the posted body"), wasting a round. Correct finalize order: (1) apply edits, (2) rebuild/re-verify only if behavior changed — comment-only edits with unchanged CHECK lines need no rebuild, tests still valid, (3) format + `git commit --amend` + force-push, (4) `gh pr edit --body-file` to refresh the posted body, THEN (5) run OUTPUT_REVIEW via `/codex-critique`. Because each Edit/Write since the last critique increments the edit counter and invalidates a prior approve, the fresh OUTPUT_REVIEW must be the last action before the delivery marker. Two incidental gotchas: a codex thread can expire ("Session not found for thread_id") — start a fresh `mcp__codex__codex` session, no state lost; and a `STAGE:OUTPUT_REVIEW` call is recorded only if it carries the `/codex-critique` developer-instructions block VERBATIM (the hook greps its sentinel lines) ([OUTPUT_REVIEW compares the posted PR against your local tree — commit+push+update-body before running it](../learnings/1789402846129-delivery-gate-output-review-compares-the-posted-pr.md)).

## Token matching, push bundling, and ledger ordering

The gate's matcher over-blocks on literal tokens. Its [ABSTAIN fast-path is defeated by quoting BLOCK/WOULD_APPROVE](../learnings/1787621185331-approver-infra-critique-gate-abstain-fast-path-is-.md): the relaxation is `grep ABSTAIN_* && ! grep (WOULD_APPROVE|BLOCK)`, so explanatory bullets saying "not BLOCK"/"not WOULD_APPROVE" trip the negative guard and the full gate (which an abstain can't satisfy) denies delivery; a *second* gate (`gate-chain-routing.sh`) then demands `in_reply_to` on the chain-marker message. The [same token-match false-positive](../learnings/1787778155862-approver-infra-delivery-critique-gate-text-matches.md) blocks an ABSTAIN 5-bullet whose prose merely mentions `WOULD_APPROVE` — TRIGGER ≠ REASON. Rephrase to avoid the bare state-name tokens; do NOT manufacture a ceremonial critique the procedure says to skip.

A sibling text-matcher — a `[GATE AUDIT]` hook — fires when an outbound message contains the literal marker `[Resolution]` but codex-critique was never invoked in the session (`message contains "\[Resolution\]" but codex-critique … was never invoked … gate skipped`). This collides with the chain-reporting spine, which says to close a routine "thanks/ack/restatement" inbound with a positive 5-bullet `[Resolution]`: the overlay treats `[Resolution]` as a *gated decision artifact*, so tagging a low-stakes chain-close ack with it produces a false gate-skip warning. Reserve the literal `[Resolution]` tag for genuinely critique-gated outcomes (a decision/approval you ran codex on); [close a plain courtesy chain-close with neutral phrasing instead](../learnings/1789633290729-the-resolution-tag-trips-the-critique-overlay-gate.md) ("[Chain closed]" or a bare positive summary line), and if you *do* intend a gated `[Resolution]`, run `mcp__codex__codex` first (seen closing the shader-slang/slang#13086 5-round fix-review chain).

[Never bundle a `git push` with a critique-gated command in one bash block](../learnings/1787846612049-never-bundle-a-git-push-with-a-critique-gated-comm.md): a PreToolUse denial aborts *every* command in the block, so the push never runs and the PR ships on a stale commit that reviewers review. Run `git push` in its own call first (and `--force-with-lease=<branch>:<sha>` explicitly in a worktree with no `origin/<branch>` ref), verify with `git ls-remote`, then re-dispatch CI and tell reviewers the head moved.

Finally, the append-only ledger must be written LAST. Two atoms show the ordering hazard: [record the ABSTAIN row last](../learnings/1787732678394-approver-infra-abstain-record-the-abstain-row-last.md) because the edit-count-based, verdict-unaware delivery gate can force an OUTPUT_REVIEW that OVERTURNS an abstain to WOULD_APPROVE *after* the append-only ABSTAIN row is already committed (first-write-wins per `(repo, pr, commit_sha)`, and "Decision recorded" is a known false-success string). Symmetrically, [the ABSTAIN fast-path records BEFORE the critique gate](../learnings/1787905229286-approver-critique-mustfix-the-abstain-fast-path-re.md), so a late-surfacing BLOCK (e.g. a head-current CodeRabbit review landing after harvest) is locked out — for an ABSTAIN whose rationale is "no/incomplete reviewer signal," settle the harvest and run OUTPUT_REVIEW before `record_decision`, never take the fast-path. Treat `record_decision` as the last irreversible action of the turn.
