# Critique-gate mechanics — stage counting, attestation, and the live-PR read

## TL;DR

The `gate-critique-on-deliver.sh` PreToolUse hook gates delivery/handoff messages and GitHub writes on recorded codex-critique stages plus an edit-count/attestation freshness check. This page owns stage counting, attestation and the live-PR read; token matching, denial-abort mechanics, push bundling, ledger ordering and the review-request format are on [token matching & delivery formats](agent-routing-f0909b1-critique-gate-token-matching.md); the edit-event counter, ABSTAIN tokens, read-only `gh` workarounds and chain routing are on [critique and delivery gates](agent-routing-f0909b2-critique-and-delivery-gates.md); the fails-open recorder and recall stubs on [critique gate and decision recording](review-critique-gate-and-recording.md).

- **Open each stage with a fresh canonical `mcp__codex__codex` call** (`/codex-critique` developer-instructions verbatim, `sandbox: "danger-full-access"`); one call records only its first `STAGE:` token, so budget ~4 calls for 3 stages. A same-thread `codex-reply` with **no** `STAGE:` line updates that stage's verdict; a `STAGE:` reply, a freeform or a read-only call records nothing — and recording is name-exact (`mcp__codex__codex` + `developer-instructions`; opencode's `codex_codex` alias records nothing), so verify `jq .critique_stages` after every round. Fixer rounds (`ROUND:` + `REQUIREMENTS:`) are safest as fresh calls. Recording-name matching, bridge-dispatch reliability (app-server deaths, `setsid` vs `nohup`), hung-`gh api` rounds and state-reset recovery: [codex-critique recording reliability](agent-routing-codex-critique-recording-reliability.md).

- **Read the reply before trusting the gate.** Any reply is logged as a round, even a wiki-recall summary or an empty string. Prevent recall with `cwd` outside `/workspace/agent` plus "skip any workspace recall step"; recover with a same-thread reply asking for the structured output. Count only a reply whose `### Verdict` + `### Attested` match your artifact's hash.

- **Ask for plain formats up front:** a one-word Verdict and Attested lines exactly `- <64hex> <absolute-path>` (backticked or truncated hashes record nothing). Attest only stable deliverables, never `.claude-trace/`, `logs/` or `.codex/` files.

- **Any file write between approve and delivery re-arms the gate** (edit events, not content). Write everything before the final OUTPUT_REVIEW, open PRs with `--body-file <attested file>`, then deliver back-to-back.

- **A round with no parsed Attested line leaves the previous round's hashes in force.** Check `jq '.critique_attested.OUTPUT_REVIEW'`; fix with one fresh OUTPUT_REVIEW listing every path the gate names.

- **On an open PR, commit, push and refresh the posted body before OUTPUT_REVIEW** — codex reads the live PR.

## Stage counting: codex vs codex-reply

Each stage is completed by a fresh `mcp__codex__codex` call whose `developer-instructions` are the canonical `/codex-critique` block verbatim (its "You are an independent reviewer…" sentinels). The tracker parses only the first `STAGE:` token ("STAGE: PLAN_REVIEW, CODE_REVIEW, OUTPUT_REVIEW" records only PLAN_REVIEW); delivery clears when every required stage count is ≥ 1 and OUTPUT_REVIEW is approve. A reply carrying `STAGE:` has no `developer-instructions` and fails with "Critique round NOT recorded: developer-instructions do not match the canonical block": it [records no round](../learnings/1787339458278-codex-reply-does-not-record-a-critique-round-for-t.md), [does not count toward the gate](../learnings/1787672164164-codex-reply-does-not-count-toward-the-critique-del.md), and the OUTPUT_REVIEW before `gh pr create`/`gh pr edit` [must be a fresh call](../learnings/1789452785929-codex-reply-does-not-count-toward-the-critique-gat.md). The rule in practice: never put a `STAGE:` line in a `codex-reply` prompt — track-critique treats any prompt carrying `STAGE:` as an initial call, which a reply cannot satisfy; start reply prompts with `ROUND: n/3 — addressed …` and let the hook resolve the stage from the threadId map ([reply rounds must not carry a stage marker](../learnings/1794402652579-codex-critique-reply-rounds-must-not-carry-a-stage.md)). Re-confirmed at ~4 rounds' cost on slang#14593 (2026-11-18): the STAGE-carrying reply logged only a "start" event in critique-attempts.jsonl while the gate kept refusing on the stale must-fix ([delivery-gate mechanics](../learnings/1795017778129-delivery-gate-mechanics-codex-reply-must-not-carry.md), [round-dropping gotchas](../learnings/1795020358261-critique-gate-round-dropping-gotchas-no-stage-in-c.md)). Fresh-call prompts [re-supply full context](../learnings/1789943197626-critique-gate-codex-reply-does-not-count-use-fresh.md) ("items were X, Y, Z; addressed by…"); steady convergence (each round resolving prior items, surfacing narrower ones) is healthy, not the "3 unresolved rounds → escalate" deadlock (~$0.15–0.9 of Opus per round, #13189). Re-confirmed 2026-11-20 (slang#14666): a `codex-reply` continuation that omits `developer-instructions` records nothing while the gate keeps refusing "N edit(s) recorded since the last critique round" even though codex just approved ([codex-reply rounds don't record toward the gate](../learnings/1795168733283-codex-reply-rounds-don-t-record-toward-the-critiqu.md)); the resets are also per-context-window — after a context boundary the gate demands all three stages fresh even if they were recorded earlier in the session, and only a fresh `codex` STAGE call records ([/dev/null counts as an edit; per-window stage reset](../learnings/1795196011137-critique-gate-dev-null-counts-as-an-edit-per-windo.md)).

**What a reply does count for.** When a canonical `STAGE:` call is recorded, `container/hooks/track-critique.sh` maps its codex `threadId` to the stage (`critique_threads`); a later STAGE-less `codex-reply` on that thread updates verdict and attestation without re-counting (measured 2026-10-12: a STAGE-less reply recorded as round 63 approve, a `STAGE:` reply not) ([codex-reply on a fresh canonical thread counts; a STAGE: reply does not](../learnings/1791843438982-codex-reply-on-a-fresh-codex-thread-counts-toward-.md)). A later file edit (a memory-file commit too) still resets the edit counter, so run OUTPUT_REVIEW after the memory commit. Same atom: a bot PR's testing `pull_request` run and a `workflow_dispatch` run that yielded at `wait-for-human-priority` are different run IDs on one SHA; report the former. The fixer overlay is stricter: on slangpy-fixer a `codex-reply` round was not recorded, so open every fixer round with a fresh call carrying the verbatim instructions plus `ROUND:` and `REQUIREMENTS:` lines ([fixer rounds need fresh calls](../learnings/1793010303873-slangpy-worktrees-submodule-init-needs-protocol-fi.md); REQUIREMENTS format on [critique gate and decision recording](review-critique-gate-and-recording.md)).

**Freeform calls do not count.** A round is recorded only when `developer-instructions` contain the verbatim sentinel block **and** `sandbox: "danger-full-access"` (bwrap read-only is rejected inside Docker anyway). A call with your own instructions or `sandbox: read-only` may print `APPROVE`, but the gate stays pinned to the last formatted round (five ad-hoc approves left a `must-fix` frozen and the `[Fix Report]` denied). Load the template via `Skill` `codex-critique` and use its `STAGE: … / TASK / WHAT I DID / WHY / ARTIFACTS` shape. Full access also lets codex build and dump IR, so prefer it for IR-shape claims (it caught a nested-`TaggedUnionType` operand shape three read-only rounds got wrong) ([only /codex-critique-format calls with danger-full-access count](../learnings/1789485657779-critique-gate-only-counts-codex-critique-skill-cal.md), [the recorder only counts the exact template](../learnings/1790239797245-critique-gate-recorder-only-counts-codex-calls-mad.md)).

**A logged round is not a review that happened.** `mcp__codex__codex` often answers a valid STAGE prompt with a two-bullet shared-wiki recall (titles and `/workspace/shared/wiki/…` paths) instead of the review, and the hook logs it as a round (3× across stages on 10-23; on slang PR #11387 a verdict-less recall logged as `OUTPUT_REVIEW=approve`) ([3× on 10-23](../learnings/1792748776667-codex-first-reply-in-a-fresh-critique-thread-can-b.md), [hook-logged approve can hide a malformed reply](../learnings/1792758398499-codex-critique-hook-logged-approve-can-hide-a-malf.md)). It stayed the common first reply from October (4 of 4 fresh calls on 10-17) into November (all three stages for slang#14297 on 11-04); an empty string also happens ([recall summary or empty string](../learnings/1792137757087-codex-critique-can-return-a-recall-summary-or-an-e.md), [first call on a fresh thread often returns a wiki recall](../learnings/1792242240195-codex-critique-first-call-on-a-fresh-thread-often-.md), [wiki-recall first replies](../learnings/1792199075282-codex-critique-gotchas-wiki-recall-first-replies-b.md), [recall bullets recorded as approve](../learnings/1792488875310-slang-test-compare-compute-ignores-entry-codex-cri.md), [round 1 recall on all three stages](../learnings/1793815964150-codex-critique-round-1-can-return-a-wiki-recall-su.md)). The mechanism (codex reads the group recall rule from `cwd: /workspace/agent`; the guarded write keeps the previous verdict) is on [critique gate and decision recording](review-critique-gate-and-recording.md).
- *Prevent:* `cwd: "/tmp"` or the worktree plus "Skip any workspace recall step; do the review directly; your first reply must be the structured output" (it worked on the next #14297 stage), or name the exact `VERDICT: approve|must-fix` line in the first prompt ([run with cwd outside /workspace/agent](../learnings/1792695817981-codex-critique-run-with-cwd-outside-workspace-agen.md), [codex OUTPUT_REVIEW can return a wiki-recall digest](../learnings/1793640100680-codex-output-review-can-return-a-wiki-recall-diges.md)).
- *Recover:* a same-thread `mcp__codex__codex-reply` with no `STAGE:` line ("that was a recall lookup, not the review; perform the <STAGE> review now and return ONLY the structured output") got the real review every time and is recorded under the thread's stage ([continue via codex-reply without STAGE](../learnings/1792462132240-codex-critique-gate-fresh-mcp-codex-codex-may-retu.md), [cwd=/workspace/agent returns a recall summary](../learnings/1792429620370-codex-critique-with-cwd-workspace-agent-returns-a-.md), [task-started fixer sessions](../learnings/1793658431464-task-started-fixer-sessions-delivery-gates-want-in.md)); on #14438 (11-10) it took this extra round-trip on 5 of 5 fresh calls, with a reply opening "ROUND: 1/3 — your reply was a recall summary, not the review" ([5 of 5 first calls were recall](../learnings/1794316305654-codex-critique-often-answers-the-first-call-with-a.md)). A "do NOT return a recall summary" line alone did not help; an empty reply needs a fresh full-prompt call; a recovered OUTPUT_REVIEW can keep the stub's attestation (below). Budget one of the 3 rounds for recovery — and count it precisely: the non-answer first reply still counts as round 1 and the recovery `codex-reply` as round 2, leaving only one round for fixes (#14451); write the drafts in their final form before round 1, do the review-dependent GitHub writes (filing the issue, posting a delta) between rounds using exactly the files that were reviewed so their hashes stay unchanged in the final attested round, and put the issue number into the deliverable only after filing, before the last round ([a non-answer first reply still counts as a round](../learnings/1794384327816-codex-critique-a-non-answer-first-reply-still-coun.md)).

Two deliver-hook quirks from the same chain: a Bash heredoc over 1000 bytes counts as an inline public-comment body (append with Edit/Write), and `--body-file "$var"` is refused (literal-path rule on [critique and delivery gates](agent-routing-f0909b2-critique-and-delivery-gates.md)). Re-ask history: [Codex & provider parity](agent-fixer-codex-provider.md).

## Attestation: what invalidates an approve

**The gate re-hashes every `### Attested` file at send time.** Editing one after the approve blocks the next delivery ("reviewed artifacts changed since the approve"), even to apply the reviewer's advisories; apply them first, then refresh with a same-thread `codex-reply` ("applied advisories 1,2, re-verify"); that delivery's marker also needs `in_reply_to` ([edit-after-approve blocks delivery](../learnings/1789505147702-critique-delivery-gate-re-hashes-attested-files-ed.md)). If codex attests volatile session files (`.claude-trace/session-*.jsonl`, `logs/`, `.codex/sessions/*.jsonl`), the approve expires on the next turn and OUTPUT_REVIEW loops forever; tell codex to attest only stable deliverables ([volatile session-trace files](../learnings/1787684241707-critique-gate-approve-expires-if-codex-attests-vol.md)).

**Any file write re-arms the gate, not just attested files** (rule in full on [critique and delivery gates](agent-routing-f0909b2-critique-and-delivery-gates.md)). Instances: a `cat > /tmp/issue-comment.md` scratch body ([any write between approve and delivery](../learnings/1788259463864-critique-gate-re-arms-on-any-file-write-between-ap.md)); a `/tmp` JSON-escaped copy of a `[Fix Report]` (paste the reviewed text directly) ([any write after the final OUTPUT_REVIEW](../learnings/1792059427221-critique-gate-any-file-write-after-the-final-outpu.md)); a byte-identical revert despite matching sha256 (budget one more round if you undo formatter churn) ([edit events, not content](../learnings/1789652658992-critique-gate-counts-edit-events-since-last-critiq.md)); the explain-diff HTML written after the OUTPUT approve ([explain-diff write re-arms](../learnings/1793010303873-slangpy-worktrees-submodule-init-needs-protocol-fi.md)); the deliverable file itself written after the approving round — write the deliverable first, then critique it, then send it unchanged ([codex-reply rounds don't record toward the gate](../learnings/1795168733283-codex-reply-rounds-don-t-record-toward-the-critiqu.md)). If a write already happened, one same-thread `codex-reply` stating the artifact is unchanged (same sha256) clears the counter. A bash call containing ANY `>` redirect counts as an edit and track-edits.sh fires AFTER the whole call completes, so a single command that both records a round and redirects self-poisons the freshness counter — keep the round-recording call redirect-free and deliver in the IMMEDIATE next tool call ([round-dropping gotchas](../learnings/1795020358261-critique-gate-round-dropping-gotchas-no-stage-in-c.md)); the write-regex and no-space workarounds on [recording reliability](agent-routing-codex-critique-recording-reliability.md). The matcher is shape-only: even `> /dev/null` counts as an edit (fix-5667, PR #14666), so run NO redirect-looking bash between the last OUTPUT_REVIEW approve and the marker send — no `sha256sum`, `cat`, or printf-to-/dev/null checks — even when the text is byte-identical to the attested file ([/dev/null counts as an edit](../learnings/1795196011137-critique-gate-dev-null-counts-as-an-edit-per-windo.md)). Long public GitHub comments (≥1000 chars) are posted only from a body file whose sha256 an OUTPUT_REVIEW attested — finalize the body file before the attest round and leave it untouched between the round and the post (the gate re-hashes at send time; the 1000-char limit counts UTF-8 BYTES, not Python len() — a 996-char body with an emoji fails it) ([round-dropping gotchas](../learnings/1795020358261-critique-gate-round-dropping-gotchas-no-stage-in-c.md), [comment gate counts bytes](../learnings/1795196011137-critique-gate-dev-null-counts-as-an-edit-per-windo.md)).

**PR bodies.** The PR-body file is re-hashed at `gh pr create`, so open with `--body-file <the attested file>`; a retyped `--body` mismatches ([worktree + PR-body](../learnings/1787818646140-fresh-git-worktree-lacks-submodules-critique-gate-.md)). A body heredoc in the same call as a gated `gh api .../pulls` is lost when the call is blocked, and opening the PR plus posting a comment re-blocks the handoff; refresh OUTPUT_REVIEW on the same thread citing the unchanged sha256 instead of redoing the critique ([PR-body-file traps](../learnings/1787821097042-critique-gate-and-pr-body-file-interaction-traps.md)).

**Gated-pushback replies** (declining a maintainer's stated preference) are approved for their exact wording, so re-flag any post-approval wording change to the approver before posting, even an accuracy tightening codex flagged; routine "addressed your finding" replies stay pre-authorized ([re-flag any post-approval wording change](../learnings/1789490573346-gated-pushback-replies-re-flag-any-post-approval-w.md)).

**The tracker parses the Verdict word and each Attested line strictly.** Only lines matching `-[ \t]*<64 hex>[ \t]+<path>` are captured; a backtick-wrapped (`` - `abc…` `/path` ``) or truncated hash, both common, records nothing. Side traps: a read-only `gh api …/pulls/<n>/reviews` is blocked as "PR creation" (use slang-mcp `github_get_pull_request_reviews`), and `-F body=@…/$id.md` in a loop is refused as "not a literal path" ([backtick-wrapped hashes rejected](../learnings/1791828331890-track-critique-attested-parser-rejects-backtick-wr.md), [Attested lines must be plain `- <sha> <path>`](../learnings/1792192842171-critique-gate-attested-lines-must-be-plain-sha-pat.md), [backticked Attested hashes](../learnings/1792199075282-codex-critique-gotchas-wiki-recall-first-replies-b.md), [seen again on a slang-rhi triage](../learnings/1792518561170-slang-rhi-d3d11-d3d12-cleartextureuint-sint-are-no.md)). Then the comment gate refuses a 1,000+-char public comment for an approved file ("not among the files an OUTPUT_REVIEW attested", #11387), or, with an older round's hashes in force, delivery says "reviewed artifacts changed" though every sha256 matches (#13887); a same-thread `codex-reply` re-emitting plain Attested lines fixed both with no content change ([backticked Attested lines leave a stale attestation](../learnings/1792747172115-critique-gate-backticked-attested-lines-are-not-re.md), [Attested lines must be plain](../learnings/1792758398499-codex-critique-hook-logged-approve-can-hide-a-malf.md)). The Verdict line is lowercased and stripped to letters and hyphens, so `approve — for PLAN_REVIEW only` records `unparseable`; bold or a trailing period still parses ([unparseable Verdict and truncated hashes](../learnings/1792242240195-codex-critique-first-call-on-a-fresh-thread-often-.md)). The parser maps only the two words `approve`/`must-fix`: a freehand "APPROVE_WITH_NITS" records `unparseable` and the OUTPUT_REVIEW gate then fails closed. With the skill's verbatim `developer-instructions` (sentinels in place) AND `REQUIREMENTS:` URLs carrying anchors (`#issuecomment-<id>`, `#discussion_r<id>`, `#pullrequestreview-<id>`, `#issue-<n>`) the reviewer uses the two-word vocabulary on the first try — never hand-write your own reviewer prompt ([critique rounds record only with pinned developer-instructions and anchored REQUIREMENTS](../learnings/1795154512935-critique-rounds-record-only-with-pinned-developer-.md)). It recurred in November, so: put both formats in the prompt ("Verdict: one word; each Attested line exactly `- <64-hex sha256> <absolute path>`, no backticks"); after any approve check `jq '.critique_attested' /workspace/.claude/workflow-state.json`; if null or stale, ask on the same thread for plain lines or run a fresh OUTPUT_REVIEW carrying that FORMAT NOTE. Codex sometimes garbles a hash (wrong length), so compare with your own `sha256sum`; only `/workspace` paths are re-hashed, so a bad `/tmp` hash is harmless ([codex attested hashes in backticks are not recorded](../learnings/1793610870468-codex-attested-hashes-in-backticks-are-not-recorde.md), [codex wrapping Attested hashes in backticks records no attestation](../learnings/1793659362706-codex-wrapping-attested-hashes-in-backticks-record.md)). On 11-10 a backticked or relative-path Attested line again got a 1,000+-char comment refused despite an approve and a matching hash; the FORMAT NOTE fixed it, and the file was then posted unchanged with `--body-file` ([Attested lines as `- <sha> <absolute path>`](../learnings/1794300949892-public-comment-gate-needs-attested-lines-as-sha-ab.md)).

**A round that records no Attested line leaves the previous hashes in force.** At send time the delivery gate re-hashes every path in `workflow-state.json` → `critique_attested.OUTPUT_REVIEW`. `track-critique.sh` replaces a stage's map (jq object `+`, whole key) only when a round on that stage parses at least one Attested line; a round parsing none (backticked hashes, a recall reply) or a reply mapped to another stage leaves the old map. So a narrow `codex-reply` re-check of three files approved, yet delivery was refused with "reviewed artifacts changed since the OUTPUT_REVIEW approve: <paths>", naming files an earlier round attested and later edited [a narrow codex-reply approve leaves stale attested hashes](../learnings/1792261551774-critique-gate-a-narrow-codex-reply-approve-leaves-.md); a recall-stub first call plus a same-thread reply carrying the real review hit the same refusal with hashes matching ([recall stub](../learnings/1792695817981-codex-critique-run-with-cwd-outside-workspace-agen.md)). A reply whose plain Attested lines parse does refresh it, so check `jq` after any reply. Fix: one fresh OUTPUT_REVIEW whose ARTIFACTS list every path the gate names plus the deliverables, then compare the `jq` map against `sha256sum`. Variants: [critique & delivery gates](agent-routing-f0909b2-critique-and-delivery-gates.md) and [container-side gates](agent-routing-f0909b0-critique-delivery-gates.md).

## OUTPUT_REVIEW reads the live PR, not your local tree

On an open PR, OUTPUT_REVIEW compares the live head SHA and posted body with your tree, so unpushed corrections draw a staleness must-fix ("PR still at `<old-sha>`") and waste a round. Finalize in order: (1) apply edits; (2) rebuild only if behavior changed (comment-only edits with unchanged CHECK lines need none); (3) format, `git commit --amend`, force-push; (4) `gh pr edit --body-file`; (5) OUTPUT_REVIEW last, before the delivery marker. An expired thread ("Session not found") just needs a fresh session ([OUTPUT_REVIEW compares the posted PR against your local tree](../learnings/1789402846129-delivery-gate-output-review-compares-the-posted-pr.md)).
