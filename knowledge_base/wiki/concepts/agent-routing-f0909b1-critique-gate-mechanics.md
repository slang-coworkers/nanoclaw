# Critique / delivery gate mechanics — satisfying it and not tripping it

## TL;DR

The `gate-critique-on-deliver.sh` PreToolUse hook gates delivery/handoff messages and GitHub writes on recorded codex-critique stages plus an edit-count/attestation freshness check. This page covers stage counting, what invalidates an approve, text-matcher over-blocking, and ledger ordering.

- **Open each stage with a fresh canonical `mcp__codex__codex` call** (`/codex-critique` developer-instructions verbatim, `sandbox: "danger-full-access"`); it counts the stage and maps its thread to it. One call records only the first `STAGE:` token; budget ~4 calls for a 3-stage gate. A same-thread `codex-reply` with **no** `STAGE:` line updates that stage's verdict; a `STAGE:` reply is rejected. Freeform or read-only calls record nothing.
- **Read the reply before trusting the gate.** Any reply is logged as a round, even a wiki-recall summary or an empty string. Fix a recall with a STAGE-less same-thread reply asking for only the structured output; count only a reply with `### Verdict` + `### Attested` matching your artifact's hash.
- **Ask for plain formats up front:** a one-word Verdict and Attested lines exactly `- <64hex> <absolute-path>` (backticked or truncated hashes record nothing). Attest only stable deliverables, never `.claude-trace/`, `logs/` or `.codex/` files.
- **Any file write between approve and delivery re-arms the gate** — it counts edit events, not content, so a scratch heredoc or byte-identical revert counts. Write everything before the final OUTPUT_REVIEW, open PRs with `--body-file <attested file>`, then deliver back-to-back.
- **A round with no parsed Attested line leaves the previous round's hashes in force.** Inspect `jq '.critique_attested.OUTPUT_REVIEW'`; fix with one fresh OUTPUT_REVIEW listing every path the gate names plus the deliverables.
- **On an open PR, commit, push and refresh the posted body before OUTPUT_REVIEW** — codex reads the live PR.
- **The gate is a text matcher.** An ABSTAIN report containing bare `WOULD_APPROVE`/`BLOCK` tokens is blocked even when denying them; `[Resolution]`/`[Fix Report]` text trips `[GATE AUDIT]`. Rephrase; don't run a ceremonial critique.
- **A denial aborts the whole Bash call** — never chain `git push` or a file edit with a gated command. After a must-fix, even a read-only `gh api` call is refused.
- **Record the append-only ledger row last:** artifact/memory writes → gate-forced critique → `record_decision` → deliver.
- **A `[Fix Review Request]` whose `Maintainer direction:` section links any GitHub comment also needs `Fixer self-check:` with R1…Rn items.**

## Stage counting: codex vs codex-reply

Each stage is completed by a fresh `mcp__codex__codex` call whose `developer-instructions` are the canonical `/codex-critique` block verbatim (the "You are an independent reviewer… Return ONLY the structured output below" sentinels). The tracker parses only the first `STAGE:` token, so "STAGE: PLAN_REVIEW, CODE_REVIEW, OUTPUT_REVIEW" records only PLAN_REVIEW. Delivery clears when every required stage count is ≥ 1 and OUTPUT_REVIEW is approve. Three sessions first recorded this as "`codex-reply` never counts" — it [records no round](../learnings/1787339458278-codex-reply-does-not-record-a-critique-round-for-t.md), [does not count toward the gate](../learnings/1787672164164-codex-reply-does-not-count-toward-the-critique-del.md), and the OUTPUT_REVIEW before `gh pr create`/`gh pr edit` [must be a fresh call](../learnings/1789452785929-codex-reply-does-not-count-toward-the-critique-gat.md) — because a reply carrying `STAGE:` has no `developer-instructions` and fails with "Critique round NOT recorded: developer-instructions do not match the canonical block". An approver on #13189 added that fresh-call prompts must [re-supply full context](../learnings/1789943197626-critique-gate-codex-reply-does-not-count-use-fresh.md) ("re-review after must-fix; items were X, Y, Z; addressed by…"), and that steady convergence (each round resolving prior items, surfacing narrower ones) is healthy, not the "3 unresolved rounds → escalate" deadlock; keep fixing, at ~$0.15–0.9 of Opus per round.

**What a reply does count for (current hook source).** `container/hooks/track-critique.sh` maps the codex `threadId` to its stage (`critique_threads`) when a canonical `STAGE:` call is recorded; a later STAGE-less `codex-reply` resolves its stage from that map and updates verdict and attestation without re-counting (replies are exempt from instruction pinning because the thread was pinned at its first call). Measured 2026-10-12: a STAGE-less reply on a canonical thread was recorded (round 63 approve) and a `STAGE:` reply was not, so "never reply" overstated it. Any later file edit, including a memory-file commit, still resets the edit counter, so write a `[Fix Report]` to its file and run OUTPUT_REVIEW on it after the memory commit. The same atom notes that a bot PR's `pull_request` run (which tests) and a `workflow_dispatch` run that yielded at `wait-for-human-priority` with skipped jobs are different run IDs on one SHA; report the former ([codex-reply on a fresh canonical thread counts; a STAGE: reply does not](../learnings/1791843438982-codex-reply-on-a-fresh-codex-thread-counts-toward-.md)).

**Freeform calls do not count at all.** A round is recorded only when `developer-instructions` contain the verbatim sentinel block **and** `sandbox: "danger-full-access"` (bwrap read-only is rejected inside Docker anyway). A call with your own instructions or `sandbox: read-only` may print `APPROVE`, but the gate stays pinned to the last properly formatted round: five ad-hoc OUTPUT_REVIEW approves left a recorded `must-fix` frozen and the `[Fix Report]` denied. Load the template with the `Skill` tool `codex-critique` and use its `STAGE: … / TASK / WHAT I DID / WHY / ARTIFACTS` prompt shape. Full access also lets codex build and dump IR, so prefer it for claims about IR shapes — it caught a nested-`TaggedUnionType` operand shape three read-only rounds had described wrong ([only /codex-critique-format calls with danger-full-access count](../learnings/1789485657779-critique-gate-only-counts-codex-critique-skill-cal.md), [the recorder only counts the exact template](../learnings/1790239797245-critique-gate-recorder-only-counts-codex-calls-mad.md)).

**A logged round is not a review that happened.** `mcp__codex__codex` often answers a valid STAGE prompt with a two-bullet shared-wiki recall (titles and `/workspace/shared/wiki/…` paths) instead of the review — four of four fresh slang-fixer calls on 2026-10-17. `track-critique.sh` logs it as a round with whatever verdict it parses (usually `approve`), so a review that never happened can satisfy or block the gate. The cause is codex reading the group recall rule from `cwd: /workspace/agent`; a "do NOT return a recall summary" prompt line did not stop it on slang-vscode-extension#78 (the `cwd` fix is on [critique gate and decision recording](review-critique-gate-and-recording.md)). What has worked every time (10-17, 10-19, 10-20; codex-cli 0.153.4) is a same-thread `mcp__codex__codex-reply` with no `STAGE:` line ("ROUND: 2/3 — your round-1 reply was a recall summary; now perform the actual <STAGE> review and return ONLY the structured output"), recorded under the thread's stage. Don't keep opening new threads; if the reply is empty (slang-vscode-extension#78, 10-16), start a fresh call with the full prompt [recall summary or empty string](../learnings/1792137757087-codex-critique-can-return-a-recall-summary-or-an-e.md), [first call on a fresh thread often returns a wiki recall](../learnings/1792242240195-codex-critique-first-call-on-a-fresh-thread-often-.md), [wiki-recall first replies](../learnings/1792199075282-codex-critique-gotchas-wiki-recall-first-replies-b.md), [continue via codex-reply without STAGE](../learnings/1792462132240-codex-critique-gate-fresh-mcp-codex-codex-may-retu.md), [cwd=/workspace/agent returns a recall summary](../learnings/1792429620370-codex-critique-with-cwd-workspace-agent-returns-a-.md), [recall bullets recorded as approve](../learnings/1792488875310-slang-test-compare-compute-ignores-entry-codex-cri.md). Deliver-hook quirks (10-20): a Bash heredoc over 1000 bytes counts as an inline public-comment body (append with Edit/Write), and `--body-file "$var"` is refused (literal-path rule on [critique and delivery gates](agent-routing-f0909b2-critique-and-delivery-gates.md)). Re-ask history: [Codex & provider parity](agent-fixer-codex-provider.md).

## Attestation: what invalidates an approve

**The gate re-hashes every `### Attested` file at send time.** Editing one after the approve blocks the next delivery ("reviewed artifacts changed since the approve"), even to apply the reviewer's own advisories; apply them first, then refresh with a same-thread `codex-reply` ("applied advisories 1,2, re-verify"). A bracketed delivery marker (`[Fix Report]`, `[Fix Review Request]`, …) also hits the chain-routing gate, which requires `in_reply_to=<inbound id>` even on a fresh peer delegation; set `to=` and `thread_id=` explicitly, since they override `in_reply_to`'s default routing ([edit-after-approve blocks delivery](../learnings/1789505147702-critique-delivery-gate-re-hashes-attested-files-ed.md)). If codex attests volatile session files (`.claude-trace/session-*.jsonl`, `logs/`, `.codex/sessions/*.jsonl`), the approve expires on the next turn and OUTPUT_REVIEW loops forever; tell codex to attest only stable deliverables ([volatile session-trace files](../learnings/1787684241707-critique-gate-approve-expires-if-codex-attests-vol.md)).

**Any file write re-arms the gate, not just attested files** — the counter is over edit events, not content. A `cat > /tmp/issue-comment.md` scratch body blocks the next `send_message` with "1 edit(s) recorded since the last critique round" ([any write between approve and delivery](../learnings/1788259463864-critique-gate-re-arms-on-any-file-write-between-ap.md)); so does a `/tmp` JSON-escaped copy of a `[Fix Report]` (paste the reviewed text directly) ([any write after the final OUTPUT_REVIEW](../learnings/1792059427221-critique-gate-any-file-write-after-the-final-outpu.md)), and a byte-identical revert despite the matching sha256 — budget one more round if you undo formatter churn ([edit events, not content](../learnings/1789652658992-critique-gate-counts-edit-events-since-last-critiq.md)). If a write already happened, one same-thread `codex-reply` stating the artifact is unchanged (same sha256) clears the counter.

**PR bodies.** The PR-body file is re-hashed at `gh pr create`, so open with `--body-file <the attested file>`; a retyped `--body` mismatches ([worktree + PR-body](../learnings/1787818646140-fresh-git-worktree-lacks-submodules-critique-gate-.md)). A body heredoc in the same bash call as the gated `gh api .../pulls` is lost when that call is blocked, and opening the PR plus posting a comment is an external state change that re-blocks the handoff; refresh OUTPUT_REVIEW on the same thread citing the unchanged sha256 rather than redoing the critique ([PR-body-file traps](../learnings/1787821097042-critique-gate-and-pr-body-file-interaction-traps.md)).

**Gated-pushback replies** (declining a maintainer's stated preference) are approved for their exact wording, so re-flag any post-approval wording change to the approver before posting, even an accuracy tightening codex flagged, since it could be substantive. Routine "addressed your finding" replies stay pre-authorized ([re-flag any post-approval wording change](../learnings/1789490573346-gated-pushback-replies-re-flag-any-post-approval-w.md)).

**The tracker parses the Verdict word and each Attested line strictly.** Only lines matching `-[ \t]*<64 hex>[ \t]+<path>` are captured; a backtick-wrapped (`` - `abc…` `/path` ``) or truncated hash, both common, records nothing. The comment gate then refuses a 1,000+-character public comment for an approved, unchanged file ("not among the files an OUTPUT_REVIEW attested"), or, with an older round's hashes in force, the delivery gate says "reviewed artifacts changed" (next paragraph). The Verdict line is lowercased and stripped to letters and hyphens, so `approve — for PLAN_REVIEW only` records `unparseable`; bold or a trailing period still parses. Specify both formats in the prompt ("Verdict: one word; each Attested line exactly `- <64-hex sha256> <absolute path>`, no backticks"), and if a reply still comes back wrong, ask on the same thread to re-emit the lines plain. Side traps: a read-only `gh api …/pulls/<n>/reviews` was blocked as "PR creation" (use slang-mcp `github_get_pull_request_reviews`), and `-F body=@…/$id.md` in a `for` loop is refused as "not a literal path"; use literal absolute paths [backtick-wrapped hashes rejected](../learnings/1791828331890-track-critique-attested-parser-rejects-backtick-wr.md), [Attested lines must be plain `- <sha> <path>`](../learnings/1792192842171-critique-gate-attested-lines-must-be-plain-sha-pat.md), [backticked Attested hashes](../learnings/1792199075282-codex-critique-gotchas-wiki-recall-first-replies-b.md), [unparseable Verdict and truncated hashes](../learnings/1792242240195-codex-critique-first-call-on-a-fresh-thread-often-.md), [seen again on a slang-rhi triage](../learnings/1792518561170-slang-rhi-d3d11-d3d12-cleartextureuint-sint-are-no.md).

**A round that records no Attested line leaves the previous hashes in force.** At send time the delivery gate re-hashes every path in `workflow-state.json` → `critique_attested.OUTPUT_REVIEW`. `track-critique.sh` replaces a stage's map (jq object `+`, whole key; read 2026-10-19) only when a round on that stage parses at least one Attested line; a round parsing none (backticked hashes, a recall reply) or a reply mapped to another stage leaves the old map. On 2026-10-17 a narrow `codex-reply` re-check of three files approved, yet delivery was refused with "reviewed artifacts changed since the OUTPUT_REVIEW approve: <paths>", naming files an earlier round attested and later edited (the atom's old+new-merge reading fits the source only if that round recorded no Attested line). Fix: one fresh OUTPUT_REVIEW whose ARTIFACTS list every path the gate names plus the deliverables, then check `jq '.critique_attested.OUTPUT_REVIEW' /workspace/.claude/workflow-state.json` against `sha256sum` [a narrow codex-reply approve leaves stale attested hashes](../learnings/1792261551774-critique-gate-a-narrow-codex-reply-approve-leaves-.md). Variants: [critique & delivery gates](agent-routing-f0909b2-critique-and-delivery-gates.md) and [container-side gates](agent-routing-f0909b0-critique-delivery-gates.md).

## OUTPUT_REVIEW reads the live PR, not your local tree

On an open PR, OUTPUT_REVIEW compares the live head SHA and posted body with your working tree, so unpushed corrections draw a staleness must-fix ("PR still at `<old-sha>`", "`/tmp/pr-body.md` is not the posted body") and waste a round. Finalize in order: (1) apply edits; (2) rebuild only if behavior changed (comment-only edits with unchanged CHECK lines need none); (3) format, `git commit --amend`, force-push; (4) `gh pr edit --body-file`; (5) OUTPUT_REVIEW last, before the delivery marker. An expired thread ("Session not found for thread_id") just needs a fresh session ([OUTPUT_REVIEW compares the posted PR against your local tree](../learnings/1789402846129-delivery-gate-output-review-compares-the-posted-pr.md)).

## Token matching, push bundling, and ledger ordering

**The matcher over-blocks on literal tokens.** The ABSTAIN fast-path is `grep ABSTAIN_* && ! grep (WOULD_APPROVE|BLOCK)`, so an ABSTAIN report whose prose merely says "not BLOCK"/"not WOULD_APPROVE" falls through to the full gate, which an abstain can't satisfy, and `gate-chain-routing.sh` then also demands `in_reply_to` on the chain-marker message ([quoting BLOCK/WOULD_APPROVE defeats the fast-path](../learnings/1787621185331-approver-infra-critique-gate-abstain-fast-path-is-.md), [the gate text-matches tokens in prose](../learnings/1787778155862-approver-infra-delivery-critique-gate-text-matches.md)). TRIGGER ≠ REASON: rephrase ("no verified bug", "flagged a defect"), keep `ABSTAIN_POLICY` present, and don't manufacture a ceremonial critique. A `[GATE AUDIT]` hook likewise flags a message containing the literal `[Resolution]` when codex was never invoked, colliding with the spine's advice to close a routine ack with a `[Resolution]` 5-bullet; close courtesy chains neutrally ("[Chain closed]" or a bare positive summary) and reserve `[Resolution]` for outcomes you ran codex on (seen closing the shader-slang/slang#13086 fix-review chain) ([the `[Resolution]` tag trips the audit](../learnings/1789633290729-the-resolution-tag-trips-the-critique-overlay-gate.md)). The audit also fires on `[Fix Report]` when a reviewer merely asks for one — a false trigger, not a skipped gate ([GATE AUDIT false trigger on "[Fix Report]"](../learnings/1792058636644-container-restart-mid-review-kills-reviewer-a-c-an.md)).

**A denial aborts the whole Bash call.** A `git push` bundled with a gated command never runs, so reviewers review a stale commit. Push in its own call (`--force-with-lease=<branch>:<sha>` explicitly in a worktree with no `origin/<branch>` ref), verify with `git ls-remote`, then re-dispatch CI and tell reviewers the head moved ([never bundle a git push](../learnings/1787846612049-never-bundle-a-git-push-with-a-critique-gated-comm.md)). A chained file edit is swallowed the same way, and the trigger is command text, so a heredoc merely mentioning the PR-open command suffices: on slang#13273 a python PR-body edit chained before `gh pr create` never ran, noticed a day later. Keep edits in separate calls; write memory text naming gated commands with the Edit tool ([the gate blocks the whole Bash call](../learnings/1790593764309-critique-gate-blocks-the-whole-bash-call-gpu-less-.md)). After an OUTPUT_REVIEW must-fix any command containing `gh api` is refused, even a GET, so a fix-then-check-with-`gh` call never writes the fix and codex reports the same sha256; edit in a `gh`-free call and re-hash before claiming an item is addressed. A maintainer's `@nv-slang-bot` mention via `pr_session_mappings` authorizes your reply on that PR but does not lift a parent's separate hold; report it upstream ([a combined edit+gh call is blocked whole](../learnings/1790818878715-the-critique-delivery-gate-can-block-a-combined-ed.md)).

**Record the append-only ledger row last.** The verdict-unaware, edit-count gate can force an OUTPUT_REVIEW that overturns an ABSTAIN after the row is committed (first-write-wins per `(repo, pr, commit_sha)`; "Decision recorded" is a known false-success string) ([record the ABSTAIN row last](../learnings/1787732678394-approver-infra-abstain-record-the-abstain-row-last.md)). The ABSTAIN fast-path also records before the critique gate, locking out a late-surfacing BLOCK such as a head-current CodeRabbit review landing after harvest; for an ABSTAIN whose rationale is "no/incomplete reviewer signal", settle the harvest and run OUTPUT_REVIEW before `record_decision`, never the fast-path ([the fast-path records before the gate](../learnings/1787905229286-approver-critique-mustfix-the-abstain-fast-path-re.md)). `record_decision` is the last irreversible action of the turn.

## The review-request format check

The hook refuses a `[Fix Review Request]` without a `Maintainer direction:` line linking a canonical GitHub comment or saying `none — <reason>`. If that section contains any canonical comment link (`…/issues|pull/<n>#issuecomment-…`, `#discussion_r…`, `#pullrequestreview-…`, `#issue-…`) — even a triager comment cited in the reason — it also requires a `Fixer self-check:` line with R1, R2… items; a bare `none — <reason>` passes (hook `review_request_problem`, tested 2026-10-19). Map a triager's numbered asks to R1–Rn ([review-request gate requires Fixer self-check R-items](../learnings/1792261551774-critique-gate-a-narrow-codex-reply-approve-leaves-.md)).
