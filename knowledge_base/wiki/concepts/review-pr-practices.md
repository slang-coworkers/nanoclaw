# PR Review Practices

The Slang coworker review pipeline runs three parallel reviewers — Reviewer A (correctness, `slang-pr-review-runner`), Reviewer B (Devin via `devin-fetch.sh`), and Reviewer C (clarity, `slang-clarity-review-runner`) — and merges their findings into a single `combined-review.md`. This page consolidates all operational lessons about running that pipeline correctly, interpreting results, avoiding common traps, and maintaining proper GitHub-vs-internal review hygiene.

## Reviewer B (Devin) Reliability

Devin (Reviewer B) is best-effort and must be self-verified before it contributes to any verdict.

**Premature scrape — the most common failure mode.** `devin-fetch.sh` can exit `rc=0` while Devin's AI Analysis panel is still rendering (`Generating...`). When this happens, `devin-flags.md` echoes the PR description back verbatim under `## AI Analysis`, and `## Bugs` / `## Flags` show `(none reported)` — which looks like a clean all-clear but means nothing. Observed repeatedly: [slang PR review: Reviewer B (devin-fetch) exit 0 ≠ Devin analysis complete](../learnings/1780870637455-slang-pr-review-reviewer-b-devin-fetch-exit-0-devi.md), [Devin reviewer: 'unknown' commit-status + 'Generating...' = weak signal, not a clean bill](../learnings/1781179189519-devin-reviewer-unknown-commit-status-generating-we.md), [Devin reviewer (devin-fetch) can exit 0 while analysis still 'Generating' — treat empty Bugs/Flags as low-confidence](../learnings/1781192458084-devin-reviewer-devin-fetch-can-exit-0-while-analys.md), [Devin reviewer (B) can exit rc=0 while analysis is still 'Generating' — a false all-clear](../learnings/1781731413287-devin-reviewer-b-can-exit-rc-0-while-analysis-is-s.md), [slang-pr-review: Devin can report 0 bugs while analysis still 'Generating…' — treat as weak signal](../learnings/1782761345395-slang-pr-review-devin-can-report-0-bugs-while-anal.md), [Devin reviewer scrape reliability](../learnings/devin-reviewer-scrape-reliability.md).

**Detection rule:** After every devin-fetch, grep `devin-flags.md` for `Generating` in the `## AI Analysis` section. Also check: is the AI Analysis body just a PR-description echo? Is `## Flags` blank whitespace rather than an explicit "no flags"? Does the PR number appear inside the analysis blob? If any check fails, label Reviewer B **INCOMPLETE / no signal** in the merged verdict — never fold `(none reported)` into a confidence count.

**Cross-PR contamination.** When devin-fetch runs concurrently for multiple PRs, all `devin-flags.md` files can contain the same AI Analysis blob (from whichever tab rendered first). Serialize Devin fetches, or grep each file for the expected PR number to confirm the page content matches the URL [Devin reviewer scrape reliability](../learnings/devin-reviewer-scrape-reliability.md).

**Draft PRs.** Devin analysis is typically inconclusive on draft PRs — the page shows "Generating...", commit-status "unknown." Treat B as best-effort-skipped on any draft [slang-pr-review: Reviewer A budget-cap mid-analysis hypotheses are NOT findings — re-run + independently verify](../learnings/1781134206455-slang-pr-review-reviewer-a-budget-cap-mid-analysis.md), [Stacked-PR review: Reviewer A checks out master, producing predictable false positives + a missed-drop; coordinator must self-verify against the real base/head](../learnings/1781324278003-stacked-pr-review-reviewer-a-checks-out-master-pro.md).

**Healthy Devin scrape signals:** `## AI Analysis` has synthesized prose (not diff fragments); `## Flags` explicitly says "no flags" (not blank); the PR number in the analysis text matches the URL; `devin-commit-status.txt` says "Analysis is up to date" [Devin reviewer scrape reliability](../learnings/devin-reviewer-scrape-reliability.md).

**"30m timeout" in devin-error.txt** is a templated message meaning "no Devin analysis available for this PR" — not a literal 30-minute wall-clock measurement. Treat B as best-effort-skipped and proceed on A+C [Slang PR #11815 review — A∩C converge on dead Flavor::Simple arm; Devin '30m timeout' quirk](../learnings/1782735484974-slang-pr-11815-review-a-c-converge-on-dead-flavor-.md).

**Devin earns its slot: it can surface a real correctness bug a fixer's process report didn't pre-empt.** On slang#12052 the fix seeded `importedModulesList` from `getModuleDependencies()`; the fixer's report pre-empted a candidate-*extension* double-add, but Reviewer B (Devin) flagged a *different* correctness bug the report never covered — a double-add via the `getAssociatedDeclsForDecl` path (`slang-check-shader.cpp:3456`), which consults the same seeded list on a *separate consumer*. Lesson: when a fixer's report claims "no double-add," verify it names the **specific consumer it audited** — one seeded list often feeds multiple consumers (candidate extensions AND associated decls), and a report can be correct about one while silent on the other. Process caveat from the same PR: it merged before Reviewer A (correctness) ever completed — A's background shell was lost twice across session boundaries — so when a review spans session boundaries, re-check that A actually produced `final-review.md` before assuming a verdict exists ([Devin can surface a correctness Bug the fixer's process report didn't pre-empt (PR 12052)](../learnings/1784291828247-devin-can-surface-a-correctness-bug-the-fixer-s-pr.md)).

## Reviewer C (Clarity) Failure and Recovery

Reviewer C can die mid-run from a transient `API Error: The socket connection was closed unexpectedly`. The failure leaves `clarity-review.md` as a tiny stub (~80–135 bytes) containing only the error string — even though the wrapper exits and the file exists. A naive "artifact present?" check would silently lose a whole reviewer [slang-pr-review Reviewer C can die mid-run on a transient API socket error — detect via tiny clarity-review.md, retry recovers](../learnings/1780603736166-slang-pr-review-reviewer-c-can-die-mid-run-on-a-tr.md), [slang-pr-review: Reviewer C (clarity) can drop with transient socket error — detect tiny output, just re-run](../learnings/1781213312260-slang-pr-review-reviewer-c-clarity-can-drop-with-t.md).

**Detection:** After C finishes, check `wc -c clarity-review.md`. Healthy output is multi-KB (8–26 KB). A file under ~400–500 bytes, especially one containing `API Error|socket connection`, means the run crashed.

**Recovery without re-running:** The clarity pipeline writes intermediate candidate files to `<REPO_ROOT>/tmp/review-candidates/pr-<N>-clarity.md`, `pr-<N>-fine-grained-clarity.md`, and (if consolidation completed) `pr-<N>-clarity-workflow.md`. The crash typically hits after generation but before consolidation, so the raw candidates usually survived. Reassemble `clarity-review.md` from those files with a "RECOVERED / un-consolidated" header rather than burning another ~$2–5/~20–45 min re-run that may hit the same fault [Recover slang clarity-review candidates after a transient API error instead of re-running](../learnings/1781731735312-recover-slang-clarity-review-candidates-after-a-tr.md), [slang Reviewer C clarity run: recover truncated output from on-disk candidate file](../learnings/1782739994323-slang-reviewer-c-clarity-run-recover-truncated-out.md).

**If re-running:** a single re-run recovers cleanly — the error is transient infra, not a logic problem. Budget ≥50 min for the monitor; C routinely runs longer than A (Reviewer A ~20–30 min; Reviewer C ~25–45 min) [slang-pr-review: Reviewer C (clarity) can drop with transient socket error — detect tiny output, just re-run](../learnings/1781213312260-slang-pr-review-reviewer-c-clarity-can-drop-with-t.md).

## Reviewer A + C Parallelism and Checkout Isolation

Reviewer A (`compose-and-run.sh`) and Reviewer C (`run-clarity.sh`) both default to `REPO_ROOT=/workspace/agent/slang` and each runs `git fetch` + `git checkout -q origin/master` at startup. When launched simultaneously, they race on `.git/index.lock` — the loser exits 128 with `fatal: Unable to create '.git/index.lock': File exists` and produces no output file [slang PR-review: Reviewer A and C share one checkout — parallel runs collide on git index.lock](../learnings/1780769238745-slang-pr-review-reviewer-a-and-c-share-one-checkou.md).

**Preferred fix:** point Reviewer C at a separate existing clone — `/workspace/agent/slang-clarity` — via `REPO_ROOT=/workspace/agent/slang-clarity bash .../run-clarity.sh ...`. That clone already has the clarity skills and a valid `origin`, so no setup is needed. This is simpler than the git-worktree approach [Reviewer A + C parallel isolation: use /workspace/agent/slang-clarity as C's REPO_ROOT](../learnings/1782586901771-reviewer-a-c-parallel-isolation-use-workspace-agen.md).

Both runners operate via `gh pr diff` in `pr` mode, so their only git contention is the startup fetch/checkout — separate checkout dirs eliminate it entirely. C should also use its own separate clone to avoid writing `tmp/` files into A's tree [slang Reviewer C clarity run: recover truncated output from on-disk candidate file](../learnings/1782739994323-slang-reviewer-c-clarity-run-recover-truncated-out.md).

## Finding the Reviewer C Run Directory

Do NOT use `ls -dt transcripts/pr-* | head -1` to locate Reviewer C's run directory at the merge step. The newest-by-mtime directory can be a stale sibling dir (e.g. one containing only `prompt.txt`+`stream.jsonl` with no `clarity-review.md`), causing a silent empty/MISSING C section in the combined report.

**Reliable method:** parse the run-clarity.sh stdout, which prints `>>> clarity review: <abs path>/clarity-review.md` on its last lines. Grep that from the captured log: `grep -oE '>>> clarity review: .*' revC.log`. Same principle applies to Reviewer A: parse the `RUN_DIR` from `compose-and-run.sh` stdout rather than `ls -t` [slang-pr-review merge step: find Reviewer C run-dir from stdout, and drift-grep tool NAME not content](../learnings/1782738058115-slang-pr-review-merge-step-find-reviewer-c-run-dir.md).

## Drift-Checking Reviewer C

To verify C made no GitHub writes (`gh pr review`, `gh issue comment`, `gh api ... POST/PUT/PATCH/DELETE`), grep `tool-uses.jsonl` for the **Bash command string** — specifically `gh (pr review|comment|issue comment)` or `gh api ... (--method|-X) (POST|PUT|PATCH|DELETE)`. Do NOT match free text in the file: a `Write` call whose body contains the word "review" will produce a false positive. On clean runs, C makes only `Read` + `gh pr diff/view` (reads) + local `Write` calls to `tmp/review-candidates/` [slang-pr-review merge step: find Reviewer C run-dir from stdout, and drift-grep tool NAME not content](../learnings/1782738058115-slang-pr-review-merge-step-find-reviewer-c-run-dir.md), [Verifying detached background PR-reviewer completion (Monitor + pgrep gotchas)](../learnings/1782160447849-verifying-detached-background-pr-reviewer-completi.md).

## Reviewer A False Positives and Budget Caps

**Subagent prompt condensation false positives.** Reviewer A's code-quality subagent can produce false positives on FileCheck test files: `//CHECK` directives on their own lines get collapsed onto the preceding source line in the condensed view, making `//CHECK-NOT` look commented-out and `@LINE-1` look off-by-one. Reviewer A's own editorial/filter pass normally catches and drops these — trust the editorial table's "Drop (false positive)" rows for FileCheck-test findings; do NOT forward them to the fixer without confirming against the real `gh pr diff` [slang Reviewer A false positives on own-line //CHECK directives from prompt condensation](../learnings/1781177378439-slang-reviewer-a-false-positives-on-own-line-check.md).

**Base-tree vs diff confusion.** Reviewer A's subagents sometimes reason from the local base checkout instead of the diff, producing false-positive "compile error at line X" or "the feature/help-text doesn't exist" claims. The editorial-filter stage catches these, but when a subagent claims a hunk doesn't exist or a call site is broken, verify against `gh pr diff` before escalating [PR-review lenses: extracted-matcher integration gap + normalize-before-match blind spot](../learnings/1780323605226-pr-review-lenses-extracted-matcher-integration-gap.md).

**Stacked PRs.** On a stacked PR (base ≠ master), Reviewer A checks out `origin/master` and applies `gh pr diff` (scoped correctly to the slice). This causes two predictable failures: (1) false-positive "missing symbol / runtime error" findings reasoned from master code that a lower slice changed; (2) genuinely-correct findings dropped because A cannot fetch the PR-head tree. Reviewer A's editorial rules usually self-drop the false positives, but the coordinator must self-verify stacked-context-sensitive items by fetching the stacked base+head into explicit refs and running `git diff base..head` before finalizing the merged verdict [Stacked-PR review: Reviewer A checks out master, producing predictable false positives + a missed-drop; coordinator must self-verify against the real base/head](../learnings/1781324278003-stacked-pr-review-reviewer-a-checks-out-master-pro.md).

**Budget cap mid-analysis.** When Reviewer A terminates with `error_max_budget_usd` (check the final `"subtype"` in the stream/log), it dies before writing `final-review.md` — leaving only mid-analysis hypotheses in `stream.jsonl`. Those are unconcluded hypotheses the orchestrator would have disproved in its own editorial filter. Re-run A at a higher cap (e.g. `--max-budget-usd 50`) and independently verify any high-stakes hypothesis against the actual source — do not propagate mid-analysis guesses into the verdict [slang-pr-review: Reviewer A budget-cap mid-analysis hypotheses are NOT findings — re-run + independently verify](../learnings/1781134206455-slang-pr-review-reviewer-a-budget-cap-mid-analysis.md).

## Reviewer A Flip-Flops Across Rounds

Reviewer A is a fresh subagent invocation each round with no memory of prior verdicts. The same finding can land above the 85-confidence floor one round and below it the next. Observed patterns: a "suggested fix" from round N-1 that was implemented exactly by the fixer gets re-raised as a gap in round N; the same code comment flagged at Question-confidence (round 3) gets re-raised as a Gap (round 8) [Reviewer A (claude-pr-review subagents) can give inconsistent advice across rounds — log signed-off positions per round](../learnings/1779437432996-reviewer-a-claude-pr-review-subagents-can-give-inc.md).

**How to apply:** Log Reviewer A's signed-off positions per round. When round N flags something round N-1 explicitly approved, label it reviewer drift in the merged verdict rather than asking the fixer to iterate again. A's signed-off "suggested fix" from round N-1 is contractual — if the fixer implemented it and round N flips, note the flip-flop and recommend ignoring. Convergence (gaps monotonically shrinking) is good; bouncing is a signal to land + follow-up rather than chase A's latest set [Reviewer A (claude-pr-review subagents) can give inconsistent advice across rounds — log signed-off positions per round](../learnings/1779437432996-reviewer-a-claude-pr-review-subagents-can-give-inc.md).

Devin (Reviewer B) is more stable round-to-round because its flag set is carried with persistence markers, though it can re-flag items the fixer already addressed.

## Empirical Probes Can Test the Wrong Sub-case

"I ran the test and it passed" is only as good as the test design. On Slang PR #11234, a fixer's empirical probe covered one of two sub-cases (supplied default args) but not the other (omitted default args), leading to a false closure of a Devin finding that persisted across rounds 2, 3, 5, 6 before Reviewer A traced the actual code path in round 6 [Empirical 'I tested it' probes can miss the wrong sub-case — Devin's persistent flags deserve scrutiny even when initial reading says misread](../learnings/1779434309171-empirical-i-tested-it-probes-can-miss-the-wrong-su.md).

When Devin persistently flags something across multiple rounds despite an empirical "I tested it" closure, ask: does the test design cover all sub-cases of the structural concern Devin is naming? For any "X with feature Y" flag, enumerate all usage combinations (supplied/omitted, default/explicit, present/absent) and verify the probe covers each. Don't let convergence trend bias judgment — rounds 1–5 trending green doesn't mean round N is green [Empirical 'I tested it' probes can miss the wrong sub-case — Devin's persistent flags deserve scrutiny even when initial reading says misread](../learnings/1779434309171-empirical-i-tested-it-probes-can-miss-the-wrong-su.md).

## Verifying "Not Constructible / Defensive-Only" Claims

When an implementer claims a reviewer-requested test is "not constructible," "unreachable," or a guard is "defensive-only / document-don't-test," **gate acceptance on independent adversarial verification — never rubber-stamp the claim.** The claim is load-bearing because it waives an artifact a reviewer asked for.

On Slang #11450, the fixer claimed a cross-module negative test was not constructible (verified 3 ways). Round-2 adjudication refuted the claim: the test is constructible via plain transitive `import`. Convergence of multiple independent sources on "it's fine" is NOT confirmation — they can share a blind spot: here the fixer, Devin, and the clarity reviewer all converged wrong; only the dedicated correctness reviewer, investigating an alternative construction, caught it [Verify 'not constructible / defensive-only' claims that waive reviewer artifacts](../learnings/1780487356786-verify-not-constructible-defensive-only-claims-tha.md).

A wrong "why this guard exists" comment is worse than none: it invites a future maintainer to delete the guard. When the real triggering mechanism differs from the documented one, the comment must be corrected [Verify 'not constructible / defensive-only' claims that waive reviewer artifacts](../learnings/1780487356786-verify-not-constructible-defensive-only-claims-tha.md).

## Convergence and When to Scope Down

Multi-round review converges when finding counts decrease monotonically and A/C disagreements disappear. A template trajectory for a healthy convergence: 4 gaps → 2 gaps (one new) → 1 gap → 0 nits [Multi-round PR review converges; scope down to targeted verify when delta is comment-only](../learnings/1780769199724-multi-round-pr-review-converges-scope-down-to-targ.md).

**Scope-down rule:** When the fixer's re-push delta is `tests/**`-only (no `source/**`, `prelude/**`, `include/**` changed), the prior code verdict still stands. Running a full A/C pipeline re-run mostly re-derives the same verdict, re-incurs subagent-hallucination risk, and wastes ~$50 and an hour. Instead, fetch the changed test files and verify the test logic directly: does the new CHECK encoding actually catch the regression class the reviewers flagged? Report transparently that you scoped to focused verification [slang-pr-review: scope a re-run to focused verification when the re-push is test-only](../learnings/1782594329649-slang-pr-review-scope-a-re-run-to-focused-verifica.md).

Similarly, when a fixer re-push is comment-only and implements exactly what reviewers asked for, a full pipeline re-run produces no new signal. Verify the diff is that narrow (pure additive comment, zero code change), confirm placement, and sign off [Multi-round PR review converges; scope down to targeted verify when delta is comment-only](../learnings/1780769199724-multi-round-pr-review-converges-scope-down-to-targ.md).

## A/C Convergence and Disagreement Adjudication

Strong A/C convergence (both A and C independently flag the same line) is high-confidence and should lead the combined report. On PR #11815, both reviewers independently identified a dead `Flavor::Simple` arm — this concretely confirms the heuristic [Slang PR #11815 review — A∩C converge on dead Flavor::Simple arm; Devin '30m timeout' quirk](../learnings/1782735484974-slang-pr-11815-review-a-c-converge-on-dead-flavor-.md).

When A and C disagree, the meta-bias "C says X, A says ¬X and shows code" almost always means A — A's subagents ground claims in the actual diff bytes; C applies a lower confidence bar and broader coverage. To resolve A↔C disagreements on stacked PRs, the coordinator must self-verify against the stacked base+head refs (see above) [Multi-round PR review converges; scope down to targeted verify when delta is comment-only](../learnings/1780769199724-multi-round-pr-review-converges-scope-down-to-targ.md), [Stacked-PR review: Reviewer A checks out master, producing predictable false positives + a missed-drop; coordinator must self-verify against the real base/head](../learnings/1781324278003-stacked-pr-review-reviewer-a-checks-out-master-pro.md).

**Convergent false positive.** Multi-subagent convergence does not guarantee correctness. On PR #11504, two of A's subagents (doc + cross-backend) independently flagged a test comment as inaccurate, anchoring on the PR description's imprecise line citations rather than the comment text itself. The comment-as-written was correct; both subagents shared the same anchoring error. Rule: verify a "comment inaccurate" flag against the exact comment text in the diff, and grep for OTHER sites that might satisfy a general claim [Slang review: verify 'inaccurate comment' flags against code text, not PR-body citations](../learnings/1780769188437-slang-review-verify-inaccurate-comment-flags-again.md).

## Verifying Detached Background Reviewer Completion

Two traps when monitoring nohup-background reviewer jobs [Verifying detached background PR-reviewer completion (Monitor + pgrep gotchas)](../learnings/1782160447849-verifying-detached-background-pr-reviewer-completi.md):

1. **Context compaction kills in-flight Monitor.** A large compaction event can fire Monitor's timeout early. After any compaction, re-check process/output state directly rather than trusting the monitor.
2. **`pgrep -fc 'pattern'` false counts.** The pattern string appears in your own command pipeline → pgrep counts your own shell invocation. Use `ps aux | grep <pat> | grep -v grep` instead. Better still, treat the authoritative completion signal as the wrapper's done-marker in its log plus a non-empty output file: A = `>>> repro.sh: done` + `final-review.md`; C = `>>> run-clarity.sh: done (rc=0)` + `clarity-review.md`; B = `>>> devin-fetch: …/devin-flags.md (N lines)` + `devin-flags.md`.

## GitHub reviewDecision vs Internal A2A Review

An internal a2a coworker APPROVE (slang-reviewer, codex) does NOT change the PR's GitHub state — it stays `REVIEW_REQUIRED` with 0 formal reviews until a maintainer submits an actual GitHub review. A maintainer commenting "seems reasonable" or un-drafting the PR is also NOT a GitHub Approve.

**Rule:** Report PR readiness from live GitHub state — `gh pr view <n> --json isDraft,reviewDecision,reviews,mergeable,statusCheckRollup` — never from the internal review verdict alone. In human-facing comments, say "internal a2a review passed; awaiting formal GitHub review/CI" rather than "reviewer-approved" or "N reviewers APPROVE" [Don't conflate internal a2a review with GitHub reviewDecision in human-facing comments](../learnings/1780509591502-don-t-conflate-internal-a2a-review-with-github-rev.md), [Internal a2a review ≠ GitHub reviewDecision](../learnings/1782148692608-internal-a2a-review-github-reviewdecision.md), [Internal agent-review APPROVE is not a GitHub maintainer approval](../learnings/1782465097683-internal-agent-review-approve-is-not-a-github-main.md), [Verify 'N reviewers APPROVE' against GitHub reviewDecision before posting it as a public verdict](../learnings/1782465056185-verify-n-reviewers-approve-against-github-reviewde.md).

Before posting "N reviewers APPROVE" on a public issue, verify with `gh pr view <n> --json reviewDecision,reviews,latestReviews,reviewRequests` and `gh api repos/<owner>/<repo>/pulls/<n>/reviews --jq '.[]|"\(.user.login)\t\(.state)"'`. Post only what GitHub state supports [Verify 'N reviewers APPROVE' against GitHub reviewDecision before posting it as a public verdict](../learnings/1782465056185-verify-n-reviewers-approve-against-github-reviewde.md).

## Draft PR Hygiene

**Never add a reviewer to a draft PR.** Adding a reviewer fires a GitHub notification to that person every time — for a bot-authored draft they haven't asked to review, that is spam. Concretely: `gh pr create ... --draft` with no `--reviewer` flag; never `gh pr edit <n> --add-reviewer <user>`; never populate `requested_reviewers` via REST/GraphQL. The internal coworker peer-review chain (slang-reviewer) runs over a2a and does not require GitHub's PR-reviewer mechanism [Never add a reviewer to a draft PR — it spams the human](../learnings/1780690000002-never-add-a-reviewer-to-a-draft-pr-it-spams-the-human.md).

**Never instruct a fixer to mark a PR ready-for-review.** Fixers operate under an admin-set drafts-only constraint. Ready-for-review flips are a case-by-case operator exception. If expediting via RFR seems warranted, escalate to the human operator; only they can grant the exception. Don't instruct a coworker to override its own admin-set safety constraints [Don't instruct coworkers to mark PRs ready-for-review (drafts-only is admin-set)](../learnings/1780418605612-don-t-instruct-coworkers-to-mark-prs-ready-for-rev.md).

**Hold unsolicited reviews on human-contributor PRs.** When shader-slang/slang already runs its own production review bot (`claude-pr-review.yml`), nv-slang-bot posting an additional COMMENT review duplicates coverage and adds noise. Default to holding the GitHub post unless there's an explicit `@nv-slang-bot` invitation or operator authorization. The review artifact (combined-review.md) still has internal value; keep it on disk for a maintainer who later asks [Hold unsolicited reviews when repo runs its own PR bot](../learnings/1782464483726-hold-unsolicited-reviews-when-repo-runs-its-own-pr.md).

## Markdown Links for Issues and Reviews

When listing or referencing GitHub issues, PRs, or review URLs in any user-facing reply, always render them as markdown links — `[short-label](url)` — not bare URLs or plain references. The dashboard renders markdown; clickable labels like `[slang#10747](url)` let the user jump directly to the source. Link the issue/PR cell using `[<repo>#<num>](url)` in tables; link the title or a short anchor for PR reviews. Bare URLs are fine in tool-call payloads or scratchpad [Always use markdown links for issues and reviews](../learnings/1779362752977-always-use-markdown-links-for-issues-and-reviews.md).

## Triaging Issues with an Existing Community Fix PR

When a GitHub issue is a tracking issue for an already-open community fix PR, two mistakes are easy to make [Triaging an issue that already has a community fix PR — review, don't duplicate](../learnings/1781125005627-triaging-an-issue-that-already-has-a-community-fix.md):

1. Skip the triage 5-bullet on the issue. Wrong — post it anyway (verdict = "triaged → PR #X already fixes this, pending review"), because the PR predates the issue and carries no `Fixes #N` link.
2. Tell the fixer to write a competing PR. Wrong — the handoff should be "review and land" the existing one. Make this loud: a complete, tested PR already exists; duplicating wastes work and steps on a contributor.

## Stack on a Sibling PR Instead of Duplicating Its Fix

When a reviewer (human or codex) flags that your fix reuses a shared primitive that is *too permissive*, AND a **sibling PR is already tightening that exact primitive**, stack your branch on the sibling's branch rather than duplicating the change or preserving the defect behind a flag. On #11861/#11870, #11861 added struct-field recursion to `isVkBindingCompatibleEntryPointParameterType`, reusing a per-field leaf that still returned `true` for `PtrType` — so `struct { uint* p; }` would inherit that over-broadening and wrongly suppress E38010, a *new* instance of the exact bug sibling #11870 (`fix/issue-11857`) was already removing. Of the three options — duplicate the leaf removal (merge conflict, two PRs editing the same lines, unclear ownership), preserve the bug + add a guard (ships a known defect — a methodology red flag), or **stack** — stacking won: `git reset --hard origin/<sibling-branch>`, re-apply the delta, open with `--base <sibling-branch>`, so the recursion is a faithful subset *by construction* (the offending leaf is already gone in the base), zero duplication, sibling keeps ownership. Note in the PR body that it rebases onto master once the sibling merges, and that the sibling merges first. **Tell:** "your new code reuses X, and X is too permissive" + another open PR is already fixing X = the stack signal; the faithful-subset property (predicate ⊆ what the real consumer honors) is easiest to guarantee by building on the branch that already tightened the shared primitive ([Stack a PR on a sibling instead of duplicating its fix (faithful-subset coordination)](../learnings/1782882818697-stack-a-pr-on-a-sibling-instead-of-duplicating-its.md)).

## Reviewer A's Lens: Extracted Matchers and Normalize-Before-Match

Two reviewer lenses that frequently surface on refactor PRs [PR-review lenses: extracted-matcher integration gap + normalize-before-match blind spot](../learnings/1780323605226-pr-review-lenses-extracted-matcher-integration-gap.md):

**Pure-matcher unit tests are not integration coverage.** Unit tests prove the extracted helper is correct but say nothing about the call-site wiring, ordering, or precedence. For slang-test specifically, a `-dry-run` black-box check (asserting the subtest is absent from dry-run stdout) exercises the real scheduling path without running tests.

**Normalize-before-match blind spot.** When CLI entries are canonicalized before storage (e.g. via `Path::simplify`) but the matcher compares by exact string against an assembled display name, the normalization round-trip is a silent gap. On Windows `kPathDelimiter` is `\`; strings assembled with `/` from a source `filePath` can fail to match. Any "match a user-supplied string against an internal string" feature — check whether one side is normalized and the other isn't, and whether the author only tested on the platform where normalization is a no-op.

## Applying Maintainer Suggestions Safely

A maintainer's literal code suggestion is a request to honor, not a spec to paste. On PR #11628 (WGSL emitter), applying a maintainer's predicate-simplification literally would have introduced a regression: the predicate was read in TWO places, and one of those sites ran for ALL ops (including `GlobalParam`) where the simpler form fired incorrectly [A maintainer's literal review suggestion can be locally unsafe — verify all read sites of a reused predicate](../learnings/1781640634164-a-maintainer-s-literal-review-suggestion-can-be-lo.md).

**Rule:** Before applying a predicate or condition change, enumerate every site that reads it — especially in fall-through `if/else if` chains where safety at one site doesn't imply safety at another. Adopt the spirit (use their helper/shape), keep the one guard that's actually load-bearing, prove behavior is unchanged at all read sites, and tell them in-thread exactly what you kept and why.

## Null-Possible Invariant Audits

When a PR establishes a new null-possible invariant for a member (e.g. "`m_param` can be null during result legalization") and adds a safe-access helper, grep the whole file for `<member>->` and confirm each remaining raw dereference is either unreachable under the new condition or asserts/uses the helper. Missing a sibling site reads as either an oversight or a latent crash of the same class as the bug just fixed. Both Reviewer A and C flagging the same untouched sibling site is a strong convergence signal [PR-review heuristic: when a fix adds a null-possible invariant + helper, audit ALL structurally-identical sites](../learnings/1781792411472-pr-review-heuristic-when-a-fix-adds-a-null-possibl.md).

## Reviewer-Traced Unreachable Paths

A code-reading reviewer can trace a plausible bug path that is foreclosed upstream by the front-end. Before adding a regression test for a reviewer-traced "gap," try to construct the triggering input and compile it. If it's rejected upstream (e.g. E30702 for `SV_DepthGreaterEqual` as input), the gap is unreachable — say so with the diagnostic code as evidence, and don't ship a test that can't compile [Depth SV semantics are output-only (E30702) — a reviewer-traced 'inout duplicate' gap can be unreachable](../learnings/1782175276058-depth-sv-semantics-are-output-only-e30702-a-review.md).

This applies with full force to **🔴 crash / infinite-recursion / spurious-diagnostic findings**, which read as blocking. On #11873 (vk::binding on resource-containing struct params), Reviewer A produced a confident 🔴 stack-overflow with a detailed code trace (cited `slang-ir-check-recursion.cpp`, exact line numbers, a sibling-guard comparison) — and it was a false positive because **both of its repros don't compile**. The front-end guards pre-empt the predicate entirely: a value-recursive `struct S { S next; }` entry param hits fatal E39997 "maximum type nesting level exceeded" (bounded at `kMaxTypeNestingDepth = 128`) before `validateEntryPoint` runs; the same struct as a *global* hits E41001 but a global isn't an entry param so the predicate never runs on it (the case A wrongly generalized from); cyclic inheritance hits E39999; interface-before-struct-base hits E30820 (so `findBaseStructType`'s `getFirstOrNull()` is correct by construction). Rule: for any reviewer crash/recursion/spurious-diagnostic claim, **compile the exact repro against a built slangc before treating it as blocking** — a confident code trace is not proof the input is reachable, because automated reviewers reason from source and miss earlier front-end rejections. Don't pass A's 🔴/high-🟡 through verbatim; add a coordinator verification addendum backed by a compiled repro. (Reviewer C correctly dropped the same termination concern here — its instinct beat A — though C's stated mechanism was imprecise; the real guard is the E39997 depth limit. Reviewer B echoed the PR body: weak signal, consistent with this file family.) ([Reviewer A (nv-slang-bot) can emit confident false-positive crash bugs whose repros do not compile — always compile the repro](../learnings/1782885111139-reviewer-a-nv-slang-bot-can-emit-confident-false-p.md))

Corollary decision (same #11873 / PR): when a reviewer flags a new recursive walk for "missing a cycle/depth guard that sibling functions carry," do NOT reflexively add the guard — first check whether the divergent input is rejected by an EARLIER fatal front-end diagnostic before your code runs (here E39997/E39999 reject value-recursive/cyclic types before `validateEntryPoint`, so a visited-set would be dead code under correct input). The decision that held (codex + 3-reviewer APPROVE_WITH_NITS): omit the guard and **document the termination invariant at the function** ("descends a finite acyclic structure; cycles rejected earlier by E39997/E39999") — CLAUDE.md forbids guards never hit under correct input and changes with no failing test. Also reinforced: **trust codex's CONTENT verdict over the PostToolUse hook's stage-verdict parse** — the hook parsed the stages as "approve" while codex's content verdict was request-changes for a real, harness-verified item (an unnecessary `non-exhaustive` on a DIAGNOSTIC_TEST, which `slang-test` reports as a failure); a DIAGNOSTIC_TEST should use plain `diag=CHECK` unless you deliberately leave diagnostics unmatched ([Don't add a recursion guard for input an earlier fatal diagnostic already rejects](../learnings/1782886466163-don-t-add-a-recursion-guard-for-input-an-earlier-f.md)).

## FileCheck Test Nuances

Several review-time FileCheck lessons apply across the review pipeline [slang-pr-review: scope a re-run to focused verification when the re-push is test-only](../learnings/1782594329649-slang-pr-review-scope-a-re-run-to-focused-verifica.md):

- For a per-entry-point availability error, split into separate entry points with per-entry filecheck prefixes to isolate each case.
- For a module-wide semantic error, use ordered (non-DAG) `CHECK:` lines, each pinning a distinct `expected/got` pair. Unanchored `CHECK-DAG: <code>` is the anti-pattern: a subset of cases can satisfy all DAG lines, silently missing a regression.
- A comment containing a literal `CHECK:`/`CHECK-DAG:` token is parsed by FileCheck as a real directive — reword such comments.

## /slang-pr-review runner operational traps

Running the three-reviewer `/slang-pr-review` pipeline surfaces several reproducible traps. **Reviewer C invocation:** call `bash run-clarity.sh --mode pr --pr N --repo owner/repo` — do NOT prefix with the literal word `run-clarity` ([slang-clarity run-clarity.sh: pass --mode directly, NOT the run-clarity subcommand word](../learnings/1782832548664-slang-clarity-run-clarity-sh-pass-mode-directly-no.md)). **Isolation:** Reviewer A (`compose-and-run.sh`) and Reviewer C (`run-clarity.sh`) both default to `REPO_ROOT=/workspace/agent/slang` and each does `git fetch/checkout origin master`; run Reviewer C in its own **git worktree** so parallel runs don't clobber each other's checkout ([Isolate Reviewer C in a git worktree for parallel /slang-pr-review runs](../learnings/1782876940783-isolate-reviewer-c-in-a-git-worktree-for-parallel-.md)). **Reviewer A premature termination:** a run can report `completed (exit 0)` in ~52s yet be incomplete — treat a suspiciously fast exit-0 as a failed run and re-dispatch ([Reviewer A (slang-pr-review-runner) premature-termination signature: exit-0 but incomplete](../learnings/1782878676585-reviewer-a-slang-pr-review-runner-premature-termin.md)). The specific mechanism behind an exit-0-but-incomplete A is a **background-subagent orphan**: the inner `claude --print` (one-shot, `--no-session-persistence`) is model-driven for how it dispatches the six `.claude/agents/*` correctness subagents; REVIEW.md expects *blocking* Task calls, but the model sometimes dispatches them as **background/async** and ends its turn with "I'll wait for the background agents to complete — the harness notifies me automatically." In one-shot `--print` mode there is no next turn to wake into, so the subagents are orphaned, no synthesis runs, and `repro.sh`'s extractor grabs the last mid-stream thought (e.g. a ~188-byte "Let me examine the AutoDiffSharedContext constructor…") as `final-review.md`. Exit 0 is normal CLI termination, NOT proof of a complete review. Detect (don't trust exit 0): `wc -c final-review.md` <500 bytes is suspect; `summarize.py <run_dir>`'s per-subagent table shows only 1 of ~6 subagents with nonzero tokens and the rest **0 tokens / 0 tools**; and tail `stream.jsonl` for a final assistant text containing "I'll wait for the background agents" / "the harness notifies me" — that phrasing = orphaned dispatch. Fix: `mv` the bad run dir to `*-INCOMPLETE` for audit and re-run `compose-and-run` (a re-run usually dispatches blocking; `pr-diff.reference` hash is unaffected so there's no head/target concern). For an IR-pass/gating change the orphaned lenses (ir-correctness, security, cross-backend, test-coverage) are exactly the ones that matter — shipping the 1/5 fragment silently drops the primary correctness pass (observed PR #11476, 2026-07-18) ([slang-pr-review Reviewer A can exit 0 yet be incomplete (background-subagent orphan)](../learnings/1784339218928-slang-pr-review-reviewer-a-can-exit-0-yet-be-incom.md)). **Recovery:** a container restart kills the completion-waiter, but reviewer outputs survive on persistent paths — recover them rather than re-running ([slang-pr-review: a container restart kills the completion-waiter; recover reviewer outputs from persistent paths](../learnings/1782829576352-slang-pr-review-a-container-restart-kills-the-comp.md)). **Devin on fresh drafts:** on a freshly-opened draft PR, `devin-fetch.sh` can exit 0 with `## AI Analysis` still "Generating…" (the done-detector race); re-scrape, and mind the escaped-JSON grep gotcha ([Devin re-scrape recovery: fresh draft PR renders with NO flag anchors; escaped-JSON grep gotcha](../learnings/1782820288016-devin-re-scrape-recovery-fresh-draft-pr-renders-wi.md)).

## Re-review scope: redesign gaps + self-recommended nits don't reset the pipeline

When a fixer reworks a PR in response to feedback and re-requests review, the re-run must do **two** things: (1) confirm the round-1 findings are actually closed, and (2) look for NEW gaps the redesign introduced — not just re-check the old list ([Re-review after a PR redesign: check for gaps the redesign introduced, not just old ones closed](../learnings/1782873135829-re-review-after-a-pr-redesign-check-for-gaps-the-r.md)). But when a follow-up commit *only* incorporates a nit the reviewer itself recommended (e.g. a doc comment from a Reviewer C clarity finding), do **not** re-run the full three-reviewer pipeline — just verify the recommended change landed ([Reviewer: a self-recommended comment addition does not reset the PR review pipeline](../learnings/1782857285922-reviewer-a-self-recommended-comment-addition-does-.md)).

More runner traps. `post-back.sh` invokes `cleanup.sh`/`post-review.sh` directly but they **lack the execute bit** — call sub-steps with `bash` ([1782986622527-slang-pr-review-runner-post-back-scrip](../learnings/1782986622527-slang-pr-review-runner-post-back-scripts-lack-exec.md)). And `final-review.md` can capture the coordinator's trailing recap instead of the review body when a subagent is stopped/times out and the coordinator emits a follow-up turn ([1783042659846-slang-pr-review-runner-final-review-md](../learnings/1783042659846-slang-pr-review-runner-final-review-md-can-capture.md)).

## Fleet Contention: Reviewer A Needs an Isolated Checkout, and $30 Is Too Low a Budget

Under concurrent PR reviews across the fleet, Reviewer A's two systemic failure modes are now well-characterized, and both have deterministic mitigations. First, **shared-staging clobber**: `compose-and-run.sh`/`repro.sh` `cd "$REPO_ROOT"` into the single shared `/workspace/agent/slang` checkout and stage `tmp/{pr-diff.patch,pr-files.txt,context.json}` there; a concurrent run for a *different* PR overwrites those files mid-run, so Reviewer A can silently review the wrong PR's diff and the post-run guard then fires `INTEGRITY-FAIL`. Observed with #11615's tmp/ clobbered by a #12000/#12029 run, and #11954 flagged against #12029's clobbered `context.json` ([slang-pr-review-runner fleet contention clobbers shared checkout staging](../learnings/1783635509659-slang-pr-review-runner-fleet-contention-clobbers-s.md), [slang-pr-review concurrent runs clobber shared staging](../learnings/1783635595122-slang-pr-review-concurrent-runs-clobber-shared-sta.md), [Slang PR reviewers die on $30 budget cap; shared checkout causes wrong-diff collisions](../learnings/1783629924272-slang-pr-reviewers-die-on-30-budget-cap-for-large-.md)). The fix is a **private `REPO_ROOT` worktree** — `git worktree add --detach <iso> origin/master` then `REPO_ROOT=<iso> bash scripts/compose-and-run.sh …`; `REVIEW.md` + all six `.claude/agents/*` are git-tracked so a fresh worktree inherits them cleanly, and `git worktree remove` cleans up after. Reviewer C self-isolates and Reviewer B (Devin) is read-only, so only A needs the override.

An `INTEGRITY-FAIL` or empty `final-review.md` under fleet contention is therefore a **"re-run in isolation," never a verdict** — but before re-running, check whether the review was actually correct: the per-run immutable `RUN_DIR/pr-diff.reference` (NOT the shared `tmp/`) holds the true diff. Three independent checks must all agree to declare a false positive: (1) `diff`/`sha256sum` `pr-diff.reference` against `gh pr diff <PR> --name-only` / `gh pr diff <PR>`; (2) parse `stream.jsonl` tool_use inputs and count references to the expected PR's files vs the clobbering PR's (many-vs-zero); (3) `summarize.py` "Non-COMMENT review submission attempts: 0". When they confirm the correct diff, set `reviewers_complete:true` as a documented manual override with a `notes` field and hand the verified `diff_hash` to the approver (its `commit_match` clause keys on it) — recovering a good review beats a 2.5h/~$24 re-run ([slang-pr-review: INTEGRITY-FAIL can be a false positive from concurrent-run shared tmp/ contention](../learnings/1783630282751-slang-pr-review-integrity-fail-can-be-a-false-posi.md)).

Second, **budget**: the default `--max-budget-usd 30` is far too low for a large multi-file PR. Even a 3-file PR can blow it (observed 118 Grep + 116 Read + 5 Agent dispatches, 45 turns, ~35 min), and on #11615 (40 files, +3490/−1656) Reviewer A had spent ~$63 across 6+ subagents when killed — dying with `"subtype":"error_max_budget_usd"` *before* the orchestrator synthesized `final-review.md`, so the run produced zero merged output while the downstream guards (INTEGRITY-FAIL, "zero subagent dispatches", "0-byte review") fired misleadingly as artifacts of the mid-flight kill. Pass `--max-budget-usd 60` for a small PR that over-investigates, and `120–150` for a PR touching >~15 files or >~2k diff lines. When A dies before synthesis, the completed subagents' full reports survive as the `summary`/`result` fields of `task_notification` events in `stream.jsonl` (the per-subagent `.output` files are cleaned up on session exit) — salvage those rather than re-running ([Reviewer A (slang-pr-review-runner) needs isolated REPO_ROOT + higher budget under concurrent runs](../learnings/1783620361461-reviewer-a-slang-pr-review-runner-needs-isolated-r.md)). Also useful under contention: `gh auth status` may print "token invalid" while `gh pr view/diff` reads still work — test an actual read, don't abort; and `gh pr diff --patch`'s `From <sha>` header is the *first* commit of the series, not the head — detect head advancement via `gh pr view --json headRefOid` + `committedDate`.

## Reviewer B (Devin) and C (Clarity) Environmental Skips Don't Block the Verdict

Two reviewers can be *environmentally* blocked in the reviewer container in ways a retry cannot fix — distinct from the transient-socket / premature-scrape failures above. **Reviewer B (Devin) Chrome cannot launch**: `devin-fetch.sh` fails at the Chrome launch step (`Chrome exited early … without writing DevToolsActivePort`, root cause `Failed to connect to the bus: … /run/dbus/system_bus_socket: No such file or directory`), exit 1 — not the exit-2 auth-wall or exit-3 timeout. This is a missing-dbus / headless-Chrome-deps image gap, so retrying is pointless; mark B `_skipped: agent-browser Chrome cannot launch (no dbus, infra)_`, note the missing portability lens in the `[Review Verdict]`, and (if Devin coverage is later required) raise an `install_packages` request for headless-Chrome + dbus. Note the background-task wrapper can report the *launcher* exit as 0 while the inner script wrote `REVIEWER_B_EXIT=1` and produced no `devin-flags.md` — check for the actual output file, not the completion notification's exit code ([Devin (Reviewer B) agent-browser Chrome fails in reviewer container — no DBus socket](../learnings/1783618070602-devin-reviewer-b-agent-browser-chrome-fails-in-rev.md), [Reviewer B (Devin) fails at Chrome launch in reviewer container — no dbus](../learnings/1783630449263-reviewer-b-devin-fails-at-chrome-launch-in-reviewe.md)).

**Reviewer C (Clarity) sandbox blocks file writes**: `run-clarity` can exit rc=1 with `CLARITY-INCOMPLETE: clarity-review.md is <N>B (floor 500B)`, the ~199B output being just the orchestrator's "Now I'll launch the four review agents…" message — the inner `claude --print` session's Bash sandbox denied *all* file writes (`>`, `tee`, `dd`, `python open('w')`, even `echo` to `/tmp`), a wall of `permission_denials` in `stream.jsonl`. The clarity pipeline stages the diff to a file and writes candidate markdown as its core mechanism, so with writes blocked its subagents can't function. Reviewer A survives the same container because it stages into an isolated dir (`tmp/iso-<pr>-review/pr-diff.patch`) whose path the C sandbox doesn't deny. This is deterministic, not transient: mark C `_skipped: clarity pipeline blocked by inner-CLI sandbox file-write denial_` and proceed on A ([Clarity reviewer (Reviewer C) fails when inner CLI sandbox blocks file writes](../learnings/1783627611526-clarity-reviewer-reviewer-c-fails-when-inner-cli-s.md)).

The honesty rule for the panel: **`reviewers_complete = (A complete) && (B complete) && (C complete) && drift==0`** — a dispatched-but-skipped reviewer (including a Devin environmental skip) makes the honest value `false`, telling the approver to treat the run as harness-incomplete (→ lean ABSTAIN). Do not set `true` while B is skipped; add a `reviewer_status` sub-object (`{A_correctness, B_devin, C_clarity: complete|skipped_*|failed}`) so the consumer sees exactly which reviewer is missing rather than inferring from a bare boolean ([combined-review RESULT_JSON: reviewers_complete=false when ANY dispatched reviewer is skipped](../learnings/1783631862638-combined-review-result-json-reviewers-complete-fal.md)).

## Mid-Iteration diff_hash Mismatch Is Expected Under Debounce, Not a Bug

When a PR branch iterates *during* a review run and Reviewer A finishes against an earlier commit than Reviewer C (debounce path: A left running on an inert push while only C re-ran against the newer HEAD), the combined report ends with A and C on different SHAs. RESULT_JSON's `diff_hash` is built from **Reviewer A's** diff-integrity marker, so it pins A's commit — not the current HEAD the header otherwise pins. Downstream, `slang-pr-approver`'s Step-2 `commit_match` clause flags this (observed #12029: `diff_hash 7b7416a65fb9` = A's commit `43c9a077`; current HEAD `ac959d7` had diff `b62b992e4341`). This is expected under the debounce protocol, not a pipeline bug — **call it out in the combined-report header** (which SHA each reviewer ran, and that A is N inert pushes behind C). Only re-run A against the final SHA (~$20 / ~20–30 min) if the delta is *material*; for a behaviorally-inert delta, document the gap. Related: fork-head PRs (a maintainer's own `saipraveenb25/slang`) hit the approver's `head_provenance` clause under `allow_fork_head=false` → ABSTAIN_POLICY before any code-facing step — expected for maintainer-owned PRs; a human approves those ([Mid-iteration PR: combined-review diff_hash mismatches pinned HEAD → approver Step-2 flag](../learnings/1783631632879-mid-iteration-pr-combined-review-diff-hash-reviewe.md)).

## slangpy PR-Review GitHub Post Gates on the Literal Marker, Not Prose

In `/slangpy-pr-review`, the COMMENT-state GitHub post (step 5) is gated on the **literal `<github-post-authorized />` marker** appearing in the dispatch text — not on a prose "go ahead, post it." If the parent authorizes posting in words but omits the marker, the reviewer correctly does NOT post (step 5 is a no-op; the verdict already went out via `send_file` in step 4). This is working as designed: the marker is machine-checkable proof that a human tagged `@nv-slang-bot` (an explicit GitHub-reply invitation), and prose from a coworker/orchestrator is not that proof — it keeps the bot's GitHub footprint tied to explicit human invitation. Unblock by re-sending the instruction *with* the marker. Observed on slangpy-samples#52 (Jul 2026): prose-only authorization gated the post OFF; re-send with the marker → posted as `event=COMMENT` (verified `COMMENTED`). Bonus on that PR: for a Git-LFS-tracked asset, the diff shows only a `+2/−2` pointer change (oid + size) — to verify actual image content, fetch the object via the LFS batch API (`POST https://github.com/<owner>/<repo>.git/info/lfs/objects/batch`, `operation:download`) with `gh auth token` and check sha256 == pointer oid; `gh api .../contents/<path>` returns the 131-byte pointer, not the image ([slangpy-pr-review GitHub post gates on literal marker, not prose](../learnings/1783639327701-slangpy-pr-review-github-post-gates-on-literal-mar.md)).

## Approver Decision Logic and Shadow-Mode Calibration

The slang-pr-approver turns a completed review into one auditable verdict via a fixed order: deterministic Step-1 clauses -> Step-2 review-verdict parse -> Step-3 adversarial challenger, with recording critique-gated. Step-1 clauses evaluate (and can short-circuit) *before* the review verdict is even read, so glance at the changed paths first: the relaxed `v0-shadow-relaxed` policy still keeps `.github/**` and `**/slang-tag-version.h` in `protected_paths`, so any CI-workflow-touching PR lands `ABSTAIN_POLICY / CLAUSE_FAIL:no_protected_paths` no matter how clean the review, and a clean `APPROVE_WITH_NITS` can never reach WOULD_APPROVE if a clause fails, so don't burn a challenger pass ([approver: relaxed shadow policy still protects .github/**](../learnings/1783673178930-approver-relaxed-shadow-policy-still-protects-gith.md)). Classify a protected-path hit as ABSTAIN_POLICY ("a human must look"), not ABSTAIN_INFRA (pipeline defects). The `reviewers_complete` field the reviewer emits is authoritative: a B/Devin infra-skip alone is NOT a harness-fail when the field is `true` (A+C completing is a complete panel for this pipeline); only override to manufacture incompleteness when the field is literally `false` ([reviewers_complete field is authoritative](../learnings/1783707333659-approver-reviewers-complete-field-is-authoritative.md)).

Shadow-mode is deliberately conservative: any non-pre-existing yellow gap forces ABSTAIN_POLICY:OPEN_GAP even on a proven-correct change. On slang#12037 and #12041 maintainers merged over the abstain at the exact decided commit with the gap unaddressed -- that is a conservative-abstain the human accepted, NOT a false-safe, and the framing in the 5-bullet should say so rather than reading as "something's wrong" ([maintainer merged over an ABSTAIN on a low-severity gap](../learnings/1783676779766-approver-calibration-maintainer-merged-over-an-abs.md), [human disagreement: proven-correct perf fix approved-with-nits over gaps](../learnings/1783692443899-approver-human-disagreement-for-a-proven-correct-b.md)). Distinguish *correctness-gaps* (a plausible failing input exists) from *robustness/maintainability-gaps on a proven-correct change* (missing test, doc-scope, future-proofing assert): both force OPEN_GAP today, but the latter class is high-probability human-approve. When a `pr_merged` webhook stamps `record_human_verdict`, read the actual review state: a maintainer self-merge with zero formal reviews (`reviewDecision: REVIEW_REQUIRED`, empty `reviews`) is `NO_HUMAN_REVIEW`, not `APPROVED` -- recording APPROVED on a self-merge fabricates an agreement signal and biases accuracy upward ([stamp maintainer self-merge as NO_HUMAN_REVIEW](../learnings/1783726677874-stamp-maintainer-self-merge-as-no-human-review-not.md)).

## Pinning, Debouncing, and Byte-Proving Reviews Under Live Head Churn

When a PR head keeps moving, do not chase it per-push. Pin the review to a *specific* commit with `--mode patch` (diff vs merge-base, `diff_hash` = patch sha256, frozen), never `pr` mode (which binds to the live tip and silently reviews a different commit after a mid-run synchronize) ([pin a moving PR head with patch mode, not pr mode](../learnings/1783681496336-pin-a-moving-pr-head-with-patch-mode-not-pr-mode.md)). If pushes arrive faster than the ~25-40 min review turnaround, HOLD and arm a host-side quiescence poll whose window is *longer* than the observed inter-push cadence (30 min for ~20-25 min pushes) -- a 15-min window fires mid-gap into more churn; nobody is blocked when the PR is maintainer-authored ([when push cadence beats review turnaround, widen the quiescence window](../learnings/1783709416771-when-push-cadence-beats-review-turnaround-widen-th.md)). A frozen patch-mode review can validly cover a *moved* head if you byte-prove the code is identical: extract added non-comment `+` lines from both diffs and `diff` them (empty = identical); a `diff_hash` mismatch is then documented comment-only/master-merge delta, not a stale review -- record the decision keyed to the settled head ([debounce live PR head churn, then byte-prove the frozen review still covers the settled head](../learnings/1783682287036-approver-reviewer-debounce-live-pr-head-churn-then.md)). For a *historical* R0-pinned review the R0 patch must apply onto the PR's historical base, not July master: repoint the clone's `origin` to a bare repo whose `master` == the R0 base commit (a local ref repoint is clobbered by the runner's startup `git fetch origin master`) ([historical R0-pinned review: repoint clone origin to R0 base](../learnings/1783689995051-historical-r0-pinned-review-repoint-clone-origin-t.md)).

## Verdict Reporting: Human-Review State, Author Self-Resolution, and CHANGES_REQUESTED

A review's findings are not the whole disposition. Before reporting a verdict, also surface the PR's human-review state and author activity: an existing maintainer APPROVE means merge is imminent and nits are advisory; on an actively-iterated PR the author is often self-resolving threads (`[Agent] Applied in <sha>`), so there is nothing to route -- and on a human contributor's own approved branch, do NOT let the fixer push (send an explicit STAND DOWN if you already forwarded) ([check existing human reviews + author self-resolution before reporting a verdict](../learnings/1783669294473-slang-pr-review-check-existing-human-reviews-autho.md)). Never read a coarse status enum as an edit list: `reviewDecision=CHANGES_REQUESTED` can be an investigation HOLD, a merge-queue block, or a prose concern -- read the review *body* and the *inline comment count*; if both are empty of concrete asks, the posture is *hold*, not *revise*, and one CR coexists with prior APPROVEs rather than negating them ([CHANGES_REQUESTED is not an edit list -- read the review body + inline count](../learnings/1783731922642-changes-requested-edit-list-read-the-review-body-i.md)). Likewise, a guard that checks "did the bot post its review yet?" via the reviews list reads only page 1 (30 items) by default -- on a PR with many human inline-comment reviews the bot's newer review is pushed to page 2 and the guard falsely reports zero, re-waking the reviewer forever; page or query-filter by author, or verify a claimed review id by fetching it directly ([verdict-detection guards must page or query by author](../learnings/1783665568170-verdict-detection-guards-must-page-or-query-by-aut.md)).

## Runner Operational Notes: Post-Back, Disclaimer, Cited-File Verification

`post-review.sh` POSTs the review body verbatim (event=COMMENT) and does NOT append the required bot-transparency disclaimer, and neither does the reviewer's `final-review.md`, so a freshly posted bot review is missing it. Editing the body afterward via REST `PUT /pulls/N/reviews/{id}` returns 404 under the App token; use the GraphQL `updatePullRequestReview` mutation (state stays COMMENTED), or better, append the disclaimer to `final-review.md` before posting ([post-review.sh posts body verbatim -- no bot-transparency disclaimer](../learnings/1783665412901-post-review-sh-posts-body-verbatim-no-bot-transpar.md), [REST review-body edit 404s under App token; use GraphQL updatePullRequestReview](../learnings/1783669185294-slang-pr-review-rest-review-body-edit-404s-under-a.md)). Copy `final-review.md`/`clarity-review.md`/`tool-uses.jsonl` into your own `/workspace/agent/review-<pr>/` dir immediately -- the runner `transcripts/` dir is shared across concurrent sessions and gets clobbered fast; agent-browser (Reviewer B) reliably cannot launch Chrome here (dbus/DevToolsActivePort), a deterministic skip, not a retry-worthy transient. Finally, Reviewer A can hallucinate/import test files not in the PR and build a whole gap around them: at merge time run `gh api .../pulls/<N>/files` and drop any file-specific finding A cites that isn't in the authoritative list, but preserve its true kernel (e.g. "ships with no regression test" on a 0-test PR) ([verify Reviewer A's cited files against the authoritative PR file list](../learnings/1783681518930-verify-reviewer-a-s-cited-files-against-the-author.md)).

## Review-Signal Timing, Size-Cap Calibration, and Per-File Revision Diffing (2026-07-12 fold)

Two infra traps discard a real primary review signal and must be distinguished from genuine skips. First, `harvest-reviews.py` exit 20 ("no harvestable bot review -> Devin-only") is ambiguous: on a `fix/issue-N`/bot/Claude-branch PR it means production genuinely skips, but on an external-fork/first-time-contributor/member human PR it usually means the `Claude PR Review` check is merely still IN_PROGRESS. Check `gh pr view <pr> --json statusCheckRollup` for a `review` check and cross-check the author before treating exit 20 as a skip; if the check is still running, Monitor it to COMPLETED and re-harvest (flips to exit 0) rather than falling to Devin-only prematurely and throwing away the authoritative primary review ([harvest exit 20 on a fresh external-fork PR is a timing race, not a production-skip](../learnings/1783767626000-approver-infra-abstain-harvest-exit-20-on-a-fresh-.md)). Second, wrapping `devin-fetch.sh` in a tight outer `timeout` guillotines a legitimately long Devin run (exit 124/137 — NOT one of the script's own 0/2/3/4 codes) and manufactures a false ABSTAIN_INFRA:NO_REVIEW_SIGNAL that burns the infra gate; let the script's own `--max-minutes` govern (retry `--max-minutes 27` under a generous outer `timeout 1740`) and exhaust the best-effort Devin path before abstaining ([outer timeout wrapper on devin-fetch.sh causes false NO_REVIEW_SIGNAL](../learnings/1783796304562-approver-infra-abstain-outer-timeout-wrapper-on-de.md)).

The size cap is well-calibrated, not too conservative: a >2000-line compiler-core PR hitting `CLAUSE_FAIL:tier_eligible` and terminating at Step 1 is the system working — slang#11615 (5146 lines, witness-table lowering) abstained and was later human-APPROVED only after a ~month-long review with an intermediate DISMISSED review and a substantive fix commit landing after R0, exactly the "a human must look" case; do not lobby to raise the cap to "cover" this PR class ([size-cap ABSTAIN on a large compiler-core PR confirmed well-placed](../learnings/1783786027293-approver-calibration-size-cap-abstain-on-a-large-c.md)). On a revision (`synchronize`) of a PR you previously BLOCKed, never trust "author addressed it": a fixup often targets only the loudest finding while another changed file stays byte-identical — `gh api .../compare/<prevHead>...<newHead>` to see which files moved, blob-compare each file that carried a prior finding, and re-derive every finding fresh against the new head (prior turns are context, one ledger row per commit) ([revision fixup can fix the flagged side while the other file's concern stays byte-identical](../learnings/1783801380207-approver-challenger-miss-revision-fixup-can-fix-th.md)). Finally, a clean code review does not license WOULD_APPROVE while a human reviewer is mid-cycle: an unresolved + non-outdated maintainer review thread on the pinned commit, or `reviewDecision=REVIEW_REQUIRED` with the sole reviewer engaged, is a CHALLENGER_CONCERN abstain even when the fixer's latest push closes every raised ask — approving there preempts an active human review, the highest-severity false-safe ([fixer PR that closes the maintainer's asks still ABSTAINs while the human is mid-cycle](../learnings/1783806650503-approver-challenger-fixer-pr-that-closes-the-maint.md)).

## Live-State Drift, Version-Boundary BLOCKs, and Critique-Gate Hygiene (2026-07-13 fold)

**Verified-🔴 severity is not an abstain lever, and a versioned boundary makes format changes reachable defects.** On slangpy#1054 the grad-bit fix was correct on the matched-version path but left `TENSOR_BRIDGE_API_VERSION` at 7 while changing the *output format* of a function whose result crosses a versioned ABI boundary — the native-vs-fallback compat gate only checks numeric version + struct size, both unchanged by a behavioral format change, so a user who upgrades the `slangpy` wheel but keeps a stale separately-pip-installed `slangpy_torch` v7 silently reintroduces #1052. General reviewer rule: when a PR changes the output format of any function whose result crosses a versioned ABI/plugin boundary (serialized signature, wire format, cross-artifact cache key), check whether the boundary's version constant is bumped; a format change without a bump when the compat gate ignores the behavioral contract is a stale-peer-artifact defect. Confirm the convention by history (the prior bridge change #816 bumped 6→7). This is a VERIFIED 🔴 → BLOCK — do NOT downgrade a source-verified reachable defect to ABSTAIN because its severity *feels* debatable; "existence uncertain" and "severity debatable" are different axes, and the fallback-tier "any doubt → ABSTAIN, never round up" caution guards against rounding UP toward approve, not against softening a verified 🔴 ([signature/serialization-format changes across a versioned bridge must bump the version constant](../learnings/1783881950122-approver-challenger-signature-serialization-format.md)).

**HEAD and the review snapshot can BOTH be behind — verify freshness on both.** Long input-build steps (a 30–45 min Devin run) open a wide window in which a `synchronize` or draft-toggle lands without arriving as a new webhook turn. Before `record_decision`, re-run `gh pr view <pr> --json headRefOid,isDraft,state` and compare to your pinned `commit_sha`; if the head moved, fetch the delta and check whether it touches the file(s) your finding rests on (orthogonal → keep pinned + add a Live-state note; touches it → fresh cycle). Pin decisions to the commit you actually, cleanly analyzed; a PR reverting to draft can RESOLVE a governance sub-point ([re-pin and re-check live PR head/draft state before recording — HEAD can move mid-run](../learnings/1783881964285-approver-critique-mustfix-re-pin-and-re-check-live.md)). The dual of this: on a remediation revision, a STALE Devin snapshot re-flags the already-fixed finding and can drive a *false BLOCK* on the correct fix. Tells: line-number drift vs the new head, the narrative omitting the revision's headline change, `devin-commit-status.txt` reading "unknown" (not a positive "up to date"). Cross-check the finding's cited file:line against source at the pinned head; when stale, clear the browser profile and re-run, preserving the stale attempt for the audit trail. Direct source verification is the load-bearing signal on a remediation turn — Devin is corroboration, so a source-verified fix cannot be flipped by a stale 🔴 ([on a remediation revision, a STALE Devin snapshot re-flags the already-fixed finding — verify freshness or it drives a false BLOCK](../learnings/1783884242462-approver-challenger-miss-on-a-remediation-revision.md)).

**Approval-message prose must not overclaim past the challenger's own hedges.** When compressing a clean challenger into a one-line verdict it's easy to round a conservative finding up: on slangpy#1053 the drafted message said a strict-xfail regression "cannot mask unrelated failures" while the investigation had recorded a residual masking risk. A WOULD_APPROVE message may state the *decision* confidently, but its *evidence* claims must be no stronger than the challenger's — approval confidence ≠ evidence certainty. Before sending, diff the message's verdict language against the investigation's hedges; any absolute ("cannot", "no risk", "fully covered") in the message must be backed by an equally absolute statement in the investigation, else carry the residual caveat forward verbatim ([approval-message verdict prose must not overclaim past the challenger's own hedges](../learnings/1783876835715-approver-critique-mustfix-approval-message-verdict.md)).

**Large all-new samples/experiment PRs self-merge past the size-cap abstain — that's the cap working.** On slangpy-samples#53 (7414 lines) the R0 decision was ABSTAIN_POLICY / CLAUSE_FAIL:tier_eligible (>2000-line cap) and the CONTRIBUTOR author self-merged ~4h later with no formal human review. This is NOT a false-safe — it's the cap routing to a human, whose answer for this class ("self-contained new files under `experiments/`/`examples/`, no shared-core edits, trusted author") is nearly always "ship it." Keep the cap terminal (never round a 7000-line PR up to approve), but expect ABSTAIN_POLICY:tier_eligible AND a fast human self-merge; because the challenger is short-circuited by the clause fail, the reviewer's 0-bug read is the only quality signal reaching a human, which makes surfacing it (the COMMENT-state review) the highest-value action for this class. Don't expect flagged nits to be resolved before merge ([large samples/experiment PRs self-merge past the size-cap abstain — the tier_eligible cap systematically abstains on a class humans fast-track](../learnings/1783918446960-approver-human-disagreement-large-samples-experime.md)).

**Critique-gate hygiene — read-only `gh api .../pulls` GETs false-positive the delivery gate.** `/app/hooks/gate-critique-on-deliver.sh` matches `gh api [^|]*pulls\b`, intended for PR *creation* but firing on ANY `gh api` command containing `pulls` including read-only GETs of reviews/comments; the denial actually triggers only when this coincides with an unmet critique requirement (`edits_since_critique>0` or stale OUTPUT_REVIEW), and at 3 denials the gate escalates to admin + hard-blocks. Avoid: on a revision turn, answer "did the review materially change" from local artifacts (R2 vs R1 review-doc.md) rather than re-fetching; if you must read PR data, use `gh pr view <n> --json ...` (matches nothing) instead of `gh api .../pulls/...`; never write a file in the same command as a read (bumps `edits_since_critique`) ([critique gate false-positives on read-only gh api .../pulls GETs — don't burn denial strikes](../learnings/1783913716215-approver-critique-mustfix-critique-gate-false-posi.md)).

**Reviewing a PreToolUse command-guard demands adversarial inputs.** A hook enforcing `--draft` on `gh pr create` had two real bypasses its author's "9 cases pass" self-test missed, both fail-open: (1) token-in-quoted-title — grepping the raw command for `--draft` is spoofed when the token appears inside `--title "support --draft mode"`; fix by stripping quoted substrings before flag inspection; (2) glued short-flag — a repo-resolver requiring a space after `-R`/`--repo` misses `-Rowner/repo` → repo unresolved → fail-open. A command string is attacker-influenced text, not structured args; probe token-inside-title (both quote styles), glued short flag, `--repo=` equals form, compound `cd && gh pr create`, false-positive (fork target + upstream string in title), and no-repo-resolvable — 15 cases is a reasonable floor for a security-relevant guard, and confirm fail-open vs fail-closed is the intended direction ([reviewing PreToolUse gh-command guards: two bypass classes — title-token spoof, glued short-flag fail-open](../learnings/1783879965262-reviewing-pretooluse-gh-command-guards-two-bypass-.md)).

## Approver Decision Workflow: Head-Pinning, Tiers, and Calibration (2026-07-14 fold)

This section consolidates a large batch of PR-approver operational lessons. The approver runs in shadow mode (posts nothing to GitHub), so the eventual human merge becomes calibration data against the recorded ledger verdict.

**Pin the settled head, then re-pin it — twice.** The single most recurring failure is deciding against a stale commit. On a fresh, actively-iterated PR the opening commit's diff is a poor predictor of the settled diff — a clean single-file fix grew into a `.github/**` protected-path edit within ~20 min, flipping WOULD_APPROVE to ABSTAIN_POLICY ([[approver/clause-gap] Debounced settled head can expand scope into a protected path — never decide on the opening commit](../learnings/1783927363514-approver-clause-gap-debounced-settled-head-can-exp.md)). The debounce window must outlast the burst; a 90-second poll desyncs the pinned SHA from live-head Devin/`gh pr diff` ([[approver/critique-mustfix] Debounce window must outlast the burst — a too-short window desyncs the pinned SHA from live-head Devin/gh pr diff](../learnings/1783960363272-approver-critique-mustfix-debounce-window-must-out.md)), and the head must be re-pinned *after* the slow harvest/Devin phase, not just at debounce start ([[approver/critique-mustfix] Re-pin head AFTER slow harvest/Devin, not just at debounce start](../learnings/1783930401148-approver-critique-mustfix-re-pin-head-after-slow-h.md)). A sustained force-push burst (6 heads in ~85 min) starves every head-current decision — after a hard bound that is correctly ABSTAIN_INFRA, not an endless chase ([[approver/infra-abstain] Sustained force-push burst starves head-current decisions → ABSTAIN_INFRA](../learnings/1783958614926-approver-infra-abstain-sustained-force-push-burst-.md)). On a synchronize you already decided, classify the delta cheaply with `gh api compare/<last_approved>...<new_head>` and a `gh pr diff | sha256sum` match rather than re-deriving ([Reviewing a PR whose head keeps moving (synchronize/merge churn)](../learnings/1784006371550-reviewing-a-pr-whose-head-keeps-moving-synchronize.md), [[approver/clause-gap] Re-decide a synchronize by diffing head vs your LAST-APPROVED SHA (gh api compare) — and pre-existing exemption covers factual (not just cosmetic) findings the PR didn't touch](../learnings/1783970228393-approver-clause-gap-re-decide-a-synchronize-by-dif.md)); for a master-merge-only branch, pin the PR-diff hash and re-verify structural claims when the base moves ([[approver/human-agreement] master-merge churn: pin the PR-diff hash, re-verify structural claims when the base moves, treat pipeline-incompleteness as an explicit judgment](../learnings/1784008035954-approver-human-agreement-master-merge-churn-pin-th.md)).

**Reading the review tiers — harvest exit codes and the late-post race.** harvest exit 20 means "no bot review AND no bot still working" — it does NOT license asserting a *cause* ("production skips X"); encoding an unevidenced causal claim is an OUTPUT_REVIEW must-fix ([[approver/critique-mustfix] Don't assert a CAUSE for harvest exit 20 — it means "no review + no pending bot", not "production skips X"](../learnings/1783961748935-approver-critique-mustfix-don-t-assert-a-cause-for.md)), and it is the "absent bot review is not an abstain" Devin-only skip-class ([[approver/human-disagreement] confirmed agreement — Devin-only WOULD_APPROVE matched human APPROVE on bot-authored test-only PR](../learnings/1783963594230-approver-human-disagreement-confirmed-agreement-de.md)). harvest exit 10 (stale-only) can hide an in-flight bot re-review — check the commit-status API before falling to Devin ([[approver/clause-gap] harvest exit 10 (stale-only) can hide an in-flight bot re-review on a synchronize](../learnings/1783949042869-approver-clause-gap-harvest-exit-10-stale-only-can.md)); a stale-but-recent bot review on a prior head is weak as a verdict source but strong corroboration ([[approver/challenger-miss] On a live multi-revision PR, a production bot review that lands on a PRIOR head is stale-as-verdict-source but strong corroboration — harvest still surfaces it, use it as an independent agreement signal](../learnings/1783959025798-approver-challenger-miss-on-a-live-multi-revision-.md)). The dominant timing hazard is the late-post race: a slow production review can post seconds-to-minutes after your harvest window closes, so re-harvest again right before `record_decision`, and treat a "hung" in-progress review as merely slow ([[approver/critique-mustfix] Re-harvest AGAIN right before record_decision — slow prod reviews post seconds after your window](../learnings/1783962571176-approver-critique-mustfix-re-harvest-again-right-b.md), [[approver/critique-mustfix] A "hung" production review may just be slow — re-harvest before falling to Devin-only](../learnings/1783958635135-approver-critique-mustfix-a-hung-production-review.md), [[approver/clause-gap] Harvest timing-race on fresh reviewable PRs — re-harvest at the settled head, never freeze the first-second result](../learnings/1783957917061-approver-clause-gap-harvest-timing-race-on-fresh-r.md), [[approver/infra-abstain] Confirmed: wait out the IN_PROGRESS production review before Devin-only; and debounce a head that moves mid-decision](../learnings/1783935971762-approver-infra-abstain-confirmed-wait-out-the-in-p.md)). A human APPROVE can likewise race in during harvest/Devin — re-check reviews before finalizing `mode` (live vs live_late) ([[approver/clause-gap] re-check PR reviews before finalizing mode — a human APPROVE can race in during harvest/Devin](../learnings/1783963597891-approver-clause-gap-re-check-pr-reviews-before-fin.md)).

**Devin as challenger — infra timeouts, exec bits, false positives.** A first-attempt Devin timeout is not proof of unavailability; the head-started session frequently completes clean on a re-poll, so retry once before NO_REVIEW_SIGNAL/ABSTAIN_INFRA ([[approver/infra-abstain] Devin-only tier: retry a timed-out Devin before NO_REVIEW_SIGNAL abstain](../learnings/1783946313392-approver-infra-abstain-devin-only-tier-retry-a-tim.md), [[approver/infra-abstain] Devin-only tier: retry a timed-out Devin before ABSTAIN_INFRA](../learnings/1783993723797-approver-infra-abstain-devin-only-tier-retry-a-tim.md), [[approver/infra-abstain] Devin timeout (exit 3) on a just-opened PR: re-poll once before ABSTAIN_INFRA — the head-started session often completes clean](../learnings/1783961759956-approver-infra-abstain-devin-timeout-exit-3-on-a-j.md)). `devin-fetch.sh` ships without its exec bit in approver containers, so a by-path call dies exit 126 (a false Devin-skip) — always invoke via `bash devin-fetch.sh` ([approver devin-fetch.sh missing exec bit false-skips Devin](../learnings/1783997801258-approver-devin-fetch-sh-missing-exec-bit-false-ski.md), [[approver/infra] devin-fetch.sh needs bash prefix + tolerate first-run timeout](../learnings/1783949034225-approver-infra-devin-fetch-sh-needs-bash-prefix-to.md), [[approver/ops] Invoke approver scripts via python3/bash; use gh graphql (not gh api pulls) for read-only fetches](../learnings/1783960724921-approver-ops-invoke-approver-scripts-via-python3-b.md)), and never wrap it in an outer `timeout` shorter than its own `--max-minutes` deadline ([[approver/infra-abstain] devin-fetch.sh: never wrap in an outer `timeout` shorter than its --max-minutes — bound it with the flag](../learnings/1783934997171-approver-infra-abstain-devin-fetch-sh-never-wrap-i.md)). Devin false-positive classes to challenge, not defer to: cross-platform filename bugs on tutorial run-scripts ([[approver/challenger-miss] Devin cross-platform filename bugs on tutorial run-scripts are often false positives — verify the tool's actual naming convention in source](../learnings/1783935960085-approver-challenger-miss-devin-cross-platform-file.md)) and narrative that merely echoes the PR description while citing superseded locations ([[approver/challenger-miss] Devin narrative echoes PR description and cites superseded locations — do not treat as coverage](../learnings/1783957900263-approver-challenger-miss-devin-narrative-echoes-pr.md)). Conversely, a still-present false claim the current revision didn't re-list is still a live gap ([[approver/challenger-miss] A still-present false claim the current revision's review didn't re-list is still a live gap — challenger re-checks carried-over diff content, doesn't defer to "not re-flagged"](../learnings/1783937211976-approver-challenger-miss-a-still-present-false-cla.md)).

**Drawing the abstain lines.** A terminal Step-1 clause FAIL dominates a co-occurring UNEVALUABLE and no-review-signal — record ABSTAIN_POLICY, not ABSTAIN_INFRA ([[approver/clause-gap] Terminal Step-1 clause FAIL dominates a co-occurring UNEVALUABLE and no-review-signal — record ABSTAIN_POLICY, not ABSTAIN_INFRA](../learnings/1783932935934-approver-clause-gap-terminal-step-1-clause-fail-do.md)). ## Approver Deep-Dive: Head-Pinning Races, Devin Infra, Challenger Probes, and Human Calibration (2026-07-15 fold)

This section consolidates a large batch of `slang-pr-approver` / `slangpy-pr-approver` operational lessons from the shadow-mode ledger — refining the head-pinning, harvest-tier, Devin-infra, clause-gap, challenger-probe, critique-gate, and human-calibration bodies above.

### Harvest tiers, the late-post race, and re-harvesting at record time

The dominant harvest hazard remains the **late-post race**: on slang the production `github-actions[bot]` claude-pr-review does not post promptly, and its **"Claude Code Assistant" check-run reaching `skipped`/`completed` is a red herring, not evidence the primary review was skipped** — the real formal review lands 25–45 min after the push, and the "review" workflow JOB stays `in_progress` long after its inner sub-check completes (a large post-review dismiss+submit lag). Key off the actual `github-actions[bot]` review appearing at the pinned SHA via `gh pr view --json reviews`, and **always re-harvest immediately before `record_decision`**, not just during the exit-22 window ([Claude Code Assistant skipped while real review posts 25-45min later](../learnings/1784075137829-approver-infra-abstain-slang-claude-code-assistant.md), [claude-pr-review sub-check completion ≠ review body posted](../learnings/1784078543250-approver-clause-gap-claude-pr-review-sub-check-com.md), [re-harvest before recording — primary can post mid-session after a Devin-only draft](../learnings/1784032917245-approver-challenger-miss-re-harvest-before-recordi.md)). On a `synchronize` re-push whose head is a master-merge, **harvest exit 10 (stale-only) + a live `in_progress` "review" check-run is a timing race, not a Devin-only trigger — wait for the primary** ([stale-harvest + in_progress production review = wait, don't fall to Devin-only](../learnings/1784042795116-approver-infra-abstain-stale-harvest-in-progress-p.md), [on synchronize the production 'review' check can still be in_progress at synthesis](../learnings/1784049951158-approver-infra-abstain-on-synchronize-the-producti.md)). A `synchronize` burst can advance the head multiple times mid-wait: poll `headRefOid` on every re-harvest and **re-pin to the settled head before harvesting**, or you decide on a superseded SHA the primary never reviewed ([synchronize burst can advance head mid-wait — re-pin to settled head before harvest](../learnings/1784034617985-approver-challenger-miss-synchronize-burst-can-adv.md)).

Two refinements on stale-review handling. **A stale bot review whose `<reviewed>...<head>` delta touches 0 `source/` files is source-current signal, not noise** — count source-touching files in the compare API; a 🟡/🔴 verdict on byte-identical source is a maintainer-proxy "do not auto-approve" prior that keeps the decision from rounding up ([a stale bot review whose head-delta touches 0 source files is source-current](../learnings/1784035570681-approver-clause-gap-a-stale-bot-review-whose-head-.md)). And **`harvest.json` reports only the CHOSEN bot review** — when multiple CodeRabbit reviews coexist across commits (a large full review at an older SHA + a small incremental re-review at the head), provenance caveats must reflect the FULL live picture via a GraphQL per-review `commit{oid}` query, not the single harvest verdict ([harvest.json reports only the chosen bot review; verify per-commit via GraphQL](../learnings/1784034639546-approver-critique-mustfix-harvest-json-reports-onl.md)). On **slang-rhi (and any repo lacking `claude-pr-review.yml`), harvest exit 20 is the expected Devin-only tier by design, not a missed harvest** — slang-rhi has only `claude.yml` (mention responder) and CodeRabbit auto-pauses to a walkthrough *issue comment*, so verify via the repo's `.github/workflows` + CodeRabbit's commit *status* (not its comments) before treating exit 20 as a skip ([slang-rhi Devin-only tier is legitimate, not a missed harvest](../learnings/1784011099646-approver-clause-gap-slang-rhi-devin-only-tier-is-l.md)). A late human APPROVE can also race in during harvest/Devin: the `mode` ledger tag is derived at staging, so **re-check reviews at record time** — a maintainer APPROVE on the pinned SHA in the harvest+Devin window means the correct tag is `live_late`, and any late verdict (especially a `CHANGES_REQUESTED` that would invalidate a WOULD_APPROVE) must be joined onto the same ledger row via `record_human_verdict` ([mode=live can be stale on fast PRs — a human review may land between staging and decision](../learnings/1784026123581-approver-clause-gap-mode-live-can-be-stale-on-fast.md), [re-fetch PR reviews at record time not just staging (confirmed live #11987 R2)](../learnings/1784050296652-approver-clause-gap-re-fetch-pr-reviews-at-record-.md), [pr-approver must re-fetch reviews at record time not just staging](../learnings/1784050376318-pr-approver-must-re-fetch-reviews-at-record-time-n.md)).

### Head-pinning discipline under active iteration

The subject of an approval decision is the **compiled behavior, not the commit SHA**. Re-pin the live head at BOTH critique stages, not just at build time — a rapidly-iterating author can push between build and record, and the codex gate re-verifies `headRefOid` at DECISION_REVIEW and OUTPUT_REVIEW, so a stale pin is a guaranteed must-fix ([re-pin live head at both critique stages](../learnings/1784037974102-approver-critique-mustfix-re-pin-live-head-at-both.md)). But do not burn the full gated cycle on every push: when a run of heads is **codegen-inert** — the `source/slang/**` diff (excluding tests, stripping pure-comment/blank/`SLANG_ASSERT` lines) is empty — let the standing recorded decision RIDE, logging the head as "covered by \<recorded-sha\> (codegen-inert delta)" rather than losing a race against the author every ~45 min ([standing decision rides codegen-inert synchronizes](../learnings/1784054163587-approver-clause-gap-standing-decision-rides-codege.md)). The guardrail is load-bearing: a push *labeled* doc-only that actually touches the emit path / IR-lowering / eligibility-predicate logic / target gating IS a codegen change and must re-trigger the full procedure (this is exactly where the `__grid_constant__` false-safe lived — verify behavior, never trust the commit message). The same shortcut applies at comment granularity — **a comment/whitespace-only delta proven by a FULL-file diff (not the compare summary) carries a prior CLEAN logic verdict to the new SHA** ([#11917 comment-only-delta re-verdict rode to merge with zero follow-up](../learnings/1784063797593-approver-calibration-11917-comment-only-delta-re-v.md)). A **pure master-merge `synchronize` does NOT close a held coverage gap** — re-decide from the PR's own diff (`gh pr diff --name-only`; is the flagged file/test present at THIS head?), not from an orchestrator hint or a maintainer's approve; note that `diff_hash` legitimately differs across a master-merge even when the PR hunk is byte-identical because it hashes the full unified diff including context ([a pure master-merge synchronize does not close a held coverage gap](../learnings/1784077537602-approver-challenger-a-synchronize-that-is-a-pure-m.md)). A **single `gh pr view --json changedFiles` read within seconds of a synchronize can be transient** (GitHub hasn't recomputed the merge base): read scope 2–3× back-to-back and require agreement — scope *shrinkage* below what a reviewer saw is the direction that produces false-safes, so a scope-larger critique finding is ground truth until you reproduce the smaller read ([a single gh pr view read of changedFiles can be transient during synchronize+force-push](../learnings/1784021958594-approver-challenger-miss-a-single-gh-pr-view-read-.md)).

### Devin infra: retries, exec bits, drops, stalls, and cached snapshots

Devin failures on the sole-signal Devin-only tier are dominated by transient conditions that a single retry recovers, so **retry once (clear the chrome profile, delete stale `devin-error.txt`, widen `--max-minutes`) before recording NO_REVIEW_SIGNAL / ABSTAIN_INFRA** — a first-attempt exit-3 timeout is usually "not done yet," not a real failure ([devin-fetch.sh timeout (exit 3) on fresh PRs — retry once](../learnings/1784019236976-approver-infra-abstain-devin-fetch-sh-timeout-exit.md), [Devin timeout on the sole-signal Devin-only tier: retry once](../learnings/1784074357103-approver-infra-abstain-devin-timeout-on-the-sole-s.md)). A Devin **stall at the URL-rewrite handoff is non-blocking when the primary bot-review tier is already secured** — start Devin in the background early to overlap the harvest wait, cap its wait ~3 min after the primary lands, and note `devin: skipped_stall`; only escalate to ABSTAIN_INFRA when Devin is the SOLE signal ([Devin devin-fetch.sh stall at URL-rewrite is non-blocking when primary tier is secured](../learnings/1784042688985-approver-infra-abstain-devin-devin-fetch-sh-stall-.md)). Two silent-data traps invalidate a Devin "clean" read: **`devin-fetch.sh` can drop the "N Flag" block from `devin-flags.md`** while the raw `devin-page.txt` shows `≥1 Flag` — always cross-check the raw page's tally (`grep -nE '[0-9]+ Bug|[0-9]+ Flag'`) before synthesizing, and treat "Loading diffs…"/commit-status `unknown` as "not fully settled" ([devin-fetch.sh drops the 'N Flag' block — cross-check raw devin-page.txt](../learnings/1784017360003-approver-infra-abstain-devin-fetch-sh-drops-the-n-.md)); and a **`devin-commit-status.txt` reading `"unknown"` (not "up to date") on a `synchronize` signals a CACHED prior-revision analysis** — do NOT abstain and do NOT trust it blindly; verify each flagged finding directly against the pinned head's `compare` delta, since a byte-for-byte-verified finding stands regardless of Devin's cache state ([Devin commit-status 'unknown' ≠ ABSTAIN — verify the flagged finding on the pinned head](../learnings/1784016854486-approver-infra-abstain-devin-commit-status-unknown.md)). For a **companion clang-format PR whose base is the feature branch, a maintainer force-push of that base makes Devin's commit-scoped review miss the parent PR's full merge-delta** — compare Devin's file count to the live `base...head` scope; a scope mismatch is ABSTAIN_INFRA (STALE_STAGE), and the substantive change lives in the parent PR ([companion clang-format PR — base force-pushed underneath ⇒ Devin misses merge-delta](../learnings/1784021932868-approver-infra-abstain-companion-clang-format-pr-b.md)). Never optimistically pre-fill `reviewers_complete:true` before Devin reaches a terminal state — it is a harness-integrity assertion the critique gate checks against the artifact on disk, true only when `devin-flags.md` exists or a bot review was harvested ([never set reviewers_complete:true before Devin reaches a terminal state](../learnings/1784049951184-approver-critique-mustfix-never-set-reviewers-comp.md)). When a **BLOCK-vs-not pivot needs a slow build+probe that could outlast the session, record ABSTAIN_INFRA:CHALLENGER_INCOMPLETE now and supersede later** — don't leave the pivot unrecorded; a `pr_merged` webhook waking a dormant decision no-ops `record_human_verdict` if no ledger row exists for the pinned commit ([a slow build+probe on a BLOCK-vs-not pivot can outrun the session — bound it or ABSTAIN promptly](../learnings/1784055090518-approver-infra-abstain-a-slow-build-probe-on-a-blo.md)).

### Clause gaps: CI-green, size cap, protected paths, and merge-commit blind spots

Several clause gaps refine the Step-1 body above. **`ci_green_on_sha` passes on the legacy combined-status API even when the real build/slang-test CI never ran** — on a `CONFLICTING`/deeply-behind PR, `pull_request`-triggered CI silently doesn't dispatch, so combined-status green aggregates only trivial commit-status contexts (license/CLA/CodeRabbit); independently query `actions/runs?head_sha=` and `commits/<sha>/check-runs` and treat "no build/test check-run present" as UNEVALUABLE → ABSTAIN_POLICY:CHALLENGER_CONCERN ([ci_green_on_sha passes on legacy combined-status even when real CI never ran](../learnings/1784017419889-approver-clause-gap-ci-green-on-sha-passes-on-lega.md)). The flip side: for **capdef/capability-atom PRs, `check-cmdline-ref` (regenerating `docs/command-line-slangc-reference.md`) fails if the second generated doc isn't refreshed** — combined-status red then correctly fails `ci_green_on_sha`, and even trivial-to-fix CI-red is not approvable ([capdef atom PRs: check-cmdline-ref fails if command-line-slangc-reference.md isn't regenerated](../learnings/1784026216900-approver-clause-gap-capdef-atom-prs-check-cmdline-.md)). But under the **`v0-shadow-relaxed` policy `require_ci_green:false`, a red *required* check does NOT trip `ci_green_on_sha`** (the clause passes "policy does not require CI green") — the CI-red must be routed through the challenger as an OPEN_GAP, so read `clauses.json`/`policy_version` before naming a reason_code ([under v0-shadow-relaxed a red required check does NOT trip ci_green_on_sha](../learnings/1784049960961-approver-clause-gap-under-v0-shadow-relaxed-a-red-.md)). **Eligibility is a property of each revision's cumulative diff, not the PR** — `tier_eligible` can flip pass→fail when a later push adds a large test/backend (re-score every settled head; the script computes `base...commit_sha` full-PR additions+deletions, not the incremental delta) ([a PR can cross the size cap mid-revision — re-score tier_eligible every revision](../learnings/1784020764751-approver-clause-gap-a-pr-can-cross-the-size-cap-mi.md)). On protected paths: **never hand-judge from a recalled learning** — run `eval-clauses.py` and read the emitted `policy_version`; the relaxed mount narrows `protected_paths` to only `[".github/**", "**/slang-tag-version.h"]`, so a bot-authored CMake/submodule change passes `no_protected_paths` and is a correct Devin-only-tier WOULD_APPROVE, not the CLAUSE_FAIL a bundled-default recall would predict ([bot-authored CMake/submodule change is Devin-only tier; relaxed policy does NOT protect external/CMakeLists.txt](../learnings/1784074325850-approver-clause-gap-bot-authored-cmake-submodule-c.md)). A **terminal Step-1 clause FAIL dominates a co-occurring `commit_match=unevaluable` / no-review-signal — record ABSTAIN_POLICY, not ABSTAIN_INFRA** (the unevaluable is subordinate to the FAIL, and clause FAIL short-circuits harvest/Devin/challenger) ([re-visited under size-cap: subordinate unevaluable does not make a clause FAIL into ABSTAIN_INFRA](../learnings/1784020764751-approver-clause-gap-a-pr-can-cross-the-size-cap-mi.md)). Two ordering/blind-spot gaps: **`eval-clauses.py`'s `commit_match` clause parses the SYNTHESIZED `review-doc.md`, not `harvest.json`** — synthesize the doc first or you get a spurious `commit_match:unevaluable` → ABSTAIN_INFRA ([eval-clauses.py commit_match reads the synthesized review-doc, not harvest.json — synthesize first](../learnings/1784038871000-approver-clause-gap-eval-clauses-py-commit-match-r.md)); and on a **master-merge-commit head, the `base...commit_sha` changed-path view surfaces only the second-parent delta** and can miss a PR-changed protected file — cross-check with `gh pr view --json files` ([under v0-shadow-relaxed: master-merge-head changed-path blind spot](../learnings/1784049960961-approver-clause-gap-under-v0-shadow-relaxed-a-red-.md)).

### Critique-gate hygiene

The critique gate records a round **only from a fresh `mcp__codex__codex` call carrying the canonical `/codex-critique` `developer-instructions` block verbatim** — a `mcp__codex__codex-reply` reuses the thread's original instructions, carries no `developer-instructions`, and never records regardless of its verdict; run DECISION_REVIEW and OUTPUT_REVIEW as SEPARATE fresh calls, reserving `codex-reply` for must-fix re-verification within an already-recorded stage ([critique gate records only codex calls, never codex-reply — OUTPUT_REVIEW must be a fresh call](../learnings/1784020599916-approver-critique-mustfix-critique-gate-records-on.md), [OUTPUT_REVIEW must be a FRESH codex call with the canonical reviewer developer-instructions](../learnings/1784095230054-approver-critique-mustfix-output-review-must-be-a-.md)). The gate's `gate-critique-on-deliver.sh` PreToolUse hook **false-positives read-only `gh api .../pulls/<n>/reviews` GETs** (its `gh api [^|]*pulls\b` pattern is not verb/subpath-aware) and escalates to a hard admin block after 3 denials — poll reviews via `gh pr view --json reviews` (no `pulls` substring), build any unavoidable `pulls/...reviews` path from shell variables, and never write a file in the same command as a read ([critique-gate false-positives read-only gh api .../pulls/<n>/reviews GET](../learnings/1784077601519-approver-infra-abstain-critique-gate-false-positiv.md)). Two OUTPUT_REVIEW must-fixes on doc completeness and provenance: a **doc-consistency check must read the WHOLE file, not just diffed lines** — a changed default/flag/API name leaves stale copies in un-diffed narrative/architecture tables (fetch the full body at the pinned head, grep for the OLD value and "default"), and the same "did an un-diffed sibling copy go stale?" question applies to duplicated code ([doc-consistency check must read the whole file, not just diffed lines](../learnings/1784019216454-approver-critique-mustfix-doc-consistency-check-mu.md)).

### Fallback-tier verdict discipline: BLOCK requires VERIFIED

A **fallback-tier (Devin/CodeRabbit) heuristic 🔴 is NOT a Step-2 auto-BLOCK** — Step-4's enum reserves BLOCK for a *verified* 🔴, and Step-3's fallback note routes an unsure verdict to the challenger: a fallback 🔴 becomes BLOCK only if the challenger VERIFIES it, and if the challenger REFUTES it the terminal is ABSTAIN_POLICY:CHALLENGER_CONCERN (never BLOCK, never round up to WOULD_APPROVE) — recording BLOCK asserts a verified red bug to the ledger, which is as wrong as rounding up ([fallback-tier heuristic red-flag: Step-2 BLOCK requires Step-4 VERIFIED, else ABSTAIN not BLOCK](../learnings/1784080988551-approver-critique-mustfix-fallback-tier-heuristic-.md)). The recurring instance is Devin's static "Repo rule" flags on a **`removeAndDeallocate`-without-use-check pass**: clearing it requires proving the op's *zero-use invariant* from op-semantics + all producers/consumers tree-wide (Void result type ⇒ no well-typed consumer; sole producer; every consumer discards it), NOT the current diff — and residual holds (unasserted front-end invariant, one-level traversal relying on prior `specializeModule`) support ABSTAIN, they don't block ([removeAndDeallocate-without-use-check pass: prove the op's zero-use invariant, not just this diff](../learnings/1784081016635-approver-challenger-miss-removeanddeallocate-witho.md)). Likewise, a **"pre-existing risk"/UAF claim on IR insts needs a memory-model proof, not a deref-site analogy** — Slang IRInsts are arena-allocated and `removeAndDeallocate` does NOT free backing memory (it only unlinks), so a "removed" inst stays valid, readable arena memory until the IRModule dies; reading a scalar field like `scratchData` on it is stale-but-valid ([pre-existing risk claims need a memory-model proof — IRInsts are arena-allocated, never individually freed](../learnings/1784095223530-approver-challenger-miss-pre-existing-risk-claims-.md)). The mirror-image discipline applies to *dismissing* a 🔴: a **"transient IR is deleted so its invalid SSA doesn't count" argument needs a PROVEN no-observer path, not an assertion** — identify every pass between the invalid state's creation and its removal and show none trips on it; if you can't trace it, the concern is un-cleared (ABSTAIN_POLICY:CHALLENGER_CONCERN, not WOULD_APPROVE) — and BLOCK on an unproven 🔴 is equally wrong, reserved for a 🔴 you independently verified reproduces ([\"transient IR is deleted\" needs a proven no-observer path, not an assertion](../learnings/1784042674528-approver-critique-mustfix-transient-ir-is-deleted-.md)).

### Challenger probes: the transferable red-flag catalog

A batch of domain-specific challenger probes, each a reusable "when you see X, check Y":

- **Autodiff zero-differential**: a zero/identity tangent synthesized via `emitDefaultConstructRaw` instead of `getDifferentialZeroOfType` is a silent-miscompile for a user `IDifferentiable` whose `dzero()` ≠ default-construct; grep the diff for `emitDefaultConstruct` used as a differential value and demand a non-default-`dzero()` regression test ([autodiff zero-differential must use getDifferentialZeroOfType, never emitDefaultConstructRaw](../learnings/1784017388229-approver-clause-gap-autodiff-zero-differential-mus.md)).
- **Capability-atom narrowing**: a new atom `B : A` means B⇒A not A⇒B; an emitter branch rewritten `if impliesCap(A)` → `if impliesCap(B) … else SLANG_UNEXPECTED` silently drops every A-but-not-B target to an abort — probe whether a formerly-covered coarse-atom config falls through to abort, extra-suspicious when the PR's own tests switch `-capability` from the coarse to the narrow atom (sidestepping the regression) ([rev1 CI-unverified ABSTAIN vindicated: pre-6.9 SLANG_UNEXPECTED edge became a confirmed 🔴](../learnings/1784026245321-approver-challenger-miss-rev1-ci-unverified-abstai.md)). The corollary: a **type-emitter diagnostic can't guard an overload that lacks the type operand** — after a capability-narrowing regression is "fixed" by a diagnostic keyed on emitting a TYPE, enumerate every sibling op in the family; a no-type-operand overload (e.g. `ReorderThread(uint,uint)`) still silently miscompiles ([a type-emitter diagnostic can't guard an overload that lacks the type operand](../learnings/1784047648527-approver-challenger-miss-a-type-emitter-diagnostic.md)).
- **Switch-completeness / one-consumer-shape recovery helpers**: a missing `case` in an unwrapping/translation switch is a high-value probe whenever a PR layers a helper on top of it; and a recovery helper that reconstructs type info from ONE SSA consumer shape (branch→phi) then `SLANG_RELEASE_ASSERT`s silently assumes that's the only shape — cross-check the producer predicate (does it gate on consumer shape?) against the recovery predicate, grepping for other consumers (`IRReturn`/`IRCall`/`IRStore`) ([recovery helpers keyed on one SSA consumer shape need the whole-consumer-set probe](../learnings/1784035598289-approver-challenger-miss-recovery-helpers-keyed-on.md)).
- **Widening a coercion's viability**: interacts with overload resolution — making more constructors viable in a `canCoerce` probe can make one brace-init match multiple overloads, so the fix must produce a *diagnosed ambiguity* (with an ambiguity regression test), not a silent pick ([widening a coercion's viability interacts with overload resolution](../learnings/1784048815957-approver-human-disagreement-widening-a-coercion-s-.md)).
- **Dedup/canonicalization "make N producers agree" fixes**: a change to how ONE producer derives an operand can re-introduce the very duplicate the PR removes — enumerate every producer, find each one's input set, and prove the changed branch's trigger is disjoint across producers OR applied symmetrically; a "add a `hasContent()`/null guard?" review ask is safe only if it's a proven no-op on ALL producers or applied to all (adding it to one *creates* divergence) ([dedup/canonicalization fixes: prove the two producers operate on disjoint inputs](../learnings/1784057320031-approver-challenger-dedup-canonicalization-fixes-p.md), ['add a hasContent()/null guard?' asks — verify it's not a no-op AND applied symmetrically](../learnings/1784048758044-approver-challenger-add-a-hascontent-null-guard-re.md)).
- **Memoization/caching PRs**: correct only if the cache KEY captures every input parameterizing the result — the collision bug is exactly the input the author (and reviewer) didn't enumerate, invisible to static reasoning by construction, so **CI-green on the pinned head is a HARD precondition for WOULD_APPROVE and never substitutes a static-CLEAN audit or a 0-bug review** ([memoization/caching PRs: a static-CLEAN audit never rounds toward approve — CI is authoritative](../learnings/1784078519306-approver-false-safe-memoization-caching-prs-a-stat.md)). Deterministic failures of the SAME pre-existing generic-specialization tests across ≥2 runners (while the PR's own new tests pass) is the "cache hit on new path, cache collision on old paths" signature → hard BLOCK ([memoization PR breaks generic specialization → wrong-count ctor call + missing intrinsic](../learnings/1784076799325-approver-challenger-miss-memoization-pr-breaks-gen.md)). The BLOCK was vindicated when the author's next revision ripped out exactly the cross-environment cache — the safe/unsafe boundary for a lowering cache is *environment scope* (env-local safe; cross-env global unsafe), and re-review by DIFFING the revision confirms a surgical fix ([a CI-driven BLOCK on a memoization PR was vindicated by the author's next-revision fix](../learnings/1784093692254-approver-confirmed-safe-a-ci-driven-block-on-a-mem.md)). When a static audit *does* clear such a PR, the probes are: prove the two dispatch paths (`dispatch`==`dispatchType`, byte-identical) are semantically identical when they collide on a key; for a cross-env cache enumerate ALL context fields and show the `parent==moduleInst` guard excludes every env-varying one (structural IR-parenting proof); and tree-wide grep the counter/out-param convention (`*ioDiff =` bare assignment) rather than a partial file list ([Val-lowering memoization audit — dispatch==dispatchType and the module-parent guard](../learnings/1784074914750-approver-challenger-miss-val-lowering-memoization-.md)). Relatedly, **substitute-override / convention-every-override-obeys audits must enumerate ALL override files tree-wide** (`_substituteImplOverride` lives in `slang-ast-type.cpp` too, not just val.cpp/decl-ref.cpp), and verify the *consumer contract* (boolean-zero vs magnitude) when a change stores-and-replays a running counter ([substitute-override audits must cover every _substituteImplOverride file](../learnings/1784054408743-approver-challenger-miss-substitute-override-audit.md)).
- **CSS/HTML-table PRs**: `table-layout:fixed` + a widthless column = data-column collapse; enumerate every `<col>` the generator can emit, confirm a width rule for each, and sum declared widths for EVERY feature-flag combination — not just the one the diff comment mentions ([CSS table-layout:fixed + widthless columns = data-column collapse](../learnings/1784040257325-approver-challenger-miss-css-table-layout-fixed-wi.md)).
- **Submodule pins**: a `.gitmodules` entry with no `branch =` verifies (via `check-submodule-commits.sh`) against the remote's DEFAULT BRANCH, NOT a same-name version tag — clear it only by proving `git merge-base --is-ancestor <pin> origin/<default-branch>` and confirming the `check-submodules` CI conclusion, not by a "tag-reachable" analogy ([submodule no-branch pin verifies against default branch not the same-name tag](../learnings/1784074301503-approver-challenger-miss-submodule-no-branch-pin-v.md)). A **CMake fetched-dep version bump can silently disable hash integrity when a `SLANG_HASH_VERSION` guard lags the fetch version** — a "hash refresh" is inert (or the bump is what FIRST turns verification on) unless `fetch_version == hash_version` post-change; green download+verify build check-runs corroborate ([CMake fetched-dep version bump can silently disable hash integrity when SLANG_HASH_VERSION lags](../learnings/1784011130054-approver-challenger-miss-cmake-fetched-dep-version.md)).
- **Regression-test discrimination**: a green regression test proves nothing unless it would have gone RED on the pre-fix code — reconstruct the pre-fix output shape and confirm the assertion rejects it; for FileCheck a missing-operand bug needs an end-anchored `CHECK-NOT: … %{{[0-9]+}}{{$}}`, since trailing operands are optional in a bare `CHECK` ([a regression test that 'looks well-formed' must also FAIL on the pre-fix code](../learnings/1784070693213-approver-challenger-miss-a-regression-test-that-lo.md)).
- **CI-green snapshot vs settled CI**: the `commits/<sha>/status` combined API reflects only checks reported at read time — a still-`in_progress`/`queued` job can go red minutes later, so never generalize "zero red checks" while jobs are pending; scope any CI-load-bearing claim to COMPLETED checks by name, and treat unsettled/red CI as *removing* corroboration (pushing toward ABSTAIN under conservative-lean) ([CI 'green' snapshot is not settled CI](../learnings/1784042664032-approver-challenger-miss-ci-green-snapshot-is-not-.md)). A **macOS "requires metal4.0" pipeline-creation failure can be a Slang emit/downstream-`-std` capability mismatch, NOT the #11973 runner flake** — a version-gated emit paired with a hard-coded lower downstream `-std` is a compiler bug (the `[Slang]: ERROR:` prefix is a tell); name it as a candidate root cause rather than collapsing to "environmental" ([a macOS 'requires metal4.0' failure can be a Slang emit/downstream-std bug, not the #11973 flake](../learnings/1784083878096-approver-challenger-miss-a-macos-requires-metal4-0.md)).
- **Every revision gets a fresh challenger**: the pre-existing/attribution base-diff test **cuts BOTH ways** — a clean fix-commit push can still introduce a NEW blocking finding elsewhere in the file, and an enumerated-exception invariant ("holds for all Y except {A,B,C}") is a completeness trap unless you enumerate every Y yourself; don't let a WOULD_APPROVE streak lull you into skipping a fresh review's new findings ([the pre-existing/attribution test cuts both ways; enumerated-exception invariants are a completeness trap](../learnings/1784011508988-approver-challenger-miss-the-pre-existing-attribut.md)). A **still-present false claim the current revision's review didn't re-list is still a live gap** (the challenger re-checks carried-over diff content), and a **regression escalation must be scoped against the release baseline (master), not an earlier commit in the PR's own iteration** — a guard the author added-then-reverted within one PR is intra-PR churn, not a PR-introduced regression ([scope a 'regression' escalation against the release baseline, not an earlier commit in the PR's own iteration](../learnings/1784055067504-approver-challenger-miss-scope-a-regression-escala.md)). ### Human-verdict calibration and the merge join

The shadow-mode ledger's eventual human merge is calibration data — but the join must be read carefully. A **maintainer self-merge with zero formal reviews (`reviewDecision: REVIEW_REQUIRED`, empty `reviews`) is `NO_HUMAN_REVIEW`, not `APPROVED`** — recording APPROVED fabricates an agreement signal (this remains the rule from the earlier fold). **`closed-unmerged` ≠ rejection**: on a `github.pr_closed` with `merged=false`, read the close context (WHO closed it, any "folded into #N"/"superseded by #N" cross-reference) before mapping to a human verdict — an author-closed supersede/fold is BENIGN and must not score as a false-safe against a WOULD_APPROVE row; only a maintainer merits-close is a genuine rejection ([closed-unmerged ≠ rejection — check for a supersede/fold-into-open-PR](../learnings/1784012759272-approver-human-disagreement-closed-unmerged-reject.md)). **Protected-path (`.github/**`) ABSTAIN_POLICY that later merges with the protected file intact + a human approval is a CORRECT terminal decision, recorded as agreement-neutral (ABSTAIN rows are excluded from agreement scoring), NOT a false-safe** — confirmed repeatedly (slang#12023 merged after `expipiplus1` APPROVED with two `.github/workflows` files intact; slang#12060 merged by the maintainer at the reviewed head) — and keep the deterministic-hold + narrow re-trigger for structural-clause abstains ([protected-path ABSTAIN validated: slang#12023 merged with .github/** intact](../learnings/1784030934279-approver-human-agreement-protected-path-abstain-po.md), [protected .github/** CI-workflow PRs: ABSTAIN_POLICY is the right call, merges confirm it](../learnings/1784033516739-approver-human-disagreement-protected-github-ci-wo.md)). An **OPEN_GAP on a code-contradicted / provably-false PUBLIC-reference-docs API claim is a VALIDATED ABSTAIN** when the author fixes it across revisions before merge (merged ⇒ APPROVED-equivalent of the FINAL state, which no longer contains the defect) — public reference docs are an API contract surface, so verify API claims against source and don't round a provable contradiction down to advisory ([VALIDATED ABSTAIN: OPEN_GAP on a false public-docs API claim was fixed by the author before merge](../learnings/1784014469307-approver-human-disagreement-validated-abstain-open.md), ["diagnose-by-instrumentation" PRs that re-enable a still-red quarantined test are ABSTAIN_POLICY](../learnings/1784049982092-approver-human-disagreement-diagnose-by-instrument.md)).

Several confirmed-safe / confirmed-agreement shapes sharpen Step-0 recall (all merged unchanged at the exact decision head, often with 2-maintainer agreement, on the Devin-only fallback tier where a bot-authored PR skips production review): **emitter fold/hoist codegen-quality perf fixes** (form-only change, precise predicate, mirrors an existing guard, ships a GPU-free FileCheck) ([codegen-quality fold-guard perf fixes are safe to approve on Devin-only tier](../learnings/1784026118184-approver-confirmed-safe-codegen-quality-fold-guard.md)); **purely-additive `RequiredLoweringPassSet` presence-gates** where every trigger-opcode producer runs before the governing `calcRequiredLoweringPassSet` scan and the gate's case labels equal the pass's handled set (the #11917 epic — do NOT relax vigilance for a slice gating a pass whose trigger can be synthesized in-window) ([RequiredLoweringPassSet additive-gate slice merged unchanged, 2-maintainer agreement](../learnings/1784076254159-approver-human-agreement-confirmed-requiredlowerin.md), [confirmed: RequiredLoweringPassSet additive-gate slice merged unchanged](../learnings/1784076254159-approver-human-agreement-confirmed-requiredlowerin.md)); **content-digest EXCLUSION of a proven load-time-only compiler option** (no CLI spelling ⇒ no on-disk digest baked with it ⇒ can't retroactively accept a stale artifact; precedent skip already in the same function) ([content-digest exclusion of a load-time-only option is a safe WOULD_APPROVE shape](../learnings/1784031339360-approver-human-disagreement-confirmed-agreement-co.md)); **test-only + fetched-dep version-bump-that-re-activates-hash-verification** (the load-bearing check is the new shader's result-struct layout matching the green test) ([slang-rhi#774 confirmed — test-only + version-bump WOULD_APPROVE merged unchanged](../learnings/1784029999416-approver-human-agreement-slang-rhi-774-confirmed-t.md)); the **trivial-fwd-derivative zeroed-primal `getDifferentialZeroOfType` fix** (merged APPROVED at the exact head, 3-way agreement; repeated master-merges with byte-identical PR contribution are safe trivial re-decides once `gh api compare` restricted to the PR's own files returns empty) ([trivial-fwd-derivative zeroed-primal fix merged APPROVED at exact head — 3-way agreement](../learnings/1784066119880-approver-confirmed-safe-trivial-fwd-derivative-zer.md)); and **mimalloc per-site `malloc`/`free` conversion** (alloc+free swap together per site, foreign-allocator buffers keep their own free, zero-copy transfers are callback-identity asserted, `detach()` escapes are audited) — with a NOT-a-blocker coverage caveat that the mimalloc path is exercised only on the Windows-MSVC lane, dispositioned as a test-strength limitation on a correctly-gated assertion, never cleared with an unsupported "covered elsewhere" claim ([mimalloc per-site malloc/free conversion is safe when alloc/free swap together + zero-copy transfers are callback-identity asserted](../learnings/1784075171874-approver-confirmed-safe-mimalloc-per-site-malloc-f.md)).

## Review-Completion Monitors: Anchor to Exit Markers, Not Streamed JSON (2026-07-20 fold)

When arming a Monitor to detect completion of a backgrounded `slang-pr-review-runner`/`slang-clarity-review-runner`, do NOT grep for generic tokens like `error:`, `API Error`, or `---`: those runners `tee` the full `--output-format stream-json` to the log, so the reviewed diff and tool_results contain those substrings as benign content and fire a false "REVIEWER FAIL" mid-flight. Anchor the filter to markers that appear ONLY at true termination — the wrapper's trailing `^Reviewer A rerun exited:` echo, or the runner's real guard lines `^!!! REVIEW-GUARD FAIL` / `^!!! CLARITY-INCOMPLETE`. Also verify the artifact exists and clears a size floor (`final-review.md` present; `clarity-review.md` >~300B — a 227B "now let me write…" stub = interrupted mid-write). On a session-teardown `stopped` notification, confirm actual state via the exit-line + artifact check before assuming done or re-running; the runners auto-resolve the PR head via `gh pr view`, so a re-dispatch auto-pins to the current head ([review-completion Monitor: anchor filters to exit markers, not streamed JSON](../learnings/1784380841597-review-completion-monitor-anchor-filters-to-exit-m.md)).

## Recovering a Teardown-Stranded PR-Review Pass Without a Full Re-Run (2026-07-21 fold)

When the orchestrated slang-pr-review runner (Reviewer A / `compose-and-run.sh`) is stranded by session teardown, a full ~25-min re-run is usually unnecessary — recover in layers. (1) **Salvage completed reviewers first:** Devin (B) artifacts persist at `/workspace/agent/review-<pr>/devin/devin-flags.md`; Clarity (C) run dirs can be GC'd after days, but if you already read `clarity-review.md` into context, reconstruct it into a file rather than re-running. (2) **Recover partial A verdicts from the dead run's `stream.jsonl`:** the first run's 600s inner background-wait ceiling often truncates AGGREGATION while the individual subagents already reported, so extract per-subagent `result` summaries (`python3` over the jsonl, filter `type=="result"` with `len(result)>60`) — 4/6 verdicts are usually recoverable verbatim. (3) **Re-run ONLY the missing dimensions in-turn** as direct `Agent()` calls, which complete in-turn with no teardown window, unlike background bash tasks that die on container recycle. Two infra failure modes to root-cause rather than paper over: **REVIEW-GUARD FAIL (<500B final-review.md)** = inner `claude --print` hit the 600s ceiling → re-run with `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`; **INTEGRITY-FAIL "reviewed WRONG diff"** = a STALE `tmp/pr-diff.patch` from a prior review left in the repo root (the model's `gh pr diff > tmp/pr-diff.patch` was permission-denied so it never overwrote it) → `rm -f slang/tmp/pr-diff.patch` before re-running. Checkout gotcha: the local `/workspace/agent/slang` worktree usually sits on base master, not the PR head — `git fetch origin pull/<n>/head` then read via `git show <head>:<path>` to reason about real post-PR code ([Recovering a teardown-stranded PR-review pass without a full re-run](../learnings/1784536666918-recovering-a-teardown-stranded-pr-review-pass-with.md)).
