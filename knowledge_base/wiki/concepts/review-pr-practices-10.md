# PR Review Practices (part 9) (part 2)

> **This page is part 2 of 2** of the PR Review Practices (part 9) synthesis (split 2026-08-07 to stay under the 40 KB read cap). Siblings: [part 1](review-pr-practices-9.md). The TL;DR below is shared across all parts.

## TL;DR
- **Every reviewer fails toward CLEAN.** Devin exit 0 is not a signal; Reviewer A can emit a 0-byte or budget-capped output; Reviewer C can skip environmentally. **Verify each reviewer produced findings before treating "no findings" as a result** — an absent reviewer and a clean reviewer are byte-identical downstream.
- **Watch the ARTIFACT, not the subagent.** A Devin subagent returns before `devin-fetch.sh` finishes; a detached reviewer's completion is proven by its exit marker, never by streamed JSON. Anchor monitors to exit markers.
- **Read the full page dump, not the summary file.** `devin-flags.md` can have an EMPTY `## Flags` section while `devin-page.txt` from the same run shows real findings — synthesizing from the summary records a false "0 findings" and carries a false-clean prior into the challenger.
- **Reviewer A needs an isolated checkout.** Fleet contention on a shared repo root corrupts runs; `$30` is too low a budget cap and produces silent truncation. Use fresh per-run out-dirs to avoid `/tmp` collisions.
- **Two bots agreeing measures shared priors, not correctness.** Independent bots flagging the same item is weak corroboration; read the human review thread before scoring any structure/maintainability gap.
- **A bot finding a named maintainer already overruled ON THIS PR is not an open gap** — but **lead with the technical grounds**, never the maintainer's preference. Maintainer preference is supporting context; a repo guideline is not cleared by taste alone.
- **A refuted 🔴 does not become WOULD_APPROVE**, and a standing human `CHANGES_REQUESTED` caps the verdict at ABSTAIN. Never round up.
- **A mid-iteration `diff_hash` mismatch is expected under debounce**, not a bug. Pin the head, byte-prove reviews against it, and re-verify a stale secondary reviewer's flags at the current head.
- **Re-review scope: redesign gaps and self-recommended nits do not reset the pipeline.** Additive nit rounds are fine; a full re-run is not.
- **The review signal is endpoint-split across three surfaces** (`pulls/N/reviews`, `pulls/N/comments`, `issues/N/comments`) and the harvest reads one. That split is a property of GitHub's data model, so **every consumer inherits the blind spot independently — fixing one instance is not fixing the class.**
- **A GitHub post gates on the literal marker, not on prose.** Post only in COMMENT state; never APPROVE/REQUEST_CHANGES from a runner.
- **Empirical probes can test the wrong sub-case.** A probe that varies the intended factor while holding the confound constant reads as decisive and proves nothing — name the factor and the confound before citing a control.
- **In an artifact where claims cite `file:line`, the UNCITED SENTENCE IS THE DEFECT** — in a document whose norm is citation, the citation outlier is where an inference got restated as an observation. Run that self-check mechanically over your own draft.
- **Recording is not routing.** Documenting a blocking infra defect any number of times never reaches a file only an operator can edit. The record serves the next agent; the escalation serves the fix — do both.
- **A stale webhook dispatch on an already-decided PR is a no-op plus a report, never a re-decision.** `record_decision` is idempotent per `(repo, pr, sha)`, so re-deciding CLOBBERS a human-joined calibration row with a verdict contaminated by post-hoc information.
- **Read approval state from `latestOpinionatedReviews`, never `latestReviews`.** `latestReviews` is each reviewer's most-recent review *of any kind*, so a later COMMENTED from the same author makes a live APPROVED vanish. When an API offers two similarly-named collections, one is "most recent event" and the other "current state" — pick the one whose *definition* answers your question, and distrust any field whose name describes recency when you need state. Then check the verdict's bound commit: an APPROVED at an older commit is push-invalidated; a DISMISSED at a stale commit is not a dismissal at head.
- **Name the system a status belongs to before asserting the status.** "Approved" is meaningless without "approved *in what*". Internal review pipelines, codex stages, and peer coworker verdicts are real approvals and are **zero GitHub reviews** — a PR can carry eleven internal rounds and still read `reviewCount: 0 / reviewDecision: REVIEW_REQUIRED` to the maintainer whose queue it lands in. The honest split form ("3 internal pipelines approve; 0 GitHub reviews") is longer and strictly stronger, because the compressed form reads as overstated the instant anyone runs the query.
- **Local build + green tests are not delivery.** The heavier the local verification, the more it masquerades as shipping — a 20-minute compile produces a sense of completion a `git push` does not. "Corrected locally but undelivered" and "never corrected" are indistinguishable from outside your container. Discriminate with `git show HEAD:<path> | grep -c` vs `grep -c <path>`, then verify against the **remote object** after pushing.
- **A local grep, a clean `git status`, and a successful checkout all fail toward the answer you want.** Ask what the output would look like if the work had *not* landed; if it looks the same, you have not measured. A checkout of the wrong ref exits 0, and "0 files changed" is the expected output of both "wrong ref" and "already up to date" — so verify content arrived with a grep for a revision-unique marker whose expected count is non-zero.
- **Before merging or rebasing into a branch you authored, fast-forward the remote tip first.** A maintainer with write access can push to a bot branch, and a stale worktree gives no signal: clean status, your commit at HEAD, your branch name. Prove `git merge-base --is-ancestor HEAD origin/<branch>`, `--ff-only` the remote, and only then merge master. Compare the **index** (`git diff --cached origin/master --stat`), not the worktree, so stale submodule pointers don't ride in as accidental reverts.
- **"Nobody touched it in N days" is an inference from the wrong instrument.** `updatedAt` and your local `git log` can agree with each other and both be wrong about who last wrote to the branch. `git log -1 --format='%an' origin/<branch>` can invert "close as superseded" into "engaged maintainer, needs a merge".
- **A byte-identical revert-drill is green on a dead flag BY CONSTRUCTION.** A gate whose flag is never set skips nothing it would otherwise have done, so emission is trivially unchanged and no test asserted the pass ran. The drill proves a gate does not BREAK things; it can never prove the gate FIRES. Demand a two-sided flag-fired control — trigger-present → pass ran (catches a dead flag), trigger-absent → flag stayed 0 (catches a stuck-on flag). The cross-off column is what makes it evidence rather than a demo.
- **Scope gate-review rigor to new-flag-plus-new-gate.** A widening-only change — new `case` labels broadening an existing flag false→true — is monotone and cannot create a dead flag. A probe that fires on the safe direction of a change class is a false-abstain generator, costing exactly as much as the miss it was meant to prevent.
- **Prefer a STRUCTURAL safety argument over a contingent one.** "Opcode A implies opcode B, so gating on A covers B" owes two separate audits: can something eliminate the implier before the scan, and is there a producer path where the implier is never produced at all. The second is cheaper to check, easier to miss, and stronger — a contingent argument rots silently when the optimizer changes; a structural one cannot.
- **Read the pass's whole entry point, not its main loop.** A second unconditional job is invisible to opcode-family reasoning, so gate exactness beats "this pass obviously handles opcode X". One control per job, not per pass. But "narrow" is not "dead": a narrow gate covered by a broader implication is defense-in-depth; only a gate that covers nothing is a defect worth headlining.
- **For a claim about INTENT, the diff is the artifact.** Current-state-plus-title reads cheaper than the introducing commit and silently omits authorial intent — the exact thing being reasoned about. Any "this assertion/guard/flag exists in order to …" claim requires `git log --oneline -- <path>` then `git show <sha> -- <path>`.
- **A partial fix is honest only through three things that are omissions by default:** a visibly-disabled test carrying the root cause in the file itself, no auto-close keyword, and a real follow-up ISSUE carrying the trace verbatim. Each omission is invisible in the diff and each fails in the direction of "looks complete".
- **Verify object freshness before trusting any probe.** A mid-struct edit to a shared header during an in-flight incremental build splits the struct's layout across objects; it still links, still runs, and every dump from that binary is worthless. Prove each consuming object's mtime exceeds the header's.

## Local Verification Is Not Delivery: the Remote Blob, the Named Ref, and Who Owns Your Branch HEAD (2026-08-07 fold)

Three incidents, one generator: **a measurement made inside your own container says nothing about the artifact anyone else reads.** Each failed at a different layer — the working tree, the ref you fetched into, the branch tip you assumed you owned — and each produced a clean, confident, wrong report after an expensive build.

**The working tree: verify the remote blob, not your checkout.** A session adopted a reviewer's proposed change, rebuilt the compiler, ran the full suite, measured every pre-registered criterion, and reported "adopted — all 8 checks pass." The change was an **uncommitted working-tree edit**; the reviewer fetched the remote and found the PR head still carrying the old form, plus a 404 on a test file reported as passing 2/2. Every measurement was true, and none of it was true of the artifact anyone else could read. This slips past a rule you already hold — *verify the published copy, not your working copy* — because it gets applied to the PR body and issue comments and skipped for the code: **building and testing feels like delivery.** A 20-minute compile plus a green suite produces a sense of completion that `git push` does not, and the heavier the local verification, the more convincingly it masquerades as shipping. The discriminator costs two seconds: `git show HEAD:path | grep -c '<change>'` returning 0 while `grep -c '<change>' path` returns 1 **is the entire bug**. After pushing, verify against the remote object — `git fetch origin <branch>:refs/remotes/origin/verify -f` then `git show refs/remotes/origin/verify:path | grep -c` — and do **not** use `gh api .../contents/<path>` for this on a large file: it returns HTTP success with a zero-length body past its inline size cap, which reads exactly like "the change is absent." Generalized: "corrected locally but undelivered" and "never corrected" are **indistinguishable from outside your container**, the same class as an absent reviewer being byte-identical to a clean one. Corollary for reviewers, and the reason this was caught at all: **keep re-reporting a delivery gap until the remote shows the change** — a gap mentioned once and dropped reads as retracted, and dropping this one would have meant dropping a correct finding [Building and testing feels like delivering — verify the REMOTE blob, because a local grep cannot distinguish "corrected but unpushed" from "never corrected"](wiki/learnings/1786073630147-building-and-testing-feels-like-delivering-verify-.md).

**The ref: `FETCH_HEAD` is mutable, and a checkout of the wrong ref fails silently.** Verifying the head of #12417, a session fetched the PR, then later ran `git checkout FETCH_HEAD -- <files>`. By then `FETCH_HEAD` pointed at **master** — every `git fetch` overwrites it, including one run by a **sibling session sharing the same clone**, which is normal since `/workspace/agent` is per-agent-group, not per-session. The checkout restored master content, **exited clean, and produced zero modified files**; a ~25-minute build then ran against pristine master under the belief it was testing the patch. **A checkout of the wrong ref is not an error: it succeeds, and "0 files changed" is the expected output of both "wrong ref" and "already up to date."** Remedy: fetch into a named ref you own (`git fetch <remote> pull/<N>/head:refs/pr/<N>`), check out *that*, and then **verify the content arrived with a grep for a revision-unique marker whose expected count is non-zero** — here the new loop conjunct and `kCoreModule_MaxVectorElementCount`. That grep is what caught this; nothing else did. Sibling trap from the same session: `pkill -f 'cmake --build --preset release'` **killed the caller's own shell** (exit 144) because `-f` matched the wrapper's own command line — use `pgrep -cx ninja`, and never `-f` a pattern that appears in your own argv [FETCH_HEAD is mutable and a checkout of the wrong ref fails silently](wiki/learnings/1786081698988-fetch-head-is-mutable-and-a-checkout-of-the-wrong-.md).

**The branch tip: a maintainer may own the HEAD of your own `fix/` branch.** Before merging or rebasing into a `fix/issue-<n>` branch you authored, prove your local tip is an ancestor of the remote tip. A maintainer with write access can push to a bot branch, and a stale worktree gives **no signal whatsoever**: `git status` clean, `git log -1` shows *your* commit, the branch name is yours. On #11981 / draft PR #12014 the worktree sat at its own commit `d1141f42d6`, 29 days stale, while the real PR head was `2e8c12db84` — *"Merge branch 'master' into fix/issue-11981"*, **authored by the maintainer on a bot-authored branch**; he had already done the catch-up merge. Merging master into the local HEAD and pushing would have produced a history **omitting the maintainer's merge**, deliverable only by `git push --force` — forbidden on a PR under review — stranding the work at the final step *after* a 20-minute build. The fast-forward-first ordering costs one command: fetch the branch's own refspec explicitly, `git merge-base --is-ancestor HEAD origin/fix/issue-<n>`, `git merge --ff-only origin/fix/issue-<n>` to adopt the real PR head, and only then `git merge origin/master`. Two independently fatal halves live inside this: (1) **`origin/fix/issue-<n>` may not exist locally at all** — the clone's fetch refspec was `+refs/heads/master:refs/remotes/origin/master`, master only, so `git log origin/fix/issue-11981` died with `fatal: ambiguous argument` and 29 days of `git fetch origin master` had silently refreshed *nothing* about the session's own branch; **a plain `git fetch` does not give you your branch's remote state — name the refspec.** (2) **"Nobody touched it in N days" is an inference from the wrong instrument** — a supervisor read 29 days of idleness as *the bot sitting on the PR*, when the same 29 days were *the maintainer having already handled it*; `updatedAt` and the local `git log` agreed with each other and were both wrong about who last wrote to the branch, and one `git log -1 --format='%an' origin/fix/issue-<n>` inverted the recommendation from "close as superseded" to "engaged maintainer, just needs the merge." Companion: **compare the INDEX, not the worktree.** `git diff --cached origin/master --stat` should name only your own files; the same worktree had `external/lz4` `-dirty` and three other submodules (`spirv-headers`, `spirv-tools`, `vulkan`) at wrong commits on disk, so the worktree diff showed 3 submodule pointer changes while the index diff showed only the 4 fix files — compare the index, or stale submodule pointers ride into the merge commit as accidental reverts of someone else's dependency bumps (the same lz4 had 41 tracked files under `build/` deleted in the working tree, breaking cmake configure with `add_subdirectory given source "lz4/build/cmake" which is not an existing directory`; fix is `git checkout -- build` inside the submodule) [A maintainer may own the HEAD of your own fix/ branch — --ff-only the remote before merging master](wiki/learnings/1786075880249-a-maintainer-may-own-the-head-of-your-own-fix-bran.md).

The unifying check across all three, to run before any "done" report: **ask what this output would look like if the thing were absent; if the answer is "the same," it is not a measurement.** A clean `git status`, a zero-exit checkout, a green suite, and a local `grep` hit all satisfy that condition — so each must be paired with a read of the remote object, a revision-unique marker, or an ancestry proof before it is evidence about the PR.

## Reviewing a Pass-Gating PR: the Drill That Cannot Fail, the Implication That Fails Structurally (2026-08-09 fold)

**The whole family above — an absent reviewer indistinguishable from a clean one, a local grep indistinguishable from a pushed change — has a compiler-side twin: a broken gate is indistinguishable from a working gate by every artifact an approval pipeline normally consumes.** The standard safety evidence for a PR that makes a compiler pass conditional is (1) test suites pass and (2) a **revert-drill** showing emitted output byte-identical to the ungated build. Both are green while the gate is completely broken, and not by accident: if the flag is **declared, gated on, but never set** because the scan has no arm for the triggering opcode, the gated pass never runs on any input, so it changes nothing, so emission is trivially identical — **the drill is green BY CONSTRUCTION**, and every test passes because no test asserted the pass had run. The drill measures "this gate does not break things"; it cannot measure "this gate works," and only the first claim is on the table. Worse in the concrete instance than "dead" suggests: the gate site preceded the struct's reset/scan and `RequiredLoweringPassSet`'s bools are **uninitialized**, so a too-early read is *indeterminate*, not reliably false. Provenance, stated in its final verified form: the `assumeAddress` dead flag was **real, but a transient in-development state of the batch-2 draft (PR #12336), caught by its author before publication — it never reached `master` or any remote ref**; the positive control at `master` shows `RequiredLoweringPassSet` (`slang-code-gen.h:52-88`) carrying **34 flags, all with setters, none named `assumeAddress`**, and PR #12336's own body says *"An **earlier draft** of this change added an `assumeAddress` flag… and never set it."* The correction ran wrong in **both** directions before landing there — first filed as a shipped defect, then over-corrected to "never happened" — so carry the meta-rule too: **"it happened" and "it shipped" are different claims, a prospective hazard needs a mechanism while a shipped one needs an artifact, and a retraction is itself a claim owing evidence.** In-tree corroboration that the drill really is blind: `tests/hlsl/lower-lvalue-cast-skip.slang` states in its own comment that skip-vs-run *"is a compile-time-only property that is not observable in emitted output"* — which is also why byte-identity can never see this loss, since what a diagnostic-bearing pass loses is a **diagnostic**, not codegen (the gate now has a shipped regression test, `tests/diagnostics/get-address-validation-gpu.slang`, expecting four `InvalidAddressOf` diagnostics that all vanish if the gate fails to fire) [green tests plus byte-identical output cannot detect a dead flag](wiki/learnings/1785827882400-reviewing-a-pass-gating-pr-green-tests-plus-byte-i.md), [gating PRs need two-sided flag-fired controls](wiki/learnings/1785828391431-gating-prs-need-two-sided-flag-fired-controls-slan.md).

**What to require instead is a TWO-SIDED control matrix, and in Slang one side is free.** Fires-positive alone catches a dead flag but misses a **stuck-on** flag (always true ⇒ the gate is decorative), so require both rows — *trigger PRESENT → pass ran* (the one that catches a dead flag; the flag is reachable) and *trigger ABSENT → pass skipped and the flag stayed 0* (the optimization actually fires, which is the point of the PR). **The cross-off column is what makes the matrix evidence rather than a demo**; the batch-2 matrix that worked was a dynamic-dispatch shape (3 flags fire, 1 stays off), a `__getAddress` shape (only that flag fires), and a trivial compute shader (all off). Slang hands you the positive side with **zero instrumentation**: `SLANG_PASS(f, …)` (`slang-emit.cpp:978-984`) stringifies `#passFunc` into `wrapPass(ctx, #passFunc, lambda, irModule, …)` (`slang-pass-wrapper.h:52-61`), which constructs `PassHooksRAII` whose ctor calls `prePassHooks` unconditionally and emits `"BEFORE " + passName` via `dumpIRForPass` when `-dump-ir-before` matches (`slang-pass-wrapper.cpp:55-66`). This is stronger than "the pass name shows up in the dump" because `SLANG_PASS(…)` expands to a **call expression**: under `if (flag) SLANG_PASS(…)` a false flag means the call is never evaluated ⇒ the RAII object is never constructed ⇒ no label; a true flag emits the label **from the wrapper, before the pass body runs**, so a pass that no-ops cannot confound it ⇒ **label-present ⟺ gate-fired**, exactly the channel byte-identity cannot provide. Scope the whole apparatus to **PRs that add a NEW FLAG AND A NEW GATE**: a **widening-only** change (no new flag, only new `case` labels broadening an existing flag false→true) is **monotone**, cannot create a dead flag and cannot skip a needed pass — precedent shader-slang/slang#12050 @`4c507cb94ca3`, approved and merged unchanged — and **a probe that fires on the safe direction of a change class is a false-abstain generator, costing exactly as much as the miss it was meant to prevent.** Three review moves follow: **match the scan arms against the gated set** (for each new flag, find the `case` that sets it — a flag with no setter is dead; this is a **diff read**, and no amount of drilling substitutes for it), **count the jobs not the passes** (one control per *job*), and **check pipeline order** for a pass gated on a flag set by a scan that runs after it. Calibrate before headlining, though: the matching *claim* that `lowerUntaggedUnionTypes`' second job was a shipped must-fix **measured false** — neutering that case label still compiled because a broader implication set the flag anyway, and a 60-test sweep found no isolating shape, so **a second job is a place to look, not a defect by itself**, and "narrow" is not "dead" (a narrow gate covered by a broader implication is defense-in-depth; only a gate covering nothing is a defect). Finally, a build trap that silently voids the measurements you just built this matrix to take: **inserting a member MID-STRUCT during an in-flight incremental build** left one TU compiled 2.4s *after* the write to the shared header, so objects disagreed on layout — **it still linked, still ran, and every IR dump from that binary was worthless.** After editing a struct in a widely-included header, touch the header, force a consistent rebuild, and **verify each consuming object's mtime > the header's before trusting any measurement.**

**A conservative implication can fail STRUCTURALLY, not just via optimizer elimination — "co-emission at production" is NOT "co-presence at the governing scan."** This is the load-bearing technical rule of the #11917 epic, and it cost two wrong mechanisms before the right one. `lowerTagInsts` handles four opcodes (`GetTagOfElementInSet`, `GetTagForSuperSet`, `GetTagForSubSet`, `GetTagForMappedSet`), and the tempting simplification — gate it on the pre-existing `taggedUnion` flag, since tagged-union lowering synthesizes tag insts anyway — **is a miscompile.** The two arguments offered first are each instructive failures: *"not synthesized by `lowerTaggedUnionTypes`"* is TRUE but INSUFFICIENT (it shows the implication doesn't *create* them in-window, and says nothing about whether it *covers* them), and *"co-emission: each tag inst is emitted on a path that also emits `GetTagFromTaggedUnion`"* is outright FALSE — and interestingly so, because it was checked at **emission** time. The correct argument is that **an entire producer family never has an implier at all**: in `slang-ir-typeflow-specialize.cpp`, `getLoweredType` has `as<IRTaggedUnionType>(info)` (:5606) and `as<IRElementOfSetType>(info)` (:5611) as **sibling `if`s on the same `info`**, the element-of-set branch returning `makeTagType(...)` — a `SetTagType` with no tagged union in the chain — while `specializeLookupWitnessMethod` gates on `as<IRElementOfSetType>(info)` (:5774-5776), never tests for a tagged union, and emits `GetTagForMappedSet` (:5823). So the opcode is reachable with **zero** tagged-union opcodes present. The transferable form: **a gate reads at scan time, a producer runs at production time, and those are different instants** — so "A implies B, gate on A" owes two separate questions, the *contingent* one (can DCE/SCCP/simplification eliminate the implier while the consumer survives — the question people naturally ask) and the *structural* one (is there a producer path where the implier is never produced at all — cheaper to check, easier to miss, stronger evidence). **Prefer the structural argument whenever both are available**, because a contingent argument depends on optimizer behavior and an optimizer change silently rots it, while a whole producer family with no implier cannot rot. Corollary: a *type* used as a **function parameter type** (`makeTagType(tableSet)` in a specialized dispatch signature, :6010) is co-present with **no producing instruction at all** — a second structural way co-emission fails. Two gate-design rules the same run confirmed: **gate-vs-handled-set exactness beats opcode-family reasoning** — `lowerUntaggedUnionTypes` looks like it handles exactly `UntaggedUnionType`, but its `processModule` also calls `replaceNoneTypeElementWithVoidType()` unconditionally (`slang-ir-lower-dynamic-dispatch-insts.cpp:736-743`, called :755), so gating on `UntaggedUnionType` alone silently skips `NoneTypeElement` cleanup and `kIROp_NoneTypeElement` had to join the flag; **always read the pass's whole `processModule`, not just its main `processInstsOfType` call.** And a scan-visibility gotcha with a wrong rationale to avoid: `calcRequiredLoweringPassSet` recurses via `getDecorationsAndChildren()`, so **operands are NOT traversed** and an inst is only seen if parented in the module tree — but do *not* justify this with "all the opcodes are `hoistable`", because `GetTagForSuperSet`/`SubSet`/`MappedSet` are **not** hoistable (`slang-ir-insts.lua:3167-3183`); the correct rationale is block-insertion reachability, `emitIntrinsicInst` → `addInst` inserting at the builder's current location inside existing IR. Two process notes worth as much as the mechanism: **an `Explore` subagent recommended collapsing all three gates onto `taggedUnion` — i.e. the miscompile — while its own evidence contradicted its conclusion**, so verify every producer claim in source yourself rather than trusting a subagent verdict on gating safety; and an independent codex critique caught the `NoneTypeElement` must-fix that neither the plan nor the triage trace had, so **run both review channels — they catch different classes.** The asymmetry to hold onto: **correcting *toward less* safety (weakening a gate) needs more evidence than correcting toward more**, and here the retraction's own load-bearing premise ("every `SetTagType` traces back to a tagged-union opcode") was false [a conservative implication can fail structurally, not just via optimizer elimination](wiki/learnings/1785826645329-pass-gating-safety-a-conservative-implication-can-.md).

## Reading the Change Itself: the Diff Is the Intent Artifact, and a Partial Fix Fails Toward "Looks Complete"

**For a claim about INTENT, the diff is the artifact — current state and the commit title are not substitutes.** On shader-slang/slang#11616 / PR #11617, two tiers spent **four rounds** deriving *why* a test assertion would be brittle — IR branch structure, inst arity, emit-layer provenance, all correct and all independently verified — when the answer sat in the patch that created the assertion: the author had added a **`-O0` pin in the same commit** as the assertion block (`-//TEST:SIMPLE(filecheck=CHECK): … -g3` → `+… -g3 -O0`). The pin *was* his optimization-robustness mechanism: for checks that legitimately depend on unoptimized structure, he pinned the directive rather than loosening the checks, so both tiers' written requirement ("the new assertion must be optimization-robust") **mis-stated the goal** — for that file, robust means *pinned*, and it already was, and the `-O1` failure they reasoned from described a configuration the test cannot run in. This is a distinct defect from "the instrument dropped the data": here the instrument **answered a different question** — what the code says *now*, rather than what the author was *doing* — and **current-state-plus-title reads cheaper than the diff while silently omitting authorial intent**, the exact thing under discussion. Three separate failures in that session traced to the one missing read (one tier misattributed intent from a commit title, another **fabricated** a title outright, and both rulings reasoned from titles); none would have survived `git show <sha> -- <path>`, which was two calls away throughout. **Rule: any claim of the form "this assertion/guard/flag exists in order to …" requires the introducing commit's diff** — `git log --oneline -- <path>` then `git show <sha> -- <path>`. The same PR carries a Slang-specific instrument trap of the *silently-ignored-flag* class: **`slang-test -OX <file>` does NOT override a test directive's own `-O` flag.** A fixer reported "verified at `-O1/-O2/-O3`" — four passes — but the directive hardcodes `-O0`, so all four runs **compiled identically at `-O0`**: four green results, one measurement. Mechanism at `tools/slang-test/slang-test-optimization-options.h`: `:14` sets `kTestOptimizationOption = "-O0"` as the suite-injected default, `:19-44` `isSlangOptimizationArg()` matches any `-O<level>` in slangc's own spellings (its comment naming the intent, *"so unrelated options with a `-O` prefix do not accidentally opt a test out of the slang-test default"*), and `:56+` `hasSlangOptimizationArg(args)` is true when a command line already specifies a level ⇒ **a directive carrying its own `-O` opts that test out of the suite-level injection.** To measure optimization sensitivity, invoke `slangc` directly per level. Measured on `tests/language-feature/function-calls/forceinline-multiple-cases.slang` at master with `-target spirv-asm -g3`, anchored on `OpExtInst %void %N DebugNoScope`: `DebugNoScope` counts of **14 / 16 / 12 / 12** at `-O0`/`-O1`/`-O2`/`-O3` against a stable **9** one-operand `DebugScope` at every level — so the author's `CHECK-COUNT-14` breaks at *every* non-zero level, which is why he pinned, and the brittleness is confined to the `DebugNoScope` count. **Anchor those greps**: `-g3` embeds source, so the test's own `NOSCOPE` *comment* lines match a naive `grep -c` (16 raw mentions vs 14 emitted) [read the diff for intent claims, and `slang-test -OX` cannot override a directive's own `-O`](wiki/learnings/1785828146545-read-the-diff-for-intent-claims-current-state-plus.md).

**The commit SUBJECT is not the commit's content class either — a commit titled "Document …" can carry a live line of code.** Same PR as the pass-gating fold above (#12336, batch-2 of the #11917 epic): a recorded state said the PR was `2 files +45/-8 @8ed92efd0c`; live it was `+70/-8, two commits`, the second (`013675eb0c`) titled *"Document the gating invariants each new flag depends on (#11917)"* — a subject that reads as pure comments. It contained a live functional line, `result.tagType = true;`, added to the `tagOps` case arm in `calcRequiredLoweringPassSet` (`source/slang/slang-emit.cpp`) [a commit whose subject says "document" can carry live code](wiki/learnings/1785839519730-a-commit-whose-subject-says-document-can-carry-liv.md). Filtering added lines to non-comment ones returned `1`, which next to a +31/-6 comment commit reads like noise — a stray brace — yet it was the only functional change in the commit: **a count told me a live line existed but not that it mattered; only reading the patch did**, the same family as `grep -c` standing in for reading. It happened to be monotone-safe (all four new `RequiredLoweringPassSet` flags are only ever assigned `true` in the diff — 8 hits, all `= true`, zero `= false` — so an extra flag can only *widen* the pass set, costing a no-op walk where a missing flag would miscompile), but the safety was **derived after the fact**, and the green evidence already published (local 1484/1484, three suites, codex PLAN/CODE/OUTPUT approvals) was measured on the *first* commit only — a behaviorally-safe change still invalidates the provenance of every number pinned to the older SHA. Rules: **never infer a commit's content class from its subject** — read `gh api repos/O/R/commits/<sha> --jq '.files[].patch'`; "Document", "comment", "typo", "rename" are the subjects most likely trusted unread, which is exactly what makes them worth reading. **Re-read the PR head before refreshing any artifact that quotes a diffstat** — a branch you opened is not a branch that stopped moving, and a diffstat in a public comment is a claim with a SHA attached. And **pin your numbers explicitly** to the SHA they were measured against until re-run, rather than floating them next to a diffstat they were never measured over.

**A partial fix is a good outcome; what makes it bad is a set of omissions that are all invisible in the diff and all fail in the direction of "looks complete."** On slang#12150 an issue covered three related constructs (`#include`, `__include`, `#line`) and the fix landed **2 of 3**, because `__include` turned out **structurally** unfixable by the chosen approach — traced with numbers, `views=27 matchFile=1 withInitLoc=0`: a `SourceView` exists for the `__include`d file but carries **no initiating source loc**, because `#include` threads the directive loc into `createSourceView` (`slang-preprocessor.cpp:3728`) while `__include` receives the loc in `slang-session.cpp` and never threads it through, so the includer-chain approach cannot see it. Of the three options — ship 2/3 plus a follow-up, fix provenance recording at the producer, or special-case the construct in lowering — **shipping 2/3 was right**, and the deciding phrase was the fixer's own: option 2 is *"a provenance change masquerading as a debug-info fix"*, and since provenance is consumed by diagnostics too, its blast radius belongs in a PR where a reviewer is evaluating **provenance**, not debug info. Option 3 was worst — a second resolution mechanism for one question ("who included this file?") creates two paths that must stay in sync forever, and the next person to touch provenance won't know the second exists. The three things that make a partial fix honest, **each an omission by default**: (1) **the failing test must be VISIBLY disabled, never dropped** — deleting it destroys a verified repro while leaving it red blocks CI, so mark it disabled/expected-fail *in the file itself* with a comment naming the root cause and the follow-up issue so a future editor doesn't "clean up" a fixture that looks unused (no expected-fail mechanism? keep the fixture and remove only the `//TEST:` directive, same comment), and **say so in the PR** — a reviewer who discovers a disabled test unaided reads it as sloppiness; (2) **no auto-close keyword when the fix is partial** — `Fixes #N` on a 2/3 fix closes the issue and the remaining gap silently leaves the tracker, so reference the issue without a closing keyword and let the maintainer decide about their own tracker item; (3) **the follow-up must be a real ISSUE, not a note in the PR body** — a deferral recorded only in a merged PR body is invisible to issue search, i.e. effectively untracked, so file the issue carrying the trace verbatim (numbers + `file:line`) and comment on the original stating what landed and what is tracked where. Also **don't let the PR title/body imply the whole family is fixed** — "include handling" reads as covering `__include`; state 2/3 explicitly and name the structural reason. The operative self-check: ***if I disappeared right now, would a stranger reading the tracker know what's still broken?*** [a partial fix needs a visibly-disabled test, a real follow-up issue, and no auto-close keyword](wiki/learnings/1785827571091-a-partial-fix-needs-a-visibly-disabled-test-a-real.md).
