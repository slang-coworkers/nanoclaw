# CI Flake — Sweep Mechanics & Routing/Board Forensics

## TL;DR

- **Never rank flake signatures by an `action` field you also write on non-actions.** Reserve `action:"rerun"` for reruns actually fired; a re-confirmation, a GitHub refusal ("already running"), or a dropped deferral is `action:"none"` even when the subject is a rerun. Rank from **reason-text across all records** and by **DISTINCT ENTITIES affected** (distinct PRs), not record count — record count rewards the most *stalled* item, not the most *costly* one.
- **General form:** if a field means "what I did" but gets written on rows where you did nothing, every aggregate over it silently inflates — sanity-check any log-derived count against "how many of these were real?" before it ships.
- **`rerun-log.jsonl` verdicts follow the same discipline.** Log a confirmed approval-gate wedge (fork-PR / falcor build-approval gate) as `verdict:'intermittent'` with `labels:['approval-gate-action-required']`. `unclassifiable` means you can't tell (e.g. logs expired, 410); a wedge is a known cause you can't act on. The log is append-only, so write the verdict correctly the first time.
- **Parallelize the REST-fallback sweep.** A serial 8×-retry loop covered only 22 of 74 PRs in 10 minutes; fan out with `xargs -P 10 -n 4`, drop to 5 retries, give **each worker its own output file**, and use absolute output paths.
- **`@shader-slang/dev` added as reviewer on a bot PR at `ready_for_review` is CODEOWNERS, not the agent.** The `review_requested (team=dev)` event carries the SAME actor + timestamp as `ready_for_review` (the human who flipped ready). Verify before relaying; do NOT remove the team reviewer.
- **The board-sync "Source" (Internal/Community/Bot) field is derived in `pr-board-sync.yml` at two push-access sites** — a team-membership reclassifier needs no new PAT scope but is a bot-unpushable `.github/workflows/*` change.
- **Before calling a CI signature "distinct from" a tracked issue, read the issue body for named prior instances and check fix-sha ancestry for every hit** (`compare/<fixSha>...<testedSha>`). A pre-fix hit IS the tracked issue; a post-fix hit means the fix is incomplete, not a new bug. Count `merge_group` hits too. A registry entry going `closed` proves the issue closed, not that failures stopped; `fixIncomplete: true` keeps post-fix hits tied to the issue.
- **When two writers must run together, or a value must equal "now", enforce it in the writer's code**, not in prompt prose or a later audit: `touch_tracker_verdict(pr, verdict, at, log_row, ...)` requires the paired `rerun-log.jsonl` row, appends it first, and rejects an `at` more than 90 s in the future.
- **Don't gate live re-verification on the payload's `hasNewActivity`** — diff payload `updatedAt` against tracker `last_verdict_at`. The only safe push-gated skip is for `legitimate` verdicts, and it fails closed.
- **Schedule-only workflows (weekly `cmake-options.yml`, Saturday 08:00Z, no `merge_group` trigger) are invisible to merge-queue scans** — check their last runs every master scan and page all job pages. It is also the only `-Werror` gate for GCC-only warnings, so those reach master green. A gap in its run list can be deleted history, not a skipped week.
- **A bash-quoting bug in `pull-universe.sh` aborts the supervise-issues tick** (`syntax error near unexpected token '('` ~line 145, then `stdin is not a tty` from scan.py).

## Overview

Two families of "the tooling itself is the story" learnings: how to *run* a flake sweep so its numbers, registries and throughput are trustworthy, and the routing/board-classification machinery a maintainer keeps mistaking for a bot misfire (CODEOWNERS auto-request, board-sync "Source", the supervise-issues quoting bug).

## Sweep Mechanics: Rank by Distinct Entities, and Parallelize the REST Fallback

The flake-evidence dedup rule (dedup by `run_id`) has a companion defect one level up. `memory/rerun-log.jsonl` has `action` (`rerun` | `requeue` | `none`), and the "top infra signature" groups the last ~7 days on `check`/`reason`. Measured: of **143 `action:"rerun"` records in 7 days, only 5 were fired reruns**; the other 138 were idempotent re-confirmations, GitHub refusals (`"cannot be rerun; This workflow is already running"`) and moot deferrals, written as `rerun` because they were *about* a rerun. Naive grouping put `check-formatting` at #1 with 31 hits — all re-confirmations of two author-owned PRs that must never be rerun (formatting is deterministic) — while the true dominant flake by **distinct-PR spread** was #12145 `GBufferRTTexGrads_d3d12` (16 distinct PRs on all 7 days). Reserve the action field for **actions actually taken**, and rank by reason-text across all records and **distinct entities affected**; record count rewards the most re-observed (stalled) item, not the most costly ([don't rank flake signatures by an action field you also use for non-actions](../learnings/1785780857080-don-t-rank-flake-signatures-by-an-action-field-you.md)).

The `verdict` field has the same problem. For falcor-build-approval-gate and fork-PR-approval wedges (gates 0c/0d), `sweeplib.append_row()` must write `verdict:'intermittent', labels:['approval-gate-action-required'], reason:'gate-wedged, holding on operator'` — the literal example in the babysitter's CLAUDE.md. `unclassifiable` is only for a genuinely unknown cause such as expired (410) logs; a wedge's cause is confirmed, it just can't be rerun. On 2026-09-27 six rows (PRs 13270, 13071, 13227, 12782, 13195, 13171) went in as `unclassifiable`, caught by grepping earlier rows for the same PRs. The log is strictly append-only, so they stay; **grep the PR's prior rows before `append_row`**, and fix a wrong row only with an appended `"action":"correction"` line (see [store hygiene](ci-b-instrument-aperture-and-store-hygiene.md)) ([rerun-log.jsonl verdict for gate-wedged entries must be 'intermittent', not 'unclassifiable'](../learnings/1790469245380-rerun-log-jsonl-verdict-for-gate-wedged-entries-mu.md)).

**Parallelize the REST-fallback sweep.** When GraphQL is down and every open PR must be swept via REST `commits/<sha>/check-runs` + `statuses`, a serial loop with an 8×-retry/1 s-sleep wrapper got through only **22 of 74 PRs in 10 minutes** and hit the Bash timeout — cost is per-call latency plus retry sleep, not rate limits. Make the per-PR probe a standalone script and fan it out; the remaining 52 PRs finished inside one call:

```bash
# /tmp/one.sh takes: num sha author repo ; writes /tmp/out/red-<n>.txt or green-<n>.txt
cat /tmp/prs-remaining.tsv | while IFS=$'\t' read -r n s a r m; do echo "$n $s $a $r"; done \
  | xargs -P 10 -n 4 /tmp/one.sh 2>/dev/null
cat /tmp/out/red-*.txt >> /tmp/reds.txt
```

Use 5 retries per worker; give each worker a **separate output file** (10 processes appending to one file interleave lines); emit space-separated fields for `xargs -n 4` and keep the TSV read separate; `-P 10` raised no secondary rate limits for ~150 calls; and `cd` inside an `xargs` pipeline resets the session's cwd, so use absolute output paths ([parallelize the REST-fallback CI sweep](../learnings/1785752832168-parallelize-the-rest-fallback-ci-sweep-serial-retr.md)).

## Sweep-Classifier Registry Footguns

**Self-heal leaves a base-skew gap.** When a `tracked-regressions.json` entry self-heals `open`→`closed` (its issue closed, so it correctly stops excluding NEW PRs), a PR whose head predates the fix loses all protection: `base-skew-signatures.json` has no automatic carry-forward, so the pre-fix PR is misclassified as a fresh regression. The fix threads `baseSkewEntries` into `loadAndRefreshExclusions`, stamps each closed entry with `needsBaseSkewGuard = !baseSkewEntries.some(b => b.context === entry.job)`, and surfaces `exclusions.needsBaseSkewGuardCount` in every wake payload; whenever an entry self-heals, add or verify the matching base-skew entry keyed to the fix commit, carrying `logGrep` over verbatim ([tracked-regressions self-heal leaves a base-skew gap unless forward-guarded](../learnings/1789734357508-ci-babysitter-tracked-regressions-self-heal-leaves.md)). Name+ancestry matching is fine for a single-purpose status (`SlangPy Tests`) but wrong for a broad job name (`test-slang / build`), where any failure on a pre-fix PR would auto-classify `needs-rebase`; an optional `logGrep` (literal substrings, AND-semantics, copied not paraphrased, checked by `verifyExclusionSignature`) must confirm the signature first. Separately, `touch_tracker_verdict(pr=<new-N>)` on a PR new to `rerun-tracker.json` seeds from `{}` without `reruns`/`requeues` sub-dicts, so a direct `entry['reruns']['count']` KeyErrors until a rerun/requeue writer touches it — use `.get('reruns',{}).get('count',0)` ([touch_tracker_verdict leaves reruns/requeues keys absent for brand-new PRs](../learnings/1789812403577-touch-tracker-verdict-leaves-reruns-requeues-keys-.md)).

**Paired writers belong in one signature.** `touch_tracker_verdict()` (tracker) and `append_row()` (`rerun-log.jsonl`) were a pair only in the sweep prompt: gates 0c/0d showed both calls, gates 0g and 0i showed the tracker call alone, and a "nothing changed" sweep on 10-03 made 18 tracker writes with zero log rows. No audit could see it — `audit_summary_rows` checks only `sweep_summary` rows and `audit_bypassed_rows` only rows that exist. Now `touch_tracker_verdict(pr, verdict, at, log_row, ...)` takes `log_row` as a required argument and appends it *before* mutating the tracker, so a missing or schema-invalid row raises with the tracker untouched. `at` is wall-clock write time: passing an old `last_verdict_at` while adding metadata such as `issue_refs` backdates the log row's `ts` ([touch_tracker_verdict now requires a paired log_row](../learnings/1791004403685-touch-tracker-verdict-now-requires-a-paired-log-ro.md)). That rule failed while it lived only in memory prose — two consecutive 10-23 sweeps typed made-up `at` values, leaving rows future-dated by up to ~10 min — so the writer now rejects any `at` more than 90 s ahead of utcnow before writing. If a value must equal "now", the recording function checks or computes it; an instruction is not enough ([enforce 'timestamp = now' in the writer, not in prose](../learnings/1792735612533-enforce-timestamp-now-in-the-writer-not-in-prose.md)).

**"Never classified" is disjoint from "verdict gone stale".** Of 16 PRs truncated off `sweep-script-v2.mjs`'s full-scan tail by `FULL_SCAN_CAP=60` (`unionAll.slice(0, FULL_SCAN_CAP)`), 8 had real verdicts reconfirmed by `stale_tracked_entries()`/Gate 0g, 6 carried a legacy pre-v2 `terminal_unclassifiable` pin (self-sufficient but invisible to `heartbeat_due()`, which reads only `last_verdict`), and exactly 2 had never been classified. `heartbeat_due()`'s `if not verdict: return False` treats absence and not-due identically — **a staleness filter cannot double as an absence filter**, since absence has no `last_verdict_at` to age. Add a sibling predicate pair — a cap-independent whole-tracker scan draining the backlog a few at a time, plus a targeted scan fed by the truncating source — rather than raising the cap, which is bounded by the very limits the cap exists for ([FULL_SCAN_CAP truncation gap: "never classified" is a distinct failure mode](../learnings/1790283947352-full-scan-cap-truncation-gap-never-classified-is-a.md)).

**`status:"closed"` proves the issue closed, never that the failures stopped.** A sweep classified 5 hits of `verify-documented-compiler-version.sh` exit 4 (`build-windows-debug-cl-aarch64 / build`) as "distinct from #13041" and drafted a new issue. Two were named in #13041's own body and four predated fix `d89866432c`, so they *were* #13041; the real signal was three hits *after* the fix (an ancestor of the tested SHA), two of them `merge_group` runs a PR-head scan never sees. Before calling a signature distinct: (1) read the tracked issue's body for named instances; (2) for every hit run `gh api repos/<o>/<r>/compare/<fixSha>...<testedSha> --jq '{status,ahead_by,behind_by}'` — `ahead`/`behind_by:0` means the fix is present, so a recurrence means it is *incomplete*; (3) count `merge_group` hits alongside `prs[]`. Registry entries now carry `fixIncomplete: true`, independent of `status` (which stays `closed`): `classifyBaseSkew` used to fail open on every ahead-of-fix match, and with the flag it runs the `logGrep` first, so a matching log classifies `verdict:'fix-incomplete'` tied to the issue while a non-match stays actionable. The same atom fixed a `rollupUnexplained` false positive on 100%-green #13032: `fetchNonGreenRollups`'s GraphQL tail path lacks the floor path's `dedupeByLatestAttempt`/`checkSuiteEventMap`, so two same-named check-runs (cancelled, then success) left `statusCheckRollup.state` non-SUCCESS. `verifyRollupUnexplained(headSha)` re-checks via the floor's REST dedup only when the flag is set, fails open on fetch error, and reads `rollupReverified:true, rollupUnexplained:false` on the #13032 fixture ([before calling a signature "distinct from" a tracked issue, check the issue body and fix-sha ancestry](../learnings/1790796091473-before-calling-a-signature-distinct-from-a-tracked.md)).

**Never hand-type shas in a batch write.** `rerun-tracker.json["13078"].last_seen_head_sha` held #13256's head: a sweep had hand-built several `touch_tracker_verdict(..., head_sha=...)` calls in one invocation and pasted the wrong literal. It was harmless only because #13078's verdict was `base-skew`, which gate 0h's `legitimate_unchanged()` never consults; on a `legitimate` PR the skip would fail closed or open. Build (pr, sha) pairs programmatically from the payload's own `prs[].headSha` ([tracker head_sha cross-PR contamination](../learnings/1790511042846-tracker-head-sha-cross-pr-contamination-verify-aga.md)).

## Don't Gate Live Re-verification on the Payload's `hasNewActivity`

`hasNewActivity` is not proven to detect a new push or rebase: on one sweep it read `false` for #13086/#13181/#13186/#13187 although each PR's `updatedAt` was later than its tracker `last_verdict_at`, and live state differed (#13186's rollup read `FAILURE` with every check passing; #13086's `base-skew` had cleared after a rebase). Every sweep, diff each PR's payload `updatedAt` against `last_verdict_at` in Python and re-verify via `gh pr checks`/`gh pr view`. Open question for the `sweep-script-v2.mjs` owner: what does `hasNewActivity` key on — if never meant to cover pushes, this is a doc gap ([wake-payload hasNewActivity read false on PRs with genuine new pushes](../learnings/1789970806784-ci-babysitter-wake-payload-hasnewactivity-read-fal.md)).

The inverse optimization is safe for ONE verdict class: a `legitimate` (real-failure) PR **cannot** change without a push. `sweeplib.legitimate_unchanged(pr, payload_head_sha, tracker)` reads an additive `last_seen_head_sha` (from `touch_tracker_verdict(..., head_sha=...)`) as Gate 0h before step 1's `gh pr checks`, and **fails closed** on any missing data. Scope it **strictly to `legitimate`** — `gate-wedged`/`base-skew`/`intermittent` can flip with zero push, and `resolved`/`out-of-scope` are terminal — and prefer the additive field over widening the closed `TRACKER_VERDICTS` enum. When regenerating the paired `escaped.sh` wrapper, don't reflexively double backslashes for a `node -e "…"` block (a bare `\n`/`\d` passes through bash double-quotes); **capture the literal `-e` arg bash hands `node` and diff it against the source**, not a Python regex model of bash ([push-gated skip for stuck 'legitimate' PRs + escaped.sh backslash gotcha](../learnings/1790282099711-ci-babysitter-push-gated-skip-for-stuck-legitimate.md)).

## CODEOWNERS Auto-Routes @shader-slang/dev on ready_for_review

When a maintainer sees `@shader-slang/dev` added as reviewer on a bot-authored PR and suspects the agent, it is CODEOWNERS auto-requesting the owning team on `ready_for_review`: the `review_requested (team=dev)` event carries the SAME actor and timestamp as `ready_for_review` — the human who flipped ready, not `nv-slang-bot[bot]`. Verify before relaying (reputationally sensitive): `gh api repos/<o>/<r>/issues/<pr>/timeline --paginate --jq '.[] | select(.event=="review_requested" or .event=="ready_for_review") | {event, actor:.actor.login}'`; the bot only authors `committed` events. Do NOT remove the team reviewer; a maintainer flipping ready is not a drafts-only breach ([CODEOWNERS auto-routes @shader-slang/dev on ready_for_review](../learnings/1783531331428-codeowners-auto-routes-shader-slang-dev-on-ready-f.md)).

## Board-Sync "Source" (Internal/Community) Derivation Lives in pr-board-sync.yml

The board-sync **"Source"** single-select (Internal / Community / Bot) that drives shader-slang Issue/PR assignment is classified in `.github/workflows/pr-board-sync.yml` at **two** sites keyed on repo **push access** (`getCollaboratorPermissionLevel(...).permissions.push === true`): "Classify PR Source" (~L234-253) and the sweep helper `classifySource(info)` (~L1170-1189); both fail safe to Community on read error and short-circuit to Bot for bot authors. The same file's `listTeamMembers("org/slug")` (~L962-978) paginates `teams.listMembersInOrg` (nested members included), and the `SLANG_PR_BOT_TOKEN` PAT already has **org Members: read**, so a team-membership classifier (#12259: one `isInternal(login)` helper over a `source-internal` team routing both sites) needs no new scope. But it is a `.github/workflows/*` change the nv-slang-bot App **cannot push** (no `workflows` scope) with no local CI validation → human-apply, and the org team must exist first or everyone fails safe to Community ([Source-field Internal/Community derivation lives in pr-board-sync.yml](../learnings/1785290345255-source-field-internal-community-derivation-lives-i.md)).

## Schedule-Only Workflows Sit Outside the Merge-Queue Scan

`cmake-options.yml` (~479 jobs, cron `0 8 * * 6` = Saturday 08:00Z, no `merge_group` trigger) can fail a leg no merge-queue run shows. Its 10-10 run 38036412573 failed only `windows-vs2026-release / build (SLANG_ENABLE_ASAN, true)` with MSVC C1128 ("compile with /bigobj") in `slang-embedded-core-module-source.cpp`, likely from `*.meta.slang` growth, and sat unexamined ~44 h. Check its last runs every master scan, paging `gh api "repos/shader-slang/slang/actions/runs/<id>/jobs?per_page=100&page=N"` over pages 1..5 (the failure was on page 2; page 1 looked green). `gh run view --log-failed` printed nothing, while `gh api --allow-escape-sequences repos/shader-slang/slang/actions/jobs/<job_id>/logs | sed 's/\x1b\[[0-9;]*m//g'` worked; logs expire (410), so record toolchain versions (MSVC 14.51.36231) while readable ([weekly cmake-options.yml failures can go unexamined for days](../learnings/1791778074299-weekly-cmake-options-yml-failures-can-go-unexamine.md)). Its Saturday matrix also stalls the `ubuntu-latest` queue for hours; see [reading CI state](ci-c-reading-ci-state.md).

It is also the only `-Werror` gate for GCC-only warnings: merge-queue CI builds `build-linux-*-gcc-*` with `warnings-as-errors: false`, so e.g. GCC 13.3's `-Walloc-size-larger-than=` (from `List<T>::makeRepeated(x, signedCount)` reaching `malloc`, ubuntu-24.04-arm) lands green and errors only under `-DCMAKE_COMPILE_WARNING_AS_ERROR=ON` up to a week later; on 10-17 PR #13116 broke 31 linux-aarch64-release legs that way. The tell is the same text as a `warning:` in the merge-queue log of the same compiler. Count failed legs by error signature across ALL job pages, then diff against the introducing commit's merge-queue log ([weekly cmake-options is the only -Werror gate for GCC-only warnings](../learnings/1792253279767-weekly-cmake-options-is-the-only-werror-gate-for-g.md)). Bracket the regression window against the last-green run's head SHA with `compare`, not "last week" ([cmake-options cron is Saturday 08:00Z; bracket against the last-green SHA](../learnings/1792253897751-cmake-options-yml-weekly-cron-is-saturday-08-00z-n.md)) — and a gap in `gh run list` is not a skipped week: shader-slang/slang's Actions history is being deleted oldest-first (reaching 10-12 by 10-17; a deleted run 404s), so the "missing" 10-10 run existed and #13738's window started 10-10, not 09-26. Before claiming "no run on date X", search issue bodies for cited run ids (`gh search issues 'actions/runs'`) and ask whoever read the logs earlier ([CORRECTION: missing cmake-options runs may be deleted history](../learnings/1792254028938-correction-missing-cmake-options-runs-in-gh-run-li.md)).

**Verify a fix on the workflow that owns the leg.** On #13574 (the `/bigobj` fix) the fixer cited "CI dispatched: run 38209827992", but `gh api …/actions/runs/<id> --jq .path` showed `ci.yml`, which has no MSVC+ASan leg, and the run had bot-yielded (`wait-for-human-priority` failed, every build-* job skipped). Only `cmake-options.yml` runs the `SLANG_ENABLE_ASAN` row of `.github/cmake-options-matrix.json` (cron + no-input `workflow_dispatch`). For any cited run, check `.path` and that the leg ran; a run id plus "dispatched" proves neither. A leg that failed at one object has built nothing downstream since, so a fix dispatch can surface a second, independent failure — warn the fixer ([a fixer's "CI dispatched: run N" may be the wrong workflow](../learnings/1791788466910-a-fixer-s-ci-dispatched-run-n-may-be-the-wrong-wor.md)).

## Quoting Bugs in Sweep Tooling

`bash scripts/pull-universe.sh … | python3 scripts/scan.py` exits 1 with `syntax error near unexpected token '('` at ~line 145, and scan.py then reports `stdin is not a tty` — a bash-quoting bug (sibling to the earlier argv-overflow issue) that aborts the supervise tick ([supervise-issues pull-universe.sh bash-quoting bug](../learnings/1782995331984-supervise-issues-pull-universe-sh-bash-quoting-bug.md)). The CI-babysitter's sweep has a sibling trap: a `.mjs` deployed inside a bash double-quoted `node -e "..."` fails with `SyntaxError: missing ) after argument list` if its source contains any `"`, even in a comment. Grep the `.mjs` for `"` before stamping or deploying, and round-trip it through bash once ([sweep gate: .mjs in a bash string must have no double quotes](../learnings/1791736119391-sweep-gate-resolved-needs-positive-check-ci-succes.md)).
