## TL;DR

The approver's Step-3 challenger is where a clean-looking PR gets its one real defect surfaced — or missed. These atoms are a catalog of the analytical probes (most are `challenger-miss` post-mortems where the codex DECISION_REVIEW gate caught the error). Recurring meta-rules:

- **Reachability is about the caller/entry set, not the flagged function body.** A bad-input finding on a utility function clears only if *every real caller guards first*; a "handled elsewhere" no-op proof clears an arm only if it covers *every form* reaching it.
- **A green/byte-identical observation carries zero bits about a branch it never drives.** Ask "could this observation have come out otherwise?" Name the input shape that hits the *new* branch and confirm the evidence produces it. A perf benchmark optimized for size drives only the trivial-agreement shape.
- **Read the producer, not the narrative.** For a test-relaxation PR, open the code that emits the un-asserted output; for a "single source of truth" claim, verify *both* consumers read the table. Author/bot prose has already concluded "incidental."
- **Prove a property for the exact path the gap is about.** Proving path Y is a no-op says nothing about path X. A cast `x.as<T>()` on a DeclRef/Val is *not* null-safe — on the error-recovery branch the node may be a different kind, yielding an empty ref → downstream null-deref.
- **A relocated call preserves its defect.** A "clean" verdict from a head-current bot on a *redesigned* commit is weak when the redesign moved code a stale review flagged — diff the reviewed-commit→head interval and re-derive whether each finding survives. **Reproduce a crash claim by running** (a pre-existing test on the path is the cheapest falsification).
- **Whole-diff, both-directions, per-kind.** A clean in-scope change never launders an unrelated regression the same commit ships (backward submodule bump). A pass-move needs *backward* + specialization-identity analysis. A narrowing carve-out silently reclassifies *every sibling* of the narrowed case. Never carry a prior-revision approval forward — re-derive per diff.
- **Uncertainty never rounds up.** A code-reading "worst case is benign" hypothesis you never ran is one-directional (toward-approve) — it can add caution, never upgrade to WOULD_APPROVE.

## Reachability: trace the callers, cover every form

CodeRabbit flagged an integer-overflow in `TransientBufferHeap::allocate()` calling a round-up before the size check. The finding is a *live* bug only if a real caller can pass a near-`SIZE_MAX` size; tracing showed the sole in-repo caller (`TransientBufferArena::allocate`) rejects oversize *before* aligning, so it is defensive-hardening that clears — reachability is about the caller set, not the function body (the inverse of the public-API rule, where callers are external code) [bad-input finding on a low-level function](../learnings/1787929697169-approver-challenger-miss-a-bad-input-finding-on-a-.md). The dual failure is the **false-safe on slang-rhi#843**: a `PushConstant` no-op arm was cleared with one proof ("data written elsewhere via `vkCmdPushConstants`") true only for the *entry-point* path; the documented `[[vk::push_constant]] ConstantBuffer<T>` sub-object form has its own data path through the child object and silently *drops* the bytes. For any change marking a type a no-op in a dispatch/switch, enumerate every distinct form reaching that arm and name where each form's data is handled [slang-rhi#843: no-op cleared for one of the paths reaching it](../learnings/1787920429247-approver-false-safe-slang-rhi-843-cleared-a-no-op-.md). Relatedly, when a PR *adds* a new `case X:` arm to a per-kind accounting switch, diff the new arm against its siblings term-by-term — a mirror that silently drops one `+=` accumulator is the classic undersizing gap, louder than any bounds-assert the PR adds [slang-rhi push-constant new arm drops one accumulator](../learnings/1787910255166-approver-challenger-slang-rhi-push-constant-pr-new.md).

## Coverage that carries no bits about the new branch

On a "same result, faster path" refactor (two-pointer merge replacing HashSet+sort), an n=800 byte-identical benchmark was credited as coverage of the new interleaved branch — but Devin's own prose said the workload "grows one element at a time," i.e. only multi×singleton merges that never exercise the alternating interleave. A coverage gap's severity turns on whether the untested path has a *silent-failure mode with its guard compiled out* (here the ordering check is `#ifdef _DEBUG`) — that is what separates OPEN_GAP from advisory [byte-identical benchmark never exercises the new branch](../learnings/1787917730683-approver-challenger-miss-a-byte-identical-benchmar.md). A "variadic-only" trigger is still a *real* trigger when variadic is a supported subset of the surface the PR modifies — "narrow" is about frequency, not about being off the changed path; ask the reachability question against the PR's *new* entry point, not the legacy path [variadic-only does not mean off the stated-purpose path](../learnings/1788070918251-approver-challenger-miss-variadic-only-does-not-me.md). And a completeness proof on the *unaffected* path is not correctness on the affected one: proving a CMake `${slang_BINARY_DIR}` substitution is a no-op for the standalone build says nothing about the *submodule* build the gap is about — a "no-op on all covered paths" proof confirms the risk is isolated to the uncovered path, an argument *for* abstaining [a complete substitution on the unaffected path does not clear the affected path](../learnings/1787821699418-approver-challenger-calibration-a-complete-substit.md).

A **gate/flag on a whole-module pass** is the dead-gate mirror of the same "green by construction" failure. On slang#12840 rev2 the author gated a resolution pass on a new `RequiredLoweringPassSet` bool `unresolvedMatrixLayout`, set in `calcRequiredLoweringPassSet` and read as `if (requiredLoweringPassSet.unresolvedMatrixLayout) SLANG_PASS(specializeMatrixLayout, …)`. But the flag is computed by ONE early module scan (~slang-emit.cpp:1047) while the pass's own trigger comes partly from IR that appears LATER — the whole point of the fix is that imported generic bodies are cloned *lazily during specialization* and dynamic-interface/witness conformances mint matrix types after the early passes. If the early `calcRequiredLoweringPassSet` traversal doesn't see those not-yet-materialized types, the flag stays false, the pass is SKIPPED, and the exact unresolved-layout bug recurs — a "dead-gate always-skip" where CI-green + no dup-struct is green *by construction* because the pass simply didn't need to run on the tested inputs. Both bots landed on it independently (Devin 🔴 "Dynamic matrix conformances retain unknown layouts"; CodeRabbit "can still skip unresolved layouts in imported generic specializations … fix before merge"). The probe for any PR gating a whole-module resolution/legalization pass on a `calcRequiredLoweringPassSet` bool: don't stop at setter-exists + order + a trigger-present test — ask whether the early scan observes the SAME IR the pass observes, INCLUDING anything produced by later specialization / lazy generic-body cloning / dynamic-conformance witness instantiation; if the pass exists *precisely* to fix late-materialized IR, a gate computed from an early snapshot is suspect, and the required control is a test whose trigger materializes post-scan and still asserts the pass ran [[approver/gate-flag] Gating a whole-module resolution pass on a scan-computed RequiredLoweringPassSet flag risks skipping it for IR that materializes AFTER the scan (lazy generic clones / dynamic conformances)](../learnings/1788298915596-approver-gate-flag-gating-a-whole-module-resolutio.md).

## Read the producer / the actual head, not the story

For a test-relaxation PR (deleting the only cross-platform `.slang`-folded-source assertion because it failed on Win-ARM64), the pivotal probe is inverted: is the un-asserted behavior incidental, or is its divergence a *masked producer bug*? You cannot answer from the PR narrative — read the producer (`slang-session.cpp` `loadSourceFile`→`findFile`→`addFileDependency`), and prefer "platform-guard / preserve where supported" over outright removal [test-relaxation may be testing-away a masked producer bug](../learnings/1787828324330-approver-challenger-miss-test-relaxation-prs-a-rem.md). A subagent that reads the *local clone* reads whatever stale commit the tree happens to be on — it returned a confident "SUPPORTED" verdict from the OLD source and even noted "this PR isn't in the log" (a red flag the tree is stale, not a fact about the PR); fetch+pin the head and read via `git show <sha>:path`, never a floating worktree `Read`. A read of the wrong commit is *false evidence* — void it back to UNKNOWN, not to the flag it appeared to confirm [subagent reads the wrong commit — fetch+pin the head first](../learnings/1787785990764-approver-challenger-miss-a-subagent-that-reads-the.md).

## Whole-diff, bidirectional, per-kind

**A clean in-scope change never launders an unrelated regression the same commit ships.** A focused loop-unroll PR carried a `Merge branch 'master'` commit that kept the branch's *stale* `external/slang-rhi` gitlink — a 36-commit-backward submodule move undoing a merged bump; neither Devin, CI-green, nor a human approval flags it, so diff every `160000` gitlink at head vs master in the submodule repo [a merge-master commit can silently regress a submodule pointer backward](../learnings/1787849311207-approver-challenger-miss-a-merge-master-commit-can.md). **A pass-move is bidirectional-plus-identity:** besides the forward purpose, enumerate every pass the moved pass now *crosses* (diff the pass list at merge-base vs head — one move crossed five) and check each for a read of its output; if it crosses `specializeModule` or anything keyed on `IRInst*` pointer identity, reason explicitly about mixed implicit/explicit forms of the affected type [a pass-reorder PR needs bidirectional safety + a specialization-identity check](../learnings/1787858474414-approver-challenger-miss-a-pass-reorder-pr-needs-b.md). **A "narrowing / carve-out" refactor** (change `X.as<Base>()` to `X.as<Derived>()`, or delete an explicit branch) silently shrinks the branch's true domain and drops every *other* sibling to the fallthrough path — enumerate the base's full sibling set and verify the new target path preserves semantics *per kind*; never carry a prior-revision WOULD_APPROVE forward [a narrowing carve-out can silently reclassify sibling cases](../learnings/1788076114719-approver-clause-gap-a-narrowing-carve-out-refactor.md). **Deleting a carve-out to fix leg A can regress leg B** on an off-per-PR-CI path: removing a `-o /dev/null` guard exemption fixed the every-PR break but would fail ~972 nightly-only `docs/generated/tests` files; green per-PR CI is not exculpatory when the affected suite runs on a different schedule [a revision that deletes a carve-out to fix leg A can regress leg B](../learnings/1787940792816-approver-challenger-miss-guard-a-revision-that-del.md).

## Null-derefs, producer/consumer shape changes, and CI-download races

Three atoms trace the same slang null-deref family. `x.as<T>()` on a `DeclRef` yields an *empty* ref (not a diagnostic) when the node is a different kind — swapping a proven-safe narrowed local for a re-derived `.as<FunctionDeclBase>()` on the generic-inference-failure recovery path (where a guard diagnoses but does not `return`) crashes in `getTypeForThisExpr` [as<T>() on a DeclRef yields an empty ref → null-deref](../learnings/1787979487048-approver-challenger-confirm-as-lt-t-gt-on-a-declre.md). A producer that makes an existing IR aggregate hold a *new* value shape (a null requirement value) must inventory every consumer reading that field by raw access [producer leaving IR requirement-value null hits unguarded emit consumer](../learnings/1787989733576-approver-challenger-align-producer-leaving-ir-requ.md) — **but that inventory only clears a BLOCK when paired with a reachability check, because a lowering pass may strip the type before the consumer runs.** The cautionary case is exactly the `slang-emit-cpp.cpp:843` raw-deref of `getRequirementVal()->getOp()`: it *looks* like an unguarded `-target cpp/cuda` consumer the PR's hlsl/spirv-only test never drives, and on that basis a BLOCK was recorded on slang#12819 R1 — but it was a **FALSE BLOCK**. On the C-family path `slang-emit.cpp:1737` runs `lowerExistentials` before source emission, which rewrites every remaining non-COM / non-builtin `IRInterfaceType` into `TupleType(RTTI, witnessTableID, AnyValue)` (and a singleton conformance collapses straight to the concrete type), so an ordinary interface NEVER reaches `CPPSourceEmitter::emitInterface`'s struct body and the `:843` deref is dead for ordinary interfaces (COM interfaces return earlier via `emitComInterface`); the null value was also present pre-PR, so it was never a regression either. The transferable rule: before recording BLOCK on "producer P makes V null and consumer C raw-derefs V → crash," grep the emit pipeline for a lowering pass that REMOVES/rewrites the type before C runs; a green CI test that "exercises the path" is *not* proof C runs (the type may be lowered away first) and cannot be a trigger-present control for that branch; a crash claim that can't survive a reachability check is at most `ABSTAIN(OPEN_GAP)`, never BLOCK — BLOCK asserts a VERIFIED bug, and "the code raw-derefs and the value can be null" is only half, the other half being reachability [[approver/challenger-miss] before BLOCKing on an emit null-deref, prove the emit site is REACHED (lowerExistentials strips non-COM interfaces)](../learnings/1788235939874-approver-challenger-miss-before-blocking-on-an-emi.md). And a null-deref can *survive a PR redesign*: a stale bot review (harvest exit 10) flagged a deref that the head-current bot AND Devin then cleared — because the redesign *relocated* the call into a new helper. Diff reviewed-commit→head, re-derive whether each stale finding survives, and reproduce the crash by RUNNING a pre-existing test on the path (SIGSEGV at head, pass on master) [relocated null-deref survives a PR redesign; both head-current bots miss it](../learnings/1788069072973-approver-challenger-miss-relocated-null-deref-surv.md).

Two more probes. A "last-entry-wins / single-entry-point" safety assumption cited from an in-tree HACK comment must be probed empirically — running a prebuilt slangc on a mixed callable+compute whole-program `-target ptx` proved the multi-entry-point fold is reachable (a prebuilt binary is fine for a *reachability/dispatch* question even when it can't exercise the PR's new behavior) [don't clear a single-entry-point assumption on a HACK comment — probe reachability](../learnings/1787979428939-approver-challenger-miss-don-t-clear-a-last-entry-.md). And for a release PR that bumps a *just-published* dep tag fetched by constructed URL, check the BUILD CI, not tag existence — the tag existing is not every platform asset being uploaded, so pull the head's check-runs for RED jobs specifically and read a failing job's download step for a 404 [release PR bumping a just-published dep tag: check the build CI, not tag existence](../learnings/1787953794879-approver-challenger-miss-release-pr-bumping-a-just.md).
