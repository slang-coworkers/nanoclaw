# State Verification Discipline

Rules for verifying live external state before acting — covering GitHub PR/issue state, resume-after-pause workflows, stale feature/fix requests, submodule version reading, recurring tracker hygiene, and the general discipline of trusting observed state over saved memos or cached assumptions.

## TL;DR
- **A read of a live artifact is a MEASUREMENT WITH A TIMESTAMP, not a fact.** PR state, CI conclusion, draft/ready, review state, infra capability — all mutate. Re-probe before citing; a saved memo is a claim about a past instant.
- **A dispatch, a webhook, a nudge, and a timeout are all claims ABOUT state, never state.** Resolve live before acting on any of them. A timeout in particular describes a past instant and is not a decision.
- **Correcting the EXTENT of a claim about a mutable condition, while still stating it as a standing property, leaves the claim wrong.** Fix the tense too.
- **A matching sha does not establish a current reading.** Same-head is necessary, not sufficient — a check can have been re-run, evicted, or superseded since.
- **Verify the CI *conclusion*, not just draft+HEAD, before calling a chain terminal** — and check whether the "last activity" you are clocking is actually a terminal close.
- **A commit date is not a version, and not an edit time.** Read submodule pins by version, not by date; use `merged_at`, never a merge commit's `committer.date`, for when a PR landed.
- **Bot-filed and stale issues rot silently.** Re-verify every `file:line` against current main before relaying; a static-analysis pointer goes stale when the branch is gone, not just when the file changes.
- **A grep hit is a line, not a scope, and `grep -c` counts lines, not events.** A member cite names file, line **and** owner; a published count names the invocation that produced it — or is deleted.
- **A PR's changed-file list does not prove "not a regression."** Verify control-flow invariants against SOURCE, not against a triage memo or a reviewer's assertion.
- **Check ownership before driving anything.** Read issue comments and `head.repo.full_name`: a contributor-owned fork PR is not yours to park, close, or push. Stand down when a maintainer or contributor is driving.
- **Verify @-mention identity against the actual PR/commit author before posting** — a wrong mention is a public, unrecoverable error.
- **A corrupted tool-result turn taints its own verifications**; redo them in a clean turn rather than reasoning off the residue.
- **Post-compaction drift is real**: re-read state before autonomous action in a compacted session, because your premise may have been summarized away.
- **Recurring trackers must carry DISPOSITION, not just items**, and a daily report must carry open ship-stoppers — an item list with no disposition reads as handled.
- **Recurrence only advances on completion**, so a host event can orphan an overdue occurrence and freeze a whole daily series until a human notices. Watchdog the scheduler.
- **A verdict you already published is a past position, not a reason to skip re-checking.** A substantive new human comment re-opens a chain you closed.

## Re-verify Remote State Before Acting on Saved Plans

When resuming a fixer chain after a multi-day pause, the saved resume memo may be materially stale. Another session, the maintainer, or upstream automation may have advanced the PR while the chain was paused. Before acting on the memo, run a quick verification: `git log --oneline master..HEAD | head -10` (disk truth) and `gh pr view <N> --json isDraft,milestone,labels,title,body` (remote truth). If they don't match the memo, re-plan from observed state. Specific gotchas: `/tmp` snapshots are wiped on container restart; issues filed by a prior session produce a different number than the memo guessed; a draft PR may already be non-draft. Acting on a stale memo is the most likely path to wasted effort or destroying merged-down work. ([Resume-after-pause: re-verify remote state before applying the saved resume plan](wiki/learnings/1779847439047-resume-after-pause-re-verify-remote-state-before-a.md)) ⚠️ **`gh pr view --json` 401s ONLY WHILE GraphQL IS DOWN** (gh routes it via GraphQL; REST stays healthy) — ⛔**this was previously written as a standing property of the bot token, which is FALSE: refuted 2026-08-04, `gh pr view <n> --json isDraft,state,reviewDecision,mergeStateStatus,headRefOid` returned full JSON, exit 0.** **Probe `gh api graphql -f query='{viewer{login}}'` first**; if it answers, `--json` works and the REST recipe below is a fallback, not a requirement — use `gh api repos/<owner>/<repo>/pulls/<n> --jq '{draft,state,mergeable,mergeable_state}'` (REST is snake_case: `draft`/`mergeable_state`, not `isDraft`/`mergeStateStatus`), and get approval-on-head from `pulls/<n>/reviews` where `commit_id == .head.sha` — `reviewDecision` never establishes that an approval covers the current head.

## Re-pull Mutable PR State Before Asserting It

A PR's `isDraft`, `state`, `reviewDecision`, `mergeable`, and `mergeStateStatus` can change between turns due to maintainer or external activity. Before asserting any of these in a status report or `[Report]`, re-pull live with `gh pr view <n> --repo <owner/repo> --json isDraft,state,reviewDecision,mergeable,mergeStateStatus`. A maintainer flipped one PR from draft to ready-for-review within nine minutes of the bot opening it; the bot continued reporting it as a "parked draft" for two hours. Body edits do NOT dismiss an existing approval, so editing after approval is safe — but re-confirm `reviewDecision` before asserting it. ([Re-pull mutable PR state from GitHub before asserting it in a status report](wiki/learnings/1781702557335-re-pull-mutable-pr-state-from-github-before-assert.md)) Critically, the source must be the API `--json` field, NOT a WebFetch page summary: a WebFetch is an LLM interpretation of rendered page text, not an authoritative field, and reporting "queued for merge with auto-merge enabled" from a page scrape (slang#12178) was wrong — `gh pr view <n> --json autoMergeRequest` was `null` (auto-merge not armed, just approved + awaiting a manual merge), causing a false stand-down. WebFetch on a public repo is fine for comment text or which diff line a comment anchors, but never for structured PR STATE — read `autoMergeRequest`, `mergeStateStatus`, `reviewDecision`, `headRefOid`, and approval-on-head (`pulls/<n>/reviews --jq '.[]|select(.state=="APPROVED")|.commit_id'` must == head) from the API [Never read merge-queue / auto-merge state from a WebFetch page summary — use gh --json](wiki/learnings/1784817132922-never-read-merge-queue-auto-merge-state-from-a-web.md). ⚠️ **`gh pr view --json` 401s ONLY WHILE GraphQL IS DOWN** (gh routes it via GraphQL; REST stays healthy) — ⛔**this was previously written as a standing property of the bot token, which is FALSE: refuted 2026-08-04, `gh pr view <n> --json isDraft,state,reviewDecision,mergeStateStatus,headRefOid` returned full JSON, exit 0.** **Probe `gh api graphql -f query='{viewer{login}}'` first**; if it answers, `--json` works and the REST recipe below is a fallback, not a requirement — use `gh api repos/<owner>/<repo>/pulls/<n> --jq '{draft,state,mergeable,mergeable_state}'` (REST is snake_case: `draft`/`mergeable_state`, not `isDraft`/`mergeStateStatus`), and get approval-on-head from `pulls/<n>/reviews` where `commit_id == .head.sha` — `reviewDecision` never establishes that an approval covers the current head.

## Verify Live PR Draft/Ready State Before Reporting

A corollary: before writing "draft"/"ready"/"merged" in a `[Fix Report]`, run `gh pr view <n> -R <repo> --json isDraft,state,reviewDecision,mergeStateStatus` and report those values, not the last state set. A maintainer readying the bot's draft is the expected positive path toward merge — approval alone does not mean the PR is still draft. ## Verify the CI CONCLUSION, Not Just Draft+HEAD, Before Calling a Chain Terminal

Verifying `isDraft` + HEAD sha is NOT enough to call a coworker-PR chain "done/green/terminal" — you must also check the **CI run conclusion** on that HEAD. On slangpy#1051/PR#1053 a chain was reported terminal/"green" after verifying draft state + the expected HEAD commit, but the `ci` run had FAILED on every commit (a 6h GPU test-lane hang), forcing a public correction. Before any terminal rollup, run `gh api repos/<owner>/<repo>/actions/runs?head_sha=<sha>` (or `?branch=<branch>`), find the `ci` run, and confirm `status=completed` + `conclusion=success`. For a hang specifically, check STEP-level durations (`.../runs/<id>/jobs`), not just the conclusion — a job cancelled at the 360-min timeout reads as `cancelled`, and an in-progress wedge shows no conclusion at all. "Local tests pass" and "PR is draft at the right commit" say nothing about GPU CI lanes. This extends the "trust-but-verify a fixer's PR-state claims against live GitHub" discipline below to the CI conclusion, not just draft/ready/merge state ([Verify CI CONCLUSION (not just draft+HEAD) before calling a PR chain terminal](wiki/learnings/1784307063626-verify-ci-conclusion-not-just-draft-head-before-ca.md)).

The same discipline applies to a *cited* CI run in a release-report notification: verify it against live GitHub before trusting or forwarding, with one cheap `gh api "repos/<o>/<r>/actions/workflows/<id>/runs?per_page=3"` call. On 2026-07-20 a daily release-report re-presented the previous day's run as fresh — byte-identical `run_id` + `head_sha` + completion timestamp as the prior report — because the report path fed the latest `run_id` with no `latest_run_id == last_reported_run_id` guard, so when that day's scheduled dispatch silently failed to fire, it re-emitted the already-reported green. A genuine new run has a distinct `run_id` and a fresh completion timestamp, so **same run_id + same completion time is the tell for a stale re-report or a missed dispatch** — a green report is not proof a run happened today [Verify cited CI run against live GitHub before trusting a release-report notification](wiki/learnings/1784856735494-verify-cited-ci-run-against-live-github-before-tru.md).

## Fact-Check a "Pre-Existing Fleet Infra" CI Escalation Against Sibling PRs

When a fixer escalates a CI failure as "pre-existing fleet infrastructure issue, not my code" (often proposing to wait for some infra branch/fix), VERIFY before relaying it up or escalating to the operator — the framing is frequently wrong and the check is cheap. On slangpy PR#1053 the fixer blamed a 6h GPU-test-lane hang on a fleet-wide "CUDA-OOM cascade from `pytest --maxprocesses=4`, needs the unmerged `ci/cap-gpu-test-workers` branch," but a fact-check disproved it: ~11 contemporaneous open PRs ran the identical 12-job matrix on the same `main`/`--maxprocesses=4` and passed in ~12–17 min (not fleet-wide); the proposed cap branch was behind-main-19/ahead-1 with NO open PR (a dead end, not a plan); the PR branch was 19 commits behind main (stale-base was the leading hypothesis); and the macOS-aarch64 (Metal, no CUDA) lane was among those hanging (the CUDA-OOM story didn't fit). How to fact-check: pull ~10 recent open PRs, get each HEAD sha, list its `ci` jobs and per-job durations — if siblings pass the same matrix fast, it's the branch, not the fleet; verify any "waiting on infra branch X" claim (`compare/main...X` + `pulls?head=owner:X` — a stale/PR-less branch is not a plan); and the **cheapest discriminator for stale-base-vs-real-infra is rebase-onto-main + re-run** — if it still fails at 0-behind, stale-base is ruled out and escalation is justified (on #1053 it DID still hang post-rebase → genuinely isolated to the branch's test file wedging the GPU suite, legitimately escalated to the maintainer with runner access) ([Fact-check a fixer's "pre-existing fleet infra" CI escalation against sibling PRs before escalating to operator](wiki/learnings/1784307076980-fact-check-a-fixer-s-pre-existing-fleet-infra-ci-e.md)).

## Verify a Child's PR-State Claim Before Rolling It Upstream

A fixer/child's report of a PR's state (draft/ready, head SHA, review verdict, "held pending X") is a snapshot of *its own actions* and can be blind to maintainer-side moves that happen out-of-band. Before surfacing a state-dependent decision to the operator/parent, re-pull `gh pr view <N> --json isDraft,headRefOid,reviewDecision,state,mergeable` + the timeline. On #11881/PR #11883 the fixer accurately reported "did NOT flip ready" and teed up an operator ready-flip decision — but the maintainer (jkwak-work) had ~2 min earlier driven the PR himself (Update branch → `ready_for_review` → APPROVE → MERGE); relaying the fixer's framing verbatim would have asked the operator to authorize a flip that was already done and mis-stated the head SHA. Notes: GitHub's "Update branch" merge does NOT dismiss an existing approval (reviewDecision stays APPROVED on the new merge-commit head); a maintainer flipping/merging their OWN assigned PR is legitimate, not a bot-guardrail breach — distinguish "who acted"; and once a maintainer merges an APPROVED+MERGEABLE bot PR, a "wait for priority-yielded CI" hold becomes moot ([Verify a PR's live state before rolling a fixer's PR-state claim upstream — maintainer-side actions go stale fast](wiki/learnings/1782954654263-verify-a-pr-s-live-state-before-rolling-a-fixer-s-.md)). ⚠️ **`gh pr view --json` 401s ONLY WHILE GraphQL IS DOWN** (gh routes it via GraphQL; REST stays healthy) — ⛔**this was previously written as a standing property of the bot token, which is FALSE: refuted 2026-08-04, `gh pr view <n> --json isDraft,state,reviewDecision,mergeStateStatus,headRefOid` returned full JSON, exit 0.** **Probe `gh api graphql -f query='{viewer{login}}'` first**; if it answers, `--json` works and the REST recipe below is a fallback, not a requirement — use `gh api repos/<owner>/<repo>/pulls/<n> --jq '{draft,state,mergeable,mergeable_state}'` (REST is snake_case: `draft`/`mergeable_state`, not `isDraft`/`mergeStateStatus`), and get approval-on-head from `pulls/<n>/reviews` where `commit_id == .head.sha` — `reviewDecision` never establishes that an approval covers the current head.

## Verify Live GitHub State Before Acting on Hold/Revert Instructions

When a parent/peer sends a "hold / stop / revert / don't-do-X" instruction that could post-date a terminal action (PR opened, push done, comment posted), verify the live external state first with read-only commands rather than acting blindly. Surface any discrepancy with concrete facts and let the sender reconcile. Trust observed state over a possibly-stale instruction (the truthfulness invariant: "if a recalled memory/instruction conflicts with current information, trust what you observe now"). ([Verify live GitHub state before acting on a 'hold/revert/change-posture' instruction — instructions can be stale](wiki/learnings/1780510388169-verify-live-github-state-before-acting-on-a-hold-r.md))

## Stale Feature Requests Can Be Half-Implemented

For a feature request more than a few months old, never scope the remaining work from the issue body or maintainer comments alone — those describe the state when written. Fan out code subagents to map what has already landed versus what is missing at current HEAD. In one case a maintainer design comment described the work as unstarted, but verification showed most of the backend had already landed; the genuine remaining gap was far narrower than the issue implied. ([Stale feature requests can be half-implemented at HEAD — verify before scoping](wiki/learnings/1782215130307-stale-feature-requests-can-be-half-implemented-at-.md))

## Stale PR Fix-Requests: Verify Base Before Implementing

Before implementing a maintainer-requested fix on an aging PR, run two cheap checks: (1) verify the PR's base against current `origin/main` to see if the patched code was refactored away, and (2) confirm whether any referenced `#N` is an Issue or a PR (`gh api repos/O/R/issues/N --jq '.pull_request'` — non-null means it is a PR). A one-month-old PR base may have the patched code replaced on main, making the implementation moot. ([Stale PR fix-requests: verify base vs current main, and issue-vs-PR, before implementing](wiki/learnings/1782211781469-stale-pr-fix-requests-verify-base-vs-current-main-.md))

## Reporter's Release May Post-Date the Fix

When triaging a "this is already fixed on main, please update" response, verify the reporter's stated release version actually predates the fix commit before telling them to update. Map release tag → `gh release view <tag> --json publishedAt` and compare against the fix's merge date. Telling a reporter to update when they are already on a build that includes the fix causes them to dismiss the issue — potentially closing a real, unrefuted bug. ([Verify reporter's release actually predates the fix before telling them to update](wiki/learnings/1781251548493-verify-reporter-s-release-actually-predates-the-fi.md))

## Submodule Pin: Commit Date Is Not Version

When investigating a git submodule's pinned commit, do not trust the commit date as a proxy for the dependency version. Use `gh api repos/OWNER/REPO/commits/<sha>` cautiously — it resolves any object reachable in the fork network, including downstream patch commits not on `master`. To state the true version, read the version header at the pinned SHA (`IMGUI_VERSION`, etc.). To check reachability from the tracked branch, use `gh api .../compare/<pin>...master --jq '{status,ahead_by,behind_by}'`. ([Reading a submodule pin: commit date ≠ version; check reachability with compare](wiki/learnings/1782231360603-reading-a-submodule-pin-commit-date-version-check-.md))

**Read the pin from the committed gitlink, not the working tree.** A read-only specialist clone can have a submodule whose *working tree is checked out at a different commit than the superproject gitlink records* — and reading a version-pinned file from that stale tree fabricates the version number. On slang#11985 the `external/slang-rhi` working tree (`687dc18`, pins Vulkan-Headers v1.4.318) was ahead of the recorded gitlink (`29dc332`, pins v1.4.347); the wrong 318 reached a triage memo and a maintainer-facing GitHub comment and had to be retracted. The ~30-version gap *flipped the conclusion*: at 347, slang-rhi's Vulkan backend uses symbols (`VK_EXT_SHADER_FLOAT8_EXTENSION_NAME`, `VK_KHR_SHADER_BFLOAT16_EXTENSION_NAME`) absent from the vendored `external/vulkan` (VK_HEADER_VERSION 307), so the "redirect to vendored headers, it's a no-op" fix actually breaks the build and the network fetch is load-bearing. **Detection:** `git submodule status` prefixes a `+` when the checked-out commit differs from the recorded one; compare `git ls-tree HEAD external/<sub>` (gitlink) vs `git -C external/<sub> rev-parse HEAD` (working tree). **Fix:** `git submodule update --checkout external/<sub>` before reading any version-pinned file — critically, a standing "fetch/reset --hard origin/master; analyze against latest upstream" directive refreshes the *superproject* but does NOT re-sync submodule working trees, so add `git submodule update --recursive` after the reset for any submodule-touching analysis. When a version-dependent conclusion (symbol availability, API compat) rides on the pin, cross-check against a real build before posting it to a maintainer ([slang read-only clone: verify submodule is at gitlink before citing pinned versions](wiki/learnings/1783621027588-slang-read-only-clone-verify-submodule-is-at-gitli.md), [Verify submodule pins at the gitlink, not the working tree](wiki/learnings/1783621079268-verify-submodule-pins-at-the-gitlink-not-the-worki.md)).

## Recurring Trackers Must Carry Disposition, Not Just Items

For any periodic agent maintaining a carried-forward tracker (watch-list, status board), the file must record each item's disposition, reasoning, and who/when — not just the item. A fresh session re-derives state from raw source facts every run and keeps re-raising alarms that a human already dispositioned. The fix: structure every tracker entry with a leading Disposition line (active / de-escalated-monitor / retired), an explicit "do NOT re-flag" section for de-escalated items, and a header rule that a human's evidence-backed de-escalation overrides what the raw window re-derives. ([Recurring trackers must carry disposition + reasoning, not just items](wiki/learnings/1782461882511-recurring-trackers-must-carry-disposition-reasonin.md))

## Daily Maintainer Report Must Carry Open Ship-Stoppers

An open P0/ship-stopper fix must appear in every daily maintainer report until it reaches a terminal state (merged/closed). A PR that was opened more than 24 hours ago and is still in review falls outside the 24h merge/open window used by the fetch query and silently drops off. Keep a persistent watch-list file; at the start of every daily report, read it and carry every still-open entry forward with freshly-verified live state. Retire an entry only on merge/close or explicit human de-escalation. ([daily maintainer report must carry open ship-stoppers until merged](wiki/learnings/1781598056955-daily-maintainer-report-must-carry-open-ship-stopp.md))

## Test-Agent-Filed Issues: Strip to Minimum Before Trusting

When triaging issues filed by an agentic test-generation pipeline, do not trust the reporter's framing of the trigger. Always strip the repro to its minimum by commenting out lines one at a time to find the exact line that, when removed, makes compilation succeed. Also verify the "other targets work" claim independently — agentic reporters cite sibling tests they did not actually re-run. If the IR op in the error message is more generic than the narrow construct in the title (e.g. `castToVoid` vs. "enum-to-int cast"), the IR op is the real story. ([Test-Agent-Filed Issues Need Trigger Verification](wiki/learnings/1779958336217-test-agent-filed-issues-need-trigger-verification.md))

## Byte-Compare / Branch-Reachability to Localize a Perf or Behaviour Regression

When a perf/behaviour regression is bisected to a small diff on an LTO build, a clean bisect proves WHICH commit, not the MECHANISM. STEP-0 is to prove cheaply whether the diff even changes emitted/serialized output: build the culprit with a stderr marker inside the exact changed branch and run the real fixture (if the branch never fires, the two versions return identical values by construction — flag-independent), and byte-compare the artifact by reverting only the diff and doing an incremental relink (so build-metadata is shared and `cmp`/sha256 is confound-free). If the output is byte-identical, a regression bisected to that diff under LTO is almost always a code-LAYOUT artifact (function reorder/inlining shift) — the honest outcome is re-baseline, not chasing a phantom "optimize the hot path" fix on a path the diff doesn't touch ([Perf regression bisected to a fix ≠ the fix's logic is the cost (byte-compare serialized artifacts)](wiki/learnings/1783349482128-perf-regression-bisected-to-a-fix-the-fix-s-logic-.md)). **Critical correction:** the technique only proves a mechanism when run in the environment where the changed branch can *fire*. On slang #11952 the reverted-branch (`getRelativePath` empty-path case) is unreachable on Linux single-filesystem but DOES fire on the perf runner's cross-drive checkout (`W:` source, `C:` temp) — a green byte-compare in the wrong environment is a false negative, not evidence. Before concluding "this changed branch has no effect," ask whether it is even reachable in the env you're testing (cross-drive, Windows-only, GPU-only, big-endian, locale, filesystem-type), and when a human gives phase-resolved data (their timers put the cost in SemanticChecking) that contradicts your single-env repro, trust their measurement and find the reconciling condition ([CORRECTION: a byte-compare / branch-reachability test only proves a mechanism when run in the environment where the changed branch can fire](wiki/learnings/1783520640192-correction-a-byte-compare-branch-reachability-test.md)).

## A Corrupted Tool-Result Turn Taints Its Own Verifications

When a turn's tool results show ANY corruption signal — injected markup tokens (`</parameter>`, leaking `<invoke>`/`<parameter>` blocks), phantom fields (`_verify:null`), harness "tool result malformed / may be tampered" warnings — treat EVERYTHING derived in that turn as untrusted, INCLUDING artifact-existence "verifications" and files you wrote from it. The existing "verify before relaying a coworker's claim" discipline is not enough here: the *verification itself* can be the forged part, so re-checking within the same tainted turn proves nothing and just launders the fabrication. Re-verify any high-stakes claim (PR exists / merged / CI green / branch pushed) from a **fresh, self-issued tool call in a subsequent CLEAN turn** before publishing to GitHub or relaying upstream. Incident (slang#11982): a fabricated `[Fix Report]` claiming draft PR #11984 (never existed) was "verified" from the same corrupted stream and briefly posted "FIXED → PR #11984" publicly; clean `gh pr view 11984` ("Could not resolve") in a later turn exposed it. Publishing walks a claim *up* — the dangerous direction demanding the clean re-check; a retraction that walks a claim *down* against clean ground truth is safe to accept ([Verify claimed artifacts from a CLEAN self-issued call, never from same-turn corrupted tool output](wiki/learnings/1783467977502-verify-claimed-artifacts-from-a-clean-self-issued-.md), [A corrupted tool-result turn taints its own verifications](wiki/learnings/1783468158790-a-corrupted-tool-result-turn-taints-its-own-verifi.md)).

## A link orphaned by a byte bound is rescued by REORDERING its row, not by deleting text (2026-08-13 fold)

Amending a memory index by +457 B pushed two leaf links past the ~24.4 KB readable-prefix bound, orphaning them (0 orphans before the edit, 2 after — a self-inflicted regression). The wrong instinct, followed four times, was to shave prose to recover bytes — lossy, and it converges slowly because the shortfall is being guessed at, not computed (2→2→1→1 orphan across passes). What worked at zero information cost: the two orphaned links sat on one row that *straddled* the boundary, so reordering the links *within that row* — moving the past-bound one to the front — pulled it inside with no deletion, ending at 147/147 reachable and net index growth still +163 B. Reachability is set by whether a link's *byte offset* falls in the prefix, not by total file size; for a row spanning the cut, link order is free, so the question is never only "how do I make the file smaller" but "which side of the cut is each link on" ([A link orphaned by a byte bound can be rescued by REORDERING its row, not by deleting text](wiki/learnings/1786307748792-a-link-orphaned-by-a-byte-bound-can-be-rescued-by-.md)).

## Label Names, Denominators, and Zero-Change Instruments (2026-08-14 fold)

**A label name copied out of a prose spec is unverified until an enumeration endpoint confirms it.** The shader-slang triage label is `Dev Reviewed` (space), not `Dev_Reviewed` (underscore) — and the wrong spelling fails *silently in both polarities*: `label:"Dev_Reviewed"` → 0 (reads "nothing triaged"), `-label:"Dev_Reviewed"` → matches everything (reads "everything untriaged"). GitHub treats an unmatched label as a legitimately-empty result, no error. Control before trusting any label-filtered count: `GET /repos/{o}/{r}/labels?per_page=100` and grep the spelling; `label:"Dev Reviewed"` returns 720 as a non-empty control ([Slang triage label is "Dev Reviewed" with a space](wiki/learnings/1786263427862-slang-triage-label-is-dev-reviewed-with-a-space-de.md), [GitHub triage label is "Dev Reviewed", not "Dev_Reviewed"](wiki/learnings/1786263334409-github-triage-label-is-dev-reviewed-space-not-dev-.md)). **A tally must reconcile against its own denominator, and the denominator must be passed in, not derived from the slice being counted** — reporting "red 13 of the last 14 days" when the true population was 41 runs / 40 failure / 1 cancelled, from a `rs[:14]` literal slice (no `per_page` artifact, so "never infer a population from a page size" does not fire); `total_count=41` was printed three lines away and never compared ([a tally must reconcile against its own denominator](wiki/learnings/1786263724425-a-tally-must-reconcile-against-its-own-denominator.md)). **Validate a zero-change instrument with an independent positive control, not a re-read** — "0 count changes across 77 PRs" is indistinguishable from a probe that measures nothing; the control must come from a *different query* (list the newest 100 repo-wide runs, join against open-PR head shas, confirm the one genuinely-active PR appears in your output). A disagreement flag can also be a shape error in the comparison, not a change in the world — print both sides before believing the verdict ([validate a zero-change instrument with an independent positive control](wiki/learnings/1786270418170-validate-a-zero-change-instrument-with-an-independ.md)).

## Instrument Traps: Polymorphic Nulls, Truncated Read-Backs, Retyped Commands (2026-08-14 fold)

Three cross-domain instrument traps that also govern GitHub CI work (see the GitHub-instrument-limits page for the fuller versions). **A null from a polymorphic field is your accessor's error, not the API's absence** — on a User-vs-Team field, `.reviewer.login` returns `null` for a Team object that carries `name`/`slug` instead, indistinguishable from "unset"; the two readings imply opposite asks ("misconfigured, assign an owner" vs "a named team hasn't acted"). Print `sorted(obj.keys())` and check the `type` discriminator before concluding absence, and scrutinize a null *more* when it makes your finding scarier ([a null from a polymorphic field is your accessor's error](wiki/learnings/1786270804019-a-null-from-a-polymorphic-field-is-your-accessor-s.md)). **`ncl tasks list --json` truncates `prompt` to 120 chars** — a successful large-prompt write reads back as failed; read with `ncl tasks get <series> --json`, and generally: when a write reports success and your read-back contradicts it, suspect the READ first, before "repairing" ([ncl tasks list truncates prompt to 120 chars](wiki/learnings/1786266947337-ncl-tasks-list-truncates-prompt-to-120-chars-a-suc.md)). **Copy a command from their text — never retype it from their description** — testing your reconstruction tests nothing; a four-way refutation of a peer's `echo "exit=$?"` mechanism was entirely correct and entirely about a command nobody ran (the real defect, a `| head`, was verbatim one scroll up) ([copy the command from their text — never retype it from their description](wiki/learnings/1786268741453-copy-the-command-from-their-text-never-retype-it-f.md)).

## When Your Own Audit Flags Your Own Number, Diagnose the Predicate Before Editing the Data (2026-08-14 fold)

A self-audit flagging a figure you just wrote creates pressure to "correct" it so the check goes green — which can turn a correct number into a wrong one *and* retire the question. On a CI sweep, an audit flagged "claims skipped=22 but 23 marks pinned"; the claim was right, the audit wrong (a mark minted *during* a sweep belongs to a PR that sweep *triaged*, not skipped). What made it diagnosable was arithmetic distinguishing one cause from two: `claimed + marks_minted_this_sweep == marks_at_disk` held **exactly** for both findings (18+4=22; 22+1=23) — a shared exact offset is evidence of a common predicate bug, since two unrelated miscounts don't land on the same arithmetic. Fix the predicate, then **prove the fix didn't just silence the check**: the load-bearing control is a *planted* real undercount the guard must catch (`skipped=5` against 22 pinned) — without it, the "fix" is indistinguishable from one hardwired to pass — and assert on the finding's **message text**, not merely that a finding appeared ([when your own audit flags your own number, diagnose the predicate before editing the data](wiki/learnings/1786270644009-when-your-own-audit-flags-your-own-number-diagnose.md)).
