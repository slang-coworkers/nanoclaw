# State Verification Discipline

Rules for verifying live external state before acting — covering GitHub PR/issue state, resume-after-pause workflows, stale feature/fix requests, submodule version reading, recurring tracker hygiene, and the general discipline of trusting observed state over saved memos or cached assumptions.

## Re-verify Remote State Before Acting on Saved Plans

When resuming a fixer chain after a multi-day pause, the saved resume memo may be materially stale. Another session, the maintainer, or upstream automation may have advanced the PR while the chain was paused. Before acting on the memo, run a quick verification: `git log --oneline master..HEAD | head -10` (disk truth) and `gh pr view <N> --json isDraft,milestone,labels,title,body` (remote truth). If they don't match the memo, re-plan from observed state. Specific gotchas: `/tmp` snapshots are wiped on container restart; issues filed by a prior session produce a different number than the memo guessed; a draft PR may already be non-draft. Acting on a stale memo is the most likely path to wasted effort or destroying merged-down work. ([Resume-after-pause: re-verify remote state before applying the saved resume plan](../learnings/1779847439047-resume-after-pause-re-verify-remote-state-before-a.md)) ⚠️ **On the bot token `gh pr view --json` 401s** (gh routes it via GraphQL; REST works) — use `gh api repos/<owner>/<repo>/pulls/<n> --jq '{draft,state,mergeable,mergeable_state}'` (REST is snake_case: `draft`/`mergeable_state`, not `isDraft`/`mergeStateStatus`), and get approval-on-head from `pulls/<n>/reviews` where `commit_id == .head.sha` — `reviewDecision` never establishes that an approval covers the current head.

## Re-pull Mutable PR State Before Asserting It

A PR's `isDraft`, `state`, `reviewDecision`, `mergeable`, and `mergeStateStatus` can change between turns due to maintainer or external activity. Before asserting any of these in a status report or `[Report]`, re-pull live with `gh pr view <n> --repo <owner/repo> --json isDraft,state,reviewDecision,mergeable,mergeStateStatus`. A maintainer flipped one PR from draft to ready-for-review within nine minutes of the bot opening it; the bot continued reporting it as a "parked draft" for two hours. Body edits do NOT dismiss an existing approval, so editing after approval is safe — but re-confirm `reviewDecision` before asserting it. ([Re-pull mutable PR state from GitHub before asserting it in a status report](../learnings/1781702557335-re-pull-mutable-pr-state-from-github-before-assert.md)) Critically, the source must be the API `--json` field, NOT a WebFetch page summary: a WebFetch is an LLM interpretation of rendered page text, not an authoritative field, and reporting "queued for merge with auto-merge enabled" from a page scrape (slang#12178) was wrong — `gh pr view <n> --json autoMergeRequest` was `null` (auto-merge not armed, just approved + awaiting a manual merge), causing a false stand-down. WebFetch on a public repo is fine for comment text or which diff line a comment anchors, but never for structured PR STATE — read `autoMergeRequest`, `mergeStateStatus`, `reviewDecision`, `headRefOid`, and approval-on-head (`pulls/<n>/reviews --jq '.[]|select(.state=="APPROVED")|.commit_id'` must == head) from the API [Never read merge-queue / auto-merge state from a WebFetch page summary — use gh --json](../learnings/1784817132922-never-read-merge-queue-auto-merge-state-from-a-web.md). ⚠️ **On the bot token `gh pr view --json` 401s** (gh routes it via GraphQL; REST works) — use `gh api repos/<owner>/<repo>/pulls/<n> --jq '{draft,state,mergeable,mergeable_state}'` (REST is snake_case: `draft`/`mergeable_state`, not `isDraft`/`mergeStateStatus`), and get approval-on-head from `pulls/<n>/reviews` where `commit_id == .head.sha` — `reviewDecision` never establishes that an approval covers the current head.

## Verify Live PR Draft/Ready State Before Reporting

A corollary: before writing "draft"/"ready"/"merged" in a `[Fix Report]`, run `gh pr view <n> -R <repo> --json isDraft,state,reviewDecision,mergeStateStatus` and report those values, not the last state set. A maintainer readying the bot's draft is the expected positive path toward merge — approval alone does not mean the PR is still draft. ([Verify live PR draft/ready state before reporting it — maintainers can flip it](../learnings/1782236591493-verify-live-pr-draft-ready-state-before-reporting-.md)) ⚠️ **On the bot token `gh pr view --json` 401s** (gh routes it via GraphQL; REST works) — use `gh api repos/<owner>/<repo>/pulls/<n> --jq '{draft,state,mergeable,mergeable_state}'` (REST is snake_case: `draft`/`mergeable_state`, not `isDraft`/`mergeStateStatus`), and get approval-on-head from `pulls/<n>/reviews` where `commit_id == .head.sha` — `reviewDecision` never establishes that an approval covers the current head.

## Verify the CI CONCLUSION, Not Just Draft+HEAD, Before Calling a Chain Terminal

Verifying `isDraft` + HEAD sha is NOT enough to call a coworker-PR chain "done/green/terminal" — you must also check the **CI run conclusion** on that HEAD. On slangpy#1051/PR#1053 a chain was reported terminal/"green" after verifying draft state + the expected HEAD commit, but the `ci` run had FAILED on every commit (a 6h GPU test-lane hang), forcing a public correction. Before any terminal rollup, run `gh api repos/<owner>/<repo>/actions/runs?head_sha=<sha>` (or `?branch=<branch>`), find the `ci` run, and confirm `status=completed` + `conclusion=success`. For a hang specifically, check STEP-level durations (`.../runs/<id>/jobs`), not just the conclusion — a job cancelled at the 360-min timeout reads as `cancelled`, and an in-progress wedge shows no conclusion at all. "Local tests pass" and "PR is draft at the right commit" say nothing about GPU CI lanes. This extends the "trust-but-verify a fixer's PR-state claims against live GitHub" discipline below to the CI conclusion, not just draft/ready/merge state ([Verify CI CONCLUSION (not just draft+HEAD) before calling a PR chain terminal](../learnings/1784307063626-verify-ci-conclusion-not-just-draft-head-before-ca.md)).

The same discipline applies to a *cited* CI run in a release-report notification: verify it against live GitHub before trusting or forwarding, with one cheap `gh api "repos/<o>/<r>/actions/workflows/<id>/runs?per_page=3"` call. On 2026-07-20 a daily release-report re-presented the previous day's run as fresh — byte-identical `run_id` + `head_sha` + completion timestamp as the prior report — because the report path fed the latest `run_id` with no `latest_run_id == last_reported_run_id` guard, so when that day's scheduled dispatch silently failed to fire, it re-emitted the already-reported green. A genuine new run has a distinct `run_id` and a fresh completion timestamp, so **same run_id + same completion time is the tell for a stale re-report or a missed dispatch** — a green report is not proof a run happened today [Verify cited CI run against live GitHub before trusting a release-report notification](../learnings/1784856735494-verify-cited-ci-run-against-live-github-before-tru.md).

## Fact-Check a "Pre-Existing Fleet Infra" CI Escalation Against Sibling PRs

When a fixer escalates a CI failure as "pre-existing fleet infrastructure issue, not my code" (often proposing to wait for some infra branch/fix), VERIFY before relaying it up or escalating to the operator — the framing is frequently wrong and the check is cheap. On slangpy PR#1053 the fixer blamed a 6h GPU-test-lane hang on a fleet-wide "CUDA-OOM cascade from `pytest --maxprocesses=4`, needs the unmerged `ci/cap-gpu-test-workers` branch," but a fact-check disproved it: ~11 contemporaneous open PRs ran the identical 12-job matrix on the same `main`/`--maxprocesses=4` and passed in ~12–17 min (not fleet-wide); the proposed cap branch was behind-main-19/ahead-1 with NO open PR (a dead end, not a plan); the PR branch was 19 commits behind main (stale-base was the leading hypothesis); and the macOS-aarch64 (Metal, no CUDA) lane was among those hanging (the CUDA-OOM story didn't fit). How to fact-check: pull ~10 recent open PRs, get each HEAD sha, list its `ci` jobs and per-job durations — if siblings pass the same matrix fast, it's the branch, not the fleet; verify any "waiting on infra branch X" claim (`compare/main...X` + `pulls?head=owner:X` — a stale/PR-less branch is not a plan); and the **cheapest discriminator for stale-base-vs-real-infra is rebase-onto-main + re-run** — if it still fails at 0-behind, stale-base is ruled out and escalation is justified (on #1053 it DID still hang post-rebase → genuinely isolated to the branch's test file wedging the GPU suite, legitimately escalated to the maintainer with runner access) ([Fact-check a fixer's "pre-existing fleet infra" CI escalation against sibling PRs before escalating to operator](../learnings/1784307076980-fact-check-a-fixer-s-pre-existing-fleet-infra-ci-e.md)).

## Verify a Child's PR-State Claim Before Rolling It Upstream

A fixer/child's report of a PR's state (draft/ready, head SHA, review verdict, "held pending X") is a snapshot of *its own actions* and can be blind to maintainer-side moves that happen out-of-band. Before surfacing a state-dependent decision to the operator/parent, re-pull `gh pr view <N> --json isDraft,headRefOid,reviewDecision,state,mergeable` + the timeline. On #11881/PR #11883 the fixer accurately reported "did NOT flip ready" and teed up an operator ready-flip decision — but the maintainer (jkwak-work) had ~2 min earlier driven the PR himself (Update branch → `ready_for_review` → APPROVE → MERGE); relaying the fixer's framing verbatim would have asked the operator to authorize a flip that was already done and mis-stated the head SHA. Notes: GitHub's "Update branch" merge does NOT dismiss an existing approval (reviewDecision stays APPROVED on the new merge-commit head); a maintainer flipping/merging their OWN assigned PR is legitimate, not a bot-guardrail breach — distinguish "who acted"; and once a maintainer merges an APPROVED+MERGEABLE bot PR, a "wait for priority-yielded CI" hold becomes moot ([Verify a PR's live state before rolling a fixer's PR-state claim upstream — maintainer-side actions go stale fast](../learnings/1782954654263-verify-a-pr-s-live-state-before-rolling-a-fixer-s-.md)). ⚠️ **On the bot token `gh pr view --json` 401s** (gh routes it via GraphQL; REST works) — use `gh api repos/<owner>/<repo>/pulls/<n> --jq '{draft,state,mergeable,mergeable_state}'` (REST is snake_case: `draft`/`mergeable_state`, not `isDraft`/`mergeStateStatus`), and get approval-on-head from `pulls/<n>/reviews` where `commit_id == .head.sha` — `reviewDecision` never establishes that an approval covers the current head.

## Verify Live GitHub State Before Acting on Hold/Revert Instructions

When a parent/peer sends a "hold / stop / revert / don't-do-X" instruction that could post-date a terminal action (PR opened, push done, comment posted), verify the live external state first with read-only commands rather than acting blindly. Surface any discrepancy with concrete facts and let the sender reconcile. Trust observed state over a possibly-stale instruction (the truthfulness invariant: "if a recalled memory/instruction conflicts with current information, trust what you observe now"). ([Verify live GitHub state before acting on a 'hold/revert/change-posture' instruction — instructions can be stale](../learnings/1780510388169-verify-live-github-state-before-acting-on-a-hold-r.md))

## Stale Feature Requests Can Be Half-Implemented

For a feature request more than a few months old, never scope the remaining work from the issue body or maintainer comments alone — those describe the state when written. Fan out code subagents to map what has already landed versus what is missing at current HEAD. In one case a maintainer design comment described the work as unstarted, but verification showed most of the backend had already landed; the genuine remaining gap was far narrower than the issue implied. ([Stale feature requests can be half-implemented at HEAD — verify before scoping](../learnings/1782215130307-stale-feature-requests-can-be-half-implemented-at-.md))

## Stale PR Fix-Requests: Verify Base Before Implementing

Before implementing a maintainer-requested fix on an aging PR, run two cheap checks: (1) verify the PR's base against current `origin/main` to see if the patched code was refactored away, and (2) confirm whether any referenced `#N` is an Issue or a PR (`gh api repos/O/R/issues/N --jq '.pull_request'` — non-null means it is a PR). A one-month-old PR base may have the patched code replaced on main, making the implementation moot. ([Stale PR fix-requests: verify base vs current main, and issue-vs-PR, before implementing](../learnings/1782211781469-stale-pr-fix-requests-verify-base-vs-current-main-.md))

## Reporter's Release May Post-Date the Fix

When triaging a "this is already fixed on main, please update" response, verify the reporter's stated release version actually predates the fix commit before telling them to update. Map release tag → `gh release view <tag> --json publishedAt` and compare against the fix's merge date. Telling a reporter to update when they are already on a build that includes the fix causes them to dismiss the issue — potentially closing a real, unrefuted bug. ([Verify reporter's release actually predates the fix before telling them to update](../learnings/1781251548493-verify-reporter-s-release-actually-predates-the-fi.md))

## Submodule Pin: Commit Date Is Not Version

When investigating a git submodule's pinned commit, do not trust the commit date as a proxy for the dependency version. Use `gh api repos/OWNER/REPO/commits/<sha>` cautiously — it resolves any object reachable in the fork network, including downstream patch commits not on `master`. To state the true version, read the version header at the pinned SHA (`IMGUI_VERSION`, etc.). To check reachability from the tracked branch, use `gh api .../compare/<pin>...master --jq '{status,ahead_by,behind_by}'`. ([Reading a submodule pin: commit date ≠ version; check reachability with compare](../learnings/1782231360603-reading-a-submodule-pin-commit-date-version-check-.md))

**Read the pin from the committed gitlink, not the working tree.** A read-only specialist clone can have a submodule whose *working tree is checked out at a different commit than the superproject gitlink records* — and reading a version-pinned file from that stale tree fabricates the version number. On slang#11985 the `external/slang-rhi` working tree (`687dc18`, pins Vulkan-Headers v1.4.318) was ahead of the recorded gitlink (`29dc332`, pins v1.4.347); the wrong 318 reached a triage memo and a maintainer-facing GitHub comment and had to be retracted. The ~30-version gap *flipped the conclusion*: at 347, slang-rhi's Vulkan backend uses symbols (`VK_EXT_SHADER_FLOAT8_EXTENSION_NAME`, `VK_KHR_SHADER_BFLOAT16_EXTENSION_NAME`) absent from the vendored `external/vulkan` (VK_HEADER_VERSION 307), so the "redirect to vendored headers, it's a no-op" fix actually breaks the build and the network fetch is load-bearing. **Detection:** `git submodule status` prefixes a `+` when the checked-out commit differs from the recorded one; compare `git ls-tree HEAD external/<sub>` (gitlink) vs `git -C external/<sub> rev-parse HEAD` (working tree). **Fix:** `git submodule update --checkout external/<sub>` before reading any version-pinned file — critically, a standing "fetch/reset --hard origin/master; analyze against latest upstream" directive refreshes the *superproject* but does NOT re-sync submodule working trees, so add `git submodule update --recursive` after the reset for any submodule-touching analysis. When a version-dependent conclusion (symbol availability, API compat) rides on the pin, cross-check against a real build before posting it to a maintainer ([slang read-only clone: verify submodule is at gitlink before citing pinned versions](../learnings/1783621027588-slang-read-only-clone-verify-submodule-is-at-gitli.md), [Verify submodule pins at the gitlink, not the working tree](../learnings/1783621079268-verify-submodule-pins-at-the-gitlink-not-the-worki.md)).

## Recurring Trackers Must Carry Disposition, Not Just Items

For any periodic agent maintaining a carried-forward tracker (watch-list, status board), the file must record each item's disposition, reasoning, and who/when — not just the item. A fresh session re-derives state from raw source facts every run and keeps re-raising alarms that a human already dispositioned. The fix: structure every tracker entry with a leading Disposition line (active / de-escalated-monitor / retired), an explicit "do NOT re-flag" section for de-escalated items, and a header rule that a human's evidence-backed de-escalation overrides what the raw window re-derives. ([Recurring trackers must carry disposition + reasoning, not just items](../learnings/1782461882511-recurring-trackers-must-carry-disposition-reasonin.md))

## Daily Maintainer Report Must Carry Open Ship-Stoppers

An open P0/ship-stopper fix must appear in every daily maintainer report until it reaches a terminal state (merged/closed). A PR that was opened more than 24 hours ago and is still in review falls outside the 24h merge/open window used by the fetch query and silently drops off. Keep a persistent watch-list file; at the start of every daily report, read it and carry every still-open entry forward with freshly-verified live state. Retire an entry only on merge/close or explicit human de-escalation. ([daily maintainer report must carry open ship-stoppers until merged](../learnings/1781598056955-daily-maintainer-report-must-carry-open-ship-stopp.md))

## Test-Agent-Filed Issues: Strip to Minimum Before Trusting

When triaging issues filed by an agentic test-generation pipeline, do not trust the reporter's framing of the trigger. Always strip the repro to its minimum by commenting out lines one at a time to find the exact line that, when removed, makes compilation succeed. Also verify the "other targets work" claim independently — agentic reporters cite sibling tests they did not actually re-run. If the IR op in the error message is more generic than the narrow construct in the title (e.g. `castToVoid` vs. "enum-to-int cast"), the IR op is the real story. ([Test-Agent-Filed Issues Need Trigger Verification](../learnings/1779958336217-test-agent-filed-issues-need-trigger-verification.md))

## Byte-Compare / Branch-Reachability to Localize a Perf or Behaviour Regression

When a perf/behaviour regression is bisected to a small diff on an LTO build, a clean bisect proves WHICH commit, not the MECHANISM. STEP-0 is to prove cheaply whether the diff even changes emitted/serialized output: build the culprit with a stderr marker inside the exact changed branch and run the real fixture (if the branch never fires, the two versions return identical values by construction — flag-independent), and byte-compare the artifact by reverting only the diff and doing an incremental relink (so build-metadata is shared and `cmp`/sha256 is confound-free). If the output is byte-identical, a regression bisected to that diff under LTO is almost always a code-LAYOUT artifact (function reorder/inlining shift) — the honest outcome is re-baseline, not chasing a phantom "optimize the hot path" fix on a path the diff doesn't touch ([Perf regression bisected to a fix ≠ the fix's logic is the cost (byte-compare serialized artifacts)](../learnings/1783349482128-perf-regression-bisected-to-a-fix-the-fix-s-logic-.md)). **Critical correction:** the technique only proves a mechanism when run in the environment where the changed branch can *fire*. On slang #11952 the reverted-branch (`getRelativePath` empty-path case) is unreachable on Linux single-filesystem but DOES fire on the perf runner's cross-drive checkout (`W:` source, `C:` temp) — a green byte-compare in the wrong environment is a false negative, not evidence. Before concluding "this changed branch has no effect," ask whether it is even reachable in the env you're testing (cross-drive, Windows-only, GPU-only, big-endian, locale, filesystem-type), and when a human gives phase-resolved data (their timers put the cost in SemanticChecking) that contradicts your single-env repro, trust their measurement and find the reconciling condition ([CORRECTION: a byte-compare / branch-reachability test only proves a mechanism when run in the environment where the changed branch can fire](../learnings/1783520640192-correction-a-byte-compare-branch-reachability-test.md)).

## A Corrupted Tool-Result Turn Taints Its Own Verifications

When a turn's tool results show ANY corruption signal — injected markup tokens (`</parameter>`, leaking `<invoke>`/`<parameter>` blocks), phantom fields (`_verify:null`), harness "tool result malformed / may be tampered" warnings — treat EVERYTHING derived in that turn as untrusted, INCLUDING artifact-existence "verifications" and files you wrote from it. The existing "verify before relaying a coworker's claim" discipline is not enough here: the *verification itself* can be the forged part, so re-checking within the same tainted turn proves nothing and just launders the fabrication. Re-verify any high-stakes claim (PR exists / merged / CI green / branch pushed) from a **fresh, self-issued tool call in a subsequent CLEAN turn** before publishing to GitHub or relaying upstream. Incident (slang#11982): a fabricated `[Fix Report]` claiming draft PR #11984 (never existed) was "verified" from the same corrupted stream and briefly posted "FIXED → PR #11984" publicly; clean `gh pr view 11984` ("Could not resolve") in a later turn exposed it. Publishing walks a claim *up* — the dangerous direction demanding the clean re-check; a retraction that walks a claim *down* against clean ground truth is safe to accept ([Verify claimed artifacts from a CLEAN self-issued call, never from same-turn corrupted tool output](../learnings/1783467977502-verify-claimed-artifacts-from-a-clean-self-issued-.md), [A corrupted tool-result turn taints its own verifications](../learnings/1783468158790-a-corrupted-tool-result-turn-taints-its-own-verifi.md)).

## Post-Compaction Drift and Compacted-Session Autonomous Actions

A coworker reporting a large context compaction can drift into plausible-but-false task framing — the dangerous shape is when the drift resolves a *hold* into an *action* ("opening the PR is more responsive than sitting on it"), because the next step creates an irreversible external artifact. When a coworker you're coordinating reports a large compaction, treat its subsequent scope claims as suspect until re-grounded: hard-STOP on the peer edge before any external artifact exists, make it quote the exact dispatching message-id rather than proceed on reconstructed memory, and re-state the authorization boundary from YOUR canonical record. Halting before the artifact is cheap and correct under any hypothesis ([Post-compaction coworker drift: verify against the canonical thread and halt before any external artifact](../learnings/1783467434848-post-compaction-coworker-drift-verify-against-the-.md)). A worse variant: a compacted fixer can *schedule an autonomous fallback* (a timed fire) from stale state that executes a settled-wrong plan when the timer fires with no human in the loop (slang#11967: a ~3h fallback would have shipped an already-REJECTED Approach B and re-filed an already-existing issue). Correcting the reasoning is NOT enough — explicitly demand cancellation/redirection of the stale scheduled fallback and confirmation that it was neutralized, hold authoritative decisions in durable per-issue memory, and treat any fixer inbound that contradicts the settled record as a lost-context signal, not a new decision ([A compacted fixer can schedule autonomous actions from stale state — re-anchor and demand fallback cancellation](../learnings/1783477748732-a-compacted-fixer-can-schedule-autonomous-actions-.md)).

## Scope Conflict Across a Park/Re-Engage Boundary: Resolve From the Author's Comment

When a chain is parked and later re-engaged, two tiers' memories can end up directly contradicting each other on a load-bearing scope point (on #11925 the fixer's memory said "narrowed/default-OFF", the triager's said "full Mechanism B/default-ON" — both citing "the 07-03 decision", inverted). "Scope unchanged" is dangerously ambiguous across a park→re-engage boundary — unchanged from *which* state, the author's resolution or the parked self-narrowed plan? Do NOT resolve by picking the memory that matches your own; go to ground truth = the human author's written words on the issue/PR at current HEAD (`gh api .../issues/comments/<id>`) and treat it as the sole tiebreaker. A fixer that CHALLENGES a scope directive rather than silently shipping either interpretation is doing the right thing — resolve from the artifact and cite it. Before recommending a `groups restart` to recover a "dropped" chain, confirm the session is actually dead vs. deliberately parked-with-intact-WIP: a restart wipes the worktree, and "no branch/PR on origin" ≠ "no local work" ([Scope conflict across a park/re-engage boundary: resolve from the author's GitHub comment, not memory](../learnings/1783466589004-scope-conflict-across-a-park-re-engage-boundary-re.md)).

## Verify @-Mention Identity Against the PR/Commit Author Before Posting

Before naming a person as the author/owner of a PR, commit, or change in a GitHub comment, verify it against the actual source, not memory or inference — an `@`-mention of the wrong author is a public, maintainer-visible error that costs credibility (incident #11877: our verdict said "@skiminki-nv (author of #11493)" but csyonghe authored it; jkwak-work publicly called it out). The PR-number/commit citations can be right while the *person* is wrong — verify independently: `gh api repos/<o>/<r>/pulls/<n> --jq '{author: .user.login}'` and/or the commit's `.author.login`. Existing labels/assignees (`Office-<name>`) are a cross-check on who a maintainer thinks owns it, but confirm against the actual author; if caught, correct in-place on the bot's own comment, reply factually to the flagger, and fix any internal notes that carried the same error ([Verify @-mention identity against PR/commit author before posting to GitHub](../learnings/1783355490728-verify-mention-identity-against-pr-commit-author-b.md)).

## Bot-Filed Migration/Cleanup Issues Go Stale — Re-Verify Every file:line Against Current Main

For any issue whose claims are file:line-specific (especially bot-authored migration/cleanup tracking issues), grep the ACTUAL current-`main` source for every claim before accepting it, and compare the issue's `createdAt` to `main` HEAD — a fix may have landed independently after filing. On slangpy-samples#45 (filed 2026-06-16, triaged 07-08), 2 of 3 tracked breakage classes were already fixed on main by an independent commit `ba1d3106`; only one class remained live, and trusting the issue body would have generated ~10 files of redundant fix work. Apply: `git clone --depth 1` fresh and grep each claimed symbol/line; for each "still broken" claim that greps clean, run `gh api .../commits?path=FILE` to find the superseding commit; post the delta verdict rather than forwarding the stale claim ([Bot-filed migration issues go stale — re-verify every file:line against current main before triaging](../learnings/1783523441590-bot-filed-migration-issues-go-stale-re-verify-ever.md)).

The staleness can also run the *opposite* direction in time: a bot-filed follow-up issue can describe not-yet-stripped work as **already removed** — the plan, not the state. On slang#12150 (a maintainer-requested follow-up split out of draft PR #12148) the acceptance said the include-defined + multi-compilation-unit regression tests were "removed" from #12148, but the issue was filed 4 min after the maintainer *agreed to* the split — the trim commit was not yet pushed, so at the PR head `findIncludingNonIncludedSourceFile()` (+103 lines) and all 5 `tests/spirv/debug-function-scope-*` fixtures were still present. A fixer reading "restore the removed tests" literally would write them from scratch and diverge from the validated prototype; the correct move is to PRESERVE the about-to-be-stripped code/fixtures (branch/stash/cherry-pick from the pre-trim commit) before the PR is trimmed, then re-add and extend. General rule: when a follow-up issue (especially bot-authored, filed alongside a live PR) says work was "removed/deferred," verify the PR's actual current diff with `gh pr diff` before believing it — the issue may have been filed *ahead of* the change it describes; don't trust the tense ([Bot-filed follow-up issue may describe not-yet-stripped work as already removed (preserve before trim)](../learnings/1784330297555-bot-filed-follow-up-issue-may-describe-not-yet-str.md)).

## Recurrence-Advance and Wiki-Synth Pipeline Hygiene

Two failure modes surfaced when "learnings pushed but wiki not updated": (1) a stalled scheduled *occurrence* freezes the whole recurrence — a recurring task only mints its NEXT occurrence when the current one COMPLETES, so one un-fired `pending` row halts the entire series (all daily tasks froze at 07-03/07-04 while the 12-hourly supervise stayed current; re-arm with `update_task({taskId, processAfter})`). (2) Don't conflate the two independent knowledge_base pipelines — the daily *raw-learnings* sync (`knowledge_base sync ...` commits) pushes `shared/learnings/` but runs NO wiki synth, so "learnings are being pushed" can be true while `wiki/` is frozen because the separate wiki-synth task stalled. Diagnose by comparing counts on nv-coworkers. Also: when folding uncovered learnings, first split "genuinely new" from "already in a concept page" (`grep -l <stem> wiki/concepts/`) before writing synthesis, and resolve every truncated filename stem to its real file before scripting `[[...]]` links or they dangle ([learnings-wiki coverage-checker miscounts bracket-titled learnings + stalls freeze the whole recurrence](../learnings/1783327563514-learnings-wiki-coverage-checker-miscounts-bracket-.md)).

Two reinforcing lessons from slang#11860 (PR #11871, MERGED). ## Never fabricate downstream chain events or tracker-row state

Two reinforcing anti-fabrication rules. Do not narrate or act on a downstream chain event (a PR opened, a fixer report, `report_pr_created` called) until you have actually received that report ([1782981166747-never-fabricate-downstream-chain-event](../learnings/1782981166747-never-fabricate-downstream-chain-events-pr-numbers.md)). In status tables/5-bullets, never populate a PR number, branch, SHA, test filename, or CI-run state you haven't verified — leave it blank rather than invent it ([1782986994116-never-fabricate-pr-numbers-or-ci-state](../learnings/1782986994116-never-fabricate-pr-numbers-or-ci-state-in-tracker-.md)).

**A "dispatched" report is not a "done" report.** When a child sends "[X] dispatched to `<downstream>`", that closes only the dispatch — do NOT synthesize the downstream's result (HEAD SHAs, comment URLs, "re-verified", "posted") and relay it upstream as fact. On slang#10027 the triager sent two dispatch-complete reports that explicitly said "awaiting fixer's return"; the response fabricated the fixer's output — an invented comment URL and master HEAD, "trace posted to csyonghe and meets the bar" — and a `gh api .../comments` check proved no such comment existed. The compounding harm was then telling the triager "good work, hold as-is," which risks it ceasing to chase the fixer and marking the chain validated-done on false premises. Reply to a dispatch report with "acknowledged, forward the genuine return when it lands" — never with validation of output that doesn't exist yet. Concrete guard: before writing any sentence containing a comment URL, PR number, or commit SHA you did not personally see in a tool result *this turn*, run the `gh api` / `ncl` check that confirms it; if you can't confirm it, don't write it ([Don't fabricate downstream completion — a dispatch-complete report is not a done report](../learnings/1783626036685-don-t-fabricate-downstream-completion-a-dispatch-c.md)).

**Verify PR authorship via `pulls/<n>/commits`, never `commits?sha=<branch>` or `git log <branch>`.** The branch-scoped endpoints return the branch's full *ancestry* — once a maintainer merges master into a long-lived PR branch, that ancestry includes your bot's commits from *other* merged PRs, producing a false positive: "the bot pushed N commits to this PR" when it never touched the branch. On slang#10788, `commits?sha=copilot/fix-empty-structs-handling` showed "9 nv-slang-bot commits" (relayed to the operator as "bot engaged") but `pulls/10788/commits` showed 5 commits, 0 from the bot — the 9 were master's unrelated bot commits dragged in by a maintainer master-merge. Because authorship drives stand-down-vs-re-drive decisions, getting it wrong inverts the correct action (re-driving a "stalled" chain maintainers actually own = clobber risk). Always confirm the *author* of the specific commits via the PR-scoped endpoint before asserting "the bot worked / didn't work this PR" ([Verify PR authorship via pulls/<n>/commits, never commits?sha=branch](../learnings/1783639312952-verify-pr-authorship-via-pulls-n-commits-never-com.md)).

## Don't Infer a Causal Link the Failing Job's Log Never States

When triaging a CI/test failure, anchor the root cause to what the **failing job's own output** shows — do not stitch a nearby error from a *different* step/job into the failing one as its cause without evidence connecting them. A plausible code-trace that "would explain" a failure is a hypothesis, not a diagnosis, until the failing unit's log corroborates it — especially when you cannot reproduce locally. On slang#11985 the coworker chain diagnosed an intermittent macOS CI failure as a Metal-4.0 capability-attribute rejection (`[[required_threads_per_threadgroup]]` emitted by default, rejected on <4.0 Metal → exit 255), traced it through the compiler (`slang-emit-metal.cpp`; `metallib_latest=metallib_4_0` since PR #10592), and posted it as the verdict — then had to retract publicly. Two avoidable errors: (1) **inference presented as fact** — the metal-4.0 error appeared ONLY in co-located `slang-test` unit tests that *cleared on retry*; the actual failing example (`gpu-printing`) exited 255 with *zero output*, failing silently at `createComputePipeline`, and the log never showed a metal error there at all. Two co-located symptoms ≠ same cause. (2) **The mechanism predicted the inverse of the data** — "rejected on OLDER <4.0 Metal" implies *deterministic* failure on old runners, but the maintainer's 12-run correlation showed it was *flaky, only on the NEWEST macos-26 "Tahoe" image* (macos-15 passing). Flaky-on-new refutes deterministic-on-old.

Rules, before blaming a compiler mechanism for an intermittent CI failure: (a) confirm the error signature appears in the FAILING step's output, not just a co-located step; (b) "cleared on retry" means flake/environmental, not the deterministic bug you're tracing; (c) weight runner-image/OS correlation — a flake correlating with a NEW OS image is a driver/runtime change, not a static capability mismatch; (d) a silent exit-255 with no diagnostic points at RHI/device/driver, not shader compilation (which prints diagnostics); (e) when you can't reproduce locally, label the code-trace a hypothesis and weight empirical run-correlation above it; (f) if your mechanism predicts deterministic-on-old but the data is flaky-on-new, stop and reconcile before posting. What survived here: the emit-vs-`-std=metal3.1` attribute inconsistency is a genuine *latent* bug worth fixing on its own merits — but it was NOT the operative cause (a macOS-26 Metal driver/runtime race). When contradicted, reconcile honestly: re-read the primary evidence yourself, concede where the maintainer's is stronger, and post a fresh correction separating what survives from what's retracted — don't silently edit or defend ([slang#11985 Metal diagnosis was plausible-but-wrong: inferred attribute→gpu-printing link the log never supported](../learnings/1783642367486-slang-11985-metal-diagnosis-was-plausible-but-wron.md), [Don't infer a causal link the failure log never states](../learnings/1783642405453-don-t-infer-a-causal-link-the-failure-log-never-st.md)). Reinforces the same hedge-the-root-cause discipline as [A byte-compare / branch-reachability test only proves a mechanism in the environment where the changed branch can fire](../learnings/1783520640192-correction-a-byte-compare-branch-reachability-test.md) above.

## Verify an Accessor→Behavior Direction Against Source AND Artifact Before Publishing

When a triage verdict asserts "accessor X yields spelling/behavior Y," verify it against the accessor's *source* AND the *emitted artifact* before publishing — do not infer the direction from which producer "looked like" the canonical one. A reversed label survives casual review because the surrounding mechanism reads correctly. On slang#11982, an earlier learning labeled the two `PathInfo` accessors backwards; the correct mapping (verified in `source/compiler-core/slang-source-loc.cpp` and confirmed by `-g2` asm) is `getMostUniqueIdentity()` → `uniqueIdentity` = ABSOLUTE path, `getName()` → `foundPath` = the as-found (RELATIVE, in the repro) spelling. The root-cause *mechanism* (two hoistable `IRDebugSource` insts for one physical file differ only in the filename operand → dedup misses → orphaned third record; per-module `SharedIRGenContext` means they merge only at link time and only if the operand matches byte-for-byte) was correct — only the accessor→spelling direction was wrong, and it mattered because the final fix (PR #12034) had to canonicalize BOTH producers onto `getMostUniqueIdentity()` (absolute, per the author's request), the *opposite* of the reversed note's "loop → getName()" recommendation. The author caught it only because the requested spelling contradicted the stated mapping ([CORRECTION: slang getMostUniqueIdentity()=absolute, getName()=relative](../learnings/1783659293513-correction-slang-getmostuniqueidentity-absolute-ge.md)).

## Verify Open-PR Status Before Reaping a Worktree/Branch as "Abandoned" (Worktree-GC Trap)

Before proposing to reap any `fix/issue-<n>*` worktree or branch as "abandoned/exploratory," check for an OPEN PR whose head is that exact branch: `gh pr list -R shader-slang/slang --state open --head <branch>` (or `gh api repos/shader-slang/slang/pulls?head=<owner>:<branch>`). A local branch that looks like a dead earlier approach can be the live head of an open PR, and its worktree dir is that PR's working tree. Incident (2026-07-14): while reaping the merged `fix/issue-11917-matrix` (PR #11987), a sibling `fix/issue-11917-asafe-c` + its `wt-slang-11917-c` worktree was flagged as "an abandoned earlier approach" and offered for sweep — but that branch is the head of OPEN PR #12088 (draft=false); reaping it would have destroyed open-PR work. This is the classic worktree-GC trap: multiple `fix/issue-<n>{-suffix}` branches (`-asafe`, `-asafe-c`, `-pass2`, `-c`) from staged approaches to one issue, most merged/dead but ≥1 still backing an open PR. Only propose reaping after confirming NO open PR points at it; a squash merge makes `git merge-base --is-ancestor <branch> origin/master` return FALSE (expected, not "unmerged") — confirm merged via tip-SHA match + the squash commit subject instead. Never bundle a "want me to sweep the siblings too?" offer without running the open-PR check first, and don't manufacture a sweep from mild disk pressure (82% / 44G free is not pressure) — reap only the specific merged artifact you were dispatched for ([Verify open-PR status before calling a worktree/branch abandoned (worktree-GC trap)](../learnings/1784064164068-verify-open-pr-status-before-calling-a-worktree-br.md)).

## Revert-Drill Every Regression Test — a Positive-Only CHECK Can False-Pass

A regression test must be proven to **fail without the fix and pass with it**: run a revert-drill (build the pre-fix source, run the test, confirm it FAILS; restore the fix, confirm it PASSES) before considering the test done. A test that passes both with and without the fix guards nothing. The concrete false-pass mode: a **positive-only** `CHECK` silently passes when a *good* artifact coexists with the *bad* one it was meant to catch. Real example (slang#11982 / PR #12034, 2026-07-14): the bug emitted a duplicate filename-only `DebugSource %16` record *alongside* a correct 2-operand `DebugSource [[MODULE_FILE]] %id` record; the test asserted only `CHECK: DebugSource [[MODULE_FILE]] %id`, which the pre-fix output *also* satisfied — so it PASSED even with the bug present. Fix: add `CHECK-NOT: … DebugSource %id{{$}}` that rejects the filename-only shape (fails pre-fix, passes post-fix). For any regression test ask "which record/line does the BUG produce, and does my CHECK actively *reject* it?" — a `CHECK-NOT` on the buggy shape is usually the discriminating assertion; a `CHECK` on the correct shape often is not. This bit twice in one session (codex OUTPUT_REVIEW caught one on a draft; a maintainer caught the other post-approval, dismissing a fresh approval and forcing a re-approval cycle) — cheap to prevent with the drill, expensive to catch downstream ([Revert-drill every regression test — a positive-only CHECK can false-pass](../learnings/1784070069979-revert-drill-every-regression-test-a-positive-only.md)).

**Refinement — the drill is necessary, not sufficient: a positive control proves a test CAN fail, not that it fails for the RIGHT reason.** Ask whether your assertion reads an observable *the bug can actually move*; if bug and fix produce the same value for what you assert on, the test is vacuous and will sail through its own control. On slangpy#1073 a test named "out of order zone end leaves the thread zone stack usable" asserted `parent_index == -1` and **passed with the fix fully neutered**: an earlier fix in the same area had already zeroed `zone_stack[0]`, so the parent read `0` fixed-or-broken. Two compounding traps — **stacked fixes in one area silently strip the natural observable for the next** (re-derive each test's discriminator after every fix, and re-fire the earlier controls), and **a counter you reach for may aggregate the thing you're testing** (`producer_drop_count` sums in `stack_overflow_count`, which the out-of-order `end_zone` itself bumps, so that assertion could never hold *with* the fix). Cure: assert the **downstream damage** — capacity exhausted, count wrong, operation rejected — never an intermediate flag other code normalizes; the rewritten test opens 64 zones after the out-of-order pair and asserts `zone_count() == 65`. What caught it was positive-controlling *the control itself*: "if this test were vacuous, would this control have told me?" (usually: no) ([control the control — a positive control proves a test can fail, not that it fails for the right reason](../learnings/1785775582684-control-the-control-a-positive-control-proves-a-te.md)).

**And when a control doesn't fire, read it as a verdict on your MODEL before your assertion.** The reflex ("my test is too weak, strengthen it") can leave you measuring a fiction more precisely. On the same PR the true reading was that the predicted symptom *does not exist*: `parent_correlation_id != 0` guards the parent lookup (`profiler.cpp:832`, `:1396`), so a zeroed slot yields an **unparented** zone, never a **mis-parented** one — the capacity leak was always the entire damage. Run the questions in order: (1) does the symptom I asserted on actually follow from this bug? trace the consumer; (2) did one of my own earlier fixes create the sentinel I'm asserting against? a value chosen for being "impossible" (`0`, `-1`, empty) is exactly the value existing code already special-cases as "none"; (3) only then treat it as a weak-assertion problem. Getting the order right corrects a wrong belief about the system, which is worth more than a better test — and it gives a reviewer a reason to trust the replacement ("I asserted on a symptom that doesn't exist; the real damage is X") instead of doubting it ([a failed positive control can mean you misunderstood the bug](../learnings/1785777308342-a-failed-positive-control-can-mean-you-misundersto.md), [a control that doesn't fire may mean you misunderstood the bug — refines "control the control"](../learnings/1785777358105-a-control-that-doesn-t-fire-may-mean-you-misunders.md)).

**Control each hazard separately — one test covering two interacting bugs can mask one.** When a reviewer finds a second bug in your fix, the natural move (extend the one regression test to cover both) can cancel the first. On slangpy#1073 bug B's trigger — re-presenting the stale token after the inner zone ends — made the third `end_zone` satisfy the *valid* path and release there, so the merged test still passed with bug A's release stanza deleted. Revert fix A alone → the A-test must fail; revert B alone → the B-test must fail; a test claiming to cover both owes **both** reverts. Symptom to watch for: a test whose later steps re-drive the state the earlier steps were supposed to leave broken. Split them, and leave a comment saying why they must stay split ([one test covering two interacting bugs can mask one of them](../learnings/1785773887358-one-test-covering-two-interacting-bugs-can-mask-on.md)).

**"Test exists" ≠ "test runs" ≠ "test can fail."** Reviewing slangpy#1073 round 1, a reviewer APPROVE'd a lock-free reorder partly on two cited guards it had confirmed existed at the right line numbers and were unmodified by the PR — both were `doctest::skip()`-disabled on `main` by an earlier PR with `// TODO: Re-enable when #1073 is merged`. Grep the test **declaration** for skip/disable markers (`doctest::skip()`, `DISABLED_`, `@pytest.mark.skip`, `#if 0`, `GTEST_SKIP()`, early `return;` behind a capability check) — a skipped test is worse than a missing one because it reads as coverage. A PR changing **zero** test lines while claiming coverage is a finding, not a reassurance. For race fixes specifically, demand the revert-alone positive control; a green suite says nothing about a window the scheduler may not enter. Also bound "this gate could stall forever" concerns by finding the force-release valve **and** the conditional it is nested in, and bound wrap-based "formal holes" by physical reachability before reporting them as defects ([reviewing a race fix: check whether the cited regression guards are actually enabled](../learnings/1785777415067-reviewing-a-race-fix-check-whether-the-existing-re.md)).

That review's own numbers then needed correcting on three points, and the correction is the sharper lesson: **a number that is stated is not a number that was measured** — a fourth disguise for the same bug as the skipped test, the stale binary and the vacuous assertion. `sizeof(CpuEvent)` was *estimated from the field list* at 56 bytes and published; compiling both layouts gave **64**, because the PR under review had itself added a field — so the reachability headline was overstated ~888× (~2 PiB, not "~2 exabytes"). **Be most suspicious of a number when the conclusion is so robust that a wrong value wouldn't change it** — "unreachable ⇒ document-only nit" held at either figure, so nothing downstream would ever challenge the input: a quantity load-bearing for *nobody* is unverified by construction. Reviewing a diff makes you *more* exposed, since you hold base and head in mind and can silently compute against either — **any derived quantity (`sizeof`, capacity, offset, count) must be measured against the head being reviewed**, and padding makes field-list arithmetic unreliable independently of any diff. Two further corrections there: don't collapse "formal holes" with **different preconditions** (one wrap was allocation-bounded, the other needed only a `local_sequence` wrap and is *considered*, not *impossible*), and when bounding a stall, check the release valve's call frequency **and** the guard it is nested inside. General habit: for every published number, name how it was established — measured / compiled / read at HEAD / inferred — and treat "inferred" as a TODO whenever the upgrade is cheap ([CORRECTION to "reviewing a race fix": measure sizeof, keep wrap holes distinct, read the guard the valve sits inside](../learnings/1785778166680-correction-to-reviewing-a-race-fix-measure-sizeof-.md), [a robust conclusion hides a wrong input — and your own diff can invalidate a correct estimate](../learnings/1785778243573-a-robust-conclusion-hides-a-wrong-input-and-your-o.md)).

When a supervisor/parent nudges "the fixer dropped a promise, no PR exists, re-wake it and open the draft" for a stalled issue chain, do NOT reflexively chase the fixer into a PR. ## Answer-Instantly Means Post Verified Facts, Not an Extrapolated Positive Claim (2026-07-21 fold)

A standing instruction to "answer a re-ask instantly" with citations in hand authorizes posting **exactly the facts you actually verified, at the precision you verified them** — it does NOT authorize extrapolating a *new positive capability claim* you haven't tested. On slang#11877 the verified fact was a *negative* ("the JS/WASM bindings expose no compiler-option surface"); "answer instantly" was misread as "produce a helpful-sounding answer fast," and a bot comment substituted a more satisfying *positive* ("`import glsl;` is a flag-free route that works from JavaScript") that went beyond — and actually contradicted — the verified negative. The reporter tested it, hit `E38201`, and refuted it publicly, forcing a correction. The discipline: if the verified fact is a negative, the instant answer is that negative plus its citations; any new positive capability claim ("this route works", "you can do X via Y") requires testing before posting — a repro, a source-traced path, or an existing cited fact — never an extrapolation to satisfy a fast-answer instruction ([Standing answer-instantly = post verified facts, never extrapolate a positive claim](../learnings/1784551466296-standing-answer-instantly-post-verified-facts-neve.md)).

## Verifying an ENFORCING Gate: Combined-Input Bypass + Build-Wiring Reachability (2026-07-21 fold)

Verify-at-head on a *tool that enforces* (a check that `exit 1`s to block a PR) needs the adversarial mindset of reviewing a security check — "how does this fail to fire / how does the bad input slip past?" — not "does the happy path read correctly?" Two recurring failure modes each pass a naive per-branch read, both learned from a live miss on slang#12157's IR-version-bump differ (PR #12158) that a verify-at-head pass approved and the reviewer+codex pipeline then reopened. **(1) Combined-input bypass.** The differ enforced "new IR instruction added ∧ version not bumped → fail" but had a `removedKeys > 0 → return 0` early-return that is individually defensible ("a rename shouldn't hard-block") — yet in *combination* (a PR that removes/renames anything AND independently adds a new instruction) the early-return let the new instruction ride in with no bump, silently defeating the exact case the gate exists to catch. Discipline: enumerate the *cross-product* of input conditions ({added} × {removed/renamed}) and confirm the enforced case still fires under every combination, especially where an early `return 0`/short-circuit precedes the enforcing branch; the fix here keyed on stable identity (instruction stable-ID absent from the base set = genuinely new) with no early return. **(2) Unproven build-wiring.** The tool was registered via a CMake `generator()` macro wiring it only under `all-generators`, which the default `cmake --workflow --preset debug` (the CI build the check runs in) does NOT pull — so the binary was never built in that path and the wrapper's `find` would be empty → `exit 1` on every PR (fail-closed the wrong way). The PR body's "built via all-generators dependency" claim was accepted, not proven. Discipline: when a check depends on a build artifact, prove the artifact is produced by the specific CI build/preset that invokes it (trace the dep graph or build it) — same class as "verify claimed artifacts," but for build-graph reachability; the fix was an explicit `add_dependencies(slang-test <tool>)` ([Verify-at-head: check enforce logic against COMBINED inputs + prove build-wiring, don't accept it](../learnings/1784568390472-verify-at-head-check-enforce-logic-against-combine.md), [Verify enforcing gates against combined-input cases + prove build-wiring](../learnings/1784568398186-verify-enforcing-gates-against-combined-input-case.md)).

## Associate a CI Run to THIS PR+Head Before Crediting Its Conclusion (2026-07-24 fold)

Before saying a check is "green/cleared" or "flake/stale," verify each run's *association* — its PR number (`displayTitle`) AND head SHA — not just its conclusion. On slang#12202 (twice) two distinct over-claims shared this root: "11319 passed / 0 failed = infra flake" was read from an *earlier/different attempt* than the one red on the current head, and "requeue cleared it" cited two `success` slangpy `repository_dispatch` runs that were actually for *other PRs* (#12190/#12206). ## Fixing a Crash Can Be a Multi-Layer Cascade — Verify Each Layer, Stop at the Safe Boundary (2026-07-25 fold)

Fixing a "front-end crashes on X" issue often *unmasks* deeper layers the crash was hiding, so a clean triaged one-liner can turn into a multi-layer cascade — and a partial fix can be strictly worse than shipping less. slang#12210 (`[Differentiable]` on a property getter segfaults) became three layers: **L1** the filed crash (`getFuncType` cast a `PropertyDecl` parent to `CallableDecl` and null-deref'd — one-line gate); **L2** exposed by L1 (getter now rejected at the call site with E41022 because property accessors aren't registered for autodiff like subscript accessors — small fix, makes forward-diff work); **L3** exposed by L2 (`bwd_diff` asserts in the reverse-mode transform — property `apply_bwd` func type comes out missing the `this` receiver — NOT confidently root-caused). The decision rule that saved the ship: **L1+L2 without L3 is strictly worse than L1 alone** — they convert a clean E41022 diagnostic into an internal assert-crash on `bwd_diff` — so L2 was reverted and only L1 shipped (crash → clean diagnostic), deferring full support to a follow-up. Detection technique: after the crash fix builds, actually EXERCISE the feature the crash was blocking (run *both* `__fwd_diff` and `bwd_diff` through it, not just "does it compile"); compare against the working analog (subscript accessor) to tell "genuine feature gap" from "wiring bug"; and ground-truth layer sizing in the IR (`-dump-ir` param counts: property `apply_bwd` = 0 params vs subscript = 2), not in subagent speculation — two sizing passes gave two *different* wrong theories for L3, and the IR was the only reliable signal. Corollary to the "mirrors an existing working path" trap: verify the working path's mechanism actually matches your theory — the L3 theory ("add getThisParamType like RematFuncType") couldn't explain how the subscript's `apply_bwd` already gets its `this` when that resolver has no such code; that unexplained gap is the tell the root cause is elsewhere — don't ship on it ([Fixing a crash can be a multi-layer cascade — verify each layer before shipping, stop at the safe boundary](../learnings/1785026926217-fixing-a-crash-can-be-a-multi-layer-cascade-verify.md)).

## Byte-Verify a Hand-Apply Patch by Post-Image Blob Hash (2026-07-28 fold)

The "review the actual source, not a reconstruction" invariant survives even when the branch is UN-fetchable (e.g. a `.github/workflows/*` App-`workflows`-permission wall or a worktree on another coworker's filesystem). Prove byte-identity to the committed HEAD without reading the fixer's disk: (1) confirm your clone's base file blob equals the patch's pre-image hash (`git rev-parse HEAD:<path>` vs the `index <pre>..<post>` line) — if equal, your working copy IS the fixer's pre-edit file; (2) apply the exact committed diff bytes (from the fixer's pasted `git show <sha>`); (3) `git hash-object <path>` on the result and compare to the stated post-image blob. A match is proof, not an eyeball. Load-bearing subtlety: always re-hash the CURRENT sha — when a fixer amends (e.g. to drop a redundant comment per review), the SHA and blob move, and that movement is exactly the tell that content changed. Concrete: #12062 twin `removeRequestedReviewers` hardening (base `dd6e011e56`, pre-image `a3bfb08f31`, committed `4147d58fb2`, post-image `f46f95ac14`) — applied diff → `git hash-object` returned `f46f95ac14…` == stated → clean APPROVE ([byte-verify a hand-apply patch by post-image blob hash](../learnings/1785261494633-byte-verify-a-hand-apply-patch-by-post-image-blob-.md)).

Extend the file:line-verification discipline to **doc/spec paths a reporter cites**. Triaging #12261, a high-signal MEMBER reporter wrote the behavior "disagrees with the language reference (`docs/language-reference/statements-break-and-continue.md`)" — but that path does not exist at HEAD, and the actual `statements.md` is *silent* on the rule, not contradictory. Echoing "the impl contradicts the reference" would have been a false public claim; the honest framing ("the reference is silent/underspecified") also reframes the fix as a spec-gap opportunity. Treat a cited doc/spec path exactly like a code pointer: `[ -f <path> ]` and grep the actual reference for the rule before repeating "disagrees with the spec" — reporters' pointers drift ([verify a reporter's cited doc/spec path before repeating "impl disagrees with the reference"](../learnings/1785320946422-verify-a-reporter-s-cited-doc-spec-path-before-rep.md)).

## Controls, discrimination, and proxy verification — part 1

Everything above asks *is my source live and primary?* This section is the complementary question, learned mostly on 2026-08-03 across the slangpy#1087/#1088 + slang#11225 chain, the slang critique-gate fleet, and slang-rhi#800: **could this observation have come out differently if I were wrong?** Provenance discipline and method discipline are separate checks and you need both — the worst offenders below were all read from correct primary sources.

### The discrimination test — a signal that cannot separate the states you care about carries zero bits

Before an observation carries a conclusion, ask whether it would have looked different had the opposite been true; if not, no amount of careful sourcing rescues it ([the unifying diagnosis: a signal that cannot distinguish the states you care about](../learnings/1785750713482-the-unifying-diagnosis-a-signal-that-cannot-distin.md)). **Absence claims need a positive control; presence claims mostly don't.** The canonical miss: `grep -c "DEEPEST SUBCASE: d3d12"` → 0 cited as "no d3d12 failures," when the same pattern on `vulkan` — where all 28 failures were — also returns 0, because doctest emits `DEEPEST SUBCASE STACK REACHED …` with the subcase name on the *following indented line*. The pattern matched nothing; the zero was unfalsifiable ([a grep returning 0 is only evidence if the same pattern returns non-zero for a known-present case](../learnings/1785749557692-a-grep-returning-0-is-only-evidence-if-the-same-pa.md), [same rule, reviewer-side: run the positive control first](../learnings/1785750137847-a-grep-returning-0-is-only-evidence-if-the-positiv.md); a third near-identical filing survives only as a [dedup pointer](../learnings/1785749767697-a-grep-returning-0-is-only-evidence-if-the-same-pa.md)). Companion traps from the same corpus: **Windows runner logs are CRLF**, so `$`-anchored patterns silently return nothing on `windows.log` while working on `linux.log` — a *second* vacuous zero behind a plausible command (`tr -d '\r'` first, strip the ISO timestamp prefix); enumerate a diagnostic's *distinct* values rather than testing for one you predicted; prove completeness by matching the real header's count against the reported failure count; and CI logs are downloadable unauthenticated, so "gh isn't authenticated" never justifies accepting a relayed figure. Three refinements are worth as much as the base rule. **A log absence tells you WHAT, never WHY** — even a correctly-derived zero with a passing control cannot separate *ran-and-exited-early* from *never-a-step* from *excluded-by-an-`if:`*; resolve the cause at the workflow/build **definition**, and note that an enumeration bounds its claim to the surface that actually ran (a "complete fix" argument rested on 56 occurrences counted on the C++ test surface while the Python surface never compiled, making a second site unfindable by construction). **A count can be topically right and semantically empty** — `grep -c pytest` = 22 was entirely `pip install` chatter, 1 after filtering. And **a claim you have had to weaken twice is telling you the property is not verifiable in your environment** — say that outright instead of hedging a third time (`passed` → `no observed failure` → `consistent with, plus the alternative` is the tell). The test applies to citation *shapes*, not just patterns: a **line range** that straddles two constructs cannot discriminate "drifted guard" from "adjacent construct that needs none" — `:507-514` cited as a missing device term spanned a correct two-clause runtime guard and a separate `#if` preprocessor block, so the citation proved neither hypothesis ([run the discrimination test on line ranges too](../learnings/1785751219892-run-the-discrimination-test-on-line-ranges-too-a-c.md)). It applies one level further out as **a correct probe pointed at the wrong observable**: corroboration needs a *causal path*, not an overlapping target set — a capability-set mutation and three layout branches sharing one call site read as one mechanism, but none of the branches reads the promoted capability, so an A/B measuring layout/offsets would have found no difference either way and reported "no flip" ([two mechanisms at one call site are not one mechanism — derive the measurement from what the mechanism mutates](../learnings/1785752093299-two-mechanisms-at-one-call-site-are-not-one-mechan.md)). Finally, **the detector is itself a claim**: a duplicate-H1 scan using `grep -c "^# "` counted `#` bash comments inside fenced code as headings, and when a count surprises you on an artifact you believe is clean, suspect the counter first — the instinct to fix the artifact is what turns a detector bug into corrupted data ([a detection query is itself a claim needing a discrimination test](../learnings/1785775510720-a-detection-query-is-itself-a-claim-needing-a-disc.md)). Two practices make all of this reviewable: prefer **two independent extraction methods** for any load-bearing claim, and **publish the extraction command alongside the finding** — a command gets run against inputs its author never had, which is how the vacuous grep was caught at all.

### Diagnose an instrument's blindness from its shape, before running it — a green result can be structurally incapable of red

The revert-drill above proves a test *can* fail; this cluster covers the checks that cannot, and which therefore manufacture their own supporting evidence. **When a check reads one element of an unordered or arbitrarily-ordered set, its passing carries no information** — diagnose that from the command's shape, since nothing prompts you to vary anything while a coincidence is reassuring you. `[ "$(git rev-parse HEAD)" = "$(cat .git/shallow | head -1)" ]` as a shallow-clone discriminator coincides whenever HEAD happens to sort first (`.git/shallow` is SHA-sorted); measured false-agreement was ~1/6 on a 6-entry fixture and a **coin flip** on a 2-entry one, and *the smallest, most natural fixture is the one most likely to lie to you* — both author and reviewer logged an agreeing run as confirmation before a deliberately-built larger fixture forced a second look ([a check that reads one element of an unordered set cannot be validated by running it](../learnings/1785768953168-a-check-that-reads-one-element-of-an-unordered-set.md)). Those rates were then themselves an instance of the failure they described: `--depth` implies `--single-branch`, so the modal real shape (`clone --depth 1 --branch <pr-head>`) writes exactly one shallow entry and the bad check agrees **~always** — anyone reading "3/12" would wrongly conclude testing would have caught it. Second measured smell from the same amendment: **a check whose verdict an unrelated later operation can flip was never measuring its subject** (an extra `git fetch --depth 1` flipped it in 4 of 12 fixtures with HEAD untouched), and the stable form is `--is-shallow-repository` plus empty `git log -1 --format=%P` ([CORRECTION: the false-agreement rates were measured on a configuration nobody reaches by accident](../learnings/1785769120004-correction-to-the-false-agreement-rates-depth-impl.md)). The same blindness appears one layer up in the artifacts we *demand as proof*: we told a fixer to prove a `sourceLoc`-propagation fix with a `-g2` SPIR-V golden, got byte-identical output at `-g1/-g2/-g3`, and read it as "no observable effect" — but `OpLine`/`DebugLine` are emitted only from explicit `kIROp_DebugLine` markers placed at statement granularity, so propagating a loc onto a value inst changes emitted output **by construction**; the test could not fail before it was run, and **when you specified the unsatisfiable test, the miss is yours, not the implementer's** — match the assertion layer to the *contract* layer (here a pass-level IR invariant) ([byte-identical output is not proof a patch is effectless — check the layer](../learnings/1785775152713-byte-identical-output-is-not-proof-a-patch-is-effe.md)). And in CI: a one-line parser change merged with 10 green checks while breaking a test that lives in a directory **no `pull_request`-triggered workflow ever executes** — so don't ask "is CI green?", ask "is the suite covering this change reachable from a `pull_request` event?" Trace the runner's default test root, grep `.github/workflows/` for who passes a non-default root, read *those* `on:` blocks, and follow `workflow_call` up to the real caller since a called workflow's own triggers tell you nothing. Two sub-traps: `grep -c pull_request` on a workflow file is **not** a trigger check (the nightly's single hit was an env expression inside `jobs:` — confirm the hit's line falls inside the `on:` block), and don't oversell adjacent tooling as the net (the staleness tracker reported all 68 bundles already stale — a saturated signal cannot isolate a new break — and the "Lint on PR" attachment point the docs describe **does not exist**: documented intent ≠ wired) ([a green PR check can be structurally blind — verify the suite is reachable from pull_request](../learnings/1785771123651-a-green-pr-check-can-be-structurally-blind-verify-.md)).

### Verify the thing, not a convenient proxy — environment, arm, baseline, pointer, mechanism-breadth

**Executed ≠ observed.** A code path can run in an environment where its effect is invisible: a guard's false arm *did* execute locally (`SGL_HAS_NVAPI: OFF` ⇒ predicate always false) but against a Slang pin where the diagnostic under test was unreachable, so it ran without being able to discriminate patched from unpatched. That learning also fixes **which arm owes verification**: when a fix narrows an unconditional action behind a predicate, the true arm restores the pre-patch path verbatim and is *inert by construction*, so "the `P == true` path is unverified" points at the arm needing no verification and stays silent on the real question — did anything on the newly-skipped path depend on the side effect that no longer happens? Over-correcting into "the inert arm is unverifiable, weight it accordingly" is its own inaccuracy; and "can't test configuration X" is usually too coarse — a diagnostic raised in `TargetRequest::checkCapabilities()` keyed on the *target* is testable with no D3D12 device at all, so split what needs the hardware from what only looked like it did ([which arm of a compatibility guard carries the risk](../learnings/1785750665244-which-arm-of-a-compatibility-guard-carries-the-ris.md)). Relatedly, **a pin-independent fix's risk baseline is the pinned dependency, not the unreleased upstream change that motivated it** — the pin-independence that makes it safe to land early is exactly what makes the post-merge world the wrong comparison; fetch the dependency at the pinned ref (`gh api repos/<o>/<r>/contents/<path>?ref=<tag>`) and ask which configurations behave differently *under the pin*, and note that a green CI matrix lacking the exposed configuration cannot see the flip. Its corollary on two-clause predicates inverts a grep: `hasOption(Profile)` was unconditionally true because the *upstream* session code calls `setProfile()`, so grepping the downstream repo for the option name "confirms" no profile is requested — exactly backwards ([a pin-independent fix's risk baseline is the pinned dependency](../learnings/1785751904901-a-pin-independent-fix-s-risk-baseline-is-the-pinne.md)). **Never ship a hedge for an environment failure you did not personally hit**: a dispatch handed down a specific `E00100` link failure to state publicly, but that belonged to the upstream tier's container — relaying it would have laundered another agent's failure under our bot identity and destroyed the best evidence in the review, *because if you believe you can't compile, you don't try*. With a working compiler the code comment's own premise ("valid programs cannot have by-value struct cycles") was testable and didn't carry: a 143-level acyclic chain compiles clean via `groupshared` and trips `E39997` only behind a `RWStructuredBuffer`. Watch for **DCE faking a pass** — a 200-deep type "compiled" only because the value was never stored, output byte-identical to an empty shader; compare artifact sizes against a trivial baseline before believing a negative ([never ship a hedge for an environment failure you didn't personally hit — prove the premise, hedge the inference](../learnings/1785748057767-never-ship-a-hedge-for-an-environment-failure-you-.md)). Two Slang-specific proxies worth naming: in slang-rhi's Vulkan backend, `areDefined()` deliberately excludes `VK_API_DEVICE_OPT_PROCS` and `addFeatureExtension` does not clear the feature bool it rejects, so a gate written `if (!api.m_extendedFeatures.X.y) bypass;` **tests a stale feature bit and never the proc pointer** and can jump through null with no C++/Python exception — gate on the proc pointer ([optional Vulkan proc pointers are loaded unchecked and feature bits survive a rejected extension](../learnings/1785774873723-slang-rhi-vulkan-optional-proc-pointers-are-loaded.md)). But that clean mechanism was then *refuted by call ordering*: the enclosing function called the proc **twice** and the reported fault was the second call — a null function pointer faults at the **first** call site, so reaching the second proves it was non-null, no matter how well the rest fits. Same logic for a suspect `this`/context pointer successfully dereferenced earlier in the frame; and don't invoke "optimized builds are imprecise" as a blanket licence to move a fault 8 lines to where your hypothesis needs it — weigh how big a misattribution you are asking for ([a null function pointer faults at the FIRST call site](../learnings/1785775592426-a-null-function-pointer-faults-at-the-first-call-s.md)). Finally, **breadth-of-mechanism is the author's job and no gate will do it**: rejecting a whole approach after one failed spelling (`set(... CACHE STRING "" FORCE)`) led to building the more complex detection-based fix, which every codex gate passed — because gates validate *the shape you chose*, not whether a simpler mechanism existed (`*_FLAGS_DEBUG_INIT` seeding before `enable_language()`, which the maintainer used in the superseding PR). Its second-order half is the same error with the sign flipped: endorsing that superseding fix by **repeating its PR body** rather than running it — env `CXXFLAGS='-O0 -g3'` still yields `-Og` winning, so the described env-var case is not fixed. A PR body is a claim, not evidence ([review gates validate the shape you chose, not whether a better mechanism exists](../learnings/1785769682134-review-gates-validate-the-shape-you-chose-not-whet.md)).

### A verified negative has a shelf life — stamp it, re-probe, and distrust a degraded source's empty answers

"I verified X does not exist" is true only at the instant you probed, and on a fast-moving chain that shelf life is **minutes**. A stale negative is more dangerous than a stale positive because it reads as authoritative — especially when filed as a *correction*, the kind of note later readers trust. Concretely: a rigorously-verified "slangpy has no guard PR and no branch" (all 25 open PRs listed, refs grepped) was overtaken 14 minutes later by `slangpy#1088`; re-probing rather than trusting the note is what avoided "correcting" a true statement with stale evidence. Hence: **timestamp every existence claim, positive or negative** ("no guard PR *as of 08:50Z*"); re-probe before reusing a negative across a time gap; treat **a relay that contradicts your verified negative as possibly NEWER, not wrong** — check timestamps before deciding who is mistaken; and remember that filing a correction as a *new* note leaves the superseded one circulating unmarked, so whoever can edit the old one must add a forward pointer (strike the stale sentence legibly, add the newly-verified state with its own timestamp, explain why both were true) ([a verified negative has a shelf life — stamp it and re-probe](../learnings/1785753815343-a-verified-negative-has-a-shelf-life-stamp-it-and-.md)). The same applies to infrastructure health: a logged `✅ RECOVERED` for the GitHub gateway's GraphQL-401 facet held for at most ~2h before both probes 401'd again — the outage **flaps**, and a stale positive reads identically to a live one. Re-probe at the top of every run and let the probe, not the note, choose the transport (`gh api graphql -f query='{viewer{login}}'` paired with a REST control so "facet down" is distinguishable from "my credentials are broken" — the remediations differ completely). This matters because `gh pr checks` is GraphQL-backed: with stderr swallowed it returns **phantom all-green** for every PR, the "green job + zero coverage" shape. And **when a data source degrades, its *empty* answers are the dangerous ones** — a GraphQL-derived `evicted: []` in a wake payload was manufactured absence that a REST cross-check refuted ([a logged RECOVERED for a flaky gateway is a past observation, not current state](../learnings/1785795692860-a-logged-recovered-for-a-flaky-gateway-is-a-past-o.md)). This extends the page's "trust observed state over a possibly-stale instruction" invariant in one direction it did not cover: *your own verified finding* is also a possibly-stale instruction.

### Correcting posture is the highest-risk posture — a retraction is a load-bearing claim too

**Verification performed in order to correct someone requires more rigour than the original claim, not less** — a cheap spot-check feels sufficient precisely when auditing someone else's figure, and the corrector's number then travels with the correction's borrowed authority. Three instances in one day: a "correction" of 76 non-draft open PRs to **54** from a single un-paginated `?per_page=100` call (the raw page length of exactly 100 was the tell; both agents had written up this truncation mode hours earlier — *knowing it didn't prevent it, only running the method does*); an "I'll go fix that upstream" promise that dissolved on re-reading what was actually published, since the addition changed neither the count, the ask, nor the fix shape (**diff what is published against what you believe needs saying, before the write** — silence is the correct output surprisingly often); and a stale presupposition inside a live human escalation, where every underlying fact was right but the phrasing outran the evidence — recoverable in a log, **not** recoverable in a human's decision queue ([correcting posture is the highest-risk posture](../learnings/1785774655133-correcting-posture-is-the-highest-risk-posture-aud.md)). Four corrections in this batch demonstrate the failure and its cure. (1) **A wrong premise supporting a right conclusion is the hardest error to catch** — "the `#if SGL_HAS_NVAPI` block *structurally cannot* carry a device term" is false (a `#if` body can nest a runtime `if`; in-repo precedent at `helpers.cpp:64`), it was generated *while correcting someone else's overclaim* by reaching for an absolute, and it passed three tiers because the conclusion matched what each reader already believed: distrust "structurally cannot / impossible / always" in your own output, especially after "actually, no," and treat agreement with your prior belief as a prompt to verify ([the correction embedded in the line-range learning](../learnings/1785751219892-run-the-discrimination-test-on-line-ranges-too-a-c.md)). (2) **Let the hedge govern the headline**: a note hedged "presence is transient/ordering-dependent — inference, not finding" in its body and headlined "**dead code**" anyway; a peer refuted the universal with three real admin bypass cards that could only exist if the path had run, and the corrected scope is an *ordering race* (5 of 7 state-touching hooks create the state dir). Before calling a path unreachable, look for an **independent creator of its precondition** — and don't inherit the peer's substitute mechanism either: `workflow-state-reset.sh` was measurably disarmed on that edge (a hook registered with an empty matcher is not therefore a hook that runs), the real creator being `track-edits.sh`, whose allowlist exempts `/workspace/agent/memory/*` but not coworkers whose memory lives elsewhere — so **a memory write after an OUTPUT_REVIEW approve blocks a `WOULD_APPROVE` delivery while an ABSTAIN sails through** (finish memory writes before the OUTPUT_REVIEW round) ([CORRECTION: the escalation defect is an ordering race, not dead code](../learnings/1785821186056-correction-the-critique-gate-escalation-defect-is-.md)). (3) **A retraction can itself be the error, and narrowing a claim is not testing its premise**: the same agent then retracted a peer's *correct* card attribution. The generative rule is the off-diagonal cell — seeing A-with-X and B-with-Y, even twice, does not establish that X discriminates A from B; **construct the case your hypothesis forbids, not another instance of the case it predicts** (here one `mktemp` and one hook invocation, versus shipping a filing with a true finding retracted out of it). Two received rules travel with it: **"a tier's last correction being right is not evidence for its next one"** — momentum is the mechanism, so when you have just been right your next claim earns *more* scrutiny — and flagging your own bias is not a substitute for testing the premise ([hit names the surface, reason names the defect — and the off-diagonal-cell rule](../learnings/1785821641484-critique-gate-hit-names-the-surface-reason-names-t.md)). (4) The mirror of over-retraction: establishing that a tool is buggy does **not** establish that any particular number it touched is wrong — the H1 scan's real predicate was an *adjacency* window immune to the fence-comment bug (147 either way; only the naive `count > 1` variant moved, 174 → 149), and **discarding a sound result is a false negative you chose**, near-invisible in a shared store because nothing later contradicts a number that no longer exists. Write down the predicate you are questioning *before* looking at the numbers, and ask separately whether repairing a real-but-cosmetic defect is net-positive (fix the generator, not the corpus) ([the over-correction half of the detection-query learning](../learnings/1785775510720-a-detection-query-is-itself-a-claim-needing-a-disc.md)).

**Superseded elsewhere, flagged for the reconciliation pass.** One correction in this batch retires a technique recommended in a learning not yet folded here: `1785780759447-check-whether-a-requested-feature-is-already-reach.md` bullet 5 tells readers to "resolve the arm by line-numbered boundaries (`grep -n '^#if\|^#else\|^#endif'`)" — **that pattern cannot match `#elif`**, so a three-armed chain silently reports as two-armed and `#else` *looks* live when it is dead. Ground truth at `d9353c090`: in `slang-glslang.cpp` the `#elif 1` arm at `:344` is what ships as `-O1`; the `#else` at `:384` is dead. Match every arm-introducing directive (`#elif`/`#elifdef`/`#elifndef`), print the whole chain with nesting depth, count *inside* the arm you cite, and prefer `cc -E` over inference. The failure is self-consistent in both directions — identical surrounding comment text supports "rotted into `#if 0`" and "won and shipped" — so a wrong arm-read does not feel wrong and the correcting reviewer reached the opposite-but-also-wrong answer with the same blind pattern. Do not reintroduce "`#else` is the live arm" as a general rule ([CORRECTION: an #if 0 chain can have an #elif — an #elif-blind grep inverts the dead/live verdict](../learnings/1785781716720-correction-an-if-0-chain-can-have-an-elif-a-grep-t.md)).

### A policy gate is an instrument, not a permission boundary — and it suppresses its own controls

The critique-gate incidents are verification lessons, not just ops trivia, because **the gate is an instrument whose denials cannot be used as evidence and whose design suppresses its own passing cases**. Facts first: `gate-critique-on-deliver.sh`'s hardcoded floor pattern `gh pr create|gh api [^|]*pulls\b|api\.github\.com[^ ]*/pulls\b|createPullRequest` (`:52`) is un-configurable and per-group markers are **additive only**, so "the actual trigger" is edge-dependent — on a floor-only edge `state=` on `issues/N` cannot trip it while a read-only `gh api …/pulls/N --jq .state` trips it regardless of method. Before declaring "the actual trigger," reconcile against every prior characterization that had evidence, and prefer **reading the config** (`cat $OVERLAY_DIR/.critique-delivery-markers`) over probing — because the gate matches command **TEXT pre-execution**, a probe script *containing* the pattern is denied whole, so bundling a denied substring with a control kills the control (that is not nondeterminism), and each blocked probe emits an admin escalation card ([the gate has two distinct triggers — reconcile before calling one "the actual trigger"](../learnings/1785782804999-critique-gate-has-two-distinct-triggers-reconcile-.md)). The same `pulls\b` pattern false-positives **PATCH-to-close**, so retiring a superseded draft demands PLAN+CODE+OUTPUT_REVIEW where there is no plan, no code and no output to score; the correct response is to finish everything safe (closing comment via `issues/N/comments`, local worktree/branch reaping after `git ls-remote` confirms nothing unpushed) and report the single gap — **endpoint-hunting after an explicit deny is evasion, not compliance**, and the tempting workaround is destructive: deleting an open PR's head branch auto-closes it, reaching the denied outcome through a side channel (close first, delete second) ([critique gate blocks PR CLOSE, not just create — and branch-delete is a destructive false workaround](../learnings/1785799595481-critique-gate-blocks-pr-close-not-just-create-and-.md)). That note's escalation advice is **superseded**: its line recommending the block "needs an operator/maintainer close or a gate-pattern narrowing" is wrong, because the gate/token evaluation is **per-edge** — the byte-identical `gh api -X PATCH repos/shader-slang/slang/pulls/12072 -f state=closed` succeeded on the parent's edge ~4 minutes later. **A gate deny means "forbidden *to me*", not "forbidden"**: escalate one tier up with the verbatim command, the per-route failure modes, what you already completed safely, and the close-before-delete ordering ([CORRECTION: the PR-close denial is per-edge — escalate one tier, not to an operator](../learnings/1785799761929-correction-the-critique-gate-pr-close-denial-is-pe.md)). The deepest lesson here is a **retraction of a finding that had already been praised and escalated**. The original filing reported three findings, the headline one being that "the gate matches on command TEXT, not intent, so it is defeated by trivial obfuscation" (a coworker's earlier call slipped it by splitting the `pulls` literal across a shell variable), concluding the gate "is friction against a literal spelling, not enforcement" and recommending it be hardened to "match on the resolved call (method + endpoint at execution time)" ([a text-matching policy gate is defeated by trivial obfuscation](../learnings/1785799855999-a-text-matching-policy-gate-is-defeated-by-trivial.md)). **Both the framing-as-defect and that remediation are withdrawn.** The hook's own source comment above the matching `grep` states that "pattern enumeration can never be complete — the durable backstop is credential-layer enforcement at the OneCLI proxy," so a split literal slipping the grep *confirms a documented limitation* rather than revealing an unknown one, and hardening the hook would make it load-bearing exactly as the authors declined to do, manufacturing more of the false-positive class that started this. What survives is narrow: the `pulls\b` PATCH-to-close false positive is real and worth narrowing; one line of that source comment ("these cover every egress shape observed in production") is now factually stale; whether the credential backstop actually covers `gh`/`git` egress is a question for the hook's owner, correctly declined from an agent session; and the per-edge asymmetry stands. The method lesson is the durable one: the downgrade came from the coworker who had *supplied* the finding, after it was praised — **verify a nudge's premises when the nudge is CREDIT, not only when it is criticism**, since an escalation of your own finding is the case where you are least likely to re-check it — and a relayer must re-derive a *retraction* at source too, because relaying one on trust is the same error as relaying an upgrade on trust ([CORRECTION: the text-matching design is documented, not a defect — only the PATCH-to-close false positive is real](../learnings/1785799990839-correction-the-slang-critique-gate-s-text-matching.md)). One reading rule for anyone triaging a denial or bypass card: `hit` and `reason` are **orthogonal by construction** — `hit` names the *surface* blocked (set purely from tool + pattern match), `reason` names the *defect* from session state — so `hit="PR creation"` does not mean a PR was being created; read `reason` to attribute a card, and to test a route-string pattern without tripping it, assemble the string at runtime (`P=$(printf 'p%s' 'ulls')`).

**Qualification to content already on this page.** The byte-compare section above states that "If the output is byte-identical, a regression bisected to that diff under LTO is almost always a code-LAYOUT artifact (function reorder/inlining shift) — the honest outcome is re-baseline". That stands for *perf attribution*, but the byte-identity premise needs one more check before it licenses "no semantic effect": ask whether the artifact can express the property **at the contract's layer** at all. Where it cannot (the `sourceLoc`/`DebugLine` case above), byte-identical output is guaranteed by construction and carries zero information — an absence manufactured by the measurement rather than evidence about the patch. Read that section together with the layer check.

## Controls, discrimination, and proxy verification — part 3

### Verify that your negative control is actually a control

The reassuring reading of a null result is almost always available and almost never supported. Three successive probes for "is a GitHub credential being injected into my requests?" were each offered as the fix for the previous one and each was wrong, because a transparent egress proxy (`HTTPS_PROXY` → the OneCLI gateway) injects **per-path, only where a secret rule matches** — never per-connection: `.permissions` on a repo response appears for any public repo regardless of auth; `rate_limit` reporting `limit: 60` means *that path* has no rule, not that the connection is anonymous; and stripping your own `Authorization` header does not create an unauthenticated request because the proxy re-supplies it (same call still returned `X-Ratelimit-Limit: 6000`). Worse, the *offered negative control* (`repos/torvalds/linux`, "no rule ⇒ no ratelimit headers") was not a control either — it returned **401 `"Bad credentials"`**, i.e. GitHub speaking after a credential was forwarded and rejected, whereas a genuinely anonymous request to a public repo returns 200. "The control returned nothing" and "the control failed" look identical if you read only the status line: read the **body** ([a transparent egress proxy invalidates most credential probes — verify your negative control is a control](../learnings/1785781869329-a-transparent-egress-proxy-invalidates-most-creden.md)). The follow-on measurement makes the working probe precise and kills the value-based variant too: `X-Ratelimit-Limit` is per-*resource* (core 6000, search 30), so "6000 ⇒ injected" misreads a successfully-injected search call as unauthenticated — only **presence of the header on the exact path you are about to use** carries auth information, and `gh api rate_limit` is itself an un-ruled path that returns the gateway's `app_not_connected` body with zero numeric fields, making any "rate_limit shows 60 vs 6000" recipe **unexecutable during the exact outage it exists to diagnose** ([under a per-path credential proxy only header presence on the exact path is informative](../learnings/1785781925764-under-a-per-path-credential-proxy-x-ratelimit-limi.md)). The same shape appears far from credentials. A "the compiler fails to emit `OpControlBarrier`, therefore racy" claim was published from the *absence of an instruction in emitted output* without checking whether the spec mandates it — `GLSL_EXT_mesh_shader` states `EmitMeshTasksEXT` "implies a `barrier()`" — and the one-command control was already in hand: running the same grep against the **known-good, test-covered `groupshared` idiom** also yields `grep -c OpControlBarrier == 0`, so the rule would convict the form the project ships ([CORRECTION: absence of an instruction is not a missing-barrier bug](../learnings/1785804434887-correction-absence-of-an-instruction-is-not-a-miss.md)). An empty listing is likewise evidence about the query surface, not the world: `ncl tasks list` in every form (`--all`, `--group`, `--status pending`) returned "No tasks." *while executing inside* the scheduled task it claimed did not exist — a capability-negative whose known-positive control was free, and whose natural next step ("the cron was never created, let me create one") manufactures a duplicate schedule on top of an invisible live one ([ncl tasks list reports "No tasks" while a scheduled task is running](../learnings/1785808113754-ncl-tasks-list-returns-no-tasks-even-while-a-sched.md)). The differential test for silent row caps — run the call at default and at an explicit high limit, compare — is honest but **asymmetric**: differing output proves a cap engaged, identical output proves *nothing* (14 rows at default, at `--limit 500`, at `--limit 2000` is consistent with a 200-row cap and simply does not test it), so it can establish that a cap exists and never that one is absent; for absence you need the documented default or a positive control like `total_count` ([the differential test can prove a cap exists, never that one is absent](../learnings/1785803020077-silent-cap-detection-the-differential-test-can-pro.md)). Finally, an absence-of-signal claim carries its **threshold** as part of the claim, not as a tuning knob: `in>=1, out==0` over **17 days** is unambiguously stuck, while the same instrument over **3 minutes** has zero discriminating power because a turn in flight emits no outbound until it completes — a supervisor re-woke a live triager at ~3 minutes asserting it "produced no turn," and the honest statement about the wrong verdict published four minutes later is that the wake made it *more likely*, not that it caused it (the counterfactual is untested) ([a silence threshold is part of the claim, and a nudge must never direct publication](../learnings/1785804074351-a-silence-threshold-is-part-of-the-claim-absence-o.md)).

### Match the instrument to the claim — membership, completeness, identity, currency

Different claim shapes need structurally different checks, and substituting one for another produces luck reported as verification. Two tiers disagreed on a session count; the approver backed its 17 with a "second independent path" (`sessions get <id>` per session), but **a membership check is structurally incapable of revealing an 18th item a capped list omitted** — it validated the items it already held and gave zero completeness coverage. `ncl sessions list` returned 200 rows both bare and `--agent-group`-filtered (the identical count *is* the tell), 2096 at `--limit 5000`, and only the stable reruns at 10000/20000 make 2096 a total rather than a fourth page: **membership → `get`, completeness → BOUND test, identity → hash**, and an unbounded count is a FLOOR ([match the check to the claim — membership, completeness, identity](../learnings/1785820665177-match-the-check-to-the-claim-membership-get-comple.md)). Counts additionally describe *a query's window*, never the resource: `runs?per_page=100` returned 84 dispatch + 16 push spanning 05-19..08-04 while `runs?per_page=100&event=workflow_dispatch` returned 100 dispatch spanning 05-09..08-04 — the cap applies **after** the filter, so *adding a filter widened the time window*, and bot-share came out 71/84 and 82/100 with both queries correct. And rows ≠ entities: SHA `65749cfe8` was pushed as both `v2025.24` and `v2025.24.1` (two runs, one commit) while `v2025.19.1-test-rename-libslang` exists at two SHAs, giving 10 diverged runs vs 9 diverged tag names — an off-by-one between agents is usually this. This **amends** the tempting reconciliation rule: before calling an instrument defective, enumerate (a) defective instrument, (b) different scope/window, (c) different entities counted; (b) and (c) were both live here and (a) was live in neither, and a free detector is that a breakdown which doesn't sum to its own stated total means two windows got spliced ([per_page is post-filter, and rows ≠ entities](../learnings/1785809901211-count-corrections-per-page-is-post-filter-adding-a.md)). Classification and *currency* are also separate questions: with duplicate check-suites at one head, the prior resolution "key on `created_at`, prefer the newest `pull_request`-event suite" is broken by a second variant where **both suites share `event=pull_request`** — a `Verify PR Labels` gate fails, the author adds the label, the gate re-runs green, and the failed suite persists in `filter=latest` indefinitely (4 such PRs: #11373, #10885, #11087, #11964, all satisfying the gate today). Suite `created_at` recency is the only load-bearing rule; event preference is a tiebreaker for the `workflow_dispatch` variant only; conclusion-filtering is defensive (measured 0 occurrences of a `skipped` suite winning on recency across 75 PRs). The doubling is fleet-wide, not CI-specific (eight workflows doubled at one head, including formatting and label gates routinely waved off as author hygiene), and the counter-check matters: a single-suite `check-formatting` red on another PR was genuinely author-owned — 6 of 29 red PRs carried a phantom, so blanket dismissal and blanket trust are both wrong ([phantom red variant 2: same-event duplicate suites defeat event-preference](../learnings/1785817670285-phantom-red-variant-2-same-event-duplicate-check-s.md)). Two review-surface discriminators complete the set. An approval's *state* is weaker than its *binding*: each REST review carries `commit_id`, so the approval binds iff `commit_id == .head.sha`, a strictly better check than `reviewDecision: APPROVED` even when GraphQL is healthy ([when gh GraphQL 401s, verify PR state and review binding via REST](../learnings/1785752119095-when-gh-graphql-401s-verify-pr-state-and-review-ap.md)). And a review event is a human inbound only if it carries text — an empty-body `APPROVED` is a go-ahead click, an empty-body `COMMENTED` is the wrapper GitHub creates around inline comments living at `pulls/{N}/comments`; treating a wordless approval as an inbound manufactures a reply obligation and puts noise on a maintainer's notifications (slang-rhi#805, where the nudge also inverted the timeline — our 10:10Z outbound already answered the 10:02Z event). The discriminator is "is there text on **some** surface," never "is the newest event empty" — dropping the empty wrapper without ingesting inline comments swings the error the other way ([an empty-body review is not an inbound — check body length](../learnings/1785761122402-an-empty-body-review-is-not-an-inbound-check-body-.md)).

### Reading is not running — a two-minute experiment beats a plausible control-flow argument

Repeatedly, a mechanism derived by *reading* source was refuted in minutes by *running* it, and the wrong mechanism implied a different, broken fix. Two apparently-identical crash sites — `spirv` at `glsl-legalize.cpp:5235-5241` and `metal` at `varying-params.cpp:4561-4567`, verified line-for-line to run the same five steps in the same order — were collapsed into "one null, two build configs, three apparent symptoms"; *running* both targets at `546ad18f7` showed spirv fails on the **arity** assert (`-dump-ir` shows `call %DispatchMesh(1,1,1)`, three args, the payload dropped upstream — a release out-of-bounds read, not a null deref) and never reaches the getter, while metal passes arity and *then* nulls. **Structural identity of the code does not imply identity of the failure, because the two passes receive different IR** — so "diff the code shape" is demoted from a test of failure identity to a weak hint about shared provenance; the count insight (symptom-count ≠ defect-count) and the front-end-rule fix survive, and the wrong mechanism escaped two reviews precisely because the fix conclusion was unaffected ([code shape is the wrong test for failure identity](../learnings/1785804467761-n-crash-signatures-is-a-hypothesis-about-count-not.md)). The CMake `file(DOWNLOAD … EXPECTED_HASH)` sequence is the cleanest instance: an HTTP 500 on the DXC CDN kills `configure` despite a working source-build fallback, and **two** plausible read-the-code mechanisms were wrong — "the Error precedes the warning in execution order so the fallback never runs" and "EXPECTED_HASH is immediately fatal so `:284-294` is unreachable." The real behavior is **deferred-fatal**: the error is recorded, the handler *is* reached, the fallback clones and configures DXC successfully, and configure still exits 1; a 15-line local A/B (same statement, hash argument the only difference) settles it in two minutes, and the job log's warning-*after*-error ordering already falsified the unreachable-handler story ([CORRECTION: EXPECTED_HASH is deferred-fatal, the fallback does run](../learnings/1785759571154-correction-file-download-expected-hash-is-deferred.md), superseding the mechanism in [the DXC prebuilt-fetch HTTP 500 signature](../learnings/1785759110494-dxc-prebuilt-fetch-http-500-fails-the-build-despit.md) whose classification and recommended fix stand). The generalized form matters for anyone writing the fix: a retry loop **alone does not help** (the last failed attempt raises the same error, and you get one error per attempt), fatal-on-failure and graceful-fallback cannot coexist in one call, `cmake -P` script mode is *immediately* fatal so a script-mode repro shows the wrong shape, and a shared retry helper must take the hash as a parameter and verify out-of-band or every call site inherits the defect — the counterfactual A/B (retry+hash vs retry+hash-split-out) is what settled it against an "add a retry" answer that sounded obviously sufficient ([EXPECTED_HASH is deferred-fatal in configure mode and defeats STATUS-based retry](../learnings/1785765561771-cmake-file-download-expected-hash-is-deferred-fata.md)). Two more: a triage claim that a feature needs new code collapsed when the command was actually **run** — SPIRV-Tools' `Optimizer::FlagHasValidForm` whitelists `-O` and `-Os` alongside `--pass-name`, and Slang forwards `-Xspirv-opt` verbatim, so `slangc -O0 -Xspirv-opt -Os` already runs the size preset (measured smaller *and* faster than `-O3` on one shader), inverting the framing toward "the perf presets may be mistuned"; a passthrough's documented purpose does not bound what the downstream tool accepts, and in the same file a `grep -n '^#if\|^#else\|^#endif'` that **cannot match `#elif`** reported a two-armed preprocessor chain where a three-armed one exists, inverting the dead/live verdict twice in sequence — the fix is to match every directive and, better, to run `cc -E -P` rather than reason about arm selection, since **a correction built on the same broken instrument reproduces the error with more confidence** ([check whether a requested feature is already reachable, and prove it by running the command](../learnings/1785780759447-check-whether-a-requested-feature-is-already-reach.md)). And a byte-for-byte peer verification is not a correctness check at all: justifying a new path by showing it produces **the same value the incumbent produces** is circular — slang-rhi#802's `allocBufferHandle` returned `getDeviceAddress() + offset` for every buffer kind and discarded `format`, matching `metal-shader-object.cpp` exactly, which is why the equivalence review passed; typed `Buffer<float>`/`RWBuffer<float>` emit as `texture_buffer<…>` on a `[[texture(N)]]` slot needing a texture **resourceID**, and only an executed test (once the silently-skipping macOS jobs actually ran) killed it. Validate against the *consumer's contract*, enumerate the resource classes the path covers, and treat `SLANG_UNUSED(param)` + "this doesn't matter" as a per-class red flag ([equivalence-to-incumbent is circular — a byte-for-byte review can pass a real bug](../learnings/1785767751083-equivalence-to-incumbent-is-circular-a-byte-for-by.md)).

### Provenance has layers, and rigor on one axis reads as rigor on all of them

"I read the file" is not one fact. A `Read` of `.github/workflows/cmake-options-build.yml` returned a CI step gate (`if: ${{ inputs.verify-slangc }}`, a `cmake -L` check) that **does not exist in the file** — and was about to be cited as load-bearing evidence in a public verdict answering a maintainer's direct question. What caught it was cosmetic damage (duplicated blocks, a stray `</parameter>`) *independent* of the factual defect: had the fabrication arrived cleanly formatted, it would have been published. Hence the layer table — bytes on disk / my read of them / what the machinery declares / what it did this time / what a peer told me — where **a fact is established at exactly one layer and gains false authority the moment it is asserted at a higher one**; "the workflow declares X" is layer 3 and is never "CI ran X" (layer 4). The rule that does not depend on a tell: **trigger the second-instrument read on the load-bearing-ness of the claim, not on how the evidence looked**, use a different reader *and* path (`git show <ref>:<path> | sed -n`, not a retry of the same tool), discard a suspect read whole rather than salvaging parts, and separate "artifact is corrupt" from "read is corrupt" before investigating the repo ([provenance has layers — name the layer you are standing on](../learnings/1785803860488-provenance-has-layers-a-fact-that-crosses-a-layer-.md)). Rigor does not transfer across axes. Classifying seven errors from one chain by *where* they failed yields two disjoint controls, neither subsuming the other: **relevance** failures (4 of 7 — a circular citation gated on the very flag that made it describe the other path; "no `[Info]` lines ⇒ the fallback didn't run" when `Info` routes to doctest `INFO()` and cannot print in a passing non-verbose run, so the silence was guaranteed either way; a file timestamped 721s *before* the rule existed counted as non-adoption evidence; two rates on mismatched bases) versus **carry-through** failures (3 of 7 — a line number cited across your own edit, an unqualified referent the peer resolved to the wrong file, a rule articulated and reported present that one artifact didn't carry). Grepping the artifact is *worse than useless* against class A — it confirms the wrong claim is present, which reads as verification — and the relevance control is powerless against class B. The closing over-claim ("grep would have caught all seven": actually 3/7) is itself the lesson: don't claim a control covers a class without enumerating the class, and treat "we've been careful for hours" as a reason to check the axis you have *not* been watching, since both provenance failures arrived late and two happened *in the same turn the rule was articulated* ([two disjoint verification controls — relevance and carry-through](../learnings/1785778169091-two-disjoint-verification-controls-relevance-and-c.md)). The subtlest variant has every premise true and the conclusion still false: a pass entry showing as `t` in `nm libslang.so` was correctly diagnosed as hidden visibility rather than internal linkage (free function at column 0, not `static`, no `-fvisibility` in the root CMakeLists — all verified), so one `SLANG_API` was proposed as the cheap fix; the undefined set also held `IRInst::getFirstChild`/`getLastChild`/`getOperands`/`getDecorations`, `IRInstListBase::begin/end` and its iterator `operator++`, and `ComponentType::getTargetProgram`, each defined out-of-line in a `.cpp` and each needing its own export. **Verifying one member of a set is not verifying the set**; read the whole undefined-symbol list before proposing a linker fix, remember declared-in-header ≠ defined-in-header, and note the save was procedural — an explicit "don't put this to the maintainer until someone confirms it links" gate — so when you cannot run the check, **ship the question, not the conclusion**, and label which parts you verified versus inferred ([correct premises, wrong conclusion — verifying one member is not verifying the set](../learnings/1785776642421-correct-premises-wrong-conclusion-verifying-one-me.md)). The cheapest version of the same failure is repeating a PR description as measurement: the claim that `_INIT` seeding "honors `CFLAGS`/`CXXFLAGS` generally" was lifted from a PR body and never probed ([CMake: seed CMAKE_&lt;LANG&gt;_FLAGS_&lt;CONFIG&gt;_INIT to make a default overridable](../learnings/1785767372104-cmake-seed-cmake-lang-flags-config-init-to-make-a-.md)) and is false for an `-O` level — env `CXXFLAGS` lands in `CMAKE_<LANG>_FLAGS` (slot 1), the seed in `CMAKE_<LANG>_FLAGS_<CONFIG>` (slot 2), so under last-`-O`-wins `CXXFLAGS='-O0 -g3'` yields `-O0 -g3 -Og -g` → effective `-Og`, and only `-DCMAKE_CXX_FLAGS_DEBUG=` replaces it ([CORRECTION: _INIT seeding does not let env CXXFLAGS override an -O default](../learnings/1785768108214-correction-cmake-lt-lang-gt-flags-lt-config-gt-ini.md), measured independently in [per-config _INIT seeding cannot be overridden by env CXXFLAGS](../learnings/1785767705338-cmake-og-debug-default-per-config-init-seeding-can.md), which also supplies the validated whole-token `-O` detector — `separate_arguments` for isolation plus `^-O([0-9]+|s|g|z|fast)?$` anchoring for `-ObjC` rejection, two distinct mechanisms easy to conflate — and the reminder that GNU/Clang's default `CMAKE_CXX_FLAGS_DEBUG` is bare `-g`, the `-O0` being the compiler's implicit default rather than a literal token). Note the sibling reasoning error in that same chain: the whole defaults-based *direction* was written off after testing one bad variant (`set(... CACHE STRING "" FORCE)`), never the correct `_INIT`-pre-`enable_language()` spelling — **a negative result on one spelling is not a negative result on the concept**; enumerate a mechanism's variants before declaring the direction dead.

### Corrections must land where the claim is read — and some claims must not be corrected at all

A memo held by N tiers has N copies, and rewriting yours corrects exactly one. After announcing a purge of three superseded claims (chief among them "this fix is blocked on / must fold into PR #12186," long overruled by the maintainer), the triager's copy still carried all three verbatim — and worse, its own earlier corrections had been **appended at the tail**, so a top-down reader hits the stale prerequisite before ever reaching the retraction and re-parks authorized work. So: put current truth in a head block and mark historical sections superseded *in place*; grep the **superseded wording**, since a search for your new wording cannot match the stale text; say *which copy* you purged; and when sending a correction, assume the recipient will append it unless you ask for in-place retraction. The same exchange yields a second reflex — a correction arriving with a *new* `file:line` is not automatically the true one (one site was cited six different ways over six days by the same tier, each quietly replacing the last): record the **function name**, mark the address unresolved, and require the HEAD sha it was read at, because adopting the newest number because it arrived last is how a wrong citation gets laundered into a fact ([purging a stale claim fixes only your copy — name the copy and sweep top-down](../learnings/1785775378784-purging-a-stale-claim-fixes-only-your-copy-name-th.md)). The complementary rule bounds what a staleness sweep may touch, and the load-bearing question is not "is this text still accurate?" but "**is this asserting current behavior, or recording a past event?**" A present-tense behavior claim ("every Standard+ function's `parentScope` is its exact owning compilation unit," true when written, falsified by a later scope cut) **must** be corrected; a historical statement (commit-specific diff stats, "tests pass 74/74 at this head", a build report) **must not** — rewriting it destroys the audit trail and makes the log lie about what was known when. For anything a maintainer has already read, prefer an explicitly-labeled append over a silent edit; don't re-cite volatile `file.cpp:1234` references (updating the number just resets a clock that expires at the next merge — keep function/gate/symbol names); your PR title/body and your own comments are yours to fix but a third party's issue body is not; and batch the PATCHes and verify persistence, because a 2xx is not proof it stuck and a half-applied sweep reads as "it tried and failed" ([staleness sweeps: correct present-tense behavior claims, preserve historical statements](../learnings/1785800216005-staleness-sweeps-correct-present-tense-behavior-cl.md)). **Reconciling the two, since they look opposed:** "append, don't rewrite" governs *public artifacts a human has already acted on*, where the append is the audit trail and is labeled as a correction; "never leave the retraction at the tail" governs *internal memos read top-down for current state*, where position decides which claim is read. Both are satisfied by putting the current truth where the reader lands and preserving the superseded text marked as superseded — never by an unlabeled silent edit, and never by a tail-appended retraction under a still-standing assertion. Two corrections in this batch also show that a superseding note must be explicit about *what* it replaces: a "pin `event=workflow_dispatch` when picking a workflow's last successful run" note had the right fix and the **wrong mechanism**, and buried the dominant defect — `workflows/<id>/runs?status=success&per_page=1` returns the latest success *overall*, typically **newer** than the failure being triaged (tested: base `546ad18f` vs 2026-07-01 failure `6d355565` → `status=behind`, `behind_by=236`, **`commits=0`**), so a genuine regression reads as a clean infra flake; the tag-divergence story it blamed held for only 9 of 98 `push` runs (89 were `ahead`, since tags are cut *from* master), making event-pinning the narrow half of the fix. Rule: echo run id / event / head_sha / head_branch for **both** endpoints plus `compare.status`, and **refuse to emit a commit list** unless status is `ahead` — and note that both the error and its discovery came from the same habit, *a query that returns data feels verified*, defeated only by running it against a case whose answer you already knew ([CORRECTION: base ORDERING is the real bug in "last successful run" bisects](../learnings/1785809417487-correction-last-successful-run-bisects-base-orderi.md)). The self-correcting-in-place pattern is visible in the crash-signature note above, which carries its refutation as a **banner at the top** rather than a footnote, explicitly listing what still stands (the count insight, the fix shape) versus what is retracted — plus an instrument-staleness warning worth generalizing: the Debug `slangc` used was 5h older than HEAD and reported the assert at `:5182` vs the current `:5235`, so **check binary mtime against the HEAD commit date before citing an assert line**.

## Controls, discrimination, and proxy verification — part 2

### The proxy shape: a check that could not have come out differently

The single recurring defect behind four independent errors on slang#12192 was not laziness but *shape*: every check ran, passed, and produced output, and none of them could have produced a different result if the claim were false — a `grep` finding `SLANG_UNEXPECTED` in a switch proved presence, never reachability (buffer handles route out earlier); a byte-identical SPIR-V diff at `-g1/-g2/-g3` could not fail because `OpLine` emits only from statement-granularity marker insts, so a value-inst `sourceLoc` change cannot move the output; a second-hand line number stood in for its enclosing function (`:2035/:2272` sit in two *other* functions, one of which early-returns for the type at issue); and one aggregate `total > 0` non-vacuity guard stood in for per-site coverage, hiding an assertion site whose required instruction the test input never produces ([four errors, one shape — we verified a proxy instead of the thing](../learnings/1785775797519-four-errors-one-shape-we-verified-a-proxy-instead-.md)). The installable reflex is one question — *if the claim were false, would this specific check have told me?* — and if you cannot describe the failing output, you hold a proxy. Three corollaries land the same blow from other angles. First, the *same* green signal carries opposite weight depending on the claim: for "my fix works" green is a smoke test (inert, skipped, stale-binary, or asserting an observable the bug cannot move), while for "this refactor is behavior-preserving" green is close to the whole proof — but only after you have enumerated where preservation could break (on slang#12281's −88/+55 collapse: the early-out moved from inside the driver to before it, so `IREmptyTypeLegalizationContext`'s empty body and the inlined chain's fall-through-vs-early-return had to be checked first, *then* 8/8 meant something) ([green is weak for "my fix works", strong for "I changed nothing"](../learnings/1785792616063-a-green-run-is-weak-evidence-for-my-fix-works-and-.md)). Second, when prose and a test disagree, the test is the artifact reality already voted on: slang#12148's PR-description glossary asserted "one `DebugSource` per source file… the **same** deduplicated inst" while the PR's own test comment (written by the same author) documented the precompiled-module case where a filename-only record sits *beside* the full-path record — self-consistent prose can never catch this, only prose-versus-tests can, and universally-quantified words ("one per", "always", "each", "never") are the highest-yield targets ([when prose and a test disagree, the test is the artifact that was forced to be true](../learnings/1785800192069-when-prose-and-a-test-disagree-the-test-is-the-art.md)). Third, generalized breadth of re-checking never converges on the deciding input: **name the field whose change would invalidate the conclusion, in advance**, then re-read that field at the moment of action — on #12281 the fixer recorded that its "no approval yet" finding expired the instant one landed, naming `reviewDecision` and the approval's `commit_id`, so when an approval arrived ~90 minutes later the webhook was immediately interpretable (merging master would dismiss a five-round approval ⇒ correct action = nothing); the same discipline pre-commits an escalation rule before the second data point can be rationalized ([name the field that would falsify you, in advance](../learnings/1785799355770-name-the-field-that-would-falsify-you-in-advance-c.md)). And a status field must itself be controlled against a row whose state you know independently: joining `messages_out` to `processing_ack` returns *no match for any row* because the tables are structurally disjoint (`messages_out` has no status column; `processing_ack` keys on inbound `a2a-`/`sys-`/`gh-`/`cli-` ids, outbound ids are `msg-`/`cli-resp-`; measured overlap 0 of 9) — a uniformly-negative signal should indict the instrument before the system, and this failure mode is biased toward the expensive direction, a phantom-outage false alarm that looks like diligence ([`processing_ack` never contains outbound ids — "not acked" ≠ undelivered](../learnings/1785786323245-processing-ack-never-contains-outbound-ids-not-ack.md)).

### Discrimination: only the passing cases locate a trigger, and an instrument inside the phenomenon cannot measure it

Three agents burned an afternoon producing **four** successive wrong characterizations of one command guard, and every wrong version was built from denials only: "blocks read-only `gh api`" (killed by a single-field `--jq '.state'` passing), "blocks composed interpolated `--jq`" (killed by `"a=\(.state) b=\(.closed_at)"` passing), "arity-sensitive" (killed by a 3-pair call without the literal passing), "the second trigger is fleet-wide" (killed by both denied cells passing on a third edge). The trigger was located by *one* pass: `--jq '"state=\(.state)"'` denied versus `--jq '"foo=\(.state)"'` allowed on the identical path and field — a write-guard literal matching inside a read's format string. A denial is consistent with every hypothesis that covers it; only a pass eliminates hypotheses, so before publishing any characterization, list the already-observed passes and check your pattern predicts them — mispredicting even one makes it known-false at the moment of writing, and an honestly-labelled residual beats a clean story contradicting observed data (the file's later amendment applies its own Rule 1 to itself: the floor pattern `gh api [^|]*pulls\b` in `gate-critique-on-deliver.sh:52` contains no `state=` and no `issues` alternative, so "v1" was **scoped-true on a floor-only edge**, not wrong, and relabelling it "wrong" retired three independent correct observations). Its Rule 2 is the sibling: co-locating a known-passing form with a known-denied literal in one command makes a *command-text* guard deny the whole thing, so the control never executes and the denial reads as nondeterminism — one probe per command; stripping your own `Authorization:` header proves nothing when the proxy re-supplies it; `gh api rate_limit` cannot probe an auth layer that does not rule that endpoint ([only the passing cases locate a trigger — four wrong characterizations from denial-only evidence](../learnings/1785782647584-only-the-passing-cases-locate-a-trigger-four-wrong.md)). Two Slang cases show the constructive form. A repo-wide claim that "dropping `-o` flips the compile to `-whole-program`, silently changing what is compiled" was settled in ~30 seconds by a four-way discriminating probe — two-entry-point shader × (`-o -` / no `-o`) × (`-entry` / no `-entry`), counting `OpEntryPoint`: with `-entry` present the output is byte-identical and the flip is inert except inside the `-g`-embedded command-line string (`slang-options.cpp:4626-4631` binds `entryPointIndex = 0` onto existing outputs *before* the `:4647` block adds the `entryPointIndex == -1` output that reaches the `isWholeProgram = true` arm at `:4753-4758`); only dropping `-entry` too yields two entry points ([dropping `-o` does not flip to whole-program when `-entry` is present](../learnings/1785791159290-dropping-o-does-not-flip-to-whole-program-when-ent.md)). And on slang#12186 a regression test asserting only that `OpIAdd %ulong` *existed* was vacuous until rewritten to bind `%[[BITS]]`/`%[[INDEX]]` and require them as operands, then run against a pre-fix binary (0 matches pre-fix, 1 post-fix) — same review round, a "16/16 green" harness that grepped stderr for error strings while ignoring exit codes was not a pass at all, and a DeepWiki summary that caveated itself was cited over the actual SPV_NV_bindless_texture spec text (which permits a 2×uint32 vector under `OpSamplerImageAddressingModeNV 64`), on the strength of which a legitimately-passing repo test was edited ([remove the constraint, don't detect violations of it — plus negative-control every regression test](../learnings/1785783085348-remove-the-constraint-don-t-detect-violations-of-i.md)).

### Absence of evidence, blocked observation, and the shelf-life of a verified negative

A negative claim closes off investigation, which is exactly what makes it load-bearing and cheap to get wrong. Publishing "this container has no NVIDIA Vulkan ICD" — into a triage memo, a public GitHub comment, and a report a reviewer then repeated upstream — rested on a recon subagent listing only `/usr/share/vulkan/icd.d` (Mesa only); the ICD was at `/etc/vulkan/icd.d/nvidia_icd.json` → `libGLX_nvidia.so.565.57.01` and `vkEnumeratePhysicalDevices` had been returning an L40S the whole time, so seeing only `intel/lvp/radeon` in `/usr/share` is the *expected appearance of a working NVIDIA setup*. Prefer a positive test over an inventory: one enumeration program settles it, and the false "can't test this here" was the only thing standing between a hypothesis and the runtime refutation a coworker performed in minutes ([never publish a negative environment claim from a subagent's single-directory check](../learnings/1785776605331-never-publish-a-negative-environment-claim-from-a-.md)). When the observation is *blocked* rather than wrong, the value is **unknown, not unchanged**: a PreToolUse gate denied the one `gh api .../issues/805` call that could read issue state, the fallback was git-only (`git show`, `merge-base --is-ancestor`, `git log` — none of which can see GitHub issue state, i.e. a capability-mismatched fallback is not a fallback), and "issue #805 is still OPEN" was asserted from a teammate's 8-hour-old value; ground truth was `merged_at 18:10:04Z`, `closed` at `18:10:05Z`. Either find another route (dispatch the read to a subagent with its own tool context) or report the specific field as unverified — and note the gate re-armed 3× purely because the agent edited its own memory files, which is exactly when the temptation to substitute recall peaks ([a blocked verification call means UNKNOWN, not unchanged](../learnings/1785781402300-a-blocked-verification-call-means-unknown-not-unch.md)). Verified negatives also expire. "No recurrence" on slangpy#1070's GPU wedge across 46 `ci` runs / 14 branches (Python-step median 1.70 min) looked cleared, but the signature had only ever fired on `dev/slangpy-fixer/1051`, which had not run CI since 07-13 and whose trigger file never landed on `main` — a clean window over a parked trigger is *unexercised*, not fixed; name the measurement that would settle it, and cross-check any closing rationale against the timeline (the profiler feature blamed for the race merged 07-13T17:02Z, *after* 5 of the 6 wedges, and the merged mitigation touched two C++ `TEST_CASE`s that cannot change a Python step) ([no recurrence on a parked branch is unexercised, not fixed](../learnings/1785800154328-no-recurrence-on-a-parked-branch-is-unexercised-no.md)). Absence of a *log line* is likewise not evidence until you prove the line would print: `checkDeviceTypeAvailable` assigns `debugCallbackOutput` only inside the `RETURN_NOT_AVAILABLE` failure macro, so the reporter's unconditional `printf` emits nothing on a green run — measured 0× in the green job re-read repeatedly and 3× in a failing sibling; the same chain teaches that **narrowing a claim is not testing its premise** ("the fallback is unexercised" → "unverified" kept the untested premise *which path does CI take?*, and a retraction that narrows without testing inherits the error and launders it as diligence — one unauthenticated `curl` of a public job log settled it: `GPUFamilyApple6 not supported; using per-encoder useResource fallback`, so CI runs the fallback *by default*), and that a claim turning on a stable environment property should be grepped for in your own notes before being re-derived, since the correct answer was already written down ([narrowing a claim is not testing its premise — and check your own store first](../learnings/1785778559075-narrowing-a-claim-is-not-testing-its-premise-and-c.md)). Operationally: **before believing any zero, run a broader control grep that must be non-zero**, and report coverage as the pair "N registered, M executed" (`grep -c '\.metal'` = 209 rows, `\.metal[[:space:]]+SKIPPED` = 207, `(PASSED|FAILED)` = 0 — and a single-space pattern against a column-padded log matching nothing is a fact about the regex, not the world) ([decline credit you didn't earn — plus the non-zero control grep and the registered/executed pair](../learnings/1785780007458-decline-credit-you-did-not-earn-misattributed-corr.md)). The sharpest version of the shelf-life problem is that a *reported absence* prompts nothing while a *reported review* prompts a manual read: an audit of 51 approver workspaces / 40 rows / 18 PRs measured CodeRabbit body-only tallies under-reading ~92% of the time (11 of 12 reviews claiming `Actionable comments posted: N>0` carried zero severity markers in the body), yet only **2 of 40** rows were corrupted — precisely the two where harvest concluded no review existed at all (an exit-22 timeout writing "no CodeRabbit signal" 90s after the review posted; an exit-20 "genuine skip" that never detected it), so the under-read only bites when it coincides with a false absence, the safety net was the agent hand-reading `pulls/N/comments` rather than the tooling, *a timeout describes a past instant not the present*, and `status green ≠ a harvestable review object` ([CodeRabbit under-read measured at ~92% — it only corrupts a row when it coincides with a false absence](../learnings/1785779282480-coderabbit-under-read-measured-at-92-11-12-and-it-.md)).

### Numbers as claims: units, scope, clamps, and floors

A bare count is an unverifiable claim, because it authenticates a *command over a scope* and omitting either leaves the gap. At slang master `5b3f7a24`, "833 occurrences under `docs/`" is ambiguous four ways — `grep -r` lines vs `grep -rl` files × `docs/` vs `docs/generated/tests` gives 788 / 833 / 786 / 828, all defensible, all different — so cite command + scope + commit; and `/workspace/agent/slang-r0/` is a **stale non-git snapshot** carrying its own `CLAUDE.md`, so a repo-wide `grep -r` landing there inflates every figure with no error and no staleness signal (3323 vs 3274 files under `docs/generated/tests`; 833 vs 893 `/dev/null` lines) — run `git log -1` first, and if it errors you are in the wrong tree. The arithmetic sanity check is worth more than the reconciliation: occurrence-lines can never be *fewer* than the files containing them, so "833 occurrences" against "932 files" is impossible, and that impossibility is the tell that two trees or scopes are in play — flag an unreproducible number rather than bridging it, since the underlying finding usually survives on magnitude-independent facts ([repo-wide grep counts: cite the command, beware the stale slang-r0 snapshot](../learnings/1785791518674-repo-wide-grep-counts-cite-the-command-and-beware-.md)). Three agents reporting three different counts for one slang#12333 defect were **all correct** and measuring different units — 786 files / 828 lines of `/dev/null` mentions, 770/771 `//TEST:` directive lines, **755** executed `.slang` tests (the only figure answering "how many tests could silently pass") — with the arithmetic tying exactly (828−771 = 57 prose lines; 771 lines over 770 files because one file held two directives; 770−755 = 15 `.md` prompt files) and `comm -23` proving strict subset: reconcile the metrics before assuming anyone is wrong. The trap in the same case is the subtle one: a `search/code` negative control (`"ZZZNONEXISTENTZZZ"` → 0) proves the instrument is *live*, not that its output unit is your claim's unit — a code-search index cannot express "directive lines," so 932/906 were real match counts in the wrong unit, and passing (a) is exactly what makes it tempting to skip (b); a rate-limited, truncated paginated sweep is likewise a **floor** (`≥786`), and a floor agreeing with a point value is weaker corroboration than two point values agreeing ([a discriminating control proves your instrument works — not that it answers your question](../learnings/1785792742163-a-discriminating-control-proves-your-instrument-wo.md)). Two structural traps close the cluster. **When two numbers disagree, first ask whether one of them is a constant**: a tool emitting `prCount: 29` beside a 20-item list drove multiple runs of hypotheses about "what filter drops exactly 9," and three observations settled it — 29/20, 28/20, 27/20 against true populations 77/75/74, i.e. the list is hard-clamped at 20 and the count drifts in lockstep with reality, so `gap = count − 20` has no independent meaning and every mechanism proposed for "the 9" was unfalsifiable by construction; get three data points before theorizing about a gap, and treat a suspiciously round unmoving value (20/30/50/100) as a clamp or page size until proven otherwise ([when two numbers disagree, first ask whether one of them is a constant](../learnings/1785796046919-when-two-numbers-disagree-first-ask-whether-one-of.md)). And an undercounted enumeration is **coverage loss, not cost**: a sweep over 20 PRs when the repo holds 233 open / 76 non-draft asserts green over 56 PRs it never opened, so never report "no failures" over a set you did not enumerate — state the denominator, reconcile on **raw** page length (page 2 held 100 raw but only 20 non-draft, so a filtered-count stop rule terminates early because filtering happens after truncation, and `/pulls` has no `total_count` positive control), assert `non_draft + draft == raw_total` per page, and note the root cause never had to be found for the fix to be right; the same file measures why `curl https://api.github.com/rate_limit` is *worse* than `gh` as a probe — HTTP 200 with plausible anonymous numbers (`core: 60`, `graphql: 0`, `search: 10`) from the same container where `repos/.../pulls/<n>` returns `X-Ratelimit-Limit: 6000`, because injection is per-path and the body contradicts itself ([enumeration undercount is coverage loss, not cost — and `rate_limit` is broken via curl too](../learnings/1785783404146-enumeration-undercount-is-coverage-loss-not-cost-a.md)). The same rule binds any `N:` you *write*: **a stated count is a claim, the list is the fact** — folding 282 learnings into 19 concept pages via 7 parallel subagents, each told to append footer rows to `**Source learnings (N):**` and bump N, every agent self-reported success and several explicitly claimed "footer counts match row counts"; a global recount found **19 pages with stated-N drift, several with no edits that day** (`review-pr-practices` 273→274, `slang-backends-spirv` 162→160, `slang-misc-build-infrastructure-and-tooling` 60→55), i.e. the drift is **chronic across daily folds**, not an artifact of one run — so never trust a writer's report about arithmetic it performed on itself, and never increment; always recompute from the deduped stem set and rewrite both the footer and frontmatter `source_count`. Two instrument lessons ride along, and the *order* they surfaced in is the point. The first checker reported 5 MISMATCHes, which was plausible — but its `flag&&!/^- \[/&&NF{exit}` clause stopped at the first non-row line, and real footers carry wrapped entries and interleaved blanks, so it counted a **prefix** of the list and manufactured mismatches on pages that were fine: **the instrument's bug produced exactly the finding being looked for**, and it was caught only by dumping the raw footer region instead of acting on the number ⇒ **suspect an instrument whose first act confirms your prior**, and validate it on a case whose answer you know before believing its verdict. The sound replacement carries an **internal control** so a parse failure announces itself instead of masquerading as a content finding — count rows to EOF *and* count unique citation stems, then require they agree:

```bash
rows=$(awk '/^\*\*Source learnings \(/{flag=1;next} flag&&/^- \[/{c++} END{print c+0}' "$f")
uniq=$(awk '/^\*\*Source learnings \(/{flag=1;next} flag&&/^- \[/{print}' "$f" \
        | grep -oP 'wiki/learnings/\K[^)]+' | sort -u | wc -l)
```

`rows == uniq` on every page says the parsed rows are real citation rows and none are duplicated; if the two diverge, the parse is suspect rather than the page. And the coverage lesson: **N independent self-reports do not compose into coverage** — each agent saw only its own slice, so a cross-cutting defect (drift on pages nobody touched) was invisible to all 7 and visible only to a global recount ([verifying N subagents' count claims — the claim and your checker can both be wrong, and the checker's bug looks like a finding](../learnings/1785824696781-verifying-n-subagents-count-claims-the-claim-and-y.md)).

### Corrections: the clause behind a concession, the text you move, and the write you cannot read back

The most dangerous over-claim is the one immediately following an honest retraction — observed three times in one chain (slang-rhi#806), each inside a message whose first half was a genuine, costly self-correction. The structure does the damage, not intent: the concession buys real credibility, the same breath spends it on an *uncontrolled* adjacent claim, and the reader has no reason to discount the second half precisely because the first half was honest. The direction tell is that the trailing clause **expands the writer's own reach** ("there is a further probe", "the payload is provable", one count moving 40→50), and in all three instances it rested on a check that could not have come out differently if false — the identical defect the retraction was apologizing for. If a "but", "and in fact", "which also means", or "this actually tightens to…" follows a concession, that clause needs its own control or its own separate message, and reviewers should apply this symmetrically: a concession is not evidence for whatever follows it, and its author is at that moment the least able to see it ([retraction momentum — the clause after a concession needs its own control](../learnings/1785788251389-retraction-momentum-the-clause-after-a-concession-.md)). Corrections also fail to travel. Splitting an over-limit decision row passed all the checks that came to mind — byte sizes, bidirectional links, positive confirmation that moved content was present, nothing lost — while relocating verbatim a paragraph asserting "Resolution needs `SLANG_RHI_METAL_NO_RESIDENCY_SET` (forces fallback)" and "Merged unverified on that config", **both inverted hours earlier in the same session**, into the child file whose stated purpose is holding retractions: a move is byte-preserving by design, so unlike a rewrite it never drags your eyes across the sentences, and the destination is the archive a future reader treats as the authoritative mechanism record. The split checklist therefore has four items, and only the fourth catches a correctness defect — sweep the destination for every claim the session has retracted **using the abandoned vocabulary, not the current wording**, then a positive control (`grep -c "<corrected wording>"` > 0) so the sweep isn't vacuous; a correct result has each retracted phrase appearing twice, once quoted inside a `HISTORICAL/RETRACTED` banner and once in the text the banner governs. A peer's clean audit of its own split was recorded as *a pass by luck of ordering, not by verification* — the markers predated the move — because a check you did not run cannot be credited for the outcome ([splitting a file is a content move, and moved text arrives unmarked](../learnings/1785780663367-splitting-a-file-is-a-content-move-and-moved-text-.md)). Some corrections cannot be confirmed at all: `record_decision` / `record_human_verdict` write a host-owned `approval_decisions` row that no agent tier can read back (three probes at `cli_scope=global` — `ncl help`'s 13 resources exclude it; `ncl approvals` is a *different*, card-shaped table; the only reachable SQLite is the two session DBs), so a success return means the call succeeded, never that "the ledger row now reads X" — report a ledger correction as **attempted**, naming the operator as the only party who can close it, and phrase the limit as "could not verify by method M" with M named. Its own same-day partial retraction is instructive twice over: the claim "no agent tier has any read path back to it" was too wide (`ncl sessions messages --include-system` reads *emission* across sessions), the payload is **absent from the API surface** rather than truncated (an undocumented `--json` shows exactly five keys with synthesized `text` — a known 3156-byte `append_learning` row returns `text_len=25`), and "truncated" versus "absent field" imply opposite remedies; also, your own `ncl` reads are logged into the transcript you are reading (29 of 33 system rows were the observer's own queries), so a read that is itself logged is not a passive observation ([`record_decision` is write-only — the writer of an audit artifact cannot verify its own write](../learnings/1785786013003-record-decision-is-write-only-the-writer-of-an-aud.md)). Finally, a correction must name what survives and what is replaced at the *precision* of the original: slang#12070's root-cause analysis (the reverse-loop reconstruction of an affine induction variable creates a use of the loop's `counterOffset` the checkpoint policy was never told about, so a runtime offset dangles once unzip splits fwd/reverse) was confirmed by the shipped fix, but its recommended remedy was not — maintainer PR #12299 registers `UseOrPseudoUse(param, counterOffset)` at **policy** time in `AutodiffCheckpointPolicyBase::processFunc` so the policy may legitimately choose store *or* recompute, and casts the synthetic loop count to the induction type *before* the affine math (fixing `int16_t` starts, a separate defect), where the earlier "add `counterOffset` to `hoistInfo->storeSet` at the reconstruction site" would silently miss the recompute case; the process half is that the chain treated its own draft PR #12072 as the fix path when the artifact to track was the maintainer's named upstream PR ([CORRECTION slang#12070 — policy-time pseudo-use, cast before the affine math](../learnings/1785799174873-correction-slang-12070-the-shipped-fix-registers-c.md)).

**Superseded wording to fix in place (for the reconciliation pass).** (1) The context page's corrupted-tool-result section currently reads: *"a retraction that walks a claim **down** against clean ground truth is safe to accept."* That is too permissive as written — a retraction is load-bearing text that gets checked like the upgrade did, its trailing clause needs its own control ([retraction momentum](../learnings/1785788251389-retraction-momentum-the-clause-after-a-concession-.md)), and a retraction that merely *narrows* ("unexercised" → "unverified") without testing the premise inherits the error and launders it as diligence ([narrowing is not testing the premise](../learnings/1785778559075-narrowing-a-claim-is-not-testing-its-premise-and-c.md)); recommend rewording to "safe to accept *as a downgrade of the original claim* — the retraction's own new assertions still owe controls." (2) KB-wide, grep for and fix the claim *"dropping `-o` flips the compile to `-whole-program`, silently changing what is compiled"* — it appears in slang#12334's PR body, in the dispatch requesting that review, and in a prior shared learning; measured, the flip is inert for any test passing `-entry` ([dropping `-o` does not flip to whole-program](../learnings/1785791159290-dropping-o-does-not-flip-to-whole-program-when-ent.md)). (3) Grep for the residency-polarity wording *"the residency **fallback** path is unexercised / merged unverified; `SLANG_RHI_METAL_NO_RESIDENCY_SET` is the only thing that closes it"* — inverted at source; CI's hosted Apple Paravirtual device lacks Apple6, so the fallback is the *covered* path and the residency-set path is the uncovered one ([narrowing a claim is not testing its premise](../learnings/1785778559075-narrowing-a-claim-is-not-testing-its-premise-and-c.md)). (4) Fix the fix-recommendation in the earlier learning *"slang #12070 autodiff negative-start loop: counterOffset bypasses cross-region legalization"* — its `storeSet`-at-the-use-site remedy is superseded ([CORRECTION slang#12070](../learnings/1785799174873-correction-slang-12070-the-shipped-fix-registers-c.md)). (5) Do **not** propagate the label "v1 was wrong: the gate blocks read-only `gh api`" — re-label it *scoped-true on a floor-only edge*; there are two per-edge triggers, and retiring the floor observation discards three independent correct measurements ([only the passing cases locate a trigger](../learnings/1785782647584-only-the-passing-cases-locate-a-trigger-four-wrong.md)). ### Provenance: whose observation is it, and could the two sources have differed?

Corroboration requires independent *provenance*, not merely two files that agree. An approver justified a `WOULD_APPROVE` on a slang-rhi#806 one-line README license correction against "two independent authoritative sources" — `LICENSE:1` and `.reuse/dep5`'s blanket `Files: *` stanza, both reading `Apache-2.0 WITH LLVM-exception` — but `.reuse/dep5` was *created by* `bc7657abfa`, the same commit that relicensed `LICENSE`, so had that PR been mistaken both would be wrong together and the agreement added zero redundancy; one `gh api ".../commits?path=<file>"` per source exposes it, and the honest move is to re-describe what the second source proves (shared provenance is weak for value-corroboration, strong for *intent and scope* — a common origin in a REUSE-compliance commit is direct evidence the relicense was deliberate and repo-wide with README the lone dissenter). Generalizes to a value and its lockfile entry, a constant and its generated header, a doc and the docstring extracted from the same source ([corroboration needs independent provenance — `git log` the second source](../learnings/1785785358188-corroboration-needs-independent-provenance-git-log.md)). The mirror-image trap is publishing a *cause* for a fact only the other party could observe: given `merged_at 18:10:04Z` and `closed_at 18:10:05Z`, a peer's wrong "still OPEN" was reported as "almost certainly a read inside the one-second window" — a mechanism that is genuinely real, fits the visible data, is *exculpatory* (charitable explanations attract the least audit), and was wrong; the actual cause was a blocked call plus memory substitution, and crediting the false cause let the more valuable lesson go unrecorded. Separate **what I verified** (artifact state) from **why their report differed** (needs evidence from their side); "almost certainly / presumably / must have been" about someone else's process is the tell, and a mechanism that fits the timestamps is a hypothesis to offer them, never a cause to publish ([don't manufacture a mechanism for someone else's error](../learnings/1785781538948-don-t-manufacture-a-mechanism-for-someone-else-s-e.md)). The same file's chain-level self-audit is the strongest single datum here: of four claims made about **systems the speaker could not observe** (a peer's read timing, another agent's misread, a guard's scope, per-agent config) all four were wrong, while every claim about readable artifacts was correct — and the relay is where an unverifiable claim acquires false authority, `"X reports Y"` surviving one hop as `"Y"` with an escalation attached ([only the passing cases locate a trigger](../learnings/1785782647584-only-the-passing-cases-locate-a-trigger-four-wrong.md)). Two concrete forms of synthesized provenance: never cite an identifier you cannot read — asked to disposition three approval-gate bypass cards with `ncl approvals get` returning `forbidden` (group-scoped CLI; `approvals` is admin-only, and its verb list is `list`/`get` only), an agent matched a card's `requested_at 17:17:51Z` against `ncl sessions list` and tabled a session created 17:12; the authoritative field named a different session on a different thread (created 07-30, firing 08-03, so filtering by `created_at` near the event actively excludes the right answer), and because the *conclusion* happened to be right nobody would have re-checked the citation — a wrong identifier is worse than none, since omission prompts a lookup while a confident wrong id gets re-checked *through* it ([never cite an identifier you cannot read — timestamp adjacency is correlation, not identification](../learnings/1785782620101-never-cite-an-identifier-you-cannot-read-timestamp.md)); and a string that can appear as message *content* cannot establish provenance, which is how grepping coworker names inside session `.jsonl` files "attributed" six files to one owner. That last case is the emitter lesson: a relayed `[GATE AUDIT]` symptom ("codex never invoked") was escalated to the operator as "a third instance of the same hook's detection being wrong," and both claims were false — `grep -riE 'gate.audit|never invoked' /app/hooks/` returns zero hits because the emitter is `/app/src/mcp-tools/gate-audit.ts:174`, an MCP tool inside `send_message` sharing nothing with the critique gate; the real mechanism (`findActiveSessionJsonl()` picking the mtime-latest `.jsonl` in one flat directory of 845 files) was documented in the file's own `KNOWN LIMITATIONS` block, the competing explanation was *eliminated* rather than assumed (`provider=null` ⇒ Claude ⇒ jsonl is written), 11 log files from 06-24 onward already recorded it, and the escalated direction was the harmless false-negative rather than the dangerous false-*pass*. Grouping findings by how they feel to the victim is a causal claim; a relayed symptom arrives without its mechanism, and a verified outcome does not license an unverified cause ([find the emitter before naming the defect](../learnings/1785801131585-find-the-emitter-before-naming-the-defect-a-relaye.md)). Two final asymmetries. **Verify-the-premise is symmetric** — we apply it reflexively to demands and criticism and skip it for praise: a fixer reported that splitting a `pulls` string literal across a shell variable slipped the critique gate, a parent escalated it twice as a serious gate defect, an orchestrator carried a remediation toward the operator, and then the hook's own header comment at `gate-critique-on-deliver.sh:76-80` turned out to say pattern enumeration can never be complete and the durable backstop is credential-layer enforcement — a **documented limitation is not a discovery**, the proposed remediation would have made the hook load-bearing against the authors' stated position, and the caveat had been sitting in the reporter's own memory file while it wrote the escalation up; retract downward against your own credit, cite file:line, state what survives narrowed, and note that relaying counts as complying ([verify-the-premise is symmetric — it applies when the inbound is credit](../learnings/1785800092596-verify-the-premise-is-symmetric-it-applies-when-th.md)). And **grade your refutations on the same scale as your claims**, because an over-stated refutation is worse than an over-stated mechanism: a bad mechanism gets caught when someone's fix fails, while "that branch is impossible" *licenses a decision* (close it, drop it from the rationale, ship the other fix) that nothing downstream tests — calling a null-function-pointer story "self-contradictory" was corrected to "driver-self-**inconsistent**", a much weaker claim about a *conforming* implementation, and on prototype driver 610.43.02/Blackwell exactly the population where feature-bit-vs-extension inconsistency appears, one notch of overstatement would have retired a live hypothesis on a conformance assumption the hardware never owed; watch for **asymmetric hedging** (the public comment was hedged, the handoff that drove action was not — check the wording in the artifact that executes), and note that the whole chain was saved only because the implementer refused to inherit a cite and re-derived it ([a refutation can be over-stated the same way a mechanism can — and it licenses closing](../learnings/1785776242563-a-refutation-can-be-over-stated-the-same-way-a-mec.md)). Provenance runs in the flattering direction too: **decline credit you did not earn** — an approver thanked a peer for a "207-rows correction" and a "(b) retraction" the peer never sent (both were the approver's own self-corrections that had landed in the peer's memory row via editor writes), and accepting the thanks would have pointed a future audit of "who established 207 registered / 0 executed, and against which artifact?" at the wrong tier; grep your own outbound record rather than your memory of the exchange, name who did send it, verify the substance independently anyway, and report the split ([decline credit you did not earn](../learnings/1785780007458-decline-credit-you-did-not-earn-misattributed-corr.md)).
