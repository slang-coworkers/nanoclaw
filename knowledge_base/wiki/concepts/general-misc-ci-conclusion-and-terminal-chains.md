# CI Conclusion Verification and Terminal-Chain Discipline

## TL;DR

- **Draft + HEAD sha is NOT "done."** Before any terminal rollup, verify the **CI run conclusion** on that HEAD: `gh api repos/<o>/<r>/actions/runs?head_sha=<sha>`, find the `ci` run, confirm `status=completed` + `conclusion=success`. "Local tests pass" and "draft at the right commit" say nothing about GPU CI lanes.
- **For a suspected hang, read STEP-level durations** (`.../runs/<id>/jobs`), not just the conclusion — a job killed at a 360-min timeout reads `cancelled`; an in-progress wedge shows no conclusion at all.
- **Associate a run to THIS PR+head before crediting its conclusion.** Confirm `displayTitle` names this PR and its head is this head. Cross-repo `repository_dispatch` runs (slang→slangpy) carry the *downstream* head_sha — match by PR-number in the title, not head_sha.
- **`cancelled` ≠ `failure` ≠ pass.** A `failure` commit-status can point to a `cancelled` run (superseded by head-churn) — neither a test failure nor a stale-old-head artifact. Clear it with ONE clean requeue allowed to finish.
- **Every CI claim carries its SHA, run id, AND attempt in its published text.** A PR-level statement without a SHA has no referent once the branch moves; a rerun can flip the set under a *stable* SHA, so the attempt number is part of the claim.
- **A green check can be structurally blind.** Ask "is the suite covering this change reachable from a `pull_request` event?", not "is CI green?". `grep -c pull_request` is not a trigger check — confirm the hit is inside the `on:` block; follow `workflow_call` up to the real caller.
- **Duplicate check-suites at one head defeat event-preference.** Suite `created_at` recency is the only load-bearing rule; event preference is a tiebreaker for the `workflow_dispatch` variant only. Both blanket dismissal and blanket trust of a phantom red are wrong.
- **Fact-check a "pre-existing fleet infra" escalation against sibling PRs** before relaying it up. If ~10 contemporaneous PRs pass the same matrix fast, it's the branch, not the fleet. The cheapest stale-base-vs-real-infra discriminator is **rebase-onto-main + re-run**.
- **Elapsed time is not a stall test.** Key on `status` **plus** job-level progress. Recent job starts ⇒ progressing; all non-completed jobs at the same hours-old `started_at` with zero recent completions ⇒ *then* suspect stranding.
- **"Last successful run" bisects break on base ORDERING, not tag divergence.** `workflows/<id>/runs?status=success&per_page=1` returns the latest success *overall* (often newer than the failure). Refuse to emit a commit list unless `compare.status` is `ahead`.
- **Verify a cited CI run in a release-report against live GitHub.** Same `run_id` + same completion timestamp is the tell for a stale re-report or a missed dispatch — a green report is not proof a run happened today.
- **An empty-body review is not a human inbound.** The discriminator is "is there text on **some** surface" — not "is the newest event empty." But dropping the empty wrapper without ingesting its inline comments swings the error the other way.
- ⚠️ **A misread that confirms your hypothesis gets the least scrutiny.** Before publishing a finding that confirms what you set out to test, ask: *if this were false, would my instrument look any different?* A query that returns data *feels* verified.
- One `gh api` returning `app_not_connected` / HTTP 401 is **not** a lost credential — retry (3x succeeded) before escalating a PAT restore.

## Verifying the CI conclusion before calling a chain terminal

Verifying `isDraft` + HEAD sha is NOT enough to call a coworker-PR chain "done/green/terminal" — you must also check the **CI run conclusion** on that HEAD. On slangpy #1051 / PR #1053 a chain was reported terminal/"green" after verifying draft state + the expected HEAD commit, but the `ci` run had FAILED on every commit (a 6h GPU test-lane hang), forcing a public correction. Before any terminal rollup, run `gh api repos/<owner>/<repo>/actions/runs?head_sha=<sha>` (or `?branch=<branch>`), find the `ci` run, and confirm `status=completed` + `conclusion=success`. For a hang specifically, check STEP-level durations (`.../runs/<id>/jobs`), not just the conclusion — a job cancelled at the 360-min timeout reads as `cancelled`, and an in-progress wedge shows no conclusion at all. "Local tests pass" and "PR is draft at the right commit" say nothing about GPU CI lanes. This extends the "trust-but-verify a fixer's PR-state claims against live GitHub" discipline to the CI conclusion, not just draft/ready/merge state ([verify CI conclusion, not just draft+HEAD, before calling a PR chain terminal](../learnings/1784307063626-verify-ci-conclusion-not-just-draft-head-before-ca.md)).

The same claim-precision discipline applies whether *you* are calling a chain done or *relaying a coworker's* "all green." Before saying a check is "green/cleared" or "flake/stale," verify each run's **association** — its PR number (`displayTitle`) AND head SHA — not just its conclusion. On slang #12202 (twice) two distinct over-claims shared one root: "11319 passed / 0 failed = infra flake" was read from an *earlier/different attempt* than the one red on the current head, and "requeue cleared it" cited two `success` slangpy `repository_dispatch` runs that were actually for *other PRs* (#12190 / #12206). Also distinguish red *causes* on a rollup: a `failure` commit-status can point to a run that was **`cancelled`** (superseded by head-churn), NOT a test failure — a cancelled run is this head's own run killed, neither a pass nor a stale-old-head artifact; clear it with ONE clean requeue allowed to run to completion. Rule: pull the specific run the failing status/check points to (`gh api .../commits/<sha>/statuses` or `/check-runs`, follow `target_url`), confirm its `displayTitle` names THIS PR and its head is THIS head, and read the actual `conclusion` (`success` / `cancelled` / `failure`). Cross-repo `repository_dispatch` runs (slang → slangpy) carry the *downstream* repo's head_sha, so match by PR-number in the title, not head_sha. For the orchestrator: a coworker's "all green / cleared" on a routed chain is a verdict — verify at claim-precision (the exact run, not the rollup summary) before relaying upward; two consecutive over-clean reports from one source warrant tightening ([verify a CI run belongs to THIS PR/head before crediting its conclusion](../learnings/1784873907730-verify-a-ci-run-belongs-to-this-pr-head-before-cre.md)).

## Every CI claim carries its SHA, run id, and attempt

A CI disagreement is only a usable lead if both sides named what they measured, which is why **a "matching sha" bullet is not enough: every CI claim must carry the SHA in its published text.** Measured on shader-slang/slang #12354, two coworkers published contradictory CI findings on one PR — the babysitter counting **3** failing `test-slang` legs (linux-debug-gcc-x86_64, windows-debug-cl-x86_64-gpu, windows-release-cl-x86_64-gpu) at `0c7f96d0b` (15:36Z), triage counting **1** (windows-release-cl-x86_64-gpu) at `4bac3b2d2` (17:23Z), with two commits landed in between. Triage published *"the failure is windows-release-specific"* and framed it as correcting the bot: **true at `4bac3b2d2`, false at `0c7f96d0b`** — and *both parties wrote the phrase "at this same commit" while holding different HEADs*. `gh api repos/<o>/<r>/commits/<sha>/check-runs` is per-commit, so a PR-level statement without a SHA has no referent once the branch moves, and on a branch taking 7 commits in a day a leg census is stale in hours; a rerun can also change the set under a *stable* SHA, so the attempt number is part of the claim (`.../actions/runs/<id>/attempts/<n>/jobs`) — run `31052137029` flipped to `completed/cancelled` **8 minutes after** the triage comment posted.

Two sub-rules make this a provenance lesson rather than a formatting one. **Before "correcting" a peer's published claim, read the peer's artifact in full**: triage offered as its *decisive control* that `test-linux-release-gcc-x86_64` has both options ON, runs all three tests, and passes — a control the babysitter's comment **already contained** verbatim (*"those same three tests pass on the sibling leg … 100% of tests passed (7129/7129)"*), alongside a cause bullet explicitly labelled *"Hypothesis (not verified by execution)"*. Re-deriving a counterparty's own control and presenting it as a refutation puts a false implication — *they lacked the control* — into a maintainer-facing comment; correct the **claim**, never narrate a novelty you did not verify. And **a commit-boundary check can refute your own hypothesis, so run it before publishing**: triage's alternative cause ("the PR turns on a never-run IR validator on the same commit whose CI is red") was directionally *against* the data, since the commits enabling full-IR validation coincide with the failing set going 3 legs → 1 — one `check-runs` call per commit across the boundary would have surfaced that, and because the runs differ, runner variance is not excluded either, which is precisely why it should have been published as bounded rather than as a lead ([two agents citing the same commit while holding different HEADs](../learnings/1785984972691-two-agents-citing-the-same-commit-while-holding-di.md)). One unrelated operational note from the same sweep: a single `gh api` returning OneCLI `app_not_connected` / HTTP 401 is **not** evidence of a lost credential — three immediate retries succeeded; retry before escalating a PAT restore to the operator.

## When "green" or "red" is structurally wrong

⚠️ A one-line parser change merged with 10 green checks while breaking a test that lives in a directory **no `pull_request`-triggered workflow ever executes**. So don't ask "is CI green?", ask "is the suite covering this change reachable from a `pull_request` event?" Trace the runner's default test root, grep `.github/workflows/` for who passes a non-default root, read *those* `on:` blocks, and follow `workflow_call` up to the real caller since a called workflow's own triggers tell you nothing. Two sub-traps: `grep -c pull_request` on a workflow file is **not** a trigger check (a single hit was an env expression inside `jobs:` — confirm the hit's line falls inside the `on:` block), and don't oversell adjacent tooling as the net — a saturated signal (a staleness tracker reporting all 68 bundles already stale) cannot isolate a new break, and a documented attachment point that **does not exist** is intent, not wiring ([a green PR check can be structurally blind — verify the suite is reachable from `pull_request`](../learnings/1785771123651-a-green-pr-check-can-be-structurally-blind-verify-.md)).

The mirror failure is a **phantom red**: with duplicate check-suites at one head, the tempting rule "key on `created_at`, prefer the newest `pull_request`-event suite" breaks when **both suites share `event=pull_request`** — a `Verify PR Labels` gate fails, the author adds the label, the gate re-runs green, and the failed suite persists in `filter=latest` indefinitely (4 such PRs: #11373, #10885, #11087, #11964, all satisfying the gate today). Suite `created_at` recency is the only load-bearing rule; event preference is a tiebreaker for the `workflow_dispatch` variant only; conclusion-filtering is defensive (0 occurrences of a `skipped` suite winning on recency across 75 PRs). The doubling is fleet-wide, not CI-specific (eight workflows doubled at one head, including formatting and label gates routinely waved off as author hygiene), and the counter-check matters: a single-suite `check-formatting` red on another PR was genuinely author-owned — 6 of 29 red PRs carried a phantom, so ✅ **blanket dismissal and blanket trust are both wrong** ([phantom red variant 2: same-event duplicate check-suites defeat event-preference](../learnings/1785817670285-phantom-red-variant-2-same-event-duplicate-check-s.md)).

## Bisect and stall diagnostics — the instrument lies quietly

A "pin `event=workflow_dispatch` when picking a workflow's last successful run" note had the right fix and the **wrong mechanism**, and buried the dominant defect: `workflows/<id>/runs?status=success&per_page=1` returns the latest success *overall*, typically **newer** than the failure being triaged (tested: base `546ad18f` vs 2026-07-01 failure `6d355565` → `status=behind`, `behind_by=236`, **`commits=0`**), so a genuine regression reads as a clean infra flake. The tag-divergence story it blamed held for only 9 of 98 `push` runs (89 were `ahead`, since tags are cut *from* master). Rule: echo run id / event / head_sha / head_branch for **both** endpoints plus `compare.status`, and **refuse to emit a commit list** unless status is `ahead` ([base ORDERING is the real bug in "last successful run" bisects](../learnings/1785809417487-correction-last-successful-run-bisects-base-orderi.md)).

The stall analogue: a field whose name implies a state is not a test for it, and elapsed time is the commonest such field. Investigating why slang's CI priority-yield aging gate never opened turned up a blocking `ci.yml` run `in_progress` for **12.8 hours**, which looked stranded — a materially different report ("structurally hung, escalate a human") from the true one ("busy repo, may expire unrerun"). Job-level state said healthy: **26 `completed`, 9 `in_progress`, all nine started within the preceding ~40 minutes**; a matrix run with slow GPU/sanitizer legs takes that long. `started_at` and any age derived from it tell you when work *began*, not whether it is *proceeding* (companion to the trap that `started_at` is populated on jobs that never started). To decide stalled-vs-working, key on `status` **plus** job-level progress: `gh api repos/<o>/<r>/actions/runs/<id>/jobs?per_page=100 --jq '[.jobs[]|{status}]|group_by(.status)|map({(.[0].status):length})'`, then list non-completed jobs with their `started_at` — recent starts ⇒ progressing; all non-completed jobs at the same hours-old `started_at` with zero recent completions ⇒ *then* suspect stranding. (Resolve a run id from `run_number` via the workflow's runs list; an id guessed as adjacent to another 404s.) ([elapsed time is not a stall test — key on status plus job-level progress](../learnings/1786080026178-elapsed-time-is-not-a-stall-test-and-a-misread-tha.md)).

⚠️ Both defects share a meta-trap: the misread **pointed the same way as the hypothesis under test**. "Does this gate ever open?" would have been *confirmed* by a stranded run; a regression that reads as an infra flake confirms "it's just infra." And in the SHA-disagreement case above, both the error and its discovery came from the same habit — *a query that returns data feels verified*, defeated only by running it against a case whose answer you already knew. Before publishing a finding that confirms what you set out to test, ask: *if this were false, would my instrument look any different?*

## Fact-checking a "pre-existing fleet infra" CI escalation

When a fixer escalates a CI failure as "pre-existing fleet infrastructure issue, not my code" (often proposing to wait for some infra branch/fix), VERIFY before relaying it up or escalating to the operator — the framing is frequently wrong and the check is cheap. On slangpy PR #1053 the fixer blamed a 6h GPU-test-lane hang on a fleet-wide "CUDA-OOM cascade from `pytest --maxprocesses=4`, needs the unmerged `ci/cap-gpu-test-workers` branch," but a fact-check disproved it: ~11 contemporaneous open PRs ran the identical 12-job matrix on the same `main` / `--maxprocesses=4` and passed in ~12–17 min (not fleet-wide); the proposed cap branch was behind-main-19 / ahead-1 with NO open PR (a dead end, not a plan); the PR branch was 19 commits behind main (stale-base was the leading hypothesis); and the macOS-aarch64 (Metal, no CUDA) lane was among those hanging (the CUDA-OOM story didn't fit). How to fact-check: pull ~10 recent open PRs, get each HEAD sha, list its `ci` jobs and per-job durations — if siblings pass the same matrix fast, it's the branch, not the fleet; verify any "waiting on infra branch X" claim (`compare/main...X` + `pulls?head=owner:X` — a stale/PR-less branch is not a plan); and the **cheapest discriminator for stale-base-vs-real-infra is rebase-onto-main + re-run** — if it still fails at 0-behind, stale-base is ruled out and escalation is justified (on #1053 it DID still hang post-rebase → genuinely isolated to the branch's test file wedging the GPU suite, legitimately escalated to the maintainer with runner access) ([fact-check a fixer's "pre-existing fleet infra" CI escalation against sibling PRs before escalating](../learnings/1784307076980-fact-check-a-fixer-s-pre-existing-fleet-infra-ci-e.md)).

## Verifying a cited CI run in a release-report notification

The verify-against-live-GitHub discipline also covers a *cited* CI run in a release-report notification: verify it before trusting or forwarding, with one cheap `gh api "repos/<o>/<r>/actions/workflows/<id>/runs?per_page=3"` call. On 2026-07-20 a daily release-report re-presented the previous day's run as fresh — byte-identical `run_id` + `head_sha` + completion timestamp as the prior report — because the report path fed the latest `run_id` with no `latest_run_id == last_reported_run_id` guard, so when that day's scheduled dispatch silently failed to fire, it re-emitted the already-reported green. A genuine new run has a distinct `run_id` and a fresh completion timestamp, so **same run_id + same completion time is the tell for a stale re-report or a missed dispatch** — a green report is not proof a run happened today ([verify a cited CI run against live GitHub before trusting a release-report notification](../learnings/1784856735494-verify-cited-ci-run-against-live-github-before-tru.md)).

## Closing a chain: an empty-body review is not a human inbound

A review event is a human inbound only if it carries text. An empty-body `APPROVED` is a go-ahead click; an empty-body `COMMENTED` is the wrapper GitHub creates around inline comments that live at `pulls/{N}/comments`. Treating a wordless approval as an inbound manufactures a reply obligation and puts noise on a maintainer's notifications (slang-rhi #805, where the nudge also inverted the timeline — our 10:10Z outbound already answered the 10:02Z event). The discriminator is "is there text on **some** surface," never "is the newest event empty" — and dropping the empty wrapper *without* ingesting the inline comments swings the error the other way ([an empty-body review is not an inbound — check body length](../learnings/1785761122402-an-empty-body-review-is-not-an-inbound-check-body-.md)).
