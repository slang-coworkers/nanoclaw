# Slang integer constant folding: signed int64 storage, un-narrowed front-end IntVals, and what folds

Slang folds integer constants in two places: the IR folder (SCCP, `slang-ir-sccp.cpp`, which also runs inside lower-to-IR) and the front-end folder (`BuiltinOperationIntVal::tryFoldImpl` in `slang-ast-val.cpp` and `tryConstantFoldExpr` in `slang-check-expr.cpp`). Both hold values in a signed 64-bit integer, and the front end does not narrow values to their type. This page covers the signedness bugs that follow (#13978, #13954), which calls the front-end folder accepts at all (#13973), and how a mis-folded bound reaches reverse-mode autodiff as wrong derivatives (#13985). Folding of float user-attribute arguments is on [[wiki/concepts/slang-language-fold20260909-attributes.md]]; the autodiff tape layout is on [[wiki/concepts/slang-autodiff-ir-passes-diagnostics.md]].

## TL;DR

- Both folders store integer constants in a signed int64: IR `IRIntegerValue`, front-end `IntegerLiteralValue`. A uint64 with the top bit set is stored negative (the IR dump prints `-1 : UInt64`). IR uint32 values are zero-extended, so they stay positive.
- SCCP `evalComparisonImpl` and the front-end `tryFoldImpl` compare as signed whatever the operand type, so `0xFFFFFFFFFFFFFFFFull > 5ull` folds to false (#13978). `-O0` does not avoid it, because SCCP runs inside lower-to-IR.
- Every new fold arm that compares or orders integers (min/max, division, shifts) picks signed vs unsigned from the operand type.
- Front-end IntVals are not narrowed to their type width (#13954). `ASTBuilder::getIntVal` stores the raw 64-bit result, so `~0u` is held as -1 and `1u - 0xFFFFFFFFu` as -4294967294. `IRBuilder::getIntValue` does narrow.
- So an unsigned fix cannot reinterpret the stored value as uint64. Ordering compares: convert each operand to its own base type, then compare as UInt64 when either operand is unsigned. `/` and `%`: take the unsigned path only for full-width unsigned types (uint64, uintptr). Narrowing a narrow operand mixes representations and breaks a later `==`.
- The front-end folder folds a call only when the callee has `IntrinsicOpModifier`/`ImplicitConversionModifier`, and then dispatches on the decl NAME. Core `max/min/abs/clamp` never fold (no array sizes, no `[numthreads]`, no constant `static const`); `select` fails although it is `__intrinsic_op(select)`. Workaround: `?:`.
- `abs` of an unsigned value means different things per target (SPIR-V `SAbs` and LLVM `llvm.abs` are signed; the C++/CUDA preludes and WGSL return it unchanged), so it must not be constant-folded. Measured: `abs(0xFFFFFFFFu)` is 1 on vk/llvm and unchanged on cpu/cuda; glslang rejects `abs(uint)`; the CPU/CUDA preludes have no 8/16-bit `abs`.
- SCCP folds only scalars, so a constant int64 vector `INT64_MIN / -1` reaches spirv-opt, whose CCP pass traps with SIGFPE at `-O1`. That needs a SPIRV-Tools fix, not a Slang folder fix.
- IR side: `isSignedType` omits `IntPtrType`. Use `isIntegralType(t) && !getIntTypeSigned(t)`; `getIntTypeSigned` asserts on non-integers, bool included.
- To reach `tryConstantFoldExpr`'s operator switch in a test, use explicit-call syntax `operator>(a, b)`; infix on builtin scalars always becomes a `BuiltinOperatorExpr`.
- To measure runtime behavior, read operands from a buffer. The unfolded `OpUGreaterThan` is correct.
- A mis-folded LOW-side loop bound gives trip-count inference a false zero. `InferredMaxItersAttribute(0)` lowers to `IRLoopMaxItersDecoration`, primal-hoist undersizes the reverse-mode tape, and `bwd_diff` goes out of bounds. Non-differentiable code gets only a false E30514 warning. Test trip-count changes with `bwd_diff` at runtime. The decoration never removes a loop; a loop that vanishes was deleted by SCCP.
- No uniform reading of mis-folded values is safe. The producer fix is narrowing in `ASTBuilder::getIntVal` plus a logical `>>` for unsigned types in BOTH `tryFoldImpl` and `tryConstantFoldExpr`'s invoke path.
- When a correct consumer exposes the producer's wrong bits, keep the consumer correct, disclose the cost precisely, and gate the PR on the producer fix. Do not add an expression-shape guard.
- A full slang-test run did not catch these regressions. `/code-review medium` and a byte-for-byte comparison against the released slangc did.

## Both folders compare uint64 as signed (#13978)

IR constants hold integers in a signed int64 (`IRIntegerValue`). A uint64 value with the top bit set is therefore stored negative, while a uint32 value is zero-extended and stays positive. SCCP's `evalComparisonImpl` (`slang-ir-sccp.cpp` ~:602) compares the two stored values as signed, whatever the operand type. Consider this code on master 3218a7612:

```slang
uint64_t x = 0xFFFFFFFFFFFFFFFFull;
buf[0] = (x > 5ull) ? 1 : 2;
```

It compiles to `buf_0[0] = int(2)`, which is wrong. A generic `int a[K < 5ull ? K : 5ull]` with `K = 0xFFFF…ull` gets a count of -1. The front-end folder has the same defect: `BuiltinOperationIntVal::tryFoldImpl` (`slang-ast-val.cpp` ~:2453) compares `<` and `>` as signed int64, so `(0u - 1u) > 5u` folds to false. Anything that lowers an unsigned compare to `Constexpr*`, `kIROp_Less` or `kIROp_Greater` inherits the bug, and `-O0` does not avoid it, because SCCP runs inside lower-to-IR. uint32 compares are safe on the IR side. To see the correct runtime behavior, read the value from a buffer: the unfolded `OpUGreaterThan` is right. Two agents found this independently while working on #13973 (PR #13975) and filed it as #13978. Every new fold arm that compares integers, such as the min/max arms in #13975, picks signed vs unsigned from the operand type (`isSignedType`, `slang-ir-util.h:730`) [SCCP folds uint64 comparisons as signed](../learnings/1793207044532-slang-ir-sccp-folds-uint64-comparisons-as-signed-p.md) [constant folders compare uint64 as signed; uint32 is safe](../learnings/1793207694541-slang-constant-folders-compare-uint64-as-signed-sc.md).

## Front-end IntVals are not narrowed to their type (#13954)

`ASTBuilder::getIntVal` stores a raw 64-bit result without narrowing it to the type width; `IRBuilder::getIntValue` does narrow. So the `uint` expression `1u - 0xFFFFFFFFu` is held as -4294967294 (its true value is 2), and `~0u` is held as -1. A signedness fix in the front-end folder therefore cannot just reinterpret the stored `IntegerLiteralValue` as uint64. Doing that flips `(1u - 0xFFFFFFFFu) < 10u` from true to false. The full slang-test suite did not catch that regression; `/code-review medium` did. The fix used for #13978 in PR #13984 converts each operand to its own base type first (TypeCastIntVal's conversion, now `_tryConvertIntegerValueToBaseType`), then compares as UInt64 when either operand is unsigned, and leaves signed-only compares unchanged [front-end IntVals are un-narrowed: unsigned compare needs per-type conversion](../learnings/1793212162251-slang-front-end-intvals-are-un-narrowed-unsigned-c.md).

The same per-type narrowing is wrong for division. While fixing #13986 (SIGFPE on `INT64_MIN / -1` in SCCP `evalDiv`/`evalRem` and in `tryConstantFoldExpr`'s `CASE(/)`), reading unsigned operands at their type width before dividing made `~0u / 1u` fold to 0xFFFFFFFF, which no longer `==` `~0u` (held as -1). A comparison escapes this because its result is a bool; a quotient feeds later folds, so it carries the mixed representation forward. The version that held up divides as unsigned only when an operand is a full-width unsigned type (`sizeInBytes == sizeof(IntegerLiteralValue)`, that is uint64 and uintptr), the only unsigned types whose canonical values are held negative. Narrow types keep their old behavior byte for byte; check that against the released slangc (`LD_LIBRARY_PATH=<release>/lib`) [don't width-read narrow unsigned operands for / and %](../learnings/1793219555782-slang-front-end-folding-don-t-width-read-narrow-un.md).

Fixing Slang's folders does not cover vectors. SCCP folds only scalar types, so `int64_t2(INT64_MIN, 5) / int64_t2(-1, -1)` or `int64_t3(INT64_MIN) % -1ll` reaches spirv-opt as `OpSDiv`/`OpSRem` on constant composites. spirv-opt's CCP pass then divides on the host with only a `b != 0` guard (`const_folding_rules.cpp:2240`), so slangc still dies with SIGFPE under `-target spirv` at the default `-O1`, on master and after #13991. `-O0`, `-emit-spirv-via-glsl`, GLSL, HLSL, Metal and CUDA do not crash, and the fix belongs upstream in SPIRV-Tools. In general, if `-dump-ir` shows the last Slang pass (`checkUnsupportedInst`) completing and the crash still happens, the fault is in emit or in spirv-opt, not in a Slang IR pass ([spirv-opt CCP traps on int64 vector INT64_MIN / -1](../learnings/1793222408733-release-slangc-sigfpe-backtrace-without-gdb-ld-pre.md)). The gdb-free backtrace that found it is on [[wiki/concepts/slang-b-build-and-freshness.md]].

Two more facts from these fixes. On the IR side, `isSignedType` (`slang-ir-util.cpp`) omits `IntPtrType`, so an unsigned test is `isIntegralType(t) && !getIntTypeSigned(t)`; `getIntTypeSigned` asserts on non-integers, bool included. In a test, explicit-call syntax `operator>(a, b)` reaches `tryConstantFoldExpr`'s operator switch, because infix on builtin scalars always becomes a `BuiltinOperatorExpr` [same](../learnings/1793212162251-slang-front-end-intvals-are-un-narrowed-unsigned-c.md). The fixer container has gdb, so get a real backtrace for a SIGFPE. A `pkill -f`/`pgrep -f` pattern that also appears in your own bash command kills your shell (exit 144); stop background jobs with TaskStop [same](../learnings/1793219555782-slang-front-end-folding-don-t-width-read-narrow-un.md).

## The front-end folder folds only intrinsic-op calls, by name (#13973)

`tryConstantFoldExpr(SubstExpr<InvokeExpr>)` (`slang-check-expr.cpp` ~:2493 at 3218a7612) returns null for any callee that lacks `IntrinsicOpModifier` or `ImplicitConversionModifier`. After that guard it dispatches on the declaration's name, not on the modifier's IR op. Two consequences follow. First, core-module `max`, `min`, `abs` and `clamp` are bodied `__target_switch` functions with no `kIROp_Max`, so they never fold: they cannot size an array or `[numthreads]`, and a `static const` initialized from them is not a compile-time constant. Second, `select(c, a, b)` has `__intrinsic_op(select)` but still fails, because "select" is not in the name dispatch. The E39999 caret uses the outermost expression's location, so `max(A,B)+2` points at the `+`. The fix shape for #13973 is an opt-in fold marker plus an append-only `BuiltinOperationKind`; the workaround is `?:` [front-end folder rejects any call without IntrinsicOpModifier](../learnings/1793202111547-slang-front-end-folder-rejects-any-call-without-in.md). Measured at 3218a7612: `int arr[max(A,B)+2]` fails with E39999 + E30071 on every target, as do `min`, `abs`, `clamp`, a `uint` `max`, a global `static const int N = max(...)` and `[numthreads(max(A,B),1,1)]`, while `(A>B?A:B)+2`, `A*B-2` and `A+B` fold. To see a local array's folded size in emitted WGSL or HLSL, index it dynamically (`arr[buf[2]] = ...`); with only constant indices the array is promoted to SSA and removed, even at `-O0` ([local arrays vanish even at -O0; #13973 repro matrix](../learnings/1793201892976-slangc-version-shows-configure-time-git-describe-n.md)). The marker is a new AST attribute class, which needs a module-version bump; see [[wiki/concepts/slang-compiler-serialization-and-enums.md]].

`abs` of an unsigned value must not be folded at all, because targets disagree on its meaning: SPIR-V emits `SAbs` and LLVM `llvm.abs` (both signed), while the C++/CUDA preludes and WGSL return the value unchanged [same PR, abs note](../learnings/1793207044532-slang-ir-sccp-folds-uint64-comparisons-as-signed-p.md). Measured on master 3218a7612 on the L40S: the core `abs` for `__BuiltinIntegerType` (`hlsl.meta.slang` ~:8031-8070) emits `GLSL.std.450 SAbs` for signed and unsigned T on direct SPIR-V and `@llvm.abs(x, i1 true)` on LLVM, so `abs(0xFFFFFFFFu)` is 1 on `-vk` and `-llvm` but 4294967295 on `-cpu` and `-cuda` (uint16 and uint64 behave the same way). spirv-val accepts `SAbs` on a uint operand, and SAbs-for-all-integers dates to 858c7c57b (2021, #1921), so it is not a regression. Under `-emit-spirv-via-glsl`, glslang rejects `abs(uint)` and `abs(uint64_t)` (GLSL has no genUType `abs`, so it picks the float overload) but accepts `abs(uint16_t)` by zero-extending to int. The C++/CUDA preludes' `U32_abs`/`U64_abs` return the input unchanged and there is no `U16_abs`, `I16_abs`, `U8_abs` or `I8_abs`, so `abs(uint16_t)` fails to compile on `-cpu` and `-cuda`; the CUDA `U64_abs` is declared to return `int64_t` (`slang-cuda-prelude.h:2770`). DXC maps HLSL `abs(uint)` to `IOP_uabs`, a no-op in both DXIL and SPIR-V, and `abs(int)` to `IMax(x, -x)` in DXIL and `SAbs` in SPIR-V ([abs(unsigned) per-target behaviour](../learnings/1793211189724-abs-unsigned-per-target-behaviour-in-slang-how-to-.md)). How to run DXC `-spirv` in the container is on [[wiki/concepts/slang-tooling-dxc-prebuilts-and-cmake.md]].

## A mis-folded bound reaches autodiff: false zero-trip and `MaxIters(0)` (#13985, PR #13993)

When `tryInferLoopMaxIterations` (`slang-check-stmt.cpp`) wrongly concludes that a loop runs 0 times, it does more than warn (E30514 "will be removed"). It also attaches `InferredMaxItersAttribute(0)`, which lowers to `IRLoopMaxItersDecoration`. Primal-hoist sizes the reverse-mode per-iteration storage from that value, so `bwd_diff` through the loop reads and writes out of bounds. On the L40S this gave cpu garbage that changed between runs (1232 or 136145 where 448 was expected) and NaN on vk and cuda. Non-differentiable loops still run correctly, because no emitter reads the decoration. The decoration never removes a loop either: loop-unroll carries it along and autodiff sizes the per-iteration tape from it (`maxIters + 1`). So when a loop flagged E30514 disappears, look at SCCP: master's signed `evalComparisonImpl` folds the first test of a loop with a uint64 bound above INT64_MAX to false and deletes the loop (#13978). The control is to write the step as `i = i + 1`, which skips trip-count inference; the loop is still removed ([E30514 on a loop is not what removes it](../learnings/1793220323154-slang-compare-compute-fails-on-any-stderr-warning-.md)). Master also truncated counts above INT32_MAX to int32, so 2^32 iterations became `MaxIters 0` and silently gave wrong gradients (24 instead of 32) [false zero-trip trip count corrupts reverse-mode autodiff](../learnings/1793223526256-slang-false-zero-trip-trip-count-corrupts-reverse-.md).

PR #13993 made trip-count inference read uint64 bounds as unsigned, which is correct. That exposed the #13954 producer bits. The folder keeps `~0u` as -1, so `uint64_t(~0u)` becomes 0xFFFF…FF, and it computes `~0ull >> 61` with an arithmetic shift, giving -1. Master's signed misreading was right by luck on some of these. The harmful direction is a mis-folded LOW-side bound (the init of a counting-up loop, or the bound of a counting-down loop): read as UINT64_MAX, it gives a false zero-trip. No uniform signed or unsigned reading of mis-folded values is safe. Ordering all unsigned widths as UInt64 fixes `uint i < ~0u` but breaks `uint i = 20; i > (~0u >> 28)`. Narrowing in the consumer is no better: converting the bounds to the loop type in the loop-count code (via `TypeCastIntVal::tryFoldImpl`) turned master's harmless overcount for that same loop into a false zero-trip, so the loop-count code reads the stored bits by type (UInt64 only for unsigned 64-bit) and the folder is fixed separately ([same](../learnings/1793220323154-slang-compare-compute-fails-on-any-stderr-warning-.md)). Only the producer fix works: narrow in `ASTBuilder::getIntVal`, and use a logical `>>` for unsigned types in BOTH `BuiltinOperationIntVal::tryFoldImpl` and `tryConstantFoldExpr`'s invoke path. The second path is easy to miss, because a mixed-type shift `uint64 >> int` goes through it [same](../learnings/1793223526256-slang-false-zero-trip-trip-count-corrupts-reverse-.md).

The PR kept the consumer correct for canonical values and did not add a guard on the expression shape: the reviewer showed such a guard misses `~0ull >> 61`, which has no cast. The existing `isIntValueInRangeOfType` accepts -1 for every unsigned type and any UInt64 value, so a "skip when out of range" guard cannot catch these either. The PR's Risk line named the real cost (wrong derivatives, not just a warning), cited #13954 as a merge prerequisite, stayed draft until it lands, and deferred the regression test that needs the producer fix. The peer reviewer's revert drills found unpinned code paths (a `UIntPtr` arm, a negated step, an off-by-one in the INT32_MAX cap); ask "would the test fail if I deleted this line?" for every new branch. When reviewing any trip-count change, test `bwd_diff` at runtime as well as diagnostics, because a "false warning" can be wrong code [a correct consumer exposes a producer's wrong bits; disclose, don't guard](../learnings/1793227253947-a-correct-consumer-exposes-a-producer-s-wrong-bits.md). The general rule is on [[wiki/concepts/general-misc-stale-pointer-and-regression-checks.md]].
