# PR-Approver: Anti-Round-Up Discipline & Temporary-Test-Disable Calibration

Rounding up is the recurring failure this page guards against: inflating a weak or conservative signal into a stronger verdict — treating a human merge as vindication, a green harness as proof, a soft self-merge as independent agreement, or an unresolved gap as either "safe" or "too cautious." The calibration data points here come from `pr_merged` joins between shadow-mode decisions and what maintainers actually did, plus the mirror-image discipline of *not* over-abstaining when a question is genuinely resolvable.

## TL;DR

- A human merge is not a verdict on your finding. In shadow mode the maintainer never saw it; a merge AT your decision head (same SHA, empty approval body, no follow-up commit) is divergence WITHOUT informed disagreement — record it honestly, never lower the gap/test-integrity bar because "they merged anyway."
- Before writing any "ABSTAIN vindicated" / "WOULD_APPROVE vindicated" calibration note, run the merged-head-vs-decision-head check: `gh pr view --json headRefOid,mergeCommit,mergedAt`. Equal heads ⇒ nothing was fixed post-decision; a later head ⇒ pull the intervening commits' changed paths.
- On a head-move join, ask "would my clause/verdict change at the merged head?" If the follow-ups stay in the SAME decision class (e.g. still `.github/**`), the abstain is calibration-neutral; if a commit DELETED the exact flagged code, WOULD_APPROVE@decided-SHA would have been a false-safe.
- ABSTAIN(OPEN_GAP) vs a maintainer APPROVE is the CONSERVATIVE direction, not a miss and not a false-safe. Do NOT round it up to WOULD_APPROVE. Only the missing evidence (a test actually running, an invariant actually traced) closes the gap — expert sign-off resolves the PR but doesn't make "test unrun" false.
- "false-safe" is reserved for WOULD_APPROVE → CHANGES_REQUESTED. An abstain-where-merged is the abstain-vs-merge procedure working.
- Pull `mergedBy` + `reviews` + `reviewDecision`, not just the merged SHA. An author self-merge with `reviews:[]` is a SOFT signal — it vindicates the risk-CLASS your challenger probed, not "a maintainer independently agreed."
- WOULD_APPROVE is calibrated when (a) Step-0 recall predicted the fix shape and the diff matches axis-for-axis at the pinned head, (b) a guard provably scopes the change to one target, and (c) a reproducing test is green on the relevant CI legs.
- Safely-approvable class: a single-line sibling-repo version bump by a MEMBER on a `bump-vX.Y.Z` branch. Harvest exit 20 is EXPECTED (production skips version bumps), not NO_REVIEW_SIGNAL. Still probe two risk classes: a second version source-of-truth desync, and a fetched-dependency pin/hash desync.
- Don't over-abstain either: an abstain on a RESOLVABLE question is a deferral, not a verdict. Read the pinned dependency's source (fetch raw cross-org) to close a concurrency-atomicity question rather than guessing; completing the investigation is a legitimate reason to flip a verdict even when the diff is byte-identical.
- Don't under-probe: a lock-scope-reduction / "the deadlock is gone" fix shifts a race onto the callee. Ask what that lock serialized and whether every callee is now safe to run concurrently; read concrete callee impls at head, not the interface. A self-imposed thread-safety contract the code doesn't meet ⇒ OPEN_GAP.
- Trace an un-keyed field's CONSTRUCTION path before flagging a cache-key OPEN_GAP — the superset question ("can the OTHER members diverge in a dispatch-relevant dimension?") is answered where the field is set, not in the key-builder.
- Reason from the code, not one tool run's label — Devin severity varies run-to-run on byte-identical lines.
- Temporary, tracked, maintainer-authored test-disables: the bundled-coverage gap is a LEGITIMATE but low-severity OPEN_GAP that informed maintainers routinely accept. Keep flagging it (never round it away), but frame it as "confirm this temporary trade-off," weighted to the lenient end — leaving CI flaking is worse.

## Anti-round-up discipline: a human merge is not a verdict

**A human APPROVE over a shadow-only finding is NOT evidence the finding was wrong — and a merge AT your decision head means nothing was fixed.** On slangpy#1075 the ABSTAIN_POLICY:OPEN_GAP (R9 @`d001b2b`, the weakened-mip-assertion / Metal cross-layer divergence) met tdavidovicNV's empty-bodied APPROVED ~5 min later and a self-merge at the *same* head `d001b2b` — no intervening commits, the concern shipped unaddressed. Because the approver runs shadow mode and never posts, the maintainer had no visibility into the finding; the naive update "my ABSTAIN, their APPROVE ⇒ I'm over-conservative, relax" is exactly the wrong update, because it trains the approver to rubber-stamp whatever humans merge. Still `record_human_verdict(APPROVED)` honestly, but classify it as **divergence WITHOUT informed disagreement** (check the approval body — empty here; any comment referencing the concern; any follow-up commit — none): it is neither vindication nor a false-safe, and never a reason to lower the gap/test-integrity bar ([[approver/human-disagreement] Human APPROVED over a shadow-only ABSTAIN — a merge over an unposted finding is NOT evidence the finding was wrong; don't relax the bar](../learnings/1785493492602-approver-human-disagreement-human-approved-over-a-.md)). On a `pr_merged` join always `gh pr view --json headRefOid,mergeCommit,mergedAt` and compare the merged head to your decision commit BEFORE declaring "vindicated" — if they are equal, no fixes were applied post-decision.

This rule exists precisely because an earlier write-up of this same PR got it backwards — it invented an "intervening fix" narrative claiming the PR merged at a *later* head with both gaps fixed between, scored as a vindicated AGREEMENT. That is factually wrong and was **RETRACTED**: the PR merged at the same head over the shadow-only finding, and the regression test it cited as "proof the loop worked" is the very test narrowed to mip-0 to green a reproduced Metal failure ([[approver/human-disagreement] RETRACTION of the slangpy#1075 "ABSTAIN vindicated" learning — it was factually wrong; the PR merged AT my decision head over a shadow-only finding](../learnings/1785493972914-approver-human-disagreement-retraction-of-the-slan.md)); the retracted file itself is tombstoned DO-NOT-USE and superseded by the retraction and the authoritative human-disagreement learning ([[RETRACTED — DO NOT USE] slangpy#1075 "ABSTAIN vindicated" — factually wrong; superseded](../learnings/1785493520816-approver-human-agreement-slangpy-1075-abstain-vind.md)). Meta-lesson: celebratory "vindicated" write-ups drift into overclaiming — run the merged-head-vs-decision-head check before writing any `pr_merged` calibration learning.

**Protected-path board-sync ABSTAINs vindicate cleanly by maintainer merge — with a class-invariance check on head-move.** slangpy-samples#57 (three revisions, all `.github/**` thin callers + a `zizmor.yml`) stayed ABSTAIN_POLICY:no_protected_paths and merged at exactly the R2 decision commit `df17e0f2` after jkwak-work APPROVED with zero follow-ups — an expected-agreement shape (abstain-deferred-to-human → approved-unmodified); the abstain is the *win*, not a coverage loss, since the human approved without changing a line and `nv-slang-bot` lacks the `workflows` permission to push these anyway ([[approver/confirmed] Protected-path-only board-sync onboarding PR → ABSTAIN_POLICY was correctly calibrated (merged unchanged)](../learnings/1785536628434-approver-confirmed-protected-path-only-board-sync-.md)). slang-rhi#804 sharpens the join discipline: it merged 2 commits PAST the R3 decision head with an INDEPENDENT jkwak-work approval (not a bare self-merge) — join-SHA-first caught the head-move, but the decisive extra step is **check whether the moved head stayed in the SAME decision class**: both follow-ups were still `.github/**`, so re-deciding at the merged head yields the identical ABSTAIN and the head-move is calibration-neutral; contrast slang#12095 where a post-decision commit DELETED the exact flagged code, crossing a class boundary and making WOULD_APPROVE@decided-SHA a would-be false-safe. On any `pr_merged` join where the head moved, pull the intervening commits' changed paths and ask "would my clause/verdict have changed at the merged head?" ([[approver/human-agreement] protected-path ABSTAIN survives workflow-only follow-up commits — class-invariance check on join](../learnings/1785536765566-approver-human-agreement-protected-path-abstain-su.md)).

**ABSTAIN vs a maintainer APPROVE is the conservative direction, never a miss to round up.** On fork Metal-codegen PR #12142 the ABSTAIN(OPEN_GAP) — the validating `-target metal` test never ran (fork CI stuck at `action_required`, green status false) — met a domain maintainer's APPROVE-on-inspection at the same commit. This is the CONSERVATIVE direction (ABSTAIN vs APPROVE), the opposite of a false-safe, and is exactly the designed route-to-human; do NOT round this class up to WOULD_APPROVE. The only thing that closes the gap is the test actually running — expert approval resolves the PR but doesn't retroactively make "test unrun" false ([fork codegen PR with unrun validating test — ABSTAIN(OPEN_GAP) vs human APPROVE is directionally-correct, not a miss](../learnings/1785353094549-approver-human-disagreement-fork-codegen-pr-with-u.md)).

An abstained-where-approved point milder than a false-safe: slangpy#1082 R4 @`c4ae890` had 0 Devin 🔴 + green CI, but the DECISION_REVIEW gate held an OPEN_GAP on the new `NativeTorchTensorDiffPair` cache-signature keying only the *primal* tensor's signature when both primal+grad exist, so a matching-primal/differing-grad pair could collide. The human (ccummingsNV) merged, and post-merge tracing showed why they were right: in the real autograd dispatch a diff-pair's grad is ALWAYS either `create_zeros_like_tensor(primal)` or the upstream `grad_output` (torch autograd shape invariant), so grad dtype/shape tracks primal and the divergent case isn't reachable. The transferable lesson for a cache-key change that keys on ONE of a multi-tensor aggregate: the superset question ("can the OTHER members diverge in a dispatch-relevant dimension?") must be answered from the CONSTRUCTION path, not the key-builder — trace where the un-keyed field is set before calling it OPEN_GAP; had the `autograd_backward` construction been traced during the challenger (not post-merge) it might have cleared to advisory. Still the *good* failure direction (a human looks) — and Devin run-to-run severity variance is real (the same byte-identical `:126` was 🔴 in R2/R3, informational in R4), so reason from the code, not one run's label ([[approver/human-disagreement] Abstained on a diff-pair cache-key OPEN_GAP (primal-only keying); human merged — invariant held at runtime](../learnings/1785504649372-approver-human-disagreement-abstained-on-a-diff-pa.md)).

## Calibrated WOULD_APPROVE and safely-approvable classes

**Agreement (full-arc):** #12152 (hpp compute-wrapper prototypes) was decided WOULD_APPROVE on the Devin-only tier and MERGED at the exact decision head after a non-author maintainer approved byte-identically — the WOULD_APPROVE path is calibrated when (a) Step-0 recall predicted the fix shape and the diff matches it axis-for-axis at the pinned head, (b) a guard provably scopes the change to one target, and (c) a reproducing FileCheck test is green on the relevant CI legs ([recall-predicted hpp-emitter fix WOULD_APPROVE vindicated full-arc](../learnings/1785339839478-approver-human-agreement-recall-predicted-hpp-emit.md)).

**A safely-approvable class: the sibling-repo package version bump.** A single-line `pyproject.toml`/`setup.cfg`/`package.json` version bump by a MEMBER on a `bump-vX.Y.Z` branch (rebuild/test wheels against the latest Slang release) is WOULD_APPROVE on the Devin-only fallback — harvest exit 20 here is EXPECTED and correct (production claude-code-action genuinely skips version-bump PRs), NOT a NO_REVIEW_SIGNAL. But probe two version-bump risk classes every time: (1) **second version source-of-truth desync** — code-search the repo at head for the old string and `__version__`, confirming the version lives in exactly one place (slang-torch's `__version__` in `compile.py` is `from torch import __version__`, unrelated); (2) **fetched-dependency version/hash pin desync** — does the diff touch a pin a bump silently invalidates (cf. slang-rhi's CMake `SLANG_VERSION STREQUAL SLANG_HASH_VERSION` guard)? `pyproject.toml` is not a protected path, blast radius is package-metadata-only, and the build job actually producing the wheels is execution-verified packaging ([[approver/human-agreement] slang-torch version-bump PR — Devin-only fallback WOULD_APPROVE, harvest exit 20 is correct (production skips)](../learnings/1785530795140-approver-human-agreement-slang-torch-version-bump-.md)). Confirmed on the join: slang-torch#49 (1.3.21→1.3.22) merged byte-identical at the exact decided SHA — but `mergedBy=jhelferty-nv` is the author with `reviews:[]`, so the agreement is SOFT (author self-merge, zero independent review); it vindicates the *class* (the risk-class challenger probes are the real safety net, not a human gate) but must not be counted as "a maintainer independently agreed" — always pull `mergedBy`+`reviews`+`reviewDecision`, not just the merged SHA ([[approver/human-agreement] slang-torch#49 v1.3.22 WOULD_APPROVE — MERGED byte-identical @decided SHA (author self-merge, soft signal)](../learnings/1785537154821-approver-human-agreement-slang-torch-49-v1-3-22-wo.md)).

## Gap-resolution vs deferral: don't over-abstain, don't under-probe

**Lock-scope-reduction fixes shift a race onto the callee, and an abstain on a *resolvable* dependency-behavior question is a deferral, not a verdict.** slangpy#1081 (`Logger::log` deadlock fix) narrows a mutex to snapshot shared state then releases it before invoking `output->write()` (which can take the GIL) — reads obviously-correct and CI-green, but removes the serialization that lock was incidentally giving to every callee, and the PR even added a header contract ("outputs must support calls from multiple threads") without making the built-in Console/File/DebugConsole outputs satisfy it. For any diff that reduces a lock's scope or moves a call outside a lock, don't stop at "the deadlock is gone" — ask *what did that lock serialize, and is every callee now safe to run concurrently?* and read the concrete callee implementations at head, not the interface (also check the snapshot itself: copying refcounted handles under the lock is safe only if the refcount is atomic — verified `Object::m_state` is `std::atomic`) ([[approver/challenger-miss] Lock-scope-reduction fixes shift a race onto the callee — probe callee thread-safety](../learnings/1785412873218-approver-challenger-miss-lock-scope-reduction-fixe.md)). Crucially, the "can concurrent writes garble output?" uncertainty was *resolvable* and the R0 ABSTAIN had merely not resolved it: reading the pinned dependency's source (fmt `@40626af8` = v11.2.0: `vprint_buffered` formats into a `memory_buffer` then a SINGLE `fwrite`, flockfile held across format+write) proved each `fmt::print(FILE*,…)` is byte-atomic on the POSIX/buffered path, so concurrent writes can only reorder whole lines, not garble them — which flipped R0→R1 WOULD_APPROVE (the synchronize was doc-only, .cpp byte-identical, so the flip came from *completing the investigation*, not a code change) and the human MEMBER approved the same head. For "can concurrent calls to this sink corrupt output?" questions, read the sink library's source AT THE VERSION THE REPO PINS (fetch raw via `raw.githubusercontent.com` since a repo-scoped token 401s cross-org), and scope the proof honestly — the Windows console/`OutputDebugStringA` paths were left "per-message integrity unproven", not silently generalized ([[approver/challenger-miss] Resolve a concurrency-atomicity gap by reading the dependency's source at its pin, not by guessing — fmt::print is per-line atomic](../learnings/1785421065093-approver-challenger-miss-resolve-a-concurrency-ato.md)).

## Temporary, tracked test-disable calibration

**The human-disagreement (correct-abstain calibration): slangpy#1076** whole-`TEST_CASE` `doctest::skip()` of two flaky profiler tests — shadow = ABSTAIN_POLICY/OPEN_GAP (the skip also dropped deterministic cross-thread frame-rejection coverage as collateral), human = maintainer merged unchanged with a tracked re-enable (#1077). This is the abstain-vs-merge procedure WORKING, not a false-safe (that label is reserved for WOULD_APPROVE → CHANGES_REQUESTED). For the CLASS of *maintainer-authored, temporary, tracked test-disables*, the bundled-coverage gap is a **legitimate but low-severity OPEN_GAP** informed maintainers routinely accept — keep flagging it (never round up), but frame it as "confirm this temporary trade-off," weighted to the lenient end, since the alternative (leave CI flaking) is worse ([approver/human-disagreement — temporary maintainer test-disable: bundled-coverage OPEN_GAP is real but low-severity; maintainers merge the trade-off](../learnings/1785282531686-approver-human-disagreement-temporary-maintainer-a.md)).
