# CI Flake Triage — Runner Pools and Infrastructure

The self-hosted GPU/perf fleet that shader-slang/slang CI actually runs on, how to identify which physical box a job landed on, and why a failure pinned to one bad runner is usually a *pool lottery* (rerun on a different member) rather than a futile reland. This is the infrastructure layer under [rerun decision rules](ci-flake-rerun-decision-rules.md) and [flake-vs-real classification](ci-flake-known-signatures-and-classification.md). How the Windows GPU `test-slang` job is shaped (API split vs merged `-api all`), how long it takes and how to project it is in [Windows GPU slang-test jobs: the API split, the merge back, and sizing CI jobs](ci-windows-gpu-test-job-split-and-merge.md).

## TL;DR

- The fleet is **not one homogeneous pool**: a Windows GPU pool (`win-test-*`, `[Windows, self-hosted, test]`), a Linux GPU fleet (`2u1g-*`), and two separate perf/benchmark pools (`perf` ≠ `benchmark`). Grep the actual `runs-on:` line before naming a pool.
- The Windows pool is **heterogeneous** (one box can run low on disk); a Windows GPU test job finishing in under ~60 s usually ran no tests (disk-space/artifact preflight).
- **Resolve runner identity from the API, not the display name** (`Machine name: 'SLANG-WINDOWS-2'` is image-baked): `runs/<id>/jobs --jq '.jobs[]|{runner_name,conclusion}'`, per attempt `runs/<id>/attempts/<N>/jobs`.
- **`runner_name == ""` + `steps == []` + elapsed exactly at the job timeout ⇒ the job never ran**; escalate the missing runner, don't rerun. Exception: GitHub-hosted jobs `cancelled` at ~15 min with that shape during an Actions incident are outage kills (`gh run rerun --failed` once runners recover). A `failure` run with no failed job (only `filter`) is also an outage: wait for githubstatus `operational`.
- **A red GPU job with "log not found" means the runner died before uploading**: read `check-runs/<job-id>/annotations` for every attempt (a lost job can still show a failed step); "runner lost communication" is infra and `rerun --failed` normally clears it. #13298 (merge_group-only, exactly 14m01s, zero log) was memory exhaustion on the old Windows image (1 GiB pagefile).
- **`ubuntu-22.04` hosted labels are removed 2027-04-17**, and `release.yml` builds release binaries natively on it (jammy 2.35 bounds the glibc floor; v2026.20 measured 2.34), so moving it is a user-facing decision; the `-glibc-2.2x` archives (floor 2.17) lack slang-llvm. `ci.yml` live jobs run on the self-hosted GCP pool.
- **`ubuntu-latest` has been Ubuntu 26.04 since 2026-10-27 ~16-17Z**; read the image from the job-log header. The first breaks were slang-rhi's (GCC 15 `<ciso646>` `#warning` under `-Werror` in doctest; lavapipe Mesa 26 cooperative-matrix query).
- **A runner-scoped defect makes a rerun a POOL LOTTERY, not a futile reland**, whenever `runs-on:` is a label set; with ≥3 members and ≥2 healthy the odds are good. Two riders:
  - **The defect can be one mechanism on an otherwise-healthy box**: check for a within-window, same-box success on a *sibling* job before asking to recycle the runner.
  - **Prove attribution with a differential over `runner_name`, not over time** (one box N/N failing, siblings M/M green on the identical job). A "same pool" clue counts only if passing jobs don't share it: tally runner indexes over ~40 green jobs first.
- **`test-falcor` routes through a self-hosted `falcor-bridge` runner for EVERY PR** (PR #11915, 2026-08-07), so its opaque ~2–4 KB / 3-step log is universal and the real result lives in unreachable NVIDIA-internal GitLab. Confirm a second example's signature before a standing "defer" rule (this one had a retracted over-generalization), and still check per occurrence for a real ~309 KB / 10-step log.
- **A merge-queue `checks_timed_out` removal can be a self-hosted SM80Plus queue wait**: compare `created_at` vs `started_at` per job. The bot cannot requeue (`gh pr merge` and `enqueuePullRequest` refuse); a maintainer must. An eviction whose only failed job has no failed step and no log is a runner drop: read its annotations (#14111 had both in one day).

## Runner Pools and Infrastructure

shader-slang/slang maintains two self-hosted GPU runner pools on GCP: a Windows GPU pool (`win-test-*`, `[Windows, self-hosted, test]`) for T4-based jobs and a Linux GPU fleet (`2u1g-*`). Individual Windows machines (e.g. `SLANG-WINDOWS-2`) can run low on disk while neighbours are healthy; a Windows GPU test job completing in under ~60 s usually means a disk-space or artifact-download preflight failure, and one sick box assigned repeatedly makes several PRs fail the same job within ~6 s of each other, a cluster that looks like a flake ([Slang CI: Windows test-slang disk-space cluster flake](../learnings/1780200309948-slang-ci-windows-disk-space-cluster-flake.md)). The perf and benchmark pools are distinct (`[Windows, self-hosted, perf]` ≠ `[Windows, self-hosted, benchmark]`, used by different workflows); grep the actual `runs-on:` line before citing one ([slang CI: two distinct self-hosted runner pools (perf vs benchmark); #11501↔#11485 perf-CI overlap cross-linked](../learnings/1780769337150-slang-ci-two-distinct-self-hosted-runner-pools-per.md)).

Identify the runner a job ran on with `gh api repos/shader-slang/slang/actions/runs/<run-id>/jobs --jq '.jobs[] | select(.name | contains("test-windows-release-cl-x86_64-gpu")) | {runner_name, conclusion}'`; a log's `Machine name: 'SLANG-WINDOWS-2'` is an image-baked pool name, not a host. `actions/runs/<id>/attempts/<N>/jobs` carries the runner per attempt and is the fallback when `actions/runs/<id>/jobs` answers 502; job logs need `gh api .../jobs/<id>/logs --allow-escape-sequences` [gate-chain-routing hook blocks [Triage Resolution] in no-inbound one-shot runs](../learnings/1793289852768-gate-chain-routing-hook-blocks-triage-resolution-i.md). A pool the CI analytics frame shows as `busy 0 / total 1` with queued jobs is confirmed in two calls: `actions/runs?status=queued`, then `actions/runs/<id>/jobs` filtered to `status==queued`; the job `labels` (e.g. `Linux,self-hosted,SM80Plus`) name the stuck pool, and a merge_group run with only that job outstanding shows what it blocks [send_message refused on inherited heartbeat thread — pass explicit thread_id](../learnings/1793283475940-send-message-refused-on-inherited-heartbeat-thread.md).

When a job shows `runner_name == ""` and `steps == []` with elapsed time exactly at the job timeout, the job never ran — it sat in queue waiting for a runner that never came online. Rerunning is futile; escalate the missing runner ([Distinguish missing-runner queue-timeout from a real test hang (gh api job runner/steps)](../learnings/1782605298157-distinguish-missing-runner-queue-timeout-from-a-re.md)).

**The same never-ran shape on GitHub-hosted jobs during an Actions incident is an outage, and there a rerun is the remedy.** During the 2026-10-05 19:11Z-21:54Z incident, `ubuntu-latest` jobs (`filter`, `check-ci`, `reuse-compliance-check`) ended `cancelled` after exactly 15:00-15:02 with `runner_name: ""`, `steps: []` and "log not found"; downstream jobs read `skipped` and the aggregator `failure`. Match the window in https://www.githubstatus.com/api/v2/incidents/unresolved.json, confirm the job shape with `gh api repos/<o>/<r>/actions/jobs/<id>`, then `gh run rerun <run> --failed` once runners pick up jobs. Look-alikes differ: a `timeout-minutes` cancel has a runner and steps, and a `cancel-in-progress` supersede shares one timestamp across the run and the head has moved ([GitHub Actions outage signature: cancelled after exactly 15 min, empty runner_name, zero steps](../learnings/1791238163488-github-actions-outage-signature-jobs-cancelled-aft.md)). An outage can also leave a run with no failed job: on 2026-10-07 a slang `ci.yml` run concluded `failure` with only `filter` (success) in the jobs list. The cause showed only on the HTML run page (`curl -sL https://github.com/<repo>/actions/runs/<id>`) as an "Internal server error. Correlation ID …" annotation; `gh run rerun` and `gh workflow run` returned HTTP 500 and Actions was `major_outage`. When a run is red with no failing job, check `https://www.githubstatus.com/api/v2/summary.json` first, redispatch from a background loop that waits for `operational`, and push no code ([GitHub CI run with only 'filter' + failure = Actions outage, not code](../learnings/1791386926978-github-ci-run-with-only-filter-failure-actions-out.md)).

**A red GPU job whose log is "not found" usually means the runner died before uploading; the reason is in the check-run annotation.** Read `gh api repos/shader-slang/slang/check-runs/<job-id>/annotations`: on PR #13170 it said "The self-hosted runner lost communication with the server", and `gh run rerun --failed <run>` came back green. If the same test job passed in the sibling config (debug vs release), the diff is almost certainly not the cause. A runner loss can still show a failed step (on 2026-11-06 `sanitizer-linux-clang-x86_64` had `Run Tests with Sanitizers` = failure plus the annotation), so a sweep filtering on "no failed step" misses it. The reliable census lists jobs via `/actions/runs/<id>/attempts/<N>/jobs` for every attempt (a re-run hides attempt 1), reads `/check-runs/<job_id>/annotations` for each failed self-hosted job, and matches "lost communication" (the logs endpoint 404s). That day it found 7 losses on 4 pools (linux-test, linux-build, win-test, win-build) at 03:28:58–03:34:55Z, the daily slot of #14294, which had been tracked as Windows-GPU-only ([CI sweep: read Actions artifacts via proxy; find lost runners from annotations, not failed steps](../learnings/1793954343982-ci-sweep-read-actions-artifacts-via-proxy-find-los.md)). The ~03:25–03:35Z loss recurred on 11-04, 11-06 and 11-07; on a quiet night only one job is exposed, so only the census sees it. slangpy's `sanitizers` Linux asan leg on x570 runners instead lost its runner after ~128 min on two nights (started 04:10Z, lost 06:18–06:19Z), pointing to a duration limit or hang, not a clock event ([CI sweep: an approved fork-PR CI run in `waiting` has usually already run its tests](../learnings/1794040923411-ci-sweep-an-approved-fork-pr-ci-run-in-waiting-has.md)). Riders: a `github.ci_failed` whose only failed check-runs are `wait-for-human-priority` + `check-ci` (every real job `skipped`) is the bot-PR priority yield, so do nothing; and when the critique gate (`gate-critique-on-deliver.sh`) blocks read-only `gh api .../pulls/...` calls after a local edit, the `mcp__slang-mcp__github_get_pull_request*` tools read the same data ([diagnosing a red GPU job whose log is "not found"](../learnings/1790642965819-slang-ci-diagnosing-a-red-gpu-job-whose-log-is-not.md)).

**One runner-death variant has a constant-duration fingerprint and fires only in the merge queue (#13298).** All 8 claimed occurrences of `test-windows-release-cl-x86_64-gpu-dx / test-slang` dying with "runner lost communication" (7 PRs, 09-11→09-28) re-verified against GitHub: `merge_group` event, **exactly 14m01s**, zero log, job stuck `in_progress` on "Test Slang". Every `pull_request`-event failure of the same job in the window (773 CI runs, unpaginated) was an ordinary `exit code 1` (9) and none had this signature, so the merge_group-only split holds under direct verification. It is distinct from #12388 (Windows GPU `VK_ERROR_DEVICE_LOST`, which recovers and keeps logs). Counting by run-level `status=failure` is sound only once the workflow has no `continue-on-error` (slang's `ci.yml` has none) ([#13298: confirmed merge_group-only runner-death fingerprint, exactly 14m01s](../learnings/1790629871805-shader-slang-slang-13298-confirmed-merge-group-onl.md)). The cause was memory exhaustion on the old Windows GPU runner image (1 GiB pagefile, 31 GiB commit limit). Merging the per-API Windows GPU jobs into one `-api all` job (#13813, which also set the `test-slang` timeout to 120 min, [merged job measured](../learnings/1792592295131-merged-windows-gpu-ci-job-api-all-measured-debug-9.md)) does not reopen it: the merged 8-server job ran on the old image until 2026-08-07 with no 14m01s losses ([API-split jobs silently ignore cross-API unit tests](../learnings/1792579623451-windows-gpu-slang-test-api-split-jobs-silently-ign.md)).

**A runner-scoped defect makes a rerun a pool lottery, not a futile reland, and the defect can be job-scoped, so "reboot the box" is usually the wrong ask.** When `runs-on:` is a **label set** (`[Windows, self-hosted, regression-test]`) rather than a named host, dispatch goes to whichever member is free, so with ≥3 members and ≥2 healthy a rerun has good odds. In slang#12322 (unchanged head `ba156ebf`) attempts 1–2 on SLANGWIN5 gave `spirv-val [ 0 / 866 ]` ❌ and attempt 3 on SLANGWIN4 `[ 866 / 866 ]` ✅: the runner attribution was right, the "reruns are futile" conclusion wrong ([a rerun is a pool lottery, not a futile reland](../learnings/1785838439742-runner-scoped-ci-defect-a-rerun-is-a-pool-lottery-.md)). **The defect can be one mechanism on a healthy box:** on SLANGWIN5 in the same window `test-benchmark` (4/4), `test-falcor` and an MDL-benchmark `build` succeeded while only `test-compile-regression`'s SPIR-V validation failed 3/3, so check for a within-window, same-box success on a sibling job before asking to recycle the runner, or the escalation is rejected as unfounded. **Prove attribution with a differential over the runner, not over time:** tabulate every instance of the failing job in the window by `runner_name` (per attempt); one box N/N failing with siblings M/M green beats "it failed twice in a row." **Control a pool or host clue against passing jobs.** slangpy's build-pr Windows jobs all carry `Windows, X64, nvrgfx-kernelvm-bridge` (39/39), so "every hit ran on the same pool" says nothing; their runner names are `2u1g-b650-<idx>-<creation-ts>` (a fresh VM per job), so tally `<idx>` over ~40 passing jobs (`gh api repos/<o>/<r>/actions/runs/<id>/jobs --jq '.jobs[]|[.conclusion,.runner_name]'`) first. `runner_name` outlives the logs (~5 days). For slangpy#1223 all four hit indexes were common in the passing pool, so nothing was posted ([control a shared-pool clue against passing jobs](../learnings/1792691453073-before-citing-a-shared-runner-pool-clue-on-a-flake.md)).

**`test-falcor` routes through a self-hosted `falcor-bridge` runner for EVERY PR, so its opaque poller log is universal.** An older reading held that the opaque signature (a ~2–4 KB, 3-step log on a `kernelvm-falcor-bridge` runner, no test name recoverable) existed only on one PR's branch. PR #11915 (merged 2026-08-07) made `runs-on: [Linux, self-hosted, X64, falcor-bridge]` + `/opt/slang-ci/run-external-ci` the universal definition, so every failure log is a stub and the real result lives in an unreachable NVIDIA-internal GitLab pipeline. That justified a "defer" rule (babysitter Step 0d). The transferable discipline: before encoding a standing deference rule for an opaque-log class, pull a second example's `runner_name` + `steps` count (`gh api repos/<o>/<r>/actions/jobs/<id>`), since this signature already carried a retracted over-generalization. PR #12919 matched (`kernelvm-falcor-bridge-2`, 3 steps, ~3.9 KB), so the rule was adopted, still gated on a per-occurrence check in case a real (~309 KB, 10-step) log resurfaces ([Falcor test-falcor opaque logs are now universal (class 2), not branch-specific — verify the signature before deferring](../learnings/1789618761733-falcor-test-falcor-opaque-logs-are-now-universal-c.md)).

**slang-rhi's CUDA interop tests run on self-hosted GPU runners; read the per-test line, not the "GitHub-hosted skips" summary.** slang-rhi's `ci.yml` matrix includes self-hosted `nvrgfx-kernelvm-bridge` runners with same-adapter CUDA that run the interop tests in auto-CI, draft PRs included (`build (windows, x86_64, msvc, Release)` emits `buffer-shared-cuda.vulkan PASSED`). The recurring trap (slang-rhi #787/#881/#812) is concluding "compile-only" because GitHub-hosted jobs lack CUDA and `SKIP` the `#if SLANG_WIN64` same-adapter tests. `gh pr checks` names don't reveal which jobs are self-hosted GPU, so a green count is no evidence of execution; when a maintainer gates a ready-flip on "per-test PASSED", read that line in the self-hosted job's log ([slang-rhi CI runs CUDA interop on self-hosted GPU runners — read the per-test line, not the GitHub-hosted-skips summary](../learnings/1790197692432-slang-rhi-ci-runs-cuda-interop-tests-on-self-hoste.md)).

**GitHub-hosted `ubuntu-22.04` is deprecated (labels removed 2027-04-17), and slang's Linux release binaries build natively on it.** Per actions/runner-images (issue #14254), `ubuntu-22.04`/`22.04-arm` are deprecated since 2026-09-17 with brownouts in March–April 2027, and `ubuntu-latest` moved 24.04→26.04 over 2026-10-19..11-19. slang's `release.yml:24/30/36` builds the x86_64/aarch64/wasm packages directly on `ubuntu-22.04`, so jammy's glibc 2.35 bounds the shipped floor; 24.04 would raise it to 2.39 (26.04: 2.43), a user-facing decision that a manylinux container (as in `release-linux-glibc-2-28.yml`) avoids. Measured on v2026.20 with `readelf -V` over every ELF file (no `file` tool; filter by `head -c4 | grep -q ELF`): the highest `GLIBC_` symbol is 2.34 in the unsuffixed `linux-x86_64`/`linux-aarch64` archives and 2.17 in the container-built `-glibc-2.27`/`-glibc-2.28` archives. But only unsuffixed `linux-x86_64` ships `lib/libslang-llvm.so` (`release.yml:71`; the suffixed builds use `-DSLANG_SLANG_LLVM_FLAVOR=DISABLE`), so "just keep the 2.28 build" silently drops slang-llvm on Linux ([measured glibc floors and slang-llvm packaging, v2026.20](../learnings/1792434028042-slang-linux-release-archives-measured-glibc-floors.md)). In `ci.yml`, `ubuntu-22.04` is only the `LINUX_BUILD_RUNS_ON` fallback; live jobs run on the self-hosted GCP pool, so read a recent run's job labels (DeepWiki was stale). The formatting check pins clang-format via slang-binaries but pip-installs gersemi into the image's system Python (3.12→3.14 on 26.04) ([ubuntu-22.04 is deprecated; Linux release binaries build natively on it](../learnings/1790611288369-shader-slang-ci-ubuntu-22-04-is-deprecated-removed.md)). An `ubuntu-latest` job's image shows only in its log header (`##[group]Operating System`, `Image:`, `Version:`), not in `runner_name`/`labels`; a ranged GET (`Range: bytes=0-6000`) on `/actions/jobs/<id>/logs` is cheap enough for all ~1,300 such jobs a day ([CI sweep: snapshot misses jobs in waiting runs](../learnings/1792486355939-ci-sweep-snapshot-misses-jobs-in-waiting-runs-only.md)). On 10-19 all 137 sampled jobs were still 24.04.5 (20261012.334.1). The switch reached shader-slang on 2026-10-27 between 15:51Z and 17:21Z (38-job header sample; after it, 26.04.1 on images 20261012.163.1 and 20261025.179.1). Ubuntu 26 had been validated for slang PR CI in #13288/#13347 (closed 10-01), excluding scheduled workflows, `regenerate-cmdline-ref`, slangpy and slang-rhi, so search with no date filter before saying "no prep issue". The first breaks landed where predicted, in slang-rhi: the `sanitizers` nightly `tsan (linux, vulkan,wgpu)` no longer builds (`external/doctest/doctest.h:499` includes `<ciso646>`, for which GCC 15 emits a `#warning`, fatal under `-Werror`), and the `ci` linux gcc leg fails `cooperative-matrix-query.vulkan` at `CHECK(anySupported)` on lavapipe (Mesa 26.0.8, LLVM 21). slang `check-formatting` passed, and the slang nightly `agentic-tests` job is pinned to `ubuntu-22.04` ([Ubuntu 26.04 reached ubuntu-latest on 10-27; first breakages in slang-rhi](../learnings/1793176888015-ubuntu-26-04-reached-shader-slang-ubuntu-latest-on.md)). Through the OneCLI proxy, non-shader-slang repos such as `actions/runner-images` return 401 Bad credentials; read their github.com HTML with WebFetch ([Ubuntu image only visible in the job log header](../learnings/1792399653342-slang-bot-draft-ci-starvation-fix-pr-12738-exists-.md)).

**`checks_timed_out` from a runner-pool queue wait.** `test-linux-release-gcc-x86_64-sm80 / test-slang` runs on the self-hosted SM80Plus pool and normally waits 0–14 min. On 2026-10-12 #13371's merge-group run had it QUEUED 143 min (22:26Z → 00:49Z); the PR was removed as `checks_timed_out` at 00:18Z and the group run later went green. Measure the wait from `actions/runs/<id>/jobs` (`created_at` vs `started_at`) before blaming code or LLVM. The wake payload's `evicted` list missed this removal, so re-derive evictions from `RemovedFromMergeQueueEvent`. The bot cannot requeue (`gh pr merge <n>` and GraphQL `enqueuePullRequest` were refused; `gh pr merge` has no `--merge-queue` flag), so a maintainer must [merge-queue checks_timed_out can be a self-hosted sm80 runner queue wait](../learnings/1791873086822-merge-queue-checks-timed-out-can-be-a-self-hosted-.md). Both infra evictions hit #14111 on 2026-11-03 and left master idle 11+ h behind green nightlies (an empty queue also trips the weekday head-age check). First, `failed_checks` with every status green: the only failed job, `test-windows-debug-cl-x86_64-gpu / test-slang`, had an empty step list, a 404 BlobNotFound log and the "runner lost communication" annotation ([eviction with all statuses green = runner drop](../learnings/1793693100985-merge-queue-eviction-with-all-statuses-green-can-b.md)). Then `checks_timed_out` at 2 h: the sm80 job was created 08:31Z and started 11:11Z, passing in 8 min (its `conclusion: success` hides the wait), against that day's 20–52 min baseline ([checks_timed_out from a 2h40m sm80 queue](../learnings/1793707497432-merge-queue-checks-timed-out-can-come-from-a-linux.md)). Both are infra findings: report the PR for a human re-enqueue and the pool for a check, and file no code-regression issue.
