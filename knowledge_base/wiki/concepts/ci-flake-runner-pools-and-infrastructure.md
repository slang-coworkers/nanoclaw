# CI Flake Triage — Runner Pools and Infrastructure

The self-hosted GPU/perf fleet that shader-slang/slang CI actually runs on, how to identify which physical box a job landed on, and why a failure pinned to one bad runner is usually a *pool lottery* (rerun on a different member) rather than a futile reland. This is the infrastructure layer under [rerun decision rules](ci-flake-rerun-decision-rules.md) and [flake-vs-real classification](ci-flake-known-signatures-and-classification.md).

## TL;DR

- The fleet is **not one homogeneous pool** — a Windows GPU pool (`win-test-*`, labels `[Windows, self-hosted, test]`) and a Linux GPU fleet (`2u1g-*`), *plus* two separate perf/benchmark pools (`[Windows, self-hosted, perf]` ≠ `[Windows, self-hosted, benchmark]`). Always grep the actual `runs-on:` line before naming a pool.
- The Windows pool is **heterogeneous**: individual machines can run low on disk while neighbours are healthy. A Windows GPU test job finishing in under ~60 s usually means no tests ran (disk-space/artifact preflight), not a real result.
- **Resolve runner identity from the API, not the display name.** `Machine name: 'SLANG-WINDOWS-2'` is an image-baked pool name, not a physical host. Use `runs/<id>/jobs --jq '.jobs[]|{runner_name,conclusion}'` (per-attempt: `runs/<id>/attempts/<N>/jobs`).
- **`runner_name == ""` + `steps == []` + elapsed exactly at the job timeout ⇒ the job never ran** — it queued for a runner that never came online. Escalate the missing runner; do not rerun. Exception: GitHub-hosted jobs `cancelled` at exactly ~15 min with that shape during an Actions incident are outage kills; confirm the incident window, then `gh run rerun --failed`. A run that reads `failure` with no failed job (only `filter` listed) is also an Actions outage: check githubstatus `summary.json` and wait for `operational` before redispatching.
- **A red GPU job with "log not found" means the runner died before uploading** — read `check-runs/<job-id>/annotations`; "self-hosted runner lost communication" is infra, and `rerun --failed` normally clears it. The #13298 variant (`test-windows-release-cl-x86_64-gpu-dx`) is merge_group-only, exactly 14m01s, zero log, stuck `in_progress`.
- **`ubuntu-22.04` hosted labels are removed 2027-04-17.** slang's `release.yml` builds release binaries natively on it (glibc 2.35 floor), so moving it is a user-facing glibc decision; `ci.yml` live jobs run on the self-hosted GCP pool, so read real job labels, not the YAML fallback.
- **A runner-scoped defect makes a rerun a POOL LOTTERY, not a futile reland** — *whenever* `runs-on:` is a label set (dispatch goes to whichever member is free). With ≥3 members and ≥2 healthy, a rerun is a cheap probabilistic remedy with good odds.
- Two riders on runner attribution:
  - **The defect can be one mechanism on an otherwise-healthy box** — check for a within-window, same-box success on a *sibling* job before asking to recycle the runner, or the escalation is rejected as unfounded.
  - **Prove attribution with a differential over `runner_name`, not over time** — tabulate every instance of the failing job repo-wide in the window by runner; a clean split (one box N/N failing, siblings M/M green on the identical job) is far stronger than "it failed twice in a row."
- **`test-falcor` routes through a self-hosted `falcor-bridge` runner for EVERY PR now** (PR #11915, merged 2026-08-07) — so its opaque ~2–4 KB / 3-step GH Actions log is universal, not branch-specific; the real result lives in an unreachable NVIDIA-internal GitLab pipeline. Before encoding a standing "defer this opaque class" rule, pull a second example's `runner_name` + `steps` count to confirm the signature is universal (this exact signature had a prior *retracted* over-generalization), and still verify per-occurrence in case a rare real ~309 KB / 10-step log resurfaces.

## Runner Pools and Infrastructure

shader-slang/slang maintains two self-hosted GPU runner pools on GCP: a Windows GPU pool (`win-test-*` machines, labels `[Windows, self-hosted, test]`) for T4-based jobs, and a Linux GPU runner fleet (`2u1g-*` machines). The Windows pool is heterogeneous; individual machines (e.g. `SLANG-WINDOWS-2`) can run low on disk while neighbours are healthy, and a Windows GPU test job that completes in under ~60 seconds usually means no actual tests ran — a disk-space preflight failure or artifact-download failure, not a real test result. When one bad runner in the pool is repeatedly assigned, multiple PRs can fail the same Windows test job within ~6 seconds of each other, producing a cluster that looks like a flake but is really one sick box ([Slang CI: Windows test-slang disk-space cluster flake](../learnings/1780200309948-slang-ci-windows-disk-space-cluster-flake.md)). There are also two separate self-hosted perf/benchmark pools — `[Windows, self-hosted, perf]` is distinct from `[Windows, self-hosted, benchmark]` and used by different workflows; always grep the actual `runs-on:` line before citing which pool a workflow uses ([slang CI: two distinct self-hosted runner pools (perf vs benchmark); #11501↔#11485 perf-CI overlap cross-linked](../learnings/1780769337150-slang-ci-two-distinct-self-hosted-runner-pools-per.md)).

To identify which specific runner a job ran on: `gh api repos/shader-slang/slang/actions/runs/<run-id>/jobs --jq '.jobs[] | select(.name | contains("test-windows-release-cl-x86_64-gpu")) | {runner_name, conclusion}'`. `Machine name: 'SLANG-WINDOWS-2'` in a log is an image-baked pool name, not a physical host — resolve real identity via the jobs API. For per-attempt runner assignment, read `actions/runs/<id>/attempts/<N>/jobs`, which carries the runner each attempt landed on.

When a job shows `runner_name == ""` and `steps == []` with elapsed time exactly at the job timeout, the job never ran — it sat in queue waiting for a runner that never came online. Rerunning is futile; escalate the missing runner ([Distinguish missing-runner queue-timeout from a real test hang (gh api job runner/steps)](../learnings/1782605298157-distinguish-missing-runner-queue-timeout-from-a-re.md)).

**The same never-ran shape on GitHub-hosted jobs during an Actions incident is an outage, and there a rerun is the remedy.** During the 2026-10-05 19:11Z-21:54Z incident, `ubuntu-latest` jobs (`filter`, `check-ci`, `reuse-compliance-check`) ended `cancelled` after exactly 15:00-15:02 with `runner_name: ""` and `steps: []`: no runner was ever assigned, so no code ran, and `gh run view --log` says "log not found". Downstream jobs read `skipped` and the aggregator run reads `failure`. Check https://www.githubstatus.com/api/v2/incidents/unresolved.json for a matching window, confirm the job shape with `gh api repos/<o>/<r>/actions/jobs/<id>`, then `gh run rerun <run> --failed` once runners are picking up jobs again. Two look-alikes differ: a per-job `timeout-minutes` cancel has a runner and steps, and a `cancel-in-progress` supersede shares one timestamp across the run and the head has moved ([GitHub Actions outage signature: cancelled after exactly 15 min, empty runner_name, zero steps](../learnings/1791238163488-github-actions-outage-signature-jobs-cancelled-aft.md)). An outage can also leave a run with no failed job at all. On 2026-10-07 a slang `ci.yml` run concluded `failure` while the API jobs list showed only `filter` (success). The cause appeared only on the HTML run page (`curl -sL https://github.com/<repo>/actions/runs/<id>`), as an "Internal server error. Correlation ID …" annotation. `gh run rerun` and `gh workflow run` both returned HTTP 500, and githubstatus.com listed Actions as `major_outage`. So when a run is red with no failing job, check `https://www.githubstatus.com/api/v2/summary.json` before triaging. Redispatch from a background loop that waits until the Actions component reads `operational`, and don't push code for it ([GitHub CI run with only 'filter' + failure = Actions outage, not code](../learnings/1791386926978-github-ci-run-with-only-filter-failure-actions-out.md)).

**A red GPU job whose log is "not found" usually means the runner died before uploading, so the reason lives in the check-run annotation.** When a `test-windows-*-gpu-*` job fails and `gh run view --job <id> --log[-failed]` returns `log not found` or nothing, read `gh api repos/shader-slang/slang/check-runs/<job-id>/annotations`. On PR #13170 it said "The self-hosted runner lost communication with the server", and `gh run rerun --failed <run>` came back fully green. If the same test job passed in the sibling config (debug vs release), the diff is almost certainly not the cause. Two riders from the same session: a `github.ci_failed` whose only failed check-runs are `wait-for-human-priority` + `check-ci` (every real job `skipped`) is the bot-PR priority yield, so do nothing and let a later run force the matrix; and when the critique gate (`gate-critique-on-deliver.sh`) blocks even read-only `gh api .../pulls/...` calls after a local file edit, the `mcp__slang-mcp__github_get_pull_request*` tools read the same data outside the Bash gate ([diagnosing a red GPU job whose log is "not found"](../learnings/1790642965819-slang-ci-diagnosing-a-red-gpu-job-whose-log-is-not.md)).

**One runner-death variant has a constant-duration fingerprint and fires only in the merge queue (#13298).** All 8 claimed occurrences of `test-windows-release-cl-x86_64-gpu-dx / test-slang` dying with "The self-hosted runner lost communication with the server" (7 PRs, 09-11→09-28) re-verified exactly against GitHub: `merge_group` event, duration **exactly 14m01s** every time, zero log ever uploaded, and the job stuck permanently `in_progress` on step "Test Slang". Enumerating every `pull_request`-event `status=failure` run of the same job in the same window (773 CI runs, no pagination truncation) found 9 ordinary `exit code 1` failures and zero with this signature, so the merge_group-only split holds under direct verification rather than as a claim copied from the issue body. A constant duration with no log looks like a fixed workflow/step timeout killing a wedged VM; it is distinct from #12388 (Windows GPU `VK_ERROR_DEVICE_LOST`, where the job recovers and keeps full logs). Counting occurrences by run-level `status=failure` is sound only after confirming the workflow has no `continue-on-error` (slang's `ci.yml` has none), because only then does every job failure propagate to the run ([#13298: confirmed merge_group-only runner-death fingerprint, exactly 14m01s](../learnings/1790629871805-shader-slang-slang-13298-confirmed-merge-group-onl.md)).

**A runner-scoped defect makes a rerun a pool lottery, not a futile reland — and the defect can be job-scoped, so "reboot the box" is usually the wrong ask.** When a failure is pinned to one bad self-hosted runner, the tempting conclusion is "rerunning could just land on the same box." That is wrong whenever `runs-on:` is a **label set** (`[Windows, self-hosted, regression-test]`) rather than a named host — dispatch goes to whichever pool member is free, so with ≥3 members and ≥2 healthy a rerun is a cheap probabilistic remedy with good odds. Measured on a controlled within-PR experiment (slang#12322, unchanged head `ba156ebf`): attempts 1–2 on SLANGWIN5 gave `spirv-val [ 0 / 866 ]` ❌, attempt 3 on SLANGWIN4 gave `[ 866 / 866 ]` ✅ — the runner attribution was right (proven by the differential) but the "reruns are futile" remedy conclusion was wrong ([a rerun is a pool lottery, not a futile reland](../learnings/1785838439742-runner-scoped-ci-defect-a-rerun-is-a-pool-lottery-.md)). Two riders. **The defect can be one mechanism on an otherwise-healthy box:** on that same SLANGWIN5 in the same window `test-benchmark` (4/4), `test-falcor`, and an MDL-benchmark `build` all succeeded while only `test-compile-regression`'s SPIR-V validation failed 3/3 — so check for a **within-window, same-box success on a sibling job** before asking to recycle the runner, or the escalation gets rejected as unfounded. And **prove the attribution with a differential over the runner, not over time:** enumerate every instance of the failing job repo-wide in the window and tabulate by `runner_name` (from `actions/runs/<id>/attempts/<N>/jobs`, which carries per-attempt runner assignment); a clean split — one box N/N failing, siblings M/M green on the identical job — is far stronger than "it failed twice in a row."

**The `test-falcor` job now routes through a self-hosted `falcor-bridge` runner for EVERY PR, so its opaque poller log is universal, not branch-specific.** An older reading held that the `test-falcor` opaque-log signature (a ~2–4 KB, 3-step GH Actions log on a `kernelvm-falcor-bridge` runner, with no test name recoverable from GitHub) existed *only* on one PR's branch that routed CI through a dedicated bridge runner. That is no longer true: PR #11915 ("gate the Falcor bridge test-falcor behind the falcor-ci approval environment", merged 2026-08-07) landed the same `runs-on: [Linux, self-hosted, X64, falcor-bridge]` + `/opt/slang-ci/run-external-ci` routing as the *universal* `test-falcor` job definition on master. Since then every PR's `test-falcor` failure is class-2-shaped by default — the GH Actions log is a stub, and the real result lives only in an NVIDIA-internal GitLab pipeline unreachable from here. This justified adopting a "defer / don't-investigate" deference for the signature (Step 0d in the babysitter sweep), but the *adoption discipline* is the transferable part: before encoding a **standing** deference rule for a recurring opaque-log class, independently pull a second example's job metadata (`gh api repos/<o>/<r>/actions/jobs/<id>` → check `runner_name` + `steps` count) to confirm the signature is really universal now — because this same signature already carried a *retracted* over-generalization (sampled once, generalized to "structurally cannot contain a test name", wrong), and a persisted policy is far harder to unwind than a one-off wrong claim. Verification confirmed it here (PR #12919, unrelated to the original branch, showed the identical `kernelvm-falcor-bridge-2` / 3-step / ~3.9 KB signature), so the deference was adopted — but still gated on a per-occurrence signature check, in case a rare *real* (~309 KB, 10-step) log ever resurfaces ([Falcor test-falcor opaque logs are now universal (class 2), not branch-specific — verify the signature before deferring](../learnings/1789618761733-falcor-test-falcor-opaque-logs-are-now-universal-c.md)).

**slang-rhi's CUDA interop tests run on self-hosted GPU runners — read the per-test line, not the "GitHub-hosted skips" summary.** `shader-slang/slang-rhi`'s `ci.yml` matrix includes **self-hosted `nvrgfx-kernelvm-bridge` runners with same-adapter CUDA** (around lines 43-44) that actually **run** the interop tests — jobs like `build (windows, x86_64, msvc, Release)` / `build (windows, x86_64, clang, Debug)` emit per-test lines such as `buffer-shared-cuda.vulkan PASSED` / `texture-shared-cuda.d3d12 PASSED`. No label, manual dispatch, or ready-flip is needed; the GPU run is already in auto-CI and fires on draft PRs. The recurring trap (slang-rhi #787/#881/#812) is concluding "the matrix is compile-only / the interop tests aren't executed" because the *GitHub-hosted* jobs lack CUDA and `SKIP` the `#if SLANG_WIN64` same-adapter tests — a true statement about *some* jobs that says nothing about the self-hosted ones. `gh pr checks` job *names* look like plain "build (...)" and do NOT reveal that a job is a self-hosted GPU runner running tests, so a green summary count is **not** evidence about test execution. The only valid read of "did the interop test run and pass" is the **per-test `PASSED` line inside the self-hosted job's log** (open the specific windows job via the run URL). When a maintainer gates a ready-flip on "GPU tests executing with per-test PASSED," verify by reading that line — don't infer from the matrix shape or report "GPU tests not executed." Same instrument-conflation the pool-attribution rules turn on: read the narrowest ground-truth line, not the roll-up ([slang-rhi CI runs CUDA interop on self-hosted GPU runners — read the per-test line, not the GitHub-hosted-skips summary](../learnings/1790197692432-slang-rhi-ci-runs-cuda-interop-tests-on-self-hoste.md)).

**GitHub-hosted `ubuntu-22.04` is deprecated (labels removed 2027-04-17), and slang's Linux release binaries build natively on it.** Per actions/runner-images (checked 2026-09-28, issue #14254), `ubuntu-22.04` and `22.04-arm` have been deprecated since 2026-09-17, with brownouts in March–April 2027; `ubuntu-latest` moves 24.04→26.04 between 2026-10-19 and 11-19. In shader-slang/slang, `release.yml:24/30/36` builds the x86_64/aarch64/wasm release packages directly on `ubuntu-22.04` with no container, so the host glibc (2.35) is the floor for shipped binaries, and moving the host to 24.04 raises it to 2.39. That is a user-facing decision; a manylinux container, as in `release-linux-glibc-2-28.yml`, avoids it. In `ci.yml`, `ubuntu-22.04` appears only as the `LINUX_BUILD_RUNS_ON` fallback while live jobs run on the self-hosted GCP pool, so read a recent run's job labels rather than trusting the YAML default (DeepWiki was stale on this). The formatting check pins clang-format via slang-binaries, so image clang-format changes don't matter, but it pip-installs gersemi into the image's system Python (3.12→3.14 on 26.04) ([ubuntu-22.04 is deprecated; Linux release binaries build natively on it](../learnings/1790611288369-shader-slang-ci-ubuntu-22-04-is-deprecated-removed.md)).
