# CI Flake Triage — Runner Pools and Infrastructure

The self-hosted GPU/perf fleet that shader-slang/slang CI actually runs on, how to identify which physical box a job landed on, and why a failure pinned to one bad runner is usually a *pool lottery* (rerun on a different member) rather than a futile reland. This is the infrastructure layer under [rerun decision rules](ci-flake-rerun-decision-rules.md) and [flake-vs-real classification](ci-flake-known-signatures-and-classification.md). The Windows GPU `test-slang` job's shape and sizing is in [Windows GPU slang-test jobs](ci-windows-gpu-test-job-split-and-merge.md).

## TL;DR

- The fleet is **not one homogeneous pool**: a Windows GPU pool (`win-test-*`, `[Windows, self-hosted, test]`), a Linux GPU fleet (`2u1g-*`), and two separate perf/benchmark pools (`perf` ≠ `benchmark`). Grep the actual `runs-on:` line before naming a pool.
- On the GCP runner VMs, Google's **OS Config agent runs background `apt-get update`** for inventory, competing for the apt lock with CI steps — not stopped by masking apt-daily timers or waiting on cloud-init; use a bounded retry of `apt-get update` itself (native locking arbitrates; a `flock` wrapper does NOT coordinate with APT's fcntl locks) or mask the agent on build images.
- The Windows pool is **heterogeneous** (one box can run low on disk); a Windows GPU test job finishing in under ~60 s usually ran no tests (disk-space/artifact preflight).
- **Resolve runner identity from the API, not the display name** (`Machine name: 'SLANG-WINDOWS-2'` is image-baked): `runs/<id>/jobs --jq '.jobs[]|{runner_name,conclusion}'`, per attempt `runs/<id>/attempts/<N>/jobs`.
- **`runner_name == ""` + `steps == []` + elapsed exactly at the job timeout ⇒ the job never ran**; escalate the missing runner, don't rerun. Exception: GitHub-hosted jobs `cancelled` at ~15 min with that shape during an Actions incident are outage kills (`gh run rerun --failed` once runners recover). A `failure` run with no failed job (only `filter`) is also an outage. So are `HTTP/2 504` download failures (FetchDXC hash, optix zip, sccache `curl: (22)`, `setup-bun`) during GitHub's anonymous-traffic incidents; a nightly perf run killed that way has no timings, not "no regressions".
- **A red GPU job with "log not found" means the runner died before uploading**: read `check-runs/<job-id>/annotations` for every attempt (a lost job can still show a failed step); "runner lost communication" is infra and `rerun --failed` normally clears it. #13298 (merge_group-only, exactly 14m01s, zero log) was memory exhaustion on the old Windows image (1 GiB pagefile).
- **`ubuntu-22.04` hosted labels are removed 2027-04-17**, and `release.yml` builds release binaries natively on it (jammy 2.35 bounds the glibc floor; v2026.20 measured 2.34), so moving it is a user-facing decision; the `-glibc-2.2x` archives (floor 2.17) lack slang-llvm. `ci.yml` live jobs run on the self-hosted GCP pool.
- **`ubuntu-latest` has been Ubuntu 26.04 since 2026-10-27 ~16-17Z**; read the image from the job-log header. The first breaks were slang-rhi's (GCC 15 `<ciso646>` `#warning` under `-Werror`; lavapipe Mesa 26 cooperative-matrix query).
- **A runner-scoped defect makes a rerun a POOL LOTTERY, not a futile reland**, whenever `runs-on:` is a label set; with ≥3 members and ≥2 healthy the odds are good. Check for a within-window same-box success on a sibling job before asking to recycle the runner, and prove attribution with a differential over `runner_name` (one box N/N failing, siblings M/M green on the identical job); control a "same pool" clue against ~40 passing jobs first.
- **`test-falcor` routes through a self-hosted `falcor-bridge` runner for EVERY PR** (PR #11915), so its opaque ~2–4 KB / 3-step log is universal and the real result lives in unreachable NVIDIA-internal GitLab. Confirm a second example's signature before a standing "defer" rule, and still check per occurrence for a real ~309 KB / 10-step log. Falcor2 has no automated workflow — only a manual smoke, failed 2026-09-08 then dormant; the healthy Falcor1 nightly proves the shared bridge runner alive, so a Falcor2 failure is target-side.
- **A merge-queue `checks_timed_out` removal can be a self-hosted SM80Plus queue wait**: compare `created_at` vs `started_at` per job. The bot cannot requeue (`gh pr merge` and `enqueuePullRequest` refuse); a maintainer must. An eviction whose only failed job has no failed step and no log is a runner drop: read its annotations (#14111 had both in one day).
- **slang-rhi's CUDA interop tests run on self-hosted GPU runners** (auto-CI, draft PRs included) — read the per-test PASSED line, not the "GitHub-hosted skips" summary.
- A hosted-runner **toolchain roll beats a commit-range bisect as the FIRST hypothesis** for a link-time/optimizer crash at a trivial source line: grep the `Runner Image` block + `VCToolsVersion` in red vs last-green job logs (2026-11-20: a `windows-latest` image roll bumped MSVC 14.51→14.52 and ARM64 `/LTCG` ICE'd).

## Runner Pools and Infrastructure

shader-slang/slang maintains two self-hosted GPU runner pools on GCP: a Windows GPU pool (`win-test-*`) for T4-based jobs and a Linux GPU fleet (`2u1g-*`). Individual Windows machines can run low on disk while neighbours are healthy; a Windows GPU test job completing in under ~60 s usually means a disk-space or artifact-download preflight failure, and one sick box assigned repeatedly makes several PRs fail the same job within ~6 s of each other — a cluster that looks like a flake ([Slang CI: Windows test-slang disk-space cluster flake](../learnings/1780200309948-slang-ci-windows-disk-space-cluster-flake.md)). The perf and benchmark pools are distinct (`[Windows, self-hosted, perf]` ≠ `[Windows, self-hosted, benchmark]`, used by different workflows); grep the actual `runs-on:` line before citing one ([two distinct self-hosted runner pools (perf vs benchmark)](../learnings/1780769337150-slang-ci-two-distinct-self-hosted-runner-pools-per.md)).

Identify the runner a job ran on with `gh api repos/shader-slang/slang/actions/runs/<run-id>/jobs --jq '.jobs[] | select(.name | contains("...")) | {runner_name, conclusion}'`; a log's `Machine name:` is an image-baked pool name, not a host. `actions/runs/<id>/attempts/<N>/jobs` carries the runner per attempt and is the fallback when `actions/runs/<id>/jobs` answers 502; job logs need `gh api .../jobs/<id>/logs --allow-escape-sequences` ([gate-chain-routing hook; jobs API fallback](../learnings/1793289852768-gate-chain-routing-hook-blocks-triage-resolution-i.md)). A pool the CI analytics frame shows as `busy 0 / total 1` with queued jobs is confirmed in two calls: `actions/runs?status=queued`, then `actions/runs/<id>/jobs` filtered to `status==queued`; the job `labels` (e.g. `Linux,self-hosted,SM80Plus`) name the stuck pool ([confirm a stuck self-hosted pool](../learnings/1793283475940-send-message-refused-on-inherited-heartbeat-thread.md)).

**Do not stand down a stuck-queue escalation on a single fresh frame.** Measured on the Linux SM80Plus GPU (GCP) pool, 2026-11-22: after ~14 h at 4-queued/0-running, one analytics frame showed "busy 1/total 1, 1 running / 4 queued" — looked like recovery; ~9 min later the next frame was back to 4 queued / 0 running and the group had vanished from `runner_groups`. The runner had picked up exactly one job and deregistered (ephemeral/spot). Require **2 consecutive frames with the backlog shrinking** (or the queue fully drained) before standing down — one frame proves only that a runner existed momentarily. The converse is real too: the 11-22 08:45 "Windows Build (GCP)" transient (3 queued / 0 runners, cleared by the next frame) WAS transient, so verify the direction over time, not any single sample ([verify 2+ frames before standing down](../learnings/1795343535043-ci-stuck-queue-recovery-verify-2-frames-before-sta.md)).

On the self-hosted GCP runner VMs, **Google's OS Config agent (`google-osconfig-agent.service`) independently runs background `apt-get update`** (apparently for inventory), competing for `/var/lib/apt/lists/lock` with CI dependency steps. Two hardening steps that do NOT prevent it: masking `apt-daily.timer`/`apt-daily-upgrade.timer`/`unattended-upgrades.service` (the agent invokes apt on its own), and waiting on `cloud-init status --wait` (the collision reproduced ~3.5 min after cloud-init reported done). Confirmed by a controlled reproduction on slang#14504 (diagnostics PR #14523): PID 4196 `/usr/bin/apt-get update` ← google_osconfig. A CI `apt-get` step can hit "Could not get lock" even on a hardened image; the safe resilience is a bounded retry of `apt-get update` (native locking arbitrates), or disabling/masking the agent on build images ([GCP OS Config agent runs background apt-get update](../learnings/1794903358994-gcp-os-config-agent-runs-background-apt-get-update.md)). Ubuntu-hosted runners have the same collision, and the fix must respect APT's locking model: `flock` around `apt-get` does NOT coordinate with APT's native locks (apt takes fcntl/POSIX locks internally, so a flock wrapper only serializes callers that all use it). The coordination-safe fix is a bounded retry of `apt-get update` itself; to fully disable Ubuntu's background APT, mask the apt-daily timers and set `APT::Periodic` all "0" ([flock does not coordinate with APT's native locks](../learnings/1794895552029-flock-does-not-coordinate-with-apt-s-native-locks-.md)).

## Never-ran shapes: queue timeouts and Actions outages

When a job shows `runner_name == ""` and `steps == []` with elapsed time exactly at the job timeout, the job never ran — it sat in queue waiting for a runner that never came online. Rerunning is futile; escalate the missing runner ([Distinguish missing-runner queue-timeout from a real test hang](../learnings/1782605298157-distinguish-missing-runner-queue-timeout-from-a-re.md)).

**The same never-ran shape on GitHub-hosted jobs during an Actions incident is an outage, and there a rerun is the remedy.** During the 2026-10-05 incident, `ubuntu-latest` jobs ended `cancelled` after exactly 15:00-15:02 with `runner_name: ""`, `steps: []` and "log not found"; downstream jobs read `skipped` and the aggregator `failure`. Match the window in https://www.githubstatus.com/api/v2/incidents/unresolved.json, confirm the job shape, then `gh run rerun <run> --failed` once runners pick up jobs. Look-alikes differ: a `timeout-minutes` cancel has a runner and steps, and a `cancel-in-progress` supersede shares one timestamp across the run and the head has moved ([GitHub Actions outage signature](../learnings/1791238163488-github-actions-outage-signature-jobs-cancelled-aft.md)). An outage can also leave a run with no failed job: on 2026-10-07 a `ci.yml` run concluded `failure` with only `filter` (success) in the jobs list; the cause showed only on the HTML run page as an "Internal server error. Correlation ID …" annotation, `gh run rerun`/`gh workflow run` returned HTTP 500, and Actions was `major_outage`. When a run is red with no failing job, check `https://www.githubstatus.com/api/v2/summary.json` first, redispatch from a background loop that waits for `operational`, and push no code ([GitHub CI run with only 'filter' + failure = Actions outage](../learnings/1791386926978-github-ci-run-with-only-filter-failure-actions-out.md)). A third outage shape breaks downloads: GitHub's "anonymous traffic" 504 incidents (11-08 08:34Z to ~12:30Z; 11-09 from 05:15Z). Signatures: `cmake/FetchDXC.cmake:277 file DOWNLOAD cannot compute hash on failed download`, FetchContent `dxc_*.zip`/`optix-dev/archive/*.zip` `HTTP/2 504`, `Setup sccache` `curl: (22) … 504` or `curl: (56)`, and Claude PR Review `setup-bun` "Unexpected HTTP response: 504" then `bun: command not found` (exit 127). Classify as a GitHub outage, not PR code. The nightly MDL Perf run fails in `Build Slang (tip of tree)` in about a minute, so that night has NO timings — read it as neither "regressions fixed" nor "new regression". nv-slang-bot re-runs failed slangpy dispatches (attempt 2/3) which end success, so a `status=failure` list hides them ([Slang CI 11-09: anonymous-download 504s](../learnings/1794213563648-slang-ci-11-09-anonymous-download-504s-mq-only-prs.md)).

## Lost runners and the #13298 fingerprint

**A red GPU job whose log is "not found" usually means the runner died before uploading; the reason is in the check-run annotation.** Read `gh api repos/shader-slang/slang/check-runs/<job-id>/annotations`: on PR #13170 it said "The self-hosted runner lost communication with the server", and `gh run rerun --failed` came back green. If the same test job passed in the sibling config, the diff is almost certainly not the cause. A runner loss can still show a failed step (`sanitizer-linux-clang-x86_64` on 2026-11-06), so a sweep filtering on "no failed step" misses it. The reliable census lists jobs via `/actions/runs/<id>/attempts/<N>/jobs` for every attempt (a re-run hides attempt 1), reads annotations for each failed self-hosted job, and matches "lost communication" (the logs endpoint 404s). That day it found 7 losses on 4 pools at 03:28:58–03:34:55Z, the daily slot of #14294, which had been tracked as Windows-GPU-only; the ~03:25–03:35Z loss recurred on 11-04, 11-06 and 11-07, and on a quiet night only one job is exposed, so only the census sees it ([CI sweep: find lost runners from annotations, not failed steps](../learnings/1793954343982-ci-sweep-read-actions-artifacts-via-proxy-find-los.md)). slangpy's `sanitizers` Linux asan leg on x570 runners instead lost its runner after ~128-129 min on two nights (started 04:10Z, lost 06:18–06:19Z), while a b650 host finished the same leg in 100 min — a duration limit or hang pointing at the x570 hosts, not a clock event ([CI sweep riders: 03:2xZ loss; slangpy asan leg lost after ~128 min](../learnings/1794040923411-ci-sweep-an-approved-fork-pr-ci-run-in-waiting-has.md)). Riders from the same sweep: a `github.ci_failed` whose only failed check-runs are `wait-for-human-priority` + `check-ci` (every real job `skipped`) is the bot-PR priority yield — do nothing; and when the critique gate blocks read-only `gh api .../pulls/...` calls after a local edit, the `mcp__slang-mcp__github_get_pull_request*` tools read the same data ([diagnosing a red GPU job whose log is "not found"](../learnings/1790642965819-slang-ci-diagnosing-a-red-gpu-job-whose-log-is-not.md)).

**One runner-death variant has a constant-duration fingerprint and fires only in the merge queue (#13298).** All 8 claimed occurrences of `test-windows-release-cl-x86_64-gpu-dx / test-slang` dying with "runner lost communication" (7 PRs, 09-11→09-28) re-verified against GitHub: `merge_group` event, **exactly 14m01s**, zero log, job stuck `in_progress`. Every `pull_request`-event failure of the same job in the window (773 CI runs) was an ordinary `exit code 1`, so the merge_group-only split holds. It is distinct from #12388 (Windows GPU `VK_ERROR_DEVICE_LOST`, which recovers and keeps logs). Counting by run-level `status=failure` is sound only once the workflow has no `continue-on-error` ([#13298: confirmed merge_group-only runner-death fingerprint](../learnings/1790629871805-shader-slang-slang-13298-confirmed-merge-group-onl.md)). The cause was memory exhaustion on the old Windows GPU runner image (1 GiB pagefile, 31 GiB commit limit). Merging the per-API Windows GPU jobs into one `-api all` job (#13813, which also set the `test-slang` timeout to 120 min, [merged job measured: Debug 90.8 min, Release 21.5 min](../learnings/1792592295131-merged-windows-gpu-ci-job-api-all-measured-debug-9.md)) does not reopen it: the merged 8-server job ran on the old image until 2026-08-07 with no 14m01s losses ([API-split jobs silently ignore cross-API unit tests](../learnings/1792579623451-windows-gpu-slang-test-api-split-jobs-silently-ign.md)).

## Pool lottery: runner-scoped defects

**A runner-scoped defect makes a rerun a pool lottery, not a futile reland, and the defect can be job-scoped, so "reboot the box" is usually the wrong ask.** When `runs-on:` is a **label set** rather than a named host, dispatch goes to whichever member is free, so with ≥3 members and ≥2 healthy a rerun has good odds. In slang#12322 attempts 1–2 on SLANGWIN5 gave `spirv-val [ 0 / 866 ]` ❌ and attempt 3 on SLANGWIN4 `[ 866 / 866 ]` ✅: the runner attribution was right, the "reruns are futile" conclusion wrong ([a rerun is a pool lottery, not a futile reland](../learnings/1785838439742-runner-scoped-ci-defect-a-rerun-is-a-pool-lottery-.md)). **The defect can be one mechanism on a healthy box:** on SLANGWIN5 in the same window sibling jobs succeeded while only `test-compile-regression`'s SPIR-V validation failed 3/3 — check for a within-window, same-box success on a sibling job before asking to recycle the runner. **Prove attribution with a differential over the runner, not over time:** tabulate every instance of the failing job in the window by `runner_name` per attempt; one box N/N failing with siblings M/M green beats "it failed twice in a row." **Control a pool or host clue against passing jobs:** slangpy's build-pr Windows jobs all carry `Windows, X64, nvrgfx-kernelvm-bridge`, so "every hit ran on the same pool" says nothing; their runner names are `2u1g-b650-<idx>-<creation-ts>` (a fresh VM per job), so tally `<idx>` over ~40 passing jobs first (`runner_name` outlives the logs ~5 days). For slangpy#1223 all four hit indexes were common in the passing pool, so nothing was posted ([control a shared-pool clue against passing jobs](../learnings/1792691453073-before-citing-a-shared-runner-pool-clue-on-a-flake.md)).

## Falcor bridges

**`test-falcor` routes through a self-hosted `falcor-bridge` runner for EVERY PR, so its opaque poller log is universal.** PR #11915 (merged 2026-08-07) made `runs-on: [Linux, self-hosted, X64, falcor-bridge]` + `/opt/slang-ci/run-external-ci` the universal definition, so every failure log is a ~2–4 KB, 3-step stub and the real result lives in an unreachable NVIDIA-internal GitLab pipeline (babysitter Step 0d "defer"). The transferable discipline: before encoding a standing deference rule for an opaque-log class, pull a second example's `runner_name` + `steps` count, since this signature already carried a retracted over-generalization; PR #12919 matched, so the rule was adopted, still gated on a per-occurrence check in case a real (~309 KB, 10-step) log resurfaces ([Falcor test-falcor opaque logs are now universal (class 2)](../learnings/1789618761733-falcor-test-falcor-opaque-logs-are-now-universal-c.md)). Falcor2 has NO automated workflow at all — only the manual `ci-falcor2-perf-bridge-smoke.yml` (workflow_dispatch, runner label shared with Falcor1), whose last run FAILED 2026-09-08 and then went dormant. The Falcor1 nightly succeeding proves the shared bridge runner + entrypoint are healthy, so a future "Falcor2 smoke failure" is a falcor2-target-side issue; the bridge implementation lives outside the repo (runner-local script, docs in the external slang-ci-docs repo), so root-cause from the slang checkout is impossible — route to the bridge owner (jvepsalainen-nv) for a fresh smoke re-run, the only way to get a retained log ([Falcor2 bridge: manual smoke only, dormant](../learnings/1794894179320-falcor2-ci-bridge-manual-smoke-only-failed-2026-09.md)).

## slang-rhi CUDA interop runs on self-hosted GPU runners

slang-rhi's `ci.yml` matrix includes self-hosted `nvrgfx-kernelvm-bridge` runners with same-adapter CUDA that run the interop tests in auto-CI, draft PRs included. The recurring trap (slang-rhi #787/#881/#812) is concluding "compile-only" because GitHub-hosted jobs lack CUDA and `SKIP` the `#if SLANG_WIN64` same-adapter tests. `gh pr checks` names don't reveal which jobs are self-hosted GPU, so a green count is no evidence of execution; when a maintainer gates a ready-flip on "per-test PASSED", read that line in the self-hosted job's log ([slang-rhi CI runs CUDA interop on self-hosted GPU runners](../learnings/1790197692432-slang-rhi-ci-runs-cuda-interop-tests-on-self-hoste.md)).

## Hosted images: ubuntu-22.04/26.04 and toolchain rolls

**GitHub-hosted `ubuntu-22.04` is deprecated (labels removed 2027-04-17), and slang's Linux release binaries build natively on it.** Per actions/runner-images (#14254), `ubuntu-22.04`/`22.04-arm` are deprecated since 2026-09-17 with brownouts in March–April 2027, and `ubuntu-latest` moved 24.04→26.04 over 2026-10-19..11-19. slang's `release.yml:24/30/36` builds the x86_64/aarch64/wasm packages directly on `ubuntu-22.04`, so jammy's glibc 2.35 bounds the shipped floor; 24.04 would raise it to 2.39, a user-facing decision a manylinux container avoids. Measured on v2026.20 with `readelf -V` over every ELF: the highest `GLIBC_` symbol is 2.34 in the unsuffixed archives and 2.17 in the `-glibc-2.27`/`-glibc-2.28` ones; but only unsuffixed `linux-x86_64` ships `lib/libslang-llvm.so`, so "just keep the 2.28 build" silently drops slang-llvm on Linux ([measured glibc floors and slang-llvm packaging, v2026.20](../learnings/1792434028042-slang-linux-release-archives-measured-glibc-floors.md)). In `ci.yml`, `ubuntu-22.04` is only the `LINUX_BUILD_RUNS_ON` fallback; live jobs run on the self-hosted GCP pool, so read a recent run's job labels (DeepWiki was stale). The formatting check pins clang-format via slang-binaries but pip-installs gersemi into the image's system Python (3.12→3.14 on 26.04) ([ubuntu-22.04 is deprecated](../learnings/1790611288369-shader-slang-ci-ubuntu-22-04-is-deprecated-removed.md)). An `ubuntu-latest` job's image shows only in its log header (`##[group]Operating System`, `Image:`, `Version:`), not in `runner_name`/`labels`; a ranged GET (`Range: bytes=0-6000`) on `/actions/jobs/<id>/logs` is cheap enough for all ~1,300 such jobs a day ([CI sweep: snapshot misses jobs in waiting runs](../learnings/1792486355939-ci-sweep-snapshot-misses-jobs-in-waiting-runs-only.md)). Through the OneCLI proxy, non-shader-slang repos such as `actions/runner-images` return 401; read their github.com HTML with WebFetch ([Ubuntu image only visible in the job log header](../learnings/1792399653342-slang-bot-draft-ci-starvation-fix-pr-12738-exists-.md)). The 26.04 switch reached shader-slang on 2026-10-27 between 15:51Z and 17:21Z (38-job header sample). Ubuntu 26 had been validated for slang PR CI in #13288/#13347, excluding scheduled workflows, `regenerate-cmdline-ref`, slangpy and slang-rhi, so search with no date filter before saying "no prep issue". The first breaks landed in slang-rhi: the `sanitizers` nightly `tsan (linux, vulkan,wgpu)` no longer builds (`doctest.h:499` includes `<ciso646>`, a GCC 15 `#warning` fatal under `-Werror`), and the `ci` linux gcc leg fails `cooperative-matrix-query.vulkan` at `CHECK(anySupported)` on lavapipe (Mesa 26.0.8, LLVM 21); slang `check-formatting` passed, and the slang nightly `agentic-tests` job is pinned to `ubuntu-22.04` ([Ubuntu 26.04 reached ubuntu-latest on 10-27; first breakages in slang-rhi](../learnings/1793176888015-ubuntu-26-04-reached-shader-slang-ubuntu-latest-on.md)).

**A hosted-runner toolchain roll beats a commit-range bisect as the FIRST hypothesis for a link-time/optimizer crash at a trivial source line.** The 2026-11-20 nightly release CI failed on `release (windows, release, aarch64)` with MSVC `C1001: Internal compiler error` at a trivial `mask |= flagBits[ii]` loop during link.exe's ARM64 `/LTCG` pass — root cause a runner-image roll, not code: the `windows-latest` image `windows-2025-vs2026` rolled 20261103.298.1 → 20261116.315.1 between the last green job (MSVC 14.51.36231) and the red (14.52.37025), `release.yml` doesn't pin the MSVC toolset, and the windows-x64 leg passed on the SAME new image (isolating the crash to ARM64 cross-link codegen). Recipe for any hosted-runner build failure: download both the red and last-green job logs, grep the `##[group]Runner Image` block for `Image:`/`Version:` and the vcvars dump for `VCToolsVersion` — an image roll + version bump between adjacent runs explains the crash without a bisect. Maintainer context: the repo already pins MSVC 14.43 in `sccache-populate.yml` and has `test-msvc-update`/`windows-msvc-version` branches ([Slang 11-20 release-CI red: windows-latest image roll bumped MSVC](../learnings/1795138744970-slang-11-20-release-ci-red-windows-latest-image-ro.md)).

## Merge-queue removals: queue waits and runner drops

**`checks_timed_out` from a runner-pool queue wait.** `test-linux-release-gcc-x86_64-sm80 / test-slang` runs on the self-hosted SM80Plus pool and normally waits 0–14 min. On 2026-10-12 #13371's merge-group run had it QUEUED 143 min; the PR was removed as `checks_timed_out` and the group run later went green. Measure the wait from `actions/runs/<id>/jobs` (`created_at` vs `started_at`) before blaming code or LLVM; re-derive evictions from `RemovedFromMergeQueueEvent` (the wake payload's `evicted` list can miss them). The bot cannot requeue (`gh pr merge <n>` and GraphQL `enqueuePullRequest` were refused), so a maintainer must ([merge-queue checks_timed_out can be a self-hosted sm80 queue wait](../learnings/1791873086822-merge-queue-checks-timed-out-can-be-a-self-hosted-.md)). Both infra evictions hit #14111 on 2026-11-03 and left master idle 11+ h behind green nightlies. First, `failed_checks` with every status green: the only failed job had an empty step list, a 404 log and the "runner lost communication" annotation ([eviction with all statuses green = runner drop](../learnings/1793693100985-merge-queue-eviction-with-all-statuses-green-can-b.md)). Then `checks_timed_out` at 2 h: the sm80 job was created 08:31Z and started 11:11Z, passing in 8 min against that day's 20–52 min baseline ([checks_timed_out from a 2h40m sm80 queue](../learnings/1793707497432-merge-queue-checks-timed-out-can-come-from-a-linux.md)). Both are infra findings: report the PR for a human re-enqueue and the pool for a check, and file no code-regression issue.
