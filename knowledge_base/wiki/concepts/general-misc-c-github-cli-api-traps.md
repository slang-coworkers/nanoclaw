## TL;DR

The GitHub `gh` CLI and REST/GraphQL API are riddled with instruments that **return a clean, plausible, wrong answer** — usually one that agrees with the conclusion you were trying to confirm. The recurring shape: *broken and empty look identical*, and the failure is silent.

- **`gh api <path> -f key=value` on a GET path sends a POST → 404.** A 404 is a statement about your request, not about the world. Use `-X GET`, or put params in the URL (`?per_page=100`).
- **The bare list path truncates to the default page (30).** A count without explicit `per_page` is a *page*, not a *population*. Cross-check `.jobs|length` vs `.total_count`.
- **`gh api --jq` writes the error JSON to *stdout* on 4xx.** So `[ -z "$x" ]` emptiness guards are unreachable dead code — validate the *shape* (`grep -qE '^[0-9]+$'`), not non-emptiness. `2>/dev/null` hides the human half while the JSON still lands.
- **A bot author filter without the `[bot]` suffix matches nothing** and reads as "clean."
- **GraphQL `timelineItems(itemTypes:[...]) { totalCount }` ignores the filter** — count `nodes`, never `totalCount`.
- **GitHub Actions echoes the entire `run:` block into the log.** Grepping a marker that is also a literal in the workflow YAML measures the *source*, not behaviour.
- **The Actions API can serve a stale, internally-consistent index** during an incident — `total_count` differing across two reads of one query is the tell.
- **A background `--paginate` job drains the GraphQL budget** (separate from REST) and makes every later query fail-open to "0".
- Universal guard: **run a must-hit control that varies the suspected cause, not just the target** — and never generalize from a repeated failure (12 identical 404s were one bug).

## The master pattern: a 404/empty/zero is a claim about your request

A single insight unifies most of these: **an instrument whose failure mode is indistinguishable from its negative result cannot be the sole source of a value you act on.** Ask *what does this print when it cannot tell?* If the answer is "something indistinguishable from good news," fix the instrument before trusting one reading.

`gh api -f` is the archetype. `-f key=value` (also `-F`/`--raw-field`) is sent as a **request body**, which switches the method to POST; on a read-only Actions path GitHub has no POST route and returns `404 Not Found` — byte-identical to "the resource has no data." One investigator ran 12 cells this way, got 12 × 404, and read it as "no build/test jobs exist" — exactly the conclusion being sought. The fix is `-X GET` with `-f`, or query-string form (`?per_page=100`). What broke the case open was a must-hit control 404'ing on a run known to have data, then `gh api -i` returning `HTTP/1.1 200 OK` with `X-Ratelimit-*` headers present — proving the credential was fine and the *command form* was wrong. See [gh api -f on a GET path sends a POST and 404s: a whole matrix of false absences with a passing-looking shape](wiki/learnings/1786002146982-gh-api-f-on-a-get-path-sends-a-post-and-404s-a-who.md) and [`gh api <path> -f per_page=100` sends a POST and 404s — and the bare path silently truncates a census to 30](wiki/learnings/1786002484341-gh-api-path-f-per-page-100-sends-a-post-and-404s-a.md).

That same session produced a **retracted capability-negative** worth its own warning: an earlier version claimed a per-path proxy capability gap (`commits/<sha>/check-runs` "unreachable from my edge"). False — it was the `-f per_page=100` defect again, verified on three edges to return `total_count=304`. A capability-negative is the one error class with *no failure signature*: readers comply by not attempting the endpoint, which logs nothing. Before attributing a failure to your environment, re-run it in the plainest possible command form; and the discriminating control must **vary the suspected cause** — a control run in the same broken `-f` form 404'd alongside the target and *confirmed* the false conclusion.

## A page is not a population; a count is a reading

GitHub list endpoints answer a narrower question than their name implies. A `merge_group` CI failure rate built from repo-wide `/actions/runs` (whose 100-item pages interleave *all* workflows) gave a published 48.7% against an honest 28.5% (140/491) — the oldest row *in that page* was misread as a retention floor. The same 43-run slice measured 48.7% then 46.3% minutes apart. Rules: derive a rate from `total_count` on the **narrowest endpoint that answers the question**, state the denominator, and ship every rate with its **window (bounds + N) and a measured-at timestamp** or it gets quoted later as a constant. Never infer retention/age-floors from the last row of a page. See [A page is not a population — GitHub list endpoints, rates, and partial fetches](wiki/learnings/1786008219569-a-page-is-not-a-population-github-list-endpoints-r.md).

`--paginate` compounds this: a **401 mid-stream** injected `{"error":"app_not_connected"}` into counted output where `uniq -c` rendered it as a datum; the walk also stopped at 100 of `total_count: 122`. Guard with per-page `jq -e '.workflow_runs'` and grep the rows for error keys, or prefer an explicit `page=N` loop when a figure will be published — [gh api --jq writes the error object to stdout on 4xx, so emptiness guards are unreachable dead code](wiki/learnings/1786051213646-gh-api-jq-writes-the-error-object-to-stdout-on-4xx.md).

`/actions/workflows` itself **paginates at 30**, so a name filter (`jq 'select(.name=="CI Health")'`) on a repo with 82 workflows silently finds nothing on page 1 — byte-identical to a genuine absence, nearly read as "the workflow doesn't exist." Always pass `?per_page=100` and check `.total_count` against the rows you got before concluding a workflow (or run, issue, release, tag) is missing. Ask "if it HAD been there, would this call have returned it?" This is the same *exhaustion-looks-like-success* shape: the stopping condition (ran out of page-1 rows) and the success condition (searched everything) produce identical output. See [GitHub /actions/workflows paginates at 30 — a name filter on page 1 reads as "no such workflow"](wiki/learnings/1786036886504-github-actions-workflows-paginates-at-30-a-name-fi.md).

## Error JSON to stdout: emptiness guards are dead code

`gh api --jq` prints the API **error object to stdout** on failure, so the captured value is simultaneously a failure signal and plausible-looking data. `[ -z "$x" ] || [ "$x" = "0" ]` never fires because the value is `{"message":"...","status":"422"}` — non-empty and not "0". Capturing into `$( )` discards `rc`, throwing away the one honest signal. **Validate the shape you expect** (`grep -qE '^[0-9]+$'` — the error object fails the regex), check `rc` separately, and write a control-of-the-control: point the probe at a bogus id and confirm the "probe broken" branch actually fires. Detailed in [gh api --jq writes the error object to stdout on 4xx, so emptiness guards are unreachable dead code](wiki/learnings/1786051213646-gh-api-jq-writes-the-error-object-to-stdout-on-4xx.md).

This is exactly the mechanism behind a **self-writing state latch**: a `schedule_task` guard stored a fingerprint to suppress repeat wakes, but its failure path (any `gh` API error → empty stdout → every downstream `jq` errors → `fp="|human=0"`) *wrote the latch* with a degenerate value, producing 8 consecutive 20-minute wakes on a PR that had not moved. Any probe feeding a stored comparison value must make failure distinguishable from a negative result and **leave the stored value untouched when it cannot measure** — test by *injecting* failure (a stub `gh` earlier on `PATH`), not by repeating the happy path, and keep a positive control (a genuinely-different fingerprint must still wake). See [A state-latch its own failure path can write is not a latch (gh --jq prints errors to stdout)](wiki/learnings/1786015919170-a-state-latch-its-own-failure-path-can-write-is-no.md).

## Filters that silently match nothing, and aggregates that ignore the filter

- **Bot author filter without `[bot]`.** Every GitHub App identity carries a `[bot]` suffix in `user.login`; `select(.user.login=="nv-slang-bot")` returns 0 and reads as "nothing to correct." Prefer `startswith("nv-slang-bot")` or `.user.type=="Bot"`, and pair every null result with a positive control proving the filter can return a hit. [Bot author filters silently match nothing without the [bot] suffix](wiki/learnings/1786031677274-bot-author-filters-silently-match-nothing-without-.md)
- **`user.type` is not a person-test.** board-sync automation posts as `type=User`. A field's name is not what writes it.
- **GraphQL `totalCount` on a filtered connection ignores `itemTypes`.** `timelineItems(itemTypes:[REMOVED_FROM_MERGE_QUEUE_EVENT]){totalCount}` returned 18 while `nodes` (correctly filtered) was empty — a merge-queue eviction sweep phrased as "does this PR have removal events?" would manufacture 18 evictions on a never-evicted PR. Enumerate `nodes` and count them yourself; request `totalCount` *and* `nodes` together so a non-zero count beside an empty list announces the defect. [GraphQL timelineItems.totalCount ignores the itemTypes filter](wiki/learnings/1786047790242-graphql-timelineitems-totalcount-ignores-the-itemt.md)

## The `run:`-block echo: grepping source, not behaviour

GitHub Actions writes every line of a `run:` block into the job log wrapped in ANSI `ESC[36;1m … ESC[0m` *before* executing it. So grepping a job log for any string that also appears in the workflow YAML — including inside an `echo` in a branch that never fired — matches on **every** run of that job. Two independent agents hit this in one hour (an 11/11 and a 5/5 census), and one had already published a `5 of 5` from it. The deceptive text sits inside a log you correctly fetched (right run id, right job, rc=0), so no byte-size or exit-code guard catches it — only the *role* of the line is wrong.

Fixes: (1) pick a marker that only appears in program output, never in source (e.g. a Python script's print vs a YAML literal); (2) filter echoed lines (`grep -av $'\033\[36;1m'`, or exclude `##[group]`); (3) prove the filter discriminates with a **two-cell control** — one run per branch, require the readings to be *inverse*, and assert the impossible cell ("both markers real") is empty. Cheapest tell: `echo "` inside the matched line means you are reading source. See [GitHub Actions logs echo the run: script — ESC[36;1m lines are source, not output](wiki/learnings/1786004519214-github-actions-logs-echo-the-run-script-esc-36-1m-.md), [GitHub Actions echoes the run block into the log — grepping a marker that is also a literal in the workflow source measures the SOURCE, not behaviour](wiki/learnings/1786025727407-github-actions-echoes-the-run-block-into-the-log-g.md), and [GitHub echoes the run: block into job logs — grepping a workflow's own strings measures source, not behaviour](wiki/learnings/1786025881019-github-echoes-the-run-block-into-job-logs-grepping.md). A companion caution: **don't report a clean instrument and a dirty one in one breath** — an alternation ("5/5 `IS_THROTTLED_BOT: false` / `Not a throttled bot run`") inherits its weakest member's credibility and forces a public correction that reads as a retraction of the finding itself.

## Stale/lagged API snapshots and budget exhaustion

During the 2026-08-06 Actions outage, `GET .../actions/runs?event=schedule` returned a **17-day-old row as "newest"** — correctly sorted, self-consistent, no error field. Varying only `per_page` on the identical URL exposed two different backend snapshots (`total_count=10506` vs `13572`). **The cheap detector is `total_count`** — a differing count across two reads of one query means two different snapshots; print and compare it, don't just read `.workflow_runs[0]`. Re-read any *surprising* API result before building a finding on it — the monitoring substrate degrades along with the monitored system, silently *toward plausible*. [GitHub Actions API can serve a stale, internally-consistent index — total_count is the tell](wiki/learnings/1786058258089-github-actions-api-can-serve-a-stale-internally-co.md)

REST and GraphQL have **separate rate budgets**. A background `gh api graphql --paginate --slurp` drained GraphQL to zero while REST stayed at 3432/6000; the idiom `... 2>/dev/null | jq -r '...evictions=\(.timelineItems.nodes|length)'` then reports `evictions=0` with a clean exit — indistinguishable from "never evicted," the worst fail-open for a merge-queue babysitter. Never leave a `--paginate` job in the background while you work the same API; probe the budget you are about to spend (`gh api graphql -f query='{rateLimit{remaining}}'`); make the failure loud with `set -o pipefail`; cross-check a load-bearing zero on a second transport (REST `issues/<n>/timeline` exposes the same events on a separate budget). A semantic error (`not authorized to push`) is proof of life; only `RATE_LIMIT`/`401` invalidate the read. [A background `gh api graphql --paginate` job can exhaust the GraphQL budget and make every later eviction query fail open to "0 evictions"](wiki/learnings/1786012445815-a-background-gh-api-graphql-paginate-job-can-exhau.md)

## Merge-style and reference resolution

- **`git merge-base --is-ancestor <pre-squash branch head> master` gives a false negative on a squash merge.** A squash mints a new single-parent commit, so the branch's commits are never reachable from master — "not an ancestor" reads exactly like "my work was lost." Detect the merge style first (`git rev-list --parents -n1 <sha>`: 1 parent = squash/rebase), or prefer a **content check** (`git grep -c '<fix symbol>' origin/master -- <file>` with a must-hit control). Two instruments disagreeing is information about an instrument, not licence to pick the convenient one. [git merge-base --is-ancestor gives a FALSE NEGATIVE on a squash-merged PR — the pre-squash branch sha is never an ancestor of master](wiki/learnings/1786014389424-git-merge-base-is-ancestor-gives-a-false-negative-.md)
- **A squash-only repo cannot auto-close a subsumed PR.** One API call (`gh api repos/O/R --jq .allow_squash_merge`) decides it; if only squash is allowed, a branch tip is never an ancestor and a `Fixes #N` on the subsumed PR never fires. Phrase the finding as "structurally impossible," not "contingent on a mechanism I did not measure" — the second reads as "probably fine." [A squash-only repo cannot auto-close a subsumed PR: check merge settings before calling closure contingent](wiki/learnings/1786044919627-a-squash-only-repo-cannot-auto-close-a-subsumed-pr.md)
- **`event=merge_group` returning 0 does not mean a workflow skips the queue.** GitHub pushes the merge-queue ref under `event=push`, so a workflow declared `on: [push, pull_request]` runs there as `push` (0 `merge_group`, 1416 `push`). Census by **`head_branch`** (`gh-readonly-queue/*`), not by `event`; and read the `on:` block verbatim from `raw.githubusercontent.com`. A `head_branch=master` on a `workflow_run` row is an artifact — workflow_run always reports the default branch. [event=merge_group returning 0 does NOT mean a workflow skips the merge queue](wiki/learnings/1786033078439-event-merge-group-returning-0-does-not-mean-a-work.md)
- **`pull_request` workflows resolve from the PR *merge commit*, not the base branch** — so a `.github/workflows/*.yml` fix committed in the PR branch takes effect in that same run. The free, definitive discriminator: did the new step appear in the job's step list? A step that exists only in the head cannot run if the workflow came from the base. A wrong mechanism that licenses *inaction* ("can't fix this from here") is more expensive than one that licenses action. [pull_request workflows resolve from the PR merge commit, not the base branch](wiki/learnings/1786026455269-pull-request-workflows-resolve-from-the-pr-merge-c.md)
- **A bare `#N` across sibling repos mislinks to a real page**, not a 404, because issue-number spaces overlap — and it is the default outcome, strictly worse than a 404 (which announces itself). Always fully-qualify cross-repo references (`owner/repo#num`); naming the repo in adjacent prose does not stop the auto-link. Note `gh pr view 810 -R O/R` can 404 (it's an *issue*, not a PR) while the human clicking the link hits a real page — the pulls and issues endpoints diverge. [A bare #N across sibling repos MISLINKS to a real page — worse than a 404, and it is the default](wiki/learnings/1786023686394-a-bare-n-across-sibling-repos-mislinks-to-a-real-p.md)

## git push --dry-run and App-token auth probes

`git push --dry-run` negotiates refs but never sends the pack, so the server never evaluates write permission — on a public repo it prints `[new branch]` and exits 0 whether or not you can push. Ask about permission directly: `gh api repos/<owner>/<repo> --jq '.permissions'`. And two App-token probes cry wolf: `gh auth status` reports the token invalid (false — REST works), `gh api user` returns 403 (expected — App tokens have no user context); the working liveness probe is `gh api graphql -f query='query{viewer{login}}'`. A branch living in the upstream repo does not imply you can push to it. [git push --dry-run is a dud positive: it reports success with push:false](wiki/learnings/1785984172890-git-push-dry-run-is-a-dud-positive-it-reports-succ.md)
