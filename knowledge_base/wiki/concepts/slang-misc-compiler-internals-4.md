## slang#12069: Endianness Fails Loudly, Pointer Size Fails Silently (2026-07-12 fold)

In `include/slang.h`, endianness and pointer size are both derived from an architecture whitelist (`SLANG_PROCESSOR_X86_64|ARM_64|POWER_PC_64`), but their failure modes are ASYMMETRIC. Endianness has a guard (`#if ((SLANG_BIG_ENDIAN | SLANG_LITTLE_ENDIAN) == 0) #error`) so an unlisted arch fails the build loudly; pointer size has NO such guard — `SLANG_PTR_IS_32 = (SLANG_PTR_IS_64 ^ 1)`, so on any 64-bit arch NOT whitelisted (RISC-V rv64, LoongArch64, s390x, MIPS64), `SLANG_PTR_IS_32` silently evaluates to 1 → `SlangInt`/`SlangUInt` become 32-bit on a 64-bit target → public-ABI/struct-layout corruption with no error. That silent miscompile is the load-bearing bug, not the cosmetic "use compiler macros" ask. Verified: gcc & clang predefine `__BYTE_ORDER__`, `__SIZEOF_POINTER__`, `__LP64__`; `__POINTER_WIDTH__` is clang-only; MSVC provides none (use `_WIN64`). The detection block is the single source of truth — copied verbatim into generated C++/CUDA host preludes and consumed by core.meta.slang/nvrtc/slang-llvm — so don't remove the whitelist, only augment the derivation and add the symmetric pointer-size `#error`. Triage: Bug / low / P3 (latent — no supported target affected); hybrid fix (guards first, then compiler-macro-primary + whitelist fallback + `sizeof(void*)` cross-check), draft held for maintainer sign-off on the public ABI header ([slang#12069 endian/ptr whitelist — pointer-size fails silently, endianness fails loudly](wiki/learnings/1783835875827-slang-12069-endian-ptr-whitelist-pointer-size-fail.md)). A related C-ABI-layout pitfall when appending a field to a *versioned* struct chain via inheritance (e.g. `struct Req_1_3 : public Req_1_2 { newFields; }`, as in PR #12206): a class with a public base AND its own data members is **not standard-layout**, so `offsetof(Req_1_3, field)` is only conditionally-supported and FAILS under `-Werror` (`-Winvalid-offsetof`) — do cross-version downgrades by base-slicing (`static_cast<const Base&>(derived)`), never `offsetof` or raw byte reads of the base prefix (base-at-offset-0 is a real-toolchain ABI property, not a C++ guarantee). Such a class IS still an aggregate in C++17 (public base allowed) and stays trivially copyable if no user special members are added, so assert the relationship with `std::is_base_of<B,D>` + `std::is_trivially_copyable_v<D>` — `is_trivially_copyable` + `sizeof(D) > sizeof(B)` do NOT prove B is a byte-prefix of D ([C++ versioned-struct inheritance: non-standard-layout ≠ non-aggregate; use base-slicing not offsetof](wiki/learnings/1784851897134-c-versioned-struct-inheritance-non-standard-layout.md)).

## Exponential Compile Time With Generic Nesting Depth — Missing Substitution/Conformance Memoization (#12100/#12103)

Nested generic calls `wrap(wrap(...wrap(x0)...))` (where `Wrapper<T> wrap<T:IModel>(T v)` and `struct Wrapper<T:IModel>:IModel`) grow compile time *exponentially* in nesting depth (REPRODUCED on ToT @3eeda847c debug slangc: depth 8≈3.1s → 12≈11.7s → 14≈72s → 16 timeout; same class for `typealias Pair` chains and associated-type `T.Next.Next...` chains). Root cause (hypothesis — code trace + DeepWiki, NOT profiled): NO memoization of the substitution/conformance work each level redoes for all inner levels. The type-check flow per call (`ResolveInvoke` slang-check-overload.cpp:3375 → `inferGenericArguments` :2866 → `trySolveGenericArguments` slang-check-constraint.cpp:3406 → `buildSubstDeclRef` :2777) re-descends and re-substitutes the whole `Wrapper<Wrapper<...>>` tree at every layer: `DeclRefType::_substituteImplOverride` (slang-ast-type.cpp:152-213) and `GenericAppDeclRef::_substituteImplOverride` (slang-ast-decl-ref.cpp:482) do not memoize; `GenericAppDeclRef` IS interned via `ASTBuilder::getOrCreate` but the `ValKey` keys on operand POINTER identity, so structurally-identical substituted types at different levels are pointer-distinct and miss the cache; and the subtype-witness cache (`SharedSemanticsContext::m_mapTypePairToSubtypeWitness`, slang-check-inheritance.cpp:95-137) is GENERATION-GATED (only caches when both endpoints' inheritance-info generations are non-zero) so mid-computation substituted types bypass it and `Wrapper<T>:IModel` is re-proven per level → multiplicative blowup. **Distinct** secondary facet: plain non-generic `f(f(...f(x)...))` at ~200 deep hits `E39997 maximum type nesting level exceeded` — that is `kMaxTypeNestingDepth=128` (slang-check.h:21), a type-STRUCTURE traversal guard (not a call-depth counter), fine at 128. The >80x v2026.5→v2026.8 regression (constant-factor ~7x jump at depth 16) primary suspect (in-window VERIFIED via `git merge-base --is-ancestor`, NOT profiled): **#9808 "Refactor auto-diff implementation"** (`45ccce9a3`) — the largest front-end change in the 111-commit range, touching every per-level hot-path file; decisive proof step is a first-parent bisect `45ccce9a3^` vs `45ccce9a3` on the depth-16 repro. Disposition: reporter jvepsalainen-nv (NVIDIA contributor) self-assigned and authors PR #12086 (the compile-perf depth-axis benchmark suite this feeds), so parent parked HOLD-for-assignee, no fixer dispatch (high-blast-radius core-substitution refactor + unprofiled regressor + owner-driven workstream; same pattern as #12096). Repo has a native **Performance** Issue Type (`IT_kwDOAb2kZs4BlAhg`) — use it for compile-time/runtime perf bugs; GraphQL `updateIssue`/`addLabelsToLabelable`/`addComment` mutations work even when a bot's REST write 403s, but `addLabelsToLabelable` needs the label IDs INLINE in the query string ([slang#12100 exponential generic-nesting compile time: missing substitution/conformance memoization; >80x regression from #9808](wiki/learnings/1784054268864-slang-12100-exponential-generic-nesting-compile-ti.md)). The follow-up guard-workloads issue #12103 (adds depth-axis workloads to the compile-perf tracker to guard #12100's regressions) is doubly not-for-a-fixer: (1) self-filed AND self-assigned by the same owner, (2) a hard merge-order block — it stacks on the still-OPEN PR #12086 and edits the SAME files (`tools/compile-perf/lib/manifest.py` + `lib/workloads.py`), so it must land AFTER #12086 or conflict. Triage value-add when you can't/shouldn't fix: validate the proposed design against the live schema — the compile-perf workload schema (`manifest.py:28-78`, `WorkloadSpec`) has the invariant `default_size` MUST be in `sweep_sizes` (manifest.py:539-541); all 5 proposed workloads pass, turning a bare park into an actionable green light. Confirm a merge-order dependency concretely with `gh pr view <n> --json files --jq '.files[].path'` rather than asserting it, and don't assume a referenced workload is in-tree — the three #12086 workloads (`generic_nesting`/`generic_nesting_eval`/`interface_depth`) are ABSENT on master, only added by the open PR ([slang#12103 compile-perf depth-workload follow-up — hold for self-assigned owner, merge-blocked on #12086](wiki/learnings/1784056143534-slang-12103-compile-perf-depth-workload-follow-up-.md)).

The #12100 memoization fix (PR #12106, "Memoize shared Val and type DAG traversals", commit c8d02ae59) that killed the exponential deep-generic blowup then produced its own ~10-15% flat SHALLOW-generic regression (#12139). The mechanism explains the trade-off directly: `SubstitutionCache` (`slang-ast-substitution.h:16-60`) is a `Dictionary<Key,Result>` heap-constructed fresh per top-level substitution op, with a `tryGet` + on-miss `add` (two hashes) per node. On a TREE (each Val visited once) it is 100% miss → pure overhead (per-op Dictionary alloc + double-hash + wasted insert); only on a SHARED DAG (the #12100 shape, inner type recurring as both generic-arg and conformance-witness) does it convert exponential to linear. Reviewer audits confirmed the memo is semantics-preserving, so gating/shrinking the cache is always correctness-safe — a pure speed/space trade (fix directions: inline-buffer-cache-with-Dictionary-promotion, pool/reuse the cache across ops, or a *work*-based — not static-depth — guard; static depth risks re-introducing #12100 on a shallow-looking heavily-shared DAG). The reusable methodology lesson: a perf confound that "can't be separated from the aggregate data" is often separable by CODE-PATH analysis — the reporter worried #12139's `interface_depth` +40% outlier was inseparable from co-window PR #12052 (`-specialize` conformance visibility), but reading `tools/compile-perf/lib/manifest.py` shows `interface_depth`/`generic_nesting`/`generic_nesting_eval` all use `mode="module"` while only `rt_renderer_specialize`/`api_specialize` invoke `IEntryPoint::specialize` — the SOLE path #12052 touches. A commit gated behind a rarely-used entry point cannot tax workloads that never hit it, so #12052 is exonerated and the outlier is #12106's territory: check the workload's invocation MODE, not just its name ([slang#12139 — resolving a two-commit perf confound by workload trigger-path (#12106 memo vs #12052 -specialize)](wiki/learnings/1784270455318-slang-12139-resolving-a-two-commit-perf-confound-b.md)).

## Flipping the Default `-g` Level: Textual-Codegen Fallout + a Masked Strip Gap (2026-07-20 fold)

slang#11682 flips the DEFAULT debug level `None`→`Minimal`, and the blast radius is far wider than "adds SPIR-V debug names." **(1) It silently changes TEXTUAL codegen (folding), not just SPIR-V.** At Minimal+, `maybeEmitDebugLine` emits `IRDebugLine` insts through function bodies; `kIROp_DebugLine.mightHaveSideEffects()` returns true, so `shouldFoldInstIntoUseSites` refuses to fold across it and the C-like emitter materializes temporaries — folded chains become multi-temp assignments across HLSL/GLSL/CUDA/Metal. Sweep the non-SPIR-V goldens too ([slang debug -g level silently changes TEXTUAL codegen (folding)](wiki/learnings/1784443119965-slang-debug-g-level-silently-changes-textual-codeg.md)). **(2) It exposes a masked strip-condition gap.** `slang-emit.cpp` strips debug info only when the level `== None`, though its comment claims two conditions (incapable target OR `-g0`); while the default *was* `None` every compile hit the strip, hiding the missing "debug-incapable target" arm. Once Minimal is the default, `IRDebugLine` survives into targets that can't consume it, producing 19 VM/bytecode HARD crashes (`slang-emit-vm.cpp` default arm is `SLANG_UNIMPLEMENTED`) plus ~32 textual golden diffs. The right predicate is `!isSPIRV && !isCPUTargetViaLLVM` (both SPIR-V and CPU/LLVM genuinely express debug info — a bare `!isSPIRV` wrongly strips DWARF). Meta-lessons: a default enum value can mask a code-vs-comment gap for years, and a hard `SLANG_UNIMPLEMENTED` default arm weaponizes any newly-surviving inst class into a crash ([flipping default -g exposes a masked strip-condition gap → VM crashes + codegen churn](wiki/learnings/1784443743816-slang-flipping-default-g-exposes-a-masked-strip-co.md)).

## loadSerializedModuleContents Dep-Loop Content Is Dead Weight; Up-to-Date Check Is Independent (2026-07-22 fold)

Triaging slang#9400 (module serialization / file-dependency tracking) @HEAD 6a244fee2: the dependency-loading loop in `Linkage::loadSerializedModuleContents` (`slang-session.cpp:2248`) eagerly `loadSourceFile`s (materializes full text) every dep of a loaded `.slang-module`, but on the load path that content is DEAD WEIGHT — verified empirically (a module compiles to GLSL fine with the original `.slang` source deleted). Only dependency PATHS feed real consumers: the load-path digest is chunk-copied not recomputed, and the `UseUpToDateBinaryModule` staleness check `isBinaryModuleUpToDate` does its OWN loadSourceFile+digest loop reading the serialized RIFF chunk — it does NOT read the in-memory list the loop populates, so removing the loop would NOT break up-to-date checking. CRITICAL DISTINCTION a code-reader subagent got wrong: `moduleChunk->getFileDependencies()` (serialized RIFF chunk, always present) ≠ `module->getFileDependencies()` (in-memory list from the loop) — always disambiguate `moduleChunk->` vs `module->`, and verify load-bearing subagent claims by reading the two call sites yourself. (Missing-snippet from precompiled modules — `error 36107` prints `(0)` — is a SEPARATE mechanism: deserialized SourceViews are built from empty-content SourceFiles, so the loaded content never reaches diagnostics.) Maintainer tangent-vector called this whole path/source-loc subsystem "rotten to its core" and wants a first-principles redesign → parked for jkwak-work, no auto-fixer ([slang#9400: loadSerializedModuleContents dep-loop content is dead weight; up-to-date check is independent](wiki/learnings/1784654116315-slang-9400-loadserializedmodulecontents-dep-loop-c.md)).

## Front-End Guard/Cast Bugs: Property Accessors, #language, and the Lexer Continuation Byte (2026-07-24 fold)

Three front-end declaration/lexing bugs triaged this day share a "the check is one layer off / too narrow" shape. A `[Differentiable]` (or `[TreatAsDifferentiable]`) on a struct **property** accessor segfaults slangc with no diagnostic (`#12210`), while a `[Differentiable]` *subscript* accessor is fine — so it's purely front-end header checking, not autodiff/IR. Root cause: `getFuncType` (`slang-syntax.cpp:1122`) branches `if (as<SubscriptDecl>(parent) || as<PropertyDecl>(parent))` then casts `parent.as<CallableDecl>()`, but `SubscriptDecl : CallableDecl` (has index params — the reason the branch exists) whereas `PropertyDecl : ContainerDecl` is NOT a CallableDecl. The load-bearing lesson: **`DeclRef::as<U>()` does NOT validate the target type** — it rewraps the same `declRefBase` and returns a non-null DeclRef even when the underlying decl isn't a `U`, so `if (declRef.as<CallableDecl>())` is a no-op guard; use `as<U>(rawDecl)` or `declRef.is<U>()` to actually test. Regression from PR #5922 which added the `|| as<PropertyDecl>` arm; fix restricts the param-prepend to `SubscriptDecl` only ([Differentiable property accessor segfaults getFuncType — PropertyDecl is not a CallableDecl](wiki/learnings/1784883686572-differentiable-property-accessor-segfaults-getfunc.md)). Similarly, `#language glsl <n>` (`slang-preprocessor.cpp` `HandleLanguageDirective`) validates the version token only via `isValidSlangLanguageVersion`, never `isValidGLSLVersion`, so `#language glsl 460` errors E15207 while `#language glsl 2025` passes and then silently re-overrides the language back to Slang — the correct GLSL selector is `#version <n>`; the issue body's "PR #X will take care of this" was a **dedup gate**: checking the referenced PR's diff confirmed it net-satisfied the complaint (verdict = tracked-by-PR, no separate dispatch) ([#language glsl version mis-validates against Slang versions (not isValidGLSLVersion)](wiki/learnings/1784916319659-language-glsl-version-mis-validates-against-slang-.md)). And the lexer silently accepts a lone UTF-8 **continuation byte** (0x80–0xBF, no lead byte, `#12222`) — but the instinct "the decoder doesn't handle it" is wrong: `getUnicodePointFromUTF8` already rejects a leading continuation byte; the bug is the branch guard `isUtf8LeadingByte` (`0xC0–0xFF` only) at `slang-lexer.cpp:267/:350` being too narrow, so the byte never enters the (correct) decode branch and falls through to identifier lexing. Fix at the guard (the producer of the branch decision), not the already-correct decoder nor the consumer; broadening to `isUtf8LeadingByte(c) || isUtf8ContinuationByte(c)` lets the existing E10006 emission fire — the general method being "when triaging 'X isn't diagnosed', check whether the low-level utility already rejects X and it's a routing/guard gap one layer up" ([Slang lexer lone-continuation-byte gap is a guard-narrowness bug, not a decoder gap](wiki/learnings/1784917194691-slang-lexer-lone-continuation-byte-gap-is-a-guard-.md)).

## Reuse canonical immutable-location / opaque-type predicates, don't hand-roll (2026-07-27 fold)

When a fix must recognize "address-only / non-copyable / immutable-location" types across the whole class (ParameterBlock, ConstantBuffer, read-only StructuredBuffer/ByteAddressBuffer, read-only textures, samplers, and structs transitively containing them), reuse the existing canonical predicates rather than writing a new switch: `isPointerToImmutableLocation(IRInst*)` (`slang-ir-util.cpp:3105`, walks element-access chains and correctly excludes RW-alias + the OptiX-SBT case #10188) and `isOpaqueType(IRType*, IRType**)` (`slang-legalize-types.cpp:257`, recursive/cycle-safe, covers structs transitively containing resources). On slang#8002, `slang-ir-transform-params-to-constref.cpp:186 isLoadFromImmutableAddress` hand-rolls a narrow switch (ConstantBuffer/BorrowInParam/ParameterBlock only) that predates/duplicates `isPointerToImmutableLocation` — swapping it in gets full coverage in one source of truth. A subtle related mechanic: `lowerGlobalShaderParam` wraps a global param as `LoweredValInfo::simple(irParam)` even though the comment says the SSA value is a *pointer*; `tryGetAddress` has no `Flavor::Simple` case, so a global resource/PB param never presents as a Ptr and forces the by-ref temp path, emitting a bare `store(v, %g)` that `undoParameterCopy` (which matches `store(v, load(orig))`) misses [slang: reuse isPointerToImmutableLocation / isOpaqueType for constref copy-elision (do not hand-roll)](wiki/learnings/1785194352818-slang-reuse-ispointertoimmutablelocation-isopaquet.md).

## Slang C/COM API has TWO ownership conventions — `loadModule` returns a BORROWED pointer

Slang's COM-lite API is NOT uniformly "returned interface is caller-owned / release it." **(a) BORROWED bare-pointer returns — do NOT release:** `ISession::loadModule`/`loadModuleFromSource`/`loadModuleFromBlob`/`getLoadedModule` return a bare `slang::IModule*` whose refcount is *unchanged* for the caller — the `Linkage`/session owns the only strong references and frees the module when the *session* is released (proof: `asExternal(Module*)` is a plain `static_cast` with no `addRef`; DeepWiki wrongly claims it increments). An FFI caller that releases a `loadModule` result drops the session's own ref → double-free / heap corruption at teardown. **(b) OWNED `T**` out-params — release once:** `link()`, `getTargetCode()`, `getEntryPointCode()`, `createCompositeComponentType()`, `findEntryPointByName()`, `getDefinedEntryPoint()` transfer ownership via `.detach()`; blobs are per-call allocations. Teardown recipe: don't release `loadModule` handles → release blobs/entry-points/composites you created → release session → release global session → `slang_shutdown()` (frees process-global SPIR-V grammar/RTTI/capability tables). Meta-lesson: when a crash disagrees with a stated ownership model, read the source at the call site — don't trust DeepWiki or the generic "COM caller owns returns" rule [Slang C/COM API: loadModule returns a BORROWED IModule*, not caller-owned](wiki/learnings/1785172765216-slang-c-com-api-loadmodule-returns-a-borrowed-imod.md).

**Trust the builder's operand count, not a generated positional accessor.** `kIROp_MakeVectorFromScalar` declares a THREE-operand Lua schema `{elementType, elementCount, scalarValue}`, so FIDDLE emits `getScalarValue() → getOperand(2)`; but every builder creates it with a SINGLE operand (`emitIntrinsicInst(..., 1, &scalarValue)`), and every existing consumer reads the scalar via `getOperand(0)`. Calling `getScalarValue()` therefore reads two `IRUse` slots past the array — asserts in Debug, wild pointer in Release — reachable from a module-scope splat like `static const uint3 g = (uint3)float3(3.0);` ([MakeVectorFromScalar getScalarValue reads getOperand(2) but builder emits 1 operand](wiki/learnings/1785334765218-makevectorfromscalar-getscalarvalue-reads-getopera.md), [scalar is getOperand(0), NOT getScalarValue()](wiki/learnings/1785335653192-makevectorfromscalar-scalar-is-getoperand-0-not-ge.md)). General rule: for any IR op, verify how the *builder* emits it before trusting a positional accessor — schema and builder can diverge.

**Single-statement-body scope leak → defer-specific crash (#12266).** `Parser::ParseDeferStatement()` calls `ParseStatement()` without `pushScopeAndSetParent()`, so `defer uint i = 1;` leaks `i` into the enclosing function scope (name lookup then resolves it, suppressing `E30015`); IR lowering places the `IRVar` in the defer block, which `lowerDefer` relocates to scope-exit, so a reference before scope-exit derefs a stale value → segfault. `if(c) uint i=1;` / `while(...)` bodies leak identically but only `defer` crashes (the relocation). Fix = open a nested scope in the parser (mirror `parseBlockStatement`); the already-correct block form `defer { uint i=1; }` is the proof ([defer bare non-block decl leaks scope → IR-lowering segfault](wiki/learnings/1785345383314-slang-defer-bare-non-block-decl-leaks-scope-ir-low.md)).

**`buildHash` drops the second integer operand (#12270).** `CompilerOptionSet::buildHash`'s `Int` branch appends only `v.intValue`, never `v.intValue2` — asymmetric with the `String` branch (which appends both). Four options pack a second int into `intValue2` (`-fvk-bind-globals <index> <set>`, `VulkanBindShift`/`BindShiftAll`, `-trace-coverage-binding <index> <space>`) and all change emitted code, so they collide on the cache key that feeds BOTH the shader cache and `.slang-module` freshness. One-line generic fix (`builder.append(v.intValue2)`); regression lives in slang-unit-test (`buildHash` is API-path, not `.slang`-reachable) ([buildHash Int branch drops intValue2 — multi-integer options collide on cache key](wiki/learnings/1785350469856-buildhash-int-branch-drops-intvalue2-multi-integer.md)).
