## TL;DR

Operational gotchas across the fixer/approver toolchain: the `nv-slang-bot` GitHub App's workflow-push limit and the route around it, gateway-vs-`gh` credential divergence, the two `collect-reviews.sh` harvest-exit false-negatives, redundant/blocked CI dispatch, and one `ncl` approval-gating surprise.

- **The `nv-slang-bot[bot]` App token cannot push `.github/workflows/**` directly** — rejected "without `workflows` permission" on both `git push` and the Contents API (which silently no-ops); applies to origin and the fork. **Correction/supersession:** the bot CAN *open* a workflow-changing PR by pushing the branch to the `slang-coworkers/slang` fork and opening a cross-fork PR — so it is NOT patch-only; the merge still needs a maintainer.
- **`gh` can be stale while a direct `curl` through the gateway still posts** — `gh` binds to `GH_TOKEN` (which can degrade → `Resource not accessible by integration`), but the OneCLI gateway injects a working credential into outbound HTTPS at request time, so a raw `curl` to the REST endpoint succeeds (HTTP 201). Retry a failing write as `curl`; still flag the stale token.
- **The gateway itself can 401 on `/repos/*` while `/rate_limit` stays 200** — use `/rate_limit` as a control (200/60-limit = network path fine); a `/repos/*` 401 with that control is a gateway-side credential problem, not yours to fix from the container.
- **`collect-reviews.sh` exit 21 (pagination 401 on >100-review PRs) is a broken instrument, not NO_REVIEW_SIGNAL** — hand-page `pulls/N/reviews` via GraphQL and use a head-current trusted-bot primary before accepting exit 21.
- **`collect-reviews.sh` exit 20 drops head-current CodeRabbit SUMMARY comments** — CodeRabbit posts "0 actionable comments" as an *issue comment*, not a review object, so the collector misses it; check issue comments directly and confirm the summary names your pinned head before writing the tier as "Devin-only."
- **On a non-draft PR, don't manually dispatch `ci.yml`** — the `pull_request` trigger already runs it; a manual `workflow_dispatch` run yields to the human-priority gate and reports a cosmetic `failure` (all builds skipped). Manual dispatch is only for draft PRs.
- **`gh run rerun`/`--log-failed` are blocked while a run's overall `status:"waiting"`** on a pending approval gate — read the failure via `check-runs/{job_id}/annotations`; the rerun must defer to a later sweep (log it as `rerun_blocked`, not "declined").
- **`ncl tasks update` on a self-owned series applies instantly, no approval gate** — don't extrapolate approval-gating from the CLAUDE.md table's "mutating" framing; check by firing and observing.

## nv-slang-bot workflow-push limit and the fork route (a supersession)

Two atoms establish the limit and one supersedes the "patch-only" conclusion. [The App token cannot push `.github/workflows/` changes](../learnings/1787566137270-nv-slang-bot-app-token-cannot-push-github-workflow.md): the push is rejected "without `workflows` permission" — an App-permission limit (ordinary code pushes fine), applying to origin and the `slang-coworkers/slang` fork alike, so a CI-hardening sub-task that edits workflow YAML cannot be a bot-pushed PR. The [patch-mode atom](../learnings/1787745208437-nv-slang-bot-cannot-push-github-workflows-app-lack.md) adds that `github_create_or_update_file` on a workflow path *silently no-ops* (returns nulled fields — verify by re-fetching), and recommends delivering the fix as a `git format-patch` diff for a maintainer, plus `zizmor --offline` to prove a template-injection refactor cleared findings. **However**, the later [correction](../learnings/1787843299757-nv-slang-bot-can-open-a-github-workflows-pr-via-th.md) supersedes the "patch-only" framing: the bot CAN *open* a workflow-changing PR via the fork (verified: PR #12772, head `slang-coworkers/slang:fix/issue-12771`, changed `.github/workflows/ci-slang-build.yml`) — the direct-push limit holds, but a cross-fork PR routes around it, and the merge still needs a maintainer. Practical rule: separate "bot-pushable via fork" (source, tests, data files, AND workflow YAML) from "needs maintainer merge/approval"; tell reporters the bot can *propose* the workflow PR, not that it "can't touch workflows."

## Gateway-vs-gh credential divergence

Two atoms show the OneCLI gateway and `gh`'s env token failing independently. [`gh` can be stale while a gateway `curl` still posts](../learnings/1788089811545-gh-gh-token-can-be-stale-while-gateway-curl-still-.md): `gh` failed to comment (`GraphQL: Resource not accessible by integration`, `GH_TOKEN` invalid) yet a direct `curl` POST to `api.github.com/.../comments` returned 201 because the gateway injects a working credential at request time independent of `gh`'s env token — so on a 401/403 for a write the bot should be allowed, retry as `curl` (still flag the stale token, since any `gh`-shelling path keeps failing). Conversely, [the gateway can 401 on `/repos/*` while `/rate_limit` stays 200](../learnings/1788180429300-onecli-gateway-api-github-com-repos-401-while-rate.md): every `api.github.com/repos/*` path returned `401 Bad credentials` while `/rate_limit` through the same proxy returned a clean 200 at the unauthenticated 60/hr tier — so `/rate_limit` is the control (200 = network path fine), and a `/repos/*` 401 with that control is a gateway-side credential-injection problem to report, not fix from the container; carry standing GitHub-derived watches forward as explicitly unverified.

## Harvest-exit false-negatives, CI dispatch, and ncl

The PR-approver's `collect-reviews.sh` has two review-object false-negatives. [Exit 21 (OneCLI pagination 401) is a broken instrument, not NO_REVIEW_SIGNAL](../learnings/1787738174969-approver-infra-abstain-collector-exit-21-onecli-pa.md): PRs with >100 reviews make bare `gh --paginate` 401 on page 2 because GitHub's `rel=next` rewrites to a `repositories/<id>/...` path not on the OneCLI allow-list, so the collector fails on exactly the most-reviewed PRs "wearing the costume of conservatism" — hand-page `pulls/N/reviews` via GraphQL and use a head-current trusted-bot primary before accepting exit 21 (recording NO_REVIEW_SIGNAL would corrupt the infra-abstain rate). [Exit 20 drops head-current CodeRabbit SUMMARY comments](../learnings/1787757773270-approver-infra-abstain-collect-reviews-sh-exit-20-.md): CodeRabbit posts "0 actionable comments 🎉" as an `issues/N/comments` issue comment, not a review object, so the collector never persists it — check issue comments directly (`gh pr view --json comments`), confirm the summary's `Reviewing files that changed … between <base> and <HEAD>` names your pinned head, and describe the tier as "CodeRabbit-summary + Devin," not "Devin-only" (an OUTPUT_REVIEW critique correctly flags "Devin-only" as an overclaim).

On CI dispatch: [don't manually dispatch `ci.yml` on a non-draft PR](../learnings/1787275583180-don-t-manually-dispatch-ci-yml-on-a-non-draft-pr-t.md) — the `pull_request` trigger already runs it, and a manual `workflow_dispatch` run yields to the human-priority gate, reporting a cosmetic `conclusion: failure` (only `wait-for-human-priority` + `check-ci` failed, every build skipped) that fires a misleading `github.ci_failed` webhook; disambiguate the webhook by the run's `event` (workflow_dispatch = manual, pull_request = real signal). And [`gh run rerun` is blocked while a run's overall `status:"waiting"`](../learnings/1787596929089-gh-run-rerun-blocked-while-parent-run-status-waiti.md) on a pending gate job even when an inner job already failed — `--log-failed` and the blob fetch refuse, but `check-runs/{job_id}/annotations` returns the failure summary; the rerun itself must defer to a later sweep, logged as `rerun_blocked` so it's retried not written off.

Finally, one `ncl` surprise: [`ncl tasks update` on a self-owned series applies instantly with no approval gate](../learnings/1787250785428-ncl-tasks-update-on-own-series-applies-instantly-n.md) — contrary to CLAUDE.md's "mutating verbs trigger admin approval" framing, `tasks update --script` returned `{"touched":1}` immediately and the new script was live. Don't extrapolate approval-gating from the table's framing (which also omits `tasks` from the scoped-resource list despite it being group-scoped); check by firing and observing.
