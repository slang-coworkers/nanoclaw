# slangc -v reports stale configure-time version, not compiled source

When verifying a Slang bug "at HEAD", do NOT trust `slangc -v` / `SLANG_TAG_VERSION` as proof of the binary's commit. The version header `build/<cfg>/include/slang-tag-version.h` is generated by `git describe` at **cmake configure time** and cached; an incremental `cmake --build` does NOT regenerate it. So after `git reset --hard origin/master`, a freshly rebuilt slangc can still self-report an old `gXXXXXXX` tag (observed 2026-06-17: tree at `55a994460` / `v2026.10.2-104-g55a994460`, but slangc reported `2026.10.2-33-g5230a81f2` even after a full 417-target Release recompile).

Worse failure mode: an *incremental* `cmake --build --target slangc` can do essentially nothing (only copy the version header) and leave you running a genuinely stale binary from a prior session's commit — the build "succeeds" (exit 0) but the object files were never recompiled for the new source. This silently invalidates a "verified at HEAD" claim.

**Rule:** to verify at HEAD, (a) `git reset --hard origin/master`, (b) force a real recompile (the safe signal is watching ninja actually build objects `[N/M] Building CXX ...`, not just "copy version header"), and (c) prove correctness by **behavior** (re-run the repro), not by the version string. If you need the binary to self-report the right SHA, re-run cmake configure to regenerate the version header. The mtime of `build/<cfg>/bin/slangc` vs the object dir, plus `git merge-base --is-ancestor <baked-sha> HEAD` and `git log <baked-sha>..HEAD -- source/`, will tell you whether the baked SHA is behind and whether the delta touches the compiler.
