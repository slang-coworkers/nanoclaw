# slang-glslang is the SPIR-V backend — don't mask its load as optional (fix the build system)

**Fact (non-obvious, name is misleading):** `slang-glslang` has nothing to do with GLSL — it is Slang's **SPIR-V backend library**, bundling SPIRV-Tools including `spirv-opt`. It is always built as a runtime-loaded **MODULE** (`source/slang-glslang/CMakeLists.txt`), never static-linked; `SLANG_LIB_TYPE` governs only the **core slang** lib, never `slang-glslang`. A **static** Slang build still `dlopen`s `slang-glslang-<ver>.so` by bare name (`locateGlslangSpirvDownstreamCompiler` → `DownstreamCompilerUtil::loadSharedLibrary`). There is currently **no build path that static-links it.**

**Lesson — fix the producer, not the consumer.** When a static/standalone Slang build fails to load `slang-glslang` (or any downstream backend) at runtime, the correct fix is a **build-system change** (statically link / bundle the backend so `-target spirv` has it), NOT making the downstream-compiler load non-fatal/optional at the emit layer. The latter masks a producer-side (build-config) gap rather than fixing it.

**Incident (2026-06-22):** nv-slang-bot PR #11663 (issue shader-slang/slang#11662, reporter rg3igalia building Slang static for Vulkan CTS). Bot shipped the emit-layer approach: make the optional `spirv-opt` load non-fatal in `createArtifactFromIR` (`slang-emit.cpp`). It was CI-green, reviewer-approved, and the reporter confirmed "works for me" — yet maintainers **jkwak-work** and **jhelferty-nv** rejected it as the wrong layer and the PR was closed (not merged). We verified their objection against the code and conceded.

**Subtlety worth knowing:** jhelferty-nv's specific worry — "spirv-opt does legalization, so making it optional risks illegal SPIR-V" — does **not** hold. Slang self-legalizes via its own unconditional IR pass `legalizeIRForSPIRV` (`slang-emit-spirv.cpp`, since 2021); the spirv-opt wrapper is **perf/size-only** (no RegisterLegalizationPasses) and validation runs on the base SPIR-V. So the emit-layer fix genuinely produced valid SPIR-V. The decisive objection was **architectural** (the SPIR-V backend should be *available* in a static build, not silently optional), and that stands regardless. When conceding, concede on the architectural layer and do NOT publicly re-litigate the legalization nuance — it reads as defensive.

**Resolution (2026-06-23) — even the "correct layer" fix turned out unnecessary.** After conceding, the maintainer (jkwak-work) directly asked the bot to do the proper build-system fix. We planned + spiked it (draft PR #11694, Option A: build `slang-glslang` as a static archive + bind its 7 `extern "C"` entry points in-process + `objcopy`-localize the bundled SPIRV-Tools symbols to avoid ODR collision with an app that links its own SPIRV-Tools — validated on Linux: 3,452 `multiple definition` errors → 0; MSVC localization deferred, no `--exclude-libs`/`objcopy` analogue). The reporter then floated **Option B**: reuse the consumer's SPIRV-Tools via the **already-existing `SLANG_USE_SYSTEM_SPIRV_TOOLS`** option (one copy → no collision, cross-platform). Maintainer **closed #11694**, said Option A "less preferred over reusing the system-provided spirv-tools," and — decisively — pointed out the existing **shader-slang/VK-GL-CTS integration is generic enough *without* compiling Slang as STATIC at all**. Net: **no feature was built**; issue parked **P3/unplanned**. The Option-A prototype is preserved on `fix/issue-11662` (origin) if revived.

**Deeper lesson — confirm the feature is even needed before building it.** A *correctly-layered* fix can still be wasted effort. Before building a substantial feature for a user's **integration** use-case, check (a) whether an **existing config option** already covers it (here: `SLANG_USE_SYSTEM_SPIRV_TOOLS`, wired via `find_package(SPIRV-Tools)` + glslang's `ALLOW_EXTERNAL_SPIRV_TOOLS`), and (b) whether an **existing prior-art integration** already solves the user's actual goal (here: the `shader-slang/VK-GL-CTS` fork). Surface these as options and let the maintainer choose *before* sinking PR effort — the plan-first + spike-first + design-comparison-before-PR sequence here meant the (ultimately-shelved) work stopped at a validated draft, not a polished PR.

**How to apply:** For "missing downstream component in a static/standalone build" issues, default to the build-system/linking fix; treat "make the load non-fatal" as masking unless the component is genuinely optional with a guaranteed fallback. Defer build-system *design* calls (e.g. "should X static-link Y?") to maintainers, and explicitly check for an existing option/integration that obviates the feature. Prior art for the CTS-integration scenario: the `shader-slang/VK-GL-CTS` fork; the relevant existing build option is `SLANG_USE_SYSTEM_SPIRV_TOOLS`.
