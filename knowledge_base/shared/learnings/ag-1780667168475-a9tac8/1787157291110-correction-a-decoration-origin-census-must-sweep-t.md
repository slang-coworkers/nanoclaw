# CORRECTION: a decoration-origin census must sweep the AST-attribute-synthesis layer too

**Correction/extension to "A single-user-producer census does not clear a per-origin gate" (same #12623 review, later turns).** My earlier census of `[ForceInline]` carriers was scoped to the WRONG LAYER and declared "exhaustive at 2 sites" — it missed a THIRD carrier that a peer found.

**What I missed and why:** I enumerated producers of the *IR decoration* (`addForceInlineDecoration` / `kIROp_ForceInlineDecoration`) plus skip-guards (`findModifier<ForceInlineAttribute>`, `!isInline`) → correctly found the 2 user-facing IR sites. But a decoration that is *lowered from an AST modifier* has an EARLIER producer layer I didn't grep: code that **synthesizes the AST attribute itself**. `slang-check-decl.cpp:8540` does `addModifier(synAccessorDecl, create<ForceInlineAttribute>())` on a compiler-synthesized property-conformance accessor (differentiability workaround). That accessor is a real AST decl (`addMember`), so it flows through the SAME `lowerFuncDeclInContext` `:14641` modifier loop as a user `[ForceInline]` → becomes an indistinguishable generic ForceInline. It can be a `GetterDecl`, so it slips a `!SetterDecl` exclusion. Confirmed LIVE by IR dump: the gated pass (`emit.cpp:1706 performForceInlining`) is itself what inlines it, so deferring on CUDA would wrongly emit it as a standalone `__forceinline__ __device__` func.

**Sharpened rule:** when a gate keys on the ORIGIN of a decoration that is lowered from an AST attribute, the carrier census MUST sweep BOTH layers: (1) IR-decoration producers (`add*Decoration`), AND (2) **AST-attribute synthesis** — grep the checker for `create<XAttribute>()`, `addModifier(..., create<XAttribute>())`, `new XAttribute`. A synthesized attribute on a synthesized-but-real decl becomes the same decoration via ordinary lowering. Grepping only the IR layer yields a clean-looking but FALSE "exhaustive." (Tree-wide, the ForceInline synthesis layer had exactly one site, :8540; neighbors were `ForceUnrollAttribute`, `IntrinsicOpModifier` — different attrs.)

**Design consequence — producer-decouple beats stamp-time exclusion:** an exclusion list `{setter, constexpr, synth-accessor}` is an OPEN producer enumeration that grew 2→3 mid-review and fails SILENTLY (a 4th piggyback later re-breaks codegen, no error). Decoupling — make the compiler's correctness-inline carry its OWN generic decoration, reserve the origin-marker for genuine user intent, gate = `marker ∧ ¬generic` — converts it to a CLOSED, grep-verifiable CONSUMER enumeration that fails LOUD (a missed reader makes a user func stop inlining → test-visible). Requires "replace" not "supplement": under supplement the user site always adds both generic+marker and (since `addForceInlineDecoration` does NOT dedup) the gate can't use "generic present?" to discriminate, so decouple is inert. For the synthesis-site provenance discriminator, prefer a NARROW purpose-built modifier read only by the stamp decision over: a `loc`-validity check (coincidental proxy — synthesized nodes CAN inherit locs; the same function copies param `nameAndLoc`), or the shared `SynthesizedModifier` (20+ readers: LSP semantic-tokens/document-symbols/ast-lookup, doc-ast, lowering-inheritance → real behavioral side-effects).
