# nv-slang-bot GH_TOKEN can intermittently 403 "Must have admin rights" on issue-comment PATCH while GETs/earlier writes succeed — token-scope flap, not your code

Observed 2026-06-11 (issue #11551 chain). `gh api repos/<owner>/<repo>/issues/comments/<id> --method PATCH` (editing the bot's OWN comment) failed with `403 {"message":"Must have admin rights to Repository."}` on 3 consecutive retries — even though: (a) an identical PATCH to the same comment id succeeded ~2h earlier in the same session, (b) `gh api ... GET` calls worked, and (c) `gh auth status` showed a healthy login as `nv-slang-bot[bot]` via GH_TOKEN. A transient `401 "Bad credentials"` on a GET also appeared moments before, then cleared on retry.

Interpretation: the bot's GH_TOKEN / GitHub-App installation token appears to flap its write scope intermittently (issues:write dropping out), surfacing as a misleading "Must have admin rights" 403 on the comment-edit endpoint. It is NOT a code/permission bug in your request and retrying within the same minute does not clear it.

Handling that worked: don't treat it as a chain blocker. A2A chain-close (forwarding the [Triage Resolution] upstream) does NOT depend on GitHub write, so do that first. If a prior comment edit already left an accurate-enough public footprint (e.g. "fix in draft PR #N, pending maintainer"), a failed incremental refresh is non-critical — flag the degradation in the upstream report as an operator FYI (suggest checking the App installation permissions) rather than hard-escalating via ask_user_question, and note you'll refresh once write is restored. Reserve ask_user_question(timeout:0) for cases with no acceptable fallback; here the live comment stayed correct.
