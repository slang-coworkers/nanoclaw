# [approver/clause-gap] a "narrowing/carve-out" refactor can silently reclassify SIBLING cases — re-derive per-diff, don't carry forward a prior approval

**Symptom:** slang#12435 was WOULD_APPROVE at R3/R4 (an explicit divert of opaque decl kinds — Interface/Assoc/ThisType/GlobalGenericParam — to emitDefaultConstruct). At R5 the author re-implemented the SAME fix by INVERTING the branch: instead of "these opaque kinds → emitDefaultConstruct", they wrote "only StructDecl → member-wise makeStruct; everything else → emitDefaultConstruct". This looks cleaner/more-robust (structurally eliminates the opaque-kind zero-operand-makeStruct class), and it's tempting to carry R3/R4's WOULD_APPROVE forward. But the inversion ALSO reclassified three FIELD-BEARING sibling kinds the old AggTypeDecl catch-all had covered — ClassDecl, SynthesizedStructDecl, GLSLInterfaceBlockDecl — from eager makeStruct to the deferred path. Two real semantic differences resulted (verified from source): (1) emitDefaultConstruct has no kIROp_ClassType field-recursion, so ClassDecl→IRClassType emits a bare DefaultConstruct; (2) the deferred path drops AST field-initializer expressions the old member-wise `getDefaultVal(ff)→initExpr` honored. Neither the production bot review (0 bugs) nor Devin flagged it; the codex critique gate surfaced it, flipping a would-be WOULD_APPROVE to ABSTAIN.

**Root cause:** "Narrowing" or "carve-out" refactors (change `X.as<Base>()` to `X.as<Derived>()`) are deceptively risky: the branch's TRUE domain silently shrinks from {all Base subclasses} to {one Derived}, and every OTHER subclass falls to whatever comes next. The diff looks like a tightening of ONE case, but its blast radius is EVERY sibling of that case. A prior revision's approval covered a DIFFERENT implementation shape; it says nothing about the sibling reclassification the new shape introduces.

**How to catch it:** When a diff changes a type-dispatch predicate from a base class to a subclass (or removes an explicit branch so cases fall through), ENUMERATE the full sibling set of the base (here: grep slang-ast-decl.h for `: public AggTypeDecl` → StructDecl/ClassDecl/SynthesizedStructDecl/GLSLInterfaceBlockDecl/InterfaceDecl). For EACH sibling that changed branch, ask: does the new target path preserve the old semantics for THAT kind? Check the target's per-kind handling (does emitDefaultConstruct handle IRClassType? does it honor field initializers?), not just the headline kind the PR is "about". A "behavior-preserving" claim must be verified PER KIND, not asserted for the group.

**Fix / rule:** (a) NEVER carry a prior-revision WOULD_APPROVE forward — re-derive from the current diff; a revision that "just refactors" the same fix can introduce a new side-effect class. (b) For a narrowing/carve-out dispatch change, the challenger MUST enumerate the base's sibling set and check each reclassified sibling's new path per-kind. (c) If any reclassified kind's new-path semantics differ (field-init handling, missing IR-type case) and you cannot prove that kind unreachable on a supported path, ABSTAIN (OPEN_GAP) — uncertainty never rounds up. (d) Watch for scope changes: a "Move X to its own branch" commit that DELETES part of a PR resets what you're deciding — re-stage from the current diff.
