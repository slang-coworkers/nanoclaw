# [approver/infra-abstain] record_decision host enum is {WOULD_APPROVE,BLOCK,ABSTAIN_POLICY} only — ABSTAIN_INFRA is rejected; and a vanished policy mount must not be recorded as CLAUSE_FAIL

Two infra traps hit on the same revision (slang-rhi#841 R4), both worth encoding:

**1. `record_decision` does NOT accept `ABSTAIN_INFRA`.** The slang-pr-approver SKILL.md enumerates four decision states (WOULD_APPROVE | BLOCK | ABSTAIN_INFRA | ABSTAIN_POLICY), but the HOST `record_decision` tool's closed enum is only **three**: WOULD_APPROVE, BLOCK, ABSTAIN_POLICY. Passing `decision:"ABSTAIN_INFRA"` returns a misleading success string ("Decision recorded … = ABSTAIN_INFRA") **and is then silently IGNORED** — a follow-up host notification says: `record_decision ignored: "ABSTAIN_INFRA" is not a decision state. Use WOULD_APPROVE, BLOCK or ABSTAIN_POLICY.` So: record every abstain (including pipeline/infra ones) as **ABSTAIN_POLICY**, and carry the infra nature in `reason_code` + the challenger field. Do not trust the tool's echo — the authoritative signal is the host notification. (Corollary to the older "a tool success string is a request ack, not a write receipt.")

**2. A vanished policy mount flips the clauses — do not record the spurious FAILs.** slang-rhi#841 R1–R3 ran under the mounted `/workspace/extra/approver-policy/APPROVAL_POLICY.json` = `v0-shadow-wide` (trusted incl NONE, allow_fork_head, require_ci_green=false, protected=slang-tag-version.h only, caps 150 files/8000 lines) → all 6 eligibility clauses PASS. At R4 the container/session had been reset (fresh session id, USD budget reset) and the mount directory was **empty** — so `eval-clauses.py` fell back to the bundled strict `v0-shadow` default (trusted OWNER/MEMBER/COLLABORATOR only, fork disallowed, CI required, `.github/**`+`**/CMakeLists.txt`+`**/*.yml` protected). That flips author_trust (a CONTRIBUTOR becomes "untrusted"), head_provenance (fork "disallowed"), no_protected_paths (CMakeLists/*.yml), tier_eligible → 4 spurious CLAUSE_FAILs. **Nothing about the PR changed — only the policy vanished.** Recording those as `ABSTAIN_POLICY:CLAUSE_FAIL` would inject false policy signal, the exact failure `v0-shadow-wide` was human-approved to prevent in shadow mode ("a Step-1 terminal FAIL protects nothing and only destroys measurement signal").

**How to catch it:** every run, verify the `clauses -> … (policy <X>)` line prints the SAME policy version the prior rows of this PR used. A silent flip (e.g. v0-shadow-wide→v0-shadow) between revisions of the same PR ⇒ the mount vanished, not a real eligibility change. Confirm by reconstructing the policy-of-record and re-running `eval-clauses --policy <reconstructed>` (evidence only, not authoritative): if it restores 6/6 pass, the fallback FAILs are a mount artifact. Then record on the merits (here OPEN_GAP — established independently of policy) as ABSTAIN_POLICY, document the infra gap in reason_code/challenger, and escalate to the operator to restore the mount. Per "a missing input is an ABSTAIN naming the artifact, never a guess/workaround" — but since the host has no ABSTAIN_INFRA state, "naming the artifact" happens in the reason_code/challenger, not the decision enum.
