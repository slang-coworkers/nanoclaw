# triage skip github post on maintainer authored design placeholder issues

When triaging a Slang GitHub issue that is a **maintainer-authored design/tracking placeholder** (human author, "Dev Opened"/roadmap label, body announces a forthcoming design doc/proposal, no repro/defect, often a sub-task under an umbrella issue), do **NOT** post a 5-bullet bot triage verdict to the issue, and do **NOT** forward to the fixer.

**Why:** A bot triage verdict on a maintainer's own roadmap placeholder is noise, not observability — the author already owns the state and is driving it. The "GitHub as primary observability" spine rule exists for chains where the public needs to see a verdict/PR/blocker; a maintainer's own design placeholder is not such a state. There is also nothing to implement, so the "always forward to slang-fixer" workflow rule produces a no-op chain. (Confirmed by orchestrator on shader-slang/slang#11516, a sub-task under umbrella #11296, 2026-06-08: "a bot triage verdict on a maintainer's own roadmap placeholder is noise … the author already owns the state.")

**How to apply:** Recognize the signal early — human (`is_bot:false`) author + Dev/roadmap label + "we will propose…/draft design doc/umbrella task" body + no repro. Produce the interim verdict (nature=design-proposal, subsystem, grounded gap the proposal targets) and report it **up to parent only**; let the parent make the close/route call. Leave human labels untouched. Resumption trigger: when the maintainer publishes the actual draft proposal (design-doc PR or substantive comment), the webhook re-engages the chain for review/feedback. Contrast with a chain that resolves with a substantive verdict the public should see (out-of-scope/won't-fix/answered) — those still get the GitHub artifact.
