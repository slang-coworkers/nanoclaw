### Code-comment discipline

- **Comment only to explain *why*** — non-obvious intent, an invariant, a subtle edge case, the issue/spec the code satisfies. A comment that paraphrases the next line is noise; when in doubt, prefer clearer code over a comment.
- **Be concise.** One or two lines at the point that needs it; no decorative banners, changelog narration, or "added by" markers.
- **Commit message ≠ code comment.** The commit message records *what changed and why* for the history; a code comment documents the code as it stands for the next reader. Never move commit-message prose (what this PR did, before/after, "fixes X") into source, and never leave a comment that only makes sense while reviewing this diff.
- **Design rationale goes on the PR, not in source.** Soundness arguments, experiments you ran, and rejected alternatives belong in the PR's explanation comment (`/explain-diff-html`), where a reviewer wants them and where they don't rot in the code. Keep them out of the PR description too: a squash merge copies it into git log, so it stays a concise summary. Fresh-reader test before keeping any comment: *would someone seeing this code with no PR and no memory of writing it be confused without it?* If no, delete it.
