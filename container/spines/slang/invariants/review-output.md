### Review output rules

Apply when posting review output back to GitHub (slang-reviewer only — fixers/writers/triagers don't post reviews).

- **Bot reviews are always `event=COMMENT`.** Never `APPROVE` or `CHANGES_REQUESTED` — bots must not gate human merges. The `slang-pr-review-runner` skill's `post-review.sh` hard-codes the state and runs a safety-net dismissal pass after posting; the inner CLI must not attempt any other state.
- **Post only when authorized.** The `/slang-pr-review` workflow posts the merged review to GitHub ONLY when the orchestrator's dispatch carries the `<github-post-authorized />` marker — set by the `slang-github-webhook` skill when a human tagged `@nv-slang-bot` in the triggering comment (explicit invitation to reply). Without the marker, return via `send_file` only.
- **Round-2 hygiene before post.** Before posting a new review, run the skill's `cleanup.sh` (or `post-back.sh`, which calls it) to minimize prior bot review bodies as `OUTDATED` and resolve prior bot threads — a second review piled on the first is noise. Cleanup targets `nv-slang-bot` only; production's `claude` / `github-actions` auto-reviews are untouched.
- **403 = graceful degrade.** If the App installation token lacks `pull_requests:write` on the target repo, `post-review.sh` exits 3 and the workflow falls back to `send_file` only — the human still has the review via the parent thread. Affects `slang-coworkers/*` today (App lacks write); `shader-slang/*` repos are write-capable.
- **Three reviewers, one combined report; only correctness (A) is auto-posted.** `/slang-pr-review` runs Reviewer A (correctness), B (Devin), and C (clarity) and sends all three WHOLE to the fixer as `combined-review.md`. The GitHub post-back (when authorized) posts Reviewer A's `final-review.md` only — clarity (C) is advisory, lower-bar feedback for the fixer, never auto-posted as a bot review. Reviewer C never posts: `slang-clarity-review-runner` forbids `slang-review-post-github` and any GitHub-write tool.
