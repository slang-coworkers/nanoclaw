### Fleet topology — the baseline every design is judged against

Decided 2026-09-08 by the operator after the August Bot Mode team (five profiles on one gateway, driven from the desktop app) proved the shape. Every ADR, scenario and plugin surface follows it; a row that needs something else says so in its CORE-CHANGE section and gets the operator's decision first.

1. **One gateway per fleet, in Bot Mode.** Coworkers are **profiles** of that gateway (`$HERMES_HOME/profiles/<name>/`: own SOUL.md, config, .env, memory, state.db, plugins). They appear in the desktop app's Bots list because the app discovers profiles from the gateway it connects to. A second gateway exists only at a tenant boundary (another team, another machine); never one gateway per bot.
2. **Bot-to-bot is Bot Chat inside the gateway** (`message_agent`, rooms, @mentions); **durable hand-offs are kanban** (board, dispatcher, workers spawned per task). **a2a is for cross-gateway or cross-tenant peering only.** A `live:` criterion for anything agent-to-agent therefore defaults to "bot A messages bot B in the same gateway and B's reply is visible in the room", observable in the desktop app; it uses a2a only when the row is about peering across gateways.
3. **Isolation is per-profile podman tool sandboxes, and it is a MUST.** Every file, shell, code-execution and MCP-client tool call of a profile runs inside that profile's sandbox (its workspace mounted, its OneCLI identity, its resource limits). No `local` terminal environment anywhere in the fleet; a `pre_tool_call` veto enforces it. The gateway process itself stays shared: LLM loops, rooms, kanban, cron, approvals. Runaway loops are the job of turn caps and cost caps, not of the sandbox.
4. **An elevated orchestrator profile.** Only the orchestrator carries the fleet-admin toolset (onboard and render profiles, board and room administration, cron for others, approvals, cost-cap control). Every other profile has a restricted per-platform toolset, and the same veto hook denies admin tools to non-orchestrator profiles. This is the fleet's `cli_scope`: one small plugin plus per-profile config, not a guard catalog.
5. **Adopt Hermes-native first.** Where Hermes already has the capability (cron, platforms, approvals, memory, skills hub, dashboard analytics, kanban), the row is adopt or configure: a doc page plus a hermetic acceptance test that proves Hermes does it. Build a plugin only for what the outcomes need and Hermes lacks (coworker composition, cost caps and cards, OneCLI as secret source, the critique and plan gates, the GitHub review ledger, fleet metrics).
6. **Unified panel.** Sessions, bots, rooms, cron, approvals and cost for the whole fleet are driven and watched from one desktop app connected to the one gateway. Rooms, kanban and cron do not span gateways, which is why rule 1 holds.

Consequences for the plan: P4 stays (per-profile sandboxes); the P5 a2a wiring rows become room membership plus the veto hook; the P6 fleet launcher becomes one gateway container with N profiles and N sandboxes. The Slang test bed keeps its two-gateway a2a scenario only for cross-gateway rows.
