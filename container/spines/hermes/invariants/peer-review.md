### Peer-review-before-report rule (hermes-builder only)

Apply whenever an implementation produces a draft PR (or patch) in the fork.

- **Order is fixed:** the peer-review request to `hermes-reviewer` first; `[Fix Report]` up only after `[Review Verdict] APPROVE`. Never send `[Fix Report]` first, and never fold review state into a bare `[Report]`.
- **Round 1 is an UNMARKED fresh delegation on the reviewer's edge.** The reviewer has never written to you on this thread, so there is no inbound to reply to, and the always-on chain-routing gate denies any marker-prefixed send that lacks `in_reply_to`: `send_message(to="hermes-reviewer", thread_id="hermes-<req-id>", text="Fix review request — <fork-slug>#<N>: <title>\n…")` — first line must not begin with `[`; `thread_id` = the canonical thread you were dispatched on, propagated unchanged. Body: fork draft-PR URL + head SHA, plugin dir, ADR path, acceptance-test path and result, `hermes plugins doctor --ci` result, the `scripts/run_tests.sh` chunks you ran. Then `send_file` the ADR and the acceptance test to the reviewer with the same `thread_id`. `[Fix Review Request]` is used ONLY when answering the reviewer's `[Review Verdict] REQUEST_CHANGES` as a reply (`in_reply_to=<verdict-msg-id>`). This is additional to the `CODE_REVIEW` codex critique, not a substitute — codex reads the diff; the reviewer re-runs doctor, the acceptance test, and the suite in its own container.
- **After dispatching, end the turn.** Do not poll. Handle the reply per `/hermes-implement`: `REQUEST_CHANGES` → fix in the same worktree, push to the same PR branch, re-run doctor + tests, re-request as a reply on the reviewer's edge (`in_reply_to=<verdict-msg-id>`). Max **2** review rounds; a third `REQUEST_CHANGES` → `[Fix Report]` with `blocked: review not converged` listing the open findings, and escalate.
- **`[Fix Report]` is a reply on your parent edge** (`in_reply_to=<the inbound that delegated this requirement>`), carrying the reviewer's verdict line verbatim, the PR URL, and the test/doctor results.
- **Only legitimate skip:** `hermes-reviewer` is not in your destinations — state that in the `[Fix Report]`. Patch-only mode, "trivial change", and time pressure are not skips.
- No meta-acks to the reviewer; only substantive replies (a re-request after changes, or an answer to a question the verdict asks).
