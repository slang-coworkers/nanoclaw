### Plugin-first — PORT, not bridge

- **Every capability this team ships is a Hermes plugin.** Either a directory plugin — `plugin.yaml` with `manifest_version: 1` plus `__init__.py` exposing `register(ctx)` — or a portable Agent Plugins v1 package (`plugin.json` + `skills/<name>/SKILL.md`, optional `mcp.json`). A shell script, a NanoClaw-side hook, or a host process that Hermes calls out to at runtime is not a deliverable. If Hermes cannot do it through a plugin, that is a `CORE-CHANGE` finding to spec, never a bridge to build.
- **Allowed diff surface without an exception: `plugins/**`, `website/docs/**`, `tests/**`.** Any hunk outside those paths requires the requirement's ADR to carry a section titled exactly `CORE-CHANGE` that cites the exact release `file:line` under `/workspace/extra/hermes-release` which blocks a plugin — the missing `VALID_HOOKS` entry, the `PluginContext` method that does not exist, the discovery rule that rejects the layout. The reviewer must-changes any out-of-surface diff without that section; there is no "small edit" exemption. Inside a `CORE-CHANGE`, widen the generic plugin surface (a new hook or `ctx` method, `**kwargs`-additive) — never special-case one plugin in core (`AGENTS.md:123-125, 851-857`; `CONTRIBUTING.md:96-99`).
- **Plugins never touch core files** — `run_agent.py`, `cli.py`, `model_tools.py`, `toolsets.py`, `gateway/run.py`, `hermes_cli/main.py`, and the rest of the core tree. A plugin that needs to is either a plugin plus a `CORE-CHANGE` ADR, or a different design.
- **The footprint ladder applies inside the plugin boundary** (`AGENTS.md:24-27, 183-212`): prefer `ctx.register_skill` / `register_cli_command` → a service-gated tool (`check_fn`) → hooks and middleware → `register_platform` / provider registrations → asking for a new core tool last. Pick the lightest rung that meets the requirement and say why in the ADR.
- **Replacing a bundled plugin is still a plugin.** Later discovery sources override earlier ones on key collision (`hermes_cli/plugins.py:15-17`); the replacement declares the same manifest `name` (e.g. `name: a2a`), is listed in `plugins.enabled`, and is proven with `HERMES_PLUGINS_DEBUG=1 hermes plugins list`.
- **Proof obligations for every plugin:** (a) an acceptance test that loads it from an isolated `HERMES_HOME` with `HERMES_BUNDLED_PLUGINS` pointed at an empty dir via `PluginManager().discover_and_load()` and asserts registration plus hook/tool outcomes (shape: `tests/hermes_cli/test_plugin_api_compat.py:14-52`) — this proves the plugin works on a stock tree; (b) `hermes plugins doctor <plugin-dir> --ci` exits 0. The architect writes (a) before any code exists; the builder makes it pass; the reviewer re-runs both.
- **Citations come from the release tree only.** `/workspace/extra/hermes-release` (read-only, exact v2026.8.31) is the sole citation source for ADRs, reviews, and reports — `file:line` relative to it. DeepWiki (`mcp__deepwiki__ask_question`) is advisory: use it to orient, then confirm in the tree; when they disagree the tree wins and the disagreement is flagged explicitly in the report. A claim with only a DeepWiki citation is unverified.
- **Placement note:** upstream closes third-party-product plugins that land under `plugins/` (`AGENTS.md:126-137`; `CONTRIBUTING.md:88-102`). In the fork that placement is acceptable; the ADR records it as a fork-only decision and names the standalone-repo path (`~/.hermes/plugins/<name>` or a `hermes_agent.plugins` entry point) for upstreaming.
