name: hermes-review
type: workflow
description: 'Adversarial peer review of a hermes-builder draft PR in the Hermes fork. Intake is the builder''s review request carrying hermes-tester''s [Test Report] PASS for the PR head: check out that head in your own worktree, audit the Test Report (head SHA, PASS/FAIL table), read the diff, enforce the plugin-first boundary, spot-check at most ONE command, and return [Review Verdict] on the builder''s edge citing the report. No baseline rebuilds, no suite re-runs — a missing, FAIL or stale report means a re-run request to hermes-tester, never testing it yourself. Extends plan (mode = review); read-only, no push, no GitHub writes.'
extends: plan
requires: [issues.read, code.read, doc.read]
uses:
  skills: [hermes-code-reader, hermes-github, hermes-build]
  workflows: []
overrides:
  research: |
    **Research** — Never trust the builder's log; trust the tester's report once you have bound it to the PR head SHA. You review the DIFF and audit the EVIDENCE — you do not regenerate the evidence.

    1. **Inputs.** The review request is an inbound from `hermes-builder` — round 1 arrives as unmarked text (`Fix review request — <fork-slug>#<N>: …`), later rounds as `[Fix Review Request]`. Record `<review-request-id>` (the inbound id) — the verdict MUST reply to it. Under `/workspace/inbox/<msg-id>/` expect two attachments: the ADR and the tester's report `test-report-*.md` (written by `hermes-tester` under `/workspace/agent/reports/<thread-id>/` on ITS filesystem — the report header names that canonical path, the PR, the head SHA, the test round and the verdict). No status echoes to anyone.
    2. **Test Report gate — before any checkout.** The report is valid iff ALL hold: (a) it is attached as a file (not pasted or summarised in the message); (b) its header verdict is `PASS`; (c) its head SHA equals the PR head — `gh pr view <N> --repo {{vars.fork}} --json headRefOid --jq .headRefOid`; (d) its `## Results` table has one row per tier — `DOCTOR`, `ACCEPTANCE`, `NEGATIVE-CONTROL` (the acceptance test FAILS on the base tree), `RUFF`, `FOOTGUNS`, `SUITE T1` … `SUITE T12` (one row each; statuses `PASS | FAIL | SKIPPED(<reason>) | ADVISORY-FAIL`), `UI` (`hermes dashboard`/`hermes serve` driven by agent-browser, screenshots listed), `DESKTOP` (`PASS | FAIL | FAIL(pre-existing: <spec>) | SKIPPED — install_packages: <pkgs>`) — each with an exit code and a log path; extra rows the tester adds (`LIST`, `FOCUSED-PYTEST`, `FULL-PYTEST`) are fine. Anything else → **do not test it yourself**; request a re-run and end the turn:
       ```
       send_message(to="hermes-tester", thread_id="hermes-<req-id>", text="Test re-run request — <fork-slug>#<N> head <sha>: <no report attached | report verdict FAIL | report head <sha7> != PR head <sha7> | missing rows: …>. Reply [Test Report] on this edge; the review resumes on PASS.")
       ```
       This is a fresh delegation (the tester has not written to you on this thread): unmarked first line + explicit `thread_id` (the always-on chain-routing gate refuses a marker-prefixed send without `in_reply_to`). The tester's `[Test Report]` comes back as a reply on your edge — resume at step 3 with THAT report. `hermes-tester` not in your destinations → skip to Synthesize with the must-change `no valid Test Report for head <sha>` → `REQUEST_CHANGES` (the builder owns the tester loop). `DESKTOP=SKIPPED` is valid evidence, not a re-run reason — the report carries the exact `install_packages` request for the operator.
    3. **Pin the head, own worktree only — to READ the diff, not to rebuild it:**
       ```bash
       FORK=https://github.com/{{vars.fork}}   # the fork ({{vars.fork}}), never https://github.com/{{vars.repo}}
       [ -d /workspace/agent/hermes-agent/.git ] || git clone "$FORK" /workspace/agent/hermes-agent
       cd /workspace/agent/hermes-agent && git fetch origin
       gh pr view <N> --repo {{vars.fork}} --json headRefOid,headRefName,baseRefName,isDraft,url --jq '.'   # record HEAD_SHA, BASE; isDraft must be true
       git fetch origin "pull/<N>/head:review/<N>"
       git worktree add /workspace/agent/wt-review-<N> review/<N>
       cd /workspace/agent/wt-review-<N> && git rev-parse HEAD                                          # must equal HEAD_SHA AND the Test Report's head SHA — the verdict binds to it
       ```
       **[MUST NOT]** read, write, or remove any sibling `wt-*` directory (the builder's worktrees live on the same volume). If the head moves mid-review, restart from step 2 — a new head needs a new Test Report, not a re-read of the old one. No `uv sync` here; the venv is created only if step 5 elects a spot-check.
    4. **Scope check first (cheap, decisive):**
       ```bash
       mkdir -p /workspace/agent/reviews
       git diff --name-only origin/<BASE>...HEAD | awk '!/^(plugins\/|website\/docs\/|tests\/)/' > /workspace/agent/reviews/<N>-out-of-scope.txt
       ```
       Every path listed is a core edit. Open the ADR's `## CORE-CHANGE` section: it must cite `{{vars.release_tree}}/<file>:<line>`; open that line in the release tree and confirm it genuinely blocks a plugin and that the diff is the minimal GENERIC widening described (new hook / `ctx` method / config key — not a special case for this plugin). Missing, wrong, or over-broad → record a **must-change** now.
    5. **Evidence = the Test Report, plus at most ONE spot-check.** Copy the `## Results` table verbatim into your notes (it goes into the review and the verdict cites it). Do NOT `uv sync` by default, do NOT run `scripts/run_tests.sh` chunks, do NOT add a base-tree worktree — doctor, the acceptance test, the negative control, the suite, the UI tier and the desktop tier are the tester's rows; re-running them here is the cost this chain exists to remove. You MAY run exactly one command from the table when a row's evidence is thin (missing output tail, absent exit code, or a row that contradicts what the diff shows). Default choice, in this order of cost: `git -C /workspace/agent/wt-review-<N> show --stat HEAD` against the report's file list (free) → `.venv/bin/hermes plugins doctor plugins/<name> --ci` → `scripts/run_tests.sh tests/plugins/test_<plugin>_acceptance.py`. The latter two need the venv: `uv sync --locked --python /usr/bin/python3 --extra dev` in an `Agent` subagent (log `/workspace/agent/build/uv-sync-review-<N>.log`; never `uv python install`; never inside `scripts/run_tests.sh`, which strips the proxy env under `env -i`), then `export HERMES_HOME=/workspace/agent/.hermes-testbed`. Record `spot-check: <cmd> → <exit/result>` or `spot-check: none`. A spot-check that contradicts a PASS row → re-run request (step 2), never a self-run of the remaining rows.
    5b. **Devin Review — second opinion, best-effort (never blocks):**
       ```bash
       mkdir -p /workspace/agent/reviews/<N>-devin
       bash /home/node/.claude/skills/hermes-pr-review-runner/scripts/devin-fetch.sh \
         --url https://github.com/{{vars.fork}}/pull/<N> --out /workspace/agent/reviews/<N>-devin --poll-seconds 45 --max-minutes 20
       ```
       Exit 0 → read `<out>/devin-flags.md` and re-verify every flag against the diff before it becomes a finding (Devin is input, your verdict is your own). Exit 2 (auth-wall) / 3 (timeout) → record `devin: auth-wall|timeout` in the report and continue; exit 1 → record the error, continue. See `/hermes-pr-review-runner`.
    6. **Read the diff with these lenses** (cite the violated rule at its `{{vars.release_tree}}/AGENTS.md:<line>` or `website/docs/developer-guide/plugins/index.md:<line>`): plugin contract — `plugin.yaml` has `manifest_version: 1`, `name`/`version`/`description`, `provides_hooks`/`provides_tools` equal to what `register(ctx)` registers, hook callbacks accept `**kwargs`, tool handlers `(args: dict, **kwargs) -> str` return JSON and never raise, state via `plugin_storage`, settings via `plugins.entries.<id>.settings`; no new `HERMES_*` env for non-secret config; `get_hermes_home()` not `~/.hermes`; behavior-contract tests only (no snapshots / model lists / version literals / enumeration counts / source reading / `~/.hermes` writes; OS markers not bare `skipif`); cross-platform (`shutil.which`, `psutil`, `pathlib`); ruff ASYNC rules in `plugins/**`; deps pinned `>=floor,<next_major` with `uv.lock` regenerated (and a dep change is itself a CORE-CHANGE); prompt-caching untouched (no mid-conversation mutation of context/toolsets/system prompt); one logical change; Conventional Commit; docs under `website/docs/` for user-visible behaviour; PR is a **draft** against the **fork** (never {{vars.repo}}); scope matches the requirement's acceptance criterion — flag scope shrinkage. Cross-check the diff against the report: every test file the diff adds must appear in the report's `ACCEPTANCE`/`SUITE` rows; a plugin dir renamed after the report's head is a stale report (step 2).

    DeepWiki (`mcp__deepwiki__ask_question("NousResearch/hermes-agent", …)`) is advisory for architecture context only; the release tree is the sole citation source. Stay read-only: never push, never edit the PR branch, never comment on GitHub.
  diagnose: |
    **Synthesize** — Mode is always `review`: findings by severity, each with `<file>:<line>` in the PR diff and the rule it violates. The Test Report is evidence you cite, not a finding you re-derive.

    - **must-change** (any one → `REQUEST_CHANGES`): a diff outside `plugins/**`, `website/docs/**`, `tests/**` without a valid ADR `## CORE-CHANGE` citation of `{{vars.release_tree}}/<file>:<line>` (or with a citation that does not actually block a plugin, or a change broader than the generic widening); a plugin special-cased in core; no valid `[Test Report] PASS` bound to the reviewed head when `hermes-tester` could not be reached (when it can, that is a re-run request in Research step 2, not a verdict); a `FAIL` row the report's own verdict rule counts as blocking (the header verdict is then `FAIL` — a re-run case, not a verdict); a spot-check that contradicts a `PASS` row; tests that read source, snapshot enumerations, or write `~/.hermes`; hook callback without `**kwargs` or handler that raises; new `HERMES_*` env var for non-secret config; hardcoded `~/.hermes`; unpinned/unbounded dependency or missing `uv.lock` regen; PR opened against {{vars.repo}} or not a draft; scope shrinkage below the acceptance criterion without an evidenced blocker.
    - **should-change**: missing `website/docs/` page for user-visible behaviour; ruff/ASYNC or footgun findings; cross-platform gaps; missing negative/edge tests; declared-vs-registered manifest drift (doctor warnings quoted in the report); `FLAKY` (pass-on-retry) lines the report records; `ADVISORY-FAIL` (`T5b`/`T6`, LLM-judged), `SKIPPED(<reason>)` suite ids, and a non-blocking `DESKTOP=FAIL(pre-existing: <spec>)` — list them, never promote them to must-change; `DESKTOP=SKIPPED` when the requirement's target surface is desktop + `hermes serve` (the verdict's Next-action must carry the report's exact `install_packages` request — the tier is unverified, not failed); commit hygiene.
    - **nit**: style, naming, comment hygiene (a comment restating the line or narrating change history is a nit-to-should; a concise non-obvious *why* is correct — don't flag it).

    Verdict: `APPROVE` iff zero must-change; else `REQUEST_CHANGES`. Then run `/codex-critique` with `STAGE: CODE_REVIEW` — ARTIFACTS: `git diff origin/<BASE>...HEAD` in `/workspace/agent/wt-review-<N>`, the Test Report path (`/workspace/inbox/<msg-id>/test-report-*.md`), your spot-check result, and your findings draft. Codex is independent: where it disagrees, record both positions under `Disagreements`; your verdict stands but must say why. Codex asking you to "re-run the suite to be sure" is a disagreement to record, not an instruction — the tester's rows are the evidence.
  deliver: |
    **Deliver** — Write the review to `/workspace/agent/reviews/<N>.md` (heredoc; new file), then critique it before it leaves the session.

    Sections, in order: `# Review — <fork-slug>#<N> (round <k>)` with PR URL, **head SHA reviewed**, requirement id, ADR path, **Test Report** (inbox path `/workspace/inbox/<msg-id>/<file>`, the tester's canonical path from the report header, test round, tester msg id); `## Verdict` (`APPROVE` | `REQUEST_CHANGES`); `## Test Report` — the report's verdict line and its `## Results` PASS/FAIL table copied **verbatim**, then `spot-check: <cmd> → <result> | none`; `## Scope check` — table `file → allowed | CORE-CHANGE cited <file:line> | VIOLATION`; `## Findings` — must-change / should-change / nit, each `<file>:<line> — what is wrong, why (rule citation), the fix`; `## Test gaps` — behaviours the diff introduces that no `ACCEPTANCE`/`SUITE` row exercises (these go back to the builder as test requests; the tester's suite ids `T1`–`T12` are fixed, do not invent `T13`); `## Disagreements` (codex vs you, `none` if none); `## References` (release-tree `file:line`). Round 2+ appends a `## Round <k>` block to the same file with the new head SHA and the new Test Report path.

    Then `/codex-critique` with `STAGE: OUTPUT_REVIEW` — ARTIFACTS: `/workspace/agent/reviews/<N>.md` (attested) plus the verdict text you are about to send. Must-fix → revise the review, re-run OUTPUT_REVIEW; any later edit to the file invalidates the attested hash — re-run before Handoff. Optional cleanup of YOUR worktree only: `git -C /workspace/agent/hermes-agent worktree remove /workspace/agent/wt-review-<N>` (there is no base-tree worktree to remove any more — the negative control is the tester's row).
  handoff: |
    **Handoff** — Return the verdict on the builder's edge, as a reply. Both gates require it: the chain-routing gate refuses a marker-prefixed send without `in_reply_to`, and the critique gate releases `[Review Verdict]` only with CODE_REVIEW + OUTPUT_REVIEW recorded and fresh. The verdict MUST cite the Test Report path and its table — a verdict without them is incomplete; a verdict on a missing/FAIL/stale report is not a verdict at all (Research step 2).

    ```
    send_message(in_reply_to=<review-request-id>, text="[Review Verdict] <fork-slug>#<N> (round <k>, head <sha7>)\n\n- **Verdict:** APPROVE | REQUEST_CHANGES\n- **Test Report:** /workspace/inbox/<msg-id>/<test-report-file> — PASS (test round <k>, head <sha7>): DOCTOR <PASS>; ACCEPTANCE <PASS>; NEGATIVE-CONTROL <PASS>; RUFF <PASS>; FOOTGUNS <PASS>; SUITE T1–T12 <PASS | T<n> FAIL | T<n> ADVISORY-FAIL | skipped: <ids>>; UI <PASS>; DESKTOP <PASS | FAIL(pre-existing) | SKIPPED — install_packages: <pkgs>>; spot-check: <cmd → result | none>\n- **Scope:** all in plugins/**,website/docs/**,tests/** | CORE-CHANGE cited {{vars.release_tree}}/<file>:<line> | VIOLATION: <files>\n- **Top concern:** <highest-severity finding, or 'none'>\n- **Next-action:** merge the draft in the fork | address <n> must-change items (see attached review) | operator: install_packages <pkgs> so hermes-tester can run the desktop tier")
    send_file(in_reply_to=<review-request-id>, path="/workspace/agent/reviews/<N>.md")
    ```

    No `to=` — `in_reply_to` resolves the builder's edge exactly (do not `to="parent"` unless the builder is your parent; do not message `hermes-architect` even though the lineage rule may allow it — ADR concerns go to the builder, who relays). The only message you ever send to `hermes-tester` is the unmarked re-run request in Research step 2 — never a verdict, never test instructions. Never push, never edit the PR, never comment on GitHub, never mark the PR ready. Then stop; a round-2 request re-enters at Research step 1 with the new request, a fresh `git fetch` of the new head, and a NEW Test Report for that head (the old report is stale by definition). Do not answer status echoes.

# hermes-review

## Hermes deltas

- Mode is always `review`. The deliverable is `/workspace/agent/reviews/<N>.md`, not the base `reports/` path.
- **Intake is the builder's review request plus `hermes-tester`'s `[Test Report] PASS`** for the PR head: the report file arrives attached (`/workspace/inbox/<msg-id>/test-report-*.md`; canonical path on the tester's side `/workspace/agent/reports/<thread-id>/`), and the head SHA you check out in your OWN worktree (`/workspace/agent/wt-review-<N>`) must equal the report's head SHA — the verdict binds to both.
- **Adversarial on the diff, not on the evidence.** No baseline rebuild, no `scripts/run_tests.sh` chunks, no negative-control worktree, no `uv sync` by default — doctor, acceptance, negative control, suite `T1`–`T12`, UI and desktop tiers are the tester's rows. At most ONE spot-check command, only when a row's evidence is thin. Report missing / `FAIL` / stale (head mismatch) → an unmarked re-run request to `hermes-tester` on the same `thread_id`, never self-testing; tester unreachable → `REQUEST_CHANGES` with must-change `no valid Test Report`.
- Plugin-first boundary is a hard gate: any diff outside `plugins/**`, `website/docs/**`, `tests/**` without a valid ADR `## CORE-CHANGE` citation of `{{vars.release_tree}}/<file>:<line>` is a must-change → `REQUEST_CHANGES`.
- Read-only role: no `git push`, no PR edits, no GitHub comments. `[Review Verdict]` is always a reply (`in_reply_to=<review-request-id>`) on the builder's edge and MUST cite the Test Report path and its PASS/FAIL table; `DESKTOP=SKIPPED` is reported with the exact `install_packages` request, never as a failure.
